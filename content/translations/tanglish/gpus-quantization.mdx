## Idhu enna

Unga sondha GPU-la oru language model-a run panradhu perumbaalum **memory** pathina kelvi thaan. Moonu vishayangal adhukkaaga potti podudhu, innoru vishayam speed-a mudivu pannudhu:

- **Weights.** 16-bit precision-la ovvoru parameter-um 2 bytes edukkum; adhanaala oru 14B model edhuvum seiya aarambikkiradhukku munnaadiye sumaar 28 mudhal 30 GB venum.
- **KV cache.** Ovvoru layer-layum ovvoru token-kkum, model rendu vectors-a store pannudhu: oru key, oru value. Indha **KV cache** ovvoru request-oda neelathodayum, ore nerathula run aagura requests ennikkaiyodayum valarum.
- **Working space.** Intermediate results (activations), CUDA runtime, engine buffers. Indha lesson adhukkaaga GPU-la sumaar 10%-a spare-aa vachukkudhu.
- **Speed.** Ovvoru pudhu token-kkum ella weights-aiyum memory-la irundhu oru thadavai padikkanum. Adhanaala **memory bandwidth**, adhaavadhu GPU oru second-kku ethana gigabytes padikka mudiyum-ngradhu, podhuvaa raw compute-a vida generation speed-a adhigamaa kattuppaduthum.

**Quantization** weights-aiyum, sila neram cache-aiyum, kuraivaana bits-la store pannudhu, 16-kku badhilaa 8 allathu 4 maadhiri. Cache-kku adhiga memory minjum, oru token-kku kuraivaana bytes padikkappadum, adhanaala generation perumbaalum vegamaagum. Cost ennanna konjam quality izhappu; adhai unga sondha task-la measure pannanum.

NVIDIA L40S maadhiri oru 48 GB GPU, 40 layers, 8 key-value heads, head size 128 irukkura oru 14B model-a (Qwen3-14B-oda shape) serve pannumbodhu enna effect-nu paarunga. 10% spare poga, sumaar 43 GB use pannalaam; ovvoru request-um 4,000 tokens vachirukku.

| Precision | Weights | KV cache-kku micham | 4,000 tokens-oda requests |
|---|---|---|---|
| 16-bit weights, 16-bit cache | Sumaar 30 GB | Sumaar 13 GB | Sumaar 20 |
| 4-bit weights, 16-bit cache | Sumaar 10 GB | Sumaar 33 GB | Sumaar 50 |
| 4-bit weights, 8-bit cache | Sumaar 10 GB | Sumaar 33 GB | Sumaar 100 |

Rule idhu thaan: **weights entry cost-a fix pannudhu; ethana users fit aavaanga-nnu cache mudivu pannudhu.**

Indha lesson-la, Hyderabad-la oru analytics firm oru self-hosted extraction model-kku GPUs-a size panradhai follow pannuvom.

## Idhu eppadi work aagudhu

### Weights

Weights-kkaana memory ≈ parameters × oru parameter-kkaana bytes.

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B mudhal 8B | Sumaar 14 mudhal 16 GB | Sumaar 7 mudhal 9 GB | Sumaar 4 mudhal 6 GB |
| 14B | Sumaar 28 mudhal 30 GB | Sumaar 14 mudhal 16 GB | Sumaar 8 mudhal 10 GB |
| 32B | Sumaar 64 GB | Sumaar 32 mudhal 34 GB | Sumaar 18 mudhal 20 GB |
| 70B | Sumaar 140 GB | Sumaar 70 GB | Sumaar 37 mudhal 40 GB |

4-bit yen oru parameter-kku arai byte-a vida adhigam? Weights-oda ovvoru chinna group-um (perumbaalum 128) oru scale-aiyum (perumbaalum oru zero point-aiyum) store pannudhu; idhu oru weight-kku sumaar 0.15 bits serkkudhu. Adhoda input embeddings-um output layer-um perumbaalum 16-bit-laye irukkum: periya vocabulary irukkura oru 8B model-kku, adhu sumaar 1 billion parameters, adhaavadhu 2 GB. Plan panradhukku munnaadi checkpoint-oda unmaiyaana file size-a check pannunga.

### KV cache

Ovvoru token-kkum, ovvoru layer-um ovvoru **key-value head**-kkum oru key, oru value store pannudhu:

Oru token-kkaana cache = 2 × layers × key-value heads × head size × oru value-kkaana bytes

Numbers-a model-oda `config.json`-la irundhu padinga: `num_hidden_layers`, `num_key_value_heads`, `head_dim` (allathu `hidden_size`-a `num_attention_heads`-aala vaguthadhu). Perumbaalaana modern models **grouped-query attention** use pannudhu: niraiya attention heads konjam key-value heads-a share pannudhu. Oru common 8B shape-la 32 attention heads irukku, aanaa 8 key-value heads mattum thaan; adhanaala attention heads-a use pannaa unga estimate naalu madangu perusaa varum.

Appuram **tokens in flight**-aala perukkunga: peak active requests × oru request-kkaana tokens. Peak-a oru load test-la irundho traffic logs-la irundho edunga, orupodhum average-a illa.

Rendu gotchas. Qwen3.5 maadhiri **hybrid** models, sumaar naalu layers-la onnula mattum thaan full attention use pannudhu, adhanaala andha layers-a mattum ennunga. Adhoda **mixture-of-experts** models-kku avangaloda ella experts-kkum memory venum, ovvoru token-um sila experts-a mattum use pannaalum.

### Andha memory-a engine enna pannudhu

vLLM maadhiri serving engines rendu ideas use pannudhu. **PagedAttention** ovvoru request-oda cache-aiyum chinna blocks-la store pannudhu, request valara valara mattum blocks serkkudhu; adhanaala oru chinna request, saathiyamaana miga neelamaana request-kkaana idathai reserve pannaadhu. **Continuous batching** ovvoru step-layum, matha requests mudiya mudiya, pudhu requests-a running batch-la serkkudhu; adhanaala GPU busy-aave irukkum. Idhu rendume memory-a uruvaakkaadhu, adhanaala mela irukkura kanakku thaan limit.

Start-up-la, vLLM cache size-a tokens-la log pannudhu, unga maximum request length-kkaana "maximum concurrency"-aiyum. Andha line-a unga estimate kooda compare pannunga; unga setup-kku adhu thaan unmai. vLLM v0.34.0-la irundhu, `--gpu-memory-utilization` set pannalainnaa ella free memory-aiyum use pannum; adhanaala vera oru process GPU-a share pannumbodhu mattum oru share-a set pannunga.

### Prefill-um decode-um

Ovvoru request-kkum rendu phases irukku, ovvonnukkum vera vera limits.

- **Prefill** muzhu prompt-aiyum ore thadavaiyila padichu cache-a nirappudhu. Oru prompt token-kku sumaar 2 × parameters operations pannudhu: oru 14.8B model-kkum oru 6,000-token prompt-kkum, sumaar 180 trillion. Prefill-a **compute** kattuppaduthudhu, adhu **time to first token**-a mudivu pannudhu; adhanaala neelamaana prompts-na first tokens medhuvaa varum.
- **Decode** oru step-kku oru token ezhudhudhu. Ovvoru step-um ella weights-aiyum ovvoru request-oda cache-aiyum padikkudhu, aanaa oru byte-kku konjam thaan maths pannudhu. Adhai **memory bandwidth** kattuppaduthudhu, adhu **tokens per second**-a mudivu pannudhu.

Oru request-kkaana quick ceiling: bandwidth ÷ weights-oda bytes. Oru L40S 864 GB/s padikkum; adhanaala oru 10 GB 4-bit model oru request-kku adhigapatcham sumaar 86 tokens per second varai pogalaam; oru 30 GB 16-bit model adhigapatcham sumaar 29. Unmaiyaana numbers idhai vida kuraivaa irukkum. Serving affordable-aa irukka kaaranam batching thaan: weights-a oru thadavai padichaa batch-la irukkura ella requests-kkum serve aagum; adhanaala compute allathu cache memory theerndhu pora varai, batch size kooda motha throughput-um erum. Vilai ennanna ovvoru user-um oru token-kku konjam adhigamaa wait pannanum; adhanaala concurrency-a unga latency budget-a paarthu tune pannunga.

### Quantization formats

- **FP8** (8-bit floating point). Perumbaalaana models-kku kittathatta 16-bit quality, paadhi memory, FP8 units irukkura GPUs-la vegamaana maths. Perumbaalum mudhalla try panna vendiyadhu idhu thaan.
- **AWQ, GPTQ** (4-bit integers, weights mattum). Weight memory-la sumaar kaal pangu, kooda mela sonna overheads, midhamaana quality izhappoda. Erkanave quantize panna oru checkpoint-a download pannunga, mudinjaa model maker-e quantize pannadhai.
- **NVFP4, MXFP4** (4-bit floating point). Blackwell GPUs-la vegamaa irukkum; innum pudhusu, kuraivaana alavula thaan test aagiyirukku.
- **bitsandbytes NF4.** Transformers-la load time-la quantize pannudhu. Experiments-kkum QLoRA-kkum easy, aanaa serve panna innum medhuvaa irukkum.
- **GGUF.** llama.cpp-oda file format; Ollama, LM Studio idhu mela thaan build aagiyirukku; laptops, CPUs, Apple Silicon-kku. Oru Q4_K_M file oru weight-kku sumaar 4.8 mudhal 4.9 bits use pannudhu, adhanaala oru 8B model sumaar 5 GB. Speed bandwidth-a follow pannum: oru laptop 80 GB/s-la memory padichaa, sumaar 16 tokens per second thaan ceiling.
- **8-bit KV cache.** Cache-a FP8-la store pannaa adhu paadhiyaagum. Matha endha change maadhiriyum idhoda quality-yaiyum measure pannunga.

Fit aagura miga uyarndha precision-la irundhu keezhe irangunga: 16-bit, appuram FP8, appuram 4-bit. Ovvonnukkum, unga eval-aiyum oru chinna load test-aiyum run panni, peak-la quality, memory, speed-a record pannunga. Unga client ezhuthuppoorvamaa ethukkura quality izhappu irukkura options-la miga cheap-aanadhai thaerndhedunga.

### Code-la oru memory planner

```python
def memory_plan(cfg, params_billion, weight_bits=16, kv_bits=16,
                context_tokens=4000, concurrent=20, gpu_gb=48, spare=0.10):
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights_gb = params_billion * weight_bits / 8          # rough: real 4-bit files are larger
    kv_token_mb = 2 * cfg["num_hidden_layers"] * kv_heads * head_dim * kv_bits / 8 / 1e6
    kv_gb = kv_token_mb * context_tokens * concurrent / 1e3
    usable = gpu_gb * (1 - spare)
    fits = weights_gb + kv_gb <= usable
    max_requests = int((usable - weights_gb) * 1e3 / (kv_token_mb * context_tokens))
    return round(weights_gb, 1), round(kv_token_mb, 3), round(kv_gb, 1), fits, max_requests

# The shape of a common 8B model; in real use, load the dict from config.json
cfg = {"num_hidden_layers": 32, "num_attention_heads": 32, "num_key_value_heads": 8, "head_dim": 128}
print(memory_plan(cfg, 8, gpu_gb=24))                  # (16.0, 0.131, 10.5, False, 10)
print(memory_plan(cfg, 8, weight_bits=8, kv_bits=8, gpu_gb=24))  # (8.0, 0.066, 5.2, True, 51)
```

16-bit-la, 4,000 tokens-oda 20 requests-kku 16 GB weights-kku mela sumaar 10.5 GB cache venum: oru 24 GB card-kku idhu romba adhigam, adhu 10 requests-a mattum thaan vachukkum. 8-bit-la avai fit aagum; aanaa embeddings 16-bit-laye irukkuradhaala, unmaiyaana FP8 file sumaar 9 GB.

### Oru quantized model-a load panni serve panradhu

Transformers-la quick experiments-kku:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("your-org/your-8b-instruct",
                                             quantization_config=bnb, device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

Serving-kku, fast quantized kernels irukkura oru engine-a use pannunga. vLLM oru quantized checkpoint-oda config-la irundhu method-a padichukkum:

```bash
vllm serve your-org/your-14b-instruct-awq --max-model-len 8192 --kv-cache-dtype fp8
```

Oru 16-bit model-a load time-la FP8-kku quantize panna, vLLM v0.34.0 `--quantization fp8_per_tensor` use pannudhu; verum `fp8` inime idhai pannaadhu. `--max-model-len` oru request-oda neelathai cap pannudhu; unga users unmaiyila anuppura alavukku adhai set pannunga.

### Quality izhappai measure panradhu

Ovvoru precision-layum golden set-a run panni, overall mattum illaama ovvoru slice-kkum compare pannunga. Quantization podhuvaa mudhalla neelamaana reasoning, maths, code, avvalavaa common illaadha languages-a thaan baadhikkum; adhanaala Hindi, Telugu allathu Tamil cases-a English-la irundhu thaniyaa score pannunga. Mukkiyamaana ovvoru slice-um othukkitta limit-kkulla irundhaa mattum thaan oru precision-a vachukkunga.

## Oru worked example

Hyderabad-la oru analytics firm, 200 staff-kkaaga invoices-la irundhu fields-a extract panra oru model-a self-host panna virumburaanga. Prompts-um replies-um serndhu 6,000 tokens varai pogum. p95 time to first token 3 seconds-kku keezhe irukkanum. Keezhe irukkura quality scores-um latencies-um method-a kaatturadhukkaana illustrative numbers; memory figures kanakku pottadhu.

**1. Peak-a measure pannunga.** Oru busy naaloda logs-a replay pannaa **80 active requests**-la peak aagudhu (average sumaar 35). 80-kku size pannunga.

**2. Model.** 14.8 billion parameters, 40 layers, 8 key-value heads, head size 128 irukkura oru 14B instruct model. Oru token-kkaana cache: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes, sumaar 0.16 MB. Oru 6,000-token request sumaar 0.98 GB vachukkum; peak-kku sumaar 79 GB cache venum.

**3. Original proposal.** 16-bit-la tensor parallelism-oda rendu H100 80 GB GPUs. Use pannakkoodiya memory 2 × 72 = 144 GB; weights sumaar 30 GB edukkum, sumaar 114 GB minjum, adhaavadhu sumaar 116 requests. Fit aagudhu, aanaa oru mani nerathukku 2 × ₹362 = ₹724 aagum, oru GPU fail aanaa service ninnudum.

**4. Quantize pannunga.** Maker-oda 4-bit AWQ checkpoint sumaar 10 GB. 500 unmaiyaana invoices-la field accuracy: 16-bit-la 95.1%, 4-bit-la 94.6%, kooda FP8 cache-um serthaa 94.5%. Client-oda limit 94.0%, adhanaala rendume pass.

**5. L40S cards-la fit pannunga.** Oru L40S-la sumaar 43 GB use pannalaam. 4-bit weights-oda, 33 GB minjum. 16-bit cache-oda, adhula 6,000 tokens-oda 33 requests vaikkalaam; adhanaala peak-kku 3 GPUs venum, spare-aa naalaavadhu onnu. FP8 cache-oda, sumaar 67 vaikkalaam; adhanaala rendu GPUs peak-a (134) thaangum, onnu fail aanaa moonaavadhu onnu service-a oda vaikkum.

**6. Speed-a check pannunga.** Moonu L40S cards-la 80 concurrent requests-oda load test pannaa, p95 time to first token 1.8 seconds, budget-kkulla. Ovvoru user-oda tokens-um H100s-a vida medhuvaa varum, yenna avaikku sumaar naalu madangu bandwidth irukku; aanaa target meet aagudhu.

## Podhuvaa panra thappugal

- **Weights-kku mattum size panradhu.** Ethana users fit aavaanga-nnu peak-la irukkura cache thaan mudivu pannudhu.
- **Average traffic-la irundhu size panradhu.** Measure panna peak-a use pannunga, illainnaa miga busy-aana kaalaiyila service fail aagum.
- **Cache formula-la key-value heads-kku badhilaa attention heads-a use panradhu,** allathu 2-ngra factor-a vittudradhu.
- **4-bit-a oru parameter-kku sariyaa arai byte-nu eduthukkiradhu.** Scales-um 16-bit embeddings-um sumaar 10 mudhal 50% serkkum.
- **Slice vaariyaa evals illaama quantize panradhu.** Oru English-only average, Indhiya mozhigal, maths, code-la irukkura izhappugalai maraichudum.
- **Ore GPU-la fit aagura model-a split panradhu.** Copies innum simple-aanadhu, innum nallaa scale aagum, failures-a thaangum.
- **FP8 ella idathulayum fast-nu ninaikkiradhu.** A100-la FP8 units illa; GPU generation-a check pannunga.
- **Thevaiyai vida romba adhigamaa maximum context-a set panradhu.** Oru periya request niraiya chinna requests-a veliye thallidalaam.

## GPUs pathi yosikka thevaiyillaadha samayangal

- **Oru hosted API-aiyo** client-oda cloud model service-aiyo use pannumbodhu.
- **CPUs-la chinna models,** embedding models, classifiers, allathu oru laptop-la 4-bit GGUF demo maadhiri.
- **Kuraivaana allathu thideer-nu eri irangura volume,** anga maasam muzhukka rent panna oru GPU, per token pay panradhai vida adhigamaa selavaagum.

## Demo-la irundhu production-kku

- **Memory-a plan pannunga**: weights, peak cache, working space-kku; engine-oda start-up log-la adhai confirm pannunga.
- **Golden set-a run pannunga**: ovvoru precision change-layum, language, task vaariyaa.
- **Unmaiyaana GPUs-la load test pannunga**: scale-la rent panradhukku munnaadi, peak-la first-token time-aiyum errors-aiyum paathukkitte.
- **Kuranjadhu oru spare GPU-a vachukkunga**: oru failure-o upgrade-o service-a niruthaama irukka.
- **Production-la cache usage-aiyum queue length-aiyum monitor pannunga**, cache nirambradhukku munnaadiye alert pannunga.

## Practice pannunga

Hugging Face-oda quantization posts-aiyum vLLM PagedAttention post-aiyum padinga.

1. 7B, 14B, 32B, 70B models-kku 16, 8, 4 bits-la weight memory-a kanakku podunga; appuram oru 4-bit checkpoint-oda unmaiyaana file size-a paarthu, vithiyaasathai explain pannunga.
2. Oru open model-oda `config.json`-a thiranga. Adhoda layers, key-value heads, head size-a kandupidichu, 4,000 tokens-oda 20 requests-kku 16-bit-layum 8-bit-layum cache-a estimate pannunga.
3. Rendu models-la edhu 4,000 tokens-la 10 users-kku oru 24 GB GPU-la fit aagum-nu mudivu panna `memory_plan`-a use pannunga.
4. Oru GPU-la, allathu llama.cpp irukkura oru laptop-la, oru chinna model-a rendu precisions-la run panni, memory, speed, unga eval score-a compare pannunga.
