## Idhu enna

**LLM gateway**-naa unga applications-kkum model providers-kkum naduvula irukkura oru service. Applications ovvoru request-aiyum ore API format-la gateway-ku anuppum. Gateway adhai sariyaana provider, model-ku forward pannum, shared velaiyai ovvoru app-laiyum thanithaniyaa seiyaama ore thadavai handle pannum:

- **Routing**: indha request-a endha model, provider serve pannanum.
- **Failover**: oru provider error kudutthaa, timeout aanaa illa ungalai rate-limit pannaa enna try panradhu.
- **Keys, access**: teams-ku gateway keys kidaikkum; real provider keys gateway-la mattum irukkum.
- **Rate limits, budgets**: ovvoru team, feature illa user-kkum.
- **Logging, cost**: ovvoru request-um adhoda tokens, cost, latency-oda, ore idathula.

Indha lesson Bengaluru-la oru fintech-a follow pannudhu; anga naalu teams-oda anju AI features ovvonnum thannoda sondha keys-oda providers-a neradiyaa call pannichu.

```flow
title: One gateway in front of every provider
Chatbot -[key chatbot]-> Gateway, 2 or more instances
Claims extraction -[key claims]-> Gateway, 2 or more instances
Nightly summaries -[key batch]-> Gateway, 2 or more instances
Gateway, 2 or more instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails, cool-down]-> Model X, Hyderabad
Model X, Hyderabad -[fails]-> Fallback alias: approved model Y, India
```

Ovvoru key-kkum thani rate limit, budget irukku. Gateway forward panradhukku munnaadi avatrai check pannum, result-a log pannum, provider keys-a oru secret store-la vechukkum.

### Gateway kidaikka moonu vazhigal

| Vagai | Udhaaranangal | Eppo therndhedukkalaam |
| --- | --- | --- |
| Self-hosted, open source | LiteLLM proxy (MIT licence) | Data unga sondha cloud account, region-laye irukkanum, database-oda oru service-a ottakkoodiya platform team ungakitta irukku |
| Unga cloud-oda API management | Azure API Management (adhoda `llm-token-limit` policy), Google Apigee (adhoda LLM token quota policy) | Matha APIs-ku yerkanave andha cloud-oda API management-a use pannureenga, perumbaalum andha cloud-oda models-a dhaan call pannureenga |
| Oru vendor-oda managed gateway | Pala vendors ungalukkaaga onnai host pannuraanga | Neenga chinna team, infrastructure otta yaarum illa, vendor-oda data processing locations unga data-ku allowed |

Mudivu podhuvaa rendu kelvigalla vandhu nikkum. Unga data enga process aagalaam? Raathiri gateway odanja yaarai ezhuppuvaanga? Managed gateway ovvoru prompt-aiyum paakkum, adhanaala ellaathukkum munnaadi adhu data-va enga process pannudhunnu check pannunga.

## Idhu eppadi velai seiyudhu

### Ore interface, model aliases

Perumbaalaana gateways OpenAI-style chat format-a yethukkittu, ovvoru provider-kkum adhai translate pannum. Apps orupodhum real model-oda perai sollaadhu. Avai `chat-default` maadhiri oru **alias**-a call pannum, gateway adhai oru real model-ku map pannum. Ellaa apps-aiyum pudhu model-ku upgrade panradhu gateway config-la review panna ore oru line aayidum, mudhalla unga golden set-la test panni.

### Failover-oda rendu layers

Nalla failover-la rendu layers irukku, avatrai manasula thanithaniyaa vechukkiradhu udhavum.

1. **Ore alias-ku pinnaadi deployments.** Adhe model rendu idathula, udhaaranamaa Mumbai, Hyderabad. Onnu fail aanaa gateway innoru deployment-la retry pannum.
2. **Oru fallback alias.** Vera oru approved model; mudhal alias-oda ellaa deployments-um fail aanaa mattum dhaan use aagum.

Fail aagura oru deployment ovvoru request-aiyum slow pannak koodaadhu. Idhai oru **cool-down** (circuit breaker-nnum solluvaanga) handle pannudhu. Konja nerathukkulla romba adhigamaa failures vandhaa, gateway andha deployment-a oru fixed nerathukku skip pannum. Requests mudhalla timeout-ku kaathirukka vendiyadhilla. Cool-down mudinjadhum gateway andha deployment-a thirumba try pannum.

### Oru gateway configuration

LiteLLM-oda proxy oru common open-source choice; matha gateways idhe ideas-a vera syntax-la use pannum. Ore file-la aliases, deployments, retries, cool-downs, fallback ellaam define aagudhu. LiteLLM 1.111.0-la check pannadhu.

```yaml
# gateway.yaml: the whole gateway in one reviewed file
model_list:
  # Alias chat-default: the same model deployed in two Indian regions.
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>             # in-Region ID or India profile, never APAC or global
      aws_region_name: ap-south-1           # Mumbai
      order: 1                              # used first while healthy
      timeout: 30                           # seconds, normal calls
      stream_timeout: 10                    # seconds, streaming calls
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>
      aws_region_name: ap-south-2           # Hyderabad
      order: 2                              # used when Mumbai fails or cools down
      timeout: 30
      stream_timeout: 10
  # Fallback alias: another provider, also in India, approved and tested on the evals.
  - model_name: chat-backup
    litellm_params:
      model: vertex_ai/<model id>
      vertex_project: os.environ/GCP_PROJECT
      vertex_location: asia-south1          # Mumbai
      timeout: 30

router_settings:
  num_retries: 2                            # retries on 429s and server errors
  allowed_fails: 3                          # more than 3 failures in a minute starts a cool-down
  cooldown_time: 60                         # seconds a cooling deployment is skipped
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL     # keys, limits, budgets and spend live here
```

`litellm --config gateway.yaml --port 4000`-oda adhai start pannunga. Load balancer-ku pinnaadi rendu illa adhukku mela instances ottunga, ellaame ore database-a point pannanum.

**Bedrock-la oru region trap.** Bedrock-oda cross-Region inference profiles, neenga call panra Region-ku veliya prompts-a process pannalaam. APAC profile Asia Pacific-kkulla irukkum, India-kkulla illa; global profile support aagura endha commercial Region-aiyum use pannalaam. Sila Claude models-ku Bedrock-la ippo oru India geographic profile irukku, adhu Mumbai, Hyderabad naduvula mattum route pannum. Data India-la dhaan process aaganumnaa, andha profile-aiyo oru in-Region model ID-aiyo use pannunga, mudhalla Bedrock Regional availability table-a check pannunga: ellaa model-um Hyderabad-la in-Region-aa kidaikkaadhu.

### Apps alias-a call pannum, provider-a illa

Endha OpenAI-compatible client-um velai seiyum. Request-a unmaiyila edhu serve pannuchunnu paakka response headers-a padinga:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=os.environ["GATEWAY_URL"], api_key=os.environ["CHATBOT_KEY"])

raw = client.chat.completions.with_raw_response.create(
    model="chat-default",                       # the alias, never a provider model name
    messages=[{"role": "user", "content": "Explain my last card statement in two lines: ..."}],
)
reply = raw.parse()
print(reply.choices[0].message.content)
print("model group:", raw.headers.get("x-litellm-model-group"))      # chat-backup means it fell back
print("fallbacks:", raw.headers.get("x-litellm-attempted-fallbacks"))
print("cost in USD:", raw.headers.get("x-litellm-response-cost"))
```

### Rate limits, budgets irukkura keys

Admin ovvoru feature-kkum oru virtual key create pannuvaanga. Virtual key-naa gateway issue panra oru key; adhu real provider keys-ku map aagum, andha keys-a team orupodhum paakkaadhu.

```bash
curl -s "$GATEWAY_URL/key/generate" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"key_alias": "chatbot", "models": ["chat-default", "chat-backup"],
       "rpm_limit": 600, "tpm_limit": 200000,
       "max_budget": 400, "budget_duration": "30d",
       "metadata": {"team": "support", "feature": "chatbot", "owner": "platform-lead"}}'
```

`rpm_limit` indha key-ku oru nimishathukku requests-a cap pannudhu, `tpm_limit` oru nimishathukku tokens-a cap pannudhu. Fallback alias-aiyum `models`-la list pannunga: testing-la, `chat-default` mattum allowed aana oru key-ku backup-ku badhilaa oru plain error dhaan kidaichudhu. Key-a revoke pannaa, vera edhaiyum rotate pannaama oru feature-a mattum cut pannalaam. Indha setup-a test pannappo therinja moonu behaviours therinjukkiradhu nalladhu:

- **Rate limit-um budget-um vera vera maadhiri fail aagum.** `rpm_limit`-a thaandinappo HTTP 429 vandhuchu, adhai client konjam pause panni retry pannalaam. Budget selavaayittappo `budget_exceeded` type-oda HTTP 422 vandhuchu. Adhai retry pannaa neram dhaan veenaagum, adhanaala clients adhai final-aa eduthukkittu oru aalukku alert pannanum.
- **Budgets thoraayamaanavai.** Gateway ovvoru request-kkum munnaadi budget-a check pannudhu, adhanaala line-a thaandura request kooda complete aagum. 0.05 dollar budget-oda oru test-la, requests refuse aaguradhukku munnaadi spend 0.065 varai pochu. Unmaiyila neenga afford pannakkoodiyadhai vida cap-a konjam keezha vainga.
- **Reset date-a check pannunga.** Period innaikku aarambikkudhunnu ninaichukkaama, key create panna appuram `/key/info`-la irundhu `budget_reset_at`-a padinga. Budgets US dollars-la irukku, adhanaala unga reports-la oru stated rate-la rupaaikku convert pannunga.

### Provider-oda quota-va niyaayamaa pangidradhu

Unga provider ovvoru model-kkum oru quota tharuvaanga, udhaaranamaa Mumbai-la oru nimishathukku ithanai tokens. Ellaa keys-um adhai share pannum. Rule: **quota kidaikkaama pogave koodaadha features-oda limits-a koottinaa provider quota-va vida kuraivaa, headroom-oda irukkanum.** Batch jobs-ku chinna limit, avai raathiri odum, 429s-la kaathirukkum. Per-key limits illainnaa, mudhalla busy aagura job muzhu quota-vaiyum eduthukkum, "provider up-aa dhaan irukku"-naalum customer chatbot fail aagum.

### Fallback edge cases

Production-la gateways fail aaguradhu fallbacks-la dhaan. Ivatrukku plan pannunga:

- **Streams.** Mudhal token varradhukku munnaadi oru stream fail aanaa, gateway adutha deployment-a try pannalaam, user-ku theriyave theriyaadhu; LiteLLM ippadi dhaan pannudhu. User paadhi answer-a paatha appuram switch panna, answer-a restart pannanum illa rendu models-oda text-a ottanum. Enna kaattanumnu app-laye mudivu pannunga, udhaaranamaa "answer paadhiyila ninnuduchu, retry pannavaa?".
- **Tool calls.** Oru request-oda tool call yerkanave payment illa email maadhiri side effects irukkura edhaavadhu onnai ottiduchunnaa, adhai orupodhum retry pannaadheenga. Andha tools-a idempotency key-oda repeat panna safe-aa aakkunga, illainnaa avatrai retry pannaadheenga.
- **Prompt caching.** Provider prompt caches unga kooda nagaraadhu. Fallback nadakkumbodhu, ovvoru request-um neelamaana system prompt-ku full price-um full latency-um kudukkum, adhanaala outage nadakkumbodhu cost-um time to first token-um egirumnu edhirpaarunga.
- **Format, tool-call shape.** Backup model JSON illa tool calls-a konjam vera maadhiri format pannalaam. Feature-oda evals-a fallback alias-la ottunga, adhoda output-la parser-a test pannunga.
- **Fall back aagak koodaadha errors.** Malformed request ellaa model-laiyum fail aagum. Fall back panradhu latency-aiyum cost-aiyum dhaan koottum. Timeouts, 429s, server errors-ku fall back pannunga.
- **Odanja key-a maraikkira fallbacks.** Oru test-la, primary-la irundha thappaana key 401 return pannuchu, gateway adhai retry pannala, udane fall back pannichu. Users-ku endha prachanaiyum theriyala. Errors-ku mattum illaama, oru alias-oda fallback rate yerumbodhum alert pannunga.

### Try it: fallback chain-la cool-downs

Indha simulation-la request 3-la irundhu request 12 varai Mumbai outage irukku. Cool-down eppadi requests Mumbai-kaaga kaathirukkiradhai niruthudhu, romba neelamaana cool-down Mumbai sariyaana appuramum adhai eppadi skip pannikkitte irukkudhunnu paarunga.

```python
import random

random.seed(7)
ALLOWED_FAILS = 2      # cool down after more than this many failures
COOLDOWN = 5           # requests to skip a cooling deployment
fails = {"mumbai": 0, "hyderabad": 0, "backup": 0}
cooling_until = {"mumbai": 0, "hyderabad": 0, "backup": 0}

def call(deployment, t):
    # Mumbai has an outage from request 3 to request 12.
    if deployment == "mumbai" and 3 <= t <= 12:
        raise TimeoutError("timed out")
    if random.random() < 0.05:
        raise TimeoutError("timed out")
    return deployment

def gateway(t, chain=("mumbai", "hyderabad", "backup")):
    tried = []
    for d in chain:
        if t < cooling_until[d]:
            continue                       # skip without waiting for a timeout
        try:
            served = call(d, t)
            fails[d] = 0
            return served, tried
        except TimeoutError:
            tried.append(d)
            fails[d] += 1
            if fails[d] > ALLOWED_FAILS:
                cooling_until[d] = t + COOLDOWN
                fails[d] = 0
    return "error", tried

for t in range(16):
    served, tried = gateway(t)
    note = f"(waited on {', '.join(tried)})" if tried else ""
    print(f"request {t:2}: served by {served:9} {note}")
```

Requests 3 mudhal 5 varai ovvonnum Mumbai timeout-kaaga kaathirukkum. Appuram Mumbai cool down aagudhu, requests 6 mudhal 9 varai neraa Hyderabad-ku pogum. Request 8 rendaavadhu layer-a kaattudhu: Hyderabad-la oru random timeout varudhu, adhanaala backup answer pannudhu. Request 10-la Mumbai innum down-aa irukkumbodhe cool-down mudiyudhu, adhanaala requests 10 mudhal 12 varai thirumba adhukkaaga kaathirukkum, rendaavadhu cool-down aarambikkum. Request 13-la irundhu Mumbai thirumba vandhududhu, aanaa adhu innum cool down aagittu irukkiradhaala use aagaadhu. Timeouts-ku kaathirukkiradhukkum oru recovery-a miss panradhukkum idaiyila irukkura trade-off-a paakka `COOLDOWN = 2`, `ALLOWED_FAILS = 0` try pannunga.

### Region-aware routing, logs

Indian personal data-ku, andha features use panra aliases Indian-region deployments-a mattum dhaan point pannanum. Matha regions-a use panna allowed aana features-ku thani alias vechukkonga. Ovvoru call-oda alias, deployment, region-a log pannunga, appo rule follow aachunnu oru audit confirm pannalaam. Gateway-oda logs-la personal data-va mask pannunga: adhu ovvoru prompt-aiyum paakkudhu, adhanaala mask pannaadha logs adhai ungaloda migapperiya sensitive data store aakkidum.

### Oru gateway-oda cost

Adhu otta, secure panna, available-aa vechukka vendiya innoru service, ovvoru AI feature-um adhai nambiyirukku. Adhoda sondha overhead-a measure pannunga: adhe set of requests-a neradiyaavum gateway vazhiyaavum anuppi, median, slow (p95) latency-a compare pannunga, mukkiyamaa streams-ku time to first token. Adhai unga apps-ku pakkathulaye vainga, adhoda error rate-aiyum database-aiyum monitor pannunga, documented emergency path onnu vechukkonga, udhaaranamaa oru critical feature-a neraa adhoda provider-ku anuppura feature flag.

## Oru worked example

Bengaluru fintech-la naalu teams-oda anju AI features irukku. Ovvoru team-um thannoda sondha provider keys-a vechirukku, finance-ku oru periya monthly bill mattum theriyudhu. Keezha irukkura numbers oru typical rollout-oda illustration dhaan, measure panna results illa.

**Trigger.** Oru provider outage customer chatbot-a sumaar 50 nimisham down pannidichu. Adhe maasathula, oru nightly statement-summary job kaalai varaikkum neendu odi shared token quota-la perumbagudhiyai use pannidichu, adhanaala chatbot rate-limit errors-um return pannuchu.

**Setup.** Platform team company-oda Kubernetes cluster-la gateway-a rendu instances-aa deploy pannudhu.

- **Keys.** Ovvoru feature-kkum team, feature tag potta thani gateway key. Provider keys gateway-oda secret store-ku pogudhu, rotate pannappadudhu. Pazhaya direct keys rendu vaaram velai seiyum, appuram revoke aagum, adhanaala gateway mattum dhaan ore path aagum.
- **Aliases.** `chat-default`, `extract-default`, `embed-default`, ovvonnum oru specific model-ku map aagiyirukku.
- **`chat-default`-ku failover.** Adhe model Mumbai, Hyderabad-la, 60-second cool-down-oda, appuram rendaavadhu provider-oda model irukkura fallback alias, adhuvum India-la host aanadhu, compliance approve pannadhu.
- **Fallback-la evals.** Go-live-ku munnaadi, team chatbot-oda 300-question golden set-a rendulaiyum ottudhu. Primary 92%, backup 88% score pannudhunnu vechukkonga, rendu JSON format failures-oda, adhai oru parser fix sari pannudhu. Outages-ku team 88%-a yethukkittu runbook-la record pannudhu.
- **Quota sharing.** Mumbai quota oru nimishathukku 400,000 tokens-nu vechukkonga. Chatbot-ku 200,000, claims extraction-ku 100,000. Batch job-ku 60,000, adhu midnight-ku appuram odum. Motham 360,000, spikes-ku headroom micham irukku.
- **Budgets, logs.** Ovvoru key-kkum 75%-la alert-oda oru monthly budget. Ovvoru request-um team, feature, alias, deployment, tokens, cost, latency-oda log aagudhu, personal data mask pannappattu.

**Result.** Adutha provider incident-la, errors-ku badhilaa, Mumbai cool down aagi Hyderabad serve panra konja neram users-ku answers konjam slow-aa varum. Fallback-rate alert on-call engineer-ku enna nadandhuchunnu sollum. Feature vaariyaana mudhal cost report, statement-summary job spend-la sumaar 40% use panradhai kaattudhu. Andha team adhai oru cheaper model-kkum provider-oda batch API-kkum maathudhu.

## Podhuvaana thavarugal

- **Ore oru gateway instance.** Ovvoru AI feature-kkum oru pudhu single point of failure-a uruvaakkitteenga. Pala instances ottunga.
- **Approve aagaadha models illa regions-ku fallbacks.** Oru outage, data poga allowed illaadha idathukku adhai sathamillaama anuppak koodaadhu. Data India-laye irukkanumnaa Bedrock APAC illa global profiles-um idhula adangum.
- **Application code-la model names.** Upgrades, swaps ore idathula nadakka aliases use pannunga.
- **Koottinaa provider quota-va vida adhigamaa varra key limits.** Appo oru busy key innum mathavatrukku quota kidaikkaama pannalaam.
- **Budget error-a retry panradhu.** Selavaana budget sila seconds-la thirumba nirambaadhu. Adhai final-aa eduthukkittu yaarukkaavadhu alert pannunga.
- **Test pannaadha fallbacks.** Orupodhum fire aagaadha fallback, mudhal thadavai fire aagumbodhu output formats-aiyo quality-aiyo odaikkalaam.
- **Errors-ku mattum alert panradhu.** Fallbacks failures-a users-kitta irundhu maraikkum, adhanaala odanja primary key vaarakkanakkaa yaarukkum theriyaama pogalaam.
- **Masking illaama full prompts irukkura gateway logs.** Gateway ungakitta irukkura migapperiya sensitive data store aayidum.

## Eppo gateway thevaikku adhigam

- **Ore provider-oda ore app.** Retries, timeout, billing alert-oda provider-oda SDK podhum.
- **Oru chinna team**, gateway michappaduthura nerathai vida adhai otturadhukku adhiga neram selavazhikkumnaa.
- **Oru managed platform**, yerkanave keys, budgets, routing tharradhunnaa.

Pala teams illa apps providers, keys, quota, budgets-a share panna aarambichadhum gateway palan tharum.

## Demo-la irundhu production-ku

- **Rendu illa adhukku mela instances ottunga**, health checks, avatroda sondha monitoring, oru shared database-oda.
- **Config-a Git-la vainga**, code maadhiriye review pannunga, model changes-a golden set-la test pannunga.
- **Ovvoru feature-kkum oru key kudunga**, rate limit, budget, per sollappatta owner-oda.
- **Personal data-va approved regions-ku mattum route pannunga**, ovvoru call-oda region-aiyum log pannunga.
- **Staging-la failover drill pannunga.** Thappaana key illa blocked endpoint vechu venumne primary-a odainga. Requests innum succeed aagudhaa, latency yethukkakkoodiya alavula irukkaa, endha model serve pannuchunnu logs, headers kaattudhaannu check pannunga. Chain-la ovvoru change-kkum appuramum repeat pannunga.
- **Mudhalla oru low-risk feature-a roll out pannunga**, adhoda errors, latency, cost-a munnaadi irundhadhoda compare pannunga, appuram mathavatrai ovvonnaa maathunga.

## Practice

LiteLLM gateway docs-aiyum RouteLLM post-aiyum padinga. Virtual keys-ku oru Postgres database-um adhoda client-um thevaippadradhaala, proxy-a otta LiteLLM-oda published Docker image dhaan romba easy-aana vazhi.

1. Postgres-um rendu models-um (rendu providers, illa ore provider-oda rendu models) vechu gateway-a locally ottunga. Mudhal model-a `chat-default` alias-ku pinnaadiyum, rendaavadhai `chat-backup`-ku pinnaadiyum vainga, avatrukku naduvula oru fallback-oda.
2. Primary-ku thappaana key kudunga. Requests innum succeed aagudhu, `x-litellm-attempted-fallbacks` header 1-nu solludhunnu kaattunga.
3. `rpm_limit` 3 irukkura oru key create pannunga. Oru nimishathula 5 requests anuppi, naalaavadhu request-ku HTTP 429 kidaikkudhunnu kaattunga.
4. Romba chinna budget irukkura oru key create pannunga. Adhai selavazhichu, budget error-a kaattunga, spend cap-a thaandi evvalavu pochunnu note pannunga.
