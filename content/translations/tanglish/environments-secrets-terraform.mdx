## Idhu enna

Oru deployment-a safe-aa operate panna udhavura moonu pazhakkangal:

- **Thaniththani environments.** Build panna development, production maadhiriyaana settings-la test panna staging, real users-kku production. Ovvonnukkum thani database, keys, settings.
- **Secrets management.** Passwords, API keys, tokens oru secret store-la irukkum, run time-la app-kku varum; code, images, logs, chat, Terraform state-la eppavume varaadhu.
- **Infrastructure as code (IaC).** Servers, databases, networks, permissions-a oru console-la click panni serkkaama, files-la describe panni, code maadhiriye review panni, Terraform maadhiriyaana oru tool moolamaa apply panradhu.

```flow
Terraform files, review aanavai -> Plan -> Apply
Apply -> Development | thani database, thani model key, 1 instance
Apply -> Staging | masked data, thani model key, 1 instance
Apply -> Production | real data, spend limit irukkura thani model key, 3 instances
Adhe container image -> Development
Adhe container image -> Staging
Adhe container image -> Production
```

Ovvoru environment-um adhoda settings-a environment variables-la irundhum, secrets-a vault-la irundhum eduththukkum. Values mattum dhaan maarum; code-um image-um onnu dhaan. Adhu dhaan mukkiyam: staging pass aanaa, production-um pass aaganum.

Indha lesson-la, Chandigarh-la irukkura oru lending company, avasaramaa panna oru pilot-a Azure-la production-kku thayaar panradha follow panrom. Idhe ideas AWS-kkum Google Cloud-kkum porundhum, resource names mattum vera.

## Idhu eppadi velai seiyudhu

### Config, environment-la

Adhe image ella idaththulayum odudhu; settings mattum dhaan vera. Avatrai environment variables-la irundhu (`DATABASE_HOST`, `MODEL_NAME`, `LOG_LEVEL`) read panni, start-up-la oru settings model moolamaa validate pannunga. Appo oru value illanna, adhu raaththiri 2 manikku mudhal real request-la illaama, deploy nadakkumbodhe boot-la saththamaa fail aagum.

### Environments-kku naduvula enna maarum

| Value | Udhaaranam | Enga irukkum |
| --- | --- | --- |
| Secret illaadha setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, ovvoru environment-kkum thaniyaa set panradhu |
| Secret | Model API key, webhook signing key | Secret store, app-oda identity moolamaa read panradhu |
| Database access | Production database | Managed identity sign-in, adhanaala password-e kidaiyaadhu |
| Infrastructure | Database size, network rules | Git-la Terraform files |
| Infrastructure state | Terraform endha resources-a manage pannudhu | Remote, locked storage, ovvoru environment-kkum oru state |
| Test data | Masked customer records | Staging database-la mattum |

Production-kku innum adhigamaana instances, provider kitta monthly spend limit set panna thani model key kidaikkum, rombave kuraivaana aatkal dhaan adha thoda mudiyum.

### Secret stores-um rotation-um

Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) alladhu HashiCorp Vault maadhiriyaana tools secrets-a vachirukkum, ovvonnaiyum yaar read pannalaam-nu control pannum, ovvoru read-aiyum log panna mudiyum. Azure-la, vault-oda diagnostic settings-a on pannaa dhaan reads log aagum, adhanaala mudhal naale adha pannunga; oru auditor kandippaa keppaaru.

App adhoda **managed identity** moolamaa secrets-a read pannum: idhu odikkittu irukkura app-kku Azure kudukkura oru identity, adhanaala vault-a reach panna app-kku password thevaiyilla. Secrets-a oru schedule-padi rotate pannunga, yaaraavadhu vittu ponaalo leak aanadhaa sandhegam vandhaalo udane rotate pannunga.

Rotation-la oru catch irukku. Oru secret-a start-up-la mattum read panra app, restart aagura varai pazhaya value-aiye vachirukkum. Moonu patterns-la onna thernthedunga: ovvoru rotation-kku appuramum app-a restart panradhu, oru timer-la secrets-a reload panradhu, alladhu oru call authentication error-oda fail aanaa oru thadavai reload panradhu. Sila platforms, adhula Azure Container Apps-um onnu, oru vault secret-oda latest version-a ungalukkaaga follow panna mudiyum; adhu app-a eppo restart pannum-nu therinjukka unga platform-oda docs-a padinga. Keys repository-kku varave varaama irukka, CI-la oru secret scanner ottunga.

### Terraform: code, plan, apply, state

Ungalukku vendiya resources-a describe panni, Terraform-oda configuration language-aana HCL-la files ezhuduveenga. Region-um environment-um variables, adhanaala adhe files endha environment-aiyum enga venumnaalum build pannum:

```hcl
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "location" {
  type    = string
  default = "centralindia"
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = var.location
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false

  authentication {
    active_directory_auth_enabled = true
    password_auth_enabled         = false
    tenant_id                     = data.azurerm_client_config.current.tenant_id
  }
}
```

`authentication` block passwords-a off pannudhu: app adhoda managed identity moolamaa Postgres-la sign in pannudhu, adhanaala leak aagavo rotate pannavo database password-e kidaiyaadhu.

`terraform plan` moonu vishayangala compare pannum: unga code, **state** file (Terraform manage panra resources paththina adhoda record), real cloud. Appuram edha create, change alladhu destroy pannum-nu list pannum. `terraform apply` andha changes-a panni state-a update pannum.

### Remote state, ovvoru environment-kkum onnu

Ovvoru project-um oru backend-oda aarambikkum, appo state share aagum, oru apply nadakkumbodhu lock aagum, laptops-la irukkaadhu:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 5.15" }
  }
}
```

Indha lesson-la irukkura code-a Terraform 1.17.2, azurerm provider 5.15.0-la `terraform validate` vachu check pannom (November 2026). Neenga test panna versions-a pin pannunga. Provider upgrades arguments-oda pera maathum. azurerm 5.x-la Key Vault argument `enable_rbac_authorization` poyiduchu, `rbac_authorization_enabled` required, adhanaala pazhaya copy panna code validate aagaadhu.

Environments-a eppadi pirikkanum? Indha rule-a use pannunga:

- **Ovvoru environment-kkum oru state, adhukku-nnu thani key, production-kku thani access.** Appo staging-la nadakkura oru thappu production-a thoda mudiyaadhu.
- **Share panra code oru module-la.** Module-na Terraform-oda oru folder, ovvoru environment-um adha thannoda values-oda call pannum, adhanaala staging-um production-um ore shape-la irukkum.
- **CLI workspaces** ore backend-la, adhe credentials-oda, pala states-a vachirukkum. Environments-kku vera vera credentials alladhu access controls thevaippattaa avai porundhaadhu-nnu HashiCorp-oda docs solludhu. Ovvoru feature branch-kkum onnu maadhiriyaana kurugiya kaalam irukkura copies-kku avatrai use pannunga, production-a pirikka illa.

### Secrets-a code-layum state-layum varaama paathukkuradhu

State ovvoru resource-oda ovvoru attribute-aiyum plain text-la store pannum, Terraform vachu neenga generate panra endha password-aiyum serththu. Oru value-a `sensitive`-nu mark pannaa adhu screen-la irundhu mattum maraiyum; state-la innum irukkum. Moonu paadhugaappugal, best mudhalla:

1. **Secret-e illaama irukkuradhu.** Mela database-la panna maadhiri, managed identity sign-in.
2. **Write-only arguments** (Terraform 1.11 matrum adhukku appuram). Provider value-a vaangikkum, aanaa Terraform adha eppavume store pannaadhu. Udhaaranamaa, azurerm-la Postgres server-la `administrator_password_wo`, Key Vault secrets-la `value_wo` irukku, ovvonnukkum oru `_wo_version` number, rotate panna adha yeththuveenga. Terraform 1.10 **ephemeral resources** kondu vandhuchu, avai oru run-kku mattum vault-la irundhu oru secret-a save pannaama read pannum.
3. **Value-a Terraform-kku veliye podradhu.** Terraform vault-aiyum permissions-aiyum create pannum; oru aalo oru pipeline-o secret value-a serkkum.

```hcl
resource "azurerm_key_vault" "kv" {
  name                       = "claims-${var.env}-kv"
  location                   = var.location
  resource_group_name        = azurerm_resource_group.main.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = var.env == "prod"
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

Indha role assignment, app-a secret values-a read panna mattum anumadhikkum, vera edhuvum illa: adhaala avatrai change pannavo delete pannavo mudiyaadhu.

### Code-la validate panna settings

`pydantic-settings` environment variables-a read panni seekkirame fail aagum:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_host: str
    model_api_key: SecretStr
    model_name: str                  # required: no default, so a missing value stops start-up
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()    # raises one clear error listing every missing or invalid value
```

`model_name`-kku venumne default illa. Oru default model name, neenga pidikka ninaikkura adhe bug-a maraichudum, model names-um adikkadi maarum. `SecretStr` secrets-a logs-layum error messages-layum varaama paathukkum: adha print pannaa `**********` dhaan kaattum. `.env` file development-kku mattum dhaan, adhu `.gitignore`-la irukkanum.

### Yaar apply pannalaam: review loop

Infrastructure-la oru change, Terraform files-a edit panra oru pull request-aa aarambikkum:

1. CI `terraform fmt -check`, `terraform validate`, appuram `tflint`, Checkov maadhiriyaana scanners-a ottum; avai public storage, open firewall rules, missing encryption-a flag pannum.
2. CI `terraform plan -out=plan.bin` otti, "1 to add, 0 to change, 0 to destroy" maadhiri oru summary-a post pannum.
3. Oru reviewer code-a mattum illaama plan-a padippaaru, yenna oru line edit, oru database-a destroy panni recreate panna Terraform-a kattaayappaduththalaam.
4. Approval-kku appuram, oru pipeline save panna adhe plan-a apply pannum. Production-kku, oru required approval step (udhaaranamaa oru protected GitHub environment) serunga, kadumaiyaana rules thevai-nnaa Open Policy Agent maadhiriyaana oru policy check-aiyum serunga.

Pipeline **OpenID Connect (OIDC)** moolamaa Azure-la sign in pannum: GitHub Actions oru kurugiya kaala token vachu dhaan yaar-nu niroobikkum, adhanaala neenda kaalam irukkura endha cloud password-um CI settings-la irukkaadhu. Staging pipeline-kku staging-la mattum rights kudunga, production pipeline-kku production-la mattum. Appo production-kku yaarukkum vazhakkamaana console access thevaippadaadhu, yaarum oru laptop-la irundhu apply otta maattaanga.

### Drift: plan edha paakkum, edha paakkaadhu

Oru incident nadakkumbodhu makkal innum console-la vishayangala maaththuvaanga. Oru nightly job production-a code kooda compare pannum:

```bash
terraform plan -var-file=env/prod.tfvars -input=false -lock=false -detailed-exitcode > plan.txt
case $? in
  0) echo "no changes" ;;
  2) echo "DIFFERENCE: production does not match the code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

Exit code 2-a kavanamaa padinga. Adhukku arththam "plan oru difference-a kandupidichudhu". Adhu drift-aa irukkalaam (yaaro oru managed resource-a kaiyaala maathiyirukkaanga), illanna merge aana, aanaa apply aagaadha code-aa irukkalaam. Edhu-nnu plan text sollum. Drift-a mattum paakka, `-refresh-only` serunga.

Periya blind spot: plan yerkanave state-la irukkura resources-a mattum dhaan check pannum. Oru thani resource-aa kaiyaala create panna firewall rule theriyave theriyaadhu; job green-aave irukkum. Avatrai cloud activity-log alerts alladhu policies vachu pidinga, appuram andha resource-a delete pannunga, alladhu oru import block vachu Terraform-kku keezha kondu vaanga:

```hcl
import {
  to = azurerm_postgresql_flexible_server_firewall_rule.partner
  id = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/claims-prod-rg/providers/Microsoft.DBforPostgreSQL/flexibleServers/claims-prod-db/firewallRules/partner"
}

resource "azurerm_postgresql_flexible_server_firewall_rule" "partner" {
  name             = "partner"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "203.0.113.10"
  end_ip_address   = "203.0.113.10"
}
```

Adutha plan "1 to import"-nu kaattum. `terraform plan -generate-config-out=generated.tf` ungalukkaaga resource block-a draft panna mudiyum; andha flag innum experimental-nu dhaan mark aagiyirukku, adhanaala adhu ezhudhuradha review pannunga.

### Unga browser-la try pannunga

Start-up-la check panra settings seekkiramaavum clear-aavum fail aagum. Dictionary-la irundhu `model_name`-a delete panni thirumba run pannunga.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    model_name: str
    model_api_key: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "model_name": "example-model", "model_api_key": "sk-test-123", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.model_name, s.daily_budget_inr, s.model_api_key)   # the key prints as stars
except ValidationError as err:
    print("start-up stopped, missing or invalid:", [e["loc"][0] for e in err.errors()])
```

## Oru worked example

Chandigarh lending company-oda pilot avasaramaa build pannadhu. Testing-kkum real data-kkum ore database-a use pannuchu, model key maasakkanakkaa munnaadi commit aana oru `.env` file-la irundhuchu, portal-la kaiyaala create panna resources irundhuchu.

Production-kku munnaadi, neenga:

1. Leak aana key-a revoke panni rotate pannunga, CI-la oru secret scanner serunga. History-la innum rendu pazhaya keys-a adhu kandupidikkudhu; rendume rotate aagudhu.
2. Network, database, storage, container app, Key Vault-kku Terraform ezhudhunga, `env`, `location` variables-aa irukkattum. Irukka vendiya kaiyaala senja resources-a import pannunga, michaththa delete pannunga, plan-la endha surprise-um illa-nnu confirm pannunga.
3. Ovvoru secret-aiyum Key Vault-kku maathunga, database-a managed identity sign-in-kku switch pannunga, appo password-e irukkaadhu. Staging-kkum production-kkum thaniththani monthly limits-oda thaniththani model keys.
4. Pona maasa applications-oda masked copies-a staging-la load pannunga: names, PAN, phone numbers maathappattirukkum.
5. CI-la irundhu mattum apply pannunga: oru staging pipeline, oru production pipeline, ovvonnukkum thani OIDC identity, production-kku munnaadi oru required approval.

Client-oda auditor "production model key-a yaar read panna mudiyum?"-nu kekkumbodhu, vault-la irukkura role assignments-aiyum adhoda access log-aiyum kaattuveenga. Oru region drill-la, team `location = "southindia"`-aiyum oru pudhu state key-aiyum pass panni South India-la rendaavadhu staging-a build pannudhu. Oru gotcha veliye vandhuchu: Key Vault, Postgres server names muzhu Azure-layum unique-aa irukkanum, adhanaala copy-oda names-la oru region suffix thevai. Indha example-la rebuild oru mani nerathukkulla mudinjudhu; ungalukku adhu data size-a poruththadhu.

| Auditor-oda kelvi | Munnaadi badhil | Appuram badhil |
| --- | --- | --- |
| Secrets enga store aagiyirukku? | "Oru .env file-la" | Key Vault, oru access log-oda |
| Database password irukkaa? | Aamaa, adhe file-la | Illa, app adhoda identity vachu sign in pannudhu |
| Production-a yaar maaththa mudiyum? | Pala per, portal moolamaa | Production pipeline, oru approved plan-kku appuram |
| Oru manual change paththi eppadi therinjukkuveenga? | Theriyaadhu | Nightly drift check-um activity-log alerts-um |

## Podhuvaana thappugal

- **Production data-vukku edhiraa test panradhu.** Oru mosamaana script podhum, real customers baadhikkappaduvaanga. Piringa, test data-va mask pannunga.
- **Git-la secrets, konja neram mattumaa irundhaalum.** History avatrai vachirukkum. Eppavaavadhu commit aana endha key-aiyum rotate pannunga.
- **`sensitive = true` oru secret-a state-la varaama paathukkum-nu nambhuradhu.** Adhu screen-la irundhu mattum maraikkum. Managed identity alladhu write-only arguments use pannunga.
- **Laptop-la Terraform state.** Adhu tholainju pogum alladhu pazhasaayidum, adhula secrets-um irukkalaam. Remote, locked state use pannunga.
- **Staging-kkum production-kkum ore state, alladhu CLI workspaces.** Appo oru staging change, adhe credentials-oda production-a reach pannalaam. Thaniththani states-um access-um use pannunga.
- **Yaarum record pannaadha console changes.** Maarina attributes drift-aa theriyum; kaiyaala senja pudhu resources theriyave theriyaadhu. Activity log-la alert vainga, import alladhu delete pannunga.
- **Laptops-la irundhu apply otturadhu.** Endha code apply aachu-nnu yaarukkum theriyaadhu. Review aana plan-a CI-la irundhu mattum apply pannunga.
- **Ovvoru environment-kkum vera shape.** Production-la irukkura private network staging-la illanna, staging tests perisaa edhaiyum niroobikkaadhu.
- **Versions-a pin pannaama pazhaya provider code-a copy panradhu.** Major versions-kku naduvula arguments-oda per maarum; pin pannunga, therinje upgrade pannunga.

## Practice pannunga

Neenga thernthedutha cloud-kku Terraform-oda getting-started tutorials-a follow pannunga, config paththina Twelve-Factor page-a padinga.

1. `env = "staging"`-kku oru storage bucket-aiyum oru chinna managed database-aiyum create panra Terraform ezhudhunga, database public-aa reach aagakkoodaadhu. Adha apply pannunga, plan-a padinga, appuram destroy pannunga.
2. Unga app-oda settings-a environment variables-la irundhu read panra, validate panra oru settings model-kku maathunga, model name-kku default irukkakkoodaadhu; oru value illanna start-up clear-aa fail aagura maadhiri pannunga.
3. Unga cloud-oda secret manager-la oru secret-a store panni, app adha adhoda identity moolamaa read panna vainga. Appuram adha rotate panni, app pudhu value-a eduththukkudhaa-nnu confirm pannunga.
4. Console-la, Terraform manage panra oru resource-oda oru setting-a maathi drift check-a ottunga: adhu 2-oda exit aaganum. Andha change-a undo pannunga, appuram kaiyaala oru pudhu firewall rule create panni thirumba ottunga: adhu 0-oda exit aagum. Oru import block vachu andha rule-a import pannunga.

**Mudinjadhu-nnu eppo sollalaam:** unga staging environment-a code-la irundhu thirumba build panna mudiyum, unga repository-layo state-layo endha secret-um illa-nnu kaatta mudiyum, unga drift check edha paakka mudiyaadhu-nnu explain panna mudiyum.
