## Idhu enna

**Latency budget**-na neenga ethukkira miga medhuvaana response, oru kurippitta percentile-la, oru request-oda ovvoru step-kkum oru target-aa pirichadhu. Oru chat assistant-kku, udhaaranamaa: p95 time to first token 2 seconds-kkulla, p95 full answer 10 seconds-kkulla, errors 1%-kku keezha. Appuram first-token budget ippadi piriyum: auth 50 ms, query rewrite 300 ms, retrieval-um reranking-um 400 ms, model first token 700 ms, network-kkum queueing-kkum 550 ms slack.

**Load testing** realistic traffic-a system mela step by step koottikkitte anuppi, response times, errors, resource use-a record pannum. Endha load-la system udaiyudhu, edhu mudhalla udaiyudhu-nnu unga users kandupidikkiradhukku munnaadiye adhu solliddum.

```flow

title: Latency budget: p95 first token 2 s-kkulla
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

Ungalukku thevaippadura moonu vaarthaigal. **p95**-na 95% requests endha nerathai vida vegamaa mudiyudho andha neram. **Time to first token**-na answer-oda mudhal vaarthai theriyura varaikkumaana kaathiruppu. **Concurrent users**-na ore nerathula chat session-la irukkuravanga; avangalla perumbaalaanavanga padichukkitto type pannikkitto iruppaanga, adhanaala ore nerathula in flight-la irukkura requests romba kuraivu.

Indha lesson, Jaipur-la oru intercity bus operator festival-season traffic-kku thannoda booking assistant-a thayaar panradhai follow pannudhu.

## Idhu eppadi work aagudhu

### Averages illa, percentiles

1.5 seconds average, 5% users 4-la irundhu 9 seconds varai kaathirukkuradhai maraikkalaam. Median (p50), p95, p99-a track pannunga. Tail, paarthaa thonuradhai vida mukkiyam: oru session-la 20 messages anuppura oru user-kku, p99-a vida slow-aana kuranjadhu oru reply-a sandhikka sumaar 18% chance irukku (1 minus 0.99 power 20).

Experts follow panra rendu rules:

- **Percentiles koottinaa varaadhu.** Total-oda p95, ovvoru step-oda p95-aiyum koottinadhu illa. Slow steps ore request-la aridhaa thaan serndhu nadakkum, adhanaala koottuthogai podhuvaa total-a adhigamaa kaattum; aanaa busy database maadhiri ore kaaranam ellaa steps-aiyum ore nerathula slow pannaa, avai serndhe nagarum. Step numbers-a andha step-oda sondha p95-kkaana targets-aa vachukkunga, end-to-end p95-a traces-la irundhu neradiyaa padinga.
- **Percentiles-a average panna mudiyaadhu.** Moonu servers 1.2 seconds p95 kaattudhu, onnu, 3.5 seconds median-oda, 6 seconds kaattudhu-nnu vachukkunga; ovvonnum traffic-la kaal pangu edukkudhu. Naalu p95-oda average 2.4 seconds. Aanaa slow server-oda requests-la paadhi 3.5 seconds-kku mela edukkudhu, adhu ellaa requests-layum 12.5%, adhanaala unmaiyaana p95 3.5 seconds-kku mela. Percentiles-a ellaa raw timings-la irundho, merge panna histograms-la irundho kanakku podunga.

```python
import random

random.seed(7)
def p95(xs):
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]

# Four steps, each with its own spread of times in seconds
auth     = [random.lognormvariate(-3.5, 0.3) for _ in range(10_000)]
retrieve = [random.lognormvariate(-1.3, 0.4) for _ in range(10_000)]
rerank   = [random.lognormvariate(-1.8, 0.5) for _ in range(10_000)]
model    = [random.lognormvariate(-0.5, 0.35) for _ in range(10_000)]
total = [a + b + c + d for a, b, c, d in zip(auth, retrieve, rerank, model)]

print(f"sum of the step p95s: {p95(auth) + p95(retrieve) + p95(rerank) + p95(model):.2f} s")
print(f"p95 of the total:     {p95(total):.2f} s")
```

Idhu koottuthogaikku 2.03 seconds-um, unmaiyaana total-kku 1.67 seconds-um print pannum, yenna inga steps independent.

### AI requests-a slow aakkuradhu edhu

**Generation time** kittathatta output tokens perukkal oru token-kkaana neram. Oru second-kku 60 tokens-la, 450-token answer stream aaga 7.5 seconds, 200-token answer sumaar 3.3 seconds edukkum. Answer neelathai cap panradhu thaan perumbaalum ungakitta irukkura miga malivaana speed-up.

**Time to first token** prompt neelathodavum, unga system-layum provider-layum irukkura queueing-odavum, andha mani nerathula provider-oda load-odavum koodum. Context-a trim pannunga, unga provider support pannaa oru cached prompt prefix-a reuse pannunga. Reasoning models edhaiyum kaattradhukku munnaadi yosikkalaam, adhanaala user unmaiyaa paarkkura mudhal token-a alanga.

**Rate limits** nimishathukku tokens allathu requests mela irukkum; neenga ethanai servers ottinaalum avai calls-a 429 (Too Many Requests)-oda reject pannum. Unga provider input, output tokens-a eppadi count pannudhu-nnu check pannunga, peak-la enna venum-nu kanakku podunga, vaarakkanakkaa munnaadiye adhiga limit kelunga.

### Little's law vachu sizing

**Little's law**: requests in flight = arrival rate x ovvoru request-um system-la irukkura neram. Pilot-oda logs-la ovvoru active user-um nimishathukku sumaar 2 messages anuppuraanga-nnu theriyudhu-nnu vachukkunga. 500 users-la adhu oru second-kku sumaar 17 requests. Ovvonnum 4.5 seconds eduthaa, endha nerathulayum sumaar 75 answers stream aagittu irukkum. 500 illa, andha enn thaan unga connection pools, worker counts, endha concurrency cap-aiyum size pannum.

### Test-a design panradhu

Unmaiyaana behaviour-a model pannunga: unmaiyaana kelvigal (masked), vazhakkamaana prompt, answer neelangal, messages naduvula think time, expected peak. Kuraivula irundhu peak-a thaandi ramp pannunga, percentiles settle aaga **ovvoru step-aiyum** rendu moonu nimisham **hold pannunga**. p95, p99, status code vaariyaa errors, CPU, memory, database connections, queue neelam, provider 429s-a kavaninga.

**Closed, open tests.** Oru **closed** test-la, think time ulla Locust users maadhiri, ovvoru simulated user-um reply varra varai kaathirundhu thaan thirumba anuppuvaanga. System slow aanaa test kuraivaa anuppum, andha slow period-la vara vendiyadhai vida kuraivaana measurements thaan varum. Idhukku per **coordinated omission**: real users pinvaangaadha sariyaana andha nerathula test amaidhiyaa pinvaangudhu. Oru **open** test-la, enna aanaalum requests oru fixed rate-la varum, sale thirakkumbodhu travellers mundiyadichu varra maadhiri. k6 idhai adhoda constant-arrival-rate, ramping-arrival-rate executors moolamaa kudukkudhu. Bottlenecks-a step by step kandupidikka oru closed ramp use pannunga, appuram queue-a paarkka expected arrival rate-la oru burst-oda open test ottunga.

**Soak test.** Expected peak-a 30-la irundhu 60 nimisham varai hold pannunga. Memory, connections, file handles leaks neram pogappoga thaan theriyum.

### Oru fake model server

Real-model load tests-kku kaasu selavaagum, rate limits-um theerum. Perumbaalaana rounds-a oru chinna fake service-kku edhiraa ottunga; adhukku provider-oda API-oda adhe streaming shape irukkum, adhoda first-token delays unga traces-la irundhu sample pannadhu:

```python
import asyncio, json, os, random
from fastapi import FastAPI
from fastapi.responses import JSONResponse, StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.30, 0.35, 0.35, 0.35, 0.40, 0.40, 0.40, 0.45, 0.45, 0.45, 0.45, 0.50, 0.50,
                 0.50, 0.50, 0.55, 0.55, 0.55, 0.60, 0.60, 0.60, 0.65, 0.70, 0.70, 1.40]
TOKENS_PER_S = 60
REPLY_TOKENS = 450                                    # today's typical answer length
SHARE_429 = float(os.getenv("FAKE_429_SHARE", "0"))   # for example 0.05

@app.post("/v1/messages")
async def messages():
    if random.random() < SHARE_429:
        return JSONResponse({"error": "rate_limited"}, status_code=429,
                            headers={"retry-after": "2"})
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for i in range(REPLY_TOKENS):
            yield f"data: {json.dumps({'text': f'tok{i} '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Indha delays model-kku 0.7 seconds p95 kudukkum, adhu thaan budget-la model-oda share, 25-la oru slow reply-oda. Adhai `uvicorn fake_model:app`-oda ottunga, test environment-la mattum configuration moolamaa unga app-oda model base URL-a adhu pakkam point pannunga. Unga retries, fallback-a test panna `FAKE_429_SHARE`-a set pannunga.

### Stream-a time panra oru Locust ramp

`stream=True`-oda, request-kkaana Locust-oda sondha row, response headers vandhadhume clock-a niruthiddum, perumbaalum sila milliseconds-la, first token-kku romba munnaadiye. Adhanaala indha test thannoda sondha rendu timings-a record pannudhu:

```python
import random, time
from locust import HttpUser, LoadTestShape, between, task

QUESTIONS = [q.strip() for q in open("load/questions.txt", encoding="utf-8") if q.strip()]

class Traveller(HttpUser):
    wait_time = between(20, 30)          # think time between messages

    @task
    def ask(self):
        start, first = time.perf_counter(), None
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
                return
            for line in r.iter_lines():               # read the whole stream
                if line and first is None:
                    first = time.perf_counter()
        end = time.perf_counter()
        if first is not None:
            self.record("first token", first - start)
        self.record("full answer", end - start)

    def record(self, name, seconds):
        self.environment.events.request.fire(
            request_type="STREAM", name=name, response_time=seconds * 1000,
            response_length=0, exception=None, context={})

class Ramp(LoadTestShape):
    # (end second, users): hold each step for two minutes
    steps = [(120, 50), (240, 100), (360, 200), (480, 300), (600, 400), (720, 500), (840, 550)]

    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10                      # add up to 10 users a second
        return None
```

Adhai `locust -f load/locustfile.py --headless --host https://staging.example.in --csv results --csv-full-history`-oda ottunga. Appuram `results_stats_history.csv` file-la ovvoru name-kkum ovvoru second-um oru row varum, adhula user count-um kadaisi sumaar 10 seconds-oda percentiles-um irukkum. `first token`, `full answer` rows-a padinga, ovvoru hold-oda kadaisi nimishathula 95% column-oda median-a edunga, yenna low load-la oru 10-second window-la konjam requests thaan irukkum. Traces-la irundhu per-step p95-um work aagum. Built-in POST row-a (headers mattum) ignore pannunga, Aggregated row-aiyum ignore pannunga, adhu moonu timings-aiyum kalakkudhu.

### Overload, retries, streaming

- **Retry storms.** Ovvoru 429-aiyum timeout-aiyum udane, moonu thadavai varai retry pannaa, kashtappadura oru system-kku naalu madangu varai traffic varalaam. Exponential backoff-um random jitter-um vachu retry pannunga, provider `retry-after` header anuppinaa adhai madhinga, retries-a traffic-la oru chinna share-la cap pannunga.
- **Admission control.** Ovvoru instance-um ore nerathula serve panra streams-a cap pannunga. Koodudhal requests oru chinna queue-la, adhigabatcham sila seconds, kaathirukkattum; appuram "Ippo busy-aa irukkom, oru nimisham kazhichu try pannunga"-nu mariyaadhaiyaa kaattunga. Ellaarukkum timeout aaguradhai vida, silarai thiruppi anuppuradhu mel.
- **Autoscaling, cold starts.** Pudhu instances start aagi warm up aaga nimishakkanakkaa aagalaam. Therinja peak-kku, adhu aarambikkiradhukku munnaadiye scale up pannunga.
- **Proxies vazhiyaa streaming.** Oru proxy allathu load balancer response-a buffer pannalaam, adhanaala tokens ore kattiyaa varum; allathu idle-nu ninaikkira connection-a close pannalaam. Streaming route-la buffering, idle-timeout settings-a check pannunga.

| Load-la theriyura arikuri | Vaaippulla kaaranam | Fix |
| --- | --- | --- |
| Latency eredhu, CPU low | Database connections allathu locks-kkaaga kaathirukku | Periya pool, indexes, caching, kuraivaana queries |
| CPU 100%-la | Romba kammiyaana workers allathu heavy parsing | Adhiga workers, velaiya background jobs-kku maathunga |
| 429 errors | Provider rate limit | Adhiga limit, fallback model, chinna outputs |
| Errors aarambikkumbodhu traffic egirudhu | Udanadi retries | Jitter-oda backoff, retry cap |
| Bursts-la mattum queue valarudhu | Arrival rate-kku romba kammiyaana streams | Concurrency cap, busy message, seekkirame scale up |
| First token mattum slow | Neelamaana prompts allathu provider queueing | Context-a trim pannunga, prefix-a cache pannunga |
| Tokens ore kattiyaa varudhu | Oru proxy stream-a buffer pannudhu | Andha route-la buffering-a off pannunga |
| Sariyaa oru nimisham kazhichu errors | Edho oru layer-la timeout allathu idle limit | Ellaa layers-layum timeouts-a align pannunga |

### Traces-a open pannikkitte results-a padinga

Oru step-la p95 egirinaa, andha nimishathoda romba slow traces-a open pannunga. Valarndha step (database waits, reranker, model slot-kkaana queueing) thaan bottleneck, mela irukkura table podhuvaa fix-a solliddum. Appuram adhe test-a thirumba ottunga, appo thaan samamaanadhai samamaanadhoda compare panna mudiyum.

## Oru worked example

Jaipur bus operator, festival travel nerathula ore nerathula chat panra sumaar 500 travellers-a edhirpaarkkudhu, kaalai 10 manikku oru seat sale thirakkudhu. Budget: p95 first token 2 seconds-kku keezha, p95 full answer 10 seconds-kku keezha, errors 1%-kku keezha. Keezha irukkura ellaa numbers-um illustrative thaan.

**Round 1: closed ramp, fake model.** p95 first token 50 users-la 1.1 seconds-la irundhu 200-la 6 seconds-kku eredhu. CPU 25%-la irukku. Romba slow traces ellaam database connection-kkaaga kaathirukku: pool-la 10 thaan irukku. 40 pool-um route table-la oru index-um adhai fix pannudhu.

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| p95 first token, pool 10 | 1.1 s | 2.4 s | 6.0 s | niruthiyaachu: timeouts | ottala | ottala |
| p95 first token, pool 40 + index | 1.1 s | 1.1 s | 1.2 s | 1.2 s | 1.3 s | 1.4 s |

**Round 2: real model-la oru chinna run.** Pathu nimisham, 300 users varai ramp, API account-a vachirukkavanga kooda munnaadiye pesi othukkittadhu. Sumaar 220 users-la 429 errors aarambikkudhu. Thoraayamaana kanakkum othuppogudhu: pilot-oda logs-padi ovvoru user-um nimishathukku sumaar 2,000 tokens (1,550 in, 450 out) ulla sumaar 2 messages anuppuraanga, adhanaala oru user-kku nimishathukku 4,000 tokens; account-oda nimishathukku 900,000 tokens 225 users-la theerndhudum. Team answers-a 200 tokens-la cap pannudhu; adhu streaming nerathai 7.5-la irundhu sumaar 3.3 seconds-kkum, oru message-kkaana tokens-a 1,750-kkum kuraikkudhu. Avanga adhiga limit kekkuraanga; pathu naal kazhichu provider nimishathukku 2.5 million tokens kudukkudhu. Avanga gateway moolamaa oru fallback model-um, retries-la jitter-oda backoff-um serkkuraanga.

**Round 3: open burst test, fake model** (ippo 200-token replies-kku set pannadhu). Little's law: 500 users-la, oru second-kku sumaar 17 requests, ovvonnum sumaar 4.5 seconds-na, sumaar 75 streams in flight. Sale thirakkumbodhu arrivals oru second-kku sumaar 25-kku egirudhu, adhaavadhu sumaar 113 in flight. Ovvonnum 48 streams-la cap panna rendu instances 96-a thaan thaangum. Burst-la p95 first token 9 seconds-a thodudhu, 6% requests timeout aagudhu. Closed ramp idhai kaattave illa, yenna adhoda users summaa kaathirundhaanga. Fix: kaalai 9:45-kku start panna oru moonaavadhu instance, 3-second queue-um busy message-um ulla admission control. Re-run-la p95 first token 1.5 seconds-laye irukku, yaaraiyum thiruppi anuppala.

**Round 4: confirm.** Real model-la 550 users-la pathu nimisham: p95 first token 1.6 seconds, p95 full answer 5.2 seconds, errors 0.3%. Andha load nimishathukku 1.9 million tokens use pannudhu, limit-la 77%. Fake model-la 500 users-la oru 45 nimisha soak, memory flat-aa irukkuradhaiyum connections leak aagalai-nnum kaattudhu.

**Launch naal.** Peak 480 travellers-a thodudhu. Kaalai 10 mani burst-la demand konja nerathukku nimishathukku sumaar 2.6 million tokens kekkudhu, limit-a vida 5% adhigam; gateway rendu nimishathukku sila percent requests-a fallback model-kku anuppudhu. p95 first token 2 seconds-kku keezhaye irukku.

**Report**-la budget line-oda users-kku edhiraa p95 kaattura oru chart, kandupidicha ovvoru bottleneck-um adhoda fix-um, aduttha ceiling-um irukku: sumaar 700 steady users (2.5 million vagutthal oru user-kku nimishathukku 3,500 tokens), bursts-la adhukku munnaadiye.

## Podhuvaa panra thappugal

- **Averages-a report panradhu.** First token-kkum full answer-kkum p50, p95, p99-a report pannunga.
- **Percentiles-a koottradhu allathu average panradhu.** Rendume work aagaadhu; raw timings-la irundhu kanakku podunga.
- **Oru nerathula oru request-a mattum test panradhu.** Pools, locks, rate limits concurrency-la mattum thaan fail aagum.
- **Unrealistic traffic.** Ore maadhiriyaana chinna prompts-um think time illaadhadhum arthamillaadha numbers-a thaan kudukkum.
- **Closed tests mattum.** System slow aanaa avai pinvaangiddum, adhanaala oru real rush uruvaakkura queue-a maraichudum.
- **Streams-kku Locust-oda request row-a nambradhu.** Streaming on-aa irundhaa, adhu headers-a mattum thaan time pannum.
- **Real-model load tests-la kaasai kottradhu.** Perumbaalaana rounds-kku fake model use pannunga, oru chinna real run mattum podhum.
- **Provider limits-a marakkuradhu.** Perumbaalum avai thaan unmaiyaana ceiling. Token kanakkai pottu, seekkirame kelunga.
- **Udanadi retries.** System kashtappadura sariyaana andha nerathula avai load-a perukkum.

## Muzhu load test kaathirukkalaam-ngira nerangal

- **Konjam users mattum ulla internal tools**: pathu concurrent requests-oda oru quick check podhum.
- **Batch systems**, anga per-user latency-a vida oru mani nerathukkaana throughput thaan mukkiyam; adhai test pannunga.
- **Ungalukkaaga scale panra platforms-la aarambha pilots**, rate limits-aiyum timeouts-aiyum check panniyirundhaa podhum.

## Demo-la irundhu production-kku

- **Step vaariyaa oru latency budget vachukkunga**, ovvoru release-layum traces-a adhoda compare pannunga.
- **Launch-kku munnaadiyum periya maatrangalukku munnaadiyum load-test pannunga**, perumbaalum oru fake model server-oda.
- **Ovvoru ramp step-kkum p50, p95, p99, errors-a report pannunga**, kandupidicha bottleneck-oda serthu.
- **Traffic patterns maarumbodhu thirumba test pannunga**, exam season, oru festival sale, allathu neelamaana answers ulla oru pudhu feature maadhiri.
- **Production-la p95 first-token time-kkum 429 rate-kkum alert vainga**, tokens-per-minute headroom-a kannula vachukkunga.

## Practice pannunga

Monitoring pathina Google SRE chapter-aiyum Locust-oda first-test guide-aiyum padinga.

1. Pathu real requests-oda traces-a vachu, unga app-kku step vaariyaa oru latency budget ezhudhunga. End-to-end p95-a thaniyaa check pannunga.
2. Mela irukkura fake model server-a otti, unga app-a adhu pakkam point pannunga.
3. Locust ramp-a 50-la irundhu 550 users varai ottunga. Ovvoru hold-layum first token, full answer-kku p50, p95, p99-a record pannunga, p95 mudhal thadavaiyaa unga budget-a enga thaandudhu-nnu note pannunga.
4. Mudhal bottleneck-a kandupidichu fix panni, re-run pannunga; appuram Little's law vachu unga peak-layum, andha rate-oda 1.5 madangu burst-layum requests in flight-a estimate pannunga.

Innum aazhamaa therinjukka, Chip Huyen-oda *AI Engineering* (O'Reilly) puthagathoda chapter 9, inference optimisation pathinadhu; adhu time to first token-aiyum time per output token-aiyum cover pannudhu.

**Neenga mudichutteenga, eppo-nnaa:** unga budget line-oda users-kku edhiraa p95 kaattura chart-a kaatta mudiyumbodhu, mudhal bottleneck-aiyum adhai nagarthina maatrathaiyum solla mudiyumbodhu, unga peak-la ethanai requests in flight-la irukku-nnu solla mudiyumbodhu.
