## Idhu enna

Serving-naa real users nambi use panra maadhiri unga application-a ottradhu. Adhu thaanaa start aagum, crash aanaa restart aagum, ore nerathula niraiya requests-a handle pannum, koodudhal load-a sutthamaa marukkum, model medhuvaa irundhaalum seekkiramaa edhaavadhu kaattum.

Oru Python AI service-kku, podhuvaana stack idhu: app-kku FastAPI, adha ottura server-aa **Uvicorn**, pala worker processes-oda. HTTPS-a handle pannavum traffic-a pirichu anuppavum munnaadi edhaavadhu onnu irukkum: oru load balancer, oru ingress, alladhu Cloud Run maadhiri oru platform.

AI services oru saadhaarana web API-la irundhu moonu vidhathula vera. Requests medhuvaa irukkum, perumbaalum 2-la irundhu 30 seconds, yenna avai model calls-kkaaga kaathirukku. Progress therinjaa mattum dhaan users adha poruthukkuvaanga, adhanaala dhaan **streaming** mukkiyam. Appuram patrakkuraiyaa irukkura resource vera oruthar-odadhu: provider unga requests-aiyum tokens-aiyum oru nimishathukku ivvalavu-nnu limit pannudhu, adhanaala podhuvaa bottleneck unga CPU illa, adhoda quota-vum unga bill-um dhaan.

```flow
Users -[HTTPS]-> Load balancer | idle timeout 30 s, ready aana instances-kku anuppum
Load balancer -> Container 1 | 4 Uvicorn workers, ovvonnulayum adhigabatcham 40 model calls
Load balancer -> Container 2 | adhe maadhiri
Container 1 -[deadline 25 s, retries inside]-> Model API | tokens user-kku stream aagi varum
Container 1 -> Background queue | OCR, indexing; oru job id-a return pannum
```

Indha lesson-la Lucknow-la irukkura oru edtech company-oda doubt-solving assistant-a follow panrom. Adhu ovvoru saayangaalamum oorndhu pora alavukku medhuvaayidum.

## Idhu eppadi work aagudhu

### Workers-um event loop-um

Oru Uvicorn process adhoda async endpoints-a ore oru **event loop**-la ottudhu. Oru request model-kkaaga await pannumbodhu, loop matha requests-a serve pannum, adhanaala oru process nootrukkanakkaana kaathirukkura requests-a vechukka mudiyum. Aanaa loop-a block panra edhuvum andha process-la irukkura ellaa request-aiyum freeze pannidum: oru synchronous Redis, database alladhu `requests` call, PDF parsing, oru local embedding model.

Fixes: network calls-kku oru **async client** use pannunga; alladhu endpoint-a oru saadhaarana `def`-aa ezhudhunga, adha FastAPI oru thread pool-la ottum; alladhu heavy velaiya oru **background queue**-kku maathunga. Appuram pala workers ottunga, podhuvaa oru CPU core-kku onnu alladhu rendu, appo oru crash ellaathaiyum keezha irakkaadhu. Perumbaalum oru model API-kkaaga kaathirukkura oru service-kku, workers serkkaradha vida blocking calls-a edukkaradhu adhigamaa udhavum.

### Layers-aa timeouts

Ovvoru wait-kkum oru limit venum, ulla irukkuradhu veliya irukkuradha vida chinnadhaa; illainaa veliya irukkuradhu mudhalla fire aagum, user-kku unga message-kku badhilaa oru verumaiyaana load balancer error dhaan kidaikkum. Oru **total** timeout muzhu request-aiyum cap pannum. Oru **idle** timeout amaidhiya cap pannum, adhanaala anuppikitte irukkura oru stream eppavum vettappadaadhu; udhaaranamaa, AWS Application Load Balancer default-aa oru 60-second idle timeout use pannudhu.

Official Anthropic Python SDK-la oru pori irukku. Adhoda `timeout` connect panradhukkum, adutha chunk-kkaana ovvoru wait-kkum, ovvoru attempt-kkum thaniyaa apply aagudhu; adhu oru total deadline illa. Adhu default-aa 429s-aiyum server errors-aiyum rendu thadavai retry pannudhu, provider-oda `retry-after` header kekkura alavu kaathirundhu. Adhanaala `timeout=30, max_retries=2` oru request-a 90 seconds-a nallaave thaandi pidichu vaikkalaam. Muzhu call-a sutthi unga sondha deadline onnu vainga, retries adhukkullaye.

| Layer | Vagai | Udhaarana value | Edha pidikkum |
| --- | --- | --- | --- |
| SDK `timeout` | Ovvoru attempt, ovvoru chunk-kkum | 10 s | Oru dead connection alladhu ninnupona stream |
| SDK `max_retries` | Ennikkai | 1 | Oru chinna provider error; adhe budget-la irundhu selavaagum |
| Unga deadline | Total, retries udpada | 25 s | Mela irukkura ellaam, neenga ezhudhuna message-oda |
| Load balancer | Podhuvaa idle | 30 s | Thongi nikkura oru instance; layers sariyaa irundhaa mudhalla fire aagave aagaadhu |
| Shutdown grace | Total | 30 s server, 40 s platform | Oru deploy-la vettappadura streams |

### Streaming, adha edhu udaikkum

**Server-sent events** (SSE)-la, server response-a open-aave vechu, ovvoru piece-aiyum oru `data:` line-aa anuppum. Version 0.135.0-la irundhu, FastAPI idha neradiyaa support pannudhu: `response_class=EventSourceResponse` set panni endpoint-la irundhu `yield` pannunga. FastAPI ovvoru item-aiyum JSON-aa encode pannum, adhanaala answer-la oru newline vandhaa format udaiyaadhu. Adhu `Cache-Control: no-cache`, `X-Accel-Buffering: no` (nginx-kku oru hint) set pannum, 15 seconds amaidhiyaa irundhaa oru keep-alive comment anuppum.

Streaming generation-a vegamaakkaadhu; kaathirukkaradha kuraivaa feel panna vaikkum, yenna mudhal vaarthaigal onnu rendu second-la vandhudum. Prachanaigal production-la mattum dhaan veliya varum:

- **Buffering proxies.** Oru ingress, proxy alladhu compression layer muzhu response-aiyum pidichu vaikkalaam, adhanaala users mudhalla edhuvum paarkka maattaanga, appuram ellaathaiyum ore thadavai paarppaanga. nginx default-aa proxied responses-a buffer pannum, header mattum eppavum podhaadhu. Andha route-kku buffering-a off pannunga (nginx-la `proxy_buffering off;`), real path vazhiyaa test pannunga.
- **Idle timeouts.** Oru neelamaana amaidhi, udhaaranamaa model oru neelamaana prompt-a padikkumbodhu, balancer-a trip pannalaam. Keep-alive comments adhoda idle timeout-a vida adikkadi varanum.
- **Browser-la POST.** `EventSource` oru request body anuppa mudiyaadhu; oru POST stream-a `fetch`, oru stream reader vechu padinga.
- **Paadhiyila fail aaguradhu.** Oru 200-um paadhi answer-um ponadhukku appuram, status code-a maatha mudiyaadhu. Oru error event anuppunga, paadhi text-a "answer interrupted, try again"-oda kaattunga, adha eppavum cache pannaadheenga. Ivatrai unga logs-la count pannunga, yenna status-code dashboards ivatrai miss pannidum.
- **Disconnects.** Tab close aanaa, FastAPI generator-a cancel pannum, SDK-oda `async with` model stream-a close pannum, adhanaala padikkaadha tokens-kku kaasu kattaradhu ninnudum.

### Endpoint

Load-a shed panra oru concurrency cap, model call-a sutthi oru deadline, JSON events, padikkakkoodiya errors. API-oda oru local fake-kku edhiraa FastAPI 0.165, Anthropic SDK 2.14, Python 3.13 vechu test pannadhu; idhukku FastAPI 0.135.0 alladhu adhukku mela, Python 3.11 alladhu adhukku mela venum.

```python
import asyncio
import anthropic
from fastapi import Depends, FastAPI, HTTPException
from fastapi.sse import EventSourceResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=10, max_retries=1)   # per attempt, per chunk
SLOTS = asyncio.Semaphore(40)      # at most 40 model calls at once in this process
MODEL_DEADLINE = 25                # seconds for the whole model call, retries included

class Question(BaseModel):
    text: str

async def model_slot():
    try:                                         # wait at most 1 s for a free slot
        await asyncio.wait_for(SLOTS.acquire(), timeout=1)
    except TimeoutError:
        raise HTTPException(429, "Busy, please try again in a few seconds",
                            headers={"Retry-After": "5"})
    try:
        yield                                    # the request streams here
    finally:
        SLOTS.release()                          # after the stream ends, even on disconnect

async def with_deadline(chunks, seconds):
    loop = asyncio.get_running_loop()
    end = loop.time() + seconds
    it = aiter(chunks)
    while True:
        try:
            yield await asyncio.wait_for(anext(it), end - loop.time())
        except StopAsyncIteration:
            return

async def model_text(question: str):
    async with client.messages.stream(
            model="claude-sonnet-5-5", max_tokens=600,      # check the docs for current names
            messages=[{"role": "user", "content": question}]) as stream:
        async for text in stream.text_stream:
            yield text

@app.post("/answer", response_class=EventSourceResponse)
async def answer(body: Question, _: None = Depends(model_slot)):
    try:
        async for text in with_deadline(model_text(body.text), MODEL_DEADLINE):
            yield {"text": text}
        yield {"done": True}
    except TimeoutError:
        yield {"error": "This is taking longer than usual. Please try again."}
    except anthropic.APIError:
        yield {"error": "The AI service is busy. Please try again."}

@app.get("/health")
async def health():
    return {"ok": True}
```

Yen ippadi amaichirukku:

- **Response start aaguradhukku munnaadiye slot edukkappadudhu**, oru dependency-la, yenna 200 ponadhukku appuram oru 429 anuppa mudiyaadhu. Oru second wait chinna bursts-a ulvaangikkum; adhukku mela, oru amaidhiyaana queue-a vida oru seekkiramaana "busy" dhaan nalladhu. Stream mudinjadhum, disconnect aanaalum kooda, `finally` slot-a thiruppi kudukkum.
- **Deadline ovvoru wait-aiyum sutthi irukku, yield-a illa.** `with_deadline` ovvoru step-aiyum, retries-oda stream-a open panradhu udpada, ore end time-kku edhiraa time pannudhu. Oru `yield`-a sutthi oru timeout block vechaa async generators-la adhu sariyaa nadandhukkaadhu.
- **Cap ovvoru process-kkum thani**: 40 slots, 4 workers, 2 containers-naa ore nerathula 320 calls.

### Rate limits: ungalodadhum provider-odadhum

Saayangaala peak-la, provider-oda 429 dhaan romba adhigamaa varra failure. Backoff, **jitter**-oda (wait-la oru random pagudhi, appo aayirakkanakkaana clients ore nodiyila retry panna maattaanga) konja neram retry pannunga; SDK idha seiyudhu, `retry-after`-aiyum madhikkudhu, adhanaala count-a deadline-kkulla adangura alavu kuraivaa vainga. Appuram thelivaa fail pannunga, alladhu oru gateway vazhiyaa innoru region-kko approve aana oru chinna model-kko fallback pannunga (LLM gateways lesson-a paarunga). **Ovvoru user-aiyum limit pannunga**, udhaaranamaa 10 nimishathukku 20 kelvigal, oru daily token cap; illainaa oru script ellaarukkumaana quota-va theerthudalaam, unga bill-kku uchavarambe irukkaadhu. Unga sondha 429-la `Retry-After` irukkum, unga front end adha follow pannanum.

### Health, readiness, shutdown

- **`/health`** (liveness) process uyiroda irukku-nnu sollum, vera edhaiyum thodaadhu, adhanaala platform unmaiyileye maattikitta processes-a mattum restart pannum.
- **`/ready`** (readiness) indha instance traffic edukka mudiyum-nu sollum: oru index-a load panradhu maadhiri start-up velai mudiyara varai 503. Oru shared dependency-kkaaga adha fail pannaadheenga. Ellaa instance-um ore database-a check pannaa, oru blip ellaathaiyum ore nerathula fail pannum, balancer ellaathaiyum eduthudum, oru partial outage oru total outage-aa maaridum. Ovvoru request-kkum oru thelivaana error return pannunga, thaniyaa alert pannunga.
- **Rendume model-a call pannaadhu.** Adhukku panam aagum, oru medhuvaana provider ellaa instance-aiyum ore nerathula unhealthy-aa mark pannidum.

**Graceful shutdown.** Oru deploy-la, platform SIGTERM anuppum. Server connections edukkaradha niruthittu, odikittirukkura requests-a `--timeout-graceful-shutdown` varai mudiya vidum. Adhu unga romba neelamaana stream-a vida adhigamaa irukkanum, platform-oda grace period server-odadha vida adhigamaa irukkanum, illainaa platform mudhalla process-a kill pannidum. Kubernetes default-aa 30 seconds kudukkum (`terminationGracePeriodSeconds`-a koottunga). Cloud Run SIGTERM-kku appuram 10 seconds mattum dhaan kudukkum, adhanaala anga oru scale-down-la neelamaana streams vettappadalaam; client oru retry option kudukkattum.

### Oru queue-oda background jobs

OCR alladhu 500 pages irukkura oru PDF-a index panradhu maadhiri nimishakkanakkula edukkura velai oru worker process-kku pogum, request udane oru job id-a return pannum. Redis Queue (RQ) vechu:

```python
from fastapi import HTTPException
from redis import Redis
from rq import Queue
from rq.exceptions import DuplicateJobError

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents/{doc_id}/index")
def start_indexing(doc_id: str):        # plain def: runs in a thread, so Redis cannot block the loop
    job_id = f"index-{doc_id}"          # same document, same job id
    try:
        queue.enqueue("workers.index_pdf", doc_id, job_id=job_id, unique=True,
                      job_timeout=1800, result_ttl=86400)
    except DuplicateJobError:
        pass                            # a double click or a client retry: the job already exists
    return {"job_id": job_id, "status_url": f"/jobs/{job_id}"}

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    if job is None:
        raise HTTPException(404, "Unknown or expired job")
    return {"status": job.get_status()}
```

RQ 2.8-la serkkappatta `unique=True` submission-a **idempotent** aakkudhu: adhe request rendu thadavai vandhaa ore job dhaan. `result_ttl` mudinja job-a oru naal vechirukkum; default 500 seconds, adhukku appuram status URL 404 return pannum. Worker-aiye rendu thadavai odinaalum safe-aa irukkura maadhiri aakkunga, yenna oru worker paadhiyila crash aagalaam. Celery, Arq, cloud task queues ellaame idhe pattern-a dhaan follow pannudhu.

Ovvoru request-kkum oru line log pannunga: request id, user, model, tokens, cost, time to first token, total time, outcome (done, deadline, provider error, shed). p95 time to first token, shed rate, provider 429 rate-a gavaninga; oru request-a services muzhukka follow panradha tracing lesson cover pannudhu. ### Unga browser-la try pannunga

Arubadhu requests onnaa varudhu; ore nerathula patthu dhaan oda mudiyum. Eppavum marukkaadha oru queue-a, oru 429-kku munnaadi oru kurugiya wait-oda compare pannunga.

```python
import asyncio, random, time

async def model_call(slots, max_wait, waits):
    t0 = time.perf_counter()
    try:
        await asyncio.wait_for(slots.acquire(), max_wait)   # None queues forever
    except asyncio.TimeoutError:
        return "rejected"                                   # send a fast 429: busy, retry soon
    waits.append(time.perf_counter() - t0)                  # time spent waiting for a slot
    try:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model call
    finally:
        slots.release()
    return "served"

async def burst(cap, max_wait, n=60):
    slots, waits = asyncio.Semaphore(cap), []
    results = await asyncio.gather(*(model_call(slots, max_wait, waits) for _ in range(n)))
    print(f"max_wait {str(max_wait):>4}: served {results.count('served'):>2}, "
          f"rejected {results.count('rejected'):>2}, worst wait {max(waits, default=0):.2f} s")

random.seed(1)
for max_wait in (None, 0.1, 0.01):
    await burst(cap=10, max_wait=max_wait)
```

Limit illainaa, kadaisi request start aaguradhukku munnaadi sumaar anju model-call neram kaathirukkum; real calls seconds kanakkula edukkumbodhu, users vittuttu pora andha amaidhiyaana spinner adhu dhaan. Oru kurugiya wait irundhaa, koodudhal requests udane "busy"-nnu kettukkum.

## Oru worked example

Idhu oru illustrative case: numbers endha maadhiri maatrathai edhirpaarkkalaam-nu kaattudhu, idhu measure panna study illa. Lucknow-la oru edtech-oda doubt-solving assistant ore oru Uvicorn process-aa oduchu. Saayangaalam, edhaavadhu text-kkaaga students sumaar 12 seconds kaathirundhaanga. Sumaar moonula oru pangu requests load balancer-oda 30-second limit-a thottuchu, yenna stream aagaadha oru answer muzhusaa mudiyara varai edhaiyum anuppaadhu. Upload panna kaiyezhuthu notes mela OCR oru `async def` endpoint-kkulla oduchu, ellaarukkum server-a freeze pannuchu.

Maatrangal:

- FastAPI-oda SSE support vechu **streaming**. Staging-la answer innum ore thadavaiyaa vandhuchu, yenna nginx ingress adha buffer pannuchu; `/answer`-kku buffering-a off pannadhum sariyaachu.
- **Oru container-kku naalu workers, rendu containers**, oru worker-kku 40 model slots, ore nerathula 320 calls provider quota-kkulla adangudhu-nnu check pannadhukku appuram.
- **Layers-aa timeouts**: oru retry-oda SDK 10 s, oru model call-kku 25 s deadline, rendukkum mela balancer-oda 30 s idle timeout. Deadline fire aanaa, student "This is taking longer than usual; please try again"-nnu paarppaanga.
- **Limits**: oru student-kku 10 nimishathukku 20 kelvigal, ellaa slots-um busy-aa irukkumbodhu `Retry-After`-oda oru seekkiramaana 429, adhu "Many students are asking right now, retrying in 5 seconds"-nnu kaattappadum.
- **OCR oru background queue-la**, file-la irundhu derive panna oru job id-oda, adhanaala oru double tap ore oru job-a dhaan uruvaakkum. Result ready aagura varai page "Reading your notes..."-nnu kaattum.
- **Health-um deploys-um**: `/ready` start-up-a mattum check pannum; graceful shutdown 30 s, oru 40 s platform grace period-kkulla.

| --- | --- | --- |
| Mudhal text-kkaana neram, p95 | Sumaar 12 s | Sumaar 1-la irundhu 2 s |
| Timeout-a thodura requests | Sumaar 33% | 1%-kku keezha |

## Podhuvaa panra thappugal

- **`async def`-kkulla oru sync client.** Oru blocking Redis, database alladhu HTTP call andha worker-la irukkura ellaa request-aiyum freeze pannidum.
- **SDK timeout-a oru deadline-aa nambaradhu.** Retries-um `retry-after` waits-um adhukku mela serndhukkum.
- **Stream-kkulla cap-a check panradhu.** Adhukkulla 200 poyiduchu, oru 429 anuppa mudiyaadhu.
- **Caps perugum-nu marandhudaradhu.** 4 workers, 3 containers muzhukka oru process-kku 50-naa ore nerathula 600 calls, oruvelai provider quota-va vida romba adhigam.
- **Streaming-a localhost-la mattum test panradhu**, anga endha proxy-um adha buffer pannaadhu.
- **Oru shared dependency mela readiness check.** Oru database blip ellaa instance-aiyum onnaa eduthudum.
- **Platform-odadha vida neelamaana oru server grace period.** Platform mudhalla process-a kill panni, eppadiyum streams-a vettidum.
- **Oru 429-a udane retry panra clients**, oru kurugiya overload-a oru neelamaana overload-aa maathiduvaanga.
- **Random job ids**, adhanaala oru double click adhe selavaana job-a rendu thadavai start pannum.

## Elimaiyaana serving podhumaana nerangal

- **Sila users mattum irukkura internal tools**: oru process, model calls-kku oru deadline, oru health check podhum.
- Users-a eppavum sandhikkaadha **batch jobs**: oru web service-a vida oru scheduled script nalladhu.
- **Serverless routes**, anga platform workers-aiyum shutdown-aiyum manage pannum. Adhoda time limit-a unga romba neelamaana stream kooda compare panni check pannunga.

## Demo-la irundhu production-ku

- **Blocking calls-a edunga**, appuram pala workers ottunga.
- **Model calls-aiyum** ovvoru user-aiyum **cap pannunga**, mothathai provider quota kooda check pannunga.
- **Timeouts-a layer pannunga**, real path vazhiyaa stream pannunga.
- **Neelamaana velaiya queue pannunga**, idempotent job ids-oda, grace periods-a set pannunga.
- **Ovvoru request-kkum log pannunga**: tokens, cost, time to first token, outcome; p95-a gavaninga.

## Practice pannunga

FastAPI-oda deployment concepts page-aiyum, streaming patthina adhoda custom responses page-aiyum padinga.

1. Model tokens-a server-sent events-aa stream pannunga, browser-la time to first token-a munnaadiyum appuramum measure pannunga.
2. Slot dependency-a 2 cap-oda serunga, ore nerathula 3 requests anuppunga, moonaavadhu request sumaar oru second-kkulla oru 429 vaangudhu-nnu confirm pannunga.
3. Munnaadi nginx alladhu unga platform-oda ingress-a vainga, stream thundu thundaa varudhu-nnu confirm pannunga, appuram buffering-a on panni adhu udaiyaradha paarunga.
4. Oru medhuvaana task-a oru idempotent job id-oda oru background job-kku maathunga. Adha rendu thadavai submit panni, ore oru job dhaan odudhu-nnu confirm pannunga.
5. `--workers 4 --timeout-graceful-shutdown 30`-oda ottunga, oru neelamaana stream-a start pannunga, server-a stop panni, stream mudiyudhu-nnu confirm pannunga.
