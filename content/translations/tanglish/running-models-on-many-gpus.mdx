## Idhu enna

Oru GPU-kku memory-um speed-um oru fixed alavu thaan. Rendu vera vera problems ungala niraiya GPUs use panna vaikkum:

1. **Model oru GPU-kku romba perusu.** 16-bit precision-la oru 70B model-kku weights-kku mattumae sumaar 140 GB venum, oru 80 GB GPU-a vida adhigam.
2. **Oru copy-aala unga ellaa users-kkum serve panna mudiyaadhu.** Model porundhinaalum, busy hour-kku pala copies thevaippadalaam.

Rendu adippadai badhilgal irukku: model-a **copy** pannunga, allathu **piringa**.

- **Replica parallelism** (training-la **data parallelism**-nu solvaanga): pala GPUs-la muzhu copies ottunga. Ovvoru copy-um vera vera requests-a serve pannum, allathu vera vera batches-la train pannum.
- **Model parallelism**: oru model-a GPUs muzhukka pirikkiradhu. Mukkiya vazhigal: **tensor parallelism** (ovvoru layer-kkulla irukkura velaiya pirikkiradhu), **pipeline parallelism** (layers-a stages-nu solra groups-aa pirikkiradhu), mixture-of-experts models-kku **expert parallelism** (vera vera experts-a vera vera GPUs-la vaikkiradhu).

Unmaiyaana systems idha saerthu use pannum: udhaaranamaa, 4 GPUs muzhukka piricha oru model, appadi pala groups replicas-aa.

Ellaa thaervaiyum ottura rule: **pirichaa communication cost aagum, communication-kku bandwidth venum.** GPUs evvalavu adikkadi pesanumo, avangalukku idaiyilaana link avvalavu vegamaa irukkanum.

## Idhu eppadi work aagudhu

### Replicas: model porundhumbodhellaam idhu thaan default

Ovvoru GPU-vum, allathu GPUs-oda ovvoru group-um, oru muzhu model-a vachu thannoda requests-a serve pannum. Copies onnukkonnu pesikkaradhae illa, adhanaala endha network-um podhum, onnu fail aanaa mathadhu serve pannitte irukkum.

Edha enga vaikkiradhu-nnu mudivu panradhu oru packing pudhir, kanakku simple thaan: 16-bit-la oru parameter-kku sumaar 2 bytes, 8-bit-la 1 byte, 4-bit-la 0.5 bytes. Udhaaranamaa, oru 80 GB GPU-la 16-bit-la rendu 8B models (ovvonnum 16 GB, motham 32 GB) vaikkalaam, allathu 8-bit-la oru 32B model (32 GB). Rendumae use pannakkoodiya 72 GB-la KV caches-kku sumaar 40 GB vidum. Engine-oda sondha use-kku indha lesson sumaar 10% spare vaikkudhu. (Niraiya versions-kku vLLM default-aa ovvoru GPU-voda memory-la 90% use pannuchu; recent versions default-a maathiduchu, adhanaala unga version-a check pannunga.)

### Tensor parallelism: ovvoru layer-oda velaiyaiyum pagirradhu

Oru transformer layer perumbaalum matrix multiplication thaan. Tensor parallelism ovvoru matrix-aiyum, sollunga 4 GPUs muzhukka pirikkudhu. Ovvoru GPU-vum weights-la kaalvaasiya vachu, thannoda slice-a ore nerathula compute pannum. Vazhakkamaana scheme-la (Megatron-LM-la irundhu vandhadhu), GPUs oru layer-kku rendu thadavai partial results-a saerkkum: attention-kku appuram oru thadavai, feed-forward block-kku appuram oru thadavai. 80 layers ulla oru 70B model-kku, generate panra ovvoru token-kkum adhu 160 exchanges.

Idhu yen latency-a kuraikkalaam: ovvoru pudhu token-kkum ovvoru weight-aiyum memory-la irundhu oru thadavai padikkanum. 4 GPUs irundhaa, ovvonnum kaalvaasiya padikkum, adhanaala oru token-kkaana neram kuraiyum, aanaa 4 madangai vida kuraivaa thaan.

Sikkal andha exchanges thaan. Avai chinnadhu, aanaa romba adikkadi nadakkum, adhanaala ungakitta irukkura miga vegamaana link venum:

| Link | Enga irukkum | Bandwidth (thoraayamaana alavu) | Edhukku nalladhu |
| --- | --- | --- | --- |
| NVLink (H100 SXM) | Oru server-kkulla GPUs idaiyila | 900 GB/s per GPU, rendu directions saerthu | Tensor parallelism |
| PCIe Gen5 x16 | GPU-la irundhu CPU; NVLink illaadha servers-la GPUs | 128 GB/s, rendu directions saerthu | Replicas; pipeline |
| InfiniBand NDR | Servers idaiyila | 400 Gb/s per port, ovvoru direction-layum sumaar 50 GB/s | Pipeline; training |

Oru cloud instance listing-a padikkumbodhu "SXM", "NVLink" (allathu "NVSwitch")-a thaedunga. Oru "PCIe" GPU card-la podhuvaa NVLink irukkaadhu, illa-nnaa rendu cards-a mattum inaikkura oru bridge irukkum. L40S maadhiri NVLink illaadha GPUs-la, tensor parallelism-a vida pipeline parallelism perumbaalum nalla throughput kudukkum-nu vLLM documentation solludhu.

**Valid sizes.** Attention heads GPUs-kku idaiyila pirikkappadudhu, adhanaala tensor-parallel size head count-a sariyaa vagukkanum. 64 heads ulla oru model 1, 2, 4, 8, 16, 32 allathu 64 GPUs use pannalaam, aanaa 3, 5 allathu 6 mudiyaadhu. Nadaimuraiyila, oru server-kkulla, adhu 1, 2, 4 allathu 8.

**Gotcha: shared key-value heads.** Perumbaalaana modern models attention heads-oda groups muzhukka keys, values-a share pannudhu. 8 key-value heads ulla oru 70B model-a 8 GPUs muzhukka pirichaa, ovvoru GPU-layum oru key-value head irukkum, adhanaala KV cache samamaa piriyum. 16 GPUs muzhukka pirichaa ovvoru key-value head-um rendu GPUs-la copy aagum, adhanaala oru GPU-kkaana cache surunguradhu ninnudum.

### Pipeline parallelism: layers-a stages-aa pirikkiradhu

Layers 1-la irundhu 40-a server A-layum, 41-la irundhu 80-a server B-layum vainga. Oru request stage A vazhiyaa odi, network-a kadandhu, appuram stage B vazhiyaa odum.

Latency pathi thulliyamaa irunga. 80 layers oru GPU-la irundhaalum pala GPUs-la irundhaalum, oru request avai ellaathaiyum varisaiyaa kadakkum. Adhanaala pipeline parallelism ovvoru stage boundary-kkum oru chinna hop mattum saerkkum, aanaa adhu **oru request-a vegamaakkaadhu**, yenna endha stage-um innoru stage-oda velaiya pagirndhukkaradhilla. Tensor parallelism oru request-a vegamaakkalaam; pipeline-aala mudiyaadhu.

Adhoda balam bandwidth: ovvoru stage-um thannoda output-a mattum, oru stage-kku oru thadavai anuppudhu, oru layer-kku rendu thadavai illa. Adhanaala thaan links medhuvaa irukkura servers muzhukka pipeline-a use panraanga.

Adhoda balaveenam idle time, adha **bubble**-nu solvaanga. Ore oru request in flight-la irundhaa, oru nerathula oru stage mattum thaan velai seiyum. Ellaa stages-aiyum busy-aa vaikka, batch-a **micro-batches**-aa vettuvaanga, avai onnu pinnaadi onnaa pipe-la pogum. Training-la, `p` stages, `m` micro-batches irundhaa, nerathula sumaar (p − 1) ÷ (m + p − 1) pangu idle-aa irukkum. Udhaaranamaa, 4 stages, 16 micro-batches-naa sumaar 3 ÷ 19, adhaavadhu 16% veen. Serving-la niraiya concurrent requests adhe maadhiri pipe-a nirappum.

### Mixture-of-experts models-um expert parallelism-um

Oru **mixture-of-experts (MoE)** model-la, ovvoru layer-layum niraiya feed-forward "experts" irukkum, oru chinna router ovvoru token-aiyum adhula siladhukku mattum anuppum. Sizing rendu vera vera numbers-a follow pannum:

- **Memory total parameters-a follow pannum.** Ovvoru expert-aiyum load pannanum, yenna adutha token-kku adhula edhu venumnaalum thevaippadalaam.
- **Oru token-kkaana compute active parameters-a follow pannum.** Thaerndhedutha experts mattum thaan odum.

Udhaaranamaa, Qwen3-235B-A22B-kku 235B total parameters, adhula oru token-kku sumaar 22B active (128 experts-la 8). 8-bit-la adhoda weights-kku sumaar 235 GB venum, adhanaala kuranjadhu 80 GB-oda 4 GPUs venum (4 × 72 = 288 GB use pannakkoodiyadhu), cache-kku sumaar 53 GB thaan micham. Oru 8-GPU server innum niraiya idam kudukkum. Aanaalum ovvoru token-kkum sumaaraa oru 22B dense model-oda compute thaan aagum.

**Expert parallelism** vera vera experts-a vera vera GPUs-la vachu, ovvoru token-aiyum adhoda expert irukkura GPU-kku anuppum. Attention pagudhi podhuvaa copy pannappadum (data parallel) allathu tensor parallelism-aala pirikkappadum. vLLM-la idhu ore oru flag, `--enable-expert-parallel`. Rendu gotchas: popular experts overload aagum, mathadhu summaa irukkum, adhanaala engines expert load balancing kudukkudhu; periya batch sizes-la, kittathatta ovvoru expert-aiyum aedhaavadhu oru token use pannum, adhanaala MoE-oda memory-reading savings surungum.

### Neelamaana inputs: context, sequence parallelism

**Context parallelism** oru romba neelamaana input-a, udhaaranamaa oru 500,000-token document-a, chunks-aa vetti vera vera GPUs-la vaikkum. Keys, values group-kkulla suthi anuppappadumbodhu, ovvoru GPU-vum thannoda chunk-kku attention compute pannum. **Sequence parallelism** tensor parallelism-kku oru training add-on: normalisation maadhiri, tensor parallelism muzhusaa vittudura layer pagudhigala sequence-padi pirichu, activation memory-a michappaduthum. Romba neelamaana contexts-la mattum thaan idhula aedhaavadhu onnu thevaippadum.

### Serving-a vida training-kku romba adhiga memory venum

Mixed precision, Adam optimiser-oda full training oru parameter-kku sumaar 16 bytes vachirukkum: 16-bit weights-kku 2, gradients-kku 2, 32-bit optimiser states-kku 12 (weights-oda oru master copy, rendu running averages). Oru 70B model-kku adhu activations-kku munnaadiye sumaar 1,120 GB. **Sharded data parallelism** (DeepSpeed-la ZeRO, PyTorch-la FSDP) indha states-a copy pannaama data-parallel GPUs muzhukka parappum. Periya training runs idha tensor, pipeline parallelism kooda saerthu use pannum. Fine-tuning-kku, LoRA-um quantisation-um podhuvaa idhula perumbaalaanadhukkaana thevaiyaiye neekkidum.

### Engine ungalukkaaga enna pannudhu

vLLM-la, oru model-a 4 GPUs muzhukka pirikkiradhu ore oru setting thaan:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 NVLink-connected GPUs in this server.
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)
```

Oru server-kku romba periya model-kku, vLLM guide-oda rule of thumb: tensor-parallel size oru server-la irukkura GPUs ennikkaikku samam, pipeline-parallel size servers ennikkaikku samam. 8 GPUs-oda rendu servers-naa `--tensor-parallel-size 8 --pipeline-parallel-size 2`. Servers muzhukka vLLM default-aa Ray use pannum (oru Ray cluster-a start panni, appuram oru server-la oru `vllm serve` ottunga); oru multiprocessing launcher innoru option.

| Approach | Edha pirikkudhu | Thevaiyaana link | Edhukku best | Mukkiya cost |
| --- | --- | --- | --- | --- |
| Replicas (data parallelism) | Edhuvum illa; muzhu copies | Edhuvaanaalum | Adhiga users, failover | Ovvoru copy-um porundhanum |
| Tensor parallelism | Ovvoru layer-kkulla irukkura matrices | NVLink, oru server-kkulla | Romba periya models, oru token-kku kuraivaana neram | Ovvoru token-kkum oru layer-kku rendu exchanges |
| Pipeline parallelism | Layers-oda groups | Nalla network podhum | Servers muzhukka parava; training | Latency laabam illa; bubbles |
| Expert parallelism | Oru MoE model-oda experts | Vegamaanadhu; tokens experts-kitta pogum | Periya MoE models | Experts muzhukka samamillaadha load |
| Context allathu sequence parallelism | Input sequence | Vegamaanadhu | Romba neelamaana inputs | Complexity |
| Sharded data parallelism | Gradients, optimiser states | Periya models-kku vegamaanadhu | Periya models-a train panna | Koodudhal communication |

**Unga browser-laye try pannunga.** Oru model-kkum traffic-kkum valid-aana migach chinna tensor-parallel size-a kandupidinga. Numbers-a maathip paarunga.

```python
def kv_cache_gb(layers, kv_heads, head_dim, tokens, bytes_per=2):
    # 2 = one key and one value per token, per layer, per key-value head
    return 2 * layers * kv_heads * head_dim * bytes_per * tokens / 1e9

def smallest_tp(params_billion, bytes_per_param, cache_gb, gpu_gb, heads, usable=0.9):
    need = params_billion * bytes_per_param + cache_gb
    for tp in (1, 2, 4, 8):                      # sizes that fit in one 8-GPU server
        if heads % tp == 0 and tp * gpu_gb * usable >= need:
            return need, tp
    return need, None                            # needs pipeline across servers

# A 70B model: 80 layers, 64 heads, 8 key-value heads of size 128
cache = kv_cache_gb(80, 8, 128, tokens=60 * 4000)    # 60 requests x 4,000 tokens
for bpp, label in [(2, "16-bit"), (1, "8-bit")]:
    need, tp = smallest_tp(70, bpp, cache, gpu_gb=80, heads=64)
    print(f"{label}: {need:.0f} GB needed -> tensor-parallel size {tp}")
```

Idhu 16-bit-la sumaar 219 GB, size 4-nnum, 8-bit-la sumaar 149 GB, size 4-nnum print pannum. 8-bit model 2 GPUs-la porundhum, aanaa ovvoru copy-um kuraivaana requests-a serve pannaa mattum thaan: 4,000 tokens-la sumaar 56. Engine thaanae use panra oru GPU-kku sila GB-a indha script kanakkula edukkala, adhanaala oru margin vainga.

## Oru worked example

Hyderabad-la oru insurer, 2,000 staff-kku oru 70B open model-a (80 layers, 64 attention heads, size 128 ulla 8 key-value heads) self-host pannanum-nu ninaikkuraanga, p95 first-token time 2 seconds-kku keezha irukkanum. Ovvoru server-layum NVLink-aala inaicha 80 GB-oda 8 GPUs irukku. Keezha irukkura traffic figures avangaloda planning estimates, measurements illa.

1. **Busy hour load.** Busy hour-la 600 staff active-aa irukkaanga, ovvoruthharum 2 minutes-kku oru request anuppuraanga-nnu vachukkunga: oru second-kku 5 requests. Ovvonnum streaming mudiya sumaar 12 seconds aagum. Requests in flight = arrivals × ovvonnoda neram = 5 × 12 = **60**. Ovvonnum sumaar 4,000 tokens vachirukkum (instructions, policy text, chat history, reply).
2. **KV cache.** 2 × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes, oru token-kku sumaar 0.33 MB. 60 × 4,000 tokens × 0.33 MB ≈ **79 GB**.
3. **Oru GPU-la porundhumaa?** 16-bit-la weights mattumae sumaar 140 GB; oru GPU-la use pannakkoodiyadhu 72 GB. Porundhaadhu.
4. **Valid-aana migach chinna split.** Rendu GPUs-la use pannakkoodiyadhu 144 GB: weights-kku aridhaa podhum, cache-kku idam illa. Moonula 216 GB, thevaiyaana 219 GB-kku konjam kuraivu, eppadiyum 64 heads-a vagukkaadhu. Naalula 288 GB: 140 GB weights poga sumaar **148 GB** cache, 4,000 tokens-oda sumaar 112 requests-kku idam. Tensor-parallel size 4.
5. **Capacity, failover.** Oru copy busy hour-a thaangum, aanaa ore oru fault service-a niruthidum. 4 GPUs-oda rendu copies oru server-a nirappum; muzhu server-um fail aanaa oru rendaavadhu server kaappaathum.
6. **Cost.** Oru GPU-hour-kku ₹362-ngra oru example rate-la (E2E Networks-oda H100 page-la irukkura on-demand price, 28 November 2026 annaikku check pannadhu, 18% GST-kku munnaadi), 730 mani nera maasathukku oru 8-GPU server-kku 8 × 362 × 730 ≈ **₹21.1 lakh** aagum, GST-oda sumaar ₹24.9 lakh. Provider, plan-a poruthu prices maarum, adhanaala quotes vaangunga. 22 naalukku, oru working day-kku oruthharukku 40 requests-naa, adhu maasathukku sumaar 7 billion tokens, adhaavadhu oru million tokens-kku sumaar ₹300. Idha vida kuraivaana vilaiyulla hosted API malivu, data avanga sondha servers-laye irukkanum-naa thavira. Raathirila oru copy mattum ottunaalum panam micham.

| Layout | GPUs | Oru copy-kku cache idam | 4,000 tokens-la oru copy-kku requests | p95 first token (udhaaranathukku) |
| --- | --- | --- | --- | --- |
| Tensor 4, oru copy | 4 | Sumaar 148 GB | Sumaar 112 | 1.4 s; failover illa |
| Tensor 4, rendu copies (thaerndhedutthadhu) | 8 | Sumaar 148 GB | Sumaar 112 | 0.9 s; oru GPU fault-a thaangum |
| 8-bit-la Tensor 2, naalu copies | 8 | Sumaar 74 GB | Sumaar 56 | quality nilaichaa 0.8 s |
| Tensor 8, pipeline 2, oru copy | 16 | Sumaar 1,010 GB | Thevaiyai vida romba adhigam | Vegam koodaadhu; rendu madangu GPUs |

Memory columns kanakkup pottadhu; latency column oru load test enna kaattalaam-nu oru udhaaranam mattum. 8-bit option mudhalla unmaiyaana claim notes-la quality tests-a pass pannanum.

## Podhuvaana thappugal

- **Oru GPU-la porundhura model-a pirikkiradhu.** Replicas simple, vegamaana links thevaiyilla, failures-aiyum thaangum.
- **Weights-a mattum vachu size panradhu.** Busy hour-kkaana KV cache weights alavukke perusaa irukkalaam.
- **PCIe allathu network-la tensor parallelism.** Adhu oru layer-kku rendu thadavai pesum; oru server-kkulla NVLink-laye vainga.
- **Head count-a vagukkaadha tensor-parallel size.** Engine start aaga marukkum; 2, 4 allathu 8 use pannunga.
- **Pipeline parallelism latency-a kuraikkum-nu edhirpaarkkuradhu.** Adhu servers muzhukka parava udhavum; oru request-a orubodhum vegamaakkaadhu.
- **Mixture-of-experts model-a active parameters vachu size panradhu.** Ellaa experts-um memory-la irukkanum.
- **Key-value heads ennikkaiya thaandi pirikkiradhu.** Oru GPU-kkaana cache surunguradhu ninnudum.
- **Ore oru copy.** Oru GPU fault service-aiye niruthidum.
- **Average traffic-a vachu size panradhu.** Busy hour-kku size pannunga, unmaiyaana prompt lengths-la load tests pannunga.

## Idhu edhuvumae thevaiyillaadha neram

- **Hosted APIs**: provider adha paathukkuvaanga. Mudhalla avangaloda oru million tokens price-a unga GPU cost kooda compare pannunga.
- Cache-kku idathoda oru GPU-la porundhura **chinna models**: thevaippadumbodhu replicas saerthaa podhum.
- **LoRA, quantisation-oda fine-tuning**, idhu perumbaalum ore GPU-la porundhidum.

## Demo-la irundhu production-kku

- GPUs vaangaradhukku allathu rent panradhukku munnaadi **oru copy-kkaana memory-a measure pannunga** (unga context length, concurrency-la weights-um KV cache-um).
- **Links-a check pannunga**: tensor parallelism plan panradhukku munnaadi instance listing-la "SXM", "NVLink" irukku-nnu confirm pannunga.
- Unmaiyaana prompt, reply lengths-oda **ovvoru layout-aiyum load-test pannunga**, average illa, p95-a paarunga.
- Makkal nambi irukkura endha service-kkum, onnukku maerpatta servers-la **kuranjadhu rendu copies vainga**.
- **Ovvoru replica-vaiyum monitor pannunga**: queue length, KV cache use, latency, errors. Queue valarumbodhu copies saerunga.
- **Working day-kku aetha maadhiri scale pannunga**: traffic kuranjaa raathirila kuraivaana copies.
- **Model maarinadhukku appuram re-plan pannunga**, yenna size, head counts, context length ellaam layout-a maathum.
