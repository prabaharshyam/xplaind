## Idhu enna

**System design**-na oru software system-oda pagudhigal eppadi serndhu velai seiyanum-nu mudivu panradhu, adhanaala adhu users-ku thevaiyaanadha, adhu ethirkollura scale-la, adhoda budget-kulla seiyum. Idhula components (apps, services, databases, caches, queues), adhukkulla data eppadi pogudhu, edhaavadhu fail aanaa enna nadakkum-nu ellaam varum.

Oru correct-aana answer-aa irukkradhu rombavae arithu. Nalla design-na adhoda choices requirements-ku set aagi, trade-offs veliya sollapattirukkum. Interviewers-um idhaiye paarppaanga: theliva oru process, sensible numbers, nermaiyaana trade-offs, oru perfect diagram-a vida.

```flow
dir: LR
1. Requirements | idhu enna seiyanum? Evvalavu vegam, evvalavu periya, evvalavu reliable? -> 2. Estimates | users, requests per second, storage, bandwidth, average-layum peak-layum
2. Estimates -> 3. High-level design | clients, load balancer, app servers, cache, database, queue, workers
3. High-level design -> 4. Deep dive | data model, hot paths, scaling
4. Deep dive -> 5. Trade-offs-um failures-um | edhu udayum, neenga enna choose pannineenga, yen
```

## Idhu eppadi work aagudhu

**1. Requirements clarify pannunga.** Adha **functional** requirements (system enna seiyum, example "users seat book pannalaam", "users order status paarkkalaam"), **non-functional** requirements (evvalavu nallaa seiyum: latency, availability, consistency, scale, cost, security)-nu pirichukkunga. Users yaaru, evvalavu per, entha features scope-la irukku-nu kelunga. Answers-a ezhudhi vechukkunga.

**2. Estimate pannunga.** **Back-of-the-envelope estimate** users-a load-aa maathum. Useful facts: oru naal-ku sumaar 1 lakh seconds (86,400), adhanaala oru naalaikku 1 crore requests-na sumaar 115 per second; peaks-ku average-oda palamadangu plan pannunga. Storage-a estimate pannunga: oru item size × naalukku items × evvalavu naal vechirukkanum. Indha numbers thaan oru database podhumaa, neraya thevaiyaa-nu mudivu pannum.

**3. High-level design-a sketch pannunga.** Main boxes-um arrows-um varainga: clients, oru load balancer, stateless app servers, oru cache, oru database, files-ku object storage, mella velaigalukku background workers-oda oru queue. Oru request-a modhalla irundhu kadaisi varaikkum odi kaattunga.

**4. Deep dive.** Indha system-ku romba mukkiyamaana pagudhigala therndhedutthu deep-aa poonga: data model-um adhoda indexes-um, romba busy-aana path-a eppadi scale panradhu, data-va eppadi consistent-aa vechukkradhu, illa thideernu varra spike-a eppadi handle panradhu.

**5. Trade-offs-um failures-um.** Ovvoru choice-kum enna vilai-nu sollunga. Cache reads-a vegamaakkum, aana pazhaya data tharalaam; queue spikes-a smooth pannum, aana delay serkkum; neraya replicas availability-a ethum, aana selavu adhigam. Ovvoru component-kum "indha box fail aanaa enna?"-nu kelunga.

| Non-functional thevai | Typical numbers | Design levers |
|---|---|---|
| Latency | Oru page-ku p95 200 ms-kku keezha | caches, CDNs, kammi hops, indexes |
| Throughput | Aayirakkanakkana requests per second | adhigam app servers, load balancing, async velai |
| Availability | 99.9% = oru maadhathukku sumaar 43 min down | replicas, health checks, single point of failure illa |
| Consistency | Payments-ku strong, likes-ku eventual | transactions, primary-only reads, idempotency |
| Cost | Oru lakh requests-ku rupees | sariyaana size machines, caching, selavu kammi storage tiers |

**Browser-la try pannunga.** Back-of-envelope numbers thaan perumbaalaana designs-a mudivu pannum. Inputs-a maathi odunga.

```python
daily_users = 200_000
requests_per_user = 15
peak_factor = 3
bytes_per_record = 2_000

per_second = daily_users * requests_per_user / 86_400
print(f"average {per_second:,.0f} requests/s, peak about {per_second * peak_factor:,.0f}/s")
storage_gb_year = daily_users * requests_per_user * bytes_per_record * 365 / 1e9
print(f"about {storage_gb_year:,.0f} GB of records a year")
```

## Oru worked example

Meera-kitta interview-la Bengaluru-la oru food delivery app-oda order-status page-a design panna solraanga: order panna aprom customers-ku "Preparing", "Picked up", "Arriving" rider-oda location-oda theriyum.

**Requirements.** Avanga kettu confirm pannuraanga: active orders-ku status-um rider location-um kaattanum; updates sumaar 5 seconds-kulla; naalukku 20 lakh orders, dinner peak-oda; history scope-la illa. Perfect freshness-a vida availability mukkiyam: konja seconds pazhaya location kaattinaalum paravaayilla.

**Estimates.** Naalukku 20 lakh orders, ovvonnum sumaar 40 nimidam active. Riders ovvoru 5 seconds-kum oru location anuppuraanga, adhanaala ovvoru order-um sumaar 480 updates uruvaakkum. Idhu naalukku sumaar 96 crore updates: average-la sumaar 11,000 per second, dinner peak-la oru 40,000 irukkalaam. Customers page-a adikkadi refresh pannuvaanga, adhanaala reads innum adhigam. Ovvoru location update-um sinnadhu, sumaar 100 bytes, aana delivery mudinjadhum avanga adha vechirukka thevaiyilla.

**High-level design.** Rider apps locations-a load balancer-ku pinnaadi irukkura oru ingestion service-ku anuppum. Ovvoru order-oda latest location Redis maadhiri in-memory store-la pogum, order ID key-aa, short expiry-oda. Order status changes main database-la ezhudhappadum, oru queue-layum publish aagum. Customer apps oru notification service-oda WebSocket connection-a thirandhu vachirukkum, adhu status-yum location changes-aiyum push pannum. Connection tharundhaa, app Redis-la irundhu padikkura oru read API-a poll panna maarum.

**Deep dive-um trade-offs-um.** Adhigamaana location stream main SQL database-la yen pogala-nu explain pannuraanga: naalaikku yaarukkum thevai illaadha data-kaaga adhu andha database-a bottleneck aakkidum. Refunds-ku, support-ku mukkiyamaana status database-la pogum. Trade-off-a sollraanga: oru node fail aanaa Redis kadaisi konja seconds-oda locations-a izhakkalaam, idhu inga paravaayilla, order status durable. Failure cases-oda mudikkuraanga: notification service down-na polling innum work aagum; Redis down-na page map illaama status-a kaattum.

Interviewer apram sonnaar, avanga paartha vishayam boxes illa, ovvoru choice-um oru number-oda illa oru requirement-oda inaikkapattirundhadhu thaan.

## Podhuvaa panra thappugal

**Kekkaama varaiyradhu.** Requirements illaama diagram-ku kudhichaa, thappaana problem-ku confident-aana design aagum. Mudhal konja nimidangalai kelvikku selavu pannunga.

**Numbers-a skip panradhu.** Estimate illaama, oru database podhumaa-nu solla mudiyaadhu. Roughaana numbers-a kooda theliva sonnaa adhu onnum illaama irukkradha vida nallaa.

**Peak-ku illa, average-ku design panradhu.** Sales, results day, Tatkal windows normal traffic-a vida palamadangu kondu varum. Peak-ku size pannunga, spikes-a eppadi absorb pannuveenga-nu sollunga.

**Theriyura ella components-aiyum serkkradhu.** Ellaa idathulayum microservices, Kafka, Kubernetes irundha design-a run panradhu kashtam. Oru requirement-ku thevai-na mattum oru component-a serunga.

**Trade-offs-a maraikkradhu.** Ovvoru choice-kum oru vilai irukku. Adha veliya sollradhu judgement-a kaattum.

**Failure-a marakkradhu.** Ovvoru box-um down aanaa enna aagum-nu kelunga. Single points of failure thaan reviewers mudhalla thedura vishayam.
