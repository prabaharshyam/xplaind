## Idhu enna

Agents ethanai steps edukkanum-nu thaane mudivu pannudhu. Sila neram adhu thappaa pogum: oru tool fail aagitte irukkum, agent retry pannitte irukkum; rendu agents velaiya maathi maathi thallikkitte irukkum; allathu agent oru draft-a "improve" pannitte irukkum. Limits illai-nna, oru loop tokens-a erikkum, downstream systems-a adikkum, real actions-a thirumba thirumba seiyum.

Idhai moonu controls thadukkum:

- **Loop limits**: oru task-kku, sub-agents irundhaa oru run-kku, adhigapatcha steps allathu tool calls ennikkai.
- **Budgets**: oru task-kku, oru user-kku, muzhu feature-kku oru naalukku-nnu tokens, time, panathukku caps.
- **Kill switches**: deploy illaamale oru operator oru tool-aiyo, oru agent-aiyo, muzhu feature-aiyo niruththa oru vegamaana, nambagamaana vazhi.

Repetition checks, circuit breakers, rate, concurrency limits, idempotency keys idhukku support pannum.

```flow
title: Ovvoru limit-um enga check aagudhu
Ovvoru task | 15 steps, 60,000 tokens, 90 s varai -> Shared store | Postgres allathu Redis
Ovvoru model call | estimate-a reserve panni, appuram settle -> Shared store
Ovvoru tool call | kill switch, circuit breaker, idempotency key -> Shared store
Ovvoru naalum | oru student-kku ₹15, feature-kku ₹8,000 -> Shared store
Shared store -> Provider spend limit | kadaisi backstop
```

Indha lesson oru illustrative case-a follow pannudhu: Bengaluru-la oru edtech company-oda homework-help agent, ore raathiriyila adhoda weekly budget-a vida pathu madangu selavu pannuchu.

## Idhu eppadi work aagudhu

### Per-task limits

Loop-kkullaye steps, tool calls, tokens, aana neram ellaathaiyum count pannunga. Ovvoru cap-aiyum oru vaarathu real runs-la irundhu choose pannunga: 95th percentile-oda sumaar rendu madangu. 95% tasks 12 steps-layum ₹2-layum mudinjaa, 25 steps, ₹5 cap saadhaarana velaiya vettaama runaways-a niruthum. Model-aiyo prompt-aiyo maathumbodhu numbers-a thirumba paarunga.

Oru limit-a hit pannumbodhu, suthamaa stop pannunga: state-a save pannunga, enna mudinjudhu, adhukku badhilaa avanga enna pannalaam-nu user-kku eliya vaarthaigalla sollunga, investigate panna vendiya failure-aa log pannunga. Stop aana oru task eppavume crash maadhiri theriyakkoodaadhu.

### Repetition checks, circuit breakers

Oru **repetition check** oru task-kkulla work aagum. Ore tool ore arguments-oda moonu thadavai call aanaa, allathu ore error varisaiyaa moonu thadavai thirumba vandhaa, task-a seekkirame mudichudunga.

Oru **circuit breaker** ella tasks muzhukka work aagum. Ovvoru tool-oda failures-aiyum shared store-la count pannunga. Udhaaranamaa, ella users-layum serthu oru nimishathula oru tool 20 thadavai fail aanaa, circuit-a "open" pannunga: adutha anju nimishathukku andha tool-kku varra ovvoru call-um tool-a adaiyaamale, oru thelivaana message-oda udane fail aagum. Appuram oru trial call-a mattum vidunga; adhu work aanaa, circuit-a close pannunga. Repetition check oru task loop aagradhai niruthum. Circuit breaker aayiram tasks ovvonnum konjam konjam loop aagradhai niruthum; ore raathiriyila varra periya bill podhuvaa ippadithaan uruvaagum.

### Sub-agents muzhukka run-level caps

Oru planner sub-agents-kitta velaiya kodukkumbodhu, ovvonnum thannoda 15-step cap-a madhikkalaam, aanaa mothha run noottrukkanakkaana steps edukkalaam. Ovvoru run-kkum oru root `run_id` kodunga, adhai ovvoru sub-agent-kkum pass pannunga, andha id-kku edhiraa shared store-la steps-a count pannunga. Mothathaiyum (udhaaranamaa oru run-kku 40 steps), hand-offs ennikkaiyaiyum (udhaaranamaa 4) cap pannunga.

### Oru user-kku, oru naalukku budgets

Oru user oru naalla panra selavai count pannunga, cap-a thaandinaa mariyaadhaiyaa maruthudunga. Muzhu feature-aiyum oru naalukku count pannunga, 50%, 80%-la top users, task types-a list panra alerts-oda, appo cap ellaaraiyum vetturadhukku munnaadiye yaaraavadhu nadavadikkai eduppaanga. Asia/Kolkata naatkalai use pannunga, appo unga users-oda nadu raathiriyila limits reset aagum.

Counts oru database allathu Redis maadhiri oru shared store-la irukkanum: memory-la count panra aaru servers cap-a vida aaru madangu anumadhikkum. Aanaa shared store mattum podhaadhu. Iyalbaa ezhudhura code "check, call, record":

1. Innaikkoda total-a padinga. Adhu ₹14, cap ₹15, adhanaala oru ₹1 call-kku anumadhi undu.
2. Model-a call pannunga.
3. Real cost-a total-la serunga.

Ore user-kitta irundhu varra irubadhu requests, edhuvum step 3-a adaiyuradhukku munnaadiye ellaame step 1-a seiyalaam, adhanaala irubadhume pass aagi selavu pannum. Step 3-a atomic aakkuradhu udhavaadhu: race irukkuradhu check-kkum spend-kkum naduvula irukkura gap-la. Indha bug-kku peru **check-then-act**.

Fix **reserve, then settle**. Call-kku munnaadi, pudhu total cap-kkulla irundhaa mattum succeed aagura ore conditional statement-la, oru upper-bound estimate-a total-la serunga. Call-kku appuram, estimate-a eduthuttu real cost-a vainga. Odittu irukkura ovvoru call-um erkanave count aagiyirukku, adhanaala endha check-um pazhaya total-a paarkkaadhu.

### Code-la oru race-safe budget

Indha version SQLite use pannudhu, adhanaala oru laptop-laye odum. Oru SQLite file ore machine-la irukkura processes-kku mattum thaan shared; pala servers irundhaa, idhe pattern-a Postgres allathu Redis-la use pannunga.

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from datetime import datetime
from zoneinfo import ZoneInfo

# Adds the estimate only if the new total stays within the cap; else returns no row.
RESERVE = """INSERT INTO spend (scope, day, paise) VALUES (?, ?, ?)
  ON CONFLICT (scope, day) DO UPDATE SET paise = spend.paise + excluded.paise
  WHERE spend.paise + excluded.paise <= ?
  RETURNING paise"""

@dataclass(frozen=True)
class Reservation:
    scopes: tuple
    day: str
    paise: int

def connect(path):
    db = sqlite3.connect(path, timeout=10, isolation_level=None)  # we run our own transactions
    db.execute("CREATE TABLE IF NOT EXISTS spend (scope TEXT, day TEXT,"
               " paise INTEGER NOT NULL, PRIMARY KEY (scope, day))")
    return db

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

@contextmanager
def write_tx(db):
    db.execute("BEGIN IMMEDIATE")           # take the write lock before reading anything
    try:
        yield
        db.execute("COMMIT")
    except BaseException:
        db.execute("ROLLBACK")
        raise

class OverBudget(Exception):
    pass

def reserve(db, caps, paise):
    """caps is {scope: cap in paise}. Reserve on every scope, or on none."""
    if paise > min(caps.values()):
        return None
    day = today()
    try:
        with write_tx(db):
            for scope, cap in sorted(caps.items()):       # same order everywhere
                if not db.execute(RESERVE, (scope, day, paise, cap)).fetchall():
                    raise OverBudget(scope)               # rolls back earlier scopes
    except OverBudget:
        return None
    return Reservation(tuple(sorted(caps)), day, paise)

def settle(db, r, actual_paise):
    """Swap the estimate for the real cost, on the day it was reserved."""
    with write_tx(db):
        for scope in r.scopes:
            db.execute("UPDATE spend SET paise = paise + ? WHERE scope = ? AND day = ?",
                       (actual_paise - r.paise, scope, r.day))
```

User, feature caps rendaiyum serthu `reserve`-a call pannunga. Adhu `None` return pannaa, mariyaadhaiyaa maruthudunga; illai-nna model-a call panni, appuram usage report-la irukkura cost-oda `settle` pannunga.

Details mukkiyam:

- **Ellaame allathu edhuvume illa.** User, feature counters ore transaction-la maarum, adhanaala feature cap maruthaa user-kku charge aagi nikkaadhu.
- **Panam muzhu paise-la.** Integers sariyaa koodum; floating-point rupees drift aagum.
- **Reservation thannoda naalai vachukkum.** Iravu 11:59-kku aarambikkira oru call, adutha naalukku illa, reserve aana naalukku edhiraa thaan settle aagum.
- **Failures safe pakkam vizhum.** `settle`-kku munnaadi server crash aanaa, estimate count aanapadiye irukkum; yaarum adhigamaa selavu panna maattaanga. Oru call provider-a adaiyave illai-nna, 0-oda settle pannunga. Enna bill aachu-nnu solla mudiyalai-nna, reservation-a appadiye vachukkunga.
- **Idhe shape matha idangallayum work aagum.** Postgres `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING`-a support pannudhu; conflict aagura row lock aagum, adhanaala rendaavadhu request kaathirundhu appuram pudhu total-a paarkkum. Deadlocks-a thavirkka scopes-a oru fixed order-la lock pannunga (`sorted` call). Redis-la, read, compare, `INCRBY` moonaiyum ore Lua script-la vainga; Redis adhai atomic-aa ottum.
- **Feature row oru hot spot.** Ovvoru request-um adhai konja neram lock pannum. Romba adhiga traffic-la, adhai pala rows-aa piringa allathu Redis use pannunga.

### Call-kku munnaadi cost-a estimate panradhu

Reservation oru upper bound-aa irundhaa mattum thaan cap nikkum. Input tokens-a count pannunga (unga provider-oda token counter-aala, illai-nna adhigamaa estimate pannunga), model muzhu `max_tokens`-aiyum ezhudhum-nu eduthukkunga:

```python
def estimate_paise(input_tokens, max_tokens, in_paise_per_m, out_paise_per_m):
    """Upper bound: every input token, plus the most output max_tokens allows."""
    cost = input_tokens * in_paise_per_m + max_tokens * out_paise_per_m
    return -(-cost // 1_000_000)                     # round up to whole paise
```

Udhaaranamaa, oru model-kku oru million input tokens-kku ₹25, oru million output tokens-kku ₹125 aagudhu-nnu vachukkunga (idhu karpanai numbers; unga provider-oda price page-a use pannunga, adhai check panna date-a record pannunga). 3,000-token prompt, `max_tokens` 1,000-oda `estimate_paise(3000, 1000, 2500, 12500)`-a reserve pannum, adhu 20 paise. Perumbaalaana calls seekkirame mudinjudum, meedhiya `settle` thiruppi kodukkum.

Rendu gotchas. Unga provider output-aa bill panra ellaathaiyum, reasoning tokens irundhaa adhaiyum serthu, `max_tokens` bound pannudhaa-nnu check pannunga. Neenga stream pannaa, output vara vara count pannalaam, oru run budget-o kill switch-o stop-nu sonnaa stream-a close pannalaam; cancel aana stream-a unga provider eppadi bill pannudhu-nnu theriyura varaikkum, muzhu reservation-aiyum vachukkunga.

### Concurrent test-aala niroobikkiradhu

Oru race real concurrency-la mattum thaan veliya varum. Inga irubadhu workers, ovvonnum thanithani servers maadhiri thannoda sondha connection-oda, ore user-kku ore nerathula 100 calls pannudhu:

```python
import time
from concurrent.futures import ThreadPoolExecutor

CAPS = {"user:u42": 1500, "feature:homework": 800_000}   # ₹15 and ₹8,000

def one_call(db):
    r = reserve(db, CAPS, 200)          # estimate: ₹2
    if r is None:
        return 0
    time.sleep(0.01)                    # stands in for the model call
    settle(db, r, 150)                  # real cost: ₹1.50
    return 150

def test_cap_holds_under_concurrency(tmp_path):
    path = tmp_path / "budgets.db"
    connect(path).close()
    def server(_):
        db = connect(path)
        return sum(one_call(db) for _ in range(5))
    with ThreadPoolExecutor(max_workers=20) as pool:
        spent = sum(pool.map(server, range(20)))
    total = connect(path).execute(
        "SELECT paise FROM spend WHERE scope = 'user:u42' AND day = ?", (today(),)).fetchone()[0]
    assert 0 < spent == total <= 1500
```

Enga runs-la idhu ovvoru thadavaiyum pass aachu, ₹13.50 selavu. Check-then-spend version, adhe test-la, ₹15 cap-kku edhiraa ₹42 varaikkum vittuduchu. Indha test-a CI-la vachukkunga, appo yaarum reservation-a "simplify" panni eduthuda maattaanga.

### Rate, concurrency limits

Innum rendu limits unga panathai illaama unga systems-a paadhukaakkum:

- **Rate limits** oru nimishathukku varra requests-a cap pannum. Oru podhuvaana algorithm **token bucket**: ovvoru user-oda bucket-layum adhigapatcham, udhaaranamaa, 10 tokens irukkum, ovvoru aaru seconds-kkum onnu refill aagum. Ovvoru request-um oru token edukkum; bucket kaaliyaa irundhaa "slow down"-nu artham. Chinna bursts pass aagum, aanaa average oru nimishathukku pathulaye irukkum.
- **Concurrency limits** ore nerathula odura tasks-a cap pannum, udhaaranamaa oru user-kku 2. Appo "try again"-a pathu thadavai azhuthinaa, pathu illa, rendu tasks thaan odum. Oru "running" counter mela reserve pattern-a use pannunga, adhai oru `finally` block-la release pannunga, ovvoru slot-kkum oru expiry kodunga, yenna crash aana server thannoda `finally`-a ottave ottaadhu.

### Kill switches

Kill switch-na unga code ovvoru step-kkum ovvoru tool call-kkum munnaadi check panra oru flag, levels-oda: oru tool-a disable panradhu (ella refunds-aiyum niruthuradhu), agent-a disable panradhu (oru human queue-kko oru simple form-kko fall back aagradhu), allathu feature-a disable panradhu. Redeploy pannaama oru admin screen-la irundho oru config service-la irundho flip pannunga. Flags-a oru short cache-oda shared store-la irundhu padinga, appo oru maatram ella idathulayum sila seconds-kkulla effect-kku varum:

```python
import json, logging, time

log = logging.getLogger("agent")
WRITE_TOOLS = {"send_email", "issue_refund", "message_driver"}
MAX_STALE = 60                                           # seconds
_cache = {"read_at": float("-inf"), "ok_at": float("-inf"), "flags": {}}

def flags():
    now = time.monotonic()
    if now - _cache["read_at"] > 5:                      # refresh every 5 seconds
        _cache["read_at"] = now
        try:
            _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
            _cache["ok_at"] = now
        except Exception:
            log.warning("flag store unreachable; using last flags")
    if now - _cache["ok_at"] > MAX_STALE:                # no good read for a minute
        return {**_cache["flags"], "write_tools_off": True}
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    if tool and f.get(f"tool_{tool}_off"):
        return False
    return not (tool in WRITE_TOOLS and f.get("write_tools_off"))
```

`config_store`-na ungakitta irukkura endha shared store-aavum irukkalaam: oru database row, Redis, allathu oru feature-flag service. Indha code oru bounded vazhiyila safe-aa fail aagum. Oru chinna outage edhaiyum maathaadhu. Oru nalla read illaama oru nimisham aanaa, allathu start-up-la mudhal read fail aanaa, emails, refunds maadhiri write tools off aagum, read-only tools thodarndhu work aagum. Pazhaya flags-a ennaikkume vachukkittaa, outage nerathula flip panna oru switch vandhu serave seraadhu.

### Actions-kku idempotency

Ovvoru real-world action-kkum, adhai unique aakkuradhula irundhu build panna oru key kodunga (udhaaranamaa order id, refund reason). Receiving system adhe key-oda varra rendaavadhu action-a marukkum, adhanaala loops-um retries-um payments-aiyo messages-aiyo thirumba seiya mudiyaadhu.

### Kill switch-a drill pannunga

Maasathukku oru thadavai, mudhalla staging-la, appuram production-la oru amaidhiyaana nerathula, ovvoru switch-aiyum flip panni, tasks sila seconds-kkulla stop aagudhaa, users-kku oru thelivaana message theriyudhaa, app-oda matha pagudhigal thodarndhu work aagudhaa-nnu check pannunga. Nerathai alandhu, yaar pannaanga-nnu record pannunga. Orubodhum practice pannaadha teams, switch start-up-la mattum thaan padikkappattuchu, allathu on-call-la irundha yaarukkum adhu enga irukku-nnu theriyalai-nnu oru real incident-la thaan kathukkuvaanga.

## Oru worked example

Homework-help agent oru maasam nallaa oduchu, vaarathukku sumaar ₹18,000 model selavula. Appuram, oru nyaayitrukkizhamai raathiri, oru maths tool-la vandha oru maatram oru vagai kelvikku adhai error return panna vachudhu. Agent chinna chinna maatrangaloda retry pannuchu, students "try again"-a azhuthikkitte irundhaanga. Thingal kaalaikkulla feature ₹1.8 latcham selavu panniyirundhuchu, oru saadhaarana vaarathai vida pathu madangu.

Team oru maasathu runs-a eduthu, adhula irundhu limits-a set pannaanga:

- **Per task.** 95% tasks 7 steps, 25,000 tokens, 40 seconds-la mudinjudhu, adhanaala caps 15 steps, 60,000 tokens, 90 seconds. Moonu ore maadhiri tool errors vandhaa task "Indha kelviya ennaala solve panna mudiyala; unga teacher udhavuvaanga"-nnu mudiyum.
- **Per student.** 95% students oru naalukku ₹6-kku keezha thaan selavu pannaanga, adhanaala cap ₹15, oru friendly "naalaikku vaanga"-vaa kaattappadum. Ovvoru student-um ore nerathula 2 tasks ottalaam.
- **Oru naalukku feature.** Vaarathukku ₹18,000-na oru naalukku sumaar ₹2,600, saadhaarana naatkallaye romba busy-aana naal sumaar ₹4,000. Cap ₹8,000, oru average naaloda sumaar moonu madangu, romba busy-aana naaloda rendu madangu. 50% (₹4,000), 80% (₹6,400)-la on-call engineer-oda phone-kku alerts pogum.
- **Circuit breaker** maths tool mela: oru nimishathula 20 failures vandhaa adhai anju nimishathukku pause pannum.
- **Kill switch.** Ovvoru tool-kkum agent-kkum oru admin toggle. Agent-a off pannaa "homework help oyvula irukku"-ngra oru banner kaattum; app-oda matha pagudhigal thodarndhu odum.
- **Provider.** Backstop-aa oru hard monthly spend limit.

Andha nyaayitrukkizhamai raathiri ovvoru control-um enna panniyirukkum:

| Control | Incident mela effect |
| --- | --- |
| Circuit breaker | Fault vandha oru nimishathukkulla, ella students-kkum maths tool-a pause pannum |
| Repetition check | Loop aagura ovvoru task-aiyum moonu errors-kku appuram mudikkum |
| Per-student cap, 2 running tasks | "Try again" damage-a pala madangu aakkuradhai niruthum |
| ₹8,000 feature cap | Endha naalum ₹8,000-kku mela aagaadhu, andha raathiri aana ₹1.8 latchathukku edhiraa |
| ₹4,000-la alert | Innum malivaa irukkumbodhe yaaraiyaavadhu ezhuppum |

Rendu vaaram kazhichu, idhe maadhiri oru tool fault oru nimishathukkulla circuit breaker-a trip pannuchu. Bill sila nooru roobaai thaan, endha student-um complaint panradhukku munnaadiye alert team-a adainjuduchu.

## Podhuvaa panra thappugal

- **Step cap illaama irukkiradhu.** Idhu thaan ellaathaiyum vida malivaana paadhukaappu; mudhalla idhai serunga.
- **Memory-la vacha budgets.** Ovvoru server-um thaniyaa count pannum, unmaiyaana total cap-a romba thaandi pogum. Oru shared store use pannunga.
- **Check-then-act budgets.** Total-a padichu, model-a call panni, appuram cost-a serthaa, ore nerathula varra requests ellaame adhe check-a pass pannidum. Mudhalla reserve pannunga, ore statement-la.
- **Upper bounds illaadha estimates.** Average cost-a reserve pannaa, cap leak aagum. Muzhu `max_tokens`-kku reserve pannunga.
- **Concurrent tasks-kku cap illaama irukkiradhu.** Pathu parallel tasks ovvonnum per-task cap-a pass pannum.
- **Per-agent caps mattum.** Velaiya maathi maathi thallura sub-agents-kku oru root run-kku ore count venum.
- **Deploy thevaippadra kill switch.** Oru incident-la ungalukku seconds venum, build pipeline illa.
- **Start-up-la mattum padikkura kill switch.** Adutha restart varaikkum adhu edhuvum seiyaadhu.
- **Fail open aagradhu.** Flag store romba neram down-aa irundhaa, write tools-a off-aa eduthukkunga.
- **Sathamillaadha stops.** Enna nadandhuchu-nnu user-kku sollunga, log pannunga; stop aana task fix panna vendiya oru bug.
- **Idempotent illaadha actions-a retry panradhu.** Idempotency keys use pannunga, appo loops payments-aiyo messages-aiyo thirumba seiya mudiyaadhu.
- **Floating-point panam.** Paise-a integers-aa count pannunga.

## Eppo simple limits podhum

- **Unga sondha team use panra oru prototype**: oru step cap-um provider-oda spend alert-um mattume podhumaa irukkalaam.
- **Onnu rendu model calls mattum irukkura fixed workflows**, oru request-kku cost predictable-aa irukkura idathula.
- **Sila users mattum irukkura read-only internal tools.**

Veliyaatkal runs-a start panna mudiyumbodho, agents actions edukka mudiyumbodho thaan per-user budgets, feature caps, layered kill switches mukkiyamaagum.

## Demo-la irundhu production-kku

- **Budgets-a shared storage-la atomic-aa reserve pannunga**, ovvoru model call-kkum munnaadi, appuram settle pannunga.
- **Flags-aiyum circuit breakers-aiyum check pannunga**, ovvoru step, tool call-kkum munnaadi.
- **Feature budgets-la 50%, 80%-la alert pannunga**, adhigamaa selavu panra top users-a list panni.
- **Concurrent budget test-a CI-la vachukkunga.**
- **Kill switches-a maasaamaasam drill pannunga**, ovvonnum evvalavu neram eduthuchu-nnu record pannunga.
- **Ovvoru stop-aiyum kaaranathoda log pannunga**, limits sariyaa set aagiyirukkaa-nnu review pannunga.

## Practice pannunga

Unbounded consumption pathina OWASP-oda entry-a padinga.

1. Neenga build panna oru agent-la step, token, time caps-a, oru suthamaana stop message-oda serunga.
2. Moonu ore maadhiri tool errors-kku appuram task-a mudikkira oru repetition check-a serthu, venumne udaicha oru tool-aala adhai trigger pannunga.
3. Indha lesson-la irukkura reserve-and-settle budget-aiyum kill switch-aiyum serthu, rendum work aagradhai kaattunga.
4. Unga budget code-kku edhiraa concurrent test-a ottunga. Appuram `reserve`-a oru saadhaarana "total-a padichu, appuram serkkura" version-aala maathi, test fail aagradhai paarunga.

**Mudinjadhu-nnu eppo sollalaam:** oru tool-a venumne udaichu, agent unga limits-kkulla stop aagradhai oru log entry-odayum oru alert-odayum kaatta mudiyumbodhu.
