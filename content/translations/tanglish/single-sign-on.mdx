## Idhu enna

**Single sign-on (SSO)**-la employees avanga company account-la oru thadavai sign in panni, pudhu passwords illaama approved ella apps-ayum access pannalaam. Idhu company-oda identity provider vazhiyaa work aagum, example Microsoft Entra ID, Okta, Google Workspace, Ping. Oruthar company-a vittu poraanga-na, IT oru account-a disable pannina, ellathukkum access nindrudum.

Moonu standards mukkiyam:

- **OAuth 2.0**: oru app user-oda sarbula, limited-aana, thirumba edukka mudiyura permission-oda, access tokens vazhiyaa velai seiya vidum. Thaniyaa paatha idhu permission pathi, identity pathi illa.
- **OpenID Connect (OIDC)**: OAuth 2.0-oda mela oru sign-in layer. App-ku oru **ID token** kidaikkum, adhu user yaaru-nu solum, email, name, group memberships maadhiri claims-oda. Perumbaalaana pudhu apps OIDC use pannudhu.
- **SAML 2.0**: pazhaya, XML-based SSO standard. Neraya periya Indian enterprises-um government bodies-um internal apps-ku innum idha use pannudhu.

```flow
User app-a open pannuraanga -> Ungaloda app sign in-ku redirect pannum -> Identity provider | Entra ID, Okta
Identity provider -[password + MFA, provider-ku mattum theriyum]-> Konja neram mattum irukkura code-oda thirumba redirect
Konja neram mattum irukkura code-oda thirumba redirect -> Ungaloda app code-a tokens-aa maathum
Ungaloda app code-a tokens-aa maathum -> ID token (yaaru) + access token (enna)
ID token (yaaru) + access token (enna) -> Signature, issuer, audience, expiry verify pannu -> Session create pannu | user id, email, groups
```

Indha lesson-la Chennai-la oru automobile-parts manufacturer-oda plant staff-ku roll out panna quality-documents assistant-a follow pannuvom.

## Idhu eppadi work aagudhu

**OIDC sign-in flow** (PKCE-oda authorisation code flow, recommended-aanadhu):

1. User ungaloda app-a open pannuraanga; adhu avangala identity provider-ku redirect pannum.
2. Avanga angae sign in pannuvaanga, aduthadha multi-factor authentication-oda. Ungaloda app avanga password-a paarkkavae paarkkaadhu.
3. Provider oru konja neram mattum irukkura code-oda thirumba redirect pannum.
4. Ungaloda server andha code-a ID token-aagavum access token-aagavum maathum.
5. Ungaloda server token-oda signature, issuer, audience, expiry-a verify panni, apram thanoda session-a create pannum.

**Claims-um groups-um.** ID token-la user-oda groups illa roles irukkalaam ("claims-officers-south", "hr-admins"). Ungaloda app-ku thevaiyaana groups-a serkka client-oda identity team-a kelunga. Idhu thaan user ungaloda app-la enna panna mudiyum-nu, apram entha documents retrieve panna mudiyum-nu mudivu pannum.

**User-aa downstream systems-a call panradhu.** Ungaloda AI app-ku vera system-la irundhu data thevai padalaam, example SharePoint illa oru internal API. Best pattern: user-oda token-a andha system-ku scoped aana token-aa maathunga ("on-behalf-of" flow), adhanaala andha system user-oda sondha permissions-a apply pannum. Shared service account andha permissions-a bypass pannidum.

**App-a register panradhu.** Client-oda identity team ungaloda app-a provider-la register pannum: adhoda redirect URLs, entha users illa groups use pannalaam, entha claims anuppanum. Periya companies-la idhukku nimidangal illa, naal aagum-nu ethirpaarunga. Request-a mudhal vaaramae aarambinga.

**Library use pannunga.** Token validation-a neengale ezhudhaadheenga. Provider-oda SDK illa ungaloda framework-ku well-known library use pannunga.

**Entha standard varum-nu ethirpaakkalaam:**

| Situation | Varakkoodiya standard | Notes |
| --- | --- | --- |
| Pudhu web app, modern provider | OIDC | Romba simple, JSON tokens, nalla libraries |
| Periya enterprise, pazhaya internal apps | SAML 2.0 | XML assertions; library illa gateway use pannunga |
| User-kaaga API-a call panra app | OAuth 2.0 access tokens | Kuruganna scope kodunga |
| SharePoint illa Box padikkura AI app | OIDC sign-in plus on-behalf-of | Downstream system user permissions-a apply pannum |

**Registration request.** Oru page request neraya naal thirumba thirumba pesuradhai miccham pannum. App-oda peru, purpose, ovvoru environment-oda redirect URLs, use panna vendiya groups, thevaiyaana claims (email, name, groups), user-kaaga vera systems-a call pannudha, entha scopes-oda, oru technical contact ellaam serunga. Entha groups already irukku-nu identity team-a kelunga, pudhusa create pannaadheenga, yen-na groups create panni nirappuradhu thaan aduthadha romba mella nadakkura step.

**Sign-in-ku aprom sessions.** Tokens verify aanadhum, sensible lifetime-oda oru server-side session vachukkunga, example plant shifts-ku ettu mani neram, session renew aagum podhu group membership-a thirumba check pannunga. IT account-a disable pannina, adutha renewal fail aagum, access mudiyum.

**FastAPI-yum Authlib-yum vachu OIDC sign-in.** Library redirects, PKCE, code exchange, token checks ellaathaiyum paathukkum:

```python
import os
from authlib.integrations.starlette_client import OAuth
from fastapi import FastAPI, Request, HTTPException, Depends
from starlette.middleware.sessions import SessionMiddleware

app = FastAPI()
app.add_middleware(SessionMiddleware, secret_key=os.environ["SESSION_SECRET"], https_only=True,
                   max_age=8 * 3600)

oauth = OAuth()
oauth.register(
    name="corp",
    server_metadata_url=os.environ["OIDC_DISCOVERY_URL"],   # e.g. .../v2.0/.well-known/openid-configuration
    client_id=os.environ["OIDC_CLIENT_ID"],
    client_secret=os.environ["OIDC_CLIENT_SECRET"],
    client_kwargs={"scope": "openid email profile", "code_challenge_method": "S256"},
)

@app.get("/login")
async def login(request: Request):
    return await oauth.corp.authorize_redirect(request, request.url_for("callback"))

@app.get("/auth/callback")
async def callback(request: Request):
    token = await oauth.corp.authorize_access_token(request)    # verifies the ID token
    claims = token["userinfo"]
    request.session["user"] = {"id": claims["sub"], "email": claims.get("email"),
                               "groups": claims.get("groups", [])}
    return {"signed_in": claims.get("email")}

def require_group(group):
    def check(request: Request):
        user = request.session.get("user")
        if not user or group not in user["groups"]:
            raise HTTPException(status_code=403)
        return user
    return check

@app.get("/admin/reports")
def reports(user=Depends(require_group("claims-officers-south"))):
    return {"ok": True, "for": user["email"]}
```

Session-la verified subject id-yum groups-um thaan store aagum, browser anuppuna edhuvum illa. User-oda key-aa `sub` claim-a (illa provider-oda object id-a) use pannunga, email-a illa, yen-na email maarum.

**API-ku anuppura tokens-a verify panradhu.** Oru front end bearer tokens-a ungaloda API-ku anuppina, ovvoru request-layum check pannunga:

```python
import jwt

jwks = jwt.PyJWKClient(os.environ["OIDC_JWKS_URL"])

def verify(bearer):
    key = jwks.get_signing_key_from_jwt(bearer)
    return jwt.decode(bearer, key.key, algorithms=["RS256"],
                      audience=os.environ["API_AUDIENCE"], issuer=os.environ["OIDC_ISSUER"])
```

Signature, audience, issuer, expiry ellaathaiyum `jwt.decode` check pannum; edhaiyum skip pannaadheenga.

**Periya group lists.** Sila providers, oru user-ku romba groups irundha token-la groups list panradhai niruthidum (Microsoft Entra ID "overage" pointer-ku maarum). Onnu, app-oda groups-a mattum anuppa identity team-a kelunga (app roles oru clean vazhi), illa sign-in-la provider-oda API-la irundhu groups-a fetch pannunga.

**Leavers-um SCIM-um.** Identity provider-la user-a disable pannina pudhu sign-ins nindrudum, aana thirandhirukkura session mani neram nadakkalaam. Sessions-a short-aa vechukkunga, renewal-la thirumba check pannunga, client support pannina SCIM provisioning accept pannunga, adhanaala avanga directory-la user-a remove pannina, ungaloda app-layum udane deactivate aagum.

**SAML ezhudhaama SAML.** Client SAML mattum thandha, munnaadi oru gateway illa identity broker vechidunga (neraya managed auth services SAML-a OIDC-aa maathum), adhanaala ungaloda app oru standard-a mattum pesum.

**Browser-la try pannunga.** Oru ID token moonu base64 parts. Nadula irukkuradha decode panni claims-a paarunga, idhai thaan ungaloda library verify pannudhu.

```python
import base64, json

token = ("eyJhbGciOiJSUzI1NiJ9."
         "eyJzdWIiOiJ1LTQ0MSIsImVtYWlsIjoicHJpeWFAZXhhbXBsZS5pbiIsImdyb3VwcyI6WyJjbGFpbXMtc291dGgiXSwiZXhwIjoxOTAwMDAwMDAwfQ."
         "signature")
header, payload, signature = token.split(".")
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(claims)
print("never trust these until the signature, issuer, audience and expiry are checked")
```

## Oru worked example

Microsoft Entra ID use panra Chennai automobile-parts manufacturer, ungaloda quality-documents assistant 1,200 plant staff-ku kidaikkanum-nu virumburaanga.

Mudhal vaaram: identity team-ku oru page request anuppureenga: app peru, staging-um production-um redirect URLs, serkka vendiya groups (`quality-engineers`, `plant-chennai`, `plant-pune`, `contractors`), app user-kaaga SharePoint-a call pannanuma (aama, read-only).

Ungaloda FastAPI backend oru maintained OIDC library use pannudhu. Sign-in-ku aprom, adhu ID token-a verify panni, user-oda id, email, groups-a oru session-la store pannum. SharePoint-ku pogura requests on-behalf-of token use pannum, adhanaala oru Pune engineer avanga sondha SharePoint permissions allow panra documents-a mattum retrieve pannalaam.

Go-live-la contractors sign in panna mudiyala-nu complain pannuraanga. Provider-oda sign-in error avanga app-ku assign aagala-nu solludhu: identity team employee groups-a mattum assign pannirundhaanga, `contractors`-a illa. Provider-oda assignment-la oru maatram idha sari pannidum. Adutha maadham oru quality engineer company-a vittu pogum podhu, IT avanga account-a disable pannudhu, assistant-ku avanga access neenga edhuvum panna vendaamaa mudinjidum.

| Event | Enna nadandhudhu | Yaaru fix pannaanga |
| --- | --- | --- |
| Mudhal vaaram | Registration request anuppunaanga | Neenga, identity team-ku |
| Go-live | Contractors sign in panna mudiyala | Identity team group assignment-a serthaanga |
| Oru maadham kazhichu | Oru engineer company-a vittu ponaanga | IT oru account-a disable pannaanga; access thaanaagavae mudinjudhu |

## Podhuvaa panra thappugal

- **Sondha login-a neengale build panradhu.** Clients adha ethukka maattaanga, avanga security controls-a mosamaa duplicate pannum.
- **Token validation steps-a skip panradhu.** Signature, issuer, audience, expiry-a ovvoru thadavaiyum library vachu check pannunga.
- **OAuth access tokens-a identity-oda proof-aa use panradhu.** User yaaru-nu theriya OIDC ID token use pannunga.
- **Ella downstream calls-kum oru service account.** Appuram users avanga sondha permissions thadukkura vishayangalayum paarkkalaam.
- **App registration-a late-aa kekkradhu.** Identity teams-ku queues-um approvals-um irukku. Mudhal naalle kelunga.
- **Users-a email vachu key panradhu.** Emails maarum; stable subject illa object id use pannunga.
- **Renewal check illaama neenda sessions**, adhanaala poiruravanga access vachukkuvaanga.
- **Bearer tokens-la audience illa issuer checks-a skip panradhu.**

## Single sign-on thevai illaadha neram

- **Consumer apps**, angae Google, GitHub, email sign-in thaan users ethirpaarkkuradhu.
- **Oru team-oda prototype**, pilot approve aagura varaikkum managed auth service-oda email login podhum.
- **User illaadha machine-to-machine calls**, adhu client credentials illa API keys use pannum.

Enterprise clients kittathatta eppavum production-ku munnaadi SSO kekkuvaanga; mudhal vaaram irundhae adhukku plan pannunga.

## Demo-la irundhu production varaikkum

- **Registration request-a mudhal vaaramae anuppunga**, ovvoru environment-oda redirect URLs-oda.
- **Maintained libraries use pannunga** OIDC-kum token checks-kum.
- **Sessions-a short-aa vechukkunga**, renewal-la groups-a thirumba check pannunga.
- **SCIM illa deprovisioning hook-a support pannunga**, client tharum idathula.
- **Sign-ins, failures, group changes-a** audit log-la log pannunga.

## Practice pannunga

Okta-oda illustrated OAuth, OIDC guide-a padinga, apram Auth0-oda OIDC, SAML pages-a padinga.

1. Oru identity provider-la free developer account create panni, oru redirect URL-oda app register pannunga.
2. Ungaloda FastAPI app-la maintained library vachu OIDC sign-in serunga; sign-in-ku aprom verified claims-a print pannunga.
3. Oru group claim-a serthu, therndhedutha group-oda members mattum call panna mudiyura oru endpoint-a kaattunga.
4. Oru test user-aa sign in pannunga, provider-la avangala group-la irundhu remove pannunga, protected endpoint 403 kodukka evvalavu neram aagudhu-nu alandhu paarunga.

**Mudinjadhu-nu eppo sollalaam:** OIDC code flow-oda ovvoru step-aiyum explain panna mudiyum, allowed group-kku veliya irukkura user-a ungaloda app reject panradhai kaatta mudiyum.
