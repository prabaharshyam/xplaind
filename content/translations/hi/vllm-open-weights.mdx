## ये क्या है

**Open-weight models** अपने weights publish करते हैं, इसलिए आप उन्हें उनके licence के तहत अपने hardware पर चला सकते हो। **vLLM** एक open-source engine है जो ऐसे models को GPUs पर कुशलता से serve करता है। दो ideas इसे तेज़ बनाते हैं।

- **PagedAttention.** जब model जवाब लिखता है, तो वो हर पिछले token की एक memory रखता है, जिसे **KV cache** कहते हैं। पुराने servers हर request के लिए सबसे लंबे मुमकिन जवाब जितना एक लंबा block reserve कर देते थे, और उसका ज़्यादातर हिस्सा खाली पड़ा रहता था। vLLM cache को छोटे pages में रखता है, जो request बढ़ने पर ही जुड़ते हैं, ठीक वैसे जैसे operating system memory manage करता है। बहुत कम बर्बाद होता है, इसलिए एक GPU पर कहीं ज़्यादा requests फिट होती हैं।
- **Continuous batching.** GPU सबसे efficient तब होता है जब वो एक साथ कई requests पर काम करे। vLLM पूरे batch के ख़त्म होने का इंतज़ार करने की जगह, हर step पर, जैसे-जैसे दूसरी requests ख़त्म होती हैं, नई requests को batch में जुड़ने देता है।

vLLM एक **OpenAI-compatible API** expose करता है, इसलिए ज़्यादातर client code और gateways उसके साथ बिना बदले काम करते हैं।

```flow
title: vLLM server से होकर एक request
dir: LR
Client or gateway -[OpenAI-style API, एक key के साथ]-> vLLM server
vLLM server -> Scheduler | continuous batching: requests हर step पर जुड़ती और निकलती हैं
Scheduler -> KV cache in pages | PagedAttention; prompts की एक जैसी शुरुआत दोबारा use होती है
KV cache in pages -> GPU memory | weights और cache इसे share करते हैं
vLLM server -> Metrics | queue length, cache usage, time to first token
```

ये lesson Chennai की एक insurance company को follow करता है जिसे claim documents अपने ही servers पर रखने हैं।

## ये काम कैसे करता है

### Model चुनना

Leaderboard से नहीं, task और अपने evals से शुरू करो। फिर चार चीज़ें check करो।

- **Licence.** आज के कई models, जिनमें Qwen3.5 family और Gemma 4 शामिल हैं, Apache 2.0 के तहत release हुए हैं। कुछ दूसरे शर्तें जोड़ते हैं; Meta का Llama community licence इसका एक example है। आप जो exact weights download करते हो, उनके साथ आने वाली licence file पढ़ो।
- **Size और type.** 4 से 14 billion parameters वाले models एक GPU पर चलते हैं और extraction, classification और grounded RAG answers के लिए अक्सर काफ़ी होते हैं। Qwen3.5-35B-A3B (35 billion parameters, हर token पर लगभग 3 billion active) जैसे **mixture-of-experts (MoE)** model को अपने सारे parameters के लिए memory चाहिए, पर वो लगभग एक छोटे model जितनी तेज़ी से generate करता है।
- **Context length.** Long-context models काम के हैं, पर लंबे contexts की क़ीमत आप cache memory में चुकाते हो।
- **भाषाएँ.** Models के बीच ये बाक़ी किसी भी चीज़ से ज़्यादा बदलता है। अगला section देखो।

November 2026 तक, आम starting points में ये शामिल हैं: Qwen3.5 (0.8B से 397B तक sizes, February और March 2026 में release), Qwen3.6 (April 2026) और Qwen3.8-27B (August 2026), Gemma 4 (E2B से 31B तक), और OpenAI के gpt-oss-20b और gpt-oss-120b। हर महीने नए models आते हैं, इसलिए इसे test करने की एक shortlist समझो, ranking नहीं।

### भारतीय भाषाओं के लिए model चुनना

तीन checks किसी भी benchmark से ज़्यादा बताते हैं।

1. **हर word पर tokens (fertility).** ज़्यादातर English text पर बना tokenizer, Malayalam या Odia के words को कई छोटे टुकड़ों में तोड़ देता है। अगर किसी model को हर word पर तीन गुना tokens चाहिए, तो हर request पर तीन गुना compute लगता है, ज़्यादा समय लगता है, और उसी context में कम text फिट होता है। इसे अपने users के 200 असली sentences पर नापो:

```python
from transformers import AutoTokenizer

sentences = open("malayalam_sample.txt", encoding="utf-8").read().splitlines()
words = sum(len(s.split()) for s in sentences)
for name in ["Qwen/Qwen3.5-9B", "google/gemma-4-E4B-it"]:   # add every candidate
    tok = AutoTokenizer.from_pretrained(name)
    tokens = sum(len(tok.encode(s, add_special_tokens=False)) for s in sentences)
    print(f"{name}: {tokens / words:.2f} tokens per word")
```

2. **Native speakers का review किया हुआ golden set.** Native script, romanised text (Manglish, Hinglish) और code-mixed messages शामिल करो, क्योंकि असली users इन्हें मिलाकर लिखते हैं। Machine-translated test sets कमज़ोर models को असल से बेहतर दिखाते हैं।
3. **हर भाषा के लिए quantized quality.** Quantization अक्सर English की तुलना में lower-resource भाषाओं में ज़्यादा quality गिराता है। भारतीय भाषाओं के evals उसी quantized checkpoint पर चलाओ जिसे आप असल में serve करोगे।

Test में शामिल करने लायक candidates:

- **आम multilingual models.** Qwen3.5 कहता है कि वो 201 languages और dialects support करता है; Gemma 4 भी multilingual काम के लिए काफ़ी use होता है।
- **भारत के लिए बने models.** Sarvam AI ने February 2026 में Sarvam-30B और Sarvam-105B launch किए, दोनों mixture-of-experts models जिन्हें भारतीय भाषाओं को ध्यान में रखकर train किया गया, और Sarvam के मुताबिक़ Apache 2.0 के तहत। BharatGen का Param2-17B-A2.4B-Thinking भी vLLM के supported models में listed है।
- **एक translation step.** AI4Bharat का IndicTrans2 (MIT licence) English और 22 scheduled भारतीय भाषाओं के बीच translate करता है। ऐसी pipeline जो translate करे, एक strong English model चलाए, और वापस translate करे, कभी बेहतर होती है, कभी बदतर। इसे भी बाक़ी options की तरह test करो।

Gotcha: check करो कि आपका vLLM version उस exact checkpoint को support करता है। जब Sarvam के models launch हुए, तब उनका model card एक pending vLLM pull request की तरफ़ इशारा करता था; अब v0.34.0 की supported-models list में Sarvam के architectures शामिल हैं।

### GPU चुनना

क्या फिट होगा, ये memory तय करती है। Tokens कितनी तेज़ी से निकलेंगे, ये **memory bandwidth** तय करती है, यानी GPU अपनी memory कितनी तेज़ी से पढ़ता है, क्योंकि हर नया token सारे active weights को एक बार पढ़ता है।

| GPU memory | Example GPUs | 16-bit पर फिट | 4-bit पर फिट |
| --- | --- | --- | --- |
| 24 GB | NVIDIA L4, RTX 4090 | लगभग 8B तक, छोटे contexts | लगभग 14B तक |
| 48 GB | NVIDIA L40S, RTX 6000 Ada | लगभग 14B तक | 27B से 32B, cache के लिए जगह के साथ |
| 80 GB | NVIDIA A100 80 GB, H100 | 27B से 32B, थोड़ा cache | लगभग 70B, ठीक-ठाक cache |
| 141 GB | NVIDIA H200 | लगभग 60B | कुल लगभग 100B वाले MoE models |

भारत में आप इन्हें E2E Networks, जो Delhi NCR और Chennai में H100 capacity list करता है, और Yotta जैसे local GPU clouds से किराए पर ले सकते हो। योग्य startups, researchers और institutions सरकार के IndiaAI Compute Portal पर subsidised hours के लिए apply कर सकते हैं। Prices अक्सर बदलते हैं, इसलिए जिस दिन plan करो, उसी दिन providers के pages check करो।

### Memory का हिसाब

**Weights.** 16-bit पर लगभग 2 bytes per parameter, 8-bit पर 1 byte और 4-bit पर आधे byte से थोड़ा ज़्यादा। 27B model को 16-bit पर लगभग 54 GB और 4-bit पर लगभग 15 GB चाहिए।

**KV cache.** एक standard transformer में, हर token को `2 × layers × KV heads × head size × bytes` चाहिए। 2 keys और values के लिए है। ये चारों numbers model की `config.json` से पढ़ो। फिर इसे in flight tokens से गुणा करो: concurrent requests गुणा उनकी average length।

**अपने browser में try करो.** ये एक आम 8B model का shape (32 layers, 8 KV heads, head size 128) 16-bit पर use करता है:

```python
layers, kv_heads, head_dim, bytes_per = 32, 8, 128, 2
per_token = 2 * layers * kv_heads * head_dim * bytes_per      # 131,072 bytes
for users, context in [(10, 4000), (40, 4000), (40, 16000)]:
    gb = per_token * users * context / 1e9
    print(f"{users} users x {context} tokens: {gb:.1f} GB of KV cache")
```

ये लगभग 5, 21 और 84 GB print करता है। एक GPU कितने users को serve करेगा, ये आमतौर पर model नहीं, context length तय करती है।

दो gotchas। Qwen3.5 जैसे नए **hybrid** models लगभग हर चार में से एक layer में ही full attention use करते हैं, इसलिए उनका cache इस formula से कहीं छोटा होता है। Cache को 8-bit पर store करने (`--kv-cache-dtype fp8`) से वो आधा हो जाता है, पर quality पर असर होता है जिसे आपको नापना होगा।

### Quantization

Weights को 8 या 4 bits में store करने से weight memory लगभग आधी या तीन-चौथाई कम हो जाती है, और अक्सर generation भी तेज़ होता है, थोड़े quality loss के साथ। आम formats हैं **AWQ** और **GPTQ** (4-bit) और **FP8** (8-bit)। ऐसा checkpoint download करो जो पहले से quantized हो, जैसे model maker का publish किया हुआ; vLLM उसकी config से method पढ़ लेता है। `--quantization` flag किसी 16-bit model को AWQ में नहीं बदलता। Exception है `--quantization fp8_per_tensor` (सिर्फ़ `fp8` अब ऐसा नहीं करता), जो FP8 support वाले GPUs, जैसे L40S और H100, पर load time पर quantize करता है।

```bash
pip install vllm==0.34.0
vllm serve Qwen/Qwen3.5-9B --max-model-len 8192 --served-model-name chat-local
# now: POST http://localhost:8000/v1/chat/completions
```

Container में, weights एक volume पर रखकर:

```bash
docker run --gpus all --rm -p 8000:8000 \
  -v /data/hf-cache:/root/.cache/huggingface \
  -e HF_TOKEN -e VLLM_API_KEY \
  vllm/vllm-openai:v0.34.0 \
  --model Qwen/Qwen3.5-9B --revision <commit> \
  --max-model-len 8192 --served-model-name chat-local
```

`<commit>` की जगह Hugging Face से model का commit hash डालो, ताकि restart कभी बदले हुए weights pull न करे। `--served-model-name` वो नाम set करता है जो clients use करते हैं, इसलिए आप apps बदले बिना model swap कर सकते हो।

| Setting | Example | असल में क्या करता है |
| --- | --- | --- |
| `--max-model-len` | 8192 | एक request की length पर cap लगाता है। vLLM start-up पर check करता है कि ऐसी एक request cache में फिट होती है; ये हर request के लिए इतना reserve नहीं करता |
| `--gpu-memory-utilization` | set मत करो | v0.34.0 से, set न करने का मतलब 1.0 है। इसे, जैसे 0.5 पर, तभी set करो जब कोई दूसरा process GPU share करता हो |
| `--tensor-parallel-size` | 2 | एक machine में एक model को कई GPUs पर बाँटता है |
| `--kv-cache-dtype` | fp8 | Cache memory आधी करता है; quality नापो |
| `--speculative-config` | JSON | Speculative decoding: एक तेज़ guesser tokens draft करता है और model उन्हें check करता है, जिससे कम load पर latency घटती है |

**v0.34.0 में memory का बदलाव.** पुराने releases, जब तक अलग से न कहा जाए, GPU memory का 90%, बाद में 92%, use करते थे। v0.34.0 NVIDIA और AMD GPUs पर एक **extensible KV cache** on करता है: ये cache को warm-up के बाद असल में free memory से size करता है, और set न किया गया `--gpu-memory-utilization` अब 1.0 का मतलब रखता है। Release notes ज़्यादातर configs से ये flag हटाने की सलाह देते हैं। इससे दो gotchas निकलते हैं। उसी GPU पर कोई दूसरा process, जैसे एक embedding model, अब कोई memory नहीं पाता जब तक आप हर एक के लिए share set न करो। और notes कहते हैं कि कुछ models पर per-token latency बढ़ सकती है; opt out करने के लिए `--gpu-memory-utilization 0.9` या `--no-enable-extensible-kv-cache` pass करो। Default `--block-size` भी 16 से 64 हो गया है।

**Reasoning models.** आज के कई models जवाब देने से पहले "think" करते हैं। Model को कौन-से reasoning-parser और tool-call-parser flags चाहिए, ये GitHub पर vLLM की recipes repository में उस model के page पर देखो। इनके बिना thinking text जवाब में आ जाता है और JSON parsing तोड़ देता है।

### Structured output के साथ इसे call करना

```python
import os
from openai import OpenAI
from pydantic import BaseModel

class Claim(BaseModel):
    policy_number: str
    amount_inr: int
    reason: str

client = OpenAI(base_url="http://localhost:8000/v1", api_key=os.environ["VLLM_API_KEY"])
r = client.chat.completions.create(
    model="chat-local",
    messages=[{"role": "user", "content": "Extract: Policy HX-22981, claim of Rs 18,400 for a cracked windscreen."}],
    response_format={"type": "json_schema", "json_schema": {"name": "claim", "schema": Claim.model_json_schema()}},
)
print(Claim.model_validate_json(r.choices[0].message.content))
```

Server generation को schema के अंदर बाँध देता है, इसलिए reply parse हो जाता है। फिर भी values check करो, जैसा structured-output lesson में समझाया गया है।

### Endpoint को secure करना

`--api-key` (या `VLLM_API_KEY` variable) सिर्फ़ `/v1` के नीचे के routes और कुछ दूसरे prefixes को protect करता है। vLLM docs चेतावनी देते हैं कि दूसरे routes, जैसे `/invocations`, खुले रहते हैं। इसलिए vLLM को कभी सीधे expose मत करो। इसे अपने gateway के पीछे रखो, और Kubernetes network policy use करो ताकि सिर्फ़ gateway ही उस तक पहुँच सके।

### Go-live से पहले load testing

बढ़ती concurrency पर असली जैसे prompts भेजो और time to first token और total time record करो:

```python
import asyncio, time
from openai import AsyncOpenAI

aclient = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="your-key")

async def one(prompt):
    t0 = time.perf_counter(); first = None
    stream = await aclient.chat.completions.create(model="chat-local", stream=True, max_tokens=300,
                                                   messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if first is None and chunk.choices and chunk.choices[0].delta.content:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0

async def run(prompts, concurrency):
    sem = asyncio.Semaphore(concurrency)
    async def limited(p):
        async with sem:
            return await one(p)
    results = await asyncio.gather(*(limited(p) for p in prompts))
    ttft = sorted(r[0] for r in results if r[0]); total = sorted(r[1] for r in results)
    print(f"c={concurrency}: p95 first token {ttft[int(0.95 * (len(ttft) - 1))]:.2f}s, "
          f"p95 total {total[int(0.95 * (len(total) - 1))]:.2f}s")

# for c in (1, 8, 32, 64): asyncio.run(run(sample_prompts, c))
```

सबसे ऊँची concurrency जो p95 first-token time को आपके budget के अंदर रखे, वही एक replica की capacity है।

### इसे operate करना

vLLM `/metrics` पर Prometheus metrics expose करता है। Alert और scale CPU पर नहीं, `vllm:num_requests_waiting` (queue) और `vllm:kv_cache_usage_perc` (cache कितना भरा है) पर करो। Prefix caching default रूप से on है: जो requests एक ही system prompt या document से शुरू होती हैं, वो उसका cache दोबारा use करती हैं। Shared content को prompts की शुरुआत में रखो, और hit rate को `vllm:prefix_cache_hits` भाग `vllm:prefix_cache_queries` के रूप में track करो। एक spare replica रखो ताकि कोई failure या upgrade service न रोके, और weights को एक internal volume में रखो, क्योंकि start-up पर downloads धीमे होते हैं और locked-down networks पर अक्सर block हो जाते हैं।

## एक example से समझो

Chennai की एक insurance company को claim documents अपने ही servers पर रखने हैं। उसे claim forms से 20 fields extract करने हैं और अपने claims staff के लिए छोटे grounded answers चाहिए, दिन में लगभग 30,000 requests। नीचे के सारे numbers method दिखाने के लिए सिर्फ़ उदाहरण हैं।

**Model.** 300 असली forms पर evals, जिनमें Tamil forms भी हैं, तीन open-weight models की तुलना एक frontier API से करते हैं। सबसे अच्छा एक 27B dense model है: API के 97% के मुक़ाबले 95% field accuracy। Data अपने premises पर रखने के लिए company ये gap मान लेती है।

**Memory.** 16-bit पर weights को 54 GB चाहिए, जो 48 GB वाले L40S के लिए ज़्यादा है। Maker का 4-bit AWQ checkpoint लगभग 15 GB लेता है, और evals सिर्फ़ 94.5% तक गिरते हैं। मान लो runtime overhead लगभग 7 GB लेता है, तो cache के लिए लगभग 26 GB बचता है। Model की config 64 layers, 8 KV heads और head size 128 बताती है, तो हर token को 2 × 64 × 8 × 128 × 2 bytes, लगभग 0.26 MB चाहिए। यानी लगभग 99,000 tokens की जगह, या average 3,000 tokens वाली लगभग 33 requests।

**Traffic.** 10 घंटे के working day में 30,000 requests यानी लगभग 0.8 per second; मान लो peak इसका दोगुना है, लगभग 1.7 per second। अगर हर request लगभग 6 seconds लेती है, तो in flight requests = arrival rate × हर एक का समय (Little's law) = 1.7 × 6, लगभग 10। एक GPU 33 संभालता है, इसलिए वो peak झेल लेता है। दूसरा GPU headroom देता है और failures और upgrades के दौरान service चालू रखता है। एक load test पक्का करता है कि 30 concurrent requests पर p95 first-token time 2 seconds से कम है।

**Cost.** मान लो हर GPU ₹100 per hour का है, ये एक उदाहरण वाला figure है, quote नहीं। 730 घंटे के महीने के लिए दो GPUs का ख़र्च ₹1,46,000 है, यानी 9,00,000 requests per month पर लगभग ₹162 per 1,000 requests। मान लो API ₹100 per million input tokens और ₹400 per million output tokens लेता है, ये भी उदाहरण है। 3,000 input और 300 output tokens वाली हर request ₹0.42 की पड़ती है, यानी ₹420 per 1,000। Break-even है ₹1,46,000 ÷ ₹0.42, लगभग 3,48,000 requests per month या 11,600 per day। दिन में 3,000 requests पर self-hosting लगभग ₹1,620 per 1,000 पड़ेगा। किसी भी figure में GST या इसे चलाने वाले engineer का समय शामिल नहीं है।

| Option | Field accuracy | Weight memory | Cost per 1,000 requests | Notes |
| --- | --- | --- | --- | --- |
| Frontier API | 97% | लागू नहीं | ₹420 | Data premises से बाहर जाएगा |
| 27B model, 16-bit | 95% | लगभग 54 GB | Test नहीं किया | 80 GB GPU या दो GPUs चाहिए |
| 27B model, 4-bit AWQ | 94.5% | लगभग 15 GB | दो GPUs पर ₹162 | चुना गया: p95 पर 30 concurrent, 2 s से कम |

vLLM company के Kubernetes cluster पर pinned containers में चलता है, पहले वाले उसी gateway के पीछे, इसलिए application में सिर्फ़ एक model alias बदलता है। Upgrades हर तिमाही होते हैं, eval suite pass होने के बाद।

## आम गलतियाँ

- **Leaderboard से model चुनना.** अपने data पर, अपने users की भाषाओं और scripts में test करो।
- **Sizing में KV cache भूल जाना.** Weights फिट हो जाते हैं, फिर load पड़ने पर server धीमा हो जाता है या अटक जाता है। In flight tokens के हिसाब से size करो।
- **`--max-model-len` को model के maximum पर set करना.** 262,144-token की limit एक GPU पर start-up पर ही fail हो सकती है। इसे उतना रखो जितना आपके traffic को चाहिए।
- **आदत से `--gpu-memory-utilization 0.9` आगे ले जाना.** v0.34.0 पर ये cache से memory रोक लेता है। इसे तभी set करो जब GPU share हो।
- **बिना नापे quantize करना,** ख़ासकर भारतीय भाषाओं में, जो English से ज़्यादा quality खो सकती हैं।
- **Licences को नज़रअंदाज़ करना.** उन exact weights की licence file पढ़ो।
- **Unpinned image, engine या model revision,** जिससे restart चुपचाप outputs बदल देता है।
- **vLLM को सीधे expose करना,** सिर्फ़ `--api-key` के साथ; कुछ routes खुले रहते हैं।

## जब vLLM से self-host न करें

- **कम या अचानक ऊपर-नीचे होने वाला volume,** जहाँ idle GPUs का ख़र्च API calls से ज़्यादा होता है; break-even निकालो।
- **आपको सबसे strong models चाहिए,** जो शायद सिर्फ़ APIs के रूप में मिलें।
- **इसे चलाने वाला कोई नहीं.** GPUs, drivers, upgrades और on-call असली काम हैं।

## Demo से production तक

- **Image, vLLM version और model revision pin करो,** weights को volumes पर cache करके।
- हर model या setting बदलने के बाद **load test करो**, और एक replica की capacity record करो।
- **Queue length और KV cache usage पर alert और scale करो.**
- इसे एक alias, एक fallback और एक network policy के साथ **gateway के पीछे रखो**।
- Failures और rolling upgrades के लिए **एक spare replica रखो**।
