## ये क्या है

**Metadata** chunk के text की जगह chunk के बारे में जानकारी है। RAG में ये पाँच काम करता है:

- **Filters**: search को state, document type, language या date से सीमित करता है।
- **Citations**: बताता है कि जवाब ठीक-ठीक कहाँ से आया (document, section, page, link)।
- **Freshness**: पिछले साल वाले से नहीं, जो version in force है उससे जवाब देता है।
- **Permissions**: तय करता है कि chunk कौन देख सकता है।
- **बेहतर matching**: वो context जोड़ता है जो chunk के text में नहीं है, जैसे document का title या section path।

```flow
Chunk text | "This limit is 45 days." Hard to find on its own -> Stored with metadata | doc: Leave Policy 2026, section: Earned leave > Carry forward, page 4, state KA, access: all-employees
Stored with metadata -> Embedded text | "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days."
Stored with metadata -> Query filter | user's groups, user's state, in force today
Stored with metadata -> Citation | Leave Policy 2026, Karnataka, section 3.2, page 4
```

दिक़्क़त ये है कि metadata चुपचाप fail होता है। गलत date या गलत spelling वाला state सवाल के समय कोई error नहीं देता; सही chunk बस कभी वापस नहीं आता, और model गलत chunk से पूरे भरोसे के साथ जवाब दे देता है।

ये lesson बेंगलुरु की एक IT company के HR assistant को follow करता है, जो पाँच states को serve करता है। Exercise इन्हीं ideas को सरकारी orders पर ले जाती है, जहाँ versions और amendments और मुश्किल हैं।

## ये काम कैसे करता है

### Ingestion पर ही जमा करो

हर chunk के लिए कम से कम ये store करो:

| Field | Example | किस काम आता है |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations और links |
| `doc_group` | `LP` (सारे versions और translations) | Versions और language copies को जोड़ना |
| `section_id`, `section_path`, `page` | 3.2; Earned leave, Carry forward; page 4 | Precise citations, amendments, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | User के profile से filters |
| `issued_on` | 2025-12-10 | "The 2019 order" जैसे सवाल |
| `effective_from`, `effective_to` | 2026-01-01, खाली | Freshness और history वाले सवाल |
| `superseded_by` | खाली | जवाबों में "replaced by" notes |
| `language` | `en` | Filters, कौन-सी copy दिखानी है ये चुनना |
| `access_groups` | `all-employees` | Permissions |

अभी जमा करो; बाद में जोड़ने का मतलब है हर file को दोबारा parse करना।

**PDFs से इसे निकालना।** कुछ fields source system से आते हैं (link, owner, access groups)। बाकी document से ही पढ़ने पड़ते हैं: headers में order numbers, issue dates और section numbers। साफ़ digital PDFs के लिए rules ("No." और dates के लिए regular expressions) काम करते हैं; scanned files के लिए OCR और एक model चाहिए, और दोनों गलतियाँ करते हैं। निकाले गए fields पर भरोसा करने से पहले लगभग 50 documents का एक sample हाथ से check करो और हर field की errors गिनो। Dates पर ख़ास नज़र रखो: "03/12/2019" भारत में 3 December है, पर US defaults वाले parser के लिए 12 March, इसलिए format साफ़-साफ़ बताओ।

### Contextual text

जो chunk कहता है "This limit is 45 days" उसे retrieve करना मुश्किल है, क्योंकि उसमें कुछ नहीं बताता कि *कौन-सी* limit। जो text आप embed करते हो उसके आगे title और section path जोड़ो: "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days"। इसकी कोई cost नहीं है।

इससे मज़बूत तरीका है कि model से हर chunk के लिए एक-दो वाक्य लिखवाओ जो बताएँ कि वो chunk अपने document में कहाँ आता है। Anthropic ने इस "contextual retrieval" को अपने datasets पर test किया और report किया कि इसने top-20 retrieval failure rate को 35% घटाया, keyword (BM25) search पर भी लगाने से 49%, और reranking जोड़ने पर 67%। हर chunk पर एक model call लगती है, इसलिए अपने golden set पर नापो।

### Generated metadata

Model एक छोटा summary, keywords, या वो questions भी लिख सकता है जिनका जवाब chunk देता है। Generated questions तब काम आते हैं जब users documents से बहुत अलग शब्दों में पूछते हैं ("can I carry over my leave?" बनाम "Carry forward of earned leave")।

हर generated question को **उसके अपने vector के रूप में, parent chunk की id के साथ** store करो। जब question vector match हो, तो parent chunk return करो, question का text कभी नहीं, क्योंकि model को असली document से जवाब देना चाहिए। दो gotchas: generated questions chunk जितना कहता है उससे ज़्यादा का वादा कर सकते हैं, इसलिए एक sample spot-check करो; और वो पुराने पड़ जाते हैं, इसलिए chunk text का hash store करो और उसके बदलने पर दोबारा generate करो।

### Fixed vocabularies, code में validate किए हुए

Filters exact values compare करते हैं। Filter के लिए "HR", "Human Resources" और "hr dept" तीन अलग departments हैं। Departments, document types, states और languages के लिए fixed lists use करो, और हर chunk को index होने से पहले check करो:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, field_validator, model_validator

State = Literal["KA", "TN", "MH", "TS", "GJ", "ALL"]   # the client's five states, plus ALL
DocType = Literal["policy", "circular", "faq", "contract"]

class ChunkMeta(BaseModel):
    doc_id: str
    doc_group: str               # same for every version and translation
    title: str
    section_id: str              # stable id such as "3.2"
    section_path: str
    page: int
    doc_type: DocType
    state: State
    language: Literal["en", "hi", "ta", "kn", "mr", "te", "gu"]
    issued_on: date
    effective_from: date
    effective_to: date | None = None
    superseded_by: str | None = None
    access_groups: list[str]

    @field_validator("access_groups")
    @classmethod
    def not_empty(cls, v):
        if not v:
            raise ValueError("every chunk needs at least one access group")
        return v

    @model_validator(mode="after")
    def dates_in_order(self):
        if self.effective_to and self.effective_to < self.effective_from:
            raise ValueError("effective_to is before effective_from")
        return self
```

हर chunk को `ChunkMeta.model_validate` से गुज़ारो, जो pass हों उन्हें index करो, और जो fail हों उन्हें error के साथ एक quarantine table में लिखो। हर run पर quarantine counts report करो। "Karnatka" tag वाला document अब ज़ोर से fail होता है, बजाय इसके कि वो हर कर्नाटक employee की search से गायब हो जाए। State list client की असली list से बिल्कुल match होनी चाहिए; जो state आप जोड़ना भूल गए, उसके सारे documents quarantine में चले जाते हैं।

### Freshness: एक ही "in force" rule

सीधा-सादा "current" flag use मत करो। हर जगह एक ही date rule use करो: कोई chunk **किसी period में in force** है अगर `effective_from` उस period के आख़िरी दिन या उससे पहले हो, और `effective_to` खाली हो या period के पहले दिन या उसके बाद हो।

- **Default सवाल** ("how many leave days can I carry forward?"): period आज है, Asia/Kolkata time में।
- **"What was the rule in 2024?"**: period 1 January से 31 December 2024 तक है। 2023 से 2025 तक in force रही policy वापस आती है, भले ही वो 2024 से पहले शुरू हुई और अब superseded है।
- **"What did the 2019 order say?"**: ये 2019 में *जारी* हुए order के बारे में पूछ रहा है, इसलिए `issued_on` के साल से filter करो और ये मत देखो कि वो अभी in force है या नहीं।

एक gotcha: December में 1 January के लिए announce की गई policy अभी in force नहीं है। "Next year's policy" वाले सवाल के लिए period अगला साल होना चाहिए, वरना default rule उसे छिपा देगा।

जब नया version पूरे document की जगह लेता है, तो पुराने को उसी transaction में बंद करो, ताकि कोई भी search कभी दोनों versions एक साथ न देखे, और न ऐसा हो कि उसे एक भी न दिखे:

```sql
BEGIN;
UPDATE chunks SET superseded_by = 'HR-LP-2026', effective_to = '2025-12-31'
WHERE doc_id = 'HR-LP-2025';
INSERT INTO chunks (...) VALUES (...);   -- the new version's chunks
COMMIT;
```

Filtering date rule करता है। `superseded_by` इसलिए रखा जाता है ताकि जवाब कह सके "replaced by Leave Policy 2026"।

### Partial amendments

असली documents अक्सर एक बार में एक हिस्सा करके बदलते हैं। कोई सरकारी order कह सकता है "in paragraph 4 of order 112/2019, for 'Rs 300' substitute 'Rs 450'", और बाकी हर paragraph को in force छोड़ देता है। पूरे document वाला "superseded" flag ये बात नहीं कह सकता। पुराने order को superseded mark करो तो उसके बाकी paragraphs गायब हो जाते हैं; वैसे ही छोड़ दो तो पुराना rate जीतता रहता है।

Amendments को section level पर model करो:

- हर chunk में एक stable `section_id` हो (paragraph 4, clause 3.2)।
- एक amendments table `amending_doc`, `amended_doc`, `section_id` और लागू होने की date record करे।
- जब amendment लागू हो, तो सिर्फ़ amend हुए section का `effective_to` ख़त्म करो, और बाकी को छोड़ दो।
- Query time पर, जब कोई base section retrieve हो, तो उसके सारे amendments भी date के क्रम में fetch करो, और model को दोनों दो।

ये इसलिए ज़रूरी है क्योंकि कोई भी chunk अकेले काम नहीं करता। Amendment कहता है "substitute 'Rs 450'" पर ये नहीं बताता कि किसकी जगह; base paragraph पुराना हो चुका है। जवाब को दोनों cite करने चाहिए: "order 112/2019, paragraph 4, as amended by order 37/2022"। अगर विभाग consolidated versions publish करता है, तो उन्हें भी index करो, पर citations के लिए chain रखो।

Amendment links भी निकाला गया metadata ही हैं। "in partial modification of" या "in supersession of" जैसे phrases, जिनके बाद order number आता है, शुरुआत के अच्छे rules हैं, पर किसी भी निकाले गए field की तरह इन्हें एक sample पर check करो।

### Translations

Hindi order और उसकी English copy दो documents नहीं, दो languages में एक ही document हैं। दोनों को एक ही `doc_group` और `section_id` दो। Results में हर document group और section का एक ही chunk रखो, और user की language वाली copy दिखाओ। वरना top five results में दो जगह एक ही paragraph के दो बार आने में बर्बाद हो जाती हैं। जब दोनों में फ़र्क हो तो विभाग से पूछो कि कौन-सी copy authoritative है, उसे record करो, और उसी को cite करो।

### Permissions, sync में रखे हुए

Chunks पर user ids नहीं, **group ids** store करो (`finance`, `all-employees`), और filter search के अंदर ही लगाओ ताकि मना किया गया chunk model तक कभी न पहुँचे। दो syncs के अलग-अलग schedules चाहिए:

- **Document permissions** source system में बदलती हैं (कोई file दोबारा share होती है)। इन्हें अक्सर re-sync करो, metadata update के रूप में; text को re-embed करने की ज़रूरत नहीं।
- **User groups** तब बदलते हैं जब लोग teams बदलते हैं। User के groups query time पर identity system से पढ़ो, या उन्हें मिनटों के लिए cache करो, दिनों के लिए नहीं। Cached group list ही वजह होती है कि Finance छोड़ चुका कोई इंसान अब भी Finance circulars देखता रहता है।

### सवाल से filters

कुछ filters user के profile से आते हैं (उनका state, उनके groups)। बाकी का अंदाज़ा एक छोटा model सवाल से लगाता है। गलत inferred filter सही जवाब छिपा देता है, इसलिए इन्हें सावधानी से लगाओ:

```python
STATE_NAMES = {"KA": "Karnataka", "TN": "Tamil Nadu", "MH": "Maharashtra",
               "TS": "Telangana", "GJ": "Gujarat"}

class Filters(BaseModel):            # structured output from a small model
    state: Literal["KA", "TN", "MH", "TS", "GJ"] | None = None  # a real state, never ALL
    state_named: bool = False         # true only if the question names the state itself
    in_force_year: int | None = None  # "what was the rule in 2024?"
    issued_year: int | None = None    # "the 2019 order on transfers"
    doc_type: DocType | None = None

def in_force(start: date, end: date) -> dict:
    """In force at any time from start to end."""
    return {"effective_from": {"$lte": end},
            "$or": [{"effective_to": None}, {"effective_to": {"$gte": start}}]}

def build_filters(f: Filters, user, today: date):
    if f.state and f.state != user.state and not f.state_named:
        return None, f"Do you mean the {STATE_NAMES[f.state]} documents?"
    where = {"access_groups": {"$in": user.groups},           # never dropped
             "state": {"$in": [f.state or user.state, "ALL"]}}
    if f.in_force_year:
        y = f.in_force_year
        where |= in_force(date(y, 1, 1), date(y, 12, 31))
    elif f.issued_year:
        y = f.issued_year
        where["issued_on"] = {"$gte": date(y, 1, 1), "$lte": date(y, 12, 31)}
    else:
        where |= in_force(today, today)                       # default
    if f.doc_type:
        where["doc_type"] = f.doc_type
    return where, None
```

Filter syntax generic है; इसे अपने vector store के syntax में बदल लो। `today` के तौर पर Asia/Kolkata की date pass करो, server की UTC date नहीं। अगर filtered search कुछ नहीं लौटाती, तो सिर्फ़ access filter और user के state के साथ एक बार retry करो, जो भी वो cite करे उसकी dates दिखाओ, और खाली search को log करो। Retry में access filter कभी मत हटाओ।

### Filters और search की speed

Filters approximate vector indexes पर असर डालते हैं। मिसाल के तौर पर pgvector में filter default रूप से index scan के *बाद* लगता है। उसका documentation 10% rows से match होने वाले filter का example देता है: HNSW index और default `hnsw.ef_search` 40 के साथ, औसतन लगभग 4 rows ही बचती हैं, इसलिए आपको माँगे से कम results मिलते हैं। Version 0.8.0 से आप iterative index scans चालू कर सकते हो (`SET hnsw.iterative_scan = relaxed_order`), जो index का और हिस्सा scan करते हैं जब तक काफ़ी rows pass न हो जाएँ या scan limit (`hnsw.max_scan_tuples`) न आ जाए, और जिस field में बस कुछ ही distinct values हों उसके लिए pgvector हर value का एक partial index सुझाता है। दूसरे stores अलग तरह से काम करते हैं, इसलिए अपना सबसे selective filter (कोई छोटा state, कोई rare document type) test करो और check करो कि वो अब भी पूरा top-k लौटाता है।

### फ़ायदा check करो

अपने golden set पर हर addition (contextual text, generated questions, inferred filters) के साथ और उसके बिना recall at 5 नापो, और सिर्फ़ वही रखो जो मदद करे। History और दूसरे state वाले सवाल भी शामिल करो, क्योंकि filters वहीं गड़बड़ करते हैं।

## एक worked example

बेंगलुरु की IT company का HR assistant कर्नाटक, तमिलनाडु, महाराष्ट्र, तेलंगाना और गुजरात के employees को serve करता है। Leave और holiday rules हर state में अलग हैं, और policies हर साल revise होती हैं।

**पहले:** chunks में सिर्फ़ file name था। Assistant कर्नाटक और महाराष्ट्र की holiday lists मिला देता था और कभी-कभी पिछले साल की policy quote कर देता था। पहले fix ने एक `current = true` filter जोड़ा, और फिर "what was the carry-forward limit in 2024?" ने कुछ भी नहीं लौटाया।

**Re-ingestion के बाद:** हर chunk में ऊपर की table वाले fields हैं। State और groups employee के sign-on profile से आते हैं। Date rule default में आज का होता है; सवाल में साल का नाम हो तो उसी साल पर चला जाता है। Embed होने वाला text title और section path से शुरू होता है। नीचे के numbers सिर्फ़ ये दिखाने के लिए हैं कि किस तरह का बदलाव उम्मीद करो, ये नापा हुआ result नहीं है:

| मान लो, 100 golden questions पर | पहले | बाद में |
| --- | --- | --- |
| सही जवाब | 71 | 90 |
| गलत state quote करने वाले जवाब | 9 | 0 |
| पिछले साल की policy quote करने वाले जवाब | 7 | 1 |
| बाकी गलत जवाब | 13 | 9 |
| Citation format | सिर्फ़ file name | Document, state, section, page |

अब citations ऐसे दिखते हैं: "Leave Policy 2026, Karnataka, section 3.2, page 4", और HR staff उन्हें कुछ ही seconds में check कर सकता है।

**Filter के फ़ैसले कैसे होते हैं।** बेंगलुरु में Priya पूछती है "how many holidays in October?"। Assistant उसके profile से `state = KA` और आज in force वाला rule लगाता है। फिर वो पूछती है "holidays in Pune office in October"। छोटा model पुणे को महाराष्ट्र से map करता है, पर उसने state का नाम नहीं लिया, इसलिए `build_filters` एक सवाल लौटाता है: "Do you mean the Maharashtra documents?" पूछने में एक tap लगता है; चुपचाप लगे गलत filter की क़ीमत एक गलत जवाब है। अगर उसने "Maharashtra holidays" type किया होता, तो filter सीधे लग जाता।

जब वो पूछती है "what was the carry-forward limit in 2024?", तो model `in_force_year = 2024` लौटाता है। 2023 से 2025 वाली policy, जो January 2026 से superseded है, date rule से match करती है और "replaced by Leave Policy 2026" note के साथ वापस आती है।

## आम गलतियाँ

- **सिर्फ़ file name।** आप न filter कर सकते, न ठीक से cite कर सकते, न versions संभाल सकते।
- **Free-text metadata values।** "HR", "Human Resources" और "hr dept" filters तोड़ देते हैं। Fixed lists use करो और उन्हें validate करो।
- **ऐसी vocabulary जिसमें कोई असली value छूट जाए।** एक भूला हुआ state उसके सारे documents quarantine कर देता है, या उससे भी बुरा, उन्हें बिना state के index कर देता है।
- **हर search पर "current only" filter।** तब history वाले सवाल कुछ नहीं लौटाते। सवाल जिस period के बारे में है उसके साथ in-force rule use करो।
- **Partial amendments के लिए पूरे document का supersession।** ये या तो अभी in force paragraphs छिपा देता है या पुरानी values रख लेता है। Amendments को हर section के हिसाब से track करो।
- **Translations को अलग documents मानना।** Duplicate paragraphs बाकी results को बाहर धकेल देते हैं।
- **ज़बरदस्ती वाले inferred filters।** User के profile को तरजीह दो, और अगर inferred filter उसे बदलता है तो पूछ लो।
- **ऐसा fallback जो access filter हटा दे।** खाली result से कभी ये नहीं बढ़ना चाहिए कि user क्या देख सकता है।
- **पुरानी group lists।** Access query time पर user के groups से तय होता है, इसलिए उन्हें ताज़ा पढ़ो।
- **बिना नापे metadata generate करना।** इसमें हर chunk पर एक model call लगती है; साबित करो कि ये मदद करता है।

## जब थोड़ा metadata काफ़ी है

- **एक छोटा, एक ही topic वाला collection**, जिसमें हर document का एक ही version हो।
- **हर कोई सब कुछ देख सकता है**, और कुछ भी पुराना नहीं पड़ता।
- **एक prototype** जो ये test कर रहा है कि retrieval मदद करता भी है या नहीं।

तब भी document id, section और page store करो: citations को इनकी ज़रूरत है, और इनकी कोई cost नहीं। Rich metadata तब फ़ायदा देता है जब बहुत सारे document types, versions, regions या permission groups हों।

## Demo से production तक

- जब भी parser या document format बदले, **निकाले गए fields को एक sample पर हाथ से check करो**।
- हर search पर **लगे filters को log करो**, inferred filters और fallbacks समेत।
- **Permissions को re-sync करो** उनके अपने schedule पर, re-embedding से अलग।
- Content owners के साथ **vocabularies review करो** (states, document types, departments)।

## Practice

Metadata extraction पर LlamaIndex का page और Microsoft का security filter pattern पढ़ो।

1. अपने RAG documents को दोबारा ingest करो, हर chunk पर title, section id और path, type, dates, language और access groups के साथ।
2. Embed होने वाले text के आगे title और section path जोड़ो और पहले और बाद का recall at 5 compare करो।
3. किसी document को एक पुराना version दो जो पिछले साल ख़त्म हुआ। दिखाओ कि default सवाल को नया version मिलता है और पिछले साल का नाम लेने वाले सवाल को पुराना।
4. किसी document के एक section को दूसरे document से amend करवाओ। दिखाओ कि जवाब दोनों को cite करता है।
5. जानबूझकर खराब metadata वाले पाँच chunks `ChunkMeta` से गुज़ारो और confirm करो कि हर एक साफ़ error के साथ quarantine में पहुँचता है।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 6 RAG को cover करता है, chunking और chunks में context जोड़ने समेत।

**आपका काम पूरा है जब आप** एक precise citation वाला जवाब, पुराना version लौटाने वाला एक history सवाल, और एक ऐसा सवाल दिखा सको जहाँ metadata filter ने गलत जवाब को ठीक किया।
