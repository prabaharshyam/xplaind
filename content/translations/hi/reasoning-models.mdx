## ये क्या है

AI में ज़्यादातर पैसा तब खर्च होता है जब आपने model देखा भी नहीं होता: उसे train करने में। **Test-time compute** इसका दूसरा पहलू है। इसका मतलब है जवाब देते वक़्त ज़्यादा computing खर्च करना, ताकि जवाब के सही होने की संभावना बढ़े। "Test time" inference के लिए research वाला शब्द है, यानी वो वक़्त जब एक train हो चुका model use होता है।

इसे करने के तीन आम तरीके हैं।

1. **उससे step by step सोचने को कहो।** ये **chain-of-thought** (CoT) prompting है: model जवाब से पहले अपनी reasoning लिखता है। इसका एक करीबी रिश्तेदार है **self-critique**, जिसमें model खत्म करने से पहले अपना draft खुद check करता है।
2. **कई जवाब generate करो और सबसे अच्छा रखो।** ये **best-of-N** है। एक **verifier** (एक test, एक rule check या एक scoring model) winner चुनता है, या जवाब exact हों तो majority vote चुनता है।
3. **एक reasoning model use करो।** ये models जवाब देने से पहले लंबा सोचने के लिए train होते हैं। वो कितना effort लगाएँ, ये आप तय करते हो। Thinking अक्सर छुपी रहती है: आपको सिर्फ़ जवाब दिखता है, पर thinking के पैसे फिर भी लगते हैं।

तीनों accuracy के बदले पैसा और इंतज़ार देते हैं। Extra thinking तब फ़ायदा देती है जब model सही जवाब तक *पहुँच सकता* है पर रास्ते में अक्सर फिसल जाता है, जैसे multi-step maths, code और planning में। जब model के पास facts ही नहीं हैं, तब ये मदद नहीं करती।

```flow
title: किसी सवाल को कितनी thinking चाहिए, ये चुनना
नया सवाल -> Plain model के लिए मुश्किल? | अपना test set check करो
Plain model के लिए मुश्किल? -[नहीं]-> Plain जवाब | तेज़ और सस्ता
Plain model के लिए मुश्किल? -[हाँ]-> Step-by-step prompt | पहले ये try करो
Step-by-step prompt -> काफ़ी अच्छा?
काफ़ी अच्छा? -[हाँ]-> Ship करो
काफ़ी अच्छा? -[नहीं]-> क्या जवाब check हो सकते हैं? | tests, rules, exact values
क्या जवाब check हो सकते हैं? -[हाँ]-> N sample करो और verify करो | best-of-N या vote
क्या जवाब check हो सकते हैं? -[नहीं]-> Reasoning model | effort setting के कई levels test करो
N sample करो और verify करो -[samples असहमत]-> Reasoning model
```

## ये काम कैसे करता है

### Chain of thought

सबसे simple रूप prompt में बस एक line जोड़ता है: "Think step by step, then give only the final answer on the last line." आप चाहो तो वो steps list कर सकते हो जो आपको चाहिए, या एक worked example दिखा सकते हो। जिस 2022 paper ने इस method को नाम दिया (Wei and others, link नीचे है), उसने बड़े models के साथ maths word problems पर बड़े फ़ायदे दिखाए। आख़िरी line वाला जवाब ज़रूरी है: आपके code को उसे ढूँढना होता है।

पहला पेच लंबाई का है: reasoning वाले जवाब में बहुत ज़्यादा tokens होते हैं, और हर एक पर पैसा और वक़्त लगता है। दूसरा पेच चुपचाप वाला है: **लिखी हुई reasoning के जवाब की असली वजह होने की कोई guarantee नहीं है।** 2025 की एक Anthropic study में models को चुपके से जवाब का एक hint दिया गया। जब उन्होंने hint use किया, तो Claude 3.7 Sonnet ने अपनी reasoning में उसका ज़िक्र सिर्फ़ 25% बार किया, और DeepSeek R1 ने 39% बार। पहले के काम (Turpin and others, 2023) में chain-of-thought prompts के साथ भी यही pattern मिला था। इसलिए दिखाई गई reasoning को एक मददगार draft मानो, सबूत नहीं। Steps कितने convincing लगते हैं ये नहीं, final जवाब check करो।

### Best-of-N और verifiers

थोड़ी variety के साथ (zero से ऊपर का temperature, या थोड़े अलग prompts) कई जवाब माँगो, फिर एक चुनो।

- **Majority vote से**, जिसे **self-consistency** भी कहते हैं। वही maths सवाल पाँच बार पूछो और सबसे ज़्यादा बार आया final number लो। ये तभी चलता है जब जवाब exact हों: एक number, एक label, एक choice। सहमति भी एक signal है: जब samples असहमत हों, तो सवाल शायद मुश्किल है।
- **एक outcome verifier के साथ**, जो final जवाब check करता है। Generate हुए code को tests पर चलाओ, generate हुई SQL चलाकर उसका result पहले से पता किसी result से compare करो, या check करो कि निकाली गई तारीख़ असली है। 2021 में OpenAI ने बताया कि grade-school maths problems पर, trained verifier वाले एक 6-billion-parameter model ने एक fine-tuned 175-billion-parameter model को थोड़ा-सा हरा दिया, और इस फ़ायदे की तुलना उन्होंने model size में 30 गुना बढ़ोतरी से की।
- **एक process verifier के साथ**, आमतौर पर एक **process reward model** (PRM), जो सिर्फ़ आख़िर को नहीं बल्कि हर step को score करता है। OpenAI के 2023 paper "Let's Verify Step by Step" में पाया गया कि competition maths पर step-level feedback ने answer-level feedback को हराया, और एक test subset का 78% हल किया। Hugging Face के write-up ने, जो इस lesson का main resource है, search को guide करने के लिए एक PRM use किया और दिखाया कि काफ़ी samples मिलने पर MATH-500 benchmark पर 1B और 3B models ने अपने 8B और 70B भाइयों को हरा दिया।
- **एक scoring model के साथ**, जैसे एक LLM judge। ये open-ended text के लिए चलता है, पर उतना ही अच्छा है जितना judge।

N जवाब sample करने की cost लगभग N गुना होती है, इसलिए N आमतौर पर छोटा रहता है: products में करीब 3 से 8, research runs में use होने वाले सैकड़ों से बहुत कम।

Majority voting के लिए एक छोटा helper। Normalising step पर ध्यान दो: "12.50", "25/2" और "12.5" एक ही जवाब हैं, और एक plain text comparison vote को तीन हिस्सों में बाँट देगा।

```python
from collections import Counter
from fractions import Fraction

def normalise(text):
    """Turn '12.50', ' 25/2 ' and '12.5' into the same vote. Non-numbers stay as text."""
    t = text.strip().lower().rstrip(".")
    try:
        return Fraction(t)  # exact, so rounding never splits a vote
    except (ValueError, ZeroDivisionError):
        return t

def majority_answer(ask, question, n=3):
    """ask(question) returns the model's final answer as a short string."""
    votes = Counter(normalise(ask(question)) for _ in range(n))
    best, count = votes.most_common(1)[0]
    unanimous = count == n
    # Accept only a unanimous answer. Anything else goes to the stronger model.
    return best, unanimous

# answer, ok = majority_answer(ask, "If 3x + 7 = 25, what is x?")
# if not ok: answer = ask_reasoning_model(question)
```

Model से आख़िरी line पर सिर्फ़ एक number माँगो। "x = 6" जैसा जवाब text ही रहता है और "6" से match नहीं करेगा।

### Reasoning models

ये models जवाब देने से पहले लंबा सोचने के लिए train होते हैं, अक्सर ऐसी problems पर reinforcement learning से जिनके जवाब check हो सकते हैं। ये maths, code और planning में चमकते हैं; simple सवालों पर ज़्यादातर cost और देरी ही जोड़ते हैं।

आप इन्हें prompt से नहीं, एक **effort setting** से steer करते हो। मिसाल के तौर पर, November 2026 के हिसाब से, OpenAI की Responses API में `reasoning.effort` है, और Anthropic की API में `output_config.effort` है, जिसमें recent Claude models पर levels `low` से `max` तक हैं। Effort एक soft guidance है, token count नहीं: low effort पर आसान inputs के लिए model thinking skip कर सकता है। Defaults model के हिसाब से अलग हैं (Anthropic का default ज़्यादातर Claude models पर `high` है और कुछ नए models पर `medium`), इसलिए effort explicitly set करो और दो-तीन levels को अलग options की तरह test करो। पुराने tutorials एक fixed thinking budget (`budget_tokens`) दिखाते हैं; Anthropic ने इसे deprecate कर दिया है, और Claude 4.7 और उसके बाद के models इसे reject करते हैं।

**Reasoning model पर chain-of-thought prompts का ढेर मत लगाओ।** वो पहले से जवाब से पहले सोचता है। जब OpenAI ने अपने o1 reasoning models launch किए, तो उसकी prompting guide ने simple, direct prompts की सलाह दी और chain-of-thought instructions न देने को कहा। Anthropic पहले effort level बदलने की सलाह देता है, और उसके बाद ही, अगर किसी task को अब भी ज़रूरत हो, "Think carefully before responding" जैसा एक छोटा nudge। Steps को script मत करो और reply में पूरी reasoning मत माँगो: आप छुपी thinking के पैसे दोगे और फिर उसकी दिखने वाली copy के भी।

### आप किसके पैसे देते हो, और user किसका इंतज़ार करता है

- **Thinking output tokens की तरह bill होती है**, तब भी जब आप उसे कभी न देखो। Output tokens आमतौर पर input tokens से महँगे होते हैं।
- **Summary की cost भी पूरी thinking जितनी।** Anthropic thinking का एक छोटा summary लौटा सकता है, पर bill उसके पीछे की पूरी thinking का होता है, summary की लंबाई का नहीं।
- **Thinking output limit में गिनी जाती है।** छोटे replies के हिसाब से रखी गई output limit (Anthropic पर `max_tokens`) thinking के दौरान ही खत्म हो सकती है, और reply थोड़े-से जवाब के साथ या बिना जवाब के रुक जाता है। दोनों के लिए जगह छोड़ो, या effort कम करो।
- **असली count पढ़ो।** Anthropic इसे `usage.output_tokens_details.thinking_tokens` में report करता है; OpenAI अपने usage data में reasoning tokens को `output_tokens_details` के नीचे report करता है। इसे हर request पर log करो: यही वो number है जो आपका bill समझाता है।
- **जब तक ये सोचता है, दिखने वाला कुछ भी stream नहीं होता।** Thinking छुपी हो (Anthropic के Claude 5 models पर यही default है), तो पहला दिखने वाला शब्द thinking खत्म होने के बाद ही आता है। User को दिखने वाले पहले शब्द तक का वक़्त नापो, और progress के तौर पर एक status line या एक thinking summary दिखाओ।
- **Multi-turn chats ज़्यादा महँगी पड़ती हैं।** जो thinking conversation में रहती है, वो बाद के turns पर input की तरह bill होती है: कुछ models पर हर पिछले turn से, कुछ पर सिर्फ़ आख़िरी turn से। Conversation के बीच effort level बदलने से prompt cache भी टूट सकता है।

### Methods आमने-सामने

| Method | Extra cost | Extra इंतज़ार | सबसे अच्छा कब चलता है | किससे सावधान रहें |
| --- | --- | --- | --- | --- |
| Step-by-step prompt | Output tokens का 2 से 5 गुना | Seconds | Non-reasoning model पर multi-step problems | लंबे replies; ऐसी reasoning जो सही लगे पर हो नहीं |
| 5 का majority vote | करीब 5 गुना | Parallel चलाओ तो थोड़ा | Exact जवाब: numbers, labels | Free-form text के लिए बेकार; सबके एक जैसे blind spots |
| Verifier के साथ best-of-N | करीब N गुना plus checks | Parallel हो तो थोड़ा | Code, SQL, ऐसे formats जिन्हें आप test कर सको | कमज़ोर verifier बुरे जवाब चुनता है |
| Reasoning model | अक्सर 3 से 10 गुना | Seconds से minutes | कठिन maths, code, planning | छुपी thinking का bill; output limit बहुत छोटी |

ये multipliers options की तुलना के लिए मोटे patterns हैं, दाम नहीं। अपने सवालों पर नापो।

## एक example से समझो

Kota की एक coaching company चाहती है कि AI JEE-style maths problems पर students के जवाब check करे और गलतियाँ समझाए, करीब 300 problems रोज़। Teachers हर दिन नई practice problems लिखते हैं, और students दूसरी किताबों से भी doubts upload करते हैं, इसलिए ज़्यादातर problems **बिना answer key के** आती हैं। AI को पहले सही जवाब ढूँढना है, फिर उसे student के जवाब से compare करना है। (जहाँ key है, वहाँ एक plain comparison ये हिस्सा कर देता है और किसी model की ज़रूरत नहीं।)

Options compare करने के लिए team 200 पुरानी problems का एक test set बनाती है जिनके जवाब teachers ने check किए हैं। नीचे "सही" का मतलब है कि option ने सही जवाब ढूँढा। इसके बाद आने वाला explanation step हर option के लिए एक जैसी cost का है, इसलिए उसे छोड़ दिया है। सारे numbers मिसाल के लिए हैं, method दिखाने के लिए चुने गए; ये नापे हुए दाम नहीं हैं।

Testing से पहले तय हुए targets: कम से कम 88% सही, 100 problems पर ₹150 से कम, और ज़्यादातर students को 10 seconds के अंदर result।

| Option | सही | 100 problems की cost | आम इंतज़ार |
| --- | --- | --- | --- |
| Mid-size model, plain prompt | 71% | ₹20 | 3 s |
| वही model, step-by-step prompt | 81% | ₹55 | 8 s |
| Step-by-step, 5 का majority | 88% | ₹275 | 9 s (parallel) |
| Reasoning model, low effort | 82% | ₹45 | 8 s |
| Reasoning model, medium effort | 90% | ₹120 | 20 s |
| Reasoning model, high effort | 91% | ₹260 | 45 s |
| Router: 3 plain जवाब, reasoning model (medium) सिर्फ़ तब जब वो असहमत हों | 90.5% | ₹96 | 70% के लिए 3 s, 30% के लिए 23 s |

**इसे noise को ध्यान में रखकर पढ़ो।** 200 problems पर, 90% के आसपास margin of error दोनों तरफ़ करीब 4 points है (lesson Quality, cost और speed के trade-offs देखो)। इसलिए quality में 88%, 90%, 90.5% और 91% बराबरी पर हैं, और फ़ैसला cost और इंतज़ार करते हैं।

- Step-by-step prompt एक बड़ी, सस्ती जीत थी: 100 पर ₹35 ज़्यादा में 10 points। जो model खुद reasoning नहीं करता, उस पर इसे पहले try करो।
- Low effort target से चूक जाता है। High effort की cost medium से दोगुने से भी ज़्यादा है और students को 45 seconds इंतज़ार कराता है, उस फ़ायदे के लिए जो noise के अंदर है। Effort sweep की आम shape यही होती है: शुरू में बड़े फ़ायदे, फिर ऊँची कीमत पर छोटे फ़ायदे।
- 5 का majority और high effort budget तोड़ देते हैं। Medium effort quality और cost पार कर लेता है, पर हर student 20 seconds इंतज़ार करता है, इसलिए वो इंतज़ार वाले target में fail होता है। सिर्फ़ router तीनों पूरे करता है।

**Router कैसे काम करता है, और उसके numbers कहाँ से आते हैं।** हर problem को पहले तीन जल्दी वाले plain-prompt जवाब मिलते हैं, parallel में, हर एक 100 पर ₹20: कुल 100 पर ₹60। अगर तीनों सहमत हों, तो वही जवाब use होता है। अगर नहीं, तो problem medium effort पर reasoning model के पास जाती है।

- Test set पर, 200 में से 140 problems (70%) पर तीनों सहमत थे। उनमें से 136 पर सहमति वाला जवाब सही था, यानी 97%। 100% नहीं: जब model का कोई blind spot हो, जैसे हर बार वही sign error, तो तीनों samples एक ही गलत जवाब पर सहमत हो जाते हैं। सहमति evidence है, proof नहीं।
- बाकी 60 problems (30%) reasoning model के पास गईं, जिसने 45 सही कीं, यानी 75%। ये उसके overall 90% से काफ़ी कम है, क्योंकि यही मुश्किल problems हैं।
- Accuracy: 136 + 45 = 200 में से 181, यानी 90.5%।
- Cost: samples के लिए ₹60, plus 30% problems × ₹120 = escalations के लिए ₹36, तो 100 पर ₹96।
- इंतज़ार: जो 70% सहमत होते हैं उनके लिए 3 seconds, और जो 30% escalate होते हैं उनके लिए 3 + 20 = 23 seconds। सबसे ज़्यादा इंतज़ार करने वाले students अकेले reasoning model की तुलना में 3 seconds ज़्यादा इंतज़ार करते हैं, और 95th-percentile इंतज़ार slow path तय करता है।

पहले stage में plain जवाब क्यों? तीन step-by-step जवाबों की cost 100 पर ₹165 होती, अकेले reasoning model से ज़्यादा। पहले stage को बस difficulty का एक सस्ता test होना है।

**फ़ैसला।** उन्होंने router चुना: noise के अंदर reasoning model जितनी ही quality, 20% सस्ता, और 10 में से 7 students को 20 की जगह 3 seconds में result। Escalate हुई problems के लिए app एक progress bar के साथ "Checking your working carefully…" दिखाता है, क्योंकि जब students देख सकें कि कुछ हो रहा है तो वो छोटा इंतज़ार मान लेते हैं। जो homework रात भर में check होता है, वो एक batch API से जाता है, जिसकी कीमत OpenAI और Anthropic normal rate की आधी रखते हैं, November 2026 के हिसाब से।

वो हर escalate हुई problem को एक नए test case की तरह log करते हैं, और नई problems पर 97% वाला figure हर महीने दोबारा check करते हैं: router उतना ही अच्छा है जितना वो number।

## आम गलतियाँ

- **हर चीज़ के लिए reasoning model use करना।** Greetings, lookups और formatting को इसकी ज़रूरत नहीं। आप ऐसी thinking के पैसे देते हो जो कुछ नहीं जोड़ती।
- **सस्ता कदम छोड़ देना।** जो model खुद reasoning नहीं करता, उस पर एक step-by-step prompt अक्सर cost के छोटे-से हिस्से में फ़ासले का बड़ा हिस्सा पाट देता है।
- **Reasoning model में step-by-step prompts जोड़ना।** वो पहले से सोचता है। इसकी जगह effort level set करो।
- **बिना thinking के हिसाब से रखी output limit।** Thinking उसमें गिनी जाती है, इसलिए जवाब बीच में कट जाते हैं।
- **Free-form text पर vote करना।** दो अच्छे paragraphs कभी एक जैसे नहीं होते, इसलिए vote को कुछ नहीं मिलता। इसकी जगह verifier या judge use करो।
- **सहमति को सच मान लेना।** एक model के samples में उसके blind spots साझा होते हैं। नापो कि unanimous जवाब कितनी बार सही होते हैं।
- **कमज़ोर verifier पर भरोसा करना।** अगर checker को बेवकूफ़ बनाना आसान है, तो best-of-N वो जवाब चुनता है जो उसे सबसे अच्छे से बेवकूफ़ बनाए।
- **Raw reasoning पर भरोसा करना या उसे दिखाना।** उसमें वो बात छूट सकती है जिसने असल में जवाब तय किया, और उसमें गलत मोड़ होते हैं। Results check करो, और users को जवाब एक छोटी, checked explanation के साथ दिखाओ।

## जब ज़्यादा सोचना गलत tool है

- **Model के पास facts नहीं हैं।** ज़्यादा देर सोचने से knowledge नहीं जुड़ती। Retrieval use करो।
- **Task simple या creative है।** छोटे replies, summaries और tone बदलना शायद ही सुधरते हैं।
- **एक छोटे फ़ायदे से ज़्यादा latency मायने रखती है।** एक voice agent या autocomplete दस seconds इंतज़ार नहीं कर सकता।
- **आप फ़ायदा नाप नहीं सकते।** Test set के बिना आप ज़्यादा खर्च करोगे और पता नहीं चलेगा कि मदद हुई या नहीं।

## Demo से production तक

- **Difficulty के हिसाब से route करो।** आसान सवाल fast path पर भेजो और तभी escalate करो जब कोई check fail हो या samples असहमत हों।
- **खर्च की cap लगाओ।** Effort explicitly set करो, thinking की जगह छोड़कर output limit set करो, और हर request की thinking tokens और cost track करो।
- **Progress दिखाओ**, खासकर जब thinking छुपी हो।
- **Effort sweep दोबारा चलाओ** जब आप model या उसका version बदलो, क्योंकि वही level अलग तरह से behave कर सकता है।

## Practice करो

1. जवाब पता वाले दस maths या logic सवाल लो। किसी भी chat model पर एक plain prompt और फिर एक step-by-step prompt score करो।
2. जो सवाल उसने गलत किए, उनके लिए हर एक के पाँच जवाब sample करो और majority लो। Vote ने कितने ठीक किए? क्या कोई unanimous होकर भी गलत था?
3. अगर आपके पास किसी reasoning model का API access है, तो वही दस सवाल दो effort levels पर चलाओ। Usage data से thinking tokens log करो और हर सवाल की cost निकालो।
4. हर method के लिए accuracy, cost और इंतज़ार लिखो, और तय करो कि student app के लिए आप कौन-सा ship करोगे।

**आपका काम पूरा है जब आप** test-time compute खर्च करने के तीन तरीके समझा सको, बता सको कि majority vote कब चलता है और कब गुमराह करता है, और reasoning की cost और इंतज़ार को काबू में रखने के तीन तरीके बता सको।
