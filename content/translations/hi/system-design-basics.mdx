## ये क्या है

**System design** ये तय करना है कि software system के हिस्से आपस में कैसे जुड़ें, ताकि वो वही करे जो users को चाहिए, उस scale पर जिसका उसे सामना करना है, और अपने budget में। इसमें components (apps, services, databases, caches, queues), उनके बीच data का बहाव, और कुछ fail होने पर क्या होता है, ये सब आता है।

सही जवाब शायद ही कभी एक होता है। अच्छा design वो है जिसके चुनाव requirements से मेल खाते हों और जिसके trade-offs खुलकर बताए गए हों। Interviewers भी यही देखते हैं: एक साफ़ process, समझदार numbers और ईमानदार trade-offs, किसी perfect diagram से ज़्यादा।

```flow
dir: LR
1. Requirements | इसे क्या करना है? कितना तेज़, कितना बड़ा, कितना भरोसेमंद? -> 2. Estimates | users, requests per second, storage, bandwidth, औसत और peak पर
2. Estimates -> 3. High-level design | clients, load balancer, app servers, cache, database, queue, workers
3. High-level design -> 4. Deep dive | data model, hot paths, scaling
4. Deep dive -> 5. Trade-offs और failures | क्या टूटता है, आपने क्या चुना और क्यों
```

## ये काम कैसे करता है

**1. Requirements साफ़ करो.** उन्हें **functional** requirements (system क्या करता है, जैसे "users seat book कर सकते हैं" या "users को order status दिखता है") और **non-functional** requirements (कितना अच्छा करता है: latency, availability, consistency, scale, cost, security) में बाँटो। पूछो कि users कौन हैं, कितने हैं, और कौन-से features scope में हैं। जवाब लिख लो।

**2. अंदाज़ा लगाओ.** **Back-of-the-envelope estimate** users को load में बदलता है। काम की बातें: एक दिन में लगभग 1 लाख seconds होते हैं (86,400), इसलिए रोज़ 1 करोड़ requests लगभग 115 per second बनती हैं; औसत के कई गुना peaks की planning करो। हर item का storage, गुणा रोज़ के items, गुणा रखे जाने वाले दिन, इसका अंदाज़ा लगाओ। इन्हीं numbers से तय होता है कि एक database काफ़ी है या कई चाहिए।

**3. High-level design का sketch बनाओ.** Main boxes और arrows बनाओ: clients, load balancer, stateless app servers, cache, database, files के लिए object storage, और धीमे jobs के लिए background workers वाली queue। एक request को शुरू से अंत तक इसमें से गुज़ारकर दिखाओ।

**4. Deep dive.** इस system के लिए जो हिस्से सबसे ज़्यादा मायने रखते हैं उनमें गहराई से जाओ: data model और उसके indexes, सबसे busy path को कैसे scale करें, data को consistent कैसे रखें, या अचानक आए spike को कैसे संभालें।

**5. Trade-offs और failures.** बताओ कि हर चुनाव की कीमत क्या है। Cache reads को तेज़ करता है पर पुराना data दे सकता है; queue spikes को सँभालती है पर देरी जोड़ती है; ज़्यादा replicas availability बढ़ाते हैं पर महँगे पड़ते हैं। हर component के लिए पूछो "अगर ये box fail हो जाए तो?"

| Non-functional ज़रूरत | आम numbers | Design के levers |
|---|---|---|
| Latency | page के लिए p95 200 ms से कम | caches, CDNs, कम hops, indexes |
| Throughput | हज़ारों requests per second | ज़्यादा app servers, load balancing, async काम |
| Availability | 99.9% = महीने में लगभग 43 मिनट down | replicas, health checks, कोई single point of failure नहीं |
| Consistency | payments के लिए strong, likes के लिए eventual | transactions, सिर्फ़ primary से reads, idempotency |
| Cost | हर लाख requests पर रुपये | सही size की machines, caching, सस्ते storage tiers |

**Browser में try करो।** Back-of-envelope numbers से ज़्यादातर designs तय होते हैं। Inputs बदलो और चलाओ।

```python
daily_users = 200_000
requests_per_user = 15
peak_factor = 3
bytes_per_record = 2_000

per_second = daily_users * requests_per_user / 86_400
print(f"average {per_second:,.0f} requests/s, peak about {per_second * peak_factor:,.0f}/s")
storage_gb_year = daily_users * requests_per_user * bytes_per_record * 365 / 1e9
print(f"about {storage_gb_year:,.0f} GB of records a year")
```

## एक example से समझो

Meera से एक interview में कहा जाता है कि बेंगलुरु की एक food delivery app के order-status page को design करो: order करने के बाद customers को "Preparing", "Picked up" और "Arriving" दिखता है, साथ में rider की location।

**Requirements.** वो पूछती हैं और पक्का करती हैं: active orders के लिए status और rider location दिखाओ; updates लगभग 5 seconds के अंदर; रोज़ 20 लाख orders, डिनर के समय peak के साथ; history scope से बाहर है। Availability, perfect freshness से ज़्यादा मायने रखती है: कुछ seconds पुरानी location दिखाना ठीक है।

**Estimates.** रोज़ 20 लाख orders, हर एक लगभग 40 मिनट active रहता है। Riders हर 5 seconds में location भेजते हैं, इसलिए हर order लगभग 480 updates बनाता है। यानी रोज़ लगभग 96 करोड़ updates: औसतन लगभग 11,000 per second और डिनर के peak पर शायद 40,000। Customers page को बार-बार refresh करते हैं, इसलिए reads और भी ज़्यादा हैं। हर location update बहुत छोटा है, लगभग 100 bytes, पर delivery के बाद उन्हें रखने की ज़रूरत नहीं।

**High-level design.** Rider apps locations को load balancer के पीछे एक ingestion service को भेजते हैं। हर order की ताज़ा location Redis जैसे in-memory store में जाती है, order ID को key बनाकर, छोटे expiry के साथ। Order status के बदलाव main database में लिखे जाते हैं और साथ ही एक queue में publish होते हैं। Customer apps एक notification service से WebSocket connection खुला रखते हैं, जो status और location के बदलाव push करती है। अगर connection टूट जाए, तो app एक read API को poll करने पर लौट आता है, जो Redis से पढ़ती है।

**Deep dive और trade-offs.** वो समझाती हैं कि ज़्यादा volume वाली location stream main SQL database में क्यों नहीं जाती: वो उस database को उस data का bottleneck बना देगी जो कल किसी को नहीं चाहिए। Status, जो refunds और support के लिए मायने रखता है, database में जाता है। वो trade-off का नाम लेती हैं: अगर कोई node fail हो तो Redis आखिरी कुछ seconds की locations खो सकता है, जो यहाँ चलेगा, जबकि order status durable है। वो failure cases पर बात खत्म करती हैं: अगर notification service बंद हो, तो polling फिर भी चलती है; अगर Redis बंद हो, तो page map के बिना status दिखाता है।

Interviewer ने बाद में बताया कि जो सबसे अलग दिखा वो boxes नहीं थे, बल्कि ये कि हर चुनाव किसी number या requirement से जुड़ा था।

## आम गलतियाँ

**पूछने से पहले बनाना।** Requirements के बिना diagram पर कूद जाने से आप गलत problem के लिए पूरे confidence से design बना देते हो। पहले कुछ मिनट सवालों पर लगाओ।

**Numbers छोड़ देना।** Estimate के बिना आप ये नहीं कह सकते कि एक database काफ़ी है या नहीं। मोटे numbers भी, साफ़ बताए हुए, कुछ न होने से बेहतर हैं।

**Average के लिए design करना, peak के लिए नहीं।** Sales, results का दिन और Tatkal का समय normal traffic के कई गुना लाते हैं। Peak के हिसाब से size करो और बताओ कि spikes को कैसे सँभालोगे।

**हर जानी-पहचानी चीज़ जोड़ देना।** हर जगह microservices, Kafka और Kubernetes design को चलाना मुश्किल बना देते हैं। Component तभी जोड़ो जब कोई requirement उसे माँगे।

**Trade-offs छिपाना।** हर चुनाव की एक कीमत होती है। उसे ज़ोर से कहना आपकी समझ दिखाता है।

**Failure को भूल जाना।** पूछो कि हर box बंद हो जाए तो क्या होगा। Single points of failure वो पहली चीज़ है जो reviewers ढूँढते हैं।
