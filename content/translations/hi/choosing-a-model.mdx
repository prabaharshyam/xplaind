## ये क्या है

Model चुनने का मतलब है तय करना कि आपके application का हर हिस्सा कौन-सा language model चलाएगा, किस provider का और किस size का। सैकड़ों options हैं: API के पीछे hosted models, और open-weight models जो आप खुद चलाते हो। हर महीने नए आते हैं, हर एक के साथ record scores की press release।

ये scores **benchmarks** से आते हैं: fixed public test sets जो एक skill नापते हैं, जैसे school maths, general knowledge या code लिखना। **Leaderboard** models को rank करता है, चुने हुए benchmarks के scores जोड़कर, या लोगों के वोट से जो दो anonymous जवाबों में से एक चुनते हैं।

Benchmarks काम के हैं, पर वो आपके सवाल से अलग सवाल का जवाब देते हैं। वो पूछते हैं "इन tests में कौन-सा model अच्छा है?" आपको जानना है "मेरे task पर कौन-सा model काफ़ी अच्छा है, ऐसे price और speed पर जो मैं उठा सकूँ, मेरे rules के अंदर?" चुनने का भरोसेमंद तरीका चार steps का है।

```flow
title: चार steps में model चुनना
सारे candidate models -> Hard requirements पर छाँटो | licence, data location, languages, price
Hard requirements पर छाँटो -> Public benchmarks से shortlist बनाओ | 3 से 5 models
Public benchmarks से shortlist बनाओ -> अपने data पर test करो | आपके inputs, आपका rubric
अपने data पर test करो -> Quality, cost और speed ठीक हैं?
Quality, cost और speed ठीक हैं? -[नहीं]-> Design बदलो | छोटा task, बेहतर prompt, retrieval
Design बदलो -> अपने data पर test करो
Quality, cost और speed ठीक हैं? -[हाँ]-> Launch करो और monitor करो | models बदलने पर दोबारा check करो
```

## ये काम कैसे करता है

**Step 1: hard requirements पर छाँटो।** कुछ चीज़ें prompting से ठीक नहीं होतीं। उन्हें पहले लिख लो, और जो model किसी एक पर भी फ़ेल हो, उसे हटा दो।

- **Licence और terms।** क्या आप इसे commercial use कर सकते हो? क्या उसके outputs रख सकते हो? कुछ open-weight licences में बड़ी companies के लिए सीमाएँ होती हैं।
- **Data location और privacy।** क्या ये किसी Indian cloud region में या आपके अपने servers पर चल सकता है? India के data protection law के तहत, और banks के लिए RBI rules के तहत, इससे कई options बाहर हो सकते हैं।
- **Languages।** क्या ये उन भाषाओं को संभालता है जिनमें आपके users लिखते हैं, मिली-जुली Hinglish समेत?
- **Context length, speed और price।** क्या ये आपका सबसे लंबा document पढ़ सकता है? क्या जवाब काफ़ी तेज़ देता है? क्या हर request की cost आपके budget में आती है?

**Step 2: public benchmarks से shortlist बनाओ।** Benchmarks और leaderboards से 3 से 5 ऐसे candidates चुनो जिन्हें test करना ठीक है, winner चुनने के लिए नहीं। इन्हें इन सीमाओं के साथ पढ़ो:

- **Leaderboards अपने tests खुद चुनते हैं।** एक leaderboard हज़ारों में से मुट्ठी भर benchmarks cover करता है, और ये चुनाव तय करता है कि कौन जीतेगा। ज़्यादातर का झुकाव English और general knowledge की तरफ़ है।
- **छोटी details से scores बदलते हैं।** Hugging Face ने एक बार पाया कि एक ही model को एक ही benchmark पर बहुत अलग scores मिले, इस पर depend करते हुए कि prompt कैसे लिखा गया और score कैसे किया गया। Scores तभी compare करो जब वो एक ही तरीके से नापे गए हों।
- **Saturation।** जब top models सब 100% के करीब score करते हैं, तो benchmark उन्हें अलग नहीं कर पाता। Leaderboards saturated benchmarks को हर साल-दो साल में बदल देते हैं।
- **Contamination।** Benchmark के सवाल public होते हैं, इसलिए वो web text में और फिर training data में पहुँच जाते हैं। जिस model ने सवाल देख लिए हैं वो याददाश्त से अच्छा score करता है। Labs इसे दो आम तरीकों से check करती हैं: test और training data में साझा लंबे word sequences ढूँढना (n-gram overlap), और ये देखना कि model को test के सवाल अजीब हद तक आसानी से predict होते हैं या नहीं (low perplexity)। पुराने, popular benchmarks के scores को सावधानी से लो।
- **Vote-based rankings** वो दिखाते हैं जो बहुत से लोग छोटी chats में पसंद करते हैं, अक्सर fluent, confident और अच्छे format वाले जवाब। ये आपके task से मेल न खाए।

**Step 3: अपने data पर test करो।** यही step तय करता है। 100 से 300 असली inputs का test set बनाओ, personal data anonymise करके, जिसमें हर भाषा और हर तरह की request हो। कोई भी output देखने से पहले एक scoring rubric लिखो। हर shortlisted model को एक ही prompt से चलाओ, और quality, cost और speed साथ में record करो। Test sets और LLM judges वाले lessons बताते हैं कि score कैसे करें।

एक छोटा harness comparison को निष्पक्ष रखता है:

```python
import json, time

def run(model_name, call_model, cases, score):
    """call_model(prompt) returns (text, cost_in_rupees). score(case, text) returns 0 to 1."""
    total, cost, slow = 0.0, 0.0, []
    for case in cases:
        start = time.time()
        text, rupees = call_model(case["input"])
        slow.append(time.time() - start)
        total += score(case, text)
        cost += rupees
    slow.sort()
    return {
        "model": model_name,
        "quality": round(total / len(cases), 3),
        "cost_per_1000": round(cost / len(cases) * 1000, 1),
        "p95_seconds": round(slow[int(len(slow) * 0.95) - 1], 2),
    }

cases = [json.loads(line) for line in open("helpdesk_test.jsonl")]
# results = [run(name, fn, cases, score) for name, fn in candidates.items()]
```

**Step 4: launch करो और monitor करो।** हर हफ़्ते असली conversations का sample लो और उन्हें score करो। जब provider model update करे, price बदले, या कोई सस्ता model आए, तो अपना test set दोबारा चलाओ। आपका test set ही बदलाव को सुरक्षित बनाता है।

**Build या buy।** Hosted APIs शुरू करने में तेज़ हैं, आपके लिए scale हो जाते हैं और अक्सर सबसे मज़बूत models होते हैं। Open-weight models high volume पर data और cost पर आपको control देते हैं, पर servers आप चलाते हो। कई teams API से शुरू करती हैं, फिर जब उनका test set साबित कर दे कि छोटा open model काफ़ी अच्छा है, तो high-volume, सरल steps उस पर ले जाती हैं।

## एक example से समझो

Chennai की एक lending company को Tamil और English में loan सवालों के लिए helpdesk assistant चाहिए। Data India में रहना चाहिए, और budget करीब ₹0.37 प्रति conversation है।

वो आठ candidates से शुरू करते हैं। Filter तीन हटा देता है: एक Indian region में नहीं चल सकता, एक का licence उनका use मना करता है, और एक budget से बहुत ऊपर है। Public leaderboards से वो एक और model हटा देते हैं जो instructions follow करने में कमज़ोर है। चार बचते हैं।

वो 240 असली सवालों का test set बनाते हैं (120 Tamil, 120 English), नाम और loan numbers हटाकर, और एक rubric: policy से सही facts, साफ़ अगला कदम, विनम्र tone, सही भाषा।

| Model | Leaderboard rank | अपना test: Tamil | अपना test: English | हर conversation की cost | p95 reply time |
| --- | --- | --- | --- | --- | --- |
| A, बड़ा hosted | 1 | 81% | 93% | ₹0.62 | 3.1 s |
| B, medium hosted | 6 | 84% | 90% | ₹0.21 | 1.4 s |
| C, open-weight, self-hosted | 11 | 74% | 88% | ₹0.09 | 1.9 s |
| D, छोटा hosted | 15 | 62% | 85% | ₹0.05 | 0.8 s |

ये numbers सिर्फ़ compare करना दिखाने के लिए हैं। Leaderboard का leader A, English में सबसे अच्छा है पर budget से ऊपर है, और Tamil में B से थोड़ा खराब है। B दोनों भाषाओं में bar पूरा करता है, A की एक-तिहाई price पर, इसलिए वो B चुनते हैं। C को वो fallback के रूप में रखते हैं जिसे बाद में Tamil replies पर fine-tune किया जा सकता है, और जब भी कोई नया model announce होता है, वो 240 सवाल दोबारा चलाते हैं।

## आम गलतियाँ

- **Headline score से चुनना।** Leaderboard में जीतने का मतलब है उन tests में अच्छा, आपके task में नहीं।
- **सिर्फ़ English में test करना।** Indian languages और मिली-जुली भाषा के text में quality अक्सर गिर जाती है। हर उस भाषा में test करो जिसमें आपके users लिखते हैं।
- **अलग तरीके से नापे scores को compare करना।** अलग prompts और scoring rules scores को बहुत हिला सकते हैं।
- **Launch तक cost और speed को नज़रअंदाज़ करना।** जो model 2 points बेहतर है पर 3 गुना महँगा, वो गलत चुनाव हो सकता है।
- **कभी दोबारा check न करना।** Prices गिरती हैं और models सुधरते हैं। छह महीने पहले का चुनाव अब ज़्यादा महँगा हो सकता है।
- **पुराने benchmarks पर भरोसा करना।** Popular, पुराने test sets शायद training data में हैं, इसलिए high scores याददाश्त हो सकती हैं।

## जब benchmarks सच में काम आते हैं

- **जल्दी shortlist बनाने में।** वो उन models को हटा देते हैं जो आपकी ज़रूरत की किसी skill में साफ़ कमज़ोर हैं, जैसे coding या लंबे documents।
- **Field को track करने में।** एक ताज़ा, मुश्किल benchmark दिखाता है कि models कितनी तेज़ी से सुधर रहे हैं।
- **किसी दावे को परखने में।** अगर कोई vendor कहे कि उसका model maths में सबसे अच्छा है, तो test करने में समय लगाने से पहले public benchmark पहला check देता है।

3. अपने feature के लिए दस असली test inputs लिखो, साथ में ये कि अच्छे जवाब में क्या होना चाहिए। दो models को उन पर चलाओ और दोनों को score करो।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 4 model selection, public benchmarks और contamination cover करता है।

**आपका काम पूरा जब:** आप चारों steps गिना सको, public benchmarks की तीन सीमाएँ बता सको, और समझा सको कि आख़िरी फ़ैसला आपका अपना test set क्यों करता है।
