## ये क्या है

**Total cost of ownership (TCO)** वो सब है जो किसी system पर एक तय समय में खर्च होता है, आम तौर पर एक से तीन साल, सिर्फ़ model का bill नहीं। इसका काम है options की ईमानदार तुलना करने देना और client को एक सच्चा budget देना।

| Cost line | इसमें क्या आता है | लोग क्या भूल जाते हैं |
|---|---|---|
| Model | API से tokens, या self-host करने पर GPUs (किराए पर या खरीदे हुए) | छुपे हुए reasoning tokens; idle रहते हुए भी bill होते GPUs |
| Infrastructure | App compute, databases, vector store, storage, gateways, monitoring | Log और trace storage, staging environments |
| लोग | Build, operate, on-call, evaluations, upgrades | On-call cover के लिए ज़रूरी दूसरा engineer |
| Data | Connectors, pipelines, golden sets, documents की सफ़ाई | Embedding model बदलने पर re-embedding |
| Compliance | Audits, penetration tests, security और legal reviews | हर बड़े बदलाव के बाद दोबारा reviews |
| बदलाव | Model upgrades, provider के model retire करने पर prompt पर दोबारा काम | हर नए model पर evals दोबारा चलाना |
| India-specific | Cloud और API bills पर GST, dollar prices पर exchange rate | GST असली cost है या वापस claim हो सकता है |

```flow
dir: LR
title: मापे हुए usage से फ़ैसले तक
मापा हुआ usage | traces और load tests -> API option | tokens, infra, लोग
मापा हुआ usage -> Self-hosted option | असली utilisation पर GPUs, infra, लोग
API option -> Sensitivity और crossover
Self-hosted option -> Sensitivity और crossover
Sensitivity और crossover -> हर claim की cost बनाम हर claim की value
```

ये lesson Kolkata की एक insurance company के साथ चलता है, जो 2,000 staff के लिए एक claims-document assistant की योजना बना रही है।

## ये कैसे काम करता है

### मापे हुए usage से शुरू करो

Users, हर user की हर दिन की requests, peak बनाम average, और साल भर की growth इकट्ठा करो। फिर traces से वो तीन चीज़ें मापो जिनका लोग आम तौर पर अंदाज़ा लगा लेते हैं:

- **हर user action पर calls.** एक agent या retrieval pipeline एक सवाल के लिए तीन से छह model calls कर सकती है: query को दोबारा लिखना, retrieve करना, जवाब देना, check करना। Cost हर call की होती है, हर सवाल की नहीं।
- **हर call के input tokens.** Retrieve हुए passages अक्सर input को user के सवाल से कई गुना बड़ा कर देते हैं।
- **Reasoning समेत, हर call के output tokens.** Reasoning models जवाब देने से पहले सोचते हैं। वो thinking छुपी रहती है पर output tokens के रूप में bill होती है (OpenAI का documentation ये साफ़-साफ़ कहता है)। एक छोटे दिखने वाले जवाब के पीछे एक लंबा न दिखने वाला bill हो सकता है।

### API option

हर call की cost = input tokens × input price + output tokens × output price। फिर तीन adjustments करो:

- **Prompt caching.** हर call पर दोबारा पढ़ा जाने वाला fixed system prompt या shared document prefix, caching देने वाले providers के यहाँ normal input price के एक छोटे हिस्से पर bill होता है।
- **Batch discounts** उस काम के लिए जो घंटों रुक सकता है, जैसे रात भर में बनने वाली summaries।
- **Tiering.** Simple requests (lookups, classification) को एक सस्ते, छोटे model पर भेजो और मुश्किल वालों के लिए बड़ा model रखो।

ज़्यादातर API prices US dollars में होती हैं, इसलिए rupee rate भी एक input है। Prices provider के page से और Artificial Analysis जैसी किसी independent comparison से पढ़ो, और हर price के बगल में check की date लिखो।

### Self-hosted option

GPUs को एक spare के साथ **peak** के लिए size करना होता है, आपके latency target पर आपके अपने prompts वाले load test के हिसाब से। फिर आप महीने के हर घंटे उनके पैसे देते हो, busy हों या नहीं। फ़ैसला करने वाला number है **utilisation**:

utilisation = serve हुई requests ÷ वो requests जो fleet महीने में serve कर सकता था

Working days पर दिन में नौ घंटे use होने वाला, month-end peak के लिए size किया गया office tool अक्सर 10% या उससे कम पर चलता है। 10% utilisation पर हर request पूरे use की तुलना में दस गुना GPU cost उठाती है।

दो pricing choices मायने रखती हैं:

- **On-demand** GPUs की हर घंटे की cost सबसे ज़्यादा होती है, पर उन्हें छोड़ा जा सकता है।
- **Reserved** GPUs (एक या तीन साल का commitment) हर घंटे सस्ते पड़ते हैं, पर usage गिरे या API prices गिरें, पैसे फिर भी देने पड़ते हैं।

Serving stack चलाने, patch करने, models upgrade करने और pager संभालने वाले लोग जोड़ो, और अगर open model आपके evals पर कम score करता है तो quality का gap भी।

### India-specific lines

- **GST.** Cloud और API services पर आम तौर पर 18% GST लगता है (November 2026 तक IT और cloud services का सामान्य rate)। किसी foreign provider से खरीदने वाला GST-registered business आम तौर पर इसे reverse charge में भरता है और input tax credit के रूप में वापस claim कर सकता है। जो organisation credit claim नहीं कर सकता, उसके लिए ये असली cost है। Client की finance team से पूछो कि कौन-सा case लागू होता है; इस lesson के figures GST से पहले के हैं।
- **Exchange rate.** Rupee गिरने पर dollar में priced API bill बढ़ जाता है। November 2026 के बीच में rupee एक हफ़्ते के अंदर लगभग ₹94.2 से लगभग ₹93.5 प्रति dollar पर आया, और ₹100 तक जाने पर model line में लगभग 7% जुड़ जाता है। Rate को sensitivity table में डालो।
- **Region.** Data rules किसी Indian cloud region को ज़रूरी बना सकते हैं। Check करो कि जिस model या GPU type की price आपने ली, वो वहाँ उस region की price पर मिलता है।

### Sensitivity और crossover

एक बार में एक assumption बदलकर दोनों options दोबारा निकालो: usage आधा और दोगुना, outputs दोगुने लंबे, API prices 30% कम, कमज़ोर rupee, load test से कम GPU throughput। जो फ़ैसला सिर्फ़ एक exact number पर टिका हो, वो fragile है।

**Crossover** वो usage है जिसके ऊपर दूसरा option लगातार सस्ता रहता है। दो traps:

- **Steps.** GPUs पूरे units में आते हैं, इसलिए हर बार एक जोड़ने पर self-hosted line उछलती है। Spreadsheet एक volume पर self-hosting को जीतता और उसके ज़रा ऊपर हारता दिखा सकती है। वो volume report करो जिसके ऊपर ये लगातार जीतता है।
- **Thin margins.** अगर हर extra request पर API और GPU की cost लगभग बराबर है, तो छोटे बदलावों से crossover बहुत ज़्यादा झूलता है। ये साफ़ बताओ।

### Price trends

किसी तय quality level के लिए API prices तेज़ी से गिरी हैं। Epoch AI ने March 2025 में अंदाज़ा लगाया कि एक fixed benchmark score तक पहुँचने वाले models की per-token price साल में 9 से 900 गुना तक गिरी, इस पर निर्भर करते हुए कि कौन-सा performance level मापा गया। ये prices per token हैं, और reasoning models हर task पर कहीं ज़्यादा tokens use कर सकते हैं। तीन साल का GPU commitment इस trend के ख़िलाफ़ दाँव है, इसलिए इसे "prices 30% कम" वाली row से test करो।

### एक cost model जिसे दोबारा चला सको

हर assumption एक जगह रखो, check की date के साथ। नीचे का हर number illustrative है, worked example से मेल खाने के लिए चुना गया:

```python
import math

# Every number is illustrative. Replace each with your own dated quote or measurement.
P = {"rate_date": "2026-11-19", "usd_to_inr": 93.5,        # rupees per US dollar, about mid-November 2026
     "in_per_m": 3.0, "out_per_m": 15.0,                    # USD per million tokens, a mid-tier API model
     "cache_ratio": 0.1,                                    # cached input billed at 10% of the input price
     "gpu_month": 250_000,                                  # one rented GPU, on demand, all 730 hours
     "gpu_rps": 1.2,                                        # requests per second per GPU, from YOUR load test
     "engineer_month": 200_000,                             # loaded monthly cost of one engineer
     "busy_seconds": 22 * 9 * 3600,                         # 22 working days of 9 busy hours
     "peak_factor": 2.0}                                    # month-end peak against the busy-hour average

def api_month(req, p=P, in_tok=3000, out_tok=300, cached=0.4, small_share=0.4, small_ratio=0.25):
    in_usd = in_tok * (1 - cached + cached * p["cache_ratio"]) * p["in_per_m"] / 1e6
    per_req = (in_usd + out_tok * p["out_per_m"] / 1e6) * (1 - small_share + small_share * small_ratio)
    return req * per_req * p["usd_to_inr"] + 120_000 + 0.3 * p["engineer_month"]   # + infra + 0.3 engineer

def gpus(req, p=P):
    peak_rps = req / p["busy_seconds"] * p["peak_factor"]
    return math.ceil(peak_rps / p["gpu_rps"]) + 1                                   # + one spare

def self_month(req, p=P):
    return gpus(req, p) * p["gpu_month"] + 150_000 + 1.5 * p["engineer_month"]       # + infra + 1.5 engineers

def utilisation(req, p=P):
    return req / (gpus(req, p) * p["gpu_rps"] * 730 * 3600)

def crossover(p=P, limit=30_000_000, step=100_000):
    """Volume above which self-hosting stays cheaper, or None if it never does up to the limit."""
    last_api_win = 0
    for r in range(step, limit + 1, step):
        if self_month(r, p) >= api_month(r, p):
            last_api_win = r
    return None if last_api_win == limit else last_api_win + step

base = 1_100_000
print(f"Illustrative prices, rupee rate of {P['rate_date']}")
print(f"measured: API ₹{api_month(base)/1e5:.1f} lakh, self-hosted ₹{self_month(base)/1e5:.1f} lakh, "
      f"{gpus(base)} GPUs at {utilisation(base):.0%} utilisation")
scenarios = {"as measured": {}, "reserved GPUs at ₹1.6 lakh": {"gpu_month": 160_000},
             "load test gives 1.0 req/s": {"gpu_rps": 1.0}, "API prices 30% lower": {"in_per_m": 2.1, "out_per_m": 10.5},
             "rupee at ₹100": {"usd_to_inr": 100},
             "reserved, API 30% lower": {"gpu_month": 160_000, "in_per_m": 2.1, "out_per_m": 10.5}}
for name, change in scenarios.items():
    p = {**P, **change}
    c = crossover(p)
    print(f"{name:<27} API ₹{api_month(base, p)/1e5:4.1f} lakh  self ₹{self_month(base, p)/1e5:4.1f} lakh  "
          f"crossover {'none below 30M' if c is None else f'{c/1e6:.1f}M'}")
```

ये print करता है:

ये model volume बढ़ने पर भी लोगों और infrastructure को fixed रखता है, जिससे ज़्यादा volume पर self-hosting असल से बेहतर दिखता है: पंद्रह GPUs के fleet को डेढ़ engineers से ज़्यादा चाहिए। किसी को कोई number दिखाने से पहले client के traces, load test और quotes डालो।

## एक worked example

Kolkata की एक insurance company 2,000 staff के लिए एक claims-document assistant roll out करने की योजना बना रही है। Pilot में मापा गया: 22 working days में हर user हर working day 25 requests, हर request में 3,000 input tokens (ज़्यादातर retrieve हुए passages) और 300 output tokens, हर request पर एक model call। यानी 2,000 × 25 × 22 = महीने में 1.1 million requests। Month-end traffic normal busy-hour rate का दोगुना है। सारी prices code वाली illustrative prices हैं।

**Option A, उनके cloud के ज़रिए API.** हर request: 3,000 × $3 ÷ 1,000,000 + 300 × $15 ÷ 1,000,000 = $0.0135, ₹93.5 पर लगभग ₹1.26। 1.1 million requests पर ये महीने में लगभग ₹13.9 lakh है। Fixed system prompt और instructions (input tokens का 40%) cache करने से ये लगभग ₹10.6 lakh पर आता है। 40% requests, यानी simple lookups, को एक चौथाई price वाले model पर भेजने से ये लगभग ₹7.4 lakh पर आता है, यानी हर request ₹0.67। ₹1.2 lakh का infrastructure और एक engineer का 30% जोड़ो: लगभग **₹9.2 lakh महीना**।

**Option B, self-hosted open model.** Load test दिखाता है कि एक GPU latency target पर हर second 1.2 requests serve करता है। Month-end peak लगभग 3.1 requests प्रति second है, तो तीन GPUs और एक spare: चार GPUs, हर एक ₹2.5 lakh, कुल ₹10 lakh। ₹1.5 lakh का infrastructure और serving, upgrades और on-call के लिए डेढ़ engineers (₹3 lakh) जोड़ो: लगभग **₹14.5 lakh महीना**। Evals पर accuracy 2 points कम है। Fleet 9% utilisation पर चलता है, क्योंकि वो month-end के लिए size है और हर रात और हर weekend के पैसे दिए जाते हैं।

| हर महीने (illustrative) | Option A: API | Option B: self-hosted |
| --- | --- | --- |
| Model | Caching और tiering के बाद लगभग ₹7.4 lakh | 9% utilisation पर चार GPUs के ₹10 lakh |
| Infrastructure | ₹1.2 lakh | ₹1.5 lakh |
| लोग | 0.3 engineer, ₹0.6 lakh | 1.5 engineers, ₹3 lakh |
| Evals पर quality | Baseline | 2 points कम |
| महीने का कुल | लगभग ₹9.2 lakh | लगभग ₹14.5 lakh |
| साल का कुल | लगभग ₹1.1 crore | लगभग ₹1.74 crore |

**Crossover कहाँ है?** API पर हर extra request लगभग ₹0.67 की पड़ती है। Average के दोगुने के लिए size किए GPU पर ये लगभग ₹0.58 है। फ़र्क सिर्फ़ नौ paise का है, इसलिए self-hosting को अपने spare GPU और extra engineers का खर्च निकालने के लिए बहुत बड़ा volume चाहिए। On demand पर ये सिर्फ़ लगभग 8.3 million requests प्रति महीने के ऊपर लगातार जीतता है, जो आज के volume का सात से आठ गुना है। ₹1.6 lakh वाले reserved GPUs के साथ ये लगभग 1.9 million पर आ जाता है: करीब। पर अगर load test ने 1.2 की जगह 1.0 request प्रति second दिखाया होता, या API prices 30% गिर जातीं, तो on-demand crossover होता ही नहीं। यही fragility असली finding है।

**फ़ैसला.** A चुनो। Plan में दो review triggers लिखो: जब monthly volume 1.5 million पार करे, तो reserved GPU का quote लो और load test दोबारा चलाओ; और जब भी API price, rupee rate या कोई data rule बदले, model दोबारा चलाओ। Recommendation में लिखो कि एक साल का reservation cost को lock कर देता है, जबकि API prices आम तौर पर गिरती रहती हैं; API prices 30% कम होने पर reserved crossover लगभग 6.1 million तक खिसक जाता है।

**Value की तरफ़.** Pilot ने दिखाया कि महीने के 40,000 claims पर हर claim में 9 मिनट बचते हैं, यानी लगभग 6,000 staff hours। ₹400 प्रति घंटे की illustrative loaded staff cost पर, ये हर claim पर ₹60 का समय है, जबकि हर claim पर AI cost लगभग ₹23 (₹9.2 lakh ÷ 40,000)। Leadership team को यही ratio याद रहेगा, token bill नहीं।

## आम गलतियाँ

- **Token price की तुलना GPU किराए से करना.** दोनों तरफ़ हर line गिनो: लोग, infrastructure, evals, बदलाव। दोनों options में सबसे ज़्यादा बार छूटने वाली line लोग हैं।
- **Usage का अंदाज़ा लगाना.** हर user action पर calls और हर call के tokens traces से मापो, retrieve हुए context और छुपे reasoning tokens समेत।
- **Average के लिए size करना, या पूरा utilisation मान लेना.** GPUs peak cover करते हैं और पूरे महीने bill होते हैं। Utilisation को model में डालो।
- **पहले crossover पर भरोसा करना.** पूरे-GPU steps lines को cross और uncross कराते हैं। Stable point report करो और ये कि वो कितना खिसकता है।
- **Price-fall row के बिना GPUs reserve करना.** API prices गिरने पर लंबा commitment पुराना होकर घाटा दे सकता है।
- **Rupee और GST को नज़रअंदाज़ करना.** Dollar bill exchange rate के साथ बदलता है, और अगर GST वापस claim नहीं हो सकता तो वो असली cost है।
- **बिना date की prices.** कुछ ही महीनों में वो चुपचाप गलत हो जाती हैं।
- **Value की तरफ़ कुछ नहीं.** बचाए गए घंटों या errors के बिना cost model कुछ भी justify नहीं कर सकता।

## कब detailed cost model ज़रूरी नहीं

- **छोटे, तय budget वाला pilot**: एक spend cap और हफ़्ते में एक बार bill देखना काफ़ी है।
- **कोई असली विकल्प नहीं**, जैसे data rules on-premises hosting ज़रूरी कर दें: cost को budget बनाने के लिए model करो, चुनने के लिए नहीं।
- **बहुत कम usage**, जहाँ value के सामने cost एक rounding error है।

## Demo से production तक

- **Cost model को repository में रखो**, date वाली prices, rupee rate और मापे हुए usage के साथ।
- **हर महीने इसे reconcile करो**, traces और असली bill से, और हर फ़र्क समझाओ।
- **हर unit काम की cost track करो**, हर unit की value के बगल में, उसी dashboard पर।
- **Crossover दोबारा चलाओ** जब usage, prices, rupee, models या load-test results बदलें।
- **API account पर budget alerts लगाओ**, ताकि बेकाबू agent loop month end पर नहीं, कुछ ही घंटों में पकड़ में आ जाए।

## Practice

Artificial Analysis से तीन models की मौजूदा prices इकट्ठा करो, हर एक के बगल में check की date लिखो, और routing पर RouteLLM का post दोबारा पढ़ो ताकि दिखे कि tiering cost कैसे घटाता है।

1. अपने app के traces से हर user action पर calls और हर call के average input, output और reasoning tokens मापो।
2. Cost model को 100, 1,000 और 10,000 daily users के लिए adapt करो, एक API option और एक self-hosted option के साथ जिसमें utilisation, लोग और infrastructure शामिल हों।
3. एक sensitivity table (usage आधा और दोगुना, output दोगुना, API prices 30% कम, rupee ₹100 पर), stable crossover, और महीने की value की एक line जोड़ो।
