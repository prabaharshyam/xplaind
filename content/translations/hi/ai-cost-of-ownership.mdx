## ये क्या है

**Total cost of ownership (TCO)** वो सब कुछ है जो एक system किसी अवधि में, आमतौर पर एक से तीन साल में, खर्च कराता है, सिर्फ़ model का bill नहीं। AI system के लिए:

- **Model costs**: API पर tokens, या self-hosting के लिए GPUs (खरीदे या किराये पर)।
- **Infrastructure**: app का compute, databases, vector stores, storage, networking, monitoring, gateways।
- **लोग**: बनाना, चलाना, on-call, evaluate करना, upgrade करना। अक्सर सबसे बड़ा item।
- **Data work**: connectors, pipelines, golden sets की labelling, documents की सफ़ाई।
- **Compliance और security**: audits, penetration tests, reviews।
- **बदलाव**: model upgrades, re-embedding, providers के models deprecate करने पर prompt का दोबारा काम।

मक़सद options की निष्पक्ष तुलना और client के लिए ईमानदार budget है।

| साल का total cost of ownership | इसमें क्या जाता है |
|---|---|
| Model | API से tokens, या self-hosted हो तो पूरे महीने चलते GPUs |
| Infrastructure | App compute, databases, vector store, monitoring |
| लोग | Build, operate, on-call, evals, upgrades: **अक्सर सबसे बड़ा** |
| Data | Connectors, pipelines, golden sets, clean-up |
| Compliance | Audits, pen tests, reviews |
| बदलाव | Model upgrades, re-embedding, prompt rework |

```flow
dir: LR
title: एक ही usage पर options की तुलना करो
Model + infra + लोग + data + compliance + बदलाव -> हर claim की cost
हर claim की cost -> हर claim की value से तुलना करो
```

ये lesson Kolkata की एक insurance company को follow करता है जो 2,000 staff के लिए claims-document assistant की योजना बना रही है।

## ये काम कैसे करता है

**Usage से शुरू करो।** Users, हर user की रोज़ की requests, हर request के input और output tokens (traces से measure किए, अंदाज़े से नहीं), साल भर में बढ़त, और peak बनाम average।

**API option।** हर request की cost = input tokens गुणा input price + output tokens गुणा output price, caching discounts, batch discounts और model tiering के हिसाब से adjust करके। उसे महीने की requests से गुणा करो। मौजूदा price lists और independent comparisons use करो; prices अक्सर बदलती हैं, आमतौर पर नीचे की ओर।

**Self-hosted option।** Peak load को headroom के साथ संभालने के लिए ज़रूरी GPUs (load tests से), गुणा घंटे का दाम या amortise की गई खरीद, जो पूरा महीना चलते हैं, busy हों या नहीं। इसमें उसे चलाने, monitor करने और upgrade करने का engineering time जोड़ो, और open model कमज़ोर हो तो quality gap भी।

**Sensitivity।** दिखाओ कि usage अनुमान का आधा या दोगुना हो, output की लंबाई बढ़े, या prices 30% गिरें तो cost कैसे हिलती है। जो फ़ैसले सिर्फ़ एक ख़ास usage level पर ही समझ आते हैं वो नाज़ुक होते हैं।

**Unit economics।** Result को उस इकाई पर बताओ जो client के लिए मायने रखती है: हल हुए ticket पर cost, process हुए claim पर, हर employee पर महीने की। उसकी तुलना value से करो: बचे घंटे, तेज़ processing, कम errors।

**एक page पर तुलना (समझाने के लिए figures):**

| महीने के हिसाब से item | Option A: उनके cloud से API | Option B: self-hosted open model |
| --- | --- | --- |
| Model | Caching और tiering के बाद लगभग ₹6.5 lakh | चार GPUs के लिए लगभग ₹10 lakh |
| Infrastructure | लगभग ₹1.2 lakh | लगभग ₹1.5 lakh |
| लोग | एक engineer का एक छोटा हिस्सा | लगभग 1.5 engineers, लगभग ₹3 lakh |
| Evals पर quality | Baseline | 2 points कम |
| साल का कुल | लगभग ₹1 crore | लगभग ₹1.75 crore |

**Sensitivity व्यवहार में।** दोनों options को मापे गए usage के आधे और दोगुने पर, दोगुने लंबे outputs के साथ, और API prices 30% कम करके दोबारा निकालो। Crossover point लिख लो, यानी वो usage जहाँ self-hosting सस्ता हो जाएगा। यहाँ वो मौजूदा volume का लगभग तीन गुना है। वो एक number बहस को review trigger में बदल देता है: "महीने की requests 3 million पार करें तो दोबारा देखो"।

**Value वाला पक्ष।** अकेली cost किसी system को सही नहीं ठहरा सकती। Pilot से value जोड़ो: हर task पर बचे मिनट गुणा महीने के tasks, बचे errors, customers के लिए तेज़ turnaround। Cost और value हर इकाई पर साथ-साथ रखो, ताकि leaders सिर्फ़ bill नहीं, margin भी देखें।

**ऐसा cost model जिसे आप दोबारा चला सको।** Assumptions एक जगह रखो, हर price की check की तारीख़ के साथ:

```python
PRICES = {"checked": "2026-11-08", "usd_to_inr": 84,
          "in_per_m": 3.0, "out_per_m": 15.0, "cache_read_ratio": 0.1,      # USD per million tokens
          "gpu_hour_inr": 250, "engineer_month_inr": 250_000}

def api_month(requests, in_tok, out_tok, cached_share=0.5, small_share=0.0, small_ratio=0.25):
    p = PRICES
    per_req_usd = (in_tok * (1 - cached_share) * p["in_per_m"] + in_tok * cached_share * p["in_per_m"] * p["cache_read_ratio"]
                   + out_tok * p["out_per_m"]) / 1e6
    blended = per_req_usd * (1 - small_share + small_share * small_ratio)       # share sent to a cheaper model
    return requests * blended * p["usd_to_inr"]

def self_host_month(gpus, engineers=1.5, infra_inr=150_000):
    p = PRICES
    return gpus * p["gpu_hour_inr"] * 730 + engineers * p["engineer_month_inr"] + infra_inr

def table(base_requests, in_tok=3000, out_tok=400, gpus=4):
    print(f"prices checked {PRICES['checked']}")
    for label, mult in [("half usage", 0.5), ("measured", 1), ("double usage", 2)]:
        a = api_month(base_requests * mult, in_tok, out_tok, small_share=0.4) + 0.3 * PRICES["engineer_month_inr"]
        s = self_host_month(gpus if mult <= 1 else gpus * 2)
        print(f"{label:<13} API ₹{a/1e5:6.1f} lakh   self-hosted ₹{s/1e5:6.1f} lakh")

table(base_requests=600_000)
```

Client का असली usage traces से और मौजूदा quotes डालो। Print होने वाली तारीख़ सबको ईमानदार रखती है कि prices कब सही थीं।

**Crossover ढूँढो।** Usage तब तक बढ़ाते जाओ जब तक self-hosted line API line के नीचे न आ जाए:

```python
def crossover(in_tok=3000, out_tok=400, gpus_per_million=2):
    for r in range(100_000, 20_000_001, 100_000):
        gpus = max(1, round(r / 1e6 * gpus_per_million))
        if self_host_month(gpus) < api_month(r, in_tok, out_tok, small_share=0.4):
            return r
    return None
```

`gpus_per_million` load test से आना चाहिए, अंदाज़े से नहीं। Crossover अपेक्षित usage से बहुत ऊपर हो तो फ़ैसला आसान है; पास हो तो usage बढ़ने पर दोबारा देखने की योजना रखो।

**हर line गिनो।** Tokens और GPUs से आगे: embeddings और re-embedding, vector database, tracing और log storage, evaluation runs (judge calls जुड़ती जाती हैं), staging environments, security reviews, और system को चलाने, monitor करने और सुधारने वाले लोग। लोगों को छोड़ देना इन तुलनाओं में सबसे आम गलती है।

**Cost के साथ value जोड़ो।** काम की हर इकाई के लिए, मापी हुई value को cost के बगल में रखो: बचे मिनट गुणा प्रति मिनट loaded staff cost, बचे errors, तेज़ turnaround। एक लाइन का ratio ("हर ticket पर ₹4 AI cost, ₹60 का staff time बचा") वही है जो decision-makers को याद रहता है।

## एक example से समझो

Kolkata की एक insurance company 2,000 staff के लिए claims-document assistant roll out करने की योजना बना रही है। Pilot में मापा गया: हर user की एक काम के दिन 25 requests, हर request में 3,000 input tokens (ज़्यादातर retrieve किए passages) और 300 output tokens। यानी महीने में लगभग 1.1 million requests।

**Option A, उनके cloud से API।** समझाने के लिए ₹0.25 प्रति 1,000 input tokens और ₹1.00 प्रति 1,000 output tokens पर: (3 × 0.25) + (0.3 × 1.00) = हर request ₹1.05, महीने के लगभग ₹11.5 lakh। न बदलने वाले system prompt पर prompt caching और आसान lookups को छोटे model पर tier करने से ये लगभग ₹6.5 lakh हो जाता है। Infrastructure ₹1.2 lakh। Operations के लिए एक engineer का एक छोटा हिस्सा।

**Option B, self-hosted open model।** Load tests peak load के लिए तीन GPUs और एक spare दिखाते हैं, समझाने के लिए ₹2.5 lakh प्रति GPU प्रति महीना: ₹10 lakh। Infrastructure ₹1.5 lakh। साथ में serving stack चलाने के लिए लगभग डेढ़ engineers, महीने के लगभग ₹3 lakh। Evals में accuracy 2 points कम निकलती है।

साल भर में A की लागत लगभग ₹1 crore और B की लगभग ₹1.75 crore है। B तभी जीतता है जब usage तीन गुना हो जाए या data rules ऐसा माँगें। Client A चुनता है, और volume महीने में 3 million requests पार करे तो review के साथ। Value वाला पक्ष: pilot में महीने के 40,000 claims पर हर claim में 9 minute बचे, यानी लगभग 6,000 staff hours, जो cost से आराम से ऊपर है।

(यहाँ prices सिर्फ़ समझाने के लिए हैं। Model बनाने के दिन providers और comparisons से मौजूदा prices use करो।)

| Pilot से measure | Value |
| --- | --- |
| हर claim पर बचा समय | 9 minutes |
| महीने के claims | 40,000 |
| महीने में बचे staff hours | लगभग 6,000 |
| फ़ैसला | Option A, volume महीने में 3 million requests पार करे तो review |

## आम गलतियाँ

- **सिर्फ़ tokens या सिर्फ़ GPUs गिनना।** लोगों और बदलाव की cost अक्सर सब पर भारी पड़ती है।
- **Token counts का अंदाज़ा लगाना।** असली traces से measure करो; retrieve किया context input tokens बढ़ा देता है।
- **Average के हिसाब से size करना।** Self-hosted capacity को peaks संभालने होते हैं; APIs उन्हें खुद सोख लेती हैं।
- **Price trends को नज़रअंदाज़ करना।** API prices लगातार गिरी हैं; तीन साल की GPU commitments शायद अच्छी न बीतें।
- **Value वाला पक्ष न होना।** बचे घंटों या errors के बिना cost model किसी चीज़ को सही नहीं ठहरा सकता।
- **Self-hosted (और API) cost से लोगों को छोड़ देना।**
- **बिना तारीख़ की prices**, जो महीनों बाद चुपचाप पुरानी पड़ जाती हैं।
- **GPU counts का अंदाज़ा लगाना**, load test से capacity measure करने की जगह।

## कब विस्तृत cost model की ज़रूरत नहीं

- **छोटे, तय budget वाला pilot**: spend cap और हर हफ़्ते bill पर एक नज़र काफ़ी है।
- **कोई असली विकल्प न हो**, जैसे data rules on-premises hosting ज़रूरी कर दें: चुनने के लिए नहीं, budgeting के लिए cost model बनाओ।
- **बहुत छोटा usage**, जहाँ value के सामने cost एक rounding error है।

## Demo से production तक

- **Cost model को repository में रखो**, तारीख़ वाली prices और मापे हुए usage के साथ।
- **इसे हर महीने update करो**, traces और असली bill से, और फ़र्क समझाओ।
- **काम की हर इकाई की cost track करो**, हर इकाई की value के बगल में।
- **Usage, prices या models बदलने पर crossover दोबारा निकालो।**
- **हर line शामिल करो**: evals, tracing, storage, staging और लोग।

## Practice करो

किसी independent comparison site से तीन models की मौजूदा prices जुटाओ, और routing पर RouteLLM post दोबारा पढ़ो।

1. अपने app के traces से हर request के औसत input और output tokens measure करो।
2. रोज़ के 100, 1,000 और 10,000 users के लिए API option और self-hosted option की तुलना वाली spreadsheet बनाओ, जिसमें लोग और infrastructure शामिल हों।
3. एक sensitivity table जोड़ो (usage आधा और दोगुना, output की लंबाई दोगुनी) और महीने की value की एक लाइन।
