## ये क्या है

**Connector** वो code है जो किसी business system और आपके AI system के बीच data ले जाता है। ज़्यादातर enterprise AI projects को कई connectors चाहिए होते हैं:

- **Documents**: SharePoint और OneDrive (Microsoft Graph के ज़रिए), Google Drive, Confluence, network file shares, cloud storage buckets।
- **Records**: Salesforce जैसे CRM systems, SAP जैसे ERPs, Jira या ServiceNow जैसे ticketing, और client के अपने databases।
- **Messages**: email और chat, जिन्हें privacy की वजह से बहुत सोच-समझकर use करना होता है।

आप connectors खुद बना सकते हो, integration platform use कर सकते हो (Airbyte, Fivetran और कई दूसरे बहुत सारे ready-made connectors देते हैं), या किसी search या AI platform के साथ आने वाले connectors ले सकते हो। जो भी चुनो, आपको समझना ज़रूर चाहिए कि वो करते क्या हैं।

```flow
SharePoint -[Graph, OAuth, delta]-> Connector | pages पढ़ता है, back off करता है, resume करता है
Salesforce -[API, modified since]-> Connector
Jira, file shares, databases -> Connector
Connector -> Items + metadata + permissions + deletions -> Parse, chunk, embed -> Assistant के लिए index
Parse, chunk, embed -> Run log | 312 पढ़े, 40 added, 266 changed, 6 deleted, 0 failed
```

इस lesson में हम Gurugram की एक consumer-goods company का sales assistant देखेंगे, जो SharePoint और Salesforce पर बना है।

## ये काम कैसे करता है

**Authentication।** आम तौर पर OAuth, ऐसे app से जिसे client की IT team register करती है। Scope read-only रहता है और सिर्फ़ उन sites, objects या projects तक, जिन पर बात तय हुई हो। कुछ systems API keys या service users use करते हैं; उन्हें secret manager में रखो।

**Pages में पढ़ना।** APIs results pages में देते हैं, साथ में cursor या next link। जब तक pages ख़त्म न हों, loop चलाओ, और cursor save करो ताकि फेल हुआ run वहीं से resume हो सके।

**Rate limits।** हर API मिनट या दिन में calls की limit लगाता है; SharePoint और Salesforce भारी users को throttle करते हैं। `Retry-After` headers मानो, 429 responses पर back off करो, और बड़े पहले loads को off-peak घंटों में फैलाओ।

**Incremental sync।** पहला run सब कुछ copy करता है। बाद के runs सिर्फ़ पिछले run के बाद के बदलाव लाते हैं, change tokens (Microsoft Graph की delta queries), "modified since" filters या webhooks से। 200,000 documents को हर रात पूरा दोबारा पढ़ना धीमा है, महँगा है, और आपको throttle करवा देता है।

**Deletions।** Incremental feeds को बताना चाहिए कि क्या delete हुआ, वरना delete हुई files हमेशा के लिए searchable रहती हैं। Check करो कि आपका तरीका deletions report करता है; नहीं करता, तो ids compare करके एक periodic reconciliation चलाओ।

**Permissions।** हर item के content के साथ उसके access rights भी पढ़ो, ताकि permission-aware retrieval हो सके।

**Formats और metadata।** Source id, URL, title, author, modified time, path या object type और owner रखो। Citations, filters और debugging इन्हीं पर चलते हैं।

**Observability।** हर run में record करो कि कितने items पढ़े, added, changed, deleted और failed हुए, और कितना समय लगा। Connector रुक जाए या failures की गिनती उछल जाए, तो alert आना चाहिए।

**Changes detect करने के तरीके:**

| तरीका | कैसे काम करता है | किस पर ध्यान दें |
| --- | --- | --- |
| Change या delta tokens | API, save किए token के बाद के changes लौटाती है | Tokens expire या टूट सकते हैं; full re-scan का fallback रखो |
| Modified-since filter | पिछले run के बाद modified time वाले items query करो | अक्सर deletions miss हो जाते हैं; clocks और time zones मिलने चाहिए |
| Webhooks | कुछ बदलने पर system आपको call करता है | Calls खो सकती हैं; साथ में periodic check रखो |
| Full comparison | सारे ids की list बनाओ और अपने index से compare करो | बड़े sets पर धीमा; हफ़्ते में एक बार safety net की तरह अच्छा |

**Build, buy या borrow।** Airbyte या Fivetran जैसे integration platforms आम systems के लिए हफ़्तों बचा देते हैं, और किसी search platform के साथ आने वाले connectors शायद पहले से permissions पढ़ते हों। फिर भी उन्हें check करना पड़ता है: पक्का करो कि वो deletions report करते हैं, access rights पढ़ते हैं, और run counts दिखाते हैं जिन पर आप alert लगा सको। अपना connector तब लिखो जब system अनोखा हो, जैसे in-house database या vendor portal, या जब client की security team किसी third-party tool को approve न करे।

**Code में एक incremental connector।** SharePoint या OneDrive library के लिए Microsoft Graph की delta query बदले और delete हुए items page-by-page लौटाती है, और आख़िर में अगली बार के लिए एक link देती है:

```python
import hashlib, json, time
from pathlib import Path
import httpx

STATE = Path("state/sharepoint-delta.json")

def get(client, url):
    for attempt in range(5):
        r = client.get(url)
        if r.status_code in (429, 503):
            time.sleep(int(r.headers.get("Retry-After", 2 ** attempt)))
            continue
        r.raise_for_status()
        return r.json()
    raise RuntimeError("gave up after repeated throttling")

def sync(token, drive_id, index):
    counts = {"read": 0, "upserted": 0, "deleted": 0, "skipped": 0, "failed": 0}
    url = (json.loads(STATE.read_text())["delta_link"] if STATE.exists()
           else f"https://graph.microsoft.com/v1.0/drives/{drive_id}/root/delta")
    with httpx.Client(headers={"Authorization": f"Bearer {token}"}, timeout=30) as client:
        while url:
            page = get(client, url)
            for item in page.get("value", []):
                counts["read"] += 1
                try:
                    if "deleted" in item:
                        index.delete_doc(item["id"]); counts["deleted"] += 1
                    elif "file" in item:
                        text = download_and_parse(client, item)            # your parser
                        digest = hashlib.sha256(text.encode()).hexdigest()
                        if index.hash_of(item["id"]) == digest:
                            counts["skipped"] += 1
                        else:
                            index.upsert_doc(item["id"], text, digest, meta_from(item))
                            counts["upserted"] += 1
                except Exception:
                    counts["failed"] += 1
            url = page.get("@odata.nextLink")
            if not url and "@odata.deltaLink" in page:
                STATE.parent.mkdir(exist_ok=True)
                STATE.write_text(json.dumps({"delta_link": page["@odata.deltaLink"]}))
    print(counts)
    return counts
```

पहले run में कोई saved link नहीं होता, तो वो सब कुछ पढ़ता है; बाद के runs सिर्फ़ changes लाते हैं। Delta link तभी save करो जब आख़िरी page सफल हो जाए, ताकि fail हुआ run दोहराया जाए, changes skip न हों। अगर saved link काम करना बंद कर दे, तो full re-scan पर लौट जाओ।

**हफ़्ते में एक reconciliation।** अच्छे change feeds भी कुछ चीज़ें miss कर देते हैं। Ids compare करो:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

**बिना बदले content को skip करो।** किसी के file का नाम बदलने या property edit करने पर भी file का modified time बदल जाता है। हर document के साथ extracted text का hash store करो, और match होने पर दोबारा embed मत करो। बड़ी libraries में इससे embedding का ज़्यादातर खर्च बच जाता है।

**Source का लिहाज़ रखो।** बड़े पहले loads client के time zone में रात को चलाओ, concurrency कम रखो, और limits उनकी IT team से तय कर लो। Office hours में client का SharePoint throttle करवा देना भरोसा खोने का सबसे तेज़ तरीका है।

## एक example से समझो

Gurugram की एक consumer-goods company SharePoint (product sheets, trade-scheme circulars) और Salesforce (accounts, opportunities) पर एक sales assistant चाहती है।

SharePoint: छह sites पर read access वाला एक app registration। 38,000 files का पहला full sync throttling limits के नीचे रहने के लिए दो रातों में चलता है। उसके बाद हर 15 मिनट में delta queries सिर्फ़ बदले और delete हुए items लाती हैं, आम तौर पर हर run में 200 से 400, और इसमें करीब एक मिनट लगता है। हर item की permissions पढ़कर store की जाती हैं।

Salesforce: एक read-only integration user, जो सिर्फ़ Account, Opportunity और Product objects तक सीमित है। Records हर 30 मिनट में "modified since" query से खींचे जाते हैं और retrieval के लिए छोटे text summaries में बदले जाते हैं, record id और owner metadata के रूप में रखे जाते हैं।

तीसरे हफ़्ते में regional team एक SharePoint site का नाम बदल देती है और delta token invalid हो जाता है। Connector का error rate alert बज जाता है; job रात भर उस site का full re-scan करके संभल जाती है, और कुछ miss नहीं होता। Client की IT team के लिए आपका runbook ठीक इसी case को समझाता है।

| Measure | पहले | बाद में |
| --- | --- | --- |
| SharePoint sync | हर रात full re-read, करीब 6 घंटे, अक्सर throttle | हर 15 मिनट में delta, करीब 1 मिनट |
| Salesforce sync | रोज़ का export | हर 30 मिनट में |
| Delete हुए documents जो अब भी searchable हैं | दर्जनों | कोई नहीं, हफ़्ते में check होता है |
| Fail हुआ sync पकड़ने में लगा समय | दिनों | मिनटों में, alerts से |

## आम गलतियाँ

- **हर बार full re-sync।** Change tokens या modified-since queries use करो।
- **Deletions को ignore करना।** Delete और expire हुए documents बार-बार quote होते रहते हैं।
- **ज़रूरत से ज़्यादा access।** पूरे tenant की जगह नाम वाले sites और objects पर read-only access माँगो।
- **Failure के बाद resume नहीं।** Page 9,000 पर crash हुआ तो page 1 से दोबारा शुरू नहीं होना चाहिए।
- **चुप रहने वाले connectors।** Sync रुकने पर किसी को alert न जाए, तो assistant चुपचाप पुराना पड़ जाता है।
- **Client की IT team के लिए runbook नहीं।** लिखकर रखो कि tokens टूटें, permissions बदलें या कोई site rename हो, तो क्या करना है।
- **Run ख़त्म होने से पहले sync cursor save कर देना।** फिर crash होने पर changes हमेशा के लिए skip हो जाते हैं।
- **हर modified file को दोबारा embed करना**, भले ही सिर्फ़ metadata बदला हो।

## कब custom connector नहीं चाहिए

- **एक बार का load**, files का तय set: एक बार export करो और ingest कर दो।
- **Platform का connector उस system को पहले से cover करता है**, deletions report करता है और permissions पढ़ता है।
- **Users को जो थोड़े documents चाहिए, वो खुद सीधे upload कर सकते हैं।**

## Demo से production तक

- **हर run की counts record करो** और रुकने या failures बढ़ने पर alert लगाओ।
- **Cursors सिर्फ़ success के बाद save करो**, और full re-scan का fallback रखो।
- **हर हफ़्ते ids reconcile करो** ताकि छूटी deletions पकड़ी जाएँ।
- **Content को hash करो** ताकि बिना बदले documents skip हों।
- **Schedules और limits** client की IT team से लिखित में तय करो।

## Practice करो

Microsoft Graph overview पढ़ो, फिर कोई भी ऐसी API चुनो जिसमें paging हो और जिसे आप free में use कर सको (GitHub issues, कोई public dataset API, या developer tenant के साथ Graph)।

1. एक connector लिखो जो paging के साथ सारे items खींचे, rate limits माने और cursor store करे ताकि resume हो सके।
2. एक incremental mode जोड़ो जो पिछले run के बाद बदले items ही लाए, और ऐसा check जो delete हुए items पकड़े।
3. हर run की counts (read, added, updated, deleted, failed) record करो और एक लाइन का summary print करो।
4. अपना connector चलाओ, source पर एक file delete करो, दोबारा चलाओ, और confirm करो कि उस file के chunks index से गायब हो गए।

**आपका काम पूरा जब** आप अपना connector लगातार दो बार चला सको और दिखा सको कि दूसरा run सिर्फ़ वही लाया जो बदला था, एक deletion समेत।
