## ये क्या है

**Connector** वो code है जो business system और आपके AI system के बीच data ले जाता है। अच्छा connector चार काम करता है: सब कुछ एक बार copy करता है, उस copy को current रखता है, जो delete हुआ उसे हटाता है, और हर item के साथ ये जानकारी भी लाता है कि उसे कौन पढ़ सकता है। ज़्यादातर enterprise AI projects को कई connectors चाहिए होते हैं:

- **Documents**: SharePoint और OneDrive (Microsoft Graph के ज़रिए), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: Salesforce जैसे CRM systems, SAP जैसे ERPs, Jira या ServiceNow जैसी ticketing, और client के अपने databases.
- **Messages**: email और chat, privacy की वजह से सावधानी से use होते हैं।

Connectors आप ख़ुद build कर सकते हो, एक integration platform use कर सकते हो (Airbyte, Fivetran और कुछ और कई ready-made connectors देते हैं), या किसी search या AI platform के साथ bundled connectors use कर सकते हो। जो भी चुनो, आपको समझना होगा कि वो करते क्या हैं।

```flow
title: A connector feeding an assistant
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[REST, SystemModstamp, get deleted]-> Connector
Jira, SAP, file shares -> Connector
Connector -> Items, metadata, permissions, deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 12, changed 41, unchanged 253, deleted 6, failed 0
```

ये lesson SharePoint और Salesforce पर बने Gurugram के एक sales assistant को follow करता है।

## ये कैसे काम करता है

### Authentication

आमतौर पर OAuth, client की IT team के register किए app के साथ, read-only और तय sites, objects या projects तक scoped। कुछ systems API keys या service users use करते हैं; उन्हें secret manager में रखो, code में कभी नहीं।

लंबे runs को दो चीज़ें तोड़ती हैं। पहली, access tokens expire होते हैं: Microsoft उन्हें default 60 से 90 minute की life देता है, इसलिए दो रात चलने वाला first load एक ही token use नहीं कर सकता। हर request से पहले अपनी auth library के cache (जैसे MSAL) से token माँगो; expiry के पास वो नया token ले आता है। दूसरी, client secrets और certificates भी expire होते हैं। Date runbook में लिखो और एक महीना पहले alert करो।

### Pages में पढ़ना

APIs results pages में लौटाती हैं। हर page एक cursor या "next" link पर ख़त्म होता है। तब तक loop करो जब तक next page न बचे। जो rule मायने रखता है: **हर page पूरा process होने के बाद अपनी position save करो**, पहले नहीं और सिर्फ़ आख़िर में भी नहीं। Process करने से पहले save करोगे तो crash पर items skip हो जाएँगे; सिर्फ़ आख़िर में save करोगे तो page 9,000 पर crash होने से page 1 से restart होगा।

### Rate limits

हर API calls limit करती है। Microsoft Graph `Retry-After` header के साथ 429 Too Many Requests लौटाता है और retry करने से पहले उतनी देर wait करने को कहता है; header न हो तो exponentially back off करो। HTTP standard के हिसाब से `Retry-After` seconds की गिनती भी हो सकता है और एक date भी, इसलिए दोनों parse करो। लगभग एक second का random jitter जोड़ो ताकि parallel workers सब एक ही पल में retry करके फिर से throttle न हों।

### Incremental sync और change detection

पहला run सब कुछ copy करता है; बाद के runs सिर्फ़ बदला हुआ लाते हैं। 200,000 documents को हर रात पूरा दोबारा पढ़ना slow है, महँगा है और आपको throttle करवाता है।

| Method | उदाहरण | Deletions report करता है? | किस बात का ध्यान रखें |
| --- | --- | --- | --- |
| Delta token | Microsoft Graph delta | हाँ | Links काम करना बंद कर सकते हैं (410 Gone); full re-scan का रास्ता रखो |
| Modified-since filter | Salesforce `SystemModstamp`, Jira `updated` | नहीं | Deletion feed के साथ जोड़ो; windows को कुछ minute overlap करो |
| Deletion feed | Salesforce get-deleted resource | सिर्फ़ deletions | Salesforce ज़्यादा से ज़्यादा 15 दिन रखता है |
| Webhooks | Jira `jira:issue_deleted` | अगर वो event मौजूद हो | Deliveries खो सकती हैं; इसे कभी अकेला source मत बनाओ |
| Full id comparison | आपका weekly reconciliation | हाँ, फ़र्क़ से | बड़े sets पर slow; safety net के तौर पर हर हफ़्ते चलाओ |

Graph delta के दो gotchas: एक ही item एक feed में एक से ज़्यादा बार आ सकता है (आख़िरी वाला मान्य है, इसलिए source id से upsert करो), और delete हुआ item `deleted` marker के साथ, बिना content के लौटता है, इसलिए download करने से पहले उसे check करो।

### Deletions

Modified-since query वो record नहीं देख सकती जो अब मौजूद ही नहीं, इसलिए delete हुए documents quote होते रहते हैं। हर connector को ऐसा feed चाहिए जो deletions report करे, या एक periodic id comparison, हो सके तो दोनों।

### Permissions

सबसे मुश्किल हिस्सा: permissions को ignore करने वाला assistant एक junior employee को salary review deck दिखा देता है।

- **हर item के साथ access rights पढ़ो।** Graph का permissions endpoint किसी file की effective sharing लौटाता है, folders से inherit हुए access समेत। Allowed user और group ids हर chunk पर store करो।
- **Groups को groups ही रहने दो।** Index time पर "Sales North" को 400 user ids में expand मत करो। Query time पर user के मौजूदा groups (उनके sign-in token से या directory call से) देखो और उनसे filter करो। फिर group छोड़ने वाला इंसान उसी वक़्त access खो देता है जब आपके group lookup को बदलाव दिखता है, बिना re-index के।
- **सिर्फ़ permission वाले बदलाव दिखना मुश्किल है।** File share करने से उसका content नहीं बदलता। Graph delta sharing बदलने वाले items को mark कर सकता है अगर आप `Prefer: deltashowsharingchanges` header भेजो, साथ में `deltashowremovedasdeleted` और `deltatraversepermissiongaps`, जिन्हें Microsoft ज़रूरी बताता है। लेकिन Microsoft document करता है कि delta सिर्फ़ वो items लौटाता है जिनका content या metadata बदला, और उनके parent folders, इसलिए जो files सिर्फ़ access inherit करती हैं वो शायद न आएँ। Microsoft ये भी कहता है कि permissions ठीक से process करने के लिए `Sites.FullControl.All` app permission चाहिए, जिसे security teams अक्सर मना कर देती हैं। Marker को बस एक hint मानो। उसके पीछे उन sites और folders पर permissions का scheduled re-read रखो जिन्हें client sensitive mark करता है।
- **Fail closed.** अगर किसी item की permissions नहीं पढ़ पा रहे, तो उसे index मत करो।

### Code में एक incremental connector

एक SharePoint library के लिए ये sync ऊपर के rules follow करता है। ये हर page पर अपनी position save करता है, fail हुए items के लिए retry list रखता है, tokens refresh करता है, और throttling और टूटा delta link संभालता है:

```python
import email.utils, hashlib, json, random, time
from pathlib import Path        # client below is an httpx.Client

GRAPH = "https://graph.microsoft.com/v1.0"
STATE = Path("state/sharepoint-delta.json")

class StopRun(Exception): pass    # fatal: stop now, leave saved state as it is
class Resync(Exception): pass     # 410 Gone: the saved link no longer works

def wait_for(r, attempt):
    value = r.headers.get("Retry-After", "")
    if value.isdigit():
        delay = int(value)                                  # seconds
    elif value:
        when = email.utils.parsedate_to_datetime(value)     # an HTTP date
        delay = max(0, when.timestamp() - time.time())
    else:
        delay = min(60, 2 ** attempt)                       # no header: back off
    return delay + random.uniform(0, 1)                     # jitter

def get(client, url, token, prefer=None):
    headers = {"Authorization": f"Bearer {token()}"}  # token() reads a cache
    if prefer:
        headers["Prefer"] = prefer
    for attempt in range(6):
        r = client.get(url, headers=headers)
        if r.status_code in (429, 503):
            time.sleep(wait_for(r, attempt)); continue
        if r.status_code == 410:
            raise Resync(r.headers.get("Location"))
        if r.status_code in (401, 403):
            raise StopRun(f"access refused: {r.status_code}")
        r.raise_for_status()
        return r.json()
    raise StopRun("still throttled after 6 tries")

def process(client, token, drive_id, item, index, counts, retry):
    if "deleted" in item:
        index.delete_doc(item["id"])        # must not fail if already gone
        if item["id"] in retry:
            retry.remove(item["id"])
        counts["deleted"] += 1
        return
    if "file" not in item:
        return                              # folders carry no text
    perms = get(client, f"{GRAPH}/drives/{drive_id}/items/{item['id']}/permissions", token)
    acl = acl_from(perms)                   # user and group ids allowed to read
    text = download_and_parse(item)         # your parser
    digest = hashlib.sha256(text.encode()).hexdigest()
    if index.hash_of(item["id"]) == digest:
        index.update_meta(item["id"], meta_from(item), acl)  # renamed or reshared: no re-embed
        counts["unchanged"] += 1
    else:
        new = index.upsert_doc(item["id"], text, digest, meta_from(item), acl)
        counts["added" if new else "changed"] += 1

def save(state):
    STATE.parent.mkdir(exist_ok=True)
    tmp = STATE.with_suffix(".tmp")
    tmp.write_text(json.dumps(state))
    tmp.replace(STATE)                      # atomic: never half-written

def sync(client, token, drive_id, index):
    state = json.loads(STATE.read_text()) if STATE.exists() else {}
    retry = state.get("retry", [])
    counts = dict.fromkeys(["read", "added", "changed", "unchanged", "deleted", "failed"], 0)
    for item_id in list(retry):             # last run's failures first
        try:
            item = get(client, f"{GRAPH}/drives/{drive_id}/items/{item_id}", token)
            process(client, token, drive_id, item, index, counts, retry)
            if item_id in retry:
                retry.remove(item_id)
        except StopRun:
            raise
        except Exception:
            counts["failed"] += 1           # stays listed; alert if it stays for days
    url = (state.get("next_link") or state.get("delta_link")
           or f"{GRAPH}/drives/{drive_id}/root/delta")
    while True:
        try:
            page = get(client, url, token, prefer="deltashowremovedasdeleted, "
                       "deltatraversepermissiongaps, deltashowsharingchanges")
        except Resync as e:
            state = {"retry": retry, "reconcile": True}   # full listing, then compare ids
            url = e.args[0] or f"{GRAPH}/drives/{drive_id}/root/delta"
            continue
        for item in page.get("value", []):
            counts["read"] += 1
            try:
                process(client, token, drive_id, item, index, counts, retry)
            except StopRun:
                raise
            except Exception:
                counts["failed"] += 1
                if item["id"] not in retry:
                    retry.append(item["id"])
        state["retry"] = retry
        if "@odata.nextLink" in page:       # page done: save where to resume
            url = state["next_link"] = page["@odata.nextLink"]
            save(state)
        else:                               # last page: save the link for next time
            state.pop("next_link", None)
            state["delta_link"] = page["@odata.deltaLink"]
            save(state)
            break
    print(counts)
    return counts
```

इसे ऐसे क्यों बनाया गया है:

- **Position और failures एक साथ save होते हैं**, हर page के बाद एक atomic write में। Page के बीच crash होने पर वो page replay होता है, जो safe है क्योंकि upserts और deletes source id से keyed हैं। Fail हुआ item कभी skip नहीं होता: वो succeed होने तक retry list पर रहता है।
- **एक ख़राब file feed को freeze नहीं करती।** कोई भी item fail होने पर आगे बढ़ने से मना करना safe लगता है, लेकिन तब एक corrupt PDF आगे के हर change को block कर देगी।
- **Metadata text के साथ चलता है।** `meta_from` citations और filters के लिए source id, URL, title, path, author, modified time और owner रखता है। Rename इन्हें बदलता है पर text को नहीं, इसलिए ये बिना re-embedding के update होते हैं।
- **Fatal errors बिना save किए run रोक देते हैं।** Access error या कभी न ख़त्म होने वाली throttling item failure नहीं है; उसे item failure गिनोगे तो पूरी library retry list पर चली जाएगी।
- **टूटा link full listing trigger करता है।** 410 Gone पर Graph का `Location` header एक नया enumeration शुरू करता है। वो बताता है कि क्या मौजूद है, ये नहीं कि बीच में क्या delete हुआ, इसलिए `reconcile` flag scheduler को अगली बार id comparison चलाने को कहता है।

### एक weekly reconciliation

अच्छे change feeds से भी चीज़ें छूट जाती हैं। Source के पास जो ids हैं उन्हें index की ids से compare करो:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

अगर `removed_stale` बस दो-चार से ज़्यादा है, तो आपके change feed में bug है; उसे ठीक करो।

### Records: Salesforce, Jira और SAP

- **Salesforce.** बदले records को `LastModifiedDate` पर नहीं, `SystemModstamp` पर filter लगाकर query करो, क्योंकि automated processes record बदलें तब भी `SystemModstamp` आगे बढ़ता है। पिछले run time से कुछ minute घटा लो ताकि देर से commit हुए records न छूटें। Deletions के लिए हर object पर UTC में start और end time के साथ get-deleted REST resource call करो। ये ज़्यादा से ज़्यादा पिछले 15 दिन cover करता है और minute तक काम करता है, इसलिए अगर connector उससे ज़्यादा समय down रहा, तो सिर्फ़ full id comparison ही बराबरी करा सकता है। साथ ही, ये सिर्फ़ वही deletions दिखाता है जो integration user देख सकता था।
- **Jira Cloud.** `search/jql` endpoint से JQL के साथ search करो, जो पुराने `startAt` offset की जगह `nextPageToken` से page करता है। `updated >= "last run time"` से filter करो। Delete हुए issues search से बस ग़ायब हो जाते हैं, इसलिए `jira:issue_deleted` webhook subscribe करो और फिर भी ids reconcile करो, क्योंकि webhooks छूट सकते हैं।
- **SAP.** Direct table access कम ही मिलता है। Client की SAP team data expose करती है, आमतौर पर OData services के रूप में (अक्सर CDS views पर बनी), कभी-कभी पुराने BAPI या RFC calls से, या अपने integration middleware से। कुछ OData services delta tokens support करती हैं; वरना changed-on date field और reconciliation use करो। मुख्य gotcha समय है: service बनवाने और approve करवाने में आपके code से ज़्यादा वक़्त लगता है, इसलिए पहले हफ़्ते में ही माँग लो।
- **Schema drift.** Admins fields जोड़ते हैं, picklist values rename करते हैं और objects retire करते हैं। अपने URLs में API version pin करो, सिर्फ़ तय fields map करो, और सब कुछ चुपचाप index करने की जगह तब alert करो जब describe call नए या ग़ायब fields दिखाए।
- **Record permissions.** Salesforce access owners, roles और sharing rules से आता है, जिन्हें हूबहू copy करना मुश्किल है। Safe first release सिर्फ़ वो objects index करता है जो हर sales user पढ़ सकता है, या record दिखाने से पहले user के अपने login से live access check करता है।

### Build, buy या borrow

Airbyte या Fivetran जैसे integration platforms आम systems के लिए हफ़्तों का काम बचाते हैं। किसी पर भरोसा करने से पहले check करो कि वो deletions report करता है, access rights साथ लाता है और ऐसे run counts expose करता है जिन पर आप alert कर सको। अपना ख़ुद का connector उन systems के लिए लिखो जो आम नहीं हैं, जैसे in-house database, या जब client की security team third-party tool approve न करे।

## एक worked example

Gurugram की एक consumer-goods company SharePoint (product sheets, trade-scheme circulars) और Salesforce (accounts, opportunities) पर एक sales assistant चाहती है। नीचे के figures illustrative हैं, काम की shape दिखाने के लिए।

**SharePoint.** छह sites पर read access वाला एक app registration। मान लो 38,000 files का पहला full sync throttling limits से काफ़ी नीचे रहने के लिए दो रातों में बाँटा गया है; अगर save किया next link अब भी काम करता है तो दूसरी रात वहीं से आगे चलती है, और अगर Graph 410 जवाब दे तो listing फिर से शुरू होती है। उसके बाद हर 15 minute पर एक delta run कुछ सौ changed या deleted items लौटाता है और लगभग एक minute में ख़त्म होता है। हर run changed items की permissions भी दोबारा पढ़ता है, और एक nightly job उन दो sites पर permissions दोबारा पढ़ता है जिनमें pricing और HR files हैं।

**Salesforce.** Account, Opportunity और Product तक सीमित एक read-only integration user। हर 30 minute पर connector उन records को query करता है जिनका `SystemModstamp` पिछले run time माइनस पाँच minute के बाद का है, हर एक को record id और owner को metadata के तौर पर रखकर एक छोटी text summary में बदलता है, और उसी window के लिए get-deleted resource call करता है। अगर कोई sales manager 11:10 पर एक duplicate account delete करे, तो वो लगभग 11:30 तक index से निकल जाता है।

**Incident.** मान लो तीसरे हफ़्ते में एक delta request 410 Gone लौटाती है। Connector `Location` header follow करता है, रात भर library re-list करता है, फिर id comparison चलाकर वो 14 files हटाता है जो link टूटे रहने के दौरान delete हुईं। Client के notice करने से पहले alert on-call engineer तक पहुँच गया, और runbook में ये case पहले से था।

| पैमाना | पहले | बाद में |
| --- | --- | --- |
| SharePoint sync | हर रात full re-read, लगभग 6 घंटे, अक्सर throttled | हर 15 minute पर delta, लगभग 1 minute |
| Salesforce sync | Daily export, deletions कभी नहीं हटते | हर 30 minute, deletions एक run के अंदर |
| Delete हुए documents अब भी searchable | दर्जनों | Weekly check में एक भी नहीं |
| Fail हुए sync को notice करने का समय | दिन | Minutes, alerts के ज़रिए |

## आम गलतियाँ

- **हर बार full re-sync.** First load के बाद delta tokens या modified-since queries use करो।
- **Deletions को ignore करना.** Modified-since query delete हुए records कभी return नहीं करती; deletion feed और weekly id comparison जोड़ो।
- **गलत समय पर cursor save करना.** Process से पहले save करने से crash के बाद items skip होते हैं; सिर्फ़ आख़िर में करने से page 1 से restart होता है। हर page के बाद save करो।
- **Fail हुए items को निगल जाना.** Failure गिनकर आगे बढ़ जाने से वो item हमेशा के लिए खो जाता है। Retry list रखो।
- **लंबे run के लिए एक token.** वो 60 से 90 minute में expire होता है और job रात 3 बजे मर जाता है।
- **Index time पर groups को users में expand करना.** फिर membership के बदलाव लागू होने के लिए full re-index चाहिए।
- **ज़रूरत से ज़्यादा access.** पूरे tenant का नहीं, नाम लिए sites और objects का read-only access माँगो।
- **चुप रहने वाले connectors.** अगर sync रुकने पर किसी को alert नहीं जाता, तो assistant चुपचाप stale हो जाता है।
- **हर modified file को re-embed करना**, तब भी जब सिर्फ़ उसका metadata बदला हो।

## कब custom connector की ज़रूरत नहीं

- **One-off load**, files के एक fixed set का: एक बार export करो और ingest करो।
- **कोई platform connector पहले से उस system को cover करता है**, deletions report करता है और permissions पढ़ता है।
- **Users जिन कुछ documents की ज़रूरत है उन्हें** सीधे upload कर सकते हैं।

## Demo से production तक

शुरुआती defaults, client की IT team के साथ लिखित में तय:

- **Schedules:** document delta हर 15 minute, record queries हर 30 minute, permission re-read हर रात, full id comparison हर हफ़्ते। बड़े first loads सिर्फ़ client के time zone में रात को, कम concurrency के साथ।
- **Alerts:** कोई run fail हो या दो intervals के अंदर start न हो; पढ़े गए items आम के आधे से नीचे गिरें; कोई item एक दिन से ज़्यादा retry list पर रहे; कोई secret 30 दिन के अंदर expire होने वाला हो।
- **Runbook:** 410 Gone पर, access error पर, और जब कोई site, object या field rename हो, तब क्या करना है।

## Practice करो

Microsoft Graph overview पढ़ो, फिर paging वाली कोई भी API चुनो जो free में use कर सको (GitHub issues, कोई public dataset API, या developer tenant के साथ Graph)।

1. ऐसा connector लिखो जो paging के साथ सारे items खींचे, `Retry-After` का पालन करे, और हर page के बाद अपनी position save करे ताकि resume कर सके।
2. First load के बीच में उसे kill करो और restart करो। Confirm करो कि वो save किए page से आगे बढ़ता है और फिर से शुरू नहीं करता।
3. एक incremental mode जोड़ो जो पिछले run के बाद बदले items ही लाए, और एक check जो delete हुए items detect करे।
4. हर run के counts (read, added, changed, unchanged, deleted, failed) record करो और one-line summary print करो।
5. Source पर एक item delete करो, rerun करो, और confirm करो कि उसके chunks index से चले गए।

**आपका काम पूरा है जब आप** अपना connector लगातार दो बार चला सको और दिखा सको कि दूसरा run सिर्फ़ बदला हुआ लाता है, एक deletion समेत, और दिखा सको कि crash हुआ run सही page से resume होता है।
