## ये क्या है

Public cloud आपको computers, storage, networks और ready-made services किराए पर देता है, और bill use के हिसाब से आता है। AWS, Microsoft Azure और Google Cloud लगभग एक जैसे building blocks अलग नामों से देते हैं। Enterprises आम तौर पर पूरे group की एक choice follow करते हैं, और banks, insurers और pharma companies अक्सर ये rules भी जोड़ते हैं कि data कहाँ रह सकता है।

ये lesson Azure को गहराई से देखता है, क्योंकि course के resources Microsoft Learn paths हैं। हर step का दूसरे clouds पर करीबी match है, जो नीचे की table में दिखाया गया है।

एक AI deployment लगभग सात तरह की services use करता है:

- **Compute**: जहाँ आपका code चलता है।
- **Storage**: files और documents।
- **Databases**: structured data, अक्सर embeddings के लिए pgvector extension के साथ PostgreSQL।
- **Networking**: virtual networks, private endpoints, और एक ही public entry point।
- **Identity and access**: कौन और क्या, कौन-से actions कर सकता है।
- **Managed models**: hosted model APIs, जहाँ deployment type तय करता है कि prompts कहाँ process होंगे।
- **Monitoring**: logs, metrics और alerts, ताकि आप देख सको कि क्या हुआ।

**Shared responsibility.** Provider buildings, hardware और managed services को secure करता है। जो आप configure करते हो वो आपकी ज़िम्मेदारी है: आपका data, उसे कौन access कर सकता है, कौन-से endpoints public हैं, और आप कितना खर्च करते हो। "Cloud security basics" lesson इसमें और गहराई से जाता है।

```flow
title: Central India में, एक virtual network के अंदर document assistant
Staff | Entra ID sign-in -> Application Gateway | अकेला public entry, HTTPS
Application Gateway -> Container Apps | internal-only environment, managed identity
Container Apps -[private endpoint]-> Blob Storage
Container Apps -[private access]-> PostgreSQL with pgvector
Container Apps -[secret reference]-> Key Vault
Container Apps -[private endpoint]-> Foundry model | regional Standard deployment
Container Apps -> Log Analytics
```

ये lesson Hyderabad की एक pharma company को follow करता है, जब आप Azure पर उसका document assistant design करते हो।

## ये कैसे काम करता है

### Regions और zones

Region एक इलाके में data centres का एक group है। Azure के India में चार हैं: Central India (Pune), South India (Chennai), West India (Mumbai) और India South Central (Hyderabad), जो August 2026 में launch हुआ। AWS के Mumbai और Hyderabad हैं; Google Cloud के Mumbai और Delhi।

कुछ regions में availability zones होते हैं: अलग data centres जिनकी अपनी power और cooling है, इसलिए zones में फैले replicas एक के fail होने पर भी बचे रहते हैं। हर region में zones या हर service नहीं होती, इसलिए जो भी service use करनी है, उसके लिए Azure का products-by-region page check करो।

Region इस क्रम में चुनो:

1. **Residency**: client की policy, contracts और regulators क्या माँगते हैं।
2. **Availability**: क्या आपकी सारी services, और सही deployment type वाला model, वहाँ मिलते हैं?
3. **Latency**: users से दूरी। Chat app के लिए हर Indian region काफ़ी पास है।
4. **Price**: regions के बीच prices थोड़े अलग होते हैं; ये सबसे कम मायने रखता है।

वजहें लिखकर रखो; client की cloud team पूछेगी।

### Compute के choices

| आपको चाहिए | चुनो | क्यों |
| --- | --- | --- |
| Container में HTTP API (ज़्यादातर AI apps) | Container Apps | Replicas, scaling, HTTPS और revisions built-in हैं |
| Events या timer से चलने वाले छोटे jobs | Container Apps jobs या Azure Functions | सिर्फ़ job चलने तक pay करो |
| Client के मौजूदा platform में fit होना | AKS (managed Kubernetes) | तभी, जब उनकी platform team पहले से इसे चलाती हो |
| GPUs या machine का पूरा control | Virtual machines | Patch और scale आपको खुद करना होगा |

Container Apps चल रहे replicas के CPU और memory का bill करता है। `--min-replicas 0` idle होने पर zero तक scale कर देता है, लेकिन कुछ देर शांति के बाद आने वाली पहली request को cold start का इंतज़ार करना पड़ता है। Staff tool के लिए एक warm replica ठीक सौदा है।

### Storage और databases

Documents के लिए Blob Storage और records और vectors के लिए Azure Database for PostgreSQL (flexible server) use करो; backups, patching और failover built-in आते हैं। दो details लोगों को फँसा देती हैं:

- pgvector को create करने से पहले allow-list करना पड़ता है: server parameter `azure.extensions` को `vector` पर set करो, फिर `CREATE EXTENSION vector;` चलाओ। Extension का नाम `vector` है, `pgvector` नहीं।
- Server बनाते समय ही **private access** (`--vnet` और `--subnet`) चुनो। ये शुरू में ही तय करो: बाद में बदलने के लिए downtime वाला migration करना पड़ता है।

### Networking और private endpoints

सब कुछ एक virtual network में रहता है। Container Apps environment को अपना subnet मिलता है और वो internal-only होता है, इसलिए app का कोई public address नहीं होता। अकेला public entry एक Application Gateway है, या client का मौजूदा gateway।

Blob Storage, Key Vault और Foundry तक **private endpoints** से पहुँचते हैं: आपके network के अंदर उस service का एक private IP address। फिर हर service का public network access बंद करो। Classic गलती: endpoint मौजूद है, लेकिन कोई private DNS zone (जैसे `privatelink.blob.core.windows.net`) network से link नहीं है। Name अब भी public address पर resolve होता है, जिसे आपने अभी बंद किया, और हर call fail होती है।

### Identity

App को एक **managed identity** दो: Azure उसे short-lived tokens देता है, इसलिए store या leak होने के लिए कोई key नहीं होती। उसे सबसे छोटे scope पर roles दो जिस पर काम चल जाए:

- **Storage Blob Data Reader** एक blob container पर, पूरी subscription पर नहीं।
- **Key Vault Secrets User** एक vault पर।
- **Cognitive Services OpenAI User** Foundry resource पर।
- **AcrPull** container registry पर।

दो gotchas। Owner और Contributor जैसे management roles आपको resource बदलने देते हैं, लेकिन अपने token से उसका data पढ़ने नहीं देते; उसके लिए data role चाहिए। और role assignments को लागू होने में कुछ minutes लग सकते हैं, इसलिए grant करने के तुरंत बाद आया 403 अपने आप ठीक हो सकता है।

लोग company के Microsoft Entra ID से sign in करते हैं, shared accounts से कभी नहीं।

### Managed models और residency का जाल

Microsoft Foundry (November 2025 में Azure AI Foundry से नाम बदला गया) client के Azure contract के तहत models host करता है। Prompts कहाँ process होंगे, ये resource का region नहीं, **deployment type** तय करता है:

| Deployment type | Prompts कहाँ process हो सकते हैं | कब use करें |
| --- | --- | --- |
| Global (Standard या provisioned) | किसी भी Azure region में जहाँ model चलता है | कोई residency rule नहीं; सबसे ज़्यादा quota चाहिए |
| Data Zone | Microsoft के तय किए zone के अंदर: US, EU या Asia Pacific | Rule एक multi-country zone की इजाज़त देता है |
| Standard या provisioned, regional | Deployment का अपना region | Data को India में ही process होना है |

हर type में stored data resource की geography में ही रहता है; जो बदलता है वो ये है कि हर request कहाँ process होती है। Central India resource पर Global deployment भी prompt को विदेश भेज सकता है। नए models अक्सर शुरू में सिर्फ़ Global के रूप में मिलते हैं, इसलिए residency का वादा करने से पहले region-availability table और portal का deployment dialog check करो। AWS में भी यही switch है: India inference profile (`in.` से शुरू होने वाले model IDs) सिर्फ़ Mumbai और Hyderabad के बीच route करता है, जबकि `global.` profile कहीं भी route कर सकता है।

App अपनी managed identity से अपना deployment call करता है, इसलिए कोई API key है ही नहीं:

```python
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token = get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")
client = OpenAI(base_url="https://docassist-ai.openai.azure.com/openai/v1/", api_key=token)
reply = client.chat.completions.create(
    model="docassist-chat",  # your deployment's name, not a model ID
    messages=[{"role": "user", "content": "Summarise this stability report: ..."}])
```

### Quotas

Model throughput एक quota से limited होता है, tokens per minute में, हर model, region और subscription के हिसाब से। नई subscription पर GPU virtual machine quota अक्सर zero से शुरू होता है। Increases तुरंत नहीं मिलते और मना भी हो सकते हैं, इसलिए quota पहले हफ़्ते में request करो, launch वाले हफ़्ते में नहीं।

### Command line से deploy करो

ये commands वही बनाते हैं जो diagram दिखाता है; `$` variables में पिछले steps के IDs हैं।

```bash
# 1. Create the identity first, so it can be granted access before the app exists.
az identity create -g rg-docassist -n id-docassist -l centralindia
ID=$(az identity show -g rg-docassist -n id-docassist --query id -o tsv)
PRINCIPAL=$(az identity show -g rg-docassist -n id-docassist --query principalId -o tsv)
CLIENT_ID=$(az identity show -g rg-docassist -n id-docassist --query clientId -o tsv)

# 2. Least privilege. Repeat for Key Vault Secrets User, AcrPull and Cognitive Services OpenAI User.
az role assignment create --assignee-object-id "$PRINCIPAL" --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Reader" --scope "$STORAGE_ID/blobServices/default/containers/source-pdfs"

# 3. An internal-only environment on your own subnet, sending logs to Log Analytics.
az containerapp env create -g rg-docassist -n env-docassist -l centralindia \
  --infrastructure-subnet-resource-id "$APPS_SUBNET_ID" --internal-only true \
  --logs-destination log-analytics --logs-workspace-id "$WORKSPACE_GUID" --logs-workspace-key "$WORKSPACE_KEY"

# 4. The app: ingress reachable only inside the network, secrets by reference, a hard ceiling on replicas.
az containerapp create -g rg-docassist -n docassist-api --environment env-docassist \
  --image acrdocassist.azurecr.io/docassist-api:3f9c2e1 \
  --registry-server acrdocassist.azurecr.io --registry-identity "$ID" --user-assigned "$ID" \
  --secrets "db-url=keyvaultref:https://kv-docassist.vault.azure.net/secrets/db-url,identityref:$ID" \
  --env-vars DATABASE_URL=secretref:db-url AZURE_CLIENT_ID="$CLIENT_ID" \
  --ingress external --target-port 8000 --cpu 1 --memory 2Gi --min-replicas 1 --max-replicas 5
```

`AZURE_CLIENT_ID` बताता है कि `DefaultAzureCredential` कौन-सी user-assigned identity use करे; इसके बिना token requests fail हो सकती हैं। Compute खर्च पर असली cap `--max-replicas` है।

### Logs, metrics और cost

Container Apps console logs को Log Analytics workspace में भेजता है। Request times और errors के लिए Application Insights जोड़ो, और error rate और slow responses पर alert लगाओ। Logs का bill हर ingest हुए gigabyte पर लगता है, इसलिए पूरे prompts या documents log मत करो: इसमें पैसे लगते हैं और sensitive data की copy बनती है।

AI app के bill में आम तौर पर सबसे आगे model tokens होते हैं, फिर database, compute, logs और cloud से बाहर जाने वाला data। हर resource को project और environment से tag करो ताकि bill बाँटा जा सके। पहले दिन ही alerts के साथ budget set करो:

```bash
az consumption budget create-with-rg -g rg-docassist -n docassist-pilot \
  --amount 125000 --category Cost --time-grain Monthly --time-period start-date=2026-12-01 \
  --notifications "{at80:{enabled:true,operator:GreaterThan,threshold:80,contact-emails:[cloud-alerts@example.com]}}"
```

Start date किसी महीने की पहली तारीख होनी चाहिए, और तीन महीने से ज़्यादा आगे की नहीं। Amount subscription की billing currency में होता है। Budget सिर्फ़ alert करता है: ये कुछ भी नहीं रोकता, और cost data घंटों देर से आ सकता है। Alerts किसी shared mailbox या channel पर भेजो, किसी एक इंसान को नहीं।

## एक example से समझो

Azure पर Hyderabad की एक pharma company अपनी regulatory team के लिए document assistant चाहती है। Requirements: data India में store और process हो, कोई public database नहीं, company accounts से sign-in, और रोज़ लगभग 1,500 सवालों का एक pilot।

**1. Region.** Hyderabad का India South Central सबसे पास है, लेकिन वो August 2026 में खुला और Microsoft धीरे-धीरे services जोड़ रहा है। मान लो products-by-region page दिखाता है कि design को जो चाहिए वो सब Central India में है: आप उसे चुनते हो और Hyderabad को बाद के लिए note कर लेते हो।

**2. Model.** मान लो team का पहली पसंद वाला model India में सिर्फ़ Global Standard के रूप में मिलता है। वो processing rule में fail होता है। मान लो एक दूसरा model Central India में regional Standard के रूप में मिलता है और team के 40 test सवालों में pass होता है: आप उसे deploy करते हो। उसी दिन उसका tokens-per-minute quota request करते हो।

**3. Network और identity.** Design diagram को follow करता है: company के Application Gateway के पीछे एक internal Container Apps environment; Blob Storage, Key Vault और Foundry उनके DNS zones के साथ private endpoints से; PostgreSQL private access के साथ। एक user-assigned identity के पास ऊपर बताए चारों roles हैं, हर एक सबसे छोटे scope पर।

**4. Cost.** बनाने से पहले अंदाज़ा लगाओ। नीचे का हर price समझाने के लिए माना हुआ figure है, quote नहीं; जिस दिन check करो, हर एक को अपने region के लिए Azure pricing calculator के number से बदलो। आप इसे इसी page पर चला सकते हो।

```python
# Illustrative prices only. Replace each with the Azure pricing calculator's figure.
replica_rupees_per_hour = 8           # suppose: one replica, 1 vCPU and 2 GiB
replica_hours = (2 * 12 + 1 * 12) * 30  # 2 replicas by day, 1 at night
fixed = {"PostgreSQL": 12_000, "Blob, Key Vault, private endpoints": 3_000,
         "Log Analytics": 4_000, "Data transfer out": 500}

questions = 1_500 * 30                 # per month
input_tokens, output_tokens = 4_000, 500  # per question, with retrieved chunks
rupees_per_m_in, rupees_per_m_out = 250, 1_000  # suppose

compute = replica_rupees_per_hour * replica_hours
infra = compute + sum(fixed.values())
tokens = questions * (input_tokens * rupees_per_m_in + output_tokens * rupees_per_m_out) / 1e6
print(f"compute ₹{compute:,}  infrastructure ₹{infra:,}  tokens ₹{tokens:,.0f}")
print(f"total ₹{infra + tokens:,.0f} a month, ₹{(infra + tokens) / questions:.2f} per question")
```

ये infrastructure ₹28,140 और tokens ₹67,500 print करता है: महीने के ₹95,640, यानी हर सवाल पर ₹2.13। Tokens का खर्च पूरे infrastructure से भी ज़्यादा है, इसलिए पहले उन्हें optimise करो।

| Line (समझाने के लिए) | महीने का | किससे बढ़ता है | कैसे कम करें |
| --- | --- | --- | --- |
| Model tokens | ₹67,500 | सवाल × हर सवाल के tokens | कम और छोटे retrieved chunks; दोहराए जाने वाले answers cache करो |
| PostgreSQL | ₹12,000 | Server size और storage | छोटा शुरू करो; नापे हुए load पर resize करो |
| Container Apps | ₹8,640 | Replica-hours | रात में एक replica; dev के लिए zero तक scale |
| Log Analytics | ₹4,000 | Ingest हुए logs के gigabytes | Prompts नहीं, metadata log करो |
| Blob, Key Vault, endpoints | ₹3,000 | Stored data, हर घंटे के endpoints | पुराने versions archive करो |
| Data transfer out | ₹500 | Azure से बाहर जाने वाला data | Traffic को region के अंदर रखो |

Client को rupees में bill होता है, इसलिए budget महीने का 1,25,000 है, ताकि उसका 80% alert ₹95,640 के अंदाज़े से थोड़ा ऊपर आए। `--max-replicas 5` और हर user के लिए घंटे में 60 सवालों की limit, budget का email आने से बहुत पहले बेकाबू loop पर cap लगा देते हैं।

**5. Review.** Cloud teams बाहर के designs को आम तौर पर public endpoints, stored keys, विदेशी regions या साफ़ न बताई गई model processing की वजह से reject करती हैं। ये design चारों से बचता है, वही services use करता है जो वो पहले से चलाते हैं, और diagram और region और deployment type पर एक page के note के साथ आता है। उनका अकेला बदलाव उनकी naming convention है।

## आम गलतियाँ

- **तीन clouds ऊपर-ऊपर से सीखना।** एक को ठीक से सीखो, फिर translate करो।
- **Model residency के लिए resource के region पर भरोसा करना।** Global और Data Zone deployments prompts को India के बाहर process कर सकते हैं। Deployment type check करो।
- **Public databases और storage।** Private access और private endpoints use करो, और public network access बंद करो।
- **Private DNS zone के बिना private endpoint।** Name बंद public address पर resolve होता है और हर call fail होती है।
- **Code या settings में keys।** इसमें portal से copy की गई storage account keys भी आती हैं। Managed identities और Key Vault references use करो, और shared-key access बंद करो।
- **Data role की जगह Owner या Contributor**, या "काम चलाने के लिए" subscription scope पर roles देना।
- **Budget को cap समझना।** ये सिर्फ़ alert करता है। `--max-replicas` और rate limits set करो।
- **Compute गिनना लेकिन tokens और logs नहीं**, जो AI apps में अक्सर बड़ी lines होती हैं।
- **Launch वाले हफ़्ते में quota request करना।** Increases तुरंत नहीं मिलते।
- **बिना tag के resources**, जिससे कोई नहीं बता सकता कि किस project का कितना खर्च है।

## कब कम cloud से काम चल जाता है

- **Prototype या demo**: Vercel, Render या Railway जैसा platform और एक hosted database ज़्यादा तेज़ है। असली data आने पर move करो।

- **बिना sensitive data वाला छोटा internal tool**: built-in sign-in वाला एक Container App काफ़ी हो सकता है; पूरा private network ज़रूरत से ज़्यादा है।

## Demo से production तक

- **सब कुछ code में।** Repository में Bicep या Terraform, pull requests में review हुआ; production में portal से हाथ से कोई बदलाव नहीं।
- **अलग environments।** Dev और prod के लिए अलग resource groups या subscriptions, हर एक का अपना budget।
- **Policy से guardrails।** सिर्फ़ Indian regions की इजाज़त देने वाली Azure Policy residency लागू रखती है, चाहे कोई गलती कर दे, और एक और policy public network access को deny कर सकती है।
- **Resilience।** जहाँ region में zone redundancy हो वहाँ use करो, database restore test करो, और client को चाहिए तो disaster recovery के लिए दूसरा Indian region चुनो।
- **ऐसे alerts जिन पर लोग action लें।** Error rate, slow responses, रोज़ का token use और quota use, एक named owner वाले shared channel पर भेजे गए।
- **एक design record।** Region, deployment type, network boundaries और identities, हर एक की वजह के साथ, client के review के लिए तैयार।
