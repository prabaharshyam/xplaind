## ये क्या है

**Deployment model** दो सवालों का जवाब देता है: model और application कहाँ चलते हैं, और उन्हें कौन control करता है? मुख्य options, कम से ज़्यादा control तक:

1. **Vendor API (multi-tenant SaaS)**: आप model provider के public endpoint को बुलाते हो। शुरू करने में सबसे तेज़, सबसे नए models, सबसे कम control।
2. **Client के cloud से model**: वही या मिलते-जुलते models client के अपने cloud account और region के अंदर (Amazon Bedrock, Azure AI Foundry, Google Vertex AI), उस cloud contract के तहत जो उनके पास पहले से है।
3. **Dedicated या private capacity**: reserved capacity या private endpoint, कभी-कभी private networking के साथ ताकि traffic कभी public internet से न गुज़रे।
4. **Client के cloud में self-hosted open-weight models**: आप Llama, Qwen, Mistral या Gemma variants जैसे models उनके account की GPU machines पर चलाते हो।
5. **On-premises**: वही, client के अपने data centre में।
6. **Air-gapped**: बाहरी networks से बिल्कुल कोई connection नहीं। Models, code और updates controlled transfer से आते हैं।

Application (API, retrieval, database) भी model से अलग, यही choices follow कर सकती है।

```flow
dir: LR
title: कम control और तेज़ शुरुआत से, ज़्यादा control और ज़्यादा काम तक
Vendor API | हफ़्ते -> Client का cloud | मंज़ूर tenancy और region
Client का cloud -> Dedicated | private network
Dedicated -> Self-hosted | उनके GPUs, आप चलाते हो
Self-hosted -> On-prem | उनका data centre
On-prem -> Air-gapped | कोई network नहीं, सिर्फ़ transfers
```

App, retrieval और logs model से अलग rung पर हो सकते हैं।

ये lesson तीन clients के साथ चलता है, Bengaluru, Mumbai और Hyderabad में, जिन्हें हर एक को अलग deployment चाहिए था।

## ये काम कैसे करता है

**चुनाव किससे तय होता है।**

- *Data rules*: regulation, contracts और internal policy कि data कहाँ जा सकता है। Indian regulators और कई enterprises चाहते हैं कि data India में रहे; कुछ data premises से बाहर जा ही नहीं सकता।
- *ज़रूरी model quality*: सबसे मज़बूत models आम तौर पर सिर्फ़ APIs या cloud partners के ज़रिए मिलते हैं। Open-weight models कई tasks पर करीब पीछे हैं और extraction, classification और अच्छे से तय scope वाले documents पर RAG के लिए ठीक हैं।
- *Cost और volume*: APIs प्रति token charge करते हैं; self-hosting में बड़ी fixed GPU cost होती है जो सिर्फ़ high, steady volume पर वसूल होती है।
- *Skills*: self-hosting के लिए ऐसे लोग चाहिए जो GPUs, serving engines, monitoring और upgrades चला सकें।
- *Latency और availability*: on-premises network delay घटा सकता है, पर uptime client की team पर आ जाता है।

**शुरू में पूछने वाले सवाल।** Data कहाँ process हो सकता है? क्या कोई provider पहले से मंज़ूर है? क्या कोई मौजूदा cloud contract है? Handover के बाद system कौन चलाएगा? Model को upgrade करना पड़े तो क्या होगा?

**Hybrid आम है।** Sensitive requests को self-hosted model पर और बाकी को API पर भेजो; या embeddings के लिए self-hosted model और generation के लिए cloud model use करो।

**Air-gapped की ख़ास बातें।** कोई package downloads नहीं, कोई model downloads नहीं, कोई SaaS monitoring नहीं, internet पर कोई license checks नहीं। सब कुछ (container images, model weights, Python packages) bundle, scan और transfer होता है। Updates को scheduled releases की तरह plan करो।

**Options को score करना:**

| Factor | Vendor API | Client का cloud | Self-hosted | Air-gapped |
| --- | --- | --- | --- | --- |
| Data control | सबसे कम | ज़्यादा, उनके tenancy में | बहुत ज़्यादा | पूरा |
| Model quality | सबसे मज़बूत | मज़बूत | अच्छा open-weight | अच्छा open-weight |
| कम volume पर cost | सबसे कम | कम | ज़्यादा: बेकार GPUs | सबसे ज़्यादा |
| Launch का समय | दिन से हफ़्ते | हफ़्ते | महीने | महीने |
| ज़रूरी skills | कम | Cloud skills | GPU serving, monitoring | ये सब, offline |

**पहली meeting के सवाल।** ये data कहाँ process हो सकता है, और क्या कोई provider पहले से मंज़ूर है? क्या कोई मौजूदा cloud contract और region है? कौन-सा data, अगर कोई है, premises से कभी बाहर नहीं जा सकता? Handover के बाद system कौन चलाएगा, और क्या उनके पास GPU skills हैं? Model को कितनी बार upgrade करना पड़ेगा, और कौन मंज़ूर करेगा? जवाब आम तौर पर घंटे भर में छह options को एक-दो तक ला देते हैं।

**Offline sites के लिए bill of materials।** Air-gapped build के लिए हर artefact list करो: pinned versions वाली container images, checksums वाले model weights, Python और system packages, vector database, offline चलने वाले monitoring tools, और documentation। Client की security team उन्हें scan और transfer करती है। एक package छूटने से release हफ़्तों देर हो सकता है, इसलिए असली visit से पहले disconnected test machine पर install का rehearsal कर लो।

**API या self-hosted, numbers में।** पहली तुलना जिसे आप असली quotes के साथ दोबारा कर सकते हो (हर price की date record करो):

```python
def monthly_costs(tokens_in_m, tokens_out_m, api_in_usd, api_out_usd,
                  gpu_hour_inr, gpus, hours=730, ops_people=0.5, ops_cost_inr=250_000, usd_to_inr=84):
    """tokens in millions per month; API prices in USD per million tokens."""
    api = (tokens_in_m * api_in_usd + tokens_out_m * api_out_usd) * usd_to_inr
    self_host = gpu_hour_inr * gpus * hours + ops_people * ops_cost_inr
    return {"API ₹/month": round(api), "self-hosted ₹/month": round(self_host),
            "cheaper": "API" if api < self_host else "self-hosted"}

print(monthly_costs(tokens_in_m=900, tokens_out_m=120, api_in_usd=0.8, api_out_usd=4,
                    gpu_hour_inr=250, gpus=2))
```

GPUs हर घंटे पैसे लेते हैं, चाहे use हों या नहीं, इसलिए self-hosting सिर्फ़ high, steady volume पर जीतता है, या जब data rules कोई और रास्ता न छोड़ें। लोगों को भी गिनो: किसी को serving stack patch, monitor और upgrade करना होगा।

**Sensitivity से route करो।** Hybrid design में एक छोटा rule तय करता है कि हर request कहाँ जाए:

```python
SENSITIVE_FIELDS = {"aadhaar", "pan", "medical_history", "bank_account"}

def route(request):
    if request.get("classification") == "restricted" or SENSITIVE_FIELDS & set(request.get("fields", [])):
        return "self_hosted"            # stays on the client's servers
    return "cloud_model"                # stronger model, client's cloud region
```

Rule को client के data owner के साथ लिखो, हर data class के examples से test करो, और हर request का route log करो।

**Air-gapped bundle बनाना।** Connected build machine पर versions और checksums के साथ सब कुछ जमा करो, फिर client की मंज़ूर प्रक्रिया से transfer करो:

```bash
mkdir -p bundle/{images,models,wheels}
docker pull vllm/vllm-openai:v0.10.1 && docker save vllm/vllm-openai:v0.10.1 | gzip > bundle/images/vllm.tar.gz
docker save claims-api:1.4.0 | gzip > bundle/images/claims-api.tar.gz
huggingface-cli download org/model-8b-instruct --revision <commit> --local-dir bundle/models/model-8b
pip download -r requirements.txt -d bundle/wheels
(cd bundle && find . -type f -exec sha256sum {} \; > SHA256SUMS)
```

Offline तरफ़, `sha256sum -c SHA256SUMS` साबित करता है कि रास्ते में कुछ नहीं बदला, `docker load` images वापस लाता है, और `pip install --no-index --find-links wheels -r requirements.txt` बिना internet के install करता है। असली visit से पहले, networking बंद की हुई machine पर पूरे install का rehearsal करो।

**Upgrades शुरू से plan करो।** हर option को नए model versions का रास्ता चाहिए: API खुद बदलता है (pin करो और test करो), client का cloud अपने schedule पर models जोड़ता है, और self-hosted या offline setups को दोहराने लायक bundle-और-test process चाहिए।

## एक example से समझो

तीन clients, तीन जवाब:

- *Bengaluru का एक D2C brand*: customer-support assistant, सिर्फ़ public data, छोटी team। Gateway के ज़रिए **Vendor API**, जहाँ मिले वहाँ Indian region। तीन हफ़्ते में live।
- *Mumbai का एक private bank*: confidential documents पर internal policy assistant। Bank की risk team ने Central India में उसका Azure tenancy पहले ही मंज़ूर किया हुआ है। **Client के cloud से models**, private networking और bank की keys के साथ। Approval छह महीने की जगह चार हफ़्ते में हो गया क्योंकि कुछ नया मंज़ूर कराना ही नहीं था।
- *Hyderabad का एक defence electronics supplier*: classified network पर engineering-document search। **Air-gapped self-hosting**: दो on-premises GPU servers पर vLLM से serve होता open-weight model, उसी network पर embeddings और vector database, और images और weights का तिमाही update package जिसे client की security team scan और transfer करती है। Model frontier APIs से कम सक्षम है, इसलिए scope retrieval और summarisation तक सीमित है, जहाँ evals दिखाते हैं कि वो अच्छा चलता है।

| Client | Deployment | क्यों | नतीजा |
| --- | --- | --- | --- |
| Bengaluru D2C brand | Gateway के ज़रिए Vendor API | Public data, छोटी team | तीन हफ़्ते में live |
| Mumbai private bank | अपने मंज़ूर Azure tenancy में models | Confidential documents, मौजूदा approval | चार हफ़्ते में मंज़ूर |
| Hyderabad defence supplier | Local GPUs पर air-gapped vLLM | Classified network | Scope retrieval और summaries तक सीमित |

## आम गलतियाँ

- **Data rules पूछने से पहले public API सुझाना।** आप हफ़्ते और साख खो देते हो।
- **मान लेना कि self-hosting सस्ता है।** कम volume पर बेकार पड़े GPUs tokens से कहीं ज़्यादा महँगे हैं।
- **ये नज़रअंदाज़ करना कि इसे कौन चलाएगा।** Self-hosted model जिसे client में कोई upgrade न कर सके, बोझ बन जाता है।
- **"Open-weight" को "कोई licence terms नहीं" समझना।** हर model का licence commercial use की सीमाओं के लिए पढ़ो।
- **बाकी stack भूल जाना।** Traces, logs और vector stores पर भी model जैसे ही rules लगने चाहिए।
- **GPU cost की API cost से तुलना**, बेकार घंटे और चलाने वाले लोग गिने बिना।
- **Air-gapped installs का offline rehearsal न करना**, जो पहले छूटे package पर fail हो जाते हैं।
- **Self-hosted या offline setups में models के लिए upgrade का रास्ता न होना।**

## जब चुनाव सीधा है

- **कम या अनिश्चित volume और कोई सख़्त data rules नहीं**: API या client के cloud की model service से शुरू करो।
- **Data premises से कभी बाहर नहीं जा सकता**: self-hosted या air-gapped, cost जो भी हो।
- **Value साबित करने के लिए pilot**: जो सबसे तेज़ option मंज़ूर है उसे use करो, और scale करने से पहले फिर देखो।

## Demo से production तक

- **Data rules और decision को record करो**, तारीखों और सहमत हुए लोगों के साथ।
- **पहले कुछ महीनों के बाद cost की तुलना असली volumes से दोबारा करो।**
- **Hybrid setups में हर request का route log करो।**
- **Offline और self-hosted upgrades के लिए test की हुई bundle process रखो।**
- **जो भी option चुनो, model versions को pin और test करो।**
