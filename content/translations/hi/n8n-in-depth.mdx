## ये क्या है

आपके पहले n8n workflow में एक trigger और कुछ nodes थे। जिन workflows पर कोई business टिका होता है, वो इससे आगे जाते हैं। वो हज़ारों records process करते हैं, सख़्त limits वाली APIs को call करते हैं, ऐसे दो systems का data जोड़ते हैं जो आपस में मेल नहीं खाते, और उन्हें तब भी चलते रहना होता है जब रात 3 बजे कुछ fail हो और कोई देख न रहा हो।

इनमें से हर चीज़ के लिए n8n में एक building block है:

| Building block | किस काम का |
| --- | --- |
| **Sub-workflows** | साझा steps जिन्हें कई workflows call करते हैं, functions की तरह |
| **Paging, batches और waits** | किसी API की limits तोड़े बिना data fetch करना और भेजना |
| **Merge** | दो sources को एक shared id से जोड़ना, match न होने वाले items समेत |
| **Code nodes** | छोटे JavaScript या Python snippets, उस logic के लिए जो visual nodes cover नहीं करते |
| **AI nodes** | Emails जैसे बिखरे text को पढ़कर ऐसे fields बनाना जिन्हें rules check कर सकें |
| **Error workflows** | Automatic run fail होने पर किसी इंसान को alert करना |

ये lesson Bengaluru के एक skincare brand को follow करता है जो अपना daily payment reconciliation automate करता है, यानी ये check करने का काम कि हर prepaid order का पैसा payment gateway ने सच में pay out किया या नहीं।

```flow
title: रोज़ का payment reconciliation
Schedule: सुबह 6 बजे IST -> Shopify: prepaid orders, पिछले 10 दिन
Schedule: सुबह 6 बजे IST -> Gateway: settled payments, पिछले 3 दिन | pages में, रफ़्तार कंट्रोल करके
Shopify: prepaid orders, पिछले 10 दिन -> Payment id पर Merge | दोनों तरफ़ के unmatched items रखता है
Gateway: settled payments, पिछले 3 दिन -> Payment id पर Merge
Payment id पर Merge -> Code: हर row को flag करो -> Sub-workflow: sheet में upsert -> Slack: summary
कोई भी failure -> Error workflow | execution link के साथ finance-ops को alert
```

## ये कैसे काम करता है

### Items: हर चीज़ के नीचे का idea

हर node **items** की एक list लेता है और एक list आगे भेजता है। हर item एक JSON record है, जैसे sheet की एक row। ज़्यादातर nodes हर item के लिए एक बार चलते हैं: Gmail में दस items गए तो दस emails। `{{ $json.email }}` जैसा **expression** current item का एक field पढ़ता है। किसी पिछले node का field पढ़ने के लिए उस node का नाम लो: `{{ $('Get orders').item.json.order_name }}`।

### Structure: एक workflow, एक काम

हर workflow को एक काम तक रखो। साझा steps को एक **sub-workflow** में रखो: एक अलग workflow जो **When Executed by Another Workflow** trigger से शुरू होता है और **Execute Sub-workflow** node से call होता है। Trigger में कोई भी data लेने की जगह वो input fields define करो जिनकी आपको उम्मीद है, जैसे `payment_id` और `flag`। फिर call करने वाला node ठीक-ठीक बताता है कि कौन-से fields भरने हैं, और कोई छूट जाए तो आसानी से दिख जाता है।

Nodes के नाम उनके काम के हिसाब से रखो, जैसे "Get prepaid orders", न कि "HTTP Request 3", ताकि कोई भी canvas पढ़ सके।

### Volume और rate limits

ज़्यादातर APIs results एक बार में एक **page** देती हैं और limit लगाती हैं कि आप एक second या एक मिनट में कितनी requests भेज सकते हो। तीन tools साथ मिलकर काम करते हैं:

- **Pagination** page के बाद page fetch करता है जब तक और pages न बचें। HTTP Request node में pagination option है, और कई app nodes में "Return All" switch होता है जो आपके लिए paging कर देता है।
- **Batching** कंट्रोल करता है कि आप कितनी तेज़ी से भेजते हो। HTTP Request node में Batching option है (हर batch में कितने items, और batches के बीच pause)। ज़्यादा कंट्रोल के लिए batch size के साथ **Loop Over Items** और loop के अंदर एक **Wait** node use करो।
- **Retry On Fail**, जो हर node की settings में है, fail हुई call को दोहराता है। ये ज़्यादा से ज़्यादा पाँच tries और उनके बीच ज़्यादा से ज़्यादा पाँच seconds देता है, इसलिए ये छोटी-सी रुकावट संभालता है, pacing नहीं और लंबा outage भी नहीं।

Pacing का rule सीधा हिसाब है। अगर limit एक मिनट में L requests है और हर batch B requests भेजता है, तो batches के बीच कम से कम B × 60 ÷ L seconds wait करो। एक batch में 20 requests और एक मिनट में 60 की limit हो, तो 20 seconds। थोड़ा margin जोड़ो, क्योंकि एक batch के अंदर की requests एक ही पल में निकल सकती हैं।

```flow
dir: LR
एक page request करो | 100 rows -> Rows process करो -> और pages हैं?
और pages हैं? -[हाँ, एक pause के बाद]-> एक page request करो
और pages हैं? -[नहीं]-> अगला step
```

### Data merge करना, और जो match न हो उसे रखना

**Merge** node दो inputs को position से, या **matching fields** से जोड़ सकता है, जैसे एक payment id जो दोनों में हो। Matching fields के लिए output setting तय करती है कि क्या बचेगा:

| Output choice | क्या निकलता है | किसके जैसा |
| --- | --- | --- |
| Keep Matches | सिर्फ़ वो items जो दोनों inputs में मिले | एक inner join |
| Keep Non-Matches | सिर्फ़ वो items जिनका कोई partner नहीं | बचे हुए items |
| Keep Everything | दोनों inputs से matches और non-matches | एक full outer join |
| Enrich Input 1 or 2 | एक input पूरा, साथ में दूसरे से match होने वाला data | एक left या right join |

ऊपर के labels recent versions के हैं; अपने version में dropdown check करो। Reconciliation में unmatched items ही findings हैं, इसलिए Keep Matches हर problem छिपा देगा। Keep Everything चुनो; अकेला Keep Non-Matches उन matched rows को भी drop कर देगा जिनके amounts अभी check करने हैं। दो और traps: अगर दोनों inputs में `amount` नाम का field है, तो एक दूसरे को overwrite कर देता है, इसलिए पहले एक **Edit Fields** node से fields का नाम बदलो। और ऐसी key पर match करो जो दोनों तरफ़ unique हो, जैसे payment id, न कि ऐसी जो दोहराई जा सके, जैसे customer का phone number।

### Code nodes

**Code** node JavaScript या Python चलाता है। "Run Once for All Items" mode में, जो default है, ये `$input.all()` से हर item पढ़ता है, `$('Node name').all()` से किसी दूसरे node के items पढ़ सकता है, और इसे objects की एक list return करनी होती है, हर एक में एक `json` key के साथ। ये वाला भारतीय तरीके से लिखा amount जोड़ता है:

```js
// Mode: Run Once for All Items
return $input.all().map((item) => ({
  json: {
    ...item.json,
    amount_text: (item.json.amount / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' }),
  },
}));
```

12500000 paise के amount के लिए `amount_text` "₹1,25,000.00" है। जब तक Python की ज़रूरत न हो, JavaScript ही चुनो: n8n 2.0 से Code node native Python चलाता है, जो items को `_items` के रूप में पढ़ता है और उसमें n8n के बाकी built-in helpers में से कोई नहीं होता। Code nodes छोटे और comments के साथ रखो। अगर कोई एक screen से बड़ा हो जाए, तो वो node के अंदर छिपी एक छोटी service है, और वहाँ उसे test करना मुश्किल है।

### Schedules और time zones

Schedule trigger workflow के time zone में fire होता है। Self-hosted instance default रूप से America/New_York पर रहता है जब तक आप `GENERIC_TIMEZONE` variable set न करो, इसलिए "सुबह 6 बजे" वाला job भारत की दोपहर में चल सकता है। Workflow की settings में time zone Asia/Kolkata set करो, फिर executions list में run times check करो। `$now` जैसे expressions भी इसी setting को follow करते हैं, तो "कल" का मतलब भारत का कल।

### AI कब use करें, और कब नहीं

AI node सिर्फ़ वहीं use करो जहाँ rules काम नहीं कर सकते: free text पढ़ने में। एक अच्छा उदाहरण है किसी wholesale buyer का email जिसमें लिखा हो "paid ₹48,300 against invoices 112 and 118, less TDS"। Structured output वाला **Information Extractor** इसे invoice numbers और एक amount में बदल सकता है, जिसे फिर एक IF node आपकी invoice list से check करता है, इससे पहले कि कोई इंसान confirm करे। Rule ये है: अगर IF, Switch या Code node फ़ैसला कर सकता है, तो model से मत पूछो। पैसों के mismatches के लिए "reasons" लिखने वाला model खर्च बढ़ाता है और कोई ऐसी वजह गढ़ सकता है जो सही लगे। AI Agent को उन tasks के लिए रखो जहाँ अगली tool call इस पर निर्भर करती है कि पिछली ने क्या लौटाया, "Automation with n8n" lesson वाले safeguards के साथ।

| --- | --- |
| API nodes पर Retry On Fail | छोटे network errors दूसरी try में अपने आप ठीक हो जाते हैं |
| Idempotent writes | Unique id पर upsert, ताकि rerun rows को duplicate करने की जगह update करे |
| Overlapping time windows | सिर्फ़ कल का नहीं, कुछ दिनों का data fetch करो, ताकि एक छूटा run अगले दिन अपने आप ठीक हो जाए |
| एक error workflow | Error Trigger से शुरू होता है और workflow, fail हुआ node और execution link team को post करता है |
| Item-count checks | जो step rows लौटाना चाहिए वो कुछ न लौटाए तो alert; zero items एक branch रोक देते हैं, इसलिए पहले Always Output Data on करो |

Error workflow को main workflow की settings में set करो, और error workflow को भी publish करो। ये सिर्फ़ automatic runs के लिए fire होता है, उन runs के लिए नहीं जो आप editor में हाथ से शुरू करते हो, इसलिए इसे एक छोटे schedule से test करो।

### Pinned data से testing

किसी node का output **Pin** करो, जैसे gateway call, और editor API को दोबारा call करने की जगह उसी को reuse करता है। Production runs pinned data को ignore करते हैं। मुश्किल pinned cases का एक set रखो, जैसे एक refund, अजीब paise वाला amount और बिना payment id वाला order, और हर बदलाव के बाद उन्हें दोबारा चलाओ।

### Maintainability

November 2026 तक, n8n का built-in Git source control उसके Business और Enterprise plans पर है। दूसरे plans पर workflows को JSON में export करो और खुद Git में commit करो। अपने credentials के साथ एक अलग test instance या project रखो, और production तभी बदलो जब test run pass हो जाए।

### Self-hosting basics

n8n open source नहीं है। इसका Sustainable Use License आपके अपने business के लिए self-hosting allow करता है; client work के बारे में "Automation with n8n" lesson बताता है। Self-hosting, जैसे Docker के साथ, आपको operator बना देता है:

- **Encryption key.** n8n saved credentials को अपनी बनाई एक key से encrypt करता है। अगर data volume नहीं रखा गया, तो दोबारा बना container नई key बनाता है और हर credential पढ़ा नहीं जा सकता। `N8N_ENCRYPTION_KEY` खुद set करो और database के साथ उसका भी backup लो।
- **Disk.** Execution data default रूप से 14 दिन या 10,000 executions के बाद prune होता है। Pruning on रखो, और किसी busy workflow के हर successful run का पूरा data save मत करो।
- **Database और scale.** किसी भी serious काम के लिए Postgres use करो। High volume के लिए **queue mode** Redis से runs को अलग worker processes को देता है।
- **Updates.** n8n में critical security flaws आ चुके हैं, January 2026 वाला भी शामिल है। Security releases कुछ ही दिनों में लगाओ।

## एक worked example

Bengaluru का एक D2C skincare brand Shopify पर रोज़ लगभग 1,500 orders बेचता है। उदाहरण के लिए मान लो लगभग 60% Razorpay से prepaid हैं और बाकी cash on delivery। हर सुबह finance में Kavya दो घंटे ये check करने में लगाती है कि हर prepaid order का पैसा pay out हुआ या नहीं। Gateway के बारे में तीन बातें design तय करती हैं:

- **Settlements बाद में आते हैं।** Razorpay का standard domestic cycle capture से T+2 working days है, और ये merchant के हिसाब से बदलता है। कल के orders अभी settle नहीं हुए, इसलिए कल को कल से match करोगे तो सब कुछ flag हो जाएगा।
- **Rows की key payment id है।** हर settlement row में एक `entity_id` (`pay_` से शुरू होने वाला payment id), `amount`, `fee`, `tax` और `credit` होता है। इसका `order_id` Razorpay का अपना order id है, Shopify order number नहीं। इसलिए store को checkout पर हर order में Razorpay payment id save करना होगा; ये कहाँ रहता है, ये आपकी checkout app पर निर्भर है।
- **Amounts paise में हैं, और fees कटती हैं।** `amount` paise में gross payment है। `fee` में वो GST पहले से शामिल है जो `tax` दिखाता है, और `credit` है `amount` में से `fee` घटाकर। `credit` को order total से compare करोगे तो हर order flag होगा। उसकी जगह `amount` compare करो, और fee अलग से check करो।

Kavya का workflow, time zone Asia/Kolkata पर set करके:

| # | Node | क्या करता है |
| --- | --- | --- |
| 1 | Schedule trigger और Sheets | IST सुबह 6 बजे चलता है; ऊपर वाली branch पर एक Sheets node, ताकि वो पहले चले, results sheet को "Read results" के रूप में पढ़ता है |
| 2 | Shopify, फिर Filter | Return All से पिछले 10 दिन के orders लेता है, prepaid वाले रखता है |
| 3 | HTTP Request | पिछले 3 दिन की settlement rows page by page लेता है, लगभग एक request प्रति second |
| 4 | Filter और Edit Fields | Payment rows रखता है (refunds का अपना type है), fields का नाम बदलता है ताकि कुछ न टकराए |
| 5 | Merge | `payment_id` पर match करता है, Keep Everything |
| 6 | Code | पहले से ok mark हुए payments skip करता है, बाकी को flag करता है (नीचे देखो) |
| 7 | Sub-workflow "Upsert result" | Sheets Append or Update Row, `payment_id` पर match करके |
| 8 | IF और Slack | Working day पर step 3 को कोई row न मिले तो alert; वरना counts और sheet link post करता है |
| + | Error workflow | Execution link के साथ finance-ops को alert |

Step 6 का Code node:

```js
// Mode: Run Once for All Items. Each item is one merged row.
const done = new Set($('Read results').all()
  .filter((i) => i.json.flag === 'ok').map((i) => i.json.payment_id));
const out = [];
for (const item of $input.all()) {
  const r = item.json;
  if (done.has(r.payment_id)) continue; // never downgrade an ok row
  const orderPaise = Math.round(Number(r.order_total) * 100);
  let flag = 'ok';
  if (!r.order_name) {
    flag = 'settled, no order found';
  } else if (!r.settlement_id) {
    const days = $now.diff(DateTime.fromISO(r.paid_at), 'days').days;
    flag = days > 5 ? 'settlement overdue' : 'waiting';
  } else if (r.gateway_amount !== orderPaise) {
    flag = 'amount differs';
  } else if (r.gateway_fee > Math.ceil(r.gateway_amount * 0.0236)) {
    flag = 'fee above contract'; // 2% plus 18% GST; use your rate
  }
  const paise = r.gateway_amount ?? orderPaise;
  const amount_text = (paise / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' });
  out.push({ json: { ...r, flag, amount_text } });
}
return out;
```

`Math.round` order total को, जिसे Shopify "1499.50" जैसे text में भेजता है, पूरे paise में बदल देता है, ताकि छोटी decimal गलतियाँ, जैसे ₹1.15 के लिए 114.99999, false alarm न बना सकें। `Math.ceil` fee की rounding की गुंजाइश देता है। 2% rate सिर्फ़ एक उदाहरण है; अपने contract वाला rate use करो। जैसे, 2% पर ₹1,000 के UPI payment की fee ₹20 और साथ में ₹3.60 GST है, तो `fee` 2360 paise है और `credit` 97640।

हर flag एक साफ़ action तक ले जाता है, जिसे एक template लिखता है, model नहीं:

| Flag | आम तौर पर मतलब | कौन action लेता है |
| --- | --- | --- |
| waiting | Pay हो गया, normal settlement window के अंदर है | अभी कोई नहीं |
| settlement overdue | 5 दिन से ज़्यादा हुए और अभी भी settle नहीं हुआ | Finance इसे gateway के साथ उठाता है |
| amount differs | Payment के बाद order edit हुआ, या part refund | Finance order history check करता है |
| settled, no order found | किसी दूसरे channel का payment, या गायब payment id | Store team order record ठीक करती है |
| fee above contract | गलत pricing plan लगा है | Finance इसे gateway के साथ उठाता है |

क्योंकि writes `payment_id` पर upserts हैं, कोई row duplicates के ढेर बनने की जगह किसी अगली सुबह "waiting" से "ok" हो जाती है। Skip ज़रूरी है: जैसे ही कोई settlement 3-day window से बाहर जाता है, वरना उसका order unsettled दिखेगा और दोबारा "overdue" flag हो जाएगा। 10-day order window देर से settle होने वाले payments को cover करती है। 5-day limit एक trade-off है: bank holidays वाला लंबा weekend कुछ false alarms ला सकता है, जिन्हें team किसी असली problem को miss करने की जगह मंज़ूर करती है।

**एक बुरी सुबह।** एक दिन सुबह 6 बजे gateway की API errors लौटा रही थी। Retries fail हुए, और error workflow ने execution link के साथ alert post किया। Kavya ने सुबह 9 बजे इसे दोबारा चलाया। Upserts की वजह से कोई duplicate नहीं बना, और क्योंकि हर run तीन दिन का data fetch करता है, पूरा दिन छूट भी जाता तो अगली सुबह cover हो जाता।

## आम गलतियाँ

- **एक बहुत बड़ा workflow।** साझा steps को defined inputs वाले, नाम दिए sub-workflows में बाँटो।
- **Rate limits को नज़रअंदाज़ करना।** Page, batch और wait करो; retries pacing नहीं हैं।
- **Reconciliation के लिए Keep Matches से merge करना।** ये चुपचाप वही problems drop कर देता है जो आप ढूँढ रहे हो।
- **Net को gross से, या rupees को paise से compare करना।** एक जैसी चीज़ों को एक जैसी चीज़ों से, पूरे paise में compare करो।
- **कल को कल से match करना।** Settlements देर से आते हैं; overlapping windows use करो।
- **Non-idempotent writes।** सादे appends हर rerun पर duplicates बनाते हैं।
- **Time zone को default पर छोड़ना।** Workflow settings में Asia/Kolkata set करो।
- **जहाँ rule काफ़ी हो वहाँ AI use करना।** कभी किसी model को पैसों की वजह समझाने मत दो।
- **Error workflow को हाथ से test करना।** ये सिर्फ़ automatic runs के लिए fire होता है।
- **Encryption key खो देना।** ज़रूरत पड़ने से पहले database के साथ इसका backup लो।

## Practice

नीचे linked n8n का N8N102 Integrations course पूरा करो, और hosting overview पढ़ो।

1. **Volume.** एक workflow बनाओ जो किसी API या sheet से कम से कम 300 rows pages में ले और उन्हें Wait के साथ batches में process करे। Limit से wait निकालो, और वो हिसाब एक sticky note में लिखो।
2. **Merge और write.** दो sources को एक shared id पर Keep Everything से merge करो, एक छोटे Code node में हर row को flag करो, और एक sub-workflow से लिखो जो id पर upsert करे। हर flag के लिए एक मुश्किल case pin करो।
3. **Failure.** Time zone Asia/Kolkata set करो, एक error workflow जोड़ो, जानबूझकर एक node तोड़ो, और workflow को एक छोटे schedule पर चलने दो। Alert confirm करो, फिर दोबारा चलाओ।

**आपका काम पूरा है जब आप** अपना workflow लगातार दो बार बिना duplicates बनाए दोबारा चला सको, और fail हुए execution के link के साथ एक error alert दिखा सको।
