## ये क्या है

**Latency budget** वो सबसे धीमा response है जो आप एक तय percentile पर मानते हो, और जिसे request के हर step के एक target में बांटा जाता है। जैसे एक chat assistant के लिए: p95 time to first token 2 seconds के अंदर, p95 full answer 10 seconds के अंदर, errors 1% से कम। फिर first-token budget ऐसे बंटता है: auth 50 ms, query rewrite 300 ms, retrieval और reranking 400 ms, model first token 700 ms, और network और queueing के लिए 550 ms की slack।

**Load testing** system पर realistic traffic भेजता है, step by step बढ़ाते हुए, और response times, errors और resource use record करता है। ये बताता है कि किस load पर system टूटता है, और सबसे पहले क्या टूटता है, आपके users को पता चलने से पहले।

```flow
dir: LR
title: Latency budget: p95 first token 2 s में
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

तीन शब्द जो आपको चाहिए होंगे। **p95** वो time है जिससे 95% requests जल्दी पूरी होती हैं। **Time to first token** वो इंतज़ार है जब तक answer का पहला शब्द नहीं दिखता। **Concurrent users** का मतलब है एक ही पल में chat session में मौजूद लोग; उनमें से ज़्यादातर पढ़ रहे होते हैं या type कर रहे होते हैं, इसलिए एक साथ in flight requests बहुत कम होती हैं।

ये lesson Jaipur के एक intercity bus operator को follow करता है, जो festival-season traffic के लिए अपना booking assistant तैयार कर रहा है।

## ये कैसे काम करता है

### Averages नहीं, percentiles

1.5 seconds का average, 5% users के 4 से 9 seconds इंतज़ार को छुपा सकता है। Median (p50), p95 और p99 track करो। Tail जितनी दिखती है उससे ज़्यादा मायने रखती है: एक session में 20 messages भेजने वाले user को कम से कम एक reply p99 से धीमा मिलने का करीब 18% chance है (1 minus 0.99 की power 20)।

Experts के दो rules:

- **Percentiles जुड़ते नहीं।** Total का p95, हर step के p95 का जोड़ नहीं होता। धीमे steps एक ही request में कम ही एक साथ होते हैं, इसलिए जोड़ आम तौर पर total को ज़्यादा बताता है; लेकिन जब एक ही वजह, जैसे busy database, हर step को एक साथ धीमा कर दे, तो वो साथ-साथ चलते हैं। Step numbers को उस step के अपने p95 का target मानो, और end-to-end p95 सीधे traces से पढ़ो।
- **Percentiles का average नहीं निकलता।** मान लो तीन servers का p95 1.2 seconds है और एक का, जिसका median 3.5 seconds है, 6 seconds है, और हर एक traffic का एक चौथाई लेता है। चारों p95 का average 2.4 seconds है। लेकिन धीमे server की आधी requests 3.5 seconds से ज़्यादा लेती हैं, जो सारी requests का 12.5% है, इसलिए असली p95 3.5 seconds से ऊपर है। Percentiles सारी raw timings से, या merge किए हुए histograms से निकालो।

```python
import random

random.seed(7)
def p95(xs):
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]

# Four steps, each with its own spread of times in seconds
auth     = [random.lognormvariate(-3.5, 0.3) for _ in range(10_000)]
retrieve = [random.lognormvariate(-1.3, 0.4) for _ in range(10_000)]
rerank   = [random.lognormvariate(-1.8, 0.5) for _ in range(10_000)]
model    = [random.lognormvariate(-0.5, 0.35) for _ in range(10_000)]
total = [a + b + c + d for a, b, c, d in zip(auth, retrieve, rerank, model)]

print(f"sum of the step p95s: {p95(auth) + p95(retrieve) + p95(rerank) + p95(model):.2f} s")
print(f"p95 of the total:     {p95(total):.2f} s")
```

ये जोड़ के लिए 2.03 seconds और असली total के लिए 1.67 seconds print करता है, क्योंकि यहां steps independent हैं।

### AI requests को धीमा क्या करता है

**Generation time** मोटे तौर पर output tokens गुणा हर token का time है। 60 tokens per second पर, 450-token answer को stream होने में 7.5 seconds लगते हैं और 200-token answer को करीब 3.3 seconds। Answer की लंबाई cap करना अक्सर आपके पास सबसे सस्ता speed-up होता है।

**Time to first token** prompt की लंबाई के साथ, आपके अपने system में और provider के पास queueing के साथ, और उस घंटे provider के load के साथ बढ़ता है। Context trim करो और जहां provider support करे वहां cached prompt prefix reuse करो। Reasoning models कुछ भी दिखाने से पहले सोच सकते हैं, इसलिए वो पहला token नापो जो user को सच में दिखता है।

**Rate limits** tokens या requests per minute पर होती हैं, और आप कितने भी servers चलाओ, calls को 429 (Too Many Requests) के साथ reject कर देती हैं। देखो कि आपका provider input और output tokens कैसे गिनता है, peak पर कितना चाहिए इसका हिसाब लगाओ, और हफ्तों पहले ऊंची limit मांगो।

### Little's law से sizing

**Little's law**: requests in flight = arrival rate x हर request का system में बिताया time। मान लो pilot के logs दिखाते हैं कि हर active user मिनट में करीब 2 messages भेजता है। 500 users पर ये करीब 17 requests per second है। अगर हर एक 4.5 seconds लेती है, तो किसी भी पल करीब 75 answers stream हो रहे होते हैं। 500 नहीं, यही number आपके connection pools, worker counts और किसी भी concurrency cap का size तय करता है।

### Test design करना

असली behaviour को model करो: असली सवाल (masked), आम prompt और answer लंबाई, messages के बीच think time, और expected peak। कम से शुरू करके peak से आगे तक ramp करो और **हर step को hold करो** कुछ मिनटों के लिए, ताकि percentiles settle हो जाएं। p95 और p99, status code के हिसाब से errors, CPU, memory, database connections, queue की लंबाई और provider के 429s देखो।

**Closed और open tests।** **Closed** test में, जैसे think time वाले Locust users, हर simulated user reply आने तक रुककर फिर भेजता है। System धीमा होने पर test कम भेजता है, और धीमे दौर में जितने measurements आने चाहिए उससे कम आते हैं। इसे **coordinated omission** कहते हैं: test चुपचाप ठीक उसी वक्त पीछे हट जाता है जब असली users नहीं हटते। **Open** test में requests एक तय rate पर आती हैं, चाहे कुछ भी हो, जैसे sale खुलते ही travellers टूट पड़ते हैं। k6 ये अपने constant-arrival-rate और ramping-arrival-rate executors से देता है। Bottlenecks को step by step ढूंढने के लिए closed ramp use करो, फिर queue देखने के लिए expected arrival rate पर burst के साथ एक open test चलाओ।

**Soak test।** Expected peak को 30 से 60 मिनट तक hold करो। Memory, connections या file handles के leaks वक्त के साथ ही दिखते हैं।

### एक fake model server

Real-model load tests में पैसे लगते हैं और rate limits खत्म होती हैं। ज़्यादातर rounds एक छोटी fake service पर चलाओ, जिसका streaming shape provider की API जैसा ही हो और first-token delays आपके traces से sample किए गए हों:

```python
import asyncio, json, os, random
from fastapi import FastAPI
from fastapi.responses import JSONResponse, StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.30, 0.35, 0.35, 0.35, 0.40, 0.40, 0.40, 0.45, 0.45, 0.45, 0.45, 0.50, 0.50,
                 0.50, 0.50, 0.55, 0.55, 0.55, 0.60, 0.60, 0.60, 0.65, 0.70, 0.70, 1.40]
TOKENS_PER_S = 60
REPLY_TOKENS = 450                                    # today's typical answer length
SHARE_429 = float(os.getenv("FAKE_429_SHARE", "0"))   # for example 0.05

@app.post("/v1/messages")
async def messages():
    if random.random() < SHARE_429:
        return JSONResponse({"error": "rate_limited"}, status_code=429,
                            headers={"retry-after": "2"})
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for i in range(REPLY_TOKENS):
            yield f"data: {json.dumps({'text': f'tok{i} '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

ये delays model का p95 0.7 seconds देते हैं, जो budget में model का हिस्सा है, और 25 में से एक reply धीमा। इसे `uvicorn fake_model:app` से चलाओ, और सिर्फ test environment में configuration के ज़रिए अपने app का model base URL इस पर point करो। अपने retries और fallback test करने के लिए `FAKE_429_SHARE` set करो।

### Stream को time करने वाला Locust ramp

`stream=True` के साथ, request के लिए Locust की अपनी row response headers आते ही अपनी घड़ी रोक देती है, अक्सर कुछ milliseconds में, first token से बहुत पहले। इसलिए ये test अपनी दो timings खुद record करता है:

```python
import random, time
from locust import HttpUser, LoadTestShape, between, task

QUESTIONS = [q.strip() for q in open("load/questions.txt", encoding="utf-8") if q.strip()]

class Traveller(HttpUser):
    wait_time = between(20, 30)          # think time between messages

    @task
    def ask(self):
        start, first = time.perf_counter(), None
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
                return
            for line in r.iter_lines():               # read the whole stream
                if line and first is None:
                    first = time.perf_counter()
        end = time.perf_counter()
        if first is not None:
            self.record("first token", first - start)
        self.record("full answer", end - start)

    def record(self, name, seconds):
        self.environment.events.request.fire(
            request_type="STREAM", name=name, response_time=seconds * 1000,
            response_length=0, exception=None, context={})

class Ramp(LoadTestShape):
    # (end second, users): hold each step for two minutes
    steps = [(120, 50), (240, 100), (360, 200), (480, 300), (600, 400), (720, 500), (840, 550)]

    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10                      # add up to 10 users a second
        return None
```

इसे `locust -f load/locustfile.py --headless --host https://staging.example.in --csv results --csv-full-history` से चलाओ। फिर `results_stats_history.csv` file में हर name के लिए हर second एक row आती है, जिसमें user count और पिछले करीब 10 seconds के percentiles होते हैं। `first token` और `full answer` rows पढ़ो, और हर hold के आखिरी मिनट में 95% column का median लो, क्योंकि low load पर 10-second window में कम requests होती हैं। Traces से per-step p95 भी चलता है। Built-in POST row (सिर्फ headers) और Aggregated row को ignore करो, जो तीनों timings को मिला देती है।

### Overload, retries और streaming

- **Retry storms।** अगर हर 429 या timeout को तुरंत, तीन बार तक retry किया जाए, तो मुश्किल में पड़े system पर चार गुना तक traffic आ सकता है। Exponential backoff और random jitter के साथ retry करो, provider `retry-after` header भेजे तो उसे मानो, और retries को traffic के छोटे हिस्से पर cap करो।
- **Admission control।** हर instance एक साथ जितने streams serve करता है, उन्हें cap करो। Extra requests को एक छोटी queue में, ज़्यादा से ज़्यादा कुछ seconds, रुकने दो, फिर विनम्रता से "अभी हम busy हैं, कृपया एक मिनट बाद try करें" दिखाओ। सबका timeout होने से अच्छा है कुछ लोगों को लौटा देना।
- **Autoscaling और cold starts।** नए instances को start और warm up होने में मिनट लग सकते हैं। पहले से पता peak के लिए, उसके शुरू होने से पहले scale up करो।
- **Proxies से streaming।** कोई proxy या load balancer response को buffer कर सकता है, जिससे tokens एक ही ढेर में आते हैं, या idle समझकर connection बंद कर सकता है। Streaming route पर buffering और idle-timeout settings check करो।

| Load में लक्षण | संभावित वजह | Fix |
| --- | --- | --- |
| Latency बढ़ती है, CPU low | Database connections या locks का इंतज़ार | बड़ा pool, indexes, caching, कम queries |
| CPU 100% पर | बहुत कम workers या भारी parsing | ज़्यादा workers, काम background jobs में भेजो |
| 429 errors | Provider rate limit | ऊंची limit, fallback model, छोटे outputs |
| Errors शुरू होते ही traffic उछलता है | तुरंत retries | Jitter के साथ backoff, retry cap |
| Queue सिर्फ bursts में बढ़ती है | Arrival rate के लिए बहुत कम streams | Concurrency cap, busy message, जल्दी scale up |
| सिर्फ first token धीमा | लंबे prompts या provider queueing | Context trim करो, prefix cache करो |
| Tokens एक ढेर में आते हैं | कोई proxy stream को buffer कर रहा है | उस route पर buffering बंद करो |
| ठीक एक मिनट बाद errors | किसी layer में timeout या idle limit | हर layer में timeouts align करो |

### Traces खोलकर results पढ़ो

जब किसी step पर p95 उछले, तो उस मिनट के सबसे धीमे traces खोलो। जो step बढ़ा (database waits, reranker, model slot के लिए queueing) वही bottleneck है, और ऊपर की table आम तौर पर fix बता देती है। फिर वही test दोबारा चलाओ, ताकि बराबर की चीज़ों की तुलना हो।

## एक worked example

Jaipur का bus operator festival travel के दौरान एक साथ chat कर रहे करीब 500 travellers की उम्मीद करता है, और सुबह 10 बजे एक seat sale खुलती है। Budget: p95 first token 2 seconds से कम, p95 full answer 10 seconds से कम, errors 1% से कम। नीचे के सारे numbers illustrative हैं।

**Round 1: closed ramp, fake model।** p95 first token 50 users पर 1.1 seconds से 200 पर 6 seconds तक चढ़ता है। CPU 25% पर रहता है। सबसे धीमे traces सब database connection का इंतज़ार कर रहे हैं: pool में 10 ही हैं। 40 का pool और route table पर एक index इसे ठीक कर देते हैं।

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| p95 first token, pool 10 | 1.1 s | 2.4 s | 6.0 s | रोका: timeouts | नहीं चलाया | नहीं चलाया |
| p95 first token, pool 40 + index | 1.1 s | 1.1 s | 1.2 s | 1.2 s | 1.3 s | 1.4 s |

**Round 2: real model पर एक छोटा run।** दस मिनट, 300 users तक ramp, API account के owner से पहले ही तय करके। करीब 220 users पर 429 errors शुरू होते हैं। मोटा हिसाब भी यही कहता है: pilot के logs दिखाते हैं कि हर user मिनट में करीब 2,000 tokens (1,550 in, 450 out) के करीब 2 messages भेजता है, यानी हर user के 4,000 tokens per minute, और account के 900,000 tokens per minute 225 users पर खत्म हो जाते हैं। Team answers को 200 tokens पर cap करती है, जिससे streaming time 7.5 से करीब 3.3 seconds और हर message के tokens 1,750 हो जाते हैं। वो ऊंची limit मांगते हैं; दस दिन बाद provider 2.5 million tokens per minute दे देता है। वो अपने gateway से एक fallback model और retries पर jitter के साथ backoff भी जोड़ते हैं।

**Round 3: open burst test, fake model** (अब 200-token replies पर set)। Little's law: 500 users पर, करीब 17 requests per second, हर एक करीब 4.5 seconds की, यानी करीब 75 streams in flight। Sale खुलते ही arrivals करीब 25 per second तक उछलते हैं, यानी करीब 113 in flight। दो instances, हर एक 48 streams पर capped, 96 ही संभालते हैं। Burst में p95 first token 9 seconds तक पहुंचता है और 6% requests timeout हो जाती हैं। Closed ramp ने ये कभी नहीं दिखाया, क्योंकि उसके users बस इंतज़ार करते रहे। Fix: सुबह 9:45 बजे start किया गया तीसरा instance, और 3-second queue और busy message वाला admission control। Re-run पर p95 first token 1.5 seconds पर रहता है और किसी को लौटाया नहीं जाता।

**Round 4: confirm।** Real model पर 550 users के साथ दस मिनट: p95 first token 1.6 seconds, p95 full answer 5.2 seconds, errors 0.3%। ये load 1.9 million tokens per minute use करता है, limit का 77%। Fake model पर 500 users के साथ 45 मिनट का soak flat memory दिखाता है और कोई connection leak नहीं।

**Launch day।** Peak 480 travellers तक पहुंचता है। सुबह 10 बजे के burst में demand थोड़ी देर के लिए करीब 2.6 million tokens per minute मांगती है, limit से 5% ज़्यादा, और gateway दो मिनट के लिए कुछ percent requests fallback model पर भेजता है। p95 first token 2 seconds से नीचे रहता है।

**Report** में budget line के साथ users के मुकाबले p95 का chart है, हर मिला bottleneck और उसका fix, और अगली ceiling: करीब 700 steady users (2.5 million भाग 3,500 tokens per user per minute), और bursts में उससे पहले।

## आम गलतियां

- **Averages report करना।** First token और full answer के लिए p50, p95 और p99 report करो।
- **Percentiles जोड़ना या उनका average निकालना।** दोनों काम नहीं करते; raw timings से निकालो।
- **एक बार में एक ही request test करना।** Pools, locks और rate limits सिर्फ concurrency में fail होते हैं।
- **Unrealistic traffic।** एक जैसे छोटे prompts और बिना think time के numbers का कोई मतलब नहीं।
- **सिर्फ closed tests।** System धीमा होने पर वो पीछे हट जाते हैं, इसलिए असली rush से बनने वाली queue छुपा देते हैं।
- **Streams के लिए Locust की request row पर भरोसा।** Streaming on होने पर वो सिर्फ headers को time करती है।
- **Real-model load tests पर पैसे फूंकना।** ज़्यादातर rounds के लिए fake model use करो और एक छोटा real run।
- **Provider limits भूल जाना।** अक्सर असली ceiling वही होती हैं। Token का हिसाब लगाओ और जल्दी मांगो।
- **तुरंत retries।** ये ठीक उसी वक्त load कई गुना कर देते हैं जब system मुश्किल में होता है।

## कब पूरा load test रुक सकता है

- **गिने-चुने users वाले internal tools**: दस concurrent requests के साथ एक quick check काफी है।
- **Batch systems**, जहां per-user latency से ज़्यादा per hour throughput मायने रखता है; वही test करो।
- **ऐसे platforms पर early pilots जो आपके लिए scale करते हैं**, बशर्ते आपने rate limits और timeouts check कर लिए हों।

## Demo से production तक

- **Step के हिसाब से latency budget रखो** और हर release में traces को उससे compare करो।
- **Launch से पहले और बड़े बदलावों से पहले load-test करो**, ज़्यादातर fake model server के साथ।
- **हर ramp step के लिए p50, p95, p99 और errors report करो**, मिले bottleneck के साथ।
- **Traffic patterns बदलें तो दोबारा test करो**, जैसे exam season, festival sale या लंबे answers वाला नया feature।
- **Production में p95 first-token time और 429 rate पर alert लगाओ**, और tokens-per-minute headroom पर नज़र रखो।

## Practice

Monitoring पर Google SRE का chapter और Locust की first-test guide पढ़ो।

1. दस real requests के traces से अपने app के लिए step के हिसाब से latency budget लिखो। End-to-end p95 अलग से check करो।
2. ऊपर वाला fake model server चलाओ और अपने app को उस पर point करो।
3. Locust ramp को 50 से 550 users तक चलाओ। हर hold पर first token और full answer के p50, p95 और p99 record करो, और note करो कि p95 पहली बार आपका budget कहां पार करता है।
4. पहला bottleneck ढूंढकर ठीक करो, दोबारा चलाओ, फिर Little's law से अपने peak पर और उस rate के 1.5 गुना burst पर requests in flight का अंदाज़ा लगाओ।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly) का chapter 9, जो inference optimisation पर है, time to first token और time per output token को cover करता है।

**आपका काम पूरा है जब आप** अपनी budget line के साथ users के मुकाबले p95 का chart दिखा सको, पहला bottleneck और उसे हटाने वाला बदलाव बता सको, और बता सको कि आपके peak पर कितनी requests in flight हैं।
