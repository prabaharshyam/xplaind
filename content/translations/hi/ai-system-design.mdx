## ये क्या है

**AI system design** का मतलब है कागज़ पर तय करना कि कोई AI product किन चीज़ों से बना है, और numbers से साबित करना कि वो चलेगा। अच्छा design छह सवालों के जवाब देता है: parts क्या हैं, हर arrow से कौन-सा data गुज़रता है, एक request का cost कितना है, user कितना इंतज़ार करता है, क्या टूटता है और हमें कैसे पता चलेगा, और quality कैसे measure करेंगे?

"Design interview" lesson में एक design को घड़ी के दबाव में present करने की बात है; ये lesson बताता है कि उसमें क्या होना चाहिए।

जो product documents से जवाब देता है, उसकी दो pipelines होती हैं: **ingestion** offline चलती है और documents को एक index में बदलती है; **request path** हर सवाल पर चलता है। ज़्यादातर quality problems ingestion में शुरू होती हैं, इसलिए दोनों बनाओ।

```flow
title: Underwriting assistant, request path
Underwriter का सवाल -> API service | login, department, हर user की cap
API service -> Input checks | personal data mask करना, injection flag करना
Input checks -> Query rewrite | small model
Query rewrite -> Hybrid search | department और effective-date filters
Hybrid search -[top 40]-> Reranker
Reranker -[top 6]-> Main model | सिर्फ़ passages से जवाब, citations के साथ
Main model -[outage]-> Fallback model
Main model -> Citation check
Fallback model -> Citation check
Citation check -[pass]-> Clauses के links के साथ जवाब
Citation check -[fail]-> जवाब से इनकार, senior underwriter को route
```

```flow
dir: LR
title: Ingestion pipeline, हर रात
नई wordings और circulars -> Parser and OCR | tables को tables ही रखता है -> Chunker | section path के साथ 400 tokens -> Embeddings and keyword index -> Index | version, effective date, department
```

ये lesson एक ही design को follow करता है: Mumbai की एक general insurer में 300 underwriters के लिए एक assistant, जो 2,000 policy wordings, circulars और guidelines से जवाब देता है। सारे volumes, token counts और timings इसी design की assumptions हैं, किसी असली insurer के measurements नहीं।

## ये काम कैसे करता है

### User और constraints से शुरू करो

Goal को एक baseline वाले metric की तरह लिखो: "किसी policy सवाल का जवाब ढूँढने का median time, 6 minutes से 2 से कम।" फिर वो constraints लिखो जो किसी box या number को बदलते हैं।

- **जवाब कौन पढ़ता है, और गलत जवाब की कीमत क्या है?** एक trained underwriter, पर एक गलत exclusion किसी policy की गलत pricing करवा सकता है। इसलिए हर जवाब एक clause cite करता है।
- **Volume और peaks।** 300 users, हर एक हर working day लगभग 25 सवाल, ज़्यादातर 8 busy hours के अंदर।
- **Data rules।** Documents, index और logs India में ही रहते हैं। Model calls India के बाहर process हो सकती हैं या नहीं, ये compliance team तय करेगी, और वही फ़ैसला तय करेगा कि provider को सीधे call करना है या किसी cloud provider का regional endpoint लेना है, अगर India में कोई endpoint चुना हुआ model देता हो। पहले हफ़्ते में ही पूछो।
- **Access।** Motor underwriters को health reinsurance treaties नहीं दिखनी चाहिए, और यही rule search का ढाँचा तय करता है।

### वो decisions जो हर design को बताने होते हैं

Boxes की list design नहीं होती। बड़े choices और हर एक की वजह बताओ।

| Decision | इस design का choice | इसे कब बदलो |
| --- | --- | --- |
| सिर्फ़ prompt, retrieval या fine-tuning | Retrieval: documents हर महीने बदलते हैं और जवाबों को citations चाहिए | ज़रूरत knowledge की नहीं, volume पर format या style की हो ("Prompting, RAG या fine-tuning" देखो) |
| Long context या retrieval | Retrieval: लगभग 25 million tokens के documents, 1-million-token window के सामने | Corpus छोटा और स्थिर हो, और caching उसे सस्ता रखे |
| Model tier | जवाबों के लिए mid-sized model; query rewriting के लिए small model | Small model किसी पूरी category के लिए launch bar पार कर ले |
| Hosted API या self-hosted open weights | Hosted, region compliance तय करेगी | Data आपके servers से बाहर न जा सके, या स्थिर volume GPUs को busy रखे |
| Vector store | Vector extension के साथ Postgres | Index एक machine से बड़ा हो जाए |
| Streamed या batch | Streamed: कोई इंसान इंतज़ार कर रहा है | कोई इंतज़ार नहीं कर रहा: batch API आधे cost पर |

Database चुनने से पहले index का size निकालो। मान लो 2,000 documents, औसतन 25 pages, हर page लगभग 500 tokens: 25 million tokens, यानी 400 tokens के 62,500 chunks। हर embedding में 1,024 numbers और हर number 4 bytes का, तो लगभग 256 MB vectors, जो एक आम server की memory में आ जाते हैं। Distributed vector database बिना किसी फ़ायदे के cost बढ़ाएगा।

### एक request trace करो, हर step के data के साथ

हर step क्या लेता है और आगे क्या भेजता है, ये लिखो; privacy और cost की problems यहीं दिखती हैं।

1. **API service।** सवाल, user id और department लेता है; जो users अपनी daily cap पार कर चुके हैं उन्हें reject करता है।
2. **Input checks।** Log करने से पहले policy और phone numbers mask करता है; जो text model को instructions देने की कोशिश करे उसे flag करता है।
3. **Query rewrite।** एक small model "does the fire one cover riots" जैसे सवाल को policy name वाली query में बदलता है: लगभग 300 tokens अंदर, 40 बाहर।
4. **Hybrid search।** Keyword और vector search parallel में चलते हैं, department और effective date से filter होकर। Keyword search policy codes और clause numbers पकड़ता है, यानी वो exact strings जो embeddings अक्सर miss कर देते हैं।
5. **Reranker।** Top 40 candidates को score करता है और 6 रखता है।
6. **Main model।** लगभग 1,500 tokens के fixed instructions लेता है (हर call पर एक जैसे, इसलिए cached) और 2,700 नए tokens: 400 tokens के छह passages और सवाल। ये लगभग 350 tokens लिखता है।
7. **Citation check।** सादा code: हर cited clause id भेजे गए passages में होनी चाहिए, वरना जवाब refuse होकर किसी इंसान के पास route होता है।

Access control step 4 में रहता है। जवाब के बाद filter करोगे तो model वो text पहले ही पढ़ चुका होगा जो user को नहीं दिखना चाहिए।

### Boxes से पहले numbers: load, limits और cost

```python
# Anthropic list prices, US dollars per million tokens, checked 28 November 2026
SONNET = {"in": 2.00, "cache_read": 0.10, "out": 10.00}   # Claude Sonnet 5.5
HAIKU = {"in": 0.10, "out": 0.50}                          # Claude Haiku 5.5, prompts up to 100,000 tokens

def estimate(users=300, questions_per_user=25, work_days=22, busy_hours=8, peak_factor=2.5,
             cached_in=1_500, fresh_in=2_700, out=350,   # main model, tokens per question
             rewrite_in=300, rewrite_out=40,             # small model rewrites the query
             usd_to_inr=94, fixed_inr_month=60_000):     # suppose: search, hosting, tracing
    daily = users * questions_per_user
    peak_per_min = daily / (busy_hours * 60) * peak_factor
    usd = ((fresh_in * SONNET["in"] + cached_in * SONNET["cache_read"] + out * SONNET["out"])
           + (rewrite_in * HAIKU["in"] + rewrite_out * HAIKU["out"])) / 1e6
    month_inr = daily * work_days * usd * usd_to_inr + fixed_inr_month
    return {
        "peak questions a minute": round(peak_per_min),
        "peak uncached input tokens a minute": round(peak_per_min * fresh_in),
        "peak output tokens a minute": round(peak_per_min * out),
        "model cost per question (rupees)": round(usd * usd_to_inr, 2),
        "model spend a month (US dollars)": round(daily * work_days * usd),
        "total a month (rupees)": round(month_inr),
        "per user a month (rupees)": round(month_inr / users),
    }

print(estimate())
# {'peak questions a minute': 39, 'peak uncached input tokens a minute': 105469,
#  'peak output tokens a minute': 13672, 'model cost per question (rupees)': 0.86,
#  'model spend a month (US dollars)': 1502, 'total a month (rupees)': 201141,
#  'per user a month (rupees)': 670}
```

₹94 का एक dollar और ₹60,000 के fixed costs सिर्फ़ उदाहरण के लिए हैं। इसे published limits से मिलाओ। Claude API पर, November 2026 तक, सबसे निचला standard tier (Start) Sonnet 5.5 के लिए एक minute में 2,000,000 input tokens और 400,000 output tokens देता है। Cache reads input limit में नहीं गिने जाते। तो peak load उसका लगभग 5% ही use करता है: rate limit problem नहीं है।

Problem monthly bill है। हर tier का एक monthly spend cap भी है: Start का $500, Build का $1,000 और Scale का $200,000। लगभग $1,500 महीने पर ये design दोनों निचले tiers में से किसी पर भी महीने के बीच में रुक जाएगा, ऐसी errors के साथ जिन्हें retries ठीक नहीं कर सकते। Design को tier या cloud contract का नाम बताना होगा और cap से नीचे एक budget alert लगाना होगा। Cloud platforms अपने quotas खुद तय करते हैं, और Anthropic के pricing page के मुताबिक उनके regional और multi-region endpoints global वालों से 10% महँगे हैं, इसलिए compliance जो route चुने उसके लिए हिसाब फिर से करो।

Fresh input सबसे बड़ा cost है: हर सवाल के $0.0091 में से $0.0054 (2,700 tokens, $2 प्रति million पर)। 6 की जगह 4 passages भेजने से लगभग 18% बचता है, अगर eval set पर recall बना रहे। Cache writes छोड़े गए हैं: इस traffic पर cached prefix कभी-कभार ही expire होता है। Fixed costs total का 30% हैं, इसलिए usage बढ़ने के साथ प्रति user cost घटता है।

### एक latency budget, step by step

Underwriters जवाब stream होते-होते पढ़ते हैं, इसलिए target है: 100 में से 95 सवालों (p95) पर पहला text 2 seconds से कम में दिखे।

| Step | Allowance (p95) |
| --- | --- |
| Login, cap और input checks | 50 ms |
| Query rewrite, small model | 300 ms |
| Hybrid search, keyword और vector parallel में | 150 ms |
| 40 candidates की reranking | 200 ms |
| Main model, पहले token तक का समय | 1,000 ms |
| Total, लगभग 300 ms बचाकर | 1.7 s |

p95s को जोड़ने से असली p95 ज़्यादा दिखता है, क्योंकि सारे steps शायद ही कभी एक साथ धीमे होते हैं, इसलिए ये budget safe है, exact नहीं। अगर model, मान लो, एक second में 60 tokens stream करे, तो 350-token जवाब को लगभग 6 seconds और लगेंगे। जब total फिसले, तो trace दिखाता है कि किस step ने अपना allowance तोड़ा। सबसे पहले काटने वाला step query rewrite है।

### Failure modes, उन्हें कैसे पकड़ें, और guard

Failure row तभी काम की है जब किसी को failure का पता चले, इसलिए हर row में एक detection signal दो।

| Component | क्या गलत होता है | आपको कैसे पता चलेगा | Guard |
| --- | --- | --- | --- |
| Parsing | Scanned tables उलझा हुआ text बन जाती हैं | हर document का parse score | Table extraction; flagged pages indexing से पहले check |
| Index | पुराना पड़ चुका (superseded) circular पहले नंबर पर आता है | Eval set के dated trap questions fail होते हैं | Effective-date filter; पुराने versions रखे जाते हैं पर marked |
| Search | सही clause छूट जाता है | Eval set पर recall at 5, हर हफ़्ते track | Hybrid search, reranker, query rewrite |
| Access | कोई user दूसरे department की treaty देख लेता है | हर department के एक user के साथ CI test | Search के अंदर permission filter |
| Model | ऐसा claim जिसे passages support नहीं करते | Citation check failures; sampled traffic पर judge score | सिर्फ़ passages से जवाब, वरना refuse |
| Documents | Upload हुई file में छिपे instructions | Traces में injection flags | कोई write tools नहीं; passages को instructions नहीं, data के रूप में mark किया जाता है |
| Provider | Outage, rate limit या ramp limit errors (429) | Error rate और fallback share | Backoff के साथ retries, fallback model, साफ़ message |
| Cost | Usage बेकाबू हो जाता है | Budget के सामने daily spend | हर user की caps, budget के 80% पर एक alert |

### Human review: कहाँ, और कितना

लोगों को वहाँ रखो जहाँ model सबसे कमज़ोर है और गलतियाँ सबसे महँगी हैं। यहाँ, refused और कम score वाले जवाब एक senior underwriter के पास जाते हैं, नए circulars indexing से पहले check होते हैं, और हर महीने 30 जवाब sample किए जाते हैं।

फिर उसका size निकालो। रोज़ 7,500 सवालों में से अगर 4% route हों, तो 300 reviews। हर एक पर 3 minutes, यानी रोज़ 15 घंटे, लगभग दो full-time reviewers। अगर client इतने लोग नहीं लगा सकता, तो retrieval ठीक करो या कम तरह के सवाल route करो। जिस queue पर कोई बैठा नहीं, वो guard नहीं है।

### Evaluation और launch bar

Test set असली सवालों से, category के हिसाब से बनाओ, जैसे 60 single-document सवाल, 25 जिनमें दो documents चाहिए, 15 superseded-circular traps, और 20 जो documents cover नहीं करते, जिन्हें refuse होना ही चाहिए। Retrieval measure करो (recall at 5: क्या सही clause top five में है?) और जवाब भी (सही और cited, एक model judge से score, जिसे underwriter labels से check किया गया हो)।

जानो कि एक छोटा set क्या दिखा सकता है: 120 सवालों पर 85% सही का 95% margin दोनों तरफ़ लगभग 6 points है। तो दो models के बीच 2-point का फ़र्क noise है। और 20 में से 20 refusals के बाद भी असली failure rate लगभग 15% हो सकता है। असली traffic आने के साथ traps बढ़ाओ। हर prompt या model change पर CI में fast checks चलाओ: 120 सवाल, लगभग ₹0.86 हर एक, यानी लगभग ₹100 एक run, ऊपर से judge।

### Document को ज़िंदा रखो

इसे repository में Markdown के रूप में रखो, pull requests में review करो, और आखिर में open questions और एक decision log हो: date, decision, options, reason, किसने माना। जैसे: "2026-11-02: reranker के साथ hybrid search। Vector-only search policy codes miss कर रहा था (recall at 5: eval set पर 71% बनाम 89%)। Client IT के साथ तय।" पहले हफ़्ते में ही किसी compliance reviewer को इसे समझा दो, जब "ये कहाँ store होता है?" का जवाब देना अभी सस्ता है।

## एक example से समझो

Insurer के design document का पहला page:

| Section | Content |
| --- | --- |
| Goal | 300 underwriters के लिए median lookup time 6 minutes से 2 से कम |
| Launch bar | 120 सवालों पर कम से कम 85% सही और cited; सभी 20 out-of-scope सवाल refuse; recall at 5 कम से कम 85% |
| Load and cost | रोज़ 7,500 सवाल, peak पर 39 एक minute में; हर सवाल पर ₹0.86 model cost; लगभग ₹2 lakh महीना, ₹670 प्रति user, prices 28 November 2026 को check |
| Latency | p95 पर पहला text 2 s से कम; पूरा जवाब लगभग 8 s में |
| Components | OCR और table extraction के साथ nightly ingestion; department और date filters के साथ hybrid search; reranker; tested fallback के साथ mid-sized model; citation check |
| Human review | लगभग 4% सवाल senior underwriters को, लगभग दो reviewers का समय; हर महीने 30 जवाब sample |
| Open questions | क्या model calls India से बाहर जा सकती हैं? लगभग $1,500 महीने को कौन-सा API tier या cloud contract cover करेगा? |

किसी भी code से पहले numbers ने क्या बदला:

1. **Spend cap।** Bill दो tiers के monthly caps से ऊपर है, इसलिए तीसरे हफ़्ते में service रुकने की जगह, contract का फ़ैसला plan में आ गया।
2. **Review queue।** Client ने "कभी-कभार" review मान रखा था; दो लोगों के घंटे देखकर उन्होंने retrieval के काम और एक rota के लिए पैसे दिए।
3. **Vector store।** 256 MB vectors insurer के मौजूदा Postgres में आ जाते हैं: review करने के लिए एक vendor कम।
4. **Compliance का सवाल।** पहले हफ़्ते में उठाया गया, इसलिए gateway बनने से पहले model route तय हो गया।

अब इसे एक बदलाव से test करो। मान लो अगले साल 2,700 claims staff जुड़ते हैं। दस गुना users का मतलब peak पर लगभग 390 सवाल एक minute में और लगभग 1.05 million uncached input tokens एक minute में: अब भी Start tier की input limit से नीचे, पर लगभग $15,000 महीना। प्रति user cost लगभग ₹490 पर आ जाता है, क्योंकि fixed costs बँट जाते हैं। सबसे पहले review queue टूटती है: 75,000 का 4% यानी रोज़ 3,000 reviews, इसलिए पहले route होने वाला हिस्सा घटाना होगा।

## आम गलतियाँ

- **बिना numbers के boxes।** लक्षण: किसी box का न owner है, न latency allowance, न failure row, इसलिए reviewers उसे challenge नहीं कर सकते।
- **सिर्फ़ request path बनाना।** लक्षण: न parsing, न versions, न effective dates, जब तक कोई पुराना circular user तक न पहुँच जाए।
- **Rate limit check करना पर spend cap नहीं।** लक्षण: "हम tokens-per-minute limit से काफ़ी नीचे हैं", पर न monthly bill, न price check date।
- **Generation के बाद access filter करना।** लक्षण: "UI restricted जवाब छिपा देता है"। Model restricted text पहले ही पढ़ चुका है।
- **Detection column के बिना failure table।** लक्षण: ऐसी failures के guards जिन्हें कोई नोटिस ही नहीं करेगा।
- **बिना size की human review।** लक्षण: "uncertain जवाब किसी इंसान के पास जाते हैं", पर न हिस्सा, न minutes, न team।
- **छोटे eval set पर भरोसा।** लक्षण: 120 सवालों पर 2-point की बढ़त से model चुनना, या 20 में से 20 refusals को सबूत मानना।
- **लंबा document जिसे कोई नहीं पढ़ता।** दो से चार pages, summary table पहले।

## कब पूरा design document ज़रूरत से ज़्यादा है

- **एक हफ़्ते का prototype:** आधा page, जिसमें goal, data, success measure और प्रति request मोटा cost हो।
- **एक छोटा internal tool**, जिसके users कम हों और कोई sensitive data न हो।
- **किसी मौजूदा system के अंदर बदलाव:** उसकी जगह उसका document और decision log update करो।

## Demo से production तक

- जब भी traffic, models, token counts या prices बदलें, **estimate फिर से चलाओ**, और prices पर date डालो।
- हर हफ़्ते **traces को latency budget से मिलाओ**।
- **हर detection signal को dashboard पर रखो**, fallback use, spend और refusal rate के alerts के साथ।
- **हर incident के बाद एक failure row जोड़ो।**
- **हर महीने human review का size फिर से निकालो।**

## Practice करो

नीचे linked, LLM-based systems के लिए Eugene Yan के patterns पढ़ो। गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 10 AI application architecture को layer by layer cover करता है, और chapter 9 latency और cost को।

इस lesson का check एक project है: अपनी पसंद के किसी AI product के लिए दो से चार page का design document। ये सातों हों तो pass:

1. Baseline के साथ एक success metric।
2. Peak-load और cost-per-user estimate, उसकी assumptions और prices check करने की date के साथ।
3. हर component से trace की गई एक request, हर step के data के साथ।
4. हर step के allowance वाला latency budget।
5. कम से कम छह rows की failure table, हर row में एक detection signal और एक guard।
6. Category के हिसाब से test set, launch bar के साथ।
7. Open questions और एक छोटा decision log।

फिर worked example की तरह किसी एक assumption को दस से गुणा करो, और लिखो कि सबसे पहले क्या टूटता है।

**आपका काम पूरा है जब आप** किसी को दस minutes में अपना design समझा सको और हर component के लिए जवाब दे सको: "इसका cost क्या है, ये कितना धीमा हो सकता है, और fail होने पर क्या होता है?"
