## ये क्या है

कई भारतीय businesses अब भी ऐसे software पर चलते हैं जो किसी और से बात ही नहीं कर सकता: 15 साल पुराना desktop ERP, bank की back-office screens, बिना API वाला सरकारी portal। लोग अपने दिन एक screen से दूसरी screen में values कॉपी करने में बिताते हैं। **Robotic process automation (RPA)** वो copying अपने हाथ में ले लेता है।

RPA ऐसे software "robots" use करता है जो applications को उनके **user interface** से चलाते हैं, ठीक किसी इंसान की तरह: programs खोलना, buttons पर click करना, fields में type करना, screens से values कॉपी करना, reports download करना। इसे वहाँ use किया जाता है जहाँ systems में API नहीं है, या integration बनाने में बहुत समय लगेगा।

```flow
dir: LR
title: API automation: तेज़, मज़बूत, पहली पसंद
System A, API वाला -[data, सीधे]-> System B, API वाला
```

```flow
dir: LR
title: RPA: वहाँ भी चलता है जहाँ इंसान चल सकता है, ज़्यादा नाज़ुक
Robot | UiPath, Power Automate Desktop -[screen पर click और typing]-> पुराना desktop app, बिना API
```

मुख्य RPA tools में **UiPath**, **Automation Anywhere** और **Microsoft Power Automate Desktop** आते हैं। इनमें आप steps record या design करते हो, फिर उन्हें schedule पर या जब चाहो तब, desktop या server पर चलाते हो।

इस lesson में हम Kolkata के एक general insurer की claims team के साथ चलेंगे, जब एक AI step और एक RPA robot मिलकर एक पुराने claims system में data entry संभाल लेते हैं। अंत तक आप जान जाओगे कि RPA कब सही tool है और इसे चालू रखने में कितना खर्च आता है।

## ये काम कैसे करता है

### Attended और unattended robots

| Type | कब चलता है | Example |
| --- | --- | --- |
| **Attended** | किसी इंसान के computer पर, जब वो शुरू करे | एक robot जो agent के "Go" दबाने के बाद 40 fields वाला form भर देता है |
| **Unattended** | अपने आप, dedicated machines पर, queue के काम निपटाते हुए | एक robot जो रात भर में 300 claims enter करता है |

### Robots screen पर चीज़ें कैसे ढूँढते हैं

अच्छा RPA screen की fixed positions पर click नहीं करता। वो elements को उनकी properties से पहचानता है: button का नाम, field का label, web page की structure। इन identifiers को **selectors** कहते हैं। तब layout के छोटे बदलाव robot को नहीं तोड़ते।

पुरानी applications या remote desktops में, जहाँ properties नहीं मिलतीं, robots **image matching** या **OCR** पर लौट सकते हैं, जो ज़्यादा नाज़ुक हैं: रंग या font बदलने से वो टूट सकते हैं।

### RPA कहाँ फ़िट होता है

- Legacy desktop applications, जैसे पुराने ERPs और banking back-office screens, और बिना API वाले portals।
- High-volume, stable, rule-based काम: systems के बीच data कॉपी करना, रोज़ के reports बनाना और download करना, orders enter करना।
- एक पुल की तरह, जब तक proper integration बन रहा हो।

### RPA कहाँ फ़िट नहीं होता

| स्थिति | बेहतर चुनाव |
| --- | --- |
| System में अच्छी API है | API use करो: तेज़ और मज़बूत |
| Process या screens अक्सर बदलती हैं | पहले process ठीक करो, या रुको |
| काम में अलग-अलग inputs पर judgement चाहिए | एक AI step और एक इंसान, RPA सिर्फ़ data entry के लिए |

### RPA के साथ AI

RPA data को screens से गुज़ारता है; AI documents पढ़ता है, emails classify करता है या अगला step तय करता है। साथ मिलकर वो ऐसे processes संभालते हैं जो कोई अकेला नहीं संभाल सकता:

```flow
Claim वाला email -> AI step | email और attachment पढ़ो; policy no., vehicle no., तारीख़, जगह निकालो
AI step -> Policy database से validate करो
Policy database से validate करो -[ठीक]-> RPA robot | उसे पुराने claims system में type करता है
Policy database से validate करो -[ठीक नहीं]-> इंसान की queue | screenshots के साथ
RPA robot -> Claim number वापस tracking sheet में
```

**Computer-use agents**, यानी AI जो screenshots से screens चलाता है, नए और ज़्यादा flexible हैं, पर design किए हुए RPA steps से धीमे, महँगे और कम predictable हैं। एक आम pattern: stable steps के लिए RPA, और AI सिर्फ़ वहाँ जहाँ variation में judgement चाहिए।

### Running cost और governance

Screens बदलने, passwords expire होने या अचानक pop-ups आने पर robots टूट जाते हैं। इनके लिए budget रखो:

- RPA platform और robot machines के **licences**;
- **monitoring**, ताकि रुके हुए robot पर alert आए;
- **maintenance**, यानी कोई जो selectors जल्दी ठीक कर सके।

हर robot का एक register रखो: उसका owner, वो किन systems को छूता है और कौन-से credentials use करता है। Robots को **least-privilege** accounts दो, जिनमें सिर्फ़ उतना access हो जितना चाहिए, और उनके passwords एक vault में रखो, robot की script में नहीं।

## एक example से समझो

Kolkata के एक general insurer को email पर motor claim intimations मिलते हैं: रोज़ लगभग 300। Claims team हर email और उसके attachments से details एक पुराने desktop claims system में कॉपी करती है जिसमें API नहीं है। हर claim में लगभग 6 मिनट लगते हैं, यानी पूरी team का रोज़ का लगभग 30 घंटे का काम।

**हल:**

1. एक **AI extraction step** हर intimation email और attachment पढ़ता है और structured fields बनाता है: policy number, vehicle number, नुकसान की तारीख़ और जगह, description।
2. Fields को policy database से **validate** किया जाता है: क्या policy मौजूद है, active है, और vehicle मेल खाता है?
3. एक **unattended RPA robot** claims system खोलता है, "New intimation" पर जाता है, validated fields भरता है, save करता है, और नया claim number tracking sheet में वापस लिख देता है।
4. जो validations fail हों, और कोई भी screen जिसे robot पहचान न पाए, screenshots के साथ **किसी इंसान की queue** में जाती है।

**पहली तिमाही के results:**

| Measure | पहले | बाद में |
| --- | --- | --- |
| Data entry पर staff का समय | रोज़ लगभग 30 घंटे | रोज़ लगभग 6 घंटे, ज़्यादातर exceptions |
| उसी दिन enter हुए claims | लगभग 70% | लगभग 98% |
| Robot outages | लागू नहीं | 2, दोनों system updates के बाद fields हिलने से |
| हर outage ठीक करने का समय | लागू नहीं | एक दिन से कम; monitoring ने RPA developer को alert किया |

Insurer की योजना है कि अगले साल जब claims system upgrade हो, तो robot की जगह सीधा API integration लगा दिया जाए। तब तक robot ही पुल है।

## आम गलतियाँ

- **जहाँ API है वहाँ RPA।** APIs तेज़ और मज़बूत होती हैं।
- **Screen की fixed positions।** Element properties use करो ताकि छोटे बदलाव robots को न तोड़ें।
- **अस्थिर processes को automate करना।** Process या screens बदलते ही robots टूट जाते हैं।
- **न monitoring, न कोई owner।** टूटे robots चुपचाप fail होते हैं, और काम बिना दिखे जमा होता जाता है।
- **Admin credentials वाले robots।** Vault में रखे least-privilege accounts use करो।
- **Exits को भूल जाना।** पहले से तय करो कि कौन-से cases किसी इंसान के पास जाएँगे, और उस queue को चलाना आसान बनाओ।

## Practice करो

नीचे link किया UiPath Academy का free beginner course करो, या Microsoft Learn पर Power Automate Desktop के modules।

1. **Build करो।** एक simple robot बनाओ जो कोई website या desktop app खोले, spreadsheet की एक row से form भरे और confirmation save करे।
2. **उसे तोड़ो।** Layout थोड़ा बदलो, window का size बदलकर या screen resolution बदलकर, और देखो कि वो अब भी चलता है या नहीं। बेहतर selectors से ठीक करो।
3. **चुनो।** अपने organisation के किसी एक process के लिए लिखो कि RPA, API integration या AI agent में से कौन सबसे सही बैठता है, और क्यों।

**आपका काम पूरा जब:** आप समझा सको कि API या AI agent की जगह RPA कब चुनोगे, और एक ऐसा robot दिखा सको जो layout के छोटे बदलाव से टूटे नहीं।
