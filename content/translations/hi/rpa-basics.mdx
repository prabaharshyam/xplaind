## ये क्या है

भारत के बहुत सारे businesses आज भी ऐसे software पर चलते हैं जो किसी और चीज़ से बात ही नहीं कर सकता: 15 साल पुराना कोई desktop ERP, किसी bank की back-office screens, बिना API वाला कोई government portal. लोग पूरा दिन एक screen से दूसरी screen में values copy करते रहते हैं। **Robotic process automation (RPA)** ये copy वाला काम अपने हाथ में ले लेता है।

RPA software "robots" use करता है जो applications को उनके **user interface** से चलाते हैं, जैसे कोई इंसान चलाए: programs खोलना, buttons click करना, fields में type करना, screens से values पढ़ना और reports download करना। ये उन systems का tool है जिनमें API नहीं है, या जहाँ integration बनाने में बहुत ज़्यादा time लगेगा।

असली बात ये है: API software के लिए बना दरवाज़ा है, जबकि RPA में software उस दरवाज़े से चलता है जो इंसानों के लिए बना था। वो दरवाज़ा कभी robots के लिए design ही नहीं हुआ। किसी button का नाम बदल गया, कोई screen slow है या अचानक कोई pop-up आ गया, तो robot रुक सकता है। इसलिए RPA powerful है पर नाज़ुक भी, और ज़्यादातर skill इसी नाज़ुकपन को संभालने में है।

```flow
dir: LR
title: API automation: तेज़, मज़बूत, पहली पसंद
System A, API है -[data, सीधे]-> System B, API है
```

```flow
dir: LR
title: RPA: जहाँ इंसान काम कर सके वहाँ चलता है, पर ज़्यादा नाज़ुक
Robot | UiPath, Power Automate Desktop -[screen पर clicks और typing]-> पुराना desktop app, API नहीं
```

बड़े RPA tools में **UiPath**, **Automation Anywhere** और **Microsoft Power Automate Desktop** हैं। Steps एक studio app में design करते हो, फिर उन्हें schedule पर या ज़रूरत पड़ने पर, desktop या server पर चलाते हो। Power Automate for desktop Windows 11 के साथ बिना extra cost के आता है, इसलिए practice के लिए ये आसान जगह है, हालाँकि flows को unattended चलाने या cloud से trigger करने के लिए paid licence चाहिए।

ये lesson Kolkata के एक general insurer की claims team के साथ चलता है, जहाँ एक पुराने claims system में data entry का काम एक AI step और एक RPA robot संभाल लेते हैं। आखिर तक आपको पता होगा कि RPA कब सही tool है, ऐसा robot कैसे बनाएँ जो duplicates न बनाए या चुपचाप fail न हो, और कैसे check करें कि वो अपना खर्च निकालता है या नहीं।

## ये काम कैसे करता है

### Attended और unattended robots

| Type | कहाँ और कब चलता है | Example |
| --- | --- | --- |
| **Attended** | किसी इंसान के computer पर, जब वो इंसान उसे start करे | एक robot जो agent के "Go" click करते ही 40 fields वाला form भर देता है |
| **Unattended** | अपने आप, अलग machines पर, queue से items लेकर | एक robot जो रात भर में 300 claims डाल देता है |

Attended robots एक इंसान को तेज़ काम करने में मदद करते हैं; हर run पर कोई इंसान नज़र रखता है। Unattended robots पूरी एक shift का काम संभाल लेते हैं, और उन्हें कोई नहीं देखता। नीचे दिया हर design rule सबसे ज़्यादा unattended robots के लिए मायने रखता है।

### Production model: queue, orchestrator, robot

Demo robot spreadsheet की rows पर loop चलाता है। Production robot एक **queue** से काम करता है। हर काम, जैसे एक claim email, एक **queue item** बन जाता है जिसमें उसका data और एक status होता है, जैसे new, in progress, successful या failed. एक **orchestrator**, यानी RPA platform का control centre (UiPath इसे Orchestrator कहता है), queues रखता है, schedules पर robots start करता है, credentials store करता है और logs रखता है।

Queues तीन ऐसी चीज़ें देती हैं जो spreadsheet loop नहीं देता। कई robots काम बाँट सकते हैं। Crash होने पर सिर्फ़ वो item जाता है जो चल रहा था, पूरा batch नहीं। और business एक नज़र में देख सकता है कि कितने items इंतज़ार में हैं, हो गए या अटके हैं।

### Business और system exceptions

चीज़ें दो बिल्कुल अलग तरीकों से गड़बड़ होती हैं, और robot को इन्हें अलग पहचानना आना चाहिए।

| | Business exception | System exception |
| --- | --- | --- |
| **क्या हुआ** | Data किसी rule को तोड़ता है: policy expire हो गई, GSTIN match नहीं हुआ, कोई ज़रूरी field खाली है | कुछ technical fail हुआ: app crash हुआ, screen time out हुई, network चला गया |
| **क्या retry से मदद मिलेगी?** | नहीं। अगली बार भी data उतना ही गलत होगा | अक्सर हाँ। वही item दूसरी कोशिश में अक्सर चल जाता है |
| **क्या करें** | Item को failed mark करो और वजह के साथ किसी इंसान को भेजो | App बंद करके restart करो, फिर retry, किसी limit तक, जैसे तीन बार |

Classic गलती है सब कुछ retry करना। Business exception को तीन बार retry किया तो तीन runs बर्बाद, और आखिर में फिर भी इंसान के पास जाएगा। System exception को सीधे इंसान के पास भेजा तो वो manual काम बन गया जो एक restart से निपट जाता। UiPath के REFramework जैसे templates में ये बँटवारा पहले से बना होता है। Tools की exact retry settings अलग-अलग होती हैं, इसलिए अपने version की documentation check करो।

### Retries और duplicates: idempotency

RPA की सबसे खतरनाक failure retries से ही आती है। सोचो: robot एक claim type करता है, Save click करता है, और पुराना app दो मिनट के लिए freeze हो जाता है। Robot time out होकर system exception report करता है। Queue उस item को retry करती है। लेकिन पहला Save असल में हो चुका था। Retry claim को दूसरी बार डाल देता है, और अब insurer के पास एक accident के दो claims हैं।

इसका fix है **idempotency**: किसी item को दो बार चलाने पर वही result आना चाहिए जो एक बार चलाने पर आता है। Practice में:

1. **ऐसी unique key चुनो जिसे पुराना system search कर सके**, जैसे policy number plus date of loss.
2. **बनाने से पहले search करो।** हर item की शुरुआत में target system में वो key ढूँढो। अगर record पहले से है, तो उसका reference उठाओ और अगले step पर जाओ।
3. **Item को successful बिल्कुल आखिर में ही mark करो**, जब नया reference tracking sheet में वापस लिख दिया जाए; Save click करते ही कभी नहीं।

```flow
title: एक idempotent queue item
Queue का अगला item लो -> Claims system में पहले से है?
Claims system में पहले से है? -[हाँ]-> मौजूदा claim number पढ़ो
Claims system में पहले से है? -[नहीं]-> Form भरो और save करो | फिर नया claim number पढ़ो
मौजूदा claim number पढ़ो -> Claim number tracking sheet में लिखो
Form भरो और save करो -> Claim number tracking sheet में लिखो
Claim number tracking sheet में लिखो -> Item को successful mark करो
```

कुछ orchestrators एक ही reference वाला दूसरा queue item लेने से मना भी कर सकते हैं। इससे duplicate काम queue में आने से रुकता है, पर retry को target app में दो बार save करने से नहीं रोकता। वो सिर्फ़ search-before-create step रोकता है।

### Robots screen पर चीज़ें कैसे ढूँढते हैं: selectors

अच्छा RPA fixed screen positions पर click नहीं करता। वो हर element को उसकी properties से ढूँढता है: window का title, field का label, उसका type. इस description को **selector** कहते हैं। एक ही Policy number box के लिए दो simplified selectors, UiPath वाले style में:

```text
Brittle:  <wnd app='claims.exe' title='Claims v4.2 - User RKUMAR' />
          <ctrl automationid='txt_4471' idx='7' />

Robust:   <wnd app='claims.exe' title='Claims*' />
          <ctrl name='Policy No*' role='editable text' />
```

Brittle वाला तीन वजहों से टूटता है। Window title में version number और user name है, जो बदलते हैं। Id `txt_4471` app खुद generate करता है और अगले build में बदल सकता है। और `idx='7'` box को मिलते-जुलते boxes में उसके क्रम से चुनता है: उसके ऊपर एक field जोड़ो और robot गलत box में type कर देगा। UiPath की अपनी guidance है कि जहाँ बाकी attributes काम कर दें, वहाँ `idx` से बचो। Robust वाला वो चीज़ें use करता है जिन्हें इंसान पहचान ले: app, window title की शुरुआत और field का label. `*` एक **wildcard** है जो कोई भी characters match करता है, इसलिए "Claims v4.3" भी match हो जाता है। `?` ठीक एक character match करता है।

दो आदतें selectors को टिकाऊ बनाती हैं। Position की जगह label को तरजीह दो। और type करने के बाद, आगे बढ़ने से पहले value वापस पढ़ो, या check करो कि अगली expected screen आई या नहीं।

### Remote desktops और Citrix

कुछ organisations पुराने apps को **Citrix** या remote desktop से publish करते हैं। तब robot को screen की बस एक तस्वीर दिखती है, element properties कुछ नहीं। वो **image matching** पर आ जाता है, यानी button को उसके दिखने से ढूँढना, या **OCR** पर, यानी तस्वीर से text पढ़ना। Theme, font, screen resolution या display scaling बदलने पर दोनों टूट सकते हैं।

पहले IT team से पूछो कि क्या RPA vendor का remote component install हो सकता है। जैसे, UiPath का एक Remote Runtime है जो Citrix server पर चलता है और robot की machine पर एक extension के साथ काम करता है, जिससे robot को फिर से असली selectors मिल जाते हैं। अगर इसकी इजाज़त नहीं है, तो robot machine का resolution और scaling fix करो, हर image को पास के किसी text label से anchor करो, और हर step को text वापस पढ़कर verify करो।

### RPA, computer-use agent या API?

**Computer-use agents** ऐसे AI models हैं जो screenshots देखकर screens चलाते हैं, और हर click चलते-चलते तय करते हैं। वो उन screens को भी संभाल लेते हैं जो उन्होंने पहले कभी नहीं देखीं, पर हर step पर एक model call का खर्च है, वो धीमे हैं, और एक ही screen पर अलग action चुन सकते हैं। जब robot किसी claims या banking system में लिख रहा हो, तो ये अनिश्चितता मानना मुश्किल है।

| हालात | सबसे सही choice | क्यों |
| --- | --- | --- |
| System में काम का API है | API integration | सबसे तेज़, सबसे मज़बूत, साफ़ errors |
| Stable screens, high volume, कोई API नहीं | RPA | Per item सस्ता, predictable, audit हो सकता है |
| बदलती या अनजान screens, कम volume | Computer-use agent, हर change को कोई इंसान approve करे | Flexible, जहाँ RPA को बार-बार fix करना पड़ता |

एक अच्छा pattern इन्हें मिलाता है: stable steps के लिए RPA, और agent सिर्फ़ किसी अनपेक्षित screen से निकलने के लिए, और कुछ भी save होने से पहले कोई इंसान approve करे।

### RPA plus AI

RPA screens के ज़रिए data आगे बढ़ाता है; AI documents पढ़ता है, emails classify करता है या fields निकालता है। साथ मिलकर ये वो processes संभालते हैं जो अकेले कोई नहीं संभाल पाता। AI step उलझे हुए input को साफ़ fields में बदलता है; validation उन्हें आपके अपने data से check करता है; robot सिर्फ़ validated fields type करता है। Robot को कभी भी AI का अंदाज़ा सीधे system of record में डालने मत दो।

### क्या ये फ़ायदे का है? एक break-even check

Robots free नहीं होते। बनाने से पहले compare करो:

- **हर महीने की saving** = हर महीने बचे घंटे × staff की loaded hourly cost (salary plus overheads).
- **हर महीने का cost** = licences + robot machines + AI calls, अगर हों + maintenance घंटे × developer rate.

फिर एक बार के build cost को हर महीने की net saving से divide करो, payback period मिल जाएगा। एक ईमानदार rule: saving तभी गिनो जब खाली हुए घंटे सच में किसी और काम में लगें। वरना robot सिर्फ़ खर्च बढ़ाता है।

### Robots को safe और चालू रखना

Screens बदलने, passwords expire होने या pop-ups आने पर robots टूटते हैं। पहले दिन से इसकी planning करो:

- **Monitoring.** कोई run fail हो या queue आगे बढ़ना बंद कर दे, तो एक तय owner को alert भेजो। रुका हुआ robot आवाज़ नहीं करता; पहला संकेत अक्सर कोई नाराज़ customer होता है।
- **एक robot register.** हर robot का owner, वो किन systems को छूता है और कौन से accounts use करता है, ये record करो।
- **Least-privilege accounts और एक vault.** हर robot को उसका अपना account दो जिसमें सिर्फ़ उतना access हो जितना उसे चाहिए। उसका password credential vault में रखो, जैसे orchestrator का अपना store या CyberArk, script में कभी नहीं।
- **Audit logs.** हर item की key, हर step और result log करो, ताकि साबित कर सको कि robot ने क्या किया। Logs में personal data, जैसे phone numbers, mask करो।
- **Target app बदलने से पहले test करो।** App team से release dates पूछो। हर नया version live होने से पहले उसकी test copy पर robot चलाओ, ताकि खिसके हुए fields production में नहीं, testing में ही पकड़े जाएँ।

## एक example से समझो

ये typical numbers से बना एक illustrative case है, कोई नापा हुआ deployment नहीं।

Kolkata के एक general insurer को motor claim intimations email पर आते हैं: रोज़ करीब 300. Claims team हर email और उसके attachments से details एक पुराने desktop claims system में copy करती है जिसमें API नहीं है। हर claim में करीब 6 मिनट लगते हैं, तो 300 × 6 = 1,800 मिनट, यानी रोज़ 30 घंटे का काम।

**Design:**

```flow
Claim वाला email -> AI extraction step | policy no., vehicle no., नुकसान की तारीख और जगह
AI extraction step -> Policy database से validate करो
Policy database से validate करो -[ok]-> Queue item | key: policy no. plus date of loss
Policy database से validate करो -[ok नहीं]-> किसी इंसान की queue | वजह और एक screenshot के साथ
Queue item -> Unattended robot | पहले search, न मिले तो create
Unattended robot -[app crash]-> App restart करके retry | system exception, 3 tries तक
App restart करके retry -> Unattended robot
Unattended robot -[screen पहचान में नहीं आई]-> किसी इंसान की queue
Unattended robot -> Claim number वापस tracking sheet में
```

1. एक **AI extraction step** हर email और attachment पढ़कर fields निकालता है: policy number, vehicle number, नुकसान की तारीख और जगह, description.
2. Fields को policy database से **validate** किया जाता है: policy है या नहीं, active है या नहीं, vehicle match करता है या नहीं? जो fail हों वो business exceptions हैं और वजह के साथ किसी इंसान के पास जाते हैं।
3. Valid claims, policy number plus date of loss को key बनाकर **queue items** बन जाते हैं।
4. एक **unattended robot** claims system में वो key search करता है। अगर कोई claim नहीं है, तो वो "New intimation" खोलता है, fields भरता है, save करता है, नया claim number पढ़ता है, और उसे tracking sheet में लिखता है। तभी item successful mark होता है।
5. App crashes system exceptions हैं: restart करो और retry, तीन बार तक। जो भी screen robot पहचान न पाए, वो screenshot के साथ किसी इंसान के पास जाती है।

**पहला quarter कुछ ऐसा दिख सकता है:**

| पैमाना | पहले | बाद में |
| --- | --- | --- |
| Data entry पर staff का time | रोज़ करीब 30 घंटे | रोज़ करीब 6 घंटे, ज़्यादातर exceptions |
| उसी दिन डाले गए claims | करीब 70% | करीब 98% |
| Robot outages | लागू नहीं | 2, दोनों बार system updates से fields खिसकने के बाद |
| Retries से बने duplicate claims | लागू नहीं | 0, search-before-create की वजह से |

**क्या ये फ़ायदे का है?** ये मान लिए गए figures use करो; फ़ैसला करने से पहले असली quotes लो।

- बचे घंटे: 30 − 6 = रोज़ 24. 25 working days में, ये हर महीने 600 घंटे हैं।
- मान लो loaded staff cost ₹400 प्रति घंटा है। Saving: 600 × ₹400 = हर महीने ₹2,40,000.
- मान लो running costs हर महीने licences और robot machines के लिए ₹1,00,000, AI extraction के लिए ₹15,000, और ₹1,000 प्रति घंटे पर 20 maintenance घंटे (₹20,000) हैं। कुल: ₹1,35,000.
- Net saving: ₹2,40,000 − ₹1,35,000 = हर महीने ₹1,05,000. अगर build में ₹6,00,000 लगते हैं, तो payback में करीब 6 महीने लगेंगे।

अब इसे उल्टा करके देखो। हर claim 6 मिनट × 24/30 = 4.8 मिनट, यानी 0.08 घंटे बचाता है, तो एक claim की कीमत 0.08 × ₹400 = ₹32 है। 25 दिनों में हर महीने ₹1,35,000 cover करने के लिए robot को ₹1,35,000 ÷ (25 × ₹32), यानी रोज़ करीब 170 claims चाहिए। इन assumptions के साथ, रोज़ करीब 170 claims से कम पर robot घाटे में है। Case volume तय करता है, robot कितना smart है ये नहीं।

Insurer का plan है कि claims system upgrade होने पर robot की जगह direct API integration लगाई जाए। तब तक robot ही पुल है, और उसे हटाना भी सस्ता है क्योंकि सारा logic एक documented queue process में है।

## आम गलतियाँ

- **जहाँ API है वहाँ RPA use करना।** API तेज़ है, मज़बूत है और साफ़ errors देता है। बनाने से पहले vendor या IT team से पूछो।
- **Positions, generated ids या index numbers से बँधे selectors.** Labels और wildcards use करो, और type करने के बाद values वापस पढ़ो।
- **सब कुछ retry करना, या कुछ भी नहीं।** Business exceptions किसी इंसान को भेजो; system exceptions को तय गिनती तक retry करो।
- **बनाने से पहले search नहीं।** Save के बाद एक timeout, और retry duplicate record बना देता है।
- **Item को बहुत जल्दी done mark करना।** Successful तभी mark करो जब reference वापस लिख दिया जाए।
- **ऐसा process automate करना जो बदलता रहता है।** पहले process ठीक या पक्का करो; robot आज की गड़बड़ को वैसे ही जमा देता है।
- **कोई owner नहीं, कोई alerts नहीं।** टूटे हुए unattended robots चुपचाप fail होते हैं और काम ढेर होता जाता है।
- **Admin accounts वाले robots या scripts में passwords.** Least-privilege accounts और vault use करो।
- **हिसाब लगाए बिना बनाना।** कम volume पर licences और maintenance बचे हुए time से ज़्यादा महँगे पड़ सकते हैं।

## Practice करो

नीचे link की गई UiPath Academy पर एक free beginner course करो। अगर आप Windows 11 पर हो, तो Power Automate for desktop में भी practice कर सकते हो, जो पहले से installed है। नीचे link किया गया Microsoft Learn path Power Automate cloud flows cover करता है, जो API वाले हिस्से के लिए अच्छा साथी है।

1. **बनाओ।** एक robot बनाओ जो spreadsheet से rows पढ़े, हर row के लिए एक web या desktop form भरे, save करे, और confirmation number वापस sheet में लिखे।
2. **इसे तोड़ो।** Window resize करो, display scaling बदलो और target box के ऊपर एक field जोड़ो। हर failure को बेहतर selectors से ठीक करो, और type करने के बाद read-back check जोड़ो।
3. **इसे idempotent बनाओ।** वही sheet दो बार चलाओ। दूसरे run में कुछ भी नया नहीं बनना चाहिए; उसे हर record ढूँढकर उसका मौजूदा number उठाना चाहिए।
4. **चुनो और खर्च निकालो।** अपने workplace या college के किसी एक process के लिए RPA, API और computer-use agent में से चुनो, और अपने खुद के माने हुए figures से उसका break-even volume निकालो।

**आपका काम पूरा है जब आप** समझा सको कि API या AI agent की जगह RPA कब चुनोगे, ऐसा robot दिखा सको जो छोटे layout change और बिना duplicates वाले दूसरे run को झेल ले, और किसी एक असली process का break-even volume बता सको।
