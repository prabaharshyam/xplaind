## ये क्या है

**Code review** वो है जब कोई teammate आपका change merge होने से पहले पढ़ता है। GitHub और GitLab पर ये एक **pull request** (या merge request) पर होता है: change, उसका description, automated checks, और specific lines पर comments का एक thread।

Reviews तीन काम करते हैं। वो bugs को users से पहले पकड़ते हैं। वो codebase को एक जैसा रखते हैं, ताकि वो अलग-अलग styles का जोड़-तोड़ न बन जाए। और वो knowledge फैलाते हैं: review के बाद एक की जगह दो लोग उस change को समझते हैं।

Review code के बारे में बातचीत है, इंसान पर फ़ैसला नहीं। जो teams अच्छे से review करती हैं वो तेज़ी से ship करती हैं, क्योंकि problems तब पकड़ी जाती हैं जब उन्हें ठीक करना सस्ता होता है।

## ये कैसे काम करता है

```flow
title: खुलने से merge तक एक pull request
Author एक छोटा pull request खोलता है | क्या, क्यों, कैसे test किया -> Automated checks | tests, linter, build
Automated checks -[fail]-> Author ठीक करता है -> Automated checks
Automated checks -[pass]-> Reviewer पढ़ता है | पहले correctness, फिर design, फिर style
Reviewer पढ़ता है -[बदलाव चाहिए]-> Comments: specific, अच्छे ढंग से, label के साथ
Comments: specific, अच्छे ढंग से, label के साथ -> Author जवाब देता है या fixes push करता है -> Reviewer पढ़ता है
Reviewer पढ़ता है -[ठीक लग रहा है]-> Approve करो और merge करो
```

**Author के तौर पर**, अपना change review के लिए आसान बनाओ:

- उसे छोटा रखो और एक ही चीज़ के बारे में। 200 lines के pull request का ध्यान से review होता है; 2,000 lines वाले को बस सरसरी नज़र से देखा जाता है।
- Description लिखो: क्या बदला, क्यों, और कैसे test किया। Ticket का link दो। जो कुछ दिखता है उसके screenshots जोड़ो।
- पहले अपना diff खुद review करो। बची हुई prints और typos आप किसी और से पहले पकड़ लोगे।
- Review माँगने से पहले checks को pass करा लो।

**Reviewer के तौर पर**, सबसे ज़रूरी चीज़ें इस क्रम में देखो:

| क्रम | क्या देखो | Examples |
| --- | --- | --- |
| 1 | Correctness | गलत logic, न संभाली गई errors, edge cases, security, data leaks |
| 2 | Tests | क्या नए behaviour का test है? क्या change के बिना test fail होता? |
| 3 | Design | क्या ये system में फिट होता है? कुछ दोहराया गया है? क्या आगे बदलना आसान होगा? |
| 4 | Readability | Names, लंबे functions, उलझा हुआ logic, "क्यों" वाले comments की कमी |
| 5 | Style | Formatting और import का क्रम, जिसे आदर्श रूप से linter ठीक करे, इंसान नहीं |

ऐसे comments लिखो जो specific हों (क्या और कहाँ), बताएँ कि क्यों मायने रखता है, और एक fix सुझाएँ। जो optional है उसे "nit:" या "optional:" से label करो। जहाँ पक्का न हो, दावा करने की जगह सवाल पूछो। जो अच्छा है वो भी बताओ; इससे author को पता चलता है कि क्या करते रहना है।

**Comments पाने वाले author के तौर पर**, नीयत अच्छी मानो। धन्यवाद दो, ठीक करो, और हर thread पर जवाब दो। अगर असहमत हो, तो सबूत के साथ समझाओ। अगर कोई thread दो बार से ज़्यादा आगे-पीछे जाए, तो call पर बात कर लो।

**अनजान area में review करना।** अच्छा review करने के लिए पूरा codebase जानना ज़रूरी नहीं है। पहले description और ticket पढ़ो, ताकि पता हो कि change क्या करने वाला है। हो सके तो code या tests अपने यहाँ चलाओ। उन चीज़ों पर ध्यान दो जिन्हें आप परख सकते हो, जैसे error handling, edge cases, tests और readability, और साफ़ बताओ कि किन हिस्सों को आप नहीं परख पाए, ताकि author उनके बारे में किसी और से पूछ सके।

**AI changes का review।** Prompt, model या retrieval settings में बदलाव भी code change है, पर उसका असर outputs में दिखता है, diff में नहीं। Category के हिसाब से पहले और बाद के eval results माँगो, और कुछ example outputs जो बदले हैं। Prompt में एक शब्द का edit एक तरह के सवाल को ठीक कर सकता है और चुपचाप दूसरे को बिगाड़ सकता है।

**Speed मायने रखती है।** जो pull request तीन दिन review का इंतज़ार करता है वो बासी हो जाता है: main आगे निकल जाता है, conflicts जमा होते हैं और author का context छूट जाता है। कई teams का लक्ष्य होता है एक working day में पहला review देना। अगर आप समय पर ठीक से review नहीं कर सकते, तो बता दो, ताकि author किसी और को ढूँढ सके।

**अपने browser में try करो।** ये function चलाओ, फिर इसे review करो: नीचे के tests एक bug दिखाते हैं। उसे ठीक करो और दोबारा चलाओ।

```python
def average_rating(ratings):
    """Average of 1 to 5 star ratings, ignoring missing ones (None)."""
    total = sum(r for r in ratings if r is not None)
    return total / len(ratings)            # review: is this the right count?

print(average_rating([5, 4, None, 3]))     # expected 4.0
print(average_rating([2, 4]))              # expected 3.0
```

## एक example से समझो

Aditya, Gurugram के एक food-delivery startup में junior engineer, एक pull request खोलता है जो "आखिरी meal दोबारा order करो" वाला button जोड़ता है। ये app, API और database में 640 lines बदलता है।

उसकी reviewer, Meera, उससे इसे बाँटने को कहती हैं: एक pull request tests के साथ API endpoint के लिए, एक button के लिए। पहला 180 lines का है। वो उसे पंद्रह मिनट में review करती हैं और चार comments छोड़ती हैं:

- "Endpoint user id request body से लेता है, तो कोई भी किसी और user की तरफ़ से दोबारा order कर सकता है। क्या हम logged-in session की id use कर सकते हैं?" (correctness और security, blocking)
- "ऐसे user का कोई test नहीं है जिसने पहले कोई order नहीं किया। उसमें क्या return होना चाहिए?" (tests, blocking)
- "क्या `get_last()`, `OrderRepository.latest_for_user()` को reuse कर सकता है? ये वही query लग रही है।" (design)
- "nit: `res` को `last_order` कर सकते हो। Blocking नहीं है।"

वो ये कहकर खत्म करती हैं: "बंद restaurant के लिए error handling सच में बहुत साफ़ है, बढ़िया।"

Aditya security वाली दिक्कत ठीक करता है, test जोड़ता है, मौजूदा query reuse करता है और variable का नाम बदलता है। वो हर thread पर जवाब देता है कि क्या बदला। Meera approve करती हैं; change उसी दिन merge हो जाता है। दूसरा pull request, button वाला, और भी जल्दी निकल जाता है, क्योंकि API का review पहले ही हो चुका था।

## आम गलतियाँ

- **बहुत बड़े pull requests।** Reviewers उन्हें सरसरी नज़र से देखते हैं और bugs निकल जाते हैं। Step के हिसाब से बाँटो।
- **सिर्फ़ style पर comment करना।** Formatting tools पर छोड़ो; इंसानी ध्यान logic, tests और security पर लगाओ।
- **धुँधले comments।** "ये गलत है" से author अंदाज़े लगाता रहता है। बताओ क्या, क्यों, और एक सुझाव।
- **Comments को निजी ले लेना।** Comment code के बारे में है। अगर कोई कठोर लगे तो सवाल पूछ लो।
- **बिना पढ़े approve करना।** बिना पढ़ी मुहर, review न होने से भी बुरी है, क्योंकि लोग उस पर भरोसा करते हैं।
- **पसंद-नापसंद पर block करना।** अगर ये बस पसंद की बात है, तो उसे optional mark करो और author को तय करने दो।

## Practice करो

1. अपना आखिरी pull request खोलो और उसका description दोबारा लिखो: क्या, क्यों और कैसे test किया।
2. जिस open-source project को आप use करते हो उसके किसी pull request का review करो और अहमियत के क्रम में पाँच comments का draft बनाओ।
3. अपने पाए या लिखे हुए तीन धुँधले comments को specific और अच्छे ढंग वाले comments में दोबारा लिखो।
4. Behavioural interviews के लिए एक ऐसे code review की STAR story तैयार करो जिसने आपकी सोच बदली।
