## ये क्या है

आपकी AI application आपके laptop पर चलती है। फिर वो server पर जाती है, और एक शाम client का फ़ोन आता है: "Assistant ने जवाब देना बंद कर दिया।" जिन servers पर आपका AI system चलता है, उनमें लगभग सब **Linux** हैं, और आप उन तक एक text **shell** से पहुँचते हो, आमतौर पर Bash, **SSH** के ज़रिए। कोई desktop नहीं, कोई mouse नहीं और कोई File Explorer नहीं।

आपको Linux का expert होने की ज़रूरत नहीं है। आपको skills का एक छोटा, भरोसेमंद set चाहिए:

| Skill | Commands |
| --- | --- |
| घूमना-फिरना और files पढ़ना | `pwd`, `ls -la`, `cd`, `cat`, `less`, `head`, `tail`, `grep` |
| क्या चल रहा है और वो कितना use कर रहा है | `ps aux`, `top` या `htop`, `df -h`, `du -sh`, `free -h` |
| Logs को आते हुए पढ़ना | `tail -f`, `journalctl -u name -f`, `docker logs -f` |
| Settings और scripts | `export`, `env`, `chmod +x`, `set -euo pipefail` |
| सुरक्षित connect करना | `ssh-keygen`, `ssh`, `~/.ssh/config`, `ssh -J` |

```flow
dir: LR
आपका laptop | private key यहीं रहती है -[SSH key]-> Bastion, jump host | आपकी public key check करता है
Bastion, jump host -[SSH]-> App server | ai-assistant service, logs, disk, memory
```

इस lesson में हम आपके साथ Pune के एक logistics client के असली outage से गुज़रेंगे: connect करने से, कारण ढूँढने तक, उसे ठीक करने और लिख डालने तक। Lesson के अंत तक आप भरी हुई disk diagnose कर पाओगे और SSH keys से भरोसे के साथ connect कर पाओगे।

## ये काम कैसे करता है

### Navigation और files

`pwd` दिखाता है कि आप कहाँ हो। `ls -la` files की list देता है, hidden वाली भी। `cd` घुमाता है। `cat` छोटी file print करता है; `less` से आप लंबी file scroll कर सकते हो; `head` और `tail` शुरू और अंत दिखाते हैं।

`grep -i "timeout" app.log` case की परवाह किए बिना मेल खाती lines ढूँढता है; `grep -c` उन्हें गिनता है।

**Pipes** (`|`) छोटे tools को जोड़कर ताकतवर बना देते हैं:

```bash
grep ERROR app.log | sort | uniq -c | sort -rn | head
```

ये error वाली lines ढूँढता है, एक जैसी को group करता है, हर एक को गिनता है, count से sort करता है और ऊपर के दस दिखाता है: सबसे आम errors एक line में।

### Processes और resources

| सवाल | Command |
| --- | --- |
| क्या मेरी service चल रही है? | `ps aux \| grep uvicorn` या `systemctl status ai-assistant` |
| अभी CPU और memory कौन use कर रहा है? | `top` या `htop` |
| Disks कितनी भरी हैं? | `df -h` |
| कौन-से folders बड़े हैं? | `du -sh *` या `sudo du -sh /var/* \| sort -h` |
| कितनी memory खाली है? | `free -h` |

भरी हुई disk रहस्यमयी outages का आम कारण है: logs, temporary files और model downloads चुपचाप उसे भर देते हैं जब तक service कुछ लिख ही न सके।

### Logs

- `tail -f app.log` बढ़ते हुए log file को follow करता है।
- **systemd** से चलने वाली services journal में log करती हैं: `journalctl -u ai-assistant --since "1 hour ago"`।
- Containers: `docker logs -f container-name`।

### Environment variables

Programs `DATABASE_URL` और API keys जैसी settings **environment** से पढ़ते हैं। `export NAME=value` आपके session के लिए एक set करता है; `env` उनकी list देता है। Secrets को environment या secret manager में रखो, कभी code या shell history में नहीं।

### Scripts

Shell script commands की एक file है। हर script को इससे शुरू करो:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

`set -euo pipefail` script को पहले failed command पर, किसी भी unset variable पर और pipe के किसी भी failed step पर रुकवा देता है, आधा-अधूरा काम करते हुए आगे बढ़ने की जगह। `chmod +x script.sh` से इसे executable बनाओ।

### SSH और keys

1. `ssh-keygen -t ed25519` आपकी machine पर एक key pair बनाता है।
2. आप server को अपनी **public** key देते हो। **Private** key आपकी machine से बाहर कभी नहीं जाती।
3. `ssh deploy@10.0.4.12` आपको बिना password के login करा देता है।

`~/.ssh/config` में एक entry servers को छोटे नाम दे देती है। कई companies SSH को **jump host** या **bastion** से गुज़ारती हैं: `ssh -J bastion app-server` उसके ज़रिए hop करता है।

### Permissions

हर file की owner, group और बाकी सबके लिए permissions होती हैं: read, write और execute। Private key को `chmod 600` चाहिए, वरना SSH उसे use करने से मना कर देता है। `sudo` सिर्फ़ उन अकेले commands के लिए use करो जिन्हें उसकी ज़रूरत है, और `rm -rf` के बाद Enter दबाने से पहले दो बार सोचो।

## एक example से समझो

Pune का एक logistics client बताता है कि उनका delivery-query assistant 19:05 पर जवाब देना बंद कर गया। आप उनके bastion से होकर connect करते हो:

```bash
ssh -J bastion.client.in deploy@assistant-01
systemctl status ai-assistant        # active, but restarting every 30 seconds
journalctl -u ai-assistant --since "19:00" | tail -50
```

Log में `OSError: [Errno 28] No space left on device` दिखता है। आप disk check करते हो:

```bash
df -h /                                # 100% used
sudo du -sh /var/* | sort -h | tail -3
```

`/var/log/ai-assistant` में 38 GB है। दो हफ़्ते पहले एक test के बाद debug logging चालू छोड़ दी गई थी, और logs कभी rotate नहीं हुए।

| समय | Step | क्या मिला |
| --- | --- | --- |
| 19:08 | `systemctl status` | Service हर 30 seconds में restart हो रही है |
| 19:09 | `journalctl` | "No space left on device" |
| 19:10 | `df -h` | Disk 100% भरी |
| 19:11 | `du -sh` | 38 GB debug logs |
| 19:15 | पुराने logs compress करके हटाओ, level को INFO करो, logrotate rule जोड़ो, restart करो | Disk 34% पर |
| 19:20 | एक query test करो | Assistant फिर जवाब दे रहा है |

अपने incident note में आप कारण, fix और दो follow-ups लिखते हो: 80% पर disk-space alert, और CI में एक check कि production में log level DEBUG न हो।

## आम गलतियाँ

- **आदत से root के रूप में काम करना।** गलतियाँ आफ़त बन जाती हैं। Normal user और अकेले commands के लिए `sudo` use करो।
- **Secrets को command line पर paste करना।** वो shell history में चले जाते हैं। Restricted permissions वाली environment files या client का secret manager use करो।
- **Production को हाथ से edit करना और किसी को बताना नहीं।** अगला deploy आपका fix मिटा देगा। Change को code या config में डालो और लिख दो।
- **`set -euo pipefail` के बिना scripts।** Failed step पर किसी का ध्यान नहीं जाता और बाद के steps data बिगाड़ देते हैं।
- **Private keys share करना।** हर इंसान और हर machine की अपनी key हो, ताकि access साफ़-सुथरे ढंग से हटाया जा सके।
- **जगह बनाने के लिए वो files delete करना जो समझ नहीं आतीं।** पहले ढूँढो कि क्या बड़ा है और क्यों।
