## ये क्या है

ML engineer interview loop कई rounds का set होता है, और हर round एक skill test करता है। Pass आप हर round में solid होकर होते हो, किसी एक में brilliant होकर नहीं। ML में strong लोग भी उस round में fail हो सकते हैं जिसकी उन्होंने तैयारी नहीं की, जैसे DSA coding।

| Round | क्या test होता है | Strong candidate क्या दिखाता है |
| --- | --- | --- |
| Online assessment या DSA coding | एक timed problem में data structures और algorithms | एक सही, tested solution और उसकी time और space complexity |
| ML coding | Pandas, NumPy, कोई metric या छोटा algorithm scratch से | Clean code जो ties और empty inputs जैसे edge cases संभाले |
| ML fundamentals | Models, losses, metrics और validation कैसे काम करते हैं | Mechanism, trade-off और एक default choice |
| ML system design | एक धुंधले business problem को deployed system में बदलना | साफ़ structure, बोलकर बताए numbers, production thinking |
| LLM या GenAI design | RAG, evals, prompting बनाम fine-tuning, cost और latency | पहले measurement, फिर सबसे simple design जो उस पर खरा उतरे |
| Project deep-dive | आपका एक project, गहराई से | Numbers, decisions, गलतियाँ और आप क्या बदलते |
| Behavioural या hiring manager | Ownership, conflict, failure | असली numbers वाली छोटी STAR stories |

Mix हर जगह अलग होता है। Google और Meta जैसी बड़ी product companies में ML roles के कुछ candidate reports, ML design और behavioural rounds के साथ standard algorithm coding rounds भी बताते हैं। कुछ companies इसकी जगह take-home या practical ML coding task देती हैं। इसलिए recruiter से rounds की list पूछो; वो इस सवाल की उम्मीद करते हैं।

```flow
title: 40 मिनट में ML system design
1 Goal और metric -> 2 Framing और label -> 3 Data -> 4 Features | लगभग 15 मिनट
4 Features -> 5 Baseline, फिर model -> 6 Evaluation | offline और A/B, लगभग 12 मिनट
6 Evaluation -> 7 Serving | batch या real time, fallback के साथ -> 8 Monitoring | लगभग 8 मिनट
8 Monitoring -> 9 Risks | fairness, abuse, failure; लगभग 5 मिनट
```

## ये काम कैसे करता है

### DSA round

ये round अक्सर वैसा ही होता है जैसा software engineers के लिए। Role ML है इसलिए आसान problems की उम्मीद मत करो, और जान लो कि अकेला यही round पूरा loop डुबा सकता है। Big-tech ML roles के कुछ candidate reports medium और कभी-कभी hard problems बताते हैं।

**क्या test होता है।** ये patterns सीखो, रटे हुए answers नहीं।

- Hash maps, two pointers और sliding windows के साथ arrays और strings।
- Sorting, binary search और intervals (merge, overlap)।
- Stacks, queues और heaps (top k, running median)।
- Trees और graphs: BFS, DFS, shortest paths, topological sort।
- Basic level पर dynamic programming (एक और दो dimensions)।

**बोलते-बोलते solve करो।** Interviewers सिर्फ़ code नहीं, process को भी score करते हैं।

1. Problem को अपने शब्दों में दोहराओ और inputs, sizes और edge cases के बारे में पूछो।
2. एक छोटा example हाथ से करके देखो।
3. एक brute-force solution और उसकी cost बताओ।
4. उसे improve करो, और बताओ कि नया idea क्यों काम करता है।
5. साफ़ names के साथ code करो।
6. अपने example और एक edge case पर test करो, फिर time और space complexity बताओ।

ML interviewers किसी DSA problem को data की भाषा में पूछ सकते हैं। जैसे: "Time order में `(merchant_id, timestamp)` pairs के रूप में UPI payments दिए हैं; उन merchants को flag करो जिनके किसी भी 60-second window में `k` से ज़्यादा payments हों।" ये hash map वाली sliding window है:

```python
from collections import defaultdict, deque

def flag_bursts(events, k, window_s):
    """events: (merchant_id, unix_seconds) sorted by time.
    Return merchants with more than k payments inside any window_s seconds."""
    recent = defaultdict(deque)          # merchant -> timestamps still in the window
    flagged = set()
    for merchant, t in events:
        q = recent[merchant]
        q.append(t)
        while q[0] <= t - window_s:      # drop payments older than the window
            q.popleft()
        if len(q) > k:
            flagged.add(merchant)
    return flagged

events = [("m1", 0), ("m2", 5), ("m1", 10), ("m1", 20), ("m1", 70), ("m2", 80)]
print(flag_bursts(events, k=2, window_s=60))   # {'m1'}
```

हर timestamp अपनी queue में ज़्यादा से ज़्यादा एक बार आता है और एक बार निकलता है, इसलिए n events के लिए time O(n) है। फिर follow-up risk बताओ: अब तक आए हर merchant के साथ memory बढ़ती है, क्योंकि idle merchants की queues कभी हटाई नहीं जातीं।

**तैयारी।** Python में `collections`, `heapq` और `bisect` के साथ practice करो। हर pattern के कुछ problems solve करो और जो fail हुए उन्हें एक हफ़्ते बाद दोबारा करो, ऐसे timed mocks में जहाँ आप पूरे समय बोलते रहो। बोलकर सोचना चुपचाप solve करने से अलग skill है, और test वही होती है।

### ML coding round

यहाँ आप puzzles नहीं, data code लिखते हो: pandas groupby, join या rolling window; time के हिसाब से split; scratch से कोई metric; NumPy में k-means या logistic regression। ये example दो favourites को जोड़ता है: label delay का ध्यान रखने वाला time split, और k पर precision और recall।

```python
import numpy as np
import pandas as pd

def split_with_gap(df, test_start, test_end, delay_days, labels_pulled_on):
    delay = pd.Timedelta(days=delay_days)
    test_start, test_end = pd.Timestamp(test_start), pd.Timestamp(test_end)
    # Test labels must have matured too, or late fraud looks like "not fraud".
    assert test_end + delay <= pd.Timestamp(labels_pulled_on), "test labels not mature"
    train = df[df["txn_time"] < test_start - delay]   # what you could know on test_start
    test = df[(df["txn_time"] >= test_start) & (df["txn_time"] < test_end)]
    return train, test

def precision_recall_at_k(y_true, scores, k):
    y_true = np.asarray(y_true)
    top_k = np.argsort(-np.asarray(scores))[:k]     # the k highest scores
    caught = y_true[top_k].sum()
    return caught / k, caught / y_true.sum()

df = pd.DataFrame({"txn_time": pd.date_range("2026-01-01", "2026-06-30", freq="D")})
train, test = split_with_gap(df, "2026-05-01", "2026-06-01", 60, "2026-08-01")
print(train["txn_time"].max().date(), len(train), len(test))   # 2026-03-01 60 31

y = [1, 0, 0, 1, 0, 0, 0, 1, 0, 0]
s = [0.9, 0.8, 0.1, 0.7, 0.3, 0.2, 0.6, 0.4, 0.05, 0.15]
p, r = precision_recall_at_k(y, s, 3)
print(round(p, 2), round(r, 2))   # 0.67 0.67
```

Gap क्यों? मान लो fraud labels आने में 60 दिन तक लगते हैं। 1 May को deploy हुआ model सिर्फ़ उन्हीं transactions पर train हो सकता था जिनके final labels थे, यानी लगभग 2 March से पहले वाले। March और April की rows पर बाद में निकाले गए labels के साथ train करना ऐसी जानकारी use करना है जो उस समय आपके पास नहीं होती, इसलिए test score ज़रूरत से ज़्यादा अच्छा दिखता है। किसी असली retraining job में, delay से नई rows unlabelled होती हैं, negatives नहीं। बिना पूछे ये बताना एक strong signal है।

### ML fundamentals: mechanism, trade-off और default के साथ जवाब दो

Strong answer में mechanism, trade-off और आपकी default choice होती है। दो model answers:

**"Random forests और gradient boosting में क्या फ़र्क है?"** "दोनों बहुत सारे decision trees को जोड़ते हैं। Random forest गहरे trees को अलग-अलग train करता है, हर एक को एक bootstrap sample पर, हर split पर features के एक random subset में से चुनकर, और फिर उनका average लेता है। इससे मुख्य रूप से variance घटता है, इसलिए tuning कम लगती है और बुरी तरह overfit कम ही होता है। Gradient boosting छोटे trees को एक के बाद एक train करता है, हर tree अब तक के trees की errors को fit करता है। इससे bias घटता है और tabular data पर ये अक्सर जीतता है, लेकिन overfit हो सकता है, इसलिए मैं learning rate और depth tune करता हूँ और early stopping use करता हूँ। Tabular data के लिए मेरा default boosting है, जैसे LightGBM या XGBoost, और quick baseline के तौर पर random forest।"

**"Data leakage कैसे पकड़ोगे?"** "Leakage का मतलब है model ऐसी जानकारी देख रहा है जो prediction के समय उसके पास नहीं होगी। मेरा पहला signal है problem के हिसाब से ज़रूरत से ज़्यादा अच्छा score। फिर मैं तीन जगह check करता हूँ। Features: क्या कोई top feature outcome के बाद record होता है, जैसे churn model में `refund_issued`? Split: क्या एक ही customer या लगभग duplicate rows train और test दोनों में हैं, या training data test data के बाद का है? Preprocessing: क्या scaling या target encoding पूरे data पर fit किया गया? Fix ये है कि हर feature prediction time के हिसाब से compute करो, time या customer के हिसाब से split करो, और preprocessing सिर्फ़ training data पर fit करो।"

हर answer एक mechanism, एक ठोस example और एक decision बताता है; कोई भी definition नहीं रटता। इन topics के लिए भी यही shape तैयार करो।

| Topic | अच्छे answer का core |
| --- | --- |
| Bias और variance | Training और validation error दोनों high हों तो underfitting; दोनों के बीच बड़ा gap हो तो overfitting। इसे learning curves से पढ़ो |
| Regularisation | L2 सारे weights छोटे करता है; L1 कुछ को ठीक zero तक धकेल देता है, जिससे features select होते हैं। दोनों थोड़ा bias देकर variance कम करते हैं |
| Imbalanced data | Accuracy धोखा देती है। PR AUC use करो, और उस threshold या capacity पर precision और recall जिस पर business action ले सके |
| Cross-validation | Independent rows के लिए K-fold; rows time order में हों या एक customer share करती हों तो time-based या grouped folds |
| Logistic regression | एक linear score जो sigmoid से गुज़रता है, log loss से train होता है। Fast, समझाने में आसान, एक strong baseline |
| Attention | हर token की query हर token की key से compare होती है; scores का softmax उनकी values को weight देता है |

सबसे ज़्यादा पूछे जाने वाले topics पर I1 के lessons "Cross-validation and leakage" और "Choosing a metric" और गहराई में जाते हैं।

### ML system design

Diagram के नौ steps को क्रम से use करो, और numbers बोलकर बताओ। तीन steps पर सबसे ज़्यादा ध्यान चाहिए। *Framing* में बताओ कि label कहाँ से आता है और कितनी देर से आता है। *Evaluation* में ऐसा split चुनो जो असलियत से मेल खाए, और operating point पर एक metric, segment के हिसाब से। *Serving* में latency budget और एक fallback बताओ।

**Offline बनाम online।** बेहतर offline score बेहतर business result की guarantee नहीं है, क्योंकि live users model पर react करते हैं। एक A/B test plan करो जिसमें एक primary metric हो और complaint rate या latency जैसे guardrails हों। Pitfalls जान लो। Result significant दिखते ही रोक देना ("peeking") झूठी जीत बढ़ाता है। पूरे हफ़्ते से छोटा test weekday और weekend के patterns miss कर देता है। और जो model चीज़ें block करता है या छुपाता है, वो आपको ये देखने नहीं देता कि वरना क्या होता, इसलिए एक छोटा random holdout रखो।

**"Why not X?" को handle करना।** Trade-off के साथ जवाब दो। जैसे: "Deep model मदद कर सकता है, लेकिन tabular features और देर से आने वाले labels के साथ gradient boosting अक्सर मिलती-जुलती accuracy देता है, minutes में train होता है और risk team को समझाना आसान है। अगर error analysis में ऐसे patterns दिखें जो trees miss करते हैं, तो मैं deep model try करूँगा।"

### LLM और GenAI design सवाल

कुछ ML loops में अब large language model पर बने product के बारे में एक सवाल आता है, जैसे:

- "एक assistant design करो जो bank के policy documents से customers के सवालों के जवाब English और Hindi में दे।"
- "Support tickets को 40 categories में बाँटने के लिए prompting use करें, RAG या fine-tuning?"

Goal और गलत जवाब की cost clear करो, फिर सबसे simple approach चुनो जो काम कर सकता है: जब answers बदलते रहने वाले documents से आने हों और citations चाहिए, तो RAG; task simple हो तो कुछ examples के साथ prompting; volume ज़्यादा हो और cost या latency मायने रखे, तो एक छोटे model को fine-tune करना। बहुत सारी labelled history वाली ticket sorting के लिए एक classic classifier को baseline के रूप में भी रखो। फिर measurement को पहले रखो: असली सवालों का eval set, retrieval को answers से अलग score करना, और कुछ relevant न मिले तो क्या करना है उसका plan। आखिर में हर query की cost और latency, privacy और एक human fallback। "Build a RAG app", "Test sets and evals", "Prompting, RAG or fine-tuning" और "The design interview" lessons हर हिस्सा cover करते हैं।

### Project deep-dive और behavioural

**Project deep-dive।** एक या दो projects गहराई से तैयार करो: problem, data, baseline, क्या try किया, numbers के साथ results, क्या गलत हुआ, आगे क्या। Team project में आपने खुद क्या किया, ये साफ़ बताओ।

**Behavioural।** STAR (situation, task, action, result) use करो, numbers और एक सीख के साथ। एक illustrative failure story (आप अपनी असली story use करो):

- *Situation*: "Pune में एक insurance sales team के लिए मेरा lead-scoring model live हुआ। दो हफ़्तों में top-scored leads पर conversion testing के लगभग 9% से गिरकर लगभग 4% रह गया।"
- *Task*: "Model मेरा था और मुझे cause जल्दी ढूँढना था।"
- *Action*: "मैंने training और live feature values compare कीं। एक 'last call outcome' field training data में call के बाद भरी जाती थी, लेकिन scoring के समय खाली होती थी। वो leakage था। मैंने features को scoring time के हिसाब से दोबारा बनाया और एक pre-launch check जोड़ा जो training और live features compare करता है।"
- *Result*: "Offline AUC 0.91 से गिरकर 0.78 हो गया, लेकिन top leads पर live conversion वापस लगभग 7% पर आ गया। अब training से पहले मैं check करता हूँ कि हर feature prediction time पर मौजूद है।"

### Interviewers आपको कैसे score करते हैं

अपने recorded practice answers को इस list से score करो। Weak column में आम no-hire signals हैं।

| वो क्या सुनना चाहते हैं | Weak | Strong |
| --- | --- | --- |
| Clarifying सवाल | तुरंत design शुरू कर देता है | पहले goal, scale और constraints पूछता है |
| Label | मान लेता है कि labels मौजूद हैं | बताता है कि labels कहाँ से और कितनी देर से आते हैं |
| Metric | "Accuracy" | Operating point पर एक metric, business metric से जुड़ा |
| Baseline | बड़े model से शुरू करता है | पहले rules या linear model, complexity की वजह बताता है |
| Split | Random split | Time या group split, label delay के लिए gap के साथ |
| Serving | ज़िक्र ही नहीं | Batch या real time, latency budget, fallback |
| Monitoring | "कभी-कभी retrain कर लेंगे" | Drift checks, feedback loops, एक holdout, एक retrain trigger |
| Communication | लंबी चुप्पी, कोई structure नहीं | हर step को signpost करता है और numbers बताता है |

## एक example से समझो

सवाल: "एक payments company के लिए fraudulent UPI merchant payments detect करने का system design करो।" नीचे के numbers वो assumptions हैं जो आप interview में बताओगे, असली figures नहीं।

1. **Goal**: सीमित analyst time में fraud losses घटाना। Latency के बारे में पूछो; मान लो payment flow block करने के लिए लगभग 100 ms देता है, साथ में एक review queue।
2. **Framing**: हर payment पर binary classification। Labels chargebacks और confirmed investigations से आते हैं। मान लो वो 60 दिनों के अंदर आ जाते हैं।
3. **Data**: payments, merchant profiles, device और network signals, पुराना fraud। Fraud rare है; मान लो payments का 0.05%।
4. **Features**: पिछले एक घंटे में merchant के payments, merchant की आम amounts के मुकाबले amount, नया device, दिन का समय, merchant category। सब payment time के हिसाब से एक feature store से compute किए जाते हैं, ताकि training और serving match करें।
5. **Model**: एक rules baseline, फिर class weights के साथ gradient-boosted trees। बाद में merchants, devices और accounts को जोड़ने वाले graph features।
6. **Evaluation**: ऊपर के code की तरह 60-day gap वाला time split। Analysts जितना alert volume संभाल सकते हैं उस पर PR AUC, precision और recall measure करो, merchant category और region के हिसाब से। फिर traffic के एक हिस्से पर A/B test चलाओ।
7. **Serving**: Real-time scoring, और model time out हो तो rules पर fallback। दो thresholds: बहुत high score के ऊपर auto-block, उससे नीचे review queue।
8. **Monitoring**: Key features पर drift, alert rate में बदलाव, और monthly retraining। Block हुए payments से कभी पता नहीं चलता कि वो fraud थे या नहीं, इसलिए जो payments block होने वाले थे उनका एक छोटा random sample block करने की जगह analysts को भेजो।
9. **Risks**: असली छोटे merchants को block कर देना (appeal का रास्ता दो), fraudsters का तरीका बदल लेना (बार-बार retrain करो), अलग-अलग regions में असमान error rates।

अब numbers बोलकर बताओ। ये दिखाते हैं कि accuracy गलत metric क्यों है।

| Quantity (assumed) | Value |
| --- | --- |
| हर दिन payments | 20 lakh |
| Fraud rate | 0.05%, यानी हर दिन 1,000 frauds |
| "Never fraud" की accuracy | 99.95%, और पकड़ा गया fraud zero |
| Analysts कितने alerts review कर सकते हैं | हर दिन 2,000 |
| Top 2,000 alerts में frauds (example) | 600 |
| 2,000 पर precision | 600 / 2,000 = 30% |
| 2,000 पर recall | 600 / 1,000 = 60% |

फिर पूछो: "30% precision पर 60% fraud पकड़ना क्या analyst cost के लायक है, और क्या हर दिन 500 और reviews अपना खर्च निकाल लेंगे?" इससे model एक business decision बन जाता है।

## आम गलतियाँ

- **DSA की तैयारी छोड़ देना।** कुछ candidate reports बड़ी product companies के ML loops में standard coding round बताते हैं, और ये एक strong ML candidate को भी डुबा सकता है।
- **सीधे deep learning पर कूदना।** Baseline से शुरू करो और complexity के हर कदम की वजह बताओ।
- **Label को नज़रअंदाज़ करना।** Labels कहाँ से और कितनी देर से आते हैं, यही data, split, metric और retraining को तय करता है।
- **Time-based problems में random या बिना gap वाले splits।** दोनों future की जानकारी leak करते हैं और scores बढ़ा देते हैं।
- **Imbalanced data पर accuracy बताना।** उस capacity पर precision और recall बताओ जिस पर business action ले सके।
- **Offline जीत को launch मान लेना।** A/B test, guardrails और holdout plan करो।
- **Serving या monitoring का कोई plan नहीं।** Latency budget, fallback और retraining किस बात से trigger होगी, ये बताओ।
- **ऊपरी-ऊपरी project stories।** अपने numbers, अपना खुद का contribution और अपनी गलतियाँ पता होनी चाहिए।

## Practice करो

Chip Huyen के ML systems design notes और उनकी ML interviews book पढ़ो; behavioural rounds के लिए Tech Interview Handbook use करो।

1. **DSA**: हर pattern के कुछ medium problems Python में solve करो, बोलकर और timed।
2. **ML coding**: बिना notes के, label-delay gap वाला time split, k पर precision और recall, और NumPy में k-means लिखो। हर एक को एक छोटे example पर test करो।
3. **Fundamentals**: दस सवालों के 60 से 90 शब्दों के answers mechanism, trade-off और default वाले shape में लिखो, हर एक में एक Indian example के साथ।
4. **System design**: दो अनदेखे सवालों का जवाब नौ steps के साथ 40-40 मिनट में दो, record करके। जैसे, Hyderabad की एक grocery chain के लिए demand forecasting, या किसी jobs app के लिए ranking। Table से खुद को score करो।
5. **GenAI**: Bank assistant वाले सवाल का जवाब दो और ठीक-ठीक बताओ कि उसका eval set कैसे बनाओगे।
6. **Deep-dive और behavioural**: एक project deep-dive और तीन STAR stories तैयार करो, जिनमें एक failure के बारे में हो।

**आपका काम पूरा है जब आप** बोलते-बोलते एक medium DSA problem 30 मिनट में solve कर सको, और एक अनदेखा ML system 40 मिनट में design कर सको, साफ़ label, ईमानदार split, operating point पर metric, serving और monitoring के साथ।
