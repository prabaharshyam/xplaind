## ये क्या है

Code से language model को call करना किसी भी web API को call करने जैसा है: आपका program prompt के साथ एक request भेजता है, provider model चलाता है, और आपको reply मिलता है, साथ में कुछ details जैसे कितने tokens लगे। इसके साथ आपके अपने programs summarise, classify, extract और write कर सकते हैं।

हर बड़ा provider एक API और एक official Python SDK (software development kit) देता है, जो HTTP की details को लपेट लेता है।

```flow
dir: LR
Your script | client = Anthropic(), key from the environment, messages.create(...) -[HTTPS POST: model, max_tokens, system, messages]-> Model provider | runs the model on the system prompt + message history
Model provider -[reply text, usage, stop reason]-> Your script reads it | text blocks of .content, reply.usage in tokens
```

ये lesson Gurugram के backend developer Vikram के साथ चलता है, जो एक ऐसा tool बना रहा है जो बिखरे meeting notes को साफ़ summaries में बदलता है।

## ये काम कैसे करता है

**Key लो।** Provider के developer console में account बनाओ, ज़रूरत हो तो थोड़ा credit डालो, और एक API key बनाओ। उसे password की तरह संभालो।

**Key को code से बाहर रखो।** उसे environment variable में रखो, अक्सर `.gitignore` में लिखी `.env` file में। SDK आमतौर पर उसे एक standard variable name से अपने आप पढ़ लेता है।

**SDK install करो**, अपने project के virtual environment में pip से।

**Message भेजो।** एक आम call model का नाम बताती है, output की length पर limit लगाती है, और messages की list पास करती है। यहाँ Anthropic के Python SDK के साथ दिखाया है; दूसरे providers के SDKs भी यही pattern follow करते हैं:

```python
import anthropic

client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment

reply = client.messages.create(
    model="claude-sonnet-5-5",          # check the docs for current model names
    max_tokens=300,
    system="You are a concise assistant for a small bakery in Pune.",
    messages=[{"role": "user", "content": "Write a two-line WhatsApp message announcing fresh plum cakes for Christmas."}],
)

text = "".join(b.text for b in reply.content if b.type == "text")
print(text)
print("tokens in:", reply.usage.input_tokens, "out:", reply.usage.output_tokens)
```

Reply का `content` blocks की एक list है। नए models text से पहले एक thinking block रख सकते हैं, इसलिए ये मानने की जगह कि पहला block ही answer है, उन blocks को चुनो जिनका type `text` है।

**Message list।** बातचीत roles (user और assistant) वाले messages की list होती है। Chat आगे बढ़ाने के लिए पिछले turns नए message के साथ दोबारा भेजो; API खुद पिछली calls याद नहीं रखती। **System** prompt स्थायी instructions तय करता है।

**Usage और cost।** हर reply input और output tokens बताता है। Model की per-token कीमत से गुणा करो और पता चल जाता है कि हर call का cost क्या है। Build करते समय usage print करते रहो ताकि cost कभी चौंकाए नहीं।

**Model चुनना।** Providers बड़े, ज़्यादा काबिल models और छोटे, तेज़, सस्ते models देते हैं। एक mid-sized model से शुरू करो और बदलने से पहले test करो।

**Request के हिस्से, और वो क्या control करते हैं:**

| हिस्सा | क्या control करता है | Tip |
| --- | --- | --- |
| `model` | Capability, speed और कीमत | मौजूदा नाम docs में देखो |
| `max_tokens` | Reply की अधिकतम length | इसे हमेशा set करो |
| `system` | पूरी chat के लिए role, tone, rules | Calls के बीच इसे स्थिर रखो |
| `messages` | अब तक की बातचीत | User और assistant turns बारी-बारी से |
| Reply का `usage` | कितने tokens लगे | पहले दिन से log करो |
| Reply का stop reason | क्यों रुका: पूरा हो गया, या token limit आ गई | अगर limit आई, तो answer कटा हुआ है |

**Streaming।** लंबे reply को पूरा होने में दस सेकंड या ज़्यादा लग सकते हैं। Streaming में API text लिखे जाते ही भेजती है, इसलिए user लगभग एक सेकंड में पढ़ना शुरू कर देता है। Chat interfaces लगभग हमेशा stream करते हैं; background jobs, जैसे रात भर में हज़ार files का summary बनाना, को आमतौर पर इसकी ज़रूरत नहीं होती।

**Errors और retries।** API calls कभी-कभी fail होती हैं, और आपका code इसकी उम्मीद रखे:

| Error | मतलब | क्या करें |
| --- | --- | --- |
| 401 या 403 | Key गायब, गलत या allowed नहीं | Key ठीक करो; retry मत करो |
| 400 | आपकी request में कुछ invalid है | Message पढ़ो और request ठीक करो |
| 429 | Rate limit: हर मिनट बहुत ज़्यादा requests या tokens | रुको और retry करो, धीमे होकर |
| 500, 529 या timeout | Provider की error या overload | बढ़ते इंतज़ार के साथ retry करो; जारी रहे तो backup model पर जाओ |

Anthropic का SDK rate limits, overloads और connection errors को पहले से बढ़ते इंतज़ार के साथ दो-तीन बार retry करता है; कितनी बार, ये आप `max_retries` से और कितना इंतज़ार, ये `timeout` से set कर सकते हो। फिर भी आपके code को तय करना है कि अगर हर retry fail हो जाए तो user को क्या दिखे।

**एक छोटा chat program।** ये सारे हिस्से जोड़ता है: history, streaming, भेजने से पहले token check, कटे हुए reply की पहचान और errors।

```python
import anthropic

client = anthropic.Anthropic(max_retries=3, timeout=60)
MODEL = "claude-sonnet-5-5"            # check the docs for current model names
SYSTEM = "You help students in Kerala plan their study week. Be brief."
history = []

def ask(text):
    history.append({"role": "user", "content": text})
    size = client.messages.count_tokens(model=MODEL, system=SYSTEM, messages=history).input_tokens
    if size > 20_000:
        history.pop()
        return "This conversation is too long. Please start a new one."
    try:
        with client.messages.stream(model=MODEL, max_tokens=500, system=SYSTEM, messages=history) as stream:
            for chunk in stream.text_stream:
                print(chunk, end="", flush=True)        # words appear as they arrive
            reply = stream.get_final_message()
    except anthropic.RateLimitError:
        history.pop()
        return "Busy right now. Please try again in a minute."
    except anthropic.APIStatusError as err:
        history.pop()
        return f"The AI service returned an error ({err.status_code})."
    except anthropic.APIConnectionError:
        history.pop()
        return "Could not reach the AI service. Check the connection."
    history.append({"role": "assistant", "content": reply.content})
    if reply.stop_reason == "max_tokens":
        print("\n[reply cut off at the length limit]")
    print(f"\n(tokens in {reply.usage.input_tokens}, out {reply.usage.output_tokens})")

ask("I have maths and chemistry exams in two weeks. Make a plan for Monday.")
ask("Move chemistry to the evening.")             # the model sees the first turn too
```

Error आने पर user का message history से हटा दिया जाता है, ताकि अगली कोशिश में लगातार दो user messages न जाएँ।

**Sampling settings।** कुछ models `temperature` जैसी settings मानते हैं, जो control करती हैं कि शब्दों में कितनी variety हो; models शब्द कैसे चुनते हैं, उस lesson में ये समझाया गया है। नए models में इनमें से कुछ settings fixed हो सकती हैं, इसलिए उन पर भरोसा करने से पहले model का documentation देखो।

**Conversation history में पैसे लगते हैं।** क्योंकि आप हर turn पर पूरी history दोबारा भेजते हो, लंबी chats हर message के साथ महँगी होती जाती हैं: turn 20 में turns 1 से 19 का input दोबारा देना पड़ता है। असली apps पुराने turns को trim या summarise करते हैं, और system prompt स्थिर रखते हैं ताकि providers उसे cache कर सकें और दोहराए गए हिस्से के लिए कम charge करें।

**Browser में try करो।** देखो कि history दोबारा भेजने से हर turn का cost कैसे बढ़ता है। Numbers बदलो और फिर चलाओ।

```python
system_tokens, question, answer = 1200, 100, 250
history = 0
for turn in range(1, 11):
    sent = system_tokens + history + question
    print(f"turn {turn:>2}: {sent:>5} input tokens")
    history += question + answer       # this turn is resent next time
```

## आम गलतियाँ

- **API key को code में लिख देना।** Environment variables use करो; जो key कभी commit हुई हो उसे rotate करो।
- **`max_tokens` भूल जाना।** Output पर हमेशा cap लगाओ।
- **API से पिछली calls याद रखने की उम्मीद करना।** Conversation history खुद भेजो।
- **पुराने model names use करना।** मौजूदा list docs में देखो।
- **Usage numbers को नज़रअंदाज़ करना।** पहली call से tokens track करो।

- **पूरा response object logs में print करना।** उसमें user का text हो सकता है। इसकी जगह ids, token counts और timings log करो।
- **ये मान लेना कि हर call सफल होगी।** Rate limits, overloads और timeouts संभालो, और user को साफ़ message दिखाओ।
- **हर चीज़ को retry करना।** गलत key या invalid request हर बार एक जैसे ही fail होती है।
- **Stop reason को नज़रअंदाज़ करना।** जो reply `max_tokens` पर पहुँचा, वो अधूरा है।

## API की अभी ज़रूरत कब नहीं

- **One-off काम**: एक summary या draft के लिए chat app तेज़ है।
- **Spreadsheet या no-code काम**: n8n जैसे tools या spreadsheet add-on शायद पहले से आपके लिए model call कर रहे हैं।
- **Prompts सीखना**: पहले provider के console या workbench में prompts try करो, फिर जो चले उसे code में ले जाओ।

## Demo से production तक

- **Key को server पर रखो।** उसे mobile app या browser code में कभी मत भेजो; browser आपके server को call करता है, और आपका server model को।
- **हर user की limits लगाओ**: हर मिनट की requests और रोज़ के tokens, ताकि एक user या script bill न बढ़ा दे।
- **Metadata log करो**: request id, model, tokens, लगा हुआ समय, stop reason और error type।
- **Model version pin करो** जहाँ provider तारीख वाले नाम देता है, और नए पर जाने से पहले test करो।
- **Outages की योजना रखो**: user के लिए साफ़ message, और ज़रूरी features के लिए backup model।
