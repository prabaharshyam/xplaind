## ये क्या है

**Security questionnaire** (vendor risk assessment) वो तरीका है जिससे कोई enterprise किसी supplier को data या systems का access देने से पहले उसे जाँचता है। ये client की अपनी spreadsheet हो सकती है, Cloud Security Alliance का CAIQ या SIG questionnaire जैसा कोई standard हो सकता है, या किसी vendor-risk platform का portal हो सकता है। सवाल इन चीज़ों को cover करते हैं:

- company का security programme, policies और certifications (SOC 2, ISO 27001);
- access control, authentication और staff की जाँच;
- transit और rest में encryption, key management;
- network security, vulnerability management और penetration tests;
- logging, monitoring और incident response;
- business continuity, backups और disaster recovery;
- data handling: location, retention, deletion, sub-processors;
- और, अब ज़्यादा, AI-specific सवाल: client data पर training, model providers, prompt injection, output review, human oversight।

```flow
Questionnaire, 240 सवाल -> Answer library
Answer library -[170 match हुए]-> Evidence links के साथ reviewed answers
Answer library -[40 AI-specific]-> Design docs से जवाब | data flow map, gateway config, masking rules, guardrail tests, approval step, audit log schema
Answer library -[30 client-specific]-> Legal के साथ draft | RBI outsourcing, localisation
Design docs से जवाब -> Gaps: "Partially" + तारीख़ वाला plan
Legal के साथ draft -> Gaps: "Partially" + तारीख़ वाला plan
Gaps: "Partially" + तारीख़ वाला plan -[नए answers वापस जोड़े गए]-> Answer library
```

ये lesson Meera को follow करता है, जो Bengaluru के एक AI startup में FDE है और सफल pilot के बाद एक बड़े private bank के questionnaire का जवाब दे रही है।

## ये काम कैसे करता है

**Answer library बनाओ।** ज़्यादातर सवाल clients के बीच दोहराए जाते हैं। Approved answers की एक reviewed library रखो, हर एक के साथ owner, last-checked date और evidence के links (policy documents, SOC 2 report, penetration test summary, architecture diagrams)। नए questionnaires का जवाब उसी से दो, और review के बाद नए answers वापस जोड़ दो।

**सटीक और सच्चा जवाब दो।** बिना विवरण का "Yes" follow-up सवाल बुलाता है; overclaim contract breach बन सकता है। अच्छे answers बताते हैं क्या, कैसे और कहाँ: "सारा data rest पर AES-256 से encrypted है, keys Central India में Azure Key Vault में हैं; keys साल में एक बार rotate होती हैं।"

**Partial और planned।** बाकी के लिए explanation और तारीख़ के साथ "Partially" चलता है; झूठा "Yes" नहीं चलता।

**AI section.** वो जवाब तैयार रखो जो बार-बार पूछे जाएँगे:

- कौन-से model providers और regions use होते हैं, और किन terms पर (data पर training, retention)?
- Model को कौन-सा data भेजा जाता है, और क्या personal data mask होता है?
- Prompt injection कैसे handle होता है, और क्या risky actions के outputs लोग review करते हैं?
- कौन-से guardrails, audit logs और kill switches हैं?
- Release से पहले model या prompt बदलाव कैसे test होते हैं?

**Sub-processors.** हर उस third party को list करो जो client data को छूता है (cloud, model provider, tracing tool, email service), purpose और location के साथ। Clients को अक्सर नए sub-processors पर आपत्ति करने का हक़ होता है।

**Evidence और NDAs.** पूरी SOC 2 report जैसा sensitive evidence non-disclosure agreement के तहत, expire होने वाले secure link से share करो।

**कमज़ोर और मज़बूत answers:**

| सवाल | कमज़ोर | मज़बूत |
| --- | --- | --- |
| Rest पर encryption? | "Yes" | "AES-256, keys Central India में Azure Key Vault में; साल में एक बार rotate" |
| क्या data training के लिए use होता है? | "No" | "Provider X का contract client data पर training को बाहर रखता है; retention 30 दिन; clause 7.2 attached" |
| Prompt injection? | "हम industry-standard AI security use करते हैं" | "Least-privilege tools, outbound actions के लिए approval, CI में injection test set; ताज़ा results attached" |
| Pen testing? | "Yes" | "Web app का सालाना external test; अगले महीने book हुए test में AI endpoints जोड़े गए हैं" |

**Library को ज़िंदा रखना।** हर answer को एक owner दो, आमतौर पर वो व्यक्ति जो वो control चलाता है, और एक review date। जब architecture बदले, जैसे नया model provider या नया tracing tool, तो library में प्रभावित answers खोजो और उसी हफ़्ते update करो। हर questionnaire के बाद नए सवाल और उनके reviewed answers जोड़ दो। ऐसे maintain की गई library दो हफ़्ते की भागदौड़ को कुछ दिनों के focused काम में बदल देती है।

**Client के reviewers के साथ काम करना।** Follow-up calls की उम्मीद रखो। उस engineer को साथ लाओ जो system जानता है, data flow map और evidence भी। सिर्फ़ वही जवाब दो जो आपको पता है, जो check करना हो उसे लिख लो, और उसी दिन भेजो। Reviewers उन vendors पर कहीं ज़्यादा भरोसा करते हैं जो कहते हैं "ये हम अभी नहीं करते, और plan ये है", बजाय उनके जो सब कुछ करने का दावा करते हैं।

**Answer library को data की तरह रखना।** Answers को एक file में रखो जिसे team code की तरह review करे, और bookkeeping एक script करे:

```yaml
# security-answers.yaml
- id: enc-at-rest
  question: Is customer data encrypted at rest?
  answer: >
    Yes. Postgres and object storage use AES-256 with keys in Azure Key Vault (Central India), rotated yearly.
  owner: platform-lead
  evidence: [docs/architecture.pdf#storage, key-vault-policy.pdf]
  reviewed: 2026-09-14
  tags: [encryption, storage]
- id: ai-training
  question: Is our data used to train AI models?
  answer: >
    No. Our model provider's enterprise terms exclude training on API data; retention is 30 days for abuse
    monitoring (terms version and clause attached).
  owner: cto
  evidence: [provider-terms-2026-07.pdf]
  reviewed: 2026-07-30
  tags: [ai, vendor]
```

```python
import yaml
from datetime import date, timedelta

def load(path="security-answers.yaml"):
    return yaml.safe_load(open(path))

def stale(answers, max_age_days=180):
    cutoff = date.today() - timedelta(days=max_age_days)
    return [(a["id"], a["owner"]) for a in answers if a["reviewed"] < cutoff or not a.get("evidence")]

def suggest(question, answers, top=3):
    words = set(question.lower().split())
    scored = sorted(answers, key=lambda a: -len(words & set((a["question"] + " " + " ".join(a["tags"])).lower().split())))
    return [a["id"] for a in scored[:top]]
```

`stale` को हर महीने चलाओ और हर owner को उसकी list भेजो। नए questionnaire के लिए candidate answers खोजने में `suggest` (या बड़ी libraries के लिए embeddings) use करो, लेकिन भेजने से पहले हर answer किसी इंसान से check करवाओ: model या keyword match ऐसा answer चुन सकता है जो क़रीब है पर गलत है।

**AI से draft करना, सावधानी से।** Model आपकी library और architecture notes से answers draft कर सकता है, जो लंबे questionnaires में समय बचाता है। नियम: वो सिर्फ़ library और attach किए documents use कर सकता है, हर draft उन library ids को cite करता है जो उसने use किए, और एक नामित व्यक्ति हर answer को approve करता है। Model को कभी ऐसा control गढ़ने मत दो जो आपके पास नहीं है।

**AI section, current रखा हुआ।** अपने model providers को list करो, terms जाँचने की तारीख़ के साथ, use हो रहे regions, कौन-सा data भेजा जाता है और क्या वो masked है, guardrails और उनके test results, kill switches, prompt और model बदलाव कैसे test होते हैं, और sub-processor list। इसमें कुछ भी बदले तो उसी हफ़्ते ये section update करो।

**वो evidence जो पुराना नहीं पड़ता।** ऐसे text को paste करने की जगह जो बासी हो जाता है, living documents (मौजूदा architecture diagram, ताज़ा eval और penetration test summaries) के links दो। Injection tests और permission tests के CI results को एक छोटे PDF के रूप में export करने लायक रखो, क्योंकि AI-specific evidence वही है जो reviewers ने सबसे कम देखा होता है।

## एक example से समझो

Bengaluru का एक AI startup, एक बड़े private bank के साथ सफल pilot के बाद, दो हफ़्ते की deadline के साथ 240 सवालों वाली spreadsheet पाता है। FDE Meera coordinate करती है।

वो answer library से शुरू करती है, जो 170 सवाल cover करती है। बाकी में से 40 AI-specific हैं और 30 bank-specific (जैसे RBI की outsourcing guidelines और data localisation)।

AI सवालों के लिए वो system के असली design documents use करती है: data flow map, gateway configuration (सिर्फ़ Indian region, model provider data पर train न करने के लिए contract से बँधा), masking rules, test results के साथ guardrail list, customer-facing messages के लिए human approval step, और audit log schema। हर answer संबंधित document section को cite करता है।

दो सवाल असली gaps दिखाते हैं: AI endpoints का कोई औपचारिक सालाना penetration test नहीं, और model के गड़बड़ करने के लिए कोई documented incident plan नहीं। दोनों के लिए वो "Partially" कहती है, अगले महीने के लिए book एक external penetration test और attach की गई एक draft incident runbook के साथ। Bank की security team शर्तों के साथ plan मान लेती है, और contract सामान्य तीन महीने की जगह चार हफ़्तों में आगे बढ़ जाता है।

| Questionnaire का हिस्सा | गिनती | कैसे handle हुआ |
| --- | --- | --- |
| Library से answer | 170 | Checks के साथ दोबारा use |
| AI-specific | 40 | Design documents से, citations के साथ जवाब |
| Bank-specific | 30 | Legal के साथ draft |
| Gaps | 2 | Book हुए pen test और draft runbook के साथ "Partially" |
| Outcome | | तीन महीने की जगह चार हफ़्तों में contract |

## आम गलतियाँ

- **Overclaim करना।** झूठा "Yes" बाद में legal समस्या बन सकता है। "Partially" कहो और समझाओ।
- **हर बार शुरू से शुरू करना।** Owners और dates के साथ answer library maintain करो।
- **अस्पष्ट AI answers।** "हम industry-standard AI security use करते हैं" का कोई मतलब नहीं है। Providers, regions, terms और controls के नाम बताओ।
- **Sub-processors भूल जाना।** जो tracing या email tool client data देखता है, वो भी गिना जाता है।
- **Library को बासी होने देना।** पिछले साल के architecture के answers गलत answers हैं।
- **बिना owner या review date वाले answers।** उनके पुराने पड़ने पर किसी का ध्यान नहीं जाता।
- **हर AI-drafted answer को किसी इंसान से check करवाए बिना भेजना।**
- **नए sub-processors भूल जाना**, जैसे पिछले महीने जोड़ा गया कोई tracing tool।

## जब पूरी library ज़रूरत से ज़्यादा हो

- **आपके पहले एक-दो questionnaires**: उनका जवाब ध्यान से दो, फिर उन answers को library में बदल दो।
- **छोटे clients** जो email पर कुछ सवाल पूछते हैं: उसी सटीकता से सीधे जवाब दो।
- **Internal projects** जो company की अपनी security review process में आते हैं।

## Demo से production तक

- **Library को version control में रखो**, owners, dates और evidence links के साथ।
- **बासी answers को हर महीने और हर architecture बदलाव पर flag करो।**
- **Sub-processor list maintain करो**, हर एक के purpose और location के साथ।
- **AI test results export करो** (injection, permissions, guardrails), evidence के रूप में।
- **हर questionnaire को track करो**: उसकी तारीख़, भेजे गए answers का version और किए गए follow-up वादे।
