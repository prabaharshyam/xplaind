## ये क्या है

लगभग सारे software काम के नीचे दो tools होते हैं:

- **Terminal** (इसे shell या command line भी कहते हैं) एक window है जहाँ आप click करने की जगह commands type करते हो। इसी से आप folders के बीच जाते हो, programs चलाते हो, packages install करते हो और Git जैसे tools use करते हो।
- **Git** एक version control system है। ये आपके project के snapshots record करता है, जिन्हें **commits** कहते हैं, ताकि आप देख सको कि क्या बदला, गलतियाँ undo कर सको और code share कर सको। **GitHub** एक website है जो Git repositories की copies online रखती है, ताकि दूसरे उन्हें देख सकें और आपके साथ काम कर सकें। Git, GitHub के बिना भी चलता है; GitHub तो बस आपकी history भेजने की एक जगह है।

Git लगभग हर जगह है: Stack Overflow के 2022 developer survey में 93% developers ने कहा कि वो इसे use करते हैं। Course material, take-home tasks और आपकी पहली team का code लगभग हमेशा एक Git repository के रूप में ही आएगा।

वो एक idea जो Git को आसान बना देता है: आपके changes चार जगहों में से किसी एक में रहते हैं, और हर command उन्हें एक जगह से अगली जगह ले जाती है।

```flow
title: आपके changes कहाँ रहते हैं
dir: LR
Working folder | वो files जिन्हें आप edit करते हो -[git add]-> Staging area | अगले commit में क्या होगा
Staging area -[git commit]-> Local repository | आपके commits की history
Local repository -[git push]-> GitHub | online shared copy
GitHub -[git clone, git pull]-> Working folder
```

Git में ज़्यादातर confusion इसी से आता है कि पता नहीं होता कोई change किस जगह पर है। `git status` ये बताता है, इसलिए हर दूसरी Git command से पहले और बाद में इसे चलाओ।

ये lesson Nagpur में Python सीख रहे Ravi के साथ चलता है, जो exercise scripts के एक folder को public repository बनाता है। इसका check आपका अपना एक छोटा project है, जिसे आख़िर में दिए rubric से mark किया जाता है।

## ये काम कैसे करता है

### Terminal basics

**पहले अपना terminal चुनो।** Mac पर Terminal app खोलो। Linux पर कोई भी terminal चलेगा। Windows पर Git for Windows install करो, जिसके साथ **Git Bash** आता है, और इस course के लिए Git Bash (या WSL, यानी Windows के अंदर Linux) use करो, ताकि हर command वैसे ही चले जैसे लिखी है। PowerShell भी `pwd`, `ls` और `cd` समझता है; पुराना Command Prompt अलग commands use करता है, जैसे `ls` की जगह `dir`।

| Command | ये क्या करता है |
| --- | --- |
| `pwd` | वो folder print करता है जिसमें आप हो |
| `ls` | इस folder की files की list देता है |
| `ls -a` | Hidden files भी दिखाता है, जिनके नाम dot से शुरू होते हैं, जैसे `.gitignore` और `.env` |
| `cd python-practice` | एक folder के अंदर जाता है |
| `cd ..` | एक folder ऊपर जाता है |
| `cd ~` | आपके home folder में जाता है |
| `mkdir python-practice` | एक नया folder बनाता है |
| `python expenses.py` | एक program चलाता है (कुछ Mac और Linux machines पर `python3`) |

**Paths.** Absolute path disk के सबसे ऊपर से शुरू होता है, जैसे `/home/ravi/python-practice` (Git Bash में C drive `/c` है, इसलिए Windows का home folder `/c/Users/Ravi` जैसा दिखता है)। Relative path वहाँ से शुरू होता है जहाँ आप अभी हो: `python-practice` तभी चलेगा जब वो folder मौजूदा folder के अंदर हो। जब "No such file or directory" दिखे, तो लगभग हमेशा आप गलत folder में हो: कुछ भी और करने से पहले `pwd` और `ls` चलाओ। Folder के नामों में spaces मत रखो; अगर किसी में हैं, तो उसे quotes में लिखो, जैसे `cd "My Projects"`।

**Environment variables** नाम वाली values हैं जो terminal अपने शुरू किए हर program को देता है। `echo $HOME` एक को print करता है। `export CITY=Nagpur` एक set करता है, पर सिर्फ़ उसी terminal window के लिए; window बंद की और value गई। इसीलिए projects API keys को एक `.env` file में रखते हैं जिसे program पढ़ता है, और ठीक यही वो file है जो कभी Git तक नहीं पहुँचनी चाहिए।

तीन keys घंटों बचाती हैं: **up arrow** पिछली commands वापस लाता है, **Tab** file और folder के नाम पूरे कर देता है (और typos से बचाता है), और **Ctrl+C** चल रहे या अटके हुए program को रोक देता है।

### Git को एक बार set up करो

Check करो कि Git install है, फिर उसे बताओ कि आप कौन हो:

```bash
git --version
git config --global user.name "Ravi Deshmukh"
git config --global user.email "12345678+ravi-d@users.noreply.github.com"
git config --global init.defaultBranch main
```

आपका नाम और email हर commit पर लग जाते हैं, और push करने के बाद कोई भी उन्हें पढ़ सकता है। अगर आप अपना personal email public नहीं करना चाहते, तो GitHub आपको एक private "noreply" address देता है: GitHub की email settings में "Keep my email address private" tick करो और जो address दिखे उसे copy करो। ऊपर वाला बस उसकी shape का एक example है।

आख़िरी line पहली branch का नाम `main` रखती है, जो नाम GitHub use करता है। इसके बिना, कुछ Git versions पहली branch को `master` कहते हैं और उसके बारे में एक लंबा hint print करते हैं।

### रोज़ का loop: status, add, commit

```bash
cd python-practice
git init                  # once per project: start tracking this folder
git status                # which files are new, changed or staged?
git add expenses.py       # stage this file for the next commit
git commit -m "Add expense tracker with category totals"
git log --oneline         # one line per commit, newest first
```

`git add` changes को **staging area** में रखता है, और `git commit` जो कुछ staged है उसे एक snapshot के रूप में save करता है। दो steps इसलिए हैं ताकि एक commit में एक ही idea हो। अगर आपने एक bug fix किया और साथ में एक नया feature भी शुरू कर दिया, तो सिर्फ़ bug fix stage करो, उसे commit करो, और आधा बना feature बाद के लिए रखो।

`git add .` folder की वो हर चीज़ stage करता है जिसे ignore करने को Git से नहीं कहा गया। ये तेज़ है, और secrets और कचरा commit होने का तरीका भी यही है, इसलिए पहले `git status` चलाओ और list पढ़ो। `git diff` वो changes दिखाता है जो अभी stage नहीं हुए; `git diff --staged` दिखाता है कि क्या commit होने वाला है।

### Commit messages जो काम आएँ

| कमज़ोर | मज़बूत |
| --- | --- |
| "update" | "Add expense totals by category" |
| "fixed stuff" | "Handle missing amounts in expense CSV" |
| "final" | "Add README with usage examples" |

जो rules मायने रखते हैं:

- **Verb से शुरू करो, एक instruction की तरह:** "Add", "Fix", "Handle", "Remove"। एक काम का test: message को ये sentence पूरा करना चाहिए, "If applied, this commit will..."।
- **एक commit में एक change।** अगर उसे बताने के लिए "and" लगाना पड़े, तो शायद वो दो commits हैं।
- **पहली line छोटी रखो।** एक आम convention करीब 50 characters की है। अगर "क्यों" समझाना है, तो एक blank line छोड़ो और उसके नीचे और लिखो।
- **तब commit करो जब code चलता हो।** तब आपकी history का हर commit वापस जाने के लिए एक safe point होता है।

### Secrets और कचरे को बाहर रखो: .gitignore

Project के top folder में `.gitignore` नाम की एक file उन चीज़ों की list रखती है जिन्हें Git को कभी track नहीं करना चाहिए:

```text
.venv/
__pycache__/
.env
```

`.venv/` आपका virtual environment है (बड़ा, और `requirements.txt` से दोबारा बन जाता है), `__pycache__/` Python का cache है, और `.env` में keys हैं। सबसे ज़्यादा मायने `.env` वाली line रखती है।

वो rule जो beginners से छूट जाता है: **`.gitignore` सिर्फ़ उन files पर असर करता है जिन्हें Git अभी track नहीं कर रहा।** अगर `.env` पहले से किसी commit में है, तो बाद में उसे `.gitignore` में डालने से कुछ नहीं बदलता, और `git status` उसे दिखाता रहता है। उसे track करना ऐसे बंद करो:

```bash
git rm --cached .env      # stop tracking; the file stays on your disk
git commit -m "Stop tracking .env"
```

इससे वो सिर्फ़ आगे के commits से हटती है। पुराने commit में key अब भी है, और जो भी repository देख सकता है वो उसे पढ़ सकता है। इसलिए key को leak हुआ मानो: provider की website पर उसे revoke करो और नई बनाओ। File delete करना काफ़ी नहीं है।

GitHub एक safety net जोड़ता है। Public repositories पर ये personal accounts के लिए default रूप से **push protection** चालू करता है, जो ऐसे push को रोक देता है जिसमें उसकी पहचानी हुई format का secret हो, जैसे कई cloud और AI provider keys। ये हर secret नहीं पहचान सकता, जैसे आपका खुद बनाया कोई password, इसलिए असली बचाव है अपने पहले `git add` से पहले `.gitignore` बनाना।

### Commit बनने से पहले undo करो

| Situation | Command |
| --- | --- |
| देखो क्या बदला है जो stage नहीं हुआ | `git diff` |
| देखो अगले commit के लिए क्या staged है | `git diff --staged` |
| एक file में किए अपने edits फेंक दो | `git restore expenses.py` |
| File को unstage करो पर edits रखो | `git restore --staged expenses.py` |
| कोई पुराना commit देखो | `git log --oneline`, फिर `git show a7d7b78` |

`git restore expenses.py` से सावधान रहो: ये आख़िरी committed version वापस लाता है, और जो edits आप फेंकते हो वो हमेशा के लिए चले जाते हैं, क्योंकि Git ने उन्हें कभी save ही नहीं किया। किसी commit को undo करना, उसे भी जो आप push कर चुके हो, Git में चीज़ें undo करने वाले lesson का topic है।

### GitHub पर push करो, ऐसे sign-in के साथ जो चले

GitHub पर **New repository** click करो, उसका नाम `python-practice` रखो, और README, .gitignore और licence वाले options off छोड़ दो, ताकि repository खाली शुरू हो। फिर अपने folder को उससे जोड़ो और push करो:

```bash
git remote add origin https://github.com/ravi-d/python-practice.git
git push -u origin main
```

`origin` आपकी GitHub copy का आम निकनेम है। `-u` आपकी `main` को उससे जोड़ देता है, ताकि उसके बाद सिर्फ़ `git push` और `git pull` चल जाएँ।

**ज़्यादातर beginners sign in पर ही अटकते हैं।** 13 August 2021 से GitHub, Git commands के लिए आपका account password नहीं लेता। अगर terminal username और password माँगे और आप अपना GitHub password type करो, तो push fail हो जाता है। इसकी जगह इनमें से एक चुनो:

| आपका setup | क्या करना है |
| --- | --- |
| Git for Windows वाला Windows | Git Credential Manager इसके साथ आता है। पहले push पर एक sign-in window खुलती है; browser चुनो, GitHub में sign in करो, और ये आपको याद रखता है। |
| Mac या Linux | GitHub CLI install करो और `gh auth login` चलाओ। GitHub.com और HTTPS चुनो, अपने GitHub credentials से Git को authenticate करने के लिए yes कहो, और browser में पूरा करो। |
| और कुछ भी | एक fine-grained personal access token बनाओ (GitHub Settings, फिर Developer settings) जिसमें इस repository के Contents का read और write access हो, और जहाँ terminal password माँगे वहाँ उसे paste करो। इसे password की तरह ही संभालो। |

SSH keys एक और option है; Linux, shell और SSH वाला lesson उन्हें cover करता है।

**एक और trap।** अगर आपने GitHub पर "Add a README" tick कर दिया था, तो आपका पहला push refuse हो जाता है, क्योंकि GitHub के पास एक ऐसा commit है जो आपके computer पर नहीं है:

```text
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ravi-d/python-practice.git'
```

नई repository के लिए सबसे आसान fix है उसे GitHub पर delete करना (उसका Settings page, सबसे नीचे), फिर से खाली बनाना और push करना। पहले `git pull` चलाने से मदद नहीं मिलती: Git "refusing to merge unrelated histories" कहकर रुक जाता है।

### दूसरों के साथ काम करना: पहली झलक

Team का काम और take-home tasks उल्टी तरफ़ से शुरू होते हैं: repository पहले से GitHub पर होती है।

```bash
git clone https://github.com/example-team/expense-app.git
cd expense-app
git pull                          # bring in teammates' new commits
git switch -c add-monthly-report  # a new branch for your change
# edit files, then git add and git commit
git push -u origin add-monthly-report
```

**Branch** commits की एक अलग line है, ताकि आपका change तैयार होने तक `main` को न छुए। Branch push करने के बाद आप GitHub पर एक **pull request** खोलते हो: एक page जो आपके changes दिखाता है ताकि `main` में merge होने से पहले कोई teammate उन्हें review कर सके।

अगर आप और कोई teammate एक ही lines बदलते हो, तो Git आप दोनों में से चुन नहीं सकता। वो एक **merge conflict** के साथ रुक जाता है और file पर निशान लगा देता है:

```text
<<<<<<< HEAD
print(sorted(totals.items()))
=======
print("Totals:", totals)
>>>>>>> 3c1dea94b5893015fb3b508cd578f48b684bd511
```

`=======` के ऊपर वाला हिस्सा आपका version है; नीचे वाला आने वाला version है। File को उस version में edit करो जो आपको चाहिए, तीनों marker lines delete करो, फिर file को `git add` करो और Git का message रखने के लिए `git commit --no-edit` चलाओ। अगर `git pull` "Need to specify how to reconcile divergent branches" कहकर रुक जाए, तो आप दोनों ने commits किए हैं; `git pull --no-rebase --no-edit` उन्हें merge कर देता है। Branches वाले और team के साथ Git वाले lessons इसमें और गहराई तक जाते हैं।

## एक example से समझो

Ravi के पास एक folder है जिसमें एक expense tracker, एक marks calculator और एक weather fetcher है जो `.env` से API key पढ़ता है। ये रहा उसका असली session, output छोटा करके। आपके commit hashes (`81d3fe3` जैसे छोटे codes) अलग होंगे।

**1. Tracking शुरू करो, और कुछ भी add करने से पहले देखो।**

```text
$ cd ~/python-practice
$ git init
Initialized empty Git repository in /home/ravi/python-practice/.git/
$ git status
On branch main

No commits yet

Untracked files:
	.env
	.venv/
	__pycache__/
	expenses.py
	marks.py
	weather.py
```

ख़तरा `.env` वाली line है: अभी एक `git add .` उसकी key commit कर देगा।

**2. `.gitignore` बनाओ और फिर से check करो।**

```text
$ printf '.venv/\n__pycache__/\n.env\n' > .gitignore
$ git status --short
?? .gitignore
?? expenses.py
?? marks.py
?? weather.py
```

`??` का मतलब untracked है। `.env`, `.venv/` और `__pycache__/` list से गायब हो गए हैं, यही सबूत है कि ignore file काम कर रही है।

**3. पहला commit: एक script, साथ में ignore file।**

```text
$ git add .gitignore expenses.py
$ git commit -m "Add expense tracker with category totals"
[main (root-commit) 81d3fe3] Add expense tracker with category totals
 2 files changed, 9 insertions(+)
```

**4. Bug fix, अपने अलग commit में।** उसकी CSV में एक खाली amount से tracker crash हो गया। वो line ठीक करता है, फिर check करता है कि उसने ठीक-ठीक क्या बदला:

```text
$ git diff
-        totals[row["category"]] = totals.get(row["category"], 0) + float(row["amount"])
+        totals[row["category"]] = totals.get(row["category"], 0) + float(row["amount"] or 0)
$ git add expenses.py
$ git commit -m "Handle missing amounts in expense CSV"
```

**5. बाकी scripts और एक README, हर एक का अपना commit।** उसका README:

```markdown
# Python practice
Small scripts from my first month of learning Python.

- expenses.py: reads expenses.csv and prints total spending per category
- marks.py: turns a list of marks into grades
- weather.py: prints today's weather for a city; needs WEATHER_API_KEY in a .env file

Run any script with: python expenses.py
```

```text
$ git log --oneline
e2c538a Add README with usage examples
cf4559b Add weather fetcher that reads its key from .env
812980e Add marks calculator with grade bands
a7d7b78 Handle missing amounts in expense CSV
81d3fe3 Add expense tracker with category totals
```

**6. Push।** वो GitHub पर एक खाली repository बनाता है, अपने Ubuntu laptop पर एक बार `gh auth login` चलाता है, फिर:

```text
$ git remote add origin https://github.com/ravi-d/python-practice.git
$ git push -u origin main
To https://github.com/ravi-d/python-practice.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

**7. एक गलती, undo हो गई।** एक हफ़्ते बाद वो एक line जोड़ता है जो tracker को crash कर देती है। कुछ भी commit करने से पहले:

```text
$ git status --short
 M expenses.py
$ git diff
+print(totals["food"])
$ git restore expenses.py
$ git status --short
```

`M` का मतलब modified है। `git restore` के बाद `git status` कुछ print नहीं करता: file फिर से उसके आख़िरी commit से match करती है।

**8. आख़िरी check।** `git log --all --oneline -- .env` हर उस commit की list देता है जिसने कभी `.env` को छुआ हो। Ravi के लिए ये कुछ print नहीं करता, यानी उसकी key कभी उसकी history में थी ही नहीं।

अब जो भी उसकी repository खोलता है, चाहे reviewer हो या interviewer, एक मिनट में तीन चीज़ें देखता है: एक README जो बताता है कि हर script कैसे चलानी है, छोटे और साफ़ नाम वाले steps की history, और कोई `.env`, `.venv/` या cache files नहीं।

## आम गलतियाँ

- **गलत folder में Git चलाना।** "fatal: not a git repository" का मतलब है आप project के बाहर हो; अपने home folder में `git init` चलाया तो `git status` आपकी हर file की list दिखाएगा। पहले `pwd` चलाओ।
- **Push prompt पर अपना GitHub password type करना।** ये reject हो जाता है। Git Credential Manager, `gh auth login` या personal access token use करो।
- **`.env` commit होने के बाद `.gitignore` जोड़ना।** Tracked files पर इसका कोई असर नहीं होता। `git rm --cached .env` use करो, commit करो, और key बदल दो।
- **`git status` पढ़े बिना `git add .`।** Keys, `.venv/` और बड़ी data files ऐसे ही commit होती हैं।
- **नई GitHub repository पर "Add a README" tick करना** और फिर एक मौजूदा folder push करना। Push refuse हो जाता है। नई repositories खाली बनाओ।
- **एक बड़ा-सा commit, या "update" जैसे messages।** हर पूरा हुआ step commit करो, और बताओ कि वो क्या बदलता है।
- **उन edits पर `git restore` जो आपको रखने थे।** वो edits वापस नहीं मिल सकते। पहले `git diff` check करो।
