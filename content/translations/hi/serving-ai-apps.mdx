## ये क्या है

Serving का मतलब है अपनी application को ऐसे चलाना कि real users उस पर भरोसा कर सकें। वो अपने-आप start होती है, crash होने पर restart होती है, एक साथ कई requests संभालती है, extra load को साफ़ तरीके से मना करती है, और model धीमा हो तब भी जल्दी कुछ दिखा देती है।

एक Python AI service के लिए आम stack है app के लिए FastAPI और उसे चलाने वाले server के रूप में **Uvicorn**, कई worker processes के साथ। HTTPS संभालने और traffic बाँटने के लिए आगे कुछ बैठा होता है, जैसे एक load balancer, एक ingress, या Cloud Run जैसा कोई platform।

AI services एक आम web API से तीन तरह से अलग हैं। Requests धीमी होती हैं, अक्सर 2 से 30 seconds, क्योंकि वो model calls का इंतज़ार करती हैं। Users इसे तभी झेलते हैं जब उन्हें progress दिखे, इसीलिए **streaming** ज़रूरी है। और जो resource कम है वो किसी और का है: provider आपकी requests और tokens प्रति मिनट limit करता है, इसलिए आमतौर पर bottleneck आपका CPU नहीं, उसका quota और आपका bill होता है।

```flow
Users -[HTTPS]-> Load balancer | idle timeout 30 s, ready instances को भेजता है
Load balancer -> Container 1 | 4 Uvicorn workers, हर एक में ज़्यादा से ज़्यादा 40 model calls
Load balancer -> Container 2 | वैसा ही
Container 1 -[deadline 25 s, retries inside]-> Model API | tokens user तक stream होकर आते हैं
Container 1 -> Background queue | OCR और indexing; एक job id return करती है
```

इस lesson में हम लखनऊ की एक edtech company के doubt-solving assistant के साथ चलेंगे, जो हर शाम रेंगने लगता था।

## ये काम कैसे करता है

### Workers और event loop

एक Uvicorn process अपने async endpoints एक ही **event loop** पर चलाता है। जब एक request model का await कर रही होती है, loop बाकी requests को serve करता है, इसलिए एक process सैकड़ों इंतज़ार करती requests संभाल सकता है। लेकिन जो भी चीज़ loop को block करे, वो उस process की हर request को freeze कर देती है: एक synchronous Redis, database या `requests` call, PDF parsing, एक local embedding model।

इलाज: network calls के लिए एक **async client** use करो; या endpoint को एक सादा `def` लिखो, जिसे FastAPI एक thread pool में चलाता है; या भारी काम को एक **background queue** पर ले जाओ। फिर कई workers चलाओ, आमतौर पर हर CPU core पर एक या दो, ताकि एक crash सब कुछ न गिरा दे। जो service ज़्यादातर किसी model API का इंतज़ार करती है, उसके लिए workers जोड़ने से ज़्यादा blocking calls हटाना मदद करता है।

### Layers में timeouts

हर wait की एक limit चाहिए, अंदर वाली बाहर वाली से छोटी, वरना बाहर वाली पहले fire होगी और user को आपके message की जगह एक खाली load balancer error मिलेगा। एक **total** timeout पूरी request पर cap लगाता है। एक **idle** timeout चुप्पी पर cap लगाता है, इसलिए जो stream भेजती रहे वो कभी नहीं कटती; उदाहरण के लिए, AWS Application Load Balancer default रूप से 60-second idle timeout use करता है।

Official Anthropic Python SDK में एक जाल है। उसका `timeout` connect करने पर और अगले chunk के हर wait पर, हर attempt के लिए अलग से लगता है; ये total deadline नहीं है। ये default रूप से 429s और server errors को दो बार retry भी करता है, और उतना इंतज़ार करता है जितना provider का `retry-after` header कहे। इसलिए `timeout=30, max_retries=2` एक request को 90 seconds से काफ़ी आगे तक रोक सकता है। पूरी call के चारों ओर अपनी एक deadline रखो, retries उसके अंदर।

| Layer | किस तरह का | Example value | ये क्या पकड़ता है |
| --- | --- | --- | --- |
| SDK `timeout` | हर attempt, हर chunk पर | 10 s | एक dead connection या रुकी हुई stream |
| SDK `max_retries` | गिनती | 1 | Provider की एक छोटी error; उसी budget में से खर्च होता है |
| आपकी deadline | Total, retries समेत | 25 s | ऊपर का सब कुछ, आपके लिखे message के साथ |
| Load balancer | आमतौर पर idle | 30 s | एक लटका हुआ instance; layers सही हों तो कभी पहले fire नहीं होता |
| Shutdown grace | Total | 30 s server, 40 s platform | Deploy के दौरान कटती streams |

### Streaming, और उसे क्या तोड़ता है

**Server-sent events** (SSE) में server response को खुला रखता है और हर टुकड़ा एक `data:` line के रूप में भेजता है। Version 0.135.0 से FastAPI इसे सीधे support करता है: `response_class=EventSourceResponse` set करो और endpoint से `yield` करो। FastAPI हर item को JSON के रूप में encode करता है, इसलिए answer में एक newline format को नहीं तोड़ सकती। ये `Cache-Control: no-cache` और `X-Accel-Buffering: no` (nginx के लिए एक hint) set करता है, और 15 seconds चुप्पी के बाद एक keep-alive comment भेजता है।

Streaming generation को तेज़ नहीं करती; ये इंतज़ार को छोटा महसूस कराती है, क्योंकि पहले शब्द एक-दो second में आ जाते हैं। दिक्कतें सिर्फ़ production में दिखती हैं:

- **Buffering proxies।** कोई ingress, proxy या compression layer पूरा response रोक कर रख सकती है, तो users को पहले कुछ नहीं दिखता और फिर सब एक साथ। nginx default रूप से proxied responses को buffer करता है, और सिर्फ़ header हमेशा काफ़ी नहीं होता। उस route के लिए buffering off करो (nginx में `proxy_buffering off;`) और real path से test करो।
- **Idle timeouts।** एक लंबी चुप्पी, जैसे जब model एक लंबा prompt पढ़ रहा हो, balancer को trip कर सकती है। Keep-alive comments उसके idle timeout से ज़्यादा बार आने चाहिए।
- **Browser में POST।** `EventSource` request body नहीं भेज सकता; POST stream को `fetch` और एक stream reader से पढ़ो।
- **बीच में failure।** एक 200 और आधे answer के बाद status code नहीं बदल सकता। एक error event भेजो, आधा text "answer interrupted, try again" के साथ दिखाओ, और उसे कभी cache मत करो। इन्हें अपने logs में गिनो, क्योंकि status-code dashboards इन्हें miss कर देते हैं।
- **Disconnects।** जब tab बंद होता है, FastAPI generator को cancel करता है और SDK का `async with` model stream को बंद कर देता है, तो बिना पढ़े tokens के पैसे देना बंद हो जाता है।

### Endpoint

Load shed करने वाला एक concurrency cap, model call के चारों ओर एक deadline, JSON events और पढ़ने लायक errors। API के एक local fake के against FastAPI 0.165, Anthropic SDK 2.14 और Python 3.13 के साथ test किया गया; इसके लिए FastAPI 0.135.0 या उसके बाद का और Python 3.11 या उसके बाद का चाहिए।

```python
import asyncio
import anthropic
from fastapi import Depends, FastAPI, HTTPException
from fastapi.sse import EventSourceResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=10, max_retries=1)   # per attempt, per chunk
SLOTS = asyncio.Semaphore(40)      # at most 40 model calls at once in this process
MODEL_DEADLINE = 25                # seconds for the whole model call, retries included

class Question(BaseModel):
    text: str

async def model_slot():
    try:                                         # wait at most 1 s for a free slot
        await asyncio.wait_for(SLOTS.acquire(), timeout=1)
    except TimeoutError:
        raise HTTPException(429, "Busy, please try again in a few seconds",
                            headers={"Retry-After": "5"})
    try:
        yield                                    # the request streams here
    finally:
        SLOTS.release()                          # after the stream ends, even on disconnect

async def with_deadline(chunks, seconds):
    loop = asyncio.get_running_loop()
    end = loop.time() + seconds
    it = aiter(chunks)
    while True:
        try:
            yield await asyncio.wait_for(anext(it), end - loop.time())
        except StopAsyncIteration:
            return

async def model_text(question: str):
    async with client.messages.stream(
            model="claude-sonnet-5-5", max_tokens=600,      # check the docs for current names
            messages=[{"role": "user", "content": question}]) as stream:
        async for text in stream.text_stream:
            yield text

@app.post("/answer", response_class=EventSourceResponse)
async def answer(body: Question, _: None = Depends(model_slot)):
    try:
        async for text in with_deadline(model_text(body.text), MODEL_DEADLINE):
            yield {"text": text}
        yield {"done": True}
    except TimeoutError:
        yield {"error": "This is taking longer than usual. Please try again."}
    except anthropic.APIError:
        yield {"error": "The AI service is busy. Please try again."}

@app.get("/health")
async def health():
    return {"ok": True}
```

इसे ऐसा क्यों बनाया गया है:

- **Slot response शुरू होने से पहले लिया जाता है**, एक dependency में, क्योंकि 200 जाने के बाद 429 भेजना नामुमकिन है। एक second का wait छोटे bursts को सोख लेता है; उससे आगे, एक चुप queue से एक तेज़ "busy" बेहतर है। Stream खत्म होने पर, disconnect पर भी, `finally` slot वापस कर देता है।
- **Deadline हर wait को लपेटती है, yield को नहीं।** `with_deadline` हर step को, retries के साथ stream खोलने समेत, एक ही end time के against time करता है। किसी `yield` के चारों ओर timeout block async generators में गड़बड़ करता है।
- **Cap हर process का अलग है**: 40 slots, 4 workers और 2 containers मतलब एक साथ 320 calls।

### Rate limits: आपकी और provider की

शाम के peak पर provider का 429 सबसे आम failure है। Backoff और **jitter** (wait का एक random हिस्सा, ताकि हज़ारों clients एक ही पल में retry न करें) के साथ थोड़ी देर retry करो; SDK ये करता है और `retry-after` को मानता है, तो गिनती इतनी कम रखो कि deadline में फ़िट हो। फिर साफ़ तरीके से fail करो, या एक gateway के ज़रिए किसी दूसरे region या approved छोटे model पर fallback करो (LLM gateways वाला lesson देखो)। **हर user को भी limit करो**, जैसे 10 मिनट में 20 सवाल और एक daily token cap, वरना एक script सबका quota खत्म कर सकती है और आपके bill की कोई सीमा नहीं रहेगी। आपके अपने 429 में `Retry-After` होता है, और आपके front end को उसे मानना चाहिए।

### Health, readiness और shutdown

- **`/health`** (liveness) बताता है कि process ज़िंदा है और किसी और चीज़ को नहीं छूता, ताकि platform सिर्फ़ उन्हीं processes को restart करे जो सच में अटके हैं।
- **`/ready`** (readiness) बताता है कि ये instance traffic ले सकता है: start-up का काम, जैसे index load करना, पूरा होने तक 503. इसे किसी shared dependency पर fail मत करो। अगर हर instance एक ही database check करे, तो एक blip सबको एक साथ fail कर देती है और balancer सबको हटा देता है, जिससे partial outage total outage बन जाता है। हर request पर एक साफ़ error return करो और अलग से alert करो।
- **दोनों में से कोई model को call नहीं करता।** इसमें पैसे लगते हैं, और एक धीमा provider हर instance को एक साथ unhealthy mark कर देगा।

**Graceful shutdown।** Deploy पर platform SIGTERM भेजता है। Server connections लेना बंद करता है और चल रही requests को `--timeout-graceful-shutdown` तक पूरा होने देता है। ये आपकी सबसे लंबी stream से ज़्यादा होना चाहिए, और platform का grace period server वाले से ज़्यादा, वरना platform पहले ही process को kill कर देगा। Kubernetes default रूप से 30 seconds देता है (`terminationGracePeriodSeconds` बढ़ाओ)। Cloud Run SIGTERM के बाद सिर्फ़ 10 seconds देता है, तो वहाँ scale-down के दौरान लंबी streams कट सकती हैं; client को retry का option देने दो।

### इसे चलाना

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4 \
  --timeout-graceful-shutdown 30
```

दो workers वाले एक test में, SIGTERM आने पर चल रही एक stream ने अपने सारे tokens पूरे किए, जबकि नई requests serve नहीं हुईं। अगर आप Gunicorn use करते हो, तो ध्यान रखो कि हाल के Uvicorn versions `uvicorn.workers` को deprecate करते हैं; `uvicorn-worker` package use करो (`-k uvicorn_worker.UvicornWorker`)।

### Queue के साथ background jobs

जो काम मिनटों लेता है, जैसे OCR या 500 pages के PDF को index करना, वो एक worker process पर जाता है, और request तुरंत एक job id return करती है। Redis Queue (RQ) के साथ:

```python
from fastapi import HTTPException
from redis import Redis
from rq import Queue
from rq.exceptions import DuplicateJobError

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents/{doc_id}/index")
def start_indexing(doc_id: str):        # plain def: runs in a thread, so Redis cannot block the loop
    job_id = f"index-{doc_id}"          # same document, same job id
    try:
        queue.enqueue("workers.index_pdf", doc_id, job_id=job_id, unique=True,
                      job_timeout=1800, result_ttl=86400)
    except DuplicateJobError:
        pass                            # a double click or a client retry: the job already exists
    return {"job_id": job_id, "status_url": f"/jobs/{job_id}"}

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    if job is None:
        raise HTTPException(404, "Unknown or expired job")
    return {"status": job.get_status()}
```

RQ 2.8 में जोड़ा गया `unique=True` submission को **idempotent** बनाता है: एक ही request दो बार आए तो एक ही job बनता है। `result_ttl` पूरे हुए job को एक दिन तक रखता है; default 500 seconds है, जिसके बाद status URL 404 return करता है। Worker को भी दो बार चलने पर safe बनाओ, क्योंकि worker बीच में crash हो सकता है। Celery, Arq और cloud task queues भी यही pattern follow करते हैं।

### Measure और observe करना

हर request की एक line log करो: request id, user, model, tokens, cost, time to first token, total time और outcome (done, deadline, provider error, shed)। p95 time to first token, shed rate और provider 429 rate पर नज़र रखो; एक request को services के पार follow करना tracing वाला lesson cover करता है। Launch से पहले और हर change के बाद Locust जैसे किसी tool से शाम के peak का load-test करो।

### अपने browser में try करो

साठ requests एक साथ आती हैं; एक साथ दस ही चल सकती हैं। एक ऐसी queue जो कभी मना नहीं करती, उसकी तुलना 429 से पहले एक छोटे wait से करो।

```python
import asyncio, random, time

async def model_call(slots, max_wait, waits):
    t0 = time.perf_counter()
    try:
        await asyncio.wait_for(slots.acquire(), max_wait)   # None queues forever
    except asyncio.TimeoutError:
        return "rejected"                                   # send a fast 429: busy, retry soon
    waits.append(time.perf_counter() - t0)                  # time spent waiting for a slot
    try:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model call
    finally:
        slots.release()
    return "served"

async def burst(cap, max_wait, n=60):
    slots, waits = asyncio.Semaphore(cap), []
    results = await asyncio.gather(*(model_call(slots, max_wait, waits) for _ in range(n)))
    print(f"max_wait {str(max_wait):>4}: served {results.count('served'):>2}, "
          f"rejected {results.count('rejected'):>2}, worst wait {max(waits, default=0):.2f} s")

random.seed(1)
for max_wait in (None, 0.1, 0.01):
    await burst(cap=10, max_wait=max_wait)
```

बिना limit के, आखिरी request शुरू होने से पहले लगभग पाँच model-call के बराबर समय इंतज़ार करती है; जब real calls seconds लेती हैं, तो यही वो चुप spinner है जिसे देखकर users छोड़ जाते हैं। एक छोटे wait के साथ, extra requests को तुरंत "busy" सुनने को मिलता है।

## एक example से समझो

ये एक illustrative case है: numbers दिखाते हैं कि किस तरह के बदलाव की उम्मीद करें, ये कोई measured study नहीं है। लखनऊ की एक edtech का doubt-solving assistant एक ही Uvicorn process पर चलता था। शाम को students को कोई भी text दिखने के लिए लगभग 12 seconds इंतज़ार करना पड़ता था। लगभग एक तिहाई requests load balancer की 30-second limit से टकराती थीं, क्योंकि बिना stream वाला answer पूरा होने तक कुछ नहीं भेजता। Upload किए गए हाथ से लिखे notes पर OCR एक `async def` endpoint के अंदर चलता था और सबके लिए server को freeze कर देता था।

बदलाव:

- FastAPI के SSE support के साथ **streaming**। Staging में answer फिर भी एक साथ आता था, क्योंकि nginx ingress उसे buffer कर रहा था; `/answer` के लिए buffering off करने से ठीक हो गया।
- **हर container में चार workers, दो containers**, हर worker में 40 model slots, ये check करने के बाद कि एक साथ 320 calls provider quota में फ़िट होती हैं।
- **Layers में timeouts**: एक retry के साथ SDK 10 s, हर model call पर 25 s deadline, और दोनों के ऊपर balancer का 30 s idle timeout। Deadline fire होने पर student को "This is taking longer than usual; please try again" दिखता है।
- **Limits**: हर student के लिए 10 मिनट में 20 सवाल, और सारे slots busy होने पर `Retry-After` के साथ एक तेज़ 429, जो "Many students are asking right now, retrying in 5 seconds" के रूप में दिखता है।
- **OCR एक background queue पर**, file से derive किए गए job id के साथ, ताकि एक double tap से एक ही job बने। Result ready होने तक page "Reading your notes..." दिखाता है।
- **Health और deploys**: `/ready` सिर्फ़ start-up check करता है; graceful shutdown 30 s है, 40 s के platform grace period के अंदर।

| शाम के peak पर measure (illustrative) | पहले | बाद में |
| --- | --- | --- |
| पहले text तक का समय, p95 | लगभग 12 s | लगभग 1 से 2 s |
| Timeout से टकराती requests | लगभग 33% | 1% से कम |
| OCR uploads से server freeze | रोज़ | कोई नहीं |
| Answer से पहले छोड़ने वाले students | Baseline | लगभग दो तिहाई कम |
| Students तक पहुँचते provider 429s | अक्सर, खाली errors के रूप में | कभी-कभार, एक साफ़ "busy, retrying" के रूप में |

## आम गलतियाँ

- **`async def` के अंदर एक sync client।** एक blocking Redis, database या HTTP call उस worker की हर request को freeze कर देती है।
- **SDK timeout को deadline मान लेना।** Retries और `retry-after` waits उसके ऊपर जुड़ते जाते हैं।
- **Stream के अंदर cap check करना।** तब तक 200 जा चुका होता है और 429 नामुमकिन है।
- **ये भूल जाना कि caps गुणा होते हैं।** 4 workers और 3 containers में हर process पर 50 मतलब एक साथ 600 calls, शायद provider quota से बहुत ज़्यादा।
- **Streaming को सिर्फ़ localhost पर test करना**, जहाँ कोई proxy उसे buffer नहीं करता।
- **किसी shared dependency पर readiness check।** एक database blip हर instance को एक साथ हटा देती है।
- **Platform से लंबा server grace period।** Platform पहले process को kill कर देता है और streams फिर भी कट जाती हैं।
- **Clients जो 429 पर तुरंत retry करते हैं**, और एक छोटे overload को लंबे overload में बदल देते हैं।
- **Random job ids**, जिससे एक double click वही महँगा job दो बार start कर देता है।

## जब सादा serving काफ़ी है

- **कुछ ही users वाले internal tools**: एक process, model calls पर एक deadline और एक health check काफ़ी हैं।
- **Batch jobs** जो कभी users के सामने नहीं आते: web service से एक scheduled script बेहतर है।
- **Serverless routes**, जहाँ platform workers और shutdown संभालता है। उसकी time limit को अपनी सबसे लंबी stream से मिलाकर check करो।

## Demo से production तक

- **Blocking calls हटाओ**, फिर कई workers चलाओ।
- **Model calls पर** और हर user पर **cap लगाओ**, और total को provider quota से मिलाकर check करो।
- **Timeouts को layers में रखो** और real path से stream करो।
- **लंबे काम को queue करो**, idempotent job ids के साथ, और grace periods set करो।
- **हर request पर log करो**: tokens, cost, time to first token और outcome; p95 पर नज़र रखो।

FastAPI का deployment concepts page और streaming पर उसका custom responses page पढ़ो।

1. Model tokens को server-sent events के रूप में stream करो, और browser में time to first token पहले और बाद में measure करो।
