## ये क्या है

**Test** code का एक छोटा हिस्सा है जो आपके code को आपके चुने हुए input के साथ चलाता है और check करता है कि result वही है जो आप expect करते हो। **Unit test** एक छोटा हिस्सा, आमतौर पर एक function, अकेले में check करता है। Result गलत हो तो test fail होता है और बताता है कहाँ।

Tests आज लिखे code के लिए उतने ज़रूरी नहीं जितने उसके बाद आने वाले हर change के लिए। छह महीने बाद आप या आपका कोई teammate किसी function को बदलेगा। Tests के बिना, ये जानने का एक ही तरीका है कि कुछ टूटा नहीं: app में click करते जाओ और उम्मीद करो। Tests हों तो एक command चलाओ और कुछ seconds में पता चल जाता है।

**pytest** Python का standard testing tool है। आप सीधे-सादे functions लिखते हो जिनके नाम `test_` से शुरू होते हैं, और सीधे-सादे `assert` statements use करते हो। pytest उन्हें ढूँढता है, चलाता है, और जब कोई fail होता है तो ठीक-ठीक दिखाता है कि कौन सी values अलग थीं।

शुरू से एक limit याद रखो: test वही पकड़ता है जो आपने check करने का सोचा। Cases चुनना ही असली skill है, और इस lesson का ज़्यादातर हिस्सा उसी चुनाव के बारे में है।

## ये काम कैसे करता है

### आपके पहले tests

एक test के तीन steps होते हैं, जिन्हें अक्सर **arrange, act, assert** कहते हैं: inputs तैयार करो, code को एक बार call करो, result check करो।

ये रहा एक GST helper. ये `Decimal` use करता है, जो Python का exact decimal type है, क्योंकि money में drift नहीं होना चाहिए (क्यों, ये अगला हिस्सा दिखाता है)। इस example के लिए मान लो finance team का rule ये है: paisa तक round करो, और आधा paisa ऊपर जाता है। ये rule एक business decision है, तो अपनी finance team से confirm कर लेना।

```python
# gst.py
from decimal import Decimal, ROUND_HALF_UP

PAISA = Decimal("0.01")

def gst(amount: Decimal, rate: Decimal = Decimal("0.18")) -> Decimal:
    """GST on an amount, rounded to the paisa, half a paisa rounded up."""
    if amount < 0:
        raise ValueError("amount must not be negative")
    return (amount * rate).quantize(PAISA, rounding=ROUND_HALF_UP)
```

```python
# test_gst.py
from decimal import Decimal as D
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(D("100")) == D("18.00")

def test_half_paisa_rounds_up():
    # 100.25 x 0.18 = 18.045 exactly, so it must round up to 18.05
    assert gst(D("100.25")) == D("18.05")

def test_negative_amount_is_refused():
    with pytest.raises(ValueError, match="negative"):
        gst(D("-1"))
```

Folder में `pytest` चलाओ और ये `3 passed` print करता है। हर नाम बताता है कि वो किस behaviour की उम्मीद करता है, तो failure report एक वाक्य जैसी पढ़ी जाती है। `match=` error message भी check करता है, ताकि test किसी और `ValueError` की वजह से गलती से pass न हो जाए।

जिस loop में आप काम करते हो:

```flow
dir: LR
Code लिखो या बदलो -> pytest चलाओ
pytest चलाओ -[कोई test fail हुआ]-> Failure पढ़ो | कौन सी values अलग थीं
Failure पढ़ो -> Code लिखो या बदलो
pytest चलाओ -[सब pass]-> Commit
```

### Money और floats

सीधे floats क्यों नहीं? यही function `round(amount * rate, 2)` से लिखो और rounding test fail हो जाता है:

```
>       assert gst(100.25) == 18.05
E       assert 18.04 == 18.05
E        +  where 18.04 = gst(100.25)
```

Float numbers को binary में store करता है, और ज़्यादातर decimal fractions का कोई exact binary रूप नहीं होता। `100.25 * 0.18` 18.044999999999998... के रूप में store होता है, बीच वाले point से ज़रा नीचे, इसलिए ये नीचे round हो जाता है। ये error 15वें digit में छुपी नहीं है: customer को एक paisa गलत bill दिखता है। इससे तीन rules निकलते हैं:

- **Money:** strings से बना `Decimal` use करो (`Decimal("100.25")`), या पूरे paise integers के रूप में store करो। कभी `Decimal(0.1)` मत लिखो: ये float की error copy कर लेता है और 0.1000000000000000055511151231257827.... देता है।
- **जो floats money नहीं हैं** (model का confidence score, एक average, एक similarity): `pytest.approx` से compare करो, जो default में दस लाख में एक का relative difference allow करता है।
- **Compute किए गए floats पर कभी `==` नहीं।** ये आपके laptop पर तभी तक चलता है जब तक inputs नहीं बदलते।

```python
def test_mean_score_needs_approx():
    # (0.1 + 0.2) / 2 is 0.15000000000000002, so == 0.15 alone fails
    assert (0.1 + 0.2) / 2 == pytest.approx(0.15)
```

### Copy करने की जगह parametrise करो

22 September 2025 से GST के दो main slabs हैं, 5% और 18%, और साथ में goods के एक छोटे set के लिए एक special 40% rate, जैसे sugary fizzy drinks और बड़ी cars। (पुराने 12% और 28% slabs हटा दिए गए, हालाँकि कुछ special rates अभी भी हैं।) एक parametrised test slabs और zero वाले edges cover कर लेता है:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (D("1000"), D("0.05"), D("50.00")),
    (D("1000"), D("0.18"), D("180.00")),
    (D("1000"), D("0.40"), D("400.00")),
    (D("1000"), D("0"), D("0.00")),
    (D("0"), D("0.18"), D("0.00")),
], ids=["5-percent", "18-percent", "40-percent", "zero-rate", "zero-amount"])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

हर row अपने अलग test की तरह report होती है, जैसे `test_rates[40-percent]`, तो failure case का नाम बताता है। `ids` के बिना pytest इन rows को `amount0-rate0-expected0` जैसे नाम देता है, जो पढ़ने में मुश्किल हैं।

### Fixtures और conftest.py

**Fixture** shared setup है जिसे test अपने parameter में उसका नाम लिखकर माँगता है। जो fixtures कई test files use करती हैं उन्हें `conftest.py` में रखो; pytest उस file को अपने आप load करता है, import की ज़रूरत नहीं।

```python
# invoice.py
from decimal import Decimal
from gst import gst

def invoice_total(invoice: dict) -> Decimal:
    subtotal = sum((price for _, price in invoice["items"]), Decimal("0"))
    return subtotal + gst(subtotal, invoice["rate"])
```

```python
# conftest.py
from decimal import Decimal as D
import pytest

@pytest.fixture
def invoice():
    return {"items": [("Charger", D("999.00")), ("Cable", D("299.00"))],
            "rate": D("0.18")}
```

```python
# test_invoice.py
from decimal import Decimal as D
from invoice import invoice_total

def test_total_adds_gst_to_subtotal(invoice):
    assert invoice_total(invoice) == D("1531.64")   # 1298.00 + 233.64

def test_empty_invoice_totals_zero(invoice):
    invoice["items"] = []          # changes only this test's copy
    assert invoice_total(invoice) == D("0")
```

Default में fixture हर test के लिए फिर से चलती है, तो एक test उसे बदल दे तो दूसरा नहीं टूटता। बड़ा scope (`scope="session"`) सिर्फ़ उस setup के लिए use करो जो धीमा है और कभी नहीं बदलता, जैसे एक बड़ी sample file load करना। Fixture अपनी value `yield` कर सकती है और `yield` के बाद clean up कर सकती है। Built-in `tmp_path` fixture, files लिखने वाले code के लिए, हर test को एक नया temporary folder देती है।

### Model और API calls के लिए fakes

असली model calls धीमी होती हैं, पैसे लगते हैं, और हर बार अलग reply दे सकती हैं। Unit tests में इन्हें एक **fake** से बदलो जो एक fixed reply return करे। किसी हिस्से को ऐसे बदलने को **mocking** कहते हैं।

अगर code आप लिख रहे हो, तो सबसे साफ़ design है client को parameter की तरह pass करना। इसे **dependency injection** कहते हैं:

```python
# triage.py
import json

def classify(ticket: str, client) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    return json.loads(reply)["category"]
```

```python
# test_triage.py
from triage import classify

class FakeClient:
    def complete(self, prompt: str) -> str:
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

जो code आपको विरासत में मिलता है, उसमें ज़्यादातर client module level पर एक बार बनाया जाता है। तब आप उसे pytest के `monkeypatch` से swap करते हो, जो test के बाद original वापस रख देता है। `unittest.mock.Mock` fake बनाता है और record करता है कि उसे कैसे call किया गया। ये version bad replies भी handle करता है, और AI projects में सबसे ज़्यादा test करने लायक code यही है:

```python
# llm.py
class ModelClient:
    """Stands in for a real model SDK client."""
    def complete(self, prompt: str) -> str:
        raise RuntimeError("this would make a real, paid network call")
```

```python
# tickets.py
import json
from llm import ModelClient

client = ModelClient()          # created once, when the module is imported
CATEGORIES = {"refund", "delivery", "other"}

def classify(ticket: str) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    try:
        category = json.loads(reply)["category"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return "needs_review"
    return category if category in CATEGORIES else "needs_review"
```

```python
# test_tickets.py
from unittest.mock import Mock
import pytest
import tickets
from llm import ModelClient

def fake_client(reply: str) -> Mock:
    fake = Mock(spec=ModelClient)    # only methods the real client has
    fake.complete.return_value = reply
    return fake

def test_reads_category_and_sends_ticket(monkeypatch):
    fake = fake_client('{"category": "refund"}')
    monkeypatch.setattr(tickets, "client", fake)
    assert tickets.classify("Money not returned") == "refund"
    fake.complete.assert_called_once()
    assert "Money not returned" in fake.complete.call_args.args[0]

@pytest.mark.parametrize("reply", [
    "Sure! This looks like a refund.",   # prose, not JSON
    '{"label": "refund"}',               # wrong key
    '{"category": "lottery"}',           # unknown category
    "null",                              # valid JSON, wrong shape
    "",                                  # empty reply
])
def test_bad_reply_goes_to_review(monkeypatch, reply):
    monkeypatch.setattr(tickets, "client", fake_client(reply))
    assert tickets.classify("Where is my parcel?") == "needs_review"
```

दो gotchas जो experienced engineers को भी फँसा देते हैं:

- **Patch वहाँ करो जहाँ नाम use होता है, वहाँ नहीं जहाँ define होता है।** अगर `tickets.py` में `from llm import client` लिखा होता, तो उसके पास उस नाम की अपनी copy होती, तो `llm.client` patch करने से कुछ नहीं बदलता और असली call फिर भी चल जाती। `tickets.client` patch करो।
- **सादा `Mock()` कोई भी attribute मान लेता है।** कोई typo, या असली client में rename हुआ कोई method, test में फिर भी "चल" जाता है और bug production तक पहुँच जाता है। `Mock(spec=ModelClient)` हर उस चीज़ पर `AttributeError` raise करता है जो असली class में नहीं है।

कब क्या use करें:

| Situation | Use करो | क्यों |
| --- | --- | --- |
| नया code जो आप लिख रहे हो | Client pass करो (dependency injection) | Patching नहीं; test ठीक-ठीक दिखाता है कि code को क्या चाहिए |
| Module-level client वाला inherited code | जो module उसे use करता है उस पर `monkeypatch.setattr` | एक test के लिए एक नाम swap करता है और बाद में वापस रख देता है |
| आपको check करना ही है कि क्या भेजा गया, जैसे prompt | `Mock(spec=...)` और `call_args` | हर call record करता है; spec typos पकड़ता है |
| Files लिखने वाला code | Built-in `tmp_path` fixture | हर test के लिए नया folder, पीछे कुछ नहीं छूटता |
| असली model का behaviour | Golden set पर evaluation run, unit test नहीं | Unit tests जवाब की quality नहीं परख सकते |

### Unit tests बनाम evaluations

AI projects में दो तरह के tests अलग रखो। तेज़ unit tests आपका अपना logic check करते हैं: prompts बनाना, replies parse करना, validation, scoring. ये हर commit पर चलते हैं। धीमे **evaluations** inputs का एक fixed golden set असली model को भेजते हैं और जवाबों को score करते हैं, ताकि पकड़ा जा सके कि किसी prompt change या model update ने results खराब कर दिए। इन्हें कैसे बनाएँ, ये "Test sets and evals" lesson (P1) में है। दोनों को मिलाने से रोज़ के tests धीमे, महँगे और flaky हो जाते हैं।

एक **marker** इन्हें अलग रखता है। उसे `pyproject.toml` में register करो; `--strict-markers` गलत type हुए marker को warning की जगह error बना देता है:

```toml
[tool.pytest.ini_options]
addopts = "--strict-markers"
markers = ["eval: calls the real model on the golden set; run on a schedule"]
```

हर evaluation test पर `@pytest.mark.eval` tag लगाओ, और हर commit पर `pytest -m "not eval"` चलाओ।

### रोज़ tests चलाना

| Command | क्या करता है |
| --- | --- |
| `pytest -x` | पहले failure पर रुक जाता है |
| `pytest -k rounding` | सिर्फ़ वो tests चलाता है जिनके नाम में "rounding" है |
| `pytest test_gst.py::test_half_paisa_rounds_up` | एक test चलाता है |
| `pytest --lf` | सिर्फ़ वो tests फिर से चलाता है जो पिछली बार fail हुए |
| `pytest -m "not eval"` | `eval` mark वाले tests skip करता है |
| `pytest --cov=. --cov-report=term-missing` | Coverage दिखाता है, उन line numbers के साथ जो किसी test ने नहीं चलाईं (`pytest-cov` package चाहिए) |

**Coverage** आपके code का वो हिस्सा है जो tests के दौरान चला। "Missing" column पढ़ो: उसमें वो lines हैं जो किसी test ने नहीं चलाईं, और वही आपके blind spots हैं। `--cov-branch` जोड़ो ताकि ऐसा `if` भी दिखे जिसका true या false side कभी नहीं चला। लेकिन coverage सिर्फ़ ये साबित करता है कि code चला, ये नहीं कि किसी ने result check किया: जो test बिना `assert` के `gst(D("100"))` call करता है, वो भी गिना जाता है। इसे gaps ढूँढने के लिए use करो, 100% तक पहुँचने वाले score की तरह नहीं।

**Continuous integration (CI)** हर push या pull request पर वही command एक साफ़ machine पर चलाता है, और fail होने पर team merging रोक देती है। दो चीज़ें वहाँ टूटती हैं जो आपके laptop पर pass होती हैं। पहली, CI machine पर सिर्फ़ वो packages होते हैं जो आपका project list करता है, तो कोई missing dependency सामने आ जाती है। दूसरी, CI machines अक्सर UTC use करती हैं, जो India से साढ़े पाँच घंटे पीछे है। तब "आज" वाला कोई test IST में आधी रात से सुबह 5:30 के बीच चलने पर fail हो सकता है। Date या clock अपने code में pass करो, और machine की setting पर भरोसा करने की जगह time zone का नाम दो (`ZoneInfo("Asia/Kolkata")`)।

### पहले क्या test करें

जिस project में कोई tests नहीं हैं, वहाँ से शुरू करो जहाँ bug सबसे महँगा पड़ेगा:

1. **Money और कानूनी कुछ भी:** totals, tax, refunds, limits.
2. **वो data जो दूसरे systems पढ़ते हैं:** आपकी API जो JSON return करती है, आप जो CSV export करते हो।
3. **वो code जो आप बदलने वाले हो:** पहले ऐसे tests लिखो जो उसका अभी का behaviour pin कर दें, फिर उसे बदलो।
4. **हर bug जो आप fix करते हो:** पहले एक test जो उसे reproduce करे, फिर fix. इसे **regression test** कहते हैं; ये वही bug वापस आने से रोकता है।

Project में tests कहाँ रहते हैं (एक `tests/` folder, एक `src` layout, README commands), इसके लिए "Project tooling: environments, tests and logs" lesson देखो।

## एक example से समझो

Sneha Chennai की एक logistics company में एक invoice-extraction service maintain करती है। Service एक scan किया हुआ invoice पढ़ती है, line amounts और छपा हुआ total निकालती है, और दोनों न मिलें तो invoice reject कर देती है। एक customer report करता है कि एक असली invoice reject हो गया। उसकी lines हैं freight ₹1,040.37, loading ₹128.98 और toll ₹10.65, जिनका जोड़ ₹1,180.00 है, लेकिन छपा हुआ total ₹1,180.50 है। Business ₹1 तक का rounding difference allow करता है (इस example के लिए एक illustrative rule)।

**पहले, एक fail होने वाला test.** Code छूने से पहले वो एक test लिखती है जो bug reproduce करे और expect करे कि invoice accept हो। वो pytest चलाती है और नया test fail होता है। इससे साबित होता है कि test सच में bug पकड़ता है; जो test fix से पहले ही pass हो जाए, वो कुछ साबित नहीं करता।

**फिर fix.** पुराना check था `sum(lines) == printed_total`. वो इसे बदलकर ₹1.00 तक का difference allow करती है, और नया test pass हो जाता है।

**फिर edges.** एक limit के दो edges होते हैं, तो वो parametrise करती है: ठीक ₹1 ऊपर और ठीक ₹1 नीचे accept होने चाहिए, और किसी भी तरफ़ ₹1.01 reject. एक case fail होता है: ठीक ₹1 ऊपर वाला reject हो जाता है। Floats इसकी वजह बताते हैं। Python 3.12 या उसके बाद के versions में तीनों lines का `sum()` 1180 नहीं, `1179.9999999999998` देता है (पुराने versions में, या `+` से जोड़ने पर, संयोग से 1180.0 आता है), तो 1181.00 से difference `1.0000000000002274` है, limit से ज़रा ऊपर। वो extractor को बदलती है ताकि amounts text के रूप में दे, और check को `Decimal` use करने के लिए:

```python
# validate.py
from decimal import Decimal

TOLERANCE = Decimal("1.00")          # business rule: up to Rs 1 of rounding

def total_is_valid(line_amounts: list[str], printed_total: str) -> bool:
    lines_total = sum((Decimal(a) for a in line_amounts), Decimal("0"))
    return abs(lines_total - Decimal(printed_total)) <= TOLERANCE
```

```python
# test_validate.py
import pytest
from validate import total_is_valid

LINES = ["1040.37", "128.98", "10.65"]      # add up to exactly 1180.00

@pytest.mark.parametrize("printed, expected", [
    ("1180.50", True),    # the customer's bug: 50 paise of rounding
    ("1181.00", True),    # exactly Rs 1 over: allowed
    ("1179.00", True),    # exactly Rs 1 under: allowed
    ("1181.01", False),   # just over the limit
    ("1178.99", False),   # just under the limit
], ids=["50-paise", "plus-1", "minus-1", "plus-1.01", "minus-1.01"])
def test_rounding_tolerance(printed, expected):
    assert total_is_valid(LINES, printed) is expected
```

पाँचों cases pass होते हैं। ध्यान दो कि float bug किसने पकड़ा: customer वाले case ने नहीं, बल्कि ठीक limit वाले edge ने। Bugs edges पर ही रहते हैं।

**आखिर में, पूरा suite.** वो project के सारे tests, कुछ सौ, एक मिनट से कम में चलाती है। एक असंबंधित test fail होता है: वो एक नकली invoice को reject करने के लिए पुराने exact match पर निर्भर था, जिसका total कुछ paise बदल दिया गया था। वो team से बात करती है। सब मानते हैं कि forgery check को अपना अलग rule चाहिए, और वो दोनों update करती है। Tests के बिना, वो forgery check production में काम करना बंद कर देता और किसी को पता नहीं चलता।

## आम गलतियाँ

- **सिर्फ़ happy path test करना।** Bugs edges पर रहते हैं: zero, empty lists, negatives, ठीक limit, बहुत बड़ी values, missing fields.
- **एक test जो दस चीज़ें check करे।** जब वो fail होगा, आप बता नहीं पाओगे कौन सी। हर test में एक behaviour, ऐसे नाम के साथ जो बताए क्या।
- **ऐसे tests जो एक-दूसरे पर या order पर निर्भर हों।** हर test खुद अपनी ज़रूरत का setup करे और अकेले चलाने पर भी pass हो। Module level पर shared lists या dictionaries आमतौर पर इसकी वजह होती हैं।
- **Unit tests में असली network या model calls.** ये धीमी हैं, पैसे लगते हैं और tests को flaky बनाती हैं। इन्हें fake करो, और असली model को एक scheduled evaluation run से परखो।
- **Floats को `==` से compare करना, या float से `Decimal` बनाना।** Money के लिए `Decimal("1.10")` और बाकी floats के लिए `pytest.approx` use करो।
- **गलत जगह patch करना, या `spec` के बिना `Mock` use करना।** असली call फिर भी चल जाती है, या typo चुपचाप pass हो जाता है।
- **Code क्या करता है उसकी जगह ये test करना कि वो कैसे करता है।** जो test check करे कि कौन सा private helper call हुआ, वो हर harmless refactor पर टूटता है। Outputs और दिखने वाले effects check करो।
- **ऐसा test जिसे आपने कभी fail होते नहीं देखा।** उसे fix से पहले लिखो, या एक बार जान-बूझकर code तोड़ो। जो test fail हो ही नहीं सकता, वो किसी चीज़ की रक्षा नहीं करता।
- **Clock या machine के time zone पर निर्भर रहना।** Dates pass करो और जब दिन मायने रखता हो तो `Asia/Kolkata` नाम से दो।
- **100% coverage के पीछे भागना।** Coverage दिखाता है कि क्या चला, ये नहीं कि वो check हुआ या नहीं। जो behaviour मायने रखता है उसे test करो।
