## ये क्या है

कई automations को **कुछ होते ही उसी पल** react करना होता है: कोई payment सफल होता है, कोई order आता है, कोई form submit होता है। **Webhook** यही मुमकिन बनाता है।

Webhook एक message है जो कोई app event होते ही आपके दिए web address (URL) पर भेजता है। ये doorbell जैसा है। हर कुछ मिनट में दरवाज़ा check करने की जगह, जिसे **polling** कहते हैं, कोई आता है तो आपको बता दिया जाता है।

```flow
dir: LR
title: Polling: धीमा, बहुत सारी बेकार requests
आपका app -[कुछ नया है?]-> Store
Store -[नहीं ... नहीं ... हाँ, एक order]-> आपका app
```

```flow
dir: LR
title: Webhook: होते ही बता देता है, तेज़, कोई बेकार check नहीं
Store -[event POST करता है]-> आपका URL (n8n)
आपका URL (n8n) -[200 OK]-> Store
```

Message आमतौर पर एक HTTP **POST** request होता है, जिसकी **JSON** body event के बारे में बताती है। एक आसान किया हुआ example, किसी payment gateway के event जैसा:

```json
{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}
```

इस sample में amount paise में है, तो 420000 का मतलब ₹4,200।

**Webhook या API?** API में *आप* provider को call करके पूछते हो। Webhook में कुछ बदलने पर provider *आपको* call करता है। अच्छे automations दोनों use करते हैं: webhook बताता है कि कुछ हुआ, और API से आप details check करते हो और gaps भरते हो।

ये lesson Jaipur के एक handicrafts store के साथ चलता है, जो चाहता है कि payment सफल होते ही invoice email हो जाए।

## ये काम कैसे करता है

### एक delivery की पूरी कहानी

हर delivery एक ही loop से गुज़रती है। Sender सिर्फ़ आपका reply देखता है।

```flow
title: एक webhook delivery
Event होता है | जैसे कोई payment capture होता है -> Sender आपके secret से JSON sign करता है
Sender आपके secret से JSON sign करता है -> आपके URL पर POST
आपके URL पर POST -> आपका reply
आपका reply -[timeout के अंदर 2xx]-> Delivered | sender रुक जाता है
आपका reply -[error या समय पर reply नहीं]-> बाद में retry | वही event, वही id
बाद में retry -> आपके URL पर POST
```

यानी sender के लिए `2xx` reply का मतलब है "हो गया", भले ही आपका workflow एक second बाद fail हो जाए, और कोई भी failure वही event वापस ले आता है।

### Receive करना: test और production URLs

आपका automation tool आपको एक URL देता है, जैसे n8n के **Webhook** node से। उसे sending app की settings में paste करो और चुनो कि कौन-से events भेजने हैं। कई tools दो URLs देते हैं:

| URL | कब काम करता है | किसके लिए use करो |
| --- | --- | --- |
| Test URL | जब आप editor में listen कर रहे हो | Build और debug करने के लिए |
| Production URL | जब workflow publish (active) हो | Real events के लिए |

Beginners की एक आम गलती है sender की settings में test URL ही छोड़ देना: जब तक आप देख रहे हो सब चलता है, फिर बंद हो जाता है।

यहाँ Webhook node की दो settings मायने रखती हैं। **Raw Body** sender के भेजे exact bytes वैसे ही रखता है, जो signature check करने के लिए चाहिए। **Respond** तय करता है कि n8n कब reply करे: तुरंत, आखिरी node खत्म होने पर, या किसी **Respond to Webhook** node पर जिसे आप ठीक वहीं रखते हो जहाँ चाहिए।

### Real events आने से पहले test करो

Field names हर provider में अलग होते हैं, इसलिए mappings किसी real sample से बनाओ। आप खुद `curl` से एक भेज सकते हो: n8n में "Listen for test event" पर click करो, फिर अपने test URL के साथ ये चलाओ:

```bash
curl -X POST "https://your-n8n.example.com/webhook-test/payments" \
  -H "Content-Type: application/json" \
  -d '{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
```

एक trap कई beginners को रोक देता है। अगर n8n आपके laptop पर चलता है, तो उसका URL `localhost` से शुरू होता है, जिस तक internet पर बैठा gateway नहीं पहुँच सकता। Public n8n (n8n Cloud, या HTTPS वाला server) use करो, ngrok या Cloudflare Tunnel जैसा कोई **tunnel** जो आपके laptop को public address देता है, या सिर्फ़ ये देखने के लिए कि provider क्या भेजता है, webhook.site।

ज़्यादातर gateways में एक **test mode** भी होता है जिसमें असली पैसा नहीं लगता। Test और live mode के webhooks और secrets आमतौर पर अलग-अलग होते हैं।

### आपका reply sender को क्या बताता है

Sender सिर्फ़ आपके reply का status code पढ़ता है, और सिर्फ़ कुछ seconds रुकता है। Razorpay, एक भारतीय payment gateway, 5 seconds के अंदर `2xx` reply की उम्मीद करता है। कोई और code, या समय पर reply न आना, वो failure मानता है और event बनने के 24 घंटे तक बढ़ते gaps के साथ retry करता है। अगर उन 24 घंटों तक deliveries fail होती रहें, तो वो webhook disable कर देता है (ये सब November 2026 के हिसाब से)। दूसरे providers के windows अलग होते हैं, इसलिए उनके docs पढ़ो।

| आपका reply | Sender क्या समझता है | कब भेजना है |
| --- | --- | --- |
| `200` (या कोई और `2xx`) | Delivered; दोबारा कभी नहीं भेजेगा | Event save हो गया है, या ये duplicate है जो आपके पास पहले से है |
| `401` | Failed; आमतौर पर retry होता है | Signature match नहीं होता |
| `500` | Failed; बाद में retry होता है | आप event save नहीं कर पाए, जैसे आपका database down है |
| समय पर reply नहीं | Failed; बाद में retry होता है | आपका workflow बहुत धीमा था या server down था |

### पहले save, फिर reply, फिर काम

इस lesson का सबसे ज़रूरी idea यही है। तीन मुमकिन orders में से दो fail होते हैं।

| Order | क्या गड़बड़ होती है |
| --- | --- |
| सारा काम करो, फिर reply | धीमा काम, जैसे PDF बनाना, timeout पार कर जाता है। आप काम कर रहे होते हो और sender retry कर देता है, और आपको duplicates मिलते हैं। |
| पहले reply, फिर काम | अगर `200` के बाद n8n crash या restart हो जाए, तो sender कभी दोबारा नहीं भेजता और event खो जाता है। |
| Save, reply, फिर saved copy से काम | Sender के "हो गया" सुनने से पहले ही event safe है। Fail हुआ काम आपकी copy से retry होता है। |

**Durable तरीके से save करना** मतलब event को ऐसी जगह लिखना जो restart के बाद भी बचा रहे: database table (जैसे Postgres या Supabase) या message queue। एक insert तेज़ होता है, timeout के काफ़ी अंदर। Raw body, event id, receive होने का समय और एक **status** store करो: save होने पर `received`, काम खत्म होने पर `done`।

```flow
title: Save, reply, फिर काम
Webhook आता है -> Signature match होता है?
Signature match होता है? -[नहीं]-> 401 reply करो और रुको
Signature match होता है? -[हाँ]-> Event id insert करो | status received
Event id insert करो -[पहले से है]-> 200 reply करो और रुको | एक duplicate
Event id insert करो -[save हो गया]-> 200 reply करो
200 reply करो -> Invoice बनाओ और email करो
Invoice बनाओ और email करो -> Status done mark करो
```

अगर reply के बाद workflow crash हो जाए, तो row `received` ही रहती है। एक **sweep**, यानी एक scheduled workflow जो लगभग हर 15 मिनट में चलता है, उन rows को उठाता है जो 10 मिनट बाद भी `received` हैं और काम दोबारा चलाता है। इसलिए काम दोहराने के लिए safe होना चाहिए: हर sub-step (invoice बना, email गया) record करो, ताकि rerun सिर्फ़ वही करे जो बाकी है।

### Duplicates और idempotency

ज़्यादातर senders **at-least-once delivery** का वादा करते हैं: वो event खोने की बजाय उसे दो बार भेजना पसंद करते हैं। इसका बचाव है **idempotency**: किसी event को दो बार process करने का असर वही हो जो एक बार process करने का।

दो अलग कामों के लिए दो ids use करो:

- **Event id** एक delivery को पहचानता है। उस event के हर retry पर उसकी value वही रहती है, इसलिए ये बताता है कि "ये delivery मैं पहले देख चुका हूँ"। जैसे Razorpay इसे `x-razorpay-event-id` header में भेजता है।
- **Business id**, जैसे payment id, असली चीज़ को पहचानता है। दो *अलग* events एक ही payment के बारे में हो सकते हैं (जैसे `payment.captured` और `order.paid`), इसलिए invoice को payment id पर key करो।

**वो race जिसमें experts भी फँसते हैं।** एक आसान-सा design लगता है: "sheet में id ढूँढो; नहीं मिली तो जोड़ दो"। धीमे reply के बाद retry original के एक second बाद ही आ सकता है। दोनों copies `pay_771` ढूँढती हैं, दोनों को कुछ नहीं मिलता, दोनों invoice बना देती हैं, क्योंकि check और write के बीच दूसरी copy घुस गई।

इसका fix है **एक ही step जो duplicate पर fail हो**। `event_id` column को unique key दो और बस insert करो। ठीक एक insert सफल होता है; दूसरे को "duplicate key" error मिलता है, जिसे आपका workflow "पहले से है, 200 reply करो और रुको" मानता है। Invoice के `payment_id` पर भी unique key लगाओ।

Google Sheet में unique key नहीं होती। Sheet lookup सिर्फ़ उस छोटी, कम volume वाली shop के लिए ठीक है जिसे कभी-कभार double invoice चल जाए। Sale से पहले database table पर चले जाओ।

### Events order बदलकर आ सकते हैं

Delivery order की कोई guarantee नहीं है; Razorpay की webhook guidance ये सीधे कहती है (November 2026 के हिसाब से)। किसी पुरानी attempt का retry हुआ `payment.failed` सफल `payment.captured` के *बाद* आ सकता है, और "आखिरी event जीतता है" वाला तरीका paid order को failed mark कर देगा। दो rules इसे संभालते हैं:

- **States को सिर्फ़ आगे बढ़ाओ।** Order `created` से `paid` तक जा सकता है, पर `paid` से वापस `failed` कभी नहीं। जो events उसे पीछे ले जाएँ उन्हें ignore करो।
- **जब मायने रखे, current state पूछो।** Ship या refund करने से पहले, provider के API को call करके अभी का status देखो।

### Security

जिसे भी आपका URL पता चल जाए, वो एक fake "payment captured" post करके असली shipment trigger करवा सकता है। इसे layers में protect करो।

**Signature verify करो।** आप और provider एक **webhook secret** share करते हो। हर delivery के लिए provider एक **HMAC** compute करता है, यानी secret से बना body का fingerprint, और उसे एक header में भेजता है। जैसे Razorpay `X-Razorpay-Signature` में एक HMAC-SHA256 hex value भेजता है (November 2026 के हिसाब से)। आप receive हुई body पर वही HMAC compute करते हो; दोनों match हों, तो sender को secret पता है और body नहीं बदली। Webhook का अपना secret use करो, अपने API key का secret नहीं।

तीन details तय करती हैं कि check काम करेगा या नहीं:

1. **Raw body use करो।** Signature भेजे गए exact bytes को cover करता है। JSON parse करके वापस text बनाओ तो spaces या key order बदल सकते हैं, और genuine event भी fail हो जाता है। n8n में **Raw Body** on करो।
2. **Constant time में compare करो।** Normal comparison पहले गलत character पर रुक जाता है, जिससे timing के clues leak हो सकते हैं। n8n का **Crypto** node HMAC compute कर सकता है, पर IF node वाला comparison constant-time नहीं है। High-value flows के लिए **Code** node में Node के `crypto.timingSafeEqual` से compare करो; self-hosted n8n पर पहले `NODE_FUNCTION_ALLOW_BUILTIN` environment variable से `crypto` module allow करो।
3. **जहाँ provider timestamp sign करता है, वहाँ पुराने messages reject करो।** Signature साबित करता है कि message किसने भेजा, कब नहीं, इसलिए पकड़ी गई request बाद में replay की जा सकती है। कुछ providers, जैसे Stripe, timestamp sign करते हैं ताकि आप कुछ मिनट से पुरानी कोई भी चीज़ reject कर सको। जहाँ ये नहीं है, वहाँ आपका unique event id replay को बेअसर कर देता है।

ये Python script, सिर्फ़ standard library से, raw-body trap दिखाता है:

```python
import hmac, hashlib, json

SECRET = b"test_secret_123"

def is_genuine(raw_body: bytes, signature: str) -> bool:
    expected = hmac.new(SECRET, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)  # constant-time

raw = b'{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
sig = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()

print(is_genuine(raw, sig))                          # True
print(is_genuine(json.dumps(json.loads(raw)).encode(), sig))  # False: spaces were added
```

दूसरी बार ये fail होता है क्योंकि `json.dumps` spaces जोड़ देता है: वही data, अलग bytes।

**बाकी layers:** HTTPS और एक लंबा, random URL path use करो (इनमें से कोई भी signature की जगह नहीं लेता)। सामान ship करने से पहले provider के API से payment दोबारा fetch करो; Razorpay खुद webhooks के backstop के तौर पर अपने fetch APIs use करने की सलाह देता है, जैसे जब कोई time-sensitive flow webhook आने का इंतज़ार नहीं कर सकता।

### छूटे हुए events और reconciliation

Retries छोटे outages cover करते हैं, लंबे नहीं। Retry window के बाद events बिना किसी error के खो जाते हैं, और कुछ providers webhook बंद कर देते हैं। ज़रूरी flows में दो safety nets होते हैं:

- **Sweep** उन events का काम retry करता है जो आपने save किए पर पूरे नहीं किए।
- **Reconciliation**, जैसे nightly, provider के API से दिन के सारे captured payments माँगता है और उन्हें आपके invoices से compare करता है। जो भी छूटा है, वो तब process होता है।

एक alert भी लगाओ: अगर business hours में एक घंटे तक कोई webhook न आए, या provider बताए कि कोई webhook disable हो गया, तो कोई उसी दिन देखे।

## एक example से समझो

Jaipur का एक handicrafts store Razorpay use करता है और चाहता है कि payment सफल होते ही invoice email हो जाए। एक typical order ₹4,200 का है। Gateway details November 2026 के हिसाब से हैं। वो n8n में ये बनाते हैं:

| # | Step | क्यों |
| --- | --- | --- |
| 1 | Webhook node: production URL, Raw Body on, Respond to Webhook node से reply करता है। Razorpay dashboard में `payment.captured` के लिए जोड़ा गया। | Events तुरंत receive करना, exact bytes के साथ |
| 2 | Raw body का HMAC-SHA256 webhook secret से compute करो और Code node में `X-Razorpay-Signature` से compare करो। Mismatch पर `401` reply करो। | Fake requests reject करना |
| 3 | `x-razorpay-event-id`, payment id और raw body को `webhook_events` में insert करो (unique event id, status `received`)। Duplicate key: `200` reply करो और रुको। कोई और failure: `500` reply करो। | Gateway के "हो गया" सुनने से पहले event safe है; copies यहीं रुक जाती हैं |
| 4 | Respond to Webhook: `200`। | 5-second limit के काफ़ी अंदर |
| 5 | Unique payment id वाली `invoices` table में invoice PDF बनाओ, email करो, फिर event का status `done` set करो। | धीमा काम, दोहराने के लिए safe |
| 6 | हर 15 मिनट: जो rows 10 मिनट बाद भी `received` हैं उनके लिए step 5 फिर चलाओ। | Crash हुआ काम पूरा करना |
| 7 | Nightly: Razorpay API से दिन के captured payments fetch करो और invoices से compare करो। | जो कभी पहुँचा ही नहीं, उसे पकड़ना |

**Festival sale (एक illustration)।** Diwali sale के दौरान हर कुछ seconds में orders आते हैं।

- PDF service अटक जाती है और एक payment का invoice बनते-बनते n8n restart हो जाता है। वो event पहले ही save हो चुका था और उसका जवाब जा चुका था, इसलिए Razorpay उसे दोबारा नहीं भेजता। दस मिनट बाद sweep देखता है कि row अभी भी `received` है और invoice भेज देता है।
- एक और restart server को दो मिनट के लिए down कर देता है। Razorpay को उन payments का कोई reply नहीं मिलता और server वापस आने पर वो उन्हें retry करता है।
- pay_771 उस restart से ठीक पहले save हो गया था, पर `200` कभी server से निकला ही नहीं। Razorpay उसे retry करता है; step 3 का insert duplicate key से टकराता है, और workflow `200` reply करके रुक जाता है।

| स्थिति | क्या हुआ | किस step ने संभाला |
| --- | --- | --- |
| किसी अनजान sender की fake request | Signature match नहीं हुआ | Step 2: `401` से reject |
| Reply के बाद, invoice से पहले crash | Row `received` ही रही | Step 6: sweep ने पूरा किया |
| 2 मिनट के outage में भेजे गए events | Razorpay ने बाद में retry किए | Steps 1 to 5, कुछ मिनट देर से |
| pay_771 दो बार deliver हुआ | Event id पहले से table में था | Step 3: `200` के साथ रुका |
| एक हफ़्ते का nightly reconciliation | कोई छूटा payment नहीं मिला | Step 7 |

Store का पहला version तुरंत reply करता था और sheet lookup use करता था। Crash हुआ invoice हमेशा के लिए खो जाता, क्योंकि gateway को उसका `200` मिल चुका था, और duplicate pay_771 एक दूसरा invoice बना देता: ₹4,200 की ऐसी sales जो कभी हुई ही नहीं।

## आम गलतियाँ

- **Production में test URL use करना।** Editor बंद करते ही events आना बंद हो जाते हैं।
- **Event save होने से पहले reply करना।** `200` के बाद crash होने पर event खो जाता है, क्योंकि sender उसे दोबारा नहीं भेजेगा।
- **Reply से पहले धीमा काम करना।** Sender timeout होकर retry करता है, और duplicates बनते हैं।
- **Duplicate check के लिए "पहले ढूँढो, फिर लिखो"।** साथ आने वाली दो copies दोनों pass हो जाती हैं। Unique key use करो।
- **Duplicate का जवाब error से देना।** Sender उस event को retry करता रहता है जो आपके पास पहले से है। `200` reply करो।
- **Parse किए JSON पर signature check करना, या सिर्फ़ URL पर भरोसा करना।** Raw body use करो; secret URL leak हो सकता है।
- **मान लेना कि events order में आएँगे।** States को सिर्फ़ आगे बढ़ाओ, और पैसे से जुड़ा action लेने से पहले दोबारा fetch करो।
- **Test और live secrets मिला देना।** हर mode का आमतौर पर अपना webhook और secret होता है।
- **न sweep, न reconciliation, न alert।** Crashes और लंबे outages चुपचाप events खो देते हैं।
- **Secrets log करना।** Webhook secret और पूरी payment details shared logs से बाहर रखो।

## Practice करो

नीचे link किया Zapier का webhooks वाला explanation और n8n के Webhook node docs पढ़ो।

1. **Receive करो।** n8n में एक Webhook workflow बनाओ, ऊपर वाला `curl` command अपने test URL पर भेजो और आया हुआ JSON study करो। अगर n8n laptop पर चलता है, तो बाहर से उस तक tunnel से पहुँचो।
2. **Reply से पहले save करो।** Unique event id और एक status column वाली `webhook_events` table बनाओ। हर event insert करो, फिर Respond to Webhook node से reply करो। Reply के बाद जानबूझकर workflow रोको और दिखाओ कि row `received` ही रहती है।
3. **Duplicates।** वही event एक साथ दो बार भेजो (`&` से जुड़े दो `curl` commands)। दिखाओ कि एक row, एक invoice, और दोनों copies के लिए `200` आता है।
4. **Security।** Body को test secret से sign करो (`openssl dgst -sha256 -hmac "test_secret_123"`, या ऊपर वाला Python script), उसे signature header में भेजो और raw body पर verify करो। Body का एक character बदलो और `401` दिखाओ।
5. **Sweep और reconcile।** 15-मिनट वाला sweep बनाओ, और तीन sentences में बताओ कि आपके provider के लिए nightly reconciliation कैसे काम करेगा।

**आपका काम पूरा है जब आप** समझा सको कि "पहले reply" से events क्यों खोते हैं, दिखा सको कि दो copies साथ आने पर आपका duplicate check टिका रहता है, दिखा सको कि छेड़छाड़ की गई request reject होती है, और बता सको कि दो दिन के outage में छूटे events आप कैसे पकड़ोगे।
