## ये क्या है

**Vibe coding** का मतलब है code खुद type करने की जगह, एक AI agent को describe करके software बनाना कि आपको क्या चाहिए। Andrej Karpathy, एक जाने-माने AI researcher, ने February 2025 में एक post में ये शब्द बनाया। उन्होंने एक ऐसा style बताया जिसमें आप vibes के आगे झुक जाते हो, AI जो लिखे उसे accept कर लेते हो और code को मुश्किल से देखते हो। ये phrase इतनी तेज़ी से फैला कि Collins Dictionary ने "vibe coding" को 2025 का Word of the Year बना दिया।

उस original, बिना review वाले style की भी अपनी जगह है। Weekend prototype के लिए, अपने laptop पर एक one-off script के लिए, या फेंक देने वाले demo के लिए ये ठीक है। लेकिन जिस भी चीज़ में दूसरे लोगों का data, पैसा, passwords या private notes हों, उसके लिए ये risky है, क्योंकि किसी ने check ही नहीं किया कि code करता क्या है। **ये lesson review वाला version सिखाता है**: ज़्यादातर code Claude लिखता है, और goal आप set करते हो, हर step आप check करते हो और क्या ship होगा ये आप तय करते हो। जब कोई interviewer "vibe coding" कहे, तो पता करो कि उनका मतलब कौन-सा है।

**Claude Code**, Anthropic का coding agent है। **Agent** एक ऐसा AI है जो सिर्फ़ text replies नहीं देता, बल्कि एक loop में actions लेता है। एक chatbot आपको copy करने के लिए code suggest करता है। Claude Code आपके project में काम करता है: files पढ़ता है, लिखता और edit करता है, tests और builds जैसे commands चलाता है, errors पढ़ता है और फिर से try करता है। इसे आप terminal में, VS Code या किसी JetBrains IDE में, Claude desktop app में, या browser में claude.ai/code पर use कर सकते हो।

यहाँ skill चालाक शब्दों की नहीं है। ये वही skill है जो एक अच्छा team lead एक तेज़ नए colleague के साथ use करता है: goal समझाना, काम को छोटे steps में तोड़ना, जो वापस आए उसे review करना, और साफ़-साफ़ बताना कि क्या बदलना है।

```flow
title: हर feature के लिए एक loop; हर चलते हुए step के बाद commit
आप: एक spec और एक feature -> Claude plan mode में plan बनाता है
Claude plan mode में plan बनाता है -[आप approve या trim करते हो]-> Claude files edit करता है
Claude files edit करता है -> Claude tests और app चलाता है
Claude tests और app चलाता है -> आप diff पढ़ते हो और app try करते हो
आप diff पढ़ते हो और app try करते हो -[चल रहा है]-> Commit, अगला feature
आप diff पढ़ते हो और app try करते हो -[गलत है]-> Precise feedback या rewind
Precise feedback या rewind -> Claude plan mode में plan बनाता है
```

## ये काम कैसे करता है

### 1. Set up करो और cost जानो

Official overview page पर दिए command से Claude Code install करो, फिर एक नए folder में terminal खोलो और `claude` चलाओ। पहली बार ये login करने को कहेगा। उसी folder में `git init` भी चलाओ, ताकि हर change दिख सके और undo हो सके। अगर आपने कभी terminal use नहीं किया, तो docs में एक छोटा terminal guide है।

आपको एक paid Claude plan या Claude Console पर एक API account चाहिए। Claude Code, Free plan में शामिल नहीं है। Anthropic के pricing page पर 28 November 2026 के हिसाब से prices:

| Plan | US dollars में price (28 Nov 2026 को check किया) | Usage |
|---|---|---|
| Free | $0 | सिर्फ़ chat; Claude Code शामिल नहीं |
| Pro | $20 महीना, या yearly billing पर $17 महीना ($200 एक साथ पहले) | Free से ज़्यादा, एक 5-hour और एक weekly limit के साथ |
| Max | $100 महीना | Pro का 5x usage |
| Ultra | $200 महीना | एक हफ़्ते में Pro का 10x usage, verified accounts के लिए कोई 5-hour limit नहीं |

India में plans का bill rupees में आता है, और rupee amount बदल सकता है, इसलिए जिस दिन खरीदो उसी दिन claude.ai/upgrade check करो। Claude Code आपके plan की limits chat के साथ share करता है। Anthropic का pricing page Pro को "for everyday work" और Max को "for all-day work" बताता है। अगर build के बीच में 5-hour limit लग जाए, तो reset का इंतज़ार करो या paid usage credits on करो। कितना use हो चुका है ये देखने के लिए session में `/usage` type करो। ज़्यादा pay करने से पहले, नीचे जैसा एक छोटा app ये test करने का अच्छा तरीका है कि Pro आपके लिए काफ़ी है या नहीं।

### 2. एक छोटा spec लिखो

कोई भी code लिखने से पहले `SPEC.md` में आधा page लिखो: app क्या करता है, उसे कौन use करेगा, तीन से पाँच features जो सच में ज़रूरी हैं, phone पर वो कैसा दिखना चाहिए, और क्या scope से बाहर है। Out-of-scope list सबसे ज़्यादा ज़रूरी है, क्योंकि ये Claude को वो चीज़ें जोड़ने से रोकती है जो आपने कभी माँगी ही नहीं। अगर आपको पक्का नहीं पता कि आपको क्या चाहिए, तो Claude से अपना interview लेने को कहो: "Ask me questions one at a time until you could write SPEC.md, then write it."

### 3. CLAUDE.md से उसे memory दो

हर session एक fresh context के साथ शुरू होता है। Claude हर session की शुरुआत में `CLAUDE.md` पढ़ता है, इसलिए उसमें वो डालो जो वो code से खुद नहीं समझ सकता: app को कैसे चलाना और test करना है, और आपके rules, जैसे "mobile first, 360 px wide", "no paid APIs" या "never put keys in client code"। पहले draft के लिए `/init` चलाओ, फिर lines delete करो। Anthropic के docs हर file को 200 lines से कम रखने का सुझाव देते हैं, क्योंकि हर line हर task पर Claude के attention का कुछ हिस्सा लेती है। अगर आप Claude को एक ही बात पर दो बार correct करते हो, तो एक line जोड़ दो।

### 4. वो controls जो आप use करोगे

| आप ये चाहते हो | ये करो |
|---|---|
| बिना edits के plan लेना | `/plan` और task type करो, या Shift+Tab तब तक दबाओ जब तक mode में plan न दिखे |
| हर command खुद approve करना | Auto mode से manual (default) mode में जाने के लिए Shift+Tab दबाओ |
| देखना कि क्या बदला | `/diff` type करो, या `git diff` चलाओ |
| Claude के आख़िरी edits undo करना | खाली prompt पर Esc दो बार दबाओ, या `/rewind` type करो |
| एक नया, अलग task शुरू करना | `/clear` type करो (`/resume` से वापस आ सकते हो) |
| लंबे session को छोटा करना | क्या रखना है ये बताते हुए `/compact` type करो, जैसे `/compact keep the test commands` |
| Claude को किसी step के बीच में रोकना | Esc दबाओ |

**Permission modes** तय करते हैं कि Claude आपसे पूछे बिना क्या कर सकता है। नए terminal और VS Code sessions **auto mode** में शुरू होते हैं: Claude routine steps के लिए बिना रुके काम करता है, और एक अलग safety model हर action check करके risky actions block करता है, जैसे production deploy, force push या किसी अनजान server पर data भेजना। Anthropic साफ़ कहता है कि auto mode prompts कम करता है लेकिन safety की guarantee नहीं देता। अपने पहले project पर manual mode के बारे में सोचो, जिसमें Claude हर command से पहले पूछता है, ताकि आप सीखो कि वो क्या चलाता है। अपने laptop पर bypass mode कभी use मत करो; docs इसे सिर्फ़ isolated containers तक सीमित रखते हैं।

**Checkpoints backup नहीं हैं।** `/rewind` वो edits undo करता है जो Claude ने अपने file tools से किए, लेकिन shell command से हुआ हर change नहीं। आपकी असली history Git है: हर चलते हुए step के बाद commit करो।

### 5. पहले plan, फिर छोटे steps में build

पहले plan माँगो, उसे पढ़ो, और जो ज़रूरी नहीं उसे काट दो। फिर एक बार में एक feature build करो: layout, फिर data, फिर calculations, फिर saving, फिर deployment। छोटा step मतलब छोटा diff, और छोटा diff ही वो है जिसे आप सच में पढ़ सकते हो। Claude को अपना काम खुद check करने का तरीका दो: tests, या "run the app and check it at 360 px wide"। Built-in `/verify` command, Claude से app build करके चलाने और result देखने को कहता है।

### 6. Diff में red flags पढ़ो

अच्छा review करने के लिए हर line समझना ज़रूरी नहीं। इन चीज़ों के लिए skim करो और जब कोई दिखे तो "क्यों?" पूछो:

- **वो files जिनका आपने ज़िक्र नहीं किया।** Layout fix को settlement maths नहीं छूना चाहिए।
- **Delete किए गए या कमज़ोर किए गए tests।** दबाव में एक agent कभी-कभी fail होते test को उसका expected result बदलकर "fix" कर देता है।
- **नए packages** जिनके लिए आपने हाँ नहीं कहा। हर package ऐसा code है जिस पर अब आप depend करते हो।
- **Secret key** किसी भी ऐसी file में जो browser में चलती है।
- **Size जो task के हिसाब से बहुत बड़ा हो।** One-line bug के लिए 300-line diff हो तो उसका explanation चाहिए।

### 7. Link share करने से पहले security check करो

AI से बने apps को नुकसान पहुँचने का एक आम तरीका कोई चालाक hacking नहीं है। ये खुली छोड़ी गई key या database होता है। किसी और को link मिलने से पहले:

- **Client code में कोई secret key नहीं।** Next.js में, जिस भी variable का नाम `NEXT_PUBLIC_` से शुरू होता है, वो हर visitor को भेजे जाने वाले JavaScript में copy हो जाता है। ये prefix सिर्फ़ उन values के लिए use करो जिन्हें publish करना safe है।
- **`.env`, `.gitignore` में है**, और आपकी git history में कोई key नहीं है।
- **हर Supabase table पर row-level security।** Supabase की browser key public होने के लिए ही बनी है; row-level security तय करती है कि हर user कौन-सी rows पढ़ या बदल सकता है। Secret (service role) key इन rules को skip कर देती है, इसलिए उसे server पर ही रहना चाहिए।
- **Input को server पर check करो**, सिर्फ़ form में नहीं।
- फिर Claude से सीधे पूछो: "Review this project for exposed secrets, tables without row-level security and unchecked input. List each problem with the file."

## एक example से समझो

ये एक उदाहरण वाली कहानी है; समय भी सिर्फ़ उदाहरण के लिए हैं, measure नहीं किए गए। Nisha, Pune में तीन दोस्तों के साथ एक flat share करती है और WhatsApp chat में bills बाँटते-बाँटते थक चुकी है। वो product designer है, developer नहीं।

**Spec।** वो `SPEC.md` लिखती है: "एक one-page web app। एक bill जोड़ो: amount, किसने pay किया, कौन-कौन share करता है (pay करने वाला हमेशा share करता है)। दिखाओ कि किसे किसको देना है, सबसे कम payments में। Phone पर चले। Browser में save हो; कोई login नहीं। Rupees, पूरे numbers। Scope से बाहर: accounts, बराबर न होने वाले splits, payment links।" वो `claude` चलाती है, `/init` type करती है, और Claude से spec पढ़कर सवाल पूछने को कहती है। Claude पूछता है कि क्या कोई bill सिर्फ़ कुछ flatmates में share हो सकता है। हाँ, वो कहती है: जब कोई बाहर गया हो, तो groceries तीन लोगों में बँटती हैं।

**Plan, और उसका push-back।** Plan mode में Claude एक Next.js app propose करता है, जिसमें एक server, एक form, एक bill list, एक settlement function, local storage और tests हैं। Nisha पूछती है: "There is no login and no database. Is there a simpler stack?" Claude दो options देता है: plain HTML और JavaScript, या tests के लिए Vitest के साथ एक छोटा Vite app। वो Vite चुनती है, क्योंकि वो plain static files में build होता है जिन्हें Vercel host कर सकता है, और Vitest से maths test करना आसान हो जाता है। वो सिर्फ़ step one approve करती है: page और form। ये उसके phone पर चलता है। वो commit करती है।

**वो bug जो tests ने पकड़ा।** Step three, यानी settlement maths, के लिए वो पहले tests माँगती है। एक test ऐसा case use करता है जिसे वो हाथ से check कर सकती है: Nisha, Aarti और Meera में share होने वाली groceries के लिए Nisha ₹1,000 pay करती है। ₹1,000 को तीन से भाग दो तो ₹333.33 आता है, इसलिए किसी एक को एक rupee ज़्यादा देना होगा। Claude एक rule-based test भी लिखता है: shares का जोड़ हमेशा bill के बराबर होना चाहिए। वो test fail होता है। पहले version ने सबको ₹333 दिए, जिनका जोड़ ₹999 होता है, यानी एक rupee गायब हो जाता है। Claude cause समझाता है और बचा हुआ rupee pay करने वाले को देकर इसे ठीक करता है:

```js
export function splitBill(amount, payer, people) {
  const share = Math.floor(amount / people.length); // 1000 / 3 -> 333
  const shares = Object.fromEntries(people.map((p) => [p, share]));
  shares[payer] += amount - share * people.length; // payer is a sharer: 333 + 1 = 334
  return shares;
}
// splitBill(1000, "Nisha", ["Nisha", "Aarti", "Meera"])
// -> { Nisha: 334, Aarti: 333, Meera: 333 }; Aarti and Meera each owe Nisha 333
```

खोया हुआ एक rupee वो आँखों से कभी नहीं पकड़ पाती। Rule-based test ने उसे पकड़ा, और अगर बाद का कोई change यही गलती वापस लाए तो ये उसे भी पकड़ लेगा।

**एक red flag।** 360 px screen पर table ठीक करते समय Claude का diff settlement file को भी edit करता है। Nisha पूछती है क्यों। वो एक ऐसा rename था जिसका इस fix से कोई लेना-देना नहीं था। वो Esc दो बार दबाती है, rewind करती है, और "change only the CSS" जोड़कर फिर से पूछती है।

**Shipping।** Deploy करने से पहले वो step 7 वाला security review माँगती है। कोई keys नहीं हैं और कोई server नहीं है, इसलिए एक ही finding निकलती है कि `.env`, `.gitignore` में नहीं है; Claude उसे जोड़ देता है। शाम को वो Vercel पर deploy करती है। अगली सुबह उसके flatmates app use करते हैं। इसमें लगभग पाँच घंटे लगे, जिनमें से ज़्यादातर समय ये तय करने में गया कि उसे क्या चाहिए।

## आम गलतियाँ

**एक ही message में पूरा app माँगना।** आपको एक बड़ा, बिना test किया उलझा हुआ ढेर मिलता है जिसे आप review नहीं कर सकते। एक बार में एक feature माँगो।

**Spec skip करना।** Spec के बिना Claude अंदाज़ा लगाता है, और गलत अंदाज़ा आपको तब दिखता है जब वो उसके ऊपर build कर चुका होता है। क्या scope से बाहर है, वो भी लिखो।

**ज़रूरत से ज़्यादा बड़ा plan accept करना।** Agents अक्सर ज़रूरत से बड़ा stack propose करते हैं। Approve करने से पहले पूछो "is there a simpler way?"।

**ऐसे changes accept करना जो आपको समझ नहीं आते।** Explanation माँगो। Code, उसके bugs और उसकी security के owner आप हो।

**Auto mode या checkpoints को अपना safety net मान लेना।** Auto mode एक model का judgement है, guarantee नहीं, और checkpoints कुछ changes miss कर देते हैं। हर चलते हुए step के बाद commit करो।

**Keys वहाँ रखना जहाँ browser उन्हें देख सके।** Client code में या किसी `NEXT_PUBLIC_` variable में रखा secret public ही है। Secrets को server-side environment variables में और ऐसी `.env` file में रखो जिसे git ignore करता है।

**Database खुला छोड़ देना।** बिना row-level security वाली Supabase table को कोई भी पढ़ सकता है, और अक्सर बदल भी सकता है, जिसके पास आपके app की public key है, और वो key हर visitor के पास होती है।

**कभी न खत्म होने वाले "fix it" loops।** अगर वही bug दो corrections के बाद भी बचा रहे, तो रुक जाओ। `/clear` चलाओ, फिर exact steps, expected और actual result, और आपने क्या सीखा, इनके साथ एक नया prompt लिखो, और किसी भी change से पहले cause पूछो।
