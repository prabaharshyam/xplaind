## ये क्या है

LangGraph एक open-source Python और JavaScript framework है, जिससे agents और multi-step AI workflows को **graphs** की तरह बनाया जाता है। एक graph के चार हिस्से होते हैं:

- **State**: एक typed dictionary जिसमें वो सब रहता है जो run को पता है, जैसे messages, ticket id और एक proposed credit।
- **Nodes**: functions जो state पढ़ते हैं और सिर्फ़ वही fields लौटाते हैं जो वो बदलते हैं। Node model call कर सकता है, tool call कर सकता है या plain code चला सकता है।
- **Edges**: आगे कौन-सा node चलेगा। **Conditional edge** एक function है जो state पढ़कर अगले node का नाम लौटाता है।
- **Checkpointer**: हर step के बाद state को एक `thread_id` के नीचे save करता है, ताकि run pause हो सके, resume हो सके, restart झेल सके और replay हो सके।

Agent loop एक छोटा graph है: एक model node, एक tool node, और एक conditional edge जो दोनों के बीच तब तक loop करता है जब तक model tools माँगना बंद न कर दे। Workflow fixed edges वाला graph है। LangGraph आपको दोनों को एक ही system में मिलाने देता है।

ये lesson एक ही graph शुरू से आखिर तक बनाता है। चेन्नई के एक broadband provider के पास support tickets आते हैं। Billing tickets में बिना service वाले दिनों के लिए credit मिल सकता है, और हर credit billing system तक पहुँचने से पहले एक supervisor को approve करना होता है।

```flow
title: Support-ticket graph (हर step के बाद state save होती है, हर thread_id के लिए अलग)
START -> classify
classify -[billing]-> billing_agent | outage के दिन देखता है, credit propose करता है
classify -[outage]-> outage_agent
billing_agent -[credit zero से ज़्यादा]-> approve_credit | interrupt: supervisor फ़ैसला करता है
billing_agent -[कोई credit नहीं]-> reply
approve_credit -[approve हुआ]-> apply_credit | billing system को एक ही बार call करता है
approve_credit -[reject हुआ]-> reply
apply_credit -> reply
outage_agent -> END
reply -> END
```

### पूरा graph

इसे एक बार ऊपर से नीचे तक पढ़ो। Model और billing system की जगह छोटे stand-ins हैं, इसलिए ये बिना API key के चलता है। इसे `ticket_graph.py` नाम से save करो; आगे के blocks इसी के नाम use करते हैं।

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Ticket(TypedDict, total=False):
    messages: Annotated[list, add_messages]  # reducer: new messages are appended
    ticket_id: str
    category: str              # "billing" or "outage"
    outage_days: int
    proposed_credit_inr: int
    approved_credit_inr: int   # 0 means the supervisor said no
    credit_ref: str

# Stand-ins for real systems, so the graph runs with no API key.
OUTAGE_DAYS = {"TKT-4471": 3}     # the network status tool
CREDITS = {}                      # the billing system, keyed by idempotency key

def add_credit(key: str, amount_inr: int) -> str:
    return CREDITS.setdefault(key, f"CR-{len(CREDITS) + 1:04d}")  # same key, one credit

def classify(state: Ticket) -> dict:
    text = state["messages"][-1].content.lower()   # a model call in real life
    return {"category": "billing" if "bill" in text else "outage"}

def route_ticket(state: Ticket) -> str:
    return "billing_agent" if state["category"] == "billing" else "outage_agent"

def billing_agent(state: Ticket) -> dict:
    days = OUTAGE_DAYS.get(state["ticket_id"], 0)
    return {"outage_days": days, "proposed_credit_inr": min(days * 100, 500)}

def outage_agent(state: Ticket) -> dict:
    return {"messages": [("ai", "There is a fibre cut in your area. We will update you by 6 pm.")]}

def approve_credit(state: Ticket) -> dict:
    decision = interrupt({                          # the run pauses here
        "ticket_id": state["ticket_id"],
        "proposed_credit_inr": state["proposed_credit_inr"],
        "reason": f"{state['outage_days']} days without service",
    })
    # On resume this node runs again from the top, and interrupt() returns the decision.
    return {"approved_credit_inr": decision["credit_inr"] if decision["approved"] else 0}

def apply_credit(state: Ticket) -> dict:
    ref = add_credit(key=state["ticket_id"], amount_inr=state["approved_credit_inr"])
    return {"credit_ref": ref}

def reply(state: Ticket) -> dict:
    amount = state.get("approved_credit_inr", 0)
    text = (f"We have added a ₹{amount} credit to your next bill (ref {state['credit_ref']})."
            if amount else "We checked your account. No credit applies this time.")
    return {"messages": [("ai", text)]}

g = StateGraph(Ticket)
for node in (classify, billing_agent, outage_agent, approve_credit, apply_credit, reply):
    g.add_node(node)                                # the node is named after the function
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route_ticket, ["billing_agent", "outage_agent"])
g.add_conditional_edges("billing_agent",
    lambda s: "approve_credit" if s["proposed_credit_inr"] > 0 else "reply",
    ["approve_credit", "reply"])
g.add_conditional_edges("approve_credit",
    lambda s: "apply_credit" if s["approved_credit_inr"] > 0 else "reply",
    ["apply_credit", "reply"])
g.add_edge("apply_credit", "reply")
g.add_edge("outage_agent", END)
g.add_edge("reply", END)
app = g.compile(checkpointer=InMemorySaver())
```

Credit policy (बिना service वाले हर दिन के ₹100, ज़्यादा से ज़्यादा ₹500) इस lesson के लिए एक example है, किसी असली provider का rule नहीं। असली system में `classify` एक model call होगा जो एक label लौटाता है, और `billing_agent` एक छोटा model-and-tool loop होगा (नीचे prebuilt agent देखो)। हर `add_conditional_edges` call के आखिर वाली list उन nodes के नाम बताती है जो route लौटा सकता है। `app.get_graph().draw_mermaid()` graph को Mermaid diagram के रूप में print करता है; ये जल्दी से check करने का तरीका है कि edges वैसे ही हैं जैसा आपने सोचा था।

### State updates कैसे merge होते हैं

Node सिर्फ़ वही fields लौटाता है जो वो बदलता है, और LangGraph उन्हें state में merge कर देता है। ज़्यादातर fields में नई value पुरानी को replace कर देती है। जिस field में **reducer** हो, जैसे `add_messages` वाला `messages`, वो replace होने की जगह combine होता है: नए messages आखिर में जुड़ जाते हैं। इसीलिए `reply` एक message लौटाता है और customer का message बना रहता है। Reducer भूल गए तो `messages` में लिखने वाला हर node पूरी conversation मिटा देगा। शुरुआत में सबसे आम bug यही है।

### Pause, approve, resume

हर run एक thread का नाम लेता है। यहाँ thread ही ticket है, इसलिए TKT-4471 से जुड़ी हर चीज़ एक ही जगह रहती है:

```python
config = {"configurable": {"thread_id": "TKT-4471"}, "recursion_limit": 20}
first = {"ticket_id": "TKT-4471",
         "messages": [("user", "Net was down 3 days. Why is my bill the full ₹799?")]}
out = app.invoke(first, config)
print(out["__interrupt__"][0].value)
# {'ticket_id': 'TKT-4471', 'proposed_credit_inr': 300, 'reason': '3 days without service'}

# Hours later, the supervisor's dashboard resumes the same thread:
out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
print(out["messages"][-1].content)
# We have added a ₹300 credit to your next bill (ref CR-0001).
```

Approval को safe बनाने वाले तीन rules:

- **Resume पर node दोबारा चलता है।** LangGraph `interrupt()` के बाद वाली line से आगे नहीं बढ़ता; वो `approve_credit` को उसकी पहली line से दोबारा चलाता है, और इस बार `interrupt()` फ़ैसला लौटाता है। एक test में `interrupt()` से पहले रखा counter दो बार बढ़ा। इसलिए `interrupt()` से पहले की किसी चीज़ का side effect नहीं होना चाहिए।
- **Action अगले node में रखो।** Credit `approve_credit` में नहीं, `apply_credit` में लगता है। वो node ticket id को idempotency key की तरह use करता है, इसलिए वो दो बार भी चल जाए तो customer को एक ही credit मिलता है।
- **Supervisor edit कर सकता है।** Resume value वही है जो आपका dashboard भेजे। `{"approved": True, "credit_inr": 250}` भेजोगे तो ₹250 लगेगा।

Checkpointer के बिना भी `interrupt()` run रोक देता है, लेकिन `Command(resume=...)` "Cannot use Command(resume=...) without checkpointer" के साथ fail हो जाता है। `compile(interrupt_before=["apply_credit"])` भी pause करता है, लेकिन node के अंदर `interrupt()` से आप supervisor को ठीक वही data भेज सकते हो जो उसे चाहिए।

### Checkpoints: inspect, replay और fork

हर step save होता है, इसलिए आप किसी thread की history पढ़ सकते हो, सबसे नया पहले:

```python
for snap in app.get_state_history(config):
    print(snap.metadata["step"], snap.next, snap.values.get("credit_ref"))
```

"अगर agent ने ₹200 propose किया होता और supervisor ने मना कर दिया होता तो?" ये पूछने के लिए approval से ठीक पहले वाले checkpoint से fork करो:

```python
past = next(s for s in app.get_state_history(config) if s.next == ("approve_credit",))
fork = app.update_state(past.config, {"proposed_credit_inr": 200})
out = app.invoke(None, fork)                       # runs on and pauses again, now at ₹200
out = app.invoke(Command(resume={"approved": False}), config)
print(out["messages"][-1].content)
# We checked your account. No credit applies this time.
```

`invoke(None, ...)` का मतलब है "बिना किसी नए input के इस checkpoint से आगे चलो"। Fork latest state बन जाता है; original steps history में बने रहते हैं।

### Database checkpointer

`InMemorySaver` एक ही Python process के अंदर रहता है। Restart या deploy होते ही हर paused ticket खो जाता है। Production में checkpoints Postgres में रखो, और saver को हर request के अंदर नहीं, server start होने पर एक बार बनाओ:

```python
# pip install "langgraph-checkpoint-postgres==3.2.1" "psycopg[binary,pool]"
import os
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver

pool = ConnectionPool(os.environ["CHECKPOINT_DB_URL"],
                      kwargs={"autocommit": True, "prepare_threshold": 0}, open=True)
saver = PostgresSaver(pool)
saver.setup()                       # creates the checkpoint tables if missing
app = g.compile(checkpointer=saver)
```

दोनों connection settings उन settings में से दो हैं जो `PostgresSaver.from_conn_string` use करता है (row factory saver खुद set करता है)। वो helper एक `with` block है जो अपने आखिर में connection बंद कर देता है, जो script के लिए ठीक है पर web server के लिए नहीं। Connection string को environment variable में रखो, और shutdown पर `pool.close()` call करो।

इस saver के साथ हमने TKT-4471 को एक process में pause किया, उस process को बंद किया, और एक नए process से approve किया: thread तब भी `approve_credit` पर इंतज़ार कर रहा था और normal तरीके से पूरा हुआ।

**Crash और pause अलग चीज़ें हैं।** हमने process को `apply_credit` के अंदर kill भी किया। Thread अपने आप दोबारा शुरू नहीं हुआ। नए process ने उसे `approve_credit` पर पाया, क्योंकि default mode हर step background में save करता है और आखिरी step अभी लिखा नहीं गया था। `app.invoke(None, config)` ने saved फ़ैसले के साथ `approve_credit` दोबारा चलाया, फिर `apply_credit` और `reply`। `invoke` में `durability="sync"` देने पर हर step अगले के शुरू होने से पहले save होता है, इसलिए तब thread `apply_credit` पर इंतज़ार कर रहा था। इससे दो सबक निकलते हैं: आखिरी saved step के बाद वाला node दो बार चल सकता है, इसलिए side effects idempotent बनाओ; और आपको एक छोटा job चाहिए जो अधूरे threads को आगे बढ़ाए।

### Progress stream करना

हर step होते ही देखने के लिए `invoke` की जगह `stream` use करो:

```python
demo = {"configurable": {"thread_id": "TKT-4471-demo"}, "recursion_limit": 20}
for update in app.stream(first, demo, stream_mode="updates"):
    print(update)
# {'classify': {'category': 'billing'}}
# {'billing_agent': {'outage_days': 3, 'proposed_credit_inr': 300}}
# {'__interrupt__': (Interrupt(value={...}, ...),)}
```

हर item एक node का update है, इसलिए chat screen लंबी चुप्पी की जगह "Checking your connection…" दिखा सकती है।

### Model के बिना testing

Routes और nodes plain functions हैं, इसलिए ज़्यादातर tests को model की ज़रूरत ही नहीं:

```python
def test_billing_ticket_goes_to_billing_agent():
    assert route_ticket({"category": "billing"}) == "billing_agent"

def test_credit_waits_for_approval_then_applies():
    config = {"configurable": {"thread_id": "test-1"}, "recursion_limit": 20}
    out = app.invoke({"ticket_id": "TKT-4471",
                      "messages": [("user", "Why is my bill the full amount?")]}, config)
    assert out["__interrupt__"][0].value["proposed_credit_inr"] == 300
    out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
    assert out["credit_ref"].startswith("CR-")
```

जो nodes model call करते हैं, उनमें fixed replies वाला fake model pass करो, और CI में कुछ saved असली tickets पूरे graph से चलाओ।

### Prebuilt agent

पुराने tutorials `langgraph.prebuilt.create_react_agent` use करते हैं। LangGraph 1.0 से ये deprecated है: इसे call करने पर warning आती है कि ये "has been moved to `langchain.agents`"। अभी का prebuilt model-and-tools loop LangChain का `create_agent` है, जो LangGraph पर चलता है:

```python
# pip install "langchain==1.5.2" plus your model provider's package
from langchain.agents import create_agent

def outage_days(ticket_id: str) -> int:
    """Days without service on this ticket's connection."""
    return OUTAGE_DAYS.get(ticket_id, 0)

billing_helper = create_agent(chat_model, tools=[outage_days],
                              system_prompt="You answer broadband billing questions.")
out = billing_helper.invoke({"messages": [("user", "Ticket TKT-4471: why is my bill high?")]})
```

`chat_model` कोई भी LangChain chat model है जो tool calling support करता हो। Result एक compiled graph है, इसलिए ये किसी और बड़े graph का एक node बन सकता है। इसे **sub-graph** कहते हैं। Plain tool loop के लिए `create_agent` से शुरू करो। जब routing, approvals या कई specialists चाहिए हों, तब अपना `StateGraph` लिखो।

### हर run की limit रखो

`recursion_limit` एक run में steps की गिनती पर cap लगाता है। Run वहाँ पहुँचे तो LangGraph `GraphRecursionError` raise करता है, जिसे आप catch करके किसी इंसान को handover में बदल सकते हो। इसे हर call पर खुद set करो: default LangGraph 1.0.5 तक 25 था, 1.0.6 से 1.1.3 तक 10,000 और 1.1.4 से (1.2.24 समेत) 10,007, इसलिए एक draft-and-check loop जो कभी खुद से संतुष्ट न हो, default के रोकने से पहले हज़ारों model calls कर सकता है।

### Basics से आगे

- **Parallel branches.** Conditional edge कई `Send("node", data)` objects लौटाकर एक node को parallel में कई बार चला सकता है, जैसे दस connections एक साथ check करना, और एक reducer results merge करता है।
- **Long-term memory.** Checkpoints एक thread के होते हैं। जो facts customer के साथ हर ticket में चलने चाहिए, जैसे "Tamil पसंद करते हैं", वो `compile(store=...)` के साथ दिए गए एक **store** में जाते हैं, जैसे `InMemoryStore` या एक Postgres store।
- **Functional API.** `langgraph.func` के `@entrypoint` और `@task` बिना graph बनाए ordinary Python functions को checkpoints और interrupts देते हैं।
- **Tracing.** `LANGSMITH_TRACING=true` और एक LangSmith API key के साथ हर node का input और output record होता है, इसलिए "bot ने कुछ अजीब कहा" एक link बन जाता है जिसे आप खोल सकते हो।

**सारे हिस्से एक नज़र में:**

| हिस्सा | Ticket graph में | Gotcha |
| --- | --- | --- |
| Reducer वाली state | `messages` में `add_messages` | Reducer के बिना हर reply history मिटा देता है |
| Conditional edge | `route_ticket` और दोनों lambdas | अपनी possible nodes की list में से ही कोई नाम लौटाना चाहिए |
| Checkpointer | `InMemorySaver`, फिर `PostgresSaver` | In memory में restart पर paused tickets खो जाते हैं |
| `interrupt()` | `approve_credit` के अंदर | Resume पर node अपनी पहली line से दोबारा चलता है |
| Idempotency key | `add_credit` में ticket id | इसके बिना rerun दूसरा credit लगा देता है |
| `recursion_limit` | हर config में 20 | Default अब इतना ज़्यादा है कि आपको बचा नहीं सकता |

## एक example से समझो

चेन्नई में ticket TKT-4471 आता है: "Net was down 3 days. Why is my bill the full ₹799?" Table दिखाती है कि checkpointer ने क्या save किया, ऊपर वाले code के एक असली run से `get_state_history` से पढ़कर।

| Step | अगला node | State में क्या बदला |
| --- | --- | --- |
| 0 | classify | Customer का message और `ticket_id` आ गए |
| 1 | billing_agent | `category` = billing |
| 2 | approve_credit | `outage_days` = 3, `proposed_credit_inr` = 300. Run यहाँ pause होता है और dashboard proposal दिखाता है |
| 3 | apply_credit | Supervisor के approve करने के बाद: `approved_credit_inr` = 300 |
| 4 | reply | `credit_ref` = CR-0001 |
| 5 | (पूरा) | Reply message जुड़ गया; अब दो messages हैं |

तीन बातें देखो। Pause ने अपना कोई अलग checkpoint नहीं जोड़ा: step 2 बस इतना कहता है कि अगला node `approve_credit` है। Approval और side effect अलग steps हैं, इसलिए `approve_credit` दोबारा चले तो भी credit नहीं लगा सकता। और हर value जो कोई auditor पूछ सकता है (₹300 क्यों, कौन-सा credit reference), वो किसी prompt के अंदर छिपी नहीं, एक saved state में है।

उसी ticket के दो variations:

- **Supervisor reject कर देता है।** `approve_credit` के बाद route सीधा `reply` पर जाता है, `apply_credit` कभी नहीं चलता, और customer को बताया जाता है कि कोई credit नहीं बनता।
- **Customer एक हफ़्ते बाद complain करता है।** आप thread TKT-4471 खोलते हो, हर step पढ़ते हो, और original history को छुए बिना step 2 से fork करके test कर सकते हो कि अलग credit से क्या होता।

## आम गलतियाँ

- **एक बहुत बड़ा node.** Classify, look up, approve और reply सब एक function में करने से वो visibility, testability और safe pause points चले जाते हैं जिनके लिए graph बनाया जाता है।
- **`interrupt()` से पहले side effects.** Resume पर node ऊपर से दोबारा चलता है, इसलिए वहाँ रखा SMS, email या credit दो बार हो जाता है।
- **Actions जो idempotent नहीं हैं.** Resumes और crash recovery किसी node को दोबारा चला सकते हैं। हर payment, credit या message API को ticket id जैसी idempotency key दो।
- **Production में in-memory checkpoints.** हर restart या deploy पर paused runs और conversations खो जाती हैं। Database checkpointer use करो और उसका backup लो।
- **हर message के लिए नया `thread_id`.** तब assistant हर बार conversation भूल जाता है। हर conversation या हर ticket के लिए एक thread रखो, और एक thread कभी दो customers के बीच share मत करो।
- **बिना limit बढ़ती state.** हर tool result को हमेशा जोड़ते रहने से prompts लंबे और महँगे हो जाते हैं। किसी node में trim या summarise करो।
- **Default `recursion_limit` पर भरोसा.** 1.2.24 में ये 10,007 steps है। छोटी limit set करो और `GraphRecursionError` catch करो।
- **पुराने tutorials copy करना.** कई अब भी deprecated `create_react_agent` use करते हैं, या `MemorySaver`, जो अब `InMemorySaver` का alias है। Versions pin करो और upgrade से पहले changelog पढ़ो।

## जब आपको LangGraph नहीं चाहिए

- **Simple tool loop**: agent-loop lesson वाला छोटा loop, `create_agent`, या model provider का अपना agent SDK काफ़ी हो सकता है।
- **Fixed pipeline** जिसमें pauses या branching न हो: क्रम से call किए गए ordinary functions पढ़ने और debug करने में ज़्यादा आसान हैं।
- **पहले से किसी दूसरे framework पर चल रही team**, अगर वो framework saved state, pauses और tracing cover करता हो।

LangGraph तब अपनी जगह कमाता है जब आपको हर conversation की saved state, इंसानों के लिए pauses, branching, और किसी run को inspect और replay करने की क्षमता चाहिए।

## Demo से production तक

- **Database checkpointer use करो**, start-up पर एक बार बनाओ, और बाकी production data की तरह उसका backup लो।
- **Durability सोच-समझकर चुनो।** Default background में save करता है; `durability="sync"` हर अगले step से पहले save करता है, जो payments और credits के आसपास extra time के लायक है।
- **अटके threads recover करो।** एक छोटा job चलाओ जो crash के बाद बीच में छूटे threads ढूँढे और उन्हें `invoke(None, config)` से आगे बढ़ाए।
- **हर run पर `recursion_limit` और timeout set करो**, और `GraphRecursionError` को किसी इंसान को handover में बदलो।
- **Graph का version रखो।** Paused thread उसी graph में resume होता है जो उस वक़्त deployed हो। नए state fields optional के रूप में जोड़ो, और ऐसे node का नाम न बदलो, न उसे हटाओ जिस पर paused threads इंतज़ार कर रहे हो सकते हैं। Breaking change के लिए पुराना graph तब तक चलाते रहो जब तक उसके paused threads पूरे न हो जाएँ, या पहले उन्हें approve या cancel कर दो।
- **हर node को thread id के साथ trace करो**, ताकि support ticket सीधे अपने run तक ले जाए।
- **Routes, nodes और कुछ पूरे tickets** CI में fake models के साथ test करो।

## Practice करो

LangChain Academy का free Introduction to LangGraph करो, कम से कम पहले तीन modules।

1. ऊपर वाला ticket graph अपनी पसंद की दो categories के लिए दोबारा बनाओ, ऐसे routing tests के साथ जिन्हें model की ज़रूरत न हो।
2. उसी `thread_id` पर दूसरा message भेजो और दिखाओ कि state में पहला message अब भी है।
3. `interrupt()` से पहले एक counter रखो और उसे दो बार चलते देखो; फिर side effect को अगले node में ले जाओ और idempotency key जोड़ो।
4. `PostgresSaver` के साथ एक run pause करो, अपना Python process बंद करो, और नए process से उसे approve करो।
5. एक पूरे हो चुके thread को approval से पहले वाले step से `update_state` के साथ fork करो, और अलग फ़ैसले के साथ resume करो।

**आपका काम पूरा है जब आप** अपना graph बना सको, बता सको कि state कहाँ save होती है, समझा सको कि approval node दोबारा क्यों चलता है, और अपना program restart करने के बाद एक paused run resume कर सको।
