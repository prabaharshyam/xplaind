## ये क्या है

Git किसी codebase के हर change को रिकॉर्ड करता है। अकेले आप ज़्यादातर commit और push करते हो। Team में **main** branch shared होती है और उसे हमेशा चालू रहना चाहिए, क्योंकि दूसरे लोग, और अक्सर एक live product, उस पर निर्भर होते हैं। इसलिए teams एक routine follow करती हैं:

```flow
dir: LR
main | हमेशा चालू -> आपकी branch | छोटे commits
आपकी branch -[push]-> Pull request | review और automated checks
Pull request -> Teammates comment करते हैं, आप ठीक करते हो -> Pull request
Pull request -[merge]-> main, updated
```

1. काम के एक हिस्से के लिए **branch** बनाओ।
2. साफ़ messages के साथ छोटे **commits** करो।
3. Push करो और **pull request** (PR) खोलो।
4. Teammates **review** करते हैं; automated checks चलते हैं।
5. जो flag हो उसे ठीक करो, फिर **merge** करो।

जब दो लोग एक ही lines बदलते हैं, तो Git **merge conflict** उठाता है, और नतीजा कोई इंसान तय करता है।

इस lesson में हम आपके साथ चलेंगे, Mumbai की एक brokerage के project के तीसरे हफ़्ते में, जब आप एक market-data client में retries जोड़ते हो, review करवाते हो और एक teammate के change से conflict सुलझाते हो। Lesson के अंत तक आप हर step में सहज हो जाओगे।

## ये काम कैसे करता है

### Branches

Branches किसी commit की तरफ़ इशारा करने वाले सस्ते labels हैं। `git switch -c fix/gst-rounding` एक बनाता है और आपको उस पर ले जाता है। Branches के नाम इस हिसाब से रखो कि वो क्या करती हैं:

| Prefix | किसके लिए | Example |
| --- | --- | --- |
| `feat/` | नया feature | `feat/retry-market-data` |
| `fix/` | Bug fix | `fix/gst-rounding` |
| `docs/` | Documentation | `docs/setup-guide` |
| `chore/` | Tooling, dependencies | `chore/update-pandas` |

अपनी पहली branch से पहले client की naming convention देख लो।

### Commits

हर commit एक काम करे और बताए कि क्यों:

| कमज़ोर | मज़बूत |
| --- | --- |
| "fix" | "Fix GST rounding to two decimals for invoices over ₹1 lakh" |
| "wip" | "Add retry wrapper for market data client (no callers yet)" |
| "changes" | "MD-214: retry market data calls with backoff on 429 and 503" |

कई teams messages के आगे ticket id लगाती हैं। छह महीने बाद, साफ़ history से ही कोई भी, आप भी, समझ पाता है कि code ऐसा क्यों दिखता है।

### Pull requests

PR में वो context होता है जो reviewer को चाहिए:

- **क्या** बदला और **क्यों**।
- आपने इसे **कैसे test किया**।
- **कोई risky बात**: performance, security, behaviour में बदलाव।
- Ticket का link, और जो कुछ दिखता है उसके लिए screenshots।

PRs छोटे रखो। 200 lines की PR को ध्यान से review मिलता है; 3,000 lines वाली पर बस मुहर लग जाती है और bugs छिप जाते हैं।

### Review दोनों तरफ़ चलता है

जब आप **review कर रहे हो**, तो style से पहले behaviour और risk देखो: क्या ये सही काम करता है, क्या टूट सकता है, क्या test हुआ है? जब **आपका review हो रहा हो**, तो हर comment का जवाब दो, या तो code बदलकर या ये समझाकर कि क्यों नहीं, और इसे कभी personally मत लो। Review code के बारे में है, आपके बारे में नहीं।

### ताज़ा रहना और conflicts सुलझाना

जब तक आपकी PR इंतज़ार करती है, main आगे बढ़ जाता है। नए main को अपनी branch में `git merge main` से लाओ, या अगर team rebase पसंद करती है तो `git rebase main` से। अगर दोनों तरफ़ वही lines बदली हैं, तो Git file में conflict पर निशान लगा देता है:

```text
<<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = Decimal("0.18")
>>>>>>> main
```

ऊपर वाला हिस्सा आपकी branch का है; नीचे वाला main का। (Rebase के दौरान sides उलट जाते हैं: HEAD main है और नीचे वाला आपका commit।) आप file को सही **final** version में edit करते हो, जो अक्सर दोनों को मिलाता है, markers हटाते हो, tests चलाते हो, फिर `git add` और commit करते हो।

### Protected branches और history

Clients अक्सर main को **protect** करते हैं: सीधे push नहीं, review और passing checks ज़रूरी। इसे कभी बायपास मत करो। और जिस branch को कोई और use कर रहा हो, उसे कभी **force-push** मत करो: ये उनके पैरों तले history दोबारा लिख देता है और उनका काम खो सकता है।

### Secrets

Git में commit हुई API key file delete करने के बाद भी history में रहती है। Secrets को environment variables में रखो, secret files को `.gitignore` में डालो, और अगर कभी कोई key leak हो जाए तो उसे **तुरंत rotate** करो, फिर सफ़ाई करो।

## एक example से समझो

आप Mumbai की एक brokerage के साथ project के तीसरे हफ़्ते में हो। आपका ticket, MD-214: market-data client में retries जोड़ना, जो market खुलते वक़्त कभी-कभी rate-limited हो जाता है।

```text
git switch main && git pull
git switch -c feat/retry-market-data
# edit, test
git add src/marketdata/client.py tests/test_client.py
git commit -m "MD-214: retry market data calls with backoff on 429 and 503"
git push -u origin feat/retry-market-data
```

**PR।** आपके description में लिखा है कि क्या बदला, कि आपने एक fake server से test किया जो दो बार 429 लौटाता है, और एक risk flag किया है: सबसे बुरी हालत में retries मिलाकर 7 seconds जोड़ देते हैं, और dashboard 10 seconds पर time out होता है।

**Review।** Reviewer Farhan कहता है कि कुल retry time 3 seconds पर cap कर दो। आप बदल देते हो, cap के लिए एक test जोड़ते हो, "Done, capped at 3s total, test added" लिखकर जवाब देते हो, और push करते हो।

**Conflict।** इस बीच Priya ने उसी client में एक change merge किया जिसने configurable timeout जोड़ा। अब आपकी branch conflict कर रही है। आप main को merge करते हो, दोनों तरफ़ पढ़ते हो, उसका नया timeout setting **और** अपना retry wrapper दोनों रखते हो, tests चलाते हो, और push करते हो।

| Step | Command या action | नतीजा |
| --- | --- | --- |
| शुरुआत | `git switch -c feat/retry-market-data` | आपकी अपनी branch |
| काम save करना | `git commit -m "MD-214: ..."` | एक साफ़ commit |
| Share करना | `git push -u origin ...` और PR खोलना | Review और checks शुरू |
| Review का fix | Retries को 3 s पर cap करने वाला नया commit | Farhan का comment सुलझा |
| Conflict | `git merge main`, edit, test, commit | दोनों changes रखे गए |
| ख़त्म करना | Checks green, approval, merge, branch delete | main में आपका feature है |

Checks green हो जाते हैं, Farhan approve करता है, आप merge करते हो और branch delete कर देते हो।

## आम गलतियाँ

- **विशाल pull requests।** काम बाँटो; लंबे diffs में reviewers bugs चूक जाते हैं।
- **"wip" और "changes" जैसे commit messages।** बाद में कोई नहीं जानेगा कि क्यों।
- **Secrets commit करना।** Environment variables और `.gitignore` use करो; leak हुई हर key तुरंत rotate करो।
- **Conflicts आँख बंद करके सुलझाना।** हर conflict में "mine" चुनने से teammate का fix गिर जाता है। दोनों तरफ़ पढ़ो।
- **Shared branches को force-push करना।** History सिर्फ़ उन branches पर दोबारा लिखो जिन्हें कोई और use नहीं करता।
- **Branch को हफ़्तों पुरानी होने देना।** main को नियमित रूप से merge करते रहो ताकि conflicts छोटे रहें।

## Practice करो

नीचे link किया GitHub flow पढ़ो, और Pro Git का basic branching और merging वाला chapter भी।

1. **एक असली PR।** अपनी किसी repository में branch बनाओ, दो छोटे commits करो और ठीक description के साथ pull request खोलो।
2. **एक conflict।** जानबूझकर बनाओ: main पर और अपनी branch पर एक ही line बदलो, फिर merge करके उसे सुलझाओ।
3. **Review।** किसी दोस्त की PR, या किसी open-source की, review करो और दो काम के comments छोड़ो।

**आपका काम पूरा जब:** आप बिना डरे merge conflict सुलझा सको और ऐसा PR description लिख सको जिसे कोई अजनबी review कर सके।
