## ये क्या है

तीन cost levers जो साथ मिलकर काम करते हैं:

- **Model tiering** (या routing)। हर request को सबसे capable model की ज़रूरत नहीं होती। Classify करना, extract करना या आसान सवालों के जवाब देना एक छोटे, सस्ते, तेज़ model से करवाओ, और सिर्फ़ मुश्किल वाली requests बड़े model को भेजो।
- **Reasoning effort।** आज के models जवाब देने से पहले सोचते हैं, और उन thinking tokens का bill output tokens की तरह बनता है, भले आप वो text कभी न देखो। Model कितना सोचे, ये एक effort setting तय करती है। आसान, ज़्यादा volume वाले काम को default की ज़रूरत कम ही पड़ती है।
- **Batching।** जिस काम का जवाब seconds में नहीं चाहिए, वो provider के **batch API** से जाता है: आप एक साथ बहुत सारी requests upload करते हो और results बाद में बड़ी छूट पर लेते हो। Examples हैं रात में documents tag करना, कल के tickets का summary बनाना और किसी archive को re-score करना।

शब्दों पर एक note। इस lesson में "batching" का मतलब provider का discount वाला, asynchronous product है। **Continuous batching** कुछ और है: वो तरीका जिससे vLLM जैसा serving engine आपके अपने GPUs पर एक साथ बहुत सारी requests pack करता है। "Inside LLM inference: prefill, decode and the KV cache" lesson उसे cover करता है।

तीनों levers इस पर टिके हैं कि आप अपना traffic जानते हो: कितनी requests आसान हैं, और कितनी रुक सकती हैं।

```flow
title: हर request कहाँ जाती है
Incoming work -> क्या ये घंटों रुक सकता है?
क्या ये घंटों रुक सकता है? -[हाँ]-> आधी क़ीमत पर Batch API | अपने id से results match करो, failures retry करो
क्या ये घंटों रुक सकता है? -[नहीं]-> छोटा model, low effort -> Validator पास हुआ?
Validator पास हुआ? -[हाँ]-> Answer
Validator पास हुआ? -[नहीं, लगभग 7%]-> बड़ा model -> Answer
Fit summaries जैसे मुश्किल tasks -[सीधे]-> बड़ा model
```

ये lesson Pune की एक HR-tech company की resume-screening service को follow करता है, जो महीने में 400,000 resumes process करती है।

## ये काम कैसे करता है

### तीन tiering patterns

- **Task के हिसाब से fixed।** हर feature वो सबसे सस्ता model use करता है जो उसके evals पास करे। Standard form से extraction के लिए शायद छोटा model काफ़ी हो; legal summary के लिए बड़ा चाहिए हो सकता है। ये सबसे simple और सबसे common pattern है। यहीं से शुरू करो।
- **Cascade।** पहले छोटा model try करो, उसका output check करो, और सिर्फ़ check fail होने पर बड़े model पर escalate करो। ये उन tasks के लिए ठीक है जहाँ एक सस्ता check अच्छे और ख़राब output में फ़र्क कर सके, जैसे structured extraction।
- **Router।** एक classifier, या एक छोटा model, मुश्किल का अंदाज़ा लगाकर पहले ही model चुनता है। RouteLLM जैसे research systems ये preference data से सीखते हैं। Router chat के लिए ठीक है, जहाँ आप एक के बाद एक दो calls नहीं झेल सकते और check करने के लिए अभी कोई output भी नहीं होता।

हर route को अपना eval चाहिए। असली सवाल "क्या छोटा model अच्छा है?" नहीं, बल्कि "क्या वो उन requests पर काफ़ी अच्छा है जो हम उसे भेजते हैं?" है।

### Cascade का cost formula

हर item पर cascade का ख़र्च है छोटी call, और जो हिस्सा escalate होता है उसके लिए बड़ी call:

`cost per item = small cost + escalation rate × large cost`

Escalate हुए items दोनों calls का पैसा देते हैं। तो दसवें हिस्से की क़ीमत वाला छोटा model, 40% escalation के साथ, अकेले बड़े model का 0.1 + 0.4 = 0.5 पड़ता है: आधी क़ीमत, अगर quality बनी रहे। 20 गुना या उससे ज़्यादा के price gap पर, जैसे Haiku 5.5 और Sonnet 5.5 के बीच, cascade तब तक सस्ता रहता है जब तक लगभग हर item escalate न होने लगे। पैसा कम ही risk होता है। Risk दो चीज़ें हैं: वो ग़लत जवाब जो check निकल जाने देता है, और escalate हुई requests का extra इंतज़ार।

### Validators और उनका miss rate

क्या escalate होगा, ये check तय करता है, तो इसे भी किसी और model की तरह test करो। सस्ते checks layers में लगाओ:

1. **Format।** क्या output schema के हिसाब से parse होता है?
2. **Range।** क्या values सही लगती हैं? जैसे, years of experience 0 से 50 के बीच, और कम से कम एक skill।
3. **Grounding।** क्या जवाब source में मौजूद है? जैसे, candidate का नाम, ज़्यादातर listed skills और last employer resume text में होने चाहिए। ये उन गढ़े हुए values को पकड़ता है जो format में बिल्कुल ठीक दिखते हैं।
4. **Call से मिलने वाले signals।** जो response `max_tokens` पर पहुँचकर रुक गया, या कोई refusal, वो failure है, जवाब नहीं।

फिर छोटे model को एक labelled golden set पर चलाओ और **miss rate** गिनो: जो outputs ग़लत थे, उनमें से कितने हर check पास कर गए? Format checks ज़ोरदार failures पकड़ते हैं। चुपचाप वाली errors (एक भरोसेमंद लगने वाला पर ग़लत employer) उन्हें पास कर जाती हैं। Free text के लिए model का ख़ुद कहा "unsure" या एक सस्ता judge model एक signal जोड़ सकता है, पर उसका miss rate भी इसी तरह नापो।

### Reasoning effort और thinking tokens

Claude models पर `output_config.effort` में `low`, `medium`, `high`, `xhigh` या `max` दिया जाता है। ये thinking समेत सारे output tokens को shape करता है। November 2026 के हिसाब से default Claude Haiku 5.5 और Claude Opus 5.5 पर `medium` है और Claude Sonnet 5.5 पर `high`। Anthropic आसान, ज़्यादा volume वाले काम के लिए `low` suggest करता है।

तीन gotchas:

- **Thinking `max_tokens` में गिनी जाती है।** बहुत tight `max_tokens` जवाब को बीच में काट सकता है। जगह छोड़ो, और `stop_reason == "max_tokens"` को failure मानो।
- **Thinking switches हर model पर अलग हैं।** Haiku 5.5 पर `high` effort या उससे नीचे आप `thinking: {"type": "disabled"}` भेज सकते हो। Sonnet 5.5 और Opus 5.5 इसे error के साथ reject करते हैं, तो वहाँ effort घटाओ।
- **Effort एक चौथा tier है।** Cascade बनाने से पहले बड़े model को कम effort पर भी test करो। कभी-कभी उससे एक ही model और एक ही cache में quality बनी रहती है।

हर route के लिए `usage.output_tokens` पढ़ो। अगर output tokens दिखने वाले जवाब से बहुत ज़्यादा हैं, तो आपका पैसा thinking में जा रहा है।

### Batching: ये कैसे चलता है

ये 28 November 2026 के हिसाब से Anthropic के Message Batches rules हैं; बाक़ी providers details में अलग हैं।

- **Price:** input और output tokens पर 50% छूट। OpenAI और Google भी discount वाले batch modes देते हैं; उनकी मौजूदा terms check करो।
- **Speed:** ज़्यादातर batches एक घंटे के अंदर ख़त्म हो जाते हैं, पर जो request 24 घंटे में process नहीं होती वो expire हो जाती है। जिस काम का कोई इंतज़ार कर रहा हो, उसे कभी batch मत करो।
- **Size:** हर batch में 100,000 requests या 256 MB तक। Results 29 दिन तक मिलते रहते हैं।
- **Results:** ये किसी भी order में आ सकते हैं। अपने `custom_id` से match करो। हर item `succeeded`, `errored`, `canceled` या `expired` होता है, और आख़िरी तीन का bill नहीं बनता।
- **Limits:** batches की अपनी rate limits हैं, जो सारे models में shared हैं: per minute requests, और queue में इंतज़ार कर रही requests पर एक cap (Build tier पर 300,000)। ये real-time limits से अलग हैं, और batches पर ramp limits लागू नहीं होतीं। इसलिए रात का बड़ा job उन per-minute token limits को ख़त्म नहीं करता जिन पर दिन में recruiters निर्भर हैं।
- **Batch में allowed नहीं:** streaming, fast mode और server-side fallbacks।

### इस picture में caching

Prompt caching, tiering और batching के साथ जुड़ जाती है। Stable हिस्सा पहले रखो (instructions, फिर job description) और उसे `cache_control` से mark करो। Claude Opus 5.5, Sonnet 5.5 और Haiku 5.5 कम से कम 512 tokens के prefixes cache करते हैं; इससे छोटा prefix बिना किसी error के आम तरह process होता है। 5-minute cache write की क़ीमत input price का 1.25 गुना है और 1-hour write की 2 गुना। Reads बहुत सस्ते हैं। Batches में cache hits best effort होते हैं, क्योंकि requests किसी भी order में चलती हैं। 1-hour cache use करो, और जैसा Anthropic suggest करता है, बाक़ी submit करने से पहले prefix लिखने के लिए एक request पहले भेजो।

| Claude Opus 5.5 | $4 | $20 | $2 | $10 | $0.20 |

Per token Sonnet 5.5, Haiku 5.5 से 20 गुना महँगा है। हर cost review से पहले prices दोबारा check करो और उनके साथ check date लिखो।

### Code में एक cascade

Low effort पर छोटा model, layers में checks, और बड़ा model सिर्फ़ तब जब कोई check fail हो:

```python
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()
SMALL, LARGE = "claude-haiku-5-5", "claude-sonnet-5-5"   # check the models page for current names

PROMPT = ("Return only JSON with name, years_experience, skills and "
          "last_employer (null if absent). Copy names exactly as written.\n\n")

class Resume(BaseModel):
    name: str
    years_experience: float
    skills: list[str]
    last_employer: str | None = None

def extract(model, effort, text):
    r = client.messages.create(
        model=model, max_tokens=2000,              # thinking counts toward max_tokens
        output_config={"effort": effort},
        messages=[{"role": "user", "content": PROMPT + text}])
    if r.stop_reason != "end_turn":                # cut off or refused: treat as a failure
        return None, r.usage
    return "".join(b.text for b in r.content if b.type == "text"), r.usage

def valid(raw, text):
    if raw is None:
        return None
    try:
        item = Resume.model_validate_json(raw)
    except ValidationError:
        return None
    page = text.lower()
    words = item.name.lower().split()
    if not words or not all(w in page for w in words):          # name must be in the resume
        return None
    if not 0 <= item.years_experience <= 50 or not item.skills:
        return None
    found = sum(s.lower() in page for s in item.skills)
    if found < 0.8 * len(item.skills):                          # most skills must be in the text
        return None
    if item.last_employer and item.last_employer.lower() not in page:
        return None
    return item

def cascade(text, stats):
    raw, _ = extract(SMALL, "low", text)
    stats["small"] += 1
    if item := valid(raw, text):
        return item
    stats["escalated"] += 1
    raw, _ = extract(LARGE, "high", text)
    return valid(raw, text)                                      # None goes to a person
```

ख़ाली name `if not words` check में fail होता है और crash होने की जगह escalate होता है। Escalation rate रोज़ track करो। अगर ये बढ़े, तो कोई नए तरह का input आया है और बचत घट रही है।

### Fit summary, cached और batched

एक hiring drive में हर resume के लिए job description एक जैसा होता है, तो वो पहले जाता है और caching के लिए mark होता है:

```python
import time

def run_batch(items, job_description):
    batch = client.messages.batches.create(requests=[
        {"custom_id": it["id"],                                  # your id: 1-64 letters, digits, - or _
         "params": {"model": LARGE, "max_tokens": 4000,
                    "output_config": {"effort": "medium"},
                    "system": [{"type": "text",
                                "text": "You screen resumes for this role.\n\n" + job_description,
                                "cache_control": {"type": "ephemeral", "ttl": "1h"}}],
                    "messages": [{"role": "user",
                                  "content": "Write a five-line fit summary.\n\n" + it["text"]}]}}
        for it in items])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    done, retry = {}, []
    for r in client.messages.batches.results(batch.id):         # any order: key by custom_id
        if r.result.type == "succeeded":
            m = r.result.message
            done[r.custom_id] = "".join(b.text for b in m.content if b.type == "text")
        else:                                                    # errored, expired or canceled
            retry.append(r.custom_id)
    return done, retry
```

`retry` को एक नए, छोटे batch में भेजो, या अगर recruiters को सुबह तक चाहिए तो real-time path पर। Batch outputs को बिल्कुल वैसे ही validate करो जैसे real-time वालों को। एक sample पर `usage.cache_read_input_tokens` check करो: अगर ये zero पर ही रहे, तो prefix में कुछ बदल रहा है।

## एक example से समझो

Pune की एक HR-tech company अपने clients के लिए resumes screen करती है। हर resume का structured extraction होता है (name, experience, skills, last employer) और job description के हिसाब से एक fit summary बनती है। Volume महीने में 400,000 resumes है, जिनमें से लगभग 80% hiring drive से पहले वाली शाम को bulk में upload होते हैं।

नीचे के सारे figures assumed token counts के साथ एक illustration हैं, मिसाल के तौर पर ₹90 का एक dollar और ऊपर की 28 November 2026 वाली prices लेकर। आपके अपने numbers `usage` logs से आएँगे।

**पहले।** सब कुछ Claude Sonnet 5.5 पर real time में उसके default `high` effort पर चलता है। हर resume पर:

- Extraction: 3,400 input tokens ($0.0068) और 900 output tokens, जिनमें लगभग 650 thinking हैं ($0.009)। कुल $0.0158।
- Fit summary: 5,000 input tokens ($0.010) और 1,400 output tokens, जिनमें लगभग 1,050 thinking हैं ($0.014)। कुल $0.024।

यानी हर resume पर $0.0398, महीने में $15,920, लगभग ₹14.3 lakh। ध्यान दो कि हर call में अकेली thinking ही 40% से ज़्यादा है।

**Step 1: golden set पर validator चुनना।** Team 500 resumes को हाथ से label करती है और गिनती है कि कितने resumes में हर field सही है:

| Path | Escalate हुए | Checks पास करने वाले ग़लत outputs | पूरी तरह सही resumes |
| --- | --- | --- | --- |
| सिर्फ़ Sonnet 5.5 | लागू नहीं | लागू नहीं | 489 (97.8%) |
| सिर्फ़ Haiku 5.5 | लागू नहीं | लागू नहीं | 466 (93.2%) |
| Cascade, format और range checks | 15 (3%) | 34 में से 22 | 476 (95.2%) |
| Cascade, साथ में grounding checks | 35 (7%) | 34 में से 7 | 489 (97.8%) |

सिर्फ़ format वाला validator 3% escalation पर आकर्षक लग रहा था, पर वो 34 ग़लत outputs में से 22 miss कर गया। Grounding checks escalation rate को दोगुने से ज़्यादा कर देते हैं और बड़े model की quality के बराबर पहुँच जाते हैं। Team इन्हें चुनती है।

**Step 2: levers एक-एक करके लगाना।**

| Lever | क्या बदलता है | बाद में महीने का ख़र्च | बचत |
| --- | --- | --- | --- |
| शुरुआत | हर चीज़ के लिए Sonnet 5.5, real time | ₹14.33 lakh | कोई नहीं |
| 1. Extraction के लिए cascade | Low effort पर Haiku 5.5: हर resume पर $0.0005, साथ में escalations के लिए 7% × $0.0158 | ₹9.22 lakh | ₹5.11 lakh |
| 2. Fit summaries पर कम effort | Medium effort: thinking घटकर लगभग 400 tokens, summary cost $0.0175 | ₹6.88 lakh | ₹2.34 lakh |
| 3. Bulk uploads को batch करना | 80% resumes आधी क़ीमत पर | ₹4.13 lakh | ₹2.75 lakh |
| 4. Job description को cache करना | 2,000-token prefix, 90% calls उसे cache से पढ़ती हैं (batches में 1-hour writes, real time में 5-minute) | ₹3.45 lakh | ₹0.68 lakh |

Table को वैसे पढ़ो जैसे एक reviewer पढ़ेगा:

- **Lever 1:** escalations की cost, सारी छोटे-model calls की कुल cost के दोगुने से भी ज़्यादा है। Escalation rate का हर point bill पर दिखता है।
- **Lever 2:** effort के बदलाव को अपना eval चाहिए था। Recruiters ने दोनों settings पर 100 summaries को blind-rate किया और कोई फ़र्क नहीं दिखा। उस check के बिना ये बस एक अंदाज़ा होता।
- **Lever 3:** batching अपने से पहले की हर चीज़ को 0.6 से गुणा कर देता है (80% आधी क़ीमत पर, 20% पूरी क़ीमत पर)।
- **Lever 4:** यहाँ caching की बचत छोटी है क्योंकि prefix 5,000 input tokens में से सिर्फ़ 2,000 है। 400-token वाले extraction instructions बिल्कुल cache नहीं होते: वो 512-token minimum से नीचे हैं।

Bill महीने में लगभग ₹14.3 lakh से घटकर लगभग ₹3.45 lakh हो जाता है, क़रीब 76% कम, और golden-set accuracy और recruiter ratings वैसे ही रहते हैं। दिन के uploads real time में ही रहते हैं। वहाँ जो 7% resumes escalate होते हैं वो दो calls का इंतज़ार करते हैं, इसलिए team उस path की p95 latency अलग से track करती है।

## आम गलतियाँ

- **छोटा model अंदाज़े से चुनना।** हर route के evals चलाओ। सस्ता और ग़लत, महँगा पड़ता है।
- **कम escalation rate पर भरोसा करना।** सिर्फ़ format check करने वाला validator सही format वाले पर ग़लत जवाब पास कर देता है। Golden set पर उसका miss rate नापो।
- **Cost per successful task की जगह cost per call गिनना।** Escalations, retries और इंसानों के fixes भी जोड़ो।
- **Thinking tokens को नज़रअंदाज़ करना।** बड़े model पर default effort से reasoning bill की सबसे बड़ी line बन सकती है। हर route के लिए effort set करो और evals से check करो।
- **`max_tokens` बहुत tight रखना।** Thinking इसमें गिनी जाती है, तो जवाब कट जाते हैं और model failures जैसे दिखते हैं।
- **Users के सामने वाले काम को batch करना।** Batches आम तौर पर एक घंटे में ख़त्म होते हैं पर 24 घंटे तक ले सकते हैं।
- **Fail हुए batch items खो देना।** `custom_id` से match करो, errored और expired items retry करो, और writes idempotent रखो ताकि reruns से duplicates न बनें।
- **Escalation की latency भूल जाना।** Chat में cascade सबसे मुश्किल सवालों को सबसे slow बना देता है। एक router या एक ही model users के लिए बेहतर हो सकता है।
- **ऐसा prefix cache करना जो cache हो ही नहीं सकता।** वो बहुत छोटा है, हर request में बदलता है, या दिन के uploads के बीच 5-minute cache expire हो जाता है।

## Tiering और batching कब फ़ायदे के नहीं

- **कम volume।** बचत engineering के समय से कम पड़ती है।
- **हर request urgent है**, तो batching fit नहीं होता।
- **छोटा model आपके evals में fail होता है** उस traffic पर जो आप उसे भेजोगे, और बड़े model पर कम effort setting से भी फ़ायदा नहीं होता।
- **Cascade के escalate करने के लिए कोई भरोसेमंद check नहीं है**, और router के लिए कोई साफ़ signal भी नहीं।

## Demo से production तक

- **Escalation rate, validator miss rate और cost per successful task track करो**, हर feature के लिए, हर हफ़्ते।
- **Golden set दोबारा चलाओ** हर model, prompt या effort बदलाव पर। Model बदलने पर effort दोबारा sweep करो, क्योंकि levels अलग-अलग models पर अलग बर्ताव करते हैं।
- **Batch failures संभालो** id से, retries, एक report और deadline से पहले एक real-time fallback के साथ।
- **Urgent और batch काम अलग रखो।** Batch की अपनी limits हैं; workspace limits use करो ताकि बेकाबू job real-time quota ख़त्म न कर दे।
- **Prices dates के साथ record करो** हर cost comparison में, और हर review से पहले उन्हें दोबारा check करो।

## Practice करो

अपने provider की batch processing guide और RouteLLM post पढ़ो।

1. एक feature चुनो और 50 golden cases पर एक छोटा और एक बड़ा model चलाओ। हर एक के लिए accuracy, output tokens (thinking समेत) और per case cost record करो।
2. Format, range और grounding checks के साथ एक cascade बनाओ। Escalation rate और validator का miss rate report करो।
3. उन्हीं 50 cases पर बड़े model को दो effort levels पर चलाओ और quality और output tokens compare करो।
4. 100 non-urgent requests एक batch के रूप में submit करो, fail हुए items को `custom_id` से retry करो, और cost की तुलना real-time calls से करो।
5. Worked example जैसी एक lever-by-lever table लिखो, अपने `usage` numbers और dated prices के साथ।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 9 batching और inference cost cover करता है, और chapter 10 model routers।

**आपका काम पूरा है जब आप** एक feature के लिए cost, quality और latency की lever-by-lever table दिखा सको और हर route को उसके eval से justify कर सको।
