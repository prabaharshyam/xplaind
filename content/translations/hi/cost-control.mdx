## ये क्या है

Hosted model को किया गया हर call **token** के हिसाब से bill होता है; token यानी एक शब्द या शब्द का एक टुकड़ा। **Cost control** का मतलब है ये जानना कि कौन-से features, users और steps वो tokens खर्च कर रहे हैं, और users को नुकसान पहुँचाए बिना वो खर्च घटाना। एक request के bill के चार हिस्से होते हैं:

- **Fresh input**: system prompt, tool definitions, history, retrieve किया गया text और user का message, पूरी input price पर।
- **Cache reads and writes**: input का वो हिस्सा जो provider के prompt cache से आता है या उसमें save होता है, काफ़ी कम या थोड़ी ज़्यादा price पर।
- **Output**: दिखने वाला reply, input price से कई गुना price पर।
- **Thinking**: reasoning model के छिपे हुए reasoning tokens. ये output की तरह bill होते हैं, चाहे response में इनमें से एक भी न दिखे।

```flow
title: एक request में पैसा कहाँ जाता है
dir: LR
System prompt और tools | हर call पर वही, इसलिए cache हो सकते हैं -> Input bill
History और retrieve किया text | हर turn के साथ बढ़ता है -> Input bill
User message | आम तौर पर छोटा -> Input bill
Input bill -> Model
Model -[छिपी हुई reasoning]-> Output bill | thinking output की तरह bill होती है
Model -[दिखने वाला reply]-> Output bill
```

इस lesson का ज़्यादातर हिस्सा दो बातों पर टिका है। Token की गिनती में आम तौर पर input ज़्यादा होता है, क्योंकि लंबा fixed prefix हर call पर दोबारा भेजा जाता है। Per token price में आम तौर पर output (thinking मिलाकर) ज़्यादा होता है। इसलिए बड़ी बचत यहीं से आती है: prefix को पूरी price पर दोबारा न भेजना, task की ज़रूरत से ज़्यादा think न करवाना, और जहाँ छोटा model pass करे वहाँ बड़ा model use न करना।

## ये काम कैसे करता है

### पहले नापो

हर call को उसके usage numbers के साथ log करो: fresh input tokens, cache-read tokens, cache-write tokens, output tokens और, जहाँ API बताए, output में thinking का हिस्सा (Anthropic का field `usage.output_tokens_details.thinking_tokens` है; OpenAI भी reasoning tokens `output_tokens_details` के अंदर ही बताता है)। हर call को feature, user, model, effort setting और prompt version से tag करो। तब आप जवाब दे पाओगे: कौन-सा feature सबसे महँगा है, कौन-से users, कौन-सा agent step, और कितना हिस्सा thinking है। सिर्फ़ महीने का total ये सब छिपा देता है।

सिर्फ़ cost per request नहीं, **cost per completed task** track करो। जो सस्ता call fail हो जाए, retry हो या किसी इंसान के पास जाए, वो सस्ता नहीं है।

### Price page पढ़ो, और तारीख लिखो

28 November 2026 तक, Anthropic की API तीन मौजूदा model sizes की price ऐसे रखती है (US dollars per million tokens):

| Model | Input | Output | Cache read | 5-minute cache write | Batch input / output |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | $4 | $20 | $0.20 | $5 | $2 / $10 |
| Claude Sonnet 5.5 | $2 | $10 | $0.10 | $2.50 | $1 / $5 |
| Claude Haiku 5.5, 100,000 tokens तक के prompts | $0.10 | $0.50 | $0.01 | $0.125 | $0.05 / $0.25 |

इससे तीन बातें पढ़ो। Output की cost input से पाँच गुना है। सबसे छोटा model दोनों में सबसे बड़े से 40 गुना सस्ता है। Batch ठीक आधी price है। बाकी providers भी यही structure अलग numbers के साथ use करते हैं, इसलिए उनके मौजूदा pages पढ़ो और जिस तारीख को check किया वो लिख लो।

### Model choice: सबसे बड़ा lever

Classification, साफ़ text से extraction, routing और छोटे replies के लिए छोटा model अक्सर बड़े model के बराबर निकलता है। हर task को अपने eval set पर दो-तीन model sizes के साथ test करो, जो pass करे उनमें सबसे सस्ता use करो, और सिर्फ़ मुश्किल requests बड़े model को भेजो। Batching और model tiering वाला lesson routers को गहराई से cover करता है। Switch करते समय tokens दोबारा गिनो: अलग models अलग tokenizers use कर सकते हैं, इसलिए वही text अलग गिनती के tokens बन सकता है।

### Reasoning tokens और effort

ज़्यादातर मौजूदा models जवाब देने से पहले think करते हैं, और वो thinking पूरी output price पर output की तरह bill होती है। Anthropic की documentation साफ़ कहती है कि पूरी thinking के पैसे लगते हैं, चाहे response में सिर्फ़ summary दिखे या कुछ भी न दिखे, इसलिए दिखने वाले reply की लंबाई bill से match नहीं करती।

Opus 5.5 की prices पर एक छोटा example: एक ticket label जिसमें 10 visible tokens और 90 thinking tokens हैं, उसका output 100 × $20 per million = $0.002 पड़ता है, सिर्फ़ label के $0.0002 का दस गुना।

इसका control है **effort** setting (दूसरे providers पर "reasoning effort")। कम effort यानी कम thinking, और low effort पर simple inputs के लिए model thinking skip भी कर सकता है। Anthropic की API पर default, Opus 5.5 और Haiku 5.5 के लिए `medium` और बाकी ज़्यादातर models के लिए `high` है, इसलिए इसे explicitly set करो। तीन rules:

- **हर route के लिए tune करो।** Chat, tagging और extraction अक्सर low effort पर भी quality बनाए रखते हैं; multi-step maths, code और planning को अक्सर high चाहिए। हर route के लिए eval पर नापो।
- **`max_tokens` में जगह छोड़ो।** Thinking भी इसमें गिनी जाती है। 200-token reply के हिसाब से रखा cap, model के think करने पर answer को truncate कर देता है, और retry की cost उससे ज़्यादा होती है जितना cap ने बचाया।
- **एक conversation के अंदर effort एक जैसा रखो।** Requests के बीच इसे बदलने से prompt cache invalidate हो सकता है।

### Prompt caching

Prompt caching prompt के लंबे, न बदलने वाले शुरुआती हिस्से को, जैसे system prompt, tool definitions या कोई बड़ा document, store कर लेती है, ताकि अगले calls उसे सस्ते में read करें। ये prefix match है: पहले tools, फिर system prompt, फिर messages, और किसी भी जगह बदलाव होने पर उसके बाद का सब कुछ invalidate हो जाता है। Anthropic की API पर, November 2026 तक:

- 5-minute cache write की cost input price की 1.25 गुना है और एक read में वसूल हो जाती है। 1-hour write 2 गुना है और दो reads में वसूल होता है।
- एक read की cost ज़्यादातर models पर input की 0.1 गुना है, और Opus 5.5 और Sonnet 5.5 पर 0.05 गुना।
- एक minimum length से छोटे prompts, मौजूदा models पर 512 tokens, cache नहीं होते, और कोई error ये नहीं बताता।

Caching चुपचाप fail होती है। आम वजहें: system prompt के ऊपर के हिस्से में कोई date या request ID, हर बार अलग order में बनने वाली tool definitions, बदली हुई effort setting, दूसरे model पर switch (हर model का अपना cache होता है), या इतना कम traffic कि calls के बीच 5-minute lifetime खत्म हो जाए। Usage में cache-read count check करो। अगर वो zero पर ही रहे, तो वो बदलाव ढूँढो।

**Response caching** अलग चीज़ है: आप पूरे answers store करते हो और दोहराए गए सवालों पर model को skip कर देते हो। इसमें हर hit पर ज़्यादा बचत होती है, पर पुराने या leak हुए answers जाने का risk है। Caching और speed वाला lesson दोनों को cover करता है।

### Batch APIs

जो काम रुक सकता है, जैसे रात की summaries, bulk tagging, eval runs और backfills, वो batch API से जा सकता है। Anthropic की Message Batches API input और output के लिए normal price का 50% लेती है। ज़्यादातर batches एक घंटे में पूरे हो जाते हैं; जो requests 24 घंटे में पूरी नहीं होतीं वो expire हो जाती हैं और उनका bill नहीं बनता। Batch और caching के discounts साथ मिलते हैं, और 1-hour cache batches के लिए सही है क्योंकि उनमें 5 minute से ज़्यादा लग सकते हैं।

### Agents: हर step पर history बढ़ती है

Agent हर step पर पूरी conversation भेजता है, इसलिए हर step के साथ input बढ़ता है। मान लो 4,000-token prefix है और हर step में 1,500 नए tokens. आठ steps में 4,000 × 8 + 1,500 × (0 + 1 + … + 7) = 32,000 + 42,000 = 74,000 input tokens जाते हैं, उस चीज़ के लिए जो एक ही task लगती है। Fixed prefix और पुरानी history cache करो, सिर्फ़ task की ज़रूरत के tools load करो, step limit लगाओ, और लंबे runs में पुराने tool results summarise या clear करो। Agent budgets और kill switches वाला lesson limits को cover करता है।

### भारतीय भाषाएँ और self-hosting

Tokenizer के हिसाब से, वही reply English के मुकाबले Hindi, Tamil या Bengali में कई गुना ज़्यादा tokens ले सकता है, इसलिए जिस भी भाषा में serve करते हो, उसके लिए tokens per request नापो। भारतीय भाषाओं में AI वाला lesson इसे cover करता है।

Open model को self-host करने पर per-token bill की जगह एक fixed महीने का bill आ जाता है। उदाहरण के लिए, मान लो एक GPU server को चलाने में, लोगों का समय मिलाकर, ₹2.5 लाख महीना लगता है। एक batched summary के ₹0.47 पर, API की cost तब बराबर हो जाती है जब आप महीने में लगभग 5.3 लाख summaries भेजते हो (2,50,000 ÷ 0.47)। उससे नीचे API जीतती है, और उससे ऊपर self-hosting तभी जीतता है जब open model वही evals pass करे और server busy रहे। vLLM और total cost of ownership वाले lessons दिखाते हैं कि असली numbers कैसे भरें।

### एक calculator

ये calculator table की prices और ₹94 per dollar का एक illustrative rate use करता है (mid November 2026 में rupee लगभग ₹93 से ₹94 पर trade हुआ)। ये नीचे वाले worked example की rows print करता है।

```python
RATE = 94  # rupees per US dollar: illustrative (about 93 to 94 in mid November 2026)

# US dollars per million tokens, Anthropic API pricing page, checked 28 November 2026
PRICES = {
    "opus-5.5":  {"in": 4.00, "out": 20.00, "cache_read": 0.20, "cache_write": 5.00},
    "haiku-5.5": {"in": 0.10, "out": 0.50, "cache_read": 0.01, "cache_write": 0.125},
}

def cost_inr(model, fresh_in, out, cache_read=0, cache_write=0, batch=False):
    """Rupees for one request. `out` includes thinking tokens, which bill as output."""
    p = PRICES[model]
    usd = (fresh_in * p["in"] + out * p["out"]
           + cache_read * p["cache_read"] + cache_write * p["cache_write"]) / 1e6
    return usd * RATE * (0.5 if batch else 1)

rows = {  # (rupees per request, requests per month)
    "summary, before":  (cost_inr("opus-5.5", 1500, 200), 300_000),
    "summary, batch":   (cost_inr("opus-5.5", 1500, 200, batch=True), 300_000),
    "classify, before": (cost_inr("opus-5.5", 600, 100), 300_000),
    "classify, small":  (cost_inr("haiku-5.5", 600, 10), 300_000),
    "chat, before":     (cost_inr("opus-5.5", 6000, 750), 60_000),
    "chat, after":      (cost_inr("opus-5.5", 1000, 500, cache_read=2700, cache_write=300), 60_000),
}
for name, (per, n) in rows.items():
    print(f"{name:17} ₹{per:.4f} each, ₹{per * n / 1e5:.2f} lakh a month")
```

### Safely घटाना

एक बार में एक ही lever बदलो और पहले और बाद में उस feature के evals चलाओ। Cost और quality साथ-साथ report करो। जब कोई बदलाव पैसा बचाए पर quality थोड़ी घटाए, तो लिख लो कि team ने वो trade मान लिया और क्यों।

### Launch से पहले feature की price तय करना

Pilot से हर user की महीने की cost का अंदाज़ा लगाओ: हर user की requests × एक request की cost. इसे उससे compare करो जो user GST और payment fees के बाद देता है। उदाहरण के लिए, नीचे वाले trimmed chat में ₹1.51 per reply पर, महीने में 600 messages भेजने वाले student की cost ₹906 है, जबकि ₹149 का plan लगभग ₹120 ही लाता है। या तो chat ऐसे सस्ते route पर चले जो अपना eval pass करे, या plan में daily limit हो। Launch से पहले caps लगाओ, और पहले दो हफ़्तों में दोबारा check करो, क्योंकि असली users शायद ही कभी pilot group जैसा behave करते हैं।

## एक example से समझो

Kolkata का एक customer-service platform model calls पर महीने में लगभग ₹6.3 लाख खर्च करता है, सब Opus 5.5 पर, और इसे आधा करना चाहता है। नीचे के सारे volumes और token counts illustrative हैं, ऊपर वाली table से ₹94 per dollar पर price किए गए।

**Step 1: नापो।** Tag किए गए logs तीन features दिखाते हैं:

- **रात की ticket summaries**: हर रात 10,000, महीने में 3 लाख। हर एक में 1,500 input और 200 output tokens. सुबह 10 बजे से पहले इन्हें कोई नहीं पढ़ता।
- **Ticket classification**: महीने में 3 लाख। हर एक में 600 input tokens, पर output 100 tokens है: 10-token का label और 90 tokens की thinking.
- **Live chat**: महीने में 60,000 replies. हर एक में 5,000-token का system prompt और tools, uncached, और साथ में 1,000 tokens की history और सवाल। Output 750 tokens है: 450 visible और 300 thinking.

**Step 2: हर feature की price निकालो।**

- Summaries: (1,500 × $4 + 200 × $20) ÷ 10 लाख = $0.0100, यानी ₹0.94 हर एक, तो 3 लाख × ₹0.94 = ₹2.82 लाख (45%)।
- Classification: (600 × $4 + 100 × $20) ÷ 10 लाख = $0.0044, यानी ₹0.41 हर एक, तो ₹1.24 लाख (20%)। 100 output tokens में से 90 thinking हैं।
- Chat: (6,000 × $4 + 750 × $20) ÷ 10 लाख = $0.0390, यानी ₹3.67 हर एक, तो 60,000 × ₹3.67 = ₹2.20 लाख (35%)।

Total: ₹6.26 लाख।

**Step 3: हर feature पर एक lever बदलो।**

- **Summaries batch API पर जाती हैं।** वही tokens आधी price पर: ₹0.47 हर एक, ₹1.41 लाख महीना। ये सुबह 10 बजे से बहुत पहले तैयार हो जाती हैं।
- **Classification low effort पर Haiku 5.5 पर जाता है।** Opus 5.5 पर सिर्फ़ effort घटाने से thinking हट जाती है (600 × $4 + 10 × $20 = $0.0026, ₹0.24 हर एक, 41% कम)। Low effort पर छोटे model की cost (600 × $0.10 + 10 × $0.50) ÷ 10 लाख = $0.000065, ₹0.0061 हर एक, लगभग ₹1,800 महीना है। 400 labelled tickets पर accuracy 94% से 93% होती है, और team इसे मान लेती है।
- **Chat Opus 5.5 पर ही रहता है।** System prompt को 5,000 से 3,000 tokens तक trim करके cache किया जाता है। दिन का busy traffic 90% hit rate देता है, तो औसतन 2,700 tokens $0.20 per million पर cache reads हैं और 300 tokens $5 per million पर writes. Prompt लगभग 150 शब्दों से छोटे replies माँगता है, जिससे visible output 450 से 200 tokens पर आ जाता है। Thinking 300 पर ही रहती है। `max_tokens` 200 नहीं, 1,200 पर set है, ताकि thinking कभी reply को truncate न करे। Per reply: 1,000 × $4 + 2,700 × $0.20 + 300 × $5 + 500 × $20 = $0.01604, यानी ₹1.51, तो ₹0.90 लाख महीना।
- **Limits.** हर support agent के लिए daily cap, chat के tool use पर step limit, budget के 80% पर spending alert और provider console में hard monthly limit.

| Feature | पहले | बाद में | Lever | Quality check |
| --- | --- | --- | --- | --- |
| रात की summaries | ₹2.82 लाख | ₹1.41 लाख | Batch API, आधी price | पहले की तरह सुबह 10 बजे से पहले तैयार |
| Classification | ₹1.24 लाख | ₹0.02 लाख | छोटा model, low effort | 400 tickets पर 94% से 93%, मान लिया गया |
| Live chat | ₹2.20 लाख | ₹0.90 लाख | छोटा cached prompt, छोटे replies | Satisfaction scores में कोई बदलाव नहीं |
| Total | ₹6.26 लाख | ₹2.33 लाख | | 63% कम |

₹2.33 लाख एक अंदाज़ा है। Team इसे अगले महीने के असली bill से मिलाती है, क्योंकि 90% cache hit rate एक assumption है: रात में, जब chats के बीच 5 minute से ज़्यादा का gap होता है, cache expire हो जाता है और हर reply read की जगह write के पैसे देता है।

## आम गलतियाँ

- **सिर्फ़ दिखने वाला reply पढ़ना।** Model upgrade के बाद bill दोगुना हो जाता है जबकि replies उतने ही लंबे दिखते हैं। वजह thinking tokens हैं: price को दोष देने से पहले usage में thinking count check करो।
- **सब कुछ दोबारा भेजने वाले retries.** Timeout पर तीन तुरंत retries एक 6,000-token prompt को चार बार तक bill करते हैं और overload को और बिगाड़ते हैं। Exponential backoff और jitter के साथ ज़्यादा से ज़्यादा दो retries use करो।
- **ऐसा cache जो कभी hit नहीं होता।** System prompt के ऊपर एक timestamp हर prefix को अलग बना देता है। लक्षण: cache-read tokens zero पर रहते हैं जबकि cache writes, जो plain input से महँगे हैं, आते रहते हैं।
- **हर call पर हर tool.** 200 tokens वाली तीस tool definitions हर step में 6,000 input tokens जोड़ देती हैं, भले ही step को दो ही tools चाहिए हों।
- **Thinking के लिए जगह के बिना `max_tokens` cap.** Replies `max_tokens` stop reason के साथ वाक्य के बीच में रुक जाते हैं, users retry करते हैं, और आप दो बार पैसे देते हो।
- **Cost को completed task के बजाय request के हिसाब से judge करना।** जो model per call 20 गुना सस्ता है पर हर पाँच में से एक बार fail होता है, retries और human review जोड़ने पर ज़्यादा महँगा पड़ सकता है।
- **Quality check किए बिना cost घटाना।** हर बदलाव पर evals चलाओ, और numbers संभालकर रखो।

## जब cost घटाना गलत लक्ष्य हो

- **Feature अभी काम ही नहीं कर रहा।** पहले अपने evals पर quality ठीक करो; optimise बाद में।
- **बचत बहुत छोटी है।** महीने के ₹2,000 बचाना हफ़्तों की engineering या नापी जा सकने वाली quality drop के लायक नहीं है।
- **Latency या trust ज़्यादा मायने रखता है।** High-stakes task पर ऐसा सस्ता model जो धीमा हो या ज़्यादा गलतियाँ करे, support और खोए हुए users में ज़्यादा महँगा पड़ सकता है।

## Demo से production तक

- **हर call को tag करो**, feature, user, model, effort और prompt version से, और सारे token counts और cost store करो।
- **एक cost dashboard बनाओ**: feature के हिसाब से रोज़ का spend, cost per completed task, सबसे heavy users, output में thinking का हिस्सा और cache hit rate, budget और alert threshold की lines के साथ। इसे quality metrics के साथ हर हफ़्ते review करो।
- **हर feature का budget तय करो**, alerts के साथ, और provider पर hard limits लगाओ।
- **बार-बार re-price करो।** Providers prices घटाते हैं और सस्ते models release करते हैं; छह महीने पुराना फ़ैसला अब ज़रूरत से ज़्यादा पैसे दिलवा रहा हो सकता है।
- **सस्ता रास्ता tested रखो**, जैसे एक छोटा fallback model, ताकि costs अचानक बढ़ें तो जल्दी switch कर सको।
