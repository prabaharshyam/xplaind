## ये क्या है

**Big-O notation** बताता है कि input बढ़ने पर algorithm का काम कैसे बढ़ता है। ये आपको seconds की सही गिनती नहीं बताता; ये curve का आकार बताता है। Input दोगुना करने पर काम वही रहता है, दोगुना होता है, या चार गुना?

ये इसलिए मायने रखता है क्योंकि असली data बढ़ता है। जो script 100 test orders को पलक झपकते check कर लेती है, वो Big Billion Days sale में Flipkart seller को मिलने वाले 10 लाख orders पर पूरी रात ले सकती है। Big-O आपको code चलाने से पहले ये अंदाज़ा देता है, और ऐसा approach चुनने देता है जो बड़े data पर भी चले।

| Growth | नाम | 1,000 items का काम | 10 लाख items का काम | Example |
|---|---|---|---|---|
| O(1) | Constant | 1 | 1 | Dict में key ढूँढना |
| O(log n) | Logarithmic | लगभग 10 | लगभग 20 | Sorted list में binary search |
| O(n) | Linear | 1,000 | 10 लाख | हर order को एक बार check करना |
| O(n log n) | Linearithmic | लगभग 10,000 | लगभग 2 करोड़ | Orders को sort करना |
| O(n²) | Quadratic | 10 लाख | 10 लाख करोड़ | हर order की हर दूसरे से तुलना |

```flow
title: Input दोगुना होने पर क्या होता है
Input दोगुना करो -> O(1) | उतना ही काम
Input दोगुना करो -> O(log n) | एक step और
Input दोगुना करो -> O(n) | दोगुना काम
Input दोगुना करो -> O(n²) | चार गुना काम
```

आम classes, अच्छे से बुरे के क्रम में, O(1), O(log n), O(n), O(n log n) और O(n²) हैं। इनसे भी बुरी हैं, जैसे O(2ⁿ), जो सिर्फ़ बहुत छोटे inputs पर चलती हैं।

## ये काम कैसे करता है

किसी code का Big-O निकालने के लिए गिनो कि n बढ़ने पर सबसे ज़्यादा दोहराया जाने वाला step कितनी बार चलता है, फिर सिर्फ़ सबसे बड़ा term रखो और constants छोड़ दो।

- n items पर एक अकेला loop अपनी body n बार चलाता है: **O(n)**।
- उन्हीं items पर loop के अंदर loop n × n बार चलता है: **O(n²)**।
- हर step में problem को आधा करना, जैसे binary search करता है, लगभग log₂ n steps लेता है: **O(log n)**।
- अच्छा sort, जैसे Python का built-in `sorted`, लगभग n × log n comparisons करता है: **O(n log n)**।
- Position से list item पढ़ना, या key से dict value, collection कितना भी बड़ा हो, उतना ही समय लेता है: **O(1)**।

हम constants छोड़ते हैं क्योंकि वो आकार नहीं बदलते। List पर दो बार loop चलाना O(2n) है, जिसे हम फिर भी O(n) लिखते हैं: n दोगुना करने पर दोनों में काम दोगुना ही होता है। छोटे terms भी इसी वजह से छोड़ते हैं: O(n² + n) को O(n²) कहते हैं, क्योंकि जब n 10 लाख हो तो n² वाला हिस्सा बाकी सब दबा देता है।

**Space complexity** यही notation memory के लिए use करती है। हर order ID का set बनाने के लिए O(n) extra space चाहिए; amounts जोड़ने के लिए सिर्फ़ O(1)।

अगर एक step एक microsecond लेता है, तो practice में इन classes का मतलब ये है:

| Complexity | n = 1,000 | n = 10 लाख (1,000,000) | आम example |
|---|---|---|---|
| O(1) | 1 µs | 1 µs | dict lookup |
| O(log n) | 10 µs | 20 µs | binary search |
| O(n) | 1 ms | 1 second | list पर एक pass |
| O(n log n) | 10 ms | 20 seconds | sorting |
| O(n²) | 1 second | लगभग 11.5 दिन | सारे pairs पर nested loops |

आखिरी row ही असली चोट देती है। जो O(n²) तरीका testing में तुरंत चल जाता है, वो production में बेकार हो सकता है।

## एक example से समझो

Priya Bengaluru की एक fintech की payments team में काम करती है। हर रात उसे settlement से पहले उस दिन की file में duplicate UPI transaction IDs flag करने होते हैं। व्यस्त दिन में file में लगभग 20 लाख rows होती हैं।

उसका पहला version हर transaction की तुलना हर दूसरे से करता है:

```python
def has_duplicate(ids):
    for i in range(len(ids)):
        for j in range(i + 1, len(ids)):
            if ids[i] == ids[j]:
                return True
    return False
```

ये O(n²) है। 20 लाख IDs के साथ ये लगभग 2 लाख करोड़ comparisons करता है। Settlement deadline से पहले ये कभी खत्म नहीं हुआ।

उसका दूसरा version पहले list को sort करता है, ताकि duplicates बगल-बगल आ जाएँ, फिर एक pass करता है:

```python
def has_duplicate(ids):
    ids = sorted(ids)
    for i in range(1, len(ids)):
        if ids[i] == ids[i - 1]:
            return True
    return False
```

Sorting O(n log n) है और pass O(n), इसलिए पूरा O(n log n) हुआ। ये कुछ seconds में चल गया।

उसका तीसरा version set use करता है, जो keys का **hash map** है:

```python
def has_duplicate(ids):
    seen = set()
    for t in ids:
        if t in seen:
            return True
        seen.add(t)
    return False
```

हर `in` check और `add` औसतन O(1) है, इसलिए पूरा function O(n) time का है। Set के लिए ये O(n) extra memory लेता है, जो server पर ठीक थी। ये version एक second से कम में चला, और duplicate मिलते ही जल्दी रुक भी जाता है।

Priya ने अपनी team के notes में जो सीख लिखी: code को line-by-line optimise करने से पहले उसका Big-O देखो। O(n²) से O(n) पर जाना किसी भी tuning से बेहतर निकला।

## आम गलतियाँ

**"सादे" call के अंदर loop छिपा होना।** `if x in my_list` एक step जैसा दिखता है, पर list पर ये हर item scan करता है: O(n)। इसे loop के अंदर डालो तो O(n²) हो जाता है। जब membership बार-बार check करनी हो तो set या dict use करो।

**Repetitions की जगह lines गिनना।** पाँच lines जो एक-एक बार चलती हैं, O(1) हैं। दो nested loops के अंदर की एक line O(n²) है। देखो कि सबसे व्यस्त line कितनी बार चलती है।

**चीज़ें बनाने का cost भूल जाना।** List को set में बदलना O(n) है। ये तब सही है जब उसके बाद बहुत सारे lookups करने हों, तब नहीं जब एक ही करना हो।

**Average को worst case मान लेना।** Dict lookups औसतन O(1) हैं, पर खराब hash function उन्हें slow कर सकता है। Quicksort औसतन O(n log n) है और worst case में O(n²)। Interviewers अक्सर दोनों के बारे में पूछते हैं।

**Memory को नज़रअंदाज़ करना।** जो O(n) time वाला solution O(n) extra memory माँगता है, वो तब फिट नहीं हो सकता जब n करोड़ों rows हो। Time के साथ space का cost भी बताओ।

**बहुत जल्दी optimise करना।** अगर n कभी 50 से ज़्यादा नहीं होगा, तो साफ़ O(n²) code चालाक O(n log n) code से बेहतर हो सकता है। Big-O तब मायने रखता है जब n बड़ा हो।
