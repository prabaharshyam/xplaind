## ये क्या है

जब एक language model वो नहीं करता जो आपको चाहिए, तो fix इस पर निर्भर करता है कि असल में ग़लत क्या है। Problems दो तरह की होती हैं, और पाँच मुख्य tools होते हैं।

**Model के पास knowledge नहीं है** (आपकी policies, किसी customer का account, इस हफ़्ते के prices)। Knowledge को query के time, prompt में लाओ:

- **Long context**: पूरे documents prompt में डालो। **Prompt caching** में provider prompt की बिना बदली शुरुआत को store कर लेता है, ताकि दोबारा आने वाली calls उसे सस्ते में पढ़ें।
- **RAG (retrieval-augmented generation)**: अपने documents में search करो और सिर्फ़ कुछ सबसे अच्छे passages prompt में डालो।
- **Tools और agentic search**: model को एक database, एक API या एक search tool call करने दो, result पढ़ने दो और ज़रूरत हो तो फिर से search करने दो।

**Model को काफ़ी पता है पर वो ग़लत behave करता है** (format, tone, steps, edge cases):

- **Prompting**: साफ़ instructions, examples, और API का **structured output**, जिसमें आप एक JSON schema देते हो और reply को उससे match करना होता है।
- **Fine-tuning**: model को आपके examples पर आगे train करो ताकि behaviour अंदर ही built-in हो जाए। ये model के weights बदलता है, इसलिए ये सबसे धीमा और सबसे कम reversible fix है।

छोटा rule: knowledge context में जाती है; behaviour पहले prompt में और सबसे आख़िर में weights में।

```flow
title: चुनने से पहले diagnose करो
क्या ग़लत है? -[उसे कुछ पता नहीं है]-> Knowledge को query के time लाओ
क्या ग़लत है? -[उसे पता है, पर ग़लत करता है]-> Prompting और structured output
Knowledge को query के time लाओ -[छोटा, stable, अक्सर पूछा जाता है]-> Caching के साथ long context
Knowledge को query के time लाओ -[बड़ा, बदलता हुआ या हर user का अलग]-> RAG
Knowledge को query के time लाओ -[live records या कई lookups]-> Tools या agentic search
Prompting और structured output -[high volume पर अब भी महँगा या inconsistent]-> Fine-tune, अक्सर एक छोटा model
```

Mature systems इन्हें मिलाकर use करते हैं, और हर option एक ही test set पर मापा जाता है। ये lesson Pune की एक software company की तीन problems को follow करता है, जिनमें से हर एक को अलग fix चाहिए था।

## ये कैसे काम करता है

### Step 1: knowledge है या behaviour, ये diagnose करो

कुछ भी चुनने से पहले 20 से 30 fail हुए outputs पढ़ो। हर एक के लिए पूछो: क्या ज़रूरी fact prompt में था? अगर नहीं, तो ये knowledge problem है, और style पर कितनी भी instruction या training इसे ठीक नहीं करेगी। अगर fact था और फिर भी जवाब ग़लत आया, ग़लत format में या ग़लत tone में, तो ये behaviour problem है। कई teams ये step छोड़ देती हैं और model को fine-tune कर देती हैं ताकि वो ठीक हो जो असल में missing context था।

### Step 2: behaviour को पहले prompt से ठीक करो

Prompting fast, सस्ता और reversible है: आप एक बदलाव को minutes में test कर सकते हो। किसी भी बड़ी चीज़ से पहले एक दोपहर लगाओ। Task और output format सीधे-सीधे बताओ, एक edge case समेत दो-तीन अच्छे examples जोड़ो, और अपना test set चलाओ। इससे वो fair baseline भी set होता है जिसे हर बाद वाले option को हराना है।

**Format** problems के लिए API का structured output use करो: आप एक JSON schema देते हो और provider model को सिर्फ़ वही replies बनाने देता है जो उसमें fit हों। तब shape guaranteed होता है, पर values फिर भी ग़लत हो सकती हैं, इसलिए उन्हें code में validate करो। Structured output वाला lesson इसे cover करता है। सिर्फ़ valid JSON पाने के लिए fine-tune करना 2026 में आमतौर पर ग़लती है।

### Step 3: knowledge को सबसे सस्ते भरोसेमंद तरीके से लाओ

तीनों options query के time facts को model के सामने रखते हैं। Update करने का मतलब है एक document या एक database row बदलना, retrain करना नहीं।

**Caching के साथ long context।** November 2026 तक, Anthropic के latest Claude models 1 million tokens का input लेते हैं। Caching cost को बहुत बदल देती है। Claude Sonnet 5.5 के Anthropic list prices, 28 November 2026 को check किए गए: input $2 per million tokens, cache read $0.10 (input का 5%), 5-minute cache write $2.50, output $10। तो Sonnet 5.5 पर एक cached corpus हर सवाल पर RAG prompt से कम पड़ता है, जब तक corpus RAG context के लगभग 20 गुना से कम हो। Cache से पढ़ी गई एक 60,000-token handbook उतनी ही पड़ती है जितने 3,000 fresh tokens। दूसरे models और providers caching को अलग तरह price करते हैं (Claude Haiku 5.5 पर एक cache read input का 10% है), इसलिए अपने वाले के लिए हिसाब दोबारा लगाओ।

दिक़्क़तें: default रूप से cache 5 minutes तक use न हो तो expire हो जाता है, इसलिए ये steady traffic के साथ ही फ़ायदा देता है; prompt की शुरुआत में कोई भी बदलाव इसे तोड़ देता है; बहुत लंबे inputs में accuracy गिरती है ("lost in the middle" effect); और लंबे inputs पहले token को धीमा कर देते हैं। "Long context or RAG" lesson इन्हें गहराई से cover करता है।

**RAG।** इसे तब use करो जब corpus बड़ा हो (हर call पर जितना pay करना चाहोगे उससे कहीं ज़्यादा), अक्सर बदलता हो, उसे हर user की permissions का ध्यान रखना हो, या answers को किसी passage को cite करना हो। इसके लिए chunking, indexing और tuning चाहिए, और search जो miss करता है वो ये भी miss करता है।

**Tools और agentic search।** Live, structured data के लिए (एक fixed-deposit rate, एक order status, एक balance), system of record को एक tool से query करो। Documents पर RAG पुराना figure दे सकता है; database query नहीं देगी। Agentic search, जिसमें model step by step ख़ुद search करता है, उन सवालों में fit होता है जहाँ अगला lookup पिछले पर निर्भर करता है। इसकी cost ज़्यादा है: हर step बढ़ती हुई conversation को दोबारा भेजता है। जैसे, 2,000 tokens के instructions में हर बार 3,000 tokens के results जोड़ने वाले छह steps कुल 57,000 input tokens भेजते हैं, जबकि एक RAG call में लगभग 4,000।

### Step 4: fine-tune सिर्फ़ form के लिए, volume पर करो

Fine-tuning उस narrow task में fit होती है जिसमें बहुत सारे अच्छे examples हों और जहाँ prompting काम करता है पर high volume पर बहुत लंबा, बहुत महँगा, बहुत धीमा या फिर भी inconsistent है: 30 labels वाला classification, millions of replies में एक house style, एक छोटा model जिसे एक बड़े model जैसा बनना है।

**Facts retrieval में रहने चाहिए।** दो EMNLP 2024 papers को नाम से जानना फ़ायदेमंद है। Ovadia और साथियों ("Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs") ने पाया कि जानी-पहचानी और पूरी तरह नई, दोनों तरह की knowledge के लिए RAG unsupervised fine-tuning से बेहतर रहा। Gekhman और साथियों ("Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?") ने supervised closed-book question answering में पाया कि नए facts वाले examples धीरे-धीरे सीखे जाते हैं और, सीखने के बाद, hallucination बढ़ाते हैं। Models ज़्यादातर facts pre-training से पाते हैं; fine-tuning उन्हें सिखाती है कि जो पता है उसे कैसे use करें।

"Fine-tuning" में कई methods आते हैं जिनकी data ज़रूरतें अलग हैं:

| Method | Training data | आम use |
| --- | --- | --- |
| Supervised fine-tuning (SFT) | Ideal outputs के साथ जोड़े गए inputs | Format, style, classification, extraction |
| Preference tuning, जैसे DPO | एक बेहतर और एक बदतर answer के जोड़े | Tone, helpfulness, किसे मना करना है |
| Reinforcement fine-tuning | Prompts और answers को score देने वाला एक grader | Check होने लायक answers, कम labels वाले tasks |
| Distillation | एक बड़े model के outputs, SFT data के रूप में | एक task पर बड़े model की नकल करता एक छोटा, सस्ता model |

ज़्यादातर teams LoRA use करती हैं, जो model के सारे weights की जगह एक छोटा add-on train करता है; fine-tuning कैसे काम करती है और practice में fine-tuning वाले lessons इन methods को cover करते हैं। किसी भी plan से पहले दो practical checks आते हैं। पहला, availability: हर model fine-tuning offer नहीं करता, और offer बदलता रहता है। OpenAI ने 8 May 2026 की तारीख़ वाला एक update post किया कि वो अपना fine-tuning platform धीरे-धीरे बंद कर रहा है, जो अब नए users के लिए accessible नहीं है। अपने provider का documentation check करो और तारीख़ लिख लो। Open-weight models जिन्हें आप ख़ुद train और host करते हो, इस risk से बचते हैं पर उनके लिए GPUs और skills चाहिए। दूसरा, distillation के लिए terms of use पढ़ो: कई providers अपने outputs से competing models train करने से मना करते हैं।

### हर option को एक ही test set पर मापो

हर candidate के लिए वही सवाल, graders, और cost और latency measurements use करो। Test set को problem type के हिसाब से बाँटो: वो सवाल जिन्हें private या recent facts चाहिए, और format या behaviour वाले सवाल। पहले group में knowledge options को जीतना चाहिए; अगर नहीं जीतते, तो आपका diagnosis ग़लत था।

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.3f}{p95:>8.0f}")
    return rows
```

### Fine-tuning को सबसे अच्छे सस्ते baseline के सामने price करो

Monthly बचत की तुलना एक छोटी useful life पर build cost से करो। Build cost का मतलब है data इकट्ठा और check करने और evals चलाने में लगा लोगों का time, सिर्फ़ GPU hours नहीं। छोटी life realistic है, क्योंकि एक बेहतर base model अक्सर कुछ ही महीनों में आ जाता है और काम दोबारा करना पड़ता है।

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.414, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
print(finetune_break_even(2_000_000, 0.056, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
```

नीचे का worked example inputs समझाता है। पहली line fine-tuning को एक uncached बड़े model के सामने price करती है: हर महीने ₹7.68 लाख की बचत और 0.5 महीने में break-even। दूसरी उसे उसी model के सामने price करती है जिसमें prompt cached है: हर महीने ₹52,000 की बचत, break-even में 7.7 महीने और छह महीनों में ₹88,000 का net loss। Fine-tune वही, जवाब उल्टा। हमेशा उस सबसे सस्ते option के सामने price करो जो पहले से काम करता है।

## एक worked example

Pune की एक software company की तीन problems। सारी costs उदाहरण के लिए हैं: ये 28 November 2026 को check किए गए Claude Sonnet 5.5 और Haiku 5.5 के list prices, उदाहरण के लिए ₹94 प्रति dollar का rate, और low effort पर माने गए token counts use करती हैं, इसलिए thinking tokens लगभग नहीं हैं। Real responses में `usage` check करो, क्योंकि thinking का bill output के रूप में बनता है। Accuracy figures उस तरह के हैं जो एक team record करेगी, मापे गए results नहीं।

**1. Support bot और हर हफ़्ते बदलने वाली छह handbooks।** Company छह products बेचती है, हर customer सिर्फ़ अपने product की handbook देख सकता है, और हर handbook लगभग 400,000 tokens की है। Cached long context, एक ही product की handbook के लिए भी, हर सवाल पर लगभग ₹4.10 पड़ेगा (cache-read price पर 400,000 tokens, साथ में एक 300-token सवाल और एक 300-token जवाब)। लगभग 4,000 tokens के passages वाला RAG लगभग ₹1.09 पड़ता है। RAG एक metadata filter से हर customer की permissions भी लागू करता है और use किए गए section को cite करता है। तो वो **RAG** चुनते हैं, हर update पर re-index करके।

Crossover मायने रखता है। अगर एक ही 60,000-token handbook होती जिसके बारे में दिन भर पूछा जाता, तो cached long context हर सवाल पर ₹1.09 के मुक़ाबले लगभग ₹0.90 पड़ता, उसे index नहीं चाहिए होता, और वो हर section एक साथ देखता। इसे cross-section सवालों पर test करो, हो सकता है ये बेहतर choice हो।

**2. Ticket summaries अलग-अलग होती हैं और customer की priority छोड़ देती हैं।** Model के पास ticket है; instruction साफ़ नहीं है। **Prompting और structured output**: एक schema जिसमें ज़रूरी `priority` field चार values तक सीमित हो, priority कैसे judge करें इस पर एक rule, और दो examples। मान लो कि 50 test tickets पर सही priority 31 से 46 हो जाती है और format फिर कभी नहीं टूटता। इसमें एक दोपहर लगी।

**3. हर महीने 20 लाख log lines को 30 categories में classify करना।** आज वो Sonnet 5.5 को एक 2,000-token prompt (category definitions और examples) के साथ call करते हैं जो हर बार fresh भेजा जाता है, साथ में लगभग 100 tokens की log line और 20 tokens का output। ये हर line पर लगभग ₹0.41, या हर महीने ₹8.3 लाख है। उनके पास 50,000 labelled lines हैं, और एक vendor एक छोटे open-weight model को fine-tune करने का offer देता है: मान लो build करने में ₹4 लाख, maintain करने में हर महीने ₹40,000, और serve करने में हर line पर ₹0.01।

आज के bill के सामने fine-tuning दो हफ़्तों में पैसा वसूल कर देती है। पर पहले वो prompt को cache करते हैं। लगभग 46 lines per minute पर cache कभी cold नहीं होता, और 2,000-token prompt 512-token minimum से ऊपर है। Accuracy में बिना किसी बदलाव के cost गिरकर हर line पर लगभग ₹0.056 (हर महीने ₹1.13 लाख) हो जाती है। उस baseline के सामने वही fine-tune पैसा वसूल करने में 7.7 महीने लेता है। वो उसी cached prompt के साथ Haiku 5.5 भी try करते हैं: हर line पर लगभग ₹0.004, हर महीने ₹7,500, पर मान लो accuracy 96% से गिरकर 91% हो जाती है। Lines urgent नहीं हैं, इसलिए batch API, जो November 2026 तक Anthropic पर आधी क़ीमत पर है, दोनों में से किसी भी bill को और कम कर देगा।

Volume फ़ैसला करता है। छह महीने की life पर, ऊपर के inputs cached baseline के सामने लगभग 23 लाख lines per month का break-even volume देते हैं। दो नए clients अगले quarter में volume को 1 करोड़ lines per month तक ले जाएँगे। मान लो 10,000 labels पर एक pilot fine-tune test set पर 96% score करता है, Sonnet जितना। 1 करोड़ lines पर fine-tune हर महीने लगभग ₹4.2 लाख बचाता है और लगभग एक महीने में पैसा वसूल कर देता है। Haiku और भी सस्ता होगा, पर उसके 5-point gap का मतलब है हर महीने लगभग 5 लाख ज़्यादा ग़लत tags। तो वो **आज prompt cache करते हैं और बड़े volume के लिए fine-tune करते हैं**, cached prompt को fallback और baseline के रूप में रखते हुए।

| Problem | Diagnosis | Approach | उदाहरण के लिए result |
| --- | --- | --- | --- |
| छह handbooks, हर एक 400,000 tokens की, हर customer का अलग access | Knowledge, बड़ी और permission वाली | Filters के साथ RAG, हर हफ़्ते re-index | Cached long context के ₹4.10 के मुक़ाबले हर सवाल पर ₹1.09 |

| हर महीने 20 लाख log lines, 1 करोड़ तक बढ़ती हुई | Volume पर form | अभी cache, बड़े volume के लिए एक छोटे model को fine-tune | अभी हर महीने ₹8.3 लाख से ₹1.13 लाख; 1 करोड़ पर fine-tune एक महीने में पैसा वसूल |

## आम ग़लतियाँ

- **Facts जोड़ने के लिए fine-tuning।** Facts context में रहने चाहिए, long context, RAG या एक tool के ज़रिए।
- **Prompt को छोड़ देना।** ये सबसे सस्ता fix है, अक्सर काफ़ी होता है, और वो baseline है जिसे बाक़ी सबको हराना है।
- **JSON format के लिए fine-tuning** structured output try करने से पहले।
- **एक छोटे, stable document के लिए RAG बनाना** जिसे cached long context ज़्यादा आसानी से संभाल लेता।
- **Rates या balances जैसे live numbers के लिए documents पर RAG use करना**, एक tool की जगह।
- **Fine-tuning को uncached bill के सामने price करना।** पहले prompt cache करो और एक छोटा model try करो, फिर compare करो।
- **Build cost में लोगों का time छोड़ देना**, या एक लंबी useful life मान लेना।
- **Options को अलग-अलग test sets पर** या अलग graders के साथ compare करना।
- **किसी fine-tuning service के भरोसे plan करना** बिना check किए कि वो आज आपके model के लिए मौजूद है।

## जब चुनाव पहले से साफ़ हो

- **जवाब को private documents cite करने हैं**: retrieval, आप साथ में और जो भी जोड़ो।
- **Data एक database में रहता है**: एक tool, documents का index नहीं।
- **Low volume**: fine-tuning शायद ही कभी पैसा वसूल करती है; prompt improve करो।
- **Task हर कुछ हफ़्तों में बदलता है**: prompts और retrieval retraining से तेज़ी से adapt होते हैं।
- **आपके पास labelled examples नहीं हैं**: fine-tuning अभी possible नहीं है; reviewed outputs से उन्हें इकट्ठा करना शुरू करो।

## Demo से production तक

- **एक test set रखो** जो problem type के हिसाब से बँटा हो, और हर approach के लिए उसे use करो।
- **हर option के लिए quality, cost और p95 latency record करो**, तारीख़ों के साथ।
- **अगर caching पर निर्भर हो तो cache hit rate पर नज़र रखो**; एक चुपचाप गिरावट bill को कई गुना कर सकती है।
- **Break-even दोबारा निकालो** जब prices, volumes या models बदलें।
- **Reviewed outputs इकट्ठा करो** future training data के रूप में, भले अभी fine-tune न कर रहे हो।
- **Fine-tuned models को हर नए base model के सामने दोबारा test करो**, एक अच्छे, cached prompt के साथ।
