## ये क्या है

जब language model वो नहीं करता जो आपको चाहिए, तो उसे सुधारने के तीन मुख्य तरीके हैं:

- **Better prompting**: साफ़ instructions, examples, structure और format।
- **RAG (retrieval-augmented generation)**: आपके documents या data से काम की जानकारी निकालकर prompt में डालना।
- **Fine-tuning**: model को आपके अपने examples पर और train करना ताकि वो कोई behaviour सीख ले।

ये अलग-अलग problems हल करते हैं और अक्सर साथ में use होते हैं। अच्छे से चुनने पर महीनों बचते हैं।

```flow
क्या गलत है? -[model को कुछ पता नहीं: facts, policies, accounts, हाल की घटनाएँ]-> RAG या tools | दोबारा index करके update; sources cite करो
क्या गलत है? -[उसे पता है, पर गलत करता है: format, tone, steps, edge cases]-> पहले Prompting | instructions, examples, एक template
क्या गलत है? -[prompting काम करती है, पर ज़्यादा volume पर लंबी, महँगी या बेतरतीब है]-> Fine-tune, अक्सर छोटा model | बहुत सारे अच्छे examples और evals चाहिए
```

परिपक्व systems तीनों को जोड़ते हैं, और हर एक को एक ही test set पर जाँचा जाता है।

ये lesson पुणे की एक software company की तीन problems को follow करता है जिनमें से हर एक को अलग fix चाहिए था।

## ये काम कैसे करता है

**पहले problem पहचानो।**

- *Model को कुछ पता नहीं* (आपके products, policies, हाल की घटनाएँ, किसी customer का account): ये knowledge problem है। **RAG** या tools use करो। Facts जोड़ने के लिए fine-tuning खराब तरीका है: update करना महँगा है और model फिर भी उन्हें गलत याद रख सकता है।
- *Model को काफ़ी पता है पर task गलत तरीके से करता है* (format, tone, steps, edge cases): पहले **prompting** आज़माओ: instructions, examples, साफ़ format।
- *Prompting काम करती है पर narrow, ज़्यादा volume वाले task के लिए लंबी, महँगी, धीमी या फिर भी बेतरतीब है*: बहुत सारे अच्छे examples पर model को, अक्सर छोटे को, **fine-tune** करने पर विचार करो।

**पहले prompting क्यों।** ये तेज़, सस्ती और पलटने लायक है: आप बदलाव मिनटों में test कर सकते हो। "Model" पर डाले गए कई problems साफ़ instructions और दो अच्छे examples से गायब हो जाते हैं।

**RAG कब ठीक बैठता है।** वो जानकारी जो अक्सर बदलती है (हर हफ़्ते update होने वाली handbook), बड़ी है (हज़ारों documents), private है, या जिसे cite करना ज़रूरी है। Update का मतलब दोबारा index करना है, दोबारा train करना नहीं।

**Fine-tuning कब ठीक बैठता है।**

- बहुत सारे requests पर लगातार style या format;
- ढेर सारे labelled examples वाला narrow classification या extraction task;
- किसी एक task पर छोटे, सस्ते model को बड़े model के बराबर बनाना;
- कई examples ढोने वाले prompts को छोटा करना।

इसे सैकड़ों से हज़ारों quality examples, evaluation, और base model बदलने पर दोहराना चाहिए।

**मिलाओ।** एक आम परिपक्व setup: अच्छी तरह design किया हुआ prompt, knowledge के लिए RAG, और हो सके तो एक ज़्यादा volume वाले step के लिए fine-tuned छोटा model। हर बदलाव को एक ही test set पर evaluate करो।

**Approaches की तुलना:**

| कारक | Prompting | RAG | Fine-tuning |
| --- | --- | --- | --- |
| क्या ठीक करता है | Behaviour, format | गायब या बदलती knowledge | बड़े scale पर लगातार behaviour |
| आज़माने का समय | मिनट | दिन | हफ़्ते |
| ज़रूरी data | कुछ examples | आपके documents | सैकड़ों से हज़ारों labelled examples |
| Update करना | Prompt edit करो | Re-index | Retrain |
| हर request की cost | Prompt की लंबाई के साथ बढ़ती है | Retrieval और context जुड़ते हैं | छोटे model के साथ सबसे कम हो सकती है |
| Citations | नहीं | हाँ | नहीं |

**अंदाज़ा लगाना कि fine-tuning कब वसूल होगी।** मौजूदा approach की मासिक cost की तुलना fine-tuned option से करो: उसकी उपयोगी उम्र पर फैली training cost, आपके volume पर serving cost, और training data बनाने और संभालने का समय। Fine-tuning आमतौर पर ज़्यादा volume वाले, narrow tasks में वसूल होती है जहाँ छोटा model बड़े की जगह ले सके, और कम volume या तेज़ी से बदलने वाले tasks में शायद ही कभी। हिसाब लिख लो, उस volume के साथ जिस पर वो break even होता है।

**पहले prompt fixes test करना।** किसी भी बड़े बदलाव से पहले prompt पर एक दोपहर लगाओ: task और format साफ़ बताओ, एक edge case समेत दो-तीन अच्छे examples जोड़ो, और test set चलाओ। Teams अक्सर हैरान होती हैं कि इससे कितनी problems हल हो जाती हैं, और ये RAG या fine-tuning को परखने के लिए एक सही baseline भी देता है।

**सभी candidates को एक ही test set पर चलाओ।** सबसे निष्पक्ष तुलना वही सवाल, वही graders और वही cost और latency माप use करती है:

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.2f}{p95:>8.0f}")
    return rows

# compare({"prompt v3": prompt_only, "prompt + RAG": with_rag, "fine-tuned small": tuned}, tests, grade)
```

Test set को problem type से बाँटो: वो सवाल जिन्हें private या हाल के facts चाहिए, और वो जो format या behaviour के बारे में हैं। पहले समूह में RAG को जीतना चाहिए और दूसरे में fine-tuning जीत सकती है; अगर नहीं, तो आपका diagnosis गलत था।

**Fine-tuning कब वसूल होती है, numbers में।**

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.40, 0.06, build_cost_inr=600_000, upkeep_per_month_inr=50_000))
```

`build_cost_inr` में सिर्फ़ GPU घंटे नहीं, बल्कि data जमा करने, जाँचने और evals चलाने में लगा लोगों का समय भी होना चाहिए। छोटा `life_months` यथार्थवादी है: नया base model अक्सर महीनों में आ जाता है और काम दोहराना पड़ता है।

**Facts retrieval में रहें।** नई knowledge के लिए दोनों की तुलना करने वाली studies में retrieval आमतौर पर जीतता मिला, और जो facts base model ने कभी नहीं देखे उन पर fine-tune करना भरोसे वाली गलतियों को भी बढ़ावा दे सकता है। रूप सिखाने (format, tone, narrow classification) के लिए fine-tuning और facts देने के लिए retrieval use करो।

**कोशिशों का क्रम।** Prompt, फिर prompt के साथ retrieval या tools, और fine-tuning तभी जब कोई नापा हुआ gap बचे और ऊपर के numbers सही बैठें। हर कदम पिछले को baseline की तरह रखता है।

## एक example से समझो

पुणे की एक software company की तीन problems:

1. *Support bot को एक product handbook से जवाब देने हैं जो हर हफ़्ते बदलती है।* बदलती knowledge: handbook पर **RAG**, हर update पर दोबारा index। Fine-tuning एक हफ़्ते में पुरानी हो जाती।
2. *Ticket summaries का format अलग-अलग होता है और customer की priority छूट जाती है।* Model के पास जानकारी है; instruction साफ़ नहीं है। **Prompting**: एक fixed template, priority का एक rule और दो examples एक दोपहर में 90% cases ठीक कर देते हैं।
3. *बड़े model से महीने के 20 लाख log lines को 30 categories में classify करना बहुत महँगा है।* उनके पास पुराने काम से 50,000 labelled lines हैं। एक छोटे model को **fine-tune** करो: उनके test set पर वो cost और latency के एक छोटे हिस्से में बड़े model की accuracy के बराबर है।

| Problem | Diagnosis | Approach | नतीजा |
| --- | --- | --- | --- |
| Support bot और हफ़्ते भर में बदलती handbook | Knowledge | RAG, हर update पर re-index | हमेशा ताज़ा |
| Ticket summaries अलग-अलग और priority छूटती है | Behaviour | Template, एक priority rule, दो examples | एक दोपहर में 90% ठीक |
| महीने के 20 लाख log lines, बहुत महँगा | Narrow task पर volume | 50,000 labels पर fine-tuned छोटा model | वही accuracy, cost और latency कहीं कम |

## आम गलतियाँ

- **Facts जोड़ने के लिए fine-tuning।** Retrieval use करो।
- **Prompting छोड़ देना।** ये सबसे सस्ता fix है और अक्सर काफ़ी होता है।
- **Fashion देखकर चुनना।** Knowledge बनाम behaviour पहचानो।
- **Evaluation set का न होना।** उसके बिना approaches की तुलना नहीं हो सकती।
- **Maintenance भूल जाना।** Fine-tuned models को दोबारा train करना पड़ता है; RAG को ताज़ा indexes चाहिए।
- **अलग test sets पर** या अलग graders के साथ approaches की तुलना करना।
- **Fine-tuning की cost में लोगों का समय छोड़ देना।**
- **बदलते facts जोड़ने के लिए fine-tuning**, जिसे retrieval बेहतर संभालता है।

## जब चुनाव पहले से साफ़ हो

- **जवाब को private documents cite करने हों**: retrieval, और जो भी जोड़ो।
- **कम volume**: fine-tuning शायद ही वसूल होती है; prompt सुधारो।
- **Task हर कुछ हफ़्तों में बदलता है**: retraining से तेज़ prompts और retrieval ढल जाते हैं।
- **आपके पास labelled examples नहीं हैं**: fine-tuning अभी मुमकिन नहीं; reviewed outputs से उन्हें जमा करना शुरू करो।

## Demo से production तक

- **एक test set रखो**, problem type से बँटा हुआ, और हर approach के लिए उसी को use करो।
- **हर option की quality, cost और p95 latency** तारीखों के साथ दर्ज करो।
- **Prices, volumes या models बदलने पर break-even दोबारा निकालो।**
- **Reviewed outputs को भविष्य के training data की तरह जमा करो**, भले ही अभी fine-tune न कर रहे हो।
- **नए base models अच्छे prompts के साथ आएँ तो** fine-tuned models को उनके मुकाबले दोबारा test करो।

## Practice करो

नीचे link किया गया Chip Huyen का production के लिए LLM applications बनाने पर लेख पढ़ो।

1. अपनी जानी हुई तीन problems के लिए बताओ कि हर एक knowledge problem है या behaviour problem, और एक approach चुनो।
2. एक के लिए दो prompt सुधार आज़माओ और छोटे test set पर नापो।
3. आधा पन्ना लिखो कि उस problem के लिए fine-tuning कब सार्थक होगी।
4. अपने छोटे test set पर अपने मौजूदा prompt और एक सुधारे हुए prompt के साथ compare चलाओ, और fine-tuned option के लिए break-even numbers भरो।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 7 बताता है कि fine-tune कब करना है, और knowledge और रूप के लिए fine-tuning की RAG से तुलना कैसे होती है।
