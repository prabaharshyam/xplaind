## ये क्या है

**LLM gateway** आपकी applications और model providers के बीच की एक service है। Applications हर request एक ही API format में gateway को भेजती हैं। Gateway उसे सही provider और model तक forward करता है, और shared काम हर app में अलग-अलग करने की बजाय एक ही बार संभालता है:

- **Routing**: कौन-सा model और provider इस request को serve करेगा।
- **Failover**: जब कोई provider error दे, timeout हो या आपको rate-limit करे, तब क्या try करें।
- **Keys और access**: teams को gateway keys मिलती हैं; real provider keys सिर्फ gateway में रहती हैं।
- **Rate limits और budgets**: हर team, हर feature या हर user के लिए।
- **Logging और cost**: हर request उसके tokens, cost और latency के साथ, एक ही जगह।

ये lesson Bengaluru की एक fintech को follow करता है, जहाँ चार teams के पाँच AI features में से हर एक अपनी keys से providers को सीधे call करता था।

```flow
title: One gateway in front of every provider
Chatbot -[key chatbot]-> Gateway, 2 or more instances
Claims extraction -[key claims]-> Gateway, 2 or more instances
Nightly summaries -[key batch]-> Gateway, 2 or more instances
Gateway, 2 or more instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails, cool-down]-> Model X, Hyderabad
Model X, Hyderabad -[fails]-> Fallback alias: approved model Y, India
```

हर key की अपनी rate limit और budget होता है। Gateway forward करने से पहले उन्हें check करता है, result log करता है, और provider keys एक secret store में रखता है।

### Gateway पाने के तीन तरीके

| किस्म | Examples | कब चुनें |
| --- | --- | --- |
| Self-hosted, open source | LiteLLM proxy (MIT licence) | Data आपके अपने cloud account और region में ही रहना चाहिए, और आपके पास एक platform team है जो database वाली service चला सके |
| आपके cloud का API management | Azure API Management (उसकी `llm-token-limit` policy), Google Apigee (उसकी LLM token quota policy) | आप दूसरी APIs के लिए पहले से उस cloud का API management use करते हो और ज़्यादातर उसी cloud के models call करते हो |
| किसी vendor का managed gateway | कई vendors आपके लिए host करते हैं | आप छोटे हो, infrastructure चलाने वाला कोई नहीं है, और vendor की data processing locations आपके data के लिए allowed हैं |

फैसला आमतौर पर दो सवालों पर आकर टिकता है। आपका data कहाँ process हो सकता है? और रात को gateway टूटे तो किसे जगाया जाएगा? Managed gateway हर prompt देखता है, इसलिए सबसे पहले ये check करो कि वो data कहाँ process करता है।

## ये कैसे काम करता है

### एक interface और model aliases

ज़्यादातर gateways OpenAI-style chat format लेते हैं और हर provider के लिए उसे translate करते हैं। Apps कभी real model का नाम नहीं लेते। वो `chat-default` जैसे किसी **alias** को call करते हैं, और gateway उसे एक real model से map करता है। हर app को नए model पर upgrade करना gateway config की एक reviewed line बन जाता है, पहले आपके golden set पर test करके।

### Failover की दो layers

अच्छे failover में दो layers होती हैं, और इन्हें दिमाग में अलग-अलग रखना मदद करता है।

1. **एक alias के पीछे deployments.** वही model दो जगह, जैसे Mumbai और Hyderabad। एक fail हो तो gateway दूसरे deployment पर retry करता है।
2. **एक fallback alias.** एक अलग, approved model, जो तभी use होता है जब पहले alias के सारे deployments fail हो चुके हों।

Fail होता हुआ deployment हर request को slow नहीं करना चाहिए। इसे एक **cool-down** (जिसे circuit breaker भी कहते हैं) संभालता है। थोड़े समय में बहुत ज़्यादा failures होने पर gateway उस deployment को एक तय समय के लिए skip करता है। Requests को पहले timeout नहीं झेलना पड़ता। Cool-down खत्म होने पर gateway उस deployment को फिर से try करता है।

### एक gateway configuration

LiteLLM का proxy एक common open-source choice है; दूसरे gateways यही ideas अलग syntax में use करते हैं। एक ही file aliases, deployments, retries, cool-downs और fallback define करती है। LiteLLM 1.111.0 पर check किया गया।

```yaml
# gateway.yaml: the whole gateway in one reviewed file
model_list:
  # Alias chat-default: the same model deployed in two Indian regions.
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>             # in-Region ID or India profile, never APAC or global
      aws_region_name: ap-south-1           # Mumbai
      order: 1                              # used first while healthy
      timeout: 30                           # seconds, normal calls
      stream_timeout: 10                    # seconds, streaming calls
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>
      aws_region_name: ap-south-2           # Hyderabad
      order: 2                              # used when Mumbai fails or cools down
      timeout: 30
      stream_timeout: 10
  # Fallback alias: another provider, also in India, approved and tested on the evals.
  - model_name: chat-backup
    litellm_params:
      model: vertex_ai/<model id>
      vertex_project: os.environ/GCP_PROJECT
      vertex_location: asia-south1          # Mumbai
      timeout: 30

router_settings:
  num_retries: 2                            # retries on 429s and server errors
  allowed_fails: 3                          # more than 3 failures in a minute starts a cool-down
  cooldown_time: 60                         # seconds a cooling deployment is skipped
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL     # keys, limits, budgets and spend live here
```

इसे `litellm --config gateway.yaml --port 4000` से start करो। Load balancer के पीछे दो या ज़्यादा instances चलाओ, सब एक ही database की ओर point करें।

**Bedrock पर एक region trap.** Bedrock के cross-Region inference profiles prompts को उस Region के बाहर process कर सकते हैं जिसे आप call करते हो। APAC profile Asia Pacific के अंदर रहता है, India के अंदर नहीं, और global profile कोई भी supported commercial Region use कर सकता है। कुछ Claude models के लिए Bedrock में अब एक India geographic profile है जो सिर्फ Mumbai और Hyderabad के बीच route करता है। अगर data India में ही process होना चाहिए, तो वो profile या in-Region model ID use करो, और पहले Bedrock Regional availability table check करो: हर model Hyderabad में in-Region नहीं मिलता।

### Apps alias को call करते हैं, provider को नहीं

कोई भी OpenAI-compatible client चलेगा। Request को असल में किसने serve किया, ये देखने के लिए response headers पढ़ो:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=os.environ["GATEWAY_URL"], api_key=os.environ["CHATBOT_KEY"])

raw = client.chat.completions.with_raw_response.create(
    model="chat-default",                       # the alias, never a provider model name
    messages=[{"role": "user", "content": "Explain my last card statement in two lines: ..."}],
)
reply = raw.parse()
print(reply.choices[0].message.content)
print("model group:", raw.headers.get("x-litellm-model-group"))      # chat-backup means it fell back
print("fallbacks:", raw.headers.get("x-litellm-attempted-fallbacks"))
print("cost in USD:", raw.headers.get("x-litellm-response-cost"))
```

### Rate limits और budgets वाली keys

Admin हर feature के लिए एक virtual key बनाता है। Virtual key वो key है जो gateway issue करता है; ये real provider keys से map होती है, जिन्हें team कभी नहीं देखती।

```bash
curl -s "$GATEWAY_URL/key/generate" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"key_alias": "chatbot", "models": ["chat-default", "chat-backup"],
       "rpm_limit": 600, "tpm_limit": 200000,
       "max_budget": 400, "budget_duration": "30d",
       "metadata": {"team": "support", "feature": "chatbot", "owner": "platform-lead"}}'
```

`rpm_limit` इस key के लिए हर मिनट की requests पर cap लगाता है और `tpm_limit` हर मिनट के tokens पर। Fallback alias को भी `models` में list करो: testing में, जिस key को सिर्फ `chat-default` allowed था, उसे backup की जगह एक plain error मिला। Key revoke करने से बाकी कुछ rotate किए बिना एक feature कट जाता है। इस setup को test करते हुए दिखे तीन behaviours जानने लायक हैं:

- **Rate limit और budget अलग तरह से fail होते हैं.** `rpm_limit` पार करने पर HTTP 429 आया, जिसे client थोड़ा रुककर retry कर सकता है। Budget खत्म होने पर `budget_exceeded` type के साथ HTTP 422 आया। उसे retry करना बस समय बर्बाद करता है, इसलिए clients को उसे final मानकर किसी इंसान को alert करना चाहिए।
- **Budgets लगभग होते हैं.** Gateway हर request से पहले budget check करता है, इसलिए जो request line पार करती है वो फिर भी पूरी हो जाती है। 0.05 dollar budget वाले एक test में requests refuse होने से पहले spend 0.065 तक पहुँच गया। Cap को उससे थोड़ा नीचे रखो जितना आप सच में afford कर सकते हो।
- **Reset date check करो.** ये मानने की बजाय कि period आज से शुरू होता है, key बनाने के बाद `/key/info` से `budget_reset_at` पढ़ो। Budgets US dollars में होते हैं, इसलिए अपनी reports में एक stated rate पर रुपये में convert करो।

### Provider का quota ठीक से बाँटना

आपका provider हर model के लिए एक quota देता है, जैसे Mumbai में हर मिनट इतने tokens। हर key उसे share करती है। Rule: **जिन features को कभी quota की कमी नहीं होनी चाहिए, उनकी limits का जोड़ provider quota से कम होना चाहिए, headroom के साथ।** Batch jobs को छोटी limit मिलती है, वो रात को चलते हैं, और 429s पर इंतज़ार करते हैं। Per-key limits के बिना पहला busy job पूरा quota ले लेता है, और customer chatbot fail हो जाता है, भले ही "provider up है"।

### Fallback edge cases

Production में gateways fallbacks पर ही fail होते हैं। इनके लिए plan करो:

- **Streams.** अगर stream पहले token से पहले fail हो, तो gateway अगला deployment try कर सकता है और user को कभी पता नहीं चलता; LiteLLM यही करता है। जब user आधा answer देख चुका हो, तब switch का मतलब है answer restart करना या दो models का text जोड़ना। App में तय करो कि क्या दिखाना है, जैसे "answer बीच में रुक गया, retry करें?"।
- **Tool calls.** ऐसी request को कभी retry मत करो जिसकी tool call पहले ही side effects वाला कुछ चला चुकी हो, जैसे payment या email। ऐसे tools को idempotency key के साथ दोहराने के लिए safe बनाओ, या उन्हें retry मत करो।
- **Prompt caching.** Provider prompt caches आपके साथ move नहीं होते। Fallback के दौरान हर request लंबे system prompt के लिए पूरी price और पूरी latency देती है, इसलिए outage के दौरान cost और time to first token उछलने की उम्मीद रखो।
- **Format और tool-call shape.** Backup model JSON या tool calls को थोड़ा अलग format कर सकता है। Feature के evals fallback alias पर चलाओ, और उसके output पर parser test करो।
- **वो errors जिन पर fall back नहीं होना चाहिए.** Malformed request हर model पर fail होती है। Fall back करने से सिर्फ latency और cost बढ़ती है। Timeouts, 429s और server errors पर fall back करो।
- **टूटी key को छुपाने वाले fallbacks.** एक test में primary की गलत key ने 401 return किया, gateway ने उसे retry नहीं किया, और तुरंत fall back कर दिया। Users को कुछ गलत नहीं दिखा। सिर्फ errors पर नहीं, किसी alias का fallback rate बढ़ने पर भी alert करो।

### Try it: fallback chain में cool-downs

इस simulation में request 3 से request 12 तक Mumbai outage है। देखो कि cool-down कैसे requests को Mumbai का इंतज़ार करने से रोकता है, और बहुत लंबा cool-down कैसे Mumbai के ठीक होने के बाद भी उसे skip करता रहता है।

```python
import random

random.seed(7)
ALLOWED_FAILS = 2      # cool down after more than this many failures
COOLDOWN = 5           # requests to skip a cooling deployment
fails = {"mumbai": 0, "hyderabad": 0, "backup": 0}
cooling_until = {"mumbai": 0, "hyderabad": 0, "backup": 0}

def call(deployment, t):
    # Mumbai has an outage from request 3 to request 12.
    if deployment == "mumbai" and 3 <= t <= 12:
        raise TimeoutError("timed out")
    if random.random() < 0.05:
        raise TimeoutError("timed out")
    return deployment

def gateway(t, chain=("mumbai", "hyderabad", "backup")):
    tried = []
    for d in chain:
        if t < cooling_until[d]:
            continue                       # skip without waiting for a timeout
        try:
            served = call(d, t)
            fails[d] = 0
            return served, tried
        except TimeoutError:
            tried.append(d)
            fails[d] += 1
            if fails[d] > ALLOWED_FAILS:
                cooling_until[d] = t + COOLDOWN
                fails[d] = 0
    return "error", tried

for t in range(16):
    served, tried = gateway(t)
    note = f"(waited on {', '.join(tried)})" if tried else ""
    print(f"request {t:2}: served by {served:9} {note}")
```

Requests 3 से 5 तक हर एक Mumbai timeout का इंतज़ार करती है। फिर Mumbai cool down होता है और requests 6 से 9 सीधे Hyderabad जाती हैं। Request 8 दूसरी layer दिखाती है: Hyderabad में एक random timeout आता है, इसलिए backup जवाब देता है। Request 10 पर cool-down खत्म होता है जबकि Mumbai अभी भी down है, इसलिए requests 10 से 12 फिर उसका इंतज़ार करती हैं और दूसरा cool-down शुरू होता है। Request 13 से Mumbai वापस आ जाता है, पर वो अभी भी cool down हो रहा है, इसलिए use नहीं होता। Timeouts पर इंतज़ार करने और recovery miss करने के बीच का trade-off देखने के लिए `COOLDOWN = 2` और `ALLOWED_FAILS = 0` try करो।

### Region-aware routing और logs

Indian personal data के लिए, उन features के aliases सिर्फ Indian-region deployments की ओर point करने चाहिए। जिन features को दूसरे regions use करने की इजाज़त है, उनके लिए अलग alias रखो। हर call का alias, deployment और region log करो, ताकि audit confirm कर सके कि rule माना गया। Gateway के logs में personal data mask करो: वो हर prompt देखता है, इसलिए unmasked logs उसे आपका सबसे बड़ा sensitive data store बना देते हैं।

### Gateway की cost

ये चलाने, secure करने और available रखने के लिए एक और service है, और हर AI feature इस पर निर्भर है। इसका अपना overhead measure करो: वही requests का set सीधे और gateway के through भेजो, और median और slow (p95) latency compare करो, खासकर streams के लिए time to first token। इसे अपने apps के पास रखो, इसका error rate और database monitor करो, और एक documented emergency path रखो, जैसे एक feature flag जो किसी एक critical feature को सीधे उसके provider पर भेज दे।

## एक worked example

Bengaluru की fintech में चार teams के पाँच AI features हैं। हर team के पास अपनी provider keys हैं, और finance को एक बड़ा monthly bill दिखता है। नीचे के आँकड़े एक typical rollout का illustration हैं, measured results नहीं।

**Trigger.** एक provider outage ने customer chatbot को करीब 50 मिनट तक down रखा। उसी महीने एक nightly statement-summary job सुबह तक खिंच गया और shared token quota का ज़्यादातर हिस्सा use कर गया, इसलिए chatbot ने rate-limit errors भी दिए।

**Setup.** Platform team company के Kubernetes cluster पर gateway को दो instances के रूप में deploy करती है।

- **Keys.** हर feature को team और feature tag वाली अपनी gateway key मिलती है। Provider keys gateway के secret store में चली जाती हैं और rotate होती हैं। पुरानी direct keys दो हफ्ते चलती हैं, फिर revoke होती हैं, ताकि gateway ही अकेला रास्ता बने।
- **Aliases.** `chat-default`, `extract-default` और `embed-default`, हर एक किसी specific model से mapped।
- **`chat-default` के लिए failover.** वही model Mumbai और Hyderabad में, 60-second cool-down के साथ, फिर एक fallback alias जिसमें दूसरे provider का model है, वो भी India में hosted और compliance से approved।
- **Fallback पर evals.** Go-live से पहले team chatbot का 300-question golden set दोनों पर चलाती है। मान लो primary 92% और backup 88% score करता है, दो JSON format failures के साथ जिन्हें एक parser fix ठीक कर देता है। Team outages के लिए 88% accept करती है और runbook में record करती है।
- **Quota sharing.** मान लो Mumbai quota हर मिनट 400,000 tokens है। Chatbot को 200,000 और claims extraction को 100,000 मिलते हैं। Batch job को 60,000 मिलते हैं और वो midnight के बाद चलता है। कुल 360,000, जिससे spikes के लिए headroom बचता है।
- **Budgets और logs.** हर key का एक monthly budget है, 75% पर alert के साथ। हर request team, feature, alias, deployment, tokens, cost और latency के साथ log होती है, personal data mask करके।

**Result.** अगले provider incident में users को errors की जगह थोड़ी देर धीमे answers मिलते हैं, जब तक Mumbai cool down होता है और Hyderabad serve करता है। Fallback-rate alert on-call engineer को बताता है कि क्या हुआ। Feature के हिसाब से पहली cost report दिखाती है कि statement-summary job करीब 40% spend use कर रहा है। वो team उसे एक सस्ते model और provider के batch API पर ले जाती है।

## आम गलतियाँ

- **एक ही gateway instance.** आपने हर AI feature के लिए एक नया single point of failure बना दिया। कई चलाओ।
- **Unapproved models या regions पर fallbacks.** Outage को data चुपचाप ऐसी जगह नहीं भेजना चाहिए जहाँ उसे जाने की इजाज़त नहीं है। इसमें Bedrock APAC या global profiles भी शामिल हैं जब data India में ही रहना हो।
- **Application code में model names.** Aliases use करो ताकि upgrades और swaps एक ही जगह हों।
- **Key limits जिनका जोड़ provider quota से ज़्यादा है.** तब एक busy key फिर भी बाकियों का quota खा सकती है।
- **Budget error को retry करना.** खत्म हुआ budget कुछ seconds में दोबारा नहीं भरेगा। उसे final मानो और किसी को alert करो।
- **Untested fallbacks.** जो fallback कभी चला ही नहीं, वो पहली बार चलने पर output formats या quality तोड़ सकता है।
- **सिर्फ errors पर alert करना.** Fallbacks failures को users से छुपा देते हैं, इसलिए टूटी primary key हफ्तों तक किसी की नज़र में आए बिना रह सकती है।
- **बिना masking के full prompts वाले gateway logs.** Gateway आपके पास का सबसे बड़ा sensitive data store बन जाता है।

## कब gateway ज़रूरत से ज़्यादा है

- **एक provider वाला एक app.** Retries, timeout और billing alert के साथ provider का SDK काफी है।
- **एक छोटी team**, जो gateway जितना समय बचाएगा उससे ज़्यादा उसे चलाने में लगा देगी।
- **एक managed platform**, जो पहले से keys, budgets और routing देता है।

Gateway तब फायदा देता है जब कई teams या apps providers, keys, quota और budgets share करने लगें।

## Demo से production तक

- **दो या ज़्यादा instances चलाओ**, health checks, उनकी अपनी monitoring और एक shared database के साथ।
- **Config Git में रखो**, code की तरह review करो, और model changes golden set पर test करो।
- **हर feature के लिए एक key दो**, rate limit, budget और एक named owner के साथ।
- **Personal data सिर्फ approved regions पर route करो**, और हर call का region log करो।
- **Staging में failover drill करो.** गलत key या blocked endpoint से primary को जानबूझकर तोड़ो। Check करो कि requests फिर भी succeed होती हैं, latency acceptable रहती है, और logs और headers दिखाते हैं कि किस model ने serve किया। Chain में हर बदलाव के बाद दोहराओ।
- **पहले एक low-risk feature roll out करो**, उसके errors, latency और cost पहले से compare करो, फिर बाकियों को एक-एक करके move करो।
