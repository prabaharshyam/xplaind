## ये क्या है

हर AI product एक जैसे शुरू होता है: आपका app एक सवाल model को भेजता है और जवाब दिखाता है। ये अपने आप में पूरा, चलने वाला architecture है। ज़्यादातर असली products यहाँ से parts जोड़कर बढ़ते हैं, और क्रम मायने रखता है।

कई teams जिस क्रम में बढ़ती हैं, वो आम क्रम:

1. **Context बेहतर करो।** Model को सही information दो: documents से retrieval, data lookups, tools।
2. **Guardrails लगाओ।** जो model में जाता है और जो बाहर आता है, दोनों check करो।
3. **Router और gateway जोड़ो।** हर request को सही जगह भेजो, और सारे model calls एक जगह से manage करो।
4. **Caches जोड़ो।** एक ही काम के लिए दो बार पैसे न दो।
5. **Agent patterns जोड़ो।** Loops, कई steps, और ऐसे actions जो दुनिया में कुछ बदलते हैं।

इन सबके साथ, पहले दिन से: **monitoring**, ताकि दिखे कि हर हिस्सा क्या कर रहा है।

ये कोई सख़्त recipe नहीं है। बात ये है कि layer तभी जोड़ो जब कोई असली problem माँगे, ताकि system उतना ही सरल रहे जितना product इजाज़त दे।

```flow
title: बढ़े हुए AI app से गुज़रती एक request
User का सवाल -> Input guardrails | personal data mask, injection block
Input guardrails -> Router | intent: FAQ, account, scope से बाहर
Router -[FAQ]-> Cache | exact या semantic
Cache -[miss]-> Context retrieve करो | documents, data, tools
Router -[account]-> Context retrieve करो
Router -[scope से बाहर]-> तैयार जवाब
Context retrieve करो -> Gateway | keys, limits, retries, fallback
Gateway -> Model
Model -> Output guardrails | format, facts, safety
Output guardrails -[fail]-> Retry या इंसान को दो
Output guardrails -[pass]-> जवाब दो और trace log करो
```

## ये काम कैसे करता है

**Step 1: context बेहतर करना।** Model को सिर्फ़ अपना training data पता होता है और वो जो आप prompt में डालते हो। शुरुआती quality problems ज़्यादातर गायब या पुराने facts की वजह से होती हैं, इसलिए पहला जोड़ आमतौर पर retrieval (documents, database, search index) या tools (order lookup, calculator) होता है। RAG और tool-calling के lessons इन्हें गहराई से समझाते हैं।

**Step 2: guardrails।** दो तरह के होते हैं।

- **Input guardrails** private data को बाहरी services तक leak होने से रोकते हैं, जैसे model call से पहले Aadhaar numbers, phone numbers और names mask करके, और हानिकारक या injected instructions पकड़ते हैं।
- **Output guardrails** user के देखने से पहले जवाब check करते हैं: format सही हो, बिना आधार के claims न हों, personal data न हो, और आपकी policy के ख़िलाफ़ कुछ न हो। Check fail होने पर आप retry कर सकते हो, दूसरे model पर fallback कर सकते हो, safe message लौटा सकते हो, या किसी इंसान को दे सकते हो।

Guardrails latency बढ़ाते हैं, ख़ासकर streamed जवाबों में, जहाँ तय करना पड़ता है कि text दिखाने से पहले check करना है या दिखाते हुए। तेज़ checks inline रखो और धीमे checks एक sample पर चलाओ।

**Step 3: router और gateway।**

- **Router** तय करता है कि request कहाँ जाएगी, आमतौर पर एक छोटे, तेज़ intent classifier से। वो आसान सवाल सस्ते model को और मुश्किल सवाल strong model को भेज सकता है, billing disputes किसी इंसान को भेज सकता है, scope से बाहर के सवालों का विनम्र तैयार जवाब model call किए बिना दे सकता है, या message अस्पष्ट हो तो स्पष्टीकरण माँग सकता है ("मेरा account freeze करना है, या मौसम पूछ रहे हो?")।
- **Gateway** वो एक जगह है जहाँ से हर model call गुज़रता है। वो API keys रखता है ताकि वो services में बिखरी न हों, तय करता है कि कौन-सा model कौन use कर सकता है, spend limits लागू करता है, हर call log करता है, और कोई provider down हो तो retry करता है या दूसरे provider पर fallback करता है।

**Step 4: caches।**

- **Exact cache:** वही normalise किया सवाल, template version और model हो तो वही stored जवाब मिलता है। Safe और सरल।
- **Semantic cache:** जब नया सवाल पुराने सवाल जैसा *मतलब* रखे तो जवाब दोबारा use करना, embeddings और similarity threshold से match करके। सवाल दोहराए जाएँ तो बहुत बचत हो सकती है, पर ढीला match गलत जवाब दे देता है ("order 1 का refund" "order 2 के refund" के बहुत करीब है)। इसे तभी जोड़ो जब hit rate ऊँचा हो और आपने उसकी गलतियाँ measure कर ली हों।
Reuse के लिए safe exact cache key में वो सब कुछ होना चाहिए जो जवाब बदल सकता है:

```python
import hashlib, re

def cache_key(question, template_version, model, day):
    """Same key only when the answer would be the same: same words, prompt, model and day."""
    normalised = re.sub(r"\s+", " ", question.strip().lower())
    raw = f"{normalised}|{template_version}|{model}|{day}"
    return hashlib.sha256(raw.encode()).hexdigest()

# cache_key("What are Dr Mehta's timings?", "v7", "fast-model", "2026-11-08")
```

- **Prompt caching** और **KV cache** model provider या server पर होते हैं; इनके काम करने के लिए अपने prompt का न बदलने वाला हिस्सा सबसे पहले रखो।

**Step 5: agent patterns।** अब तक हर request एक ही दिशा में बहती है। Agent patterns loops जोड़ते हैं (पहला जवाब अधूरा हो तो दोबारा retrieve करो), कई steps जोड़ते हैं, और ऐसे **write actions** जोड़ते हैं जैसे email भेजना या appointment book करना। ये system को बहुत ज़्यादा capable बनाते हैं और उतना ही ज़्यादा risky भी। इन्हें आखिर में जोड़ो, data बदलने वाली हर चीज़ पर approvals के साथ, tools क्या कर सकते हैं इस पर limits के साथ, और steps व spend पर budgets के साथ।

**पहले दिन से monitoring।** हर request को trace की तरह log करो: input, retrieve किया context, model, prompt version, output, guardrail results, latency और cost, personal data mask करके। Dashboard पर कुछ signals track करो: error और refusal rates, guardrail triggers, हर request की cost, latency, और user feedback। System बढ़ने पर, कौन-सी layer fail हुई ये traces से ही पता चलता है।

| Layer | कब जोड़ें | आम tools | साथ आने वाला नया risk |
| --- | --- | --- | --- |
| Context | जवाब facts चूक जाएँ या गढ़ें | Vector search, SQL, APIs | गलत या पुराने documents |
| Guardrails | असली users और असली data आएँ | PII masking, validators, judge checks | Latency, गलत block होना |
| Router | Requests मुश्किल या type में अलग हों | छोटा classifier, rules | गलत route हुई requests |
| Gateway | एक से ज़्यादा model, service या team हो | LiteLLM, cloud gateways | एक ही जगह fail होने का खतरा |
| Cache | कई सवाल दोहराए जाएँ | Redis, vector index | पुराना या गलत reuse |
| Agents और actions | Tasks को कई steps या बदलाव चाहिए | Agent SDKs, LangGraph | बेकाबू loops, हानिकारक actions |

## एक example से समझो

Pune में 40 clinics की एक chain WhatsApp assistant चलाती है। वो एक model call और timings व fees की लंबी list वाले prompt से शुरू हुआ था। छह महीने बाद चार problems हैं: बताई गई fees कभी-कभी पुरानी होती हैं, patients अपने messages में Aadhaar और phone numbers भेज देते हैं, वही दस सवाल traffic का 40% हैं, और patients appointments book करने को कहते रहते हैं।

वो इसे क्रम से बढ़ाते हैं:

1. **Context।** Timings, fees और doctor schedules अब सवाल के समय clinic system से आते हैं। पुरानी fees की दिक्कत ख़त्म।
2. **Guardrails।** किसी भी model call से पहले Aadhaar और phone numbers mask होते हैं। एक output check diagnosis जैसी लगने वाली हर चीज़ block करता है और confirm करता है कि fees clinic system से मेल खाती हैं।
3. **Router।** एक छोटा classifier top FAQs को fixed जवाबों पर, lab-report के सवालों को secure link पर, और किसी भी अर्जेंट चीज़ को phone number पर भेजता है, बिना model call के।
4. बाकी दोहराए जाने वाले सवालों के लिए **Exact cache**, normalise किए सवाल और तारीख़ से key बनाकर, क्योंकि schedules रोज़ बदलते हैं।
5. **Booking एक tool के रूप में**, सबसे आखिर में: assistant एक slot सुझाता है, patient button से confirm करता है, और हर booking log होती है।

| Measure | पहले | बाद में |
| --- | --- | --- |
| हर 1,000 messages पर model calls | 1,000 | 520 |
| गलत fee या timing जवाब (हफ़्ते का sample) | 6% | 1% से कम |
| Aadhaar numbers के साथ model को भेजे messages | रोज़ कुछ | कोई नहीं |
| Chat में पूरी हुई bookings | 0 | booking requests का 22% |

ये numbers सिर्फ़ समझाने के लिए हैं। उन्होंने semantic cache नहीं जोड़ा: एक test ने दिखाया कि वो "Dr Mehta's timings" को "Dr Mehra's timings" से match कर रहा था।

## आम गलतियाँ

- **पहले ही पूरा platform बना देना।** दस users से पहले पाँच layers का मतलब debug करने की पाँच जगहें और सीखा कुछ नहीं।
- **Context ठीक होने से पहले agents जोड़ना।** गलत facts पर काम करने वाला agent तेज़ी से ज़्यादा नुकसान करता है।
- **ऐसे guardrails जो सिर्फ़ log करें।** जो check block, retry या escalate न करे वो किसी को नहीं बचाता।
- **Details वाले सवालों पर semantic cache।** Order numbers, names और dates के कारण मिलते-जुलते सवालों के मतलब अलग हो जाते हैं।
- **Traces न होना।** हर request का trace न हो तो पता नहीं चलता कि retrieval, router या model में से क्या fail हुआ।
- **Services में बिखरी keys और limits।** Gateway, सरल वाला भी, spend और access एक जगह रखता है।

## कब सरल ही रहना है

- **मुट्ठी भर लोगों के internal tools** को शायद कभी router, gateway या cache चाहिए ही नहीं।
- **कम volume** में caching और routing की बचत इतनी छोटी होती है कि फ़र्क नहीं पड़ता।
- **सिर्फ़ पढ़ने वाले जवाबों** को agent loops या write actions नहीं चाहिए।

## Demo से production तक

- **लिखकर रखो कि हर layer क्यों है**, उसने कौन-सी problem हल की और measure किया असर क्या रहा।
- **Layers को अलग-अलग test करो**: retrieval recall, router accuracy, guardrail false-block rate, cache error rate।
- **सब कुछ साथ में version करो**: prompts, router model, guardrail rules और cache keys, ताकि release को एक साथ rollback किया जा सके।
- **सुरक्षित तरीके से fail हो**: कोई layer down हो तो request error page की जगह सरल path पर fallback करे।

## Practice करो

1. किसी AI feature का architecture जैसा आज है वैसा बनाओ जो आप जानते हो। पाँच layers में से कौन-सी उसमें हैं?
2. हर गायब layer के लिए वो problem लिखो जो उसे जोड़ना सही ठहराएगी, और ये कि उसे कैसे measure करोगे।
