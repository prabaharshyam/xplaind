## ये क्या है

**Trace** एक request का शुरू से अंत तक का record होता है। ये **spans** से बनता है, हर step का एक span: query rewrite, retrieval, reranker, हर model call, हर tool call। हर span अपने inputs, outputs, start और end times store करता है, और model calls के लिए model का नाम, token counts और cost भी। Spans nested होते हैं, इसलिए आप देख सकते हो कि agent की तीसरी tool call दूसरे model turn के अंदर हुई थी।

आम application logs बताते हैं कि कुछ हुआ। AI system के traces बताते हैं कि उसने वही जवाब क्यों दिया। Langfuse और Arize Phoenix जैसे open-source tools, commercial tools और cloud providers के अपने tools, सब traces store और दिखाते हैं। इनमें से कई OpenTelemetry पर बने हैं, जो traces का आम standard है।

```flow
title: Trace 8f3a, एक citizen का सवाल: 3.8 s, ₹0.42
Trace 8f3a | tags: user anon-5521, session s-901, app 2.4.0, prompt v17 -> rewrite_query, 0.4 s | in: सवाल, out: search text
rewrite_query, 0.4 s -> hybrid_search, 0.3 s | out: doc ids और scores
hybrid_search, 0.3 s -> rerank, 0.2 s | out: दोबारा क्रम में ids
rerank, 0.2 s -> generate, 2.9 s | model, tokens in और out, cost, output text
```

इस lesson में हम Bhubaneswar के एक state-government helpdesk assistant को follow करेंगे, जिसने एक किसान को scheme की गलत रकम बता दी थी।

## ये काम कैसे करता है

**Instrument करो।** ज़्यादातर tools model client के लिए decorator या wrapper देते हैं। हर decorated function एक span बन जाता है, और model calls अपने आप tokens और cost record करती हैं। बाद में काम आने वाले attributes जोड़ो: user id (या pseudonymous id), session id, app version, prompt version, retrieved document ids और उनके scores।

**Group करो।** **Session** एक conversation के traces को एक साथ group करता है; user ids से आप देख सकते हो कि एक user ने पूरा क्या-क्या झेला।

**Data का ध्यान रखो।** Traces में prompts और outputs होते हैं, जिनमें personal data हो सकता है। भेजने से पहले sensitive fields mask करो या हटा दो, retention period तय करो, traces कौन देख सकता है ये सीमित रखो, और client माँगे तो self-hosted या in-region tool चुनो।

**इस्तेमाल कैसे करो।**

- *Debug*: खराब जवाब का trace खोलो। क्या सही passage retrieve हुआ? क्या वो prompt में था? क्या model ने उसे ignore कर दिया?
- *Measure*: हर step का latency, हर request के tokens और cost, हर model की error rates।
- *Improve*: दिलचस्प traces को dataset में save करो; वो eval cases बन जाते हैं।

**Sampling।** ज़्यादा volume में, errors या कम feedback वाले सारे traces रखो, और बाकी का एक sample।

**हर तरह के tool से क्या मिलता है:**

| Option | ताकत | कब सोचो |
| --- | --- | --- |
| Open-source, self-hosted (Langfuse, Phoenix) | Data आपके पास रहता है; चलाना free है | Client को in-region या on-premises data चाहिए |
| Commercial hosted tools | चलाने का झंझट कम; extra analysis features | Speed ज़रूरी है और data rules इजाज़त देते हैं |
| Cloud provider की tracing | मौजूदा cloud stack में फिट बैठती है | App पहले से उसी cloud पर चल रहा है |
| Plain OpenTelemetry और अपना store | पूरा control, standard format | आपके पास पहले से observability tooling चल रही है |

**हफ़्ते का trace review।** हर हफ़्ते तीस मिनट अलग रखो। खराब user feedback, errors या असामान्य रूप से ज़्यादा cost वाले traces निकालो, और आम traces का एक random sample भी। हर खराब जवाब के लिए note करो कि कौन-सा step fail हुआ: query rewrite, retrieval, reranking, prompt या model। इन notes को गिनो। कुछ हफ़्तों बाद ये counts बताते हैं कि engineering मेहनत कहाँ रंग लाएगी, और save किए गए traces असली use से बने eval cases का बढ़ता हुआ set बन जाते हैं।

**हर step का cost और latency।** हर span time और tokens record करता है, इसलिए step के हिसाब से totals का chart बनाना आसान है। Teams अक्सर चौंक जाती हैं: बड़े model पर चलने वाली query-rewrite call का cost जवाब से भी ज़्यादा हो सकता है, या reranker model से ज़्यादा देरी जोड़ सकता है।

**Plain OpenTelemetry से tracing।** ज़्यादातर LLM tracing tools (Langfuse, Arize Phoenix और दूसरे) OpenTelemetry data लेते हैं, इसलिए standard से instrument करोगे तो बाद में tool बदलने की आज़ादी रहती है:

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))   # endpoint and auth from env vars
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("policy-rag")

def answer(question, user_id, session_id):
    with tracer.start_as_current_span("answer") as root:
        root.set_attributes({"app.release": "assistant-2026.11.3", "user.id": user_id, "session.id": session_id})
        with tracer.start_as_current_span("retrieve") as span:
            hits = search(question)
            span.set_attributes({"retrieval.ids": [h["id"] for h in hits],
                                 "retrieval.top_score": hits[0]["score"] if hits else 0})
        with tracer.start_as_current_span("generate") as span:
            reply = call_model(question, hits)
            span.set_attributes({"gen_ai.request.model": reply.model,
                                 "gen_ai.usage.input_tokens": reply.usage.input_tokens,
                                 "gen_ai.usage.output_tokens": reply.usage.output_tokens})
        return reply
```

`gen_ai.*` नाम generative AI के लिए OpenTelemetry की conventions follow करते हैं, जिन्हें tracing tools समझते हैं। `OTEL_EXPORTER_OTLP_ENDPOINT` को अपने tool की तरफ़ point करो, और client माँगे तो उसे Indian region में self-host करो।

**Export से पहले mask करो।** Personal data को span attributes या events में जाने से पहले अपने code में ही हटा दो। हर prompt और answer पर, जो आप attach करते हो, एक छोटा helper लगाओ, जो security lessons वाले masking patterns use करे; शुरू करने के लिए इतना काफ़ी है। फिर store हुए traces का एक sample देखो कि ये सच में काम कर रहा है।

**काम के traces बचाकर रखो।** सब कुछ 10% पर sample करोगे तो वो ज़्यादातर rare failures खो जाएँगी जो आपको चाहिए। दो आम तरीके:

- **Head sampling और exceptions**: जिन requests में error आए, thumbs down मिले या latency threshold पार हो, उनके traces हमेशा रखो (उन्हें ऐसे attribute से mark करो जिसे आपका exporter या collector check करे), और बाकी का sample लो।
- **OpenTelemetry Collector में tail sampling**: collector हर trace के पूरा होने का इंतज़ार करता है, फिर errors या slow spans वाले सारे traces रखता है और बाकी का एक percentage।

**Traces से हर step का cost और latency।** Spans को नाम से group करो और रोज़ का time और tokens जोड़ो। "हर step का कुल cost में हिस्सा" वाला chart अक्सर कोई सस्ती जीत दिखा देता है, जैसे बड़े model पर चलता rewrite step, या एक बहुत बड़े filter की वजह से धीमा retrieval।

**Trace से test case तक।** एक button या command जोड़ो जो trace id लेकर उसका सवाल, retrieved ids और expected answer eval set में लिख दे। ये जितना आसान होगा, eval set असली failures से उतनी तेज़ी से बढ़ेगा।

**Browser में try करो।** एक छोटा tracer: हर step अपना time record करता है, इसलिए धीमा वाला साफ़ दिख जाता है।

```python
import time, random
from contextlib import contextmanager

spans = []
@contextmanager
def span(name):
    t0 = time.perf_counter()
    yield
    spans.append((name, (time.perf_counter() - t0) * 1000))

random.seed(2)
with span("answer"):
    with span("rewrite"): time.sleep(0.02)
    with span("retrieve"): time.sleep(random.uniform(0.05, 0.2))
    with span("generate"): time.sleep(0.1)
for name, ms in sorted(spans, key=lambda s: -s[1]):
    print(f"{name:<9} {ms:6.0f} ms")
```

## एक example से समझो

Bhubaneswar का एक state-government helpdesk assistant citizens के schemes के सवालों के जवाब देता है। एक अफ़सर बताते हैं: "इसने एक किसान को बताया कि state की crop-support scheme की instalment ₹4,000 है। असल में ₹2,000 है।" (यहाँ scheme और रकमें example के लिए बनाई गई हैं।)

आप उस session के traces search करते हो और उस वाले को खोलते हो:

```text
trace 8f3a  user=anon-5521  app=2.4.0  prompt=v17   3.8 s  ₹0.42
  rewrite_query        0.4 s   "crop-support scheme instalment amount"
  hybrid_search        0.3 s   top: doc 112 (0.71), doc 87 (0.69), doc 113 (0.66)
  rerank               0.2 s   top: doc 87, doc 112, doc 113
  generate             2.9 s   in 3,210 tok / out 182 tok
```

Doc 87 एक 2019 का note है, scheme के पुराने version के बारे में, जिसमें रकम अलग थी। Reranking के बाद ये सबसे ऊपर आया, मौजूदा scheme guideline से भी ऊपर। Model ने उसे ईमानदारी से quote कर दिया। Bug model में नहीं है; वो एक पुराना document है जिस पर effective date ही नहीं थी।

आप `effective_from` metadata और एक filter जोड़ते हो, उस trace की query को test में दोबारा चलाते हो, और इस trace को golden set में save कर देते हो ताकि ये case अब से test होता रहे। पूरी जाँच में पंद्रह मिनट लगे क्योंकि हर step record था।

| जाँच का step | लगा समय |
| --- | --- |
| User और time से session का trace ढूँढना | 2 मिनट |
| देखना कि 2019 का note सबसे ऊपर आया | 3 मिनट |
| Effective dates और filter जोड़ना, query दोबारा चलाना | 8 मिनट |
| Trace को golden-set case की तरह save करना | 2 मिनट |

## आम गलतियाँ

- **सिर्फ़ final answer log करना।** तब आप retrieval failures और generation failures में फ़र्क नहीं कर पाते।
- **Version tags न लगाना।** Traces पर app और prompt versions के बिना आप किसी change को quality गिरने से जोड़ नहीं सकते।
- **Personal data को बिना mask किए trace करना।** Traces एक sensitive data store बन जाते हैं। Mask करो, access सीमित रखो और expire करो।
- **कभी देखना ही नहीं।** Traces तभी काम के हैं जब कोई उन्हें पढ़े; हर हफ़्ते एक sample review करो।
- **Failures को tests में न बदलना।** हर traced खराब जवाब एक तैयार eval case है।
- **सिर्फ़ model call को trace करना**, जिससे retrieval और tool की problems दिखती ही नहीं।
- **Uniform sampling**, जो ज़्यादातर rare failures फेंक देती है।
- **हर जगह proprietary tracing calls**, जिससे बाद में बदलना दर्दनाक हो जाता है; OpenTelemetry को prefer करो।

## जब simple logs काफ़ी हों

- **हर request में एक model call**, बिना retrieval या tools के: tokens, time और outcome वाली एक structured log line काफ़ी हो सकती है।
- **सिर्फ़ आपके अपने use का prototype।**
- **Batch jobs**, जहाँ हर item के logs और एक summary report से debugging हो जाती है।

## Demo से production तक

- **हर step को trace करो** release, user और session attributes के साथ।
- **Export से पहले personal data mask करो**, और retention और access controls लगाओ।
- **सारे failures और slow requests रखो**, बाकी का sample लो।
- **हर हफ़्ते step के हिसाब से cost और latency का chart देखो।**
- **खराब traces को eval cases में बदलो** एक ही command से।

## Practice करो

Langfuse का tracing overview और OpenTelemetry का traces वाला page पढ़ो।

1. अपने RAG app में एक free, self-host हो सकने वाले tool से tracing जोड़ो, rewrite, retrieval (document ids और scores के साथ), reranking और generation को अलग-अलग spans की तरह record करते हुए।
2. Traces पर app version और prompt version का tag लगाओ, और भेजने से पहले email addresses और phone numbers mask करो।
3. दस सवाल पूछो, सबसे धीमा step और सबसे महँगी request ढूँढो, और एक खराब जवाब का trace eval case की तरह save करो।
4. अपने traces को OpenTelemetry से एक self-hosted tool में export करो, फिर endpoint दूसरे tool पर बदल दो और confirm करो कि वही spans दिखते हैं।
