## ये क्या है

**Sorting** items को order में रखता है। Data sort होने के बाद duplicates साथ-साथ आ जाते हैं, extremes सिरों पर होते हैं, और तुम कुछ भी जल्दी ढूँढ सकते हो।

**Binary search** sorted data में किसी item को ढूँढने के लिए बीच वाला item check करता है और वो आधा हिस्सा फेंक देता है जिसमें item हो ही नहीं सकता। हर check बचे हुए हिस्से को आधा करता है, इसलिए लगभग log₂ n checks लगते हैं: 10 लाख items के लिए 20, 1 करोड़ के लिए 24। और general तरीके से कहें तो, ये ढूँढता है कि कोई yes/no test "no" से "yes" पर कहाँ flip होता है, जैसे "क्या `a[i]` कम से कम x है?"। इसी तरह possible answers की एक range में search करना **binary search on the answer** कहलाता है।

**Two pointers** एक array में दो positions चलाकर pair और range वाले problems nested loops की जगह एक ही pass में हल करते हैं। **Sliding window** सबसे अच्छा contiguous stretch ढूँढने वाला two-pointer pattern है।

आगे दिखाए गए `first_at_least` code से 42 के लिए binary search (`lo = 0`, `hi = 10` से शुरू करके):

```flow
dir: LR
title: [3 8 15 21 27 33 42 50 61 77] में 42 के लिए binary search
Check 1: index 5 पर 33 -[42 से छोटा: दाएँ जाओ]-> Check 2: index 8 पर 61
Check 2: index 8 पर 61 -[छोटा नहीं: रखो, बाएँ जाओ]-> Check 3: index 7 पर 50
Check 3: index 7 पर 50 -[छोटा नहीं: रखो, बाएँ जाओ]-> Check 4: index 6 पर 42
Check 4: index 6 पर 42 -[छोटा नहीं: lo और hi मिल गए]-> Answer: index 6
```

चार checks, जबकि बाएँ से scan करने पर सात लगते।

## ये काम कैसे करता है

### Sorting algorithms और उनकी cost

| Algorithm | Average time | Worst time | Extra space | Stable? | कब ये सही choice है |
|---|---|---|---|---|---|
| Insertion sort (और bubble sort) | O(n²) | O(n²) | O(1) | हाँ | बहुत छोटी या लगभग sorted lists, जहाँ insertion sort O(n) के करीब होता है |
| Merge sort | O(n log n) | O(n log n) | O(n) | हाँ | predictable time; linked lists; memory के लिए बहुत बड़ी files |
| Quicksort | O(n log n) | O(n²) | O(log n) | नहीं | memory में तेज़, random या median-of-three pivot के साथ |
| Heap sort | O(n log n) | O(n log n) | O(1) | नहीं | extra memory के बिना एक guaranteed bound |
| Python का `sorted` और `list.sort` | O(n log n) | O(n log n) | O(n) तक | हाँ | real data, जिसमें अक्सर पहले से order में runs होते हैं |
| Counting sort (radix sort इसी पर बना है) | O(n + k) | O(n + k) | O(n + k) | हाँ | छोटी range k वाली integer keys, जैसे 100 में से marks |

**Merge sort** list को तब तक आधा-आधा करता है जब तक हर टुकड़े में एक item न रह जाए, फिर बार-बार आगे वाला छोटा item उठाकर sorted टुकड़ों को merge करता है: लगभग log₂ n levels, हर level पर O(n) merging, इसलिए O(n log n)।

**Quicksort** एक pivot चुनता है, छोटे items बाएँ और बड़े दाएँ ले जाता है, और हर side को sort करता है। बराबर splits से O(n log n) मिलता है। पहले से sorted data पर "हमेशा पहला item चुनो" करने से हर बार n items 0 और n − 1 में बँटते हैं, cost O(n²), इसलिए असली implementations random pivot या median of three चुनते हैं।

**Python का sort**, जिसे आम तौर पर Timsort कहते हैं, merge sort और insertion sort का hybrid है। ये पहले से order में मौजूद runs ढूँढता है, छोटे runs को insertion sort से बढ़ाता है और उन्हें merge करता है, इसलिए पहले से sorted list में बस एक O(n) pass लगता है। Python 3.11 से ये merges का order Powersort strategy से चुनता है।

**Comparison sorts O(n log n) को beat क्यों नहीं कर सकते।** n items n! orders में हो सकते हैं, और sort को उनमें फ़र्क करना पड़ता है। हर comparison ज़्यादा से ज़्यादा possibilities को आधा करता है, इसलिए worst case में कम से कम log₂(n!) comparisons चाहिए, मोटा-मोटा n log₂ n। 10 items के लिए 10! होता है 36,28,800, तो कम से कम 22 comparisons। Counting sort कभी compare नहीं करता, इसलिए इस limit से बच जाता है: 0 से 100 तक के 10 लाख marks को 101 counters से एक pass में sort कर देता है।

### Stability और sort keys

Sort **stable** होता है जब equal keys वाले items अपना original order बनाए रखें। Multi-key sorts में ये matter करता है। Orders को city के हिसाब से list करने के लिए, और हर city के अंदर dates order में रखने के लिए, तुम पहले date से और फिर city से sort कर सकते हो: दूसरा sort बराबर cities के बीच date order सिर्फ़ इसलिए बनाए रखता है क्योंकि वो stable है। Python में एक-step वाला `sorted(orders, key=lambda o: (o.city, o.date))` भी यही result देता है। Python stability की guarantee देता है, `reverse=True` के साथ भी; C++ `std::sort`, heap sort और typical quicksort नहीं देते।

### क्या पूरा sort चाहिए?

- **सिर्फ़ सबसे छोटा या सबसे बड़ा:** `min()` या `max()`, एक O(n) pass।
- **1 करोड़ scores में से top 10:** `heapq.nlargest(10, scores)` 10 items का heap रखता है, k = 10 के साथ लगभग O(n log k)।
- **सिर्फ़ exact lookups,** जैसे "क्या ये PAN list में है?": एक बार `set` बनाओ, फिर हर lookup average पर O(1)। Sort तब करो जब order चाहिए: ranges, "पर या उसके बाद पहला", सबसे नज़दीकी value, ranks।

### Off-by-one bugs के बिना binary search

ज़्यादातर bugs conventions मिलाने से आते हैं। एक भरोसेमंद convention है **half-open range**: answer हमेशा `lo` से `hi` के बीच कहीं होता है, और जब दोनों मिलते हैं तो तुम रुक जाते हो।

```python
def first_at_least(a, x):
    """Index of the first item that is at least x; len(a) if there is none."""
    lo, hi = 0, len(a)            # the answer is always in lo..hi
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1          # mid and everything left of it is too small
        else:
            hi = mid              # mid might be the answer, so keep it
    return lo

marks = [10, 20, 20, 20, 30]
print(first_at_least(marks, 20))   # 1
print(first_at_least(marks, 99))   # 5, which is len(marks): not found
```

हर pass range को छोटा करता है, इसलिए loop खत्म होता है। 20 के लिए ये indices 2, 1 और 0 check करता है और 1 return करता है, यानी तीन 20 में से पहला। Python का `bisect.bisect_left` यही करता है, इसलिए असली code में library call करो:

| Call | क्या return करता है | `[10, 20, 20, 20, 30]` पर |
|---|---|---|
| `bisect_left(a, x)` | पहला index जिसका item कम से कम x हो | `bisect_left(a, 20)` है 1 |
| `bisect_right(a, x)` | पहला index जिसका item x से बड़ा हो | `bisect_right(a, 20)` है 4 |
| `bisect_right(a, x) - bisect_left(a, x)` | कितने items x के बराबर हैं | 4 − 1 = 3 |
| result `len(a)` के बराबर | कुछ भी qualify नहीं करता | `bisect_left(a, 99)` है 5 |

तो अगर x मौजूद है, तो वो पहली बार `bisect_left` पर और आखिरी बार `bisect_right(a, x) - 1` पर आता है।

Java या C++ में 32-bit integers के साथ, `lo + hi` लगभग 2.1 billion पार होते ही `(lo + hi) / 2` overflow हो सकता है; Joshua Bloch ने 2006 में Java की अपनी library में ये bug बताया था। वहाँ `lo + (hi - lo) / 2` लिखो। Python के integers overflow नहीं होते।

### Binary search on the answer

कई problems "सबसे छोटी value जो काम करे" पूछते हैं: एक capacity, एक daily limit, सबसे पहला दिन। अगर "क्या v काम करता है?" test **monotonic** है (एक बार yes, तो हर बड़े v के लिए yes), तो possible answers की range पर binary search करो। `first_at_least` template use करो, बस `a[mid] < x` की जगह "mid काम नहीं करता" रखो। इसमें लगभग log₂(range का size) checks लगते हैं, हर एक test का एक run।

Precondition सबसे ज़्यादा matter करती है। "क्या day d तक cumulative sign-ups 50,000 तक पहुँच गए?" monotonic है, क्योंकि totals कभी कम नहीं होते। "क्या उस दिन की sales ₹1 लाख से ऊपर थी?" yes, no, yes जा सकता है, और binary search बिना किसी error के गलत दिन return करेगा।

Real-valued answer के लिए, जैसे कोई rate, floats शायद कभी न मिलें: तय संख्या में halvings चलाओ, जैसे 60, या तब रुको जब `hi - lo` तुम्हारी ज़रूरत की precision से कम हो जाए।

### Two pointers और sliding windows

**Pair method सही क्यों है।** मान लो बचे हुए सबसे छोटे और सबसे बड़े items का sum बहुत कम है। सबसे छोटा item बचे हुए किसी और के साथ और भी छोटा sum देगा, इसलिए वो किसी answer में नहीं हो सकता, और उसे छोड़ना safe है। Sum बहुत बड़ा हो तो यही logic सबसे बड़े item को छोड़ता है। हर step एक item हटाता है, इसलिए ज़्यादा से ज़्यादा n − 1 steps।

```python
def has_pair(prices, target):
    left, right = 0, len(prices) - 1
    while left < right:
        total = prices[left] + prices[right]
        if total == target:
            return prices[left], prices[right]
        if total < target:
            left += 1             # need a bigger sum
        else:
            right -= 1            # need a smaller sum
    return None

print(has_pair([5, 12, 18, 25, 30, 38, 45], 56))   # (18, 38)
```

Unsorted data के लिए, पहले sort करो (O(n log n)), या एक set के साथ एक pass करो और check करो कि `target - p` पहले दिख चुका है या नहीं (O(n) time और memory)।

**Sliding window** अपना right edge एक बार में एक step बढ़ाता है और, जब तक rule टूटा हुआ है, अपना left edge छोटा करता है। ये तभी सही है जब छोटा करने से rule पूरा करना हमेशा आसान हो। "Total budget के अंदर" में ये property तभी होती है जब हर value zero या उससे ज़्यादा हो।

### Pattern पहचानना

```flow
title: कौन-सा pattern fit होता है?
Contiguous stretch? -[हाँ]-> Sliding window | O(n); छोटा करने से मदद मिलनी चाहिए
Contiguous stretch? -[नहीं]-> Target वाला pair?
Target वाला pair? -[हाँ, sorted]-> Two pointers | O(n) time, O(1) memory
Target वाला pair? -[हाँ, unsorted]-> Hash set | O(n) time और memory
Target वाला pair? -[नहीं]-> पहला, आखिरी या सबसे छोटा जो काम करे?
पहला, आखिरी या सबसे छोटा जो काम करे? -[test monotonic है]-> Binary search | O(log n) checks
पहला, आखिरी या सबसे छोटा जो काम करे? -[test आगे-पीछे flip होता है]-> Scan करो या फिर से सोचो
```

Interview में, code करने से पहले pattern और उसकी precondition (sorted, monotonic या non-negative) बताओ।

## एक example से समझो

Sneha Hyderabad के एक online coaching platform के लिए analytics चलाती है। Numbers सिर्फ़ समझाने के लिए हैं।

### 1. Budget के अंदर दिनों का सबसे लंबा run

लगातार दिनों का सबसे लंबा run कौन-सा है जिसका कुल ad spend ₹1 लाख के अंदर रहा? एक साल में 66,795 possible runs होते हैं (365 × 366 ÷ 2), इसलिए सबको check करना O(n²) है। Sliding window एक pass लेता है:

```python
def longest_within(spend, budget):
    best = total = left = 0
    for right, amount in enumerate(spend):
        total += amount                   # grow: day `right` joins
        while total > budget:             # shrink until within budget
            total -= spend[left]
            left += 1
        best = max(best, right - left + 1)
    return best

week = [30, 20, 40, 10, 25, 60, 15]       # spend in thousands of rupees
print(longest_within(week, 100))          # 4
```

एक हफ़्ते का trace, budget 100 (₹1 लाख) के साथ:

| दिन | Spend | छोटा करने के बाद window | Total | अब तक का best |
|---|---|---|---|---|
| 1 | 30 | दिन 1 से 1 | 30 | 1 |
| 2 | 20 | दिन 1 से 2 | 50 | 2 |
| 3 | 40 | दिन 1 से 3 | 90 | 3 |
| 4 | 10 | दिन 1 से 4 | 100 | 4 |
| 5 | 25 | दिन 2 से 5 (दिन 1 हटा) | 95 | 4 |
| 6 | 60 | दिन 4 से 6 (दिन 2 और 3 हटे) | 95 | 4 |
| 7 | 15 | दिन 5 से 7 (दिन 4 हटा) | 100 | 4 |

Answer है 4 दिन (दिन 1 से 4)। हर दिन एक बार जुड़ता है और ज़्यादा से ज़्यादा एक बार निकलता है, इसलिए ज़्यादा से ज़्यादा 2n steps: O(n)। दिन 6 पर एक shrink step काफ़ी नहीं था, इसीलिए code `if` नहीं, `while` use करता है।

ये सिर्फ़ इसलिए safe है क्योंकि spend कभी negative नहीं होता। Figures में net refunds डालो और ये टूट जाता है: `[80, 30, -50]` और budget 100 के साथ, total 110 पहुँचने पर window दिन 1 हटा देती है और 2 report करती है, लेकिन तीनों दिनों का total 60 है, तो सही answer 3 है। Negative values के साथ कोई और method use करो, जैसे prefix sums।

### 2. वो पहला दिन जब sign-ups target तक पहुँचे

Finance पूछता है: cumulative sign-ups पहली बार किस दिन target तक पहुँचे? Sign-ups कभी negative नहीं होते, इसलिए "क्या day d तक पहुँच गए?" no, no, फिर उसके बाद हर दिन yes है। यानी monotonic:

```python
from bisect import bisect_left
from itertools import accumulate

def first_day_reaching(daily, target):
    totals = list(accumulate(daily))      # running totals, O(n)
    i = bisect_left(totals, target)       # first day whose total is at least target
    return i if i < len(totals) else -1   # len(totals) means never reached

print(first_day_reaching([120, 90, 200, 150, 80], 400))   # 2
print(first_day_reaching([120, 90, 200, 150, 80], 9999))  # -1
```

ये `first_at_least` template ही है, जो library कर रही है। Totals तीसरे दिन, index 2 पर, 410 तक पहुँचते हैं।

`totals` बनाना खुद एक O(n) pass है, इसलिए एक target के लिए सीधा scan भी उतना ही अच्छा है। Search तब फ़ायदा देता है जब उसे कई targets के जवाब देने हों: एक साल के daily data के लिए हर एक में लगभग 9 checks, और दस साल के hourly data (87,600 hours) के लिए लगभग 17।

### 3. ऐसा answer ढूँढना जो किसी list में नहीं है

Mentors assignment batches को submission order में grade करते हैं। इस हफ़्ते के सात batches में 40, 25, 35, 50, 20, 30 और 45 pages हैं, और सब 3 दिन में grade होने चाहिए, हर दिन के batches एक daily page limit के अंदर। सबसे छोटी limit कौन-सी है जो काम करे?

Answer 50 (सबसे बड़ा batch fit होना चाहिए) और 245 (सब कुछ एक दिन में) के बीच है, और बड़ी limit को कभी ज़्यादा दिन नहीं लगते, इसलिए test monotonic है:

```python
def days_needed(pages, limit):
    days, today = 1, 0
    for p in pages:
        if today + p > limit:             # today is full; start a new day
            days, today = days + 1, 0
        today += p
    return days

def smallest_limit(pages, max_days):
    lo, hi = max(pages), sum(pages)       # smallest and largest sensible answers
    while lo < hi:
        mid = (lo + hi) // 2
        if days_needed(pages, mid) <= max_days:
            hi = mid                      # mid works; try smaller
        else:
            lo = mid + 1                  # too small; go bigger
    return lo

print(smallest_limit([40, 25, 35, 50, 20, 30, 45], 3))    # 95
```

Answer है रोज़ 95 pages: 40 + 25, फिर 35 + 50, फिर 20 + 30 + 45। 94 की limit को 4 दिन लगते हैं। Search 196 possible limits को 7 checks में cover करता है, हर check एक O(n) pass।

## आम गलतियाँ

**Unsorted data पर या ऐसे test पर binary search जो monotonic नहीं है।** गलत answer मिलता है और कोई error नहीं आता। Prove करो कि test "no, फिर yes" जाता है और कभी वापस नहीं आता।

**Off-by-one bounds।** Inclusive और exclusive `hi` मिलाना, या `mid` नीचे round होने पर `lo = mid` लिखना, दो items बचने पर loop को हमेशा के लिए चलाता रहता है। एक ही convention use करो, जैसे half-open template, और lengths 0, 1 और 2 test करो। Java या C++ में `lo + (hi - lo) / 2` भी लिखो।

**bisect का result check किए बिना use करना।** कुछ भी qualify न करे तो `bisect_left` `len(a)` return करता है, इसलिए उससे indexing करने पर `IndexError` आता है।

**Loop के अंदर sort करना।** Loop के बाहर एक बार sort करो। और जब पूरे order से कम चाहिए, तो `min()`, `heapq.nlargest` या set use करो।

**मान लेना कि हर sort stable है।** C++ `std::sort`, heap sort और ज़्यादातर quicksorts stable नहीं हैं, इसलिए two-step multi-key sort गलत निकल सकता है।

**Unsorted data पर two pointers use करना।** पहले sort करो या hash set use करो।

**Negative values के साथ sum-based sliding window use करना।** Refunds या losses इसे चुपचाप तोड़ देते हैं। Check करो कि हर value zero या उससे ज़्यादा है।

**Window को `while` की जगह `if` से छोटा करना।** एक step काफ़ी नहीं हो सकता, जैसा trace में दिन 6 दिखाता है।
