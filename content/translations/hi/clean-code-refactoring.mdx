## ये क्या है

**Clean code** वो code है जिसे अगला इंसान बिना डरे पढ़ सके, समझ सके और बदल सके। वो अगला इंसान अक्सर आप ही होते हो, तीन महीने बाद, बिना याद के कि आपने उसे ऐसे क्यों लिखा था।

Clean code चालाक tricks या सबसे कम lines की बात नहीं है। ये पढ़ने वाले की बात है। क्या वो function का काम उसके नाम से समझ सकता है? क्या वो उसे ऊपर से नीचे बिना इधर-उधर कूदे follow कर सकता है? क्या वो एक rule को एक ही जगह बदल सकता है?

**Refactoring** का मतलब है code कैसे लिखा है ये बदलना, बिना ये बदले कि वो क्या करता है। आप नाम बदलते हो, split करते हो, सरल करते हो और duplication हटाते हो, एक-एक छोटे step में, और tests पुष्टि करते हैं कि behaviour वही रहा। इसी तरह गड़बड़ code बिना risky rewrite के clean code बनता है।

## ये काम कैसे करता है

वो आदतें जो सबसे ज़्यादा फ़र्क डालती हैं:

| आदत | पहले | बाद में |
| --- | --- | --- |
| साफ़ नाम | `def calc(d, f):` | `def invoice_total(items, include_gst):` |
| नाम वाले constants | `amount * 1.18` | `amount * (1 + GST_RATE)` |
| छोटे functions | एक 120-line का `process()` | `read_orders()`, `validate()`, `total()`, `write_report()` |
| Early returns | चार nested `if` blocks | पहले गलत cases संभालो, फिर मुख्य रास्ता |
| सच का एक ही source | वही rule तीन files में copy | एक function जिसे सब बुलाएँ |
| ईमानदार comments | `# loop over items` | `# Refunds older than 30 days need manager approval (policy 4.2)` |

अच्छे comments **क्यों** बताते हैं, क्या नहीं। Code पहले ही बताता है कि वो क्या करता है; comment को वो बताना चाहिए जो code नहीं बता सकता, जैसे कोई business rule या किसी अजीब चुनाव की वजह।

Refactoring एक safe loop में चलती है:

```flow
dir: LR
Tests pass हैं -> एक छोटा बदलाव | नाम बदलो, function extract करो, constant जोड़ो
एक छोटा बदलाव -> Tests चलाओ
Tests चलाओ -[pass]-> Commit
Commit -> एक छोटा बदलाव
Tests चलाओ -[fail]-> Undo करो और छोटा step try करो
Undo करो और छोटा step try करो -> एक छोटा बदलाव
```

छोटे steps मायने रखते हैं। एक rename, tests का एक run, एक commit। एक extract किया हुआ function, एक run, एक commit। अगर कोई test fail हो, तो आपको ठीक पता होता है कि कौन-से step ने तोड़ा और सिर्फ़ उसी को undo कर सकते हो। एक बड़ा rewrite आपको इनमें से कुछ नहीं देता।

**Extract function** सबसे काम का refactor है। किसी लंबे function के अंदर का वो block लो जो एक ही काम करता है, उसे अपने function में डालो, ऐसे नाम के साथ जो वो काम बताता हो, और उसे call करो। लंबा function steps की list जैसा पढ़ा जाने लगता है।

**Code smells** वो संकेत हैं कि code बदलना मुश्किल होगा: functions जो एक screen में न आएँ, वही logic कई जगह copy हुई, एक बदलाव जिसके लिए पाँच files में edit करना पड़े, गहरी nesting, और `data`, `temp` या `x` नाम के variables। ये bugs नहीं हैं; ये वो जगह हैं जहाँ bugs पनपते हैं।

**AI projects में clean code।** यही आदतें prompts और pipelines पर भी लागू होती हैं। Prompts को functions में दबी लंबी strings की जगह साफ़ नामों वाली अपनी files में रखो। Pipeline के हर step (load, chunk, embed, retrieve, generate) का अपना function बनाओ, ताकि आप एक को बाकी को छुए बिना test और बदल सको। Chunk size, top-k और temperature जैसी settings को एक config file में constants के नाम दो, ताकि एक experiment में एक ही line बदले और diff साफ़ दिखाए कि क्या try हुआ।

**Refactor कब नहीं करना।** Refactoring की कीमत होती है: समय, review की मेहनत और थोड़ा risk। उस code के लिए इसे छोड़ दो जो चलता है और जिसे कोई बदलने वाला नहीं, throwaway scripts के लिए, और outage के बीच में, जहाँ सबसे छोटा fix ही सही है। जब urgent बदलाव ship हो जाए और उसके चारों ओर tests हों, तब अपने अलग pull request में सफ़ाई करो।

## एक example से समझो

Kavya को Kochi की एक edtech company में 140 lines का function `process_file()` विरासत में मिलता है। वो course purchases की CSV पढ़ता है, refunds filter करता है, GST जोड़ता है, coupons लगाता है और summary लिखता है। एक नया rule आ रहा है: एक सरकारी scheme के लिए GST skip होना चाहिए। Function बदलना risky लगता है।

**पहले, tests।** वो आज के behaviour के आसपास छोटी sample CSVs से छह tests लिखती है: सामान्य purchases, एक refund, एक coupon, एक zero amount, एक missing field और एक duplicate row। पुराने code पर सब pass होते हैं। अब उसके पास safety net है।

**फिर छोटे steps।** वो `d` को `purchases` और `t` को `total` नाम देती है। Tests pass; commit। वो `* 1.18` की तीन copies को एक `GST_RATE` constant और `with_gst()` function से बदलती है। Tests pass; commit। वो `read_purchases()`, `apply_coupon()` और `write_summary()` extract करती है। हर step tests चलाता है और उसका अपना commit होता है।

मुख्य function अब ग्यारह lines का है जो business process की तरह पढ़ा जाता है:

```python
def process_file(path):
    purchases = read_purchases(path)
    paid = [p for p in purchases if not p.is_refund]
    totals = [with_gst(apply_coupon(p)) for p in paid]
    write_summary(totals)
```

**फिर नया rule।** Scheme के लिए GST skip करना अब एक जगह, एक function `with_gst()` में, एक बदलाव है, और एक नया test। Pull request छोटा है और review करना आसान, और उसका reviewer उसी दिन approve कर देता है।

## आम गलतियाँ

- **बिना tests के refactor करना।** आप नहीं बता सकते कि behaviour बदला या नहीं। पहले वो tests लिखो जो आज का behaviour पकड़ें।
- **Refactoring और behaviour बदलना एक ही step में।** सफ़ाई और नया feature अलग commits में करो, ताकि हर एक को review करना आसान हो।
- **बड़े rewrites।** उनमें हफ़्ते लगते हैं और वो चीज़ें तोड़ देते हैं जो किसी को याद नहीं थीं। छोटे, safe steps जीतते हैं।
- **चालाक one-liners।** छोटा होना clean होना नहीं है अगर पढ़ने वाले को उसे decode करना पड़े।
- **Code को दोहराने वाले comments।** वो पुराने पड़ जाते हैं। क्यों समझाओ, या नाम बदलो जब तक comment की ज़रूरत न रहे।
- **ऐसे code को चमकाना जिसे कोई नहीं छुएगा।** वो refactor करो जिसे आप बदलने वाले हो, सब कुछ नहीं।

## Practice करो

1. Exercise वाला one-line function लो और उसे tests के साथ साफ़ तरीके से दोबारा लिखो।
2. अपने किसी project का सबसे लंबा function ढूँढो और उससे दो छोटे functions extract करो, tests green रखते हुए।
3. किसी script के हर बिना समझाए number को नाम वाले constant से बदलो।
4. किसी take-home या review में, दो वाक्यों में समझाओ कि आपने code को ऐसे क्यों बनाया।
