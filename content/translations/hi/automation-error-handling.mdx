## ये क्या है

हर automation कभी न कभी fail होता है। कोई API down होता है, कोई token expire होता है, कोई customer अपना phone number गलत type कर देता है, कोई provider limit लगा देता है कि आप कितनी तेज़ी से भेज सकते हो। सवाल ये नहीं कि fail **होगा या नहीं**, बल्कि ये कि **कैसे** होगा। अच्छी तरह बना automation सुरक्षित तरीके से fail होता है: कुछ खोता नहीं, कुछ दो बार नहीं होता, और सही इंसान को पता होता है कि क्या करना है।

**Error handling** वो सब है जो automation तब करता है जब कोई step fail हो, या कोई step "success" हो पर कुछ गलत लौटाए:

| काम | इसका मतलब |
| --- | --- |
| **Retry** | जो errors शायद temporary हैं उन्हें फिर से try करना, धीरे-धीरे और गिनी-चुनी बार |
| **Stop** | जो errors अपने आप ठीक नहीं होंगे उन्हें बार-बार try न करना; उन्हें record करना |
| **Alert** | किसी इंसान को एक बार बताना, इतनी details के साथ कि वो कुछ कर सके |
| **Recover** | वजह ठीक होने के बाद सुरक्षित तरीके से दोबारा process करना, बिना कुछ दो बार किए |
| **Record** | हर item के साथ क्या हुआ उसकी history रखना, review और reruns के लिए |

इन पाँचों कामों के नीचे दो ideas हैं। पहला, सही response इस पर निर्भर करता है कि **retry से क्या बदलेगा**: busy server अगली बार जवाब दे सकता है, गलत phone number कभी ठीक नहीं होगा। दूसरा, "send" या "pay" की call fail होने का मतलब हमेशा ये नहीं कि कुछ भेजा या pay नहीं हुआ। ज़्यादातर असली duplicates यही भूलने से आते हैं।

ये lesson Bengaluru के एक logistics startup को follow करता है, जिसके delivery updates दो बार गए, rate limits से टकराए और एक बार पूरे दिन रुके रहे। Example tool n8n है।

## ये काम कैसे करता है

### Error को इस हिसाब से बाँटो कि retry से क्या बदलेगा

```flow
एक error आता है -> क्या step सिर्फ़ data पढ़ रहा था?
क्या step सिर्फ़ data पढ़ रहा था? -[हाँ]-> Temporary error? | timeout, 429, 500 से 504
क्या step सिर्फ़ data पढ़ रहा था? -[नहीं]-> नतीजा पता नहीं? | send, pay या create पर timeout या 500 से 504
नतीजा पता नहीं? -[हाँ]-> अपनी key से status check करो | फिर उसी key से retry करो
नतीजा पता नहीं? -[नहीं]-> Temporary error?
Temporary error? -[हाँ]-> Backoff के साथ retry करो | फिर भी fail हो तो needs attention
Temporary error? -[नहीं]-> एक record की बात है? | 400, 404, invalid data
एक record की बात है? -[हाँ]-> Needs attention list | बाकी के साथ आगे बढ़ो
एक record की बात है? -[नहीं]-> Run रोक दो | 401, 403, expire हुआ token; owner को alert करो
```

| तरह | Examples | क्या करना है |
| --- | --- | --- |
| **Temporary** | Network blips, rate limits (HTTP 429), किसी read पर server errors (500 से 504) | Throttle करो, फिर backoff और एक cap के साथ retry करो |
| **नतीजा पता नहीं** | किसी step पर timeout या 500 से 504, जो कुछ send, pay या create करता है | पहले check करो, फिर सिर्फ़ उसी key के साथ retry करो |
| **Permanent, एक record** | Bad input (400), गायब record (404), "12345" जैसा phone number | Reason के साथ record करो, बाकी के साथ आगे बढ़ो |
| **Permanent, पूरा workflow** | गलत या expire हुए credentials (401, 403), delete हुई sheet | तुरंत रुको और owner को alert करो |
| **Logic** | Run success होता है पर गलत काम करता है, जैसे कोई field गलत map हुआ हो | इन्हें सिर्फ़ validation और monitoring पकड़ते हैं |

Status codes बस शुरुआत हैं। दो patterns ज़्यादा बताते हैं:

- **बाकी records निकल जाते हैं, पर एक ही record हर attempt पर fail होता है।** तब दिक्कत उस record में है, भले code 500 कहे। कुछ APIs bad input पर crash होकर server error report करती हैं। आम retries के बाद उसे "needs attention" में भेजो।
- **हर record एक के बाद एक fail होता है।** तब दिक्कत service या आपके credentials में है, records में नहीं। 2,000 items को एक-एक करके fail होने देने की जगह जल्दी रुक जाओ।

### Timeouts का मतलब साफ़ नहीं होता

Timeout का मतलब है कि आपने इंतज़ार करना बंद कर दिया, ये नहीं कि provider ने कुछ नहीं किया। SMS शायद चला गया हो और सिर्फ़ जवाब खो गया हो। आँख बंद करके retry करो और customer को वो दो बार मिलेगा। मिसाल के लिए, Stripe के docs कहते हैं कि 500 को भी ऐसे ही मानो: पैसा गया भी हो सकता है, नहीं भी।

सुरक्षित pattern के तीन हिस्से हैं:

1. **Call से पहले attempt record करो।** एक unique key और "sending" status के साथ send-log row लिखो; बाद में उसे "sent" या "failed" में update करो।
2. **Provider support करे तो idempotency key भेजो।** Idempotency key एक unique value है जो आप request के साथ भेजते हो ताकि provider repeat को पहचान सके। मिसाल के लिए, Stripe एक `Idempotency-Key` header लेता है: उसी key और उन्हीं details के साथ retry करो तो वो दोबारा charge करने की जगह पहला result लौटा देता है। उसके v1 API docs कहते हैं कि उसी key के साथ 24 hours के अंदर retry करो (November 2026 के हिसाब से)। अपने provider के docs check करो; कुछ ये देते हैं, कुछ नहीं।
3. **Timeout पर retry से पहले देखो।** अगर provider के पास status API है, तो पूछो कि message या payment मौजूद है या नहीं। Retry सिर्फ़ तब करो जब वो न हो। Retry के लिए कभी नई key मत बनाओ: नई key provider को बताती है कि "ये एक नई request है"।

अगर provider के पास न idempotency key है न status lookup, तो हर action के लिए तय करो कि कौन-सी गलती सस्ती है। दो बार भेजा गया delivery update परेशान करता है; दो बार दिया गया refund असली पैसा है। पैसे से जुड़ी किसी भी चीज़ में unknown नतीजे को auto-retry मत करो: उसे "needs attention" में डालो ताकि कोई इंसान check करे।

### Retry से पहले throttle करो

किसी जाने-पहचाने daily peak पर rate limits (HTTP 429) बदकिस्मती नहीं हैं: आप अपने plan की इजाज़त से तेज़ भेज रहे हो। **Provider की documented limit से तेज़ मत भेजो**, ताकि 429s कम ही आएँ, और retries को safety net की तरह रखो।

मान लो, plan हर second 10 messages की इजाज़त देता है। एक second के gap के साथ 8 के batches भेजो: इससे उसी account को use करने वाले दूसरे workflows के लिए 20 percent headroom बचता है। तब 3,000 evening messages में लगभग 375 seconds लगते हैं, छह मिनट से थोड़ा ज़्यादा। n8n में ये HTTP Request node के **Batching** option (Items per Batch और Batch Interval) से कर सकते हो, या एक **Loop Over Items** node और loop के अंदर एक **Wait** node से।

### Backoff और jitter के साथ retry

Temporary errors को कुछ बार retry करो, हर बार ज़्यादा इंतज़ार करके। फिर **jitter** जोड़ो, यानी हर wait पर थोड़ा random extra समय। इसके बिना, जब 7 pm पर 500 items fail होते हैं, तो सारे 500 ठीक उसी second पर retry करते हैं और फिर साथ में fail हो जाते हैं।

```flow
dir: LR
Attempt 1 -[fail]-> 5 से 10 s wait -> Attempt 2 -[fail]-> 10 से 20 s wait -> Attempt 3 -[fail]-> 20 से 40 s wait -> Attempt 4 -[fail]-> Needs attention और alert
```

एक समझदारी वाला default: हर बार wait को double करो, 0 से 100 percent random जोड़ो, 3 से 5 attempts के बाद रुक जाओ। किसी 429 के साथ **Retry-After** header आ सकता है, seconds में या एक date के रूप में। अपने number की जगह उसे use करो।

**n8n आपको क्या देता है।** हर node में **Max Tries** और **Wait Between Tries (ms)** के साथ एक **Retry On Fail** setting होती है। November 2026 के हिसाब से, n8n के docs कहते हैं कि Max Tries ज़्यादा से ज़्यादा 5 और wait ज़्यादा से ज़्यादा 5,000 ms हो सकता है, और HTTP Request node आपके लिए Retry-After नहीं पढ़ता। Wait की एक ही setting है, इसलिए wait बढ़ता नहीं। Network blip के लिए ये ठीक है। लंबे, बढ़ते waits के लिए retry खुद बनाओ: node के error output को एक Wait node पर route करो और वापस loop करो, एक counter के साथ ताकि वो रुक जाए।

### Idempotency: दो बार चलाना भी safe

कोई step **idempotent** है जब उसे दो बार चलाने का असर एक बार चलाने जितना ही हो। Retries और reruns steps को दोहराते हैं, इसलिए कुछ भी create करने वाले हर step को इसकी ज़रूरत है।

हर action के लिए एक **unique key** के साथ send log रखो। Act करने से पहले check करो कि key पहले से "sent" mark है या नहीं; है तो skip करो। Key को **action जिस चीज़ के बारे में है** उससे चुनो, ताकि एक ही real-world action से हमेशा एक ही key बने:

| Action | अच्छी key | खराब key, और क्यों |
| --- | --- | --- |
| Delivery update SMS | Order id plus status, जैसे ORD-4471 plus "out for delivery" | Run id: हर rerun को नई मिलती है, तो कभी कुछ skip नहीं होता |
| Monthly fee reminder | Member id plus billing month | सिर्फ़ member id: ये अगले महीने का reminder रोक देती है |
| Ledger में invoice | Supplier का invoice number | Process करने का समय: हर बार unique, तो कुछ नहीं पकड़ता |

अगर दो runs overlap कर सकते हैं, तो check के बाद action में भी race हो सकती है: दोनों runs check करते हैं, दोनों को कुछ नहीं दिखता, दोनों भेज देते हैं। "sending" row पहले लिखना, ऐसे store में जो उसी key की दूसरी row मना कर दे (जैसे unique constraint वाली database table), ये gap बंद कर देता है।

### जो वापस आता है उसे validate करो

Green tick का मतलब सिर्फ़ इतना है कि call लौट आई। Check करो कि response समझ में आता है: जो list आनी थी वो खाली नहीं है, ज़रूरी fields मौजूद हैं, "200 OK" body में कोई error message नहीं है। अगर जिस export में आम तौर पर 8,000 rows होती हैं उसमें एक भी नहीं है, तो उसे error मानकर रुको, "successfully" कुछ न करने की जगह। n8n में एक IF node bad responses को **Stop and Error** node पर route कर सकता है, जो जानबूझकर run fail कर देता है।

### खराब records अलग करो, पर सब fail हो तो रुको

300 में से एक खराब item बाकी 299 को नहीं रोकना चाहिए। Items को अलग-अलग process करो और हर failure को उसके reason के साथ एक "needs attention" list में लिखो, जिसे कभी-कभी **dead-letter queue** कहते हैं। n8n में node का **On Error** **Continue (using error output)** पर set करो और उस output को list से जोड़ो। कोई उन records को ठीक करके बाद में दोबारा process करता है। कुछ भी चुपचाप नहीं खोता।

उल्टे case में **circuit breaker** चाहिए: एक rule जो failures जमा होने पर run को pause कर दे, जैसे लगातार 20 failures, या आखिरी 50 items में से आधे से ज़्यादा। इसके बिना एक outage 2,000 dead-letter rows और 2,000 alerts बन जाता है।

### काम के alerts

| कमज़ोर alert | काम का alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. SMS provider का token expire हो गया है। Settings, Credentials, SMS provider में उसे renew करो, फिर rerun करो; भेजे जा चुके messages skip होंगे। Run link: ..." |

वहाँ भेजो जहाँ owner सच में देखता है, जैसे email, Slack, Teams या WhatsApp। Repeats को group करो, ताकि एक outage पर 500 नहीं, एक message जाए।

n8n में एक अलग **error workflow** बनाओ जो **Error Trigger** node से शुरू हो, और उसे हर workflow की Settings में चुनो। ये तब चलता है जब कोई automatic execution fail हो। जब आप हाथ से test करते हो तब ये नहीं चलता, इसलिए इसे किसी असली scheduled या webhook run से test करो।

### सिर्फ़ errors नहीं, volume भी monitor करो

सबसे खतरनाक failure में कोई error होता ही नहीं। हर दिन processed items और failures track करो। "1,000 से कम" जैसा fixed threshold हर शांत Sunday को fire होता है और आधे टूटे दिन को miss कर देता है। इसकी जगह **उसी weekday के हाल के average** से compare करो, जैसे "अगर 8 pm तक हमने पिछले चार Tuesdays के average के आधे से कम भेजे हैं तो alert करो", और rule को हर महीने review करो।

### n8n में क्या use करें

| काम | n8n feature |
| --- | --- |
| Blip के लिए छोटा retry | Node Settings, Retry On Fail |
| लंबे या बढ़ते waits | Error output से Wait node पर, counter के साथ वापस loop |
| Rate limit के अंदर रहना | HTTP Request Batching, या Wait node के साथ Loop Over Items |
| एक खराब record के बावजूद आगे बढ़ना | On Error को Continue (using error output) पर set करना |
| पूरा run रोकना | On Error को Stop Workflow पर set करना, या एक Stop and Error node |
| किसी भी failed run पर alert | Error Trigger node से शुरू होने वाला error workflow |
| Duplicates और dead letters | आपके send log में lookup, और failed records के लिए एक sheet या table |

### Ownership और एक runbook

हर automation का एक नामित owner और एक छोटा runbook होता है: ये क्या करता है, आम failures, हर एक को कैसे ठीक करें, और सुरक्षित तरीके से rerun कैसे करें।

## एक example से समझो

Bengaluru का एक logistics startup एक automation चलाता है जो customers को SMS से delivery updates भेजता है और order system update करता है: दिन में लगभग 8,000 messages, ज़्यादातर 6 pm से 9 pm के बीच। नीचे के numbers एक typical पहले महीने का illustration हैं, measured results नहीं।

**पहला महीना बुरा गया:**

| दिक्कत | वजह |
| --- | --- |
| Evening peaks पर messages fail हुए | Workflow जितना तेज़ हो सका भेजता रहा, और SMS provider ने उसे rate-limit कर दिया (HTTP 429) |
| कुछ customers को दो messages मिले | एक failed run को हाथ से rerun किया गया और उसने पहले वाले messages फिर भेज दिए; timeout वाले sends आँख बंद करके retry हुए |
| एक दिन कुछ नहीं गया, और कोई error भी नहीं | Order system का login token expire हो गया था; export step ज़ोर से fail होने की जगह खाली list लौटा रहा था |

**Fixes:**

1. **Plan की limit तक throttle:** provider के documented rate से नीचे batches, बीच में एक wait के साथ।
2. 429s पर **backoff और jitter के साथ retries**, Retry-After हो तो उसे use करके, ज़्यादा से ज़्यादा चार attempts, फिर "needs attention" sheet। किसी send पर timeout या 500 से 504 पहले fix 3 वाले status check से गुज़रता है।
3. **Order id plus status से key किया हुआ send log।** हर message call से पहले "sending" के रूप में लिखा जाता है। Rerun "sent" mark वाली हर चीज़ skip करता है। Timeout के बाद, workflow दोबारा भेजने से पहले उस key से provider का delivery status check करता है।
4. **Export को validate करना।** खाली या बहुत छोटा export अब green खत्म होने की जगह run को "order export ने 0 rows लौटाईं; order system login check करो" के साथ रोक देता है। यही वो fix है जो उस चुप दिन को पकड़ लेता।
5. **Credentials errors run को तुरंत रोकते हैं** और owner को alert करते हैं कि token कहाँ renew करना है।
6. **एक circuit breaker:** लगातार 20 failed sends run को pause करते हैं और एक alert भेजते हैं।
7. **8 pm पर एक volume check**, उसी weekday के पिछले चार दिनों के average से compare करके, 50 percent से नीचे होने पर alert।

**अगला महीना (illustrative):**

| Measure | महीना 1 | महीना 2 |
| --- | --- | --- |
| Duplicate messages | लगभग 900 | 3, सब उन timeouts के बाद जब status lookup खुद down था |
| Rate limits की वजह से खोए messages | लगभग 1,200 | 0; कुछ 429s, सब retry पर भेज दिए गए |
| अगला login expiry ठीक करने में लगा समय | लगभग 9 hours (पहले एक customer ने complain किया) | 20 minutes (alert ने बताया कि क्या करना है) |
| Attention वाले records | पता नहीं | 35, हर एक reason के साथ, सब एक दिन के अंदर ठीक |

जब provider बता नहीं सकता कि क्या हुआ, तो आपको एक कभी-कभार के duplicate और एक कभी-कभार छूटे update में से चुनना पड़ता है। Delivery updates के लिए team ने duplicate चुना।

## आम गलतियाँ

- **सब कुछ retry करना।** Permanent errors को ठीक करना पड़ता है; जो record हर बार fail हो उसकी जगह "needs attention" में है।
- **Timeout वाले send को आँख बंद करके retry करना।** पहला attempt शायद काम कर गया हो। पहले अपनी key से check करो।
- **हर attempt पर नई key।** Run id या timestamp हर retry को नया दिखाता है, तो कुछ skip नहीं होता।
- **Throttling की जगह retries।** अगर 429s रोज़ उसी घंटे आते हैं, तो धीमे हो जाओ; बस और ज़ोर से retry मत करो।
- **बिना jitter और बिना cap के fixed waits।** सब कुछ एक साथ retry होता है, outage और बिगड़ता है और आप block भी हो सकते हो।
- **Green run पर भरोसा करना।** खाली या अजीब "successful" responses को validate करो।
- **एक खराब item batch रोक देता है, या एक dead service हर item fail कर देती है।** Records अलग करो, पर failures जमा हों तो run रोक दो।
- **बिना details के alerts, या 500 alerts।** एक बार बताओ कि क्या टूटा और क्या करना है।

## Practice करो

नीचे linked n8n की error handling guide पढ़ो, और N8N102 course का error-handling हिस्सा फिर से देखो।

1. **Retries।** एक HTTP Request node को ऐसे endpoint पर point करो जो जानबूझकर fail होता है (जैसे आपका अपना छोटा webhook workflow जो 503 लौटाए)। Retry On Fail on करो और execution log में confirm करो कि retries सच में चले। फिर error output, एक Wait node और एक counter से एक लंबा retry बनाओ।
2. **Throttle।** 50 test items timed batches में भेजो और check करो कि timing आपके plan से match करती है।
3. **Duplicates और dead letters।** एक unique key वाला send log, "sending" फिर "sent" status, और एक "needs attention" sheet जोड़ो। Workflow दो बार चलाओ और दिखाओ कि कुछ भी दो बार नहीं गया।
4. **Alerts और checks।** Error Trigger node और एक काम के alert के साथ एक error workflow बनाओ, एक empty-result check और एक same-weekday volume check भी।

**आपका काम पूरा है जब आप** अपने workflow को चार तरीकों से तोड़ सको, एक temporary error, एक permanent error, एक खराब item और एक खाली input से, हर एक के लिए सही behaviour दिखा सको, और उसे बिना duplicates के rerun कर सको।
