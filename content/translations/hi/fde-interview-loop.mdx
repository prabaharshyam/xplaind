## ये क्या है

Forward deployed engineer (FDE) client के organisation के अंदर रहकर काम करता है और किसी धुंधली business problem को ऐसे software में बदलता है जिसे लोग सच में use करते हैं। Interview loop कुछ घंटों में आपको यही करते हुए देखने की कोशिश करता है।

### ये role और loop कहाँ से आए

Palantir कहता है कि ये role उसी ने शुरू किया। वो इन engineers को Forward Deployed Software Engineers कहता है, निकनेम "Deltas", और इनकी तुलना "Devs" से करता है जो core platform बनाते हैं: एक Dev कई customers के लिए एक capability बनाता है, एक Delta एक customer को कई capabilities से serve करता है। Candidate reports और prep guides बताते हैं कि ज़्यादातर Palantir FDE onsites में एक "decomposition" round होता है: लगभग 60 मिनट, code थोड़ा या बिल्कुल नहीं, और interviewer ऐसा customer बनता है जिसकी problem धुंधली है। कुछ लोग एक "learning" round भी बताते हैं, जिसमें आपको कोई अनजाना concept, API या system जल्दी समझकर उस पर build करना होता है।

अब AI labs और AI startups भी ये title use करते हैं। OpenAI और Anthropic दोनों ऐसे FDEs hire करते हैं जो बड़े customers के साथ embed होते हैं। OpenAI के loop पर prep guides production-level coding और system design, एक customer-facing exercise और एक project deep-dive बताते हैं जिसमें आपको अपनी बनाई चीज़ का हर फ़ैसला defend करना होता है। बताए गए rounds की गिनती अलग-अलग है, इसलिए किसी exact number पर भरोसा मत करो।

भारत में ये title तेज़ी से फैल रहा है। July 2026 में TCS के chief executive K Krithivasan ने Reuters को बताया कि company अपने staff का 1% से 1.5% हिस्सा forward deployed roles में चाहती है, जिसे Reuters ने लगभग 5,900 से 8,900 लोग आँका; उन्होंने ये नहीं बताया कि ये लोग hire होंगे या retrain। July 2026 में खबर आई कि Coforge अपनी FDE team को लगभग 20 से 100 तक बढ़ाने का plan कर रहा है। 2026 में इस title वाली Bengaluru postings में Google Cloud और Nanonets शामिल थे। कुछ firms इसी काम के लिए दूसरे titles use करती हैं, इसलिए job description पढ़ो।

### Rounds और हर एक क्या test करता है

| Round | क्या test करता है | Strong कैसा दिखता है |
|---|---|---|
| Practical coding | उलझा data, APIs, validation, tests | पहले data के बारे में पूछता है; खराब rows report करता है; edge cases test करता है |
| Problem decomposition | धुंधले goal को plan में बदलना | Solutions से पहले सवाल; एक KPI, एक baseline और gate वाला पहला step |
| Learning (Palantir में बताया गया) | अनजाने system को जल्दी समझना | अच्छे सवाल; system को तोड़े बिना extend करना |
| AI system design | Client constraints के अंदर end-to-end design | Client के data, rules, budget और team से जुड़े choices |
| Client role-play | दबाव में expectations संभालना | न झुकता है, न मना करता है; options देता है; एक owner और एक तारीख के साथ खत्म करता है |
| Behavioural और project deep-dive | Ownership, टकराव, failure, सीखना | नापे गए result और एक lesson वाली STAR कहानियाँ |
| Take-home या work sample | Time box के अंदर judgement | चलता हुआ core path, ईमानदार README, छोटा eval, लगा समय लिखा हुआ |

हर company हर round नहीं रखती। FDE roles के लिए सबसे खास decomposition है:

```flow
dir: LR
title: Decomposition round
एक धुंधली problem -> Goal और owner -> Process और data -> KPI + baseline -> Non-AI समेत options -> Proof of concept + gate -> Risks
```

ये lesson Arjun को follow करता है, एक काल्पनिक candidate जो Indian banks को बेचने वाले एक AI startup के FDE loop की तैयारी कर रहा है।

### Practical coding

कई FDE coding rounds असली client काम जैसे दिखते हैं, हालाँकि कुछ loops, जिनमें candidates के हिसाब से Palantir का loop भी है, algorithm जैसे problems भी देते हैं; पूछ लो कि क्या आएगा। एक realistic 30 मिनट का task: "एक lender अपने branch system से UPI collections CSV में export करता है। कुछ rows में amount नहीं है, dates दो formats में हैं, या transaction ID repeat है। साफ़ records और reasons के साथ rejected rows की list return करो, फिर इसे एक API endpoint के पीछे रखो।"

पहले दो मिनट सवालों पर लगाओ। Duplicate को reject करना है, या दूसरी copy जीतेगी? Negative amounts refunds हैं या errors? कौन-से date formats आते हैं? फिर core लिखो:

```python
from datetime import date, datetime
from decimal import Decimal
from pydantic import BaseModel, Field, ValidationError, field_validator

class Txn(BaseModel):
    txn_id: str = Field(min_length=1)
    amount: Decimal = Field(gt=0)
    paid_on: date

    @field_validator("paid_on", mode="before")
    @classmethod
    def parse_date(cls, v: str) -> date:
        for fmt in ("%Y-%m-%d", "%d/%m/%Y"):
            try:
                return datetime.strptime(str(v).strip(), fmt).date()
            except ValueError:
                pass
        raise ValueError(f"unknown date format: {v!r}")

def clean(rows):
    good, rejected, seen = [], [], set()
    for line, row in enumerate(rows, start=2):  # line 1 is the header
        try:
            txn = Txn(**row)
        except ValidationError as e:
            rejected.append((line, e.errors()[0]["msg"]))
            continue
        if txn.txn_id in seen:
            rejected.append((line, "duplicate txn_id"))
            continue
        seen.add(txn.txn_id)
        good.append(txn)
    return good, rejected
```

छह rows का sample दो (एक अच्छी row, एक बिना amount, एक `dd/mm/yyyy` date वाली, एक repeat ID, एक negative amount और एक "Nov 5" date वाली), तो ये दो rows रखता है और चार reject करता है, हर एक के साथ उसका line number और reason। `float` की जगह `Decimal` जानबूझकर है: पैसे में rounding errors नहीं आने चाहिए। Upload की गई file लेने वाले FastAPI endpoint में `clean` को wrap करने में बस कुछ मिनट और लगते हैं ("FastAPI से REST APIs" lesson देखो)।

| Interviewers क्या check करते हैं | Weak | Strong |
|---|---|---|
| सवाल | तुरंत type करना शुरू | पूछता है कि खराब row किसे मानें और duplicates का क्या करें |
| खराब data | खराब rows चुपचाप skip | हर rejected row reason के साथ return |
| Types | पैसे के लिए floats, dates के लिए strings | `Decimal`, असली dates, एक validation model |
| Tests | "मेरे sample पर चल रहा है" | शुरू में बताए edge cases के लिए दो-तीन tests |
| बोलना | दस मिनट चुप | हर trade-off ज़ोर से बोलना, जैसे "अभी duplicates reject कर रहा हूँ; बदलना आसान है" |

अगर task में language model है, तो भी यही आदतें: एक schema define करो, reply validate करो, validation error के साथ एक-दो बार retry करो, फिर साफ़-साफ़ fail करो और log करो। ये pattern "Structured JSON output पाना" lesson में है।

### Problem decomposition

"एक hospital discharge delays कम करना चाहता है" जैसा prompt मिले, तो score final answer पर नहीं, आपके सोचने के तरीके पर होता है। छह steps ज़ोर से बोलते हुए करो:

1. **Goal और उसका owner clarify करो।** कौन पूछ रहा है, और उसके लिए क्या बदलेगा?
2. **अभी के process, volumes और data के बारे में पूछो।** समय असल में कहाँ जाता है? रोज़ कितने discharges? क्या record होता है, और कहाँ?
3. **एक KPI और एक baseline पर सहमति बनाओ**, जैसे "fit for discharge" से bed छोड़ने तक के median घंटे, आज नापे हुए।
4. **Non-AI समेत options की list बनाओ**, जैसे एक checklist या pharmacy timing में बदलाव, फिर एक चुनो और बताओ क्यों।
5. **Gate के साथ एक proof of concept plan करो।** Proof of concept असली data पर एक छोटा, time-boxed test है। Gate पहले से तय एक number है जो बताता है कि आगे बढ़ना है या नहीं, जैसे "एक ward में चार हफ़्ते में median delay 20% कम करना"।
6. **Risks बताओ और उन्हें कैसे कम करोगे**: patient data rules, staff adoption, गलत outputs।

अगर interviewer कोई numbers न दे, तो assumptions ज़ोर से बोलो ("मान लो तीन hospitals में रोज़ 200 discharges")। दो failure modes आम हैं: पहले पाँच मिनट में ही model propose कर देना, और बस सवाल पूछते रहना। आधे समय तक board पर एक KPI और एक पहला option होना चाहिए। सवालों पर "Discovery" lesson और गहराई में जाता है।

### Learning round

Palantir के loop पर prep guides और candidate reports एक interviewer के बारे में बताते हैं जो आपका reference बनता है, जब आप कोई अनजाना concept, API या system सीखते हो और फिर उस पर build करते हो। Score आपकी learning curve है: आप सटीक सवाल पूछते हो या नहीं, summarise करके अपनी समझ check करते हो या नहीं, और जो बताया गया उस पर build करते हो या नहीं। Practice के लिए किसी अनजानी open-source repository को 20 मिनट पढ़ो, फिर एक module ज़ोर से समझाओ और एक छोटा feature जोड़ो।

### AI system design

Structure "Design interview" lesson में है। FDE वाला twist ये है कि client के constraints ही problem हैं, noise नहीं: ऐसा data जो भारत में ही रहना चाहिए, पहले से मौजूद vendor stack, fixed budget, एक छोटी team जो आपके जाने के बाद इसे maintain करेगी। हर choice को इनमें से किसी एक से जोड़ो, और evals, एक human fallback और एक handover plan शामिल करो।

### Client role-play

Interviewer एक ऐसा client बनता है जो शक करता है, बेसब्र है या requirements बदलता रहता है। पाँच moves use करो:

1. जो सुना उसे एक वाक्य में **summarise करो**।
2. **Demand के पीछे की ज़रूरत ढूँढो।** पूछो कि तारीख या request के पीछे क्या है।
3. **Risks को facts की तरह बताओ**, डर की तरह नहीं: क्या untested है, क्या गलत हो सकता है, किस पर असर पड़ेगा।
4. **Trade-offs के साथ दो options दो** और client को चुनने दो।
5. अगले step, एक owner, एक तारीख और लिखित confirmation के साथ **खत्म करो**।

| Situation | Weak response | Strong response |
| --- | --- | --- |
| "अगले हफ़्ते सभी branches में live कर दो" | "ठीक है, try करेंगे" या "नामुमकिन" | पूछो कि तारीख के पीछे क्या है; risks बताओ; board demo या partial rollout offer करो |
| "AI ने गलती की; हम cancel कर रहे हैं" | Model को defend करना | पूछो क्या हुआ, case देखो, safeguards और fix plan समझाओ |
| "ये feature भी जोड़ दो" | मौके पर हाँ कह देना | "मैं इसे size करके गुरुवार तक options के साथ आता हूँ" |
| आपके proposal के बाद चुप्पी | बोलते रहना | सीधा सवाल पूछो: "इनमें से कौन-सा आपकी board timeline में fit होता है?" |

नई request को size करने पर "Scope creep को संभालना" lesson और गहराई में बात करता है।

### Behavioural सवाल और project deep-dive

STAR (situation, task, action, result) से छह से आठ कहानियाँ तैयार करो, हर एक में नापा हुआ result और एक lesson। ये cover करो: एक project जो आपने शुरू से आख़िर तक चलाया, किसी stakeholder से असहमति, एक failure, एक बार जब आपने मना किया, धुंधली स्थिति में काम करना, और कुछ जल्दी सीखना। जो आपने किया उसके लिए "मैं" बोलो और "हम" सिर्फ़ team के काम के लिए।

ये रही एक strong कहानी। Situation: "हमारी team की monthly sales report में तीन दिन का manual spreadsheet काम लगता था।" Task: "मुझसे इसे तेज़ करने को कहा गया।" Action: "मैंने steps map किए, data pulls और checks Python में automate किए, और एक validation step जोड़ा जिसे analysts review करते थे।" Result: "अगले तीन monthly cycles में हर बार लगभग चार घंटे लगे, और release के बाद मिलने वाली errors महीने में पाँच से शून्य हो गईं।" Lesson: "मुझे analysts को पहले शामिल करना चाहिए था; उनके checks ने दो edge cases पकड़े जो मुझसे छूट गए थे।" इस result में एक before, एक after, एक समय और नापने का तरीका है।

Project deep-dive में हर choice पर "X क्यों नहीं?" की उम्मीद रखो: जो alternative आपने reject किया और क्यों, वो तैयार रखो।

### Take-home

- **Time box का सम्मान करो।** अगर चार घंटे कहा है, तो लगभग चार लगाओ और README में असली number लिखो। बीस घंटे की polish बताती है कि आप constraints को नज़रअंदाज़ करते हो।
- **Breadth जोड़ने से पहले एक path को end to end चलाओ।**
- **README लिखो**: एक command में कैसे चलाएँ, assumptions, trade-offs, आगे आप क्या करोगे।
- **Evidence दिखाओ**: कुछ tests, या labelled examples पर एक छोटा eval, failures की ईमानदार list के साथ।
- **अगर present करो**, तो client की problem और result से शुरू करो, फिर design।
- **जो AI-tool rules दिए गए, उन्हें follow करो**, और बताओ कि allowed tools आपने कैसे use किए।

### अभी तक client experience नहीं है

इस path पर ज़्यादातर learners का कभी पैसे देने वाला client नहीं रहा। फिर भी आपके पास कहानियाँ हैं। एक professor, एक internship manager, एक hackathon judge, एक family business या एक NGO "client" हो सकता है। हर एक के लिए note करो कि उन्होंने क्या माँगा, उन्हें क्या चाहिए था, एक असहमति और एक number। इससे भी बेहतर, किसी असली इंसान के लिए कुछ छोटा बनाओ, जैसे किसी kirana दुकान के लिए low-stock alert sheet, और notes रखो। आपकी capstone case study ("एक case study, शुरू से आख़िर तक" lesson देखो) एक project deep-dive दे सकती है।

## एक example से समझो

Arjun के पास loop से पहले एक हफ़्ता है। उसका plan:

| Day | Focus | Output |
| --- | --- | --- |
| 1 | Recruiter सवाल; rounds की list | Round list, timings और AI-tool rules एक note में |
| 2 | Coding | दो 30 मिनट के tasks: ऊपर वाला CSV cleaner और retries के साथ एक structured-output call |
| 3 | Decomposition | "एक state transport corporation कम complaints चाहता है" पर दो timed, recorded attempts |
| 4 | Behavioural | छह STAR कहानियाँ लिखीं, हर एक दो मिनट से कम में ज़ोर से पढ़ी |
| 5 | Role-play | दो role-plays, एक दोस्त client बना |
| 6 | System design | Bank branch staff के लिए policy assistant का एक design |
| 7 | Full mock | हर type का एक mock round; शाम को आराम |

Day 3 पर उसकी पहली recording में वो तीन मिनट में ही chatbot propose कर देता है। दूसरी attempt में बारह मिनट सवालों पर लगाकर वो प्रति लाख passenger trips complaints वाले KPI पर पहुँचता है।

असली loop में role-play ऐसे चलता है। Interviewer Mumbai के एक private bank की branch operations head Meera बनता है। Pilot assistant bank की 180 में से 12 branches में staff के policy सवालों के जवाब देता है।

> **Meera:** "ये pilot बहुत धीमा चल रहा है। हमारे MD चाहते हैं कि अगले शुक्रवार तक ये सभी 180 branches में live हो।"
>
> **Arjun:** "मैं check कर लूँ कि सही समझा: pilot धीमा लग रहा है, इसलिए MD चाहते हैं कि शुक्रवार तक हर branch live हो। अगले शुक्रवार क्या हो रहा है?"
>
> **Meera:** "Board meeting है। वो दिखाना चाहते हैं कि हम AI में आगे हैं।"
>
> **Arjun:** "इससे मदद मिली। तो असली goal board के लिए एक मज़बूत कहानी है। दो facts मायने रखते हैं। आपका security review अभी पूरा नहीं हुआ, और दो pilot branches में अभी आधे से कम staff assistant use करता है। अगर review के बिना 180 branches चालू कर दीं, तो आपकी security team इसे रोक सकती है, और board को rollback की खबर मिलेगी।"
>
> **Meera:** "मतलब आप मना कर रहे हो।"
>
> **Arjun:** "मैं कह रहा हूँ कि शुक्रवार तक MD को कुछ असली देने के दो तरीके हैं। एक: live pilot numbers के साथ board demo और तारीखों वाला तीन-wave rollout plan। दो: जो पाँच pilot branches तैयार हैं उनमें full use चालू करना, अगर आपकी security team सोमवार तक एक fast review पूरा कर दे। पहला ज़्यादा safe है; दूसरा ज़्यादा दिखाता है पर review पर निर्भर है।"
>
> **Meera:** "Board को असली branches पसंद आएँगी। Option दो try करते हैं।"
>
> **Arjun:** "तो मैं आज ही आपकी security team को review pack भेजता हूँ, और हम सोमवार शाम 5 बजे तक फ़ैसला करेंगे। अगर clear नहीं हुआ, तो demo पर लौट आएँगे। मैं एक घंटे के अंदर owners और तारीखों के साथ email पर ये confirm करता हूँ।"

पाँचों role-play moves यहाँ हैं, साथ में एक fallback भी। जब Meera कहती है "मतलब आप मना कर रहे हो", तो वो बहस नहीं करता; वापस options पर जाता है।

Behavioural round में वो ऊपर वाली sales-report कहानी (तीन दिन से लगभग चार घंटे) use करता है, और एक दूसरी college project से, जहाँ उसके retries और alerts जोड़ने के बाद एक महीने में nightly failed data jobs 12% से 1% पर आ गईं।

## आम गलतियाँ

- **सिर्फ़ coding की तैयारी।** Decomposition और role-play को भी उतनी ही timed practice चाहिए।
- **सीधे solution पर कूदना।** पहले goal, process और data के बारे में पूछो, ज़ोर से।
- **Drive किए बिना बस सवाल पूछते रहना।** Decomposition round के आधे तक board पर एक KPI और एक पहला option रखो।
- **हर बात पर हाँ, या सीधा ना।** Interviewers ये test करते हैं कि आप request को size करके client को असली choice दे सकते हो या नहीं।
- **बिना results की कहानियाँ।** हर कहानी में एक before और एक after, कैसे नापा, आपका अपना हिस्सा और एक lesson चाहिए।
- **Generic system designs।** हर choice को client के constraints से जोड़ो।
- **Take-home को overbuild करना।** Time box से बहुत आगे जाने से आपका judgement दिखता नहीं, छिप जाता है।
- **AI-tool rules को नज़रअंदाज़ करना।** हर round में पूछो कि क्या allowed है और उसे follow करो।

## Practice करो

Tech Interview Handbook की behavioural guide और FDE role पर a16z का essay पढ़ो।

1. अपने काम या projects से छह STAR कहानियाँ लिखो, हर एक में नापा हुआ result और एक lesson। हर एक को दो मिनट से कम में ज़ोर से पढ़ो।
2. ऊपर वाला CSV-cleaning task tests के साथ 30 मिनट में करो, करते हुए ज़ोर से बोलते रहो।
3. अपनी पसंद की Indian business problems पर तीन timed decomposition exercises (हर एक 30 मिनट) करो। खुद को record करो और note करो कि पहले proposal से पहले कितने मिनट बीते। पाँच से कम मतलब आप कूद गए।
4. किसी दोस्त से इस path के lessons के किसी scenario पर मुश्किल client बनने को कहो। पाँचों role-play moves practice करो और एक owner और एक तारीख के साथ खत्म करो।

**आपका काम पूरा है जब आप** किसी अनदेखी business problem को 30 मिनट में, ज़ोर से बोलते हुए, सवालों, एक KPI और gate वाले proof of concept में तोड़ सको, और role-play client की अव्यावहारिक demand को बिना झुके या मना किए संभाल सको।
