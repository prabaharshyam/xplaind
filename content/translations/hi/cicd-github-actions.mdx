## ये क्या है

**Continuous integration (CI)** हर change पर checks चलाता है: lint, type checks, unit tests, और AI systems के लिए एक छोटा eval suite। जो change fail हो, वो merge नहीं होता।

**Continuous delivery (CD)** merge हुए change को अपने आप environments से गुज़ारता है: image build करो, staging पर deploy करो, smoke tests चलाओ, फिर production पर deploy करो, अक्सर किसी इंसान की approval के बाद।

GitHub Actions दोनों करने का एक आम तरीका है। Workflows `.github/workflows/` में YAML files होती हैं, जो pull request या main पर push जैसे events पर चलती हैं। GitLab CI, Azure DevOps और Jenkins भी ऐसे ही काम करते हैं; clients अपनी पसंद का चुनेंगे।

```flow
Pull request -> CI: lint, types, tests, smoke eval -> Pass हुआ?
Pass हुआ? -[no]-> Block
Pass हुआ? -[yes]-> Merge हो सकता है -> Merge to main
Merge to main -> Image build करो | tag = commit hash
Image build करो -> Staging पर deploy -> Smoke tests -> तय reviewer की approval -> वही image production पर deploy -> कोई दिक्कत?
कोई दिक्कत? -[yes]-> पिछला tag दोबारा deploy करो
```

इस lesson में हम Kochi के एक insurer की engineering team को claims assistant के handover के साथ चलेंगे।

## ये कैसे काम करता है

**Triggers और jobs।** Workflow events पर चलता है (`pull_request`, main पर `push`, एक tag, manual dispatch)। उसमें jobs होते हैं; हर job एक नई machine पर steps चलाता है, जिसे runner कहते हैं।

**CI job** code checkout करता है, dependencies install करता है (caching के साथ), और lint, types और tests चलाता है। AI app के लिए एक छोटा, तेज़ eval जोड़ो: एक fixed retrieval index पर 20 golden questions, और accuracy threshold से नीचे गिरे तो build fail कर दो। धीमे और महँगे evals को रात की job के लिए रखो।

**Build job** Docker image बनाता है, उसे commit hash से tag करता है और client की registry में push करता है।

**Deploy jobs** **environments** use करते हैं। `staging` environment अपने आप deploy होता है; `production` environment के लिए एक तय reviewer की approval चाहिए और उसके अपने secrets होते हैं। Secrets CI system में रखे जाते हैं या run time पर cloud से लिए जाते हैं; repository में कभी नहीं। और बेहतर ये है कि runner stored keys की जगह OpenID Connect से short-lived credentials के साथ cloud में sign in करे।

**Rollback।** हर deploy एक commit से tag की गई image use करता है, इसलिए rollback का मतलब पिछला tag दोबारा deploy करना है। इसे एक button या एक command बनाओ और उसकी practice करो।

**क्या कहाँ और कितनी बार चलता है:**

| Check | कब | आम समय | Build fail करता है? |
| --- | --- | --- | --- |
| Lint और format | हर PR पर | Seconds | हाँ |
| Type checks | हर PR पर | एक मिनट से कम | हाँ |
| Fake model के साथ unit tests | हर PR पर | 1 से 3 मिनट | हाँ |
| Smoke eval, 20 golden questions | prompts या retrieval छूने वाले हर PR पर | 1 से 2 मिनट | हाँ, threshold से नीचे |
| Full eval, सैकड़ों cases | हर रात | 10 से 60 मिनट | Team को alert करता है |
| Load test | बड़े releases से पहले | बदलता रहता है | बहुत धीमा हो तो release रोकता है |

**Caching।** हर run पर dependencies install करना धीमा है। उन्हें lock file के हिसाब से cache करो, ताकि CI दस मिनट की जगह कुछ मिनट में चले। तेज़ CI use होता है; धीमे CI को लोग bypass कर देते हैं।

**Branch protection।** Repository settings में main पर merge करने से पहले CI job का pass होना और कम से कम एक review ज़रूरी करो। इसके बिना CI सिर्फ़ सलाह है।

**Secrets असल में।** Workflow को कुछ secrets चाहिए: smoke eval के लिए model API key, images push करने के credentials, deploy करने के credentials। उन्हें repository या environment की secret settings में रखो, जहाँ वो encrypted होते हैं और logs में छुपे रहते हैं। हर environment को अपने secrets दो, ताकि staging की key कभी production को न छू सके। Cloud access के लिए OpenID Connect पसंद करो: cloud एक खास repository और branch पर भरोसा करता है, और ऐसा credential देता है जो थोड़े समय में expire हो जाता है, अक्सर एक घंटे में। फिर leak होने के लिए कोई लंबे समय वाली key होती ही नहीं।

**एक पूरा workflow।** हर pull request पर CI, smoke eval सिर्फ़ तब जब AI files बदलें, और main पर build और deploy:

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: {enable-cache: true}
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - uses: astral-sh/setup-uv@v5
        if: steps.changed.outputs.ai == 'true'
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --min-accuracy 0.85
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@v6
        with: {push: true, tags: "ghcr.io/${{ github.repository }}:${{ github.sha }}"}

  deploy-production:
    needs: build
    runs-on: ubuntu-latest
    environment: production                    # requires a reviewer's approval
    permissions: {id-token: write, contents: read}
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh ghcr.io/${{ github.repository }}:${{ github.sha }}
```

Production job को cloud access OIDC से मिलता है (`id-token: write` और एक role जिस पर cloud भरोसा करता है), इसलिए GitHub में कोई लंबे समय वाली cloud keys नहीं रहतीं। Azure और Google Cloud के पास भी ऐसे ही login actions हैं।

**Smoke eval script अपने exit code से फ़ैसला करती है।** कोई भी non-zero exit job को fail कर देता है:

```python
import argparse, json, sys
from app.answer import answer                 # your pipeline

p = argparse.ArgumentParser(); p.add_argument("--min-accuracy", type=float, default=0.85)
args = p.parse_args()
cases = [json.loads(l) for l in open("evals/smoke.jsonl")]
correct = sum(c["expected"].lower() in answer(c["question"]).lower() for c in cases)
acc = correct / len(cases)
print(f"smoke accuracy {acc:.0%} on {len(cases)} cases")
sys.exit(0 if acc >= args.min_accuracy else 1)
```

**Actions को pin करो।** Third-party actions आपकी repository तक access के साथ चलते हैं। उन्हें एक version पर (या ज़्यादा सख़्त setups में पूरे commit hash पर) pin करो और updates review करो, ताकि कोई compromised action आपकी pipeline में न घुस सके।

**पुराने runs cancel करो।** `concurrency` block उसी branch पर दोबारा push करने पर पुराना run cancel कर देता है, जिससे runner minutes और model calls बचते हैं।

**अपने browser में try करो।** किसी workflow में unpinned actions और गायब timeouts check करो। YAML बदलो और चलाओ।

```python
import yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: some-org/setup-thing@main
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes so a stuck job cannot run for hours")
    for step in job["steps"]:
        ref = step.get("uses", "")
        if ref and ref.split("@")[-1] in ("main", "master"):
            print(f"{name}: pin {ref} to a version, not a branch")
```

## एक example से समझो

आप Kochi के एक insurer की engineering team को एक claims-assistant hand over करते हो। उनकी lead, Anjali, चाहती हैं कि हर change tested हो और उनकी team की sign-off के बिना production में कुछ न जाए।

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q
      - run: uv run python evals/smoke.py --min-accuracy 0.85
  deploy-staging:
    if: github.event_name == 'push'
    needs: test
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/build_push_deploy.sh staging ${{ github.sha }}
  deploy-production:
    needs: deploy-staging
    environment: production        # requires approval from the insurer's leads
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy.sh production ${{ github.sha }}   # same image, no rebuild
```

एक हफ़्ते बाद एक teammate prompt बदलता है और smoke eval 0.89 से 0.78 पर गिर जाता है; CI fail होता है और PR merge नहीं हो सकता। बाद में एक production deploy से responses धीमे हो जाते हैं; Anjali ज़्यादातर users को पता चलने से पहले ही, workflow page से पिछले commit की image दो मिनट में दोबारा deploy कर देती हैं।

**Insurer की team के लिए क्या बदला।** Pipeline से पहले deploys तब होते थे जब किसी को याद आता, किसी के laptop से, और किसी को पक्का पता नहीं होता था कि कौन-सा version live है। उसके बाद, production का हर version एक commit hash है जो workflow page पर दिखता है, हर deploy का एक नाम वाला approver है, और smoke eval ने दो महीनों में तीन prompt changes रोके, जिनमें से हर एक answer quality घटा देता। Anjali कहती हैं कि सबसे काम की चीज़ speed नहीं, भरोसा है: जब कोई claims manager बुरे जवाब की report करता है, तो team ठीक-ठीक बता सकती है कि कौन-सा code और prompt उसे बना रहा था।

## आम गलतियाँ

- **Tests सिर्फ़ main पर।** Problems merge के बाद पकड़ी जाती हैं। CI को pull requests पर चलाओ।
- **Prompt changes के लिए CI में कोई eval नहीं।** Prompt edits भी code changes हैं; उन्हें test करो।
- **Workflow files में secrets।** CI system के secrets या short-lived cloud credentials use करो।
- **हर environment के लिए अलग images बनाना।** एक बार build करो, वही image staging से production तक promote करो।
- **ऐसा rollback जिसे किसी ने कभी आज़माया नहीं।** ज़रूरत पड़ने से पहले practice करो।

- **Flaky tests को वैसे ही छोड़ देना।** जो test बेतरतीब fail होता है, वो लोगों को सिखा देता है कि pass होने तक CI दोबारा चला लो, और फिर असली failures भी नज़रअंदाज़ होने लगते हैं। Flaky tests को जल्दी ठीक करो या हटाओ।
- **बिना budget के हर PR पर live model call करने वाले evals।** PR eval छोटा और सस्ता रखो, जो हो सके cache करो, और पूरा suite schedule पर चलाओ।
- **OIDC उपलब्ध होने पर भी secrets में रखी लंबे समय वाली cloud keys।**
- **हर push पर paid evals चलाना**, सिर्फ़ ज़रूरी changes पर चलाने की जगह।
- **Unpinned third-party actions।**

## कब हल्की pipeline काफ़ी है

- **Personal project**: push पर lint और tests काफ़ी हैं।
- **Built-in deploys वाले platforms**, जैसे Vercel previews, जहाँ CI को सिर्फ़ checks चाहिए।
- **Notebooks और research code** जो कभी deploy नहीं होते।

## Demo से production तक

- **main पर merge से पहले CI और review ज़रूरी करो।**
- **Environments use करो**, approvals और production के अलग secrets के साथ।
- **Stored cloud keys की जगह OIDC से deploy करो।**
- **AI changes को smoke eval से gate करो** और पूरा eval हर रात चलाओ।
- **पिछले image tag पर rollback की practice करो।**

## Practice करो

GitHub का Actions quickstart और deployment environments वाला page पढ़ो।

1. अपनी किसी repository में ऐसा workflow जोड़ो जो हर pull request पर lint और tests चलाए।
2. ऐसी job जोड़ो जो main पर merges में आपकी Docker image बनाए और commit hash से tag करके push करे।
3. Staging और production environments बनाओ, production के लिए अपनी ही approval ज़रूरी करो, और पिछली image पर rollback की practice करो।
4. Paths filter जोड़ो ताकि आपका smoke eval सिर्फ़ तब चले जब prompts या retrieval code बदलें, और दो pull requests खोलकर दिखाओ कि एक बार चला और एक बार skip हुआ।

**आपका काम पूरा जब:** आप CI से रुका हुआ एक failing PR, production से पहले एक approval gate और आपका किया हुआ एक rollback दिखा सको।
