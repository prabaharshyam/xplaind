## ये क्या है

**Continuous integration (CI)** हर pull request पर checks चलाता है: lint, type checks, unit tests और AI systems के लिए एक छोटा eval। Branch protection की वजह से fail होने वाला change merge हो ही नहीं सकता।

**Continuous delivery (CD)** merge हुए हर change को अपने आप environments से गुज़ारता है: image build करो, staging पर deploy करो, smoke test करो, फिर किसी इंसान के approve करने पर production में promote करो। अगर वो approval step न हो तो उसे **continuous deployment** कहते हैं। Banking, insurance और health के ज़्यादातर client teams approval चाहते हैं।

दोनों करने का एक common तरीका GitHub Actions है। GitLab CI, Azure DevOps और Jenkins यही ideas अलग syntax में use करते हैं; client की अपनी पसंद होगी।

```flow
title: Pull request से production तक
Pull request -> CI: lint, types, tests, smoke eval -> Pass हुआ?
Pass हुआ? -[नहीं]-> Merge block
Pass हुआ? -[हाँ]-> Review करके main में merge
Review करके main में merge -> एक ही image build | tag = commit hash
एक ही image build -> Staging पर deploy -> Staging का smoke test -> नामित reviewer का approval
नामित reviewer का approval -> वही image production में promote -> Healthy है?
Healthy है? -[नहीं]-> आखिरी अच्छा tag redeploy
```

ये lesson Kochi में एक insurer की engineering team को एक claims assistant handover करने की कहानी follow करता है।

## ये कैसे काम करता है

### Workflow के parts

| Part | ये क्या है | इस lesson में |
| --- | --- | --- |
| Workflow | `.github/workflows/` में एक YAML file | `ci-cd.yml` और `rollback.yml` |
| Event | इसे क्या start करता है | एक pull request, main पर push, एक manual run |
| Job | एक fresh machine (runner) पर steps का group | test, smoke-eval, build, deploy-staging, deploy-production |
| Step | एक command, या एक ready-made **action** | `uv run pytest`, `docker/build-push-action` |
| Environment | अपने secrets और rules वाला नाम वाला deploy target | staging, production |

Jobs parallel चलते हैं जब तक एक job दूसरे को `needs` न करे। हर job एक साफ़ machine पर start होता है, इसलिए उसे जो भी चाहिए (code, tools, credentials) वो खुद fetch करना पड़ता है।

### क्या कहाँ चलता है, और कितनी बार

| Check | कब | आम तौर पर समय | Build fail करता है? |
| --- | --- | --- | --- |
| Lint, format, type checks | हर pull request पर | एक मिनट से कम | हाँ |
| Fake model के साथ unit tests | हर pull request पर | 1 से 3 मिनट | हाँ |
| Smoke eval, 50 golden questions | Prompts, retrieval या evals छूने वाले pull requests | 2 से 4 मिनट | हाँ, अगर main से साफ़ नीचे गिरे |
| Staging smoke test | हर staging deploy के बाद | एक मिनट से कम | हाँ, production को block करता है |
| Full eval, सैकड़ों cases | हर रात | 10 से 60 मिनट | Team को alert करता है |

ये समय आम ranges हैं, measurements नहीं। Table के पीछे का rule: check जितना fast और सस्ता, वो उतना पहले चले।

### ऐसा smoke eval जो flake न करे

Model पूरी तरह repeatable नहीं होता, इसलिए छोटा eval उसी code पर pass भी हो सकता है और fail भी। 20 questions हों तो हर question 5 points का होता है: एक answer पलटा तो score 0.85 से 0.80 हो जाता है। जो gate rerun पर पलट जाए, वो लोगों को सिखाता है कि green आने तक "Re-run" दबाते रहो, और फिर असली failures भी ignore होने लगते हैं। चार आदतें इसे ठीक करती हैं:

- **करीब 50 cases use करें।** तब हर case 5 नहीं, 2 points का होता है।
- **Temperature 0 use करें** जहाँ आपका model support करे, और एक fixed retrieval index।
- **Fail हुए case को एक बार retry करें।** असली regression दोनों बार fail होता है; noise आम तौर पर नहीं।
- **Fixed number से नहीं, main से compare करें।** Main का score `evals/baseline.json` में store करें (एक nightly job इसे refresh कर सकता है) और सिर्फ़ तब fail करें जब pull request 2 cases से ज़्यादा खराब हो। साथ में एक hard floor भी रखें, ताकि धीमा drift pass न हो जाए।

नीचे वाला `expected in answer` check एक crude smoke test है: ये उन लंबे answers को reward देता है जिनमें वो phrase इत्तफ़ाक से आ जाए। Nightly full eval को ज़्यादा strict grading use करनी चाहिए। Script अपने exit code से फ़ैसला करती है; कोई भी non-zero exit job को fail कर देता है।

```python
import argparse, json, sys
from app.answer import answer   # your pipeline, called with temperature 0

p = argparse.ArgumentParser()
p.add_argument("--baseline", default="evals/baseline.json")
p.add_argument("--tolerance", type=int, default=2)   # cases, not percent
p.add_argument("--floor", type=float, default=0.80)
args = p.parse_args()

def ok(case):
    return case["expected"].lower() in answer(case["question"]).lower()

cases = [json.loads(line) for line in open("evals/smoke.jsonl")]
correct = sum(ok(c) or ok(c) for c in cases)          # one retry per failed case
base = json.load(open(args.baseline))["correct"]
print(f"smoke: {correct}/{len(cases)} correct, main has {base}")
failed = correct < base - args.tolerance or correct / len(cases) < args.floor
sys.exit(1 if failed else 0)
```

### Secrets, environments और OIDC

**Secrets** repository या environment की settings में रहते हैं, encrypted और logs में masked, repository में कभी नहीं। हर environment को उसके अपने secrets दें, ताकि staging की key कभी production तक न पहुँचे। किसी environment के secrets तब तक locked रहते हैं जब तक required reviewer job को approve न करे।

**Required reviewers.** आप छह लोगों या teams तक के नाम दे सकते हैं; एक approval काफ़ी है। आप deploy start करने वाले इंसान को उसे approve करने से रोक भी सकते हैं। GitHub Free, Pro और Team पर required reviewers सिर्फ़ public repositories में काम करते हैं; private repositories के लिए GitHub Enterprise चाहिए। Approval gate का promise करने से पहले client का plan check करें।

**Forks से आए pull requests को secrets नहीं मिलते** (एक limited `GITHUB_TOKEN` के अलावा)। इसीलिए नीचे वाला smoke eval fork pull requests को skip करता है, जिन्हें फिर कोई maintainer हाथ से evaluate करता है। Workaround के तौर पर `pull_request_target` trigger से बचें: ये आपके secrets के साथ चलता है, इसलिए उसमें किसी fork का code चलाने से कोई अनजान इंसान उन्हें पढ़ सकता है।

**Keys की जगह OIDC.** `id-token: write` हो तो job GitHub से एक signed token माँग सकता है जिसमें repository और environment का नाम हो, जैसे `repo:kochi-insure/claims-assistant:environment:production`। Cloud सिर्फ़ उन्हीं tokens पर भरोसा करता है जो ठीक इसी नाम से match करें, और ऐसे credentials लौटाता है जो expire हो जाते हैं, AWS पर default रूप से एक घंटे बाद। Leak होने के लिए कोई long-lived key है ही नहीं। Azure और Google Cloud में भी यही pattern है।

**Registry.** GitHub की registry (GHCR) में push करने के लिए सिर्फ़ `GITHUB_TOKEN` चाहिए। लेकिन AWS पर चल रही कोई service अगर private GHCR image pull करे, तो उसे एक stored pull credential चाहिए। अगर client AWS पर चलता है, तो उनकी ECR registry में push करना अक्सर आसान है, क्योंकि IAM role पहले से pull access देता है।

### Supply chain: हर action को pin करें

Third-party action आपके code और secrets के access के साथ चलता है। `@v4` जैसा version tag बस एक pointer है, और उसका owner (या कोई attacker) उसे move कर सकता है। March 2025 में attackers ने popular `tj-actions/changed-files` action के tags को ऐसे malicious code पर move कर दिया जो secrets को build logs में print करता था (CVE-2025-30066)। जो workflows पहले के किसी commit SHA पर pinned थे, वो safe code ही चलाते रहे।

इसलिए हर third-party action को उसके full 40-character commit SHA पर pin करें, version एक comment में लिखें, और Dependabot को updates propose करने दें (`.github/dependabot.yml` में `package-ecosystem: "github-actions"` add करें)। Update merge करने से पहले diff पढ़ें। 28 November 2026 को check करते वक्त के दो notes:

- `astral-sh/setup-uv` v7 के बाद moving major tags publish नहीं करता, इसलिए `@v10` resolve नहीं होगा। उसका अपना README एक SHA pin करता है।
- GitHub अब workflow lockfiles (`.github/workflows/actions.lock`, जो `gh actions-lock` से बनती है) document करता है, जो आपके actions के इस्तेमाल किए actions को भी pin करती हैं। इसकी setup guide GitHub Enterprise Cloud के लिए listed है; बाकी plans पर SHA pins use करें।

### Speed, cost और safety switches

- **Caching.** GitHub-hosted runners पर `setup-uv` default रूप से packages cache करता है। दूसरे tools के लिए lock file पर cache करें। Fast CI use होता है; slow CI bypass होता है।
- **Concurrency.** जब कोई उसी pull request पर फिर से push करे, तो पुराना run cancel करें। Main पर चल रहा run कभी cancel न करें: वो किसी deploy के बीच में हो सकता है। हर deploy target को उसका अपना concurrency group दें, ताकि दो deploys कभी overlap न हों।
- **Timeouts.** Job का default timeout 360 मिनट है। हर job पर `timeout-minutes` set करें, ताकि अटकी हुई model call छह घंटे का runner time न जला दे।
- **Path filters job के अंदर।** अगर आप `on.pull_request.paths` से पूरा workflow skip करते हैं, तो उससे आने वाला required check "Pending" ही रहता है और merge को block करता है। इसलिए smoke eval job हमेशा चलता है और उसके steps check करते हैं कि क्या बदला।
- **Least privilege.** ऊपर `permissions: {contents: read}` set करें और सिर्फ़ वही add करें जो किसी job को चाहिए, जैसे `packages: write` या `id-token: write`।

### Branch protection

Main के लिए repository के rules में, merge से पहले test और smoke-eval checks का pass होना और कम से कम एक review require करें। इसके बिना CI बस एक सलाह है।

### पूरा workflow

Action versions 28 November 2026 को check किए गए। छहों Node 24 runtime declare करते हैं।

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]

permissions: {contents: read}

  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: true

  IMAGE: ${{ vars.IMAGE_REPO }}:${{ github.sha }}   # registry names must be lowercase

  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: {contents: read, pull-requests: read}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: dorny/paths-filter@ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d # v4.0.3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - if: steps.changed.outputs.ai == 'true'
        uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --tolerance 2
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: docker/login-action@8aa5831fb8d48d8f76594c7ddde61ae58019f550 # v4.8.0
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@c3c9e263c25d99ce0380d002d59b67737d91b0dc # v7.4.0
        with: {context: ., push: true, tags: "${{ env.IMAGE }}"}

  deploy-staging:
    needs: build
    environment: staging
    concurrency: {group: deploy-staging}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"   # health check plus five real questions

  deploy-production:
    needs: deploy-staging
    environment: production          # required reviewers; its own role and secrets
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"   # same image, no rebuild
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"
```

`vars.DEPLOY_ROLE_ARN` और `vars.BASE_URL` environment variables हैं, इसलिए वही lines एक job में staging की ओर और दूसरे में production की ओर point करती हैं।

### Rollback, और migrations क्यों तय करते हैं कि ये काम करेगा या नहीं

क्योंकि हर image अपने commit से tagged है, rollback मतलब आखिरी अच्छे tag को redeploy करना। इसे एक manual workflow बनाएँ जो वही production environment और approval use करे:

```yaml
name: rollback
on:
  workflow_dispatch:
    inputs:
      sha: {description: "Commit of the last good image", required: true}
permissions: {contents: read, id-token: write}
jobs:
  rollback:
    environment: production
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh "${{ vars.IMAGE_REPO }}:$SHA"
        env: {SHA: "${{ inputs.sha }}"}   # passed as a variable, not pasted into the script
```

App roll back करने से database roll back नहीं होता। अगर release 42 किसी column का नाम बदलता है, तो release 41 की image नए schema पर crash होगी। इसलिए migrations को deploy से पहले अलग step में चलाएँ, और schema को **expand and contract** steps में बदलें: release एक नया column add करता है और दोनों में लिखता है; release दो नया वाला पढ़ता है; release तीन, हफ़्तों बाद, पुराना column drop करता है। हर point पर पिछली image अभी भी काम करती है।

**अपने browser में try करें।** ये checker बिना timeouts वाले jobs और commit SHA पर pin न किए actions ढूँढता है। अपना workflow paste करके चलाइए।

```python
import re, yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: some-org/setup-thing@v2
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes (the default is 360)")
    for step in job.get("steps", []):
        ref = step.get("uses", "")
        if ref and not ref.startswith("./") and not re.fullmatch(r"[0-9a-f]{40}", ref.split("@")[-1]):
            print(f"{name}: pin {ref} to a full commit SHA")
```

## एक worked example

आप claims assistant को Kochi के insurer की engineering team को handover कर रहे हैं। उनकी lead, Anjali, चाहती हैं कि हर change test हो और उनकी team के sign-off के बिना production में कुछ न जाए। Insurer private repositories के साथ GitHub Enterprise Cloud use करता है, इसलिए required reviewers available हैं। आप ऊपर वाले दोनों workflows set up करते हैं। नीचे के numbers बस ये दिखाने के लिए हैं कि gates कैसे behave करते हैं।

**Day 1: set up.** आप staging और production environments बनाते हैं। Production में Anjali और उनके deputy reviewers हैं, self-review blocked है। AWS में आप दो IAM roles बनाते हैं। Production role सिर्फ़ `repo:kochi-insure/claims-assistant:environment:production` पर भरोसा करता है। आप वो पुरानी access key delete करते हैं जो एक contractor `.env` file में छोड़ गया था। आप main का smoke score `evals/baseline.json` में record करते हैं: 50 में से 46।

**Week 2: एक prompt change.** एक teammate tokens बचाने के लिए system prompt छोटा करता है। `prompts/` बदला है, इसलिए smoke eval चलता है। First pass: 50 में से 39। 11 failures में से दो retry पर pass होते हैं, तो score 50 में से 41 (0.82) है। ये main के 46 से 5 cases कम है, tolerance 2 से ज़्यादा, इसलिए check fail होता है और pull request merge नहीं हो सकता। 0.80 का fixed threshold होता तो ये निकल जाता। Teammate policy numbers के बारे में दो sentences वापस डालता है, 45 score करता है, और merge करता है।

**Week 5: एक slow release.** एक नई retrieval setting हर check pass करती है लेकिन production में answers slow कर देती है। Anjali rollback workflow खोलती हैं, पिछला commit hash paste करती हैं और approve करती हैं। आखिरी अच्छी image करीब दो मिनट में वापस आ जाती है, बिना rebuild के। उस release ने बस एक column add किया था, इसलिए पुरानी image database के साथ ठीक चलती है।

**Insurer के लिए क्या बदला।** पहले deploys किसी laptop से होते थे, और किसी को पक्का नहीं पता था कि कौन सा version live है। अब हर production version एक commit hash है जिसके साथ एक नामित approver है। जब कोई claims manager किसी खराब answer की report करता है, तो team ठीक-ठीक बता सकती है कि किस code और prompt ने उसे बनाया।

## आम गलतियाँ

- **सिर्फ़ main पर CI.** Problems merge के बाद पता चलती हैं। CI को pull requests पर चलाइए और required check बनाइए।
- **Fixed threshold के साथ छोटा सा eval.** ये flake करता है, और लोग green आने तक rerun करना सीख जाते हैं। करीब 50 cases, temperature 0, एक retry use करें, और main से compare करें।
- **हर push पर paid evals.** Smoke eval सिर्फ़ तब चलाएँ जब prompts, retrieval या evals बदलें; full suite हर रात चलाएँ।
- **Path filter से पूरा workflow skip करना.** उसके required checks Pending ही रहते हैं। Job के अंदर filter करें।
- **Files में secrets, या long-lived cloud keys को secrets बनाना.** Environment secrets use करें, और cloud access के लिए OIDC।
- **हर environment के लिए rebuild.** एक बार build करें, वही image promote करें।
- **Tag से pinned third-party actions.** Tags move होते हैं। Full SHAs pin करें और Dependabot को updates propose करने दें।
- **पूरे workflow पर cancel-in-progress.** एक नया merge deploy को बीच में मार देता है। सिर्फ़ pull request runs cancel करें।
- **कोई timeouts नहीं.** अटका हुआ job छह घंटे तक चलता है।
- **ऐसा rollback जो किसी ने try नहीं किया, या ऐसा migration जो उसे तोड़ दे.** Rollback practice करें, और expand and contract use करें।
- **Flaky tests को वैसे ही छोड़ देना.** उन्हें जल्दी fix करें या हटाएँ, वरना असली failures भी ignore होने लगते हैं।

## Demo से production तक

आपकी pipeline take over करने से पहले client का engineering lead ये check करेगा:

- **Main protected है**: required checks और कम से कम एक review।
- **Production को approval चाहिए**, उसके अपने secrets हैं और एक role है जो सिर्फ़ उसी environment पर भरोसा करता है।
- **कोई long-lived cloud keys नहीं** GitHub में कहीं भी।
- **हर action pinned है** commit SHA पर, Dependabot on के साथ।
- **AI gate stable है**, एक baseline और एक nightly full eval के साथ।
- **Rollback लिखा हुआ है और चलाया जा चुका है**, और migrations expand and contract follow करते हैं।

## Practice

GitHub का Actions quickstart और deployment environments वाला page follow करें। एक public repository use करें, ताकि free account पर required reviewers काम करें।

1. एक workflow add करें जो हर pull request पर lint और tests चलाए, और उसे main पर required check बनाएँ।
2. हर action को commit SHA पर pin करें और `github-actions` के लिए एक Dependabot file add करें।
3. एक job add करें जो main पर merge होने पर आपकी Docker image को commit hash से tag करके build और push करे।
4. Staging और production environments बनाएँ, production के लिए खुद को required reviewer के तौर पर add करें, और वही image दोनों पर deploy करें।
5. In-job path filter के साथ smoke eval add करें। दो pull requests खोलकर दिखाएँ कि ये एक बार चलता है और एक बार skip होता है।
6. पिछली image redeploy करने के लिए rollback workflow चलाएँ।

**आपका काम पूरा है जब आप** CI से block हुआ एक failing pull request, production से पहले एक approval gate, और खुद किया हुआ एक rollback दिखा सकें।
