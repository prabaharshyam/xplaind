## यह क्या है

तीन आदतें जो किसी deployment को operate करने के लिए safe बनाती हैं:

- **अलग environments.** Build करने के लिए development, production जैसी settings के साथ test करने के लिए staging, असली users के लिए production। हर एक का अपना database, keys और settings होते हैं।
- **Secrets management.** Passwords, API keys और tokens एक secret store में रहते हैं, run time पर app तक पहुँचते हैं और कभी code, images, logs, chat या Terraform state में नहीं दिखते।
- **Infrastructure as code (IaC).** Servers, databases, networks और permissions को console में click करके जोड़ने की बजाय files में describe किया जाता है, code की तरह review किया जाता है और Terraform जैसे tool से apply किया जाता है।

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | अपना database, अपनी model key, 1 instance
Apply -> Staging | masked data, अपनी model key, 1 instance
Apply -> Production | असली data, spend limit वाली अपनी model key, 3 instances
वही container image -> Development
वही container image -> Staging
वही container image -> Production
```

हर environment अपनी settings environment variables से और अपने secrets vault से लेता है। सिर्फ़ values अलग होती हैं; code और image एक ही हैं। यही असली बात है: अगर staging pass होता है, तो production भी होना चाहिए।

यह lesson Chandigarh की एक lending company को follow करता है जो जल्दबाज़ी में बने एक pilot को Azure पर production के लिए तैयार कर रही है। ये ideas AWS और Google Cloud पर भी लागू होते हैं, बस resource names अलग होते हैं।

## यह कैसे काम करता है

### Config environment में

वही image हर जगह चलता है; सिर्फ़ settings अलग होती हैं। उन्हें environment variables (`DATABASE_HOST`, `MODEL_NAME`, `LOG_LEVEL`) से read करो और start-up पर एक settings model से validate करो। तब कोई missing value boot पर, deploy के दौरान ही ज़ोर से fail होती है, रात 2 बजे पहली असली request पर नहीं।

### Environments के बीच क्या अलग होता है

| Value | उदाहरण | कहाँ रहती है |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, हर environment के लिए अलग set |
| Secret | Model API key, webhook signing key | Secret store, app की identity से read |
| Database access | Production database | Managed identity sign-in, इसलिए कोई password होता ही नहीं |
| Infrastructure | Database size, network rules | Git में Terraform files |
| Infrastructure state | Terraform कौन-से resources manage करता है | Remote, locked storage, हर environment की एक state |
| Test data | Masked customer records | सिर्फ़ staging database |

Production को ज़्यादा instances भी मिलते हैं, provider पर monthly spend limit के साथ अपनी model key, और उसे छू सकने वाले लोग कहीं कम होते हैं।

### Secret stores और rotation

Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) या HashiCorp Vault जैसे tools secrets रखते हैं, control करते हैं कि हर एक को कौन read कर सकता है और हर read को log कर सकते हैं। Azure पर reads तभी log होते हैं जब आप vault की diagnostic settings on करते हो, इसलिए यह पहले दिन ही करो; auditor ज़रूर पूछेगा।

App अपनी **managed identity** से secrets read करता है: यह एक identity है जो Azure चलते हुए app को देता है, इसलिए vault तक पहुँचने के लिए app को किसी password की ज़रूरत नहीं होती। Secrets को एक schedule पर rotate करो, और जब कोई छोड़कर जाए या leak का शक हो तो तुरंत।

Rotation में एक catch है। जो app secret को सिर्फ़ start-up पर read करता है, वह restart होने तक पुरानी value ही रखता है। तीन patterns में से एक चुनो: हर rotation के बाद app restart करो, timer पर secrets reload करो, या कोई call authentication error के साथ fail हो तो एक बार reload करो। कुछ platforms, जिनमें Azure Container Apps भी है, आपके लिए vault secret के latest version को follow कर सकते हैं; वह app को कब restart करता है, यह जानने के लिए अपने platform के docs पढ़ो। CI में एक secret scanner चलाओ ताकि keys repository तक कभी पहुँचें ही नहीं।

### Terraform: code, plan, apply, state

आप HCL में files लिखते हो, जो Terraform की configuration language है, और उनमें वे resources describe करते हो जो आपको चाहिए। Region और environment variables हैं, इसलिए वही files कोई भी environment कहीं भी build कर देती हैं:

```hcl
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "location" {
  type    = string
  default = "centralindia"
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = var.location
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false

  authentication {
    active_directory_auth_enabled = true
    password_auth_enabled         = false
    tenant_id                     = data.azurerm_client_config.current.tenant_id
  }
}
```

`authentication` block passwords बंद कर देता है: app अपनी managed identity से Postgres में sign in करता है, इसलिए leak या rotate करने के लिए कोई database password होता ही नहीं।

`terraform plan` तीन चीज़ें compare करता है: आपका code, **state** file (Terraform जिन resources को manage करता है उनका उसका record), और असली cloud। फिर वह list करता है कि वह क्या create, change या destroy करेगा। `terraform apply` वे changes करता है और state update करता है।

### Remote state, हर environment की एक

हर project एक backend से शुरू होता है, ताकि state share हो, apply के दौरान lock रहे और laptops से दूर रहे:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 5.15" }
  }
}
```

इस lesson का code Terraform 1.17.2 और azurerm provider 5.15.0 पर `terraform validate` से check किया गया था (November 2026)। जिन versions को आपने test किया है उन्हें pin करो। Provider upgrades arguments के नाम बदल देते हैं। azurerm 5.x में Key Vault argument `enable_rbac_authorization` हट गया है और `rbac_authorization_enabled` required है, इसलिए पुराना copy किया हुआ code validate नहीं होता।

Environments को कैसे बाँटें? यह rule use करो:

- **हर environment की एक state, उसकी अपनी key के साथ और production के लिए उसके अपने access के साथ।** तब staging की कोई गलती production को छू नहीं सकती।
- **Shared code एक module में।** Module Terraform का एक folder है जिसे हर environment अपनी values के साथ call करता है, ताकि staging और production एक ही shape के रहें।
- **CLI workspaces** एक ही backend में, उन्हीं credentials के साथ, कई states रखते हैं। HashiCorp के docs कहते हैं कि जब environments को अलग credentials या access controls चाहिए तब ये suitable नहीं हैं। इन्हें कम समय वाली copies के लिए use करो, जैसे हर feature branch के लिए एक, production को अलग करने के लिए नहीं।

### Secrets को code और state से बाहर रखना

State हर resource का हर attribute plain text में store करती है, Terraform से generate किया गया कोई भी password भी। किसी value को `sensitive` mark करने से वह सिर्फ़ screen से छिपती है; वह state में फिर भी रहती है। तीन बचाव, सबसे अच्छा पहले:

1. **कोई secret ही नहीं।** Managed identity sign-in, जैसा ऊपर database पर है।
2. **Write-only arguments** (Terraform 1.11 और बाद के)। Provider को value मिलती है लेकिन Terraform उसे कभी store नहीं करता। उदाहरण के लिए, azurerm में Postgres server पर `administrator_password_wo` और Key Vault secrets पर `value_wo` है, हर एक के साथ एक `_wo_version` number जिसे rotate करने के लिए आप बढ़ाते हो। Terraform 1.10 ने **ephemeral resources** जोड़े, जो एक run के लिए vault से secret read करते हैं बिना उसे save किए।
3. **Value को Terraform के बाहर डालो।** Terraform vault और permissions बनाता है; कोई व्यक्ति या pipeline secret value जोड़ता है।

```hcl
resource "azurerm_key_vault" "kv" {
  name                       = "claims-${var.env}-kv"
  location                   = var.location
  resource_group_name        = azurerm_resource_group.main.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = var.env == "prod"
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

यह role assignment app को secret values read करने देता है और कुछ नहीं: वह उन्हें change या delete नहीं कर सकता।

### Code में validated settings

`pydantic-settings` environment variables read करता है और जल्दी fail होता है:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_host: str
    model_api_key: SecretStr
    model_name: str                  # required: no default, so a missing value stops start-up
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()    # raises one clear error listing every missing or invalid value
```

`model_name` का जानबूझकर कोई default नहीं है। Default model name ठीक उसी bug को छिपा देता है जिसे आप पकड़ना चाहते हो, और model names अक्सर बदलते हैं। `SecretStr` secrets को logs और error messages से बाहर रखता है: उसे print करने पर `**********` दिखता है। `.env` file सिर्फ़ development के लिए है और `.gitignore` में होनी चाहिए।

### कौन apply कर सकता है: review loop

Infrastructure का कोई भी change एक pull request से शुरू होता है जो Terraform files edit करता है:

1. CI `terraform fmt -check`, `terraform validate` और `tflint` और Checkov जैसे scanners चलाता है, जो public storage, खुले firewall rules और missing encryption को flag करते हैं।
2. CI `terraform plan -out=plan.bin` चलाता है और एक summary post करता है, जैसे "1 to add, 0 to change, 0 to destroy"।
3. Reviewer सिर्फ़ code नहीं, plan पढ़ता है, क्योंकि एक line का edit Terraform को database destroy करके दोबारा बनाने पर मजबूर कर सकता है।
4. Approval के बाद, एक pipeline ठीक वही saved plan apply करती है। Production के लिए एक required approval step जोड़ो (जैसे एक protected GitHub environment) और, अगर सख़्त rules चाहिए, तो Open Policy Agent जैसा एक policy check।

Pipeline **OpenID Connect (OIDC)** से Azure में sign in करती है: GitHub Actions एक कम समय वाले token से साबित करता है कि वह कौन है, इसलिए CI settings में कोई लंबे समय वाला cloud password नहीं रहता। Staging pipeline को सिर्फ़ staging पर rights दो, और production pipeline को सिर्फ़ production पर। तब किसी को production पर routine console access की ज़रूरत नहीं पड़ती, और कोई laptop से apply नहीं चलाता।

### Drift: plan क्या देख सकता है और क्या नहीं

Incident के दौरान लोग अब भी console में चीज़ें बदलते हैं। एक nightly job production को code से compare करता है:

```bash
terraform plan -var-file=env/prod.tfvars -input=false -lock=false -detailed-exitcode > plan.txt
case $? in
  0) echo "no changes" ;;
  2) echo "DIFFERENCE: production does not match the code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

Exit code 2 को ध्यान से पढ़ो। इसका मतलब है "plan को एक difference मिला"। वह या तो drift है (किसी ने किसी managed resource को हाथ से बदला) या ऐसा code जो merge हुआ लेकिन कभी apply नहीं हुआ। Plan का text बताता है कि कौन-सा। सिर्फ़ drift देखने के लिए `-refresh-only` जोड़ो।

बड़ा blind spot: plan सिर्फ़ उन resources को check करता है जो पहले से state में हैं। हाथ से एक अलग resource के रूप में बनाया गया firewall rule दिखता ही नहीं; job green ही रहता है। उन्हें cloud activity-log alerts या policies से पकड़ो, फिर resource delete करो या import block से उसे Terraform के अंदर लाओ:

```hcl
import {
  to = azurerm_postgresql_flexible_server_firewall_rule.partner
  id = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/claims-prod-rg/providers/Microsoft.DBforPostgreSQL/flexibleServers/claims-prod-db/firewallRules/partner"
}

resource "azurerm_postgresql_flexible_server_firewall_rule" "partner" {
  name             = "partner"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "203.0.113.10"
  end_ip_address   = "203.0.113.10"
}
```

अगला plan "1 to import" दिखाता है। `terraform plan -generate-config-out=generated.tf` आपके लिए resource block draft कर सकता है; वह flag अभी भी experimental marked है, इसलिए जो वह लिखे उसे review करो।

### अपने browser में try करो

Start-up पर check की गई settings जल्दी और साफ़ fail होती हैं। Dictionary से `model_name` delete करो और फिर से run करो।

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    model_name: str
    model_api_key: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "model_name": "example-model", "model_api_key": "sk-test-123", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.model_name, s.daily_budget_inr, s.model_api_key)   # the key prints as stars
except ValidationError as err:
    print("start-up stopped, missing or invalid:", [e["loc"][0] for e in err.errors()])
```

## एक worked example

Chandigarh की lending company का pilot जल्दबाज़ी में बना था। उसमें testing और असली data के लिए एक ही database था, model key महीनों पहले commit हुई एक `.env` file में थी, और कुछ resources portal में हाथ से बनाए गए थे।

Production से पहले, आप:

1. Leaked key को revoke और rotate करते हो और CI में एक secret scanner जोड़ते हो। उसे history में दो और पुरानी keys मिलती हैं; दोनों rotate की जाती हैं।
2. Network, database, storage, container app और Key Vault के लिए Terraform लिखते हो, `env` और `location` को variables रखकर। हाथ से बने जो resources रहने चाहिए उन्हें import करते हो, बाकी delete करते हो, और confirm करते हो कि plan में कोई surprise नहीं है।
3. हर secret को Key Vault में ले जाते हो, और database को managed identity sign-in पर switch करते हो ताकि कोई password हो ही नहीं। Staging और production की अलग-अलग model keys हैं, अलग-अलग monthly limits के साथ।
4. Staging में पिछले महीने की applications की masked copies load करते हो: names, PAN और phone numbers बदल दिए गए।
5. सिर्फ़ CI से apply करते हो: एक staging pipeline और एक production pipeline, हर एक की अपनी OIDC identity, और production से पहले एक required approval।

जब client का auditor पूछता है "production model key कौन read कर सकता है?", तो आप vault पर role assignments और उसका access log दिखाते हो। एक region drill में team `location = "southindia"` और एक नई state key pass करके South India में दूसरा staging build करती है। एक gotcha सामने आया: Key Vault और Postgres server के names पूरे Azure में unique होने चाहिए, इसलिए copy के names में एक region suffix चाहिए। इस example में rebuild में एक घंटे से कम लगा; आपके case में यह data size पर depend करता है।

| Auditor का सवाल | पहले का जवाब | बाद का जवाब |
| --- | --- | --- |
| Secrets कहाँ stored हैं? | "एक .env file में" | Key Vault, access log के साथ |
| क्या कोई database password है? | हाँ, उसी file में | नहीं, app अपनी identity से sign in करता है |
| Production कौन बदल सकता है? | कई लोग, portal के ज़रिए | Production pipeline, approved plan के बाद |
| Manual change का पता कैसे चलेगा? | नहीं चलेगा | Nightly drift check और activity-log alerts |
| क्या test data असली है? | हाँ | नहीं, masked copies |

## आम गलतियाँ

- **Production data पर testing.** एक खराब script और असली customers पर असर पड़ता है। अलग करो, और test data को mask करो।
- **Git में secrets, थोड़ी देर के लिए भी.** History उन्हें रखती है। जो भी key कभी commit हुई हो उसे rotate करो।
- **यह मानना कि `sensitive = true` secret को state से बाहर रखता है.** यह उसे सिर्फ़ screen से छिपाता है। Managed identity या write-only arguments use करो।
- **Laptop पर Terraform state.** वह खो जाती है या पुरानी हो जाती है, और उसमें secrets हो सकते हैं। Remote, locked state use करो।
- **Staging और production के लिए एक state, या CLI workspaces.** तब staging का कोई change production तक पहुँच सकता है, उन्हीं credentials के साथ। अलग states और access use करो।
- **Console changes जिन्हें कोई record नहीं करता.** बदले हुए attributes drift के रूप में दिखते हैं; हाथ से बने नए resources बिल्कुल नहीं दिखते। Activity log पर alert लगाओ और import या delete करो।
- **Laptops से apply चलाना.** किसी को नहीं पता कि कौन-सा code apply हुआ। Reviewed plan को सिर्फ़ CI से apply करो।
- **हर environment का अलग shape.** अगर staging में वह private network नहीं है जो production में है, तो staging tests बहुत कम साबित करते हैं।
- **Versions pin किए बिना पुराना provider code copy करना.** Major versions के बीच arguments के नाम बदल जाते हैं; pin करो और सोच-समझकर upgrade करो।

## जब Terraform आपकी ज़रूरत से ज़्यादा है

- **एक छोटी single service** ऐसे platform पर जो आपके लिए infrastructure manage करता है।
- **कम समय का prototype** जिसे आप अगले महीने delete करने वाले हो।
- **ऐसा client जिसकी अपनी infrastructure team और tool है** (जैसे Bicep, CloudFormation या Pulumi): उन्हीं का use करो।

Licence fit भी check करो। Version 1.6 से आगे Terraform Business Source License के तहत है, अब IBM licensor है। इसे अपना या किसी client का infrastructure चलाने के लिए use करना allowed है, लेकिन इस पर एक competing hosted product बनाना allowed नहीं है। OpenTofu, Mozilla Public License 2.0 के तहत एक open-source fork है, जिसे Linux Foundation चलाती है और जो 2025 से एक CNCF project है, और वही HCL read करता है। कुछ clients इसी वजह से इसे पसंद करते हैं।

Environment variables, validated settings और एक secret store सबसे छोटे project में भी रखने लायक हैं।

## Demo से production तक

- **Remote, locked state रखो** हर environment के लिए, access restricted करके।
- **Pull requests में plan करो** और सिर्फ़ reviewed plan को CI से apply करो, OIDC से sign in करके।
- **Approval ज़रूरी करो** किसी भी production apply से पहले।
- **Nightly drift checks चलाओ** production पर, साथ में Terraform के बाहर बने resources के लिए alerts।
- **Terraform को scan करो** CI में risky settings के लिए।
- **Secrets को state से बाहर रखो** managed identity और write-only arguments से।
- **Start-up पर settings validate करो**, secrets को `SecretStr` रखकर और app की identity से read करके।

## Practice

अपने चुने हुए cloud के लिए Terraform के getting-started tutorials follow करो और config पर Twelve-Factor का page पढ़ो।

1. ऐसा Terraform लिखो जो `env = "staging"` के लिए एक storage bucket और एक छोटा managed database बनाए, और database publicly reachable न हो। उसे apply करो, plan पढ़ो, फिर destroy करो।
2. अपने app की settings को environment variables से read होने वाले एक validated settings model में ले जाओ, model name का कोई default न हो, और कोई value missing हो तो start-up साफ़ तौर पर fail हो।
3. अपने cloud के secret manager में एक secret store करो और app को उसे अपनी identity से read करवाओ। फिर उसे rotate करो और confirm करो कि app नई value उठा लेता है।
4. Console में, Terraform के manage किए किसी resource की एक setting बदलो और drift check चलाओ: उसे 2 के साथ exit करना चाहिए। वह change undo करो, फिर हाथ से एक नया firewall rule बनाओ और फिर से चलाओ: वह 0 के साथ exit करता है। Import block से उस rule को import करो।

**आपका काम पूरा है जब आप** अपना staging environment code से दोबारा build कर सको, दिखा सको कि आपकी repository या state में कोई secret नहीं है, और समझा सको कि आपका drift check क्या नहीं देख सकता।
