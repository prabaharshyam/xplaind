## ये क्या है

तीन आदतें जो deployment को चलाने के लिए सुरक्षित बनाती हैं:

- **अलग environments।** Development बनाने के लिए, staging production जैसी settings के साथ testing के लिए, production असली users के लिए। हर एक का अपना database, keys और settings होती हैं।
- **Secrets management।** Passwords, API keys और tokens एक secret store में रहते हैं, run time पर app तक पहुँचते हैं, और code, images, logs या chat में कभी नहीं दिखते।
- **Infrastructure as code (IaC)।** Servers, databases, networks और permissions files में लिखे जाते हैं, code की तरह review होते हैं और Terraform जैसे tool से apply होते हैं। Console में click करके जोड़-तोड़ नहीं होती।

```flow
Reviewed Terraform files -> Plan -> Apply
Apply -> Development | अपना database, अपनी model key, 1 instance
Apply -> Staging | masked data, अपनी model key, 1 instance
Apply -> Production | असली data, spend limit वाली अपनी model key, 3 instances
वही container image -> Development
वही container image -> Staging
वही container image -> Production
```

हर environment अपनी settings environment से और अपने secrets vault से लेता है।

इस lesson में हम Chandigarh की एक lending company को देखेंगे, जो जल्दबाज़ी में बने pilot को production के लिए तैयार कर रही है।

## ये काम कैसे करता है

**Config environment में।** वही image हर जगह चलती है; सिर्फ़ settings अलग होती हैं। उन्हें environment variables (`DATABASE_URL`, `MODEL_NAME`, `LOG_LEVEL`) से पढ़ो और start-up पर settings model से validate करो। फिर कोई value गायब हो तो boot पर ही साफ़ error आता है, रात 2 बजे पहली असली request पर नहीं।

**Environments में क्या अलग होता है।** अलग databases (staging को कभी production data पर मत लगाओ, जब तक वो masked न हो), अपनी spend limits वाली अलग model API keys, production के बाहर कम instances, और production तक सख़्त access।

**Secret stores।** Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) या HashiCorp Vault जैसे tools secrets रखते हैं, तय करते हैं कि हर एक को कौन पढ़ सकता है, और हर access का log रखते हैं। App उन्हें start-up पर अपनी service identity से पढ़ता है। Secrets को schedule पर rotate करो, और जब कोई company छोड़े या leak का शक हो तो तुरंत। CI में secret scanner चलाओ ताकि keys repository तक पहुँचने से पहले पकड़ी जाएँ।

**Terraform।** आप HCL में files लिखते हो जो resources describe करती हैं:

```hcl
resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = "centralindia"
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false
}
```

`terraform plan` ठीक-ठीक दिखाता है कि क्या बदलेगा; reviewer pull request में plan पढ़ता है; `terraform apply` उसे कर देता है। Terraform जो कुछ manage करता है उसे एक **state** file में record करता है। ये file remote में रखनी होती है (locking वाला storage bucket), laptop पर कभी नहीं, और इसे protect करना होता है क्योंकि इसमें sensitive values हो सकती हैं। हर environment के लिए एक variable वाली एक ही files का set staging और production को एक जैसी shape में रखता है।

**हर तरह की value कहाँ रहती है:**

| Value | Example | कहाँ रहती है |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, हर environment में अलग set |
| Secret | Database password, model API key | Secret store, app की identity से पढ़ी जाती है |
| Infrastructure | Database का size, network rules | Git में Terraform files |
| Infrastructure state | Terraform कौन-से resources manage करता है | Remote, locked, access-controlled storage |
| Test data | Masked customer records | सिर्फ़ staging database |

**Review का चक्र।** Infrastructure का कोई भी बदलाव एक pull request से शुरू होता है जो Terraform files edit करता है। CI `terraform plan` चलाता है और output post करता है, जैसे "1 to add, 0 to change, 0 to destroy"। Reviewer सिर्फ़ code नहीं, plan पढ़ता है, क्योंकि plan दिखाता है कि असल में क्या होगा। Approval के बाद अपनी identity वाली pipeline `terraform apply` चलाती है। रोज़ के बदलावों के लिए किसी को production का console access नहीं चाहिए, तो वहाँ गलती कर सकने वाले लोग कम हो जाते हैं।

**Code में validated settings।** `pydantic-settings` environment variables पढ़ता है और जल्दी fail हो जाता है:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_url: SecretStr
    model_api_key: SecretStr
    model_name: str = "claude-sonnet-5-5"            # check the docs for current names
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()        # raises a clear error listing every missing or invalid value
```

`SecretStr` secrets को logs और error messages से बाहर रखता है: उसे print करो तो `**********` दिखता है।

**Locking के साथ remote state।** हर Terraform project की शुरुआत एक backend से होती है, ताकि state shared रहे और दो लोग एक साथ apply न कर सकें:

```hcl
terraform {
  required_version = ">= 1.6"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}
```

हर environment के लिए एक अलग state file रखो (अलग `key`), और अलग variable files जैसे `env/staging.tfvars` और `env/prod.tfvars`।

**Secrets को Terraform में store किए बिना।** Terraform से vault बनवाओ और app की identity को access दिलवाओ; secret values vault के ज़रिए ही डालो, ताकि वो code या state में कभी न दिखें:

```hcl
resource "azurerm_key_vault" "kv" {
  name                      = "claims-${var.env}-kv"
  location                  = "centralindia"
  resource_group_name       = azurerm_resource_group.main.name
  tenant_id                 = data.azurerm_client_config.current.tenant_id
  sku_name                  = "standard"
  enable_rbac_authorization = true
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

**Drift को schedule पर पकड़ो।** कभी-कभी लोग console में चीज़ें बदल देते हैं। रात की एक job उसे पकड़ लेती है:

```bash
terraform plan -var-file=env/prod.tfvars -detailed-exitcode -lock=false > plan.txt
case $? in
  0) echo "no drift" ;;
  2) echo "DRIFT: production differs from code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

**Code को scan करो।** `tflint` और Checkov जैसे tools pull requests में public storage, खुले firewall rules और missing encryption को flag कर देते हैं, कुछ भी apply होने से पहले।

**Browser में try करो।** Start-up पर check की गई settings जल्दी और साफ़ तरीके से fail होती हैं। कोई value हटाओ और चलाकर देखो।

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    database_url: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "database_url": "postgresql://app:secret@db/app", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.daily_budget_inr, s.database_url)     # the secret prints as stars
except ValidationError as err:
    print("start-up stopped:", [e["loc"][0] for e in err.errors()])
```

## एक example से समझो

Chandigarh की एक lending company का pilot जल्दबाज़ी में बना था। उसमें testing और असली data के लिए एक ही database था, model key एक `.env` file में थी जो महीनों पहले commit हो चुकी थी, और resources console में हाथ से बनाए गए थे।

Production से पहले आप ये करते हो:

1. Leak हुई key rotate करो और CI में secret scanner जोड़ो। वो history में दो और पुरानी keys ढूँढ लेता है; दोनों rotate होती हैं।
2. Network, database, storage, container app और Key Vault के लिए Terraform लिखो, `env` को variable बनाकर। `terraform apply` से साफ़ staging बनता है; reviewed plan से production।
3. हर secret Key Vault में डालो; app उन्हें अपनी managed identity से पढ़ता है। Staging और production की model keys अलग हैं, और हर एक की monthly limit अलग।
4. Staging में पिछले महीने की applications की masked copies load करो: नाम, PAN और phone numbers बदले हुए।

जब client का auditor पूछता है "production database का password कौन पढ़ सकता है?", तो आप Key Vault की access policy और उसका access log दिखाकर जवाब देते हो। जब region outage का drill होता है, team उसी Terraform से staging को दूसरे region में 40 मिनट में दोबारा बना लेती है।

| Auditor का सवाल | पहले का जवाब | बाद का जवाब |
| --- | --- | --- |
| Secrets कहाँ store हैं? | ".env file में" | Key Vault में, access log के साथ |
| Production कौन बदल सकता है? | कई लोग, console से | Deployment pipeline, review के बाद |
| क्या system दोबारा बना सकते हो? | साफ़ नहीं | हाँ, Terraform से, 40 मिनट में |
| क्या test data असली है? | हाँ | नहीं, masked copies |

## आम गलतियाँ

- **Production data पर testing।** एक गलत script और असली customers पर असर पड़ता है। Environments अलग रखो, और test data mask करो।
- **Secrets Git में, थोड़ी देर के लिए भी।** History उन्हें रख लेती है। जो भी key कभी commit हुई, उसे rotate करो।
- **Terraform state laptop पर।** वो खो जाती है या पुरानी पड़ जाती है, और उसमें secrets हो सकते हैं। Remote, locked state use करो।
- **Terraform के साथ-साथ console में बदलाव।** अगला apply उन्हें पलट देता है या उनसे टकराता है। Code बदलो।
- **हर environment की अलग shape।** अगर staging में वो private network नहीं है जो production में है, तो staging के tests बहुत कम साबित करते हैं।
- **Secret values Terraform files में लिखना**, जहाँ से वो state में भी पहुँच जाती हैं।
- **सारे environments के लिए एक state file**, जिससे staging का बदलाव production को छू सकता है।
- **Console के बदलाव जिन्हें कोई record नहीं करता**, महीनों बाद drift के रूप में मिलते हैं।

## कब Terraform ज़रूरत से ज़्यादा है

- **एक छोटी single service**, ऐसे platform पर जो infrastructure खुद संभालता है।
- **कम समय का prototype** जिसे आप अगले महीने delete कर दोगे।
- **ऐसा client जिसकी अपनी infrastructure team और tool है** (जैसे Bicep, CloudFormation या Pulumi): उनका ही use करो।

Environment variables, validated settings और secret store सबसे छोटे project में भी रखने लायक हैं।

## Demo से production तक

- **हर environment के लिए remote, locked state रखो**, restricted access के साथ।
- **Pull requests में plan करो** और review के बाद ही CI से apply करो।
- **Production पर रात को drift checks चलाओ।**
- **CI में Terraform को scan करो**, risky settings के लिए।
- **Start-up पर settings validate करो**, secrets `SecretStr` में, और app की identity से पढ़े हुए।

## Practice करो

अपने चुने cloud के लिए Terraform के getting-started tutorials follow करो और config पर Twelve-Factor page पढ़ो।

1. `env = "staging"` के लिए Terraform लिखो जो एक storage bucket और छोटा managed database बनाए, database public से पहुँच में न हो। Apply करो, plan पढ़ो, फिर destroy कर दो।
2. अपने app की settings को environment variables से पढ़ने वाले validated settings model में ले जाओ, और कोई setting गायब होने पर start-up साफ़ तरीके से fail करवाओ।
3. अपने cloud के secret manager में एक secret रखो और app से उसे अपनी identity के ज़रिए पढ़वाओ।
4. Cloud console में हाथ से एक setting बदलो, फिर drift check चलाओ और confirm करो कि वो फ़र्क report करता है।

**आपका काम पूरा जब** आप अपना staging environment code से दोबारा बना सको और दिखा सको कि आपकी repository में कहीं कोई secret नहीं है।
