## ये क्या है

MCP से पहले हर AI app को हर system के लिए अपना code चाहिए होता था। तीन assistants और चार systems मतलब बारह integrations। **Model Context Protocol** (MCP) एक open standard है जो इसे ठीक करता है। आप हर system को एक बार **MCP server** की तरह लपेटते हो, और हर AI app में एक **MCP client** होता है जो किसी भी server से बात कर सकता है: तीन गुणा चार की जगह तीन जमा चार हिस्से।

Anthropic ने MCP 25 November 2024 को release किया। December 2025 में उसने MCP को Agentic AI Foundation को दे दिया, जो Linux Foundation के तहत एक directed fund है जिसे Anthropic, Block और OpenAI ने मिलकर शुरू किया, और जहाँ इसके maintainers इसे खुले में develop करते हैं। Versions के नाम तारीख से होते हैं। अभी वाला **2026-07-28** है, पाँचवाँ release; उससे पहले वाला 2025-11-25 था। हमेशा check करो कि कोई tutorial किस version के लिए लिखा है।

एक server तीन तरह की चीज़ें दे सकता है। सबसे ज़रूरी बात ये है कि हर एक को use करने का फ़ैसला कौन करता है:

| Feature | ये क्या है | Use करने का फ़ैसला कौन करता है | मिसाल | Messages |
| --- | --- | --- | --- | --- |
| Tools | JSON schema वाले functions | Model, task के दौरान | `search_tickets(query, status)` | `tools/list`, `tools/call` |
| Resources | URI से पहचाना जाने वाला data | App या user उसे जोड़ता है | `ticket://T-1042` | `resources/list`, `resources/read` |
| Prompts | दोबारा काम आने वाले prompt templates | User menu से एक चुनता है | "इस ticket thread का summary बनाओ" | `prompts/list`, `prompts/get` |

## ये काम कैसे करता है

### Host, client और server

**Host** वो AI app है जिसमें user काम करता है। उसके अंदर एक **client** एक **server** से connection रखता है, तो तीन servers वाले host में तीन clients होते हैं। Client अपने server के tools की list model को देता है। जब model कोई tool माँगता है, तो client वो call उस server को भेजता है और result लौटा देता है। Model कभी server से सीधे बात नहीं करता, इसलिए control host के हाथ में रहता है।

```flow
dir: LR
title: हर system के लिए एक server, जिसे हर host share करता है
IDE assistant | हर server के लिए एक client वाला host -> Maintenance-log server | find_machine, get_maintenance_history, log_observation
Chat assistant | हर server के लिए एक client वाला host -> Maintenance-log server
Chat assistant -> Spare-parts server
```

### Wire पर चलने वाले messages

MCP messages JSON-RPC 2.0 होते हैं: request में एक `id`, एक `method` और `params` होते हैं, और reply में वही `id` आता है। 2026-07-28 से protocol **stateless** है। पुराने versions एक `initialize` handshake से शुरू होते थे और एक session रखते थे। अब हर request protocol version और client capabilities `_meta` में साथ लाती है, और उसे client का नाम और version भी साथ लाना चाहिए। Client चाहे तो पहले `server/discover` call कर सकता है, पर ज़रूरी नहीं। जिन clients ने upgrade नहीं किया, उनके लिए official Python SDK उसी server से अभी भी पुराना handshake serve करता है।

Failures दो तरह के होते हैं:

- **Tool error** एक normal result है जिसमें `isError: true` होता है। Model उसे पढ़कर दोबारा try कर सकता है, इसलिए बताओ कि क्या गलत हुआ और उसकी जगह क्या करना है।
- **Protocol error** एक JSON-RPC `error` है जिसमें एक code होता है, जैसे किसी malformed request के लिए। इसे client संभालता है; model इसे आमतौर पर देखता ही नहीं।

**अपने browser में try करो।** ये worked example वाले server से record की गई एक request और दो replies हैं, जगह के लिए छोटी की गईं। Code एक reply को उस रूप में बदलता है जो model देखता है।

```python
import json

request = {"jsonrpc": "2.0", "id": 7, "method": "tools/call",
           "params": {"name": "get_maintenance_history", "arguments": {"tag": "CNC-14", "limit": 1},
                      "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}

ok = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": False,
      "content": [{"type": "text", "text": "{\"date\": \"2026-11-18\", \"note\": \"Vibration at high RPM\"}"}]}}
refused = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": True,
      "content": [{"type": "text", "text": "Error executing tool get_maintenance_history: No machine 'CNC-14' in your plant."}]}}

def for_the_model(reply):
    assert reply["id"] == request["id"], "a reply must match its request id"
    if "error" in reply:  # protocol error: the host deals with it
        raise RuntimeError(reply["error"]["message"])
    text = "\n".join(c["text"] for c in reply["result"]["content"] if c["type"] == "text")
    return {"tool_result": text, "is_error": reply["result"]["isError"]}

print(json.dumps(for_the_model(ok)))
print(json.dumps(for_the_model(refused)))
```

### Transports: local और remote

| पहलू | stdio (local) | Streamable HTTP (remote) |
| --- | --- | --- |
| कैसे चलता है | Host server को child process की तरह चालू करता है और standard input और output से बात करता है | Server एक URL पर चलने वाली web service है, जैसे `https://mcp.example.in/maintenance` |
| किसके लिए अच्छा | Files, local databases, developer tools | Shared company systems, जिन्हें एक जगह update और log किया जाता है |
| User कौन है | जो भी उस machine पर host चला रहा है | जिसने sign-in किया: हर request पर एक OAuth token |

**Streamable HTTP** में client हर message उसी एक URL पर POST करता है, और server JSON से जवाब देता है, या पहले progress भेजना हो तो events की एक stream से। 2026-07-28 में हर request में body से copy किया हुआ एक `Mcp-Method` header होता है, और tool, resource और prompt requests में `Mcp-Name` भी होता है, ताकि gateway body parse किए बिना requests route कर सके; जिस request के headers और body मेल न खाएँ, उसे 400 error मिलता है। अब कोई session id नहीं है: server पुराने `Mcp-Session-Id` header को ignore करता है और नया नहीं बनाता। अगर किसी workflow को state चाहिए, तो tool `draft_id` जैसा एक handle लौटाता है और model उसे वापस भेजता है।

दो gotchas। पुराने tutorials **HTTP+SSE** transport (`transport="sse"`) use करते हैं, जो deprecated है: उस पर कुछ नया शुरू मत करो। और stdio server को standard output पर सिर्फ़ MCP messages लिखने चाहिए: एक भी भटका हुआ `print` connection तोड़ देता है, इसलिए standard error पर log करो।

### Python में server बनाना

Official Python SDK `mcp` package है, November 2026 तक version 2.x (`pip install "mcp[cli]"`)। उसकी main class `MCPServer` है। SDK 1.x वाले tutorials `mcp.server.fastmcp` से `FastMCP` import करते हैं, जो 2.x पर fail होता है: code update करो या `mcp<2` pin करो।

```python
# tickets_server.py
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open") -> list[dict]:
    """Search support tickets by keywords. status is 'open' or 'closed'. Returns up to 10."""
    if status not in ("open", "closed"):
        raise ToolError("status must be 'open' or 'closed'.")
    return ticket_db.search(query, status=status, limit=10)

@mcp.resource("ticket://{ticket_id}")
def ticket(ticket_id: str) -> str:
    """The full text of one ticket."""
    return ticket_db.get(ticket_id).body

@mcp.prompt()
def summarise_ticket(ticket_id: str) -> str:
    return f"Summarise ticket {ticket_id} in five bullets."

if __name__ == "__main__":
    mcp.run()  # stdio; use mcp.run(transport="streamable-http") for a remote server
```

Function का नाम, type hints और docstring ही tool का name, input schema और description बन जाते हैं, इसलिए tool-design वाला lesson यहाँ सीधे लागू होता है। `ToolError` raise करने पर एक `isError: true` result लौटता है: `Error executing tool <name>:` prefix के बाद आपका message।

**Model जोड़ने से पहले test करो।** MCP Inspector (`npx @modelcontextprotocol/inspector`, या `mcp dev tickets_server.py`) से आप हर tool को अपने arguments से call कर सकते हो, गलत arguments समेत, और raw results देख सकते हो। ज़्यादातर bugs यहाँ chat से जल्दी दिख जाते हैं।

**आपका अपना client।** Assistants और code editors में clients पहले से होते हैं; आपका अपना agent SDK use कर सकता है:

```python
import asyncio
from mcp import Client, StdioServerParameters

async def main():
    server = StdioServerParameters(command="python", args=["tickets_server.py"])
    async with Client(server) as client:  # or Client("https://.../mcp") for a remote server
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("search_tickets", {"query": "refund"})
        print(result.is_error, result.structured_content)

asyncio.run(main())
```

हर tool का `name`, `description` और `input_schema` model को दो, उसकी calls `client.call_tool` को भेजो, और `is_error` वापस दो ताकि model को पता चले कि call fail हुई।

### Server client से क्या माँग सकता है

**Elicitation** से कोई tool call के बीच में user से कुछ पूछ सकता है: कोई छूटी हुई detail, या bulk change से पहले "सारे 40 tickets close कर दें?"। 2026-07-28 में ये rounds में चलता है: server अपने सवालों के साथ `resultType: "input_required"` लौटाता है, host user से पूछता है, और client जवाबों के साथ call दोहराता है। Password या payment के लिए, जो AI app से होकर नहीं जाने चाहिए, server user को एक web page पर भेज देता है (URL mode)।

पुराने material में **sampling** (server host के model से text लिखवाता है) और **roots** (host server को बताता है कि कौन-से folders use करने हैं) का भी ज़िक्र है। दोनों 2026-07-28 में deprecated हो गए, साथ में logging भी। ये कम से कम 28 July 2027 को या उसके बाद release होने वाले पहले revision तक spec में रहेंगे, पर इन पर कुछ नया मत बनाओ। 2026-07-28 में लंबे चलने वाले jobs (**tasks**) core से निकलकर एक extension में चले गए। Interactive screens (**MCP Apps**) एक अलग extension है।

### Tools context खाते हैं

हर जुड़े हुए tool का name, description और schema हर turn पर model के context में बैठा रहता है। Anthropic का documentation (November 2026 में check किया) कहता है कि पाँच servers वाला एक आम setup काम शुरू होने से पहले ही definitions में करीब 55,000 tokens खा सकता है, और 30 से 50 tools के बाद tool चुनने की quality गिरती है। इसलिए:

- कम, task के हिसाब से बने और अलग-अलग नाम वाले tools दो; अगर दो servers में `search` हो सकता है, तो system का prefix लगाओ (`maint_search`)।
- Results पर cap लगाओ: एक `limit` argument, छोटे fields, पूरे documents की जगह IDs।
- जहाँ host सपोर्ट करे, tools ज़रूरत पड़ने पर load करो। मिसाल के तौर पर, Claude का tool search tool `defer_loading` mark किए गए tools को तब तक context से बाहर रखता है जब तक model उन्हें search न करे।

### Security, छोटे में

Server ऐसा code है जिसकी पहुँच असली systems तक है, और उसका output model में जाता है। मुख्य risks: **tool poisoning** (descriptions या results में छुपे instructions), **approval के बाद बदलाव** (versions pin करो), servers के बीच **नामों की टक्कर**, और **बहुत ज़्यादा पहुँच** (पूरी company का एक token)। आगे वाला lesson, Securing agent tools and MCP servers, इसमें और गहराई में जाता है; worked example बनाने वाले का पक्ष दिखाता है।

## एक worked example

Pune की एक manufacturing company के दो plants हैं, PUN-1 और PUN-2। Engineers अपने IDE में एक AI assistant और chat में दूसरा use करते हैं, और दोनों को maintenance log चाहिए। Contractors को सिर्फ़ अपना plant दिखना चाहिए।

आप तीन tools वाला एक remote MCP server बनाते हो: `find_machine`, `get_maintenance_history` और `log_observation`। Remote MCP OAuth use करता है: company का single sign-on (SSO) **authorization server** है जो tokens issue करता है, और आपका MCP server **resource server** है जो उन्हें check करता है।

```flow
title: Remote server से पहला connection
Assistant बिना token के server को call करता है -> Server के metadata link के साथ 401 reply
Server के metadata link के साथ 401 reply -> Assistant पढ़ता है कि कौन-सी sign-in service use करनी है
Assistant पढ़ता है कि कौन-सी sign-in service use करनी है -> Engineer company SSO से sign in करता है
Engineer company SSO से sign in करता है -> SSO सिर्फ़ इसी server के लिए token देता है | user, plant, scopes
SSO सिर्फ़ इसी server के लिए token देता है -> Assistant token के साथ call दोहराता है
Assistant token के साथ call दोहराता है -> Server token check करके उसी user के तौर पर tool चलाता है
```

Metadata serve करना और 401 भेजना SDK आपके लिए कर देता है। आपका code tokens check करता है और user की सीमाएँ लागू करता है:

```python
# maintenance_server.py
import json, sqlite3
from mcp.server import MCPServer
from mcp.server.auth.middleware.auth_context import get_access_token
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver.exceptions import ToolError

db = sqlite3.connect("maintenance.db", check_same_thread=False)
audit = open("audit.jsonl", "a", buffering=1)  # one JSON line per call

def verify_with_sso(token: str) -> dict | None:
    """Your SSO library checks signature, expiry and issuer; returns the claims or None."""
    ...

class SSOTokenVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        claims = verify_with_sso(token)
        if claims is None:
            return None
        return AccessToken(token=token, client_id=claims["azp"], subject=claims["sub"],
                           scopes=claims["scope"].split(), resource=claims["aud"],
                           claims={"plant": claims["plant"]})

mcp = MCPServer("maintenance", token_verifier=SSOTokenVerifier(), auth=AuthSettings(
    issuer_url="https://sso.example.in",
    resource_server_url="https://mcp.example.in/maintenance",
    required_scopes=["maintenance.read"],
    validate_token_resource=True,  # refuse tokens issued for any other service
))

def caller(tool: str, args: dict) -> tuple[str, str, list[str]]:
    """Who is calling, from the checked token, never from the model. Writes the audit line."""
    tok = get_access_token()
    audit.write(json.dumps({"user": tok.subject, "client": tok.client_id, "tool": tool, "args": args}) + "\n")
    return tok.subject, tok.claims["plant"], tok.scopes

@mcp.tool()
def get_maintenance_history(tag: str, limit: int = 5) -> list[dict]:
    """Latest maintenance events for one machine in your plant, newest first. limit is 1 to 20."""
    user, plant, _ = caller("get_maintenance_history", {"tag": tag, "limit": limit})
    rows = db.execute(
        "SELECT e.done_on, e.kind, e.note, e.by_user FROM events e JOIN machines m ON m.id = e.machine_id "
        "WHERE m.tag = ? AND m.plant_id = ? ORDER BY e.done_on DESC LIMIT ?",
        (tag, plant, max(1, min(limit, 20)))).fetchall()
    if not rows:
        raise ToolError(f"No machine '{tag}' in your plant. Call find_machine to search by name.")
    return [{"date": d, "kind": k, "note": n, "by": b} for d, k, n, b in rows]

@mcp.tool()
def log_observation(tag: str, note: str) -> str:
    """Add a short note (max 500 characters) to a machine's log. Writes only to the notes table."""
    user, plant, scopes = caller("log_observation", {"tag": tag, "note": note[:80]})
    if "maintenance.write" not in scopes:
        raise ToolError("Your sign-in does not allow writing notes. Ask your supervisor to add it.")
    row = db.execute("SELECT id FROM machines WHERE tag = ? AND plant_id = ?", (tag, plant)).fetchone()
    if row is None:
        raise ToolError(f"No machine '{tag}' in your plant.")
    db.execute("INSERT INTO notes (machine_id, note, by_user) VALUES (?, ?, ?)", (row[0], note[:500], user))
    db.commit()
    return f"Note added to {tag}."

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000,
            streamable_http_path="/maintenance")  # serve behind HTTPS in production
```

तीन design choices security संभालती हैं:

1. **Plant token से आता है, model से नहीं।** किसी tool में `plant_id` argument नहीं है, इसलिए कोई prompt दूसरा plant नहीं माँग सकता। हर query उस plant से filter होती है जो SSO ने token में डाला।
2. **Token इसी server के लिए होना चाहिए।** `validate_token_resource=True` के साथ, किसी दूसरी service के लिए issue हुए असली token को भी 401 मिलता है।
3. **Writes के लिए scope चाहिए।** पढ़ने के लिए `maintenance.read` चाहिए; `log_observation` को `maintenance.write` भी चाहिए।

हमने इस server को दो users के stand-in tokens से test किया (`find_machine` भी उसी pattern पर है, ऊपर छोड़ दिया)। PUN-1 की engineer Anita chat में पूछती है: "CNC-14 का spindle आखिरी बार कब service हुआ था, और उसके बाद किसी ने vibration report किया है क्या?" Assistant `get_maintenance_history` call करता है और दो rows पाता है: 2 October 2026 को suresh.p ने bearings बदले, और 18 November 2026 को meera.d ने "Vibration at high RPM" लिखा। वो दोनों के साथ जवाब देता है, फिर `log_observation` से उसका note log करता है।

Ravi एक contractor है जिसके token में PUN-2 और सिर्फ़ `maintenance.read` है; वो अपने IDE से वही पूछता है। वही query `plant_id = 'PUN-2'` के साथ चलती है, कुछ नहीं मिलता, और "No machine 'CNC-14' in your plant." लौटता है। उसकी `log_observation` call को "Your sign-in does not allow writing notes." मिलता है। दोनों `isError: true` वाले results हैं, इसलिए assistant उन्हें समझा देता है। Audit log में हर call की एक line है, जैसे `{"user": "ravi.contractor", "client": "ide-assistant", "tool": "get_maintenance_history", "args": {"tag": "CNC-14", "limit": 2}}`।

इसे production-grade बनाने के लिए दो layers और। Server का database account सिर्फ़ machines और events पढ़ सके और notes में insert कर सके, ताकि आपके filter में bug हो तब भी कुछ delete न हो। और server **Anita का token कभी** किसी दूसरी API को **आगे न भेजे**। वो token passthrough है, जिसे MCP security guidance मना करती है; अगर किसी downstream API को user चाहिए, तो उसी API के लिए issue हुआ एक अलग token लो।

बाद में जब IT एक spare-parts system जोड़ता है, तो वो उसी sign-in के साथ एक दूसरा server deploy करते हैं, और दोनों assistants को बिना किसी बदलाव के उसके tools मिल जाते हैं।

## आम गलतियाँ

- **किसी पुराने tutorial को line-by-line follow करना।** `FastMCP` imports, `transport="sse"`, session ids और `initialize` handshake 2024 और 2025 के हैं। पहले versions check करो।
- **सबके लिए एक super-user credential।** अगर server ये नहीं देखता कि कौन पूछ रहा है, तो हर user हर चीज़ तक पहुँच जाता है। Sign-in किए हुए user की तरह काम करो।
- **Identity किसी tool argument से लेना।** `user_id` या `plant_id` parameter से model, या उसमें inject किया गया text, किसी और का data चुन सकता है। Identity check किए गए token से पढ़ो।
- **Token passthrough।** जो tokens आपके server के लिए issue नहीं हुए उन्हें मानना, या user का token दूसरी services को आगे भेजना, audit और scope checks तोड़ देता है।
- **पूरा database खोल देना।** जब तक users database administrators न हों, `run_sql` नहीं, task के हिसाब से बने tools दो।
- **बहुत बड़े results।** हज़ारों rows context भर देती हैं और हर अगला turn धीमा कर देती हैं। Cap करो, paginate करो और summarise करो।
- **Timeouts नहीं।** धीमे ERP का इंतज़ार करता tool agent को रोक देता है। Server की अपनी calls पर timeout लगाओ, और client read timeout भी set करो (Python `Client` में `read_timeout_seconds`)।
- **Servers और results पर भरोसा करना।** अनजान या बिना pin किए servers, और instructions मान लिया गया ticket text, tool poisoning और prompt injection को न्योता देते हैं।
- **Logging नहीं।** हर call का user, tool और arguments न हो, तो किसी incident की जाँच नहीं हो सकती।

## कब आपको MCP नहीं चाहिए

- **कुछ tools वाला एक ही app**, जिन्हें सिर्फ़ वही use करता है: आपके code में सीधी tool definitions आसान हैं।
- **Fixed workflows**, जहाँ आपका code functions सीधे call करता है और कोई model tools नहीं चुनता।
- **Strict environments**, जहाँ हर नई network service को review चाहिए: in-process tools से शुरू करो, और जब दूसरे app को उनकी ज़रूरत हो तब MCP पर जाओ।

MCP तब फ़ायदा देता है जब कई hosts या agents को वही tools चाहिए, या लोग अपने पहले से इस्तेमाल हो रहे assistants को आपके systems से जोड़ना चाहते हैं।

## Demo से production तक

- **Company sign-in के ज़रिए OAuth**, narrow scopes, इसी server के लिए check किए गए tokens, token से identity, और एक least-privilege database account।
- **एक central audit log**: user, client, tool, arguments और result size।
- **Approved servers की एक list**, pin किए गए versions, और जब भी tool descriptions बदलें तब review।
- **हर tool पर सीमाएँ:** timeouts, result caps, rate limits, और writes के लिए user confirmation।
