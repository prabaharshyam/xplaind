## ये क्या है

LLM apps में तीन techniques cost और इंतज़ार का समय घटाती हैं। ये अलग-अलग layers पर काम करती हैं, और इन्हें आपस में मिला देना ही ज़्यादातर caching bugs की वजह बनता है।

- **Prompt caching** model provider के पास होती है। Provider आपके prompt की शुरुआत (instructions, tool definitions, एक लंबा document) का processed रूप रख लेता है। बाद की जो request ठीक उसी content से शुरू होती है, वो ये काम skip कर देती है, इसलिए उसकी cost कम होती है और पहला token जल्दी आता है। Model फिर भी हर बार नया जवाब लिखता है।
- **Response caching** आपके अपने app में होती है। आप तैयार जवाब store करते हो और वही request दोबारा आने पर उनमें से एक लौटा देते हो, model call के बिना ही। इसे आप खुद बनाते हो, इसलिए हर store किया जवाब कौन देख सकता है, ये आप तय करते हो।
- **Streaming** delivery बदलती है, काम नहीं। Reply जैसे-जैसे generate होता है, टुकड़ों में screen पर पहुँचता है, इसलिए user एक-दो second में पढ़ना शुरू कर देता है।

तीनों use करने वाली एक request ऐसी दिखती है:

```flow
title: एक request, तीन layers
सवाल आता है -> मेरे response cache में है?
मेरे response cache में है? -[hit, वही scope]-> Store किया जवाब लौटाओ | model call नहीं
मेरे response cache में है? -[miss]-> Model को call करो -> Provider cached prefix पढ़ता है | instructions और documents
Provider cached prefix पढ़ता है -> Tokens screen पर stream करो -> तैयार जवाब store करो | सिर्फ तब जब reuse करना safe हो
```

ये lesson Chennai की एक legal-tech company के contract assistant को follow करता है। Lawyers एक agreement upload करते हैं और उस पर करीब दस सवाल पूछते हैं।

## ये कैसे काम करता है

### समय कहाँ जाता है

एक reply के दो phases होते हैं। पहले model पूरा input पढ़ता है (**prefill**)। फिर reply एक बार में एक token करके लिखता है (**decode**)। लंबा input पहले token को धीमा करता है। लंबा output उसके बाद की हर चीज़ को धीमा करता है। तो 30,000-token का contract ज़्यादातर **time to first token** (TTFT) पर असर डालता है, जबकि 1,000-token का जवाब ज़्यादातर total time पर। Prompt caching पहले वाले पर वार करती है; streaming दूसरे को छिपाती है; छोटे जवाब और छोटे models उसे घटाते हैं।

### Prompt caching

Cache एक **exact prefix** match करता है: request उन्हीं bytes से, उसी क्रम में शुरू होनी चाहिए, जैसे हाल में देखी गई कोई request। एक character बदला तो उसके बाद का सब कुछ invalid हो जाता है। इसलिए prompt को सबसे stable से सबसे कम stable के क्रम में रखो:

1. tool definitions, एक तय क्रम में;
2. system instructions;
3. लंबे reference documents (contract, policy, codebase);
4. per-user या per-session data;
5. latest सवाल और conversation turns।

Timestamp, request id या user का नाम कभी ऊपर मत रखो। Model को आज की date चाहिए तो उसे आखिर के पास रखो।

**वो numbers जो तय करते हैं कि ये फ़ायदेमंद है या नहीं।** Claude के API के साथ, November 2026 के हिसाब से (28 November 2026 को check किया; नीचे link किया pricing page देखो):

| Item | Value |
| --- | --- |
| Cache write, 5-minute lifetime (default) | Normal input price का 1.25x |
| Cache write, 1-hour lifetime (`"ttl": "1h"`) | Normal input price का 2x |
| Cache read | ज़्यादातर models पर 0.1x; Sonnet 5.5 और Opus 5.5 पर 0.05x; Fable 5.1 और 5.2 पर 0.025x |
| Lifetime | Entry को write या read करने वाली आखिरी request के शुरू होने से गिनी जाती है; हर read बिना extra cost के clock फिर से शुरू कर देता है |
| Minimum cacheable prefix | Current models पर 512 tokens (कुछ पुराने models पर 1,024 से 4,096); इससे छोटे prefixes cache नहीं होते और कोई error नहीं आता |
| हर request में breakpoints | 4 तक |
| Entry कौन share करता है | सिर्फ आपका workspace; कोई दूसरी organisation कभी नहीं |

इससे दो rules निकलते हैं। 5-minute cache एक read के बाद अपनी cost वसूल कर लेता है; 1-hour cache को दो चाहिए। और price से ज़्यादा lifetime मायने रखती है: अगर एक prefix share करने वाली requests lifetime से ज़्यादा दूरी पर आती हैं, तो हर request write premium देती है और किसी को read discount नहीं मिलता, जो caching न करने से भी महँगा पड़ता है।

Lifetime prefix share करने वाली requests के बीच के gap से चुनो। 5 minute से कम हो तो default use करो; steady traffic उसे अपने-आप warm रखता है। 5 से 60 minute के बीच हो तो 1-hour cache। एक घंटे से ज़्यादा हो तो या तो पहली request के cold होने को मान लो या **pre-warm** करो: traffic आने की उम्मीद से ठीक पहले (worker start, पहले lawyer का login), shared prefix को `max_tokens` 0 set करके एक बार भेजो। तब Claude का API cache write कर देता है और कुछ भी generate किए बिना लौट आता है।

**Parallel requests ऐसा cache share नहीं करतीं जो अभी write हो रहा है।** Entry तभी readable होती है जब पहला response शुरू हो जाए। एक साथ दस requests भेजोगे तो दसों पूरी कीमत देंगी। पहले एक भेजो, उसके पहले token का इंतज़ार करो, फिर बाकी भेजो।

**दूसरे providers।** कुछ providers, जैसे OpenAI, prompt के एक minimum length तक पहुँचते ही अपने-आप cache कर लेते हैं (उनके documentation के हिसाब से, model के अनुसार कम से कम 1,024 tokens)। Claude automatic caching या explicit breakpoints देता है। Stable content पहले रखना हर जगह काम करता है; minimums, lifetimes और prices अलग होते हैं, इसलिए savings का अंदाज़ा लगाने से पहले अपने provider का page पढ़ो।

**Code में prompt caching।** Anthropic के Python SDK में आप stable हिस्से का अंत mark करते हो, और usage report दिखाती है कि cache से क्या पढ़ा गया:

```python
import anthropic

client = anthropic.Anthropic()
POLICY = open("returns_policy.md").read()          # long, rarely changes

def ask(question):
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000,  # check the docs for current model names
        system=[
            {"type": "text", "text": "You answer questions about our returns policy. Be brief."},
            {"type": "text", "text": POLICY,
             "cache_control": {"type": "ephemeral"}},  # cache up to here; add "ttl": "1h" for slow traffic
        ],
        messages=[{"role": "user", "content": question}],   # changing part goes last
    )
    u = reply.usage
    print(f"cache write {u.cache_creation_input_tokens}, cache read {u.cache_read_input_tokens}, "
          f"uncached {u.input_tokens}")
    return reply

ask("Can I return a kurta after 10 days?")       # first call writes the cache
ask("Do you refund shipping charges?")           # later calls read it
```

**काम कर रहा है या नहीं, ये check करना।** हर call पर तीनों usage numbers log करो। लगातार पाँच requests भेजो: पहली में cache write दिखना चाहिए और बाकी में लगभग उतने ही size के cache reads। अगर reads zero पर ही रहें, तो prefix में कुछ अभी भी बदल रहा है: timestamp, request id, अलग क्रम में बने tools, बिना sorted keys वाला JSON, minimum से छोटा prefix, या बदला हुआ model या thinking setting। अगर reads prefix से बहुत छोटे हैं, तो breakpoint गलत जगह पर है।

### Response caching, user तक scoped

Response cache एक key-value store होता है, जैसे dictionary या Redis। Key में **जवाब बदलने वाली हर चीज़** होनी चाहिए: normalise किया सवाल, document या data version, prompt version, model, और **scope**, यानी जवाब देखने की इजाज़त किसे है।

Scope वो हिस्सा है जिसे teams भूल जाती हैं, और इसे भूलने से data leak होता है। मान लो key में सिर्फ सवाल है। Asha पूछती है "मेरा order कहाँ है?" और उसके address वाला जवाब store हो जाता है। Ravi वही शब्द पूछता है और उसे cache से Asha का जवाब मिल जाता है, milliseconds में, किसी log में कोई error नहीं। Provider का prompt cache ऐसा नहीं कर सकता, क्योंकि model हर बार नया जवाब लिखता है। आपका response cache कर सकता है, क्योंकि वो store किया text लौटाता है।

तीन scopes use करो। **Public**: सबके लिए एक जैसा, जैसे product FAQs और fixed help text। **Tenant**: एक company के अंदर एक जैसा, जैसे किसी law firm का अपना standard NDA, पर किसी दूसरी firm को कभी नहीं दिखाया जाता। **User**: personal या permission पर depend करने वाला; इसकी key user id से बनाओ, या इसे cache ही मत करो। Scope को एक required argument बना दो ताकि कोई इसे भूल न सके:

```python
import hashlib, json, time

CACHE, TTL_SECONDS = {}, 24 * 3600
PROMPT_VERSION, MODEL = "faq-v3", "claude-sonnet-5-5"

def cache_key(scope, question, doc_version):
    norm = " ".join(question.lower().split())
    raw = json.dumps([scope, norm, doc_version, PROMPT_VERSION, MODEL])
    return hashlib.sha256(raw.encode()).hexdigest()

def cached_answer(scope, question, doc_version, compute):
    # scope: "public", "firm:<id>" or "user:<id>"; there is no default on purpose
    key = cache_key(scope, question, doc_version)
    hit = CACHE.get(key)
    if hit and time.time() - hit["at"] < TTL_SECONDS:
        return hit["answer"]
    answer, complete = compute(question)          # complete: the reply finished normally
    if complete:                                  # never cache errors or cut-off replies
        CACHE[key] = {"answer": answer, "at": time.time()}
    return answer
```

Ship करने से पहले two-account test चलाओ: user A एक personal सवाल पूछता है, user B वही शब्द पूछता है, और B को A का जवाब नहीं मिलना चाहिए। Stable जवाबों के लिए भी expiry रखो, और source बदलने पर entries clear करो; cache किया गलत जवाब तब तक दोहराया जाता है जब तक कोई notice न करे।

### Semantic caching, सावधानी से

**Semantic caching** embeddings से सवालों को मतलब के हिसाब से match करती है, ताकि "हमारे NDA में notice period?" का सवाल "NDA का notice period क्या है?" के जवाब को reuse कर सके। इससे hit rates बढ़ते हैं, पर हर गलत match पूरे भरोसे के साथ एक गलत जवाब देता है। तीन guards:

- **Similarity search से पहले scope से filter करो**, ताकि match सिर्फ उन जवाबों से आ सके जिन्हें पूछने वाला देख सकता है।
- **Numbers और names पर exact मेल ज़रूरी रखो।** "Order 41 का refund" और "order 14 का refund" text के तौर पर लगभग एक जैसे हैं और सवाल के तौर पर बिल्कुल अलग:

```python
import re

def numbers_match(new_q, cached_q):
    return re.findall(r"\d+", new_q) == re.findall(r"\d+", cached_q)
```

- **Similarity threshold अपने खुद के data से set करो।** कोई safe universal number नहीं है। Candidate matches log करो, किसी व्यक्ति से उनमें से 200 को सही या गलत label करवाओ, और threshold तब तक बढ़ाओ जब तक wrong-match rate उस feature के लिए आपके तय किए target से नीचे न आ जाए।

### Streaming

Streaming total generation time या cost नहीं बदलती। ये experience बदलती है: text एक-दो second में शुरू हो जाता है, बाकी आते-आते user पढ़ता रहता है, और जल्दी Stop दबा सकता है। Chat में हमेशा stream करो। TTFT measure करो:

```python
import time
import anthropic

client = anthropic.Anthropic()

def stream_answer(question):
    start, first = time.perf_counter(), None
    with client.messages.stream(model="claude-sonnet-5-5", max_tokens=2000,
                                messages=[{"role": "user", "content": question}]) as stream:
        for text in stream.text_stream:
            if first is None:
                first = time.perf_counter() - start
            print(text, end="", flush=True)     # in a web app, send each piece to the browser
        final = stream.get_final_message()
    print("\nfirst text after", round(first, 2) if first else None,
          "s; total", round(time.perf_counter() - start, 2), "s; stop:", final.stop_reason)
```

Server timing पूरी कहानी नहीं है: browser में, user के Send दबाने पर और पहले शब्दों के paint होने पर `performance.now()` record करो, और real users से p50 और p95 report करो। तीन gotchas। कुछ proxies, compression layers और hosting platforms response को buffer करते हैं, इसलिए जो stream local पर काम करता है वो production में एक साथ पहुँचता है; असली path से test करो। Stream बीच में fail हो सकता है, इसलिए partial text को साफ़ "answer interrupted, try again" के साथ दिखाओ और उसे कभी cache मत करो। और जवाब पूरा होने से पहले ही text screen पर होता है, इसलिए जिस check को पूरा जवाब चाहिए, जैसे safety filter या JSON validation, उसे हर टुकड़े पर चलना होगा या text दिखाना शुरू करने से पहले चलना होगा।

### Speed के दूसरे levers

छोटे outputs, क्योंकि generation time length के साथ बढ़ता है। Simple steps के लिए छोटे models। Sequence में कम calls। एक-दूसरे पर depend न करने वाली calls parallel में (जैसे `asyncio.gather` से), ताकि इंतज़ार सबका जोड़ न होकर सबसे धीमी call जितना हो; rate limits का ध्यान रखो, क्योंकि एक burst 429 errors लौटा सकता है। कम, पर बेहतर retrieved chunks।

## एक worked example

Chennai का contract assistant 40-page के agreement पर सवालों के जवाब देता है। नीचे के numbers November 2026 के हिसाब से Claude Sonnet 5.5 की list prices पर बना एक **illustration** हैं ($2 per million input tokens, $10 per million output, cache writes 5 minute के लिए $2.50 या 1 hour के लिए $4, cache reads $0.10), इन assumptions के साथ: instructions और contract 30,000 tokens हैं, हर सवाल 100 tokens का है और अकेले भेजा जाता है, हर जवाब 300 output tokens use करता है, और हर contract पर 10 सवाल हैं। ये figures दोबारा use करने से पहले current prices check करो।

**पहले।** हर सवाल पूरे 30,100 tokens पूरी कीमत पर भेजता है: $0.0602 का input और $0.003 का output, यानी $0.0632 per सवाल और **$0.63 per contract**। कुछ भी stream नहीं होता, इसलिए lawyer को करीब 9 seconds तक कुछ नहीं दिखता।

**बाद में, पहली कोशिश।** Team contract और instructions को आगे ले आती है, एक breakpoint जोड़ती है, और default 5-minute cache रखती है। अगर सवाल 5 minute से कम के अंतर पर आते, तो सवाल 1 की cost $0.078 होती (write premium उसे पहले से महँगा बना देता है) और बाद के हर सवाल की $0.0062, यानी **$0.13 per contract, 79% कम**। पर logs में लगभग हर call पर cache writes दिखते हैं। Lawyers अगला सवाल पूछने से पहले हर जवाब को clause से मिलाकर पढ़ते हैं, अक्सर 5 से 15 minute बाद। हर entry expire हो जाती है, हर सवाल write price देता है, और bill बढ़कर **$0.78 per contract हो जाता है, caching न करने से 24% ज़्यादा**।

**बाद में, ठीक किया।** वो 1-hour cache पर switch करते हैं। अब सवाल 1 की cost write के लिए $0.12 है, और अगले नौ की $0.0062 हर एक: **$0.18 per contract, पहले से करीब 72% कम**। करीब ₹94 per dollar पर (mid-November 2026), ये per contract लगभग ₹59 से घटकर ₹17 है। ध्यान दो कि output tokens ($0.003 per जवाब) अब एक cached सवाल की cost का आधा हैं, इसलिए अगली बचत छोटे जवाब हैं।

| Per contract session (illustrative) | Caching नहीं | 5-minute cache, gaps 5 min से ज़्यादा | 1-hour cache, streaming on |
| --- | --- | --- | --- |
| Input cost, 10 सवाल | हर बार पूरी कीमत | हर बार write premium | एक write, नौ सस्ते reads |
| Total cost | $0.63 | $0.78 | $0.18 |
| कोई भी text आने से पहले इंतज़ार, सवाल 1 | करीब 9 s | करीब 9 s | करीब 2 से 3 s (streamed, cache अभी खाली) |
| कोई भी text आने से पहले इंतज़ार, सवाल 2 से 10 | करीब 9 s | करीब 9 s | करीब 1 से 2 s (cached prefix, streamed) |

Firm के पास अपने standard templates पर सवालों के लिए एक response cache भी है ("हमारे standard NDA में notice period क्या है?")। इसकी key firm की id, template version और prompt version से बनी है, इसलिए firm A के template जवाब कभी firm B तक नहीं पहुँचते। Upload किए contract के बारे में जवाब response-cache होते ही नहीं: हर contract एक matter का होता है जिसकी अपनी access list है।

पहले सवाल को भी तेज़ करने के लिए, contract upload पूरा होते ही, जब lawyer अभी type कर रहा होता है, team `max_tokens` 0 set करके cache pre-warm कर देती है।

## आम गलतियाँ

- **Prompt के ऊपर कुछ बदलने वाला।** Date, request id या user name हर cache read तोड़ देता है। पहचानो: बार-बार की calls पर `cache_read_input_tokens` 0 पर ही रहता है।
- **Traffic के लिए गलत lifetime।** Cache lifetime से लंबे gaps caching को surcharge बना देते हैं। पहचानो: ज़्यादातर calls पर cache writes और कम reads।
- **बिना scope वाली response cache keys।** एक user का order, salary या contract दूसरे user तक पहुँच जाता है। पहचानो: launch से पहले और हर cache change के बाद चलाया गया two-account test।
- **बदलने वाले data से बने जवाबों को cache करना, key में expiry या version के बिना।** पुरानी prices और पुराने rules serve होते रहते हैं। पहचानो: update के बाद source से मेल न खाने वाले जवाब।
- **Failures को cache करना।** Timeout, refusal या `max_tokens` से कटा reply store हो जाता है और सबको replay होता है। सिर्फ वही replies store करो जो normal तरीके से पूरे हुए।
- **Cold cache पर parallel requests भेजना।** सब पूरी कीमत देती हैं। पहचानो: एक ही second में cache writes का burst।
- **ये मानना कि streaming generation को तेज़ करती है।** ये इंतज़ार को छोटा feel करवाती है; cost और total time वही रहते हैं।
- **सिर्फ averages measure करना।** Time to first token और total time के लिए p50 और p95 report करो, server के साथ-साथ browser में भी measure करके।

## Caching कब मदद नहीं करती

- **हर request अलग है**, कोई लंबा shared prefix नहीं और दोहराए सवाल कम।
- **Traffic कम और बिखरा हुआ है**, इसलिए cached prefixes अगली request से पहले expire हो जाते हैं, 1 hour पर भी।
- **Shared हिस्सा छोटा है**, minimum cacheable length से नीचे।
- **जवाब हर बार fresh चाहिए**, जैसे live prices या stock levels।
- **धीमा हिस्सा कहीं और है**: retrieval, कोई धीमा tool या आपका अपना server। Model call को optimise करने से पहले measure करो।

## Demo से production तक

- हर call पर **cache read और write tokens log करो**, और हर feature का hit rate track करो।
- **Time to first token और total time track करो** p50 और p95 पर, feature और model के हिसाब से, browser से।
- **Cache keys को version करो** prompt, model और data से, हर जगह expiries रखो, और release पर या source data बदलने पर response caches clear करो।
- **Scope को हर response cache key का required हिस्सा बनाओ**, और two-account test को अपने test suite में रखो।

## Practice

नीचे link किया prompt caching guide और streaming guide पढ़ो।

1. अपने किसी एक prompt को ऐसे restructure करो कि stable content पहले आए, और एक breakpoint जोड़ो। पाँच requests भेजो और हर एक के लिए cache write, cache read और uncached tokens record करो।
2. अपने real traffic में requests के बीच का gap निकालो, 5 minutes या 1 hour चुनो, और अपने provider की current prices से per session cost दोनों तरीकों से calculate करो।
3. एक chat interface में streaming जोड़ो और पहले और बाद में browser में time to first token measure करो।
4. एक दोहराए जाने वाले सवाल type के लिए scoped response cache जोड़ो, फिर two-account test लिखो और scope हटाने पर उसे fail होते देखो।
