## ये क्या है

**Experiment tracking** हर training run को अपने आप log करता है: code version (एक Git commit), data version, parameters, metrics, environment (library versions), plots जैसे artefacts, और trained model। हर run एक row बन जाता है जिसे आप sort, compare और reproduce कर सकते हो।

**Model registry** चुने हुए model versions की एक shelf है। हर version के notes और tags होते हैं (जैसे, किसने approve किया), और उस पर एक **alias** भी लग सकता है: `champion` जैसा एक खिसकाया जा सकने वाला नाम जो ठीक एक version की ओर point करता है। Production alias load करता है, कभी file path नहीं, इसलिए deployed model हमेशा पता रहता है।

आम tools हैं MLflow (open source), Weights & Biases, और cloud ML platforms में built-in tracking। ये lesson MLflow 3 use करता है। MLflow में aliases ने पुराने fixed stages (Staging, Production) की जगह ले ली है: stages version 2.9 से deprecated हैं, और MLflow 3.18 में उन्हें call करने पर warning print होती है कि उन्हें हटा दिया जाएगा।

```flow
title: From training run to production
Training run 412 | commit a1b2c3d, data claims-2026-09, val PR AUC 0.46
Training run 412 -[team picks it and registers it]-> claims-fraud v14
claims-fraud v14 -[gate on October claims, then owner signs off]-> Alias champion
Alias champion -[loaded at start-up]-> Claim scoring service
Alias champion -[rollback: point it back]-> claims-fraud v13
```

ये lesson Hyderabad के एक insurer की ML team के साथ चलता है जो हर महीने अपना claim-fraud model retrain करती है।

## ये काम कैसे करता है

### जो कुछ एक run को define करता है, सब log करो

| Item | Example | क्यों ज़रूरी है | कौन record करता है |
| --- | --- | --- | --- |
| Parameters | `max_depth=6`, `learning_rate=0.05` | Runs के बीच के फ़र्क समझाता है | आप, या autologging |
| Metrics | Overall और हर region का PR AUC | Winner चुनता है और दिखाता है कि वो किसके लिए fail होता है | आप (segments हमेशा) |
| Code version | Git commit, clean tree | Training logic reproduce करता है | MLflow, जब Git repo में script की तरह run हो |
| Data version | `claims-2026-09` और साथ में एक hash | Inputs reproduce करता है | आप |
| Environment | `requirements.txt`, Python version | "मेरी machine पर तो चलता है" वाली दिक्कत से बचाता है | MLflow, हर logged model के साथ |
| Model और schema | Model file, input columns और types | Serving को गलत inputs reject करने देता है | आप, `log_model` के ज़रिए |
| Seed | `random_state=42` | Rerun करने पर वही model देता है | आप |

दो rules इसे भरोसेमंद बनाते हैं।

- **Commit को उसी code को describe करना चाहिए जो run हुआ।** जब आप Git repository के अंदर script run करते हो, तो MLflow commit को tag `mlflow.source.git.commit` के रूप में record करता है, लेकिन uncommitted edits को वो नहीं पकड़ता। आधी edit हुई file या notebook से चला run ऐसे commit की ओर point करता है जिसने उसे कभी बनाया ही नहीं। इसलिए नीचे वाला script uncommitted changes होने पर run होने से मना कर देता है। Notebook में, पहले commit करो या training code को एक script में ले जाओ।
- **Data का नाम data version नहीं है।** `claims-2026-09` सिर्फ़ एक label है; उसके पीछे वाली file कोई भी overwrite कर सकता है। ऐसे snapshots store करो जो कभी उसी जगह edit न हों, और file का hash log करो ताकि चुपचाप हुआ बदलाव सामने आ जाए। DVC जैसे tools, या Delta Lake जैसे table formats का time travel, आपके लिए पुराने versions रखते हैं (data versioning lesson देखो)।

**Autologging** (`mlflow.autolog()`) scikit-learn और XGBoost जैसी libraries के ज़्यादातर parameters और metrics एक line में capture कर लेता है। उसे आपका data version या आपके segments पता नहीं हो सकते, इसलिए वो खुद जोड़ो।

### एक training run को track करना

ये script fraud model train करता है और एक run log करता है। ये मानकर चलता है कि claims table में एक `region` column, एक `region_code` feature और एक `is_fraud` label है।

```python
import hashlib, subprocess, sys
import mlflow
import pandas as pd
from mlflow.models import infer_signature
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import average_precision_score
from sklearn.model_selection import train_test_split

DATA = "data/claims-2026-09.parquet"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]

def git(*args):
    return subprocess.run(["git", *args], capture_output=True, text=True, check=True).stdout.strip()

if git("status", "--porcelain", "--untracked-files=no"):   # ignores mlflow.db and mlruns/
    sys.exit("Uncommitted changes: commit first, or this run cannot be reproduced.")

with open(DATA, "rb") as f:
    data_sha = hashlib.file_digest(f, "sha256").hexdigest()[:12]   # Python 3.11 or newer

df = pd.read_parquet(DATA)
df[FEATURES] = df[FEATURES].astype("float64")      # floats can hold missing values at serving time
train, val = train_test_split(df, test_size=0.2, stratify=df["is_fraud"], random_state=42)
params = {"max_depth": 6, "learning_rate": 0.05, "max_iter": 300, "random_state": 42}

mlflow.set_experiment("claims-fraud")
with mlflow.start_run() as run:
    mlflow.set_tags({"data_version": "claims-2026-09", "data_sha256": data_sha})
    mlflow.log_input(mlflow.data.from_pandas(train, source=DATA, targets="is_fraud"), context="training")
    mlflow.log_params(params)

    model = HistGradientBoostingClassifier(**params).fit(train[FEATURES], train["is_fraud"])
    proba = model.predict_proba(val[FEATURES])
    mlflow.log_metric("val_pr_auc", average_precision_score(val["is_fraud"], proba[:, 1]))
    for region, part in val.groupby("region"):
        s = model.predict_proba(part[FEATURES])[:, 1]
        mlflow.log_metric(f"val_pr_auc_{region}", average_precision_score(part["is_fraud"], s))

    mlflow.sklearn.log_model(
        model, name="model",
        signature=infer_signature(val[FEATURES], proba),
        input_example=val[FEATURES].head(3),
        pyfunc_predict_fn="predict_proba",
        skops_trusted_types=["sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor"],
    )
    print("run", run.info.run_id)
```

MLflow 3 की हर detail क्या करती है (MLflow 3.18 पर check किया, November 2026):

- **`name="model"`** पुराने `artifact_path` argument की जगह लेता है, जो अब भी चलता है लेकिन अब deprecation warning log करता है।
- **कोई `registered_model_name` नहीं।** Training script के अंदर register करने से हर experiment के लिए एक registry version बन जाएगा। हर run log करो; register सिर्फ़ winner को करो।
- **`signature` और `input_example`** input columns और types को model के साथ store करते हैं, ताकि serving किसी missing या गलत spelling वाले column वाली request को reject कर सके। Features पहले floats में cast किए जाते हैं: integer के रूप में infer हुआ column serving time पर कोई value missing होने पर check में fail हो जाता है। फिर हर caller को भी floats ही भेजने होंगे; check integer columns को reject करता है। (MLflow फिर भी integer columns के बारे में एक hint print कर सकता है: वो logged dataset के `is_fraud` label के बारे में है, model के बारे में नहीं।) MLflow model के बगल में `requirements.txt` और `conda.yaml` भी लिखता है।
- **`log_input`** run को dataset से link करता है और उसका एक छोटा digest store करता है, जो आपके अपने hash के अलावा एक दूसरा check है।
- **`pyfunc_predict_fn="predict_proba"`** generic loader से hard 0 या 1 labels की जगह fraud probabilities return करवाता है।
- **`skops_trusted_types`।** MLflow अब scikit-learn models को skops से save करता है, जो pickle से ज़्यादा safe format है, क्योंकि pickle load करने पर file में छुपा कोई भी code चल सकता है। Skops उन object types को मना कर देता है जिन पर trust करने को उसे बताया नहीं गया, और `HistGradientBoostingClassifier` को ये वाला चाहिए। सिर्फ़ उन्हीं types पर trust करो जो आपने check किए हैं, और सिर्फ़ उन models के लिए जो आपने खुद train किए हैं।

Default रूप से MLflow 3.18 runs को उसी folder में एक local SQLite file, `mlflow.db`, में लिखता है जहाँ से आप run करते हो। उन्हें browse करने के लिए वहीं `mlflow ui` चलाओ।

### Runs compare करो, फिर winner को register करो

```python
import mlflow
from mlflow import MlflowClient

runs = mlflow.search_runs(experiment_names=["claims-fraud"],
                          order_by=["metrics.val_pr_auc DESC"], max_results=10)
print(runs[["run_id", "params.max_depth", "params.learning_rate",
            "metrics.val_pr_auc", "metrics.val_pr_auc_east"]].to_string(index=False))

client = MlflowClient()
run_id = runs.loc[0, "run_id"]        # in real life: the run the team chose after reading the table
model_id = client.get_run(run_id).outputs.model_outputs[0].model_id
mv = mlflow.register_model(f"models:/{model_id}", "claims-fraud")
client.update_model_version("claims-fraud", mv.version,
    description="Adds the claim-within-30-days feature; trained on claims-2026-09.")
print("registered version", mv.version)
```

MLflow 3 में logged model अपना अलग object है, `m-5f3a...` जैसी id के साथ, और उस run से linked है जिसने उसे बनाया, इसलिए आप उसे `models:/` और उस id से register करते हो। पुराना `runs:/` form अब भी चलता है लेकिन अब warning देता है कि उस run में कोई model files नहीं हैं। Version का description और tags एक छोटे **model card** का काम करते हैं: क्या बदला, उसने कौन-सा data देखा, known limits, किसने approve किया।

### Promotion check: वही data, असली gains, हर segment

यहीं trap है। Champion का logged PR AUC पिछले महीने के validation split से आया था; candidate का इस महीने के split से। Fraud patterns और fraud का share महीने-दर-महीने बदलते हैं, इसलिए उन दो numbers की तुलना जितनी models की है उतनी ही data की भी है। Fair test **दोनों models को एक ही fresh holdout पर** score करता है जिस पर कोई भी train नहीं हुआ: यहाँ, October के claims।

Insurer के rule के तीन हिस्से हैं:

1. **Overall gain noise से साफ़ ऊपर होना चाहिए।** Holdout claims को कई बार resample करो (एक bootstrap) और हर बार PR AUC gain दोबारा निकालो। Promote तभी करो जब gain का 90% interval zero से ऊपर ही रहे।
2. **किसी भी region का fraud-catching recall नहीं गिरना चाहिए।** Investigators हर महीने सिर्फ़ top 5% claims check कर सकते हैं। हर region के लिए नापो कि उसके fraud cases का कितना share उस top 5% में आता है। कोई भी region 2 points से ज़्यादा नहीं गिरना चाहिए।
3. **Check की report पढ़ने के बाद एक owner sign off करता है।**

```python
import numpy as np
import pandas as pd
import mlflow
from mlflow import MlflowClient
from sklearn.metrics import average_precision_score

NAME = "claims-fraud"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]
REVIEW_RATE = 0.05        # investigators can check the top 5% of claims each month
MAX_RECALL_DROP = 0.02    # no region may lose more than 2 points of recall
client = MlflowClient()

def scores_of(version, X):
    model = mlflow.pyfunc.load_model(f"models:/{NAME}/{version}")
    return model.predict(X)[:, 1]          # column 1 = probability of fraud

def recall_by_region(y, s, region):
    flagged = np.zeros(len(s), dtype=bool)
    flagged[np.argsort(-s)[: int(len(s) * REVIEW_RATE)]] = True   # the claims investigators open
    return {r: flagged[(region == r) & (y == 1)].mean() for r in np.unique(region)}

def pr_auc_gain_interval(y, s_new, s_old, n=500, seed=0):
    rng = np.random.default_rng(seed)
    gains = []
    for _ in range(n):
        i = rng.integers(0, len(y), len(y))   # resample claims with replacement
        gains.append(average_precision_score(y[i], s_new[i]) - average_precision_score(y[i], s_old[i]))
    return np.percentile(gains, [5, 95])

def check(candidate, holdout):
    champion = client.get_model_version_by_alias(NAME, "champion").version
    X = holdout[FEATURES].astype("float64")      # match the logged signature, or loading code rejects it
    y, region = holdout["is_fraud"].to_numpy(), holdout["region"].to_numpy()
    s_new, s_old = scores_of(candidate, X), scores_of(champion, X)

    low, high = pr_auc_gain_interval(y, s_new, s_old)
    problems = []
    if low <= 0:
        problems.append(f"PR AUC gain not clear: 90% interval {low:+.3f} to {high:+.3f}")
    r_new, r_old = recall_by_region(y, s_new, region), recall_by_region(y, s_old, region)
    for r in r_old:
        if r_new[r] < r_old[r] - MAX_RECALL_DROP:
            problems.append(f"{r}: recall {r_old[r]:.2f} -> {r_new[r]:.2f}")
    return champion, problems

holdout = pd.read_parquet("data/claims-2026-10.parquet")    # last month: neither model trained on it
champion, problems = check(candidate="14", holdout=holdout)
print("blocked:" if problems else "passed: ready for owner sign-off", problems)
```

तीन सावधानियाँ। Holdout को judge रहना चाहिए, coach नहीं: अगर लोग models को तब तक tune करते रहें जब तक वो October के claims पर pass न हो जाएँ, तो October fresh नहीं रहता। 2-point limit एक business decision है; किसी के results देखने से पहले ही fraud team के साथ उसे तय कर लो। और करीब 150 fraud cases वाले region में सिर्फ़ तीन cases के इधर-उधर होने से 2 points हिल जाते हैं, इसलिए ये guardrail जानबूझकर noisy है: ये कभी-कभार एक ठीक model को भी block कर देता है, और ये दोनों में से सस्ती गलती है। Block हुआ model किसी इंसान के पास जाता है, कूड़ेदान में नहीं।

### Aliases खिसकाकर promote और roll back करो

```python
from mlflow import MlflowClient
NAME = "claims-fraud"
client = MlflowClient()

def promote(candidate, champion, approver):
    client.set_model_version_tag(NAME, candidate, "approved_by", approver)
    client.set_registered_model_alias(NAME, "previous", champion)
    client.set_registered_model_alias(NAME, "champion", candidate)

def rollback():
    previous = client.get_model_version_by_alias(NAME, "previous").version
    client.set_registered_model_alias(NAME, "champion", previous)
```

Serving code `mlflow.pyfunc.load_model("models:/claims-fraud@champion")` load करता है। चलते हुए server ने model एक बार, start-up पर, load किया था, इसलिए जब तक service reload या restart न हो, alias खिसकाने से कुछ नहीं बदलता। Reload को promotion और rollback steps का हिस्सा बनाओ, और हर prediction के साथ served version log करो ताकि lineage एक-एक decision तक पहुँचे।

### क्या gain असली है? अपने browser में try करो

दो models उन्हीं 6,000 claims को score करते हैं, जिनमें से करीब 3% fraud हैं। Candidate बेहतर दिखता है, लेकिन bootstrap पूछता है कि क्या ये gain ऐसे ही claims वाले किसी दूसरे महीने में भी टिकेगा।

```python
import numpy as np
from sklearn.metrics import average_precision_score

rng = np.random.default_rng(7)
n = 6000                                    # one month of claims, about 3% of them fraud
y = (rng.random(n) < 0.03).astype(int)
signal = 2.5 * y + rng.normal(0, 1, n)      # the pattern both models learned
champion = signal + rng.normal(0, 0.60, n)  # each model adds its own errors
candidate = signal + rng.normal(0, 0.55, n) # slightly fewer errors

print("champion PR AUC ", round(average_precision_score(y, champion), 3))
print("candidate PR AUC", round(average_precision_score(y, candidate), 3))

gains = []
for _ in range(200):                        # resample the same claims for both models
    i = rng.integers(0, n, n)
    gains.append(average_precision_score(y[i], candidate[i]) - average_precision_score(y[i], champion[i]))
low, high = np.percentile(gains, [5, 95])
print(f"90% interval for the gain: {low:+.3f} to {high:+.3f}")
print("promote" if low > 0 else "too close to call: keep the champion")
```

ये PR AUC 0.439 के मुकाबले 0.472 print करता है, फिर भी interval करीब -0.02 से +0.07 तक जाता है: 200 से कम fraud cases पर 0.03 का gain अभी proof नहीं है। Candidate का `0.55` बदलकर `0.30` करो और फिर से run करो: अब gain इतना बड़ा है कि promote किया जा सके।

### LLM apps के लिए भी यही idea

Prompt या retrieval के बदलाव को एक experiment की तरह देखो। Prompt version, model name, top-k, chunk size और हर category के eval scores को एक run की तरह log करो। फिर "क्या prompt के version 13 से Hindi questions में मदद मिली?" एक sorted table बन जाता है, याददाश्त नहीं। यही noise rule यहाँ भी लगता है: 50 eval questions पर 2-point gain आमतौर पर chance होता है।

## एक example से समझो

Hyderabad insurer की ML team हर महीने अपना claim-fraud model retrain करती है। Tracking से पहले models `final_v3_really_final.pkl` जैसे नामों वाली files थे, और जब एक auditor ने पूछा कि production model को किस data ने train किया, तो कोई नहीं बता पाया।

अब हर run अपने parameters, commit, data snapshot और hash, और overall व हर region का validation PR AUC log करता है। नीचे के numbers सिर्फ़ समझाने के लिए हैं।

| Run | बदलाव | Val PR AUC (अपना split) | सबसे कमज़ोर region | फ़ैसला |
| --- | --- | --- | --- | --- |
| 398 | पिछले महीने का champion, v13, August data पर trained | 0.41 | 0.33 | Baseline |
| 405 | ज़्यादा गहरे trees | 0.42 | 0.31 | Drop किया: सबसे कमज़ोर region गिरा |
| 409 | नया feature: policy शुरू होने के 30 दिन के अंदर claim | 0.45 | 0.38 | उम्मीद जगाता है |
| 412 | नया feature, tuned learning rate | 0.46 | 0.39 | v14 के रूप में registered |

लुभाने वाला नतीजा है "0.46 ने 0.41 को हरा दिया, promote करो"। लेकिन run 398 को August के validation split पर score किया गया था और run 412 को September के। इसलिए gate v13 और v14 को October के 20,000 claims पर score करता है, जिनमें से करीब 600 fraud हैं:

- PR AUC: v13 0.40, v14 0.44। Gain का 90% bootstrap interval +0.02 से +0.06 है, तो gain असली है।
- Region के हिसाब से top 5% में recall: north 0.52 से 0.55, south 0.48 से 0.53, east 0.44 से 0.47, west 0.50 से 0.49। West 1 point गिरता है, जो 2-point limit के अंदर है।

Check pass हो जाता है। Fraud analytics lead report पढ़ती हैं, `promote` उनका नाम एक tag के रूप में record करता है और `champion` को v14 पर और `previous` को v13 पर खिसका देता है, और scoring service reload हो जाती है।

छह महीने बाद auditor एक disputed claim के बारे में पूछता है। Prediction log दिखाता है कि उसे v14 ने score किया था; v14 run 412, commit `a1b2c3d`, अपने hash के साथ snapshot `claims-2026-09`, और gate report की ओर point करता है। जवाब देने में कुछ मिनट लगते हैं। Spreadsheet के ज़माने में run 405 शायद अपने overall score के दम पर ship हो भी गया होता।

**Banking और lending में यही सवाल लिखित में आने की उम्मीद रखो।** August 2025 में RBI ने finance में responsible AI पर FREE-AI report publish की, जिसे उसकी बनाई एक committee ने लिखा था। उसकी recommendations में ये है कि regulated entities अपने AI models की एक inventory रखें और risk के आधार पर उनका audit करें। ये recommendations हैं, rules नहीं, लेकिन lineage, approvals और model cards वाली registry दोनों के लिए कच्चा माल है।

## आम गलतियाँ

- **Spreadsheets में हाथ से tracking करना।** ये अधूरी रहती है, पुरानी पड़ जाती है और data version कभी record नहीं करती।
- **Data के नाम को data version मान लेना।** उसी नाम से overwrite हुई file चुपचाप reproducibility तोड़ देती है; hash log करो और snapshots read-only रखो।
- **ऐसे code का commit log करना जो commit ही नहीं हुआ।** Notebook edits और uncommitted changes commit tag को झूठा बना देते हैं।
- **अलग-अलग महीनों के logged metrics compare करना।** Champion और candidate को एक ही fresh holdout पर score करो।
- **बहुत छोटे gain पर promote करना।** कुछ सौ positive cases के साथ 0.01 से 0.03 का बदलाव chance हो सकता है।
- **सिर्फ़ overall score पर promote करना।** Overall gain किसी एक region या customer group के नुकसान को छुपा सकता है।
- **Models चुनने के लिए test set को बार-बार use करना।** एक बार उस पर tune कर लिया, तो वो future को नहीं नापता।
- **हर run को register करना।** Registry experiments से भर जाती है; सिर्फ़ वही register करो जो आप शायद ship करो।
- **Production में file path load करना।** Registry alias से serve करो, एक `previous` alias रखो, और alias खिसकने पर service reload करो।
- **Integer input columns जो खाली हो सकते हैं।** Infer हुआ signature उन्हें integers mark करता है, तो serving time पर missing value schema check में fail हो जाती है; ऐसे columns के लिए floats use करो।
- **Failed runs delete करना, या एक ही laptop पर tracking करना।** Failed runs दिखाते हैं कि क्या काम नहीं करता, और एक laptop पर रखी history उसी के साथ चली जाती है।

## कब tracking हल्की हो सकती है

- **एक अकेला quick experiment**: notebook और लिखे हुए results काफ़ी हो सकते हैं।
- **सिर्फ़ prompt वाले prototypes**: prompt versions और scores की spreadsheet अच्छी शुरुआत है, जब तक एक से ज़्यादा लोग prompts बदलना शुरू न करें।
- **एक बार train हुआ और बहुत कम बदलने वाला model**: उसकी lineage एक बार, ध्यान से record करो, और फिर भी उसे registry से serve करो।

## Demo से production तक

- **एक shared tracking server चलाओ**, database backend और artefacts के लिए cloud storage के साथ, company के sign-in के पीछे, जैसे `mlflow server --backend-store-uri postgresql://... --artifacts-destination s3://...`। उसका backup रखो: ये हर model decision की history है।
- **Pipeline में tracking automatic बनाओ**, ताकि कोई run बिना log हुए हो ही न सके।
- **Promotion को code में gate करो**, उसी fresh holdout पर, noise और segment checks के साथ, फिर owner का sign-off ज़रूरी करो।
- **Alias से serve करो**, हर prediction के साथ served version log करो, और ज़रूरत पड़ने से पहले rollback की rehearsal कर लो।
- **Prompt और retrieval experiments को** training runs की तरह ही track करो।

## Practice करो

MLflow की tracking guide और Made With ML के experiment tracking और versioning lessons पढ़ो।

1. एक training script में tracking जोड़ो: parameters, per-segment metrics, एक clean commit, एक data hash, और signature के साथ model। Check करो कि uncommitted edit होने पर script run होने से मना करता है।
2. दो settings बदल-बदलकर दस experiments चलाओ और उन्हें `mlflow ui` में compare करो। ऐसा एक run ढूँढो जो overall जीतता है लेकिन किसी segment पर हारता है।
3. सबसे अच्छे दो को register करो, एक को `champion` set करो, और दूसरे के खिलाफ़ promotion check ऐसे holdout पर चलाओ जिस पर दोनों में से कोई train नहीं हुआ।
4. Promote करो, फिर roll back करो, और confirm करो कि नए सिरे से start हुआ prediction script पुराना version load करता है।

**आपका काम पूरा है जब आप** किसी एक prediction को उस model version, run, code commit और data snapshot तक trace कर सको जिसने उसे बनाया।
