## ये क्या है

**Evaluation metric** model की predictions को एक ऐसे number में बदल देता है जिसकी तुलना की जा सके। अलग-अलग metrics अलग-अलग बर्ताव को इनाम देते हैं, इसलिए चुनाव इस पर होना चाहिए कि असल use में क्या मायने रखता है।

| | Predicted positive | Predicted negative |
|---|---|---|
| **असल में positive** | True positive (पकड़ा) | False negative (छूट गया) |
| **असल में negative** | False positive (false alarm) | True negative (सही से ठीक) |

```flow
dir: LR
title: Precision और recall कहाँ से आते हैं
हर असली positive -> पकड़ा: true positives
हर असली positive -> छूटा: false negatives
हर बजाया गया alarm -> सही: true positives
हर बजाया गया alarm -> गलत: false positives
```

**Recall** = TP / (TP + FN): असली positives में से आपने कितने पकड़े। **Precision** = TP / (TP + FP): जिन्हें आपने flag किया, उनमें से कितने सही थे।

इस lesson में हम Mumbai के एक bank की तीन teams के साथ चलेंगे, जो अलग-अलग problems के लिए अलग-अलग metric चुनती हैं।

## ये कैसे काम करता है

**Classification।**

- *Accuracy*: कितने सही निकले। Balanced classes के लिए ठीक; rare events के लिए भ्रामक।
- *Precision*: जिन्हें positive कहा, उनमें कितने सही हैं। जब false alarms महँगे हों (असली payments block होना), तब ज़रूरी।
- *Recall*: असली positives में से कितने पकड़े गए। जब miss महँगा हो (छूटा fraud, छूटी बीमारी), तब ज़रूरी।
- *F1*: एक threshold पर precision और recall का संतुलन।
- *ROC AUC*: सारे thresholds पर model positives को negatives से ऊपर कितनी अच्छी तरह rank करता है; class balance से बेअसर, जो rare classes पर खराब performance को छुपा सकता है।
- *PR AUC* (average precision): positive class पर focus करता है; rare events के लिए बेहतर।
- *Log loss* और calibration: probabilities पर भरोसा किया जा सकता है या नहीं।

**Regression।**

- *MAE*: average absolute error, original units में; outliers से कम हिलता है और समझाना आसान है।
- *RMSE*: बड़ी गलतियों को ज़्यादा सज़ा देता है; जब बड़े miss खास तौर पर बुरे हों तब use करो।
- *MAPE*: percentage error; समझने में आसान पर zero के पास की values पर टूट जाता है और छोटे actuals को ज़रूरत से ज़्यादा सज़ा देता है।
- *Quantile या pinball loss*: जब आप range predict करते हो (जैसे वादे के लिए delivery time का 90th percentile)।

**Ranking और recommendation।** Precision at k, recall at k, NDCG: क्या सही items ऊपर के पास आए?

**Cost-weighted metrics।** Outcomes पर पैसे लगाओ: false positive की cost, false negative की cost, true positive की value। वो model और threshold चुनो जो expected value सबसे ज़्यादा करे। Business owners के लिए अक्सर यही सबसे साफ़ metric होता है।

**Offline metric बनाम business KPI।** Offline metric एक proxy है। A/B tests या pilots से check करो कि उसे बेहतर करने से असली KPI (losses, revenue, बचा समय) भी हिलता है।

**Segment के हिसाब से।** Metrics को ज़रूरी groups (region, भाषा, customer type) के हिसाब से report करो, ताकि वो models पकड़ में आएँ जो average में अच्छे और कुछ users के लिए खराब हैं।

**Metric को problem से मिलाना:**

| Problem | ज़्यादा बुरी गलती | Primary metric | और क्या report करें |
| --- | --- | --- | --- |
| Card fraud (rare) | छूटा fraud | PR AUC, fixed alert budget पर recall | Cost-weighted value |
| Spam filter | असली email का spam में जाना | Precision | Recall |
| बीमारी की screening | छूटी बीमारी | Recall | Precision, ताकि doctors पर बोझ न पड़े |
| Delivery time का वादा | देर से delivery | 90th percentile quantile loss | MAE |
| Sales forecast | बड़े miss | RMSE | Reporting के लिए MAE |
| Recommendations | ऊपर के irrelevant items | Precision at k, NDCG | Clicks या sign-ups पर A/B test |

**Thresholds scores को फ़ैसलों में बदलते हैं।** ज़्यादातर classifiers 0 और 1 के बीच एक score देते हैं। आप एक threshold चुनते हो, जिसके ऊपर case flag होता है। कम threshold ज़्यादा positives पकड़ता है (ऊँचा recall) पर ज़्यादा false alarms भी देता है (कम precision); ऊँचा threshold उल्टा करता है। आम तौर पर कोई एक सही threshold नहीं होता: ये इस पर निर्भर है कि हर गलती की cost क्या है और आपकी team कितने cases review कर सकती है। एक आम practical तरीका है capacity पहले तय करना, जैसे "fraud team रोज़ 300 alerts review कर सकती है", वो threshold चुनना जो लगभग 300 alerts दे, और फिर उस point पर recall report करना।

**Calibration।** अगर model 0.8 कहता है, तो क्या इसका मतलब 80% chance है? अक्सर नहीं होता। Calibrated model के scores असली frequencies से मिलते हैं: जिन cases को लगभग 0.8 score मिला, उनमें से करीब 80% positive होते हैं। Calibration तब मायने रखता है जब लोग probability के हिसाब से ही कुछ करते हैं, जैसे insurance की pricing या doctor को risk level दिखाना। इसे reliability plot से check करो, और Platt scaling या isotonic regression जैसे तरीकों से ठीक करो।

**Rare-event problem पर metrics, code में।** 2% positives वाला एक synthetic fraud जैसा dataset दिखाता है कि numbers कितने अलग बर्ताव करते हैं:

```python
import numpy as np
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import (accuracy_score, roc_auc_score, average_precision_score,
                             precision_score, recall_score, brier_score_loss)

X, y = make_classification(n_samples=20_000, n_features=12, weights=[0.98], class_sep=0.9, random_state=7)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, stratify=y, random_state=7)
p = LogisticRegression(max_iter=1000).fit(X_tr, y_tr).predict_proba(X_te)[:, 1]

print("accuracy, always 'no':", round(accuracy_score(y_te, np.zeros_like(y_te)), 3))
print("ROC AUC:", round(roc_auc_score(y_te, p), 3), " PR AUC:", round(average_precision_score(y_te, p), 3))
print("precision, recall at 0.5:", round(precision_score(y_te, p > 0.5), 3), round(recall_score(y_te, p > 0.5), 3))
print("Brier:", round(brier_score_loss(y_te, p), 4))
```

"कभी fraud नहीं" predict करने पर भी लगभग 98% accuracy मिलती है, ROC AUC तसल्ली देने वाला दिखता है, और rare class की ईमानदार कहानी PR AUC बताता है।

**Costs से threshold चुनो।** Thresholds को sweep करो और सबसे कम कुल cost वाला रखो:

```python
def best_threshold(y_true, scores, cost_fp=200, cost_fn=15_000):
    best = None
    for t in np.linspace(0.01, 0.99, 99):
        pred = scores >= t
        fp = int(((pred == 1) & (y_true == 0)).sum())
        fn = int(((pred == 0) & (y_true == 1)).sum())
        cost = fp * cost_fp + fn * cost_fn
        if best is None or cost < best[1]:
            best = (round(float(t), 2), cost, fp, fn)
    return {"threshold": best[0], "cost_inr": best[1], "false_alarms": best[2], "missed": best[3]}

print(best_threshold(y_te, p))
```

जब एक छूटा fraud, false alarm से 75 गुना महँगा हो, तो best threshold 0.5 से काफ़ी नीचे बैठता है।

**क्या फ़र्क असली है?** Interval पाने के लिए test set को bootstrap करो:

```python
def bootstrap_ci(y_true, scores, metric=average_precision_score, n=1000, seed=0):
    rng = np.random.default_rng(seed)
    vals = []
    for _ in range(n):
        idx = rng.integers(0, len(y_true), len(y_true))
        if y_true[idx].sum() == 0:
            continue
        vals.append(metric(y_true[idx], scores[idx]))
    return np.percentile(vals, [2.5, 97.5]).round(3)

print("PR AUC 95% interval:", bootstrap_ci(y_te, p))
```

अगर दो models के intervals काफ़ी overlap करते हैं, तो सिर्फ़ इस test set के आधार पर मत कहो कि एक बेहतर है।

**Range predict करना।** Delivery के वादों के लिए 90th percentile के लिए train करो और pinball loss से score करो:

```python
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.metrics import mean_pinball_loss

rng = np.random.default_rng(1)
km = rng.uniform(1, 12, 3000).reshape(-1, 1)
minutes = 10 + 3 * km[:, 0] + rng.gamma(2, 4, 3000)          # skewed delays
q90 = GradientBoostingRegressor(loss="quantile", alpha=0.9).fit(km[:2000], minutes[:2000])
pred = q90.predict(km[2000:])
print("share delivered within the promise:", round(float((minutes[2000:] <= pred).mean()), 2))
print("pinball loss:", round(mean_pinball_loss(minutes[2000:], pred, alpha=0.9), 2))
```

लगभग 90% deliveries वादे के समय के अंदर पहुँचनी चाहिए; असली data पर इलाके के हिसाब से ये हिस्सा check करो।

## एक example से समझो

Mumbai के एक bank की तीन teams:

- **Card payments पर fraud** (0.2% fraud): accuracy का कोई मतलब नहीं। वो models compare करने के लिए PR AUC use करते हैं और फिर threshold चुनने के लिए cost-weighted measure (औसत loss पर छूटा fraud बनाम हर alert पर analyst का समय)।
- **ATM में cash की demand का forecast**: cash खत्म होना ज़्यादा cash रखने से कहीं बुरा है, इसलिए वो demand का 90th percentile predict करते हैं और quantile loss से evaluate करते हैं, reporting के लिए MAE के साथ।
- **Mobile app में product recommendations**: सिर्फ़ ऊपर की तीन suggestions दिखती हैं, इसलिए वो precision at 3 use करते हैं और product sign-ups पर A/B test से confirm करते हैं।

हर team अपना metric customer segment के हिसाब से report करती है। Recommendation model metros में अच्छा और rural branches के customers के लिए खराब निकलता है; rural customers के लिए अलग feature set लगाने से काफ़ी gap भर जाता है।

**Business को चुनाव कैसे समझाएँ।** Fraud team की head को PR AUC नहीं चाहिए था; वो जानना चाहती थीं कि model bank के लिए क्या करेगा। तो team ने उसे ऐसे बदला: "रोज़ 300 alerts पर, जो आपके analysts संभाल सकते हैं, नया model हर 100 fraud cases में से लगभग 78 पकड़ता है, जो पहले 64 था। इससे हर महीने लगभग ₹1.1 करोड़ का नुकसान बचता है, analyst का कोई extra समय लगाए बिना।" Model metric ने model चुना; rupee वाले आँकड़े ने फ़ैसला कराया।

| Team | Model metric | Business में मतलब |
| --- | --- | --- |
| Fraud | PR AUC, रोज़ 300 alerts पर recall | हर महीने बचा हुआ नुकसान |
| ATM cash | 90th percentile पर quantile loss | हर महीने cash खत्म होने वाले ATMs |
| Recommendations | Precision at 3 | A/B test में extra product sign-ups |

## आम गलतियाँ

- **Imbalanced data पर accuracy।**
- **Rare events के लिए सिर्फ़ ROC AUC।** PR AUC और अपने operating point पर precision भी देखो।
- **छोटे या zero actuals के साथ MAPE।** MAE या weighted variants use करो।
- **ऐसा metric optimise करना जो KPI को नहीं हिलाता।** Pilots या A/B tests से validate करो।
- **सिर्फ़ overall numbers।** Segments भी check करो।

- **आदत से threshold चुनना।** 0.5 शायद ही कभी best threshold होता है। इसे costs और review capacity से चुनो।
- **Calibration check किए बिना scores को probabilities मान लेना।**
- **नतीजे देखने के बाद metric चुनना।** Experiment से पहले तय करो।
- **छोटे test sets पर interval न लगाना**, जिससे noise को progress बताकर report कर दिया जाता है।
- **Error costs में भारी फ़र्क होने पर भी default threshold 0.5।**

## कब सादा metric काफ़ी है

- **Balanced classes और लगभग बराबर error costs**: accuracy ठीक है और समझाना आसान।
- **शुरुआती exploration**, जहाँ एक समझदार metric से ideas जल्दी compare हो जाते हैं।
- **पूरे evaluation से पहले baseline के सामने एक quick sanity check।**

## Demo से production तक

- **Training से पहले metric, threshold और costs लिख लो**, business owner के साथ।
- **सिर्फ़ एक overall number नहीं, intervals और segment-level metrics report करो।**
- **Costs, volumes या model बदलें तो threshold दोबारा check करो।**
- **Launch के बाद offline metric के साथ business KPI भी track करो।**
- **अगर कोई probabilities के हिसाब से कदम उठाता है तो calibration monitor करो।**

## Practice करो

scikit-learn की metrics guide और precision, recall और ROC पर Google का classification module पढ़ो।

1. अपनी जानी हुई तीन problems के लिए (एक rare-event classification, एक forecast, एक ranking) primary metric चुनो और हर एक को एक वाक्य में justify करो।
2. एक imbalanced dataset पर दो models के लिए ROC AUC और PR AUC compare करो, और note करो कहाँ दोनों में असहमति है।
3. अपनी cost assumptions के साथ एक cost-weighted evaluation बनाओ और उससे threshold चुनो।
4. एक imbalanced dataset पर अपनी costs के साथ best_threshold चलाओ, फिर एक छूटे case की cost आधी करके देखो कि threshold कितना खिसकता है।

**आपका काम पूरा जब:** आप अपने metric का चुनाव business owner को rupees में और engineer को model के behaviour के हिसाब से समझा सको।
