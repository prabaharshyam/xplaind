## ये क्या है

Standard RAG वो passages निकालता है जो सवाल से मिलते-जुलते हों। दो तरह के सवाल इसे हरा देते हैं:

- **Multi-hop सवाल** जो links पर चलते हैं: "कौन-से projects का contractor वही है जो delayed Chennai metro package का है?" Facts अलग-अलग documents में हैं और कोई एक passage सवाल से मिलता-जुलता नहीं है।
- **Global सवाल** पूरे collection के बारे में: "पिछले साल की customer complaints में बार-बार आने वाली problems कौन-सी हैं?" किसी एक passage में जवाब नहीं है; वो कई से उभरता है।

**Graph RAG** एक **knowledge graph** जोड़ता है: entities (लोग, companies, products, जगहें, events) nodes की तरह, और उनके बीच के relationships edges की तरह, documents से निकाले हुए। फिर retrieval relationships पर चल सकता है और related entities के groups की पहले से लिखी summaries use कर सकता है। Microsoft का open-source GraphRAG एक जाना-माना implementation है; Neo4j जैसे graph databases दूसरा रास्ता हैं।

```flow
Documents -> Chunks -> Model entities और relationships निकालता है -> Knowledge graph
Knowledge graph -> Communities पहचानी और summarise की जाती हैं
सवाल -[local search]-> Entities + पड़ोसी + source chunks
सवाल -[global search]-> Community summaries पर map, फिर reduce
```

```flow

Project: Metro Pkg 4 | overrun 27% -[contractor]-> ABC Infra
ABC Infra -[इसमें भी]-> Project: Pune Ring Road

```

ये lesson Mumbai की एक infrastructure finance company के साथ चलता है, जिसके analysts ऐसे सवाल पूछते हैं जो सैकड़ों project documents में फैले होते हैं।

## ये काम कैसे करता है

**Indexing (GraphRAG style)।**

1. Documents को हमेशा की तरह chunk करो।
2. हर chunk से entities और relationships निकालने के लिए model use करो, छोटे descriptions के साथ ("ABC Infra, contractor; Package 4 के लिए steel supply करता है")।
3. Duplicates merge करो ("ABC Infra Ltd" और "ABC Infrastructure")।
4. **Communities** पहचानो: आपस में गहराई से जुड़ी entities के clusters।
5. Model से हर community की summary लिखवाओ, कई स्तरों के detail पर।

**Querying।**

- *Local search* किसी specific entity के सवालों के लिए: सवाल में आई entities ढूँढो, उनके पड़ोसी, relationships और source chunks इकट्ठा करो, और उसी से answer दो।
- *Global search* पूरे collection के सवालों के लिए: सवाल को community summaries पर map करो, फिर आंशिक answers को reduce करके एक बना दो।

**Costs।** Indexing हर chunk और हर community पर model call करती है, इसलिए ये सिर्फ़ embedding से कई गुना महँगी हो सकती है, और documents बदलने पर इसे दोबारा चलाना या update करना पड़ता है। Entity extraction गलतियाँ करता है; merges ऐसी चीज़ें जोड़ सकते हैं जो अलग रहनी चाहिए थीं। Queries, खासकर global वाली, बहुत tokens खाती हैं।

**कब फ़ायदेमंद है।** ऐसे collections जिनमें entities और relationships भरे हों (contracts, investigations, research literature, supplier networks, case files), जहाँ multi-hop या global सवाल अक्सर आते हैं और कीमती हैं। ज़्यादातर FAQ-style या policy-lookup assistants के लिए अच्छी metadata के साथ hybrid search सस्ता और काफ़ी है।

**हल्के विकल्प।** निकाली गई entities को metadata की तरह रखो और उन पर filter करो; key relationships की एक छोटी structured table रखो; documents के groups की summaries बनाओ। अक्सर इनसे ज़्यादातर फ़ायदा मिल जाता है।

**Standard RAG बनाम Graph RAG:**

| पहलू | Hybrid RAG | Graph RAG |
| --- | --- | --- |
| एक-document वाले सवाल | मज़बूत | बेहतर नहीं |
| Multi-hop सवाल | कमज़ोर | मज़बूत |
| पूरे collection के सवाल | कमज़ोर | Community summaries के साथ मज़बूत |
| Indexing cost | सिर्फ़ embeddings | हर chunk और community पर model calls |
| Updates | बदले हुए chunks दोबारा embed करो | दोबारा extract और दोबारा merge |
| Failure का risk | छूटे हुए passages | गलत extractions और merges |

**दोनों के बीच routing।** कम teams hybrid RAG को बदलती हैं; वो उन सवालों के लिए graph जोड़ती हैं जिनका वो जवाब नहीं दे सकता। एक छोटा classifier, या एक model call, तय करता है कि सवाल entities के बीच relationships का ज़िक्र करता है ("कौन-से contractors भी काम करते हैं...", "और कौन जुड़ा है...") या पूरे collection के बारे में है ("बार-बार आने वाली... कौन-सी हैं"). वो graph search पर जाते हैं; बाकी सब hybrid RAG पर। हर सवाल का route log करो, ताकि test set पर router की गलतियाँ जाँच सको।

**Citations बनाए रखना।** हर entity, relationship और community summary को उन chunks के links रखने चाहिए जहाँ से वो आई। तब answers असली documents को cite कर सकते हैं, और analysts जाँच सकते हैं कि कोई निकाला हुआ relationship सच में लिखा था या extraction में गढ़ लिया गया।

**Code में एक छोटा graph।** Model से triples निकालो (structured output की तरह), उन्हें NetworkX में load करो, और local सवालों के जवाब पड़ोस से दो:

```python
import networkx as nx
from pydantic import BaseModel

class Triple(BaseModel):
    subject: str
    relation: str
    object: str

class Extraction(BaseModel):
    triples: list[Triple]

def normalise(name):
    n = name.lower().replace("limited", "ltd").replace("infrastructure", "infra")
    return " ".join(w for w in n.replace(".", "").split() if w not in {"ltd", "pvt", "private"})

def build_graph(chunks, extract):
    """extract(text) -> Extraction, via structured output from a model."""
    g = nx.MultiDiGraph()
    for c in chunks:
        for t in extract(c["text"]).triples:
            s, o = normalise(t.subject), normalise(t.object)
            g.add_node(s, label=t.subject); g.add_node(o, label=t.object)
            g.add_edge(s, o, relation=t.relation, source=c["id"])
    return g

def local_context(g, entities, hops=2, limit=40):
    nodes = set()
    for e in map(normalise, entities):
        if e in g:
            nodes |= set(nx.ego_graph(g.to_undirected(as_view=True), e, radius=hops))
    facts = [f'{g.nodes[u]["label"]} —{d["relation"]}→ {g.nodes[v]["label"]} [{d["source"]}]'
             for u, v, d in g.subgraph(nodes).edges(data=True)]
    return facts[:limit]
```

Facts अपने source chunk ids साथ रखते हैं, इसलिए answer असली documents को cite कर सकता है। `normalise` के rules entity resolution की एक कच्ची शुरुआत हैं; ज़रूरी entities के merges हाथ से check करो, और उन नामों की एक list रखो जिन्हें कभी merge नहीं करना।

**Global सवालों के लिए communities।** आपस में गहराई से जुड़ी entities को group करो और हर group को एक बार summarise करो:

```python
from networkx.algorithms.community import louvain_communities

def communities(g, seed=7):
    groups = louvain_communities(g.to_undirected(), seed=seed)
    return sorted(groups, key=len, reverse=True)
```

Model हर community की summary लिखता है (उन chunk ids के साथ जिन पर वो आधारित है)। "सभी packages में delay की बार-बार आने वाली वजहें कौन-सी हैं?" के लिए, हर community summary से वो सवाल पूछो, फिर आंशिक answers को मिला दो।

**Graph पर भरोसा करने से पहले extraction check करो।** 50 निकाले हुए triples का sample लो और हर एक को mark करो: source में लिखा है, implied है, या गलत है। अगर कुछ प्रतिशत से ज़्यादा गलत हैं, तो उसके ऊपर कुछ बनाने से पहले extraction prompt सुधारो (allowed entity types और relations दो)।

**पहले indexing का बिल अंदाज़ो।** Chunks × (extraction prompt + chunk + output tokens) गिनो, साथ में हर community के लिए एक summary call। पूरे collection पर लगाने से पहले उसके 5% पर चलाओ, नापो, और गुणा करो।

## एक example से समझो

Mumbai की एक infrastructure finance company हज़ारों project reports, contractor agreements और site inspection notes review करती है। Analysts ऐसे सवाल पूछते हैं: "कौन-से contractors उन projects में आते हैं जिनमें cost overrun 20% से ऊपर है, और वो और कहाँ काम करते हैं?"

Hybrid RAG एक-project वाले सवाल अच्छे से संभालता है पर ये नहीं: facts सैकड़ों documents में फैले हैं।

एक pilot 3,000 documents से projects, contractors, sub-contractors, locations और inspection findings का graph बनाता है। Indexing की cost सिर्फ़-embedding वाली pipeline से करीब 25 गुना है, एक बार की cost और साथ में हफ़्तेवार updates। Entity merging के लिए company name variants की हाथ से बनी list चाहिए, क्योंकि एक ही contractor कई spellings में दिखता है।

Multi-hop और global सवालों के 40-सवाल वाले test set पर graph approach 70% अच्छे से जवाब देता है, जबकि hybrid RAG 30%। एक-document वाले सवालों पर वो बेहतर नहीं है। कंपनी दोनों रखती है: जब सवाल projects के बीच relationships का ज़िक्र करे तो graph search पर route होता है, वरना hybrid RAG पर।

| नाप | Hybrid RAG | Graph approach |
| --- | --- | --- |
| 40 में से multi-hop और global सवाल जो अच्छे से answer हुए | 30% | 70% |
| एक-document वाले सवाल | अच्छा | बेहतर नहीं |
| Indexing cost | Baseline | करीब 25 गुना, साथ में हफ़्तेवार updates |
| अतिरिक्त काम | कोई नहीं | Contractor name variants की हाथ से बनी list |

## आम गलतियाँ

- **सादे lookups के लिए Graph RAG।** ये बिना फ़ायदे के cost जोड़ता है।
- **Entity resolution को नज़रअंदाज़ करना।** Duplicate या गलत merge हुई entities हर उस answer को बिगाड़ देती हैं जो उन्हें use करता है।
- **Updates भूल जाना।** एक बार बना graph पुराना पड़ जाता है।
- **कोई comparison नहीं।** जो सवाल मायने रखते हैं उन पर hybrid RAG के सामने नापो।
- **Citations खो देना।** Entities और summaries से वापस source chunks तक links रखो।
- **निकाले हुए relationships पर बिना source text से sample किए भरोसा करना।**
- **Free-form relation names।** Extractor को fixed list दो, वरना graph मिलते-जुलते duplicates से भर जाता है।
- **पूरे collection को index करने से पहले cost का अंदाज़ा न लगाना।**

## Graph RAG कब फ़ायदेमंद नहीं है

- **सवाल ज़्यादातर एक document या एक fact के बारे में हैं**: hybrid RAG उन्हें सस्ते में संभाल लेता है।
- **Documents लगातार बदलते हैं**, जिससे दोबारा extraction महँगा पड़ता है।
- **कम entities और relationships मायने रखते हैं**: लोगों की बनाई key facts की एक छोटी table काफ़ी हो सकती है।
