## ये क्या है

Calculator को test करना आसान है: 2 + 2 हमेशा 4 होना चाहिए। Emails, summaries या explanations लिखने वाले AI को test करना मुश्किल है, क्योंकि कई अच्छे answers होते हैं। ये lesson ऐसे answers पर number लगाने के मुख्य तरीके बताता है, और ये भी कि कौन-सा कब फिट बैठता है।

चार families हैं, सबसे exact से कम exact तक:

1. **Functional correctness.** क्या output काम करता है? Generate किया code अपने tests pass करता है, generate की गई SQL query सही rows देती है, extract किया invoice total ledger से मेल खाता है।
2. **Exact match.** क्या answer reference जैसा ही है? Numbers, dates, labels और multiple-choice letters के लिए अच्छा है।
3. **Reference से similarity.** Answer एक जाने-माने अच्छे answer से कितना क़रीब है, **शब्दों** में (lexical similarity, जैसे BLEU और ROUGE) या **मतलब** में (semantic similarity, embeddings से)?
4. **Judgement.** कोई इंसान या judge model answer को rate करता है, अकेले (5 में से score) या किसी दूसरे answer के सामने (**pairwise comparison**)। LLM judges वाला lesson judge prompts को गहराई से बताता है।

```flow
title: Answer को कैसे score करें, ये चुनना
Score करने वाला answer -> क्या आप इसे run या test कर सकते हो? | code, SQL, schema
क्या आप इसे run या test कर सकते हो? -[हाँ]-> Functional check | सबसे भरोसेमंद
क्या आप इसे run या test कर सकते हो? -[नहीं]-> क्या एक ही सही छोटा answer है? | number, label, date
क्या एक ही सही छोटा answer है? -[हाँ]-> Exact match
क्या एक ही सही छोटा answer है? -[नहीं]-> क्या अच्छे reference answers हैं?
क्या अच्छे reference answers हैं? -[हाँ]-> Meaning similarity या reference के साथ judge
क्या अच्छे reference answers हैं? -[नहीं]-> Rubric के साथ judge
Meaning similarity या reference के साथ judge -> क्या दो systems में से चुन रहे हो? -[हाँ]-> Side-by-side comparison
```

## ये काम कैसे करता है

**Functional correctness.** अगर आप उसे execute या test कर सकते हो, तो सबसे पहले वही करो। Code assistant को unit tests चलाकर score किया जाता है। Text-to-SQL feature generate की गई और reference, दोनों queries को एक test database पर चलाकर results compare करता है। Extraction feature fields को system of record से check करता है। और कुछ भी इतना भरोसेमंद नहीं है। OpenAI ने पाया कि एक coding benchmark पर सही और गलत solutions के word-overlap scores लगभग एक जैसे थे, इसलिए सिर्फ़ code चलाने से ही फ़र्क पता चला।

**Exact match**, सावधानी से। पहले normalise करो: lowercase, spaces trim, number formats एक जैसे। उन answers से सावधान रहो जिनमें सही value गलत answer के अंदर हो: "Born on 12 September 1929" में "1929" है, पर अगर असली date 12 June है तो ये गलत है। Labels के लिए पूरा वाक्य नहीं, label field compare करो।

**Lexical similarity.** दोनों texts को शब्दों या शब्दों के जोड़ों में बाँटकर overlap गिना जाता है। BLEU (machine translation से) और ROUGE (summarisation से) सबसे जाने-माने versions हैं। एक जुड़ा idea है **edit distance**, जो गिनता है कि एक string को दूसरी में बदलने के लिए कितने अक्षर बदलने पड़ेंगे, नामों और codes के लिए काम का है।

आज के models के लिए इनकी कमज़ोरियाँ गंभीर हैं:

- अलग शब्दों में दिया सही answer कम score पाता है। "How is it going?" में "How are you?" से बहुत कम शब्द मिलते हैं।
- Reference के शब्द copy करने वाला गलत answer ज़्यादा score पाता है। "Let's eat, grandma" और "Let's eat grandma" शब्दों के हिसाब से लगभग एक जैसे हैं।
- References में अच्छे answers छूट सकते हैं, या वो सीधे गलत हो सकते हैं।

फिर भी ये सस्ते smoke alarms की तरह मदद करते हैं, जैसे ये पकड़ने के लिए कि template बदलने से हर reply टूट गया।

**Semantic similarity.** Answer और reference को embeddings में बदलो और -1 से 1 तक cosine similarity से compare करो। Paraphrases को ऊँचा score मिलता है। बड़े scale पर ये सस्ती है, लेकिन score embedding model पर निर्भर है, ये "refund approved" और "refund rejected" को क़रीब बता सकती है, और सही threshold लोगों के judgements से मिलाकर ही तय करना होता है।

```python
import numpy as np

def cosine(a, b):
    a, b = np.asarray(a), np.asarray(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

def score(answer, reference, embed, must_include=()):
    """embed(text) returns a vector. must_include holds facts that need an exact check."""
    facts_ok = all(f.lower() in answer.lower() for f in must_include)
    return {"facts_ok": facts_ok, "meaning": round(cosine(embed(answer), embed(reference)), 3)}

# score(draft, agent_reply, embed, must_include=["ORD-48213", "₹2,499"])
```

Pattern देखो: जिन facts का सही होना ज़रूरी है उनके लिए exact checks, wording के लिए similarity।

**Pairwise comparison.** दो गानों में से कौन-सा पसंद है ये बताना, हर एक को 10 में से score देने से आसान है। Answers के लिए भी यही सच है। एक ही सवाल के दो answers random order में, बिना labels के दिखाओ, और पूछो कौन-सा बेहतर है, tie की भी इजाज़त दो। Wins गिनो। कई models हों तो Elo या Bradley–Terry जैसे ranking methods wins को league table में बदल देते हैं; public arenas इसी तरह लाखों votes से chatbots को rank करते हैं।

दो limits मायने रखती हैं:

- **Preference का मतलब correctness नहीं है।** अगर voter को सही answer नहीं पता, जैसे maths result या medical fact, तो वो आत्मविश्वास से कहे गलत answer को पसंद कर सकता है। Style और helpfulness पर vote कराओ; facts अलग से check करो।
- **इसमें बहुत सारी comparisons लगती हैं**, और models जोड़ने पर pairs की संख्या तेज़ी से बढ़ती है। दो prompts या दो models के बीच product का फ़ैसला करने के लिए, आपके अपने सवालों पर 100 से 300 side-by-side comparisons आमतौर पर काफ़ी होती हैं।

| Method | किसके लिए सबसे अच्छा | Cost | मुख्य risk |
| --- | --- | --- | --- |
| Functional check | Code, SQL, extraction, formats | बनने के बाद कम | ऐसे tests जो cases छोड़ देते हैं |
| Exact match | Numbers, labels, छोटे facts | बहुत कम | गलत answer के अंदर सही value |
| Lexical (BLEU, ROUGE) | Smoke tests, translation drift | बहुत कम | शब्द copy करने को इनाम, मतलब को नहीं |
| Semantic similarity | Reference वाले paraphrased answers | कम | उल्टे facts को भी क़रीबी score |
| Rubric के साथ judge | बिना reference का open text | मध्यम | Judge bias; लोगों से मिलाकर check करो |
| Pairwise comparison | दो systems में से चुनना | मध्यम से ज़्यादा | Preference को correctness समझ लेना |

## एक example से समझो

Delhi के एक electronics retailer का एक assistant है जो customer emails के replies Hindi और English में draft करता है। हर reply में सही order number और refund amount बताना है और विनम्रता से ख़त्म करना है। Team 300 पुराने emails और उनके best agents के replies से prompt A (मौजूदा) को prompt B (नया) से compare करना चाहती है।

वो पहले agents के replies के सामने ROUGE try करते हैं। Prompt A को 0.41 और prompt B को 0.33 मिलता है, जिससे लगता है B ख़राब है। Drafts पढ़ने पर कहानी अलग निकलती है: B छोटी, साफ़ Hindi लिखता है जो agents के लंबे replies से कम शब्द share करती है।

तो वो तीन layers में score करते हैं:

| Layer | Prompt A | Prompt B |
| --- | --- | --- |
| Order number और refund amount सही (order system से exact check) | 94% | 97% |
| Agent के reply के मतलब के क़रीब (cosine 0.80 से ऊपर) | 88% | 90% |
| दो senior agents के judge किए side-by-side wins, 150 emails, ties allowed | 38% | 51% (11% ties) |
| Agent के reply के सामने ROUGE-L | 0.41 | 0.33 |

Numbers सिर्फ़ समझाने के लिए हैं। B facts और preference दोनों में जीतता है, और सिर्फ़ word overlap में हारता है, जिसे वो dashboard से हटा देते हैं। Exact checks हर release पर चलते रहते हैं।

## आम गलतियाँ

- **Chat, summaries या explanations के लिए BLEU या ROUGE को मुख्य quality score बनाना।**
- **Similarity score से facts check करवाना।** "Approved" और "rejected" क़रीब दिख सकते हैं। मुख्य facts exact check करो।
- **जिन सवालों के सही answers हैं उन पर vote कराना।** Preference ये बताती है कि लोगों को क्या पसंद है, ये नहीं कि सच क्या है।
- **Answers हमेशा एक ही क्रम में दिखाना।** लोग और judges पहले या लंबे answer को पसंद करते हैं। Order randomise करो और एक जैसी लंबाई के answers compare करो।
- **ऐसे threshold पर भरोसा करना जिसे किसी ने जाँचा नहीं।** Similarity thresholds एक sample पर इंसानी judgements से मिलाकर चुनो।
- **सब कुछ के लिए एक ही number।** ज़्यादातर products को कुछ scores चाहिए: facts, format, meaning, preference।

## कब सादा रखें

- **Closed tasks:** classification, extraction और routing को exact checks और precision, recall से score करो। Similarity या judges की ज़रूरत नहीं।
- **शुरुआती prototypes:** कोई भी metric बनाने से पहले 30 answers ख़ुद पढ़ो।
- **दुर्लभ high-stakes answers:** legal या medical outputs को, scores जो भी कहें, expert review चाहिए।

## Demo से production तक

- **Scores को layers में रखो:** हर response पर exact checks, एक sample पर judge या similarity, releases के लिए side-by-side comparison।
- **References को test set के साथ version करो**, और गलत मिलने पर ठीक करो।
- **हर कुछ महीनों में metrics को लोगों से फिर मिलाकर check करो**, क्योंकि जो metric इंसानी judgement से दूर होता जाता है, वो बिना metric से भी बुरा है।
- **Scores segment के हिसाब से report करो:** भाषा, topic, लंबाई। कुल मिलाकर सुधार, Hindi replies में आई गिरावट छिपा सकता है।
