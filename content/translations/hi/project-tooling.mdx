## ये क्या है

जो code आपके laptop पर चलता है, वो शुरुआत है, अंत नहीं। **Project tooling** आपके code के आसपास की वो हर चीज़ है जिससे कोई और उसे चला सके, safely बदल सके और रात 2 बजे debug कर सके। हर हिस्सा उस एक सवाल का जवाब देता है जो कोई अनजान पूछेगा:

| अनजान पूछता है | जवाब देने वाली file या tool | इसके बिना |
| --- | --- | --- |
| कौन-सा Python और कौन-से packages? | `pyproject.toml`, `uv.lock`, `.python-version` | "मेरी machine पर तो चलता है" |
| Code कहाँ है और उसे import कैसे करूँ? | `.venv` में install किया हुआ एक `src` layout | Imports जो सिर्फ़ एक folder से चलते हैं |
| क्या मेरे change ने कुछ तोड़ा? | pytest tests | Bugs जो users ढूँढते हैं |
| क्या ये code साफ़-सुथरा है और obvious गलतियों से बचा है? | ruff | हर review में style पर बहस |
| API key कहाँ जाती है? | `.env` (ignored) और `.env.example` (committed) | Git में leak हुई keys |
| Production में क्या हुआ? | एक बार configure की हुई `logging` | अंदाज़ा |
| क्या ये clean machine पर भी चलता है? | हर push पर CI | "मेरे laptop पर तो pass हुआ था" |
| सबसे पहले क्या type करूँ? | Exact commands वाला README | आपको एक WhatsApp message |

इसमें कुछ भी glamorous नहीं है। पर इनमें से हर चीज़ की कमी नज़र आती है, आमतौर पर client के engineer को, आपके handover के अगले हफ़्ते।

ये lesson एक invoice extractor के साथ चलता है जो आपने Coimbatore के एक textile exporter के लिए बनाया, जब उनका engineer Karthik उसे संभालता है। इसमें **uv** use होता है, Astral का एक fast tool जो environment बनाता है, packages install करता है, lock file लिखता है और Python खुद भी install कर सकता है। Plain `venv` और `pip` भी चलते हैं; हर section फ़र्क दिखाता है।

```flow
title: Clone से भरोसेमंद change तक
dir: LR
Repository clone करो -> Locked versions install करो | uv sync
Locked versions install करो -> Secrets डालो | .env.example को .env में copy करो
Secrets डालो -> Lint और test | ruff और pytest
Lint और test -> Code बदलो
Code बदलो -> Push
Push -> CI clean machine पर checks दोहराता है
```

## ये काम कैसे करता है

### Layout

```text
invoice-extractor/
  pyproject.toml          # what the project is and needs
  uv.lock                 # exact versions of everything (commit it)
  .python-version         # the Python version the team uses
  .gitignore              # .venv, .env, __pycache__
  .env.example            # variable names, no real values
  README.md
  .github/workflows/ci.yml
  src/invoice_extractor/
      __init__.py
      cli.py              # entry point: configures logging, builds the client
      extract.py
      models.py
      llm.py              # the real model client
  tests/
      conftest.py         # shared fixtures, including a fake model client
      test_extract.py
      fixtures/sample_invoice.txt
```

`uv init --package invoice-extractor` इसका ज़्यादातर हिस्सा आपके लिए बना देता है, जिसमें एक `src` folder, एक `.python-version` और एक git repository शामिल हैं।

### pyproject.toml

ये रही एक पूरी file, जैसी हमने uv 0.13.10, pytest 9.2.0 और ruff 0.17.6 के साथ चलाई (28 November 2026 तक की सबसे नई releases):

```toml
[project]
name = "invoice-extractor"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pydantic>=2.10",
]

[project.scripts]
invoice-extractor = "invoice_extractor.cli:main"

[dependency-groups]
dev = ["pytest>=9.0", "ruff>=0.17"]

[build-system]
requires = ["uv_build>=0.13.10,<0.14.0"]
build-backend = "uv_build"

[tool.pytest]
testpaths = ["tests"]
addopts = ["-ra", "--strict-markers"]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```

हर हिस्सा क्या करता है:

- **`[project]`** package का नाम रखता है और बताता है कि चलने के लिए उसे क्या चाहिए। यहाँ ranges (`>=2.10`) use करो, exact pins नहीं; exact versions lock file रखती है।
- **`[project.scripts]`** एक command बनाता है, तो `uv run invoice-extractor` `cli.py` में `main()` को call करता है।
- **`[dependency-groups]`** में वो tools होते हैं जो सिर्फ़ developers को चाहिए। `uv sync` default रूप से `dev` group install करता है; `uv sync --no-dev` उसे production image से बाहर रखता है।
- **`[build-system]`** बताता है कि `src/` को installable package कैसे बनाना है। इसके बिना uv folder को scripts का एक ढीला collection मानता है और आपका package install नहीं करता।
- **`[tool.pytest]`** pytest 9 में जुड़ी native TOML table है। पुराने pytest पर, उन्हीं keys के साथ `[tool.pytest.ini_options]` use करो।

**Python pin करना।** `requires-python` वो range है जिसे support करने का आप वादा करते हो। `.python-version` वो एक version है जो सब लोग, CI समेत, असल में use करते हैं; न हो तो uv उसे download कर लेता है। Python 3.15 9 October 2026 को आया, पर पहले ही दिन move करना ज़रूरी नहीं: `.python-version` बढ़ाने से पहले check करो कि आपकी भारी libraries नए version के लिए wheels publish करती हैं, फिर CI को साबित करने दो।

### src layout, और install वाला step जो सब भूल जाते हैं

Code `src/` में हो तो Python `invoice_extractor` को सिर्फ़ इसलिए import नहीं कर सकता कि आप project folder में खड़े हो। यही तो point है: tests आपके package तक वैसे ही पहुँच सकते हैं जैसे कोई user, यानी install के ज़रिए। Package में कोई file छूट जाए, या `pyproject.toml` में कोई गलत setting हो, तो वो client के server पर नहीं, आपके laptop पर ही दिख जाती है।

इसका नतीजा लगभग हर beginner को अटका देता है। अगर package install नहीं है, तो tests शुरू होने से पहले ही fail हो जाते हैं:

```text
E   ModuleNotFoundError: No module named 'invoice_extractor'
```

`uv sync` project को `.venv` में **editable** mode में install करता है, तो आपके edits बिना reinstall किए असर करते हैं। Plain pip के साथ यही हाथ से करो: एक venv बनाओ और activate करो, फिर `pip install -e . --group dev` चलाओ (`--group` के लिए pip 25.1 या उसके बाद का version चाहिए)। `PYTHONPATH` में `src` जोड़कर या `conftest.py` में `sys.path` hacks डालकर error को "fix" मत करो; इससे layout की दी हुई सुरक्षा ही हट जाती है।

### Lock files और --locked

`uv add httpx` एक ही step में range को `pyproject.toml` में जोड़ता है और `uv.lock` update करता है। Lock हर package का exact version और file hash record करती है, उन packages समेत जिन पर आपके packages depend करते हैं। जो भी application या service आप deploy करते हो, उसके लिए इसे commit करो। दूसरों के लिए publish की गई library `pyproject.toml` में फिर भी ढीली ranges रखती है, ताकि अपने users पर versions न थोपे, पर अपने CI के लिए उसकी lock commit करना फिर भी काम का है।

CI, Dockerfiles और README में `uv sync --locked` से install करो। अगर किसी ने `pyproject.toml` हाथ से edit की और `uv lock` चलाना भूल गया, तो ये तुरंत रुक जाता है:

```text
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
  cause: Requirements for `invoice-extractor==0.1.0` differ; added: httpx>=0.28
```

Plain `uv sync` इसकी जगह चुपचाप lock को दोबारा लिख देता, और जो versions आप test करते हो वो उन versions से भटक जाते जो आप ship करते हो। Upgrade जानबूझकर करो, एक बार में एक package: `uv lock --upgrade-package pydantic`, tests चलाओ, दोनों files commit करो। pip में lock के बराबर pip-tools जैसे tool से बनी fully pinned requirements file होती है; `pip freeze` भी चलता है पर उसमें वो सब भी मिल जाता है जो संयोग से install पड़ा हो।

### ruff से lint और format

**Ruff** एक fast tool है जो दो काम करता है। `ruff check` एक **linter** है: ये संभावित bugs और खराब patterns ढूँढता है। `ruff format` एक **formatter** है: ये spacing और line breaks को एक house style में दोबारा लिखता है, ताकि reviews commas पर नहीं, logic पर हों।

```text
uv run ruff check --fix    # find problems, fix the safe ones
uv run ruff format         # rewrite layout
```

ruff 0.16 से default set बड़ा है: कई groups से 400 से ज़्यादा rules। एक `select` line उस default को हटाकर ठीक उन्हीं groups को रखती है जिनके नाम आप लेते हो। ऊपर वाली line उससे छोटा, predictable set देती है: `E` और `F` (pycodestyle और Pyflakes), `I` (sorted imports), `B` (bugbear: आम bug patterns जैसे mutable default argument) और `UP` (आपके Python version के लिए नया, आसान syntax)। Rule groups एक-एक करके जोड़ो; पुराने codebase पर सब कुछ एक साथ चालू करने से सैकड़ों warnings आती हैं और team linter ही बंद कर देती है।

### Secrets और settings

Code secrets को environment variables से पढ़ता है, और कहीं से नहीं:

```python
client = ModelClient(api_key=os.environ["MODEL_API_KEY"])
```

अगर variable नहीं है, तो ये start-up पर ही `KeyError: 'MODEL_API_KEY'` raise करता है, जो पहले invoice पर आने वाली उलझी हुई failure से कहीं बेहतर है। Local पर values एक `.env` file में रखो और `uv run --env-file .env` से load करो। एक `.env.example` commit करो जिसमें नाम हों और असली values न हों:

```text
MODEL_API_KEY=
LOG_LEVEL=INFO
```

अपनी `.gitignore` check करो: `uv init` जो लिखता है वो `.venv` को cover करती है पर `.env` को नहीं, तो उसे खुद जोड़ो और `git check-ignore .env` से confirm करो। अगर कभी कोई असली key किसी commit में पहुँच जाए, तो बाद के commit में file delete करने से कुछ नहीं होता, क्योंकि वो git history में रहती है। पहले key revoke और rotate करो, फिर सफ़ाई करो।

### Logging

Logging **एक बार**, entry point पर configure करो, और कहीं नहीं:

```python
# cli.py
import logging
import os


def main() -> None:
    logging.basicConfig(
        level=os.environ.get("LOG_LEVEL", "INFO").upper(),
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
    )
```

बाकी हर module बस अपने नाम का एक logger माँगता है और ऐसे facts log करता है जिन पर कोई अनजान action ले सके:

```python
# extract.py
log = logging.getLogger(__name__)

log.warning(
    "invoice=%s field=total model_value=%r error=%s",
    data.get("id"),
    data["total"],
    err,
)
```

Values को arguments की तरह pass करो, जैसे ऊपर, f-string बनाने की जगह; तब logging module सिर्फ़ उन्हीं messages को format करता है जो वो असल में emit करता है। अगर आपका log platform JSON fields में search कर सकता है, तो format को हर line पर एक JSON object कर दो; ids, fields और timings log करने की आदत वही रहती है। किसी command के असली output के लिए, जैसे extract किया हुआ JSON, `print` अब भी ठीक है; program क्या कर रहा है इसके messages के लिए ये गलत है।

| Level | किसके लिए | Production में |
| --- | --- | --- |
| DEBUG | Developers के लिए detail: prompts, raw replies | Off |
| INFO | आम events: एक file process हुई, उसकी duration के साथ | On |
| WARNING | अजीब पर संभाल लिया गया: एक retry जो सफल रहा, एक bad input जो skip हुआ | On |
| ERROR | कुछ fail हुआ और किसी इंसान की ज़रूरत है | On, और alerts |

API keys, passwords, पूरे documents या personal data, जैसे customer phone numbers या PAN numbers, कभी log मत करो। उनकी जगह ids, sizes और timings log करो।

### Tests, और एक fake model client

pytest खुद, fixtures, parametrised tests और mocking "Writing tests with pytest" lesson (B3) में हैं। Project structure के लिए ज़रूरी ये है कि चीज़ें कहाँ रहती हैं। Shared fixtures `tests/conftest.py` में जाते हैं, जिसे pytest अपने आप load करता है। जो code model को call करता है, उसके लिए सबसे साफ़ design client को अंदर pass करना है, ताकि test उसे एक fake दे सके:

```python
# tests/conftest.py
import json
from pathlib import Path

import pytest

FIXTURES = Path(__file__).parent / "fixtures"


class FakeModelClient:
    """Returns a fixed reply and records each prompt. No network, no cost."""

    def __init__(self, reply: dict):
        self.reply = json.dumps(reply)
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply


@pytest.fixture
def sample_invoice() -> str:
    return (FIXTURES / "sample_invoice.txt").read_text(encoding="utf-8")


@pytest.fixture
def fake_client() -> FakeModelClient:
    return FakeModelClient(
        {
            "id": "INV-0001",
            "gstin": "33ABCDE1234F1Z5",
            "total": "1500.00",
            "items": [
                {"description": "Cotton yarn", "amount": "1000.00"},
                {"description": "Dyeing", "amount": "500.00"},
            ],
        }
    )
```

ये unit tests आपका अपना logic check करते हैं और हर push पर एक second से काफ़ी कम में चल जाते हैं। असली model के जवाबों को परखना अलग काम है, जो असली, labelled examples के एक fixed set पर evaluation run से होता है; "Test sets and evals" lesson (P1) 30 से 100 cases से शुरू करने का सुझाव देता है।

### हर push पर CI

CI (continuous integration) हर push और pull request पर एक clean machine पर वही checks चलाता है, तो "मेरे laptop पर pass हुआ था" कोई दलील नहीं रह जाती। एक पूरा GitHub Actions workflow:

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.4.0
      - run: uv sync --locked
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run pytest
```

uv `.python-version` पढ़ता है और runner पर वही Python install करता है। एक gotcha: `setup-uv` की नई releases के लिए `@v10` जैसा कोई short tag नहीं है, तो पूरा version लिखो (या, और सख़्ती से, commit hash)। Branch protection चालू करो ताकि CI red होने पर कोई pull request merge न हो सके।

### README

अच्छा README किसी अनजान को आपसे कुछ भी पूछे बिना clone से passing tests तक पहुँचा देता है:

```text
git clone <repository-url> && cd invoice-extractor
uv sync --locked
cp .env.example .env          # then put your own key in .env
uv run pytest
uv run --env-file .env invoice-extractor tests/fixtures/sample_invoice.txt
```

इसे लिखो, फिर `/tmp` में एक fresh clone में खुद follow करो। ज़्यादातर READMEs दूसरी line पर ही टूट जाते हैं।

## एक example से समझो

आपने Coimbatore के exporter के लिए invoice extractor बनाया। अगले महीने Karthik को इसे आपके बिना चलाना और संभालना है।

**पहला दिन।** वो repository clone करता है और README follow करता है। `uv sync --locked` ठीक वही versions install करता है जो आपने test किए थे, और `uv run pytest` 12 passed बताता है। बारह में से दो tests:

```python
import pytest
from pydantic import ValidationError

from invoice_extractor.extract import parse_amount, parse_invoice
from invoice_extractor.models import Invoice


def test_total_matches_line_items(sample_invoice, fake_client):
    inv = parse_invoice(sample_invoice, client=fake_client)
    assert inv.total == sum(i.amount for i in inv.items)
    assert "Cotton yarn" in fake_client.prompts[0]


def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValidationError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

पहला test `parse_invoice` को `conftest.py` वाला fake client देता है, तो ये बिना network call के parsing logic check करता है और ये भी कि invoice का text prompt तक पहुँचा। GSTIN हमेशा 15 characters का होता है, और `Invoice` model 11 characters वाले को reject कर देता है।

**एक महीने बाद।** Production में एक invoice fail होता है। Log line ये है:

```text
2026-12-18 10:14:03,512 WARNING invoice_extractor.extract invoice=INV-8812 field=total model_value='12,40,000.00' error=not a number
```

Karthik तुरंत समझ जाता है कि क्या हुआ। Model ने total को Indian digit grouping (12 lakh 40 thousand) के साथ copy किया, और `parse_amount` ने सीधे `Decimal(value)` call किया, जो commas reject करता है। हर test pass हुआ क्योंकि fake reply में `"1500.00"` था, ऐसा format जो असली invoices में कभी था ही नहीं। वो तीन steps में काम करता है:

1. **Reproduce.** वो एक test जोड़ता है जो किसी भी fix से पहले fail होता है:

```python
def test_reads_indian_digit_grouping():
    assert str(parse_amount("12,40,000.00")) == "1240000.00"
```

2. **Fix.** वो एक line बदलता है: `return Decimal(value.replace(",", ""))`। `float` की जगह `Decimal` use करने से paise exact रहते हैं।
3. **Prove.** सभी 13 tests pass होते हैं, ruff clean है, और वो push करता है। Change merge होने से पहले CI एक clean runner पर checks दोहराता है।

वो fake reply को भी `"1,500.00"` कर देता है, क्योंकि fake उतना ही अच्छा होता है जितने अच्छे replies आप उसे देते हो; उनकी shape असली logs से copy करो। पूरा fix उसे अकेले करीब 20 minutes में हो जाता है।

| Tooling के बिना | Tooling के साथ |
| --- | --- |
| किसी user से "कभी-कभी fail होता है" | Invoice, field और value बताने वाली एक log line |
| Fix साबित करने का कोई तरीका नहीं | एक test जो fix से पहले fail और बाद में pass होता है |
| Server पर अलग package versions | हर जगह `uv sync --locked` |
| Karthik आपको WhatsApp पर message करता है | Karthik अकेले fix करता है, और CI उसका काम check करता है |

## आम गलतियाँ

- **System Python में install करना।** आपके laptop पर चलता है और कहीं नहीं। हर project की अपनी `.venv` होती है।
- **ऐसा src layout जो कभी install ही नहीं हुआ।** Tests `ModuleNotFoundError` के साथ fail होते हैं। एक `[build-system]` जोड़ो और `uv sync` चलाओ, या `pip install -e .`; `sys.path` patch मत करो।
- **Lock file commit न करना, या CI में plain `uv sync` चलाना।** महीनों बाद किसी dependency की नई release fresh install तोड़ देती है। `uv.lock` commit करो और `--locked` use करो।
- **`.venv` या `.env` commit करना।** पहला repository को फुला देता है; दूसरा keys leak करता है। दोनों को ignore करो, `.env.example` commit करो, और जो भी key कभी commit हुई हो उसे rotate करो।
- **हर module में, या library code के अंदर `basicConfig` call करना।** Logging एक बार, entry point में configure करो।
- **Secrets या personal data log करना।** Ids, sizes और timings log करो, keys, पूरे documents या phone numbers कभी नहीं।
- **Production में DEBUG चालू छोड़ देना।** ये disks भर देता है, paid log platforms पर पैसे लगते हैं, और अक्सर customer data वाले raw prompts print करता है।
- **Unit tests जो असली model को call करते हैं।** ये धीमे होते हैं, पैसे लगते हैं और random fail होते हैं। Fake client pass करो; quality अलग evaluation में नापो।
- **हर lint rule एक साथ चालू करना।** सैकड़ों warnings, और team उन्हें पढ़ना छोड़ देती है। Rule groups धीरे-धीरे जोड़ो।
- **ऐसा README जिसे किसी ने follow ही नहीं किया।** Handover से पहले fresh clone से उसे test करो।

## Practice करो

नीचे linked pytest का Get Started page पूरा करो, फिर Python के logging tutorial का basic section।

1. **Restructure करो।** `uv init --package` चलाओ और अपनी लिखी कोई एक script `src/` में ले जाओ। `pyproject.toml` में `[dependency-groups]`, `[tool.pytest]` और `[tool.ruff.lint]` जोड़ो, फिर `uv sync` करो और `uv.lock` और `.python-version` commit करो।
2. **Install का असर देखो।** एक scratch venv में जहाँ package install नहीं है, pytest चलाओ और `ModuleNotFoundError` पढ़ो। फिर उसे install करो और दोबारा चलाओ।
3. **Model को fake करो।** अगर आपका code model को call करता है, तो function को ऐसा बदलो कि वो client को parameter की तरह ले, `conftest.py` में एक `FakeModelClient` fixture लिखो, और एक test जोड़ो जो इसे use करे और एक जो check करे कि bad reply पर साफ़ error raise होता है।
4. **Lint और log करो।** `ruff check --fix` और `ruff format` चलाओ। Debugging वाले हर `print` को सही level की logger call से बदलो, और environment से `LOG_LEVEL` लेकर अपने entry point में logging एक बार configure करो।
5. **Secrets और CI।** कोई भी key `.env` में ले जाओ, `.env` को `.gitignore` में जोड़ो, एक `.env.example` commit करो, और ऊपर वाला workflow जोड़ो। Push करो और उसे green होते देखो।
6. **अनजान वाला test।** अपनी repository `/tmp` में clone करो, सिर्फ़ अपना README follow करो, और जो भी step टूटे उसे ठीक करो।

**आपका काम पूरा है जब आप** repository किसी दोस्त को दे सको जो README से `uv sync --locked` और `uv run pytest` चलाए और हर test pass होते देखे, और साथ ही CI latest commit पर वही result दिखाए।
