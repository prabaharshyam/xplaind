## ये क्या है

हर AI product idea के सामने शुरू में ही दो सवाल आते हैं, और इनमें गलती महँगी पड़ती है:

1. **Feasibility.** क्या AI हमारे real data पर, ठीक-ठाक cost और speed पर, ये task काफ़ी अच्छे से कर सकता है?
2. **Build बनाम buy.** क्या हम एक तैयार product खरीदें, पहले से use हो रहे platform में एक AI feature configure करें, या अपना build करें?

Teams अक्सर पहला सवाल छोड़ देती हैं और दूसरे पर महीनों बहस करती हैं। बेहतर क्रम ये है: कुछ दिनों में feasibility test करो, जो options काम नहीं कर सकते उन्हें छाँट दो, फिर बचे हुए options की cost और risk पर तुलना करो।

```flow
title: Idea से delivery के फ़ैसले तक
Idea -> 20-50 real examples पर prototype | महीने नहीं, दिन
20-50 real examples पर prototype -[बहुत दूर]-> अभी feasible नहीं | context या data जोड़ो, या इंतज़ार करो
20-50 real examples पर prototype -[करीब]-> Options को छाँटो
Options को छाँटो -[fit या compliance में fail]-> बाहर
Options को छाँटो -[pass]-> दो साल की cost की तुलना करो
दो साल की cost की तुलना करो -> चुनो और review date तय करो
चुनो और review date तय करो -> Go-live से पहले बड़ा evaluation
```

ये lesson Sana के साथ चलता है, जो Hyderabad की एक hospital chain में product manager हैं। वो test करती हैं कि क्या AI discharge summaries draft कर सकता है, फिर numbers के साथ तय करती हैं कि इसे कैसे deliver करें। आखिर तक आप एक quick feasibility test चला पाओगे, फ़ैसले के दोनों पहलुओं की cost निकाल पाओगे, और buy, configure या build के चुनाव का बचाव कर पाओगे।

## ये कैसे काम करता है

### Step 1: कुछ दिनों में prototype बनाओ

20 से 50 **real** examples लो, और अगर उनमें personal data है तो mask करो। एक capable model और एक simple prompt के साथ task try करो, हाथ से या किसी notebook में। यही **proof of concept** है: छोटा, तेज़ और ईमानदार। सिर्फ़ साफ़-सुथरे cases नहीं, मुश्किल cases भी लो, जैसे खराब scans, मिली-जुली भाषाएँ और लंबे records।

फिर outputs को एक **domain expert** से judge करवाओ, prompt लिखने वाले engineers से नहीं। जिन्होंने कुछ बनाया है, वो वही देखते हैं जो उनका मतलब था, वो नहीं जो page पर लिखा है। हर output को एक simple scale पर rate करो:

| Rating | मतलब |
| --- | --- |
| Usable | सही, ज़्यादा से ज़्यादा छोटे edits चाहिए |
| Needs work | Idea सही, बड़े edits चाहिए |
| Unsafe या wrong | Use किया तो नुकसान होगा |

- अगर results बहुत दूर हैं, तो शायद task अभी feasible नहीं है। उसे ज़्यादा context, बेहतर data, या आगे चलकर एक बेहतर model चाहिए हो सकता है।
- अगर results करीब हैं, तो feasibility की संभावना ज़्यादा है। अब असली काम reliability, integration, safety और evaluation है, ये नहीं कि model ये कर भी सकता है या नहीं।

ये 20 से 50 examples और उनकी ratings संभालकर रखो। यही आपका पहला evaluation set बनेगा, और हर vendor और आगे आने वाले हर model को आप इसी set पर चलाओगे।

### छोटा sample क्या बता सकता है और क्या नहीं

Prototype "क्या हम आगे बढ़ें?" का जवाब देता है, "क्या launch करना safe है?" का नहीं। छोटे samples में rare failures छिप जाते हैं।

मान लो 40 में से 2 outputs unsafe हैं। ये 5% जैसा दिखता है। पर सिर्फ़ 40 examples के साथ, असली unsafe rate 1% से कम से लेकर लगभग 17% तक कुछ भी हो सकता है (एक exact 95% confidence interval)। 300 में से 0 unsafe भी सिर्फ़ इतना बताता है कि असली rate शायद लगभग 1.2% से कम है।

तो rule ये है: feasibility का फ़ैसला छोटे sample पर करो, पर go-live का फ़ैसला इससे कहीं बड़े evaluation पर करो, जिसमें सबसे गंभीर failure type को अलग से गिना जाए।

### Step 2: cost और speed का अंदाज़ा लगाओ

Prototype से note करो कि हर request कितने tokens use करती है और हर जवाब में कितना समय लगता है। फिर उसे volume से गुणा करो। मिसाल के लिए, समझाने के लिए बनाई गई prices के साथ:

- मान लो एक request 12,000 input tokens और 1,000 output tokens use करती है।
- मान लो model की कीमत ₹250 प्रति million input tokens और ₹1,000 प्रति million output tokens है।
- तो एक request की cost है 12,000 × ₹250 ÷ 1,000,000 + 1,000 × ₹1,000 ÷ 1,000,000 = ₹3 + ₹1 = ₹4।

असली prices अक्सर बदलती हैं। उन्हें provider के pricing page से लो और साथ में वो तारीख लिखो जिस दिन आपने check किया। Retries और evaluation runs के लिए एक margin जोड़ो, मिसाल के लिए 25%।

Speed को user के सब्र से भी मिलाकर देखो। एक doctor draft के लिए दस seconds रुकेगा, दो minute नहीं।

### Step 3: तीन options को जानो

| Option | ये क्या है | ताकत | कमज़ोरी |
| --- | --- | --- | --- |
| **Product खरीदना** | उस use case के लिए एक तैयार tool, जैसे कोई document-processing service | सबसे तेज़; updates और model बदलाव vendor संभालता है | Customisation कम; vendor का roadmap; आपका data vendor के पास जाता है |
| **Platform configure करना** | पहले से use हो रहे software के अंदर एक AI feature, जैसे आपका CRM, help desk या hospital system | तेज़; मौजूदा data और permissions use करता है | Flexibility कम; उसी platform से बँधा |
| **Build** | Model API या open-weight model पर आपका अपना system | Fit, safety checks और data पर सबसे ज़्यादा control | Engineers, evaluation और लगातार maintenance चाहिए |

"Build" के अंदर एक दूसरा फ़ैसला छिपा है, जो regulated Indian sectors में अक्सर मामला तय कर देता है:

| Build route | Cost के मुख्य कारण | ज़रूरी skills | Data control |
| --- | --- | --- | --- |
| Hosted model API, हो सके तो किसी Indian cloud region में | हर token के हिसाब से pay; set-up थोड़ा | Prompting, evaluation, integration | Data आपके contract के तहत cloud provider के पास जाता है; region और retention check करो |
| Open-weight model self-host करना | GPUs जिनका पैसा idle रहने पर भी लगता है, और उन्हें चलाने वाले लोग | Model serving, scaling, security patching | Data आपके अपने account या data centre में रहता है, पर हर failure आपकी है |

एक समझदार default: hosted API से शुरू करो। Self-host तभी करो जब आपके rules data को आपके systems से बाहर जाने न दें, या जब volume इतना ज़्यादा और स्थिर हो कि GPUs शायद ही कभी idle रहें। हर model की availability cloud region के हिसाब से अलग होती है, इसलिए किसी model के इर्द-गिर्द design करने से पहले region check करो।

### Step 4: छाँटो, फिर तुलना करो

कुछ factors pass या fail वाले होते हैं। इन्हें पहले check करो, क्योंकि कोई भी कीमत एक fail होने वाले option को ठीक नहीं बना सकती:

1. **Fit.** क्या ये आपकी languages, document formats, templates और workflows संभालता है? इसे vendor के demo data पर नहीं, अपने evaluation set पर test करो।
2. **Data और compliance.** Data कहाँ जा सकता है? क्या ये आपके security, privacy और sector rules पूरे करता है?

फिर बाकी को तौलो:

3. **Total cost of ownership**, दो से तीन साल के लिए (नीचे देखो)।
4. **Speed.** Value कितनी जल्दी चाहिए? महीनों की देरी की भी cost होती है, मिसाल के लिए doctor hours जो बचे नहीं।
5. **Differentiation.** क्या customers किसी competitor की जगह आपको इसलिए चुनेंगे क्योंकि आप ये बेहतर करते हो? अगर आपके sector की हर firm को ये एक ही तरह से चाहिए, तो ये commodity है। "ये हमारे लिए ज़रूरी है" कहना test नहीं है: लगभग सब कुछ ज़रूरी होता है।
6. **Lock-in.** बाद में छोड़ना कितना मुश्किल होगा?

### Vendor due-diligence checklist

किसी भी vendor के साथ sign करने से पहले, इन सात सवालों के लिखित जवाब लो:

1. **Location.** Data कहाँ store और process होता है, backups और support access समेत?
2. **Training.** क्या vendor या उसका model provider आपके data पर train करता है? Contract में "नहीं" लिखवाओ।
3. **Retention.** Data कितने समय तक रखा जाता है, और क्या वो deletion confirm करेंगे?
4. **Sub-processors.** और कौन data को छूता है, मिसाल के लिए product के पीछे का model provider?
5. **Security evidence.** ISO 27001 जैसे certifications या एक SOC 2 report, और हाल का एक penetration test।
6. **Breach notice.** वो आपको कितनी जल्दी बताएँगे? DPDP Act और CERT-In के rules के तहत आपकी अपनी ज़िम्मेदारियाँ भी हो सकती हैं।
7. **Exit.** क्या आप अपना data और outputs किसी usable format में export कर सकते हो? Price या model बदलने से पहले कितना notice मिलेगा?

### Total cost of ownership

दोनों तरफ़ पूरा गिनो। खरीदना कभी सिर्फ़ licence fee नहीं होता: integration, एक internal owner, quality checks और छोड़ने की cost भी होती है। Build करना कभी सिर्फ़ tokens नहीं होता: engineers, evaluation, hosting और maintenance भी होते हैं। जो costs हर option में एक जैसी हैं, जैसे हर output को review करने में expert का समय, वो एक-दूसरे को cancel कर देती हैं, इसलिए उन्हें तुलना से बाहर रख सकते हो।

दो gotchas experienced teams को भी पकड़ लेते हैं:

- **Tokens से ज़्यादा लोगों की cost होती है।** Build के total में model usage अक्सर छोटा हिस्सा होता है। ये मान लेने से पहले अपना split check करो।
- **Sunk costs सवाल ही बदल देती हैं।** एक बार build कर लिया, तो खर्च हुआ पैसा जा चुका। बाद के review में सिर्फ़ future costs की तुलना करो: अपना build चलाना बनाम किसी vendor पर switch करना।

अपनी finance team के साथ tax भी check करो। IT और cloud services पर GST 18% है (November 2026 तक)। ज़्यादातर healthcare services GST से exempt हैं, इसलिए hospital अक्सर वो tax वापस claim नहीं कर पाता, जिससे हर vendor और cloud bill की असली cost बढ़ जाती है।

### बदलाव के लिए plan करो

ज़्यादातर organisations आखिर में मिला-जुला रास्ता अपनाते हैं: commodity tasks के लिए खरीदते हैं, और जहाँ कुछ fit नहीं होता या जहाँ वो अलग दिखते हैं वहाँ build करते हैं। आप जो भी चुनो, models और vendors आपके पैरों तले बदलते रहेंगे।

Model providers पुराने models retire करते हैं। मिसाल के लिए, November 2026 तक, Anthropic वादा करता है कि किसी publicly released model को retire करने से पहले कम से कम 60 दिन का notice देगा, और उसके बाद उस model को भेजी गई requests fail होती हैं। Amazon Bedrock जैसे partner clouds अपने retirement schedules खुद तय करते हैं। इसलिए कम से कम एक model migration का budget रखो, और replacement को test करने के लिए अपना evaluation set तैयार रखो। खरीदते समय vendor से पूछो कि वो यही problem कैसे संभालते हैं।

## एक worked example

Hyderabad की एक hospital chain चाहती है कि AI doctors के notes और lab reports से discharge summaries draft करे। लंबी shifts के आखिर में doctors हर summary पर 20 से 30 minute लगाते हैं। Chain महीने में लगभग 6,000 discharges संभालती है। इस example के सारे numbers illustrative हैं, सिखाने के लिए बनाए गए।

### Feasibility

Sana 40 de-identified patient records इकट्ठा करती हैं। एक capable model और hospital के summary template से वो 40 drafts बनाती हैं। तीन senior doctors उन्हें rate करते हैं:

| Rating | Drafts | Notes |
| --- | --- | --- |
| छोटे edits के साथ usable | 31 | ज़्यादातर शब्दों के बदलाव |
| बड़े edits चाहिए | 7 | पिछले notes का context छूट गया |
| Unsafe | 2 | दोनों में एक medication बदलाव छूट गया |

फ़ैसला: आगे बढ़ने लायक feasible, पर सिर्फ़ तब जब doctor sign-off ज़रूरी हो और draft की हर medication को pharmacy record से अपने-आप check किया जाए। 40 में से 2 unsafe drafts का मतलब हो सकता है कि असली rate 1% से कम से लेकर लगभग 17% तक कुछ भी है, इसलिए Sana launch से पहले 400 records का evaluation plan करती हैं, जिसमें medication errors अलग से गिने जाएँगे।

### Options को छाँटना

वो वही 40 records हर option पर चलाती हैं और हर option को hospital की data policy से check करती हैं:

| Option | Sana को क्या मिला | फ़ैसला |
| --- | --- | --- |
| Product A खरीदना | Drafts अच्छे, पर उनके hospital information system से integrate नहीं होता | Fit की वजह से बाहर |
| Product B खरीदना | Data India के बाहर process करता है; hospital की legal team hospital की data policy के तहत इसे reject करती है | Compliance की वजह से बाहर |
| Hospital system का add-on configure करना | उनका template follow नहीं कर सकता, न medication check चला सकता है | Fit और safety की वजह से बाहर |
| उनके मौजूदा cloud के Indian region में hosted model API पर build करना | Hospital system से integrate होता है, medication check और doctor sign-off के साथ | अकेला बचा हुआ option |

Build क्यों जीता, इस पर ईमानदार रहो। Discharge summaries draft करना वो चीज़ नहीं है जो इस hospital को अलग बनाती है: हर hospital को ये लगभग एक ही तरह से चाहिए। Build इसलिए जीता क्योंकि और कुछ भी fit और compliance में pass नहीं हुआ। ठीक इसी वजह से इस फ़ैसले की एक review date है।

Team regulatory counsel से ये भी पूछती है कि क्या ये tool medical device software गिना जा सकता है। India के drug regulator, CDSCO, ने Medical Devices Rules, 2017 के तहत medical device software पर guidance जारी की है, और कोई software device है या नहीं, ये उसके intended medical purpose पर निर्भर करता है। इसलिए team intended purpose को ध्यान से लिखती है, और build शुरू होने से पहले counsel की राय लिखित में लेती है।

### Build करने की दो साल की cost

Sana का अंदाज़ा है कि build में तीन महीने लगेंगे, फिर दो साल की window में 21 महीने चलेगा: 6,000 × 21 = 126,000 summaries।

| Illustrative cost item | कैसे निकाला | दो साल की cost |
| --- | --- | --- |
| Build team | 3 लोग × 3 महीने × ₹2.5 lakh महीना | ₹22.5 lakh |
| Pre-launch clinical evaluation | Doctors 400 drafts rate करते हैं | ₹3 lakh |
| Security और compliance review | एक बार | ₹3 lakh |
| Model usage | ₹5 प्रति summary (₹4 और 25%) × 126,000 | ₹6.3 lakh |
| Hosting, logging, monitoring | ₹40,000 महीना × 21 | ₹8.4 lakh |
| Maintenance | एक engineer आधा समय, ₹1.25 lakh महीना × 21 | ₹26.25 lakh |
| Ongoing quality sampling | Doctors एक sample review करते हैं, ₹25,000 महीना × 21 | ₹5.25 lakh |
| एक model migration | Model retire होने पर re-test और adjust | ₹4 lakh |
| **Total** | | **₹78.7 lakh, लगभग ₹62 प्रति summary** |

Doctor sign-off का समय इसमें नहीं गिना गया: hospital कोई भी option use करे, ये एक जैसा रहता है। Figures में GST शामिल नहीं है।

### Numbers Sana को क्या बताते हैं

- **लोगों की cost सबसे भारी है।** Total में model usage सिर्फ़ लगभग 8% है। लोग (build, evaluation, maintenance और migration) लगभग 78% हैं। Token price दोगुना होने से total लगभग 8% ही बढ़ेगा। System maintain करने वाला engineer चला जाए तो इससे कहीं ज़्यादा नुकसान होगा।
- **Volume build के पक्ष में है।** ज़्यादातर cost fixed है। 12,000 summaries महीना पर, illustrative total सिर्फ़ लगभग ₹85 lakh तक बढ़ता है (उसी team के साथ), यानी लगभग ₹34 प्रति summary। Vendor की per-summary fee volume के साथ-साथ बढ़ती है।
- **आज खरीदने का bar.** मान लो build शुरू होने से पहले एक ऐसा vendor आ जाता जो fit और compliance में pass होता। उसकी costs होतीं integration (₹4 lakh) और quality checks के साथ एक internal owner (₹50,000 महीना), और वो एक महीने बाद live हो सकता। दो साल में वो build को किसी भी ऐसी illustrative fee पर हरा देता जो लगभग ₹45 प्रति summary से कम हो: (₹78.7 lakh − ₹4 lakh − ₹12 lakh) ÷ 138,000 summaries (23 live महीनों में) = लगभग ₹45।
- **बाद में switch करने का bar.** Build के बाद उसके ₹22.5 lakh sunk हैं। तब उसे चलाने में लगभग ₹2.37 lakh महीना लगता है, future migrations के reserve समेत। Switch करने में integration और re-evaluation के लिए लगभग ₹7 lakh लगेंगे, यानी 24 महीनों में फैलाएँ तो लगभग ₹0.29 lakh महीना। तो switch करने लायक होने के लिए, एक compliant vendor को अब illustrative ₹26 प्रति summary से कम charge करना होगा: (₹2.37 lakh − ₹0.5 lakh − ₹0.29 lakh) ÷ 6,000 = लगभग ₹26।

### फ़ैसला

Leadership build को approve करती है, self-hosted model की जगह hosted API पर, क्योंकि volume GPUs चलाने को justify नहीं करता। Sana prompts, medication check और 400-record evaluation set hospital के अपने हाथ में रखती हैं, ताकि model बदला जा सके। सालाना market review का एक ठोस trigger है: अगर कोई product fit और compliance में pass हो और लगभग ₹26 प्रति summary से कम पर मिले (illustrative switching bar), या volume या rules बदलें, तो फिर से देखो।

## आम गलतियाँ

- **Prototype छोड़ देना।** Feasibility के अंदाज़े अक्सर दोनों तरफ़ गलत निकलते हैं।
- **Prototype को launch का सबूत मान लेना।** 40 में से 2 unsafe बड़े पैमाने पर evaluate करने की वजह है, कोई नापा हुआ 5% rate नहीं।
- **बनाने वालों से ही उनके outputs judge करवाना।** Domain experts से पूछो, एक लिखे हुए rubric के साथ।
- **Vendors को उनके demo data पर judge करना।** हर option को अपने evaluation set पर चलाओ।
- **किसी चीज़ को differentiating कहना क्योंकि वो आपके लिए ज़रूरी है।** पूछो कि क्या customers इसकी वजह से आपको चुनेंगे।
- **Licence fee की तुलना सिर्फ़ token costs से करना।** Build की ज़्यादातर cost लोग, evaluation, maintenance और migrations हैं।
- **Review के समय sunk costs को नज़रअंदाज़ करना।** Build हो जाने के बाद, सिर्फ़ future costs की तुलना करो।
- **Exit भूल जाना।** Sign करने से पहले data export और notice की शर्तें तय करो, और अपना evaluation set अपने पास रखो।

## Practice

नीचे linked SVPG के four big risks और Hamel Husain की field guide पढ़ो।

1. **Prototype.** 20 real examples पर एक AI task try करो। Domain जानने वाले किसी व्यक्ति से outputs को usable, needs work या unsafe rate करवाओ। लिखो कि ये sample क्या नहीं बता सकता।
2. **Screen.** दो products और एक platform feature ढूँढो जो एक ही task solve करने का दावा करते हैं। अपने examples हर एक पर चलाओ, और उनमें से एक के लिए सातों due-diligence सवालों के जवाब दो।
3. **Cost.** Build route के लिए Sana की तरह एक दो साल की cost table बनाओ, हर figure को estimate mark करके। निकालो कि प्रति unit कितनी vendor fee पर खरीदना जीत जाएगा।
4. **Recommend.** एक page की buy, configure या build recommendation लिखो, जिसमें एक review date और फ़ैसला दोबारा खोलने का एक ठोस trigger हो।

**आपका काम पूरा है जब आप** expert-rated prototype results, एक costed दो साल की तुलना, और एक ऐसा चुनाव दिखा सको जिसका बचाव आप fit, compliance, cost और lock-in पर कर सको।
