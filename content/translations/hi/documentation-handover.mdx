## ये क्या है

**Handover** किसी system को उन लोगों को योजना के साथ सौंपना है जो उसके मालिक बनेंगे। इसके तीन हिस्से हैं:

- हर audience के लिए **Documentation**: users, operators, developers और owners।
- **Knowledge transfer**: training, pairing और एक ऐसा period जिसमें client की team system चलाती है और आप अभी उपलब्ध हो।
- **Formal close**: handover पूरा होने के तय criteria, access हटाना, और अगर हो तो support की व्यवस्था।

AI systems को अतिरिक्त handover material चाहिए, क्योंकि उनका behaviour सिर्फ़ code पर नहीं, prompts, models, data और evals पर भी निर्भर करता है।

```flow
dir: LR
title: चार हफ़्ते में handover
हफ़्ता 1: shadow | वो आपको operate करते देखते हैं और docs पढ़ते हैं -> हफ़्ता 2: reverse shadow | वो एक prompt बदलते हैं और simulated incident संभालते हैं; आप देखते हो
हफ़्ता 2: reverse shadow -> हफ़्ता 3: अकेले चलाओ | वो KPI report और cost review चलाते हैं
हफ़्ता 3: अकेले चलाओ -> हफ़्ता 4: close | checklist sign-off, आपका access हटा, secrets rotate, support terms
```

| पाठक | Documents |
|---|---|
| Users | एक guide |
| Operators | Runbooks |
| Developers | How-tos और architecture |
| Owners | KPIs, costs, risks |
| सब | Decision records |

ये lesson चेन्नई के एक lender के credit-file assistant के handover को follow करता है।

## ये काम कैसे करता है

**हर पाठक के लिए लिखो।** (Diátaxis framework से) एक काम का बँटवारा: सीखने के लिए tutorials, tasks के लिए how-to guides, तथ्यों के लिए reference, और कारणों के लिए explanations।

- *Users*: system को अच्छी तरह इस्तेमाल करने की छोटी guide, वो किसमें अच्छा और किसमें कमज़ोर है, outputs कैसे check करें और feedback कैसे दें।
- *Operators*: routine tasks और जानी-पहचानी incidents के लिए **runbooks**, जैसे "model provider errors दे रहा है", "जवाब पुराने documents का हवाला दे रहे हैं", "costs उछल गए", "connector रुक गया"। हर runbook में: symptoms, checks, fix, escalation।
- *Developers*: architecture overview, local में कैसे चलाएँ, कैसे deploy करें, prompt सुरक्षित तरीके से कैसे बदलें, configuration कहाँ रहती है।
- *Owners*: system क्या करता है, उसका KPI और मौजूदा numbers, risks, costs, और कारणों के साथ लिए गए फ़ैसले।

**AI-specific ज़रूरी चीज़ें।** Golden sets और evals कैसे चलाएँ; इस्तेमाल हो रहे prompt और model versions और उन्हें कैसे बदलें; data pipeline और re-index कैसे करें; guardrails और उनके test sets; audit log schema; cost dashboard; examples के साथ जाने-पहचाने failure modes।

**Decision records।** अहम choices के छोटे notes: क्या तय हुआ, alternatives और क्यों। ये अगली team को अच्छे फ़ैसले पलटने या बुरे experiments दोहराने से रोकते हैं।

**पहले shadow, फिर reverse shadow।** पहले client के engineers आपको system operate करते और बदलते देखते हैं। फिर आपके देखते हुए वो खुद करते हैं: एक deploy, evals के साथ CI से prompt change, runbook से एक simulated incident। Handover तब पूरा है जब वो हर core task खुद कर चुके हों।

**Clean exit।** अपना access हटाओ, shared secrets rotate करो, accounts और billing transfer करो, और support terms पक्के करो।

**एक runbook page:**

| Section | Example: "जवाब पुराने documents को cite कर रहे हैं" |
| --- | --- |
| Symptoms | Users पुराने rates बता रहे हैं; refusal rate normal; feedback में dates का ज़िक्र |
| Checks | Index freshness dashboard; आख़िरी pipeline run; effective-date filter setting |
| Fix | प्रभावित source का indexing job दोबारा चलाओ; superseded flags की पुष्टि करो |
| Verify | मौजूदा rates के बारे में golden set से तीन test सवाल पूछो |
| Escalate | अगर source connector दो बार fail हो, तो platform team lead से संपर्क करो |

**Handover checklist।** Sign-off से पहले, हर item को उस client engineer के नाम के साथ tick करो जिसने उसे किया: एक release deploy किया; एक को rollback किया; evals के साथ CI से prompt बदला; एक source re-index किया; runbooks से दो simulated incidents संभाले; मासिक KPI और cost report बनाई; एक secret rotate किया। दिए गए documents और हटाए गए accounts भी जोड़ो। Client की team का signed checklist engagement का अंत साफ़ कर देता है और इस पर विवाद से बचाता है कि क्या सौंपा गया था।

**उनके लिए लिखना जो वहाँ नहीं थे।** मान लो पाठक साल भर बाद जुड़ता है और आपकी team से कभी नहीं मिला। समझाओ कि चीज़ें ऐसी क्यों हैं, decision records से link करो, और examples असली रखो। Project से बाहर किसी को हर how-to guide बिना मदद के follow करने दो, और जहाँ-जहाँ वो अटके वो सब ठीक करो।

## एक example से समझो

चेन्नई के lender के credit-file assistant का handover चार हफ़्ते लेता है।

हफ़्ता 1: Lender के दो engineers, Karthik और Divya, रोज़ के operations में आपके साथ pair करते हैं और developer docs पढ़ते हैं, 23 सवाल उठाते हैं जो doc fixes बन जाते हैं।

हफ़्ता 2: Divya नए regional format के लिए summary prompt बदलती है। वो CI में eval suite चलाती है, golden set पर 1.5-point की गिरावट देखती है, एक instruction ठीक करके merge करती है। Karthik runbook से एक simulated incident ("document store का connector रुक गया") 25 मिनट में संभालता है।

हफ़्ता 3: वो खुद मासिक KPI report और cost review चलाते हैं; operations team का champion आपकी user guide से नए officers का training session लेता है।

हफ़्ता 4: Handover checklist पर sign-off, आपके accounts हटाए गए, आपके इस्तेमाल किए gateway keys rotate हुए, और सिर्फ़ escalations के लिए तीन महीने का support agreement।

छह महीने बाद, Karthik evals pass होने पर बिना आपको फ़ोन किए gateway के पीछे का model upgrade कर देता है। यही एक सफल handover है।

| हफ़्ता | Transfer का सबूत |
| --- | --- |
| 1 | Client engineers के 23 सवाल doc fixes बने |
| 2 | Divya के prompt change में CI ने 1.5-point की गिरावट पकड़ी और ठीक हुई; Karthik ने simulated connector incident 25 मिनट में सुलझाया |
| 3 | Client team ने KPI और cost reviews चलाए; उनके champion ने officer training ली |
| 4 | Checklist sign हुआ; accounts हटे; gateway keys rotate हुए; तीन महीने का escalation support |
| छह महीने बाद | Evals pass होने पर Karthik ने बिना फ़ोन किए model upgrade किया |

## आम गलतियाँ

- **एक विशाल document।** अलग पाठकों को अलग documents चाहिए।
- **Runbooks का न होना।** Operators system को अपनी पहली incident में सीखते हैं।
- **Evals छोड़ देना।** Golden sets और eval scripts के बिना client prompts या models सुरक्षित तरीके से नहीं बदल सकता।
- **आख़िरी हफ़्ते में handover।** Pilot में ही शुरू करो; इसे time और practice चाहिए।
- **Access भूल जाना।** आपके keys और accounts हटने चाहिए और secrets rotate होने चाहिए।

## Practice करो

अगर नहीं पढ़ा है तो Diátaxis का overview और Google की technical writing का पहला unit पढ़ो।

1. अपने बनाए किसी system के लिए एक पन्ने का architecture overview, prompt को सुरक्षित तरीके से बदलने की how-to guide और संभावित incidents के लिए दो runbooks लिखो।
2. अपने लिए गए दो फ़ैसलों के लिए alternatives और कारणों के साथ दो decision records लिखो।
3. किसी दोस्त से कहो कि आपकी how-to guide और एक runbook बिना आपकी मदद के follow करे; उसके हर सवाल को नोट करो और docs ठीक करो।

**आपका काम पूरा जब:** आप सिर्फ़ अपने documents के सहारे किसी और को prompt बदलते, evals चलाते और deploy करते देख सको।
