## ये क्या है

**Feature engineering** का मतलब है raw data से model के inputs बनाना। Model किसी transactions table को वैसे नहीं पढ़ सकता जैसे इंसान पढ़ता है। उसे हर उस चीज़ के लिए एक row चाहिए जिसके बारे में आप predict करते हो (यहाँ, एक date पर एक customer), और ऐसे columns जो past का सार बताएँ: "पिछले 30 दिनों में orders", "आख़िरी order के बाद कितने दिन", "हाल के orders में late delivered का हिस्सा"।

अच्छे features वो पकड़ते हैं जो कोई domain expert देखता, ऐसी शक्ल में जिसे model use कर सके। Tabular data पर अक्सर ज़्यादातर accuracy यहीं से आती है।

हर feature का एक **prediction time** होता है: वो पल जब model से सवाल पूछा जाता। उससे पहले की हर चीज़ use हो सकती है। उसके बाद की हर चीज़ future है, और label वहीं रहता है।

```flow
dir: LR
title: Prediction time: 00:00 IST, 1 November
1 Nov से पहले के events | orders, ratings, tickets -> 1 Nov के हिसाब से features | counts, trends, recency
1 Nov के हिसाब से features -[model]-> Label: 1 से 14 Nov के बीच order किया | किसी feature में कभी use नहीं होता
```

ये lesson Bengaluru की एक food-delivery company के साथ चलता है जो predict करती है कि कौन-से customers 14 दिनों के अंदर फिर से order करेंगे।

## ये कैसे काम करता है

### एक ही नियम: सब कुछ prediction time के हिसाब से compute करो

**Leakage** तब होता है जब किसी feature में ऐसी जानकारी हो जो prediction time पर model के पास नहीं होती। इससे validation scores शानदार दिखते हैं और production के नतीजे निराश करते हैं। तीन आदतें इसका ज़्यादातर हिस्सा रोक देती हैं।

1. **Cutoff से पूरी तरह पहले का ही filter करो।** `ts < cutoff` use करो, `<=` नहीं। जिस event पर ठीक cutoff का time stamp है, वो prediction के बाद भी हुआ हो सकता है।
2. **धीरे-धीरे बदलने वाली tables को cutoff के हिसाब से join करो।** Ratings, loyalty tier या credit limit के लिए, cutoff से पहले की latest value लो, आज की latest value नहीं। Pandas में `merge_asof` ये करता है:

```python
import pandas as pd

labels = pd.DataFrame({"customer": [1, 1, 2], "cutoff": pd.to_datetime(["2026-09-01", "2026-10-01", "2026-10-01"])})
ratings = pd.DataFrame({"customer": [1, 1, 2, 2],
                        "rated_at": pd.to_datetime(["2026-08-20", "2026-10-01", "2026-09-15", "2026-10-03"]),
                        "rating": [5, 2, 4, 1]})
joined = pd.merge_asof(labels.sort_values("cutoff"), ratings.sort_values("rated_at"),
                       left_on="cutoff", right_on="rated_at", by="customer",
                       allow_exact_matches=False)     # strictly before the cutoff
print(joined)
```

1 October के cutoff पर customer 1 को 20 August वाली 5 की rating मिलती है। 1 October को ही दी गई 2 की rating बाहर रहती है, और customer 2 की 3 October वाली rating भी।

3. **बाद के time period पर validate करो।** कई cutoffs पर training rows बनाओ (हर महीने एक), पहले वालों पर train करो और बाद वालों पर test करो। Random split future की rows को training में मिला देता है, इसलिए leaks और थोड़े समय के patterns skill जैसे दिखते हैं।

### Feature families

| Raw data | Example features | ये क्यों मदद करता है |
| --- | --- | --- |
| Orders | पिछले 7, 30 और 90 दिनों के orders और spend; आख़िरी order के बाद कितने दिन | "क्या वो वापस आएँगे" के लिए habit और recency सबसे मज़बूत signals हैं |
| Changes | 30 दिन का average basket बनाम 90 दिन का average; इस महीने बनाम पिछले महीने | धीरे-धीरे दूर होते customers को पकड़ता है |
| Ratios | EMI बनाम income, हर order पर returns, category average के मुक़ाबले price | अलग-अलग लोगों के amounts को एक तुलना लायक scale पर लाता है |
| Service | पिछले 30 दिनों में late deliveries का हिस्सा; आख़िरी rating; हाल के tickets | वो बुरे अनुभव पकड़ता है जो लोगों को competitors की तरफ़ धकेलते हैं |
| Calendar | हफ़्ते का दिन, salary week, अगले त्योहार तक कितने दिन | भारत में demand और payments त्योहारों और pay cycles के साथ चलते हैं |
| Categories | City tier, channel, PIN code | अलग groups अलग तरह से behave करते हैं; encoding चाहिए (नीचे देखो) |
| Text और location | Keyword flags, text embeddings; सबसे नज़दीकी kitchen तक की दूरी | Unstructured data को numbers में बदलता है |

**Experts से शुरू करो।** Business चलाने वालों से पूछो: "आपको किस बात से लगता है कि कोई customer छोड़ने वाला है?" Delivery managers late deliveries बताएँगे; finance वाले payday timing बताएँगे। फिर हर idea को measure करो, क्योंकि समझदारी भरा idea भी कुछ न जोड़े, ऐसा हो सकता है (worked example में ऐसा एक दिखता है)।

### Numeric transforms

- **Missing values।** तय करो कि gap का मतलब क्या है। "30 दिनों में कोई order नहीं" असली zero है; "कभी कोई order नहीं" में average undefined हो जाता है। असली zeros को 0 से भरो, और जहाँ कुछ न होना ख़ुद एक जानकारी है वहाँ एक missing flag (`never_ordered = 1`) जोड़ो। scikit-learn का `HistGradientBoostingClassifier` missing values सीधे accept करता है।
- **Skewed amounts।** Rupees में spend long-tailed होता है: ज़्यादातर customers कुछ हज़ार खर्च करते हैं, कुछ लोग लाखों। Linear models और neural networks के लिए `log1p(amount)` use करो।
- **Scaling।** Linear models, k-nearest neighbours और neural networks के लिए standardise करो। Tree models order के हिसाब से split करते हैं, इसलिए scaling से उनके लिए कुछ नहीं बदलता।
- **Interactions।** Trees interactions ख़ुद ढूँढ लेते हैं। Linear models के लिए इन्हें लिखकर देना पड़ता है, जैसे `late_share × orders_30d`।

### Categories

- **कम values** (city tier, channel): one-hot encoding, और rare values को "other" में group कर दो।
- **बहुत सारी values** (PIN code, restaurant ID): frequency encoding, target encoding, या **hashing trick** (`FeatureHasher` हर value को तय संख्या वाले columns में से किसी एक पर map करता है; collisions से थोड़ी accuracy जाती है पर memory fixed रहती है)। Millions IDs के लिए deep models हर ID का एक **embedding** सीखते हैं।

**Target encoding** हर category की जगह उसका average label रख देता है। ये powerful है और इसमें leak होना आसान है। अगर averages सारी rows पर compute करो, तो हर row का अपना label उसके feature के अंदर होता है। नीचे का demo PIN codes को कोई असली signal नहीं देता:

```python
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import TargetEncoder
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.metrics import roc_auc_score

rng = np.random.default_rng(0)
df = pd.DataFrame({"pin_code": rng.integers(0, 2000, 6000).astype(str),
                   "y": rng.random(6000) < 0.3})          # pin code carries NO real signal

# Wrong: encode with means from ALL rows, then split
df["pin_mean"] = df.groupby("pin_code").y.transform("mean")
tr, te = train_test_split(df, test_size=0.3, random_state=0)
m = LogisticRegression().fit(tr[["pin_mean"]], tr.y)
print("encoded before split:", round(roc_auc_score(te.y, m.predict_proba(te[["pin_mean"]])[:, 1]), 2))

# Right: the encoder lives inside the pipeline and is fitted on training rows only
pipe = make_pipeline(TargetEncoder(), LogisticRegression()).fit(tr[["pin_code"]], tr.y)
print("encoded after split :", round(roc_auc_score(te.y, pipe.predict_proba(te[["pin_code"]])[:, 1]), 2))
```

गलत तरीके के लिए ये 0.85 print करता है और सही तरीके के लिए लगभग 0.5 (exact value हर run में थोड़ी बदलती है): शुद्ध noise एक मज़बूत feature जैसा score हो गया। scikit-learn का `TargetEncoder` `fit_transform` के अंदर cross-fit भी करता है, इसलिए training rows भी कभी अपना label नहीं देखतीं। यही नियम scalers, imputers और feature selection पर भी लागू होता है: इन्हें split के बाद, pipeline के अंदर fit करो। ये demo random split सिर्फ़ इसलिए use करता है क्योंकि data में कोई time order नहीं है।

### Calendar features

```python
import pandas as pd

# In production this is a reviewed data file, one row per festival, year and region
festivals = pd.DataFrame([
    ("onam", "2026-08-26", "kerala"),          # Thiruvonam day
    ("dussehra", "2026-10-20", "all"),
    ("diwali", "2026-11-08", "all"),
], columns=["festival", "date", "region"]).assign(date=lambda d: pd.to_datetime(d.date))

def calendar_features(dates, region):
    d = pd.Series(pd.to_datetime(dates))
    fest = festivals[festivals.region.isin([region, "all"])].date
    gap = d.apply(lambda x: min(((f - x).days for f in fest if f >= x), default=60))
    return pd.DataFrame({"date": d, "dow": d.dt.day_of_week, "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": gap.clip(upper=60)})

print(calendar_features(["2026-08-20", "2026-10-15", "2026-11-03"], "kerala"))
```

Festival dates हर साल बदलती हैं, और कुछ (जैसे Eid) चाँद दिखने पर निर्भर करती हैं, इसलिए official lists के बीच dates में एक दिन का फ़र्क हो सकता है। एक region column रखो और table को हर साल official holiday lists से update करो।

### Training-serving consistency

**Training-serving skew** तब होता है जब production किसी feature को training से अलग तरीके से compute करता है। आम वजहें: serving में UTC days और training में IST days, "active customer" की अलग definition, या ऐसी serving query जो data का आख़िरी घंटा miss कर देती है। Model crash नहीं होता; बस चुपचाप ख़राब होता जाता है।

```flow
dir: LR
title: एक feature function, दो callers
Raw events -> features_as_of | एक tested function
features_as_of -[कई past cutoffs]-> Training rows
features_as_of -[cutoff = now]-> Live features
```

Feature code एक बार लिखो और दोनों जगहों से call करो, और encoders को model pipeline के अंदर रखो ताकि fitted objects model के साथ ही चलें। बड़े scale पर, Feast (open source) जैसा कोई **feature store** ये आपके लिए करता है। ये point-in-time join से training sets बनाता है (हर label के timestamp पर या उससे पहले की latest feature value), fresh values को एक तेज़ online store में copy करता है (इसे materialisation कहते हैं), और prediction time पर वही values serve करता है।

### Features चुनना

ज़्यादा features हमेशा बेहतर नहीं होते। हर एक के साथ maintain करने को एक pipeline आती है और leak होने का एक मौका। Groups में measure करो (counts, recency, service, calendar), दो तरीकों से: हर group को एक simple baseline में जोड़कर, और हर group को full set से हटाकर। Features अक्सर overlap करते हैं, इसलिए किसी group को अकेले जोड़ने से फ़ायदा हो तब भी उसे हटाने से शायद ज़्यादा नुकसान न हो। वही groups रखो जिनका gain कई test months में दोहराया जाए।

## एक worked example

Bengaluru team का सवाल: हर monthly cutoff के बाद के 14 दिनों में क्या कोई customer order करेगा? नीचे का code synthetic data use करता है, ताकि आप इसे चला सको, numbers देख सको और इसे तोड़कर भी देख सको। इसमें दो effects plant किए गए हैं: आधे customers किसी समय धीरे-धीरे दूर होने लगते हैं (पहले छोटे baskets, फिर दो महीने बाद कम orders), और एक महीने में दो late deliveries किसी customer से app बदलवा सकती हैं।

```python
import numpy as np, pandas as pd
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

# 1. Synthetic orders for 3,000 customers, January to October 2026, with two planted effects
rng = np.random.default_rng(7)
N, days = 3000, pd.date_range("2026-01-01", "2026-10-31")
base = rng.gamma(2, 0.06, N)                             # usual daily chance of ordering
late_p = np.where(rng.random(N) < 0.3, 0.3, 0.05)        # 30% live where deliveries run late
drift = np.where(rng.random(N) < 0.5, rng.integers(30, 270, N), 9999)  # day a customer starts drifting
late_log, left, rows = np.zeros((len(days), N), bool), np.zeros(N, bool), []
for t, day in enumerate(days):
    shrink = np.clip(1 - (t - drift) / 60, 0.4, 1)       # drifters first buy smaller baskets,
    fade = np.clip(1 - (t - drift - 60) / 20, 0.05, 1)   # then two months later stop ordering
    left |= (late_log[max(0, t - 30):t].sum(0) >= 2) & (rng.random(N) < 0.03)  # 2 late orders: may switch apps
    ordered = rng.random(N) < base * fade * np.where(left, 0.1, 1)
    late_log[t] = ordered & (rng.random(N) < late_p)
    for c in np.flatnonzero(ordered):
        rows.append((c, day, round(rng.gamma(4, 100) * shrink[c]), late_log[t, c]))
orders = pd.DataFrame(rows, columns=["customer", "ts", "amount", "late"])

# 2. Features as of a cutoff, from orders strictly before it
def features_as_of(orders, cutoff):
    past, out = orders[orders.ts < cutoff], {}
    for d in (7, 30, 90):
        g = past[past.ts >= cutoff - pd.Timedelta(days=d)].groupby("customer")
        out[f"orders_{d}d"], out[f"spend_{d}d"] = g.size(), g.amount.sum()
        if d == 30: out["late_share_30d"] = g.late.mean()
    out["days_since_last"] = (cutoff - past.groupby("customer").ts.max()).dt.days
    f = pd.DataFrame(out).reindex(range(N))
    f = f.fillna({c: 0 for c in f if c.startswith(("orders_", "spend_"))})
    f["basket_change"] = (f.spend_30d / f.orders_30d) / (f.spend_90d / f.orders_90d)  # NaN if no orders
    return f                                              # trees accept NaN; it means "no recent orders"

# 3. One row per customer per monthly cutoff; label = ordered in the 14 days after it
def labelled(cutoff):
    X = features_as_of(orders, cutoff)
    nxt = orders[(orders.ts >= cutoff) & (orders.ts < cutoff + pd.Timedelta(days=14))]
    X["leaky_orders_7d"] = features_as_of(orders, cutoff + pd.Timedelta(days=7)).orders_7d  # bad join
    return X, X.index.isin(nxt.customer).astype(int)

def stack(months):
    parts = [labelled(pd.Timestamp(f"2026-{m:02d}-01")) for m in months]
    return pd.concat([x for x, _ in parts]), np.concatenate([y for _, y in parts])

Xtr, ytr = stack(range(4, 9))     # train on April to August cutoffs
Xte, yte = stack([9, 10])         # test on later months, never a random split

def auc(cols):
    m = HistGradientBoostingClassifier(random_state=0).fit(Xtr[cols], ytr)
    return round(roc_auc_score(yte, m.predict_proba(Xte[cols])[:, 1]), 3)

full = [c for c in Xtr if c != "leaky_orders_7d"]
print("orders_30d only     ", auc(["orders_30d"]))
for name, extra in [("+ 7 and 90 day counts", ["orders_7d", "orders_90d"]), ("+ recency", ["days_since_last"]),
                    ("+ basket change", ["basket_change"]), ("+ late share", ["late_share_30d"])]:
    print(name.ljust(20), auc(["orders_30d"] + extra))
print("all features        ", auc(full))
print("all + leaky feature ", auc(full + ["leaky_orders_7d"]))
```

Leaky column एक असली bug की नकल करता है: एक weekly table जिसकी key हफ़्ते का आख़िरी दिन थी, उसे cutoff से ऐसे join किया गया जैसे key पहला दिन हो, इसलिए "पिछले 7 दिन" चुपचाप "अगले 7 दिन" बन गए।

ये क्या print करता है (September और October cutoffs पर test AUC; synthetic data है, इसलिए इन्हें सिर्फ़ उदाहरण समझो):

| Features | Test AUC |
| --- | --- |
| सिर्फ़ पिछले 30 दिनों के orders | 0.803 |
| + 7-दिन और 90-दिन की counts | 0.832 |
| + आख़िरी order के बाद कितने दिन | 0.818 |
| + basket change | 0.807 |
| + late-delivery share | 0.805 |
| सारे honest features | 0.848 |
| सारे, + leaky join | 0.935 |

पाँच दूसरे seeds के साथ दोबारा चलाने पर भी यही pattern आता है, हर number लगभग 0.01 ऊपर-नीचे होता है।

**Numbers क्या सिखाते हैं।**

- **भारी काम windows और recency करते हैं।** एक अकेला 30-दिन count "पिछले हफ़्ते दो बार order किया" और "एक महीने पहले दो बार order किया" में फ़र्क नहीं कर सकता। 7-दिन और 90-दिन के windows जोड़ने से model को एक trend मिलता है, और आख़िरी order के बाद के दिन उसे timing देते हैं।
- **असली वजह भी कम ही जोड़ सकती है।** इस data में late deliveries सच में customers को भगाती हैं, क्योंकि simulation में यही लिखा है। फिर भी late-share feature अकेले लगभग कुछ नहीं जोड़ता: किसी भी 14-दिन के window में ये कुछ ही customers पर असर डालता है, और जो पहले ही जा चुके हैं वो कम orders के रूप में दिख जाते हैं। Basket change भी ऐसा ही करता है। Meeting में समझदार लगने वाले ideas को भी test में अपनी जगह कमानी पड़ती है।
- **Leak ज़ोर से दिखता है।** एक column से 0.85 से 0.93 का jump ही warning है। इसे ढूँढने के लिए सबसे नए columns को एक-एक करके हटाओ, फिर उस join को पढ़ो जिसने winner बनाया।

## आम गलतियाँ

- **Cutoff पर या उसके बाद के events use करना।** `ts < cutoff` से filter करो, और धीरे-धीरे बदलने वाली tables को "आज की latest value" से नहीं, as-of join से join करो।
- **Time-ordered data पर random splits।** एक ही customer कई cutoffs पर आता है, और future training में leak हो जाता है। पहले के महीनों पर train करो, बाद के महीनों पर test करो।
- **Split से पहले encoders, scalers या imputers fit करना।** इन्हें pipeline के अंदर रखो ताकि ये सिर्फ़ training rows पर fit हों।
- **Training और serving के लिए अलग feature code।** दो versions धीरे-धीरे अलग हो जाते हैं (UTC बनाम IST, "active" की दो definitions)। एक function share करो या feature store use करो।
- **Festival dates को hard-code करना।** ये हर साल बदलती हैं और region के हिसाब से अलग होती हैं। Dates वाली एक table रखो।
- **किसी jump की जाँच करने की जगह जश्न मनाना।** एक feature या एक join से आया बड़ा gain तब तक leak है जब तक उल्टा साबित न हो।
- **एक साथ सैकड़ों features जोड़ना।** इन्हें groups में जोड़ो और हर group को measure करो, ताकि पता रहे कि कौन-से अपने maintenance का ख़र्च निकालते हैं।

## कब भारी feature engineering की ज़रूरत नहीं

- **Unstructured data**, जैसे images, audio या लंबा text, जहाँ neural networks अपने features ख़ुद सीखते हैं।
- **एक मज़बूत pretrained model या embeddings** जो आपकी ज़रूरत की चीज़ पहले से पकड़ लेते हैं।
- **बहुत छोटा data**, जहाँ कुछ expert features और एक simple model सौ engineered features से बेहतर करते हैं।

## Demo से production तक

- **As-of rule को test करो**: एक unit test जो कोई future event जोड़े और check करे कि कोई feature नहीं बदला।
- **Training और serving के outputs की तुलना करो**, launch से पहले customers के एक sample पर, और उसके बाद एक schedule पर।
- **Feature distributions और missing rates track करो**, हर source के लिए, ताकि कोई टूटी हुई upstream table धीरे-धीरे गिरती accuracy की जगह एक alert के रूप में दिखे।
- **हर retrain पर feature groups को फिर से measure करो**, और जो मदद करना बंद कर दें उन्हें हटा दो।

Kaggle का Feature Engineering course पूरा करो और Google के Rules of ML का feature engineering section पढ़ो। फिर worked example का code use करो:

1. अपने तीन features जोड़ो (जैसे orders में weekend का हिस्सा, या अगले त्योहार तक कितने दिन) और हर एक को baseline में जोड़कर और full set से हटाकर measure करो।
2. एक test लिखो जो किसी cutoff के एक मिनट बाद की date वाला order जोड़े और अगर `features_as_of` बदले तो fail हो।
3. Time split की जगह सारी rows का एक random 80/20 split करो। यहाँ इससे scores नहीं बढ़ते, क्योंकि simulation में महीने-दर-महीने कोई shifts नहीं हैं। दो असली बदलाव बताओ (कीमत बढ़ना, नया competitor) जो random split को ज़रूरत से ज़्यादा optimistic बना दें।
4. April से June पर train करो और August से October पर test करो। Check करो कि table में feature groups की ranking अब भी वैसी ही रहती है या नहीं।

**आपका काम पूरा है जब आप** हर feature के लिए बता सको कि वो prediction time के हिसाब से कैसे compute होता है, आपने उसे बाद के period पर कैसे validate किया, और production उसे बिल्कुल वैसे ही कैसे compute करता है।
