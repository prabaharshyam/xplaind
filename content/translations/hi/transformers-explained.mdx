## ये क्या है

**Transformer** एक neural network architecture है, जो 2017 में आई, और **attention** नाम के mechanism पर बनी है। ये एक sequence (शब्द, image patches, audio frames) को process करता है और हर position को बाकी हर position को देखने देता है, ताकि तय हो सके कि क्या मायने रखता है।

इसकी तीन families हैं:

- **Decoder-only** models text को एक-एक token करके generate करते हैं: आज के chat और coding models।
- **Encoder-only** models text पढ़कर representations बनाते हैं: search के लिए कई embedding models, और classifiers। (कुछ हाल के embedding models decoder-only models से बदलकर बनाए गए हैं।)
- **Encoder-decoder** models एक sequence को दूसरी sequence में बदलते हैं: translation और summarisation।

Vision transformers images को patches में बाँटते हैं और उन्हें tokens की तरह treat करते हैं।

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| "it" से attention | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |

"The bank approved the loan because it trusted the applicant" में token "it" एक query भेजता है, उसे हर key से compare करता है, और अपना मतलब ज़्यादातर "bank" से लेता है।

```flow

Token vectors -> Multi-head attention -> Add and normalise -> Feed-forward -> Add and normalise, again
```

## ये काम कैसे करता है

**Tokens और embeddings।** Text को tokens में बाँटा जाता है; हर token एक vector (embedding) बन जाता है। Positional information जोड़ी जाती है ताकि model को क्रम पता रहे।

**Attention।** हर token के लिए model तीन vectors निकालता है: एक query (मैं क्या ढूँढ रहा हूँ?), एक key (मुझमें क्या है?) और एक value (मैं आगे क्या दूँगा?)। वो query को हर key से compare करके attention weights निकालता है, फिर values का weighted mix लेता है। "The bank approved the loan because it trusted the applicant" में attention "it" को "the bank" पर focus करने में मदद करता है।

**Multi-head attention।** कई attention heads एक साथ parallel में चलते हैं, और हर head अलग रिश्ते सीखने के लिए आज़ाद है (grammar, references, topics)।

**Layers।** हर transformer layer में attention होता है, उसके बाद एक छोटा feed-forward network, और shortcuts और normalisation जो गहरे stacks को train करने लायक बनाते हैं। बड़े models में दर्जनों layers stack होती हैं।

**Generation।** Decoder-only model हर संभव अगले token की probability predict करता है, एक चुनता है (sampling), उसे जोड़ता है और दोहराता है। Training के समय एक mask हर position को future tokens देखने से रोकता है।

**Cost।** Attention हर token की हर दूसरे token से तुलना करता है, इसलिए sequence की length बढ़ने पर cost बहुत तेज़ी से बढ़ता है। इसीलिए context windows की limits होती हैं, और लंबे prompts धीमे और महँगे होते हैं। Engineering tricks (efficient attention kernels, keys और values की caching) cost घटाते हैं।

**Pre-training और adaptation।** Models को बहुत बड़े data पर missing या अगले tokens predict करने के लिए pre-train किया जाता है, फिर adapt किया जाता है: chat models के लिए instruction tuning और preference training, खास tasks के लिए fine-tuning, या prompts और retrieval के साथ जैसे हैं वैसे use किया जाता है।

**ये क्यों जीता।** Attention लंबी दूरी के रिश्तों को अच्छे से संभालता है और GPUs पर parallel में कुशलता से train होता है, जिससे बहुत बड़े models और datasets तक scale करना संभव हुआ।

**तीनों families साथ-साथ:**

| Family | क्या पढ़ती है | क्या बनाती है | आम उपयोग |
| --- | --- | --- | --- |
| Encoder-only | पूरा input एक साथ | हर token या पूरे text का एक vector | Classification, embeddings, search |
| Decoder-only | बाएँ से दाएँ, आगे झाँके बिना | अगला token, बार-बार | Chat, coding, drafting, reasoning |
| Encoder-decoder | पूरा input पढ़कर फिर generate करती है | एक नई sequence | Translation, summarisation |

**Attention सीधे गणित में।** एक token के लिए, उसकी query का हर token की key के साथ dot product लो। बड़े dot products का मतलब "relevant"। Scores को vector size के square root से भाग दो ताकि वो stable range में रहें, फिर softmax से उन्हें ऐसे weights में बदलो जिनका जोड़ 1 हो। हर token की value को उसके weight से गुणा करो और सब जोड़ दो। नतीजा उस token के लिए एक नया vector है, जिसमें उन tokens की जानकारी मिली हुई है जिन पर उसने attention दिया। हर head ये काम अपनी सीखी हुई queries, keys और values से करता है, और नतीजे जोड़ दिए जाते हैं।

**Pre-training क्या सिखाती है।** बहुत सारे text पर अगला या missing token predict करते-करते model grammar, facts, styles और reasoning के patterns सीख जाता है, क्योंकि ये सब predict करने में काम आते हैं। फिर instruction tuning और preference training उस कच्ची क्षमता को एक helpful assistant में ढालते हैं जो requests follow करता है।

**कुछ lines के NumPy में attention।** एक head, एक causal mask, और weights print किए हुए ताकि आप देख सको कौन किस पर attention दे रहा है:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                       # how relevant each token is to each other
    if causal:
        scores = np.where(np.triu(np.ones_like(scores), k=1) == 1, -np.inf, scores)
    weights = softmax(scores)                           # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "she"]
x = rng.normal(size=(len(tokens), 16))                  # token embeddings plus position
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(np.round(w, 2))                                   # upper triangle is 0: no peeking ahead
```

Train हुए model में "she" वाली row "Priya" पर ज़्यादा weight डालेगी। यहाँ weights random हैं, पर shapes और mask ठीक वही हैं जो असली models हर layer के हर head के लिए compute करते हैं।

**Multi-head के shapes।** 768 की model width और 12 heads के साथ, हर head 64 dimensions पर काम करता है; उनके outputs वापस जोड़कर 768 बनाए जाते हैं और एक और matrix से mix होते हैं। यही idea PyTorch में:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                           # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                         # (2, 10, 768) and (2, 10, 10)
```

**Parameters कहाँ हैं।** हर layer में attention के पास width × width की चार matrices होती हैं (queries, keys, values, output); feed-forward block आम तौर पर width का लगभग चार गुना फैलता है और वापस आता है, जो फिर से लगभग दोगुने weights हैं:

```python
def layer_params(width, ff_mult=4):
    attn = 4 * width * width
    ff = 2 * width * (ff_mult * width)
    return attn + ff

w, layers, vocab = 4096, 32, 128_000
total = layers * layer_params(w) + vocab * w
print(f"about {total / 1e9:.1f} billion parameters")    # about 7 billion: the 7B to 8B range
```

असली models में details अलग होती हैं (grouped key-value heads, gated feed-forward layers), पर ये अंदाज़ा सही range में बैठता है।

**लंबे inputs महँगे क्यों हैं।** Attention हर token की हर पिछले token से तुलना करता है, इसलिए काम length के square के हिसाब से बढ़ता है: 8,000 tokens में 1,000 tokens के मुकाबले लगभग 64 गुना attention का काम लगता है। Generation हर पिछले token की keys और values का cache भी रखता है, इसीलिए लंबे contexts को बहुत सारी GPU memory चाहिए।

## एक example से समझो

Chennai का एक legal-tech startup Indian court judgments को कानून के क्षेत्र (property, family, criminal, tax, labour) के हिसाब से classify करता है और उन पर semantic search भी चाहता है।

- **Classification**: वो 12,000 labelled judgment summaries पर एक छोटा encoder-only transformer fine-tune करते हैं। ये 91% accuracy पाता है, जबकि keyword features पर gradient-boosted model 82% पाता है, क्योंकि attention "the appellant's claim to ancestral property" जैसा context पकड़ लेता है।
- **Search**: वो paragraphs को embed करने और मिलते-जुलते passages retrieve करने के लिए एक embedding model (encoder) use करते हैं।
- **Summaries**: वो API से एक decoder-only language model use करते हैं, जिसके prompt में retrieved passages होते हैं।

जब judgments encoder की 512-token limit से बड़े होते हैं, तो वो पूरा text नहीं, पहले और सबसे relevant sections classify करते हैं। ये सीधा नतीजा है कि length के साथ attention का cost बढ़ता है।

| Task | Model type | नतीजा |
| --- | --- | --- |
| Area-of-law classification | Fine-tuned छोटा encoder | 91%, जबकि keyword features से 82% |
| मिलते-जुलते passages की search | Encoder embedding model | Judgments में semantic matches |
| Summaries | API से decoder-only model | Retrieved passages से citations वाली summaries |
| लंबे judgments | 512-token limit वाला encoder | सबसे relevant sections classify करो |

## आम गलतियाँ

- **सब transformers को chatbot समझना।** Encoders, decoders और encoder-decoders अलग-अलग कामों के लिए हैं।
- **Sequence limits को ignore करना।** लंबे inputs कट जाते हैं या महँगे पड़ते हैं।
- **जहाँ छोटा encoder काफ़ी हो, वहाँ विशाल model fine-tune करना।** Model का size task से match करो।
- **ये मान लेना कि attention weights ही explanation हैं।** वो फ़ैसलों की भरोसेमंद explanations नहीं हैं।
- **Tokenisation भूल जाना।** Indian languages में अक्सर हर शब्द पर ज़्यादा tokens लगते हैं, जिससे limits और cost पर असर पड़ता है।
- **ये सोचना कि attention अपने आप "समझता" है**: वो weighted averaging है; मतलब training से आता है।
- **लंबे inputs के quadratic cost को ignore करना** जब prompts और context design करते हो।

## जब transformer के internals ज़रूरी नहीं

- **Models को API से use करते हुए**: रोज़ के काम में prompts, retrieval और evals ज़्यादा मायने रखते हैं।
- **Tabular prediction**, जहाँ आम तौर पर boosted trees बेहतर tool हैं।
- **सीधे text tasks** जिन्हें एक keyword rule या छोटा classifier पहले से अच्छे से संभाल लेता है।

Models चुनते समय, hardware का size तय करते समय, लंबे-context के behaviour को debug करते समय या fine-tuning में internals जानना काम आता है।

- **Hardware चुनने से पहले architecture से memory और cost का अंदाज़ा लगाओ** (layers, width, heads, context)।
- **Quadratic attention cost को देखते हुए prompts और contexts को ज़रूरत से लंबा मत रखो।**
- **Model का अपना tokenizer और chat template ठीक वैसे ही use करो** जैसा documented है।
- **लंबे-context की accuracy अपने documents पर benchmark करो**, सिर्फ़ विज्ञापित window पर नहीं।
- **हर deployment के साथ model architecture और version record करो।**
