## ये क्या है

**Transformer** एक neural network architecture है, जो 2017 में आई और **attention** नाम के mechanism पर बनी है। ये एक sequence (शब्द, image patches, audio frames) को process करता है। हर layer में, हर position तय करती है कि बाकी positions से कितना लेना है।

तीन families इसे use करती हैं:

- **Decoder-only** models एक बार में एक token करके text generate करते हैं। Llama family जैसे आज के open chat और coding models ऐसे ही बने हैं।
- **Encoder-only** models पूरा text एक साथ पढ़ते हैं और representations बनाते हैं: classifiers, और search के लिए कई embedding models। Qwen3-Embedding (June 2025) जैसे कुछ नए embedding models इसकी जगह decoder models से बने हैं।
- **Encoder-decoder** models एक sequence पढ़कर दूसरी लिखते हैं: translation और summarisation।

Vision transformers image को patches में काटते हैं और हर patch को token की तरह treat करते हैं।

नीचे की table एक head में "it" शब्द से attention दिखाती है। Numbers सिर्फ़ समझाने के लिए हैं, किसी असली model से नहीं।

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| Encoder (दोनों तरफ़ देखता है) | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |
| Decoder (सिर्फ़ पीछे का देखता है) | 0.03 | **0.45** | 0.06 | 0.02 | 0.36 | 0.03 | 0.05 | 0 | 0 | 0 |

Encoder "trusted" देख सकता है, जिससे उसे पता चलता है कि "it" bank है (loan किसी पर trust नहीं कर सकता)। Decoder बाद के शब्द नहीं देख सकता, इसलिए "it" पर "bank" और "loan" के बीच फ़ैसला अभी खुला है। "trusted" जैसे बाद के tokens पीछे देखकर इसे तय करते हैं। हर row का जोड़ 1 है।

## ये कैसे काम करता है

### Tokens और embeddings

एक **tokenizer** text को tokens में तोड़ता है: पूरे शब्द, शब्दों के टुकड़े या अकेले bytes। कई chat-model tokenizers byte-pair encoding use करते हैं: bytes से शुरू करो और बार-बार सबसे common पास-पास वाले pairs को merge करके नए tokens बनाओ। फिर हर token id एक learned table से एक row चुनता है, जिससे एक vector (एक **embedding**) मिलता है। जैसे, Llama 3 8B की vocabulary 128,256 tokens की है और vectors 4,096 numbers चौड़े हैं।

Tokenizers अपने merges अपने training text से सीखते हैं, इसलिए जो languages उस text में कम थीं, वो ज़्यादा टुकड़ों में टूटती हैं। हमने OpenAI के पुराने `cl100k_base` और नए `o200k_base` tokenizers से एक sentence के tokens गिने (November 2026):

| Sentence | cl100k_base | o200k_base |
| --- | --- | --- |
| The bank approved the loan. | 6 | 6 |
| Bank ne loan approve kar diya. | 8 | 7 |
| बैंक ने लोन मंज़ूर कर दिया। | 31 | 11 |

नए tokenizer के साथ भी Hindi sentence को English वाले से लगभग दोगुने tokens चाहिए। ज़्यादा tokens का मतलब ज़्यादा bill, धीमे replies और context में कम जगह। Indian languages में AI वाला lesson इसमें और गहराई से जाता है।

### Position

Attention खुद order नहीं देखता: शब्दों को shuffle कर दो, तब भी हर token को वही mix मिलेगा। इसलिए model को position की information चाहिए। 2017 वाले transformer और BERT ने हर embedding में एक position vector **जोड़ा**। BERT ने ऐसे 512 vectors सीखे, इसीलिए वो 512 tokens से आगे नहीं पढ़ सकता।

Llama-family models और ModernBERT इसकी जगह **rotary position embeddings (RoPE)** use करते हैं। हर attention layer के अंदर, हर query और key को उसकी position पर depend करने वाले angle से rotate किया जाता है। फिर दो tokens के बीच का score इस पर depend करता है कि वो कितनी दूर हैं। थोड़ी extra training से rotary embeddings को उन contexts तक stretch किया जा सकता है जो model के पहले देखे contexts से लंबे हों; context windows के बढ़ने का ये एक तरीका है।

### Attention

हर token तीन learned matrices से अपने embedding से तीन vectors निकालता है:

- एक **query**: मैं क्या ढूँढ रहा हूँ?
- एक **key**: मुझे किस चीज़ पर match किया जा सकता है?
- एक **value**: चुना गया तो मैं आगे क्या दूँगा?

Model token की query का हर key से dot product लेता है। बड़ा dot product मतलब "relevant"। फिर वो scores को key size के square root से divide करता है, क्योंकि vector size के साथ dot products बढ़ते हैं और बहुत बड़े scores पर softmax एक ही token चुन लेता है और सीखना बंद कर देता है। एक **softmax** scores को ऐसे weights में बदलता है जिनका जोड़ 1 हो। Output values का weighted sum है: token के लिए एक नया vector, जिसमें वो मिला हुआ है जिस पर उसने attend किया।

Decoder में, एक **causal mask** softmax से पहले future tokens के scores को minus infinity कर देता है, इसलिए उनके weights बिल्कुल 0 हो जाते हैं। इसके बिना, training में हर position वही token देख लेती जिसे उसे predict करना है।

Mask के साथ एक head, NumPy में:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                  # relevance of every token to every other
    if causal:                                     # hide future tokens
        future = np.triu(np.ones_like(scores), k=1) == 1
        scores = np.where(future, -np.inf, scores)
    weights = softmax(scores)                      # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "because", "she"]
x = rng.normal(size=(len(tokens), 16))             # one 16-number vector per token
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(out.shape)                                   # (6, 8): one new vector per token
print(np.round(w, 2))                              # zeros above the diagonal
```

पहली row `[1, 0, 0, 0, 0, 0]` है: "Priya" सिर्फ़ खुद पर attend कर सकता है। यहाँ weights random हैं। Trained model में "she" वाली row "Priya" पर ज़्यादा weight डालेगी।

### Multi-head attention और layer

कई heads साथ-साथ चलते हैं, हर एक के अपने query, key और value matrices के साथ, इसलिए हर head अलग रिश्ता सीख सकता है। 768 की width और 12 heads में हर head 64 numbers पर काम करता है; outputs वापस जोड़कर 768 किए जाते हैं और एक और matrix से mix होते हैं। PyTorch में ये built-in है:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                      # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)   # True = hidden
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                    # (2, 10, 768) and (2, 10, 10)
```

एक layer मतलब attention, और उसके बाद एक **feed-forward** network जो हर token पर अलग से काम करता है। Shortcut connections हर block के input को उसके output में वापस जोड़ते हैं, ताकि गहरे stacks भी train हो सकें। 2017 वाला model हर block के बाद normalise करता था; Llama-style models हर block से पहले normalise करते हैं (RMSNorm से), जिससे training ज़्यादा stable रहती है। बड़े models ऐसी दर्जनों layers stack करते हैं।

```flow
dir: TB
title: Llama style में एक decoder layer, हर layer में दोहराई जाती है
Token vectors -> Normalise
Normalise -> Masked multi-head attention | queries और keys पर rotary positions लगती हैं
Masked multi-head attention -> Input वापस जोड़ो
Input वापस जोड़ो -> फिर से Normalise
फिर से Normalise -> Feed-forward | gated, लगभग 3.5 गुना चौड़ा
Feed-forward -> फिर से जोड़ो
फिर से जोड़ो -> अगली layer
```

### Generation, KV cache और sampling

Decoder आखिरी position के vector को अपनी vocabulary के हर token के लिए एक score में बदलता है, फिर एक चुनता है। **Temperature** softmax से पहले scores को divide करता है: 1 से कम पर choice safe होती है, 1 से ज़्यादा पर ज़्यादा varied। **Top-p** सिर्फ़ सबसे likely tokens रखता है जिनकी probabilities का जोड़ p (जैसे 0.9) हो, और उन्हीं में से sample करता है। चुना गया token जुड़ता है और loop फिर चलता है।

हर step पर पूरे text के keys और values फिर से compute करना बेकार का काम होगा, इसलिए model उन्हें store कर लेता है: यही **KV cache** है। हर नया token सिर्फ़ अपनी query, key और value compute करता है और cache पर attend करता है। इससे generation तेज़ होता है, पर cache हर token और हर user के साथ बढ़ता है।

### लंबे context के तीन costs

| Cost | किसके साथ बढ़ता है | आपके लिए इसका मतलब |
| --- | --- | --- |
| API bill | Tokens, linearly | Prompt के हर extra token के पैसे लगते हैं, हर call पर |
| KV cache memory | Tokens × users | लंबी chats और ज़्यादा users GPU memory भर देते हैं |
| Attention compute | Length का square | सिर्फ़ तब मायने रखता है जब context लंबा हो जाए |

Llama 3 8B shape के लिए, हर नया token हर layer में weight matrices में लगभग 218 million multiply-adds करता है, और हर उस पुराने token के लिए जिस पर वो attend करता है लगभग 8,000 और (config से मोटा हिसाब)। 2,000 tokens पर attention काम के दसवें हिस्से से भी कम है; लगभग 27,000 tokens पर जाकर ही वो बराबरी पर आता है। पूरी sequence पर attention का काम square के साथ बढ़ता है: 8,000 tokens में 1,000 के मुकाबले लगभग 64 गुना attention का काम। **FlashAttention** वही exact result slow GPU memory के बहुत कम चक्करों में निकालता है, इसलिए वो तेज़ है, पर comparisons की गिनती वही रहती है।

| --- | --- | --- |
| Rotary positions | Position attention के अंदर आती है; contexts stretch किए जा सकते हैं | `rope_theta`, `rope_scaling` |
| Grouped-query attention | Query heads के groups एक key-value head share करते हैं: छोटा KV cache, quality में थोड़ा ही नुकसान | `num_attention_heads` से कम `num_key_value_heads` |
| Gated feed-forward | दो की जगह तीन matrices | `intermediate_size`, `hidden_act` |
| Mixture of experts | कई feed-forward "experts"; एक router हर token को कुछ ही experts के पास भेजता है | `num_local_experts`, `num_experts_per_tok` |
| Local attention | कुछ layers सिर्फ़ पास के tokens पर attend करती हैं, जिससे लंबे input का cost घटता है | sliding-window settings |

Mixture of experts दो numbers को अलग करता है। **Total** parameters सब memory में होने चाहिए; **active** parameters हर token का compute तय करते हैं। Mixtral 8x7B में कुल 46.7 billion हैं और हर token पर 12.9 billion use होते हैं; DeepSeek-V3 में कुल 671 billion और active 37 billion। Hardware size करने से पहले दोनों numbers पढ़ो।

### Parameters कहाँ हैं

```python
def params(width, layers, vocab, ffn, heads, kv_heads, gated=True, tied=False):
    head = width // heads
    attn = 2 * width * width + 2 * width * kv_heads * head   # Q and output, then K and V
    ff = (3 if gated else 2) * width * ffn                     # gated layers use 3 matrices
    emb = vocab * width * (1 if tied else 2)                   # input table, output layer
    return layers * (attn + ff) + emb

# Llama 3 8B, from its published config
print(params(width=4096, layers=32, vocab=128_256, ffn=14_336, heads=32, kv_heads=8) / 1e9)
# about 8.03, matching the published 8B size
```

हर layer के weights का लगभग चार-पाँचवाँ हिस्सा feed-forward block में है, attention में नहीं। हर number के 2 bytes (16-bit) पर, 8 billion parameters को किसी भी KV cache से पहले ही लगभग 16 GB GPU memory चाहिए।

### Pre-training और adaptation

Models को बहुत सारे text पर अगला token (decoders) या छिपाए गए tokens (encoders) predict करने के लिए pre-train किया जाता है। Grammar, facts और reasoning के patterns, सब prediction में मदद करते हैं, इसलिए model उन्हें सीख लेता है। फिर chat models को instruction tuning और preference training से shape किया जाता है। अपने tasks के लिए आप fine-tune कर सकते हो, या model को वैसे ही prompts और retrieval के साथ use कर सकते हो।

Transformers इसलिए जीते क्योंकि attention दूर के tokens को सीधे जोड़ता है और सारी positions GPUs पर parallel में train होती हैं, जिससे बहुत बड़े models और datasets तक scale करना मुमकिन हुआ।

## एक worked example

Chennai के एक legal-tech startup के पास Indian court judgments पर तीन काम हैं।

**1. Area of law के हिसाब से classify करना** (property, family, criminal, tax, labour)। उनके पास 12,000 labelled judgment summaries हैं। एक छोटा fine-tuned encoder साफ़ choice है: सस्ता, तेज़ और labels का फ़ायदा उठा सकता है। मान लो उनके test set पर ये 91% accuracy देता है, जबकि keyword counts पर gradient-boosted model 82% (समझाने के लिए numbers)। ये फ़ायदा context से आता है: "the appellant's claim to ancestral property" का मतलब property law है, तब भी जब "property" शब्द न हो।

पूरे judgments उनके BERT-style encoder की 512-token limit से लंबे होते हैं। ये limit उन 512 learned position vectors से आती है जिनके साथ वो train हुआ था, attention cost से नहीं। उनके पास दो options हैं:

- हर judgment को chunks में बाँटो, हर chunk classify करो और votes मिलाओ।
- ModernBERT जैसा long-context encoder use करो, जो 8,192 tokens पढ़ता है। उसका model card चेतावनी देता है कि पूरी window छोटे inputs से slow है, इसलिए वो speed भी test करते हैं।

**2. Semantic search.** एक embedding model हर paragraph को एक बार vector में बदलता है; queries vector search से match होती हैं।

**3. Summaries.** Privacy के लिए वो एक GPU पर 8B open model self-host करने की सोचते हैं। कुछ भी खरीदने से पहले config से size निकालते हैं:

```python
def kv_cache_gb(tokens, layers=32, kv_heads=8, head_dim=128, bytes_per_number=2, users=1):
    per_token = 2 * layers * kv_heads * head_dim * bytes_per_number   # one key and one value
    return per_token * tokens * users / 1e9

print(kv_cache_gb(1))                     # 0.000131 GB, about 0.13 MB per token
print(kv_cache_gb(6_500, users=10))       # 8.5 GB for 10 judgments at once
print(kv_cache_gb(6_500, users=10, kv_heads=32))   # 34 GB without grouped-query attention
```

| Item | Memory |
| --- | --- |
| Weights, 2 bytes पर 8 billion | लगभग 16 GB |
| KV cache, 6,000 tokens के 10 judgments और summary के लिए 500 और | लगभग 8.5 GB |
| Runtime overhead से पहले total | लगभग 25 GB |

Runtime overhead जोड़ने के बाद 24 GB GPU में एक साथ 10 के लिए कोई headroom नहीं बचता; 40 या 48 GB GPU में जगह बचती है, या वो एक बार में 5 process करें। ये fit grouped-query attention की वजह से होता है: हर query head के लिए एक key-value head होता तो cache चार गुना बड़ा होता।

## आम गलतियाँ

- **हर transformer को chatbot समझना।** Encoders, decoders और encoder-decoders अलग-अलग कामों के लिए हैं; classification में छोटा encoder अक्सर बड़े chat model को हरा देता है।
- **सिर्फ़ weights से hardware size करना।** KV cache context length और users के साथ बढ़ता है; लंबे contexts और ज़्यादा users को weights से भी ज़्यादा memory चाहिए हो सकती है।
- **Encoder की 512-token limit को attention cost समझ लेना।** ये उस position table से आती है जिसके साथ model train हुआ था।
- **Attention maps को explanation मान लेना।** Attention weights दिखाते हैं कि एक head में information कहाँ से बही, ये नहीं कि model ने फ़ैसला क्यों लिया।
- **गलत chat template या tokenizer use करना।** एक template से fine-tune हुआ model दूसरे template पर खराब चलता है; वही template use करो जो documented है।
- **Mixture-of-experts model के total parameters को उसकी speed बताना।** Memory total parameters के हिसाब से चलती है; हर token का compute active parameters के हिसाब से।
- **Tokenisation भूल जाना।** Hindi या Tamil text को English से कई गुना tokens लग सकते हैं, जिससे cost, speed और context में जगह बदलती है।

## जब transformer के internals ज़रूरी नहीं

- **API से models use करते समय**: रोज़ के काम में prompts, retrieval और evals ज़्यादा मायने रखते हैं।
- **Tabular prediction**, जहाँ boosted trees आमतौर पर बेहतर tool हैं।
- **आसान text tasks**, जिन्हें keyword rule या छोटा classifier पहले से अच्छे से संभाल लेता है।

Internals जानना तब काम आता है जब models चुनने हों, GPUs size करने हों, long-context behaviour debug करना हो या fine-tune करना हो।

## Demo से production तक

- **Hardware खरीदने से पहले memory का अंदाज़ा लगाओ**: weights, और साथ में आपकी असली context length और users की संख्या पर KV cache।
- **Prompts ज़रूरत से लंबे मत रखो**: हर token का bill लगता है, वो cache होता है और उस पर attend किया जाता है।
- **Model का अपना tokenizer और chat template** बिल्कुल वैसे use करो जैसे documented है।
- **Long-context accuracy को अपने documents पर benchmark करो**, सिर्फ़ advertised window पर भरोसा मत करो।
- **हर language के tokens गिनो**, उन languages के जिनमें आपके users लिखते हैं।
- **हर deployment के साथ model, version और config record करो**।
