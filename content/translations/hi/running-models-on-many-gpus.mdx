## ये क्या है

एक GPU की memory और speed तय होती है। दो अलग problems आपको कई GPUs use करने पर मजबूर करती हैं:

1. **Model एक GPU के लिए बहुत बड़ा है।** 16-bit precision पर एक 70B model को सिर्फ़ weights के लिए लगभग 140 GB चाहिए, जो एक 80 GB GPU से ज़्यादा है।
2. **एक copy आपके सारे users को serve नहीं कर सकती।** Model आ भी जाए, तो busy hour में कई copies चाहिए हो सकती हैं।

दो बुनियादी जवाब हैं: model को **copy** करो, या **बाँटो**।

- **Replica parallelism** (training में इसे **data parallelism** कहते हैं): कई GPUs पर पूरी copies चलाओ। हर copy अलग requests serve करती है, या अलग batches पर train करती है।
- **Model parallelism**: एक model को GPUs में बाँटना। मुख्य तरीके हैं **tensor parallelism** (हर layer के अंदर का काम बाँटो), **pipeline parallelism** (layers को stages नाम के groups में बाँटो) और, mixture-of-experts models के लिए, **expert parallelism** (अलग experts को अलग GPUs पर रखो)।

असली systems इन्हें मिलाते हैं: जैसे, 4 GPUs में बँटा एक model, और ऐसे कई groups replicas के रूप में।

हर फ़ैसले के पीछे का rule: **बाँटने की कीमत communication है, और communication को bandwidth चाहिए।** GPUs को जितनी बार बात करनी पड़ती है, उनके बीच का link उतना तेज़ होना चाहिए।

```flow
title: Model को कैसे फैलाना है, ये चुनना
Model और busy hour traffic -> Weights और KV cache एक GPU में आते हैं?
Weights और KV cache एक GPU में आते हैं? -[हाँ]-> Replicas | हर GPU पर एक copy
Weights और KV cache एक GPU में आते हैं? -[नहीं]-> एक NVLink server के अंदर आता है?
एक NVLink server के अंदर आता है? -[हाँ]-> Tensor parallelism | size 2, 4 या 8
एक NVLink server के अंदर आता है? -[नहीं]-> Servers के अंदर tensor, उनके बीच pipeline
Replicas -> ज़्यादा traffic के लिए copies जोड़ो | load balancer के पीछे
Tensor parallelism -> ज़्यादा traffic के लिए copies जोड़ो | load balancer के पीछे
Servers के अंदर tensor, उनके बीच pipeline -> ज़्यादा traffic के लिए copies जोड़ो | load balancer के पीछे
```

## ये कैसे काम करता है

### Replicas: जब भी model आ जाए, यही default है

हर GPU, या GPUs का हर group, एक पूरा model रखता है और अपनी requests serve करता है। Copies आपस में कभी बात नहीं करतीं, इसलिए कोई भी network चल जाता है, और एक fail हो जाए तो बाकी serve करती रहती हैं।

क्या कहाँ रखना है, ये तय करना एक packing पहेली है, और हिसाब आसान है: 16-bit पर हर parameter के लगभग 2 bytes, 8-bit पर 1 byte और 4-bit पर 0.5 bytes। जैसे, एक 80 GB GPU पर आप 16-bit पर दो 8B models (हर एक 16 GB, कुल 32 GB) रख सकते हो, या 8-bit पर एक 32B model (32 GB)। दोनों में usable 72 GB में से KV caches के लिए लगभग 40 GB बचता है। ये lesson engine के अपने use के लिए लगभग 10% spare रखता है। (vLLM कई versions तक default में हर GPU की 90% memory use करता था; नए versions में default बदल गया है, तो अपना version check करो।)

### Tensor parallelism: हर layer का काम बाँटना

एक transformer layer ज़्यादातर matrix multiplication है। Tensor parallelism हर matrix को, मान लो 4 GPUs में बाँटता है। हर GPU weights का एक चौथाई रखता है और अपना slice एक साथ compute करता है। आम scheme में (Megatron-LM वाली), GPUs हर layer में दो बार अपने partial results जोड़ते हैं, एक बार attention के बाद और एक बार feed-forward block के बाद। 80 layers वाले 70B model के लिए, ये हर generate होने वाले token पर 160 exchanges हैं।

ये latency क्यों घटा सकता है: हर नए token के लिए हर weight को memory से एक बार पढ़ना पड़ता है। 4 GPUs हों, तो हर एक चौथाई पढ़ता है, इसलिए हर token का समय घटता है, हालाँकि 4 गुना से कम।

दिक्कत वही exchanges हैं। वो छोटे हैं पर बहुत बार होते हैं, इसलिए उन्हें आपका सबसे तेज़ link चाहिए:

| Link | कहाँ मिलता है | Bandwidth (मोटा अंदाज़ा) | किसके लिए अच्छा |
| --- | --- | --- | --- |
| NVLink (H100 SXM) | एक server के अंदर GPUs के बीच | 900 GB/s per GPU, दोनों directions मिलाकर | Tensor parallelism |
| PCIe Gen5 x16 | GPU से CPU; बिना NVLink वाले servers में GPUs | 128 GB/s, दोनों directions मिलाकर | Replicas; pipeline |
| InfiniBand NDR | Servers के बीच | 400 Gb/s per port, हर direction में लगभग 50 GB/s | Pipeline; training |

Cloud instance की listing पढ़ते समय "SXM" और "NVLink" (या "NVSwitch") देखो। एक "PCIe" GPU card में आमतौर पर NVLink नहीं होता, या बस एक bridge होता है जो सिर्फ़ दो cards को जोड़ता है। vLLM documentation की सलाह है कि बिना NVLink वाले GPUs पर, जैसे L40S, pipeline parallelism अक्सर tensor parallelism से बेहतर throughput देता है।

**Valid sizes.** Attention heads GPUs में बाँटे जाते हैं, इसलिए tensor-parallel size को head count को पूरा-पूरा बाँटना चाहिए। 64 heads वाला model 1, 2, 4, 8, 16, 32 या 64 GPUs use कर सकता है, पर 3, 5 या 6 नहीं। असल में, एक server के अंदर, इसका मतलब 1, 2, 4 या 8 है।

**Gotcha: shared key-value heads.** ज़्यादातर modern models attention heads के groups में keys और values share करते हैं। 8 key-value heads वाले 70B model को 8 GPUs में बाँटो तो हर GPU पर एक key-value head आता है, और KV cache बराबर बँट जाता है। 16 GPUs में बाँटो तो हर key-value head दो GPUs पर copy होता है, और हर GPU का cache घटना बंद हो जाता है।

### Pipeline parallelism: layers को stages में बाँटना

Layers 1 से 40 को server A पर और 41 से 80 को server B पर रखो। एक request stage A से गुज़रती है, network पार करती है, फिर stage B से गुज़रती है।

Latency के बारे में सटीक रहो। एक request सारी 80 layers से क्रम में गुज़रती है, चाहे वो एक GPU पर हों या कई पर। इसलिए pipeline parallelism हर stage boundary पर बस एक छोटा hop जोड़ता है, पर ये **एक request को तेज़ नहीं करता**, क्योंकि कोई stage दूसरे का काम नहीं बाँटता। Tensor parallelism request को तेज़ कर सकता है; pipeline नहीं कर सकता।

इसकी ताकत bandwidth है: हर stage सिर्फ़ अपना output भेजता है, हर stage पर एक बार, हर layer पर दो बार नहीं। इसीलिए servers के बीच, जहाँ links धीमे होते हैं, pipeline वाला split use होता है।

इसकी कमज़ोरी idle time है, जिसे **bubble** कहते हैं। अगर एक ही request in flight है, तो एक समय पर सिर्फ़ एक stage काम करता है। सारे stages को busy रखने के लिए batch को **micro-batches** में काटा जाता है, जो एक के पीछे एक pipe में चलते हैं। Training में, `p` stages और `m` micro-batches के साथ, समय का लगभग (p − 1) ÷ (m + p − 1) हिस्सा idle रहता है। जैसे, 4 stages और 16 micro-batches में लगभग 3 ÷ 19, यानी 16% बर्बाद होता है। Serving में कई concurrent requests इसी तरह pipe भर देती हैं।

### Mixture-of-experts models और expert parallelism

**Mixture-of-experts (MoE)** model में हर layer में कई feed-forward "experts" होते हैं, और एक छोटा router हर token को उनमें से बस कुछ के पास भेजता है। Size दो अलग numbers के हिसाब से चलता है:

- **Memory total parameters के हिसाब से चलती है।** हर expert load होना चाहिए, क्योंकि अगले token को उनमें से कोई भी चाहिए हो सकता है।
- **हर token का compute active parameters के हिसाब से चलता है।** सिर्फ़ चुने गए experts चलते हैं।

जैसे, Qwen3-235B-A22B में 235B total parameters हैं, जिनमें से हर token पर लगभग 22B active होते हैं (128 में से 8 experts)। 8-bit पर इसके weights को लगभग 235 GB चाहिए, इसलिए इसे कम से कम 80 GB के 4 GPUs चाहिए (4 × 72 = 288 GB usable), और cache के लिए बस लगभग 53 GB बचता है। एक 8-GPU server कहीं ज़्यादा जगह देता है। फिर भी हर token की cost लगभग एक 22B dense model के compute जितनी होती है।

**Expert parallelism** अलग experts को अलग GPUs पर रखता है और हर token को उस GPU पर भेजता है जिस पर उसका expert है। Attention वाला हिस्सा आमतौर पर copy किया जाता है (data parallel) या tensor parallelism से बाँटा जाता है। vLLM में ये एक flag है, `--enable-expert-parallel`। दो gotchas: popular experts पर load ज़्यादा हो जाता है जबकि बाकी खाली बैठे रहते हैं, इसलिए engines expert load balancing देते हैं; और बड़े batch sizes पर लगभग हर expert किसी न किसी token के काम आता है, इसलिए MoE की memory-reading वाली बचत घट जाती है।

### लंबे inputs: context और sequence parallelism

**Context parallelism** एक बहुत लंबे input को, जैसे 500,000-token का document, chunks में काटकर अलग GPUs पर रखता है। हर GPU अपने chunk के लिए attention compute करता है, जबकि keys और values group में घुमाए जाते हैं। **Sequence parallelism** tensor parallelism का एक training add-on है: layer के जो हिस्से tensor parallelism पूरे छोड़ देता है, जैसे normalisation, उन्हें sequence के हिसाब से बाँटता है, ताकि activation memory बचे। इनमें से किसी की भी ज़रूरत सिर्फ़ बहुत लंबे contexts पर पड़ती है।

### Training को serving से कहीं ज़्यादा memory चाहिए

Mixed precision और Adam optimiser के साथ full training हर parameter पर लगभग 16 bytes रखती है: 16-bit weights के 2, gradients के 2 और 32-bit optimiser states के 12 (weights की एक master copy और दो running averages)। एक 70B model के लिए ये activations से पहले ही लगभग 1,120 GB है। **Sharded data parallelism** (DeepSpeed में ZeRO, PyTorch में FSDP) इन states को copy करने की जगह data-parallel GPUs में फैला देता है। बड़े training runs इसे tensor और pipeline parallelism के साथ मिलाते हैं। Fine-tuning में LoRA और quantisation से आमतौर पर इसकी ज़्यादातर ज़रूरत ही खत्म हो जाती है।

### Engine आपके लिए क्या करता है

vLLM में, model को 4 GPUs में बाँटना बस एक setting है:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 NVLink-connected GPUs in this server.
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)
```

जो model एक server के लिए बहुत बड़ा हो, उसके लिए vLLM guide का rule of thumb है: tensor-parallel size बराबर हर server के GPUs, और pipeline-parallel size बराबर servers की गिनती। 8 GPUs वाले दो servers का मतलब `--tensor-parallel-size 8 --pipeline-parallel-size 2`। Servers के बीच vLLM default में Ray use करता है (एक Ray cluster start करो, फिर एक server पर एक `vllm serve` चलाओ); दूसरा option एक multiprocessing launcher है।

| Approach | क्या बाँटता है | कौन-सा link चाहिए | किसके लिए best | मुख्य cost |
| --- | --- | --- | --- | --- |
| Replicas (data parallelism) | कुछ नहीं; पूरी copies | कोई भी | ज़्यादा users, failover | हर copy को fit होना चाहिए |
| Tensor parallelism | हर layer के अंदर की matrices | NVLink, एक server के अंदर | बहुत बड़े models, हर token का कम समय | हर token पर हर layer में दो exchanges |
| Pipeline parallelism | Layers के groups | अच्छा network काफ़ी है | Servers के पार जाना; training | Latency में फ़ायदा नहीं; bubbles |
| Expert parallelism | MoE model के experts | तेज़; tokens experts तक जाते हैं | बड़े MoE models | Experts पर बराबर नहीं बँटा load |
| Context या sequence parallelism | Input sequence | तेज़ | बहुत लंबे inputs | Complexity |
| Sharded data parallelism | Gradients और optimiser states | बड़े models के लिए तेज़ | बड़े models train करना | ज़्यादा communication |

**अपने browser में try करो।** किसी model और traffic के लिए सबसे छोटा valid tensor-parallel size ढूँढो। Numbers बदलकर देखो।

```python
def kv_cache_gb(layers, kv_heads, head_dim, tokens, bytes_per=2):
    # 2 = one key and one value per token, per layer, per key-value head
    return 2 * layers * kv_heads * head_dim * bytes_per * tokens / 1e9

def smallest_tp(params_billion, bytes_per_param, cache_gb, gpu_gb, heads, usable=0.9):
    need = params_billion * bytes_per_param + cache_gb
    for tp in (1, 2, 4, 8):                      # sizes that fit in one 8-GPU server
        if heads % tp == 0 and tp * gpu_gb * usable >= need:
            return need, tp
    return need, None                            # needs pipeline across servers

# A 70B model: 80 layers, 64 heads, 8 key-value heads of size 128
cache = kv_cache_gb(80, 8, 128, tokens=60 * 4000)    # 60 requests x 4,000 tokens
for bpp, label in [(2, "16-bit"), (1, "8-bit")]:
    need, tp = smallest_tp(70, bpp, cache, gpu_gb=80, heads=64)
    print(f"{label}: {need:.0f} GB needed -> tensor-parallel size {tp}")
```

ये 16-bit पर लगभग 219 GB और size 4, और 8-bit पर लगभग 149 GB और size 4 print करता है। 8-bit model 2 GPUs में तभी आता है जब हर copy कम requests serve करे: 4,000 tokens पर लगभग 56। Script उन कुछ GB को गिनती में नहीं लेता जो engine खुद हर GPU पर use करता है, इसलिए margin रखो।

## एक worked example

Hyderabad की एक insurer 2,000 staff के लिए एक 70B open model (80 layers, 64 attention heads, size 128 के 8 key-value heads) self-host करना चाहती है, और p95 first-token time 2 seconds से कम चाहिए। हर server में 80 GB के 8 GPUs हैं, जो NVLink से जुड़े हैं। नीचे के traffic figures उनके planning के अनुमान हैं, measurements नहीं।

1. **Busy hour load.** मान लो busy hour में 600 staff active हैं, और हर एक 2 minutes में एक request भेजता है: यानी हर second 5 requests। हर request को streaming पूरी करने में लगभग 12 seconds लगते हैं। Requests in flight = arrivals × हर एक का समय = 5 × 12 = **60**। हर एक में लगभग 4,000 tokens होते हैं (instructions, policy text, chat history और reply)।
2. **KV cache.** 2 × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes, यानी हर token पर लगभग 0.33 MB। 60 × 4,000 tokens × 0.33 MB ≈ **79 GB**।
3. **क्या ये एक GPU में आता है?** 16-bit पर सिर्फ़ weights ही लगभग 140 GB हैं; एक GPU में 72 GB usable है। नहीं।
4. **सबसे छोटा valid split.** दो GPUs में 144 GB usable है: मुश्किल से weights, cache के लिए कुछ नहीं। तीन में 216 GB है, जो ज़रूरी 219 GB से थोड़ा कम है, और वैसे भी 64 heads को नहीं बाँटता। चार में 288 GB है: 140 GB weights के बाद लगभग **148 GB** cache बचता है, जो 4,000 tokens की लगभग 112 requests के लिए काफ़ी है। Tensor-parallel size 4।
5. **Capacity और failover.** एक copy busy hour संभाल लेती है, पर एक ही fault पूरी service रोक देगा। 4 GPUs की दो copies एक server भर देती हैं; दूसरा server पूरे server के fail होने से बचाता है।
6. **Cost.** ₹362 per GPU-hour के एक example rate पर (E2E Networks के H100 page पर on-demand price, 28 November 2026 को check किया, 18% GST से पहले), 730 घंटे के महीने के लिए एक 8-GPU server की cost 8 × 362 × 730 ≈ **₹21.1 lakh** है, GST के साथ लगभग ₹24.9 lakh। Prices provider और plan के हिसाब से बदलते हैं, इसलिए quotes लो। हर व्यक्ति के 40 requests per working day, 22 दिनों तक, यानी महीने में लगभग 7 billion tokens, या लगभग ₹300 per million tokens। इससे सस्ता hosted API ज़्यादा सस्ता पड़ेगा, जब तक data को उनके अपने servers पर ही न रहना हो। रात में एक ही copy चलाने से भी पैसे बचते हैं।

| Layout | GPUs | हर copy में cache की जगह | 4,000 tokens पर हर copy की requests | p95 first token (उदाहरण के लिए) |
| --- | --- | --- | --- | --- |
| Tensor 4, एक copy | 4 | लगभग 148 GB | लगभग 112 | 1.4 s; failover नहीं |
| Tensor 4, दो copies (चुना गया) | 8 | लगभग 148 GB | लगभग 112 | 0.9 s; एक GPU fault झेल लेता है |
| 8-bit पर Tensor 2, चार copies | 8 | लगभग 74 GB | लगभग 56 | 0.8 s, अगर quality टिकी रहे |
| Tensor 8, pipeline 2, एक copy | 16 | लगभग 1,010 GB | ज़रूरत से कहीं ज़्यादा | तेज़ नहीं; दोगुने GPUs |

Memory वाले columns हिसाब से निकाले गए हैं; latency वाला column बस ये दिखाता है कि एक load test क्या दिखा सकता है। 8-bit option को पहले असली claim notes पर quality tests पास करने होंगे।

## आम गलतियाँ

- **जो model एक GPU में आ जाए, उसे बाँटना।** Replicas आसान हैं, उन्हें तेज़ links नहीं चाहिए, और वो failures झेल लेते हैं।
- **सिर्फ़ weights से size निकालना।** Busy hour का KV cache weights जितना बड़ा हो सकता है।
- **PCIe या network पर tensor parallelism.** ये हर layer में दो बार बात करता है; इसे एक server के अंदर NVLink पर रखो।
- **ऐसा tensor-parallel size जो head count को पूरा न बाँटे।** Engine start होने से मना कर देगा; 2, 4 या 8 use करो।
- **Pipeline parallelism से latency घटने की उम्मीद करना।** ये servers के पार जाने के लिए है; ये एक request को कभी तेज़ नहीं करता।
- **Mixture-of-experts model का size active parameters से निकालना।** सारे experts memory में होने चाहिए।
- **Key-value heads की गिनती से आगे बाँटना।** हर GPU का cache घटना बंद हो जाता है।
- **सिर्फ़ एक copy.** एक GPU fault पूरी service गिरा देता है।
- **Average traffic से size निकालना।** Busy hour के लिए size निकालो, और असली prompt lengths पर load tests करो।

## जब आपको इसमें से कुछ नहीं चाहिए

- **Hosted APIs**: provider ये सब संभालता है। पहले उनकी per million tokens price को अपनी GPU cost से compare करो।
- **छोटे models** जो cache की जगह के साथ एक GPU में आ जाएँ: ज़रूरत पड़ने पर बस replicas जोड़ो।
- **LoRA और quantisation के साथ fine-tuning**, जो अक्सर एक ही GPU में हो जाती है।

## Demo से production तक

- GPUs खरीदने या किराए पर लेने से पहले **हर copy की memory measure करो** (अपनी context length और concurrency पर weights और KV cache)।
- **Links check करो**: tensor parallelism plan करने से पहले instance listing में "SXM" और "NVLink" confirm करो।
- असली prompt और reply lengths के साथ **हर layout का load-test करो**, और average नहीं, p95 देखो।
- जिस service पर लोग निर्भर हैं, उसके लिए **कम से कम दो copies रखो**, एक से ज़्यादा server पर।
- **हर replica को monitor करो**: queue length, KV cache use, latency और errors। Queue बढ़े तो copies जोड़ो।
- **Working day के हिसाब से scale करो**: traffic घटे तो रात में कम copies।
- **Model बदलने के बाद दोबारा plan करो**, क्योंकि size, head counts और context length से layout बदलता है।

2. 500 users को failover के साथ एक 70B model serve करने का layout बनाओ। बताओ हर हिस्सा कौन-सा parallelism use करता है और क्यों।
3. एक mixture-of-experts model में 120B total और 5B active parameters हैं। 8-bit पर weights के लिए कितने 80 GB GPUs चाहिए, और हर token एक 5B dense model और एक 120B dense model के मुकाबले कितना तेज़ हो सकता है?
4. किसी दोस्त को समझाओ कि tensor parallelism को NVLink क्यों चाहिए और pipeline parallelism को क्यों नहीं।

और गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 9 replica, tensor और pipeline parallelism को cover करता है, और Hugging Face Ultra-Scale Playbook बड़े पैमाने पर training को cover करता है।

**आपका काम पूरा तब है जब आप** किसी model और GPU के लिए replicas और बाँटने में से चुन सको, समझा सको कि tensor parallelism को NVLink क्यों चाहिए और pipeline को क्यों नहीं, mixture-of-experts model का size निकाल सको, और एक simple serving layout के GPUs और महीने की cost निकाल सको।
