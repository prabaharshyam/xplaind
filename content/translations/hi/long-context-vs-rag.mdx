## ये क्या है

किसी सवाल का जवाब देने के लिए model को ज़रूरी जानकारी देने के तीन तरीके हैं:

- **Long context**: पूरे documents prompt में डालो, फिर पूछो।
- **Retrieval (RAG)**: एक index पर एक बार search चलाओ और सिर्फ़ सबसे अच्छे कुछ passages prompt में डालो।
- **Agentic search**: model को search tools दो (keyword search, एक metadata filter, "open document", एक database query) और उसे तय करने दो कि क्या ढूँढना है, results पढ़ने दो और फिर से search करने दो, जब तक वो जवाब न दे सके।

28 November 2026 तक, Anthropic के हर latest Claude model की context window 1-million-token की है, Anthropic के अंदाज़े से लगभग 555,000 शब्द। तो long context अक्सर possible है। वो समझदारी है या नहीं, ये accuracy, cost, latency और scale पर निर्भर है।

| | Long context | RAG | Agentic search |
| --- | --- | --- | --- |
| Model क्या पढ़ता है | पूरे documents | एक search से 3 से 10 passages | कई steps में उसकी searches जो भी लौटाएँ |
| ताक़त | सब कुछ देखता है; cross-reference कर सकता है | सस्ता, तेज़, millions of documents तक scale करता है | Multi-step सवाल और exact identifiers follow करता है |
| कमज़ोरी | Length के साथ cost और delay बढ़ते हैं; लंबे inputs में accuracy गिरती है | एक search जो miss करे, वो ये भी miss करता है | ज़्यादा calls, धीमा, कम predictable |
| Engineering | कम | Chunking, indexing, tuning | अच्छे tools, step limits, logging |

```flow
title: Measure करने से पहले, पहला फ़ैसला
आपके documents -[window में आ जाएँ, अक्सर reuse हों]-> Caching के साथ long context
आपके documents -[बहुत ज़्यादा, छोटे factual सवाल]-> RAG
आपके documents -[बहुत ज़्यादा, जवाब को कई lookups चाहिए]-> Agentic search
RAG -[सवालों को पूरे documents चाहिए]-> Document-level retrieval, फिर long context
```

ये lesson Chennai की एक law firm को follow करता है, जो तीन बहुत अलग-अलग uses के लिए एक contract assistant बना रही है।

## ये कैसे काम करता है

### Inputs बढ़ने पर accuracy गिरती है

Models लंबे input की हर position को बराबर अच्छी तरह use नहीं करते।

- **Lost in the middle.** Liu और साथियों (2023) ने models को कई documents दिए और पाया कि accuracy तब सबसे ज़्यादा थी जब जवाब शुरुआत या आख़िर के पास था, और बीच में सबसे कम: एक U-shaped curve।
- **Context rot.** Chroma की report (July 2025) ने 18 models test किए और पाया कि input बढ़ने के साथ performance कम भरोसेमंद होती गई, simple tasks पर भी। जब सवाल और जवाब शब्दों और मतलब में कम मिलते-जुलते थे, यानी model को match करने की जगह infer करना पड़ा, तो ये और तेज़ी से गिरी। एक भी plausible distractor, यानी ऐसा sentence जो जवाब जैसा दिखे पर हो नहीं, accuracy घटा देता था, और ज़्यादा distractors उसे और घटाते थे।

इसे ऐसे समझो: जवाब के आसपास जितने ज़्यादा मिलते-जुलते sentences होंगे, model के ग़लत वाला उठाने के उतने ज़्यादा मौके होंगे।

इसलिए **advertised window** (API जितना accept करती है) को **effective context** से अलग रखो: वो length जिस पर *आपका* task accurate रहता है। "Needle in a haystack" test, यानी एक planted sentence ढूँढना, सबसे आसान case है, और आजकल के models इसे अक्सर pass कर लेते हैं। Pass होने से उन सवालों के बारे में कम पता चलता है जो clauses compare करते हैं, figures जोड़ते हैं या किसी rule के पुराने version को ignore करना माँगते हैं।

### Cost: हर call पर हर token के पैसे

जब तक document cache न हो, हर सवाल उसे पूरा दोबारा भेजता है और पूरे के पैसे दोबारा देता है। Claude Sonnet 5.5 की list prices, 28 November 2026 को Anthropic के pricing page पर check कीं:

| Item | USD प्रति million tokens | Input price का गुना |
| --- | --- | --- |
| Input | $2.00 | 1x |
| Cache write, 5-minute lifetime | $2.50 | 1.25x |
| Cache write, 1-hour lifetime | $4.00 | 2x |
| Cache read | $0.10 | 0.05x |
| Output | $10.00 | 5x |

Cache-read का गुना model के हिसाब से बदलता है: Claude Fable 5.2 पर 0.025x, Claude Opus 5.5 और Sonnet 5.5 पर 0.05x, और Claude Haiku 5.5 समेत बाक़ी ज़्यादातर पर 0.1x। कुछ models लंबे prompts के लिए प्रति token ज़्यादा charge भी करते हैं: Claude Haiku 5.5 का input $0.10 प्रति million tokens है जब prompt 100,000 tokens तक हो, और उससे लंबा होने पर पूरी request के लिए $0.50 (वही check date)। दूसरे providers caching का price अलग तरह से रखते हैं, इसलिए अपने provider का page पढ़ो और date लिख लो।

### Prompt caching: ये क्या बदलती है, और कब fail होती है

**कैसे काम करती है।** Provider आपके prompt की processed शुरुआत (prefix) store कर लेता है। बाद की कोई request जिसका prefix byte-for-byte वही हो, उसे cache से पढ़ती है: सस्ता, और first token तक तेज़। इसलिए लंबा, stable हिस्सा पहले रखो और सवाल आख़िर में, इससे सवाल भी वहीं रहता है जहाँ से model लिखना शुरू करता है।

**Lifetime.** Default में एक cache entry 5 minutes रहती है, और हर hit clock को reset करता है। 1-hour lifetime का write 2x पड़ता है। Anthropic के docs कहते हैं कि 5-minute cache एक read के बाद अपनी क़ीमत वसूल कर लेता है और 1-hour cache दो के बाद।

**Gotchas जो experts check करते हैं:**

- **Lifetime से लंबे gaps.** अगर 5-minute cache के साथ सवाल हर 15 minutes पर आएँ, तो हर call फिर से 1.25x write देती है, यानी आप बिना cache से *ज़्यादा* पैसे देते हो।
- **बदलता prefix.** Document से पहले एक timestamp, एक user name या re-order की गई tool list उसके बाद आने वाली हर चीज़ का match तोड़ देती है।
- **Parallel calls.** Cache entry तभी available होती है जब पहला response शुरू हो जाए, इसलिए एक साथ भेजे गए दस सवाल सब miss करते हैं।
- **हर user का एक document.** अगर 500 users अपना-अपना contract upload करें, तो वो 500 अलग cache writes हैं। Caching हर session की मदद करती है, पूरे system की नहीं।
- **Isolation.** Caches organisations के बीच कभी share नहीं होते, और Anthropic की API पर workspaces के बीच भी नहीं।

Check करो कि ये चला: response का `usage` `cache_creation_input_tokens` और `cache_read_input_tokens` report करता है। अगर reads zero पर ही रहें, तो कुछ prefix को तोड़ रहा है।

### Latency और scale

Input length के साथ time to first token बढ़ता है, इसलिए बहुत लंबे uncached prompts chat को धीमा महसूस कराते हैं। Agentic search हर step पर एक model round trip जोड़ता है। और window की एक limit है; किसी company के documents की नहीं। जैसे, लगभग 30,000 tokens वाले 18,000 manuals कुल 540 million tokens बनते हैं, यानी 1-million-token window का 540 गुना। जब corpus window से बड़ा हो जाए, तो किसी चीज़ को चुनना पड़ता है कि क्या भेजना है।

### Agentic search, तीसरा option

आपके code के चुने एक search की जगह, model खुद search चलाता है। Anthropic अपनी context engineering guide (September 2025) में इस "just in time" approach को समझाता है: Claude Code ज़रूरत पड़ने पर files ढूँढने के लिए glob और grep जैसे tools use करता है, जबकि कुछ files पहले से load होती हैं। Guide trade-off साफ़ बताती है: run time पर explore करना pre-computed retrieval results पढ़ने से धीमा है।

```flow
dir: LR
title: एक सवाल पर agentic search
सवाल -> Client से contracts search करो | filters के साथ keyword search
Client से contracts search करो -> Master agreement खोलो | clause 9 पढ़ता है
Master agreement खोलो -> Clause 9 के references search करो
Clause 9 के references search करो -> Citations के साथ जवाब
```

**कहाँ जीतता है:** ऐसे सवाल जहाँ अगला lookup पिछले result पर निर्भर हो, exact identifiers (clause numbers, error codes, part numbers) जिन्हें embeddings धुँधला कर देते हैं, और तेज़ी से बदलता data जिसे re-index करने की जगह live query कर सको। Tools हर user की permissions भी लागू कर सकते हैं।

**क्या cost है:** हर step एक और model call है जो बढ़ती हुई conversation दोबारा भेजती है। जैसे, 2,000 tokens के instructions और tools हों और हर step पर 3,000 tokens के results जुड़ें, तो छह steps 2,000 + 5,000 + ... + 17,000 = 57,000 input tokens भेजते हैं, जबकि एक RAG call में लगभग 3,000। पहले के turns cache करने से ये कम होता है।

**कैसे fail होता है:** बहुत जल्दी रुक जाता है, एक ही search पर loop करता है, या tool output से अपना context भर लेता है। समझदार defaults: steps पर cap लगाओ (जैसे, 8), tools पूरी files की जगह document IDs के साथ छोटे snippets लौटाएँ, और हर tool call log करो ताकि failures पढ़ सको।

### दो और patterns

- **Document-level retrieval.** Titles, summaries या metadata पर search करके सही कुछ पूरे documents चुनो, फिर long context को उन्हें पढ़ने दो। ये contracts, policies और reports के लिए ठीक है।
- **Map-reduce.** "सारी 40 board meetings summarise करो" जैसे काम के लिए, हर document को अलग से summarise करो (map), फिर summaries को जोड़ो (reduce)। ये किसी भी corpus size पर चलता है पर detail खो देता है, इसलिए हर summary से citations रखने को कहो।

```python
def doc_level_prompt(question, search_docs, load_doc, max_docs=3):
    docs = search_docs(question, k=max_docs)    # over titles, summaries and metadata
    context = "\n\n".join(f"<document title='{d['title']}'>\n{load_doc(d['id'])}\n</document>" for d in docs)
    return context + f"\n\nAnswer from the documents above. Cite titles and clause numbers.\nQuestion: {question}"
```

### Privacy

Long context पूरे documents model provider को भेजता है; RAG सिर्फ़ passages भेजता है। अगर documents में personal data है, तो client का data agreement और भारत की data-protection obligations check करो, और जो task को नहीं चाहिए उसे redact करो।

### Decision rules

- एक या कुछ documents, एक session में कई सवाल, ऐसे जवाब जिन्हें पूरा text चाहिए: **long context, cached**।
- बड़ा या बढ़ता collection, छोटे factual सवाल, कई users: **RAG**।
- ऐसे जवाब जिन्हें कई dependent lookups या exact identifiers चाहिए: **agentic search**, step limits के साथ।
- पूरे documents चाहिए पर चुनने को सैकड़ों हैं: **document-level retrieval, फिर long context**।

### अपने documents पर position और distractors test करो

Published studies चेतावनी देती हैं, जवाब नहीं। ये harness बनावटी audit notes (जो किसी real चीज़ से टकरा नहीं सकते) कई depths पर plant करता है, मिलते-जुलते distractors जोड़ता है और एक two-hop सवाल test करता है:

```python
import random

FACT = "Audit note: the Hosur warehouse inspection code is HW-7319."
DISTRACTORS = ["Audit note: the Hosur office inspection code is HO-7391.",
               "Audit note: the 2019 Hosur warehouse code, now withdrawn, was HW-1973."]
HOPS = ["Audit note: the Hosur warehouse audit is led by Farida Sheikh.",
        "Audit note: Farida Sheikh's desk extension is 4826."]
CODE_Q = "What is the current inspection code for the Hosur warehouse?"
TESTS = {   # name: (where to insert notes, question, expected answer)
    "single fact": (lambda d: [(d, FACT)], CODE_Q, "HW-7319"),
    "distractors": (lambda d: [(d, FACT)] + [(random.random(), s) for s in DISTRACTORS], CODE_Q, "HW-7319"),
    "two hops": (lambda d: [(d, HOPS[0]), ((d + 0.5) % 1, HOPS[1])],
                 "Which extension reaches the person who leads the Hosur warehouse audit?", "4826"),
}

def build(doc, inserts):
    paras = doc.split("\n\n")                        # insert between paragraphs, never mid-sentence
    for depth, note in sorted(inserts, reverse=True):
        paras.insert(int(len(paras) * depth), note)
    return "\n\n".join(paras)

def run(doc, ask, depths=(0.05, 0.25, 0.5, 0.75, 0.95), runs=3):
    for name, (inserts, question, expected) in TESTS.items():
        for d in depths:
            ok = sum(expected in ask(build(doc, inserts(d)) + "\n\nAnswer from the document only. " + question)
                     for _ in range(runs))
            print(f"{name:12} depth {d:4.0%}: {ok}/{runs} correct")
```

`ask` कोई भी function है जो prompt भेजे और text लौटाए। Anthropic SDK के साथ:

```python
import anthropic

client = anthropic.Anthropic()

def ask(prompt):
    r = client.messages.create(model="claude-opus-5-5", max_tokens=2000,   # the model you will deploy
                               output_config={"effort": "low"},
                               messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in r.content if b.type == "text")
```

उम्मीद करो कि single-fact row लगभग perfect होगी; distractor और two-hop rows ही असली जानकारी देती हैं। फिर अपने real सवालों के types जोड़ो, जैसे sections के बीच comparisons।

### एक cost model जिसे आप बदल सकते हो

```python
# Claude Sonnet 5.5 list prices in USD per million tokens, checked 28 November 2026
# (platform.claude.com/docs/en/about-claude/pricing). Re-check before you use them.
PRICE_IN, PRICE_OUT = 2.00, 10.00
WRITE_X, READ_X = 1.25, 0.05   # 5-minute cache write and cache read, as multiples of PRICE_IN

def call_usd(fresh_in, out, cache_write=0, cache_read=0):
    """Cost of one call. fresh_in: normal input tokens; cache_write/cache_read: cached prefix tokens."""
    inp = fresh_in + cache_write * WRITE_X + cache_read * READ_X
    return (inp * PRICE_IN + out * PRICE_OUT) / 1e6

Q, DOC, ASK, OUT, RAG_IN = 12, 40_000, 100, 300, 3_000

no_cache = Q * call_usd(DOC + ASK, OUT)
cached = call_usd(ASK, OUT, cache_write=DOC) + (Q - 1) * call_usd(ASK, OUT, cache_read=DOC)
expired = Q * call_usd(ASK, OUT, cache_write=DOC)   # every gap longer than the cache lifetime
rag = Q * call_usd(RAG_IN + ASK, OUT)

for name, usd in [("long context, no cache", no_cache), ("long context, cached", cached),
                  ("long context, cache always expired", expired), ("RAG, 3,000 tokens", rag)]:
    print(f"{name:36} ${usd:.3f}")
```

ये no cache पर $0.998, cached पर $0.182, cache हमेशा expire होने पर $1.238, और RAG के लिए $0.110 print करता है। Caching long-context bill को 80% से ज़्यादा घटा देती है, जिससे वो RAG के क़रीब आ जाता है; expire हुआ cache उसे सबसे महँगा option बना देता है। Dollars को उस दिन के rate पर convert करो, और अपने documents के tokens अपने provider के counter से गिनो, क्योंकि tokenizers अलग-अलग होते हैं।

## एक worked example

Chennai की एक law firm को contract assistant चाहिए। नीचे के numbers illustrative हैं, उस तरह के जो team record करेगी; costs 28 November 2026 को check की गई Claude Sonnet 5.5 prices पर हैं।

**1. एक contract review करना.** एक lawyer 60-page agreement (लगभग 40,000 tokens) upload करता है और लगभग 12 सवाल पूछता है: termination rights, indemnity caps, conflict करने वाले clauses। कई जवाबों को पूरा document चाहिए, इसलिए team long context use करती है, contract cached और सवाल आख़िर में। Lawyers सवालों के बीच अक्सर 5 minutes से ज़्यादा रुकते हैं, इसलिए वो 1-hour cache चुनते हैं। तब बारह सवालों की cost लगभग $0.24 होती है, uncached लगभग $1.00 के मुक़ाबले। मान लो 30-question test पर long context 27 सही करता है और chunk-based RAG 22, और RAG की ज़्यादातर ग़लतियाँ clauses के बीच cross-references पर हैं। Team distractor test भी चलाती है, क्योंकि उनके contracts में उसी clause के पुराने, बदले जा चुके versions हैं।

**2. Precedent library में search करना.** 25,000 पुराने contracts, किसी भी window से बहुत आगे। Lawyers पूछते हैं "IT services contracts में ऐसे indemnity clauses ढूँढो जो पिछले 12 months में दी गई fees तक capped हों"। Team metadata filters (contract type, year) के साथ hybrid retrieval use करके सबसे अच्छे 20 clauses ढूँढती है, फिर एक model उन्हें citations के साथ summarise करता है। वो recall measure करते हैं: मान लो 50 test सवालों में से 46 के लिए सही clause top 20 में है।

**3. Cross-references follow करना.** एक partner पूछता है: "इस client के साथ हमारे कौन-से contracts उस master agreement clause पर निर्भर हैं जो 2025 amendment में बदला?" एक search इसका जवाब नहीं दे सकता: system को amendment ढूँढना है, पढ़ना है कि कौन-सा clause बदला, फिर उस clause को cite करने वाले contracts ढूँढने हैं। Team तीन tools (client से search, document खोलना, clause number से search) और 8 steps के cap के साथ agentic search use करती है। मान लो एक typical जवाब में 5 tool calls और लगभग 30 seconds लगते हैं: chat के लिए बहुत धीमा, research task के लिए ठीक।

| Use case | Approach | क्यों | Illustrative result |
| --- | --- | --- | --- |
| एक 60-page contract | Long context, 1-hour cache | जवाबों को पूरा text चाहिए | Chunk RAG के 22/30 के मुक़ाबले 27/30; एक session का लगभग $0.24 |
| 25,000 precedents | Filters के साथ hybrid retrieval | किसी भी window से बहुत आगे | 46/50 के लिए सही clause top 20 में |
| Cross-reference सवाल | Agentic search, 8-step cap | अगला lookup पिछले पर निर्भर | हर जवाब पर लगभग 5 calls और 30 seconds |

## आम ग़लतियाँ

- **Advertised window पर भरोसा करना.** 1 million tokens accept करने वाला model उन्हें अच्छी तरह use करे, ये ज़रूरी नहीं। अपने सवालों के types पर effective context measure करो।
- **सिर्फ़ एक planted fact से test करना.** ये सबसे आसान case है। Distractors, two-hop सवाल और बिना जवाब वाले सवाल जोड़ो।
- **Caching के बिना costs compare करना**, या ऐसे cache पर भरोसा करना जो कभी hit नहीं होगा (ऊपर के gotchas देखो)।
- **सवाल, timestamp या user name को document से पहले रखना.** इससे cache टूटता है और accuracy पर भी असर पड़ता है।
- **"RAG ख़त्म हो गया" वाली सोच.** बड़े और बदलते collections को अब भी retrieval चाहिए, कम से कम documents चुनने के लिए।
- **One-hop lookups के लिए agent use करना.** अगर एक search से जवाब मिल जाए, तो agent बस calls और delay जोड़ता है।
- **बिना step limit या logs के agent चलाना.** जो failures दिखें ही नहीं, उन्हें ठीक नहीं कर सकते।
- **Personal data से भरे पूरे documents भेजना**, जब passages से ही सवाल का जवाब मिल जाता।

## जब choice साफ़ हो

- **एक छोटा document**: बस उसे prompt में डाल दो।
- **Millions of documents**: किसी न किसी तरह का retrieval चाहिए, कम से कम documents चुनने के लिए।
- **Structured data से जवाब**, जैसे records या tables: इनमें से कुछ नहीं, एक tool के ज़रिए database query करो।

## Demo से production तक

- **चुने हुए approach के लिए accuracy, cost और latency record करो** अपने golden set पर, और हर model change पर फिर check करो।
- **Cache hit rate track करो** `cache_read_input_tokens` से, और गिरने पर alert करो।
- **हर request के input tokens log करो** और अचानक बढ़ने पर alert करो।
- **Position और distractor tests फिर चलाओ** जब models बदलो या documents बढ़ें।
- **Agents के लिए, हर tool call log करो** और हर जवाब के steps पर नज़र रखो; बढ़ती गिनती एक early warning है।
- **Prices उनकी date के साथ फिर check करो**, कम से कम हर quarter।
