## ये क्या है

बाहर से AI product एक chat box जैसा दिखता है जो सवालों के जवाब देता है। अंदर से वो हिस्सों का एक छोटा system है, और जब कुछ गलत हो, तो fix इस पर निर्भर करता है कि **कौन-सा हिस्सा** fail हुआ। जो product managers हिस्से बना सकते हैं, वो engineers से काम की बातचीत कर सकते हैं। जो नहीं बना सकते, वो हर बार "बेहतर model" माँगते रह जाते हैं।

Language models पर बने ज़्यादातर AI products में वही हिस्से होते हैं। एक request को उनके बीच से गुज़रते देखो:

```flow
User -> 1 Interface | chat, in-app button, email, WhatsApp, API
1 Interface -> 2 Context assembly | system prompt + user input + history
3 Retrieval | company के documents और data में search -> 2 Context assembly
2 Context assembly -> 6 Input पर guardrails | topic limits, personal data, injection checks
6 Input पर guardrails -> 4 Model | जवाब लिखता है, या tool use करने को कहता है
4 Model -[tool माँगता है]-> 5 Tools | order देखो, ticket बनाओ
5 Tools -[result वापस]-> 4 Model
4 Model -> 6 Output पर guardrails | policy rules, format, ऐसे वादे नहीं जो निभा न सको
6 Output पर guardrails -> 7 Human checkpoint | जहाँ गलतियाँ महँगी हैं वहाँ review या approve
7 Human checkpoint -> User को जवाब -> 8 Evaluation और monitoring | quality, cost, feedback
```

| हिस्सा | क्या करता है | Fail हो तो |
| --- | --- | --- |
| **Interface** | जहाँ user product से मिलता है | Feature उलझा हुआ या छिपा हुआ |
| **Context assembly** | Instructions, input और history जोड़ता है | Model काम गलत समझता है |
| **Retrieval (RAG)** | Company के data से सही facts लाता है | गलत या पुराने जवाब |
| **Model** | जवाब बनाता है | मुश्किल कामों पर कमज़ोर reasoning |
| **Tools** | वो actions जो model माँग सकता है | गलत action, या कोई नहीं |
| **Guardrails** | Input और output पर checks | Unsafe या policy के बाहर के replies |
| **Human checkpoints** | महँगे cases के लिए review या approval | महँगी गलतियाँ customers तक पहुँच जाती हैं |
| **Evaluation और monitoring** | Release से पहले test sets; बाद में tracking | Problems आपको नहीं, customers को मिलती हैं |

इस lesson में हम Ritu के साथ चलेंगे, जो Mumbai के एक bank में product manager है, और पता लगा रही है कि bank के assistant ने एक customer से fee waiver का वादा क्यों कर दिया जो कभी हुआ ही नहीं। Lesson के अंत तक आप इस तस्वीर से समझा पाओगे कि जवाब गलत क्यों था और क्या बदलना चाहिए।

## ये काम कैसे करता है

### Quality कहाँ से आती है

गलत जवाब आमतौर पर चार जगहों में से किसी एक से आते हैं:

1. **गायब या पुरानी जानकारी**: retrieval को गलत document मिला, या सही वाला है ही नहीं।
2. **अस्पष्ट instructions**: system prompt में नहीं लिखा कि इस situation में क्या करना है।
3. **काम के लिए बहुत कमज़ोर model**: हो सकता है, पर लोगों के सोचने से कम होता है।
4. **Output पर कोई check नहीं**: user के देखने से पहले किसी ने गलती नहीं पकड़ी।

जब कुछ गलत हो, तो बड़ा model माँगने से पहले पूछो कि कौन-सा हिस्सा fail हुआ।

### Cost कहाँ से आती है

हर request की cost में आता है:

- **model tokens**, input (prompt, history, retrieved text) और output दोनों के;
- retrieval, tools और infrastructure।

लंबे prompts और लंबे जवाब ज़्यादा महँगे हैं। बड़े models हर token पर ज़्यादा महँगे हैं। दो आम बचतें: prompts के दोहराए जाने वाले हिस्सों की **caching**, और आसान requests को छोटे, सस्ते models तक **routing**।

### Risk कहाँ से आता है

आत्मविश्वास से बोले गलत जवाब, बिना check के लिए गए actions, खुला हुआ personal data, **prompt injection** (documents या emails में छिपे instructions जिन्हें model पढ़ता है), और अनुचित नतीजे। इनके controls हैं guardrails, tools पर permissions, human review और evaluation।

### Prompting, retrieval या fine-tuning?

| Approach | क्या बदलता है | बदलने की speed और cost | कब use करें |
| --- | --- | --- | --- |
| **Prompting** | Instructions और examples | तेज़, सस्ता | Behaviour, tone, format |
| **Retrieval (RAG)** | हर request पर model जो facts देखता है | मध्यम | ताज़ा या private जानकारी |
| **Fine-tuning** | Training से model की आदतें | धीमा, महँगा | बड़े पैमाने पर कोई खास style या skill |

ज़्यादातर products prompting और retrieval से शुरू होते हैं, और कई को fine-tuning की कभी ज़रूरत नहीं पड़ती।

### Agents

जब model खुद tool calls का पूरा सिलसिला तय करता है, तो वो product एक **agent** है। Agents लचीले हैं पर उनका अंदाज़ा लगाना कठिन है, इसलिए उन पर ये सीमाएँ चाहिए कि वो क्या कर सकते हैं, हर step के logs, और risky actions के लिए approvals। जहाँ fixed workflows काम करें वहाँ वही use करो, और agents वहाँ जहाँ लचीलापन फ़ायदा दे।

### Product manager के levers

Engineers **कैसे** तय करते हैं। आप तय करते हो **क्या और कितना अच्छा**:

- User की समस्या और success metric;
- कौन-से actions को approval चाहिए;
- कौन-सी failures मंज़ूर हैं और कौन-सी नहीं;
- हर request का budget;
- evaluation set में क्या-क्या आना चाहिए।

## एक example से समझो

Ritu, Mumbai के एक bank के mobile app में उस feature की product manager है जो credit card charges के बारे में customers के सवालों के जवाब देता है।

**शिकायत।** Assistant ने एक customer को बताया कि उनकी ₹2,500 की annual fee माफ़ कर दी जाएगी। वो नहीं हुई, और customer से पैसे कट गए।

Ritu और engineers request को हिस्सों से गुज़ारकर पीछा करते हैं:

| हिस्सा | उन्हें क्या मिला | Problem? |
| --- | --- | --- |
| Interface | In-app chat, normal चल रहा था | नहीं |
| Context assembly | System prompt में लिखा था कि सिर्फ़ bank के documents से जवाब दो | नहीं |
| Retrieval | पिछले साल का fee-waiver offer लौटाया, जो expire हो चुका था | **हाँ: यही कारण है** |
| Model | जो document दिया गया उसी से ईमानदारी से जवाब दिया | नहीं |
| Guardrails | कोई rule fees के वादे नहीं रोकता था | **हाँ: एक गायब control** |
| Evaluation | कोई test सवाल expired offers के बारे में नहीं था | **हाँ: एक कमी** |

**हर हिस्से के हिसाब से fixes:**

- **Retrieval:** documents को उनकी valid-from और valid-until dates से filter करो, ताकि expired offers कभी न लौटें।
- **Guardrails:** assistant को waivers या refunds का वादा करने से रोको; वो इसकी जगह कहता है, "आप eligible हो सकते हो। Check करने का तरीका ये है," और एक link देता है।
- **Evaluation:** test set में 30 fee सवाल जोड़ो, expired और भविष्य के offers समेत।
- **Monitoring:** एक नया metric, हर 10,000 chats पर गलत fee जानकारी की शिकायतें, जिसे हर हफ़्ते देखा जाए।

किसी को अलग model नहीं चाहिए था। जवाब इसलिए गलत था कि model को क्या दिया गया और किसी ने क्या check नहीं किया।

## आम गलतियाँ

- **हर error के लिए model को दोष देना।** कई data, retrieval या गायब checks से आते हैं।
- **Prompt को secret sauce समझना।** वो एक हिस्सा है; evaluation और data ज़्यादा मायने रखते हैं।
- **हर request की cost को नज़रअंदाज़ करना।** जो feature users को पसंद है, वो बड़े पैमाने पर घाटा कर सकता है।
- **कोई evaluation set नहीं।** इसके बिना हर बदलाव एक अंदाज़ा है।
- **Default में agents।** जहाँ fixed workflows काम करें वहाँ वही use करो।
- **Documents का कोई owner नहीं।** Retrieval उतना ही अच्छा है जितना उसके पीछे का content।

## Practice करो

Chip Huyen का "Building a Generative AI Platform" नीचे के link से पढ़ो, और Eugene Yan के LLM-based systems बनाने के patterns पर नज़र डालो।

1. **बनाओ।** अपने use किए किसी AI feature को चुनो, जैसे banking chatbot, shopping assistant या email writer, और उसके संभावित हिस्से बनाओ।
2. **Failures का पीछा करो।** उस feature की तीन संभावित failures के लिए बताओ कि कौन-सा हिस्सा शायद कारण होगा और एक fix क्या होगा।
3. **आपके फ़ैसले।** उन फ़ैसलों की list बनाओ जो product manager को उसके लिए लेने चाहिए: metric, approval points, मंज़ूर errors और हर request का budget।

**आपका काम पूरा जब:** आप किसी engineer को इस तस्वीर से समझा सको कि जवाब गलत क्यों था और आप क्या बदलवाना चाहते हो।
