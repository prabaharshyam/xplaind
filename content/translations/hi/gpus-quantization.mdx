## ये क्या है

अपने GPU पर language model चलाना ज़्यादातर **memory** का सवाल है। तीन चीज़ें इसके लिए होड़ करती हैं, और एक और चीज़ speed तय करती है:

- **Weights.** 16-bit precision पर हर parameter 2 bytes लेता है, तो एक 14B model को कुछ भी करने से पहले ही लगभग 28 से 30 GB चाहिए।
- **KV cache.** हर layer में हर token के लिए, model दो vectors store करता है, एक key और एक value। ये **KV cache** हर request की लंबाई के साथ और एक साथ चल रही requests की गिनती के साथ बढ़ता है।
- **Working space.** बीच के results (activations), CUDA runtime और engine buffers। ये lesson इनके लिए GPU का लगभग 10% spare रखता है।
- **Speed.** हर नए token का मतलब है सारे weights को memory से एक बार पढ़ना। इसलिए **memory bandwidth**, यानी GPU हर second कितने gigabytes पढ़ सकता है, आमतौर पर raw compute से ज़्यादा generation speed को limit करती है।

**Quantization** weights को, और कभी-कभी cache को भी, कम bits में store करता है, जैसे 16 की जगह 8 या 4। Cache के लिए ज़्यादा memory बचती है, और हर token पर कम bytes पढ़ने पड़ते हैं, तो generation अक्सर तेज़ हो जाती है। कीमत है कुछ quality का नुकसान, जिसे आप अपने task पर measure करते हो।

देखो एक 48 GB GPU, जैसे NVIDIA L40S, पर इसका क्या असर होता है, जब वो 40 layers, 8 key-value heads और head size 128 वाला एक 14B model (Qwen3-14B की shape) serve करता है। 10% spare के बाद, लगभग 43 GB usable है; हर request 4,000 tokens रखती है।

| Precision | Weights | KV cache के लिए बचा | 4,000 tokens की requests |
|---|---|---|---|
| 16-bit weights, 16-bit cache | लगभग 30 GB | लगभग 13 GB | लगभग 20 |
| 4-bit weights, 16-bit cache | लगभग 10 GB | लगभग 33 GB | लगभग 50 |
| 4-bit weights, 8-bit cache | लगभग 10 GB | लगभग 33 GB | लगभग 100 |

Rule ये है: **weights entry की कीमत तय करते हैं; कितने users fit होंगे, ये cache तय करता है।**

```flow
title: Precision कैसे चुनें
dir: LR
Model और peak traffic -> Cache के साथ 16-bit में fit?
Cache के साथ 16-bit में fit? -[हाँ]-> 16-bit serve करो
Cache के साथ 16-bit में fit? -[नहीं]-> FP8 weights और cache try करो | FP8 support चाहिए
FP8 weights और cache try करो -> Eval टिकता है? | हर language और task के हिसाब से
Eval टिकता है? -[हाँ]-> Ship करो और load test करो
Eval टिकता है? -[नहीं]-> 4-bit AWQ या GPTQ try करो, या ज़्यादा बड़ा GPU
```

इस lesson में हम Hyderabad की एक analytics firm के साथ चलेंगे, जो एक self-hosted extraction model के लिए GPUs size कर रही है।

## ये काम कैसे करता है

### Weights

Weights के लिए memory ≈ parameters × हर parameter के bytes।

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B से 8B | लगभग 14 से 16 GB | लगभग 7 से 9 GB | लगभग 4 से 6 GB |
| 14B | लगभग 28 से 30 GB | लगभग 14 से 16 GB | लगभग 8 से 10 GB |
| 32B | लगभग 64 GB | लगभग 32 से 34 GB | लगभग 18 से 20 GB |
| 70B | लगभग 140 GB | लगभग 70 GB | लगभग 37 से 40 GB |

4-bit हर parameter के लिए आधे byte से ज़्यादा क्यों है? Weights के हर छोटे group (अक्सर 128) के साथ एक scale (और अक्सर एक zero point) भी store होता है, जो हर weight पर लगभग 0.15 bits जोड़ता है। और input embeddings और output layer अक्सर 16-bit पर ही रहते हैं: बड़ी vocabulary वाले 8B model के लिए, ये लगभग 1 billion parameters, यानी 2 GB है। Plan करने से पहले checkpoint की असली file size check करो।

### KV cache

हर token के लिए, हर layer हर **key-value head** के लिए एक key और एक value store करती है:

हर token का cache = 2 × layers × key-value heads × head size × हर value के bytes

Numbers model की `config.json` से पढ़ो: `num_hidden_layers`, `num_key_value_heads` और `head_dim` (या `hidden_size` को `num_attention_heads` से भाग देकर)। ज़्यादातर modern models **grouped-query attention** use करते हैं: कई attention heads कुछ key-value heads share करते हैं। एक common 8B shape में 32 attention heads हैं पर सिर्फ़ 8 key-value heads, तो attention heads use करने से आपका estimate चार गुना बड़ा हो जाता है।

फिर **tokens in flight** से गुणा करो: peak active requests × हर request के tokens। Peak एक load test या traffic logs से लो, कभी average नहीं।

दो gotchas। **Hybrid** models, जैसे Qwen3.5, लगभग चार में से सिर्फ़ एक layer में full attention use करते हैं, तो सिर्फ़ उन्हीं layers को गिनो। और **mixture-of-experts** models को अपने सारे experts के लिए memory चाहिए, भले ही हर token उनमें से कुछ ही use करे।

### Engine उस memory के साथ क्या करता है

vLLM जैसे serving engines दो ideas use करते हैं। **PagedAttention** हर request का cache छोटे blocks में store करता है, जो request के बढ़ने पर ही जुड़ते हैं, तो एक छोटी request सबसे लंबी मुमकिन request जितनी जगह reserve नहीं करती। **Continuous batching** हर step पर, जैसे-जैसे बाकी requests खत्म होती हैं, नई requests को running batch में जोड़ता है, तो GPU busy रहता है। दोनों में से कोई भी memory पैदा नहीं करता, तो ऊपर वाला हिसाब ही limit रहता है।

Start-up पर, vLLM cache size को tokens में log करता है, और आपकी maximum request length के लिए "maximum concurrency" भी। उस line को अपने estimate से compare करो; आपके setup के लिए वही सच है। vLLM v0.34.0 से, `--gpu-memory-utilization` unset हो तो सारी free memory use होती है, तो कोई share सिर्फ़ तब set करो जब कोई और process GPU share कर रहा हो।

### Prefill और decode

हर request के दो phases होते हैं, और दोनों की limits अलग हैं।

- **Prefill** पूरा prompt एक साथ पढ़ता है और cache भरता है। ये हर prompt token पर लगभग 2 × parameters operations करता है: 14.8B model और 6,000-token prompt के लिए, लगभग 180 trillion। Prefill **compute** से limited है और **time to first token** तय करता है, तो लंबे prompts का मतलब है धीमे first tokens।
- **Decode** हर step में एक token लिखता है। हर step सारे weights और हर request का cache पढ़ता है, पर हर byte पर थोड़ा ही maths करता है। ये **memory bandwidth** से limited है, और **tokens per second** तय करता है।

एक request के लिए quick ceiling: bandwidth ÷ weights के bytes। एक L40S 864 GB/s पढ़ता है, तो एक 10 GB 4-bit model एक request के लिए ज़्यादा से ज़्यादा लगभग 86 tokens per second तक पहुँच सकता है; एक 30 GB 16-bit model ज़्यादा से ज़्यादा लगभग 29। असली numbers कम होते हैं। Batching की वजह से ही serving affordable है: weights को एक बार पढ़ने से batch की हर request serve होती है, तो total throughput batch size के साथ बढ़ता है, जब तक compute या cache memory खत्म न हो जाए। कीमत ये है कि हर user हर token के लिए थोड़ा ज़्यादा इंतज़ार करता है, तो concurrency को अपने latency budget के हिसाब से tune करो।

### GPU चुनना

| GPU | Memory | Bandwidth | Native FP8 | आम use |
| --- | --- | --- | --- | --- |
| NVIDIA L4 | 24 GB | 300 GB/s | हाँ | 8B तक के models, हल्का traffic |
| NVIDIA L40S | 48 GB | 864 GB/s | हाँ | Quantization के साथ 8B से 32B models |
| NVIDIA A100 80 GB | 80 GB | लगभग 2,000 GB/s | नहीं | 16-bit पर 14B से 32B, fine-tuning |
| NVIDIA H100 SXM | 80 GB | 3,350 GB/s | हाँ | Busy services, NVLink के साथ बड़े models |
| NVIDIA H200 | 141 GB | 4,800 GB/s | हाँ | एक GPU पर 8-bit में लगभग 70B |

तीन gotchas। A100 में FP8 units नहीं हैं: vLLM उस पर FP8 checkpoints को weight-only load कर सकता है, जिससे memory बचती है पर compute नहीं। Blackwell GPUs, जैसे B200, hardware 4-bit floating point (NVFP4 और MXFP4) जोड़ते हैं; OpenAI के gpt-oss models MXFP4 में ship होते हैं, इसीलिए gpt-oss-120b एक 80 GB GPU पर fit हो जाता है। और H100 PCIe cards में SXM version से कम bandwidth (लगभग 2,000 GB/s) है।

India में आप इन्हें local GPU clouds जैसे E2E Networks (जो Delhi NCR और Chennai में H100 capacity list करता है) और Yotta से, या global clouds के Indian regions से rent कर सकते हो। Eligible startups, researchers और institutions IndiaAI Compute Portal पर subsidised hours के लिए apply कर सकते हैं। ये example rates हैं: E2E के pages पर L40S ₹102 per GPU-hour और H100 ₹362 per GPU-hour on demand list थे, 18% GST से पहले (28 November 2026 को check किया)। Prices और stock अक्सर बदलते हैं, तो जिस दिन plan करो, उस दिन providers के pages, और अपना quota, check करो।

### Quantization formats

- **FP8** (8-bit floating point). ज़्यादातर models के लिए लगभग 16-bit जैसी quality, आधी memory, और FP8 units वाले GPUs पर तेज़ maths। अक्सर सबसे पहले यही try करना चाहिए।
- **AWQ और GPTQ** (4-bit integers, सिर्फ़ weights). Weight memory का लगभग एक चौथाई, साथ में ऊपर वाले overheads, और थोड़ा-सा quality नुकसान। पहले से quantized checkpoint download करो, हो सके तो model maker का बनाया हुआ।
- **NVFP4 और MXFP4** (4-bit floating point). Blackwell GPUs पर तेज़; ज़्यादा नए हैं और कम बड़े पैमाने पर test हुए हैं।
- **bitsandbytes NF4.** Transformers में load time पर quantize करता है। Experiments और QLoRA के लिए आसान, पर serve करने में ज़्यादा धीमा।
- **GGUF.** llama.cpp का file format, जिस पर Ollama और LM Studio बने हैं, laptops, CPUs और Apple Silicon के लिए। एक Q4_K_M file हर weight पर लगभग 4.8 से 4.9 bits use करती है, तो एक 8B model लगभग 5 GB का होता है। Speed bandwidth के हिसाब से चलती है: अगर laptop 80 GB/s पर memory पढ़ता है, तो लगभग 16 tokens per second ceiling है।
- **8-bit KV cache.** Cache को FP8 में store करने से वो आधा हो जाता है। किसी भी और बदलाव की तरह इसकी quality भी measure करो।

जो सबसे ऊँची precision fit हो, वहाँ से नीचे आओ: 16-bit, फिर FP8, फिर 4-bit। हर एक के लिए अपना eval और एक छोटा load test चलाओ, और peak पर quality, memory और speed record करो। वो सबसे सस्ता option चुनो जिसका quality नुकसान आपका client लिखित में accept करे।

### Code में एक memory planner

```python
def memory_plan(cfg, params_billion, weight_bits=16, kv_bits=16,
                context_tokens=4000, concurrent=20, gpu_gb=48, spare=0.10):
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights_gb = params_billion * weight_bits / 8          # rough: real 4-bit files are larger
    kv_token_mb = 2 * cfg["num_hidden_layers"] * kv_heads * head_dim * kv_bits / 8 / 1e6
    kv_gb = kv_token_mb * context_tokens * concurrent / 1e3
    usable = gpu_gb * (1 - spare)
    fits = weights_gb + kv_gb <= usable
    max_requests = int((usable - weights_gb) * 1e3 / (kv_token_mb * context_tokens))
    return round(weights_gb, 1), round(kv_token_mb, 3), round(kv_gb, 1), fits, max_requests

# The shape of a common 8B model; in real use, load the dict from config.json
cfg = {"num_hidden_layers": 32, "num_attention_heads": 32, "num_key_value_heads": 8, "head_dim": 128}
print(memory_plan(cfg, 8, gpu_gb=24))                  # (16.0, 0.131, 10.5, False, 10)
print(memory_plan(cfg, 8, weight_bits=8, kv_bits=8, gpu_gb=24))  # (8.0, 0.066, 5.2, True, 51)
```

16-bit पर, 4,000 tokens की 20 requests को 16 GB weights के ऊपर लगभग 10.5 GB cache चाहिए: 24 GB card के लिए बहुत ज़्यादा, जो सिर्फ़ 10 रख पाता है। 8-bit में ये fit हो जाती हैं, हालाँकि असली FP8 file लगभग 9 GB की है, क्योंकि embeddings 16-bit पर ही रहते हैं।

### Quantized model को load और serve करना

Transformers में quick experiments के लिए:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("your-org/your-8b-instruct",
                                             quantization_config=bnb, device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

Serving के लिए, fast quantized kernels वाला engine use करो। vLLM quantized checkpoint की config से method पढ़ लेता है:

```bash
vllm serve your-org/your-14b-instruct-awq --max-model-len 8192 --kv-cache-dtype fp8
```

16-bit model को load time पर FP8 में quantize करने के लिए, vLLM v0.34.0 `--quantization fp8_per_tensor` use करता है; सिर्फ़ `fp8` अब ये नहीं करता। `--max-model-len` एक request की लंबाई पर cap लगाता है; इसे उतना set करो जितना आपके users सच में भेजते हैं।

### Quality का नुकसान measure करना

हर precision पर golden set चलाओ और हर slice के हिसाब से compare करो, सिर्फ़ overall नहीं। Quantization का असर अक्सर सबसे पहले लंबी reasoning, maths, code और कम common languages पर पड़ता है, तो Hindi, Telugu या Tamil cases को English से अलग score करो। कोई precision तभी रखो जब हर ज़रूरी slice तय limit के अंदर रहे।

## एक example से समझो

Hyderabad की एक analytics firm 200 staff के लिए invoices से fields निकालने वाला model self-host करना चाहती है। Prompts और replies मिलाकर 6,000 tokens तक जाते हैं। p95 time to first token 3 seconds से कम रहना चाहिए। नीचे दिए quality scores और latencies illustrative हैं, method दिखाने के लिए; memory figures calculate किए गए हैं।

**1. Peak measure करो.** एक busy दिन के logs replay करने पर peak **80 active requests** पर आता है (average लगभग 35)। 80 के लिए size करो।

**2. Model.** 14.8 billion parameters, 40 layers, 8 key-value heads और head size 128 वाला एक 14B instruct model। हर token का cache: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes, लगभग 0.16 MB। एक 6,000-token request लगभग 0.98 GB रखती है; peak को लगभग 79 GB cache चाहिए।

**3. Original proposal.** 16-bit पर tensor parallelism के साथ दो H100 80 GB GPUs। Usable memory 2 × 72 = 144 GB है; weights लगभग 30 GB लेते हैं, लगभग 114 GB बचता है, यानी लगभग 116 requests। Fit हो जाता है, पर 2 × ₹362 = ₹724 प्रति घंटा लगता है, और एक GPU fail हुआ तो service रुक जाती है।

**4. Quantize करो.** Maker का 4-bit AWQ checkpoint लगभग 10 GB है। 500 असली invoices पर field accuracy: 16-bit पर 95.1%, 4-bit पर 94.6%, और साथ में FP8 cache भी हो तो 94.5%। Client की limit 94.0% है, तो दोनों pass।

**5. L40S cards पर fit करो.** एक L40S लगभग 43 GB usable देता है। 4-bit weights के साथ 33 GB बचता है। 16-bit cache के साथ, उसमें 6,000 tokens की 33 requests आती हैं, तो peak के लिए 3 GPUs चाहिए और एक चौथा spare के तौर पर। FP8 cache के साथ, लगभग 67 आती हैं, तो दो GPUs peak (134) संभाल लेते हैं और एक fail हो तो तीसरा service चालू रखता है।

**6. Speed check करो.** तीन L40S cards पर 80 concurrent requests के load test में p95 time to first token 1.8 seconds आता है, budget के अंदर। हर user के tokens H100s से धीमे आते हैं, जिनमें लगभग चार गुना bandwidth है, पर target पूरा होता है।

| Option | GPUs | 6,000 tokens पर requests | एक GPU failure झेल लेता है? | प्रति घंटा cost (GST से पहले) |
| --- | --- | --- | --- | --- |
| 16-bit, tensor parallelism | दो H100 | लगभग 116 | नहीं | ₹724 |
| 16-bit, दो copies | दो H100 | लगभग 86 (हर एक में 43) | नहीं, 43 तो 80 से कम है | ₹724 |
| 4-bit weights, 16-bit cache, copies | चार L40S | लगभग 132 (हर एक में 33) | हाँ | ₹408 |
| 4-bit weights, FP8 cache, copies (चुना गया) | तीन L40S | लगभग 201 (हर एक में 67) | हाँ | ₹306 |

हर L40S एक load balancer के पीछे अपनी copy चलाता है। 28 November 2026 को check किए गए example rates पर, चुना गया plan 730-hour महीने के लिए लगभग ₹2.23 lakh का पड़ता है, जबकि proposal ₹5.29 lakh का, दोनों 18% GST से पहले। Reserved prices अलग होते हैं, इसलिए firm फिर भी quotes लेती है।

## आम गलतियाँ

- **सिर्फ़ weights के लिए size करना.** कितने users fit होंगे, ये peak पर cache तय करता है।
- **Average traffic से size करना.** Measured peak use करो, वरना सबसे busy सुबह service fail हो जाएगी।
- **Cache formula में key-value heads की जगह attention heads use करना,** या 2 का factor छोड़ देना।
- **4-bit को हर parameter के लिए ठीक आधा byte मान लेना.** Scales और 16-bit embeddings लगभग 10 से 50% जोड़ते हैं।
- **Slice के हिसाब से evals के बिना quantize करना.** एक English-only average, Indian languages, maths और code में नुकसान छुपा देता है।
- **एक GPU पर fit होने वाले model को split करना.** Copies ज़्यादा आसान हैं, बेहतर scale होती हैं और failures झेल लेती हैं।
- **ये मान लेना कि FP8 हर जगह तेज़ है.** A100 में FP8 units नहीं हैं; GPU generation check करो।
- **Maximum context ज़रूरत से बहुत ज़्यादा set करना.** एक बहुत बड़ी request कई छोटी requests को बाहर धकेल सकती है।

## कब GPUs के बारे में सोचने की ज़रूरत नहीं

- **Hosted API use कर रहे हो,** या client की cloud model service।
- **CPUs पर छोटे models,** जैसे embedding models, classifiers या laptop पर एक 4-bit GGUF demo।
- **कम या अचानक उछलने वाला volume,** जहाँ पूरे महीने rent किया GPU per token pay करने से महँगा पड़ता है।

## Demo से production तक

- **Memory plan करो** weights, peak cache और working space के लिए; engine के start-up log में इसे confirm करो।
- **Golden set चलाओ** हर precision बदलने पर, हर language और task के हिसाब से।
- **असली GPUs पर load test करो** बड़े पैमाने पर rent करने से पहले, peak पर first-token time और errors देखते हुए।
- **कम से कम एक spare GPU रखो** ताकि failure या upgrade से service न रुके।
- **Production में cache usage और queue length monitor करो,** और cache भरने से पहले alert करो।
