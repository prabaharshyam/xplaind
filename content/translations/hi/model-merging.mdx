## ये क्या है

Fine-tuning एक model को बदलता है। **Model merging** दो या ज़्यादा models के weights मिलाकर उन्हें एक model में जोड़ता है। कोई training run नहीं चाहिए: merge बस weight files पर किया गया arithmetic है।

Merging सबसे अच्छा तब काम करता है जब models **एक ही base model** से fine-tune हुए हों। क्यों? Fine-tuning weights को उनकी शुरुआती जगह से बस थोड़ी दूर ले जाता है। एक base से fine-tune हुए दो models अब भी उसके पास और एक-दूसरे के पास रहते हैं, और weight number 1,000 का दोनों में लगभग एक ही मतलब होता है। Scratch से train हुए दो models अपने features अलग-अलग order में सीखते हैं, इसलिए उनका average बेमेल numbers मिला देता है और अक्सर दोनों को तोड़ देता है।

Merge क्यों करें?

- **Mixed requests के लिए एक model.** अगर एक request में दो skills चाहिए (complaint classify करना और reply draft करना), तो merged model उसे एक call में संभाल लेता है, models के बीच चुनने के लिए कोई router नहीं चाहिए।
- **Ship करने के लिए एक file.** Merged model एक सादा model है। कोई भी runtime उसे load कर सकता है, वो भी जिनमें adapter support नहीं है।
- **एक के बाद एक train करने से कम forgetting.** Task A पर और फिर task B पर train करने से model अक्सर A भूल जाता है। हर task को अलग train करके merge करने से ये risk कम होता है, पर इसकी अपनी problem है: tasks के बदलाव आपस में interfere करते हैं, इसलिए हर task को फिर से test करना पड़ता है।
- **GPUs नहीं चाहिए.** Simple merges CPU पर चल जाते हैं। आपको models के लिए disk space और memory चाहिए, GPU नहीं।

जब inputs LoRA adapters हों, तो merging से आपको memory **नहीं** बचती। LoRA adapter छोटा होता है। मिसाल के तौर पर, Llama-3-8B shape वाले model की हर linear layer पर rank 16 करीब 42 million parameters है, 16-bit पर लगभग 84 MB, जबकि base 16-bit पर लगभग 16 GB है। तीन adapters base में करीब 1.6% जोड़ते हैं। उन्हें merge करने से लगभग कुछ नहीं बचता।

Merging **ensemble** से भी अलग है। Ensemble हर request पर कई models चलाता है और उनके जवाब जोड़ता है, इसलिए हर request में कई calls का खर्च होता है। Merge weights को एक बार जोड़ता है; उसके बाद आप एक model को normal cost पर serve करते हो।

Reputation पर एक note. 2024 में Hugging Face के Open LLM Leaderboard का top merges से भर गया था। Leaderboard team ने merges को default में छिपा दिया, ये कहकर कि उनके scores अक्सर असली use में टिकते नहीं थे। Leaderboard खुद March 2025 में retire हो गया। सबक वही है: किसी merge के public scores आपके tasks के बारे में बहुत कम बताते हैं।

```flow
title: Merging fine-tuned models
Base model -> Fine-tune for task A | adapter or full
Base model -> Fine-tune for task B
Fine-tune for task A -> Task vector A | A minus base
Fine-tune for task B -> Task vector B | B minus base
Task vector A -> Combine | average, SLERP, TIES, DARE
Task vector B -> Combine
Combine -> Merged model
Merged model -> Test every task and safety
Test every task and safety -[pass the bar]-> Ship one model
Test every task and safety -[miss the bar]-> Keep separate models
```

## ये काम कैसे करता है

### Task vectors

Fine-tuned model के weights में से base model के weights घटाओ तो आपको एक **task vector** मिलता है: वो बदलाव जो fine-tuning ने किया। Task vectors को base में जोड़ो तो skills जुड़ती हैं। एक को घटाओ तो कोई behaviour कमज़ोर होता है। जिस paper ने task vectors को ये नाम दिया (Ilharco and others, ICLR 2023), उसने toxic text से सीखा गया task vector घटाकर GPT-2 से कहीं कम toxic outputs निकलवाए।

LoRA में adapter task vector को factored form में store करता है: दो पतली matrices, A और B, जिनका product B times A हर layer का बदलाव है। ये detail आगे काम आएगी। A matrices और B matrices को अलग-अलग जोड़ना, असली बदलावों को जोड़ने जैसा नहीं है।

### Weighted average और task arithmetic

सबसे simple merge है task vectors का एक weighted sum, जो base में जोड़ा जाता है। Weights 0.5 और 0.5 हों तो ये average है; 1.0 और 1.0 हों तो ये plain **task arithmetic** है। एक base वाले models के लिए averaging हैरानी की हद तक अच्छा काम करता है। "Model soups" paper (Wortsman and others, ICML 2022) ने एक model के कई fine-tuned versions का average लिया और अक्सर सबसे अच्छे single version को भी पीछे छोड़ दिया, बिना किसी extra running cost के।

कमज़ोरी है interference. Average उस बदलाव को आधा कर देता है जो सिर्फ़ एक task ने किया, और जब दो tasks किसी weight को उल्टी दिशाओं में धकेलते हैं, तो वो एक-दूसरे को cancel कर देते हैं।

### SLERP

**Spherical linear interpolation** दो models को सीधी line की जगह एक arc पर blend करता है। Arc क्यों? अगर दो weight vectors अलग-अलग दिशाओं में point करते हैं, तो उनके बीच की सीधी line का midpoint दोनों से छोटा होता है। Model के weights सिकुड़ जाते हैं, जिससे दोनों models की धार कम हो सकती है। Arc size बनाए रखता है। 0 से 1 तक का एक factor `t` blend तय करता है: 0 पहला model है, 1 दूसरा। SLERP ठीक दो models लेता है; तीसरे के लिए फिर से merge करो।

### TIES और DARE

Fine-tuning लगभग हर weight बदलता है, पर ज़्यादातर बदलाव बहुत छोटे होते हैं। ये छोटे बदलाव कम ही जोड़ते हैं, फिर भी merge होने पर टकराते हैं। **TIES** (Yadav and others, NeurIPS 2023) हर task vector को तीन steps में साफ़ करता है:

1. **Trim.** हर task vector में सिर्फ़ सबसे बड़े बदलाव रखो। `density` setting वो हिस्सा है जो रखा जाता है: 0.3 का मतलब top 30% रखो।
2. **Sign elect करो.** हर weight के लिए kept changes को जोड़ो। जिस दिशा में कुल बदलाव ज़्यादा है, वो जीतती है।
3. **Disjoint mean.** सिर्फ़ उन kept changes का average लो जो जीतने वाले sign से मेल खाते हैं। जो बदलाव सिर्फ़ एक task ने किया, वो अपने पूरे size में रहता है।

**DARE** (Yu and others, 2023) trim step की जगह लेता है। ये हर task vector के बदलावों का एक random हिस्सा drop करता है और बचे हुओं को scale up करता है ताकि कुल असर लगभग उतना ही रहे। इसे TIES के साथ `dare_ties` के रूप में जोड़ा जा सकता है: DARE का random drop, फिर TIES का sign election.

जिन papers ने ये दोनों methods पेश किए, वो plain averaging से बेहतर नतीजे report करते हैं। इसे अपने tasks पर check करो। Model Breadcrumbs और DELLA जैसे नए variants भी हैं, और mergekit उन्हें support करता है। Sakana AI ने 2024 में दिखाया कि एक evolutionary search अपने आप अच्छी merge recipes ढूँढ सकती है। पहले TIES अच्छे से सीखो।

**अपने browser में try करो.** दो task vectors: weight 0 पर conflict, weight 3 पर सहमति, और weights 4 और 5 पर ऐसे बदलाव जो सिर्फ़ एक task ने किए।

```python
import numpy as np

# Changes two fine-tunes made to the same 8 weights (their task vectors).
# Weight 0: the tasks disagree. Weight 3: they agree. Weights 4 and 5: only one task cares.
# The rest are tiny changes, mostly noise.
task_a = np.array([ 0.90, 0.02, -0.03, 0.80, 0.01, -0.70,  0.02, 0.00])
task_b = np.array([-0.85, 0.03,  0.02, 0.75, 0.60,  0.01, -0.02, 0.01])

def ties(vectors, density=0.4):
    stacked = np.stack(vectors)
    # 1. Trim: in each vector, keep only the largest changes (the top `density` share).
    trimmed = []
    for v in stacked:
        cut = np.quantile(np.abs(v), 1 - density)
        trimmed.append(np.where(np.abs(v) >= cut, v, 0.0))
    trimmed = np.stack(trimmed)
    # 2. Elect a sign per weight: the direction with more total change wins.
    sign = np.where(trimmed.sum(axis=0) >= 0, 1.0, -1.0)
    # 3. Disjoint mean: average only the kept changes that agree with that sign.
    agree = (np.sign(trimmed) == sign) & (trimmed != 0)
    count = np.maximum(agree.sum(axis=0), 1)
    return (trimmed * agree).sum(axis=0) / count

average = (task_a + task_b) / 2
merged = ties([task_a, task_b])
for name, v in [("task A ", task_a), ("task B ", task_b), ("average", average), ("TIES   ", merged)]:
    print(name, v.round(2) + 0.0)
```

```text
TIES    [ 0.9   0.    0.    0.78  0.6  -0.7   0.    0.  ]
```

इसे weight by weight पढ़ो। Average weight 0 को लगभग शून्य तक cancel कर देता है, तो दोनों tasks उसे खो देते हैं, और weights 4 और 5 को आधा कर देता है। TIES 4 और 5 को पूरे size में रखता है और noise साफ़ कर देता है। पर weight 0 देखो: TIES task A का 0.9 रखता है और task B का बदलाव पूरी तरह फेंक देता है। TIES conflicts को गायब नहीं करता। वो एक winner चुनता है, और हारने वाला task कीमत चुकाता है। इसीलिए merge के बाद precise task अक्सर drop होता है।

### Layer stacking

Weights मिलाने की जगह आप अलग-अलग models की layers से एक model बना सकते हो, जिसे कभी-कभी "frankenmerge" कहते हैं। इससे model बड़ा हो सकता है। SOLAR 10.7B (Kim and others, 2023) ने एक 32-layer 7B model की दो copies लीं, हर एक से 8 layers हटाईं, और उन्हें जोड़कर 48 layers बनाईं। अच्छा काम करने के लिए उसे further pretraining चाहिए थी, और ज़्यादातर stacked models को चाहिए होती है।

### PEFT से LoRA adapters merge करना

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("base-model-id")
model = PeftModel.from_pretrained(base, "adapters/complaints", adapter_name="complaints")
model.load_adapter("adapters/replies", adapter_name="replies")

# ties_svd applies TIES to the real change (B times A) of each layer, then compresses it back to a LoRA.
model.add_weighted_adapter(
    adapters=["complaints", "replies"], weights=[1.0, 1.0],
    adapter_name="merged", combination_type="ties_svd", density=0.5,
)
model.set_adapter("merged")
merged = model.merge_and_unload()   # one plain model, no adapter needed at run time
merged.save_pretrained("merged-model")
```

PEFT की gotchas (version 0.22 पर check की हुई):

- Plain `linear`, `ties` और `dare_*` types A और B matrices को अलग-अलग जोड़ते हैं। PEFT का अपना documentation `linear` को rough approximation कहता है। `_svd` types को prefer करो, जो असली बदलाव पर काम करते हैं।
- Plain types के लिए हर adapter का rank `r` एक जैसा होना चाहिए। `_svd` types के लिए नहीं।
- `cat` adapters को साथ-साथ जोड़ता है। ये बदलावों का exact sum देता है, पर नए adapter का rank सारे ranks का जोड़ होता है।
- DoRA adapters support नहीं होते।

### mergekit से full models merge करना

Full fine-tunes के लिए open-source tool mergekit एक छोटी YAML file से merge चलाता है:

```yaml
merge_method: ties
base_model: ./base-8b
models:
  - model: ./complaints-8b
    parameters: {density: 0.5, weight: 1.0}
  - model: ./replies-8b
    parameters: {density: 0.5, weight: 1.0}
dtype: bfloat16
```

इसे `mergekit-yaml merge.yml ./merged` से चलाओ। TIES के लिए mergekit default में कुल weight से divide करता है (`normalize`), इसलिए weights 1.0 और 1.0 एक बराबर blend की तरह काम करते हैं।

### Settings चुनना

जब तक measure न करो, merge settings बस अंदाज़े हैं। एक छोटी search सस्ती है, क्योंकि merge में training run नहीं लगता।

1. हर task के लिए एक छोटा **dev set** अलग रखो, जैसे 100 से 200 examples, final test set से अलग।
2. बराबर weights से शुरू करो और density 0.2, 0.5 और 0.8 try करो। SLERP के लिए `t` 0.3, 0.5 और 0.7 try करो।
3. अगर कोई task drop हो, तो उसका weight बढ़ाओ, जैसे 1.0 से 1.5, और फिर try करो।
4. सबसे अच्छी setting अपने acceptance bar से चुनो, average score से नहीं। फिर test set एक बार चलाओ।
5. हर config को उसके scores के साथ save करो, ताकि कोई भी merge फिर से बना सको।

| Method | कैसे जोड़ता है | ताकत | ध्यान रखो |
| --- | --- | --- | --- |
| Weighted average | Task vectors का weighted sum | Simple baseline, अक्सर अच्छा | Single-task बदलाव आधे होते हैं; conflicts cancel होते हैं |
| SLERP | दो models को arc पर blend करता है | Weight size बना रहता है; smooth blend | एक बार में दो models |
| TIES | Trim, sign elect, disjoint mean | कई tasks के साथ बेहतर | Conflict पर एक task हारता है; density tune करो |
| DARE | Random drop, फिर rescale | TIES के साथ अच्छा जमता है | Random: कुछ seeds compare करो |
| Layer stacking | Layers जोड़ता है, size बढ़ा सकता है | बड़ा model बना सकता है | आमतौर पर further training चाहिए |

## एक example से समझो

Mumbai के एक bank के पास तीन LoRA adapters हैं, सभी rank 16, एक ही open 8B base model पर: complaint classification, English और Hindi में reply drafting, और KYC field extraction. Branch staff पूरा customer letter paste करता है, और कई letters ऐसी complaints होती हैं जिनका reply भी चाहिए। Bank की IT team ने जो offline app approve किया है वो एक बार में एक model file load करता है और हर request के लिए adapter नहीं चुन सकता। KYC scanning app में एक अलग screen है, जो दिन में कुछ ही बार use होती है।

यहाँ merge करने की वजह memory नहीं है। 16-bit पर करीब 16 GB के base में तीन adapters बस करीब 250 MB जोड़ते हैं। वजहें हैं एक model file और mixed letter के लिए एक call.

Merge करने से पहले team test sets और bar लिख लेती है:

- **Complaints:** 400 labelled letters; accuracy.
- **Replies:** 150 letters; दो reviewers हर draft को एक rubric से 1 से 5 तक score देते हैं, और scores का average लिया जाता है।
- **KYC:** 300 scanned documents; बिल्कुल सही extract हुए fields का हिस्सा।
- **Safety:** 200 prompts जिन्हें assistant को मना करना है, जैसे किसी दूसरे customer के account details की request.
- **Bar:** कोई भी task अपने अलग adapter से 2 points से ज़्यादा नीचे न हो (replies के लिए 0.2), और refusals कम न हों।

वो अलग dev sets पर tune करते हैं, फिर test sets चलाते हैं। नीचे के numbers समझाने के लिए हैं, measured results नहीं।

| Model | PEFT setting | Complaints | Replies (5 में से) | KYC | Bar पूरा? |
| --- | --- | --- | --- | --- | --- |
| अलग adapters (target) | कोई नहीं | 93% | 4.3 | 96% | target |
| तीनों का average | `svd`, हर एक का weight 1/3 | 89% | 4.0 | 84% | नहीं |
| तीनों का TIES | `ties_svd`, density 0.5, weights 1.0 | 92% | 4.2 | 88% | नहीं: KYC |
| TIES, KYC का weight बढ़ाया | ऊपर जैसा, KYC weight 1.5 | 91% | 4.1 | 91% | नहीं: KYC |
| Complaints और replies का TIES | `ties_svd`, density 0.5 | 92% | 4.2 | n/a | हाँ |

Plain average हर skill को एक-तिहाई तक dilute कर देता है, इसलिए हर जगह fail होता है। TIES बेहतर करता है, पर KYC extraction, जो सबसे precise task है, ऐसे conflicts हारता है जो वो झेल नहीं सकता। उसका weight बढ़ाने से KYC को मदद मिलती है और बाकियों को नुकसान होने लगता है।

तो team दो files ship करती है। Letter screen merged complaints-and-replies model use करती है, जो mixed letter को एक call में संभाल लेता है। Scan screen एक दूसरा model load करती है, यानी base जिसमें KYC adapter fold किया गया है, सिर्फ़ तब जब कोई document scan हो। Safety set उसी refusal count के साथ pass होता है। उन्होंने इसे फिर से चलाया क्योंकि merging ऐसे behaviour को भी कमज़ोर कर सकता है जिस पर कोई adapter train नहीं हुआ था।

## आम गलतियाँ

- **अलग-अलग bases वाले models merge करना.** ये भी check करो कि inputs का tokenizer और chat template एक ही हो। अलग-अलग prompt formats की उम्मीद रखने वाले models का merge टूटे हुए replies दे सकता है।
- **Memory बचाने के लिए LoRA adapters merge करना.** Adapters छोटे होते हैं; बचत बहुत कम है।
- **Average score से judge करना.** एक task बुरी तरह गिरे तब भी merge average पर ठीक दिख सकता है। हर task को उसके अपने target से compare करो।
- **Test set पर tune करना.** Test set पर density और weights चुनने से test score असली use से बेहतर दिखता है। Dev set use करो।
- **LoRA adapters पर plain `linear` या `ties` use करके exact sum की उम्मीद करना.** ये types A और B matrices को अलग-अलग जोड़ते हैं। Exact sum के लिए `cat` use करो; `_svd` types तभी exact हैं जब `svd_rank` कम से कम सारे ranks के जोड़ जितना हो।
- **Safety checks छोड़ देना.** 2024 की एक study (Hammoud and others, Findings of EMNLP) ने पाया कि merging एक model का कमज़ोर safety behaviour merged model में ला सकता है।
- **Public merges पर भरोसा करना.** Download किए गए merge को अपने data पर test करो।
- **Licence भूल जाना.** Merge को उसमें शामिल हर model की terms माननी होती हैं। एक non-commercial input ये limit कर सकता है कि आप merge को कैसे use कर सकते हो, इसलिए हर licence पढ़ो। कुछ licences naming rules भी जोड़ते हैं: Llama 3.1 का licence कहता है कि उससे बने और share किए गए model का नाम "Llama" से शुरू हो।

## Merge कब न करें

ये सवाल इसी order में पूछो:

1. **क्या आप adapters को अलग-अलग serve कर सकते हो?** LoRA adapters के लिए ये आमतौर पर सबसे अच्छी choice है। vLLM जैसे servers एक base model को GPU memory में रखते हैं और हर request पर अलग adapter लगाते हैं, एक ही batch में भी। मिसाल: `vllm serve base-model-id --enable-lora --lora-modules complaints=./adapters/complaints replies=./adapters/replies --max-loras 4`. हर request अपने adapter का नाम बताती है। LoRA adapters को mainly तब merge करो जब runtime ये न कर सके, या एक request को एक साथ कई skills चाहिए हों।
2. **क्या कोई task बहुत precise है?** Extraction, maths या strict formats अक्सर merge में हारते हैं। उसे अलग रखो।
3. **क्या आप एक multi-task fine-tune कर सकते हो?** हर task का data हो, तो mix पर train करना अक्सर merge से बेहतर होता है, क्योंकि model tasks को balance करना सीखता है।
4. **क्या models अलग-अलग bases से हैं?** Merge मत करो।

## Demo से production तक

- **Merges को models की तरह version करो.** Config file, input model versions, scores और test set versions साथ रखो।
- **अलग models रखो**, fallback के तौर पर और comparison point के तौर पर।
- **हर task, साथ में general और safety checks test करो**, हर release से पहले, उस bar के सामने जो आपने पहले से तय किया।
- **कोई भी input बदले तो फिर से merge और test करो.** नया adapter version मतलब नया merge.
- **हर input का licence record करो**, merged model के card में।
