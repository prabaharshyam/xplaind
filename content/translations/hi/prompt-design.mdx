## ये क्या है

किसी application में prompt ही code है। **System prompt** में वो standing instructions होती हैं जो हर request में एक जैसी रहती हैं: model का role, task, rules, output format और examples। **User message** में इस request का खास input होता है। अच्छा prompt design नतीजों को साफ़, एक जैसा और testable बनाता है, हज़ारों अलग-अलग inputs पर, सिर्फ़ उस एक पर नहीं जो आपने try किया।

```flow
System prompt | हर request में वही, एक versioned file: role और audience, task, context (price list, timings, policies), rules ("पक्का न हो तो बता दो और handover करो"), output format और length, 2-3 अलग-अलग examples -> Model
User message | हर request में बदलता है: customer का message, data की तरह माना जाता है -> Model
Model -> जवाब -> आपके test set से check
```

System prompt fixed और versioned रहता है; एक request से दूसरी request तक सिर्फ़ user message बदलता है।

इस lesson में हम चेन्नई की एक phone-repair chain को देखेंगे, जो एक लाइन के prompt को ऐसे prompt में बदलती है जो सैकड़ों असली messages पर चलता है।

## ये काम कैसे करता है

**System prompt में क्या जाता है।**

- *Role और audience*: "आप चेन्नई की एक mobile phone repair chain के customers के सवालों के जवाब देते हो।"
- *Task*: हर input के साथ क्या करना है।
- *Context*: model को जिन facts की ज़रूरत है (policies, product names, tone के guidelines)।
- *Rules*: क्या करना है और क्या नहीं, और पक्का न होने पर क्या करना है ("अगर सवाल repairs के बारे में नहीं है, तो कहो कि आप सिर्फ़ repairs में मदद कर सकते हो")।
- *Output format*: सही structure, length, भाषा।
- *Examples*: एक से तीन solved input-output जोड़े।

Secrets को prompts से बाहर रखो; users कभी-कभी model से उन्हें बुलवा लेते हैं।

**साफ़ बोलो और वजह बताओ।** "जवाब 80 words से कम रखो क्योंकि customers phone पर पढ़ते हैं", "concise रहो" से बेहतर काम करता है। Models वजहें अच्छे से follow करते हैं।

**Examples, descriptions से बेहतर हैं।** एक अच्छा example tone, length, format और edge-case की handling, सब एक साथ दिखा देता है। अलग-अलग तरह के examples use करो, जिनमें एक मुश्किल case भी हो, ताकि model किसी एक example की हूबहू नकल न करे।

**लंबे prompts को structure दो।** Instructions, context और examples के लिए साफ़ sections या tags use करो ताकि model उन्हें अलग-अलग पहचान सके। लंबे reference documents सवाल से पहले रखो।

**Data को instructions से अलग रखो।** User के दिए text को साफ़ mark करो ("customer का message नीचे दिए tags के बीच है") ताकि उसके अंदर की instructions को data माना जाए।

**कई inputs पर test करो।** जो prompt एक example पर चलता है, वो अक्सर दूसरों पर फ़ेल होता है। 20 से 50 असली inputs का set बनाओ, जिसमें मुश्किल और अजीब वाले भी हों, सब चलाओ, failures पढ़ो, एक चीज़ बदलो, और फिर चलाओ। यहीं से evals शुरू होते हैं।

**Prompts को version करो।** उन्हें version control में files की तरह रखो, कई जगह code में paste करके नहीं।

**Prompt सुधारने का loop:**

| Round | क्या बदला | 50 test messages में pass count |
| --- | --- | --- |
| 0 | "Customer को politely जवाब दो।" | 18 |
| 1 | Role, facts और price list जोड़ी | 31 |
| 2 | Rules जोड़े: list से बाहर की prices नहीं, rival shops नहीं, भाषा customer जैसी | 39 |
| 3 | Format और 60-word की वजह जोड़ी | 42 |
| 4 | दो examples जोड़े | 44 |
| 5 | Water-damage का rule और example जोड़ा | 47 |

हर round में एक ही चीज़ बदली, इसलिए team को पता था कि किस बदलाव से फ़ायदा हुआ। जब किसी बदलाव से pass count घटा, तो उन्होंने उसे वापस कर दिया। यही अनुशासन prompt के काम को अंदाज़े से engineering बनाता है।

**साफ़ sections वाला prompt।** Tags से model को साफ़ पता चलता है कि कौन-सा हिस्सा क्या है, और आपके लिए एक बार में एक हिस्सा बदलना आसान होता है:

```python
SYSTEM = """<role>
You answer WhatsApp questions from customers of Fixit, a phone repair chain in Chennai.
</role>

<facts>
Shops: T. Nagar, Velachery, Anna Nagar. Open 10 am to 8 pm, closed Tuesdays.
{price_list}
</facts>

<rules>
- Quote only prices in the price list. If a repair is not listed, say a technician will call.
- Never mention other shops.
- Reply in the customer's language (English, Tamil or Tanglish).
- Keep replies under 60 words, because customers read on phones.
- Water damage: never promise a fix; ask them to bring the phone in, switched off.
</rules>

<examples>
Customer: screen change for redmi note 12 how much
Reply: A Redmi Note 12 screen replacement is ₹2,400 and takes about an hour. Visit any Fixit shop, 10 am to 8 pm, except Tuesdays.
</examples>"""

def build_messages(customer_text):
    return [{"role": "user", "content": f"<customer_message>\n{customer_text}\n</customer_message>"}]
```

**Prompt को code की तरह test करो।** हर test message चलाओ, code में properties check करो, और pass count print करो:

```python
import re

PRICES = {"2,400", "1,800", "3,200", "650"}                # every price in the list
TAMIL = re.compile(r"[஀-௿]")

def check(customer_text, reply):
    problems = []
    if len(reply.split()) > 60:
        problems.append("too long")
    for amount in re.findall(r"₹\s?([\d,]+)", reply):
        if amount not in PRICES:
            problems.append(f"unlisted price ₹{amount}")
    if TAMIL.search(customer_text) and not TAMIL.search(reply):
        problems.append("did not reply in Tamil")
    if re.search(r"\b(other shop|competitor)\b", reply, re.I):
        problems.append("mentioned another shop")
    return problems

def run(cases, generate):
    failures = {c: p for c in cases if (p := check(c, generate(c)))}
    print(f"{len(cases) - len(failures)}/{len(cases)} passed")
    return failures
```

Code checks ज़्यादातर rule-तोड़ने वाली गलतियाँ मुफ़्त में पकड़ लेते हैं। Model judge सिर्फ़ उन खूबियों के लिए रखो जो code नहीं देख सकता, जैसे कि जवाब ने सच में सवाल का जवाब दिया या नहीं।

**बड़े tasks को steps में तोड़ो।** एक ही prompt जो classify करे, price ढूँढे, जवाब लिखे और उसका translate भी करे, debug करना मुश्किल होता है। कई छोटे prompts (पहले classify, फिर जवाब, फिर check) में से हर एक को test करना आसान है, आसान steps के लिए सस्ते models use हो सकते हैं, और ये भी साफ़ दिखता है कि गड़बड़ी कहाँ हुई। कीमत ये है कि calls ज़्यादा होती हैं और थोड़ी देरी भी।

**जहाँ ज़रूरी हो, reasoning के लिए जगह दो।** जिन tasks में हिसाब लगाना पड़ता है, जैसे कई rules के हिसाब से eligibility check करना, वहाँ model से जवाब देने से पहले reasoning करवाने पर अक्सर accuracy बढ़ती है। Reasoning models ये खुद करते हैं। Reasoning को customer को दिखने वाले हिस्से से बाहर रखो, और reasoning को नहीं, final answer को check करो।

**Prompts को versions के साथ files में रखो।** हर prompt को version नाम के साथ file में रखो, start-up पर load करो, और हर request के साथ version को log करो। फिर quality में गिरावट उस prompt बदलाव तक ढूँढी जा सकती है जिसने उसे पैदा किया।

## एक example से समझो

चेन्नई की एक phone-repair chain ऐसा assistant चाहती है जो customers के WhatsApp messages के जवाब का draft बनाए।

पहला prompt: "Customer को politely जवाब दो।" 30 असली messages पर जवाब लंबे होते हैं, ऐसी prices का वादा करते हैं जो shop देती ही नहीं, और rival brands की warranty के सवालों का भी जवाब दे देते हैं।

बेहतर system prompt (संक्षेप में):

- Role: "FixFast Mobiles" के लिए, जिसके चेन्नई में चार stores हैं, staff के review के लिए जवाबों के draft बनाना।
- Facts: आम repairs की price list, store timings, parts पर 90 दिन की warranty।
- Rules: list में न हो ऐसी price का वादा कभी मत करो ("inspection के बाद confirm करेंगे" कहो); दूसरी shops की बात मत करो; customer की भाषा (Tamil या English) में जवाब दो; 60 words से कम, क्योंकि staff इन्हें WhatsApp पर भेजते हैं।
- Format: greeting, जवाब, अगला step।
- दो examples: English में screen replacement का सवाल और Tamil में battery का सवाल।

उन्हीं 30 messages और 20 नए messages पर दोबारा चलाया: 50 में से 44 drafts बिना या मामूली edits के काम के निकले, पहले 30 में से 11 थे। छह failures ज़्यादातर water damage के बारे में हैं; team उनके लिए एक rule और एक example जोड़ती है और दोबारा चलाती है।

**बाकी छह failures ने क्या सिखाया।** Failures पढ़ने में दस मिनट लगे और ये किसी भी आम prompting tip से ज़्यादा काम का निकला। Customers ने water damage को कई तरह से बताया ("phone बाल्टी में गिर गया", "बारिश में भीग गया"), और model ने ऐसी खराबी के लिए repair prices बता दीं जिसमें पहले inspection चाहिए। एक rule ("किसी भी liquid damage के लिए phone को लाने को कहो; price कभी मत बताओ") और एक example ने ज़्यादातर ठीक कर दिए।

## आम गलतियाँ

- **एक ही example पर test करना।** अलग-अलग तरह का set use करो और failures पढ़ो।
- **धुंधली instructions।** साफ़ बोलो कि क्या चाहिए और क्यों।
- **पक्का न होने के case का कोई rule नहीं।** Model को बताओ कि जवाब उसके context में न हो तो क्या करना है।
- **Prompts में secrets।** वहाँ कभी passwords या keys मत डालो।
- **एक साथ कई बदलाव।** एक चीज़ बदलो, दोबारा चलाओ, तुलना करो।

- **Prompt में rules ठूँस देना।** "कभी नहीं" और "हमेशा" की पूरी page model को उलझा देती है और खुद का विरोध करती है। Rules कम, खास और वजह के साथ रखो, और जो test set के हिसाब से ज़रूरी नहीं हैं, उन्हें हटा दो।
- **Prompt को दो-तीन inputs पर test करना।** 20 से 50 का set use करो, जिसमें अजीब वाले भी हों।
- **कई steps वाले task के लिए एक विशाल prompt।** उसे बाँटो ताकि हर step test हो सके।
- **Prompts को कई जगह code में paste करना**, जिससे versions अलग-अलग हो जाते हैं।

## जब prompt पर काम करना जवाब नहीं है

- **Model के पास facts ही नहीं हैं**: लंबे prompts की जगह retrieval या tools जोड़ो।
- **कई ध्यान से किए rounds के बाद भी एक ही format की गलती बनी रहे**: structured output या fine-tuning इसे ठीक कर सकते हैं।
- **Task को सटीक logic चाहिए**, जैसे tax की गणना: उसे code में करो और model से नतीजा समझवाओ।
- **फ़ायदा थम गया है**: अगर तीन rounds में हर बार सिर्फ़ एक pass बढ़ रहा है, तो रुकावट कहीं और है।

## Demo से production तक

- **Prompts को files में version करो** और हर request पर version log करो।
- **हर prompt बदलाव पर CI में test set चलाओ**, pull request पर pass count के साथ।
- **एक बार में एक चीज़ बदलो** और एक छोटा changelog रखो कि हर version ने क्या ठीक किया।
- **Model बदले तो दोबारा test करो**, क्योंकि एक model के लिए tune किया prompt दूसरे पर अलग चल सकता है।
- **User text को साफ़ mark किए tags में रखो** और उसे कभी rules बदलने मत दो।

## Practice करो

नीचे link की prompting best-practices guide पढ़ो।

1. किसी ऐसे domain के assistant के लिए system prompt लिखो जिसे आप जानते हो, role, rules, format और दो examples के साथ।
2. 20 test inputs का set बनाओ जिसमें पाँच मुश्किल वाले हों, और लिखो कि कौन-से outputs फ़ेल होते हैं।
3. Prompt को दो rounds में बेहतर करो, हर बार एक चीज़ बदलकर, और हर के बाद pass count लिखो।
4. अपने 20 test inputs पर check function जोड़ो, और हर prompt version का pass count एक छोटी table में लिखो।

ज़्यादा गहराई के लिए, Chip Huyen की *AI Engineering* (O'Reilly, 2025) का chapter 5 prompt structure, examples, tasks को steps में तोड़ना, model को सोचने का समय देना और prompts को organise करना कवर करता है।

**आपका काम पूरा जब** आप एक prompt, एक test set और before-and-after pass count दिखा सको।
