## ये क्या है

**Software design** का मतलब है तय करना कि program को parts में कैसे बाँटना है और वो parts आपस में कैसे बात करेंगे। ज़्यादातर अच्छे designs के नीचे दो idea होते हैं:

- **Cohesion**: हर part एक काम करता है, और उसके अंदर सब कुछ उसी काम का है।
- **Coupling**: parts एक-दूसरे की details पर कितना depend करते हैं। Loose coupling का मतलब है कि एक part बदलो तो बाकी को छूना नहीं पड़ता।

अच्छा design यानी high cohesion और loose coupling। बुरी तरह design किया program वो है जहाँ email template बदलने के लिए model को call करने वाला code भी edit करना पड़ता है।

**SOLID principles** वहाँ तक पहुँचने के पाँच जाने-माने guidelines हैं। ये object-oriented programming से आए हैं, पर यही ideas सादे Python functions और modules पर भी लगते हैं। इन्हें रटना ज़रूरी नहीं; ज़रूरी है वो problems पहचानना जिनसे ये बचाते हैं।

## ये काम कैसे करता है

पाँचों principles, आसान शब्दों में:

| Principle | आसान शब्दों में | कैसे पता चले कि आप इसे तोड़ रहे हो |
| --- | --- | --- |
| **S**ingle responsibility | एक module या class, बदलने की एक वजह | ऐसी file जो data पढ़ती है, model call करती है और email भेजती है |
| **O**pen for extension | नया behaviour नया code जोड़कर लाओ, चलते हुए code को edit करके नहीं | हर नए provider के लिए एक लंबी chain में एक और `elif` |
| **L**iskov substitution | Interface की कोई भी implementation वहाँ चले जहाँ interface चाहिए | ऐसा "provider" जो अपने आधे methods पर "not supported" raise करता है |
| **I**nterface segregation | छोटे, focused interfaces | एक विशाल `Storage` class जिस पर हर part depend करता है |
| **D**ependency inversion | Interface पर depend करो, किसी specific library पर नहीं | Business logic के बीचोंबीच `openai.chat...` call होना |

**Dependency injection** इनमें से ज़्यादातर के पीछे का practical tool है। Function अपनी ज़रूरत की चीज़ खुद बनाने की जगह, उसे अंदर receive करता है:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

अब `summarise` को फ़र्क नहीं पड़ता कि कौन-सा provider use हो रहा है। Production में असली client पास होता है; tests में fake; provider बदलना मतलब एक नई class लिखना, `summarise` को edit करना नहीं।

```flow
title: Business logic एक छोटे interface पर depend करता है, provider पर नहीं
summarise() -> ModelClient interface | complete(prompt) -> str
ModelClient interface -> Provider A client
ModelClient interface -> Provider B client
ModelClient interface -> Fake client for tests
```

AI application organise करने का एक आम तरीका यही idea पूरे codebase में लगाता है:

- **Core logic** (product जो करता है: ticket classify करना, prompt बनाना, answer score करना) किसी बाहरी चीज़ पर depend नहीं करता।
- **Adapters** (model client, vector store, database, email) छोटे interfaces implement करते हैं।
- **Wiring** किनारे पर (API startup, CLI) असली adapters बनाकर अंदर पास करती है।

**Functions या classes?** हर जगह classes ज़रूरी नहीं। साफ़ inputs और outputs वाले सादे functions अक्सर Python में सबसे साफ़ design होते हैं। Class तब लो जब कुछ ऐसा state या settings हों जो कई functions share करते हैं, जैसे API key और timeout वाला client, या जब एक ही interface की कई बदली जा सकने वाली implementations चाहिए।

**Interviews में।** Low-level design rounds में किसी छोटी चीज़ के classes और interfaces design करने को कहते हैं, जैसे rate limiter या parking lot। System design rounds में पूछते हैं कि services आपस में कैसे जुड़ती हैं। दोनों में वही idea चलता है: parts के नाम बताओ, हर एक को एक काम दो, और दिखाओ कि बाकी को छुए बिना एक को कैसे बदलोगे या test करोगे।

## एक example से समझो

Delhi के एक legal-tech startup में Rohit की team ने एक हफ़्ते में contract summariser बना लिया। सब कुछ एक 300 lines की file में था: वो PDF पढ़ती थी, एक model provider को सीधे call करती थी, Markdown format करती थी और result email करती थी।

दो महीने बाद तीन requests एक साथ आती हैं: एक client चाहता है कि उसका data उसके अपने cloud में hosted model से process हो, sales team को summaries Word documents में चाहिए, और tests में minutes लगते हैं क्योंकि हर test असली API calls करता है।

Rohit steps में refactor करता है, पहले आज के behaviour के चारों ओर tests लगाकर:

1. **Single responsibility।** वो file को बाँट देता है: `reader.py` (PDF से text), `summariser.py` (prompt और parsing), `formatters.py` (Markdown, और अब Word) और `delivery.py` (email)।
2. **Model के लिए एक interface।** `summariser.py` अब एक `ModelClient` लेता है। वो `ProviderAClient` और `SelfHostedClient` लिखता है, दोनों `complete()` वाली छोटी classes।
3. **किनारे पर injection।** API startup customer की settings पढ़ता है और सही client और formatter अंदर पास करता है।
4. **तेज़ tests।** Unit tests एक `FakeClient` पास करते हैं जो fixed summary लौटाता है। Test suite चार मिनट से तीन सेकंड पर आ जाता है।

Self-hosted client एक नई class है जिसके अपने tests हैं; `summarise()` बिल्कुल नहीं बदला। Word output एक नया formatter है; और कुछ नहीं बदला। हर request में rewrite की जगह एक दिन लगा।

वो आगे भी नहीं बढ़ता: PDF reader के लिए interfaces नहीं जोड़ता, क्योंकि reader एक ही है और दूसरे का कोई plan नहीं है। Abstraction तब जोड़ो जब सच में दूसरा case हो या test करने की ज़रूरत हो।

## आम गलतियाँ

- **Logic के बीच में बाहरी services को call करना।** इससे network के बिना test करना नामुमकिन हो जाता है और provider बदलना मुश्किल।
- **बहुत जल्दी बहुत ज़्यादा abstraction।** 100 lines की script के लिए interfaces, factories और layers उसे पढ़ना आसान नहीं, मुश्किल बनाते हैं।
- **विशाल "utils" या "manager" modules।** अगर module का नाम बताता ही नहीं कि वो क्या करता है, तो शायद वो कई काम करता है।
- **एक implementation के हिसाब से interface बदल देना।** तब बाकी हर implementation और caller को भी बदलना पड़ता है।
- **SOLID को रटने वाले rules समझना।** Interviewer ये देखते हैं कि आप असली code में problem पहचानकर ठीक कर पाते हो या नहीं।

## Practice करो

1. कोई भी script लो जो API को सीधे call करती है और client को बाहर से पास करो। Fake के साथ एक test लिखो।
2. अपनी सबसे बड़ी file के बदलने की वजहें लिखो। अगर दो से ज़्यादा हैं, तो sketch करो कि उसे कैसे बाँटोगे।
3. अपने बनाए interface के पीछे दूसरी implementation जोड़ो, उसे use करने वाले code को edit किए बिना।
4. दो मिनट में समझाने की practice करो कि AI app को ऐसे कैसे structure करोगे कि model provider बदला जा सके।
