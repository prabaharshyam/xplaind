## ये क्या है

**Software design** का मतलब है ये तय करना कि एक program को किन parts में बाँटें और वो parts आपस में कैसे बात करें। ज़्यादातर अच्छे designs के नीचे दो ideas होते हैं:

- **Cohesion**: एक part के अंदर की चीज़ें आपस में कितनी करीब से जुड़ी हैं। High cohesion का मतलब है कि हर part एक काम करता है, और उसके अंदर की हर चीज़ उसी काम के लिए है।
- **Coupling**: एक part दूसरे की details पर कितना depend करता है। Loose coupling का मतलब है कि आप बाकी parts को छुए बिना एक part बदल सकते हो।

अच्छा design यानी high cohesion और loose coupling। बुरा design तब महसूस होता है जब एक छोटा बदलाव फैल जाता है: email template बदलने के लिए किसी तरह model को call करने वाला code भी edit करना पड़ता है।

AI के काम में ये ज़्यादातर software से भी ज़्यादा मायने रखता है। एक साल में कोई team model providers बदल सकती है, privacy-sensitive customer के लिए एक self-hosted model जोड़ सकती है और vector store बदल सकती है। अगर model call बीस जगह दबा हुआ है, तो हर बदलाव एक risky rewrite है। एक छोटी boundary के पीछे हो, तो हर बदलाव बस एक नई file और एक test है।

वहाँ तक पहुँचने के लिए पाँच जानी-मानी guidelines हैं: **SOLID principles**। Robert C. Martin ने इन्हें object-oriented code के लिए इकट्ठा किया, लेकिन ये ideas सादे Python functions और modules पर भी काम करते हैं। इन्हें रटकर सुनाने की ज़रूरत नहीं है। ज़रूरत ये है कि जिन problems को ये रोकते हैं, उन्हें आप असली code में पहचान सको।

## ये कैसे काम करता है

### पाँच principles, आसान शब्दों में

| Principle | आसान शब्दों में | इसे तोड़ने का एक संकेत |
| --- | --- | --- |
| **S**ingle responsibility | एक module या class, बदलने की एक वजह | एक file जो PDFs पढ़ती है, model को call करती है और email भेजती है |
| **O**pen-closed | "Open for extension, closed for modification": behaviour नया code जोड़कर बढ़ाओ, पहले से चल रहे code को edit करके नहीं | हर नए provider के लिए business logic के अंदर एक और `elif` |
| **L**iskov substitution | किसी interface का हर implementation हर उस जगह काम करना चाहिए जहाँ वो interface expected है | एक client `None` return करता है जहाँ बाकी text return करते हैं |
| **I**nterface segregation | एक बड़े interface की जगह कई छोटे, focused interfaces | एक बहुत बड़ी `Storage` class जिस पर हर part depend करता है, जबकि हर एक उसके दो ही methods use करता है |
| **D**ependency inversion | High-level logic किसी खास library पर नहीं, बल्कि अपने खुद के interface पर depend करता है | `openai` business logic के अंदर गहराई में import और call किया गया |

**Open-closed का मतलब "कभी कोई file edit मत करो" नहीं है।** इसका मतलब है कि जो code अक्सर बदलता है (कौन-सा provider, कौन-सा output format) वो नए pieces के रूप में जोड़ा जाए, और जो core चल रहा है वो जस का तस रहे। कहीं न कहीं, एक जगह को फिर भी चुनना होगा कि कौन-सा piece use हो। वो चुनाव program के किनारे पर एक ही जगह रखो, पूरे logic में फैलाओ मत।

**Liskov वादों के बारे में है, class names के बारे में नहीं।** एक interface एक वादा है: "मुझे एक prompt string दो, मैं एक text string return करूँगा"। ये रहा एक client जो इसे तोड़ता है:

```python
class CheapClient:
    def complete(self, prompt: str) -> str | None:
        try:
            return self._call_api(prompt)
        except TimeoutError:
            return None   # every caller now has to check for None
```

इसका method name सही है, तो ये swap करने लायक लगता है। लेकिन बाकी clients के लिए लिखा code `reply.splitlines()` करता है, और जैसे ही ये पहली बार time out होता है, `AttributeError` के साथ crash हो जाता है। यही जाल तब भी आता है जब कोई implementation कम accept करता है (वो लंबे prompts मना कर देता है जो बाकी ले लेते हैं) या अपने आधे methods के लिए "not supported" raise करता है। वादा निभाओ: ऐसा error raise करो जिसे caller पहले से handle करता है, या client के अंदर ही retry करो।

### Dependency injection

SOLID के ज़्यादातर हिस्से के पीछे का practical tool है **dependency injection**। Function अपनी ज़रूरत की चीज़ खुद बनाने की जगह उसे बाहर से लेता है:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

`Protocol` एक shape बताता है। जिस भी class में matching `complete` method है वो fit हो जाती है, किसी से inherit किए बिना, और mypy जैसा type checker आपके लिए ये check करता है। अब `summarise` को न पता है, न फ़र्क पड़ता है कि वो कौन-सा provider use कर रहा है। Production एक real client pass करता है, tests एक fake pass करते हैं, और provider switch करने का मतलब है एक नई class लिखना, `summarise` को edit करना नहीं।

Direction पर ध्यान दो। Interface business logic का है: `summarise` बताता है कि उसे क्या चाहिए। Provider library को बाहर की तरफ़ धकेल दिया जाता है। Dependency inversion में "inversion" यही है।

### Model interface कितना thin होना चाहिए?

ऊपर के code पर एक experienced engineer यही सवाल पूछेगा। असली provider APIs एक जैसी नहीं होतीं। वो messages लेने, tools call करने, structured JSON return करने, tokens stream करने और prompts cache करने के तरीके में अलग होती हैं। एक method वाला `complete(prompt) -> str` interface ये सब छुपा देता है। तो आपके सामने एक असली trade-off है:

- **बहुत thin** हो, तो features खो दोगे। अगर आपके product को tool calling चाहिए, तो एक plain text interface उसे express नहीं कर सकता।
- **बहुत wide** हो, तो provider की details बाहर रिसने लगती हैं। `messages`, `tools`, `response_format` और `stream` वाला interface असल में एक provider की API की copy है, और अगला provider उसमें fit नहीं होगा।

तीन rules ज़्यादातर cases संभाल लेते हैं:

1. **Interface को chat call के हिसाब से नहीं, अपने product की ज़रूरत के हिसाब से shape करो।** अगर आपका app invoice fields निकालता है, तो interface `extract_invoice(text) -> Invoice` हो सकता है, जहाँ `Invoice` आपकी अपनी typed class है। फिर हर adapter अंदर structured output के लिए अपने provider का best feature use करता है, और आपके core logic को एक साफ़, typed result मिलता है।
2. **Provider-specific features को adapter के अंदर ही रहने दो।** Prompt caching या कोई खास retry header adapter का मामला है। अगर कोई provider सच में वो नहीं कर सकता जो आपके product को चाहिए, तो वो एक product decision है, "not supported" error के पीछे छुपाने की चीज़ नहीं।
3. **Gateway के बारे में सोचो।** LiteLLM जैसी libraries, और OpenAI-style chat format बोलने वाले servers (जैसे vLLM), कई models को एक जैसा दिखाते हैं, तो आपका adapter छोटा रहता है। तब आप gateway पर और उन features पर depend करते हो जो उसके सारे models share करते हैं। *LLM gateways* lesson इसे cover करता है।

एक summariser के लिए `complete(prompt) -> str` सही size है।

```flow
title: एक AI app में ports and adapters
Wiring at start-up | settings पढ़ता है, adapters बनाता है -[एक client अंदर pass करता है]-> Core logic | prompts, parsing, rules
Core logic -[call करता है]-> ModelClient port | core का अपना interface
ModelClient port -[implement करने वाली class]-> HostedClient | provider SDK को wrap करता है
ModelClient port -[implement करने वाली class]-> SelfHostedClient | HTTP पर vLLM को call करता है
ModelClient port -[implement करने वाली class]-> FakeClient | tests में use होता है
```

### Ports and adapters

यही idea पूरे codebase पर लागू करो, तो इसका एक नाम है: **ports and adapters**, जिसे **hexagonal architecture** भी कहते हैं। Alistair Cockburn ने इसे describe किया। Interviewers दोनों नाम use करते हैं।

- **Core logic** वो है जो product करता है: एक ticket classify करना, एक prompt बनाना, एक answer को score करना। ये बाहर से कुछ import नहीं करता।
- **Ports** वो छोटे interfaces हैं जो core को चाहिए: एक model client, एक document store, एक notifier।
- **Adapters** ports को असली services से implement करते हैं: किसी provider का SDK, एक vector database, email या WhatsApp।
- **Wiring** किनारे पर होती है (web app का start-up, command-line entry point): ये settings पढ़ती है, असली adapters बनाती है और उन्हें अंदर pass करती है।

अपने design का एक quick test: क्या आप core logic को एक unit test में बिना network, बिना API key और बिना database के चला सकते हो? अगर हाँ, तो boundaries सही जगह पर हैं।

### Inheritance से बेहतर composition

जब आपको retries, logging या cost tracking जैसा behaviour जोड़ना हो, तो सबसे पहले subclass बनाने का मन करता है: `RetryingOpenAIClient(OpenAIClient)`। फिर आपको `RetryingSelfHostedClient`, `LoggingRetryingOpenAIClient` चाहिए, और हर combination के साथ classes की गिनती बढ़ती जाती है। **Composition** का मतलब है इसकी जगह wrap करना:

```python
import time

class RetryingClient:
    """Wraps any ModelClient and retries failed calls."""

    def __init__(self, inner: ModelClient, attempts: int = 3):
        self._inner, self._attempts = inner, attempts

    def complete(self, prompt: str) -> str:
        for i in range(self._attempts):
            try:
                return self._inner.complete(prompt)
            except Exception:
                if i == self._attempts - 1:
                    raise
                time.sleep(2 ** i)
```

`RetryingClient` खुद एक `ModelClient` है, इसलिए ये किसी भी provider के साथ काम करता है, और आप wiring step पर wrappers को एक के ऊपर एक लगाते हो: `RetryingClient(HostedClient(...))`। यही है open-closed असल में: नया behaviour, मौजूदा clients में कोई edit नहीं। (असली code में हर `Exception` पर नहीं, सिर्फ़ timeouts और rate limits पर retry करो; *Errors, retries and cost* lesson देखो।)

### Functions या classes?

आपको हर जगह classes की ज़रूरत नहीं है। साफ़ inputs और outputs वाले सादे functions अक्सर सबसे साफ़ Python design होते हैं, और आप किसी function में dependency inject करने के लिए बस उसे एक parameter बना सकते हो। Class तब लो जब कोई चीज़ ऐसी state या settings रखती है जो कई calls share करती हैं, जैसे API key और timeout वाला client, या जब आपको एक interface के कई ऐसे implementations चाहिए जिन्हें एक-दूसरे की जगह लगाया जा सके।

### Refactor कब करें

**Refactoring** का मतलब है code क्या करता है वो बदले बिना उसका structure बदलना। ये तब करो जब आप वो code वैसे भी बदलने वाले हो और बदलाव मुश्किल है। पहले code को ऐसा reshape करो कि बदलाव आसान हो जाए, फिर वो आसान बदलाव करो। Safe तरीका:

1. **पहले tests।** कुछ भी छूने से पहले ऐसे tests लिखो जो आज का behaviour pin कर दें, चाहे वो behaviour बदसूरत ही क्यों न हो। कुछ टूटेगा तो वो बता देंगे।
2. **छोटे steps।** एक function move करो, tests चलाओ, commit करो। Branch पर एक हफ़्ता लेने वाला refactor आम तौर पर एक दर्दनाक merge में खत्म होता है।
3. **Structure और behaviour को अलग रखो।** एक commit या तो code को reshape करता है या बदलता है कि code क्या करता है, कभी दोनों नहीं, ताकि reviewer हर एक को check कर सके।

जो code चल रहा है और जिसे किसी को बदलना नहीं है, उसे refactor मत करो। जब तक असली दूसरा case (दूसरा provider, दूसरा output format) या fake माँगने वाला कोई test न हो, interface मत जोड़ो।

### Low-level design interviews

कई भारतीय product companies एक **low-level design** (LLD) round रखती हैं। आपसे किसी छोटी चीज़ के लिए classes और interfaces design करने को कहा जाता है, जैसे rate limiter या parking lot। (**System design** round इसकी जगह पूछता है कि पूरी services आपस में कैसे fit होती हैं।)

"एक rate limiter design करो जो हर user को प्रति मिनट N requests allow करे" का एक model answer interfaces से शुरू होता है, फिर एक simple strategy:

```python
from typing import Protocol

class Clock(Protocol):
    def now(self) -> float: ...

class RateLimiter(Protocol):
    def allow(self, user_id: str) -> bool: ...

class FixedWindow:
    def __init__(self, limit: int, window_s: float, clock: Clock):
        self.limit, self.window_s, self.clock = limit, window_s, clock
        self.counts: dict[str, tuple[int, int]] = {}  # user -> (window number, count)

    def allow(self, user_id: str) -> bool:
        window = int(self.clock.now() // self.window_s)
        seen, n = self.counts.get(user_id, (window, 0))
        n = n if seen == window else 0
        if n >= self.limit:
            return False
        self.counts[user_id] = (window, n + 1)
        return True
```

फिर trade-offs ज़ोर से बोलो। Clock inject किया गया है, तो test एक मिनट इंतज़ार करने की जगह fake clock से समय set कर देता है। Fixed window की एक जानी-पहचानी कमज़ोरी है: एक user 0:59 पर N requests और 1:00 पर N और कर सकता है, यानी दो seconds में limit का दोगुना। **Token bucket**, जो user का allowance समय के साथ धीरे-धीरे refill करता है, इसे smooth कर देता है, और वो उसी `RateLimiter` interface के पीछे एक दूसरी class है, तो `allow()` को call करने वाला API code कभी नहीं बदलता। कई servers पर counts Redis जैसे shared store में चले जाते हैं: बस एक और adapter।

## एक worked example

दिल्ली के एक legal-tech startup में Rohit की team ने एक हफ़्ते में एक contract summariser बनाया। सब कुछ 300 lines की एक ही file में था: वो PDF पढ़ती थी, एक hosted model provider को सीधे call करती थी, Markdown format करती थी और result email करती थी।

दो महीने बाद एक साथ तीन requests आती हैं। एक बड़ा client चाहता है कि उसके contracts उसके अपने cloud account में चल रहे model से process हों। Sales team को summaries Word documents में चाहिए। और tests चलने में लगभग चार मिनट लगते हैं, क्योंकि हर test एक असली API call करता है और पैसे लगते हैं।

Rohit छोटे steps में refactor करता है, पहले आज के behaviour के चारों तरफ़ tests लगाकर।

**1. बदलने की वजह के हिसाब से बाँटो।** वो `reader.py` (PDF से text), `summariser.py` (prompt और parsing), `formatters.py` (Markdown, और अब Word), `delivery.py` (email) और `llm.py` (model clients) बनाता है। हर file के बदलने की एक ही वजह है।

**2. एक port और दो adapters।** `llm.py` में:

```python
import httpx
from openai import OpenAI

# ModelClient is the Protocol shown earlier, defined in this file.

class HostedClient:
    """A hosted provider, reached through its own SDK."""
    def __init__(self, api_key: str, model: str):
        self._sdk = OpenAI(api_key=api_key, timeout=30)
        self._model = model

    def complete(self, prompt: str) -> str:
        resp = self._sdk.chat.completions.create(
            model=self._model,
            messages=[{"role": "user", "content": prompt}],
        )
        return resp.choices[0].message.content or ""

class SelfHostedClient:
    """A model served with vLLM inside the customer's own cloud."""
    def __init__(self, base_url: str, model: str):
        self._http = httpx.Client(base_url=base_url, timeout=60)
        self._model = model

    def complete(self, prompt: str) -> str:
        r = self._http.post("/v1/chat/completions", json={
            "model": self._model,
            "messages": [{"role": "user", "content": prompt}],
        })
        r.raise_for_status()
        return r.json()["choices"][0]["message"]["content"] or ""
```

दोनों एक string return करते हैं, कभी `None` नहीं, इसलिए दोनों एक ही वादा निभाते हैं। दोनों failure पर एक error raise करते हैं, जिसे caller पहले से handle करता है।

**3. Core logic जो सिर्फ़ port को जानता है।** `summariser.py` `ModelClient` import करता है और बाहर से कुछ नहीं:

```python
from llm import ModelClient

PROMPT = "Summarise this contract in 5 bullet points. Flag any termination clause.\n\n{text}"

def summarise(text: str, client: ModelClient) -> list[str]:
    reply = client.complete(PROMPT.format(text=text))
    return [line.lstrip("-* ").strip() for line in reply.splitlines() if line.strip()]
```

**4. किनारे पर wiring।** `main.py` हर customer की settings पढ़ता है और client चुनता है। Codebase में यही एक जगह है जिसे पता है कि कौन-से providers मौजूद हैं:

```python
from dataclasses import dataclass

from llm import HostedClient, ModelClient, SelfHostedClient

@dataclass
class Settings:
    model_host: str      # "hosted" or "self_hosted"
    model: str
    api_key: str = ""
    base_url: str = ""

def make_client(s: Settings) -> ModelClient:
    if s.model_host == "self_hosted":
        return SelfHostedClient(s.base_url, s.model)
    return HostedClient(s.api_key, s.model)
```

**5. Fake के साथ तेज़ tests।** `test_summariser.py` में:

```python
from summariser import summarise

class FakeClient:
    def __init__(self, reply: str):
        self.reply = reply
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply

def test_summarise_returns_clean_bullets():
    fake = FakeClient("- Term: 2 years\n\n- Notice period: 90 days\n")
    assert summarise("CONTRACT TEXT", fake) == ["Term: 2 years", "Notice period: 90 days"]
    assert "CONTRACT TEXT" in fake.prompts[0]
```

Test check करता है कि reply साफ़ bullets में बदला गया और contract का text prompt तक पहुँचा, बिना network या API key के। जब हर unit test fakes use करने लगता है, तो Rohit का suite मिनटों की जगह seconds में चलता है। वो दो-तीन slow tests रखता है जो असली providers को call करते हैं और हर release से पहले चलते हैं, ताकि वो चीज़ें पकड़ी जा सकें जो fake नहीं पकड़ सकता: बदला हुआ response shape या गलत model name।

Self-hosted client एक नई class थी, और `summarise()` बिल्कुल नहीं बदला। Word output एक नया formatter था। हर request में rewrite की जगह लगभग एक दिन लगा।

उसे ये भी पता है कि कहाँ रुकना है। वो PDF reader के लिए interface नहीं जोड़ता, क्योंकि reader एक ही है और दूसरे का कोई plan नहीं।

## आम गलतियाँ

- **Logic के अंदर गहराई में external services को call करना।** Code बिना network के test नहीं हो सकता, और provider बदलने का मतलब है हर file में ढूँढना।
- **ऐसा fake जो वादा नहीं निभाता।** अगर असली clients string return करते हैं और fake एक list return करता है, तो आपके tests pass होंगे और production fail होगा। Fakes असली चीज़ वाला ही interface follow करते हैं।
- **ऐसा interface जो एक provider की API की copy है।** वो general दिखता है लेकिन सिर्फ़ उसी provider में fit होता है। उसे caller की तरफ़ से design करो: core logic को असल में क्या चाहिए?
- **बहुत जल्दी बहुत ज़्यादा abstraction।** 100 lines की script के लिए interfaces, factories और layers उसे पढ़ना मुश्किल बना देते हैं। Abstraction किसी असली दूसरे case या test के लिए जोड़ो।
- **Behaviour जोड़ने के लिए subclass बनाना।** Retries, logging और caching को subclasses बनाओगे तो हर combination के लिए एक class बनती जाएगी। इसकी जगह wrap करो।
- **बिना tests के, या एक ही बड़े step में refactor करना।** आपको पता नहीं चलेगा कि क्या तोड़ा। Tests से behaviour pin करो, फिर छोटे commits में आगे बढ़ो।
- **Interviews में SOLID रटकर सुनाना।** Interviewers ये देखते हैं कि क्या आप असली code में problem पहचान सकते हो, trade-off बता सकते हो और उसे fix कर सकते हो।

## Practice

नीचे linked ArjanCodes का Python में SOLID principles वाला video देखो, और हर principle के बाद रुककर अपने खुद के code में उसका एक example ढूँढो।

फिर इस lesson का project check करो, अपने छोटे app को वैसे ही refactor करते हुए जैसे Rohit ने किया: पहले आज के behaviour का एक test, फिर interface, एक दूसरा implementation और start-up पर एक `make_client` function। Submit करने से पहले खुद mark करो:

| Check | ये pass है अगर |
| --- | --- |
| Boundary | Core logic की file कोई provider SDK import नहीं करती; सिर्फ़ adapter file और wiring करते हैं |
| Tests | कम से कम दो unit tests fake client use करते हैं, बिना network या API key के चलते हैं, और `pytest` से pass होते हैं |
| Swappable | दूसरे implementation पर switch करने से सिर्फ़ settings या wiring बदलती है, core logic नहीं |

अगर आपने पहले pytest से tests नहीं लिखे हैं, तो पहले *Writing tests with pytest* lesson करो; *Project tooling* उन्हें एक project के हिस्से के रूप में चलाना cover करता है।

**आपका काम पूरा है जब आप** असली code में single-responsibility और Liskov problems पहचान सको, एक model provider को अपने product के हिसाब से sized interface के पीछे रख सको, उसे start-up पर inject कर सको, logic को fake से test कर सको, और rate limiter जैसे एक छोटे low-level design को उसके trade-offs के साथ समझा सको।
