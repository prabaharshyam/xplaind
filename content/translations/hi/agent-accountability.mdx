## ये क्या है

**Accountability** का मतलब है कि agent जो भी action ले, उसके लिए कोई चार सवालों के जवाब दे सके। ज़िम्मेदार कौन था? Agent को क्या करने की अनुमति थी? उसने वो क्यों किया? गलती कैसे सुधारी जाएगी? Agents ज़िम्मेदारी नहीं उठाते; लोग और organisations उठाते हैं।

Governance frameworks इसे केंद्र में रखते हैं। NIST AI Risk Management Framework का "govern" function साफ़ roles और responsibilities माँगता है। EU AI Act high-risk systems के providers और deployers के लिए human oversight, record-keeping और named duties ज़रूरी करता है।

```flow
title: Accountability की chain
Business owner | scope तय करता है, नतीजों का जवाब देता है -> Agent card | purpose, tools, अकेले क्या कर सकता है, approval कब चाहिए, कभी नहीं, limits, evals
Technical owner | उसे चलाता है, records रखता है -> Agent card
Compliance reviewer | नियमों से मिलाकर देखता है -> Agent card
Agent card -> Action -> Approval | किसने, कब, क्या देखा
Approval -> Audit record | steps और versions
Complaint -> इंसान records देखता है -> Refund, fix या नया eval case -> Report
Audit record -> इंसान records देखता है
```

इस lesson में हम Delhi के एक insurance broker के motor-insurance renewal agent के साथ चलेंगे।

## ये काम कैसे करता है

**Owners के नाम तय करो।** हर agent के लिए: एक business owner जो तय करता है कि agent क्या कर सकता है और उसके नतीजों का जवाब देता है, एक technical owner जो उसे चलाता है, और एक risk या compliance reviewer। उनके नाम agent के documentation में लिखो।

**Scope लिखो।** एक छोटा "agent card": purpose, users, tools और permissions, जो actions वो अकेले ले सकता है, जिनके लिए approval चाहिए, जो उसे कभी नहीं लेने हैं, known limits और जो evals उसने पास किए। Agent बदले तो इसे review करो।

**Identity के साथ approvals।** जब कोई इंसान किसी action को approve करे, तो record करो कि किसने, कब और क्या देखकर किया। उसकी approval accountability chain का हिस्सा है, इसलिए approval screen पर इतना दिखना चाहिए कि असली फ़ैसला लिया जा सके।

**Records।** ऐसे audit logs जो हर action को दोबारा बना सकें: request, agent के steps, arguments के साथ tool calls, approvals, और prompt, model व tools के versions। इन्हें तय अवधि तक रखो।

**Disclosure।** लोगों को बताओ कि वो agent से बात कर रहे हैं, और ये भी कि कोई content या फ़ैसला AI की मदद से बना, जैसा कानून या अच्छी practice माँगती है।

**Redress।** प्रभावित लोगों के लिए problem report करने और किसी इंसान तक पहुँचने का साफ़ तरीका, records से जाँच करने की process, और सुधारने व सीखने की प्रतिबद्धता (case को eval suite में जोड़ दो)।

**Review।** नियमित रूप से देखो कि agent ने क्या किया: actions के samples, overrides, complaints, incidents। सबूत कहे तो उसका scope बदलो, घटाना हो या बढ़ाना।

**Practice में एक agent card:**

| Section | Example entry |
| --- | --- |
| Purpose | Motor policies renew करना: quotes लाना, recommend करना, confirmation के बाद purchase करना |
| Users | App में renew करने वाले retail customers |
| Tools | get_vehicle, get_quotes, purchase_policy |
| अकेले कर सकता है | Quotes लाना, कारण के साथ recommend करना |
| Approval चाहिए | Purchase, सिर्फ़ customer की साफ़ confirmation के बाद |
| कभी नहीं | Confirmation के बिना cover type या add-ons बदलना |
| Known limits | Commercial vehicles supported नहीं हैं |
| Owners | Head of retail operations; platform lead; compliance officer |
| आख़िरी review | 2026-10-01 |

**Chain को test करना।** पिछले हफ़्ते का कोई एक असली action उठाओ। सिर्फ़ documents और records से पाँच सवालों के जवाब देने की कोशिश करो: किसने माँगा, agent को क्या करने की अनुमति थी, उसने step by step क्या किया, किसने approve किया और उसे क्या दिखा, और कौन-से versions चल रहे थे। देखो कितना समय लगता है। अगर किसी जवाब के लिए किसी की याद चाहिए, या एक घंटे से ज़्यादा लगता है, तो कमी तब ठीक करो जब तक कोई regulator या नाराज़ customer उसे न पकड़े।

**Vendors की accountability।** जब agent किसी third-party model या tool का use करे, तो contract में लिखा हो कि कौन क्या संभालता है: incident की सूचना, data का use, records कितने रखे जाएँगे और model में बदलाव। Customers के सामने जवाबदेह फिर भी आपकी organisation है, इसलिए agent card में vendor का नाम और contract क्या cover करता है, ये लिखो।

**Agent card को code के बगल में रखो।** उसे repository में file की तरह रखो और test करो, ताकि वो agent के असली काम से अलग न हो जाए:

```yaml
# agents/renewals.card.yaml
purpose: Renew motor policies after the customer confirms
owners: {business: Head of retail operations, technical: Platform lead, risk: Compliance officer}
tools:
  get_vehicle: {kind: read}
  get_quotes: {kind: read}
  purchase_policy: {kind: write, approval: customer_confirmation}
never: [change cover type without confirmation, add add-ons without confirmation]
last_reviewed: 2026-10-01
```

```python
import yaml
from datetime import date, timedelta
from agents.renewals import TOOLS          # the tool definitions the agent really uses

def test_card_matches_code():
    card = yaml.safe_load(open("agents/renewals.card.yaml"))
    assert set(card["tools"]) == {t["name"] for t in TOOLS}, "card and code list different tools"
    for name, spec in card["tools"].items():
        if spec["kind"] == "write":
            assert "approval" in spec, f"{name} writes but has no approval rule"

def test_card_reviewed_recently():
    card = yaml.safe_load(open("agents/renewals.card.yaml"))
    assert date.today() - card["last_reviewed"] < timedelta(days=180), "card review overdue"
```

अब card update किए बिना कोई tool जोड़ो तो build fail होता है, जो owners से बातचीत करने पर मजबूर करता है।

**ऐसा audit record जो पाँचों सवालों का जवाब दे।** एक append-only table, जो platform लिखे और जिसे agent का service account कभी edit न कर सके:

```sql
CREATE TABLE agent_audit (
  id bigserial PRIMARY KEY,
  run_id text NOT NULL,
  at timestamptz NOT NULL DEFAULT now(),
  actor text NOT NULL,           -- the customer, the agent, or the approver's staff id
  kind text NOT NULL,            -- request, tool_call, approval, result
  detail jsonb NOT NULL,         -- tool name and arguments, what the approver saw, the outcome
  prompt_version text, model text, tool_versions jsonb
);
-- Reconstruct one run in order:
SELECT at AT TIME ZONE 'Asia/Kolkata', actor, kind, detail FROM agent_audit WHERE run_id = $1 ORDER BY at;
```

Application role को सिर्फ़ `INSERT` और `SELECT` दो। Records को उतने समय तक रखो जितना आपका sector माँगता है, और जल्दी delete करने की जगह उन्हें सस्ते storage में export करो।

**India में sector की अपेक्षाएँ।** Regulators बता रहे हैं कि वो अपने sectors में AI से क्या उम्मीद रखते हैं। जैसे RBI ने financial services में responsible AI के लिए एक framework छापा है, जो governance, named accountability और audit trails पर ज़ोर देता है। अपने client के sector की मौजूदा guidance design से पहले पढ़ो, launch के बाद नहीं।

**ज़िम्मेदारी vendor पर नहीं जाती।** अगर model provider के update से behaviour बदल जाए, तब भी customer के सामने जवाबदेह आपकी organisation है। इसीलिए card में pinned model version और पास किए गए evals का नाम होता है, और model के बदलाव भी code के बदलावों की तरह वही review पाते हैं।

**अपने browser में try करो।** किसी agent card को उन tools से मिलाओ जो agent के पास सच में हैं। एक tool जोड़ो और चलाओ।

```python
card = {"tools": {"get_vehicle": "read", "get_quotes": "read", "purchase_policy": "write"},
        "approvals": {"purchase_policy": "customer confirmation"}}
tools_in_code = ["get_vehicle", "get_quotes", "purchase_policy", "cancel_policy"]

missing = set(tools_in_code) - set(card["tools"])
if missing:
    print("tools missing from the card:", sorted(missing))
for name, kind in card["tools"].items():
    if kind == "write" and name not in card["approvals"]:
        print(f"{name} writes but has no approval rule")
print("check done")
```

## एक worked example

Delhi का एक insurance broker एक agent लगाता है जो motor policies renew करता है। वो vehicle की details check करता है, तीन insurers से quotes लाता है और एक को recommend करता है। Customer के confirm करने के बाद वो insurer के API से purchase पूरा कर देता है।

Accountability का set-up:

- **Owners**: head of retail operations (business), platform lead (technical), compliance officer (review)।
- **Agent card**: quotes ला सकता है और recommend कर सकता है; purchase तभी कर सकता है जब customer app में साफ़ confirm करे; confirmation के बिना cover type या add-ons कभी नहीं बदल सकता; उसे बताना होगा कि वो एक automated assistant है।
- **Records**: हर quote, recommendation का कारण, confirmation message और purchase call, versions के साथ।
- **Redress**: हर screen पर "किसी इंसान से बात करो" का option; complaints की हर हफ़्ते समीक्षा।

तीन महीने बाद एक customer शिकायत करता है कि renewal में zero-depreciation cover हट गया। Records दिखाते हैं कि agent ने बिना उस add-on वाला सस्ता quote recommend किया था और confirmation screen ने इस बदलाव को highlight नहीं किया था। Accountability साफ़ है: गलती design की थी, customer की नहीं। Broker फ़र्क की रकम लौटाता है, confirmation screen को बदलता है ताकि cover का हर बदलाव highlight हो, ये rule जोड़ता है कि cover बदलने के लिए साफ़ सहमति चाहिए, और ऐसे दस cases evals में जोड़ देता है। Compliance officer की board report में incident और उसका fix शामिल होता है।

| Complaint के बाद का step | Broker ने क्या किया |
| --- | --- |
| जाँच | Records में दिखा कि add-on के बिना सस्ता quote recommend हुआ |
| नतीजा | Confirmation screen ने cover का बदलाव highlight नहीं किया |
| Redress | Customer को फ़र्क की रकम लौटाई |
| Fix | Cover के बदलाव highlight हों; साफ़ सहमति ज़रूरी |
| सीख | ऐसे दस cases evals में जोड़े; incident board को report हुआ |

## आम गलतियाँ

- **कोई named owner नहीं।** "AI team" नतीजों का जवाब नहीं दे सकती।
- **Scope सिर्फ़ लोगों के दिमाग में।** Agent card लिखो और उसे current रखो।
- **Context के बिना approvals।** आँख मूँदकर approve करने वाले लोग oversight नहीं दे रहे होते।
- **ऐसे records जिन्हें query नहीं कर सकते।** जाँच में जवाब घंटों में चाहिए।
- **प्रभावित लोगों के लिए कोई रास्ता नहीं।** नुकसान हो और report करने का तरीका न हो, तो वो public शिकायत बन जाता है।
- **Agent card जो किसी slide deck में पड़ा है।** उसे repository में रखो और test करो।
- **Audit tables जिन्हें agent की service edit या delete कर सकती है।**
- **Audit records पर versions नहीं।** आप बता नहीं सकते कि कौन-से prompt या model ने फ़ैसला लिया।

## जब हल्की process काफ़ी है

- **Internal read-only assistants**, जैसे staff के लिए policy search: named owner, छोटा card और आम logs काफ़ी हैं।
- **Prototypes** जो असली customers या systems को कभी नहीं छूते।
- **Personal productivity tools** जो एक इंसान अपने ही data पर use करता है।

पूरे cards, approval की identity, append-only audits और redress के रास्ते तब ज़रूरी हो जाते हैं जब agent customers के लिए काम करे, पैसे या personal data को छुए, या regulated sector में चले।

## Demo से production तक

- **CI में card को test करो**, agent के असली tools के सामने, और overdue reviews पर fail करो।
- **Audits को append-only storage में लिखो**, run ids और versions के साथ।
- **हर महीने एक असली action पर पाँच-सवाल वाली drill चलाओ** और समय नापो।
- **Redress cases को बंद होने तक track करो**, और हर एक को eval suite में जोड़ो।
- **हर तिमाही scope review करो** business owner के साथ, actions, overrides और complaints के आँकड़ों के साथ।

## Practice करो

NIST AI Risk Management Framework का overview और EU AI Act summary का high-risk obligations वाला section पढ़ो।

1. अपने बनाए किसी agent के लिए agent card लिखो: purpose, users, tools, allowed और forbidden actions, approvals, known limits, owners।
2. Check करो कि आपके audit records इन सवालों के जवाब दे सकते हैं या नहीं: किसने माँगा, agent ने क्या किया, किसने approve किया, और कौन-से versions चल रहे थे।
3. Redress का रास्ता design करो: प्रभावित इंसान problem कैसे report करे और उसके बाद क्या होगा, समय की सीमा के साथ।
4. अपने agent की repository में card-matches-code test जोड़ो, फिर card update किए बिना एक नया tool जोड़ो और पक्का करो कि build fail होता है।

**आपका काम पूरा जब** आप अपने agent का कोई एक action लेकर, सिर्फ़ documents और records से दिखा सको कि उसके लिए accountable कौन था और वो क्यों हुआ।
