## ये क्या है

Agents खुद तय करते हैं कि कितने steps लेने हैं। कभी-कभी ये गड़बड़ा जाता है: कोई tool fail होता रहता है और agent retry करता रहता है, दो agents काम एक-दूसरे को आगे-पीछे करते रहते हैं, या agent किसी draft को "improve" करता ही रहता है। Limits के बिना, loop tokens जलाता है, downstream systems पर बोझ डालता है और असली actions दोहराता है।

तीन controls इसे रोकते हैं:

- **Loop limits**: हर task के लिए, और sub-agents हों तो हर run के लिए, steps या tool calls की अधिकतम संख्या।
- **Budgets**: हर task, हर user, और पूरे feature के लिए हर दिन, tokens, time और पैसे पर caps।
- **Kill switches**: operator के लिए बिना deploy के किसी tool, agent या पूरे feature को रोकने का तेज़ और भरोसेमंद तरीका।

Repetition checks, circuit breakers, rate और concurrency limits और idempotency keys इनका साथ देते हैं।

```flow
title: हर limit कहाँ check होती है
हर task | 15 steps, 60,000 tokens, 90 s तक -> Shared store | Postgres या Redis
हर model call | estimate reserve करो, फिर settle -> Shared store
हर tool call | kill switch, circuit breaker, idempotency key -> Shared store
हर दिन | हर student के लिए ₹15, feature के लिए ₹8,000 -> Shared store
Shared store -> Provider spend limit | आखिरी backstop
```

ये lesson एक illustrative case के साथ चलता है: Bengaluru की एक edtech company का homework-help agent, जिसने एक रात में अपने weekly budget का दस गुना खर्च कर दिया।

## ये काम कैसे करता है

### Per-task limits

Loop में steps, tool calls, tokens और बीता समय गिनो। हर cap एक हफ़्ते के real runs से चुनो: 95th percentile का लगभग दोगुना। अगर 95% tasks 12 steps और ₹2 में खत्म होते हैं, तो 25 steps और ₹5 का cap आम काम को काटे बिना runaways को रोक देगा। Model या prompt बदलो तो numbers दोबारा देखो।

Limit पर पहुँचने पर साफ़ तरीके से रुको: state save करो, user को आसान शब्दों में बताओ कि क्या हो गया और इसकी जगह वो क्या कर सकते हैं, और इसे investigate करने वाले failure की तरह log करो। रुका हुआ task कभी crash जैसा नहीं दिखना चाहिए।

### Repetition checks और circuit breakers

**Repetition check** एक task के अंदर काम करता है। अगर एक ही tool एक ही arguments के साथ तीन बार call हो, या एक ही error लगातार तीन बार लौटे, तो task जल्दी खत्म कर दो।

**Circuit breaker** सभी tasks में काम करता है। हर tool के failures shared store में गिनो। मान लो, सभी users में मिलाकर कोई tool एक मिनट में 20 बार fail होता है, तो circuit "open" कर दो: अगले पाँच मिनट तक उस tool की हर call, tool तक पहुँचे बिना, एक साफ़ message के साथ तुरंत fail होगी। फिर एक trial call जाने दो; अगर वो चल जाए, तो circuit close कर दो। Repetition check एक task को loop करने से रोकता है। Circuit breaker हज़ार tasks को थोड़ा-थोड़ा loop करने से रोकता है, और रात भर का बड़ा bill आम तौर पर इसी तरह बनता है।

### Sub-agents में run-level caps

जब कोई planner sub-agents को काम देता है, तो हर एक अपने 15-step cap का पालन कर सकता है, जबकि पूरा run सैकड़ों steps ले लेता है। हर run को एक root `run_id` दो, उसे हर sub-agent को pass करो, और shared store में उसी id के against steps गिनो। Total पर cap लगाओ (जैसे हर run के लिए 40 steps) और hand-offs की संख्या पर भी (जैसे 4)।

### हर user और हर दिन के budgets

हर user का हर दिन का खर्च गिनो और cap पार होने पर विनम्रता से मना कर दो। पूरे feature का भी हर दिन का खर्च गिनो, 50% और 80% पर ऐसे alerts के साथ जो top users और task types की list दें, ताकि cap सबको रोके उससे पहले कोई कदम उठाए। Asia/Kolkata के दिन use करो, ताकि limits आपके users की आधी रात को reset हों।

Counts किसी shared store में रहने चाहिए, जैसे database या Redis: memory में गिनने वाले छह servers cap का छह गुना होने देते हैं। पर सिर्फ़ shared store काफ़ी नहीं है। स्वाभाविक code "check, call, record" होता है:

1. आज का total पढ़ो। वो ₹14 है और cap ₹15 है, तो ₹1 की call allowed है।
2. Model को call करो।
3. Real cost total में जोड़ो।

एक ही user की बीस requests, किसी के step 3 तक पहुँचने से पहले ही, सभी step 1 कर सकती हैं, तो बीसों pass होकर खर्च कर देती हैं। Step 3 को atomic बनाने से मदद नहीं मिलती: race check और खर्च के बीच के gap में है। इस bug को **check-then-act** कहते हैं।

इसका fix है **reserve, then settle**। Call से पहले, एक ऐसे conditional statement में total में upper-bound estimate जोड़ो जो तभी succeed हो जब नया total cap के अंदर रहे। Call के बाद, estimate को real cost से बदल दो। हर चल रही call पहले से गिनी हुई है, तो कोई भी check पुराना total नहीं देखता।

### Code में race-safe budget

ये version SQLite use करता है, ताकि laptop पर चल जाए। SQLite file सिर्फ़ एक machine के processes में shared होती है; कई servers हों तो यही pattern Postgres या Redis पर use करो।

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from datetime import datetime
from zoneinfo import ZoneInfo

# Adds the estimate only if the new total stays within the cap; else returns no row.
RESERVE = """INSERT INTO spend (scope, day, paise) VALUES (?, ?, ?)
  ON CONFLICT (scope, day) DO UPDATE SET paise = spend.paise + excluded.paise
  WHERE spend.paise + excluded.paise <= ?
  RETURNING paise"""

@dataclass(frozen=True)
class Reservation:
    scopes: tuple
    day: str
    paise: int

def connect(path):
    db = sqlite3.connect(path, timeout=10, isolation_level=None)  # we run our own transactions
    db.execute("CREATE TABLE IF NOT EXISTS spend (scope TEXT, day TEXT,"
               " paise INTEGER NOT NULL, PRIMARY KEY (scope, day))")
    return db

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

@contextmanager
def write_tx(db):
    db.execute("BEGIN IMMEDIATE")           # take the write lock before reading anything
    try:
        yield
        db.execute("COMMIT")
    except BaseException:
        db.execute("ROLLBACK")
        raise

class OverBudget(Exception):
    pass

def reserve(db, caps, paise):
    """caps is {scope: cap in paise}. Reserve on every scope, or on none."""
    if paise > min(caps.values()):
        return None
    day = today()
    try:
        with write_tx(db):
            for scope, cap in sorted(caps.items()):       # same order everywhere
                if not db.execute(RESERVE, (scope, day, paise, cap)).fetchall():
                    raise OverBudget(scope)               # rolls back earlier scopes
    except OverBudget:
        return None
    return Reservation(tuple(sorted(caps)), day, paise)

def settle(db, r, actual_paise):
    """Swap the estimate for the real cost, on the day it was reserved."""
    with write_tx(db):
        for scope in r.scopes:
            db.execute("UPDATE spend SET paise = paise + ? WHERE scope = ? AND day = ?",
                       (actual_paise - r.paise, scope, r.day))
```

User और feature के caps एक साथ देकर `reserve` call करो। अगर ये `None` लौटाए, तो विनम्रता से मना कर दो; वरना model को call करो, फिर usage report की cost के साथ `settle` करो।

Details मायने रखती हैं:

- **सब या कुछ नहीं।** User और feature के counters एक ही transaction में बदलते हैं, तो feature cap से मना होने पर user पर charge नहीं रह जाता।
- **पैसा पूरे paise में।** Integers ठीक-ठीक जुड़ते हैं; floating-point rupees drift होते हैं।
- **Reservation अपना दिन याद रखता है।** रात 11:59 पर शुरू हुई call उसी दिन के against settle होती है जिस दिन reserve हुई थी, अगले दिन के against नहीं।
- **Failures safe side पर गिरते हैं।** अगर `settle` से पहले server crash हो जाए, तो estimate गिना हुआ रहता है; कोई ज़्यादा खर्च नहीं करता। अगर call provider तक पहुँची ही नहीं, तो 0 से settle करो। अगर पता न चले कि कितना bill हुआ, तो reservation रहने दो।
- **यही shape दूसरी जगह भी चलता है।** Postgres `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING` support करता है; conflict वाली row lock हो जाती है, तो दूसरी request इंतज़ार करती है और फिर नया total देखती है। Deadlocks से बचने के लिए scopes को एक fixed order में lock करो (`sorted` call)। Redis में read, compare और `INCRBY` को एक Lua script में रखो, जिसे Redis atomic तरीके से चलाता है।
- **Feature row एक hot spot है।** हर request उसे थोड़ी देर lock करती है। बहुत ज़्यादा traffic पर उसे कई rows में बाँट दो या Redis use करो।

### Call से पहले cost का estimate

Cap तभी टिकता है जब reservation upper bound हो। Input tokens गिनो (अपने provider के token counter से, या ज़्यादा अंदाज़ा लगाकर) और मान लो कि model पूरे `max_tokens` लिखेगा:

```python
def estimate_paise(input_tokens, max_tokens, in_paise_per_m, out_paise_per_m):
    """Upper bound: every input token, plus the most output max_tokens allows."""
    cost = input_tokens * in_paise_per_m + max_tokens * out_paise_per_m
    return -(-cost // 1_000_000)                     # round up to whole paise
```

मान लो, एक model की कीमत ₹25 प्रति million input tokens और ₹125 प्रति million output tokens है (ये बनाए हुए numbers हैं; अपने provider का price page use करो और जिस तारीख को check किया वो record करो)। 3,000-token prompt, `max_tokens` 1,000 के साथ, `estimate_paise(3000, 1000, 2500, 12500)` reserve करता है, जो 20 paise है। ज़्यादातर calls जल्दी खत्म हो जाती हैं और `settle` बाकी लौटा देता है।

दो gotchas। Check करो कि `max_tokens` उस सब पर सीमा लगाता है जिसे आपका provider output के रूप में bill करता है, reasoning tokens समेत अगर हों। और अगर आप stream करते हो, तो output आते-आते गिन सकते हो और run budget या kill switch के रुकने को कहने पर stream बंद कर सकते हो; जब तक पता न हो कि आपका provider cancel हुई stream को कैसे bill करता है, पूरा reservation रखो।

### Concurrent test से साबित करना

Race सिर्फ़ असली concurrency में दिखता है। यहाँ बीस workers, हर एक अपने connection के साथ, जैसे अलग-अलग servers, एक user के लिए एक साथ 100 calls करते हैं:

```python
import time
from concurrent.futures import ThreadPoolExecutor

CAPS = {"user:u42": 1500, "feature:homework": 800_000}   # ₹15 and ₹8,000

def one_call(db):
    r = reserve(db, CAPS, 200)          # estimate: ₹2
    if r is None:
        return 0
    time.sleep(0.01)                    # stands in for the model call
    settle(db, r, 150)                  # real cost: ₹1.50
    return 150

def test_cap_holds_under_concurrency(tmp_path):
    path = tmp_path / "budgets.db"
    connect(path).close()
    def server(_):
        db = connect(path)
        return sum(one_call(db) for _ in range(5))
    with ThreadPoolExecutor(max_workers=20) as pool:
        spent = sum(pool.map(server, range(20)))
    total = connect(path).execute(
        "SELECT paise FROM spend WHERE scope = 'user:u42' AND day = ?", (today(),)).fetchone()[0]
    assert 0 < spent == total <= 1500
```

हमारे runs में ये हर बार pass हुआ, ₹13.50 खर्च के साथ। Check-then-spend version ने उसी test में ₹15 के cap के against ₹42 तक जाने दिया। ये test CI में रखो ताकि कोई reservation को "simplify" करके हटा न दे।

### Rate और concurrency limits

दो और limits आपके पैसे की नहीं, आपके systems की रक्षा करती हैं:

- **Rate limits** हर मिनट की requests पर cap लगाती हैं। एक आम algorithm है **token bucket**: हर user के bucket में ज़्यादा से ज़्यादा, मान लो, 10 tokens होते हैं और हर छह seconds में एक refill होता है। हर request एक token लेती है; खाली bucket का मतलब है "धीरे चलो"। छोटे bursts निकल जाते हैं, पर average दस प्रति मिनट पर रहता है।
- **Concurrency limits** एक साथ चल रहे tasks पर cap लगाती हैं, जैसे हर user के लिए 2। तब "try again" दस बार दबाने से दस नहीं, दो tasks चलते हैं। एक "running" counter पर reserve pattern use करो, उसे `finally` block में release करो, और हर slot को एक expiry दो, क्योंकि crash हुआ server अपना `finally` कभी नहीं चलाता।

### Kill switches

Kill switch एक flag है जिसे आपका code हर step और हर tool call से पहले check करता है, levels के साथ: एक tool disable करना (सारे refunds रोकना), agent disable करना (human queue या simple form पर fall back करना), या feature disable करना। इसे बिना redeploy के admin screen या config service से flip करो। Flags को shared store से short cache के साथ पढ़ो, ताकि बदलाव कुछ seconds में हर जगह लागू हो जाए:

```python
import json, logging, time

log = logging.getLogger("agent")
WRITE_TOOLS = {"send_email", "issue_refund", "message_driver"}
MAX_STALE = 60                                           # seconds
_cache = {"read_at": float("-inf"), "ok_at": float("-inf"), "flags": {}}

def flags():
    now = time.monotonic()
    if now - _cache["read_at"] > 5:                      # refresh every 5 seconds
        _cache["read_at"] = now
        try:
            _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
            _cache["ok_at"] = now
        except Exception:
            log.warning("flag store unreachable; using last flags")
    if now - _cache["ok_at"] > MAX_STALE:                # no good read for a minute
        return {**_cache["flags"], "write_tools_off": True}
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    if tool and f.get(f"tool_{tool}_off"):
        return False
    return not (tool in WRITE_TOOLS and f.get("write_tools_off"))
```

`config_store` कोई भी shared store हो सकता है जो आपके पास है: database row, Redis या feature-flag service। ये code एक सीमित तरीके से safe fail होता है। छोटा outage कुछ नहीं बदलता। एक मिनट तक कोई अच्छा read न मिले, या start-up पर पहला read fail हो, तो emails और refunds जैसे write tools बंद हो जाते हैं जबकि read-only tools चलते रहते हैं। पुराने flags हमेशा रखने का मतलब होगा कि outage के दौरान flip हुआ switch कभी पहुँचेगा ही नहीं।

### Actions के लिए idempotency

हर real-world action को उस चीज़ से बनी key दो जो उसे unique बनाती है (जैसे order id और refund reason)। लेने वाला system उसी key वाले दूसरे action को मना कर देता है, तो loops और retries payments या messages दोहरा नहीं सकते।

### Kill switch की drill करो

महीने में एक बार, पहले staging में और फिर production में किसी शांत घंटे में, हर switch flip करो और check करो कि tasks कुछ seconds में रुकते हैं, users को साफ़ message दिखता है, और बाकी app चलता रहता है। समय नापो और record करो कि किसने किया। जो teams कभी practice नहीं करतीं, वो असली incident में सीखती हैं कि switch सिर्फ़ start-up पर पढ़ा जाता था, या on call पर किसी को नहीं पता था कि वो कहाँ है।

## एक worked example

Homework-help agent एक महीने ठीक चला, लगभग ₹18,000 प्रति हफ़्ते के model खर्च पर। फिर एक रविवार रात, एक maths tool में हुए बदलाव से वो एक तरह के सवाल पर error लौटाने लगा। Agent छोटे-छोटे बदलावों के साथ retry करता रहा, और students "try again" दबाते रहे। सोमवार सुबह तक feature ₹1.8 lakh खर्च कर चुका था, एक आम हफ़्ते का दस गुना।

Team ने एक महीने के runs निकाले और उनसे limits तय कीं:

- **Per task.** 95% tasks 7 steps, 25,000 tokens और 40 seconds में खत्म हुए, तो caps हैं 15 steps, 60,000 tokens और 90 seconds। तीन एक जैसे tool errors पर task इस message के साथ खत्म होता है: "मैं ये सवाल हल नहीं कर पाया; आपके teacher मदद कर सकते हैं।"
- **Per student.** 95% students ने दिन में ₹6 से कम खर्च किया, तो cap ₹15 है, जो एक friendly "कल फिर आना" के रूप में दिखता है। हर student एक साथ 2 tasks चला सकता है।
- **हर दिन feature.** ₹18,000 प्रति हफ़्ता यानी लगभग ₹2,600 प्रति दिन, और सबसे busy आम दिन लगभग ₹4,000 का था। Cap ₹8,000 है, एक average दिन का लगभग तीन गुना और सबसे busy दिन का दोगुना। 50% (₹4,000) और 80% (₹6,400) पर on-call engineer के phone पर alerts जाते हैं।
- **Circuit breaker** maths tool पर: एक मिनट में 20 failures होने पर वो पाँच मिनट के लिए pause हो जाता है।
- **Kill switch.** हर tool के लिए और agent के लिए एक admin toggle। Agent बंद करने पर "homework help आराम कर रहा है" banner दिखता है; बाकी app चलता रहता है।
- **Provider.** Backstop के रूप में एक hard monthly spend limit।

उस रविवार रात हर control क्या करता:

| Control | Incident पर असर |
| --- | --- |
| Circuit breaker | Fault के एक मिनट के अंदर, हर student के लिए maths tool pause कर देता |
| Repetition check | Loop कर रहे हर task को तीन errors के बाद खत्म कर देता |
| Per-student cap और 2 running tasks | "Try again" को नुकसान कई गुना करने से रोकता |
| ₹8,000 का feature cap | कोई भी दिन ₹8,000 से ज़्यादा का नहीं हो सकता, जबकि उस रात ₹1.8 lakh लगे |
| ₹4,000 पर alert | मामला सस्ता रहते ही किसी को जगा देता |

दो हफ़्ते बाद, ऐसे ही एक tool fault ने एक मिनट के अंदर circuit breaker trip कर दिया। Bill कुछ सौ rupees का रहा, और किसी student के शिकायत करने से पहले ही alert team तक पहुँच गया।

## आम गलतियाँ

- **Step cap न होना।** ये अकेली सबसे सस्ती सुरक्षा है; इसे सबसे पहले जोड़ो।
- **Memory में रखे budgets।** हर server अलग गिनता है और असली total cap से बहुत आगे निकल जाता है। Shared store use करो।
- **Check-then-act budgets।** Total पढ़ने, model call करने और फिर cost जोड़ने से एक साथ आई सारी requests एक ही check pass कर लेती हैं। पहले reserve करो, एक statement में।
- **ऐसे estimates जो upper bound नहीं हैं।** Average cost reserve करोगे तो cap leak होगा। पूरे `max_tokens` के लिए reserve करो।
- **Concurrent tasks पर cap न होना।** दस parallel tasks में से हर एक per-task cap pass कर लेता है।
- **सिर्फ़ per-agent caps।** काम आगे-पीछे करने वाले sub-agents को हर root run के लिए एक count चाहिए।
- **ऐसा kill switch जिसके लिए deploy चाहिए।** Incident में आपको seconds चाहिए, build pipeline नहीं।
- **सिर्फ़ start-up पर पढ़ा जाने वाला kill switch।** वो अगले restart तक कुछ नहीं करता।
- **Fail open होना।** अगर flag store देर तक down रहे, तो write tools को बंद मानो।
- **चुपचाप रुकना।** User को बताओ कि क्या हुआ और log करो; रुका हुआ task एक bug है जिसे fix करना है।
- **Non-idempotent actions को retry करना।** Idempotency keys use करो ताकि loops payments या messages दोहरा न सकें।
- **Floating-point पैसा।** Paise को integers में गिनो।

## जब सरल limits काफ़ी हैं

- **आपकी अपनी team का prototype**: शायद एक step cap और provider का spend alert ही काफ़ी हो।
- **एक या दो model calls वाले fixed workflows**, जहाँ हर request की cost predictable हो।
- **गिने-चुने users वाले read-only internal tools।**

Per-user budgets, feature caps और layered kill switches तब मायने रखते हैं जब बाहर के लोग runs शुरू कर सकें या agents actions ले सकें।

## Demo से production तक

- **Shared storage में budgets atomic तरीके से reserve करो**, हर model call से पहले, और बाद में settle करो।
- **Flags और circuit breakers check करो**, हर step और tool call से पहले।
- **Feature budgets के 50% और 80% पर alert करो**, सबसे ज़्यादा खर्च करने वालों की list के साथ।
- **Concurrent budget test CI में रखो।**
- **Kill switches की drill हर महीने करो** और record करो कि हर एक में कितना समय लगा।
- **हर stop को उसकी वजह के साथ log करो**, और review करो कि limits सही set हैं या नहीं।

## Practice करो

Unbounded consumption पर OWASP की entry पढ़ो।

1. अपने बनाए किसी agent में step, token और time caps जोड़ो, एक साफ़ stop message के साथ।
2. एक repetition check जोड़ो जो तीन एक जैसे tool errors के बाद task खत्म कर दे, और जानबूझकर तोड़े गए tool से उसे trigger करो।
3. इस lesson का reserve-and-settle budget और kill switch जोड़ो, और दोनों को काम करते दिखाओ।
4. अपने budget code पर concurrent test चलाओ। फिर `reserve` को एक सादे "total पढ़ो, फिर जोड़ो" version से बदलो और test को fail होते देखो।

**आपका काम पूरा है जब आप** जानबूझकर कोई tool तोड़कर दिखा सको कि agent आपकी limits के अंदर रुक जाता है, log entry और alert के साथ।
