## Ye kya hai

Jab agent kuch galat karta hai, toh jaanna padta hai kyun: kaunsa step bhatka, model ne kya dekha, kaunse tool ne kya diya. **Agent logs** (aksar traces kehte hain) har run ke har step ko record karte hain:

- har model call: input messages, reply, tokens, time;
- har tool call: tool, arguments, result ya error, time;
- final outcome, user, aur prompt aur model ke versions.

| Step | Type | Input | Output | Time |
|---|---|---|---|---|
| 1 | model | Question + tools | Calls get_tracking | 1.1 s |
| 2 | tool | get_tracking(SHP-77812) | "Nagpur hub, 3 Nov" | 0.4 s |
| 3 | model | ... + tracking result | Calls get_eta | 0.9 s |
| 4 | tool | get_eta(SHP-77812) | **ERROR: timeout** | 5.0 s |
| 5 | model | ... + the error | **"Arrives 5 November"**: gadha hua | 0.8 s |

Run 9c1f, user cust-2231, prompt v6, model chat-default.

Ye lesson Hyderabad ki ek logistics company ko follow karta hai, jiska shipment agent kabhi-kabhi customers ko galat delivery dates bata deta tha.

## Ye kaam kaise karta hai

**Har step ko structured data ki tarah record karo**, loose print statements ki tarah nahi. Ek simple shape: run id, step number, type (model ya tool), inputs, outputs, start aur end time, tokens aur cost. Runs ko JSON lines mein ya kisi tracing tool mein store karo.

**Ho sake toh tracing tool use karo.** LLM apps ke liye bane tools (Langfuse, Arize Phoenix, LangSmith aur kai, zyadatar OpenTelemetry par) har run ko steps ke tree ki tarah dikhate hain jise expand kar sakte ho, timings aur costs ke saath.

**Sab kuch link karo.** Har run ko ek id do, aur use tool logs aur application logs ko pass karo, taaki ek request ko har system mein follow kar sako.

**Failed runs padho.** End se shuru karo (kya galat hua) aur peeche chalo: kya tool result galat tha? Kya model ne use galat padha? Kya usne pehle galat tool chuna? Kya information kabhi available hi nahi thi?

**Failures ko tests banao.** Har interesting failure ka input test case ke roop mein save karo aur changes ke baad dobara chalao.

**Privacy ka dhyaan rakho.** Logs mein user messages aur tool data hota hai. Personal data mask karo, access restrict karo aur retention periods set karo.

**Measure karo.** Logs se success rates, ek task ke steps, ek task ki cost, sabse slow steps aur sabse common errors milte hain.

**JSON lines mein ek step record:**

```text
{"run":"9c1f","step":4,"type":"tool","name":"get_eta","args":{"id":"SHP-77812"},
 "error":"timeout after 5 s","start":"2026-11-03T21:52:10+05:30","ms":5004}
```

**Logs ko jin sawaalon ka jawab jaldi dena chahiye:**

| Sawaal | Zaroori fields |
| --- | --- |
| Ye answer galat kyun gaya? | Har step ke inputs aur outputs, order mein |
| Kaunsa tool sabse zyada fail hota hai? | Har step ka tool name aur error |
| Ek task ki cost kitni hai? | Har model call ke tokens aur cost, har run ke hisaab se jode hue |
| Kya naye prompt se madad mili? | Har run par prompt version, plus outcome |
| Kis user ko problem hui? | Pseudonymous user id aur run id |

**Regular review ki aadat.** Hafte mein ek baar das runs padho: paanch jo fail hue ya jinka feedback kharab tha, aur paanch random chune hue. Random runs zaroori hain, kyunki unse aisi problems dikhti hain jinki abhi kisi ne shikayat nahi ki, jaise agent ka aath steps lena jahan teen kaafi hote. Har run ke liye ek line likho ki kya sahi gaya ya galat. Ek mahine mein ye notes kisi bhi dashboard se behtar batate hain ki agla fix kaunsa karna hai.

**Volume badhne par logs ko kaam ka rakhna.** Error, refusal ya negative feedback waala har run store karo, plus baaki ka ek sample. Unhein itni der rakho ki aapka release cycle cover ho jaye, taaki change se pehle aur baad ki tulna kar sako.

**Chhota tracer jo aap khud likh sakte ho.** Tool apnaane se pehle, kuch lines har step ko run id, timing aur structured record de deti hain:

```python
import json, time, uuid
from contextlib import contextmanager
from contextvars import ContextVar

RUN_ID = ContextVar("run_id", default=None)
STEP = ContextVar("step", default=0)

def start_run(user, prompt_version, model):
    rid = uuid.uuid4().hex[:8]
    RUN_ID.set(rid); STEP.set(0)
    write({"run": rid, "type": "run_start", "user": user, "prompt": prompt_version, "model": model})
    return rid

def write(record):
    record["at"] = time.strftime("%Y-%m-%dT%H:%M:%S%z")
    with open("traces.jsonl", "a") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")

@contextmanager
def step(kind, name, **inputs):
    STEP.set(STEP.get() + 1)
    rec = {"run": RUN_ID.get(), "step": STEP.get(), "type": kind, "name": name, "inputs": inputs}
    t0 = time.monotonic()
    try:
        yield rec                           # the caller sets rec["output"], tokens, cost
    except Exception as err:
        rec["error"] = f"{type(err).__name__}: {err}"
        raise
    finally:
        rec["ms"] = round((time.monotonic() - t0) * 1000)
        write(rec)

# Use it around every model and tool call:
start_run("cust-2231", "v6", "chat-default")
with step("tool", "get_tracking", id="SHP-77812") as rec:
    rec["output"] = "Nagpur hub, 3 Nov 21:40"
```

**Run ko wapas padhna.** Wahi file "run 9c1f mein kya hua?" ka jawab deti hai:

```python
def show(run_id, path="traces.jsonl"):
    rows = [json.loads(l) for l in open(path) if json.loads(l)["run"] == run_id]
    for r in sorted(rows, key=lambda r: r.get("step", 0)):
        what = r.get("error") or str(r.get("output", ""))[:60]
        print(f'{r.get("step", "-"):>2} {r["type"]:<9} {r.get("name", ""):<14} {r.get("ms", ""):>6} ms  {what}')
```

Tracing tool par jaao toh wahi fields rakho. Zyadatar tools OpenTelemetry spans leti hain, isliye move mostly itna hai ki records kahaan bheje jaate hain, wo badalna.

**Jo bhi behaviour badalta hai, sab log karo.** Model ka naam aur version, sampling settings, prompt template ka version, asal mein bheja gaya final prompt, tool versions aur retrieval settings. Jab hafton baad koi bug aata hai, sawaal hamesha hota hai "is run mein kya alag tha?", aur sirf log ki hui settings hi iska jawab de sakti hain.

**Data dekhna aapka nazariya badal deta hai.** Jo teams real runs regular padhti hain, unhein lagta hai ki achhe answer ka unka khayal badal jaata hai: unhein aise failure types dikhte hain jo unhone socha nahi tha aur aisi requirements jo kisi ne likhi nahi thi. Unhein prompt aur eval set mein daalo.

**Traces se agent metrics.** Run ke hisaab se group karke compute karo: success rate, ek run ke steps, ek run ki cost, tool error waale runs ka share, aur woh tools jinke baad aksar failure aata hai. Ek run ke steps ka badhna aksar pehla sanket hota hai ki prompt ya tool change ne agent ko confuse kar diya.

## Ek example se samjho

Hyderabad ki ek logistics company ka agent "Where is my shipment?" ka jawab tracking, delay-reason aur ETA tools call karke deta hai. Customers kabhi-kabhi galat delivery dates ki shikayat karte hain.

Team ek reported run ka trace kholti hai:

```text
run 9c1f  user=cust-2231  prompt=v6  model=chat-default  5 steps  6.2 s  Rs 0.38
 1 model      -> calls get_tracking("SHP-77812")
 2 tool       get_tracking: last scan "Nagpur hub, 3 Nov 21:40"
 3 model      -> calls get_eta("SHP-77812")
 4 tool       get_eta: ERROR timeout after 5 s
 5 model      -> "Your shipment will arrive on 5 November."
```

ETA tool timeout ho gaya, aur model ne "pata nahi" kehne ki jagah ek date gadh di. Fixes: tool ab saaf error message deta hai ("ETA unavailable right now"); prompt kehta hai ki jab tak `get_eta` ne date na di ho, kabhi date mat batao; aur ek check final answer mein dates ko block karta hai agar run mein koi ETA result nahi hai. Wo trace ek test case ban jaata hai.

| Fix | Asar |
| --- | --- |
| ETA tool "ETA unavailable right now" deta hai | Model ko khamoshi nahi, saaf error dikhta hai |
| Prompt: jab tak get_eta ne na di ho, date mat batao | Kam gadhi hui dates |
| ETA result na ho toh check answers mein dates block karta hai | Gadhi hui dates customers ke dekhne se pehle pakdi jaati hain |
| Run test case ke roop mein save hua | Har change ke baad case dobara test hota hai |

**Trace ne ye kaam jaldi kyun kiya.** Step logs ke bina team ko sirf final message dikhta, "Your shipment will arrive on 5 November", aur wo random mein ETA service ya model ko doshi thehra sakti thi. Trace ne dono ek saath dikhaye: tool timeout hua, aur model ne us khamoshi ko bhar diya. Har fix ne in do wajahon mein se ek ko target kiya, aur save kiya hua test saabit karta hai ki dono theek rahein.

## Aam galtiyaan

- **Sirf final answers log karna.**
- **Unstructured print statements.** Search aur analyse karna mushkil.
- **Run ids nahi.** Systems ke beech steps ko connect nahi kar sakte.
- **Personal data bina mask kiye log karna.**
- **Sirf shikayat ke baad logs padhna.** Ek sample regular review karo.

- **Runs par versions nahi.** Prompt aur model versions ke bina, aap nahi bata sakte ki change se cheezein behtar hui ya kharab.
- **Der se aane waale logs.** Agar traces event ke 15 minute baad dikhte hain, toh live debugging unka intezaar karti hai.
- **Prompt template log karna par final prompt nahi.** Bugs aksar usmein chhupe hote hain jo bhara gaya tha.

## Jab simple logging kaafi ho

- **Bina tools ka ek model call**: har request ke liye tokens, time aur outcome ke saath ek log line kaafi hai.
- **Prototype jo aap khud chalate ho**: har step ko console mein print karna tab tak chalta hai jab tak doosre log use na karein.
- **Do-teen steps waale fixed workflows**: shared request id ke saath normal application logs kaafi ho sakte hain.

Full traces par tab jao jab runs mein kai steps hon, tools aise fail hon jo matter karte hain, ya kai log ek hi system debug karein.

## Demo se production tak

- **Har run trace karo**, saare failures aur negative-feedback runs store karo, aur baaki ka sample lo.
- **Likhne se pehle personal data mask karo**, access restrict karo, aur retention ko apne release cycle tak rakho.
- **Support ticket se ek run kholna aasaan banao**: user ko dikhne waale error message mein run id daalo.
- **Trace metrics par alert lagao**: tool error rate, ek run ke steps aur ek run ki cost.
- **Interesting runs ko test cases banao**, ek click ya ek command se.
