## Ye kya hai

**Code review** tab hota hai jab teammate aapka change merge hone se pehle padhta hai. GitHub aur GitLab par ye ek **pull request** (ya merge request) par hota hai: change, uska description, automated checks, aur specific lines par comments ka thread.

Reviews teen kaam karte hain. Users ke dekhne se pehle bugs pakadte hain. Codebase ko consistent rakhte hain, taaki wo styles ka patchwork na ban jaye. Aur knowledge failate hain: review ke baad change ek ki jagah do logon ko samajh aata hai.

Review code ke baare mein baatcheet hai, insaan ka judgement nahi. Jo teams achhe se review karti hain wo tez ship karti hain, kyunki problems tab pakdi jaati hain jab unhe theek karna sasta hota hai.

## Ye kaam kaise karta hai

```flow
title: Open hone se merge tak ek pull request
Author ek chhota pull request kholta hai | kya, kyun, kaise test hua -> Automated checks | tests, linter, build
Automated checks -[fail]-> Author fix karta hai -> Automated checks
Automated checks -[pass]-> Reviewer padhta hai | pehle correctness, phir design, phir style
Reviewer padhta hai -[changes chahiye]-> Comments: specific, kind, label ke saath
Comments: specific, kind, label ke saath -> Author reply karta hai ya fixes push karta hai -> Reviewer padhta hai
Reviewer padhta hai -[sab theek hai]-> Approve karke merge
```

**Author ke roop mein**, apne change ko review karna aasaan banao:

- Use chhota rakho aur ek hi cheez ke baare mein. 200-line pull request ka dhyaan se review hota hai; 2,000-line waale ko log skim kar dete hain.
- Description likho: kya badla, kyun, aur kaise test kiya. Ticket link karo. Jo dikhta hai uske screenshots jodo.
- Pehle apna hi diff review karo. Bache hue prints aur typos aap kisi aur se pehle pakad loge.
- Review maangne se pehle checks pass karao.

**Reviewer ke roop mein**, sabse zaroori cheez ko is order mein dekho:

| Order | Kya dekho | Examples |
| --- | --- | --- |
| 1 | Correctness | Galat logic, unhandled errors, edge cases, security, data leaks |
| 2 | Tests | Kya naye behaviour ka test hai? Kya change ke bina test fail hoga? |
| 3 | Design | Kya ye system mein fit hota hai? Kuch duplicate hai? Kya ise badalna aasaan hoga? |
| 4 | Readability | Names, lambe functions, uljha logic, "kyun" waale comments ki kami |
| 5 | Style | Formatting aur import order, ideal roop se linter fix kare, insaan nahi |

Aise comments likho jo specific hon (kya aur kahan), bataayein ki kyun zaroori hai, aur fix suggest karein. Jo optional hai use "nit:" ya "optional:" se label karo. Jab pakka na ho toh assert karne ki jagah sawaal poochho. Jo achha hai wo bhi batao; isse author ko pata chalta hai ki kya karte rehna hai.

**Comments paane waale author ke roop mein**, maano ki irada achha tha. Thanks bolo, fix karo, aur har thread par reply karo. Agar aap agree nahi ho, toh evidence ke saath samjhao. Agar thread do baar se zyada aage-peeche jaaye, toh call par baat karke suljhao.

**Anjaan area mein review karna.** Achha review karne ke liye poora codebase jaanna zaroori nahi. Pehle description aur ticket padho, taaki pata chale ki change kya karna chahiye. Ho sake toh code ya tests local mein chalao. Un cheezon par dhyaan do jinhe aap judge kar sakte ho, jaise error handling, edge cases, tests aur readability, aur saaf bolo ki kaun se hisse aap assess nahi kar paaye, taaki author unke baare mein kisi aur se pooch sake.

**AI changes ka review.** Prompt, model ya retrieval settings ka change bhi ek code change hai, par uska asar outputs mein dikhta hai, diff mein nahi. Pehle aur baad ke eval results category ke hisaab se maango, aur kuch example outputs jo badle. Prompt mein ek shabd ka edit ek tarah ke sawaal ko theek kar sakta hai aur chupchaap doosre ko bigaad sakta hai.

**Speed matter karti hai.** Jo pull request teen din review ka intezaar karta hai wo purana ho jaata hai: main aage badh jaata hai, conflicts jama hote hain aur author ka context chhoot jaata hai. Kai teams ek working day ke andar pehla review dene ka target rakhti hain. Agar aap time par theek se review nahi kar sakte, toh bata do, taaki author kisi aur ko dhoondh sake.

**Browser mein try karo.** Ye function chalao, phir review karo: neeche ke tests ek bug dikhate hain. Use fix karke dobara chalao.

```python
def average_rating(ratings):
    """Average of 1 to 5 star ratings, ignoring missing ones (None)."""
    total = sum(r for r in ratings if r is not None)
    return total / len(ratings)            # review: is this the right count?

print(average_rating([5, 4, None, 3]))     # expected 4.0
print(average_rating([2, 4]))              # expected 3.0
```

## Ek example se samjho

Aditya, Gurugram ke ek food-delivery startup mein junior engineer, ek pull request kholta hai jo "reorder last meal" button jodta hai. Ye app, API aur database mein 640 lines badalta hai.

Uski reviewer Meera use ise todne ko kehti hai: ek pull request tests ke saath API endpoint ke liye, ek button ke liye. Pehla 180 lines ka hai. Wo pandrah minute mein review karti hai aur chaar comments chhodti hai:

- "The endpoint takes the user id from the request body, so anyone could reorder for another user. Could we use the id from the logged-in session instead?" (correctness aur security, blocking)
- "There is no test for a user with no past orders. What should it return?" (tests, blocking)
- "Could `get_last()` reuse `OrderRepository.latest_for_user()`? It looks like the same query." (design)
- "nit: `res` could be `last_order`. Not blocking."

Wo ye likhkar khatam karti hai: "The error handling for a closed restaurant is really clear, nice."

Aditya security issue fix karta hai, test jodta hai, maujooda query reuse karta hai aur variable rename karta hai. Har thread par reply karta hai ki usne kya badla. Meera approve karti hai; change usi din merge ho jaata hai. Doosra pull request, button waala, aur bhi tez nikal jaata hai, kyunki API pehle hi review ho chuki thi.

## Aam galtiyaan

- **Bade pull requests.** Reviewers skim kar dete hain aur bugs nikal jaate hain. Step ke hisaab se todo.
- **Sirf style par comment karna.** Formatting tools par chhodo; insaani dhyaan logic, tests aur security par lagao.
- **Vague comments.** "This is wrong" author ko andaaza lagane par chhod deta hai. Kya, kyun aur ek suggestion batao.
- **Comments ko personally lena.** Comment code ke baare mein hota hai. Agar koi kathor lage toh ek sawaal poochh lo.
- **Bina padhe approve karna.** Rubber stamp bina review ke se bhi bura hai, kyunki log us par bharosa karte hain.
- **Preferences par block karna.** Agar ye pasand ki baat hai, toh optional mark karo aur author ko decide karne do.

## Practice karo

1. Apna pichhla pull request kholo aur uska description kya, kyun aur kaise test kiya ke saath dobara likho.
2. Jis open-source project ko aap use karte ho, usme ek pull request review karo aur importance ke order mein paanch comments ka draft banao.
3. Teen vague comments, jo aapne paaye ya likhe, unhe specific aur kind comments mein dobara likho.
4. Behavioural interviews ke liye ek code review ki STAR story taiyaar karo jisne aapka mann badla.
