## Ye kya hai

**Transformer** ek neural network architecture hai, jo 2017 mein aaya, aur **attention** naam ke mechanism ke aas-paas bana hai. Ye ek sequence (words, image patches, audio frames) ko process karta hai aur har position ko baaki har position ko dekhne deta hai taaki tay ho sake ki kya maayne rakhta hai.

Teen families ise use karti hain:

- **Decoder-only** models ek ek token karke text generate karte hain: aaj ke chat aur coding models.
- **Encoder-only** models text padhte hain aur representations banate hain: search ke liye kai embedding models, aur classifiers. (Kuch haal ke embedding models decoder-only models se adapt kiye gaye hain.)
- **Encoder-decoder** models ek sequence ko doosri mein map karte hain: translation aur summarisation.

Vision transformers images ko patches mein todte hain aur unhe tokens ki tarah treat karte hain.

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| "it" se attention | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |

"The bank approved the loan because it trusted the applicant" mein, token "it" ek query bhejta hai, use har key se compare karta hai, aur zyadatar apna matlab "bank" se leta hai.

```flow
dir: LR
title: Ek transformer layer, darjanon layers mein dohraayi hui
Token vectors -> Multi-head attention -> Add aur normalise -> Feed-forward -> Add aur normalise, phir se
```

Is lesson mein hum Chennai ki ek legal-tech startup ke saath chalenge jo court judgments ke liye teen tarah ke transformer use karti hai.

## Ye kaam kaise karta hai

**Tokens aur embeddings.** Text ko tokens mein toda jaata hai; har token ek vector (embedding) ban jaata hai. Positional information jodi jaati hai taaki model ko order pata ho.

**Attention.** Har token ke liye, model teen vectors nikalta hai: ek query (main kya dhundh raha hoon?), ek key (mujhmein kya hai?) aur ek value (main aage kya pass karta hoon?). Woh query ko har key se compare karke attention weights nikalta hai, phir values ka weighted mix leta hai. "The bank approved the loan because it trusted the applicant" mein, attention "it" ko "the bank" par focus karne mein madad karta hai.

**Multi-head attention.** Kai attention heads ek saath chalte hain, har ek alag relationships seekhne ke liye azaad (grammar, references, topics).

**Layers.** Har transformer layer mein attention ke baad ek chhota feed-forward network hota hai, shortcuts aur normalisation ke saath jo gehre stacks ko train karne layak banate hain. Bade models mein darjanon layers stack hoti hain.

**Generation.** Decoder-only model har mumkin agle token ke liye ek probability predict karta hai, ek chunta hai (sampling), use jodta hai, aur dohraata hai. Ek mask training ke dauran har position ko future tokens dekhne se rokta hai.

**Cost.** Attention har token ko har doosre se compare karta hai, isliye sequence length ke saath cost tezi se badhti hai. Isiliye context windows ki limits hoti hain aur lambe prompts dheeme aur mehnge hote hain. Engineering tricks (efficient attention kernels, keys aur values ki caching) cost ghatate hain.

**Pre-training aur adaptation.** Models ko bahut bade data par missing ya agle tokens predict karne ke liye pre-train kiya jaata hai, phir adapt kiya jaata hai: chat models ke liye instruction tuning aur preference training, khaas tasks ke liye fine-tuning, ya prompts aur retrieval ke saath jaise hain waise use karna.

**Ye kyun jeeta.** Attention lambi doori ke relationships achhe se sambhaalta hai aur GPUs par parallel mein efficiently train hota hai, jisse bahut bade models aur datasets tak scale karna mumkin hua.

**Teen families saath-saath:**

| Family | Kya padhta hai | Kya banata hai | Aam istemaal |
| --- | --- | --- | --- |
| Encoder-only | Poora input ek saath | Har token ya har text ke liye ek vector | Classification, embeddings, search |
| Decoder-only | Left se right, aage jhaankna nahi | Agla token, baar-baar | Chat, coding, drafting, reasoning |
| Encoder-decoder | Pehle poora input, phir generate | Ek nayi sequence | Translation, summarisation |

**Attention seedhe arithmetic mein.** Ek token ke liye, uski query ka har token ki key ke saath dot product lo. Bade dot products ka matlab "relevant". Scores ko vector size ke square root se bhaago taaki woh stable range mein rahein, phir softmax se unhe aise weights mein badlo jinka jod 1 ho. Har token ki value ko uske weight se guna karo aur jodo. Nateeja us token ke liye ek naya vector hai jo un tokens ki jaankari milata hai jin par usne attend kiya. Har head ye apni seekhi hui queries, keys aur values ke saath karta hai, aur nateeje jod diye jaate hain.

**Pre-training kya sikhata hai.** Bahut zyada text mein agla ya missing token predict karte-karte model grammar, facts, styles aur reasoning ke patterns seekh leta hai, kyunki ye sab prediction mein madad karte hain. Phir instruction tuning aur preference training us kachchi kshamta ko ek helpful assistant mein dhaalte hain jo requests follow karta hai.

**NumPy ki kuch lines mein attention.** Ek head, ek causal mask, aur weights print kiye hue taaki aap dekh sako kaun kis par attend karta hai:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                       # how relevant each token is to each other
    if causal:
        scores = np.where(np.triu(np.ones_like(scores), k=1) == 1, -np.inf, scores)
    weights = softmax(scores)                           # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "she"]
x = rng.normal(size=(len(tokens), 16))                  # token embeddings plus position
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(np.round(w, 2))                                   # upper triangle is 0: no peeking ahead
```

Ek trained model mein, "she" ki row "Priya" par zyada weight daalegi. Yahan weights random hain, par shapes aur mask bilkul waise hi hain jaise asli models har layer ke har head ke liye compute karte hain.

**Multi-head ke shapes.** 768 ki model width aur 12 heads ke saath, har head 64 dimensions par kaam karta hai; unke outputs wapas 768 mein jode jaate hain aur ek aur matrix se mix hote hain. Wahi idea PyTorch mein:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                           # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                         # (2, 10, 768) and (2, 10, 10)
```

**Parameters kahan hote hain.** Har layer mein, attention ke paas width × width ke chaar matrices hote hain (queries, keys, values, output); feed-forward block aam taur par width ka lagbhag chaar guna failta hai aur wapas aata hai, jo lagbhag utne hi aur weights hain:

```python
def layer_params(width, ff_mult=4):
    attn = 4 * width * width
    ff = 2 * width * (ff_mult * width)
    return attn + ff

w, layers, vocab = 4096, 32, 128_000
total = layers * layer_params(w) + vocab * w
print(f"about {total / 1e9:.1f} billion parameters")    # about 7 billion: the 7B to 8B range
```

Asli models details mein alag hote hain (grouped key-value heads, gated feed-forward layers), par andaaza sahi range mein baithta hai.

**Lambe inputs zyada cost kyun karte hain.** Attention har token ko har pehle token se compare karta hai, isliye kaam length ke square ke saath badhta hai: 8,000 tokens mein 1,000 ke mukable lagbhag 64 guna attention kaam lagta hai. Generation har pehle token ke keys aur values ka ek cache bhi rakhti hai, isliye lambe contexts ko bahut GPU memory chahiye.

## Ek example se samjho

Chennai ki ek legal-tech startup Indian court judgments ko area of law (property, family, criminal, tax, labour) ke hisaab se classify karti hai aur unpar semantic search bhi chahti hai.

- **Classification**: woh ek chhote encoder-only transformer ko 12,000 labelled judgment summaries par fine-tune karte hain. Ye 91% accuracy tak pahunchta hai, jabki keyword features par gradient-boosted model 82% tak, kyunki attention "the appellant's claim to ancestral property" jaisa context pakadta hai.
- **Search**: woh paragraphs ko embed karne aur milte-julte passages retrieve karne ke liye ek embedding model (encoder) use karte hain.
- **Summaries**: woh API ke zariye ek decoder-only language model use karte hain, prompt mein retrieved passages ke saath.

Jab judgments encoder ki 512-token limit se zyada hote hain, toh woh poora text classify karne ki jagah pehle aur sabse relevant sections classify karte hain, jo length ke saath attention ki cost ka seedha nateeja hai.

| Task | Model type | Nateeja |
| --- | --- | --- |
| Area-of-law classification | Fine-tuned chhota encoder | 91%, keyword features ke 82% ke mukable |
| Milte-julte passages ka search | Encoder embedding model | Judgments ke beech semantic matches |
| Summaries | API ke zariye decoder-only model | Retrieved passages se cited summaries |
| Lambe judgments | 512-token limit wala encoder | Sabse relevant sections ko classify karo |

## Aam galtiyaan

- **Saare transformers ko chatbots maanna.** Encoders, decoders aur encoder-decoders alag kaamon ke liye hain.
- **Sequence limits ko ignore karna.** Lambe inputs truncate hote hain ya mehnge padte hain.
- **Jab chhota encoder kaafi ho tab bada model fine-tune karna.** Model ka size kaam ke hisaab se rakho.
- **Attention weights ko explanations maanna.** Ye faislon ki bharose layak explanations nahi hain.
- **Tokenisation bhoolna.** Indian languages mein aksar har word par zyada tokens lagte hain, jisse limits aur cost par asar padta hai.
- **Ye sochna ki attention akele "samajhta" hai**: ye weighted averaging hai; matlab training se aata hai.
- **Prompts aur context design karte samay lambe inputs ki quadratic cost ko ignore karna.**

## Jab transformer internals ki zaroorat nahi

- **API ke zariye models use karna**: roz ke kaam mein prompts, retrieval aur evals zyada maayne rakhte hain.
- **Tabular prediction**, jahan boosted trees aksar behtar tool hote hain.
- **Simple text tasks** jinhe keyword rule ya chhota classifier pehle se achhe se sambhaal leta hai.

Internals ka gyaan tab kaam aata hai jab models chunne, hardware size karne, long-context behaviour debug karne ya fine-tuning karne hon.

## Demo se production tak

- **Hardware chunne se pehle architecture se memory aur cost estimate karo** (layers, width, heads, context).
- **Prompts aur contexts ko zaroorat se lamba mat rakho**, quadratic attention cost ko dekhte hue.
- **Model ka apna tokenizer aur chat template** bilkul waise hi use karo jaise documented hai.
- **Long-context accuracy ko apne documents par benchmark karo**, sirf advertised window par nahi.
- **Har deployment ke saath model architecture aur version record karo.**
