## Ye kya hai

**Transformer** ek neural network architecture hai, jo 2017 mein aayi aur **attention** naam ke mechanism par bani hai. Ye ek sequence (shabd, image patches, audio frames) ko process karta hai. Har layer mein, har position tay karti hai ki baaki positions se kitna lena hai.

Teen families ise use karti hain:

- **Decoder-only** models ek baar mein ek token karke text generate karte hain. Llama family jaise aaj ke open chat aur coding models aise hi bane hain.
- **Encoder-only** models poora text ek saath padhte hain aur representations banate hain: classifiers, aur search ke liye kai embedding models. Qwen3-Embedding (June 2025) jaise kuch naye embedding models iski jagah decoder models se bane hain.
- **Encoder-decoder** models ek sequence padhkar doosri likhte hain: translation aur summarisation.

Vision transformers image ko patches mein kaatte hain aur har patch ko token ki tarah treat karte hain.

Neeche ki table ek head mein "it" shabd se attention dikhaati hai. Numbers sirf samjhaane ke liye hain, kisi asli model se nahi.

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| Encoder (dono taraf dekhta hai) | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |
| Decoder (sirf peeche ka dekhta hai) | 0.03 | **0.45** | 0.06 | 0.02 | 0.36 | 0.03 | 0.05 | 0 | 0 | 0 |

Encoder "trusted" dekh sakta hai, jisse use pata chalta hai ki "it" bank hai (loan kisi par trust nahi kar sakta). Decoder baad ke shabd nahi dekh sakta, isliye "it" par "bank" aur "loan" ke beech faisla abhi khula hai. "trusted" jaise baad ke tokens peeche dekhkar ise tay karte hain. Har row ka jod 1 hai.

## Ye kaise kaam karta hai

### Tokens aur embeddings

Ek **tokenizer** text ko tokens mein todta hai: poore shabd, shabdon ke tukde ya akele bytes. Kai chat-model tokenizers byte-pair encoding use karte hain: bytes se shuru karo aur baar-baar sabse common paas-paas waale pairs ko merge karke naye tokens banao. Phir har token id ek learned table se ek row chunta hai, jisse ek vector (ek **embedding**) milta hai. Jaise, Llama 3 8B ki vocabulary 128,256 tokens ki hai aur vectors 4,096 numbers chaude hain.

Tokenizers apne merges apne training text se seekhte hain, isliye jo languages us text mein kam thi, woh zyada tukdon mein tootti hain. Humne OpenAI ke puraane `cl100k_base` aur naye `o200k_base` tokenizers se ek sentence ke tokens gine (November 2026):

| Sentence | cl100k_base | o200k_base |
| --- | --- | --- |
| The bank approved the loan. | 6 | 6 |
| Bank ne loan approve kar diya. | 8 | 7 |
| बैंक ने लोन मंज़ूर कर दिया। | 31 | 11 |

Naye tokenizer ke saath bhi Hindi sentence ko English waale se lagbhag dogune tokens chahiye. Zyada tokens ka matlab zyada bill, dheeme replies aur context mein kam jagah. Indian languages mein AI waala lesson ismein aur gehraai se jaata hai.

### Position

Attention khud order nahi dekhta: shabdon ko shuffle kar do, tab bhi har token ko wahi mix milega. Isliye model ko position ki information chahiye. 2017 waale transformer aur BERT ne har embedding mein ek position vector **joda**. BERT ne aise 512 vectors seekhe, isiliye woh 512 tokens se aage nahi padh sakta.

Llama-family models aur ModernBERT iski jagah **rotary position embeddings (RoPE)** use karte hain. Har attention layer ke andar, har query aur key ko uski position par depend karne waale angle se rotate kiya jaata hai. Phir do tokens ke beech ka score is par depend karta hai ki woh kitni door hain. Thodi extra training se rotary embeddings ko un contexts tak stretch kiya ja sakta hai jo model ke pehle dekhe contexts se lambe hon; context windows ke badhne ka ye ek tareeka hai.

### Attention

Har token teen learned matrices se apne embedding se teen vectors nikaalta hai:

- ek **query**: main kya dhoondh raha hoon?
- ek **key**: mujhe kis cheez par match kiya ja sakta hai?
- ek **value**: chuna gaya to main aage kya doonga?

Model token ki query ka har key se dot product leta hai. Bada dot product matlab "relevant". Phir woh scores ko key size ke square root se divide karta hai, kyunki vector size ke saath dot products badhte hain aur bahut bade scores par softmax ek hi token chun leta hai aur seekhna band kar deta hai. Ek **softmax** scores ko aise weights mein badalta hai jinka jod 1 ho. Output values ka weighted sum hai: token ke liye ek naya vector, jismein woh mila hua hai jis par usne attend kiya.

Decoder mein, ek **causal mask** softmax se pehle future tokens ke scores ko minus infinity kar deta hai, isliye unke weights bilkul 0 ho jaate hain. Iske bina, training mein har position wahi token dekh leti jise use predict karna hai.

Mask ke saath ek head, NumPy mein:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                  # relevance of every token to every other
    if causal:                                     # hide future tokens
        future = np.triu(np.ones_like(scores), k=1) == 1
        scores = np.where(future, -np.inf, scores)
    weights = softmax(scores)                      # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "because", "she"]
x = rng.normal(size=(len(tokens), 16))             # one 16-number vector per token
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(out.shape)                                   # (6, 8): one new vector per token
print(np.round(w, 2))                              # zeros above the diagonal
```

Pehli row `[1, 0, 0, 0, 0, 0]` hai: "Priya" sirf khud par attend kar sakta hai. Yahan weights random hain. Trained model mein "she" waali row "Priya" par zyada weight daalegi.

### Multi-head attention aur layer

Kai heads saath-saath chalte hain, har ek ke apne query, key aur value matrices ke saath, isliye har head alag rishta seekh sakta hai. 768 ki width aur 12 heads mein har head 64 numbers par kaam karta hai; outputs wapas jodkar 768 kiye jaate hain aur ek aur matrix se mix hote hain. PyTorch mein ye built-in hai:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                      # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)   # True = hidden
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                    # (2, 10, 768) and (2, 10, 10)
```

Ek layer matlab attention, aur uske baad ek **feed-forward** network jo har token par alag se kaam karta hai. Shortcut connections har block ke input ko uske output mein wapas jodte hain, taaki gehre stacks bhi train ho sakein. 2017 waala model har block ke baad normalise karta tha; Llama-style models har block se pehle normalise karte hain (RMSNorm se), jisse training zyada stable rehti hai. Bade models aisi darjanon layers stack karte hain.

```flow
dir: TB
title: Llama style mein ek decoder layer, har layer mein dohraai jaati hai
Token vectors -> Normalise
Normalise -> Masked multi-head attention | queries aur keys par rotary positions lagti hain
Masked multi-head attention -> Input wapas jodo
Input wapas jodo -> Phir se Normalise
Phir se Normalise -> Feed-forward | gated, lagbhag 3.5 guna chauda
Feed-forward -> Phir se jodo
Phir se jodo -> Agli layer
```

### Generation, KV cache aur sampling

Decoder aakhri position ke vector ko apni vocabulary ke har token ke liye ek score mein badalta hai, phir ek chunta hai. **Temperature** softmax se pehle scores ko divide karta hai: 1 se kam par choice safe hoti hai, 1 se zyada par zyada varied. **Top-p** sirf sabse likely tokens rakhta hai jinki probabilities ka jod p (jaise 0.9) ho, aur unhi mein se sample karta hai. Chuna gaya token judta hai aur loop phir chalta hai.

Har step par poore text ke keys aur values phir se compute karna bekaar ka kaam hoga, isliye model unhe store kar leta hai: yahi **KV cache** hai. Har naya token sirf apni query, key aur value compute karta hai aur cache par attend karta hai. Isse generation tez hota hai, par cache har token aur har user ke saath badhta hai.

### Lambe context ke teen costs

| Cost | Kiske saath badhta hai | Aapke liye iska matlab |
| --- | --- | --- |
| API bill | Tokens, linearly | Prompt ke har extra token ke paise lagte hain, har call par |
| KV cache memory | Tokens × users | Lambi chats aur zyada users GPU memory bhar dete hain |
| Attention compute | Length ka square | Sirf tab maayne rakhta hai jab context lamba ho jaaye |

Llama 3 8B shape ke liye, har naya token har layer mein weight matrices mein lagbhag 218 million multiply-adds karta hai, aur har us puraane token ke liye jis par woh attend karta hai lagbhag 8,000 aur (config se mota hisaab). 2,000 tokens par attention kaam ke dasven hisse se bhi kam hai; lagbhag 27,000 tokens par jaakar hi woh baraabari par aata hai. Poori sequence par attention ka kaam square ke saath badhta hai: 8,000 tokens mein 1,000 ke mukaable lagbhag 64 guna attention ka kaam. **FlashAttention** wahi exact result slow GPU memory ke bahut kam chakkaron mein nikaalta hai, isliye woh tez hai, par comparisons ki ginti wahi rehti hai.

### Naye variations: 2026 ka model card padhna

| Idea | Ye kya badalta hai | Config mein kahan dikhta hai |
| --- | --- | --- |
| Rotary positions | Position attention ke andar aati hai; contexts stretch kiye ja sakte hain | `rope_theta`, `rope_scaling` |
| Grouped-query attention | Query heads ke groups ek key-value head share karte hain: chhota KV cache, quality mein thoda hi nuksaan | `num_attention_heads` se kam `num_key_value_heads` |
| Gated feed-forward | Do ki jagah teen matrices | `intermediate_size`, `hidden_act` |
| Mixture of experts | Kai feed-forward "experts"; ek router har token ko kuch hi experts ke paas bhejta hai | `num_local_experts`, `num_experts_per_tok` |
| Local attention | Kuch layers sirf paas ke tokens par attend karti hain, jisse lambe input ka cost ghatta hai | sliding-window settings |

Mixture of experts do numbers ko alag karta hai. **Total** parameters sab memory mein hone chahiye; **active** parameters har token ka compute tay karte hain. Mixtral 8x7B mein kul 46.7 billion hain aur har token par 12.9 billion use hote hain; DeepSeek-V3 mein kul 671 billion aur active 37 billion. Hardware size karne se pehle dono numbers padho.

### Parameters kahan hain

```python
def params(width, layers, vocab, ffn, heads, kv_heads, gated=True, tied=False):
    head = width // heads
    attn = 2 * width * width + 2 * width * kv_heads * head   # Q and output, then K and V
    ff = (3 if gated else 2) * width * ffn                     # gated layers use 3 matrices
    emb = vocab * width * (1 if tied else 2)                   # input table, output layer
    return layers * (attn + ff) + emb

# Llama 3 8B, from its published config
print(params(width=4096, layers=32, vocab=128_256, ffn=14_336, heads=32, kv_heads=8) / 1e9)
# about 8.03, matching the published 8B size
```

Har layer ke weights ka lagbhag chaar-paanchvaan hissa feed-forward block mein hai, attention mein nahi. Har number ke 2 bytes (16-bit) par, 8 billion parameters ko kisi bhi KV cache se pehle hi lagbhag 16 GB GPU memory chahiye.

### Pre-training aur adaptation

Models ko bahut saare text par agla token (decoders) ya chhipaaye gaye tokens (encoders) predict karne ke liye pre-train kiya jaata hai. Grammar, facts aur reasoning ke patterns, sab prediction mein madad karte hain, isliye model unhe seekh leta hai. Phir chat models ko instruction tuning aur preference training se shape kiya jaata hai. Apne tasks ke liye aap fine-tune kar sakte ho, ya model ko waise hi prompts aur retrieval ke saath use kar sakte ho.

Transformers isliye jeete kyunki attention door ke tokens ko seedhe jodta hai aur saari positions GPUs par parallel mein train hoti hain, jisse bahut bade models aur datasets tak scale karna mumkin hua.

## Ek worked example

Chennai ke ek legal-tech startup ke paas Indian court judgments par teen kaam hain.

**1. Area of law ke hisaab se classify karna** (property, family, criminal, tax, labour). Unke paas 12,000 labelled judgment summaries hain. Ek chhota fine-tuned encoder saaf choice hai: sasta, tez aur labels ka faayda utha sakta hai. Maan lo unke test set par ye 91% accuracy deta hai, jabki keyword counts par gradient-boosted model 82% (samjhaane ke liye numbers). Ye faayda context se aata hai: "the appellant's claim to ancestral property" ka matlab property law hai, tab bhi jab "property" shabd na ho.

Poore judgments unke BERT-style encoder ki 512-token limit se lambe hote hain. Ye limit un 512 learned position vectors se aati hai jinke saath woh train hua tha, attention cost se nahi. Unke paas do options hain:

- Har judgment ko chunks mein baanto, har chunk classify karo aur votes milaao.
- ModernBERT jaisa long-context encoder use karo, jo 8,192 tokens padhta hai. Uska model card chetaavni deta hai ki poori window chhote inputs se slow hai, isliye woh speed bhi test karte hain.

**2. Semantic search.** Ek embedding model har paragraph ko ek baar vector mein badalta hai; queries vector search se match hoti hain.

**3. Summaries.** Privacy ke liye woh ek GPU par 8B open model self-host karne ki sochte hain. Kuch bhi khareedne se pehle config se size nikaalte hain:

```python
def kv_cache_gb(tokens, layers=32, kv_heads=8, head_dim=128, bytes_per_number=2, users=1):
    per_token = 2 * layers * kv_heads * head_dim * bytes_per_number   # one key and one value
    return per_token * tokens * users / 1e9

print(kv_cache_gb(1))                     # 0.000131 GB, about 0.13 MB per token
print(kv_cache_gb(6_500, users=10))       # 8.5 GB for 10 judgments at once
print(kv_cache_gb(6_500, users=10, kv_heads=32))   # 34 GB without grouped-query attention
```

| Item | Memory |
| --- | --- |
| Weights, 2 bytes par 8 billion | Lagbhag 16 GB |
| KV cache, 6,000 tokens ke 10 judgments aur summary ke liye 500 aur | Lagbhag 8.5 GB |
| Runtime overhead se pehle total | Lagbhag 25 GB |

Runtime overhead jodne ke baad 24 GB GPU mein ek saath 10 ke liye koi headroom nahi bachta; 40 ya 48 GB GPU mein jagah bachti hai, ya woh ek baar mein 5 process karein. Ye fit grouped-query attention ki wajah se hota hai: har query head ke liye ek key-value head hota to cache chaar guna bada hota.

## Aam galtiyaan

- **Har transformer ko chatbot samajhna.** Encoders, decoders aur encoder-decoders alag-alag kaamon ke liye hain; classification mein chhota encoder aksar bade chat model ko hara deta hai.
- **Sirf weights se hardware size karna.** KV cache context length aur users ke saath badhta hai; lambe contexts aur zyada users ko weights se bhi zyada memory chahiye ho sakti hai.
- **Encoder ki 512-token limit ko attention cost samajh lena.** Ye us position table se aati hai jiske saath model train hua tha.
- **Attention maps ko explanation maan lena.** Attention weights dikhaate hain ki ek head mein information kahan se bahi, ye nahi ki model ne faisla kyun liya.
- **Galat chat template ya tokenizer use karna.** Ek template se fine-tune hua model doosre template par kharaab chalta hai; wahi template use karo jo documented hai.
- **Mixture-of-experts model ke total parameters ko uski speed batana.** Memory total parameters ke hisaab se chalti hai; har token ka compute active parameters ke hisaab se.
- **Tokenisation bhool jaana.** Hindi ya Tamil text ko English se kai guna tokens lag sakte hain, jisse cost, speed aur context mein jagah badalti hai.

## Jab transformer ke internals zaroori nahi

- **API se models use karte samay**: roz ke kaam mein prompts, retrieval aur evals zyada maayne rakhte hain.
- **Tabular prediction**, jahan boosted trees aamtaur par behtar tool hain.
- **Aasaan text tasks**, jinhe keyword rule ya chhota classifier pehle se achhe se sambhaal leta hai.

Internals jaanna tab kaam aata hai jab models chunne hon, GPUs size karne hon, long-context behaviour debug karna ho ya fine-tune karna ho.

## Demo se production tak

- **Hardware khareedne se pehle memory ka andaaza lagao**: weights, aur saath mein aapki asli context length aur users ki sankhya par KV cache.
- **Prompts zaroorat se lambe mat rakho**: har token ka bill lagta hai, woh cache hota hai aur us par attend kiya jaata hai.
- **Model ka apna tokenizer aur chat template** bilkul waise use karo jaise documented hai.
- **Long-context accuracy ko apne documents par benchmark karo**, sirf advertised window par bharosa mat karo.
- **Har language ke tokens gino**, un languages ke jinmein aapke users likhte hain.
- **Har deployment ke saath model, version aur config record karo**.
