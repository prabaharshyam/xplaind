## Ye kya hai

**Latency budget** sabse lamba acceptable response time hai, jo steps mein toda gaya ho. Chat assistant ke liye: pehla token 95th percentile par 1.5 seconds ke andar, poora answer 8 seconds ke andar. Phir budget steps mein baant jaata hai: auth 50 ms, query rewrite 300 ms, retrieval aur reranking 400 ms, model time to first token 700 ms.

**Load testing** system par realistic traffic bhejna hai, step-by-step badhate hue, aur response times, errors aur resource use record karna hai, taaki aapko pata chale ki kis load par woh tootta hai aur sabse pehle kya tootta hai.

```flow
dir: LR
title: Latency budget: p95 pehla token 2 s mein
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| Pehle: 10 connections ka pool | 1 s | 2 s | 6 s | | | |
| Baad mein: 40 ka pool + ek index | 1 s | 1 s | 1 s | 1 s | 1 s | 1 s |

Users ki sankhya ke hisaab se p95 pehla token, ek fake model ke saath naapa gaya.

Ye lesson Jaipur ke ek intercity bus operator ko follow karta hai, jo apne booking assistant ko festival-season traffic ke liye taiyaar kar raha hai.

## Ye kaam kaise karta hai

**Percentiles, averages nahi.** 2 seconds ka average 5% users ke 15 seconds wait karne ko chhupa sakta hai. Median (p50), 95th (p95) aur 99th percentile (p99) track karo. Users slow waalon ko yaad rakhte hain.

**Step ke hisaab se budget.** Traces aapko har step ka timing dete hain. Jab total target miss kare, budget dikhata hai ki kaunse step par hamla karna hai: slow reranker, bahut zyada chunks, jahan chhota model kaafi hota wahan bada model, ya cold start.

**AI-specific factors.** Output length generation time par haavi hoti hai, isliye chhote answers tez hote hain. Time to first token prompt length par depend karta hai, isliye context trim karo. Provider latency ghante aur region ke hisaab se badalti hai. Tokens per minute par rate limits throughput ko cap karti hain chaahe aap kitne bhi servers chalao; bade launch se pehle unhe check karo aur provider se jaldi zyada limits maango.

**Test design karna.** Real behaviour model karo: question types ka mix, messages ke beech think time, typical prompt aur answer lengths, aur expected peak (maan lo, shaam 7 baje 300 concurrent users). Locust (Python) ya k6 jaise tools use karo. Kam se expected peak se aage tak ramp karo, hold karo, aur p95, error rate, CPU, memory, database connections aur provider 429 responses dekho.

**Tests mein model costs.** Real models ke khilaaf load tests mein asli paisa lagta hai aur rate limits khatam hoti hain. Zyadatar rounds ek fake model server ke khilaaf chalao jo realistic delay ke baad reply karta hai, phir real provider ke khilaaf ek chhota, kaabu mein test.

**Common bottlenecks aur fixes:**

| Load mein symptom | Sambhaavit wajah | Fix |
| --- | --- | --- |
| Latency badhti hai, CPU kam | Database connections ya locks ka intezaar | Bada pool, indexes, kam queries |
| CPU 100% par | Bahut kam workers ya heavy parsing | Zyada workers, background jobs |
| 429 errors | Provider rate limit | Zyada limit, fallback model, chhote outputs |
| Sirf pehla token slow | Lambe prompts | Context trim karo, prefix cache karo |
| Poore answers slow | Lambe outputs | Answer length cap karo |
| Ek minute ke baad errors | Timeouts bahut kam set hain | Layers mein timeouts align karo |

**Fake model server banana.** Provider ke jaise hi API waali ek chhoti service likho. Woh pehle token se pehle ek realistic time wait karti hai, jo aapke traces se sample kiya gaya ho, phir ek typical token rate par ek fixed reply stream karti hai. Ek setting se app ko uski taraf point karo. Ab aap din bhar free mein load tests chala sakte ho aur provider ki apni limits ke alawa har bottleneck dhoondh sakte ho, jise ek chhota real test check karta hai.

**Result report karna.** Users ke saamne p95 ka chart, budget line, har round mein mila bottleneck aur uska fix, aur agli ceiling jo aap expect karte ho, dikhao. Clients ko ye jaanna pasand hai ki system agla kahan tootega, kyunki isse unhe pata chalta hai ki kis cheez ki planning karni hai.

**Ek fake model server.** Real API jaisi hi streaming shape, aapke traces se sample kiye gaye delays:

```python
import asyncio, json, random
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.6, 0.8, 0.9, 1.1, 1.4, 2.2]       # sampled from real traces
TOKENS_PER_S = 60
REPLY = "This is a fixed answer of realistic length used only for load testing. " * 6

@app.post("/v1/messages")
async def messages():
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for word in REPLY.split():
            yield f"data: {json.dumps({'text': word + ' '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Apne app ke model base URL ko sirf test environment mein configuration ke zariye iski taraf point karo. Requests ke ek hisse ke liye 429 errors lautane ka switch jodo, apne retries aur fallbacks test karne ke liye.

**Ek Locust test jo ramp up karta hai.**

```python
from locust import HttpUser, task, between, LoadTestShape
import random

QUESTIONS = [l.strip() for l in open("load/questions.txt")]     # real questions, masked

class Learner(HttpUser):
    wait_time = between(5, 20)                                   # think time between messages

    @task
    def ask(self):
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            for _ in r.iter_lines():
                pass                                             # read the whole stream
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")

class Ramp(LoadTestShape):
    steps = [(60, 10), (120, 50), (180, 100), (240, 200), (300, 300)]   # (end second, users)
    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10
        return None
```

`locust -f load/locustfile.py --host https://staging.example.in --csv results` ke saath chalao. CSV files har step ke liye p50, p95 aur p99 deti hain; users ke saamne p95 plot karo aur apni budget line mark karo.

**Time to first token ko apna alag measurement chahiye.** Locust ki built-in timing poori request cover karti hai. Streaming ke liye, app ke apne traces mein first-byte time bhi record karo, aur har ramp step ke liye p95 first-token time wahin se padho.

**Real model par ek kaabu mein run.** Fake server se bottlenecks theek karne ke baad, provider latency aur limits confirm karne ke liye, apni rate limits aur budget ke andar, expected peak par real model ke khilaaf ek chhota test chalao. Run ko pehle se us insaan ke saath tay kar lo jiske paas API account hai.

**Traces khol kar results padho.** Jab 100 users par p95 koodta hai, toh us minute ke sabse slow traces kholo. Jo step badha (database waits, reranker, model slots ke liye queueing) wahi bottleneck hai, aur upar ki fix table aam taur par ilaaj bata deti hai.

**Apne browser mein try karo.** Timings ki list se percentiles. Average slow tail ko chhupa deta hai.

```python
import random, statistics

random.seed(6)
timings = [random.gauss(1.2, 0.2) for _ in range(950)] + [random.uniform(4, 9) for _ in range(50)]
timings.sort()
p = lambda q: timings[int(q * (len(timings) - 1))]
print(f"average {statistics.mean(timings):.2f} s")
print(f"p50 {p(0.5):.2f} s, p95 {p(0.95):.2f} s, p99 {p(0.99):.2f} s")
```

## Ek example se samjho

Jaipur ka ek intercity bus operator bus bookings aur complaints ke liye ek AI assistant launch kar raha hai, jo festival travel ke dauraan 500 concurrent users par peak hone ki ummeed hai.

Budget: pehla token p95 par 2 s se kam, poora answer p95 par 10 s se kam, errors 1% se kam.

Round 1, realistic delays waale fake model ke khilaaf: p95 pehla token 50 users par 1.1 s se 200 users par 6 s tak badhta hai. Traces dikhate hain ki requests database connections ke liye queue mein hain: pool size 10 hai. Use 40 karne aur route table par ek index jodne se 500 users par p95 1.3 s par aa jaata hai.

Round 2, 300 users par real model ke khilaaf 10 minute ka test: provider 429 errors lagbhag 220 users par shuru hote hain. Token-per-minute limit hi ceiling hai. Aap do hafte pehle zyada limit maangte ho, gateway ke zariye ek fallback model jodte ho, aur answer length 200 tokens par cap karte ho, jo average generation time ko ek tihaai kam bhi karta hai.

Final test 550 users par budget poora karta hai. Launch day ka peak 480 users tak pahunchta hai bina kisi incident ke, aur aapki report agla bottleneck (lagbhag 700 users par provider limits) list karti hai taaki client plan kar sake.

| Round | Finding | Fix | Result |
| --- | --- | --- | --- |
| 1, fake model | 200 users par p95 6 s; 10 ka connection pool | 40 ka pool, route-table index | 500 users par p95 1.3 s |
| 2, real model | Lagbhag 220 users se 429s | Zyada limit, fallback, 200-token cap | 550 users par budget poora |
| Launch day | Peak 480 users | Kuch nahi chahiye tha | Koi incident nahi |

## Aam galtiyaan

- **Averages report karna.** p95 aur p99 use karo.
- **Ek baar mein ek hi request test karna.** Concurrency problems (pools, locks, rate limits) sirf load mein dikhti hain.
- **Unrealistic traffic.** Bina think time ke ek jaise chhote prompts galat numbers dete hain.
- **Real-model load tests par paisa phoonkna.** Zyadatar rounds ke liye fake model use karo.
- **Provider limits bhool jaana.** Woh aksar asli ceiling hoti hain. Jaldi check karo aur badhwao.
- **Har round ke liye real model ke khilaaf load-test karna**, budget aur rate limits jala deta hai.
- **Think time nahi**, isliye kuch test users hazaaron jaise behave karte hain.
- **Stream hue answers ke liye sirf total time naapna**; first-token time bhi track karo.

## Jab poora load test ruk sakta hai

- **Kuch users waale internal tools**: das concurrent requests ke saath ek quick check kaafi hai.
- **Batch systems**, jahan per-user latency se zyada per hour throughput matter karta hai; wahi test karo.
- **Aise platforms jo aapke liye scale karte hain** achhi limits ke saath, shuruaati pilots ke liye, jab tak rate limits check ho gayi hon.

## Demo se production tak

- **Step ke hisaab se ek latency budget rakho** aur traces ko usse compare karo.
- **Launch se pehle aur bade badlaavon se pehle load-test karo**, zyadatar ek fake model server ke saath.
- **p50, p95, p99 aur errors report karo** har ramp step ke liye, mile bottleneck ke saath.
- **Traffic patterns badalne par dobara test karo**, jaise exam season ya festival sale.
- **Production mein p95 first-token time par alert lagao.**
