## Ye kya hai

**Latency budget** wo sabse dheema response hai jo aap ek tay percentile par maante ho, aur jise request ke har step ke ek target mein baanta jaata hai. Jaise ek chat assistant ke liye: p95 time to first token 2 seconds ke andar, p95 full answer 10 seconds ke andar, errors 1% se kam. Phir first-token budget aise bant-ta hai: auth 50 ms, query rewrite 300 ms, retrieval aur reranking 400 ms, model first token 700 ms, aur network aur queueing ke liye 550 ms ki slack.

**Load testing** system par realistic traffic bhejta hai, step by step badhaate hue, aur response times, errors aur resource use record karta hai. Ye bataata hai ki kis load par system toot-ta hai, aur sabse pehle kya toot-ta hai, aapke users ko pata chalne se pehle.

```flow
dir: LR
title: Latency budget: p95 first token 2 s mein
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

Teen shabd jo aapko chahiye honge. **p95** wo time hai jisse 95% requests jaldi poori hoti hain. **Time to first token** wo intezaar hai jab tak answer ka pehla shabd nahi dikhta. **Concurrent users** ka matlab hai ek hi pal mein chat session mein maujood log; unmein se zyaadatar padh rahe hote hain ya type kar rahe hote hain, isliye ek saath in flight requests bahut kam hoti hain.

Ye lesson Jaipur ke ek intercity bus operator ko follow karta hai, jo festival-season traffic ke liye apna booking assistant taiyaar kar raha hai.

## Ye kaise kaam karta hai

### Averages nahi, percentiles

1.5 seconds ka average, 5% users ke 4 se 9 seconds intezaar ko chhupa sakta hai. Median (p50), p95 aur p99 track karo. Tail jitni dikhti hai usse zyaada maayne rakhti hai: ek session mein 20 messages bhejne waale user ko kam se kam ek reply p99 se dheema milne ka kareeb 18% chance hai (1 minus 0.99 ki power 20).

Experts ke do rules:

- **Percentiles judte nahi.** Total ka p95, har step ke p95 ka jod nahi hota. Dheeme steps ek hi request mein kam hi ek saath hote hain, isliye jod aam taur par total ko zyaada bataata hai; lekin jab ek hi wajah, jaise busy database, har step ko ek saath dheema kar de, to wo saath-saath chalte hain. Step numbers ko us step ke apne p95 ka target maano, aur end-to-end p95 seedhe traces se padho.
- **Percentiles ka average nahi nikalta.** Maan lo teen servers ka p95 1.2 seconds hai aur ek ka, jiska median 3.5 seconds hai, 6 seconds hai, aur har ek traffic ka ek chauthaai leta hai. Chaaron p95 ka average 2.4 seconds hai. Lekin dheeme server ki aadhi requests 3.5 seconds se zyaada leti hain, jo saari requests ka 12.5% hai, isliye asli p95 3.5 seconds se upar hai. Percentiles saari raw timings se, ya merge kiye hue histograms se nikaalo.

```python
import random

random.seed(7)
def p95(xs):
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]

# Four steps, each with its own spread of times in seconds
auth     = [random.lognormvariate(-3.5, 0.3) for _ in range(10_000)]
retrieve = [random.lognormvariate(-1.3, 0.4) for _ in range(10_000)]
rerank   = [random.lognormvariate(-1.8, 0.5) for _ in range(10_000)]
model    = [random.lognormvariate(-0.5, 0.35) for _ in range(10_000)]
total = [a + b + c + d for a, b, c, d in zip(auth, retrieve, rerank, model)]

print(f"sum of the step p95s: {p95(auth) + p95(retrieve) + p95(rerank) + p95(model):.2f} s")
print(f"p95 of the total:     {p95(total):.2f} s")
```

Ye jod ke liye 2.03 seconds aur asli total ke liye 1.67 seconds print karta hai, kyunki yahaan steps independent hain.

### AI requests ko dheema kya karta hai

**Generation time** mote taur par output tokens guna har token ka time hai. 60 tokens per second par, 450-token answer ko stream hone mein 7.5 seconds lagte hain aur 200-token answer ko kareeb 3.3 seconds. Answer ki lambaai cap karna aksar aapke paas sabse sasta speed-up hota hai.

**Time to first token** prompt ki lambaai ke saath, aapke apne system mein aur provider ke paas queueing ke saath, aur us ghante provider ke load ke saath badhta hai. Context trim karo aur jahaan provider support kare wahaan cached prompt prefix reuse karo. Reasoning models kuch bhi dikhaane se pehle soch sakte hain, isliye wo pehla token naapo jo user ko sach mein dikhta hai.

**Rate limits** tokens ya requests per minute par hoti hain, aur aap kitne bhi servers chalao, calls ko 429 (Too Many Requests) ke saath reject kar deti hain. Dekho ki aapka provider input aur output tokens kaise ginta hai, peak par kitna chahiye iska hisaab lagao, aur hafton pehle oonchi limit maango.

### Little's law se sizing

**Little's law**: requests in flight = arrival rate x har request ka system mein bitaaya time. Maan lo pilot ke logs dikhaate hain ki har active user minute mein kareeb 2 messages bhejta hai. 500 users par ye kareeb 17 requests per second hai. Agar har ek 4.5 seconds leti hai, to kisi bhi pal kareeb 75 answers stream ho rahe hote hain. 500 nahi, yahi number aapke connection pools, worker counts aur kisi bhi concurrency cap ka size tay karta hai.

### Test design karna

Asli behaviour ko model karo: asli sawaal (masked), aam prompt aur answer lambaai, messages ke beech think time, aur expected peak. Kam se shuru karke peak se aage tak ramp karo aur **har step ko hold karo** kuch minuton ke liye, taaki percentiles settle ho jaayein. p95 aur p99, status code ke hisaab se errors, CPU, memory, database connections, queue ki lambaai aur provider ke 429s dekho.

**Closed aur open tests.** **Closed** test mein, jaise think time waale Locust users, har simulated user reply aane tak rukkar phir bhejta hai. System dheema hone par test kam bhejta hai, aur dheeme daur mein jitne measurements aane chahiye usse kam aate hain. Ise **coordinated omission** kehte hain: test chupchaap theek usi waqt peechhe hat jaata hai jab asli users nahi hat-te. **Open** test mein requests ek tay rate par aati hain, chaahe kuch bhi ho, jaise sale khulte hi travellers toot padte hain. k6 ye apne constant-arrival-rate aur ramping-arrival-rate executors se deta hai. Bottlenecks ko step by step dhoondhne ke liye closed ramp use karo, phir queue dekhne ke liye expected arrival rate par burst ke saath ek open test chalaao.

**Soak test.** Expected peak ko 30 se 60 minute tak hold karo. Memory, connections ya file handles ke leaks waqt ke saath hi dikhte hain.

### Ek fake model server

Real-model load tests mein paise lagte hain aur rate limits khatam hoti hain. Zyaadatar rounds ek chhoti fake service par chalaao, jiska streaming shape provider ki API jaisa hi ho aur first-token delays aapke traces se sample kiye gaye hon:

```python
import asyncio, json, os, random
from fastapi import FastAPI
from fastapi.responses import JSONResponse, StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.30, 0.35, 0.35, 0.35, 0.40, 0.40, 0.40, 0.45, 0.45, 0.45, 0.45, 0.50, 0.50,
                 0.50, 0.50, 0.55, 0.55, 0.55, 0.60, 0.60, 0.60, 0.65, 0.70, 0.70, 1.40]
TOKENS_PER_S = 60
REPLY_TOKENS = 450                                    # today's typical answer length
SHARE_429 = float(os.getenv("FAKE_429_SHARE", "0"))   # for example 0.05

@app.post("/v1/messages")
async def messages():
    if random.random() < SHARE_429:
        return JSONResponse({"error": "rate_limited"}, status_code=429,
                            headers={"retry-after": "2"})
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for i in range(REPLY_TOKENS):
            yield f"data: {json.dumps({'text': f'tok{i} '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Ye delays model ka p95 0.7 seconds dete hain, jo budget mein model ka hissa hai, aur 25 mein se ek reply dheema. Ise `uvicorn fake_model:app` se chalaao, aur sirf test environment mein configuration ke zariye apne app ka model base URL is par point karo. Apne retries aur fallback test karne ke liye `FAKE_429_SHARE` set karo.

### Stream ko time karne waala Locust ramp

`stream=True` ke saath, request ke liye Locust ki apni row response headers aate hi apni ghadi rok deti hai, aksar kuch milliseconds mein, first token se bahut pehle. Isliye ye test apni do timings khud record karta hai:

```python
import random, time
from locust import HttpUser, LoadTestShape, between, task

QUESTIONS = [q.strip() for q in open("load/questions.txt", encoding="utf-8") if q.strip()]

class Traveller(HttpUser):
    wait_time = between(20, 30)          # think time between messages

    @task
    def ask(self):
        start, first = time.perf_counter(), None
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
                return
            for line in r.iter_lines():               # read the whole stream
                if line and first is None:
                    first = time.perf_counter()
        end = time.perf_counter()
        if first is not None:
            self.record("first token", first - start)
        self.record("full answer", end - start)

    def record(self, name, seconds):
        self.environment.events.request.fire(
            request_type="STREAM", name=name, response_time=seconds * 1000,
            response_length=0, exception=None, context={})

class Ramp(LoadTestShape):
    # (end second, users): hold each step for two minutes
    steps = [(120, 50), (240, 100), (360, 200), (480, 300), (600, 400), (720, 500), (840, 550)]

    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10                      # add up to 10 users a second
        return None
```

Ise `locust -f load/locustfile.py --headless --host https://staging.example.in --csv results --csv-full-history` se chalaao. Phir `results_stats_history.csv` file mein har name ke liye har second ek row aati hai, jismein user count aur pichhle kareeb 10 seconds ke percentiles hote hain. `first token` aur `full answer` rows padho, aur har hold ke aakhri minute mein 95% column ka median lo, kyunki low load par 10-second window mein kam requests hoti hain. Traces se per-step p95 bhi chalta hai. Built-in POST row (sirf headers) aur Aggregated row ko ignore karo, jo teenon timings ko mila deti hai.

### Overload, retries aur streaming

- **Retry storms.** Agar har 429 ya timeout ko turant, teen baar tak retry kiya jaaye, to mushkil mein pade system par chaar guna tak traffic aa sakta hai. Exponential backoff aur random jitter ke saath retry karo, provider `retry-after` header bheje to use maano, aur retries ko traffic ke chhote hisse par cap karo.
- **Admission control.** Har instance ek saath jitne streams serve karta hai, unhein cap karo. Extra requests ko ek chhoti queue mein, zyaada se zyaada kuch seconds, rukne do, phir vinamrata se "Abhi hum busy hain, kripya ek minute baad try karein" dikhaao. Sabka timeout hone se achha hai kuch logon ko lauta dena.
- **Autoscaling aur cold starts.** Naye instances ko start aur warm up hone mein minute lag sakte hain. Pehle se pata peak ke liye, uske shuru hone se pehle scale up karo.
- **Proxies se streaming.** Koi proxy ya load balancer response ko buffer kar sakta hai, jisse tokens ek hi dher mein aate hain, ya idle samajhkar connection band kar sakta hai. Streaming route par buffering aur idle-timeout settings check karo.

| Load mein lakshan | Sambhaavit wajah | Fix |
| --- | --- | --- |
| Latency badhti hai, CPU low | Database connections ya locks ka intezaar | Bada pool, indexes, caching, kam queries |
| CPU 100% par | Bahut kam workers ya bhaari parsing | Zyaada workers, kaam background jobs mein bhejo |
| 429 errors | Provider rate limit | Oonchi limit, fallback model, chhote outputs |
| Errors shuru hote hi traffic uchhalta hai | Turant retries | Jitter ke saath backoff, retry cap |
| Queue sirf bursts mein badhti hai | Arrival rate ke liye bahut kam streams | Concurrency cap, busy message, jaldi scale up |
| Sirf first token dheema | Lambe prompts ya provider queueing | Context trim karo, prefix cache karo |
| Tokens ek dher mein aate hain | Koi proxy stream ko buffer kar raha hai | Us route par buffering band karo |
| Theek ek minute baad errors | Kisi layer mein timeout ya idle limit | Har layer mein timeouts align karo |

### Traces kholkar results padho

Jab kisi step par p95 uchhle, to us minute ke sabse dheeme traces kholo. Jo step badha (database waits, reranker, model slot ke liye queueing) wahi bottleneck hai, aur upar ki table aam taur par fix bata deti hai. Phir wahi test dobaara chalaao, taaki barabar ki cheezon ki tulna ho.

## Ek worked example

Jaipur ka bus operator festival travel ke dauraan ek saath chat kar rahe kareeb 500 travellers ki ummeed karta hai, aur subah 10 baje ek seat sale khulti hai. Budget: p95 first token 2 seconds se kam, p95 full answer 10 seconds se kam, errors 1% se kam. Neeche ke saare numbers illustrative hain.

**Round 1: closed ramp, fake model.** p95 first token 50 users par 1.1 seconds se 200 par 6 seconds tak chadhta hai. CPU 25% par rehta hai. Sabse dheeme traces sab database connection ka intezaar kar rahe hain: pool mein 10 hi hain. 40 ka pool aur route table par ek index ise theek kar dete hain.

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| p95 first token, pool 10 | 1.1 s | 2.4 s | 6.0 s | roka: timeouts | nahi chalaaya | nahi chalaaya |
| p95 first token, pool 40 + index | 1.1 s | 1.1 s | 1.2 s | 1.2 s | 1.3 s | 1.4 s |

**Round 2: real model par ek chhota run.** Das minute, 300 users tak ramp, API account ke owner se pehle hi tay karke. Kareeb 220 users par 429 errors shuru hote hain. Mota hisaab bhi yahi kehta hai: pilot ke logs dikhaate hain ki har user minute mein kareeb 2,000 tokens (1,550 in, 450 out) ke kareeb 2 messages bhejta hai, yaani har user ke 4,000 tokens per minute, aur account ke 900,000 tokens per minute 225 users par khatam ho jaate hain. Team answers ko 200 tokens par cap karti hai, jisse streaming time 7.5 se kareeb 3.3 seconds aur har message ke tokens 1,750 ho jaate hain. Wo oonchi limit maangte hain; das din baad provider 2.5 million tokens per minute de deta hai. Wo apne gateway se ek fallback model aur retries par jitter ke saath backoff bhi jodte hain.

**Round 3: open burst test, fake model** (ab 200-token replies par set). Little's law: 500 users par, kareeb 17 requests per second, har ek kareeb 4.5 seconds ki, yaani kareeb 75 streams in flight. Sale khulte hi arrivals kareeb 25 per second tak uchhalte hain, yaani kareeb 113 in flight. Do instances, har ek 48 streams par capped, 96 hi sambhaalte hain. Burst mein p95 first token 9 seconds tak pahunchta hai aur 6% requests timeout ho jaati hain. Closed ramp ne ye kabhi nahi dikhaaya, kyunki uske users bas intezaar karte rahe. Fix: subah 9:45 baje start kiya gaya teesra instance, aur 3-second queue aur busy message waala admission control. Re-run par p95 first token 1.5 seconds par rehta hai aur kisi ko lautaaya nahi jaata.

**Round 4: confirm.** Real model par 550 users ke saath das minute: p95 first token 1.6 seconds, p95 full answer 5.2 seconds, errors 0.3%. Ye load 1.9 million tokens per minute use karta hai, limit ka 77%. Fake model par 500 users ke saath 45 minute ka soak flat memory dikhaata hai aur koi connection leak nahi.

**Launch day.** Peak 480 travellers tak pahunchta hai. Subah 10 baje ke burst mein demand thodi der ke liye kareeb 2.6 million tokens per minute maangti hai, limit se 5% zyaada, aur gateway do minute ke liye kuch percent requests fallback model par bhejta hai. p95 first token 2 seconds se neeche rehta hai.

**Report** mein budget line ke saath users ke muqaable p95 ka chart hai, har mila bottleneck aur uska fix, aur agli ceiling: kareeb 700 steady users (2.5 million bhaag 3,500 tokens per user per minute), aur bursts mein usse pehle.

## Aam galtiyaan

- **Averages report karna.** First token aur full answer ke liye p50, p95 aur p99 report karo.
- **Percentiles jodna ya unka average nikaalna.** Dono kaam nahi karte; raw timings se nikaalo.
- **Ek baar mein ek hi request test karna.** Pools, locks aur rate limits sirf concurrency mein fail hote hain.
- **Unrealistic traffic.** Ek jaise chhote prompts aur bina think time ke numbers ka koi matlab nahi.
- **Sirf closed tests.** System dheema hone par wo peechhe hat jaate hain, isliye asli rush se banne waali queue chhupa dete hain.
- **Streams ke liye Locust ki request row par bharosa.** Streaming on hone par wo sirf headers ko time karti hai.
- **Real-model load tests par paise phoonkna.** Zyaadatar rounds ke liye fake model use karo aur ek chhota real run.
- **Provider limits bhool jaana.** Aksar asli ceiling wahi hoti hain. Token ka hisaab lagao aur jaldi maango.
- **Turant retries.** Ye theek usi waqt load kai guna kar dete hain jab system mushkil mein hota hai.

## Kab poora load test ruk sakta hai

- **Gine-chune users waale internal tools**: das concurrent requests ke saath ek quick check kaafi hai.
- **Batch systems**, jahaan per-user latency se zyaada per hour throughput maayne rakhta hai; wahi test karo.
- **Aise platforms par early pilots jo aapke liye scale karte hain**, basharte aapne rate limits aur timeouts check kar liye hon.

## Demo se production tak

- **Step ke hisaab se latency budget rakho** aur har release mein traces ko usse compare karo.
- **Launch se pehle aur bade badlaavon se pehle load-test karo**, zyaadatar fake model server ke saath.
- **Har ramp step ke liye p50, p95, p99 aur errors report karo**, mile bottleneck ke saath.
- **Traffic patterns badlein to dobaara test karo**, jaise exam season, festival sale ya lambe answers waala naya feature.
- **Production mein p95 first-token time aur 429 rate par alert lagaao**, aur tokens-per-minute headroom par nazar rakho.

## Practice

Monitoring par Google SRE ka chapter aur Locust ki first-test guide padho.

1. Das real requests ke traces se apne app ke liye step ke hisaab se latency budget likho. End-to-end p95 alag se check karo.
2. Upar waala fake model server chalaao aur apne app ko us par point karo.
3. Locust ramp ko 50 se 550 users tak chalaao. Har hold par first token aur full answer ke p50, p95 aur p99 record karo, aur note karo ki p95 pehli baar aapka budget kahaan paar karta hai.
4. Pehla bottleneck dhoondhkar theek karo, dobaara chalaao, phir Little's law se apne peak par aur us rate ke 1.5 guna burst par requests in flight ka andaaza lagaao.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly) ka chapter 9, jo inference optimisation par hai, time to first token aur time per output token ko cover karta hai.

**Aapka kaam poora hai jab aap** apni budget line ke saath users ke muqaable p95 ka chart dikha sako, pehla bottleneck aur use hataane waala badlaav bata sako, aur bata sako ki aapke peak par kitni requests in flight hain.
