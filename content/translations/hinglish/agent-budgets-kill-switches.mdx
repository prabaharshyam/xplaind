## Ye kya hai

Agents khud tay karte hain ki kitne steps lene hain. Kabhi-kabhi ye gadbada jaata hai: koi tool fail hota rehta hai aur agent retry karta rehta hai, do agents kaam ek-doosre ko aage-peechhe karte rehte hain, ya agent kisi draft ko "improve" karta hi rehta hai. Limits ke bina, loop tokens jalaata hai, downstream systems par bojh daalta hai aur asli actions dohraata hai.

Teen controls ise rokte hain:

- **Loop limits**: har task ke liye, aur sub-agents hon toh har run ke liye, steps ya tool calls ki adhiktam sankhya.
- **Budgets**: har task, har user, aur poore feature ke liye har din, tokens, time aur paise par caps.
- **Kill switches**: operator ke liye bina deploy ke kisi tool, agent ya poore feature ko rokne ka tez aur bharosemand tareeka.

Repetition checks, circuit breakers, rate aur concurrency limits aur idempotency keys inka saath dete hain.

```flow
title: Har limit kahaan check hoti hai
Har task | 15 steps, 60,000 tokens, 90 s tak -> Shared store | Postgres ya Redis
Har model call | estimate reserve karo, phir settle -> Shared store
Har tool call | kill switch, circuit breaker, idempotency key -> Shared store
Har din | har student ke liye ₹15, feature ke liye ₹8,000 -> Shared store
Shared store -> Provider spend limit | aakhri backstop
```

Ye lesson ek illustrative case ke saath chalta hai: Bengaluru ki ek edtech company ka homework-help agent, jisne ek raat mein apne weekly budget ka das guna kharch kar diya.

## Ye kaam kaise karta hai

### Per-task limits

Loop mein steps, tool calls, tokens aur beeta samay gino. Har cap ek hafte ke real runs se chuno: 95th percentile ka lagbhag dugna. Agar 95% tasks 12 steps aur ₹2 mein khatam hote hain, toh 25 steps aur ₹5 ka cap aam kaam ko kaate bina runaways ko rok dega. Model ya prompt badlo toh numbers dobaara dekho.

Limit par pahunchne par saaf tareeke se ruko: state save karo, user ko aasaan shabdon mein batao ki kya ho gaya aur iski jagah wo kya kar sakte hain, aur ise investigate karne waale failure ki tarah log karo. Ruka hua task kabhi crash jaisa nahi dikhna chahiye.

### Repetition checks aur circuit breakers

**Repetition check** ek task ke andar kaam karta hai. Agar ek hi tool ek hi arguments ke saath teen baar call ho, ya ek hi error lagaataar teen baar laute, toh task jaldi khatam kar do.

**Circuit breaker** sabhi tasks mein kaam karta hai. Har tool ke failures shared store mein gino. Maan lo, sabhi users mein milaakar koi tool ek minute mein 20 baar fail hota hai, toh circuit "open" kar do: agle paanch minute tak us tool ki har call, tool tak pahunche bina, ek saaf message ke saath turant fail hogi. Phir ek trial call jaane do; agar wo chal jaaye, toh circuit close kar do. Repetition check ek task ko loop karne se rokta hai. Circuit breaker hazaar tasks ko thoda-thoda loop karne se rokta hai, aur raat bhar ka bada bill aam taur par isi tarah banta hai.

### Sub-agents mein run-level caps

Jab koi planner sub-agents ko kaam deta hai, toh har ek apne 15-step cap ka paalan kar sakta hai, jabki poora run saikdon steps le leta hai. Har run ko ek root `run_id` do, use har sub-agent ko pass karo, aur shared store mein usi id ke against steps gino. Total par cap lagao (jaise har run ke liye 40 steps) aur hand-offs ki sankhya par bhi (jaise 4).

### Har user aur har din ke budgets

Har user ka har din ka kharch gino aur cap paar hone par vinamrata se mana kar do. Poore feature ka bhi har din ka kharch gino, 50% aur 80% par aise alerts ke saath jo top users aur task types ki list dein, taaki cap sabko roke usse pehle koi kadam uthaaye. Asia/Kolkata ke din use karo, taaki limits aapke users ki aadhi raat ko reset hon.

Counts kisi shared store mein rehne chahiye, jaise database ya Redis: memory mein ginne waale chhah servers cap ka chhah guna hone dete hain. Par sirf shared store kaafi nahi hai. Swaabhaavik code "check, call, record" hota hai:

1. Aaj ka total padho. Wo ₹14 hai aur cap ₹15 hai, toh ₹1 ki call allowed hai.
2. Model ko call karo.
3. Real cost total mein jodo.

Ek hi user ki bees requests, kisi ke step 3 tak pahunchne se pehle hi, sabhi step 1 kar sakti hain, toh beeson pass hokar kharch kar deti hain. Step 3 ko atomic banaane se madad nahi milti: race check aur kharch ke beech ke gap mein hai. Is bug ko **check-then-act** kehte hain.

Iska fix hai **reserve, then settle**. Call se pehle, ek aise conditional statement mein total mein upper-bound estimate jodo jo tabhi succeed ho jab naya total cap ke andar rahe. Call ke baad, estimate ko real cost se badal do. Har chal rahi call pehle se gini hui hai, toh koi bhi check puraana total nahi dekhta.

### Code mein race-safe budget

Ye version SQLite use karta hai, taaki laptop par chal jaaye. SQLite file sirf ek machine ke processes mein shared hoti hai; kai servers hon toh yahi pattern Postgres ya Redis par use karo.

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from datetime import datetime
from zoneinfo import ZoneInfo

# Adds the estimate only if the new total stays within the cap; else returns no row.
RESERVE = """INSERT INTO spend (scope, day, paise) VALUES (?, ?, ?)
  ON CONFLICT (scope, day) DO UPDATE SET paise = spend.paise + excluded.paise
  WHERE spend.paise + excluded.paise <= ?
  RETURNING paise"""

@dataclass(frozen=True)
class Reservation:
    scopes: tuple
    day: str
    paise: int

def connect(path):
    db = sqlite3.connect(path, timeout=10, isolation_level=None)  # we run our own transactions
    db.execute("CREATE TABLE IF NOT EXISTS spend (scope TEXT, day TEXT,"
               " paise INTEGER NOT NULL, PRIMARY KEY (scope, day))")
    return db

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

@contextmanager
def write_tx(db):
    db.execute("BEGIN IMMEDIATE")           # take the write lock before reading anything
    try:
        yield
        db.execute("COMMIT")
    except BaseException:
        db.execute("ROLLBACK")
        raise

class OverBudget(Exception):
    pass

def reserve(db, caps, paise):
    """caps is {scope: cap in paise}. Reserve on every scope, or on none."""
    if paise > min(caps.values()):
        return None
    day = today()
    try:
        with write_tx(db):
            for scope, cap in sorted(caps.items()):       # same order everywhere
                if not db.execute(RESERVE, (scope, day, paise, cap)).fetchall():
                    raise OverBudget(scope)               # rolls back earlier scopes
    except OverBudget:
        return None
    return Reservation(tuple(sorted(caps)), day, paise)

def settle(db, r, actual_paise):
    """Swap the estimate for the real cost, on the day it was reserved."""
    with write_tx(db):
        for scope in r.scopes:
            db.execute("UPDATE spend SET paise = paise + ? WHERE scope = ? AND day = ?",
                       (actual_paise - r.paise, scope, r.day))
```

User aur feature ke caps ek saath dekar `reserve` call karo. Agar ye `None` lautaaye, toh vinamrata se mana kar do; varna model ko call karo, phir usage report ki cost ke saath `settle` karo.

Details maayne rakhti hain:

- **Sab ya kuch nahi.** User aur feature ke counters ek hi transaction mein badalte hain, toh feature cap se mana hone par user par charge nahi reh jaata.
- **Paisa poore paise mein.** Integers theek-theek judte hain; floating-point rupees drift hote hain.
- **Reservation apna din yaad rakhta hai.** Raat 11:59 par shuru hui call usi din ke against settle hoti hai jis din reserve hui thi, agle din ke against nahi.
- **Failures safe side par girte hain.** Agar `settle` se pehle server crash ho jaaye, toh estimate gina hua rehta hai; koi zyada kharch nahi karta. Agar call provider tak pahunchi hi nahi, toh 0 se settle karo. Agar pata na chale ki kitna bill hua, toh reservation rehne do.
- **Yahi shape doosri jagah bhi chalta hai.** Postgres `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING` support karta hai; conflict waali row lock ho jaati hai, toh doosri request intezaar karti hai aur phir naya total dekhti hai. Deadlocks se bachne ke liye scopes ko ek fixed order mein lock karo (`sorted` call). Redis mein read, compare aur `INCRBY` ko ek Lua script mein rakho, jise Redis atomic tareeke se chalaata hai.
- **Feature row ek hot spot hai.** Har request use thodi der lock karti hai. Bahut zyada traffic par use kai rows mein baant do ya Redis use karo.

### Call se pehle cost ka estimate

Cap tabhi tikta hai jab reservation upper bound ho. Input tokens gino (apne provider ke token counter se, ya zyada andaaza lagaakar) aur maan lo ki model poore `max_tokens` likhega:

```python
def estimate_paise(input_tokens, max_tokens, in_paise_per_m, out_paise_per_m):
    """Upper bound: every input token, plus the most output max_tokens allows."""
    cost = input_tokens * in_paise_per_m + max_tokens * out_paise_per_m
    return -(-cost // 1_000_000)                     # round up to whole paise
```

Maan lo, ek model ki keemat ₹25 prati million input tokens aur ₹125 prati million output tokens hai (ye banaaye hue numbers hain; apne provider ka price page use karo aur jis taareekh ko check kiya wo record karo). 3,000-token prompt, `max_tokens` 1,000 ke saath, `estimate_paise(3000, 1000, 2500, 12500)` reserve karta hai, jo 20 paise hai. Zyaadatar calls jaldi khatam ho jaati hain aur `settle` baaki lauta deta hai.

Do gotchas. Check karo ki `max_tokens` us sab par seema lagaata hai jise aapka provider output ke roop mein bill karta hai, reasoning tokens samet agar hon. Aur agar aap stream karte ho, toh output aate-aate gin sakte ho aur run budget ya kill switch ke rukne ko kehne par stream band kar sakte ho; jab tak pata na ho ki aapka provider cancel hui stream ko kaise bill karta hai, poora reservation rakho.

### Concurrent test se saabit karna

Race sirf asli concurrency mein dikhta hai. Yahaan bees workers, har ek apne connection ke saath, jaise alag-alag servers, ek user ke liye ek saath 100 calls karte hain:

```python
import time
from concurrent.futures import ThreadPoolExecutor

CAPS = {"user:u42": 1500, "feature:homework": 800_000}   # ₹15 and ₹8,000

def one_call(db):
    r = reserve(db, CAPS, 200)          # estimate: ₹2
    if r is None:
        return 0
    time.sleep(0.01)                    # stands in for the model call
    settle(db, r, 150)                  # real cost: ₹1.50
    return 150

def test_cap_holds_under_concurrency(tmp_path):
    path = tmp_path / "budgets.db"
    connect(path).close()
    def server(_):
        db = connect(path)
        return sum(one_call(db) for _ in range(5))
    with ThreadPoolExecutor(max_workers=20) as pool:
        spent = sum(pool.map(server, range(20)))
    total = connect(path).execute(
        "SELECT paise FROM spend WHERE scope = 'user:u42' AND day = ?", (today(),)).fetchone()[0]
    assert 0 < spent == total <= 1500
```

Hamare runs mein ye har baar pass hua, ₹13.50 kharch ke saath. Check-then-spend version ne usi test mein ₹15 ke cap ke against ₹42 tak jaane diya. Ye test CI mein rakho taaki koi reservation ko "simplify" karke hata na de.

### Rate aur concurrency limits

Do aur limits aapke paise ki nahi, aapke systems ki raksha karti hain:

- **Rate limits** har minute ki requests par cap lagaati hain. Ek aam algorithm hai **token bucket**: har user ke bucket mein zyada se zyada, maan lo, 10 tokens hote hain aur har chhah seconds mein ek refill hota hai. Har request ek token leti hai; khaali bucket ka matlab hai "dheere chalo". Chhote bursts nikal jaate hain, par average das prati minute par rehta hai.
- **Concurrency limits** ek saath chal rahe tasks par cap lagaati hain, jaise har user ke liye 2. Tab "try again" das baar dabaane se das nahi, do tasks chalte hain. Ek "running" counter par reserve pattern use karo, use `finally` block mein release karo, aur har slot ko ek expiry do, kyunki crash hua server apna `finally` kabhi nahi chalaata.

### Kill switches

Kill switch ek flag hai jise aapka code har step aur har tool call se pehle check karta hai, levels ke saath: ek tool disable karna (saare refunds rokna), agent disable karna (human queue ya simple form par fall back karna), ya feature disable karna. Ise bina redeploy ke admin screen ya config service se flip karo. Flags ko shared store se short cache ke saath padho, taaki badlaav kuch seconds mein har jagah laagu ho jaaye:

```python
import json, logging, time

log = logging.getLogger("agent")
WRITE_TOOLS = {"send_email", "issue_refund", "message_driver"}
MAX_STALE = 60                                           # seconds
_cache = {"read_at": float("-inf"), "ok_at": float("-inf"), "flags": {}}

def flags():
    now = time.monotonic()
    if now - _cache["read_at"] > 5:                      # refresh every 5 seconds
        _cache["read_at"] = now
        try:
            _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
            _cache["ok_at"] = now
        except Exception:
            log.warning("flag store unreachable; using last flags")
    if now - _cache["ok_at"] > MAX_STALE:                # no good read for a minute
        return {**_cache["flags"], "write_tools_off": True}
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    if tool and f.get(f"tool_{tool}_off"):
        return False
    return not (tool in WRITE_TOOLS and f.get("write_tools_off"))
```

`config_store` koi bhi shared store ho sakta hai jo aapke paas hai: database row, Redis ya feature-flag service. Ye code ek seemit tareeke se safe fail hota hai. Chhota outage kuch nahi badalta. Ek minute tak koi achha read na mile, ya start-up par pehla read fail ho, toh emails aur refunds jaise write tools band ho jaate hain jabki read-only tools chalte rehte hain. Puraane flags hamesha rakhne ka matlab hoga ki outage ke dauraan flip hua switch kabhi pahunchega hi nahi.

### Actions ke liye idempotency

Har real-world action ko us cheez se bani key do jo use unique banaati hai (jaise order id aur refund reason). Lene waala system usi key waale doosre action ko mana kar deta hai, toh loops aur retries payments ya messages dohra nahi sakte.

### Kill switch ki drill karo

Mahine mein ek baar, pehle staging mein aur phir production mein kisi shaant ghante mein, har switch flip karo aur check karo ki tasks kuch seconds mein rukte hain, users ko saaf message dikhta hai, aur baaki app chalta rehta hai. Samay naapo aur record karo ki kisne kiya. Jo teams kabhi practice nahi kartin, wo asli incident mein seekhti hain ki switch sirf start-up par padha jaata tha, ya on call par kisi ko nahi pata tha ki wo kahaan hai.

## Ek worked example

Homework-help agent ek mahine theek chala, lagbhag ₹18,000 prati hafte ke model kharch par. Phir ek Ravivaar raat, ek maths tool mein hue badlaav se wo ek tarah ke sawaal par error lautaane laga. Agent chhote-chhote badlaavon ke saath retry karta raha, aur students "try again" dabaate rahe. Somvaar subah tak feature ₹1.8 lakh kharch kar chuka tha, ek aam hafte ka das guna.

Team ne ek mahine ke runs nikaale aur unse limits tay kin:

- **Per task.** 95% tasks 7 steps, 25,000 tokens aur 40 seconds mein khatam hue, toh caps hain 15 steps, 60,000 tokens aur 90 seconds. Teen ek jaise tool errors par task is message ke saath khatam hota hai: "Main ye sawaal hal nahi kar paaya; aapke teacher madad kar sakte hain."
- **Per student.** 95% students ne din mein ₹6 se kam kharch kiya, toh cap ₹15 hai, jo ek friendly "kal phir aana" ke roop mein dikhta hai. Har student ek saath 2 tasks chala sakta hai.
- **Har din feature.** ₹18,000 prati hafta yaani lagbhag ₹2,600 prati din, aur sabse busy aam din lagbhag ₹4,000 ka tha. Cap ₹8,000 hai, ek average din ka lagbhag teen guna aur sabse busy din ka dugna. 50% (₹4,000) aur 80% (₹6,400) par on-call engineer ke phone par alerts jaate hain.
- **Circuit breaker** maths tool par: ek minute mein 20 failures hone par wo paanch minute ke liye pause ho jaata hai.
- **Kill switch.** Har tool ke liye aur agent ke liye ek admin toggle. Agent band karne par "homework help aaraam kar raha hai" banner dikhta hai; baaki app chalta rehta hai.
- **Provider.** Backstop ke roop mein ek hard monthly spend limit.

Us Ravivaar raat har control kya karta:

| Control | Incident par asar |
| --- | --- |
| Circuit breaker | Fault ke ek minute ke andar, har student ke liye maths tool pause kar deta |
| Repetition check | Loop kar rahe har task ko teen errors ke baad khatam kar deta |
| Per-student cap aur 2 running tasks | "Try again" ko nuksaan kai guna karne se rokta |
| ₹8,000 ka feature cap | Koi bhi din ₹8,000 se zyada ka nahi ho sakta, jabki us raat ₹1.8 lakh lage |
| ₹4,000 par alert | Maamla sasta rehte hi kisi ko jaga deta |

Do hafte baad, aise hi ek tool fault ne ek minute ke andar circuit breaker trip kar diya. Bill kuch sau rupees ka raha, aur kisi student ke shikaayat karne se pehle hi alert team tak pahunch gaya.

## Aam galtiyan

- **Step cap na hona.** Ye akeli sabse sasti suraksha hai; ise sabse pehle jodo.
- **Memory mein rakhe budgets.** Har server alag ginta hai aur asli total cap se bahut aage nikal jaata hai. Shared store use karo.
- **Check-then-act budgets.** Total padhne, model call karne aur phir cost jodne se ek saath aayi saari requests ek hi check pass kar leti hain. Pehle reserve karo, ek statement mein.
- **Aise estimates jo upper bound nahi hain.** Average cost reserve karoge toh cap leak hoga. Poore `max_tokens` ke liye reserve karo.
- **Concurrent tasks par cap na hona.** Das parallel tasks mein se har ek per-task cap pass kar leta hai.
- **Sirf per-agent caps.** Kaam aage-peechhe karne waale sub-agents ko har root run ke liye ek count chahiye.
- **Aisa kill switch jiske liye deploy chahiye.** Incident mein aapko seconds chahiye, build pipeline nahi.
- **Sirf start-up par padha jaane waala kill switch.** Wo agle restart tak kuch nahi karta.
- **Fail open hona.** Agar flag store der tak down rahe, toh write tools ko band maano.
- **Chupchaap rukna.** User ko batao ki kya hua aur log karo; ruka hua task ek bug hai jise fix karna hai.
- **Non-idempotent actions ko retry karna.** Idempotency keys use karo taaki loops payments ya messages dohra na sakein.
- **Floating-point paisa.** Paise ko integers mein gino.

## Jab saral limits kaafi hain

- **Aapki apni team ka prototype**: shaayad ek step cap aur provider ka spend alert hi kaafi ho.
- **Ek ya do model calls waale fixed workflows**, jahaan har request ki cost predictable ho.
- **Gine-chune users waale read-only internal tools.**

Per-user budgets, feature caps aur layered kill switches tab maayne rakhte hain jab baahar ke log runs shuru kar sakein ya agents actions le sakein.

## Demo se production tak

- **Shared storage mein budgets atomic tareeke se reserve karo**, har model call se pehle, aur baad mein settle karo.
- **Flags aur circuit breakers check karo**, har step aur tool call se pehle.
- **Feature budgets ke 50% aur 80% par alert karo**, sabse zyada kharch karne waalon ki list ke saath.
- **Concurrent budget test CI mein rakho.**
- **Kill switches ki drill har mahine karo** aur record karo ki har ek mein kitna samay laga.
- **Har stop ko uski wajah ke saath log karo**, aur review karo ki limits sahi set hain ya nahi.

## Practice karo

Unbounded consumption par OWASP ki entry padho.

1. Apne banaaye kisi agent mein step, token aur time caps jodo, ek saaf stop message ke saath.
2. Ek repetition check jodo jo teen ek jaise tool errors ke baad task khatam kar de, aur jaanbujhkar tode gaye tool se use trigger karo.
3. Is lesson ka reserve-and-settle budget aur kill switch jodo, aur dono ko kaam karte dikhao.
4. Apne budget code par concurrent test chalaao. Phir `reserve` ko ek saade "total padho, phir jodo" version se badlo aur test ko fail hote dekho.

**Aapka kaam poora hai jab aap** jaanbujhkar koi tool todkar dikha sako ki agent aapki limits ke andar ruk jaata hai, log entry aur alert ke saath.
