## Ye kya hai

**Software design** ka matlab hai ye tay karna ki ek program ko kin parts mein baantein aur wo parts aapas mein kaise baat karein. Zyaadatar achhe designs ke neeche do ideas hote hain:

- **Cohesion**: ek part ke andar ki cheezein aapas mein kitni kareeb se judi hain. High cohesion ka matlab hai ki har part ek kaam karta hai, aur uske andar ki har cheez usi kaam ke liye hai.
- **Coupling**: ek part doosre ki details par kitna depend karta hai. Loose coupling ka matlab hai ki aap baaki parts ko chhue bina ek part badal sakte ho.

Achha design yaani high cohesion aur loose coupling. Bura design tab mehsoos hota hai jab ek chhota badlaav phail jaata hai: email template badalne ke liye kisi tarah model ko call karne wala code bhi edit karna padta hai.

AI ke kaam mein ye zyaadatar software se bhi zyada maayne rakhta hai. Ek saal mein koi team model providers badal sakti hai, privacy-sensitive customer ke liye ek self-hosted model jod sakti hai aur vector store badal sakti hai. Agar model call bees jagah daba hua hai, to har badlaav ek risky rewrite hai. Ek chhoti boundary ke peeche ho, to har badlaav bas ek nayi file aur ek test hai.

Wahaan tak pahunchne ke liye paanch jaani-maani guidelines hain: **SOLID principles**. Robert C. Martin ne inhein object-oriented code ke liye ikattha kiya, lekin ye ideas saade Python functions aur modules par bhi kaam karte hain. Inhein ratkar sunaane ki zaroorat nahi hai. Zaroorat ye hai ki jin problems ko ye rokte hain, unhein aap asli code mein pehchaan sako.

## Ye kaise kaam karta hai

### Paanch principles, aasaan shabdon mein

| Principle | Aasaan shabdon mein | Ise todne ka ek sanket |
| --- | --- | --- |
| **S**ingle responsibility | Ek module ya class, badalne ki ek wajah | Ek file jo PDFs padhti hai, model ko call karti hai aur email bhejti hai |
| **O**pen-closed | "Open for extension, closed for modification": behaviour naya code jodkar badhao, pehle se chal rahe code ko edit karke nahi | Har naye provider ke liye business logic ke andar ek aur `elif` |
| **L**iskov substitution | Kisi interface ka har implementation har us jagah kaam karna chahiye jahaan wo interface expected hai | Ek client `None` return karta hai jahaan baaki text return karte hain |
| **I**nterface segregation | Ek bade interface ki jagah kai chhote, focused interfaces | Ek bahut badi `Storage` class jis par har part depend karta hai, jabki har ek uske do hi methods use karta hai |
| **D**ependency inversion | High-level logic kisi khaas library par nahi, balki apne khud ke interface par depend karta hai | `openai` business logic ke andar gehraai mein import aur call kiya gaya |

**Open-closed ka matlab "kabhi koi file edit mat karo" nahi hai.** Iska matlab hai ki jo code aksar badalta hai (kaun-sa provider, kaun-sa output format) wo naye pieces ke roop mein joda jaaye, aur jo core chal raha hai wo jas ka tas rahe. Kahin na kahin, ek jagah ko phir bhi chunna hoga ki kaun-sa piece use ho. Wo chunaav program ke kinaare par ek hi jagah rakho, poore logic mein phailaao mat.

**Liskov waadon ke baare mein hai, class names ke baare mein nahi.** Ek interface ek waada hai: "Mujhe ek prompt string do, main ek text string return karunga". Ye raha ek client jo ise todta hai:

```python
class CheapClient:
    def complete(self, prompt: str) -> str | None:
        try:
            return self._call_api(prompt)
        except TimeoutError:
            return None   # every caller now has to check for None
```

Iska method name sahi hai, to ye swap karne laayak lagta hai. Lekin baaki clients ke liye likha code `reply.splitlines()` karta hai, aur jaise hi ye pehli baar time out hota hai, `AttributeError` ke saath crash ho jaata hai. Yahi jaal tab bhi aata hai jab koi implementation kam accept karta hai (wo lambe prompts mana kar deta hai jo baaki le lete hain) ya apne aadhe methods ke liye "not supported" raise karta hai. Waada nibhaao: aisa error raise karo jise caller pehle se handle karta hai, ya client ke andar hi retry karo.

### Dependency injection

SOLID ke zyaadatar hisse ke peeche ka practical tool hai **dependency injection**. Function apni zaroorat ki cheez khud banaane ki jagah use bahar se leta hai:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

`Protocol` ek shape batata hai. Jis bhi class mein matching `complete` method hai wo fit ho jaati hai, kisi se inherit kiye bina, aur mypy jaisa type checker aapke liye ye check karta hai. Ab `summarise` ko na pata hai, na farq padta hai ki wo kaun-sa provider use kar raha hai. Production ek real client pass karta hai, tests ek fake pass karte hain, aur provider switch karne ka matlab hai ek nayi class likhna, `summarise` ko edit karna nahi.

Direction par dhyaan do. Interface business logic ka hai: `summarise` batata hai ki use kya chahiye. Provider library ko bahar ki taraf dhakel diya jaata hai. Dependency inversion mein "inversion" yahi hai.

### Model interface kitna thin hona chahiye?

Upar ke code par ek experienced engineer yahi sawaal poochhega. Asli provider APIs ek jaisi nahi hotin. Wo messages lene, tools call karne, structured JSON return karne, tokens stream karne aur prompts cache karne ke tareeke mein alag hoti hain. Ek method wala `complete(prompt) -> str` interface ye sab chhupa deta hai. To aapke saamne ek asli trade-off hai:

- **Bahut thin** ho, to features kho doge. Agar aapke product ko tool calling chahiye, to ek plain text interface use express nahi kar sakta.
- **Bahut wide** ho, to provider ki details bahar risne lagti hain. `messages`, `tools`, `response_format` aur `stream` wala interface asal mein ek provider ki API ki copy hai, aur agla provider usmein fit nahi hoga.

Teen rules zyaadatar cases sambhaal lete hain:

1. **Interface ko chat call ke hisaab se nahi, apne product ki zaroorat ke hisaab se shape karo.** Agar aapka app invoice fields nikaalta hai, to interface `extract_invoice(text) -> Invoice` ho sakta hai, jahaan `Invoice` aapki apni typed class hai. Phir har adapter andar structured output ke liye apne provider ka best feature use karta hai, aur aapke core logic ko ek saaf, typed result milta hai.
2. **Provider-specific features ko adapter ke andar hi rehne do.** Prompt caching ya koi khaas retry header adapter ka maamla hai. Agar koi provider sach mein wo nahi kar sakta jo aapke product ko chahiye, to wo ek product decision hai, "not supported" error ke peeche chhupaane ki cheez nahi.
3. **Gateway ke baare mein socho.** LiteLLM jaisi libraries, aur OpenAI-style chat format bolne wale servers (jaise vLLM), kai models ko ek jaisa dikhaate hain, to aapka adapter chhota rehta hai. Tab aap gateway par aur un features par depend karte ho jo uske saare models share karte hain. *LLM gateways* lesson ise cover karta hai.

Ek summariser ke liye `complete(prompt) -> str` sahi size hai.

```flow
title: Ek AI app mein ports and adapters
Wiring at start-up | settings padhta hai, adapters banaata hai -[ek client andar pass karta hai]-> Core logic | prompts, parsing, rules
Core logic -[call karta hai]-> ModelClient port | core ka apna interface
ModelClient port -[ismein implement hota hai]-> HostedClient | provider SDK ko wrap karta hai
ModelClient port -[ismein implement hota hai]-> SelfHostedClient | HTTP par vLLM ko call karta hai
ModelClient port -[ismein implement hota hai]-> FakeClient | tests mein use hota hai
```

### Ports and adapters

Yahi idea poore codebase par laagu karo, to iska ek naam hai: **ports and adapters**, jise **hexagonal architecture** bhi kehte hain. Alistair Cockburn ne ise describe kiya. Interviewers dono naam use karte hain.

- **Core logic** wo hai jo product karta hai: ek ticket classify karna, ek prompt banaana, ek answer ko score karna. Ye bahar se kuchh import nahi karta.
- **Ports** wo chhote interfaces hain jo core ko chahiye: ek model client, ek document store, ek notifier.
- **Adapters** ports ko asli services se implement karte hain: kisi provider ka SDK, ek vector database, email ya WhatsApp.
- **Wiring** kinaare par hoti hai (web app ka start-up, command-line entry point): ye settings padhti hai, asli adapters banaati hai aur unhein andar pass karti hai.

Apne design ka ek quick test: kya aap core logic ko ek unit test mein bina network, bina API key aur bina database ke chala sakte ho? Agar haan, to boundaries sahi jagah par hain.

### Inheritance se behtar composition

Jab aapko retries, logging ya cost tracking jaisa behaviour jodna ho, to sabse pehle subclass banaane ka mann karta hai: `RetryingOpenAIClient(OpenAIClient)`. Phir aapko `RetryingSelfHostedClient`, `LoggingRetryingOpenAIClient` chahiye, aur har combination ke saath classes ki ginti badhti jaati hai. **Composition** ka matlab hai iski jagah wrap karna:

```python
import time

class RetryingClient:
    """Wraps any ModelClient and retries failed calls."""

    def __init__(self, inner: ModelClient, attempts: int = 3):
        self._inner, self._attempts = inner, attempts

    def complete(self, prompt: str) -> str:
        for i in range(self._attempts):
            try:
                return self._inner.complete(prompt)
            except Exception:
                if i == self._attempts - 1:
                    raise
                time.sleep(2 ** i)
```

`RetryingClient` khud ek `ModelClient` hai, isliye ye kisi bhi provider ke saath kaam karta hai, aur aap wiring step par wrappers ko ek ke upar ek lagaate ho: `RetryingClient(HostedClient(...))`. Yahi hai open-closed asal mein: naya behaviour, maujooda clients mein koi edit nahi. (Asli code mein har `Exception` par nahi, sirf timeouts aur rate limits par retry karo; *Errors, retries and cost* lesson dekho.)

### Functions ya classes?

Aapko har jagah classes ki zaroorat nahi hai. Saaf inputs aur outputs wale saade functions aksar sabse saaf Python design hote hain, aur aap kisi function mein dependency inject karne ke liye bas use ek parameter bana sakte ho. Class tab lo jab koi cheez aisi state ya settings rakhti hai jo kai calls share karti hain, jaise API key aur timeout wala client, ya jab aapko ek interface ke kai aise implementations chahiye jinhein ek-doosre ki jagah lagaaya ja sake.

### Refactor kab karein

**Refactoring** ka matlab hai code kya karta hai wo badle bina uska structure badalna. Ye tab karo jab aap wo code waise bhi badalne wale ho aur badlaav mushkil hai. Pehle code ko aisa reshape karo ki badlaav aasaan ho jaaye, phir wo aasaan badlaav karo. Safe tareeka:

1. **Pehle tests.** Kuchh bhi chhoone se pehle aise tests likho jo aaj ka behaviour pin kar dein, chaahe wo behaviour badsoorat hi kyun na ho. Kuchh tootega to wo bata denge.
2. **Chhote steps.** Ek function move karo, tests chalaao, commit karo. Branch par ek hafta lene wala refactor aam taur par ek dardnaak merge mein khatam hota hai.
3. **Structure aur behaviour ko alag rakho.** Ek commit ya to code ko reshape karta hai ya badalta hai ki code kya karta hai, kabhi dono nahi, taaki reviewer har ek ko check kar sake.

Jo code chal raha hai aur jise kisi ko badalna nahi hai, use refactor mat karo. Jab tak asli doosra case (doosra provider, doosra output format) ya fake maangne wala koi test na ho, interface mat jodo.

### Low-level design interviews

Kai Bhaarateeya product companies ek **low-level design** (LLD) round rakhti hain. Aapse kisi chhoti cheez ke liye classes aur interfaces design karne ko kaha jaata hai, jaise rate limiter ya parking lot. (**System design** round iski jagah poochhta hai ki poori services aapas mein kaise fit hoti hain.)

"Ek rate limiter design karo jo har user ko prati minute N requests allow kare" ka ek model answer interfaces se shuru hota hai, phir ek simple strategy:

```python
from typing import Protocol

class Clock(Protocol):
    def now(self) -> float: ...

class RateLimiter(Protocol):
    def allow(self, user_id: str) -> bool: ...

class FixedWindow:
    def __init__(self, limit: int, window_s: float, clock: Clock):
        self.limit, self.window_s, self.clock = limit, window_s, clock
        self.counts: dict[str, tuple[int, int]] = {}  # user -> (window number, count)

    def allow(self, user_id: str) -> bool:
        window = int(self.clock.now() // self.window_s)
        seen, n = self.counts.get(user_id, (window, 0))
        n = n if seen == window else 0
        if n >= self.limit:
            return False
        self.counts[user_id] = (window, n + 1)
        return True
```

Phir trade-offs zor se bolo. Clock inject kiya gaya hai, to test ek minute intezaar karne ki jagah fake clock se samay set kar deta hai. Fixed window ki ek jaani-pehchaani kamzori hai: ek user 0:59 par N requests aur 1:00 par N aur kar sakta hai, yaani do seconds mein limit ka doguna. **Token bucket**, jo user ka allowance samay ke saath dheere-dheere refill karta hai, ise smooth kar deta hai, aur wo usi `RateLimiter` interface ke peeche ek doosri class hai, to `allow()` ko call karne wala API code kabhi nahi badalta. Kai servers par counts Redis jaise shared store mein chale jaate hain: bas ek aur adapter.

## Ek worked example

Delhi ke ek legal-tech startup mein Rohit ki team ne ek hafte mein ek contract summariser banaaya. Sab kuchh 300 lines ki ek hi file mein tha: wo PDF padhti thi, ek hosted model provider ko seedhe call karti thi, Markdown format karti thi aur result email karti thi.

Do mahine baad ek saath teen requests aati hain. Ek bada client chaahta hai ki uske contracts uske apne cloud account mein chal rahe model se process hon. Sales team ko summaries Word documents mein chahiye. Aur tests chalne mein lagbhag chaar minute lagte hain, kyunki har test ek asli API call karta hai aur paise lagte hain.

Rohit chhote steps mein refactor karta hai, pehle aaj ke behaviour ke chaaron taraf tests lagaakar.

**1. Badalne ki wajah ke hisaab se baanto.** Wo `reader.py` (PDF se text), `summariser.py` (prompt aur parsing), `formatters.py` (Markdown, aur ab Word), `delivery.py` (email) aur `llm.py` (model clients) banaata hai. Har file ke badalne ki ek hi wajah hai.

**2. Ek port aur do adapters.** `llm.py` mein:

```python
import httpx
from openai import OpenAI

# ModelClient is the Protocol shown earlier, defined in this file.

class HostedClient:
    """A hosted provider, reached through its own SDK."""
    def __init__(self, api_key: str, model: str):
        self._sdk = OpenAI(api_key=api_key, timeout=30)
        self._model = model

    def complete(self, prompt: str) -> str:
        resp = self._sdk.chat.completions.create(
            model=self._model,
            messages=[{"role": "user", "content": prompt}],
        )
        return resp.choices[0].message.content or ""

class SelfHostedClient:
    """A model served with vLLM inside the customer's own cloud."""
    def __init__(self, base_url: str, model: str):
        self._http = httpx.Client(base_url=base_url, timeout=60)
        self._model = model

    def complete(self, prompt: str) -> str:
        r = self._http.post("/v1/chat/completions", json={
            "model": self._model,
            "messages": [{"role": "user", "content": prompt}],
        })
        r.raise_for_status()
        return r.json()["choices"][0]["message"]["content"] or ""
```

Dono ek string return karte hain, kabhi `None` nahi, isliye dono ek hi waada nibhaate hain. Dono failure par ek error raise karte hain, jise caller pehle se handle karta hai.

**3. Core logic jo sirf port ko jaanta hai.** `summariser.py` `ModelClient` import karta hai aur bahar se kuchh nahi:

```python
from llm import ModelClient

PROMPT = "Summarise this contract in 5 bullet points. Flag any termination clause.\n\n{text}"

def summarise(text: str, client: ModelClient) -> list[str]:
    reply = client.complete(PROMPT.format(text=text))
    return [line.lstrip("-* ").strip() for line in reply.splitlines() if line.strip()]
```

**4. Kinaare par wiring.** `main.py` har customer ki settings padhta hai aur client chunta hai. Codebase mein yahi ek jagah hai jise pata hai ki kaun-se providers maujood hain:

```python
from dataclasses import dataclass

from llm import HostedClient, ModelClient, SelfHostedClient

@dataclass
class Settings:
    model_host: str      # "hosted" or "self_hosted"
    model: str
    api_key: str = ""
    base_url: str = ""

def make_client(s: Settings) -> ModelClient:
    if s.model_host == "self_hosted":
        return SelfHostedClient(s.base_url, s.model)
    return HostedClient(s.api_key, s.model)
```

**5. Fake ke saath tez tests.** `test_summariser.py` mein:

```python
from summariser import summarise

class FakeClient:
    def __init__(self, reply: str):
        self.reply = reply
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply

def test_summarise_returns_clean_bullets():
    fake = FakeClient("- Term: 2 years\n\n- Notice period: 90 days\n")
    assert summarise("CONTRACT TEXT", fake) == ["Term: 2 years", "Notice period: 90 days"]
    assert "CONTRACT TEXT" in fake.prompts[0]
```

Test check karta hai ki reply saaf bullets mein badla gaya aur contract ka text prompt tak pahuncha, bina network ya API key ke. Jab har unit test fakes use karne lagta hai, to Rohit ka suite minuton ki jagah seconds mein chalta hai. Wo do-teen slow tests rakhta hai jo asli providers ko call karte hain aur har release se pehle chalte hain, taaki wo cheezein pakdi ja sakein jo fake nahi pakad sakta: badla hua response shape ya galat model name.

Self-hosted client ek nayi class thi, aur `summarise()` bilkul nahi badla. Word output ek naya formatter tha. Har request mein rewrite ki jagah lagbhag ek din laga.

Use ye bhi pata hai ki kahaan rukna hai. Wo PDF reader ke liye interface nahi jodta, kyunki reader ek hi hai aur doosre ka koi plan nahi.

## Aam galtiyaan

- **Logic ke andar gehraai mein external services ko call karna.** Code bina network ke test nahi ho sakta, aur provider badalne ka matlab hai har file mein dhoondhna.
- **Aisa fake jo waada nahi nibhaata.** Agar asli clients string return karte hain aur fake ek list return karta hai, to aapke tests pass honge aur production fail hoga. Fakes asli cheez wala hi interface follow karte hain.
- **Aisa interface jo ek provider ki API ki copy hai.** Wo general dikhta hai lekin sirf usi provider mein fit hota hai. Use caller ki taraf se design karo: core logic ko asal mein kya chahiye?
- **Bahut jaldi bahut zyada abstraction.** 100 lines ki script ke liye interfaces, factories aur layers use padhna mushkil bana dete hain. Abstraction kisi asli doosre case ya test ke liye jodo.
- **Behaviour jodne ke liye subclass banaana.** Retries, logging aur caching ko subclasses banaoge to har combination ke liye ek class banti jaayegi. Iski jagah wrap karo.
- **Bina tests ke, ya ek hi bade step mein refactor karna.** Aapko pata nahi chalega ki kya toda. Tests se behaviour pin karo, phir chhote commits mein aage badho.
- **Interviews mein SOLID ratkar sunaana.** Interviewers ye dekhte hain ki kya aap asli code mein problem pehchaan sakte ho, trade-off bata sakte ho aur use fix kar sakte ho.

## Practice

Neeche linked ArjanCodes ka Python mein SOLID principles wala video dekho, aur har principle ke baad rukkar apne khud ke code mein uska ek example dhoondho.

Phir is lesson ka project check karo, apne chhote app ko waise hi refactor karte hue jaise Rohit ne kiya: pehle aaj ke behaviour ka ek test, phir interface, ek doosra implementation aur start-up par ek `make_client` function. Submit karne se pehle khud mark karo:

| Check | Ye pass hai agar |
| --- | --- |
| Boundary | Core logic ki file koi provider SDK import nahi karti; sirf adapter file aur wiring karte hain |
| Tests | Kam se kam do unit tests fake client use karte hain, bina network ya API key ke chalte hain, aur `pytest` se pass hote hain |
| Swappable | Doosre implementation par switch karne se sirf settings ya wiring badalti hai, core logic nahi |

Agar aapne pehle pytest se tests nahi likhe hain, to pehle *Writing tests with pytest* lesson karo; *Project tooling* unhein ek project ke hisse ke roop mein chalaana cover karta hai.

**Aapka kaam poora hai jab aap** asli code mein single-responsibility aur Liskov problems pehchaan sako, ek model provider ko apne product ke hisaab se sized interface ke peeche rakh sako, use start-up par inject kar sako, logic ko fake se test kar sako, aur rate limiter jaise ek chhote low-level design ko uske trade-offs ke saath samjha sako.
