## Ye kya hai

**Software design** ka matlab hai ye tay karna ki program ko parts mein kaise todna hai aur wo parts aapas mein kaise baat karenge. Zyadatar achhe designs ke neeche do ideas hote hain:

- **Cohesion**: har part ek kaam karta hai, aur uske andar sab kuch usi kaam ka hai.
- **Coupling**: parts ek-doosre ki details par kitna depend karte hain. Loose coupling ka matlab hai ki ek part badlo toh baaki ko chhuna nahi padta.

Achha design matlab high cohesion aur loose coupling. Bura design woh hai jahan email template badalne ke liye model ko call karne waala code bhi edit karna padta hai.

**SOLID principles** wahan tak pahunchne ke paanch jaane-maane guidelines hain. Ye object-oriented programming se aaye hain, par ideas simple Python functions aur modules par bhi lagte hain. Inhe ratna zaroori nahi; zaroori hai un problems ko pehchaanna jinse ye bachate hain.

## Ye kaam kaise karta hai

Paanch principles, aasaan shabdon mein:

| Principle | Aasaan shabdon mein | Is baat ka sign ki aap ise tod rahe ho |
| --- | --- | --- |
| **S**ingle responsibility | Ek module ya class, badalne ki ek wajah | Ek file jo data padhti hai, model call karti hai aur email bhejti hai |
| **O**pen for extension | Naya behaviour code jodkar add karo, chalte code ko edit karke nahi | Har naye provider ke liye lambi chain mein ek aur `elif` |
| **L**iskov substitution | Interface ka koi bhi implementation wahan chalta hai jahan interface expected ho | Ek "provider" jo aadhe methods par "not supported" raise karta hai |
| **I**nterface segregation | Chhote, focused interfaces | Ek bada `Storage` class jis par har part depend karta hai |
| **D**ependency inversion | Interface par depend karo, kisi specific library par nahi | Business logic ke andar gehraai mein `openai.chat...` call karna |

**Dependency injection** inmein se zyadatar ke peeche ka practical tool hai. Function jo cheez chahiye use khud banane ki jagah receive karta hai:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

Ab `summarise` ko fark nahi padta ki kaunsa provider hai. Production mein asli client pass hota hai, tests mein fake; provider badalna ho toh ek nayi class likhni hoti hai, `summarise` edit nahi karna padta.

```flow
title: Business logic ek chhote interface par depend karta hai, provider par nahi
summarise() -> ModelClient interface | complete(prompt) -> str
ModelClient interface -> Provider A client
ModelClient interface -> Provider B client
ModelClient interface -> Tests ke liye fake client
```

Ek AI application ko organise karne ka common tareeka isi idea ko poore codebase mein lagata hai:

- **Core logic** (product kya karta hai: ticket classify karna, prompt banana, answer score karna) bahar ki kisi cheez par depend nahi karta.
- **Adapters** (model client, vector store, database, email) chhote interfaces implement karte hain.
- **Wiring** kinare par (API startup, CLI) asli adapters banakar andar pass karti hai.

**Functions ya classes?** Har jagah classes ki zaroorat nahi. Python mein saaf inputs aur outputs waale simple functions aksar sabse clean design hote hain. Class tab lo jab kuch state ya settings hold karni ho jo kai functions share karte hon, jaise API key aur timeout waala client, ya jab ek hi interface ke kai badle ja sakne waale implementations chahiye.

**Interviews mein.** Low-level design rounds mein aapse kisi chhoti cheez, jaise rate limiter ya parking lot, ke classes aur interfaces design karne ko kehte hain. System design rounds mein poochha jaata hai ki services aapas mein kaise fit hoti hain. Dono mein ek hi idea chalta hai: parts ke naam rakho, har ek ko ek kaam do, aur dikhao ki baaki ko chhue bina ek ko kaise badloge ya test karoge.

## Ek example se samjho

Delhi ke ek legal-tech startup mein Rohit ki team ne ek hafte mein contract summariser banaya. Sab kuch ek 300-line file mein tha: woh PDF padhti thi, ek model provider ko seedhe call karti thi, Markdown format karti thi aur result email karti thi.

Do mahine baad teen requests ek saath aati hain: ek client chahta hai ki unka data unke apne cloud mein hosted model se process ho, sales team ko summaries Word documents mein chahiye, aur tests minutes lete hain kyunki har test asli API calls karta hai.

Rohit steps mein refactor karta hai, pehle aaj ke behaviour ke aas-paas tests likhkar:

1. **Single responsibility.** Woh file ko `reader.py` (PDF se text), `summariser.py` (prompt aur parsing), `formatters.py` (Markdown, aur ab Word) aur `delivery.py` (email) mein todta hai.
2. **Model ke liye interface.** `summariser.py` ab ek `ModelClient` leta hai. Woh `ProviderAClient` aur `SelfHostedClient` likhta hai, dono `complete()` waali chhoti classes.
3. **Kinare par injection.** API startup customer ki settings padhta hai aur sahi client aur formatter pass karta hai.
4. **Tez tests.** Unit tests ek `FakeClient` pass karte hain jo fixed summary deta hai. Test suite chaar minute se teen second par aa jaata hai.

Self-hosted client ek nayi class hai jiske apne tests hain; `summarise()` mein koi badlaav nahi hua. Word output ek naya formatter hai; baaki kuch nahi badla. Har request rewrite ki jagah ek din mein ho gayi.

Woh aage bhi nahi badhta: PDF reader ke liye interfaces nahi jodta, kyunki ek hi reader hai aur doosre ka koi plan nahi. Abstraction tab jodi jaati hai jab sach mein doosra case ho ya testing ki zaroorat ho.

## Aam galtiyaan

- **Logic ke andar gehraai mein external services call karna.** Isse code network ke bina test nahi ho paata aur provider badalna mushkil hota hai.
- **Bahut jaldi bahut zyada abstraction.** 100-line script ke liye interfaces, factories aur layers use padhna aasaan nahi, mushkil bana dete hain.
- **Bade "utils" ya "manager" modules.** Agar module ka naam nahi batata ki woh kya karta hai, toh shaayad woh kai kaam karta hai.
- **Ek implementation ke hisaab se interface badalna.** Phir baaki har implementation aur caller ko bhi badalna padta hai.
- **SOLID ko ratne waale rules samajhna.** Interviewers dekhte hain ki aap asli code mein problem pehchaan kar fix kar sakte ho ya nahi.

## Practice karo

1. Koi bhi script lo jo API ko seedhe call karti hai, aur client ko andar pass karo. Ek fake ke saath ek test likho.
2. Apni sabse badi file ke badalne ki wajahein list karo. Agar do se zyada hain, toh sketch karo ki use kaise todoge.
3. Apne banaye interface ke peeche doosra implementation jodo, use use karne waale code ko edit kiye bina.
4. Do minute mein samjhane ki practice karo ki AI app ko aise kaise structure karoge ki model provider badla ja sake.
