## Ye kya hai

AI system ka behaviour code se zyada cheezon par depend karta hai:

- **prompts** (system prompts, templates, few-shot examples);
- **model** (provider, model ka naam aur snapshot ya version);
- temperature aur maximum tokens jaisi **settings**;
- **tool definitions** jo model ko dikhti hain;
- **retrieval configuration** (index version, chunking, top-k, reranker).

Versioning ka matlab hai ki inmein se har ek ki ek identifier ho, badlaav review aur tests se guzrein, live combination har request ke saath record ho, aur koi bhi pichhla combination restore kiya ja sake.

```flow
Release assistant-2026.11.3 | prompts support-system v12 aur refund-rules v4; ek pinned, dated model snapshot; temperature 0.2; tools lookup_order v3, create_ticket v2; index 2026-11-01 -[har trace aur audit event mein record]-> Ek badlaav
Ek badlaav -> CI mein golden set -> Staging -> Production alias
Production alias -[rollback: alias ko wapas hilao]-> Pichhla release
```

Release ke har hisse ka apna version hota hai, isliye kisi bhi answer ko wapas us cheez tak trace kiya ja sakta hai jisne use banaya.

Is lesson mein hum Gurugram ke ek fintech ke support assistant ke saath chalenge, jahan teen teams production mein seedhe prompts edit kar rahi thi.

## Ye kaam kaise karta hai

**Prompts version control mein.** Prompts ko repository mein files ki tarah (ya prompt registry mein) store karo, code mein bikhre strings ki tarah ya dashboard mein edit hote hue nahi. Badlaav pull requests se guzarte hain, CI mein evals ke saath.

**Prompt registries.** MLflow ki prompt registry, Langfuse aur doosre tools aliases ("production", "staging") ke saath naam wale, numbered prompt versions store karte hain. Application prompt ko alias se maangta hai; alias hilane se code release ke bina deploy ya rollback ho jaata hai. Tab kaam ka hai jab non-engineers prompts edit karte hain, bas badlaav tab bhi evals paas karein.

**Models ko pin karo.** Jahan providers dete hain wahan dated model snapshots use karo, un aliases ki jagah jo chupchaap badal jaate hain. Agar aap apne gateway ke aliases ("chat-default") use karte ho, toh gateway configuration khud versioned aur reviewed hota hai.

**Ek release identifier.** Prompt version, model, settings aur index version ko ek release mein bundle karo (jaise "assistant-2026.11.3") jo har trace aur audit event mein record ho.

**Promote karne se pehle test karo.** Har badlaav golden set chalata hai. Maujooda release se quality, cost aur latency par compare karo. Staging se production tak promote karo.

**Provider deprecations.** Providers announced dates par models retire karte hain. Ek calendar rakho, replacement ko jaldi test karo, aur switch ko ek release ki tarah plan karo.

**Rollback.** Pichhla release taiyaar rakho. Rollback ek action hona chahiye: alias hilao ya pichhla tag dobara deploy karo.

**Kya aur kaise version karein:**

| Hissa | Kaise version karein | Aam badlaav |
| --- | --- | --- |
| Prompts | Git mein files ya numbered versions wali registry | Wording, examples, rules |
| Model | Pinned dated snapshot, ya reviewed gateway alias | Naye model par upgrade |
| Settings | Git mein config file | Temperature, max tokens |
| Tool definitions | Git mein code | Naya parameter ya tool |
| Retrieval | Git mein index version aur config | Chunk size, top-k, reranker |

**Ek baar mein ek cheez badlo.** Jab ek release prompt, model aur index ek saath badalta hai aur quality gir jaati hai, toh koi nahi bata sakta ki kisne kiya. Jahan mumkin ho unhe alag releases ki tarah ship karo, har ek golden set se guzarte hue. Jab kai ko saath ship karna pade, jaise model switch jise prompt adjustments chahiye, toh staging mein har step par golden set chalao taaki production se pehle har hisse ka asar pata ho.

**Model switches.** Naye model ko release candidate ki tarah treat karo: poora golden set chalao, cost aur latency compare karo, jin bhashaon mein aap serve karte ho unmein sample conversations par refusals aur tone check karo, aur dheere-dheere roll out karo. Ek model ke liye tune kiye gaye prompts ko aksar agle ke liye chhote badlaav chahiye hote hain.

**Prompts files ki tarah, releases ek manifest ki tarah.**

```text
prompts/
  answer.v13.md
  answer.v14.md
  rewrite.v4.md
release.yaml
```

```yaml
# release.yaml
release: assistant-2026.11.3
model: claude-sonnet-5-5-YYYYMMDD     # a dated snapshot where the provider offers one
settings: {max_tokens: 600}
prompts: {answer: v14, rewrite: v4}
index: policies-2026-11-01
tools: tools-v7
```

```python
import hashlib, json, yaml
from pathlib import Path

def load_release(path="release.yaml"):
    rel = yaml.safe_load(open(path))
    rel["prompt_text"] = {name: Path(f"prompts/{name}.{ver}.md").read_text()
                          for name, ver in rel["prompts"].items()}
    blob = json.dumps({k: rel[k] for k in ("model", "settings", "prompts", "index", "tools")}, sort_keys=True)
    rel["fingerprint"] = hashlib.sha256(blob.encode()).hexdigest()[:10]
    return rel

RELEASE = load_release()     # log RELEASE["release"] and RELEASE["fingerprint"] on every trace
```

Agar koi release ko rename kiye bina edit kare toh fingerprint badal jaata hai, jo "chhote" untracked badlaav pakad leta hai.

**CI mein checks.** Build fail karo jab release kisi missing ya risky cheez ko point kare:

```python
import re
from datetime import date

RETIREMENTS = yaml.safe_load(open("model-retirements.yaml"))     # {model_id: "YYYY-MM-DD"}

def check_release(rel):
    problems = []
    for name, ver in rel["prompts"].items():
        if not Path(f"prompts/{name}.{ver}.md").exists():
            problems.append(f"missing prompt file {name}.{ver}")
    if not re.search(r"\d{8}$", rel["model"]):
        problems.append("model is not pinned to a dated snapshot")
    retire = RETIREMENTS.get(rel["model"])
    if retire and (date.fromisoformat(retire) - date.today()).days < 60:
        problems.append(f"{rel['model']} retires on {retire}; plan the switch")
    return problems
```

Jahan provider dated naam nahi deta, wahan jo pin kar sakte ho woh karo (aapke gateway ka alias, reviewed) aur chupchaap badlaav pakadne ke liye golden set ko schedule par chalao.

**Promotion aur rollback.** Production deployed commit se `release.yaml` padhta hai, isliye promote karna ek pull request merge karna hai aur rollback pichhle commit ko dobara deploy karna. Agar aap iski jagah prompt registry use karte ho, toh wahi rule lagta hai: app ek alias padhta hai, aur golden set paas hone ke baad promotion alias ko hilata hai.

**Ek changelog jo insaan padhein.** `release.yaml` ke bagal mein ek chhota `CHANGELOG.md` rakho: release id, date, kya badla, pichhle release ke mukable eval results, aur kisne approve kiya. Clients ke reviewers aksar yahi maangte hain.

## Ek example se samjho

Gurugram ke ek fintech ke support assistant ke prompts teen teams admin panel mein seedhe edit karti thi. Ek Friday, complaint volume double ho gaya. Koi nahi bata paya ki kya badla tha; traces sirf model ka naam dikhate the.

Fix:

- Prompts repository mein files ki tarah chale gaye, har prompt ke owners ke saath.
- Ek prompt registry published versions rakhti hai; production alias `support-prod` use karta hai.
- Har trace release record karta hai: prompt versions, model snapshot, temperature, index version.
- CI har prompt change par 120-sawaal ka golden set chalata hai aur ek point se zyada ki girawat ko block karta hai.
- Gateway model aliases sirf pull request se badle jaate hain.

Do mahine baad ek naya prompt version evals paas karta hai par Hindi conversations mein customer feedback gir jaata hai. Traces dikhate hain ki girawat release 2026.12.2 se shuru hui. Team ek minute mein alias ko wapas 2026.12.1 par le jaati hai, phir golden set mein 25 Hindi cases jodti hai, jo problem ko saamne laate hain. Theek kiya hua version agle din ship hota hai.

| Event | Versioning se pehle | Versioning ke baad |
| --- | --- | --- |
| Complaint spike | Kisi ko nahi pata kya badla | Traces ne release 2026.12.2 ki taraf ishara kiya |
| Rollback | Ghanton ka andaaza | Alias ek minute mein wapas hila |
| Root cause | Anjaan | 25 naye Hindi golden cases ne ise saamne laaya |
| Fix ship hua | Saaf nahi | Agle din, CI ke zariye |

## Aam galtiyaan

- **Production dashboards mein bina review ke edit hote prompts.** Badlaav dikhna band ho jaate hain.
- **Floating model aliases.** Provider model update karta hai aur aapka behaviour bina bataye badal jaata hai.
- **Traces mein versions na hona.** Aap quality ke badlaav ko kisi release se jod nahi sakte.
- **Golden-set gate na hona.** Prompt changes code changes hain; unhe test karo.
- **Deprecation dates ko ignore karna.** Aakhri waqt ka majboori switch ek risky release hai.
- **Ek release mein kai hisse badalna.** Quality girne par aap nahi bata sakte ki kaunsa hissa zimmedaar hai.
- **Har prompt ka owner na hona.** Kisi ko har badlaav approve karna hai aur uske asar ka jawab dena hai.
- **Naya version jodne ki jagah prompt file ko usi jagah edit karna.**
- **Aise model aliases jo ek fixed naam ke neeche chupchaap badal jaate hain.**
- **Retirement calendar na hona**, jisse deprecation emergency ban jaati hai.

## Jab halka versioning bhi theek hai

- **Ek prompt wala prototype**: use Git mein rakho aur likh lo ki kaunsa model use kiya.
- **Personal tools** jahan koi aur consistent behaviour par nirbhar nahi hai.
- **Ek baar chalaye jaane wale fixed batch jobs**, jahan output mein prompt aur model record karna kaafi hai.

## Demo se production tak

- **Har hissa ek release file mein pin karo**, aur har trace par release id aur fingerprint log karo.
- **Golden set chalao** CI mein har release change par.
- **Model retirement dates track karo** aur replacements ko jaldi test karo.
- **Ek changelog rakho**, eval results aur approvals ke saath.
- **Pichhla release dobara deploy karke rollback karo.**

## Practice karo

MLflow ke prompt registry docs padho.

1. Apne app ke prompts ko versioned files ya aliases wali registry mein le jao.
2. Har trace mein ek release identifier (prompt versions, model snapshot, settings, index version) record karo.
3. Ek prompt badlo, CI mein apna golden set chalao, use promote karo, phir ek action se rollback karo.
4. CI mein check_release jodo, phir release.yaml ko ek aise prompt version par point karo jo exist nahi karta aur confirm karo ki build fail hota hai.

**Aapka kaam poora jab:** aap kisi bhi pichhli request ke liye "is answer ko exactly kisne banaya?" ka jawab de sako, aur paanch minute se kam mein rollback kar sako.
