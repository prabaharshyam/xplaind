## Ye kya hai

Har automation kabhi na kabhi fail hota hai. Koi API down hota hai, koi token expire hota hai, koi customer apna phone number galat type kar deta hai, koi provider limit laga deta hai ki aap kitni tezi se bhej sakte ho. Sawaal ye nahi ki fail **hoga ya nahi**, balki ye ki **kaise** hoga. Achhi tarah bana automation surakshit tareeke se fail hota hai: kuch khota nahi, kuch do baar nahi hota, aur sahi insaan ko pata hota hai ki kya karna hai.

**Error handling** wo sab hai jo automation tab karta hai jab koi step fail ho, ya koi step "success" ho par kuch galat lautaaye:

| Kaam | Iska matlab |
| --- | --- |
| **Retry** | Jo errors shaayad temporary hain unhe phir se try karna, dheere-dheere aur gini-chuni baar |
| **Stop** | Jo errors apne aap theek nahi honge unhe baar-baar try na karna; unhe record karna |
| **Alert** | Kisi insaan ko ek baar bataana, itni details ke saath ki wo kuch kar sake |
| **Recover** | Wajah theek hone ke baad surakshit tareeke se dobaara process karna, bina kuch do baar kiye |
| **Record** | Har item ke saath kya hua uski history rakhna, review aur reruns ke liye |

In paanchon kaamon ke neeche do ideas hain. Pehla, sahi response is par nirbhar karta hai ki **retry se kya badlega**: busy server agli baar jawaab de sakta hai, galat phone number kabhi theek nahi hoga. Doosra, "send" ya "pay" ki call fail hone ka matlab hamesha ye nahi ki kuch bheja ya pay nahi hua. Zyaadatar asli duplicates yahi bhoolne se aate hain.

Ye lesson Bengaluru ke ek logistics startup ko follow karta hai, jiske delivery updates do baar gaye, rate limits se takraaye aur ek baar poore din ruke rahe. Example tool n8n hai.

## Ye kaam kaise karta hai

### Error ko is hisaab se baanto ki retry se kya badlega

```flow
Ek error aata hai -> Kya step sirf data padh raha tha?
Kya step sirf data padh raha tha? -[haan]-> Temporary error? | timeout, 429, 500 se 504
Kya step sirf data padh raha tha? -[nahi]-> Nateeja pata nahi? | send, pay ya create par timeout ya 500 se 504
Nateeja pata nahi? -[haan]-> Apni key se status check karo | phir usi key se retry karo
Nateeja pata nahi? -[nahi]-> Temporary error?
Temporary error? -[haan]-> Backoff ke saath retry karo | phir bhi fail ho toh needs attention
Temporary error? -[nahi]-> Ek record ki baat hai? | 400, 404, invalid data
Ek record ki baat hai? -[haan]-> Needs attention list | baaki ke saath aage badho
Ek record ki baat hai? -[nahi]-> Run rok do | 401, 403, expire hua token; owner ko alert karo
```

| Tarah | Examples | Kya karna hai |
| --- | --- | --- |
| **Temporary** | Network blips, rate limits (HTTP 429), kisi read par server errors (500 se 504) | Throttle karo, phir backoff aur ek cap ke saath retry karo |
| **Nateeja pata nahi** | Kisi step par timeout ya 500 se 504, jo kuch send, pay ya create karta hai | Pehle check karo, phir sirf usi key ke saath retry karo |
| **Permanent, ek record** | Bad input (400), gaayab record (404), "12345" jaisa phone number | Reason ke saath record karo, baaki ke saath aage badho |
| **Permanent, poora workflow** | Galat ya expire hue credentials (401, 403), delete hui sheet | Turant ruko aur owner ko alert karo |
| **Logic** | Run success hota hai par galat kaam karta hai, jaise koi field galat map hua ho | Inhe sirf validation aur monitoring pakadte hain |

Status codes bas shuruaat hain. Do patterns zyada bataate hain:

- **Baaki records nikal jaate hain, par ek hi record har attempt par fail hota hai.** Tab dikkat us record mein hai, bhale code 500 kahe. Kuch APIs bad input par crash hokar server error report karti hain. Aam retries ke baad use "needs attention" mein bhejo.
- **Har record ek ke baad ek fail hota hai.** Tab dikkat service ya aapke credentials mein hai, records mein nahi. 2,000 items ko ek-ek karke fail hone dene ki jagah jaldi ruk jaao.

### Timeouts ka matlab saaf nahi hota

Timeout ka matlab hai ki aapne intezaar karna band kar diya, ye nahi ki provider ne kuch nahi kiya. SMS shaayad chala gaya ho aur sirf jawaab kho gaya ho. Aankh band karke retry karo aur customer ko wo do baar milega. Misaal ke liye, Stripe ke docs kehte hain ki 500 ko bhi aise hi maano: paisa gaya bhi ho sakta hai, nahi bhi.

Surakshit pattern ke teen hisse hain:

1. **Call se pehle attempt record karo.** Ek unique key aur "sending" status ke saath send-log row likho; baad mein use "sent" ya "failed" mein update karo.
2. **Provider support kare toh idempotency key bhejo.** Idempotency key ek unique value hai jo aap request ke saath bhejte ho taaki provider repeat ko pehchaan sake. Misaal ke liye, Stripe ek `Idempotency-Key` header leta hai: usi key aur unhi details ke saath retry karo toh wo dobaara charge karne ki jagah pehla result lauta deta hai. Uske v1 API docs kehte hain ki usi key ke saath 24 hours ke andar retry karo (November 2026 ke hisaab se). Apne provider ke docs check karo; kuch ye dete hain, kuch nahi.
3. **Timeout par retry se pehle dekho.** Agar provider ke paas status API hai, toh poochho ki message ya payment maujood hai ya nahi. Retry sirf tab karo jab wo na ho. Retry ke liye kabhi nayi key mat banao: nayi key provider ko batati hai ki "ye ek nayi request hai".

Agar provider ke paas na idempotency key hai na status lookup, toh har action ke liye tay karo ki kaun-si galti sasti hai. Do baar bheja gaya delivery update pareshaan karta hai; do baar diya gaya refund asli paisa hai. Paise se judi kisi bhi cheez mein unknown nateeje ko auto-retry mat karo: use "needs attention" mein daalo taaki koi insaan check kare.

### Retry se pehle throttle karo

Kisi jaane-pehchaane daily peak par rate limits (HTTP 429) badkismati nahi hain: aap apne plan ki ijaazat se tez bhej rahe ho. **Provider ki documented limit se tez mat bhejo**, taaki 429s kam hi aayein, aur retries ko safety net ki tarah rakho.

Maan lo, plan har second 10 messages ki ijaazat deta hai. Ek second ke gap ke saath 8 ke batches bhejo: isse usi account ko use karne waale doosre workflows ke liye 20 percent headroom bachta hai. Tab 3,000 evening messages mein lagbhag 375 seconds lagte hain, chhah minute se thoda zyada. n8n mein ye HTTP Request node ke **Batching** option (Items per Batch aur Batch Interval) se kar sakte ho, ya ek **Loop Over Items** node aur loop ke andar ek **Wait** node se.

### Backoff aur jitter ke saath retry

Temporary errors ko kuch baar retry karo, har baar zyada intezaar karke. Phir **jitter** jodo, yaani har wait par thoda random extra samay. Iske bina, jab 7 pm par 500 items fail hote hain, toh saare 500 theek usi second par retry karte hain aur phir saath mein fail ho jaate hain.

```flow
dir: LR
Attempt 1 -[fail]-> 5 se 10 s wait -> Attempt 2 -[fail]-> 10 se 20 s wait -> Attempt 3 -[fail]-> 20 se 40 s wait -> Attempt 4 -[fail]-> Needs attention aur alert
```

Ek samajhdaari waala default: har baar wait ko double karo, 0 se 100 percent random jodo, 3 se 5 attempts ke baad ruk jaao. Kisi 429 ke saath **Retry-After** header aa sakta hai, seconds mein ya ek date ke roop mein. Apne number ki jagah use use karo.

**n8n aapko kya deta hai.** Har node mein **Max Tries** aur **Wait Between Tries (ms)** ke saath ek **Retry On Fail** setting hoti hai. November 2026 ke hisaab se, n8n ke docs kehte hain ki Max Tries zyada se zyada 5 aur wait zyada se zyada 5,000 ms ho sakta hai, aur HTTP Request node aapke liye Retry-After nahi padhta. Wait ki ek hi setting hai, isliye wait badhta nahi. Network blip ke liye ye theek hai. Lambe, badhte waits ke liye retry khud banao: node ke error output ko ek Wait node par route karo aur waapas loop karo, ek counter ke saath taaki wo ruk jaaye.

### Idempotency: do baar chalaana bhi safe

Koi step **idempotent** hai jab use do baar chalaane ka asar ek baar chalaane jitna hi ho. Retries aur reruns steps ko dohraate hain, isliye kuch bhi create karne waale har step ko iski zaroorat hai.

Har action ke liye ek **unique key** ke saath send log rakho. Act karne se pehle check karo ki key pehle se "sent" mark hai ya nahi; hai toh skip karo. Key ko **action jis cheez ke baare mein hai** usse chuno, taaki ek hi real-world action se hamesha ek hi key bane:

| Action | Achhi key | Kharaab key, aur kyun |
| --- | --- | --- |
| Delivery update SMS | Order id plus status, jaise ORD-4471 plus "out for delivery" | Run id: har rerun ko nayi milti hai, toh kabhi kuch skip nahi hota |
| Monthly fee reminder | Member id plus billing month | Sirf member id: ye agle mahine ka reminder rok deti hai |
| Ledger mein invoice | Supplier ka invoice number | Process karne ka samay: har baar unique, toh kuch nahi pakadta |

Agar do runs overlap kar sakte hain, toh check ke baad action mein bhi race ho sakti hai: dono runs check karte hain, dono ko kuch nahi dikhta, dono bhej dete hain. "sending" row pehle likhna, aise store mein jo usi key ki doosri row mana kar de (jaise unique constraint waali database table), ye gap band kar deta hai.

### Jo waapas aata hai use validate karo

Green tick ka matlab sirf itna hai ki call laut aayi. Check karo ki response samajh mein aata hai: jo list aani thi wo khaali nahi hai, zaroori fields maujood hain, "200 OK" body mein koi error message nahi hai. Agar jis export mein aam taur par 8,000 rows hoti hain usmein ek bhi nahi hai, toh use error maankar ruko, "successfully" kuch na karne ki jagah. n8n mein ek IF node bad responses ko **Stop and Error** node par route kar sakta hai, jo jaanboojhkar run fail kar deta hai.

### Kharaab records alag karo, par sab fail ho toh ruko

300 mein se ek kharaab item baaki 299 ko nahi rokna chahiye. Items ko alag-alag process karo aur har failure ko uske reason ke saath ek "needs attention" list mein likho, jise kabhi-kabhi **dead-letter queue** kehte hain. n8n mein node ka **On Error** **Continue (using error output)** par set karo aur us output ko list se jodo. Koi un records ko theek karke baad mein dobaara process karta hai. Kuch bhi chupchaap nahi khota.

Ulte case mein **circuit breaker** chahiye: ek rule jo failures jama hone par run ko pause kar de, jaise lagaataar 20 failures, ya aakhri 50 items mein se aadhe se zyada. Iske bina ek outage 2,000 dead-letter rows aur 2,000 alerts ban jaata hai.

### Kaam ke alerts

| Kamzor alert | Kaam ka alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. SMS provider ka token expire ho gaya hai. Settings, Credentials, SMS provider mein use renew karo, phir rerun karo; bheje ja chuke messages skip honge. Run link: ..." |

Wahaan bhejo jahaan owner sach mein dekhta hai, jaise email, Slack, Teams ya WhatsApp. Repeats ko group karo, taaki ek outage par 500 nahi, ek message jaaye.

n8n mein ek alag **error workflow** banao jo **Error Trigger** node se shuru ho, aur use har workflow ki Settings mein chuno. Ye tab chalta hai jab koi automatic execution fail ho. Jab aap haath se test karte ho tab ye nahi chalta, isliye ise kisi asli scheduled ya webhook run se test karo.

### Sirf errors nahi, volume bhi monitor karo

Sabse khatarnaak failure mein koi error hota hi nahi. Har din processed items aur failures track karo. "1,000 se kam" jaisa fixed threshold har shaant Sunday ko fire hota hai aur aadhe toote din ko miss kar deta hai. Iski jagah **usi weekday ke haal ke average** se compare karo, jaise "agar 8 pm tak humne pichhle chaar Tuesdays ke average ke aadhe se kam bheje hain toh alert karo", aur rule ko har mahine review karo.

### Ownership aur ek runbook

Har automation ka ek naamit owner aur ek chhota runbook hota hai: ye kya karta hai, aam failures, har ek ko kaise theek karein, aur surakshit tareeke se rerun kaise karein.

## Ek example se samjho

Bengaluru ka ek logistics startup ek automation chalaata hai jo customers ko SMS se delivery updates bhejta hai aur order system update karta hai: din mein lagbhag 8,000 messages, zyaadatar 6 pm se 9 pm ke beech. Neeche ke numbers ek typical pehle mahine ka illustration hain, measured results nahi.

**Pehla mahina bura gaya:**

| Dikkat | Wajah |
| --- | --- |
| Evening peaks par messages fail hue | Workflow jitna tez ho saka bhejta raha, aur SMS provider ne use rate-limit kar diya (HTTP 429) |
| Kuch customers ko do messages mile | Ek failed run ko haath se rerun kiya gaya aur usne pehle waale messages phir bhej diye; timeout waale sends aankh band karke retry hue |
| Ek din kuch nahi gaya, aur koi error bhi nahi | Order system ka login token expire ho gaya tha; export step zor se fail hone ki jagah khaali list lauta raha tha |

**Fixes:**

1. **Plan ki limit tak throttle:** provider ke documented rate se neeche batches, beech mein ek wait ke saath.
2. 429s par **backoff aur jitter ke saath retries**, Retry-After ho toh use use karke, zyada se zyada chaar attempts, phir "needs attention" sheet. Kisi send par timeout ya 500 se 504 pehle fix 3 waale status check se guzarta hai.
3. **Order id plus status se key kiya hua send log.** Har message call se pehle "sending" ke roop mein likha jaata hai. Rerun "sent" mark waali har cheez skip karta hai. Timeout ke baad, workflow dobaara bhejne se pehle us key se provider ka delivery status check karta hai.
4. **Export ko validate karna.** Khaali ya bahut chhota export ab green khatam hone ki jagah run ko "order export ne 0 rows lautaayin; order system login check karo" ke saath rok deta hai. Yahi wo fix hai jo us chup din ko pakad leta.
5. **Credentials errors run ko turant rokte hain** aur owner ko alert karte hain ki token kahaan renew karna hai.
6. **Ek circuit breaker:** lagaataar 20 failed sends run ko pause karte hain aur ek alert bhejte hain.
7. **8 pm par ek volume check**, usi weekday ke pichhle chaar dinon ke average se compare karke, 50 percent se neeche hone par alert.

**Agla mahina (illustrative):**

| Measure | Mahina 1 | Mahina 2 |
| --- | --- | --- |
| Duplicate messages | Lagbhag 900 | 3, sab un timeouts ke baad jab status lookup khud down tha |
| Rate limits ki wajah se khoye messages | Lagbhag 1,200 | 0; kuch 429s, sab retry par bhej diye gaye |
| Agla login expiry theek karne mein laga samay | Lagbhag 9 hours (pehle ek customer ne complain kiya) | 20 minutes (alert ne bataaya ki kya karna hai) |
| Attention waale records | Pata nahi | 35, har ek reason ke saath, sab ek din ke andar theek |

Jab provider bata nahi sakta ki kya hua, toh aapko ek kabhi-kabhaar ke duplicate aur ek kabhi-kabhaar chhoote update mein se chunna padta hai. Delivery updates ke liye team ne duplicate chuna.

## Aam galtiyaan

- **Sab kuch retry karna.** Permanent errors ko theek karna padta hai; jo record har baar fail ho uski jagah "needs attention" mein hai.
- **Timeout waale send ko aankh band karke retry karna.** Pehla attempt shaayad kaam kar gaya ho. Pehle apni key se check karo.
- **Har attempt par nayi key.** Run id ya timestamp har retry ko naya dikhaata hai, toh kuch skip nahi hota.
- **Throttling ki jagah retries.** Agar 429s roz usi ghante aate hain, toh dheeme ho jaao; bas aur zor se retry mat karo.
- **Bina jitter aur bina cap ke fixed waits.** Sab kuch ek saath retry hota hai, outage aur bigadta hai aur aap block bhi ho sakte ho.
- **Green run par bharosa karna.** Khaali ya ajeeb "successful" responses ko validate karo.
- **Ek kharaab item batch rok deta hai, ya ek dead service har item fail kar deti hai.** Records alag karo, par failures jama hon toh run rok do.
- **Bina details ke alerts, ya 500 alerts.** Ek baar batao ki kya toota aur kya karna hai.

## Practice karo

Neeche linked n8n ki error handling guide padho, aur N8N102 course ka error-handling hissa phir se dekho.

1. **Retries.** Ek HTTP Request node ko aise endpoint par point karo jo jaanboojhkar fail hota hai (jaise aapka apna chhota webhook workflow jo 503 lautaaye). Retry On Fail on karo aur execution log mein confirm karo ki retries sach mein chale. Phir error output, ek Wait node aur ek counter se ek lamba retry banao.
2. **Throttle.** 50 test items timed batches mein bhejo aur check karo ki timing aapke plan se match karti hai.
3. **Duplicates aur dead letters.** Ek unique key waala send log, "sending" phir "sent" status, aur ek "needs attention" sheet jodo. Workflow do baar chalaao aur dikhaao ki kuch bhi do baar nahi gaya.
4. **Alerts aur checks.** Error Trigger node aur ek kaam ke alert ke saath ek error workflow banao, ek empty-result check aur ek same-weekday volume check bhi.

**Aapka kaam poora hai jab aap** apne workflow ko chaar tareekon se tod sako, ek temporary error, ek permanent error, ek kharaab item aur ek khaali input se, har ek ke liye sahi behaviour dikha sako, aur use bina duplicates ke rerun kar sako.
