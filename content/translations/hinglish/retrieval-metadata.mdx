## Ye kya hai

**Metadata** chunk ke text ki jagah chunk ke baare mein jaankaari hai. RAG mein ye paanch kaam karta hai:

- **Filters**: search ko state, document type, language ya date se seemit karta hai.
- **Citations**: bataata hai ki jawaab theek-theek kahaan se aaya (document, section, page, link).
- **Freshness**: pichhle saal waale se nahi, jo version in force hai usse jawaab deta hai.
- **Permissions**: tay karta hai ki chunk kaun dekh sakta hai.
- **Behtar matching**: wo context jodta hai jo chunk ke text mein nahi hai, jaise document ka title ya section path.

```flow
Chunk text | "This limit is 45 days." Hard to find on its own -> Stored with metadata | doc: Leave Policy 2026, section: Earned leave > Carry forward, page 4, state KA, access: all-employees
Stored with metadata -> Embedded text | "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days."
Stored with metadata -> Query filter | user's groups, user's state, in force today
Stored with metadata -> Citation | Leave Policy 2026, Karnataka, section 3.2, page 4
```

Dikkat ye hai ki metadata chupchaap fail hota hai. Galat date ya galat spelling waala state sawaal ke samay koi error nahi deta; sahi chunk bas kabhi waapas nahi aata, aur model galat chunk se poore bharose ke saath jawaab de deta hai.

Ye lesson Bengaluru ki ek IT company ke HR assistant ko follow karta hai, jo paanch states ko serve karta hai. Exercise inhi ideas ko sarkaari orders par le jaati hai, jahaan versions aur amendments aur mushkil hain.

## Ye kaam kaise karta hai

### Ingestion par hi jama karo

Har chunk ke liye kam se kam ye store karo:

| Field | Example | Kis kaam aata hai |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations aur links |
| `doc_group` | `LP` (saare versions aur translations) | Versions aur language copies ko jodna |
| `section_id`, `section_path`, `page` | 3.2; Earned leave, Carry forward; page 4 | Precise citations, amendments, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | User ke profile se filters |
| `issued_on` | 2025-12-10 | "The 2019 order" jaise sawaal |
| `effective_from`, `effective_to` | 2026-01-01, khaali | Freshness aur history waale sawaal |
| `superseded_by` | khaali | Jawaabon mein "replaced by" notes |
| `language` | `en` | Filters, kaun-si copy dikhaani hai ye chunna |
| `access_groups` | `all-employees` | Permissions |

Abhi jama karo; baad mein jodne ka matlab hai har file ko dobaara parse karna.

**PDFs se ise nikaalna.** Kuch fields source system se aate hain (link, owner, access groups). Baaki document se hi padhne padte hain: headers mein order numbers, issue dates aur section numbers. Saaf digital PDFs ke liye rules ("No." aur dates ke liye regular expressions) kaam karte hain; scanned files ke liye OCR aur ek model chahiye, aur dono galtiyaan karte hain. Nikaale gaye fields par bharosa karne se pehle lagbhag 50 documents ka ek sample haath se check karo aur har field ki errors gino. Dates par khaas nazar rakho: "03/12/2019" India mein 3 December hai, par US defaults waale parser ke liye 12 March, isliye format saaf-saaf batao.

### Contextual text

Jo chunk kehta hai "This limit is 45 days" use retrieve karna mushkil hai, kyunki usmein kuch nahi bataata ki *kaun-si* limit. Jo text aap embed karte ho uske aage title aur section path jodo: "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days". Iski koi cost nahi hai.

Isse mazboot tareeka hai ki model se har chunk ke liye ek-do vaakya likhwaao jo bataayein ki wo chunk apne document mein kahaan aata hai. Anthropic ne is "contextual retrieval" ko apne datasets par test kiya aur report kiya ki isne top-20 retrieval failure rate ko 35% ghataaya, keyword (BM25) search par bhi lagaane se 49%, aur reranking jodne par 67%. Har chunk par ek model call lagti hai, isliye apne golden set par naapo.

### Generated metadata

Model ek chhota summary, keywords, ya wo questions bhi likh sakta hai jinka jawaab chunk deta hai. Generated questions tab kaam aate hain jab users documents se bahut alag shabdon mein poochhte hain ("can I carry over my leave?" banaam "Carry forward of earned leave").

Har generated question ko **uske apne vector ke roop mein, parent chunk ki id ke saath** store karo. Jab question vector match ho, toh parent chunk return karo, question ka text kabhi nahi, kyunki model ko asli document se jawaab dena chahiye. Do gotchas: generated questions chunk jitna kehta hai usse zyada ka vaada kar sakte hain, isliye ek sample spot-check karo; aur wo puraane pad jaate hain, isliye chunk text ka hash store karo aur uske badalne par dobaara generate karo.

### Fixed vocabularies, code mein validate kiye hue

Filters exact values compare karte hain. Filter ke liye "HR", "Human Resources" aur "hr dept" teen alag departments hain. Departments, document types, states aur languages ke liye fixed lists use karo, aur har chunk ko index hone se pehle check karo:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, field_validator, model_validator

State = Literal["KA", "TN", "MH", "TS", "GJ", "ALL"]   # the client's five states, plus ALL
DocType = Literal["policy", "circular", "faq", "contract"]

class ChunkMeta(BaseModel):
    doc_id: str
    doc_group: str               # same for every version and translation
    title: str
    section_id: str              # stable id such as "3.2"
    section_path: str
    page: int
    doc_type: DocType
    state: State
    language: Literal["en", "hi", "ta", "kn", "mr", "te", "gu"]
    issued_on: date
    effective_from: date
    effective_to: date | None = None
    superseded_by: str | None = None
    access_groups: list[str]

    @field_validator("access_groups")
    @classmethod
    def not_empty(cls, v):
        if not v:
            raise ValueError("every chunk needs at least one access group")
        return v

    @model_validator(mode="after")
    def dates_in_order(self):
        if self.effective_to and self.effective_to < self.effective_from:
            raise ValueError("effective_to is before effective_from")
        return self
```

Har chunk ko `ChunkMeta.model_validate` se guzaaro, jo pass hon unhein index karo, aur jo fail hon unhein error ke saath ek quarantine table mein likho. Har run par quarantine counts report karo. "Karnatka" tag waala document ab zor se fail hota hai, bajaay iske ki wo har Karnataka employee ki search se gaayab ho jaaye. State list client ki asli list se bilkul match honi chahiye; jo state aap jodna bhool gaye, uske saare documents quarantine mein chale jaate hain.

### Freshness: ek hi "in force" rule

Seedha-saada "current" flag use mat karo. Har jagah ek hi date rule use karo: koi chunk **kisi period mein in force** hai agar `effective_from` us period ke aakhiri din ya usse pehle ho, aur `effective_to` khaali ho ya period ke pehle din ya uske baad ho.

- **Default sawaal** ("how many leave days can I carry forward?"): period aaj hai, Asia/Kolkata time mein.
- **"What was the rule in 2024?"**: period 1 January se 31 December 2024 tak hai. 2023 se 2025 tak in force rahi policy waapas aati hai, bhale hi wo 2024 se pehle shuru hui aur ab superseded hai.
- **"What did the 2019 order say?"**: ye 2019 mein *jaari* hue order ke baare mein poochh raha hai, isliye `issued_on` ke saal se filter karo aur ye mat dekho ki wo abhi in force hai ya nahi.

Ek gotcha: December mein 1 January ke liye announce ki gayi policy abhi in force nahi hai. "Next year's policy" waale sawaal ke liye period agla saal hona chahiye, varna default rule use chhipa dega.

Jab naya version poore document ki jagah leta hai, toh puraane ko usi transaction mein band karo, taaki koi bhi search kabhi dono versions ek saath na dekhe, aur na aisa ho ki use ek bhi na dikhe:

```sql
BEGIN;
UPDATE chunks SET superseded_by = 'HR-LP-2026', effective_to = '2025-12-31'
WHERE doc_id = 'HR-LP-2025';
INSERT INTO chunks (...) VALUES (...);   -- the new version's chunks
COMMIT;
```

Filtering date rule karta hai. `superseded_by` isliye rakha jaata hai taaki jawaab keh sake "replaced by Leave Policy 2026".

### Partial amendments

Asli documents aksar ek baar mein ek hissa karke badalte hain. Koi sarkaari order keh sakta hai "in paragraph 4 of order 112/2019, for 'Rs 300' substitute 'Rs 450'", aur baaki har paragraph ko in force chhod deta hai. Poore document waala "superseded" flag ye baat nahi keh sakta. Puraane order ko superseded mark karo toh uske baaki paragraphs gaayab ho jaate hain; waise hi chhod do toh puraana rate jeetta rehta hai.

Amendments ko section level par model karo:

- Har chunk mein ek stable `section_id` ho (paragraph 4, clause 3.2).
- Ek amendments table `amending_doc`, `amended_doc`, `section_id` aur laagu hone ki date record kare.
- Jab amendment laagu ho, toh sirf amend hue section ka `effective_to` khatam karo, aur baaki ko chhod do.
- Query time par, jab koi base section retrieve ho, toh uske saare amendments bhi date ke kram mein fetch karo, aur model ko dono do.

Ye isliye zaroori hai kyunki koi bhi chunk akele kaam nahi karta. Amendment kehta hai "substitute 'Rs 450'" par ye nahi bataata ki kiski jagah; base paragraph puraana ho chuka hai. Jawaab ko dono cite karne chahiye: "order 112/2019, paragraph 4, as amended by order 37/2022". Agar vibhaag consolidated versions publish karta hai, toh unhein bhi index karo, par citations ke liye chain rakho.

Amendment links bhi nikaala gaya metadata hi hain. "in partial modification of" ya "in supersession of" jaise phrases, jinke baad order number aata hai, shuruaat ke achhe rules hain, par kisi bhi nikaale gaye field ki tarah inhein ek sample par check karo.

### Translations

Hindi order aur uski English copy do documents nahi, do languages mein ek hi document hain. Dono ko ek hi `doc_group` aur `section_id` do. Results mein har document group aur section ka ek hi chunk rakho, aur user ki language waali copy dikhao. Varna top five results mein do jagah ek hi paragraph ke do baar aane mein barbaad ho jaati hain. Jab dono mein farq ho toh vibhaag se poochho ki kaun-si copy authoritative hai, use record karo, aur usi ko cite karo.

### Permissions, sync mein rakhe hue

Chunks par user ids nahi, **group ids** store karo (`finance`, `all-employees`), aur filter search ke andar hi lagaao taaki mana kiya gaya chunk model tak kabhi na pahunche. Do syncs ke alag-alag schedules chahiye:

- **Document permissions** source system mein badalti hain (koi file dobaara share hoti hai). Inhein aksar re-sync karo, metadata update ke roop mein; text ko re-embed karne ki zaroorat nahi.
- **User groups** tab badalte hain jab log teams badalte hain. User ke groups query time par identity system se padho, ya unhein minuton ke liye cache karo, dinon ke liye nahi. Cached group list hi wajah hoti hai ki Finance chhod chuka koi insaan ab bhi Finance circulars dekhta rehta hai.

### Sawaal se filters

Kuch filters user ke profile se aate hain (unka state, unke groups). Baaki ka andaaza ek chhota model sawaal se lagaata hai. Galat inferred filter sahi jawaab chhipa deta hai, isliye inhein saavdhaani se lagaao:

```python
STATE_NAMES = {"KA": "Karnataka", "TN": "Tamil Nadu", "MH": "Maharashtra",
               "TS": "Telangana", "GJ": "Gujarat"}

class Filters(BaseModel):            # structured output from a small model
    state: Literal["KA", "TN", "MH", "TS", "GJ"] | None = None  # a real state, never ALL
    state_named: bool = False         # true only if the question names the state itself
    in_force_year: int | None = None  # "what was the rule in 2024?"
    issued_year: int | None = None    # "the 2019 order on transfers"
    doc_type: DocType | None = None

def in_force(start: date, end: date) -> dict:
    """In force at any time from start to end."""
    return {"effective_from": {"$lte": end},
            "$or": [{"effective_to": None}, {"effective_to": {"$gte": start}}]}

def build_filters(f: Filters, user, today: date):
    if f.state and f.state != user.state and not f.state_named:
        return None, f"Do you mean the {STATE_NAMES[f.state]} documents?"
    where = {"access_groups": {"$in": user.groups},           # never dropped
             "state": {"$in": [f.state or user.state, "ALL"]}}
    if f.in_force_year:
        y = f.in_force_year
        where |= in_force(date(y, 1, 1), date(y, 12, 31))
    elif f.issued_year:
        y = f.issued_year
        where["issued_on"] = {"$gte": date(y, 1, 1), "$lte": date(y, 12, 31)}
    else:
        where |= in_force(today, today)                       # default
    if f.doc_type:
        where["doc_type"] = f.doc_type
    return where, None
```

Filter syntax generic hai; ise apne vector store ke syntax mein badal lo. `today` ke taur par Asia/Kolkata ki date pass karo, server ki UTC date nahi. Agar filtered search kuch nahi lautaati, toh sirf access filter aur user ke state ke saath ek baar retry karo, jo bhi wo cite kare uski dates dikhao, aur khaali search ko log karo. Retry mein access filter kabhi mat hatao.

### Filters aur search ki speed

Filters approximate vector indexes par asar daalte hain. Misaal ke taur par pgvector mein filter default roop se index scan ke *baad* lagta hai. Uska documentation 10% rows se match hone waale filter ka example deta hai: HNSW index aur default `hnsw.ef_search` 40 ke saath, ausatan lagbhag 4 rows hi bachti hain, isliye aapko maange se kam results milte hain. Version 0.8.0 se aap iterative index scans chaalu kar sakte ho (`SET hnsw.iterative_scan = relaxed_order`), jo index ka aur hissa scan karte hain jab tak kaafi rows pass na ho jaayein ya scan limit (`hnsw.max_scan_tuples`) na aa jaaye, aur jis field mein bas kuch hi distinct values hon uske liye pgvector har value ka ek partial index sujhaata hai. Doosre stores alag tarah se kaam karte hain, isliye apna sabse selective filter (koi chhota state, koi rare document type) test karo aur check karo ki wo ab bhi poora top-k lautaata hai.

### Faayda check karo

Apne golden set par har addition (contextual text, generated questions, inferred filters) ke saath aur uske bina recall at 5 naapo, aur sirf wahi rakho jo madad kare. History aur doosre state waale sawaal bhi shaamil karo, kyunki filters wahin gadbad karte hain.

## Ek worked example

Bengaluru ki IT company ka HR assistant Karnataka, Tamil Nadu, Maharashtra, Telangana aur Gujarat ke employees ko serve karta hai. Leave aur holiday rules har state mein alag hain, aur policies har saal revise hoti hain.

**Pehle:** chunks mein sirf file name tha. Assistant Karnataka aur Maharashtra ki holiday lists mila deta tha aur kabhi-kabhi pichhle saal ki policy quote kar deta tha. Pehle fix ne ek `current = true` filter joda, aur phir "what was the carry-forward limit in 2024?" ne kuch bhi nahi lautaaya.

**Re-ingestion ke baad:** har chunk mein upar ki table waale fields hain. State aur groups employee ke sign-on profile se aate hain. Date rule default mein aaj ka hota hai; sawaal mein saal ka naam ho toh usi saal par chala jaata hai. Embed hone waala text title aur section path se shuru hota hai. Neeche ke numbers sirf ye dikhaane ke liye hain ki kis tarah ka badlaav ummeed karo, ye naapa hua result nahi hai:

| Maan lo, 100 golden questions par | Pehle | Baad mein |
| --- | --- | --- |
| Sahi jawaab | 71 | 90 |
| Galat state quote karne waale jawaab | 9 | 0 |
| Pichhle saal ki policy quote karne waale jawaab | 7 | 1 |
| Baaki galat jawaab | 13 | 9 |
| Citation format | Sirf file name | Document, state, section, page |

Ab citations aise dikhte hain: "Leave Policy 2026, Karnataka, section 3.2, page 4", aur HR staff unhein kuch hi seconds mein check kar sakta hai.

**Filter ke faisle kaise hote hain.** Bengaluru mein Priya poochhti hai "how many holidays in October?". Assistant uske profile se `state = KA` aur aaj in force waala rule lagaata hai. Phir wo poochhti hai "holidays in Pune office in October". Chhota model Pune ko Maharashtra se map karta hai, par usne state ka naam nahi liya, isliye `build_filters` ek sawaal lautaata hai: "Do you mean the Maharashtra documents?" Poochhne mein ek tap lagta hai; chupchaap lage galat filter ki keemat ek galat jawaab hai. Agar usne "Maharashtra holidays" type kiya hota, toh filter seedhe lag jaata.

Jab wo poochhti hai "what was the carry-forward limit in 2024?", toh model `in_force_year = 2024` lautaata hai. 2023 se 2025 waali policy, jo January 2026 se superseded hai, date rule se match karti hai aur "replaced by Leave Policy 2026" note ke saath waapas aati hai.

## Aam galtiyaan

- **Sirf file name.** Aap na filter kar sakte, na theek se cite kar sakte, na versions sambhaal sakte.
- **Free-text metadata values.** "HR", "Human Resources" aur "hr dept" filters tod dete hain. Fixed lists use karo aur unhein validate karo.
- **Aisi vocabulary jismein koi asli value chhoot jaaye.** Ek bhoola hua state uske saare documents quarantine kar deta hai, ya usse bhi bura, unhein bina state ke index kar deta hai.
- **Har search par "current only" filter.** Tab history waale sawaal kuch nahi lautaate. Sawaal jis period ke baare mein hai uske saath in-force rule use karo.
- **Partial amendments ke liye poore document ka supersession.** Ye ya toh abhi in force paragraphs chhipa deta hai ya puraani values rakh leta hai. Amendments ko har section ke hisaab se track karo.
- **Translations ko alag documents maanna.** Duplicate paragraphs baaki results ko baahar dhakel dete hain.
- **Zabardasti waale inferred filters.** User ke profile ko tarjeeh do, aur agar inferred filter use badalta hai toh poochh lo.
- **Aisa fallback jo access filter hata de.** Khaali result se kabhi ye nahi badhna chahiye ki user kya dekh sakta hai.
- **Puraani group lists.** Access query time par user ke groups se tay hota hai, isliye unhein taaza padho.
- **Bina naape metadata generate karna.** Ismein har chunk par ek model call lagti hai; saabit karo ki ye madad karta hai.

## Jab thoda metadata kaafi hai

- **Ek chhota, ek hi topic waala collection**, jismein har document ka ek hi version ho.
- **Har koi sab kuch dekh sakta hai**, aur kuch bhi puraana nahi padta.
- **Ek prototype** jo ye test kar raha hai ki retrieval madad karta bhi hai ya nahi.

Tab bhi document id, section aur page store karo: citations ko inki zaroorat hai, aur inki koi cost nahi. Rich metadata tab faayda deta hai jab bahut saare document types, versions, regions ya permission groups hon.

## Demo se production tak

- Jab bhi parser ya document format badle, **nikaale gaye fields ko ek sample par haath se check karo**.
- Har search par **lage filters ko log karo**, inferred filters aur fallbacks samet.
- **Permissions ko re-sync karo** unke apne schedule par, re-embedding se alag.
- Content owners ke saath **vocabularies review karo** (states, document types, departments).

## Practice

Metadata extraction par LlamaIndex ka page aur Microsoft ka security filter pattern padho.

1. Apne RAG documents ko dobaara ingest karo, har chunk par title, section id aur path, type, dates, language aur access groups ke saath.
2. Embed hone waale text ke aage title aur section path jodo aur pehle aur baad ka recall at 5 compare karo.
3. Kisi document ko ek puraana version do jo pichhle saal khatam hua. Dikhao ki default sawaal ko naya version milta hai aur pichhle saal ka naam lene waale sawaal ko puraana.
4. Kisi document ke ek section ko doosre document se amend karwaao. Dikhao ki jawaab dono ko cite karta hai.
5. Jaanboojhkar kharaab metadata waale paanch chunks `ChunkMeta` se guzaaro aur confirm karo ki har ek saaf error ke saath quarantine mein pahunchta hai.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly, 2025) ka chapter 6 RAG ko cover karta hai, chunking aur chunks mein context jodne samet.

**Aapka kaam poora hai jab aap** ek precise citation waala jawaab, puraana version lautaane waala ek history sawaal, aur ek aisa sawaal dikha sako jahaan metadata filter ne galat jawaab ko theek kiya.
