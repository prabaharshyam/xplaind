## Ye kya hai

Standard RAG sawaal se milte-julte passages retrieve karta hai. Do tarah ke sawaal ise haraate hain:

- Links follow karne waale **multi-hop sawaal**: "Delay hue Chennai metro package ke contractor ke saath kaun se projects share karte hain?" Facts alag-alag documents mein hain aur koi ek passage sawaal se milta-julta nahi hai.
- Poori collection ke baare mein **global sawaal**: "Pichhle saal ki customer complaints mein baar-baar aane waali problems kya hain?" Kisi ek passage mein answer nahi hai; woh kai se ubharta hai.

**Graph RAG** ek **knowledge graph** jodta hai: entities (log, companies, products, jagahein, events) nodes ke roop mein aur unke beech ke relationships edges ke roop mein, documents se nikale hue. Phir retrieval relationships follow kar sakta hai aur related entities ke groups ke pehle se likhe summaries use kar sakta hai. Microsoft ka open-source GraphRAG ek jaana-maana implementation hai; Neo4j jaise graph databases doosra raasta hain.

```flow
Documents -> Chunks -> Model entities aur relationships nikaalta hai -> Knowledge graph
Knowledge graph -> Communities dhoondhi aur summarise ki jaati hain
Sawaal -[local search]-> Entities + neighbours + source chunks
Sawaal -[global search]-> Community summaries par map, phir reduce
```

```flow
dir: LR
title: Graph ka ek hissa
Project: Metro Pkg 4 | overrun 27% -[contractor]-> ABC Infra
ABC Infra -[also on]-> Project: Pune Ring Road
ABC Infra -[sub-contracts to]-> XYZ Steel
```

Is lesson mein hum Mumbai ki ek infrastructure finance company ko follow karenge, jiske analysts aise sawaal poochte hain jo sau-sau project documents tak failte hain.

## Ye kaam kaise karta hai

**Indexing (GraphRAG style).**

1. Documents ko hamesha ki tarah chunk karo.
2. Har chunk se entities aur relationships, chhoti descriptions ke saath ("ABC Infra, contractor; Package 4 ke liye steel supply karta hai"), nikaalne ke liye ek model use karo.
3. Duplicates ko merge karo ("ABC Infra Ltd" aur "ABC Infrastructure").
4. **Communities** dhoondho: kareeb se jude entities ke clusters.
5. Har community ka summary ek model se kai level of detail par likhwao.

**Querying.**

- Khaas entities ke baare mein sawaalon ke liye *local search*: sawaal ki entities dhoondho, unke neighbours, relationships aur source chunks jama karo, aur usi se answer do.
- Poori collection ke sawaalon ke liye *global search*: sawaal ko community summaries par map karo, phir adhoore answers ko ek mein reduce karo.

**Kharche.** Indexing har chunk aur har community par ek model call karti hai, isliye sirf embedding se kai guna zyada kharcha ho sakta hai, aur documents badalne par ise dobara chalana ya update karna padta hai. Entity extraction galtiyan karta hai; merges aisi cheezein jod sakte hain jo alag rehni chahiye. Queries, khaaskar global wali, bahut tokens use karti hain.

**Kab kaam ka hai.** Aisi collections jo entities aur relationships se bhari hon (contracts, investigations, research literature, supplier networks, case files), jahan multi-hop ya global sawaal aksar aur keemti hon. Zyadatar FAQ-style ya policy-lookup assistants ke liye achhi metadata ke saath hybrid search sasta aur kaafi hai.

**Halke alternatives.** Nikaale hue entities ko metadata ki tarah store karo aur unpar filter karo; key relationships ki ek chhoti structured table rakho; document groups ke summaries generate karo. Aksar ye zyadatar fayda de dete hain.

**Standard RAG versus Graph RAG:**

| Pehlu | Hybrid RAG | Graph RAG |
| --- | --- | --- |
| Single-document sawaal | Strong | Behtar nahi |
| Multi-hop sawaal | Weak | Strong |
| Poori collection ke sawaal | Weak | Community summaries ke saath strong |
| Indexing cost | Sirf embeddings | Har chunk aur community par model calls |
| Updates | Badle chunks ko dobara embed | Dobara extract aur dobara merge |
| Failure risk | Chhoote hue passages | Galat extractions aur merges |

**Dono ke beech routing.** Kam teams hybrid RAG ko replace karti hain; woh un sawaalon ke liye ek graph jodti hain jinka jawab hybrid nahi de sakta. Ek chhota classifier, ya ek model call, tay karta hai ki sawaal entities ke beech relationships ki baat karta hai ("kaun se contractors ... par bhi kaam karte hain", "aur kaun ... se juda hai") ya poori collection ke baare mein hai ("baar-baar aane waale ..."). Woh graph search par jaate hain; baaki sab hybrid RAG par. Har sawaal ka route log karo, taaki test set par router ki galtiyan check kar sako.

**Citations rakhna.** Har entity, relationship aur community summary ko un chunks ke links rakhne chahiye jinse woh bana. Phir answers asli documents ko cite kar sakte hain, aur analysts check kar sakte hain ki koi nikaala hua relationship sach mein likha hai ya extraction ke dauraan gadh liya gaya.

**Code mein ek chhota graph.** Model se triples (structured output ke roop mein) nikalo, NetworkX mein load karo, aur neighbourhoods se local sawaalon ke jawab do:

```python
import networkx as nx
from pydantic import BaseModel

class Triple(BaseModel):
    subject: str
    relation: str
    object: str

class Extraction(BaseModel):
    triples: list[Triple]

def normalise(name):
    n = name.lower().replace("limited", "ltd").replace("infrastructure", "infra")
    return " ".join(w for w in n.replace(".", "").split() if w not in {"ltd", "pvt", "private"})

def build_graph(chunks, extract):
    """extract(text) -> Extraction, via structured output from a model."""
    g = nx.MultiDiGraph()
    for c in chunks:
        for t in extract(c["text"]).triples:
            s, o = normalise(t.subject), normalise(t.object)
            g.add_node(s, label=t.subject); g.add_node(o, label=t.object)
            g.add_edge(s, o, relation=t.relation, source=c["id"])
    return g

def local_context(g, entities, hops=2, limit=40):
    nodes = set()
    for e in map(normalise, entities):
        if e in g:
            nodes |= set(nx.ego_graph(g.to_undirected(as_view=True), e, radius=hops))
    facts = [f'{g.nodes[u]["label"]} —{d["relation"]}→ {g.nodes[v]["label"]} [{d["source"]}]'
             for u, v, d in g.subgraph(nodes).edges(data=True)]
    return facts[:limit]
```

Facts ke saath unke source chunk ids bhi aate hain, isliye answer asli documents ko cite kar sakta hai. `normalise` rules entity resolution ki ek kachchi shuruaat hain; zaroori entities ke liye merges haath se check karo, aur un naamon ki ek list rakho jinhe kabhi merge nahi karna.

**Global sawaalon ke liye communities.** Kareeb se jude entities ko group karo aur har group ko ek baar summarise karo:

```python
from networkx.algorithms.community import louvain_communities

def communities(g, seed=7):
    groups = louvain_communities(g.to_undirected(), seed=seed)
    return sorted(groups, key=len, reverse=True)
```

Ek model har community ka summary likhta hai (un chunk ids ke saath jinse usne liya). "Saare packages mein baar-baar aane waale delay ke kaaran kya hain?" jaise sawaal ke liye, har community summary se ye sawaal poochho, phir adhoore answers ko jodo.

**Graph par bharosa karne se pehle extraction check karo.** 50 nikaale hue triples ka sample lo aur har ek ko mark karo: source mein likha hai, implied hai, ya galat hai. Agar kuch percent se zyada galat hain, toh uske upar kuch bhi banane se pehle extraction prompt behtar karo (allowed entity types aur relations do).

**Pehle indexing ka bill estimate karo.** Chunks × (extraction prompt + chunk + output tokens) gino, plus har community ke liye ek summary call. Collection ke 5% par chalao, naapo, aur poori cheez karne se pehle guna karo.

## Ek example se samjho

Mumbai ki ek infrastructure finance company hazaaron project reports, contractor agreements aur site inspection notes review karti hai. Analysts aise sawaal poochte hain jaise "20% se zyada cost overruns waale projects mein kaun se contractors dikhte hain, aur woh aur kahaan kaam karte hain?"

Hybrid RAG single-project sawaalon ka achha jawab deta hai par ye nahi sambhaal paata: facts sau-sau documents mein bikhre hain.

Ek pilot 3,000 documents se projects, contractors, sub-contractors, locations aur inspection findings ka graph banata hai. Indexing ka kharcha embedding-only pipeline se lagbhag 25 guna hai, ek baar ka kharcha plus weekly updates. Entity merging ke liye company name variants ki haath se banayi list chahiye, kyunki ek hi contractor kai spellings mein dikhta hai.

Multi-hop aur global sawaalon ke 40-sawaal test set par graph approach 70% ka achha jawab deta hai, hybrid RAG 30%. Single-document sawaalon par woh behtar nahi hai. Company dono rakhti hai: sawaal jab projects ke beech relationships ki baat karein toh graph search par jaate hain, warna hybrid RAG par.

| Measure | Hybrid RAG | Graph approach |
| --- | --- | --- |
| 40 mein se multi-hop aur global sawaal jinka achha jawab mila | 30% | 70% |
| Single-document sawaal | Achha | Behtar nahi |
| Indexing cost | Baseline | Lagbhag 25 guna, plus weekly updates |
| Extra kaam | Koi nahi | Contractor name variants ki haath se banayi list |

## Aam galtiyaan

- **Simple lookups ke liye Graph RAG.** Bina fayde ke kharcha badhata hai.
- **Entity resolution ko ignore karna.** Duplicate ya galat merge hue entities unhe use karne waale har answer ko bigaad dete hain.
- **Updates bhool jaana.** Ek baar bana graph purana ho jaata hai.
- **Koi comparison nahi.** Jo sawaal matter karte hain unpar hybrid RAG ke saamne naapo.
- **Citations kho dena.** Entities aur summaries se source chunks tak wapas links rakho.
- **Nikaale hue relationships par bharosa karna bina unka source text se sample check kiye.**
- **Free-form relation names.** Extractor ko ek fixed list do, warna graph lagbhag-duplicates se bhar jaata hai.
- **Poori collection ko index karne se pehle cost estimate chhod dena.**

## Kab Graph RAG kaam ka nahi

- **Sawaal zyadatar ek document ya ek fact ke baare mein hain**: hybrid RAG unhe sasta jawab deta hai.
- **Documents lagataar badalte rehte hain**, jisse re-extraction mehenga ho jaata hai.
- **Kam entities aur relationships matter karte hain**: logon dwara maintain ki hui key facts ki ek chhoti table kaafi ho sakti hai.

## Demo se production tak

- Har entity, relationship aur summary par **source chunk ids rakho.**
- Har prompt ya model change ke baad ek sample par **extraction accuracy naapo.**
- **Incrementally update karo**: badle documents ko dobara extract karo aur community summaries ko schedule par dobara chalao.
- Graph aur hybrid search ke beech **sawaalon ko route karo**, aur route log karo.
- **Indexing aur query cost** ko ordinary RAG se alag **track karo.**
