## Ye kya hai

Jin bhi companies ke saath aap kaam karoge, lagbhag sab apne customers, orders, tickets aur payments kisi relational database mein rakhti hain, jaise PostgreSQL, MySQL ya SQL Server. **SQL** woh bhasha hai jisse in databases se sawaal puchhe jaate hain. AI engineer ke liye SQL optional nahi hai. Aap ise in kaamon mein use karte ho:

- AI system ko chahiye woh **data nikaalna**, jaise purane tickets aur unke resolutions;
- Kuch banane se pehle **baseline naapna**: "Aaj refunds mein kitna samay lagta hai?";
- System chalu hone ke baad **check karna ki usse fayda hua ya nahi**.

Is kaam ka zyadatar hissa chaar ideas se nikal jaata hai:

| Idea | Kya karta hai | Aam use |
| --- | --- | --- |
| **Joins** | Tables ko matching column par jodte hain | Orders aur unke customers ke cities |
| **GROUP BY** | Har group ki ek row, totals ya averages ke saath | Har city mein refunds |
| **Window functions** | Related rows par calculate karte hain, har row bani rehti hai | Har customer ka pehla ticket; moving averages |
| **Indexes** | Lookups tez karte hain | 40 seconds ki query ko 2 seconds ka banana |

```flow
dir: LR
title: Matching ids par join karke "har city mein refunds" ka jawab
refunds | id, order_id, created_at -[order_id = orders.id]-> orders | id, customer_id
orders -[customer_id = customers.id]-> customers | id, city
```

Is lesson mein hum Hyderabad ki ek food delivery company ke saath chalenge, jab aap AI assistant banane se pehle uska refund baseline naapte ho. Lesson ke end tak aap joins, grouping aur window functions se business sawaalon ke jawab nikaal paoge, aur slow query ko tez kar paoge.

## Ye kaam kaise karta hai

### Joins

Join tables ko ek matching column par jodta hai.

| Join | Kya rakhta hai | Kab use karein |
| --- | --- | --- |
| `JOIN` (inner) | Sirf woh rows jo dono taraf match karein | Jin orders ka customer hai |
| `LEFT JOIN` | Left table ki har row; jahan right mein match na ho wahan khaali | Bina orders wale customers; bina reply wale tickets |

```sql
-- customers who have never ordered
SELECT c.id, c.city
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

### GROUP BY

`GROUP BY` rows ko har group ki ek row mein samet deta hai aur aggregates nikaalta hai: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. Rows ko grouping se **pehle** `WHERE` se filter karo; groups ko **baad** mein `HAVING` se:

```sql
SELECT city, COUNT(*) AS refunds
FROM refunds r JOIN orders o ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY city
HAVING COUNT(*) > 100;
```

### Window functions

Window functions related rows par calculate karte hain, unhe samete **bina**:

| Function | Example | Kya deta hai |
| --- | --- | --- |
| `ROW_NUMBER()` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | Har customer ki rows ko time ke kram mein 1, 2, 3 |
| `LAG(col)` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | Pichhli row ki value, row-to-row comparison ke liye |
| `SUM(col)` | `OVER (ORDER BY day)` | Running total |
| `AVG(col)` | `OVER (ORDER BY day ROWS 6 PRECEDING)` | Saat din ka moving average |

`PARTITION BY` rows ko `GROUP BY` ki tarah groups mein baantta hai, par har row result mein bani rehti hai.

### Indexes aur query plans

Index ke bina database matches dhoondhne ke liye har row padhta hai: ise **sequential scan** kehte hain. `refunds(created_at)` par index ho, toh woh seedhe sahi rows par pahunch jaata hai.

```flow
dir: LR
title: 3 crore rows mein se July ke refunds dhoondhna
Index nahi -> saari 30,000,000 rows padho, 2,000,000 rakho -> 40 s
created_at par index -> 1 July par jao, aage padhte jao -> 2 s
```

Indexes reads tez karte hain aur writes ko thoda dheema, isliye unn columns par lagao jin par aap sabse zyada filter aur join karte ho. Kisi query ke aage `EXPLAIN ANALYZE` lagao, jo use chalata bhi hai, taaki dikhe ki database ne index use kiya ya poora table scan kiya, aur har step mein kitna samay laga.

## Ek example se samjho

Hyderabad ki ek food delivery company refund requests ke liye AI assistant chahti hai. Kuch bhi banane se pehle aapko baseline chahiye: aaj refund mein kitna samay lagta hai, city ke hisaab se?

```sql
SELECT c.city,
       COUNT(*) AS refunds,
       ROUND(AVG(EXTRACT(EPOCH FROM r.resolved_at - r.created_at) / 3600), 1) AS avg_hours
FROM refunds r
JOIN orders o    ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY c.city
ORDER BY avg_hours DESC;
```

Ab assistant ke training examples ke liye aapko har customer ki sirf **pehli** refund request chahiye, taaki baar-baar shikayat karne wale haavi na ho jaayein:

```sql
SELECT *
FROM (
  SELECT r.*,
         ROW_NUMBER() OVER (PARTITION BY o.customer_id ORDER BY r.created_at) AS n
  FROM refunds r JOIN orders o ON o.id = r.order_id
) t
WHERE n = 1;
```

**Slow query.** Baseline query 3 crore rows par 40 seconds leti hai. `EXPLAIN ANALYZE` mein date filter ke liye `refunds` par sequential scan dikhta hai. Aap client ki data team se kehte ho, jo kisi shaant samay par primary database par `CREATE INDEX CONCURRENTLY ON refunds (created_at)` chalati hai; phir woh index us read replica tak pahunchta hai jis par aap query karte ho. Ab query do seconds se kam mein chalti hai.

| City | July se refunds | Resolve hone ke ausat ghante |
| --- | --- | --- |
| Hyderabad | 48,200 | 31.4 |
| Vijayawada | 9,800 | 27.9 |
| Warangal | 4,100 | 22.6 |

Aap numbers aur query times apne notes mein likh lete ho. Ye table woh baseline hai jise aapke assistant ko haraana hai, aur index ek quick win hai jisse client ki data team ke saath achha rishta banta hai.

## Aam galtiyaan

- **Join karke multiply kar dena.** Orders ko order items se join karke order totals ka sum lene par har order apne items ki ginti ke barabar baar gina jaata hai. Join se pehle sahi level par aggregate karo.
- **Jahan left join chahiye tha wahan inner join.** Bina orders wale customers report se chupchaap gaayab ho jaate hain.
- **WHERE mein aggregates filter karna.** `WHERE COUNT(*) > 5` fail hota hai; `HAVING` use karo.
- **Production database par bhaari queries chalana.** Read replica ya export maango. Client ka live app dheema kar dena pehle hafte ki buri shuruaat hai.
- **Har cheez par index lagana.** Har index storage aur write speed ka kharcha leta hai. Asli slow queries ke liye lagao, aur `EXPLAIN ANALYZE` se confirm karo.
- **Dates ki tulna text se karna.** Sahi date types aur `DATE '2026-07-01'` jaise literals use karo.
