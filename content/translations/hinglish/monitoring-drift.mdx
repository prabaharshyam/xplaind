## Ye kya hai

Model monitoring chaar layers dekhti hai:

- **Service health**: kya model chal raha hai? Latency, errors, throughput.
- **Data quality aur input drift**: kya inputs ab bhi valid hain aur training data jaise hain? Missing values, nayi categories, shift hui distributions.
- **Prediction drift**: kya scores ya predicted classes ki distribution badal gayi hai?
- **Performance**: jab sachche outcomes aate hain, kya accuracy wahin hai jahan thi, overall aur segment ke hisaab se?

**Data drift** ka matlab inputs badal gaye; **concept drift** ka matlab inputs aur outcomes ke beech ka relationship badal gaya (wahi features ab alag tarah predict karte hain, jaise fraud patterns badalne par).

| Layer | Kya check hota hai | Kya pakadta hai |
|---|---|---|
| Service health | Latency aur errors, har minute | Outages |
| Inputs | Schema, missing rates, baseline ke saath har feature ka drift, roz | Upstream bugs, naye data shapes |
| Predictions | Partner aur city ke hisaab se approval rate, roz | Behaviour mein achanak badlaav |
| Performance | Labels aate hi mahine aur segment ke hisaab se default rate | Dheera decay, concept drift |

```flow
dir: LR
Alert -> Owner -> Runbook
Runbook -> Investigate
Runbook -> Fallback
Runbook -> Roll back
Runbook -> Retrain
```

Ye lesson Bengaluru ki ek buy-now-pay-later company ko follow karta hai jiska credit model checkout par chhote loans approve karta hai.

## Ye kaam kaise karta hai

**Baselines.** Training aur validation data ke summary statistics save karo (har feature ki distributions, score distributions, segment shares). Monitoring live data ko inse compare karti hai.

**Data checks.** Schema checks (types, allowed values), missing-value rates, aur har feature ke drift scores, jaise population stability index ya statistical distance measures. Un features ko flag karo jinki distribution threshold se aage khisak jaaye.

**Prediction checks.** Har predicted class ka share, average score, action threshold se upar ka share. Achanak jump aksar kisi bhi outcome ke aane se pehle upstream bug ka sanket hota hai.

**Der se aane wala ground truth.** Outcomes aksar der se aate hain: loan default 90 din baad, churn ek mahine baad. Labels aate hi performance track karo, aur tab tak proxies (complaints, overrides, early repayment behaviour) use karo.

**Segments.** Region, channel, product aur customer type ke hisaab se track karo; drift aksar ek segment mein shuru hota hai.

**Alerts aur response.** Har drift par action ki zaroorat nahi hoti. Severity ke saath thresholds define karo: investigate, retrain, roll back, ya fallback par switch. Alerts ko runbook ke saath ek owner tak route karo.

**Retraining policy.** Schedule par retrain karo (maheene mein), trigger par (drift ya performance drop), ya dono. Har retrain kiya model pehle model jaise hi evaluation aur promotion checks se guzarta hai, maujooda production model se comparison samet.

**Feedback loops.** Models us data ko badal sakte hain jisse woh baad mein seekhte hain: transactions block karne wale fraud model ka matlab hai aapko kabhi pata nahi chalta ki woh fraud the ya nahi. Unbiased labels ke liye ek chhota random holdout ya human review sample rakho.

**Severities ke saath alert thresholds:**

| Signal | Threshold | Severity | Response |
| --- | --- | --- | --- |
| Error rate | 5 minute tak 1% se upar | High | On-call ko page karo; service check karo |
| Feature missing rate | Baseline ke mukable double | Medium | Source ki jaanch karo |
| Partner ke hisaab se approval rate | Ek din mein 10 points se zyada badlaav | High | Inputs check karo; zaroorat ho toh fallback model |
| Kisi key feature par drift score | 3 din tak agreed limit se upar | Medium | Review karo; retrain ka socho |
| Segment ke hisaab se default rate | Do mahine plan se upar | Medium | Recent data se retrain karo |

**Drift score padhna.** Population stability index compare karta hai ki kisi feature ki values training data aur live data mein buckets mein kaise girti hain. Chhoti values ka matlab thoda badlaav; badi values ka matlab asli shift. Ise ek pointer maano, verdict nahi: jis feature ko model bahut kam use karta hai usme shift maayne na rakhe, jabki uske sabse zaroori feature mein chhota shift maayne rakh sakta hai. Action se pehle drift ke saath feature importance bhi check karo.

**Runbook likhna.** Har alert ke liye likho ki owner kaun hai, pehli teen cheezein jo check karni hain, fallback par kaise switch karna hai, aur roll back kab karna hai. Fallback ko ready aur tested rakho, jaise bina pareshaan karne wale feature ke ek simple model ya rules policy, taaki containment minutes mein ho jaye.

**Code mein population stability index.** Training data par ek feature ko buckets mein baanto, phir live data ko usi buckets mein compare karo:

```python
import numpy as np

def psi(expected, actual, buckets=10):
    edges = np.unique(np.quantile(expected, np.linspace(0, 1, buckets + 1)))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

def drift_report(train_df, live_df, features, warn=0.1, alert=0.25):
    rows = []
    for f in features:
        value = psi(train_df[f].dropna(), live_df[f].dropna())
        missing_change = live_df[f].isna().mean() - train_df[f].isna().mean()
        level = "alert" if value > alert else "warn" if value > warn else "ok"
        rows.append((f, round(value, 3), f"{missing_change:+.1%}", level))
    return sorted(rows, key=lambda r: -r[1])
```

Common rules of thumb PSI 0.1 se neeche ko stable aur 0.25 se upar ko bada shift maante hain, par thresholds model owner ke saath tay karo aur pichhle mahino se check karo. Evidently jaisi libraries charts ke saath aisi hi reports banati hain.

**Segment ke hisaab se prediction rates.** Upstream bugs aksar pehle kisi ek partner ya region ke positive predictions ke share mein jump ke roop mein dikhte hain:

```python
def rate_alerts(today, history, min_change=0.10):
    """today/history: dict segment -> approval rate; history holds the 30-day average."""
    return {s: (history[s], r) for s, r in today.items()
            if s in history and abs(r - history[s]) > min_change}
```

**Imaandaar outcomes ke liye ek holdout.** Agar model transaction block karta hai, toh aapko kabhi pata nahi chalta ki woh fraud tha ya nahi. Ek chhota random hissa (business aur risk teams ke saath tay kiya hua, aksar 1% se bahut kam) model ke decision ko chhod kar normal handling ya human review mein jaane do, aur outcome record karo:

```python
import random

def decide(txn, model_score, threshold=0.8, holdout_rate=0.005):
    if random.random() < holdout_rate:
        return {"action": "review", "holdout": True}       # outcome measured without the model's influence
    return {"action": "block" if model_score > threshold else "allow", "holdout": False}
```

Holdout par precision aur recall naapo ye dekhne ke liye ki duniya badalne par model asli mein kaisa kar raha hai.

Hindi sawaalon ka badhta share ya naya topic cluster aisa drift hai jise naye documents ya prompt changes chahiye ho sakte hain, retraining nahi.

## Ek example se samjho

Bengaluru ki ek BNPL (buy now, pay later) company ka credit model checkout par chhote loans approve karta hai.

Monitoring dashboard aur alerts:

- Service: p95 latency aur error rate.
- Inputs: training baseline ke mukable 40 features ke roz drift scores; har partner ke payloads par schema checks.
- Predictions: partner aur city ke hisaab se approval rate.
- Performance: outcomes aate hi approval month aur segment ke hisaab se 60-din default rate.

March mein, ek bade e-commerce partner ka approval rate raaton-raat 61% se 79% tak uchhal jata hai. Input drift dikhata hai ki us partner ke liye "device age" feature zero par ghir gaya: unke app update ne use bhejna band kar diya, aur model ne zero ko "bilkul naya device" padha, jo ek low-risk signal hai. Team do ghante ke andar us partner ko bina us feature ke fallback model par switch kar deti hai, aur partner apna payload theek karta hai.

Alag se, chaar mahine mein tier-3 cities ke first-time borrowers mein defaults ka dheere-dheere badhna recent data aur pehle ke chhote loans par repayment behaviour ke ek naye feature ke saath retraining trigger karta hai. Retrain kiya model promotion checks paas karta hai aur shadow aur canary stages se roll out hota hai.

Borderline applicants ka 2% random sample score ki parwah kiye bina approve hota hai, taaki company un applicants ke baare mein seekhti rahe jinhe model warna reject kar deta.

| Event | Kisse pakda gaya | Response | Samay |
| --- | --- | --- | --- |
| Partner approvals 61% se 79% tak uchhle | Approval-rate alert, phir input drift | Us partner ke liye fallback model | Do ghante |
| Tier-3 first-time borrowers zyada default kar rahe | Chaar mahine mein segment ke hisaab se performance | Naye feature ke saath retrain, shadow phir canary | Hafte |

## Aam galtiyaan

- **Sirf uptime monitor karna.** Chalta hua model bhi bahut galat ho sakta hai.
- **Baselines na hona.** Drift ke liye compare karne ko kuch chahiye.
- **Har chhote drift par alert karna.** Thresholds aur severities set karo, warna alerts ignore ho jaate hain.
- **Problems pakadne ke liye labels ka intezaar karna.** Inputs aur predictions roz dekho.
- **Feedback loops ko ignore karna.** Seekhne ke liye unbiased samples rakho.
- **Har PSI wobble par alert karna**, jo logon ko alerts ignore karna sikha deta hai.
- **Holdout na hona**, isliye outcomes sirf unhi cases ke hote hain jinhe model ne allow kiya.
- **Sirf inputs monitor karna**, segment ke hisaab se prediction rates nahi.

## Jab halki monitoring theek ho

- **Ek baar ke analysis ke liye use hua model.**
- **Kam asar waali recommendations** jahan log hamesha decide karte hain, aur errors sasti hain.
- **Stable inputs**, jaise kisi controlled process mein ek fixed sensor, jahan error aur range checks zyadatar problems pakad lete hain.

## Demo se production tak

- **Har model version ke saath baselines save karo.**
- **Drift aur segment reports roz chalao**, agreed thresholds aur owners ke saath.
- **Ek random holdout rakho** jahan decisions outcomes ko chhupa dete hain, business ke saath tay karke.
- **Labels aate hi performance track karo**, segment ke hisaab se.
- **Har alert ke liye fallback aur rollback steps ke saath runbooks likho.**
