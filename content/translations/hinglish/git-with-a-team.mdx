## Ye kya hai

Git codebase ke har change ko record karta hai. Akele kaam karte waqt aap zyadatar commit aur push karte ho. Team mein **main** branch shared hoti hai aur hamesha kaam karti honi chahiye, kyunki doosre log, aur aksar ek live product, uspar depend karte hain. Isliye teams ek routine follow karti hain:

```flow
dir: LR
main | always works -> Your branch | small commits
Your branch -[push]-> Pull request | review and automated checks
Pull request -> Teammates comment, you fix -> Pull request
Pull request -[merge]-> main, updated
```

1. Kaam ke ek hisse ke liye ek **branch** banao.
2. Saaf messages ke saath chhote **commits** karo.
3. Push karo aur ek **pull request** (PR) kholo.
4. Teammates **review** karte hain; automated checks chalte hain.
5. Jo flag ho use fix karo, phir **merge** karo.

Jab do log same lines badalte hain, Git **merge conflict** uthata hai, aur ek insaan result decide karta hai.

Ye lesson aapke saath chalta hai, Mumbai ki ek brokerage ke project ke teen hafte baad, jab aap ek market-data client mein retries jodte ho, review hote ho aur ek teammate ke change ke saath conflict resolve karte ho. End tak aap har step mein comfortable ho jaoge.

## Ye kaam kaise karta hai

### Branches

Branches ek commit ki taraf point karne waale sasta labels hain. `git switch -c fix/gst-rounding` ek banata hai aur aapko uspar le jaata hai. Branches ka naam unke kaam ke hisaab se rakho:

| Prefix | Kis liye | Example |
| --- | --- | --- |
| `feat/` | Naya feature | `feat/retry-market-data` |
| `fix/` | Bug fix | `fix/gst-rounding` |
| `docs/` | Documentation | `docs/setup-guide` |
| `chore/` | Tooling, dependencies | `chore/update-pandas` |

Apni pehli branch se pehle client ka naming convention check karo.

### Commits

Har commit ek hi kaam kare aur bataye kyun:

| Weak | Strong |
| --- | --- |
| "fix" | "Fix GST rounding to two decimals for invoices over ₹1 lakh" |
| "wip" | "Add retry wrapper for market data client (no callers yet)" |
| "changes" | "MD-214: retry market data calls with backoff on 429 and 503" |

Kai teams messages ke aage ticket id lagati hain. Chhe mahine baad, saaf history hi wo tareeka hai jisse koi bhi, aap bhi, samajh sakta hai ki code aisa kyun dikhta hai.

### Pull requests

Ek PR reviewer ko chahiye context saath leke chalti hai:

- **Kya** badla aur **kyun**.
- Aapne use **kaise test** kiya.
- **Koi risky cheez**: performance, security, behaviour changes.
- Ticket ka link, aur jo bhi dikhta hai uske liye screenshots.

PRs chhote rakho. 200-line ki PR ka review dhyaan se hota hai; 3,000-line ki PR par rubber stamp lagta hai aur bugs chhup jaate hain.

### Review dono taraf chalta hai

**Review karte waqt**, style se pehle behaviour aur risk dekho: kya ye sahi kaam karta hai, kya tootega, kya test hua hai? **Review hote waqt**, har comment ka jawab do, ya toh code badal kar ya samjha kar ki kyun nahi, aur kabhi personally mat lo. Review code ke baare mein hai, aapke baare mein nahi.

### Current rehna aur conflicts resolve karna

Jab aapki PR intezaar kar rahi hai, main aage badhta rehta hai. Naya main apni branch mein `git merge main` se laao, ya agar team rebase pasand karti hai toh `git rebase main`. Agar dono taraf same lines badli hain, toh Git file mein conflict mark karta hai:

```text
<<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = Decimal("0.18")
>>>>>>> main
```

Upar ka hissa aapki branch hai; neeche main hai. (Rebase ke dauran sides ulte ho jaate hain: HEAD main hota hai aur neeche aapka commit.) Aap file ko sahi **final** version mein edit karte ho, jo aksar dono ko milata hai, markers hatate ho, tests chalate ho, phir `git add` aur commit karte ho.

### Protected branches aur history

Clients aksar main ko **protect** karte hain: seedha push nahi, review aur passing checks chahiye. Isse kabhi bypass mat karo. Aur jo branch koi aur use kar raha ho use kabhi **force-push** mat karo: ye unke paaon ke neeche se history rewrite karta hai aur unka kaam kho sakta hai.

### Secrets

Git mein commit hui API key file delete karne ke baad bhi history mein rehti hai. Secrets ko environment variables mein rakho, secret files ko `.gitignore` mein list karo, aur agar kabhi key leak ho jaaye toh **turant rotate karo**, phir clean up karo.

## Ek worked example

Aap Mumbai ki ek brokerage ke saath ek project mein teen hafte ho chuke ho. Aapka ticket, MD-214: market-data client mein retries jodna, jo market open par kabhi-kabhi rate-limit ho jaata hai.

```text
git switch main && git pull
git switch -c feat/retry-market-data
# edit, test
git add src/marketdata/client.py tests/test_client.py
git commit -m "MD-214: retry market data calls with backoff on 429 and 503"
git push -u origin feat/retry-market-data
```

**PR.** Aapka description batata hai ki kya badla, ki aapne ek fake server se test kiya jo do baar 429 deta hai, aur ek risk flag karta hai: worst case mein retries milkar 7 seconds jodte hain, aur dashboard 10 seconds par time out ho jaata hai.

**Review.** Reviewer Farhan aapse total retry time ko 3 seconds par cap karne ko kehta hai. Aap badalte ho, cap ke liye ek test jodte ho, "Done, capped at 3s total, test added" likhkar jawab dete ho, aur push karte ho.

**Conflict.** Is beech Priya ne usi client mein ek configurable timeout jodne waala change merge kar diya. Aapki branch ab conflict karti hai. Aap main merge karte ho, dono sides padhte ho, uski nayi timeout setting **aur** aapka retry wrapper dono rakhte ho, tests chalate ho, aur push karte ho.

| Step | Command ya action | Result |
| --- | --- | --- |
| Shuru | `git switch -c feat/retry-market-data` | Aapki apni branch |
| Kaam save karna | `git commit -m "MD-214: ..."` | Ek saaf commit |
| Share karna | `git push -u origin ...` aur PR kholo | Review aur checks shuru |
| Review fix | Retries ko 3 s par cap karne waala naya commit | Farhan ka comment resolve |
| Conflict | `git merge main`, edit, test, commit | Dono changes rahe |
| Khatam | Checks green, approval, merge, branch delete | Main mein aapka feature hai |

Checks green ho jaate hain, Farhan approve karta hai, aap merge karke branch delete kar dete ho.

## Aam galtiyaan

- **Bahut badi pull requests.** Kaam ko todo; lambe diffs mein reviewers bugs miss kar dete hain.
- **"wip" aur "changes" jaise commit messages.** Baad mein kisi ko nahi pata chalega ki kyun.
- **Secrets commit karna.** Environment variables aur `.gitignore` use karo; leak hui key ko turant rotate karo.
- **Aankh band karke conflicts resolve karna.** Har conflict mein "mine" accept karne se teammate ka fix chhoot jaata hai. Dono sides padho.
- **Shared branches ko force-push karna.** History sirf un branches par rewrite karo jinhe koi aur use nahi karta.
- **Branch ko hafton tak stale chhod dena.** Main ko regular merge karte raho taaki conflicts chhote rahein.

## Practice karo

Neeche link kiya GitHub flow padho, aur Pro Git ka basic branching aur merging chapter.

1. **Ek asli PR.** Apni khud ki repository mein ek branch, do chhote commits aur sahi description ke saath ek pull request banao.
2. **Ek conflict.** Jaan-boojhkar ek banao: main aur apni branch par same line badlo, phir merge karke resolve karo.
3. **Review.** Kisi dost ki PR, ya open-source ki ek PR review karo, aur do kaam ke comments chhodo.

**Aapka kaam poora jab:** aap bina dar ke merge conflict resolve kar sako aur aisi PR description likh sako jise ek ajnabi review kar sake.
