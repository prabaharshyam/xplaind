## Ye kya hai

Ek **evaluation metric** model ki predictions ko ek aisa number bana deta hai jise aap compare kar sako. Alag metrics alag behaviour ko inaam dete hain, isliye choice us par depend karni chahiye ki use mein kya matter karta hai.

| | Predicted positive | Predicted negative |
|---|---|---|
| **Asal mein positive** | True positive (pakda) | False negative (chhut gaya) |
| **Asal mein negative** | False positive (false alarm) | True negative (sahi se theek) |

```flow
dir: LR
title: Precision aur recall kahan se aate hain
Har asli positive -> Pakda: true positives
Har asli positive -> Chhut gaya: false negatives
Uthaya gaya har alarm -> Sahi: true positives
Uthaya gaya har alarm -> Galat: false positives
```

**Recall** = TP / (TP + FN): asli positives mein se kitne aapne pakde. **Precision** = TP / (TP + FP): jo aapne flag kiye, unmein se kitne sahi the.

Ye lesson Mumbai ke ek bank ki teen teams ke saath chalta hai, jo har ek alag problem ke liye alag metric chunti hai.

## Ye kaam kaise karta hai

**Classification.**

- *Accuracy*: sahi ka share. Balanced classes ke liye theek; rare events ke liye gumraah karne waali.
- *Precision*: predicted positives mein se kitne sahi hain. Tab zaroori jab false alarms mehnge hon (genuine payments block karna).
- *Recall*: actual positives mein se kitne pakde gaye. Tab zaroori jab misses mehnge hon (chhuta hua fraud, chhuti hui bimari).
- *F1*: ek threshold par precision aur recall ka balance.
- *ROC AUC*: sabhi thresholds par model positives ko negatives se upar kitni achhi tarah rank karta hai; class balance se bepaarvah, jo rare classes par kharab performance chhupa sakta hai.
- *PR AUC* (average precision): positive class par focus karta hai; rare events ke liye behtar.
- *Log loss* aur calibration: probabilities par bharosa kiya ja sakta hai ya nahi.

**Regression.**

- *MAE*: average absolute error, original units mein; outliers se kam hilta hai aur samjhana aasaan hai.
- *RMSE*: bade errors ko zyada saza deta hai; tab use karo jab bade misses khaas taur par bure hon.
- *MAPE*: percentage error; samajhna aasaan hai par zero ke paas ki values par toot jaata hai aur chhote actuals ko zyada saza deta hai.
- *Quantile ya pinball loss*: jab aap ranges predict karte ho (jaise promises ke liye delivery time ka 90th percentile).

**Ranking aur recommendation.** Precision at k, recall at k, NDCG: kya sahi items upar ke paas dikhe?

**Cost-weighted metrics.** Outcomes par paisa lagao: false positive ki cost, false negative ki cost, true positive ki value. Wo model aur threshold chuno jo expected value ko sabse zyada karein. Business owners ke liye ye aksar sabse saaf metric hota hai.

**Offline metric versus business KPI.** Offline metric ek proxy hai. A/B tests ya pilots se check karo ki use behtar karne par asli KPI (losses, revenue, bacha hua time) badalta hai.

**Segment ke hisaab se.** Metrics ko important groups (region, language, customer type) ke hisaab se report karo, taaki aise models pakde jaayein jo average mein achhe hain aur kuch users ke liye kharab.

**Metric ko problem se match karna:**

| Problem | Zyada bura error | Primary metric | Aur kya report karein |
| --- | --- | --- | --- |
| Card fraud (rare) | Chhuta hua fraud | PR AUC, ek fixed alert budget par recall | Cost-weighted value |
| Spam filter | Asli email spam mein | Precision | Recall |
| Disease screening | Chhuti hui bimari | Recall | Precision, taaki doctors par baadh na aaye |
| Delivery time promise | Der se delivery | 90th percentile quantile loss | MAE |
| Sales forecast | Bade misses | RMSE | Reporting ke liye MAE |
| Recommendations | Irrelevant top items | Precision at k, NDCG | Clicks ya sign-ups par A/B test |

**Thresholds scores ko decisions mein badalte hain.** Zyadatar classifiers 0 aur 1 ke beech ka score dete hain. Aap ek threshold chunte ho jiske upar ek case flag hota hai. Kam threshold zyada positives pakadta hai (zyada recall) lekin zyada false alarms uthata hai (kam precision); zyada threshold ulta karta hai. Aam taur par koi sahi threshold nahi hota: wo is par depend karta hai ki har error ki cost kya hai aur aapki team kitne cases review kar sakti hai. Ek common practical tareeka: capacity pehle fix karo, jaise "fraud team din mein 300 alerts review kar sakti hai", wo threshold chuno jo lagbhag 300 alerts de, phir us point par recall report karo.

**Calibration.** Agar model 0.8 kehta hai, toh kya iska matlab 80% chance hai? Aksar nahi. Ek calibrated model ke scores asli frequencies se milte hain: jin sabhi cases ka score lagbhag 0.8 hai, unmein se lagbhag 80% positive hote hain. Calibration tab matter karti hai jab log probability par hi act karte hain, jaise insurance ki pricing ya doctor ko risk level dikhana. Ise reliability plot se check karo, aur Platt scaling ya isotonic regression jaise tareekon se theek karo.

**Rare-event problem par metrics, code mein.** 2% positives waala ek synthetic fraud jaisa dataset dikhata hai ki numbers kitne alag behave karte hain:

```python
import numpy as np
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import (accuracy_score, roc_auc_score, average_precision_score,
                             precision_score, recall_score, brier_score_loss)

X, y = make_classification(n_samples=20_000, n_features=12, weights=[0.98], class_sep=0.9, random_state=7)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, stratify=y, random_state=7)
p = LogisticRegression(max_iter=1000).fit(X_tr, y_tr).predict_proba(X_te)[:, 1]

print("accuracy, always 'no':", round(accuracy_score(y_te, np.zeros_like(y_te)), 3))
print("ROC AUC:", round(roc_auc_score(y_te, p), 3), " PR AUC:", round(average_precision_score(y_te, p), 3))
print("precision, recall at 0.5:", round(precision_score(y_te, p > 0.5), 3), round(recall_score(y_te, p > 0.5), 3))
print("Brier:", round(brier_score_loss(y_te, p), 4))
```

"Kabhi fraud nahi" predict karne par lagbhag 98% accuracy milti hai, ROC AUC tasalli dene waala dikhta hai, aur PR AUC rare class ki sachchi kahaani batata hai.

**Costs se threshold chuno.** Thresholds sweep karo aur sabse kam total cost waala rakho:

```python
def best_threshold(y_true, scores, cost_fp=200, cost_fn=15_000):
    best = None
    for t in np.linspace(0.01, 0.99, 99):
        pred = scores >= t
        fp = int(((pred == 1) & (y_true == 0)).sum())
        fn = int(((pred == 0) & (y_true == 1)).sum())
        cost = fp * cost_fp + fn * cost_fn
        if best is None or cost < best[1]:
            best = (round(float(t), 2), cost, fp, fn)
    return {"threshold": best[0], "cost_inr": best[1], "false_alarms": best[2], "missed": best[3]}

print(best_threshold(y_te, p))
```

Jab chhuta hua fraud false alarm se 75 guna mehnga ho, toh best threshold 0.5 se bahut neeche hota hai.

**Kya farak asli hai?** Interval paane ke liye test set ko bootstrap karo:

```python
def bootstrap_ci(y_true, scores, metric=average_precision_score, n=1000, seed=0):
    rng = np.random.default_rng(seed)
    vals = []
    for _ in range(n):
        idx = rng.integers(0, len(y_true), len(y_true))
        if y_true[idx].sum() == 0:
            continue
        vals.append(metric(y_true[idx], scores[idx]))
    return np.percentile(vals, [2.5, 97.5]).round(3)

print("PR AUC 95% interval:", bootstrap_ci(y_te, p))
```

Agar do models ke intervals bahut overlap karte hain, toh sirf is test set ke bharose ye mat kaho ki ek behtar hai.

**Ek range predict karna.** Delivery promises ke liye, 90th percentile ke liye train karo aur pinball loss se score karo:

```python
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.metrics import mean_pinball_loss

rng = np.random.default_rng(1)
km = rng.uniform(1, 12, 3000).reshape(-1, 1)
minutes = 10 + 3 * km[:, 0] + rng.gamma(2, 4, 3000)          # skewed delays
q90 = GradientBoostingRegressor(loss="quantile", alpha=0.9).fit(km[:2000], minutes[:2000])
pred = q90.predict(km[2000:])
print("share delivered within the promise:", round(float((minutes[2000:] <= pred).mean()), 2))
print("pinball loss:", round(mean_pinball_loss(minutes[2000:], pred, alpha=0.9), 2))
```

Lagbhag 90% deliveries promise kiye gaye time ke andar aani chahiye; us share ko asli data par area ke hisaab se check karo.

## Ek example se samjho

Mumbai ke ek bank ki teen teams:

- **Card payments par fraud** (0.2% fraud): accuracy ka koi matlab nahi. Wo models compare karne ke liye PR AUC use karte hain aur phir threshold chunne ke liye ek cost-weighted measure (average loss par chhuta hua fraud versus har alert par analyst time).
- **ATM cash demand forecasting**: cash khatam hona extra rakhne se kahin zyada bura hai, isliye wo demand ka 90th percentile predict karte hain aur quantile loss se evaluate karte hain, reporting ke liye MAE ke saath.
- **Mobile app mein product recommendations**: sirf top teen suggestions dikhte hain, isliye wo precision at 3 use karte hain aur product sign-ups par A/B test se confirm karte hain.

Har team apna metric customer segment ke hisaab se report karti hai. Recommendation model metros mein achha aur rural branches ke customers ke liye kharab nikalta hai; rural customers ke liye alag feature set gap ka bada hissa theek kar deta hai.

**Business ko choice samjhana.** Fraud team ki head ko PR AUC nahi chahiye tha; wo jaanna chahti thi ki model bank ke liye kya karega. Isliye team ne translate kiya: "Din mein 300 alerts par, jo aapke analysts sambhal sakte hain, naya model har 100 fraud cases mein se lagbhag 78 pakadta hai, pehle 64 tha. Ye lagbhag ₹1.1 crore prati mahine ke losses bachana hai, bina extra analyst time ke." Model metric ne model chuna; rupee figure ne decision liya.

| Team | Model metric | Business translation |
| --- | --- | --- |
| Fraud | PR AUC, din mein 300 alerts par recall | Prati mahine bache losses |
| ATM cash | 90th percentile par quantile loss | Prati mahine cash khatam hone waale ATMs |
| Recommendations | Precision at 3 | A/B test mein extra product sign-ups |

## Aam galtiyaan

- **Imbalanced data par accuracy.**
- **Rare events ke liye sirf ROC AUC.** PR AUC aur apne operating point par precision dekho.
- **Chhote ya zero actuals ke saath MAPE.** MAE ya weighted variants use karo.
- **Aise metric ko optimise karna jo KPI ko nahi hilata.** Pilots ya A/B tests se validate karo.
- **Sirf overall numbers.** Segments check karo.

- **Aadat se threshold chunna.** 0.5 shaayad hi kabhi best threshold hota hai. Costs aur review capacity se chuno.
- **Calibration check kiye bina scores ko probabilities maan lena.**
- **Results dekhne ke baad metric chunna.** Experiment se pehle tay kar lo.
- **Chhote test sets par interval na hona**, jisse noise ko progress ki tarah report kiya jaata hai.
- **Jab error costs ek taraf jhuki hon tab 0.5 ka default threshold.**

## Jab ek simple metric kaafi hai

- **Balanced classes aur ek jaisi error costs**: accuracy theek hai aur samjhana aasaan hai.
- **Shuruaati exploration**, jahan ek samajhdaar metric ideas ko tezi se compare karne mein madad karta hai.
- **Ek baseline ke saath quick sanity check**, poori evaluation se pehle.

## Demo se production tak

- **Training se pehle metric, threshold aur costs likh lo**, business owner ke saath.
- **Intervals aur segment-level metrics report karo**, sirf ek overall number nahi.
- **Threshold dobara check karo** jab costs, volumes ya model badlein.
- **Launch ke baad offline metric ke saath business KPI track karo.**
- **Calibration monitor karo** agar koi probabilities par act karta hai.
