## Ye kya hai

MCP se pehle har AI app ko har system ke liye apna code chahiye hota tha. Teen assistants aur chaar systems matlab baarah integrations. **Model Context Protocol** (MCP) ek open standard hai jo ise theek karta hai. Aap har system ko ek baar **MCP server** ki tarah lapet-te ho, aur har AI app mein ek **MCP client** hota hai jo kisi bhi server se baat kar sakta hai: teen guna chaar ki jagah teen jama chaar hisse.

Anthropic ne MCP 25 November 2024 ko release kiya. December 2025 mein usne MCP ko Agentic AI Foundation ko de diya, jo Linux Foundation ke tahat ek directed fund hai jise Anthropic, Block aur OpenAI ne milkar shuru kiya, aur jahan iske maintainers ise khule mein develop karte hain. Versions ke naam taareekh se hote hain. Abhi wala **2026-07-28** hai, paanchva release; usse pehle wala 2025-11-25 tha. Hamesha check karo ki koi tutorial kis version ke liye likha hai.

Ek server teen tarah ki cheezein de sakta hai. Sabse zaroori baat ye hai ki har ek ko use karne ka faisla kaun karta hai:

| Feature | Ye kya hai | Use karne ka faisla kaun karta hai | Misaal | Messages |
| --- | --- | --- | --- | --- |
| Tools | JSON schema wale functions | Model, task ke dauraan | `search_tickets(query, status)` | `tools/list`, `tools/call` |
| Resources | URI se pehchaana jaane wala data | App ya user use jodta hai | `ticket://T-1042` | `resources/list`, `resources/read` |
| Prompts | Dobara kaam aane wale prompt templates | User menu se ek chunta hai | "Is ticket thread ka summary banao" | `prompts/list`, `prompts/get` |

## Ye kaam kaise karta hai

### Host, client aur server

**Host** woh AI app hai jisme user kaam karta hai. Uske andar ek **client** ek **server** se connection rakhta hai, toh teen servers wale host mein teen clients hote hain. Client apne server ke tools ki list model ko deta hai. Jab model koi tool maangta hai, toh client woh call us server ko bhejta hai aur result lauta deta hai. Model kabhi server se seedhe baat nahi karta, isliye control host ke haath mein rehta hai.

```flow
dir: LR
title: Har system ke liye ek server, jise har host share karta hai
IDE assistant | har server ke liye ek client wala host -> Maintenance-log server | find_machine, get_maintenance_history, log_observation
Chat assistant | har server ke liye ek client wala host -> Maintenance-log server
Chat assistant -> Spare-parts server
```

### Wire par chalne wale messages

MCP messages JSON-RPC 2.0 hote hain: request mein ek `id`, ek `method` aur `params` hote hain, aur reply mein wahi `id` aata hai. 2026-07-28 se protocol **stateless** hai. Purane versions ek `initialize` handshake se shuru hote the aur ek session rakhte the. Ab har request protocol version aur client capabilities `_meta` mein saath laati hai, aur use client ka naam aur version bhi saath laana chahiye. Client chahe toh pehle `server/discover` call kar sakta hai, par zaroori nahi. Jin clients ne upgrade nahi kiya, unke liye official Python SDK usi server se abhi bhi purana handshake serve karta hai.

Failures do tarah ke hote hain:

- **Tool error** ek normal result hai jisme `isError: true` hota hai. Model use padhkar dobara try kar sakta hai, isliye batao ki kya galat hua aur uski jagah kya karna hai.
- **Protocol error** ek JSON-RPC `error` hai jisme ek code hota hai, jaise kisi malformed request ke liye. Ise client sambhalta hai; model ise aamtaur par dekhta hi nahi.

**Apne browser mein try karo.** Ye worked example wale server se record ki gayi ek request aur do replies hain, jagah ke liye chhoti ki gayin. Code ek reply ko us roop mein badalta hai jo model dekhta hai.

```python
import json

request = {"jsonrpc": "2.0", "id": 7, "method": "tools/call",
           "params": {"name": "get_maintenance_history", "arguments": {"tag": "CNC-14", "limit": 1},
                      "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}

ok = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": False,
      "content": [{"type": "text", "text": "{\"date\": \"2026-11-18\", \"note\": \"Vibration at high RPM\"}"}]}}
refused = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": True,
      "content": [{"type": "text", "text": "Error executing tool get_maintenance_history: No machine 'CNC-14' in your plant."}]}}

def for_the_model(reply):
    assert reply["id"] == request["id"], "a reply must match its request id"
    if "error" in reply:  # protocol error: the host deals with it
        raise RuntimeError(reply["error"]["message"])
    text = "\n".join(c["text"] for c in reply["result"]["content"] if c["type"] == "text")
    return {"tool_result": text, "is_error": reply["result"]["isError"]}

print(json.dumps(for_the_model(ok)))
print(json.dumps(for_the_model(refused)))
```

### Transports: local aur remote

| Pehlu | stdio (local) | Streamable HTTP (remote) |
| --- | --- | --- |
| Kaise chalta hai | Host server ko child process ki tarah chaalu karta hai aur standard input aur output se baat karta hai | Server ek URL par chalne wali web service hai, jaise `https://mcp.example.in/maintenance` |
| Kiske liye achha | Files, local databases, developer tools | Shared company systems, jinhe ek jagah update aur log kiya jaata hai |
| User kaun hai | Jo bhi us machine par host chala raha hai | Jisne sign-in kiya: har request par ek OAuth token |

**Streamable HTTP** mein client har message usi ek URL par POST karta hai, aur server JSON se jawab deta hai, ya pehle progress bhejna ho toh events ki ek stream se. 2026-07-28 mein har request mein body se copy kiya hua ek `Mcp-Method` header hota hai, aur tool, resource aur prompt requests mein `Mcp-Name` bhi hota hai, taaki gateway body parse kiye bina requests route kar sake; jis request ke headers aur body mel na khaayen, use 400 error milta hai. Ab koi session id nahi hai: server purane `Mcp-Session-Id` header ko ignore karta hai aur naya nahi banata. Agar kisi workflow ko state chahiye, toh tool `draft_id` jaisa ek handle lautata hai aur model use wapas bhejta hai.

Do gotchas. Purane tutorials **HTTP+SSE** transport (`transport="sse"`) use karte hain, jo deprecated hai: us par kuch naya shuru mat karo. Aur stdio server ko standard output par sirf MCP messages likhne chahiye: ek bhi bhatka hua `print` connection tod deta hai, isliye standard error par log karo.

### Python mein server banana

Official Python SDK `mcp` package hai, November 2026 tak version 2.x (`pip install "mcp[cli]"`). Uski main class `MCPServer` hai. SDK 1.x wale tutorials `mcp.server.fastmcp` se `FastMCP` import karte hain, jo 2.x par fail hota hai: code update karo ya `mcp<2` pin karo.

```python
# tickets_server.py
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open") -> list[dict]:
    """Search support tickets by keywords. status is 'open' or 'closed'. Returns up to 10."""
    if status not in ("open", "closed"):
        raise ToolError("status must be 'open' or 'closed'.")
    return ticket_db.search(query, status=status, limit=10)

@mcp.resource("ticket://{ticket_id}")
def ticket(ticket_id: str) -> str:
    """The full text of one ticket."""
    return ticket_db.get(ticket_id).body

@mcp.prompt()
def summarise_ticket(ticket_id: str) -> str:
    return f"Summarise ticket {ticket_id} in five bullets."

if __name__ == "__main__":
    mcp.run()  # stdio; use mcp.run(transport="streamable-http") for a remote server
```

Function ka naam, type hints aur docstring hi tool ka name, input schema aur description ban jaate hain, isliye tool-design wala lesson yahan seedhe laagu hota hai. `ToolError` raise karne par ek `isError: true` result lautta hai: "Error executing tool <name>: " prefix ke baad aapka message.

**Model jodne se pehle test karo.** MCP Inspector (`npx @modelcontextprotocol/inspector`, ya `mcp dev tickets_server.py`) se aap har tool ko apne arguments se call kar sakte ho, galat arguments samet, aur raw results dekh sakte ho. Zyaadatar bugs yahan chat se jaldi dikh jaate hain.

**Aapka apna client.** Assistants aur code editors mein clients pehle se hote hain; aapka apna agent SDK use kar sakta hai:

```python
import asyncio
from mcp import Client, StdioServerParameters

async def main():
    server = StdioServerParameters(command="python", args=["tickets_server.py"])
    async with Client(server) as client:  # or Client("https://.../mcp") for a remote server
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("search_tickets", {"query": "refund"})
        print(result.is_error, result.structured_content)

asyncio.run(main())
```

Har tool ka `name`, `description` aur `input_schema` model ko do, uski calls `client.call_tool` ko bhejo, aur `is_error` wapas do taaki model ko pata chale ki call fail hui.

### Server client se kya maang sakta hai

**Elicitation** se koi tool call ke beech mein user se kuch poochh sakta hai: koi chhooti hui detail, ya bulk change se pehle "Saare 40 tickets close kar dein?". 2026-07-28 mein ye rounds mein chalta hai: server apne sawaalon ke saath `resultType: "input_required"` lautata hai, host user se poochhta hai, aur client jawaabon ke saath call dohraata hai. Password ya payment ke liye, jo AI app se hokar nahi jaane chahiye, server user ko ek web page par bhej deta hai (URL mode).

Purane material mein **sampling** (server host ke model se text likhwata hai) aur **roots** (host server ko batata hai ki kaunse folders use karne hain) ka bhi zikr hai. Dono 2026-07-28 mein deprecated ho gaye, saath mein logging bhi. Ye kam se kam 28 July 2027 ko ya uske baad release hone wale pehle revision tak spec mein rahenge, par in par kuch naya mat banao. 2026-07-28 mein lambe chalne wale jobs (**tasks**) core se nikalkar ek extension mein chale gaye. Interactive screens (**MCP Apps**) ek alag extension hai.

### Tools context khaate hain

Har jude hue tool ka name, description aur schema har turn par model ke context mein baitha rehta hai. Anthropic ka documentation (November 2026 mein check kiya) kehta hai ki paanch servers wala ek aam setup kaam shuru hone se pehle hi definitions mein kareeb 55,000 tokens kha sakta hai, aur 30 se 50 tools ke baad tool chunne ki quality girti hai. Isliye:

- Kam, task ke hisaab se bane aur alag-alag naam wale tools do; agar do servers mein `search` ho sakta hai, toh system ka prefix lagao (`maint_search`).
- Results par cap lagao: ek `limit` argument, chhote fields, poore documents ki jagah IDs.
- Jahan host support kare, tools zaroorat padne par load karo. Misaal ke taur par, Claude ka tool search tool `defer_loading` mark kiye gaye tools ko tab tak context se bahar rakhta hai jab tak model unhe search na kare.

### Security, chhote mein

Server aisa code hai jiski pahunch asli systems tak hai, aur uska output model mein jaata hai. Mukhya risks: **tool poisoning** (descriptions ya results mein chhupe instructions), **approval ke baad badlaav** (versions pin karo), servers ke beech **naamon ki takkar**, aur **bahut zyaada pahunch** (poori company ka ek token). Aage wala lesson, Securing agent tools and MCP servers, isme aur gehraai mein jaata hai; worked example banane wale ka paksh dikhata hai.

## Ek worked example

Pune ki ek manufacturing company ke do plants hain, PUN-1 aur PUN-2. Engineers apne IDE mein ek AI assistant aur chat mein doosra use karte hain, aur dono ko maintenance log chahiye. Contractors ko sirf apna plant dikhna chahiye.

Aap teen tools wala ek remote MCP server banate ho: `find_machine`, `get_maintenance_history` aur `log_observation`. Remote MCP OAuth use karta hai: company ka single sign-on (SSO) **authorization server** hai jo tokens issue karta hai, aur aapka MCP server **resource server** hai jo unhe check karta hai.

```flow
title: Remote server se pehla connection
Assistant bina token ke server ko call karta hai -> Server ke metadata link ke saath 401 reply
Server ke metadata link ke saath 401 reply -> Assistant padhta hai ki kaunsi sign-in service use karni hai
Assistant padhta hai ki kaunsi sign-in service use karni hai -> Engineer company SSO se sign in karta hai
Engineer company SSO se sign in karta hai -> SSO sirf isi server ke liye token deta hai | user, plant, scopes
SSO sirf isi server ke liye token deta hai -> Assistant token ke saath call dohraata hai
Assistant token ke saath call dohraata hai -> Server token check karke usi user ke taur par tool chalata hai
```

Metadata serve karna aur 401 bhejna SDK aapke liye kar deta hai. Aapka code tokens check karta hai aur user ki seemaayen laagu karta hai:

```python
# maintenance_server.py
import json, sqlite3
from mcp.server import MCPServer
from mcp.server.auth.middleware.auth_context import get_access_token
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver.exceptions import ToolError

db = sqlite3.connect("maintenance.db", check_same_thread=False)
audit = open("audit.jsonl", "a", buffering=1)  # one JSON line per call

def verify_with_sso(token: str) -> dict | None:
    """Your SSO library checks signature, expiry and issuer; returns the claims or None."""
    ...

class SSOTokenVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        claims = verify_with_sso(token)
        if claims is None:
            return None
        return AccessToken(token=token, client_id=claims["azp"], subject=claims["sub"],
                           scopes=claims["scope"].split(), resource=claims["aud"],
                           claims={"plant": claims["plant"]})

mcp = MCPServer("maintenance", token_verifier=SSOTokenVerifier(), auth=AuthSettings(
    issuer_url="https://sso.example.in",
    resource_server_url="https://mcp.example.in/maintenance",
    required_scopes=["maintenance.read"],
    validate_token_resource=True,  # refuse tokens issued for any other service
))

def caller(tool: str, args: dict) -> tuple[str, str, list[str]]:
    """Who is calling, from the checked token, never from the model. Writes the audit line."""
    tok = get_access_token()
    audit.write(json.dumps({"user": tok.subject, "client": tok.client_id, "tool": tool, "args": args}) + "\n")
    return tok.subject, tok.claims["plant"], tok.scopes

@mcp.tool()
def get_maintenance_history(tag: str, limit: int = 5) -> list[dict]:
    """Latest maintenance events for one machine in your plant, newest first. limit is 1 to 20."""
    user, plant, _ = caller("get_maintenance_history", {"tag": tag, "limit": limit})
    rows = db.execute(
        "SELECT e.done_on, e.kind, e.note, e.by_user FROM events e JOIN machines m ON m.id = e.machine_id "
        "WHERE m.tag = ? AND m.plant_id = ? ORDER BY e.done_on DESC LIMIT ?",
        (tag, plant, max(1, min(limit, 20)))).fetchall()
    if not rows:
        raise ToolError(f"No machine '{tag}' in your plant. Call find_machine to search by name.")
    return [{"date": d, "kind": k, "note": n, "by": b} for d, k, n, b in rows]

@mcp.tool()
def log_observation(tag: str, note: str) -> str:
    """Add a short note (max 500 characters) to a machine's log. Writes only to the notes table."""
    user, plant, scopes = caller("log_observation", {"tag": tag, "note": note[:80]})
    if "maintenance.write" not in scopes:
        raise ToolError("Your sign-in does not allow writing notes. Ask your supervisor to add it.")
    row = db.execute("SELECT id FROM machines WHERE tag = ? AND plant_id = ?", (tag, plant)).fetchone()
    if row is None:
        raise ToolError(f"No machine '{tag}' in your plant.")
    db.execute("INSERT INTO notes (machine_id, note, by_user) VALUES (?, ?, ?)", (row[0], note[:500], user))
    db.commit()
    return f"Note added to {tag}."

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000,
            streamable_http_path="/maintenance")  # serve behind HTTPS in production
```

Teen design choices security sambhaalti hain:

1. **Plant token se aata hai, model se nahi.** Kisi tool mein `plant_id` argument nahi hai, isliye koi prompt doosra plant nahi maang sakta. Har query us plant se filter hoti hai jo SSO ne token mein daala.
2. **Token isi server ke liye hona chahiye.** `validate_token_resource=True` ke saath, kisi doosri service ke liye issue hue asli token ko bhi 401 milta hai.
3. **Writes ke liye scope chahiye.** Padhne ke liye `maintenance.read` chahiye; `log_observation` ko `maintenance.write` bhi chahiye.

Humne is server ko do users ke stand-in tokens se test kiya (`find_machine` bhi usi pattern par hai, upar chhod diya). PUN-1 ki engineer Anita chat mein poochhti hai: "CNC-14 ka spindle aakhri baar kab service hua tha, aur uske baad kisi ne vibration report kiya hai kya?" Assistant `get_maintenance_history` call karta hai aur do rows paata hai: 2 October 2026 ko suresh.p ne bearings badle, aur 18 November 2026 ko meera.d ne "Vibration at high RPM" likha. Woh dono ke saath jawab deta hai, phir `log_observation` se uska note log karta hai.

Ravi ek contractor hai jiske token mein PUN-2 aur sirf `maintenance.read` hai; woh apne IDE se wahi poochhta hai. Wahi query `plant_id = 'PUN-2'` ke saath chalti hai, kuch nahi milta, aur "No machine 'CNC-14' in your plant." lautta hai. Uski `log_observation` call ko "Your sign-in does not allow writing notes." milta hai. Dono `isError: true` wale results hain, isliye assistant unhe samjha deta hai. Audit log mein har call ki ek line hai, jaise `{"user": "ravi.contractor", "client": "ide-assistant", "tool": "get_maintenance_history", "args": {"tag": "CNC-14", "limit": 2}}`.

Ise production-grade banane ke liye do layers aur. Server ka database account sirf machines aur events padh sake aur notes mein insert kar sake, taaki aapke filter mein bug ho tab bhi kuch delete na ho. Aur server **Anita ka token kabhi** kisi doosri API ko **aage na bheje**. Woh token passthrough hai, jise MCP security guidance mana karti hai; agar kisi downstream API ko user chahiye, toh usi API ke liye issue hua ek alag token lo.

Baad mein jab IT ek spare-parts system jodta hai, toh woh usi sign-in ke saath ek doosra server deploy karte hain, aur dono assistants ko bina kisi badlaav ke uske tools mil jaate hain.

## Aam galtiyan

- **Kisi purane tutorial ko line-by-line follow karna.** `FastMCP` imports, `transport="sse"`, session ids aur `initialize` handshake 2024 aur 2025 ke hain. Pehle versions check karo.
- **Sabke liye ek super-user credential.** Agar server ye nahi dekhta ki kaun poochh raha hai, toh har user har cheez tak pahunch jaata hai. Sign-in kiye hue user ki tarah kaam karo.
- **Identity kisi tool argument se lena.** `user_id` ya `plant_id` parameter se model, ya usme inject kiya gaya text, kisi aur ka data chun sakta hai. Identity check kiye gaye token se padho.
- **Token passthrough.** Jo tokens aapke server ke liye issue nahi hue unhe maanna, ya user ka token doosri services ko aage bhejna, audit aur scope checks tod deta hai.
- **Poora database khol dena.** Jab tak users database administrators na hon, `run_sql` nahi, task ke hisaab se bane tools do.
- **Bahut bade results.** Hazaaron rows context bhar deti hain aur har agla turn dheema kar deti hain. Cap karo, paginate karo aur summarise karo.
- **Timeouts nahi.** Dheeme ERP ka intezaar karta tool agent ko rok deta hai. Server ki apni calls par timeout lagao, aur client read timeout bhi set karo (Python `Client` mein `read_timeout_seconds`).
- **Servers aur results par bharosa karna.** Anjaan ya bina pin kiye servers, aur instructions maan liya gaya ticket text, tool poisoning aur prompt injection ko nyota dete hain.
- **Logging nahi.** Har call ka user, tool aur arguments na ho, toh kisi incident ki jaanch nahi ho sakti.

## Kab aapko MCP nahi chahiye

- **Kuch tools wala ek hi app**, jinhe sirf wahi use karta hai: aapke code mein seedhi tool definitions aasaan hain.
- **Fixed workflows**, jahan aapka code functions seedhe call karta hai aur koi model tools nahi chunta.
- **Strict environments**, jahan har nayi network service ko review chahiye: in-process tools se shuru karo, aur jab doosre app ko unki zaroorat ho tab MCP par jao.

MCP tab faayda deta hai jab kai hosts ya agents ko wahi tools chahiye, ya log apne pehle se istemaal ho rahe assistants ko aapke systems se jodna chahte hain.

## Demo se production tak

- **Company sign-in ke zariye OAuth**, narrow scopes, isi server ke liye check kiye gaye tokens, token se identity, aur ek least-privilege database account.
- **Ek central audit log**: user, client, tool, arguments aur result size.
- **Approved servers ki ek list**, pin kiye gaye versions, aur jab bhi tool descriptions badlein tab review.
- **Har tool par seemaayen:** timeouts, result caps, rate limits, aur writes ke liye user confirmation.

## Practice karo

Anthropic ka free Introduction to Model Context Protocol course karo, ya official introduction aur Python SDK ki get-started guide padho.

1. Apni pasand ke ek chhote SQLite database (books, fees, appointments) par `MCPServer` se do tools wala ek local stdio server banao.
2. Use MCP Inspector mein kholo, har tool ko galat arguments se call karo, aur har woh error message dobara likho jo model ko sambhalne mein madad na kare.
3. Use kisi MCP-capable assistant se jodo aur aise sawaal poochho jinme dono tools lagein. Ek write tool jodo jo sirf ek table mein insert kare, har call log karo, aur ek record mein prompt injection chhupakar dekho ki kya hota hai.
4. Use `transport="streamable-http"` se chalao, ek `TokenVerifier` jodo jo do users ke do test tokens maane, aur dikhao ki har user ko sirf apni rows dikhti hain.

**Aapka kaam tab poora hai jab aap** host, client aur server samjha sako, apna server kisi asli client mein chalta dikha sako, ek hi tool se do users ko alag results milte dikha sako, aur kisi aur ka server install karne se pehle poochhne wale teen sawaal bata sako.
