## Ye kya hai

**LLM gateway** aapki applications aur model providers ke beech ki ek service hai. Applications har request ek hi API format mein gateway ko bhejti hain. Gateway use sahi provider aur model tak forward karta hai, aur shared kaam har app mein alag-alag karne ki bajaay ek hi baar sambhaalta hai:

- **Routing**: kaun-sa model aur provider is request ko serve karega.
- **Failover**: jab koi provider error de, timeout ho ya aapko rate-limit kare, tab kya try karein.
- **Keys aur access**: teams ko gateway keys milti hain; real provider keys sirf gateway mein rehti hain.
- **Rate limits aur budgets**: har team, har feature ya har user ke liye.
- **Logging aur cost**: har request uske tokens, cost aur latency ke saath, ek hi jagah.

Ye lesson Bengaluru ki ek fintech ko follow karta hai, jahan chaar teams ke paanch AI features mein se har ek apni keys se providers ko seedhe call karta tha.

```flow
title: One gateway in front of every provider
Chatbot -[key chatbot]-> Gateway, 2 or more instances
Claims extraction -[key claims]-> Gateway, 2 or more instances
Nightly summaries -[key batch]-> Gateway, 2 or more instances
Gateway, 2 or more instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails, cool-down]-> Model X, Hyderabad
Model X, Hyderabad -[fails]-> Fallback alias: approved model Y, India
```

Har key ki apni rate limit aur budget hota hai. Gateway forward karne se pehle unhe check karta hai, result log karta hai, aur provider keys ek secret store mein rakhta hai.

### Gateway paane ke teen tareeke

| Kism | Examples | Kab chunein |
| --- | --- | --- |
| Self-hosted, open source | LiteLLM proxy (MIT licence) | Data aapke apne cloud account aur region mein hi rehna chahiye, aur aapke paas ek platform team hai jo database waali service chala sake |
| Aapke cloud ka API management | Azure API Management (uski `llm-token-limit` policy), Google Apigee (uski LLM token quota policy) | Aap doosri APIs ke liye pehle se us cloud ka API management use karte ho aur zyaadatar usi cloud ke models call karte ho |
| Kisi vendor ka managed gateway | Kai vendors aapke liye host karte hain | Aap chhote ho, infrastructure chalaane waala koi nahi hai, aur vendor ki data processing locations aapke data ke liye allowed hain |

Faisla aamtaur par do sawaalon par aakar tikta hai. Aapka data kahan process ho sakta hai? Aur raat ko gateway toote toh kise jagaaya jaayega? Managed gateway har prompt dekhta hai, isliye sabse pehle ye check karo ki wo data kahan process karta hai.

## Ye kaise kaam karta hai

### Ek interface aur model aliases

Zyaadatar gateways OpenAI-style chat format lete hain aur har provider ke liye use translate karte hain. Apps kabhi real model ka naam nahi lete. Wo `chat-default` jaise kisi **alias** ko call karte hain, aur gateway use ek real model se map karta hai. Har app ko naye model par upgrade karna gateway config ki ek reviewed line ban jaata hai, pehle aapke golden set par test karke.

### Failover ki do layers

Achhe failover mein do layers hoti hain, aur inhe dimaag mein alag-alag rakhna madad karta hai.

1. **Ek alias ke peeche deployments.** Wahi model do jagah, jaise Mumbai aur Hyderabad. Ek fail ho toh gateway doosre deployment par retry karta hai.
2. **Ek fallback alias.** Ek alag, approved model, jo tabhi use hota hai jab pehle alias ke saare deployments fail ho chuke hon.

Fail hota hua deployment har request ko slow nahi karna chahiye. Ise ek **cool-down** (jise circuit breaker bhi kehte hain) sambhaalta hai. Thode samay mein bahut zyada failures hone par gateway us deployment ko ek tay samay ke liye skip karta hai. Requests ko pehle timeout nahi jhelna padta. Cool-down khatam hone par gateway us deployment ko phir se try karta hai.

### Ek gateway configuration

LiteLLM ka proxy ek common open-source choice hai; doosre gateways yahi ideas alag syntax mein use karte hain. Ek hi file aliases, deployments, retries, cool-downs aur fallback define karti hai. LiteLLM 1.111.0 par check kiya gaya.

```yaml
# gateway.yaml: the whole gateway in one reviewed file
model_list:
  # Alias chat-default: the same model deployed in two Indian regions.
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>             # in-Region ID or India profile, never APAC or global
      aws_region_name: ap-south-1           # Mumbai
      order: 1                              # used first while healthy
      timeout: 30                           # seconds, normal calls
      stream_timeout: 10                    # seconds, streaming calls
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>
      aws_region_name: ap-south-2           # Hyderabad
      order: 2                              # used when Mumbai fails or cools down
      timeout: 30
      stream_timeout: 10
  # Fallback alias: another provider, also in India, approved and tested on the evals.
  - model_name: chat-backup
    litellm_params:
      model: vertex_ai/<model id>
      vertex_project: os.environ/GCP_PROJECT
      vertex_location: asia-south1          # Mumbai
      timeout: 30

router_settings:
  num_retries: 2                            # retries on 429s and server errors
  allowed_fails: 3                          # more than 3 failures in a minute starts a cool-down
  cooldown_time: 60                         # seconds a cooling deployment is skipped
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL     # keys, limits, budgets and spend live here
```

Ise `litellm --config gateway.yaml --port 4000` se start karo. Load balancer ke peeche do ya zyada instances chalao, sab ek hi database ki or point karein.

**Bedrock par ek region trap.** Bedrock ke cross-Region inference profiles prompts ko us Region ke bahar process kar sakte hain jise aap call karte ho. APAC profile Asia Pacific ke andar rehta hai, India ke andar nahi, aur global profile koi bhi supported commercial Region use kar sakta hai. Kuch Claude models ke liye Bedrock mein ab ek India geographic profile hai jo sirf Mumbai aur Hyderabad ke beech route karta hai. Agar data India mein hi process hona chahiye, toh wo profile ya in-Region model ID use karo, aur pehle Bedrock Regional availability table check karo: har model Hyderabad mein in-Region nahi milta.

### Apps alias ko call karte hain, provider ko nahi

Koi bhi OpenAI-compatible client chalega. Request ko asal mein kisne serve kiya, ye dekhne ke liye response headers padho:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=os.environ["GATEWAY_URL"], api_key=os.environ["CHATBOT_KEY"])

raw = client.chat.completions.with_raw_response.create(
    model="chat-default",                       # the alias, never a provider model name
    messages=[{"role": "user", "content": "Explain my last card statement in two lines: ..."}],
)
reply = raw.parse()
print(reply.choices[0].message.content)
print("model group:", raw.headers.get("x-litellm-model-group"))      # chat-backup means it fell back
print("fallbacks:", raw.headers.get("x-litellm-attempted-fallbacks"))
print("cost in USD:", raw.headers.get("x-litellm-response-cost"))
```

### Rate limits aur budgets waali keys

Admin har feature ke liye ek virtual key banaata hai. Virtual key wo key hai jo gateway issue karta hai; ye real provider keys se map hoti hai, jinhe team kabhi nahi dekhti.

```bash
curl -s "$GATEWAY_URL/key/generate" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"key_alias": "chatbot", "models": ["chat-default", "chat-backup"],
       "rpm_limit": 600, "tpm_limit": 200000,
       "max_budget": 400, "budget_duration": "30d",
       "metadata": {"team": "support", "feature": "chatbot", "owner": "platform-lead"}}'
```

`rpm_limit` is key ke liye har minute ki requests par cap lagata hai aur `tpm_limit` har minute ke tokens par. Fallback alias ko bhi `models` mein list karo: testing mein, jis key ko sirf `chat-default` allowed tha, use backup ki jagah ek plain error mila. Key revoke karne se baaki kuch rotate kiye bina ek feature kat jaata hai. Is setup ko test karte hue dikhe teen behaviours jaanne laayak hain:

- **Rate limit aur budget alag tarah se fail hote hain.** `rpm_limit` paar karne par HTTP 429 aaya, jise client thoda rukkar retry kar sakta hai. Budget khatam hone par `budget_exceeded` type ke saath HTTP 422 aaya. Use retry karna bas samay barbaad karta hai, isliye clients ko use final maankar kisi insaan ko alert karna chahiye.
- **Budgets lagbhag hote hain.** Gateway har request se pehle budget check karta hai, isliye jo request line paar karti hai wo phir bhi poori ho jaati hai. 0.05 dollar budget waale ek test mein requests refuse hone se pehle spend 0.065 tak pahunch gaya. Cap ko usse thoda neeche rakho jitna aap sach mein afford kar sakte ho.
- **Reset date check karo.** Ye maanne ki bajaay ki period aaj se shuru hota hai, key banaane ke baad `/key/info` se `budget_reset_at` padho. Budgets US dollars mein hote hain, isliye apni reports mein ek stated rate par rupaye mein convert karo.

### Provider ka quota theek se baantna

Aapka provider har model ke liye ek quota deta hai, jaise Mumbai mein har minute itne tokens. Har key use share karti hai. Rule: **jin features ko kabhi quota ki kami nahi honi chahiye, unki limits ka jod provider quota se kam hona chahiye, headroom ke saath.** Batch jobs ko chhoti limit milti hai, wo raat ko chalte hain, aur 429s par intezaar karte hain. Per-key limits ke bina pehla busy job poora quota le leta hai, aur customer chatbot fail ho jaata hai, bhale hi "provider up hai".

### Fallback edge cases

Production mein gateways fallbacks par hi fail hote hain. Inke liye plan karo:

- **Streams.** Agar stream pehle token se pehle fail ho, toh gateway agla deployment try kar sakta hai aur user ko kabhi pata nahi chalta; LiteLLM yahi karta hai. Jab user aadha answer dekh chuka ho, tab switch ka matlab hai answer restart karna ya do models ka text jodna. App mein tay karo ki kya dikhaana hai, jaise "answer beech mein ruk gaya, retry karein?".
- **Tool calls.** Aisi request ko kabhi retry mat karo jiski tool call pehle hi side effects waala kuch chala chuki ho, jaise payment ya email. Aise tools ko idempotency key ke saath dohraane ke liye safe banao, ya unhe retry mat karo.
- **Prompt caching.** Provider prompt caches aapke saath move nahi hote. Fallback ke dauraan har request lambe system prompt ke liye poori price aur poori latency deti hai, isliye outage ke dauraan cost aur time to first token uchhalne ki ummeed rakho.
- **Format aur tool-call shape.** Backup model JSON ya tool calls ko thoda alag format kar sakta hai. Feature ke evals fallback alias par chalao, aur uske output par parser test karo.
- **Wo errors jin par fall back nahi hona chahiye.** Malformed request har model par fail hoti hai. Fall back karne se sirf latency aur cost badhti hai. Timeouts, 429s aur server errors par fall back karo.
- **Tooti key ko chhupaane waale fallbacks.** Ek test mein primary ki galat key ne 401 return kiya, gateway ne use retry nahi kiya, aur turant fall back kar diya. Users ko kuch galat nahi dikha. Sirf errors par nahi, kisi alias ka fallback rate badhne par bhi alert karo.

### Try it: fallback chain mein cool-downs

Is simulation mein request 3 se request 12 tak Mumbai outage hai. Dekho ki cool-down kaise requests ko Mumbai ka intezaar karne se rokta hai, aur bahut lamba cool-down kaise Mumbai ke theek hone ke baad bhi use skip karta rehta hai.

```python
import random

random.seed(7)
ALLOWED_FAILS = 2      # cool down after more than this many failures
COOLDOWN = 5           # requests to skip a cooling deployment
fails = {"mumbai": 0, "hyderabad": 0, "backup": 0}
cooling_until = {"mumbai": 0, "hyderabad": 0, "backup": 0}

def call(deployment, t):
    # Mumbai has an outage from request 3 to request 12.
    if deployment == "mumbai" and 3 <= t <= 12:
        raise TimeoutError("timed out")
    if random.random() < 0.05:
        raise TimeoutError("timed out")
    return deployment

def gateway(t, chain=("mumbai", "hyderabad", "backup")):
    tried = []
    for d in chain:
        if t < cooling_until[d]:
            continue                       # skip without waiting for a timeout
        try:
            served = call(d, t)
            fails[d] = 0
            return served, tried
        except TimeoutError:
            tried.append(d)
            fails[d] += 1
            if fails[d] > ALLOWED_FAILS:
                cooling_until[d] = t + COOLDOWN
                fails[d] = 0
    return "error", tried

for t in range(16):
    served, tried = gateway(t)
    note = f"(waited on {', '.join(tried)})" if tried else ""
    print(f"request {t:2}: served by {served:9} {note}")
```

Requests 3 se 5 tak har ek Mumbai timeout ka intezaar karti hai. Phir Mumbai cool down hota hai aur requests 6 se 9 seedhe Hyderabad jaati hain. Request 8 doosri layer dikhaati hai: Hyderabad mein ek random timeout aata hai, isliye backup jawaab deta hai. Request 10 par cool-down khatam hota hai jabki Mumbai abhi bhi down hai, isliye requests 10 se 12 phir uska intezaar karti hain aur doosra cool-down shuru hota hai. Request 13 se Mumbai wapas aa jaata hai, par wo abhi bhi cool down ho raha hai, isliye use nahi hota. Timeouts par intezaar karne aur recovery miss karne ke beech ka trade-off dekhne ke liye `COOLDOWN = 2` aur `ALLOWED_FAILS = 0` try karo.

### Region-aware routing aur logs

Indian personal data ke liye, un features ke aliases sirf Indian-region deployments ki or point karne chahiye. Jin features ko doosre regions use karne ki ijaazat hai, unke liye alag alias rakho. Har call ka alias, deployment aur region log karo, taaki audit confirm kar sake ki rule maana gaya. Gateway ke logs mein personal data mask karo: wo har prompt dekhta hai, isliye unmasked logs use aapka sabse bada sensitive data store bana dete hain.

### Gateway ki cost

Ye chalaane, secure karne aur available rakhne ke liye ek aur service hai, aur har AI feature is par nirbhar hai. Iska apna overhead measure karo: wahi requests ka set seedhe aur gateway ke through bhejo, aur median aur slow (p95) latency compare karo, khaaskar streams ke liye time to first token. Ise apne apps ke paas rakho, iska error rate aur database monitor karo, aur ek documented emergency path rakho, jaise ek feature flag jo kisi ek critical feature ko seedhe uske provider par bhej de.

## Ek worked example

Bengaluru ki fintech mein chaar teams ke paanch AI features hain. Har team ke paas apni provider keys hain, aur finance ko ek bada monthly bill dikhta hai. Neeche ke aankde ek typical rollout ka illustration hain, measured results nahi.

**Trigger.** Ek provider outage ne customer chatbot ko kareeb 50 minute tak down rakha. Usi mahine ek nightly statement-summary job subah tak khinch gaya aur shared token quota ka zyaadatar hissa use kar gaya, isliye chatbot ne rate-limit errors bhi diye.

**Setup.** Platform team company ke Kubernetes cluster par gateway ko do instances ke roop mein deploy karti hai.

- **Keys.** Har feature ko team aur feature tag waali apni gateway key milti hai. Provider keys gateway ke secret store mein chali jaati hain aur rotate hoti hain. Puraani direct keys do hafte chalti hain, phir revoke hoti hain, taaki gateway hi akela raasta bane.
- **Aliases.** `chat-default`, `extract-default` aur `embed-default`, har ek kisi specific model se mapped.
- **`chat-default` ke liye failover.** Wahi model Mumbai aur Hyderabad mein, 60-second cool-down ke saath, phir ek fallback alias jismein doosre provider ka model hai, wo bhi India mein hosted aur compliance se approved.
- **Fallback par evals.** Go-live se pehle team chatbot ka 300-question golden set dono par chalaati hai. Maan lo primary 92% aur backup 88% score karta hai, do JSON format failures ke saath jinhe ek parser fix theek kar deta hai. Team outages ke liye 88% accept karti hai aur runbook mein record karti hai.
- **Quota sharing.** Maan lo Mumbai quota har minute 400,000 tokens hai. Chatbot ko 200,000 aur claims extraction ko 100,000 milte hain. Batch job ko 60,000 milte hain aur wo midnight ke baad chalta hai. Kul 360,000, jisse spikes ke liye headroom bachta hai.
- **Budgets aur logs.** Har key ka ek monthly budget hai, 75% par alert ke saath. Har request team, feature, alias, deployment, tokens, cost aur latency ke saath log hoti hai, personal data mask karke.

**Result.** Agle provider incident mein users ko errors ki jagah thodi der dheeme answers milte hain, jab tak Mumbai cool down hota hai aur Hyderabad serve karta hai. Fallback-rate alert on-call engineer ko batata hai ki kya hua. Feature ke hisaab se pehli cost report dikhaati hai ki statement-summary job kareeb 40% spend use kar raha hai. Wo team use ek saste model aur provider ke batch API par le jaati hai.

## Aam galtiyaan

- **Ek hi gateway instance.** Aapne har AI feature ke liye ek naya single point of failure bana diya. Kai chalao.
- **Unapproved models ya regions par fallbacks.** Outage ko data chupchaap aisi jagah nahi bhejna chahiye jahan use jaane ki ijaazat nahi hai. Ismein Bedrock APAC ya global profiles bhi shaamil hain jab data India mein hi rehna ho.
- **Application code mein model names.** Aliases use karo taaki upgrades aur swaps ek hi jagah hon.
- **Key limits jinka jod provider quota se zyada hai.** Tab ek busy key phir bhi baakiyon ka quota kha sakti hai.
- **Budget error ko retry karna.** Khatam hua budget kuch seconds mein dobaara nahi bharega. Use final maano aur kisi ko alert karo.
- **Untested fallbacks.** Jo fallback kabhi chala hi nahi, wo pehli baar chalne par output formats ya quality tod sakta hai.
- **Sirf errors par alert karna.** Fallbacks failures ko users se chhupa dete hain, isliye tooti primary key hafton tak kisi ki nazar mein aaye bina reh sakti hai.
- **Bina masking ke full prompts waale gateway logs.** Gateway aapke paas ka sabse bada sensitive data store ban jaata hai.

## Kab gateway zaroorat se zyada hai

- **Ek provider waala ek app.** Retries, timeout aur billing alert ke saath provider ka SDK kaafi hai.
- **Ek chhoti team**, jo gateway jitna samay bachaayega usse zyada use chalaane mein laga degi.
- **Ek managed platform**, jo pehle se keys, budgets aur routing deta hai.

Gateway tab faayda deta hai jab kai teams ya apps providers, keys, quota aur budgets share karne lagein.

## Demo se production tak

- **Do ya zyada instances chalao**, health checks, unki apni monitoring aur ek shared database ke saath.
- **Config Git mein rakho**, code ki tarah review karo, aur model changes golden set par test karo.
- **Har feature ke liye ek key do**, rate limit, budget aur ek named owner ke saath.
- **Personal data sirf approved regions par route karo**, aur har call ka region log karo.
- **Staging mein failover drill karo.** Galat key ya blocked endpoint se primary ko jaanboojhkar todo. Check karo ki requests phir bhi succeed hoti hain, latency acceptable rehti hai, aur logs aur headers dikhaate hain ki kis model ne serve kiya. Chain mein har badlaav ke baad dohraao.
- **Pehle ek low-risk feature roll out karo**, uske errors, latency aur cost pehle se compare karo, phir baakiyon ko ek-ek karke move karo.
