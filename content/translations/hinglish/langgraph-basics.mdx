## Ye kya hai

LangGraph ek open-source Python aur JavaScript framework hai, jisse agents aur multi-step AI workflows ko **graphs** ki tarah banaya jaata hai. Ek graph ke chaar hisse hote hain:

- **State**: ek typed dictionary jismein wo sab rehta hai jo run ko pata hai, jaise messages, ticket id aur ek proposed credit.
- **Nodes**: functions jo state padhte hain aur sirf wahi fields lautaate hain jo wo badalte hain. Node model call kar sakta hai, tool call kar sakta hai ya plain code chala sakta hai.
- **Edges**: aage kaun-sa node chalega. **Conditional edge** ek function hai jo state padhkar agle node ka naam lautaata hai.
- **Checkpointer**: har step ke baad state ko ek `thread_id` ke neeche save karta hai, taaki run pause ho sake, resume ho sake, restart jhel sake aur replay ho sake.

Agent loop ek chhota graph hai: ek model node, ek tool node, aur ek conditional edge jo dono ke beech tab tak loop karta hai jab tak model tools maangna band na kar de. Workflow fixed edges waala graph hai. LangGraph aapko dono ko ek hi system mein milaane deta hai.

Ye lesson ek hi graph shuru se aakhir tak banata hai. Chennai ke ek broadband provider ke paas support tickets aate hain. Billing tickets mein bina service waale dinon ke liye credit mil sakta hai, aur har credit billing system tak pahunchne se pehle ek supervisor ko approve karna hota hai.

```flow
title: Support-ticket graph (har step ke baad state save hoti hai, har thread_id ke liye alag)
START -> classify
classify -[billing]-> billing_agent | outage ke din dekhta hai, credit propose karta hai
classify -[outage]-> outage_agent
billing_agent -[credit zero se zyada]-> approve_credit | interrupt: supervisor faisla karta hai
billing_agent -[koi credit nahi]-> reply
approve_credit -[approve hua]-> apply_credit | billing system ko ek hi baar call karta hai
approve_credit -[reject hua]-> reply
apply_credit -> reply
outage_agent -> END
reply -> END
```

### Poora graph

Ise ek baar upar se neeche tak padho. Model aur billing system ki jagah chhote stand-ins hain, isliye ye bina API key ke chalta hai. Ise `ticket_graph.py` naam se save karo; aage ke blocks isi ke naam use karte hain.

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Ticket(TypedDict, total=False):
    messages: Annotated[list, add_messages]  # reducer: new messages are appended
    ticket_id: str
    category: str              # "billing" or "outage"
    outage_days: int
    proposed_credit_inr: int
    approved_credit_inr: int   # 0 means the supervisor said no
    credit_ref: str

# Stand-ins for real systems, so the graph runs with no API key.
OUTAGE_DAYS = {"TKT-4471": 3}     # the network status tool
CREDITS = {}                      # the billing system, keyed by idempotency key

def add_credit(key: str, amount_inr: int) -> str:
    return CREDITS.setdefault(key, f"CR-{len(CREDITS) + 1:04d}")  # same key, one credit

def classify(state: Ticket) -> dict:
    text = state["messages"][-1].content.lower()   # a model call in real life
    return {"category": "billing" if "bill" in text else "outage"}

def route_ticket(state: Ticket) -> str:
    return "billing_agent" if state["category"] == "billing" else "outage_agent"

def billing_agent(state: Ticket) -> dict:
    days = OUTAGE_DAYS.get(state["ticket_id"], 0)
    return {"outage_days": days, "proposed_credit_inr": min(days * 100, 500)}

def outage_agent(state: Ticket) -> dict:
    return {"messages": [("ai", "There is a fibre cut in your area. We will update you by 6 pm.")]}

def approve_credit(state: Ticket) -> dict:
    decision = interrupt({                          # the run pauses here
        "ticket_id": state["ticket_id"],
        "proposed_credit_inr": state["proposed_credit_inr"],
        "reason": f"{state['outage_days']} days without service",
    })
    # On resume this node runs again from the top, and interrupt() returns the decision.
    return {"approved_credit_inr": decision["credit_inr"] if decision["approved"] else 0}

def apply_credit(state: Ticket) -> dict:
    ref = add_credit(key=state["ticket_id"], amount_inr=state["approved_credit_inr"])
    return {"credit_ref": ref}

def reply(state: Ticket) -> dict:
    amount = state.get("approved_credit_inr", 0)
    text = (f"We have added a ₹{amount} credit to your next bill (ref {state['credit_ref']})."
            if amount else "We checked your account. No credit applies this time.")
    return {"messages": [("ai", text)]}

g = StateGraph(Ticket)
for node in (classify, billing_agent, outage_agent, approve_credit, apply_credit, reply):
    g.add_node(node)                                # the node is named after the function
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route_ticket, ["billing_agent", "outage_agent"])
g.add_conditional_edges("billing_agent",
    lambda s: "approve_credit" if s["proposed_credit_inr"] > 0 else "reply",
    ["approve_credit", "reply"])
g.add_conditional_edges("approve_credit",
    lambda s: "apply_credit" if s["approved_credit_inr"] > 0 else "reply",
    ["apply_credit", "reply"])
g.add_edge("apply_credit", "reply")
g.add_edge("outage_agent", END)
g.add_edge("reply", END)
app = g.compile(checkpointer=InMemorySaver())
```

Credit policy (bina service waale har din ke ₹100, zyada se zyada ₹500) is lesson ke liye ek example hai, kisi asli provider ka rule nahi. Asli system mein `classify` ek model call hoga jo ek label lautaata hai, aur `billing_agent` ek chhota model-and-tool loop hoga (neeche prebuilt agent dekho). Har `add_conditional_edges` call ke aakhir waali list un nodes ke naam batati hai jo route lauta sakta hai. `app.get_graph().draw_mermaid()` graph ko Mermaid diagram ke roop mein print karta hai; ye jaldi se check karne ka tareeka hai ki edges waise hi hain jaisa aapne socha tha.

### State updates kaise merge hote hain

Node sirf wahi fields lautaata hai jo wo badalta hai, aur LangGraph unhein state mein merge kar deta hai. Zyadatar fields mein nayi value puraani ko replace kar deti hai. Jis field mein **reducer** ho, jaise `add_messages` waala `messages`, wo replace hone ki jagah combine hota hai: naye messages aakhir mein jud jaate hain. Isiliye `reply` ek message lautaata hai aur customer ka message bana rehta hai. Reducer bhool gaye to `messages` mein likhne waala har node poori conversation mita dega. Shuruaat mein sabse aam bug yahi hai.

### Pause, approve, resume

Har run ek thread ka naam leta hai. Yahaan thread hi ticket hai, isliye TKT-4471 se judi har cheez ek hi jagah rehti hai:

```python
config = {"configurable": {"thread_id": "TKT-4471"}, "recursion_limit": 20}
first = {"ticket_id": "TKT-4471",
         "messages": [("user", "Net was down 3 days. Why is my bill the full ₹799?")]}
out = app.invoke(first, config)
print(out["__interrupt__"][0].value)
# {'ticket_id': 'TKT-4471', 'proposed_credit_inr': 300, 'reason': '3 days without service'}

# Hours later, the supervisor's dashboard resumes the same thread:
out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
print(out["messages"][-1].content)
# We have added a ₹300 credit to your next bill (ref CR-0001).
```

Approval ko safe banaane waale teen rules:

- **Resume par node dobara chalta hai.** LangGraph `interrupt()` ke baad waali line se aage nahi badhta; wo `approve_credit` ko uski pehli line se dobara chalata hai, aur is baar `interrupt()` faisla lautaata hai. Ek test mein `interrupt()` se pehle rakha counter do baar badha. Isliye `interrupt()` se pehle ki kisi cheez ka side effect nahi hona chahiye.
- **Action agle node mein rakho.** Credit `approve_credit` mein nahi, `apply_credit` mein lagta hai. Wo node ticket id ko idempotency key ki tarah use karta hai, isliye wo do baar bhi chal jaaye to customer ko ek hi credit milta hai.
- **Supervisor edit kar sakta hai.** Resume value wahi hai jo aapka dashboard bheje. `{"approved": True, "credit_inr": 250}` bhejoge to ₹250 lagega.

Checkpointer ke bina bhi `interrupt()` run rok deta hai, lekin `Command(resume=...)` "Cannot use Command(resume=...) without checkpointer" ke saath fail ho jaata hai. `compile(interrupt_before=["apply_credit"])` bhi pause karta hai, lekin node ke andar `interrupt()` se aap supervisor ko theek wahi data bhej sakte ho jo use chahiye.

### Checkpoints: inspect, replay aur fork

Har step save hota hai, isliye aap kisi thread ki history padh sakte ho, sabse naya pehle:

```python
for snap in app.get_state_history(config):
    print(snap.metadata["step"], snap.next, snap.values.get("credit_ref"))
```

"Agar agent ne ₹200 propose kiya hota aur supervisor ne mana kar diya hota to?" Ye poochhne ke liye approval se theek pehle waale checkpoint se fork karo:

```python
past = next(s for s in app.get_state_history(config) if s.next == ("approve_credit",))
fork = app.update_state(past.config, {"proposed_credit_inr": 200})
out = app.invoke(None, fork)                       # runs on and pauses again, now at ₹200
out = app.invoke(Command(resume={"approved": False}), config)
print(out["messages"][-1].content)
# We checked your account. No credit applies this time.
```

`invoke(None, ...)` ka matlab hai "bina kisi naye input ke is checkpoint se aage chalo". Fork latest state ban jaata hai; original steps history mein bane rehte hain.

### Database checkpointer

`InMemorySaver` ek hi Python process ke andar rehta hai. Restart ya deploy hote hi har paused ticket kho jaata hai. Production mein checkpoints Postgres mein rakho, aur saver ko har request ke andar nahi, server start hone par ek baar banao:

```python
# pip install "langgraph-checkpoint-postgres==3.2.1" "psycopg[binary,pool]"
import os
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver

pool = ConnectionPool(os.environ["CHECKPOINT_DB_URL"],
                      kwargs={"autocommit": True, "prepare_threshold": 0}, open=True)
saver = PostgresSaver(pool)
saver.setup()                       # creates the checkpoint tables if missing
app = g.compile(checkpointer=saver)
```

Dono connection settings un settings mein se do hain jo `PostgresSaver.from_conn_string` use karta hai (row factory saver khud set karta hai). Wo helper ek `with` block hai jo apne aakhir mein connection band kar deta hai, jo script ke liye theek hai par web server ke liye nahi. Connection string ko environment variable mein rakho, aur shutdown par `pool.close()` call karo.

Is saver ke saath humne TKT-4471 ko ek process mein pause kiya, us process ko band kiya, aur ek naye process se approve kiya: thread tab bhi `approve_credit` par intezaar kar raha tha aur normal tareeke se poora hua.

**Crash aur pause alag cheezein hain.** Humne process ko `apply_credit` ke andar kill bhi kiya. Thread apne aap dobara shuru nahi hua. Naye process ne use `approve_credit` par paaya, kyunki default mode har step background mein save karta hai aur aakhri step abhi likha nahi gaya tha. `app.invoke(None, config)` ne saved faisle ke saath `approve_credit` dobara chalaya, phir `apply_credit` aur `reply`. `invoke` mein `durability="sync"` dene par har step agle ke shuru hone se pehle save hota hai, isliye tab thread `apply_credit` par intezaar kar raha tha. Isse do sabak nikalte hain: aakhri saved step ke baad waala node do baar chal sakta hai, isliye side effects idempotent banao; aur aapko ek chhota job chahiye jo adhoore threads ko aage badhaaye.

### Progress stream karna

Har step hote hi dekhne ke liye `invoke` ki jagah `stream` use karo:

```python
demo = {"configurable": {"thread_id": "TKT-4471-demo"}, "recursion_limit": 20}
for update in app.stream(first, demo, stream_mode="updates"):
    print(update)
# {'classify': {'category': 'billing'}}
# {'billing_agent': {'outage_days': 3, 'proposed_credit_inr': 300}}
# {'__interrupt__': (Interrupt(value={...}, ...),)}
```

Har item ek node ka update hai, isliye chat screen lambi chuppi ki jagah "Checking your connection…" dikha sakti hai.

### Model ke bina testing

Routes aur nodes plain functions hain, isliye zyadatar tests ko model ki zaroorat hi nahi:

```python
def test_billing_ticket_goes_to_billing_agent():
    assert route_ticket({"category": "billing"}) == "billing_agent"

def test_credit_waits_for_approval_then_applies():
    config = {"configurable": {"thread_id": "test-1"}, "recursion_limit": 20}
    out = app.invoke({"ticket_id": "TKT-4471",
                      "messages": [("user", "Why is my bill the full amount?")]}, config)
    assert out["__interrupt__"][0].value["proposed_credit_inr"] == 300
    out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
    assert out["credit_ref"].startswith("CR-")
```

Jo nodes model call karte hain, unmein fixed replies waala fake model pass karo, aur CI mein kuch saved asli tickets poore graph se chalao.

### Prebuilt agent

Puraane tutorials `langgraph.prebuilt.create_react_agent` use karte hain. LangGraph 1.0 se ye deprecated hai: ise call karne par warning aati hai ki ye "has been moved to `langchain.agents`". Abhi ka prebuilt model-and-tools loop LangChain ka `create_agent` hai, jo LangGraph par chalta hai:

```python
# pip install "langchain==1.5.2" plus your model provider's package
from langchain.agents import create_agent

def outage_days(ticket_id: str) -> int:
    """Days without service on this ticket's connection."""
    return OUTAGE_DAYS.get(ticket_id, 0)

billing_helper = create_agent(chat_model, tools=[outage_days],
                              system_prompt="You answer broadband billing questions.")
out = billing_helper.invoke({"messages": [("user", "Ticket TKT-4471: why is my bill high?")]})
```

`chat_model` koi bhi LangChain chat model hai jo tool calling support karta ho. Result ek compiled graph hai, isliye ye kisi aur bade graph ka ek node ban sakta hai. Ise **sub-graph** kehte hain. Plain tool loop ke liye `create_agent` se shuru karo. Jab routing, approvals ya kai specialists chahiye hon, tab apna `StateGraph` likho.

### Har run ki limit rakho

`recursion_limit` ek run mein steps ki ginti par cap lagaata hai. Run wahaan pahunche to LangGraph `GraphRecursionError` raise karta hai, jise aap catch karke kisi insaan ko handover mein badal sakte ho. Ise har call par khud set karo: default LangGraph 1.0.5 tak 25 tha, 1.0.6 se 1.1.3 tak 10,000 aur 1.1.4 se (1.2.24 samet) 10,007, isliye ek draft-and-check loop jo kabhi khud se santusht na ho, default ke rokne se pehle hazaaron model calls kar sakta hai.

### Basics se aage

- **Parallel branches.** Conditional edge kai `Send("node", data)` objects lautaakar ek node ko parallel mein kai baar chala sakta hai, jaise das connections ek saath check karna, aur ek reducer results merge karta hai.
- **Long-term memory.** Checkpoints ek thread ke hote hain. Jo facts customer ke saath har ticket mein chalne chahiye, jaise "Tamil pasand karte hain", wo `compile(store=...)` ke saath diye gaye ek **store** mein jaate hain, jaise `InMemoryStore` ya ek Postgres store.
- **Functional API.** `langgraph.func` ke `@entrypoint` aur `@task` bina graph banaaye ordinary Python functions ko checkpoints aur interrupts dete hain.
- **Tracing.** `LANGSMITH_TRACING=true` aur ek LangSmith API key ke saath har node ka input aur output record hota hai, isliye "bot ne kuch ajeeb kaha" ek link ban jaata hai jise aap khol sakte ho.

**Saare hisse ek nazar mein:**

| Hissa | Ticket graph mein | Gotcha |
| --- | --- | --- |
| Reducer waali state | `messages` mein `add_messages` | Reducer ke bina har reply history mita deta hai |
| Conditional edge | `route_ticket` aur dono lambdas | Apni possible nodes ki list mein se hi koi naam lautaana chahiye |
| Checkpointer | `InMemorySaver`, phir `PostgresSaver` | In memory mein restart par paused tickets kho jaate hain |
| `interrupt()` | `approve_credit` ke andar | Resume par node apni pehli line se dobara chalta hai |
| Idempotency key | `add_credit` mein ticket id | Iske bina rerun doosra credit laga deta hai |
| `recursion_limit` | Har config mein 20 | Default ab itna zyada hai ki aapko bacha nahi sakta |

## Ek example se samjho

Chennai mein ticket TKT-4471 aata hai: "Net was down 3 days. Why is my bill the full ₹799?" Table dikhaati hai ki checkpointer ne kya save kiya, upar waale code ke ek asli run se `get_state_history` se padhkar.

| Step | Agla node | State mein kya badla |
| --- | --- | --- |
| 0 | classify | Customer ka message aur `ticket_id` aa gaye |
| 1 | billing_agent | `category` = billing |
| 2 | approve_credit | `outage_days` = 3, `proposed_credit_inr` = 300. Run yahaan pause hota hai aur dashboard proposal dikhaata hai |
| 3 | apply_credit | Supervisor ke approve karne ke baad: `approved_credit_inr` = 300 |
| 4 | reply | `credit_ref` = CR-0001 |
| 5 | (poora) | Reply message jud gaya; ab do messages hain |

Teen baatein dekho. Pause ne apna koi alag checkpoint nahi joda: step 2 bas itna kehta hai ki agla node `approve_credit` hai. Approval aur side effect alag steps hain, isliye `approve_credit` dobara chale to bhi credit nahi laga sakta. Aur har value jo koi auditor poochh sakta hai (₹300 kyun, kaun-sa credit reference), wo kisi prompt ke andar chhipi nahi, ek saved state mein hai.

Usi ticket ke do variations:

- **Supervisor reject kar deta hai.** `approve_credit` ke baad route seedha `reply` par jaata hai, `apply_credit` kabhi nahi chalta, aur customer ko bataya jaata hai ki koi credit nahi banta.
- **Customer ek hafte baad complain karta hai.** Aap thread TKT-4471 kholte ho, har step padhte ho, aur original history ko chhue bina step 2 se fork karke test kar sakte ho ki alag credit se kya hota.

## Aam galtiyaan

- **Ek bahut bada node.** Classify, look up, approve aur reply sab ek function mein karne se wo visibility, testability aur safe pause points chale jaate hain jinke liye graph banaya jaata hai.
- **`interrupt()` se pehle side effects.** Resume par node upar se dobara chalta hai, isliye wahaan rakha SMS, email ya credit do baar ho jaata hai.
- **Actions jo idempotent nahi hain.** Resumes aur crash recovery kisi node ko dobara chala sakte hain. Har payment, credit ya message API ko ticket id jaisi idempotency key do.
- **Production mein in-memory checkpoints.** Har restart ya deploy par paused runs aur conversations kho jaati hain. Database checkpointer use karo aur uska backup lo.
- **Har message ke liye naya `thread_id`.** Tab assistant har baar conversation bhool jaata hai. Har conversation ya har ticket ke liye ek thread rakho, aur ek thread kabhi do customers ke beech share mat karo.
- **Bina limit badhti state.** Har tool result ko hamesha jodte rehne se prompts lambe aur mehenge ho jaate hain. Kisi node mein trim ya summarise karo.
- **Default `recursion_limit` par bharosa.** 1.2.24 mein ye 10,007 steps hai. Chhoti limit set karo aur `GraphRecursionError` catch karo.
- **Puraane tutorials copy karna.** Kai ab bhi deprecated `create_react_agent` use karte hain, ya `MemorySaver`, jo ab `InMemorySaver` ka alias hai. Versions pin karo aur upgrade se pehle changelog padho.

## Jab aapko LangGraph nahi chahiye

- **Simple tool loop**: agent-loop lesson waala chhota loop, `create_agent`, ya model provider ka apna agent SDK kaafi ho sakta hai.
- **Fixed pipeline** jismein pauses ya branching na ho: kram se call kiye gaye ordinary functions padhne aur debug karne mein zyada aasaan hain.
- **Pehle se kisi doosre framework par chal rahi team**, agar wo framework saved state, pauses aur tracing cover karta ho.

LangGraph tab apni jagah kamaata hai jab aapko har conversation ki saved state, insaanon ke liye pauses, branching, aur kisi run ko inspect aur replay karne ki kshamta chahiye.

## Demo se production tak

- **Database checkpointer use karo**, start-up par ek baar banao, aur baaki production data ki tarah uska backup lo.
- **Durability soch-samajhkar chuno.** Default background mein save karta hai; `durability="sync"` har agle step se pehle save karta hai, jo payments aur credits ke aaspaas extra time ke laayak hai.
- **Atke threads recover karo.** Ek chhota job chalao jo crash ke baad beech mein chhoote threads dhoondhe aur unhein `invoke(None, config)` se aage badhaaye.
- **Har run par `recursion_limit` aur timeout set karo**, aur `GraphRecursionError` ko kisi insaan ko handover mein badlo.
- **Graph ka version rakho.** Paused thread usi graph mein resume hota hai jo us waqt deployed ho. Naye state fields optional ke roop mein jodo, aur aise node ka naam na badlo, na use hatao jis par paused threads intezaar kar rahe ho sakte hain. Breaking change ke liye puraana graph tab tak chalaate raho jab tak uske paused threads poore na ho jaayein, ya pehle unhein approve ya cancel kar do.
- **Har node ko thread id ke saath trace karo**, taaki support ticket seedhe apne run tak le jaaye.
- **Routes, nodes aur kuch poore tickets** CI mein fake models ke saath test karo.

## Practice karo

LangChain Academy ka free Introduction to LangGraph karo, kam se kam pehle teen modules.

1. Upar waala ticket graph apni pasand ki do categories ke liye dobara banao, aise routing tests ke saath jinhein model ki zaroorat na ho.

**Aapka kaam poora hai jab aap** apna graph bana sako, bata sako ki state kahaan save hoti hai, samjha sako ki approval node dobara kyun chalta hai, aur apna program restart karne ke baad ek paused run resume kar sako.
