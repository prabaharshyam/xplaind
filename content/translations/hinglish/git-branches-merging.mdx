## Ye kya hai

Git mein **branch** ek label hota hai jo ek commit ki taraf point karta hai. Jab aap branch par naya commit karte ho, label uske aage badh jaata hai. Branch bas itna hi hai, isliye ise banana instant hai, aur teams har change ke liye ek banati hain: bug fix, feature, experiment.

Shared branch, jise aam taur par **main** kehte hain, hamesha kaam karti honi chahiye, kyunki sab usi par build karte hain aur wahi deploy hoti hai. Isliye main par seedha kaam kabhi nahi karte. Branch banao, wahan apna change banao aur test karo, aur ready hone par wapas lao.

Kaam ko wapas laane ke do tareeke hain:

- **Merge** history ki do lines ko jodta hai. Agar aapke branch karne ke baad main aage badh gaya, toh Git do parents waala ek **merge commit** banata hai. History bilkul dikhati hai ki kya hua, side branch ke saath.
- **Rebase** aapke commits ko kisi doosri branch ke upar replay karta hai, jaise aapne uske latest commit se shuru kiya ho. History seedhi line ban jaati hai, jo padhne mein aasaan hai, par aapke commits ke ids naye ho jaate hain.

Dono ka end code same hota hai. Farak is mein hai ki history kaisi dikhti hai aur ye kiske liye safe hai.

## Ye kaam kaise karta hai

Team mein roz ka loop kuch aisa dikhta hai:

```flow
title: Feature branch, shuru se merge tak
Update main | git switch main, git pull -> New branch | git switch -c feature/otp
New branch -> Commit small steps | git add, git commit
Commit small steps -> Push the branch | git push -u origin feature/otp
Push the branch -> Pull request | review and checks
Pull request -[main moved on]-> Bring main in | merge main, or rebase onto main
Bring main in -> Pull request
Pull request -[approved, green]-> Merge into main
Merge into main -> Delete the branch
```

**Banana aur switch karna.** `git switch -c feature/otp` jahan aap ho wahan branch banata hai aur aapko uspar le jaata hai. `git switch main` wapas le jaata hai. `git branch` branches ki list deta hai; current waali par star hota hai.

**Merge karna.** Main se `git merge feature/otp` branch ko andar laata hai. Agar aapke branch karne ke baad main aage nahi badha, toh Git **fast-forward** karta hai: bas main ka label aapke last commit par le jaata hai. Agar main aage badh gaya hai, toh Git merge commit banata hai.

**Conflicts.** Agar dono taraf ne ek hi file ki same lines badli hain, toh Git ruk jaata hai aur file ko mark kar deta hai:

```text
<<<<<<< HEAD
OTP_EXPIRY_SECONDS = 300
=======
OTP_EXPIRY_SECONDS = 120
>>>>>>> feature/otp
```

`=======` ke upar waala hissa aapki current branch par hai; neeche waala incoming change hai. Aap file ko apne chahe version mein edit karte ho, markers delete karte ho, uspar `git add` chalate ho, aur commit karte ho. Conflict error nahi hai. Ye Git ka ek sawaal hai jiska jawab woh akele nahi de sakta.

**Rebase karna.** Apni branch par `git rebase main` aapke commits ko ek taraf rakh deta hai, aapki branch ko main ke tip par le jaata hai, aur unhe ek-ek karke replay karta hai. Agar koi conflict kare, toh Git ruk jaata hai; aap file fix karo, `git add` karo aur `git rebase --continue` chalao. `git rebase --abort` sab kuch waise hi wapas rakh deta hai jaisa tha.

| | Merge | Rebase |
| --- | --- | --- |
| History | Dono lines rakhta hai, merge commit jodta hai | Ek seedhi line |
| Commit ids | Nahi badalte | Aapke commits ke naye ids |
| Shared branches par safe | Haan | Nahi: sirf un commits par jo kisi aur ke paas nahi |
| Conflicts | Merge mein ek baar resolve hote hain | Har commit par resolve karne pad sakte hain |
| Kiske liye achha | Poori ho chuki branch ko main mein laana | Review se pehle apni branch update karna |

Kai teams dono ko milati hain: kaam ke dauran apni branch current rakhne ke liye rebase, aur pull request main mein jaate waqt merge (aksar **squash merge**, jo branch ko ek commit bana deta hai).

## Ek worked example

Priya Bengaluru ke ek fintech startup mein login service par kaam karti hai. Uska ticket: OTP expiry ko paanch minute se ghata kar do minute karna.

Woh fresh main se shuru karke ek branch banati hai:

```bash
git switch main
git pull
git switch -c feature/otp-expiry
```

Woh `config.py` mein `OTP_EXPIRY_SECONDS` badalti hai, test update karti hai, aur do baar commit karti hai: ek commit change ke liye, ek test ke liye. Branch push karke pull request kholti hai.

Jab uski pull request review ka intezaar kar rahi hai, uska teammate Arjun usi line par ek change merge kar deta hai: usne value ko 300 seconds kar diya aur ek regulator guideline ka comment jod diya. Priya ki pull request ab "This branch has conflicts" dikhati hai.

Uski branch uski apni hai aur kisi ne use pull nahi kiya, isliye woh rebase karti hai:

```bash
git fetch origin
git rebase origin/main
```

Git uska pehla commit replay karta hai aur ruk jaata hai: `config.py` mein conflict hai. Woh Arjun ka comment padhti hai, apne lead se check karti hai, aur pata chalta hai ki regulator is flow ke liye 120 seconds allow karta hai. Woh apni value rakhti hai, Arjun ka comment bhi rakhti hai, markers hatati hai aur continue karti hai:

```bash
git add config.py
git rebase --continue
git push --force-with-lease
```

`--force-with-lease` GitHub par uski branch replace karta hai, lekin tabhi jab beech mein kisi aur ne usmein push nahi kiya. Rebase ke baad push karne ka ye safe tareeka hai. Pull request green aur conflict-free hai; approve hoti hai aur ek clean commit ki tarah main mein squash-merge ho jaati hai, aur woh branch delete kar deti hai.

## Aam galtiyaan

- **Seedha main par kaam karna.** Ek bad commit sabka base tod deta hai. Ek line ke fix ke liye bhi hamesha branch banao.
- **Bahut lambi chalne waali branches.** Teen hafte jeene waali branch dardnaak conflicts jama kar leti hai. Chhote changes ko jaldi-jaldi merge karo.
- **Shared branch ko rebase karna.** Jin commits ko teammates pull kar chuke hain unhe rewrite karne se unke paas aisi copies reh jaati hain jo ab match nahi karti. Sirf apna unshared kaam rebase karo.
- **Seedha `git push --force`.** Ye teammate ke commits mita sakta hai. `--force-with-lease` use karo, aur sirf apni branch par.
- **Aankh band karke conflicts resolve karna.** Dono padhe bina "mine" ya "theirs" chunne se kisi ka fix chupchaap undo ho sakta hai. Dono sides padho, aur baad mein tests chalao.
- **Conflict markers commit kar dena.** Commit se pehle `<<<<<<<` search karo. Kai teams iske liye CI mein check jod deti hain.

## Practice karo

1. Ek file waali practice repository banao. Do branches banao jo dono line 3 badlein, ek ko main mein merge karo, phir doosri ko merge karke conflict resolve karo.
2. Teen chhote commits waali ek branch banao. Jab tak woh hai, main mein ek commit jodo. Apni branch ko main par rebase karo aur pehle aur baad `git log --oneline --graph --all` dekho.
3. Rebase ke beech mein `git rebase --abort` try karo aur confirm karo ki sab kuch waise hi wapas aa gaya.
4. Interview mein jaise bologe, ek minute ke andar zor se samjhao ki aap kab merge karoge aur kab rebase.
