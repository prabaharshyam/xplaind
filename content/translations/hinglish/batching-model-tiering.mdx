## Ye kya hai

Teen cost levers jo saath milkar kaam karte hain:

- **Model tiering** (ya routing). Har request ko sabse capable model ki zaroorat nahi hoti. Classify karna, extract karna ya aasaan sawaalon ke jawaab dena ek chhote, saste, tez model se karwao, aur sirf mushkil waali requests bade model ko bhejo.
- **Reasoning effort.** Aaj ke models jawaab dene se pehle sochte hain, aur un thinking tokens ka bill output tokens ki tarah banta hai, bhale aap wo text kabhi na dekho. Model kitna soche, ye ek effort setting tay karti hai. Aasaan, zyada volume waale kaam ko default ki zaroorat kam hi padti hai.
- **Batching.** Jis kaam ka jawaab seconds mein nahi chahiye, wo provider ke **batch API** se jaata hai: aap ek saath bahut saari requests upload karte ho aur results baad mein badi chhoot par lete ho. Examples hain raat mein documents tag karna, kal ke tickets ka summary banaana aur kisi archive ko re-score karna.

Shabdon par ek note. Is lesson mein "batching" ka matlab provider ka discount waala, asynchronous product hai. **Continuous batching** kuch aur hai: wo tareeka jisse vLLM jaisa serving engine aapke apne GPUs par ek saath bahut saari requests pack karta hai. "Inside LLM inference: prefill, decode and the KV cache" lesson use cover karta hai.

Teenon levers is par tike hain ki aap apna traffic jaante ho: kitni requests aasaan hain, aur kitni ruk sakti hain.

```flow
title: Har request kahaan jaati hai
Incoming work -> Kya ye ghanton ruk sakta hai?
Kya ye ghanton ruk sakta hai? -[haan]-> Aadhi keemat par Batch API | apne id se results match karo, failures retry karo
Kya ye ghanton ruk sakta hai? -[nahi]-> Chhota model, low effort -> Validator pass hua?
Validator pass hua? -[haan]-> Answer
Validator pass hua? -[nahi, lagbhag 7%]-> Bada model -> Answer
Fit summaries jaise mushkil tasks -[seedhe]-> Bada model
```

Ye lesson Pune ki ek HR-tech company ki resume-screening service ko follow karta hai, jo mahine mein 400,000 resumes process karti hai.

## Ye kaam kaise karta hai

### Teen tiering patterns

- **Task ke hisaab se fixed.** Har feature wo sabse sasta model use karta hai jo uske evals pass kare. Standard form se extraction ke liye shaayad chhota model kaafi ho; legal summary ke liye bada chahiye ho sakta hai. Ye sabse simple aur sabse common pattern hai. Yahin se shuru karo.
- **Cascade.** Pehle chhota model try karo, uska output check karo, aur sirf check fail hone par bade model par escalate karo. Ye un tasks ke liye theek hai jahaan ek sasta check achhe aur kharaab output mein farq kar sake, jaise structured extraction.
- **Router.** Ek classifier, ya ek chhota model, mushkil ka andaaza lagaakar pehle hi model chunta hai. RouteLLM jaise research systems ye preference data se seekhte hain. Router chat ke liye theek hai, jahaan aap ek ke baad ek do calls nahi jhel sakte aur check karne ke liye abhi koi output bhi nahi hota.

Har route ko apna eval chahiye. Asli sawaal "kya chhota model achha hai?" nahi, balki "kya wo un requests par kaafi achha hai jo hum use bhejte hain?" hai.

### Cascade ka cost formula

Har item par cascade ka kharch hai chhoti call, aur jo hissa escalate hota hai uske liye badi call:

`cost per item = small cost + escalation rate × large cost`

Escalate hue items dono calls ka paisa dete hain. Toh dasven hisse ki keemat waala chhota model, 40% escalation ke saath, akele bade model ka 0.1 + 0.4 = 0.5 padta hai: aadhi keemat, agar quality bani rahe. 20 guna ya usse zyada ke price gap par, jaise Haiku 5.5 aur Sonnet 5.5 ke beech, cascade tab tak sasta rehta hai jab tak lagbhag har item escalate na hone lage. Paisa kam hi risk hota hai. Risk do cheezein hain: wo galat jawaab jo check nikal jaane deta hai, aur escalate hui requests ka extra intezaar.

### Validators aur unka miss rate

Kya escalate hoga, ye check tay karta hai, toh ise bhi kisi aur model ki tarah test karo. Saste checks layers mein lagao:

1. **Format.** Kya output schema ke hisaab se parse hota hai?
2. **Range.** Kya values sahi lagti hain? Jaise, years of experience 0 se 50 ke beech, aur kam se kam ek skill.
3. **Grounding.** Kya jawaab source mein maujood hai? Jaise, candidate ka naam, zyaadatar listed skills aur last employer resume text mein hone chahiye. Ye un gadhe hue values ko pakadta hai jo format mein bilkul theek dikhte hain.
4. **Call se milne waale signals.** Jo response `max_tokens` par pahunchkar ruk gaya, ya koi refusal, wo failure hai, jawaab nahi.

Phir chhote model ko ek labelled golden set par chalao aur **miss rate** gino: jo outputs galat the, unmein se kitne har check pass kar gaye? Format checks zordaar failures pakadte hain. Chupchaap waali errors (ek bharosemand lagne waala par galat employer) unhe pass kar jaati hain. Free text ke liye model ka khud kaha "unsure" ya ek sasta judge model ek signal jod sakta hai, par uska miss rate bhi isi tarah naapo.

### Reasoning effort aur thinking tokens

Claude models par `output_config.effort` mein `low`, `medium`, `high`, `xhigh` ya `max` diya jaata hai. Ye thinking samet saare output tokens ko shape karta hai. November 2026 ke hisaab se default Claude Haiku 5.5 aur Claude Opus 5.5 par `medium` hai aur Claude Sonnet 5.5 par `high`. Anthropic aasaan, zyada volume waale kaam ke liye `low` suggest karta hai.

Teen gotchas:

- **Thinking `max_tokens` mein gini jaati hai.** Bahut tight `max_tokens` jawaab ko beech mein kaat sakta hai. Jagah chhodo, aur `stop_reason == "max_tokens"` ko failure maano.
- **Thinking switches har model par alag hain.** Haiku 5.5 par `high` effort ya usse neeche aap `thinking: {"type": "disabled"}` bhej sakte ho. Sonnet 5.5 aur Opus 5.5 ise error ke saath reject karte hain, toh wahaan effort ghatao.
- **Effort ek chautha tier hai.** Cascade banaane se pehle bade model ko kam effort par bhi test karo. Kabhi-kabhi usse ek hi model aur ek hi cache mein quality bani rehti hai.

Har route ke liye `usage.output_tokens` padho. Agar output tokens dikhne waale jawaab se bahut zyada hain, toh aapka paisa thinking mein ja raha hai.

### Batching: ye kaise chalta hai

Ye 28 November 2026 ke hisaab se Anthropic ke Message Batches rules hain; baaki providers details mein alag hain.

- **Price:** input aur output tokens par 50% chhoot. OpenAI aur Google bhi discount waale batch modes dete hain; unki maujooda terms check karo.
- **Speed:** zyaadatar batches ek ghante ke andar khatam ho jaate hain, par jo request 24 ghante mein process nahi hoti wo expire ho jaati hai. Jis kaam ka koi intezaar kar raha ho, use kabhi batch mat karo.
- **Size:** har batch mein 100,000 requests ya 256 MB tak. Results 29 din tak milte rehte hain.
- **Results:** ye kisi bhi order mein aa sakte hain. Apne `custom_id` se match karo. Har item `succeeded`, `errored`, `canceled` ya `expired` hota hai, aur aakhri teen ka bill nahi banta.
- **Limits:** batches ki apni rate limits hain, jo saare models mein shared hain: per minute requests, aur queue mein intezaar kar rahi requests par ek cap (Build tier par 300,000). Ye real-time limits se alag hain, aur batches par ramp limits laagu nahi hotin. Isliye raat ka bada job un per-minute token limits ko khatam nahi karta jin par din mein recruiters nirbhar hain.
- **Batch mein allowed nahi:** streaming, fast mode aur server-side fallbacks.

### Is picture mein caching

Prompt caching, tiering aur batching ke saath jud jaati hai. Stable hissa pehle rakho (instructions, phir job description) aur use `cache_control` se mark karo. Claude Opus 5.5, Sonnet 5.5 aur Haiku 5.5 kam se kam 512 tokens ke prefixes cache karte hain; isse chhota prefix bina kisi error ke aam tarah process hota hai. 5-minute cache write ki keemat input price ka 1.25 guna hai aur 1-hour write ki 2 guna. Reads bahut saste hain. Batches mein cache hits best effort hote hain, kyunki requests kisi bhi order mein chalti hain. 1-hour cache use karo, aur jaisa Anthropic suggest karta hai, baaki submit karne se pehle prefix likhne ke liye ek request pehle bhejo.

### Code mein ek cascade

Low effort par chhota model, layers mein checks, aur bada model sirf tab jab koi check fail ho:

```python
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()
SMALL, LARGE = "claude-haiku-5-5", "claude-sonnet-5-5"   # check the models page for current names

PROMPT = ("Return only JSON with name, years_experience, skills and "
          "last_employer (null if absent). Copy names exactly as written.\n\n")

class Resume(BaseModel):
    name: str
    years_experience: float
    skills: list[str]
    last_employer: str | None = None

def extract(model, effort, text):
    r = client.messages.create(
        model=model, max_tokens=2000,              # thinking counts toward max_tokens
        output_config={"effort": effort},
        messages=[{"role": "user", "content": PROMPT + text}])
    if r.stop_reason != "end_turn":                # cut off or refused: treat as a failure
        return None, r.usage
    return "".join(b.text for b in r.content if b.type == "text"), r.usage

def valid(raw, text):
    if raw is None:
        return None
    try:
        item = Resume.model_validate_json(raw)
    except ValidationError:
        return None
    page = text.lower()
    words = item.name.lower().split()
    if not words or not all(w in page for w in words):          # name must be in the resume
        return None
    if not 0 <= item.years_experience <= 50 or not item.skills:
        return None
    found = sum(s.lower() in page for s in item.skills)
    if found < 0.8 * len(item.skills):                          # most skills must be in the text
        return None
    if item.last_employer and item.last_employer.lower() not in page:
        return None
    return item

def cascade(text, stats):
    raw, _ = extract(SMALL, "low", text)
    stats["small"] += 1
    if item := valid(raw, text):
        return item
    stats["escalated"] += 1
    raw, _ = extract(LARGE, "high", text)
    return valid(raw, text)                                      # None goes to a person
```

Khaali name `if not words` check mein fail hota hai aur crash hone ki jagah escalate hota hai. Escalation rate roz track karo. Agar ye badhe, toh koi naye tarah ka input aaya hai aur bachat ghat rahi hai.

### Fit summary, cached aur batched

Ek hiring drive mein har resume ke liye job description ek jaisa hota hai, toh wo pehle jaata hai aur caching ke liye mark hota hai:

```python
import time

def run_batch(items, job_description):
    batch = client.messages.batches.create(requests=[
        {"custom_id": it["id"],                                  # your id: 1-64 letters, digits, - or _
         "params": {"model": LARGE, "max_tokens": 4000,
                    "output_config": {"effort": "medium"},
                    "system": [{"type": "text",
                                "text": "You screen resumes for this role.\n\n" + job_description,
                                "cache_control": {"type": "ephemeral", "ttl": "1h"}}],
                    "messages": [{"role": "user",
                                  "content": "Write a five-line fit summary.\n\n" + it["text"]}]}}
        for it in items])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    done, retry = {}, []
    for r in client.messages.batches.results(batch.id):         # any order: key by custom_id
        if r.result.type == "succeeded":
            m = r.result.message
            done[r.custom_id] = "".join(b.text for b in m.content if b.type == "text")
        else:                                                    # errored, expired or canceled
            retry.append(r.custom_id)
    return done, retry
```

`retry` ko ek naye, chhote batch mein bhejo, ya agar recruiters ko subah tak chahiye toh real-time path par. Batch outputs ko bilkul waise hi validate karo jaise real-time waalon ko. Ek sample par `usage.cache_read_input_tokens` check karo: agar ye zero par hi rahe, toh prefix mein kuch badal raha hai.

## Ek example se samjho

Pune ki ek HR-tech company apne clients ke liye resumes screen karti hai. Har resume ka structured extraction hota hai (name, experience, skills, last employer) aur job description ke hisaab se ek fit summary banti hai. Volume mahine mein 400,000 resumes hai, jinmein se lagbhag 80% hiring drive se pehle waali shaam ko bulk mein upload hote hain.

Neeche ke saare figures assumed token counts ke saath ek illustration hain, misaal ke taur par ₹90 ka ek dollar aur upar ki 28 November 2026 waali prices lekar. Aapke apne numbers `usage` logs se aayenge.

**Pehle.** Sab kuch Claude Sonnet 5.5 par real time mein uske default `high` effort par chalta hai. Har resume par:

- Extraction: 3,400 input tokens ($0.0068) aur 900 output tokens, jinmein lagbhag 650 thinking hain ($0.009). Kul $0.0158.
- Fit summary: 5,000 input tokens ($0.010) aur 1,400 output tokens, jinmein lagbhag 1,050 thinking hain ($0.014). Kul $0.024.

Yaani har resume par $0.0398, mahine mein $15,920, lagbhag ₹14.3 lakh. Dhyaan do ki har call mein akeli thinking hi 40% se zyada hai.

**Step 1: golden set par validator chunna.** Team 500 resumes ko haath se label karti hai aur ginti hai ki kitne resumes mein har field sahi hai:

| Path | Escalate hue | Checks pass karne waale galat outputs | Poori tarah sahi resumes |
| --- | --- | --- | --- |
| Sirf Sonnet 5.5 | Laagu nahi | Laagu nahi | 489 (97.8%) |
| Sirf Haiku 5.5 | Laagu nahi | Laagu nahi | 466 (93.2%) |
| Cascade, format aur range checks | 15 (3%) | 34 mein se 22 | 476 (95.2%) |
| Cascade, saath mein grounding checks | 35 (7%) | 34 mein se 7 | 489 (97.8%) |

Sirf format waala validator 3% escalation par aakarshak lag raha tha, par wo 34 galat outputs mein se 22 miss kar gaya. Grounding checks escalation rate ko dugne se zyada kar dete hain aur bade model ki quality ke baraabar pahunch jaate hain. Team inhe chunti hai.

**Step 2: levers ek-ek karke lagaana.**

| Lever | Kya badalta hai | Baad mein mahine ka kharch | Bachat |
| --- | --- | --- | --- |
| Shuruaat | Har cheez ke liye Sonnet 5.5, real time | ₹14.33 lakh | Koi nahi |
| 1. Extraction ke liye cascade | Low effort par Haiku 5.5: har resume par $0.0005, saath mein escalations ke liye 7% × $0.0158 | ₹9.22 lakh | ₹5.11 lakh |
| 2. Fit summaries par kam effort | Medium effort: thinking ghatkar lagbhag 400 tokens, summary cost $0.0175 | ₹6.88 lakh | ₹2.34 lakh |
| 3. Bulk uploads ko batch karna | 80% resumes aadhi keemat par | ₹4.13 lakh | ₹2.75 lakh |
| 4. Job description ko cache karna | 2,000-token prefix, 90% calls use cache se padhti hain (batches mein 1-hour writes, real time mein 5-minute) | ₹3.45 lakh | ₹0.68 lakh |

Table ko waise padho jaise ek reviewer padhega:

- **Lever 1:** escalations ki cost, saari chhote-model calls ki kul cost ke dugne se bhi zyada hai. Escalation rate ka har point bill par dikhta hai.
- **Lever 2:** effort ke badlaav ko apna eval chahiye tha. Recruiters ne dono settings par 100 summaries ko blind-rate kiya aur koi farq nahi dikha. Us check ke bina ye bas ek andaaza hota.
- **Lever 3:** batching apne se pehle ki har cheez ko 0.6 se guna kar deta hai (80% aadhi keemat par, 20% poori keemat par).
- **Lever 4:** yahaan caching ki bachat chhoti hai kyunki prefix 5,000 input tokens mein se sirf 2,000 hai. 400-token waale extraction instructions bilkul cache nahi hote: wo 512-token minimum se neeche hain.

Bill mahine mein lagbhag ₹14.3 lakh se ghatkar lagbhag ₹3.45 lakh ho jaata hai, kareeb 76% kam, aur golden-set accuracy aur recruiter ratings waise hi rehte hain. Din ke uploads real time mein hi rehte hain. Wahaan jo 7% resumes escalate hote hain wo do calls ka intezaar karte hain, isliye team us path ki p95 latency alag se track karti hai.

## Aam galtiyaan

- **Chhota model andaaze se chunna.** Har route ke evals chalao. Sasta aur galat, mehnga padta hai.
- **Kam escalation rate par bharosa karna.** Sirf format check karne waala validator sahi format waale par galat jawaab pass kar deta hai. Golden set par uska miss rate naapo.
- **Cost per successful task ki jagah cost per call ginna.** Escalations, retries aur insaanon ke fixes bhi jodo.
- **Thinking tokens ko nazarandaaz karna.** Bade model par default effort se reasoning bill ki sabse badi line ban sakti hai. Har route ke liye effort set karo aur evals se check karo.
- **`max_tokens` bahut tight rakhna.** Thinking ismein gini jaati hai, toh jawaab kat jaate hain aur model failures jaise dikhte hain.
- **Users ke saamne waale kaam ko batch karna.** Batches aam taur par ek ghante mein khatam hote hain par 24 ghante tak le sakte hain.
- **Fail hue batch items kho dena.** `custom_id` se match karo, errored aur expired items retry karo, aur writes idempotent rakho taaki reruns se duplicates na banein.
- **Escalation ki latency bhool jaana.** Chat mein cascade sabse mushkil sawaalon ko sabse slow bana deta hai. Ek router ya ek hi model users ke liye behtar ho sakta hai.
- **Aisa prefix cache karna jo cache ho hi nahi sakta.** Wo bahut chhota hai, har request mein badalta hai, ya din ke uploads ke beech 5-minute cache expire ho jaata hai.

## Tiering aur batching kab faayde ke nahi

- **Kam volume.** Bachat engineering ke samay se kam padti hai.
- **Har request urgent hai**, toh batching fit nahi hota.
- **Chhota model aapke evals mein fail hota hai** us traffic par jo aap use bhejoge, aur bade model par kam effort setting se bhi faayda nahi hota.
- **Cascade ke escalate karne ke liye koi bharosemand check nahi hai**, aur router ke liye koi saaf signal bhi nahi.

## Demo se production tak

- **Escalation rate, validator miss rate aur cost per successful task track karo**, har feature ke liye, har hafte.
- **Golden set dobaara chalao** har model, prompt ya effort badlaav par. Model badalne par effort dobaara sweep karo, kyunki levels alag-alag models par alag bartaav karte hain.
- **Batch failures sambhaalo** id se, retries, ek report aur deadline se pehle ek real-time fallback ke saath.
- **Urgent aur batch kaam alag rakho.** Batch ki apni limits hain; workspace limits use karo taaki bekaabu job real-time quota khatam na kar de.
- **Prices dates ke saath record karo** har cost comparison mein, aur har review se pehle unhe dobaara check karo.

## Practice karo

Apne provider ki batch processing guide aur RouteLLM post padho.

1. Ek feature chuno aur 50 golden cases par ek chhota aur ek bada model chalao. Har ek ke liye accuracy, output tokens (thinking samet) aur per case cost record karo.
2. Format, range aur grounding checks ke saath ek cascade banao. Escalation rate aur validator ka miss rate report karo.
3. Unhi 50 cases par bade model ko do effort levels par chalao aur quality aur output tokens compare karo.
4. 100 non-urgent requests ek batch ke roop mein submit karo, fail hue items ko `custom_id` se retry karo, aur cost ki tulna real-time calls se karo.
5. Worked example jaisi ek lever-by-lever table likho, apne `usage` numbers aur dated prices ke saath.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly, 2025) ka chapter 9 batching aur inference cost cover karta hai, aur chapter 10 model routers.

**Aapka kaam poora hai jab aap** ek feature ke liye cost, quality aur latency ki lever-by-lever table dikha sako aur har route ko uske eval se justify kar sako.
