## Ye kya hai

Apne GPU par language model chalana zyadatar **memory** ka sawaal hai. Teen cheezein iske liye hod karti hain, aur ek aur cheez speed tay karti hai:

- **Weights.** 16-bit precision par har parameter 2 bytes leta hai, to ek 14B model ko kuch bhi karne se pehle hi lagbhag 28 se 30 GB chahiye.
- **KV cache.** Har layer mein har token ke liye, model do vectors store karta hai, ek key aur ek value. Ye **KV cache** har request ki lambai ke saath aur ek saath chal rahi requests ki ginti ke saath badhta hai.
- **Working space.** Beech ke results (activations), CUDA runtime aur engine buffers. Ye lesson inke liye GPU ka lagbhag 10% spare rakhta hai.
- **Speed.** Har naye token ka matlab hai saare weights ko memory se ek baar padhna. Isliye **memory bandwidth**, yaani GPU har second kitne gigabytes padh sakta hai, aamtaur par raw compute se zyada generation speed ko limit karti hai.

**Quantization** weights ko, aur kabhi-kabhi cache ko bhi, kam bits mein store karta hai, jaise 16 ki jagah 8 ya 4. Cache ke liye zyada memory bachti hai, aur har token par kam bytes padhne padte hain, to generation aksar tez ho jaati hai. Keemat hai kuch quality ka nuksaan, jise aap apne task par measure karte ho.

Dekho ek 48 GB GPU, jaise NVIDIA L40S, par iska kya asar hota hai, jab wo 40 layers, 8 key-value heads aur head size 128 wala ek 14B model (Qwen3-14B ki shape) serve karta hai. 10% spare ke baad, lagbhag 43 GB usable hai; har request 4,000 tokens rakhti hai.

| Precision | Weights | KV cache ke liye bacha | 4,000 tokens ki requests |
|---|---|---|---|
| 16-bit weights, 16-bit cache | Lagbhag 30 GB | Lagbhag 13 GB | Lagbhag 20 |
| 4-bit weights, 16-bit cache | Lagbhag 10 GB | Lagbhag 33 GB | Lagbhag 50 |
| 4-bit weights, 8-bit cache | Lagbhag 10 GB | Lagbhag 33 GB | Lagbhag 100 |

Rule ye hai: **weights entry ki keemat tay karte hain; kitne users fit honge, ye cache tay karta hai.**

```flow

Model aur peak traffic -> Cache ke saath 16-bit mein fit?

```

Is lesson mein hum Hyderabad ki ek analytics firm ke saath chalenge, jo ek self-hosted extraction model ke liye GPUs size kar rahi hai.

## Ye kaam kaise karta hai

### Weights

Weights ke liye memory ≈ parameters × har parameter ke bytes.

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B se 8B | Lagbhag 14 se 16 GB | Lagbhag 7 se 9 GB | Lagbhag 4 se 6 GB |
| 14B | Lagbhag 28 se 30 GB | Lagbhag 14 se 16 GB | Lagbhag 8 se 10 GB |
| 32B | Lagbhag 64 GB | Lagbhag 32 se 34 GB | Lagbhag 18 se 20 GB |
| 70B | Lagbhag 140 GB | Lagbhag 70 GB | Lagbhag 37 se 40 GB |

4-bit har parameter ke liye aadhe byte se zyada kyun hai? Weights ke har chhote group (aksar 128) ke saath ek scale (aur aksar ek zero point) bhi store hota hai, jo har weight par lagbhag 0.15 bits jodta hai. Aur input embeddings aur output layer aksar 16-bit par hi rehte hain: badi vocabulary wale 8B model ke liye, ye lagbhag 1 billion parameters, yaani 2 GB hai. Plan karne se pehle checkpoint ki asli file size check karo.

### KV cache

Har token ke liye, har layer har **key-value head** ke liye ek key aur ek value store karti hai:

Har token ka cache = 2 × layers × key-value heads × head size × har value ke bytes

Numbers model ki `config.json` se padho: `num_hidden_layers`, `num_key_value_heads` aur `head_dim` (ya `hidden_size` ko `num_attention_heads` se bhaag dekar). Zyadatar modern models **grouped-query attention** use karte hain: kai attention heads kuch key-value heads share karte hain. Ek common 8B shape mein 32 attention heads hain par sirf 8 key-value heads, to attention heads use karne se aapka estimate chaar guna bada ho jaata hai.

Phir **tokens in flight** se guna karo: peak active requests × har request ke tokens. Peak ek load test ya traffic logs se lo, kabhi average nahi.

Do gotchas. **Hybrid** models, jaise Qwen3.5, lagbhag chaar mein se sirf ek layer mein full attention use karte hain, to sirf unhi layers ko gino. Aur **mixture-of-experts** models ko apne saare experts ke liye memory chahiye, bhale hi har token unmein se kuch hi use kare.

### Engine us memory ke saath kya karta hai

vLLM jaise serving engines do ideas use karte hain. **PagedAttention** har request ka cache chhote blocks mein store karta hai, jo request ke badhne par hi judte hain, to ek chhoti request sabse lambi mumkin request jitni jagah reserve nahi karti. **Continuous batching** har step par, jaise-jaise baaki requests khatam hoti hain, nayi requests ko running batch mein jodta hai, to GPU busy rehta hai. Dono mein se koi bhi memory paida nahi karta, to upar wala hisaab hi limit rehta hai.

Start-up par, vLLM cache size ko tokens mein log karta hai, aur aapki maximum request length ke liye "maximum concurrency" bhi. Us line ko apne estimate se compare karo; aapke setup ke liye wahi sach hai. vLLM v0.34.0 se, `--gpu-memory-utilization` unset ho to saari free memory use hoti hai, to koi share sirf tab set karo jab koi aur process GPU share kar raha ho.

### Prefill aur decode

Har request ke do phases hote hain, aur dono ki limits alag hain.

- **Prefill** poora prompt ek saath padhta hai aur cache bharta hai. Ye har prompt token par lagbhag 2 × parameters operations karta hai: 14.8B model aur 6,000-token prompt ke liye, lagbhag 180 trillion. Prefill **compute** se limited hai aur **time to first token** tay karta hai, to lambe prompts ka matlab hai dheeme first tokens.
- **Decode** har step mein ek token likhta hai. Har step saare weights aur har request ka cache padhta hai, par har byte par thoda hi maths karta hai. Ye **memory bandwidth** se limited hai, aur **tokens per second** tay karta hai.

Ek request ke liye quick ceiling: bandwidth ÷ weights ke bytes. Ek L40S 864 GB/s padhta hai, to ek 10 GB 4-bit model ek request ke liye zyada se zyada lagbhag 86 tokens per second tak pahunch sakta hai; ek 30 GB 16-bit model zyada se zyada lagbhag 29. Asli numbers kam hote hain. Batching ki wajah se hi serving affordable hai: weights ko ek baar padhne se batch ki har request serve hoti hai, to total throughput batch size ke saath badhta hai, jab tak compute ya cache memory khatam na ho jaaye. Keemat ye hai ki har user har token ke liye thoda zyada intezaar karta hai, to concurrency ko apne latency budget ke hisaab se tune karo.

### GPU chunna

| GPU | Memory | Bandwidth | Native FP8 | Aam use |
| --- | --- | --- | --- | --- |
| NVIDIA L4 | 24 GB | 300 GB/s | Haan | 8B tak ke models, halka traffic |
| NVIDIA L40S | 48 GB | 864 GB/s | Haan | Quantization ke saath 8B se 32B models |
| NVIDIA A100 80 GB | 80 GB | Lagbhag 2,000 GB/s | Nahi | 16-bit par 14B se 32B, fine-tuning |
| NVIDIA H100 SXM | 80 GB | 3,350 GB/s | Haan | Busy services, NVLink ke saath bade models |
| NVIDIA H200 | 141 GB | 4,800 GB/s | Haan | Ek GPU par 8-bit mein lagbhag 70B |

Teen gotchas. A100 mein FP8 units nahi hain: vLLM us par FP8 checkpoints ko weight-only load kar sakta hai, jisse memory bachti hai par compute nahi. Blackwell GPUs, jaise B200, hardware 4-bit floating point (NVFP4 aur MXFP4) jodte hain; OpenAI ke gpt-oss models MXFP4 mein ship hote hain, isiliye gpt-oss-120b ek 80 GB GPU par fit ho jaata hai. Aur H100 PCIe cards mein SXM version se kam bandwidth (lagbhag 2,000 GB/s) hai.

India mein aap inhe local GPU clouds jaise E2E Networks (jo Delhi NCR aur Chennai mein H100 capacity list karta hai) aur Yotta se, ya global clouds ke Indian regions se rent kar sakte ho. Eligible startups, researchers aur institutions IndiaAI Compute Portal par subsidised hours ke liye apply kar sakte hain. Ye example rates hain: E2E ke pages par L40S ₹102 per GPU-hour aur H100 ₹362 per GPU-hour on demand list the, 18% GST se pehle (28 November 2026 ko check kiya). Prices aur stock aksar badalte hain, to jis din plan karo, us din providers ke pages, aur apna quota, check karo.

### Quantization formats

- **FP8** (8-bit floating point). Zyadatar models ke liye lagbhag 16-bit jaisi quality, aadhi memory, aur FP8 units wale GPUs par tez maths. Aksar sabse pehle yahi try karna chahiye.
- **AWQ aur GPTQ** (4-bit integers, sirf weights). Weight memory ka lagbhag ek chauthai, saath mein upar wale overheads, aur thoda-sa quality nuksaan. Pehle se quantized checkpoint download karo, ho sake to model maker ka banaya hua.
- **NVFP4 aur MXFP4** (4-bit floating point). Blackwell GPUs par tez; naye hain aur abhi kam test hue hain.
- **bitsandbytes NF4.** Transformers mein load time par quantize karta hai. Experiments aur QLoRA ke liye aasaan, par serve karne mein dheema.
- **GGUF.** llama.cpp ka file format, jis par Ollama aur LM Studio bane hain, laptops, CPUs aur Apple Silicon ke liye. Ek Q4_K_M file har weight par lagbhag 4.8 se 4.9 bits use karti hai, to ek 8B model lagbhag 5 GB ka hota hai. Speed bandwidth ke hisaab se chalti hai: agar laptop 80 GB/s par memory padhta hai, to lagbhag 16 tokens per second ceiling hai.
- **8-bit KV cache.** Cache ko FP8 mein store karne se wo aadha ho jaata hai. Kisi bhi aur badlaav ki tarah iski quality bhi measure karo.

Jo sabse oonchi precision fit ho, wahaan se neeche aao: 16-bit, phir FP8, phir 4-bit. Har ek ke liye apna eval aur ek chhota load test chalao, aur peak par quality, memory aur speed record karo. Wo sabse sasta option chuno jiska quality nuksaan aapka client likhit mein accept kare.

### Code mein ek memory planner

```python
def memory_plan(cfg, params_billion, weight_bits=16, kv_bits=16,
                context_tokens=4000, concurrent=20, gpu_gb=48, spare=0.10):
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights_gb = params_billion * weight_bits / 8          # rough: real 4-bit files are larger
    kv_token_mb = 2 * cfg["num_hidden_layers"] * kv_heads * head_dim * kv_bits / 8 / 1e6
    kv_gb = kv_token_mb * context_tokens * concurrent / 1e3
    usable = gpu_gb * (1 - spare)
    fits = weights_gb + kv_gb <= usable
    max_requests = int((usable - weights_gb) * 1e3 / (kv_token_mb * context_tokens))
    return round(weights_gb, 1), round(kv_token_mb, 3), round(kv_gb, 1), fits, max_requests

# The shape of a common 8B model; in real use, load the dict from config.json
cfg = {"num_hidden_layers": 32, "num_attention_heads": 32, "num_key_value_heads": 8, "head_dim": 128}
print(memory_plan(cfg, 8, gpu_gb=24))                  # (16.0, 0.131, 10.5, False, 10)
print(memory_plan(cfg, 8, weight_bits=8, kv_bits=8, gpu_gb=24))  # (8.0, 0.066, 5.2, True, 51)
```

16-bit par, 4,000 tokens ki 20 requests ko 16 GB weights ke upar lagbhag 10.5 GB cache chahiye: 24 GB card ke liye bahut zyada, jo sirf 10 rakh paata hai. 8-bit mein ye fit ho jaati hain, haalaanki asli FP8 file lagbhag 9 GB ki hai, kyunki embeddings 16-bit par hi rehte hain.

### Quantized model ko load aur serve karna

Transformers mein quick experiments ke liye:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("your-org/your-8b-instruct",
                                             quantization_config=bnb, device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

Serving ke liye, fast quantized kernels wala engine use karo. vLLM quantized checkpoint ki config se method padh leta hai:

```bash
vllm serve your-org/your-14b-instruct-awq --max-model-len 8192 --kv-cache-dtype fp8
```

16-bit model ko load time par FP8 mein quantize karne ke liye, vLLM v0.34.0 `--quantization fp8_per_tensor` use karta hai; sirf `fp8` ab ye nahi karta. `--max-model-len` ek request ki lambai par cap lagata hai; ise utna set karo jitna aapke users sach mein bhejte hain.

### Quality ka nuksaan measure karna

Har precision par golden set chalao aur har slice ke hisaab se compare karo, sirf overall nahi. Quantization ka asar aksar sabse pehle lambi reasoning, maths, code aur kam common languages par padta hai, to Hindi, Telugu ya Tamil cases ko English se alag score karo. Koi precision tabhi rakho jab har zaroori slice tay limit ke andar rahe.

## Ek example se samjho

Hyderabad ki ek analytics firm 200 staff ke liye invoices se fields nikaalne wala model self-host karna chahti hai. Prompts aur replies milakar 6,000 tokens tak jaate hain. p95 time to first token 3 seconds se kam rehna chahiye. Neeche diye quality scores aur latencies illustrative hain, method dikhane ke liye; memory figures calculate kiye gaye hain.

**1. Peak measure karo.** Ek busy din ke logs replay karne par peak **80 active requests** par aata hai (average lagbhag 35). 80 ke liye size karo.

**2. Model.** 14.8 billion parameters, 40 layers, 8 key-value heads aur head size 128 wala ek 14B instruct model. Har token ka cache: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes, lagbhag 0.16 MB. Ek 6,000-token request lagbhag 0.98 GB rakhti hai; peak ko lagbhag 79 GB cache chahiye.

**3. Original proposal.** 16-bit par tensor parallelism ke saath do H100 80 GB GPUs. Usable memory 2 × 72 = 144 GB hai; weights lagbhag 30 GB lete hain, lagbhag 114 GB bachta hai, yaani lagbhag 116 requests. Fit ho jaata hai, par 2 × ₹362 = ₹724 prati ghanta lagta hai, aur ek GPU fail hua to service ruk jaati hai.

**4. Quantize karo.** Maker ka 4-bit AWQ checkpoint lagbhag 10 GB hai. 500 asli invoices par field accuracy: 16-bit par 95.1%, 4-bit par 94.6%, aur saath mein FP8 cache bhi ho to 94.5%. Client ki limit 94.0% hai, to dono pass.

**5. L40S cards par fit karo.** Ek L40S lagbhag 43 GB usable deta hai. 4-bit weights ke saath 33 GB bachta hai. 16-bit cache ke saath, usmein 6,000 tokens ki 33 requests aati hain, to peak ke liye 3 GPUs chahiye aur ek chautha spare ke taur par. FP8 cache ke saath, lagbhag 67 aati hain, to do GPUs peak (134) sambhaal lete hain aur ek fail ho to teesra service chaalu rakhta hai.

**6. Speed check karo.** Teen L40S cards par 80 concurrent requests ke load test mein p95 time to first token 1.8 seconds aata hai, budget ke andar. Har user ke tokens H100s se dheeme aate hain, jinmein lagbhag chaar guna bandwidth hai, par target poora hota hai.

| Option | GPUs | 6,000 tokens par requests | Ek GPU failure jhel leta hai? | Prati ghanta cost (GST se pehle) |
| --- | --- | --- | --- | --- |
| 16-bit, tensor parallelism | Do H100 | Lagbhag 116 | Nahi | ₹724 |
| 16-bit, do copies | Do H100 | Lagbhag 86 (har ek mein 43) | Nahi, 43 to 80 se kam hai | ₹724 |
| 4-bit weights, 16-bit cache, copies | Chaar L40S | Lagbhag 132 (har ek mein 33) | Haan | ₹408 |
| 4-bit weights, FP8 cache, copies (chuna gaya) | Teen L40S | Lagbhag 201 (har ek mein 67) | Haan | ₹306 |

Har L40S ek load balancer ke peechhe apni copy chalata hai. 28 November 2026 ko check kiye gaye example rates par, chuna gaya plan 730-hour mahine ke liye lagbhag ₹2.23 lakh ka padta hai, jabki proposal ₹5.29 lakh ka, dono 18% GST se pehle. Reserved prices alag hote hain, isliye firm phir bhi quotes leti hai.

## Aam galtiyaan

- **Sirf weights ke liye size karna.** Kitne users fit honge, ye peak par cache tay karta hai.
- **Average traffic se size karna.** Measured peak use karo, warna sabse busy subah service fail ho jaayegi.
- **Cache formula mein key-value heads ki jagah attention heads use karna,** ya 2 ka factor chhod dena.
- **4-bit ko har parameter ke liye theek aadha byte maan lena.** Scales aur 16-bit embeddings lagbhag 10 se 50% jodte hain.
- **Slice ke hisaab se evals ke bina quantize karna.** Ek English-only average, Indian languages, maths aur code mein nuksaan chhupa deta hai.
- **Ek GPU par fit hone wale model ko split karna.** Copies zyada aasaan hain, behtar scale hoti hain aur failures jhel leti hain.
- **Ye maan lena ki FP8 har jagah tez hai.** A100 mein FP8 units nahi hain; GPU generation check karo.
- **Maximum context zaroorat se bahut zyada set karna.** Ek bahut badi request kai chhoti requests ko bahar dhakel sakti hai.

## Kab GPUs ke baare mein sochne ki zaroorat nahi

- **Hosted API use kar rahe ho,** ya client ki cloud model service.
- **CPUs par chhote models,** jaise embedding models, classifiers ya laptop par ek 4-bit GGUF demo.
- **Kam ya achaanak uchhalne wala volume,** jahaan poore mahine rent kiya GPU per token pay karne se mehnga padta hai.

## Demo se production tak

- **Memory plan karo** weights, peak cache aur working space ke liye; engine ke start-up log mein ise confirm karo.
- **Golden set chalao** har precision badalne par, har language aur task ke hisaab se.
- **Asli GPUs par load test karo** bade paimaane par rent karne se pehle, peak par first-token time aur errors dekhte hue.
- **Kam se kam ek spare GPU rakho** taaki failure ya upgrade se service na ruke.
- **Production mein cache usage aur queue length monitor karo,** aur cache bharne se pehle alert karo.
