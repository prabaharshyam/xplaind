## Ye kya hai

**AI system design** ka matlab hai kaagaz par tay karna ki koi AI product kin cheezon se bana hai, aur numbers se saabit karna ki wo chalega. Achha design chhah sawaalon ke jawaab deta hai: parts kya hain, har arrow se kaun-sa data guzarta hai, ek request ka cost kitna hai, user kitna intezaar karta hai, kya toot-ta hai aur humein kaise pata chalega, aur quality kaise measure karenge?

"Design interview" lesson mein ek design ko ghadi ke dabaav mein present karne ki baat hai; ye lesson batata hai ki usmein kya hona chahiye.

Jo product documents se jawaab deta hai, uski do pipelines hoti hain: **ingestion** offline chalti hai aur documents ko ek index mein badalti hai; **request path** har sawaal par chalta hai. Zyaadatar quality problems ingestion mein shuru hoti hain, isliye dono banao.

```flow
title: Underwriting assistant, request path
Underwriter ka sawaal -> API service | login, department, har user ki cap
API service -> Input checks | personal data mask karna, injection flag karna
Input checks -> Query rewrite | small model
Query rewrite -> Hybrid search | department aur effective-date filters
Hybrid search -[top 40]-> Reranker
Reranker -[top 6]-> Main model | sirf passages se jawaab, citations ke saath
Main model -[outage]-> Fallback model
Main model -> Citation check
Fallback model -> Citation check
Citation check -[pass]-> Clauses ke links ke saath jawaab
Citation check -[fail]-> Jawaab se inkaar, senior underwriter ko route
```

```flow
dir: LR
title: Ingestion pipeline, har raat
Nayi wordings aur circulars -> Parser and OCR | tables ko tables hi rakhta hai -> Chunker | section path ke saath 400 tokens -> Embeddings and keyword index -> Index | version, effective date, department
```

Ye lesson ek hi design ko follow karta hai: Mumbai ki ek general insurer mein 300 underwriters ke liye ek assistant, jo 2,000 policy wordings, circulars aur guidelines se jawaab deta hai. Saare volumes, token counts aur timings isi design ki assumptions hain, kisi asli insurer ke measurements nahi.

## Ye kaam kaise karta hai

### User aur constraints se shuru karo

Goal ko ek baseline waale metric ki tarah likho: "Kisi policy sawaal ka jawaab dhoondhne ka median time, 6 minutes se 2 se kam." Phir wo constraints likho jo kisi box ya number ko badalte hain.

- **Jawaab kaun padhta hai, aur galat jawaab ki keemat kya hai?** Ek trained underwriter, par ek galat exclusion kisi policy ki galat pricing karwa sakta hai. Isliye har jawaab ek clause cite karta hai.
- **Volume aur peaks.** 300 users, har ek har working day lagbhag 25 sawaal, zyaadatar 8 busy hours ke andar.
- **Data rules.** Documents, index aur logs India mein hi rehte hain. Model calls India ke bahar process ho sakti hain ya nahi, ye compliance team tay karegi, aur wahi faisla tay karega ki provider ko seedhe call karna hai ya kisi cloud provider ka regional endpoint lena hai, agar India mein koi endpoint chuna hua model deta ho. Pehle hafte mein hi poochho.
- **Access.** Motor underwriters ko health reinsurance treaties nahi dikhni chahiye, aur yahi rule search ka dhaancha tay karta hai.

### Wo decisions jo har design ko batane hote hain

Boxes ki list design nahi hoti. Bade choices aur har ek ki wajah batao.

| Decision | Is design ka choice | Ise kab badlo |
| --- | --- | --- |
| Sirf prompt, retrieval ya fine-tuning | Retrieval: documents har mahine badalte hain aur jawaabon ko citations chahiye | Zaroorat knowledge ki nahi, volume par format ya style ki ho ("Prompting, RAG ya fine-tuning" dekho) |
| Long context ya retrieval | Retrieval: lagbhag 25 million tokens ke documents, 1-million-token window ke saamne | Corpus chhota aur sthir ho, aur caching use sasta rakhe |
| Model tier | Jawaabon ke liye mid-sized model; query rewriting ke liye small model | Small model kisi poori category ke liye launch bar paar kar le |
| Hosted API ya self-hosted open weights | Hosted, region compliance tay karegi | Data aapke servers se bahar na ja sake, ya sthir volume GPUs ko busy rakhe |
| Vector store | Vector extension ke saath Postgres | Index ek machine se bada ho jaaye |
| Streamed ya batch | Streamed: koi insaan intezaar kar raha hai | Koi intezaar nahi kar raha: batch API aadhe cost par |

Database chunne se pehle index ka size nikaalo. Maan lo 2,000 documents, ausatan 25 pages, har page lagbhag 500 tokens: 25 million tokens, yaani 400 tokens ke 62,500 chunks. Har embedding mein 1,024 numbers aur har number 4 bytes ka, toh lagbhag 256 MB vectors, jo ek aam server ki memory mein aa jaate hain. Distributed vector database bina kisi faayde ke cost badhaayega.

### Ek request trace karo, har step ke data ke saath

Har step kya leta hai aur aage kya bhejta hai, ye likho; privacy aur cost ki problems yahin dikhti hain.

1. **API service.** Sawaal, user id aur department leta hai; jo users apni daily cap paar kar chuke hain unhe reject karta hai.
2. **Input checks.** Log karne se pehle policy aur phone numbers mask karta hai; jo text model ko instructions dene ki koshish kare use flag karta hai.
3. **Query rewrite.** Ek small model "does the fire one cover riots" jaise sawaal ko policy name waali query mein badalta hai: lagbhag 300 tokens andar, 40 bahar.
4. **Hybrid search.** Keyword aur vector search parallel mein chalte hain, department aur effective date se filter hokar. Keyword search policy codes aur clause numbers pakadta hai, yaani wo exact strings jo embeddings aksar miss kar dete hain.
5. **Reranker.** Top 40 candidates ko score karta hai aur 6 rakhta hai.
6. **Main model.** Lagbhag 1,500 tokens ke fixed instructions leta hai (har call par ek jaise, isliye cached) aur 2,700 naye tokens: 400 tokens ke chhah passages aur sawaal. Ye lagbhag 350 tokens likhta hai.
7. **Citation check.** Saada code: har cited clause id bheje gaye passages mein honi chahiye, warna jawaab refuse hokar kisi insaan ke paas route hota hai.

Access control step 4 mein rehta hai. Jawaab ke baad filter karoge toh model wo text pehle hi padh chuka hoga jo user ko nahi dikhna chahiye.

### Boxes se pehle numbers: load, limits aur cost

```python
# Anthropic list prices, US dollars per million tokens, checked 28 November 2026
SONNET = {"in": 2.00, "cache_read": 0.10, "out": 10.00}   # Claude Sonnet 5.5
HAIKU = {"in": 0.10, "out": 0.50}                          # Claude Haiku 5.5, prompts up to 100,000 tokens

def estimate(users=300, questions_per_user=25, work_days=22, busy_hours=8, peak_factor=2.5,
             cached_in=1_500, fresh_in=2_700, out=350,   # main model, tokens per question
             rewrite_in=300, rewrite_out=40,             # small model rewrites the query
             usd_to_inr=94, fixed_inr_month=60_000):     # suppose: search, hosting, tracing
    daily = users * questions_per_user
    peak_per_min = daily / (busy_hours * 60) * peak_factor
    usd = ((fresh_in * SONNET["in"] + cached_in * SONNET["cache_read"] + out * SONNET["out"])
           + (rewrite_in * HAIKU["in"] + rewrite_out * HAIKU["out"])) / 1e6
    month_inr = daily * work_days * usd * usd_to_inr + fixed_inr_month
    return {
        "peak questions a minute": round(peak_per_min),
        "peak uncached input tokens a minute": round(peak_per_min * fresh_in),
        "peak output tokens a minute": round(peak_per_min * out),
        "model cost per question (rupees)": round(usd * usd_to_inr, 2),
        "model spend a month (US dollars)": round(daily * work_days * usd),
        "total a month (rupees)": round(month_inr),
        "per user a month (rupees)": round(month_inr / users),
    }

print(estimate())
# {'peak questions a minute': 39, 'peak uncached input tokens a minute': 105469,
#  'peak output tokens a minute': 13672, 'model cost per question (rupees)': 0.86,
#  'model spend a month (US dollars)': 1502, 'total a month (rupees)': 201141,
#  'per user a month (rupees)': 670}
```

₹94 ka ek dollar aur ₹60,000 ke fixed costs sirf udaaharan ke liye hain. Ise published limits se milaao. Claude API par, November 2026 tak, sabse nichla standard tier (Start) Sonnet 5.5 ke liye ek minute mein 2,000,000 input tokens aur 400,000 output tokens deta hai. Cache reads input limit mein nahi gine jaate. Toh peak load uska lagbhag 5% hi use karta hai: rate limit problem nahi hai.

Problem monthly bill hai. Har tier ka ek monthly spend cap bhi hai: Start ka $500, Build ka $1,000 aur Scale ka $200,000. Lagbhag $1,500 mahine par ye design dono nichle tiers mein se kisi par bhi mahine ke beech mein ruk jaayega, aisi errors ke saath jinhe retries theek nahi kar sakte. Design ko tier ya cloud contract ka naam batana hoga aur cap se neeche ek budget alert lagaana hoga. Cloud platforms apne quotas khud tay karte hain, aur Anthropic ke pricing page ke mutaabik unke regional aur multi-region endpoints global waalon se 10% mehenge hain, isliye compliance jo route chune uske liye hisaab phir se karo.

Fresh input sabse bada cost hai: har sawaal ke $0.0091 mein se $0.0054 (2,700 tokens, $2 prati million par). 6 ki jagah 4 passages bhejne se lagbhag 18% bachta hai, agar eval set par recall bana rahe. Cache writes chhode gaye hain: is traffic par cached prefix kabhi-kabhaar hi expire hota hai. Fixed costs total ka 30% hain, isliye usage badhne ke saath prati user cost ghatta hai.

### Ek latency budget, step by step

Underwriters jawaab stream hote-hote padhte hain, isliye target hai: 100 mein se 95 sawaalon (p95) par pehla text 2 seconds se kam mein dikhe.

| Step | Allowance (p95) |
| --- | --- |
| Login, cap aur input checks | 50 ms |
| Query rewrite, small model | 300 ms |
| Hybrid search, keyword aur vector parallel mein | 150 ms |
| 40 candidates ki reranking | 200 ms |
| Main model, pehle token tak ka samay | 1,000 ms |
| Total, lagbhag 300 ms bachaakar | 1.7 s |

p95s ko jodne se asli p95 zyada dikhta hai, kyunki saare steps shaayad hi kabhi ek saath dheeme hote hain, isliye ye budget safe hai, exact nahi. Agar model, maan lo, ek second mein 60 tokens stream kare, toh 350-token jawaab ko lagbhag 6 seconds aur lagenge. Jab total phisle, toh trace dikhata hai ki kis step ne apna allowance toda. Sabse pehle kaatne waala step query rewrite hai.

### Failure modes, unhe kaise pakdein, aur guard

Failure row tabhi kaam ki hai jab kisi ko failure ka pata chale, isliye har row mein ek detection signal do.

| Component | Kya galat hota hai | Aapko kaise pata chalega | Guard |
| --- | --- | --- | --- |
| Parsing | Scanned tables uljha hua text ban jaati hain | Har document ka parse score | Table extraction; flagged pages indexing se pehle check |
| Index | Puraana pad chuka (superseded) circular pehle number par aata hai | Eval set ke dated trap questions fail hote hain | Effective-date filter; puraane versions rakhe jaate hain par marked |
| Search | Sahi clause chhoot jaata hai | Eval set par recall at 5, har hafte track | Hybrid search, reranker, query rewrite |
| Access | Koi user doosre department ki treaty dekh leta hai | Har department ke ek user ke saath CI test | Search ke andar permission filter |
| Model | Aisa claim jise passages support nahi karte | Citation check failures; sampled traffic par judge score | Sirf passages se jawaab, warna refuse |
| Documents | Upload hui file mein chhipe instructions | Traces mein injection flags | Koi write tools nahi; passages ko instructions nahi, data ke roop mein mark kiya jaata hai |
| Provider | Outage, rate limit ya ramp limit errors (429) | Error rate aur fallback share | Backoff ke saath retries, fallback model, saaf message |
| Cost | Usage bekaaboo ho jaata hai | Budget ke saamne daily spend | Har user ki caps, budget ke 80% par ek alert |

### Human review: kahaan, aur kitna

Logon ko wahaan rakho jahaan model sabse kamzor hai aur galtiyaan sabse mehengi hain. Yahaan, refused aur kam score waale jawaab ek senior underwriter ke paas jaate hain, naye circulars indexing se pehle check hote hain, aur har mahine 30 jawaab sample kiye jaate hain.

Phir uska size nikaalo. Roz 7,500 sawaalon mein se agar 4% route hon, toh 300 reviews. Har ek par 3 minutes, yaani roz 15 ghante, lagbhag do full-time reviewers. Agar client itne log nahi laga sakta, toh retrieval theek karo ya kam tarah ke sawaal route karo. Jis queue par koi baitha nahi, wo guard nahi hai.

### Evaluation aur launch bar

Test set asli sawaalon se, category ke hisaab se banao, jaise 60 single-document sawaal, 25 jinmein do documents chahiye, 15 superseded-circular traps, aur 20 jo documents cover nahi karte, jinhe refuse hona hi chahiye. Retrieval measure karo (recall at 5: kya sahi clause top five mein hai?) aur jawaab bhi (sahi aur cited, ek model judge se score, jise underwriter labels se check kiya gaya ho).

Jaano ki ek chhota set kya dikha sakta hai: 120 sawaalon par 85% sahi ka 95% margin dono taraf lagbhag 6 points hai. Toh do models ke beech 2-point ka farq noise hai. Aur 20 mein se 20 refusals ke baad bhi asli failure rate lagbhag 15% ho sakta hai. Asli traffic aane ke saath traps badhaao. Har prompt ya model change par CI mein fast checks chalaao: 120 sawaal, lagbhag ₹0.86 har ek, yaani lagbhag ₹100 ek run, upar se judge.

### Document ko zinda rakho

Ise repository mein Markdown ke roop mein rakho, pull requests mein review karo, aur aakhir mein open questions aur ek decision log ho: date, decision, options, reason, kisne maana. Jaise: "2026-11-02: reranker ke saath hybrid search. Vector-only search policy codes miss kar raha tha (recall at 5: eval set par 71% banaam 89%). Client IT ke saath tay." Pehle hafte mein hi kisi compliance reviewer ko ise samjha do, jab "Ye kahaan store hota hai?" ka jawaab dena abhi sasta hai.

Kisi bhi code se pehle numbers ne kya badla:

1. **Spend cap.** Bill do tiers ke monthly caps se upar hai, isliye teesre hafte mein service rukne ki jagah, contract ka faisla plan mein aa gaya.
2. **Review queue.** Client ne "kabhi-kabhaar" review maan rakha tha; do logon ke ghante dekhkar unhone retrieval ke kaam aur ek rota ke liye paise diye.
3. **Vector store.** 256 MB vectors insurer ke maujooda Postgres mein aa jaate hain: review karne ke liye ek vendor kam.
4. **Compliance ka sawaal.** Pehle hafte mein uthaaya gaya, isliye gateway banne se pehle model route tay ho gaya.

Ab ise ek badlaav se test karo. Maan lo agle saal 2,700 claims staff judte hain. Das guna users ka matlab peak par lagbhag 390 sawaal ek minute mein aur lagbhag 1.05 million uncached input tokens ek minute mein: ab bhi Start tier ki input limit se neeche, par lagbhag $15,000 mahina. Prati user cost lagbhag ₹490 par aa jaata hai, kyunki fixed costs bant jaate hain. Sabse pehle review queue toot-ti hai: 75,000 ka 4% yaani roz 3,000 reviews, isliye pehle route hone waala hissa ghataana hoga.

## Aam galtiyaan

- **Bina numbers ke boxes.** Lakshan: kisi box ka na owner hai, na latency allowance, na failure row, isliye reviewers use challenge nahi kar sakte.
- **Sirf request path banaana.** Lakshan: na parsing, na versions, na effective dates, jab tak koi puraana circular user tak na pahunch jaaye.
- **Rate limit check karna par spend cap nahi.** Lakshan: "Hum tokens-per-minute limit se kaafi neeche hain", par na monthly bill, na price check date.
- **Generation ke baad access filter karna.** Lakshan: "UI restricted jawaab chhipa deta hai". Model restricted text pehle hi padh chuka hai.
- **Detection column ke bina failure table.** Lakshan: aisi failures ke guards jinhe koi notice hi nahi karega.
- **Bina size ki human review.** Lakshan: "Uncertain jawaab kisi insaan ke paas jaate hain", par na hissa, na minutes, na team.
- **Chhote eval set par bharosa.** Lakshan: 120 sawaalon par 2-point ki badhat se model chunna, ya 20 mein se 20 refusals ko saboot maanna.
- **Lamba document jise koi nahi padhta.** Do se chaar pages, summary table pehle.

## Kab poora design document zaroorat se zyada hai

- **Ek hafte ka prototype:** aadha page, jismein goal, data, success measure aur prati request mota cost ho.
- **Ek chhota internal tool**, jiske users kam hon aur koi sensitive data na ho.
- **Kisi maujooda system ke andar badlaav:** uski jagah uska document aur decision log update karo.

3. Har component se trace ki gayi ek request, har step ke data ke saath.
4. Har step ke allowance waala latency budget.
5. Kam se kam chhah rows ki failure table, har row mein ek detection signal aur ek guard.
6. Category ke hisaab se test set, launch bar ke saath.
7. Open questions aur ek chhota decision log.

Phir worked example ki tarah kisi ek assumption ko das se guna karo, aur likho ki sabse pehle kya toot-ta hai.

**Aapka kaam poora hai jab aap** kisi ko das minutes mein apna design samjha sako aur har component ke liye jawaab de sako: "Iska cost kya hai, ye kitna dheema ho sakta hai, aur fail hone par kya hota hai?"
