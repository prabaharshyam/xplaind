## Ye kya hai

Hosted model ko kiya gaya har call **token** ke hisaab se bill hota hai; token yaani ek shabd ya shabd ka ek tukda. **Cost control** ka matlab hai ye jaanna ki kaun-se features, users aur steps wo tokens kharch kar rahe hain, aur users ko nuksaan pahunchaaye bina wo kharch ghataana. Ek request ke bill ke chaar hisse hote hain:

- **Fresh input**: system prompt, tool definitions, history, retrieve kiya gaya text aur user ka message, poori input price par.
- **Cache reads and writes**: input ka wo hissa jo provider ke prompt cache se aata hai ya usmein save hota hai, kaafi kam ya thodi zyaada price par.
- **Output**: dikhne waala reply, input price se kai guna price par.
- **Thinking**: reasoning model ke chhipe hue reasoning tokens. Ye output ki tarah bill hote hain, chaahe response mein inmein se ek bhi na dikhe.

```flow
title: Ek request mein paisa kahaan jaata hai
dir: LR
System prompt aur tools | har call par wahi, isliye cache ho sakte hain -> Input bill
History aur retrieve kiya text | har turn ke saath badhta hai -> Input bill
User message | aam taur par chhota -> Input bill
Input bill -> Model
Model -[chhipi hui reasoning]-> Output bill | thinking output ki tarah bill hoti hai
Model -[dikhne waala reply]-> Output bill
```

Is lesson ka zyaadatar hissa do baaton par tika hai. Token ki ginti mein aam taur par input zyaada hota hai, kyunki lamba fixed prefix har call par dobaara bheja jaata hai. Per token price mein aam taur par output (thinking milaakar) zyaada hota hai. Isliye badi bachat yahin se aati hai: prefix ko poori price par dobaara na bhejna, task ki zaroorat se zyaada think na karwaana, aur jahaan chhota model pass kare wahaan bada model use na karna.

## Ye kaam kaise karta hai

### Pehle naapo

Har call ko uske usage numbers ke saath log karo: fresh input tokens, cache-read tokens, cache-write tokens, output tokens aur, jahaan API bataaye, output mein thinking ka hissa (Anthropic ka field `usage.output_tokens_details.thinking_tokens` hai; OpenAI bhi reasoning tokens `output_tokens_details` ke andar hi bataata hai). Har call ko feature, user, model, effort setting aur prompt version se tag karo. Tab aap jawaab de paaoge: kaun-sa feature sabse mehnga hai, kaun-se users, kaun-sa agent step, aur kitna hissa thinking hai. Sirf mahine ka total ye sab chhipa deta hai.

Sirf cost per request nahi, **cost per completed task** track karo. Jo sasta call fail ho jaaye, retry ho ya kisi insaan ke paas jaaye, wo sasta nahi hai.

### Price page padho, aur taareekh likho

28 November 2026 tak, Anthropic ki API teen maujooda model sizes ki price aise rakhti hai (US dollars per million tokens):

| Model | Input | Output | Cache read | 5-minute cache write | Batch input / output |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | $4 | $20 | $0.20 | $5 | $2 / $10 |
| Claude Sonnet 5.5 | $2 | $10 | $0.10 | $2.50 | $1 / $5 |
| Claude Haiku 5.5, 100,000 tokens tak ke prompts | $0.10 | $0.50 | $0.01 | $0.125 | $0.05 / $0.25 |

Isse teen baatein padho. Output ki cost input se paanch guna hai. Sabse chhota model dono mein sabse bade se 40 guna sasta hai. Batch theek aadhi price hai. Baaki providers bhi yahi structure alag numbers ke saath use karte hain, isliye unke maujooda pages padho aur jis taareekh ko check kiya wo likh lo.

### Model choice: sabse bada lever

Classification, saaf text se extraction, routing aur chhote replies ke liye chhota model aksar bade model ke baraabar nikalta hai. Har task ko apne eval set par do-teen model sizes ke saath test karo, jo pass kare unmein sabse sasta use karo, aur sirf mushkil requests bade model ko bhejo. Batching aur model tiering waala lesson routers ko gehraai se cover karta hai. Switch karte samay tokens dobaara gino: alag models alag tokenizers use kar sakte hain, isliye wahi text alag ginti ke tokens ban sakta hai.

### Reasoning tokens aur effort

Zyaadatar maujooda models jawaab dene se pehle think karte hain, aur wo thinking poori output price par output ki tarah bill hoti hai. Anthropic ki documentation saaf kehti hai ki poori thinking ke paise lagte hain, chaahe response mein sirf summary dikhe ya kuch bhi na dikhe, isliye dikhne waale reply ki lambaai bill se match nahi karti.

Opus 5.5 ki prices par ek chhota example: ek ticket label jismein 10 visible tokens aur 90 thinking tokens hain, uska output 100 × $20 per million = $0.002 padta hai, sirf label ke $0.0002 ka das guna.

Iska control hai **effort** setting (doosre providers par "reasoning effort"). Kam effort yaani kam thinking, aur low effort par simple inputs ke liye model thinking skip bhi kar sakta hai. Anthropic ki API par default, Opus 5.5 aur Haiku 5.5 ke liye `medium` aur baaki zyaadatar models ke liye `high` hai, isliye ise explicitly set karo. Teen rules:

- **Har route ke liye tune karo.** Chat, tagging aur extraction aksar low effort par bhi quality banaaye rakhte hain; multi-step maths, code aur planning ko aksar high chaahiye. Har route ke liye eval par naapo.
- **`max_tokens` mein jagah chhodo.** Thinking bhi ismein gini jaati hai. 200-token reply ke hisaab se rakha cap, model ke think karne par answer ko truncate kar deta hai, aur retry ki cost usse zyaada hoti hai jitna cap ne bachaaya.
- **Ek conversation ke andar effort ek jaisa rakho.** Requests ke beech ise badalne se prompt cache invalidate ho sakta hai.

### Prompt caching

Prompt caching prompt ke lambe, na badalne waale shuruaati hisse ko, jaise system prompt, tool definitions ya koi bada document, store kar leti hai, taaki agle calls use saste mein read karein. Ye prefix match hai: pehle tools, phir system prompt, phir messages, aur kisi bhi jagah badlaav hone par uske baad ka sab kuch invalidate ho jaata hai. Anthropic ki API par, November 2026 tak:

- 5-minute cache write ki cost input price ki 1.25 guna hai aur ek read mein vasool ho jaati hai. 1-hour write 2 guna hai aur do reads mein vasool hota hai.
- Ek read ki cost zyaadatar models par input ki 0.1 guna hai, aur Opus 5.5 aur Sonnet 5.5 par 0.05 guna.
- Ek minimum length se chhote prompts, maujooda models par 512 tokens, cache nahi hote, aur koi error ye nahi bataata.

Caching chupchaap fail hoti hai. Aam vajahein: system prompt ke upar ke hisse mein koi date ya request ID, har baar alag order mein banne waali tool definitions, badli hui effort setting, doosre model par switch (har model ka apna cache hota hai), ya itna kam traffic ki calls ke beech 5-minute lifetime khatm ho jaaye. Usage mein cache-read count check karo. Agar wo zero par hi rahe, to wo badlaav dhoondho.

**Response caching** alag cheez hai: aap poore answers store karte ho aur dohraaye gaye sawaalon par model ko skip kar dete ho. Ismein har hit par zyaada bachat hoti hai, par puraane ya leak hue answers jaane ka risk hai. Caching aur speed waala lesson dono ko cover karta hai.

### Batch APIs

Jo kaam ruk sakta hai, jaise raat ki summaries, bulk tagging, eval runs aur backfills, wo batch API se ja sakta hai. Anthropic ki Message Batches API input aur output ke liye normal price ka 50% leti hai. Zyaadatar batches ek ghante mein poore ho jaate hain; jo requests 24 ghante mein poori nahi hotin wo expire ho jaati hain aur unka bill nahi banta. Batch aur caching ke discounts saath milte hain, aur 1-hour cache batches ke liye sahi hai kyunki unmein 5 minute se zyaada lag sakte hain.

### Agents: har step par history badhti hai

Agent har step par poori conversation bhejta hai, isliye har step ke saath input badhta hai. Maan lo 4,000-token prefix hai aur har step mein 1,500 naye tokens. Aath steps mein 4,000 × 8 + 1,500 × (0 + 1 + … + 7) = 32,000 + 42,000 = 74,000 input tokens jaate hain, us cheez ke liye jo ek hi task lagti hai. Fixed prefix aur puraani history cache karo, sirf task ki zaroorat ke tools load karo, step limit lagao, aur lambe runs mein puraane tool results summarise ya clear karo. Agent budgets aur kill switches waala lesson limits ko cover karta hai.

### Bhaarteey bhaashaayein aur self-hosting

Tokenizer ke hisaab se, wahi reply English ke muqaable Hindi, Tamil ya Bengali mein kai guna zyaada tokens le sakta hai, isliye jis bhi bhaasha mein serve karte ho, uske liye tokens per request naapo. Bhaarteey bhaashaaon mein AI waala lesson ise cover karta hai.

Open model ko self-host karne par per-token bill ki jagah ek fixed mahine ka bill aa jaata hai. Udaaharan ke liye, maan lo ek GPU server ko chalaane mein, logon ka samay milaakar, ₹2.5 lakh mahina lagta hai. Ek batched summary ke ₹0.47 par, API ki cost tab baraabar ho jaati hai jab aap mahine mein lagbhag 5.3 lakh summaries bhejte ho (2,50,000 ÷ 0.47). Usse neeche API jeetti hai, aur usse upar self-hosting tabhi jeetta hai jab open model wahi evals pass kare aur server busy rahe. vLLM aur total cost of ownership waale lessons dikhaate hain ki asli numbers kaise bharein.

### Ek calculator

Ye calculator table ki prices aur ₹94 per dollar ka ek illustrative rate use karta hai (mid November 2026 mein rupee lagbhag ₹93 se ₹94 par trade hua). Ye neeche waale worked example ki rows print karta hai.

```python
RATE = 94  # rupees per US dollar: illustrative (about 93 to 94 in mid November 2026)

# US dollars per million tokens, Anthropic API pricing page, checked 28 November 2026
PRICES = {
    "opus-5.5":  {"in": 4.00, "out": 20.00, "cache_read": 0.20, "cache_write": 5.00},
    "haiku-5.5": {"in": 0.10, "out": 0.50, "cache_read": 0.01, "cache_write": 0.125},
}

def cost_inr(model, fresh_in, out, cache_read=0, cache_write=0, batch=False):
    """Rupees for one request. `out` includes thinking tokens, which bill as output."""
    p = PRICES[model]
    usd = (fresh_in * p["in"] + out * p["out"]
           + cache_read * p["cache_read"] + cache_write * p["cache_write"]) / 1e6
    return usd * RATE * (0.5 if batch else 1)

rows = {  # (rupees per request, requests per month)
    "summary, before":  (cost_inr("opus-5.5", 1500, 200), 300_000),
    "summary, batch":   (cost_inr("opus-5.5", 1500, 200, batch=True), 300_000),
    "classify, before": (cost_inr("opus-5.5", 600, 100), 300_000),
    "classify, small":  (cost_inr("haiku-5.5", 600, 10), 300_000),
    "chat, before":     (cost_inr("opus-5.5", 6000, 750), 60_000),
    "chat, after":      (cost_inr("opus-5.5", 1000, 500, cache_read=2700, cache_write=300), 60_000),
}
for name, (per, n) in rows.items():
    print(f"{name:17} ₹{per:.4f} each, ₹{per * n / 1e5:.2f} lakh a month")
```

### Safely ghataana

Ek baar mein ek hi lever badlo aur pehle aur baad mein us feature ke evals chalaao. Cost aur quality saath-saath report karo. Jab koi badlaav paisa bachaaye par quality thodi ghataaye, to likh lo ki team ne wo trade maan liya aur kyun.

### Launch se pehle feature ki price tay karna

Pilot se har user ki mahine ki cost ka andaaza lagao: har user ki requests × ek request ki cost. Ise usse compare karo jo user GST aur payment fees ke baad deta hai. Udaaharan ke liye, neeche waale trimmed chat mein ₹1.51 per reply par, mahine mein 600 messages bhejne waale student ki cost ₹906 hai, jabki ₹149 ka plan lagbhag ₹120 hi laata hai. Ya to chat aise saste route par chale jo apna eval pass kare, ya plan mein daily limit ho. Launch se pehle caps lagao, aur pehle do hafton mein dobaara check karo, kyunki asli users shaayad hi kabhi pilot group jaisa behave karte hain.

## Ek example se samjho

Kolkata ka ek customer-service platform model calls par mahine mein lagbhag ₹6.3 lakh kharch karta hai, sab Opus 5.5 par, aur ise aadha karna chaahta hai. Neeche ke saare volumes aur token counts illustrative hain, upar waali table se ₹94 per dollar par price kiye gaye.

**Step 1: naapo.** Tag kiye gaye logs teen features dikhaate hain:

- **Raat ki ticket summaries**: har raat 10,000, mahine mein 3 lakh. Har ek mein 1,500 input aur 200 output tokens. Subah 10 baje se pehle inhein koi nahi padhta.
- **Ticket classification**: mahine mein 3 lakh. Har ek mein 600 input tokens, par output 100 tokens hai: 10-token ka label aur 90 tokens ki thinking.
- **Live chat**: mahine mein 60,000 replies. Har ek mein 5,000-token ka system prompt aur tools, uncached, aur saath mein 1,000 tokens ki history aur sawaal. Output 750 tokens hai: 450 visible aur 300 thinking.

**Step 2: har feature ki price nikaalo.**

- Summaries: (1,500 × $4 + 200 × $20) ÷ 10 lakh = $0.0100, yaani ₹0.94 har ek, to 3 lakh × ₹0.94 = ₹2.82 lakh (45%).
- Classification: (600 × $4 + 100 × $20) ÷ 10 lakh = $0.0044, yaani ₹0.41 har ek, to ₹1.24 lakh (20%). 100 output tokens mein se 90 thinking hain.
- Chat: (6,000 × $4 + 750 × $20) ÷ 10 lakh = $0.0390, yaani ₹3.67 har ek, to 60,000 × ₹3.67 = ₹2.20 lakh (35%).

Total: ₹6.26 lakh.

**Step 3: har feature par ek lever badlo.**

- **Summaries batch API par jaati hain.** Wahi tokens aadhi price par: ₹0.47 har ek, ₹1.41 lakh mahina. Ye subah 10 baje se bahut pehle taiyaar ho jaati hain.
- **Classification low effort par Haiku 5.5 par jaata hai.** Opus 5.5 par sirf effort ghataane se thinking hat jaati hai (600 × $4 + 10 × $20 = $0.0026, ₹0.24 har ek, 41% kam). Low effort par chhote model ki cost (600 × $0.10 + 10 × $0.50) ÷ 10 lakh = $0.000065, ₹0.0061 har ek, lagbhag ₹1,800 mahina hai. 400 labelled tickets par accuracy 94% se 93% hoti hai, aur team ise maan leti hai.
- **Chat Opus 5.5 par hi rehta hai.** System prompt ko 5,000 se 3,000 tokens tak trim karke cache kiya jaata hai. Din ka busy traffic 90% hit rate deta hai, to ausatan 2,700 tokens $0.20 per million par cache reads hain aur 300 tokens $5 per million par writes. Prompt lagbhag 150 shabdon se chhote replies maangta hai, jisse visible output 450 se 200 tokens par aa jaata hai. Thinking 300 par hi rehti hai. `max_tokens` 200 nahi, 1,200 par set hai, taaki thinking kabhi reply ko truncate na kare. Per reply: 1,000 × $4 + 2,700 × $0.20 + 300 × $5 + 500 × $20 = $0.01604, yaani ₹1.51, to ₹0.90 lakh mahina.
- **Limits.** Har support agent ke liye daily cap, chat ke tool use par step limit, budget ke 80% par spending alert aur provider console mein hard monthly limit.

| Feature | Pehle | Baad mein | Lever | Quality check |
| --- | --- | --- | --- | --- |
| Raat ki summaries | ₹2.82 lakh | ₹1.41 lakh | Batch API, aadhi price | Pehle ki tarah subah 10 baje se pehle taiyaar |
| Classification | ₹1.24 lakh | ₹0.02 lakh | Chhota model, low effort | 400 tickets par 94% se 93%, maan liya gaya |
| Live chat | ₹2.20 lakh | ₹0.90 lakh | Chhota cached prompt, chhote replies | Satisfaction scores mein koi badlaav nahi |
| Total | ₹6.26 lakh | ₹2.33 lakh | | 63% kam |

₹2.33 lakh ek andaaza hai. Team ise agle mahine ke asli bill se milaati hai, kyunki 90% cache hit rate ek assumption hai: raat mein, jab chats ke beech 5 minute se zyaada ka gap hota hai, cache expire ho jaata hai aur har reply read ki jagah write ke paise deta hai.

## Aam galtiyaan

- **Sirf dikhne waala reply padhna.** Model upgrade ke baad bill doguna ho jaata hai jabki replies utne hi lambe dikhte hain. Vajah thinking tokens hain: price ko dosh dene se pehle usage mein thinking count check karo.
- **Sab kuch dobaara bhejne waale retries.** Timeout par teen turant retries ek 6,000-token prompt ko chaar baar tak bill karte hain aur overload ko aur bigaadte hain. Exponential backoff aur jitter ke saath zyaada se zyaada do retries use karo.
- **Aisa cache jo kabhi hit nahi hota.** System prompt ke upar ek timestamp har prefix ko alag bana deta hai. Lakshan: cache-read tokens zero par rehte hain jabki cache writes, jo plain input se mehnge hain, aate rehte hain.
- **Har call par har tool.** 200 tokens waali tees tool definitions har step mein 6,000 input tokens jod deti hain, bhale hi step ko do hi tools chaahiye hon.
- **Thinking ke liye jagah ke bina `max_tokens` cap.** Replies `max_tokens` stop reason ke saath vaakya ke beech mein ruk jaate hain, users retry karte hain, aur aap do baar paise dete ho.
- **Cost ko completed task ke bajaay request ke hisaab se judge karna.** Jo model per call 20 guna sasta hai par har paanch mein se ek baar fail hota hai, retries aur human review jodne par zyaada mehnga pad sakta hai.
- **Quality check kiye bina cost ghataana.** Har badlaav par evals chalaao, aur numbers sambhaalkar rakho.

## Jab cost ghataana galat lakshya ho

- **Feature abhi kaam hi nahi kar raha.** Pehle apne evals par quality theek karo; optimise baad mein.
- **Bachat bahut chhoti hai.** Mahine ke ₹2,000 bachaana hafton ki engineering ya naapi ja sakne waali quality drop ke laayak nahi hai.
- **Latency ya trust zyaada maayne rakhta hai.** High-stakes task par aisa sasta model jo dheema ho ya zyaada galtiyaan kare, support aur khoye hue users mein zyaada mehnga pad sakta hai.

## Demo se production tak

- **Har call ko tag karo**, feature, user, model, effort aur prompt version se, aur saare token counts aur cost store karo.
- **Ek cost dashboard banao**: feature ke hisaab se roz ka spend, cost per completed task, sabse heavy users, output mein thinking ka hissa aur cache hit rate, budget aur alert threshold ki lines ke saath. Ise quality metrics ke saath har hafte review karo.
- **Har feature ka budget tay karo**, alerts ke saath, aur provider par hard limits lagao.
- **Baar-baar re-price karo.** Providers prices ghataate hain aur saste models release karte hain; chhah mahine puraana faisla ab zaroorat se zyaada paise dilwa raha ho sakta hai.
- **Sasta raasta tested rakho**, jaise ek chhota fallback model, taaki costs achaanak badhein to jaldi switch kar sako.
