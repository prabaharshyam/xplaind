## Ye kya hai

Model ko zaroori information dene ke do tareeke hain:

- **Long context**: poora document, ya kai documents, prompt mein daalo aur sawaal poochho.
- **Retrieval (RAG)**: sabse relevant kuch passages search karo aur sirf wahi prompt mein daalo.

Modern models bahut lambe inputs le lete hain, isliye long context aksar possible hota hai. Wo samajhdaari hai ya nahi, ye accuracy, cost, latency aur scale par depend karta hai.

| | Long context | RAG |
|---|---|---|
| Model ko kya milta hai | Poora contract (40,000 tokens), instructions aur end mein sawaal | 3 chunks aur sawaal (3,000 tokens) |
| Taakat | Sab kuch dekhta hai, cross-reference kar sakta hai | Sasta, tez, millions of documents tak scale hota hai |
| Kamzori | Cache na ho toh mehenga, dheema | Jo retrieval miss kare, wo ye bhi miss karta hai |

```flow
dir: LR
title: Beech ka raasta
Sawaal -> Sahi 2 documents dhoondho -> Poore documents model ko bhejo
```

Is lesson mein hum Chennai ki ek law firm ko follow karenge jo contract-review assistant bana rahi hai, do bilkul alag use cases ke saath.

## Ye kaam kaise karta hai

**Lambe inputs mein accuracy.** Models saari positions ko barabar use nahi karte. Studies mein paaya gaya ki lambe context ke beech ki information ko shuru ya end ki information se kam achhe se use kiya jaata hai ("lost in the middle"), aur input badhne par simple tasks mein bhi performance gir sakti hai. Naye models behtar hue hain, par aapko apne documents aur question types par khud test karna chahiye.

**Cost.** Har call mein har input token ka paisa lagta hai. Har sawaal ke saath 200,000-token ka document bhejna, 3,000 tokens ke retrieved passages bhejne se kahin mehenga padta hai. **Prompt caching** isse badal deti hai: agar wahi lamba document kai sawaalon mein reuse ho, toh baad ki calls mein cached input bahut sasta aur tez ho sakta hai.

**Latency.** Input jitna lamba, pehla token aane mein utna zyada time lagta hai. Cache na ho toh lambe prompts interactive use ko dheema kar dete hain.

**Scale.** Context window ki ek limit hoti hai; company ke documents ki nahi. Corpus window se bada ho jaaye, toh kuch retrieve karna hi padega, kam se kam ye chunne ke liye ki kaunse documents bhejne hain.

**Thumb rules.**

- Ek ya kuch documents, ek session mein un par kai sawaal, aur aise sawaal jinhe poora document chahiye (summaries, sections ke beech comparison): long context, ho sake toh cached.
- Bade ya badhte collections, chhote factual sawaal, bahut saare users: RAG.
- Beech ka raasta: document level par retrieve karo (sahi do contracts dhoondho), phir wo poore documents context mein daalo.

**Hybrid aadatein.** Long context ke saath bhi instructions aur sawaal end mein rakho, sections ya pages ke citations maango, aur documents ko ek consistent, labelled format mein rakho.

**Options ki tulna:**

| Factor | Long context | RAG |
| --- | --- | --- |
| Corpus size | Context window tak | Unlimited |
| Poora document chahiye wale sawaal | Strong | Weak, chunking par depend |
| Chhote factual lookups | Theek, par mehenga | Strong |
| Ek sawaal ka cost | Uncached mein zyada, caching ke saath kam | Kam |
| Latency | Zyada, caching ke saath kam | Kam |
| Badalte documents | Har baar dobara bhejo | Badle huye items re-index karo |
| Engineering effort | Kam | Zyada: chunking, indexing, retrieval tuning |

**Ek worked cost comparison.** Maan lo input ka price per million tokens fixed hai. 12 sawaalon mein se har ek ke saath 40,000-token ka contract bhejne ka matlab lagbhag 480,000 input tokens. Caching ke saath, baad ki calls cached contract ko normal price ke ek hisse mein padhti hain, isliye total lagbhag chauthai tak gir sakta hai. RAG har sawaal par lagbhag 3,000 tokens bhejta hai, total 36,000, jo aur sasta hai, par cross-reference wale sawaalon par uska score kharab raha. Sahi choice, us task ke liye accuracy ko in costs ke saath tolkar hoti hai, sirf cost dekhkar nahi.

**Apne documents par test karo.** Published studies chetavni deti hain, jawab nahi. Aise sawaal likho jinka jawab document mein shuru mein, beech mein aur end mein ho, aur aise sawaal jinhe do door ke sections chahiye. Dono tareeke se chalao aur failures padho.

**Code mein ek position test.** Ek asli document ki alag-alag depths par ek fact daalo aur dekho ki jawab sahi rehte hain ya nahi:

```python
import anthropic

client = anthropic.Anthropic()
FACT = "The penalty for late GST filing under clause 14.3 is ₹750 per day."
QUESTION = "What is the penalty per day for late GST filing under clause 14.3?"

def plant(doc, depth):
    cut = int(len(doc) * depth)
    return doc[:cut] + "\n\n" + FACT + "\n\n" + doc[cut:]

def position_test(doc, depths=(0.05, 0.5, 0.95), runs=3):
    for d in depths:
        correct = 0
        for _ in range(runs):
            r = client.messages.create(
                model="claude-sonnet-5-5", max_tokens=100,       # check the docs for current names
                messages=[{"role": "user", "content": plant(doc, d) + "\n\n" + QUESTION}])
            text = "".join(b.text for b in r.content if b.type == "text")
            correct += "750" in text
        print(f"fact at {d:.0%} depth: {correct}/{runs} correct")
```

Ise apne asli documents aur lengths ke saath chalao. Phir aise sawaal test karo jinhe do door ke sections chahiye, jahan long context aksar RAG ko haraata hai.

**Ek cost comparison jo aap adjust kar sakte ho.** Current prices daalo, us date ke saath jab aapne check kiye:

```python
def cost_inr(input_tokens, output_tokens, price_in, price_out, cached_tokens=0, cache_read_ratio=0.1,
             usd_to_inr=84):
    """Prices in USD per million tokens. cache_read_ratio: cached input price as a share of normal."""
    uncached = input_tokens - cached_tokens
    usd = (uncached * price_in + cached_tokens * price_in * cache_read_ratio + output_tokens * price_out) / 1e6
    return usd * usd_to_inr

questions, doc, out = 12, 40_000, 300
long_ctx = sum(cost_inr(doc + 100, out, 3, 15, cached_tokens=doc if i else 0) for i in range(questions))
rag = questions * cost_inr(3_000, out, 3, 15)
print(f"long context with caching ₹{long_ctx:.1f}, RAG ₹{rag:.1f}")
```

Pehli call poore document ka paisa deti hai (aur cache likhne ke liye aam taur par thoda extra), baad ki calls agar cache lifetime ke andar aayein toh use sasta padhti hain. Numbers ko apne document sizes aur traffic ke hisaab se badlo.

**Beech ka raasta code mein.** Chunks nahi, poore documents retrieve karo, phir padhne ka kaam long context ko karne do:

```python
def doc_level_answer(question, search_docs, load_doc, max_docs=2):
    docs = search_docs(question, k=max_docs)          # search over document summaries or titles
    context = "\n\n".join(f"<document title='{d['title']}'>\n{load_doc(d['id'])}\n</document>" for d in docs)
    return context + f"\n\nAnswer using the documents above, citing titles and sections.\nQuestion: {question}"
```

Ye contracts, policies aur reports ke liye theek hai, jahan sawaalon ko poora document chahiye par aapke paas sainkdon documents hain.

**Teen cheezein naapkar faisla karo.** Apne question types par accuracy, apne traffic par ek jawab ka cost, aur pehla token aane ka time. Har option ke liye numbers ek chhoti table mein likho aur aadat se nahi, client ke saath milkar chuno.

## Ek example se samjho

Chennai ki ek law firm contract review ke liye assistant chahti hai. Do use cases:

*Ek contract review karna.* Ek lawyer 60-page agreement (lagbhag 40,000 tokens) upload karta hai aur ek darjan sawaal poochhta hai: termination rights, indemnity caps, clauses ke beech conflicts. Kai jawabon ke liye poora document chahiye. Aap contract cache karke long context use karte ho. Pehla sawaal 9 seconds leta hai; baad ke 2 se 3 seconds lete hain aur cache ki wajah se bahut kam kharch hota hai. 30 sawaalon ke test mein long context ka score 90% raha jabki chunk-based RAG ka 73%, jisne clauses ke beech cross-references miss kiye.

*Firm ki precedent library mein search karna.* 25,000 purane contracts, kisi bhi context window se bahut bade. Lawyers poochhte hain "IT services contracts mein wo indemnity clauses dhoondho jo pichhle 12 mahine mein diye fees tak capped hain." Aap metadata filters ke saath hybrid retrieval se sabse achhe 20 clauses dhoondhte ho, phir ek model citations ke saath unka summary banata hai.

Firm ko dono milte hain, har ek wahan jahan woh fit hota hai.

| Use case | Approach | Accuracy | Notes |
| --- | --- | --- | --- |
| Ek 60-page contract review karna | Long context, cached | 90% | Chunk-based RAG ka score 73% |
| 25,000 precedents mein search | Filters ke saath hybrid retrieval | Recall se naapi jaati hai | Kisi bhi window se bahut bada |

## Aam galtiyaan

- **Maan lena ki long context hamesha zyada accurate hota hai.** Test karo; length aur position ke saath accuracy gir sakti hai.
- **Ek sawaal ka cost ignore karna.** Har sawaal par lambe uncached prompts scale par mehenge ho jaate hain.
- **Caching bhool jaana.** Wahi document baar-baar use karne par ye economics badal deti hai.
- **Sawaal pehle rakhna.** Instructions aur sawaal lambe material ke baad rakho.
- **"RAG khatam ho gaya" wali soch.** Bade collections ko ab bhi retrieval chahiye.
- **Caching ke bina costs compare karna** jab wahi document kai sawaalon ke kaam aa raha ho.
- **Maan lena ki bada window matlab model use poori tarah achhe se use karta hai.** Positions aur cross-references test karo.

## Jab choice saaf ho

- **Ek chhota document**: seedha prompt mein daal do.
- **Millions of documents**: kisi na kisi tarah ka retrieval chahiye, kam se kam documents chunne ke liye.
- **Structured data se jawab**, jaise records ya tables: database query ya tool use karo, inme se koi nahi.

## Demo se production tak

- Apne golden set par chune hue approach ka **accuracy, cost aur latency record karo**, aur model badalne par dobara check karo.
- Jo lambe documents kuch minutes ke andar reuse hote hain, unke liye **prompt caching use karo**.
- **Har request ke input tokens log karo** aur achanak badhne par alert lagao.
- Model badalne ya document lengths badhne par **position test dobara chalao**.
- **Beech ka raasta yaad rakho**: collections badhne par document-level retrieval aksar jeet jaata hai.
