## Ye kya hai

Teen aadatein jo deployment ko operate karne ke liye surakshit banati hain:

- **Alag environments.** Banane ke liye development, production jaisi settings ke saath testing ke liye staging, asli users ke liye production. Har ek ka apna database, keys aur settings hote hain.
- **Secrets management.** Passwords, API keys aur tokens secret store mein rehte hain, run time par app tak pahunchte hain, aur code, images, logs ya chat mein kabhi nahi aate.
- **Infrastructure as code (IaC).** Servers, databases, networks aur permissions files mein describe hote hain, code ki tarah review hote hain aur console mein click karke jodne ki jagah Terraform jaise tool se apply hote hain.

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | own database, own model key, 1 instance
Apply -> Staging | masked data, own model key, 1 instance
Apply -> Production | real data, own model key with a spend limit, 3 instances
The same container image -> Development
The same container image -> Staging
The same container image -> Production
```

Har environment apni settings environment se aur apne secrets vault se leta hai.

Is lesson mein hum Chandigarh ki ek lending company ke saath chalenge, jo jaldbaazi mein bane pilot ko production ke liye taiyaar kar rahi hai.

## Ye kaam kaise karta hai

**Environment mein config.** Wahi image sab jagah chalti hai; sirf settings badalti hain. Unhein environment variables (`DATABASE_URL`, `MODEL_NAME`, `LOG_LEVEL`) se padho aur start-up par settings model se validate karo. Tab koi missing value boot par zor se fail hoti hai, raat 2 baje pehli asli request par nahi.

**Environments ke beech kya alag hota hai.** Alag databases (staging ko production data par point mat karo jab tak woh masked na ho), apni spend limits ke saath alag model API keys, production ke bahar kam instance counts, aur production par sakht access.

**Secret stores.** Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) ya HashiCorp Vault jaise tools secrets rakhte hain, control karte hain ki har ek ko kaun padh sakta hai, aur har access log karte hain. App unhein start-up par apni service identity se padhta hai. Secrets ko schedule par rotate karo, aur jab koi chhod kar jaaye ya leak ka shak ho toh turant. CI mein secret scanner chalao taaki keys repository tak pahunchne se pehle pakdi jayein.

**Terraform.** Aap HCL mein files likhte ho jo resources describe karti hain:

```hcl
resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = "centralindia"
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false
}
```

`terraform plan` dikhata hai ki exactly kya badlega; reviewer plan ko pull request mein padhta hai; `terraform apply` use kar deta hai. Terraform ek **state** file mein record karta hai ki woh kya manage kar raha hai, jise remote mein (locking waale storage bucket mein) rakhna padta hai, kabhi laptop par nahi, aur use protect karna padta hai kyunki usmein sensitive values ho sakti hain. Ek hi set files aur har environment ke liye ek variable staging aur production ko shape mein ek jaisa rakhta hai.

**Har tarah ki value kahan rehti hai:**

| Value | Example | Kahan rehti hai |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, har environment ke liye set |
| Secret | Database password, model API key | Secret store, app ki identity se padhi jaati hai |
| Infrastructure | Database size, network rules | Git mein Terraform files |
| Infrastructure state | Terraform kaunse resources manage karta hai | Remote, locked, access-controlled storage |
| Test data | Masked customer records | Sirf staging database mein |

**Review loop.** Infrastructure ka badlaav ek pull request se shuru hota hai jo Terraform files edit karta hai. CI `terraform plan` chalata hai aur output post karta hai, jaise "1 to add, 0 to change, 0 to destroy". Reviewer sirf code nahi, plan padhta hai, kyunki plan dikhata hai ki asal mein kya hoga. Approval ke baad, apni identity waali pipeline `terraform apply` chalati hai. Routine badlaavon ke liye kisi ko production console access nahi chahiye, jisse un logon ki ginti ghat jaati hai jo wahan galti kar sakte hain.

**Code mein validated settings.** `pydantic-settings` environment variables padhta hai aur jaldi fail hota hai:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_url: SecretStr
    model_api_key: SecretStr
    model_name: str = "claude-sonnet-5-5"            # check the docs for current names
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()        # raises a clear error listing every missing or invalid value
```

`SecretStr` secrets ko logs aur error messages se bahar rakhta hai: print karne par `**********` dikhta hai.

**Locking ke saath remote state.** Har Terraform project backend se shuru hota hai, taaki state shared ho aur do log ek saath apply na kar sakein:

```hcl
terraform {
  required_version = ">= 1.6"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}
```

Har environment ke liye ek state file rakho (alag `key`), aur `env/staging.tfvars` aur `env/prod.tfvars` jaisi alag variable files.

**Secrets ko Terraform mein store kiye bina.** Terraform ko vault banane do aur app ki identity ko access dene do; secret values vault ke through hi daalo, taaki woh code ya state mein kabhi na aayein:

```hcl
resource "azurerm_key_vault" "kv" {
  name                      = "claims-${var.env}-kv"
  location                  = "centralindia"
  resource_group_name       = azurerm_resource_group.main.name
  tenant_id                 = data.azurerm_client_config.current.tenant_id
  sku_name                  = "standard"
  enable_rbac_authorization = true
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

**Schedule par drift pakdo.** Kabhi-kabhi log console mein cheezein badal dete hain. Raat ki ek job ise pakad leti hai:

```bash
terraform plan -var-file=env/prod.tfvars -detailed-exitcode -lock=false > plan.txt
case $? in
  0) echo "no drift" ;;
  2) echo "DRIFT: production differs from code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

**Code scan karo.** `tflint` aur Checkov jaise tools pull requests mein hi, kuch apply hone se pehle, public storage, khule firewall rules aur missing encryption flag kar dete hain.

**Browser mein try karo.** Start-up par check ki gayi settings jaldi aur saaf fail hoti hain. Koi value hatao aur run karo.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    database_url: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "database_url": "postgresql://app:secret@db/app", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.daily_budget_inr, s.database_url)     # the secret prints as stars
except ValidationError as err:
    print("start-up stopped:", [e["loc"][0] for e in err.errors()])
```

## Ek example se samjho

Chandigarh ki ek lending company ka pilot jaldi mein bana tha. Usne testing aur asli data ke liye ek hi database use kiya, model key ek `.env` file mein rakhi jo mahino pehle commit hui thi, aur resources console mein haath se bane the.

Production se pehle, aap:

1. Leak hui key rotate karte ho aur CI mein secret scanner jodte ho. Woh history mein do aur purani keys dhoondhta hai; dono rotate hoti hain.
2. Network, database, storage, container app aur Key Vault ke liye Terraform likhte ho, `env` ko ek variable ke roop mein. `terraform apply` saaf staging banata hai; reviewed plan production banata hai.
3. Har secret Key Vault mein le jaate ho; app unhein apni managed identity se padhta hai. Staging aur production ki alag model keys hain, alag monthly limits ke saath.
4. Staging mein pichhle mahine ki applications ki masked copies load karte ho: names, PAN aur phone numbers badal diye gaye.

Jab client ka auditor poochhta hai "production database password kaun padh sakta hai?", aap Key Vault access policy aur uske access log se jawab dete ho. Jab region outage drill hoti hai, team wahi Terraform use karke 40 minute mein doosre region mein staging dobara bana leti hai.

| Auditor ka sawaal | Pehle jawab | Baad mein jawab |
| --- | --- | --- |
| Secrets kahan store hain? | ".env file mein" | Key Vault, access log ke saath |
| Production kaun badal sakta hai? | Kai log, console ke through | Review ke baad, deployment pipeline |
| Kya aap system dobara bana sakte ho? | Pata nahi | Haan, Terraform se, 40 minute mein |
| Kya test data asli hai? | Haan | Nahi, masked copies |

## Aam galtiyaan

- **Production data par test karna.** Ek kharab script aur asli customers prabhavit. Alag rakho, aur test data mask karo.
- **Secrets Git mein, thodi der ke liye bhi.** History unhein rakhti hai. Jo key kabhi commit hui ho, use rotate karo.
- **Laptop par Terraform state.** Woh kho jaati hai ya purani ho jaati hai, aur usmein secrets ho sakte hain. Remote, locked state use karo.
- **Terraform ke saath console changes.** Agla apply unhein revert karta hai ya conflict karta hai. Code badlo.
- **Har environment ki alag shape.** Agar staging mein woh private network nahi hai jo production mein hai, toh staging ke tests kam hi saabit karte hain.
- **Terraform files mein likhi secret values,** jo state mein bhi pahunch jaati hain.
- **Saare environments ke liye ek hi state file,** jisse staging ka badlaav production ko chhoo sakta hai.
- **Console changes jinka koi record nahi,** jo mahino baad drift ke roop mein milte hain.

## Jab Terraform zaroorat se zyada hai

- **Ek chhoti si service** aise platform par jo infrastructure khud manage karta hai.
- **Chhote samay ka prototype** jise aap agle mahine delete kar doge.
- **Apni infrastructure team aur tool waala client** (jaise Bicep, CloudFormation ya Pulumi): unka tool use karo.

Environment variables, validated settings aur secret store sabse chhote project mein bhi rakhne layak hain.

## Demo se production tak

- **Har environment ke liye remote, locked state rakho,** restricted access ke saath.
- **Pull requests mein plan karo** aur review ke baad hi CI se apply karo.
- **Production par raat ko drift checks chalao.**
- **CI mein Terraform scan karo,** risky settings ke liye.
- **Start-up par settings validate karo,** secrets `SecretStr` ki tarah aur app ki identity se padhe hue.

## Practice karo

Apne chune cloud ke liye Terraform ke getting-started tutorials follow karo aur config par Twelve-Factor page padho.

1. `env = "staging"` ke liye ek storage bucket aur ek chhota managed database banane waala Terraform likho, database publicly reachable na ho. Apply karo, plan padho, phir destroy karo.
2. Apne app ki settings ko environment variables se padhne waale validated settings model mein le jao, aur kuch missing hone par start-up saaf tareeke se fail karao.
3. Ek secret apne cloud ke secret manager mein rakho aur app se use identity ke through padhwao.
4. Cloud console mein ek setting haath se badlo, phir drift check chalao aur confirm karo ki woh farak report karta hai.

**Aapka kaam poora jab:** aap apna staging environment code se dobara bana sako aur dikha sako ki aapki repository mein kahin koi secret nahi hai.
