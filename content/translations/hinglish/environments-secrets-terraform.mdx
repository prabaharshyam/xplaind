## Yeh kya hai

Teen aadatein jo kisi deployment ko operate karne ke liye safe banaati hain:

- **Alag environments.** Build karne ke liye development, production jaisi settings ke saath test karne ke liye staging, asli users ke liye production. Har ek ka apna database, keys aur settings hote hain.
- **Secrets management.** Passwords, API keys aur tokens ek secret store mein rehte hain, run time par app tak pahunchte hain aur kabhi code, images, logs, chat ya Terraform state mein nahi dikhte.
- **Infrastructure as code (IaC).** Servers, databases, networks aur permissions ko console mein click karke jodne ki bajaay files mein describe kiya jaata hai, code ki tarah review kiya jaata hai aur Terraform jaise tool se apply kiya jaata hai.

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | apna database, apni model key, 1 instance
Apply -> Staging | masked data, apni model key, 1 instance
Apply -> Production | asli data, spend limit waali apni model key, 3 instances
Wahi container image -> Development
Wahi container image -> Staging
Wahi container image -> Production
```

Har environment apni settings environment variables se aur apne secrets vault se leta hai. Sirf values alag hoti hain; code aur image ek hi hain. Yahi asli baat hai: agar staging pass hota hai, to production bhi hona chahiye.

Yeh lesson Chandigarh ki ek lending company ko follow karta hai jo jaldbaazi mein bane ek pilot ko Azure par production ke liye taiyaar kar rahi hai. Ye ideas AWS aur Google Cloud par bhi laagu hote hain, bas resource names alag hote hain.

## Yeh kaise kaam karta hai

### Config environment mein

Wahi image har jagah chalta hai; sirf settings alag hoti hain. Unhe environment variables (`DATABASE_HOST`, `MODEL_NAME`, `LOG_LEVEL`) se read karo aur start-up par ek settings model se validate karo. Tab koi missing value boot par, deploy ke dauraan hi zor se fail hoti hai, raat 2 baje pehli asli request par nahi.

### Environments ke beech kya alag hota hai

| Value | Udaaharan | Kahaan rehti hai |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, har environment ke liye alag set |
| Secret | Model API key, webhook signing key | Secret store, app ki identity se read |
| Database access | Production database | Managed identity sign-in, isliye koi password hota hi nahi |
| Infrastructure | Database size, network rules | Git mein Terraform files |
| Infrastructure state | Terraform kaun-se resources manage karta hai | Remote, locked storage, har environment ki ek state |
| Test data | Masked customer records | Sirf staging database |

Production ko zyada instances bhi milte hain, provider par monthly spend limit ke saath apni model key, aur use chhoo sakne waale log kahin kam hote hain.

### Secret stores aur rotation

Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) ya HashiCorp Vault jaise tools secrets rakhte hain, control karte hain ki har ek ko kaun read kar sakta hai aur har read ko log kar sakte hain. Azure par reads tabhi log hote hain jab aap vault ki diagnostic settings on karte ho, isliye yeh pehle din hi karo; auditor zaroor poochhega.

App apni **managed identity** se secrets read karta hai: yeh ek identity hai jo Azure chalte hue app ko deta hai, isliye vault tak pahunchne ke liye app ko kisi password ki zaroorat nahi hoti. Secrets ko ek schedule par rotate karo, aur jab koi chhodkar jaaye ya leak ka shak ho to turant.

Rotation mein ek catch hai. Jo app secret ko sirf start-up par read karta hai, woh restart hone tak purani value hi rakhta hai. Teen patterns mein se ek chuno: har rotation ke baad app restart karo, timer par secrets reload karo, ya koi call authentication error ke saath fail ho to ek baar reload karo. Kuch platforms, jinmein Azure Container Apps bhi hai, aapke liye vault secret ke latest version ko follow kar sakte hain; woh app ko kab restart karta hai, yeh jaanne ke liye apne platform ke docs padho. CI mein ek secret scanner chalao taaki keys repository tak kabhi pahunchein hi nahi.

### Terraform: code, plan, apply, state

Aap HCL mein files likhte ho, jo Terraform ki configuration language hai, aur unmein woh resources describe karte ho jo aapko chahiye. Region aur environment variables hain, isliye wahi files koi bhi environment kahin bhi build kar deti hain:

```hcl
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "location" {
  type    = string
  default = "centralindia"
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = var.location
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false

  authentication {
    active_directory_auth_enabled = true
    password_auth_enabled         = false
    tenant_id                     = data.azurerm_client_config.current.tenant_id
  }
}
```

`authentication` block passwords band kar deta hai: app apni managed identity se Postgres mein sign in karta hai, isliye leak ya rotate karne ke liye koi database password hota hi nahi.

`terraform plan` teen cheezein compare karta hai: aapka code, **state** file (Terraform jin resources ko manage karta hai unka uska record), aur asli cloud. Phir woh list karta hai ki woh kya create, change ya destroy karega. `terraform apply` woh changes karta hai aur state update karta hai.

### Remote state, har environment ki ek

Har project ek backend se shuru hota hai, taaki state share ho, apply ke dauraan lock rahe aur laptops se door rahe:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 5.15" }
  }
}
```

Is lesson ka code Terraform 1.17.2 aur azurerm provider 5.15.0 par `terraform validate` se check kiya gaya tha (November 2026). Jin versions ko aapne test kiya hai unhe pin karo. Provider upgrades arguments ke naam badal dete hain. azurerm 5.x mein Key Vault argument `enable_rbac_authorization` hat gaya hai aur `rbac_authorization_enabled` required hai, isliye puraana copy kiya hua code validate nahi hota.

Environments ko kaise baantein? Yeh rule use karo:

- **Har environment ki ek state, uski apni key ke saath aur production ke liye uske apne access ke saath.** Tab staging ki koi galti production ko chhoo nahi sakti.
- **Shared code ek module mein.** Module Terraform ka ek folder hai jise har environment apni values ke saath call karta hai, taaki staging aur production ek hi shape ke rahein.
- **CLI workspaces** ek hi backend mein, unhi credentials ke saath, kai states rakhte hain. HashiCorp ke docs kehte hain ki jab environments ko alag credentials ya access controls chahiye tab ye suitable nahi hain. Inhe kam samay waali copies ke liye use karo, jaise har feature branch ke liye ek, production ko alag karne ke liye nahi.

### Secrets ko code aur state se bahar rakhna

State har resource ka har attribute plain text mein store karti hai, Terraform se generate kiya gaya koi bhi password bhi. Kisi value ko `sensitive` mark karne se woh sirf screen se chhipti hai; woh state mein phir bhi rehti hai. Teen bachaav, sabse achha pehle:

1. **Koi secret hi nahi.** Managed identity sign-in, jaisa upar database par hai.
2. **Write-only arguments** (Terraform 1.11 aur baad ke). Provider ko value milti hai lekin Terraform use kabhi store nahi karta. Udaaharan ke liye, azurerm mein Postgres server par `administrator_password_wo` aur Key Vault secrets par `value_wo` hai, har ek ke saath ek `_wo_version` number jise rotate karne ke liye aap badhaate ho. Terraform 1.10 ne **ephemeral resources** jode, jo ek run ke liye vault se secret read karte hain bina use save kiye.
3. **Value ko Terraform ke bahar daalo.** Terraform vault aur permissions banaata hai; koi vyakti ya pipeline secret value jodta hai.

```hcl
resource "azurerm_key_vault" "kv" {
  name                       = "claims-${var.env}-kv"
  location                   = var.location
  resource_group_name        = azurerm_resource_group.main.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = var.env == "prod"
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

Yeh role assignment app ko secret values read karne deta hai aur kuch nahi: woh unhe change ya delete nahi kar sakta.

### Code mein validated settings

`pydantic-settings` environment variables read karta hai aur jaldi fail hota hai:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_host: str
    model_api_key: SecretStr
    model_name: str                  # required: no default, so a missing value stops start-up
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()    # raises one clear error listing every missing or invalid value
```

`model_name` ka jaanboojhkar koi default nahi hai. Default model name theek usi bug ko chhipa deta hai jise aap pakadna chahte ho, aur model names aksar badalte hain. `SecretStr` secrets ko logs aur error messages se bahar rakhta hai: use print karne par `**********` dikhta hai. `.env` file sirf development ke liye hai aur `.gitignore` mein honi chahiye.

### Kaun apply kar sakta hai: review loop

Infrastructure ka koi bhi change ek pull request se shuru hota hai jo Terraform files edit karta hai:

1. CI `terraform fmt -check`, `terraform validate` aur `tflint` aur Checkov jaise scanners chalaata hai, jo public storage, khule firewall rules aur missing encryption ko flag karte hain.
2. CI `terraform plan -out=plan.bin` chalaata hai aur ek summary post karta hai, jaise "1 to add, 0 to change, 0 to destroy".
3. Reviewer sirf code nahi, plan padhta hai, kyunki ek line ka edit Terraform ko database destroy karke dobara banaane par majboor kar sakta hai.
4. Approval ke baad, ek pipeline theek wahi saved plan apply karti hai. Production ke liye ek required approval step jodo (jaise ek protected GitHub environment) aur, agar sakht rules chahiye, to Open Policy Agent jaisa ek policy check.

Pipeline **OpenID Connect (OIDC)** se Azure mein sign in karti hai: GitHub Actions ek kam samay waale token se saabit karta hai ki woh kaun hai, isliye CI settings mein koi lambe samay waala cloud password nahi rehta. Staging pipeline ko sirf staging par rights do, aur production pipeline ko sirf production par. Tab kisi ko production par routine console access ki zaroorat nahi padti, aur koi laptop se apply nahi chalaata.

### Drift: plan kya dekh sakta hai aur kya nahi

Incident ke dauraan log ab bhi console mein cheezein badalte hain. Ek nightly job production ko code se compare karta hai:

```bash
terraform plan -var-file=env/prod.tfvars -input=false -lock=false -detailed-exitcode > plan.txt
case $? in
  0) echo "no changes" ;;
  2) echo "DIFFERENCE: production does not match the code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

Exit code 2 ko dhyaan se padho. Iska matlab hai "plan ko ek difference mila". Woh ya to drift hai (kisi ne kisi managed resource ko haath se badla) ya aisa code jo merge hua lekin kabhi apply nahi hua. Plan ka text bataata hai ki kaun-sa. Sirf drift dekhne ke liye `-refresh-only` jodo.

Bada blind spot: plan sirf un resources ko check karta hai jo pehle se state mein hain. Haath se ek alag resource ke roop mein banaaya gaya firewall rule dikhta hi nahi; job green hi rehta hai. Unhe cloud activity-log alerts ya policies se pakdo, phir resource delete karo ya import block se use Terraform ke andar laao:

```hcl
import {
  to = azurerm_postgresql_flexible_server_firewall_rule.partner
  id = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/claims-prod-rg/providers/Microsoft.DBforPostgreSQL/flexibleServers/claims-prod-db/firewallRules/partner"
}

resource "azurerm_postgresql_flexible_server_firewall_rule" "partner" {
  name             = "partner"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "203.0.113.10"
  end_ip_address   = "203.0.113.10"
}
```

Agla plan "1 to import" dikhaata hai. `terraform plan -generate-config-out=generated.tf` aapke liye resource block draft kar sakta hai; woh flag abhi bhi experimental marked hai, isliye jo woh likhe use review karo.

### Apne browser mein try karo

Start-up par check ki gayi settings jaldi aur saaf fail hoti hain. Dictionary se `model_name` delete karo aur phir se run karo.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    model_name: str
    model_api_key: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "model_name": "example-model", "model_api_key": "sk-test-123", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.model_name, s.daily_budget_inr, s.model_api_key)   # the key prints as stars
except ValidationError as err:
    print("start-up stopped, missing or invalid:", [e["loc"][0] for e in err.errors()])
```

## Ek worked example

Chandigarh ki lending company ka pilot jaldbaazi mein bana tha. Usmein testing aur asli data ke liye ek hi database tha, model key mahinon pehle commit hui ek `.env` file mein thi, aur kuch resources portal mein haath se banaaye gaye the.

Production se pehle, aap:

1. Leaked key ko revoke aur rotate karte ho aur CI mein ek secret scanner jodte ho. Use history mein do aur purani keys milti hain; dono rotate ki jaati hain.
2. Network, database, storage, container app aur Key Vault ke liye Terraform likhte ho, `env` aur `location` ko variables rakhkar. Haath se bane jo resources rehne chahiye unhe import karte ho, baaki delete karte ho, aur confirm karte ho ki plan mein koi surprise nahi hai.
3. Har secret ko Key Vault mein le jaate ho, aur database ko managed identity sign-in par switch karte ho taaki koi password ho hi nahi. Staging aur production ki alag-alag model keys hain, alag-alag monthly limits ke saath.
4. Staging mein pichhle mahine ki applications ki masked copies load karte ho: names, PAN aur phone numbers badal diye gaye.
5. Sirf CI se apply karte ho: ek staging pipeline aur ek production pipeline, har ek ki apni OIDC identity, aur production se pehle ek required approval.

Jab client ka auditor poochhta hai "production model key kaun read kar sakta hai?", to aap vault par role assignments aur uska access log dikhaate ho. Ek region drill mein team `location = "southindia"` aur ek nayi state key pass karke South India mein doosra staging build karti hai. Ek gotcha saamne aaya: Key Vault aur Postgres server ke names poore Azure mein unique hone chahiye, isliye copy ke names mein ek region suffix chahiye. Is example mein rebuild mein ek ghante se kam laga; aapke case mein yeh data size par depend karta hai.

| Auditor ka sawaal | Pehle ka jawaab | Baad ka jawaab |
| --- | --- | --- |
| Secrets kahaan stored hain? | "Ek .env file mein" | Key Vault, access log ke saath |
| Kya koi database password hai? | Haan, usi file mein | Nahi, app apni identity se sign in karta hai |
| Production kaun badal sakta hai? | Kai log, portal ke zariye | Production pipeline, approved plan ke baad |
| Manual change ka pata kaise chalega? | Nahi chalega | Nightly drift check aur activity-log alerts |
| Kya test data asli hai? | Haan | Nahi, masked copies |

## Aam galtiyaan

- **Production data par testing.** Ek kharaab script aur asli customers par asar padta hai. Alag karo, aur test data ko mask karo.
- **Git mein secrets, thodi der ke liye bhi.** History unhe rakhti hai. Jo bhi key kabhi commit hui ho use rotate karo.
- **Yeh maanna ki `sensitive = true` secret ko state se bahar rakhta hai.** Yeh use sirf screen se chhipaata hai. Managed identity ya write-only arguments use karo.
- **Laptop par Terraform state.** Woh kho jaati hai ya puraani ho jaati hai, aur usmein secrets ho sakte hain. Remote, locked state use karo.
- **Staging aur production ke liye ek state, ya CLI workspaces.** Tab staging ka koi change production tak pahunch sakta hai, unhi credentials ke saath. Alag states aur access use karo.
- **Console changes jinhe koi record nahi karta.** Badle hue attributes drift ke roop mein dikhte hain; haath se bane naye resources bilkul nahi dikhte. Activity log par alert lagao aur import ya delete karo.
- **Laptops se apply chalaana.** Kisi ko nahi pata ki kaun-sa code apply hua. Reviewed plan ko sirf CI se apply karo.
- **Har environment ka alag shape.** Agar staging mein woh private network nahi hai jo production mein hai, to staging tests bahut kam saabit karte hain.
- **Versions pin kiye bina puraana provider code copy karna.** Major versions ke beech arguments ke naam badal jaate hain; pin karo aur soch-samajhkar upgrade karo.

## Jab Terraform aapki zaroorat se zyada hai

- **Ek chhoti single service** aise platform par jo aapke liye infrastructure manage karta hai.
- **Kam samay ka prototype** jise aap agle mahine delete karne waale ho.
- **Aisa client jiski apni infrastructure team aur tool hai** (jaise Bicep, CloudFormation ya Pulumi): unhi ka use karo.

Licence fit bhi check karo. Version 1.6 se aage Terraform Business Source License ke tahat hai, ab IBM licensor hai. Ise apna ya kisi client ka infrastructure chalaane ke liye use karna allowed hai, lekin is par ek competing hosted product banaana allowed nahi hai. OpenTofu, Mozilla Public License 2.0 ke tahat ek open-source fork hai, jise Linux Foundation chalaati hai aur jo 2025 se ek CNCF project hai, aur wahi HCL read karta hai. Kuch clients isi wajah se ise pasand karte hain.

Environment variables, validated settings aur ek secret store sabse chhote project mein bhi rakhne laayak hain.

## Demo se production tak

- **Remote, locked state rakho** har environment ke liye, access restricted karke.
- **Pull requests mein plan karo** aur sirf reviewed plan ko CI se apply karo, OIDC se sign in karke.
- **Approval zaroori karo** kisi bhi production apply se pehle.
- **Nightly drift checks chalao** production par, saath mein Terraform ke bahar bane resources ke liye alerts.
- **Terraform ko scan karo** CI mein risky settings ke liye.
- **Secrets ko state se bahar rakho** managed identity aur write-only arguments se.
- **Start-up par settings validate karo**, secrets ko `SecretStr` rakhkar aur app ki identity se read karke.

## Practice

Apne chune hue cloud ke liye Terraform ke getting-started tutorials follow karo aur config par Twelve-Factor ka page padho.

1. Aisa Terraform likho jo `env = "staging"` ke liye ek storage bucket aur ek chhota managed database banaaye, aur database publicly reachable na ho. Use apply karo, plan padho, phir destroy karo.
2. Apne app ki settings ko environment variables se read hone waale ek validated settings model mein le jaao, model name ka koi default na ho, aur koi value missing ho to start-up saaf taur par fail ho.
3. Apne cloud ke secret manager mein ek secret store karo aur app ko use apni identity se read karwaao. Phir use rotate karo aur confirm karo ki app nayi value utha leta hai.
4. Console mein, Terraform ke manage kiye kisi resource ki ek setting badlo aur drift check chalao: use 2 ke saath exit karna chahiye. Woh change undo karo, phir haath se ek naya firewall rule banao aur phir se chalao: woh 0 ke saath exit karta hai. Import block se us rule ko import karo.

**Aapka kaam poora hai jab aap** apna staging environment code se dobara build kar sako, dikha sako ki aapki repository ya state mein koi secret nahi hai, aur samjha sako ki aapka drift check kya nahi dekh sakta.
