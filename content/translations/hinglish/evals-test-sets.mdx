## Ye kya hai

**Evals** kisi AI application ke repeatable tests hain. Aap app ko asli inputs ke ek fixed **test set** par chalate ho aur har output ko score karte ho, taaki har change (naya prompt, model ya retrieval setting) ko ek number mile jise pichhle number se compare kar sako. Evals ke bina teams prompts feel se badalti hain aur bata nahi paatin ki cheezein behtar hui ya kharab.

```flow
Asli inputs | logs, tickets -> Test set: 60 cases | routine 35, claims 10, complaints 8, must escalate 7
Mushkil cases -> Test set: 60 cases
Purane failures -> Test set: 60 cases
Test set: 60 cases -> App version N -> Outputs -> Scorers | code checks, phir model judge, phir human sample
Scorers -> Version aur category ke hisaab se results -> Tabhi ship karo jab koi category kharab na ho
```

Is lesson mein hum Pune ke ek insurance broker ka policyholder email assistant follow karenge, jahan team is baat par behes kar rahi thi ki kaunsa prompt behtar hai.

## Ye kaam kaise karta hai

**Test set asliyat se banao.** Jahan tak ho sake asli user inputs jama karo (logs, support tickets, sample documents), saath mein woh cases jo aapko pata hai mushkil hain. Shuru mein 30 se 100 cases rakho, jinmein ye cover ho:

- common, roz aane waale cases;
- edge cases (lambe inputs, alag formats, mixed languages);
- woh cases jinhe refuse ya escalate karna chahiye;
- purane failures (har bug ek test case banta hai).

**Har case ke liye tay karo ki "achha" ka matlab kya hai.** Task ke hisaab se:

- ek exact expected value (category, extract kiya hua field, number);
- zaroori facts ya citations jo answer mein hone chahiye;
- woh baatein jo answer ko nahi karni chahiye (refund ka promise, medical advice);
- ek rubric jise insaan ya model judge lagaye (sahi, poora, polite).

**Sabse sasti reliable method se score karo.** Pehle code checks: exact match, JSON validity, required keywords, length limits, sahi citations. Open-ended quality ke liye model judges, jinka agreement human grades se check kiya ho. Ek sample ka human review, khaaskar shuru mein.

**Data ko dekho.** Scorers likhne se pehle 50 se 100 asli outputs padho aur note karo ki woh kaise fail hote hain. Sabse kaam ke evals dekhe gaye failure patterns se bante hain, generic metrics se nahi.

**Har change par chalao aur compare karo.** Versions aur scores ki ek table rakho, case category ke hisaab se. Jo change average badhaye par refusals tod de, woh improvement nahi hai.

**Ise zinda rakho.** Jab users nayi problems dhoondhein toh naye cases jodo; jo cases ab sachchai nahi dikhate unhe hatao; set par itna tune mat karo ki woh users jaisa rahe hi nahi.

**Ek results table jo behes khatam kar de:**

| Version | Judge score | Escalations pakde | Policy number rakha | Approval ka promise kiya |
| --- | --- | --- | --- | --- |
| Purana prompt | 71% | 4 of 7 | 58 of 60 | 0 |
| Naya prompt | 78% | 3 of 7 | 59 of 60 | 0 |
| Escalation rules ke saath | 80% | 7 of 7 | 60 of 60 | 0 |

**Pehle outputs padho.** Ek bhi scorer likhne se pehle app ko 50 se 100 asli inputs par chalao aur har output padho. Har kharab output ke liye chhota note likho: "doosra sawaal ignore kiya", "policy clause khud gadh diya", "complaint ke liye bahut formal tha". Notes ko group karo. Sabse bade groups tumhare pehle evals ban jaate hain, jahan ho sake code checks ki tarah. Is step mein aksar ek dopahar lagti hai aur galat cheez measure karne ke hafte bach jaate hain.

**Ise ek command bana do.** Jo eval koi chalata nahi, woh eval nahi hai. Test set ko repository mein rakho, ek script likho jo har case chalaye aur table print kare, aur har prompt, model ya retrieval change par use CI mein chalao. Har run ke results version ke saath save karo, taaki kisi bhi do runs ko compare kar sako.

**Kitne cases.** Tees achhe se chune cases zyadatar bade regressions pakad lete hain; sau cases category ke hisaab se stable numbers dete hain. Size se zyada coverage matter karti hai: har woh category jo users ke liye zaroori hai, aur critical categories, jaise escalations, mein itne cases ki ek miss dikhe. Saat escalation cases mein ek miss 14 points ki girawat hai jise koi ignore nahi kar sakta. Product ke saath set badhao, aur lagbhag das cases ka ek chhota "smoke" set alag rakho jo kaam karte waqt quick checks ke liye seconds mein chal jaye.

**Sirf end nahi, har step evaluate karo.** Agar app email se details nikalta hai aur phir reply draft karta hai, toh extraction ko alag se bhi test karo. Final score girne par per-step scores batate hain ki kaunsa step toota.

**Ek set nahi, kai chhote sets rakho.** Asli traffic jaisa ek set batata hai ki app overall kaisa hai. Mushkil cases ka ek set, out-of-scope inputs ka ek set jinhe app ko mana karna chahiye, aur typos, mixed languages aur Romanised text waala ek set bhi jodo jo asli users bhejte hain. Jis cheez ki aapko parwah hai, uske liye ek test set do.

**Kya farak asli hai?** 60 cases par 4 points ka gain noise ho sakta hai. OpenAI ka ek mota niyam: ek version ke behtar hone par lagbhag 95% sure hone ke liye 30 points ke farak ke liye takriban 10 cases, 10 points ke liye 100, 3 points ke liye 1,000 aur 1 point ke liye 10,000 chahiye. Har 3 guna chhote farak ke liye lagbhag 10 guna zyada cases. Isliye chhote sets bade regressions pakadne ke liye use karo, aur chhote gains par bharosa karne se pehle bade sets.

**Stability check karne ke liye bootstrap karo.** Apne cases ko replacement ke saath re-sample karo, har re-sample ko score karo, aur dekho score kitna hilta hai. Agar ek re-sample 90% de aur doosra 70%, toh versions compare karne ke liye set bahut chhota hai.

```python
import json, random, statistics
from collections import defaultdict

def run_eval(cases, app, checks):
    """cases: dicts with 'input', 'category' and expectations. checks: functions(case, output) -> bool."""
    rows = []
    for case in cases:
        out = app(case["input"])
        rows.append({"category": case["category"], "passed": all(check(case, out) for check in checks)})
    return rows

def report(rows, bootstraps=1000, seed=7):
    by_cat = defaultdict(list)
    for r in rows:
        by_cat[r["category"]].append(r["passed"])
    for cat, results in sorted(by_cat.items()):
        print(f"{cat:<12} {sum(results)}/{len(results)}")
    rng = random.Random(seed)
    scores = [statistics.mean(rng.choice(rows)["passed"] for _ in rows) for _ in range(bootstraps)]
    scores.sort()
    print(f"overall {statistics.mean(r['passed'] for r in rows):.0%}, "
          f"95% of re-samples between {scores[25]:.0%} and {scores[-26]:.0%}")

# report(run_eval(cases, my_app, [no_dosage_advice, keeps_policy_number, escalates_when_needed]))
```

Agar end mein print hua range chauda hai, toh chhote farak par behes karne se pehle aur cases jama karo.

**Un averages se saavdhaan jo bhatkate hain.** Agar categories ke sizes bahut alag hon, toh version A har category mein version B ko haraye phir bhi overall haar sakta hai. Ise Simpson's paradox kehte hain. Ye ek aur wajah hai ki scores sirf total nahi, category ke hisaab se padho.

**Model judge ko calibrate karna.** Do logon se ek hi rubric par 30 outputs grade karwao, phir judge se grade karwao. Compare karo. Agar agreement kam hai, toh rubric aksar saaf nahi hota: pass aur fail ke examples ke saath use dobara likho aur phir test karo. Judge ka model ya prompt badalne par agreement dobara check karo, aur judge ko temperature 0 par chalao, taaki ek jaise answer ko ek jaisa grade mile. LLM judges aur open-ended answers ko score karne waale lessons aur gehrai mein jaate hain.

## Ek example se samjho

Pune ke ek insurance broker ka assistant policyholder emails ke replies draft karta hai. Team is par behes karti hai ki naya prompt behtar hai ya nahi.

Unhone ek eval banaya:

- 60 asli emails (anonymised): 35 routine sawaal, 10 claims-status queries, 8 complaints, 7 jinhe human chahiye (legal threats, medical details).
- Code checks: agar email mein policy number tha toh reply mein hona chahiye; koi reply claim approval ka promise na kare; saat escalation cases "needs human" mark hon.
- Rubric ke saath ek model judge (policy wording ke hisaab se sahi, har sawaal ka jawab, polite), jise 30 replies par do staff members ke grades se calibrate kiya gaya (85% agreement).

Results: purana prompt judge par 71% laata hai aur 7 mein se 3 escalations miss karta hai; naya prompt 78% laata hai par 4 escalations miss karta hai. Dono manzoor nahi. Teesre version mein explicit escalation rules jode gaye: 80% aur 7 mein se 7 escalations pakde gaye. Table ne behes ek dopahar mein khatam kar di.

**Broker ne kya rakha.** Ab team har kharab reply ki complaint ko uski category ke saath naye case ki tarah jodti hai. Teen mahine baad set 60 se 140 cases tak badh gaya, aur prompts par behes table se, aksar kuch minutes mein, nipat jaati hai.

## Aam galtiyaan

- **Test set hi nahi.** Changes ko do-teen examples se judge karna.
- **Sirf banaye hue test cases.** Asli inputs use karo.
- **Sirf averages.** Categories dekho, khaaskar safety cases.
- **Bina check kiye model judges.** Human grades se compare karo.
- **Jama hua set.** Har naya failure jodo.

## Kab chhota eval kaafi hai

- **Shuruaati prototypes**: haath se padhe hue 20 se 30 cases kisi elaborate pipeline se behtar hain.
- **Bade, saaf changes**, jaise koi naya model jo saaf behtar ya kharab hai, chhote set par bhi dikh jaate hain.
- **Closed tasks**, jaise classification, sirf code se score ho sakte hain, judge ki zaroorat nahi.

## Demo se production tak

- **Ek command, CI mein**: har prompt, model, retrieval ya code change par eval chalao, aur koi critical category kharab ho toh release roko.
- **Results ke saath sab kuch version karo**: test set, rubric, judge prompt aur model, app prompt aur settings, taaki kisi bhi do runs ko compare kar sako.
- **Eval ko hi check karo**: kya ooncha score waisa hi hai jise users aur reviewers behtar bolte hain? Agar do metrics hamesha saath chalte hain, toh ek chhod do; agar kabhi match nahi karte, toh jaanch karo.
- **Kharche ka dhyaan rakho**: kaam karte waqt quick smoke set chalao, aur release se pehle poora set.
- **Production ko wapas andar daalo**: logs, complaints aur online evals ke failures har hafte naye cases ban jaate hain.
