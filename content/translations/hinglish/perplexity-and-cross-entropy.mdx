## Ye kya hai

Language model ka basic kaam agla token predict karna hai. Ye metrics napte hain ki woh kisi text par ye kaam kitna achha karta hai.

**Cross-entropy** woh average "surprise" hai jo model ko har us token par hota hai jo sach mein aage aaya. Agar model ne asli agle token ko 0.9 probability di, toh woh bas zara sa hairaan hua; agar 0.01 di, toh bahut hairaan hua. Surprise ko probability ke negative logarithm se napte hain, isliye pakki predictions ki lagbhag koi cost nahi hoti aur confident galtiyon ki bahut cost hoti hai. Language model train karne ka matlab hai uske training text par uski cross-entropy kam karna; training run mein jo "loss" girta dikhta hai woh yahi number hai.

**Perplexity** cross-entropy ka exponential hai. Ye ek abstract number ko samajhne laayak number bana deti hai: lagbhag, **har step par model kitne equally likely options mein se chun raha hai**. Perplexity 4 ka matlab hai ki model average mein utna hi unsure hai jaise woh chaar equally likely agle tokens mein se pick kar raha ho. Kam behtar hai.

Papers mein do related units dikhti hain. **Bits** log base 2 use karte hain aur **nats** natural logarithm; PyTorch aur TensorFlow nats report karte hain. **Bits per character** aur **bits per byte** total ko tokens ki ginti se nahi balki text ki length se baantte hain, jo models compare karte time bahut matter karta hai, jaisa aap dekhoge.

Ye ideas Claude Shannon ke 1951 ke kaam se aaye hain, English text predict karne par. Jo model text ko achhe se predict karta hai woh use achhe se compress bhi kar sakta hai: 3.4 bits per byte par chalne waala model, principle mein, text ko uske original size ke aadhe se bhi kam mein store kar sakta hai.

```flow
title: Token probabilities se perplexity tak
Text -> Tokenize
Tokenize -> Model har actual agle token ki probability deta hai
Model har actual agle token ki probability deta hai -> Har ek ka minus log lo | per token surprise
Har ek ka minus log lo -> Average lo | cross-entropy
Average lo -> Exponentiate | perplexity
Average lo -> Total ko text ke bytes se baanto | bits per byte, tokenizers ke aar-paar comparable
```

## Ye kaam kaise karta hai

**Compute karna.** Aapko woh probability chahiye jo model ne har actual agle token ko di. Kai APIs ise **logprobs** ki tarah lautati hain; open models mein seedhe milti hain.

```python
import math

def perplexity_from_logprobs(logprobs):
    """logprobs: natural-log probabilities of each actual next token."""
    cross_entropy = -sum(logprobs) / len(logprobs)    # nats per token
    return math.exp(cross_entropy), cross_entropy

def bits_per_byte(logprobs, text):
    total_bits = -sum(logprobs) / math.log(2)         # convert nats to bits
    return total_bits / len(text.encode("utf-8"))

# Example: three tokens predicted with probabilities 0.5, 0.25 and 0.8
lp = [math.log(0.5), math.log(0.25), math.log(0.8)]
print(perplexity_from_logprobs(lp))                   # perplexity about 2.15
```

Hugging Face Transformers mein input ko labels ki tarah pass karne par cross-entropy loss seedhe milta hai, aur `exp(loss)` perplexity hai. Primary resource lambe texts ke liye sliding-window version dikhata hai.

**Value ka matlab text par depend karta hai.**

- **Structured text** (HTML, code, forms) zyada predictable hota hai, isliye perplexity kam hoti hai.
- **Bada vocabulary** har step par zyada options deta hai, isliye perplexity zyada hoti hai.
- **Zyada context** prediction mein madad karta hai, isliye model jitna pichhla text dekhta hai perplexity utni girti hai.
- **Jo text model ne yaad kar liya** uski perplexity asaadhaaran roop se kam hoti hai; **gibberish ya anokhe ideas** ki perplexity bahut zyada hoti hai.

**Comparison ka jaal.** Perplexity per token hoti hai, aur alag models alag tokenizers use karte hain. Jo tokenizer Telugu ko bahut chhote tukdon mein todta hai woh har tukde ko predict karna aasaan bana deta hai, aur model behtar hue bina per-token perplexity kam aati hai. Models ko same text par compare karne ke liye **bits per byte** (ya per character) use karo: total surprise ko text ki apni length se baanto, jo har model ke liye same hai.

**Post-trained models.** Instruction tuning aur preference tuning model ko helpful hona sikhate hain, raw text predict karna nahi. Chat models ki perplexity aksar apne base models se *zyada* hoti hai jabki woh kahin zyada useful hote hain. Quantisation bhi perplexity ko ummeed ke khilaaf badal sakta hai. Isliye perplexity raw text par **base models** compare karne aur training curves ke liye sabse achhi hai, chat assistants ko rank karne ke liye nahi.

**Practical uses.**

- **Apne domain ke liye base model chunna.** Aapke held-out text par kam bits per byte ka matlab continued training ya fine-tuning ke liye behtar starting point.
- **Training ko dekhna.** Validation loss (cross-entropy) learning dikhata hai, aur training loss se gap overfitting ka signal hai.
- **Contamination pakadna.** Benchmark questions par asaadhaaran roop se kam perplexity ka matlab hai ki model ne unhe training mein dekha tha.
- **Data saaf karna.** Bahut zyada perplexity toote extractions, galat bhashaon ya spam ko flag karti hai; bahut kam perplexity un cheezon ke near-duplicates ko flag karti hai jo model pehle se jaanta hai.

| Use | Kya compare karein | Kis baat se savdhaan rahein |
| --- | --- | --- |
| Apne text ke liye base model chunna | Held-out text par bits per byte | Alag tokenizers per-token numbers ko unfair bana dete hain |
| Training monitor karna | Training aur validation loss | Units: zyadatar frameworks mein nats |
| Contamination pakadna | Test items par perplexity vs milte-julte anjaane text par | Kuch text waise hi predict karna aasaan hota hai |
| Training data filter karna | Bahut zyada ya bahut kam perplexity ke outliers | Anokha par valid text bhi zyada score karta hai |
| Chat assistants rank karna | Perplexity use mat karo | Post-training perplexity badha deti hai |

## Ek example se samjho

Hyderabad ki ek legal-tech team ek open model ko Telugu court judgements par aage train karna chahti hai. Unke paas teen candidate base models aur 2,000 held-out judgement paragraphs hain.

| Model | Report hui perplexity (per token) | Poore set ke tokens | Bits per byte |
| --- | --- | --- | --- |
| A | 9 | 2.4 million | 1.77 |
| B | 14 | 1.1 million | 0.97 |
| C | 21 | 1.3 million | 1.33 |

Wo set lagbhag 4.3 million bytes ka text hai. Numbers samjhane ke liye hain. Per-token perplexity par A sabse achha dikhta hai. Par A ka tokenizer Telugu ko B ke tokenizer se do guna se zyada tokens mein todta hai, jisse har token ka guess lagana aasaan ho jaata hai. Jab total surprise ko same bytes ki ginti se baanta jaaye, toh B Telugu legal text ko sabse achhe se model karta hai, aur uska efficient tokenizer training aur use ko bhi sasta banayega.

Woh paragraphs ko perplexity se sort bhi karte hain. Sabse zyada wale 30 garbled scans aur kuch English pages nikalte hain; woh training se pehle extraction theek karte hain. Aakhir mein, commit karne se pehle B ko real tasks (judgements summarise karna, unke baare mein sawaalon ke jawab dena) par test karte hain, kyunki text ko achhe se model karna ek signal hai, task quality ki guarantee nahi.

## Aam galtiyaan

- **Alag tokenizers ke beech per-token perplexity compare karna.** Bits per byte ya per character use karo.
- **Bits aur nats ko mila dena.** 2.0 nats ka loss lagbhag 2.9 bits hai; perplexity dono mein same hai.
- **Chat models ko perplexity se rank karna.** Post-training use aise badalti hai jinka usefulness se koi lena-dena nahi.
- **Kam perplexity ko quality samajhna.** Iska matlab memorisation ho sakta hai, ya bas bahut predictable text.
- **Har model ke liye alag test set use karna.** Bilkul same text par compare karo.
- **Context length ko ignore karna.** Lambe context ke saath score kiye gaye models ki perplexity kam aati hai.

## Jab in metrics ki zaroorat nahi

- **API ke through hosted chat model use karna** kisi application ke liye: use task tests par judge karo, perplexity par nahi.
- **Instruction-tuned assistants compare karna**: apne tasks par evals aur side-by-side comparisons use karo.
- **Classification ke liye chhote fine-tunes**: accuracy, precision aur recall zyada batate hain.

## Demo se production tak

- **Har training run mein validation loss track karo**, ek bataayi hui unit mein.
- **Ek held-out domain set rakho** aur har base model ke liye jise aap consider karte ho bits per byte record karo.
- **Data pipelines mein perplexity filters use karo** toote ya off-language text pakadne ke liye, aur unke flag kiye hue ka ek sample review karo.
- **Jab kisi model ke scores bahut achhe lagein toh naye benchmark results mein contamination check karo.**
