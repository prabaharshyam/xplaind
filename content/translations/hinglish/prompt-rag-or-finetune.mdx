## Ye kya hai

Jab language model woh nahi karta jo aapko chahiye, to use improve karne ke teen main tareeke hain:

- **Better prompting**: clearer instructions, examples, structure aur format.
- **RAG (retrieval-augmented generation)**: aapke documents ya data se relevant information nikaal kar prompt mein daalna.
- **Fine-tuning**: model ko aapke apne examples par aur train karna taaki woh ek behaviour seekh le.

Ye alag-alag problems solve karte hain aur aksar saath mein use hote hain. Achhe se choose karne se mahine bach jaate hain.

```flow
Kya galat hai? -[model ko kuch pata nahi: facts, policies, accounts, haal ki ghatnayein]-> RAG ya tools | re-index karke update; sources cite karo
Kya galat hai? -[use pata hai, par galat tareeke se karta hai: format, tone, steps, edge cases]-> Pehle Prompting | instructions, examples, ek template
Kya galat hai? -[prompting kaam karti hai, par high volume par lambi, mehngi ya inconsistent hai]-> Fine-tune, aksar chhota model | bahut saare achhe examples aur evals chahiye
```

Mature systems teeno ko milaate hain, aur har ek ko usi test set par check kiya jaata hai.

Is lesson mein hum Pune ki ek software company ki teen problems dekhenge, jinmein har ek ko alag fix chahiye tha.

## Ye kaam kaise karta hai

**Pehle problem diagnose karo.**

- *Model ko kuch nahi pata* (aapke products, policies, haal ki ghatnayein, kisi customer ka account): ye knowledge problem hai. **RAG** ya tools use karo. Facts add karne ke liye fine-tuning kharab tareeka hai: update karna mehnga hai aur model phir bhi galat yaad rakh sakta hai.
- *Model ko kaafi pata hai par woh task galat tareeke se karta hai* (format, tone, steps, edge cases): pehle **prompting** try karo: instructions, examples, clearer format.
- *Prompting kaam karti hai par narrow, high-volume task ke liye lambi, mehngi, slow ya phir bhi inconsistent hai*: bahut saare achhe examples par kisi model, aksar chhote model, ko **fine-tune** karne ka socho.

**Pehle prompting kyun.** Ye fast, sasta aur reversible hai: aap kisi change ko minutes mein test kar sakte ho. "Model" ko jis problem ka dosh diya jaata hai, unme se bahut saari clearer instructions aur do achhe examples se gayab ho jaati hain.

**RAG kab fit hota hai.** Jab information aksar badalti ho (har hafte update hone waala handbook), badi ho (hazaaron documents), private ho, ya cite karni ho. Update ka matlab re-index karna hai, retrain karna nahi.

**Fine-tuning kab fit hoti hai.**

- bahut saari requests par consistent style ya format;
- bahut saare labelled examples waala narrow classification ya extraction task;
- chhote, sasta model ko ek task par bade model ke barabar banana;
- un prompts ko chhota karna jinme bahut saare examples hain.

Ise sau se hazaaron quality examples, evaluation, aur base model badalne par dobara karna chahiye.

**Milao.** Ek common mature setup: achhe se design kiya prompt, knowledge ke liye RAG, aur ho sake to ek high-volume step ke liye fine-tuned chhota model. Har change ko usi test set par evaluate karo.

**Approaches ki tulna:**

| Factor | Prompting | RAG | Fine-tuning |
| --- | --- | --- | --- |
| Kya theek karta hai | Behaviour, format | Missing ya badalti knowledge | Scale par consistent behaviour |
| Try karne ka time | Minutes | Din | Hafte |
| Data chahiye | Kuch examples | Aapke documents | Sau se hazaaron labelled examples |
| Update karna | Prompt edit karo | Re-index | Retrain |
| Per request cost | Prompt ki length ke saath badhti hai | Retrieval aur context jodta hai | Chhote model ke saath sabse kam ho sakti hai |
| Citations | Nahi | Haan | Nahi |

**Andaza lagana ki fine-tuning kab paisa vasool hai.** Maujooda approach ka monthly cost fine-tuned option se compare karo: training cost ko uski useful life par failaao, plus aapke volume par serving cost, plus training data banane aur maintain karne ka time. Fine-tuning aam taur par high-volume, narrow tasks mein paisa vasool hoti hai jahan chhota model bade ki jagah le sake, aur low-volume ya tezi se badalne waale tasks mein kam hi. Calculation likh kar rakho, us volume ke saath jis par break even hota hai.

**Pehle prompt fixes test karna.** Kisi bhi bade change se pehle ek dopahar prompt par lagao: task aur format saaf likho, ek edge case sahit do-teen achhe examples jodo, aur test set chalao. Teams aksar hairaan hoti hain ki kitni problems isi se solve ho jaati hain, aur ye RAG ya fine-tuning ko judge karne ke liye ek fair baseline bhi deta hai.

**Saare candidates ko ek test set par chalao.** Sabse fair comparison wahi sawaal, wahi graders aur wahi cost aur latency measurements use karta hai:

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.2f}{p95:>8.0f}")
    return rows
```

Test set ko problem type ke hisaab se baanto: jinhe private ya haal ke facts chahiye woh sawaal, aur format ya behaviour waale sawaal. Pehle group mein RAG ko jeetna chahiye aur doosre mein fine-tuning jeet sakti hai; agar aisa nahi hai, to aapka diagnosis galat tha.

**Fine-tuning kab paisa vasool hoti hai, numbers mein.**

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.40, 0.06, build_cost_inr=600_000, upkeep_per_month_inr=50_000))
```

`build_cost_inr` mein data collect aur check karne aur evals chalane waale logon ka time bhi shaamil hona chahiye, sirf GPU hours nahi. Chhota `life_months` realistic hai: naya base model aksar kuch mahino mein aa jaata hai aur kaam dobara karna padta hai.

**Facts retrieval mein rakho.** Naye knowledge ke liye dono ko compare karne waali studies mein retrieval aam taur par jeeti, aur jo facts base model ne kabhi dekhe hi nahi unpar fine-tune karna confident galtiyon ko bhi badhava de sakta hai. Form (format, tone, narrow classification) sikhane ke liye fine-tuning aur facts dene ke liye retrieval use karo.

**Koshishon ka order.** Prompt, phir prompt ke saath retrieval ya tools, phir fine-tuning sirf tab jab koi measured gap bacha ho aur upar ke numbers sense banate ho. Har step pichhle ko baseline ki tarah rakhta hai.

## Ek worked example

Pune ki ek software company ki teen problems:

1. *Support bot ko ek product handbook se jawab dene hain jo har hafte badalta hai.* Badalti knowledge: handbook par **RAG**, har update par re-index. Fine-tuning ek hafte mein outdated ho jaati.
2. *Ticket summaries ka format alag-alag hai aur customer ki priority chhoot jaati hai.* Model ke paas information hai; instruction saaf nahi hai. **Prompting**: ek fixed template, priority ka ek rule aur do examples ek dopahar mein 90% cases theek kar dete hain.
3. *Mahine ki 2 million log lines ko bade model se 30 categories mein classify karna bahut mehnga hai.* Unke paas pichhle kaam se 50,000 labelled lines hain. Ek chhote model ko **fine-tune** karo: unke test set par woh bade model ki accuracy ke barabar hai, cost aur latency ke ek chhote hisse par.

| Problem | Diagnosis | Approach | Result |
| --- | --- | --- | --- |
| Support bot aur har hafte badalta handbook | Knowledge | RAG, har update par re-index | Hamesha current |
| Ticket summaries alag-alag aur priority miss | Behaviour | Template, priority rule, do examples | Ek dopahar mein 90% theek |
| Mahine ki 2 million log lines, bahut mehnga | Narrow task par volume | 50,000 labels par fine-tuned chhota model | Wahi accuracy, cost aur latency bahut kam |

## Common galtiyan

- **Facts add karne ke liye fine-tune karna.** Retrieval use karo.
- **Prompting skip karna.** Ye sabse sasta fix hai aur aksar kaafi hota hai.
- **Fashion ke hisaab se choose karna.** Knowledge versus behaviour diagnose karo.
- **Evaluation set na hona.** Uske bina approaches compare nahi kar sakte.
- **Maintenance bhoolna.** Fine-tuned models ko retrain karna padta hai; RAG ko fresh indexes chahiye.
- **Approaches ko alag test sets par** ya alag graders ke saath compare karna.
- **Logon ka time chhod dena** fine-tuning cost se.
- **Badalte facts add karne ke liye fine-tune karna**, jise retrieval behtar sambhaalta hai.

## Jab choice pehle se clear ho

- **Jawab ko private documents cite karne hain**: retrieval, aur jo bhi jodo.
- **Low volume**: fine-tuning shaayad hi paisa wapas deti hai; prompt improve karo.
- **Task har kuch hafte mein badalta hai**: prompts aur retrieval retraining se tez adapt hote hain.
- **Aapke paas labelled examples nahi hain**: fine-tuning abhi possible nahi hai; reviewed outputs se unhe collect karna shuru karo.

## Demo se production tak

- **Ek test set rakho**, problem type ke hisaab se baanta hua, aur har approach ke liye use karo.
- **Har option ki quality, cost aur p95 latency** dates ke saath record karo.
- **Prices, volumes ya models badalne par break-even** dobara calculate karo.
- **Reviewed outputs ko** future training data ki tarah collect karo, chahe abhi fine-tune na karo.
- **Fine-tuned models ko** naye base models ke saath achhe prompts ke against dobara test karo, jab woh aayein.
