## Ye kya hai

Jab ek language model woh nahi karta jo aapko chahiye, to fix is par nirbhar karta hai ki asal mein galat kya hai. Problems do tarah ki hoti hain, aur paanch mukhya tools hote hain.

**Model ke paas knowledge nahi hai** (aapki policies, kisi customer ka account, is hafte ke prices). Knowledge ko query ke time, prompt mein laao:

- **Long context**: poore documents prompt mein daalo. **Prompt caching** mein provider prompt ki bina badli shuruaat ko store kar leta hai, taaki dobara aane waali calls use saste mein padhein.
- **RAG (retrieval-augmented generation)**: apne documents mein search karo aur sirf kuch sabse achhe passages prompt mein daalo.
- **Tools aur agentic search**: model ko ek database, ek API ya ek search tool call karne do, result padhne do aur zaroorat ho to phir se search karne do.

**Model ko kaafi pata hai par woh galat behave karta hai** (format, tone, steps, edge cases):

- **Prompting**: saaf instructions, examples, aur API ka **structured output**, jismein aap ek JSON schema dete ho aur reply ko usse match karna hota hai.
- **Fine-tuning**: model ko aapke examples par aage train karo taaki behaviour andar hi built-in ho jaaye. Ye model ke weights badalta hai, isliye ye sabse dheema aur sabse kam reversible fix hai.

Chhota rule: knowledge context mein jaati hai; behaviour pehle prompt mein aur sabse aakhir mein weights mein.

```flow
title: Chunne se pehle diagnose karo
Kya galat hai? -[use kuch pata nahi hai]-> Knowledge ko query ke time laao
Kya galat hai? -[use pata hai, par galat karta hai]-> Prompting aur structured output
Knowledge ko query ke time laao -[chhota, stable, aksar poochha jaata hai]-> Caching ke saath long context
Knowledge ko query ke time laao -[bada, badalta hua ya har user ka alag]-> RAG
Knowledge ko query ke time laao -[live records ya kai lookups]-> Tools ya agentic search
Prompting aur structured output -[high volume par ab bhi mehenga ya inconsistent]-> Fine-tune, aksar ek chhota model
```

Mature systems inhein milaakar use karte hain, aur har option ek hi test set par maapa jaata hai. Ye lesson Pune ki ek software company ki teen problems ko follow karta hai, jinmein se har ek ko alag fix chahiye tha.

## Ye kaise kaam karta hai

### Step 1: knowledge hai ya behaviour, ye diagnose karo

Kuch bhi chunne se pehle 20 se 30 fail hue outputs padho. Har ek ke liye poochho: kya zaroori fact prompt mein tha? Agar nahi, to ye knowledge problem hai, aur style par kitni bhi instruction ya training ise theek nahi karegi. Agar fact tha aur phir bhi jawaab galat aaya, galat format mein ya galat tone mein, to ye behaviour problem hai. Kai teams ye step chhod deti hain aur model ko fine-tune kar deti hain taaki woh theek ho jo asal mein missing context tha.

### Step 2: behaviour ko pehle prompt se theek karo

Prompting fast, sasta aur reversible hai: aap ek badlaav ko minutes mein test kar sakte ho. Kisi bhi badi cheez se pehle ek dopahar lagao. Task aur output format seedhe-seedhe batao, ek edge case samet do-teen achhe examples jodo, aur apna test set chalao. Isse woh fair baseline bhi set hota hai jise har baad waale option ko harana hai.

**Format** problems ke liye API ka structured output use karo: aap ek JSON schema dete ho aur provider model ko sirf wahi replies banane deta hai jo usmein fit hon. Tab shape guaranteed hota hai, par values phir bhi galat ho sakti hain, isliye unhein code mein validate karo. Structured output waala lesson ise cover karta hai. Sirf valid JSON paane ke liye fine-tune karna 2026 mein aamtaur par galti hai.

### Step 3: knowledge ko sabse saste bharosemand tareeke se laao

Teenon options query ke time facts ko model ke saamne rakhte hain. Update karne ka matlab hai ek document ya ek database row badalna, retrain karna nahi.

**Caching ke saath long context.** November 2026 tak, Anthropic ke latest Claude models 1 million tokens ka input lete hain. Caching cost ko bahut badal deti hai. Claude Sonnet 5.5 ke Anthropic list prices, 28 November 2026 ko check kiye gaye: input $2 per million tokens, cache read $0.10 (input ka 5%), 5-minute cache write $2.50, output $10. To Sonnet 5.5 par ek cached corpus har sawaal par RAG prompt se kam padta hai, jab tak corpus RAG context ke lagbhag 20 guna se kam ho. Cache se padhi gayi ek 60,000-token handbook utni hi padti hai jitne 3,000 fresh tokens. Doosre models aur providers caching ko alag tarah price karte hain (Claude Haiku 5.5 par ek cache read input ka 10% hai), isliye apne waale ke liye hisaab dobara lagao.

Dikkatein: default roop se cache 5 minutes tak use na ho to expire ho jaata hai, isliye ye steady traffic ke saath hi faayda deta hai; prompt ki shuruaat mein koi bhi badlaav ise tod deta hai; bahut lambe inputs mein accuracy girti hai ("lost in the middle" effect); aur lambe inputs pehle token ko dheema kar dete hain. "Long context or RAG" lesson inhein gehraai se cover karta hai.

**RAG.** Ise tab use karo jab corpus bada ho (har call par jitna pay karna chahoge usse kahin zyada), aksar badalta ho, use har user ki permissions ka dhyaan rakhna ho, ya answers ko kisi passage ko cite karna ho. Iske liye chunking, indexing aur tuning chahiye, aur search jo miss karta hai woh ye bhi miss karta hai.

**Tools aur agentic search.** Live, structured data ke liye (ek fixed-deposit rate, ek order status, ek balance), system of record ko ek tool se query karo. Documents par RAG purana figure de sakta hai; database query nahi degi. Agentic search, jismein model step by step khud search karta hai, un sawaalon mein fit hota hai jahan agla lookup pichhle par nirbhar karta hai. Iski cost zyada hai: har step badhti hui conversation ko dobara bhejta hai. Jaise, 2,000 tokens ke instructions mein har baar 3,000 tokens ke results jodne waale chhah steps kul 57,000 input tokens bhejte hain, jabki ek RAG call mein lagbhag 4,000.

### Step 4: fine-tune sirf form ke liye, volume par karo

Fine-tuning us narrow task mein fit hoti hai jismein bahut saare achhe examples hon aur jahan prompting kaam karta hai par high volume par bahut lamba, bahut mehenga, bahut dheema ya phir bhi inconsistent hai: 30 labels waala classification, millions of replies mein ek house style, ek chhota model jise ek bade model jaisa banna hai.

**Facts retrieval mein rehne chahiye.** Do EMNLP 2024 papers ko naam se jaanna faaydemand hai. Ovadia aur saathiyon ("Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs") ne paaya ki jaani-pehchaani aur poori tarah nayi, dono tarah ki knowledge ke liye RAG unsupervised fine-tuning se behtar raha. Gekhman aur saathiyon ("Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?") ne supervised closed-book question answering mein paaya ki naye facts waale examples dheere-dheere seekhe jaate hain aur, seekhne ke baad, hallucination badhaate hain. Models zyaadatar facts pre-training se paate hain; fine-tuning unhein sikhaati hai ki jo pata hai use kaise use karein.

"Fine-tuning" mein kai methods aate hain jinki data zarooratein alag hain:

| Method | Training data | Aam use |
| --- | --- | --- |
| Supervised fine-tuning (SFT) | Ideal outputs ke saath jode gaye inputs | Format, style, classification, extraction |
| Preference tuning, jaise DPO | Ek behtar aur ek badtar answer ke jode | Tone, helpfulness, kise mana karna hai |
| Reinforcement fine-tuning | Prompts aur answers ko score dene waala ek grader | Check hone laayak answers, kam labels waale tasks |
| Distillation | Ek bade model ke outputs, SFT data ke roop mein | Ek task par bade model ki nakal karta ek chhota, sasta model |

Zyaadatar teams LoRA use karti hain, jo model ke saare weights ki jagah ek chhota add-on train karta hai; fine-tuning kaise kaam karti hai aur practice mein fine-tuning waale lessons in methods ko cover karte hain. Kisi bhi plan se pehle do practical checks aate hain. Pehla, availability: har model fine-tuning offer nahi karta, aur offer badalta rehta hai. OpenAI ne 8 May 2026 ki taareekh waala ek update post kiya ki woh apna fine-tuning platform dheere-dheere band kar raha hai, jo ab naye users ke liye accessible nahi hai. Apne provider ka documentation check karo aur taareekh likh lo. Open-weight models jinhein aap khud train aur host karte ho, is risk se bachte hain par unke liye GPUs aur skills chahiye. Doosra, distillation ke liye terms of use padho: kai providers apne outputs se competing models train karne se mana karte hain.

### Har option ko ek hi test set par maapo

Har candidate ke liye wahi sawaal, graders, aur cost aur latency measurements use karo. Test set ko problem type ke hisaab se baanto: woh sawaal jinhein private ya recent facts chahiye, aur format ya behaviour waale sawaal. Pehle group mein knowledge options ko jeetna chahiye; agar nahi jeette, to aapka diagnosis galat tha.

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.3f}{p95:>8.0f}")
    return rows
```

### Fine-tuning ko sabse achhe saste baseline ke saamne price karo

Monthly bachat ki tulna ek chhoti useful life par build cost se karo. Build cost ka matlab hai data ikattha aur check karne aur evals chalaane mein laga logon ka time, sirf GPU hours nahi. Chhoti life realistic hai, kyunki ek behtar base model aksar kuch hi mahinon mein aa jaata hai aur kaam dobara karna padta hai.

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.414, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
print(finetune_break_even(2_000_000, 0.056, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
```

Neeche ka worked example inputs samjhaata hai. Pehli line fine-tuning ko ek uncached bade model ke saamne price karti hai: har mahine ₹7.68 lakh ki bachat aur 0.5 mahine mein break-even. Doosri use usi model ke saamne price karti hai jismein prompt cached hai: har mahine ₹52,000 ki bachat, break-even mein 7.7 mahine aur chhah mahinon mein ₹88,000 ka net loss. Fine-tune wahi, jawaab ulta. Hamesha us sabse saste option ke saamne price karo jo pehle se kaam karta hai.

## Ek worked example

Pune ki ek software company ki teen problems. Saari costs udaaharan ke liye hain: ye 28 November 2026 ko check kiye gaye Claude Sonnet 5.5 aur Haiku 5.5 ke list prices, udaaharan ke liye ₹94 prati dollar ka rate, aur low effort par maane gaye token counts use karti hain, isliye thinking tokens lagbhag nahi hain. Real responses mein `usage` check karo, kyunki thinking ka bill output ke roop mein banta hai. Accuracy figures us tarah ke hain jo ek team record karegi, maape gaye results nahi.

**1. Support bot aur har hafte badalne waali chhah handbooks.** Company chhah products bechti hai, har customer sirf apne product ki handbook dekh sakta hai, aur har handbook lagbhag 400,000 tokens ki hai. Cached long context, ek hi product ki handbook ke liye bhi, har sawaal par lagbhag ₹4.10 padega (cache-read price par 400,000 tokens, saath mein ek 300-token sawaal aur ek 300-token jawaab). Lagbhag 4,000 tokens ke passages waala RAG lagbhag ₹1.09 padta hai. RAG ek metadata filter se har customer ki permissions bhi laagu karta hai aur use kiye gaye section ko cite karta hai. To woh **RAG** chunte hain, har update par re-index karke.

Crossover maayne rakhta hai. Agar ek hi 60,000-token handbook hoti jiske baare mein din bhar poochha jaata, to cached long context har sawaal par ₹1.09 ke muqaable lagbhag ₹0.90 padta, use index nahi chahiye hota, aur woh har section ek saath dekhta. Ise cross-section sawaalon par test karo, ho sakta hai ye behtar choice ho.

**2. Ticket summaries alag-alag hoti hain aur customer ki priority chhod deti hain.** Model ke paas ticket hai; instruction saaf nahi hai. **Prompting aur structured output**: ek schema jismein zaroori `priority` field chaar values tak seemit ho, priority kaise judge karein is par ek rule, aur do examples. Maan lo ki 50 test tickets par sahi priority 31 se 46 ho jaati hai aur format phir kabhi nahi tootta. Ismein ek dopahar lagi.

**3. Har mahine 20 lakh log lines ko 30 categories mein classify karna.** Aaj woh Sonnet 5.5 ko ek 2,000-token prompt (category definitions aur examples) ke saath call karte hain jo har baar fresh bheja jaata hai, saath mein lagbhag 100 tokens ki log line aur 20 tokens ka output. Ye har line par lagbhag ₹0.41, ya har mahine ₹8.3 lakh hai. Unke paas 50,000 labelled lines hain, aur ek vendor ek chhote open-weight model ko fine-tune karne ka offer deta hai: maan lo build karne mein ₹4 lakh, maintain karne mein har mahine ₹40,000, aur serve karne mein har line par ₹0.01.

Aaj ke bill ke saamne fine-tuning do hafton mein paisa vasool kar deti hai. Par pehle woh prompt ko cache karte hain. Lagbhag 46 lines per minute par cache kabhi cold nahi hota, aur 2,000-token prompt 512-token minimum se upar hai. Accuracy mein bina kisi badlaav ke cost girkar har line par lagbhag ₹0.056 (har mahine ₹1.13 lakh) ho jaati hai. Us baseline ke saamne wahi fine-tune paisa vasool karne mein 7.7 mahine leta hai. Woh usi cached prompt ke saath Haiku 5.5 bhi try karte hain: har line par lagbhag ₹0.004, har mahine ₹7,500, par maan lo accuracy 96% se girkar 91% ho jaati hai. Lines urgent nahi hain, isliye batch API, jo November 2026 tak Anthropic par aadhi keemat par hai, dono mein se kisi bhi bill ko aur kam kar dega.

Volume faisla karta hai. Chhah mahine ki life par, upar ke inputs cached baseline ke saamne lagbhag 23 lakh lines per month ka break-even volume dete hain. Do naye clients agle quarter mein volume ko 1 crore lines per month tak le jaayenge. Maan lo 10,000 labels par ek pilot fine-tune test set par 96% score karta hai, Sonnet jitna. 1 crore lines par fine-tune har mahine lagbhag ₹4.2 lakh bachaata hai aur lagbhag ek mahine mein paisa vasool kar deta hai. Haiku aur bhi sasta hoga, par uske 5-point gap ka matlab hai har mahine lagbhag 5 lakh zyada galat tags. To woh **aaj prompt cache karte hain aur bade volume ke liye fine-tune karte hain**, cached prompt ko fallback aur baseline ke roop mein rakhte hue.

| Problem | Diagnosis | Approach | Udaaharan ke liye result |
| --- | --- | --- | --- |
| Chhah handbooks, har ek 400,000 tokens ki, har customer ka alag access | Knowledge, badi aur permission waali | Filters ke saath RAG, har hafte re-index | Cached long context ke ₹4.10 ke muqaable har sawaal par ₹1.09 |
| Summaries priority chhod deti hain | Behaviour | Schema, ek priority rule, do examples | 50 mein se 46 par priority sahi, 31 se upar |
| Har mahine 20 lakh log lines, 1 crore tak badhti hui | Volume par form | Abhi cache, bade volume ke liye ek chhote model ko fine-tune | Abhi har mahine ₹8.3 lakh se ₹1.13 lakh; 1 crore par fine-tune ek mahine mein paisa vasool |

## Aam galtiyan

- **Facts jodne ke liye fine-tuning.** Facts context mein rehne chahiye, long context, RAG ya ek tool ke zariye.
- **Prompt ko chhod dena.** Ye sabse sasta fix hai, aksar kaafi hota hai, aur woh baseline hai jise baaki sabko harana hai.
- **JSON format ke liye fine-tuning** structured output try karne se pehle.
- **Ek chhote, stable document ke liye RAG banana** jise cached long context zyada aasaani se sambhaal leta.
- **Rates ya balances jaise live numbers ke liye documents par RAG use karna**, ek tool ki jagah.
- **Fine-tuning ko uncached bill ke saamne price karna.** Pehle prompt cache karo aur ek chhota model try karo, phir compare karo.
- **Build cost mein logon ka time chhod dena**, ya ek lambi useful life maan lena.
- **Options ko alag-alag test sets par** ya alag graders ke saath compare karna.
- **Kisi fine-tuning service ke bharose plan karna** bina check kiye ki woh aaj aapke model ke liye maujood hai.

## Jab chunaav pehle se saaf ho

- **Jawaab ko private documents cite karne hain**: retrieval, aap saath mein aur jo bhi jodo.
- **Data ek database mein rehta hai**: ek tool, documents ka index nahi.
- **Low volume**: fine-tuning shaayad hi kabhi paisa vasool karti hai; prompt improve karo.
- **Task har kuch hafton mein badalta hai**: prompts aur retrieval retraining se tezi se adapt hote hain.
- **Aapke paas labelled examples nahi hain**: fine-tuning abhi possible nahi hai; reviewed outputs se unhein ikattha karna shuru karo.

## Demo se production tak

- **Ek test set rakho** jo problem type ke hisaab se banta ho, aur har approach ke liye use use karo.
- **Har option ke liye quality, cost aur p95 latency record karo**, taareekhon ke saath.
- **Agar caching par nirbhar ho to cache hit rate par nazar rakho**; ek chupchaap giraavat bill ko kai guna kar sakti hai.
- **Break-even dobara nikaalo** jab prices, volumes ya models badlein.
- **Reviewed outputs ikattha karo** future training data ke roop mein, bhale abhi fine-tune na kar rahe ho.
- **Fine-tuned models ko har naye base model ke saamne dobara test karo**, ek achhe, cached prompt ke saath.

## Practice karo

Neeche linked, production ke liye LLM applications banane par Chip Huyen ka article padho.

1. Teen problems jinhein aap jaante ho, har ek ke 20 fail hue outputs padho aur batao ki problem knowledge ki hai ya behaviour ki.
2. Ek knowledge problem ke liye, apne provider ke current prices se har sawaal par cached long context ko RAG ke saamne price karo, aur unke saath check ki taareekh likho.
3. Ek behaviour problem ke liye, do prompt improvements aur structured output try karo, aur unhein ek chhote test set par `compare` se maapo.
4. `finetune_break_even` do baar chalao: apne current bill ke saamne aur apne sabse saste working baseline ke saamne. Woh volume dhoondho jis par fine-tuning paisa vasool karne lagti hai.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly, 2025) ka chapter 7 cover karta hai ki kab fine-tune karein, aur knowledge aur form ke liye fine-tuning ki tulna RAG se kaisi hai.

**Aapka kaam poora hai jab aap** ek teammate ko samjha sako ki har hafte badalne waali handbook ko fine-tuning ki jagah retrieval kyun chahiye, cached long context RAG se kab behtar hai, aur fine-tuning ko sabse saste working baseline ke saamne kyun price karna chahiye.
