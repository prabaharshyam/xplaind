## Ye kya hai

Bharat ke bahut saare businesses aaj bhi aise software par chalte hain jo kisi aur cheez se baat hi nahi kar sakta: 15 saal puraana koi desktop ERP, kisi bank ki back-office screens, bina API waala koi government portal. Log poora din ek screen se doosri screen mein values copy karte rehte hain. **Robotic process automation (RPA)** ye copy waala kaam apne haath mein le leta hai.

RPA software "robots" use karta hai jo applications ko unke **user interface** se chalaate hain, jaise koi insaan chalaaye: programs kholna, buttons click karna, fields mein type karna, screens se values padhna aur reports download karna. Ye un systems ka tool hai jinmein API nahi hai, ya jahaan integration banaane mein bahut zyada time lagega.

Asli baat ye hai: API software ke liye bana darwaaza hai, jabki RPA mein software us darwaaze se chalta hai jo insaanon ke liye bana tha. Wo darwaaza kabhi robots ke liye design hi nahi hua. Kisi button ka naam badal gaya, koi screen slow hai ya achaanak koi pop-up aa gaya, to robot ruk sakta hai. Isliye RPA powerful hai par naazuk bhi, aur zyaadatar skill isi naazukpan ko sambhaalne mein hai.

```flow
dir: LR
title: API automation: tez, mazboot, pehli pasand
System A, API hai -[data, seedhe]-> System B, API hai
```

```flow
dir: LR
title: RPA: jahaan insaan kaam kar sake wahaan chalta hai, par zyada naazuk
Robot | UiPath, Power Automate Desktop -[screen par clicks aur typing]-> Puraana desktop app, API nahi
```

Bade RPA tools mein **UiPath**, **Automation Anywhere** aur **Microsoft Power Automate Desktop** hain. Steps ek studio app mein design karte ho, phir unhein schedule par ya zaroorat padne par, desktop ya server par chalaate ho. Power Automate for desktop Windows 11 ke saath bina extra cost ke aata hai, isliye practice ke liye ye aasaan jagah hai, haalaanki flows ko unattended chalaane ya cloud se trigger karne ke liye paid licence chahiye.

Ye lesson Kolkata ke ek general insurer ki claims team ke saath chalta hai, jahaan ek puraane claims system mein data entry ka kaam ek AI step aur ek RPA robot sambhaal lete hain. Aakhir tak aapko pata hoga ki RPA kab sahi tool hai, aisa robot kaise banaayein jo duplicates na banaaye ya chupchaap fail na ho, aur kaise check karein ki wo apna kharcha nikaalta hai ya nahi.

## Ye kaam kaise karta hai

### Attended aur unattended robots

| Type | Kahaan aur kab chalta hai | Example |
| --- | --- | --- |
| **Attended** | Kisi insaan ke computer par, jab wo insaan use start kare | Ek robot jo agent ke "Go" click karte hi 40 fields waala form bhar deta hai |
| **Unattended** | Apne aap, alag machines par, queue se items lekar | Ek robot jo raat bhar mein 300 claims daal deta hai |

Attended robots ek insaan ko tez kaam karne mein madad karte hain; har run par koi insaan nazar rakhta hai. Unattended robots poori ek shift ka kaam sambhaal lete hain, aur unhein koi nahi dekhta. Neeche diya har design rule sabse zyada unattended robots ke liye maayne rakhta hai.

### Production model: queue, orchestrator, robot

Demo robot spreadsheet ki rows par loop chalaata hai. Production robot ek **queue** se kaam karta hai. Har kaam, jaise ek claim email, ek **queue item** ban jaata hai jismein uska data aur ek status hota hai, jaise new, in progress, successful ya failed. Ek **orchestrator**, yaani RPA platform ka control centre (UiPath ise Orchestrator kehta hai), queues rakhta hai, schedules par robots start karta hai, credentials store karta hai aur logs rakhta hai.

Queues teen aisi cheezein deti hain jo spreadsheet loop nahi deta. Kai robots kaam baant sakte hain. Crash hone par sirf wo item jaata hai jo chal raha tha, poora batch nahi. Aur business ek nazar mein dekh sakta hai ki kitne items intezaar mein hain, ho gaye ya atke hain.

### Business aur system exceptions

Cheezein do bilkul alag tareekon se gadbad hoti hain, aur robot ko inhein alag pehchaanna aana chahiye.

| | Business exception | System exception |
| --- | --- | --- |
| **Kya hua** | Data kisi rule ko todta hai: policy expire ho gayi, GSTIN match nahi hua, koi zaroori field khaali hai | Kuch technical fail hua: app crash hua, screen time out hui, network chala gaya |
| **Kya retry se madad milegi?** | Nahi. Agli baar bhi data utna hi galat hoga | Aksar haan. Wahi item doosri koshish mein aksar chal jaata hai |
| **Kya karein** | Item ko failed mark karo aur wajah ke saath kisi insaan ko bhejo | App band karke restart karo, phir retry, kisi limit tak, jaise teen baar |

Classic galti hai sab kuch retry karna. Business exception ko teen baar retry kiya to teen runs barbaad, aur aakhir mein phir bhi insaan ke paas jaayega. System exception ko seedhe insaan ke paas bheja to wo manual kaam ban gaya jo ek restart se nipat jaata. UiPath ke REFramework jaise templates mein ye bantwaara pehle se bana hota hai. Tools ki exact retry settings alag-alag hoti hain, isliye apne version ki documentation check karo.

### Retries aur duplicates: idempotency

RPA ki sabse khatarnaak failure retries se hi aati hai. Socho: robot ek claim type karta hai, Save click karta hai, aur puraana app do minute ke liye freeze ho jaata hai. Robot time out hokar system exception report karta hai. Queue us item ko retry karti hai. Lekin pehla Save asal mein ho chuka tha. Retry claim ko doosri baar daal deta hai, aur ab insurer ke paas ek accident ke do claims hain.

Iska fix hai **idempotency**: kisi item ko do baar chalaane par wahi result aana chahiye jo ek baar chalaane par aata hai. Practice mein:

1. **Aisi unique key chuno jise puraana system search kar sake**, jaise policy number plus date of loss.
2. **Banaane se pehle search karo.** Har item ki shuruaat mein target system mein wo key dhoondho. Agar record pehle se hai, to uska reference uthaao aur agle step par jaao.
3. **Item ko successful bilkul aakhir mein hi mark karo**, jab naya reference tracking sheet mein waapas likh diya jaaye; Save click karte hi kabhi nahi.

```flow
title: Ek idempotent queue item
Queue ka agla item lo -> Claims system mein pehle se hai?
Claims system mein pehle se hai? -[haan]-> Maujooda claim number padho
Claims system mein pehle se hai? -[nahi]-> Form bharo aur save karo | phir naya claim number padho
Maujooda claim number padho -> Claim number tracking sheet mein likho
Form bharo aur save karo -> Claim number tracking sheet mein likho
Claim number tracking sheet mein likho -> Item ko successful mark karo
```

Kuch orchestrators ek hi reference waala doosra queue item lene se mana bhi kar sakte hain. Isse duplicate kaam queue mein aane se rukta hai, par retry ko target app mein do baar save karne se nahi rokta. Wo sirf search-before-create step rokta hai.

### Robots screen par cheezein kaise dhoondhte hain: selectors

Achha RPA fixed screen positions par click nahi karta. Wo har element ko uski properties se dhoondhta hai: window ka title, field ka label, uska type. Is description ko **selector** kehte hain. Ek hi Policy number box ke liye do simplified selectors, UiPath waale style mein:

```text
Brittle:  <wnd app='claims.exe' title='Claims v4.2 - User RKUMAR' />
          <ctrl automationid='txt_4471' idx='7' />

Robust:   <wnd app='claims.exe' title='Claims*' />
          <ctrl name='Policy No*' role='editable text' />
```

Brittle waala teen wajahon se toot-ta hai. Window title mein version number aur user name hai, jo badalte hain. Id `txt_4471` app khud generate karta hai aur agle build mein badal sakta hai. Aur `idx='7'` box ko milte-julte boxes mein uske kram se chunta hai: uske upar ek field jodo aur robot galat box mein type kar dega. UiPath ki apni guidance hai ki jahaan baaki attributes kaam kar dein, wahaan `idx` se bacho. Robust waala wo cheezein use karta hai jinhein insaan pehchaan le: app, window title ki shuruaat aur field ka label. `*` ek **wildcard** hai jo koi bhi characters match karta hai, isliye "Claims v4.3" bhi match ho jaata hai. `?` theek ek character match karta hai.

Do aadatein selectors ko tikaau banaati hain. Position ki jagah label ko tarjeeh do. Aur type karne ke baad, aage badhne se pehle value waapas padho, ya check karo ki agli expected screen aayi ya nahi.

### Remote desktops aur Citrix

Kuch organisations puraane apps ko **Citrix** ya remote desktop se publish karte hain. Tab robot ko screen ki bas ek tasveer dikhti hai, element properties kuch nahi. Wo **image matching** par aa jaata hai, yaani button ko uske dikhne se dhoondhna, ya **OCR** par, yaani tasveer se text padhna. Theme, font, screen resolution ya display scaling badalne par dono toot sakte hain.

Pehle IT team se poochho ki kya RPA vendor ka remote component install ho sakta hai. Jaise, UiPath ka ek Remote Runtime hai jo Citrix server par chalta hai aur robot ki machine par ek extension ke saath kaam karta hai, jisse robot ko phir se asli selectors mil jaate hain. Agar iski ijaazat nahi hai, to robot machine ka resolution aur scaling fix karo, har image ko paas ke kisi text label se anchor karo, aur har step ko text waapas padhkar verify karo.

### RPA, computer-use agent ya API?

**Computer-use agents** aise AI models hain jo screenshots dekhkar screens chalaate hain, aur har click chalte-chalte tay karte hain. Wo un screens ko bhi sambhaal lete hain jo unhone pehle kabhi nahi dekhin, par har step par ek model call ka kharcha hai, wo dheeme hain, aur ek hi screen par alag action chun sakte hain. Jab robot kisi claims ya banking system mein likh raha ho, to ye anishchitata maanna mushkil hai.

| Haalaat | Sabse sahi choice | Kyun |
| --- | --- | --- |
| System mein kaam ka API hai | API integration | Sabse tez, sabse mazboot, saaf errors |
| Stable screens, high volume, koi API nahi | RPA | Per item sasta, predictable, audit ho sakta hai |
| Badalti ya anjaan screens, kam volume | Computer-use agent, har change ko koi insaan approve kare | Flexible, jahaan RPA ko baar-baar fix karna padta |

Ek achha pattern inhein milaata hai: stable steps ke liye RPA, aur agent sirf kisi anapekshit screen se nikalne ke liye, aur kuch bhi save hone se pehle koi insaan approve kare.

### RPA plus AI

RPA screens ke zariye data aage badhaata hai; AI documents padhta hai, emails classify karta hai ya fields nikaalta hai. Saath milkar ye wo processes sambhaalte hain jo akele koi nahi sambhaal paata. AI step uljhe hue input ko saaf fields mein badalta hai; validation unhein aapke apne data se check karta hai; robot sirf validated fields type karta hai. Robot ko kabhi bhi AI ka andaaza seedhe system of record mein daalne mat do.

### Kya ye faayde ka hai? Ek break-even check

Robots free nahi hote. Banaane se pehle compare karo:

- **Har mahine ki saving** = har mahine bache ghante × staff ki loaded hourly cost (salary plus overheads).
- **Har mahine ka cost** = licences + robot machines + AI calls, agar hon + maintenance ghante × developer rate.

Phir ek baar ke build cost ko har mahine ki net saving se divide karo, payback period mil jaayega. Ek imaandaar rule: saving tabhi gino jab khaali hue ghante sach mein kisi aur kaam mein lagein. Varna robot sirf kharcha badhaata hai.

### Robots ko safe aur chaalu rakhna

Screens badalne, passwords expire hone ya pop-ups aane par robots toot-te hain. Pehle din se iski planning karo:

- **Monitoring.** Koi run fail ho ya queue aage badhna band kar de, to ek tay owner ko alert bhejo. Ruka hua robot aawaaz nahi karta; pehla sanket aksar koi naaraaz customer hota hai.
- **Ek robot register.** Har robot ka owner, wo kin systems ko chhoota hai aur kaun se accounts use karta hai, ye record karo.
- **Least-privilege accounts aur ek vault.** Har robot ko uska apna account do jismein sirf utna access ho jitna use chahiye. Uska password credential vault mein rakho, jaise orchestrator ka apna store ya CyberArk, script mein kabhi nahi.
- **Audit logs.** Har item ki key, har step aur result log karo, taaki saabit kar sako ki robot ne kya kiya. Logs mein personal data, jaise phone numbers, mask karo.
- **Target app badalne se pehle test karo.** App team se release dates poochho. Har naya version live hone se pehle uski test copy par robot chalaao, taaki khiske hue fields production mein nahi, testing mein hi pakde jaayein.

## Ek example se samjho

Ye typical numbers se bana ek illustrative case hai, koi naapa hua deployment nahi.

Kolkata ke ek general insurer ko motor claim intimations email par aate hain: roz kareeb 300. Claims team har email aur uske attachments se details ek puraane desktop claims system mein copy karti hai jismein API nahi hai. Har claim mein kareeb 6 minute lagte hain, to 300 × 6 = 1,800 minute, yaani roz 30 ghante ka kaam.

**Design:**

```flow
Claim waala email -> AI extraction step | policy no., vehicle no., nuksaan ki taareekh aur jagah
AI extraction step -> Policy database se validate karo
Policy database se validate karo -[ok]-> Queue item | key: policy no. plus date of loss
Policy database se validate karo -[ok nahi]-> Kisi insaan ki queue | wajah aur ek screenshot ke saath
Queue item -> Unattended robot | pehle search, na mile to create
Unattended robot -[app crash]-> App restart karke retry | system exception, 3 tries tak
App restart karke retry -> Unattended robot
Unattended robot -[screen pehchaan mein nahi aayi]-> Kisi insaan ki queue
Unattended robot -> Claim number waapas tracking sheet mein
```

1. Ek **AI extraction step** har email aur attachment padhkar fields nikaalta hai: policy number, vehicle number, nuksaan ki taareekh aur jagah, description.
2. Fields ko policy database se **validate** kiya jaata hai: policy hai ya nahi, active hai ya nahi, vehicle match karta hai ya nahi? Jo fail hon wo business exceptions hain aur wajah ke saath kisi insaan ke paas jaate hain.
3. Valid claims, policy number plus date of loss ko key banaakar **queue items** ban jaate hain.
4. Ek **unattended robot** claims system mein wo key search karta hai. Agar koi claim nahi hai, to wo "New intimation" kholta hai, fields bharta hai, save karta hai, naya claim number padhta hai, aur use tracking sheet mein likhta hai. Tabhi item successful mark hota hai.
5. App crashes system exceptions hain: restart karo aur retry, teen baar tak. Jo bhi screen robot pehchaan na paaye, wo screenshot ke saath kisi insaan ke paas jaati hai.

**Pehla quarter kuch aisa dikh sakta hai:**

| Paimaana | Pehle | Baad mein |
| --- | --- | --- |
| Data entry par staff ka time | Roz kareeb 30 ghante | Roz kareeb 6 ghante, zyaadatar exceptions |
| Usi din daale gaye claims | Kareeb 70% | Kareeb 98% |
| Robot outages | Laagu nahi | 2, dono baar system updates se fields khisakne ke baad |
| Retries se bane duplicate claims | Laagu nahi | 0, search-before-create ki wajah se |

**Kya ye faayde ka hai?** Ye maan liye gaye figures use karo; faisla karne se pehle asli quotes lo.

- Bache ghante: 30 − 6 = roz 24. 25 working days mein, ye har mahine 600 ghante hain.
- Maan lo loaded staff cost ₹400 prati ghanta hai. Saving: 600 × ₹400 = har mahine ₹2,40,000.
- Maan lo running costs har mahine licences aur robot machines ke liye ₹1,00,000, AI extraction ke liye ₹15,000, aur ₹1,000 prati ghante par 20 maintenance ghante (₹20,000) hain. Kul: ₹1,35,000.
- Net saving: ₹2,40,000 − ₹1,35,000 = har mahine ₹1,05,000. Agar build mein ₹6,00,000 lagte hain, to payback mein kareeb 6 mahine lagenge.

Ab ise ulta karke dekho. Har claim 6 minute × 24/30 = 4.8 minute, yaani 0.08 ghante bachaata hai, to ek claim ki keemat 0.08 × ₹400 = ₹32 hai. 25 dinon mein har mahine ₹1,35,000 cover karne ke liye robot ko ₹1,35,000 ÷ (25 × ₹32), yaani roz kareeb 170 claims chahiye. In assumptions ke saath, roz kareeb 170 claims se kam par robot ghaate mein hai. Case volume tay karta hai, robot kitna smart hai ye nahi.

Insurer ka plan hai ki claims system upgrade hone par robot ki jagah direct API integration lagaayi jaaye. Tab tak robot hi pul hai, aur use hataana bhi sasta hai kyunki saara logic ek documented queue process mein hai.

## Aam galtiyaan

- **Jahaan API hai wahaan RPA use karna.** API tez hai, mazboot hai aur saaf errors deta hai. Banaane se pehle vendor ya IT team se poochho.
- **Positions, generated ids ya index numbers se bandhe selectors.** Labels aur wildcards use karo, aur type karne ke baad values waapas padho.
- **Sab kuch retry karna, ya kuch bhi nahi.** Business exceptions kisi insaan ko bhejo; system exceptions ko tay ginti tak retry karo.
- **Banaane se pehle search nahi.** Save ke baad ek timeout, aur retry duplicate record bana deta hai.
- **Item ko bahut jaldi done mark karna.** Successful tabhi mark karo jab reference waapas likh diya jaaye.
- **Aisa process automate karna jo badalta rehta hai.** Pehle process theek ya pakka karo; robot aaj ki gadbad ko waise hi jama deta hai.
- **Koi owner nahi, koi alerts nahi.** Toote hue unattended robots chupchaap fail hote hain aur kaam dher hota jaata hai.
- **Admin accounts waale robots ya scripts mein passwords.** Least-privilege accounts aur vault use karo.
- **Hisaab lagaaye bina banaana.** Kam volume par licences aur maintenance bache hue time se zyada mehenge pad sakte hain.

## Practice karo

Neeche link ki gayi UiPath Academy par ek free beginner course karo. Agar aap Windows 11 par ho, to Power Automate for desktop mein bhi practice kar sakte ho, jo pehle se installed hai. Neeche link kiya gaya Microsoft Learn path Power Automate cloud flows cover karta hai, jo API waale hisse ke liye achha saathi hai.

1. **Banaao.** Ek robot banaao jo spreadsheet se rows padhe, har row ke liye ek web ya desktop form bhare, save kare, aur confirmation number waapas sheet mein likhe.
2. **Ise todo.** Window resize karo, display scaling badlo aur target box ke upar ek field jodo. Har failure ko behtar selectors se theek karo, aur type karne ke baad read-back check jodo.
3. **Ise idempotent banaao.** Wahi sheet do baar chalaao. Doosre run mein kuch bhi naya nahi banna chahiye; use har record dhoondhkar uska maujooda number uthaana chahiye.
4. **Chuno aur kharcha nikaalo.** Apne workplace ya college ke kisi ek process ke liye RPA, API aur computer-use agent mein se chuno, aur apne khud ke maane hue figures se uska break-even volume nikaalo.

**Aapka kaam poora hai jab aap** samjha sako ki API ya AI agent ki jagah RPA kab chunoge, aisa robot dikha sako jo chhote layout change aur bina duplicates waale doosre run ko jhel le, aur kisi ek asli process ka break-even volume bata sako.
