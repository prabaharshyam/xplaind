## Ye kya hai

LLM apps mein teen techniques cost aur intezaar ka samay ghataati hain. Ye alag-alag layers par kaam karti hain, aur inhein aapas mein mila dena hi zyaadatar caching bugs ki wajah banta hai.

- **Prompt caching** model provider ke paas hoti hai. Provider aapke prompt ki shuruaat (instructions, tool definitions, ek lamba document) ka processed roop rakh leta hai. Baad ki jo request theek usi content se shuru hoti hai, wo ye kaam skip kar deti hai, isliye uski cost kam hoti hai aur pehla token jaldi aata hai. Model phir bhi har baar naya jawaab likhta hai.
- **Response caching** aapke apne app mein hoti hai. Aap taiyaar jawaab store karte ho aur wahi request dobara aane par unmein se ek lauta dete ho, model call ke bina hi. Ise aap khud banaate ho, isliye har store kiya jawaab kaun dekh sakta hai, ye aap tay karte ho.
- **Streaming** delivery badalti hai, kaam nahi. Reply jaise-jaise generate hota hai, tukdon mein screen par pahunchta hai, isliye user ek-do second mein padhna shuru kar deta hai.

Teenon use karne waali ek request aisi dikhti hai:

```flow
title: Ek request, teen layers
Sawaal aata hai -> Mere response cache mein hai?
Mere response cache mein hai? -[hit, wahi scope]-> Store kiya jawaab lautao | model call nahi
Mere response cache mein hai? -[miss]-> Model ko call karo -> Provider cached prefix padhta hai | instructions aur documents
Provider cached prefix padhta hai -> Tokens screen par stream karo -> Taiyaar jawaab store karo | sirf tab jab reuse karna safe ho
```

Ye lesson Chennai ki ek legal-tech company ke contract assistant ko follow karta hai. Lawyers ek agreement upload karte hain aur us par kareeb das sawaal poochte hain.

## Ye kaise kaam karta hai

### Samay kahaan jaata hai

Ek reply ke do phases hote hain. Pehle model poora input padhta hai (**prefill**). Phir reply ek baar mein ek token karke likhta hai (**decode**). Lamba input pehle token ko dheema karta hai. Lamba output uske baad ki har cheez ko dheema karta hai. To 30,000-token ka contract zyaadatar **time to first token** (TTFT) par asar daalta hai, jabki 1,000-token ka jawaab zyaadatar total time par. Prompt caching pehle waale par vaar karti hai; streaming doosre ko chhipaati hai; chhote jawaab aur chhote models use ghataate hain.

### Prompt caching

Cache ek **exact prefix** match karta hai: request unhi bytes se, usi kram mein shuru honi chahiye, jaise haal mein dekhi gayi koi request. Ek character badla to uske baad ka sab kuch invalid ho jaata hai. Isliye prompt ko sabse stable se sabse kam stable ke kram mein rakho:

1. tool definitions, ek tay kram mein;
2. system instructions;
3. lambe reference documents (contract, policy, codebase);
4. per-user ya per-session data;
5. latest sawaal aur conversation turns.

Timestamp, request id ya user ka naam kabhi upar mat rakho. Model ko aaj ki date chahiye to use aakhir ke paas rakho.

**Wo numbers jo tay karte hain ki ye faaydemand hai ya nahi.** Claude ke API ke saath, November 2026 ke hisaab se (28 November 2026 ko check kiya; neeche link kiya pricing page dekho):

| Item | Value |
| --- | --- |
| Cache write, 5-minute lifetime (default) | Normal input price ka 1.25x |
| Cache write, 1-hour lifetime (`"ttl": "1h"`) | Normal input price ka 2x |
| Cache read | Zyaadatar models par 0.1x; Sonnet 5.5 aur Opus 5.5 par 0.05x; Fable 5.1 aur 5.2 par 0.025x |
| Lifetime | Entry ko write ya read karne waali aakhri request ke shuru hone se gini jaati hai; har read bina extra cost ke clock phir se shuru kar deta hai |
| Minimum cacheable prefix | Current models par 512 tokens (kuch puraane models par 1,024 se 4,096); isse chhote prefixes cache nahi hote aur koi error nahi aata |
| Har request mein breakpoints | 4 tak |
| Entry kaun share karta hai | Sirf aapka workspace; koi doosri organisation kabhi nahi |

Isse do rules nikalte hain. 5-minute cache ek read ke baad apni cost vasool kar leta hai; 1-hour cache ko do chahiye. Aur price se zyaada lifetime maayne rakhti hai: agar ek prefix share karne waali requests lifetime se zyaada doori par aati hain, to har request write premium deti hai aur kisi ko read discount nahi milta, jo caching na karne se bhi mehenga padta hai.

Lifetime prefix share karne waali requests ke beech ke gap se chuno. 5 minute se kam ho to default use karo; steady traffic use apne-aap warm rakhta hai. 5 se 60 minute ke beech ho to 1-hour cache. Ek ghante se zyaada ho to ya to pehli request ke cold hone ko maan lo ya **pre-warm** karo: traffic aane ki ummeed se theek pehle (worker start, pehle lawyer ka login), shared prefix ko `max_tokens` 0 set karke ek baar bhejo. Tab Claude ka API cache write kar deta hai aur kuch bhi generate kiye bina laut aata hai.

**Parallel requests aisa cache share nahi kartin jo abhi write ho raha hai.** Entry tabhi readable hoti hai jab pehla response shuru ho jaaye. Ek saath das requests bhejoge to dason poori keemat dengi. Pehle ek bhejo, uske pehle token ka intezaar karo, phir baaki bhejo.

**Doosre providers.** Kuch providers, jaise OpenAI, prompt ke ek minimum length tak pahunchte hi apne-aap cache kar lete hain (unke documentation ke hisaab se, model ke anusaar kam se kam 1,024 tokens). Claude automatic caching ya explicit breakpoints deta hai. Stable content pehle rakhna har jagah kaam karta hai; minimums, lifetimes aur prices alag hote hain, isliye savings ka andaaza lagaane se pehle apne provider ka page padho.

**Code mein prompt caching.** Anthropic ke Python SDK mein aap stable hisse ka ant mark karte ho, aur usage report dikhaati hai ki cache se kya padha gaya:

```python
import anthropic

client = anthropic.Anthropic()
POLICY = open("returns_policy.md").read()          # long, rarely changes

def ask(question):
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000,  # check the docs for current model names
        system=[
            {"type": "text", "text": "You answer questions about our returns policy. Be brief."},
            {"type": "text", "text": POLICY,
             "cache_control": {"type": "ephemeral"}},  # cache up to here; add "ttl": "1h" for slow traffic
        ],
        messages=[{"role": "user", "content": question}],   # changing part goes last
    )
    u = reply.usage
    print(f"cache write {u.cache_creation_input_tokens}, cache read {u.cache_read_input_tokens}, "
          f"uncached {u.input_tokens}")
    return reply

ask("Can I return a kurta after 10 days?")       # first call writes the cache
ask("Do you refund shipping charges?")           # later calls read it
```

**Kaam kar raha hai ya nahi, ye check karna.** Har call par teenon usage numbers log karo. Lagaataar paanch requests bhejo: pehli mein cache write dikhna chahiye aur baaki mein lagbhag utne hi size ke cache reads. Agar reads zero par hi rahein, to prefix mein kuch abhi bhi badal raha hai: timestamp, request id, alag kram mein bane tools, bina sorted keys waala JSON, minimum se chhota prefix, ya badla hua model ya thinking setting. Agar reads prefix se bahut chhote hain, to breakpoint galat jagah par hai.

### Response caching, user tak scoped

Response cache ek key-value store hota hai, jaise dictionary ya Redis. Key mein **jawaab badalne waali har cheez** honi chahiye: normalise kiya sawaal, document ya data version, prompt version, model, aur **scope**, yaani jawaab dekhne ki ijaazat kise hai.

Scope wo hissa hai jise teams bhool jaati hain, aur ise bhoolne se data leak hota hai. Maan lo key mein sirf sawaal hai. Asha poochti hai "Mera order kahaan hai?" aur uske address waala jawaab store ho jaata hai. Ravi wahi shabd poochta hai aur use cache se Asha ka jawaab mil jaata hai, milliseconds mein, kisi log mein koi error nahi. Provider ka prompt cache aisa nahi kar sakta, kyunki model har baar naya jawaab likhta hai. Aapka response cache kar sakta hai, kyunki wo store kiya text lautaata hai.

Teen scopes use karo. **Public**: sabke liye ek jaisa, jaise product FAQs aur fixed help text. **Tenant**: ek company ke andar ek jaisa, jaise kisi law firm ka apna standard NDA, par kisi doosri firm ko kabhi nahi dikhaaya jaata. **User**: personal ya permission par depend karne waala; iski key user id se banao, ya ise cache hi mat karo. Scope ko ek required argument bana do taaki koi ise bhool na sake:

```python
import hashlib, json, time

CACHE, TTL_SECONDS = {}, 24 * 3600
PROMPT_VERSION, MODEL = "faq-v3", "claude-sonnet-5-5"

def cache_key(scope, question, doc_version):
    norm = " ".join(question.lower().split())
    raw = json.dumps([scope, norm, doc_version, PROMPT_VERSION, MODEL])
    return hashlib.sha256(raw.encode()).hexdigest()

def cached_answer(scope, question, doc_version, compute):
    # scope: "public", "firm:<id>" or "user:<id>"; there is no default on purpose
    key = cache_key(scope, question, doc_version)
    hit = CACHE.get(key)
    if hit and time.time() - hit["at"] < TTL_SECONDS:
        return hit["answer"]
    answer, complete = compute(question)          # complete: the reply finished normally
    if complete:                                  # never cache errors or cut-off replies
        CACHE[key] = {"answer": answer, "at": time.time()}
    return answer
```

Ship karne se pehle two-account test chalao: user A ek personal sawaal poochta hai, user B wahi shabd poochta hai, aur B ko A ka jawaab nahi milna chahiye. Stable jawaabon ke liye bhi expiry rakho, aur source badalne par entries clear karo; cache kiya galat jawaab tab tak dohraaya jaata hai jab tak koi notice na kare.

### Semantic caching, saavdhaani se

**Semantic caching** embeddings se sawaalon ko matlab ke hisaab se match karti hai, taaki "Hamaare NDA mein notice period?" ka sawaal "NDA ka notice period kya hai?" ke jawaab ko reuse kar sake. Isse hit rates badhte hain, par har galat match poore bharose ke saath ek galat jawaab deta hai. Teen guards:

- **Similarity search se pehle scope se filter karo**, taaki match sirf un jawaabon se aa sake jinhein poochne waala dekh sakta hai.
- **Numbers aur names par exact mel zaroori rakho.** "Order 41 ka refund" aur "order 14 ka refund" text ke taur par lagbhag ek jaise hain aur sawaal ke taur par bilkul alag:

```python
import re

def numbers_match(new_q, cached_q):
    return re.findall(r"\d+", new_q) == re.findall(r"\d+", cached_q)
```

- **Similarity threshold apne khud ke data se set karo.** Koi safe universal number nahi hai. Candidate matches log karo, kisi vyakti se unmein se 200 ko sahi ya galat label karwao, aur threshold tab tak badhao jab tak wrong-match rate us feature ke liye aapke tay kiye target se neeche na aa jaaye.

### Streaming

Streaming total generation time ya cost nahi badalti. Ye experience badalti hai: text ek-do second mein shuru ho jaata hai, baaki aate-aate user padhta rehta hai, aur jaldi Stop daba sakta hai. Chat mein hamesha stream karo. TTFT measure karo:

```python
import time
import anthropic

client = anthropic.Anthropic()

def stream_answer(question):
    start, first = time.perf_counter(), None
    with client.messages.stream(model="claude-sonnet-5-5", max_tokens=2000,
                                messages=[{"role": "user", "content": question}]) as stream:
        for text in stream.text_stream:
            if first is None:
                first = time.perf_counter() - start
            print(text, end="", flush=True)     # in a web app, send each piece to the browser
        final = stream.get_final_message()
    print("\nfirst text after", round(first, 2) if first else None,
          "s; total", round(time.perf_counter() - start, 2), "s; stop:", final.stop_reason)
```

Server timing poori kahaani nahi hai: browser mein, user ke Send dabaane par aur pehle shabdon ke paint hone par `performance.now()` record karo, aur real users se p50 aur p95 report karo. Teen gotchas. Kuch proxies, compression layers aur hosting platforms response ko buffer karte hain, isliye jo stream local par kaam karta hai wo production mein ek saath pahunchta hai; asli path se test karo. Stream beech mein fail ho sakta hai, isliye partial text ko saaf "answer interrupted, try again" ke saath dikhao aur use kabhi cache mat karo. Aur jawaab poora hone se pehle hi text screen par hota hai, isliye jis check ko poora jawaab chahiye, jaise safety filter ya JSON validation, use har tukde par chalna hoga ya text dikhaana shuru karne se pehle chalna hoga.

### Speed ke doosre levers

Chhote outputs, kyunki generation time length ke saath badhta hai. Simple steps ke liye chhote models. Sequence mein kam calls. Ek-doosre par depend na karne waali calls parallel mein (jaise `asyncio.gather` se), taaki intezaar sabka jod na hokar sabse dheemi call jitna ho; rate limits ka dhyaan rakho, kyunki ek burst 429 errors lauta sakta hai. Kam, par behtar retrieved chunks.

## Ek worked example

Chennai ka contract assistant 40-page ke agreement par sawaalon ke jawaab deta hai. Neeche ke numbers November 2026 ke hisaab se Claude Sonnet 5.5 ki list prices par bana ek **illustration** hain ($2 per million input tokens, $10 per million output, cache writes 5 minute ke liye $2.50 ya 1 hour ke liye $4, cache reads $0.10), in assumptions ke saath: instructions aur contract 30,000 tokens hain, har sawaal 100 tokens ka hai aur akele bheja jaata hai, har jawaab 300 output tokens use karta hai, aur har contract par 10 sawaal hain. Ye figures dobara use karne se pehle current prices check karo.

**Pehle.** Har sawaal poore 30,100 tokens poori keemat par bhejta hai: $0.0602 ka input aur $0.003 ka output, yaani $0.0632 per sawaal aur **$0.63 per contract**. Kuch bhi stream nahi hota, isliye lawyer ko kareeb 9 seconds tak kuch nahi dikhta.

**Baad mein, pehli koshish.** Team contract aur instructions ko aage le aati hai, ek breakpoint jodti hai, aur default 5-minute cache rakhti hai. Agar sawaal 5 minute se kam ke antar par aate, to sawaal 1 ki cost $0.078 hoti (write premium use pehle se mehenga bana deta hai) aur baad ke har sawaal ki $0.0062, yaani **$0.13 per contract, 79% kam**. Par logs mein lagbhag har call par cache writes dikhte hain. Lawyers agla sawaal poochne se pehle har jawaab ko clause se milaakar padhte hain, aksar 5 se 15 minute baad. Har entry expire ho jaati hai, har sawaal write price deta hai, aur bill badhkar **$0.78 per contract ho jaata hai, caching na karne se 24% zyaada**.

**Baad mein, theek kiya.** Wo 1-hour cache par switch karte hain. Ab sawaal 1 ki cost write ke liye $0.12 hai, aur agle nau ki $0.0062 har ek: **$0.18 per contract, pehle se kareeb 72% kam**. Kareeb ₹94 per dollar par (mid-November 2026), ye per contract lagbhag ₹59 se ghatkar ₹17 hai. Dhyaan do ki output tokens ($0.003 per jawaab) ab ek cached sawaal ki cost ka aadha hain, isliye agli bachat chhote jawaab hain.

| Per contract session (illustrative) | Caching nahi | 5-minute cache, gaps 5 min se zyaada | 1-hour cache, streaming on |
| --- | --- | --- | --- |
| Input cost, 10 sawaal | Har baar poori keemat | Har baar write premium | Ek write, nau saste reads |
| Total cost | $0.63 | $0.78 | $0.18 |
| Koi bhi text aane se pehle intezaar, sawaal 1 | Kareeb 9 s | Kareeb 9 s | Kareeb 2 se 3 s (streamed, cache abhi khaali) |
| Koi bhi text aane se pehle intezaar, sawaal 2 se 10 | Kareeb 9 s | Kareeb 9 s | Kareeb 1 se 2 s (cached prefix, streamed) |

Firm ke paas apne standard templates par sawaalon ke liye ek response cache bhi hai ("Hamaare standard NDA mein notice period kya hai?"). Iski key firm ki id, template version aur prompt version se bani hai, isliye firm A ke template jawaab kabhi firm B tak nahi pahunchte. Upload kiye contract ke baare mein jawaab response-cache hote hi nahi: har contract ek matter ka hota hai jiski apni access list hai.

Pehle sawaal ko bhi tez karne ke liye, contract upload poora hote hi, jab lawyer abhi type kar raha hota hai, team `max_tokens` 0 set karke cache pre-warm kar deti hai.

## Aam galtiyaan

- **Prompt ke upar kuch badalne waala.** Date, request id ya user name har cache read tod deta hai. Pehchaano: baar-baar ki calls par `cache_read_input_tokens` 0 par hi rehta hai.
- **Traffic ke liye galat lifetime.** Cache lifetime se lambe gaps caching ko surcharge bana dete hain. Pehchaano: zyaadatar calls par cache writes aur kam reads.
- **Bina scope waali response cache keys.** Ek user ka order, salary ya contract doosre user tak pahunch jaata hai. Pehchaano: launch se pehle aur har cache change ke baad chalaaya gaya two-account test.
- **Badalne waale data se bane jawaabon ko cache karna, key mein expiry ya version ke bina.** Puraani prices aur puraane rules serve hote rehte hain. Pehchaano: update ke baad source se mel na khaane waale jawaab.
- **Failures ko cache karna.** Timeout, refusal ya `max_tokens` se kata reply store ho jaata hai aur sabko replay hota hai. Sirf wahi replies store karo jo normal tareeke se poore hue.
- **Cold cache par parallel requests bhejna.** Sab poori keemat deti hain. Pehchaano: ek hi second mein cache writes ka burst.
- **Ye maanna ki streaming generation ko tez karti hai.** Ye intezaar ko chhota feel karwaati hai; cost aur total time wahi rehte hain.
- **Sirf averages measure karna.** Time to first token aur total time ke liye p50 aur p95 report karo, server ke saath-saath browser mein bhi measure karke.

## Caching kab madad nahi karti

- **Har request alag hai**, koi lamba shared prefix nahi aur dohraaye sawaal kam.
- **Traffic kam aur bikhra hua hai**, isliye cached prefixes agli request se pehle expire ho jaate hain, 1 hour par bhi.
- **Shared hissa chhota hai**, minimum cacheable length se neeche.
- **Jawaab har baar fresh chahiye**, jaise live prices ya stock levels.
- **Dheema hissa kahin aur hai**: retrieval, koi dheema tool ya aapka apna server. Model call ko optimise karne se pehle measure karo.

## Demo se production tak

- Har call par **cache read aur write tokens log karo**, aur har feature ka hit rate track karo.
- **Time to first token aur total time track karo** p50 aur p95 par, feature aur model ke hisaab se, browser se.
- **Cache keys ko version karo** prompt, model aur data se, har jagah expiries rakho, aur release par ya source data badalne par response caches clear karo.
- **Scope ko har response cache key ka required hissa banao**, aur two-account test ko apne test suite mein rakho.

## Practice

Neeche link kiya prompt caching guide aur streaming guide padho.

1. Apne kisi ek prompt ko aise restructure karo ki stable content pehle aaye, aur ek breakpoint jodo. Paanch requests bhejo aur har ek ke liye cache write, cache read aur uncached tokens record karo.
2. Apne real traffic mein requests ke beech ka gap nikaalo, 5 minutes ya 1 hour chuno, aur apne provider ki current prices se per session cost dono tareekon se calculate karo.
3. Ek chat interface mein streaming jodo aur pehle aur baad mein browser mein time to first token measure karo.
4. Ek dohraaye jaane waale sawaal type ke liye scoped response cache jodo, phir two-account test likho aur scope hataane par use fail hote dekho.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly, 2025) ka chapter 9 prefill aur decode, prompt caching aur parallelism cover karta hai, aur chapter 10 exact aur semantic caches cover karta hai.

**Aapka kaam poora hai jab aap** samjha sako ki prompt caching kya bachaati hai aur uski cost kya hai, requests ke beech ke gap se cache lifetime chun sako, response cache ko aise scope kar sako ki koi jawaab users ke beech na jaaye, aur bata sako ki total time wahi rehne par bhi streaming kyun madad karti hai.
