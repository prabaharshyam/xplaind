## Ye kya hai

**Clean code** woh code hai jise agla insaan bina dare padh, samajh aur badal sake. Wo agla insaan aksar aap hi hote ho, teen mahine baad, bina ye yaad kiye ki aisa kyun likha tha.

Clean code clever tricks ya kam se kam lines ki baat nahi hai. Ye padhne waale ki baat hai. Kya woh function ka naam dekhkar samajh sakta hai ki woh kya karta hai? Kya woh use upar se neeche bina idhar-udhar kudey follow kar sakta hai? Kya woh ek rule ek hi jagah badal sakta hai?

**Refactoring** code kaise likha hai ye badalna hai, bina ye badle ki woh kya karta hai. Aap rename karte ho, split karte ho, simplify karte ho aur duplication hatate ho, ek-ek chhote step mein, tests confirm karte hue ki behaviour same hai. Risky rewrite ke bina messy code aise hi clean code banta hai.

## Ye kaam kaise karta hai

Jo aadatein sabse zyada farak daalti hain:

| Aadat | Pehle | Baad mein |
| --- | --- | --- |
| Saaf naam | `def calc(d, f):` | `def invoice_total(items, include_gst):` |
| Named constants | `amount * 1.18` | `amount * (1 + GST_RATE)` |
| Chhote functions | Ek 120 line ka `process()` | `read_orders()`, `validate()`, `total()`, `write_report()` |
| Early returns | Chaar nested `if` blocks | Pehle bure cases handle karo, phir main path |
| Sach ka ek source | Wahi rule teen files mein copy | Ek function jise sab bulaate hain |
| Imaandaar comments | `# loop over items` | `# Refunds older than 30 days need manager approval (policy 4.2)` |

Achhe comments **kyun** batate hain, kya nahi. Code pehle se batata hai ki woh kya karta hai; comment ko woh batana chahiye jo code nahi bata sakta, jaise business rule ya kisi ajeeb choice ki wajah.

Refactoring ek safe loop follow karti hai:

```flow
dir: LR
Tests pass -> One small change | rename, extract a function, add a constant
One small change -> Run the tests
Run the tests -[pass]-> Commit
Commit -> One small change
Run the tests -[fail]-> Undo and try a smaller step
Undo and try a smaller step -> One small change
```

Chhote steps matter karte hain. Ek rename, tests ka run, ek commit. Ek extracted function, ek run, ek commit. Test fail ho toh pata hota hai ki kaunse step ne todha aur sirf wahi undo kar sakte ho. Big-bang rewrite mein ye kuch nahi milta.

**Extract function** sabse kaam ka refactor hai. Lambe function ke andar ka koi block lo jo ek hi kaam karta hai, use apne function mein daalo jiska naam wahi kaam bataye, aur use bula do. Lamba function steps ki list jaisa padhne lagta hai.

**Code smells** woh nishaan hain ki code badalna mushkil hoga: functions itne lambe ki ek screen mein na aayein, wahi logic kai jagah copy, ek change jise paanch files mein edit karna pade, gehri nesting, aur `data`, `temp` ya `x` naam ke variables. Ye bugs nahi hain; ye wahan hain jahan bugs panapte hain.

**AI projects mein clean code.** Wahi aadatein prompts aur pipelines par bhi lagti hain. Prompts ko functions mein dabi lambi strings ki jagah saaf naam waali apni files mein rakho. Pipeline ke har step (load, chunk, embed, retrieve, generate) ko apna function do, taaki baaki ko chhue bina ek ko test aur badal sako. Chunk size, top-k aur temperature jaisi settings ko ek config file mein constants ki tarah naam do, taaki experiment mein ek hi line badle aur diff saaf dikhaye ki kya try hua.

**Refactor kab nahi karna.** Refactoring ka cost hai: time, review ki mehnat aur thoda risk. Jo code chalta hai aur jise koi badalne wala nahi, throwaway scripts, aur outage ke beech mein ise chhod do, jahan sabse chhota fix hi sahi hai. Safai baad mein karo, apne alag pull request mein, jab urgent change ship ho chuka ho aur uske aas-paas tests hon.

## Ek example se samjho

Kavya ko Kochi ki ek edtech company mein 140 line ka function `process_file()` inherit hota hai. Ye course purchases ki CSV padhta hai, refunds filter karta hai, GST jodta hai, coupons lagata hai aur summary likhta hai. Ek naya rule aa raha hai: ek sarkari scheme ke liye GST skip karna hoga. Function badalna risky lagta hai.

**Pehle, tests.** Woh aaj ke behaviour ke aas-paas chhe tests likhti hai, chhoti sample CSVs se: normal purchases, ek refund, ek coupon, ek zero amount, ek missing field aur ek duplicate row. Sab purane code par pass hote hain. Ab uske paas safety net hai.

**Phir chhote steps.** Woh `d` ko `purchases` aur `t` ko `total` rename karti hai. Tests pass; commit. Woh `* 1.18` ki teen copies ko `GST_RATE` constant aur `with_gst()` function se badalti hai. Tests pass; commit. Woh `read_purchases()`, `apply_coupon()` aur `write_summary()` extract karti hai. Har step tests chalata hai aur apna commit paata hai.

Main function ab gyarah lines ka hai jo business process ki tarah padhta hai:

```python
def process_file(path):
    purchases = read_purchases(path)
    paid = [p for p in purchases if not p.is_refund]
    totals = [with_gst(apply_coupon(p)) for p in paid]
    write_summary(totals)
```

**Phir naya rule.** Scheme ke liye GST skip karna ab ek jagah, ek function `with_gst()` mein ek change hai, saath mein ek naya test. Pull request chhota aur review mein aasaan hai, aur uska reviewer usi din approve kar deta hai.

## Aam galtiyaan

- **Bina tests ke refactor.** Aap bata nahi sakte ki behaviour badla ya nahi. Pehle aaj jo ye karta hai uske tests likho.
- **Ek hi step mein refactor aur behaviour change.** Safai aur naya feature alag commits mein karo, taaki har ek review mein aasaan ho.
- **Bade rewrites.** Inmein hafte lagte hain aur woh cheezein tod dete hain jo kisi ko yaad nahi thi. Chhote, safe steps jeette hain.
- **Clever one-liners.** Chhota hona clean hona nahi hai agar padhne waale ko use decode karna pade.
- **Code ko doharane waale comments.** Ye purane ho jaate hain. Wajah batao, ya rename karo jab tak comment ki zaroorat na rahe.
- **Aise code ko chamkana jise koi chhuega nahi.** Jo badalne waale ho wahi refactor karo, sab kuch nahi.
