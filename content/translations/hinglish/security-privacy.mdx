## Ye kya hai

LLM apps aam web security ki chintaon ke saath kuch naye khatre bhi laate hain. LLM applications ke liye OWASP Top 10 ek bahut use ki jaane wali checklist hai. Zyadatar apps ke liye ye areas sabse zaroori hain:

- **Secrets**: API keys aur credentials.
- **User data**: models ko bheji gayi, logs mein store hui ya answers mein dikhi personal information.
- **Access**: app kaun use kar sakta hai aur har user kya dekh sakta hai.
- **Model-specific risks**: prompt injection, system prompt leak, excessive agency, model output ka insecure handling.

| | Pehle | Baad mein |
|---|---|---|
| API key | Browser ke JavaScript mein, seedhe model ko jaati hui | Sirf backend par, secrets se |
| Prompt | "admin password: ..." | Koi secrets nahi |
| Customer data | Poora record model ko jaata hai | Tool sirf order id, status aur date deta hai |
| Customer id | Browser se liya jaata hai | Verified session se liya jaata hai |
| Reply | Raw HTML ki tarah daala jaata hai | Text ki tarah render hota hai |
| Logs | Phone numbers ke saath poori chats | Masked, 30 din rakhe jaate hain |


## Ye kaam kaise karta hai

**Keys server par rakho.** Model API key server-side environment variables ya secret manager mein rehti hai. Use kabhi browser JavaScript, mobile apps ya Git mein mat daalo. Browser aapke backend ko call karta hai; aapka backend model ko call karta hai. Agar key leak ho jaaye toh turant revoke karo.

**Prompts mein secrets nahi.** Maan lo ki users system prompt nikaal sakte hain. Passwords, keys ya internal-only information mat daalo jo aap dikhana nahi chahoge.

**Sirf wahi bhejo jo task ko chahiye.** "Mera order kahan hai?" ka jawab dene waale support bot ko order status chahiye, customer ka poora profile, payment details ya address history nahi. Data minimisation kuch leak hone par nuksaan ghatati hai aur India ke DPDP Act ka ek principle hai.

**Personal data ko mask karo** logs aur traces mein, retention periods tay karo aur access restrict karo.

**Authenticate aur authorise karo.** Users sign in karte hain; har request check karti hai ki woh kaun hain; retrieval aur tools sirf us user ka data access karte hain. Browser se aaye user id par bina verify kiye kabhi bharosa mat karo.

**Model output ko untrusted maano.** Use seedhe HTML (cross-site scripting), SQL ya shell commands mein mat daalo. Kisi bhi user input ki tarah escape ya validate karo.

**Capabilities limit karo.** Jitni kam permissions chahiye utne ke saath tools; risky actions ke liye approvals; har user ke liye rate limits.

**Vendor terms.** Check karo ki aapka model provider data kaise store aur use karta hai, aur aise settings aur regions chuno jo aapke users aur clients ki zaroorat se match karein.

**Checklist chalao.** Apne app ke liye LLM applications ka OWASP Top 10 chalao aur har item ke liye apni defence note karo.

**Zyadatar LLM apps ke liye checklist items:**

| Area | Sawaal | Achha jawab |
| --- | --- | --- |
| Keys | Kya key browser ya Git history mein dikhti hai? | Nahi; server-side, kabhi khuli toh rotate |
| Prompts | Kya system prompt mein kuch secret hai? | Nahi |
| Data | Har feature ke liye model tak kya pahunchta hai? | Sirf task ke liye zaroori fields |
| Identity | User id kahan se aata hai? | Verified session se |
| Output | Model output kaise dikhaya ya use kiya jaata hai? | Escaped text; kisi bhi query ya command se pehle validate |
| Logs | Kaunsa personal data log hota hai, kitne time ke liye? | Masked; tay retention; restricted access |
| Tools | Model kya trigger kar sakta hai? | Least privilege; risky actions ke liye approval |
| Vendor | Provider data kaise use aur rakhta hai? | Terms check kiye; suitable region aur settings |

**Aane aur jaane par guardrails.** Ek **input guardrail** check karta hai ki model ke liye kya nikalne waala hai: personal data, company secrets, attack ke signs. Ek **output guardrail** check karta hai ki wapas kya aaya, kisi ke dekhne ya code ke act karne se pehle: personal data, unsafe content, malformed output, ek tool call jo nahi hona chahiye. Guardrail fire ho toh aap block, mask, retry ya kisi insaan ko handover kar sakte ho. Do trade-offs: har check delay badhata hai, aur streaming mein output checks mushkil hain, kyunki poore reply ko check karne se pehle shabd user tak pahunch jaate hain. Streamed chat ke liye chunks mein check karo, aur sabse kadi checks shabdon ki jagah actions ke liye rakho.

**Leaks aksar achhe irade se shuru hote hain.** 2023 mein Samsung ke engineers ne internal source code ek public chatbot mein paste kar diya, usme madad ke liye. Apps mein bhi yahi hota hai: koi developer internal policy system prompt mein paste kar deta hai, ya koi tool poori database row context mein kheench leta hai. Har feature ke liye poochho: "hamare servers se kya nikal raha hai, aur kya uski zaroorat hai?"

**Mask, call, unmask.** Kai tasks mein model ko asli identifiers ki zaroorat nahi hoti. Call se pehle unhe placeholders se badlo, apne server par ek map rakho, aur baad mein asli values wapas daalo:

```python
import re

PATTERNS = {
    "PAN": r"\b[A-Z]{5}[0-9]{4}[A-Z]\b",
    "AADHAAR": r"\b[2-9][0-9]{3}\s?[0-9]{4}\s?[0-9]{4}\b",
    "PHONE": r"(?<!\d)(?:\+91[\s-]?)?[6-9][0-9]{9}(?!\d)",
    "EMAIL": r"\b[\w.+-]+@[\w-]+\.[\w.-]+\b",
    "UPI": r"\b[\w.-]+@(?:ok\w+|ybl|paytm|upi|ibl|axl)\b",
}

def mask(text):
    mapping, count = {}, {}
    for label in ["UPI", "EMAIL", "PAN", "AADHAAR", "PHONE"]:     # UPI first: UPI ids look like emails
        def swap(m, label=label):
            count[label] = count.get(label, 0) + 1
            key = f"[{label}_{count[label]}]"
            mapping[key] = m.group(0)
            return key
        text = re.sub(PATTERNS[label], swap, text)
    return text, mapping

def unmask(text, mapping):
    for key, value in mapping.items():
        text = text.replace(key, value)
    return text

safe, keys = mask("My PAN is ABCDE1234F and mobile 9876543210, UPI ravi@okaxis.")
print(safe)    # My PAN is [PAN_1] and mobile [PHONE_1], UPI [UPI_1].
```

Aise patterns kuch forms chhod dete hain aur kuch innocent numbers pakad lete hain, isliye real (masked) samples par test karo, aur jab dao ooncha ho toh Microsoft Presidio jaisa dedicated detection tool use karo. Masking ki limits bhi hain: model ek aisa PAN check nahi kar sakta jo usne dekha hi nahi, isliye un tasks ke liye check aapke apne code mein hona chahiye.

**Retrieval ko permissions ka dhyaan rakhna hoga.** RAG app mein search index aksar kai users ya departments ke documents rakhta hai. Kuch bhi prompt mein jaane se **pehle** results ko is aadhaar par filter karo ki sign-in kiya hua user kya padh sakta hai; model us secret ko nahi rakh sakta jo use dikha di gayi ho.

**Bill ko bhi control karo.** Unlimited requests ek user, ek script ya ek attacker ko kharcha badhane ya sabke liye app slow karne dete hain. Per-user rate limits, input length par cap aur daily budget alert lagao.

**LLM applications ke liye OWASP Top 10 (2025), har ek ke liye ek defence:**

| Risk | Ek defence |
| --- | --- |
| Prompt injection | Retrieved aur user text ko data maano; tools kya kar sakte hain use limit karo |
| Sensitive information disclosure | Data minimisation, masking, output checks |
| Supply chain | Packages pin karo aur scan karo; trusted sources ke models aur datasets use karo |
| Data and model poisoning | Training aur retrieval data sources ko review aur track karo |
| Improper output handling | Output escape karo; SQL, shell ya HTML se pehle validate karo |
| Excessive agency | Least-privilege tools; actions ke liye approval |
| System prompt leakage | Prompts mein secrets ya access rules nahi; unhe code mein enforce karo |
| Vector and embedding weaknesses | Retrieval par permission filters; har tenant ke liye alag indexes |
| Misinformation | Grounding, citations, aur "mujhe nahi pata" kehna |
| Unbounded consumption | Rate limits, input caps, budgets |

**Indian kanoon, sankshep mein.** Digital Personal Data Protection Act, 2023 aur uske Rules, jo charanon mein lagu honge, India mein logon ke digital personal data par lagu hote hain. Practice mein: jo aap collect karte ho uske liye saaf notice aur consent, sirf bataye gaye purpose ke liye use, sirf zaroorat tak rakho, reasonable security se protect karo, logon ko apna data access aur erase karne do, aur breaches report karo. Bachchon ke data ke liye verifiable parental consent chahiye. Ye ek summary hai, legal advice nahi; apne case ke liye current rules check karo.

**Git history mein secrets check karna.** Code se key hatane se woh history se nahi hatti. Poori repository history par secret scanner chalao, jo bhi mile use rotate karo, aur scanner ko CI mein jodo taaki naye secrets push hone se pehle pakde jaayein.

**Users ke beech access test karna.** Do test accounts banao aur pehle wale se requests mein ids badal kar aur bot se seedhe poochh kar doosre ke orders padhne ki koshish karo. Dono fail hone chahiye. Inhe automated tests ki tarah rakho.

## Ek example se samjho

Bengaluru ka ek D2C brand support bot banata hai. Pehle version ka security review ye paata hai:

- API key React front end mein thi, browser ke developer tools mein dikhti thi. Fix: calls backend par gaye; key rotate hui.
- System prompt mein admin dashboard ka password "reference ke liye" tha. Hataya aur rotate kiya.
- Order sawaalon ka jawab dene ke liye bot ne customer ka poora record (address, phone, past orders, saved payment method) prompt mein kheencha. Fix: ek tool sirf order id, status aur expected date deta hai.
- Customer id browser request ke ek field se aata tha. Fix: uski jagah verified session se liya jaata hai.
- Bot replies raw HTML ki tarah daale jaate the; ek crafted message ek script inject kar sakta tha. Fix: replies text ki tarah render hote hain.
- Logs phone numbers ke saath poori conversations store karte the. Fix: masking aur 30 din ki retention.

| Finding | Fix |
| --- | --- |
| React front end mein API key | Calls backend par gaye; key rotate |
| System prompt mein admin password | Hataya aur rotate kiya |
| Prompt mein poora customer record | Tool sirf order id, status aur date deta hai |
| Browser se customer id | Verified session se liya |
| Replies raw HTML ki tarah | Text ki tarah render |
| Logs mein phone numbers ke saath poori chats | Masked, 30 din retention |

## Aam galtiyaan

- **Front-end code ya Git mein API keys.**
- **System prompts mein secrets.**
- **Model ko poore customer records bhejna.**
- **Browser se aaye user ids par bharosa karna.**
- **Model output ko raw HTML ki tarah render karna.**
- **Permission filters ke bina retrieval.** Model khushi se woh document quote kar dega jo user ko kabhi nahi dekhna chahiye.
- **Access rules sirf prompt mein likhna.** Prompt mein "doosre customers ke orders kabhi mat dikhao" ek umeed hai; code mein check ek control hai.
- **Use par limits nahi.** Ek script bill badha sakti hai ya sabke liye app slow kar sakti hai.

## Jab risk kam ho

- **Apne laptop par ek personal tool**, apne data ke saath, tab bhi key ko Git se bahar rakhna hai, par masking ya audit logs nahi chahiye.
- **Sirf public data**, jaise published government circulars par ek bot: output handling, injection aur cost limits par focus karo.
- **Chhoti trusted team ke liye read-only internal tools**: key safe rakho aur tools kahan tak pahunch sakte hain use limit karo, par poore guardrail stacks ruk sakte hain.

Personal data, paise, write actions, kai users ya banking, insurance aur health jaise regulated sectors ke saath risk tezi se badhta hai.

## Demo se production tak

- **Data map likho**: har feature ke liye, kaunsa personal data use hota hai, kahan jaata hai, kitne time tak rakha jaata hai.
- **Apne model provider ke saath data processing agreement sign karo**, aur retention aur region settings us hisaab se chuno.
- **Checks automate karo**: CI mein secret scanner, do-account access tests, injection tests aur output-escaping tests.
- **Keys ko schedule par rotate karo** aur jab bhi access wala koi chhode toh turant.
- **Incidents ke liye plan karo**: kaun decide karta hai, keys kaise revoke karni hain, affected users aur regulator ko kaise batana hai, aur kitni jaldi.
- **Har kuch mahine access review karo**: logs, index aur admin tools kaun padh sakta hai.
