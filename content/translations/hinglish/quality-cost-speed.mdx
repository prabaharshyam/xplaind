## Ye kya hai

Har LLM app teen cheezon ko ek-doosre ke against trade karta hai:

- **Quality**: jawaab kitni baar sahi, poore aur safe hote hain.
- **Cost**: har request aur har mahine ka paisa.
- **Speed**: users kitna intezaar karte hain, pehle shabdon ke liye bhi aur poore reply ke liye bhi.

Bade models, zyada retrieved context, rerankers, reflection steps aur agent loops aam taur par quality badhaate hain. Saath mein ye cost aur latency bhi badhaate hain. Achhi engineering in trade-offs ko saamne laati hai, inhe imaandaari se naapti hai, aur product ke owners ko soch-samajhkar faisla karne deti hai.

Mushkil hissa ye jaanna hai ki table mein kaun-se differences asli hain. Test set ek sample hota hai, isliye har accuracy figure ke saath ek margin of error hota hai. 150 questions par 86% aur 88% ek hi result hain. Aur agar aap test set par system ke failures padhkar use improve karte ho, toh us set par uska score ab fair estimate nahi rehta.

```flow
title: Faisla karne ka tareeka
Tuning set par options naapo | category ke hisaab se quality, cost, p95
Tuning set par options naapo -> Dominated options drop karo
Dominated options drop karo -> Budgets laagu karo | latency aur cost ceilings
Budgets laagu karo -> Margin ke andar ke gaps ko tie maano
Margin ke andar ke gaps ko tie maano -> Chune hue option ko tune karo
Chune hue option ko tune karo -> Fresh questions par gate pass karo | ek baar chalao
Fresh questions par gate pass karo -> Recommend karo aur date daalo
```

Example mein Hyderabad ki ek health-insurance company hai, jiske call-centre agents live calls ke dauraan ek assistant use karte hain.

## Ye kaam kaise karta hai

### Teenon ko ek hi questions par naapo

Har option ke liye record karo:

- apne eval se quality, category ke hisaab se baantkar (jaise exclusions, claims, premiums, general questions);
- har request ki cost: input aur output tokens guna price, saath mein koi reranker ya router call;
- median aur 95th percentile (p95) par latency, aur time to first token.

Har option ke liye wahi questions, usi order mein use karo, taaki neeche waala paired check kar sako.

### Kya difference asli hai?

n questions par naapi gayi accuracy ek estimate hai. Rough 95% margin of error ye hai:

**margin ≈ 2 × √(p × (1 − p) / n)**

| Accuracy | Questions | Mota-mota margin |
| --- | --- | --- |
| 88% | 150 | ±5.3 points |
| 86% | 200 | ±4.9 points |
| 88% | 470 | ±3.0 points |
| 88% | 1,060 | ±2.0 points |

Margin n ke square root ke hisaab se ghatta hai: ise aadha karne ke liye chaar guna questions chahiye. Isliye 150 questions par two-point gap akele kuch nahi batata.

**Alag-alag nahi, paired compare karo.** Do margins ka overlap hona sawaal ka faisla nahi karta, kyunki dono options ne wahi questions face kiye. Do numbers gino: wo questions jo sirf A ne sahi kiye, aur wo jo sirf B ne sahi kiye. Jo questions dono ne sahi kiye ya dono ne galat kiye, wo difference ke baare mein koi information nahi dete. Agar dono counts ka gap 2 × √(unka sum) se chhota hai, toh difference saabit nahi hua. Jaise, 8 ke muqaable 4 flips ka gap 4 hai, par 2 × √12 lagbhag 7 hai, isliye ye tie hai. 18 ke muqaable 3 mein gap 15 hai aur threshold lagbhag 9: wo difference asli hai. (Ye McNemar test ka rough version hai.)

**Noise floor naapo.** Ek hi option ko ek hi questions par do baar chalao. LLM outputs har run mein badalte hain, aur LLM judges bhi badalte hain. Agar rerun mein 6 answers flip hote hain, toh 6 answers flip karne waale naye option ne kuch saabit nahi kiya.

**Chhoti categories oonche floors saabit nahi kar sakti.** Agar koi option kisi category ke saare 30 questions sahi karta hai, tab bhi asli error rate lagbhag 30 mein 3, yaani 10%, ho sakta hai. Yahi "rule of three" hai: n questions mein zero errors hone par bhi error rate lagbhag 3/n tak ho sakta hai. "Claims par kam se kam 85%" jaisa floor dikhane ke liye pehle se hisaab lagao ki kitne claims questions chahiye, aur utne banao.

### Ek set par tune karo, doosre par gate pass karo

Jab aap test set par failures padhte ho aur unhe theek karne ke liye prompts, routing rules ya thresholds badalte ho, toh fixes us set ki quirks par fit ho jaate hain. Us set par score asli quality se zyada badhta hai. Ek hi set par kai options mein se best chunne ka bhi yahi asar hota hai: jeetne waale ka score kuch had tak luck hai.

Isliye do sets rakho:

- ek **tuning set**, jise aap khulkar dekhte ho, options compare karne aur failures dhoondhne ke liye;
- ek **gate set**, fresh questions ka (jaise haal ki calls se sample kiye hue), jise building ke dauraan koi nahi padhta. Ise ek baar, sign-off par chalao. Agar option fail ho, toh tuning set par theek karo, aur agli koshish se pehle gate ko naye questions se refresh karo. Jo gate aapne padh liya, wo gate nahi raha.

### Nateeje ke hisaab se weight do

Plain accuracy har galat jawaab ko ek jaisa maanti hai. Policy exclusion ke baare mein galat jawaab se complaint aur refund ho sakta hai; office hours ke baare mein galat jawaab ka nuksaan kam hai. Har category ko error ki business cost ke hisaab se weight do, jo client ke apne data se li gayi ho aur product owner ke saath tay hui ho. Jaise, maan lo insurer ke records dikhaate hain ki exclusion ya claims ka galat jawaab lagbhag ₹1,500 ki escalation tak le jaata hai, premiums ki galti lagbhag ₹1,000 aur general galti lagbhag ₹500: toh weights 3, 3, 2 aur 1 bante hain. Weights aur unka source comparison ke saath likho, kyunki weights ranking badal sakte hain.

### Jin options ko koi nahi chunega, unhe drop karo

Koi option **dominated** hai agar koi doosra option quality, cost aur speed par kam se kam utna achha hai, aur kam se kam ek par behtar hai. Dominated options drop karne par **Pareto frontier** bachta hai: asli choices. Quality ko margin dhyaan mein rakhkar padho. Agar do options quality mein noise ke andar hain, toh unhe tie maano, aur cost aur speed faisla karein. Agar faisla margin se chhote quality gap par tika hai, toh jawaab hai aur questions, confident guess nahi.

### Levers aur wo kya badalte hain

| Lever | Quality | Cost | Speed |
| --- | --- | --- | --- |
| Aur bada model | badhti hai | badhti hai | zyada dheema |
| Oonchi reasoning ya effort setting | Mushkil tasks par badhti hai | badhti hai (zyada tokens) | zyada dheema |
| Reranker | badhti hai | thodi badhti hai | thoda zyada dheema |
| Zyada retrieved context | badhti hai, phir ghatti hai | badhti hai | First token zyada dheema |
| Router | Achha route kare toh strong model ke kareeb | ghatti hai | Median zyada tez; p95 slow path ke kareeb |
| Batch API (sirf offline kaam) | wahi | Major providers par lagbhag aadhi | 24 ghante tak |
| Priority ya fast tier | wahi | badhti hai | zyada tez, zyada steady |
| Streaming, prompt caching, aur chhote outputs | wahi | wahi ya ghatti hai | zyada tez, ya tez lagta hai |

Kai reasoning models mein effort setting hoti hai (jaise OpenAI ka `reasoning.effort`). Ye ek hi model ke andar quality ko cost aur latency ke against trade karti hai, isliye do-teen settings ko alag-alag options ki tarah test karo. November 2026 ke hisaab se, OpenAI aur Anthropic ke Batch APIs ruk sakne waali requests ke liye normal keemat ka aadha charge karte hain: nightly summaries ya puraane tickets ko re-score karne ke liye achha, live call par bekaar. Aakhri row ko Caching and speed, Cost control aur Latency budgets and load testing lessons cover karte hain; kisi cheez ke liye paise dene se pehle wo free wins laagu karo.

### Router ko naapo, uski apni cost samet

Router aasaan requests saste model ko aur mushkil requests strong model ko bhejta hai. Paise tabhi bachte hain jab wo achha route kare, aur uski apni costs bhi hain:

- **Misroutes.** Ek sample ko easy ya hard label karo, router chalao, aur gino ki kitne hard questions small model ko gaye (ye quality bigaadte hain) aur kitne easy questions large model ko gaye (ye paisa barbaad karte hain). Pehli tarah waale zyada maayne rakhte hain. Agar kisi high-risk category mein ye aam hai, toh us poori category ko strong model ko bhejo.
- **Overhead.** Routing decision har request par chalta hai. Router ke taur par language-model call apni keemat aur delay jodti hai; simple rules ya chhota embedding classifier kahin zyada saste aur tez hain. Dono haalat mein overhead naapo.
- **Tail.** Agar 30% traffic 3.9 s p95 waale model ko jaata hai, toh router ka p95 small model waala nahi hai. Sabse dheemi 5% requests mein se lagbhag saari slow path se aati hain, isliye blended p95 usi path ke distribution ke andar aata hai.

### Code mein ek comparison

```python
import math

WEIGHTS = {"exclusions": 3.0, "claims": 3.0, "premiums": 2.0, "general": 1.0}

def weighted_quality(results):
    """results: list of (category, correct) pairs; correct is True or False."""
    num = sum(WEIGHTS[c] * ok for c, ok in results)
    den = sum(WEIGHTS[c] for c, _ in results)
    return num / den

def margin(p, n):
    """Rough 95% margin of error for an accuracy p measured on n questions."""
    return 2 * math.sqrt(p * (1 - p) / n)

def paired(a, b):
    """a, b: True/False per question for two options, same questions, same order."""
    a_only = sum(x and not y for x, y in zip(a, b))
    b_only = sum(y and not x for x, y in zip(a, b))
    real = abs(a_only - b_only) > 2 * math.sqrt(a_only + b_only)
    return a_only, b_only, real

def frontier(options):
    """options: dicts with quality, cost_inr and p95_s. Drops dominated options."""
    def dominates(a, b):
        no_worse = (a["quality"] >= b["quality"] and a["cost_inr"] <= b["cost_inr"]
                    and a["p95_s"] <= b["p95_s"])
        better = (a["quality"] > b["quality"] or a["cost_inr"] < b["cost_inr"]
                  or a["p95_s"] < b["p95_s"])
        return no_worse and better
    return [o for o in options if not any(dominates(x, o) for x in options if x is not o)]
```

`margin(0.88, 150)` lagbhag 0.053 return karta hai, yaani 5 points.

### Pehle budgets, phir quality maximise karo

Results dekhne se pehle product owner ke saath do ceilings tay karo: ek latency budget (jaise p95 par pehle shabd 1 s ke andar aur poora reply 4 s ke andar) aur har request ki cost. Frontier ko un options tak filter karo jo dono ke andar hain, phir unmein best quality waala chuno, ties ko ties hi padhte hue. Safety-critical categories ke liye ek minimum quality bhi tay karo jisse neeche koi saving nahi le ja sakti.

## Ek example se samjho

Hyderabad ke insurer ka assistant live calls par agents ke liye policy questions ke jawaab deta hai. Neeche ke saare numbers illustrative hain, method dikhaane ke liye chune gaye hain.

Tay hue budgets: p95 par pehle shabd 1 s ke andar aur poora reply 4 s ke andar, aur har request par zyada se zyada ₹0.40.

**Round 1, 150 questions ke tuning set par:**

| Option | Accuracy | Har request ki cost | p95 latency |
| --- | --- | --- | --- |
| Small model | 76% | ₹0.08 | 1.6 s |
| Large model | 85% | ₹0.60 | 3.9 s |
| Large model + reranker | 89% | ₹0.64 | 4.3 s |
| Router (70% small, 30% large) | 86% | ₹0.24 | 3.0 s |

Router ki cost uske traffic split se nikalti hai: 0.7 × ₹0.08 + 0.3 × ₹0.60, saath mein uske classifier ke liye lagbhag ₹0.002, kul lagbhag ₹0.24. Iska p95 3.0 s hai, small model ke lagbhag dugna, kyunki sabse dheemi 5% requests zyaadatar large model se aati hain.

Team kya nateeja nikaal sakti hai aur kya nahi:

- Akela large model dominated hai: router uski accuracy ke barabar hai aur usse sasta aur tez hai. Use drop karo.
- Small model router se saaf taur par kharaab hai. Paired check mein usne 3 questions sahi kiye jo router se chhoote, aur router ne 18 sahi kiye jo usse chhoote. Wo gap asli hai.
- Large model plus reranker dono budgets todta hai (4.3 s, ₹0.64). Router par uski badhat bhi ±5-point margin ke andar hai: paired check 4 ke muqaable 8 flips dikhata hai, tie.

Router ki galtiyaan padhkar team ne dekha ki wo exclusions aur claims mein ikattha thi. Unhone design badla: saare exclusions aur claims questions reranker waale large model ko jaate hain, aur baaki router sambhaalta hai. Ab 38% traffic strong path leta hai. Unhi 150 questions par isne 88% score kiya, par unhone inhi questions par tune kiya tha, isliye wo figure optimistic hai.

```flow
dir: LR
title: Chuna hua design: har request par lagbhag ₹0.30, 3.5 s p95
Question -> Router | rules aur ek chhota classifier
Router -[general, premiums]-> Small model | 62% traffic
Router -[exclusions, claims]-> Large model + reranker | 38% traffic
```

**Round 2, gate.** Building se pehle unhone ek floor tay kiya tha: exclusions aur claims par kam se kam 85%, margin ke low end se judge kiya jaayega. Ek quick calculation ne dikhaya ki 90% accuracy par 120 high-risk questions se low end sirf lagbhag 84.5% aayega, isliye unhone pichhle mahine ki calls se 400 fresh questions ka gate banaya, jismein 240 exclusions aur claims par the. Tuning ke dauraan kisi ne unhe nahi padha.

| Option | Exclusions aur claims (240) | Baaki (160) | Cost | p95 |
| --- | --- | --- | --- | --- |
| Chuna hua design | 90.0% | 83.8% | ₹0.30 | 3.5 s |
| Har jagah Large + reranker | 90.8% | 86.3% | ₹0.64 | 4.3 s |

High-risk questions par chune hue design ne 240 mein se 216 score kiye; margin lagbhag 86% se 94% tak hai, isliye ye floor paar karta hai. In questions ke liye dono options ek hi path use karte hain, isliye 216 ke muqaable 218 ka gap sirf run-to-run noise se ya router ke inmein se kuch ko galat jagah bhejne se aa sakta hai. Poore 400 par, isne 14 questions sahi kiye jo zyada mehnge option se chhoote, aur 20 chhode jo usne sahi kiye. Lagbhag 12 ke threshold ke muqaable 6 ka gap tie hai. Har request ki cost 0.62 × ₹0.08 + 0.38 × ₹0.64 + ₹0.002 hai, lagbhag ₹0.30.

**Product owner ne jis recommendation par sign kiya:** "Hum router recommend karte hain, saare exclusions aur claims questions large model aur reranker par. 400 fresh questions par isne exclusions aur claims par 90% haasil kiya, tay 85% floor se upar, lagbhag ₹0.30 per request aur p95 par 3.5 s mein. Har jagah reranker waala large model use karne mein 400 questions par koi aisa quality difference nahi dikha jise hum naap sakein, uski cost dugni hai aur wo 4 s budget todta hai. Streaming pehle shabdon ko 1 s ke andar rakhta hai. Prices aur results November 2026 mein naape gaye hain, test set version 2; jab koi provider prices badlega ya naya model ship karega, hum comparison dobaara chalaayenge."

## Aam galtiyaan

- **Chupchaap ek hi dimension optimise karna.** Quality, cost aur speed saath dikhao.
- **Noise ko jeet kehna.** 150 questions par 86% ke muqaable 88% tie hai. Margin aur paired flips do, ya questions jodo.
- **Tuning set par gate pass karna.** Kisi set par fit kiye gaye fixes uska score phula dete hain. Ek fresh gate set rakho aur use ek baar chalao.
- **Sirf overall accuracy.** Category ke hisaab se baanto aur errors ki cost se weight do.
- **Engineer ke gadhe hue weights.** Unhe client ke data se nikaalo aur unka source record karo.
- **Sirf average latency.** p95 aur time to first token report karo.
- **Router ki apni costs bhool jaana.** Uski call, uske misroutes aur uski tail, sab ginti mein aate hain.
- **Dominated options ko meeting mein rakhna**, jahan wo samay barbaad karte hain.
- Comparison par **date, prices ya test-set version na hona**, jisse wo bina kisi ke dhyaan diye puraani ho jaati hai.
- **Product owner ke bina faisla karna.** Trade-off ek business decision hai; table dikhao aur unhe taulne do.

## Jab poori trade-off study zaroori nahi

- **Kam volume.** Agar aapke traffic par sabse strong model ki cost mahine mein kuch sau rupees hai, toh use use karo aur baad mein optimise karo.
- **Ek option har target kaafi gunjaaish ke saath paar karta hai**, apne margin ke low end samet.
- **Early prototypes**, jahan pehle ye seekhna zaroori hai ki task chalta bhi hai ya nahi. Phir bhi jo questions ikattha karo unhe rakho: wahi aapka tuning set banenge.

## Demo se production tak

- **Comparison table rakho**, dates, prices, weights aur tuning aur gate dono sets ke test-set versions ke saath.
- Production mein feature aur category ke hisaab se **quality, har request ki cost aur p95 latency track karo**.
- Har sign-off se pehle haal ke traffic se **gate set refresh karo**, taaki wo usse match kare jo users abhi poochte hain.
- High-risk categories ke liye **minimum quality banaaye rakho**, jisse neeche koi routing change nahi le ja sakta.
- Har mahine category ke hisaab se **router ki galtiyaan naapo**.
- Price changes, naye models aur bade traffic changes par **comparison dobaara chalao**.
