## Ye kya hai

**Continuous integration (CI)** har pull request par checks chalata hai: lint, type checks, unit tests aur AI systems ke liye ek chhota eval. Branch protection ki wajah se fail hone wala change merge ho hi nahi sakta.

**Continuous delivery (CD)** merge hue har change ko apne aap environments se guzaarta hai: image build karo, staging par deploy karo, smoke test karo, phir kisi insaan ke approve karne par production mein promote karo. Agar wo approval step na ho to use **continuous deployment** kehte hain. Banking, insurance aur health ke zyaadatar client teams approval chahte hain.

Dono karne ka ek common tareeka GitHub Actions hai. GitLab CI, Azure DevOps aur Jenkins yahi ideas alag syntax mein use karte hain; client ki apni pasand hogi.

```flow
title: Pull request se production tak
Pull request -> CI: lint, types, tests, smoke eval -> Pass hua?
Pass hua? -[nahi]-> Merge block
Pass hua? -[haan]-> Review karke main mein merge
Review karke main mein merge -> Ek hi image build | tag = commit hash
Ek hi image build -> Staging par deploy -> Staging ka smoke test -> Naamit reviewer ka approval
Naamit reviewer ka approval -> Wahi image production mein promote -> Healthy hai?
Healthy hai? -[nahi]-> Aakhri achha tag redeploy
```

Ye lesson Kochi mein ek insurer ki engineering team ko ek claims assistant handover karne ki kahani follow karta hai.

## Ye kaise kaam karta hai

### Workflow ke parts

| Part | Ye kya hai | Is lesson mein |
| --- | --- | --- |
| Workflow | `.github/workflows/` mein ek YAML file | `ci-cd.yml` aur `rollback.yml` |
| Event | Ise kya start karta hai | Ek pull request, main par push, ek manual run |
| Job | Ek fresh machine (runner) par steps ka group | test, smoke-eval, build, deploy-staging, deploy-production |
| Step | Ek command, ya ek ready-made **action** | `uv run pytest`, `docker/build-push-action` |
| Environment | Apne secrets aur rules wala naam wala deploy target | staging, production |

Jobs parallel chalte hain jab tak ek job doosre ko `needs` na kare. Har job ek saaf machine par start hota hai, isliye use jo bhi chahiye (code, tools, credentials) wo khud fetch karna padta hai.

### Kya kahan chalta hai, aur kitni baar

| Check | Kab | Aam taur par samay | Build fail karta hai? |
| --- | --- | --- | --- |
| Lint, format, type checks | Har pull request par | Ek minute se kam | Haan |
| Fake model ke saath unit tests | Har pull request par | 1 se 3 minute | Haan |
| Smoke eval, 50 golden questions | Prompts, retrieval ya evals chhoone wale pull requests | 2 se 4 minute | Haan, agar main se saaf neeche gire |
| Staging smoke test | Har staging deploy ke baad | Ek minute se kam | Haan, production ko block karta hai |
| Full eval, saikdon cases | Har raat | 10 se 60 minute | Team ko alert karta hai |

Ye samay aam ranges hain, measurements nahi. Table ke peechhe ka rule: check jitna fast aur sasta, wo utna pehle chale.

### Aisa smoke eval jo flake na kare

Model poori tarah repeatable nahi hota, isliye chhota eval usi code par pass bhi ho sakta hai aur fail bhi. 20 questions hon to har question 5 points ka hota hai: ek answer palta to score 0.85 se 0.80 ho jaata hai. Jo gate rerun par palat jaaye, wo logon ko sikhata hai ki green aane tak "Re-run" dabaate raho, aur phir asli failures bhi ignore hone lagte hain. Chaar aadatein ise theek karti hain:

- **Kareeb 50 cases use karein.** Tab har case 5 nahi, 2 points ka hota hai.
- **Temperature 0 use karein** jahan aapka model support kare, aur ek fixed retrieval index.
- **Fail hue case ko ek baar retry karein.** Asli regression dono baar fail hota hai; noise aam taur par nahi.
- **Fixed number se nahi, main se compare karein.** Main ka score `evals/baseline.json` mein store karein (ek nightly job ise refresh kar sakta hai) aur sirf tab fail karein jab pull request 2 cases se zyaada kharab ho. Saath mein ek hard floor bhi rakhein, taaki dheema drift pass na ho jaaye.

Neeche wala `expected in answer` check ek crude smoke test hai: ye un lambe answers ko reward deta hai jinmein wo phrase ittefaq se aa jaaye. Nightly full eval ko zyaada strict grading use karni chahiye. Script apne exit code se faisla karti hai; koi bhi non-zero exit job ko fail kar deta hai.

```python
import argparse, json, sys
from app.answer import answer   # your pipeline, called with temperature 0

p = argparse.ArgumentParser()
p.add_argument("--baseline", default="evals/baseline.json")
p.add_argument("--tolerance", type=int, default=2)   # cases, not percent
p.add_argument("--floor", type=float, default=0.80)
args = p.parse_args()

def ok(case):
    return case["expected"].lower() in answer(case["question"]).lower()

cases = [json.loads(line) for line in open("evals/smoke.jsonl")]
correct = sum(ok(c) or ok(c) for c in cases)          # one retry per failed case
base = json.load(open(args.baseline))["correct"]
print(f"smoke: {correct}/{len(cases)} correct, main has {base}")
failed = correct < base - args.tolerance or correct / len(cases) < args.floor
sys.exit(1 if failed else 0)
```

### Secrets, environments aur OIDC

**Secrets** repository ya environment ki settings mein rehte hain, encrypted aur logs mein masked, repository mein kabhi nahi. Har environment ko uske apne secrets dein, taaki staging ki key kabhi production tak na pahunche. Kisi environment ke secrets tab tak locked rehte hain jab tak required reviewer job ko approve na kare.

**Required reviewers.** Aap chhe logon ya teams tak ke naam de sakte hain; ek approval kaafi hai. Aap deploy start karne wale insaan ko use approve karne se rok bhi sakte hain. GitHub Free, Pro aur Team par required reviewers sirf public repositories mein kaam karte hain; private repositories ke liye GitHub Enterprise chahiye. Approval gate ka promise karne se pehle client ka plan check karein.

**Forks se aaye pull requests ko secrets nahi milte** (ek limited `GITHUB_TOKEN` ke alawa). Isiliye neeche wala smoke eval fork pull requests ko skip karta hai, jinhein phir koi maintainer haath se evaluate karta hai. Workaround ke taur par `pull_request_target` trigger se bachein: ye aapke secrets ke saath chalta hai, isliye usmein kisi fork ka code chalane se koi anjaan insaan unhein padh sakta hai.

**Keys ki jagah OIDC.** `id-token: write` ho to job GitHub se ek signed token maang sakta hai jismein repository aur environment ka naam ho, jaise `repo:kochi-insure/claims-assistant:environment:production`. Cloud sirf unhi tokens par bharosa karta hai jo theek isi naam se match karein, aur aise credentials lautata hai jo expire ho jaate hain, AWS par default roop se ek ghante baad. Leak hone ke liye koi long-lived key hai hi nahi. Azure aur Google Cloud mein bhi yahi pattern hai.

**Registry.** GitHub ki registry (GHCR) mein push karne ke liye sirf `GITHUB_TOKEN` chahiye. Lekin AWS par chal rahi koi service agar private GHCR image pull kare, to use ek stored pull credential chahiye. Agar client AWS par chalta hai, to unki ECR registry mein push karna aksar aasaan hai, kyonki IAM role pehle se pull access deta hai.

### Supply chain: har action ko pin karein

Third-party action aapke code aur secrets ke access ke saath chalta hai. `@v4` jaisa version tag bas ek pointer hai, aur uska owner (ya koi attacker) use move kar sakta hai. March 2025 mein attackers ne popular `tj-actions/changed-files` action ke tags ko aise malicious code par move kar diya jo secrets ko build logs mein print karta tha (CVE-2025-30066). Jo workflows pehle ke kisi commit SHA par pinned the, wo safe code hi chalaate rahe.

Isliye har third-party action ko uske full 40-character commit SHA par pin karein, version ek comment mein likhein, aur Dependabot ko updates propose karne dein (`.github/dependabot.yml` mein `package-ecosystem: "github-actions"` add karein). Update merge karne se pehle diff padhein. 28 November 2026 ko check karte waqt ke do notes:

- `astral-sh/setup-uv` v7 ke baad moving major tags publish nahi karta, isliye `@v10` resolve nahi hoga. Uska apna README ek SHA pin karta hai.
- GitHub ab workflow lockfiles (`.github/workflows/actions.lock`, jo `gh actions-lock` se banti hai) document karta hai, jo aapke actions ke istemaal kiye actions ko bhi pin karti hain. Iski setup guide GitHub Enterprise Cloud ke liye listed hai; baaki plans par SHA pins use karein.

### Speed, cost aur safety switches

- **Caching.** GitHub-hosted runners par `setup-uv` default roop se packages cache karta hai. Doosre tools ke liye lock file par cache karein. Fast CI use hota hai; slow CI bypass hota hai.
- **Concurrency.** Jab koi usi pull request par phir se push kare, to purana run cancel karein. Main par chal raha run kabhi cancel na karein: wo kisi deploy ke beech mein ho sakta hai. Har deploy target ko uska apna concurrency group dein, taaki do deploys kabhi overlap na hon.
- **Timeouts.** Job ka default timeout 360 minute hai. Har job par `timeout-minutes` set karein, taaki atki hui model call chhe ghante ka runner time na jala de.
- **Path filters job ke andar.** Agar aap `on.pull_request.paths` se poora workflow skip karte hain, to usse aane wala required check "Pending" hi rehta hai aur merge ko block karta hai. Isliye smoke eval job hamesha chalta hai aur uske steps check karte hain ki kya badla.
- **Least privilege.** Upar `permissions: {contents: read}` set karein aur sirf wahi add karein jo kisi job ko chahiye, jaise `packages: write` ya `id-token: write`.

### Branch protection

Main ke liye repository ke rules mein, merge se pehle test aur smoke-eval checks ka pass hona aur kam se kam ek review require karein. Iske bina CI bas ek salaah hai.

### Poora workflow

Action versions 28 November 2026 ko check kiye gaye. Chhahon Node 24 runtime declare karte hain.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]

permissions: {contents: read}
concurrency:                       # cancels old pull request runs only
  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: true
env:
  IMAGE: ${{ vars.IMAGE_REPO }}:${{ github.sha }}   # registry names must be lowercase

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: {contents: read, pull-requests: read}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: dorny/paths-filter@ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d # v4.0.3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - if: steps.changed.outputs.ai == 'true'
        uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --tolerance 2
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: docker/login-action@8aa5831fb8d48d8f76594c7ddde61ae58019f550 # v4.8.0
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@c3c9e263c25d99ce0380d002d59b67737d91b0dc # v7.4.0
        with: {context: ., push: true, tags: "${{ env.IMAGE }}"}

  deploy-staging:
    needs: build
    environment: staging
    concurrency: {group: deploy-staging}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"   # health check plus five real questions

  deploy-production:
    needs: deploy-staging
    environment: production          # required reviewers; its own role and secrets
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"   # same image, no rebuild
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"
```

`vars.DEPLOY_ROLE_ARN` aur `vars.BASE_URL` environment variables hain, isliye wahi lines ek job mein staging ki or aur doosre mein production ki or point karti hain.

### Rollback, aur migrations kyon tay karte hain ki ye kaam karega ya nahi

Kyonki har image apne commit se tagged hai, rollback matlab aakhri achhe tag ko redeploy karna. Ise ek manual workflow banayein jo wahi production environment aur approval use kare:

```yaml
name: rollback
on:
  workflow_dispatch:
    inputs:
      sha: {description: "Commit of the last good image", required: true}
permissions: {contents: read, id-token: write}
jobs:
  rollback:
    environment: production
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh "${{ vars.IMAGE_REPO }}:$SHA"
        env: {SHA: "${{ inputs.sha }}"}   # passed as a variable, not pasted into the script
```

App roll back karne se database roll back nahi hota. Agar release 42 kisi column ka naam badalta hai, to release 41 ki image naye schema par crash hogi. Isliye migrations ko deploy se pehle alag step mein chalayein, aur schema ko **expand and contract** steps mein badlein: release ek naya column add karta hai aur dono mein likhta hai; release do naya wala padhta hai; release teen, hafton baad, purana column drop karta hai. Har point par pichhli image abhi bhi kaam karti hai.

**Apne browser mein try karein.** Ye checker bina timeouts wale jobs aur commit SHA par pin na kiye actions dhoondhta hai. Apna workflow paste karke chalaiye.

```python
import re, yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: some-org/setup-thing@v2
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes (the default is 360)")
    for step in job.get("steps", []):
        ref = step.get("uses", "")
        if ref and not ref.startswith("./") and not re.fullmatch(r"[0-9a-f]{40}", ref.split("@")[-1]):
            print(f"{name}: pin {ref} to a full commit SHA")
```

## Ek worked example

Aap claims assistant ko Kochi ke insurer ki engineering team ko handover kar rahe hain. Unki lead, Anjali, chahti hain ki har change test ho aur unki team ke sign-off ke bina production mein kuch na jaaye. Insurer private repositories ke saath GitHub Enterprise Cloud use karta hai, isliye required reviewers available hain. Aap upar wale dono workflows set up karte hain. Neeche ke numbers bas ye dikhane ke liye hain ki gates kaise behave karte hain.

**Day 1: set up.** Aap staging aur production environments banate hain. Production mein Anjali aur unke deputy reviewers hain, self-review blocked hai. AWS mein aap do IAM roles banate hain. Production role sirf `repo:kochi-insure/claims-assistant:environment:production` par bharosa karta hai. Aap wo purani access key delete karte hain jo ek contractor `.env` file mein chhod gaya tha. Aap main ka smoke score `evals/baseline.json` mein record karte hain: 50 mein se 46.

**Week 2: ek prompt change.** Ek teammate tokens bachaane ke liye system prompt chhota karta hai. `prompts/` badla hai, isliye smoke eval chalta hai. First pass: 50 mein se 39. 11 failures mein se do retry par pass hote hain, to score 50 mein se 41 (0.82) hai. Ye main ke 46 se 5 cases kam hai, tolerance 2 se zyaada, isliye check fail hota hai aur pull request merge nahi ho sakta. 0.80 ka fixed threshold hota to ye nikal jaata. Teammate policy numbers ke baare mein do sentences wapas daalta hai, 45 score karta hai, aur merge karta hai.

**Week 5: ek slow release.** Ek nayi retrieval setting har check pass karti hai lekin production mein answers slow kar deti hai. Anjali rollback workflow kholti hain, pichhla commit hash paste karti hain aur approve karti hain. Aakhri achhi image kareeb do minute mein wapas aa jaati hai, bina rebuild ke. Us release ne bas ek column add kiya tha, isliye purani image database ke saath theek chalti hai.

**Insurer ke liye kya badla.** Pehle deploys kisi laptop se hote the, aur kisi ko pakka nahi pata tha ki kaun sa version live hai. Ab har production version ek commit hash hai jiske saath ek naamit approver hai. Jab koi claims manager kisi kharab answer ki report karta hai, to team theek-theek bata sakti hai ki kis code aur prompt ne use banaya.

## Aam galtiyan

- **Sirf main par CI.** Problems merge ke baad pata chalti hain. CI ko pull requests par chalaiye aur required check banaiye.
- **Fixed threshold ke saath chhota sa eval.** Ye flake karta hai, aur log green aane tak rerun karna seekh jaate hain. Kareeb 50 cases, temperature 0, ek retry use karein, aur main se compare karein.
- **Har push par paid evals.** Smoke eval sirf tab chalayein jab prompts, retrieval ya evals badlein; full suite har raat chalayein.
- **Path filter se poora workflow skip karna.** Uske required checks Pending hi rehte hain. Job ke andar filter karein.
- **Files mein secrets, ya long-lived cloud keys ko secrets banana.** Environment secrets use karein, aur cloud access ke liye OIDC.
- **Har environment ke liye rebuild.** Ek baar build karein, wahi image promote karein.
- **Tag se pinned third-party actions.** Tags move hote hain. Full SHAs pin karein aur Dependabot ko updates propose karne dein.
- **Poore workflow par cancel-in-progress.** Ek naya merge deploy ko beech mein maar deta hai. Sirf pull request runs cancel karein.
- **Koi timeouts nahi.** Atka hua job chhe ghante tak chalta hai.
- **Aisa rollback jo kisi ne try nahi kiya, ya aisa migration jo use tod de.** Rollback practice karein, aur expand and contract use karein.
- **Flaky tests ko waise hi chhod dena.** Unhein jaldi fix karein ya hatayein, warna asli failures bhi ignore hone lagte hain.

## Kab halki pipeline kaafi hai

- **Personal project**: pull requests par lint aur tests kaafi hain.
- **Built-in deploys wale platforms**, jaise Vercel previews, jahan CI ko sirf checks chahiye.
- **Notebooks aur research code** jo kabhi deploy nahi hote.

## Demo se production tak

Aapki pipeline take over karne se pehle client ka engineering lead ye check karega:

- **Main protected hai**: required checks aur kam se kam ek review.
- **Production ko approval chahiye**, uske apne secrets hain aur ek role hai jo sirf usi environment par bharosa karta hai.
- **Koi long-lived cloud keys nahi** GitHub mein kahin bhi.
- **Har action pinned hai** commit SHA par, Dependabot on ke saath.
- **AI gate stable hai**, ek baseline aur ek nightly full eval ke saath.
- **Rollback likha hua hai aur chalaya ja chuka hai**, aur migrations expand and contract follow karte hain.

## Practice

GitHub ka Actions quickstart aur deployment environments wala page follow karein. Ek public repository use karein, taaki free account par required reviewers kaam karein.

1. Ek workflow add karein jo har pull request par lint aur tests chalaye, aur use main par required check banayein.
2. Har action ko commit SHA par pin karein aur `github-actions` ke liye ek Dependabot file add karein.
3. Ek job add karein jo main par merge hone par aapki Docker image ko commit hash se tag karke build aur push kare.
4. Staging aur production environments banayein, production ke liye khud ko required reviewer ke taur par add karein, aur wahi image dono par deploy karein.
5. In-job path filter ke saath smoke eval add karein. Do pull requests kholkar dikhayein ki ye ek baar chalta hai aur ek baar skip hota hai.
6. Pichhli image redeploy karne ke liye rollback workflow chalayein.

**Aapka kaam poora hai jab aap** CI se block hua ek failing pull request, production se pehle ek approval gate, aur khud kiya hua ek rollback dikha sakein.
