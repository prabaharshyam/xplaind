## Ye kya hai

**Continuous integration (CI)** har change par checks chalata hai: lint, type checks, unit tests, aur AI systems ke liye ek chhota eval suite. Jo change fail ho, wo merge nahi hota.

**Continuous delivery (CD)** merge hue change ko apne aap environments se guzaarta hai: image build karo, staging mein deploy karo, smoke tests chalao, phir production mein deploy karo, aksar kisi insaan ke approve karne ke baad.

GitHub Actions dono ka ek common tareeka hai. Workflows `.github/workflows/` mein YAML files hoti hain jo pull request ya main par push jaise events par chalti hain. GitLab CI, Azure DevOps aur Jenkins bhi isi tarah kaam karte hain; clients ki apni choice hogi.

```flow
Pull request -> CI: lint, types, tests, smoke eval -> Pass?
Pass? -[nahi]-> Block ho gaya
Pass? -[haan]-> Merge ho sakta hai -> Main mein merge
Main mein merge -> Image build karo | tag = commit hash
Image build karo -> Staging mein deploy -> Smoke tests -> Named reviewer ka approval -> Wahi image production mein deploy -> Problem?
Problem? -[haan]-> Pichhla tag dobara deploy karo
```

Ye lesson Kochi ke ek insurer ki engineering team ko claims assistant ke handover ke saath chalta hai.

## Ye kaam kaise karta hai

**Triggers aur jobs.** Ek workflow events par chalta hai (`pull_request`, main par `push`, ek tag, ek manual dispatch). Isme jobs hote hain; har job ek nayi machine par steps chalata hai, jise runner kehte hain.

**CI job** code checkout karta hai, dependencies install karta hai (caching ke saath), lint, types aur tests chalata hai. AI app ke liye, ek chhota, tez eval jodo: ek fixed retrieval index par 20 golden questions, aur accuracy threshold se neeche gire toh build fail kar do. Slow, mehnge evals ko nightly job ke liye rakho.

**Build job** Docker image build karta hai, use commit hash se tag karta hai aur client ke registry mein push karta hai.

**Deploy jobs** **environments** use karte hain. `staging` environment apne aap deploy hota hai; `production` environment ke liye ek named reviewer ka approval chahiye aur uske apne secrets hote hain. Secrets CI system mein store hote hain ya run time par cloud se liye jaate hain; repository mein kabhi nahi. Aur behtar, stored keys ki jagah runner ko OpenID Connect ke zariye chhoti umr ke credentials se cloud mein sign in karne do.

**Rollback.** Kyunki har deploy commit se tag ki hui image use karta hai, roll back karne ka matlab pichhla tag dobara deploy karna hai. Ise ek button ya command banao aur practice karo.

**Kya kahan chalta hai, aur kitni baar:**

| Check | Kab | Typical time | Build fail karta hai? |
| --- | --- | --- | --- |
| Lint aur format | Har PR | Seconds | Haan |
| Type checks | Har PR | Ek minute se kam | Haan |
| Fake model ke saath unit tests | Har PR | 1 se 3 minute | Haan |
| Smoke eval, 20 golden questions | Har PR jo prompts ya retrieval ko chhuti hai | 1 se 2 minute | Haan, threshold se neeche |
| Full eval, sainkdon cases | Nightly | 10 se 60 minute | Team ko alert |
| Load test | Bade releases se pehle | Alag-alag | Bahut slow ho toh release rokta hai |

**Caching.** Har run par dependencies install karna slow hai. Unhe cache karo, lock file par key karke, taaki CI dus minute ki jagah kuch minute le. Tez CI use hota hai; slow CI ko log bypass kar dete hain.

**Branch protection.** Repository settings mein, main mein merge karne se pehle CI job pass hona aur kam se kam ek review zaroori karo. Iske bina CI sirf salaah hai.

**Practice mein secrets.** Workflow ko kuch secrets chahiye: smoke eval ke liye ek model API key, images push karne ke credentials, deploy karne ke credentials. Unhe repository ya environment ki secret settings mein store karo, jahan wo encrypted hote hain aur logs mein chhupe rehte hain. Har environment ko apne secrets do, taaki staging key kabhi production ko chhoo na sake. Cloud access ke liye OpenID Connect ko tarjeeh do: cloud us khaas repository aur branch par bharosa karta hai, aur ek aisa credential deta hai jo thodi der baad expire ho jaata hai, aksar ek ghante mein. Phir leak hone ke liye koi lambe samay ki key hi nahi hoti.

**Ek poora workflow.** Har pull request par CI, sirf jab AI files badlein tab smoke eval, aur main par build plus deploy:

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: {enable-cache: true}
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - uses: astral-sh/setup-uv@v5
        if: steps.changed.outputs.ai == 'true'
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --min-accuracy 0.85
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@v6
        with: {push: true, tags: "ghcr.io/${{ github.repository }}:${{ github.sha }}"}

  deploy-production:
    needs: build
    runs-on: ubuntu-latest
    environment: production                    # requires a reviewer's approval
    permissions: {id-token: write, contents: read}
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh ghcr.io/${{ github.repository }}:${{ github.sha }}
```

Production job ko cloud access OIDC se milta hai (`id-token: write` aur ek role jis par cloud bharosa karta hai), isliye GitHub mein koi lambe samay ki cloud keys nahi rehti. Azure aur Google Cloud ke paas bhi aise hi login actions hain.

**Smoke eval script apne exit code se decide karta hai.** Koi bhi non-zero exit job ko fail karta hai:

```python
import argparse, json, sys
from app.answer import answer                 # your pipeline

p = argparse.ArgumentParser(); p.add_argument("--min-accuracy", type=float, default=0.85)
args = p.parse_args()
cases = [json.loads(l) for l in open("evals/smoke.jsonl")]
correct = sum(c["expected"].lower() in answer(c["question"]).lower() for c in cases)
acc = correct / len(cases)
print(f"smoke accuracy {acc:.0%} on {len(cases)} cases")
sys.exit(0 if acc >= args.min_accuracy else 1)
```

**Actions ko pin karo.** Third-party actions aapki repository ke access ke saath chalte hain. Unhe ek version par (ya zyada sakht setups mein poore commit hash par) pin karo aur updates review karo, taaki koi compromised action aapki pipeline mein na ghus sake.

**Purane runs cancel karo.** `concurrency` block usi branch par dobara push karne par purana run cancel kar deta hai, jisse runner minutes aur model calls bachte hain.

**Apne browser mein try karo.** Ek workflow mein unpinned actions aur missing timeouts check karo. YAML badlo aur chalao.

```python
import yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: some-org/setup-thing@main
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes so a stuck job cannot run for hours")
    for step in job["steps"]:
        ref = step.get("uses", "")
        if ref and ref.split("@")[-1] in ("main", "master"):
            print(f"{name}: pin {ref} to a version, not a branch")
```

## Ek example se samjho

Aap ek claims-assistant Kochi ke ek insurer ki engineering team ko handover karte ho. Unki lead Anjali chahti hai ki har change tested ho aur unki team ke sign-off ke bina production mein kuch na jaaye.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q
      - run: uv run python evals/smoke.py --min-accuracy 0.85
  deploy-staging:
    if: github.event_name == 'push'
    needs: test
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/build_push_deploy.sh staging ${{ github.sha }}
  deploy-production:
    needs: deploy-staging
    environment: production        # requires approval from the insurer's leads
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy.sh production ${{ github.sha }}   # same image, no rebuild
```

Ek hafte baad ek teammate prompt badalta hai aur smoke eval 0.89 se 0.78 par gir jaata hai; CI fail hota hai aur PR merge nahi ho sakta. Baad mein ek production deploy se responses slow ho jaate hain; Anjali workflow page se pichhle commit ki image do minute mein dobara deploy kar deti hai, zyadatar users ke notice karne se pehle.

**Insurer ki team ke liye kya badla.** Pipeline se pehle, deploys tab hote the jab kisi ko yaad aata tha, laptop se, aur kisi ko pakka nahi pata tha ki kaunsa version live hai. Uske baad, har production version ek commit hash hai jo workflow page par dikhta hai, har deploy ka ek named approver hai, aur smoke eval ne do mahine mein teen prompt changes roke hain jo har ek answer quality ghatata. Anjali kehti hain sabse kaam ki cheez speed nahi, yakeen hai: jab koi claims manager kharab answer report karta hai, team bilkul bata sakti hai ki kaunse code aur prompt ne use banaya.

## Aam galtiyaan

- **Sirf main par tests.** Problems merge ke baad pakdi jaati hain. Pull requests par CI chalao.
- **Prompt changes ke liye CI mein eval nahi.** Prompt edits code changes hain; unhe test karo.
- **Workflow files mein secrets.** CI system ke secrets ya chhoti umr ke cloud credentials use karo.
- **Har environment ke liye alag images build karna.** Ek baar build karo, wahi image staging se production tak promote karo.
- **Ek rollback jo kisi ne try nahi kiya.** Zaroorat padne se pehle practice karo.

- **Flaky tests ko chhod dena.** Ek test jo random fail hota hai, logon ko sikhata hai ki CI tab tak dobara chalao jab tak pass na ho, aur phir asli failures bhi ignore ho jaati hain. Flaky tests ko jaldi fix ya remove karo.
- **Bina budget ke har PR par live model call karne waale evals.** PR eval ko chhota aur sasta rakho, jo ho sake cache karo, aur poora suite schedule par chalao.
- **Jab OIDC available hai tab lambe samay ki cloud keys secrets mein store karna.**
- **Har push par paid evals chalana**, sirf relevant changes par nahi.
- **Unpinned third-party actions.**

## Jab halki pipeline kaafi hai

- **Ek personal project**: push par lint aur tests kaafi hain.
- **Built-in deploys waale platforms**, jaise Vercel previews, jahan CI ko sirf checks chahiye.
- **Notebooks aur research code** jo kabhi deploy nahi hote.

## Demo se production tak

- **Main mein merge se pehle CI aur review zaroori karo.**
- **Environments use karo** approvals ke saath aur production ke liye alag secrets ke saath.
- **OIDC se deploy karo**, stored cloud keys se nahi.
- **AI changes ko** smoke eval se gate karo aur poora eval nightly chalao.
- **Pichhle image tag par rollback ki practice karo.**

## Practice karo

GitHub ka Actions quickstart aur deployment environments ka page follow karo.

1. Apni kisi repository mein ek workflow jodo jo har pull request par lint aur tests chalaye.
2. Ek job jodo jo main par merges par aapki Docker image build karke commit hash se tag karke push kare.
3. Staging aur production environments banao, production ke liye apna approval zaroori karo, aur pichhli image par rollback ki practice karo.
4. Paths filter jodo taaki aapka smoke eval sirf tab chale jab prompts ya retrieval code badle, aur do pull requests kholo jo ek baar chalta aur ek baar skip hota dikhayein.

**Aapka kaam poora jab:** aap CI se block hui ek failing PR, production se pehle ek approval gate, aur aapka kiya hua ek rollback dikha sako.
