## Ye kya hai

**Feature engineering** ka matlab hai raw data se model ke inputs banaana. Model kisi transactions table ko waise nahi padh sakta jaise insaan padhta hai. Use har us cheez ke liye ek row chahiye jiske baare mein aap predict karte ho (yahaan, ek date par ek customer), aur aise columns jo past ka saar batayein: "pichhle 30 dinon mein orders", "aakhri order ke baad kitne din", "haal ke orders mein late delivered ka hissa".

Achhe features wo pakadte hain jo koi domain expert dekhta, aisi shakl mein jise model use kar sake. Tabular data par aksar zyaadatar accuracy yahin se aati hai.

Har feature ka ek **prediction time** hota hai: wo pal jab model se sawaal poochha jaata. Usse pehle ki har cheez use ho sakti hai. Uske baad ki har cheez future hai, aur label wahin rehta hai.

```flow
dir: LR
title: Prediction time: 00:00 IST, 1 November
1 Nov se pehle ke events | orders, ratings, tickets -> 1 Nov ke hisaab se features | counts, trends, recency
1 Nov ke hisaab se features -[model]-> Label: 1 se 14 Nov ke beech order kiya | kisi feature mein kabhi use nahi hota
```

Ye lesson Bengaluru ki ek food-delivery company ke saath chalta hai jo predict karti hai ki kaun-se customers 14 dinon ke andar phir se order karenge.

## Ye kaise kaam karta hai

### Ek hi niyam: sab kuch prediction time ke hisaab se compute karo

**Leakage** tab hota hai jab kisi feature mein aisi jaankaari ho jo prediction time par model ke paas nahi hoti. Isse validation scores shaandaar dikhte hain aur production ke nateeje niraash karte hain. Teen aadatein iska zyaadatar hissa rok deti hain.

1. **Cutoff se poori tarah pehle ka hi filter karo.** `ts < cutoff` use karo, `<=` nahi. Jis event par theek cutoff ka time stamp hai, wo prediction ke baad bhi hua ho sakta hai.
2. **Dheere-dheere badalne waali tables ko cutoff ke hisaab se join karo.** Ratings, loyalty tier ya credit limit ke liye, cutoff se pehle ki latest value lo, aaj ki latest value nahi. Pandas mein `merge_asof` ye karta hai:

```python
import pandas as pd

labels = pd.DataFrame({"customer": [1, 1, 2], "cutoff": pd.to_datetime(["2026-09-01", "2026-10-01", "2026-10-01"])})
ratings = pd.DataFrame({"customer": [1, 1, 2, 2],
                        "rated_at": pd.to_datetime(["2026-08-20", "2026-10-01", "2026-09-15", "2026-10-03"]),
                        "rating": [5, 2, 4, 1]})
joined = pd.merge_asof(labels.sort_values("cutoff"), ratings.sort_values("rated_at"),
                       left_on="cutoff", right_on="rated_at", by="customer",
                       allow_exact_matches=False)     # strictly before the cutoff
print(joined)
```

1 October ke cutoff par customer 1 ko 20 August waali 5 ki rating milti hai. 1 October ko hi di gayi 2 ki rating baahar rehti hai, aur customer 2 ki 3 October waali rating bhi.

3. **Baad ke time period par validate karo.** Kai cutoffs par training rows banao (har mahine ek), pehle waalon par train karo aur baad waalon par test karo. Random split future ki rows ko training mein mila deta hai, isliye leaks aur thode samay ke patterns skill jaise dikhte hain.

### Feature families

| Raw data | Example features | Ye kyun madad karta hai |
| --- | --- | --- |
| Orders | Pichhle 7, 30 aur 90 dinon ke orders aur spend; aakhri order ke baad kitne din | "Kya wo waapas aayenge" ke liye habit aur recency sabse mazboot signals hain |
| Changes | 30 din ka average basket banaam 90 din ka average; is mahine banaam pichhle mahine | Dheere-dheere door hote customers ko pakadta hai |
| Ratios | EMI banaam income, har order par returns, category average ke muqaable price | Alag-alag logon ke amounts ko ek tulna laayak scale par laata hai |
| Service | Pichhle 30 dinon mein late deliveries ka hissa; aakhri rating; haal ke tickets | Wo bure anubhav pakadta hai jo logon ko competitors ki taraf dhakelte hain |
| Calendar | Hafte ka din, salary week, agle tyohaar tak kitne din | Bhaarat mein demand aur payments tyohaaron aur pay cycles ke saath chalte hain |
| Categories | City tier, channel, PIN code | Alag groups alag tarah se behave karte hain; encoding chahiye (neeche dekho) |
| Text aur location | Keyword flags, text embeddings; sabse nazdeeki kitchen tak ki doori | Unstructured data ko numbers mein badalta hai |

**Experts se shuru karo.** Business chalaane waalon se poochho: "Aapko kis baat se lagta hai ki koi customer chhodne waala hai?" Delivery managers late deliveries batayenge; finance waale payday timing batayenge. Phir har idea ko measure karo, kyunki samajhdaari bhara idea bhi kuch na jode, aisa ho sakta hai (worked example mein aisa ek dikhta hai).

### Numeric transforms

- **Missing values.** Tay karo ki gap ka matlab kya hai. "30 dinon mein koi order nahi" asli zero hai; "kabhi koi order nahi" mein average undefined ho jaata hai. Asli zeros ko 0 se bharo, aur jahaan kuch na hona khud ek jaankaari hai wahaan ek missing flag (`never_ordered = 1`) jodo. scikit-learn ka `HistGradientBoostingClassifier` missing values seedhe accept karta hai.
- **Skewed amounts.** Rupees mein spend long-tailed hota hai: zyaadatar customers kuch hazaar kharch karte hain, kuch log laakhon. Linear models aur neural networks ke liye `log1p(amount)` use karo.
- **Scaling.** Linear models, k-nearest neighbours aur neural networks ke liye standardise karo. Tree models order ke hisaab se split karte hain, isliye scaling se unke liye kuch nahi badalta.
- **Interactions.** Trees interactions khud dhoondh lete hain. Linear models ke liye inhe likhkar dena padta hai, jaise `late_share × orders_30d`.

### Categories

- **Kam values** (city tier, channel): one-hot encoding, aur rare values ko "other" mein group kar do.
- **Bahut saari values** (PIN code, restaurant ID): frequency encoding, target encoding, ya **hashing trick** (`FeatureHasher` har value ko tay sankhya waale columns mein se kisi ek par map karta hai; collisions se thodi accuracy jaati hai par memory fixed rehti hai). Millions IDs ke liye deep models har ID ka ek **embedding** seekhte hain.

**Target encoding** har category ki jagah uska average label rakh deta hai. Ye powerful hai aur ismein leak hona aasaan hai. Agar averages saari rows par compute karo, toh har row ka apna label uske feature ke andar hota hai. Neeche ka demo PIN codes ko koi asli signal nahi deta:

```python
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import TargetEncoder
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.metrics import roc_auc_score

rng = np.random.default_rng(0)
df = pd.DataFrame({"pin_code": rng.integers(0, 2000, 6000).astype(str),
                   "y": rng.random(6000) < 0.3})          # pin code carries NO real signal

# Wrong: encode with means from ALL rows, then split
df["pin_mean"] = df.groupby("pin_code").y.transform("mean")
tr, te = train_test_split(df, test_size=0.3, random_state=0)
m = LogisticRegression().fit(tr[["pin_mean"]], tr.y)
print("encoded before split:", round(roc_auc_score(te.y, m.predict_proba(te[["pin_mean"]])[:, 1]), 2))

# Right: the encoder lives inside the pipeline and is fitted on training rows only
pipe = make_pipeline(TargetEncoder(), LogisticRegression()).fit(tr[["pin_code"]], tr.y)
print("encoded after split :", round(roc_auc_score(te.y, pipe.predict_proba(te[["pin_code"]])[:, 1]), 2))
```

Galat tareeke ke liye ye 0.85 print karta hai aur sahi tareeke ke liye lagbhag 0.5 (exact value har run mein thodi badalti hai): shuddh noise ek mazboot feature jaisa score ho gaya. scikit-learn ka `TargetEncoder` `fit_transform` ke andar cross-fit bhi karta hai, isliye training rows bhi kabhi apna label nahi dekhtin. Yahi niyam scalers, imputers aur feature selection par bhi laagu hota hai: inhe split ke baad, pipeline ke andar fit karo. Ye demo random split sirf isliye use karta hai kyunki data mein koi time order nahi hai.

### Calendar features

```python
import pandas as pd

# In production this is a reviewed data file, one row per festival, year and region
festivals = pd.DataFrame([
    ("onam", "2026-08-26", "kerala"),          # Thiruvonam day
    ("dussehra", "2026-10-20", "all"),
    ("diwali", "2026-11-08", "all"),
], columns=["festival", "date", "region"]).assign(date=lambda d: pd.to_datetime(d.date))

def calendar_features(dates, region):
    d = pd.Series(pd.to_datetime(dates))
    fest = festivals[festivals.region.isin([region, "all"])].date
    gap = d.apply(lambda x: min(((f - x).days for f in fest if f >= x), default=60))
    return pd.DataFrame({"date": d, "dow": d.dt.day_of_week, "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": gap.clip(upper=60)})

print(calendar_features(["2026-08-20", "2026-10-15", "2026-11-03"], "kerala"))
```

Festival dates har saal badalti hain, aur kuch (jaise Eid) chaand dikhne par nirbhar karti hain, isliye official lists ke beech dates mein ek din ka farq ho sakta hai. Ek region column rakho aur table ko har saal official holiday lists se update karo.

### Training-serving consistency

**Training-serving skew** tab hota hai jab production kisi feature ko training se alag tareeke se compute karta hai. Aam wajahein: serving mein UTC days aur training mein IST days, "active customer" ki alag definition, ya aisi serving query jo data ka aakhri ghanta miss kar deti hai. Model crash nahi hota; bas chupchaap kharaab hota jaata hai.

```flow
dir: LR
title: Ek feature function, do callers
Raw events -> features_as_of | ek tested function
features_as_of -[kai past cutoffs]-> Training rows
features_as_of -[cutoff = now]-> Live features
```

Feature code ek baar likho aur dono jagahon se call karo, aur encoders ko model pipeline ke andar rakho taaki fitted objects model ke saath hi chalein. Bade scale par, Feast (open source) jaisa koi **feature store** ye aapke liye karta hai. Ye point-in-time join se training sets banaata hai (har label ke timestamp par ya usse pehle ki latest feature value), fresh values ko ek tez online store mein copy karta hai (ise materialisation kehte hain), aur prediction time par wahi values serve karta hai.

### Features chunna

Zyada features hamesha behtar nahi hote. Har ek ke saath maintain karne ko ek pipeline aati hai aur leak hone ka ek mauka. Groups mein measure karo (counts, recency, service, calendar), do tareekon se: har group ko ek simple baseline mein jodkar, aur har group ko full set se hatakar. Features aksar overlap karte hain, isliye kisi group ko akele jodne se faayda ho tab bhi use hataane se shaayad zyada nuksaan na ho. Wahi groups rakho jinka gain kai test months mein dohraaya jaaye.

## Ek worked example

Bengaluru team ka sawaal: har monthly cutoff ke baad ke 14 dinon mein kya koi customer order karega? Neeche ka code synthetic data use karta hai, taaki aap ise chala sako, numbers dekh sako aur ise todkar bhi dekh sako. Ismein do effects plant kiye gaye hain: aadhe customers kisi samay dheere-dheere door hone lagte hain (pehle chhote baskets, phir do mahine baad kam orders), aur ek mahine mein do late deliveries kisi customer se app badalwa sakti hain.

```python
import numpy as np, pandas as pd
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

# 1. Synthetic orders for 3,000 customers, January to October 2026, with two planted effects
rng = np.random.default_rng(7)
N, days = 3000, pd.date_range("2026-01-01", "2026-10-31")
base = rng.gamma(2, 0.06, N)                             # usual daily chance of ordering
late_p = np.where(rng.random(N) < 0.3, 0.3, 0.05)        # 30% live where deliveries run late
drift = np.where(rng.random(N) < 0.5, rng.integers(30, 270, N), 9999)  # day a customer starts drifting
late_log, left, rows = np.zeros((len(days), N), bool), np.zeros(N, bool), []
for t, day in enumerate(days):
    shrink = np.clip(1 - (t - drift) / 60, 0.4, 1)       # drifters first buy smaller baskets,
    fade = np.clip(1 - (t - drift - 60) / 20, 0.05, 1)   # then two months later stop ordering
    left |= (late_log[max(0, t - 30):t].sum(0) >= 2) & (rng.random(N) < 0.03)  # 2 late orders: may switch apps
    ordered = rng.random(N) < base * fade * np.where(left, 0.1, 1)
    late_log[t] = ordered & (rng.random(N) < late_p)
    for c in np.flatnonzero(ordered):
        rows.append((c, day, round(rng.gamma(4, 100) * shrink[c]), late_log[t, c]))
orders = pd.DataFrame(rows, columns=["customer", "ts", "amount", "late"])

# 2. Features as of a cutoff, from orders strictly before it
def features_as_of(orders, cutoff):
    past, out = orders[orders.ts < cutoff], {}
    for d in (7, 30, 90):
        g = past[past.ts >= cutoff - pd.Timedelta(days=d)].groupby("customer")
        out[f"orders_{d}d"], out[f"spend_{d}d"] = g.size(), g.amount.sum()
        if d == 30: out["late_share_30d"] = g.late.mean()
    out["days_since_last"] = (cutoff - past.groupby("customer").ts.max()).dt.days
    f = pd.DataFrame(out).reindex(range(N))
    f = f.fillna({c: 0 for c in f if c.startswith(("orders_", "spend_"))})
    f["basket_change"] = (f.spend_30d / f.orders_30d) / (f.spend_90d / f.orders_90d)  # NaN if no orders
    return f                                              # trees accept NaN; it means "no recent orders"

# 3. One row per customer per monthly cutoff; label = ordered in the 14 days after it
def labelled(cutoff):
    X = features_as_of(orders, cutoff)
    nxt = orders[(orders.ts >= cutoff) & (orders.ts < cutoff + pd.Timedelta(days=14))]
    X["leaky_orders_7d"] = features_as_of(orders, cutoff + pd.Timedelta(days=7)).orders_7d  # bad join
    return X, X.index.isin(nxt.customer).astype(int)

def stack(months):
    parts = [labelled(pd.Timestamp(f"2026-{m:02d}-01")) for m in months]
    return pd.concat([x for x, _ in parts]), np.concatenate([y for _, y in parts])

Xtr, ytr = stack(range(4, 9))     # train on April to August cutoffs
Xte, yte = stack([9, 10])         # test on later months, never a random split

def auc(cols):
    m = HistGradientBoostingClassifier(random_state=0).fit(Xtr[cols], ytr)
    return round(roc_auc_score(yte, m.predict_proba(Xte[cols])[:, 1]), 3)

full = [c for c in Xtr if c != "leaky_orders_7d"]
print("orders_30d only     ", auc(["orders_30d"]))
for name, extra in [("+ 7 and 90 day counts", ["orders_7d", "orders_90d"]), ("+ recency", ["days_since_last"]),
                    ("+ basket change", ["basket_change"]), ("+ late share", ["late_share_30d"])]:
    print(name.ljust(20), auc(["orders_30d"] + extra))
print("all features        ", auc(full))
print("all + leaky feature ", auc(full + ["leaky_orders_7d"]))
```

Leaky column ek asli bug ki nakal karta hai: ek weekly table jiski key hafte ka aakhri din thi, use cutoff se aise join kiya gaya jaise key pehla din ho, isliye "pichhle 7 din" chupchaap "agle 7 din" ban gaye.

Ye kya print karta hai (September aur October cutoffs par test AUC; synthetic data hai, isliye inhe sirf udaaharan samjho):

| Features | Test AUC |
| --- | --- |
| Sirf pichhle 30 dinon ke orders | 0.803 |
| + 7-din aur 90-din ki counts | 0.832 |
| + aakhri order ke baad kitne din | 0.818 |
| + basket change | 0.807 |
| + late-delivery share | 0.805 |
| Saare honest features | 0.848 |
| Saare, + leaky join | 0.935 |

Paanch doosre seeds ke saath dobaara chalaane par bhi yahi pattern aata hai, har number lagbhag 0.01 oopar-neeche hota hai.

**Numbers kya sikhaate hain.**

- **Bhaari kaam windows aur recency karte hain.** Ek akela 30-din count "pichhle hafte do baar order kiya" aur "ek mahine pehle do baar order kiya" mein farq nahi kar sakta. 7-din aur 90-din ke windows jodne se model ko ek trend milta hai, aur aakhri order ke baad ke din use timing dete hain.
- **Asli wajah bhi kam hi jod sakti hai.** Is data mein late deliveries sach mein customers ko bhagaati hain, kyunki simulation mein yahi likha hai. Phir bhi late-share feature akele lagbhag kuch nahi jodta: kisi bhi 14-din ke window mein ye kuch hi customers par asar daalta hai, aur jo pehle hi ja chuke hain wo kam orders ke roop mein dikh jaate hain. Basket change bhi aisa hi karta hai. Meeting mein samajhdaar lagne waale ideas ko bhi test mein apni jagah kamaani padti hai.
- **Leak zor se dikhta hai.** Ek column se 0.85 se 0.93 ka jump hi warning hai. Ise dhoondhne ke liye sabse naye columns ko ek-ek karke hatao, phir us join ko padho jisne winner banaaya.

## Aam galtiyaan

- **Cutoff par ya uske baad ke events use karna.** `ts < cutoff` se filter karo, aur dheere-dheere badalne waali tables ko "aaj ki latest value" se nahi, as-of join se join karo.
- **Time-ordered data par random splits.** Ek hi customer kai cutoffs par aata hai, aur future training mein leak ho jaata hai. Pehle ke mahinon par train karo, baad ke mahinon par test karo.
- **Split se pehle encoders, scalers ya imputers fit karna.** Inhe pipeline ke andar rakho taaki ye sirf training rows par fit hon.
- **Training aur serving ke liye alag feature code.** Do versions dheere-dheere alag ho jaate hain (UTC banaam IST, "active" ki do definitions). Ek function share karo ya feature store use karo.
- **Festival dates ko hard-code karna.** Ye har saal badalti hain aur region ke hisaab se alag hoti hain. Dates waali ek table rakho.
- **Kisi jump ki jaanch karne ki jagah jashn manaana.** Ek feature ya ek join se aaya bada gain tab tak leak hai jab tak ulta saabit na ho.
- **Ek saath saikadon features jodna.** Inhe groups mein jodo aur har group ko measure karo, taaki pata rahe ki kaun-se apne maintenance ka kharch nikaalte hain.

## Kab bhaari feature engineering ki zaroorat nahi

- **Unstructured data**, jaise images, audio ya lamba text, jahaan neural networks apne features khud seekhte hain.
- **Ek mazboot pretrained model ya embeddings** jo aapki zaroorat ki cheez pehle se pakad lete hain.
- **Bahut chhota data**, jahaan kuch expert features aur ek simple model sau engineered features se behtar karte hain.

## Demo se production tak

- **As-of rule ko test karo**: ek unit test jo koi future event jode aur check kare ki koi feature nahi badla.
- **Training aur serving ke outputs ki tulna karo**, launch se pehle customers ke ek sample par, aur uske baad ek schedule par.
- **Feature distributions aur missing rates track karo**, har source ke liye, taaki koi tooti hui upstream table dheere-dheere girti accuracy ki jagah ek alert ke roop mein dikhe.
- **Har retrain par feature groups ko phir se measure karo**, aur jo madad karna band kar dein unhe hata do.

## Practice

Kaggle ka Feature Engineering course poora karo aur Google ke Rules of ML ka feature engineering section padho. Phir worked example ka code use karo:

1. Apne teen features jodo (jaise orders mein weekend ka hissa, ya agle tyohaar tak kitne din) aur har ek ko baseline mein jodkar aur full set se hatakar measure karo.
2. Ek test likho jo kisi cutoff ke ek minute baad ki date waala order jode aur agar `features_as_of` badle toh fail ho.
3. Time split ki jagah saari rows ka ek random 80/20 split karo. Yahaan isse scores nahi badhte, kyunki simulation mein mahine-dar-mahine koi shifts nahi hain. Do asli badlaav batao (keemat badhna, naya competitor) jo random split ko zaroorat se zyada optimistic bana dein.
4. April se June par train karo aur August se October par test karo. Check karo ki table mein feature groups ki ranking ab bhi waisi hi rehti hai ya nahi.

**Aapka kaam poora hai jab aap** har feature ke liye bata sako ki wo prediction time ke hisaab se kaise compute hota hai, aapne use baad ke period par kaise validate kiya, aur production use bilkul waise hi kaise compute karta hai.
