## Ye kya hai

Kai automations ko **kuch hote hi usi pal** react karna hota hai: koi payment safal hota hai, koi order aata hai, koi form submit hota hai. **Webhook** yahi mumkin banata hai.

Webhook ek message hai jo koi app event hote hi aapke diye web address (URL) par bhejta hai. Ye doorbell jaisa hai. Har kuch minute mein darwaaza check karne ki jagah, jise **polling** kehte hain, koi aata hai toh aapko bata diya jaata hai.

```flow
dir: LR
title: Polling: dheema, bahut saari bekaar requests
Aapka app -[kuch naya hai?]-> Store
Store -[nahi ... nahi ... haan, ek order]-> Aapka app
```

```flow
dir: LR
title: Webhook: hote hi bata deta hai, tez, koi bekaar check nahi
Store -[event POST karta hai]-> Aapka URL (n8n)
Aapka URL (n8n) -[200 OK]-> Store
```

Message aamtaur par ek HTTP **POST** request hota hai, jiski **JSON** body event ke baare mein batati hai. Ek aasaan kiya hua example, kisi payment gateway ke event jaisa:

```json
{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}
```

Is sample mein amount paise mein hai, toh 420000 ka matlab ₹4,200.

**Webhook ya API?** API mein *aap* provider ko call karke poochhte ho. Webhook mein kuch badalne par provider *aapko* call karta hai. Achhe automations dono use karte hain: webhook batata hai ki kuch hua, aur API se aap details check karte ho aur gaps bharte ho.

Ye lesson Jaipur ke ek handicrafts store ke saath chalta hai, jo chahta hai ki payment safal hote hi invoice email ho jaaye.

## Ye kaam kaise karta hai

### Ek delivery ki poori kahaani

Har delivery ek hi loop se guzarti hai. Sender sirf aapka reply dekhta hai.

```flow
title: Ek webhook delivery
Event hota hai | jaise koi payment capture hota hai -> Sender aapke secret se JSON sign karta hai
Sender aapke secret se JSON sign karta hai -> Aapke URL par POST
Aapke URL par POST -> Aapka reply
Aapka reply -[timeout ke andar 2xx]-> Delivered | sender ruk jaata hai
Aapka reply -[error ya samay par reply nahi]-> Baad mein retry | wahi event, wahi id
Baad mein retry -> Aapke URL par POST
```

Yaani sender ke liye `2xx` reply ka matlab hai "ho gaya", bhale hi aapka workflow ek second baad fail ho jaaye, aur koi bhi failure wahi event waapas le aata hai.

### Receive karna: test aur production URLs

Aapka automation tool aapko ek URL deta hai, jaise n8n ke **Webhook** node se. Use sending app ki settings mein paste karo aur chuno ki kaun-se events bhejne hain. Kai tools do URLs dete hain:

| URL | Kab kaam karta hai | Kiske liye use karo |
| --- | --- | --- |
| Test URL | Jab aap editor mein listen kar rahe ho | Build aur debug karne ke liye |
| Production URL | Jab workflow publish (active) ho | Real events ke liye |

Beginners ki ek aam galti hai sender ki settings mein test URL hi chhod dena: jab tak aap dekh rahe ho sab chalta hai, phir band ho jaata hai.

Yahaan Webhook node ki do settings maayne rakhti hain. **Raw Body** sender ke bheje exact bytes waise hi rakhta hai, jo signature check karne ke liye chahiye. **Respond** tay karta hai ki n8n kab reply kare: turant, aakhri node khatam hone par, ya kisi **Respond to Webhook** node par jise aap theek wahin rakhte ho jahaan chahiye.

### Real events aane se pehle test karo

Field names har provider mein alag hote hain, isliye mappings kisi real sample se banao. Aap khud `curl` se ek bhej sakte ho: n8n mein "Listen for test event" par click karo, phir apne test URL ke saath ye chalao:

```bash
curl -X POST "https://your-n8n.example.com/webhook-test/payments" \
  -H "Content-Type: application/json" \
  -d '{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
```

Ek trap kai beginners ko rok deta hai. Agar n8n aapke laptop par chalta hai, toh uska URL `localhost` se shuru hota hai, jis tak internet par baitha gateway nahi pahunch sakta. Public n8n (n8n Cloud, ya HTTPS waala server) use karo, ngrok ya Cloudflare Tunnel jaisa koi **tunnel** jo aapke laptop ko public address deta hai, ya sirf ye dekhne ke liye ki provider kya bhejta hai, webhook.site.

Zyaadatar gateways mein ek **test mode** bhi hota hai jismein asli paisa nahi lagta. Test aur live mode ke webhooks aur secrets aamtaur par alag-alag hote hain.

### Aapka reply sender ko kya batata hai

Sender sirf aapke reply ka status code padhta hai, aur sirf kuch seconds rukta hai. Razorpay, ek Indian payment gateway, 5 seconds ke andar `2xx` reply ki ummeed karta hai. Koi aur code, ya samay par reply na aana, wo failure maanta hai aur event banne ke 24 ghante tak badhte gaps ke saath retry karta hai. Agar un 24 ghanton tak deliveries fail hoti rahein, toh wo webhook disable kar deta hai (ye sab November 2026 ke hisaab se). Doosre providers ke windows alag hote hain, isliye unke docs padho.

| Aapka reply | Sender kya samajhta hai | Kab bhejna hai |
| --- | --- | --- |
| `200` (ya koi aur `2xx`) | Delivered; dobara kabhi nahi bhejega | Event save ho gaya hai, ya ye duplicate hai jo aapke paas pehle se hai |
| `401` | Failed; aamtaur par retry hota hai | Signature match nahi hota |
| `500` | Failed; baad mein retry hota hai | Aap event save nahi kar paaye, jaise aapka database down hai |
| Samay par reply nahi | Failed; baad mein retry hota hai | Aapka workflow bahut dheema tha ya server down tha |

### Pehle save, phir reply, phir kaam

Is lesson ka sabse zaroori idea yahi hai. Teen mumkin orders mein se do fail hote hain.

| Order | Kya gadbad hoti hai |
| --- | --- |
| Saara kaam karo, phir reply | Dheema kaam, jaise PDF banaana, timeout paar kar jaata hai. Aap kaam kar rahe hote ho aur sender retry kar deta hai, aur aapko duplicates milte hain. |
| Pehle reply, phir kaam | Agar `200` ke baad n8n crash ya restart ho jaaye, toh sender kabhi dobara nahi bhejta aur event kho jaata hai. |
| Save, reply, phir saved copy se kaam | Sender ke "ho gaya" sunne se pehle hi event safe hai. Fail hua kaam aapki copy se retry hota hai. |

**Durable tareeke se save karna** matlab event ko aisi jagah likhna jo restart ke baad bhi bacha rahe: database table (jaise Postgres ya Supabase) ya message queue. Ek insert tez hota hai, timeout ke kaafi andar. Raw body, event id, receive hone ka samay aur ek **status** store karo: save hone par `received`, kaam khatam hone par `done`.

```flow
title: Save, reply, phir kaam
Webhook aata hai -> Signature match hota hai?
Signature match hota hai? -[nahi]-> 401 reply karo aur ruko
Signature match hota hai? -[haan]-> Event id insert karo | status received
Event id insert karo -[pehle se hai]-> 200 reply karo aur ruko | ek duplicate
Event id insert karo -[save ho gaya]-> 200 reply karo
200 reply karo -> Invoice banao aur email karo
Invoice banao aur email karo -> Status done mark karo
```

Agar reply ke baad workflow crash ho jaaye, toh row `received` hi rehti hai. Ek **sweep**, yaani ek scheduled workflow jo lagbhag har 15 minute mein chalta hai, un rows ko uthaata hai jo 10 minute baad bhi `received` hain aur kaam dobara chalaata hai. Isliye kaam dohraane ke liye safe hona chahiye: har sub-step (invoice bana, email gaya) record karo, taaki rerun sirf wahi kare jo baaki hai.

### Duplicates aur idempotency

Zyaadatar senders **at-least-once delivery** ka vaada karte hain: wo event khone ki bajaay use do baar bhejna pasand karte hain. Iska bachaav hai **idempotency**: kisi event ko do baar process karne ka asar wahi ho jo ek baar process karne ka.

Do alag kaamon ke liye do ids use karo:

- **Event id** ek delivery ko pehchaanta hai. Us event ke har retry par uski value wahi rehti hai, isliye ye batata hai ki "ye delivery main pehle dekh chuka hoon". Jaise Razorpay ise `x-razorpay-event-id` header mein bhejta hai.
- **Business id**, jaise payment id, asli cheez ko pehchaanta hai. Do *alag* events ek hi payment ke baare mein ho sakte hain (jaise `payment.captured` aur `order.paid`), isliye invoice ko payment id par key karo.

**Wo race jismein experts bhi phanste hain.** Ek aasaan-sa design lagta hai: "sheet mein id dhoondho; nahi mili toh jod do". Dheeme reply ke baad retry original ke ek second baad hi aa sakta hai. Dono copies `pay_771` dhoondhti hain, dono ko kuch nahi milta, dono invoice bana deti hain, kyunki check aur write ke beech doosri copy ghus gayi.

Iska fix hai **ek hi step jo duplicate par fail ho**. `event_id` column ko unique key do aur bas insert karo. Theek ek insert safal hota hai; doosre ko "duplicate key" error milta hai, jise aapka workflow "pehle se hai, 200 reply karo aur ruko" maanta hai. Invoice ke `payment_id` par bhi unique key lagao.

Google Sheet mein unique key nahi hoti. Sheet lookup sirf us chhoti, kam volume waali shop ke liye theek hai jise kabhi-kabhaar double invoice chal jaaye. Sale se pehle database table par chale jaao.

### Events order badalkar aa sakte hain

Delivery order ki koi guarantee nahi hai; Razorpay ki webhook guidance ye seedhe kehti hai (November 2026 ke hisaab se). Kisi puraani attempt ka retry hua `payment.failed` safal `payment.captured` ke *baad* aa sakta hai, aur "aakhri event jeetta hai" waala tareeka paid order ko failed mark kar dega. Do rules ise sambhaalte hain:

- **States ko sirf aage badhaao.** Order `created` se `paid` tak ja sakta hai, par `paid` se waapas `failed` kabhi nahi. Jo events use peechhe le jaayein unhe ignore karo.
- **Jab maayne rakhe, current state poochho.** Ship ya refund karne se pehle, provider ke API ko call karke abhi ka status dekho.

### Security

Jise bhi aapka URL pata chal jaaye, wo ek fake "payment captured" post karke asli shipment trigger karwa sakta hai. Ise layers mein protect karo.

**Signature verify karo.** Aap aur provider ek **webhook secret** share karte ho. Har delivery ke liye provider ek **HMAC** compute karta hai, yaani secret se bana body ka fingerprint, aur use ek header mein bhejta hai. Jaise Razorpay `X-Razorpay-Signature` mein ek HMAC-SHA256 hex value bhejta hai (November 2026 ke hisaab se). Aap receive hui body par wahi HMAC compute karte ho; dono match hon, toh sender ko secret pata hai aur body nahi badli. Webhook ka apna secret use karo, apne API key ka secret nahi.

Teen details tay karti hain ki check kaam karega ya nahi:

1. **Raw body use karo.** Signature bheje gaye exact bytes ko cover karta hai. JSON parse karke waapas text banao toh spaces ya key order badal sakte hain, aur genuine event bhi fail ho jaata hai. n8n mein **Raw Body** on karo.
2. **Constant time mein compare karo.** Normal comparison pehle galat character par ruk jaata hai, jisse timing ke clues leak ho sakte hain. n8n ka **Crypto** node HMAC compute kar sakta hai, par IF node waala comparison constant-time nahi hai. High-value flows ke liye **Code** node mein Node ke `crypto.timingSafeEqual` se compare karo; self-hosted n8n par pehle `NODE_FUNCTION_ALLOW_BUILTIN` environment variable se `crypto` module allow karo.
3. **Jahaan provider timestamp sign karta hai, wahaan puraane messages reject karo.** Signature saabit karta hai ki message kisne bheja, kab nahi, isliye pakdi gayi request baad mein replay ki ja sakti hai. Kuch providers, jaise Stripe, timestamp sign karte hain taaki aap kuch minute se puraani koi bhi cheez reject kar sako. Jahaan ye nahi hai, wahaan aapka unique event id replay ko be-asar kar deta hai.

Ye Python script, sirf standard library se, raw-body trap dikhaata hai:

```python
import hmac, hashlib, json

SECRET = b"test_secret_123"

def is_genuine(raw_body: bytes, signature: str) -> bool:
    expected = hmac.new(SECRET, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)  # constant-time

raw = b'{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
sig = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()

print(is_genuine(raw, sig))                          # True
print(is_genuine(json.dumps(json.loads(raw)).encode(), sig))  # False: spaces were added
```

Doosri baar ye fail hota hai kyunki `json.dumps` spaces jod deta hai: wahi data, alag bytes.

**Baaki layers:** HTTPS aur ek lamba, random URL path use karo (inmein se koi bhi signature ki jagah nahi leta). Saamaan ship karne se pehle provider ke API se payment dobara fetch karo; Razorpay khud webhooks ke backstop ke taur par apne fetch APIs use karne ki salaah deta hai, jaise jab koi time-sensitive flow webhook aane ka intezaar nahi kar sakta.

### Chhoote hue events aur reconciliation

Retries chhote outages cover karte hain, lambe nahi. Retry window ke baad events bina kisi error ke kho jaate hain, aur kuch providers webhook band kar dete hain. Zaroori flows mein do safety nets hote hain:

- **Sweep** un events ka kaam retry karta hai jo aapne save kiye par poore nahi kiye.
- **Reconciliation**, jaise nightly, provider ke API se din ke saare captured payments maangta hai aur unhe aapke invoices se compare karta hai. Jo bhi chhoota hai, wo tab process hota hai.

Ek alert bhi lagao: agar business hours mein ek ghante tak koi webhook na aaye, ya provider bataaye ki koi webhook disable ho gaya, toh koi usi din dekhe.

## Ek example se samjho

Jaipur ka ek handicrafts store Razorpay use karta hai aur chahta hai ki payment safal hote hi invoice email ho jaaye. Ek typical order ₹4,200 ka hai. Gateway details November 2026 ke hisaab se hain. Wo n8n mein ye banaate hain:

| # | Step | Kyun |
| --- | --- | --- |
| 1 | Webhook node: production URL, Raw Body on, Respond to Webhook node se reply karta hai. Razorpay dashboard mein `payment.captured` ke liye joda gaya. | Events turant receive karna, exact bytes ke saath |
| 2 | Raw body ka HMAC-SHA256 webhook secret se compute karo aur Code node mein `X-Razorpay-Signature` se compare karo. Mismatch par `401` reply karo. | Fake requests reject karna |
| 3 | `x-razorpay-event-id`, payment id aur raw body ko `webhook_events` mein insert karo (unique event id, status `received`). Duplicate key: `200` reply karo aur ruko. Koi aur failure: `500` reply karo. | Gateway ke "ho gaya" sunne se pehle event safe hai; copies yahin ruk jaati hain |
| 4 | Respond to Webhook: `200`. | 5-second limit ke kaafi andar |
| 5 | Unique payment id waali `invoices` table mein invoice PDF banao, email karo, phir event ka status `done` set karo. | Dheema kaam, dohraane ke liye safe |
| 6 | Har 15 minute: jo rows 10 minute baad bhi `received` hain unke liye step 5 phir chalao. | Crash hua kaam poora karna |
| 7 | Nightly: Razorpay API se din ke captured payments fetch karo aur invoices se compare karo. | Jo kabhi pahuncha hi nahi, use pakadna |

**Festival sale (ek illustration).** Diwali sale ke dauraan har kuch seconds mein orders aate hain.

- PDF service atak jaati hai aur ek payment ka invoice bante-bante n8n restart ho jaata hai. Wo event pehle hi save ho chuka tha aur uska jawaab ja chuka tha, isliye Razorpay use dobara nahi bhejta. Das minute baad sweep dekhta hai ki row abhi bhi `received` hai aur invoice bhej deta hai.
- Ek aur restart server ko do minute ke liye down kar deta hai. Razorpay ko un payments ka koi reply nahi milta aur server waapas aane par wo unhe retry karta hai.
- pay_771 us restart se theek pehle save ho gaya tha, par `200` kabhi server se nikla hi nahi. Razorpay use retry karta hai; step 3 ka insert duplicate key se takraata hai, aur workflow `200` reply karke ruk jaata hai.

| Sthiti | Kya hua | Kis step ne sambhaala |
| --- | --- | --- |
| Kisi anjaan sender ki fake request | Signature match nahi hua | Step 2: `401` se reject |
| Reply ke baad, invoice se pehle crash | Row `received` hi rahi | Step 6: sweep ne poora kiya |
| 2 minute ke outage mein bheje gaye events | Razorpay ne baad mein retry kiye | Steps 1 to 5, kuch minute der se |
| pay_771 do baar deliver hua | Event id pehle se table mein tha | Step 3: `200` ke saath ruka |
| Ek hafte ka nightly reconciliation | Koi chhoota payment nahi mila | Step 7 |

Store ka pehla version turant reply karta tha aur sheet lookup use karta tha. Crash hua invoice hamesha ke liye kho jaata, kyunki gateway ko uska `200` mil chuka tha, aur duplicate pay_771 ek doosra invoice bana deta: ₹4,200 ki aisi sales jo kabhi hui hi nahi.

## Aam galtiyaan

- **Production mein test URL use karna.** Editor band karte hi events aana band ho jaate hain.
- **Event save hone se pehle reply karna.** `200` ke baad crash hone par event kho jaata hai, kyunki sender use dobara nahi bhejega.
- **Reply se pehle dheema kaam karna.** Sender timeout hokar retry karta hai, aur duplicates bante hain.
- **Duplicate check ke liye "pehle dhoondho, phir likho".** Saath aane waali do copies dono pass ho jaati hain. Unique key use karo.
- **Duplicate ka jawaab error se dena.** Sender us event ko retry karta rehta hai jo aapke paas pehle se hai. `200` reply karo.
- **Parse kiye JSON par signature check karna, ya sirf URL par bharosa karna.** Raw body use karo; secret URL leak ho sakta hai.
- **Maan lena ki events order mein aayenge.** States ko sirf aage badhaao, aur paise se juda action lene se pehle dobara fetch karo.
- **Test aur live secrets mila dena.** Har mode ka aamtaur par apna webhook aur secret hota hai.
- **Na sweep, na reconciliation, na alert.** Crashes aur lambe outages chupchaap events kho dete hain.
- **Secrets log karna.** Webhook secret aur poori payment details shared logs se baahar rakho.

1. **Receive karo.** n8n mein ek Webhook workflow banao, upar waala `curl` command apne test URL par bhejo aur aaya hua JSON study karo. Agar n8n laptop par chalta hai, toh baahar se us tak tunnel se pahuncho.
2. **Reply se pehle save karo.** Unique event id aur ek status column waali `webhook_events` table banao. Har event insert karo, phir Respond to Webhook node se reply karo. Reply ke baad jaanboojhkar workflow roko aur dikhaao ki row `received` hi rehti hai.
3. **Duplicates.** Wahi event ek saath do baar bhejo (`&` se jude do `curl` commands). Dikhaao ki ek row, ek invoice, aur dono copies ke liye `200` aata hai.
4. **Security.** Body ko test secret se sign karo (`openssl dgst -sha256 -hmac "test_secret_123"`, ya upar waala Python script), use signature header mein bhejo aur raw body par verify karo. Body ka ek character badlo aur `401` dikhaao.
5. **Sweep aur reconcile.** 15-minute waala sweep banao, aur teen sentences mein batao ki aapke provider ke liye nightly reconciliation kaise kaam karega.

**Aapka kaam poora hai jab aap** samjha sako ki "pehle reply" se events kyun khote hain, dikha sako ki do copies saath aane par aapka duplicate check tika rehta hai, dikha sako ki chhedchhaad ki gayi request reject hoti hai, aur bata sako ki do din ke outage mein chhoote events aap kaise pakdoge.
