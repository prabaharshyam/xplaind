## Ye kya hai

**Connector** wo code hai jo business system aur aapke AI system ke beech data le jaata hai. Achha connector chaar kaam karta hai: sab kuch ek baar copy karta hai, us copy ko current rakhta hai, jo delete hua use hataata hai, aur har item ke saath ye jaankaari bhi laata hai ki use kaun padh sakta hai. Zyaadatar enterprise AI projects ko kai connectors chahiye hote hain:

- **Documents**: SharePoint aur OneDrive (Microsoft Graph ke zariye), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: Salesforce jaise CRM systems, SAP jaise ERPs, Jira ya ServiceNow jaisi ticketing, aur client ke apne databases.
- **Messages**: email aur chat, privacy ki wajah se saavdhaani se use hote hain.

Connectors aap khud build kar sakte ho, ek integration platform use kar sakte ho (Airbyte, Fivetran aur kuch aur kai ready-made connectors dete hain), ya kisi search ya AI platform ke saath bundled connectors use kar sakte ho. Jo bhi chuno, aapko samajhna hoga ki wo karte kya hain.

```flow
title: A connector feeding an assistant
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[REST, SystemModstamp, get deleted]-> Connector
Jira, SAP, file shares -> Connector
Connector -> Items, metadata, permissions, deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 12, changed 41, unchanged 253, deleted 6, failed 0
```

Ye lesson SharePoint aur Salesforce par bane Gurugram ke ek sales assistant ko follow karta hai.

## Ye kaise kaam karta hai

### Authentication

Aamtaur par OAuth, client ki IT team ke register kiye app ke saath, read-only aur tay sites, objects ya projects tak scoped. Kuch systems API keys ya service users use karte hain; unhe secret manager mein rakho, code mein kabhi nahi.

Lambe runs ko do cheezein todti hain. Pehli, access tokens expire hote hain: Microsoft unhe default 60 se 90 minute ki life deta hai, isliye do raat chalne wala first load ek hi token use nahi kar sakta. Har request se pehle apni auth library ke cache (jaise MSAL) se token maango; expiry ke paas wo naya token le aata hai. Doosri, client secrets aur certificates bhi expire hote hain. Date runbook mein likho aur ek mahina pehle alert karo.

### Pages mein padhna

APIs results pages mein lautaati hain. Har page ek cursor ya "next" link par khatam hota hai. Tab tak loop karo jab tak next page na bache. Jo rule maayne rakhta hai: **har page poora process hone ke baad apni position save karo**, pehle nahi aur sirf aakhir mein bhi nahi. Process karne se pehle save karoge to crash par items skip ho jaayenge; sirf aakhir mein save karoge to page 9,000 par crash hone se page 1 se restart hoga.

### Rate limits

Har API calls limit karti hai. Microsoft Graph `Retry-After` header ke saath 429 Too Many Requests lautaata hai aur retry karne se pehle utni der wait karne ko kehta hai; header na ho to exponentially back off karo. HTTP standard ke hisaab se `Retry-After` seconds ki ginti bhi ho sakta hai aur ek date bhi, isliye dono parse karo. Lagbhag ek second ka random jitter jodo taaki parallel workers sab ek hi pal mein retry karke phir se throttle na hon.

### Incremental sync aur change detection

Pehla run sab kuch copy karta hai; baad ke runs sirf badla hua laate hain. 200,000 documents ko har raat poora dobaara padhna slow hai, mehenga hai aur aapko throttle karwaata hai.

| Method | Udaharan | Deletions report karta hai? | Kis baat ka dhyaan rakhein |
| --- | --- | --- | --- |
| Delta token | Microsoft Graph delta | Haan | Links kaam karna band kar sakte hain (410 Gone); full re-scan ka raasta rakho |
| Modified-since filter | Salesforce `SystemModstamp`, Jira `updated` | Nahi | Deletion feed ke saath jodo; windows ko kuch minute overlap karo |
| Deletion feed | Salesforce get-deleted resource | Sirf deletions | Salesforce zyaada se zyaada 15 din rakhta hai |
| Webhooks | Jira `jira:issue_deleted` | Agar wo event maujood ho | Deliveries kho sakti hain; ise kabhi akela source mat banao |
| Full id comparison | Aapka weekly reconciliation | Haan, farq se | Bade sets par slow; safety net ke taur par har hafte chalao |

Graph delta ke do gotchas: ek hi item ek feed mein ek se zyaada baar aa sakta hai (aakhiri wala maanya hai, isliye source id se upsert karo), aur delete hua item `deleted` marker ke saath, bina content ke lautta hai, isliye download karne se pehle use check karo.

### Deletions

Modified-since query wo record nahi dekh sakti jo ab maujood hi nahi, isliye delete hue documents quote hote rehte hain. Har connector ko aisa feed chahiye jo deletions report kare, ya ek periodic id comparison, ho sake to dono.

### Permissions

Sabse mushkil hissa: permissions ko ignore karne wala assistant ek junior employee ko salary review deck dikha deta hai.

- **Har item ke saath access rights padho.** Graph ka permissions endpoint kisi file ki effective sharing lautaata hai, folders se inherit hue access samet. Allowed user aur group ids har chunk par store karo.
- **Groups ko groups hi rehne do.** Index time par "Sales North" ko 400 user ids mein expand mat karo. Query time par user ke maujooda groups (unke sign-in token se ya directory call se) dekho aur unse filter karo. Phir group chhodne wala insaan usi waqt access kho deta hai jab aapke group lookup ko badlaav dikhta hai, bina re-index ke.
- **Sirf permission wale badlaav dikhna mushkil hai.** File share karne se uska content nahi badalta. Graph delta sharing badalne wale items ko mark kar sakta hai agar aap `Prefer: deltashowsharingchanges` header bhejo, saath mein `deltashowremovedasdeleted` aur `deltatraversepermissiongaps`, jinhe Microsoft zaroori batata hai. Lekin Microsoft document karta hai ki delta sirf wo items lautaata hai jinka content ya metadata badla, aur unke parent folders, isliye jo files sirf access inherit karti hain wo shaayad na aayein. Microsoft ye bhi kehta hai ki permissions theek se process karne ke liye `Sites.FullControl.All` app permission chahiye, jise security teams aksar mana kar deti hain. Marker ko bas ek hint maano. Uske peechhe un sites aur folders par permissions ka scheduled re-read rakho jinhe client sensitive mark karta hai.
- **Fail closed.** Agar kisi item ki permissions nahi padh pa rahe, to use index mat karo.

### Code mein ek incremental connector

Ek SharePoint library ke liye ye sync upar ke rules follow karta hai. Ye har page par apni position save karta hai, fail hue items ke liye retry list rakhta hai, tokens refresh karta hai, aur throttling aur toota delta link sambhaalta hai:

```python
import email.utils, hashlib, json, random, time
from pathlib import Path        # client below is an httpx.Client

GRAPH = "https://graph.microsoft.com/v1.0"
STATE = Path("state/sharepoint-delta.json")

class StopRun(Exception): pass    # fatal: stop now, leave saved state as it is
class Resync(Exception): pass     # 410 Gone: the saved link no longer works

def wait_for(r, attempt):
    value = r.headers.get("Retry-After", "")
    if value.isdigit():
        delay = int(value)                                  # seconds
    elif value:
        when = email.utils.parsedate_to_datetime(value)     # an HTTP date
        delay = max(0, when.timestamp() - time.time())
    else:
        delay = min(60, 2 ** attempt)                       # no header: back off
    return delay + random.uniform(0, 1)                     # jitter

def get(client, url, token, prefer=None):
    headers = {"Authorization": f"Bearer {token()}"}  # token() reads a cache
    if prefer:
        headers["Prefer"] = prefer
    for attempt in range(6):
        r = client.get(url, headers=headers)
        if r.status_code in (429, 503):
            time.sleep(wait_for(r, attempt)); continue
        if r.status_code == 410:
            raise Resync(r.headers.get("Location"))
        if r.status_code in (401, 403):
            raise StopRun(f"access refused: {r.status_code}")
        r.raise_for_status()
        return r.json()
    raise StopRun("still throttled after 6 tries")

def process(client, token, drive_id, item, index, counts, retry):
    if "deleted" in item:
        index.delete_doc(item["id"])        # must not fail if already gone
        if item["id"] in retry:
            retry.remove(item["id"])
        counts["deleted"] += 1
        return
    if "file" not in item:
        return                              # folders carry no text
    perms = get(client, f"{GRAPH}/drives/{drive_id}/items/{item['id']}/permissions", token)
    acl = acl_from(perms)                   # user and group ids allowed to read
    text = download_and_parse(item)         # your parser
    digest = hashlib.sha256(text.encode()).hexdigest()
    if index.hash_of(item["id"]) == digest:
        index.update_meta(item["id"], meta_from(item), acl)  # renamed or reshared: no re-embed
        counts["unchanged"] += 1
    else:
        new = index.upsert_doc(item["id"], text, digest, meta_from(item), acl)
        counts["added" if new else "changed"] += 1

def save(state):
    STATE.parent.mkdir(exist_ok=True)
    tmp = STATE.with_suffix(".tmp")
    tmp.write_text(json.dumps(state))
    tmp.replace(STATE)                      # atomic: never half-written

def sync(client, token, drive_id, index):
    state = json.loads(STATE.read_text()) if STATE.exists() else {}
    retry = state.get("retry", [])
    counts = dict.fromkeys(["read", "added", "changed", "unchanged", "deleted", "failed"], 0)
    for item_id in list(retry):             # last run's failures first
        try:
            item = get(client, f"{GRAPH}/drives/{drive_id}/items/{item_id}", token)
            process(client, token, drive_id, item, index, counts, retry)
            if item_id in retry:
                retry.remove(item_id)
        except StopRun:
            raise
        except Exception:
            counts["failed"] += 1           # stays listed; alert if it stays for days
    url = (state.get("next_link") or state.get("delta_link")
           or f"{GRAPH}/drives/{drive_id}/root/delta")
    while True:
        try:
            page = get(client, url, token, prefer="deltashowremovedasdeleted, "
                       "deltatraversepermissiongaps, deltashowsharingchanges")
        except Resync as e:
            state = {"retry": retry, "reconcile": True}   # full listing, then compare ids
            url = e.args[0] or f"{GRAPH}/drives/{drive_id}/root/delta"
            continue
        for item in page.get("value", []):
            counts["read"] += 1
            try:
                process(client, token, drive_id, item, index, counts, retry)
            except StopRun:
                raise
            except Exception:
                counts["failed"] += 1
                if item["id"] not in retry:
                    retry.append(item["id"])
        state["retry"] = retry
        if "@odata.nextLink" in page:       # page done: save where to resume
            url = state["next_link"] = page["@odata.nextLink"]
            save(state)
        else:                               # last page: save the link for next time
            state.pop("next_link", None)
            state["delta_link"] = page["@odata.deltaLink"]
            save(state)
            break
    print(counts)
    return counts
```

Ise aise kyun banaya gaya hai:

- **Position aur failures ek saath save hote hain**, har page ke baad ek atomic write mein. Page ke beech crash hone par wo page replay hota hai, jo safe hai kyunki upserts aur deletes source id se keyed hain. Fail hua item kabhi skip nahi hota: wo succeed hone tak retry list par rehta hai.
- **Ek kharaab file feed ko freeze nahi karti.** Koi bhi item fail hone par aage badhne se mana karna safe lagta hai, lekin tab ek corrupt PDF aage ke har change ko block kar degi.
- **Metadata text ke saath chalta hai.** `meta_from` citations aur filters ke liye source id, URL, title, path, author, modified time aur owner rakhta hai. Rename inhe badalta hai par text ko nahi, isliye ye bina re-embedding ke update hote hain.
- **Fatal errors bina save kiye run rok dete hain.** Access error ya kabhi na khatam hone wali throttling item failure nahi hai; use item failure ginoge to poori library retry list par chali jaayegi.
- **Toota link full listing trigger karta hai.** 410 Gone par Graph ka `Location` header ek naya enumeration shuru karta hai. Wo batata hai ki kya maujood hai, ye nahi ki beech mein kya delete hua, isliye `reconcile` flag scheduler ko agli baar id comparison chalaane ko kehta hai.

### Ek weekly reconciliation

Achhe change feeds se bhi cheezein chhoot jaati hain. Source ke paas jo ids hain unhe index ki ids se compare karo:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

Agar `removed_stale` bas do-chaar se zyaada hai, to aapke change feed mein bug hai; use theek karo.

### Records: Salesforce, Jira aur SAP

- **Salesforce.** Badle records ko `LastModifiedDate` par nahi, `SystemModstamp` par filter lagaakar query karo, kyunki automated processes record badlein tab bhi `SystemModstamp` aage badhta hai. Pichhle run time se kuch minute ghata lo taaki der se commit hue records na chhootein. Deletions ke liye har object par UTC mein start aur end time ke saath get-deleted REST resource call karo. Ye zyaada se zyaada pichhle 15 din cover karta hai aur minute tak kaam karta hai, isliye agar connector usse zyaada samay down raha, to sirf full id comparison hi barabari kara sakta hai. Saath hi, ye sirf wahi deletions dikhata hai jo integration user dekh sakta tha.
- **Jira Cloud.** `search/jql` endpoint se JQL ke saath search karo, jo purane `startAt` offset ki jagah `nextPageToken` se page karta hai. `updated >= "last run time"` se filter karo. Delete hue issues search se bas gaayab ho jaate hain, isliye `jira:issue_deleted` webhook subscribe karo aur phir bhi ids reconcile karo, kyunki webhooks chhoot sakte hain.
- **SAP.** Direct table access kam hi milta hai. Client ki SAP team data expose karti hai, aamtaur par OData services ke roop mein (aksar CDS views par bani), kabhi-kabhi purane BAPI ya RFC calls se, ya apne integration middleware se. Kuch OData services delta tokens support karti hain; warna changed-on date field aur reconciliation use karo. Mukhya gotcha samay hai: service banwaane aur approve karwaane mein aapke code se zyaada waqt lagta hai, isliye pehle hafte mein hi maang lo.
- **Schema drift.** Admins fields jodte hain, picklist values rename karte hain aur objects retire karte hain. Apne URLs mein API version pin karo, sirf tay fields map karo, aur sab kuch chupchaap index karne ki jagah tab alert karo jab describe call naye ya gaayab fields dikhaaye.
- **Record permissions.** Salesforce access owners, roles aur sharing rules se aata hai, jinhe hoobahoo copy karna mushkil hai. Safe first release sirf wo objects index karta hai jo har sales user padh sakta hai, ya record dikhaane se pehle user ke apne login se live access check karta hai.

### Build, buy ya borrow

Airbyte ya Fivetran jaise integration platforms aam systems ke liye hafton ka kaam bachaate hain. Kisi par bharosa karne se pehle check karo ki wo deletions report karta hai, access rights saath laata hai aur aise run counts expose karta hai jin par aap alert kar sako. Apna khud ka connector un systems ke liye likho jo aam nahi hain, jaise in-house database, ya jab client ki security team third-party tool approve na kare.

## Ek worked example

Gurugram ki ek consumer-goods company SharePoint (product sheets, trade-scheme circulars) aur Salesforce (accounts, opportunities) par ek sales assistant chahti hai. Neeche ke figures illustrative hain, kaam ki shape dikhaane ke liye.

**SharePoint.** Chhah sites par read access wala ek app registration. Maan lo 38,000 files ka pehla full sync throttling limits se kaafi neeche rehne ke liye do raaton mein baanta gaya hai; agar save kiya next link ab bhi kaam karta hai to doosri raat wahin se aage chalti hai, aur agar Graph 410 jawaab de to listing phir se shuru hoti hai. Uske baad har 15 minute par ek delta run kuch sau changed ya deleted items lautaata hai aur lagbhag ek minute mein khatam hota hai. Har run changed items ki permissions bhi dobaara padhta hai, aur ek nightly job un do sites par permissions dobaara padhta hai jinmein pricing aur HR files hain.

**Salesforce.** Account, Opportunity aur Product tak seemit ek read-only integration user. Har 30 minute par connector un records ko query karta hai jinka `SystemModstamp` pichhle run time minus paanch minute ke baad ka hai, har ek ko record id aur owner ko metadata ke taur par rakhkar ek chhoti text summary mein badalta hai, aur usi window ke liye get-deleted resource call karta hai. Agar koi sales manager 11:10 par ek duplicate account delete kare, to wo lagbhag 11:30 tak index se nikal jaata hai.

**Incident.** Maan lo teesre hafte mein ek delta request 410 Gone lautaati hai. Connector `Location` header follow karta hai, raat bhar library re-list karta hai, phir id comparison chalaakar wo 14 files hataata hai jo link toote rehne ke dauraan delete huin. Client ke notice karne se pehle alert on-call engineer tak pahunch gaya, aur runbook mein ye case pehle se tha.

| Paimaana | Pehle | Baad mein |
| --- | --- | --- |
| SharePoint sync | Har raat full re-read, lagbhag 6 ghante, aksar throttled | Har 15 minute par delta, lagbhag 1 minute |
| Salesforce sync | Daily export, deletions kabhi nahi hat-te | Har 30 minute, deletions ek run ke andar |
| Delete hue documents ab bhi searchable | Darjanon | Weekly check mein ek bhi nahi |
| Fail hue sync ko notice karne ka samay | Din | Minutes, alerts ke zariye |

## Aam galtiyaan

- **Har baar full re-sync.** First load ke baad delta tokens ya modified-since queries use karo.
- **Deletions ko ignore karna.** Modified-since query delete hue records kabhi return nahi karti; deletion feed aur weekly id comparison jodo.
- **Galat samay par cursor save karna.** Process se pehle save karne se crash ke baad items skip hote hain; sirf aakhir mein karne se page 1 se restart hota hai. Har page ke baad save karo.
- **Fail hue items ko nigal jaana.** Failure ginkar aage badh jaane se wo item hamesha ke liye kho jaata hai. Retry list rakho.
- **Lambe run ke liye ek token.** Wo 60 se 90 minute mein expire hota hai aur job raat 3 baje mar jaata hai.
- **Index time par groups ko users mein expand karna.** Phir membership ke badlaav laagu hone ke liye full re-index chahiye.
- **Zaroorat se zyaada access.** Poore tenant ka nahi, naam liye sites aur objects ka read-only access maango.
- **Chup rehne wale connectors.** Agar sync rukne par kisi ko alert nahi jaata, to assistant chupchaap stale ho jaata hai.
- **Har modified file ko re-embed karna**, tab bhi jab sirf uska metadata badla ho.

## Kab custom connector ki zaroorat nahi

- **One-off load**, files ke ek fixed set ka: ek baar export karo aur ingest karo.
- **Koi platform connector pehle se us system ko cover karta hai**, deletions report karta hai aur permissions padhta hai.
- **Users jin kuch documents ki zaroorat hai unhe** seedhe upload kar sakte hain.

## Demo se production tak

Shuruaati defaults, client ki IT team ke saath likhit mein tay:

- **Schedules:** document delta har 15 minute, record queries har 30 minute, permission re-read har raat, full id comparison har hafte. Bade first loads sirf client ke time zone mein raat ko, kam concurrency ke saath.
- **Alerts:** koi run fail ho ya do intervals ke andar start na ho; padhe gaye items aam ke aadhe se neeche girein; koi item ek din se zyaada retry list par rahe; koi secret 30 din ke andar expire hone wala ho.
- **Runbook:** 410 Gone par, access error par, aur jab koi site, object ya field rename ho, tab kya karna hai.

## Practice karo

Microsoft Graph overview padho, phir paging wali koi bhi API chuno jo free mein use kar sako (GitHub issues, koi public dataset API, ya developer tenant ke saath Graph).

1. Aisa connector likho jo paging ke saath saare items kheenche, `Retry-After` ka paalan kare, aur har page ke baad apni position save kare taaki resume kar sake.
2. First load ke beech mein use kill karo aur restart karo. Confirm karo ki wo save kiye page se aage badhta hai aur phir se shuru nahi karta.
3. Ek incremental mode jodo jo pichhle run ke baad badle items hi laaye, aur ek check jo delete hue items detect kare.
4. Har run ke counts (read, added, changed, unchanged, deleted, failed) record karo aur one-line summary print karo.
5. Source par ek item delete karo, rerun karo, aur confirm karo ki uske chunks index se chale gaye.

**Aapka kaam poora hai jab aap** apna connector lagaataar do baar chala sako aur dikha sako ki doosra run sirf badla hua laata hai, ek deletion samet, aur dikha sako ki crash hua run sahi page se resume hota hai.
