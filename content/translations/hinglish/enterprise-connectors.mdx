## Ye kya hai

**Connector** woh code hai jo kisi business system aur aapke AI system ke beech data le jaata hai. Zyadatar enterprise AI projects ko kai connectors chahiye:

- **Documents**: SharePoint aur OneDrive (Microsoft Graph ke through), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: Salesforce jaise CRM systems, SAP jaise ERPs, Jira ya ServiceNow jaisa ticketing, aur client ke apne databases.
- **Messages**: email aur chat, jinhein privacy ki wajah se savdhaani se use karte hain.

Connectors aap khud bana sakte ho, integration platform use kar sakte ho (Airbyte, Fivetran aur doosre kai ready-made dete hain), ya kisi search ya AI platform ke saath aaye connectors use kar sakte ho. Kuch bhi karo, aapko samajhna padega ki woh kya karte hain.

```flow
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[API, modified since]-> Connector
Jira, file shares, databases -> Connector
Connector -> Items + metadata + permissions + deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 40, changed 266, deleted 6, failed 0
```

Is lesson mein hum Gurugram ki ek consumer-goods company ke liye SharePoint aur Salesforce par bane sales assistant ke saath chalenge.

## Ye kaam kaise karta hai

**Authentication.** Aam taur par OAuth, client ki IT team ke register kiye app ke saath, jo read-only ho aur sirf tay kiye gaye sites, objects ya projects tak scoped ho. Kuch systems API keys ya service users use karte hain; unhein secret manager mein rakho.

**Pages mein padhna.** APIs results pages mein dete hain, cursor ya next link ke saath. Jab tak pages khatam na ho, loop chalao, aur cursor save karo taaki fail hui run aage badh sake.

**Rate limits.** Har API per minute ya per day calls limit karti hai; SharePoint aur Salesforce heavy users ko throttle karte hain. `Retry-After` headers ka maan rakho, 429 responses par back off karo aur bade initial loads ko off-peak hours mein baant do.

**Incremental sync.** Pehli run sab kuch copy karti hai. Baad ki runs sirf pichhli run ke baad ke changes kheenchti hain, change tokens (Microsoft Graph ki delta queries), "modified since" filters ya webhooks ke saath. Har raat 200,000 documents dobara padhna slow hai, mehnga hai aur throttle bhi karwata hai.

**Deletions.** Incremental feeds ko batana padta hai ki kya delete hua, warna delete ki hui files hamesha searchable rehti hain. Check karo ki aapka method deletions report karta hai; nahi karta toh samay-samay par reconciliation chalao jo ids compare kare.

**Permissions.** Har item ke access rights uske content ke saath padho, permission-aware retrieval ke liye.

**Formats aur metadata.** Source id, URL, title, author, modified time, path ya object type aur owner rakho. Ye citations, filters aur debugging ko chalate hain.

**Observability.** Har run ke liye items read, added, changed, deleted, failed aur kitna time laga, record karo. Jab connector ruk jaaye ya failure counts achanak badh jayein, alert do.

**Changes pakadne ke tareeke:**

| Method | Kaise kaam karta hai | Dhyaan rakho |
| --- | --- | --- |
| Change ya delta tokens | API saved token ke baad ke changes deti hai | Tokens expire ya toot sakte hain; full re-scan fallback rakho |
| Modified-since filter | Pichhli run ke baad modified time waale items query karta hai | Aksar deletions miss karta hai; clocks aur time zones match hone chahiye |
| Webhooks | Kuch badalne par system aapko call karta hai | Calls kho sakti hain; periodic check ke saath jodo |
| Full comparison | Saare ids list karke index se compare karta hai | Bade sets par slow; hafte mein ek baar safety net ke roop mein achha |

**Build, buy ya borrow.** Airbyte ya Fivetran jaise integration platforms common systems ke liye hafton ka time bachate hain, aur search platform ke bundled connectors pehle se permissions padh sakte hain. Phir bhi inhein check karna padta hai: confirm karo ki woh deletions report karte hain, access rights padhte hain, aur aisi run counts dikhate hain jin par aap alert laga sako. Apna likho jab system anokha ho, jaise in-house database ya vendor portal, ya jab client ki security team third-party tool approve na kare.

**Code mein ek incremental connector.** SharePoint ya OneDrive library ke liye Microsoft Graph ki delta query badle aur delete hue items page-by-page deti hai, aur ant mein ek link deti hai jo agli baar use hota hai:

```python
import hashlib, json, time
from pathlib import Path
import httpx

STATE = Path("state/sharepoint-delta.json")

def get(client, url):
    for attempt in range(5):
        r = client.get(url)
        if r.status_code in (429, 503):
            time.sleep(int(r.headers.get("Retry-After", 2 ** attempt)))
            continue
        r.raise_for_status()
        return r.json()
    raise RuntimeError("gave up after repeated throttling")

def sync(token, drive_id, index):
    counts = {"read": 0, "upserted": 0, "deleted": 0, "skipped": 0, "failed": 0}
    url = (json.loads(STATE.read_text())["delta_link"] if STATE.exists()
           else f"https://graph.microsoft.com/v1.0/drives/{drive_id}/root/delta")
    with httpx.Client(headers={"Authorization": f"Bearer {token}"}, timeout=30) as client:
        while url:
            page = get(client, url)
            for item in page.get("value", []):
                counts["read"] += 1
                try:
                    if "deleted" in item:
                        index.delete_doc(item["id"]); counts["deleted"] += 1
                    elif "file" in item:
                        text = download_and_parse(client, item)            # your parser
                        digest = hashlib.sha256(text.encode()).hexdigest()
                        if index.hash_of(item["id"]) == digest:
                            counts["skipped"] += 1
                        else:
                            index.upsert_doc(item["id"], text, digest, meta_from(item))
                            counts["upserted"] += 1
                except Exception:
                    counts["failed"] += 1
            url = page.get("@odata.nextLink")
            if not url and "@odata.deltaLink" in page:
                STATE.parent.mkdir(exist_ok=True)
                STATE.write_text(json.dumps({"delta_link": page["@odata.deltaLink"]}))
    print(counts)
    return counts
```

Pehli run mein koi saved link nahi hota, isliye woh sab kuch padhti hai; baad ki runs sirf changes laati hain. Delta link tabhi save karo jab aakhri page safal ho jaaye, taaki fail hui run changes skip karne ki jagah dohraaye. Agar saved link kaam karna band kar de, toh full re-scan par fall back karo.

**Hafte mein ek reconciliation.** Achhe change feeds bhi kuch cheezein miss kar dete hain. Ids compare karo:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

**Unchanged content ko skip karo.** Jab koi file rename kare ya property edit kare, toh uska modified time badal jaata hai. Har document ke saath extracted text ka hash store karo aur match hone par re-embedding skip karo. Bade libraries par isse embedding cost ka zyadatar hissa bach jaata hai.

**Source ka lihaaz rakho.** Bade first loads client ke time zone mein raat ko chalao, concurrency kam rakho, aur limits client ki IT team ke saath tay karo. Office hours mein client ka SharePoint throttle karwana bharosa kho dene ka sabse tez tareeka hai.

## Ek example se samjho

Gurugram ki ek consumer-goods company ko SharePoint (product sheets, trade-scheme circulars) aur Salesforce (accounts, opportunities) par ek sales assistant chahiye.

SharePoint: chhe sites par read access ke saath ek app registration. 38,000 files ka pehla full sync throttling limits ke andar rehne ke liye do raaton mein chalta hai. Uske baad, har 15 minute mein delta queries sirf badle aur delete hue items deti hain, aam taur par har run mein 200 se 400, jismein lagbhag ek minute lagta hai. Har item ki permissions padhkar store ki jaati hain.

Salesforce: ek read-only integration user, jo sirf Account, Opportunity aur Product objects tak limited hai. Records har 30 minute mein "modified since" query se kheenche jaate hain aur retrieval ke liye chhote text summaries mein badle jaate hain, jahan record id aur owner metadata ke roop mein rakhe jaate hain.

Teesre hafte, regional team ek SharePoint site ka naam badal deti hai aur delta token invalid ho jaata hai. Connector ka error rate alert bajta hai; job us site ke liye raat bhar full re-scan par fall back karti hai, aur kuch miss nahi hota. Client ki IT team ke liye aapka runbook theek isi case ko samjhata hai.

| Measure | Pehle | Baad mein |
| --- | --- | --- |
| SharePoint sync | Har raat full re-read, lagbhag 6 ghante, aksar throttled | Har 15 minute delta, lagbhag 1 minute |
| Salesforce sync | Roz ka export | Har 30 minute |
| Delete hone ke baad bhi searchable documents | Darjanon | Koi nahi, hafte mein check |
| Fail hue sync ka pata chalne mein time | Din | Minutes, alerts ke through |

## Aam galtiyaan

- **Har baar full re-sync.** Change tokens ya modified-since queries use karo.
- **Deletions ko ignore karna.** Delete aur expire hue documents quote hote rehte hain.
- **Bahut zyada access.** Poore tenant ki jagah naam waale sites aur objects ke liye read-only access maango.
- **Failure ke baad resume nahi.** Page 9,000 par crash hone par page 1 se dobara shuru nahi hona chahiye.
- **Chup rehne waale connectors.** Agar sync ruke toh kisi ko alert nahi jaata, toh assistant chupchaap purana ho jaata hai.
- **Client ki IT team ke liye runbook nahi.** Likh kar rakho ki tokens toot jaayein, permissions badlein ya site ka naam badle toh kya karna hai.
- **Run khatam hone se pehle sync cursor save karna.** Phir crash hone par changes hamesha ke liye skip ho jaate hain.
- **Har modified file ko re-embed karna,** chaahe sirf uska metadata badla ho.

## Jab custom connector ki zaroorat nahi

- **Ek baar ka load**, files ke fixed set ke liye: ek baar export karo aur ingest kar do.
- **Platform connector pehle se system cover karta hai**, deletions report karta hai aur permissions padhta hai.
- **Users apne zaroorat ke kuch documents** seedhe upload kar sakte hain.

## Demo se production tak

- **Har run ki counts record karo** aur rukne ya failure spikes par alert do.
- **Cursors tabhi save karo jab run safal ho**, aur full re-scan fallback rakho.
- **Hafte mein ids reconcile karo** taaki chhooti hui deletions pakdi jayein.
- **Content ko hash karo** taaki unchanged documents skip ho jayein.
- **Schedules aur limits** client ki IT team ke saath likhit mein tay karo.

## Practice karo

Microsoft Graph overview padho, phir paging waali koi bhi API chuno jo aap free mein use kar sako (GitHub issues, koi public dataset API, ya developer tenant ke saath Graph).

1. Ek connector likho jo paging ke saath saare items kheenche, rate limits ka maan rakhe aur resume ke liye cursor store kare.
2. Ek incremental mode jodo jo pichhli run ke baad badle items hi laaye, aur ek check jo delete hue items pakde.
3. Har run ki counts (read, added, updated, deleted, failed) record karo aur ek line ka summary print karo.
4. Apna connector chalao, source par ek file delete karo, dobara chalao, aur confirm karo ki us file ke chunks index se gaye.

**Aapka kaam poora jab:** aap apna connector lagaatar do baar chala sako aur dikha sako ki doosri run sirf wahi laayi jo badla, ek deletion samet.
