## Ye kya hai

Zyadatar systems apna zaroori data ek **database** mein rakhte hain. Product badhne par database aksar sabse pehle dabav mein aata hai, kyunki har app server usse baat karta hai aur uska data sahi rehna chahiye. Chaar ideas aapko bahut door tak le jaate hain.

- **Model chunna.** PostgreSQL aur MySQL jaise relational (SQL) databases data ko relationships waali tables mein rakhte hain aur transactions support karte hain. DynamoDB, MongoDB aur Cassandra jaise NoSQL databases usmein se kuch chhodkar aasaan horizontal scale ya flexible documents dete hain.
- **Indexes** chune hue columns ka sorted structure rakhkar lookups tez karte hain.
- **Replication** data ki copies kai servers par rakhta hai, reads baantne aur failures se bachne ke liye.
- **Sharding** jab ek database kaafi na ho, toh data ko hi kai databases mein baant deta hai.

```flow
App servers -[writes]-> Primary
Primary -[replication, may lag]-> Replica 1
Primary -[replication, may lag]-> Replica 2
App servers -[reads]-> Replica 1
```


## Ye kaam kaise karta hai

**Access pattern ke hisaab se model chuno.** Relational database zyadatar products ke liye strong default hai: orders, users aur payments ke saaf relationships hote hain, transactions chahiye aur flexible queries kaam aati hain. NoSQL tab fit hota hai jab simple key lookups ke saath massive write scale, flexible document shapes ya time-series data chahiye. Kai systems dono use karte hain: core data ke liye PostgreSQL aur hot, simple data ke liye Redis ya key-value store.

**Indexes** kitaab ke peeche ke index ki tarah kaam karte hain. Iske bina kisi customer ke orders dhoondhne ke liye har row scan karni padti hai: O(n). `customer_id` par B-tree index ke saath database lagbhag O(log n) mein seedha sahi rows par jump karta hai. `(customer_id, created_at)` par **composite index** unhein time se pehle se sorted bhi lautata hai. Indexes storage lete hain aur writes slow karte hain, isliye unhein asli query patterns ke liye jodo, aur `EXPLAIN` se check karo ki queries unhein use karti hain.

**Replication** har badlaav ko ek **primary** se ek ya zyada **replicas** par copy karta hai. Writes primary par jaate hain; reads replicas par ja sakte hain. Isse read load baant jaata hai aur primary fail hone par replica sambhaal sakta hai. Zyadatar replication asynchronous hota hai, isliye replicas milliseconds ya seconds peeche reh sakte hain. Isi se wo classic bug aata hai jahan user kuch save karta hai aur agli screen par use nahi dikhta; fix hai user ki apni fresh writes primary se padhna.

**Sharding** ek bade table ko **shard key** ke hisaab se kai independent databases mein baant deta hai. Ek hi key value waali har row ek hi shard par rehti hai. Achhi key data aur traffic dono ko barabar failati hai aur ek request ko jo chahiye use ek shard par rakhti hai. Sharding asli complexity jodta hai: shards ke paar queries slow hoti hain, shards ke paar transactions mushkil hain, aur shards jodte waqt data ko hilaana dhyaan maangta hai. Jab tak indexes, caching aur replicas kaafi na ho jaayein, ise taalo.

| Technique | Kya solve karta hai | Cost |
|---|---|---|
| Index | slow lookups aur sorts | storage, slow writes |
| Read replicas | bahut saare reads; failover | replication lag, zyada servers |
| Vertical scaling | sab kuch, thodi der ke liye | price, ceiling |
| Sharding | ek server ke liye bahut zyada data ya writes | complex queries, rebalancing, cross-shard transactions |
| Caching (agla lesson) | hot data ke baar-baar reads | stale data, invalidation |

**Browser mein try karo.** Consistent hashing shard jodne par sirf kuch keys hilaata hai. Chalao aur compare karo.

```python
import hashlib, bisect

def ring(shards, points=50):
    r = sorted((int(hashlib.md5(f"{s}-{i}".encode()).hexdigest(), 16), s) for s in shards for i in range(points))
    return [h for h, _ in r], [s for _, s in r]

def lookup(key, hashes, owners):
    h = int(hashlib.md5(key.encode()).hexdigest(), 16)
    return owners[bisect.bisect(hashes, h) % len(hashes)]

keys = [f"user-{i}" for i in range(10_000)]
before = {k: lookup(k, *ring(["A", "B", "C"])) for k in keys}
after = {k: lookup(k, *ring(["A", "B", "C", "D"])) for k in keys}
moved = sum(before[k] != after[k] for k in keys)
print(f"{moved / len(keys):.0%} of keys moved when adding shard D")
```

## Ek example se samjho

Fatima ki team poore India mein concerts aur events ke liye ek ticketing platform chalati hai. `bookings` table 30 crore rows tak badh gayi thi aur pages slow ho rahe the.

**Step 1: indexes.** "My bookings" screen `SELECT * FROM bookings WHERE user_id = ? ORDER BY created_at DESC LIMIT 20` chalati thi. `EXPLAIN` ne full table scan dikhaya. `(user_id, created_at)` par composite index ne use 4 seconds se 3 milliseconds par la diya.

**Step 2: read replicas.** Events browse karna aur bookings dekhna 90% traffic tha. Unhone do replicas jode aur wo reads wahan route kiye, seat holds aur payments primary par hi rakhe. Primary CPU 85% se 30% par aa gaya. Jaldi hi support tickets aaye: "I booked but my ticket is not showing." Busy sales ke dauran replica lag do seconds tak tha. Unhone app badli ki ki user ke book karne ke baad 30 seconds tak uski apni bookings primary se padhi jaayein.

**Step 3: sharding, baad mein.** Ek saal baad, ek superstar ki tour sale ne writes ko us had se upar pahuncha diya jo ek primary le sakta tha. Unhone bookings ko `user_id` se shard kiya, jisne writes ko barabar baanta aur har user ki history ek shard par rakhi. Unhone `event_id` se shard karne ka socha, par ek hit tour apni saari bookings ek overloaded shard par daal deti, ek **hot shard**. Har event ki seat inventory ek alag, chhoti table mein apne database par rahi, kyunki seat holds ko ek event ke andar strong consistency chahiye thi.

Order matter karta tha: har step agle se sasta tha, aur unhone agla step tabhi liya jab measurements ne dikhaya ki zaroorat hai.

## Aam galtiyaan

**Sab kuch index karna.** Har index har write ko slow karta hai. Un columns ko index karo jinpar aapki asli queries filter aur sort karti hain.

**Replication lag ko ignore karna.** Write ke turant baad replicas se padhne par stale data dikhta hai. Primary se "read your own writes" plan karo.

**Bahut jaldi sharding.** Ye baad ke har badlaav ko mushkil bana deta hai. Pehle indexes, query fixes, caching aur replicas khatam karo.

**Aisi shard key jo hot spots banati hai.** Dates, ya ek popular customer ya event load ko ek shard par dher kar sakte hain. Aisi keys chuno jinki kai barabar use hone waali values hon.

**Hot paths par cross-shard joins ki zaroorat.** Agar aam requests ko har shard padhna pade, toh key aapke access pattern ke liye galat hai.

**NoSQL sirf isliye chunna kyunki wo scalable sunai deta hai.** Agar aapko transactions aur flexible queries chahiye, toh achhe se index kiya hua relational database aksar saalon tak aapka kaam chalayega.
