## Ye kya hai

Ek **test** ek chhota code hota hai jo aapke code ko aapke chune hue input ke saath chalata hai aur check karta hai ki result wahi hai jo aap expect karte ho. Ek **unit test** ek chhote hisse ko, aam taur par ek function ko, akele check karta hai. Result galat ho toh test fail hota hai aur batata hai kahan.

Tests aaj likhe ja rahe code ke liye utne zaroori nahi, jitne uske baad ke har change ke liye. Chhe mahine baad, aap ya aapka teammate ek function badlega. Tests ke bina, ye jaanne ka ek hi tareeka hai ki kuch toota nahi: app mein click karke dekho aur umeed rakho. Tests ke saath, ek command chalao aur seconds mein pata chal jaata hai.

**pytest** Python ka standard testing tool hai. Aap `test_` se shuru hone waale simple functions likhte ho, simple `assert` statements use karte ho, aur pytest unhe dhundhkar chalata hai, aur fail hone par bilkul dikhata hai ki kaunsi values alag thi.

## Ye kaam kaise karta hai

Ek test teen steps follow karta hai, jinhe aksar **arrange, act, assert** kehte hain: inputs taiyaar karo, code ko ek baar call karo, result check karo.

```python
# gst.py
def gst(amount: float, rate: float = 0.18) -> float:
    if amount < 0:
        raise ValueError("amount must not be negative")
    return round(amount * rate, 2)
```

```python
# test_gst.py
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(100) == 18.0

def test_rounds_to_two_decimals():
    assert gst(10.555) == 1.9

def test_negative_amount_is_refused():
    with pytest.raises(ValueError):
        gst(-1)
```

Project folder mein `pytest` chalao aur wo kuch aisa report karega: `3 passed in 0.02s`.

Jis loop mein aap kaam karte ho:

```flow
dir: LR
Code likho ya badlo -> pytest chalao
pytest chalao -[koi test fail hua]-> Failure padho | kaunsi values alag thi
Failure padho -> Code likho ya badlo
pytest chalao -[sab pass]-> Commit
```

Teen tools zyadatar real tests cover karte hain:

| Tool | Kya karta hai | Example use |
| --- | --- | --- |
| `@pytest.mark.parametrize` | Ek test ko kai inputs par chalata hai | Har GST rate: 5%, 12%, 18%, 28% |
| `@pytest.fixture` | Shared setup jo test naam se maangta hai | Ek sample invoice, ek temporary folder |
| Fakes aur mocks | Slow ya external parts ko replace karte hain | Ek model client jo fixed reply deta hai |
| `pytest.raises` | Check karta hai ki error raise hota hai | Negative amounts mana kiye jaate hain |
| `tmp_path` | Har test ke liye naya temporary folder | Files likhne waala code |

Tests copy karne ki jagah **parametrise** karo:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (100, 0.05, 5.0),
    (100, 0.12, 12.0),
    (100, 0.28, 28.0),
])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

**Fixtures** shared setup rakhte hain:

```python
@pytest.fixture
def invoice():
    return {"items": [("Charger", 999.0), ("Cable", 299.0)], "rate": 0.18}

def test_invoice_total(invoice):
    assert invoice_total(invoice) == 1531.64
```

**Fakes** tests ko tez aur repeatable rakhte hain. Agar koi function model client ko parameter ke roop mein leta hai (ise **dependency injection** kehte hain), toh test ek fake pass kar sakta hai:

```python
class FakeClient:
    def complete(self, prompt):
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

**Sabse pehle kya test karein.** Bina tests waale project mein wahan se shuru karo jahan bug sabse mehnga padega: paise ki calculations, wo data jo doosre systems padhte hain, aur wo code jo aap badalne waale ho. Phir har bug fix ke liye ek test jodo. AI projects mein do kism alag rakho: apni parsing, validation aur scoring logic ke tez unit tests, jo har commit par chalte hain, aur real model ke saath golden set par slow evaluation runs, jo schedule par chalte hain. Dono ko mila diya toh rozana ke tests slow aur flaky ho jaate hain.

## Ek example se samjho

Sneha Chennai ki ek logistics company mein invoice-extraction service maintain karti hai. Ek customer report karta hai ki ₹0.50 rounding difference waala ek invoice reject ho gaya. Wo ise bina kuch aur toote fix karna chahti hai.

**Pehle, ek failing test.** Code ko haath lagane se pehle, wo ek test likhti hai jo bug reproduce kare: ek invoice jiski lines ka total ₹1,180.00 hai lekin printed total ₹1,180.50 hai. Test expect karta hai ki ise accept kiya jaaye, kyunki business ₹1 tak ki rounding allow karta hai. Wo pytest chalati hai: naya test fail hota hai, jo saabit karta hai ki wo bug pakad raha hai.

**Phir fix.** `validate_total` mein check `lines_total == printed_total` tha. Wo ise `abs(lines_total - printed_total) <= 1.0` kar deti hai. Naya test pass ho jaata hai.

**Phir edges.** ₹1 ki tolerance naye sawaal khade karti hai, isliye wo parametrise karti hai: bilkul ₹1 ka difference accept ho, ₹1.01 reject ho, negative difference ko positive jaisa hi treat kiya jaaye. Ek case fail hota hai: floating-point error ki wajah se uska check ₹1.01 ka difference accept kar leta tha. Wo amounts ko `Decimal` mein badal deti hai, aur saare cases pass ho jaate hain.

**Aakhir mein, poora suite.** Wo saare 214 tests chalati hai. Ek unrelated test fail hota hai: wo ek forged invoice reject karne ke liye purane exact-match behaviour par tika tha. Wo team se baat karti hai, sab maante hain ki forgery check ko alag rule use karna chahiye, aur wo dono update karti hai. Tests ke bina, wo forgery check production mein chupchaap kaam karna band kar deta.

## Aam galtiyaan

- **Sirf happy path test karna.** Bugs edges par rehte hain: zero, empty lists, negatives, bahut bade values, missing fields.
- **Ek test jo das cheezein check kare.** Fail hone par pata nahi chalta kaunsi. Ek test mein ek behaviour, aise naam ke saath jo bataye kya.
- **Aise tests jo ek doosre ya order par depend karte hain.** Har test ko jo chahiye wo khud set up karna chahiye aur akele pass hona chahiye.
- **Unit tests mein real network ya model calls.** Slow hote hain, paise lagte hain aur tests ko flaky banate hain. Unhe fake karo; real service ko alag se aur kam baar test karo.
- **Bug fix hone ke baad tests likhna.** Pehle failing test likho, taaki pata ho ki wo sach mein bug pakadta hai.
- **100% coverage ke peeche bhaagna.** Coverage dikhata hai kya chala, ye nahi ki check hua ya nahi. Jo behaviour matter karta hai use test karo.
