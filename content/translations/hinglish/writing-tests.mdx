## Ye kya hai

**Test** code ka ek chhota hissa hai jo aapke code ko aapke chune hue input ke saath chalata hai aur check karta hai ki result wahi hai jo aap expect karte ho. **Unit test** ek chhota hissa, aamtaur par ek function, akele mein check karta hai. Result galat ho to test fail hota hai aur batata hai kahaan.

Tests aaj likhe code ke liye utne zaroori nahi jitne uske baad aane waale har change ke liye. Chhah mahine baad aap ya aapka koi teammate kisi function ko badlega. Tests ke bina, ye jaanne ka ek hi tareeka hai ki kuch toota nahi: app mein click karte jao aur ummeed karo. Tests hon to ek command chalao aur kuch seconds mein pata chal jaata hai.

**pytest** Python ka standard testing tool hai. Aap seedhe-saade functions likhte ho jinke naam `test_` se shuru hote hain, aur seedhe-saade `assert` statements use karte ho. pytest unhe dhoondhta hai, chalata hai, aur jab koi fail hota hai to theek-theek dikhata hai ki kaun si values alag thi.

Shuru se ek limit yaad rakho: test wahi pakadta hai jo aapne check karne ka socha. Cases chunna hi asli skill hai, aur is lesson ka zyaadatar hissa usi chunaav ke baare mein hai.

## Ye kaam kaise karta hai

### Aapke pehle tests

Ek test ke teen steps hote hain, jinhe aksar **arrange, act, assert** kehte hain: inputs taiyaar karo, code ko ek baar call karo, result check karo.

Ye raha ek GST helper. Ye `Decimal` use karta hai, jo Python ka exact decimal type hai, kyunki money mein drift nahi hona chahiye (kyun, ye agla hissa dikhata hai). Is example ke liye maan lo finance team ka rule ye hai: paisa tak round karo, aur aadha paisa upar jaata hai. Ye rule ek business decision hai, to apni finance team se confirm kar lena.

```python
# gst.py
from decimal import Decimal, ROUND_HALF_UP

PAISA = Decimal("0.01")

def gst(amount: Decimal, rate: Decimal = Decimal("0.18")) -> Decimal:
    """GST on an amount, rounded to the paisa, half a paisa rounded up."""
    if amount < 0:
        raise ValueError("amount must not be negative")
    return (amount * rate).quantize(PAISA, rounding=ROUND_HALF_UP)
```

```python
# test_gst.py
from decimal import Decimal as D
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(D("100")) == D("18.00")

def test_half_paisa_rounds_up():
    # 100.25 x 0.18 = 18.045 exactly, so it must round up to 18.05
    assert gst(D("100.25")) == D("18.05")

def test_negative_amount_is_refused():
    with pytest.raises(ValueError, match="negative"):
        gst(D("-1"))
```

Folder mein `pytest` chalao aur ye `3 passed` print karta hai. Har naam batata hai ki wo kis behaviour ki ummeed karta hai, to failure report ek vaakya jaisi padhi jaati hai. `match=` error message bhi check karta hai, taaki test kisi aur `ValueError` ki wajah se galti se pass na ho jaaye.

Jis loop mein aap kaam karte ho:

```flow
dir: LR
Code likho ya badlo -> pytest chalao
pytest chalao -[koi test fail hua]-> Failure padho | kaun si values alag thi
Failure padho -> Code likho ya badlo
pytest chalao -[sab pass]-> Commit
```

### Money aur floats

Seedhe floats kyun nahi? Yahi function `round(amount * rate, 2)` se likho aur rounding test fail ho jaata hai:

```
>       assert gst(100.25) == 18.05
E       assert 18.04 == 18.05
E        +  where 18.04 = gst(100.25)
```

Float numbers ko binary mein store karta hai, aur zyaadatar decimal fractions ka koi exact binary roop nahi hota. `100.25 * 0.18` 18.044999999999998... ke roop mein store hota hai, beech waale point se zara neeche, isliye ye neeche round ho jaata hai. Ye error 15ve digit mein chhupi nahi hai: customer ko ek paisa galat bill dikhta hai. Isse teen rules nikalte hain:

- **Money:** strings se bana `Decimal` use karo (`Decimal("100.25")`), ya poore paise integers ke roop mein store karo. Kabhi `Decimal(0.1)` mat likho: ye float ki error copy kar leta hai aur 0.1000000000000000055511151231257827.... deta hai.
- **Jo floats money nahi hain** (model ka confidence score, ek average, ek similarity): `pytest.approx` se compare karo, jo default mein das lakh mein ek ka relative difference allow karta hai.
- **Compute kiye gaye floats par kabhi `==` nahi.** Ye aapke laptop par tabhi tak chalta hai jab tak inputs nahi badalte.

```python
def test_mean_score_needs_approx():
    # (0.1 + 0.2) / 2 is 0.15000000000000002, so == 0.15 alone fails
    assert (0.1 + 0.2) / 2 == pytest.approx(0.15)
```

### Copy karne ki jagah parametrise karo

22 September 2025 se GST ke do main slabs hain, 5% aur 18%, aur saath mein goods ke ek chhote set ke liye ek special 40% rate, jaise sugary fizzy drinks aur badi cars. (Puraane 12% aur 28% slabs hata diye gaye, haalaanki kuch special rates abhi bhi hain.) Ek parametrised test slabs aur zero waale edges cover kar leta hai:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (D("1000"), D("0.05"), D("50.00")),
    (D("1000"), D("0.18"), D("180.00")),
    (D("1000"), D("0.40"), D("400.00")),
    (D("1000"), D("0"), D("0.00")),
    (D("0"), D("0.18"), D("0.00")),
], ids=["5-percent", "18-percent", "40-percent", "zero-rate", "zero-amount"])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

Har row apne alag test ki tarah report hoti hai, jaise `test_rates[40-percent]`, to failure case ka naam batata hai. `ids` ke bina pytest in rows ko `amount0-rate0-expected0` jaise naam deta hai, jo padhne mein mushkil hain.

### Fixtures aur conftest.py

**Fixture** shared setup hai jise test apne parameter mein uska naam likhkar maangta hai. Jo fixtures kai test files use karti hain unhe `conftest.py` mein rakho; pytest us file ko apne aap load karta hai, import ki zaroorat nahi.

```python
# invoice.py
from decimal import Decimal
from gst import gst

def invoice_total(invoice: dict) -> Decimal:
    subtotal = sum((price for _, price in invoice["items"]), Decimal("0"))
    return subtotal + gst(subtotal, invoice["rate"])
```

```python
# conftest.py
from decimal import Decimal as D
import pytest

@pytest.fixture
def invoice():
    return {"items": [("Charger", D("999.00")), ("Cable", D("299.00"))],
            "rate": D("0.18")}
```

```python
# test_invoice.py
from decimal import Decimal as D
from invoice import invoice_total

def test_total_adds_gst_to_subtotal(invoice):
    assert invoice_total(invoice) == D("1531.64")   # 1298.00 + 233.64

def test_empty_invoice_totals_zero(invoice):
    invoice["items"] = []          # changes only this test's copy
    assert invoice_total(invoice) == D("0")
```

Default mein fixture har test ke liye phir se chalti hai, to ek test use badal de to doosra nahi toot-ta. Bada scope (`scope="session"`) sirf us setup ke liye use karo jo dheema hai aur kabhi nahi badalta, jaise ek badi sample file load karna. Fixture apni value `yield` kar sakti hai aur `yield` ke baad clean up kar sakti hai. Built-in `tmp_path` fixture, files likhne waale code ke liye, har test ko ek naya temporary folder deti hai.

### Model aur API calls ke liye fakes

Asli model calls dheemi hoti hain, paise lagte hain, aur har baar alag reply de sakti hain. Unit tests mein inhe ek **fake** se badlo jo ek fixed reply return kare. Kisi hisse ko aise badalne ko **mocking** kehte hain.

Agar code aap likh rahe ho, to sabse saaf design hai client ko parameter ki tarah pass karna. Ise **dependency injection** kehte hain:

```python
# triage.py
import json

def classify(ticket: str, client) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    return json.loads(reply)["category"]
```

```python
# test_triage.py
from triage import classify

class FakeClient:
    def complete(self, prompt: str) -> str:
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

Jo code aapko viraasat mein milta hai, usmein zyaadatar client module level par ek baar banaya jaata hai. Tab aap use pytest ke `monkeypatch` se swap karte ho, jo test ke baad original waapas rakh deta hai. `unittest.mock.Mock` fake banata hai aur record karta hai ki use kaise call kiya gaya. Ye version bad replies bhi handle karta hai, aur AI projects mein sabse zyaada test karne laayak code yahi hai:

```python
# llm.py
class ModelClient:
    """Stands in for a real model SDK client."""
    def complete(self, prompt: str) -> str:
        raise RuntimeError("this would make a real, paid network call")
```

```python
# tickets.py
import json
from llm import ModelClient

client = ModelClient()          # created once, when the module is imported
CATEGORIES = {"refund", "delivery", "other"}

def classify(ticket: str) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    try:
        category = json.loads(reply)["category"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return "needs_review"
    return category if category in CATEGORIES else "needs_review"
```

```python
# test_tickets.py
from unittest.mock import Mock
import pytest
import tickets
from llm import ModelClient

def fake_client(reply: str) -> Mock:
    fake = Mock(spec=ModelClient)    # only methods the real client has
    fake.complete.return_value = reply
    return fake

def test_reads_category_and_sends_ticket(monkeypatch):
    fake = fake_client('{"category": "refund"}')
    monkeypatch.setattr(tickets, "client", fake)
    assert tickets.classify("Money not returned") == "refund"
    fake.complete.assert_called_once()
    assert "Money not returned" in fake.complete.call_args.args[0]

@pytest.mark.parametrize("reply", [
    "Sure! This looks like a refund.",   # prose, not JSON
    '{"label": "refund"}',               # wrong key
    '{"category": "lottery"}',           # unknown category
    "null",                              # valid JSON, wrong shape
    "",                                  # empty reply
])
def test_bad_reply_goes_to_review(monkeypatch, reply):
    monkeypatch.setattr(tickets, "client", fake_client(reply))
    assert tickets.classify("Where is my parcel?") == "needs_review"
```

Do gotchas jo experienced engineers ko bhi phansa dete hain:

- **Patch wahaan karo jahaan naam use hota hai, wahaan nahi jahaan define hota hai.** Agar `tickets.py` mein `from llm import client` likha hota, to uske paas us naam ki apni copy hoti, to `llm.client` patch karne se kuch nahi badalta aur asli call phir bhi chal jaati. `tickets.client` patch karo.
- **Saada `Mock()` koi bhi attribute maan leta hai.** Koi typo, ya asli client mein rename hua koi method, test mein phir bhi "chal" jaata hai aur bug production tak pahunch jaata hai. `Mock(spec=ModelClient)` har us cheez par `AttributeError` raise karta hai jo asli class mein nahi hai.

Kab kya use karein:

| Situation | Use karo | Kyun |
| --- | --- | --- |
| Naya code jo aap likh rahe ho | Client pass karo (dependency injection) | Patching nahi; test theek-theek dikhata hai ki code ko kya chahiye |
| Module-level client waala inherited code | Jo module use use karta hai us par `monkeypatch.setattr` | Ek test ke liye ek naam swap karta hai aur baad mein waapas rakh deta hai |
| Aapko check karna hi hai ki kya bheja gaya, jaise prompt | `Mock(spec=...)` aur `call_args` | Har call record karta hai; spec typos pakadta hai |
| Files likhne waala code | Built-in `tmp_path` fixture | Har test ke liye naya folder, peeche kuch nahi chhootta |
| Asli model ka behaviour | Golden set par evaluation run, unit test nahi | Unit tests jawaab ki quality nahi parakh sakte |

### Unit tests banaam evaluations

AI projects mein do tarah ke tests alag rakho. Tez unit tests aapka apna logic check karte hain: prompts banana, replies parse karna, validation, scoring. Ye har commit par chalte hain. Dheeme **evaluations** inputs ka ek fixed golden set asli model ko bhejte hain aur jawaabon ko score karte hain, taaki pakda ja sake ki kisi prompt change ya model update ne results kharaab kar diye. Inhe kaise banayein, ye "Test sets and evals" lesson (P1) mein hai. Dono ko milaane se roz ke tests dheeme, mehenge aur flaky ho jaate hain.

Ek **marker** inhe alag rakhta hai. Use `pyproject.toml` mein register karo; `--strict-markers` galat type hue marker ko warning ki jagah error bana deta hai:

```toml
[tool.pytest.ini_options]
addopts = "--strict-markers"
markers = ["eval: calls the real model on the golden set; run on a schedule"]
```

Har evaluation test par `@pytest.mark.eval` tag lagao, aur har commit par `pytest -m "not eval"` chalao.

### Roz tests chalana

| Command | Kya karta hai |
| --- | --- |
| `pytest -x` | Pehle failure par ruk jaata hai |
| `pytest -k rounding` | Sirf wo tests chalata hai jinke naam mein "rounding" hai |
| `pytest test_gst.py::test_half_paisa_rounds_up` | Ek test chalata hai |
| `pytest --lf` | Sirf wo tests phir se chalata hai jo pichhli baar fail hue |
| `pytest -m "not eval"` | `eval` mark waale tests skip karta hai |
| `pytest --cov=. --cov-report=term-missing` | Coverage dikhata hai, un line numbers ke saath jo kisi test ne nahi chalaayi (`pytest-cov` package chahiye) |

**Coverage** aapke code ka wo hissa hai jo tests ke dauraan chala. "Missing" column padho: usmein wo lines hain jo kisi test ne nahi chalaayi, aur wahi aapke blind spots hain. `--cov-branch` jodo taaki aisa `if` bhi dikhe jiska true ya false side kabhi nahi chala. Lekin coverage sirf ye saabit karta hai ki code chala, ye nahi ki kisi ne result check kiya: jo test bina `assert` ke `gst(D("100"))` call karta hai, wo bhi gina jaata hai. Ise gaps dhoondhne ke liye use karo, 100% tak pahunchne waale score ki tarah nahi.

**Continuous integration (CI)** har push ya pull request par wahi command ek saaf machine par chalata hai, aur fail hone par team merging rok deti hai. Do cheezein wahaan toot-ti hain jo aapke laptop par pass hoti hain. Pehli, CI machine par sirf wo packages hote hain jo aapka project list karta hai, to koi missing dependency saamne aa jaati hai. Doosri, CI machines aksar UTC use karti hain, jo India se saadhe paanch ghante peechhe hai. Tab "aaj" waala koi test IST mein aadhi raat se subah 5:30 ke beech chalne par fail ho sakta hai. Date ya clock apne code mein pass karo, aur machine ki setting par bharosa karne ki jagah time zone ka naam do (`ZoneInfo("Asia/Kolkata")`).

### Pehle kya test karein

Jis project mein koi tests nahi hain, wahaan se shuru karo jahaan bug sabse mehenga padega:

1. **Money aur kaanooni kuch bhi:** totals, tax, refunds, limits.
2. **Wo data jo doosre systems padhte hain:** aapki API jo JSON return karti hai, aap jo CSV export karte ho.
3. **Wo code jo aap badalne waale ho:** pehle aise tests likho jo uska abhi ka behaviour pin kar dein, phir use badlo.
4. **Har bug jo aap fix karte ho:** pehle ek test jo use reproduce kare, phir fix. Ise **regression test** kehte hain; ye wahi bug waapas aane se rokta hai.

Project mein tests kahaan rehte hain (ek `tests/` folder, ek `src` layout, README commands), iske liye "Project tooling: environments, tests and logs" lesson dekho.

## Ek example se samjho

Sneha Chennai ki ek logistics company mein ek invoice-extraction service maintain karti hai. Service ek scan kiya hua invoice padhti hai, line amounts aur chhapa hua total nikaalti hai, aur dono na milein to invoice reject kar deti hai. Ek customer report karta hai ki ek asli invoice reject ho gaya. Uski lines hain freight ₹1,040.37, loading ₹128.98 aur toll ₹10.65, jinka jod ₹1,180.00 hai, lekin chhapa hua total ₹1,180.50 hai. Business ₹1 tak ka rounding difference allow karta hai (is example ke liye ek illustrative rule).

**Pehle, ek fail hone waala test.** Code chhoone se pehle wo ek test likhti hai jo bug reproduce kare aur expect kare ki invoice accept ho. Wo pytest chalaati hai aur naya test fail hota hai. Isse saabit hota hai ki test sach mein bug pakadta hai; jo test fix se pehle hi pass ho jaaye, wo kuch saabit nahi karta.

**Phir fix.** Puraana check tha `sum(lines) == printed_total`. Wo ise badalkar ₹1.00 tak ka difference allow karti hai, aur naya test pass ho jaata hai.

**Phir edges.** Ek limit ke do edges hote hain, to wo parametrise karti hai: theek ₹1 upar aur theek ₹1 neeche accept hone chahiye, aur kisi bhi taraf ₹1.01 reject. Ek case fail hota hai: theek ₹1 upar waala reject ho jaata hai. Floats iski wajah batate hain. Python 3.12 ya uske baad ke versions mein teenon lines ka `sum()` 1180 nahi, `1179.9999999999998` deta hai (puraane versions mein, ya `+` se jodne par, sanyog se 1180.0 aata hai), to 1181.00 se difference `1.0000000000002274` hai, limit se zara upar. Wo extractor ko badalti hai taaki amounts text ke roop mein de, aur check ko `Decimal` use karne ke liye:

```python
# validate.py
from decimal import Decimal

TOLERANCE = Decimal("1.00")          # business rule: up to Rs 1 of rounding

def total_is_valid(line_amounts: list[str], printed_total: str) -> bool:
    lines_total = sum((Decimal(a) for a in line_amounts), Decimal("0"))
    return abs(lines_total - Decimal(printed_total)) <= TOLERANCE
```

```python
# test_validate.py
import pytest
from validate import total_is_valid

LINES = ["1040.37", "128.98", "10.65"]      # add up to exactly 1180.00

@pytest.mark.parametrize("printed, expected", [
    ("1180.50", True),    # the customer's bug: 50 paise of rounding
    ("1181.00", True),    # exactly Rs 1 over: allowed
    ("1179.00", True),    # exactly Rs 1 under: allowed
    ("1181.01", False),   # just over the limit
    ("1178.99", False),   # just under the limit
], ids=["50-paise", "plus-1", "minus-1", "plus-1.01", "minus-1.01"])
def test_rounding_tolerance(printed, expected):
    assert total_is_valid(LINES, printed) is expected
```

Paanchon cases pass hote hain. Dhyaan do ki float bug kisne pakda: customer waale case ne nahi, balki theek limit waale edge ne. Bugs edges par hi rehte hain.

**Aakhir mein, poora suite.** Wo project ke saare tests, kuch sau, ek minute se kam mein chalaati hai. Ek asambandhit test fail hota hai: wo ek nakli invoice ko reject karne ke liye puraane exact match par nirbhar tha, jiska total kuch paise badal diya gaya tha. Wo team se baat karti hai. Sab maante hain ki forgery check ko apna alag rule chahiye, aur wo dono update karti hai. Tests ke bina, wo forgery check production mein kaam karna band kar deta aur kisi ko pata nahi chalta.

## Aam galtiyaan

- **Sirf happy path test karna.** Bugs edges par rehte hain: zero, empty lists, negatives, theek limit, bahut badi values, missing fields.
- **Ek test jo das cheezein check kare.** Jab wo fail hoga, aap bata nahi paoge kaun si. Har test mein ek behaviour, aise naam ke saath jo bataaye kya.
- **Aise tests jo ek-doosre par ya order par nirbhar hon.** Har test khud apni zaroorat ka setup kare aur akele chalaane par bhi pass ho. Module level par shared lists ya dictionaries aamtaur par iski wajah hoti hain.
- **Unit tests mein asli network ya model calls.** Ye dheemi hain, paise lagte hain aur tests ko flaky banaati hain. Inhe fake karo, aur asli model ko ek scheduled evaluation run se parkho.
- **Floats ko `==` se compare karna, ya float se `Decimal` banana.** Money ke liye `Decimal("1.10")` aur baaki floats ke liye `pytest.approx` use karo.
- **Galat jagah patch karna, ya `spec` ke bina `Mock` use karna.** Asli call phir bhi chal jaati hai, ya typo chupchaap pass ho jaata hai.
- **Code kya karta hai uski jagah ye test karna ki wo kaise karta hai.** Jo test check kare ki kaun sa private helper call hua, wo har harmless refactor par toot-ta hai. Outputs aur dikhne waale effects check karo.
- **Aisa test jise aapne kabhi fail hote nahi dekha.** Use fix se pehle likho, ya ek baar jaan-boojhkar code todo. Jo test fail ho hi nahi sakta, wo kisi cheez ki raksha nahi karta.
- **Clock ya machine ke time zone par nirbhar rehna.** Dates pass karo aur jab din maayne rakhta ho to `Asia/Kolkata` naam se do.
- **100% coverage ke peechhe bhaagna.** Coverage dikhata hai ki kya chala, ye nahi ki wo check hua ya nahi. Jo behaviour maayne rakhta hai use test karo.
