## Ye kya hai

Serving ka matlab hai apni application ko aise chalaana ki real users us par bharosa kar sakein. Wo apne-aap start hoti hai, crash hone par restart hoti hai, ek saath kai requests sambhaalti hai, extra load ko saaf tareeke se mana karti hai, aur model dheema ho tab bhi jaldi kuch dikha deti hai.

Ek Python AI service ke liye aam stack hai app ke liye FastAPI aur use chalaane waale server ke roop mein **Uvicorn**, kai worker processes ke saath. HTTPS sambhaalne aur traffic baantne ke liye aage kuch baitha hota hai, jaise ek load balancer, ek ingress, ya Cloud Run jaisa koi platform.

AI services ek aam web API se teen tarah se alag hain. Requests dheemi hoti hain, aksar 2 se 30 seconds, kyunki wo model calls ka intezaar karti hain. Users ise tabhi jhelte hain jab unhe progress dikhe, isiliye **streaming** zaroori hai. Aur jo resource kam hai wo kisi aur ka hai: provider aapki requests aur tokens prati minute limit karta hai, isliye aamtaur par bottleneck aapka CPU nahi, uska quota aur aapka bill hota hai.

```flow
Users -[HTTPS]-> Load balancer | idle timeout 30 s, ready instances ko bhejta hai
Load balancer -> Container 1 | 4 Uvicorn workers, har ek mein zyaada se zyaada 40 model calls
Load balancer -> Container 2 | waisa hi
Container 1 -[deadline 25 s, retries inside]-> Model API | tokens user tak stream hokar aate hain
Container 1 -> Background queue | OCR aur indexing; ek job id return karti hai
```

Is lesson mein hum Lucknow ki ek edtech company ke doubt-solving assistant ke saath chalenge, jo har shaam rengne lagta tha.

## Ye kaam kaise karta hai

### Workers aur event loop

Ek Uvicorn process apne async endpoints ek hi **event loop** par chalaata hai. Jab ek request model ka await kar rahi hoti hai, loop baaki requests ko serve karta hai, isliye ek process saikdon intezaar karti requests sambhaal sakta hai. Lekin jo bhi cheez loop ko block kare, wo us process ki har request ko freeze kar deti hai: ek synchronous Redis, database ya `requests` call, PDF parsing, ek local embedding model.

Ilaaj: network calls ke liye ek **async client** use karo; ya endpoint ko ek saada `def` likho, jise FastAPI ek thread pool mein chalaata hai; ya bhaari kaam ko ek **background queue** par le jaao. Phir kai workers chalao, aamtaur par har CPU core par ek ya do, taaki ek crash sab kuch na gira de. Jo service zyaadatar kisi model API ka intezaar karti hai, uske liye workers jodne se zyaada blocking calls hataana madad karta hai.

### Layers mein timeouts

Har wait ki ek limit chahiye, andar waali baahar waali se chhoti, warna baahar waali pehle fire hogi aur user ko aapke message ki jagah ek khaali load balancer error milega. Ek **total** timeout poori request par cap lagaata hai. Ek **idle** timeout chuppi par cap lagaata hai, isliye jo stream bhejti rahe wo kabhi nahi katti; udaaharan ke liye, AWS Application Load Balancer default roop se 60-second idle timeout use karta hai.

Official Anthropic Python SDK mein ek jaal hai. Uska `timeout` connect karne par aur agle chunk ke har wait par, har attempt ke liye alag se lagta hai; ye total deadline nahi hai. Ye default roop se 429s aur server errors ko do baar retry bhi karta hai, aur utna intezaar karta hai jitna provider ka `retry-after` header kahe. Isliye `timeout=30, max_retries=2` ek request ko 90 seconds se kaafi aage tak rok sakta hai. Poori call ke chaaron ore apni ek deadline rakho, retries uske andar.

| Layer | Kis tarah ka | Example value | Ye kya pakadta hai |
| --- | --- | --- | --- |
| SDK `timeout` | Har attempt, har chunk par | 10 s | Ek dead connection ya ruki hui stream |
| SDK `max_retries` | Ginti | 1 | Provider ki ek chhoti error; usi budget mein se kharch hota hai |
| Aapki deadline | Total, retries samet | 25 s | Upar ka sab kuch, aapke likhe message ke saath |
| Load balancer | Aamtaur par idle | 30 s | Ek latka hua instance; layers sahi hon toh kabhi pehle fire nahi hota |
| Shutdown grace | Total | 30 s server, 40 s platform | Deploy ke dauraan katti streams |

### Streaming, aur use kya todta hai

**Server-sent events** (SSE) mein server response ko khula rakhta hai aur har tukda ek `data:` line ke roop mein bhejta hai. Version 0.135.0 se FastAPI ise seedhe support karta hai: `response_class=EventSourceResponse` set karo aur endpoint se `yield` karo. FastAPI har item ko JSON ke roop mein encode karta hai, isliye answer mein ek newline format ko nahi tod sakti. Ye `Cache-Control: no-cache` aur `X-Accel-Buffering: no` (nginx ke liye ek hint) set karta hai, aur 15 seconds chuppi ke baad ek keep-alive comment bhejta hai.

Streaming generation ko tez nahi karti; ye intezaar ko chhota mehsoos karaati hai, kyunki pehle shabd ek-do second mein aa jaate hain. Dikkatein sirf production mein dikhti hain:

- **Buffering proxies.** Koi ingress, proxy ya compression layer poora response rok kar rakh sakti hai, toh users ko pehle kuch nahi dikhta aur phir sab ek saath. nginx default roop se proxied responses ko buffer karta hai, aur sirf header hamesha kaafi nahi hota. Us route ke liye buffering off karo (nginx mein `proxy_buffering off;`) aur real path se test karo.
- **Idle timeouts.** Ek lambi chuppi, jaise jab model ek lamba prompt padh raha ho, balancer ko trip kar sakti hai. Keep-alive comments uske idle timeout se zyaada baar aane chahiye.
- **Browser mein POST.** `EventSource` request body nahi bhej sakta; POST stream ko `fetch` aur ek stream reader se padho.
- **Beech mein failure.** Ek 200 aur aadhe answer ke baad status code nahi badal sakta. Ek error event bhejo, aadha text "answer interrupted, try again" ke saath dikhao, aur use kabhi cache mat karo. Inhe apne logs mein gino, kyunki status-code dashboards inhe miss kar dete hain.
- **Disconnects.** Jab tab band hota hai, FastAPI generator ko cancel karta hai aur SDK ka `async with` model stream ko band kar deta hai, toh bina padhe tokens ke paise dena band ho jaata hai.

### Endpoint

Load shed karne waala ek concurrency cap, model call ke chaaron ore ek deadline, JSON events aur padhne laayak errors. API ke ek local fake ke against FastAPI 0.165, Anthropic SDK 2.14 aur Python 3.13 ke saath test kiya gaya; iske liye FastAPI 0.135.0 ya uske baad ka aur Python 3.11 ya uske baad ka chahiye.

```python
import asyncio
import anthropic
from fastapi import Depends, FastAPI, HTTPException
from fastapi.sse import EventSourceResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=10, max_retries=1)   # per attempt, per chunk
SLOTS = asyncio.Semaphore(40)      # at most 40 model calls at once in this process
MODEL_DEADLINE = 25                # seconds for the whole model call, retries included

class Question(BaseModel):
    text: str

async def model_slot():
    try:                                         # wait at most 1 s for a free slot
        await asyncio.wait_for(SLOTS.acquire(), timeout=1)
    except TimeoutError:
        raise HTTPException(429, "Busy, please try again in a few seconds",
                            headers={"Retry-After": "5"})
    try:
        yield                                    # the request streams here
    finally:
        SLOTS.release()                          # after the stream ends, even on disconnect

async def with_deadline(chunks, seconds):
    loop = asyncio.get_running_loop()
    end = loop.time() + seconds
    it = aiter(chunks)
    while True:
        try:
            yield await asyncio.wait_for(anext(it), end - loop.time())
        except StopAsyncIteration:
            return

async def model_text(question: str):
    async with client.messages.stream(
            model="claude-sonnet-5-5", max_tokens=600,      # check the docs for current names
            messages=[{"role": "user", "content": question}]) as stream:
        async for text in stream.text_stream:
            yield text

@app.post("/answer", response_class=EventSourceResponse)
async def answer(body: Question, _: None = Depends(model_slot)):
    try:
        async for text in with_deadline(model_text(body.text), MODEL_DEADLINE):
            yield {"text": text}
        yield {"done": True}
    except TimeoutError:
        yield {"error": "This is taking longer than usual. Please try again."}
    except anthropic.APIError:
        yield {"error": "The AI service is busy. Please try again."}

@app.get("/health")
async def health():
    return {"ok": True}
```

Ise aisa kyun banaaya gaya hai:

- **Slot response shuru hone se pehle liya jaata hai**, ek dependency mein, kyunki 200 jaane ke baad 429 bhejna naamumkin hai. Ek second ka wait chhote bursts ko sokh leta hai; usse aage, ek chup queue se ek tez "busy" behtar hai. Stream khatam hone par, disconnect par bhi, `finally` slot waapas kar deta hai.
- **Deadline har wait ko lapet-ti hai, yield ko nahi.** `with_deadline` har step ko, retries ke saath stream kholne samet, ek hi end time ke against time karta hai. Kisi `yield` ke chaaron ore timeout block async generators mein gadbad karta hai.
- **Cap har process ka alag hai**: 40 slots, 4 workers aur 2 containers matlab ek saath 320 calls.

### Rate limits: aapki aur provider ki

Shaam ke peak par provider ka 429 sabse aam failure hai. Backoff aur **jitter** (wait ka ek random hissa, taaki hazaaron clients ek hi pal mein retry na karein) ke saath thodi der retry karo; SDK ye karta hai aur `retry-after` ko maanta hai, toh ginti itni kam rakho ki deadline mein fit ho. Phir saaf tareeke se fail karo, ya ek gateway ke zariye kisi doosre region ya approved chhote model par fallback karo (LLM gateways waala lesson dekho). **Har user ko bhi limit karo**, jaise 10 minute mein 20 sawaal aur ek daily token cap, warna ek script sabka quota khatam kar sakti hai aur aapke bill ki koi seema nahi rahegi. Aapke apne 429 mein `Retry-After` hota hai, aur aapke front end ko use maanna chahiye.

### Health, readiness aur shutdown

- **`/health`** (liveness) batata hai ki process zinda hai aur kisi aur cheez ko nahi chhoota, taaki platform sirf unhi processes ko restart kare jo sach mein atke hain.
- **`/ready`** (readiness) batata hai ki ye instance traffic le sakta hai: start-up ka kaam, jaise index load karna, poora hone tak 503. Ise kisi shared dependency par fail mat karo. Agar har instance ek hi database check kare, toh ek blip sabko ek saath fail kar deti hai aur balancer sabko hata deta hai, jisse partial outage total outage ban jaata hai. Har request par ek saaf error return karo aur alag se alert karo.
- **Dono mein se koi model ko call nahi karta.** Ismein paise lagte hain, aur ek dheema provider har instance ko ek saath unhealthy mark kar dega.

**Graceful shutdown.** Deploy par platform SIGTERM bhejta hai. Server connections lena band karta hai aur chal rahi requests ko `--timeout-graceful-shutdown` tak poora hone deta hai. Ye aapki sabse lambi stream se zyaada hona chahiye, aur platform ka grace period server waale se zyaada, warna platform pehle hi process ko kill kar dega. Kubernetes default roop se 30 seconds deta hai (`terminationGracePeriodSeconds` badhao). Cloud Run SIGTERM ke baad sirf 10 seconds deta hai, toh wahaan scale-down ke dauraan lambi streams kat sakti hain; client ko retry ka option dene do.

### Ise chalaana

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4 \
  --timeout-graceful-shutdown 30
```

Do workers waale ek test mein, SIGTERM aane par chal rahi ek stream ne apne saare tokens poore kiye, jabki nayi requests serve nahi huin. Agar aap Gunicorn use karte ho, toh dhyaan rakho ki haal ke Uvicorn versions `uvicorn.workers` ko deprecate karte hain; `uvicorn-worker` package use karo (`-k uvicorn_worker.UvicornWorker`).

### Queue ke saath background jobs

Jo kaam minuton leta hai, jaise OCR ya 500 pages ke PDF ko index karna, wo ek worker process par jaata hai, aur request turant ek job id return karti hai. Redis Queue (RQ) ke saath:

```python
from fastapi import HTTPException
from redis import Redis
from rq import Queue
from rq.exceptions import DuplicateJobError

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents/{doc_id}/index")
def start_indexing(doc_id: str):        # plain def: runs in a thread, so Redis cannot block the loop
    job_id = f"index-{doc_id}"          # same document, same job id
    try:
        queue.enqueue("workers.index_pdf", doc_id, job_id=job_id, unique=True,
                      job_timeout=1800, result_ttl=86400)
    except DuplicateJobError:
        pass                            # a double click or a client retry: the job already exists
    return {"job_id": job_id, "status_url": f"/jobs/{job_id}"}

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    if job is None:
        raise HTTPException(404, "Unknown or expired job")
    return {"status": job.get_status()}
```

RQ 2.8 mein joda gaya `unique=True` submission ko **idempotent** banaata hai: ek hi request do baar aaye toh ek hi job banta hai. `result_ttl` poore hue job ko ek din tak rakhta hai; default 500 seconds hai, jiske baad status URL 404 return karta hai. Worker ko bhi do baar chalne par safe banao, kyunki worker beech mein crash ho sakta hai. Celery, Arq aur cloud task queues bhi yahi pattern follow karte hain.

### Measure aur observe karna

Har request ki ek line log karo: request id, user, model, tokens, cost, time to first token, total time aur outcome (done, deadline, provider error, shed). p95 time to first token, shed rate aur provider 429 rate par nazar rakho; ek request ko services ke paar follow karna tracing waala lesson cover karta hai. Launch se pehle aur har change ke baad Locust jaise kisi tool se shaam ke peak ka load-test karo.

### Apne browser mein try karo

Saath requests ek saath aati hain; ek saath das hi chal sakti hain. Ek aisi queue jo kabhi mana nahi karti, uski tulna 429 se pehle ek chhote wait se karo.

```python
import asyncio, random, time

async def model_call(slots, max_wait, waits):
    t0 = time.perf_counter()
    try:
        await asyncio.wait_for(slots.acquire(), max_wait)   # None queues forever
    except asyncio.TimeoutError:
        return "rejected"                                   # send a fast 429: busy, retry soon
    waits.append(time.perf_counter() - t0)                  # time spent waiting for a slot
    try:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model call
    finally:
        slots.release()
    return "served"

async def burst(cap, max_wait, n=60):
    slots, waits = asyncio.Semaphore(cap), []
    results = await asyncio.gather(*(model_call(slots, max_wait, waits) for _ in range(n)))
    print(f"max_wait {str(max_wait):>4}: served {results.count('served'):>2}, "
          f"rejected {results.count('rejected'):>2}, worst wait {max(waits, default=0):.2f} s")

random.seed(1)
for max_wait in (None, 0.1, 0.01):
    await burst(cap=10, max_wait=max_wait)
```

Bina limit ke, aakhri request shuru hone se pehle lagbhag paanch model-call ke barabar samay intezaar karti hai; jab real calls seconds leti hain, toh yahi wo chup spinner hai jise dekhkar users chhod jaate hain. Ek chhote wait ke saath, extra requests ko turant "busy" sunne ko milta hai.

## Ek example se samjho

Ye ek illustrative case hai: numbers dikhaate hain ki kis tarah ke badlaav ki umeed karein, ye koi measured study nahi hai. Lucknow ki ek edtech ka doubt-solving assistant ek hi Uvicorn process par chalta tha. Shaam ko students ko koi bhi text dikhne ke liye lagbhag 12 seconds intezaar karna padta tha. Lagbhag ek tihaai requests load balancer ki 30-second limit se takraati thin, kyunki bina stream waala answer poora hone tak kuch nahi bhejta. Upload kiye gaye haath se likhe notes par OCR ek `async def` endpoint ke andar chalta tha aur sabke liye server ko freeze kar deta tha.

Badlaav:

- FastAPI ke SSE support ke saath **streaming**. Staging mein answer phir bhi ek saath aata tha, kyunki nginx ingress use buffer kar raha tha; `/answer` ke liye buffering off karne se theek ho gaya.
- **Har container mein chaar workers, do containers**, har worker mein 40 model slots, ye check karne ke baad ki ek saath 320 calls provider quota mein fit hoti hain.
- **Layers mein timeouts**: ek retry ke saath SDK 10 s, har model call par 25 s deadline, aur dono ke upar balancer ka 30 s idle timeout. Deadline fire hone par student ko "This is taking longer than usual; please try again" dikhta hai.
- **Limits**: har student ke liye 10 minute mein 20 sawaal, aur saare slots busy hone par `Retry-After` ke saath ek tez 429, jo "Many students are asking right now, retrying in 5 seconds" ke roop mein dikhta hai.
- **OCR ek background queue par**, file se derive kiye gaye job id ke saath, taaki ek double tap se ek hi job bane. Result ready hone tak page "Reading your notes..." dikhaata hai.
- **Health aur deploys**: `/ready` sirf start-up check karta hai; graceful shutdown 30 s hai, 40 s ke platform grace period ke andar.

| Shaam ke peak par measure (illustrative) | Pehle | Baad mein |
| --- | --- | --- |
| Pehle text tak ka samay, p95 | Lagbhag 12 s | Lagbhag 1 se 2 s |
| Timeout se takraati requests | Lagbhag 33% | 1% se kam |
| OCR uploads se server freeze | Roz | Koi nahi |
| Answer se pehle chhodne waale students | Baseline | Lagbhag do tihaai kam |
| Students tak pahunchte provider 429s | Aksar, khaali errors ke roop mein | Kabhi-kabhaar, ek saaf "busy, retrying" ke roop mein |

## Aam galtiyaan

- **`async def` ke andar ek sync client.** Ek blocking Redis, database ya HTTP call us worker ki har request ko freeze kar deti hai.
- **SDK timeout ko deadline maan lena.** Retries aur `retry-after` waits uske upar judte jaate hain.
- **Stream ke andar cap check karna.** Tab tak 200 ja chuka hota hai aur 429 naamumkin hai.
- **Ye bhool jaana ki caps guna hote hain.** 4 workers aur 3 containers mein har process par 50 matlab ek saath 600 calls, shaayad provider quota se bahut zyaada.
- **Streaming ko sirf localhost par test karna**, jahaan koi proxy use buffer nahi karta.
- **Kisi shared dependency par readiness check.** Ek database blip har instance ko ek saath hata deti hai.
- **Platform se lamba server grace period.** Platform pehle process ko kill kar deta hai aur streams phir bhi kat jaati hain.
- **Clients jo 429 par turant retry karte hain**, aur ek chhote overload ko lambe overload mein badal dete hain.
- **Random job ids**, jisse ek double click wahi mehenga job do baar start kar deta hai.

## Jab saada serving kaafi hai

- **Kuch hi users waale internal tools**: ek process, model calls par ek deadline aur ek health check kaafi hain.
- **Batch jobs** jo kabhi users ke saamne nahi aate: web service se ek scheduled script behtar hai.
- **Serverless routes**, jahaan platform workers aur shutdown sambhaalta hai. Uski time limit ko apni sabse lambi stream se milaakar check karo.

## Demo se production tak

- **Blocking calls hatao**, phir kai workers chalao.
- **Model calls par** aur har user par **cap lagao**, aur total ko provider quota se milaakar check karo.
- **Timeouts ko layers mein rakho** aur real path se stream karo.
- **Lambe kaam ko queue karo**, idempotent job ids ke saath, aur grace periods set karo.
- **Har request par log karo**: tokens, cost, time to first token aur outcome; p95 par nazar rakho.

FastAPI ka deployment concepts page aur streaming par uska custom responses page padho.

1. Model tokens ko server-sent events ke roop mein stream karo, aur browser mein time to first token pehle aur baad mein measure karo.
2. Slot dependency ko 2 ke cap ke saath jodo, ek saath 3 requests bhejo, aur confirm karo ki teesri ko lagbhag ek second ke andar 429 milta hai.
3. Aage nginx ya apne platform ka ingress lagao, confirm karo ki stream tukdon mein aati hai, phir buffering on karo aur use toot-te dekho.
4. Ek dheeme task ko idempotent job id ke saath background job par le jaao. Use do baar submit karo aur confirm karo ki sirf ek job chalta hai.
5. `--workers 4 --timeout-graceful-shutdown 30` ke saath chalao, ek lambi stream shuru karo, server roko aur confirm karo ki stream poori hoti hai.
