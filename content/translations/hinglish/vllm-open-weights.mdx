## Ye kya hai

**Open-weight models** apne weights publish karte hain, isliye aap unhe unke licence ke tahat apne hardware par chala sakte ho. **vLLM** ek open-source engine hai jo aise models ko GPUs par kushalta se serve karta hai. Do ideas ise tez banaate hain.

- **PagedAttention.** Jab model jawaab likhta hai, to wo har pichhle token ki ek memory rakhta hai, jise **KV cache** kehte hain. Puraane servers har request ke liye sabse lambe mumkin jawaab jitna ek lamba block reserve kar dete the, aur uska zyadatar hissa khaali pada rehta tha. vLLM cache ko chhote pages mein rakhta hai, jo request badhne par hi judte hain, theek waise jaise operating system memory manage karta hai. Bahut kam barbaad hota hai, isliye ek GPU par kahin zyada requests fit hoti hain.
- **Continuous batching.** GPU sabse efficient tab hota hai jab wo ek saath kai requests par kaam kare. vLLM poore batch ke khatam hone ka intezaar karne ki jagah, har step par, jaise-jaise doosri requests khatam hoti hain, nayi requests ko batch mein judne deta hai.

vLLM ek **OpenAI-compatible API** expose karta hai, isliye zyadatar client code aur gateways uske saath bina badle kaam karte hain.

```flow
title: vLLM server se hokar ek request
dir: LR
Client or gateway -[OpenAI-style API, ek key ke saath]-> vLLM server
vLLM server -> Scheduler | continuous batching: requests har step par judti aur nikalti hain
Scheduler -> KV cache in pages | PagedAttention; prompts ki ek jaisi shuruaat dobara use hoti hai
KV cache in pages -> GPU memory | weights aur cache ise share karte hain
vLLM server -> Metrics | queue length, cache usage, time to first token
```

Ye lesson Chennai ki ek insurance company ko follow karta hai jise claim documents apne hi servers par rakhne hain.

## Ye kaam kaise karta hai

### Model chunna

Leaderboard se nahi, task aur apne evals se shuru karo. Phir chaar cheezein check karo.

- **Licence.** Aaj ke kai models, jinmein Qwen3.5 family aur Gemma 4 shaamil hain, Apache 2.0 ke tahat release hue hain. Kuch doosre shartein jodte hain; Meta ka Llama community licence iska ek example hai. Aap jo exact weights download karte ho, unke saath aane waali licence file padho.
- **Size aur type.** 4 se 14 billion parameters waale models ek GPU par chalte hain aur extraction, classification aur grounded RAG answers ke liye aksar kaafi hote hain. Qwen3.5-35B-A3B (35 billion parameters, har token par lagbhag 3 billion active) jaise **mixture-of-experts (MoE)** model ko apne saare parameters ke liye memory chahiye, par wo lagbhag ek chhote model jitni tezi se generate karta hai.
- **Context length.** Long-context models kaam ke hain, par lambe contexts ki keemat aap cache memory mein chukaate ho.
- **Bhashayein.** Models ke beech ye baaki kisi bhi cheez se zyada badalta hai. Agla section dekho.

November 2026 tak, aam starting points mein ye shaamil hain: Qwen3.5 (0.8B se 397B tak sizes, February aur March 2026 mein release), Qwen3.6 (April 2026) aur Qwen3.8-27B (August 2026), Gemma 4 (E2B se 31B tak), aur OpenAI ke gpt-oss-20b aur gpt-oss-120b. Har mahine naye models aate hain, isliye ise test karne ki ek shortlist samjho, ranking nahi.

### Bhartiya bhashaon ke liye model chunna

Teen checks kisi bhi benchmark se zyada batate hain.

1. **Har word par tokens (fertility).** Zyadatar English text par bana tokenizer, Malayalam ya Odia ke words ko kai chhote tukdon mein tod deta hai. Agar kisi model ko har word par teen guna tokens chahiye, to har request par teen guna compute lagta hai, zyada samay lagta hai, aur usi context mein kam text fit hota hai. Ise apne users ke 200 asli sentences par naapo:

```python
from transformers import AutoTokenizer

sentences = open("malayalam_sample.txt", encoding="utf-8").read().splitlines()
words = sum(len(s.split()) for s in sentences)
for name in ["Qwen/Qwen3.5-9B", "google/gemma-4-E4B-it"]:   # add every candidate
    tok = AutoTokenizer.from_pretrained(name)
    tokens = sum(len(tok.encode(s, add_special_tokens=False)) for s in sentences)
    print(f"{name}: {tokens / words:.2f} tokens per word")
```

2. **Native speakers ka review kiya hua golden set.** Native script, romanised text (Manglish, Hinglish) aur code-mixed messages shaamil karo, kyunki asli users inhe milaakar likhte hain. Machine-translated test sets kamzor models ko asal se behtar dikhaate hain.
3. **Har bhasha ke liye quantized quality.** Quantization aksar English ki tulna mein lower-resource bhashaon mein zyada quality giraata hai. Bhartiya bhashaon ke evals usi quantized checkpoint par chalao jise aap asal mein serve karoge.

Test mein shaamil karne laayak candidates:

- **Aam multilingual models.** Qwen3.5 kehta hai ki wo 201 languages aur dialects support karta hai; Gemma 4 bhi multilingual kaam ke liye kaafi use hota hai.
- **Bharat ke liye bane models.** Sarvam AI ne February 2026 mein Sarvam-30B aur Sarvam-105B launch kiye, dono mixture-of-experts models jinhe Bhartiya bhashaon ko dhyaan mein rakhkar train kiya gaya, aur Sarvam ke mutaabik Apache 2.0 ke tahat. BharatGen ka Param2-17B-A2.4B-Thinking bhi vLLM ke supported models mein listed hai.
- **Ek translation step.** AI4Bharat ka IndicTrans2 (MIT licence) English aur 22 scheduled Bhartiya bhashaon ke beech translate karta hai. Aisi pipeline jo translate kare, ek strong English model chalaaye, aur wapas translate kare, kabhi behtar hoti hai, kabhi badtar. Ise bhi baaki options ki tarah test karo.

Gotcha: check karo ki aapka vLLM version us exact checkpoint ko support karta hai. Jab Sarvam ke models launch hue, tab unka model card ek pending vLLM pull request ki taraf ishaara karta tha; ab v0.34.0 ki supported-models list mein Sarvam ke architectures shaamil hain.

### GPU chunna

Kya fit hoga, ye memory tay karti hai. Tokens kitni tezi se niklenge, ye **memory bandwidth** tay karti hai, yaani GPU apni memory kitni tezi se padhta hai, kyunki har naya token saare active weights ko ek baar padhta hai.

| GPU memory | Example GPUs | 16-bit par fit | 4-bit par fit |
| --- | --- | --- | --- |
| 24 GB | NVIDIA L4, RTX 4090 | Lagbhag 8B tak, chhote contexts | Lagbhag 14B tak |
| 48 GB | NVIDIA L40S, RTX 6000 Ada | Lagbhag 14B tak | 27B se 32B, cache ke liye jagah ke saath |
| 80 GB | NVIDIA A100 80 GB, H100 | 27B se 32B, thoda cache | Lagbhag 70B, theek-thaak cache |
| 141 GB | NVIDIA H200 | Lagbhag 60B | Kul lagbhag 100B waale MoE models |

Bharat mein aap inhe E2E Networks, jo Delhi NCR aur Chennai mein H100 capacity list karta hai, aur Yotta jaise local GPU clouds se kiraaye par le sakte ho. Yogya startups, researchers aur institutions sarkaar ke IndiaAI Compute Portal par subsidised hours ke liye apply kar sakte hain. Prices aksar badalte hain, isliye jis din plan karo, usi din providers ke pages check karo.

### Memory ka hisaab

**Weights.** 16-bit par lagbhag 2 bytes per parameter, 8-bit par 1 byte aur 4-bit par aadhe byte se thoda zyada. 27B model ko 16-bit par lagbhag 54 GB aur 4-bit par lagbhag 15 GB chahiye.

**KV cache.** Ek standard transformer mein, har token ko `2 × layers × KV heads × head size × bytes` chahiye. 2 keys aur values ke liye hai. Ye chaaron numbers model ki `config.json` se padho. Phir ise in flight tokens se guna karo: concurrent requests guna unki average length.

**Apne browser mein try karo.** Ye ek aam 8B model ka shape (32 layers, 8 KV heads, head size 128) 16-bit par use karta hai:

```python
layers, kv_heads, head_dim, bytes_per = 32, 8, 128, 2
per_token = 2 * layers * kv_heads * head_dim * bytes_per      # 131,072 bytes
for users, context in [(10, 4000), (40, 4000), (40, 16000)]:
    gb = per_token * users * context / 1e9
    print(f"{users} users x {context} tokens: {gb:.1f} GB of KV cache")
```

Ye lagbhag 5, 21 aur 84 GB print karta hai. Ek GPU kitne users ko serve karega, ye aamtaur par model nahi, context length tay karti hai.

Do gotchas. Qwen3.5 jaise naye **hybrid** models lagbhag har chaar mein se ek layer mein hi full attention use karte hain, isliye unka cache is formula se kahin chhota hota hai. Cache ko 8-bit par store karne (`--kv-cache-dtype fp8`) se wo aadha ho jaata hai, par quality par asar hota hai jise aapko naapna hoga.

### Quantization

Weights ko 8 ya 4 bits mein store karne se weight memory lagbhag aadhi ya teen-chauthaai kam ho jaati hai, aur aksar generation bhi tez hota hai, thode quality loss ke saath. Aam formats hain **AWQ** aur **GPTQ** (4-bit) aur **FP8** (8-bit). Aisa checkpoint download karo jo pehle se quantized ho, jaise model maker ka publish kiya hua; vLLM uski config se method padh leta hai. `--quantization` flag kisi 16-bit model ko AWQ mein nahi badalta. Exception hai `--quantization fp8_per_tensor` (sirf `fp8` ab aisa nahi karta), jo FP8 support waale GPUs, jaise L40S aur H100, par load time par quantize karta hai.

### Ise chalaana

28 November 2026 tak maujooda release **vLLM v0.34.0** (16 November 2026) hai. Kuch naya aaya ho to GitHub par vLLM releases page check karo.

```bash
pip install vllm==0.34.0
vllm serve Qwen/Qwen3.5-9B --max-model-len 8192 --served-model-name chat-local
# now: POST http://localhost:8000/v1/chat/completions
```

Container mein, weights ek volume par rakhkar:

```bash
docker run --gpus all --rm -p 8000:8000 \
  -v /data/hf-cache:/root/.cache/huggingface \
  -e HF_TOKEN -e VLLM_API_KEY \
  vllm/vllm-openai:v0.34.0 \
  --model Qwen/Qwen3.5-9B --revision <commit> \
  --max-model-len 8192 --served-model-name chat-local
```

`<commit>` ki jagah Hugging Face se model ka commit hash daalo, taaki restart kabhi badle hue weights pull na kare. `--served-model-name` wo naam set karta hai jo clients use karte hain, isliye aap apps badle bina model swap kar sakte ho.

| Setting | Example | Asal mein kya karta hai |
| --- | --- | --- |
| `--max-model-len` | 8192 | Ek request ki length par cap lagata hai. vLLM start-up par check karta hai ki aisi ek request cache mein fit hoti hai; ye har request ke liye itna reserve nahi karta |
| `--gpu-memory-utilization` | set mat karo | v0.34.0 se, set na karne ka matlab 1.0 hai. Ise, jaise 0.5 par, tabhi set karo jab koi doosra process GPU share karta ho |
| `--tensor-parallel-size` | 2 | Ek machine mein ek model ko kai GPUs par baant-ta hai |
| `--kv-cache-dtype` | fp8 | Cache memory aadhi karta hai; quality naapo |
| `--speculative-config` | JSON | Speculative decoding: ek tez guesser tokens draft karta hai aur model unhe check karta hai, jisse kam load par latency ghatti hai |

**v0.34.0 mein memory ka badlaav.** Puraane releases, jab tak alag se na kaha jaaye, GPU memory ka 90%, baad mein 92%, use karte the. v0.34.0 NVIDIA aur AMD GPUs par ek **extensible KV cache** on karta hai: ye cache ko warm-up ke baad asal mein free memory se size karta hai, aur set na kiya gaya `--gpu-memory-utilization` ab 1.0 ka matlab rakhta hai. Release notes zyadatar configs se ye flag hataane ki salaah dete hain. Isse do gotchas nikalte hain. Usi GPU par koi doosra process, jaise ek embedding model, ab koi memory nahi paata jab tak aap har ek ke liye share set na karo. Aur notes kehte hain ki kuch models par per-token latency badh sakti hai; opt out karne ke liye `--gpu-memory-utilization 0.9` ya `--no-enable-extensible-kv-cache` pass karo. Default `--block-size` bhi 16 se 64 ho gaya hai.

**Reasoning models.** Aaj ke kai models jawaab dene se pehle "think" karte hain. Model ko kaun-se reasoning-parser aur tool-call-parser flags chahiye, ye GitHub par vLLM ki recipes repository mein us model ke page par dekho. Inke bina thinking text jawaab mein aa jaata hai aur JSON parsing tod deta hai.

### Structured output ke saath ise call karna

```python
import os
from openai import OpenAI
from pydantic import BaseModel

class Claim(BaseModel):
    policy_number: str
    amount_inr: int
    reason: str

client = OpenAI(base_url="http://localhost:8000/v1", api_key=os.environ["VLLM_API_KEY"])
r = client.chat.completions.create(
    model="chat-local",
    messages=[{"role": "user", "content": "Extract: Policy HX-22981, claim of Rs 18,400 for a cracked windscreen."}],
    response_format={"type": "json_schema", "json_schema": {"name": "claim", "schema": Claim.model_json_schema()}},
)
print(Claim.model_validate_json(r.choices[0].message.content))
```

Server generation ko schema ke andar baandh deta hai, isliye reply parse ho jaata hai. Phir bhi values check karo, jaisa structured-output lesson mein samjhaaya gaya hai.

### Endpoint ko secure karna

`--api-key` (ya `VLLM_API_KEY` variable) sirf `/v1` ke neeche ke routes aur kuch doosre prefixes ko protect karta hai. vLLM docs chetaavni dete hain ki doosre routes, jaise `/invocations`, khule rehte hain. Isliye vLLM ko kabhi seedhe expose mat karo. Ise apne gateway ke peeche rakho, aur Kubernetes network policy use karo taaki sirf gateway hi us tak pahunch sake.

### Go-live se pehle load testing

Badhti concurrency par asli jaise prompts bhejo aur time to first token aur total time record karo:

```python
import asyncio, time
from openai import AsyncOpenAI

aclient = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="your-key")

async def one(prompt):
    t0 = time.perf_counter(); first = None
    stream = await aclient.chat.completions.create(model="chat-local", stream=True, max_tokens=300,
                                                   messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if first is None and chunk.choices and chunk.choices[0].delta.content:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0

async def run(prompts, concurrency):
    sem = asyncio.Semaphore(concurrency)
    async def limited(p):
        async with sem:
            return await one(p)
    results = await asyncio.gather(*(limited(p) for p in prompts))
    ttft = sorted(r[0] for r in results if r[0]); total = sorted(r[1] for r in results)
    print(f"c={concurrency}: p95 first token {ttft[int(0.95 * (len(ttft) - 1))]:.2f}s, "
          f"p95 total {total[int(0.95 * (len(total) - 1))]:.2f}s")

# for c in (1, 8, 32, 64): asyncio.run(run(sample_prompts, c))
```

Sabse oonchi concurrency jo p95 first-token time ko aapke budget ke andar rakhe, wahi ek replica ki capacity hai.

### Ise operate karna

vLLM `/metrics` par Prometheus metrics expose karta hai. Alert aur scale CPU par nahi, `vllm:num_requests_waiting` (queue) aur `vllm:kv_cache_usage_perc` (cache kitna bhara hai) par karo. Prefix caching default roop se on hai: jo requests ek hi system prompt ya document se shuru hoti hain, wo uska cache dobara use karti hain. Shared content ko prompts ki shuruaat mein rakho, aur hit rate ko `vllm:prefix_cache_hits` bhaag `vllm:prefix_cache_queries` ke roop mein track karo. Ek spare replica rakho taaki koi failure ya upgrade service na roke, aur weights ko ek internal volume mein rakho, kyunki start-up par downloads dheeme hote hain aur locked-down networks par aksar block ho jaate hain.

## Ek example se samjho

Chennai ki ek insurance company ko claim documents apne hi servers par rakhne hain. Use claim forms se 20 fields extract karne hain aur apne claims staff ke liye chhote grounded answers chahiye, din mein lagbhag 30,000 requests. Neeche ke saare numbers method dikhaane ke liye sirf udaharan hain.

**Model.** 300 asli forms par evals, jinmein Tamil forms bhi hain, teen open-weight models ki tulna ek frontier API se karte hain. Sabse achha ek 27B dense model hai: API ke 97% ke muqaable 95% field accuracy. Data apne premises par rakhne ke liye company ye gap maan leti hai.

**Memory.** 16-bit par weights ko 54 GB chahiye, jo 48 GB waale L40S ke liye zyada hai. Maker ka 4-bit AWQ checkpoint lagbhag 15 GB leta hai, aur evals sirf 94.5% tak girte hain. Maan lo runtime overhead lagbhag 7 GB leta hai, to cache ke liye lagbhag 26 GB bachta hai. Model ki config 64 layers, 8 KV heads aur head size 128 batati hai, to har token ko 2 × 64 × 8 × 128 × 2 bytes, lagbhag 0.26 MB chahiye. Yaani lagbhag 99,000 tokens ki jagah, ya average 3,000 tokens waali lagbhag 33 requests.

**Traffic.** 10 ghante ke working day mein 30,000 requests yaani lagbhag 0.8 per second; maan lo peak iska doguna hai, lagbhag 1.7 per second. Agar har request lagbhag 6 seconds leti hai, to in flight requests = arrival rate × har ek ka samay (Little's law) = 1.7 × 6, lagbhag 10. Ek GPU 33 sambhaalta hai, isliye wo peak jhel leta hai. Doosra GPU headroom deta hai aur failures aur upgrades ke dauraan service chaalu rakhta hai. Ek load test pakka karta hai ki 30 concurrent requests par p95 first-token time 2 seconds se kam hai.

**Cost.** Maan lo har GPU ₹100 per hour ka hai, ye ek udaharan waala figure hai, quote nahi. 730 ghante ke mahine ke liye do GPUs ka kharcha ₹1,46,000 hai, yaani 9,00,000 requests per month par lagbhag ₹162 per 1,000 requests. Maan lo API ₹100 per million input tokens aur ₹400 per million output tokens leta hai, ye bhi udaharan hai. 3,000 input aur 300 output tokens waali har request ₹0.42 ki padti hai, yaani ₹420 per 1,000. Break-even hai ₹1,46,000 ÷ ₹0.42, lagbhag 3,48,000 requests per month ya 11,600 per day. Din mein 3,000 requests par self-hosting lagbhag ₹1,620 per 1,000 padega. Kisi bhi figure mein GST ya ise chalaane waale engineer ka samay shaamil nahi hai.

vLLM company ke Kubernetes cluster par pinned containers mein chalta hai, pehle waale usi gateway ke peeche, isliye application mein sirf ek model alias badalta hai. Upgrades har timaahi hote hain, eval suite pass hone ke baad.

## Aam galtiyaan

- **Leaderboard se model chunna.** Apne data par, apne users ki bhashaon aur scripts mein test karo.
- **Sizing mein KV cache bhool jaana.** Weights fit ho jaate hain, phir load padne par server dheema ho jaata hai ya atak jaata hai. In flight tokens ke hisaab se size karo.
- **`--max-model-len` ko model ke maximum par set karna.** 262,144-token ki limit ek GPU par start-up par hi fail ho sakti hai. Ise utna rakho jitna aapke traffic ko chahiye.
- **Aadat se `--gpu-memory-utilization 0.9` aage le jaana.** v0.34.0 par ye cache se memory rok leta hai. Ise tabhi set karo jab GPU share ho.
- **Bina naape quantize karna,** khaaskar Bhartiya bhashaon mein, jo English se zyada quality kho sakti hain.
- **Licences ko nazarandaaz karna.** Un exact weights ki licence file padho.
- **Unpinned image, engine ya model revision,** jisse restart chupchaap outputs badal deta hai.
- **vLLM ko seedhe expose karna,** sirf `--api-key` ke saath; kuch routes khule rehte hain.

## Jab vLLM se self-host na karein

- **Kam ya achaanak oopar-neeche hone waala volume,** jahan idle GPUs ka kharcha API calls se zyada hota hai; break-even nikaalo.
- **Aapko sabse strong models chahiye,** jo shaayad sirf APIs ke roop mein milein.
- **Ise chalaane waala koi nahi.** GPUs, drivers, upgrades aur on-call asli kaam hain.

## Demo se production tak

- **Image, vLLM version aur model revision pin karo,** weights ko volumes par cache karke.
- Har model ya setting badalne ke baad **load test karo**, aur ek replica ki capacity record karo.
- **Queue length aur KV cache usage par alert aur scale karo.**
- Ise ek alias, ek fallback aur ek network policy ke saath **gateway ke peeche rakho**.
- Failures aur rolling upgrades ke liye **ek spare replica rakho**.

## Practice karo

Jo bhi GPU aapki pahunch mein ho, us par vLLM quickstart follow karo, aur PagedAttention waala post padho. Ek free notebook GPU par chhota model chal sakta hai; agar vLLM use reject kare, to docs mein supported GPUs ki list hai.

1. Qwen3.5-2B jaisa ek chhota instruct model serve karo aur use OpenAI client se call karo.
2. 9B, 27B aur 70B model ki weight memory 16-bit aur 4-bit par nikaalo, aur table se har ek ke liye GPU chuno.
3. Apni jaani-pehchaani kisi Bhartiya bhasha ke 200 sentences par do models ke liye har word par tokens naapo.
4. Apna golden set self-hosted model aur ek API model par chalao, aur accuracy, latency aur cost per 1,000 requests ki tulna karo.
5. Load test chaar concurrency levels par chalao aur sabse ooncha level likho jo p95 first-token time ko 2 seconds se kam rakhe.

Aur gehraai ke liye, Chip Huyen ki *AI Engineering* (O'Reilly, 2025) ka chapter 9 inference servers, batching, prefix caching aur throughput aur latency naapne ko cover karta hai.

**Aapka kaam poora hai jab aap** kisi model ko OpenAI-compatible endpoint ke peeche serve kar sako aur uske size, quantization, GPU aur cost ko numbers ke saath justify kar sako.
