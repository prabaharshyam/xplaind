## Ye kya hai

Aapke pehle n8n workflow mein ek trigger aur kuch nodes the. Jin workflows par koi business tika hota hai, wo isse aage jaate hain. Wo hazaaron records process karte hain, sakht limits waali APIs ko call karte hain, aise do systems ka data jodte hain jo aapas mein mel nahi khaate, aur unhein tab bhi chalte rehna hota hai jab raat 3 baje kuch fail ho aur koi dekh na raha ho.

Inmein se har cheez ke liye n8n mein ek building block hai:

| Building block | Kis kaam ka |
| --- | --- |
| **Sub-workflows** | Saajha steps jinhein kai workflows call karte hain, functions ki tarah |
| **Paging, batches aur waits** | Kisi API ki limits tode bina data fetch karna aur bhejna |
| **Merge** | Do sources ko ek shared id se jodna, match na hone waale items samet |
| **Code nodes** | Chhote JavaScript ya Python snippets, us logic ke liye jo visual nodes cover nahi karte |
| **AI nodes** | Emails jaise bikhre text ko padhkar aise fields banaana jinhein rules check kar sakein |
| **Error workflows** | Automatic run fail hone par kisi insaan ko alert karna |

Ye lesson Bengaluru ke ek skincare brand ko follow karta hai jo apna daily payment reconciliation automate karta hai, yaani ye check karne ka kaam ki har prepaid order ka paisa payment gateway ne sach mein pay out kiya ya nahi.

```flow
title: Roz ka payment reconciliation
Schedule: subah 6 baje IST -> Shopify: prepaid orders, pichhle 10 din
Schedule: subah 6 baje IST -> Gateway: settled payments, pichhle 3 din | pages mein, raftaar control karke
Shopify: prepaid orders, pichhle 10 din -> Payment id par Merge | dono taraf ke unmatched items rakhta hai
Gateway: settled payments, pichhle 3 din -> Payment id par Merge
Payment id par Merge -> Code: har row ko flag karo -> Sub-workflow: sheet mein upsert -> Slack: summary
Koi bhi failure -> Error workflow | execution link ke saath finance-ops ko alert
```

## Ye kaise kaam karta hai

### Items: har cheez ke neeche ka idea

Har node **items** ki ek list leta hai aur ek list aage bhejta hai. Har item ek JSON record hai, jaise sheet ki ek row. Zyaadatar nodes har item ke liye ek baar chalte hain: Gmail mein das items gaye toh das emails. `{{ $json.email }}` jaisa **expression** current item ka ek field padhta hai. Kisi pichhle node ka field padhne ke liye us node ka naam lo: `{{ $('Get orders').item.json.order_name }}`.

### Structure: ek workflow, ek kaam

Har workflow ko ek kaam tak rakho. Saajha steps ko ek **sub-workflow** mein rakho: ek alag workflow jo **When Executed by Another Workflow** trigger se shuru hota hai aur **Execute Sub-workflow** node se call hota hai. Trigger mein koi bhi data lene ki jagah wo input fields define karo jinki aapko ummeed hai, jaise `payment_id` aur `flag`. Phir call karne waala node theek-theek batata hai ki kaun-se fields bharne hain, aur koi chhoot jaaye toh aasaani se dikh jaata hai.

Nodes ke naam unke kaam ke hisaab se rakho, jaise "Get prepaid orders", na ki "HTTP Request 3", taaki koi bhi canvas padh sake.

### Volume aur rate limits

Zyaadatar APIs results ek baar mein ek **page** deti hain aur limit lagaati hain ki aap ek second ya ek minute mein kitni requests bhej sakte ho. Teen tools saath milkar kaam karte hain:

- **Pagination** page ke baad page fetch karta hai jab tak aur pages na bachein. HTTP Request node mein pagination option hai, aur kai app nodes mein "Return All" switch hota hai jo aapke liye paging kar deta hai.
- **Batching** control karta hai ki aap kitni tezi se bhejte ho. HTTP Request node mein Batching option hai (har batch mein kitne items, aur batches ke beech pause). Zyada control ke liye batch size ke saath **Loop Over Items** aur loop ke andar ek **Wait** node use karo.
- **Retry On Fail**, jo har node ki settings mein hai, fail hui call ko dohraata hai. Ye zyada se zyada paanch tries aur unke beech zyada se zyada paanch seconds deta hai, isliye ye chhoti-si rukaavat sambhaalta hai, pacing nahi aur lamba outage bhi nahi.

Pacing ka rule seedha hisaab hai. Agar limit ek minute mein L requests hai aur har batch B requests bhejta hai, toh batches ke beech kam se kam B × 60 ÷ L seconds wait karo. Ek batch mein 20 requests aur ek minute mein 60 ki limit ho, toh 20 seconds. Thoda margin jodo, kyunki ek batch ke andar ki requests ek hi pal mein nikal sakti hain.

```flow
dir: LR
Ek page request karo | 100 rows -> Rows process karo -> Aur pages hain?
Aur pages hain? -[haan, ek pause ke baad]-> Ek page request karo
Aur pages hain? -[nahi]-> Agla step
```

### Data merge karna, aur jo match na ho use rakhna

**Merge** node do inputs ko position se, ya **matching fields** se jod sakta hai, jaise ek payment id jo dono mein ho. Matching fields ke liye output setting tay karti hai ki kya bachega:

| Output choice | Kya nikalta hai | Kiske jaisa |
| --- | --- | --- |
| Keep Matches | Sirf wo items jo dono inputs mein mile | Ek inner join |
| Keep Non-Matches | Sirf wo items jinka koi partner nahi | Bache hue items |
| Keep Everything | Dono inputs se matches aur non-matches | Ek full outer join |
| Enrich Input 1 or 2 | Ek input poora, saath mein doosre se match hone waala data | Ek left ya right join |

Upar ke labels recent versions ke hain; apne version mein dropdown check karo. Reconciliation mein unmatched items hi findings hain, isliye Keep Matches har problem chhipa dega. Keep Everything chuno; akela Keep Non-Matches un matched rows ko bhi drop kar dega jinke amounts abhi check karne hain. Do aur traps: agar dono inputs mein `amount` naam ka field hai, toh ek doosre ko overwrite kar deta hai, isliye pehle ek **Edit Fields** node se fields ka naam badlo. Aur aisi key par match karo jo dono taraf unique ho, jaise payment id, na ki aisi jo dohraayi ja sake, jaise customer ka phone number.

### Code nodes

**Code** node JavaScript ya Python chalaata hai. "Run Once for All Items" mode mein, jo default hai, ye `$input.all()` se har item padhta hai, `$('Node name').all()` se kisi doosre node ke items padh sakta hai, aur ise objects ki ek list return karni hoti hai, har ek mein ek `json` key ke saath. Ye waala Bhaarteeya tareeke se likha amount jodta hai:

```js
// Mode: Run Once for All Items
return $input.all().map((item) => ({
  json: {
    ...item.json,
    amount_text: (item.json.amount / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' }),
  },
}));
```

12500000 paise ke amount ke liye `amount_text` "₹1,25,000.00" hai. Jab tak Python ki zaroorat na ho, JavaScript hi chuno: n8n 2.0 se Code node native Python chalaata hai, jo items ko `_items` ke roop mein padhta hai aur usmein n8n ke baaki built-in helpers mein se koi nahi hota. Code nodes chhote aur comments ke saath rakho. Agar koi ek screen se bada ho jaaye, toh wo node ke andar chhipi ek chhoti service hai, aur wahan use test karna mushkil hai.

### Schedules aur time zones

Schedule trigger workflow ke time zone mein fire hota hai. Self-hosted instance default roop se America/New_York par rehta hai jab tak aap `GENERIC_TIMEZONE` variable set na karo, isliye "subah 6 baje" waala job Bhaarat ki dopahar mein chal sakta hai. Workflow ki settings mein time zone Asia/Kolkata set karo, phir executions list mein run times check karo. `$now` jaise expressions bhi isi setting ko follow karte hain, toh "kal" ka matlab Bhaarat ka kal.

### AI kab use karein, aur kab nahi

AI node sirf wahin use karo jahan rules kaam nahi kar sakte: free text padhne mein. Ek achha udaaharan hai kisi wholesale buyer ka email jismein likha ho "paid ₹48,300 against invoices 112 and 118, less TDS". Structured output waala **Information Extractor** ise invoice numbers aur ek amount mein badal sakta hai, jise phir ek IF node aapki invoice list se check karta hai, isse pehle ki koi insaan confirm kare. Rule ye hai: agar IF, Switch ya Code node faisla kar sakta hai, toh model se mat poochho. Paison ke mismatches ke liye "reasons" likhne waala model kharch badhaata hai aur koi aisi wajah gadh sakta hai jo sahi lage. AI Agent ko un tasks ke liye rakho jahan agli tool call is par nirbhar karti hai ki pichhli ne kya lautaaya, "Automation with n8n" lesson waale safeguards ke saath.

### Reliability

| Practice | Kyun |
| --- | --- |
| API nodes par Retry On Fail | Chhote network errors doosri try mein apne aap theek ho jaate hain |
| Idempotent writes | Unique id par upsert, taaki rerun rows ko duplicate karne ki jagah update kare |
| Overlapping time windows | Sirf kal ka nahi, kuch dinon ka data fetch karo, taaki ek chhoota run agle din apne aap theek ho jaaye |
| Ek error workflow | Error Trigger se shuru hota hai aur workflow, fail hua node aur execution link team ko post karta hai |
| Item-count checks | Jo step rows lautaana chahiye wo kuch na lautaaye toh alert; zero items ek branch rok dete hain, isliye pehle Always Output Data on karo |

Error workflow ko main workflow ki settings mein set karo, aur error workflow ko bhi publish karo. Ye sirf automatic runs ke liye fire hota hai, un runs ke liye nahi jo aap editor mein haath se shuru karte ho, isliye ise ek chhote schedule se test karo.

### Pinned data se testing

Kisi node ka output **Pin** karo, jaise gateway call, aur editor API ko dobaara call karne ki jagah usi ko reuse karta hai. Production runs pinned data ko ignore karte hain. Mushkil pinned cases ka ek set rakho, jaise ek refund, ajeeb paise waala amount aur bina payment id waala order, aur har badlaav ke baad unhein dobaara chalaao.

### Maintainability

November 2026 tak, n8n ka built-in Git source control uske Business aur Enterprise plans par hai. Doosre plans par workflows ko JSON mein export karo aur khud Git mein commit karo. Apne credentials ke saath ek alag test instance ya project rakho, aur production tabhi badlo jab test run pass ho jaaye.

### Self-hosting basics

n8n open source nahi hai. Iska Sustainable Use License aapke apne business ke liye self-hosting allow karta hai; client work ke baare mein "Automation with n8n" lesson batata hai. Self-hosting, jaise Docker ke saath, aapko operator bana deta hai:

- **Encryption key.** n8n saved credentials ko apni banaayi ek key se encrypt karta hai. Agar data volume nahi rakha gaya, toh dobaara bana container nayi key banaata hai aur har credential padha nahi ja sakta. `N8N_ENCRYPTION_KEY` khud set karo aur database ke saath uska bhi backup lo.
- **Disk.** Execution data default roop se 14 din ya 10,000 executions ke baad prune hota hai. Pruning on rakho, aur kisi busy workflow ke har successful run ka poora data save mat karo.
- **Database aur scale.** Kisi bhi serious kaam ke liye Postgres use karo. High volume ke liye **queue mode** Redis se runs ko alag worker processes ko deta hai.
- **Updates.** n8n mein critical security flaws aa chuke hain, January 2026 waala bhi shaamil hai. Security releases kuch hi dinon mein lagaao.

## Ek worked example

Bengaluru ka ek D2C skincare brand Shopify par roz lagbhag 1,500 orders bechta hai. Udaaharan ke liye maan lo lagbhag 60% Razorpay se prepaid hain aur baaki cash on delivery. Har subah finance mein Kavya do ghante ye check karne mein lagaati hai ki har prepaid order ka paisa pay out hua ya nahi. Gateway ke baare mein teen baatein design tay karti hain:

- **Settlements baad mein aate hain.** Razorpay ka standard domestic cycle capture se T+2 working days hai, aur ye merchant ke hisaab se badalta hai. Kal ke orders abhi settle nahi hue, isliye kal ko kal se match karoge toh sab kuch flag ho jaayega.
- **Rows ki key payment id hai.** Har settlement row mein ek `entity_id` (`pay_` se shuru hone waala payment id), `amount`, `fee`, `tax` aur `credit` hota hai. Iska `order_id` Razorpay ka apna order id hai, Shopify order number nahi. Isliye store ko checkout par har order mein Razorpay payment id save karna hoga; ye kahan rehta hai, ye aapki checkout app par nirbhar hai.
- **Amounts paise mein hain, aur fees katti hain.** `amount` paise mein gross payment hai. `fee` mein wo GST pehle se shaamil hai jo `tax` dikhaata hai, aur `credit` hai `amount` mein se `fee` ghataakar. `credit` ko order total se compare karoge toh har order flag hoga. Uski jagah `amount` compare karo, aur fee alag se check karo.

Kavya ka workflow, time zone Asia/Kolkata par set karke:

| # | Node | Kya karta hai |
| --- | --- | --- |
| 1 | Schedule trigger aur Sheets | IST subah 6 baje chalta hai; upar waali branch par ek Sheets node, taaki wo pehle chale, results sheet ko "Read results" ke roop mein padhta hai |
| 2 | Shopify, phir Filter | Return All se pichhle 10 din ke orders leta hai, prepaid waale rakhta hai |
| 3 | HTTP Request | Pichhle 3 din ki settlement rows page by page leta hai, lagbhag ek request prati second |
| 4 | Filter aur Edit Fields | Payment rows rakhta hai (refunds ka apna type hai), fields ka naam badalta hai taaki kuch na takraaye |
| 5 | Merge | `payment_id` par match karta hai, Keep Everything |
| 6 | Code | Pehle se ok mark hue payments skip karta hai, baaki ko flag karta hai (neeche dekho) |
| 7 | Sub-workflow "Upsert result" | Sheets Append or Update Row, `payment_id` par match karke |
| 8 | IF aur Slack | Working day par step 3 ko koi row na mile toh alert; warna counts aur sheet link post karta hai |
| + | Error workflow | Execution link ke saath finance-ops ko alert |

Step 6 ka Code node:

```js
// Mode: Run Once for All Items. Each item is one merged row.
const done = new Set($('Read results').all()
  .filter((i) => i.json.flag === 'ok').map((i) => i.json.payment_id));
const out = [];
for (const item of $input.all()) {
  const r = item.json;
  if (done.has(r.payment_id)) continue; // never downgrade an ok row
  const orderPaise = Math.round(Number(r.order_total) * 100);
  let flag = 'ok';
  if (!r.order_name) {
    flag = 'settled, no order found';
  } else if (!r.settlement_id) {
    const days = $now.diff(DateTime.fromISO(r.paid_at), 'days').days;
    flag = days > 5 ? 'settlement overdue' : 'waiting';
  } else if (r.gateway_amount !== orderPaise) {
    flag = 'amount differs';
  } else if (r.gateway_fee > Math.ceil(r.gateway_amount * 0.0236)) {
    flag = 'fee above contract'; // 2% plus 18% GST; use your rate
  }
  const paise = r.gateway_amount ?? orderPaise;
  const amount_text = (paise / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' });
  out.push({ json: { ...r, flag, amount_text } });
}
return out;
```

`Math.round` order total ko, jise Shopify "1499.50" jaise text mein bhejta hai, poore paise mein badal deta hai, taaki chhoti decimal galtiyaan, jaise ₹1.15 ke liye 114.99999, false alarm na bana sakein. `Math.ceil` fee ki rounding ki gunjaaish deta hai. 2% rate sirf ek udaaharan hai; apne contract waala rate use karo. Jaise, 2% par ₹1,000 ke UPI payment ki fee ₹20 aur saath mein ₹3.60 GST hai, toh `fee` 2360 paise hai aur `credit` 97640.

Har flag ek saaf action tak le jaata hai, jise ek template likhta hai, model nahi:

| Flag | Aam taur par matlab | Kaun action leta hai |
| --- | --- | --- |
| waiting | Pay ho gaya, normal settlement window ke andar hai | Abhi koi nahi |
| settlement overdue | 5 din se zyada hue aur abhi bhi settle nahi hua | Finance ise gateway ke saath uthaata hai |
| amount differs | Payment ke baad order edit hua, ya part refund | Finance order history check karta hai |
| settled, no order found | Kisi doosre channel ka payment, ya gaayab payment id | Store team order record theek karti hai |
| fee above contract | Galat pricing plan laga hai | Finance ise gateway ke saath uthaata hai |

Kyunki writes `payment_id` par upserts hain, koi row duplicates ke dher banne ki jagah kisi agli subah "waiting" se "ok" ho jaati hai. Skip zaroori hai: jaise hi koi settlement 3-day window se baahar jaata hai, warna uska order unsettled dikhega aur dobaara "overdue" flag ho jaayega. 10-day order window der se settle hone waale payments ko cover karti hai. 5-day limit ek trade-off hai: bank holidays waala lamba weekend kuch false alarms la sakta hai, jinhein team kisi asli problem ko miss karne ki jagah manzoor karti hai.

**Ek buri subah.** Ek din subah 6 baje gateway ki API errors lauta rahi thi. Retries fail hue, aur error workflow ne execution link ke saath alert post kiya. Kavya ne subah 9 baje ise dobaara chalaaya. Upserts ki wajah se koi duplicate nahi bana, aur kyunki har run teen din ka data fetch karta hai, poora din chhoot bhi jaata toh agli subah cover ho jaata.

## Aam galtiyaan

- **Ek bahut bada workflow.** Saajha steps ko defined inputs waale, naam diye sub-workflows mein baanto.
- **Rate limits ko nazarandaaz karna.** Page, batch aur wait karo; retries pacing nahi hain.
- **Reconciliation ke liye Keep Matches se merge karna.** Ye chupchaap wahi problems drop kar deta hai jo aap dhoondh rahe ho.
- **Net ko gross se, ya rupees ko paise se compare karna.** Ek jaisi cheezon ko ek jaisi cheezon se, poore paise mein compare karo.
- **Kal ko kal se match karna.** Settlements der se aate hain; overlapping windows use karo.
- **Non-idempotent writes.** Saade appends har rerun par duplicates banaate hain.
- **Time zone ko default par chhodna.** Workflow settings mein Asia/Kolkata set karo.
- **Jahan rule kaafi ho wahan AI use karna.** Kabhi kisi model ko paison ki wajah samjhaane mat do.
- **Error workflow ko haath se test karna.** Ye sirf automatic runs ke liye fire hota hai.
- **Encryption key kho dena.** Zaroorat padne se pehle database ke saath iska backup lo.

## Practice

Neeche linked n8n ka N8N102 Integrations course poora karo, aur hosting overview padho.

1. **Volume.** Ek workflow banao jo kisi API ya sheet se kam se kam 300 rows pages mein le aur unhein Wait ke saath batches mein process kare. Limit se wait nikaalo, aur wo hisaab ek sticky note mein likho.
2. **Merge aur write.** Do sources ko ek shared id par Keep Everything se merge karo, ek chhote Code node mein har row ko flag karo, aur ek sub-workflow se likho jo id par upsert kare. Har flag ke liye ek mushkil case pin karo.
3. **Failure.** Time zone Asia/Kolkata set karo, ek error workflow jodo, jaanboojhkar ek node todo, aur workflow ko ek chhote schedule par chalne do. Alert confirm karo, phir dobaara chalaao.

**Aapka kaam poora hai jab aap** apna workflow lagaataar do baar bina duplicates banaaye dobaara chala sako, aur fail hue execution ke link ke saath ek error alert dikha sako.
