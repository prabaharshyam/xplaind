## Ye kya hai

Agent ko evaluate karne ka matlab hai use tasks ke ek set par chalana aur score karna ki kya hua. Do cheezein score hoti hain:

- **Outcome**: kya goal achieve hua? Refund sahi se issue hua, report accurate thi, ticket sahi team ko gaya?
- **Trajectory**: wahan tak kaise pahunche? Kaun se tools, kitne steps, koi unsafe ya waste hua action, jahan zaroori tha wahan approval maanga?

Kyunki agents deterministic nahi hote aur kai steps lete hain, aap **consistency** bhi measure karte ho: har task ko kai baar chalao aur dekho woh kitni baar succeed hota hai.

```flow
Task | "refund my course, I joined 5 days ago"; seeded sandbox: student 812, payment ₹3,499 -> Agent run 1
Task -> Agent run 2
Task -> Agent run 3
Agent run 1 -> Graders | outcome code se: student 812 ko ₹3,499 ka refund? trajectory rules se: refund se pehle quote, payment se pehle approval, zyada se zyada 10 steps; quality calibrated model grader se
Agent run 2 -> Graders
Agent run 3 -> Graders
Graders -> Metrics | success, teeno runs mein success, steps, cost, safety violations (0 hone chahiye)
```

Har run ek fresh sandbox se shuru hota hai.

Is lesson mein hum Hyderabad ki ek edtech company ke course-refund agent ko follow karenge.

## Ye kaam kaise karta hai

**Tasks.** 30 se 100 realistic tasks likho, ek defined starting state ke saath (ek fake customer account, ek sandbox database, documents ka set) aur ek saaf success condition ke saath. Common cases, mushkil cases, woh tasks jinhe refuse ya escalate karna chahiye, aur traps waale tasks (error dene waala tool, missing information jiske liye sawaal poochna pade) cover karo.

**Graders.** Har check ke liye sabse sasta reliable grader use karo:

- End state par *code checks*: kya refund row database mein sahi amount ke saath hai? File ban gayi? Ye precise aur sasta hai.
- Trajectory par *rules*: pehle `get_cancellation_quote` call kiye bina `issue_refund` ka call nahi; 12 se zyada steps nahi; kisi bhi payment se pehle approval maanga gaya.
- Open-ended quality ke liye (customer reply accurate aur polite thi?) *model graders*, rubric ke saath, human grades se check kiye hue.
- Ek sample ka *human review*, khaaskar shuru mein.

**Metrics.** Success rate; kai runs mein se saare runs mein success (reliability ka ek sakht measure); har task ke average steps, tokens, cost aur time; safety violations (zero hone chahiye); escalation correctness.

**Environment.** Evals ko aise sandbox mein chalao jo tasks ke beech reset ho: fake APIs ya seed data waala test database. Evals ko kabhi production systems par mat chalao.

**Waqt ke saath track karo.** Har prompt, tool ya model change par suite chalao aur history rakho. Har dilchasp production failure ko naye task ki tarah jodo.

**Transcripts padho.** Numbers batate hain ki kuch badla; das failed trajectories padhne se pata chalta hai kyun.

**Metrics aur woh kya batate hain:**

| Metric | Definition | Kya batata hai |
| --- | --- | --- |
| Success rate | Un runs ka hissa jo success condition poori karte hain | Average capability |
| All-runs success | Un tasks ka hissa jo har run mein succeed hote hain | Woh reliability jo users feel karte hain |
| Steps, tokens, cost per task | Runs par averages | Efficiency |
| Safety violations | Forbidden actions, missing approvals | Us par bharosa kiya bhi ja sakta hai ya nahi |
| Escalation correctness | Tabhi aur sirf tabhi escalate kiya jab karna chahiye tha | Edge cases mein judgement |

**Sandbox banana.** Tools ko boundary par fake karo: kuch students aur payments ke saath seed kiya hua test database, ek fake payment API jise ek baar fail hone ko kaha ja sake, aur ek approval tool jo test script se jawab de. Har run se pehle sab kuch reset karo. Seed data ko repository mein rakho, taaki koi bhi failure reproduce kar sake. Sandbox wahi jagah hai jahan aap traps bhi rakh sakte ho, jaise student ke message mein chhupa hua instruction, asli systems ko khatre mein daale bina.

**Transcripts ko fixes mein badalna.** Jab koi task fail ho, uski trajectory padho aur fail hone waale step ka naam lo: galat tool, galat argument, chhoota hua check, ya kharab final reply. Jis tool, description ya prompt ne ise kiya use fix karo, us task ko kai baar dobara chalao, phir poora suite dobara chalao taaki pata chale kuch aur nahi toota.

**Code mein ek eval harness.** Har task apna seed data, apna success check aur woh trajectory rules lekar chalta hai jinhe use maanna hai:

```python
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class Task:
    id: str
    prompt: str
    seed: dict                                   # starting state for the sandbox
    success: Callable[[dict], bool]              # checks the final sandbox state
    rules: list[Callable[[list], str | None]] = field(default_factory=list)

def no_refund_without_quote(trace):
    names = [s["name"] for s in trace if s["type"] == "tool"]
    if "issue_refund" in names and ("get_quote" not in names or names.index("get_quote") > names.index("issue_refund")):
        return "refund issued before a quote"

def at_most(n):
    return lambda trace: f"{len(trace)} steps" if len(trace) > n else None

def run_suite(tasks, run_agent, make_sandbox, k=3):
    results = []
    for t in tasks:
        outcomes = []
        for _ in range(k):
            box = make_sandbox(t.seed)           # fresh state every run
            trace = run_agent(t.prompt, box)
            broken = [msg for rule in t.rules if (msg := rule(trace))]
            outcomes.append({"ok": t.success(box.state) and not broken, "broken": broken,
                             "steps": len(trace)})
        results.append({"task": t.id, "outcomes": outcomes})
    n = len(results)
    any_ok = sum(any(o["ok"] for o in r["outcomes"]) for r in results) / n
    all_ok = sum(all(o["ok"] for o in r["outcomes"]) for r in results) / n
    print(f"pass@{k} {any_ok:.0%}   pass^{k} {all_ok:.0%}")
    return results
```

**Success count karne ke do tareeke.** **pass@k** task ko solved maanta hai agar k runs mein se koi ek succeed ho; ye measure karta hai ki agent *kar sakta kya hai*. **pass^k** use tabhi maanta hai jab saare k runs succeed hon; ye measure karta hai ki users kis par *bharosa kar sakte hain*. Har run par 90% waale agent ka pass^3 lagbhag 73% hota hai, agar runs independent hon. Customer-service tasks ke agent benchmarks isi wajah se pass^k report karte hain.

**Model graders ko calibrate karo.** Open-ended checks ke liye (reply accurate aur polite thi?), 50 transcripts haath se grade karo, usi 50 par model grader chalao, aur agreement count karo. Agar woh lagbhag 85% se kam cases mein sahmat ho, toh rubric behtar karo ya woh check human ke paas hi rakho. Grader ka prompt ya model badalne par dobara check karo.

**Har task ka cost aur time.** Har run ke liye success ke saath tokens, cost aur wall-clock time bhi record karo. Jo change success mein 3 points jodta hai par cost doguni kar deta hai, shaayad us layak nahi; jo success wahi rakhkar cost aadha kar de, woh aam taur par layak hai.

**Suite ko production se badhao.** Har hafte traces mein asli failures ya ajeeb requests se do-teen tasks jodo, customer ki details ko seed data se badalkar.

## Ek example se samjho

Hyderabad ki ek ed-tech company ka ek agent course-refund requests sambhaalta hai: enrolment check karta hai, refund policy lagata hai, ₹5,000 se kam ke refunds approval ke baad issue karta hai, aur baaki escalate karta hai.

Eval suite mein seeded students aur payments waale sandbox mein 60 tasks hain:

- 30 routine refunds (succeed hone chahiye),
- 10 policy window ke bahar (tameez se decline hone chahiye),
- 10 ₹5,000 se upar ke (escalate hone chahiye),
- 5 jahan payment API ek baar error deti hai (retry karna chahiye, phir escalate),
- 5 jinmein student ke message mein prompt injection hai (ignore karna chahiye).

Graders: refunds table par code checks; trajectory rules (refund se pehle quote, payment se pehle approval, zyada se zyada 10 steps); reply tone ke liye ek model grader, 40 human-graded replies par calibrate kiya hua (88% agreement).

Har task teen baar chalta hai. Baseline: 82% success, teeno runs mein 71% success, aur ek safety violation (approval tool ke timeout hone par bina approval ke refund issue ho gaya). Fix ye hai ki timeout ko "approve nahi hua" maana jaaye. Changes ke baad suite 93% success, teeno runs mein 88% aur zero violations dikhata hai. Wahi suite ab har change par CI mein chalta hai.

| Measure | Baseline | Fixes ke baad |
| --- | --- | --- |
| Success | 82% | 93% |
| Teeno runs mein success | 71% | 88% |
| Safety violations | 1: timeout ke baad bina approval ke refund | 0: timeout ab approve nahi hua maana jaata hai |

## Aam galtiyaan

- **Sirf final message ko score karna.** Agent ne raaste mein kuch unsafe kiya ho sakta hai.
- **Har task ka ek hi run.** Agents badalte rehte hain; consistency measure karo.
- **Asli systems par evals.** Resettable sandbox use karo.
- **Sirf happy paths.** Refusals, escalations, tool failures aur injection attempts bhi rakho.
- **Transcripts kabhi na padhna.** Scores batate hain ki fail hua, kyun nahi.
- **Har task ka ek run report karna.** Kai chalao aur pass@k aur pass^k dono report karo.
- **Aise model grader par bharosa jise kisi ne check nahi kiya**, human grades ke saath.
- **Runs ke beech shared sandbox.** Ek run ki bachi hui state agle run ko ittefaq se pass ya fail kara deti hai.

## Kab halka evaluation kaafi hai

- **Kuch tools waale read-only agents**: expected answers waale sawaalon ka set aur step limit check kaafi ho sakta hai.
- **Shuruaati prototypes**: haath se padhe hue das tasks us harness se zyada batate hain jise aap baar-baar likhte rehte ho.
- **Fixed workflows**: har step ko aam code ki tarah test karo, saath mein kuch end-to-end cases.

Sandboxes, trajectory rules aur repeated runs mein tabhi invest karo jab agents asli systems par kaam karne lagein ya bahut saare users unpar nirbhar hon.

## Demo se production tak

- **Har prompt, tool aur model change par suite chalao**, history ke saath.
- **Releases ko safety violations par gate karo** (zero allowed) aur critical tasks ke liye pass^k par.
- **Seed data aur sandboxes ko repository mein rakho**, taaki koi bhi failure reproduce kar sake.
- **Model graders ko dobara calibrate karo** har quarter taaza human grades ke saath.
- **Production failures ko** har hafte naye tasks ki tarah **jodo.**
