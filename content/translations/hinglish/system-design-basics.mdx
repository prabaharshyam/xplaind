## Ye kya hai

**System design** ka matlab hai ye tay karna ki software system ke hisse aapas mein kaise judte hain, taaki woh users ki zaroorat poori kare, jis scale ka use saamna karna hai wahan, aur apne budget ke andar. Isme components aate hain (apps, services, databases, caches, queues), unke beech data kaise behta hai, aur kuch fail ho jaye toh kya hota hai.

Shaayad hi koi ek sahi jawab hota hai. Achha design wo hai jiske choices requirements se mel khate hain aur jiske trade-offs khulkar bataye gaye hain. Interviewers bhi yahi dekhte hain: ek saaf process, samajhdaar numbers aur imaandaar trade-offs, perfect diagram se zyada.

```flow
dir: LR
1. Requirements | ye kya kare? Kitna tez, kitna bada, kitna reliable? -> 2. Estimates | users, requests per second, storage, bandwidth, average aur peak par
2. Estimates -> 3. High-level design | clients, load balancer, app servers, cache, database, queue, workers
3. High-level design -> 4. Deep dive | data model, hot paths, scaling
4. Deep dive -> 5. Trade-offs aur failures | kya tootega, aapne kya chuna aur kyun
```

## Ye kaam kaise karta hai

**1. Requirements clarify karo.** Unhe **functional** requirements (system kya karta hai, jaise "users seat book kar sakte hain" ya "users order status dekhte hain") aur **non-functional** requirements (woh kitna achha karta hai: latency, availability, consistency, scale, cost, security) mein baanto. Poochho ki users kaun hain, kitne hain, aur kaunse features scope mein hain. Jawab likh lo.

**2. Estimate karo.** Ek **back-of-the-envelope estimate** users ko load mein badalta hai. Kaam ke facts: ek din mein lagbhag 1 lakh seconds hote hain (86,400), toh din mein 1 crore requests ka matlab hai lagbhag 115 per second; peaks ke liye average ka kai guna plan karo. Storage estimate karo: per item size × din mein items × kitne din rakhne hain. Ye numbers tay karte hain ki ek database kaafi hai ya kai chahiye.

**3. High-level design ka sketch banao.** Main boxes aur arrows banao: clients, ek load balancer, stateless app servers, ek cache, ek database, files ke liye object storage, aur dheeme kaamon ke liye background workers ke saath ek queue. Ek request ko shuru se aakhir tak chalakar dikhao.

**4. Deep dive.** Is system ke liye jo hisse sabse zyada maayne rakhte hain unhe chuno aur gehre jao: data model aur uske indexes, sabse busy path ko kaise scale karein, data ko consistent kaise rakhein, ya achaanak aayi spike ko kaise sambhaalein.

**5. Trade-offs aur failures.** Batao ki har choice ki keemat kya hai. Cache reads tez karta hai par purana data de sakta hai; queue spikes ko smooth karti hai par deri jodti hai; zyada replicas availability badhate hain par mehnge padte hain. Har component ke liye poochho "ye box fail ho gaya toh?"

| Non-functional zaroorat | Aam numbers | Design levers |
|---|---|---|
| Latency | Ek page ke liye p95 200 ms se neeche | caches, CDNs, kam hops, indexes |
| Throughput | Hazaaron requests per second | zyada app servers, load balancing, async kaam |
| Availability | 99.9% = mahine mein lagbhag 43 min down | replicas, health checks, koi single point of failure nahi |
| Consistency | Payments ke liye strong, likes ke liye eventual | transactions, primary-only reads, idempotency |
| Cost | Per lakh requests ke rupees | sahi size ki machines, caching, sasti storage tiers |

**Browser mein try karo.** Back-of-envelope numbers zyadatar designs tay karte hain. Inputs badlo aur chalao.

```python
daily_users = 200_000
requests_per_user = 15
peak_factor = 3
bytes_per_record = 2_000

per_second = daily_users * requests_per_user / 86_400
print(f"average {per_second:,.0f} requests/s, peak about {per_second * peak_factor:,.0f}/s")
storage_gb_year = daily_users * requests_per_user * bytes_per_record * 365 / 1e9
print(f"about {storage_gb_year:,.0f} GB of records a year")
```

## Ek example se samjho

Meera se interview mein Bengaluru ke ek food delivery app ka order-status page design karne ko kaha jaata hai: order dene ke baad customers ko "Preparing", "Picked up" aur "Arriving" rider ki location ke saath dikhta hai.

**Requirements.** Woh poochti hai aur confirm karti hai: active orders ke liye status aur rider location dikhao; updates lagbhag 5 seconds ke andar; din mein 20 lakh orders, dinner peak ke saath; history scope se bahar hai. Perfect freshness se zyada availability maayne rakhti hai: kuch seconds purani location dikhana theek hai.

**Estimates.** Din mein 20 lakh orders, har ek lagbhag 40 minutes active. Riders har 5 seconds mein location bhejte hain, toh har order lagbhag 480 updates banata hai. Ye din mein lagbhag 96 crore updates hue: average mein lagbhag 11,000 per second aur dinner peak par shaayad 40,000. Customers page baar-baar refresh karte hain, isliye reads aur bhi zyada hain. Har location update chhota hai, lagbhag 100 bytes, par delivery ke baad unhe rakhne ki use zaroorat nahi.

**High-level design.** Rider apps locations ko load balancer ke peeche ek ingestion service ko bhejte hain. Har order ki latest location ek in-memory store jaise Redis mein jaati hai, order ID se keyed, chhote expiry ke saath. Order status changes main database mein likhe jaate hain aur ek queue mein publish bhi hote hain. Customer apps ek notification service se WebSocket connection khula rakhte hain, jo status aur location changes push karti hai. Agar connection toot jaye, toh app ek read API ko poll karne par aa jaata hai jo Redis se padhti hai.

**Deep dive aur trade-offs.** Woh samjhati hai ki high-volume location stream main SQL database mein kyun nahi jaati: woh us database ko bottleneck bana deti, aise data ke liye jo kal kisi ko nahi chahiye. Status, jo refunds aur support ke liye maayne rakhta hai, database mein jaata hai. Woh trade-off batati hai: agar koi node fail ho jaye toh Redis aakhri kuch seconds ki locations kho sakta hai, jo yahan theek hai, jabki order status durable hai. Woh failure cases se khatam karti hai: agar notification service band ho toh polling phir bhi kaam karta hai; agar Redis band ho toh page map ke bina status dikhata hai.

Interviewer ne baad mein kaha ki jo baat alag lagi woh boxes nahi the, balki ye ki har choice ko kisi number ya requirement se jodkar rakha gaya tha.

## Aam galtiyaan

**Poochhe bina draw karna.** Requirements ke bina diagram par kood padne se galat problem ke liye ek confident design ban jaata hai. Shuru ke kuch minutes sawaalon par lagao.

**Numbers skip karna.** Estimate ke bina aap nahi bata sakte ki ek database kaafi hai ya nahi. Mote numbers bhi, saaf bataye hue, kuch na hone se behtar hain.

**Average ke liye design karna, peak ke liye nahi.** Sales, results day aur Tatkal windows normal traffic ka kai guna laate hain. Peak ke hisaab se size karo aur batao ki spikes ko kaise absorb karoge.

**Jo bhi component aata hai woh sab jodna.** Har jagah microservices, Kafka aur Kubernetes design ko chalana mushkil bana dete hain. Component tabhi jodo jab kisi requirement ko uski zaroorat ho.

**Trade-offs chhupana.** Har choice ki ek keemat hoti hai. Use zor se bolna judgement dikhata hai.

**Failure bhoolna.** Poochho ki har box band ho jaye toh kya hota hai. Single points of failure woh pehli cheez hain jo reviewers dhundhte hain.
