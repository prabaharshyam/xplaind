## Ye kya hai

Bahar se AI product ek chat box jaisa dikhta hai jo sawaalon ke jawab deta hai. Andar se woh parts ka ek chhota system hai, aur jab woh galat jaata hai, toh fix is par depend karta hai ki **kaunsa part** fail hua. Jo product managers parts draw kar sakte hain woh engineers ke saath kaam ki baat kar sakte hain. Jo nahi kar sakte woh har baar "behtar model" maangte rehte hain.

Language models par bane zyadatar AI products mein wahi parts hote hain. Ek request ko unke beech follow karo:

```flow
User -> 1 Interface | chat, an in-app button, email, WhatsApp, an API
1 Interface -> 2 Context assembly | system prompt + user input + history
3 Retrieval | search company documents and data -> 2 Context assembly
2 Context assembly -> 6 Guardrails on input | topic limits, personal data, injection checks
6 Guardrails on input -> 4 Model | writes the answer, or asks to use a tool
4 Model -[asks for a tool]-> 5 Tools | look up an order, create a ticket
5 Tools -[result back]-> 4 Model
4 Model -> 6 Guardrails on output | policy rules, format, no promises it can't keep
6 Guardrails on output -> 7 Human checkpoint | review or approve where mistakes are costly
7 Human checkpoint -> Answer to the user -> 8 Evaluation and monitoring | quality, cost, feedback
```

| Part | Kya karta hai | Fail hone par |
| --- | --- | --- |
| **Interface** | Jahan user product se milta hai | Confusing ya chhupa hua feature |
| **Context assembly** | Instructions, input aur history jodta hai | Model task galat samajhta hai |
| **Retrieval (RAG)** | Company data se relevant facts laata hai | Galat ya purane answers |
| **Model** | Answer banata hai | Mushkil tasks par kamzor reasoning |
| **Tools** | Woh actions jo model request kar sakta hai | Galat action, ya koi nahi |
| **Guardrails** | Input aur output par checks | Unsafe ya policy se bahar replies |
| **Human checkpoints** | Mehngi cases ke liye review ya approval | Mehngi galtiyan customers tak pahunchti hain |
| **Evaluation aur monitoring** | Release se pehle test sets; baad mein tracking | Problems aap nahi, customers dhoondhte hain |

Ye lesson Ritu ke saath chalta hai, jo Mumbai ke ek bank mein product manager hai, jab woh trace karti hai ki bank ke assistant ne ek customer se fee waiver ka vaada kyun kiya jo kabhi hua hi nahi. End tak aap picture ka use karke samjha paoge ki answer galat kyun tha aur kya badalna chahiye.

## Ye kaam kaise karta hai

### Quality kahan se aati hai

Galat answers aam taur par chaar jagahon mein se ek se aate hain:

1. **Missing ya purani information**: retrieval ko galat document mila, ya sahi waala hai hi nahi.
2. **Unclear instructions**: system prompt nahi batata ki is situation mein kya karna hai.
3. **Task ke liye kamzor model**: ho sakta hai, par logon ke sochne se kam common hai.
4. **Output par koi check nahi**: user ke dekhne se pehle kisi ne galti nahi pakdi.

Jab kuch galat ho, toh bade model ki maang karne se pehle poochho ki kaunsa part fail hua.

### Cost kahan se aati hai

Har request mein cost aati hai:

- **model tokens**, input (prompt, history, retrieved text) aur output dono ke liye;
- retrieval, tools aur infrastructure.

Lambe prompts aur lambe answers zyada cost karte hain. Bade models per token zyada cost karte hain. Do common bachat: prompts ke repeated parts ko **caching** karna, aur aasaan requests ko chhote, sasta models ki taraf **routing** karna.

### Risk kahan se aata hai

Confident galat answers, bina checks ke liye gaye actions, expose hua personal data, **prompt injection** (model jo documents ya emails padhta hai unke andar chhupe instructions), aur unfair nateeje. Controls hain guardrails, tools par permissions, human review aur evaluation.

### Prompting, retrieval ya fine-tuning?

| Approach | Kya badalta hai | Badalne ki speed aur cost | Kab use karein |
| --- | --- | --- | --- |
| **Prompting** | Instructions aur examples | Tez, sasta | Behaviour, tone, format |
| **Retrieval (RAG)** | Jo facts model har request par dekhta hai | Medium | Current ya private information |
| **Fine-tuning** | Training se model ki aadatein | Dheema, mehnga | Scale par ek narrow style ya skill |

Zyadatar products prompting aur retrieval se shuru hote hain, aur kai ko fine-tuning ki kabhi zaroorat nahi padti.

### Agents

Jab model tool calls ka poora sequence khud decide karta hai, toh product ek **agent** hota hai. Agents flexible hote hain par unhe predict karna mushkil hota hai, isliye unhe limits chahiye ki woh kya kar sakte hain, har step ke logs, aur risky actions ke liye approvals. Jahan fixed workflows kaam karte hain wahan unhe use karo, aur agents wahan jahan flexibility ka fayda ho.

### Product manager ke levers

Engineers **kaise** decide karte hain. Aap **kya aur kitna achha** decide karte ho:

- user problem aur success metric;
- kin actions ko approval chahiye;
- kaunse failures acceptable hain aur kaunse nahi;
- har request ka budget;
- evaluation set ko kya cover karna hai.

## Ek worked example

Ritu Mumbai ke ek bank ke mobile app ke ek feature ki product manager hai jo credit card charges ke baare mein customers ke sawaalon ke jawab deta hai.

**Complaint.** Assistant ne ek customer ko bataya ki unki ₹2,500 ki annual fee waive ho jaayegi. Nahi hui, aur customer se charge le liya gaya.

Ritu aur engineers request ko parts ke beech trace karte hain:

| Part | Kya mila | Problem? |
| --- | --- | --- |
| Interface | In-app chat, normal chal raha hai | Nahi |
| Context assembly | System prompt ne kaha sirf bank documents se jawab do | Nahi |
| Retrieval | Pichhle saal ka fee-waiver offer laaya, jo expire ho chuka tha | **Haan: wajah** |
| Model | Diye gaye document se imaandaari se jawab diya | Nahi |
| Guardrails | Fees ke vaadon ko koi rule nahi rokta tha | **Haan: ek missing control** |
| Evaluation | Kisi test question mein expired offers nahi the | **Haan: ek gap** |

**Fixes, part ke hisaab se:**

- **Retrieval:** documents ko unki valid-from aur valid-until dates se filter karo, taaki expired offers kabhi wapas na aayein.
- **Guardrails:** assistant ko waivers ya refunds ka vaada karne se roko; woh iski jagah kehta hai, "You may be eligible. Here is how to check," ek link ke saath.
- **Evaluation:** test set mein expired aur future offers samet 30 fee questions jodo.
- **Monitoring:** ek naya metric, har 10,000 chats mein galat fee information ki complaints, har hafte review.

Kisi ko alag model ki zaroorat nahi thi. Answer isliye galat tha ki model ko kya diya gaya aur kisi ne kya check nahi kiya.

## Aam galtiyaan

- **Har error ke liye model ko dosh dena.** Kai data, retrieval ya missing checks se aate hain.
- **Prompt ko secret sauce maanna.** Ye ek part hai; evaluation aur data zyada matter karte hain.
- **Har request ki cost ko ignore karna.** Jo feature users ko pasand hai woh scale par paisa kho sakta hai.
- **Evaluation set nahi.** Uske bina har change ek andaaza hai.
- **Default mein agents.** Jahan fixed workflows kaam karte hain wahan unhe use karo.
- **Documents ka koi owner nahi.** Retrieval utni hi achhi hai jitna uske peeche ka content.

## Practice karo

Neeche link kiya Chip Huyen ka "Building a Generative AI Platform" padho, aur Eugene Yan ke LLM-based systems banane ke patterns skim karo.

1. **Draw karo.** Ek AI feature chuno jo aap use karte ho, jaise banking chatbot, shopping assistant ya email writer, aur uske sambhaavit parts banao.
2. **Failures trace karo.** Us feature ke teen sambhaavit failures ke liye, har ek ka kaaran bane part ka naam aur ek fix batao.
3. **Aapke decisions.** Us ke liye product manager ke decisions ki list banao: metric, approval points, acceptable errors aur har request ka budget.

**Aapka kaam poora jab:** aap ek engineer ko picture ka use karke samjha sako ki answer galat kyun tha aur aap kya badalwana chahte ho.
