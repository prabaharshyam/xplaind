## Ye kya hai

Jo code aapke laptop par chalta hai, wo shuruaat hai, ant nahi. **Project tooling** aapke code ke aaspaas ki wo har cheez hai jisse koi aur use chala sake, safely badal sake aur raat 2 baje debug kar sake. Har hissa us ek sawaal ka jawaab deta hai jo koi anjaan poochega:

| Anjaan poochta hai | Jawaab dene wali file ya tool | Iske bina |
| --- | --- | --- |
| Kaun-sa Python aur kaun-se packages? | `pyproject.toml`, `uv.lock`, `.python-version` | "Meri machine par to chalta hai" |
| Code kahan hai aur use import kaise karoon? | `.venv` mein install kiya hua ek `src` layout | Imports jo sirf ek folder se chalte hain |
| Kya mere change ne kuch toda? | pytest tests | Bugs jo users dhoondhte hain |
| Kya ye code saaf-suthra hai aur obvious galtiyon se bacha hai? | ruff | Har review mein style par bahas |
| API key kahan jaati hai? | `.env` (ignored) aur `.env.example` (committed) | Git mein leak hui keys |
| Production mein kya hua? | Ek baar configure ki hui `logging` | Andaaza |
| Kya ye clean machine par bhi chalta hai? | Har push par CI | "Mere laptop par to pass hua tha" |
| Sabse pehle kya type karoon? | Exact commands wala README | Aapko ek WhatsApp message |

Ismein kuch bhi glamorous nahi hai. Par inmein se har cheez ki kami nazar aati hai, aamtaur par client ke engineer ko, aapke handover ke agle hafte.

Ye lesson ek invoice extractor ke saath chalta hai jo aapne Coimbatore ke ek textile exporter ke liye banaya, jab unka engineer Karthik use sambhalta hai. Ismein **uv** use hota hai, Astral ka ek fast tool jo environment banata hai, packages install karta hai, lock file likhta hai aur Python khud bhi install kar sakta hai. Plain `venv` aur `pip` bhi chalte hain; har section farq dikhata hai.

```flow
title: Clone se bharosemand change tak
dir: LR
Repository clone karo -> Locked versions install karo | uv sync
Locked versions install karo -> Secrets daalo | .env.example ko .env mein copy karo
Secrets daalo -> Lint aur test | ruff aur pytest
Lint aur test -> Code badlo
Code badlo -> Push
Push -> CI clean machine par checks dohraata hai
```

## Ye kaam kaise karta hai

### Layout

```text
invoice-extractor/
  pyproject.toml          # what the project is and needs
  uv.lock                 # exact versions of everything (commit it)
  .python-version         # the Python version the team uses
  .gitignore              # .venv, .env, __pycache__
  .env.example            # variable names, no real values
  README.md
  .github/workflows/ci.yml
  src/invoice_extractor/
      __init__.py
      cli.py              # entry point: configures logging, builds the client
      extract.py
      models.py
      llm.py              # the real model client
  tests/
      conftest.py         # shared fixtures, including a fake model client
      test_extract.py
      fixtures/sample_invoice.txt
```

`uv init --package invoice-extractor` iska zyaadatar hissa aapke liye bana deta hai, jismein ek `src` folder, ek `.python-version` aur ek git repository shaamil hain.

### pyproject.toml

Ye rahi ek poori file, jaisi humne uv 0.13.10, pytest 9.2.0 aur ruff 0.17.6 ke saath chalayi (28 November 2026 tak ki sabse nayi releases):

```toml
[project]
name = "invoice-extractor"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pydantic>=2.10",
]

[project.scripts]
invoice-extractor = "invoice_extractor.cli:main"

[dependency-groups]
dev = ["pytest>=9.0", "ruff>=0.17"]

[build-system]
requires = ["uv_build>=0.13.10,<0.14.0"]
build-backend = "uv_build"

[tool.pytest]
testpaths = ["tests"]
addopts = ["-ra", "--strict-markers"]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```

Har hissa kya karta hai:

- **`[project]`** package ka naam rakhta hai aur batata hai ki chalne ke liye use kya chahiye. Yahan ranges (`>=2.10`) use karo, exact pins nahi; exact versions lock file rakhti hai.
- **`[project.scripts]`** ek command banata hai, to `uv run invoice-extractor` `cli.py` mein `main()` ko call karta hai.
- **`[dependency-groups]`** mein wo tools hote hain jo sirf developers ko chahiye. `uv sync` default roop se `dev` group install karta hai; `uv sync --no-dev` use production image se bahar rakhta hai.
- **`[build-system]`** batata hai ki `src/` ko installable package kaise banana hai. Iske bina uv folder ko scripts ka ek dheela collection maanta hai aur aapka package install nahi karta.
- **`[tool.pytest]`** pytest 9 mein judi native TOML table hai. Puraane pytest par, unhi keys ke saath `[tool.pytest.ini_options]` use karo.

**Python pin karna.** `requires-python` wo range hai jise support karne ka aap waada karte ho. `.python-version` wo ek version hai jo sab log, CI samet, asal mein use karte hain; na ho to uv use download kar leta hai. Python 3.15 9 October 2026 ko aaya, par pehle hi din move karna zaroori nahi: `.python-version` badhaane se pehle check karo ki aapki bhaari libraries naye version ke liye wheels publish karti hain, phir CI ko saabit karne do.

### src layout, aur install wala step jo sab bhool jaate hain

Code `src/` mein ho to Python `invoice_extractor` ko sirf isliye import nahi kar sakta ki aap project folder mein khade ho. Yahi to point hai: tests aapke package tak waise hi pahunch sakte hain jaise koi user, yaani install ke zariye. Package mein koi file chhoot jaaye, ya `pyproject.toml` mein koi galat setting ho, to wo client ke server par nahi, aapke laptop par hi dikh jaati hai.

Iska nateeja lagbhag har beginner ko atka deta hai. Agar package install nahi hai, to tests shuru hone se pehle hi fail ho jaate hain:

```text
E   ModuleNotFoundError: No module named 'invoice_extractor'
```

`uv sync` project ko `.venv` mein **editable** mode mein install karta hai, to aapke edits bina reinstall kiye asar karte hain. Plain pip ke saath yahi haath se karo: ek venv banao aur activate karo, phir `pip install -e . --group dev` chalao (`--group` ke liye pip 25.1 ya uske baad ka version chahiye). `PYTHONPATH` mein `src` jodkar ya `conftest.py` mein `sys.path` hacks daalkar error ko "fix" mat karo; isse layout ki di hui suraksha hi hat jaati hai.

### Lock files aur --locked

`uv add httpx` ek hi step mein range ko `pyproject.toml` mein jodta hai aur `uv.lock` update karta hai. Lock har package ka exact version aur file hash record karti hai, un packages samet jin par aapke packages depend karte hain. Jo bhi application ya service aap deploy karte ho, uske liye ise commit karo. Doosron ke liye publish ki gayi library `pyproject.toml` mein phir bhi dheeli ranges rakhti hai, taaki apne users par versions na thope, par apne CI ke liye uski lock commit karna phir bhi kaam ka hai.

CI, Dockerfiles aur README mein `uv sync --locked` se install karo. Agar kisi ne `pyproject.toml` haath se edit ki aur `uv lock` chalana bhool gaya, to ye turant ruk jaata hai:

```text
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
  cause: Requirements for `invoice-extractor==0.1.0` differ; added: httpx>=0.28
```

Plain `uv sync` iski jagah chupchaap lock ko dobara likh deta, aur jo versions aap test karte ho wo un versions se bhatak jaate jo aap ship karte ho. Upgrade jaanboojhkar karo, ek baar mein ek package: `uv lock --upgrade-package pydantic`, tests chalao, dono files commit karo. pip mein lock ke baraabar pip-tools jaise tool se bani fully pinned requirements file hoti hai; `pip freeze` bhi chalta hai par usmein wo sab bhi mil jaata hai jo sanyog se install pada ho.

### ruff se lint aur format

**Ruff** ek fast tool hai jo do kaam karta hai. `ruff check` ek **linter** hai: ye sambhavit bugs aur kharaab patterns dhoondhta hai. `ruff format` ek **formatter** hai: ye spacing aur line breaks ko ek house style mein dobara likhta hai, taaki reviews commas par nahi, logic par hon.

```text
uv run ruff check --fix    # find problems, fix the safe ones
uv run ruff format         # rewrite layout
```

ruff 0.16 se default set bada hai: kai groups se 400 se zyaada rules. Ek `select` line us default ko hatakar theek unhi groups ko rakhti hai jinke naam aap lete ho. Upar wali line usse chhota, predictable set deti hai: `E` aur `F` (pycodestyle aur Pyflakes), `I` (sorted imports), `B` (bugbear: aam bug patterns jaise mutable default argument) aur `UP` (aapke Python version ke liye naya, aasaan syntax). Rule groups ek-ek karke jodo; puraane codebase par sab kuch ek saath chalu karne se saikdon warnings aati hain aur team linter hi band kar deti hai.

### Secrets aur settings

Code secrets ko environment variables se padhta hai, aur kahin se nahi:

```python
client = ModelClient(api_key=os.environ["MODEL_API_KEY"])
```

Agar variable nahi hai, to ye start-up par hi `KeyError: 'MODEL_API_KEY'` raise karta hai, jo pehle invoice par aane wali uljhi hui failure se kahin behtar hai. Local par values ek `.env` file mein rakho aur `uv run --env-file .env` se load karo. Ek `.env.example` commit karo jismein naam hon aur asli values na hon:

```text
MODEL_API_KEY=
LOG_LEVEL=INFO
```

Apni `.gitignore` check karo: `uv init` jo likhta hai wo `.venv` ko cover karti hai par `.env` ko nahi, to use khud jodo aur `git check-ignore .env` se confirm karo. Agar kabhi koi asli key kisi commit mein pahunch jaaye, to baad ke commit mein file delete karne se kuch nahi hota, kyunki wo git history mein rehti hai. Pehle key revoke aur rotate karo, phir safaai karo.

### Logging

Logging **ek baar**, entry point par configure karo, aur kahin nahi:

```python
# cli.py
import logging
import os


def main() -> None:
    logging.basicConfig(
        level=os.environ.get("LOG_LEVEL", "INFO").upper(),
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
    )
```

Baaki har module bas apne naam ka ek logger maangta hai aur aise facts log karta hai jin par koi anjaan action le sake:

```python
# extract.py
log = logging.getLogger(__name__)

log.warning(
    "invoice=%s field=total model_value=%r error=%s",
    data.get("id"),
    data["total"],
    err,
)
```

Values ko arguments ki tarah pass karo, jaise upar, f-string banane ki jagah; tab logging module sirf unhi messages ko format karta hai jo wo asal mein emit karta hai. Agar aapka log platform JSON fields mein search kar sakta hai, to format ko har line par ek JSON object kar do; ids, fields aur timings log karne ki aadat wahi rehti hai. Kisi command ke asli output ke liye, jaise extract kiya hua JSON, `print` ab bhi theek hai; program kya kar raha hai iske messages ke liye ye galat hai.

| Level | Kiske liye | Production mein |
| --- | --- | --- |
| DEBUG | Developers ke liye detail: prompts, raw replies | Off |
| INFO | Aam events: ek file process hui, uski duration ke saath | On |
| WARNING | Ajeeb par sambhaal liya gaya: ek retry jo safal raha, ek bad input jo skip hua | On |
| ERROR | Kuch fail hua aur kisi insaan ki zaroorat hai | On, aur alerts |

API keys, passwords, poore documents ya personal data, jaise customer phone numbers ya PAN numbers, kabhi log mat karo. Unki jagah ids, sizes aur timings log karo.

### Tests, aur ek fake model client

pytest khud, fixtures, parametrised tests aur mocking "Writing tests with pytest" lesson (B3) mein hain. Project structure ke liye zaroori ye hai ki cheezein kahan rehti hain. Shared fixtures `tests/conftest.py` mein jaate hain, jise pytest apne aap load karta hai. Jo code model ko call karta hai, uske liye sabse saaf design client ko andar pass karna hai, taaki test use ek fake de sake:

```python
# tests/conftest.py
import json
from pathlib import Path

import pytest

FIXTURES = Path(__file__).parent / "fixtures"


class FakeModelClient:
    """Returns a fixed reply and records each prompt. No network, no cost."""

    def __init__(self, reply: dict):
        self.reply = json.dumps(reply)
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply


@pytest.fixture
def sample_invoice() -> str:
    return (FIXTURES / "sample_invoice.txt").read_text(encoding="utf-8")


@pytest.fixture
def fake_client() -> FakeModelClient:
    return FakeModelClient(
        {
            "id": "INV-0001",
            "gstin": "33ABCDE1234F1Z5",
            "total": "1500.00",
            "items": [
                {"description": "Cotton yarn", "amount": "1000.00"},
                {"description": "Dyeing", "amount": "500.00"},
            ],
        }
    )
```

Ye unit tests aapka apna logic check karte hain aur har push par ek second se kaafi kam mein chal jaate hain. Asli model ke jawaabon ko parakhna alag kaam hai, jo asli, labelled examples ke ek fixed set par evaluation run se hota hai; "Test sets and evals" lesson (P1) 30 se 100 cases se shuru karne ka sujhaav deta hai.

### Har push par CI

CI (continuous integration) har push aur pull request par ek clean machine par wahi checks chalata hai, to "mere laptop par pass hua tha" koi daleel nahi reh jaati. Ek poora GitHub Actions workflow:

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.4.0
      - run: uv sync --locked
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run pytest
```

uv `.python-version` padhta hai aur runner par wahi Python install karta hai. Ek gotcha: `setup-uv` ki nayi releases ke liye `@v10` jaisa koi short tag nahi hai, to poora version likho (ya, aur sakhti se, commit hash). Branch protection chalu karo taaki CI red hone par koi pull request merge na ho sake.

### README

Achha README kisi anjaan ko aapse kuch bhi pooche bina clone se passing tests tak pahuncha deta hai:

```text
git clone <repository-url> && cd invoice-extractor
uv sync --locked
cp .env.example .env          # then put your own key in .env
uv run pytest
uv run --env-file .env invoice-extractor tests/fixtures/sample_invoice.txt
```

Ise likho, phir `/tmp` mein ek fresh clone mein khud follow karo. Zyaadatar READMEs doosri line par hi toot jaate hain.

## Ek example se samjho

Aapne Coimbatore ke exporter ke liye invoice extractor banaya. Agle mahine Karthik ko ise aapke bina chalana aur sambhalna hai.

**Pehla din.** Wo repository clone karta hai aur README follow karta hai. `uv sync --locked` theek wahi versions install karta hai jo aapne test kiye the, aur `uv run pytest` 12 passed batata hai. Baarah mein se do tests:

```python
import pytest
from pydantic import ValidationError

from invoice_extractor.extract import parse_amount, parse_invoice
from invoice_extractor.models import Invoice


def test_total_matches_line_items(sample_invoice, fake_client):
    inv = parse_invoice(sample_invoice, client=fake_client)
    assert inv.total == sum(i.amount for i in inv.items)
    assert "Cotton yarn" in fake_client.prompts[0]


def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValidationError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

Pehla test `parse_invoice` ko `conftest.py` wala fake client deta hai, to ye bina network call ke parsing logic check karta hai aur ye bhi ki invoice ka text prompt tak pahuncha. GSTIN hamesha 15 characters ka hota hai, aur `Invoice` model 11 characters wale ko reject kar deta hai.

**Ek mahine baad.** Production mein ek invoice fail hota hai. Log line ye hai:

```text
2026-12-18 10:14:03,512 WARNING invoice_extractor.extract invoice=INV-8812 field=total model_value='12,40,000.00' error=not a number
```

Karthik turant samajh jaata hai ki kya hua. Model ne total ko Indian digit grouping (12 lakh 40 thousand) ke saath copy kiya, aur `parse_amount` ne seedhe `Decimal(value)` call kiya, jo commas reject karta hai. Har test pass hua kyunki fake reply mein `"1500.00"` tha, aisa format jo asli invoices mein kabhi tha hi nahi. Wo teen steps mein kaam karta hai:

1. **Reproduce.** Wo ek test jodta hai jo kisi bhi fix se pehle fail hota hai:

```python
def test_reads_indian_digit_grouping():
    assert str(parse_amount("12,40,000.00")) == "1240000.00"
```

2. **Fix.** Wo ek line badalta hai: `return Decimal(value.replace(",", ""))`. `float` ki jagah `Decimal` use karne se paise exact rehte hain.
3. **Prove.** Sabhi 13 tests pass hote hain, ruff clean hai, aur wo push karta hai. Change merge hone se pehle CI ek clean runner par checks dohraata hai.

Wo fake reply ko bhi `"1,500.00"` kar deta hai, kyunki fake utna hi achha hota hai jitne achhe replies aap use dete ho; unki shape asli logs se copy karo. Poora fix use akele kareeb 20 minutes mein ho jaata hai.

| Tooling ke bina | Tooling ke saath |
| --- | --- |
| Kisi user se "kabhi-kabhi fail hota hai" | Invoice, field aur value batane wali ek log line |
| Fix saabit karne ka koi tareeka nahi | Ek test jo fix se pehle fail aur baad mein pass hota hai |
| Server par alag package versions | Har jagah `uv sync --locked` |
| Karthik aapko WhatsApp par message karta hai | Karthik akele fix karta hai, aur CI uska kaam check karta hai |

## Aam galtiyaan

- **System Python mein install karna.** Aapke laptop par chalta hai aur kahin nahi. Har project ki apni `.venv` hoti hai.
- **Aisa src layout jo kabhi install hi nahi hua.** Tests `ModuleNotFoundError` ke saath fail hote hain. Ek `[build-system]` jodo aur `uv sync` chalao, ya `pip install -e .`; `sys.path` patch mat karo.
- **Lock file commit na karna, ya CI mein plain `uv sync` chalana.** Mahinon baad kisi dependency ki nayi release fresh install tod deti hai. `uv.lock` commit karo aur `--locked` use karo.
- **`.venv` ya `.env` commit karna.** Pehla repository ko phula deta hai; doosra keys leak karta hai. Dono ko ignore karo, `.env.example` commit karo, aur jo bhi key kabhi commit hui ho use rotate karo.
- **Har module mein, ya library code ke andar `basicConfig` call karna.** Logging ek baar, entry point mein configure karo.
- **Secrets ya personal data log karna.** Ids, sizes aur timings log karo, keys, poore documents ya phone numbers kabhi nahi.
- **Production mein DEBUG chalu chhod dena.** Ye disks bhar deta hai, paid log platforms par paise lagte hain, aur aksar customer data wale raw prompts print karta hai.
- **Unit tests jo asli model ko call karte hain.** Ye dheeme hote hain, paise lagte hain aur random fail hote hain. Fake client pass karo; quality alag evaluation mein naapo.
- **Har lint rule ek saath chalu karna.** Saikdon warnings, aur team unhein padhna chhod deti hai. Rule groups dheere-dheere jodo.
- **Aisa README jise kisi ne follow hi nahi kiya.** Handover se pehle fresh clone se use test karo.

## Practice karo

Neeche linked pytest ka Get Started page poora karo, phir Python ke logging tutorial ka basic section.

1. **Restructure karo.** `uv init --package` chalao aur apni likhi koi ek script `src/` mein le jao. `pyproject.toml` mein `[dependency-groups]`, `[tool.pytest]` aur `[tool.ruff.lint]` jodo, phir `uv sync` karo aur `uv.lock` aur `.python-version` commit karo.
2. **Install ka asar dekho.** Ek scratch venv mein jahan package install nahi hai, pytest chalao aur `ModuleNotFoundError` padho. Phir use install karo aur dobara chalao.
3. **Model ko fake karo.** Agar aapka code model ko call karta hai, to function ko aisa badlo ki wo client ko parameter ki tarah le, `conftest.py` mein ek `FakeModelClient` fixture likho, aur ek test jodo jo ise use kare aur ek jo check kare ki bad reply par saaf error raise hota hai.
4. **Lint aur log karo.** `ruff check --fix` aur `ruff format` chalao. Debugging wale har `print` ko sahi level ki logger call se badlo, aur environment se `LOG_LEVEL` lekar apne entry point mein logging ek baar configure karo.
5. **Secrets aur CI.** Koi bhi key `.env` mein le jao, `.env` ko `.gitignore` mein jodo, ek `.env.example` commit karo, aur upar wala workflow jodo. Push karo aur use green hote dekho.
6. **Anjaan wala test.** Apni repository `/tmp` mein clone karo, sirf apna README follow karo, aur jo bhi step toote use theek karo.

**Aapka kaam poora hai jab aap** repository kisi dost ko de sako jo README se `uv sync --locked` aur `uv run pytest` chalaye aur har test pass hote dekhe, aur saath hi CI latest commit par wahi result dikhaye.
