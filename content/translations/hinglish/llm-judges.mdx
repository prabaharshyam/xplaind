## Ye kya hai

**LLM judge** ek language model hai jise doosre model ke output ko grade karne ko kaha jata hai: "Kya ye answer passages ke prati faithful hai? Reason ke saath yes ya no mein jawab do", ya "Is reply ko is rubric ke against 1 se 5 tak rate karo". Judges se open-ended outputs (summaries, explanations, replies) ko scale par evaluate karna possible ho jata hai, jahan code checks kaam nahi karte.

Lekin judge khud bhi ek model hai, jisme errors aur biases hote hain. Uske scores par bharosa karne se pehle use check karna zaroori hai.

```flow
Case | ek excerpt aur uski summary -> Code checks | word limit 150? citation maujood? Exact aur free
Case -> Judge | "Unsupported statements ki list banao, phir SUPPORTED ya UNSUPPORTED"
Judge -> Calibration | 80 summaries do lawyers ne grade ki; judge 74 par agree karta hai: 92.5%
Calibration -> Is rubric ke liye bharosemand
Judge -> Pairwise tests | A, B aur B, A dikhao; sirf consistent verdicts rakho
```

Ye lesson Chennai ke ek legal-tech startup ko follow karta hai jo naap raha hai ki uski judgment summaries mein unsupported claims hain ya nahi.

## Ye kaam kaise karta hai

**Narrow, specific rubric likho.** Judges vague scales ("Ye answer kitna achha hai, 1 se 10?") ki jagah ek baar mein ek saaf sawaal ("Kya answer mein koi aisa claim hai jo passages se support nahi hota?") par behtar karte hain. Yes ya no, ya chhota labelled scale pasand karo, aur pehle ek chhota reason maango.

**Judge ko wo do jo use chahiye.** Sawaal, output aur reference: faithfulness ke liye retrieve kiye passages, correctness ke liye expected answer, compliance ke liye policy.

**Logon ke saath agreement check karo.** Ek ya do logon se 30 se 100 outputs usi rubric se grade karwao. Judge se compare karo. Agar agreement kam hai, toh disagreements padho aur rubric ya examples theek karo. Judge ka prompt ya model badalne ke baad dobara check karo.

**Jaane-pehchaane biases.**

- *Position bias*: do answers compare karte waqt judges aksar pehle (ya doosre) dikhaye gaye ko pasand karte hain. Positions badlo aur average lo.
- *Length bias*: lambe, zyada detailed answers behtar na hone par bhi zyada scores le jaate hain.
- *Self-preference*: models apni family ke outputs ko zyada rate kar sakte hain.
- *Leniency*: judges aksar zyada udaar hote hain; saaf-saaf kharab examples se calibrate karo.

**Jab code decide kar sake toh code use karo.** Exact values, JSON validity, required fields, word limits, citation ki maujoodgi, banned phrases: ye sab code se check karna behtar hai, jo free, tez aur hamesha consistent hota hai.

**Cost.** Judges har case par model calls jodte hain. Jahan agreement unchi rehti hai wahan chhote models use karo, aur judges ko offline ya samples par chalao.

**Biases aur unke fixes:**

| Bias | Kaisa dikhta hai | Fix |
| --- | --- | --- |
| Position | Pehle dikhaya gaya answer zyada chunta hai | Dono orders chalao; consistent verdicts rakho |
| Length | Lambe answers ko zyada score | Code mein word limit; rubric kahe ki length quality nahi hai |
| Self-preference | Apni family ke outputs ko zyada rate karta hai | Alag family ka judge use karo, ya logon se check karo |
| Leniency | Zyadatar outputs pass ho jaate hain | Saaf kharab examples jodo; verdict se pehle problems poochho |

**Agreement compute karna.** Yes-or-no judge ke liye, agreement un cases ka hissa hai jahan judge aur human label match karte hain. Sirf rate nahi, disagreements bhi dekho: agar judge un outputs ko pass karta hai jinhe log fail karte hain, toh woh bahut udaar hai aur asli problems nikal jaayengi. Dono tarah ke disagreements ko alag track karo, aur failures par high agreement ka lakshya rakho, kyunki eval inhi ko pakadne ke liye hai.

**Judge prompt likhna.** Ek hi sawaal batao, reference material do, pass aur fail ko ek-ek chhote example ke saath define karo, aur jawab dene se pehle judge se evidence list karne ko kaho. Pehle reason maangne se verdicts zyada consistent hote hain aur padhte waqt disagreements samajhna aasaan ho jata hai.

**Judge model chunna.** Agreement ka level set karne ke liye pehle ek strong model se shuru karo, phir usi calibration set par ek chhota, sasta model try karo. Agar agreement kuch points ke andar rahe, toh routine runs ke liye chhota wala use karo aur spot checks ke liye strong wala rakho. Judge ka model version baaki dependencies ki tarah pin karo: ek chupke se hua model update scores ko shift kar sakta hai aur is mahine ke numbers ko pichhle mahine se incomparable bana sakta hai.

**Pipeline mein judges kahan fit hote hain.** Pehle code checks chalao aur jo outputs unhe pehle hi fail kar chuke hain unke liye judge skip karo, isse calls bachti hain. Offline evals mein har case par judge chalao, aur online monitoring ke liye live traffic ke chhote random sample par. Production mein judge failures ko review queue mein bhejo, jahan log unhe confirm ya overturn karte hain, aur confirm huye ko test set mein jodo.

**Code mein ek judge.** Pehle evidence aur aakhir mein verdict maango, structured output ke roop mein, taaki verdicts gina aasaan ho aur reasons padhna aasaan:

```python
import json
import anthropic

client = anthropic.Anthropic()
JUDGE_MODEL = "claude-sonnet-5-5"           # pin a dated version where offered
JUDGE_PROMPT = """You check one thing: does the ANSWER contain any claim not supported by the PASSAGES?
Ignore style, length and tone.
PASS example: every number and fact in the answer appears in a passage.
FAIL example: the answer gives a fee the passages never mention.
Reply only with JSON: {"unsupported_claims": [...], "verdict": "pass" or "fail"}"""

def judge(question, passages, answer):
    msg = f"QUESTION:\n{question}\n\nPASSAGES:\n{passages}\n\nANSWER:\n{answer}"
    r = client.messages.create(model=JUDGE_MODEL, max_tokens=400, system=JUDGE_PROMPT,
                               messages=[{"role": "user", "content": msg}])
    text = "".join(b.text for b in r.content if b.type == "text")
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        return {"verdict": "error", "raw": text}       # count these; do not guess
```

Jab guaranteed shape chahiye ho toh us lesson ke structured-output features use karo; upar ka fallback kam se kam broken replies ko chhupane ki jagah gin leta hai.

**Logon ke saath agreement, code mein.** Same cases par judge aur human labels compare karo, aur chance ke liye correct karo:

```python
def agreement(human, judge):
    """Two equal-length lists of 'pass' / 'fail'."""
    n = len(human)
    observed = sum(h == j for h, j in zip(human, judge)) / n
    p_h, p_j = human.count("pass") / n, judge.count("pass") / n
    expected = p_h * p_j + (1 - p_h) * (1 - p_j)
    kappa = (observed - expected) / (1 - expected) if expected < 1 else 1.0
    missed = sum(h == "fail" and j == "pass" for h, j in zip(human, judge))
    return {"agreement": round(observed, 2), "kappa": round(kappa, 2), "failures_missed": missed}
```

Kappa lagbhag 0.6 se upar aam taur par workable hai aur 0.8 se upar strong. `failures_missed` ka har case padho: ye wahi problems hain jo judge nikalne dega.

**Judge ek model plus ek prompt hai.** Dono mein se kuch bhi badlo aur aapke paas ek naya judge hai jiske scores purane se comparable nahi hain. Har score ke saath judge ka model version aur prompt version store karo, aur jab bhi kuch badlo, naye numbers par bharosa karne se pehle calibration set par dobara chalao.

**Judges ke prakaar.** Rubric waale general model ke alawa, specialised bhi hote hain: outputs ko score karne ke liye train kiye reward models, ek check (toxicity, faithfulness) ke liye fine-tune kiye chhote classifiers, aur comparison judges jo do answers mein se behtar chunte hain. Specialised judges ek narrow kaam ke liye sasta aur zyada consistent hote hain; general judges flexible aur shuru karne mein tez.

**Judges apne aap se bhi disagree karte hain.** Ek hi judge ko ek hi case par do baar chalao toh woh alag verdicts de sakta hai. Ise apne calibration set par naapo; agar kuch percent se zyada flip ho, toh rubric tight karo, jahan support ho wahan temperature 0 use karo, ya close cases ke liye teen runs ka majority lo.

## Ek example se samjho

Chennai ka ek legal-tech startup court judgments summarise karta hai. Woh naapna chahte hain ki summaries mein unsupported claims hain ya nahi.

- Judge prompt: "Ye ek judgment excerpt aur ek summary hai. Summary ka koi bhi statement jo excerpt se support nahi hota, list karo. Phir SUPPORTED ya UNSUPPORTED mein jawab do."
- Do lawyers 80 summaries grade karte hain. Judge unse 74 par agree karta hai (92.5%).
- Ek alag comparison task mein (do summaries mein se kaunsi behtar hai), judge 63% baar jo pehle dikhayi gayi thi use chunta tha. Woh dono orders dikhane aur sirf consistent verdicts ginne par switch karte hain.
- Unhe ye bhi pata chalta hai ki judge lambi summaries ko zyada rate karta tha. Woh 150-word limit ka code check aur rubric mein ek line jodte hain ki length koi quality nahi hai.

Faithfulness judge ab har model ya prompt change par chalta hai, aur lawyers mahine mein 20 cases spot-check karte hain.

| Khoj | Fix | Result |
| --- | --- | --- |
| Judge 80 mein se 74 par lawyers se agree hua | Kuch zaroorat nahi | Faithfulness ke liye bharosemand |
| 63% baar pehli summary chuni | Dono orders, sirf consistent verdicts | Fair comparisons |
| Lambi summaries ko zyada rate kiya | Code mein 150-word limit; length par rubric line | Length ko ab inaam nahi |

## Aam galtiyaan

- **Logon ke saath agreement check kiye bina judge par bharosa karna.**
- **Vague 1-to-10 scales.**
- **Position aur length bias ko ignore karna.**
- **Jo code check kar sakta hai uske liye judge use karna.**
- **Judge badalne ke baad dobara check na karna.**
- **Alag judge versions ke scores compare karna.** Pehle recalibrate karo.
- **Unparseable judge replies ko chhupana.** Unhe errors ki tarah gino aur dekho.
- **Sirf agreement report karna**, chance-corrected agreement ya missed failures nahi.

## Jab LLM judge use na karein

- **Code decide kar sakta hai**: exact values, formats, word counts, required fields, banned phrases.
- **Reference answer maujood hai aur exact match hona chahiye**, jaise koi number ya category.
- **High-stakes verdicts** jinki zimmedaari insaanon ko leni chahiye, jaise medical ya legal correctness: experts use karo, aur judge sirf unke review ko prioritise karne ke liye.
- **Aapne abhi agreement check nahi ki**: jab tak nahi karte, judge ka score ek andaaza hai.

## Demo se production tak

- **Judge ke model aur prompt versions pin karo** aur har score ke saath store karo.
- **50 se 100 human-graded cases ka calibration set rakho** aur har judge change par dobara chalao.
- **Judge error aur flip rates track karo.**
- **Production mein judge failures ko human review mein bhejo**, aur confirm huye ko test set mein jodo.
- **Judge cost ka alag budget rakho** aur sab kuch judge karne ki jagah live traffic ko sample karo.
