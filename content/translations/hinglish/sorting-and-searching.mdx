## Ye kya hai

**Sorting** items ko order mein rakhta hai. Data sort hone ke baad duplicates saath-saath aa jaate hain, extremes siron par hote hain, aur tum kuchh bhi jaldi dhoondh sakte ho.

**Binary search** sorted data mein kisi item ko dhoondhne ke liye beech waala item check karta hai aur woh aadha hissa phenk deta hai jismein item ho hi nahin sakta. Har check bache hue hisse ko aadha karta hai, isliye lagbhag log₂ n checks lagte hain: 10 lakh items ke liye 20, 1 crore ke liye 24. Aur general tareeke se kahein to, ye dhoondhta hai ki koi yes/no test "no" se "yes" par kahaan flip hota hai, jaise "kya `a[i]` kam se kam x hai?". Isi tarah possible answers ki ek range mein search karna **binary search on the answer** kehlaata hai.

**Two pointers** ek array mein do positions chalaakar pair aur range waale problems nested loops ki jagah ek hi pass mein hal karte hain. **Sliding window** sabse achha contiguous stretch dhoondhne waala two-pointer pattern hai.

Aage dikhaaye gaye `first_at_least` code se 42 ke liye binary search (`lo = 0`, `hi = 10` se shuru karke):

```flow
dir: LR
title: [3 8 15 21 27 33 42 50 61 77] mein 42 ke liye binary search
Check 1: index 5 par 33 -[42 se chhota: daayein jaao]-> Check 2: index 8 par 61
Check 2: index 8 par 61 -[chhota nahin: rakho, baayein jaao]-> Check 3: index 7 par 50
Check 3: index 7 par 50 -[chhota nahin: rakho, baayein jaao]-> Check 4: index 6 par 42
Check 4: index 6 par 42 -[chhota nahin: lo aur hi mil gaye]-> Answer: index 6
```

Chaar checks, jabki baayein se scan karne par saat lagte.

56 ka sum dene waala pair dhoondhte two pointers:

```flow

title: Two pointers: sorted [5 12 18 25 30 38 45] mein 56 ka sum dene waala pair
L 5 par, R 45 par: sum 50 -[bahut chhota: L ko daayein khiskaao]-> L 12 par, R 45 par: sum 57

L 12 par, R 38 par: sum 50 -[bahut chhota: L ko daayein khiskaao]-> L 18 par, R 38 par: sum 56, mil gaya
```

## Ye kaam kaise karta hai

### Sorting algorithms aur unki cost

| Algorithm | Average time | Worst time | Extra space | Stable? | Kab ye sahi choice hai |
|---|---|---|---|---|---|
| Insertion sort (aur bubble sort) | O(n²) | O(n²) | O(1) | haan | bahut chhoti ya lagbhag sorted lists, jahaan insertion sort O(n) ke kareeb hota hai |
| Merge sort | O(n log n) | O(n log n) | O(n) | haan | predictable time; linked lists; memory ke liye bahut badi files |
| Quicksort | O(n log n) | O(n²) | O(log n) | nahin | memory mein tez, random ya median-of-three pivot ke saath |
| Heap sort | O(n log n) | O(n log n) | O(1) | nahin | extra memory ke bina ek guaranteed bound |
| Python ka `sorted` aur `list.sort` | O(n log n) | O(n log n) | O(n) tak | haan | real data, jismein aksar pehle se order mein runs hote hain |
| Counting sort (radix sort isi par bana hai) | O(n + k) | O(n + k) | O(n + k) | haan | chhoti range k waali integer keys, jaise 100 mein se marks |

**Merge sort** list ko tab tak aadha-aadha karta hai jab tak har tukde mein ek item na reh jaaye, phir baar-baar aage waala chhota item uthaakar sorted tukdon ko merge karta hai: lagbhag log₂ n levels, har level par O(n) merging, isliye O(n log n).

**Quicksort** ek pivot chunta hai, chhote items baayein aur bade daayein le jaata hai, aur har side ko sort karta hai. Baraabar splits se O(n log n) milta hai. Pehle se sorted data par "hamesha pehla item chuno" karne se har baar n items 0 aur n − 1 mein bant-te hain, cost O(n²), isliye asli implementations random pivot ya median of three chunte hain.

**Python ka sort**, jise aam taur par Timsort kehte hain, merge sort aur insertion sort ka hybrid hai. Ye pehle se order mein maujood runs dhoondhta hai, chhote runs ko insertion sort se badhaata hai aur unhein merge karta hai, isliye pehle se sorted list mein bas ek O(n) pass lagta hai. Python 3.11 se ye merges ka order Powersort strategy se chunta hai.

**Comparison sorts O(n log n) ko beat kyun nahin kar sakte.** n items n! orders mein ho sakte hain, aur sort ko unmein farq karna padta hai. Har comparison zyada se zyada possibilities ko aadha karta hai, isliye worst case mein kam se kam log₂(n!) comparisons chahiye, mota-mota n log₂ n. 10 items ke liye 10! hota hai 36,28,800, to kam se kam 22 comparisons. Counting sort kabhi compare nahin karta, isliye is limit se bach jaata hai: 0 se 100 tak ke 10 lakh marks ko 101 counters se ek pass mein sort kar deta hai.

### Stability aur sort keys

Sort **stable** hota hai jab equal keys waale items apna original order banaaye rakhein. Multi-key sorts mein ye matter karta hai. Orders ko city ke hisaab se list karne ke liye, aur har city ke andar dates order mein rakhne ke liye, tum pehle date se aur phir city se sort kar sakte ho: doosra sort baraabar cities ke beech date order sirf isliye banaaye rakhta hai kyunki woh stable hai. Python mein ek-step waala `sorted(orders, key=lambda o: (o.city, o.date))` bhi yahi result deta hai. Python stability ki guarantee deta hai, `reverse=True` ke saath bhi; C++ `std::sort`, heap sort aur typical quicksort nahin dete.

### Kya poora sort chahiye?

- **Sirf sabse chhota ya sabse bada:** `min()` ya `max()`, ek O(n) pass.
- **1 crore scores mein se top 10:** `heapq.nlargest(10, scores)` 10 items ka heap rakhta hai, k = 10 ke saath lagbhag O(n log k).
- **Sirf exact lookups,** jaise "kya ye PAN list mein hai?": ek baar `set` banaao, phir har lookup average par O(1). Sort tab karo jab order chahiye: ranges, "par ya uske baad pehla", sabse nazdeeki value, ranks.

### Off-by-one bugs ke bina binary search

Zyadatar bugs conventions milaane se aate hain. Ek bharosemand convention hai **half-open range**: answer hamesha `lo` se `hi` ke beech kahin hota hai, aur jab dono milte hain to tum ruk jaate ho.

```python
def first_at_least(a, x):
    """Index of the first item that is at least x; len(a) if there is none."""
    lo, hi = 0, len(a)            # the answer is always in lo..hi
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1          # mid and everything left of it is too small
        else:
            hi = mid              # mid might be the answer, so keep it
    return lo

marks = [10, 20, 20, 20, 30]
print(first_at_least(marks, 20))   # 1
print(first_at_least(marks, 99))   # 5, which is len(marks): not found
```

Har pass range ko chhota karta hai, isliye loop khatam hota hai. 20 ke liye ye indices 2, 1 aur 0 check karta hai aur 1 return karta hai, yaani teen 20 mein se pehla. Python ka `bisect.bisect_left` yahi karta hai, isliye asli code mein library call karo:

| Call | Kya return karta hai | `[10, 20, 20, 20, 30]` par |
|---|---|---|
| `bisect_left(a, x)` | pehla index jiska item kam se kam x ho | `bisect_left(a, 20)` hai 1 |
| `bisect_right(a, x)` | pehla index jiska item x se bada ho | `bisect_right(a, 20)` hai 4 |
| `bisect_right(a, x) - bisect_left(a, x)` | kitne items x ke baraabar hain | 4 − 1 = 3 |
| result `len(a)` ke baraabar | kuchh bhi qualify nahin karta | `bisect_left(a, 99)` hai 5 |

To agar x maujood hai, to woh pehli baar `bisect_left` par aur aakhri baar `bisect_right(a, x) - 1` par aata hai.

Java ya C++ mein 32-bit integers ke saath, `lo + hi` lagbhag 2.1 billion paar hote hi `(lo + hi) / 2` overflow ho sakta hai; Joshua Bloch ne 2006 mein Java ki apni library mein ye bug bataaya tha. Wahaan `lo + (hi - lo) / 2` likho. Python ke integers overflow nahin hote.

### Binary search on the answer

Kai problems "sabse chhoti value jo kaam kare" poochhte hain: ek capacity, ek daily limit, sabse pehla din. Agar "kya v kaam karta hai?" test **monotonic** hai (ek baar yes, to har bade v ke liye yes), to possible answers ki range par binary search karo. `first_at_least` template use karo, bas `a[mid] < x` ki jagah "mid kaam nahin karta" rakho. Ismein lagbhag log₂(range ka size) checks lagte hain, har ek test ka ek run.

Precondition sabse zyada matter karti hai. "Kya day d tak cumulative sign-ups 50,000 tak pahunch gaye?" monotonic hai, kyunki totals kabhi kam nahin hote. "Kya us din ki sales ₹1 lakh se upar thi?" yes, no, yes ja sakta hai, aur binary search bina kisi error ke galat din return karega.

Real-valued answer ke liye, jaise koi rate, floats shaayad kabhi na milein: tay sankhya mein halvings chalaao, jaise 60, ya tab ruko jab `hi - lo` tumhari zaroorat ki precision se kam ho jaaye.

### Two pointers aur sliding windows

**Pair method sahi kyun hai.** Maan lo bache hue sabse chhote aur sabse bade items ka sum bahut kam hai. Sabse chhota item bache hue kisi aur ke saath aur bhi chhota sum dega, isliye woh kisi answer mein nahin ho sakta, aur use chhodna safe hai. Sum bahut bada ho to yahi logic sabse bade item ko chhodta hai. Har step ek item hataata hai, isliye zyada se zyada n − 1 steps.

```python
def has_pair(prices, target):
    left, right = 0, len(prices) - 1
    while left < right:
        total = prices[left] + prices[right]
        if total == target:
            return prices[left], prices[right]
        if total < target:
            left += 1             # need a bigger sum
        else:
            right -= 1            # need a smaller sum
    return None

print(has_pair([5, 12, 18, 25, 30, 38, 45], 56))   # (18, 38)
```

Unsorted data ke liye, pehle sort karo (O(n log n)), ya ek set ke saath ek pass karo aur check karo ki `target - p` pehle dikh chuka hai ya nahin (O(n) time aur memory).

**Sliding window** apna right edge ek baar mein ek step badhaata hai aur, jab tak rule toota hua hai, apna left edge chhota karta hai. Ye tabhi sahi hai jab chhota karne se rule poora karna hamesha aasaan ho. "Total budget ke andar" mein ye property tabhi hoti hai jab har value zero ya usse zyada ho.

### Pattern pehchaanna

```flow
title: Kaun-sa pattern fit hota hai?
Contiguous stretch? -[haan]-> Sliding window | O(n); chhota karne se madad milni chahiye
Contiguous stretch? -[nahin]-> Target waala pair?
Target waala pair? -[haan, sorted]-> Two pointers | O(n) time, O(1) memory
Target waala pair? -[haan, unsorted]-> Hash set | O(n) time aur memory
Target waala pair? -[nahin]-> Pehla, aakhri ya sabse chhota jo kaam kare?
Pehla, aakhri ya sabse chhota jo kaam kare? -[test monotonic hai]-> Binary search | O(log n) checks
Pehla, aakhri ya sabse chhota jo kaam kare? -[test aage-peechhe flip hota hai]-> Scan karo ya phir se socho
```

Interview mein, code karne se pehle pattern aur uski precondition (sorted, monotonic ya non-negative) batao.

## Ek example se samjho

Sneha Hyderabad ke ek online coaching platform ke liye analytics chalaati hai. Numbers sirf samjhaane ke liye hain.

### 1. Budget ke andar dinon ka sabse lamba run

Lagaataar dinon ka sabse lamba run kaun-sa hai jiska kul ad spend ₹1 lakh ke andar raha? Ek saal mein 66,795 possible runs hote hain (365 × 366 ÷ 2), isliye sabko check karna O(n²) hai. Sliding window ek pass leta hai:

```python
def longest_within(spend, budget):
    best = total = left = 0
    for right, amount in enumerate(spend):
        total += amount                   # grow: day `right` joins
        while total > budget:             # shrink until within budget
            total -= spend[left]
            left += 1
        best = max(best, right - left + 1)
    return best

week = [30, 20, 40, 10, 25, 60, 15]       # spend in thousands of rupees
print(longest_within(week, 100))          # 4
```

Ek hafte ka trace, budget 100 (₹1 lakh) ke saath:

| Din | Spend | Chhota karne ke baad window | Total | Ab tak ka best |
|---|---|---|---|---|
| 1 | 30 | din 1 se 1 | 30 | 1 |
| 2 | 20 | din 1 se 2 | 50 | 2 |
| 3 | 40 | din 1 se 3 | 90 | 3 |
| 4 | 10 | din 1 se 4 | 100 | 4 |
| 5 | 25 | din 2 se 5 (din 1 hata) | 95 | 4 |
| 6 | 60 | din 4 se 6 (din 2 aur 3 hate) | 95 | 4 |
| 7 | 15 | din 5 se 7 (din 4 hata) | 100 | 4 |

Answer hai 4 din (din 1 se 4). Har din ek baar judta hai aur zyada se zyada ek baar nikalta hai, isliye zyada se zyada 2n steps: O(n). Din 6 par ek shrink step kaafi nahin tha, isiliye code `if` nahin, `while` use karta hai.

Ye sirf isliye safe hai kyunki spend kabhi negative nahin hota. Figures mein net refunds daalo aur ye toot jaata hai: `[80, 30, -50]` aur budget 100 ke saath, total 110 pahunchne par window din 1 hata deti hai aur 2 report karti hai, lekin teenon dinon ka total 60 hai, to sahi answer 3 hai. Negative values ke saath koi aur method use karo, jaise prefix sums.

### 2. Woh pehla din jab sign-ups target tak pahunche

Finance poochhta hai: cumulative sign-ups pehli baar kis din target tak pahunche? Sign-ups kabhi negative nahin hote, isliye "kya day d tak pahunch gaye?" no, no, phir uske baad har din yes hai. Yaani monotonic:

```python
from bisect import bisect_left
from itertools import accumulate

def first_day_reaching(daily, target):
    totals = list(accumulate(daily))      # running totals, O(n)
    i = bisect_left(totals, target)       # first day whose total is at least target
    return i if i < len(totals) else -1   # len(totals) means never reached

print(first_day_reaching([120, 90, 200, 150, 80], 400))   # 2
print(first_day_reaching([120, 90, 200, 150, 80], 9999))  # -1
```

Ye `first_at_least` template hi hai, jo library kar rahi hai. Totals teesre din, index 2 par, 410 tak pahunchte hain.

`totals` banaana khud ek O(n) pass hai, isliye ek target ke liye seedha scan bhi utna hi achha hai. Search tab faayda deta hai jab use kai targets ke jawaab dene hon: ek saal ke daily data ke liye har ek mein lagbhag 9 checks, aur das saal ke hourly data (87,600 hours) ke liye lagbhag 17.

### 3. Aisa answer dhoondhna jo kisi list mein nahin hai

Mentors assignment batches ko submission order mein grade karte hain. Is hafte ke saat batches mein 40, 25, 35, 50, 20, 30 aur 45 pages hain, aur sab 3 din mein grade hone chahiye, har din ke batches ek daily page limit ke andar. Sabse chhoti limit kaun-si hai jo kaam kare?

Answer 50 (sabse bada batch fit hona chahiye) aur 245 (sab kuchh ek din mein) ke beech hai, aur badi limit ko kabhi zyada din nahin lagte, isliye test monotonic hai:

```python
def days_needed(pages, limit):
    days, today = 1, 0
    for p in pages:
        if today + p > limit:             # today is full; start a new day
            days, today = days + 1, 0
        today += p
    return days

def smallest_limit(pages, max_days):
    lo, hi = max(pages), sum(pages)       # smallest and largest sensible answers
    while lo < hi:
        mid = (lo + hi) // 2
        if days_needed(pages, mid) <= max_days:
            hi = mid                      # mid works; try smaller
        else:
            lo = mid + 1                  # too small; go bigger
    return lo

print(smallest_limit([40, 25, 35, 50, 20, 30, 45], 3))    # 95
```

Answer hai roz 95 pages: 40 + 25, phir 35 + 50, phir 20 + 30 + 45. 94 ki limit ko 4 din lagte hain. Search 196 possible limits ko 7 checks mein cover karta hai, har check ek O(n) pass.

## Aam galtiyaan

**Unsorted data par ya aise test par binary search jo monotonic nahin hai.** Galat answer milta hai aur koi error nahin aata. Prove karo ki test "no, phir yes" jaata hai aur kabhi waapas nahin aata.

**Off-by-one bounds.** Inclusive aur exclusive `hi` milaana, ya `mid` neeche round hone par `lo = mid` likhna, do items bachne par loop ko hamesha ke liye chalaata rehta hai. Ek hi convention use karo, jaise half-open template, aur lengths 0, 1 aur 2 test karo. Java ya C++ mein `lo + (hi - lo) / 2` bhi likho.

**bisect ka result check kiye bina use karna.** Kuchh bhi qualify na kare to `bisect_left` `len(a)` return karta hai, isliye usse indexing karne par `IndexError` aata hai.

**Loop ke andar sort karna.** Loop ke bahar ek baar sort karo. Aur jab poore order se kam chahiye, to `min()`, `heapq.nlargest` ya set use karo.

**Maan lena ki har sort stable hai.** C++ `std::sort`, heap sort aur zyadatar quicksorts stable nahin hain, isliye two-step multi-key sort galat nikal sakta hai.

**Unsorted data par two pointers use karna.** Pehle sort karo ya hash set use karo.

**Negative values ke saath sum-based sliding window use karna.** Refunds ya losses ise chupchaap tod dete hain. Check karo ki har value zero ya usse zyada hai.

**Window ko `while` ki jagah `if` se chhota karna.** Ek step kaafi nahin ho sakta, jaisa trace mein din 6 dikhaata hai.
