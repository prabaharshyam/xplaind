## Ye kya hai

Kisi application mein prompt code hota hai. **System prompt** mein woh standing instructions hote hain jo har request mein common hote hain: model ka role, task, rules, output format aur examples. **User message** mein is request ka khaas input hota hai. Achha prompt design sirf us ek input par nahi, hazaaron alag-alag inputs par results ko clear, consistent aur testable banata hai.

```flow
System prompt | har request ke liye same, versioned file: role aur audience, task, context (price list, timings, policies), rules ("pata na ho toh bolo aur hand over karo"), output format aur length, 2-3 alag examples -> Model
User message | har request mein badalta hai: customer ka message, data ki tarah treat hota hai -> Model
Model -> Reply -> Aapke test set se check hota hai
```

System prompt fixed aur versioned rehta hai; sirf user message ek request se agli request tak badalta hai.

Ye lesson Chennai ki ek phone-repair chain ko follow karta hai, jab woh ek line ke prompt ko aise prompt mein badalti hai jo sainkdon real messages par kaam kare.

## Ye kaam kaise karta hai

**System prompt mein kya jaata hai.**

- *Role aur audience*: "Aap Chennai ki ek mobile phone repair chain ke customers ke sawaalon ke jawab dete ho."
- *Task*: har input ke saath kya karna hai.
- *Context*: model ko chahiye facts (policies, product names, tone guidelines).
- *Rules*: kya karna hai aur kya nahi, aur pata na ho toh kya karna hai ("Agar sawaal repairs ke baare mein nahi hai, toh bolo ki aap sirf repairs mein madad kar sakte ho").
- *Output format*: exact structure, length, language.
- *Examples*: ek se teen worked input-output pairs.

Secrets ko prompts se bahar rakho; users kabhi-kabhi model se unhe bulwa lete hain.

**Specific raho aur wajah batao.** "Customers phone par padhte hain isliye answers 80 words se kam rakho" "be concise" se behtar kaam karta hai. Models wajah ko achhe se follow karte hain.

**Examples descriptions se behtar hote hain.** Ek achha example tone, length, format aur edge-case handling sab ek saath dikhata hai. Alag-alag examples use karo, ek tricky case bhi, taaki model ek example ko bahut literally copy na kare.

**Lambe prompts ko structure do.** Instructions, context aur examples ke liye saaf sections ya tags use karo taaki model unhe alag pehchaan sake. Lambe reference documents ko sawaal se pehle rakho.

**Data ko instructions se alag karo.** User ke diye text ko saaf mark karo ("Customer ka message neeche ke tags ke beech hai") taaki uske andar ke instructions data ki tarah treat hon.

**Bahut saare inputs par test karo.** Jo prompt ek example par chalta hai woh aksar doosron par fail hota hai. Mushkil aur ajeeb inputs sahit 20 se 50 realistic inputs ka set banao, sab chalao, failures padho, ek cheez badlo aur phir chalao. Yahi evals ki shuruaat hai.

**Prompts ko version karo.** Unhe version control mein files mein rakho, code mein kai jagah paste mat karo.

**Prompt improvement loop:**

| Round | Badlaav | 50 test messages par pass count |
| --- | --- | --- |
| 0 | "Customer ko politely reply do." | 18 |
| 1 | Role, facts aur price list jode | 31 |
| 2 | Rules jode: list mein na ho woh prices nahi, rival shops nahi, language matching | 39 |
| 3 | Format aur 60-word ki wajah jodi | 42 |
| 4 | Do examples jode | 44 |
| 5 | Water-damage rule aur example joda | 47 |

Har round mein ek hi cheez badli, isliye team ko pata tha ki kis badlaav se madad mili. Jab koi badlaav pass count ghatata tha, toh use revert kar diya jaata tha. Yahi discipline prompt ke kaam ko andaaze ki jagah engineering banati hai.

**Saaf sections wala prompt.** Tags model ko saaf batate hain ki kaunsa hissa kaunsa hai, aur aapke liye ek baar mein ek hissa badalna aasaan hota hai:

```python
SYSTEM = """<role>
You answer WhatsApp questions from customers of Fixit, a phone repair chain in Chennai.
</role>

<facts>
Shops: T. Nagar, Velachery, Anna Nagar. Open 10 am to 8 pm, closed Tuesdays.
{price_list}
</facts>

<rules>
- Quote only prices in the price list. If a repair is not listed, say a technician will call.
- Never mention other shops.
- Reply in the customer's language (English, Tamil or Tanglish).
- Keep replies under 60 words, because customers read on phones.
- Water damage: never promise a fix; ask them to bring the phone in, switched off.
</rules>

<examples>
Customer: screen change for redmi note 12 how much
Reply: A Redmi Note 12 screen replacement is ₹2,400 and takes about an hour. Visit any Fixit shop, 10 am to 8 pm, except Tuesdays.
</examples>"""

def build_messages(customer_text):
    return [{"role": "user", "content": f"<customer_message>\n{customer_text}\n</customer_message>"}]
```

**Prompt ko code ki tarah test karo.** Har test message chalao, code mein properties check karo aur pass count print karo:

```python
import re

PRICES = {"2,400", "1,800", "3,200", "650"}                # every price in the list
TAMIL = re.compile(r"[஀-௿]")

def check(customer_text, reply):
    problems = []
    if len(reply.split()) > 60:
        problems.append("too long")
    for amount in re.findall(r"₹\s?([\d,]+)", reply):
        if amount not in PRICES:
            problems.append(f"unlisted price ₹{amount}")
    if TAMIL.search(customer_text) and not TAMIL.search(reply):
        problems.append("did not reply in Tamil")
    if re.search(r"\b(other shop|competitor)\b", reply, re.I):
        problems.append("mentioned another shop")
    return problems

def run(cases, generate):
    failures = {c: p for c in cases if (p := check(c, generate(c)))}
    print(f"{len(cases) - len(failures)}/{len(cases)} passed")
    return failures
```

Code checks zyadatar rule breaks ko free mein pakad lete hain. Model judge sirf un qualities ke liye rakho jo code nahi dekh sakta, jaise reply ne sach mein sawaal ka jawab diya ya nahi.

**Bade tasks ko steps mein todo.** Ek prompt jo classify kare, price lookup kare, reply likhe aur use translate kare, debug karna mushkil hota hai. Kai chhote prompts (classify, phir reply, phir check) har ek ko test karna aasaan hota hai, simple steps ke liye sasta model use ho sakta hai, aur ye bilkul dikhate hain ki kahan fail hua. Cost: zyada calls aur thodi zyada delay.

**Jab madad kare tab reasoning ko jagah do.** Jin tasks mein kaam nikalna padta hai, jaise kai rules ke against eligibility check karna, wahan answer dene se pehle model se reason karne ko kehne se accuracy aksar badh jaati hai. Reasoning models ye khud karte hain. Reasoning ko us cheez se bahar rakho jo customer dekhta hai, aur reasoning nahi, final answer check karo.

**Prompts ko versions ke saath files mein rakho.** Har prompt ko version name ke saath file ki tarah store karo, start-up par load karo, aur har request ke saath version log karo. Tab quality mein girawat ko us prompt badlaav tak trace kiya ja sakta hai jisne use kiya.

## Ek example se samjho

Chennai ki ek phone-repair chain ek assistant chahti hai jo customers ke WhatsApp messages ke replies draft kare.

Pehla prompt: "Customer ko politely reply do." 30 real messages par replies lambe hain, aise prices ka wada karte hain jo shop offer nahi karti, aur rival brands ki warranties ke sawaalon ka bhi jawab de dete hain.

Improved system prompt (sankshep mein):

- Role: Chennai mein chaar stores wali "FixFast Mobiles" ke liye staff ke review ke liye replies draft karta hai.
- Facts: common repairs ki price list, store timings, parts par 90 din ki warranty.
- Rules: list mein na ho aisi price ka wada kabhi mat karo ("inspection ke baad confirm karenge" bolo); doosri shops ke baare mein baat mat karo; customer ki language mein reply do (Tamil ya English); 60 words se kam kyunki staff ye WhatsApp par bhejta hai.
- Format: greeting, answer, next step.
- Do examples: English mein screen replacement ka sawaal aur Tamil mein battery ka sawaal.

Wahi 30 messages aur 20 naye par dobara chalane par: 50 mein se 44 drafts bina ya thode edits ke use ho sakte hain, pehle 30 mein se 11 the. Chhe failures zyadatar water damage ke baare mein hain; team un ke liye ek rule aur example jodti hai aur dobara chalati hai.

**Bache chhe failures ne kya sikhaya.** Failures padhne mein das minute lage aur ye kisi bhi general prompting tip se zyada useful tha. Customers ne water damage ko kai tareeke se bataya ("phone balti mein gir gaya", "baarish mein bheeg gaya"), aur model ne aisi kharabi ke liye repair prices bata diye jisme pehle inspection chahiye. Ek rule ("kisi bhi liquid damage ke liye phone laane ko bolo; price kabhi mat batao") aur ek example ne zyadatar ko theek kar diya.

## Aam galtiyaan

- **Ek example par test karna.** Alag-alag inputs ka set use karo aur failures padho.
- **Dhundhle instructions.** Bilkul batao ki kya chahiye aur kyun.
- **Pata na hone wale case ke liye rule na hona.** Model ko batao ki jab jawab uske context mein na ho toh kya kare.
- **Prompts mein secrets.** Wahan kabhi passwords ya keys mat daalo.
- **Ek saath kai badlaav.** Ek cheez badlo, dobara chalao, compare karo.

- **Prompt ko rules se lad dena.** "Never" aur "always" wali lines ka ek page model ko confuse karta hai aur khud ko hi kaat deta hai. Rules kam, specific aur samjhaye hue rakho, aur test set jinhe zaroori nahi dikhata unhe hata do.
- **Prompt ko do-teen inputs par test karna.** Ajeeb wale sahit 20 se 50 ka set use karo.
- **Kai-step wale task ke liye ek bada prompt.** Use todo taaki har step test ho sake.
- **Prompts ko code mein kai jagah paste karna**, jisse versions alag ho jaate hain.

## Jab prompt ka kaam jawab nahi hai

- **Model ke paas facts nahi hain**: lambe prompts ki jagah retrieval ya tools jodo.
- **Kai dhyaan wale rounds ke baad bhi same format galti rehti hai**: structured output ya fine-tuning ise theek kar sakta hai.
- **Task ko exact logic chahiye**, jaise tax calculations: use code mein karo aur model ko result samjhane do.
- **Gains tham gaye hain**: agar teen rounds mein har ek se sirf ek pass badhta hai, toh bottleneck kahin aur hai.

## Demo se production tak

- **Prompts ko files mein version karo** aur har request par version log karo.
- **Har prompt badlaav par CI mein test set chalao**, pull request par pass count ke saath.
- **Ek baar mein ek cheez badlo** aur ek chhota changelog rakho ki har version ne kya theek kiya.
- **Model badalne par dobara test karo**, kyunki ek model ke liye tune kiye prompts doosre par alag chal sakte hain.
- **User text ko saaf marked tags mein rakho** aur use kabhi rules badalne mat do.
