## இது என்ன

**Graph**-னா **edges**-ஆ இணைச்ச **nodes**-ஓட தொகுப்பு. Tracks-ஆ இணைச்ச metro stations, friendship-ஆ இணைச்ச மனுஷங்க, links-ஆ இணைச்ச web pages, இதெல்லாமே graphs தான். Edges-க்கு direction இருக்கலாம் (one-way street), weight-உம் இருக்கலாம் (தூரம் அல்லது விலை).

**Tree** ஒரு special graph: connected-ஆ இருக்கும், cycles இருக்காது, அதனால எந்த ரெண்டு nodes-க்கு நடுவுலயும் சரியா ஒரே ஒரு path தான். பொதுவா மேல ஒரு **root**-உம், அதுக்கு கீழ **children**-உம் இருக்கும். உங்க laptop-ல இருக்குற folders, ஒரு company-யோட org chart, ஒரு web page-ஓட HTML எல்லாமே trees. **Binary tree**-ல ஒவ்வொரு node-க்கும் அதிகபட்சம் ரெண்டு children; **binary search tree**-ல சின்ன values இடது பக்கமும் பெரிய values வலது பக்கமும் இருக்கும்.

இதை explore பண்ண ரெண்டு வழிகள் திரும்ப திரும்ப வரும்: **breadth-first search** (BFS), **depth-first search** (DFS).

## இது எப்படி work ஆகுது

Code-ல graph-ஐ பொதுவா **adjacency list**-ஆ வைப்போம்: ஒவ்வொரு node-ல இருந்தும் அதோட neighbours-க்கு போற ஒரு dict.

```python
metro = {
    "Rajiv Chowk": ["Kashmere Gate", "Mandi House", "Central Secretariat"],
    "Kashmere Gate": ["Rajiv Chowk", "Civil Lines"],
    "Mandi House": ["Rajiv Chowk", "ITO"],
    "Central Secretariat": ["Rajiv Chowk", "ITO"],
    "ITO": ["Mandi House", "Central Secretariat"],
    "Civil Lines": ["Kashmere Gate", "Vishwavidyalaya"],
    "Vishwavidyalaya": ["Civil Lines"],
}
```

**BFS** வட்டம் வட்டமா explore பண்ணும். ஒரு node-ல ஆரம்பிச்சு, அதோட எல்லா neighbours-ஐயும் visit பண்ணி, அப்புறம் அவங்களோட neighbours-ஐ, இப்படியே போகும். Nodes கண்டுபிடிச்ச வரிசையிலேயே handle ஆகணும்னு **queue** use பண்ணும். ஒரு நேரத்துல ஒரு edge தான் வெளியே போறதால, BFS ஒரு node-ஐ முதல் தடவை அடையுறது குறைஞ்ச edges வழியாதான். அதனால "குறைஞ்ச stops" அல்லது "degrees of separation"-க்கு இதுதான் சரியான tool.

**DFS** ஒரு path-ல முடிஞ்ச அளவு ஆழமா போகும், அப்புறம் பின்னாடி வந்து அடுத்த branch-ஐ try பண்ணும். இது **stack** use பண்ணும், பெரும்பாலும் recursion வழியா call stack. அடைய முடிஞ்ச எல்லாத்தையும் explore பண்றதுக்கும், cycles கண்டுபிடிக்கிறதுக்கும், trees-ஐ ஒரு குறிப்பிட்ட order-ல நடக்கிறதுக்கும் DFS இயல்பா பொருந்தும்.

Graphs-ல ரெண்டுக்குமே **visited** set வேணும், இல்லன்னா cycles இருக்குறதால முடிவில்லாம சுத்தும். ரெண்டுமே O(V + E) time எடுக்கும்; V-னா nodes எண்ணிக்கை, E-னா edges எண்ணிக்கை.

| கேள்வி | எதை use பண்றது | ஏன் |
|---|---|---|
| ரெண்டு nodes-க்கு நடுவுல குறைஞ்ச hops, unweighted | BFS | edges தூரத்தை வச்சு explore பண்ணுது |
| ஒரு node-ல இருந்து அடைய முடிஞ்ச எல்லாம் | DFS அல்லது BFS | ரெண்டுமே எல்லாத்தையும் visit பண்ணும்; DFS எழுத சின்னதா இருக்கும் |
| Cycle கண்டுபிடிக்கிறது, dependencies இருக்குற tasks-ஐ order பண்றது | DFS | அதோட back-tracking cycles-ஐ காட்டும்; topological order கொடுக்கும் |
| ஒரு network-ல connected groups | Visit பண்ணாத ஒவ்வொரு node-ல இருந்தும் DFS அல்லது BFS | ஒவ்வொரு run-உம் ஒரு group-ஐ mark பண்ணும் |
| Weighted edges இருக்குறப்போ மலிவான path | Dijkstra's algorithm | BFS weights-ஐ கண்டுக்காது |
| Sorted tree-ல ஒரு value-ஐ தேடுறது | binary search tree walk | ஒவ்வொரு step-லயும் தேடலை பாதியா குறைக்கும் |

## ஒரு worked example

Kabir, Delhi-ல commuters-க்கு ஒரு route helper app build பண்றாங்க. User ரெண்டு stations-ஐ தேர்ந்தெடுத்தா, app குறைஞ்ச stops இருக்குற route-ஐ காட்டும். பக்கத்துல இருக்குற stations-க்கு நடுவுல ஒவ்வொரு hop-உம் ஒரே மாதிரி count ஆகுறதால, BFS பொருந்தும்.

```python
from collections import deque

def fewest_stops(graph, start, goal):
    queue = deque([[start]])          # each item is a path so far
    visited = {start}
    while queue:
        path = queue.popleft()
        station = path[-1]
        if station == goal:
            return path
        for nxt in graph[station]:
            if nxt not in visited:
                visited.add(nxt)
                queue.append(path + [nxt])
    return None
```

"Mandi House"-ல இருந்து "Civil Lines"-க்கு, BFS முதல்ல Rajiv Chowk, ITO (ஒரு stop தூரம்), அப்புறம் Kashmere Gate, Central Secretariat (ரெண்டு stops தூரம்), அப்புறம் Civil Lines (மூணு stops தூரம்) கண்டுபிடிக்கும். அது `Mandi House → Rajiv Chowk → Kashmere Gate → Civil Lines`-ஐ return பண்ணும்; இதைவிட சின்ன route இல்ல, ஏன்னா BFS முதல்ல எல்லா ரெண்டு-stop routes-ஐயும் check பண்ணிடுச்சு.

Maintenance-ல ஒரு station மூடியிருந்தா, மத்த stations அங்கிருந்து cut off ஆகுதான்னு app எச்சரிக்கணும். Kabir மூடின station-ஐ graph-ல இருந்து எடுத்துட்டு, ஒரு பெரிய interchange-ல இருந்து DFS run பண்ணி, இன்னும் அடைய முடிஞ்ச எல்லா stations-ஐயும் list பண்றாங்க:

```python
def reachable(graph, start, seen=None):
    seen = seen if seen is not None else set()
    seen.add(start)
    for nxt in graph[start]:
        if nxt not in seen:
            reachable(graph, nxt, seen)
    return seen
```

Result-ல இல்லாத எந்த station-ஐயும் அடைய முடியாது, அதுக்கு warning banner காட்டுவாங்க.

அப்புறம் team fares-ஐ சேர்க்கும்போது, குறைஞ்ச stops இருக்குற route எப்பவும் மலிவா இருக்காது. அது ஒரு weighted graph; Kabir Dijkstra's algorithm-க்கு மாறுறாங்க. அது total cost வச்சு order பண்ற priority queue இருக்குற BFS.

## பொதுவா பண்ற தப்புகள்

**Visited set இல்லாம இருக்குறது.** Cycles இருக்குற graph-ல BFS, DFS முடிவில்லாம சுத்தும். Node-ஐ queue-ல சேர்க்கும்போதே visited-ன்னு mark பண்ணுங்க, வெளியே எடுக்கும்போது இல்ல; இல்லன்னா அதே node-ஐ நிறைய தடவை சேர்ப்பீங்க.

**Shortest path-க்கு DFS use பண்றது.** DFS ஒரு path-ஐ கண்டுபிடிக்கும், shortest path-ஐ இல்ல. குறைஞ்ச edges வேணும்னா BFS use பண்ணுங்க.

**Weighted graph-ல BFS use பண்றது.** BFS edges-ஐ எண்ணும், cost-ஐ இல்ல. Edges-க்கு வேற வேற weights இருந்தா Dijkstra's algorithm use பண்ணுங்க.

**ஆழமான recursion limits.** நீளமான chain-ல recursive DFS Python-ஓட recursion limit (சுமார் 1,000)-ஐ தாண்டலாம். ரொம்ப ஆழமான graphs-க்கு explicit stack use பண்ணுங்க.

**எல்லா tree-உம் balanced-ன்னு நினைக்கிறது.** ஏற்கனவே sorted ஆன data-ல build பண்ண binary search tree நீளமான chain-ஆ மாறிடும், search O(n)-க்கு விழுந்துடும். Real systems self-balancing trees use பண்ணும்.

**Edge direction-ஐ மறக்குறது.** Instagram-ல ஒரு follow ஒரு பக்கம் மட்டும் தான். Directed edges-ஐ அவை போற direction-ல மட்டும் store பண்ணுங்க.
