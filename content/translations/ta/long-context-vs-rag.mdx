## இது என்ன

ஒரு model-க்கு தேவையான தகவலை கொடுக்க ரெண்டு வழிகள் இருக்கு:

- **Long context**: முழு document-ஐ (அல்லது பல documents-ஐ) prompt-ல போட்டு கேள்வியை கேக்குறது.
- **Retrieval (RAG)**: மிகவும் relevant ஆன சில passages-ஐ search பண்ணி, அவற்றை மட்டும் prompt-ல போடுறது.

நவீன models ரொம்ப நீளமான inputs-ஐ ஏத்துக்கும், அதனால long context பெரும்பாலும் சாத்தியம். அது புத்திசாலித்தனமான்றது accuracy, cost, latency, scale-ஐ பொறுத்தது.

| | Long context | RAG |
|---|---|---|
| Model-க்கு என்ன கிடைக்குது | முழு contract (40,000 tokens), instructions, கடைசில கேள்வி | 3 chunks, கேள்வி (3,000 tokens) |
| பலம் | எல்லாத்தையும் பார்க்கும், cross-reference பண்ண முடியும் | மலிவு, வேகம், மில்லியன் கணக்கான documents-க்கு scale ஆகும் |
| பலவீனம் | Cache பண்ணாட்டி costly, slow | Retrieval miss பண்றதை இதுவும் miss பண்ணும் |

இந்த lesson-ல Chennai-ல ஒரு law firm, ரெண்டு ரொம்ப வேற வேற பயன்பாடுகளுக்காக ஒரு contract-review assistant build பண்றதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**நீளமான inputs-ல accuracy.** Models எல்லா positions-ஐயும் சமமா use பண்றதில்ல. நீளமான context-ல நடுவுல இருக்குற தகவலை, ஆரம்பத்துலயோ கடைசியிலயோ இருக்குறதை விட குறைவா நல்லா use பண்ணுதுன்னு ("lost in the middle") studies கண்டுபிடிச்சிருக்கு. எளிமையான tasks-லயும் input வளரும்போது performance குறையலாம்னும் சொல்லுது. புது models இதுல முன்னேறிருக்கு, ஆனாலும் உங்க சொந்த documents, கேள்வி வகைகள்ல test பண்ணணும்.

**Cost.** ஒவ்வொரு call-லயும் ஒவ்வொரு input token-க்கும் நீங்க காசு கொடுக்குறீங்க. ஒவ்வொரு கேள்விக்கும் 200,000-token document-ஐ அனுப்புறது, retrieve பண்ண passages-ஓட 3,000 tokens அனுப்புறதை விட ரொம்ப costly. **Prompt caching** இதை மாத்தும்: ஒரே நீளமான document பல கேள்விகள்ல திரும்ப use ஆனா, அடுத்தடுத்த calls-ல cache ஆன input ரொம்ப மலிவா, வேகமா இருக்கும்.

**Latency.** Input நீளமானா முதல் token வர்ற நேரம் கூடும். Cache பண்ணாட்டி நீளமான prompts, interactive use-ஐ slow ஆக்கும்.

**Scale.** ஒரு context window-க்கு limit இருக்கு; ஒரு company-ஓட documents-க்கு இல்லை. Corpus window-ஐ விட பெருசானதும், குறைஞ்சது எந்த documents-ஐ அனுப்பணும்னு தேர்ந்தெடுக்கவாவது ஏதாவது retrieve பண்ணியே ஆகணும்.

**கட்டைவிரல் விதிகள்.**

- ஒரு document அல்லது சில documents, அதை பத்தி ஒரே session-ல பல கேள்விகள், முழு document தேவைப்படுற கேள்விகள் (summaries, sections-க்கு நடுவுல comparisons): long context, முடிஞ்சா cache பண்ணி.
- பெரிய அல்லது வளர்ற collections, சின்ன factual கேள்விகள், நிறைய users: RAG.
- நடுவுல இருக்குற வழி: document level-ல retrieve பண்ணுங்க (சரியான ரெண்டு contracts-ஐ கண்டுபிடிங்க), அப்புறம் அந்த முழு documents-ஐ context-ல போடுங்க.

**Hybrid பழக்கங்கள்.** Long context-லயும், instructions-ஐயும் கேள்வியையும் கடைசில வைங்க, sections அல்லது pages-ஐ cite பண்ணச் சொல்லுங்க, documents-ஐ ஒரே மாதிரியான, label பண்ண format-ல வச்சுக்கோங்க.

**Options-ஐ compare பண்றது:**

| Factor | Long context | RAG |
| --- | --- | --- |
| Corpus size | Context window வரை | வரம்பே இல்லை |
| முழு document தேவைப்படுற கேள்விகள் | வலிமை | பலவீனம், chunking-ஐ பொறுத்தது |
| சின்ன factual lookups | ஓகே, ஆனா costly | வலிமை |
| ஒரு கேள்விக்கான cost | Cache இல்லாம அதிகம், caching-ஓட குறைவு | குறைவு |
| Latency | அதிகம், caching-ஓட குறைவு | குறைவு |
| மாறுற documents | ஒவ்வொரு தடவையும் திரும்ப அனுப்பணும் | மாறின items-ஐ மட்டும் re-index பண்ணணும் |
| Engineering முயற்சி | குறைவு | அதிகம்: chunking, indexing, retrieval tuning |

**ஒரு worked cost comparison.** Input-க்கு ஒரு million tokens-க்கு fixed விலைன்னு வச்சுக்கோங்க. 12 கேள்விகள்ல ஒவ்வொண்ணோடும் 40,000-token contract அனுப்புனா சுமார் 480,000 input tokens. Caching இருந்தா, அடுத்தடுத்த calls cache ஆன contract-ஐ சாதாரண விலையோட ஒரு சின்ன பகுதிக்கு படிக்கும், அதனால மொத்தம் கிட்டத்தட்ட கால் பங்குக்கு குறையலாம். RAG ஒவ்வொரு கேள்விக்கும் சுமார் 3,000 tokens அனுப்பும், மொத்தம் 36,000, இது இன்னும் மலிவு, ஆனா cross-reference கேள்விகள்ல மோசமா score பண்ணுச்சு. சரியான தேர்வு, cost-ஐ மட்டும் இல்லாம, அந்த task-க்கு accuracy-யையும் இந்த costs-யையும் சேர்த்து எடை போடணும்.

**உங்க சொந்த documents-ல test பண்றது.** Published studies எச்சரிக்கைகளை தரும், பதில்களை தராது. பதில் document-ஓட ஆரம்பத்துல, நடுவுல, கடைசில இருக்குற மாதிரி கேள்விகளையும், ரெண்டு தூரமான sections தேவைப்படுற கேள்விகளையும் எழுதுங்க. ரெண்டு வழிலயும் ஓட்டி, failures-ஐ படிங்க.

**Code-ல ஒரு position test.** ஒரு real document-ஓட வேற வேற ஆழங்கள்ல ஒரு fact-ஐ வச்சு, பதில்கள் சரியா இருக்குதான்னு பாருங்க:

```python
import anthropic

client = anthropic.Anthropic()
FACT = "The penalty for late GST filing under clause 14.3 is ₹750 per day."
QUESTION = "What is the penalty per day for late GST filing under clause 14.3?"

def plant(doc, depth):
    cut = int(len(doc) * depth)
    return doc[:cut] + "\n\n" + FACT + "\n\n" + doc[cut:]

def position_test(doc, depths=(0.05, 0.5, 0.95), runs=3):
    for d in depths:
        correct = 0
        for _ in range(runs):
            r = client.messages.create(
                model="claude-sonnet-5-5", max_tokens=100,       # check the docs for current names
                messages=[{"role": "user", "content": plant(doc, d) + "\n\n" + QUESTION}])
            text = "".join(b.text for b in r.content if b.type == "text")
            correct += "750" in text
        print(f"fact at {d:.0%} depth: {correct}/{runs} correct")
```

உங்க real documents, நீளங்களோட ஓட்டுங்க. அப்புறம் ரெண்டு தூரமான sections தேவைப்படுற கேள்விகளை test பண்ணுங்க, long context பெரும்பாலும் RAG-ஐ ஜெயிக்கிற இடம் அதுதான்.

**நீங்களே மாத்தக்கூடிய cost comparison.** இப்போதைய விலைகளை, நீங்க check பண்ண தேதியோட போடுங்க:

```python
def cost_inr(input_tokens, output_tokens, price_in, price_out, cached_tokens=0, cache_read_ratio=0.1,
             usd_to_inr=84):
    """Prices in USD per million tokens. cache_read_ratio: cached input price as a share of normal."""
    uncached = input_tokens - cached_tokens
    usd = (uncached * price_in + cached_tokens * price_in * cache_read_ratio + output_tokens * price_out) / 1e6
    return usd * usd_to_inr

questions, doc, out = 12, 40_000, 300
long_ctx = sum(cost_inr(doc + 100, out, 3, 15, cached_tokens=doc if i else 0) for i in range(questions))
rag = questions * cost_inr(3_000, out, 3, 15)
print(f"long context with caching ₹{long_ctx:.1f}, RAG ₹{rag:.1f}")
```

முதல் call முழு document-க்கும் காசு கொடுக்கும் (cache-ஐ எழுத பொதுவா கொஞ்சம் extra-வும்); அடுத்த calls cache lifetime-க்குள்ள வந்தா மலிவா படிக்கும். Numbers-ஐ உங்க சொந்த document sizes, traffic-க்கு மாத்திக்கோங்க.

**Code-ல நடுவுல இருக்குற வழி.** Chunks-ஐ இல்லாம முழு documents-ஐ retrieve பண்ணுங்க, அப்புறம் படிக்கிற வேலையை long context-க்கு விடுங்க:

```python
def doc_level_answer(question, search_docs, load_doc, max_docs=2):
    docs = search_docs(question, k=max_docs)          # search over document summaries or titles
    context = "\n\n".join(f"<document title='{d['title']}'>\n{load_doc(d['id'])}\n</document>" for d in docs)
    return context + f"\n\nAnswer using the documents above, citing titles and sections.\nQuestion: {question}"
```

கேள்விகளுக்கு முழு document தேவை, ஆனா உங்க கிட்ட நூற்றுக்கணக்கான documents இருக்கு-ன்ற contracts, policies, reports-க்கு இது பொருந்தும்.

**மூணு விஷயங்களை அளந்து தீர்மானிங்க.** உங்க கேள்வி வகைகள்ல accuracy, உங்க traffic-ல ஒரு பதிலுக்கான cost, முதல் token வர்ற நேரம். ஒவ்வொரு option-க்கும் numbers-ஐ ஒரு சின்ன table-ல எழுதி, பழக்கத்தை வச்சு இல்லாம client-கூட சேர்ந்து தேர்ந்தெடுங்க.

## ஒரு example

Chennai-ல ஒரு law firm, contract review-க்கு ஒரு assistant வேணும்னு கேக்குது. ரெண்டு use cases:

*ஒரு contract-ஐ review பண்றது.* ஒரு lawyer 60-page agreement-ஐ (சுமார் 40,000 tokens) upload பண்ணி ஒரு டஜன் கேள்விகள் கேக்குறாங்க: termination rights, indemnity caps, clauses-க்கு நடுவுல conflicts. பல பதில்களுக்கு முழு document தேவை. நீங்க contract-ஐ cache பண்ணி long context use பண்றீங்க. முதல் கேள்வி 9 seconds எடுக்குது; அடுத்தவை 2-ல இருந்து 3 seconds, cache-ஆல cost-உம் ரொம்ப குறைவு. 30 கேள்விகள் test-ல long context 90% score பண்ணுது; chunk-based RAG 73%, clauses-க்கு நடுவுல cross-references-ஐ அது miss பண்ணுச்சு.

*Firm-ஓட precedent library-ல search பண்றது.* 25,000 பழைய contracts, எந்த context window-க்கும் ரொம்ப அதிகம். Lawyers கேக்குறாங்க "Find indemnity clauses capped at fees paid in the last 12 months in IT services contracts." நீங்க metadata filters-ஓட hybrid retrieval use பண்ணி சிறந்த 20 clauses-ஐ கண்டுபிடிச்சு, அப்புறம் ஒரு model அவற்றை citations-ஓட summarise பண்ணுது.

Firm-க்கு ரெண்டும் கிடைக்குது, ஒவ்வொண்ணும் பொருந்துற இடத்துல.

| Use case | Approach | Accuracy | Notes |
| --- | --- | --- | --- |
| ஒரு 60-page contract-ஐ review பண்றது | Long context, cached | 90% | Chunk-based RAG 73% score பண்ணுச்சு |
| 25,000 precedents-ல search பண்றது | Filters-ஓட hybrid retrieval | Recall-ஆல அளக்கப்படுது | எந்த window-க்கும் ரொம்ப பெருசு |

## பொதுவா பண்ற தப்புகள்

- **Long context எப்பவும் அதிக accuracy-னு நினைக்கிறது.** Test பண்ணுங்க; நீளம், position-ஐ பொறுத்து accuracy குறையலாம்.
- **ஒரு கேள்விக்கான cost-ஐ கண்டுக்காம இருக்கிறது.** ஒவ்வொரு கேள்விக்கும் cache இல்லாத நீளமான prompts, scale-ல costly ஆகும்.
- **Caching-ஐ மறக்கிறது.** ஒரே document-ஐ திரும்ப திரும்ப use பண்றப்போ அது economics-ஐயே மாத்தும்.
- **கேள்வியை முதல்ல வைக்கிறது.** Instructions-ஐயும் கேள்வியையும் நீளமான material-க்கு அப்புறம் வைங்க.
- **"RAG செத்துடுச்சு"ன்னு நினைக்கிறது.** பெரிய collections-க்கு இன்னும் retrieval வேணும்.
- **ஒரே document பல கேள்விகளுக்கு use ஆகும்போது caching இல்லாம costs-ஐ compare பண்றது.**
- **பெரிய window இருந்தா model அதை முழுசா நல்லா use பண்ணும்னு நினைக்கிறது.** Positions, cross-references-ஐ test பண்ணுங்க.

## தேர்வு தெளிவா இருக்கும் நேரங்கள்

- **ஒரு சின்ன document**: அதை prompt-லயே போடுங்க.
- **மில்லியன் கணக்கான documents**: ஏதாவது ஒரு வகை retrieval வேணும், குறைஞ்சது documents-ஐ தேர்ந்தெடுக்கவாவது.
- **Records, tables மாதிரி structured data-ல இருந்து வர்ற பதில்கள்**: இந்த ரெண்டுல ஒண்ணும் இல்லாம, ஒரு database query அல்லது tool use பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **தேர்ந்தெடுத்த approach-க்கு accuracy, cost, latency-ஐ** உங்க golden set-ல record பண்ணுங்க, model மாறினா திரும்ப check பண்ணுங்க.
