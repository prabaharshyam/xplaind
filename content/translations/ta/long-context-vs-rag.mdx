## இது என்ன

ஒரு கேள்விக்கு பதில் சொல்ல model-க்கு தேவையான information-ஐ குடுக்க மூணு வழிகள் இருக்கு:

- **Long context**: முழு documents-ஐ prompt-ல போட்டு, அப்புறம் கேளுங்க.
- **Retrieval (RAG)**: ஒரு index மேல ஒரு தடவை search பண்ணி, best-ஆன சில passages-ஐ மட்டும் prompt-ல போடுங்க.
- **Agentic search**: model-க்கு search tools குடுங்க (keyword search, ஒரு metadata filter, "open document", ஒரு database query), எதை தேடணும்னு அதுவே முடிவு பண்ணி, results-ஐ படிச்சு, பதில் சொல்ல முடியுற வரை திரும்ப தேட விடுங்க.

28 November 2026 நிலவரப்படி, Anthropic-ஓட லேட்டஸ்ட் Claude models ஒவ்வொண்ணுக்கும் 1-million-token context window இருக்கு, Anthropic-ஓட கணக்குப்படி அது சுமார் 555,000 வார்த்தைகள். அதனால long context பெரும்பாலும் possible தான். அது புத்திசாலித்தனமான்னு accuracy, cost, latency, scale தான் முடிவு பண்ணும்.

| | Long context | RAG | Agentic search |
| --- | --- | --- | --- |
| Model என்ன படிக்குது | முழு documents | ஒரு search-ல இருந்து 3 முதல் 10 passages | பல steps-ல அதோட searches என்ன குடுக்குதோ அது |
| பலம் | எல்லாத்தையும் பாக்குது; cross-reference பண்ணலாம் | Cheap, fast, millions of documents வரை scale ஆகும் | Multi-step கேள்விகளையும் exact identifiers-ஐயும் follow பண்ணும் |
| பலவீனம் | Length கூட கூட cost-உம் delay-உம் கூடும்; நீளமான inputs-ல accuracy குறையும் | ஒரு search miss பண்றதை இதுவும் miss பண்ணும் | அதிக calls, slow, predict பண்றது கஷ்டம் |
| Engineering | குறைவு | Chunking, indexing, tuning | நல்ல tools, step limits, logging |

## இது எப்படி வேலை செய்யுது

### Inputs பெருசாக accuracy குறையுது

நீளமான input-ல இருக்குற எல்லா position-ஐயும் models ஒரே மாதிரி நல்லா use பண்றதில்ல.

- **Lost in the middle.** Liu-வும் colleagues-உம் (2023) models-க்கு நிறைய documents குடுத்து பாத்தாங்க: பதில் ஆரம்பத்துக்கோ கடைசிக்கோ பக்கத்துல இருந்தப்போ accuracy எல்லாத்தையும் விட அதிகமா இருந்துச்சு, நடுவுல இருந்தப்போ எல்லாத்தையும் விட குறைவா இருந்துச்சு: ஒரு U-shaped curve.
- **Context rot.** Chroma-வோட report (July 2025) 18 models-ஐ test பண்ணுச்சு; input பெருசாக பெருசாக performance-ஐ நம்ப முடியாம போச்சு, simple tasks-லயும் கூட. கேள்விக்கும் பதிலுக்கும் வார்த்தையிலயும் அர்த்தத்துலயும் ஒற்றுமை குறைவா இருந்தப்போ, அதாவது model match பண்ணாம infer பண்ண வேண்டியிருந்தப்போ, இன்னும் வேகமா குறைஞ்சுது. பதில் மாதிரியே தெரியுற ஆனா பதில் இல்லாத, நம்பத்தகுந்த ஒரே ஒரு distractor sentence கூட accuracy-ஐ குறைச்சுது, distractors கூட கூட இன்னும் குறைஞ்சுது.

இதை இப்படி யோசிச்சு பாருங்க: பதிலை சுத்தி ஒரே மாதிரி தெரியுற sentences எவ்வளவு அதிகமா இருக்கோ, model தப்பானதை எடுக்க அவ்வளவு வாய்ப்பு அதிகம்.

அதனால **advertised window**-ஐயும் (API எவ்வளவு எடுத்துக்குது) **effective context**-ஐயும் தனித்தனியா பாருங்க: effective context-னா *உங்க* task accurate-ஆ இருக்குற length. ஒரு "needle in a haystack" test, அதாவது plant பண்ண ஒரு sentence-ஐ கண்டுபிடிக்குறது, ரொம்ப ஈஸியான case, இப்போதைய models பெரும்பாலும் அதை pass பண்ணிடும். அது pass ஆனாலும், clauses-ஐ compare பண்ற, figures-ஐ கூட்டுற, அல்லது ஒரு rule-ஓட பழைய version-ஐ ignore பண்ண வேண்டிய கேள்விகள் பத்தி அது பெருசா எதுவும் சொல்லாது.

### Cost: ஒவ்வொரு call-லயும் ஒவ்வொரு token-க்கும் காசு

Document cache ஆகலைன்னா, ஒவ்வொரு கேள்வியும் அதை முழுசா திரும்ப அனுப்பி, முழுசுக்கும் திரும்ப காசு கட்டுது. Claude Sonnet 5.5 list prices, 28 November 2026 அன்னைக்கு Anthropic-ஓட pricing page-ல check பண்ணது:

| Item | Million tokens-க்கு USD | Input price-ஓட மடங்கு |
| --- | --- | --- |
| Input | $2.00 | 1x |
| Cache write, 5-minute lifetime | $2.50 | 1.25x |
| Cache write, 1-hour lifetime | $4.00 | 2x |
| Cache read | $0.10 | 0.05x |

Cache-read மடங்கு model-க்கு model மாறும்: Claude Fable 5.2-ல 0.025x, Claude Opus 5.5, Sonnet 5.5-ல 0.05x, Claude Haiku 5.5 உட்பட மத்த பெரும்பாலானதுல 0.1x. சில models நீளமான prompts-க்கு ஒரு token-க்கு அதிகமாவும் charge பண்ணும்: Claude Haiku 5.5 input, prompt 100,000 tokens வரை இருந்தா million tokens-க்கு $0.10, அதை விட நீளமா இருந்தா முழு request-க்கும் $0.50 (அதே check date). மத்த providers caching-க்கு வேற மாதிரி price பண்றாங்க, அதனால உங்க provider-ஓட page-ஐ படிச்சு, date-ஐ எழுதி வைங்க.

### Prompt caching: அது என்ன மாத்துது, எப்போ fail ஆகுது

**எப்படி வேலை செய்யுது.** உங்க prompt-ஓட process பண்ண ஆரம்ப பகுதியை (prefix) provider store பண்ணி வச்சுக்குது. அப்புறம் byte-for-byte அதே prefix-ஓட வர்ற request அதை cache-ல இருந்து படிக்குது: cheap-ஆவும், first token-க்கு வேகமாவும். அதனால நீளமான, மாறாத பகுதியை முதல்ல போடுங்க, கேள்வியை கடைசியில போடுங்க; இதனால model எழுத ஆரம்பிக்குற இடத்துக்கு பக்கத்துலயே கேள்வியும் இருக்கும்.

**Lifetime.** Default-ஆ ஒரு cache entry 5 minutes இருக்கும், ஒவ்வொரு hit-உம் clock-ஐ reset பண்ணும். 1-hour lifetime-க்கு write பண்ண 2x ஆகும். Anthropic docs சொல்றபடி, 5-minute cache ஒரு read-லயே தன்னோட செலவை மீட்டுடும், 1-hour cache ரெண்டு reads-ல.

**Experts check பண்ற gotchas:**

- **Lifetime-ஐ விட நீளமான இடைவெளிகள்.** 5-minute cache-ஓட 15 minutes-க்கு ஒரு தடவை கேள்விகள் வந்தா, ஒவ்வொரு call-உம் 1.25x write-ஐ திரும்ப கட்டும், அதனால cache இல்லாம இருக்குறதை விட *அதிகமா* காசு கட்டுவீங்க.
- **மாறுற prefix.** Document-க்கு முன்னாடி ஒரு timestamp, ஒரு user name, அல்லது order மாத்தின ஒரு tool list இருந்தா, அதுக்கு அப்புறம் வர்ற எல்லாத்துக்கும் match உடைஞ்சுடும்.
- **Parallel calls.** முதல் response ஆரம்பிச்ச பிறகு தான் ஒரு cache entry available ஆகும், அதனால ஒரே நேரத்துல அனுப்புற பத்து கேள்விகளும் miss ஆகும்.
- **ஒரு user-க்கு ஒரு document.** 500 users ஒவ்வொருத்தரும் அவங்க சொந்த contract-ஐ upload பண்ணா, அது 500 தனித்தனி cache writes. Caching ஒவ்வொரு session-க்கும் உதவும், மொத்த system-க்கு இல்ல.
- **Isolation.** Caches organisations நடுவுல எப்பவுமே share ஆகாது, Anthropic-ஓட API-ல workspaces நடுவுலயும் இல்ல.

வேலை செஞ்சுதான்னு check பண்ணுங்க: response-ஓட `usage` `cache_creation_input_tokens`-ஐயும் `cache_read_input_tokens`-ஐயும் report பண்ணும். Reads zero-லயே இருந்தா, ஏதோ ஒண்ணு prefix-ஐ உடைக்குது.

### Latency-யும் scale-உம்

Input length கூட கூட time to first token கூடும், அதனால ரொம்ப நீளமான uncached prompts chat-ஐ slow-ஆ feel பண்ண வைக்கும். Agentic search ஒவ்வொரு step-க்கும் ஒரு model round trip சேர்க்கும். அப்புறம் window-க்கு ஒரு limit இருக்கு; ஒரு company-யோட documents-க்கு இல்ல. உதாரணமா, ஒவ்வொண்ணும் சுமார் 30,000 tokens இருக்குற 18,000 manuals மொத்தம் 540 million tokens, அதாவது 1-million-token window-ஓட 540 மடங்கு. Corpus window-ஐ விட பெருசானதும், எதை அனுப்பணும்னு ஏதாவது ஒண்ணு தேர்ந்தெடுக்கணும்.

### Agentic search, மூணாவது option

உங்க code தேர்ந்தெடுக்குற ஒரு search-க்கு பதிலா, model-ஏ search-ஐ ஓட்டுது. Anthropic தன்னோட context engineering guide-ல (September 2025) இந்த "just in time" approach-ஐ விவரிக்குது: Claude Code, files தேவைப்படும்போது அவற்றை கண்டுபிடிக்க glob, grep மாதிரி tools-ஐ use பண்ணுது, சில files மட்டும் முன்னாடியே load ஆகும். Guide trade-off-ஐ நேரடியா சொல்லுது: run time-ல explore பண்றது, முன்னாடியே compute பண்ண retrieval results-ஐ படிக்குறதை விட slow.

```flow
dir: LR
title: ஒரு கேள்விக்கு agentic search
கேள்வி -> Client வச்சு contracts-ஐ தேடு | filters-ஓட keyword search
Client வச்சு contracts-ஐ தேடு -> Master agreement-ஐ திற | clause 9-ஐ படிக்குது
Master agreement-ஐ திற -> Clause 9 references-ஐ தேடு
Clause 9 references-ஐ தேடு -> Citations-ஓட பதில்
```

**எங்க ஜெயிக்கும்:** அடுத்த lookup போன result-ஐ பொறுத்து இருக்குற கேள்விகள், embeddings மழுங்கடிக்குற exact identifiers (clause numbers, error codes, part numbers), re-index பண்றதுக்கு பதிலா live-ஆ query பண்ணக்கூடிய வேகமா மாறுற data. Tools ஒவ்வொரு user-ஓட permissions-ஐயும் enforce பண்ணலாம்.

**என்ன செலவாகும்:** ஒவ்வொரு step-உம் இன்னொரு model call, அது வளர்ந்துக்கிட்டே இருக்குற conversation-ஐ திரும்ப அனுப்புது. உதாரணமா, instructions-உம் tools-உம் 2,000 tokens, ஒவ்வொரு step-லயும் 3,000 tokens results சேருதுன்னா, ஆறு steps 2,000 + 5,000 + ... + 17,000 = 57,000 input tokens அனுப்பும்; ஒரு RAG call-க்கு சுமார் 3,000 தான். முந்தைய turns-ஐ cache பண்ணா இது கொஞ்சம் குறையும்.

**எப்படி fail ஆகும்:** ரொம்ப சீக்கிரம் நிறுத்திடும், அதே search-லயே loop ஆகும், அல்லது tool output-ஆல தன்னோட context-ஐ நிரப்பிடும். நல்ல defaults: steps-க்கு ஒரு cap வைங்க (உதாரணமா, 8), tools முழு files-க்கு பதிலா document IDs-ஓட சின்ன snippets-ஐ return பண்ணட்டும், failures-ஐ படிக்க ஒவ்வொரு tool call-ஐயும் log பண்ணுங்க.

### இன்னும் ரெண்டு patterns

- **Document-level retrieval.** Titles, summaries அல்லது metadata மேல search பண்ணி சரியான சில முழு documents-ஐ தேர்ந்தெடுங்க, அப்புறம் long context அவற்றை படிக்கட்டும். Contracts, policies, reports-க்கு இது பொருந்தும்.
- **Map-reduce.** "40 board meetings-ஐயும் summarise பண்ணு" மாதிரி வேலைக்கு, ஒவ்வொரு document-ஐயும் தனியா summarise பண்ணுங்க (map), அப்புறம் summaries-ஐ சேருங்க (reduce). எந்த corpus size-க்கும் பொருந்தும், ஆனா detail போயிடும், அதனால ஒவ்வொரு summary-லயும் citations-ஐ வச்சுக்க சொல்லுங்க.

```python
def doc_level_prompt(question, search_docs, load_doc, max_docs=3):
    docs = search_docs(question, k=max_docs)    # over titles, summaries and metadata
    context = "\n\n".join(f"<document title='{d['title']}'>\n{load_doc(d['id'])}\n</document>" for d in docs)
    return context + f"\n\nAnswer from the documents above. Cite titles and clause numbers.\nQuestion: {question}"
```

### Privacy

Long context முழு documents-ஐ model provider-க்கு அனுப்புது; RAG passages-ஐ மட்டும் அனுப்புது. Documents-ல personal data இருந்தா, client-ஓட data agreement-ஐயும் இந்தியாவோட data-protection obligations-ஐயும் check பண்ணுங்க, task-க்கு தேவையில்லாததை redact பண்ணுங்க.

### Decision rules

- ஒண்ணு அல்லது சில documents, ஒரு session-ல நிறைய கேள்விகள், முழு text தேவைப்படுற பதில்கள்: **long context, cached**.
- பெரிய அல்லது வளர்ந்துக்கிட்டே இருக்குற collection, சின்ன factual கேள்விகள், நிறைய users: **RAG**.
- ஒண்ணை ஒண்ணு சார்ந்த பல lookups அல்லது exact identifiers தேவைப்படுற பதில்கள்: **agentic search**, step limits-ஓட.
- முழு documents வேணும், ஆனா தேர்ந்தெடுக்க நூத்துக்கணக்குல இருக்கு: **document-level retrieval, அப்புறம் long context**.

### உங்க சொந்த documents-ல position-ஐயும் distractors-ஐயும் test பண்ணுங்க

Publish ஆன studies எச்சரிக்கைகளை தான் குடுக்கும், பதில்களை இல்ல. இந்த harness கற்பனையான audit notes-ஐ (அவை real எதோடயும் மோதாது) பல depths-ல plant பண்ணுது, ஒரே மாதிரி தெரியுற distractors-ஐ சேர்க்குது, ஒரு two-hop கேள்வியை test பண்ணுது:

```python
import random

FACT = "Audit note: the Hosur warehouse inspection code is HW-7319."
DISTRACTORS = ["Audit note: the Hosur office inspection code is HO-7391.",
               "Audit note: the 2019 Hosur warehouse code, now withdrawn, was HW-1973."]
HOPS = ["Audit note: the Hosur warehouse audit is led by Farida Sheikh.",
        "Audit note: Farida Sheikh's desk extension is 4826."]
CODE_Q = "What is the current inspection code for the Hosur warehouse?"
TESTS = {   # name: (where to insert notes, question, expected answer)
    "single fact": (lambda d: [(d, FACT)], CODE_Q, "HW-7319"),
    "distractors": (lambda d: [(d, FACT)] + [(random.random(), s) for s in DISTRACTORS], CODE_Q, "HW-7319"),
    "two hops": (lambda d: [(d, HOPS[0]), ((d + 0.5) % 1, HOPS[1])],
                 "Which extension reaches the person who leads the Hosur warehouse audit?", "4826"),
}

def build(doc, inserts):
    paras = doc.split("\n\n")                        # insert between paragraphs, never mid-sentence
    for depth, note in sorted(inserts, reverse=True):
        paras.insert(int(len(paras) * depth), note)
    return "\n\n".join(paras)

def run(doc, ask, depths=(0.05, 0.25, 0.5, 0.75, 0.95), runs=3):
    for name, (inserts, question, expected) in TESTS.items():
        for d in depths:
            ok = sum(expected in ask(build(doc, inserts(d)) + "\n\nAnswer from the document only. " + question)
                     for _ in range(runs))
            print(f"{name:12} depth {d:4.0%}: {ok}/{runs} correct")
```

`ask`-னா ஒரு prompt-ஐ அனுப்பி text-ஐ return பண்ற எந்த function-உம். Anthropic SDK-ஓட:

```python
import anthropic

client = anthropic.Anthropic()

def ask(prompt):
    r = client.messages.create(model="claude-opus-5-5", max_tokens=2000,   # the model you will deploy
                               output_config={"effort": "low"},
                               messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in r.content if b.type == "text")
```

Single-fact row கிட்டத்தட்ட perfect-ஆ இருக்கும்னு எதிர்பாருங்க; distractor, two-hop rows தான் உண்மையா ஏதாவது சொல்லும். அப்புறம் sections நடுவுல comparisons மாதிரி உங்க real கேள்வி வகைகளை சேருங்க.

### நீங்க மாத்தக்கூடிய ஒரு cost model

```python
# Claude Sonnet 5.5 list prices in USD per million tokens, checked 28 November 2026
# (platform.claude.com/docs/en/about-claude/pricing). Re-check before you use them.
PRICE_IN, PRICE_OUT = 2.00, 10.00
WRITE_X, READ_X = 1.25, 0.05   # 5-minute cache write and cache read, as multiples of PRICE_IN

def call_usd(fresh_in, out, cache_write=0, cache_read=0):
    """Cost of one call. fresh_in: normal input tokens; cache_write/cache_read: cached prefix tokens."""
    inp = fresh_in + cache_write * WRITE_X + cache_read * READ_X
    return (inp * PRICE_IN + out * PRICE_OUT) / 1e6

Q, DOC, ASK, OUT, RAG_IN = 12, 40_000, 100, 300, 3_000

no_cache = Q * call_usd(DOC + ASK, OUT)
cached = call_usd(ASK, OUT, cache_write=DOC) + (Q - 1) * call_usd(ASK, OUT, cache_read=DOC)
expired = Q * call_usd(ASK, OUT, cache_write=DOC)   # every gap longer than the cache lifetime
rag = Q * call_usd(RAG_IN + ASK, OUT)

for name, usd in [("long context, no cache", no_cache), ("long context, cached", cached),
                  ("long context, cache always expired", expired), ("RAG, 3,000 tokens", rag)]:
    print(f"{name:36} ${usd:.3f}")
```

இது no cache-ல $0.998, cached-ல $0.182, cache எப்பவும் expire ஆனா $1.238, RAG-க்கு $0.110-னு print பண்ணும். Caching long-context bill-ஐ 80%-க்கு மேல குறைக்குது, அது அதை RAG-க்கு கிட்ட கொண்டு வருது; expire ஆன cache அதை எல்லாத்தையும் விட expensive option ஆக்குது. அன்னைக்கு rate-ல dollars-ஐ convert பண்ணுங்க, tokenizers வேற வேற என்பதால உங்க documents-ஓட tokens-ஐ உங்க provider-ஓட counter வச்சு எண்ணுங்க.

## ஒரு worked example

Chennai-ல ஒரு law firm-க்கு ஒரு contract assistant வேணும். கீழ இருக்குற numbers illustrative, team record பண்ற மாதிரியானவை; costs 28 November 2026 அன்னைக்கு check பண்ண Claude Sonnet 5.5 prices-ஐ வச்சு போட்டது.

**1. ஒரு contract-ஐ review பண்றது.** ஒரு lawyer 60-page agreement-ஐ (சுமார் 40,000 tokens) upload பண்ணி சுமார் 12 கேள்விகள் கேக்குறாரு: termination rights, indemnity caps, conflict ஆகுற clauses. நிறைய பதில்களுக்கு முழு document வேணும், அதனால team long context use பண்ணுது, contract cached, கேள்வி கடைசியில. Lawyers கேள்விகளுக்கு நடுவுல அடிக்கடி 5 minutes-க்கு மேல நிறுத்துவாங்க, அதனால 1-hour cache-ஐ தேர்ந்தெடுக்குறாங்க. அப்போ பன்னிரண்டு கேள்விகளுக்கு சுமார் $0.24 ஆகும், uncached-ஆ சுமார் $1.00. ஒரு 30-question test-ல long context 27 சரியா சொல்லுது, chunk-based RAG 22 சொல்லுதுன்னு வச்சுக்கோங்க, RAG miss பண்ணது பெரும்பாலும் clauses நடுவுல இருக்குற cross-references. Team distractor test-ஐயும் ஓட்டுது, ஏன்னா அவங்க contracts-ல அதே clause-ஓட பழைய, மாத்தப்பட்ட versions இருக்கு.

**2. Precedent library-ல தேடுறது.** 25,000 பழைய contracts, எந்த window-ஐயும் விட ரொம்ப பெருசு. Lawyers கேக்குறாங்க: "IT services contracts-ல, கடந்த 12 months-ல கட்டின fees அளவுக்கு cap பண்ண indemnity clauses-ஐ கண்டுபிடி". Team metadata filters (contract type, year) கூட hybrid retrieval use பண்ணி best 20 clauses-ஐ கண்டுபிடிக்குது, அப்புறம் ஒரு model அவற்றை citations-ஓட summarise பண்ணுது. அவங்க recall-ஐ measure பண்றாங்க: 50 test கேள்விகள்ல 46-க்கு சரியான clause top 20-ல இருக்குன்னு வச்சுக்கோங்க.

**3. Cross-references-ஐ follow பண்றது.** ஒரு partner கேக்குறாரு: "இந்த client கூட இருக்குற நம்ம contracts-ல எதெல்லாம், 2025 amendment-ல மாறின ஒரு master agreement clause-ஐ சார்ந்திருக்கு?" ஒரு search-ஆல இதுக்கு பதில் சொல்ல முடியாது: system amendment-ஐ கண்டுபிடிச்சு, எந்த clause மாறுச்சுன்னு படிச்சு, அப்புறம் அந்த clause-ஐ cite பண்ற contracts-ஐ கண்டுபிடிக்கணும். Team மூணு tools (client வச்சு search, document-ஐ open பண்றது, clause number வச்சு search), 8 steps cap கூட agentic search use பண்ணுது. ஒரு typical பதிலுக்கு 5 tool calls-உம் சுமார் 30 seconds-உம் ஆகுதுன்னு வச்சுக்கோங்க: chat-க்கு ரொம்ப slow, ஒரு research task-க்கு பரவாயில்ல.

## பொதுவான தப்புகள்

- **Advertised window-ஐ நம்புறது.** 1 million tokens எடுத்துக்குற ஒரு model அவற்றை நல்லா use பண்ணும்னு இல்ல. உங்க சொந்த கேள்வி வகைகள்ல effective context-ஐ measure பண்ணுங்க.
- **ஒரே ஒரு planted fact வச்சு மட்டும் test பண்றது.** அது தான் ரொம்ப ஈஸியான case. Distractors, two-hop கேள்விகள், பதிலே இல்லாத கேள்விகளை சேருங்க.
- **Caching இல்லாம costs-ஐ compare பண்றது**, அல்லது hit ஆகவே ஆகாத ஒரு cache-ஐ நம்புறது (மேல இருக்குற gotchas-ஐ பாருங்க).
- **கேள்வி, ஒரு timestamp அல்லது ஒரு user name-ஐ document-க்கு முன்னாடி போடுறது.** அது cache-ஐ உடைக்கும், accuracy-ஐயும் பாதிக்கும்.
- **"RAG செத்துடுச்சு" மாதிரி யோசிக்குறது.** பெரிய, மாறிக்கிட்டே இருக்குற collections-க்கு இன்னும் retrieval வேணும், குறைஞ்சபட்சம் documents-ஐ தேர்ந்தெடுக்கவாவது.
- **One-hop lookups-க்கு ஒரு agent-ஐ use பண்றது.** ஒரு search-லயே பதில் கிடைச்சா, agent calls-ஐயும் delay-ஐயும் தான் சேர்க்கும்.
- **Step limit அல்லது logs இல்லாம ஒரு agent-ஐ ஓட்டுறது.** பாக்க முடியாத failures-ஐ சரி பண்ண முடியாது.
- **Personal data நிறைஞ்ச முழு documents-ஐ அனுப்புறது**, passages-லயே கேள்விக்கு பதில் கிடைக்கும்போது.

## Choice obvious-ஆ இருக்கும்போது

- **ஒரு சின்ன document**: அதை அப்படியே prompt-ல போடுங்க.
- **Millions of documents**: ஏதாவது ஒரு வகை retrieval வேணும், குறைஞ்சபட்சம் documents-ஐ தேர்ந்தெடுக்கவாவது.
- **Records, tables மாதிரி structured data-ல இருந்து பதில்கள்**: இதுல எதையும் use பண்ணாம, ஒரு tool மூலமா database-ஐ query பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **தேர்ந்தெடுத்த approach-க்கு accuracy, cost, latency-ஐ record பண்ணுங்க**, உங்க golden set-ல, ஒவ்வொரு model change-லயும் திரும்ப check பண்ணுங்க.
- **Cache hit rate-ஐ track பண்ணுங்க**, `cache_read_input_tokens`-ல இருந்து, அது குறைஞ்சா alert பண்ணுங்க.
- **ஒவ்வொரு request-ஓட input tokens-ஐயும் log பண்ணுங்க**, எதிர்பாராத வளர்ச்சிக்கு alert பண்ணுங்க.
- **Position, distractor tests-ஐ திரும்ப ஓட்டுங்க**, models மாத்தும்போதோ documents பெருசாகும்போதோ.
- **Agents-க்கு, ஒவ்வொரு tool call-ஐயும் log பண்ணுங்க**, ஒரு பதிலுக்கு எத்தனை steps-னு பாருங்க; அந்த count கூடுறது ஒரு early warning.
- **Prices-ஐ அவற்றோட date கூட திரும்ப check பண்ணுங்க**, குறைஞ்சது மூணு மாசத்துக்கு ஒரு தடவை.

## Practice

Lost in the Middle abstract-ஐயும் figures-ஐயும், Chroma-வோட context rot report-ஐயும், உங்க provider-ஓட prompt caching guide-ஐயும் படிங்க.

1. ஒரு நீளமான document-ஐ (ஒரு annual report அல்லது ஒரு policy) எடுத்து 15 கேள்விகள் எழுதுங்க: சில single facts, சில தூரத்துல இருக்குற ரெண்டு sections தேவைப்படுறவை, ஒண்ணு document-ல பதிலே இல்லாதது.
2. அவற்றுக்கு long context-லயும் உங்க RAG pipeline-லயும் பதில் வாங்குங்க. ஒவ்வொண்ணுக்கும் accuracy, latency, cost-ஐ record பண்ணுங்க.
