## இது என்ன

ஒரு AI product அதோட data எவ்வளவு நல்லதோ அவ்வளவு தான் நல்லது: பதில் சொல்லும்போது அது படிக்குற documents, அது எதோட ஒப்பிட்டு judge ஆகுதோ அந்த examples, அதை better ஆக்குற feedback. **Data strategy**-னா இதெல்லாத்துக்கும் ஆன plan; build ஆரம்பிக்கிறதுக்கு முன்னாடியே எழுதணும், launch-க்கு அப்புறம் தட்டுத்தடுமாறி கண்டுபிடிக்கக்கூடாது.

இது ஆறு கேள்விகளுக்கு பதில் சொல்லுது:

| கேள்வி | Example பதில் |
| --- | --- |
| Product-க்கு run time-லயும் மேம்படுத்தவும் **என்ன data** வேணும்? | Run time-ல policy documents; evaluation-க்கு real customer questions, expert answers |
| அது **எங்க இருந்து** வருது, **யாருக்கு சொந்தம்**? | Documents policy team-க்கு சொந்தம்; question log support-க்கு சொந்தம் |
| இந்த purpose-க்கு அதை use பண்ண **நமக்கு அனுமதி இருக்கா**? | Chats பதில்களை மேம்படுத்த உதவும்னு customers-க்கு சொல்லப்பட்டிருக்கு, அவங்க opt out பண்ணலாம் |
| அது **எவ்வளவு நல்லது**, எப்படி current-ஆ வச்சுக்கிறோம்? | ஒவ்வொரு quarter-உம் documents review; duplicates நீக்கம் |
| அதை வச்சு product-ஐ **எப்படி evaluate பண்றோம்**? | ஒவ்வொரு release-க்கு முன்னாடியும் run பண்ற 150 questions-ஓட golden set |
| Use பண்றது **எப்படி better data-வை உருவாக்குது**? | Thumbs down, காரணம்; வாரம் ஒரு தடவை review; fixes golden set-ல சேர்றது |

Lesson முடியும்போது, ஒரு privacy officer-உம் ஒரு engineer-உம் ரெண்டு பேருமே ஒத்துக்கக்கூடிய ஒரு one-page data plan எழுத முடியும்.

## இது எப்படி work ஆகுது

### Run-time data

Documents-ல இருந்து பதில் சொல்ற product-க்கு, எந்த document collections-ஐ search பண்ணும், அவற்றை எப்படி fresh-ஆ வச்சிருக்கோம், யார் எதை பார்க்கலாம்னு முடிவு பண்ணுங்க. Personalisation-க்கு, consent-ஓட, எந்த user data use ஆகும்னு முடிவு பண்ணுங்க. Run-time data இல்லாம போறது அல்லது பழசா இருக்குறது, பல சமயம் model-ஐ விட அதிகமா தப்பான பதில்களை கொடுக்குது.

### Evaluation data

**Golden set**-னா domain experts-ஓட சேர்ந்து உருவாக்குன, expected outputs அல்லது quality judgements இருக்குற realistic inputs-ஓட collection. Real users-ட இருந்து 50 முதல் 100 cases-ல ஆரம்பிங்க, கற்பனையா உருவாக்குனதை இல்ல. நீங்க கண்டுபிடிக்குற ஒவ்வொரு முக்கியமான failure-ஓடவும் அதை வளர்க்குங்க. Golden set தான் product-ஓட quality contract: அது இல்லன்னா, "இப்போ better-ஆ இருக்கா?"ங்குறது வெறும் அபிப்பிராயம் தான்.

### Feedback data

முதல் நாள்ல இருந்தே feedback capture பண்ற மாதிரி product-ஐ design பண்ணுங்க:

- ஒரு சின்ன காரணத்தோட thumbs up, down;
- drafts-ல users பண்ற edits, அவை என்ன தப்புன்னு சரியா காட்டும்;
- human reviewers பண்ற overrides;
- ஒரு ஆளுக்கு போற escalations.

யாராவது ஒரு schedule-ல review பண்ணி, அதை fixes-ஆவும் புது golden-set cases-ஆவும் மாத்தினா தான் feedback useful.

### Labelling

சில improvements-க்கு labelled data வேணும்: சரியான categories, சரியான extractions, சரியான answers. யார் label பண்றாங்க (domain experts, trained staff அல்லது ஒரு vendor), எந்த எழுதப்பட்ட guidelines-ஓட, label quality-ஐ எப்படி check பண்றோம் (உதாரணம்: ஒரு sample-ஐ ரெண்டு பேர் label பண்ணி ஒப்பிடுறது) என்பதை முடிவு பண்ணுங்க.

### Permission, privacy

இந்தியாவோட **DPDP Act**, இதே மாதிரி laws-படி, personal data மக்களுக்கு சொல்லப்பட்டு அவங்க ஒத்துக்கிட்ட purposes-க்கு மட்டும், அல்லது வேற lawful ground-ல தான் use பண்ணலாம். ஒரு model-ஐ மேம்படுத்த customer chats-ஐ use பண்ண, தெளிவான notice-உம் consent-உம் தேவைப்படலாம். Business clients-ஓட contracts, அவங்க data-வை அவங்களோட சொந்த service-க்கு தவிர வேற எதுக்கும் use பண்றதை தடுக்கலாம். இதையெல்லாம் collect பண்றதுக்கு **முன்னாடியே** முடிவு பண்ணுங்க.

### Quality, coverage

| Check | கேள்வி | புறக்கணிச்சா risk |
| --- | --- | --- |
| Coverage | நம்மகிட்ட எல்லா user types, மொழிகள், regions-உம் இருக்கா? | விடுபட்ட குழுக்களுக்கு failures, bias |
| Freshness | Data current-ஆ இருக்கா? | பழைய பதில்கள் |
| Duplicates | ஒரே விஷயம் பல தடவை எண்ணப்படுதா? | Results திரிபடும் |
| Errors | Labels, records சரியா இருக்கா? | Product தப்புகளை கத்துக்கும் |

Data-வுல இருக்குற bias product-ல bias ஆகும்.

### Ownership, governance

ஒவ்வொரு dataset-க்கும் ஒரு owner-ஐ பெயர் சொல்லுங்க, எவ்வளவு காலம் வச்சிருப்போம், எப்போ delete பண்ணுவோம்னு define பண்ணுங்க, அது எங்க இருந்து வந்ததுன்னு record பண்ணுங்க. Owner இல்லாத data சத்தமில்லாம பழசாகிடும்.

### Flywheel

```flow
dir: LR
title: Flywheel
அதிக usage -> அதிக feedback -> Better data -> Fixes, புது golden cases -> Better product -> அதிக usage
```

நல்ல products usage-ஐ, product-ஐ மேம்படுத்துற data-வா மாத்தும். Feedback capture ஆகி, அனுமதிக்கப்பட்டு, உண்மையிலயே use பண்ணப்பட்டா தான் flywheel சுத்தும்.

## ஒரு worked example

Chennai-ல ஒரு agri-tech startup, Tamil, English ரெண்டுலயும் farmers-ஓட crop கேள்விகளுக்கு பதில் சொல்ற ஒரு voice assistant-ஐ build பண்ணுது. Product manager Lakshmi data plan எழுதுறாங்க.

| Data | Source | Owner | Permission | எவ்வளவு காலம் வச்சிருப்பாங்க |
| --- | --- | --- | --- | --- |
| Run-time: crop advisories | Agricultural university advisories, state agriculture department guidance; ஒவ்வொரு season-உம் update | Content lead | Public sources | Replace ஆகுற வரைக்கும் |
| Run-time: weather, prices | Weather, market price feeds | Engineering | Licensed feeds | Rolling 30 நாள் |
| Evaluation: golden set | Field staff-ஓட சேகரிச்ச 200 real farmer questions, அஞ்சு crops, மூணு districts முழுக்க; ரெண்டு agronomists answers-ஐ check பண்ணாங்க | Lakshmi | Collect பண்ணும்போது farmers ஒத்துக்கிட்டாங்க | தொடர்ந்து |
| Feedback | ஒவ்வொரு answer-க்கு அப்புறமும் "Did this help?" voice prompt, ஒரு callback option, field staff-ஓட வாராந்திர corrections | Support lead | முதல் use-ல Tamil-ல notice, opt-out-ஓட | Recordings 90 நாள், farmer வேற மாதிரி ஒத்துக்கிட்டா தவிர |

**ஒரு coverage gap.** முதல் 200 questions-ஐ review பண்ணும்போது, target districts-ல field work-ல பெரும்பகுதியை பண்ற பெண் farmers-கிட்ட இருந்து கிட்டத்தட்ட எதுவுமே வரல. Field staff பெண்களோட self-help groups-ஓட ரெண்டு sessions நடத்தி 60 questions சேர்க்கிறாங்க; அதுல நிறைய, முதல் sample தவறவிட்ட crops, pests பத்தினது.

**ஆறு மாசம் கழிச்சு:**

| Measure | Launch-ல | ஆறு மாசத்துல |
| --- | --- | --- |
| Golden set size | 200 questions | 650 questions |
| Accuracy reporting | Overall மட்டும் | Crop வாரியா, district வாரியா, மாசா மாசம் |
| மிக பொதுவான failure | Local dialect-ல pest பெயர்கள் | Feedback-ல இருந்து உருவாக்குன glossary-ஆல fix ஆச்சு |

அந்த glossary flywheel-ல இருந்தே நேரடியா வந்தது: farmers "did not help" அழுத்துனாங்க, field staff recordings-ஐ கேட்டாங்க, team local பெயர்களை சேர்த்துச்சு.

## பொதுவா பண்ற தப்புகள்

- **கையில இருக்குற எந்த data-வையும் use பண்ணலாம்னு நினைக்கிறது.** முதல்ல consent, law, contracts-ஐ check பண்ணுங்க.
- **Evaluation set இல்லாதது.** அது இல்லன்னா quality வெறும் அபிப்பிராயம் ஆயிடும், ஒவ்வொரு change-உம் சூதாட்டம்.
- **யாருமே படிக்காத feedback buttons.** Button மட்டும் இல்ல, வாராந்திர review routine-ஐயும் build பண்ணுங்க.
- **Coverage-ஐ புறக்கணிக்கிறது.** விடுபட்ட குழுக்களும் மொழிகளும் failures-ஆவும் bias-ஆவும் மாறும்.
- **Owner இல்லாதது.** Owner இல்லாத data பழசாகும், யாருக்கும் தெரியாது.
- **Test questions-ஐ கற்பனை பண்றது.** Team கற்பனை பண்றதை விட real user questions messy-ஆவும் அதிக useful-ஆவும் இருக்கும்.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற data collection, evaluation பத்தின PAIR guidebook chapter-ஐயும், AI products-ஐ மேம்படுத்துறது பத்தின Hamel Husain-ஓட field guide-ஐயும் படிங்க.

1. **Data-வை list பண்ணுங்க.** ஒரு AI product idea-க்கு, run-time, evaluation, feedback data-வை, ஒவ்வொண்ணோட source, owner-ஓட list பண்ணுங்க.
2. **Permission.** ஒவ்வொண்ணுக்கும், permission அடிப்படையையும், எவ்வளவு காலம் வச்சிருப்பீங்கன்னும் எழுதுங்க.
3. **Golden set.** அந்த domain தெரிஞ்ச ஒருத்தரோட சேர்ந்து 30 evaluation cases-ஐ draft பண்ணி, ஒரு coverage gap-ஐ note பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு privacy officer-உம் ஒரு engineer-உம் ரெண்டு பேருமே ஒத்துக்கக்கூடிய ஒரு one-page data plan-ஐ present பண்ண முடியும்.
