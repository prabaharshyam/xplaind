## இது என்ன

ஒரு deployment-ஐ பாதுகாப்பா operate பண்ண வைக்கிற மூணு பழக்கங்கள்:

- **Separate environments.** Build பண்ண development, production மாதிரி settings-ல test பண்ண staging, real users-க்கான production. ஒவ்வொண்ணுக்கும் தனி database, keys, settings.
- **Secrets management.** Passwords, API keys, tokens ஒரு secret store-ல இருக்கும். Run time-ல app-க்கு வரும். Code, images, logs, chat எதுலயும் வரக்கூடாது.
- **Infrastructure as code (IaC).** Servers, databases, networks, permissions எல்லாம் files-ல எழுதப்படும், code மாதிரி review ஆகும், Terraform மாதிரி tool மூலமா apply ஆகும். Console-ல click பண்ணி உருவாக்குறது இல்லை.

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | own database, own model key, 1 instance
Apply -> Staging | masked data, own model key, 1 instance
Apply -> Production | real data, own model key with a spend limit, 3 instances
The same container image -> Development
The same container image -> Staging
The same container image -> Production
```

ஒவ்வொரு environment-உம் settings-ஐ environment-ல இருந்து, secrets-ஐ vault-ல இருந்து எடுத்துக்கும்.

இந்த lesson-ல Chandigarh-ல ஒரு lending company, அவசர அவசரமா பண்ண pilot-ஐ production-க்கு தயார் பண்றதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Config environment-ல.** எல்லா இடத்துலயும் ஒரே image ஓடும்; settings மட்டும் வேற. அதை environment variables-ல இருந்து படிங்க (`DATABASE_URL`, `MODEL_NAME`, `LOG_LEVEL`), start-up-ல ஒரு settings model வச்சு validate பண்ணுங்க. அப்போ ஒரு value இல்லைன்னா, அதிகாலை 2 மணிக்கு முதல் real request-ல இல்லாம, boot ஆகும்போதே சத்தமா fail ஆகும்.

**Environments-க்கு நடுவுல என்ன வேற.** தனி databases (masked இல்லன்னா staging-ஐ production data-வுக்கு ஒருபோதும் point பண்ணாதீங்க), தனி spend limits உள்ள தனி model API keys, production-க்கு வெளியே குறைவான instances, production-க்கு இன்னும் கடுமையான access.

**Secret stores.** Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) அல்லது HashiCorp Vault மாதிரி tools secrets-ஐ வச்சிருக்கும், ஒவ்வொண்ணையும் யார் படிக்கலாம்னு control பண்ணும், ஒவ்வொரு access-ஐயும் log பண்ணும். App அதை start-up-ல தன்னோட service identity வழியா படிக்கும். Secrets-ஐ schedule-ஆ rotate பண்ணுங்க; யாராவது வேலையை விட்டு போனாலோ leak ஆனதா சந்தேகம் வந்தாலோ உடனே rotate பண்ணுங்க. Keys repository-க்கு போறதுக்கு முன்னாடியே பிடிக்க CI-ல ஒரு secret scanner ஓட்டுங்க.

**Terraform.** Resources-ஐ விவரிக்கிற HCL files-ஐ எழுதுவீங்க:

```hcl
resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = "centralindia"
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false
}
```

`terraform plan` என்ன மாறப்போகுதுன்னு சரியா காட்டும்; reviewer pull request-ல அந்த plan-ஐ படிப்பாங்க; `terraform apply` அதை நடத்தும். Terraform தான் manage பண்றதை ஒரு **state** file-ல record பண்ணும். அதை remote-ஆ (locking இருக்குற storage bucket-ல) store பண்ணணும், laptop-ல ஒருபோதும் கூடாது. Sensitive values இருக்கலாம்ங்கிறதால அதை பாதுகாக்கணும். ஒரே set files-ஐ வச்சு ஒவ்வொரு environment-க்கும் ஒரு variable கொடுத்தா, staging-உம் production-உம் ஒரே வடிவத்துல இருக்கும்.

**ஒவ்வொரு வகை value-வும் எங்க இருக்கணும்:**

| Value | Example | எங்க இருக்கும் |
| --- | --- | --- |
| Secret இல்லாத setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, ஒவ்வொரு environment-க்கும் set பண்ணி |
| Secret | Database password, model API key | Secret store, app-ஓட identity வழியா படிக்கணும் |
| Infrastructure | Database size, network rules | Git-ல இருக்குற Terraform files |
| Infrastructure state | Terraform எந்த resources-ஐ manage பண்ணுது | Remote, locked, access-controlled storage |
| Test data | Masked customer records | Staging database-ல மட்டும் |

**Review loop.** Infrastructure மாற்றம் Terraform files-ஐ edit பண்ற ஒரு pull request-ஆ ஆரம்பிக்கும். CI `terraform plan` ஓட்டி, "1 to add, 0 to change, 0 to destroy" மாதிரி output-ஐ post பண்ணும். Reviewer code-ஐ மட்டும் இல்லாம plan-ஐயும் படிக்கணும், ஏன்னா உண்மையில என்ன நடக்கும்னு plan தான் காட்டும். Approve ஆன பிறகு, தன்னோட சொந்த identity உள்ள ஒரு pipeline `terraform apply` ஓட்டும். சாதாரண மாற்றங்களுக்கு யாருக்கும் production console access தேவையில்லை. அங்க தப்பு பண்ணக்கூடியவங்க எண்ணிக்கை குறையும்.

**Code-ல validate பண்ண settings.** `pydantic-settings` environment variables-ஐ படிச்சு, உடனே fail ஆகும்:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_url: SecretStr
    model_api_key: SecretStr
    model_name: str = "claude-sonnet-5-5"            # check the docs for current names
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()        # raises a clear error listing every missing or invalid value
```

`SecretStr` secrets-ஐ logs, error messages-ல இருந்து தள்ளி வைக்கும்: அதை print பண்ணா `**********` தான் வரும்.

**Locking உள்ள remote state.** ஒவ்வொரு Terraform project-உம் ஒரு backend-ஓட ஆரம்பிக்கும். அப்போ state share ஆகும், ரெண்டு பேர் ஒரே நேரத்துல apply பண்ண முடியாது:

```hcl
terraform {
  required_version = ">= 1.6"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}
```

ஒவ்வொரு environment-க்கும் ஒரு state file வைங்க (வேற `key`), `env/staging.tfvars`, `env/prod.tfvars` மாதிரி தனி variable files-உம் வைங்க.

**Terraform-ல secrets-ஐ store பண்ணாம secrets.** Vault-ஐ உருவாக்கவும் app-ஓட identity-க்கு access கொடுக்கவும் மட்டும் Terraform-ஐ விடுங்க. Secret values-ஐ vault வழியாவே உள்ள போடுங்க. அப்போ அவை code-லயும் state-லயும் வராது:

```hcl
resource "azurerm_key_vault" "kv" {
  name                      = "claims-${var.env}-kv"
  location                  = "centralindia"
  resource_group_name       = azurerm_resource_group.main.name
  tenant_id                 = data.azurerm_client_config.current.tenant_id
  sku_name                  = "standard"
  enable_rbac_authorization = true
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

**Schedule-ல drift-ஐ detect பண்ணுங்க.** சில நேரம் மக்கள் console-ல ஏதாவது மாத்துவாங்க. ஒரு nightly job அதை கண்டுபிடிக்கும்:

```bash
terraform plan -var-file=env/prod.tfvars -detailed-exitcode -lock=false > plan.txt
case $? in
  0) echo "no drift" ;;
  2) echo "DRIFT: production differs from code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

**Code-ஐ scan பண்ணுங்க.** `tflint`, Checkov மாதிரி tools public storage, திறந்த firewall rules, இல்லாத encryption-ஐ pull requests-லயே காட்டும், எதுவும் apply ஆகுறதுக்கு முன்னாடியே.

**Browser-லயே try பண்ணுங்க.** Start-up-ல check பண்ற settings உடனே, தெளிவா fail ஆகும். ஒரு value-வை எடுத்துட்டு ஓட்டிப் பாருங்க.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    database_url: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "database_url": "postgresql://app:secret@db/app", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.daily_budget_inr, s.database_url)     # the secret prints as stars
except ValidationError as err:
    print("start-up stopped:", [e["loc"][0] for e in err.errors()])
```

## ஒரு example

Chandigarh-ல ஒரு lending company-ஓட pilot அவசரமா build ஆனது. Testing-க்கும் real data-வுக்கும் ஒரே database, மாசங்களுக்கு முன்னாடி commit ஆன `.env` file-ல model key, console-ல கையால உருவாக்கின resources.

Production-க்கு போறதுக்கு முன்னாடி நீங்க பண்றது:

1. Leak ஆன key-ஐ rotate பண்ணி, CI-ல ஒரு secret scanner சேருங்க. History-ல இன்னும் ரெண்டு பழைய keys கிடைக்குது; ரெண்டையும் rotate பண்றீங்க.
2. Network, database, storage, container app, Key Vault-க்கு Terraform எழுதுறீங்க, `env` ஒரு variable-ஆ. `terraform apply` ஒரு clean staging-ஐ build பண்ணுது; review ஆன plan production-ஐ build பண்ணுது.
3. எல்லா secrets-ஐயும் Key Vault-க்கு மாத்துறீங்க; app அதை தன்னோட managed identity வழியா படிக்குது. Staging, production-க்கு தனி model keys, தனி மாசாந்திர limits.
4. Staging-ல போன மாசத்து applications-ஓட masked copies-ஐ load பண்றீங்க: பெயர்கள், PAN, phone numbers மாத்தப்பட்டிருக்கு.

Client-ஓட auditor "production database password-ஐ யாரெல்லாம் படிக்க முடியும்?"ன்னு கேக்கும்போது, Key Vault access policy-யையும் அதோட access log-ஐயும் காட்டி பதில் சொல்றீங்க. Region outage drill நடக்கும்போது, அதே Terraform-ஐ வச்சு team staging-ஐ இன்னொரு region-ல 40 நிமிஷத்துல திரும்ப build பண்ணுது.

| Auditor-ஓட கேள்வி | முன்னாடி பதில் | பின்னாடி பதில் |
| --- | --- | --- |
| Secrets எங்க store ஆகுது? | ".env file-ல" | Key Vault, access log-ஓட |
| Production-ஐ யார் மாத்தலாம்? | பல பேர், console வழியா | Review-க்கு அப்புறம், deployment pipeline |
| System-ஐ திரும்ப build பண்ண முடியுமா? | தெளிவா தெரியல | முடியும், Terraform-ல இருந்து, 40 நிமிஷத்துல |
| Test data real-ஆ? | ஆமா | இல்லை, masked copies |

## பொதுவா பண்ற தப்புகள்

- **Production data-வுக்கு எதிரா test பண்றது.** ஒரு மோசமான script போதும், real customers பாதிக்கப்படுவாங்க. Separate பண்ணுங்க, test data-வை mask பண்ணுங்க.
- **Secrets-ஐ Git-ல போடுறது, கொஞ்ச நேரமா இருந்தாலும் சரி.** History அதை வச்சிருக்கும். எப்பவாவது commit ஆன எந்த key-ஐயும் rotate பண்ணுங்க.
- **Laptop-ல Terraform state.** அது தொலையும், பழசாகும், secrets-உம் வச்சிருக்கலாம். Remote, locked state use பண்ணுங்க.
- **Terraform-கூடவே console-ல மாற்றங்கள்.** அடுத்த apply அவற்றை revert பண்ணும் அல்லது conflict ஆகும். Code-ஐ மாத்துங்க.
- **ஒவ்வொரு environment-க்கும் வேற வடிவம்.** Production-ல இருக்குற private network staging-ல இல்லைன்னா, staging tests பெருசா எதையும் நிரூபிக்காது.
- **Terraform files-ல secret values-ஐ எழுதுறது**, அது state-லயும் போய் சேரும்.
- **எல்லா environments-க்கும் ஒரே state file**, அதனால staging மாற்றம் production-ஐ தொடலாம்.
- **யாரும் record பண்ணாத console மாற்றங்கள்**, மாசங்கள் கழிச்சு drift-ஆ கண்டுபிடிக்கப்படும்.

## Terraform தேவைக்கு அதிகமா இருக்கும் நேரங்கள்

- **ஒரே சின்ன service**, infrastructure-ஐ உங்களுக்காக manage பண்ற platform-ல.
- **குறுகிய காலம் வாழும் prototype**, அடுத்த மாசம் delete பண்ணப்போறது.
- **சொந்த infrastructure team, tool இருக்குற client** (Bicep, CloudFormation, Pulumi மாதிரி): அவங்களுடையதை use பண்ணுங்க.

Environment variables, validate பண்ண settings, ஒரு secret store இவை மூணும் சின்ன project-லயும் இருக்குறது நல்லது.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு environment-க்கும் remote, locked state** வைங்க, access restrict பண்ணுங்க.
- **Pull requests-ல plan பண்ணுங்க**, review-க்கு அப்புறம் CI-ல இருந்து மட்டும் apply பண்ணுங்க.
- **Production-ல nightly drift checks** ஓட்டுங்க.
- **CI-ல Terraform-ஐ scan பண்ணுங்க**, risky settings-க்காக.
- **Start-up-ல settings-ஐ validate பண்ணுங்க**, secrets-ஐ `SecretStr`-ஆ, app-ஓட identity வழியா படிக்கணும்.

## Practice பண்ணுங்க

நீங்க எடுத்த cloud-க்கான Terraform getting-started tutorials-ஐ follow பண்ணி, config பத்தின Twelve-Factor page-ஐ படிங்க.

1. `env = "staging"`-க்கு ஒரு storage bucket-ஐயும் ஒரு சின்ன managed database-ஐயும் உருவாக்குற Terraform எழுதுங்க, database public-ஆ reach பண்ண முடியாத மாதிரி. Apply பண்ணுங்க, plan-ஐ படிங்க, அப்புறம் destroy பண்ணுங்க.
2. உங்க app-ஓட settings-ஐ environment variables-ல இருந்து படிக்குற validate பண்ண settings model-க்கு மாத்துங்க. ஒண்ணு இல்லைன்னா start-up தெளிவா fail ஆகணும்.
3. ஒரு secret-ஐ உங்க cloud-ஓட secret manager-ல store பண்ணி, app அதை identity வழியா படிக்க வைங்க.
4. Cloud console-ல ஒரு setting-ஐ கையால மாத்துங்க, அப்புறம் drift check ஓட்டி அது வித்தியாசத்தை report பண்றதை confirm பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க staging environment-ஐ code-ல இருந்து திரும்ப build பண்ண முடியும், உங்க repository-ல எங்கயும் ஒரு secret கூட இல்லைன்னு காட்ட முடியும்.
