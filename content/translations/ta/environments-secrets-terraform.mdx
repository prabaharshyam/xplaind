## இது என்ன

ஒரு deployment-ஐ safe-ஆ operate பண்ண உதவுற மூணு பழக்கங்கள்:

- **தனித்தனி environments.** Build பண்ண development, production மாதிரியான settings-ல test பண்ண staging, real users-க்கு production. ஒவ்வொண்ணுக்கும் தனி database, keys, settings.
- **Secrets management.** Passwords, API keys, tokens ஒரு secret store-ல இருக்கும், run time-ல app-க்கு வரும்; code, images, logs, chat, Terraform state-ல எப்பவுமே வராது.
- **Infrastructure as code (IaC).** Servers, databases, networks, permissions-ஐ ஒரு console-ல click பண்ணி சேர்க்காம, files-ல describe பண்ணி, code மாதிரியே review பண்ணி, Terraform மாதிரியான ஒரு tool மூலமா apply பண்றது.

```flow
Terraform files, review ஆனவை -> Plan -> Apply
Apply -> Development | தனி database, தனி model key, 1 instance
Apply -> Staging | masked data, தனி model key, 1 instance
Apply -> Production | real data, spend limit இருக்குற தனி model key, 3 instances
அதே container image -> Development
அதே container image -> Staging
அதே container image -> Production
```

ஒவ்வொரு environment-உம் அதோட settings-ஐ environment variables-ல இருந்தும், secrets-ஐ vault-ல இருந்தும் எடுத்துக்கும். Values மட்டும் தான் மாறும்; code-உம் image-உம் ஒண்ணு தான். அது தான் முக்கியம்: staging pass ஆனா, production-உம் pass ஆகணும்.

இந்த lesson-ல, Chandigarh-ல இருக்குற ஒரு lending company, அவசரமா பண்ண ஒரு pilot-ஐ Azure-ல production-க்கு தயார் பண்றதை follow பண்றோம். இதே ideas AWS-க்கும் Google Cloud-க்கும் பொருந்தும், resource names மட்டும் வேற.

## இது எப்படி வேலை செய்யுது

### Config, environment-ல

அதே image எல்லா இடத்துலயும் ஓடுது; settings மட்டும் தான் வேற. அவற்றை environment variables-ல இருந்து (`DATABASE_HOST`, `MODEL_NAME`, `LOG_LEVEL`) read பண்ணி, start-up-ல ஒரு settings model மூலமா validate பண்ணுங்க. அப்போ ஒரு value இல்லன்னா, அது ராத்திரி 2 மணிக்கு முதல் real request-ல இல்லாம, deploy நடக்கும்போதே boot-ல சத்தமா fail ஆகும்.

### Environments-க்கு நடுவுல என்ன மாறும்

| Value | உதாரணம் | எங்க இருக்கும் |
| --- | --- | --- |
| Secret இல்லாத setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, ஒவ்வொரு environment-க்கும் தனியா set பண்றது |
| Secret | Model API key, webhook signing key | Secret store, app-ஓட identity மூலமா read பண்றது |
| Database access | Production database | Managed identity sign-in, அதனால password-ஏ கிடையாது |
| Infrastructure | Database size, network rules | Git-ல Terraform files |
| Infrastructure state | Terraform எந்த resources-ஐ manage பண்ணுது | Remote, locked storage, ஒவ்வொரு environment-க்கும் ஒரு state |
| Test data | Masked customer records | Staging database-ல மட்டும் |

Production-க்கு இன்னும் அதிகமான instances, provider கிட்ட monthly spend limit set பண்ண தனி model key கிடைக்கும், ரொம்பவே குறைவான ஆட்கள் தான் அதை தொட முடியும்.

### Secret stores-உம் rotation-உம்

Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) அல்லது HashiCorp Vault மாதிரியான tools secrets-ஐ வச்சிருக்கும், ஒவ்வொண்ணையும் யார் read பண்ணலாம்னு control பண்ணும், ஒவ்வொரு read-ஐயும் log பண்ண முடியும். Azure-ல, vault-ஓட diagnostic settings-ஐ on பண்ணா தான் reads log ஆகும், அதனால முதல் நாளே அதை பண்ணுங்க; ஒரு auditor கண்டிப்பா கேப்பாரு.

App அதோட **managed identity** மூலமா secrets-ஐ read பண்ணும்: இது ஓடிக்கிட்டு இருக்குற app-க்கு Azure குடுக்குற ஒரு identity, அதனால vault-ஐ reach பண்ண app-க்கு password தேவையில்ல. Secrets-ஐ ஒரு schedule-படி rotate பண்ணுங்க, யாராவது விட்டுப் போனாலோ leak ஆனதா சந்தேகம் வந்தாலோ உடனே rotate பண்ணுங்க.

Rotation-ல ஒரு catch இருக்கு. ஒரு secret-ஐ start-up-ல மட்டும் read பண்ற app, restart ஆகுற வரை பழைய value-ஐயே வச்சிருக்கும். மூணு patterns-ல ஒண்ணை தேர்ந்தெடுங்க: ஒவ்வொரு rotation-க்கு அப்புறமும் app-ஐ restart பண்றது, ஒரு timer-ல secrets-ஐ reload பண்றது, அல்லது ஒரு call authentication error-ஓட fail ஆனா ஒரு தடவை reload பண்றது. சில platforms, அதுல Azure Container Apps-உம் ஒண்ணு, ஒரு vault secret-ஓட latest version-ஐ உங்களுக்காக follow பண்ண முடியும்; அது app-ஐ எப்போ restart பண்ணும்னு தெரிஞ்சுக்க உங்க platform-ஓட docs-ஐ படிங்க. Keys repository-க்கு வரவே வராம இருக்க, CI-ல ஒரு secret scanner ஓட்டுங்க.

### Terraform: code, plan, apply, state

உங்களுக்கு வேண்டிய resources-ஐ describe பண்ணி, Terraform-ஓட configuration language-ஆன HCL-ல files எழுதுவீங்க. Region-உம் environment-உம் variables, அதனால அதே files எந்த environment-ஐயும் எங்க வேணும்னாலும் build பண்ணும்:

```hcl
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "location" {
  type    = string
  default = "centralindia"
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = var.location
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false

  authentication {
    active_directory_auth_enabled = true
    password_auth_enabled         = false
    tenant_id                     = data.azurerm_client_config.current.tenant_id
  }
}
```

`authentication` block passwords-ஐ off பண்ணுது: app அதோட managed identity மூலமா Postgres-ல sign in பண்ணுது, அதனால leak ஆகவோ rotate பண்ணவோ database password-ஏ கிடையாது.

`terraform plan` மூணு விஷயங்களை compare பண்ணும்: உங்க code, **state** file (Terraform manage பண்ற resources பத்தின அதோட record), real cloud. அப்புறம் எதை create, change அல்லது destroy பண்ணும்னு list பண்ணும். `terraform apply` அந்த changes-ஐ பண்ணி state-ஐ update பண்ணும்.

### Remote state, ஒவ்வொரு environment-க்கும் ஒண்ணு

ஒவ்வொரு project-உம் ஒரு backend-ஓட ஆரம்பிக்கும், அப்போ state share ஆகும், ஒரு apply நடக்கும்போது lock ஆகும், laptops-ல இருக்காது:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 5.15" }
  }
}
```

இந்த lesson-ல இருக்குற code-ஐ Terraform 1.17.2, azurerm provider 5.15.0-ல `terraform validate` வச்சு check பண்ணோம் (November 2026). நீங்க test பண்ண versions-ஐ pin பண்ணுங்க. Provider upgrades arguments-ஓட பேரை மாத்தும். azurerm 5.x-ல Key Vault argument `enable_rbac_authorization` போயிடுச்சு, `rbac_authorization_enabled` required, அதனால பழைய copy பண்ண code validate ஆகாது.

Environments-ஐ எப்படி பிரிக்கணும்? இந்த rule-ஐ use பண்ணுங்க:

- **ஒவ்வொரு environment-க்கும் ஒரு state, அதுக்குன்னு தனி key, production-க்கு தனி access.** அப்போ staging-ல நடக்குற ஒரு தப்பு production-ஐ தொட முடியாது.
- **Share பண்ற code ஒரு module-ல.** Module-னா Terraform-ஓட ஒரு folder, ஒவ்வொரு environment-உம் அதை தன்னோட values-ஓட call பண்ணும், அதனால staging-உம் production-உம் ஒரே shape-ல இருக்கும்.
- **CLI workspaces** ஒரே backend-ல, அதே credentials-ஓட, பல states-ஐ வச்சிருக்கும். Environments-க்கு வேற வேற credentials அல்லது access controls தேவைப்பட்டா அவை பொருந்தாதுன்னு HashiCorp-ஓட docs சொல்லுது. ஒவ்வொரு feature branch-க்கும் ஒண்ணு மாதிரியான குறுகிய காலம் இருக்குற copies-க்கு அவற்றை use பண்ணுங்க, production-ஐ பிரிக்க இல்ல.

### Secrets-ஐ code-லயும் state-லயும் வராம பாத்துக்குறது

State ஒவ்வொரு resource-ஓட ஒவ்வொரு attribute-ஐயும் plain text-ல store பண்ணும், Terraform வச்சு நீங்க generate பண்ற எந்த password-ஐயும் சேர்த்து. ஒரு value-ஐ `sensitive`-னு mark பண்ணா அது screen-ல இருந்து மட்டும் மறையும்; state-ல இன்னும் இருக்கும். மூணு பாதுகாப்புகள், best முதல்ல:

1. **Secret-ஏ இல்லாம இருக்குறது.** மேல database-ல பண்ண மாதிரி, managed identity sign-in.
2. **Write-only arguments** (Terraform 1.11 மற்றும் அதுக்கு அப்புறம்). Provider value-ஐ வாங்கிக்கும், ஆனா Terraform அதை எப்பவுமே store பண்ணாது. உதாரணமா, azurerm-ல Postgres server-ல `administrator_password_wo`, Key Vault secrets-ல `value_wo` இருக்கு, ஒவ்வொண்ணுக்கும் ஒரு `_wo_version` number, rotate பண்ண அதை ஏத்துவீங்க. Terraform 1.10 **ephemeral resources** கொண்டு வந்துச்சு, அவை ஒரு run-க்கு மட்டும் vault-ல இருந்து ஒரு secret-ஐ save பண்ணாம read பண்ணும்.
3. **Value-ஐ Terraform-க்கு வெளியே போடுறது.** Terraform vault-ஐயும் permissions-ஐயும் create பண்ணும்; ஒரு ஆளோ ஒரு pipeline-ஓ secret value-ஐ சேர்க்கும்.

```hcl
resource "azurerm_key_vault" "kv" {
  name                       = "claims-${var.env}-kv"
  location                   = var.location
  resource_group_name        = azurerm_resource_group.main.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = var.env == "prod"
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

இந்த role assignment, app-ஐ secret values-ஐ read பண்ண மட்டும் அனுமதிக்கும், வேற எதுவும் இல்ல: அதால அவற்றை change பண்ணவோ delete பண்ணவோ முடியாது.

### Code-ல validate பண்ண settings

`pydantic-settings` environment variables-ஐ read பண்ணி சீக்கிரமே fail ஆகும்:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_host: str
    model_api_key: SecretStr
    model_name: str                  # required: no default, so a missing value stops start-up
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()    # raises one clear error listing every missing or invalid value
```

`model_name`-க்கு வேணும்னே default இல்ல. ஒரு default model name, நீங்க பிடிக்க நினைக்குற அதே bug-ஐ மறைச்சுடும், model names-உம் அடிக்கடி மாறும். `SecretStr` secrets-ஐ logs-லயும் error messages-லயும் வராம பாத்துக்கும்: அதை print பண்ணா `**********` தான் காட்டும். `.env` file development-க்கு மட்டும் தான், அது `.gitignore`-ல இருக்கணும்.

### யார் apply பண்ணலாம்: review loop

Infrastructure-ல ஒரு change, Terraform files-ஐ edit பண்ற ஒரு pull request-ஆ ஆரம்பிக்கும்:

1. CI `terraform fmt -check`, `terraform validate`, அப்புறம் `tflint`, Checkov மாதிரியான scanners-ஐ ஓட்டும்; அவை public storage, open firewall rules, missing encryption-ஐ flag பண்ணும்.
2. CI `terraform plan -out=plan.bin` ஓட்டி, "1 to add, 0 to change, 0 to destroy" மாதிரி ஒரு summary-ஐ post பண்ணும்.
3. ஒரு reviewer code-ஐ மட்டும் இல்லாம plan-ஐ படிப்பாரு, ஏன்னா ஒரு line edit, ஒரு database-ஐ destroy பண்ணி recreate பண்ண Terraform-ஐ கட்டாயப்படுத்தலாம்.
4. Approval-க்கு அப்புறம், ஒரு pipeline save பண்ண அதே plan-ஐ apply பண்ணும். Production-க்கு, ஒரு required approval step (உதாரணமா ஒரு protected GitHub environment) சேருங்க, கடுமையான rules தேவைன்னா Open Policy Agent மாதிரியான ஒரு policy check-ஐயும் சேருங்க.

Pipeline **OpenID Connect (OIDC)** மூலமா Azure-ல sign in பண்ணும்: GitHub Actions ஒரு குறுகிய கால token வச்சு தான் யார்னு நிரூபிக்கும், அதனால நீண்ட காலம் இருக்குற எந்த cloud password-உம் CI settings-ல இருக்காது. Staging pipeline-க்கு staging-ல மட்டும் rights குடுங்க, production pipeline-க்கு production-ல மட்டும். அப்போ production-க்கு யாருக்கும் வழக்கமான console access தேவைப்படாது, யாரும் ஒரு laptop-ல இருந்து apply ஓட்ட மாட்டாங்க.

### Drift: plan எதை பாக்கும், எதை பாக்காது

ஒரு incident நடக்கும்போது மக்கள் இன்னும் console-ல விஷயங்களை மாத்துவாங்க. ஒரு nightly job production-ஐ code கூட compare பண்ணும்:

```bash
terraform plan -var-file=env/prod.tfvars -input=false -lock=false -detailed-exitcode > plan.txt
case $? in
  0) echo "no changes" ;;
  2) echo "DIFFERENCE: production does not match the code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

Exit code 2-ஐ கவனமா படிங்க. அதுக்கு அர்த்தம் "plan ஒரு difference-ஐ கண்டுபிடிச்சுது". அது drift-ஆ இருக்கலாம் (யாரோ ஒரு managed resource-ஐ கையால மாத்தியிருக்காங்க), இல்லன்னா merge ஆன, ஆனா apply ஆகாத code-ஆ இருக்கலாம். எது-ன்னு plan text சொல்லும். Drift-ஐ மட்டும் பாக்க, `-refresh-only` சேருங்க.

பெரிய blind spot: plan ஏற்கனவே state-ல இருக்குற resources-ஐ மட்டும் தான் check பண்ணும். ஒரு தனி resource-ஆ கையால create பண்ண firewall rule தெரியவே தெரியாது; job green-ஆவே இருக்கும். அவற்றை cloud activity-log alerts அல்லது policies வச்சு பிடிங்க, அப்புறம் அந்த resource-ஐ delete பண்ணுங்க, அல்லது ஒரு import block வச்சு Terraform-க்கு கீழ கொண்டு வாங்க:

```hcl
import {
  to = azurerm_postgresql_flexible_server_firewall_rule.partner
  id = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/claims-prod-rg/providers/Microsoft.DBforPostgreSQL/flexibleServers/claims-prod-db/firewallRules/partner"
}

resource "azurerm_postgresql_flexible_server_firewall_rule" "partner" {
  name             = "partner"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "203.0.113.10"
  end_ip_address   = "203.0.113.10"
}
```

அடுத்த plan "1 to import"-னு காட்டும். `terraform plan -generate-config-out=generated.tf` உங்களுக்காக resource block-ஐ draft பண்ண முடியும்; அந்த flag இன்னும் experimental-னு தான் mark ஆகியிருக்கு, அதனால அது எழுதுறதை review பண்ணுங்க.

### உங்க browser-ல try பண்ணுங்க

Start-up-ல check பண்ற settings சீக்கிரமாவும் clear-ஆவும் fail ஆகும். Dictionary-ல இருந்து `model_name`-ஐ delete பண்ணி திரும்ப run பண்ணுங்க.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    model_name: str
    model_api_key: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "model_name": "example-model", "model_api_key": "sk-test-123", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.model_name, s.daily_budget_inr, s.model_api_key)   # the key prints as stars
except ValidationError as err:
    print("start-up stopped, missing or invalid:", [e["loc"][0] for e in err.errors()])
```

## ஒரு worked example

Chandigarh lending company-ஓட pilot அவசரமா build பண்ணது. Testing-க்கும் real data-க்கும் ஒரே database-ஐ use பண்ணுச்சு, model key மாசக்கணக்கா முன்னாடி commit ஆன ஒரு `.env` file-ல இருந்துச்சு, portal-ல கையால create பண்ண resources இருந்துச்சு.

Production-க்கு முன்னாடி, நீங்க:

1. Leak ஆன key-ஐ revoke பண்ணி rotate பண்ணுங்க, CI-ல ஒரு secret scanner சேருங்க. History-ல இன்னும் ரெண்டு பழைய keys-ஐ அது கண்டுபிடிக்குது; ரெண்டுமே rotate ஆகுது.
2. Network, database, storage, container app, Key Vault-க்கு Terraform எழுதுங்க, `env`, `location` variables-ஆ இருக்கட்டும். இருக்க வேண்டிய கையால செஞ்ச resources-ஐ import பண்ணுங்க, மிச்சத்தை delete பண்ணுங்க, plan-ல எந்த surprise-உம் இல்லன்னு confirm பண்ணுங்க.
3. ஒவ்வொரு secret-ஐயும் Key Vault-க்கு மாத்துங்க, database-ஐ managed identity sign-in-க்கு switch பண்ணுங்க, அப்போ password-ஏ இருக்காது. Staging-க்கும் production-க்கும் தனித்தனி monthly limits-ஓட தனித்தனி model keys.
4. போன மாச applications-ஓட masked copies-ஐ staging-ல load பண்ணுங்க: names, PAN, phone numbers மாத்தப்பட்டிருக்கும்.
5. CI-ல இருந்து மட்டும் apply பண்ணுங்க: ஒரு staging pipeline, ஒரு production pipeline, ஒவ்வொண்ணுக்கும் தனி OIDC identity, production-க்கு முன்னாடி ஒரு required approval.

Client-ஓட auditor "production model key-ஐ யார் read பண்ண முடியும்?"-னு கேக்கும்போது, vault-ல இருக்குற role assignments-ஐயும் அதோட access log-ஐயும் காட்டுவீங்க. ஒரு region drill-ல, team `location = "southindia"`-ஐயும் ஒரு புது state key-ஐயும் pass பண்ணி South India-ல ரெண்டாவது staging-ஐ build பண்ணுது. ஒரு gotcha வெளியே வந்துச்சு: Key Vault, Postgres server names முழு Azure-லயும் unique-ஆ இருக்கணும், அதனால copy-ஓட names-ல ஒரு region suffix தேவை. இந்த example-ல rebuild ஒரு மணி நேரத்துக்குள்ள முடிஞ்சுது; உங்களுக்கு அது data size-ஐ பொறுத்தது.

| Auditor-ஓட கேள்வி | முன்னாடி பதில் | அப்புறம் பதில் |
| --- | --- | --- |
| Secrets எங்க store ஆகியிருக்கு? | "ஒரு .env file-ல" | Key Vault, ஒரு access log-ஓட |
| Database password இருக்கா? | ஆமா, அதே file-ல | இல்ல, app அதோட identity வச்சு sign in பண்ணுது |
| Production-ஐ யார் மாத்த முடியும்? | பல பேர், portal மூலமா | Production pipeline, ஒரு approved plan-க்கு அப்புறம் |
| ஒரு manual change பத்தி எப்படி தெரிஞ்சுக்குவீங்க? | தெரியாது | Nightly drift check-உம் activity-log alerts-உம் |
| Test data real-ஆ? | ஆமா | இல்ல, masked copies |

## பொதுவான தப்புகள்

- **Production data-வுக்கு எதிரா test பண்றது.** ஒரு மோசமான script போதும், real customers பாதிக்கப்படுவாங்க. பிரிங்க, test data-வை mask பண்ணுங்க.
- **Git-ல secrets, கொஞ்ச நேரம் மட்டுமா இருந்தாலும்.** History அவற்றை வச்சிருக்கும். எப்பவாவது commit ஆன எந்த key-ஐயும் rotate பண்ணுங்க.
- **`sensitive = true` ஒரு secret-ஐ state-ல வராம பாத்துக்கும்னு நம்புறது.** அது screen-ல இருந்து மட்டும் மறைக்கும். Managed identity அல்லது write-only arguments use பண்ணுங்க.
- **Laptop-ல Terraform state.** அது தொலைஞ்சு போகும் அல்லது பழசாயிடும், அதுல secrets-உம் இருக்கலாம். Remote, locked state use பண்ணுங்க.
- **Staging-க்கும் production-க்கும் ஒரே state, அல்லது CLI workspaces.** அப்போ ஒரு staging change, அதே credentials-ஓட production-ஐ reach பண்ணலாம். தனித்தனி states-உம் access-உம் use பண்ணுங்க.
- **யாரும் record பண்ணாத console changes.** மாறின attributes drift-ஆ தெரியும்; கையால செஞ்ச புது resources தெரியவே தெரியாது. Activity log-ல alert வைங்க, import அல்லது delete பண்ணுங்க.
- **Laptops-ல இருந்து apply ஓட்டுறது.** எந்த code apply ஆச்சுன்னு யாருக்கும் தெரியாது. Review ஆன plan-ஐ CI-ல இருந்து மட்டும் apply பண்ணுங்க.
- **ஒவ்வொரு environment-க்கும் வேற shape.** Production-ல இருக்குற private network staging-ல இல்லன்னா, staging tests பெரிசா எதையும் நிரூபிக்காது.
- **Versions-ஐ pin பண்ணாம பழைய provider code-ஐ copy பண்றது.** Major versions-க்கு நடுவுல arguments-ஓட பேர் மாறும்; pin பண்ணுங்க, தெரிஞ்சே upgrade பண்ணுங்க.

## Terraform உங்களுக்கு தேவைக்கு அதிகமா இருக்குறப்போ

- **ஒரு சின்ன single service**, உங்களுக்காக infrastructure-ஐ manage பண்ற ஒரு platform-ல.
- **குறுகிய காலம் மட்டும் இருக்குற ஒரு prototype**, அடுத்த மாசம் delete பண்ணப்போறீங்க.
- **தனக்குன்னு infrastructure team-உம் tool-உம் இருக்குற ஒரு client** (Bicep, CloudFormation அல்லது Pulumi மாதிரி): அவங்களோடதையே use பண்ணுங்க.

Licence பொருந்துதான்னும் check பண்ணுங்க. Version 1.6-ல இருந்து Terraform, Business Source License-க்கு கீழ இருக்கு, இப்போ IBM தான் licensor. உங்க சொந்த அல்லது ஒரு client-ஓட infrastructure-ஐ ஓட்ட அதை use பண்ணலாம், ஆனா அதை வச்சு போட்டியா ஒரு hosted product build பண்ணக்கூடாது. OpenTofu, Mozilla Public License 2.0-க்கு கீழ இருக்குற ஒரு open-source fork, Linux Foundation நடத்துது, 2025-ல இருந்து ஒரு CNCF project, அதே HCL-ஐ read பண்ணும். அந்த காரணத்துக்காக சில clients அதை விரும்புறாங்க.

Environment variables, validate பண்ண settings, ஒரு secret store மூணுமே, சின்னதிலும் சின்ன project-லயும் கூட வச்சுக்க வேண்டியவை.

## Demo-ல இருந்து production-க்கு

- **Remote, locked state வைங்க**, ஒவ்வொரு environment-க்கும், access-ஐ restrict பண்ணி.
- **Pull requests-ல plan பண்ணுங்க**, review ஆன plan-ஐ மட்டும் CI-ல இருந்து apply பண்ணுங்க, OIDC மூலமா sign in பண்ணி.
- **ஒரு approval-ஐ கட்டாயமாக்குங்க**, எந்த production apply-க்கும் முன்னாடி.
- **Nightly drift checks ஓட்டுங்க** production-ல, Terraform-க்கு வெளியே create ஆன resources-க்கு alerts-உம் சேர்த்து.
- **Terraform-ஐ scan பண்ணுங்க**, CI-ல risky settings இருக்கான்னு.
- **Secrets-ஐ state-ல வராம பாத்துக்குங்க**, managed identity, write-only arguments வச்சு.
- **Start-up-ல settings-ஐ validate பண்ணுங்க**, secrets `SecretStr`-ஆ இருக்கட்டும், app-ஓட identity மூலமா read ஆகட்டும்.

## Practice பண்ணுங்க

நீங்க தேர்ந்தெடுத்த cloud-க்கு Terraform-ஓட getting-started tutorials-ஐ follow பண்ணுங்க, config பத்தின Twelve-Factor page-ஐ படிங்க.

1. `env = "staging"`-க்கு ஒரு storage bucket-ஐயும் ஒரு சின்ன managed database-ஐயும் create பண்ற Terraform எழுதுங்க, database public-ஆ reach ஆகக்கூடாது. அதை apply பண்ணுங்க, plan-ஐ படிங்க, அப்புறம் destroy பண்ணுங்க.
2. உங்க app-ஓட settings-ஐ environment variables-ல இருந்து read பண்ற, validate பண்ற ஒரு settings model-க்கு மாத்துங்க, model name-க்கு default இருக்கக்கூடாது; ஒரு value இல்லன்னா start-up clear-ஆ fail ஆகுற மாதிரி பண்ணுங்க.
3. உங்க cloud-ஓட secret manager-ல ஒரு secret-ஐ store பண்ணி, app அதை அதோட identity மூலமா read பண்ண வைங்க. அப்புறம் அதை rotate பண்ணி, app புது value-ஐ எடுத்துக்குதான்னு confirm பண்ணுங்க.
4. Console-ல, Terraform manage பண்ற ஒரு resource-ஓட ஒரு setting-ஐ மாத்தி drift check-ஐ ஓட்டுங்க: அது 2-ஓட exit ஆகணும். அந்த change-ஐ undo பண்ணுங்க, அப்புறம் கையால ஒரு புது firewall rule create பண்ணி திரும்ப ஓட்டுங்க: அது 0-ஓட exit ஆகும். ஒரு import block வச்சு அந்த rule-ஐ import பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க staging environment-ஐ code-ல இருந்து திரும்ப build பண்ண முடியும், உங்க repository-லயோ state-லயோ எந்த secret-உம் இல்லன்னு காட்ட முடியும், உங்க drift check எதை பாக்க முடியாதுன்னு explain பண்ண முடியும்.
