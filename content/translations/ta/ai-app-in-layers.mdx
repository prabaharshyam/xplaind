## இது என்ன

எல்லா AI product-உம் ஒரே மாதிரிதான் ஆரம்பிக்கும்: உங்க app ஒரு கேள்வியை model-க்கு அனுப்பி, answer-ஐ காட்டும். அதுவே ஒரு முழுமையான, வேலை செய்யுற architecture. நிஜமான products பெரும்பாலும் இதுல இருந்து parts சேர்த்து வளரும், அந்த வரிசை முக்கியம்.

நிறைய teams வளர்ற ஒரு பொதுவான வரிசை:

1. **Context-ஐ மேம்படுத்துங்க.** Model-க்கு சரியான information கொடுங்க: documents-ல retrieval, data lookups, tools.
2. **Guardrails போடுங்க.** Model-க்குள்ள போறதையும் வெளியே வர்றதையும் check பண்ணுங்க.
3. **Router, gateway சேருங்க.** ஒவ்வொரு request-ஐயும் சரியான இடத்துக்கு அனுப்பி, எல்லா model calls-ஐயும் ஒரே இடத்துல manage பண்ணுங்க.
4. **Caches சேருங்க.** ஒரே வேலைக்கு ரெண்டு தடவை காசு கொடுக்காம இருக்க.
5. **Agent patterns சேருங்க.** Loops, பல steps, உலகத்துல எதையாவது மாத்துற actions.

இதெல்லாத்தோடயும், முதல் நாள்ல இருந்தே: **monitoring**, அப்பதான் ஒவ்வொரு part-உம் என்ன பண்ணுதுன்னு பார்க்கலாம்.

இது கண்டிப்பான recipe இல்ல. நிஜமான problem கேக்கும்போது மட்டும் ஒரு layer-ஐ சேர்க்கணும், அப்பதான் product அனுமதிக்கிற அளவுக்கு system எளிமையா இருக்கும்.

```flow
title: வளர்ந்த AI app வழியா ஒரு request
User கேள்வி -> Input guardrails | personal data mask, injection block
Input guardrails -> Router | intent: FAQ, account, scope-க்கு வெளியே
Router -[FAQ]-> Cache | exact அல்லது semantic
Cache -[miss]-> Context retrieve பண்ணு | documents, data, tools
Router -[account]-> Context retrieve பண்ணு
Router -[scope-க்கு வெளியே]-> Ready-made reply
Context retrieve பண்ணு -> Gateway | keys, limits, retries, fallback
Gateway -> Model
Model -> Output guardrails | format, facts, safety
Output guardrails -[fail]-> Retry அல்லது ஆள்கிட்ட கொடு
Output guardrails -[pass]-> Answer, trace-ஐ log பண்ணு
```

## இது எப்படி work ஆகுது

**Step 1: context-ஐ மேம்படுத்துறது.** Model-க்கு அதோட training data-வும், நீங்க prompt-ல வைக்கிறதும் மட்டும்தான் தெரியும். ஆரம்ப quality problems பெரும்பாலும் missing அல்லது பழைய facts-னால தான், அதனால முதல்ல சேர்க்குறது பொதுவா retrieval (documents, database, search index) அல்லது tools (order lookup, calculator). RAG, tool-calling lessons இதை ஆழமா பேசும்.

**Step 2: guardrails.** ரெண்டு வகை இருக்கு.

- **Input guardrails**, private data வெளி services-க்கு leak ஆகாம தடுக்கும், உதாரணத்துக்கு model call-க்கு முன்னாடி Aadhaar numbers, phone numbers, names-ஐ mask பண்ணி; கெடுதலான அல்லது injected instructions-ஐயும் பிடிக்கும்.
- **Output guardrails**, user பார்க்குறதுக்கு முன்னாடியே answer-ஐ check பண்ணும்: format சரியா, support இல்லாத claims இல்லையா, personal data இல்லையா, உங்க policy-க்கு எதிரா எதுவும் இல்லையா. Check fail ஆச்சுன்னா retry பண்ணலாம், வேற model-க்கு fallback பண்ணலாம், safe message திருப்பலாம், இல்லன்னா ஒரு ஆள்கிட்ட கொடுக்கலாம்.

Guardrails latency சேர்க்கும், குறிப்பா streamed answers-ல, அங்க text-ஐ காட்டுறதுக்கு முன்னாடி check பண்ணுவீங்களா இல்ல காட்டும்போதே பண்ணுவீங்களான்னு முடிவு பண்ணணும். Fast checks-ஐ inline-ஆ வச்சு, மெதுவான checks-ஐ ஒரு sample-ல பண்ணுங்க.

**Step 3: router, gateway.**

- **Router**, request எங்க போகணும்னு முடிவு பண்ணும், பொதுவா சின்ன, fast intent classifier வச்சு. ஈசியான கேள்விகளை cheap model-க்கும், கஷ்டமானதை strong model-க்கும் அனுப்பலாம், billing disputes-ஐ ஒரு ஆள்கிட்ட அனுப்பலாம், scope-க்கு வெளியே இருக்குற கேள்விகளுக்கு model-ஐ call பண்ணாமலே மரியாதையான ready-made reply கொடுக்கலாம், message தெளிவில்லாம இருந்தா clarification கேக்கலாம் ("என் account-ஐ freeze பண்ணணுமா, இல்ல weather பத்தி கேக்குறீங்களா?").
- **Gateway** என்பது ஒவ்வொரு model call-உம் போற ஒரே இடம். API keys-ஐ services முழுக்க சிதறாம இங்கதான் வச்சிருக்கும், யார் எந்த model-ஐ use பண்ணலாம்னு கட்டுப்படுத்தும், spend limits-ஐ அமல்படுத்தும், ஒவ்வொரு call-ஐயும் log பண்ணும், ஒரு provider down ஆச்சுன்னா retry பண்ணும் அல்லது வேற provider-க்கு fallback பண்ணும்.

**Step 4: caches.**

- **Exact cache:** அதே normalise பண்ணின கேள்வி, template version, model இருந்தா அதே stored answer கிடைக்கும். Safe, எளிமை.
- **Semantic cache:** புது கேள்வி பழைய கேள்வியோட *அர்த்தத்துல* ஒண்ணுன்னா பழைய answer-ஐ reuse பண்றது, embeddings, similarity threshold வச்சு match பண்ணி. கேள்விகள் திரும்பத் திரும்ப வந்தா நிறைய சேமிக்கலாம், ஆனா loose match தப்பான answer கொடுக்கும் ("order 1-க்கு refund" என்பது "order 2-க்கு refund"-க்கு ரொம்ப பக்கத்துல இருக்கு). Hit rate அதிகமா இருந்து, அதோட தப்புகளை அளந்து பார்த்த பிறகுதான் சேருங்க.
Reuse பண்ண safe-ஆ இருக்குற exact cache key, answer-ஐ மாத்தக்கூடிய எல்லாத்தையும் உள்ளடக்கணும்:

```python
import hashlib, re

def cache_key(question, template_version, model, day):
    """Same key only when the answer would be the same: same words, prompt, model and day."""
    normalised = re.sub(r"\s+", " ", question.strip().lower())
    raw = f"{normalised}|{template_version}|{model}|{day}"
    return hashlib.sha256(raw.encode()).hexdigest()

# cache_key("What are Dr Mehta's timings?", "v7", "fast-model", "2026-11-08")
```

- **Prompt caching**, **KV cache** model provider-ல அல்லது server-ல நடக்கும்; அவை வேலை செய்ய உங்க prompt-ஓட மாறாத பகுதியை முதல்ல வைங்க.

**Step 5: agent patterns.** இதுவரை ஒவ்வொரு request-ம் ஒரே திசையில போகுது. Agent patterns loops சேர்க்கும் (முதல் answer முழுசா இல்லன்னா மறுபடி retrieve பண்றது), பல steps சேர்க்கும், email அனுப்புறது, appointment book பண்றது மாதிரி **write actions**-ஐயும் சேர்க்கும். இவை system-ஐ ரொம்ப capable ஆக்கும், ஆனா அதே அளவு risky-ம் ஆக்கும். கடைசியில சேருங்க; data-வை மாத்துற எதுக்கும் approvals, tools என்ன பண்ணலாம்ங்கிறதுக்கு limits, steps, spend-க்கு budgets வச்சு.

**முதல் நாள்ல இருந்தே monitoring.** ஒவ்வொரு request-ஐயும் ஒரு trace-ஆ log பண்ணுங்க: input, retrieve ஆன context, model, prompt version, output, guardrail results, latency, cost; personal data mask பண்ணி. Dashboard-ல சில signals-ஐ track பண்ணுங்க: error, refusal rates, guardrail triggers, ஒரு request-க்கு cost, latency, user feedback. System வளர வளர, எந்த layer fail ஆச்சுன்னு கண்டுபிடிக்க traces தான் வழி.

| Layer | எப்போ சேர்க்கணும் | வழக்கமான tools | கொண்டு வர்ற புது risk |
| --- | --- | --- | --- |
| Context | Answers facts-ஐ miss பண்ணும்போது அல்லது கற்பனை பண்ணும்போது | Vector search, SQL, APIs | தப்பான அல்லது பழைய documents |
| Guardrails | நிஜ users, நிஜ data வரும்போது | PII masking, validators, judge checks | Latency, தப்பா block ஆகுறது |
| Router | Requests கஷ்டத்துலயோ வகையிலயோ வேறுபடும்போது | சின்ன classifier, rules | தப்பான route-க்கு போன requests |
| Gateway | ஒரு model, service அல்லது team-க்கு மேல இருக்கும்போது | LiteLLM, cloud gateways | ஒரே இடத்துல fail ஆகும் ஆபத்து |
| Cache | நிறைய கேள்விகள் திரும்ப வரும்போது | Redis, vector index | பழைய அல்லது தப்பான reuse |
| Agents, actions | Tasks-க்கு பல steps அல்லது மாற்றங்கள் வேணும்போது | Agent SDKs, LangGraph | கட்டுப்பாடில்லாம ஓடும் loops, கெடுதலான actions |

## ஒரு worked example

Pune-ல 40 clinics இருக்குற ஒரு chain WhatsApp assistant நடத்துது. அது timings, fees list பண்ணின நீளமான prompt-ஓட ஒரே model call-ஆ ஆரம்பிச்சுது. ஆறு மாசம் ஆன பிறகு நாலு problems: சொல்ற fees சில நேரம் பழசா இருக்கு, patients தங்க messages-ல Aadhaar, phone numbers-ஐ share பண்றாங்க, அதே பத்து கேள்விகள் traffic-ல 40% இருக்கு, patients appointments book பண்ண சொல்லிக்கிட்டே இருக்காங்க.

அவங்க வரிசையா வளர்க்குறாங்க:

1. **Context.** Timings, fees, doctor schedules இப்போ கேள்வி வர்ற நேரத்துல clinic system-ல இருந்து வருது. பழைய fees பிரச்சனை போயிடுச்சு.
2. **Guardrails.** எந்த model call-க்கும் முன்னாடி Aadhaar, phone numbers mask ஆகுது. Diagnosis மாதிரி படிக்குற எதையும் output check block பண்ணுது, fees clinic system-ஓட பொருந்துதான்னும் confirm பண்ணுது.
3. **Router.** ஒரு சின்ன classifier top FAQs-ஐ fixed answers-க்கும், lab-report கேள்விகளை secure link-க்கும், அவசரமான எதையும் ஒரு phone number-க்கும் அனுப்புது, model call இல்லாம.
4. மீதி திரும்ப வர்ற கேள்விகளுக்கு **Exact cache**, normalise பண்ணின கேள்வி, தேதி key-ஆ வச்சு, ஏன்னா schedules தினமும் மாறும்.
5. **Booking ஒரு tool-ஆ**, கடைசியா: assistant ஒரு slot-ஐ propose பண்ணும், patient ஒரு button-ல confirm பண்ணுவாங்க, ஒவ்வொரு booking-உம் log ஆகும்.

| அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| 1,000 messages-க்கு model calls | 1,000 | 520 |
| தப்பான fee அல்லது timing answers (வாராந்திர sample) | 6% | 1%-க்கு கீழ |
| Aadhaar numbers-ஓட model-க்கு போன messages | தினமும் சிலது | ஒண்ணும் இல்ல |
| Chat-ல முடிஞ்ச bookings | 0 | booking requests-ல 22% |

இந்த numbers உதாரணத்துக்கு மட்டும். அவங்க semantic cache சேர்க்கல: ஒரு test, அது "Dr Mehta's timings"-ஐ "Dr Mehra's timings"-ஓட match பண்ணுதுன்னு காட்டுச்சு.

## பொதுவா பண்ற தப்புகள்

- **முதல்லயே முழு platform-ஐ கட்டுறது.** பத்து users வர்றதுக்கு முன்னாடியே அஞ்சு layers-ன்னா, debug பண்ண அஞ்சு இடம், கத்துக்கிட்டது ஒண்ணும் இல்ல.
- **Context வேலை செய்றதுக்கு முன்னாடியே agents சேர்க்குறது.** தப்பான facts-ஐ வச்சு செயல்படுற agent சீக்கிரமா அதிக சேதம் பண்ணும்.
- **Log மட்டும் பண்ற guardrails.** Block பண்ணாத, retry பண்ணாத, escalate பண்ணாத check எதையும் காப்பாத்தாது.
- **Details இருக்குற கேள்விகள்ல semantic cache.** Order numbers, names, dates இருந்தா ஒத்த கேள்விகளுக்கு வேற அர்த்தம் வந்துடும்.
- **Traces இல்லாம இருக்கறது.** ஒவ்வொரு request-க்கும் trace இல்லன்னா, retrieval, router, model-ல எது fail ஆச்சுன்னு சொல்ல முடியாது.
- **Services முழுக்க சிதறின keys, limits.** ஒரு gateway, எளிமையானதா இருந்தாலும், spend-ஐயும் access-ஐயும் ஒரே இடத்துல வச்சிருக்கும்.

## எப்போ எளிமையாவே இருக்கணும்

- **கொஞ்சம் பேர் மட்டும் use பண்ற internal tools**-க்கு router, gateway, cache எப்பவும் தேவைப்படாம போகலாம்.
- **Volume குறைவா** இருந்தா, caching, routing சேமிப்பு கவனிக்கற அளவுக்கு இருக்காது.
- **Read-only answers**-க்கு agent loops, write actions தேவையில்ல.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு layer-ம் ஏன் இருக்குன்னு எழுதி வைங்க**, அது தீர்த்த problem, அளந்த effect-ஓட.
- **Layers-ஐ தனித்தனியா test பண்ணுங்க**: retrieval recall, router accuracy, guardrail false-block rate, cache error rate.
- **எல்லாத்தையும் சேர்த்து version பண்ணுங்க**: prompts, router model, guardrail rules, cache keys, அப்பதான் ஒரு release-ஐ ஒண்ணா rollback பண்ணலாம்.
- **பாதுகாப்பா fail ஆகுங்க**: ஒரு layer down ஆச்சுன்னா, request error page-க்கு போகாம எளிமையான path-க்கு fallback ஆகணும்.

## Practice பண்ணுங்க

1. உங்களுக்கு தெரிஞ்ச ஒரு AI feature-ஓட architecture-ஐ இன்னைக்கு இருக்கற மாதிரியே வரைங்க. அஞ்சு layers-ல எது அதுல இருக்கு?
2. இல்லாத ஒவ்வொரு layer-க்கும், அதை சேர்க்கறதை நியாயப்படுத்துற problem-ஐயும், அதை எப்படி அளப்பீங்கன்னும் எழுதுங்க.
3. திரும்ப வர்ற ஒரு கேள்வி வகையை எடுத்து முடிவு பண்ணுங்க: ready-made answer, exact cache, semantic cache இல்லன்னா எதுவும் இல்ல. ஏன்னு explain பண்ணுங்க.
