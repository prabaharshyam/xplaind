## இது என்ன

Language models **tokens**-ஐ படிக்கும், எழுதும். Tokens-னா சின்ன text துண்டுகள்: பெரும்பாலும் ஒரு முழு common வார்த்தை, சில சமயம் ஒரு வார்த்தையோட பகுதி, ஒரு number அல்லது ஒரு punctuation mark. Models use பண்றதுல எல்லாமே tokens-ல அளக்கப்படும்:

- **Price**: providers ஒரு மில்லியன் input tokens-க்கும், ஒரு மில்லியன் output tokens-க்கும் charge பண்றாங்க; output tokens பெரும்பாலும் பல மடங்கு costly.
- **Limits**: **context window**-னா ஒரு call-ல இருக்கக்கூடிய அதிகபட்ச tokens எண்ணிக்கை, அனுப்பின எல்லாத்தையும், reply-ஐயும் சேர்த்து.
- **Speed**: அதிக output tokens generate ஆக அதிக நேரம் எடுக்கும்.

| ஒரு API call-ஓட context window-ல பகுதி | Tokens | குறிப்பு |
|---|---|---|
| System prompt | 1,200 | ஒவ்வொரு call-லயும் ஒரே மாதிரி |
| Conversation history | 3,000 | ஒவ்வொரு turn-லயும் வளரும் |
| Retrieved passages | 800 | |
| புது user message | 150 | Tamil text அதிக tokens எடுக்கும் |
| Reply, max_tokens வரை | 300 | |

எல்லாமே எண்ணப்படும், input முழுசுக்கும் ஒவ்வொரு call-லயும் பணம் கொடுக்கணும்.

```flow
dir: LR
title: ஒரு call, ஆரம்பம் முதல் முடிவு வரை
System prompt + history + passages + புது message -[input tokens, ஒவ்வொரு call-லயும் பணம்]-> Model
Model -[output tokens, max_tokens வரை]-> Reply
```

இந்த lesson-ல Chennai-ல ஒரு e-learning company, Tamil-லயும் English-லயும் ஒரு doubt-solving chatbot build பண்றதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Token-னா என்ன.** ஒரு tokenizer, text-ஐ ஒரு fixed vocabulary-ல இருந்து துண்டுகளா பிரிக்கும். English-ல 100 tokens தோராயமா 75 வார்த்தைகள். Hindi, Tamil, மத்த இந்திய scripts-க்கு அதே அர்த்தத்துக்கு பெரும்பாலும் அதிக tokens தேவைப்படும், அதனால அதே message அதிகம் cost ஆகும், window-ல அதிக இடத்தையும் எடுக்கும். Numbers-உம் code-உம் கூட நிறைய tokens-ஆ பிரியும்.

**எண்ணுறது.** Provider dashboards-உம் replies-உம் ஒவ்வொரு call-க்கும் token usage-ஐ report பண்ணும், அனுப்புறதுக்கு முன்னாடியே எண்ண providers token-counting endpoints அல்லது libraries-ஐ கொடுப்பாங்க.

**Context window-ஐ எது நிரப்புது.** ஒரு chat app-ல ஒவ்வொரு call-லயும் அனுப்புற எல்லாமே கணக்குல வரும்:

- system prompt;
- இது வரைக்குமான முழு conversation (API-க்கு memory இல்ல; நீங்க திரும்ப அனுப்புறீங்க);
- documents அல்லது retrieved passages;
- tool definitions, tool results;
- `max_tokens` வரை reply.

Conversation வளர வளர, ஒவ்வொரு turn-உம் அதிக history-ஐ திரும்ப அனுப்பும், அதனால ஒரு turn-க்கான cost ஏறும்.

**Cost-ஐ estimate பண்றது.** Cost = input tokens × input price + output tokens × output price. உதாரணம்: 2,000 input tokens, 500 output tokens, ஒரு token-க்கு output-ஓட price, input-ஐ விட ஐந்து மடங்கு. Input 2,000 units; output 500 × 5 = 2,500 units. Output நீளத்துல கால் பங்கா இருந்தாலும் அதுக்கு தான் அதிக cost.

**Window-க்குள்ள இருக்கிறது.** பழைய conversation turns-ஐ trim அல்லது summarise பண்ணுங்க; முழு documents-க்கு பதிலா தேவையான passages-ஐ மட்டும் retrieve பண்ணுங்க; நியாயமான `max_tokens` set பண்ணுங்க; ரொம்ப பெரிய inputs-ஐ warning-ஓட truncate பண்ணுங்க. ரொம்ப நீளமான contexts, நடுவுல புதைஞ்ச details-க்கு answer quality-ஐயும் குறைக்கும்.

**Caching.** நிறைய calls ஒரு நீளமான, ஒரே மாதிரியான ஆரம்பத்தை (பெரிய system prompt அல்லது ஒரு document) share பண்ணா, prompt caching திரும்ப வர்ற input-ஐ ரொம்ப மலிவாவும் வேகமாவும் ஆக்கும். அதை பத்தி ஒரு அடுத்த lesson பேசும்.

**Conversation நீளத்தோட cost எப்படி வளருது** (1,200-token system prompt, 100-token கேள்விகள், 250-token answers, history திரும்ப அனுப்பப்படுது):

| Turn | அனுப்புன input tokens | அதுல history |
| --- | --- | --- |
| 1 | 1,300 | 0 |
| 3 | 2,000 | 700 |
| 6 | 3,050 | 1,750 |
| 10 | 4,450 | 3,150 |

Turn 10-க்குள்ள, நீங்க பணம் கொடுக்குறதுல பெரும்பாலானது history தான். பழைய turns-ஐ ஒரு குட்டி paragraph-ஆ summarise பண்ணா input கிட்டத்தட்ட ஒரே அளவுல இருக்கும், system prompt-ஐ cache பண்ணா அதோட 1,200 tokens முதல் call-க்கு அப்புறம் ஒவ்வொரு call-லயும் ரொம்ப மலிவாகும்.

**அனுப்புறதுக்கு முன்னாடி எண்ணுங்க.** ஒரு document அல்லது நீளமான message மாதிரி user paste பண்ணக்கூடிய எதுக்கும், model-ஐ call பண்றதுக்கு முன்னாடி tokens-ஐ எண்ணுங்க. ரொம்ப நீளமா இருந்தா, தேவையான பகுதிகளை மட்டும் retrieve பண்ணுங்க, முதல்ல summarise பண்ணுங்க, இல்லன்னா ரொம்ப நீளம்னு user-கிட்ட தெளிவா சொல்லுங்க. சத்தமில்லாத cut-off அல்லது எதிர்பாராத bill-ஐ விட, தெளிவான message-ஓட fail ஆகுறது ரொம்ப நல்லது.

**Code-ல tokens-ஐ எண்ணுங்க.** User பெருசா ஆக்கக்கூடிய எதையும் அனுப்புறதுக்கு முன்னாடி எண்ணுங்க. Anthropic-ஓட SDK-ல, model use பண்ற அதே tokenizer-ஐ தான் count use பண்ணும்:

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"                  # check the docs for current names

def count(system, messages):
    return client.messages.count_tokens(model=MODEL, system=system, messages=messages).input_tokens

english = [{"role": "user", "content": "Please send the electricity bill for October."}]
hindi = [{"role": "user", "content": "कृपया अक्टूबर का बिजली का बिल भेजें।"}]
print(count("Be brief.", english), count("Be brief.", hindi))   # the Hindi line usually costs more
```

Open models-க்கு, Hugging Face-ல இருந்து model-ஓட சொந்த tokenizer (`AutoTokenizer.from_pretrained(...)`) offline-லயே exact counts தரும். "ஒரு token-க்கு 4 characters" மாதிரி தோராய rules English-க்கு மட்டும் தான் பொருந்தும்.

**ஒரு context budget.** Window எப்படி பகிரப்படும்ன்னு முன்னாடியே முடிவு பண்ணுங்க, அப்போ ஒரு பகுதி மத்ததை நெருக்கிடாது:

| பகுதி | Budget (உதாரணம், 16,000-token target) | Budget-ஐ தாண்டினா |
| --- | --- | --- |
| System prompt, tools | 2,000 | சுருக்குங்க; அரிதா use ஆகுற rules-ஐ retrieval-க்கு மாத்துங்க |
| Conversation history | 4,000 | பழைய turns-ஐ summarise பண்ணுங்க |
| Retrieved passages | 6,000 | குறைவான, சிறந்த chunks |
| Tool results | 2,000 | தேவையான fields-ஐ மட்டும் திருப்புங்க |
| Reply (`max_tokens`) | 2,000 | குறுகிய answers கேளுங்க |

Target பெரும்பாலும் model-ஓட maximum-ஐ விட ரொம்ப குறைவு, ஏன்னா ஒவ்வொரு token-உம் cost-ஐயும் delay-ஐயும் கூட்டும், quality-உம் limit-க்கு முன்னாடியே பெரும்பாலும் குறையும்.

**History-ஐ budget-க்குள்ள வச்சிருக்கிறது.** சமீபத்திய turns-ஐ வார்த்தை மாறாம வச்சிருந்து, பழையதை ஒரு running summary-க்குள்ள மடிங்க:

```python
def fit_history(history, summary, budget_tokens, count_fn, keep_last=6):
    """history: list of {"role", "content"} turns, oldest first."""
    recent = history[-keep_last:]
    older = history[:-keep_last]
    if older:
        summary = summarise(summary, older)       # one cheap model call, done rarely
    prefix = [{"role": "user", "content": f"Summary of the earlier conversation: {summary}"},
              {"role": "assistant", "content": "Understood."}] if summary else []
    msgs = prefix + recent
    while count_fn(msgs) > budget_tokens and len(recent) > 2:
        recent = recent[2:]                       # drop the oldest user-assistant pair
        msgs = prefix + recent
    return msgs, summary
```

`summarise` உங்க சொந்த function: பழைய summary-ஐயும் மடிக்கப்படுற turns-ஐயும் சேர்க்குற ஒரு சின்ன model call. History budget-ஐ தாண்டும்போது மட்டும் summarise பண்ணுங்க, ஒவ்வொரு turn-லயும் இல்ல.

**நீளமான context-ல கவனம் இலவசம் இல்ல.** ஒரு நீளமான input-ஓட எல்லா பகுதிகளையும் models சமமா நல்லா use பண்றதில்ல. ஒரு நீளமான document-ல ஒரு fact-ஐ மறைச்சு வைக்கிற tests ("needle in a haystack"ன்னு சொல்வாங்க), நடுவுல இருக்குற facts, ஆரம்பத்துக்கோ கடைசிக்கோ பக்கத்துல இருக்குறதை விட குறைவான நம்பகத்தன்மையோட கண்டுபிடிக்கப்படுதுன்னு காட்டுது. மிக முக்கியமான instructions-ஐ ஆரம்பத்துலயும், கேள்வியை கடைசிலயும் வைங்க, retrieved passages-ஐ relevance order-ல கொடுங்க.

**Maximum context-உம், effective context-உம்.** ஒரு model 200,000 tokens அல்லது அதுக்கு மேல ஏத்துக்கலாம், ஆனா அவற்றை எவ்வளவு நல்லா use பண்ணுதுங்குறது task-க்கு task மாறும். உங்க சொந்த case-ஐ test பண்ணுங்க: ஒரு realistic document-ல வேற வேற இடங்கள்ல ஒரு தெரிஞ்ச fact-ஐ மறைச்சு வச்சு, answers சரியா இருக்கான்னு பாருங்க.

## ஒரு worked example

Chennai-ல ஒரு e-learning company, Class 10 students-க்கு Tamil-லயும் English-லயும் ஒரு doubt-solving chatbot build பண்றாங்க.

ஒரு வார testing-ல இருந்து அளவீடுகள்:

- Syllabus guidance-ஓட system prompt: 1,200 tokens.
- ஒரு typical கேள்வி: English-ல 60 tokens, Tamil-ல சுமார் 150.
- ஒரு typical answer: 250 tokens.
- பத்து turns-க்கு அப்புறம், history ஒவ்வொரு call-லயும் சுமார் 3,000 tokens-ஐ சேர்க்குது.

அவங்க model-ஓட prices-ல, பத்து-turn chat, ரெண்டு-turn chat-ஐ விட சுமார் நாலு மடங்கு cost ஆச்சு, பெரும்பாலும் திரும்ப அனுப்பப்படுற history-ஆல. அவங்க மூணு விஷயங்களை மாத்துறாங்க: ஆறு turns-க்கு அப்புறம் history-ஐ summarise பண்றது, system prompt-ஐ cache பண்றது, answers-ஐ 300 tokens-ல cap பண்றது. ஒரு conversation-க்கு average cost 55% குறையுது, நீளமான sessions-ல Tamil users இனி app-ஓட per-call input cap-ஐ தொடுறதில்ல.

**Tamil users ஏன் முதல்ல limit-ஐ தொட்டாங்க.** அதே கேள்விக்கு English-ஐ விட Tamil-ல சுமார் இரண்டரை மடங்கு tokens ஆச்சு, Tamil answers-உம் tokens-ல நீளமா இருந்துச்சு. Cost-ஐ கட்டுப்படுத்த team, ஒவ்வொரு call-ஐயும் 16,000 input tokens-ல cap பண்ணாங்க. நீளமான revision sessions-ல Tamil conversations சுமார் 30 turns-க்கு அப்புறம் அந்த cap-ஐ எட்டுச்சு, English ones அரிதாதான் எட்டுச்சு. ஆறு turns-க்கு அப்புறம் history-ஐ summarise பண்றது ரெண்டுக்கும் இதை சரி பண்ணுச்சு, bot-ஐ வேகமா பதில் சொல்லவும் வச்சுது, ஏன்னா குறுகிய inputs வேகமா process ஆகும். Team இப்போ ஒவ்வொரு prompt மாற்றத்தையும் Tamil, English ரெண்டு conversations-லயும் test பண்ணுது, ஒவ்வொரு மொழிக்கும் தனியா conversation-க்கான cost-ஐ report பண்ணுது. அதனால English-ல மலிவா, Tamil-ல costly-ஆ இருக்குற மாற்றம் ship ஆகுறதுக்கு முன்னாடியே பிடிபடும்.

## பொதுவான தவறுகள்

- **Tokens-க்கு பதிலா வார்த்தைகளை எண்ணுறது.** Prices-உம் limits-உம் tokens-ல இருக்கு, இந்திய மொழிகள் அதிகம் use பண்ணும்.
- **History திரும்ப அனுப்பப்படுதுங்குறதை மறந்துடுறது.** நீளமான chats costly ஆயிடும்.
- **Output price-ஐ கவனிக்காம விடுறது.** Output tokens பெரும்பாலும் அதிகம் cost ஆகும்.
- **`max_tokens` இல்லாதது.** Replies நீளமா, costly-ஆ ஆகலாம்.
- **முழு documents-ஐ திணிக்கிறது.** தேவையானதை retrieve பண்ணுங்க.

- **பெரிய context window எல்லாத்தையும் தீர்த்துடும்னு நினைக்கிறது.** ரொம்ப நீளமான inputs அதிகம் cost ஆகும், மெதுவு, நடுவுல இருக்குற details பெரும்பாலும் miss ஆகும். உங்ககிட்ட இருக்குற எல்லாத்தையும் இல்ல, தேவையானதை மட்டும் அனுப்புங்க.
- **இந்திய மொழி tokens-ஐ English rules வச்சு estimate பண்றது.** Real tokenizer-ஆல எண்ணுங்க.
- **Window இருக்குன்னு அதை நிரப்புறது.** ஒவ்வொரு கூடுதல் token-உம் cost-ஐயும் delay-ஐயும் சேர்க்கும், accuracy-ஐயும் குறைக்கலாம்.

## Context-ஐ நெருக்கமா manage பண்ண தேவையில்லாத இடங்கள்

- **குறுகிய, single-turn calls**, உதாரணம் ஒரு message-ஐ classify பண்றது: design பண்ணும்போது ஒரு தடவை எண்ணிட்டு முன்னேறுங்க.
- **குறைந்த volume உள்ள internal tools**, அங்க பெரிய bill, engineering நேரத்தை விட மலிவு.
- **குறுகிய records மேல batch jobs**, எல்லா inputs-உம் கிட்டத்தட்ட ஒரே அளவுல இருக்கும்போது.

நீளமான chats, paste பண்ண documents, நிறைய tool results உள்ள agents, scale-ல இந்திய மொழிகள்ல எதுவா இருந்தாலும் context-ஐ நெருக்கமா manage பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு call-க்கும் input, output tokens-ஐ log பண்ணுங்க**, முடிஞ்ச இடத்துல பகுதி வாரியா பிரிச்சு: system, history, retrieved, tools.
- **Budgets-ஐ prompt-ல மட்டும் இல்ல, code-ல enforce பண்ணுங்க.**
- **User input நீளத்தை cap பண்ணுங்க**, தெளிவான message-ஓட, அனுப்புறதுக்கு முன்னாடி எண்ணுங்க.
- **Token வளர்ச்சிக்கு alert வைங்க**: average input size ஏறிக்கிட்டே போனா, history அல்லது retrieval trim ஆகலைன்னு பெரும்பாலும் அர்த்தம்.
- **Models மாத்தும்போது budgets-ஐ மறுபடி check பண்ணுங்க**, ஏன்னா tokenizers-உம் prices-உம் வேறுபடும்.

## Practice

கீழ link பண்ணியிருக்குற context windows guide-ஐயும், token-counting page-ஐயும் படிங்க.

1. அதே 100-வார்த்தை paragraph-க்கு English-லயும், உங்களுக்கு தெரிஞ்ச ஒரு இந்திய மொழியிலயும் tokens-ஐ எண்ணுங்க.
2. உங்க app-க்கான 10-turn conversation-ஓட cost-ஐ தற்போதைய prices-ல estimate பண்ணுங்க, அப்புறம் ஐந்து turns-க்கு அப்புறம் history-ஐ summarise பண்ணா.
3. உங்க apps-ல ஒண்ணுல `max_tokens` cap-ஐயும், ரொம்ப பெரிய inputs-க்கு ஒரு warning-ஐயும் சேருங்க.
4. 30-பக்க document-ல ஆரம்பம், நடு, கடைசில ஒரு fact-ஐ மறைச்சு, ஒவ்வொரு தடவையும் அதை பத்தி கேட்டு, model எங்க miss பண்ணுதுன்னு note பண்ணுங்க.
