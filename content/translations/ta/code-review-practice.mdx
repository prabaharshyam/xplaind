## இது என்ன

**Code review**-னா, உங்க change merge ஆகுறதுக்கு முன்னாடி ஒரு teammate அதை படிக்கிறது. GitHub, GitLab-ல இது ஒரு **pull request** (அல்லது merge request)-ல நடக்கும்: change, அதோட description, automated checks, குறிப்பிட்ட lines-ல comments-ஓட ஒரு thread.

Reviews மூணு வேலை செய்யும். Users பார்க்குறதுக்கு முன்னாடியே bugs-ஐ பிடிக்கும். Codebase-ஐ consistent-ஆ வச்சிருக்கும், அதனால அது styles-ஓட ஒரு ஒட்டுவேலையா ஆகாது. Knowledge-ஐயும் பரப்பும்: review-க்கு அப்புறம் அந்த change-ஐ ஒருத்தருக்கு பதிலா ரெண்டு பேர் புரிஞ்சுக்கிறாங்க.

Review-ங்கிறது code பத்தின ஒரு உரையாடல், ஆளை judge பண்றது இல்ல. நல்லா review பண்ற teams வேகமா ship பண்ணுவாங்க, ஏன்னா problems fix பண்ண மலிவா இருக்கும்போதே பிடிபடுது.

## இது எப்படி work ஆகுது

```flow
title: Open ஆகுறதுல இருந்து merge வரை ஒரு pull request
Author சின்ன pull request open பண்றாங்க | என்ன, ஏன், எப்படி test பண்ணாங்க -> Automated checks | tests, linter, build
Automated checks -[fail]-> Author fix பண்றாங்க -> Automated checks
Automated checks -[pass]-> Reviewer படிக்கிறாங்க | முதல்ல correctness, அப்புறம் design, அப்புறம் style
Reviewer படிக்கிறாங்க -[changes வேணும்]-> Comments: specific, kind, labelled
Comments: specific, kind, labelled -> Author reply பண்றாங்க அல்லது fixes push பண்றாங்க -> Reviewer படிக்கிறாங்க
Reviewer படிக்கிறாங்க -[நல்லா இருக்கு]-> Approve பண்ணி merge
```

**Author-ஆ**, உங்க change-ஐ review பண்ண எளிதா ஆக்குங்க:

- சின்னதா, ஒரே விஷயத்தை பத்தி வச்சுக்கோங்க. 200-line pull request-க்கு கவனமான review கிடைக்கும்; 2,000-line ஒண்ணை மேலோட்டமா தான் பார்ப்பாங்க.
- ஒரு description எழுதுங்க: என்ன மாறுச்சு, ஏன், எப்படி test பண்ணீங்க. Ticket-ஐ link பண்ணுங்க. கண்ணுக்கு தெரியுற எதுக்கும் screenshots சேருங்க.
- முதல்ல உங்க சொந்த diff-ஐ நீங்களே review பண்ணுங்க. யாரும் பார்க்குறதுக்கு முன்னாடியே, மிச்சம் இருக்குற prints, typos-ஐ நீங்களே பிடிப்பீங்க.
- Review கேக்குறதுக்கு முன்னாடி checks pass ஆகட்டும்.

**Reviewer-ஆ**, எது அதிக முக்கியமோ அதை, வரிசையா பாருங்க:

| வரிசை | எதை பார்க்கிறது | உதாரணங்கள் |
| --- | --- | --- |
| 1 | Correctness | தப்பான logic, handle பண்ணாத errors, edge cases, security, data leaks |
| 2 | Tests | புது behaviour test ஆகியிருக்கா? Change இல்லன்னா அந்த test fail ஆகுமா? |
| 3 | Design | System-ஓட பொருந்துதா? எதுவும் duplicate ஆகியிருக்கா? மாத்த எளிதா இருக்குமா? |
| 4 | Readability | பேர்கள், நீளமான functions, குழப்பமான logic, இல்லாத "why" comments |
| 5 | Style | Formatting, import order; ஒரு ஆளால இல்ல, ஒரு linter-ஆல fix ஆகுறது தான் better |

Specific-ஆ (என்ன, எங்க) comments எழுதுங்க, ஏன் முக்கியம்னு சொல்லுங்க, ஒரு fix-ஐ suggest பண்ணுங்க. Optional-ஆனதை "nit:" அல்லது "optional:"-ன்னு label பண்ணுங்க. உறுதியா தெரியலன்னா assert பண்றதுக்கு பதிலா கேள்வி கேளுங்க. நல்லா இருக்குறதையும் சொல்லுங்க; அது author எதை தொடர்ந்து பண்ணணும்னு சொல்லும்.

**Comments வாங்கும் author-ஆ**, நல்ல எண்ணத்துல சொல்றாங்கன்னு எடுத்துக்கோங்க. நன்றி சொல்லுங்க, fix பண்ணுங்க, ஒவ்வொரு thread-லயும் reply பண்ணுங்க. ஒத்துக்கலன்னா evidence-ஓட explain பண்ணுங்க. ஒரு thread ரெண்டு தடவைக்கு மேல முன்னயும் பின்னயும் போனா, ஒரு call-ல பேசி தீர்த்துக்கோங்க.

**தெரியாத ஒரு area-ஐ review பண்றது.** நல்லா review பண்ண, முழு codebase-ஐயும் தெரிஞ்சிருக்க தேவையில்ல. முதல்ல description-ஐயும் ticket-ஐயும் படிங்க, அப்போ அந்த change என்ன பண்ணணும்னு தெரியும். முடிஞ்சா code-ஐயோ tests-ஐயோ local-ல run பண்ணுங்க. உங்களால judge பண்ண முடியுறதுல focus பண்ணுங்க, உதாரணம்: error handling, edge cases, tests, readability; எந்த parts-ஐ உங்களால assess பண்ண முடியலன்னு தெளிவா சொல்லுங்க, அப்போ author அதை பத்தி வேற யார்கிட்டயாவது கேட்கலாம்.

**AI changes-ஐ review பண்றது.** ஒரு prompt, ஒரு model, retrieval settings-ல வர்ற change-உம் ஒரு code change தான், ஆனா அதோட effect diff-ல இல்ல, outputs-ல தெரியும். Category வாரியா முன்னாடி-பின்னாடி eval results-ஐயும், மாறுன சில example outputs-ஐயும் கேளுங்க. ஒரு வார்த்தை prompt edit ஒரு வகை கேள்வியை fix பண்ணிட்டு, இன்னொண்ணை அமைதியா உடைச்சிடலாம்.

**வேகம் முக்கியம்.** Review-க்கு மூணு நாள் காத்திருக்குற ஒரு pull request பழசாயிடும்: main முன்னாடி போயிடும், conflicts குவியும், author context-ஐ இழப்பாரு. நிறைய teams ஒரு வேலை நாளுக்குள்ள முதல் review கொடுக்க target வைக்கிறாங்க. நேரத்துக்குள்ள ஒழுங்கா review பண்ண முடியலன்னா, அதை சொல்லிடுங்க, அப்போ author வேற யாரையாவது கண்டுபிடிப்பாங்க.

**உங்க browser-லயே try பண்ணுங்க.** இந்த function-ஐ run பண்ணுங்க, அப்புறம் review பண்ணுங்க: கீழ இருக்குற tests ஒரு bug-ஐ காட்டுது. அதை fix பண்ணி மறுபடி run பண்ணுங்க.

```python
def average_rating(ratings):
    """Average of 1 to 5 star ratings, ignoring missing ones (None)."""
    total = sum(r for r in ratings if r is not None)
    return total / len(ratings)            # review: is this the right count?

print(average_rating([5, 4, None, 3]))     # expected 4.0
print(average_rating([2, 4]))              # expected 3.0
```

## ஒரு worked example

Gurugram-ல ஒரு food-delivery startup-ல junior engineer Aditya, "reorder last meal" button-ஐ சேர்க்குற ஒரு pull request-ஐ open பண்றாரு. அது app, API, database முழுக்க 640 lines-ஐ மாத்துது.

அவரோட reviewer Meera, அதை பிரிக்க சொல்றாங்க: tests-ஓட API endpoint-க்கு ஒரு pull request, button-க்கு ஒண்ணு. முதல் PR 180 lines. அவங்க அதை பதினைஞ்சு நிமிஷத்துல review பண்ணி நாலு comments போடுறாங்க:

- "Endpoint user id-ஐ request body-ல இருந்து எடுக்குது, அதனால யார் வேணும்னாலும் இன்னொரு user-க்கு reorder பண்ணலாம். அதுக்கு பதிலா logged-in session-ல இருந்து id-ஐ எடுக்கலாமா?" (correctness-ம் security-யும், blocking)
- "முன்னாடி orders எதுவும் இல்லாத user-க்கு test இல்ல. அவங்களுக்கு என்ன return ஆகணும்?" (tests, blocking)
- "`get_last()`, `OrderRepository.latest_for_user()`-ஐ reuse பண்ணலாமா? அதே query மாதிரி தெரியுது." (design)
- "nit: `res`-ஐ `last_order`-ன்னு வைக்கலாம். Blocking இல்ல."

கடைசியில அவங்க சொல்றாங்க: "மூடியிருக்குற restaurant-க்கான error handling ரொம்ப தெளிவா இருக்கு, நல்லா பண்ணியிருக்கீங்க."

Aditya security issue-ஐ fix பண்றாரு, test-ஐ சேர்க்குறாரு, இருக்குற query-ஐ reuse பண்றாரு, variable-ஐ rename பண்றாரு. ஒவ்வொரு thread-லயும் என்ன மாத்தினாருன்னு reply பண்றாரு. Meera approve பண்றாங்க; change அதே நாள்ல merge ஆகுது. Button-க்கான ரெண்டாவது pull request, API ஏற்கனவே review ஆனதால, இன்னும் வேகமா போகுது.

## பொதுவா பண்ற தப்புகள்

- **பெரிய pull requests.** Reviewers அவற்றை மேலோட்டமா தான் பார்ப்பாங்க, bugs நழுவிடும். Step வாரியா பிரிங்க.
- **Style-ல மட்டும் comment போடுறது.** Formatting-ஐ tools பார்த்துக்கட்டும்; மனுஷங்களோட கவனத்தை logic, tests, security-க்கு செலவழிங்க.
- **தெளிவில்லாத comments.** "This is wrong" author-ஐ யூகிக்க விட்டுடும். என்ன, ஏன், ஒரு suggestion சொல்லுங்க.
- **Comments-ஐ personal-ஆ எடுத்துக்கிறது.** Comment code பத்தினது. ஒண்ணு கடுமையா தெரிஞ்சா ஒரு கேள்வி கேளுங்க.
- **படிக்காம approve பண்றது.** Rubber stamp, review இல்லாததை விட மோசம், ஏன்னா மக்கள் அதை நம்புறாங்க.
- **Preferences-க்காக block பண்றது.** அது ஒரு taste-னா, optional-ன்னு mark பண்ணி author-ஐ decide பண்ண விடுங்க.

## Practice பண்ணுங்க

1. உங்க கடைசி pull request-ஐ open பண்ணி, அதோட description-ஐ என்ன, ஏன், எப்படி test பண்ணீங்கன்னு திருப்பி எழுதுங்க.
2. நீங்க use பண்ற ஒரு open-source project-ல ஒரு pull request-ஐ review பண்ணி, முக்கியத்துவம் வரிசையில அஞ்சு comments-ஐ draft பண்ணுங்க.
3. நீங்க வாங்கின அல்லது எழுதின மூணு தெளிவில்லாத comments-ஐ, specific-ஆன, kind-ஆன comments-ஆ திருப்பி எழுதுங்க.
4. Behavioural interviews-க்கு, உங்க மனசை மாத்தின ஒரு code review பத்தின STAR story-ஐ தயார் பண்ணுங்க.
