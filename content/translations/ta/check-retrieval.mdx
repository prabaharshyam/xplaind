## இது என்ன

RAG system-ல வர்ற தப்பான answers-ல பெரும்பாலானவை retrieval-ல தான் ஆரம்பிக்குது: சரியான passage கிடைக்கவே இல்லை, அதனால model அதை use பண்ண முடியல. **Retrieval-ஐ check பண்றது**-னா, fixed-ஆன test கேள்விகள் வச்சு, சரியான passages திரும்ப வருதான்னு அளக்கிறது. Final answer நல்லா இருக்கான்னு பாக்குறது தனி விஷயம்.

```flow
தப்பான answer -> சரியான passage top k-ல இருந்துச்சா?
சரியான passage top k-ல இருந்துச்சா? -[இல்லை]-> Retrieval problem | chunking, embeddings, hybrid search, query rewriting, filters
சரியான passage top k-ல இருந்துச்சா? -[இருந்துச்சு]-> Generation problem | prompt, grounding rules, citations, model தேர்வு
```

இந்த lesson-ல Kochi-ல இருக்குற ஒரு bank-ஓட கதையை follow பண்ணுவோம். அவங்க staff assistant circulars பத்தி நிறைய தப்பான answers கொடுத்துச்சு.

## இது எப்படி work ஆகுது

**Test set build பண்ணுங்க.** 30 முதல் 100 realistic கேள்விகளை சேருங்க. ஒவ்வொண்ணுக்கும் பதில் இருக்குற passage அல்லது passages-ஐ சேர்த்து வைங்க. முடிஞ்சா real user கேள்விகளை use பண்ணுங்க. Easy, hard, vague, பதிலே இல்லாத கேள்விகளும் இருக்கட்டும். மாற்றங்களை நியாயமா compare பண்ண, set-ஐ fixed-ஆ வச்சுக்கோங்க.

**Retrieval metrics.**

- **Recall at k**: எத்தனை சதவீத கேள்விகளுக்கு, top k results-ல குறைஞ்சது ஒரு சரியான passage வருது? Recall at 5 ஒரு common headline number. கறாரா சொன்னா, இந்த "குறைஞ்சது ஒண்ணு" version-ஐ hit rate-னும் சொல்லுவாங்க. ஒரு கேள்விக்கு பல சரியான passages இருந்தா, சில tools recall at k-வை அதுல எத்தனை கிடைச்சுதுங்குற சதவீதமா define பண்ணும்.
- **Precision at k** அல்லது **context precision**: Retrieve ஆன k passages-ல எத்தனை உண்மையிலேயே relevant? RAGAS-ஓட context precision, relevant ஆனவற்றை மேல rank பண்ணா கூடுதலா reward கொடுக்கும். Precision குறைவா இருந்தா prompts-ல noise நிறைஞ்சிடும்.
- **MRR** (mean reciprocal rank): சரியான passage-ஐ மேல கொண்டு வந்தா reward கொடுக்கும்.

**Answer metrics**, இதை தனியா அளக்கணும்:

- **Faithfulness**: Answer-ல இருக்குற claims-ஐ retrieve ஆன passages support பண்ணுதா?
- **Answer correctness**: எதிர்பார்த்த answer-ஓட match ஆகுதா?

RAGAS மாதிரி tools இதை compute பண்ணும், பெரும்பாலும் ஒரு model-ஐ judge-ஆ use பண்ணி. ஒரு sample-ஐ கையால check பண்ணுங்க.

**Split வச்சு diagnose பண்ணுங்க.** ஒரு answer தப்பா இருந்தா:

- சரியான passage retrieve ஆகல → retrieval-ஐ fix பண்ணுங்க (chunking, embeddings, hybrid search, query rewriting, filters);
- சரியான passage retrieve ஆச்சு, ஆனா answer தப்பு → generation-ஐ fix பண்ணுங்க (prompt, grounding, model).

**ஒவ்வொரு மாற்றத்துக்கும் run பண்ணுங்க.** Chunk size, embedding model, top-k மாத்தினா சில கேள்விகளுக்கு உதவலாம், சிலதை கெடுக்கலாம். Fixed set தான் மொத்த effect-ஐ காட்டும்.

**Metrics-க்கு ஒரு சின்ன worked example.** நாலு test கேள்விகள், ஒவ்வொண்ணுக்கும் top 5 results. முதல் சரியான passage எந்த இடத்துல இருக்குன்னு காட்டியிருக்கு:

| Question | First correct passage at | In top 5? | Reciprocal rank |
| --- | --- | --- | --- |
| Q1 | 1 | yes | 1.0 |
| Q2 | 3 | yes | 0.33 |
| Q3 | not found | no | 0 |
| Q4 | 2 | yes | 0.5 |

Recall at 5 = 4-ல 3 = 75%. MRR = (1.0 + 0.33 + 0 + 0.5) ÷ 4, கிட்டத்தட்ட 0.46.

**Test set-ஐ வேகமா build பண்றது.** Support tickets, search logs, chats-ல இருக்குற real கேள்விகள்ல இருந்து ஆரம்பிங்க. ஒவ்வொண்ணுக்கும், documents-ஐ தெரிஞ்ச ஒரு ஆள் பதில் இருக்குற passage-ஐ கண்டுபிடிச்சு, அதோட document, section-ஐ note பண்ணுவாங்க. முப்பது கேள்விகளை ஒரு மதியத்துல முடிச்சிடலாம். Documents-ஆல பதில் சொல்ல முடியாத கேள்விகளையும் சேருங்க. அதுக்கு expected passage-ஆ "none"-னு போடுங்க. அப்போ system "எனக்கு தெரியாது"ன்னு சொல்லுதான்னு check பண்ணலாம். ஒரு user தப்பான answer-ஐ report பண்ணும்போதெல்லாம் ஒரு புது கேள்வியை சேருங்க.

**Model-ஐ judge-ஆ use பண்றது.** RAGAS மாதிரி tools faithfulness, relevance-ஐ பெரிய அளவுல score பண்ண ஒரு model-ஐ use பண்ணும். இது உதவும், ஆனா perfect இல்லை. 20 examples-ஐ கையால score பண்ணி compare பண்ணுங்க. Judge மக்களோட அடிக்கடி disagree ஆனா, அதோட numbers-ஐ நம்புறதுக்கு முன்னாடி அதோட instructions-ஐ fix பண்ணுங்க.

**Metrics-ஐ code-ல.** ஒவ்வொரு test case-லயும் அதுக்கு பதில் இருக்குற passages-ஓட ids இருக்கும்; retriever rank பண்ணுன ids-ஐ திருப்பி கொடுக்கும்:

```python
import math

def metrics(cases, retrieve, k=5):
    """cases: list of (question, set_of_relevant_ids). Empty set = unanswerable."""
    recall = precision = mrr = ndcg = 0.0
    answerable = [c for c in cases if c[1]]
    for q, relevant in answerable:
        ranked = retrieve(q)[:k]
        hits = [1 if r in relevant else 0 for r in ranked]
        recall += any(hits)
        precision += sum(hits) / k
        mrr += next((1 / (i + 1) for i, h in enumerate(hits) if h), 0)
        dcg = sum(h / math.log2(i + 2) for i, h in enumerate(hits))
        ideal = sum(1 / math.log2(i + 2) for i in range(min(len(relevant), k)))
        ndcg += dcg / ideal
    n = len(answerable)
    return {"recall@k": recall / n, "precision@k": precision / n, "mrr": mrr / n, "ndcg@k": ndcg / n}
```

பதில் சொல்ல முடியாத cases-ஐ இந்த numbers-ல வேணும்னே விட்டிருக்கோம். அதை தனியா check பண்ணுங்க: final answer "தெரியாது"ன்னு சொல்லுதான்னு பாருங்க.

**Results-ஐ பிரிச்சு பாருங்க.** ஒரு overall recall பிரச்சனைகளை மறைச்சிடும். ஒவ்வொரு கேள்விக்கும் tag போடுங்க (exact code, vague, Hindi, multi-part, recent policy). அப்புறம் tag வாரியா recall report பண்ணுங்க. Ingestion மாத்தினதுக்கு அப்புறம் "recent policy" கேள்விகள்ல recall விழுந்தா, பெரும்பாலும் புது documents index ஆகலைன்னு அர்த்தம்.

```python
from collections import defaultdict

def by_tag(cases_with_tags, retrieve, k=5):
    groups = defaultdict(list)
    for q, rel, tag in cases_with_tags:
        groups[tag].append((q, rel))
    return {tag: metrics(cs, retrieve, k)["recall@k"] for tag, cs in groups.items()}
```

**சின்ன sets noisy-ஆ இருக்கும்.** 30 கேள்விகள்னா, ஒரு கேள்வி 3 points-ஐ விட அதிகம். 3 points மாற்றத்துக்கு கொண்டாடவும் வேண்டாம், பயப்படவும் வேண்டாம். எந்த கேள்விகள் flip ஆச்சு, ஏன்னு பாருங்க. Set-ஐ நேரம் போக போக பெருசாக்குங்க, முக்கியமா உங்களுக்கு முக்கியமான tags-ல.

**Model வச்சு கேள்விகளை draft பண்றது.** வேகமா ஆரம்பிக்க, ஒரு model-க்கு ஒரு passage-ஐ கொடுத்து, அதுக்கு பதில் சொல்ற ரெண்டு கேள்விகளை, ஒரு user பேசுற வார்த்தைகள்ல கேளுங்க. அப்புறம் ஒரு ஆள் ஒவ்வொண்ணையும் edit பண்ணுவாங்க அல்லது reject பண்ணுவாங்க, அந்த passage-ஐ expected answer-ஆ record பண்ணுவாங்க. இதை synthetic-னு mark பண்ணுங்க, logs-ல இருந்து real கேள்விகளை சேர்த்துட்டே இருங்க. Models passage-ஓட சொந்த வார்த்தைகளையே திரும்ப use பண்ணும், அதனால retrieval உண்மையை விட ஈஸியா தெரியும்.

**Retrieval-உம் answers-உம் சேர்த்து.** ஒவ்வொரு case-க்கும், retrieve ஆன ids, answer, verdicts-ஐ store பண்ணுங்க. அப்புறம் எந்த தப்பான answer-உம் ஒரே பார்வையில ரெண்டு bucket-ல ஒண்ணுல விழும்: சரியான passage இல்லை (retrieval problem) அல்லது இருக்கு (generation problem).

## ஒரு worked example

Kochi-ல ஒரு bank-ஓட internal assistant, 900 circulars-ல இருந்து staff கேள்விகளுக்கு பதில் சொல்லுது. Answers அடிக்கடி தப்பா இருக்குன்னு staff புகார் பண்றாங்க.

Team 60 கேள்விகளை எழுதுது, ஒவ்வொண்ணுக்கும் பதில் இருக்குற circular, paragraph-உடன். Results:

- recall at 5: 63%;
- answers-ஓட faithfulness: 0.92;
- correctness: 58%.

Faithfulness அதிகம், அதனால retrieve ஆன passages என்ன சொல்லுதோ model பெரும்பாலும் அதையே சொல்லுது. Recall குறைவு: சரியான passages அடிக்கடி வரவே இல்லை. Misses-ஐ பார்த்தப்போ, பெரும்பாலானவை circular numbers ("as per RBI/2026-27/41") சம்பந்தப்பட்டவை, அப்புறம் சமீபத்துல revise ஆன circulars, அங்க பழைய versions புதுசை விட மேல rank ஆகுது.

மாற்றங்கள்: circular numbers-க்கு keyword matching இருக்குற hybrid search, அப்புறம் superseded circulars-ஐ ஒதுக்குற ஒரு filter. அதே 60 கேள்விகள்ல அளந்தப்போ, recall at 5 87%-க்கும், correctness 81%-க்கும் ஏறுச்சு.

| Measure | Before | After hybrid search and the superseded filter |
| --- | --- | --- |
| Recall at 5 | 63% | 87% |
| Faithfulness | 0.92 | 0.93 |
| Correctness | 58% | 81% |

Model பிரச்சனையே இல்லை. அது தப்பான circulars-ல இருந்து, உண்மையா (faithfully) பதில் சொல்லிட்டிருந்துச்சு.

**Misses-ஐ படிக்கிறது.** Team numbers-ஓட நிக்கல. Top five-ல சரியான passage இல்லாத 22 கேள்விகளையும் படிச்சாங்க, காரணங்களா பிரிச்சாங்க: 9 கேள்விகள்ல circular numbers இருந்துச்சு, embedding search அதை exact-ஆ match பண்ண முடியல; 7 கேள்விகள்ல superseded circular, current-ஐ விட மேல retrieve ஆச்சு; 4 vague கேள்விகள்; 2-ல test set-லயே expected passage தப்பா இருந்துச்சு. ஒவ்வொரு காரணமும் வேற வேற fix-ஐ காட்டுச்சு. Test set-ஓட சொந்த தப்புகளை சரி பண்றதும் இந்த வேலையில சாதாரண விஷயம்.

## பொதுவா பண்ற தப்புகள்

- **Final answers-ஐ மட்டும் பாக்குறது.** Retrieval fail ஆச்சா, generation fail ஆச்சான்னு சொல்ல முடியாது.
- **Runs-க்கு நடுவுல test set-ஐ மாத்துறது.** Compare பண்ண அதை fixed-ஆ வைங்க.
- **பதில் இல்லாத கேள்விகள் இல்லாம இருக்கிறது.** Refusals test பண்ண அவை வேணும்.
- **Automatic judges-ஐ கண்மூடித்தனமா நம்புறது.** ஒரு sample-ஐ check பண்ணுங்க.
- **Precision சரியுறப்போ recall-ஐ மட்டும் optimise பண்றது.** ரெண்டையும் track பண்ணுங்க.
- **Easy கேள்விகள் மட்டும் இருக்குற test sets.** Real users கேக்குற மாதிரி vague, multi-part, பதில் இல்லாத கேள்விகளையும் சேருங்க.
- **Re-test பண்றதுக்கு முன்னாடி பல விஷயங்களை மாத்துறது.** ஒரு setting-ஐ மாத்துங்க, set-ஐ rerun பண்ணுங்க, numbers-ஐ record பண்ணுங்க, அப்புறம் அடுத்ததை மாத்துங்க.
- **Synthetic கேள்விகள் மட்டும்**, அவை documents-ஓட சொந்த வார்த்தைகளை use பண்றதால retrieval-ஐ நல்லா காட்டும்.
- **ஒரே ஒரு overall number.** Recall-ஐ கேள்வி வகை வாரியா பிரிச்சு பாருங்க.
- **பதில் இல்லாத கேள்விகளை recall-ஓட கலக்குறது**, அது ரெண்டு numbers-ஐயும் மறைச்சிடும்.

## ஒரு lighter check போதும்னா

- **ஒரு சின்ன prototype**: கையால check பண்ண பத்து கேள்விகள், retrieval பொதுவா work ஆகுதான்னு சொல்லிடும்.
- **அரிதா மாறுற collection**, launch-ல ஒரு கவனமான test, அப்புறம் spot checks போதும்.
- **Use பண்றதுக்கு முன்னாடி மக்கள் எப்பவும் source-ஓட verify பண்ற answers.**

## Demo-ல இருந்து production-க்கு

- **Test set-ஐ repository-ல வச்சுக்கோங்க**, கேள்வி வகை வாரியா tag போட்டு, ஒவ்வொரு retrieval மாற்றத்துக்கும் run பண்ணுங்க.
- **Recall, precision, MRR, nDCG-ஐ record பண்ணுங்க**, settings, index version-ஓட.
- **Report ஆன ஒவ்வொரு தப்பான answer-ஐயும்** புது கேள்வியா சேருங்க.
- **Model judge பண்ண scores-ஐ** மாசா மாசம் கையால spot-check பண்ணுங்க.
- **எந்த முக்கியமான tag-லயாவது recall விழுந்தா** alert வரணும்.

## Practice பண்ணுங்க

1. உங்க RAG app-க்கு 30 கேள்விகளை எழுதுங்க, ஒவ்வொண்ணுக்கும் சரியான passage-ஓட.

3. ஒரு retrieval மாற்றத்தை பண்ணி, அதே set-ல rerun பண்ணுங்க.
4. உங்க 30 கேள்விகளையும் வகை வாரியா tag பண்ணி, retrieval மாற்றத்துக்கு முன்னாடி, அப்புறம் tag வாரியா recall at 5-ஐ report பண்ணுங்க.
