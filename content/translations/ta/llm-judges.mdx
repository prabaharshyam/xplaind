## இது என்ன

**LLM judge** வேற ஒரு model-ஓட output-ஐ grade பண்ண சொல்லப்படுற ஒரு language model: "இந்த answer passages-ஓட faithful-ஆ இருக்கா? Reason-ஓட yes அல்லது no-ன்னு சொல்லு", அல்லது "இந்த reply-ஐ இந்த rubric-க்கு எதிரா 1-ல இருந்து 5 வரை rate பண்ணு". Code checks-ஆல முடியாத இடங்கள்ல, open-ended outputs-ஐ (summaries, explanations, replies) பெரிய அளவுல evaluate பண்ண judges வழி செய்யுது.

ஆனா judge-ஏ ஒரு model தான், அதுக்கும் errors, biases இருக்கு. அதோட scores-ஐ நம்புறதுக்கு முன்னாடி அதை check பண்ணணும்.

```flow
Case | ஒரு excerpt-உம் அதோட summary-உம் -> Code checks | word limit 150? citation இருக்கா? Exact, இலவசம்
Case -> Judge | "List unsupported statements, then SUPPORTED or UNSUPPORTED"
Judge -> Calibration | 80 summaries-ஐ ரெண்டு lawyers grade பண்ணாங்க; judge 74-ல ஒத்துப்போனுச்சு: 92.5%
Calibration -> இந்த rubric-க்கு நம்பகமானது
Judge -> Pairwise tests | A, B-யும் B, A-யும் காட்டுங்க; ஒத்துப்போற verdicts-ஐ மட்டும் வச்சுக்கோங்க
```

இந்த lesson, Chennai-ல ஒரு legal-tech startup தங்க judgment summaries-ல unsupported claims இருக்கான்னு அளக்குறதை follow பண்ணுது.

## இது எப்படி work ஆகுது

**Narrow, specific rubric எழுதுங்க.** மங்கலான scales-ஐ விட ("இந்த answer எவ்வளவு நல்லா இருக்கு, 1-ல இருந்து 10?"), ஒரு தடவைக்கு ஒரு தெளிவான கேள்விக்கு ("Passages ஆதரிக்காத ஏதாவது claim answer-ல இருக்கா?") judges நல்லா செய்யும். Yes அல்லது no, அல்லது சின்ன labelled scale-ஐ விரும்புங்க, முதல்ல ஒரு சின்ன reason கேளுங்க.

**Judge-க்கு தேவையானதை கொடுங்க.** கேள்வி, output, reference: faithfulness-க்கு retrieved passages, correctness-க்கு எதிர்பார்க்குற answer, compliance-க்கு policy.

**ஆட்களோட agreement-ஐ check பண்ணுங்க.** ஒருத்தர் அல்லது ரெண்டு பேரை 30-ல இருந்து 100 outputs-ஐ அதே rubric-ல grade பண்ண வைங்க. Judge-ஓட ஒப்பிடுங்க. Agreement குறைவா இருந்தா, வேறுபாடுகளை படிச்சு rubric அல்லது examples-ஐ சரி பண்ணுங்க. Judge-ஓட prompt அல்லது model-ஐ மாத்தினதுக்கு அப்புறம் திருப்பி check பண்ணுங்க.

**தெரிஞ்ச biases.**

- *Position bias*: ரெண்டு answers-ஐ ஒப்பிடும்போது, judges பெரும்பாலும் முதல்ல (அல்லது ரெண்டாவதா) காட்டுனதை விரும்பும். Positions-ஐ மாத்தி average எடுங்க.
- *Length bias*: நீளமான, அதிக விவரமான answers நல்லதா இல்லன்னாலும் அதிக scores வாங்கும்.
- *Self-preference*: models தங்க சொந்த குடும்பத்தோட outputs-ஐ அதிகமா rate பண்ணலாம்.
- *Leniency*: judges பெரும்பாலும் ரொம்ப தாராளமா இருக்கும்; தெளிவா மோசமான examples வச்சு calibrate பண்ணுங்க.

**Code முடிவு பண்ண முடியும்போது code-ஐ use பண்ணுங்க.** Exact values, JSON validity, required fields, word limits, citation இருக்கா, banned phrases: இவற்றை code-ஆல check பண்றது நல்லது, அது இலவசம், வேகம், எப்பவும் ஒரே மாதிரி.

**Cost.** Judges ஒவ்வொரு case-க்கும் model calls-ஐ சேர்க்கும். Agreement அதிகமா இருக்குற இடத்துல சின்ன models use பண்ணுங்க, judges-ஐ offline-ல அல்லது samples-ல ஓட்டுங்க.

**Biases-உம் அவற்றோட fixes-உம்:**

| Bias | எப்படி தெரியும் | Fix |
| --- | --- | --- |
| Position | முதல்ல காட்டுன answer-ஐ அதிக தடவை தேர்ந்தெடுக்கும் | ரெண்டு வரிசையிலயும் ஓட்டுங்க; ஒத்துப்போற verdicts-ஐ வச்சுக்கோங்க |
| Length | நீளமான answers-க்கு அதிக score | Code-ல word limit; rubric-ல length quality இல்லன்னு சொல்லுங்க |
| Self-preference | தன் குடும்பத்தோட outputs-ஐ அதிகமா rate பண்ணும் | வேற குடும்பத்தோட judge-ஐ use பண்ணுங்க, அல்லது ஆட்களோட ஒப்பிட்டு check பண்ணுங்க |
| Leniency | பெரும்பாலான outputs pass ஆகும் | தெளிவா மோசமான examples சேருங்க; verdict-க்கு முன்னாடி பிரச்சனைகளை கேளுங்க |

**Agreement-ஐ கணக்கிடுறது.** Yes-or-no judge-க்கு, agreement-ங்கிறது judge-ஓட label-உம் மனுஷனோட label-உம் ஒத்துப்போற cases-ஓட பங்கு. Rate-ஐ மட்டும் இல்ல, வேறுபாடுகளையும் பாருங்க: மக்கள் fail பண்ற outputs-ஐ judge pass பண்ணுதுன்னா, அது ரொம்ப தாராளம், உண்மையான பிரச்சனைகள் தப்பிச்சுடும். ரெண்டு வகை வேறுபாடுகளையும் தனித்தனியா track பண்ணுங்க, failures-ல அதிக agreement-ஐ இலக்கா வைங்க, ஏன்னா eval இருக்குறதே அவற்றை பிடிக்க தான்.

**Judge prompt-ஐ எழுதுறது.** அந்த ஒரு கேள்வியை சொல்லுங்க, reference material-ஐ கொடுங்க, pass, fail-ஐ ஒவ்வொண்ணுக்கும் ஒரு சின்ன example-ஓட define பண்ணுங்க, பதில் சொல்றதுக்கு முன்னாடி evidence-ஐ list பண்ண சொல்லுங்க. முதல்ல reason கேக்குறது verdicts-ஐ அதிக consistent-ஆ ஆக்கும், வேறுபாடுகளை படிக்கும்போது புரிஞ்சுக்க சுலபமாவும் ஆக்கும்.

**Judge model-ஐ தேர்ந்தெடுக்குறது.** Agreement level-ஐ நிர்ணயிக்க ஒரு வலுவான model-ல தொடங்குங்க, அப்புறம் அதே calibration set-ல ஒரு சின்ன, மலிவான model-ஐ try பண்ணுங்க. Agreement ரெண்டு மூணு points-க்குள்ள இருந்தா, வழக்கமான runs-க்கு சின்னதை use பண்ணி, spot checks-க்கு வலுவானதை வச்சுக்கோங்க. Judge-ஓட model version-ஐ மத்த dependency மாதிரி pin பண்ணுங்க: அமைதியான model update scores-ஐ நகர்த்தி, இந்த மாசம் numbers-ஐ போன மாசத்தோட ஒப்பிட முடியாம ஆக்கலாம்.

**Pipeline-ல judges எங்க பொருந்தும்.** முதல்ல code checks-ஐ ஓட்டி, அவற்றுல ஏற்கனவே fail ஆன outputs-க்கு judge-ஐ தவிர்த்துடுங்க, அது calls-ஐ மிச்சப்படுத்தும். Offline evals-ல ஒவ்வொரு case-லயும் judge-ஐ ஓட்டுங்க, online monitoring-க்கு live traffic-ஓட ஒரு சின்ன random sample-ல. Production-ல judge failures-ஐ ஒரு review queue-க்கு அனுப்புங்க, அங்க ஆட்கள் அவற்றை confirm பண்ணுவாங்க அல்லது மாத்துவாங்க, confirm ஆனவற்றை test set-ல சேருங்க.

**Code-ல ஒரு judge.** முதல்ல evidence-ஐயும் கடைசில verdict-ஐயும் structured output-ஆ கேளுங்க, அப்போ verdicts-ஐ எண்ணவும் reasons-ஐ படிக்கவும் சுலபம்:

```python
import json
import anthropic

client = anthropic.Anthropic()
JUDGE_MODEL = "claude-sonnet-5-5"           # pin a dated version where offered
JUDGE_PROMPT = """You check one thing: does the ANSWER contain any claim not supported by the PASSAGES?
Ignore style, length and tone.
PASS example: every number and fact in the answer appears in a passage.
FAIL example: the answer gives a fee the passages never mention.
Reply only with JSON: {"unsupported_claims": [...], "verdict": "pass" or "fail"}"""

def judge(question, passages, answer):
    msg = f"QUESTION:\n{question}\n\nPASSAGES:\n{passages}\n\nANSWER:\n{answer}"
    r = client.messages.create(model=JUDGE_MODEL, max_tokens=400, system=JUDGE_PROMPT,
                               messages=[{"role": "user", "content": msg}])
    text = "".join(b.text for b in r.content if b.type == "text")
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        return {"verdict": "error", "raw": text}       # count these; do not guess
```

உறுதியான shape வேணும்ன்னா அந்த lesson-ஓட structured-output features-ஐ use பண்ணுங்க; மேல இருக்குற fallback குறைஞ்சது உடைஞ்ச replies-ஐ மறைக்காம எண்ணுது.

**ஆட்களோட agreement, code-ல.** அதே cases-ல judge, மனுஷ labels-ஐ ஒப்பிட்டு, தற்செயலுக்கு சரி பண்ணுங்க:

```python
def agreement(human, judge):
    """Two equal-length lists of 'pass' / 'fail'."""
    n = len(human)
    observed = sum(h == j for h, j in zip(human, judge)) / n
    p_h, p_j = human.count("pass") / n, judge.count("pass") / n
    expected = p_h * p_j + (1 - p_h) * (1 - p_j)
    kappa = (observed - expected) / (1 - expected) if expected < 1 else 1.0
    missed = sum(h == "fail" and j == "pass" for h, j in zip(human, judge))
    return {"agreement": round(observed, 2), "kappa": round(kappa, 2), "failures_missed": missed}
```

Kappa கிட்டத்தட்ட 0.6-க்கு மேல இருந்தா பொதுவா பயன்படுத்தலாம், 0.8-க்கு மேல இருந்தா வலுவானது. `failures_missed`-ல உள்ள ஒவ்வொரு case-ஐயும் படிங்க: அவை தான் judge தப்பிக்க விட்டிருக்கும் பிரச்சனைகள்.

**Judge ஒரு model-உம் ஒரு prompt-உம்.** ரெண்டுல எதை மாத்துனாலும் உங்ககிட்ட ஒரு புது judge இருக்கு, அதோட scores பழையதோட ஒப்பிடத்தக்கவை இல்ல. ஒவ்வொரு score-ஓடயும் judge-ஓட model version-ஐயும் prompt version-ஐயும் store பண்ணுங்க, எதை மாத்துனாலும், புது numbers-ஐ நம்புறதுக்கு முன்னாடி calibration set-ல திருப்பி ஓட்டுங்க.

**Judges-ஓட வகைகள்.** Rubric உள்ள ஒரு general model-ஐ தவிர, specialised ones-உம் இருக்கு: outputs-ஐ score பண்ண train பண்ண reward models, ஒரே check-க்கு (toxicity, faithfulness) fine-tune பண்ண சின்ன classifiers, ரெண்டு answers-ல நல்லதை தேர்ந்தெடுக்குற comparison judges. Specialised judges ஒரு narrow வேலைக்கு மலிவு, அதிக consistent; general judges flexible, தொடங்க வேகம்.

**Judges தங்களுக்குள்ளயே ஒத்துப்போகாது.** ஒரே judge-ஐ ஒரே case-ல ரெண்டு தடவை ஓட்டுனா வேற verdicts தரலாம். உங்க calibration set-ல இதை அளங்க; சில percent-க்கு மேல மாறுச்சுன்னா, rubric-ஐ இறுக்குங்க, support இருக்குற இடத்துல temperature 0 use பண்ணுங்க, அல்லது நெருக்கமான cases-க்கு மூணு runs-ஓட majority-ஐ எடுங்க.

## ஒரு worked example

Chennai-ல ஒரு legal-tech startup court judgments-ஐ summarise பண்றாங்க. Summaries-ல unsupported claims இருக்கான்னு அளக்க விரும்புறாங்க.

- Judge prompt: "Here is a judgment excerpt and a summary. List any statement in the summary not supported by the excerpt. Then answer SUPPORTED or UNSUPPORTED."
- ரெண்டு lawyers 80 summaries-ஐ grade பண்றாங்க. Judge அவங்களோட 74-ல ஒத்துப்போகுது (92.5%).
- தனியா ஒரு comparison வேலையில (ரெண்டு summaries-ல எது நல்லது), judge 63% தடவை முதல்ல காட்டுனதையே தேர்ந்தெடுத்துச்சு. அவங்க ரெண்டு வரிசையையும் காட்டி, ஒத்துப்போற verdicts-ஐ மட்டும் எண்ண மாறுறாங்க.
- Judge நீளமான summaries-ஐ அதிகமா rate பண்றதையும் கண்டுபிடிக்கிறாங்க. 150-word limit-க்கு ஒரு code check-ஐயும், rubric-ல length quality இல்லன்னு ஒரு line-ஐயும் சேக்குறாங்க.

Faithfulness judge இப்போ ஒவ்வொரு model அல்லது prompt மாற்றத்துலயும் ஓடுது, lawyers மாசத்துக்கு 20 cases-ஐ spot-check பண்றாங்க.

| 63% தடவை முதல் summary-ஐ தேர்ந்தெடுத்துச்சு | ரெண்டு வரிசை, ஒத்துப்போற verdicts மட்டும் | நியாயமான ஒப்பீடுகள் |

## பொதுவா பண்ற தப்புகள்

- **ஆட்களோட agreement-ஐ check பண்றதுக்கு முன்னாடியே judge-ஐ நம்புறது.**
- **மங்கலான 1-to-10 scales.**
- **Position, length bias-ஐ கண்டுக்காம விடுறது.**
- **Code check பண்ணக்கூடிய விஷயங்களுக்கு judge-ஐ use பண்றது.**
- **Judge-ஐ மாத்துனதுக்கு அப்புறம் திருப்பி check பண்ணவே பண்ணாம இருக்குறது.**
- **வேற வேற judge versions-ஓட scores-ஐ ஒப்பிடுறது.** முதல்ல recalibrate பண்ணுங்க.
- **Parse ஆகாத judge replies-ஐ மறைக்கிறது.** அவற்றை errors-ஆ எண்ணி, பாருங்க.
- **Agreement-ஐ மட்டும் report பண்றது**, chance-corrected agreement அல்லது தவறவிட்ட failures-ஐ இல்ல.

## LLM judge-ஐ use பண்ணக்கூடாத நேரங்கள்

- **Code முடிவு பண்ண முடியும்**: exact values, formats, word counts, required fields, banned phrases.
- **ஒரு reference answer இருக்கு, அது சரியா பொருந்தணும்**, ஒரு number அல்லது category மாதிரி.
- **ஆட்கள் பொறுப்பேத்துக்க வேண்டிய high-stakes verdicts**, medical அல்லது legal correctness மாதிரி: experts-ஐ use பண்ணுங்க, judge-ஐ அவங்க review-ஓட முன்னுரிமையை தீர்மானிக்க மட்டும்.
- **நீங்க இன்னும் agreement-ஐ check பண்ணல**: பண்ணுற வரை, judge-ஓட score ஒரு ஊகம்.

## Demo-ல இருந்து production-க்கு

- **Judge-ஓட model, prompt versions-ஐ pin பண்ணி** ஒவ்வொரு score-ஓடயும் store பண்ணுங்க.
- **50-ல இருந்து 100 human-graded cases-ஓட ஒரு calibration set** வச்சுக்கோங்க, ஒவ்வொரு judge மாற்றத்துக்கும் திருப்பி ஓட்டுங்க.

- **Judge cost-க்கு தனி budget வைங்க**, எல்லாத்தையும் judge பண்றதுக்கு பதிலா live traffic-ஓட sample எடுங்க.
