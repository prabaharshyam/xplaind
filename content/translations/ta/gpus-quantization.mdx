## இது என்ன

உங்க சொந்த GPU-ல ஒரு language model-ஐ run பண்றது பெரும்பாலும் **memory** பத்தின கேள்வி தான். மூணு விஷயங்கள் அதுக்காக போட்டி போடுது, இன்னொரு விஷயம் speed-ஐ முடிவு பண்ணுது:

- **Weights.** 16-bit precision-ல ஒவ்வொரு parameter-உம் 2 bytes எடுக்கும்; அதனால ஒரு 14B model எதுவும் செய்ய ஆரம்பிக்கிறதுக்கு முன்னாடியே சுமார் 28 முதல் 30 GB வேணும்.
- **KV cache.** ஒவ்வொரு layer-லயும் ஒவ்வொரு token-க்கும், model ரெண்டு vectors-ஐ store பண்ணுது: ஒரு key, ஒரு value. இந்த **KV cache** ஒவ்வொரு request-ஓட நீளத்தோடயும், ஒரே நேரத்துல run ஆகுற requests எண்ணிக்கையோடயும் வளரும்.
- **Working space.** Intermediate results (activations), CUDA runtime, engine buffers. இந்த lesson அதுக்காக GPU-ல சுமார் 10%-ஐ spare-ஆ வச்சுக்குது.
- **Speed.** ஒவ்வொரு புது token-க்கும் எல்லா weights-ஐயும் memory-ல இருந்து ஒரு தடவை படிக்கணும். அதனால **memory bandwidth**, அதாவது GPU ஒரு second-க்கு எத்தனை gigabytes படிக்க முடியும்ங்குறது, பொதுவா raw compute-ஐ விட generation speed-ஐ அதிகமா கட்டுப்படுத்தும்.

**Quantization** weights-ஐயும், சில நேரம் cache-ஐயும், குறைவான bits-ல store பண்ணுது, 16-க்கு பதிலா 8 அல்லது 4 மாதிரி. Cache-க்கு அதிக memory மிஞ்சும், ஒரு token-க்கு குறைவான bytes படிக்கப்படும், அதனால generation பெரும்பாலும் வேகமாகும். Cost என்னன்னா கொஞ்சம் quality இழப்பு; அதை உங்க சொந்த task-ல measure பண்ணணும்.

NVIDIA L40S மாதிரி ஒரு 48 GB GPU, 40 layers, 8 key-value heads, head size 128 இருக்குற ஒரு 14B model-ஐ (Qwen3-14B-ஓட shape) serve பண்ணும்போது என்ன effect-னு பாருங்க. 10% spare போக, சுமார் 43 GB use பண்ணலாம்; ஒவ்வொரு request-உம் 4,000 tokens வச்சிருக்கு.

| Precision | Weights | KV cache-க்கு மிச்சம் | 4,000 tokens-ஓட requests |
|---|---|---|---|
| 16-bit weights, 16-bit cache | சுமார் 30 GB | சுமார் 13 GB | சுமார் 20 |
| 4-bit weights, 16-bit cache | சுமார் 10 GB | சுமார் 33 GB | சுமார் 50 |
| 4-bit weights, 8-bit cache | சுமார் 10 GB | சுமார் 33 GB | சுமார் 100 |

Rule இது தான்: **weights entry cost-ஐ fix பண்ணுது; எத்தனை users fit ஆவாங்கன்னு cache முடிவு பண்ணுது.**

## இது எப்படி work ஆகுது

### Weights

Weights-க்கான memory ≈ parameters × ஒரு parameter-க்கான bytes.

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B முதல் 8B | சுமார் 14 முதல் 16 GB | சுமார் 7 முதல் 9 GB | சுமார் 4 முதல் 6 GB |
| 14B | சுமார் 28 முதல் 30 GB | சுமார் 14 முதல் 16 GB | சுமார் 8 முதல் 10 GB |
| 32B | சுமார் 64 GB | சுமார் 32 முதல் 34 GB | சுமார் 18 முதல் 20 GB |
| 70B | சுமார் 140 GB | சுமார் 70 GB | சுமார் 37 முதல் 40 GB |

4-bit ஏன் ஒரு parameter-க்கு அரை byte-ஐ விட அதிகம்? Weights-ஓட ஒவ்வொரு சின்ன group-உம் (பெரும்பாலும் 128) ஒரு scale-ஐயும் (பெரும்பாலும் ஒரு zero point-ஐயும்) store பண்ணுது; இது ஒரு weight-க்கு சுமார் 0.15 bits சேர்க்குது. அதோட input embeddings-உம் output layer-உம் பெரும்பாலும் 16-bit-லயே இருக்கும்: பெரிய vocabulary இருக்குற ஒரு 8B model-க்கு, அது சுமார் 1 billion parameters, அதாவது 2 GB. Plan பண்றதுக்கு முன்னாடி checkpoint-ஓட உண்மையான file size-ஐ check பண்ணுங்க.

### KV cache

ஒவ்வொரு token-க்கும், ஒவ்வொரு layer-உம் ஒவ்வொரு **key-value head**-க்கும் ஒரு key, ஒரு value store பண்ணுது:

ஒரு token-க்கான cache = 2 × layers × key-value heads × head size × ஒரு value-க்கான bytes

Numbers-ஐ model-ஓட `config.json`-ல இருந்து படிங்க: `num_hidden_layers`, `num_key_value_heads`, `head_dim` (அல்லது `hidden_size`-ஐ `num_attention_heads`-ஆல வகுத்தது). பெரும்பாலான modern models **grouped-query attention** use பண்ணுது: நிறைய attention heads கொஞ்சம் key-value heads-ஐ share பண்ணுது. ஒரு common 8B shape-ல 32 attention heads இருக்கு, ஆனா 8 key-value heads மட்டும் தான்; அதனால attention heads-ஐ use பண்ணா உங்க estimate நாலு மடங்கு பெருசா வரும்.

அப்புறம் **tokens in flight**-ஆல பெருக்குங்க: peak active requests × ஒரு request-க்கான tokens. Peak-ஐ ஒரு load test-ல இருந்தோ traffic logs-ல இருந்தோ எடுங்க, ஒருபோதும் average-ஐ இல்ல.

ரெண்டு gotchas. Qwen3.5 மாதிரி **hybrid** models, சுமார் நாலு layers-ல ஒண்ணுல மட்டும் தான் full attention use பண்ணுது, அதனால அந்த layers-ஐ மட்டும் எண்ணுங்க. அதோட **mixture-of-experts** models-க்கு அவங்களோட எல்லா experts-க்கும் memory வேணும், ஒவ்வொரு token-உம் சில experts-ஐ மட்டும் use பண்ணாலும்.

### அந்த memory-ஐ engine என்ன பண்ணுது

vLLM மாதிரி serving engines ரெண்டு ideas use பண்ணுது. **PagedAttention** ஒவ்வொரு request-ஓட cache-ஐயும் சின்ன blocks-ல store பண்ணுது, request வளர வளர மட்டும் blocks சேர்க்குது; அதனால ஒரு சின்ன request, சாத்தியமான மிக நீளமான request-க்கான இடத்தை reserve பண்ணாது. **Continuous batching** ஒவ்வொரு step-லயும், மத்த requests முடிய முடிய, புது requests-ஐ running batch-ல சேர்க்குது; அதனால GPU busy-ஆவே இருக்கும். இது ரெண்டுமே memory-ஐ உருவாக்காது, அதனால மேல இருக்குற கணக்கு தான் limit.

Start-up-ல, vLLM cache size-ஐ tokens-ல log பண்ணுது, உங்க maximum request length-க்கான "maximum concurrency"-ஐயும். அந்த line-ஐ உங்க estimate கூட compare பண்ணுங்க; உங்க setup-க்கு அது தான் உண்மை. vLLM v0.34.0-ல இருந்து, `--gpu-memory-utilization` set பண்ணலைன்னா எல்லா free memory-ஐயும் use பண்ணும்; அதனால வேற ஒரு process GPU-ஐ share பண்ணும்போது மட்டும் ஒரு share-ஐ set பண்ணுங்க.

### Prefill-உம் decode-உம்

ஒவ்வொரு request-க்கும் ரெண்டு phases இருக்கு, ஒவ்வொண்ணுக்கும் வேற வேற limits.

- **Prefill** முழு prompt-ஐயும் ஒரே தடவையில படிச்சு cache-ஐ நிரப்புது. ஒரு prompt token-க்கு சுமார் 2 × parameters operations பண்ணுது: ஒரு 14.8B model-க்கும் ஒரு 6,000-token prompt-க்கும், சுமார் 180 trillion. Prefill-ஐ **compute** கட்டுப்படுத்துது, அது **time to first token**-ஐ முடிவு பண்ணுது; அதனால நீளமான prompts-னா first tokens மெதுவா வரும்.
- **Decode** ஒரு step-க்கு ஒரு token எழுதுது. ஒவ்வொரு step-உம் எல்லா weights-ஐயும் ஒவ்வொரு request-ஓட cache-ஐயும் படிக்குது, ஆனா ஒரு byte-க்கு கொஞ்சம் தான் maths பண்ணுது. அதை **memory bandwidth** கட்டுப்படுத்துது, அது **tokens per second**-ஐ முடிவு பண்ணுது.

ஒரு request-க்கான quick ceiling: bandwidth ÷ weights-ஓட bytes. ஒரு L40S 864 GB/s படிக்கும்; அதனால ஒரு 10 GB 4-bit model ஒரு request-க்கு அதிகபட்சம் சுமார் 86 tokens per second வரை போகலாம்; ஒரு 30 GB 16-bit model அதிகபட்சம் சுமார் 29. உண்மையான numbers இதை விட குறைவா இருக்கும். Serving affordable-ஆ இருக்க காரணம் batching தான்: weights-ஐ ஒரு தடவை படிச்சா batch-ல இருக்குற எல்லா requests-க்கும் serve ஆகும்; அதனால compute அல்லது cache memory தீர்ந்து போற வரை, batch size கூட மொத்த throughput-உம் ஏறும். விலை என்னன்னா ஒவ்வொரு user-உம் ஒரு token-க்கு கொஞ்சம் அதிகமா wait பண்ணணும்; அதனால concurrency-ஐ உங்க latency budget-ஐ பார்த்து tune பண்ணுங்க.

### Quantization formats

- **FP8** (8-bit floating point). பெரும்பாலான models-க்கு கிட்டத்தட்ட 16-bit quality, பாதி memory, FP8 units இருக்குற GPUs-ல வேகமான maths. பெரும்பாலும் முதல்ல try பண்ண வேண்டியது இது தான்.
- **AWQ, GPTQ** (4-bit integers, weights மட்டும்). Weight memory-ல சுமார் கால் பங்கு, கூட மேல சொன்ன overheads, மிதமான quality இழப்போட. ஏற்கனவே quantize பண்ண ஒரு checkpoint-ஐ download பண்ணுங்க, முடிஞ்சா model maker-ஏ quantize பண்ணதை.
- **NVFP4, MXFP4** (4-bit floating point). Blackwell GPUs-ல வேகமா இருக்கும்; இன்னும் புதுசு, குறைவான அளவுல தான் test ஆகியிருக்கு.
- **bitsandbytes NF4.** Transformers-ல load time-ல quantize பண்ணுது. Experiments-க்கும் QLoRA-க்கும் ஈஸி, ஆனா serve பண்ண இன்னும் மெதுவா இருக்கும்.
- **GGUF.** llama.cpp-ஓட file format; Ollama, LM Studio இது மேல தான் build ஆகியிருக்கு; laptops, CPUs, Apple Silicon-க்கு. ஒரு Q4_K_M file ஒரு weight-க்கு சுமார் 4.8 முதல் 4.9 bits use பண்ணுது, அதனால ஒரு 8B model சுமார் 5 GB. Speed bandwidth-ஐ follow பண்ணும்: ஒரு laptop 80 GB/s-ல memory படிச்சா, சுமார் 16 tokens per second தான் ceiling.
- **8-bit KV cache.** Cache-ஐ FP8-ல store பண்ணா அது பாதியாகும். மத்த எந்த change மாதிரியும் இதோட quality-யையும் measure பண்ணுங்க.

Fit ஆகுற மிக உயர்ந்த precision-ல இருந்து கீழே இறங்குங்க: 16-bit, அப்புறம் FP8, அப்புறம் 4-bit. ஒவ்வொண்ணுக்கும், உங்க eval-ஐயும் ஒரு சின்ன load test-ஐயும் run பண்ணி, peak-ல quality, memory, speed-ஐ record பண்ணுங்க. உங்க client எழுத்துப்பூர்வமா ஏத்துக்குற quality இழப்பு இருக்குற options-ல மிக cheap-ஆனதை தேர்ந்தெடுங்க.

### Code-ல ஒரு memory planner

```python
def memory_plan(cfg, params_billion, weight_bits=16, kv_bits=16,
                context_tokens=4000, concurrent=20, gpu_gb=48, spare=0.10):
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights_gb = params_billion * weight_bits / 8          # rough: real 4-bit files are larger
    kv_token_mb = 2 * cfg["num_hidden_layers"] * kv_heads * head_dim * kv_bits / 8 / 1e6
    kv_gb = kv_token_mb * context_tokens * concurrent / 1e3
    usable = gpu_gb * (1 - spare)
    fits = weights_gb + kv_gb <= usable
    max_requests = int((usable - weights_gb) * 1e3 / (kv_token_mb * context_tokens))
    return round(weights_gb, 1), round(kv_token_mb, 3), round(kv_gb, 1), fits, max_requests

# The shape of a common 8B model; in real use, load the dict from config.json
cfg = {"num_hidden_layers": 32, "num_attention_heads": 32, "num_key_value_heads": 8, "head_dim": 128}
print(memory_plan(cfg, 8, gpu_gb=24))                  # (16.0, 0.131, 10.5, False, 10)
print(memory_plan(cfg, 8, weight_bits=8, kv_bits=8, gpu_gb=24))  # (8.0, 0.066, 5.2, True, 51)
```

16-bit-ல, 4,000 tokens-ஓட 20 requests-க்கு 16 GB weights-க்கு மேல சுமார் 10.5 GB cache வேணும்: ஒரு 24 GB card-க்கு இது ரொம்ப அதிகம், அது 10 requests-ஐ மட்டும் தான் வச்சுக்கும். 8-bit-ல அவை fit ஆகும்; ஆனா embeddings 16-bit-லயே இருக்குறதால, உண்மையான FP8 file சுமார் 9 GB.

### ஒரு quantized model-ஐ load பண்ணி serve பண்றது

Transformers-ல quick experiments-க்கு:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("your-org/your-8b-instruct",
                                             quantization_config=bnb, device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

Serving-க்கு, fast quantized kernels இருக்குற ஒரு engine-ஐ use பண்ணுங்க. vLLM ஒரு quantized checkpoint-ஓட config-ல இருந்து method-ஐ படிச்சுக்கும்:

```bash
vllm serve your-org/your-14b-instruct-awq --max-model-len 8192 --kv-cache-dtype fp8
```

ஒரு 16-bit model-ஐ load time-ல FP8-க்கு quantize பண்ண, vLLM v0.34.0 `--quantization fp8_per_tensor` use பண்ணுது; வெறும் `fp8` இனிமே இதை பண்ணாது. `--max-model-len` ஒரு request-ஓட நீளத்தை cap பண்ணுது; உங்க users உண்மையில அனுப்புற அளவுக்கு அதை set பண்ணுங்க.

### Quality இழப்பை measure பண்றது

ஒவ்வொரு precision-லயும் golden set-ஐ run பண்ணி, overall மட்டும் இல்லாம ஒவ்வொரு slice-க்கும் compare பண்ணுங்க. Quantization பொதுவா முதல்ல நீளமான reasoning, maths, code, அவ்வளவா common இல்லாத languages-ஐ தான் பாதிக்கும்; அதனால Hindi, Telugu அல்லது Tamil cases-ஐ English-ல இருந்து தனியா score பண்ணுங்க. முக்கியமான ஒவ்வொரு slice-உம் ஒத்துக்கிட்ட limit-க்குள்ள இருந்தா மட்டும் தான் ஒரு precision-ஐ வச்சுக்குங்க.

## ஒரு worked example

Hyderabad-ல ஒரு analytics firm, 200 staff-க்காக invoices-ல இருந்து fields-ஐ extract பண்ற ஒரு model-ஐ self-host பண்ண விரும்புறாங்க. Prompts-உம் replies-உம் சேர்ந்து 6,000 tokens வரை போகும். p95 time to first token 3 seconds-க்கு கீழே இருக்கணும். கீழே இருக்குற quality scores-உம் latencies-உம் method-ஐ காட்டுறதுக்கான illustrative numbers; memory figures கணக்கு போட்டது.

**1. Peak-ஐ measure பண்ணுங்க.** ஒரு busy நாளோட logs-ஐ replay பண்ணா **80 active requests**-ல peak ஆகுது (average சுமார் 35). 80-க்கு size பண்ணுங்க.

**2. Model.** 14.8 billion parameters, 40 layers, 8 key-value heads, head size 128 இருக்குற ஒரு 14B instruct model. ஒரு token-க்கான cache: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes, சுமார் 0.16 MB. ஒரு 6,000-token request சுமார் 0.98 GB வச்சுக்கும்; peak-க்கு சுமார் 79 GB cache வேணும்.

**3. Original proposal.** 16-bit-ல tensor parallelism-ஓட ரெண்டு H100 80 GB GPUs. Use பண்ணக்கூடிய memory 2 × 72 = 144 GB; weights சுமார் 30 GB எடுக்கும், சுமார் 114 GB மிஞ்சும், அதாவது சுமார் 116 requests. Fit ஆகுது, ஆனா ஒரு மணி நேரத்துக்கு 2 × ₹362 = ₹724 ஆகும், ஒரு GPU fail ஆனா service நின்னுடும்.

**4. Quantize பண்ணுங்க.** Maker-ஓட 4-bit AWQ checkpoint சுமார் 10 GB. 500 உண்மையான invoices-ல field accuracy: 16-bit-ல 95.1%, 4-bit-ல 94.6%, கூட FP8 cache-உம் சேர்த்தா 94.5%. Client-ஓட limit 94.0%, அதனால ரெண்டுமே pass.

**5. L40S cards-ல fit பண்ணுங்க.** ஒரு L40S-ல சுமார் 43 GB use பண்ணலாம். 4-bit weights-ஓட, 33 GB மிஞ்சும். 16-bit cache-ஓட, அதுல 6,000 tokens-ஓட 33 requests வைக்கலாம்; அதனால peak-க்கு 3 GPUs வேணும், spare-ஆ நாலாவது ஒண்ணு. FP8 cache-ஓட, சுமார் 67 வைக்கலாம்; அதனால ரெண்டு GPUs peak-ஐ (134) தாங்கும், ஒண்ணு fail ஆனா மூணாவது ஒண்ணு service-ஐ ஓட வைக்கும்.

**6. Speed-ஐ check பண்ணுங்க.** மூணு L40S cards-ல 80 concurrent requests-ஓட load test பண்ணா, p95 time to first token 1.8 seconds, budget-க்குள்ள. ஒவ்வொரு user-ஓட tokens-உம் H100s-ஐ விட மெதுவா வரும், ஏன்னா அவைக்கு சுமார் நாலு மடங்கு bandwidth இருக்கு; ஆனா target meet ஆகுது.

## பொதுவா பண்ற தப்புகள்

- **Weights-க்கு மட்டும் size பண்றது.** எத்தனை users fit ஆவாங்கன்னு peak-ல இருக்குற cache தான் முடிவு பண்ணுது.
- **Average traffic-ல இருந்து size பண்றது.** Measure பண்ண peak-ஐ use பண்ணுங்க, இல்லைன்னா மிக busy-ஆன காலையில service fail ஆகும்.
- **Cache formula-ல key-value heads-க்கு பதிலா attention heads-ஐ use பண்றது,** அல்லது 2-ங்குற factor-ஐ விட்டுடுறது.
- **4-bit-ஐ ஒரு parameter-க்கு சரியா அரை byte-னு எடுத்துக்கிறது.** Scales-உம் 16-bit embeddings-உம் சுமார் 10 முதல் 50% சேர்க்கும்.
- **Slice வாரியா evals இல்லாம quantize பண்றது.** ஒரு English-only average, இந்திய மொழிகள், maths, code-ல இருக்குற இழப்புகளை மறைச்சுடும்.
- **ஒரே GPU-ல fit ஆகுற model-ஐ split பண்றது.** Copies இன்னும் simple-ஆனது, இன்னும் நல்லா scale ஆகும், failures-ஐ தாங்கும்.
- **FP8 எல்லா இடத்துலயும் fast-னு நினைக்கிறது.** A100-ல FP8 units இல்ல; GPU generation-ஐ check பண்ணுங்க.
- **தேவையை விட ரொம்ப அதிகமா maximum context-ஐ set பண்றது.** ஒரு பெரிய request நிறைய சின்ன requests-ஐ வெளியே தள்ளிடலாம்.

## GPUs பத்தி யோசிக்க தேவையில்லாத சமயங்கள்

- **ஒரு hosted API-ஐயோ** client-ஓட cloud model service-ஐயோ use பண்ணும்போது.
- **CPUs-ல சின்ன models,** embedding models, classifiers, அல்லது ஒரு laptop-ல 4-bit GGUF demo மாதிரி.
- **குறைவான அல்லது திடீர்னு ஏறி இறங்குற volume,** அங்க மாசம் முழுக்க rent பண்ண ஒரு GPU, per token pay பண்றதை விட அதிகமா செலவாகும்.

## Demo-ல இருந்து production-க்கு

- **Memory-ஐ plan பண்ணுங்க**: weights, peak cache, working space-க்கு; engine-ஓட start-up log-ல அதை confirm பண்ணுங்க.
- **Golden set-ஐ run பண்ணுங்க**: ஒவ்வொரு precision change-லயும், language, task வாரியா.
- **உண்மையான GPUs-ல load test பண்ணுங்க**: scale-ல rent பண்றதுக்கு முன்னாடி, peak-ல first-token time-ஐயும் errors-ஐயும் பாத்துக்கிட்டே.
- **குறைஞ்சது ஒரு spare GPU-ஐ வச்சுக்குங்க**: ஒரு failure-ஓ upgrade-ஓ service-ஐ நிறுத்தாம இருக்க.
- **Production-ல cache usage-ஐயும் queue length-ஐயும் monitor பண்ணுங்க**, cache நிரம்புறதுக்கு முன்னாடியே alert பண்ணுங்க.
