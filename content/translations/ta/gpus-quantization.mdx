## இது என்ன

ஒரு language model-ஐ சொந்த hardware-ல run பண்றது பெரும்பாலும் **GPU memory**, **memory bandwidth** பத்தின கேள்வி:

- **Weights** GPU memory-ல fit ஆகணும். 16-bit precision-ல, ஒவ்வொரு parameter-க்கும் 2 bytes ஆகும்.
- **KV cache**, ஒவ்வொரு active request-ஓட ஒவ்வொரு token-க்குமான attention data-வை store பண்ணும்; context length, concurrency அதிகமாக அதுவும் வளரும்.
- **Generation speed** பெரும்பாலும், ஒவ்வொரு புது token-க்கும் memory-ல இருந்து weights எவ்வளவு வேகமா படிக்க முடியுதுங்குறதால தான் கட்டுப்படுது, raw compute-ஆல இல்ல.

**Quantization**, weights-ஐ (சில நேரம் cache-ஐயும்) 16-க்கு பதிலா 8 அல்லது 4 மாதிரி குறைவான bits-ல store பண்ணும்; memory குறையும், பெரும்பாலும் speed ஏறும், கொஞ்சம் quality இழப்போட.

| ஒரு 48 GB GPU, ஒரு 14B model | Weights | KV cache | Serve ஆகுற users |
|---|---|---|---|
| 16-bit weights | 28 GB | 20 GB | சுமார் 25 |
| 4-bit weights | 9 GB | 35 GB | சுமார் 45 |

Weights-க்கான memory ≈ parameters × ஒரு parameter-க்கான bytes. KV cache ≈ ஒரு request-க்கு tokens × active requests × ஒரு token-க்கான cache size.

```flow
dir: LR
Weights-ஐ 4-bit-க்கு quantize பண்ணுங்க -> Weights 28 GB-ல இருந்து 9 GB-க்கு சுருங்கும் -> KV cache-க்கு அதிக இடம் -> 25-க்கு பதிலா சுமார் 45 users
```

இந்த lesson-ல, Hyderabad-ல ஒரு analytics firm, self-hosted extraction model-க்கு GPUs-ஐ size பண்றதை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Weights.** Memory ≈ parameters × ஒரு parameter-க்கான bytes. ஒரு 7B model: 16-bit-ல சுமார் 14 GB, 8-bit-ல 7 GB, 4-bit-ல 3.5 முதல் 4 GB. ஒரு 70B model: 16-bit-ல சுமார் 140 GB, அதனால பல GPUs; 4-bit-ல சுமார் 35 முதல் 40 GB.

**KV cache.** Context-ல இருக்குற ஒவ்வொரு token-க்கும், ஒவ்வொரு layer-உம் keys, values store பண்ணும். ஒரு நடுத்தர model-க்கு இது ஒரு token-க்கு பத்து முதல் சில நூறு kilobytes வரை இருக்கலாம். அதை context length-ஆலயும் concurrent requests-ஆலயும் பெருக்குங்க: 8,000 tokens-ஓட 32 requests-க்கு weights-ஐ விட அதிக memory தேவைப்படலாம். vLLM மாதிரி engines இந்த memory-ஐ திறமையா manage பண்ணும், ஆனா இல்லாத memory-ஐ அவங்களால உருவாக்க முடியாது. குறைவான maximum contexts, quantize பண்ண caches, அதிக requests fit ஆக உதவும்.

**GPU தேர்வுகள்.** Data-centre GPUs முக்கியமா memory size (24 GB முதல் 80 GB, அதுக்கு மேலயும்), memory bandwidth, FP8 மாதிரி low-precision formats-க்கான support-ல வேறுபடும். சின்ன models பெரும்பாலும் cheap-ஆன 24 முதல் 48 GB cards-ல நல்லா run ஆகும்; பெரிய models-க்கு high-memory cards-உம் அவற்றுக்கு நடுவுல வேகமான links-உம் வேணும். ஒரு GPU-வை சுத்தி design பண்றதுக்கு முன்னாடி, உங்க cloud இந்திய regions-ல என்ன offer பண்ணுது, quotas என்னன்னு check பண்ணுங்க.

**ஒரு model-ஐ பரப்புறது.** Tensor parallelism ஒவ்வொரு layer-ஐயும் ஒரே machine-ல இருக்குற GPUs முழுக்க பிரிக்கும்; வேகமான GPU-to-GPU links வேணும். ஒரு சின்ன model-ஓட பல copies-ஐ, ஒவ்வொண்ணையும் தனி GPU-ல run பண்றது எளிமையானது; model ஒரு card-ல fit ஆகும்போது throughput-ஐ இன்னும் நல்லா scale பண்ணும்.

**Quantization methods.** Weight-only methods (4-bit-ல GPTQ, AWQ மாதிரி) கொஞ்சமா quality இழந்து memory-ஐ சுருக்கும்; புதிய GPUs-ல FP8, பாதி memory-ல கிட்டத்தட்ட 16-bit quality கொடுக்கும். எப்பவும் உங்க evals-ஐ திரும்ப run பண்ணுங்க: maths, code, இந்திய மொழி text மாதிரி சில tasks, averages காட்டுறதை விட அதிக இழக்கலாம்.

**Throughput vs latency.** பெரிய batches overall-ஆ அதிக tokens per second கொடுக்கும், ஆனா ஒவ்வொரு user-க்கும் response மெதுவா வரும். உங்க latency budget-க்கு ஏத்த மாதிரி batch size, concurrency-ஐ tune பண்ணுங்க.

**Weight memory ஒரு பார்வையில்:**

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B | சுமார் 14 GB | சுமார் 7 GB | சுமார் 4 GB |
| 14B | சுமார் 28 GB | சுமார் 14 GB | சுமார் 8 முதல் 9 GB |
| 32B | சுமார் 64 GB | சுமார் 32 GB | சுமார் 18 முதல் 20 GB |
| 70B | சுமார் 140 GB | சுமார் 70 GB | சுமார் 35 முதல் 40 GB |

**KV cache-ஐ estimate பண்றது.** ஒரு model-ஓட configuration அதோட layers, key-value heads, head size-ஐ list பண்ணும். ஒரு token-க்கான cache சுமார் 2 (keys, values) × layers × key-value heads × head size × ஒரு value-க்கான bytes. அதை நீங்க allow பண்ற context length-ஆலயும், peak active requests-ஆலயும் பெருக்குங்க; அந்த peak-ஐ user numbers-ல இருந்து guess பண்ணாம, load test-ல அளந்து எடுங்க. Engine-ஓட working space-க்கு கொஞ்சம் memory-ஐ free-ஆ விடுங்க. GPUs வாங்கறதுக்கோ reserve பண்றதுக்கோ முன்னாடி இந்த கணக்கை போட்டா, மிக costly-ஆன sizing தப்புகளை தடுக்கலாம்.

**ஒரு quantization-ஐ தேர்ந்தெடுக்கிறது.** உங்க budget-க்குள்ள fit ஆகுற அதிகபட்ச precision-ல இருந்து ஆரம்பிங்க. GPUs support பண்ணா FP8 try பண்ணுங்க, அப்புறம் 8-bit, அப்புறம் 4-bit weight-only methods. ஒவ்வொண்ணுக்கும் உங்க சொந்த eval-ஐயும் ஒரு short load test-ஐயும் run பண்ணி, peak-ல quality, memory, tokens per second, latency-ஐ record பண்ணுங்க. Quality இழப்பை உங்க client எழுத்துபூர்வமா ஏத்துக்கிற, மிக cheap-ஆன option-ஐ எடுங்க.

**Code-ல ஒரு memory planner.** Model-ஓட configuration-ஐ படிச்சு, உங்க traffic-க்கு weights + KV cache-ஐ estimate பண்ணுங்க:

```python
import json

def memory_gb(config_path, params_billion, weight_bits=16, kv_bits=16, context_tokens=4000, concurrent=20):
    cfg = json.load(open(config_path))
    layers = cfg["num_hidden_layers"]
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights = params_billion * 1e9 * weight_bits / 8
    kv_per_token = 2 * layers * kv_heads * head_dim * kv_bits / 8
    kv_total = kv_per_token * context_tokens * concurrent
    return {"weights GB": round(weights / 1e9, 1),
            "KV per token KB": round(kv_per_token / 1e3, 1),
            "KV total GB": round(kv_total / 1e9, 1),
            "total with 10% overhead GB": round((weights + kv_total) * 1.1 / 1e9, 1)}

# memory_gb("config.json", params_billion=8, weight_bits=8)
```

Grouped-query attention இருக்குற ஒரு வழக்கமான 8B model-க்கு (32 layers, 8 key-value heads, head size 128), cache 16-bit-ல ஒரு token-க்கு சுமார் 131 KB; அதனால 4,000 tokens-ஓட 20 requests-க்கு, weights-க்கு மேல கிட்டத்தட்ட 10 GB வேணும்.

**Quantize பண்ண model-ஐ load பண்றது.** Transformers-ல quick experiments-க்கு, 4-bit loading சில வரிகள்ல முடியும்:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("org/model-8b-instruct", quantization_config=bnb,
                                             device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

Serving-க்கு, வேகமான quantized kernels உள்ள ஒரு engine-ஐ தேர்ந்தெடுங்க: vLLM, ஏற்கனவே AWQ அல்லது GPTQ-ல quantize பண்ண checkpoints-ஐ load பண்ணலாம், இல்ல support பண்ற GPUs-ல FP8-க்கு quantize பண்ணலாம் (`vllm serve org/model-8b-instruct --quantization fp8`).

**Cache-ஐயும் quantize பண்ணுங்க.** நீளமான context workloads-ல KV cache, weights-ஐ விட பெரிசா வளரலாம். vLLM மாதிரி engines அதை 8-bit-ல store பண்ணி, memory-ஐ கிட்டத்தட்ட பாதியா குறைக்கலாம், பெரும்பாலும் கொஞ்சம் தான் quality இழப்போட. Weight quantization மாதிரியே இதையும் test பண்ணுங்க.

**உங்க task-ல quality இழப்பை அளவுங்க.** ஒவ்வொரு precision-லயும் golden set-ஐ run பண்ணி, overall மட்டும் இல்லாம category வாரியா ஒப்பிடுங்க. Quantization முதல்ல நீளமான reasoning, maths, அதிகம் பேசப்படாத மொழிகளை பாதிக்கும்; அதனால இந்திய மொழி cases-ஐ தனியா check பண்ணுங்க. Drop ஏத்துக்கக்கூடிய இடத்துல மட்டும் அந்த precision-ஐ வச்சுக்கோங்க.

**Speed என்பது memory மட்டும் இல்ல.** Generation பெரும்பாலும் memory bandwidth-ஆல கட்டுப்படுது: ஒவ்வொரு token-உம் weights-ஐ ஒரு தடவை படிக்கும், அதனால சின்ன weights வேகமான tokens-ஐ குறிக்கலாம். ஆனா சில quantized formats, பொருந்துற kernels இல்லாத பழைய GPUs-ல மெதுவா run ஆகும். உங்க உண்மையான hardware-ல tokens per second, time to first token-ஐ benchmark பண்ணுங்க.

## ஒரு நாள், ஒரு example

Hyderabad-ல ஒரு analytics firm, 200 concurrent users, 6,000 tokens வரை prompts-ஓட, ஒரு extraction model-ஐ self-host பண்ண விரும்புது.

Candidate: ஒரு 14B instruct model. 16-bit-ல weights-க்கு சுமார் 28 GB வேணும். 200 requests × 6,000 tokens-க்கான KV cache estimate ஒரு card-ஐ விட ரொம்ப அதிகம், ஆனா load tests-ல உண்மையான concurrency சராசரியா 40 active requests தான். 48 GB GPU-ல 4-bit AWQ weights-ஓட (சுமார் 9 GB), cache-க்கு சுமார் 35 GB மிச்சம்: இந்த model-ஓட configuration-ல, அந்த context length-ல சுமார் 40 முதல் 50 active requests-க்கு போதும்.

Evals: 16-bit field accuracy 95.1% score பண்ணுது; 4-bit 94.6%. ஏத்துக்கப்பட்டது.

Plan: மூணு 48 GB GPUs, ஒவ்வொண்ணும் 4-bit model-ஓட தன் சொந்த copy-ஐ ஒரு load balancer-க்கு பின்னாடி run பண்ணும்; அளந்த peak-க்கு ஏத்த size, ஒரு GPU headroom-ஓட. இது, tensor parallelism-ஓட 16-bit model-ஐ run பண்ணுற ரெண்டு 80 GB GPUs-ங்குற அசல் proposal-ஓட செலவுல சுமார் மூணுல ஒரு பங்கு, இந்த workload-க்கு better throughput-ஓட.

| Option | GPUs | Field accuracy | Relative cost |
| --- | --- | --- | --- |
| Tensor parallelism-ஓட 16-bit | ரெண்டு 80 GB | 95.1% | 3 |
| 4-bit AWQ, மூணு copies | மூணு 48 GB | 94.6% | 1 |

## பொதுவா பண்ற தப்புகள்

- **Weights-க்கு மட்டும் size பண்றது.** Concurrency-ஐ முடிவு பண்றது KV cache.
- **Evals இல்லாம quantize பண்றது.** உங்க tasks, மொழிகள்ல இழப்பை அளவுங்க.
- **ஒரே GPU-ல fit ஆகுற model-ஐ பிரிக்கிறது.** பெரும்பாலும் copies, tensor parallelism-ஐ விட நல்லா scale ஆகும்.
- **ஒரு GPU type கிடைக்கும்னு எடுத்துக்கிறது.** Regional availability, quotas-ஐ சீக்கிரமே check பண்ணுங்க.
- **தேவைக்கு ரொம்ப மேல maximum context வைக்கிறது.** இது cache memory-ஐ வீணாக்கும்; users உண்மையா அனுப்புறதுக்கு ஏத்த மாதிரி வைங்க.
- **KV estimates-ல grouped-query attention-ஐ மறக்கிறது**; attention heads இல்ல, key-value heads-ஐ use பண்ணுங்க.
- **Users இந்திய மொழிகள்ல எழுதும்போது, English-only tests-ல quantization-ஐ judge பண்றது.**
- **4-bit எப்பவும் வேகம்னு நினைக்கிறது.** உங்க GPU-ல benchmark பண்ணுங்க.

## GPUs பத்தி யோசிக்க தேவையில்லாத சமயங்கள்

- **Hosted API-ஐ use பண்றது**, அல்லது client-ஓட cloud model service-ஐ.
- **CPUs-ல சின்ன models**, GPU இல்லாமலே போதுமான வேகத்துல run ஆகுற embeddings அல்லது classifiers மாதிரி.
- **குறைவான volume**, GPU-வை மணி நேர கணக்குல rent பண்றது API calls-ஐ விட costly-ஆ இருக்கும்போது.

## Demo-ல இருந்து production-க்கு

- **Memory-ஐ plan பண்ணுங்க**: weights, peak concurrency-ல KV cache, overhead, headroom-ஓட.
- **Precision-ஐயும் quantization method-ஐயும்** release file-ல record பண்ணுங்க.
- **ஒவ்வொரு precision மாற்றத்துலயும் golden set-ஐ run பண்ணுங்க**, category, மொழி வாரியா.
- **வேகத்தை benchmark பண்ணுங்க**, பெரிய அளவுல வாங்கறதுக்கோ rent பண்றதுக்கோ முன்னாடி உண்மையான GPUs-ல.
