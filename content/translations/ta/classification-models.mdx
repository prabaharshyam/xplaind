## இது என்ன

**Classification** ஒரு category-ஐ predict பண்ணும்: fraud அல்லது genuine, churn ஆகுமா இல்ல இருக்குமா, அஞ்சு complaint types-ல எது. பெரும்பாலான classifiers ஒரு **probability** அல்லது score-ஐ கொடுக்கும்; ஒரு **threshold** அதை decision-ஆ மாத்தும் ("probability 0.3-க்கு மேல இருந்தா fraud-ன்னு flag பண்ணு").

Common models: **logistic regression** (probabilities கொடுக்கிற linear model, explain பண்ண எளிது), decision trees, random forests, gradient boosting, neural networks.

```flow
Features | amount, merchant, time, device -> Classifier -> 0.0-ல இருந்து 1.0 வரை score
0.0-ல இருந்து 1.0 வரை score -[0.3-க்கு கீழ, review threshold]-> Allow
0.0-ல இருந்து 1.0 வரை score -[0.3-க்கும் 0.9-க்கும் இடையில]-> ஒரு analyst review பண்றாங்க
0.0-ல இருந்து 1.0 வரை score -[0.9-க்கு மேல, block threshold]-> Block, fast appeal-ஓட
```

இந்த lesson-ல Pune-ல ஒரு payments company, fraud rules-ஐ ஒரு classifier வச்சு மாத்துறதை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Logistic regression.** Linear regression மாதிரி தான், ஆனா weighted sum ஒரு function வழியா போய் 0-க்கும் 1-க்கும் இடையில ஒரு probability-ஆ squeeze ஆகும். Coefficients எந்த features எந்த class பக்கம் தள்ளுதுன்னு காட்டும்.

**Confusion matrix.** ஒரு குறிப்பிட்ட threshold-க்கு, true positives (flag ஆன fraud), false positives (flag ஆன genuine), false negatives (miss ஆன fraud), true negatives-ஐ count பண்ணுங்க. எல்லா metric-உம் இந்த நாலு numbers-ல இருந்து தான் வருது.

**Precision and recall.** Precision: flag ஆன cases-ல எத்தனை உண்மையிலேயே positive. Recall: உண்மையான positives-ல எத்தனை flag ஆச்சு. Threshold-ஐ குறைச்சா recall ஏறும், precision குறையும்; ஏத்துனா எதிர்மாறா நடக்கும்.

**Threshold-ஐ தேர்ந்தெடுக்கிறது.** Errors-க்கு ரூபாய் values போடுங்க. ஒரு missed fraud-க்கு average-ஆ ₹15,000 cost, ஒரு false alarm-ஐ investigate பண்ண ₹200 analyst நேரம்னா, அதிக fraud-ஐ பிடிக்க நிறைய false alarms-ஐ ஏத்துக்கலாம். Capacity-யையும் பாருங்க: analysts ஒரு நாளைக்கு 500 cases review பண்ண முடியும்னா, சுமார் 500-ஐ flag பண்ற மாதிரி threshold-ஐ set பண்ணலாம்.

**Imbalanced classes.** Positives rare-ஆ இருக்கும்போது (0.5% fraud), accuracy useless: "never fraud"ன்னு predict பண்ணா 99.5% score கிடைக்கும். Precision, recall, precision-recall curve, ROC AUC use பண்ணுங்க. Techniques: rare class-ல errors-ஐ அதிகமா count பண்ற class weights, sampling methods, training-க்கு போதுமான positive examples.

**Calibration.** Model 0.3-ன்னு சொன்னா, அந்த score-ல fraud சுமார் 30% நேரம் நடக்குதா? Well-calibrated probabilities, thresholds-ஐயும் business rules-ஐயும் நம்பக்கூடியதா ஆக்கும்.

**Multi-class.** ரெண்டுக்கு மேல categories இருந்தா, எந்த classes எந்த classes-ஓட குழம்புதுன்னு பார்க்க confusion matrix-ஐ பாருங்க.

**Common classifiers compare:**

| Model | Strengths | Weaknesses | எப்போ முதல் choice-ஆ நல்லது |
| --- | --- | --- | --- |
| Logistic regression | Fast, explain பண்ணலாம், ஓரளவு calibrated probabilities | Complex interactions-ஐ miss பண்ணும் | Credit மாதிரி decisions-ஐ explain பண்ண வேண்டியிருக்கும்போது |
| Decision tree | Draw பண்றதும் explain பண்றதும் எளிது | Overfit ஆகும், stable இல்ல | Teaching அல்லது simple rules |
| Random forest | Robust, குறைவான tuning | பெருசு, slow | Tables-ல ஒரு strong baseline |
| Gradient boosting | Tables-ல பெரும்பாலும் most accurate | Tuning வேணும், explain பண்றது குறைவு | Tabular data-ல fraud, churn, risk |
| Neural network | Text, images, ரொம்ப பெரிய data | நிறைய data வேணும், explain பண்றது கஷ்டம் | Unstructured inputs |

**ஒரு நல்ல workflow.** ஒரு simple baseline-ஓட ஆரம்பிங்க, உதாரணம்: இப்போ இருக்குற rules அல்லது logistic regression; அப்போ "better"ன்னா என்னன்னு தெரியும். Data-வை time வச்சு split பண்ணுங்க. Class weights-ஓட ஒரு strong model-ஐ train பண்ணுங்க. Accuracy இல்ல, precision, recall, PR AUC வச்சு compare பண்ணுங்க. Costs-ஐயும் capacity-யையும் வச்சு threshold-ஐ தேர்ந்தெடுங்க. Calibration-ஐ check பண்ணுங்க. அப்புறம் result-ஐ ரூபாய்லயும் operational terms-லயும் (ஒரு நாளைக்கு alerts மாதிரி) report பண்ணுங்க.

**Model-ஓட தப்புகளை படிக்கிறது.** Threshold-ஐ தேர்ந்தெடுத்த பிறகு, 50 false positives-ஐயும் 50 false negatives-ஐயும் கையால படிங்க. Patterns சீக்கிரம் தெரிய வரும்: festival season-ல வர்ற genuine spikes fraud-ன்னு flag ஆகுறது, அல்லது training data பார்க்காத ஒரு புது fraud pattern. ஒவ்வொரு pattern-உம் ஒரு fix-ஐ சொல்லும்: "days to Diwali" மாதிரி ஒரு feature, இன்னும் சமீபத்திய training data, அல்லது ஒரு குறிப்பிட்ட case-க்கு ஒரு rule. Model எவ்வளவு அடிக்கடி தப்பு பண்ணுதுன்னு metrics சொல்லும்; ஏன்னு cases-ஐ படிச்சா தான் தெரியும்.

**ஒரு baseline-ஐயும் ஒரு strong model-ஐயும், ஒழுங்கா compare பண்றது.** 1% fraud இருக்குற synthetic transactions, time வச்சு split (முதல் 80% training-க்கு):

```python
import numpy as np
from sklearn.datasets import make_classification
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import average_precision_score, confusion_matrix

X, y = make_classification(n_samples=30_000, n_features=15, n_informative=8,
                           weights=[0.99], class_sep=1.0, random_state=3)
cut = int(0.8 * len(y))                                   # pretend rows are in time order
X_tr, X_te, y_tr, y_te = X[:cut], X[cut:], y[:cut], y[cut:]

logit = make_pipeline(StandardScaler(), LogisticRegression(class_weight="balanced", max_iter=2000))
gbm = HistGradientBoostingClassifier(class_weight="balanced", max_iter=300, learning_rate=0.05, random_state=3)
for name, model in [("logistic", logit), ("boosting", gbm)]:
    model.fit(X_tr, y_tr)
    print(name, "PR AUC", round(average_precision_score(y_te, model.predict_proba(X_te)[:, 1]), 3))
```

`class_weight="balanced"`, training-ல ஒவ்வொரு fraud case-ஐயும் பல genuine cases-க்கு சமமா count பண்ண வைக்கும்; அதனால model வெறுமனே "never fraud"ன்னு கத்துக்காது.

**Calibrate பண்ணி, அப்புறம் ரூபாய்ல threshold-ஐ தேர்ந்தெடுங்க.** Class weights probabilities-ஐ கோணலாக்கும்; calibration அதை சரி பண்ணும்:

```python
from sklearn.calibration import CalibratedClassifierCV

cal = CalibratedClassifierCV(HistGradientBoostingClassifier(max_iter=300, learning_rate=0.05, random_state=3),
                             method="isotonic", cv=3).fit(X_tr, y_tr)
p = cal.predict_proba(X_te)[:, 1]

COST_FN, COST_FP = 15_000, 200            # missed fraud, analyst review
t = COST_FP / (COST_FP + COST_FN)         # flag when expected loss from missing exceeds review cost
tn, fp, fn, tp = confusion_matrix(y_te, p >= t).ravel()
print(f"threshold {t:.3f}: caught {tp}, missed {fn}, false alarms {fp}")
print(f"cost of errors ₹{fn * COST_FN + fp * COST_FP:,}")
```

Calibrated probabilities இருந்தா, best threshold costs-ல இருந்தே நேரா வரும்: ஒரு case-ஓட fraud chance-ஐ ₹15,000-ஆல பெருக்கினா ₹200-ஐ விட அதிகமா வந்தா அதை flag பண்ணுங்க.

**Capacity limits rule-ஐ மாத்தும்.** Analysts ஒரு நாளைக்கு 300 cases மட்டும் review பண்ண முடியும்னா, score வச்சு sort பண்ணி மேல இருக்குற 300-ஐ எடுங்க; threshold-ல இல்ல, அந்த budget-ல recall-ஐ அளவுங்க.

**தனித்தனி decisions-ஐ explain பண்ணுங்க.** Logistic model-க்கு, ஒவ்வொரு feature-ஓட contribution அதோட coefficient × (scaled) value. Boosted trees-க்கு, permutation importance எந்த features overall-ஆ முக்கியம்னு காட்டும், SHAP மாதிரி tools தனி predictions-ஐ explain பண்ணும். Credit, insurance decisions-க்கு customers-க்கும் regulators-க்கும் இந்த மாதிரி explanations அடிக்கடி தேவைப்படும்.

## ஒரு worked example

Pune-ல ஒரு payments company-க்கு ஒரு மாசத்துக்கு 20 lakh UPI merchant transactions; அதுல சுமார் 0.3% பின்னாடி fraud-ன்னு confirm ஆகுது.

1. Baseline: அவங்க rules 40% fraud-ஐ பிடிக்குது, ஒரு மாசத்துக்கு 6,000 alerts-ஓட.
2. Class weights-ஓட ஒரு gradient-boosted classifier, ஆறு மாச data-ல train பண்ணி, அடுத்த மாசத்துல test பண்ணது.
3. ஒரு மாசத்துக்கு 6,000 alerts தர்ற threshold-ல (analysts-ஓட capacity), அது 68% fraud-ஐ பிடிக்குது.
4. மாசா மாசம் fraud சுமார் 6,000 cases (20 lakh-ல 0.3%). 68%-ஐ பிடிக்கிறதுன்னா, 6,000 alerts-ல சுமார் 4,080 உண்மையான fraud: precision சுமார் 68%, rules-க்கு 40%.
5. Business view: ஒவ்வொரு மாசமும் சுமார் 1,680 கூடுதல் frauds பிடிபடுது; சராசரி loss ₹9,000-ன்னா, அதே analyst team-ஓட மாசத்துக்கு சுமார் ₹1.5 crore மிச்சம்.

ரெண்டாவதா, இன்னும் அதிகமான ஒரு threshold-ஐயும் set பண்றாங்க; score ரொம்ப அதிகமா இருக்கும்போதும், precision 98%-ஐ தாண்டும்போதும் மட்டும் transactions-ஐ தானா block பண்ணும், merchants-க்கு ஒரு fast appeal route-ஓட.

**Risk committee-க்கு explain பண்றது.** Committee gradient boosting பத்தி கேக்கல. மூணு கேள்விகள் கேட்டாங்க: analysts-க்கு வேலை அதிகமாகுமா, genuine merchants பாதிக்கப்படுவாங்களா, எவ்வளவு மிச்சமாகும்? Team சொன்ன பதில்: இன்னைக்கு இருக்குற அதே alerts எண்ணிக்கை, precision 40%-க்கு பதிலா சுமார் 68% (analysts-ஓட நேரம் ரொம்ப குறைவா வீணாகும்), precision 98%-ஐ தாண்டுற score-க்கு மேல மட்டும் automatic block, appeals நாலு மணி நேரத்துக்குள்ள பதில், rules miss பண்ண fraud-ல மாசத்துக்கு சுமார் ₹1.5 crore பிடிபடும். Merchant category, city வாரியா model-ஓட performance-ஐயும் காட்டினாங்க, ஏன்னா average-ல நல்லா இருந்து சின்ன kirana merchants-க்கு மோசமா இருக்குற model, ஒரு fairness-க்கும் business-க்கும் ஒரு problem-ஆ ஆயிருக்கும். History குறைவான புது merchants-க்கு அது கொஞ்சம் weak-ஆ இருந்துச்சு; அதனால புது merchants-ஐ அவங்களோட முதல் மாசம் automatic blocking-க்கு பதிலா review-க்கு route பண்ணாங்க.

## பொதுவா பண்ற தப்புகள்

- **Imbalanced data-ல accuracy-ஐ report பண்றது.** Precision, recall, PR curves use பண்ணுங்க.
- **Default 0.5 threshold-ஐ use பண்றது.** Costs-ஐயும் capacity-யையும் வச்சு தேர்ந்தெடுங்க.
- **Time-based data-ல random rows-ல test பண்றது.** உண்மையான use மாதிரி, ஒரு பிந்தைய period-ல test பண்ணுங்க.
- **Calibration-ஐ புறக்கணிக்கிறது.** Decisions-க்கு use பண்ற scores, அவை சொல்றதை உண்மையிலேயே குறிக்கணும்.
- **எல்லா actions-க்கும் ஒரே threshold.** Review-க்கும் automatic blocking-க்கும் வேற வேற precision வேணும்.

- **Baseline இல்லாதது.** இப்போ இருக்குற rules அல்லது ஒரு simple model-ஓட compare பண்ணாம, புது model worth-ன்னு உங்களால காட்ட முடியாது.
- **Time-ordered data-ல random splits**, இது எதிர்காலத்தை leak பண்ணும்.
- **Calibrate பண்ணாம, class-weighted probabilities-ஐ உண்மையான probabilities-ஆ use பண்றது.**
- **Review capacity-யை புறக்கணிக்கிறது**: மூணு பேர் இருக்குற team-க்கு ஒரு நாளைக்கு 5,000 cases-ஐ flag பண்ற threshold ஒரு solution இல்ல.

## ஒரு simple rule model-ஐ விட better-ஆ இருக்கிறது எப்போ

- **ரொம்ப குறைவான positive examples**, கத்துக்க போதாது: expert rules-ஓட ஆரம்பிச்சு labels-ஐ collect பண்ணுங்க.
- **ஒரு தெளிவான rule ஏற்கனவே work ஆகுது**, உதாரணம்: stolen-ன்னு report ஆன cards-ஐ block பண்றது.
- **Decisions-ஐ ஒரே வாக்கியத்துல explain பண்ணணும்**, ஒரு குட்டி scorecard-ஏ அந்த bar-ஐ எட்டும்.

## Demo-ல இருந்து production-க்கு

- **Time வச்சு split பண்ணி**, மிக சமீபத்திய period-ல test பண்ணுங்க.
- **Costs-ல இருந்து thresholds set பண்றதுக்கு முன்னாடி calibrate** பண்ணுங்க.
- **Business-ஓட agree பண்ணி, costs அல்லது capacity-ல இருந்து thresholds-ஐ set பண்ணி**, அவற்றை மறுபடி மறுபடி பாருங்க.
- **Labels வரும்போது precision, recall-ஐ segment வாரியா monitor** பண்ணுங்க.
- **Customers அல்லது regulators கேக்கக்கூடிய ஒவ்வொரு decision-க்கும் explanations-ஐ** வச்சிருங்க.

## Practice பண்ணுங்க

Google-ஓட classification module-ஐ படிச்சு முடிங்க.

1. ஒரு public imbalanced dataset-ல (credit card fraud அல்லது churn), logistic regression-ஐயும் ஒரு tree-based model-ஐயும் train பண்ணி, held-out data-ல test பண்ணுங்க.
2. Threshold-க்கு எதிரா precision-ஐயும் recall-ஐயும் plot பண்ணி, நீங்க assume பண்ற costs-ல இருந்து ஒரு threshold-ஐ தேர்ந்தெடுங்க.
3. உங்க threshold-ல confusion matrix-ஐ report பண்ணி, ரூபாய்ல explain பண்ணுங்க.
4. COST_FN-ஐ ₹5,000-க்கும் ₹50,000-க்கும் மாத்தி, மறுபடி run பண்ணி, threshold-உம் false alarms எண்ணிக்கையும் எப்படி மாறுதுன்னு எழுதுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு threshold-ஐ costs-ஐயும் capacity-யையும் வச்சு justify பண்ணவும், rare events-ல accuracy ஏன் ஏமாத்துதுன்னு explain பண்ணவும் முடியும்.
