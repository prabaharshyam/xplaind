## இது என்ன

**Debugging** என்பது ஒரு program நீங்க எதிர்பார்த்ததை விட வேற ஏதோ பண்றதுக்கு காரணம் என்னன்னு கண்டுபிடிச்சு, அந்த காரணத்தை சரி பண்றது. Bug program-ஐ crash ஆக்கலாம், தப்பான number தரலாம், இல்லன்னா உங்க laptop-ல work ஆகி server-ல fail ஆகலாம்.

Beginners பெரும்பாலும் guess பண்ணி debug பண்றாங்க: ஒரு line-ஐ மாத்து, மறுபடி run பண்ணு, இன்னொண்ணை மாத்து. சின்ன bugs-க்கு இது work ஆகும், நிஜமான bugs-ல மணிக்கணக்கை வீணாக்கும். அனுபவமுள்ள engineers ஒரு முறையை use பண்றாங்க. சுலபமான bugs-ல அது வேகமில்ல, ஆனா எப்பவும் முடியும், ஒண்ணை எப்படி track பண்ணுவீங்கன்னு interviewers கேக்கும்போது அவங்க கேக்க விரும்புறதும் இதுதான்.

## இது எப்படி work ஆகுது

```flow
title: Debugging loop
அதை reproduce பண்ணு | ஒவ்வொரு தடவையும் fail ஆகுற சின்ன input -> Error-ஐ படி | traceback-ஐ கீழ இருந்து மேல
Error-ஐ படி -> ஒரு guess உருவாக்கு | இது நடக்கணும்னா என்ன உண்மையா இருக்கணும்?
ஒரு guess உருவாக்கு -> குறுக்கு | print, breakpoint, search-ஐ பாதியாக்கு
குறுக்கு -[guess தப்பு]-> ஒரு guess உருவாக்கு
குறுக்கு -[காரணம் கிடைச்சுது]-> அறிகுறியை இல்ல, காரணத்தை fix பண்ணு
அறிகுறியை இல்ல, காரணத்தை fix பண்ணு -> Fix இல்லாம fail ஆகுற ஒரு test சேரு
```

**Reproduce.** Bug-ஐ ஒவ்வொரு தடவையும் trigger பண்ற மிக சின்ன input-ஐ கண்டுபிடிங்க. "அது சில நேரம் fail ஆகுது"ங்கறது "CSV-ல amount காலியா இருந்தா fail ஆகுது"ன்னு ஆகும். நம்பகமான reproduction பாதி வேலை.

**Error-ஐ படிங்க.** Python traceback கீழ இருந்து மேல படிக்கப்படும்:

```text
Traceback (most recent call last):
  File "report.py", line 31, in <module>
    print(monthly_total(rows))
  File "report.py", line 12, in monthly_total
    total = total + row["amount"]
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

கடைசி line தான் error: ஒரு number-ஓட ஒரு string-ஐ கூட்ட try பண்ணீங்க. அதுக்கு மேல இருக்குற line அது நடந்த இடம். அதுக்கு மேல இருக்குற lines program அங்க எப்படி வந்துச்சுன்னு காட்டும்.

**குறுக்குங்க.** இந்த error நடக்க என்ன உண்மையா இருக்கணும்னு கேட்டு, அதை check பண்ணுங்க. வேகமானதுல இருந்து முழுமையானது வரை மூணு tools:

| Tool | எப்படி | எதுக்கு நல்லது |
| --- | --- | --- |
| `print(repr(x))` | முக்கிய இடங்கள்ல values-ஐ print பண்றது | Quick checks; `repr` quotes-ஐயும் types-ஐயும் காட்டும் |
| `breakpoint()` | Pause பண்ணி debugger-ல பார்க்கிறது | தப்பாகுற நேரத்துல எல்லா variables-ஐயும் பார்க்க |
| Editor debugger | Click பண்ணி breakpoints வச்சு, step பண்ணி, values-ஐ watch பண்றது | நீளமான investigations |
| Logging | Context-ஓட `logging.debug(...)` | Server-ல மட்டும் தெரியுற bugs |
| `git bisect` | Commits வழியா binary search | "போன வாரம் work ஆச்சே" |

**Debugger.** ஒரு line-ல `breakpoint()` போட்டு program-ஐ run பண்ணுங்க. அது அங்க pause ஆகும், நீங்க `p row` type பண்ணி ஒரு variable-ஐ print பண்ணலாம், `n` அடுத்த line-ஐ run பண்ண, `s` ஒரு function-க்குள்ள step பண்ண, `c` continue பண்ண. Guess பண்றதுக்கு பதிலா, முக்கியமான நேரத்துல இருக்குற நிஜ state-ஐ பார்க்கிறீங்க.

**Search-ஐ பாதியாக்குங்க.** 200 lines pipeline தப்பான total தந்தா, நடுவுல இருக்குற value-ஐ check பண்ணுங்க. அங்க சரியா இருக்கா? அப்போ bug ரெண்டாவது பாதியில. தப்பா? முதல் பாதியில. சில checks-ல அந்த line கிடைச்சிடும். `git bisect` commits முழுக்க இதையே பண்ணும்: ஒரு நல்ல commit-ஐயும் ஒரு மோசமான commit-ஐயும் mark பண்ணுங்க, அதை உடைச்ச மாற்றத்துக்கு Git உங்களை கூட்டிட்டு போகும்.

**காரணத்தை fix பண்ணுங்க.** Fail ஆகுற line-ஐ `try/except`-ல சுத்துறது ஒரு அறிகுறியை மறைக்கும்; தப்பான data இன்னும் அங்கேயே இருக்கும். தப்பான value எங்க இருந்து வருதோ அங்க fix பண்ணுங்க.

**நிரூபிங்க.** உங்க fix இல்லாம fail ஆகி, fix-ஓட pass ஆகுற ஒரு test எழுதுங்க.

**AI apps-ல bugs.** ஒரு LLM feature தப்பான பதில் தந்தா, அதே முறை தான், traceback-க்கு பதிலா ஒரு trace-ஓட. அந்த request-ஓட trace-ஐ திறந்து, ஒவ்வொரு step-ஐயும் வரிசையா check பண்ணுங்க: கேள்வி சரியா rewrite ஆச்சா, retrieval சரியான passage-ஐ கண்டுபிடிச்சுதா, prompt-ல அது இருந்துச்சா, model அதை use பண்ணுச்சா? தப்பா தெரியுற முதல் step-ல தான் தோண்டணும்.

## ஒரு worked example

Imran-ஓட Pune-ல இருக்குற ஒரு pharmacy chain-க்கான மாதாந்திர sales report, ஒரு store-க்கு ₹0 காட்டுது, ஆனா dashboard ₹4.2 lakh காட்டுது.

**Reproduce.** அவர் அதே export file-ஓட, அக்டோபருக்கான report-ஐ தன் laptop-ல ஓட்டுறாரு. அதே result: Kothrud store-க்கு ₹0. Reproducible.

**படிக்கிறது.** எந்த error-உமே இல்ல, அதுவே ஒரு clue: code ஓடுது, ஆனா data-வை skip பண்ணுது அல்லது zero ஆக்குது.

**Guess, குறுக்கு.** Total zero-ஆ இருக்க என்ன உண்மையா இருக்கணும்? ஒண்ணு, அந்த store-க்கு rows எதுவும் match ஆகல, இல்லன்னா எல்லா amounts-உம் zero. Loop-க்குள்ள `breakpoint()` போட்டு, முதல் சில rows-க்கு `row["store"]`-ஐ print பண்றாரு: `'Kothrud '`, கடைசியில ஒரு space-ஓட. அவரோட filter `'Kothrud'`-ஓட compare பண்ணுது. எந்த row-உம் match ஆகல.

**காரணத்தை fix பண்ணுங்க.** Filter-ல அந்த space-ஐ சேர்த்துடலாம், ஆனா நிஜ பிரச்சனை export-ல இருந்து வர்ற ஒழுங்கில்லாத data. File படிக்கிற இடத்துலயே store names-ல இருந்து whitespace-ஐ strip பண்றாரு, அதனால அப்புறம் வர்ற ஒவ்வொரு step-க்கும் clean values கிடைக்கும்.

**நிரூபிங்க.** கடைசியில space இருக்குற ஒரு store name-ஓட ஒரு test சேர்த்து, அது count ஆகுதுன்னு check பண்றாரு. Master list-ல இருக்குற ஒரு store-க்கு rows இல்லன்னா எச்சரிக்கிற ஒரு check-ஐயும் சேர்க்கிறாரு, அதனால அடுத்த தடவை இதே மாதிரி mismatch சத்தமில்லாம ₹0 காட்டாம, சத்தமா தெரியும்.

## பொதுவான தப்புகள்

- **Bug-ஐ reproduce பண்ண முடியறதுக்கு முன்னாடியே code-ஐ மாத்துறது.** உங்க fix work ஆச்சான்னு உங்களுக்கு தெரியாது.
- **Traceback-ஐ மேல இருந்து படிக்கிறது.** Error-உம், fail ஆன line-உம் கீழ இருக்கும்.
- **அறிகுறியை fix பண்றது.** Error-ஐ விழுங்குற `try/except` அடுத்த bug-ஐ கண்டுபிடிக்க கஷ்டமாக்கும்.
- **ஒரே நேரத்துல பல விஷயங்களை மாத்துறது.** அது work ஆக ஆரம்பிச்சா, எந்த மாற்றம் முக்கியம்னு உங்களுக்கு தெரியாது.
- **Debug prints, breakpoints-ஐ விட்டுடுறது.** Commit பண்றதுக்கு முன்னாடி `breakpoint(`-ஐயும் மிச்சமிருக்குற prints-ஐயும் தேடுங்க.
- **Test சேர்க்காம இருக்கிறது.** அது இல்லன்னா, அடுத்த தடவை யாராவது அந்த code-ஐ தொடும்போது bug திரும்பி வரலாம்.

## Practice
