## இது என்ன

Standard RAG, கேள்விக்கு similar-ஆ இருக்குற passages-ஐ retrieve பண்ணும். ரெண்டு வகை கேள்விகள் இதை தோற்கடிக்கும்:

- **Multi-hop கேள்விகள்**, links-ஐ follow பண்ணுறவை: "தாமதமான Chennai metro package-ஓட contractor-ஐ share பண்ற projects எவை?" Facts வேற வேற documents-ல இருக்கு, எந்த ஒரு passage-உம் கேள்வியோட similar இல்ல.
- **Global கேள்விகள்**, ஒரு முழு collection பத்தினவை: "கடந்த வருஷ customer complaints-ல திரும்ப திரும்ப வர்ற பிரச்சனைகள் என்ன?" எந்த ஒரு passage-லயும் answer இல்ல; பலதுல இருந்து அது உருவாகும்.

**Graph RAG** ஒரு **knowledge graph**-ஐ சேக்குது: documents-ல இருந்து extract பண்ண entities (people, companies, products, places, events) nodes-ஆவும், அவற்றுக்கு இடையிலான relationships edges-ஆவும். அப்போ retrieval relationships-ஐ follow பண்ணலாம், தொடர்புடைய entities-ஓட groups-க்கு முன்னாடியே எழுதின summaries-ஐ use பண்ணலாம். Microsoft-ஓட open-source GraphRAG ஒரு பிரபலமான implementation; Neo4j மாதிரி graph databases இன்னொரு வழி.

```flow
Documents -> Chunks -> Model entities, relationships-ஐ extract பண்ணும் -> Knowledge graph
Knowledge graph -> Communities கண்டுபிடிச்சு summarise பண்ணப்படும்
Question -[local search]-> Entities + neighbours + source chunks
Question -[global search]-> Community summaries மேல map, அப்புறம் reduce
```


இந்த lesson-ல, Mumbai-ல ஒரு infrastructure finance company-ஐ follow பண்ணப் போறோம்; அங்க analysts நூற்றுக்கணக்கான project documents முழுக்க பரவிய கேள்விகளை கேக்குறாங்க.

## இது எப்படி work ஆகுது

**Indexing (GraphRAG style).**

1. Documents-ஐ வழக்கம் போல chunk பண்ணுங்க.
2. ஒவ்வொரு chunk-ல இருந்தும், சின்ன descriptions-ஓட entities, relationships-ஐ extract பண்ண ஒரு model-ஐ use பண்ணுங்க ("ABC Infra, contractor; Package 4-க்கு steel supply பண்ணுது").
3. Duplicates-ஐ merge பண்ணுங்க ("ABC Infra Ltd", "ABC Infrastructure").
4. **Communities**-ஐ கண்டுபிடிங்க: நெருக்கமா connect ஆன entities-ஓட clusters.
5. ஒவ்வொரு community-க்கும் ஒரு model summary-ஐ, பல விவர நிலைகள்ல எழுதட்டும்.

**Querying.**

- குறிப்பிட்ட entities பத்தின கேள்விகளுக்கு *local search*: கேள்வியில இருக்குற entities-ஐ கண்டுபிடிச்சு, அவற்றோட neighbours, relationships, source chunks-ஐ சேகரிச்சு, அதுல இருந்து பதில் சொல்லுங்க.
- Collection முழுக்க இருக்குற கேள்விகளுக்கு *global search*: கேள்வியை community summaries மேல map பண்ணி, அப்புறம் பகுதி பதில்களை ஒண்ணா reduce பண்ணுங்க.

**செலவுகள்.** Indexing ஒவ்வொரு chunk, ஒவ்வொரு community மேலயும் ஒரு model-ஐ call பண்ணும்; அதனால embedding-க்கான செலவை விட பல மடங்கு ஆகலாம், documents மாறும்போது திரும்ப run பண்ணணும் அல்லது update பண்ணணும். Entity extraction தப்பு பண்ணும்; merges தனியா இருக்க வேண்டிய விஷயங்களை இணைச்சுடலாம். Queries, குறிப்பா global queries, நிறைய tokens use பண்ணும்.

**எப்போ தகுதியானது.** Entities, relationships நிறைஞ்ச collections (contracts, investigations, research literature, supplier networks, case files), multi-hop அல்லது global கேள்விகள் அடிக்கடி வந்து, மதிப்பும் அதிகமா இருக்கும்போது. பெரும்பாலான FAQ-style அல்லது policy-lookup assistants-க்கு, நல்ல metadata-ஓட hybrid search cheap-ஆவும், போதுமானதாவும் இருக்கும்.

**இலகுவான மாற்று வழிகள்.** Extract பண்ண entities-ஐ metadata-வா store பண்ணி அதுல filter பண்ணுங்க; முக்கிய relationships-ஓட ஒரு சின்ன structured table வச்சுக்கோங்க; document groups-ஓட summaries generate பண்ணுங்க. பெரும்பாலும் இவையே பலனோட பெரும்பகுதியை கொடுக்கும்.

**Standard RAG vs Graph RAG:**

| அம்சம் | Hybrid RAG | Graph RAG |
| --- | --- | --- |
| ஒரே document-ஓட கேள்விகள் | Strong | அதைவிட நல்லது இல்ல |
| Multi-hop கேள்விகள் | Weak | Strong |
| Collection முழுக்க இருக்குற கேள்விகள் | Weak | Community summaries-ஓட Strong |
| Indexing cost | Embeddings மட்டும் | ஒவ்வொரு chunk, community-க்கும் model calls |
| Updates | மாறின chunks-ஐ re-embed | Re-extract, re-merge |
| Failure risk | தவறவிட்ட passages | தப்பான extractions, merges |

**ரெண்டுக்கும் நடுவுல routing.** Hybrid RAG-ஐ மாத்துற teams கொஞ்சம் தான்; அது பதில் சொல்ல முடியாத கேள்விகளுக்கு ஒரு graph-ஐ சேக்குறாங்க. ஒரு சின்ன classifier அல்லது ஒரு model call, ஒரு கேள்வி entities முழுக்க relationships-ஐ குறிப்பிடுதா ("எந்த contractors-உம் வேலை செய்யுறாங்க...", "வேற யார் தொடர்புல இருக்காங்க..."), இல்ல முழு collection பத்தினதா ("திரும்ப திரும்ப வர்றவை என்ன...") முடிவு பண்ணும். அவை graph search-க்கு போகும்; மத்ததெல்லாம் hybrid RAG-க்கு. Router-ஓட தப்புகளை test set-ல check பண்ண, ஒவ்வொரு கேள்விக்கும் route-ஐ log பண்ணுங்க.

**Citations-ஐ வச்சுக்கிறது.** ஒவ்வொரு entity, relationship, community summary-யும் அது வந்த chunks-க்கு links-ஐ வச்சிருக்கணும். அப்போ answers உண்மையான documents-ஐ cite பண்ணலாம், extract பண்ண relationship உண்மையிலேயே சொல்லப்பட்டிருக்கா, இல்ல extraction-ல கற்பனையா வந்ததான்னு analysts check பண்ணலாம்.

**Code-ல ஒரு சின்ன graph.** ஒரு model-ஆல triples-ஐ (structured output-ஆ) extract பண்ணி, NetworkX-ல load பண்ணி, neighbourhoods-ல இருந்து local கேள்விகளுக்கு பதில் சொல்லுங்க:

```python
import networkx as nx
from pydantic import BaseModel

class Triple(BaseModel):
    subject: str
    relation: str
    object: str

class Extraction(BaseModel):
    triples: list[Triple]

def normalise(name):
    n = name.lower().replace("limited", "ltd").replace("infrastructure", "infra")
    return " ".join(w for w in n.replace(".", "").split() if w not in {"ltd", "pvt", "private"})

def build_graph(chunks, extract):
    """extract(text) -> Extraction, via structured output from a model."""
    g = nx.MultiDiGraph()
    for c in chunks:
        for t in extract(c["text"]).triples:
            s, o = normalise(t.subject), normalise(t.object)
            g.add_node(s, label=t.subject); g.add_node(o, label=t.object)
            g.add_edge(s, o, relation=t.relation, source=c["id"])
    return g

def local_context(g, entities, hops=2, limit=40):
    nodes = set()
    for e in map(normalise, entities):
        if e in g:
            nodes |= set(nx.ego_graph(g.to_undirected(as_view=True), e, radius=hops))
    facts = [f'{g.nodes[u]["label"]} —{d["relation"]}→ {g.nodes[v]["label"]} [{d["source"]}]'
             for u, v, d in g.subgraph(nodes).edges(data=True)]
    return facts[:limit]
```

Facts தங்களோட source chunk ids-ஐ கொண்டிருக்கும், அதனால answer உண்மையான documents-ஐ cite பண்ணலாம். `normalise` rules, entity resolution-ஓட ஒரு முரட்டுத்தனமான ஆரம்பம் தான்; முக்கியமான entities-க்கு merges-ஐ கையால check பண்ணுங்க, ஒருபோதும் merge பண்ணக்கூடாத பெயர்களோட ஒரு list-ஐயும் வச்சுக்கோங்க.

**Global கேள்விகளுக்கு communities.** நெருக்கமா link ஆன entities-ஐ group பண்ணி, ஒவ்வொரு group-ஐயும் ஒரு தடவை summarise பண்ணுங்க:

```python
from networkx.algorithms.community import louvain_communities

def communities(g, seed=7):
    groups = louvain_communities(g.to_undirected(), seed=seed)
    return sorted(groups, key=len, reverse=True)
```

ஒரு model ஒவ்வொரு community-க்கும் (அது எடுத்த chunk ids-ஓட) ஒரு summary எழுதும். "எல்லா packages-லயும் திரும்ப திரும்ப வர்ற delay காரணங்கள் என்ன?"ன்னு கேக்கணும்னா, அந்த கேள்வியை ஒவ்வொரு community summary-க்கும் கேட்டு, பகுதி பதில்களை இணைங்க.

**Graph-ஐ நம்புறதுக்கு முன்னாடி extraction-ஐ check பண்ணுங்க.** Extract பண்ண 50 triples-ஐ sample எடுத்து, ஒவ்வொண்ணையும் source-ல சொல்லப்பட்டது, குறிப்பா உணர்த்தப்பட்டது, தப்பானதுன்னு mark பண்ணுங்க. சில சதவீதத்துக்கு மேல தப்பா இருந்தா, அதுக்கு மேல எதையும் build பண்றதுக்கு முன்னாடி extraction prompt-ஐ improve பண்ணுங்க (allowed entity types, relations-ஐ கொடுங்க).

**முதல்ல indexing bill-ஐ estimate பண்ணுங்க.** Chunks × (extraction prompt + chunk + output tokens) எண்ணுங்க, கூடவே ஒரு community-க்கு ஒரு summary call. Collection-ஓட 5%-ல run பண்ணி, அளந்து, முழுசுக்கும் commit பண்றதுக்கு முன்னாடி பெருக்குங்க.

## ஒரு நாள், ஒரு example

Mumbai-ல ஒரு infrastructure finance company ஆயிரக்கணக்கான project reports, contractor agreements, site inspection notes-ஐ review பண்றாங்க. Analysts "20%-க்கு மேல cost overrun இருக்குற projects-ல எந்த contractors வராங்க, அவங்க வேற எங்க வேலை செய்யுறாங்க?" மாதிரி கேள்விகளை கேக்குறாங்க.

Hybrid RAG ஒரு project பத்தின கேள்விகளுக்கு நல்லா பதில் சொல்லும், ஆனா இவற்றுல தோத்துடும்: facts நூற்றுக்கணக்கான documents-ல பரவி இருக்கு.

ஒரு pilot, 3,000 documents-ல இருந்து projects, contractors, sub-contractors, locations, inspection findings-ஓட ஒரு graph-ஐ build பண்ணுது. Indexing செலவு, embedding மட்டும் உள்ள pipeline-ஐ விட சுமார் 25 மடங்கு; அது ஒரு தடவை ஆகுற செலவு, கூடவே வாராந்திர updates. Entity merging-க்கு, கையால உருவாக்கின company name variants list வேணும், ஏன்னா ஒரே contractor பல spellings-ல வராங்க.

Multi-hop, global கேள்விகள் உள்ள 40-question test set-ல, graph approach 70% கேள்விகளுக்கு நல்லா பதில் சொல்லுது, hybrid RAG 30%. ஒரே document பத்தின கேள்விகள்ல இது அதைவிட நல்லது இல்ல. Company ரெண்டையும் வச்சுக்குது: projects முழுக்க relationships-ஐ குறிப்பிடும் கேள்விகள் graph search-க்கும், மத்தவை hybrid RAG-க்கும் route ஆகுது.

| அளவு | Hybrid RAG | Graph approach |

| ஒரே document-ஓட கேள்விகள் | நல்லா | அதைவிட நல்லது இல்ல |

## பொதுவா பண்ற தப்புகள்

- **எளிய lookups-க்கு Graph RAG.** செலவை கூட்டும், பலன் இல்ல.
- **Entity resolution-ஐ ignore பண்றது.** Duplicate அல்லது தப்பா merge ஆன entities, அதை use பண்ற ஒவ்வொரு answer-ஐயும் கெடுக்கும்.
- **Updates-ஐ மறக்கிறது.** ஒரு தடவை build பண்ண graph பழசாகிடும்.
- **ஒப்பீடே இல்லாம இருக்கிறது.** முக்கியமான கேள்விகள்ல hybrid RAG-ஓட ஒப்பிட்டு அளவுங்க.
- **Citations-ஐ இழக்கிறது.** Entities, summaries-ல இருந்து source chunks-க்கு links-ஐ வச்சுக்கோங்க.
- **Extract பண்ண relationships-ஐ source text-ஓட sample பண்ணி பார்க்காம நம்புறது.**
- **Free-form relation names.** Extractor-க்கு ஒரு fixed list கொடுங்க, இல்லைன்னா graph கிட்டத்தட்ட duplicate-களால நிறைஞ்சுடும்.
- **முழு collection-ஐ index பண்றதுக்கு முன்னாடி cost estimate-ஐ skip பண்றது.**

## Graph RAG தகுதியில்லாத சமயங்கள்

- **கேள்விகள் பெரும்பாலும் ஒரு document அல்லது ஒரு fact பத்தினவை**: hybrid RAG அவற்றை cheap-ஆ answer பண்ணும்.
- **Documents தொடர்ந்து மாறிட்டே இருக்கு**, re-extraction costly ஆகும்.
- **கொஞ்சம் entities, relationships மட்டும் முக்கியம்**: மனுஷங்க maintain பண்ற முக்கிய facts-ஓட ஒரு சின்ன table போதுமா இருக்கலாம்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு entity, relationship, summary-லயும் source chunk ids-ஐ** வச்சுக்கோங்க.
- **ஒவ்வொரு prompt அல்லது model change-க்கு அப்புறமும்**, ஒரு sample-ல extraction accuracy-ஐ அளவுங்க.
- **Incremental-ஆ update பண்ணுங்க**: மாறின documents-ஐ re-extract பண்ணி, community summaries-ஐ ஒரு schedule-ல re-run பண்ணுங்க.
- **கேள்விகளை graph, hybrid search இடையே route பண்ணி**, route-ஐ log பண்ணுங்க.
- **Indexing, query cost-ஐ சாதாரண RAG-ல இருந்து தனியா track பண்ணுங்க.**

## Practice பண்ணுங்க

Microsoft Research-ஓட GraphRAG post-ஐ படிச்சு, local, global search பத்தின GraphRAG docs-ஐ ஒரு தடவை பாருங்க.

1. 30 முதல் 50 தொடர்புடைய documents-ஐ எடுங்க (ஒரு industry பத்தின news articles நல்லா work ஆகும்); ஒரு model-ஆல entities, relationships-ஐ extract பண்ணி ஒரு எளிய table-ல வைங்க.
2. ஐந்து multi-hop அல்லது global கேள்விகளை எழுதி, உங்க hybrid RAG-லயும் ஒரு சின்ன graph-based approach-லயும் பதில் சொல்லுங்க.
3. ரெண்டுக்கும் indexing cost-ஐயும் answer quality-யையும் record பண்ணுங்க.
4. உங்க graph-ல இருந்து 30 triples-ஐ sample எடுத்து, ஒவ்வொண்ணையும் stated, implied, wrong-னு mark பண்ணுங்க; ஒவ்வொண்ணோட பங்கையும் report பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** எந்த கேள்விகளுக்கு graph உதவுச்சு, எவ்வளவு உதவுச்சு, indexing cost-க்கு அது தகுதியா இருந்துச்சான்னு சொல்ல முடியும்.
