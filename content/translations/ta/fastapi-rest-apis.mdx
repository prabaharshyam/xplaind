## இது என்ன

ஒரு REST API மத்த programs உங்க system-ஐ HTTP வழியா use பண்ண விடும். ஒவ்வொரு **endpoint**-உம் ஒரு URL-உம் ஒரு method-உம்: `POST /tickets` ஒரு ticket-ஐ create பண்ணும், `GET /tickets/42` ஒண்ணை படிக்கும். Caller JSON அனுப்புவாங்க, JSON திரும்ப வரும், என்ன நடந்துச்சுன்னு சொல்ற ஒரு **status code**-ஓட.

FastAPI இந்த APIs-ஐ build பண்ற ஒரு Python framework. Type hints, Pydantic models இருக்குற சாதாரண functions-ஐ எழுதுவீங்க; FastAPI அவற்றை input-ஐ validate பண்ணி, output-ஐ JSON-ஆ மாத்தி, `/docs`-ல interactive documentation-ஐ publish பண்ற endpoints-ஆ மாத்தும். Async code-ஐயும் இயல்பா run பண்ணும்; model APIs-க்காக காத்திருக்குற services-க்கு இது பொருந்தும்.

```flow
Caller | வேற team-ஓட app: POST /claims/triage -> Pydantic வச்சு FastAPI body-ஐ validate பண்ணுது
Pydantic வச்சு FastAPI body-ஐ validate பண்ணுது -[fails]-> 422 | தப்பான fields-ஓட list
Pydantic வச்சு FastAPI body-ஐ validate பண்ணுது -[ok]-> Model client-ஐ inject பண்ணு | Depends
Model client-ஐ inject பண்ணு -> உங்க function model API-ஐ call பண்ணுது
உங்க function model API-ஐ call பண்ணுது -[model down]-> 503 | "கொஞ்ச நேரத்துல மறுபடி try பண்ணுங்க"
உங்க function model API-ஐ call பண்ணுது -[ok]-> response_model output-ஐ filter பண்ணுது
response_model output-ஐ filter பண்ணுது -> 200 | category: "motor", summary: "Rear bumper damage"
```

இந்த lesson, Kochi-ல ஒரு insurance broker-ஐ follow பண்ணுது; மத்த teams ஒரு claims-triage service-ஐ call பண்ணணும்னு அவங்க விரும்புறாங்க.

## இது எப்படி work ஆகுது

**Methods.** GET படிக்கும், எதையும் மாத்தக்கூடாது. POST create பண்ணும் அல்லது வேலையை trigger பண்ணும். PUT replace பண்ணும், PATCH பகுதியை update பண்ணும், DELETE remove பண்ணும். இந்த அர்த்தங்களை பின்பற்றுனா caches, retries, மத்த engineers சரியா யூகிக்க முடியும்.

**Status codes.** Success-க்கு 200 OK, 201 Created. Malformed request-க்கு 400, caller sign in பண்ணாதப்போ 401, sign in பண்ணியிருந்தும் இதை செய்ய அனுமதி இல்லன்னா 403, அந்த விஷயம் இல்லன்னா 404, body validation-ல fail ஆனா 422 (FastAPI-ஓட default), ரொம்ப அதிகமா அனுப்புனா 429. 500-னா உங்க code உடைஞ்சிடுச்சு, 503-னா model provider மாதிரி ஒரு dependency down.

**Models.** Request body-ல ஒரு Pydantic model இருந்தா, உங்க function run ஆகுறதுக்கு முன்னாடியே FastAPI bad input-ஐ 422-ஓடயும், சரியா எந்த fields fail ஆச்சுன்னு ஒரு list-ஓடயும் reject பண்ணும். ஒரு `response_model` என்ன திரும்ப போகுதுன்னு கட்டுப்படுத்தும், அதனால cost figure மாதிரி ஒரு internal field தவறுதலா leak ஆகாது.

**Dependencies.** FastAPI-ஓட `Depends` database session, current user, model client மாதிரி shared விஷயங்களை ஒவ்வொரு endpoint-க்குள்ளயும் inject பண்ணும். Tests-ல அவற்றை fakes-ஆ swap பண்ணலாம்.

**Testing.** `TestClient` உங்க app-ஐ memory-லயே call பண்ணும், server தேவையில்ல, அதனால endpoint tests milliseconds-ல run ஆகும்.

**Callers நம்பியிருக்குற status codes:**

| Code | அர்த்தம் | Caller-ஓட வழக்கமான reaction |
| --- | --- | --- |
| 200, 201 | Success, அல்லது created | Result-ஐ use பண்ணும் |
| 400 | Malformed request | Request-ஐ fix பண்ணணும்; retry பண்ணக்கூடாது |
| 401 | Sign in பண்ணல | Sign in பண்ணி, அப்புறம் retry |
| 403 | அனுமதி இல்லை | நிறுத்தணும்; access கேக்கணும் |
| 404 | Not found | Id-ஐ check பண்ணணும் |
| 422 | Body validation-ல fail | குறிப்பிட்ட fields-ஐ fix பண்ணணும் |
| 429 | ரொம்ப அதிகமான requests | காத்திருந்து, அப்புறம் retry |
| 500 | உங்க code உடைஞ்சிடுச்சு | Report பண்ணணும் |
| 503 | ஒரு dependency down | Backoff-ஓட பிறகு retry |

**நல்லா வயசாகுற endpoints-ஐ design பண்றது.** Resources-க்கு nouns-ஐ (`/claims`, `/claims/{id}`), actions-க்கு methods-ஐ use பண்ணுங்க. Path-ல அல்லது ஒரு header-ல ஒரு version-ஐ வைங்க (`/v1/claims`); அப்போ callers-ஐ உடைக்காம, பிறகு API-ஐ மாத்தலாம். எல்லா இடத்துலயும் ஒரே error shape-ஐ திருப்புங்க, உதாரணமா `{"detail": "..."}`, அப்போ callers errors-ஐ ஒரே இடத்துல handle பண்ணலாம். ஒவ்வொரு endpoint-ஐயும் code-லயே ஒரு summary-ஓடயும் examples-ஓடயும் document பண்ணுங்க; FastAPI அவற்றை `/docs`-ல தானா காட்டும், மத்த teams படிக்குற ஒரே documentation அதுவா தான் பல நேரம் இருக்கும்.

**Browser-லயே try பண்ணுங்க.** Request validation தான் ஒரு நல்ல API-ஓட இதயம். Dictionary-ஐ மாத்தி ஒரு bad body-ஐ அனுப்பி பாருங்க.

```python
from pydantic import BaseModel, Field, ValidationError

class NewOrder(BaseModel):
    item_id: str = Field(pattern=r"^SKU-\d{4}$")
    quantity: int = Field(gt=0, le=20)
    pin_code: str = Field(pattern=r"^[1-9]\d{5}$")

body = {"item_id": "SKU-0042", "quantity": 0, "pin_code": "56001"}
try:
    print(NewOrder.model_validate(body))
except ValidationError as err:
    for e in err.errors():
        print("422:", e["loc"][0], "-", e["msg"])
```

## ஒரு worked example

Kochi-ல ஒரு insurance broker, மத்த teams claim descriptions-ஐ அனுப்பி, ஒரு category-யையும் ஒரு summary-யையும் திரும்ப பெறணும்னு விரும்புறாங்க.

```python
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel, Field

app = FastAPI(title="Claims triage")

class ClaimIn(BaseModel):
    policy_no: str = Field(pattern=r"^[A-Z]{3}\d{7}$")
    description: str = Field(min_length=20, max_length=5000)

class ClaimOut(BaseModel):
    category: str
    summary: str

@app.post("/claims/triage", response_model=ClaimOut, status_code=200)
async def triage(claim: ClaimIn, llm=Depends(get_llm)):
    try:
        result = await llm.classify(claim.description)
    except ProviderDown:
        raise HTTPException(503, "Triage is unavailable; try again shortly")
    return ClaimOut(category=result.category, summary=result.summary)
```

"abc123"ன்னு ஒரு policy number இருக்குற request model-ஐ ஒருபோதும் reach பண்ணாது: FastAPI அந்த field-ஐ குறிப்பிட்டு 422 திருப்பும். Model provider down-ஆ இருந்தா, callers குழப்பமான 500-க்கு பதிலா, retry பண்ணக்கூடிய ஒரு 503-ஐ பெறுவாங்க.

Test model-ஐ fake பண்ணும்:

```python
from fastapi.testclient import TestClient

def test_triage_returns_category():
    app.dependency_overrides[get_llm] = lambda: FakeLLM("motor", "Rear bumper damage")
    r = TestClient(app).post("/claims/triage",
        json={"policy_no": "MOT1234567", "description": "Car was hit from behind at a signal"})
    assert r.status_code == 200 and r.json()["category"] == "motor"
```

`/docs`-ஐ திறந்தா broker-ஓட மத்த teams endpoint-ஐ browser-லயே try பண்ணலாம், request schema அவங்களுக்காக ஏற்கனவே எழுதப்பட்டிருக்கும்.

**மத்த teams முதல்ல கவனிச்சது.** Broker-ஓட mobile team ஒரு நாள்ல integrate பண்ணிடுச்சு; பெரும்பாலும் `/docs` ஒவ்வொரு field-ஐயும், அதோட rules-ஐயும், ஒரு example-ஐயும் காட்டுனதாலயும், bad requests சரியான field-ஐ குறிப்பிட்டு 422-ஓட திரும்ப வந்ததாலயும். Model provider-க்கு ஒரு சின்ன outage வந்தப்போ, அவங்க app crash ஆகாம, 503-க்கு "Triage is busy, try again in a minute"ன்னு காட்டுச்சு; ஏன்னா எந்த வகையான failure-ன்னு status code அதுக்கு சொல்லுச்சு.

## பொதுவா பண்ற தப்புகள்

- **Errors-க்கு 200 திருப்புறது.** Status 200-ஓட `"error": true` இருக்குற ஒரு body ஒவ்வொரு retry, monitoring tool-ஐயும் உடைக்கும். சரியான code-ஐ use பண்ணுங்க.
- **உங்க database rows-ஐ நேரடியா திருப்புறது.** Internal fields leak ஆகும். எப்பவும் ஒரு response model வைங்க.
- **Async endpoints-ல blocking calls.** `async def`-க்குள்ள ஒரு synchronous model client server-ஐ freeze பண்ணும். ஒரு async client-ஐ use பண்ணுங்க, அல்லது endpoint-ஐ சாதாரண `def`-ஆ declare பண்ணுங்க, அப்போ FastAPI அதை ஒரு thread pool-ல run பண்ணும்.
- **Model call-ல timeout இல்லாதது.** ஒரு hung request ஒரு worker-ஐ என்னென்னைக்கும் கட்டிப்போடும். Timeouts வச்சு 503 அல்லது 504 திருப்புங்க.
- **Input limits-ஐ தவிர்க்கிறது.** Maximum length இல்லன்னா, யாராவது 300-page document-ஐ paste பண்ணுவாங்க, உங்க token bill எகிறும்.

## Practice பண்ணுங்க

"Handling Errors", "Testing" வரை FastAPI tutorial-ஐ செய்து, MDN-ஓட HTTP overview-ஐ ஒரு தடவை பாருங்க.

1. Text-ஐ (20 முதல் 5,000 characters) வாங்கி, ஏதாவது ஒரு model API-ல இருந்து அல்லது ஒரு fake-ல இருந்து ஒரு summary-ஐ திருப்பி தர்ற `POST /summaries`-ஐ build பண்ணுங்க.
2. தெரியாத id-க்கு 404 திருப்புற `GET /summaries/{id}`-ஐ சேருங்க.
