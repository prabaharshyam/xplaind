## இது என்ன

ஒரு **connector**-னா ஒரு business system-க்கும் உங்க AI system-க்கும் நடுவுல data-வை நகர்த்துற code. ஒரு நல்ல connector நாலு வேலை பண்ணும்: எல்லாத்தையும் ஒரு தடவை copy பண்ணும், அந்த copy-ஐ current-ஆ வச்சிருக்கும், delete ஆனதை நீக்கும், ஒவ்வொரு item-ஐயும் யாரு படிக்கலாம்ங்குற தகவலையும் கூடவே கொண்டு வரும். பெரும்பாலான enterprise AI projects-க்கு பல connectors தேவைப்படும்:

- **Documents**: SharePoint, OneDrive (Microsoft Graph வழியா), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: Salesforce மாதிரி CRM systems, SAP மாதிரி ERPs, Jira அல்லது ServiceNow மாதிரி ticketing, கூடவே client-ஓட சொந்த databases.
- **Messages**: email, chat; privacy காரணமா கவனமா use பண்ணணும்.

Connectors-ஐ நீங்களே build பண்ணலாம், ஒரு integration platform-ஐ use பண்ணலாம் (Airbyte, Fivetran மற்றும் சில platforms நிறைய ready-made connectors குடுக்குது), அல்லது ஒரு search அல்லது AI platform கூட bundled-ஆ வர்ற connectors-ஐ use பண்ணலாம். எதை use பண்ணாலும், அவை என்ன பண்ணுதுன்னு நீங்க புரிஞ்சுக்கணும்.

```flow
title: A connector feeding an assistant
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[REST, SystemModstamp, get deleted]-> Connector
Jira, SAP, file shares -> Connector
Connector -> Items, metadata, permissions, deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 12, changed 41, unchanged 253, deleted 6, failed 0
```

இந்த lesson, SharePoint, Salesforce மேல build பண்ணின ஒரு Gurugram sales assistant-ஐ follow பண்ணுது.

## இது எப்படி வேலை செய்யுது

### Authentication

பொதுவா client-ஓட IT team register பண்ணின ஒரு app-ஓட OAuth; read-only-க்கும், ஒத்துக்கிட்ட sites, objects அல்லது projects-க்கும் மட்டும் scope பண்ணப்பட்டது. சில systems API keys அல்லது service users use பண்ணும்; அவற்றை ஒரு secret manager-ல வைங்க, code-ல ஒருபோதும் வைக்காதீங்க.

நீண்ட runs-ஐ ரெண்டு விஷயங்கள் உடைக்கும். முதல்ல, access tokens expire ஆகும்: Microsoft அவற்றுக்கு default-ஆ 60 முதல் 90 நிமிஷம் ஆயுள் குடுக்குது, அதனால ரெண்டு ராத்திரி ஓடுற ஒரு first load ஒரே token-ஐ use பண்ண முடியாது. ஒவ்வொரு request-க்கு முன்னாடியும் உங்க auth library-ஓட cache-கிட்ட (உதாரணமா MSAL) ஒரு token கேளுங்க; expiry நெருங்கும்போது அது புது token-ஐ எடுத்துக்கும். ரெண்டாவது, client secrets, certificates-ம் expire ஆகும். அந்த date-ஐ runbook-ல போடுங்க, ஒரு மாசம் முன்னாடியே alert பண்ணுங்க.

### Pages-ஆ படிக்குறது

APIs results-ஐ pages-ஆ return பண்ணும். ஒவ்வொரு page-ம் ஒரு cursor அல்லது ஒரு "next" link-ஓட முடியும். அடுத்த page இல்லாத வரைக்கும் loop பண்ணுங்க. முக்கியமான rule: **ஒவ்வொரு page-ம் முழுசா process ஆன பிறகு உங்க position-ஐ save பண்ணுங்க**, முன்னாடி இல்ல, கடைசியில மட்டும் இல்ல. Process பண்றதுக்கு முன்னாடி save பண்ணா, crash ஆனா items skip ஆகும்; கடைசியில மட்டும் save பண்ணா, page 9,000-ல ஒரு crash ஆனா page 1-ல இருந்து restart ஆகும்.

### Rate limits

ஒவ்வொரு API-ம் calls-ஐ limit பண்ணும். Microsoft Graph ஒரு `Retry-After` header-ஓட 429 Too Many Requests return பண்ணும், retry பண்றதுக்கு முன்னாடி அவ்வளவு நேரம் wait பண்ண சொல்லும்; header இல்லைன்னா exponential-ஆ back off பண்ணுங்க. HTTP standard-படி, `Retry-After` ஒரு seconds எண்ணிக்கையாவும் இருக்கலாம், ஒரு date-ஆவும் இருக்கலாம், அதனால ரெண்டையும் parse பண்ணுங்க. Parallel workers எல்லாம் ஒரே நொடியில retry பண்ணி மறுபடியும் throttle ஆகாம இருக்க, சுமார் ஒரு நொடி அளவுக்கு random jitter சேருங்க.

### Incremental sync-உம் change detection-உம்

முதல் run எல்லாத்தையும் copy பண்ணும்; அடுத்தடுத்த runs மாறினதை மட்டும் எடுக்கும். 200,000 documents-ஐ ஒவ்வொரு ராத்திரியும் முழுசா திரும்ப படிக்குறது slow, செலவு அதிகம், throttle-உம் ஆக வைக்கும்.

| Method | உதாரணம் | Deletions-ஐ report பண்ணுமா? | கவனிக்க வேண்டியது |
| --- | --- | --- | --- |
| Delta token | Microsoft Graph delta | ஆமா | Links வேலை செய்யாம போகலாம் (410 Gone); ஒரு full re-scan வழியை வச்சிருங்க |
| Modified-since filter | Salesforce `SystemModstamp`, Jira `updated` | இல்ல | ஒரு deletion feed கூட சேருங்க; windows-ஐ சில நிமிஷம் overlap பண்ணுங்க |
| Deletion feed | Salesforce get-deleted resource | Deletions மட்டும் | Salesforce அதிகபட்சம் 15 நாள் தான் வச்சிருக்கும் |
| Webhooks | Jira `jira:issue_deleted` | அந்த event இருந்தா | Deliveries தொலையலாம்; அதை மட்டுமே source-ஆ வைக்காதீங்க |
| Full id comparison | உங்க weekly reconciliation | ஆமா, வித்தியாசம் மூலமா | பெரிய sets-ல slow; safety net-ஆ வாரா வாரம் run பண்ணுங்க |

Graph delta-ல ரெண்டு gotchas: ஒரே item ஒரே feed-ல ஒரு தடவைக்கு மேல வரலாம் (கடைசியா வர்றது தான் கணக்கு, அதனால source id வச்சு upsert பண்ணுங்க), delete ஆன ஒரு item ஒரு `deleted` marker-ஓட, content இல்லாம திரும்ப வரும், அதனால download பண்றதுக்கு முன்னாடி அதை check பண்ணுங்க.

### Deletions

இப்போ இல்லாத ஒரு record-ஐ ஒரு modified-since query பார்க்க முடியாது, அதனால delete ஆன documents quote ஆகிட்டே இருக்கும். ஒவ்வொரு connector-க்கும் deletions-ஐ report பண்ற ஒரு feed அல்லது ஒரு periodic id comparison வேணும், முடிஞ்சா ரெண்டுமே.

### Permissions

எல்லாத்தையும் விட கஷ்டமான பகுதி இது தான்: permissions-ஐ கண்டுக்காத ஒரு assistant, ஒரு junior employee-க்கு salary review deck-ஐ காட்டிடும்.

- **ஒவ்வொரு item-ஓடயும் access rights-ஐ படிங்க.** Graph-ஓட permissions endpoint ஒரு file-ஓட effective sharing-ஐ return பண்ணும், folders-ல இருந்து inherit ஆன access உட்பட. அனுமதி இருக்குற user, group ids-ஐ ஒவ்வொரு chunk-லயும் store பண்ணுங்க.
- **Groups-ஐ groups-ஆவே வைங்க.** Index time-ல "Sales North"-ஐ 400 user ids-ஆ expand பண்ணாதீங்க. Query time-ல user-ஓட இப்போதைய groups-ஐ (அவங்க sign-in token-ல இருந்தோ ஒரு directory call மூலமோ) lookup பண்ணி, அதை வச்சு filter பண்ணுங்க. அப்போ ஒரு group-ஐ விட்டு போற ஒருத்தர், உங்க group lookup மாற்றத்தைப் பார்த்த உடனே access-ஐ இழப்பாங்க, re-index இல்லாமலே.
- **Permission மட்டும் மாறினா பார்க்குறது கஷ்டம்.** ஒரு file-ஐ share பண்றது அதோட content-ஐ மாத்தாது. `Prefer: deltashowsharingchanges` header-ஐ, Microsoft தேவைன்னு சொல்ற `deltashowremovedasdeleted`, `deltatraversepermissiongaps` கூட சேர்த்து அனுப்பினா, sharing மாறின items-ஐ Graph delta mark பண்ணலாம். ஆனா content அல்லது metadata மாறின items-ஐயும் அவற்றோட parent folders-ஐயும் மட்டும் தான் delta return பண்ணும்னு Microsoft document பண்ணியிருக்கு, அதனால access-ஐ inherit மட்டும் பண்ற files வராம போகலாம். Permissions-ஐ சரியா process பண்ண `Sites.FullControl.All` app permission வேணும்னும் Microsoft சொல்லுது; security teams அதை அடிக்கடி மறுப்பாங்க. Marker-ஐ ஒரு hint-ஆ மட்டும் பாருங்க. Client sensitive-னு mark பண்ற sites, folders-ல permissions-ஐ schedule பண்ணி திரும்ப படிக்குறதை அதுக்கு backup-ஆ வைங்க.
- **Fail closed.** ஒரு item-ஓட permissions-ஐ படிக்க முடியலைன்னா, அதை index பண்ணாதீங்க.

### Code-ல ஒரு incremental connector

ஒரு SharePoint library-க்கான இந்த sync மேல சொன்ன rules-ஐ follow பண்ணுது. ஒவ்வொரு page-க்கும் position-ஐ save பண்ணுது, fail ஆன items-க்கு ஒரு retry list வச்சிருக்கு, tokens-ஐ refresh பண்ணுது, throttling-ஐயும் உடைஞ்ச delta link-ஐயும் handle பண்ணுது:

```python
import email.utils, hashlib, json, random, time
from pathlib import Path        # client below is an httpx.Client

GRAPH = "https://graph.microsoft.com/v1.0"
STATE = Path("state/sharepoint-delta.json")

class StopRun(Exception): pass    # fatal: stop now, leave saved state as it is
class Resync(Exception): pass     # 410 Gone: the saved link no longer works

def wait_for(r, attempt):
    value = r.headers.get("Retry-After", "")
    if value.isdigit():
        delay = int(value)                                  # seconds
    elif value:
        when = email.utils.parsedate_to_datetime(value)     # an HTTP date
        delay = max(0, when.timestamp() - time.time())
    else:
        delay = min(60, 2 ** attempt)                       # no header: back off
    return delay + random.uniform(0, 1)                     # jitter

def get(client, url, token, prefer=None):
    headers = {"Authorization": f"Bearer {token()}"}  # token() reads a cache
    if prefer:
        headers["Prefer"] = prefer
    for attempt in range(6):
        r = client.get(url, headers=headers)
        if r.status_code in (429, 503):
            time.sleep(wait_for(r, attempt)); continue
        if r.status_code == 410:
            raise Resync(r.headers.get("Location"))
        if r.status_code in (401, 403):
            raise StopRun(f"access refused: {r.status_code}")
        r.raise_for_status()
        return r.json()
    raise StopRun("still throttled after 6 tries")

def process(client, token, drive_id, item, index, counts, retry):
    if "deleted" in item:
        index.delete_doc(item["id"])        # must not fail if already gone
        if item["id"] in retry:
            retry.remove(item["id"])
        counts["deleted"] += 1
        return
    if "file" not in item:
        return                              # folders carry no text
    perms = get(client, f"{GRAPH}/drives/{drive_id}/items/{item['id']}/permissions", token)
    acl = acl_from(perms)                   # user and group ids allowed to read
    text = download_and_parse(item)         # your parser
    digest = hashlib.sha256(text.encode()).hexdigest()
    if index.hash_of(item["id"]) == digest:
        index.update_meta(item["id"], meta_from(item), acl)  # renamed or reshared: no re-embed
        counts["unchanged"] += 1
    else:
        new = index.upsert_doc(item["id"], text, digest, meta_from(item), acl)
        counts["added" if new else "changed"] += 1

def save(state):
    STATE.parent.mkdir(exist_ok=True)
    tmp = STATE.with_suffix(".tmp")
    tmp.write_text(json.dumps(state))
    tmp.replace(STATE)                      # atomic: never half-written

def sync(client, token, drive_id, index):
    state = json.loads(STATE.read_text()) if STATE.exists() else {}
    retry = state.get("retry", [])
    counts = dict.fromkeys(["read", "added", "changed", "unchanged", "deleted", "failed"], 0)
    for item_id in list(retry):             # last run's failures first
        try:
            item = get(client, f"{GRAPH}/drives/{drive_id}/items/{item_id}", token)
            process(client, token, drive_id, item, index, counts, retry)
            if item_id in retry:
                retry.remove(item_id)
        except StopRun:
            raise
        except Exception:
            counts["failed"] += 1           # stays listed; alert if it stays for days
    url = (state.get("next_link") or state.get("delta_link")
           or f"{GRAPH}/drives/{drive_id}/root/delta")
    while True:
        try:
            page = get(client, url, token, prefer="deltashowremovedasdeleted, "
                       "deltatraversepermissiongaps, deltashowsharingchanges")
        except Resync as e:
            state = {"retry": retry, "reconcile": True}   # full listing, then compare ids
            url = e.args[0] or f"{GRAPH}/drives/{drive_id}/root/delta"
            continue
        for item in page.get("value", []):
            counts["read"] += 1
            try:
                process(client, token, drive_id, item, index, counts, retry)
            except StopRun:
                raise
            except Exception:
                counts["failed"] += 1
                if item["id"] not in retry:
                    retry.append(item["id"])
        state["retry"] = retry
        if "@odata.nextLink" in page:       # page done: save where to resume
            url = state["next_link"] = page["@odata.nextLink"]
            save(state)
        else:                               # last page: save the link for next time
            state.pop("next_link", None)
            state["delta_link"] = page["@odata.deltaLink"]
            save(state)
            break
    print(counts)
    return counts
```

ஏன் இப்படி build பண்ணியிருக்கு:

- **Position-உம் failures-உம் சேர்ந்தே save ஆகுது**, ஒவ்வொரு page-க்கு அப்புறமும் ஒரே atomic write-ல. Page நடுவுல crash ஆனா அந்த page replay ஆகும்; upserts, deletes source id வச்சு key பண்ணப்பட்டதால அது safe. Fail ஆன ஒரு item ஒருபோதும் skip ஆகாது: succeed ஆகுற வரைக்கும் retry list-ல இருக்கும்.
- **ஒரு கெட்ட file feed-ஐ freeze பண்ணாது.** ஏதாவது ஒரு item fail ஆகும்போது முன்னேற மறுக்குறது safe-ஆ தெரியும், ஆனா அப்போ ஒரு corrupt PDF எதிர்கால மாற்றங்கள் எல்லாத்தையும் block பண்ணிடும்.
- **Metadata text கூடவே போகுது.** Citations, filters-க்காக `meta_from` source id, URL, title, path, author, modified time, owner-ஐ வச்சிருக்கு. ஒரு rename இவற்றை மாத்தும், text-ஐ மாத்தாது, அதனால re-embed பண்ணாமலே இவை update ஆகுது.
- **Fatal errors save பண்ணாமலே run-ஐ நிறுத்துது.** ஒரு access error அல்லது முடிவில்லாத throttling ஒரு item failure இல்ல; அதை item failure-ஆ count பண்ணா, முழு library-ம் retry list-க்கு போயிடும்.
- **உடைஞ்ச ஒரு link ஒரு full listing-ஐ trigger பண்ணுது.** 410 Gone வந்தா, Graph-ஓட `Location` header ஒரு புது enumeration-ஐ start பண்ணும். அது இப்போ என்ன இருக்குன்னு list பண்ணும், இடையில என்ன delete ஆச்சுன்னு இல்ல, அதனால `reconcile` flag அடுத்ததா id comparison-ஐ run பண்ண scheduler-கிட்ட சொல்லுது.

### ஒரு weekly reconciliation

நல்ல change feeds-ம் சில விஷயங்களை miss பண்ணும். Source-கிட்ட இருக்குற ids-ஐ index-கிட்ட இருக்குற ids கூட compare பண்ணுங்க:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

`removed_stale` ஒரு சிலதுக்கு மேல இருந்தா, உங்க change feed-ல ஒரு bug இருக்கு; அதை சரி பண்ணுங்க.

### Records: Salesforce, Jira, SAP

- **Salesforce.** மாறின records-ஐ `LastModifiedDate` மேல இல்லாம `SystemModstamp` மேல filter போட்டு query பண்ணுங்க, ஏன்னா automated processes ஒரு record-ஐ மாத்தும்போதும் `SystemModstamp` நகரும். லேட்டா commit ஆன records miss ஆகாம இருக்க, கடைசி run time-ல இருந்து சில நிமிஷம் கழிச்சுக்கோங்க. Deletions-க்கு, ஒவ்வொரு object-க்கும் UTC-ல ஒரு start, end time-ஓட get-deleted REST resource-ஐ call பண்ணுங்க. அது அதிகபட்சம் கடைசி 15 நாளை தான் cover பண்ணும், நிமிஷ அளவுக்கு தான் வேலை செய்யும், அதனால connector அதை விட அதிக நாள் down-ஆ இருந்தா, ஒரு full id comparison மட்டும் தான் சரிக்கட்ட முடியும். அதோட, integration user பார்க்க முடிஞ்ச deletions-ஐ மட்டும் தான் அது காட்டும்.
- **Jira Cloud.** `search/jql` endpoint வழியா JQL-ஓட search பண்ணுங்க; அது பழைய `startAt` offset-க்கு பதிலா ஒரு `nextPageToken`-ஓட page பண்ணும். `updated >= "last run time"`-ஓட filter பண்ணுங்க. Delete ஆன issues search-ல இருந்து அப்படியே மறைஞ்சிடும், அதனால `jira:issue_deleted` webhook-க்கு subscribe பண்ணுங்க, webhooks miss ஆகலாம்ங்குறதால அப்பவும் ids-ஐ reconcile பண்ணுங்க.
- **SAP.** Direct table access அரிதா தான் கிடைக்கும். Client-ஓட SAP team data-வை expose பண்ணும், பொதுவா OData services-ஆ (அடிக்கடி CDS views மேல build பண்ணினது), சில நேரம் பழைய BAPI அல்லது RFC calls மூலமா, அல்லது அவங்க integration middleware மூலமா. சில OData services delta tokens-ஐ support பண்ணும்; இல்லைன்னா ஒரு changed-on date field-ஐயும் ஒரு reconciliation-ஐயும் use பண்ணுங்க. முக்கிய gotcha நேரம் தான்: ஒரு service build ஆகி approve ஆக உங்க code-ஐ விட அதிக நேரம் ஆகும், அதனால முதல் வாரத்துலயே கேளுங்க.
- **Schema drift.** Admins fields-ஐ சேர்ப்பாங்க, picklist values-ஐ rename பண்ணுவாங்க, objects-ஐ retire பண்ணுவாங்க. உங்க URLs-ல API version-ஐ pin பண்ணுங்க, ஒத்துக்கிட்ட fields-ஐ மட்டும் map பண்ணுங்க, எல்லாத்தையும் சத்தமில்லாம index பண்றதுக்கு பதிலா, ஒரு describe call புது அல்லது காணாம போன fields-ஐ காட்டும்போது alert பண்ணுங்க.
- **Record permissions.** Salesforce access owners, roles, sharing rules-ல இருந்து வருது; அவற்றை அப்படியே copy பண்றது கஷ்டம். ஒரு safe first release, எல்லா sales users-ம் படிக்கக் கூடிய objects-ஐ மட்டும் index பண்ணும், அல்லது ஒரு record-ஐ காட்டுறதுக்கு முன்னாடி user-ஓட சொந்த login வச்சு live-ஆ access-ஐ check பண்ணும்.

### Build, buy அல்லது borrow

Airbyte, Fivetran மாதிரி integration platforms பொதுவான systems-க்கு வாரக்கணக்கான நேரத்தை மிச்சப்படுத்தும். ஒண்ணை நம்புறதுக்கு முன்னாடி, அது deletions-ஐ report பண்ணுதா, access rights-ஐ கொண்டு வருதா, நீங்க alert பண்ணக் கூடிய run counts-ஐ expose பண்ணுதான்னு check பண்ணுங்க. ஒரு in-house database மாதிரி அசாதாரணமான systems-க்கு, அல்லது client-ஓட security team ஒரு third-party tool-ஐ approve பண்ணாதப்போ, உங்க சொந்த connector-ஐ எழுதுங்க.

## ஒரு worked example

Gurugram-ல ஒரு consumer-goods company, SharePoint (product sheets, trade-scheme circulars), Salesforce (accounts, opportunities) மேல ஒரு sales assistant வேணும்னு கேக்குது. கீழே இருக்குற figures illustrative தான், வேலை எப்படி இருக்கும்னு காட்ட.

**SharePoint.** ஆறு sites-க்கு read access-ஓட ஒரு app registration. 38,000 files-ஓட முதல் full sync, throttling limits-க்கு நல்லா கீழே இருக்க ரெண்டு ராத்திரிக்கு பிரிச்சு பண்றதா வச்சுக்கோங்க; save பண்ணின next link இன்னும் வேலை செஞ்சா ரெண்டாவது ராத்திரி அதுல இருந்து தொடரும், Graph 410 பதில் சொன்னா listing திரும்ப ஆரம்பத்துல இருந்து start ஆகும். அதுக்கு அப்புறம் ஒவ்வொரு 15 நிமிஷமும் ஒரு delta run சில நூறு changed அல்லது deleted items-ஐ return பண்ணி, சுமார் ஒரு நிமிஷத்துல முடியும். ஒவ்வொரு run-ம் changed items-க்கு permissions-ஐயும் திரும்ப படிக்கும், pricing, HR files இருக்குற ரெண்டு sites-ல ஒரு nightly job permissions-ஐ திரும்ப படிக்கும்.

**Salesforce.** Account, Opportunity, Product-க்கு மட்டும் limit பண்ணின ஒரு read-only integration user. ஒவ்வொரு 30 நிமிஷமும், `SystemModstamp` கடைசி run time-ல அஞ்சு நிமிஷம் கழிச்சதுக்கு அப்புறம் இருக்குற records-ஐ connector query பண்ணி, ஒவ்வொண்ணையும் record id, owner-ஐ metadata-வா வச்சு ஒரு சின்ன text summary-ஆ மாத்தி, அதே window-க்கு get-deleted resource-ஐ call பண்ணுது. ஒரு sales manager 11:10-க்கு ஒரு duplicate account-ஐ delete பண்ணா, அது சுமார் 11:30-க்குள்ள index-ல இருந்து போயிடும்.

**நடந்த incident.** மூணாவது வாரத்துல ஒரு delta request 410 Gone return பண்ணுதுன்னு வச்சுக்கோங்க. Connector `Location` header-ஐ follow பண்ணி, ராத்திரி முழுக்க library-ஐ re-list பண்ணி, அப்புறம் id comparison-ஐ run பண்ணி, link உடைஞ்சிருந்த நேரத்துல delete ஆன 14 files-ஐ நீக்குது. Client கவனிக்குறதுக்கு முன்னாடியே alert on-call engineer-கிட்ட போயிடுச்சு, runbook-ம் இந்த case-ஐ ஏற்கனவே cover பண்ணியிருந்தது.

| அளவு | முன்னாடி | அப்புறம் |
| --- | --- | --- |
| SharePoint sync | ஒவ்வொரு ராத்திரியும் full re-read, சுமார் 6 மணி நேரம், அடிக்கடி throttle ஆகும் | ஒவ்வொரு 15 நிமிஷமும் delta, சுமார் 1 நிமிஷம் |
| Salesforce sync | Daily export, deletions ஒருபோதும் நீக்கப்படல | ஒவ்வொரு 30 நிமிஷமும், deletions ஒரு run-க்குள்ள |

| Fail ஆன sync-ஐ கவனிக்க ஆகுற நேரம் | நாட்கள் | நிமிஷங்கள், alerts மூலமா |

## பொதுவான தப்புகள்

- **ஒவ்வொரு தடவையும் full re-sync.** First load-க்கு அப்புறம் delta tokens அல்லது modified-since queries use பண்ணுங்க.
- **Deletions-ஐ கண்டுக்காம விடுறது.** ஒரு modified-since query delete ஆன records-ஐ ஒருபோதும் return பண்ணாது; ஒரு deletion feed-ஐயும் ஒரு weekly id comparison-ஐயும் சேருங்க.
- **தப்பான நேரத்துல cursor-ஐ save பண்றது.** Process பண்றதுக்கு முன்னாடி save பண்ணா crash-க்கு அப்புறம் items skip ஆகும்; கடைசியில மட்டும் save பண்ணா page 1-ல இருந்து restart ஆகும். ஒவ்வொரு page-க்கு அப்புறமும் save பண்ணுங்க.
- **Fail ஆன items-ஐ விழுங்கிடுறது.** ஒரு failure-ஐ count பண்ணிட்டு அடுத்ததுக்கு போனா அந்த item நிரந்தரமா தொலைஞ்சிடும். ஒரு retry list வச்சிருங்க.
- **நீண்ட run-க்கு ஒரே token.** அது 60 முதல் 90 நிமிஷத்துல expire ஆகும், job அதிகாலை 3 மணிக்கு செத்துடும்.
- **Index time-ல groups-ஐ users-ஆ expand பண்றது.** அப்போ membership மாற்றங்கள் effect-க்கு வர ஒரு full re-index தேவைப்படும்.
- **அளவுக்கு மீறின access.** முழு tenant-க்கு இல்லாம, பேர் சொன்ன sites, objects-க்கு மட்டும் read-only access கேளுங்க.
- **சத்தமில்லாத connectors.** ஒரு sync நின்னா யாருக்கும் alert போகலைன்னா, assistant சத்தமில்லாம stale ஆகிடும்.
- **Modified ஆன ஒவ்வொரு file-ஐயும் re-embed பண்றது**, அதோட metadata மட்டும் மாறியிருந்தாலும்.

## Custom connector எப்போ தேவையில்ல

- **ஒரு one-off load**, ஒரு fixed set of files-க்கு: ஒரு தடவை export பண்ணி ingest பண்ணுங்க.
- **ஒரு platform connector ஏற்கனவே அந்த system-ஐ cover பண்ணுது**, deletions-ஐ report பண்ணுது, permissions-ஐ படிக்குது.
- **Users-க்கு தேவையான சில documents-ஐ அவங்களே** நேரடியா upload பண்ண முடியும்.

## Demo-ல இருந்து production-க்கு

Client-ஓட IT team கூட எழுத்துப்பூர்வமா ஒத்துக்கிட்ட starting defaults:

- **Schedules:** document delta ஒவ்வொரு 15 நிமிஷமும், record queries ஒவ்வொரு 30 நிமிஷமும், permission re-read ஒவ்வொரு ராத்திரியும், full id comparison வாரா வாரம். பெரிய first loads client-ஓட time zone-ல ராத்திரி மட்டும், குறைவான concurrency-ஓட.
- **Alerts:** ஒரு run fail ஆகுது அல்லது ரெண்டு intervals-க்குள்ள start ஆகல; படிச்ச items வழக்கமா வர்றதுல பாதிக்கு கீழே போகுது; ஏதாவது ஒரு item ஒரு நாளுக்கு மேல retry list-ல இருக்கு; ஒரு secret 30 நாளுக்குள்ள expire ஆகுது.
- **Runbook:** 410 Gone வந்தா, ஒரு access error வந்தா, ஒரு site, object அல்லது field rename ஆனா என்ன பண்ணணும்.

## Practice பண்ணுங்க

Microsoft Graph overview-ஐ படிங்க, அப்புறம் free-ஆ use பண்ணக் கூடிய, paging இருக்குற ஏதாவது ஒரு API-ஐ எடுத்துக்கோங்க (GitHub issues, ஒரு public dataset API, அல்லது ஒரு developer tenant-ஓட Graph).

1. Paging-ஓட எல்லா items-ஐயும் எடுக்குற, `Retry-After`-ஐ மதிக்குற, resume பண்ண முடியுற மாதிரி ஒவ்வொரு page-க்கு அப்புறமும் position-ஐ save பண்ற ஒரு connector-ஐ எழுதுங்க.
2. First load பாதியில இருக்கும்போது அதை kill பண்ணி restart பண்ணுங்க. அது save பண்ணின page-ல இருந்து தொடருது, திரும்ப ஆரம்பிக்கலைன்னு confirm பண்ணுங்க.
3. கடைசி run-ல இருந்து மாறின items-ஐ மட்டும் எடுக்குற ஒரு incremental mode-ஐயும், delete ஆன items-ஐ detect பண்ற ஒரு check-ஐயும் சேருங்க.
4. ஒவ்வொரு run-க்கும் counts-ஐ (read, added, changed, unchanged, deleted, failed) record பண்ணி, ஒரு one-line summary-ஐ print பண்ணுங்க.
5. Source-ல ஒரு item-ஐ delete பண்ணி, rerun பண்ணி, அதோட chunks index-ல இருந்து போயிடுச்சுன்னு confirm பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க connector-ஐ தொடர்ந்து ரெண்டு தடவை run பண்ணி, ரெண்டாவது run ஒரு deletion உட்பட மாறினதை மட்டும் எடுக்குதுன்னு காட்ட முடியும், crash ஆன ஒரு run சரியான page-ல இருந்து resume ஆகுதுன்னும் காட்ட முடியும்.
