## இது என்ன

**Connector**-னா ஒரு business system-க்கும் உங்க AI system-க்கும் நடுவுல data-வை நகர்த்துற code. பெரும்பாலான enterprise AI projects-க்கு பல connectors தேவைப்படும்:

- **Documents**: SharePoint, OneDrive (Microsoft Graph வழியா), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: Salesforce மாதிரி CRM systems, SAP மாதிரி ERPs, Jira அல்லது ServiceNow மாதிரி ticketing, அப்புறம் client-ஓட சொந்த databases.
- **Messages**: email, chat. Privacy காரணமா இதை ரொம்ப கவனமா use பண்ணணும்.

Connectors-ஐ நீங்களே build பண்ணலாம், integration platform use பண்ணலாம் (Airbyte, Fivetran மாதிரி பல platforms நிறைய ready-made connectors தராங்க), இல்லன்னா search அல்லது AI platform-கூடவே வர்ற connectors-ஐ use பண்ணலாம். எதுவா இருந்தாலும் அது என்ன பண்ணுதுன்னு நீங்க புரிஞ்சுக்கணும்.

```flow
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[API, modified since]-> Connector
Jira, file shares, databases -> Connector
Connector -> Items + metadata + permissions + deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 40, changed 266, deleted 6, failed 0
```

இந்த lesson-ல Gurugram-ல ஒரு consumer-goods company-க்கு SharePoint, Salesforce மேல build பண்ண sales assistant-ஐ follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Authentication.** பொதுவா OAuth, client-ஓட IT team register பண்ணின app வழியா. Read-only scope, ஒத்துக்கிட்ட sites, objects, projects மட்டும். சில systems API keys அல்லது service users use பண்ணும்; அதை secret manager-ல store பண்ணுங்க.

**Pages-ஆ படிக்கிறது.** APIs results-ஐ pages-ஆ தரும், cursor அல்லது next link-ஓட. Pages தீர்ற வரைக்கும் loop பண்ணுங்க, cursor-ஐ save பண்ணுங்க. அப்போ fail ஆன run resume ஆக முடியும்.

**Rate limits.** ஒவ்வொரு API-யும் நிமிஷத்துக்கோ நாளுக்கோ இவ்வளவு calls தான்னு limit வைக்கும். SharePoint, Salesforce அதிகமா use பண்றவங்களை throttle பண்ணும். `Retry-After` headers-ஐ மதிங்க, 429 response வந்தா back off பண்ணுங்க, பெரிய initial loads-ஐ off-peak நேரத்துல பரப்பி பண்ணுங்க.

**Incremental sync.** முதல் run எல்லாத்தையும் copy பண்ணும். அடுத்தடுத்த runs கடைசி run-ல இருந்து மாறினதை மட்டும் எடுக்கும்: change tokens (Microsoft Graph-ஓட delta queries), "modified since" filters, இல்லன்னா webhooks மூலமா. 200,000 documents-ஐ ஒவ்வொரு ராத்திரியும் முழுசா திரும்ப படிச்சா slow-ஆ இருக்கும், செலவும் ஆகும், throttle-உம் ஆவீங்க.

**Deletions.** Incremental feeds எது delete ஆச்சுன்னு சொல்லணும். இல்லைன்னா delete ஆன files எப்பவும் search-ல வந்துக்கிட்டே இருக்கும். உங்க method deletions-ஐ report பண்ணுதான்னு check பண்ணுங்க. இல்லைன்னா ids-ஐ compare பண்ற periodic reconciliation ஓட்டுங்க.

**Permissions.** ஒவ்வொரு item-ஓட content-கூடவே அதோட access rights-ஐயும் படிங்க. அப்போ தான் permission-aware retrieval பண்ண முடியும்.

**Formats, metadata.** Source id, URL, title, author, modified time, path அல்லது object type, owner இதெல்லாம் வச்சுக்கோங்க. Citations, filters, debugging எல்லாம் இதை வச்சு தான் நடக்கும்.

**Observability.** ஒவ்வொரு run-க்கும் படிச்ச, சேர்த்த, மாத்தின, delete பண்ண, fail ஆன items, எடுத்த நேரம் record பண்ணுங்க. Connector நின்னா அல்லது failure counts திடீர்னு ஏறினா alert வரணும்.

**மாற்றங்களை detect பண்ற வழிகள்:**

| Method | எப்படி work ஆகுது | கவனிக்க வேண்டியது |
| --- | --- | --- |
| Change அல்லது delta tokens | Save பண்ண token-ல இருந்து மாறினதை API தரும் | Tokens expire ஆகலாம், உடையலாம்; full re-scan fallback வச்சுக்கோங்க |
| Modified-since filter | கடைசி run-க்கு அப்புறம் modified time உள்ள items-ஐ query பண்றது | Deletions-ஐ பெரும்பாலும் miss பண்ணும்; clocks, time zones பொருந்தணும் |
| Webhooks | ஏதாவது மாறினா system உங்களை call பண்ணும் | Calls தொலையலாம்; periodic check-ஓட சேர்த்து use பண்ணுங்க |
| Full comparison | எல்லா ids-ஐயும் list பண்ணி index-ஓட compare பண்றது | பெரிய sets-ல slow; வாராந்திர safety net-ஆ நல்லது |

**Build பண்ணுறதா, வாங்குறதா, இரவல் வாங்குறதா.** Airbyte, Fivetran மாதிரி integration platforms பொதுவான systems-க்கு வாரக்கணக்கான நேரத்தை மிச்சப்படுத்தும். Search platform-ஓட bundled connectors permissions-ஐ ஏற்கனவே படிக்கலாம். ஆனாலும் check பண்ணணும்: deletions-ஐ report பண்ணுதா, access rights-ஐ படிக்குதா, alert வைக்க முடியுற run counts கொடுக்குதான்னு பாருங்க. System வித்தியாசமா இருந்தா (in-house database, vendor portal மாதிரி), அல்லது client-ஓட security team third-party tool-ஐ approve பண்ணலைன்னா, நீங்களே எழுதுங்க.

**Code-ல ஒரு incremental connector.** SharePoint அல்லது OneDrive library-க்கான Microsoft Graph delta query, மாறின, delete ஆன items-ஐ page by page தரும். கடைசியில அடுத்த தடவை use பண்ண ஒரு link கொடுக்கும்:

```python
import hashlib, json, time
from pathlib import Path
import httpx

STATE = Path("state/sharepoint-delta.json")

def get(client, url):
    for attempt in range(5):
        r = client.get(url)
        if r.status_code in (429, 503):
            time.sleep(int(r.headers.get("Retry-After", 2 ** attempt)))
            continue
        r.raise_for_status()
        return r.json()
    raise RuntimeError("gave up after repeated throttling")

def sync(token, drive_id, index):
    counts = {"read": 0, "upserted": 0, "deleted": 0, "skipped": 0, "failed": 0}
    url = (json.loads(STATE.read_text())["delta_link"] if STATE.exists()
           else f"https://graph.microsoft.com/v1.0/drives/{drive_id}/root/delta")
    with httpx.Client(headers={"Authorization": f"Bearer {token}"}, timeout=30) as client:
        while url:
            page = get(client, url)
            for item in page.get("value", []):
                counts["read"] += 1
                try:
                    if "deleted" in item:
                        index.delete_doc(item["id"]); counts["deleted"] += 1
                    elif "file" in item:
                        text = download_and_parse(client, item)            # your parser
                        digest = hashlib.sha256(text.encode()).hexdigest()
                        if index.hash_of(item["id"]) == digest:
                            counts["skipped"] += 1
                        else:
                            index.upsert_doc(item["id"], text, digest, meta_from(item))
                            counts["upserted"] += 1
                except Exception:
                    counts["failed"] += 1
            url = page.get("@odata.nextLink")
            if not url and "@odata.deltaLink" in page:
                STATE.parent.mkdir(exist_ok=True)
                STATE.write_text(json.dumps({"delta_link": page["@odata.deltaLink"]}))
    print(counts)
    return counts
```

முதல் run-ல save பண்ண link இல்லாததால எல்லாத்தையும் படிக்கும். அடுத்த runs-ல மாற்றங்கள் மட்டும் வரும். Delta link-ஐ கடைசி page வெற்றிகரமா முடிஞ்ச பிறகு மட்டும் save பண்ணுங்க. அப்போ run fail ஆனா அதே changes திரும்ப வரும், skip ஆகாது. Save பண்ண link வேலை செய்யலைன்னா, full re-scan-க்கு fallback பண்ணுங்க.

**வாராந்திர reconciliation.** நல்ல change feeds கூட சிலதை miss பண்ணும். Ids-ஐ compare பண்ணுங்க:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

**மாறாத content-ஐ skip பண்ணுங்க.** யாராவது file-ஐ rename பண்ணாலோ property-ஐ edit பண்ணாலோ அதோட modified time மாறும். ஒவ்வொரு document-கூடவும் extract பண்ண text-ஓட hash-ஐ store பண்ணுங்க. Hash பொருந்துச்சுன்னா re-embed பண்ணாம skip பண்ணுங்க. பெரிய libraries-ல இது embedding செலவுல பெரும்பகுதியை மிச்சப்படுத்தும்.

**Source-ஐ மதிங்க.** பெரிய first loads-ஐ client-ஓட time zone-ல ராத்திரி ஓட்டுங்க, concurrency-ஐ குறைவா வைங்க, limits-ஐ அவங்க IT team-கூட பேசி முடிவு பண்ணுங்க. Office hours-ல client-ஓட SharePoint-ஐ throttle ஆக்குனா, trust போறதுக்கு அதுவே வேகமான வழி.

## ஒரு example

Gurugram-ல ஒரு consumer-goods company, SharePoint (product sheets, trade-scheme circulars), Salesforce (accounts, opportunities) மேல ஒரு sales assistant வேணும்னு கேக்குறாங்க.

SharePoint: ஆறு sites-க்கு read access உள்ள ஒரு app registration. 38,000 files-ஓட முதல் full sync, throttling limits-க்குள்ள இருக்க ரெண்டு ராத்திரி எடுத்துச்சு. அதுக்கு அப்புறம் ஒவ்வொரு 15 நிமிஷத்துக்கும் delta queries, மாறின, delete ஆன items-ஐ மட்டும் தருது. ஒரு run-க்கு பொதுவா 200-ல இருந்து 400 வரை, சுமார் ஒரு நிமிஷம் ஆகும். ஒவ்வொரு item-ஓட permissions-ம் படிச்சு store பண்றாங்க.

Salesforce: Account, Opportunity, Product objects-க்கு மட்டும் limit பண்ண read-only integration user. ஒவ்வொரு 30 நிமிஷத்துக்கும் "modified since" query மூலமா records எடுத்து, retrieval-க்காக சின்ன text summaries-ஆ மாத்துறாங்க. Record id, owner metadata-ஆ இருக்கும்.

மூணாவது வாரத்துல regional team ஒரு SharePoint site-ஐ rename பண்றாங்க, delta token invalid ஆகுது. Connector-ஓட error rate alert அடிக்குது. Job அந்த site-ஐ ராத்திரி முழுசா re-scan பண்ணுது, எதுவும் miss ஆகல. Client-ஓட IT team-க்கான உங்க runbook இந்த case-ஐ சரியா explain பண்ணுது.

| அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| SharePoint sync | தினமும் ராத்திரி full re-read, சுமார் 6 மணி நேரம், அடிக்கடி throttle | ஒவ்வொரு 15 நிமிஷத்துக்கும் delta, சுமார் 1 நிமிஷம் |
| Salesforce sync | தினசரி export | ஒவ்வொரு 30 நிமிஷத்துக்கும் |
| இன்னும் search-ல வர்ற deleted documents | பல டஜன் | ஒண்ணும் இல்லை, வாரா வாரம் check |
| Failed sync-ஐ கவனிக்க ஆகுற நேரம் | நாள் கணக்கு | நிமிஷங்கள், alerts மூலமா |

## பொதுவா பண்ற தப்புகள்

- **ஒவ்வொரு தடவையும் full re-sync.** Change tokens அல்லது modified-since queries use பண்ணுங்க.
- **Deletions-ஐ கண்டுக்காம விடுறது.** Delete ஆன, expire ஆன documents தொடர்ந்து quote ஆகிக்கிட்டே இருக்கும்.
- **ரொம்ப பரந்த access.** Tenant முழுசுக்கும் இல்ல, பேர் சொன்ன sites, objects-க்கு read-only access மட்டும் கேளுங்க.
- **Fail ஆன பிறகு resume இல்லாதது.** Page 9,000-ல crash ஆனா page 1-ல இருந்து restart ஆகக்கூடாது.
- **சத்தமே இல்லாத connectors.** Sync நின்னா யாருக்கும் alert போகலைன்னா, assistant அமைதியா பழசாகிடும்.
- **Client-ஓட IT team-க்கு runbook இல்லாதது.** Tokens உடைஞ்சா, permissions மாறினா, site rename ஆனா என்ன பண்ணணும்னு எழுதி வைங்க.
- **Run முடியறதுக்கு முன்னாடியே sync cursor-ஐ save பண்றது.** அப்புறம் crash ஆனா changes எப்பவுமே skip ஆகிடும்.
- **Metadata மட்டும் மாறினாலும் modified ஆன ஒவ்வொரு file-ஐயும் re-embed பண்றது.**

## Custom connector தேவையில்லாத நேரங்கள்

- **ஒரு தடவை மட்டும் load** பண்ற fixed files: ஒருமுறை export பண்ணி ingest பண்ணிடுங்க.
- **Platform connector ஏற்கனவே அந்த system-ஐ cover பண்ணுது**, deletions-ஐ report பண்ணுது, permissions-ஐ படிக்குது.
- **User-களே தங்களுக்கு வேண்டிய சில documents-ஐ** நேரடியா upload பண்ணலாம்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு run-க்கும் counts record பண்ணி**, நின்னாலோ failures ஏறினாலோ alert வைங்க.
- **Success-க்கு அப்புறம் மட்டும் cursors save பண்ணுங்க**, full re-scan fallback-உம் வச்சுக்கோங்க.
- **வாரா வாரம் ids-ஐ reconcile பண்ணுங்க**, miss ஆன deletions பிடிபடும்.
- **Content-ஐ hash பண்ணுங்க**, மாறாத documents-ஐ skip பண்ணலாம்.
- **Schedules, limits-ஐ** client-ஓட IT team-கூட எழுத்துல ஒத்துக்கோங்க.

## Practice பண்ணுங்க

Microsoft Graph overview-ஐ படிச்சுட்டு, free-ஆ use பண்ணக்கூடிய, paging உள்ள ஏதாவது ஒரு API எடுத்துக்கோங்க (GitHub issues, ஒரு public dataset API, அல்லது developer tenant-ஓட Graph).

1. Paging வச்சு எல்லா items-ஐயும் எடுக்கிற, rate limits-ஐ மதிக்கிற, resume ஆகுற மாதிரி cursor store பண்ற ஒரு connector எழுதுங்க.
2. கடைசி run-க்கு அப்புறம் மாறின items-ஐ மட்டும் எடுக்கிற incremental mode-ஐயும், delete ஆன items-ஐ detect பண்ற check-ஐயும் சேருங்க.
3. ஒவ்வொரு run-க்கும் counts (read, added, updated, deleted, failed) record பண்ணி, ஒரு வரி summary print பண்ணுங்க.
4. Connector-ஐ ஓட்டுங்க, source-ல ஒரு file-ஐ delete பண்ணுங்க, திரும்ப ஓட்டுங்க, அந்த file-ஓட chunks index-ல இருந்து போயிடுச்சான்னு confirm பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க connector-ஐ தொடர்ந்து ரெண்டு தடவை ஓட்டி, ரெண்டாவது run மாறினதை மட்டும் (ஒரு deletion உட்பட) எடுக்குறதை காட்ட முடியும்.
