## இது என்ன

Fine-tuning ஒரு model-ஐ மாத்துது. **Model merging** ரெண்டு அல்லது அதுக்கு மேல models-ஓட weights-ஐ கலந்து ஒரே model-ஆ சேர்க்குது. Training run எதுவும் தேவையில்ல: merge-னா weight files மேல பண்ற arithmetic தான்.

Models **ஒரே base model**-ல இருந்து fine-tune ஆனப்போ தான் merging நல்லா work ஆகும். ஏன்? Fine-tuning weights-ஐ ஆரம்பிச்ச இடத்துல இருந்து கொஞ்ச தூரம் தான் நகர்த்தும். ஒரே base-ல இருந்து fine-tune ஆன ரெண்டு models இன்னும் அதுக்கு பக்கத்துலயும் ஒண்ணுக்கொண்ணு பக்கத்துலயும் இருக்கும், weight number 1,000-க்கு ரெண்டுலயும் கிட்டத்தட்ட ஒரே அர்த்தம் தான். Scratch-ல இருந்து train ஆன ரெண்டு models அவற்றோட features-ஐ வேற வேற order-ல கத்துக்கும், அதனால அவற்றை average பண்ணா சம்பந்தமில்லாத numbers கலக்கும், பெரும்பாலும் ரெண்டுமே உடைஞ்சுடும்.

ஏன் merge பண்ணணும்?

- **Mixed requests-க்கு ஒரே model.** ஒரு request-க்கு ரெண்டு skills தேவைப்பட்டா (ஒரு complaint-ஐ classify பண்ணி reply-ஐ draft பண்றது), merged model அதை ஒரே call-ல handle பண்ணும், models-க்கு நடுவுல தேர்ந்தெடுக்க router எதுவும் வேண்டாம்.
- **Ship பண்ண ஒரே file.** Merged model ஒரு சாதாரண model தான். எந்த runtime-உம் அதை load பண்ணலாம், adapter support இல்லாதவை கூட.
- **வரிசையா train பண்றதை விட குறைவான forgetting.** Task A-ல train பண்ணி அப்புறம் task B-ல train பண்ணா, model பெரும்பாலும் A-ஐ மறந்துடும். ஒவ்வொரு task-ஐயும் தனியா train பண்ணி merge பண்ணா அந்த risk குறையும், ஆனா அதுக்குன்னு ஒரு பிரச்சனை வரும்: tasks-ஓட மாற்றங்கள் ஒண்ணோட ஒண்ணு interfere பண்ணும், அதனால ஒவ்வொரு task-ஐயும் திரும்ப test பண்ணணும்.
- **GPUs வேண்டாம்.** Simple merges CPU-லயே run ஆகும். Models-க்கு disk space-உம் memory-உம் தான் வேணும், GPU இல்ல.

Inputs LoRA adapters-ஆ இருக்கும்போது, merging உங்களுக்கு memory-ஐ மிச்சப்படுத்தித் **தராது**. LoRA adapter சின்னது. உதாரணமா, Llama-3-8B shape-ல இருக்குற ஒரு model-ஓட ஒவ்வொரு linear layer-லயும் rank 16-னா சுமார் 42 million parameters, 16-bit-ல சுமார் 84 MB; base 16-bit-ல சுமார் 16 GB. மூணு adapters base-க்கு சுமார் 1.6% தான் சேர்க்கும். அவற்றை merge பண்ணா கிட்டத்தட்ட எதுவும் மிச்சமாகாது.

Merging ஒரு **ensemble**-ல இருந்தும் வேற. Ensemble ஒவ்வொரு request-க்கும் பல models-ஐ run பண்ணி அவற்றோட பதில்களை சேர்க்குது, அதனால ஒவ்வொரு request-க்கும் பல calls செலவாகும். Merge weights-ஐ ஒரே தடவை சேர்க்குது; அதுக்கப்புறம் ஒரே model-ஐ சாதாரண cost-ல serve பண்ணுவீங்க.

Reputation பத்தி ஒரு note. 2024-ல Hugging Face-ஓட Open LLM Leaderboard-ஓட top முழுக்க merges தான் இருந்துச்சு. அவற்றோட scores பெரும்பாலும் real use-ல அப்படியே வரலைன்னு சொல்லி, leaderboard team merges-ஐ default-ஆ hide பண்ணாங்க. Leaderboard-ஏ March 2025-ல retire ஆயிடுச்சு. பாடம் அப்படியே இருக்கு: ஒரு merge-ஓட public scores உங்க tasks பத்தி கொஞ்சம் தான் சொல்லும்.

```flow
title: Merging fine-tuned models
Base model -> Fine-tune for task A | adapter or full
Base model -> Fine-tune for task B
Fine-tune for task A -> Task vector A | A minus base
Fine-tune for task B -> Task vector B | B minus base
Task vector A -> Combine | average, SLERP, TIES, DARE
Task vector B -> Combine
Combine -> Merged model
Merged model -> Test every task and safety
Test every task and safety -[pass the bar]-> Ship one model
Test every task and safety -[miss the bar]-> Keep separate models
```

## இது எப்படி work ஆகுது

### Task vectors

Fine-tuned model-ஓட weights-ல இருந்து base model-ஓட weights-ஐ கழிச்சா உங்களுக்கு ஒரு **task vector** கிடைக்கும்: fine-tuning பண்ணின மாற்றம். Task vectors-ஐ base-ல கூட்டினா skills சேரும். ஒண்ணை கழிச்சா ஒரு behaviour குறையும். Task vectors-க்கு பேர் வச்ச paper (Ilharco and others, ICLR 2023), toxic text-ல இருந்து கத்துக்கிட்ட ஒரு task vector-ஐ கழிச்சு, GPT-2 ரொம்ப குறைவான toxic outputs-ஐ குடுக்குற மாதிரி பண்ணுச்சு.

LoRA-ல, adapter task vector-ஐ factored form-ல store பண்ணுது: A, B-ங்குற ரெண்டு மெல்லிய matrices, அவற்றோட product B times A தான் ஒவ்வொரு layer-லயும் வர்ற மாற்றம். இந்த detail பின்னாடி முக்கியமாகும். A matrices-ஐயும் B matrices-ஐயும் தனித்தனியா சேர்க்குறதும், உண்மையான மாற்றங்களை சேர்க்குறதும் ஒண்ணு இல்ல.

### Weighted average-உம் task arithmetic-உம்

ரொம்ப simple merge-னா task vectors-ஓட ஒரு weighted sum-ஐ base-ல கூட்டுறது. Weights 0.5, 0.5-னா அது ஒரு average; weights 1.0, 1.0-னா அது plain **task arithmetic**. ஒரே base-ல இருந்து வர்ற models-க்கு averaging ஆச்சரியப்படுற அளவுக்கு நல்லா work ஆகும். "Model soups" paper (Wortsman and others, ICML 2022) ஒரு model-ஓட நிறைய fine-tuned versions-ஐ average பண்ணி, பெரும்பாலும் best single version-ஐயே தாண்டுச்சு, extra running cost எதுவும் இல்லாம.

பலவீனம் interference. ஒரே ஒரு task பண்ணின மாற்றத்தை average பாதியாக்கிடும், ரெண்டு tasks ஒரு weight-ஐ எதிர் திசைல தள்ளும்போது அவை ஒண்ணை ஒண்ணு cancel பண்ணிடும்.

### SLERP

**Spherical linear interpolation** ரெண்டு models-ஐ நேர் கோட்டுக்கு பதிலா ஒரு arc வழியா blend பண்ணுது. ஏன் arc? ரெண்டு weight vectors வேற வேற திசைல point பண்ணா, அவற்றுக்கு நடுவுல இருக்குற நேர் கோட்டோட midpoint ரெண்டையும் விட சின்னதா இருக்கும். Model-ஓட weights சுருங்கும், அது ரெண்டு models-ஐயும் மழுங்கடிக்கலாம். Arc size-ஐ காப்பாத்தும். 0-ல இருந்து 1 வரை இருக்குற ஒரு factor `t` blend-ஐ set பண்ணும்: 0-னா முதல் model, 1-னா ரெண்டாவது. SLERP சரியா ரெண்டு models-ஐ தான் எடுக்கும்; மூணாவதுக்கு திரும்ப merge பண்ணுங்க.

### TIES-உம் DARE-உம்

Fine-tuning கிட்டத்தட்ட எல்லா weights-ஐயும் மாத்தும், ஆனா பெரும்பாலான மாற்றங்கள் ரொம்ப சின்னவை. இந்த சின்ன மாற்றங்கள் கொஞ்சம் தான் சேர்க்கும், ஆனாலும் merge பண்ணும்போது மோதும். **TIES** (Yadav and others, NeurIPS 2023) ஒவ்வொரு task vector-ஐயும் மூணு steps-ல clean பண்ணுது:

1. **Trim.** ஒவ்வொரு task vector-லயும் பெரிய மாற்றங்களை மட்டும் வச்சுக்கோங்க. `density` setting-னா வச்சுக்குற share: 0.3-னா top 30%-ஐ வச்சுக்கும்.
2. **ஒரு sign-ஐ elect பண்ணுங்க.** ஒவ்வொரு weight-க்கும், kept changes-ஐ கூட்டுங்க. மொத்த மாற்றம் அதிகமா இருக்குற திசை ஜெயிக்கும்.
3. **Disjoint mean.** ஜெயிச்ச sign கூட ஒத்துப்போற kept changes-ஐ மட்டும் average பண்ணுங்க. ஒரே ஒரு task பண்ணின மாற்றம் அதோட முழு size-ஓட இருக்கும்.

**DARE** (Yu and others, 2023) trim step-ஐ replace பண்ணுது. அது ஒவ்வொரு task vector-ஓட மாற்றங்கள்ல ஒரு random share-ஐ drop பண்ணி, மொத்த effect கிட்டத்தட்ட அதே அளவுல இருக்க மிச்சம் இருக்குறதை scale up பண்ணுது. இதை TIES கூட `dare_ties`-ஆ சேர்க்கலாம்: DARE-ஓட random drop, அப்புறம் TIES-ஓட sign election.

ரெண்டு methods-ஐயும் அறிமுகப்படுத்தின papers, plain averaging-ஐ விட gains-ஐ report பண்றாங்க. இதை உங்க சொந்த tasks-ல check பண்ணுங்க. Model Breadcrumbs, DELLA மாதிரி புது variants இருக்கு, mergekit அவற்றை support பண்ணுது. ஒரு evolutionary search நல்ல merge recipes-ஐ தானா கண்டுபிடிக்க முடியும்னு Sakana AI 2024-ல காட்டுச்சு. முதல்ல TIES-ஐ நல்லா கத்துக்கோங்க.

**உங்க browser-லயே try பண்ணுங்க.** ரெண்டு task vectors: weight 0-ல ஒரு conflict, weight 3-ல ரெண்டும் ஒத்துப்போகுது, weights 4, 5-ல ஒரே ஒரு task மட்டும் பண்ணின மாற்றங்கள்.

```python
import numpy as np

# Changes two fine-tunes made to the same 8 weights (their task vectors).
# Weight 0: the tasks disagree. Weight 3: they agree. Weights 4 and 5: only one task cares.
# The rest are tiny changes, mostly noise.
task_a = np.array([ 0.90, 0.02, -0.03, 0.80, 0.01, -0.70,  0.02, 0.00])
task_b = np.array([-0.85, 0.03,  0.02, 0.75, 0.60,  0.01, -0.02, 0.01])

def ties(vectors, density=0.4):
    stacked = np.stack(vectors)
    # 1. Trim: in each vector, keep only the largest changes (the top `density` share).
    trimmed = []
    for v in stacked:
        cut = np.quantile(np.abs(v), 1 - density)
        trimmed.append(np.where(np.abs(v) >= cut, v, 0.0))
    trimmed = np.stack(trimmed)
    # 2. Elect a sign per weight: the direction with more total change wins.
    sign = np.where(trimmed.sum(axis=0) >= 0, 1.0, -1.0)
    # 3. Disjoint mean: average only the kept changes that agree with that sign.
    agree = (np.sign(trimmed) == sign) & (trimmed != 0)
    count = np.maximum(agree.sum(axis=0), 1)
    return (trimmed * agree).sum(axis=0) / count

average = (task_a + task_b) / 2
merged = ties([task_a, task_b])
for name, v in [("task A ", task_a), ("task B ", task_b), ("average", average), ("TIES   ", merged)]:
    print(name, v.round(2) + 0.0)
```

Output:

```text
task A  [ 0.9   0.02 -0.03  0.8   0.01 -0.7   0.02  0.  ]
task B  [-0.85  0.03  0.02  0.75  0.6   0.01 -0.02  0.01]
average [ 0.03  0.02  0.    0.78  0.3  -0.34  0.    0.  ]
TIES    [ 0.9   0.    0.    0.78  0.6  -0.7   0.    0.  ]
```

Weight by weight-ஆ படிங்க. Average weight 0-ஐ கிட்டத்தட்ட ஒண்ணுமே இல்லாத அளவுக்கு cancel பண்ணிடுது, அதனால ரெண்டு tasks-உம் அதை இழக்குது; weights 4, 5-ஐ பாதியாக்கிடுது. TIES 4, 5-ஐ முழு size-ல வச்சு, noise-ஐ clear பண்ணுது. ஆனா weight 0-ஐ பாருங்க: TIES task A-ஓட 0.9-ஐ வச்சுக்கிட்டு, task B-ஓட மாற்றத்தை முழுசா தூக்கி போடுது. TIES conflicts-ஐ மறைய வைக்காது. அது ஒரு winner-ஐ தேர்ந்தெடுக்குது, தோத்த task அதுக்கு விலை குடுக்குது. அதனால தான் ஒரு merge-க்கு அப்புறம் ஒரு precise task பெரும்பாலும் drop ஆகுது.

### Layer stacking

Weights-ஐ கலக்குறதுக்கு பதிலா, வேற வேற models-ஓட layers-ல இருந்து ஒரு model-ஐ build பண்ணலாம், இதை சில சமயம் "frankenmerge"-னு சொல்வாங்க. இது ஒரு model-ஐ பெரிசாக்கலாம். SOLAR 10.7B (Kim and others, 2023) ஒரு 32-layer 7B model-ஓட ரெண்டு copies-ஐ எடுத்து, ஒவ்வொண்ணுலயும் 8 layers-ஐ நீக்கி, அவற்றை 48 layers-ஆ சேர்த்துச்சு. நல்லா work ஆக அதுக்கு further pretraining தேவைப்பட்டுச்சு, பெரும்பாலான stacked models-க்கும் அப்படி தான்.

### PEFT வச்சு LoRA adapters-ஐ merge பண்றது

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("base-model-id")
model = PeftModel.from_pretrained(base, "adapters/complaints", adapter_name="complaints")
model.load_adapter("adapters/replies", adapter_name="replies")

# ties_svd applies TIES to the real change (B times A) of each layer, then compresses it back to a LoRA.
model.add_weighted_adapter(
    adapters=["complaints", "replies"], weights=[1.0, 1.0],
    adapter_name="merged", combination_type="ties_svd", density=0.5,
)
model.set_adapter("merged")
merged = model.merge_and_unload()   # one plain model, no adapter needed at run time
merged.save_pretrained("merged-model")
```

PEFT-ல கவனிக்க வேண்டியவை (version 0.22-ஓட check பண்ணது):

- Plain `linear`, `ties`, `dare_*` types A, B matrices-ஐ தனித்தனியா சேர்க்கும். PEFT-ஓட சொந்த documentation `linear`-ஐ ஒரு rough approximation-னு சொல்லுது. உண்மையான மாற்றத்து மேல work பண்ற `_svd` types-ஐ prefer பண்ணுங்க.
- Plain types-க்கு எல்லா adapters-உம் ஒரே rank `r`-ல இருக்கணும். `_svd` types-க்கு அது தேவையில்ல.
- `cat` adapters-ஐ பக்கம் பக்கமா சேர்க்கும். அது மாற்றங்களோட exact sum-ஐ குடுக்கும், ஆனா புது adapter-ஓட rank எல்லா ranks-ஓட கூட்டுத்தொகையா இருக்கும்.
- DoRA adapters support ஆகாது.

### mergekit வச்சு full models-ஐ merge பண்றது

Full fine-tunes-க்கு, open-source tool mergekit ஒரு சின்ன YAML file-ல இருந்து merge-ஐ run பண்ணுது:

```yaml
merge_method: ties
base_model: ./base-8b
models:
  - model: ./complaints-8b
    parameters: {density: 0.5, weight: 1.0}
  - model: ./replies-8b
    parameters: {density: 0.5, weight: 1.0}
dtype: bfloat16
```

`mergekit-yaml merge.yml ./merged` வச்சு run பண்ணுங்க. TIES-க்கு, mergekit default-ஆ மொத்த weight-ஆல divide பண்ணும் (`normalize`), அதனால weights 1.0, 1.0 ஒரு சம blend மாதிரி act பண்ணும்.

### Settings-ஐ தேர்ந்தெடுக்குறது

Measure பண்ற வரைக்கும் merge settings வெறும் guesses தான். ஒரு சின்ன search மலிவு, ஏன்னா ஒரு merge-க்கு training run தேவையில்ல.

1. ஒவ்வொரு task-க்கும் ஒரு சின்ன **dev set**-ஐ தனியா வச்சுக்கோங்க, உதாரணமா 100-ல இருந்து 200 examples, final test set-ல இருந்து தனியா.
2. சம weights-ல ஆரம்பிச்சு density 0.2, 0.5, 0.8-ஐ try பண்ணுங்க. SLERP-க்கு, `t` 0.3, 0.5, 0.7-ஐ try பண்ணுங்க.
3. ஒரு task drop ஆனா, அதோட weight-ஐ ஏத்துங்க, உதாரணமா 1.0-ல இருந்து 1.5-க்கு, திரும்ப try பண்ணுங்க.
4. Average score-ஐ வச்சு இல்ல, உங்க acceptance bar-ஐ வச்சு best setting-ஐ வச்சுக்கோங்க. அப்புறம் test set-ஐ ஒரே ஒரு தடவை run பண்ணுங்க.
5. எந்த merge-ஐயும் திரும்ப build பண்ண முடியுற மாதிரி, ஒவ்வொரு config-ஐயும் அதோட scores கூட save பண்ணுங்க.

| Method | எப்படி சேர்க்குது | பலம் | கவனிக்க வேண்டியது |
| --- | --- | --- | --- |
| Weighted average | Task vectors-ஓட weighted sum | Simple baseline, பெரும்பாலும் நல்லது | Single-task மாற்றங்களை பாதியாக்கும்; conflicts cancel ஆகும் |
| SLERP | ரெண்டு models-ஐ ஒரு arc வழியா blend பண்ணும் | Weight size-ஐ காப்பாத்தும்; smooth blend | ஒரு தடவைக்கு ரெண்டு models |
| TIES | Trim, sign elect, disjoint mean | பல tasks-க்கு இன்னும் நல்லது | Conflict-ல ஒரு task தோக்கும்; density-ஐ tune பண்ணுங்க |
| DARE | Random drop, அப்புறம் rescale | TIES கூட நல்லா சேரும் | Random: சில seeds-ஐ compare பண்ணுங்க |
| Layer stacking | Layers-ஐ சேர்க்கும், size-ஐ பெரிசாக்கலாம் | பெரிய model-ஐ உருவாக்கலாம் | பொதுவா further training தேவை |

## ஒரு worked example

Mumbai-ல ஒரு bank-கிட்ட மூணு LoRA adapters இருக்கு, எல்லாமே ஒரே open 8B base model மேல rank 16: complaint classification, English-லயும் Hindi-லயும் reply drafting, KYC field extraction. Branch staff ஒரு முழு customer letter-ஐ paste பண்றாங்க, நிறைய letters reply-உம் தேவைப்படுற complaints. Bank-ஓட IT team approve பண்ணின offline app ஒரு தடவைக்கு ஒரு model file-ஐ தான் load பண்ணும், ஒவ்வொரு request-க்கும் ஒரு adapter-ஐ தேர்ந்தெடுக்க முடியாது. KYC scanning app-ல ஒரு தனி screen, ஒரு நாளைக்கு சில தடவை தான் use ஆகும்.

இங்க merge பண்ண காரணம் memory இல்ல. 16-bit-ல சுமார் 16 GB இருக்குற base-க்கு மூணு adapters சுமார் 250 MB தான் சேர்க்கும். காரணங்கள்: ஒரே model file, ஒரு mixed letter-க்கு ஒரே call.

Merge பண்றதுக்கு முன்னாடி, team test sets-ஐயும் bar-ஐயும் எழுதி வைக்குது:

- **Complaints:** label பண்ணின 400 letters; accuracy.
- **Replies:** 150 letters; ரெண்டு reviewers ஒவ்வொரு draft-க்கும் ஒரு rubric வச்சு 1-ல இருந்து 5 வரை score போடுறாங்க, அந்த scores average பண்ணப்படும்.
- **KYC:** scan பண்ணின 300 documents; சரியா exact-ஆ extract ஆன fields-ஓட share.
- **Safety:** assistant refuse பண்ண வேண்டிய 200 prompts, உதாரணமா இன்னொரு customer-ஓட account details கேக்குற requests.
- **Bar:** எந்த task-உம் அதோட தனி adapter-ஐ விட 2 points-க்கு மேல கீழ போகக்கூடாது (replies-க்கு 0.2), refusals குறையக்கூடாது.

அவங்க தனி dev sets-ல tune பண்ணி, அப்புறம் test sets-ஐ run பண்றாங்க. கீழ இருக்குற numbers illustration-க்கு தான், measure பண்ணின results இல்ல.

| --- | --- | --- | --- | --- | --- |
| தனி adapters (target) | எதுவும் இல்ல | 93% | 4.3 | 96% | target |
| மூணோட average | `svd`, ஒவ்வொண்ணுக்கும் weights 1/3 | 89% | 4.0 | 84% | இல்ல |
| மூணோட TIES | `ties_svd`, density 0.5, weights 1.0 | 92% | 4.2 | 88% | இல்ல: KYC |
| TIES, KYC weight ஏத்தினது | மேல உள்ள மாதிரி, KYC weight 1.5 | 91% | 4.1 | 91% | இல்ல: KYC |
| Complaints, replies-ஓட TIES | `ties_svd`, density 0.5 | 92% | 4.2 | n/a | ஆமா |

Plain average ஒவ்வொரு skill-ஐயும் மூணுல ஒரு பங்கா dilute பண்ணுது, அதனால எல்லா இடத்துலயும் fail ஆகுது. TIES இன்னும் நல்லா பண்ணுது, ஆனா ரொம்ப precise task-ஆன KYC extraction, அது தாங்க முடியாத conflicts-ல தோக்குது. அதோட weight-ஐ ஏத்தினா KYC-க்கு உதவுது, ஆனா மத்த tasks-ஐ பாதிக்க ஆரம்பிக்குது.

அதனால team ரெண்டு files-ஐ ship பண்ணுது. Letter screen, merged complaints-and-replies model-ஐ use பண்ணுது, அது ஒரு mixed letter-ஐ ஒரே call-ல handle பண்ணும். Scan screen, ஒரு document scan ஆகும்போது மட்டும், KYC adapter-ஐ உள்ள fold பண்ணின base-ஆன ரெண்டாவது model-ஐ load பண்ணுது. Safety set அதே refusal count-ஓட pass ஆகுது. எந்த adapter-உம் train ஆகாத behaviour-ஐ கூட merging பலவீனப்படுத்தலாம்ங்குறதால அவங்க அதை திரும்ப run பண்ணாங்க.

## பொதுவா பண்ற தப்புகள்

- **வேற வேற bases-ல இருந்து வர்ற models-ஐ merge பண்றது.** Inputs ஒரே tokenizer-ஐயும் chat template-ஐயும் share பண்ணுதான்னும் check பண்ணுங்க. வேற வேற prompt formats-ஐ எதிர்பார்க்குற models-ஐ merge பண்ணா உடைஞ்ச replies வரலாம்.
- **Memory மிச்சப்படுத்த LoRA adapters-ஐ merge பண்றது.** Adapters சின்னவை; மிச்சமாகுறது ரொம்ப கொஞ்சம்.
- **Average score-ஐ வச்சு judge பண்றது.** ஒரு task மோசமா drop ஆனாலும் average-ல merge சரியா தெரியலாம். ஒவ்வொரு task-ஐயும் அதோட சொந்த target கூட compare பண்ணுங்க.
- **Test set-ல tune பண்றது.** Test set-ல density-யையும் weights-ஐயும் தேர்ந்தெடுத்தா, real use-ல வர்றதை விட test score நல்லா தெரியும். Dev set-ஐ use பண்ணுங்க.
- **LoRA adapters மேல plain `linear` அல்லது `ties`-ஐ use பண்ணி exact sum-ஐ எதிர்பார்க்குறது.** இந்த types A, B matrices-ஐ தனித்தனியா சேர்க்கும். Exact sum-க்கு `cat`-ஐ use பண்ணுங்க; `svd_rank` ranks-ஓட கூட்டுத்தொகைக்கு சமமா அல்லது அதுக்கு மேல இருக்கும்போது மட்டும் தான் `_svd` types exact.
- **Safety checks-ஐ skip பண்றது.** ஒரு 2024 study (Hammoud and others, Findings of EMNLP), merging ஒரு model-ஓட பலவீனமான safety behaviour-ஐ merged model-க்குள்ள கொண்டு வரலாம்னு கண்டுபிடிச்சுது.
- **Public merges-ஐ நம்புறது.** Download பண்ணின merge-ஐ உங்க சொந்த data-ல test பண்ணுங்க.
- **Licence-ஐ மறக்குறது.** ஒரு merge அதுல இருக்குற ஒவ்வொரு model-ஓட terms-ஐயும் follow பண்ணணும். ஒரு non-commercial input, merge-ஐ நீங்க எப்படி use பண்ணலாம்னு limit பண்ணலாம், அதனால ஒவ்வொரு licence-ஐயும் படிங்க. சில licences naming rules-ஐயும் சேர்க்கும்: Llama 3.1-ஓட licence, அதுல இருந்து build பண்ணி share பண்ற model-ஓட பேர் "Llama"-ல ஆரம்பிக்கணும்னு கேக்குது.

## எப்போ merge பண்ணக்கூடாது

இந்த கேள்விகளை வரிசையா கேளுங்க:

1. **Adapters-ஐ தனித்தனியா serve பண்ண முடியுமா?** LoRA adapters-க்கு இது பொதுவா best choice. vLLM மாதிரி servers ஒரே base model-ஐ GPU memory-ல வச்சுக்கிட்டு, ஒவ்வொரு request-க்கும் வேற adapter-ஐ apply பண்ணும், ஒரே batch-ல கூட. உதாரணமா: `vllm serve base-model-id --enable-lora --lora-modules complaints=./adapters/complaints replies=./adapters/replies --max-loras 4`. ஒவ்வொரு request-உம் அதோட adapter-ஐ name பண்ணும். Runtime-ஆல இதை பண்ண முடியாதப்போ, அல்லது ஒரு request-க்கு ஒரே நேரத்துல பல skills தேவைப்படும்போது தான் முக்கியமா LoRA adapters-ஐ merge பண்ணுங்க.
2. **ஒரு task ரொம்ப precise-ஆ?** Extraction, maths, strict formats பெரும்பாலும் merge-ல தோக்கும். அதை தனியா வச்சுக்கோங்க.
3. **ஒரு multi-task fine-tune பண்ண உங்களால முடியுமா?** ஒவ்வொரு task-க்கும் data இருந்தா, mix-ல train பண்றது பெரும்பாலும் merge-ஐ விட நல்லது, ஏன்னா model tasks-ஐ balance பண்ண கத்துக்கும்.
4. **Models வேற வேற bases-ல இருந்து வருதா?** Merge பண்ணாதீங்க.

## Demo-ல இருந்து production-க்கு

- **Merges-ஐ models மாதிரியே version பண்ணுங்க.** Config file, input model versions, scores, test set versions எல்லாத்தையும் ஒண்ணா வச்சுக்கோங்க.
- **தனி models-ஐ வச்சுக்கோங்க**, fallback-ஆவும் comparison point-ஆவும்.
- **ஒவ்வொரு task-ஐயும், கூடவே general, safety checks-ஐயும் test பண்ணுங்க**, ஒவ்வொரு release-க்கு முன்னாடியும், நீங்க முன்னாடியே fix பண்ணின bar-ஓட.
- **எந்த input மாறினாலும் re-merge பண்ணி re-test பண்ணுங்க.** புது adapter version-னா புது merge.
- **ஒவ்வொரு input-ஓட licence-ஐயும் record பண்ணுங்க**, merged model-ஓட card-ல.

## Practice பண்ணுங்க

1. Hugging Face-ல ஒரு merged model-ஐ கண்டுபிடிச்சு அதோட card-ஐ படிங்க. எந்த models, எந்த method, எந்த settings use பண்ணாங்க? mergekit config சேர்க்கப்பட்டிருக்கா?
2. மேல இருக்குற browser example-ஐ run பண்ணுங்க. Task B-ஓட weight 0-ஐ -0.85-ல இருந்து -0.95-க்கு மாத்தி, run பண்றதுக்கு முன்னாடி TIES-ஓட output-ஐ predict பண்ணுங்க. அப்புறம் density 0.2, 0.8-ஐ try பண்ணுங்க.
3. ஒரே base மேல இருக்குற ரெண்டு சின்ன LoRA adapters-ஐ, `svd` வச்சு weights 0.5, 0.5-ல (ஒரு average) merge பண்ணுங்க, `ties_svd` வச்சு மூணு densities-லயும் merge பண்ணுங்க. ஒவ்வொண்ணையும் ஒரு task-க்கு 20 examples-ல score பண்ணி, எந்த setting-ஐ ship பண்ணுவீங்க, ஏன்னு எழுதுங்க.
4. உங்க சொந்த field-ல ஒரு merge-க்கு test plan எழுதுங்க: tasks, test sets, safety checks, acceptance bar.
