## இது என்ன

Fine-tuning ஒரு model-ஐ மாத்தும். **Model merging** ரெண்டு அல்லது அதிக models-ஐ அவற்றோட weights-ஐ கலந்து ஒண்ணா சேர்க்கும். பொதுவா models **ஒரே base model**-ல இருந்து fine-tune ஆனப்போ இது நல்லா வேலை செய்யும், ஏன்னா அவற்றோட weights பொருந்தும்.

எதுக்கு இதை பண்ணணும்?

- **ஒரு model-ல பல skills.** Complaints-க்கு ஒரு model-ஐயும் replies-க்கு இன்னொண்ணையும் fine-tune பண்ணிருந்தா, ஒரு merge ரெண்டையும் செய்யும்.
- **Tasks-ஐ வரிசையா train பண்றதால வர்ற forgetting இல்ல.** Task A-ல train பண்ணி, அப்புறம் task B-ல பண்ணா, model பெரும்பாலும் A-வை மறந்துடும். ஒவ்வொண்ணையும் தனியா train பண்ணி merge பண்ணா அது தவிர்க்கப்படும்.
- **GPUs தேவையில்ல.** எளிய merges weights மேல கணக்கு தான், ஒரு சாதாரண computer-ல run ஆகும்.
- **சிறிய deployments.** பல models-க்கு பதிலா ஒண்ணு, phones, laptops, குறைந்த memory உள்ள மற்ற devices-ல, அல்லது data device-ஐ விட்டு வெளியே போகக்கூடாத இடங்கள்ல பயனுள்ளது.

Merging ஒரு **ensemble**-ல இருந்து வேறுபட்டது. Ensemble பல models-ஐ run பண்ணி அவற்றோட பதில்களை சேர்க்கும், அதனால ஒவ்வொரு request-க்கும் பல calls செலவாகும். Merge weights-ஐ ஒரே தடவை சேர்க்கும்; அப்புறம் ஒரு model-ஐ மட்டும் normal cost-ல serve பண்ணுவீங்க.

Merging இன்னும் புதுசு, ஓரளவு experimental-உம். Open model leaderboards-ல நிறைய top entries merges தான், ஆனா results மாறுபடும், அதனால ஒவ்வொரு merge-ஐயும் test பண்ண வேண்டிய ஒரு புது model-ஆ பாருங்க.

```flow
title: Fine-tuned models-ஐ merge பண்றது
Base model -> Task A-க்கு fine-tune | adapter அல்லது full
Base model -> Task B-க்கு fine-tune
Task A-க்கு fine-tune -> Task vector A | A கழித்தல் base
Task B-க்கு fine-tune -> Task vector B | B கழித்தல் base
Task vector A -> சேர்க்குறது | average, SLERP, TIES, DARE
Task vector B -> சேர்க்குறது
சேர்க்குறது -> Merged model
Merged model -> ஒவ்வொரு task, பொது skills, safety-ஐ test பண்ணுங்க
```

## இது எப்படி work ஆகுது

**Task vectors.** ஒரு fine-tuned model-ஓட weights-ல இருந்து base model-ஓட weights-ஐ கழிச்சா, ஒரு **task vector** கிடைக்கும்: fine-tuning பண்ண மாற்றம். LoRA-ல, adapter தானே அடிப்படையில task vector தான். Base-ஓட task vectors-ஐ கூட்டினா skills சேரும், ஒண்ணை கழிச்சா ஒரு behaviour குறையும்; தேவையில்லாத திறன்களையோ biases-ஐயோ பலவீனப்படுத்த ஆராய்ச்சியாளர்கள் இதை use பண்ணிருக்காங்க.

**Linear combination.** எளிய merge-னா weights அல்லது task vectors-ஓட ஒரு weighted average. இது ஆச்சரியப்படும் அளவுக்கு நல்லா வேலை செய்யும், குறிப்பா ஒரே base-ல இருந்து வந்த models-க்கு. "Model soups" ஒரே model-ஓட பல fine-tuned versions-ஐ average பண்ணி, extra running cost இல்லாம accuracy-ஐ கூட்டுச்சு. Weights ஒரு model-ஐ இன்னொண்ணை விட அதிகம் மதிக்க விடும்.

**SLERP.** Spherical linear interpolation ரெண்டு models-ஐ நேர் கோட்டுக்கு பதிலா ஒரு வளைவு பாதையில கலக்கும், இது சாதாரண average-ஐ விட ஒவ்வொரு model-ஓட தன்மையை நல்லா காப்பாத்தலாம். 0-ல இருந்து 1 வரை ஒரு interpolation factor எந்த model-க்கு அதிக மதிப்புன்னு தீர்மானிக்கும். இது ஒரு நேரத்துல ரெண்டு models-ஐ merge பண்ணும்; மூணாவதை திரும்ப திரும்ப பண்ணி merge பண்ணுங்க.

**TIES, DARE.** Fine-tuning கிட்டத்தட்ட எல்லா weight-ஐயும் மாத்தும், ஆனா பெரும்பாலான மாற்றங்கள் ரொம்ப சின்னவை, கொஞ்சம் தான் சேர்க்கும். வெவ்வேற tasks-ல இருந்து வர்ற அந்த சின்ன மாற்றங்கள் merge பண்ணும்போது மோதலாம். ரெண்டு methods-உம் முதல்ல ஒவ்வொரு task vector-ஐயும் **prune** பண்ணி, முக்கிய மாற்றங்களை மட்டும் வச்சுக்கும்:

- **TIES** பெரிய மாற்றங்களை வச்சுக்கும், அப்புறம் merge பண்றதுக்கு முன்னாடி tasks ஒரு weight-ஐ எதிர் திசைகள்ல தள்ளுற இடங்கள்ல மோதல்களை தீர்க்கும்.
- **DARE** பெரும்பாலான மாற்றங்களை random-ஆ விட்டுடும், மிச்சத்தை அவற்றோட மொத்த தாக்கம் அப்படியே இருக்க rescale பண்ணும்.

ரெண்டும் பெரும்பாலும் சாதாரண averaging-ஐ விட தெளிவா நல்ல merges-ஐ தரும், அதிக models-ஐ merge பண்ணப் பண்ண அந்த நன்மை கூடும்.

**Layer stacking.** Weights-ஐ கலக்குறதுக்கு பதிலா, வெவ்வேற models-ஓட layers-ல இருந்து ஒரு model-ஐ கட்டுறது, சில நேரம் "frankenmerge"-னு சொல்வாங்க. சின்ன models-ல இருந்து ஒரு பெரிய model-ஐ செய்யலாம் (ஒரு team ஒரு 7B model-ஓட ரெண்டு copies-ல இருந்து ஒரு 10.7B model-ஐ கட்டுச்சு), ஏற்கனவே இருக்குற ஒண்ணுல இருந்து mixture-of-experts model-ஐ ஆரம்பிக்குற ஒரு வழியும் இது. இவை நல்லா வேலை செய்ய பொதுவா கூடுதல் training வேணும்.

**Concatenation** adapters-ஐ பக்கத்துல பக்கத்துல சேர்க்கும். எல்லா parameters-ஐயும் வச்சிருக்கும், அதனால memory மிச்சமாகாது, அரிதா தான் பயனுள்ளது.

PEFT-ஓட ரெண்டு LoRA adapters-ஐ merge பண்றது இப்படி இருக்கும்:

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("base-model-id")
model = PeftModel.from_pretrained(base, "adapters/complaints", adapter_name="complaints")
model.load_adapter("adapters/replies", adapter_name="replies")

# Combine into a new adapter; TIES keeps the strongest changes (density) and resolves conflicts.
model.add_weighted_adapter(
    adapters=["complaints", "replies"], weights=[1.0, 1.0],
    adapter_name="merged", combination_type="ties", density=0.3,
)
model.set_adapter("merged")
```

முழு models-க்கு, open-source tool mergekit ஒரு சின்ன configuration file-ல இருந்து merges-ஐ run பண்ணும்.

| Method | எப்படி சேர்க்கும் | பலம் | கவனிக்க வேண்டியவை |
| --- | --- | --- | --- |
| Weighted average | Weights அல்லது task vectors-ஐ average பண்ணும் | எளிது, பெரும்பாலும் நல்லது | Tasks இடையூறு பண்ணலாம் |
| SLERP | ரெண்டு models-ஐ ஒரு வளைவுல கலக்கும் | ரெண்டோட சீரான கலவை | ஒரு நேரத்துல ரெண்டு models |
| TIES | பெரிய மாற்றங்களை வச்சுக்கும், sign மோதல்களை தீர்க்கும் | பல tasks-க்கு நல்லது | Density setting-ஐ tune பண்ணணும் |
| DARE | பெரும்பாலான மாற்றங்களை random-ஆ விடும், rescale பண்ணும் | Robust, apply பண்ண எளிது | Randomness; ஒரு தடவைக்கு மேல test பண்ணுங்க |
| Layer stacking | Layers-ஐ சேர்க்கும், அளவை வளர்க்கலாம் | Upscale பண்ணலாம் அல்லது MoE கட்டலாம் | பொதுவா கூடுதல் training வேணும் |

**உங்க browser-லயே try பண்ணுங்க.** ரெண்டு task vectors-ஐ average பண்ணுங்க, அப்புறம் பெரிய மாற்றங்களை மட்டும் வச்சுக்குற ஒரு TIES-style merge-ஐ try பண்ணுங்க.

```python
import numpy as np

rng = np.random.default_rng(7)
base = rng.normal(size=10)
task_a = np.where(rng.random(10) < 0.3, rng.normal(0, 1, 10), rng.normal(0, 0.05, 10))
task_b = np.where(rng.random(10) < 0.3, rng.normal(0, 1, 10), rng.normal(0, 0.05, 10))

average = base + (task_a + task_b) / 2
def trim(v, keep=0.3):
    cut = np.quantile(np.abs(v), 1 - keep)
    return np.where(np.abs(v) >= cut, v, 0)
ties = base + trim(task_a) + trim(task_b)
print("average change:", (average - base).round(2))
print("TIES change:   ", (ties - base).round(2))
```

## ஒரு worked example

Mumbai-ல ஒரு bank-ல ஒரே open 8B base model மேல மூணு LoRA adapters இருக்கு: complaint classification, English, Hindi-ல reply drafting, KYC field extraction. அவங்க இன்டர்நெட் இல்லாத branch laptops-ல ஒரு model வேணும்னு விரும்புறாங்க.

மூணு merges-ஐ try பண்ணி, ஒவ்வொண்ணையும் ஒவ்வொரு task-ஓட சொந்த test set-லயும் test பண்றாங்க:

| Model | Complaint accuracy | Reply quality (reviewer score, 5-ல) | KYC extraction accuracy |
| --- | --- | --- | --- |
| தனி adapters (இலக்கு) | 93% | 4.3 | 96% |
| மூணுத்தோட weighted average | 89% | 4.0 | 84% |
| TIES, density 0.3 | 92% | 4.2 | 88% |
| Complaints, replies-ஓட TIES; KYC தனியா | 92% | 4.2 | 96% |

எண்கள் புரிய வைக்குறதுக்கான உதாரணம். ரொம்ப துல்லியம் வேணும்ங்குற extraction தான் ஒவ்வொரு முழு merge-லயும் அதிகம் பாதிக்கப்பட்டுச்சு. Team complaints, replies-க்கு ஒரு merged model-ஐ ship பண்ணி, KYC adapter-ஐ தனியா வச்சு, ஒரு document scan ஆகுறப்போ மட்டும் load பண்றாங்க. ரெண்டும் laptops-ல பொருந்தும். அவங்க safety, refusal checks-ஐயும் திரும்ப run பண்றாங்க, ஏன்னா எந்த adapter-உம் train ஆகாத behaviour-ஐ merging பலவீனப்படுத்தலாம்.

## பொதுவா பண்ற தப்புகள்

- **வெவ்வேற bases-ல இருந்து வந்த models-ஐ** risks புரியாம merge பண்றது. Results பொதுவா மோசமா இருக்கும்.
- **ஒரு task-ஐ மட்டும் test பண்றது.** ஒரு merge சத்தமில்லாம இன்னொரு task-ஐயோ பொது திறன்களையோ பாதிக்கலாம்.
- **Safety checks-ஐ தவிர்க்கிறது.** Merge பண்ணின பிறகு refusal, safety behaviour பலவீனமாகலாம்.
- **Leaderboard merges-ஐ கண்மூடித்தனமா நம்புறது.** சில benchmarks-க்காக tune பண்ணப்பட்டவை; உங்க சொந்த data-ல test பண்ணுங்க.
- **Memory சேமிக்க concatenation use பண்றது.** அது சேமிக்காது.
- **Licence-ஐ மறக்குறது.** ஒரு merge அதுல இருக்குற ஒவ்வொரு model-ஓட licence விதிமுறைகளையும் பெறும்.

## எப்போ merge பண்ணக்கூடாது

- **அதிக துல்லியம் வேண்டிய tasks** தனி adapters-ஆ வச்சுக்குறது நல்லா இருக்கலாம்.
- **ஒவ்வொரு task-க்கும் போதுமான data இருக்குற, ஒரு நல்ல multi-task fine-tune-ஐ உங்களால தாங்க முடியும்.**
- **பல adapters-ஐ serve பண்றது ஏற்கனவே மலிவு**, நிறைய servers அதை திறமையா support பண்ணுது.
- **Models வெவ்வேற base models-ல இருந்து வந்தவை.**

## Demo-ல இருந்து production-க்கு

- **Merges-ஐ models மாதிரி version பண்ணுங்க**: inputs, method, weights, settings-ஐ ஒரு config file-ல.
- **தனி adapters-ஐ வச்சிருங்க**, fallback-க்காகவும் compare பண்றதுக்காகவும்.
- **ஒவ்வொரு release-க்கு முன்னாடியும் ஒவ்வொரு task-ஐயும், கூடவே பொது, safety checks-ஐயும் test பண்ணுங்க.**
- **எந்த input model மாறினாலும் re-merge பண்ணி**, திரும்ப test பண்ணுங்க.
