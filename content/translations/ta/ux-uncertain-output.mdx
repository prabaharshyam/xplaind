## இது என்ன

Traditional software predictable: அதே input அதே output தரும், தப்பா இருந்தா அது ஒரு bug. AI output மாறும், இயல்பாகவே சில நேரம் தப்பாவும் இருக்கும். **உறுதியில்லாத output-க்கான UX**-னா அந்த உண்மைக்கு ஏத்த மாதிரி design பண்றது.

இலக்கு **calibrated trust**:

```flow
dir: LR
நம்பிக்கை குறைவு | ஒரு தப்புக்கு அப்புறம் useful tool-ஐ users ignore பண்றாங்க: வீணான value -> Calibrated trust | சரியா இருக்க வாய்ப்பு இருந்தா நம்புறது, உறுதி இல்லன்னா check பண்றது, சீக்கிரம் மீண்டு வர்றது: இலக்கு
Calibrated trust -> அதிக நம்பிக்கை | எல்லா பதிலையும் ஏத்துக்குறது, தப்புகளை customers-க்கு கடத்துறது: உண்மையான பாதிப்பு
```

Microsoft-ஓட Guidelines for Human-AI Interaction, Google-ஓட People + AI Guidebook மாதிரி research அடிப்படையிலான guidelines, ஒரு core set patterns-ல ஒத்துப்போகுது. இந்த lesson அதை, ஒரு screen-ல நீங்க எடுக்கக்கூடிய decisions-ஆ மாத்துது.

Chennai-ல ஒரு insurance company-ல product manager Divya-வை follow பண்ணுவீங்க. Agents தப்பான பதில்களை customers-க்கு சொன்ன பிறகு, அவங்க ஒரு AI coverage assistant-ஐ மறுபடி design பண்றாங்க. Lesson முடியும்போது, ஒரு தப்பான AI பதிலை users சில வினாடிகள்ல கவனிச்சு மீண்டு வர்ற ஒரு screen-ஐ design பண்ண முடியும்.

## இது எப்படி work ஆகுது

### Patterns

| Pattern | எப்படி இருக்கும் | ஏன் work ஆகுது |
| --- | --- | --- |
| **Expectations set பண்றது** | "உங்க policy documents பத்தின கேள்விகளுக்கு பதில் சொல்லும். Legal advice கொடுக்காது." | எதுக்கு இதை நம்பலாம்னு users-க்கு தெரியும் |
| **இது AI-ன்னு காட்டுறது** | Users தெரிஞ்சுக்க விரும்புற இடத்துல தெளிவான ஒரு label | எவ்வளவு கவனமா check பண்றதுன்னு users அதுக்கேத்த மாதிரி மாத்திக்குவாங்க |
| **Sources காட்டுறது** | Number போட்ட citations; ஒண்ணை tap பண்ணா சரியான passage வரும் | Users check பண்ணலாம், தப்பான பதில்கள் தனியா தெரியும் |
| **Uncertainty-ஐ signal பண்றது** | "Confidence குறைவு: தொகையை check பண்ணுங்க"; highlight பண்ண fields | கவனம் தேவையான இடத்துக்கு போகும் |
| **Correction-ஐ எளிதாக்குறது** | Edit பண்ணக்கூடிய drafts, ஒரு reason-ஓட ஒரே click-ல "இது தப்பு", undo | தப்புகளை சரி பண்றது மலிவு, feedback system-ஐ improve பண்ணும் |
| **மனுஷங்களுக்கு control கொடுக்குறது** | அனுப்புறதுக்கு முன்னாடி preview; பணம், messages, deletions-க்கு முன்னாடி confirm | விளைவுகளுக்கு ஒரு மனுஷ decision வேணும் |
| **Gracefully fail ஆகுறது** | "எனக்கு தெளிவான பதில் கிடைக்கல. Underwriting helpdesk-ஐ try பண்ணுங்க." | blank screens இல்லை, confident guesses இல்லை |
| **Progress காட்டுறது** | Streaming text; "3 documents-ஐ check பண்றேன்..." | Feedback இல்லாம காத்திருக்கிறது உடைஞ்சு போன மாதிரி இருக்கும் |

### Confidence-ஐ கவனமா signal பண்ணுங்க

"93.7% confident" மாதிரி துல்லியமான numbers scientific-ஆ தோணி, தவறான நம்பிக்கையை உண்டாக்கும்; குறிப்பா அந்த number சரியா calibrate ஆகாதப்போ. நல்ல options:

- System-க்கு உறுதியில்லாத குறிப்பிட்ட fields-ஐ highlight பண்ணுங்க;
- எளிய வார்த்தைகள்: "இந்த தொகை பத்தி எனக்கு உறுதி இல்லை";
- Retrieval பலவீனமா இருக்கும்போது, பதில் சொல்ல மறுத்து ஒரு ஆள்கிட்ட வழி காட்டுறது மாதிரி, behaviour-ஐ மாத்துங்க.

### இந்திய products-ல patterns

நிறைய இந்திய users AI-ஐ WhatsApp chats, voice assistants, regional-language apps-ல சந்திக்கிறாங்க; அங்க screens சின்னது, கவனம் குறைவு. Patterns இன்னும் பொருந்தும், சுருக்கமான வடிவத்துல. ஒரு WhatsApp bot பதிலை இப்படி முடிக்கலாம்: "Source: Policy section 4.2. இது சரியா தெரியலன்னா WRONG-னு reply பண்ணுங்க." ஒரு voice assistant சொல்லலாம்: "எனக்கு உறுதியில்லை. உங்களை ஒரு agent-கிட்ட connect பண்ணட்டுமா?" ஒரு regional-language app source passage-ஐ பதில் இருக்குற அதே மொழியில காட்டலாம். Users ஒரே நேரத்துல நிறைய context பார்க்க முடியாததால, சின்ன screens-ல sources-உம் எளிதான correction-உம் இன்னும் முக்கியம்.

### முதல் தப்புக்காக design பண்ணுங்க

ஒரு feature-ஐ நம்பணுமான்னு users சீக்கிரமே முடிவு பண்ணிடுவாங்க. உறுதியா தெரிஞ்ச ஒரு tool-ல இருந்து முதல் தப்பு வந்தா நம்பிக்கை சரிஞ்சு போகும். ஆரம்பத்துல இருந்தே அந்த tool தன்னோட limits-ஐயும் sources-ஐயும் காட்டியிருந்தா, முதல் தப்பு ரொம்ப குறைவா பாதிக்கும்: user அதை கண்டுபிடிச்சாங்க, product அவங்களுக்கு உதவுச்சு.

### உண்மையான errors-ஓட test பண்ணுங்க

Usability tests பெரும்பாலும் users ஒரு task-ஐ முடிக்க முடியுதான்னு பார்க்கும். AI features-க்கு, AI **வேணும்னே தப்பா** இருக்கும் cases-ஐயும் சேர்த்து, users கவனிச்சு மீண்டு வர்றாங்களான்னு பாருங்க. அதுதான் design-ஓட உண்மையான test.

```text
  Test plan for an AI answer screen
  8 questions:  6 with correct AI answers, 2 with planted errors
  Measure:      did the user spot the error?  how long did it take?
                did they know what to do next?
```

## ஒரு worked example

Chennai-ல ஒரு insurance company, agents customers-ஓட பேசும்போது policy coverage கேள்விகளுக்கு பதில் சொல்ல, தன்னோட agent app-ல ஒரு AI assistant சேர்க்குது.

**முதல் version** ஒரு confident paragraph பதிலை காட்டுது; sources இல்லை, limits இல்லை, problems-ஐ report பண்ண வழி இல்லை. எட்டு கேள்விகள் உள்ள ஒரு usability test-ல ரெண்டு பதில்கள் வேணும்னே தப்பா இருந்துச்சு. Agents அரிதா தான் check பண்ணாங்க, role-play-ல தப்பான **ரெண்டு** பதில்களும் customers-க்கு போச்சு.

**ரெண்டாவது version**, product manager Divya மறுபடி design பண்ணது:

| மாற்றம் | Agent இப்போ என்ன பார்க்கிறாங்க |
| --- | --- |
| Expectations | ஒரு header வரி: "Policy wordings-ல இருந்து AI பதில் சொல்லுது. Customers-க்கு advice கொடுக்குறதுக்கு முன்னாடி check பண்ணுங்க." |
| Sources | ஒவ்வொரு பதிலுக்கும் number போட்ட citations; ஒண்ணை tap பண்ணா சரியான clause வரும் |
| Graceful failure | Retrieval பலவீனமான matches மட்டும் கண்டுபிடிச்சா, பதில் "எனக்கு தெளிவான பதில் கிடைக்கல"ன்னு ஆரம்பிச்சு underwriting helpdesk-ஐ suggest பண்ணும் |
| Uncertainty | Amounts-உம் exclusions-உம் agent confirm பண்ணுறதுக்காக highlight ஆகும் |
| Correction | மூணு reasons-ஓட ஒரு "தப்பான பதில்" button, product team வாரம் ஒரு தடவை review பண்ணும் |

**அடுத்த test:**

| Measure | முதல் version | ரெண்டாவது version |
| --- | --- | --- |
| Agents கண்டுபிடிச்ச planted தப்பான பதில்கள் | ஒரு session-க்கு சராசரி 2-ல 0 | எல்லா sessions-உம் சேர்த்து 8-ல 7 |
| Agents-ஓட satisfaction score | 5-ல 3.1 | 5-ல 4.2 |
| முதல் உண்மையான தப்புக்கு அப்புறம் usage | குறைஞ்சுது | அதிகரிச்சுது |

Agents ரெண்டாவது version-ஐ **அதிகமா** நம்புனாங்க, குறைவா இல்லை, ஏன்னா control தங்ககிட்ட இருக்குன்னு feel பண்ணாங்க, ஒரு பதில் ஏன் வந்துச்சுன்னும் பார்க்க முடிஞ்சுது. Production-ல முதல் உண்மையான தப்புகள் வந்ததுக்கு அப்புறமும், usage குறையாம தொடர்ந்து வளர்ந்துச்சு.

## பொதுவா பண்ற தப்புகள்

- **இது AI-ன்னு மறைக்கிறது.** Users தங்களுக்கு தெரிஞ்சதை வச்சு தான் நம்பிக்கையை calibrate பண்றாங்க.
- **Sources இல்லாத confident பதில்கள்.** Users check பண்ண முடியாது, அதனால அதிகமா நம்புவாங்க.
- **போலி துல்லியம்.** "93.7% confident" தவறான நம்பிக்கையை உண்டாக்கும்; எளிய signals use பண்ணுங்க.
- **திருத்த கஷ்டமான outputs.** Final-ஆ edit பண்ண முடியாத outputs, users தப்புகளை ஏத்துக்க வைக்கும்.
- **வெற்றி cases-ஐ மட்டும் test பண்றது.** AI தப்பா இருக்கும்போது users என்ன பண்றாங்கன்னு test பண்ணுங்க.
- **Blank failures.** அடுத்த step இல்லாத "ஏதோ தப்பா போச்சு" users-ஐ மாட்டிவிடும்.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற Microsoft-ஓட Guidelines for Human-AI Interaction-ஐயும், explainability and trust பத்தின PAIR chapter-ஐயும் படிங்க.

1. **Audit.** நீங்க use பண்ற ஒரு AI feature-ஐ எடுத்து, ஐந்து guidelines-ஓட check பண்ணுங்க. எங்க fail ஆகுதுன்னு note பண்ணுங்க.
2. **Sketch.** Expectations, sources, uncertainty signals, எளிதான correction இருக்குற ஒரு மறுவடிவமைச்ச screen-ஐ paper-ல sketch பண்ணுங்க.
3. **Test.** ஒரு சரியான, ஒரு தப்பான AI பதிலோட உங்க sketch-ஐ ரெண்டு பேருக்கு காட்டி, அவங்க தப்பானதை கண்டுபிடிக்கிறாங்களான்னு note பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு user தப்பான AI பதிலை கவனிச்சு சில வினாடிகள்ல மீண்டு வர்ற ஒரு design-ஐ காட்ட முடியும்.
