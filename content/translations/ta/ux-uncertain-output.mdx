## இது என்ன

பழைய மாதிரியான software predictable: அதே input-க்கு அதே output வரும், தப்பா இருந்தா அது நீங்க fix பண்ணக்கூடிய ஒரு bug. AI output மாறிட்டே இருக்கும், எதுவும் உடையாம இருந்தாலும் அது இயல்பாவே சில நேரம் தப்பா இருக்கும். **உறுதியில்லாத output-க்கான UX**-னா அந்த உண்மைக்காக design பண்றது.

Goal **calibrated trust**: ஒவ்வொரு case-லயும், AI எவ்வளவு நம்பிக்கைக்கு தகுதியோ அவ்வளவு தான் users அதை நம்பணும்.

```flow
dir: LR
Under-trust | ஒரு தப்புக்கு அப்புறம் users ஒரு useful tool-ஐ ignore பண்றாங்க: value வீணாகுது -> Calibrated trust | சரியா இருக்க வாய்ப்பிருந்தா நம்புறது, உறுதியில்லன்னா check பண்றது, சீக்கிரம் recover ஆகுறது
Calibrated trust -> Over-trust | எல்லா answer-ஐயும் ஏத்துக்கிட்டு தப்புகளை அடுத்தவங்களுக்கு கடத்துறது: உண்மையான பாதிப்பு
```

Over-trust-க்கு ஒரு பேர் இருக்கு: **automation bias**, ஒரு machine-ஓட output-ஐ check பண்ணாம ஏத்துக்குற பழக்கம்; மக்கள் busy-ஆ இருக்கும்போதோ, machine பொதுவா சரியா தெரியும்போதோ இது இன்னும் வலுவாகுது. Human in the loop-ஐ design பண்றது பத்தின lesson இதை ஆழமா பேசுது. இங்க point simple: உறுதியா தெரியுற ஒரு screen, check பண்றதை நிறுத்த மக்களை பழக்குது; தன்னோட evidence-ஐ காட்டுற ஒரு screen, check பண்றதை வேகமாக்குது.

இந்த field-ஐ research அடிப்படையிலான ரெண்டு guides வடிவமைக்குது. Microsoft-ஓட Guidelines for Human-AI Interaction 18 guidelines-ஐ அவை எப்போ apply ஆகுதுன்னு group பண்ணுது: **ஆரம்பத்துல**, **interaction நடக்கும்போது**, **system தப்பா இருக்கும்போது**, **காலப்போக்குல**. Google-ஓட People + AI Guidebook இதே மாதிரி விஷயங்களை cover பண்ணுது, explainability, trust பத்தி ஒரு chapter-ஓட. இந்த lesson அவற்றை ஒரு screen-ல நீங்க எடுக்கக்கூடிய முடிவுகளா மாத்துது, designers அடிக்கடி skip பண்ற பகுதியையும் சேர்க்குது: "இது தப்பா இருக்கலாம்"ங்குற signal உண்மையில எங்க இருந்து வருது.

Chennai-ல ஒரு insurance company-ல product manager-ஆ இருக்குற Divya-வை நீங்க follow பண்ணுவீங்க; agents customers-க்கு தப்பான answers-ஐ சொன்னதுக்கு அப்புறம் அவங்க ஒரு AI coverage assistant-ஐ redesign பண்றாங்க.

| ஆரம்பத்துல | **இது AI-ன்னு காட்டுங்க** | Answer-ஐ நம்பலாமான்னு users முடிவு பண்ற இடத்துல ஒரு தெளிவான label |
| Interaction நடக்கும்போது | **Check பண்ண sources-ஐ காட்டுங்க** | Numbered citations; ஒண்ணை tap பண்ணா exact passage தெரியும், match ஆகுற sentence highlight ஆகியிருக்கும் |

| Interaction நடக்கும்போது | **Progress-ஐ காட்டுங்க** | Streaming text, அல்லது "3 documents-ஐ check பண்ணிட்டிருக்கு..." |
| தப்பா இருக்கும்போது | **Correction-ஐ ஈஸியாக்குங்க** | Edit பண்ணக்கூடிய drafts, ஒரு காரணத்தோட ஒரே tap "Wrong answer", undo |
| தப்பா இருக்கும்போது | **நாசூக்கா fail ஆகுங்க** | "தெளிவான பதில் கிடைக்கல. Underwriting helpdesk-ஐ try பண்ணுங்க." |
| தப்பா இருக்கும்போது | **Control மக்கள் கையிலயே இருக்கட்டும்** | அனுப்புறதுக்கு முன்னாடி preview; பணம், messages, deletions-க்கு முன்னாடி confirm |
| காலப்போக்குல | **கத்துக்கோங்க, சொல்லுங்க** | Feedback-ஐ வாரா வாரம் review பண்றது; coverage அல்லது behaviour மாறும்போது "What's new" |

முதல் ரெண்டு rows செலவு குறைஞ்சது, இருந்தாலும் teams அவற்றை skip பண்றாங்க. "Interaction நடக்கும்போது" rows, system தான் எப்போ உறுதியில்லாம இருக்குன்னு சொல்ல முடிஞ்சா மட்டும் தான் work ஆகும்; அது தான் அடுத்த section.

### Uncertainty signal எங்க இருந்து வருது

ஒரு designer ஒரு நிமிஷத்துல ஒரு மஞ்சள் "please check" badge-ஐ வரைஞ்சிடலாம். அப்புறம் அதை எப்போ காட்டணும்னு ஒரு engineer முடிவு பண்ணணும். யாருமே முடிவு பண்ணலன்னா, badge ஒண்ணு எல்லாத்துலயும் வரும் (users அதை ignore பண்ண கத்துக்குவாங்க), இல்லன்னா எதுலயும் வராது. Teams உண்மையில use பண்ற signals இவை:

| Signal | எப்படி work ஆகுது | எதை பிடிக்கும் | எதை miss பண்ணும் |
| --- | --- | --- | --- |
| Retrieval score | எல்லாத்தையும் விட நல்லா match ஆகுற passage-ஓட score, labelled questions வெச்சு நீங்க tune பண்ற threshold-ஐ விட கீழ இருக்கு | Documents cover பண்ணாத கேள்விகள் | ஒரே மாதிரி தெரியுற ஆனா தப்பான passages, உதாரணம் வேற plan-ஓட clause |
| Citation support check | Cited passage-ல answer-ஓட amount, date அல்லது yes or no இருக்கா? Numbers-க்கு exact match; wording-க்கு இன்னொரு checking step | கற்பனையா உருவாக்கின numbers, claim-ஐ support பண்ணாத citations | Match ஆக முடியாத அளவுக்கு ரொம்ப தளர்வா paraphrase பண்ண claims |
| Rule, schema checks | Amount அனுமதிக்கப்பட்ட range-ல இருக்கு, plan customer-ஓட plan கூட match ஆகுது, தேவையான fields இருக்கு | சாத்தியமில்லாத அல்லது match ஆகாத values | நம்பக்கூடியதா தெரியுற ஆனா தப்பான values |
| Runs-க்கு இடையில agreement | அதே கேள்வியை ரெண்டு மூணு தடவை கேளுங்க, அல்லது ரெண்டு models-கிட்ட கேளுங்க; key fields ஒத்துப்போகலன்னா flag பண்ணுங்க | நிலையில்லாத, ஊகம் மாதிரியான answers | ஒவ்வொரு தடவையும் ஒரே மாதிரி தப்பா இருக்குற answers |
| Self-reported confidence | Model-கிட்ட "எவ்வளவு உறுதியா இருக்க?"ன்னு கேக்குறது | தனியா பெரிசா எதுவும் இல்ல | பெரும்பாலும் overconfident |

கடைசி row தான் trap. Xiong-உம் அவரோட colleagues-உம் 2024-ல பண்ண ஒரு study-ல, confidence-ஐ சொல்லச் சொன்ன language models ரொம்ப அதிகமா overconfident-ஆ இருந்துச்சு, values பெரும்பாலும் 80%-க்கும் 100%-க்கும் இடையில. பல answers-ஐ compare பண்ற methods இதை விட நல்லா பண்ணுச்சு. Model-ஓட சொந்த confidence-ஐ weak evidence-ஆ தான் பாருங்க, ஒருபோதும் ஒரே signal-ஆ இல்ல.

Signals-ஐ சேர்த்து ஒரு சின்ன set display modes-ஆ ஆக்குங்க; இதை code-ல முடிவு பண்ணணும், model-கிட்ட விடக்கூடாது:

```flow
title: Signals-ல இருந்து user பார்க்குறது வரை
கேள்வி -> Passages-ஐ retrieve பண்ணு
Passages-ஐ retrieve பண்ணு -[top score threshold-ஐ விட கீழ]-> Answer இல்ல | அதை சொல்லிட்டு helpdesk-ஐ குடு
Passages-ஐ retrieve பண்ணு -[நல்ல match]-> Draft answer
Draft answer -[amount cited clause-ல இல்ல]-> Flag-ஓட answer | இந்த amount-ஐ check பண்ணுங்க
Draft answer -[எல்லா checks-உம் pass]-> Sources-ஓட answer
```

Amounts-க்கு அந்த முடிவோட ஒரு minimal version இப்படி இருக்கும். 0.6 threshold ஒரு உதாரணம் தான்; சில நூறு labelled questions-ஐ score பண்ணி, weak matches எங்க ஆரம்பிக்குதுன்னு தேர்ந்தெடுத்து நீங்க உங்களோடதை set பண்ணுவீங்க.

```python
import re

def numbers(text):
    return set(re.findall(r"\d[\d,]*", text))

def display_mode(answer, cited_passage, top_score, threshold=0.6):
    if top_score < threshold:
        return "no_answer"          # say so and offer the helpdesk
    if not numbers(answer) <= numbers(cited_passage):
        return "check_amount"       # an amount is not in the cited clause
    return "answer"                 # show with sources

clause = "Room rent is covered up to Rs 5,000 per day."
print(display_mode("Room rent is covered up to Rs 5,000 per day.", clause, 0.82))  # answer
print(display_mode("Room rent is covered up to Rs 7,500 per day.", clause, 0.82))  # check_amount
print(display_mode("Dental implants are covered.", clause, 0.41))                  # no_answer
```

உண்மையான systems "5000", "5,000", "five thousand" எல்லாத்தையும் normalise-உம் பண்ணும், ஆனா shape அதே தான்: செலவு குறைஞ்ச checks, screen வரையறதுக்கு முன்னாடியே முடிவு பண்ணது.

### Citations-ஐ காட்டுறதுக்கு முன்னாடி check பண்ணுங்க

இங்க இருக்குறதுல citations தான் எல்லாத்தையும் விட வலுவான pattern, ஆனா அது எதிர்மறையாவும் போகலாம். Ding-உம் அவரோட colleagues-உம் 2025-ல பண்ண ஒரு study-ல, citations இருந்தப்போ மக்கள் chatbot answers-ஐ அதிகமா நம்புனாங்க, அந்த citations random-ஆ தேர்ந்தெடுக்கப்பட்டிருந்தாலும் கூட. மக்கள் அவற்றை உண்மையிலேயே check பண்ணப்போ மட்டும் தான் trust குறைஞ்சுது. அதனால answer-ஐ support பண்ணாத ஒரு citation, citation-ஏ இல்லாததை விட மோசம்: அது ஒரு தப்பான answer-ஐ verify பண்ணது மாதிரி காட்டுது.

இதுல இருந்து மூணு rules:

- **காட்டுறதுக்கு முன்னாடி verify பண்ணுங்க.** Citation support check-ஐ run பண்ணுங்க. Cited passage-ல முக்கியமான claim இல்லன்னா, citation-ஐ drop பண்ணிட்டு claim-ஐ flag பண்ணுங்க.
- **Document-க்கு இல்ல, passage-க்கு link பண்ணுங்க.** "Policy wording, page 14"-ன்னா check பண்றது மெதுவாகும். Match ஆகுற sentence highlight ஆன நிலையில clause-ஐ open பண்ணுங்க.
- **அஞ்சை விட ஒரு நல்ல citation மேல்.** ஒரு citation, கிட்டத்தட்ட அஞ்சு citations அளவுக்கே trust-ஐ கூட்டுச்சுன்னு Ding-உம் colleagues-உம் கண்டுபிடிச்சாங்க. கூடுதல் links checking-ஐ கூட்டாம clutter-ஐ மட்டும் கூட்டுது.

### Percentages அல்லது colour மட்டும் இல்லாம, வார்த்தைகள்ல சொல்லுங்க

"93.7% confident" மாதிரி துல்லியமான numbers scientific-ஆ கேக்குது, தவறான trust-ஐ வரவழைக்குது, அதுக்கு பின்னாடி இருக்குற number அரிதா தான் நல்லா calibrate ஆகியிருக்கும். Users ஒரு percentage-ஐ வெச்சு act-உம் பண்ண முடியாது: ஒரு customer கிட்ட சொல்ல 81% போதுமா? இதை விட நல்ல options:

- flag-ஐ குறிப்பிட்ட field மேல வைங்க: "இந்த amount-ஐ check பண்ணுங்க", முழு answer மேல ஒரு தெளிவில்லாத banner இல்ல;
- ஒரு action-ஓட சேர்ந்த எளிய வார்த்தைகளை use பண்ணுங்க: "இந்த limit பத்தி எனக்கு உறுதியா தெரியல. Clause 4.2-ல confirm பண்ணுங்க";
- signals weak-ஆ இருக்கும்போது behaviour-ஐ மாத்துங்க: answer பண்ணாதீங்க, ஒரு ஆள்கிட்ட வழிகாட்டுங்க.

Colour-ஐ மட்டும் நம்பாதீங்க. Colour-blind users-க்கு சிவப்பு அல்லது மஞ்சள் border தெரியாம போகலாம், accessibility standard-ஆன WCAG 2.1, information-ஐ காட்டுற ஒரே வழியா colour இருக்கக் கூடாதுன்னு சொல்லுது. Colour கூட ஒரு icon-ஐயும் வார்த்தைகளையும் சேருங்க, screen reader "check பண்ணணும்"னு announce பண்றதை உறுதி பண்ணுங்க. Voice product-ல அதை வாயால சொல்லுங்க: "இந்த amount பத்தி எனக்கு உறுதியா தெரியல."

### Friction-ஐ stakes-க்கு ஏத்த மாதிரி வைங்க

நீங்க சேர்க்குற ஒவ்வொரு check-உம் சில seconds செலவாக்கும். எல்லாத்துலயும் confirm step வெச்சா, மக்கள் படிக்காமயே click பண்ணிட்டு போவாங்க; அதுவும் automation bias தான். தப்புகள் எங்க எல்லாத்தையும் விட அதிகமா செலவாகுதோ அங்க friction வைங்க:

| Stakes | உதாரணம் | Design |
| --- | --- | --- |
| Low | Agent-ஓட சொந்த notes-க்காக ஒரு call-ஓட summary | AI label, ஈஸியான edit; கட்டாய checks இல்ல |
| Medium | ஒரு agent customer கிட்ட திரும்ப சொல்ற coverage answer | ஒவ்வொரு answer-லயும் check பண்ண source, highlight பண்ண amounts, exclusions, "advise பண்றதுக்கு முன்னாடி check பண்ணுங்க" |
| High | ஒரு claim rejection, ஒரு payment, ஒரு legal அல்லது medical statement | Key fields-ஐ காட்டுற ஒரு confirm step, human approval, அல்லது AI answer-ஏ இல்லாம இருக்குறது |

Useful-ஆன ஒரு decision rule: "இந்த answer தப்பா இருந்து யாருமே கவனிக்கலன்னா, யார் எவ்வளவு கட்டுவாங்க?"ன்னு கேளுங்க. Cost எவ்வளவு பெருசோ, row அவ்வளவு மேல.

### இந்திய products-ல patterns

நிறைய இந்திய users AI-ஐ WhatsApp chats, voice assistants, regional-language apps-ல தான் சந்திக்கிறாங்க; அங்க screens சின்னது, கவனம் குறைவு. Patterns இன்னும் apply ஆகும், சுருக்கமான வடிவத்துல. ஒரு WhatsApp bot ஒரு answer-ஐ "Source: Policy section 4.2. இது சரியா தெரியலன்னா WRONG-ன்னு reply பண்ணுங்க."ன்னு முடிக்கலாம். ஒரு voice assistant "எனக்கு உறுதியா தெரியல. உங்களை ஒரு agent கிட்ட connect பண்ணட்டுமா?"ன்னு சொல்லலாம்.

Language இன்னும் கஷ்டமான ஒரு பிரச்சனையை கொண்டு வருது. Answer Tamil-லயோ Hindi-லயோ இருக்கலாம், ஆனா policy wording பெரும்பாலும் English-ல மட்டும் தான் இருக்கும், அதனால Tamil பேசுற ஒரு user citation-ஐ check பண்ண முடியாது. ரெண்டையும் காட்டுங்க: match ஆகுற sentence highlight ஆன original English clause, அப்புறம் "Machine translation. English text தான் official wording."ன்னு label பண்ண ஒரு translated excerpt. ரெண்டுலயும் amounts-ஐ digits-ஆவே வைங்க, support check-ஐ English original மேல run பண்ணுங்க, ஏன்னா ஒரு translation ஒரு number-ஐயோ ஒரு "not"-ஐயோ சத்தமில்லாம மாத்திடலாம்.

### இது AI-ன்னு மக்களுக்கு சொல்லுங்க: rules

Labelling வெறும் நல்ல design மட்டும் இல்ல, ஒரு legal எதிர்பார்ப்பா ஆகிட்டு வருது. EU AI Act-ஓட Article 50, 2 August 2026-ல இருந்து, மக்கள் கூட பேசுற AI systems, தாங்க AI கூட deal பண்றோம்னு மக்களுக்கு தெரியுற மாதிரி design பண்ணப்படணும்னு require பண்ணுது, அது வெளிப்படையா தெரிஞ்சா தவிர. EU users-க்கு service குடுக்குற இந்திய companies-க்கு இது முக்கியம். இந்தியால, Reserve Bank-ஓட FREE-AI committee-ஓட August 2025 report, customers AI கூட deal பண்ணும்போது அதை அவங்களுக்கு தெரியப்படுத்தணும்னு financial firms-க்கு recommend பண்ணுது. இது ஒரு committee report, அதனால அதை binding rule-ஆ எடுத்துக்குறதுக்கு முன்னாடி RBI-ஓட இப்போதைய directions-ஐ check பண்ணுங்க.

### முதல் தப்புக்காக design பண்ணுங்க

ஒரு feature-ஐ நம்பலாமான்னு users சீக்கிரமே முடிவு பண்ணிடுறாங்க. உறுதியா தெரிஞ்ச ஒரு tool-ல இருந்து முதல் தப்பு வந்தா, trust உடைஞ்சு போகும், நிறைய பேர் திரும்ப வரவே மாட்டாங்க. ஆரம்பத்துல இருந்தே tool தன்னோட limits-ஐயும் sources-ஐயும் காட்டியிருந்தா, முதல் தப்போட விலை இதை விட ரொம்ப குறைவு: user அதை பிடிச்சாங்க, அதை பிடிக்க product அவங்களுக்கு உதவுச்சு.

### Planted errors வெச்சு test பண்ணுங்க

Usability tests பொதுவா users ஒரு task-ஐ முடிக்க முடியுதான்னு check பண்ணும். AI features-க்கு, **வேணும்னே தப்பா** இருக்குற answers-ஐயும் உள்ள வைங்க (plant பண்ணுங்க), users கவனிச்சு recover ஆகுறாங்களான்னு பாருங்க. எல்லா participants-க்கும் ஒரே unit-ல count பண்ணுங்க, அப்போ தான் versions-ஐ compare பண்ண முடியும்.

```text
  Test plan for an AI answer screen
  Per participant: 8 questions, 6 correct AI answers, 2 planted errors
  4 participants:  8 planted errors in total
  Measure:         planted errors caught (out of 8), seconds to catch,
                   did they know what to do next?
```

நாலு பேரை வெச்சு, இது மாதிரி ஒரு test பெரிய design problems-ஐ கண்டுபிடிக்கும். ஒரு சின்ன improvement-ஐ அது prove பண்ணாது, அதனால production numbers வெச்சு confirm பண்ணுங்க.

### Launch-க்கு அப்புறம் trust-ஐ measure பண்ணுங்க

Calibration நகர்ந்துட்டே இருக்கும். முதல் வாரத்துல கவனமா check பண்ணவங்க ஆறாவது வாரத்துக்குள்ள பார்க்காமயே rubber-stamp பண்ண ஆரம்பிக்கலாம். மூணு numbers-ஐ track பண்ணுங்க, stakes வாரியா பிரிச்சு:

| Metric | கவலை தர்ற pattern |
| --- | --- |
| High-stakes answers-ல citation open rate | Accept rate ரொம்ப அதிகமாவே இருக்கும்போது கிட்டத்தட்ட zero: மக்கள் check பண்றதை நிறுத்திட்டாங்க |
| Flag ஆன fields-ல edit அல்லது override rate | Flag ஆன fields சில seconds-லயே மாத்தாம accept ஆகுது: flags ignore ஆகுது |
| 100 answers-க்கு wrong-answer reports | AI answers பத்தின customer complaints கூடும்போது இது குறையுது: மக்கள் report பண்றதை நிறுத்திட்டாங்க, errors நிக்கல |

இதுல எதுவுமே accuracy இல்ல. இதோட கூட, answers-ஓட ஒரு random sample-ஐ வாரா வாரம் ஒரு expert audit பண்ணுங்க, அப்போ trust match ஆக வேண்டிய உண்மையான error rate உங்களுக்கு தெரியும்.

## ஒரு worked example

Chennai-ல ஒரு insurance company தன்னோட agent app-ல ஒரு AI assistant-ஐ சேர்க்குது, agents customers கூட பேசும்போது policy coverage கேள்விகளுக்கு பதில் சொல்ல. கீழ இருக்குற numbers விளக்கத்துக்காக தான், மேல சொன்ன மாதிரியான ஒரு சின்ன usability test-ல இருந்து வந்தது; production-ல measure பண்ண results இல்ல.

**Version one** ஒரு confident paragraph answer-ஐ காட்டுது: sources இல்ல, limits இல்ல, problems-ஐ report பண்ண வழியும் இல்ல. நாலு agents ஒவ்வொருத்தரும் 8 role-play கேள்விகளுக்கு பதில் சொன்னாங்க, அதுல 2-ல planted தப்பான answers. Agents அரிதா தான் check பண்ணாங்க: planted errors-ல **8-ல 0** தான் பிடிபட்டுச்சு, 8-உம் "customer"-கிட்ட போயிடுச்சு.

**Version two**, product manager Divya redesign பண்ணது:

| மாற்றம் | Agent இப்போ என்ன பார்க்குறாங்க | அதுக்கு பின்னாடி இருக்குற signal |
| --- | --- | --- |
| Expectations | Header: "AI policy wordings-ல இருந்து பதில் சொல்லுது. Customers-க்கு advise பண்றதுக்கு முன்னாடி check பண்ணுங்க." | எதுவும் தேவையில்ல |
| Check பண்ண sources | ஒவ்வொரு claim-க்கும் ஒரு citation; tap பண்ணா clause open ஆகும், match ஆகுற sentence highlight ஆகியிருக்கும் | Citation support check |
| Uncertainty | Clause-ல கிடைக்காத amounts, exclusions மேல ஒரு icon-ஓட "இந்த amount-ஐ check பண்ணுங்க" | Cited clause கூட number match |
| நாசூக்கான failure | "தெளிவான பதில் கிடைக்கல"-உம் underwriting helpdesk-க்கு ஒரு button-உம் | Tune பண்ண threshold-ஐ விட கீழ retrieval score |
| Plan match | Customer-ஓட சொந்த plan variant-ஓட wording-ல இருந்து மட்டும் answers | Plan code மேல rule check |
| Correction | மூணு காரணங்களோட ஒரு "Wrong answer" button, வாரா வாரம் review ஆகுது | User feedback |

வேற நாலு agents அதே test-ஐ எடுத்தாங்க. அவங்க planted errors-ல **8-ல 7**-ஐ பிடிச்சாங்க, அவங்க satisfaction 5-க்கு 3.1-ல இருந்து 4.2-க்கு ஏறுச்சு. Agents version two-ஐ **அதிகமா** நம்புனாங்க, குறைவா இல்ல, ஏன்னா ஒவ்வொரு answer-உம் ஏன் வந்துச்சுன்னு அவங்களால பார்க்க முடிஞ்சுது, தப்பா இருந்தப்போ அதை fix பண்ண முடிஞ்சுது.

Miss ஆன அந்த ஒரு error தான் useful-ஆன பகுதி. ஒரு procedure cover ஆகுதுன்னு answer சொல்லிச்சு, அதையே சொல்ற ஒரு உண்மையான clause-ஐயும் cite பண்ணுச்சு, ஆனா அது customer-ஓட basic variant-ல இருந்து இல்ல, plan-ஓட premium variant-ல இருந்து. Text match ஆனதால citation check pass ஆகிடுச்சு. Divya மேல இருக்குற plan-match rule-ஐ சேர்த்தாங்க, அதனால தான் அது table-ல இருக்கு. இதுல இருந்து பாடம்: passage அதை சொல்லுதுன்னு citation check prove பண்ணும், அந்த passage இங்க apply ஆகுதுன்னு prove பண்ணாது.

4 agents, 8 planted errors இருக்குற ஒரு test improvement-ஓட direction-ஐ காட்டும், அளவை இல்ல. இதை வெற்றின்னு சொல்றதுக்கு முன்னாடி, முதல் ரெண்டு மாசத்துல production என்ன காட்டணும்னு Divya-வோட team ஒத்துக்கிட்டாங்க: claim-amount answers-ல citation open rate zero-வை விட நல்லா மேலயே இருக்கணும், flag ஆன amounts குறைஞ்சது சில நேரமாவது edit ஆகணும், wrong-answer reports குறையும்போது AI answers-ஆல வந்த complaints கூடக் கூடாது.

## பொதுவா பண்ற தப்புகள்

- **இது AI-ன்னு மறைக்கிறது.** Users தங்களுக்கு தெரிஞ்சதை வெச்சு தான் trust-ஐ calibrate பண்றாங்க, சில markets-ல labelling இப்போ ஒரு legal கடமை.
- **பின்னாடி எந்த signal-உம் இல்லாத uncertainty badges.** Flag எப்போ வரணும்னு யாருமே முடிவு பண்ணலன்னா, அது எப்பவுமே வரும், இல்லன்னா ஒருபோதும் வராது.
- **Model-ஓட சொந்த confidence-ஐ நம்புறது.** Self-reported confidence சரியோ தப்போ பெரும்பாலும் அதிகமா தான் இருக்கும்; compute பண்ண checks-ஐ use பண்ணுங்க.
- **Check பண்ணாத citations.** Answer-ஐ support பண்ணாத ஒரு citation ஒரு தப்பான answer-ஐ verify பண்ணது மாதிரி காட்டும்.
- **போலியான துல்லியம்.** "93.7% confident" தவறான trust-ஐ வரவழைக்குது, act பண்ண users-க்கு எதுவும் குடுக்காது.
- **Colour மட்டுமே cue.** ஒரு சிவப்பு border மட்டும் colour-blind users-க்கும் screen readers-க்கும் fail ஆகும்; ஒரு icon-ஐயும் வார்த்தைகளையும் சேருங்க.
- **எல்லா இடத்துலயும் ஒரே friction.** Low-stakes outputs மேல confirm steps வெச்சா, high-stakes ones-லயும் மக்கள் click பண்ணிட்டு போக பழகிடுவாங்க.
- **Correct பண்ண கஷ்டமான outputs.** Final-ஆன, edit பண்ண முடியாத outputs தப்புகளை ஏத்துக்க users-ஐ தள்ளுது.
- **Success cases-ஐ மட்டும் test பண்றது.** தப்பான answers-ஐ plant பண்ணி, எத்தனை users பிடிக்கிறாங்கன்னு count பண்ணுங்க.
- **வெறுமையான failures.** அடுத்த step இல்லாத "ஏதோ தப்பாயிடுச்சு" users-ஐ மாட்டி வைக்கும்.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற Microsoft-ஓட Guidelines for Human-AI Interaction-ஐயும், explainability, trust பத்தின PAIR chapter-ஐயும் படிங்க.

1. **Audit.** நீங்க use பண்ற ஒரு AI feature-ஐ எடுங்க. நாலு phases ஒவ்வொண்ணுக்கும் (ஆரம்பத்துல, interaction நடக்கும்போது, தப்பா இருக்கும்போது, காலப்போக்குல), அது நல்லா பண்ற ஒரு விஷயத்தையும் fail ஆகுற ஒரு இடத்தையும் note பண்ணுங்க.
2. **Signal-ஐ கண்டுபிடிங்க.** உங்க redesign-ல ஒரு "please check" moment-க்கு, table-ல இருக்குற எந்த signal அதை trigger பண்ணுது, அது எதை miss பண்ணும்னு எழுதுங்க.
3. **Sketch.** Paper-ல ஒரு redesigned screen-ஐ sketch பண்ணுங்க: expectations, ஒரு check பண்ண source, colour-ஐ மட்டும் நம்பாத ஒரு field-level flag, ஒரே tap correction. அதோட stakes row-ஐ mark பண்ணி, friction ஏன் பொருந்துதுன்னு சொல்லுங்க.
4. **Test.** ஒரு சரியான answer, ஒரு planted தப்பான answer-ஓட உங்க sketch-ஐ ரெண்டு பேருக்கு காட்டுங்க. அவங்க எத்தனை planted errors-ஐ பிடிக்கிறாங்க, அதுக்கு எவ்வளவு நேரம் ஆகுதுன்னு record பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு planted தப்பான answer-ஐ ஒரு user சில seconds-க்குள்ள கவனிச்சு அதுல இருந்து recover ஆகுற ஒரு design-ஐ காட்ட முடியும், screen அதை flag பண்ண காரணமான computed signal-ஐ பேர் சொல்ல முடியும்.
