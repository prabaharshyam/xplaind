## இது என்ன

**Feature engineering**-னா raw data-ல இருந்து model inputs உருவாக்குறது. ஒரு மனுஷன் படிக்குற மாதிரி ஒரு model-ஆல transactions table-ஐ படிக்க முடியாது. நீங்க எதைப் பத்தி predict பண்றீங்களோ அந்த ஒவ்வொண்ணுக்கும் ஒரு row வேணும் (இங்க, ஒரு date-ல ஒரு customer), past-ஐ summarise பண்ற columns வேணும்: "கடைசி 30 நாள்ல orders", "கடைசி order-ல இருந்து எத்தனை நாள்", "சமீபத்திய orders-ல late-ஆ deliver ஆனதோட share".

நல்ல features, ஒரு domain expert எதை பார்ப்பாங்களோ அதை model use பண்ணக்கூடிய form-ல capture பண்ணும். Tabular data-ல பல நேரம் accuracy-ல பெரும்பகுதி இங்க இருந்து தான் வருது.

ஒவ்வொரு feature-க்கும் ஒரு **prediction time** இருக்கு: model-கிட்ட கேள்வி கேக்கப்படுற அந்த நேரம். அதுக்கு முன்னாடி இருக்குற எல்லாத்தையும் use பண்ணலாம். அதுக்கு அப்புறம் இருக்குறது எல்லாம் எதிர்காலம், label அங்க தான் இருக்கு.

```flow
dir: LR
title: Prediction time: 00:00 IST, 1 November
1 Nov-க்கு முன்னாடி நடந்த events | orders, ratings, tickets -> 1 Nov நிலவரப்படி features | counts, trends, recency
1 Nov நிலவரப்படி features -[model]-> Label: 1 முதல் 14 Nov வரை order பண்ணாங்களா | எந்த feature-லயும் use ஆகாது
```

இந்த lesson-ல Bengaluru-ல இருக்குற ஒரு food-delivery company, எந்த customers 14 நாளுக்குள்ள மறுபடி order பண்ணுவாங்கன்னு predict பண்றதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

### ஒரே rule: எல்லாத்தையும் prediction time நிலவரப்படி compute பண்ணுங்க

**Leakage**-னா prediction time-ல model-கிட்ட இருக்காத தகவல் ஒரு feature-க்குள்ள இருக்குறது. இது validation scores-ஐ brilliant-ஆ காட்டும், production results ஏமாத்தும். மூணு பழக்கங்கள் இதுல பெரும்பகுதியை தடுக்கும்.

1. **Cutoff-க்கு கண்டிப்பா முன்னாடி இருக்குறதை மட்டும் filter பண்ணுங்க.** `<=` இல்ல, `ts < cutoff` use பண்ணுங்க. Cutoff நேரத்தோட stamp ஆன ஒரு event, prediction-க்கு அப்புறம் நடந்திருக்கலாம்.
2. **மெதுவா மாறுற tables-ஐ cutoff நிலவரப்படி join பண்ணுங்க.** Ratings, loyalty tier, credit limit மாதிரியானதுக்கு, இன்னைக்கு இருக்குற latest value இல்ல, cutoff-க்கு முன்னாடி இருந்த latest value-ஐ எடுங்க. Pandas-ல `merge_asof` இதை செய்யும்:

```python
import pandas as pd

labels = pd.DataFrame({"customer": [1, 1, 2], "cutoff": pd.to_datetime(["2026-09-01", "2026-10-01", "2026-10-01"])})
ratings = pd.DataFrame({"customer": [1, 1, 2, 2],
                        "rated_at": pd.to_datetime(["2026-08-20", "2026-10-01", "2026-09-15", "2026-10-03"]),
                        "rating": [5, 2, 4, 1]})
joined = pd.merge_asof(labels.sort_values("cutoff"), ratings.sort_values("rated_at"),
                       left_on="cutoff", right_on="rated_at", by="customer",
                       allow_exact_matches=False)     # strictly before the cutoff
print(joined)
```

Customer 1-ஓட 1 October cutoff-க்கு, 20 August-ல குடுத்த 5 rating கிடைக்குது. 1 October அன்னைக்கே குடுத்த 2 rating விலக்கப்படுது, customer 2-ஓட 3 October rating-உம் அப்படித்தான்.

3. **ஒரு பிந்தைய time period-ல validate பண்ணுங்க.** பல cutoffs-ல (மாசத்துக்கு ஒண்ணு) training rows build பண்ணுங்க, முந்தையதுல train பண்ணி பிந்தையதுல test பண்ணுங்க. Random split எதிர்கால rows-ஐ training-க்குள்ள கலந்துடும், அதனால leaks-உம் கொஞ்ச நாள் மட்டும் இருக்குற patterns-உம் skill மாதிரி தெரியும்.

| Ratios | EMI vs income, ஒரு order-க்கு returns, category average கூட ஒப்பிட்டா price | வேற வேற ஆளுங்களுக்கு இடையில amounts-ஐ ஒப்பிடக்கூடிய scale-க்கு கொண்டு வருது |
| Service | கடைசி 30 நாள்ல late deliveries-ஓட share; கடைசி rating; சமீபத்திய tickets | ஆளுங்களை competitors பக்கம் தள்ளுற மோசமான அனுபவங்களை பிடிக்குது |
| Calendar | வாரத்தோட நாள், salary week, அடுத்த festival-க்கு எத்தனை நாள் | Indian demand-உம் payments-உம் festivals-ஐயும் pay cycles-ஐயும் follow பண்ணுது |
| Categories | City tier, channel, PIN code | Groups வேற வேற மாதிரி நடந்துக்கும்; encoding வேணும் (கீழ பாருங்க) |
| Text, location | Keyword flags, text embeddings; ரொம்ப பக்கத்துல இருக்குற kitchen-க்கு தூரம் | Unstructured data-வை numbers-ஆ மாத்துது |

**Experts-ல இருந்து ஆரம்பிங்க.** Business-ஐ நடத்துறவங்ககிட்ட கேளுங்க: "ஒரு customer விட்டுப் போகப் போறாங்கன்னு உங்களுக்கு எதை வச்சு தோணுது?" Delivery managers late deliveries-ஐ சொல்லுவாங்க; finance payday timing-ஐ சொல்லும். அப்புறம் ஒவ்வொரு idea-வையும் measure பண்ணுங்க, ஏன்னா ஒரு sensible idea-வும் எதையுமே சேர்க்காம போகலாம் (worked example-ல அப்படி ஒண்ணு வருது).

### Numeric transforms

- **Missing values.** ஒரு gap-க்கு என்ன அர்த்தம்னு முடிவு பண்ணுங்க. "30 நாள்ல orders இல்ல"-னா அது உண்மையான zero; "எப்பவுமே orders இல்ல"-னா average undefined ஆகிடும். உண்மையான zeros-ஐ 0-ஆல fill பண்ணுங்க, இல்லாததே ஒரு தகவலா இருக்குற இடத்துல ஒரு missing flag (`never_ordered = 1`) சேருங்க. scikit-learn-ல இருக்குற `HistGradientBoostingClassifier` missing values-ஐ நேரடியா ஏத்துக்கும்.
- **Skewed amounts.** Rupees-ல spend long-tailed: பெரும்பாலான customers சில ஆயிரங்கள் செலவழிப்பாங்க, ஒரு சிலர் லட்சங்கள். Linear models, neural networks-க்கு `log1p(amount)` use பண்ணுங்க.
- **Scaling.** Linear models, k-nearest neighbours, neural networks-க்கு standardise பண்ணுங்க. Tree models order-ஐ வச்சு split பண்ணுது, அதனால scaling அவற்றுக்கு எதையும் மாத்தாது.
- **Interactions.** Trees interactions-ஐ தானாவே கண்டுபிடிக்கும். Linear models-க்கு அவற்றை எழுதிக் குடுக்கணும், உதாரணமா `late_share × orders_30d`.

### Categories

- **கொஞ்சம் values** (city tier, channel): one-hot encoding, அரிதான values-ஐ "other"-ஆ group பண்ணி.
- **நிறைய values** (PIN code, restaurant ID): frequency encoding, target encoding, அல்லது **hashing trick** (`FeatureHasher` ஒவ்வொரு value-வையும் ஒரு fixed எண்ணிக்கை columns-ல ஒண்ணுக்கு map பண்ணும்; collisions கொஞ்சம் accuracy-ஐ குறைக்கும், ஆனா memory fixed-ஆ இருக்கும்). Millions கணக்குல IDs இருந்தா, deep models ஒவ்வொரு ID-க்கும் ஒரு **embedding** கத்துக்கும்.

**Target encoding** ஒவ்வொரு category-ஐயும் அதோட average label-ஆல replace பண்ணும். இது powerful, leak ஆகுறதும் ஈஸி. Averages-ஐ எல்லா rows-லயும் compute பண்ணா, ஒவ்வொரு row-ஓட சொந்த label-உம் அதோட feature-க்குள்ளயே இருக்கும். கீழ இருக்குற demo-ல PIN codes-க்கு உண்மையான signal எதுவுமே இல்ல:

```python
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import TargetEncoder
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.metrics import roc_auc_score

rng = np.random.default_rng(0)
df = pd.DataFrame({"pin_code": rng.integers(0, 2000, 6000).astype(str),
                   "y": rng.random(6000) < 0.3})          # pin code carries NO real signal

# Wrong: encode with means from ALL rows, then split
df["pin_mean"] = df.groupby("pin_code").y.transform("mean")
tr, te = train_test_split(df, test_size=0.3, random_state=0)
m = LogisticRegression().fit(tr[["pin_mean"]], tr.y)
print("encoded before split:", round(roc_auc_score(te.y, m.predict_proba(te[["pin_mean"]])[:, 1]), 2))

# Right: the encoder lives inside the pipeline and is fitted on training rows only
pipe = make_pipeline(TargetEncoder(), LogisticRegression()).fit(tr[["pin_code"]], tr.y)
print("encoded after split :", round(roc_auc_score(te.y, pipe.predict_proba(te[["pin_code"]])[:, 1]), 2))
```

தப்பான வழிக்கு 0.85, சரியான வழிக்கு சுமார் 0.5 print ஆகும் (exact value ஒவ்வொரு run-க்கும் கொஞ்சம் மாறும்): சுத்தமான noise ஒரு strong feature மாதிரி score ஆகுது. scikit-learn-ஓட `TargetEncoder` `fit_transform`-க்குள்ள cross-fit-உம் பண்ணுது, அதனால training rows கூட அவற்றோட சொந்த label-ஐ பார்க்கவே பார்க்காது. Scalers, imputers, feature selection-க்கும் இதே rule தான்: split-க்கு அப்புறம், pipeline-க்குள்ள fit பண்ணுங்க. Data-க்கு time order இல்லாததால மட்டும் தான் இந்த demo random split use பண்ணுது.

### Calendar features

```python
import pandas as pd

# In production this is a reviewed data file, one row per festival, year and region
festivals = pd.DataFrame([
    ("onam", "2026-08-26", "kerala"),          # Thiruvonam day
    ("dussehra", "2026-10-20", "all"),
    ("diwali", "2026-11-08", "all"),
], columns=["festival", "date", "region"]).assign(date=lambda d: pd.to_datetime(d.date))

def calendar_features(dates, region):
    d = pd.Series(pd.to_datetime(dates))
    fest = festivals[festivals.region.isin([region, "all"])].date
    gap = d.apply(lambda x: min(((f - x).days for f in fest if f >= x), default=60))
    return pd.DataFrame({"date": d, "dow": d.dt.day_of_week, "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": gap.clip(upper=60)})

print(calendar_features(["2026-08-20", "2026-10-15", "2026-11-03"], "kerala"))
```

Festival dates ஒவ்வொரு வருஷமும் மாறும், சில (Eid மாதிரி) நிலா பார்க்குறதை பொறுத்தது, அதனால official lists-க்கு இடையில dates ஒரு நாள் வித்தியாசப்படலாம். ஒரு region column வச்சு, ஒவ்வொரு வருஷமும் official holiday lists-ல இருந்து table-ஐ update பண்ணுங்க.

### Training-serving consistency

**Training-serving skew**-னா production ஒரு feature-ஐ training-ல இருந்து வேற மாதிரி compute பண்றது. பொதுவான காரணங்கள்: serving-ல UTC days, training-ல IST days; "active customer"-க்கு வேற definition; இல்லன்னா data-வோட கடைசி ஒரு மணி நேரத்தை miss பண்ற ஒரு serving query. Model crash ஆகாது; சத்தமில்லாம மோசமாகிட்டே போகும்.

```flow
dir: LR
title: ஒரு feature function, ரெண்டு callers
Raw events -> features_as_of | test பண்ண ஒரே function
features_as_of -[நிறைய past cutoffs]-> Training rows
features_as_of -[cutoff = now]-> Live features
```

Feature code-ஐ ஒரே தடவை எழுதி ரெண்டு இடத்துல இருந்தும் call பண்ணுங்க, encoders-ஐ model pipeline-க்குள்ளயே வைங்க, அப்போ fit பண்ண objects model கூடவே போகும். பெரிய scale-ல, Feast (open source) மாதிரி ஒரு **feature store** இதை உங்களுக்கு பண்ணும். அது ஒரு point-in-time join வச்சு training sets build பண்ணும் (ஒவ்வொரு label-ஓட timestamp-லயோ அதுக்கு முன்னாடியோ இருந்த latest feature value), fresh values-ஐ ஒரு fast online store-க்கு copy பண்ணும் (இதுக்கு materialisation-ன்னு பேரு), prediction time-ல அந்த values-ஐ serve பண்ணும்.

### Features-ஐ தேர்ந்தெடுக்குறது

அதிக features எப்பவுமே நல்லது இல்ல. ஒவ்வொண்ணுக்கும் maintain பண்ண ஒரு pipeline செலவு, leak ஆக ஒரு வாய்ப்பு. Groups-ஆ measure பண்ணுங்க (counts, recency, service, calendar), ரெண்டு வழியில: ஒவ்வொரு group-ஐயும் ஒரு simple baseline-ல சேர்த்து, ஒவ்வொரு group-ஐயும் full set-ல இருந்து எடுத்து. Features பல நேரம் overlap ஆகும், அதனால ஒரு group-ஐ தனியா சேர்த்தா உதவினாலும், அதை எடுக்குறதால பெருசா இழப்பு இல்லாம போகலாம். பல test months-ல gain repeat ஆகுற groups-ஐ வச்சுக்கோங்க.

## ஒரு worked example

Bengaluru team-ஓட கேள்வி: ஒவ்வொரு monthly cutoff-க்கு அப்புறம் வர்ற 14 நாள்ல ஒரு customer order பண்ணுவாங்களா? கீழ இருக்குற code synthetic data use பண்ணுது, அதனால நீங்க run பண்ணி, numbers-ஐ பார்த்து, break பண்ணியும் பார்க்கலாம். ரெண்டு effects plant பண்ணியிருக்கு: பாதி customers ஏதோ ஒரு கட்டத்துல மெதுவா விலக ஆரம்பிப்பாங்க (முதல்ல சின்ன baskets, அப்புறம் ரெண்டு மாசம் கழிச்சு குறைவான orders), ஒரு மாசத்துல ரெண்டு late deliveries ஒரு customer-ஐ வேற app-க்கு மாத்த வைக்கலாம்.

```python
import numpy as np, pandas as pd
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

# 1. Synthetic orders for 3,000 customers, January to October 2026, with two planted effects
rng = np.random.default_rng(7)
N, days = 3000, pd.date_range("2026-01-01", "2026-10-31")
base = rng.gamma(2, 0.06, N)                             # usual daily chance of ordering
late_p = np.where(rng.random(N) < 0.3, 0.3, 0.05)        # 30% live where deliveries run late
drift = np.where(rng.random(N) < 0.5, rng.integers(30, 270, N), 9999)  # day a customer starts drifting
late_log, left, rows = np.zeros((len(days), N), bool), np.zeros(N, bool), []
for t, day in enumerate(days):
    shrink = np.clip(1 - (t - drift) / 60, 0.4, 1)       # drifters first buy smaller baskets,
    fade = np.clip(1 - (t - drift - 60) / 20, 0.05, 1)   # then two months later stop ordering
    left |= (late_log[max(0, t - 30):t].sum(0) >= 2) & (rng.random(N) < 0.03)  # 2 late orders: may switch apps
    ordered = rng.random(N) < base * fade * np.where(left, 0.1, 1)
    late_log[t] = ordered & (rng.random(N) < late_p)
    for c in np.flatnonzero(ordered):
        rows.append((c, day, round(rng.gamma(4, 100) * shrink[c]), late_log[t, c]))
orders = pd.DataFrame(rows, columns=["customer", "ts", "amount", "late"])

# 2. Features as of a cutoff, from orders strictly before it
def features_as_of(orders, cutoff):
    past, out = orders[orders.ts < cutoff], {}
    for d in (7, 30, 90):
        g = past[past.ts >= cutoff - pd.Timedelta(days=d)].groupby("customer")
        out[f"orders_{d}d"], out[f"spend_{d}d"] = g.size(), g.amount.sum()
        if d == 30: out["late_share_30d"] = g.late.mean()
    out["days_since_last"] = (cutoff - past.groupby("customer").ts.max()).dt.days
    f = pd.DataFrame(out).reindex(range(N))
    f = f.fillna({c: 0 for c in f if c.startswith(("orders_", "spend_"))})
    f["basket_change"] = (f.spend_30d / f.orders_30d) / (f.spend_90d / f.orders_90d)  # NaN if no orders
    return f                                              # trees accept NaN; it means "no recent orders"

# 3. One row per customer per monthly cutoff; label = ordered in the 14 days after it
def labelled(cutoff):
    X = features_as_of(orders, cutoff)
    nxt = orders[(orders.ts >= cutoff) & (orders.ts < cutoff + pd.Timedelta(days=14))]
    X["leaky_orders_7d"] = features_as_of(orders, cutoff + pd.Timedelta(days=7)).orders_7d  # bad join
    return X, X.index.isin(nxt.customer).astype(int)

def stack(months):
    parts = [labelled(pd.Timestamp(f"2026-{m:02d}-01")) for m in months]
    return pd.concat([x for x, _ in parts]), np.concatenate([y for _, y in parts])

Xtr, ytr = stack(range(4, 9))     # train on April to August cutoffs
Xte, yte = stack([9, 10])         # test on later months, never a random split

def auc(cols):
    m = HistGradientBoostingClassifier(random_state=0).fit(Xtr[cols], ytr)
    return round(roc_auc_score(yte, m.predict_proba(Xte[cols])[:, 1]), 3)

full = [c for c in Xtr if c != "leaky_orders_7d"]
print("orders_30d only     ", auc(["orders_30d"]))
for name, extra in [("+ 7 and 90 day counts", ["orders_7d", "orders_90d"]), ("+ recency", ["days_since_last"]),
                    ("+ basket change", ["basket_change"]), ("+ late share", ["late_share_30d"])]:
    print(name.ljust(20), auc(["orders_30d"] + extra))
print("all features        ", auc(full))
print("all + leaky feature ", auc(full + ["leaky_orders_7d"]))
```

Leaky column ஒரு உண்மையான bug-ஐ copy பண்ணுது: வாரத்தோட கடைசி நாளை key-ஆ வச்ச ஒரு weekly table-ஐ, அதோட முதல் நாள் key மாதிரி நினைச்சு cutoff கூட join பண்ணது, அதனால "கடைசி 7 நாள்" சத்தமில்லாம "அடுத்த 7 நாள்"-ஆ மாறிடுச்சு.

அது print பண்றது (September, October cutoffs-ல test AUC; synthetic data, அதனால இதை illustrations-ஆ மட்டும் பாருங்க):

| Features | Test AUC |
| --- | --- |
| கடைசி 30 நாள்ல orders மட்டும் | 0.803 |
| + 7 நாள், 90 நாள் counts | 0.832 |
| + கடைசி order-ல இருந்து எத்தனை நாள் | 0.818 |
| + basket change | 0.807 |
| + late-delivery share | 0.805 |
| எல்லா honest features | 0.848 |
| எல்லாம், + leaky join | 0.935 |

வேற அஞ்சு seeds-ல மறுபடி run பண்ணாலும் இதே pattern தான் வருது, ஒவ்வொரு number-உம் சுமார் 0.01 அளவுக்கு நகரும்.

**இந்த numbers என்ன கத்துக்குடுக்குது.**

- **பெரிய வேலையை windows-உம் recency-உம் தான் பண்ணுது.** ஒரே ஒரு 30 நாள் count-ஆல "போன வாரம் ரெண்டு தடவை order பண்ணாங்க"-ஐயும் "ஒரு மாசம் முன்னாடி ரெண்டு தடவை order பண்ணாங்க"-ஐயும் பிரிச்சு சொல்ல முடியாது. 7 நாள், 90 நாள் windows சேர்த்தா model-க்கு ஒரு trend கிடைக்குது, கடைசி order-ல இருந்து எத்தனை நாள்ங்குறது timing-ஐ குடுக்குது.
- **ஒரு உண்மையான காரணமும் கொஞ்சம் தான் சேர்க்கலாம்.** இந்த data-ல late deliveries உண்மையாவே customers-ஐ விரட்டுது, ஏன்னா simulation அப்படித்தான் சொல்லுது. ஆனாலும் late-share feature தனியா கிட்டத்தட்ட எதையுமே சேர்க்கல: எந்த 14 நாள் window-லயும் அது கொஞ்ச customers-ஐ தான் பாதிக்குது, ஏற்கனவே விட்டுப் போனவங்க குறைவான orders-ஆவே தெரிஞ்சுடுறாங்க. Basket change-உம் அதே மாதிரி தான். Meeting-ல sensible-ஆ தோணுற ideas-உம் ஒரு test-ல தங்களோட இடத்தை சம்பாதிக்கணும்.
- **Leak சத்தமா தெரியும்.** ஒரே column-ஆல 0.85-ல இருந்து 0.93-க்கு jump வந்தா அது தான் warning. கடைசியா சேர்த்த columns-ஐ ஒவ்வொண்ணா remove பண்ணி கண்டுபிடிங்க, அப்புறம் அந்த winner-ஐ உருவாக்குன join-ஐ படிங்க.

## பொதுவான தவறுகள்

- **Cutoff நேரத்துலயோ அதுக்கு அப்புறமோ நடந்த events-ஐ use பண்றது.** `ts < cutoff` வச்சு filter பண்ணுங்க, மெதுவா மாறுற tables-ஐ "இன்னைக்கு இருக்குற latest value" வச்சு இல்ல, as-of join வச்சு join பண்ணுங்க.
- **Time-ordered data-ல random splits.** ஒரே customer பல cutoffs-ல வருவாங்க, எதிர்காலம் training-க்குள்ள leak ஆகும். முந்தைய மாசங்கள்ல train பண்ணுங்க, பிந்தைய மாசங்கள்ல test பண்ணுங்க.
- **Split-க்கு முன்னாடியே encoders, scalers, imputers-ஐ fit பண்றது.** அவற்றை pipeline-க்குள்ள வைங்க, அப்போ training rows-ல மட்டும் fit ஆகும்.
- **Training-க்கும் serving-க்கும் தனித்தனி feature code.** ரெண்டு versions-உம் விலகிப் போகும் (UTC vs IST, "active"-க்கு ரெண்டு definitions). ஒரே function-ஐ share பண்ணுங்க, இல்லன்னா ஒரு feature store use பண்ணுங்க.
- **Festival dates-ஐ hard-code பண்றது.** அவை ஒவ்வொரு வருஷமும் மாறும், region-க்கு region வேறுபடும். Dates இருக்குற ஒரு table வைங்க.
- **ஒரு jump-ஐ investigate பண்ணாம கொண்டாடுறது.** ஒரு feature-ஆலயோ ஒரு join-ஆலயோ வர்ற பெரிய gain, வேற மாதிரி prove ஆகுற வரைக்கும் leak தான்.
- **ஒரே நேரத்துல நூத்துக்கணக்கான features சேர்க்குறது.** Groups-ஆ சேர்த்து ஒவ்வொரு group-ஐயும் measure பண்ணுங்க, அப்போ எந்த features அவற்றோட maintenance-க்கு தகுந்த பலன் தருதுன்னு தெரியும்.

## அதிகமான feature engineering எப்போ தேவையில்ல

- **Unstructured data**: images, audio, long text மாதிரி, அங்க neural networks தங்களோட features-ஐ தாங்களே கத்துக்கும்.
- **ஒரு strong pretrained model அல்லது embeddings** உங்களுக்கு வேண்டியதை ஏற்கனவே capture பண்ணியிருக்கும்போது.
- **ரொம்ப கம்மியான data**: அங்க நூறு engineered features-ஐ விட சில expert features-உம் ஒரு simple model-உம் தான் ஜெயிக்கும்.

## Demo-ல இருந்து production-க்கு

- **As-of rule-ஐ test பண்ணுங்க**: ஒரு எதிர்கால event-ஐ சேர்த்து, எந்த feature-உம் மாறலன்னு check பண்ற ஒரு unit test.
- **Training, serving outputs-ஐ compare பண்ணுங்க**: launch-க்கு முன்னாடி customers-ஓட ஒரு sample-க்கு, அதுக்கு அப்புறம் ஒரு schedule-ல.
- **Feature distributions-ஐயும் missing rates-ஐயும் track பண்ணுங்க**, ஒவ்வொரு source-க்கும், அப்போ ஒரு உடைஞ்ச upstream table மெதுவான accuracy drop-ஆ இல்லாம ஒரு alert-ஆ தெரியும்.
- **ஒவ்வொரு retrain-லயும் feature groups-ஐ மறுபடி measure பண்ணுங்க**, உதவுறதை நிறுத்துனதை drop பண்ணுங்க.

## Practice

Kaggle-ஓட Feature Engineering course-ஐ முடிச்சு, Google-ஓட Rules of ML-ல feature engineering section-ஐ படிங்க. அப்புறம் worked example code-ஐ use பண்ணுங்க:

1. உங்களோட சொந்த மூணு features சேருங்க (உதாரணமா, orders-ல weekend share, இல்லன்னா அடுத்த festival-க்கு எத்தனை நாள்), ஒவ்வொண்ணையும் baseline-ல சேர்த்தும் full set-ல இருந்து எடுத்தும் measure பண்ணுங்க.
2. ஒரு cutoff-க்கு ஒரு நிமிஷம் அப்புறம் date போட்ட ஒரு order-ஐ சேர்த்து, `features_as_of` மாறுனா fail ஆகுற ஒரு test எழுதுங்க.
3. Time split-ஐ எல்லா rows-லயும் ஒரு random 80/20 split-ஆ மாத்துங்க. இங்க அது scores-ஐ ஏத்தாது, ஏன்னா simulation-ல மாசத்துக்கு மாசம் shifts இல்ல. ஒரு random split-ஐ over-optimistic ஆக்குற ரெண்டு உண்மையான மாற்றங்களை சொல்லுங்க (ஒரு price rise, ஒரு புது competitor).
4. April-ல இருந்து June வரை train பண்ணி, August-ல இருந்து October வரை test பண்ணுங்க. Table-ல இருக்குற feature groups-ஓட ranking இன்னும் அப்படியே இருக்கான்னு check பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒவ்வொரு feature-க்கும், அது prediction time நிலவரப்படி எப்படி compute ஆகுது, ஒரு பிந்தைய period-ல அதை எப்படி validate பண்ணீங்க, production அதை எப்படி அதே மாதிரி compute பண்ணுதுன்னு சொல்ல முடியும்போது தான்.
