## இது என்ன

**Feature engineering**-னா raw data-ல இருந்து model inputs உருவாக்குறது. Transactions table churn model-க்கு நேரடியா பெருசா எதுவும் சொல்லாது. ஆனா "கடைசி 30 நாள்ல orders", "போன quarter-ஐ விட மாசாந்திர செலவுல மாற்றம்", "கடைசி order-ல இருந்து எத்தனை நாள்" மாதிரி features சொல்லும்.

நல்ல features, domain expert எதை பார்ப்பாங்களோ அதை capture பண்ணும்.

```flow
dir: LR
title: Prediction date: 1 Nov
கடந்த காலம், use பண்ணலாம் | orders, sessions, tickets -> 1 Nov "as of" Features | counts, trends, recency
1 Nov "as of" Features -[predict]-> எதிர்காலம், features-ல வரவே கூடாது | அடுத்த orders: இதுதான் label
```

இந்த lesson-ல Bengaluru-ல இருக்குற ஒரு food-delivery company, எந்த customers அடுத்த 14 நாள்ல மறுபடி order பண்ணுவாங்கன்னு predict பண்றதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Time windows மேல aggregates.** கடைசி 7, 30, 90 நாள்ல counts, sums, averages, maximums. Trends: இந்த மாசம் vs போன மாசம். Recency: கடைசி event-ல இருந்து எத்தனை நாள்.

**Ratios மற்றும் differences.** EMI to income, ஒரு visit-க்கு spend, ஒரு order-க்கு returns, category average-ஓட ஒப்பிட்ட price.

**Date, time parts.** வாரத்தோட நாள், மணி, மாசம், festival காலங்கள் (Diwali, Onam, Eid, Pongal), மாத ஆரம்பத்துல salary days. இந்தியாவுல demand-உம் payment patterns-உம் seasonal-ஆ ரொம்ப மாறும்.

**Categories.** கொஞ்சம் values இருந்தா one-hot encoding; நிறைய இருந்தா frequency அல்லது target encoding (target encoding-ஐ leakage வராம இருக்க training folds-ல மட்டும் compute பண்ணுங்க); அரிதான categories-ஐ "other"-ல group பண்றது.

**Text.** Simple-ஆ: length, keyword flags. Strong-ஆ: language model-ல இருந்து embeddings, அதை features-ஆ use பண்றது.

**Location.** Store அல்லது hub-க்கு distance, PIN code characteristics, city tier.

**Leakage.** முக்கிய rule: ஒரு feature, prediction நேரத்துல கிடைக்குற தகவலை மட்டும்தான் use பண்ணணும். ஒவ்வொரு aggregate-ஐயும் prediction time "as of" compute பண்ணுங்க. எதிர்கால data-வை சத்தமில்லாம உள்ள வச்சிருக்குற features (நீங்க score பண்ற order-க்கு அப்புறம் record ஆன ஒரு refund) testing-ல model-ஐ பிரமாதமா காட்டும், production-ல fail ஆகும்.

**Training-serving consistency.** Training-லயும் serving-லயும் features ஒரே மாதிரி compute ஆகணும். Feature code-ஐ ஒரு தடவை எழுதி திரும்ப use பண்ணுங்க, இல்லன்னா feature store use பண்ணுங்க. Mismatches (timezone வித்தியாசம், "active"-க்கு வேற definition) production models-ஐ சத்தமில்லாம மோசமாக்கும்.

**Selection.** அதிக features எப்பவும் நல்லது இல்ல. தேவையில்லாத அல்லது repeat ஆகுற features-ஐ நீக்குங்க; importance-ஐயும், காலப்போக்குல stability-யையும் check பண்ணுங்க.

**Data வகைக்கு feature ideas:**

| Raw data | Example features |
| --- | --- |
| Transactions | கடைசி 7, 30, 90 நாள்ல orders; average value; முந்தைய 30 நாளோட ஒப்பிட்ட மாற்றம்; கடைசி order-ல இருந்து நாட்கள் |
| Ratings, support | கடைசி rating; கடைசி 30 நாள்ல tickets; late deliveries-ஓட share |
| Dates | வாரத்தோட நாள், மணி, மாசம், festival window, salary week |
| Categories | கொஞ்சம் values-க்கு one-hot; நிறைய values-க்கு frequency அல்லது fold-safe target encoding; அரிதான values "other"-ஆ group |
| Text | Length, keyword flags, embeddings |
| Location | Store அல்லது hub-க்கு distance, city tier |

**Experts-ஓட ஆரம்பிங்க.** பெரும்பாலும் best features, business தெரிஞ்சவங்ககிட்ட கேக்குறதுல இருந்து வரும்: "ஒரு customer போகப் போறாங்கன்னு உங்களுக்கு எப்போ தோணும்?" Delivery managers late-delivery share-ஐ சொன்னாங்க; finance payday timing-ஐ சொன்னாங்க. ஒவ்வொண்ணும் எந்த automatic feature-ஐயும் விட நல்லா வேலை செஞ்சுது.

**Pandas-ல point-in-time features.** எல்லாத்தையும் ஒரு cutoff date "as of" compute பண்ணுங்க, அதுக்கு முன்னாடி மட்டும் நடந்த events-ல இருந்து:

```python
import numpy as np, pandas as pd

rng = np.random.default_rng(2)
events = pd.DataFrame({
    "customer": rng.integers(1, 301, 6000),
    "ts": pd.Timestamp("2026-01-01") + pd.to_timedelta(rng.integers(0, 300, 6000), unit="D"),
    "amount": rng.gamma(2, 400, 6000).round(),
    "late": rng.random(6000) < 0.1,
})

def features_as_of(events, cutoff):
    past = events[events.ts < cutoff]
    out = {}
    for days in (7, 30, 90):
        w = past[past.ts >= cutoff - pd.Timedelta(days=days)]
        g = w.groupby("customer")
        out[f"orders_{days}d"] = g.size()
        out[f"spend_{days}d"] = g.amount.sum()
    g = past.groupby("customer")
    out["days_since_last"] = (cutoff - g.ts.max()).dt.days
    out["late_share"] = g.late.mean()
    f = pd.DataFrame(out).fillna(0)
    f["spend_trend"] = f.spend_30d / (f.spend_90d / 3 + 1)          # last month vs monthly average
    return f

cut = pd.Timestamp("2026-09-01")
X = features_as_of(events, cut)
print(X.describe().T[["mean", "max"]].round(1).head(8))
```

Training-க்கு, பல cutoffs-ல (மாசத்துக்கு ஒண்ணு) features build பண்ணுங்க, ஒவ்வொண்ணுக்கும் அதன் cutoff-க்கு அப்புறமான labels-ஐ சேர்த்து. இப்படி செஞ்சா examples அதிகமாகும், காலப்போக்குல stability-யையும் test பண்ணலாம்.

**Festival, salary-cycle features.**

```python
FESTIVALS = pd.to_datetime(["2026-03-04", "2026-08-28", "2026-10-20", "2026-11-08"])   # check the year's dates

def calendar_features(dates):
    d = pd.Series(pd.to_datetime(dates))
    days_to_fest = d.apply(lambda x: min(((f - x).days for f in FESTIVALS if f >= x), default=365))
    return pd.DataFrame({"dow": d.dt.dayofweek, "month": d.dt.month,
                         "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": days_to_fest.clip(upper=60)})
```

Festival dates ஒவ்வொரு வருஷமும் மாறும், region-க்கு region வேறவும் இருக்கும். அதனால code-ல இல்லாம, dated table-ல வைங்க.

**Pipeline-க்குள்ள encoding.** Categorical handling-ஐ model-ஓடவே வைங்க, அப்போ serving, training மாதிரியே இருக்கும்:

```python
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, TargetEncoder
from sklearn.pipeline import make_pipeline
from sklearn.ensemble import HistGradientBoostingClassifier

prep = ColumnTransformer([
    ("few", OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=20), ["city_tier", "channel"]),
    ("many", TargetEncoder(), ["pin_code"]),           # fitted with internal cross-fitting to limit leakage
], remainder="passthrough")
model = make_pipeline(prep, HistGradientBoostingClassifier())
```

scikit-learn-ல `TargetEncoder` `fit_transform`-ல cross-fitting பண்ணும். அது naive target encoding வர வைக்குற leakage-ஐ குறைக்கும்.

**ஒவ்வொரு feature group-ஓட value-வையும் அளந்து பாருங்க.** ஒவ்வொரு group-உம் (recency, spend, delivery, calendar) இருக்கும்போதும் இல்லாதப்போவும், ஒரே time split-ல train பண்ணி, தெளிவா உதவுற groups-ஐ வச்சுக்கோங்க. ஒரு cutoff month-ல மட்டும் உதவுற features பெரும்பாலும் noise தான்.

## ஒரு worked example

Bengaluru-ல ஒரு food-delivery company, ஒரு customer அடுத்த 14 நாள்ல மறுபடி order பண்ணுவாரான்னு predict பண்றாங்க.

Raw data: orders, ratings, app sessions, support tickets, promotions.

ஒவ்வொரு prediction date-க்கும் "as of" build பண்ண features:

- கடைசி 7, 30, 90 நாள்ல orders; கடைசி order-ல இருந்து நாட்கள்;
- average order value, முந்தைய 30 நாளோட ஒப்பிட்ட மாற்றம்;
- கடைசி 30 நாள்ல 15 நிமிஷத்துக்கு மேல delay ஆன orders-ஓட share;
- கடைசியா கொடுத்த rating; கடைசி 30 நாள்ல support tickets;
- orders-ல weekend share; customer வழக்கமா payday week-ல order பண்றாரா;
- city tier, பக்கத்துல இருக்குற cloud kitchen cluster-க்கு distance.

Results: order counts மட்டும் வச்ச baseline AUC 0.72 எடுத்துச்சு; engineered features-ஓட 0.81. புதுசா சேர்த்ததுல ரொம்ப value கொடுத்தது delay share-ம், order value-ல மாற்றமும்.

Leakage பயம்: ஒரு early draft-ல misaligned join வழியா "customer அடுத்த 7 நாள்ல support-ஐ contact பண்ணாங்க"ங்குற feature வந்திருந்தது. Validation score 0.95-க்கு குதிச்சதால, அது நம்ப முடியாத அளவு நல்லா இருந்ததால, கண்டுபிடிச்சாங்க.

| Model | AUC |
| --- | --- |
| Baseline: order counts மட்டும் | 0.72 |
| Engineered features-ஓட | 0.81 |
| தவறா வந்த leaky feature-ஓட | 0.95 (நம்ப முடியாத அளவு நல்லா இருக்கு) |
| Leak-ஐ நீக்கினதுக்கு அப்புறம் | 0.81 |

**எந்த features முக்கியம், ஏன்.** Delay share, business ஏற்கனவே சந்தேகப்பட்டதை capture பண்ணுச்சு: ஒரு late delivery-ஐ customers மன்னிப்பாங்க, ஆனா ஒரு மாசத்துல ரெண்டு வந்தா போட்டியாளரை try பண்ணுவாங்க. Order value-ல மாற்றம், customers மெதுவா விலகிப் போறதை பிடிச்சுது: நிறுத்துறதுக்கு முன்னாடி சின்ன baskets order பண்ணுவாங்க. ரெண்டும் raw order counts-ல தெரியாது. ரெண்டும் operations team கூட பேசினதுல இருந்து வந்தது, company-கிட்ட ஏற்கனவே இருந்த data-ல இருந்து compute பண்றதும் சுலபம். எது உதவலைன்னும் team கத்துக்கிட்டாங்க: order recency இருந்தப்போ app session counts கிட்டத்தட்ட எதுவும் சேர்க்கல. அதனால அதை விட்டுட்டு, செலவு அதிகமான ஒரு daily data pipeline-ஐ மிச்சப்படுத்துனாங்க.

## பொதுவான தவறுகள்

- **Features-ல எதிர்கால தகவல்.** எல்லாத்தையும் prediction time "as of" compute பண்ணுங்க.
- **Training-க்கும் serving-க்கும் வேற வேற code.** Feature code-ஐ share பண்ணுங்க, இல்லன்னா feature store use பண்ணுங்க.
- **எல்லா data-லயும் target encoding.** Training folds-க்குள்ள மட்டும் compute பண்ணுங்க.
- **Indian calendar effects-ஐ கவனிக்காம விடுறது.** Festivals-உம் salary cycles-உம் முக்கியம்.
- **நம்ப முடியாத அளவு நல்ல scores.** Leakage இருக்கான்னு investigate பண்ணுங்க.

- **ஒரே நேரத்துல நூற்றுக்கணக்கான features build பண்றது.** Features-ஐ சின்ன groups-ஆ சேர்த்து, ஒவ்வொரு group-ஓட gain-ஐயும் அளவுங்க. அப்போதான் எது தன் இடத்துக்கும், maintenance செலவுக்கும் தகுதின்னு தெரியும்.
- **Prediction day அல்லது அதுக்கு அப்புறத்தை சேர்க்குற aggregates.**
- **Festival dates ஒரு தடவை hard-code பண்ணி**, அடுத்த வருஷம் தப்பாகிடுறது.
- **Training-க்கும் serving-க்கும் share பண்றதுக்கு பதிலா, feature code-ஐ copy பண்றது.**

## Heavy feature engineering தேவையில்லாத இடங்கள்

- **Unstructured data**: images, audio, நீளமான text. அங்க neural networks தங்களுக்கான features-ஐ தானே கத்துக்கும்.
- **Strong pretrained model அல்லது embeddings** உங்களுக்கு வேண்டியதை ஏற்கனவே capture பண்ணியிருந்தா.
- **ரொம்ப சின்ன data**: அங்க நூறு engineered features-ஐ விட, சில expert features-உம் simple model-உம் நல்லா வேலை செய்யும்.

## Demo-ல இருந்து production-க்கு

- **Features-ஐ prediction time "as of" compute பண்ணுங்க**, எதிர்கால data வந்தா fail ஆகுற tests-ஓட.
- **Training-க்கும் serving-க்கும் feature code-ஐ share பண்ணுங்க**, இல்லன்னா feature store use பண்ணுங்க.
- **Calendars-ஐ data tables-ல வைங்க**, வருஷம், region வாரியா dates-ஓட.
- **Feature distributions-ஐ drift-க்காக track பண்ணுங்க**, ஒவ்வொரு source-க்கும் missing rates-ஐயும்.
- **ஒவ்வொரு retrain-லயும் feature group வாரியா value-வை அளவுங்க**, உதவுறதை நிறுத்தினதை drop பண்ணுங்க.

## Practice

Kaggle-ஓட Feature Engineering course-ஐ முடிச்சு, Google-ஓட Rules of ML-ல feature engineering section-ஐ படிங்க.

1. ஒரு transactions dataset-ல இருந்து, தேர்ந்தெடுத்த ஒரு date "as of" compute பண்ண பத்து time-windowed features build பண்ணுங்க, எதிர்கால data இல்லாம.
2. உங்க features, simple baseline-ஐ விட model-ஐ எவ்வளவு improve பண்ணுதுன்னு அளவுங்க.
3. வேணும்னே ஒரு leaky feature-ஐ சேர்த்து, score குதிக்குறதை பாருங்க, அதை பிடிக்குற ஒரு test எழுதுங்க.
4. மூணு மாசாந்திர cutoffs-ல features build பண்ணி, முதல் ரெண்டுல train பண்ணி மூணாவதுல test பண்ணுங்க, days_since_last மட்டும் use பண்ற model-ஓட ஒப்பிடுங்க.

**இது முடிஞ்சதுன்னு சொல்லலாம், எப்போன்னா** ஒவ்வொரு feature-உம் prediction time "as of" எப்படி compute ஆகுதுன்னும், training-உம் serving-உம் அதை எப்படி ஒரே மாதிரி compute பண்ணுதுன்னும் உங்களால explain பண்ண முடியும்போது.
