## இது என்ன

**Cache**, data-வோட ஒரு copy-ஐ, அது வழக்கமா இருக்குற இடத்தை விட வேகமான அல்லது பக்கத்துல இருக்குற இடத்துல வச்சிருக்கும்; அதனால repeat requests, வேலையை திரும்ப பண்ணாம சீக்கிரம் பதில் வாங்கும். Memory-ல இருந்து படிக்க microseconds ஆகும்; ஒரு database query-க்கு milliseconds ஆகலாம்; உலகத்தோட மறுபக்கத்துக்கு ஒரு request போக நூற்றுக்கணக்கான milliseconds ஆகும்.

Caches பல layers-ல இருக்கு:

- **Browser**, ஏற்கனவே download பண்ண images, scripts-ஐ வச்சிருக்கும்;
- ஒரு **CDN** (content delivery network), பல நகரங்கள்ல இருக்குற servers-ல files-ஐ வச்சிருக்கும்;
- Redis மாதிரி ஒரு **application cache**, செலவான queries அல்லது API calls-ஓட results-ஐ வச்சிருக்கும்;
- **Database**, அடிக்கடி use ஆகுற pages-ஐ தன்னோட சொந்த memory-ல வச்சிருக்கும்.

```flow
Patna-ல இருக்குற User -[1. ஒரு image]-> Kolkata-ல இருக்குற CDN edge
Kolkata-ல இருக்குற CDN edge -[hit]-> சுமார் 20 ms-ல serve ஆச்சு
Kolkata-ல இருக்குற CDN edge -[miss]-> Origin storage
Patna-ல இருக்குற User -[2. product API]-> App server -> Redis cache
Redis cache -[hit]-> சுமார் 1 ms
Redis cache -[miss]-> Database | result TTL-ஓட Redis-ல store ஆகும்
```

## இது எப்படி work ஆகுது

**Cache-aside** application caches-க்கு மிகவும் பொதுவான pattern. ஒவ்வொரு read-லயும் app முதல்ல cache-ஐ check பண்ணும். Hit ஆனா cached value-ஐ return பண்ணும். Miss ஆனா database-ல இருந்து படிச்சு, result-ஐ expiry-ஓட cache-ல store பண்ணி, return பண்ணும். Writes database-க்கு போகும், அப்புறம் app cached copy-ஐ delete அல்லது update பண்ணும்.

ஒவ்வொரு cached item-க்கும் ஒரு **TTL** (time to live) வேணும். குறுகிய TTLs data-வை fresh-ஆ வச்சிருக்கும், ஆனா அதிக misses வரும்; நீண்ட TTLs வேகமா இருக்கும், ஆனா பழைய data-வை serve பண்ற risk இருக்கும். Data எவ்வளவு அடிக்கடி மாறுது, பழசா இருந்தா என்ன செலவுன்னு பார்த்து, வகை வாரியா தேர்ந்தெடுங்க.

**Cache invalidation**, அதாவது source மாறின பிறகு cached data-வை சரியா வச்சுக்கிறது, தான் கஷ்டமான பகுதி. Options: items-ஐ அவற்றோட TTL-ல expire ஆக விடுறது; data எழுதப்படும் போதெல்லாம் key-ஐ delete பண்றது; அல்லது `price:v42` மாதிரி keys-ஐ version பண்றது, அப்போ புது data புது key-ஐ use பண்ணும். CDN-ல இருக்குற files-க்கு, வழக்கமான trick: file name-ல `app.3f9a1c.js` மாதிரி ஒரு content hash-ஐ வைக்கிறது; அப்போ மாறின file ஒரு புது URL, பழைய copies-ஐ clear பண்ணவே தேவையில்ல.

ரொம்ப popular ஆன ஒரு key expire ஆகும்போது, ஆயிரக்கணக்கான requests ஒரே நேரத்துல miss ஆகி, எல்லாம் database-ஐ தாக்கலாம்: இதுதான் **cache stampede**. Fixes: ஒரே ஒரு request key-ஐ refresh பண்ணும்போது, மத்தவை காத்திருக்குற அல்லது பழைய value-ஐ வாங்குற மாதிரி வைக்கிறது; TTLs-ல சின்ன random jitter சேர்க்கிறது; hot keys-ஐ expire ஆகுறதுக்கு முன்னாடியே refresh பண்றது.

Cloudflare, Akamai, Amazon CloudFront, Google Cloud CDN மாதிரி **CDNs**-க்கு இந்தியா முழுக்கவும் உலகம் முழுக்கவும் servers இருக்கு. அவை images, video, scripts, ஏன், cache பண்ணக்கூடிய முழு pages-ஐயும் கூட user-க்கு பக்கத்துல இருந்து serve பண்ணும்; இது load time-ஐ குறைச்சு, உங்க origin servers-ஓட சுமையை குறைக்கும். Video platforms இவற்றை முழுசா நம்பியிருக்கு.

| என்ன | எங்க cache பண்றது | வழக்கமான TTL | கவனிக்க வேண்டியது |
|---|---|---|---|
| Images, video, JS, CSS | CDN, browser | நாட்கள்ல இருந்து ஒரு வருஷம் வரை, hashed names-ஓட | names மாறலைன்னா பழைய files |
| Published results மாதிரி public pages | CDN | நிமிஷங்கள் | updates-ஆகும்போது clear பண்றது |
| செலவான query results | Redis | வினாடிகள்ல இருந்து நிமிஷங்கள் | பழைய values, stampedes |
| User sessions | Redis | மணிநேரங்கள் | security; users-க்கு நடுவுல ஒருபோதும் share பண்ணாதீங்க |
| Balances, checkout-ல live inventory | cache பண்ணாதீங்க, அல்லது ரொம்ப குறுகிய நேரம் | அதிகபட்சம் வினாடிகள் | தப்பான numbers பணம் செலவழிக்கும் |

**Browser-ல try பண்ணுங்க.** ஒரு சின்ன cache-ஐ simulate பண்ணி, அதோட size-ஓட hit rate எப்படி மாறுதுன்னு பாருங்க.

```python
from collections import OrderedDict
import random

def hit_rate(capacity, requests):
    cache, hits = OrderedDict(), 0
    for key in requests:
        if key in cache:
            hits += 1; cache.move_to_end(key)
        else:
            cache[key] = True
            if len(cache) > capacity: cache.popitem(last=False)   # evict the least recently used
    return hits / len(requests)

random.seed(1)
popular = [f"page-{int(random.paretovariate(1.2))}" for _ in range(5000)]   # a few pages get most traffic
for size in (5, 20, 100):
    print(f"cache of {size:>3}: {hit_rate(size, popular):.0%} hits")
```

## ஒரு worked example

Rohan, Delhi-ல ஒரு online test-prep company-ல வேலை செய்றாங்க. JEE answer key release ஆகும்போது, லட்சக்கணக்கான students நிமிஷங்களுக்குள்ள அதே pages-ஐ திறப்பாங்க, site முன்னாடி ஊர்ந்து போற அளவுக்கு மெதுவாயிடும்.

அவங்க முதல்ல அளந்து பார்த்தாங்க. Answer-key PDF-உம் images-உம் தான் பெரும்பாலான bytes; "my score" API தான் பெரும்பாலான database queries-ஐ உருவாக்குச்சு.

**Static files CDN-க்கு.** PDF, images, front-end files-ஐ ஒரு CDN-க்கு பின்னாடி இருக்குற object storage-க்கு மாத்தினாங்க, content-hashed names, ஒரு வருஷ browser cache-ஓட. Guwahati, Kochi-ல இருக்குற students இப்போ பக்கத்துல இருக்குற edge servers-ல இருந்து download பண்ணாங்க. Origin bandwidth 90%-க்கு மேல குறைஞ்சுச்சு.

**Hot queries Redis-க்கு.** சரியான options-ஓட எல்லா questions-ஐயும் list பண்ற page, எல்லா students-க்கும் ஒரே மாதிரி இருந்துச்சு. அதை cache-aside வச்சு, 5 நிமிஷ TTL-ஓட Redis-ல cache பண்ணாங்க. Board ஒரு சர்ச்சைக்குரிய answer-ஐ திருத்தும்போது, ஒரு admin action key-ஐ delete பண்ணுச்சு; அதனால திருத்தம் 5 நிமிஷம் கழிச்சு இல்லாம உடனே தெரிஞ்சுச்சு.

**Stampede protection.** சரியா காலை 10 மணிக்கு cached list expire ஆச்சு, அதே நேரம் 20,000 students refresh பண்ணாங்க, database கூர்மையா எகிறுச்சு. Rohan ஒரு lock-ஐ சேர்த்தாங்க; அப்போ ஒரு request key-ஐ திரும்ப build பண்ணும், மத்தவை ஒரு-ரெண்டு வினாடிக்கு முந்தைய value-ஐ வாங்கும்; கூடவே TTLs-ல random jitter-உம்.

**எதை cache பண்ணல.** ஒவ்வொரு student-ஓட கணக்கிடப்பட்ட score, அவங்களோட சொந்த responses-ல இருந்து compute ஆகி, user வாரியா store ஆச்சு; அது ஒரு shared page cache-ல ஒருபோதும் போகல, அதனால எந்த student-உம் இன்னொருத்தரோட score-ஐ பார்க்க முடியாது.

அடுத்த release நாள்ல, peak நேரத்துலயும் page loads ஒரு வினாடிக்கு கீழயே இருந்துச்சு, database அதோட capacity-ல பாதியை தாண்டவே இல்ல.

## பொதுவா பண்ற தப்புகள்

**TTL இல்லாம cache பண்றது.** அப்போ ஒரு மாற்றத்துக்கு அப்புறம் data எப்பவும் தப்பாவே இருக்கும். நீண்ட expiry-ஆ இருந்தாலும் எப்பவும் ஒரு expiry set பண்ணுங்க.

**Private data-வை shared cache-ல cache பண்றது.** Login ஆன ஒரு user-க்காக cache ஆன page இன்னொருத்தருக்கு serve ஆகலாம். Personal data-வை shared caches-ல இருந்து வெளியே வச்சுக்கோங்க, அல்லது user வாரியா key பண்ணுங்க.

**Writes-ல invalidation-ஐ மறக்குறது.** Database-ஐ update பண்ணி cache-ஐ பண்ணலைன்னா, expiry வரைக்கும் பழைய value தெரியும். Freshness முக்கியமான data-க்கு, write-ல key-ஐ delete பண்ணுங்க.

**சரியா இருக்கணும்கிற data-வை cache பண்றது.** Checkout-ல seat counts, balances, stock levels, அது முக்கியமான நேரத்துல source of truth-ல இருந்து வரணும்.

**Stampedes-ஐ கண்டுக்காம இருக்குறது.** Load-ல ஒரு hot key expire ஆனா database-ஐ கீழே தள்ளிடும். Locks, early refresh, jittered TTLs use பண்ணுங்க.

**அளக்குறதுக்கு முன்னாடி cache பண்றது.** மெதுவா இருக்குற, அடிக்கடி படிக்கப்படுறதை cache பண்ணுங்க. அரிதா use ஆகுறதை cache பண்ணா சிக்கலை மட்டும் கூட்டும்.

## Practice பண்ணுங்க

1. CDNs எப்படி work ஆகுது, interviews-ல caching எப்படி வருதுன்னு Watch & learn panel-ல இருக்குற video lessons-ஐ பாருங்க.
2. மேல இருக்குற exercise-ஐ பண்ணுங்க.
3. Project check-ஐ பண்ணுங்க: ஒரு மெதுவான function-க்கு முன்னாடி cache-aside, hit, miss logs-ஓட, timings-ஓட.
4. ஒரு பெரிய site-ல உங்க browser-ஓட developer tools-ஐ திறந்து, cached responses, CDN headers-ஐ தேடுங்க.
