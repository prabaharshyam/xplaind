## இது என்ன

LLM apps-ல வழக்கமான web security கவலைகளும் சில புதுசும் சேர்ந்து வருது. LLM applications-க்கான OWASP Top 10 பரவலா use ஆகுற ஒரு checklist. பெரும்பாலான apps-க்கு இந்த பகுதிகள் தான் முக்கியம்:

- **Secrets**: API keys, credentials.
- **User data**: models-க்கு அனுப்பப்படுற, logs-ல சேமிக்கப்படுற, answers-ல வெளிப்படுற personal information.
- **Access**: app-ஐ யாரு use பண்ணலாம், ஒவ்வொரு user-உம் எதை பார்க்கலாம்.
- **Model-specific risks**: prompt injection, system prompt leak ஆகுறது, அதிகப்படியான agency, model output-ஐ பாதுகாப்பில்லாம கையாளுறது.

| | முன்னாடி | பின்னாடி |
|---|---|---|
| API key | Browser-ஓட JavaScript-ல, நேரடியா model-க்கு அனுப்பப்படுது | Backend-ல மட்டும், secrets-ல இருந்து |
| Prompt | "admin password: ..." | Secrets எதுவும் இல்ல |
| Customer data | முழு record-உம் model-க்கு போகுது | Tool order id, status, date மட்டும் தருது |
| Customer id | Browser-ல இருந்து எடுக்கப்படுது | Verify பண்ணின session-ல இருந்து எடுக்கப்படுது |
| Reply | Raw HTML-ஆ போடப்படுது | Text-ஆ render ஆகுது |
| Logs | Phone numbers-ஓட முழு chats | Mask பண்ணி, 30 நாள் வச்சிருக்கும் |

## இது எப்படி work ஆகுது

**Keys-ஐ server-ல வைங்க.** Model API key, server-side environment variables அல்லது ஒரு secret manager-ல இருக்கணும். Browser JavaScript, mobile apps, Git-ல ஒருபோதும் வைக்காதீங்க. Browser உங்க backend-ஐ call பண்ணும்; உங்க backend model-ஐ call பண்ணும். ஒரு key leak ஆனா உடனே revoke பண்ணுங்க.

**Prompts-ல secrets வேண்டாம்.** Users system prompt-ஐ வெளியே எடுத்துடுவாங்கன்னு எடுத்துக்கோங்க. Passwords, keys, பார்க்கக்கூடாதுன்னு நினைக்குற internal-only தகவல் எதையும் சேர்க்காதீங்க.

**Task-க்கு தேவையானதை மட்டும் அனுப்புங்க.** "என் order எங்க இருக்கு?"-ன்னு பதில் சொல்ற ஒரு support bot-க்கு order status வேணும், customer-ஓட முழு profile, payment details, address history வேண்டாம். Data minimisation, ஏதாவது leak ஆனா பாதிப்பை குறைக்கும், இந்தியாவோட DPDP Act-ஓட ஒரு principle-உம் கூட.

Logs, traces-ல **personal data-ஐ mask பண்ணுங்க**, retention periods வைங்க, access-ஐ restrict பண்ணுங்க.

**Authenticate பண்ணுங்க, authorise பண்ணுங்க.** Users sign in பண்றாங்க; ஒவ்வொரு request-உம் அவங்க யாருன்னு check பண்ணுது; retrieval-உம் tools-உம் அந்த user-ஓட data-ஐ மட்டும் access பண்ணும். Browser-ல இருந்து வர்ற user id-ஐ verify பண்ணாம நம்பாதீங்க.

**Model output-ஐ untrusted-ஆ நடத்துங்க.** அதை நேரடியா HTML (cross-site scripting), SQL, shell commands-ல போடாதீங்க. எந்த user input-ஐயும் போல escape அல்லது validate பண்ணுங்க.

**Capabilities-ஐ limit பண்ணுங்க.** தேவையான குறைந்தபட்ச permissions உள்ள tools; risky actions-க்கு approvals; ஒரு user-க்கு rate limits.

**Vendor terms.** உங்க model provider data-ஐ எப்படி store பண்ணி use பண்றாங்கன்னு check பண்ணுங்க, உங்க users, clients-ஓட தேவைகளுக்கு பொருந்துற settings, regions-ஐ தேர்ந்தெடுங்க.

**Checklist-ஐ நடந்து பாருங்க.** உங்க app-க்கு LLM applications-க்கான OWASP Top 10-ஐ பாருங்க, ஒவ்வொரு item-க்கும் உங்க defence-ஐ குறிச்சு வைங்க.

**பெரும்பாலான LLM apps-க்கான checklist items:**

| பகுதி | கேள்வி | நல்ல பதில் |
| --- | --- | --- |
| Keys | Key-ஐ browser-ல அல்லது Git history-ல பார்க்க முடியுமா? | முடியாது; server-side, எப்போவாவது வெளிப்பட்டா rotate பண்ணணும் |
| Prompts | System prompt-ல ரகசியமா எதாவது இருக்கா? | இல்ல |
| Data | ஒவ்வொரு feature-க்கும் model-க்கு என்ன போகுது? | Task-க்கு தேவையான fields மட்டும் |
| Identity | User id எங்கிருந்து வருது? | Verify பண்ணின session |
| Output | Model output எப்படி காட்டப்படுது, use ஆகுது? | Escape பண்ணின text; எந்த query அல்லது command-க்கும் முன்னாடி validate |
| Logs | என்ன personal data log ஆகுது, எவ்வளவு நாள்? | Mask; நிலையான retention; restricted access |
| Tools | Model எதை trigger பண்ணலாம்? | Least privilege; risky actions-க்கு approval |
| Vendor | Provider data-ஐ எப்படி use பண்ணி வச்சிருக்காங்க? | Terms check பண்ணியாச்சு; பொருத்தமான region, settings |

**உள்ளேயும் வெளியேயும் guardrails.** **Input guardrail**, model-க்கு போகப்போறதை check பண்ணும்: personal data, company secrets, attack அறிகுறிகள். **Output guardrail**, யாராவது பார்க்குறதுக்கு முன்னாடி அல்லது code அதன்படி செயல்படுறதுக்கு முன்னாடி திரும்பி வர்றதை check பண்ணும்: personal data, பாதுகாப்பில்லாத content, சிதைஞ்ச output, நடக்கக்கூடாத ஒரு tool call. ஒரு guardrail trigger ஆனா, block பண்ணலாம், mask பண்ணலாம், retry பண்ணலாம், இல்ல ஒரு நபர்கிட்ட ஒப்படைக்கலாம். ரெண்டு trade-offs: ஒவ்வொரு check-உம் delay சேர்க்கும், streaming-ல output checks கஷ்டம், ஏன்னா முழு reply-ஐ check பண்றதுக்கு முன்னாடியே வார்த்தைகள் user-கிட்ட போயிடும். Streamed chat-க்கு chunks-ஆ check பண்ணுங்க, கடுமையான checks-ஐ வார்த்தைகளுக்கு இல்ல, actions-க்கு வச்சுக்கோங்க.

**Leaks பெரும்பாலும் நல்ல எண்ணத்துல தான் ஆரம்பிக்கும்.** 2023-ல Samsung engineers உதவி கேக்க, internal source code-ஐ ஒரு public chatbot-ல paste பண்ணாங்க. Apps-லயும் இதே நடக்கும்: ஒரு developer internal policy-ஐ system prompt-ல paste பண்றாங்க, அல்லது ஒரு tool முழு database row-ஐ context-க்குள்ள இழுக்குது. ஒவ்வொரு feature-க்கும் கேளுங்க: "எது நம்ம servers-ஐ விட்டு வெளிய போகுது, அது தேவையா?"

**Mask, call, unmask.** பல tasks-க்கு model-க்கு உண்மையான identifiers தேவையில்ல. Call-க்கு முன்னாடி அவற்றை placeholders-ஆ மாத்துங்க, ஒரு map-ஐ உங்க server-ல வச்சுக்கோங்க, அப்புறம் உண்மையான values-ஐ திருப்பி போடுங்க:

```python
    for label in ["UPI", "EMAIL", "PAN", "AADHAAR", "PHONE"]:     # UPI first: UPI ids look like emails
        def swap(m, label=label):
            count[label] = count.get(label, 0) + 1
            key = f"[{label}_{count[label]}]"
            mapping[key] = m.group(0)
            return key
        text = re.sub(PATTERNS[label], swap, text)
    return text, mapping

def unmask(text, mapping):
    for key, value in mapping.items():
        text = text.replace(key, value)
    return text

safe, keys = mask("My PAN is ABCDE1234F and mobile 9876543210, UPI ravi@okaxis.")
print(safe)    # My PAN is [PAN_1] and mobile [PHONE_1], UPI [UPI_1].
```

இந்த மாதிரி patterns சில வடிவங்களை தவறவிடும், சில சாதாரண numbers-ஐ பிடிச்சுடும்; அதனால உண்மையான (mask பண்ணின) samples-ல test பண்ணுங்க, risk அதிகமா இருந்தா Microsoft Presidio மாதிரி ஒரு dedicated detection tool use பண்ணுங்க. Masking-க்கும் limits இருக்கு: ஒரு model தான் பார்க்காத PAN-ஐ check பண்ண முடியாது, அதனால அந்த tasks-க்கு check உங்க சொந்த code-ல தான் இருக்கணும்.

**Retrieval permissions-ஐ மதிக்கணும்.** ஒரு RAG app-ல search index-ல பெரும்பாலும் பல users அல்லது departments-ஓட documents இருக்கும். எதுவும் prompt-க்குள்ள போறதுக்கு **முன்னாடி**, sign in பண்ணின user படிக்கலாம்ங்கிறதை வச்சு results-ஐ filter பண்ணுங்க; model-க்கு காட்டிட்ட ரகசியத்தை அது காப்பாத்த முடியாது.

**Bill-ஐயும் கட்டுப்படுத்துங்க.** வரம்பில்லாத requests, ஒரு user, ஒரு script, இல்ல ஒரு attacker செலவை ஏத்தவோ எல்லாருக்கும் app-ஐ மெதுவாக்கவோ விடும். ஒரு user-க்கு rate limits, input length-க்கு ஒரு cap, ஒரு daily budget alert வைங்க.

**LLM applications-க்கான OWASP Top 10 (2025), ஒவ்வொண்ணுக்கும் ஒரு defence:**

| Risk | ஒரு defence |
| --- | --- |
| Prompt injection | Retrieve பண்ணின, user text-ஐ data-ஆ நடத்துங்க; tools என்ன பண்ணலாம்னு limit பண்ணுங்க |
| Sensitive information disclosure | Data minimisation, masking, output checks |
| Supply chain | Packages-ஐ pin பண்ணி scan பண்ணுங்க; நம்பகமான sources-ல இருந்து models, datasets use பண்ணுங்க |
| Data and model poisoning | Training, retrieval data sources-ஐ review பண்ணி track பண்ணுங்க |
| Improper output handling | Output-ஐ escape பண்ணுங்க; SQL, shell, HTML-க்கு முன்னாடி validate பண்ணுங்க |
| Excessive agency | Least-privilege tools; actions-க்கு approval |
| System prompt leakage | Prompts-ல secrets, access rules வேண்டாம்; அவற்றை code-ல enforce பண்ணுங்க |
| Vector and embedding weaknesses | Retrieval-ல permission filters; tenant-க்கு தனி indexes |
| Misinformation | Grounding, citations, "எனக்கு தெரியாது"ன்னு சொல்றது |
| Unbounded consumption | Rate limits, input caps, budgets |

**இந்திய சட்டம், சுருக்கமா.** Digital Personal Data Protection Act, 2023-உம் அதோட Rules-உம் (இவை படிப்படியா அமலுக்கு வருது), இந்தியாவில இருக்குறவங்களோட digital personal data-க்கு பொருந்தும். நடைமுறையில: நீங்க சேகரிக்குறதுக்கு தெளிவான notice-உம் consent-உம், சொன்ன நோக்கத்துக்கு மட்டும் use பண்றது, தேவையான வரை மட்டும் வச்சுக்கிறது, நியாயமான security-ஓட பாதுகாக்குறது, மக்கள் தங்க data-ஐ access பண்ணவும் அழிக்கவும் விடுறது, breaches-ஐ report பண்றது. Children-ஓட data-க்கு verify பண்ணக்கூடிய parental consent வேணும். இது ஒரு சுருக்கம், legal advice இல்ல; உங்க case-க்கு தற்போதைய rules-ஐ check பண்ணுங்க.

**Git history-ல secrets-ஐ check பண்றது.** Code-ல இருந்து ஒரு key-ஐ நீக்கினா, history-ல இருந்து அது போகாது. முழு repository history-ல ஒரு secret scanner-ஐ run பண்ணுங்க, அது கண்டுபிடிக்குற எதையும் rotate பண்ணுங்க, புது secrets push ஆகுறதுக்கு முன்னாடியே பிடிக்க scanner-ஐ CI-ல சேருங்க.

**Users-க்கு இடையில access-ஐ test பண்றது.** ரெண்டு test accounts உருவாக்குங்க; முதல்ல இருந்து, requests-ல ids-ஐ மாத்தியும், bot-கிட்ட நேரடியா கேட்டும், ரெண்டாவது account-ஓட orders-ஐ படிக்க try பண்ணுங்க. ரெண்டும் fail ஆகணும். இவற்றை automated tests-ஆ வச்சுக்கோங்க.

## ஒரு worked example

Bengaluru-ல ஒரு D2C brand ஒரு support bot build பண்றாங்க. முதல் version-ஓட security review இதை கண்டுபிடிக்குது:

- API key React front end-ல இருந்துச்சு, browser-ஓட developer tools-ல தெரிஞ்சுது. Fix: calls ஒரு backend-க்கு மாறுச்சு; key rotate ஆச்சு.
- System prompt-ல "reference-க்காக" admin dashboard password இருந்துச்சு. எடுத்துட்டு rotate பண்ணாங்க.
- Order கேள்விகளுக்கு பதில் சொல்ல, bot customer-ஓட முழு record-ஐ (address, phone, பழைய orders, saved payment method) prompt-க்குள்ள இழுத்துச்சு. Fix: ஒரு tool order id, status, expected date மட்டும் தருது.
- Customer id, browser request-ல இருந்த ஒரு field-ல இருந்து வந்துச்சு. Fix: அதுக்கு பதிலா verify பண்ணின session-ல இருந்து எடுக்குறாங்க.
- Bot replies raw HTML-ஆ போடப்பட்டுச்சு; ஒரு crafted message ஒரு script-ஐ inject பண்ணலாம். Fix: replies text-ஆ render ஆகுது.
- Logs, phone numbers-ஓட முழு conversations-ஐ சேமிச்சுது. Fix: masking, 30 நாள் retention.

| Finding | Fix |
| --- | --- |
| React front end-ல API key | Calls backend-க்கு மாத்தப்பட்டுச்சு; key rotate |
| System prompt-ல admin password | எடுத்து rotate பண்ணாங்க |
| Prompt-ல முழு customer record | Tool order id, status, date மட்டும் தருது |
| Browser-ல இருந்து customer id | Verify பண்ணின session-ல இருந்து எடுக்கப்படுது |
| Replies raw HTML-ஆ | Text-ஆ render |
| Logs-ல phone numbers-ஓட முழு chats | Mask, 30 நாள் retention |

## பொதுவா பண்ற தப்புகள்

- **Front-end code அல்லது Git-ல API keys.**
- **System prompts-ல secrets.**
- **முழு customer records-ஐ model-க்கு அனுப்புறது.**
- **Browser-ல இருந்து வர்ற user ids-ஐ நம்புறது.**
- **Model output-ஐ raw HTML-ஆ render பண்றது.**
- **Permission filters இல்லாத retrieval.** User பார்க்கவே கூடாத ஒரு document-ஐ model சந்தோஷமா quote பண்ணும்.
- **Prompt-ல மட்டும் எழுதின access rules.** Prompt-ல "மத்த customers-ஓட orders-ஐ காட்டாதே"ன்னு எழுதுறது ஒரு நம்பிக்கை; code-ல ஒரு check தான் ஒரு control.
- **Use-க்கு limits இல்லாதது.** ஒரு script bill-ஐ ஏத்தலாம் அல்லது எல்லாருக்கும் app-ஐ மெதுவாக்கலாம்.

## Risk குறைவா இருக்குற இடங்கள்

- **உங்க சொந்த laptop-ல உங்க சொந்த data-ஓட ஒரு personal tool**-க்கும் key Git-ல இருந்து வெளிய இருக்கணும், ஆனா masking அல்லது audit logs தேவையில்ல.
- **Public data மட்டும்**, உதாரணம் வெளியிடப்பட்ட அரசு circulars மேல ஒரு bot: output handling, injection, cost limits மேல கவனம் வைங்க.
- **சின்ன நம்பகமான team-க்கான read-only internal tools**: key-ஐ பாதுகாப்பா வைங்க, tools எதை எட்டலாம்னு limit பண்ணுங்க, ஆனா முழு guardrail stacks காத்திருக்கலாம்.

Personal data, பணம், write actions, நிறைய users, அல்லது banking, insurance, health மாதிரி regulated sectors இருக்கும்போது risk வேகமா ஏறும்.

## Demo-ல இருந்து production வரை

- **ஒரு data map எழுதுங்க**: ஒவ்வொரு feature-க்கும், என்ன personal data use ஆகுது, எங்க போகுது, எவ்வளவு நாள் வச்சிருக்கு.
- **உங்க model provider-ஓட ஒரு data processing agreement-ல** கையெழுத்து போடுங்க, retention, region settings-ஐ அதுக்கேத்த மாதிரி தேர்ந்தெடுங்க.
- **Checks-ஐ automate பண்ணுங்க**: CI-ல ஒரு secret scanner, ரெண்டு-account access tests, injection tests, output-escaping tests.
- **Keys-ஐ schedule-ல rotate பண்ணுங்க**, access இருந்த யாராவது விலகினா உடனே rotate பண்ணுங்க.
- **Incidents-க்கு plan பண்ணுங்க**: யாரு முடிவு எடுப்பாங்க, keys-ஐ எப்படி revoke பண்றது, பாதிக்கப்பட்ட users-கிட்டயும் regulator-கிட்டயும் எப்படி சொல்றது, எவ்வளவு வேகமா.
- **சில மாசத்துக்கு ஒரு தடவை access-ஐ review பண்ணுங்க**: logs, index, admin tools-ஐ யாரு படிக்கலாம்.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற LLM applications-க்கான OWASP Top 10-ஐ பாருங்க.

1. உங்க app-ஓட API key எங்க இருக்குன்னு check பண்ணி, அது ஒருபோதும் browser-க்கோ Git history-க்கோ போகலன்னு உறுதி பண்ணுங்க.
2. ஒரு feature-க்கு model-க்கு அனுப்புற data-வை list பண்ணி, task-க்கு தேவையில்லாத எதையும் எடுத்துடுங்க.
3. உங்க app-க்கு பொருந்துற ஒவ்வொரு OWASP item-க்கும் உங்க defence-ஐ எழுதுங்க.
4. பத்து realistic support messages-ல mask function-ஐ run பண்ணி, எதை தவறவிட்டுச்சு அல்லது தப்பா பிடிச்சுதுன்னு குறிச்சு, ஒரு pattern-ஐ improve பண்ணுங்க.

இன்னும் ஆழமா படிக்க, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 5 attacks, defences பத்தியும், chapter 10 input, output guardrails, masking பத்தியும் சொல்லுது.

**இவை முடிஞ்சா நீங்க ready:** key எங்க இருக்கு, model-க்கு என்ன data போகுது, ஏன்னு explain பண்ணலாம், ஒரு user இன்னொரு user-ஓட data-ஐ பார்க்காம எப்படி தடுக்கப்படுறாங்கன்னும் சொல்லலாம்.
