## இது என்ன

ஒரு GPU-க்கு memory-உம் speed-உம் ஒரு fixed அளவு தான். ரெண்டு வேற வேற problems உங்களை நிறைய GPUs use பண்ண வைக்கும்:

1. **Model ஒரு GPU-க்கு ரொம்ப பெருசு.** 16-bit precision-ல ஒரு 70B model-க்கு weights-க்கு மட்டுமே சுமார் 140 GB வேணும், ஒரு 80 GB GPU-ஐ விட அதிகம்.
2. **ஒரு copy-ஆல உங்க எல்லா users-க்கும் serve பண்ண முடியாது.** Model பொருந்தினாலும், busy hour-க்கு பல copies தேவைப்படலாம்.

ரெண்டு அடிப்படை பதில்கள் இருக்கு: model-ஐ **copy** பண்ணுங்க, அல்லது **பிரிங்க**.

- **Replica parallelism** (training-ல **data parallelism**-னு சொல்வாங்க): பல GPUs-ல முழு copies ஓட்டுங்க. ஒவ்வொரு copy-உம் வேற வேற requests-ஐ serve பண்ணும், அல்லது வேற வேற batches-ல train பண்ணும்.
- **Model parallelism**: ஒரு model-ஐ GPUs முழுக்க பிரிக்கிறது. முக்கிய வழிகள்: **tensor parallelism** (ஒவ்வொரு layer-க்குள்ள இருக்குற வேலையை பிரிக்கிறது), **pipeline parallelism** (layers-ஐ stages-னு சொல்ற groups-ஆ பிரிக்கிறது), mixture-of-experts models-க்கு **expert parallelism** (வேற வேற experts-ஐ வேற வேற GPUs-ல வைக்கிறது).

உண்மையான systems இதை சேர்த்து use பண்ணும்: உதாரணமா, 4 GPUs முழுக்க பிரிச்ச ஒரு model, அப்படி பல groups replicas-ஆ.

எல்லா தேர்வையும் ஓட்டுற rule: **பிரிச்சா communication cost ஆகும், communication-க்கு bandwidth வேணும்.** GPUs எவ்வளவு அடிக்கடி பேசணுமோ, அவங்களுக்கு இடையிலான link அவ்வளவு வேகமா இருக்கணும்.

## இது எப்படி work ஆகுது

### Replicas: model பொருந்தும்போதெல்லாம் இது தான் default

ஒவ்வொரு GPU-வும், அல்லது GPUs-ஓட ஒவ்வொரு group-உம், ஒரு முழு model-ஐ வச்சு தன்னோட requests-ஐ serve பண்ணும். Copies ஒண்ணுக்கொண்ணு பேசிக்கறதே இல்ல, அதனால எந்த network-உம் போதும், ஒண்ணு fail ஆனா மத்தது serve பண்ணிட்டே இருக்கும்.

எதை எங்க வைக்கிறதுன்னு முடிவு பண்றது ஒரு packing புதிர், கணக்கு simple தான்: 16-bit-ல ஒரு parameter-க்கு சுமார் 2 bytes, 8-bit-ல 1 byte, 4-bit-ல 0.5 bytes. உதாரணமா, ஒரு 80 GB GPU-ல 16-bit-ல ரெண்டு 8B models (ஒவ்வொண்ணும் 16 GB, மொத்தம் 32 GB) வைக்கலாம், அல்லது 8-bit-ல ஒரு 32B model (32 GB). ரெண்டுமே use பண்ணக்கூடிய 72 GB-ல KV caches-க்கு சுமார் 40 GB விடும். Engine-ஓட சொந்த use-க்கு இந்த lesson சுமார் 10% spare வைக்குது. (நிறைய versions-க்கு vLLM default-ஆ ஒவ்வொரு GPU-வோட memory-ல 90% use பண்ணுச்சு; recent versions default-ஐ மாத்திடுச்சு, அதனால உங்க version-ஐ check பண்ணுங்க.)

### Tensor parallelism: ஒவ்வொரு layer-ஓட வேலையையும் பகிர்றது

ஒரு transformer layer பெரும்பாலும் matrix multiplication தான். Tensor parallelism ஒவ்வொரு matrix-ஐயும், சொல்லுங்க 4 GPUs முழுக்க பிரிக்குது. ஒவ்வொரு GPU-வும் weights-ல கால்வாசியை வச்சு, தன்னோட slice-ஐ ஒரே நேரத்துல compute பண்ணும். வழக்கமான scheme-ல (Megatron-LM-ல இருந்து வந்தது), GPUs ஒரு layer-க்கு ரெண்டு தடவை partial results-ஐ சேர்க்கும்: attention-க்கு அப்புறம் ஒரு தடவை, feed-forward block-க்கு அப்புறம் ஒரு தடவை. 80 layers உள்ள ஒரு 70B model-க்கு, generate பண்ற ஒவ்வொரு token-க்கும் அது 160 exchanges.

இது ஏன் latency-ஐ குறைக்கலாம்: ஒவ்வொரு புது token-க்கும் ஒவ்வொரு weight-ஐயும் memory-ல இருந்து ஒரு தடவை படிக்கணும். 4 GPUs இருந்தா, ஒவ்வொண்ணும் கால்வாசியை படிக்கும், அதனால ஒரு token-க்கான நேரம் குறையும், ஆனா 4 மடங்கை விட குறைவா தான்.

சிக்கல் அந்த exchanges தான். அவை சின்னது, ஆனா ரொம்ப அடிக்கடி நடக்கும், அதனால உங்ககிட்ட இருக்குற மிக வேகமான link வேணும்:

| Link | எங்க இருக்கும் | Bandwidth (தோராயமான அளவு) | எதுக்கு நல்லது |
| --- | --- | --- | --- |
| NVLink (H100 SXM) | ஒரு server-க்குள்ள GPUs இடையில | 900 GB/s per GPU, ரெண்டு directions சேர்த்து | Tensor parallelism |
| PCIe Gen5 x16 | GPU-ல இருந்து CPU; NVLink இல்லாத servers-ல GPUs | 128 GB/s, ரெண்டு directions சேர்த்து | Replicas; pipeline |
| InfiniBand NDR | Servers இடையில | 400 Gb/s per port, ஒவ்வொரு direction-லயும் சுமார் 50 GB/s | Pipeline; training |

ஒரு cloud instance listing-ஐ படிக்கும்போது "SXM", "NVLink" (அல்லது "NVSwitch")-ஐ தேடுங்க. ஒரு "PCIe" GPU card-ல பொதுவா NVLink இருக்காது, இல்லன்னா ரெண்டு cards-ஐ மட்டும் இணைக்குற ஒரு bridge இருக்கும். L40S மாதிரி NVLink இல்லாத GPUs-ல, tensor parallelism-ஐ விட pipeline parallelism பெரும்பாலும் நல்ல throughput குடுக்கும்னு vLLM documentation சொல்லுது.

**Valid sizes.** Attention heads GPUs-க்கு இடையில பிரிக்கப்படுது, அதனால tensor-parallel size head count-ஐ சரியா வகுக்கணும். 64 heads உள்ள ஒரு model 1, 2, 4, 8, 16, 32 அல்லது 64 GPUs use பண்ணலாம், ஆனா 3, 5 அல்லது 6 முடியாது. நடைமுறையில, ஒரு server-க்குள்ள, அது 1, 2, 4 அல்லது 8.

**Gotcha: shared key-value heads.** பெரும்பாலான modern models attention heads-ஓட groups முழுக்க keys, values-ஐ share பண்ணுது. 8 key-value heads உள்ள ஒரு 70B model-ஐ 8 GPUs முழுக்க பிரிச்சா, ஒவ்வொரு GPU-லயும் ஒரு key-value head இருக்கும், அதனால KV cache சமமா பிரியும். 16 GPUs முழுக்க பிரிச்சா ஒவ்வொரு key-value head-உம் ரெண்டு GPUs-ல copy ஆகும், அதனால ஒரு GPU-க்கான cache சுருங்குறது நின்னுடும்.

### Pipeline parallelism: layers-ஐ stages-ஆ பிரிக்கிறது

Layers 1-ல இருந்து 40-ஐ server A-லயும், 41-ல இருந்து 80-ஐ server B-லயும் வைங்க. ஒரு request stage A வழியா ஓடி, network-ஐ கடந்து, அப்புறம் stage B வழியா ஓடும்.

Latency பத்தி துல்லியமா இருங்க. 80 layers ஒரு GPU-ல இருந்தாலும் பல GPUs-ல இருந்தாலும், ஒரு request அவை எல்லாத்தையும் வரிசையா கடக்கும். அதனால pipeline parallelism ஒவ்வொரு stage boundary-க்கும் ஒரு சின்ன hop மட்டும் சேர்க்கும், ஆனா அது **ஒரு request-ஐ வேகமாக்காது**, ஏன்னா எந்த stage-உம் இன்னொரு stage-ஓட வேலையை பகிர்ந்துக்கறதில்ல. Tensor parallelism ஒரு request-ஐ வேகமாக்கலாம்; pipeline-ஆல முடியாது.

அதோட பலம் bandwidth: ஒவ்வொரு stage-உம் தன்னோட output-ஐ மட்டும், ஒரு stage-க்கு ஒரு தடவை அனுப்புது, ஒரு layer-க்கு ரெண்டு தடவை இல்ல. அதனால தான் links மெதுவா இருக்குற servers முழுக்க pipeline-ஐ use பண்றாங்க.

அதோட பலவீனம் idle time, அதை **bubble**-னு சொல்வாங்க. ஒரே ஒரு request in flight-ல இருந்தா, ஒரு நேரத்துல ஒரு stage மட்டும் தான் வேலை செய்யும். எல்லா stages-ஐயும் busy-ஆ வைக்க, batch-ஐ **micro-batches**-ஆ வெட்டுவாங்க, அவை ஒண்ணு பின்னாடி ஒண்ணா pipe-ல போகும். Training-ல, `p` stages, `m` micro-batches இருந்தா, நேரத்துல சுமார் (p − 1) ÷ (m + p − 1) பங்கு idle-ஆ இருக்கும். உதாரணமா, 4 stages, 16 micro-batches-னா சுமார் 3 ÷ 19, அதாவது 16% வீண். Serving-ல நிறைய concurrent requests அதே மாதிரி pipe-ஐ நிரப்பும்.

### Mixture-of-experts models-உம் expert parallelism-உம்

ஒரு **mixture-of-experts (MoE)** model-ல, ஒவ்வொரு layer-லயும் நிறைய feed-forward "experts" இருக்கும், ஒரு சின்ன router ஒவ்வொரு token-ஐயும் அதுல சிலதுக்கு மட்டும் அனுப்பும். Sizing ரெண்டு வேற வேற numbers-ஐ follow பண்ணும்:

- **Memory total parameters-ஐ follow பண்ணும்.** ஒவ்வொரு expert-ஐயும் load பண்ணணும், ஏன்னா அடுத்த token-க்கு அதுல எது வேணும்னாலும் தேவைப்படலாம்.
- **ஒரு token-க்கான compute active parameters-ஐ follow பண்ணும்.** தேர்ந்தெடுத்த experts மட்டும் தான் ஓடும்.

உதாரணமா, Qwen3-235B-A22B-க்கு 235B total parameters, அதுல ஒரு token-க்கு சுமார் 22B active (128 experts-ல 8). 8-bit-ல அதோட weights-க்கு சுமார் 235 GB வேணும், அதனால குறைஞ்சது 80 GB-ஓட 4 GPUs வேணும் (4 × 72 = 288 GB use பண்ணக்கூடியது), cache-க்கு சுமார் 53 GB தான் மிச்சம். ஒரு 8-GPU server இன்னும் நிறைய இடம் குடுக்கும். ஆனாலும் ஒவ்வொரு token-க்கும் சுமாரா ஒரு 22B dense model-ஓட compute தான் ஆகும்.

**Expert parallelism** வேற வேற experts-ஐ வேற வேற GPUs-ல வச்சு, ஒவ்வொரு token-ஐயும் அதோட expert இருக்குற GPU-க்கு அனுப்பும். Attention பகுதி பொதுவா copy பண்ணப்படும் (data parallel) அல்லது tensor parallelism-ஆல பிரிக்கப்படும். vLLM-ல இது ஒரே ஒரு flag, `--enable-expert-parallel`. ரெண்டு gotchas: popular experts overload ஆகும், மத்தது சும்மா இருக்கும், அதனால engines expert load balancing குடுக்குது; பெரிய batch sizes-ல, கிட்டத்தட்ட ஒவ்வொரு expert-ஐயும் ஏதாவது ஒரு token use பண்ணும், அதனால MoE-ஓட memory-reading savings சுருங்கும்.

### நீளமான inputs: context, sequence parallelism

**Context parallelism** ஒரு ரொம்ப நீளமான input-ஐ, உதாரணமா ஒரு 500,000-token document-ஐ, chunks-ஆ வெட்டி வேற வேற GPUs-ல வைக்கும். Keys, values group-க்குள்ள சுத்தி அனுப்பப்படும்போது, ஒவ்வொரு GPU-வும் தன்னோட chunk-க்கு attention compute பண்ணும். **Sequence parallelism** tensor parallelism-க்கு ஒரு training add-on: normalisation மாதிரி, tensor parallelism முழுசா விட்டுடுற layer பகுதிகளை sequence-படி பிரிச்சு, activation memory-ஐ மிச்சப்படுத்தும். ரொம்ப நீளமான contexts-ல மட்டும் தான் இதுல ஏதாவது ஒண்ணு தேவைப்படும்.

### Serving-ஐ விட training-க்கு ரொம்ப அதிக memory வேணும்

Mixed precision, Adam optimiser-ஓட full training ஒரு parameter-க்கு சுமார் 16 bytes வச்சிருக்கும்: 16-bit weights-க்கு 2, gradients-க்கு 2, 32-bit optimiser states-க்கு 12 (weights-ஓட ஒரு master copy, ரெண்டு running averages). ஒரு 70B model-க்கு அது activations-க்கு முன்னாடியே சுமார் 1,120 GB. **Sharded data parallelism** (DeepSpeed-ல ZeRO, PyTorch-ல FSDP) இந்த states-ஐ copy பண்ணாம data-parallel GPUs முழுக்க பரப்பும். பெரிய training runs இதை tensor, pipeline parallelism கூட சேர்த்து use பண்ணும். Fine-tuning-க்கு, LoRA-உம் quantisation-உம் பொதுவா இதுல பெரும்பாலானதுக்கான தேவையையே நீக்கிடும்.

### Engine உங்களுக்காக என்ன பண்ணுது

vLLM-ல, ஒரு model-ஐ 4 GPUs முழுக்க பிரிக்கிறது ஒரே ஒரு setting தான்:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 NVLink-connected GPUs in this server.
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)
```

ஒரு server-க்கு ரொம்ப பெரிய model-க்கு, vLLM guide-ஓட rule of thumb: tensor-parallel size ஒரு server-ல இருக்குற GPUs எண்ணிக்கைக்கு சமம், pipeline-parallel size servers எண்ணிக்கைக்கு சமம். 8 GPUs-ஓட ரெண்டு servers-னா `--tensor-parallel-size 8 --pipeline-parallel-size 2`. Servers முழுக்க vLLM default-ஆ Ray use பண்ணும் (ஒரு Ray cluster-ஐ start பண்ணி, அப்புறம் ஒரு server-ல ஒரு `vllm serve` ஓட்டுங்க); ஒரு multiprocessing launcher இன்னொரு option.

| Approach | எதை பிரிக்குது | தேவையான link | எதுக்கு best | முக்கிய cost |
| --- | --- | --- | --- | --- |
| Replicas (data parallelism) | எதுவும் இல்ல; முழு copies | எதுவானாலும் | அதிக users, failover | ஒவ்வொரு copy-உம் பொருந்தணும் |
| Tensor parallelism | ஒவ்வொரு layer-க்குள்ள இருக்குற matrices | NVLink, ஒரு server-க்குள்ள | ரொம்ப பெரிய models, ஒரு token-க்கு குறைவான நேரம் | ஒவ்வொரு token-க்கும் ஒரு layer-க்கு ரெண்டு exchanges |
| Pipeline parallelism | Layers-ஓட groups | நல்ல network போதும் | Servers முழுக்க பரவ; training | Latency லாபம் இல்ல; bubbles |
| Expert parallelism | ஒரு MoE model-ஓட experts | வேகமானது; tokens experts-கிட்ட போகும் | பெரிய MoE models | Experts முழுக்க சமமில்லாத load |
| Context அல்லது sequence parallelism | Input sequence | வேகமானது | ரொம்ப நீளமான inputs | Complexity |
| Sharded data parallelism | Gradients, optimiser states | பெரிய models-க்கு வேகமானது | பெரிய models-ஐ train பண்ண | கூடுதல் communication |

**உங்க browser-லயே try பண்ணுங்க.** ஒரு model-க்கும் traffic-க்கும் valid-ஆன மிகச் சின்ன tensor-parallel size-ஐ கண்டுபிடிங்க. Numbers-ஐ மாத்திப் பாருங்க.

```python
def kv_cache_gb(layers, kv_heads, head_dim, tokens, bytes_per=2):
    # 2 = one key and one value per token, per layer, per key-value head
    return 2 * layers * kv_heads * head_dim * bytes_per * tokens / 1e9

def smallest_tp(params_billion, bytes_per_param, cache_gb, gpu_gb, heads, usable=0.9):
    need = params_billion * bytes_per_param + cache_gb
    for tp in (1, 2, 4, 8):                      # sizes that fit in one 8-GPU server
        if heads % tp == 0 and tp * gpu_gb * usable >= need:
            return need, tp
    return need, None                            # needs pipeline across servers

# A 70B model: 80 layers, 64 heads, 8 key-value heads of size 128
cache = kv_cache_gb(80, 8, 128, tokens=60 * 4000)    # 60 requests x 4,000 tokens
for bpp, label in [(2, "16-bit"), (1, "8-bit")]:
    need, tp = smallest_tp(70, bpp, cache, gpu_gb=80, heads=64)
    print(f"{label}: {need:.0f} GB needed -> tensor-parallel size {tp}")
```

இது 16-bit-ல சுமார் 219 GB, size 4-ன்னும், 8-bit-ல சுமார் 149 GB, size 4-ன்னும் print பண்ணும். 8-bit model 2 GPUs-ல பொருந்தும், ஆனா ஒவ்வொரு copy-உம் குறைவான requests-ஐ serve பண்ணா மட்டும் தான்: 4,000 tokens-ல சுமார் 56. Engine தானே use பண்ற ஒரு GPU-க்கு சில GB-ஐ இந்த script கணக்குல எடுக்கல, அதனால ஒரு margin வைங்க.

## ஒரு worked example

Hyderabad-ல ஒரு insurer, 2,000 staff-க்கு ஒரு 70B open model-ஐ (80 layers, 64 attention heads, size 128 உள்ள 8 key-value heads) self-host பண்ணணும்னு நினைக்குறாங்க, p95 first-token time 2 seconds-க்கு கீழ இருக்கணும். ஒவ்வொரு server-லயும் NVLink-ஆல இணைச்ச 80 GB-ஓட 8 GPUs இருக்கு. கீழ இருக்குற traffic figures அவங்களோட planning estimates, measurements இல்ல.

1. **Busy hour load.** Busy hour-ல 600 staff active-ஆ இருக்காங்க, ஒவ்வொருத்தரும் 2 minutes-க்கு ஒரு request அனுப்புறாங்கன்னு வச்சுக்குங்க: ஒரு second-க்கு 5 requests. ஒவ்வொண்ணும் streaming முடிய சுமார் 12 seconds ஆகும். Requests in flight = arrivals × ஒவ்வொண்ணோட நேரம் = 5 × 12 = **60**. ஒவ்வொண்ணும் சுமார் 4,000 tokens வச்சிருக்கும் (instructions, policy text, chat history, reply).
2. **KV cache.** 2 × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes, ஒரு token-க்கு சுமார் 0.33 MB. 60 × 4,000 tokens × 0.33 MB ≈ **79 GB**.
3. **ஒரு GPU-ல பொருந்துமா?** 16-bit-ல weights மட்டுமே சுமார் 140 GB; ஒரு GPU-ல use பண்ணக்கூடியது 72 GB. பொருந்தாது.
4. **Valid-ஆன மிகச் சின்ன split.** ரெண்டு GPUs-ல use பண்ணக்கூடியது 144 GB: weights-க்கு அரிதா போதும், cache-க்கு இடம் இல்ல. மூணுல 216 GB, தேவையான 219 GB-க்கு கொஞ்சம் குறைவு, எப்படியும் 64 heads-ஐ வகுக்காது. நாலுல 288 GB: 140 GB weights போக சுமார் **148 GB** cache, 4,000 tokens-ஓட சுமார் 112 requests-க்கு இடம். Tensor-parallel size 4.
5. **Capacity, failover.** ஒரு copy busy hour-ஐ தாங்கும், ஆனா ஒரே ஒரு fault service-ஐ நிறுத்திடும். 4 GPUs-ஓட ரெண்டு copies ஒரு server-ஐ நிரப்பும்; முழு server-உம் fail ஆனா ஒரு ரெண்டாவது server காப்பாத்தும்.
6. **Cost.** ஒரு GPU-hour-க்கு ₹362-ங்கிற ஒரு example rate-ல (E2E Networks-ஓட H100 page-ல இருக்குற on-demand price, 28 November 2026 அன்னைக்கு check பண்ணது, 18% GST-க்கு முன்னாடி), 730 மணி நேர மாசத்துக்கு ஒரு 8-GPU server-க்கு 8 × 362 × 730 ≈ **₹21.1 lakh** ஆகும், GST-ஓட சுமார் ₹24.9 lakh. Provider, plan-ஐ பொறுத்து prices மாறும், அதனால quotes வாங்குங்க. 22 நாளுக்கு, ஒரு working day-க்கு ஒருத்தருக்கு 40 requests-னா, அது மாசத்துக்கு சுமார் 7 billion tokens, அதாவது ஒரு million tokens-க்கு சுமார் ₹300. இதை விட குறைவான விலையுள்ள hosted API மலிவு, data அவங்க சொந்த servers-லயே இருக்கணும்னா தவிர. ராத்திரில ஒரு copy மட்டும் ஓட்டுனாலும் பணம் மிச்சம்.

## பொதுவான தப்புகள்

- **ஒரு GPU-ல பொருந்துற model-ஐ பிரிக்கிறது.** Replicas simple, வேகமான links தேவையில்ல, failures-ஐயும் தாங்கும்.
- **Weights-ஐ மட்டும் வச்சு size பண்றது.** Busy hour-க்கான KV cache weights அளவுக்கே பெருசா இருக்கலாம்.
- **PCIe அல்லது network-ல tensor parallelism.** அது ஒரு layer-க்கு ரெண்டு தடவை பேசும்; ஒரு server-க்குள்ள NVLink-லயே வைங்க.
- **Head count-ஐ வகுக்காத tensor-parallel size.** Engine start ஆக மறுக்கும்; 2, 4 அல்லது 8 use பண்ணுங்க.
- **Pipeline parallelism latency-ஐ குறைக்கும்னு எதிர்பார்க்குறது.** அது servers முழுக்க பரவ உதவும்; ஒரு request-ஐ ஒருபோதும் வேகமாக்காது.
- **Mixture-of-experts model-ஐ active parameters வச்சு size பண்றது.** எல்லா experts-உம் memory-ல இருக்கணும்.
- **Key-value heads எண்ணிக்கையை தாண்டி பிரிக்கிறது.** ஒரு GPU-க்கான cache சுருங்குறது நின்னுடும்.
- **ஒரே ஒரு copy.** ஒரு GPU fault service-ஐயே நிறுத்திடும்.
- **Average traffic-ஐ வச்சு size பண்றது.** Busy hour-க்கு size பண்ணுங்க, உண்மையான prompt lengths-ல load tests பண்ணுங்க.

## இது எதுவுமே தேவையில்லாத நேரம்

- **Hosted APIs**: provider அதை பாத்துக்குவாங்க. முதல்ல அவங்களோட ஒரு million tokens price-ஐ உங்க GPU cost கூட compare பண்ணுங்க.
- Cache-க்கு இடத்தோட ஒரு GPU-ல பொருந்துற **சின்ன models**: தேவைப்படும்போது replicas சேர்த்தா போதும்.
- **LoRA, quantisation-ஓட fine-tuning**, இது பெரும்பாலும் ஒரே GPU-ல பொருந்திடும்.

## Demo-ல இருந்து production-க்கு

- GPUs வாங்கறதுக்கு அல்லது rent பண்றதுக்கு முன்னாடி **ஒரு copy-க்கான memory-ஐ measure பண்ணுங்க** (உங்க context length, concurrency-ல weights-உம் KV cache-உம்).
- **Links-ஐ check பண்ணுங்க**: tensor parallelism plan பண்றதுக்கு முன்னாடி instance listing-ல "SXM", "NVLink" இருக்குன்னு confirm பண்ணுங்க.
- உண்மையான prompt, reply lengths-ஓட **ஒவ்வொரு layout-ஐயும் load-test பண்ணுங்க**, average இல்ல, p95-ஐ பாருங்க.
- மக்கள் நம்பி இருக்குற எந்த service-க்கும், ஒண்ணுக்கு மேற்பட்ட servers-ல **குறைஞ்சது ரெண்டு copies வைங்க**.
- **ஒவ்வொரு replica-வையும் monitor பண்ணுங்க**: queue length, KV cache use, latency, errors. Queue வளரும்போது copies சேருங்க.
- **Working day-க்கு ஏத்த மாதிரி scale பண்ணுங்க**: traffic குறைஞ்சா ராத்திரில குறைவான copies.
- **Model மாறினதுக்கு அப்புறம் re-plan பண்ணுங்க**, ஏன்னா size, head counts, context length எல்லாம் layout-ஐ மாத்தும்.
