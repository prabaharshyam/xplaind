## இது என்ன

ஒரு GPU-க்கு ஒரு நிலையான அளவு memory-யும் speed-உம் தான். ரெண்டு வெவ்வேறு பிரச்சனைகள் உங்களை பலதை use பண்ண தள்ளும்:

1. **Model ஒரு GPU-க்கு ரொம்ப பெரிசு.** 16-bit precision-ல ஒரு 70B model-க்கு weights-க்கு மட்டுமே கிட்டத்தட்ட 140 GB வேணும், ஒரு single 80 GB GPU-வை விட அதிகம்.
2. **ஒரு copy உங்க எல்லா users-க்கும் serve பண்ண முடியாது.** Model பொருந்தினாலும், traffic-க்கு பல copies தேவைப்படலாம்.

ரெண்டு அடிப்படை பதில்கள் இருக்கு: model-ஐ **copy** பண்ணுங்க, அல்லது **பிரிங்க**.

- **Replica parallelism** (training-ல **data parallelism**-ன்னு சொல்வாங்க): பல GPUs-ல முழு copies-ஐ ஓட்டுங்க. ஒவ்வொரு copy-உம் வேற வேற requests-ஐ serve பண்ணும், அல்லது வேற வேற batches-ல train ஆகும்.
- **Model parallelism**: ஒரு model-ஐ GPUs முழுக்க பிரிக்கிறது. ரெண்டு முக்கிய வழிகள்: **tensor parallelism** (ஒவ்வொரு layer-க்குள்ளயும் வேலையை பிரிக்கிறது), **pipeline parallelism** (layers-ஐ groups-ஆ பிரிக்கிறது).

உண்மையான systems அடிக்கடி இவற்றை சேர்க்கும்: 4 GPUs-ல பிரிச்ச ஒரு model, அதுமாதிரி பல groups replicas-ஆ.

## இது எப்படி work ஆகுது

**Replicas.** எளிமையான, வலுவான option: ஒவ்வொரு GPU-வும் (அல்லது GPUs-ஓட group-உம்) ஒரு முழு model-ஐ வச்சு தன்னோட requests-ஐ கையாளும். அதிக replicas-னா அதிக throughput, ஒண்ணு fail ஆனா மத்தவை serve பண்ணிட்டே இருக்கும். வேற வேற அளவு models, வேற வேற memory உள்ள GPUs இருக்கும்போது, எதை எங்க வைக்கிறதுன்னு முடிவு பண்றது ஒரு packing புதிர் ஆகும்: ஒரு 40 GB GPU-ல மூணு 13B models, அல்லது ஒரு 34B model?

**Tensor parallelism.** ஒரு layer பெரும்பாலும் matrix multiplication தான். Matrices-ஐ, சொல்லுங்க 4 GPUs-ல பிரிங்க: ஒவ்வொண்ணும் தன்னோட slice-ஐ ஒரே நேரத்துல compute பண்ணி, அப்புறம் results-ஐ பரிமாறிக்கும். இது ரொம்ப பெரிய model-ஐ பொருத்தும், வேலை பகிரப்படுறதால latency-யையும் குறைக்கலாம். சிக்கல் communication: GPUs ஒவ்வொரு layer-க்குள்ளயும் பேசிக்குது, அதனால அவைக்கு ரொம்ப வேகமான links வேணும், ஒரு server-க்குள்ள GPUs இடையில இருக்குற high-speed connections மாதிரி. மெதுவான networks முழுக்க, tensor parallelism பொதுவா பலன் தராம போகும்.

**Pipeline parallelism.** Layers 1-ல இருந்து 20-ஐ GPU 1-லயும், 21-ல இருந்து 40-ஐ GPU 2-லயும் இப்படியே வைங்க. ஒரு request ஒவ்வொரு stage-வழியாவும் வரிசையா போகும். Batches-ஐ சின்ன "micro-batches"-ஆ பிரிச்சா எல்லா stages-உம் busy-ஆ இருக்கும், இது training throughput-க்கு உதவும். Serving-ல ஒவ்வொரு request-உம் ஒவ்வொரு stage-க்காகவும், அவற்றுக்கு இடையிலான network hops-க்காகவும் காத்திருக்கும்; அதனால latency முக்கியம்னா pipeline parallelism தவிர்க்கப்படும். ஒரு model ஒரு server-க்கு ரொம்ப பெரிசா இருக்கும்போது servers முழுக்க பரவ இது பெரும்பாலும் use ஆகும்.

**நீண்ட inputs.** **Context parallelism** ஒரு ரொம்ப நீண்ட input-ஐ GPUs முழுக்க பிரிக்கும், **sequence parallelism** அதன் மேல நடக்குற operations-ஐ பிரிக்கும். இவை முக்கியமா ரொம்ப நீண்ட context windows-க்கு தேவை.

**Training-க்கு இன்னும் வேணும்.** Weights தவிர, training gradients, optimiser states-ஐ வச்சிருக்கும்; பெரும்பாலும் weights-ஓட பல மடங்கு அளவு. **Sharding**-ஓட data parallelism (ZeRO அல்லது FSDP மாதிரி, அந்த states-ஐ GPUs முழுக்க பரப்புறது) கூட tensor, pipeline parallelism, பெரிய teams-ஐ ரொம்ப பெரிய models-ஐ train பண்ண விடுது. Fine-tuning-க்கு, LoRA-வும் quantisation-உம் பொதுவா இதுல பெரும்பகுதியை தேவையில்லாம ஆக்கிடும்.

Serving engines விவரங்களை பாத்துக்கும். vLLM-ல, ஒரு model-ஐ 4 GPUs-ல பிரிக்கிறது ஒரு setting தான்:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 GPUs in this server (tensor parallelism).
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)

# More users? Run more copies (replicas) on other GPU groups or servers
# behind a load balancer. Spanning servers adds pipeline_parallel_size.
```

| Tensor parallelism | ஒவ்வொரு layer-க்குள்ளயும் வேலை | ரொம்ப பெரிய models, குறைவான latency | GPUs இடையில ரொம்ப வேகமான links வேணும் |
| Pipeline parallelism | Layers-ஓட groups | Servers முழுக்க ரொம்ப பெரிய models; training | ஒவ்வொரு request-க்கும் delay சேக்கும் |
| Context அல்லது sequence parallelism | Input sequence | ரொம்ப நீண்ட contexts | சிக்கலான தன்மை |
| Sharded data parallelism (training) | Gradients, optimiser states | பெரிய models-ஐ train பண்றது | Communication overhead |

**Browser-ல try பண்ணுங்க.** ஒரு model-க்கு எத்தனை GPUs வேணும்? Size, precision, GPU memory-ஐ மாத்தி பாருங்க.

```python
import math

def gpus_needed(params_billion, bytes_per_param, gpu_gb, kv_cache_gb, headroom=0.9):
    need = params_billion * bytes_per_param + kv_cache_gb
    return need, math.ceil(need / (gpu_gb * headroom))

for params, bpp in [(8, 2), (70, 2), (70, 1)]:
    need, n = gpus_needed(params, bpp, gpu_gb=80, kv_cache_gb=20)
    print(f"{params}B at {bpp} bytes: {need:.0f} GB -> {n} GPU(s) of 80 GB")
```

## ஒரு worked example

Hyderabad-ல ஒரு insurer, 2,000 staff-க்கு p95 first-token time 2 வினாடிக்கு கீழ இருக்குற மாதிரி ஒரு 70B open model-ஐ self-host பண்ண விரும்புது. ஒவ்வொரு server-லயும் ஒவ்வொண்ணும் 80 GB உள்ள 8 GPUs, server-க்குள்ள வேகமான links.

1. **ஒரு GPU-ல பொருந்துமா?** 70 billion × 2 bytes ≈ 16-bit-ல 140 GB. இல்ல.
2. **ஒரு server-க்குள்ளயா?** ஆமா. 4 GPUs முழுக்க tensor parallelism 320 GB தரும்; பல concurrent chats-ஓட KV cache-க்கு நிறைய இடம் மிச்சம். 8-bit precision-ல, அவங்க test set-ல quality உறுதியானா 2 GPUs போதும்.
3. **அதிக users.** ஒவ்வொரு server-உம் ரெண்டு copies-ஐ வச்சிருக்கு (4 GPUs-ஓட ரெண்டு groups). Load tests, ஒரு copy அவங்க busy-hour traffic-ஐ latency budget-குள்ள வசதியா கையாளுதுன்னு காட்டுது; அதனால ஒரு server-ல ரெண்டு copies headroom தந்து, ஒரு GPU failure-ஐயும் தாங்கும்.

| Set-up | பயன்படுத்தின GPUs | Busy-hour p95 first token | குறிப்புகள் |
| --- | --- | --- | --- |
| Tensor 4, ஒரு copy | 4 | 1.4 s | ஒரு GPU fail ஆனா spare இல்ல |
| Tensor 4, ரெண்டு copies | 8 | 0.9 s | தேர்ந்தெடுத்தது: headroom, failover |
| Tensor 2 at 8-bit, நாலு copies | 8 | 0.8 s | Quantise பண்ணதுக்கு அப்புறம் quality check வேணும் |
| ரெண்டு servers முழுக்க pipeline | 16 | 2.6 s | மெதுவா, செலவானது; தேவையில்ல |

இந்த numbers உதாரணத்துக்கு தான். 8-bit option-ஐயும் test பண்ணவும் திட்டமிடுறாங்க; quality நிலைச்சா அதே hardware-ல capacity-ஐ ரெண்டு மடங்கு ஆக்கலாம்.

## பொதுவா பண்ற தப்புகள்

- **ஒரு GPU-ல பொருந்துற model-ஐ பிரிக்கிறது.** Replicas எளிமையானது, பொதுவா வேகமானது.
- **மெதுவான networks முழுக்க tensor parallelism.** அதை வேகமான links உள்ள ஒரு server-க்குள்ளயே வைங்க.
- **ஒரு model பொருந்துதான்னு பாக்கும்போது KV cache-ஐ மறக்குறது.**
- **Chat serving-க்கு pipeline parallelism.** அது ஒவ்வொரு request-க்கும் delay சேக்கும்.
- **Headroom இல்லாம இருக்குறது.** ஒரு copy-க்கு failover இல்ல; ஒரு GPU fault service-ஐ கீழ இறக்கிடும்.
- **Average traffic-ல இருந்து size பண்றது.** Busy hour-க்கு size பண்ணுங்க, உண்மையான prompt lengths-ல load tests-ஓட.
