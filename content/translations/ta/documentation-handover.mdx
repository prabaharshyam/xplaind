## இது என்ன

**Handover**-னா ஒரு system-ஐ அதை சொந்தமா வச்சுக்கப்போற ஆட்கள்கிட்ட திட்டமிட்டு ஒப்படைக்கிறது. இதுக்கு மூணு பகுதிகள்:

- ஒவ்வொரு audience-க்கும் **Documentation**: users, operators, developers, owners.
- **Knowledge transfer**: training, pairing, நீங்க இன்னும் கிடைக்குற நேரத்துல client-ஓட team system-ஐ நடத்துற ஒரு period.
- **Formal close**: handover முடிஞ்சதுக்கு ஒத்துக்கிட்ட criteria, access நீக்கம், தேவைப்பட்டா ஒரு support ஏற்பாடு.

AI systems-க்கு கூடுதல் handover material வேணும், ஏன்னா அவற்றோட behaviour code-ஐ மட்டும் இல்ல, prompts, models, data, evals-ஐயும் சார்ந்தது.

```flow
dir: LR
title: நாலு வாரத்துல handover
வாரம் 1: shadow | அவங்க நீங்க operate பண்றதை பார்த்து docs படிக்கிறாங்க -> வாரம் 2: reverse shadow | அவங்க ஒரு prompt-ஐ மாத்தி simulated incident-ஐ handle பண்றாங்க; நீங்க பார்க்கறீங்க
வாரம் 2: reverse shadow -> வாரம் 3: தனியா run | அவங்க KPI report, cost review-ஐ நடத்துறாங்க
வாரம் 3: தனியா run -> வாரம் 4: close | checklist sign-off, உங்க access நீக்கம், secrets rotate, support terms
```

| வாசகர் | Documents |

| Operators | Runbooks |
| Developers | How-tos, architecture |
| Owners | KPIs, costs, risks |
| எல்லாருக்கும் | Decision records |

சென்னையில ஒரு lender-ஓட credit-file assistant-ஐ handover பண்றதை இந்த lesson பின்தொடருது.

## இது எப்படி work ஆகுது

**ஒவ்வொரு வாசகருக்கும் எழுதுங்க.** (Diátaxis framework-ல இருந்து) ஒரு நல்ல பிரிவு: கத்துக்க tutorials, tasks-க்கு how-to guides, facts-க்கு reference, காரணங்களுக்கு explanations.

- *Users*: system-ஐ நல்லா use பண்றதுக்கான ஒரு சின்ன guide, அது எதுல நல்லது எதுல மோசம், outputs-ஐ எப்படி check பண்றது, feedback எப்படி தர்றது.
- *Operators*: routine tasks, தெரிஞ்ச incidents-க்கு **runbooks**, உதாரணமா "model provider errors தருது", "answers பழைய documents-ஐ reference பண்ணுது", "costs எகிறுது", "connector நின்னுடுச்சு". ஒவ்வொரு runbook-லயும்: symptoms, checks, fix, escalation.
- *Developers*: architecture overview, locally எப்படி run பண்றது, எப்படி deploy பண்றது, ஒரு prompt-ஐ பாதுகாப்பா எப்படி மாத்துறது, configuration எங்க இருக்கு.
- *Owners*: system என்ன பண்ணுது, அதோட KPI, இப்போதைய numbers, risks, costs, எடுத்த decisions, காரணங்களோட.

**AI-specific essentials.** Golden sets, evals-ஐ எப்படி run பண்றது; use-ல இருக்குற prompt, model versions, அவற்றை எப்படி மாத்துறது; data pipeline, எப்படி re-index பண்றது; guardrails, அவற்றோட test sets; audit log schema; cost dashboard; examples-ஓட தெரிஞ்ச failure modes.

**Decision records.** முக்கிய choices பத்தின சின்ன notes: என்ன முடிவு பண்ணாங்க, alternatives, ஏன். அடுத்த team நல்ல decisions-ஐ உடைக்காம, மோசமான experiments-ஐ திரும்ப பண்ணாம இருக்க இவை உதவும்.

**Shadow, அப்புறம் reverse shadow.** முதல்ல client-ஓட engineers நீங்க system-ஐ operate பண்ணி மாத்துறதை பார்க்கறாங்க. அப்புறம் நீங்க பார்த்துக்கிட்டிருக்கும்போது அவங்க பண்றாங்க: ஒரு deploy, evals-ஓட CI வழியா ஒரு prompt change, ஒரு runbook-ல இருந்து simulated incident. ஒவ்வொரு core task-ஐயும் அவங்களே பண்ணி முடிச்சப்போ தான் handover முழுமை.

**Clean exit.** உங்க access-ஐ நீக்குங்க, shared secrets-ஐ rotate பண்ணுங்க, accounts, billing-ஐ transfer பண்ணுங்க, support terms-ஐ உறுதி பண்ணுங்க.

**ஒரு runbook page:**

| Section | Example: "answers பழைய documents-ஐ cite பண்ணுது" |
| --- | --- |
| Symptoms | Users பழைய rates-ஐ report பண்றாங்க; refusal rate normal; feedback-ல dates பத்தி வருது |
| Checks | Index freshness dashboard; கடைசி pipeline run; effective-date filter setting |
| Fix | பாதிக்கப்பட்ட source-க்கு indexing job-ஐ திரும்ப run பண்ணுங்க; superseded flags-ஐ உறுதி பண்ணுங்க |
| Verify | தற்போதைய rates பத்தி golden set-ல இருந்து மூணு test questions கேளுங்க |
| Escalate | Source connector ரெண்டு தடவை fail ஆனா, platform team lead-ஐ தொடர்பு கொள்ளுங்க |

**Handover checklist.** Sign-off-க்கு முன்னாடி, ஒவ்வொரு item-ஐயும் அதை பண்ண client engineer-ஓட பேரோட tick பண்ணுங்க: ஒரு release-ஐ deploy பண்ணது; ஒண்ணை rollback பண்ணது; evals-ஓட CI வழியா ஒரு prompt-ஐ மாத்தினது; ஒரு source-ஐ re-index பண்ணது; runbooks-ல இருந்து ரெண்டு simulated incidents-ஐ handle பண்ணது; மாசாந்திர KPI, cost report-ஐ உருவாக்கினது; ஒரு secret-ஐ rotate பண்ணது. கொடுத்த documents, நீக்கின accounts-ஐயும் சேருங்க. Client-ஓட team sign பண்ண checklist, engagement-ஓட முடிவை தெளிவாக்கி, என்ன handover ஆச்சுன்னு தகராறு வராம தடுக்கும்.

**அங்க இல்லாதவங்களுக்கு எழுதுறது.** வாசகர் ஒரு வருஷம் கழிச்சு சேர்றவரு, உங்க team-ஐ பார்த்ததே இல்லன்னு வச்சுக்கோங்க. விஷயங்கள் ஏன் இப்படி இருக்குன்னு விளக்குங்க, decision records-க்கு link பண்ணுங்க, examples உண்மையானதா வச்சிருங்க. Project-க்கு வெளியே இருக்குற ஒருத்தர் ஒவ்வொரு how-to guide-ஐயும் உதவி இல்லாம follow பண்ணி பாக்கட்டும்; அவங்க சிக்குற ஒவ்வொரு இடத்தையும் fix பண்ணுங்க.

## ஒரு worked example

சென்னை lender-ஓட credit-file assistant-ஓட handover நாலு வாரம் எடுக்குது.

வாரம் 1: Lender-ஓட ரெண்டு engineers, Karthik-உம் Divya-உம், தினசரி operations-ல உங்களோட pair பண்ணி developer docs-ஐ படிச்சு 23 கேள்விகள் கேக்குறாங்க; அவை doc fixes-ஆ மாறுது.

வாரம் 2: புது regional format-க்காக Divya summary prompt-ஐ மாத்துறாங்க. CI-ல eval suite-ஐ run பண்ணி, golden set-ல 1.5-point drop-ஐ பார்த்து, ஒரு instruction-ஐ fix பண்ணி merge பண்றாங்க. Karthik ஒரு simulated incident-ஐ ("document store-க்கான connector நின்னுடுச்சு") runbook வச்சு 25 நிமிஷத்துல handle பண்றாரு.

வாரம் 3: மாசாந்திர KPI report-ஐயும் cost review-ஐயும் அவங்களே நடத்துறாங்க; operations team-ஓட champion உங்க user guide-ஐ வச்சு புது officers-க்கு ஒரு training session நடத்துறாரு.

வாரம் 4: Handover checklist-ஓட sign-off, உங்க accounts நீக்கம், நீங்க use பண்ண gateway keys rotate, escalations-க்கு மட்டும் மூணு மாச support agreement.

ஆறு மாசம் கழிச்சு, evals pass ஆனதுக்கு அப்புறம் Karthik உங்களை கூப்பிடாமலே gateway-க்கு பின்னாடி இருக்குற model-ஐ upgrade பண்றாரு. அது தான் ஒரு வெற்றிகரமான handover.

| வாரம் | Transfer ஆனதுக்கான ஆதாரம் |
| --- | --- |
| 1 | Client engineers-ஓட 23 கேள்விகள் doc fixes-ஆ மாறுச்சு |
| 2 | Divya-ஓட prompt change CI-ல 1.5-point drop-ஐ பிடிச்சு fix ஆச்சு; Karthik simulated connector incident-ஐ 25 நிமிஷத்துல தீர்த்தாரு |
| 3 | Client team KPI, cost reviews-ஐ நடத்துச்சு; அவங்க champion officer training நடத்துனாரு |
| 4 | Checklist sign ஆச்சு; accounts நீக்கம்; gateway keys rotate; மூணு மாச escalation support |

## பொதுவா பண்ற தப்புகள்

- **ஒரே பெரிய document.** வேற வேற வாசகர்களுக்கு வேற வேற documents வேணும்.
- **Runbooks இல்லாதது.** Operators தங்க முதல் incident-லயே system-ஐ கத்துக்குவாங்க.
- **Evals-ஐ விட்டுடுறது.** Golden sets, eval scripts இல்லாம client prompts, models-ஐ பாதுகாப்பா மாத்த முடியாது.
- **கடைசி வாரத்துல handover.** Pilot-லயே ஆரம்பிங்க; அதுக்கு time, practice வேணும்.
- **Access-ஐ மறக்கிறது.** உங்க keys, accounts நீக்கப்படணும், secrets rotate ஆகணும்.

## Practice பண்ணுங்க

இன்னும் படிக்கலன்னா Diátaxis overview-ஐயும், Google technical writing-ஓட முதல் unit-ஐயும் படிங்க.

1. நீங்க build பண்ண ஒரு system-க்கு, ஒரு பக்க architecture overview, ஒரு prompt-ஐ பாதுகாப்பா மாத்துறதுக்கான how-to guide, சாத்தியமான incidents-க்கு ரெண்டு runbooks எழுதுங்க.
2. நீங்க எடுத்த ரெண்டு choices-க்கு, alternatives, காரணங்களோட ரெண்டு decision records எழுதுங்க.
3. ஒரு friend உங்க how-to guide-ஐயும் ஒரு runbook-ஐயும் உங்க உதவி இல்லாம follow பண்ணட்டும்; அவங்க கேக்குற ஒவ்வொரு கேள்வியையும் குறிச்சுக்கிட்டு docs-ஐ fix பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** வேற ஒருத்தர் உங்க documents-ஐ மட்டும் வச்சு ஒரு prompt-ஐ மாத்தி, evals-ஐ run பண்ணி, deploy பண்றதை நீங்க பார்த்துக்கிட்டிருக்க முடியும்.
