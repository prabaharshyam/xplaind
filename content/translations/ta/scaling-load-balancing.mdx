## இது என்ன

**Scaling**-னா ஒரு system அதிக வேலையை எப்படி handle பண்ணுதுங்கறது. ரெண்டு வழிகள் இருக்கு.

**Vertical scaling** (scaling up) ஒரு machine-ஐ பெரிசாக்கும்: அதிக CPU cores, அதிக memory, வேகமான disks. Code மாத்த வேண்டாம், அதனால தான் இது பெரும்பாலும் first step. ஆனா ஒரு machine எவ்வளவு பெரிசாகலாம்னு ஒரு உச்சவரம்பு இருக்கு, உச்சத்துக்கு கிட்ட விலை வேகமா ஏறும். அந்த ஒரு machine fail ஆனா எல்லாமே நின்னுடும்.

**Horizontal scaling** (scaling out) வேலையை பகிர்ந்துக்குற இன்னும் நிறைய machines-ஐ சேர்க்கும். ரொம்ப தூரம் வளர முடியும், எந்த ஒரு machine போனாலும் தாக்குப்பிடிக்கும். ரெண்டு விஷயம் தேவை: requests-ஐ பிரிக்க முன்னாடி ஒரு **load balancer**, அப்புறம் **stateless**-ஆ இருக்குற app servers. அப்போ எந்த server-ம் எந்த request-ஐயும் handle பண்ணலாம்.

```flow
title: Vertical: ஒரே பெரிய server, உச்சவரம்பும் single point of failure-உம் உண்டு
Users -> ஒரே பெரிய server | அதிக CPU, அதிக RAM
```

```flow
title: Horizontal: Load balancer-க்கு பின்னாடி stateless app servers
Users -> Load balancer | health checks
Load balancer -> app1
Load balancer -> app2
Load balancer -> app3
app1 -> Shared state | database, Redis
app2 -> Shared state
app3 -> Shared state
```

## இது எப்படி work ஆகுது

**Statelessness.** App server 1 ஒரு user-ஓட shopping cart-ஐ தன்னோட memory-ல வச்சிருந்தா, அந்த user-ஓட அடுத்த request கண்டிப்பா server 1-க்கே திரும்பி போகணும். இது users-ஐ servers-ஓட கட்டி போடும், server restart ஆனா carts போயிடும். அதுக்கு பதிலா shared state-ஐ app servers-க்கு வெளியே வைங்க. Carts, sessions-ஐ Redis அல்லது database-ல, files-ஐ object storage-ல வைங்க. Identity-ஐ client ஒவ்வொரு முறையும் அனுப்புற JWT மாதிரி signed token-ல கொண்டு போங்க. அப்போ servers ஒண்ணுக்கொண்ணு மாத்திக்கக்கூடியதா ஆகும்.

**Load balancers** வர்ற எல்லா traffic-ஐயும் வாங்கி, ஒவ்வொரு request-ஐயும் ஒரு healthy server-க்கு forward பண்ணும். பொதுவான rules:

| Rule | எப்படி தேர்ந்தெடுக்கும் | எப்போ நல்லது |
|---|---|---|
| Round robin | வரிசைப்படி அடுத்த server | Servers ஒரே மாதிரி, requests-உம் கிட்டத்தட்ட ஒரே மாதிரி இருக்கும்போது |
| Least connections | குறைவான open requests இருக்குற server | சில requests மெதுவா இருக்கும்போது, file uploads மாதிரி |
| Weighted | பெரிய servers-க்கு அதிக traffic | Servers-ஓட size வேறுபடும்போது |
| User அல்லது IP-ஓட hash | ஒரே user எப்பவும் ஒரே server-க்கு | Cache locality வேணும்போது. State-க்கு ஊன்றுகோலா use பண்ணாதீங்க |

Load balancers **health checks** அனுப்பும். உதாரணம்: ஒவ்வொரு சில வினாடிக்கும் `/health`-க்கு ஒரு request. Fail ஆகுற server recover ஆகுற வரை rotation-ல இருந்து எடுக்கப்படும். அதனால ஒரு crash outage ஆகாது. **Layer 4** balancer network address, port வச்சு route பண்ணும், ரொம்ப வேகமானது. **Layer 7** balancer HTTP-ஐ புரிஞ்சுக்கும். அதனால `/api`, `/images`-ஐ வேற வேற services-க்கு route பண்ணலாம், HTTPS-ஐயும் handle பண்ணலாம். Cloud-ல பெரும்பாலும் AWS Application Load Balancer, Google Cloud Load Balancing மாதிரி managed balancer-ஐ use பண்ணுவீங்க. nginx, HAProxy நாமே ஓட்டுற popular options.

**Autoscaling** CPU 60%-க்கு மேல அல்லது requests per second மாதிரி ஒரு metric அதிகமா இருக்கும்போது servers-ஐ சேர்க்கும், அது குறைஞ்சா நீக்கும். அமைதியான நாட்கள்ல பணம் மிச்சப்படுத்தும், busy நாட்கள்ல உங்களை காப்பாத்தும். ஆனா புது servers start ஆக ஒரு நிமிஷம் ரெண்டு நிமிஷம் ஆகும். அதனால நள்ளிரவு sale மாதிரி முன்னாடியே தெரிஞ்ச spikes-க்கு, முன்னாடியே scale up பண்ணுங்க.

App servers-ஐ scale பண்ணா, அழுத்தம் அவை பகிர்ந்துக்கறதுக்கு போயிடும்னு ஞாபகம் வச்சுக்கோங்க. ஒரே database-ஐ பத்து app servers அடிச்சா அது தாங்காது. அடுத்த lessons-ல caches, replicas, sharding அதுக்கு எப்படின்னு பார்ப்போம்.

**Interviews-ல**, scaling கேள்விகள் பெரும்பாலும் "traffic பத்து மடங்கு ஆனா என்ன ஆகும்?"ன்னு வரும். நல்ல பதில் முதல்ல bottleneck-ஐ சொல்லும், அப்புறம் fix: load balancer-க்கு பின்னாடி stateless app servers, headroom-ஓட autoscaling, அப்புறம் database, cache மாதிரி shared tiers. Health checks-ஐயும், ஒரு server செத்தா என்ன நடக்கும்னும் சொல்லுங்க. நீங்க growth மட்டும் இல்லாம failure-ஐ பத்தியும் யோசிக்கிறீங்கன்னு அது காட்டும்.

**Browser-லயே try பண்ணுங்க.** சில requests மெதுவா இருக்கும்போது round robin-ஐயும் least connections-ஐயும் compare பண்ணுங்க.

```python
import random

def simulate(policy, servers=3, n=3000, seed=4):
    rng = random.Random(seed)
    busy = [0.0] * servers
    worst, rr = 0.0, 0
    for _ in range(n):
        busy = [max(0.0, b - 1.0) for b in busy]                  # each tick, servers finish some work
        i = rr % servers if policy == "round robin" else busy.index(min(busy))
        rr += 1
        busy[i] += rng.choice([0.5] * 9 + [12.0])                 # 1 in 10 requests is slow
        worst = max(worst, busy[i])
    return worst

for p in ("round robin", "least connections"):
    print(f"{p:<18} worst queue: {simulate(p):.1f}")
```

## ஒரு நாள், ஒரு example

விக்ரம் ஒரு cricket fantasy app-ஓட engineering-ஐ பார்த்துக்கறார். சாதாரண நாட்கள்ல traffic நிலையா இருக்கும். ஆனா ஒரு IPL match lock ஆகுறதுக்கு முன்னாடி கடைசி பத்து நிமிஷத்துல users teams-ஐ edit பண்ண ஓடுவாங்க, traffic கிட்டத்தட்ட இருபது மடங்கு எகிறும்.

App ஒரு பெரிய server-ல ஆரம்பிச்சது, ஒவ்வொரு season-லயும் vertical-ஆ scale பண்ணாங்க. ஒரு final-ல CPU 100%-க்கு போய், requests queue ஆகி, நிறைய users teams-ஐ save பண்ணவே முடியலை. இன்னும் பெரிய server option-ஓட cost ரெண்டு மடங்கு, அப்பவும் போதாது.

அவர் team மூணு steps-ல horizontal scaling-க்கு மாறுச்சு:

1. **App-ஐ stateless ஆக்குனாங்க.** Sessions server memory-ல இருந்து Redis-க்கு போச்சு, upload பண்ண profile photos object storage-க்கு போச்சு. இப்போ எந்த server-ம் எந்த user-க்கும் service பண்ணலாம்.
2. **முன்னாடி ஒரு managed layer 7 load balancer வச்சாங்க.** அதுக்கு `/health` endpoint, app Redis-ஐயும் database-ஐயும் reach பண்ண முடியுதான்னு check பண்ணும். Check-ல fail ஆகுற servers தானா விலகிடும்.
3. **Requests per second மேல autoscaling set பண்ணாங்க.** கூடவே ஒவ்வொரு match lock-க்கும் 30 நிமிஷம் முன்னாடி servers-ஐ சேர்க்கற scheduled rule-உம் வச்சாங்க. ஏன்னா புது servers ready ஆக கிட்டத்தட்ட 90 seconds ஆச்சு.

அடுத்த final-ல traffic கிட்டத்தட்ட 2,000-ல இருந்து 40,000 requests per second-க்கு உயர்ந்துச்சு. Group 4-ல இருந்து 60 servers-ஆ வளர்ந்து, lock-க்கு அப்புறம் திரும்ப குறைஞ்சது. Peak-ல ரெண்டு servers crash ஆனப்போ, health checks சில நொடிகள்ல அவற்றை நீக்கிடுச்சு, users-க்கு தெரியவே இல்லை.

புது bottleneck database ஆச்சு, ஏன்னா ஒவ்வொரு team edit-ம் அதுக்கு போகுது. அதனால விக்ரம் team ஒரு cache-ஐயும் read replicas-ஐயும் சேர்த்தாங்க. அதுதான் அடுத்த lessons-ஓட subject.

## பொதுவா பண்ற தப்புகள்

**App servers-ல state வச்சிருக்கறது.** In-memory sessions, local file uploads, ரெண்டாவது server சேர்த்ததும் உடைஞ்சுடும். முதல்ல state-ஐ வெளியே மாத்துங்க.

**Sticky sessions-ஐ நம்புறது.** Users-ஐ servers-ஓட pin பண்றது state பிரச்சனையை மறைக்கும், load-ஐயும் சமமில்லாம பிரிக்கும். குறுகிய கால patch-ஆ மட்டும் use பண்ணுங்க.

**Health checks இல்லாம இருக்கறது, அல்லது ஆழமில்லாதவை.** "OK"ன்னு மட்டும் திருப்பி தர்ற check, server தன்னோட database-ஐ reach பண்ண முடியாதப்போவும் pass ஆகலாம். முக்கியமான dependencies-ஐ check பண்ணுங்க, ஆனா checks வேகமா இருக்கணும்.

**ரொம்ப லேட்டா autoscale பண்றது.** Servers start ஆக ரெண்டு நிமிஷம் ஆனா, ஒரு நிமிஷத்துல உச்சம் தொடுற spike உதவி வர்றதுக்குள்ள முடிஞ்சுடும். தெரிஞ்ச events-க்கு முன்னாடியே scale பண்ணுங்க.

**Load balancer-ஏ fail ஆகலாம்னு மறந்துடுறது.** Managed, redundant balancer-ஐ use பண்ணுங்க அல்லது ஒண்ணுக்கு மேல ஓட்டுங்க.

**தப்பான tier-ஐ scale பண்றது.** Database தான் bottleneck-னா app servers-ஐ சேர்த்து பிரயோஜனம் இல்லை. முதல்ல அளந்து பாருங்க.
