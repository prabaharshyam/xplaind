## இது என்ன

Serving-னா உங்க application-ஐ real users நம்பி use பண்ற மாதிரி ஓட்டறது. அது தானா start ஆகும், crash ஆனா restart ஆகும், ஒரே நேரத்துல நிறைய requests-ஐ handle பண்ணும், model மெதுவா இருந்தாலும் சீக்கிரம் ஏதாவது காட்டும்.

ஒரு Python AI service-க்கு வழக்கமான stack: app-க்கு FastAPI, அதை ஓட்டுற server-ஆ **Uvicorn**, parallelism-க்கு பல worker processes. HTTPS-ஐ handle பண்ணவும் traffic-ஐ பிரிக்கவும் முன்னாடி load balancer, ingress அல்லது Cloud Run மாதிரி ஒரு platform இருக்கும்.

AI services-க்கு ரெண்டு special குணங்கள் இருக்கு. Model calls-க்கு காத்திருக்கறதால requests மெதுவா இருக்கும், பெரும்பாலும் 2 முதல் 30 seconds. Users progress பார்த்தா மட்டும் தான் அதை பொறுத்துப்பாங்க. அதனால தான் **streaming** முக்கியம்.

```flow
Users -[HTTPS]-> Load balancer | timeout 30 s, /ready-ஐ check பண்ணும்
Load balancer -> Container 1 | 4 workers, Uvicorn + FastAPI
Load balancer -> Container 2 | 4 workers
Container 1 -> Model API | timeout 25 s, tokens user-க்கு stream ஆகும்
Container 1 -> Background queue | OCR, indexing; ஒரு job id, status
```

இந்த lesson-ல Lucknow-ல ஒரு edtech company-ஓட doubt-solving assistant-ஐ follow பண்ணுவோம். அது ஒவ்வொரு சாயங்காலமும் ரொம்ப மெதுவா ஆயிடுச்சு.

## இது எப்படி work ஆகுது

**Workers, concurrency.** Async endpoints இருக்குற ஒரு Uvicorn process, network-க்கு காத்திருக்குற நிறைய requests-ஐ பிடிச்சு வச்சுக்கும். PDF parse பண்றது, local embedding model ஓட்டறது மாதிரி CPU-heavy வேலை அந்த process-ஐ block பண்ணும். அதனால பல workers ஓட்டுறீங்க, பெரும்பாலும் ஒரு CPU core-க்கு ஒண்ணு அல்லது ரெண்டு. இல்லைன்னா heavy வேலையை background queue-க்கு மாத்துறீங்க.

**எல்லா இடத்துலயும் timeouts.** ஒவ்வொரு model, tool call-லயும், முழு request-லயும், load balancer-லயும் timeout வைங்க. உள்ளதை வெளியில இருக்குறதை விட சின்னதா வைங்க. தொங்க விடாம, தெளிவான 503 அல்லது 504-ஐ திருப்பி கொடுங்க.

**Streaming.** `StreamingResponse`, server-sent events வச்சு, model tokens-ஐ produce பண்ணும்போதே client-க்கு forward பண்ணலாம். Time to first token முழு generation நேரத்துல இருந்து ஒரு second-க்கு ரொம்ப குறைவா வந்துடும். Client disconnect ஆனதை handle பண்ணுங்க. அப்போ யாரும் படிக்காத tokens-க்கு நீங்க பணம் கட்ட வேண்டாம்.

**Health checks.** ஒரு மலிவான `/health` endpoint (process உயிரோட இருக்கு), ஒரு `/ready` endpoint (database மாதிரி dependencies reach ஆகுது) இருந்தா, platform உடைஞ்ச instances-ஐ restart பண்ணலாம், ready ஆனதுக்கு மட்டும் traffic அனுப்பலாம். Health check-ல model-ஐ call பண்ணாதீங்க.

**Graceful shutdown.** Deploy-க்காக platform ஒரு instance-ஐ நிறுத்தும்போது, அது புது requests-ஐ ஏத்துக்காம, ஓடிக்கிட்டிருக்குறதை ஒரு grace period-குள்ள முடிய விடணும். நீண்ட streaming responses-க்கு, உங்க வழக்கமான generation-ஐ விட நீளமான grace period வேணும்.

**Background work.** 500 பக்க PDF-ஐ index பண்றது மாதிரி நிமிஷக்கணக்குல ஆகுற jobs, ஒரு request-குள்ள இருக்கக்கூடாது. Job-ஐ ஏத்துக்கிட்டு, உடனே ஒரு id திருப்பி கொடுத்து, worker queue-ல process பண்ணி, client poll பண்ணவோ webhook பெறவோ விடுங்க.

**ஒரு streaming endpoint:**

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

# Question is your Pydantic request model; model_stream is your async model client.
@app.post("/answer")
async def answer(req: Request, body: Question):
    async def tokens():
        async for text in model_stream(body.text, timeout=25):
            if await req.is_disconnected():
                break                     # stop paying for unread tokens
            yield f"data: {text}\n\n"
    return StreamingResponse(tokens(), media_type="text/event-stream")
```

**முன்னாடி, பின்னாடி அளக்கறது.** ஒவ்வொரு request-க்கும் மூணு numbers record பண்ணுங்க: time to first token, total time, timeout ஆச்சா இல்லையா. Average-ஐ பார்க்காம 95th percentile-ஐ பாருங்க. ஏன்னா users புகார் பண்றது ரொம்ப மெதுவான requests பத்தி தான். Launch-க்கு முன்னாடி, எதிர்பார்க்குற சாயங்கால peak-ல Locust மாதிரி ஒரு tool வச்சு load-test பண்ணுங்க, ஒவ்வொரு மாற்றத்துக்கு அப்புறமும் திரும்பவும்.

**ஒரு real streaming endpoint.** Model-ல இருந்து tokens-ஐ server-sent events-ஆ forward பண்ணுங்க. Timeout, concurrency cap, disconnect handling-ஓட:

```python
import asyncio, json
import anthropic
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=30, max_retries=2)
SLOTS = asyncio.Semaphore(50)                     # at most 50 model calls at once per process

class Question(BaseModel):
    text: str

@app.post("/answer")
async def answer(req: Request, body: Question):
    if SLOTS.locked():
        raise HTTPException(status_code=429, detail="Busy, please retry in a few seconds")
    async def events():
        async with SLOTS:
            try:
                async with client.messages.stream(
                        model="claude-sonnet-5-5", max_tokens=600,         # check the docs for current names
                        messages=[{"role": "user", "content": body.text}]) as stream:
                    async for text in stream.text_stream:
                        if await req.is_disconnected():
                            return                                         # stop paying for unread tokens
                        yield f"data: {json.dumps({'text': text})}\n\n"
                yield "data: [DONE]\n\n"
            except anthropic.APIError:
                yield f"data: {json.dumps({'error': 'The AI service is unavailable. Please try again.'})}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")

@app.get("/health")
async def health():
    return {"ok": True}
```

ஒவ்வொரு chunk-ஐயும் JSON-ஆ encode பண்றதால, text-க்குள்ள இருக்குற newlines event format-ஐ உடைக்காது. `async with`-ஐ விட்டு வெளியே வந்தா stream close ஆகும். User disconnect ஆனா generation நின்னுடும்.

**ஓட்டுறது.** பல worker processes, நீளமான stream-ஐ விட நீளமான graceful timeout:

```bash
gunicorn app.main:app -k uvicorn.workers.UvicornWorker --workers 4 \
  --bind 0.0.0.0:8000 --timeout 120 --graceful-timeout 90
```

**Queue வச்சு background jobs.** நீண்ட வேலை ஒரு worker-க்கு போகும். Request உடனே ஒரு job id-ஐ திருப்பி தரும். Redis Queue-ஓட:

```python
from redis import Redis
from rq import Queue

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents")
async def upload(doc_id: str):
    job = queue.enqueue("workers.index_pdf", doc_id, job_timeout=1800, retry=None)
    return {"job_id": job.id, "status_url": f"/jobs/{job.id}"}

@app.get("/jobs/{job_id}")
async def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    return {"status": job.get_status() if job else "unknown"}
```

Celery, Arq, cloud task queues-உம் இதே pattern-ஐ தான் follow பண்ணும்.

**உண்மையை சொல்ற readiness.** `/ready` ஒரு வேகமான query, சின்ன timeout-ஓட database-ஐயும் vector store-ஐயும் check பண்ணணும். Models அல்லது indexes load ஆகுற வரை start-up நேரத்துல 503 திருப்பணும். அப்போ platform உண்மையிலேயே பதில் சொல்ல முடியுற instances-க்கு மட்டும் traffic அனுப்பும்.

**Browser-லயே try பண்ணுங்க.** Concurrency cap ஏன் முக்கியம்னு பாருங்க: அதை தாண்டின requests காத்திருக்கும். Numbers-ஐ மாத்தி run பண்ணுங்க.

```python
import asyncio, random, time

async def model_call(i, slots):
    async with slots:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model latency
        return i

async def main(cap, n=40):
    slots = asyncio.Semaphore(cap)
    t0 = time.perf_counter()
    await asyncio.gather(*(model_call(i, slots) for i in range(n)))
    print(f"cap {cap:>2}: {n} requests in {time.perf_counter() - t0:.2f} s")

random.seed(0)
for cap in (2, 10, 40):
    await main(cap)
```

## ஒரு நாள், ஒரு example

Lucknow-ல ஒரு edtech-ஓட doubt-solving assistant ஒரு Uvicorn process-ஆ ஓடிச்சு. சாயங்கால படிக்கற நேரத்துல students எந்த text-உம் வர 12 seconds காத்திருந்தாங்க. மூணுல ஒரு பங்கு requests load balancer-ஓட 30-second limit-ல timeout ஆச்சு. கையெழுத்து notes-ஐ OCR-க்கு upload பண்ணா எல்லாருக்கும் server freeze ஆச்சு.

செஞ்ச மாற்றங்கள்:

- பதில்கள் stream ஆகுது: முதல் வார்த்தைகள் கிட்டத்தட்ட 700 milliseconds-ல வருது.
- ஒரு container-க்கு நாலு Uvicorn workers, load balancer-க்கு பின்னாடி ரெண்டு containers.
- Timeouts: model call 25 s, request 28 s, load balancer 30 s. Timeout ஆனா, blank error-க்கு பதிலா "வழக்கத்தை விட நேரம் ஆகுது; திரும்ப try பண்ணுங்க"ன்னு app அனுப்பும்.
- OCR background queue-க்கு போச்சு. Upload ஒரு job id-ஐ திருப்பி தரும். Page "உங்க notes-ஐ படிச்சுக்கிட்டிருக்கு..."ன்னு காட்டி, ready ஆனதும் result-ஐ எடுக்கும்.
- `/ready` database, queue-ஐ check பண்ணும். உடைஞ்ச container 20 seconds-குள்ள traffic வாங்குறதை நிறுத்தும்.

சாயங்கால peak-ல timeouts 33%-ல இருந்து 1%-க்கும் கீழ குறைஞ்சது. பதிலை பார்க்கறதுக்கு முன்னாடியே விட்டுட்டு போன students எண்ணிக்கை மூணுல ரெண்டு பங்கு குறைஞ்சது.

| சாயங்கால peak-ல அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| முதல் text வர நேரம் | கிட்டத்தட்ட 12 s | கிட்டத்தட்ட 0.7 s |
| Timeout ஆன requests | 33% | 1%-க்கும் கீழ |
| OCR uploads-ஆல server freeze | தினமும் | இல்லை |
| பதிலுக்கு முன்னாடி வெளியேறின students | Baseline | மூணுல ரெண்டு பங்கு குறைவு |

## பொதுவா பண்ற தப்புகள்

- **Production-ல ஒரே worker.** ஒரு block ஆன request எல்லாரையும் நிறுத்திடும். பல workers ஓட்டி அளந்து பாருங்க.
- **Timeouts இல்லாம இருக்கறது.** ஒரு தொங்கிய model call ஒரு worker-ஐ எப்பவும் பிடிச்சு வச்சுக்கும்.
- **முழு பதிலுக்கு காத்திருக்கறது.** Streaming இல்லைன்னா users spinner-ஐ பார்த்துட்டு போயிடுவாங்க.
- **Model-ஐ call பண்ற health checks.** அவை பணம் செலவழிக்கும், provider மெதுவா இருந்தா fail ஆகி healthy instances-ஐயும் எடுத்துடும்.
- **Requests-குள்ள நீண்ட jobs.** சில seconds-க்கு மேல CPU எடுக்கக்கூடிய எதுவா இருந்தாலும் queue use பண்ணுங்க.
- **Launch-க்கு முன்னாடி load test இல்லாம இருக்கறது.** முதல் சாயங்கால peak தான், service real traffic-ஐ பார்க்குற முதல் நேரமா இருக்கக்கூடாது.
- **Concurrent model calls-க்கு cap இல்லாம இருக்கறது.** அப்போ ஒரு burst provider rate limits-ஐ அடிச்சு, எல்லா requests-உம் மெதுவாகும்.
- **SSE events-ல raw text.** பதிலுக்குள்ள ஒரு newline இருந்தா stream உடைஞ்சுடும்.
- **Process உயிரோட இருக்குன்னு மட்டும் சொல்ற ready checks.**

## எளிமையான serving போதுமான நேரங்கள்

- **கொஞ்சம் users இருக்குற internal tools**: ஒரு process, timeouts, ஒரு health check போதும்.
- **Users-ஐ பார்க்காத batch jobs**: web service-ஐ விட scheduled script better.
- **Platform host பண்ற functions**, serverless routes மாதிரி. Workers, shutdown-ஐ platform பார்த்துக்கும்.

## Demo-ல இருந்து production-க்கு

- ஒரு process-க்கு **concurrency-ஐ cap பண்ணுங்க**, தெளிவான 429-ஓட load-ஐ shed பண்ணுங்க.
- **Timeouts-ஐ உள்ளிருந்து வெளியே வைங்க**: model call, request, load balancer.
- **Disconnect handling-ஓட stream பண்ணுங்க**, graceful shutdown-ஐ நீளமான stream-ஐ விட நீளமா வைங்க.
- **நீண்ட வேலையை queue-க்கு மாத்துங்க**, job ids, status-ஓட.
- **Time to first token, total time, timeouts-ஐ p95-ல track பண்ணுங்க**.

## Practice பண்ணுங்க

FastAPI-ஓட deployment concepts page-ஐயும், streaming பத்தின அதோட custom responses page-ஐயும் படிங்க.

1. உங்க FastAPI app-ல model tokens-ஐ client-க்கு forward பண்ற ஒரு streaming endpoint-ஐ சேர்த்து, அதுக்கு முன்னாடியும் பின்னாடியும் time to first token-ஐ அளந்து பாருங்க.
2. Model call, request-ல timeouts, `/health`, `/ready` endpoints சேர்த்து, நாலு workers-ஓட ஓட்டுங்க.
3. ஒரு மெதுவான task-ஐ job id, status endpoint-ஓட background job-க்கு மாத்துங்க.
4. ஒரு load tool வச்சு உங்க endpoint-க்கு 100 concurrent requests அனுப்பி, கூடுதல் requests timeout ஆகாம சீக்கிரம் 429 வாங்குதுன்னு confirm பண்ணுங்க.
