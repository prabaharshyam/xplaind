## இது என்ன

**LLM gateway**-னா உங்க applications-க்கும் model providers-க்கும் நடுவுல இருக்குற ஒரு service. Applications ஒவ்வொரு request-ஐயும் ஒரே API format-ல gateway-க்கு அனுப்பும். Gateway அதை சரியான provider, model-க்கு forward பண்ணும், shared வேலையை ஒவ்வொரு app-லயும் தனித்தனியா செய்யாம ஒரே தடவை handle பண்ணும்:

- **Routing**: இந்த request-ஐ எந்த model, provider serve பண்ணணும்.
- **Failover**: ஒரு provider error குடுத்தா, timeout ஆனா அல்லது உங்களை rate-limit பண்ணா என்ன try பண்றது.
- **Keys, access**: teams-க்கு gateway keys கிடைக்கும்; real provider keys gateway-ல மட்டும் இருக்கும்.
- **Rate limits, budgets**: ஒவ்வொரு team, feature அல்லது user-க்கும்.
- **Logging, cost**: ஒவ்வொரு request-உம் அதோட tokens, cost, latency-ஓட, ஒரே இடத்துல.

இந்த lesson Bengaluru-ல ஒரு fintech-ஐ follow பண்ணுது; அங்க நாலு teams-ஓட அஞ்சு AI features ஒவ்வொண்ணும் தன்னோட சொந்த keys-ஓட providers-ஐ நேரடியா call பண்ணிச்சு.

```flow
title: One gateway in front of every provider
Chatbot -[key chatbot]-> Gateway, 2 or more instances
Claims extraction -[key claims]-> Gateway, 2 or more instances
Nightly summaries -[key batch]-> Gateway, 2 or more instances
Gateway, 2 or more instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails, cool-down]-> Model X, Hyderabad
Model X, Hyderabad -[fails]-> Fallback alias: approved model Y, India
```

ஒவ்வொரு key-க்கும் தனி rate limit, budget இருக்கு. Gateway forward பண்றதுக்கு முன்னாடி அவற்றை check பண்ணும், result-ஐ log பண்ணும், provider keys-ஐ ஒரு secret store-ல வச்சுக்கும்.

### Gateway கிடைக்க மூணு வழிகள்

| வகை | உதாரணங்கள் | எப்போ தேர்ந்தெடுக்கலாம் |
| --- | --- | --- |
| Self-hosted, open source | LiteLLM proxy (MIT licence) | Data உங்க சொந்த cloud account, region-லயே இருக்கணும், database-ஓட ஒரு service-ஐ ஓட்டக்கூடிய platform team உங்ககிட்ட இருக்கு |
| உங்க cloud-ஓட API management | Azure API Management (அதோட `llm-token-limit` policy), Google Apigee (அதோட LLM token quota policy) | மத்த APIs-க்கு ஏற்கனவே அந்த cloud-ஓட API management-ஐ use பண்றீங்க, பெரும்பாலும் அந்த cloud-ஓட models-ஐ தான் call பண்றீங்க |
| ஒரு vendor-ஓட managed gateway | பல vendors உங்களுக்காக ஒண்ணை host பண்றாங்க | நீங்க சின்ன team, infrastructure ஓட்ட யாரும் இல்ல, vendor-ஓட data processing locations உங்க data-க்கு allowed |

முடிவு பொதுவா ரெண்டு கேள்விகள்ல வந்து நிக்கும். உங்க data எங்க process ஆகலாம்? ராத்திரி gateway உடைஞ்சா யாரை எழுப்புவாங்க? Managed gateway ஒவ்வொரு prompt-ஐயும் பார்க்கும், அதனால எல்லாத்துக்கும் முன்னாடி அது data-வை எங்க process பண்ணுதுன்னு check பண்ணுங்க.

## இது எப்படி வேலை செய்யுது

### ஒரே interface, model aliases

பெரும்பாலான gateways OpenAI-style chat format-ஐ ஏத்துக்கிட்டு, ஒவ்வொரு provider-க்கும் அதை translate பண்ணும். Apps ஒருபோதும் real model-ஓட பேரை சொல்லாது. அவை `chat-default` மாதிரி ஒரு **alias**-ஐ call பண்ணும், gateway அதை ஒரு real model-க்கு map பண்ணும். எல்லா apps-ஐயும் புது model-க்கு upgrade பண்றது gateway config-ல review பண்ண ஒரே ஒரு line ஆயிடும், முதல்ல உங்க golden set-ல test பண்ணி.

### Failover-ஓட ரெண்டு layers

நல்ல failover-ல ரெண்டு layers இருக்கு, அவற்றை மனசுல தனித்தனியா வச்சுக்கிறது உதவும்.

1. **ஒரே alias-க்கு பின்னாடி deployments.** அதே model ரெண்டு இடத்துல, உதாரணமா Mumbai, Hyderabad. ஒண்ணு fail ஆனா gateway இன்னொரு deployment-ல retry பண்ணும்.
2. **ஒரு fallback alias.** வேற ஒரு approved model; முதல் alias-ஓட எல்லா deployments-உம் fail ஆனா மட்டும் தான் use ஆகும்.

Fail ஆகுற ஒரு deployment ஒவ்வொரு request-ஐயும் slow பண்ணக் கூடாது. இதை ஒரு **cool-down** (circuit breaker-னும் சொல்லுவாங்க) handle பண்ணுது. கொஞ்ச நேரத்துக்குள்ள ரொம்ப அதிகமா failures வந்தா, gateway அந்த deployment-ஐ ஒரு fixed நேரத்துக்கு skip பண்ணும். Requests முதல்ல timeout-க்கு காத்திருக்க வேண்டியதில்ல. Cool-down முடிஞ்சதும் gateway அந்த deployment-ஐ திரும்ப try பண்ணும்.

### ஒரு gateway configuration

LiteLLM-ஓட proxy ஒரு common open-source choice; மத்த gateways இதே ideas-ஐ வேற syntax-ல use பண்ணும். ஒரே file-ல aliases, deployments, retries, cool-downs, fallback எல்லாம் define ஆகுது. LiteLLM 1.111.0-ல check பண்ணது.

```yaml
# gateway.yaml: the whole gateway in one reviewed file
model_list:
  # Alias chat-default: the same model deployed in two Indian regions.
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>             # in-Region ID or India profile, never APAC or global
      aws_region_name: ap-south-1           # Mumbai
      order: 1                              # used first while healthy
      timeout: 30                           # seconds, normal calls
      stream_timeout: 10                    # seconds, streaming calls
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>
      aws_region_name: ap-south-2           # Hyderabad
      order: 2                              # used when Mumbai fails or cools down
      timeout: 30
      stream_timeout: 10
  # Fallback alias: another provider, also in India, approved and tested on the evals.
  - model_name: chat-backup
    litellm_params:
      model: vertex_ai/<model id>
      vertex_project: os.environ/GCP_PROJECT
      vertex_location: asia-south1          # Mumbai
      timeout: 30

router_settings:
  num_retries: 2                            # retries on 429s and server errors
  allowed_fails: 3                          # more than 3 failures in a minute starts a cool-down
  cooldown_time: 60                         # seconds a cooling deployment is skipped
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL     # keys, limits, budgets and spend live here
```

`litellm --config gateway.yaml --port 4000`-ஓட அதை start பண்ணுங்க. Load balancer-க்கு பின்னாடி ரெண்டு அல்லது அதுக்கு மேல instances ஓட்டுங்க, எல்லாமே ஒரே database-ஐ point பண்ணணும்.

**Bedrock-ல ஒரு region trap.** Bedrock-ஓட cross-Region inference profiles, நீங்க call பண்ற Region-க்கு வெளிய prompts-ஐ process பண்ணலாம். APAC profile Asia Pacific-க்குள்ள இருக்கும், India-க்குள்ள இல்ல; global profile support ஆகுற எந்த commercial Region-ஐயும் use பண்ணலாம். சில Claude models-க்கு Bedrock-ல இப்போ ஒரு India geographic profile இருக்கு, அது Mumbai, Hyderabad நடுவுல மட்டும் route பண்ணும். Data India-ல தான் process ஆகணும்னா, அந்த profile-ஐயோ ஒரு in-Region model ID-ஐயோ use பண்ணுங்க, முதல்ல Bedrock Regional availability table-ஐ check பண்ணுங்க: எல்லா model-உம் Hyderabad-ல in-Region-ஆ கிடைக்காது.

### Apps alias-ஐ call பண்ணும், provider-ஐ இல்ல

எந்த OpenAI-compatible client-உம் வேலை செய்யும். Request-ஐ உண்மையில எது serve பண்ணுச்சுன்னு பார்க்க response headers-ஐ படிங்க:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=os.environ["GATEWAY_URL"], api_key=os.environ["CHATBOT_KEY"])

raw = client.chat.completions.with_raw_response.create(
    model="chat-default",                       # the alias, never a provider model name
    messages=[{"role": "user", "content": "Explain my last card statement in two lines: ..."}],
)
reply = raw.parse()
print(reply.choices[0].message.content)
print("model group:", raw.headers.get("x-litellm-model-group"))      # chat-backup means it fell back
print("fallbacks:", raw.headers.get("x-litellm-attempted-fallbacks"))
print("cost in USD:", raw.headers.get("x-litellm-response-cost"))
```

### Rate limits, budgets இருக்குற keys

Admin ஒவ்வொரு feature-க்கும் ஒரு virtual key create பண்ணுவாங்க. Virtual key-னா gateway issue பண்ற ஒரு key; அது real provider keys-க்கு map ஆகும், அந்த keys-ஐ team ஒருபோதும் பார்க்காது.

```bash
curl -s "$GATEWAY_URL/key/generate" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"key_alias": "chatbot", "models": ["chat-default", "chat-backup"],
       "rpm_limit": 600, "tpm_limit": 200000,
       "max_budget": 400, "budget_duration": "30d",
       "metadata": {"team": "support", "feature": "chatbot", "owner": "platform-lead"}}'
```

`rpm_limit` இந்த key-க்கு ஒரு நிமிஷத்துக்கு requests-ஐ cap பண்ணுது, `tpm_limit` ஒரு நிமிஷத்துக்கு tokens-ஐ cap பண்ணுது. Fallback alias-ஐயும் `models`-ல list பண்ணுங்க: testing-ல, `chat-default` மட்டும் allowed ஆன ஒரு key-க்கு backup-க்கு பதிலா ஒரு plain error தான் கிடைச்சுது. Key-ஐ revoke பண்ணா, வேற எதையும் rotate பண்ணாம ஒரு feature-ஐ மட்டும் cut பண்ணலாம். இந்த setup-ஐ test பண்ணப்போ தெரிஞ்ச மூணு behaviours தெரிஞ்சுக்கிறது நல்லது:

- **Rate limit-உம் budget-உம் வேற வேற மாதிரி fail ஆகும்.** `rpm_limit`-ஐ தாண்டினப்போ HTTP 429 வந்துச்சு, அதை client கொஞ்சம் pause பண்ணி retry பண்ணலாம். Budget செலவாயிட்டப்போ `budget_exceeded` type-ஓட HTTP 422 வந்துச்சு. அதை retry பண்ணா நேரம் தான் வீணாகும், அதனால clients அதை final-ஆ எடுத்துக்கிட்டு ஒரு ஆளுக்கு alert பண்ணணும்.
- **Budgets தோராயமானவை.** Gateway ஒவ்வொரு request-க்கும் முன்னாடி budget-ஐ check பண்ணுது, அதனால line-ஐ தாண்டுற request கூட complete ஆகும். 0.05 dollar budget-ஓட ஒரு test-ல, requests refuse ஆகுறதுக்கு முன்னாடி spend 0.065 வரை போச்சு. உண்மையில நீங்க afford பண்ணக்கூடியதை விட cap-ஐ கொஞ்சம் கீழ வைங்க.
- **Reset date-ஐ check பண்ணுங்க.** Period இன்னைக்கு ஆரம்பிக்குதுன்னு நினைச்சுக்காம, key create பண்ண அப்புறம் `/key/info`-ல இருந்து `budget_reset_at`-ஐ படிங்க. Budgets US dollars-ல இருக்கு, அதனால உங்க reports-ல ஒரு stated rate-ல ரூபாய்க்கு convert பண்ணுங்க.

### Provider-ஓட quota-வை நியாயமா பங்கிடுறது

உங்க provider ஒவ்வொரு model-க்கும் ஒரு quota தருவாங்க, உதாரணமா Mumbai-ல ஒரு நிமிஷத்துக்கு இத்தனை tokens. எல்லா keys-உம் அதை share பண்ணும். Rule: **quota கிடைக்காம போகவே கூடாத features-ஓட limits-ஐ கூட்டினா provider quota-வை விட குறைவா, headroom-ஓட இருக்கணும்.** Batch jobs-க்கு சின்ன limit, அவை ராத்திரி ஓடும், 429s-ல காத்திருக்கும். Per-key limits இல்லைன்னா, முதல்ல busy ஆகுற job முழு quota-வையும் எடுத்துக்கும், "provider up-ஆ தான் இருக்கு"-னாலும் customer chatbot fail ஆகும்.

### Fallback edge cases

Production-ல gateways fail ஆகுறது fallbacks-ல தான். இவற்றுக்கு plan பண்ணுங்க:

- **Streams.** முதல் token வர்றதுக்கு முன்னாடி ஒரு stream fail ஆனா, gateway அடுத்த deployment-ஐ try பண்ணலாம், user-க்கு தெரியவே தெரியாது; LiteLLM இப்படி தான் பண்ணுது. User பாதி answer-ஐ பார்த்த அப்புறம் switch பண்ணா, answer-ஐ restart பண்ணணும் அல்லது ரெண்டு models-ஓட text-ஐ ஒட்டணும். என்ன காட்டணும்னு app-லயே முடிவு பண்ணுங்க, உதாரணமா "answer பாதியில நின்னுடுச்சு, retry பண்ணவா?".
- **Tool calls.** ஒரு request-ஓட tool call ஏற்கனவே payment அல்லது email மாதிரி side effects இருக்குற ஏதாவது ஒண்ணை ஓட்டிடுச்சுன்னா, அதை ஒருபோதும் retry பண்ணாதீங்க. அந்த tools-ஐ idempotency key-ஓட repeat பண்ண safe-ஆ ஆக்குங்க, இல்லைன்னா அவற்றை retry பண்ணாதீங்க.
- **Prompt caching.** Provider prompt caches உங்க கூட நகராது. Fallback நடக்கும்போது, ஒவ்வொரு request-உம் நீளமான system prompt-க்கு full price-உம் full latency-உம் குடுக்கும், அதனால outage நடக்கும்போது cost-உம் time to first token-உம் எகிறும்னு எதிர்பாருங்க.
- **Format, tool-call shape.** Backup model JSON அல்லது tool calls-ஐ கொஞ்சம் வேற மாதிரி format பண்ணலாம். Feature-ஓட evals-ஐ fallback alias-ல ஓட்டுங்க, அதோட output-ல parser-ஐ test பண்ணுங்க.
- **Fall back ஆகக் கூடாத errors.** Malformed request எல்லா model-லயும் fail ஆகும். Fall back பண்றது latency-ஐயும் cost-ஐயும் தான் கூட்டும். Timeouts, 429s, server errors-க்கு fall back பண்ணுங்க.
- **உடைஞ்ச key-ஐ மறைக்கிற fallbacks.** ஒரு test-ல, primary-ல இருந்த தப்பான key 401 return பண்ணுச்சு, gateway அதை retry பண்ணல, உடனே fall back பண்ணிச்சு. Users-க்கு எந்த பிரச்சனையும் தெரியல. Errors-க்கு மட்டும் இல்லாம, ஒரு alias-ஓட fallback rate ஏறும்போதும் alert பண்ணுங்க.

### Try it: fallback chain-ல cool-downs

இந்த simulation-ல request 3-ல இருந்து request 12 வரை Mumbai outage இருக்கு. Cool-down எப்படி requests Mumbai-க்காக காத்திருக்கிறதை நிறுத்துது, ரொம்ப நீளமான cool-down Mumbai சரியான அப்புறமும் அதை எப்படி skip பண்ணிக்கிட்டே இருக்குதுன்னு பாருங்க.

```python
import random

random.seed(7)
ALLOWED_FAILS = 2      # cool down after more than this many failures
COOLDOWN = 5           # requests to skip a cooling deployment
fails = {"mumbai": 0, "hyderabad": 0, "backup": 0}
cooling_until = {"mumbai": 0, "hyderabad": 0, "backup": 0}

def call(deployment, t):
    # Mumbai has an outage from request 3 to request 12.
    if deployment == "mumbai" and 3 <= t <= 12:
        raise TimeoutError("timed out")
    if random.random() < 0.05:
        raise TimeoutError("timed out")
    return deployment

def gateway(t, chain=("mumbai", "hyderabad", "backup")):
    tried = []
    for d in chain:
        if t < cooling_until[d]:
            continue                       # skip without waiting for a timeout
        try:
            served = call(d, t)
            fails[d] = 0
            return served, tried
        except TimeoutError:
            tried.append(d)
            fails[d] += 1
            if fails[d] > ALLOWED_FAILS:
                cooling_until[d] = t + COOLDOWN
                fails[d] = 0
    return "error", tried

for t in range(16):
    served, tried = gateway(t)
    note = f"(waited on {', '.join(tried)})" if tried else ""
    print(f"request {t:2}: served by {served:9} {note}")
```

Requests 3 முதல் 5 வரை ஒவ்வொண்ணும் Mumbai timeout-க்காக காத்திருக்கும். அப்புறம் Mumbai cool down ஆகுது, requests 6 முதல் 9 வரை நேரா Hyderabad-க்கு போகும். Request 8 ரெண்டாவது layer-ஐ காட்டுது: Hyderabad-ல ஒரு random timeout வருது, அதனால backup answer பண்ணுது. Request 10-ல Mumbai இன்னும் down-ஆ இருக்கும்போதே cool-down முடியுது, அதனால requests 10 முதல் 12 வரை திரும்ப அதுக்காக காத்திருக்கும், ரெண்டாவது cool-down ஆரம்பிக்கும். Request 13-ல இருந்து Mumbai திரும்ப வந்துடுது, ஆனா அது இன்னும் cool down ஆகிட்டு இருக்கிறதால use ஆகாது. Timeouts-க்கு காத்திருக்கிறதுக்கும் ஒரு recovery-ஐ miss பண்றதுக்கும் இடையில இருக்குற trade-off-ஐ பார்க்க `COOLDOWN = 2`, `ALLOWED_FAILS = 0` try பண்ணுங்க.

### Region-aware routing, logs

Indian personal data-க்கு, அந்த features use பண்ற aliases Indian-region deployments-ஐ மட்டும் தான் point பண்ணணும். மத்த regions-ஐ use பண்ண allowed ஆன features-க்கு தனி alias வச்சுக்கோங்க. ஒவ்வொரு call-ஓட alias, deployment, region-ஐ log பண்ணுங்க, அப்போ rule follow ஆச்சுன்னு ஒரு audit confirm பண்ணலாம். Gateway-ஓட logs-ல personal data-வை mask பண்ணுங்க: அது ஒவ்வொரு prompt-ஐயும் பார்க்குது, அதனால mask பண்ணாத logs அதை உங்களோட மிகப்பெரிய sensitive data store ஆக்கிடும்.

### ஒரு gateway-ஓட cost

அது ஓட்ட, secure பண்ண, available-ஆ வச்சுக்க வேண்டிய இன்னொரு service, ஒவ்வொரு AI feature-உம் அதை நம்பியிருக்கு. அதோட சொந்த overhead-ஐ measure பண்ணுங்க: அதே set of requests-ஐ நேரடியாவும் gateway வழியாவும் அனுப்பி, median, slow (p95) latency-ஐ compare பண்ணுங்க, முக்கியமா streams-க்கு time to first token. அதை உங்க apps-க்கு பக்கத்துலயே வைங்க, அதோட error rate-ஐயும் database-ஐயும் monitor பண்ணுங்க, documented emergency path ஒண்ணு வச்சுக்கோங்க, உதாரணமா ஒரு critical feature-ஐ நேரா அதோட provider-க்கு அனுப்புற feature flag.

## ஒரு worked example

Bengaluru fintech-ல நாலு teams-ஓட அஞ்சு AI features இருக்கு. ஒவ்வொரு team-உம் தன்னோட சொந்த provider keys-ஐ வச்சிருக்கு, finance-க்கு ஒரு பெரிய monthly bill மட்டும் தெரியுது. கீழ இருக்குற numbers ஒரு typical rollout-ஓட illustration தான், measure பண்ண results இல்ல.

**Trigger.** ஒரு provider outage customer chatbot-ஐ சுமார் 50 நிமிஷம் down பண்ணிடுச்சு. அதே மாசத்துல, ஒரு nightly statement-summary job காலை வரைக்கும் நீண்டு ஓடி shared token quota-ல பெரும்பகுதியை use பண்ணிடுச்சு, அதனால chatbot rate-limit errors-உம் return பண்ணுச்சு.

**Setup.** Platform team company-ஓட Kubernetes cluster-ல gateway-ஐ ரெண்டு instances-ஆ deploy பண்ணுது.

- **Keys.** ஒவ்வொரு feature-க்கும் team, feature tag போட்ட தனி gateway key. Provider keys gateway-ஓட secret store-க்கு போகுது, rotate பண்ணப்படுது. பழைய direct keys ரெண்டு வாரம் வேலை செய்யும், அப்புறம் revoke ஆகும், அதனால gateway மட்டும் தான் ஒரே path ஆகும்.
- **Aliases.** `chat-default`, `extract-default`, `embed-default`, ஒவ்வொண்ணும் ஒரு specific model-க்கு map ஆகியிருக்கு.
- **`chat-default`-க்கு failover.** அதே model Mumbai, Hyderabad-ல, 60-second cool-down-ஓட, அப்புறம் ரெண்டாவது provider-ஓட model இருக்குற fallback alias, அதுவும் India-ல host ஆனது, compliance approve பண்ணது.
- **Fallback-ல evals.** Go-live-க்கு முன்னாடி, team chatbot-ஓட 300-question golden set-ஐ ரெண்டுலயும் ஓட்டுது. Primary 92%, backup 88% score பண்ணுதுன்னு வச்சுக்கோங்க, ரெண்டு JSON format failures-ஓட, அதை ஒரு parser fix சரி பண்ணுது. Outages-க்கு team 88%-ஐ ஏத்துக்கிட்டு runbook-ல record பண்ணுது.
- **Quota sharing.** Mumbai quota ஒரு நிமிஷத்துக்கு 400,000 tokens-னு வச்சுக்கோங்க. Chatbot-க்கு 200,000, claims extraction-க்கு 100,000. Batch job-க்கு 60,000, அது midnight-க்கு அப்புறம் ஓடும். மொத்தம் 360,000, spikes-க்கு headroom மிச்சம் இருக்கு.
- **Budgets, logs.** ஒவ்வொரு key-க்கும் 75%-ல alert-ஓட ஒரு monthly budget. ஒவ்வொரு request-உம் team, feature, alias, deployment, tokens, cost, latency-ஓட log ஆகுது, personal data mask பண்ணப்பட்டு.

**Result.** அடுத்த provider incident-ல, errors-க்கு பதிலா, Mumbai cool down ஆகி Hyderabad serve பண்ற கொஞ்ச நேரம் users-க்கு answers கொஞ்சம் slow-ஆ வரும். Fallback-rate alert on-call engineer-க்கு என்ன நடந்துச்சுன்னு சொல்லும். Feature வாரியான முதல் cost report, statement-summary job spend-ல சுமார் 40% use பண்றதை காட்டுது. அந்த team அதை ஒரு cheaper model-க்கும் provider-ஓட batch API-க்கும் மாத்துது.

## பொதுவான தவறுகள்

- **ஒரே ஒரு gateway instance.** ஒவ்வொரு AI feature-க்கும் ஒரு புது single point of failure-ஐ உருவாக்கிட்டீங்க. பல instances ஓட்டுங்க.
- **Approve ஆகாத models அல்லது regions-க்கு fallbacks.** ஒரு outage, data போக allowed இல்லாத இடத்துக்கு அதை சத்தமில்லாம அனுப்பக் கூடாது. Data India-லயே இருக்கணும்னா Bedrock APAC அல்லது global profiles-உம் இதுல அடங்கும்.
- **Application code-ல model names.** Upgrades, swaps ஒரே இடத்துல நடக்க aliases use பண்ணுங்க.
- **கூட்டினா provider quota-வை விட அதிகமா வர்ற key limits.** அப்போ ஒரு busy key இன்னும் மத்தவற்றுக்கு quota கிடைக்காம பண்ணலாம்.
- **Budget error-ஐ retry பண்றது.** செலவான budget சில seconds-ல திரும்ப நிரம்பாது. அதை final-ஆ எடுத்துக்கிட்டு யாருக்காவது alert பண்ணுங்க.
- **Test பண்ணாத fallbacks.** ஒருபோதும் fire ஆகாத fallback, முதல் தடவை fire ஆகும்போது output formats-ஐயோ quality-ஐயோ உடைக்கலாம்.
- **Errors-க்கு மட்டும் alert பண்றது.** Fallbacks failures-ஐ users-கிட்ட இருந்து மறைக்கும், அதனால உடைஞ்ச primary key வாரக்கணக்கா யாருக்கும் தெரியாம போகலாம்.
- **Masking இல்லாம full prompts இருக்குற gateway logs.** Gateway உங்ககிட்ட இருக்குற மிகப்பெரிய sensitive data store ஆயிடும்.

## எப்போ gateway தேவைக்கு அதிகம்

- **ஒரே provider-ஓட ஒரே app.** Retries, timeout, billing alert-ஓட provider-ஓட SDK போதும்.
- **ஒரு சின்ன team**, gateway மிச்சப்படுத்துற நேரத்தை விட அதை ஓட்டுறதுக்கு அதிக நேரம் செலவழிக்கும்னா.
- **ஒரு managed platform**, ஏற்கனவே keys, budgets, routing தர்றதுன்னா.

பல teams அல்லது apps providers, keys, quota, budgets-ஐ share பண்ண ஆரம்பிச்சதும் gateway பலன் தரும்.

## Demo-ல இருந்து production-க்கு

- **ரெண்டு அல்லது அதுக்கு மேல instances ஓட்டுங்க**, health checks, அவற்றோட சொந்த monitoring, ஒரு shared database-ஓட.
- **Config-ஐ Git-ல வைங்க**, code மாதிரியே review பண்ணுங்க, model changes-ஐ golden set-ல test பண்ணுங்க.
- **ஒவ்வொரு feature-க்கும் ஒரு key குடுங்க**, rate limit, budget, பேர் சொல்லப்பட்ட owner-ஓட.
- **Personal data-வை approved regions-க்கு மட்டும் route பண்ணுங்க**, ஒவ்வொரு call-ஓட region-ஐயும் log பண்ணுங்க.
- **Staging-ல failover drill பண்ணுங்க.** தப்பான key அல்லது blocked endpoint வச்சு வேணும்னே primary-ஐ உடைங்க. Requests இன்னும் succeed ஆகுதா, latency ஏத்துக்கக்கூடிய அளவுல இருக்கா, எந்த model serve பண்ணுச்சுன்னு logs, headers காட்டுதான்னு check பண்ணுங்க. Chain-ல ஒவ்வொரு change-க்கு அப்புறமும் repeat பண்ணுங்க.
- **முதல்ல ஒரு low-risk feature-ஐ roll out பண்ணுங்க**, அதோட errors, latency, cost-ஐ முன்னாடி இருந்ததோட compare பண்ணுங்க, அப்புறம் மத்தவற்றை ஒவ்வொண்ணா மாத்துங்க.

## Practice

LiteLLM gateway docs-ஐயும் RouteLLM post-ஐயும் படிங்க. Virtual keys-க்கு ஒரு Postgres database-உம் அதோட client-உம் தேவைப்படுறதால, proxy-ஐ ஓட்ட LiteLLM-ஓட published Docker image தான் ரொம்ப ஈஸியான வழி.

1. Postgres-உம் ரெண்டு models-உம் (ரெண்டு providers, அல்லது ஒரே provider-ஓட ரெண்டு models) வச்சு gateway-ஐ locally ஓட்டுங்க. முதல் model-ஐ `chat-default` alias-க்கு பின்னாடியும், ரெண்டாவதை `chat-backup`-க்கு பின்னாடியும் வைங்க, அவற்றுக்கு நடுவுல ஒரு fallback-ஓட.
2. Primary-க்கு தப்பான key குடுங்க. Requests இன்னும் succeed ஆகுது, `x-litellm-attempted-fallbacks` header 1-னு சொல்லுதுன்னு காட்டுங்க.
3. `rpm_limit` 3 இருக்குற ஒரு key create பண்ணுங்க. ஒரு நிமிஷத்துல 5 requests அனுப்பி, நாலாவது request-க்கு HTTP 429 கிடைக்குதுன்னு காட்டுங்க.
4. ரொம்ப சின்ன budget இருக்குற ஒரு key create பண்ணுங்க. அதை செலவழிச்சு, budget error-ஐ காட்டுங்க, spend cap-ஐ தாண்டி எவ்வளவு போச்சுன்னு note பண்ணுங்க.
