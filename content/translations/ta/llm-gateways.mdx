## இது என்ன

**LLM gateway** உங்க applications-க்கும் model providers-க்கும் நடுவுல இருக்குற ஒரு service. Applications ஒரே API format-ல gateway-ஐ call பண்ணும்; gateway ஒவ்வொரு request-ஐயும் சரியான provider, model-க்கு அனுப்பும், பொதுவான தேவைகளை ஒரே தடவை handle பண்ணும்:

- **Routing**: எந்த model, provider இந்த request-ஐ serve பண்ணும்.
- **Fallbacks**: ஒரு provider error கொடுத்தா, timeout ஆனா அல்லது rate-limit பண்ணா என்ன try பண்றது.
- **Keys, access**: teams-க்கு gateway keys கிடைக்கும்; உண்மையான provider keys gateway-ல மட்டும் இருக்கும்.
- **Limits, budgets**: ஒவ்வொரு team, key, user-க்கும்.
- **Logging, cost**: ஒவ்வொரு request-ம், அதோட tokens-உம், cost-உம், ஒரே இடத்துல.
- **Caching**: ஒரே மாதிரி requests-ஐ விருப்பப்பட்டா திருப்பி use பண்றது.

LiteLLM மாதிரி open-source options, commercial gateways, cloud providers-ஓட API management services எல்லாமே இந்த role-ஐ செய்யும்.

```flow
Chatbot -[key A]-> Gateway, 2 instances
Extraction -[key B]-> Gateway, 2 instances
Summariser -[key C]-> Gateway, 2 instances
Search -[key D]-> Gateway, 2 instances
Gateway, 2 instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fail ஆனா]-> Fallback 1: model X, ரெண்டாவது region
Fallback 1: model X, ரெண்டாவது region -[fail ஆனா]-> Fallback 2: approve பண்ண model Y, provider 2
```

Gateway ஒவ்வொரு key-க்கும் 75%-ல alerts-ஓட budgets, retries, timeouts, masked logs (team, feature, model, tokens, cost, latency) சேர்க்கும். Provider keys இங்க மட்டும், ஒரு secret store-ல இருக்கும், rotate ஆகும்.

இந்த lesson, Bengaluru-ல நாலு teams-ஓட அஞ்சு AI features ஒவ்வொண்ணும் providers-ஐ நேரடியா call பண்ண ஒரு fintech-ஐ follow பண்ணுது.

## இது எப்படி work ஆகுது

**ஒரே interface.** பெரும்பாலான gateways OpenAI-compatible அல்லது அது மாதிரி ஒரு request format-ஐ ஏத்துக்கிட்டு, ஒவ்வொரு provider-க்கும் translate பண்ணும், அதனால ஒரு feature-ஐ ஒரு model-ல இருந்து இன்னொண்ணுக்கு மாத்துறது configuration மாற்றம், code மாற்றம் இல்ல.

**Routing rules.** Model alias வச்சு route பண்ணலாம் (`summariser-default` ஒரு specific model-ஐ சுட்டும், அதை ஒரே இடத்துல மாத்தலாம்), team வச்சு, region வச்சு (Indian users-ஓட data-ஐ Indian-region endpoints-க்கு மட்டும் அனுப்புங்க), அல்லது request-ஓட அம்சங்களை வச்சு. புத்திசாலி routers எளிய requests-ஐ மலிவான models-க்கு அனுப்பும்; அடுத்த lesson இதை கவர் பண்ணும்.

**Fallbacks.** இப்படி ஒரு chain: Mumbai region-ல primary model; timeout அல்லது 5xx வந்தா, அதே model வேற region-ல; மறுபடி fail ஆனா, வேற provider-ஓட ஒத்த model. Fallbacks-ல கவனம் வேணும்: fallback model வேலைக்கு போதுமான அளவு நல்லதா இருக்கணும், data rules-படி அனுமதிக்கப்பட்டதாவும் இருக்கணும்.

**Retries, timeouts.** Gateway 429s, transient errors-ல backoff-ஓட retry பண்ணும், timeouts-ஐ enforce பண்ணும், அதனால ஒவ்வொரு application-உம் இதை திருப்பி எழுத வேண்டாம்.

**Budgets.** ஒவ்வொரு key-க்கும் monthly அல்லது daily budget இருக்கும்; அதை தாண்டுன requests மறுக்கப்படும் அல்லது downgrade ஆகும். Thresholds-ல alerts போகும்.

**Gateway-ஓட cost.** இது ஓட்டவும், secure பண்ணவும், available-ஆ வச்சிருக்கவும் இன்னொரு service; இது விழுந்தா, ஒவ்வொரு AI feature-உம் விழும். குறைஞ்சது ரெண்டு instances, health checks, தன்னோட monitoring-ஓட ஓட்டுங்க.

**Gateway features-உம் அவை தீர்க்குற பிரச்சனைகளும்:**

| Feature | எந்த பிரச்சனையை தீர்க்குது |
| --- | --- |
| ஒரே request format | ஒவ்வொரு team-உம் ஒவ்வொரு provider-க்கும் code எழுதுறது |
| Model aliases | பல apps-ல hard-code பண்ண model பேர்கள் |
| Fallbacks | ஒரு provider outage ஒரு feature-ஐ கீழ இறக்குறது |
| Central keys | Teams, laptops-ல சிதறிக்கிடக்குற provider keys |
| ஒவ்வொரு key-க்கும் budgets | ஒரு feature அமைதியா பெரும்பாலான செலவை எடுத்துக்குறது |
| Unified logs | Features முழுக்க cost, latency, errors-ஓட எந்த பார்வையும் இல்லாதது |
| Caching | ஒரே மாதிரி requests-க்கு திருப்பி காசு கொடுக்குறது |

**Fallbacks-ஐ test பண்றது.** ஒரு தடவை கூட fire ஆகாத fallback வேலை செய்யாம போகலாம். Staging-ல, வேணும்ன்னே primary-ஐ உடைங்க, தப்பான key அல்லது block பண்ண endpoint வச்சு, அப்புறம் requests அடுத்த option வழியா வெற்றியடையுதா, latency ஏத்துக்கக்கூடிய அளவுல இருக்கா, ஒவ்வொரு request-ஐயும் உண்மையில எந்த model serve பண்ணுச்சுன்னு logs record பண்ணுதான்னு check பண்ணுங்க. Chain-ல ஒவ்வொரு மாற்றத்துக்கு அப்புறமும் திருப்பி பண்ணுங்க. ஒவ்வொரு fallback model-லயும் feature-ஓட evals-ஐ ஓட்டுங்க, அப்போ outage நேரத்துல users-க்கு என்ன quality கிடைக்குதுன்னு தெரியும்.

**Gateway-ஐ rollout பண்றது.** முதல்ல ஒரு குறைஞ்ச risk உள்ள feature-ஐ மாத்துங்க, அதோட errors, latency, cost-ஐ முன்னாடி இருந்ததோட ஒப்பிடுங்க, அப்புறம் மத்தவற்றை ஒவ்வொண்ணா migrate பண்ணுங்க. ஒவ்வொரு team-ஓட பழைய direct keys-ஐ கொஞ்ச நாள் overlap-க்கு வேலை செய்ய விடுங்க, அப்புறம் revoke பண்ணுங்க, அப்போ providers-ஐ அடையுற ஒரே வழி gateway ஆகும்.

**ஒரு gateway configuration.** LiteLLM-ஓட proxy ஒரு பொதுவான open-source தேர்வு; மத்த gateways-உம் இதே யோசனைகளை follow பண்ணும். ஒரு file aliases, உண்மையான models, fallbacks, admin key-ஐ define பண்ணும்:

```yaml
# litellm-config.yaml
model_list:
  - model_name: chat-default                 # the alias apps use
    litellm_params:
      model: anthropic/claude-sonnet-5-5     # check the docs for current names
      api_key: os.environ/ANTHROPIC_API_KEY
      timeout: 30
  - model_name: chat-backup
    litellm_params:
      model: bedrock/<model id from your Bedrock console>
      aws_region_name: ap-south-1
  - model_name: fast
    litellm_params:
      model: anthropic/claude-haiku-5-5

litellm_settings:
  num_retries: 2
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/GATEWAY_DB_URL     # stores keys, budgets and spend
```

Load balancer-க்கு பின்னாடி ரெண்டு அல்லது அதுக்கு மேல instances-ஓட ஓட்டுங்க: `litellm --config litellm-config.yaml --port 4000`.

**Apps provider-ஐ இல்ல, alias-ஐ call பண்ணும்.** எந்த OpenAI-compatible client-உம் work ஆகும்:

```python
import os
from openai import OpenAI

client = OpenAI(base_url="https://gateway.internal.example.in", api_key=os.environ["TEAM_CLAIMS_KEY"])
reply = client.chat.completions.create(model="chat-default",
                                       messages=[{"role": "user", "content": "Summarise this claim: ..."}])
```

இப்போ ஒவ்வொரு app-ஐயும் ஒரு புது model-க்கு மாத்துறது gateway config-ல ஒரு line, அதை code மாதிரி review பண்ணி, முதல்ல golden set-ல test பண்ணுவாங்க.

**ஒவ்வொரு team-க்கும் budgets உள்ள keys.** Admin ஒவ்வொரு feature-க்கும் ஒரு virtual key உருவாக்குவாரு:

```bash
curl -s https://gateway.internal.example.in/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"models": ["chat-default", "fast"], "max_budget": 50, "budget_duration": "30d",
       "metadata": {"team": "claims", "owner": "platform-lead"}}'
```

Team-க்கு provider keys ஒருபோதும் தெரியாது; அவங்க virtual key-ஐ revoke பண்ணா, வேற எதையும் rotate பண்ணாம அவங்களை cut பண்ணிடலாம். Budgets gateway-ஓட currency setting-ல இருக்கும் (பெரும்பாலும் US dollars), அதனால convert பண்ணி rate-ஐ note பண்ணுங்க.

**Region-aware routing.** Indian personal data-க்கு, அந்த features use பண்ற aliases-ஐ Indian-region endpoints-க்கு மட்டும் காட்டுங்க, மத்த regions-ஐ use பண்ண அனுமதிக்கப்பட்ட features-க்கு தனி alias வைங்க. ஒவ்வொரு call-ஓட region-ஐயும் log பண்ணுங்க, அப்போ rule நிலைச்சுதுன்னு audit உறுதிப்படுத்தலாம்.

**Gateway ஒரு critical infrastructure.** அதோட சொந்த latency (அது milliseconds மட்டும் சேர்க்கணும்), error rate, database health-ஐ monitor பண்ணுங்க, உங்க apps-க்கு பக்கத்துல வச்சுக்கோங்க, ஒரு documented emergency path வச்சுக்கோங்க, உதாரணமா ஒரு critical feature-ஐ நேரடியா அதோட provider-க்கு அனுப்புற ஒரு feature flag.

**உங்க browser-ல try பண்ணுங்க.** ஒரு gateway-ஓட fallback chain, simulate பண்ணது: primary fail ஆனா, அடுத்த model பதில் சொல்லும்.

```python
import random

random.seed(5)
def call(model):
    if model == "primary" and random.random() < 0.3:
        raise TimeoutError("primary timed out")
    return f"answer from {model}"

def gateway(chain=("primary", "backup")):
    for model in chain:
        try:
            return call(model)
        except TimeoutError as err:
            print("  fell back:", err)
    return "all models failed"

for i in range(5):
    print(i, gateway())
```

## ஒரு worked example

Bengaluru-ல ஒரு fintech-க்கு நாலு teams கட்டுன அஞ்சு AI features இருக்கு. ஒவ்வொரு team-க்கும் சொந்த provider keys; finance-க்கு ஒரு பெரிய monthly bill தான் தெரியுது. போன மாசம் ஒரு provider outage customer chatbot-ஐ 50 நிமிஷம் நிறுத்திடுச்சு.

நீங்க அவங்க Kubernetes cluster-ல ரெண்டு instances-ஓட ஒரு gateway-ஐ deploy பண்றீங்க:

- ஒவ்வொரு team-க்கும் team, feature tag போட்ட gateway key கிடைக்குது; provider keys gateway-ஓட secret store-க்கு மாத்தப்பட்டு rotate ஆகுது.
- Model aliases: `chat-default`, `extract-default`, `embed-default`, ஒவ்வொண்ணும் ஒரு specific model-ஐ சுட்டுது, அதனால evals pass ஆனதுக்கு அப்புறம் upgrades ஒரே இடத்துல நடக்குது.
- `chat-default`-க்கு fallbacks: அதே model ரெண்டாவது region-ல, அப்புறம் compliance team approve பண்ண ரெண்டாவது provider-ஓட ஒத்த model.
- Budgets: ஒவ்வொரு feature-க்கும் monthly cap-உம் 75%-ல alert-உம்.
- Logs: team, feature, model, tokens, cost, latency-ஓட ஒவ்வொரு request-ம் அவங்க analytics store-க்கு போகுது.

அடுத்த provider incident-ல 50 நிமிஷ errors-க்கு பதிலா, fallback எடுத்துக்குற வரை 90 seconds மெதுவான responses மட்டும் வருது. Finance-க்கு முதல் தடவையா feature வாரியா monthly cost report கிடைக்குது, அது ஒரு internal summarisation job 40% செலவை எடுக்குதுன்னு காட்டுது. அந்த team அதை ஒரு batch job-ஆவும் மலிவான model-ஆவும் மாத்துது.

| Measure | Gateway-க்கு முன்னாடி | பின்னாடி |
| --- | --- | --- |
| Provider incident-ஓட effect | Chatbot-ல 50 நிமிஷ errors | 90 seconds மெதுவான responses |
| Provider keys | நாலு teams-கிட்ட | gateway-ல மட்டும், rotate ஆகும் |
| Cost visibility | ஒரு monthly bill | Team, feature வாரியா report |
| மிகப்பெரிய கண்டுபிடிப்பு | தெரியாது | ஒரு summary job 40% செலவை எடுத்துச்சு, batch-க்கும் மலிவான model-க்கும் மாத்துனாங்க |

## பொதுவா பண்ற தப்புகள்

- **ஒரே ஒரு gateway instance.** நீங்க ஒரு புது single point of failure-ஐ உருவாக்கிட்டீங்க. பல instances ஓட்டுங்க.
- **Approve பண்ணாத models அல்லது regions-க்கு fallbacks.** ஒரு outage, data-ஐ போகக்கூடாத இடத்துக்கு அமைதியா அனுப்பிடக்கூடாது.
- **Apps-ல hard-code பண்ண model பேர்கள்.** Aliases use பண்ணுங்க, அப்போ upgrades, swaps ஒரே இடத்துல நடக்கும்.
- **Per-feature attribution இல்லாம இருக்குறது.** Provider வாரியா மட்டும் cost reports எதை சரி பண்ணணும்ன்னு சொல்லாது.
- **முழு prompts-ஓட, masking இல்லாத gateway logs.** Gateway உங்ககிட்ட இருக்குற மிகப்பெரிய sensitive data store ஆயிடும்.
- **ஒரே ஒரு gateway instance**, அது fail ஆனா ஒவ்வொரு AI feature-ஐயும் கீழ இறக்கும்.
- **Test பண்ணாத fallbacks**, முதல் தடவை fire ஆகும்போது output formats அல்லது quality-ஐ உடைக்கும்.
- **Gateway aliases-க்கு பதிலா application code-ல model பேர்கள்.**

## Gateway தேவைக்கு அதிகமா இருக்குற நேரங்கள்

- **ஒரு app, ஒரு provider**: retries-உம் budget alert-உம் உள்ள provider SDK போதும்.
- **ஒரு சின்ன team**, gateway மிச்சப்படுத்துறதை விட அதை ஓட்டுறதுல அதிக நேரம் செலவழிக்கும்.
- **ஏற்கனவே keys, budgets, routing தர்ற ஒரு managed platform.**

பல teams அல்லது apps providers, keys, budgets-ஐ share பண்ணும்போது gateway பலன் தரும்.

## Demo-ல இருந்து production-க்கு

- **குறைஞ்சது ரெண்டு instances ஓட்டுங்க**, health checks, தன்னோட monitoring-ஓட.
- **Config-ஐ Git-ல வச்சுக்கோங்க**, review பண்ணி, model மாற்றங்களுக்கு golden set-ல test பண்ணி.
