## இது என்ன

வெளிய இருந்து பார்த்தா ஒரு AI product, கேள்விகளுக்கு பதில் சொல்ற ஒரு chat box மாதிரி தெரியும். உள்ள அது சின்ன சின்ன பாகங்களோட ஒரு system; அது தப்பா போனா, fix **எந்த பாகம்** fail ஆச்சுன்னு பொறுத்தது. பாகங்களை வரையத் தெரிஞ்ச product managers engineers-ஓட பயனுள்ள உரையாடல் பண்ணலாம். தெரியாதவங்க ஒவ்வொரு தடவையும் "better model வேணும்"ன்னு கேட்டுக்கிட்டே இருப்பாங்க.

Language models மேல build பண்ண பெரும்பாலான AI products ஒரே பாகங்களை share பண்ணுது. ஒரு request-ஐ அவற்றுக்குள்ள follow பண்ணுங்க:

```flow
User -> 1 Interface | chat, in-app button, email, WhatsApp, API
1 Interface -> 2 Context assembly | system prompt + user input + history
3 Retrieval | company documents, data-ல search பண்றது -> 2 Context assembly
2 Context assembly -> 6 Guardrails on input | topic limits, personal data, injection checks
6 Guardrails on input -> 4 Model | பதிலை எழுதும், இல்ல tool use பண்ண கேக்கும்
4 Model -[tool வேணும்னு கேக்குது]-> 5 Tools | order-ஐ பார்க்குறது, ticket உருவாக்குறது
5 Tools -[result திரும்ப]-> 4 Model
4 Model -> 6 Guardrails on output | policy rules, format, காப்பாத்த முடியாத வாக்குறுதிகள் இல்லை
6 Guardrails on output -> 7 Human checkpoint | தப்புகள் costly-ஆ இருக்குற இடத்துல review அல்லது approve
7 Human checkpoint -> User-க்கு பதில் -> 8 Evaluation and monitoring | quality, cost, feedback
```

| பாகம் | என்ன பண்ணுது | Fail ஆனா |
| --- | --- | --- |
| **Interface** | User product-ஐ சந்திக்குற இடம் | குழப்பமான அல்லது மறைஞ்ச feature |
| **Context assembly** | Instructions, input, history-ஐ சேர்க்குது | Model task-ஐ தப்பா புரிஞ்சுக்கும் |
| **Retrieval (RAG)** | Company data-ல இருந்து தொடர்புள்ள facts-ஐ எடுத்து வருது | தப்பான அல்லது பழைய பதில்கள் |
| **Model** | பதிலை உருவாக்குது | கஷ்டமான tasks-ல weak reasoning |
| **Tools** | Model கேக்கக்கூடிய actions | தப்பான action, இல்லன்னா எதுவுமே இல்லை |
| **Guardrails** | Input, output மேல checks | Unsafe அல்லது policy-க்கு வெளியே replies |
| **Human checkpoints** | Costly cases-க்கு review அல்லது approval | Costly தப்புகள் customers-கிட்ட போயிடும் |
| **Evaluation and monitoring** | Release-க்கு முன்னாடி test sets; அப்புறம் tracking | பிரச்சனைகளை நீங்க இல்ல, customers கண்டுபிடிப்பாங்க |

இந்த lesson Mumbai-ல ஒரு bank-ல product manager-ஆ இருக்குற Ritu-வை follow பண்ணும்; bank-ஓட assistant ஒரு customer-க்கு நடக்காத fee waiver-ஐ ஏன் வாக்குறுதி கொடுத்துச்சுன்னு அவங்க trace பண்றாங்க. Lesson முடியும்போது, ஒரு பதில் ஏன் தப்பு, என்ன மாறணும்னு இந்த படத்தை வச்சு explain பண்ண முடியும்.

## இது எப்படி work ஆகுது

### Quality எங்க இருந்து வருது

தப்பான பதில்கள் பெரும்பாலும் நாலு இடங்கள்ல ஒண்ணுல இருந்து வரும்:

1. **காணாம போன அல்லது பழைய தகவல்**: retrieval தப்பான document-ஐ கண்டுபிடிச்சது, இல்லன்னா சரியான document இல்லவே இல்லை.
2. **தெளிவில்லாத instructions**: இந்த situation-ல என்ன பண்ணணும்னு system prompt சொல்லல.
3. **Task-க்கு weak-ஆன model**: நடக்கலாம், ஆனா மக்கள் நினைக்கிறதை விட குறைவு.
4. **Output மேல check இல்லாதது**: user பார்க்குறதுக்கு முன்னாடி எதுவும் அந்த தப்பை பிடிக்கல.

ஏதாவது தப்பா போகும்போது, பெரிய model கேக்குறதுக்கு முன்னாடி எந்த பாகம் fail ஆச்சுன்னு கேளுங்க.

### Cost எங்க இருந்து வருது

ஒவ்வொரு request-க்கும் செலவு:

- input (prompt, history, retrieve பண்ண text), output ரெண்டுக்கும் **model tokens**;
- retrieval, tools, infrastructure.

நீளமான prompts, நீளமான பதில்கள் cost அதிகம். பெரிய models ஒரு token-க்கு cost அதிகம். ரெண்டு பொதுவான சேமிப்புகள்: prompts-ல repeat ஆகுற பகுதிகளை **caching** பண்றது, எளிய requests-ஐ சின்ன, மலிவான models-க்கு **routing** பண்றது.

### Risk எங்க இருந்து வருது

Confident-ஆன தப்பான பதில்கள், checks இல்லாம எடுக்குற actions, வெளியே வர்ற personal data, **prompt injection** (model படிக்குற documents அல்லது emails-க்குள்ள மறைச்சு வச்ச instructions), நியாயமில்லாத outcomes. Controls: guardrails, tools மேல permissions, human review, evaluation.

### Prompting, retrieval, fine-tuning-ல எது?

| Approach | எதை மாத்துது | மாத்த வேகம், cost | எப்போ use பண்றது |
| --- | --- | --- | --- |
| **Prompting** | Instructions, examples | வேகம், மலிவு | Behaviour, tone, format |
| **Retrieval (RAG)** | ஒவ்வொரு request-க்கும் model பார்க்குற facts | நடுத்தரம் | Current அல்லது private தகவல் |
| **Fine-tuning** | Training மூலமா model-ஓட பழக்கங்கள் | மெதுவு, costly | Scale-ல ஒரு குறிப்பிட்ட style அல்லது skill |

பெரும்பாலான products prompting, retrieval-ல ஆரம்பிக்கும்; நிறைய products-க்கு fine-tuning தேவையே படாது.

### Agents

Tool calls-ஓட முழு வரிசையையும் model தானே முடிவு பண்ணும்போது, அந்த product ஒரு **agent**. Agents flexible, ஆனா predict பண்ண கஷ்டம்; அதனால அவை என்ன பண்ணலாம்னு limits, ஒவ்வொரு step-ஓட logs, risky actions-க்கு approvals வேணும். Fixed workflows work ஆகுற இடத்துல அவற்றை use பண்ணுங்க; flexibility-க்கு பலன் இருக்குற இடத்துல agents.

### Product manager-ஓட levers

**எப்படின்னு** engineers முடிவு பண்றாங்க. **என்ன, எவ்வளவு நல்லா**ன்னு நீங்க முடிவு பண்றீங்க:

- User problem, success metric;
- எந்த actions-க்கு approval வேணும்;
- எந்த failures ஏத்துக்கலாம், எவை கூடாது;
- ஒரு request-க்கான budget;
- Evaluation set எதை cover பண்ணணும்.

## ஒரு example

Ritu, Mumbai-ல ஒரு bank-ஓட mobile app-ல credit card charges பத்தின customers கேள்விகளுக்கு பதில் சொல்ற feature-க்கு product manager.

**Complaint.** Assistant ஒரு customer-கிட்ட, அவங்க ₹2,500 annual fee waive ஆகும்னு சொல்லுச்சு. ஆகல, customer-க்கு charge ஆச்சு.

Ritu-வும் engineers-உம் அந்த request-ஐ பாகங்கள் வழியா trace பண்றாங்க:

| பாகம் | என்ன கண்டுபிடிச்சாங்க | பிரச்சனையா? |
| --- | --- | --- |
| Interface | In-app chat, சாதாரணமா வேலை செய்யுது | இல்லை |
| Context assembly | Bank documents-ல இருந்து மட்டும் பதில் சொல்லணும்னு system prompt சொல்லுது | இல்லை |
| Retrieval | காலாவதி ஆன போன வருஷ fee-waiver offer-ஐ திருப்பி தந்துச்சு | **ஆமா: காரணம் இது** |
| Model | கொடுத்த document-ல இருந்து விசுவாசமா பதில் சொல்லுச்சு | இல்லை |
| Guardrails | Fees பத்தின வாக்குறுதிகளை நிறுத்த எந்த rule-உம் இல்லை | **ஆமா: ஒரு control இல்லை** |
| Evaluation | காலாவதி ஆன offers பத்தின test questions எதுவும் இல்லை | **ஆமா: ஒரு gap** |

**பாகம் வாரியா fixes:**

- **Retrieval:** documents-ஐ valid-from, valid-until dates வச்சு filter பண்ணுங்க; அப்போ காலாவதி ஆன offers திருப்பி வராது.
- **Guardrails:** waivers அல்லது refunds-ஐ assistant வாக்குறுதி கொடுக்குறதை block பண்ணுங்க; அதுக்கு பதிலா அது "You may be eligible. Here is how to check,"ன்னு ஒரு link-ஓட சொல்லும்.
- **Evaluation:** காலாவதி ஆன, வரப்போற offers உட்பட 30 fee கேள்விகளை test set-ல சேர்ங்க.
- **Monitoring:** ஒரு புது metric, 10,000 chats-க்கு தப்பான fee தகவல் பத்தின complaints; வாரம் வாரம் review.

யாருக்கும் வேற model தேவைப்படல. பதில் தப்பா இருந்ததுக்கு காரணம், model-க்கு என்ன கொடுக்கப்பட்டுச்சு, யாரும் எதை check பண்ணலைங்குறதுதான்.

## பொதுவா பண்ற தப்புகள்

- **ஒவ்வொரு தப்புக்கும் model-ஐ குறை சொல்றது.** நிறைய தப்புகள் data, retrieval அல்லது இல்லாத checks-ல இருந்து வருது.
- **Prompt-ஐ ஒரு secret sauce-ஆ நினைக்கிறது.** அது ஒரு பாகம் தான்; evaluation, data அதை விட முக்கியம்.
- **ஒரு request-க்கான cost-ஐ கவனிக்காம விடுறது.** Users விரும்புற ஒரு feature, scale-ல நஷ்டம் தரலாம்.
- **Evaluation set இல்லாதது.** அது இல்லாம ஒவ்வொரு மாற்றமும் ஒரு ஊகம்.
- **Default-ஆ agents.** Fixed workflows work ஆகுற இடத்துல அவற்றை use பண்ணுங்க.
- **Documents-க்கு owner இல்லாதது.** Retrieval அதுக்கு பின்னாடி இருக்குற content எவ்வளவு நல்லதோ அவ்வளவு தான்.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற Chip Huyen-ஓட "Building a Generative AI Platform"-ஐ படிங்க, LLM-based systems build பண்ண Eugene Yan-ஓட patterns-ஐ மேலோட்டமா பாருங்க.

1. **வரைஞ்சு பாருங்க.** நீங்க use பண்ற ஒரு AI feature-ஐ எடுங்க; banking chatbot, shopping assistant, email writer மாதிரி; அதோட வாய்ப்புள்ள பாகங்களை வரைங்க.
2. **Failures-ஐ trace பண்ணுங்க.** அந்த feature-ஓட மூணு சாத்தியமான failures-க்கு, ஒவ்வொண்ணுக்கும் காரணமா இருக்க வாய்ப்புள்ள பாகத்தையும் ஒரு fix-ஐயும் சொல்லுங்க.
3. **உங்க முடிவுகள்.** அதுக்கு ஒரு product manager எடுக்க வேண்டிய முடிவுகளை list பண்ணுங்க: metric, approval points, ஏத்துக்கக்கூடிய தப்புகள், ஒரு request-க்கான budget.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு பதில் ஏன் தப்பு, நீங்க என்ன மாத்தணும்னு நினைக்கிறீங்கன்னு ஒரு engineer-கிட்ட இந்த படத்தை வச்சு explain பண்ண முடியும்.
