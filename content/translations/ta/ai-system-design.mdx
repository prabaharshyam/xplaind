## இது என்ன

**AI system design** என்பது, ஒரு AI product-ஐ கட்டுறதுக்கு முன்னாடி அல்லது கட்டும்போதே paper-ல திட்டமிடுறது. அது யாருக்கு சேவை பண்ணுது, வெற்றியை எப்படி அளக்கிறோம், அதோட components, ஒரு request அவற்றுக்குள்ள எப்படி போகுது, எங்க fail ஆகலாம், production-ல எப்படி evaluate பண்ணி ஓட்டுறோம்ங்கிறதை உள்ளடக்கும். ஒரு குட்டி design document, team முடிவுகள்ல ஒத்துக்க, risks-ஐ சீக்கிரம் கண்டுபிடிக்க, clients, reviewers-க்கு system-ஐ விளக்க உதவும்.

```flow
User, ஒரு underwriter -> Web app -> API service -> Input guardrails
Input guardrails -> Hybrid search | department filter + effective date
Hybrid search -> Reranker -[top 5]-> Insurer-ஓட cloud region-ல Model
Insurer-ஓட cloud region-ல Model -[outage]-> Fallback model
Insurer-ஓட cloud region-ல Model -> Output guardrails -> Citation links-ஓட Answer
Fallback model -> Output guardrails
```

இதை சுத்தி: mask பண்ணின tracing, CI-ல evals, latency, cost, feedback, refusals-க்கு dashboards.

இந்த lesson, Mumbai-ல ஒரு general insurer-ஓட internal underwriting assistant-க்கான design-ஐ பின்தொடருது.

## இது எப்படி work ஆகுது

ஒரு practical design document, ரெண்டுல இருந்து நாலு pages, இதை உள்ளடக்கும்:

**1. Users, goals.** யார் use பண்றாங்க, என்ன task-க்கு, baseline-ஓட success metric (உதாரணத்துக்கு, "policy கேள்விகளுக்கு பதில் சொல்ற median நேரத்தை 6 நிமிஷத்துல இருந்து 2-க்கு கீழ குறைக்கணும்").

**2. Requirements, constraints.** Volume, peak load, latency budget, ஒரு request-க்கு cost, languages, data residency, privacy, compliance rules, யார் எந்த data-வை பார்க்கலாம்.

**3. Components.** Interface; API service; retrieval (document ingestion, parsing, chunking, embeddings, index, hybrid search, reranking); prompt, model choices (கூடவே ஒரு fallback model); tools; guardrails; மனித review points; logging, tracing, evaluation.

**4. Request flow.** ஒரு request-க்கு என்ன நடக்குதுன்னு step by step, ஒவ்வொரு step-லயும் கடத்தப்படுற data-வோட. ஒரு எளிமையான diagram உதவும்.

**5. Failure modes, guards.** ஒவ்வொரு component-க்கும், என்ன தப்பா போகலாம், அதை எது பிடிக்கும்:

- retrieval misses → hybrid search, metadata filters, recall-ஐ evaluate பண்றது;
- hallucination → grounding, citations, sources அமைதியா இருந்தா மறுக்கிறது;
- injection → குறைந்தபட்ச privilege, data-வை mark பண்றது, approvals;
- provider outage → retries, fallback model, அழகான error;
- கட்டுப்பாடில்லாத cost → caps, budgets, alerts;
- பழைய data → re-indexing pipeline, freshness alerts.

**6. Evaluation.** Test set (அளவு, sources, categories), retrieval, answers-க்கான metrics, launch bar, CI-ல regressions எப்படி பிடிக்கப்படுது.

**7. Operations.** Deployment, monitoring signals, alerts, on-call, release process, data retention.

**8. Open questions, trade-offs.** இன்னும் முடிவு பண்ணாதது, அவற்றோட options.

நீங்க interview-க்கு இல்லாம கட்டிக்கிட்டு இருந்தா, முதல் நாளே எல்லா boxes-ஐயும் வரையாம, system-ஐ ஒரு நேரத்துல ஒரு layer-ஆ வளருங்க. AI app-ஐ layers-ஆ வளர்க்குற lesson (context, guardrails, router, gateway, caches, agents) அந்த வரிசையை பேசும்.

**ஒரு failure-mode table:**

| Component | என்ன தப்பா போகலாம் | Guard |
| --- | --- | --- |
| Parsing | Scan பண்ணின tables குழம்பிப் போகும் | Table extraction; flag பண்ணின pages review |
| Retrieval | Superseded circulars முதல்ல rank ஆகும் | Effective-date filter |
| Retrieval | சரியான passage தவறும் | Hybrid search, reranker, recall track |
| Generation | Support இல்லாத claims | Citations கட்டாயம்; sources அமைதியா இருந்தா மறுப்பு |
| Documents | Upload ஆன files-ல injection | Write tools இல்ல; content data-ஆ நடத்தப்படும் |
| Provider | Outage அல்லது rate limits | Retries, fallback model, தெளிவான message |
| Cost | கட்டுப்பாடில்லாத usage | ஒரு user-க்கு caps, தினசரி budget alert |

**ஒரு design-ஐ review பண்றது.** User-ஓட tap-ல இருந்து answer வரை ஒரு request-ஐ நடந்து பாருங்க. ஒவ்வொரு box-லயும் மூணு கேள்விகள் கேளுங்க: இங்க என்ன data இருக்கு, யார் அதை பார்க்கலாம், இந்த பகுதி fail ஆனா அல்லது மெதுவா இருந்தா என்ன ஆகும். ஒரு security அல்லது compliance reviewer-ஐ walk-through-க்கு சீக்கிரமே கூப்பிடுங்க. "இந்த data எங்க store ஆகுது?" மாதிரி கேள்விகள் முதல் வாரத்துல மலிவு, பத்தாவது வாரத்துல costly.

**அதை புதுசாவே வச்சிருக்கிறது.** Document-ஐ உயிரோட இருக்கும் ஒண்ணா நடத்துங்க. ஒரு முடிவு மாறும்போது, page-ஐ update பண்ணி, முடிவுல ஒரு குட்டி decision log-ல தேதி, காரணத்தை குறிங்க. அப்ப புது team members, client reviewers chat threads-ல இருந்து வரலாற்றை மறுகட்டமைக்காம, ஒரு சரியான page-ஐ படிப்பாங்க.

**Code-ல back-of-envelope numbers.** Capacity, rate limits, cost பல design choices-ஐ முடிவு பண்ணும்; boxes-ஐ வரையறதுக்கு முன்னாடி அவற்றை கணக்கிடுங்க:

```python
def estimate(daily_requests, busy_hours=8, peak_factor=2.5,
             in_tokens=3_500, out_tokens=350, price_in=3, price_out=15, usd_to_inr=84,
             tpm_limit=400_000):
    """Prices in USD per million tokens; check current prices and note the date."""
    peak_per_min = daily_requests / (busy_hours * 60) * peak_factor
    tokens_per_min = peak_per_min * (in_tokens + out_tokens)
    cost_day = daily_requests * (in_tokens * price_in + out_tokens * price_out) / 1e6 * usd_to_inr
    return {
        "peak requests per minute": round(peak_per_min, 1),
        "peak tokens per minute": round(tokens_per_min),
        "within rate limit": tokens_per_min < tpm_limit,
        "cost per day ₹": round(cost_day),
        "cost per month ₹": round(cost_day * 30),
    }

print(estimate(daily_requests=20_000))
```

Peak tokens per minute provider limit-ஐ தாண்டினா, design-க்கு ஒரு உயர்ந்த tier, caching, சில steps-க்கு ஒரு சின்ன model அல்லது ஒரு queue தேவை. மாசாந்திர cost client-ஐ ஆச்சரியப்படுத்துச்சுன்னா, launch-க்கு பிறகு இல்ல, இப்பவே தெரிஞ்சுக்கோங்க.

**Latency budget, step by step.** ஒரு target-ஐயும், ஒவ்வொரு step-க்கும் ஒரு allowance-ஐயும் எழுதி, அதுக்கு எதிரா அளங்க:

| Step | Allowance (p95) |
| --- | --- |
| Auth, request-ஐ parse பண்றது | 50 ms |
| Query rewrite (சின்ன model) | 400 ms |
| Hybrid search | 150 ms |
| 30 candidates-ஐ reranking | 250 ms |
| Model, முதல் token வரை | 1,200 ms |
| முதல் token வரை மொத்தம் | கிட்டத்தட்ட 2 s |

இப்போ ஒவ்வொரு component owner-க்கும் ஒரு number இருக்கு. மொத்தம் நழுவும்போது, எந்த step தன் allowance-ஐ உடைச்சுதுன்னு trace காட்டும்.

**Layers-ல architecture.** Parts சேர்க்க ஒரு பயனுள்ள வரிசை, அத்தியாவசியமானதுல இருந்து விருப்பமானது வரை: நல்ல context-ஓட (retrieval, tools) model call; inputs, outputs மேல guardrails; ஒரு router, gateway (பல models, fallbacks, keys, budgets); caching; கடைசியா write actions-ஓட agent patterns. ஒவ்வொரு layer-ம் capability-ஐயும் புது failure modes-ஐயும் சேர்க்கும், அதனால அளந்த தேவை வரும்போது ஒண்ணை சேருங்க.

**Design முடிவுகள் records-ஆ.** Document-ல ஒரு குட்டி decision log வைங்க: தேதி, முடிவு, பரிசீலிச்ச options, காரணம், யார் ஒத்துக்கிட்டாங்க. உதாரணமா: "2026-11-02: reranker-ஓட hybrid search; vector-only policy codes-ஐ தவறவிட்டுச்சு (recall 71% vs 89%); client IT-யோட ஒத்துக்கிட்டோம்." பின்னாடி வர்ற reviewers, புது team members என்ன-ங்கிறது மட்டும் இல்ல, ஏன்னும் பார்ப்பாங்க.

**ஆரம்பிக்க ஒரு template.** Design document-ஐ repository-ல Markdown-ஆ, இந்த lesson-ஓட எட்டு headings, estimate output, latency budget, failure-mode table, decision log-ஓட store பண்ணுங்க. Code மாதிரியே pull requests-ல அதை review பண்ணுங்க.

## ஒரு worked example

Mumbai-ல ஒரு general insurer-ஓட internal assistant-க்கான design summary, 2,000 policy wordings, circulars, underwriting guidelines-ல இருந்து underwriters-ஓட கேள்விகளுக்கு பதில் சொல்லுது:

- *Goal*: underwriters-ஓட lookup நேரம் 6 நிமிஷத்துல இருந்து 2; launch bar, 120-கேள்வி test set-ல citations-ஓட 85% சரி, "documents-ல இல்ல" கேள்விகள்ல 100% மறுப்பு.
- *Constraints*: 300 users, peak-ல நிமிஷத்துக்கு 40 requests, முதல் token 2 s-க்கு கீழ, data இந்தியாவுல, department வாரியா access.
- *Components*: பழைய circulars-க்கு OCR-ஓட layout-aware parsing; section paths-ஓட 400-token chunks; department filters, reranker-ஓட hybrid search; ஒரு fallback-ஓட insurer-ஓட cloud region வழியா ஒரு நடுத்தர அளவு model; links-ஆ render ஆகுற citations; mask பண்ணின logs-ஓட tracing.
- *Failure modes*: superseded circulars (effective-date filter), scan பண்ணின tables (table extraction, flag பண்ணின pages), upload ஆன documents வழியா injection (write tools இல்ல), outage (fallback, அப்புறம் ஒரு தெளிவான message).
- *Evaluation*: recall at 5, calibrate பண்ணின judge மூலம் answer correctness, மாசத்துக்கு 30 answers-ஐ underwriter review; CI-ல fast checks.
- *Operations*: container service, latency, cost, feedback, refusal rate-க்கு dashboards, இரவு re-indexing.

Document-க்கு ரெண்டு நாள் ஆச்சு, முதல் வாரத்துல compliance team data residency பத்தி கேட்டப்போ ஒரு மாச rework-ஐ தவிர்த்துச்சு.

| Design element | முடிவு |
| --- | --- |
| Goal | Lookup நேரம் 6 நிமிஷத்துல இருந்து 2 |
| Launch bar | 120 கேள்விகள்ல citations-ஓட 85% சரி; scope-க்கு வெளியே இருக்கறதுக்கு 100% மறுப்பு |
| Constraints | 300 users, peak-ல நிமிஷத்துக்கு 40 requests, முதல் token 2 s-க்கு கீழ, data இந்தியாவுல |
| பலன் | Compliance-ஓட முதல் வார residency கேள்விக்கு document-ல இருந்தே பதில், ஒரு மாச rework தவிர்ப்பு |

## பொதுவா பண்ற தப்புகள்

- **User, metric-ல இருந்து இல்லாம model-ல இருந்து ஆரம்பிக்கிறது.**
- **Failure analysis இல்லாம இருக்கிறது.** ஒவ்வொரு component-ம் எப்படியாவது fail ஆகும்.
- **Evaluation plan இல்ல.** "எப்படி போகுதுன்னு பார்ப்போம்" ஒரு plan இல்ல.
- **Constraints-ஐ புறக்கணிக்கிறது.** Latency, cost, data rules design-ஐ வடிவமைக்கும்.
- **யாரும் படிக்காத நீளமான documents.** ரெண்டுல இருந்து நாலு தெளிவான pages.
- **Capacity, cost estimate-ஐ தவிர்த்து**, launch-க்கு பிறகு rate limits-ஐயோ bill-ஐயோ கண்டுபிடிக்கிறது.
- **முழு system-க்கும் ஒரே latency target**, ஒவ்வொரு step-க்கும் allowance இல்லாம.
- **பதிவு பண்ணாத காரணத்தோட design முடிவுகள்**, அதனால மாசாமாசம் மறுபடி வாதாடப்படும்.

## எப்போ முழு design document அதிகம்

- **ஒரு idea-ஐ test பண்ண ஒரு வார prototype**: goal, data, success measure-ஓட அரைப் பக்க note போதும்.
- **கொஞ்சம் users, sensitive data இல்லாத ஒரு சின்ன internal tool.**
- **ஏற்கனவே இருக்குற system-க்குள்ள ஒரு மாற்றம்**, அதுக்கு புது document இல்ல, அதோட design document-ஐ update பண்ணணும்.

## Demo-ல இருந்து production-க்கு

- **Design document-ஐ repository-ல வைங்க**, ஒவ்வொரு பெரிய மாற்றத்தோடயும் update பண்ணி.
- **Traffic, models அல்லது prices மாறும்போது capacity, cost estimate-ஐ மறுபடி ஓட்டுங்க.**
- **ஒவ்வொரு step-ஐயும் அதோட latency allowance-க்கு எதிரா** traces-ல இருந்து அளங்க.
- **Decision log-ஐ** தேதி, காரணத்தோட maintain பண்ணுங்க.
- **ஒவ்வொரு incident-க்கு பிறகும் failure modes-ஐ review பண்ணி** புது rows சேருங்க.

## Practice பண்ணுங்க

கீழ இணைச்சிருக்குற LLM-based systems கட்டுறதுக்கான Eugene Yan-ஓட patterns-ஐ படிங்க.

இந்த lesson-ஓட check ஒரு project: ஒரு AI product-க்கு users, success metrics, components, request flow, failure modes, guards, evaluation, operations-ஐ உள்ளடக்கிய ரெண்டுல இருந்து நாலு page design document எழுதுங்க.

இன்னும் ஆழமா படிக்க, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 10 AI application architecture-ஐ layer by layer-ஆவும், chapter 9 latency, cost-ஐயும் பேசுது.

**இது முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒருத்தரை உங்க design வழியா பத்து நிமிஷத்துல நடத்தி கூட்டிட்டுப் போக முடியும்போது, ஒவ்வொரு component-க்கும் "இந்த part fail ஆனா என்ன ஆகும்?" ன்னு பதில் சொல்ல முடியும்போது.
