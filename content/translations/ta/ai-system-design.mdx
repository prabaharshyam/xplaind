## இது என்ன

**AI system design**-னா ஒரு AI product எதெல்லாம் வச்சு செய்யப்பட்டிருக்குன்னு paper-லயே முடிவு பண்ணி, அது work ஆகும்னு numbers வச்சு நிரூபிக்கிறது. ஒரு நல்ல design ஆறு கேள்விகளுக்கு பதில் சொல்லும்: parts என்ன, ஒவ்வொரு arrow-வையும் எந்த data தாண்டுது, ஒரு request-க்கு எவ்வளவு cost, user எவ்வளவு நேரம் காத்திருக்கணும், எது உடையும், அது நமக்கு எப்படி தெரியும், quality-ஐ எப்படி measure பண்ணுவோம்?

"Design interview" lesson ஒரு design-ஐ நேரக் கட்டுப்பாட்டுக்குள்ள present பண்றதைப் பத்தி பேசுது; அதுக்குள்ள என்ன இருக்கணும்னு இந்த lesson பேசுது.

Documents-ல இருந்து பதில் சொல்ற ஒரு product-க்கு ரெண்டு pipelines இருக்கு: **ingestion** offline-ஆ ஓடி documents-ஐ ஒரு index-ஆ மாத்துது; **request path** ஒவ்வொரு கேள்விக்கும் ஓடுது. பெரும்பாலான quality problems ingestion-ல தான் ஆரம்பிக்குது, அதனால ரெண்டையும் வரைங்க.


இந்த lesson ஒரே ஒரு design-ஐ follow பண்ணுது: Mumbai-ல இருக்குற ஒரு general insurer-ல 300 underwriters-க்கான ஒரு assistant, 2,000 policy wordings, circulars, guidelines-ல இருந்து பதில் சொல்லுது. எல்லா volumes, token counts, timings-உம் இந்த design-ஓட assumptions தான், ஒரு நிஜ insurer-ல எடுத்த measurements இல்ல.

## இது எப்படி work ஆகுது

### User-ல இருந்தும் constraints-ல இருந்தும் ஆரம்பிங்க

Goal-ஐ ஒரு baseline கூட ஒரு metric-ஆ எழுதுங்க: "ஒரு policy கேள்விக்கு பதில் கண்டுபிடிக்க ஆகுற median time, 6 minutes-ல இருந்து 2-க்கு கீழ." அப்புறம் ஒரு box-ஐயோ ஒரு number-ஐயோ மாத்துற constraints-ஐ list பண்ணுங்க.

- **பதிலை யார் படிக்கிறாங்க, தப்பான பதிலுக்கு என்ன விலை?** Train ஆன ஒரு underwriter தான், ஆனா ஒரு தப்பான exclusion ஒரு policy-க்கு தப்பான price போட வச்சுடும். அதனால ஒவ்வொரு பதிலும் ஒரு clause-ஐ cite பண்ணும்.
- **Volume-உம் peaks-உம்.** 300 users, ஒவ்வொருத்தரும் ஒரு working day-க்கு சுமார் 25 கேள்விகள், பெரும்பாலும் 8 busy hours-க்குள்ள.
- **Data rules.** Documents, index, logs இந்தியாவுக்குள்ளயே இருக்கும். Model calls இந்தியாவுக்கு வெளியே process ஆகலாமான்னு compliance team தான் முடிவு பண்ணணும்; ஒரு provider-ஐ நேரடியா call பண்றதா, அல்லது தேர்ந்தெடுத்த model-ஐ இந்தியாவுல குடுக்குற ஒரு cloud provider-ஓட regional endpoint இருந்தா அதை use பண்றதான்னு அந்த முடிவு தான் தீர்மானிக்கும். முதல் வாரத்துலயே கேளுங்க.
- **Access.** Motor underwriters health reinsurance treaties-ஐ பார்க்கக் கூடாது; இந்த rule search-ஓட வடிவத்தையே தீர்மானிக்குது.

### ஒவ்வொரு design-உம் சொல்ல வேண்டிய decisions

Boxes-ஓட ஒரு list design ஆகாது. பெரிய choices-ஐயும் ஒவ்வொண்ணுக்கான காரணத்தையும் சொல்லுங்க.

| Decision | இந்த design-ஓட choice | இதை எப்போ மாத்தணும் |
| --- | --- | --- |
| Prompt மட்டும், retrieval அல்லது fine-tuning | Retrieval: documents மாசா மாசம் மாறுது, பதில்களுக்கு citations வேணும் | தேவை knowledge இல்ல, volume-ல format அல்லது style-னா ("Prompting, RAG அல்லது fine-tuning" பாருங்க) |
| Long context அல்லது retrieval | Retrieval: சுமார் 25 million tokens documents, ஒரு 1-million-token window-க்கு எதிரா | Corpus சின்னதா, நிலையா இருந்து, caching அதை மலிவா வச்சா |
| Model tier | பதில்களுக்கு mid-sized model; query rewriting-க்கு small model | ஒரு முழு category-க்கு small model launch bar-ஐ தொட்டா |
| Hosted API அல்லது self-hosted open weights | Hosted, region-ஐ compliance முடிவு பண்ணும் | Data உங்க servers-ஐ விட்டு போகக் கூடாதுன்னா, அல்லது நிலையான volume GPUs-ஐ busy-ஆ வச்சா |
| Vector store | Vector extension கூட Postgres | Index ஒரு machine-ஐ விட பெருசானா |
| Streamed அல்லது batch | Streamed: ஒரு ஆள் காத்திருக்காங்க | யாரும் காத்திருக்கலைன்னா: batch API-க்கு பாதி cost தான் |

Database-ஐ தேர்ந்தெடுக்கிறதுக்கு முன்னாடி index-ஐ size பண்ணுங்க. 2,000 documents, ஒவ்வொண்ணும் சராசரியா 25 pages, ஒரு page-க்கு சுமார் 500 tokens-னு வச்சுக்கோங்க: 25 million tokens, அதாவது 400 tokens-ஓட 62,500 chunks. ஒரு embedding-க்கு 1,024 numbers, ஒவ்வொண்ணும் 4 bytes-னா, அது சுமார் 256 MB vectors; ஒரு சாதாரண server-ஓட memory-லயே அடங்கிடும். ஒரு distributed vector database எந்த லாபமும் இல்லாம cost-ஐ மட்டும் கூட்டும்.

### ஒரு request-ஐ trace பண்ணுங்க, ஒவ்வொரு step-லயும் இருக்குற data கூட

ஒவ்வொரு step-உம் எதை வாங்குது, எதை அடுத்ததுக்கு அனுப்புதுன்னு note பண்ணுங்க; privacy, cost problems இங்க தான் தெரியவரும்.

1. **API service.** கேள்வி, user id, department-ஐ வாங்குது; daily cap-ஐ தாண்டின users-ஐ reject பண்ணுது.
2. **Input checks.** Log பண்றதுக்கு முன்னாடி policy, phone numbers-ஐ mask பண்ணுது; model-க்கு instructions குடுக்க முயற்சி பண்ற text-ஐ flag பண்ணுது.
3. **Query rewrite.** ஒரு small model "does the fire one cover riots" மாதிரி ஒரு கேள்வியை policy name கூட ஒரு query-ஆ மாத்துது: சுமார் 300 tokens உள்ள, 40 வெளிய.
4. **Hybrid search.** Keyword search-உம் vector search-உம் parallel-ஆ ஓடுது, department, effective date வாரியா filter பண்ணி. Embeddings அடிக்கடி miss பண்ற policy codes, clause numbers மாதிரி exact strings-ஐ keyword search பிடிச்சுடும்.
5. **Reranker.** Top 40 candidates-க்கு score போட்டு 6-ஐ வச்சுக்குது.
6. **Main model.** சுமார் 1,500 tokens fixed instructions (ஒவ்வொரு call-லயும் அப்படியே இருக்கும், அதனால cache ஆகும்), 2,700 புது tokens வாங்குது: 400 tokens-ஓட ஆறு passages-உம் கேள்வியும். அது சுமார் 350 tokens எழுதுது.
7. **Citation check.** சாதாரண code: cite பண்ண ஒவ்வொரு clause id-உம் அனுப்பின passages-ல இருக்கணும்; இல்லைன்னா பதில் refuse ஆகி ஒரு ஆளுக்கு route ஆகும்.

Access control step 4-ல இருக்கு. பதில் வந்ததுக்கு அப்புறம் filter பண்ணா, user பார்க்கக் கூடாத text-ஐ model ஏற்கனவே படிச்சிருக்கும்.

### Boxes-க்கு முன்னாடி numbers: load, limits, cost

```python
# Anthropic list prices, US dollars per million tokens, checked 28 November 2026
SONNET = {"in": 2.00, "cache_read": 0.10, "out": 10.00}   # Claude Sonnet 5.5
HAIKU = {"in": 0.10, "out": 0.50}                          # Claude Haiku 5.5, prompts up to 100,000 tokens

def estimate(users=300, questions_per_user=25, work_days=22, busy_hours=8, peak_factor=2.5,
             cached_in=1_500, fresh_in=2_700, out=350,   # main model, tokens per question
             rewrite_in=300, rewrite_out=40,             # small model rewrites the query
             usd_to_inr=94, fixed_inr_month=60_000):     # suppose: search, hosting, tracing
    daily = users * questions_per_user
    peak_per_min = daily / (busy_hours * 60) * peak_factor
    usd = ((fresh_in * SONNET["in"] + cached_in * SONNET["cache_read"] + out * SONNET["out"])
           + (rewrite_in * HAIKU["in"] + rewrite_out * HAIKU["out"])) / 1e6
    month_inr = daily * work_days * usd * usd_to_inr + fixed_inr_month
    return {
        "peak questions a minute": round(peak_per_min),
        "peak uncached input tokens a minute": round(peak_per_min * fresh_in),
        "peak output tokens a minute": round(peak_per_min * out),
        "model cost per question (rupees)": round(usd * usd_to_inr, 2),
        "model spend a month (US dollars)": round(daily * work_days * usd),
        "total a month (rupees)": round(month_inr),
        "per user a month (rupees)": round(month_inr / users),
    }

print(estimate())
# {'peak questions a minute': 39, 'peak uncached input tokens a minute': 105469,
#  'peak output tokens a minute': 13672, 'model cost per question (rupees)': 0.86,
#  'model spend a month (US dollars)': 1502, 'total a month (rupees)': 201141,
#  'per user a month (rupees)': 670}
```

ஒரு dollar-க்கு ₹94-உம், ₹60,000 fixed costs-உம் உதாரணத்துக்கு மட்டும் தான். இதை published limits கூட compare பண்ணுங்க. Claude API-ல, November 2026 நிலவரப்படி, மிகக் குறைந்த standard tier (Start) Sonnet 5.5-க்கு ஒரு minute-க்கு 2,000,000 input tokens-உம் 400,000 output tokens-உம் அனுமதிக்குது. Cache reads input limit-ல count ஆகாது. அதனால peak load அதுல சுமார் 5% தான் use பண்ணுது: rate limit பிரச்சனை இல்ல.

Monthly bill தான் பிரச்சனை. ஒவ்வொரு tier-க்கும் ஒரு monthly spend cap இருக்கு: Start-க்கு $500, Build-க்கு $1,000, Scale-க்கு $200,000. மாசத்துக்கு சுமார் $1,500-னா, கீழ இருக்குற ரெண்டு tiers-ல எதுலயும் இந்த design மாசத்தோட நடுவுலயே நின்னுடும், retries-ஆல சரி பண்ண முடியாத errors கூட. Design எந்த tier அல்லது cloud contract-னு சொல்லணும், cap-ஐ விட குறைவான அளவுல ஒரு budget alert-ஐ set பண்ணணும். Cloud platforms அவங்களோட சொந்த quotas-ஐ வைக்கிறாங்க; Anthropic-ஓட pricing page-படி, அவங்களோட regional, multi-region endpoints global endpoints-ஐ விட 10% அதிகம் cost ஆகும். அதனால compliance தேர்ந்தெடுக்குற route-க்கு கணக்கை திரும்ப போடுங்க.

Fresh input தான் மிகப் பெரிய cost: ஒரு கேள்விக்கான $0.0091-ல $0.0054 (ஒரு million-க்கு $2-ல 2,700 tokens). 6 passages-க்கு பதிலா 4 அனுப்பினா சுமார் 18% மிச்சம், eval set-ல recall குறையாம இருந்தா. Cache writes-ஐ கணக்குல சேர்க்கல: இந்த traffic-ல cached prefix அரிதா தான் expire ஆகும். Fixed costs total-ல 30%, அதனால usage கூட கூட ஒரு user-க்கான cost குறையும்.

### ஒரு latency budget, step by step

Underwriters பதில் stream ஆகும்போதே படிக்கிறாங்க, அதனால target: 100 கேள்விகள்ல 95-க்கு (p95) முதல் text 2 seconds-க்குள்ள தெரியணும்.

| Step | Allowance (p95) |
| --- | --- |
| Login, cap, input checks | 50 ms |
| Query rewrite, small model | 300 ms |
| Hybrid search, keyword-உம் vector-உம் parallel-ஆ | 150 ms |
| 40 candidates-ஐ rerank பண்றது | 200 ms |
| Main model, முதல் token வர்ற நேரம் | 1,000 ms |
| Total, சுமார் 300 ms மிச்சம் வச்சு | 1.7 s |

p95-களை கூட்டினா உண்மையான p95-ஐ விட அதிகமா காட்டும், ஏன்னா எல்லா steps-உம் ஒரே நேரத்துல slow ஆகுறது அரிது; அதனால இந்த budget safe தான், exact இல்ல. Model, உதாரணமா, ஒரு second-க்கு 60 tokens stream பண்ணா, 350-token பதிலுக்கு இன்னும் சுமார் 6 seconds ஆகும். Total தாண்டும்போது, எந்த step அதோட allowance-ஐ மீறிச்சுன்னு trace காட்டும். முதல்ல cut பண்ண வேண்டிய step query rewrite தான்.

### Failure modes, அவற்றை எப்படி detect பண்றது, guard

| Component | என்ன தப்பா போகும் | உங்களுக்கு எப்படி தெரியும் | Guard |
| --- | --- | --- | --- |
| Parsing | Scan பண்ண tables குழம்பின text-ஆ மாறும் | ஒவ்வொரு document-க்கும் parse score | Table extraction; flag ஆன pages indexing-க்கு முன்னாடி check ஆகும் |
| Index | பழசாகிப்போன (superseded) ஒரு circular முதல் rank-ல வரும் | Eval set-ல இருக்குற dated trap questions fail ஆகும் | Effective-date filter; பழைய versions வச்சிருக்கப்படும், ஆனா mark பண்ணி |
| Search | சரியான clause miss ஆகும் | Eval set-ல recall at 5, வாரா வாரம் track பண்ணி | Hybrid search, reranker, query rewrite |
| Access | ஒரு user இன்னொரு department-ஓட treaty-ஐ பார்ப்பாங்க | ஒவ்வொரு department-ல இருந்தும் ஒரு user வச்சு CI test | Search-க்குள்ளயே permission filter |
| Model | Passages support பண்ணாத ஒரு claim | Citation check failures; sample பண்ண traffic-ல judge score | Passages-ல இருந்து மட்டும் பதில், இல்லைன்னா refuse |
| Documents | Upload பண்ண ஒரு file-ல ஒளிஞ்சிருக்குற instructions | Traces-ல injection flags | Write tools இல்ல; passages instructions இல்ல, data-னு mark பண்ணப்படும் |
| Provider | Outage, rate limit அல்லது ramp limit errors (429) | Error rate, fallback share | Backoff கூட retries, fallback model, தெளிவான message |

### Human review: எங்க, எவ்வளவு

Model மிகவும் பலவீனமா இருக்குற, தப்புகள் மிக அதிகமா செலவு வைக்குற இடங்கள்ல ஆளுங்களை வைங்க. இங்க, refuse ஆன, low score வாங்கின பதில்கள் ஒரு senior underwriter-கிட்ட போகும், புது circulars indexing-க்கு முன்னாடி check ஆகும், மாசத்துக்கு 30 பதில்கள் sample பண்ணப்படும்.

அப்புறம் அதை size பண்ணுங்க. ஒரு நாளைக்கு 7,500 கேள்விகள்ல 4% route ஆனா, அது 300 reviews. ஒவ்வொண்ணுக்கும் 3 minutes-னா, ஒரு நாளைக்கு 15 மணி நேரம், சுமார் ரெண்டு full-time reviewers. Client-ஆல அந்த அளவு ஆளுங்களை போட முடியலைன்னா, retrieval-ஐ சரி பண்ணுங்க, அல்லது குறைவான வகை கேள்விகளை route பண்ணுங்க. ஆள் இல்லாத ஒரு queue guard ஆகாது.

| Latency | p95-ல முதல் text 2 s-க்குள்ள; முழு பதில் சுமார் 8 s-ல |
| Components | OCR, table extraction கூட nightly ingestion; department, date filters கூட hybrid search; reranker; test பண்ண fallback கூட mid-sized model; citation check |
| Human review | சுமார் 4% கேள்விகள் senior underwriters-க்கு, சுமார் ரெண்டு reviewers-ஓட நேரம்; மாசத்துக்கு 30 பதில்கள் sample |
| Open questions | Model calls இந்தியாவை விட்டு போகலாமா? மாசத்துக்கு சுமார் $1,500-ஐ எந்த API tier அல்லது cloud contract cover பண்ணும்? |

எந்த code-உம் எழுதுறதுக்கு முன்னாடியே numbers என்ன மாத்திச்சு:

1. **Spend cap.** Bill ரெண்டு tiers-ஓட monthly caps-ஐ விட அதிகம், அதனால மூணாவது வாரத்துல service நின்னு போறதுக்கு பதிலா, ஒரு contract decision plan-லயே சேர்ந்துச்சு.
2. **Review queue.** Client "எப்போதாவது" review-னு நினைச்சிருந்தாங்க; ரெண்டு பேரோட மணி நேரங்களைப் பார்த்ததும் retrieval வேலைக்கும் ஒரு rota-க்கும் fund பண்ணாங்க.
3. **Vector store.** 256 MB vectors insurer-கிட்ட ஏற்கனவே இருக்குற Postgres-லயே அடங்குது: review பண்ண வேண்டிய vendor ஒண்ணு குறைவு.
4. **Compliance கேள்வி.** முதல் வாரத்துலயே எழுப்பினதால, gateway build ஆகுறதுக்கு முன்னாடியே model route முடிவாச்சு.

இப்போ ஒரு மாற்றத்தை வச்சு test பண்ணுங்க. அடுத்த வருஷம் 2,700 claims staff சேருறாங்கன்னு வச்சுக்கோங்க. Users பத்து மடங்கானா, peak-ல ஒரு minute-க்கு சுமார் 390 கேள்விகள், ஒரு minute-க்கு சுமார் 1.05 million uncached input tokens: இன்னும் Start tier-ஓட input limit-க்கு கீழ தான், ஆனா மாசத்துக்கு சுமார் $15,000. Fixed costs பகிர்ந்துக்கப்படுறதால, ஒரு user-க்கான cost சுமார் ₹490-க்கு குறையும். முதல்ல உடையுறது review queue தான்: 75,000-ல 4% ஒரு நாளைக்கு 3,000 reviews, அதனால route ஆகுற share-ஐ முதல்ல குறைக்கணும்.

## பொதுவா பண்ற தப்புகள்

- **Numbers இல்லாத boxes.** அறிகுறி: எந்த box-க்கும் owner-ஓ, latency allowance-ஓ, failure row-ஓ இல்ல, அதனால reviewers அதை challenge பண்ண முடியாது.
- **Request path-ஐ மட்டும் வரையுறது.** அறிகுறி: parsing, versions, effective dates எதுவும் இல்ல, ஒரு பழைய circular ஒரு user-ஐ அடையுற வரைக்கும்.
- **Rate limit-ஐ check பண்ணி spend cap-ஐ விட்டுடுறது.** அறிகுறி: "நம்ம tokens-per-minute limit-ஐ விட ரொம்ப கீழ", ஆனா monthly bill-உம் இல்ல, price check date-உம் இல்ல.
- **Generation-க்கு அப்புறம் access-ஐ filter பண்றது.** அறிகுறி: "restricted பதில்களை UI மறைச்சுடும்". Restricted text-ஐ model ஏற்கனவே படிச்சுடுச்சு.
- **Detection column இல்லாத failure table.** அறிகுறி: யாருமே கவனிக்காத failures-க்கு guards.
- **Size பண்ணாத human review.** அறிகுறி: "உறுதியில்லாத பதில்கள் ஒரு ஆள்கிட்ட போகும்", ஆனா share-உம், minutes-உம், team-உம் இல்ல.
- **ஒரு சின்ன eval set-ஐ நம்புறது.** அறிகுறி: 120 கேள்விகள்ல 2-point gain-ஐ வச்சு ஒரு model-ஐ தேர்ந்தெடுக்கிறது, அல்லது 20-க்கு 20 refusals-ஐ proof-னு சொல்றது.
- **யாரும் படிக்காத ஒரு நீளமான document.** ரெண்டுல இருந்து நாலு pages, summary table முதல்ல.

## எப்போ முழு design document அதிகம்

- **ஒரு வார prototype:** goal, data, success measure, ஒரு request-க்கு தோராயமான cost கூட அரை page போதும்.
- **ஒரு சின்ன internal tool**, குறைவான users, sensitive data இல்லாம.
- **ஏற்கனவே இருக்குற ஒரு system-க்குள்ள ஒரு மாற்றம்:** அதுக்கு பதிலா அதோட document-ஐயும் decision log-ஐயும் update பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- Traffic, models, token counts அல்லது prices மாறும்போதெல்லாம் **estimate-ஐ திரும்ப ஓட்டுங்க**, prices-க்கு date போடுங்க.
- வாரா வாரம் **traces-ஐ latency budget கூட compare பண்ணுங்க**.
- Fallback use, spend, refusal rate-க்கு alerts கூட, **ஒவ்வொரு detection signal-ஐயும் dashboard-ல போடுங்க**.
- **ஒவ்வொரு incident-க்கு அப்புறமும் ஒரு failure row சேருங்க.**
- **மாசா மாசம் human review-ஐ re-size பண்ணுங்க.**

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற, LLM-based systems-க்கான Eugene Yan-ஓட patterns-ஐ படிங்க. ஆழமா போக, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 10 AI application architecture-ஐ layer by layer cover பண்ணுது; chapter 9 latency, cost-ஐ cover பண்ணுது.

இந்த lesson-ஓட check ஒரு project: நீங்க தேர்ந்தெடுக்குற ஒரு AI product-க்கு ரெண்டுல இருந்து நாலு pages-ல ஒரு design document. இந்த ஏழும் இருந்தா pass:

1. ஒரு baseline கூட ஒரு success metric.
2. ஒரு peak-load, cost-per-user estimate, அதோட assumptions, நீங்க prices check பண்ண date கூட.
3. ஒவ்வொரு component வழியாவும் trace பண்ண ஒரு request, ஒவ்வொரு step-லயும் இருக்குற data கூட.
4. ஒவ்வொரு step-க்கும் ஒரு allowance கூட ஒரு latency budget.
5. குறைஞ்சது ஆறு rows இருக்குற ஒரு failure table, ஒவ்வொண்ணுக்கும் ஒரு detection signal, ஒரு guard கூட.
6. Category வாரியா ஒரு test set, ஒரு launch bar கூட.
7. Open questions-உம் ஒரு சின்ன decision log-உம்.

அப்புறம், worked example-ல பண்ண மாதிரி, ஒரு assumption-ஐ பத்தால multiply பண்ணி, முதல்ல எது உடையுதுன்னு note பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க design-ஐ பத்து minutes-ல ஒருத்தருக்கு walk through பண்ணவும், ஒவ்வொரு component-க்கும் "இதுக்கு என்ன cost, இது எவ்வளவு slow-ஆ இருக்கலாம், இது fail ஆனா என்ன ஆகும்?"-ங்குற கேள்விக்கு பதில் சொல்லவும் உங்களால முடியும்போது.
