## இது என்ன

**Big-O notation** input வளரும்போது algorithm பண்ற வேலை எப்படி வளருதுன்னு சொல்லும். எத்தனை seconds ஆகும்னு exact-ஆ சொல்லாது; curve-ஓட வடிவத்தை சொல்லும். Input-ஐ ரெண்டு மடங்கு ஆக்கினா, வேலை அப்படியே இருக்குமா, ரெண்டு மடங்கு ஆகுமா, நாலு மடங்கு ஆகுமா?

இது முக்கியம், ஏன்னா நிஜ data வளரும். 100 test orders-ஐ கண்ணிமைக்கிற நேரத்துல check பண்ற ஒரு script, Big Billion Days sale-ல ஒரு Flipkart seller பார்க்குற 10 lakh orders-க்கு ராத்திரி முழுக்க எடுக்கலாம். Code-ஐ run பண்றதுக்கு முன்னாடியே அதை Big-O-வால predict பண்ணி, scale ஆகுற approach-ஐ தேர்ந்தெடுக்கலாம்.

| வளர்ச்சி | பேரு | 1,000 items-க்கு வேலை | 10 lakh items-க்கு வேலை | Example |
|---|---|---|---|---|
| O(1) | Constant | 1 | 1 | Dict-ல ஒரு key-ஐ lookup பண்றது |
| O(log n) | Logarithmic | சுமார் 10 | சுமார் 20 | Sorted list-ல binary search |
| O(n) | Linear | 1,000 | 10 lakh | ஒவ்வொரு order-ஐயும் ஒரு தடவை check பண்றது |
| O(n log n) | Linearithmic | சுமார் 10,000 | சுமார் 2 crore | Orders-ஐ sort பண்றது |
| O(n²) | Quadratic | 10 lakh | 10 lakh crore | ஒவ்வொரு order-ஐயும் மத்த எல்லாத்தோடயும் compare பண்றது |

```flow
title: Input ரெண்டு மடங்கு ஆனா என்ன நடக்குது
Input ரெண்டு மடங்கு -> O(1) | அதே வேலை
Input ரெண்டு மடங்கு -> O(log n) | இன்னும் ஒரு step
Input ரெண்டு மடங்கு -> O(n) | ரெண்டு மடங்கு வேலை
Input ரெண்டு மடங்கு -> O(n²) | நாலு மடங்கு வேலை
```

பொதுவான classes, நல்லதுல இருந்து மோசமானது வரை: O(1), O(log n), O(n), O(n log n), O(n²). இதை விட மோசமானவையும் இருக்கு, O(2ⁿ) மாதிரி; அவை ரொம்ப சின்ன inputs-ல மட்டும் தான் work ஆகும்.

## இது எப்படி work ஆகுது

ஒரு code-ஓட Big-O கண்டுபிடிக்க, n வளரும்போது அதிகமா repeat ஆகுற step எத்தனை தடவை ஓடுதுன்னு எண்ணுங்க. அப்புறம் பெரிய term-ஐ மட்டும் வச்சுக்கிட்டு, constants-ஐ விட்டுடுங்க.

- n items மேல ஒரு loop, அதோட body-ஐ n தடவை ஓட்டும்: **O(n)**.
- ஒரே items மேல ஒரு loop-க்குள்ள இன்னொரு loop, n × n தடவை ஓடும்: **O(n²)**.
- Binary search மாதிரி ஒவ்வொரு step-லயும் problem-ஐ பாதியா ஆக்குறது, சுமார் log₂ n steps எடுக்கும்: **O(log n)**.
- Python-ஓட built-in `sorted` மாதிரி ஒரு நல்ல sort, சுமார் n × log n comparisons பண்ணும்: **O(n log n)**.
- ஒரு list item-ஐ position வச்சு, அல்லது dict value-ஐ key வச்சு படிக்க, collection எவ்வளவு பெருசா இருந்தாலும் ஒரே நேரம் தான்: **O(1)**.

Constants-ஐ விட்டுடுறோம், ஏன்னா அவை வடிவத்தை மாத்தாது. List மேல ரெண்டு தடவை loop பண்றது O(2n), ஆனா அதையும் O(n)-ன்னு தான் எழுதுறோம்: எப்படி இருந்தாலும் n-ஐ ரெண்டு மடங்கு ஆக்குனா வேலையும் ரெண்டு மடங்கு ஆகும். இதே காரணத்துக்காக சின்ன terms-ஐயும் விட்டுடுறோம்: O(n² + n) என்பது O(n²), ஏன்னா n 10 lakh-ஆ இருக்கும்போது n² பகுதி மீதியை அமுக்கிடும்.

**Space complexity** memory-க்கு அதே notation-ஐ use பண்ணுது. எல்லா order ID-க்கும் ஒரு set கட்ட O(n) extra space தேவை; amounts-ஐ கூட்ட O(1) போதும்.

ஒரு step ஒரு microsecond எடுத்தா, இந்த classes நடைமுறையில என்ன அர்த்தம்னு பாருங்க:

| Complexity | n = 1,000 | n = 10 lakh (1,000,000) | Typical example |
|---|---|---|---|
| O(1) | 1 µs | 1 µs | dict lookup |
| O(log n) | 10 µs | 20 µs | binary search |
| O(n) | 1 ms | 1 second | list மேல ஒரு pass |
| O(n log n) | 10 ms | 20 seconds | sorting |
| O(n²) | 1 second | சுமார் 11.5 நாள் | எல்லா pairs மேலயும் nested loops |

கடைசி row தான் கடிக்கும். Testing-ல உடனே முடியுற மாதிரி இருக்குற O(n²) method, production-ல பயன்படுத்தவே முடியாம போகலாம்.

## ஒரு worked example

Priya Bengaluru-ல ஒரு fintech-ஓட payments team-ல வேலை செய்யுறாங்க. ஒவ்வொரு ராத்திரியும், settle ஆகுறதுக்கு முன்னாடி அன்னைக்கு file-ல இருக்குற duplicate UPI transaction IDs-ஐ flag பண்ணணும். பிஸியான நாள்ல file-ல சுமார் 20 lakh rows இருக்கும்.

அவங்களோட முதல் version ஒவ்வொரு transaction-ஐயும் மத்த எல்லாத்தோடயும் compare பண்ணுது:

```python
def has_duplicate(ids):
    for i in range(len(ids)):
        for j in range(i + 1, len(ids)):
            if ids[i] == ids[j]:
                return True
    return False
```

இது O(n²). 20 lakh IDs-க்கு சுமார் 2 lakh crore comparisons வரும். Settlement deadline-க்குள்ள அது முடியவே இல்ல.

ரெண்டாவது version முதல்ல list-ஐ sort பண்ணுது, அதனால duplicates பக்கத்து பக்கத்துல வரும். அப்புறம் ஒரு pass:

```python
def has_duplicate(ids):
    ids = sorted(ids)
    for i in range(1, len(ids)):
        if ids[i] == ids[i - 1]:
            return True
    return False
```

Sorting O(n log n), pass O(n), அதனால மொத்தமா O(n log n). சில seconds-ல ஓடிடுச்சு.

மூணாவது version ஒரு set use பண்ணுது, அது keys-ஓட **hash map**:

```python
def has_duplicate(ids):
    seen = set()
    for t in ids:
        if t in seen:
            return True
        seen.add(t)
    return False
```

ஒவ்வொரு `in` check-உம் `add`-உம் சராசரியா O(1), அதனால முழு function-உம் O(n) time. Set-க்காக O(n) extra memory எடுக்கும், server-ல அது பிரச்சனை இல்ல. இந்த version ஒரு second-க்குள்ள ஓடிச்சு, duplicate கிடைச்ச உடனே சீக்கிரமே நிறுத்தும்.

Priya தன் team-ஓட notes-ல எழுதின பாடம்: code-ஐ line by line optimise பண்றதுக்கு முன்னாடி, அதோட Big-O-ஐ பாருங்க. O(n²)-ல இருந்து O(n)-க்கு போறது, எவ்வளவு tuning பண்ணினாலும் அதை விட பெரிய gain.

## பொதுவான தப்புகள்

**"சாதாரண" call-க்குள்ள ஒரு loop மறைஞ்சிருக்கிறது.** `if x in my_list` ஒரே step மாதிரி தெரியும், ஆனா list-ல அது எல்லா items-ஐயும் scan பண்ணும்: O(n). அதை ஒரு loop-க்குள்ள போட்டா O(n²). Membership-ஐ பல தடவை check பண்ணும்போது set அல்லது dict use பண்ணுங்க.

**Repetitions-க்கு பதிலா lines-ஐ எண்ணுறது.** ஒவ்வொண்ணும் ஒரு தடவை ஓடுற அஞ்சு lines O(1). ரெண்டு nested loops-க்குள்ள இருக்குற ஒரு line O(n²). அதிகமா ஓடுற line எவ்வளவு தடவை ஓடுதுன்னு பாருங்க.

**Build பண்றதோட cost-ஐ மறக்கிறது.** List-ஐ set-ஆ மாத்துறது O(n). அப்புறம் பல lookups பண்ணும்போது அது worth. ஒரே ஒரு lookup பண்ணும்போது இல்ல.

**Average-ஐ worst case-ஆ நினைக்கிறது.** Dict lookups சராசரியா O(1), ஆனா மோசமான hash function அதை slow ஆக்கலாம். Quicksort சராசரியா O(n log n), worst case-ல O(n²). Interviewers பெரும்பாலும் ரெண்டையும் கேப்பாங்க.

**Memory-ஐ கவனிக்காம விடுறது.** O(n) extra memory தேவைப்படுற O(n) time solution, n crores of rows-ஆ இருக்கும்போது fit ஆகாம போகலாம். Time cost-ஓட space cost-ஐயும் சொல்லுங்க.

**ரொம்ப சீக்கிரமே optimise பண்றது.** n எப்பவும் 50-ஐ தாண்டாதுன்னா, தெளிவான O(n²) code, கெட்டிக்காரத்தனமான O(n log n) code-ஐ விட நல்லா இருக்கலாம். n பெருசா இருக்கும்போது தான் Big-O முக்கியம்.
