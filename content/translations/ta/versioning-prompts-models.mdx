## இது என்ன

ஒரு AI system-ஓட behaviour code-ஐ மட்டும் சார்ந்தது இல்லை:

- **prompts** (system prompts, templates, few-shot examples);
- **model** (provider, model பேரு, snapshot அல்லது version);
- temperature, maximum tokens மாதிரி **settings**;
- model பார்க்கிற **tool definitions**;
- **retrieval configuration** (index version, chunking, top-k, reranker).

Versioning-னா இவை ஒவ்வொண்ணுக்கும் ஒரு identifier இருக்கும், மாற்றங்கள் review-ஐயும் tests-ஐயும் தாண்டும், இப்போ live-ல இருக்குற combination ஒவ்வொரு request-ஓடயும் record ஆகும், முந்தின எந்த combination-ஐயும் restore பண்ணலாம்.

```flow
Release assistant-2026.11.3 | prompts support-system v12, refund-rules v4; ஒரு pin பண்ண, date போட்ட model snapshot; temperature 0.2; tools lookup_order v3, create_ticket v2; index 2026-11-01 -[ஒவ்வொரு trace-லயும் audit event-லயும் record ஆகும்]-> ஒரு மாற்றம்
ஒரு மாற்றம் -> CI-ல golden set -> Staging -> Production alias
Production alias -[rollback: alias-ஐ திரும்ப நகர்த்துங்க]-> முந்தின release
```

ஒரு release-ஓட ஒவ்வொரு பகுதிக்கும் தன்னோட சொந்த version இருக்கு; அதனால எந்த பதிலையும் அதை உருவாக்குனது எதுன்னு exact-ஆ trace பண்ணலாம்.

இந்த lesson-ல Gurugram-ல ஒரு fintech-ஓட support assistant-ஐ follow பண்ணப் போறோம்; அங்க மூணு teams production-ல நேரடியா prompts-ஐ edit பண்ணிட்டிருந்தாங்க.

## இது எப்படி work ஆகுது

**Version control-ல prompts.** Prompts-ஐ repository-ல files-ஆ (அல்லது ஒரு prompt registry-ல) store பண்ணுங்க; code-ல சிதறிக்கிடக்குற strings-ஆவோ dashboard-ல edit பண்றதாவோ வேண்டாம். மாற்றங்கள் CI-ல evals-ஓட pull requests வழியா போகணும்.

**Prompt registries.** MLflow-ஓட prompt registry, Langfuse மாதிரி tools, பேர் வச்ச, எண் இட்ட prompt versions-ஐ aliases-ஓட ("production", "staging") store பண்ணும். Application prompt-ஐ alias வச்சு கேட்கும்; alias-ஐ நகர்த்துனா code release இல்லாம deploy அல்லது rollback ஆகும். Engineers இல்லாதவங்க prompts-ஐ edit பண்ணும்போது இது உதவும், மாற்றங்கள் evals-ஐ தாண்டுதுன்னா.

**Models-ஐ pin பண்ணுங்க.** Providers தரும் இடத்துல, அமைதியா மாறுற aliases-ஐ விட்டுட்டு, date போட்ட model snapshots-ஐ use பண்ணுங்க. உங்க gateway-ஓட aliases-ஐ ("chat-default") use பண்ணா, gateway configuration-ஏ versioned-ஆவும் reviewed-ஆவும் இருக்கணும்.

**ஒரே release identifier.** Prompt version, model, settings, index version எல்லாத்தையும் ஒரு release-ஆ சேருங்க (உதாரணம் "assistant-2026.11.3"); அது ஒவ்வொரு trace-லயும் audit event-லயும் record ஆகணும்.

**Promote பண்றதுக்கு முன்னாடி test பண்ணுங்க.** ஒவ்வொரு மாற்றமும் golden set-ஐ run பண்ணணும். Quality, cost, latency-ல தற்போதைய release-ஓட compare பண்ணுங்க. Staging வழியா production-க்கு promote பண்ணுங்க.

**Provider deprecations.** Providers அறிவிச்ச dates-ல models-ஐ retire பண்ணுவாங்க. ஒரு calendar வச்சுக்கோங்க, replacement-ஐ சீக்கிரமே test பண்ணுங்க, switch-ஐ ஒரு release-ஆ plan பண்ணுங்க.

**Rollback.** முந்தின release-ஐ தயாரா வச்சிருங்க. Rollback ஒரே action-ஆ இருக்கணும்: alias-ஐ நகர்த்துங்க அல்லது முந்தின tag-ஐ redeploy பண்ணுங்க.

**எதை version பண்ணணும், எப்படி:**

| பகுதி | எப்படி version பண்றது | வழக்கமான மாற்றம் |
| --- | --- | --- |
| Prompts | Git-ல files அல்லது எண் இட்ட versions-ஓட ஒரு registry | Wording, examples, rules |
| Model | Pin பண்ண date போட்ட snapshot, அல்லது review பண்ண gateway alias | புது model-க்கு upgrade |
| Settings | Git-ல config file | Temperature, max tokens |
| Tool definitions | Git-ல code | புது parameter அல்லது tool |
| Retrieval | Git-ல index version, config | Chunk size, top-k, reranker |

**ஒரு நேரத்துல ஒரே ஒண்ணை மாத்துங்க.** ஒரு release prompt, model, index மூணையும் சேர்த்து மாத்தி quality குறைஞ்சா, எது காரணம்னு யாராலும் சொல்ல முடியாது. முடிஞ்சவரை அவற்றை தனி releases-ஆ ship பண்ணுங்க, ஒவ்வொண்ணும் golden set வழியா. பல மாற்றங்கள் சேர்ந்து போகணும்னா, உதாரணம் prompt adjustments தேவைப்படுற ஒரு model switch, production-க்கு முன்னாடி ஒவ்வொரு பகுதியோட effect-ம் தெரியும்படி staging-ல ஒவ்வொரு step-லயும் golden set-ஐ run பண்ணுங்க.

**Model switches.** ஒரு புது model-ஐ release candidate-ஆ நடத்துங்க: முழு golden set-ஐ run பண்ணுங்க, cost, latency-ஐ compare பண்ணுங்க, நீங்க serve பண்ற ஒவ்வொரு மொழியிலயும் sample conversations-ல refusals, tone-ஐ check பண்ணுங்க, படிப்படியா roll out பண்ணுங்க. ஒரு model-க்கு tune பண்ண prompts-க்கு, அடுத்ததுக்கு சின்ன மாற்றங்கள் அடிக்கடி தேவைப்படும்.

**Files-ஆ prompts, ஒரே manifest-ஆ releases.**

```text
prompts/
  answer.v13.md
  answer.v14.md
  rewrite.v4.md
release.yaml
```

```yaml
# release.yaml
release: assistant-2026.11.3
model: claude-sonnet-5-5-YYYYMMDD     # a dated snapshot where the provider offers one
settings: {max_tokens: 600}
prompts: {answer: v14, rewrite: v4}
index: policies-2026-11-01
tools: tools-v7
```

```python
import hashlib, json, yaml
from pathlib import Path

def load_release(path="release.yaml"):
    rel = yaml.safe_load(open(path))
    rel["prompt_text"] = {name: Path(f"prompts/{name}.{ver}.md").read_text()
                          for name, ver in rel["prompts"].items()}
    blob = json.dumps({k: rel[k] for k in ("model", "settings", "prompts", "index", "tools")}, sort_keys=True)
    rel["fingerprint"] = hashlib.sha256(blob.encode()).hexdigest()[:10]
    return rel

RELEASE = load_release()     # log RELEASE["release"] and RELEASE["fingerprint"] on every trace
```

யாராவது release-ஐ பேர் மாத்தாம edit பண்ணா fingerprint மாறும்; அதனால "சின்ன", track ஆகாத மாற்றங்களை இது பிடிச்சுடும்.

**CI-ல checks.** Release ஏதாவது missing-ஆன அல்லது risky-ஆன ஒண்ணை point பண்ணா build-ஐ fail ஆக்குங்க:

```python
import re
from datetime import date

RETIREMENTS = yaml.safe_load(open("model-retirements.yaml"))     # {model_id: "YYYY-MM-DD"}

def check_release(rel):
    problems = []
    for name, ver in rel["prompts"].items():
        if not Path(f"prompts/{name}.{ver}.md").exists():
            problems.append(f"missing prompt file {name}.{ver}")
    if not re.search(r"\d{8}$", rel["model"]):
        problems.append("model is not pinned to a dated snapshot")
    retire = RETIREMENTS.get(rel["model"])
    if retire and (date.fromisoformat(retire) - date.today()).days < 60:
        problems.append(f"{rel['model']} retires on {retire}; plan the switch")
    return problems
```

ஒரு provider date போட்ட பேர்களை தரலன்னா, உங்களால முடிஞ்சதை pin பண்ணுங்க (உங்க gateway-ஓட alias, review பண்ணி), அமைதியா நடக்குற மாற்றங்களை பிடிக்க golden set-ஐ ஒரு schedule-ல run பண்ணுங்க.

**Promotion, rollback.** Production deploy ஆன commit-ல இருந்து `release.yaml`-ஐ படிக்கும்; அதனால promote பண்றது ஒரு pull request-ஐ merge பண்றது, rollback பண்றது முந்தின commit-ஐ redeploy பண்றது. அதுக்கு பதிலா prompt registry use பண்ணா, அதே rule தான்: app ஒரு alias-ஐ படிக்கும், golden set pass ஆனதும் promotion alias-ஐ நகர்த்தும்.

**மனுஷங்க படிக்கிற changelog.** `release.yaml` பக்கத்துலயே ஒரு சின்ன `CHANGELOG.md` வச்சுக்கோங்க: release id, date, என்ன மாறுச்சு, முந்தின release-ஓட compare பண்ண eval results, யார் approve பண்ணாங்க. Clients-ஓட reviewers அடிக்கடி சரியா இதைத்தான் கேட்பாங்க.

## ஒரு example

Gurugram-ல ஒரு fintech-ஓட support assistant-ல, மூணு teams நேரடியா ஒரு admin panel-ல prompts-ஐ edit பண்ணிட்டிருந்தாங்க. ஒரு வெள்ளிக்கிழமை, complaints இரட்டிப்பாச்சு. என்ன மாறுச்சுன்னு யாராலும் சொல்ல முடியல; traces model பேரை மட்டும் காட்டுச்சு.

Fix:

- Prompts repository-க்கு files-ஆ போகுது, ஒவ்வொரு prompt-க்கும் owners.
- ஒரு prompt registry published versions-ஐ வச்சிருக்கு; production `support-prod` alias-ஐ use பண்ணுது.
- ஒவ்வொரு trace-உம் release-ஐ record பண்ணுது: prompt versions, model snapshot, temperature, index version.
- CI ஒவ்வொரு prompt மாற்றத்துக்கும் 120-கேள்வி golden set-ஐ run பண்ணி, ஒரு point-க்கு மேல குறைஞ்சா block பண்ணுது.
- Gateway model aliases pull request மூலமா மட்டுமே மாத்தப்படும்.

ரெண்டு மாசம் கழிச்சு, ஒரு புது prompt version evals-ஐ pass பண்ணுது, ஆனா Hindi conversations-ல customer feedback குறையுது. Dip release 2026.12.2-ல ஆரம்பிச்சதுன்னு traces காட்டுது. Team alias-ஐ ஒரு நிமிஷத்துல 2026.12.1-க்கு திருப்பி நகர்த்துறாங்க; அப்புறம் golden set-ல 25 Hindi cases சேர்க்கிறாங்க, அவை problem-ஐ வெளிக்கொண்டு வருது. சரி பண்ண version அடுத்த நாளே ship ஆகுது.

| Event | Versioning-க்கு முன்னாடி | Versioning-க்கு அப்புறம் |
| --- | --- | --- |
| Complaint spike | என்ன மாறுச்சுன்னு யாருக்கும் தெரியல | Traces release 2026.12.2-ஐ காட்டுச்சு |
| Rollback | மணிக்கணக்கான guesswork | Alias ஒரு நிமிஷத்துல திரும்ப நகர்ந்துச்சு |
| Root cause | தெரியல | 25 புது Hindi golden cases கண்டுபிடிச்சுது |
| Fix ship ஆனது | தெளிவில்ல | அடுத்த நாள், CI வழியா |

## பொதுவா பண்ற தப்புகள்

- **Production dashboards-ல review இல்லாம prompts-ஐ edit பண்றது.** மாற்றங்கள் கண்ணுக்கே தெரியாம போகும்.
- **Floating model aliases.** Provider model-ஐ update பண்ணுவாங்க, உங்க behaviour சொல்லாம கொள்ளாம மாறும்.
- **Traces-ல versions இல்லாதது.** Quality மாற்றத்தை ஒரு release-ஓட link பண்ண முடியாது.
- **Golden-set gate இல்லாதது.** Prompt மாற்றங்களும் code மாற்றங்கள் தான்; test பண்ணுங்க.
- **Deprecation dates-ஐ கவனிக்காம விடுறது.** கடைசி நேரத்துல கட்டாயப்படுத்தப்பட்ட switch ஒரு risky release.
- **ஒரே release-ல பல பகுதிகளை மாத்துறது.** Quality குறைஞ்சா, எந்த பகுதி காரணம்னு சொல்ல முடியாது.
- **ஒவ்வொரு prompt-க்கும் owner இல்லாதது.** ஒவ்வொரு மாற்றத்தையும் யாராவது approve பண்ணி, அதோட effect-க்கு பதில் சொல்லணும்.
- **புது version சேர்க்காம, ஒரு prompt file-ஐ அதே இடத்துல edit பண்றது.**
- **ஒரு fixed பேருக்கு கீழ அமைதியா மாறுற model aliases.**
- **Retirement calendar இல்லாதது**, அதனால ஒரு deprecation emergency ஆயிடும்.

## லேசான versioning போதும்ங்குற நேரங்கள்

- **ஒரு prompt இருக்குற prototype**: அதை Git-ல வச்சு, நீங்க use பண்ண model-ஐ note பண்ணுங்க.
- **Personal tools**, அங்க நிலையான behaviour-ஐ யாரும் சார்ந்திருக்கல.
- **ஒரு தடவை மட்டும் run ஆகுற fixed batch jobs**, அங்க output-ல prompt-ஐயும் model-ஐயும் record பண்ணா போதும்.

## Demo-ல இருந்து production-க்கு

- **எல்லா பகுதியையும் ஒரே release file-ல pin பண்ணுங்க**, ஒவ்வொரு trace-லயும் release id-ஐயும் fingerprint-ஐயும் log பண்ணுங்க.
- **CI-ல ஒவ்வொரு release மாற்றத்துக்கும் golden set-ஐ run பண்ணுங்க.**
- **Model retirement dates-ஐ track பண்ணுங்க**, replacements-ஐ சீக்கிரமே test பண்ணுங்க.
- **Eval results, approvals-ஓட ஒரு changelog வச்சுக்கோங்க.**
- **முந்தின release-ஐ redeploy பண்ணி rollback பண்ணுங்க.**

## Practice பண்ணுங்க

MLflow-ஓட prompt registry docs-ஐ படிங்க.

1. உங்க app-ஓட prompts-ஐ versioned files-க்கு அல்லது aliases இருக்குற ஒரு registry-க்கு மாத்துங்க.
2. ஒவ்வொரு trace-லயும் ஒரு release identifier-ஐ (prompt versions, model snapshot, settings, index version) record பண்ணுங்க.
3. ஒரு prompt-ஐ மாத்தி, CI-ல golden set-ஐ run பண்ணி, promote பண்ணி, அப்புறம் ஒரே action-ல rollback பண்ணுங்க.
4. CI-ல check_release-ஐ சேர்த்து, release.yaml-ஐ இல்லாத ஒரு prompt version-ஐ point பண்ண வச்சு, build fail ஆகுதுன்னு confirm பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** எந்த பழைய request-க்கும் "இந்த பதிலை exact-ஆ எது உருவாக்குச்சு?"ன்னு பதில் சொல்ல முடியும், அஞ்சு நிமிஷத்துக்குள்ள rollback பண்ண முடியும்.
