## இது என்ன

ஒரு language model உங்களுக்கு வேண்டியதை பண்ணலைன்னா, fix உண்மையில என்ன தப்புன்னு பொறுத்து இருக்கு. ரெண்டு வகை problems இருக்கு, அஞ்சு முக்கிய tools இருக்கு.

**Model-க்கு knowledge இல்லை** (உங்க policies, ஒரு customer-ஓட account, இந்த வாரத்து prices). Knowledge-ஐ query நேரத்துல, prompt-ல கொண்டு வாங்க:

- **Long context**: முழு documents-ஐ prompt-ல வைங்க. **Prompt caching**-ல, prompt-ஓட மாறாத ஆரம்பப் பகுதியை provider சேமிச்சு வைக்கும், அதனால திரும்ப வர்ற calls அதை மலிவா படிக்கும்.
- **RAG (retrieval-augmented generation)**: உங்க documents-ல தேடி, சிறந்த சில passages-ஐ மட்டும் prompt-ல வைங்க.
- **Tools, agentic search**: model ஒரு database, ஒரு API அல்லது ஒரு search tool-ஐ call பண்ணி, result-ஐ படிச்சு, தேவைப்பட்டா திரும்ப தேடட்டும்.

**Model-க்கு போதுமான அளவு தெரியும், ஆனா தப்பா behave பண்ணுது** (format, tone, steps, edge cases):

- **Prompting**: தெளிவான instructions, examples, API-ஓட **structured output**, அதுல நீங்க ஒரு JSON schema கொடுப்பீங்க, reply அதுக்கு பொருந்தணும்.
- **Fine-tuning**: behaviour உள்ளேயே build ஆகுற மாதிரி, உங்க examples-ல model-ஐ மேலும் train பண்றது. இது model-ஓட weights-ஐ மாத்தும், அதனால இது தான் ரொம்ப மெதுவான, ரொம்ப கம்மியா திரும்ப மாத்தக்கூடிய fix.

சுருக்கமான rule: knowledge context-க்குள்ள போகும்; behaviour முதல்ல prompt-க்குள்ள, கடைசியா weights-க்குள்ள.

## இது எப்படி work ஆகுது

### Step 1: knowledge-ஆ behaviour-ஆன்னு diagnose பண்ணுங்க

எதையும் தேர்ந்தெடுக்குறதுக்கு முன்னாடி 20 முதல் 30 fail ஆன outputs-ஐ படிங்க. ஒவ்வொண்ணுக்கும் கேளுங்க: தேவையான fact prompt-ல இருந்துச்சா? இல்லைன்னா, இது ஒரு knowledge problem, style பத்தின எவ்வளவு instruction-உம் training-உம் இதை சரி பண்ணாது. Fact இருந்தும் பதில் தப்பா, தப்பான format-ல அல்லது தப்பான tone-ல வந்தா, இது ஒரு behaviour problem. நிறைய teams இதை skip பண்ணிட்டு, உண்மையில context இல்லாததால வந்த problem-ஐ சரி பண்ண ஒரு model-ஐ fine-tune பண்றாங்க.

### Step 2: behaviour-ஐ முதல்ல prompt வச்சு சரி பண்ணுங்க

Prompting வேகமானது, மலிவானது, திரும்ப மாத்தலாம்: ஒரு மாத்தத்தை நிமிஷங்கள்ல test பண்ணலாம். பெரிய எதுக்கும் முன்னாடி ஒரு மதியம் செலவழிங்க. Task-ஐயும் output format-ஐயும் நேரடியா சொல்லுங்க, ஒரு edge case உட்பட ரெண்டு மூணு நல்ல examples சேருங்க, உங்க test set-ஐ run பண்ணுங்க. பின்னாடி வர்ற ஒவ்வொரு option-உம் ஜெயிக்க வேண்டிய நியாயமான baseline-ஐயும் இது set பண்ணுது.

**Format** problems-க்கு API-ஓட structured output use பண்ணுங்க: நீங்க ஒரு JSON schema கொடுப்பீங்க, அதுக்கு பொருந்துற replies-ஐ மட்டும் தான் provider model-ஐ உருவாக்க விடும். அப்போ shape உறுதி, ஆனா values இன்னும் தப்பா இருக்கலாம், அதனால அவற்றை code-ல validate பண்ணுங்க. Structured output பத்தின lesson இதை கவர் பண்ணுது. சரியான JSON கிடைக்கணும்ங்குறதுக்காக மட்டும் fine-tune பண்றது 2026-ல பொதுவா ஒரு தப்பு.

### Step 3: knowledge-ஐ ரொம்ப மலிவான, நம்பகமான வழியில கொண்டு வாங்க

மூணு options-உம் query நேரத்துல facts-ஐ model முன்னாடி வைக்கும். Update பண்றதுன்னா ஒரு document-ஐ அல்லது ஒரு database row-ஐ மாத்துறது, மறுபடி train பண்றது இல்ல.

**Caching-ஓட long context.** November 2026 நிலவரப்படி, Anthropic-ஓட சமீபத்திய Claude models 1 million tokens input ஏத்துக்கும். Caching cost-ஐ நிறைய மாத்துது. Claude Sonnet 5.5-க்கான Anthropic list prices, 28 November 2026 அன்னைக்கு check பண்ணது: input ஒரு million tokens-க்கு $2, cache read $0.10 (input-ல 5%), 5-minute cache write $2.50, output $10. அதனால Sonnet 5.5-ல, corpus RAG context-ஐ விட சுமார் 20 மடங்குக்கு கீழ இருக்குற வரைக்கும், cache பண்ண ஒரு corpus ஒரு கேள்விக்கு RAG prompt-ஐ விட கம்மியா தான் ஆகும். Cache-ல இருந்து படிக்குற ஒரு 60,000-token handbook, 3,000 fresh tokens-க்கு சமமான cost ஆகும். மற்ற models, providers caching-ஐ வேற மாதிரி price பண்றாங்க (Claude Haiku 5.5-ல ஒரு cache read input-ல 10%), அதனால உங்களோடதுக்கு கணக்கை திரும்ப போடுங்க.

சிக்கல்கள்: default-ஆ, use பண்ணாம 5 நிமிஷம் ஆனா cache expire ஆகிடும், அதனால steady traffic இருந்தா தான் பலன்; prompt-ஓட ஆரம்பத்துல எந்த மாத்தமும் அதை உடைச்சுடும்; ரொம்ப நீளமான inputs-ல accuracy குறையும் ("lost in the middle" effect); நீளமான inputs முதல் token-ஐ மெதுவாக்கும். "Long context or RAG" lesson இவற்றை ஆழமா கவர் பண்ணுது.

**RAG.** Corpus பெரியதா இருக்கும்போது (ஒவ்வொரு call-க்கும் நீங்க பணம் கட்ட விரும்புறதை விட ரொம்ப அதிகமா), அடிக்கடி மாறும்போது, ஒவ்வொரு user-ஓட permissions-ஐயும் மதிக்கணும்னா, அல்லது answers ஒரு passage-ஐ cite பண்ணணும்னா இதை use பண்ணுங்க. இதுக்கு chunking, indexing, tuning வேணும், search எதை தவற விடுதோ அதை இதுவும் தவற விடும்.

**Tools, agentic search.** Live, structured data-க்கு (ஒரு fixed-deposit rate, ஒரு order status, ஒரு balance), system of record-ஐ ஒரு tool மூலமா query பண்ணுங்க. Documents மேல RAG ஒரு பழைய number-ஐ தரலாம்; ஒரு database query தராது. Model தானே step by step தேடுற agentic search, அடுத்த lookup முந்தையதை பொறுத்து இருக்குற கேள்விகளுக்கு பொருந்தும். இது அதிகமா செலவாகும்: ஒவ்வொரு step-உம் வளர்ந்துக்கிட்டே போற conversation-ஐ திரும்ப அனுப்பும். உதாரணமா, 2,000 tokens instructions-ல ஒவ்வொண்ணும் 3,000 tokens results சேர்க்குற ஆறு steps மொத்தம் 57,000 input tokens அனுப்பும், ஒரு RAG call-க்கு சுமார் 4,000 தான்.

### Step 4: form-க்காக மட்டும், volume-ல fine-tune பண்ணுங்க

நிறைய நல்ல examples உள்ள ஒரு narrow task-ல, prompting வேலை செஞ்சாலும் அதிக volume-ல ரொம்ப நீளமா, ரொம்ப செலவா, ரொம்ப மெதுவா அல்லது இன்னும் தொடர்ச்சி இல்லாம இருந்தா fine-tuning பொருந்தும்: 30 labels உள்ள ஒரு classification, millions of replies முழுக்க ஒரு house style, ஒரு பெரிய model-க்கு சமமா இருக்க வேண்டிய ஒரு சின்ன model.

**Facts retrieval-ல இருக்கணும்.** ரெண்டு EMNLP 2024 papers-ஐ பேரோட தெரிஞ்சு வச்சுக்கிறது நல்லது. Ovadia குழு ("Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs"), பழக்கமான knowledge, முழுக்க புது knowledge ரெண்டுக்குமே unsupervised fine-tuning-ஐ RAG ஜெயிச்சுதுன்னு கண்டுபிடிச்சுது. Gekhman குழு ("Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?"), supervised closed-book question answering-ல, புது facts உள்ள examples மெதுவா தான் கத்துக்கப்படுது, கத்துக்கிட்ட பிறகு hallucination-ஐ கூட்டுதுன்னு கண்டுபிடிச்சுது. Models பெரும்பாலும் facts-ஐ pre-training-ல இருந்து தான் எடுக்குது; fine-tuning, தெரிஞ்சதை எப்படி use பண்ணணும்னு அவற்றுக்கு கத்துக்கொடுக்குது.

"Fine-tuning"-ல வேற வேற data தேவைகள் உள்ள பல methods அடங்கும்:

| Method | Training data | வழக்கமான use |
| --- | --- | --- |
| Supervised fine-tuning (SFT) | Ideal outputs-ஓட ஜோடி சேர்த்த inputs | Format, style, classification, extraction |
| Preference tuning, உதாரணமா DPO | ஒரு நல்ல answer, ஒரு மோசமான answer ஜோடிகள் | Tone, helpfulness, எதை மறுக்கணும் |
| Reinforcement fine-tuning | Prompts கூட answers-க்கு score போடுற ஒரு grader | Check பண்ணக்கூடிய answers, கம்மியான labels உள்ள tasks |
| Distillation | ஒரு பெரிய model-ஓட outputs, SFT data-வா | ஒரு task-ல பெரிய model-ஐ copy பண்ற ஒரு சின்ன, மலிவான model |

பெரும்பாலான teams LoRA use பண்றாங்க, அது model-ஓட எல்லா weights-ஐயும் train பண்ணாம ஒரு சின்ன add-on-ஐ train பண்ணும்; fine-tuning எப்படி work ஆகுது, practice-ல fine-tuning பத்தின lessons இந்த methods-ஐ கவர் பண்ணுது. எந்த plan-க்கும் முன்னாடி ரெண்டு practical checks வரும். முதல்ல, availability: எல்லா model-உம் fine-tuning தர்றதில்ல, அந்த offer-உம் மாறும். OpenAI 8 May 2026 தேதியிட்ட ஒரு update-ல, அதோட fine-tuning platform-ஐ படிப்படியா நிறுத்துறதா சொல்லுச்சு, அது இனிமே புது users-க்கு கிடைக்காது. உங்க provider-ஓட documentation-ஐ check பண்ணி தேதியை எழுதி வைங்க. நீங்களே train பண்ணி host பண்ற open-weight models இந்த risk-ஐ தவிர்க்கும், ஆனா GPUs-உம் skills-உம் வேணும். ரெண்டாவது, distillation-க்கு terms of use-ஐ படிங்க: போட்டி models-ஐ train பண்ண தங்களோட outputs-ஐ use பண்றதை நிறைய providers தடை பண்றாங்க.

### ஒவ்வொரு option-ஐயும் ஒரே test set-ல அளங்க

ஒவ்வொரு candidate-க்கும் அதே கேள்விகள், graders, cost, latency அளவீடுகளை use பண்ணுங்க. Test set-ஐ problem type வாரியா பிரிங்க: private அல்லது சமீபத்திய facts தேவைப்படுற கேள்விகள், format அல்லது behaviour பத்தின கேள்விகள். முதல் குழுவுல knowledge options ஜெயிக்கணும்; ஜெயிக்கலைன்னா, உங்க diagnosis தப்பு.

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.3f}{p95:>8.0f}")
    return rows
```

### Fine-tuning-ஐ சிறந்த மலிவான baseline-க்கு எதிரா price பண்ணுங்க

மாசாந்திர சேமிப்பை, ஒரு குறுகிய பயனுள்ள காலத்துக்கான build cost-ஓட ஒப்பிடுங்க. Build cost-னா GPU மணி நேரங்கள் மட்டும் இல்ல, data-வை சேகரிச்சு check பண்ணவும் evals run பண்ணவும் ஆகுற மனுஷங்களோட நேரமும் தான். குறுகிய காலம் யதார்த்தமானது, ஏன்னா ஒரு சிறந்த base model அடிக்கடி சில மாசத்துலயே வரும், வேலை திரும்பவும் செய்யணும்.

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.414, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
print(finetune_break_even(2_000_000, 0.056, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
```

கீழ இருக்குற worked example inputs-ஐ விளக்குது. முதல் line, fine-tuning-ஐ cache பண்ணாத ஒரு பெரிய model-க்கு எதிரா price பண்ணுது: மாசம் ₹7.68 லட்சம் சேமிப்பு, 0.5 மாசத்துல break-even. ரெண்டாவது, prompt cache பண்ண அதே model-க்கு எதிரா price பண்ணுது: மாசம் ₹52,000 சேமிப்பு, break-even-க்கு 7.7 மாசம், ஆறு மாசத்துல ₹88,000 net loss. அதே fine-tune, எதிரான பதில். ஏற்கனவே வேலை செய்யுற ரொம்ப மலிவான option-க்கு எதிரா தான் எப்பவும் price பண்ணுங்க.

## ஒரு worked example

புனேவுல ஒரு software company-ஓட மூணு problems. எல்லா costs-உம் விளக்கத்துக்காக தான்: 28 November 2026 அன்னைக்கு check பண்ண Claude Sonnet 5.5, Haiku 5.5 list prices, ஒரு டாலருக்கு ₹94-ங்குற விளக்கத்துக்கான rate, low effort-ல assume பண்ண token counts (அதனால thinking tokens கிட்டத்தட்ட இல்ல) இதை use பண்ணுது. Thinking output-ஆ bill ஆகும், அதனால real responses-ல `usage`-ஐ check பண்ணுங்க. Accuracy figures ஒரு team பதிவு பண்ற மாதிரியானவை, அளந்த results இல்ல.

**1. Support bot-உம் வாரா வாரம் மாறுற ஆறு handbooks-உம்.** Company ஆறு products விக்குது, ஒவ்வொரு customer-உம் தங்களோட product-ஓட handbook-ஐ மட்டும் தான் பார்க்கலாம், ஒவ்வொரு handbook-உம் சுமார் 400,000 tokens. Cached long context, ஒரு product-ஓட handbook-க்கு மட்டும் கூட, ஒரு கேள்விக்கு சுமார் ₹4.10 ஆகும் (cache-read price-ல 400,000 tokens, கூட ஒரு 300-token கேள்வி, ஒரு 300-token பதில்). சுமார் 4,000 tokens passages-ஓட RAG சுமார் ₹1.09 ஆகும். RAG ஒரு metadata filter வச்சு ஒவ்வொரு customer-ஓட permissions-ஐயும் enforce பண்ணும், use பண்ண section-ஐயும் cite பண்ணும். அதனால அவங்க **RAG**-ஐ தேர்ந்தெடுக்குறாங்க, ஒவ்வொரு update-லயும் re-index பண்ணி.

Crossover முக்கியம். நாள் முழுக்க கேள்வி கேக்கப்படுற ஒரே ஒரு 60,000-token handbook இருந்திருந்தா, cached long context ஒரு கேள்விக்கு ₹1.09-க்கு எதிரா சுமார் ₹0.90 ஆகியிருக்கும், index தேவைப்படாது, எல்லா sections-ஐயும் ஒரே நேரத்துல பார்க்கும். Cross-section கேள்விகள்ல test பண்ணுங்க, அது சிறந்த தேர்வா இருக்கலாம்.

**2. Ticket summaries வேறுபடுது, customer-ஓட priority-ஐ விட்டுடுது.** Model-கிட்ட ticket இருக்கு; instruction தான் தெளிவில்ல. **Prompting, structured output**: நாலு values-க்கு மட்டும் கட்டுப்படுத்தின கட்டாய `priority` field உள்ள ஒரு schema, priority-ஐ எப்படி judge பண்றதுன்னு ஒரு rule, ரெண்டு examples. 50 test tickets-ல சரியான priority 31-ல இருந்து 46-க்கு போகுது, format இனிமே உடையவே இல்லன்னு வச்சுக்குவோம். இதுக்கு ஒரு மதியம் ஆச்சு.

**3. மாசம் 20 லட்சம் log lines-ஐ 30 categories-ஆ classify பண்றது.** இன்னைக்கு அவங்க Sonnet 5.5-ஐ ஒவ்வொரு தடவையும் fresh-ஆ அனுப்புற ஒரு 2,000-token prompt-ஓட (category definitions, examples) call பண்றாங்க, கூட சுமார் 100 tokens log line, 20 tokens output. அது ஒரு line-க்கு சுமார் ₹0.41, அல்லது மாசம் ₹8.3 லட்சம். அவங்ககிட்ட 50,000 labelled lines இருக்கு, ஒரு vendor ஒரு சின்ன open-weight model-ஐ fine-tune பண்ணித் தர்றதா சொல்றாங்க: build பண்ண ₹4 லட்சம், maintain பண்ண மாசம் ₹40,000, serve பண்ண ஒரு line-க்கு ₹0.01-ன்னு வச்சுக்குவோம்.

இன்னைக்கு bill-க்கு எதிரா பார்த்தா, fine-tuning ரெண்டு வாரத்துல பணத்தை திருப்பும். ஆனா முதல்ல அவங்க prompt-ஐ cache பண்றாங்க. நிமிஷத்துக்கு சுமார் 46 lines-ல cache ஒருபோதும் cold ஆகாது, 2,000-token prompt 512-token minimum-க்கு மேல இருக்கு. Accuracy-ல எந்த மாத்தமும் இல்லாம cost ஒரு line-க்கு சுமார் ₹0.056-க்கு (மாசம் ₹1.13 லட்சம்) குறையுது. அந்த baseline-க்கு எதிரா, அதே fine-tune பணத்தை திருப்ப 7.7 மாசம் ஆகும். அதே cached prompt-ஓட Haiku 5.5-ஐயும் try பண்றாங்க: ஒரு line-க்கு சுமார் ₹0.004, மாசம் ₹7,500, ஆனா accuracy 96%-ல இருந்து 91%-க்கு குறையுதுன்னு வச்சுக்குவோம். Lines அவசரம் இல்ல, அதனால November 2026 நிலவரப்படி Anthropic-ல பாதி விலையான batch API, எந்த bill-ஐயும் இன்னும் குறைக்கும்.

Volume தான் முடிவு பண்ணுது. ஆறு மாச காலத்துக்கு, மேல இருக்குற inputs cached baseline-க்கு எதிரா மாசம் சுமார் 23 லட்சம் lines break-even volume-ஐ தருது. ரெண்டு புது clients அடுத்த quarter-ல volume-ஐ மாசம் 1 கோடி lines-க்கு கொண்டு போவாங்க. 10,000 labels-ல ஒரு pilot fine-tune test set-ல 96% score பண்ணுது, Sonnet-ஓட சமமா, அப்படின்னு வச்சுக்குவோம். 1 கோடி lines-ல fine-tune மாசம் சுமார் ₹4.2 லட்சம் சேமிக்கும், சுமார் ஒரு மாசத்துல பணத்தை திருப்பும். Haiku இன்னும் மலிவா இருக்கும், ஆனா அதோட 5-point இடைவெளி மாசம் சுமார் 5 லட்சம் கூடுதல் தப்பான tags-ன்னு அர்த்தம். அதனால அவங்க **இன்னைக்கு prompt-ஐ cache பண்ணி, பெரிய volume-க்கு fine-tune பண்றாங்க**, cached prompt-ஐ fallback-ஆவும் baseline-ஆவும் வச்சுக்கிட்டு.

| Problem | கண்டறிதல் | Approach | விளக்கத்துக்கான result |
| --- | --- | --- | --- |
| ஒவ்வொண்ணும் 400,000 tokens உள்ள ஆறு handbooks, customer வாரியா access | Knowledge, பெரியது, permission உள்ளது | Filters-ஓட RAG, வாரா வாரம் re-index | Cached long context-க்கு ₹4.10-க்கு எதிரா ஒரு கேள்விக்கு ₹1.09 |
| Summaries priority-ஐ விட்டுடுது | Behaviour | Schema, ஒரு priority rule, ரெண்டு examples | 50-ல 46-ல priority சரி, 31-ல இருந்து ஏறி |
| மாசம் 20 லட்சம் log lines, 1 கோடிக்கு ஏறுது | Volume-ல form | இப்போ cache, பெரிய volume-க்கு ஒரு சின்ன model-ஐ fine-tune | இப்போ மாசம் ₹8.3 லட்சத்துல இருந்து ₹1.13 லட்சம்; 1 கோடியில fine-tune ஒரு மாசத்துல பணத்தை திருப்பும் |

## பொதுவா பண்ற தப்புகள்

- **Facts சேர்க்க fine-tune பண்றது.** Facts context-ல இருக்கணும், long context, RAG அல்லது ஒரு tool மூலமா.
- **Prompt-ஐ skip பண்றது.** அதுதான் ரொம்ப மலிவான fix, அடிக்கடி போதுமானது, மற்ற எல்லாமே ஜெயிக்க வேண்டிய baseline.
- **JSON format-க்காக fine-tune பண்றது**, structured output-ஐ try பண்றதுக்கு முன்னாடியே.
- **ஒரு சின்ன, நிலையான document-க்கு RAG build பண்றது**, அதை cached long context இன்னும் எளிமையா handle பண்ணும்.
- **Rates, balances மாதிரி live numbers-க்கு documents மேல RAG use பண்றது**, ஒரு tool-க்கு பதிலா.
- **Cache பண்ணாத ஒரு bill-க்கு எதிரா fine-tuning-ஐ price பண்றது.** முதல்ல prompt-ஐ cache பண்ணி ஒரு சின்ன model-ஐ try பண்ணுங்க, அப்புறம் ஒப்பிடுங்க.
- **Build cost-ல மனுஷங்களோட நேரத்தை விட்டுடுறது**, அல்லது ஒரு நீளமான பயனுள்ள காலத்தை assume பண்றது.
- **வேற வேற test sets-ல** அல்லது வேற graders-ஓட options-ஐ ஒப்பிடுறது.
- **ஒரு fine-tuning service-ஐ நம்பி plan பண்றது**, அது இன்னைக்கு உங்க model-க்கு இருக்கான்னு check பண்ணாம.

## தேர்வு ஏற்கனவே தெளிவா இருக்கும் நேரங்கள்

- **பதில் private documents-ஐ cite பண்ணணும்**: வேற என்ன சேர்த்தாலும், retrieval.
- **Data ஒரு database-ல இருக்கு**: ஒரு tool, documents-ஓட index இல்ல.
- **குறைவான volume**: fine-tuning அரிதா தான் பணத்தை திருப்பும்; prompt-ஐ மேம்படுத்துங்க.
- **Task ஒவ்வொரு சில வாரத்துக்கும் மாறுது**: மறுபடி train பண்றதை விட prompts, retrieval வேகமா மாறிக்கும்.
- **உங்ககிட்ட labelled examples இல்ல**: fine-tuning இன்னும் முடியாது; review பண்ண outputs-ல இருந்து அவற்றை சேகரிக்க ஆரம்பிங்க.

## Demo-ல இருந்து production-க்கு

- **ஒரு test set வச்சிருங்க**, problem type வாரியா பிரிச்சு, ஒவ்வொரு approach-க்கும் அதை use பண்ணுங்க.
- **ஒவ்வொரு option-க்கும் quality, cost, p95 latency-ஐ** தேதிகளோட பதிவு பண்ணுங்க.
- **Caching-ஐ நம்பியிருந்தா cache hit rate-ஐ கவனிங்க**; சத்தமில்லாத ஒரு இறக்கம் bill-ஐ பல மடங்காக்கலாம்.
- **Prices, volumes அல்லது models மாறும்போது break-even-ஐ** திரும்ப கணக்கிடுங்க.
- **Review பண்ண outputs-ஐ எதிர்கால training data-வா சேகரிங்க**, இன்னும் fine-tune பண்ணலைன்னாலும்.
- **Fine-tuned models-ஐ ஒவ்வொரு புது base model-க்கும் எதிரா** ஒரு நல்ல, cached prompt-ஓட திரும்ப test பண்ணுங்க.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற, production-க்கான LLM applications உருவாக்குறது பத்தின Chip Huyen-ஓட கட்டுரையை படிங்க.

1. உங்களுக்கு தெரிஞ்ச மூணு problems-க்கு, ஒவ்வொண்ணுக்கும் 20 fail ஆன outputs-ஐ படிச்சு, problem knowledge-ஆ behaviour-ஆன்னு சொல்லுங்க.
2. ஒரு knowledge problem-க்கு, உங்க provider-ஓட தற்போதைய prices வச்சு ஒரு கேள்விக்கு cached long context-ஐ RAG-க்கு எதிரா price பண்ணுங்க, check பண்ண தேதியை அவற்றுக்கு பக்கத்துல எழுதுங்க.
3. ஒரு behaviour problem-க்கு, ரெண்டு prompt மேம்பாடுகளையும் structured output-ஐயும் try பண்ணி, ஒரு சின்ன test set-ல `compare` வச்சு அளங்க.
4. `finetune_break_even`-ஐ ரெண்டு தடவை run பண்ணுங்க: உங்க தற்போதைய bill-க்கு எதிரா, உங்க ரொம்ப மலிவான, வேலை செய்யுற baseline-க்கு எதிரா. எந்த volume-ல fine-tuning பணத்தை திருப்ப ஆரம்பிக்குதுன்னு கண்டுபிடிங்க.

இன்னும் ஆழமா படிக்க, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 7, எப்போ fine-tune பண்றதுன்னும், knowledge, form-க்கு fine-tuning RAG-ஓட எப்படி ஒப்பிடுதுன்னும் கவர் பண்ணுது.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** வாரா வாரம் மாறுற handbook-க்கு fine-tuning இல்லாம retrieval ஏன் வேணும்னும், cached long context எப்போ RAG-ஐ ஜெயிக்கும்னும், fine-tuning-ஐ ஏன் ரொம்ப மலிவான, வேலை செய்யுற baseline-க்கு எதிரா price பண்ணணும்னும் ஒரு teammate-க்கு விளக்க முடியும்.
