## இது என்ன

ஒரு language model நீங்க விரும்புறதை பண்ணலைன்னா, அதை மேம்படுத்த மூணு முக்கிய வழிகள் இருக்கு:

- **Better prompting**: தெளிவான instructions, examples, structure, format.
- **RAG (retrieval-augmented generation)**: உங்க documents அல்லது data-ல இருந்து தொடர்புடைய தகவலை எடுத்து prompt-ல வைக்கிறது.
- **Fine-tuning**: ஒரு behaviour-ஐ கத்துக்கும் படி, உங்க சொந்த examples-ல model-ஐ மேலும் train பண்றது.

இவை வேற வேற problems-ஐ தீர்க்கும், அடிக்கடி சேர்த்தும் use பண்ணுவாங்க. நல்லா தேர்ந்தெடுத்தா மாசக்கணக்குல மிச்சமாகும்.

```flow
என்ன தப்பு? -[model-க்கு ஏதோ ஒண்ணு தெரியல: facts, policies, accounts, சமீபத்திய நிகழ்வுகள்]-> RAG அல்லது tools | re-index பண்ணி update; sources-ஐ cite பண்ணு
என்ன தப்பு? -[அதுக்கு தெரியும், ஆனா தப்பா பண்ணுது: format, tone, steps, edge cases]-> முதல்ல Prompting | instructions, examples, ஒரு template
என்ன தப்பு? -[prompting வேலை செய்யுது, ஆனா அதிக volume-ல நீளமா, செலவா, தொடர்ச்சி இல்லாம இருக்கு]-> Fine-tune, அடிக்கடி ஒரு சின்ன model | நிறைய நல்ல examples, evals வேணும்
```

முதிர்ந்த systems மூணையும் சேர்க்கும், ஒவ்வொண்ணும் ஒரே test set-ல சரி பார்க்கப்படும்.

இந்த lesson, புனேவுல ஒரு software company-ல இருந்த மூணு problems-ஐ பின்தொடருது; ஒவ்வொண்ணுக்கும் வேற வேற fix தேவைப்பட்டுச்சு.

## இது எப்படி work ஆகுது

**முதல்ல problem-ஐ கண்டறியுங்க.**

- *Model-க்கு ஏதோ ஒண்ணு தெரியல* (உங்க products, policies, சமீபத்திய நிகழ்வுகள், ஒரு customer-ஓட account): இது ஒரு knowledge problem. **RAG** அல்லது tools use பண்ணுங்க. Facts சேர்க்க fine-tuning மோசமான வழி: update பண்ண செலவாகும், model அப்புறமும் அவற்றை தப்பா ஞாபகம் வச்சிருக்கலாம்.
- *Model-க்கு போதுமான அளவு தெரியும், ஆனா task-ஐ தப்பான வழியில பண்ணுது* (format, tone, steps, edge cases): முதல்ல **prompting**-ஐ try பண்ணுங்க: instructions, examples, தெளிவான format.
- *Prompting வேலை செய்யுது, ஆனா ஒரு narrow, அதிக volume task-க்கு நீளமா, செலவா, மெதுவா அல்லது இன்னும் தொடர்ச்சி இல்லாம இருக்கு*: நிறைய நல்ல examples-ல ஒரு model-ஐ, அடிக்கடி ஒரு சின்னதை, **fine-tune** பண்றதை பரிசீலிங்க.

**ஏன் முதல்ல prompting.** அது வேகமானது, மலிவானது, திரும்ப மாத்தலாம்: ஒரு மாத்தத்தை நிமிஷங்கள்ல test பண்ணலாம். "Model"-ஐ குறை சொல்ற பல problems, தெளிவான instructions, ரெண்டு நல்ல examples-ஓட மறைஞ்சுடும்.

**RAG எப்போ பொருந்தும்.** அடிக்கடி மாறுற (வாரா வாரம் update ஆகுற ஒரு handbook), பெரிய (ஆயிரக்கணக்கான documents), private ஆன, அல்லது cite பண்ணப்பட வேண்டிய தகவல். Update பண்றதுன்னா re-index பண்றது, மறுபடி train பண்றது இல்ல.

**Fine-tuning எப்போ பொருந்தும்.**

- ரொம்ப நிறைய requests முழுக்க தொடர்ச்சியான style அல்லது format;
- நிறைய labelled examples உள்ள ஒரு narrow classification அல்லது extraction task;
- ஒரு task-ல ஒரு சின்ன, மலிவான model-ஐ பெரிய model-க்கு சமமா ஆக்குறது;
- நிறைய examples சுமக்குற prompts-ஐ சுருக்குறது.

அதுக்கு நூற்றுக்கணக்கான முதல் ஆயிரக்கணக்கான தரமான examples, evaluation, base model மாறும்போது திரும்பவும் செய்றது வேணும்.

**சேர்த்து use பண்ணுங்க.** ஒரு பொதுவான முதிர்ந்த setup: நல்லா வடிவமைச்ச ஒரு prompt, knowledge-க்கு RAG, அதிக volume உள்ள ஒரு step-க்கு ஒருவேளை fine-tune பண்ண ஒரு சின்ன model. ஒவ்வொரு மாத்தத்தையும் ஒரே test set-ல evaluate பண்ணுங்க.

**Approaches-ஐ ஒப்பிடுறது:**

| காரணி | Prompting | RAG | Fine-tuning |
| --- | --- | --- | --- |
| சரி பண்றது | Behaviour, format | இல்லாத அல்லது மாறுற knowledge | Scale-ல தொடர்ச்சியான behaviour |
| Try பண்ற நேரம் | நிமிஷங்கள் | நாட்கள் | வாரங்கள் |
| தேவையான data | சில examples | உங்க documents | நூற்றுக்கணக்கான முதல் ஆயிரக்கணக்கான labelled examples |
| Update பண்றது | Prompt-ஐ edit பண்ணு | Re-index | மறுபடி train |
| ஒரு request-க்கு cost | Prompt நீளத்தோட கூடும் | Retrieval, context சேரும் | ஒரு சின்ன model-ஓட குறைவா இருக்கலாம் |
| Citations | இல்ல | ஆமா | இல்ல |

**Fine-tuning எப்போ பலன் தரும்னு மதிப்பிடுறது.** தற்போதைய approach-ஓட மாசாந்திர cost-ஐ, fine-tuned option-ஓடு ஒப்பிடுங்க: அதோட பயனுள்ள காலத்துல பரவின training cost, உங்க volume-ல serving cost, training data-வை உருவாக்கி பராமரிக்க ஆகுற நேரம். Fine-tuning பொதுவா, ஒரு சின்ன model பெரியதை மாத்தக்கூடிய அதிக volume, narrow tasks-ல பலன் தரும்; குறைவான volume அல்லது வேகமா மாறுற tasks-ல அரிதா தான். கணக்கை எழுதி வைங்க, break-even ஆகுற volume-உடன்.

**முதல்ல prompt fixes-ஐ test பண்றது.** பெரிய மாத்தத்துக்கு முன்னாடி, ஒரு மதியம் prompt-ல செலவழிங்க: task-ஐயும் format-ஐயும் தெளிவா சொல்லுங்க, ஒரு edge case உட்பட ரெண்டு அல்லது மூணு நல்ல examples சேருங்க, test set-ஐ run பண்ணுங்க. எத்தனை problems இதுலயே தீருதுன்னு teams பெரும்பாலும் ஆச்சரியப்படுவாங்க, RAG அல்லது fine-tuning-ஐ மதிப்பிட ஒரு நியாயமான baseline-ஐயும் இது தருது.

**எல்லா candidates-ஐயும் ஒரே test set-ல run பண்ணுங்க.** மிக நியாயமான ஒப்பீடு, அதே கேள்விகள், அதே graders, அதே cost, latency அளவீடுகளை use பண்ணும்:

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.2f}{p95:>8.0f}")
    return rows

# compare({"prompt v3": prompt_only, "prompt + RAG": with_rag, "fine-tuned small": tuned}, tests, grade)
```

Test set-ஐ problem type வாரியா பிரிங்க: private அல்லது சமீபத்திய facts தேவைப்படுற கேள்விகள், format அல்லது behaviour பத்தின கேள்விகள். முதல் குழுவுல RAG ஜெயிக்கணும், ரெண்டாவதுல fine-tuning ஜெயிக்கலாம்; இல்லன்னா, உங்க diagnosis தப்பு.

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.40, 0.06, build_cost_inr=600_000, upkeep_per_month_inr=50_000))
```

`build_cost_inr`-ல GPU மணி நேரங்கள் மட்டும் இல்ல, data-வை சேகரிச்சு check பண்ணவும் evals run பண்ணவும் ஆகுற மனுஷங்களோட நேரமும் சேரணும். குறுகிய `life_months` யதார்த்தமானது: ஒரு புது base model அடிக்கடி சில மாசத்துலயே வரும், வேலை திரும்பவும் செய்யணும்.

**Facts retrieval-ல இருக்கட்டும்.** புது knowledge-க்கு ரெண்டையும் ஒப்பிட்ட studies, retrieval பொதுவா ஜெயிக்குதுன்னு கண்டுபிடிச்சுது; base model-ஆல பார்க்கப்படாத facts-ல fine-tune பண்றது, நம்பிக்கையான தப்புகளை கூட ஊக்குவிக்கலாம். வடிவத்தை (format, tone, ஒரு narrow classification) கத்துக்கொடுக்க fine-tuning-ஐயும், facts தர retrieval-ஐயும் use பண்ணுங்க.

**முயற்சிகளோட வரிசை.** Prompt, அப்புறம் prompt கூட retrieval அல்லது tools, ஒரு அளந்த இடைவெளி இருந்து மேல இருக்குற numbers பொருந்துனா மட்டுமே fine-tuning. ஒவ்வொரு படியும் முந்தையதை baseline-ஆ வச்சுக்கும்.

## ஒரு worked example

புனேவுல ஒரு software company-ஓட மூணு problems:

1. *Support bot, வாரா வாரம் மாறுற ஒரு product handbook-ல இருந்து பதில் சொல்லணும்.* மாறுற knowledge: handbook மேல **RAG**, ஒவ்வொரு update-லயும் re-index. Fine-tuning ஒரு வாரத்துலயே பழசாகிடும்.
2. *Ticket summaries format-ல வேறுபடுது, customer-ஓட priority-ஐ விட்டுடுது.* Model-கிட்ட தகவல் இருக்கு; instruction தான் தெளிவில்ல. **Prompting**: ஒரு fixed template, priority பத்தின ஒரு rule, ரெண்டு examples, ஒரு மதியத்துல 90% cases-ஐ சரி பண்ணுது.
3. *மாசம் 20 லட்சம் log lines-ஐ 30 categories-ஆ ஒரு பெரிய model-ஓட classify பண்றது ரொம்ப செலவு.* பழைய வேலையில இருந்து அவங்ககிட்ட 50,000 labelled lines இருக்கு. ஒரு சின்ன model-ஐ **fine-tune** பண்றாங்க: அவங்க test set-ல, செலவு, latency-ல ஒரு சிறு பங்குல, பெரிய model-ஓட accuracy-க்கு சமமா இருக்கு.

| Problem | கண்டறிதல் | Approach | Result |
| --- | --- | --- | --- |
| Support bot, வாரா வாரம் மாறுற handbook | Knowledge | RAG, ஒவ்வொரு update-லயும் re-index | எப்பவும் தற்போதையது |
| Ticket summaries வேறுபடுது, priority-ஐ விட்டுடுது | Behaviour | Template, ஒரு priority rule, ரெண்டு examples | ஒரு மதியத்துல 90% சரியாச்சு |
| மாசம் 20 லட்சம் log lines, ரொம்ப செலவு | ஒரு narrow task-ல volume | 50,000 labels-ல fine-tune பண்ண சின்ன model | அதே accuracy, ரொம்ப குறைவான cost, latency |

## பொதுவா பண்ற தப்புகள்

- **Facts சேர்க்க fine-tune பண்றது.** Retrieval use பண்ணுங்க.
- **Prompting-ஐ தவிர்க்கிறது.** அதுதான் மலிவான fix, அடிக்கடி போதுமானது.
- **Fashion வச்சு தேர்ந்தெடுக்கிறது.** Knowledge-ஆ behaviour-ஆன்னு கண்டறியுங்க.
- **Evaluation set இல்லாதது.** அது இல்லாம approaches-ஐ ஒப்பிட முடியாது.
- **Maintenance-ஐ மறக்கிறது.** Fine-tuned models-ஐ திரும்ப train பண்ணணும்; RAG-க்கு புது indexes வேணும்.
- **வேற வேற test sets-ல** அல்லது வேற graders-ஓட approaches-ஐ ஒப்பிடுறது.
- **Fine-tuning cost-ல இருந்து மனுஷங்களோட நேரத்தை** விட்டுடுறது.
- **மாறுற facts-ஐ சேர்க்க fine-tune பண்றது**, அதை retrieval நல்லா handle பண்ணும்.

## தேர்வு ஏற்கனவே தெளிவா இருக்கும் நேரங்கள்

- **பதில் private documents-ஐ cite பண்ணணும்**: வேற என்ன சேர்த்தாலும், retrieval.
- **குறைவான volume**: fine-tuning அரிதா தான் பணத்தை திருப்பும்; prompt-ஐ மேம்படுத்துங்க.
- **Task ஒவ்வொரு சில வாரத்துக்கும் மாறுது**: மறுபடி train பண்றதை விட prompts, retrieval வேகமா மாறிக்கும்.
- **உங்ககிட்ட labelled examples இல்ல**: fine-tuning இன்னும் முடியாது; review பண்ண outputs-ல இருந்து அவற்றை சேகரிக்க ஆரம்பிங்க.

## Demo-ல இருந்து production-க்கு

- **ஒரு test set வச்சிருங்க**, problem type வாரியா பிரிச்சு, ஒவ்வொரு approach-க்கும் அதை use பண்ணுங்க.
- **ஒவ்வொரு option-க்கும் quality, cost, p95 latency-ஐ** தேதிகளோட பதிவு பண்ணுங்க.

- **Review பண்ண outputs-ஐ எதிர்கால training data-வா சேகரிங்க**, இன்னும் fine-tune பண்ணலைன்னாலும்.
- **புது base models நல்ல prompts-ஓட வரும்போது**, fine-tuned models-ஐ அவற்றுக்கு எதிரா திரும்ப test பண்ணுங்க.
