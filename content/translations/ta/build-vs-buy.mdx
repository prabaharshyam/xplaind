## இது என்ன

ஒவ்வொரு AI product idea-வும் ஆரம்பத்துலயே ரெண்டு கேள்விகளை சந்திக்கும். இதை தப்பா பண்ணா செலவு அதிகம்:

1. **Feasibility.** நம்ம real data-ல, ஏத்துக்கக்கூடிய cost-லயும் speed-லயும் AI இந்த வேலையை போதுமான அளவு நல்லா பண்ணுமா?
2. **Build vs buy.** ஒரு ready product-ஐ வாங்கணுமா, ஏற்கனவே use பண்ற platform-ல ஒரு AI feature-ஐ configure பண்ணணுமா, இல்ல சொந்தமா build பண்ணணுமா?

Teams பெரும்பாலும் முதல் கேள்வியை skip பண்ணிட்டு, ரெண்டாவதை பத்தி மாசக்கணக்கா விவாதிப்பாங்க. இதை விட நல்ல வரிசை: சில நாள்ல feasibility-ஐ test பண்ணுங்க, work ஆக முடியாத options-ஐ தள்ளுங்க, அப்புறம் மிச்சம் இருக்குறதை cost, risk வச்சு ஒப்பிடுங்க.

```flow

20-50 real examples-ல prototype -[நெருக்கம்]-> Options-ஐ screen பண்ணுங்க
Options-ஐ screen பண்ணுங்க -[fit அல்லது compliance-ல fail]-> தள்ளப்பட்டது
Options-ஐ screen பண்ணுங்க -[pass]-> ரெண்டு வருஷ cost-ஐ ஒப்பிடுங்க
ரெண்டு வருஷ cost-ஐ ஒப்பிடுங்க -> தேர்ந்தெடுத்து review date வைங்க
தேர்ந்தெடுத்து review date வைங்க -> Go-live-க்கு முன்னாடி பெரிய evaluation
```

இந்த lesson, Hyderabad-ல ஒரு hospital chain-ல product manager-ஆ இருக்குற Sana-வை follow பண்ணுது. AI discharge summaries-ஐ draft பண்ணுமான்னு அவங்க test பண்ணி, அப்புறம் அதை எப்படி deliver பண்றதுன்னு numbers வச்சு முடிவு பண்றாங்க. கடைசியில ஒரு quick feasibility test ஓட்டவும், முடிவோட ரெண்டு பக்கத்துக்கும் cost போடவும், ஒரு buy, configure அல்லது build தேர்வை நியாயப்படுத்தவும் உங்களால முடியும்.

## இது எப்படி work ஆகுது

### Step 1: சில நாள்ல prototype பண்ணுங்க

20 முதல் 50 **real** examples எடுங்க; personal data இருந்தா mask பண்ணுங்க. ஒரு capable model-ஓடயும் ஒரு simple prompt-ஓடயும் அந்த வேலையை try பண்ணுங்க, கையாலயோ ஒரு notebook-லயோ. இது தான் **proof of concept**: சின்னது, வேகமானது, நேர்மையானது. சுத்தமான cases மட்டும் இல்லாம, மோசமான scans, கலந்த மொழிகள், நீளமான records மாதிரி கஷ்டமான cases-ஐயும் use பண்ணுங்க.

அப்புறம் outputs-ஐ ஒரு **domain expert** judge பண்ணட்டும், prompt எழுதின engineers இல்ல. ஒண்ணை build பண்ணினவங்க page-ல என்ன இருக்குன்னு பாக்க மாட்டாங்க, தாங்க என்ன நினைச்சாங்களோ அதை தான் பாப்பாங்க. ஒவ்வொரு output-ஐயும் ஒரு simple scale-ல rate பண்ணுங்க:

| Rating | அர்த்தம் |
| --- | --- |
| Usable | சரி, அதிகபட்சம் சின்ன edits போதும் |
| Needs work | Idea சரி, பெரிய edits வேணும் |
| Unsafe அல்லது wrong | Use பண்ணா harm வரும் |

- Results ரொம்ப தூரத்துல இருந்தா, அந்த வேலை இன்னும் feasible இல்லாம இருக்கலாம். அதுக்கு கூடுதல் context, நல்ல data, அல்லது பின்னாடி வர்ற ஒரு நல்ல model தேவைப்படலாம்.
- Results நெருக்கமா இருந்தா, feasibility இருக்க வாய்ப்பு அதிகம். இப்போ நிஜ வேலை reliability, integration, safety, evaluation தான்; model இதை பண்ணவே முடியுமாங்கறது இல்ல.

இந்த 20 முதல் 50 examples-ஐயும் அவற்றோட ratings-ஐயும் வச்சுக்கோங்க. அது தான் உங்க முதல் evaluation set; ஒவ்வொரு vendor-ஐயும், பின்னாடி வர்ற ஒவ்வொரு model-ஐயும் இதே set-ல தான் ஓட்டுவீங்க.

### ஒரு சின்ன sample என்ன சொல்லும், என்ன சொல்லாது

ஒரு prototype "தொடரலாமா?"ங்கற கேள்விக்கு பதில் சொல்லும், "launch பண்றது safe-ஆ?"ங்கறதுக்கு இல்ல. சின்ன samples அரிதான failures-ஐ மறைச்சுடும்.

40 outputs-ல 2 unsafe-னு வச்சுக்கோங்க. அது 5% மாதிரி தெரியும். ஆனா 40 examples மட்டும் இருந்தா, உண்மையான unsafe rate 1%-க்கு கீழ இருந்து சுமார் 17% வரை எதுவா வேணும்னாலும் இருக்கலாம் (ஒரு exact 95% confidence interval). 300-ல 0 unsafe-னா கூட, உண்மையான rate பெரும்பாலும் சுமார் 1.2%-க்கு கீழ இருக்குன்னு மட்டும் தான் அது சொல்லும்.

அதனால rule இது தான்: feasibility-ஐ ஒரு சின்ன sample வச்சு முடிவு பண்ணுங்க, ஆனா go-live-ஐ இதை விட ரொம்ப பெரிய ஒரு evaluation வச்சு முடிவு பண்ணுங்க, அதுல எல்லாத்தையும் விட serious-ஆன failure type-ஐ தனியா count பண்ணுங்க.

### Step 2: cost, speed-ஐ estimate பண்ணுங்க

Prototype-ல இருந்து, ஒவ்வொரு request-உம் எத்தனை tokens use பண்ணுது, ஒவ்வொரு பதிலுக்கும் எவ்வளவு நேரம் ஆகுதுன்னு note பண்ணுங்க. அப்புறம் volume-ஆல பெருக்குங்க. உதாரணமா, விளக்கத்துக்காக கற்பனையா வச்ச prices-ஓட:

- ஒரு request 12,000 input tokens-உம் 1,000 output tokens-உம் use பண்ணுதுன்னு வச்சுக்கோங்க.
- Model-ஓட விலை ஒரு million input tokens-க்கு ₹250, ஒரு million output tokens-க்கு ₹1,000-னு வச்சுக்கோங்க.
- அப்போ ஒரு request-ஓட cost 12,000 × ₹250 ÷ 1,000,000 + 1,000 × ₹1,000 ÷ 1,000,000 = ₹3 + ₹1 = ₹4.

நிஜ prices அடிக்கடி மாறும். அவற்றை provider-ஓட pricing page-ல இருந்து எடுத்து, check பண்ணின தேதியை பக்கத்துலயே எழுதுங்க. Retries-க்கும் evaluation runs-க்கும் ஒரு margin சேருங்க, உதாரணமா 25%.

User-ஓட பொறுமைக்கு speed பொருந்துதான்னும் பாருங்க. ஒரு doctor ஒரு draft-க்கு பத்து seconds காத்திருப்பாரு, ரெண்டு நிமிஷம் இல்ல.

### Step 3: மூணு options-ஐ தெரிஞ்சுக்கோங்க

| Option | என்ன அது | பலம் | பலவீனம் |
| --- | --- | --- | --- |
| **Product வாங்குறது** | அந்த use case-க்கான ஒரு ready tool, உதாரணமா ஒரு document-processing service | எல்லாத்தையும் விட வேகம்; updates-ஐயும் model மாற்றங்களையும் vendor பாத்துப்பாங்க | Customisation குறைவு; vendor-ஓட roadmap; உங்க data vendor-கிட்ட போகும் |
| **Platform-ஐ configure பண்றது** | ஏற்கனவே use பண்ற software-க்குள்ள ஒரு AI feature, உதாரணமா உங்க CRM, help desk அல்லது hospital system | வேகம்; இருக்குற data-வையும் permissions-ஐயும் use பண்ணும் | Flexibility குறைவு; அந்த platform-ஓட கட்டுப்பட்டிருக்கும் |
| **Build** | ஒரு model API அல்லது open-weight model மேல உங்க சொந்த system | Fit, safety checks, data மேல எல்லாத்தையும் விட அதிக control | Engineers, evaluation, தொடர்ந்த maintenance வேணும் |

"Build"-க்குள்ள இன்னொரு முடிவு ஒளிஞ்சிருக்கு; regulated Indian sectors-ல பெரும்பாலும் அது தான் முடிவை தீர்மானிக்கும்:

| Build route | முக்கிய cost drivers | தேவையான skills | Data control |
| --- | --- | --- | --- |
| Hosted model API, முடிஞ்சா ஒரு Indian cloud region-ல | Token கணக்குல pay பண்றது; set-up கொஞ்சம் தான் | Prompting, evaluation, integration | உங்க contract-படி data cloud provider-கிட்ட போகும்; region-ஐயும் retention-ஐயும் check பண்ணுங்க |
| ஒரு open-weight model-ஐ self-host பண்றது | Idle-ஆ இருந்தாலும் நீங்க pay பண்ற GPUs, அவற்றை நடத்த ஆட்கள் | Model serving, scaling, security patching | Data உங்க சொந்த account-லயோ data centre-லயோ இருக்கும், ஆனா ஒவ்வொரு failure-உம் உங்க பொறுப்பு |

ஒரு நியாயமான default: hosted API-ல ஆரம்பிங்க. உங்க rules data-வை உங்க systems-ஐ விட்டு வெளியே போக விடாதபோது, அல்லது GPUs அரிதா தான் idle-ஆ இருக்குற அளவுக்கு volume அதிகமாவும் நிலையாவும் இருக்கும்போது மட்டும் self-host பண்ணுங்க. ஒவ்வொரு model-உம் கிடைக்கிறது cloud region-ஐ பொறுத்து மாறும், அதனால ஒரு model-ஐ சுத்தி design பண்றதுக்கு முன்னாடி region-ஐ check பண்ணுங்க.

### Step 4: screen பண்ணுங்க, அப்புறம் ஒப்பிடுங்க

சில factors pass அல்லது fail தான். அவற்றை முதல்ல check பண்ணுங்க, ஏன்னா எந்த விலையும் fail ஆகுற ஒரு option-ஐ ஏத்துக்கக்கூடியதா ஆக்காது:

1. **Fit.** உங்க languages, document formats, templates, workflows-ஐ அது handle பண்ணுமா? Vendor-ஓட demo data-ல இல்ல, உங்க சொந்த evaluation set-ல test பண்ணுங்க.
2. **Data, compliance.** Data எங்க போகலாம்? அது உங்க security, privacy, sector rules-ஐ பூர்த்தி பண்ணுதா?

அப்புறம் மீதியை எடை போடுங்க:

3. **Total cost of ownership**, ரெண்டு மூணு வருஷத்துக்கு (கீழ பாருங்க).
4. **Speed.** எவ்வளவு சீக்கிரம் value வேணும்? மாசக்கணக்கான delay-க்கும் ஒரு cost இருக்கு, உதாரணமா மிச்சப்படுத்தாம போன doctor hours.
5. **Differentiation.** இதை நீங்க நல்லா பண்றதால customers ஒரு competitor-ஐ விட்டு உங்களை தேர்ந்தெடுப்பாங்களா? உங்க sector-ல எல்லா firms-க்கும் இது ஒரே மாதிரி தேவைன்னா, அது commodity. "இது எங்களுக்கு முக்கியம்"னு சொல்றது test இல்ல: கிட்டத்தட்ட எல்லாமே முக்கியம் தான்.
6. **Lock-in.** பின்னாடி வெளியே வர்றது எவ்வளவு கஷ்டம்?

### Vendor due-diligence checklist

எந்த vendor கூடவும் sign பண்றதுக்கு முன்னாடி, இந்த ஏழு கேள்விகளுக்கு எழுத்துல பதில் வாங்குங்க:

1. **Location.** Backups, support access உட்பட, data எங்க store ஆகுது, எங்க process ஆகுது?
2. **Training.** Vendor-ஓ அவங்க model provider-ஓ உங்க data-ல train பண்றாங்களா? Contract-ல "இல்ல"-னு வாங்குங்க.
3. **Retention.** Data எவ்வளவு நாள் வச்சிருப்பாங்க, delete பண்ணினதை confirm பண்ணுவாங்களா?
4. **Sub-processors.** வேற யாரெல்லாம் data-வை தொடுறாங்க, உதாரணமா product-க்கு பின்னாடி இருக்குற model provider?
5. **Security evidence.** ISO 27001 மாதிரி certifications அல்லது ஒரு SOC 2 report, கூடவே சமீபத்துல பண்ணின ஒரு penetration test.
6. **Breach notice.** எவ்வளவு சீக்கிரம் உங்களுக்கு சொல்லுவாங்க? DPDP Act, CERT-In-ஓட rules-படி உங்களுக்கும் சொந்த கடமைகள் இருக்கலாம்.
7. **Exit.** உங்க data-வையும் outputs-ஐயும் use பண்ணக்கூடிய format-ல export பண்ண முடியுமா? Price அல்லது model மாற்றங்களுக்கு முன்னாடி எவ்வளவு notice கிடைக்கும்?

### Total cost of ownership

ரெண்டு பக்கத்தையும் முழுசா கணக்கு பண்ணுங்க. வாங்குறதுன்னா licence fee மட்டும் இல்ல: integration, ஒரு internal owner, quality checks, வெளியே வர்றதோட cost எல்லாம் இருக்கு. Build பண்றதுன்னா tokens மட்டும் இல்ல: engineers, evaluation, hosting, maintenance இருக்கு. எல்லா option-லயும் ஒரே மாதிரி இருக்குற costs, உதாரணமா ஒவ்வொரு output-ஐயும் review பண்ற expert நேரம், ஒண்ணையொண்ணு cancel பண்ணிடும், அதனால அவற்றை ஒப்பீட்டுல இருந்து விட்டுடலாம்.

Experienced teams-ஐ கூட ரெண்டு gotchas மாட்டிவிடும்:

- **Tokens-ஐ விட ஆட்களுக்கு தான் அதிக cost.** ஒரு build-ஓட total-ல model usage பெரும்பாலும் ஒரு சின்ன பகுதி தான். அப்படியே assume பண்றதுக்கு முன்னாடி உங்க சொந்த split-ஐ check பண்ணுங்க.
- **Sunk costs கேள்வியையே மாத்திடும்.** ஒரு தடவை build பண்ணிட்டா, செலவான பணம் போனது போனது தான். பின்னாடி ஒரு review-ல future costs-ஐ மட்டும் ஒப்பிடுங்க: உங்க build-ஐ ஓட்டுறது vs ஒரு vendor-க்கு மாறுறது.

உங்க finance team கூட tax-ஐயும் check பண்ணுங்க. IT, cloud services மேல GST 18% (November 2026 நிலவரப்படி). பெரும்பாலான healthcare services-க்கு GST-ல இருந்து exemption இருக்கு, அதனால ஒரு hospital பெரும்பாலும் அந்த tax-ஐ திரும்ப claim பண்ண முடியாது; இது ஒவ்வொரு vendor, cloud bill-ஓட நிஜ cost-ஐயும் கூட்டுது.

### மாற்றத்துக்கு plan பண்ணுங்க

பெரும்பாலான organisations கடைசியில கலந்து தான் பண்ணுவாங்க: commodity வேலைகளுக்கு வாங்குவாங்க, எதுவுமே பொருந்தாத இடத்துலயோ தாங்க வித்தியாசப்படுற இடத்துலயோ build பண்ணுவாங்க. நீங்க எதை தேர்ந்தெடுத்தாலும், models-உம் vendors-உம் உங்க காலுக்கு கீழயே மாறிக்கிட்டு இருக்கும்.

Model providers பழைய models-ஐ retire பண்ணுவாங்க. உதாரணமா, November 2026 நிலவரப்படி, publicly release ஆன ஒரு model-ஐ retire பண்றதுக்கு முன்னாடி குறைஞ்சது 60 நாள் notice தருவோம்னு Anthropic உறுதி தருது; அதுக்கு அப்புறம் அந்த model-க்கு போற requests fail ஆகும். Amazon Bedrock மாதிரி partner clouds தங்களோட சொந்த retirement schedules-ஐ வைக்கிறாங்க. அதனால குறைஞ்சது ஒரு model migration-க்கு budget வைங்க, replacement-ஐ test பண்ண உங்க evaluation set-ஐ ready-ஆ வச்சிருங்க. வாங்கும்போது, இதே problem-ஐ அவங்க எப்படி handle பண்றாங்கன்னு vendor-கிட்ட கேளுங்க.

## ஒரு worked example

Hyderabad-ல ஒரு hospital chain, doctors-ஓட notes-ஐயும் lab reports-ஐயும் வச்சு discharge summaries-ஐ AI draft பண்ணணும்னு நினைக்குது. நீண்ட shifts-ஓட கடைசியில, ஒவ்வொரு summary-க்கும் doctors 20 முதல் 30 நிமிஷம் செலவழிக்கிறாங்க. Chain மாசத்துக்கு சுமார் 6,000 discharges handle பண்ணுது. இந்த example-ல இருக்குற எல்லா numbers-உம் illustrative, கத்துக்குடுக்கிறதுக்காக கற்பனையா வச்சது.

### Feasibility

Sana, identity நீக்கின 40 patient records-ஐ சேகரிக்கிறாங்க. ஒரு capable model-ஐயும் hospital-ஓட summary template-ஐயும் use பண்ணி 40 drafts உருவாக்குறாங்க. மூணு senior doctors அவற்றை rate பண்றாங்க:

| Rating | Drafts | Notes |
| --- | --- | --- |
| சின்ன edits-ஓட usable | 31 | பெரும்பாலும் வார்த்தை மாற்றங்கள் |
| பெரிய edits வேணும் | 7 | முந்தைய notes-ல இருந்த context miss ஆச்சு |
| Unsafe | 2 | ரெண்டுலயும் ஒரு medication மாற்றம் miss ஆச்சு |

முடிவு: தொடர்ற அளவுக்கு feasible, ஆனா doctor sign-off கட்டாயமா இருந்து, draft-ல இருக்குற ஒவ்வொரு medication-ஐயும் pharmacy record கூட automatic-ஆ check பண்ணினா மட்டும். 40-ல 2 unsafe drafts-னா உண்மையான rate 1%-க்கு கீழ இருந்து சுமார் 17% வரை எதுவா வேணும்னாலும் இருக்கலாம், அதனால Sana launch-க்கு முன்னாடி 400 records-ல ஒரு evaluation plan பண்றாங்க, அதுல medication errors-ஐ தனியா count பண்ணுவாங்க.

### Options-ஐ screen பண்றது

அதே 40 records-ஐ அவங்க ஒவ்வொரு option-லயும் ஓட்டி, ஒவ்வொண்ணையும் hospital-ஓட data policy கூட check பண்றாங்க:

| Option | Sana கண்டுபிடிச்சது | முடிவு |

| Product B வாங்குறது | Data-வை India-க்கு வெளியே process பண்ணுது; hospital-ஓட data policy-படி hospital-ஓட legal team அதை reject பண்ணுது | Compliance காரணமா தள்ளப்பட்டது |

Build ஏன் ஜெயிச்சதுன்னு நேர்மையா இருங்க. Discharge summaries draft பண்றது இந்த hospital-ஐ வித்தியாசப்படுத்துற விஷயம் இல்ல: எல்லா hospital-க்கும் இது கிட்டத்தட்ட ஒரே மாதிரி தேவை. வேற எதுவுமே fit-லயும் compliance-லயும் pass ஆகாததால தான் build ஜெயிச்சது. அதனால தான் இந்த முடிவுக்கு ஒரு review date இருக்கு.

இந்த tool medical device software-ஆ கணக்கு ஆகுமான்னு team regulatory counsel-கிட்டயும் கேக்குது. India-வோட drug regulator CDSCO, Medical Devices Rules, 2017-ன் கீழ medical device software பத்தி guidance வெளியிட்டிருக்கு; ஒரு software device-ஆ இல்லையாங்கறது அதோட intended medical purpose-ஐ பொறுத்தது. அதனால team intended purpose-ஐ கவனமா எழுதி வைக்குது, build ஆரம்பிக்கிறதுக்கு முன்னாடியே counsel-ஓட கருத்தை எழுத்துல வாங்குது.

### Numbers Sana-வுக்கு என்ன சொல்லுது

- **ஆட்கள் தான் dominate பண்றாங்க.** Total-ல model usage சுமார் 8% தான். ஆட்கள் (build பண்றது, evaluate பண்றது, maintain பண்றது, migrate பண்றது) சுமார் 78%. Token price ரெட்டிப்பானா சுமார் 8% தான் கூடும். System-ஐ maintain பண்ற engineer போயிட்டா அதை விட ரொம்ப அதிகமா பாதிக்கும்.
- **Volume build-க்கு சாதகம்.** பெரும்பாலான cost fixed. மாசத்துக்கு 12,000 summaries-னா, illustrative total சுமார் ₹85 lakh வரை தான் கூடும் (அதே team-ஓட), அதாவது ஒரு summary-க்கு சுமார் ₹34. ஒரு vendor-ஓட per-summary fee volume கூடவே சேர்ந்து வளரும்.
- **இன்னைக்கு வாங்குறதுக்கான bar.** Build ஆரம்பிக்கிறதுக்கு முன்னாடி, fit-லயும் compliance-லயும் pass ஆகுற ஒரு vendor வந்திருந்தான்னு வச்சுக்கோங்க. அதோட costs integration (₹4 lakh), quality checks-ஓட ஒரு internal owner (மாசத்துக்கு ₹50,000); ஒரு மாசத்துக்கு அப்புறம் அது go live ஆகலாம். ரெண்டு வருஷத்துல, ஒரு summary-க்கு சுமார் ₹45-க்கு கீழ இருக்குற எந்த illustrative fee-லயும் அது build-ஐ ஜெயிக்கும்: (₹78.7 lakh − ₹4 lakh − ₹12 lakh) ÷ 138,000 summaries (23 live மாசத்துல) = சுமார் ₹45.
- **பின்னாடி switch பண்றதுக்கான bar.** Build ஆனதுக்கு அப்புறம், அதோட ₹22.5 lakh sunk. அப்போ அதை ஓட்ட மாசத்துக்கு சுமார் ₹2.37 lakh ஆகும், future migrations-க்கான ஒரு reserve உட்பட. Switch பண்ண integration, re-evaluation-க்கு சுமார் ₹7 lakh ஆகும், அதாவது 24 மாசத்துக்கு பரப்பினா மாசத்துக்கு சுமார் ₹0.29 lakh. அதனால switch பண்றது worth-ஆ இருக்கணும்னா, compliant-ஆன ஒரு vendor இப்போ ஒரு summary-க்கு illustrative ₹26-க்கு கீழ charge பண்ணணும்: (₹2.37 lakh − ₹0.5 lakh − ₹0.29 lakh) ÷ 6,000 = சுமார் ₹26.

### முடிவு

Leadership build-ஐ approve பண்ணுது, self-hosted model-ல இல்லாம ஒரு hosted API மேல, ஏன்னா GPUs ஓட்டுற அளவுக்கு volume இல்ல. Model-ஐ மாத்த முடியணும்னு, Sana prompts, medication check, 400-record evaluation set எல்லாத்தையும் hospital-ஓட சொந்த கையிலயே வச்சிருக்காங்க. வருஷாந்திர market review-க்கு ஒரு concrete trigger இருக்கு: ஒரு product fit-லயும் compliance-லயும் pass ஆகி, ஒரு summary-க்கு சுமார் ₹26-க்கு கீழ வந்தா (illustrative switching bar), அல்லது volume-ஓ rules-ஓ மாறினா, மறுபடி பாருங்க.

## பொதுவான தப்புகள்

- **Prototype-ஐ skip பண்றது.** Feasibility பத்தின guesses பெரும்பாலும் ரெண்டு பக்கமும் தப்பா போகும்.
- **ஒரு prototype-ஐ launch evidence-ஆ எடுத்துக்கறது.** 40-ல 2 unsafe-னா, அது பெரிய அளவுல evaluate பண்றதுக்கான காரணம், அளந்த ஒரு 5% rate இல்ல.
- **Build பண்ணினவங்களே தங்க outputs-ஐ judge பண்றது.** எழுதி வச்ச ஒரு rubric வச்சு domain experts-ஐ கேளுங்க.
- **Vendors-ஐ அவங்க demo data வச்சு judge பண்றது.** ஒவ்வொரு option-ஐயும் உங்க சொந்த evaluation set-ல ஓட்டுங்க.
- **உங்களுக்கு முக்கியம்ங்கறதால ஒண்ணை differentiating-னு சொல்றது.** அதனால customers உங்களை தேர்ந்தெடுப்பாங்களான்னு கேளுங்க.
- **ஒரு licence fee-ஐ token costs கூட மட்டும் ஒப்பிடுறது.** Build பண்றதோட cost-ல பெரும்பகுதி ஆட்கள், evaluation, maintenance, migrations தான்.
- **Review நேரத்துல sunk costs-ஐ கவனிக்காம விடுறது.** Build ஆனதுக்கு அப்புறம், future costs-ஐ மட்டும் ஒப்பிடுங்க.
- **Exit-ஐ மறக்கிறது.** Sign பண்றதுக்கு முன்னாடி data export, notice terms-ஐ ஒத்துக்கோங்க, உங்க evaluation set-ஐ உங்க கையிலயே வச்சுக்கோங்க.

## Practice

கீழ link பண்ணியிருக்குற SVPG-ஓட four big risks-ஐயும், Hamel Husain-ஓட field guide-ஐயும் படிங்க.

1. **Prototype.** 20 real examples-ல ஒரு AI வேலையை try பண்ணுங்க. அந்த domain தெரிஞ்ச ஒருத்தர் outputs-ஐ usable, needs work, அல்லது unsafe-னு rate பண்ணட்டும். அந்த sample எதை சொல்லாதுன்னு எழுதி வைங்க.
2. **Screen.** ஒரே வேலையை solve பண்றோம்னு சொல்ற ரெண்டு products-ஐயும் ஒரு platform feature-ஐயும் கண்டுபிடிங்க. உங்க examples-ஐ ஒவ்வொண்ணுலயும் ஓட்டுங்க, அதுல ஒண்ணுக்கு ஏழு due-diligence கேள்விகளுக்கும் பதில் எழுதுங்க.
3. **Cost.** Build route-க்கு, Sana-வோட style-ல ஒரு ரெண்டு வருஷ cost table போடுங்க; ஒவ்வொரு figure-ஐயும் estimate-னு mark பண்ணுங்க. ஒரு unit-க்கு vendor fee எவ்வளவா இருந்தா வாங்குறது ஜெயிக்கும்னு கணக்கு பண்ணுங்க.
4. **Recommend.** ஒரு review date-உம், முடிவை மறுபடி திறக்க ஒரு concrete trigger-உம் இருக்குற ஒரு பக்க buy, configure அல்லது build பரிந்துரையை எழுதுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** expert rate பண்ணின prototype results-ஐயும், costing பண்ணின ஒரு ரெண்டு வருஷ ஒப்பீட்டையும், fit, compliance, cost, lock-in வச்சு நியாயப்படுத்தக்கூடிய ஒரு தேர்வையும் காட்ட முடியும்போது.
