## இது என்ன

ஒவ்வொரு AI product idea-வும் ஆரம்பத்திலயே ரெண்டு கேள்விகளை சந்திக்கும். இதை தப்பா பண்ணா செலவு அதிகம்:

1. **Feasibility.** நம்ம real data-ல, ஏத்துக்கக்கூடிய cost-லயும் speed-லயும் AI இந்த வேலையை போதுமான அளவு நல்லா பண்ணுமா?
2. **Build vs buy.** ஒரு ready product-ஐ வாங்குறதா, ஏற்கனவே use பண்ற platform-ல ஒரு AI feature-ஐ configure பண்றதா, இல்ல சொந்தமா build பண்றதா?

Teams பெரும்பாலும் முதல் கேள்வியை skip பண்ணிட்டு, ரெண்டாவதை பத்தி மாசக்கணக்கா விவாதிப்பாங்க. சரியான வரிசை: சில நாள்ல feasibility-ஐ test பண்ணுங்க, அப்புறம் எப்படி deliver பண்றதுன்னு தேர்ந்தெடுங்க.

```flow
Idea -> 20-50 real examples-ல prototype | மாசங்கள் இல்ல, நாட்கள்
20-50 real examples-ல prototype -[ரொம்ப தூரம்]-> இன்னும் feasible இல்ல | கூடுதல் context அல்லது data வேணும், இல்லன்னா காத்திருக்கணும்
20-50 real examples-ல prototype -[நெருக்கம்]-> Feasible: இப்போ எப்படி deliver பண்றதுன்னு முடிவு பண்ணு
Feasible: இப்போ எப்படி deliver பண்றதுன்னு முடிவு பண்ணு -> Product வாங்கு
Feasible: இப்போ எப்படி deliver பண்றதுன்னு முடிவு பண்ணு -> Platform-ஐ configure பண்ணு
Feasible: இப்போ எப்படி deliver பண்றதுன்னு முடிவு பண்ணு -> சொந்த system-ஐ build பண்ணு
```

இந்த lesson Hyderabad-ல ஒரு hospital chain-ல product manager-ஆ இருக்குற Sana-வை follow பண்ணுது. AI discharge summaries-ஐ draft பண்ணுமான்னு அவங்க test பண்ணி, அப்புறம் எப்படி deliver பண்றதுன்னு முடிவு பண்றாங்க. கடைசியில ஒரு quick feasibility test ஓட்டி, build, configure, buy முடிவை நியாயப்படுத்த முடியும்.

## இது எப்படி work ஆகுது

### சில நாள்ல prototype பண்ணுங்க

20 முதல் 50 **real** examples எடுங்க, personal data இருந்தா mask பண்ணி. ஒரு திறமையான model-ஓடயும் ஒரு simple prompt-ஓடயும் அந்த வேலையை try பண்ணுங்க, கையால அல்லது ஒரு notebook-ல. இதுதான் **proof of concept**: சின்னது, வேகமானது, நேர்மையானது.

அப்புறம் outputs-ஐ **domain expert** judge பண்ணட்டும், prompt எழுதின engineers இல்ல. ஒரு simple scale-ல ஒவ்வொரு output-ஐயும் rate பண்ணுங்க:

| Rating | அர்த்தம் |
| --- | --- |
| Usable | சரி, அதிகபட்சம் சின்ன edits போதும் |
| Needs work | Idea சரி, பெரிய edits வேணும் |
| Unsafe அல்லது wrong | Use பண்ணா harm வரும் |

- Results ரொம்ப தூரத்துல இருந்தா, அந்த வேலை இன்னும் feasible இல்லாம இருக்கலாம், அல்லது கூடுதல் context அல்லது data வேணும்.
- Results நெருக்கமா இருந்தா, feasibility இருக்க வாய்ப்பு அதிகம், நிஜ வேலை reliability, integration, safety, evaluation.

### Cost, speed-ஐ estimate பண்ணுங்க

Prototype-ல இருந்து, ஒரு request-க்கு tokens எவ்வளவு, ஒவ்வொரு பதிலுக்கும் எவ்வளவு நேரம் ஆகுதுன்னு அளந்துக்கோங்க. எதிர்பார்க்குற volume-ஆல பெருக்குங்க. அது budget-க்கும் user-ஓட பொறுமைக்கும் பொருந்துதான்னு பாருங்க: ஒரு doctor draft-க்கு பத்து seconds காத்திருப்பாரு, ரெண்டு நிமிஷம் இல்ல.

### மூணு options

| Option | என்ன | பலம் | பலவீனம் |
| --- | --- | --- | --- |
| **Product வாங்குறது** | Meeting-notes tool அல்லது document-processing service மாதிரி, அந்த use case-க்கான ready tool | ரொம்ப வேகம்; updates-ஐ vendor பார்த்துப்பாங்க | Customisation குறைவு; vendor-ஓட roadmap; உங்க data vendor-கிட்ட போகும் |
| **Platform-ஐ configure பண்றது** | உங்க CRM, help desk, office suite மாதிரி ஏற்கனவே use பண்ற software-க்குள்ள ஒரு AI feature | வேகம்; இருக்குற data-வையும் permissions-ஐயும் use பண்ணும் | Flexibility குறைவு; அந்த platform-ஓட கட்டுப்பட்டிருக்கும் |
| **Build** | Model APIs அல்லது open models மேல சொந்த system | அதிக control, differentiation | Engineers, evaluation, தொடர்ந்து maintenance வேணும் |

### முடிவு பண்ற factors

1. **Differentiation.** இது நீங்க போட்டியிடுற விதத்தோட core-ஆ? உங்களை வித்தியாசப்படுத்துறதை build பண்ணுங்க; commodity functions-ஐ வாங்குங்க.
2. **Data, compliance.** Data எங்க போகலாம்? Vendor உங்க security, privacy, sector rules-ஐ பூர்த்தி பண்றாங்களா?
3. **Fit.** உங்க languages, document formats, workflows-ஐ அது handle பண்ணுமா?
4. **Total cost of ownership.** இரண்டு மூணு வருஷத்துக்கு licences அல்லது usage, integration, அதை நடத்துற ஆட்கள்.
5. **Speed.** எவ்வளவு சீக்கிரம் value வேணும்?
6. **Lock-in.** பின்னாடி மாறுறது எவ்வளவு கஷ்டம்?

### Hybrid சாதாரணம்

பெரும்பாலான organisations கடைசியில கலந்து தான் பண்ணுவாங்க: commodity வேலைகளுக்கு வாங்குவாங்க, தங்களை வித்தியாசப்படுத்துறதுல build பண்ணுவாங்க, standard interfaces வச்சு பின்னாடி models அல்லது vendors-ஐ மாத்திக்க options-ஐ திறந்து வச்சிருப்பாங்க.

## ஒரு worked example

Hyderabad-ல ஒரு hospital chain, doctors-ஓட notes-ஐயும் lab reports-ஐயும் வச்சு discharge summaries-ஐ AI draft பண்ணணும்னு நினைக்குது. நீண்ட shifts-ஓட கடைசியில, ஒவ்வொரு summary-க்கும் doctors 20 முதல் 30 நிமிஷம் செலவழிக்கிறாங்க.

**Feasibility.** Product manager Sana, identity நீக்கின 40 patient records-ஐ சேகரிக்கிறாங்க. ஒரு திறமையான model-ஐயும் hospital-ஓட summary template-ஐயும் use பண்ணி 40 drafts உருவாக்குறாங்க. மூணு senior doctors அவற்றை rate பண்றாங்க:

| Rating | Drafts | Notes |
| --- | --- | --- |
| சின்ன edits-ஓட usable | 31 | பெரும்பாலும் வார்த்தை மாற்றங்கள் |
| பெரிய edits வேணும் | 7 | முந்தைய notes-ல இருந்த context miss ஆச்சு |
| Unsafe | 2 | ரெண்டுலயும் ஒரு medication மாற்றம் miss ஆச்சு |

முடிவு: feasible, ஆனா doctor review கட்டாயம், pharmacy record-ஓட ஒரு automatic medication cross-check-உம் இருந்தா மட்டும்.

**Options:**

| Option | Sana கண்டுபிடிச்சது | முடிவு |
| --- | --- | --- |
| Product A வாங்குறது | அவங்க hospital information system-ஓட integrate ஆகல | Fit காரணமா தள்ளப்பட்டது |
| Product B வாங்குறது | Data-வை India-க்கு வெளியே process பண்ணுது; hospital-ஓட legal team reject பண்ணுச்சு | Compliance காரணமா தள்ளப்பட்டது |
| Hospital system vendor-ஓட add-on-ஐ configure பண்றது | அவங்க template-க்கோ medication checks-க்கோ customise பண்ண முடியல | Fit, safety காரணமா தள்ளப்பட்டது |
| Build | ஏற்கனவே use பண்ற cloud-ஓட India region-ல கிடைக்குற ஒரு model மேல ஒரு சின்ன team build பண்ணும், hospital system-ஓட integrate ஆகி, medication cross-check, doctor sign-off-ஓட | பரிந்துரைக்கப்பட்டது |

**Cost.** Build பண்ண மூணு மாசம் ஆகும்னும், மாசம் சுமார் 6,000 discharges என்ற அவங்க volume-ல ரெண்டு வருஷ total cost, add-on-ஓட licences-ஐ விட குறைவா இருக்கும்னும் அவங்க estimate பண்றாங்க. Discharge summaries-ஓட quality, patient care-ல hospital எப்படி போட்டியிடுதுங்கறதுக்கும் முக்கியம், அதனால build பண்றது நிஜமான differentiation தரும்.

தலைமை build-ஐ approve பண்ணுது. ஒரு வருஷத்துல, அவங்க rules-ஐ பூர்த்தி பண்ற ஒரு product வந்திருக்கான்னு market-ஐ review பண்ணுவாங்க.

## பொதுவான தப்புகள்

- **Prototype-ஐ skip பண்றது.** Feasibility guesses பெரும்பாலும் ரெண்டு பக்கமும் தப்பா போகும்.
- **Build பண்றவங்களே தங்க outputs-ஐ judge பண்றது.** Domain experts-ஐ கேளுங்க.
- **Commodity features-ஐ build பண்றது.** உங்களை வித்தியாசப்படுத்தாததை வாங்குங்க.
- **Data handling-ஐ check பண்ணாம வாங்குறது.** வேற விதத்துல நல்ல products-ஐ கூட compliance தள்ளிடலாம்.
- **ஒரு licence விலையை எதுவுமே இல்லாததோட ஒப்பிடுறது.** Build பண்றதுக்கும் ஆட்கள், maintenance cost இருக்கு.
- **Lock-in-ஐ மறக்கிறது.** Sign பண்றதுக்கு முன்னாடி எப்படி வெளியேறுவீங்கன்னு தெரிஞ்சுக்கோங்க.

## Practice

கீழ link பண்ணியிருக்குற SVPG-ஓட four big risks-ஐயும், Hamel Husain-ஓட field guide-ஐயும் மறுபடி படிங்க.

1. **Prototype.** 20 real examples-ல ஒரு AI வேலையை try பண்ணுங்க, அந்த domain தெரிஞ்ச ஒருத்தரை outputs-ஐ rate பண்ண சொல்லுங்க.
2. **Compare.** ஒரே வேலையை solve பண்றோம்னு சொல்ற ரெண்டு products-ஐயும் ஒரு platform feature-ஐயும் கண்டுபிடிங்க. Fit, data handling, cost, lock-in வச்சு ஒப்பிடுங்க.
3. **Recommend.** ரெண்டு வருஷ cost estimate-ஓட ஒரு பக்க build, configure அல்லது buy பரிந்துரையை எழுதுங்க.

**இது முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு expert rate பண்ணின prototype results-ஐ காட்டி, உங்க build-vs-buy தேர்வை நாலு factors வச்சு நியாயப்படுத்த முடியும்போது.
