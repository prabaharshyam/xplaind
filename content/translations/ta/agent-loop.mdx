## இது என்ன

**Agent**-னா tools-ஓட ஒரு loop-ல ஓடுற model: அடுத்து என்ன செய்யணும்னு முடிவு பண்ணும், ஒரு tool-ஐ கூப்பிடும், result-ஐ படிக்கும், மறுபடி முடிவு பண்ணும்; task முடியுற வரை அல்லது நிறுத்த வேண்டிய நிலை வர்ற வரை. Loop எழுதுறது சின்ன வேலை; அதை நம்பகமா ஆக்குறது தான் கஷ்டம்.

Anthropic-ஓட "Building effective agents" article மாதிரியே, ரெண்டு designs-ஐ பிரிச்சு பார்க்குறது உதவும்:

- ஒரு **workflow**: steps-ஐ உங்க code முடிவு பண்ணும் (முதல்ல classify, அப்புறம் retrieve, அப்புறம் draft). ஒவ்வொரு step-லயும் model நிரப்பும். Predictable, test பண்ண ஈஸி.
- ஒரு **agent**: steps-ஐயும் எத்தனைங்குறதையும் model முடிவு பண்ணும், போகப்போக tools-ஐ தேர்ந்தெடுக்கும். Open-ended tasks-க்கு flexible, predict பண்ண கஷ்டம்.

Steps தெரிஞ்சா workflow use பண்ணுங்க; தெரியலன்னா agent use பண்ணுங்க.

```flow
Model | task + history + tool list -> Tool வேணுமா?
Tool வேணுமா? -[இல்லை]-> இறுதி பதில், நிறுத்து
Tool வேணுமா? -[ஆமா]-> உங்க code tool-ஐ run பண்ணும் -> Step count limit-ஐ தாண்டிச்சா?
Step count limit-ஐ தாண்டிச்சா? -[இல்லை: result-ஐ சேருங்க]-> Model
Step count limit-ஐ தாண்டிச்சா? -[ஆமா]-> சுத்தமா நிறுத்தி, ஒரு ஆள்கிட்ட handover பண்ணு
```

இந்த lesson-ல Bengaluru-ல ஒரு travel startup, weekend trips plan பண்ற ஒரு assistant build பண்றதை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**முக்கிய loop.**

```python
messages = [{"role": "user", "content": task}]
for step in range(MAX_STEPS):
    reply = call_model(messages, tools=TOOLS)
    messages.append({"role": "assistant", "content": reply.content})
    if not reply.tool_calls:                 # the model is done
        return reply.text
    results = [run_tool(c.name, c.args) for c in reply.tool_calls]
    messages.append({"role": "user", "content": results})
raise RuntimeError("Step limit reached; hand over to a person")
```

ஒவ்வொரு round-லயும்: model task-ஐயும், இதுவரை நடந்த எல்லாத்தையும், tool list-ஐயும் பார்க்கும்; ஒண்ணு பதில் சொல்லும், இல்லன்னா tools கேக்கும்; உங்க code அவற்றை run பண்ணி results-ஐ சேர்க்கும்.

**நிறுத்துறது.** Model tools கேக்காம பதில் சொல்லும்போது loop முடியும். எப்பவும் ஒரு **maximum steps** எண்ணிக்கை சேருங்க; அப்போ குழம்பிப்போன agent என்றென்றும் loop ஆகி, பணத்தை எரிச்சு, actions-ஐ repeat பண்ணாது; அது வந்ததும் சுத்தமா நிறுத்தி handover பண்ணுங்க.

**நல்ல tools நல்ல agents-ஐ தரும்.** தெளிவா, நல்லா விவரிச்ச, உதவியான errors இருக்குற சில tools, புத்திசாலித்தனமான prompting-ஐ விட அதிகம் முக்கியம்.

**System prompt** agent-க்கு அதோட goal-ஐயும், tools-ஓட நோக்கத்தையும், முடிஞ்சுதுன்னு எப்படி முடிவு பண்றதுன்னும், confirmation இல்லாம எதை ஒருபோதும் செய்யக்கூடாதுன்னும் சொல்லும்.

**எளிமையா ஆரம்பிங்க.** நிறைய tasks ஒரே model call + retrieval-ஓட, அல்லது ஒரு சின்ன workflow-ஓட வேலை செய்யும். Steps-ஓட எண்ணிக்கையும் வரிசையும் நிஜமாவே மாறும்போது மட்டும் agent loops சேருங்க.

**Workflow vs agent:**

| அம்சம் | Workflow | Agent |
| --- | --- | --- |
| Steps-ஐ யார் முடிவு பண்றாங்க | உங்க code | Model |
| Predictability | அதிகம் | குறைவு |
| Testing | ஒவ்வொரு step-ஐயும் test பண்ணுங்க | பல runs முழுக்க outcomes-ஐ test பண்ணுங்க |
| ஒரு task-க்கு cost | நிலையானது, estimate பண்ண ஈஸி | Steps எண்ணிக்கையை பொறுத்து மாறும் |
| எதுக்கு best | தெரிஞ்ச, திரும்ப நடக்குற processes | Steps மாறுற open-ended tasks |

**நம்பகத்தன்மை ஏன் கஷ்டம்.** Errors சேரும். ஒவ்வொரு step-உம் 95% நேரம் சரியா போனா, பத்து-step task-ஓட பத்து steps-உம் சரியா போறது கிட்டத்தட்ட 60% நேரம் மட்டுமே (0.95-ஐ 10-ஆம் அடுக்கு). அதனாலதான் குறுகிய plans, நல்ல tools, வழியில checks ரொம்ப முக்கியம்; அதனாலதான் மூணு fixed steps இருக்குற workflow, ஒரு free agent-ஐ அடிக்கடி ஜெயிக்கும்.

**Planning.** ரெண்டு பொதுவான styles:

- **மாறி மாறி யோசிச்சு செயல்படுறது** (ReAct pattern): ஒவ்வொரு step-லயும் model சுருக்கமா reason பண்ணும், ஒரு action எடுக்கும், result-ஐ படிக்கும், மறுபடி முடிவு பண்ணும். மேல இருக்குற loop இதைத்தான் பண்ணுது, பெரும்பாலான agents இதை use பண்ணும்.
- **முதல்ல plan, அப்புறம் execute**: model முழு plan-ஐயும் எழுதும், உங்க code அதை check பண்ணும் (tools நிஜமானவையா, arguments அர்த்தமுள்ளதா, budget-க்குள்ள இருக்கா), அதுக்கு அப்புறம் தான் run பண்ணும். செயல்படுறதுக்கு முன்னாடி plan-ஐ check பண்றது, actions-ஐ undo பண்றதை விட மலிவு; அதிக risk இருக்குற tasks-க்கு ஒரு ஆள் plan-ஐ approve பண்ணலாம்.

**Reflection.** சரியான நேரங்கள்ல agent தன்னோட வேலையை தானே check பண்ணும்போது நல்லா செய்யும்: request சாத்தியமே இல்லையா, plan அர்த்தமுள்ளதா, இந்த step வேலை செஞ்சுதா, task நிஜமாவே முடிஞ்சுதா? அந்த check அதே model-க்கு ஒரு prompt-ஆ இருக்கலாம், reviewer-ஆ செயல்படுற தனி model-ஆ இருக்கலாம், அல்லது generate ஆன code-ல tests-ஐ run பண்றது மாதிரி சாதாரண code-ஆ இருக்கலாம். Reflection-க்கு கூடுதல் tokens, நேரம் ஆகும்; அதனால தப்புகள் costly-ஆ இருக்குற இடத்துல சேருங்க.

**Run பண்ணக்கூடிய ஒரு loop.** இந்த version Anthropic-ஓட Python SDK-ஐ use பண்ணுது, tool errors-ஐ crash ஆகாம model-க்கு திருப்பி தருது, step limit, budget அல்லது repeat ஆகுற ஒரே calls-ல நிக்குது, ஒவ்வொரு step-ஐயும் log பண்ணுது:

```python
import json
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"          # check the docs for current model names
MAX_STEPS, MAX_TOKENS_TOTAL = 10, 60_000

def run_agent(task, tools, handlers, system):
    messages = [{"role": "user", "content": task}]
    seen, used = {}, 0
    for step in range(1, MAX_STEPS + 1):
        reply = client.messages.create(model=MODEL, max_tokens=1000, system=system,
                                       tools=tools, messages=messages)
        used += reply.usage.input_tokens + reply.usage.output_tokens
        messages.append({"role": "assistant", "content": reply.content})
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return "".join(b.text for b in reply.content if b.type == "text"), step
        results = []
        for call in calls:
            key = call.name + json.dumps(call.input, sort_keys=True)
            seen[key] = seen.get(key, 0) + 1
            try:
                if seen[key] > 2:
                    raise RuntimeError("Same call made twice already; try something different or stop.")
                if call.name not in handlers:
                    raise RuntimeError(f"No tool named {call.name}; use one of {sorted(handlers)}.")
                output, is_error = handlers[call.name](**call.input), False
            except Exception as err:                        # unknown tool, bad arguments, tool failure
                output, is_error = f"Error: {err}", True
            print(f"step {step}: {call.name}({call.input}) -> {str(output)[:80]}")
            results.append({"type": "tool_result", "tool_use_id": call.id,
                            "content": str(output), "is_error": is_error})
        messages.append({"role": "user", "content": results})
        if used > MAX_TOKENS_TOTAL:
            break
    return None, step                                       # hand over to a person
```

`handlers` ஒவ்வொரு tool பேரையும் ஒரு Python function-ஓட map பண்ணும். தெரியாத tool பேர், தப்பான arguments, fail ஆகுற tool எல்லாமே run-ஐ crash பண்றதுக்கு பதிலா ஒரு தெளிவான error-ஆ model-க்கு திரும்பி போகும்; அதனால அது தன்னை சரி பண்ணிக்கலாம். Tools-ஐ எப்படி define பண்றதுன்னு tool-calling lesson காட்டும்.

**Agents எப்படி fail ஆகுது, அதை எப்படி measure பண்றது.** சாதாரண தப்பான பதில்களுக்கு மேல, agents-க்கு தங்களுக்குனு failure modes இருக்கு. அவற்றுக்கு பேர் வைங்க, அப்புறம் test tasks-ஓட ஒரு set முழுக்க ஒவ்வொண்ணும் எவ்வளவு அடிக்கடி நடக்குதுன்னு எண்ணுங்க:

| Failure | Example | எப்படி கண்டுபிடிக்கிறது |
| --- | --- | --- |
| Invalid tool | இல்லாத `book_hotel`-ஐ கூப்பிடுது | Logs-ல தெரியாத tool பேர்களை எண்ணுங்க |
| Invalid arguments | தேவையான `dates`-ஐ விட்டுடுது | ஒரு tool-க்கு validation errors |
| தப்பான argument values | Coorg-க்கு தப்பான weekend-ஐ search பண்ணுது | Test tasks-ல expected values-ஓட compare பண்ணுங்க |
| Goal failure | ₹25,000 budget-ல ₹31,000 ஆகுற plan | Run-க்கு அப்புறம் code-ல constraints-ஐ check பண்ணுங்க |
| பொய்யான "done" | 12 guests-ல 9 பேர் தான் book ஆனப்போ எல்லாரும் book ஆயிட்டாங்கன்னு சொல்லுது | Agent-ஓட claim-ஐ இல்லாம, final state-ஐ check பண்ணுங்க |
| Tool failure | Stays API பழைய prices-ஐ தருது | ஒவ்வொரு tool-ஐயும் தனியா test பண்ணுங்க |
| Inefficiency | 5 steps போதும்ங்குற இடத்துல 14 steps | ஒரு task-க்கு steps, tokens, நேரம், cost |

20-ல இருந்து 50 நிஜமான test tasks-ஐ வச்சுக்கோங்க, ஒவ்வொண்ணுக்கும் வெற்றின்னா என்னன்னு சேர்த்து; ஒவ்வொரு prompt, tool அல்லது model மாற்றத்துக்கு அப்புறமும் அவற்றை run பண்ணி, success rate, சராசரி steps, ஒரு task-க்கு cost-ஐ track பண்ணுங்க.

**ஒவ்வொரு step-லயும் context வளருது.** ஒவ்வொரு tool result-உம் conversation-ல தங்கிடும்; அதனால நீளமான runs slow-ஆவும் costly-ஆவும் ஆகும், model-உம் track-ஐ இழக்கலாம். சுருக்கமான, relevant ஆன tool results-ஐ திருப்பி தாங்க (top five stays, ஐநூறு இல்லை), நீளமான runs-ல பழைய results-ஐ summarise பண்ணுங்க அல்லது போட்டுடுங்க.

**பொதுவான workflow வடிவங்கள்.** ஒரு agent-ஐ நாடுறதுக்கு முன்னாடி, இவற்றுல ஒண்ணு பொருந்துதான்னு பாருங்க. ஒரு **chain** fixed steps-ஐ வரிசையா run பண்ணும், உதாரணம் extract, அப்புறம் check, அப்புறம் draft. ஒரு **router** request-ஐ classify பண்ணி, specialised prompts-ல ஒண்ணுக்கு அனுப்பும். **Parallel** calls ஒரு task-ஐ independent பகுதிகளா பிரிச்சு, results-ஐ merge பண்ணும். ஒரு **evaluator loop**-ல ஒரு call draft பண்ணும், இன்னொண்ணு criteria-க்கு எதிரா check பண்ணும், ஒரு fixed எண்ணிக்கை தடவை repeat ஆகும். Agents-ன்னு சொல்லப்படுற நிறைய products நிஜமா இந்த வடிவங்கள்ல ஒண்ணு தான், அவற்றை test பண்ணவும் ஈஸி.

**ஆரம்ப runs-ல என்ன கவனிக்கணும்.** இருபது நிஜ tasks-க்கு ஒவ்வொரு step-ஓட tool-ஐயும் arguments-ஐயும் print பண்ணுங்க. சின்ன மாற்றங்களோட repeat ஆகுற calls, model ஒருபோதும் use பண்ணாத tools, ஒரு result-ஐ அது தப்பா படிக்கிற steps இதை பாருங்க. ஒவ்வொரு pattern-உம் ஒரு tool-ஓட description-லயோ, அதோட error messages-லயோ, system prompt-ல இருக்குற stop condition-லயோ ஒரு fix-ஐ காட்டும்.

## ஒரு example

Bengaluru-ல ஒரு travel startup, "Bengaluru-ல இருந்து ரெண்டு பேருக்கு, ₹25,000-க்குள்ள, Coorg-ல 3-நாள் weekend-ஐ plan பண்ணு"ன்னு பதில் சொல்ற ஒரு assistant-ஐ விரும்புது.

Tools: `search_stays(location, dates, budget)`, `get_travel_options(from, to, date)`, `get_weather(location, dates)`.

ஒரு run:

1. Model அந்த dates-ல Coorg-க்கு `get_weather`-ஐ கூப்பிடுது: லேசான மழை எதிர்பார்க்கப்படுது.
2. `get_travel_options`-ஐ கூப்பிடுது: 6 மணி நேர drive அல்லது ஒரு bus.
3. ரெண்டு இரவுக்கு ₹14,000 budget-ஓட `search_stays`-ஐ கூப்பிடுது: மூணு homestays திரும்ப வருது.
4. ஒரு plan-ஓட பதில் சொல்லுது: drive, மழையை வச்சு மூடிய sit-out இருக்குற ஒரு homestay, indoor-க்கு ஏத்த ரெண்டு activities, சுமார் ₹22,000 cost breakdown.

நாலு model calls, மூணு tool calls. 10 steps cap இருந்தப்போ, ஒரு தடவை எதுவும் பொருந்தாதப்போ ஒரு run லேசா மாறுன budgets-ஓட `search_stays`-ல loop ஆச்சு; அது cap-ல நின்னுது, app "அந்த budget-ல stays கிடைக்கல; வேற dates try பண்ணுங்க"ன்னு காட்டுச்சு. அப்புறம் team tool-ஐ "₹X-க்குள்ள stays இல்லை; குறைந்தது ₹Y"ன்னு திருப்பி தர்ற மாதிரி மேம்படுத்துச்சு, loop சுத்துறது நின்னுது.

| Run | Steps | Outcome | செஞ்ச மாற்றம் |
| --- | --- | --- | --- |
| வழக்கமானது | 4 model calls, 3 tool calls | சுமார் ₹22,000-ல plan | இல்லை |
| Budget-ல stays இல்லை | 10-step cap-ஐ தொட்டுச்சு | User-க்கு சுத்தமான message | Tool இப்போ "cheapest is ₹Y"ன்னு சொல்லுது |
| அதே case, மாற்றத்துக்கு அப்புறம் | 5 steps | வேற dates-ஐ suggest பண்ணுச்சு | Loop போயிடுச்சு |

## பொதுவா பண்ற தப்புகள்

- **Workflow போதும்ங்குற இடத்துல agent use பண்றது.**
- **Step limit இல்லாதது.**
- **தெளிவில்லாத tools, errors.** அப்போ agent guess பண்ணும் அல்லது loop ஆகும்.
- **Instructions-ல stop condition இல்லாதது.**
- **ஒவ்வொரு step-ஐயும் log பண்ணாதது.** பார்க்க முடியாததை debug பண்ண முடியாது.

- **Fail ஆன tool-ஐ என்றென்றும் retry பண்றது.** Error-ஐ ஒரு தெளிவான message-ஓட model-க்கு திருப்பி குடுங்க, ரெண்டு அல்லது மூணு ஒரே மாதிரி failures-க்கு அப்புறம் நிறுத்துங்க.
- **Agent-ஓட "done"-ஐ நம்புறது.** முடிஞ்ச இடத்துல code-ல result-ஐ check பண்ணுங்க.
- **உங்ககிட்ட இருக்குற எல்லா tool-ஐயும் agent-க்கு குடுக்கிறது.** அதிக tools-னா அதிக தப்பான தேர்வுகள், நீளமான prompts.
- **ரெண்டு happy-path tasks-ல test பண்றது.** Agents-க்கு பலவிதமான tasks-ஓட ஒரு set வேணும், ஒண்ணுக்கு மேல தடவை run பண்ணணும்; ஏன்னா results ஒவ்வொரு run-லயும் மாறும்.

## Agent build பண்ணக்கூடாத நேரங்கள்

- **Steps தெரிஞ்சிருக்கும்போது**: ஒரு fixed workflow மலிவு, வேகம், test பண்ண ஈஸி.
- **தப்புகள் costly-ஆவும் திரும்ப எடுக்க கஷ்டமாவும் இருக்கும்போது**, payments அல்லது customers-க்கு messages மாதிரி; ஒரு ஆள் ஒவ்வொரு action-ஐயும் approve பண்ணாத வரை.
- **Latency முக்கியம்னா**: ரெண்டு seconds-க்குள்ள வேணும்ங்குற reply-க்கு பல model calls-க்கு இடமே இருக்காது.
- **Retrieval-ஓட ஒரு நல்ல call ஏற்கனவே வேலை செய்யுதுன்னா**: முதல்ல அந்த baseline-ஐ measure பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **Limits-ஐ code-ல set பண்ணுங்க**: ஒரு task-க்கு steps, tokens, நேரம், பணம்; எதுவும் வந்தா சுத்தமான handover.
- **ஒவ்வொரு run-ஐயும் trace பண்ணுங்க**: ஒவ்வொரு step-ஓட tool, arguments, result, tokens, நேரம்.
- **Tasks-ஓட ஒரு test set வச்சுக்கோங்க**, காலப்போக்கில ஒரு task-க்கு success rate, steps, cost-ஐ track பண்ணுங்க.
- **Write actions-ஐ gate பண்ணுங்க**: read-only tools சுதந்திரமா run ஆகட்டும்; data-வை மாத்துற அல்லது ஆட்களை தொடர்பு கொள்ற எதுக்கும் approval அல்லது கடுமையான rules வேணும்.
- **முதல்ல குறுகலா ship பண்ணுங்க**: ஒரு task type, சில tools, ஒரு தெளிவான stop rule; அப்புறம் numbers அனுமதிக்கிற அளவுக்கு விரிவாக்குங்க.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற Anthropic-ஓட "Building effective agents"-ஐ படிங்க.

1. மேல இருக்குற agent loop-ஐ ரெண்டு எளிய tools-ஓடயும் ஒரு step limit-ஓடயும் எழுதுங்க.
2. அஞ்சு வேற வேற tasks-ஐ run பண்ணி, agent எப்படி முடிவு பண்ணுதுன்னு பார்க்க ஒவ்வொரு step-ஐயும் (tool, arguments) print பண்ணுங்க.
3. ஒரு task-ஐ fixed workflow-ஆ திரும்ப எழுதி, நம்பகத்தன்மையையும் cost-ஐயும் compare பண்ணுங்க.
4. பத்து test tasks-ஐ ஒவ்வொண்ணுக்கும் வெற்றின்னா என்னன்னு சேர்த்து எழுதி, run பண்ணக்கூடிய loop-ல மூணு தடவை run பண்ணி, table-ல இருந்து ஒவ்வொரு failure type-ஐயும் எண்ணுங்க.
