## இது என்ன

ஒரு language model-ஓட அடிப்படை வேலை அடுத்த token-ஐ predict பண்றது. ஒரு text-ல அதை அது எவ்வளவு நல்லா பண்ணுதுன்னு இந்த metrics அளக்குது.

**Cross-entropy**-னா, அடுத்து உண்மையிலேயே வந்த ஒவ்வொரு token-லயும் model-க்கு இருந்த சராசரி "ஆச்சரியம்". உண்மையான அடுத்த token-க்கு model 0.9 probability கொடுத்திருந்தா, அதுக்கு கொஞ்சமும் ஆச்சரியம் இல்லை; 0.01 கொடுத்திருந்தா ரொம்ப ஆச்சரியம். ஆச்சரியத்தை probability-ஓட negative logarithm-ஆ அளக்குறாங்க; அதனால உறுதியான predictions கிட்டத்தட்ட செலவே வைக்காது, ஆனா நம்பிக்கையான தப்புகள் நிறைய செலவு வைக்கும். ஒரு language model-ஐ train பண்றதுன்னா, அதோட training text-ல அதோட cross-entropy-ஐ குறைக்கிறது; training run-ல குறைஞ்சுக்கிட்டே போற "loss" இந்த number தான்.

**Perplexity**-னா cross-entropy-யோட exponential. ஒரு abstract number-ஐ புரியுற மாதிரி மாத்தும்: கிட்டத்தட்ட, **ஒவ்வொரு step-லயும் model எத்தனை சம வாய்ப்புள்ள options-ல ஒண்ணை தேர்ந்தெடுக்குதுன்னு**. Perplexity 4-னா, சம வாய்ப்புள்ள நாலு அடுத்த tokens-ல ஒண்ணை எடுக்குற மாதிரி model சராசரியா குழப்பத்துல இருக்குன்னு அர்த்தம். குறைவா இருந்தா நல்லது.

Papers-ல ரெண்டு related units வரும். **Bits** log base 2 use பண்ணும், **nats** natural logarithm use பண்ணும்; PyTorch, TensorFlow nats-ல report பண்ணும். **Bits per character**, **bits per byte** ரெண்டும் total-ஐ tokens எண்ணிக்கையால வகுக்காம text-ஓட நீளத்தால வகுக்கும்; models-ஐ ஒப்பிடும்போது இது ரொம்ப முக்கியம், கீழ பார்க்கலாம்.

இந்த ideas Claude Shannon-ஓட 1951 வேலையில இருந்து வந்தது, அது ஆங்கில text-ஐ predict பண்றதை பத்தினது. Text-ஐ நல்லா predict பண்ற model, அதை நல்லா compress-உம் பண்ணலாம்: 3.4 bits per byte இருக்குற model, தத்துவரீதியா text-ஐ அதோட original அளவுல பாதிக்கும் குறைவான இடத்துல சேமிக்கலாம்.

```flow
title: Token probabilities-ல இருந்து perplexity வரை
Text -> Tokenize
Tokenize -> உண்மையான ஒவ்வொரு அடுத்த token-க்கும் model probability தருது
உண்மையான ஒவ்வொரு அடுத்த token-க்கும் model probability தருது -> ஒவ்வொண்ணுக்கும் minus log எடு | ஒரு token-க்கு ஆச்சரியம்
ஒவ்வொண்ணுக்கும் minus log எடு -> சராசரி எடு | cross-entropy
சராசரி எடு -> Exponentiate பண்ணு | perplexity
சராசரி எடு -> Total-ஐ text-ஓட bytes-ஆல வகு | bits per byte, tokenizers முழுக்க ஒப்பிடக்கூடியது
```

## இது எப்படி work ஆகுது

**எப்படி கணக்கிடுறது.** உண்மையான ஒவ்வொரு அடுத்த token-க்கும் model கொடுத்த probability உங்களுக்கு வேணும். பல APIs இதை **logprobs**-ஆ திருப்பி தரும்; open models-ல நேரடியா கிடைக்கும்.

```python
import math

def perplexity_from_logprobs(logprobs):
    """logprobs: natural-log probabilities of each actual next token."""
    cross_entropy = -sum(logprobs) / len(logprobs)    # nats per token
    return math.exp(cross_entropy), cross_entropy

def bits_per_byte(logprobs, text):
    total_bits = -sum(logprobs) / math.log(2)         # convert nats to bits
    return total_bits / len(text.encode("utf-8"))

# Example: three tokens predicted with probabilities 0.5, 0.25 and 0.8
lp = [math.log(0.5), math.log(0.25), math.log(0.8)]
print(perplexity_from_logprobs(lp))                   # perplexity about 2.15
```

Hugging Face Transformers-ல, input-ஐ labels-ஆ pass பண்ணா cross-entropy loss நேரடியா வரும், `exp(loss)` தான் perplexity. நீளமான texts-க்கு sliding-window version-ஐ primary resource காட்டும்.

**ஒரு value-ஓட அர்த்தம் text-ஐ பொறுத்தது.**

- **Structured text** (HTML, code, forms) predict பண்ண எளிது, அதனால perplexity குறைவு.
- **பெரிய vocabulary** ஒவ்வொரு step-லயும் அதிக options தரும், அதனால perplexity அதிகமா இருக்கும்.
- **அதிக context** predict பண்ண உதவும், அதனால model முன்னாடி இருக்குற text-ஐ அதிகமா பார்க்கும்போது perplexity குறையும்.
- **Model மனப்பாடம் பண்ண text**-க்கு அசாதாரணமா குறைவான perplexity வரும்; **gibberish, அசாதாரண ideas**-க்கு ரொம்ப அதிகமா வரும்.

**ஒப்பீட்டு trap.** Perplexity per token, வேற வேற models வேற வேற tokenizers use பண்ணும். தெலுங்கை நிறைய சின்ன துண்டுகளா பிரிக்குற tokenizer, ஒவ்வொரு துண்டையும் predict பண்றதை எளிதாக்குது; model நல்லா இல்லாட்டியும் per-token perplexity குறைவா வரும். ஒரே text-ல models-ஐ ஒப்பிட **bits per byte** (அல்லது per character) use பண்ணுங்க: மொத்த ஆச்சரியத்தை text-ஓட நீளத்தால வகுக்கிறது, அது எல்லா models-க்கும் ஒண்ணுதான்.

**Post-trained models.** Instruction tuning, preference tuning ரெண்டும் model-ஐ helpful-ஆ இருக்க கத்துக்கொடுக்குது, raw text-ஐ predict பண்ண இல்லை. Chat models-க்கு அவற்றோட base models-ஐ விட பெரும்பாலும் *அதிக* perplexity இருக்கும், ஆனா அவை ரொம்ப பயனுள்ளவை. Quantisation-உம் perplexity-ஐ எதிர்பாராத விதத்துல மாத்தலாம். அதனால perplexity raw text-ல **base models**-ஐ ஒப்பிடவும், training curves-க்கும் தான் நல்லது; chat assistants-ஐ rank பண்ண இல்லை.

**நடைமுறை பயன்கள்.**

- **உங்க domain-க்கு base model தேர்ந்தெடுக்குறது.** உங்க held-out text-ல bits per byte குறைவா இருந்தா, continued training அல்லது fine-tuning-க்கு அது நல்ல தொடக்கம்.
- **Training-ஐ கவனிக்கிறது.** Validation loss (cross-entropy) learning-ஐ காட்டும், training loss-ல இருந்து இருக்குற இடைவெளி overfitting-ஐ காட்டும்.
- **Contamination-ஐ கண்டுபிடிக்கிறது.** Benchmark கேள்விகள்ல அசாதாரணமா குறைவான perplexity இருந்தா, model அவற்றை training-ல பார்த்திருக்குன்னு தெரியும்.
- **Data-ஐ சுத்தம் பண்றது.** ரொம்ப அதிக perplexity உடைஞ்ச extractions, தப்பான மொழிகள், spam-ஐ காட்டும்; ரொம்ப குறைவான perplexity, model ஏற்கனவே தெரிஞ்சதுக்கு கிட்டத்தட்ட duplicates-ஐ காட்டும்.

| Use | எதை ஒப்பிடணும் | கவனிக்க வேண்டியது |
| --- | --- | --- |
| உங்க text-க்கு base model தேர்ந்தெடுக்க | Held-out text-ல bits per byte | வேற tokenizers, per-token numbers-ஐ நியாயமில்லாம ஆக்கும் |
| Training-ஐ monitor பண்ண | Training, validation loss | Units: பெரும்பாலான frameworks-ல nats |
| Contamination-ஐ கண்டுபிடிக்க | Test items-ல perplexity, அதே மாதிரி பார்க்காத text-ஓட | சில text இயல்பாவே predict பண்ண எளிது |
| Training data-ஐ filter பண்ண | ரொம்ப அதிக அல்லது ரொம்ப குறைவான perplexity outliers | அசாதாரணமான ஆனா சரியான text-க்கும் அதிகமா வரும் |
| Chat assistants-ஐ rank பண்ண | Perplexity use பண்ணாதீங்க | Post-training perplexity-ஐ அதிகரிக்கும் |

## ஒரு worked example

Hyderabad-ல இருக்குற ஒரு legal-tech team, தெலுங்கு court judgements-ல ஒரு open model-ஐ தொடர்ந்து train பண்ணணும்னு நினைக்குது. மூணு candidate base models, 2,000 held-out judgement paragraphs இருக்கு.

| Model | Report பண்ண perplexity (per token) | முழு set-க்கும் tokens | Bits per byte |
| --- | --- | --- | --- |
| A | 9 | 2.4 million | 1.77 |
| B | 14 | 1.1 million | 0.97 |
| C | 21 | 1.3 million | 1.33 |

அந்த set கிட்டத்தட்ட 43 லட்சம் bytes text. Numbers விளக்கத்துக்காக மட்டும். Per-token perplexity-ல A தான் best-ஆ தெரியும். ஆனா A-வோட tokenizer தெலுங்கை B-யை விட ரெண்டு மடங்குக்கு மேல tokens-ஆ பிரிக்குது, அதனால ஒவ்வொரு token-உம் யூகிக்க எளிது. அதே bytes எண்ணிக்கையால மொத்த ஆச்சரியத்தை வகுச்சு பார்த்தா, தெலுங்கு legal text-ஐ B தான் best-ஆ model பண்ணுது, அதோட efficient tokenizer training-ஐயும் பயன்படுத்துறதையும் மலிவாக்கும்.

Paragraphs-ஐ perplexity வச்சு sort-உம் பண்றாங்க. அதிகமா இருந்த 30, garbled scans, சில ஆங்கில pages-ஆ இருக்கு; training-க்கு முன்னாடி extraction-ஐ சரி பண்றாங்க. கடைசியா, முடிவு எடுக்குறதுக்கு முன்னாடி B-யை உண்மையான tasks-ல (judgements-ஐ summarise பண்றது, அவற்றை பத்தின கேள்விகளுக்கு பதில் சொல்றது) test பண்றாங்க, ஏன்னா text-ஐ நல்லா model பண்றது ஒரு signal தான், task quality-க்கான உத்தரவாதம் இல்லை.

## பொதுவா பண்ற தப்புகள்

- **வேற வேற tokenizers முழுக்க per-token perplexity-ஐ ஒப்பிடுறது.** Bits per byte அல்லது per character use பண்ணுங்க.
- **Bits, nats-ஐ குழப்பிக்கிறது.** 2.0 nats loss கிட்டத்தட்ட 2.9 bits; perplexity ரெண்டுலயும் ஒண்ணுதான்.
- **Chat models-ஐ perplexity வச்சு rank பண்றது.** Post-training அதை usefulness-க்கு சம்பந்தமில்லாத வழிகள்ல மாத்தும்.
- **குறைவான perplexity-ஐ quality-ன்னு படிக்கிறது.** அது மனப்பாடம் பண்ணதையோ, ரொம்ப predictable-ஆன text-ஐயோ குறிக்கலாம்.
- **ஒவ்வொரு model-க்கும் வேற test set use பண்றது.** சரியா ஒரே text-ல ஒப்பிடுங்க.
- **Context length-ஐ கவனிக்காம விடுறது.** நீளமான context-ஓட score பண்ண models-க்கு perplexity குறைவா வரும்.

## இந்த metrics தேவையில்லாத நேரங்கள்

- **ஒரு application-க்கு API வழியா hosted chat model use பண்றது**: perplexity வச்சு இல்லை, task tests வச்சு மதிப்பிடுங்க.
- **Instruction-tuned assistants-ஐ ஒப்பிடுறது**: உங்க tasks-ல evals, side-by-side ஒப்பீடுகளை use பண்ணுங்க.
- **Classification-க்கு சின்ன fine-tunes**: accuracy, precision, recall அதிகமா சொல்லும்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு training run-லயும் validation loss-ஐ** ஒரே unit-ல track பண்ணுங்க.
- **ஒரு held-out domain set வச்சிருங்க**, நீங்க பரிசீலிக்கிற ஒவ்வொரு base model-க்கும் bits per byte-ஐ பதிவு பண்ணுங்க.
- **Data pipelines-ல perplexity filters use பண்ணுங்க**, உடைஞ்ச அல்லது வேற மொழி text-ஐ பிடிக்க; அவை flag பண்றதுல ஒரு sample-ஐ review பண்ணுங்க.
- **ஒரு model-ஓட scores ரொம்ப நல்லா தெரிஞ்சா**, புது benchmark results-ல contamination இருக்கான்னு check பண்ணுங்க.

## Practice பண்ணுங்க

1. மேல இருக்குற function-ஐ நீங்களே உருவாக்கின probabilities-ஓட use பண்ணுங்க: model எப்பவும் 50% உறுதியா இருந்தா perplexity என்ன வரும்? எப்பவும் 90% உறுதியா இருந்தா?
2. ஏதாவது ஒரு சின்ன open model-ஐ வச்சு, ஒரு சாதாரண text paragraph-ல perplexity-ஐ கணக்கிடுங்க; அப்புறம் அதே paragraph-ல வார்த்தைகளை கலைச்சு போட்டு கணக்கிடுங்க. என்ன மாறுது?
3. Tokenizers வேறுபடுற ரெண்டு models-ஐ per-token perplexity வச்சு ஒப்பிட முடியாதுன்னு, ஒரு friend-க்கு ரெண்டு வாக்கியத்துல explain பண்ணுங்க.
