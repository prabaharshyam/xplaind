## இது என்ன

**Vector search**, ஒரு கேள்வியோட embedding-க்கு ரொம்ப நெருக்கமான embeddings இருக்குற chunks-ஐ கண்டுபிடிக்கும். பெரும்பாலான RAG systems-ல இருக்குற retrieval step இதுதான்:

1. ஒவ்வொரு chunk-ஐயும் ஒரு தடவை embed பண்ணி, vectors-ஐ ஒரு **index**-ல store பண்ணுங்க.
2. கேள்வி வரும்போது, அதே model-ஆல கேள்வியை embed பண்ணுங்க.
3. ரொம்ப ஒத்த chunks-ல **top-k**-ஐ திருப்பி தாங்க (உதாரணம், ரொம்ப நெருக்கமான ஐந்து).

Store உங்க program-ல FAISS மாதிரி ஒரு library-யா இருக்கலாம், PostgreSQL-ல pgvector மாதிரி ஒரு database extension-ஆ இருக்கலாம், அல்லது Qdrant, Weaviate, Pinecone மாதிரி தனி vector database-ஆ இருக்கலாம்.

```flow
title: Index, ஒரு தடவை
Chunks 1 முதல் N வரை -[embed]-> Vectors + metadata | product, type, page
```

```flow
title: Query, ஒவ்வொரு கேள்விக்கும்
"Washing machine E-4012, water வெளியே போகல" -[அதே model-ஆல embed]-> Query vector
Query vector -> Nearest neighbours | product model வச்சு filter
Nearest neighbours -[top 30]-> Rerank -[top 5]-> Prompt
```

இந்த lesson-ல Hyderabad-ல ஒரு electronics retailer-ஓட support assistant-ஐ follow பண்ணப் போறோம்; அது product manuals, help articles மேல build ஆனது.

## இது எப்படி work ஆகுது

**Similarity.** பெரும்பாலான systems normalise பண்ண vectors-ல cosine similarity அல்லது dot product use பண்ணும்: அதிகம்னா அர்த்தத்துல அதிக ஒற்றுமை.

**Exact vs approximate search.** கேள்வியை ஒவ்வொரு vector-ஓடயும் compare பண்றது exact, ஆனா லட்சக்கணக்கான chunks-க்கு slow. Approximate nearest neighbour indexes (HNSW graphs மாதிரி) கிட்டத்தட்ட அதே results-ஐ ரொம்ப வேகமா கண்டுபிடிக்கும். சில ஆயிரம் chunks-க்கு exact search போதும்.

**Top-k.** எத்தனை results திருப்பி தரணும்னு நீங்க தேர்ந்தெடுக்கலாம். ரொம்ப குறைவா இருந்தா சரியான chunk miss ஆகலாம்; ரொம்ப அதிகமா இருந்தா prompt-ல தேவையில்லாததே நிறையும். ஐந்துல இருந்து பத்து வரை பொதுவான ஆரம்பம்; உங்க கேள்விகள்ல measure பண்ணுங்க.

**Metadata, filters.** ஒவ்வொரு vector-ஓடயும் document id, title, section, page, date, access groups-ஐ store பண்ணுங்க. Search-க்குள்ளயே filter பண்ணுங்க (இந்த product மட்டும், current versions மட்டும், இந்த user பார்க்க அனுமதி இருக்கிறது மட்டும்).

**Vector search எங்க சிரமப்படும்.** Exact identifiers, அபூர்வமான வார்த்தைகள்: "E-4012" மாதிரி error codes, policy numbers, product SKUs, அசாதாரணமான பேர்கள். Embeddings அர்த்தத்தை பிடிக்கும், exact strings-ஐ இல்லை. **Hybrid search**, vector search-ஐ keyword search-ஓட (BM25) சேர்த்து இவற்றை பிடிக்கும்.

**Reranking.** **Reranker**-னா slow-ஆன, ஆனா அதிக accurate ஆன model; அது கேள்வியையும் ஒவ்வொரு candidate chunk-ஐயும் சேர்த்து படிச்சு, relevance வாரியா மறுபடி வரிசைப்படுத்தும். Vector அல்லது hybrid search-ல 20-ல இருந்து 50 candidates retrieve பண்ணி, rerank பண்ணி, prompt-க்கு சிறந்த ஐந்தை வச்சுக்கோங்க.

**Index-ஐ sync-ல வச்சுக்கிறது.** Documents மாறுனா, அவற்றோட பழைய vectors-ஐ delete பண்ணி புதுசை சேருங்க; embedding model-ஐ மாத்துனா, எல்லாத்தையும் rebuild பண்ணுங்க.

**ஒரு store-ஐ தேர்ந்தெடுக்கிறது:**

| Store | எதுக்கு best | Trade-offs |
| --- | --- | --- |
| உங்க program-ல FAISS | Experiments, offline jobs | Database features இல்லை; persistence-ஐ நீங்களே பார்த்துக்கணும் |
| PostgreSQL-ல pgvector | ஏற்கனவே Postgres-ல இருக்குற apps, லட்சக்கணக்கான chunks வரை | Data, metadata, vectors-க்கு ஒரே system |
| தனி vector database | ரொம்ப பெரிய indexes, அதிக traffic | Run பண்ணி secure பண்ண இன்னொரு system |

**Approximate index எப்படி work ஆகுது.** HNSW ஒரு graph build பண்ணும்; அதுல ஒவ்வொரு vector-உம் தன்னோட சில நெருங்கிய neighbours-ஓட link ஆகும், coarse-ல இருந்து fine வரை layers-ஆ. Search மேல layer-ல ஆரம்பிச்சு, query-க்கு நெருக்கமான vectors-ஐ நோக்கி தாவி, கீழ layers-ல refine பண்ணும். Vectors-ல ஒரு சின்ன பகுதியை மட்டுமே பார்க்கும், ஆனா பெரும்பாலும் நிஜமான nearest ones-ல கிட்டத்தட்ட எல்லாத்தையும் கண்டுபிடிக்கும். Settings வேகத்தையும், எத்தனை நிஜ neighbours கிடைக்குதுன்னு இருக்குறதையும் மாத்தி மாத்தி trade பண்ணும்; அதனால அவற்றை மாத்தும்போது recall-ஐ measure பண்ணுங்க.

**Top-k-ஐ evidence வச்சு தேர்ந்தெடுக்கிறது.** கேள்விகளும், கிடைக்க வேண்டிய chunk-உம் இருக்குற ஒரு test set build பண்ணுங்க. Recall-ஐ 1, 5, 10, 30-ல measure பண்ணுங்க. 30-ல recall, 5-ஐ விட ரொம்ப அதிகமா இருந்தா, அதிகம் retrieve பண்ணி ஒரு reranker சேருங்க. 30-லயும் குறைவா இருந்தா, problem இன்னும் முன்னாடி இருக்கு: parsing, chunking அல்லது embedding model.

**Index-ஐ sync-ல வச்சுக்கிறது, practice-ல.** ஒவ்வொரு chunk-க்கும் document id-ஓட position-ஐ வச்சு ஒரு id குடுங்க, உதாரணம் `manual-KX5-p12-c3`. ஒரு document மாறுனா, அந்த document id இருக்குற எல்லா chunks-ஐயும் delete பண்ணி, புதுசை ஒரே transaction-ல insert பண்ணுங்க; அப்போ searches பாதி update-ஐ பார்க்கவே பார்க்காது. ஒவ்வொரு vector-ஓடயும் embedding model பேரை record பண்ணுங்க. ஒவ்வொரு model-க்கும் vectors-ஐ எண்ணுற ஒரு இரவு check, இந்த lesson-ஓட exercise-ல வந்த தப்பை பிடிச்சுடும்; அங்க பழைய, புது embeddings ஒரே index-ல கலந்துடுச்சு.

**Practice-ல pgvector.** உங்க app ஏற்கனவே Postgres use பண்ணா, vectors data பக்கத்துலயே இருக்கலாம்:

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id text PRIMARY KEY,                 -- e.g. manual-KX5-p12-c3
  doc_id text NOT NULL,
  section text, page int, version text,
  access_group text NOT NULL,
  embed_model text NOT NULL,
  body text NOT NULL,
  embedding vector(384) NOT NULL
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks (doc_id);

-- Top 20 for one user's groups, current version only:
SELECT id, section, page, body, 1 - (embedding <=> $1) AS similarity
FROM chunks
WHERE access_group = ANY($2) AND version = 'current'
ORDER BY embedding <=> $1
LIMIT 20;
```

`<=>` cosine distance, அதனால சின்னதுன்னா நெருக்கம். `SET hnsw.ef_search = 100;` graph-ல அதிகமா search பண்ணும், speed கொஞ்சம் குறைஞ்சாலும் recall நல்லா இருக்கும். Strict filters இருக்கும்போது, ஒரு approximate index limit-ஐ விட குறைவான rows-ஐ திருப்பலாம்; சமீபத்திய pgvector versions போதுமான rows pass ஆகுற வரை scan பண்ணிட்டே இருக்க முடியும் (iterative index scans), அல்லது group வாரியா partition பண்ணலாம்.

**Index உங்களுக்கு என்ன cost ஆகுதுன்னு measure பண்ணுங்க.** Approximate results-ஐ உங்க சொந்த queries-ல exact ones-ஓட compare பண்ணுங்க:

```python
import numpy as np, faiss

def ann_recall(vectors, queries, k=10, m=32, ef=64):
    d = vectors.shape[1]
    exact = faiss.IndexFlatIP(d); exact.add(vectors)
    approx = faiss.IndexHNSWFlat(d, m, faiss.METRIC_INNER_PRODUCT)
    approx.hnsw.efSearch = ef
    approx.add(vectors)
    _, truth = exact.search(queries, k)
    _, found = approx.search(queries, k)
    return np.mean([len(set(t) & set(f)) / k for t, f in zip(truth, found)])
```

Inner product cosine-க்கு சமமா இருக்க vectors normalise ஆகியிருக்கணும். Recall கிட்டத்தட்ட 0.95-க்கு கீழ இருந்தா, `ef` அல்லது `m`-ஐ கூட்டி, speed-ஐ மறுபடி measure பண்ணுங்க.

**Code-ல reranking.**

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

def rerank(question, candidates, keep=5):
    scores = reranker.predict([(question, c["body"]) for c in candidates])
    order = sorted(range(len(candidates)), key=lambda i: scores[i], reverse=True)
    return [candidates[i] for i in order[:keep]]
```

20-ல இருந்து 50 candidates-ஐ rerank பண்ணா பத்துல இருந்து நூறு milliseconds சேரும்; உங்க hardware-ல measure பண்ணுங்க. Indian-language text-க்கு, ஒரு multilingual reranker-ஐ தேர்ந்தெடுத்து உங்க queries-ல test பண்ணுங்க.

**பாதி நிலை இல்லாத updates.** மாறுன document-ஓட chunks-ஐ `doc_id` வச்சு ஒரே transaction-ல delete பண்ணி insert பண்ணுங்க, அப்போ searches பாதி update-ஐ பார்க்காது. தினமும் இரவு `embed_model` வாரியா rows-ஐ எண்ணுங்க; ஒண்ணுக்கு மேற்பட்ட value இருந்தா index கலந்திருக்கு.

**Browser-லயே try பண்ணுங்க.** சில வரி NumPy-ல exact nearest-neighbour search. Query vector-ஐ மாத்தி பாருங்க.

```python
import numpy as np

rng = np.random.default_rng(0)
docs = rng.normal(size=(1000, 64))
docs /= np.linalg.norm(docs, axis=1, keepdims=True)          # normalise, so dot product = cosine
query = docs[42] + 0.1 * rng.normal(size=64)
query /= np.linalg.norm(query)

scores = docs @ query
top = np.argsort(-scores)[:5]
print("top 5:", top.tolist())
print("scores:", scores[top].round(3).tolist())
```

Hyderabad-ல ஒரு electronics retailer, 3,000 product manuals, help articles மேல ஒரு support assistant build பண்றாங்க.

- Chunks ஒரு open embedding model-ஆல embed ஆகி, product model, document type metadata-ஓட PostgreSQL-ல pgvector-ல store ஆகுது.

- Keyword search சேர்த்து, ரெண்டு result lists-ஐயும் merge பண்றாங்க; error-code page இப்போ முதல்ல வருது.

## பொதுவா பண்ற தப்புகள்

- **Queries-ஐயும் chunks-ஐயும் வேற வேற models-ஆல embed பண்றது.**
- **Codes, IDs-க்கு vectors-ஐ நம்புறது.** Keyword search சேருங்க.
- **Test பண்ணாம top-k-ஐ தேர்ந்தெடுக்கிறது.**
- **Retrieval-க்கு அப்புறம் filter பண்றது.** Search-க்குள்ளயே filter பண்ணுங்க.
- **Index-ஐ update அல்லது rebuild பண்ண மறந்துடுறது.**
- **Search-க்கு அப்புறம் application code-ல filter பண்றது.** Permission filters query-க்குள்ள இருக்கணும்.
- **Approximate index-ஓட recall-ஐ ஒருபோதும் measure பண்ணாம இருக்கிறது.** Defaults நீங்க நினைக்கிறதை விட அதிகமா miss பண்ணலாம்.
- **Inner product-ஓட normalise பண்ணாத vectors**, அது cosine similarity ஆகாது.

## Vector index தேவையில்லாத நேரங்கள்

- **Exact-match lookups**: IDs, codes, names keyword search அல்லது ஒரு database index-க்கு சேரும்.
- **Filters-ஏ பெரும்பாலான வேலையை பண்ணுது**, உதாரணம் "இந்த customer-ஓட மூணு contracts": அவற்றை நேரா fetch பண்ணுங்க.
