## இது என்ன

Model-க்கு tools கொடுக்கும்போது, அது பார்க்குறது அவற்றோட பேர், description, parameter schema மட்டும் தான். இதை வச்சே எந்த tool பொருந்தும், என்ன arguments கொடுக்கணும், result-ஐ எப்படி படிக்கணும்னு அது முடிவு பண்ணணும். ஒரு human developer-க்காக design பண்ண tool, உதாரணமா internal API-ஓட ஒவ்வொரு endpoint-க்கும் போட்ட சின்ன wrapper, model-ஐ பெரும்பாலும் குழப்பிடும்.

நல்ல agent tools-க்கு அஞ்சு குணங்கள் இருக்கும்: எண்ணிக்கை **கம்மி**, ஒவ்வொண்ணுக்கும் ஒரு **தெளிவான வேலை**, பேரும் description-உம் **எப்போ** use பண்ணணும்னு சொல்லும், parameters **tight-ஆ typed**, results-உம் errors-உம் **சின்னதாவும் actionable-ஆவும்** இருக்கும்.

| | API வடிவம்: 14 tools | Task வடிவம்: 3 tools |
|---|---|---|
| Tools | get_booking, get_booking_v2, list_segments, get_pnr_status, get_fare_rules, get_passengers, create_refund_request, ... | get_trip(booking_ref) படிக்க; get_cancellation_quote(ref) படிக்க; cancel_trip(quote_id) செயல்படுத்த, approval-ஓட |
| தப்பான tool எடுத்தது | 22% | 3% |
| ஒரு task-க்கு calls | 4.1 | 2.3 |


இந்த lesson-ல Gurugram-ல இருக்குற ஒரு travel company-ஓட support agent-ஐ follow பண்றோம். அதோட tools booking API-ஓட ஒவ்வொரு endpoint-ஐயும் அப்படியே பிரதிபலிச்சது.

## இது எப்படி work ஆகுது

**Tools-ஐ API படி இல்லாம task படி choose பண்ணுங்க.** Agents எப்பவும் ஒரு customer-ஐ தேடி, அப்புறம் அவங்க open orders-ஐ தேடுதுன்னா, model chain பண்ணணும்ங்கிற ரெண்டு calls-ஐ விட `get_customer_with_open_orders` ங்குற ஒரே tool நல்லது. Tools கம்மியா, high-level-ஆ இருந்தா தப்பு நடக்க வாய்ப்பு கம்மி.

**Model-க்காக பேர் வச்சு, describe பண்ணுங்க.** `search_policies` tool-க்கு இந்த description: "Search current HR policies by keywords. Use for questions about leave, travel, reimbursements or conduct. Returns up to 5 passages with policy name and section." இது எப்போ call பண்ணணும், என்ன திரும்பி வரும்னு model-க்கு சொல்லிடும். Tool என்ன பண்ணாதுன்னும் சொல்லுங்க.

**Parameters-ஐ constrain பண்ணுங்க.** Fixed choices-க்கு enums (`status: "open" | "closed"`), ids-க்கு formats (`pattern: ^ORD-\d{8}$`), நல்ல defaults, limits use பண்ணுங்க. ஒவ்வொரு loose string-உம் model தானா ஒரு value-ஐ உருவாக்க ஒரு வாய்ப்பு.

**Model-க்கு தேவையானதை மட்டும் திருப்புங்க.** 200 fields இருக்குற raw JSON-ஐ கொட்டாதீங்க. முக்கியமான சில fields-ஐ மட்டும், படிக்க easy-ஆன வடிவத்துல, model அடுத்த tool-க்கு கொடுக்க ids-ஓட திருப்புங்க. பெரிய results-ஐ paginate அல்லது truncate பண்ணி, அதை சொல்லிடுங்க ("312-ல 10 மட்டும் காட்டுறோம்; search-ஐ narrow பண்ணுங்க").

**Errors-ஐ instructions மாதிரி எழுதுங்க.** "Error 400" எதுவும் சொல்லாது. "No order found with id ORD-2026117. Order ids have 8 digits after ORD-; ask the user to check the id." இப்படி இருந்தா model சரி பண்ணிக்கும்.

**படிக்கிறதையும் செயல்படுத்துறதையும் பிரிங்க.** எதையாவது மாத்துற tools (refund, send, delete) படிக்கிற tools-ல இருந்து தனியா இருக்கணும். அப்போ அவற்றுக்கு approval கட்டாயமாக்கலாம், தனியா log பண்ணலாம்.

**Tool use-ஐ test பண்ணுங்க.** 20 realistic tasks எழுதி, model எந்த tools-ஐ, என்ன arguments-ஓட call பண்ணுதுன்னு பாருங்க. தப்பான tool choice வந்தா, பெரும்பாலும் tools overlap ஆகுது அல்லது descriptions தெளிவா இல்லை.

**Tool description checklist:**

| பகுதி | பலவீனம் | பலம் |
| --- | --- | --- |
| பேர் | `get_data` | `get_trip` |
| எப்போ use பண்ணணும் | இல்லை | "ஒரு trip பத்தின எந்த கேள்விக்கும் முதல்ல இதை use பண்ணுங்க" |
| என்ன திருப்பும் | இல்லை | "Flights, passengers, status, online-ல cancel பண்ண முடியுமா" |
| என்ன பண்ணாது | இல்லை | "Cancel பண்ணாது; quote எடுத்த பிறகு cancel_trip use பண்ணுங்க" |
| Parameter | `id: string` | 6-character pattern இருக்குற `booking_ref` |
| Error | "Error 400" | "ABC12-க்கு trip இல்லை; references 6 letters அல்லது digits" |

**ஒரு tool இன்னொண்ணை சார்ந்து இருக்க வைக்கிறது.** `cancel_trip`-ல quote id-ஐ கட்டாயமாக்குறது ஒரு சின்ன design trick, ஆனா பெரிய விளைவு. Model முதல்ல quote எடுக்காம cancel பண்ண முடியாது. அதனால எதுவும் நடக்குறதுக்கு முன்னாடியே customer-க்கு refund தொகையும் fees-உம் தெரிஞ்சிடும், approval screen-ல quote-ஐ காட்டவும் முடியும். ஒரு action-க்கு முன்னாடி ஒரு check வரணும்ங்கிற எல்லா இடத்துலயும் இதே idea-வை use பண்ணலாம்: verified invoice id தேவைப்படுற payment, user பார்த்த draft id தேவைப்படுற email.

**Tool set-ஐ test பண்றது.** பேர், description, schema-ல எதை மாத்துனாலும் அதே 20 tasks-ஐ மறுபடி ஓட்டுங்க, மூணு numbers எண்ணுங்க: தப்பான tool choose ஆனது, invalid arguments, ஒரு task-க்கு calls. சின்ன wording மாற்றங்கள் இந்த numbers-ஐ நீங்க நினைக்கிறதை விட அதிகமா நகர்த்தும்.

**Code-ல நல்ல வடிவ tool.** Arguments-ஐ Pydantic-ல define பண்ணி, அதுல இருந்து schema-ஐ generate பண்ணி, result-ஐ model-க்கு ஏத்த மாதிரி வடிவமைங்க:

```python
from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class SearchTrips(BaseModel):
    """Find a customer's trips. Use when they ask about a booking but give no reference.
    Returns at most 5 trips, newest first. Does not change or cancel anything."""
    status: Literal["upcoming", "past", "cancelled"] = "upcoming"
    city: str | None = Field(default=None, description="Destination city, e.g. Kochi")

TOOL = {"name": "search_trips", "description": SearchTrips.__doc__.strip(),
        "input_schema": SearchTrips.model_json_schema()}

def search_trips(customer_id, raw_args, db):
    try:
        args = SearchTrips.model_validate(raw_args)
    except ValidationError as err:
        field = err.errors()[0]["loc"][0]
        return f"Invalid {field}. Status must be upcoming, past or cancelled."
    trips = db.find_trips(customer_id, args.status, args.city)       # customer_id from the session
    if not trips:
        where = f" to {args.city}" if args.city else ""
        return f"No {args.status} trips{where}. Ask the customer for the booking reference."
    lines = [f"{t.ref}: {t.city}, {t.date:%d %b %Y}, {t.status}" for t in trips[:5]]
    more = f" (showing 5 of {len(trips)}; ask for a city or date to narrow)" if len(trips) > 5 else ""
    return "\n".join(lines) + more
```

Description எப்போ tool-ஐ use பண்ணணும், என்ன திருப்பும், என்ன பண்ணாதுன்னு சொல்லுது. Result அடுத்த tool-க்கு தேவையான ids-ஓட சில படிக்கக்கூடிய வரிகள், raw database rows இல்லை. ஒவ்வொரு failure path-உம் அடுத்து என்ன பண்ணணும்னு சொல்லுது.

**Place சம்பாதிக்கிற tools-ஐ கண்டுபிடிங்க.** Tools அதிகமானா abilities அதிகம், ஆனா தப்பா choose பண்ற வாய்ப்பும் அதிகம், ஒவ்வொரு description-உம் ஒவ்வொரு call-லயும் அனுப்பப்படுது. ரெண்டு simple experiments:

- **ஒரு நேரத்துல ஒண்ணை remove பண்ணுங்க.** ஒவ்வொரு tool-ம் இல்லாம உங்க task set-ஐ ஓட்டுங்க. Success குறையலைன்னா அந்த tool போகலாம்.
- **Calls-ஐ plot பண்ணுங்க.** ஒரு வாரத்து traces-ல ஒவ்வொரு tool-ம் எத்தனை முறை call ஆச்சு, எந்த tool-க்கு அப்புறம் எது வருதுன்னு எண்ணுங்க. ஒரு தடவை கூட call ஆகாத tool-ஓட description மோசமா இருக்கலாம்; எப்பவும் ஒண்ணுக்கு பின்னாடி ஒண்ணா call ஆகுற ரெண்டு tools-ஐ merge பண்ணலாம்.

```python
from collections import Counter

def tool_usage(runs):
    """runs: list of lists of tool names, in order, one list per run."""
    calls, pairs = Counter(), Counter()
    for names in runs:
        calls.update(names)
        pairs.update(zip(names, names[1:]))
    return calls.most_common(), pairs.most_common(5)
```

**Tools-ஐ APIs மாதிரி version பண்ணுங்க.** ஒரு parameter-ஓட பேரை மாத்துறது அல்லது tool என்ன திருப்புதுன்னு மாத்துறது agent-ஓட behaviour-ஐ சத்தமில்லாம உடைக்கலாம். Tool definitions-ஐ prompt பக்கத்துலயே code-ல வச்சு, மாற்றங்களை சேர்த்து review பண்ணி, ஒவ்வொரு மாற்றத்துக்கும் tool-choice tests-ஐ மறுபடி ஓட்டுங்க.

**ஒரு server, நிறைய agents.** பல apps-க்கு ஒரே tools தேவைன்னா, அவற்றை Model Context Protocol (MCP) வழியா ஒரு தடவை expose பண்ணுங்க; அப்போ ஒவ்வொரு app-உம் அதை மறுபடி எழுத வேண்டாம். Design rules அதேதான்: narrow tools, தெளிவான descriptions, உதவுற errors, tool உள்ளயே permission checks.

## ஒரு worked example

Gurugram travel company-ஓட support agent-க்கு முதல்ல booking API-ஐ அப்படியே பிரதிபலிக்கிற 14 tools இருந்துச்சு: `get_booking`, `get_booking_v2`, `list_segments`, `get_pnr_status`, `get_fare_rules`, `create_refund_request`, இன்னும் சில. Tests-ல 22% tasks-ல model தப்பான tool-ஐ எடுத்துச்சு, அடிக்கடி `get_booking`, `get_booking_v2` ரெண்டையும் call பண்ணி cost-ஐ ரெட்டிப்பாக்கிச்சு.

நீங்க support team-ஓட உண்மையான tasks படி redesign பண்றீங்க:

```python
{
  "name": "get_trip",
  "description": "Get a customer's trip by booking reference: flights, passengers, status, "
                 "and whether it can be cancelled online. Use first for any question about one trip.",
  "input_schema": {
    "type": "object",
    "properties": {"booking_ref": {"type": "string", "pattern": "^[A-Z0-9]{6}$"}},
    "required": ["booking_ref"]
  }

```

மத்த tools `get_cancellation_quote` (read-only: refund தொகையும் fees-உம்), `cancel_trip` (செயல்படுத்துறது: quote id தேவை, அதனால cancel பண்றதுக்கு முன்னாடி model quote எடுத்தே ஆகணும்) ஆகுது. Results சின்ன summaries, raw API objects இல்லை. தெரியாத reference வந்தா: "No trip found for ABC12. References are 6 letters or digits; ask the customer to read it from their e-ticket."

தப்பான tool choices 3%-க்கு குறையுது, ஒரு task-க்கு சராசரி tool calls 4.1-ல இருந்து 2.3-க்கு குறையுது, `cancel_trip`-ஐ இப்போ human approval step-க்கு பின்னாடி வைக்க முடியுது.

## பொதுவா பண்ற தப்புகள்

- **ஒரு API endpoint-க்கு ஒரு tool.** நிறைய சின்ன tools-ஐ chain பண்றது models-க்கு கஷ்டம். Tasks-க்காக build பண்ணுங்க.
- **Overlap ஆகுற tools.** ஒரு கேள்விக்கு ரெண்டு tools-ஆலயும் பதில் சொல்ல முடிஞ்சா, choice சுண்டு போடுற மாதிரி ஆகிடும்.
- **Raw, பெரிய results.** அவை tokens-ஐ வீணாக்கும், முக்கியமான field-ஐ மறைக்கும். Task-க்கு தேவையானதை மட்டும் திருப்புங்க.
- **சத்தமில்லாத failures.** Error-க்கு empty list திருப்பினா model யூகிக்க வேண்டியதாகும். என்ன தப்பு, என்ன பண்ணணும்னு சொல்லுங்க.
- **Read, write-ஐ கலக்குறது.** ஒரே tool ரெண்டையும் பண்ணா, risky actions-க்கு மட்டும் approval வைக்க முடியாது.
- **Raw API responses-ஐ tool results-ஆ கொடுக்குறது.** நூற்றுக்கணக்கான fields tokens-ஐ வீணாக்கும், model-ஐ குழப்பும்.
- **Tool tests-ஐ மறுபடி ஓட்டாம tool-ஐ மாத்துறது.** சின்ன wording மாற்றங்கள் model எந்த tool-ஐ எடுக்குதுங்கிறதையே மாத்திடும்.

## Tool design அவ்வளவு முக்கியம் இல்லாத நேரங்கள்

- **ஒண்ணு அல்லது ரெண்டு tools**, தெளிவா வேற வேற வேலைகளோட: சாதாரண description-உம் schema-உமே பெரும்பாலும் போதும்.
- **Fixed workflows**, model இல்லாம உங்க code தான் எந்த function ஓடணும்னு முடிவு பண்றது.
- **Prototypes**, ஒரு idea வேலை செய்யுமான்னு மட்டும் பார்க்குற நேரத்துல: task நிரூபிச்ச பிறகு tools-ஐ மெருகேத்துங்க.

## Demo-ல இருந்து production-க்கு

- **Tool-choice test set** (task, எதிர்பார்க்குற tool, எதிர்பார்க்குற arguments) வச்சிருங்க, ஒவ்வொரு மாற்றத்துக்கும் ஓட்டுங்க.
- Traces-ல இருந்து **ஒவ்வொரு tool-ஓட error rate-ஐயும், ஒரு task-க்கு calls-ஐயும் track பண்ணுங்க.**
- ஒவ்வொரு tool-க்குள்ளயும் **timeouts-ஐயும் result-size limits-ஐயும் set பண்ணுங்க.**
- Session-ஓட user id-ஐ use பண்ணி, **tool உள்ளயே permissions-ஐ check பண்ணுங்க.**
- **Tool list-ஐ காலாண்டுக்கு ஒரு தடவை review பண்ணுங்க**: use ஆகாத tools-ஐ remove பண்ணுங்க, chain ஆகுறவற்றை merge பண்ணுங்க.

Anthropic-ஓட agents-க்கு tools எழுதுறது பத்தின article-ஐயும், docs-ல இருக்குற tool-use overview-வையும் படிங்க.
