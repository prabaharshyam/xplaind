## இது என்ன

ஒரு agent loop ஒரு நேரத்துல ஒரு step-ஐ முடிவு பண்ணும். அந்த முடிவுகள் எப்படி எடுக்கப்படுதுன்னு மூணு patterns வடிவமைக்கும்:

- **ReAct** (reason, act): கொஞ்சம் யோசி, ஒரு tool-ஐ call பண்ணு, result-ஐ படி, மறுபடி யோசி. Flexible-உம் simple-உம்; பெரும்பாலான frameworks-ல default.
- **Plan-then-execute**: முதல்ல steps-ஓட முழு plan-ஐ எழுது, அப்புறம் அவற்றை செய், எதிர்பாராதது நடந்தா மட்டும் plan-ஐ மாத்து.
- **Reflection**: ஒரு result-ஐ உருவாக்கின பிறகு (அல்லது இடையிடையே), agent அதை goal அல்லது ஒரு checklist-க்கு எதிரா critique பண்ணி, குறைவா இருக்குறதை சரி பண்ணும்.

இவை சேரும்: ஒரு plan, ReAct-style steps-ல execute ஆகி, final answer-க்கு முன்னாடி ஒரு reflection pass.


```flow

Each step: ஒரு சின்ன ReAct loop -> Draft -> Checks | code: totals கூடுதா; model: ஒவ்வொரு claim-க்கும் source இருக்கா
Checks -[fail ஆனா]-> One revision -> Final
Checks -[pass ஆனா]-> Final
```

இந்த lesson-ல Bengaluru-ல இருக்குற ஒரு venture fund, ஒரு பக்க startup briefs எழுதுற agent-ஐ build பண்றதை follow பண்றோம்.

## இது எப்படி work ஆகுது

**ReAct.** ஒவ்வொரு turn-லயும் model ஒரு சின்ன thought எழுதும் ("பதில் சொல்றதுக்கு முன்னாடி order status வேணும்"), அப்புறம் ஒரு tool call, அப்புறம் observation-ஐ பார்க்கும். கண்டுபிடிக்கிறதுக்கு ஏத்த மாதிரி சீக்கிரம் adapt ஆகும். பலவீனம்: நீண்ட tasks-ல drift. பதினைஞ்சு steps-க்கு அப்புறம் அது original goal-ஐ மறக்கலாம் அல்லது திரும்ப திரும்ப சொல்லலாம்.

**Plan-then-execute.** Model, பெரும்பாலும் ஒரு strong model, ஒரு தடவை எண்ணிடப்பட்ட plan-ஐ எழுதும். ஒரு மலிவான model அல்லது சாதாரண code ஒவ்வொரு step-ஐயும் execute பண்ணும். Plans நீண்ட tasks-ஐ predictable ஆக்கும், ஒரு user அல்லது approver-க்கு காட்ட easy ("நான் இதை பண்ணப்போறேன்"), விலை உயர்ந்த model ஒரு தடவை மட்டும் ஓடுறதால cost குறையும். பலவீனம்: இறுக்கம். Step 3 புதுசா ஏதோ காட்டும்போது, agent அதை கவனிச்சு re-plan பண்ணணும், அப்படியே உழுதுட்டு போகக்கூடாது.

**Reflection.** ரெண்டாவது pass கேக்கும்: இந்த result requirements-ஐ பூர்த்தி பண்ணுதா? Numbers consistent-ஆ இருக்கா? ஒவ்வொரு பகுதிக்கும் பதில் சொன்னேனா? இது அதே model-ல ஒரு critique prompt-ஆ இருக்கலாம், வேற model-ஆ இருக்கலாம், அல்லது deterministic checks-ஆ இருக்கலாம் (tests pass ஆகுது, totals கூடுது, JSON validate ஆகுது). Deterministic checks தான் மலிவு, நம்பகமானவை; rules-ஆல judge பண்ண முடியாத இடத்துல மட்டும் model critique use பண்ணுங்க.

**Cost-உம் limits-உம்.** ஒவ்வொரு pattern-உம் calls-ஐ கூட்டும். Reflection loops-க்கு ஒரு cap வேணும் (உதாரணம் ரெண்டு revision rounds), இல்லன்னா model-ஆல பூர்த்தி பண்ண முடியாத ஒரு requirement-ல என்றென்றைக்கும் loop ஆகலாம்.

**Patterns-ஐ ஒப்பிடுறது:**

| Pattern | பலம் | பலவீனம் | எதுக்கு நல்லது |
| --- | --- | --- | --- |
| ReAct | Simple, ஒவ்வொரு result-க்கும் adapt ஆகும் | நீண்ட tasks-ல drift ஆகும் | சின்ன tasks, சில tool calls |
| Plan-then-execute | ஒவ்வொரு பகுதியையும் cover பண்ணும், steps மலிவு, plan தெரியும் | Re-plan பண்ணாட்டி இறுக்கம் | தெரிஞ்ச பகுதிகள் இருக்குற நீண்ட tasks |
| Reflection | Users பார்க்குறதுக்கு முன்னாடி errors-ஐ பிடிக்கும் | கூடுதல் calls; loop ஆகலாம் | Check பண்ணக்கூடிய requirements இருக்குற outputs |

**எப்போ re-plan பண்றது.** Rule-ஐ executor-ல எழுதுங்க: ஒரு step-ஓட result plan-ல இருக்குற ஒரு assumption-ஓட முரண்பட்டா, நிறுத்தி, அந்த இடத்துல இருந்து ஒரு revised plan-ஐ planner-கிட்ட கேளுங்க. உதாரணம், step 2 அந்த startup போன வருஷமே acquire ஆகிடுச்சுன்னு கண்டுபிடிச்சா, brief-க்கு வேற வடிவம் வேணும்; original plan-ஐ தொடர்ந்தா steps வீணாகும், தவறாக வழிநடத்துற document உருவாகும். ஒவ்வொரு re-plan-ஐயும் log பண்ணுங்க, ஏன்னா அடிக்கடி re-plans வந்தா planner-ஓட முதல் plans மோசம்னு அர்த்தம்.

**Reflection-ஐ பயனுள்ளதா ஆக்குறது.** "improve this" மாதிரி மங்கலான critique prompt மங்கலான மாற்றங்களை தரும். Critic-க்கு ஒரு குறிப்பிட்ட checklist கொடுத்து, ஒவ்வொரு item-க்கும் ஒரு காரணத்தோட pass அல்லது fail கேளுங்க. Fail ஆன items-ஐ மட்டும் revision-க்கு திருப்பி அனுப்புங்க. இது revisions-ஐ focused-ஆ வச்சிருக்கும், எந்த checks அதிகம் fail ஆகுதுன்னு அளக்கவும் easy ஆக்கும்; அது main prompt-ல என்ன மேம்படுத்தணும்னு சொல்லும்.

**Checked plan-ஓட plan-then-execute.** Plan-ஐ structured data-வா கேளுங்க, code-ல check பண்ணுங்க, அப்புறம் தான் ஓட்டுங்க:

```python
from pydantic import BaseModel, Field

TOOLS = {"web_search", "fetch_page", "compare_table"}
MAX_STEPS, MAX_SEARCHES = 8, 5

class Step(BaseModel):
    tool: str
    purpose: str
    inputs: dict

class Plan(BaseModel):
    goal: str
    steps: list[Step] = Field(min_length=1)

def check_plan(plan: Plan):
    problems = []
    if len(plan.steps) > MAX_STEPS:
        problems.append(f"{len(plan.steps)} steps; the limit is {MAX_STEPS}")
    unknown = {s.tool for s in plan.steps} - TOOLS
    if unknown:
        problems.append(f"unknown tools: {sorted(unknown)}")
    if sum(s.tool == "web_search" for s in plan.steps) > MAX_SEARCHES:
        problems.append("too many searches")
    if plan.steps[-1].tool != "compare_table":
        problems.append("the plan must end by building the comparison table")
    return problems
```

Model-ஐ structured output-ல plan தர சொல்லுங்க (structured-output lesson எப்படின்னு காட்டும்), `check_plan`-ஐ ஓட்டி, problems இருந்தா ஒரு revision-க்கு திருப்பி அனுப்புங்க. அப்பவும் fail ஆனா, நிறுத்தி ஒரு ஆள்கிட்ட கேளுங்க. ஓட்டுறதுக்கு முன்னாடி checked plan-ஐ user-க்கு காட்டுறதும் நம்பிக்கையை வளர்க்கும்: "நான் மூணு makers-ஐ search பண்ணி, அவங்க spec pages-ஐ படிச்சு, ஒரு table build பண்ணுவேன். போகலாமா?"

**Natural language-ல plan, இல்ல calls-ல plan.** ஒரு plan exact function calls-ஐ (`web_search(query="Ather 450X range")`) சொல்லலாம், அல்லது steps-ஐ வார்த்தைகள்ல ("ஒவ்வொரு maker-ஓட real-world range-ஐ கண்டுபிடி") விவரிக்கலாம்; அடுத்த step அதை calls-ஆ மாத்தும். Exact calls check பண்ண easy; வார்த்தை plans tool பேர் மாற்றங்களை தாங்கும், ஆட்கள் படிக்க easy. நிறைய teams plan-க்கு வார்த்தைகளையும், execution-க்கு exact calls-ஐயும் use பண்றாங்க.

**Checklist-ஓட reflection.** Critic-கிட்ட rewrite கேக்காம, ஒவ்வொரு item-க்கும் ஒரு verdict கேளுங்க:

```python
CHECKLIST = [
    "Every maker has price, range and service network filled in",
    "Every number has a source link",
    "Prices are in rupees and say ex-showroom or on-road",
    "No maker is missing from the final table",
]

CRITIC_PROMPT = (
    "Check the draft against each item. Reply as JSON: "
    '[{"item": ..., "pass": true or false, "reason": ...}]. Do not rewrite the draft.\n\n'
    "Checklist:\n" + "\n".join(f"- {c}" for c in CHECKLIST)
)
```

Fail ஆன items-ஐ மட்டும் writer-கிட்ட திருப்பி அனுப்புங்க, ஒண்ணு அல்லது ரெண்டு revision rounds அனுமதிங்க, எந்த items அதிகம் fail ஆகுதுன்னு log பண்ணுங்க. Code-ல check பண்ணக்கூடிய rule இருந்தா (ஒவ்வொரு row-லயும் மூணு numbers இருக்கு, ஒவ்வொரு number-க்கும் link இருக்கு), அதை code-லயே check பண்ணி, அந்த item-க்கு model critic-ஐ தவிர்த்துடுங்க.

**Fail ஆன attempt-ல இருந்து கத்துக்கிறது.** Reflexion approach-ல, ஒரு attempt ஒரு check-ல fail ஆனா, agent ஏன்னு ஒரு சின்ன note எழுதும் ("நான் launch prices use பண்ணேன்; brief கேட்டது தற்போதைய on-road prices"), அடுத்த attempt அந்த note-ஓட ஆரம்பிக்கும். சேர்க்குறது மலிவு, tests pass ஆகணும் மாதிரி தெளிவான pass அல்லது fail இருக்குற tasks-ல அதிகம் உதவும்.

**சத்தமா யோசிக்கிறதோட cost.** Thoughts, plans, critiques எல்லாமே tokens தான். Prompt-ல வடிவ examples இருந்தா இன்னும் கூடும். ஒவ்வொரு சேர்ப்பும் இருக்கும்போதும் இல்லாதப்போவும் ஒரு task-க்கு tokens-ஐயும் நேரத்தையும் அளவிடுங்க; தன் செலவை ஈடுகட்ற அளவு results-ஐ மேம்படுத்துறதை மட்டும் வச்சுக்கோங்க.

## ஒரு worked example

Bengaluru-ல ஒரு venture fund, public sources-ல இருந்து ஒரு startup பத்தின ஒரு பக்க brief-ஐ தயாரிக்கிற agent வேணும்னு நினைக்குது: funding history, founders, product, competitors, red flags.

*Version 1, சுத்தமான ReAct.* அது search பண்ணும், படிக்கும், மறுபடி search பண்ணும். பாதி companies-ல funding news-க்கு மட்டும் 25 steps செலவழிச்சு, competitors-ஐ தொடவே இல்ல. Briefs ஒரே சீரா இல்ல.

*Version 2, plan-then-execute.* ஒரு planning call இதை உருவாக்குது:

```text
1. Find the company's website and product description.
2. Find funding rounds (amount, date, lead investor) from news and filings.
3. Identify founders and their backgrounds.
4. List three to five competitors.
5. Look for red flags: lawsuits, layoffs, regulatory action.
6. Write the brief in the template.
```

ஒவ்வொரு step-உம் அஞ்சு tool calls cap-ஓட ஒரு சின்ன ReAct loop ஓட்டுது. இப்போ ஒவ்வொரு section-உம் cover ஆகுது, steps ஒரு சின்ன model-ஐ use பண்றதால சராசரி cost மூணுல ஒரு பங்கு குறையுது.

*Version 3, reflection சேர்க்குறது.* Analysts, listed rounds-ஓட பொருந்தாத funding totals-ஐ கண்டுபிடிக்கிறாங்க. ஒரு reflection step draft-ஐ ஒரு checklist-க்கு எதிரா check பண்ணுது: totals rounds-ஓட கூட்டுத்தொகைக்கு சமம், ஒவ்வொரு claim-க்கும் ஒரு source link, ஒவ்வொரு section-உம் நிரப்பப்பட்டிருக்கு. Arithmetic-ஐ code check பண்ணுது; source இல்லாத claims-ஐ model check பண்ணுது. Fail ஆனவை ஒரு revision-க்கு திரும்ப போகும். Source இல்லாத claims, sentences-ல 11%-ல இருந்து 2%-க்கு குறையுது.

| Version | Cover ஆன sections | Source இல்லாத claims | Relative cost |
| --- | --- | --- | --- |
| 1: ReAct மட்டும் | சீரில்ல; competitors அடிக்கடி விடுபடும் | Sentences-ல 11% | 1.0 |
| 2: Plan-then-execute | ஆறும் | கிட்டத்தட்ட 11% | கிட்டத்தட்ட 0.67 |
| 3: கூடவே reflection, ஒரு revision | ஆறும் | 2% | கிட்டத்தட்ட 0.75 |

## பொதுவா பண்ற தப்புகள்

- **சின்ன tasks-க்கு planning.** ரெண்டு-step lookup-க்கு plan தேவையில்ல; அது ஒரு call-ஐ மட்டும் கூட்டும்.
- **ஒருபோதும் மாறாத plans.** ஒரு step-ஓட result plan-ஓட முரண்பட்டா, agent கண்ணை மூடிட்டு தொடராம re-plan பண்ணணும்.
- **முடிவில்லாத self-critique.** Reflection rounds-ஐ cap பண்ணுங்க, critique தன்னையே திரும்ப சொல்லும்போது நிறுத்துங்க.
- **Code போதும்ங்கிற இடத்துல model critique.** ஒரு rule-ஆல check பண்ண முடிஞ்சா (sums, schemas, tests), rule-ஐ use பண்ணுங்க.
- **Plan-ஐ மறைக்கிறது.** Users-க்கு plan-ஐ காட்டினா நம்பிக்கை வளரும், திசையை சீக்கிரமே திருத்தவும் முடியும்.
- **யாரும் check பண்ணாத plans.** Check பண்ணாத plan இல்லாத tools-ஐ பேர் சொல்லலாம் அல்லது budget-ஐ தாண்டலாம்.
- **Rewrite பண்ற critics.** ஒவ்வொரு item-க்கும் pass அல்லது fail கேளுங்க; rewrite என்ன தப்புன்னு மறைச்சிடும்.

## Planning, reflection-ஐ தவிர்க்க வேண்டிய நேரங்கள்

- **ஒண்ணு அல்லது ரெண்டு tool calls இருக்குற சின்ன tasks**: சாதாரண ReAct போதும்.
- **Tight latency budgets**: ஒவ்வொரு planning, critique call-உம் seconds-ஐ சேர்க்கும்.
- **பயன்படுத்துறதுக்கு முன்னாடி எப்பவும் ஒரு ஆள் review பண்ற outputs**, அங்க critic கொஞ்சம் தான் சேர்க்கும்.
- **Check பண்ணக்கூடிய requirements இல்லாத tasks**, critic-க்கு judge பண்ண உறுதியா எதுவும் இல்லாதப்போ.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு plan, re-plan, critique-ஐயும்** run trace-ல store பண்ணுங்க.
- **Re-plan rate-ஐயும் item வாரியா critique failure rate-ஐயும் track பண்ணுங்க**; ரெண்டும் prompt fixes-ஐ காட்டும்.
- **Revision rounds-ஐ code-ல cap பண்ணுங்க**, cap-ஐ தொட்டதும் handover பண்ணுங்க.
- **நீண்ட அல்லது செலவான tasks-க்கு plans-ஐ users-க்கு காட்டுங்க**, edit அல்லது cancel பண்ண விடுங்க.
- **ஒவ்வொரு pattern-ஐயும் வச்சுக்கிறதுக்கு முன்னாடி**, அது இருக்கும்போதும் இல்லாதப்போவும் ஒரு task-க்கான cost-ஐ அளவிடுங்க.
