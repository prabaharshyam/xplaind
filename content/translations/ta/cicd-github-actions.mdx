## இது என்ன

**Continuous integration (CI)** ஒவ்வொரு pull request-லயும் checks run பண்ணும்: lint, type checks, unit tests, AI systems-க்கு ஒரு சின்ன eval. Branch protection இருக்கறதால fail ஆகுற change merge ஆகவே முடியாது.

**Continuous delivery (CD)** merge ஆன ஒவ்வொரு change-ஐயும் environments வழியா தானா கொண்டு போகும்: ஒரு image build பண்ணும், staging-ல deploy பண்ணும், smoke test பண்ணும், அப்புறம் ஒருத்தர் approve பண்ணதும் production-க்கு promote பண்ணும். அந்த approval step இல்லன்னா அதுக்கு **continuous deployment**-னு பேர். Banking, insurance, health-ல இருக்குற பெரும்பாலான client teams approval-ஐ தான் விரும்புவாங்க.

ரெண்டையும் பண்ண GitHub Actions ஒரு common வழி. GitLab CI, Azure DevOps, Jenkins-உம் இதே ideas-ஐ வேற syntax-ல use பண்ணுது; ஒரு client-க்கு அவங்களோட சொந்த choice இருக்கும்.

```flow
title: Pull request-ல இருந்து production வரை
Pull request -> CI: lint, types, tests, smoke eval -> Pass ஆச்சா?
Pass ஆச்சா? -[இல்ல]-> Merge block ஆகும்
Pass ஆச்சா? -[ஆமா]-> Review பண்ணி main-க்கு merge
Review பண்ணி main-க்கு merge -> ஒரே ஒரு image build | tag = commit hash
ஒரே ஒரு image build -> Staging-ல deploy -> Staging-ல smoke test -> பேர் சொன்ன reviewer-ஓட approval
பேர் சொன்ன reviewer-ஓட approval -> அதே image-ஐ production-க்கு promote -> Healthy-ஆ இருக்கா?
Healthy-ஆ இருக்கா? -[இல்ல]-> கடைசி நல்ல tag-ஐ redeploy
```

இந்த lesson, Kochi-ல ஒரு insurer-ஓட engineering team-க்கு ஒரு claims assistant-ஐ handover பண்றதை follow பண்ணுது.

## இது எப்படி work ஆகுது

### ஒரு workflow-ஓட parts

| Part | அது என்ன | இந்த lesson-ல |
| --- | --- | --- |
| Workflow | `.github/workflows/`-ல ஒரு YAML file | `ci-cd.yml`, `rollback.yml` |
| Event | அதை start பண்றது எது | ஒரு pull request, main-க்கு ஒரு push, ஒரு manual run |
| Job | ஒரு fresh machine-ல (runner) ஓடுற steps-ஓட group | test, smoke-eval, build, deploy-staging, deploy-production |
| Step | ஒரு command, இல்லன்னா ஒரு ready-made **action** | `uv run pytest`, `docker/build-push-action` |
| Environment | சொந்த secrets, rules இருக்குற பேர் வச்ச ஒரு deploy target | staging, production |

ஒரு job இன்னொண்ணை `needs` பண்ணலைன்னா jobs parallel-ஆ ஓடும். ஒவ்வொரு job-உம் ஒரு clean machine-ல start ஆகும், அதனால அதுக்கு என்ன வேணுமோ (code, tools, credentials) அதை அதுவே fetch பண்ணணும்.

### எது எங்க ஓடுது, எவ்வளவு தடவை

| Check | எப்போ | வழக்கமான நேரம் | Build-ஐ fail பண்ணுமா? |
| --- | --- | --- | --- |
| Lint, format, type checks | ஒவ்வொரு pull request-லயும் | ஒரு நிமிஷத்துக்குள்ள | ஆமா |
| Fake model வச்சு unit tests | ஒவ்வொரு pull request-லயும் | 1 முதல் 3 நிமிஷம் | ஆமா |
| Smoke eval, 50 golden questions | Prompts, retrieval அல்லது evals-ஐ தொடுற pull requests | 2 முதல் 4 நிமிஷம் | ஆமா, main-ஐ விட தெளிவா கீழ போனா |
| Staging smoke test | ஒவ்வொரு staging deploy-க்கும் அப்புறம் | ஒரு நிமிஷத்துக்குள்ள | ஆமா, production-ஐ block பண்ணும் |
| Full eval, நூற்றுக்கணக்கான cases | ஒவ்வொரு ராத்திரியும் | 10 முதல் 60 நிமிஷம் | Team-க்கு alert பண்ணும் |

இந்த நேரங்கள் வழக்கமான ranges தான், measurements இல்ல. Table-க்கு பின்னாடி இருக்குற rule: ஒரு check எவ்வளவு fast-ஆ, cheap-ஆ இருக்கோ, அவ்வளவு சீக்கிரம் அது ஓடணும்.

### Flake ஆகாத ஒரு smoke eval

ஒரு model perfect-ஆ repeat ஆகாது, அதனால ஒரு சின்ன eval அதே code-ல pass-உம் ஆகலாம், fail-உம் ஆகலாம். 20 questions இருந்தா, ஒவ்வொரு question-உம் 5 points: ஒரு answer மாறினா score 0.85-ல இருந்து 0.80-க்கு போயிடும். Rerun பண்ணா மாறுற ஒரு gate, green வர்ற வரை "Re-run" அமுக்க ஆளுங்களுக்கு கத்துக்குடுக்கும், அப்புறம் உண்மையான failures-ஐயும் ignore பண்ணுவாங்க. நாலு பழக்கங்கள் இதை சரி பண்ணும்:

- **சுமார் 50 cases use பண்ணுங்க.** அப்போ ஒவ்வொரு case-உம் 5 இல்ல, 2 points தான்.
- **Temperature 0 use பண்ணுங்க**, உங்க model support பண்ணா; கூடவே ஒரு fixed retrieval index.
- **Fail ஆன case-ஐ ஒரு தடவை retry பண்ணுங்க.** உண்மையான regression ரெண்டு தடவையும் fail ஆகும்; noise பொதுவா அப்படி ஆகாது.
- **Fixed number கூட இல்ல, main கூட compare பண்ணுங்க.** Main-ஓட score-ஐ `evals/baseline.json`-ல store பண்ணுங்க (ஒரு nightly job அதை refresh பண்ணலாம்), pull request 2 cases-க்கு மேல மோசமா இருந்தா மட்டும் fail பண்ணுங்க. கூடவே ஒரு hard floor-உம் வச்சுக்கோங்க, அப்போ மெதுவான drift pass ஆகாது.

கீழ இருக்குற `expected in answer` check ஒரு crude smoke test தான்: அந்த phrase-ஐ தற்செயலா வச்சிருக்குற நீளமான answers-க்கு அது reward குடுக்கும். Nightly full eval இன்னும் strict-ஆன grading use பண்ணணும். Script அதோட exit code வச்சு முடிவு பண்ணும்; non-zero exit எதுவா இருந்தாலும் job fail ஆகும்.

```python
import argparse, json, sys
from app.answer import answer   # your pipeline, called with temperature 0

p = argparse.ArgumentParser()
p.add_argument("--baseline", default="evals/baseline.json")
p.add_argument("--tolerance", type=int, default=2)   # cases, not percent
p.add_argument("--floor", type=float, default=0.80)
args = p.parse_args()

def ok(case):
    return case["expected"].lower() in answer(case["question"]).lower()

cases = [json.loads(line) for line in open("evals/smoke.jsonl")]
correct = sum(ok(c) or ok(c) for c in cases)          # one retry per failed case
base = json.load(open(args.baseline))["correct"]
print(f"smoke: {correct}/{len(cases)} correct, main has {base}")
failed = correct < base - args.tolerance or correct / len(cases) < args.floor
sys.exit(1 if failed else 0)
```

### Secrets, environments, OIDC

**Secrets** repository அல்லது environment settings-ல இருக்கும், encrypt ஆகி, logs-ல mask ஆகி; repository-க்குள்ள எப்பவும் இல்ல. ஒவ்வொரு environment-க்கும் சொந்த secrets குடுங்க, அப்போ ஒரு staging key production-ஐ எப்பவும் எட்டாது. Required reviewer job-ஐ approve பண்ற வரை ஒரு environment-ஓட secrets lock-ஆ இருக்கும்.

**Required reviewers.** ஆறு பேர் அல்லது teams வரை பேர் சொல்லலாம்; ஒரு approval போதும். Deploy-ஐ start பண்ணவரே அதை approve பண்றதையும் தடுக்கலாம். GitHub Free, Pro, Team-ல required reviewers public repositories-ல மட்டும் தான் work ஆகும்; private repositories-க்கு GitHub Enterprise வேணும். Approval gate-ஐ promise பண்றதுக்கு முன்னாடி client-ஓட plan-ஐ check பண்ணுங்க.

**Forks-ல இருந்து வர்ற pull requests-க்கு secrets கிடைக்காது** (limited-ஆன ஒரு `GITHUB_TOKEN` தவிர). அதனால தான் கீழ இருக்குற smoke eval fork pull requests-ஐ skip பண்ணுது; அதை ஒரு maintainer கையால evaluate பண்ணுவாரு. Workaround-ஆ `pull_request_target` trigger-ஐ use பண்ணாதீங்க: அது உங்க secrets கூட ஓடும், அதனால ஒரு fork-ஓட code-ஐ அதுல run பண்ணா ஒரு அந்நியர் அவற்றை படிக்க முடியும்.

**Keys-க்கு பதிலா OIDC.** `id-token: write` இருந்தா, ஒரு job GitHub கிட்ட repository, environment பேர் இருக்குற ஒரு signed token கேக்கலாம், உதாரணமா `repo:kochi-insure/claims-assistant:environment:production`. Cloud சரியா அந்த பேரோட match ஆகுற tokens-ஐ மட்டும் நம்பி, expire ஆகுற credentials-ஐ திருப்பி குடுக்கும்; AWS-ல default-ஆ ஒரு மணி நேரத்துக்கு அப்புறம். Leak ஆக long-lived key எதுவும் இல்ல. Azure, Google Cloud-லயும் இதே pattern இருக்கு.

**Registry.** GitHub-ஓட registry-க்கு (GHCR) push பண்ண `GITHUB_TOKEN` மட்டும் போதும். ஆனா AWS-ல இருக்குற ஒரு service private GHCR image-ஐ pull பண்ணணும்னா ஒரு stored pull credential வேணும். Client AWS-ல run பண்ணா, அவங்க ECR registry-க்கு push பண்றது பெரும்பாலும் simple, ஏன்னா IAM role ஏற்கனவே pull access குடுக்குது.

### Supply chain: ஒவ்வொரு action-ஐயும் pin பண்ணுங்க

ஒரு third-party action உங்க code, secrets-க்கு access கூட ஓடும். `@v4` மாதிரி ஒரு version tag ஒரு pointer தான், அதோட owner (அல்லது ஒரு attacker) அதை move பண்ணலாம். March 2025-ல attackers பிரபலமான `tj-actions/changed-files` action-ஓட tags-ஐ build logs-ல secrets-ஐ print பண்ற malicious code-க்கு move பண்ணாங்க (CVE-2025-30066). முன்னாடி இருந்த commit SHA-க்கு pin பண்ணின workflows safe code-ஐயே தொடர்ந்து run பண்ணுச்சு.

அதனால ஒவ்வொரு third-party action-ஐயும் அதோட full 40-character commit SHA-க்கு pin பண்ணுங்க, version-ஐ ஒரு comment-ல போடுங்க, Dependabot updates propose பண்ணட்டும் (`.github/dependabot.yml`-ல `package-ecosystem: "github-actions"` add பண்ணுங்க). ஒரு update-ஐ merge பண்றதுக்கு முன்னாடி diff-ஐ படிங்க. 28 November 2026 அன்னைக்கு check பண்ணப்போ ரெண்டு notes:

- `astral-sh/setup-uv` v7-க்கு அப்புறம் moving major tags publish பண்றதில்ல, அதனால `@v10` resolve ஆகாது. அதோட சொந்த README-யே ஒரு SHA-வை pin பண்ணுது.
- GitHub இப்போ workflow lockfiles-ஐ (`.github/workflows/actions.lock`, `gh actions-lock` வச்சு உருவாக்கினது) document பண்ணுது; அது உங்க actions use பண்ற actions-ஐயும் pin பண்ணும். அதோட setup guide GitHub Enterprise Cloud-க்கு தான் list ஆகியிருக்கு; மத்த plans-ல SHA pins use பண்ணுங்க.

### Speed, cost, safety switches

- **Caching.** GitHub-hosted runners-ல `setup-uv` default-ஆ packages-ஐ cache பண்ணும். மத்த tools-க்கு lock file வச்சு cache பண்ணுங்க. Fast CI-ஐ ஆளுங்க use பண்ணுவாங்க; slow CI-ஐ bypass பண்ணுவாங்க.
- **Concurrency.** அதே pull request-க்கு யாராவது திரும்ப push பண்ணா பழைய run-ஐ cancel பண்ணுங்க. Main-ல ஓடுற run-ஐ எப்பவும் cancel பண்ணாதீங்க: அது ஒரு deploy-ஓட பாதியில இருக்கலாம். ஒவ்வொரு deploy target-க்கும் சொந்த concurrency group குடுங்க, அப்போ ரெண்டு deploys எப்பவும் overlap ஆகாது.
- **Timeouts.** ஒரு job-ஓட default timeout 360 நிமிஷம். ஒவ்வொரு job-லயும் `timeout-minutes` set பண்ணுங்க, அப்போ மாட்டிக்கிட்ட ஒரு model call ஆறு மணி நேர runner time-ஐ வீணாக்காது.
- **Path filters job-க்குள்ள.** `on.pull_request.paths` வச்சு மொத்த workflow-ஐயும் skip பண்ணா, அதுல இருந்து வர்ற required check "Pending"-ஆவே இருந்து merge-ஐ block பண்ணும். அதனால smoke eval job எப்பவும் ஓடும், அதோட steps என்ன மாறிச்சுன்னு check பண்ணும்.
- **Least privilege.** மேல `permissions: {contents: read}` set பண்ணுங்க, ஒரு job-க்கு என்ன வேணுமோ அதை மட்டும் add பண்ணுங்க, உதாரணமா `packages: write` அல்லது `id-token: write`.

### Branch protection

Main-க்கான repository rules-ல, merge பண்றதுக்கு முன்னாடி test, smoke-eval checks pass ஆகணும், குறைஞ்சது ஒரு review வேணும்னு require பண்ணுங்க. இது இல்லன்னா CI வெறும் advice தான்.

### முழு workflow

Action versions 28 November 2026 அன்னைக்கு check பண்ணது. ஆறுமே Node 24 runtime-ஐ declare பண்ணுது.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]

permissions: {contents: read}
concurrency:                       # cancels old pull request runs only
  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: true
env:
  IMAGE: ${{ vars.IMAGE_REPO }}:${{ github.sha }}   # registry names must be lowercase

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: {contents: read, pull-requests: read}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: dorny/paths-filter@ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d # v4.0.3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - if: steps.changed.outputs.ai == 'true'
        uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - if: steps.changed.outputs.ai == 'true'

    timeout-minutes: 20
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1

        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@c3c9e263c25d99ce0380d002d59b67737d91b0dc # v7.4.0
        with: {context: ., push: true, tags: "${{ env.IMAGE }}"}

  deploy-staging:
    needs: build
    environment: staging
    concurrency: {group: deploy-staging}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}

  deploy-production:
    needs: deploy-staging
    environment: production          # required reviewers; its own role and secrets
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"   # same image, no rebuild

```

`vars.DEPLOY_ROLE_ARN`, `vars.BASE_URL` ரெண்டும் environment variables, அதனால அதே lines ஒரு job-ல staging-ஐயும் இன்னொண்ணுல production-ஐயும் point பண்ணும்.

### Rollback, அது work ஆகுமான்னு migrations ஏன் முடிவு பண்ணுது

ஒவ்வொரு image-உம் அதோட commit வச்சு tag ஆகியிருக்கறதால, rollback-னா கடைசி நல்ல tag-ஐ redeploy பண்றது தான். அதை அதே production environment, approval use பண்ற ஒரு manual workflow-ஆ ஆக்குங்க:

```yaml
name: rollback
on:
  workflow_dispatch:
    inputs:
      sha: {description: "Commit of the last good image", required: true}
permissions: {contents: read, id-token: write}
jobs:
  rollback:
    environment: production
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh "${{ vars.IMAGE_REPO }}:$SHA"
        env: {SHA: "${{ inputs.sha }}"}   # passed as a variable, not pasted into the script
```

App-ஐ roll back பண்ணா database roll back ஆகாது. Release 42 ஒரு column-ஐ rename பண்ணா, release 41-ஓட image புது schema-ல crash ஆகும். அதனால migrations-ஐ deploy-க்கு முன்னாடி தனி step-ஆ run பண்ணுங்க, schema-வை **expand and contract** steps-ஆ மாத்துங்க: release ஒண்ணு புது column-ஐ add பண்ணி ரெண்டுக்கும் write பண்ணும்; release ரெண்டு புதுசை read பண்ணும்; release மூணு, வாரங்கள் கழிச்சு, பழைய column-ஐ drop பண்ணும். எந்த point-லயும் முந்தைய image இன்னும் work ஆகும்.

**உங்க browser-லயே try பண்ணுங்க.** இந்த checker timeouts இல்லாத jobs-ஐயும், commit SHA-க்கு pin பண்ணாத actions-ஐயும் கண்டுபிடிக்கும். உங்க சொந்த workflow-ஐ paste பண்ணி run பண்ணுங்க.

```python
import re, yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: some-org/setup-thing@v2
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes (the default is 360)")
    for step in job.get("steps", []):
        ref = step.get("uses", "")
        if ref and not ref.startswith("./") and not re.fullmatch(r"[0-9a-f]{40}", ref.split("@")[-1]):
            print(f"{name}: pin {ref} to a full commit SHA")
```

**Insurer-க்கு என்ன மாறிச்சு.** முன்னாடி deploys ஒரு laptop-ல இருந்து நடந்துச்சு, எந்த version live-ல இருக்குன்னு யாருக்கும் உறுதியா தெரியாது. இப்போ ஒவ்வொரு production version-உம் பேர் சொன்ன approver கூட ஒரு commit hash. ஒரு claims manager ஒரு மோசமான answer-ஐ report பண்ணா, எந்த code, prompt அதை உருவாக்குச்சுன்னு team சரியா சொல்ல முடியும்.

## பொதுவா பண்ற தப்புகள்

- **Main-ல மட்டும் CI.** Problems merge ஆனதுக்கு அப்புறம் தான் தெரியும். CI-ஐ pull requests-ல run பண்ணி required check ஆக்குங்க.
- **Fixed threshold கூட ஒரு குட்டி eval.** அது flake ஆகும், ஆளுங்க green வர்ற வரை rerun பண்ண பழகிடுவாங்க. சுமார் 50 cases, temperature 0, ஒரு retry use பண்ணி, main கூட compare பண்ணுங்க.
- **ஒவ்வொரு push-லயும் paid evals.** Prompts, retrieval அல்லது evals மாறும்போது மட்டும் smoke eval run பண்ணுங்க; full suite-ஐ ராத்திரி run பண்ணுங்க.
- **Path filter வச்சு மொத்த workflow-ஐயும் skip பண்றது.** அதோட required checks Pending-ஆவே இருக்கும். Job-க்குள்ள filter பண்ணுங்க.
- **Files-ல secrets, அல்லது long-lived cloud keys-ஐ secrets-ஆ வச்சிருக்கறது.** Environment secrets use பண்ணுங்க, cloud access-க்கு OIDC.
- **ஒவ்வொரு environment-க்கும் rebuild பண்றது.** ஒரு தடவை build பண்ணி, அதே image-ஐ promote பண்ணுங்க.
- **Tag வச்சு pin பண்ணின third-party actions.** Tags move ஆகும். Full SHAs-ஐ pin பண்ணி, Dependabot updates propose பண்ணட்டும்.
- **Workflow முழுக்க cancel-in-progress.** ஒரு புது merge ஒரு deploy-ஐ பாதியில கொன்னுடும். Pull request runs-ஐ மட்டும் cancel பண்ணுங்க.
- **Timeouts இல்ல.** மாட்டிக்கிட்ட ஒரு job ஆறு மணி நேரம் வரை ஓடும்.
- **யாருமே try பண்ணாத rollback, அல்லது அதை உடைக்குற migration.** Rollback-ஐ practice பண்ணுங்க, expand and contract use பண்ணுங்க.
- **Flaky tests-ஐ அப்படியே விடுறது.** சீக்கிரமா fix பண்ணுங்க இல்லன்னா remove பண்ணுங்க, இல்லாட்டி உண்மையான failures-ஐயும் ignore பண்ணுவாங்க.

## ஒரு lighter pipeline போதும்ங்கிறது எப்போ

- **ஒரு personal project**: pull requests-ல lint, tests போதுமானது.
- **Built-in deploys இருக்குற platforms**, உதாரணமா Vercel previews; அங்க CI-க்கு checks மட்டும் போதும்.
- **Notebooks, research code**, எப்பவும் deploy ஆகாதவை.

## Demo-ல இருந்து production-க்கு

உங்க pipeline-ஐ take over பண்றதுக்கு முன்னாடி ஒரு client-ஓட engineering lead check பண்றது:

- **Main protected-ஆ இருக்கு**: required checks, குறைஞ்சது ஒரு review.
- **Production-க்கு approval வேணும்**, அதுக்கு சொந்த secrets இருக்கு, அந்த environment-ஐ மட்டும் நம்புற ஒரு role இருக்கு.
- **Long-lived cloud keys** GitHub-ல எங்கயுமே இல்ல.
- **ஒவ்வொரு action-உம் pin ஆகியிருக்கு**, commit SHA-க்கு, Dependabot on-ல.
- **AI gate stable-ஆ இருக்கு**, ஒரு baseline, ஒரு nightly full eval கூட.
- **Rollback எழுதி வச்சிருக்கு, ஒரு தடவை run-உம் பண்ணியாச்சு**, migrations expand and contract-ஐ follow பண்ணுது.

## Practice பண்ணுங்க

GitHub-ஓட Actions quickstart-ஐயும் deployment environments பத்தின page-ஐயும் follow பண்ணுங்க. ஒரு public repository use பண்ணுங்க, அப்போ free account-லயே required reviewers work ஆகும்.

1. ஒவ்வொரு pull request-லயும் lint, tests run பண்ற ஒரு workflow add பண்ணி, அதை main-ல required check ஆக்குங்க.
2. ஒவ்வொரு action-ஐயும் commit SHA-க்கு pin பண்ணி, `github-actions`-க்கு ஒரு Dependabot file add பண்ணுங்க.
3. Main-க்கு merge ஆகும்போது உங்க Docker image-ஐ commit hash வச்சு tag பண்ணி build பண்ணி push பண்ற ஒரு job add பண்ணுங்க.
4. Staging, production environments create பண்ணி, production-க்கு உங்களையே required reviewer-ஆ add பண்ணி, அதே image-ஐ ரெண்டுலயும் deploy பண்ணுங்க.
5. Job-க்குள்ள path filter கூட smoke eval-ஐ add பண்ணுங்க. ரெண்டு pull requests open பண்ணி, அது ஒரு தடவை ஓடுறதையும் ஒரு தடவை skip ஆகுறதையும் காட்டுங்க.
6. முந்தைய image-ஐ redeploy பண்ண rollback workflow-ஐ run பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** CI block பண்ணின ஒரு failing pull request-ஐயும், production-க்கு முன்னாடி ஒரு approval gate-ஐயும், நீங்களே பண்ணின ஒரு rollback-ஐயும் காட்ட முடியும்.
