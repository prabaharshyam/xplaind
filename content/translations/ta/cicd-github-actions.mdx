## இது என்ன

**Continuous integration (CI)** ஒவ்வொரு change-லயும் checks-ஐ run பண்ணும்: lint, type checks, unit tests, AI systems-க்கு ஒரு சின்ன eval suite. Fail ஆகுற change merge ஆகாது.

**Continuous delivery (CD)** merge ஆன change-ஐ environments வழியா தானா கொண்டு போகும்: image build பண்றது, staging-ல deploy பண்றது, smoke tests run பண்றது, அப்புறம் production-ல deploy பண்றது; பெரும்பாலும் ஒரு person approve பண்ணப்புறம்.

ரெண்டுக்கும் GitHub Actions ஒரு common வழி. Workflows `.github/workflows/`-ல இருக்குற YAML files; pull request அல்லது main-க்கு push மாதிரி events-ல run ஆகும். GitLab CI, Azure DevOps, Jenkins-உம் இதே மாதிரி தான் work ஆகும்; clients-க்கு அவங்களோட சொந்த choice இருக்கும்.

```flow
Pull request -> CI: lint, types, tests, smoke eval -> Pass ஆச்சா?
Pass ஆச்சா? -[இல்ல]-> Block ஆச்சு
Pass ஆச்சா? -[ஆமா]-> Merge பண்ணலாம் -> main-க்கு merge
main-க்கு merge -> Image-ஐ build பண்றது | tag = commit hash
Image-ஐ build பண்றது -> Staging-ல deploy -> Smoke tests -> பேர் வச்ச reviewer-ஓட approval -> அதே image-ஐ production-ல deploy -> Problem இருக்கா?
Problem இருக்கா? -[ஆமா]-> முந்தைய tag-ஐ redeploy பண்ணுங்க
```

இந்த lesson-ல Kochi-ல ஒரு insurer-ஓட engineering team-க்கு, ஒரு claims assistant-ஐ handover பண்றதை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Triggers and jobs.** ஒரு workflow events-ல (`pull_request`, main-க்கு `push`, ஒரு tag, ஒரு manual dispatch) run ஆகும். அதுல jobs இருக்கும்; ஒவ்வொரு job-உம் ஒரு புது machine-ல (runner-ன்னு சொல்வாங்க) steps-ஐ run பண்ணும்.

**CI job** code-ஐ checkout பண்ணும், dependencies-ஐ install பண்ணும் (caching-ஓட), lint, types, tests-ஐ run பண்ணும். AI app-க்கு, ஒரு சின்ன, fast eval-ஐ சேருங்க: ஒரு fixed retrieval index-க்கு எதிரா 20 golden questions; accuracy ஒரு threshold-க்கு கீழ போனா build fail ஆகணும். மெதுவான, costly evals-ஐ ஒரு nightly job-க்கு வச்சுக்கோங்க.

**Build job** Docker image-ஐ build பண்ணி, commit hash வச்சு tag பண்ணி, client-ஓட registry-க்கு push பண்ணும்.

**Deploy jobs** **environments**-ஐ use பண்ணும். `staging` environment தானா deploy ஆகும்; `production` environment-க்கு பேர் வச்ச reviewer-ஓட approval வேணும், அதுக்கு தனி secrets-உம் இருக்கும். Secrets CI system-ல store ஆகும் அல்லது run time-ல cloud-ல இருந்து எடுக்கப்படும்; repository-ல ஒருபோதும் இல்ல. இன்னும் better: stored keys-க்கு பதிலா, OpenID Connect வழியா short-lived credentials வச்சு runner cloud-ல sign in ஆகட்டும்.

**Rollback.** ஒவ்வொரு deploy-உம் commit வச்சு tag பண்ண image-ஐ use பண்றதால, rollback-னா முந்தைய tag-ஐ redeploy பண்றது தான். அதை ஒரே button அல்லது command-ஆ ஆக்கி, practice பண்ணுங்க.

**எது எங்க run ஆகுது, எவ்வளவு அடிக்கடி:**

| Check | எப்போ | வழக்கமான நேரம் | Build-ஐ fail பண்ணுமா? |
| --- | --- | --- | --- |
| Lint and format | ஒவ்வொரு PR | Seconds | ஆமா |
| Type checks | ஒவ்வொரு PR | ஒரு நிமிஷத்துக்கும் குறைவு | ஆமா |
| Fake model வச்சு unit tests | ஒவ்வொரு PR | 1 முதல் 3 நிமிஷம் | ஆமா |
| Smoke eval, 20 golden questions | Prompts அல்லது retrieval-ஐ தொடுற ஒவ்வொரு PR | 1 முதல் 2 நிமிஷம் | ஆமா, threshold-க்கு கீழ போனா |
| Full eval, நூற்றுக்கணக்கான cases | Nightly | 10 முதல் 60 நிமிஷம் | Team-க்கு alert போகும் |
| Load test | பெரிய releases-க்கு முன்னாடி | மாறும் | ரொம்ப slow-ஆ இருந்தா release-ஐ block பண்ணும் |

**Caching.** ஒவ்வொரு run-லயும் dependencies-ஐ install பண்றது slow. அவற்றை lock file-ஐ key-ஆ வச்சு cache பண்ணுங்க, அப்போ CI பத்து நிமிஷம் இல்ல, சில நிமிஷங்கள் தான் ஆகும். Fast CI-ஐ மக்கள் use பண்ணுவாங்க; slow CI-ஐ bypass பண்ணுவாங்க.

**Branch protection.** Repository settings-ல, main-க்கு merge பண்றதுக்கு முன்னாடி CI job pass ஆகணும், குறைஞ்சது ஒரு review-வும் வேணும்னு require பண்ணுங்க. இது இல்லன்னா, CI வெறும் advice தான்.

**Practice-ல secrets.** Workflow-க்கு சில secrets வேணும்: smoke eval-க்கு ஒரு model API key, images push பண்ண credentials, deploy பண்ண credentials. அவற்றை repository அல்லது environment-ஓட secret settings-ல store பண்ணுங்க; அங்க encrypted-ஆ இருக்கும், logs-ல hide ஆகும். ஒவ்வொரு environment-க்கும் தனி secrets கொடுங்க, அப்போ staging key production-ஐ தொடவே முடியாது. Cloud access-க்கு OpenID Connect-ஐ prefer பண்ணுங்க: cloud குறிப்பிட்ட repository-யையும் branch-ஐயும் நம்பி, கொஞ்ச நேரத்துல (பெரும்பாலும் ஒரு மணி நேரம்) expire ஆகுற ஒரு credential-ஐ கொடுக்கும். அப்போ leak ஆகக்கூடிய நீண்ட நாள் key-ஏ இருக்காது.

**ஒரு முழுமையான workflow.** ஒவ்வொரு pull request-லயும் CI, AI files மாறும்போது மட்டும் smoke eval, main-ல build-ம் deploy-உம்:

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v5
        with: {enable-cache: true}
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    runs-on: ubuntu-latest
    if: github.event_name == 'pull_request'
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - uses: astral-sh/setup-uv@v5
        if: steps.changed.outputs.ai == 'true'
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --min-accuracy 0.85
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@v6
        with: {push: true, tags: "ghcr.io/${{ github.repository }}:${{ github.sha }}"}

  deploy-production:
    needs: build
    runs-on: ubuntu-latest
    environment: production                    # requires a reviewer's approval
    permissions: {id-token: write, contents: read}
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh ghcr.io/${{ github.repository }}:${{ github.sha }}
```

Production job, OIDC வழியா (`id-token: write`-ஓடயும், cloud நம்புற ஒரு role-ஓடயும்) cloud access-ஐ பெறுது, அதனால நீண்ட நாள் cloud keys எதுவும் GitHub-ல இருக்காது. Azure, Google Cloud-க்கும் இதுக்கு இணையான login actions இருக்கு.

**Smoke eval script, தன்னோட exit code வச்சு decide பண்ணும்.** Zero இல்லாத எந்த exit-உம் job-ஐ fail பண்ணும்:

```python
import argparse, json, sys
from app.answer import answer                 # your pipeline

p = argparse.ArgumentParser(); p.add_argument("--min-accuracy", type=float, default=0.85)
args = p.parse_args()
cases = [json.loads(l) for l in open("evals/smoke.jsonl")]
correct = sum(c["expected"].lower() in answer(c["question"]).lower() for c in cases)
acc = correct / len(cases)
print(f"smoke accuracy {acc:.0%} on {len(cases)} cases")
sys.exit(0 if acc >= args.min_accuracy else 1)
```

**Actions-ஐ pin பண்ணுங்க.** Third-party actions உங்க repository-க்கு access-ஓட run ஆகும். அவற்றை ஒரு version-க்கு (இன்னும் கடுமையான setups-ல முழு commit hash-க்கு) pin பண்ணி, updates-ஐ review பண்ணுங்க; அப்போ compromised action உங்க pipeline-குள்ள நுழைய முடியாது.

**பழைய runs-ஐ cancel பண்ணுங்க.** ஒரே branch-க்கு மறுபடி push பண்ணும்போது, `concurrency` block பழைய run-ஐ cancel பண்ணும்; அதனால runner minutes-உம் model calls-உம் மிச்சமாகும்.

**உங்க browser-லயே try பண்ணுங்க.** ஒரு workflow-ல pin பண்ணாத actions, missing timeouts இருக்கான்னு check பண்ணுங்க. YAML-ஐ மாத்தி run பண்ணுங்க.

```python
import yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: some-org/setup-thing@main
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes so a stuck job cannot run for hours")
    for step in job["steps"]:
        ref = step.get("uses", "")
        if ref and ref.split("@")[-1] in ("main", "master"):
            print(f"{name}: pin {ref} to a version, not a branch")
```

## ஒரு worked example

Kochi-ல ஒரு insurer-ஓட engineering team-க்கு ஒரு claims-assistant-ஐ handover பண்றீங்க. அவங்க lead Anjali-க்கு ஒவ்வொரு change-உம் test ஆகணும், அவங்க team-ஓட sign-off இல்லாம production-ல எதுவும் போகக்கூடாது.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q
      - run: uv run python evals/smoke.py --min-accuracy 0.85
  deploy-staging:
    if: github.event_name == 'push'
    needs: test
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/build_push_deploy.sh staging ${{ github.sha }}
  deploy-production:
    needs: deploy-staging
    environment: production        # requires approval from the insurer's leads
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/deploy.sh production ${{ github.sha }}   # same image, no rebuild
```

ஒரு வாரம் கழிச்சு, ஒரு teammate prompt-ஐ மாத்துறாங்க, smoke eval 0.89-ல இருந்து 0.78-க்கு குறையுது; CI fail ஆகுது, PR merge ஆக முடியல. அப்புறம் ஒரு production deploy slow responses-ஐ உண்டாக்குது; பெரும்பாலான users கவனிக்கிறதுக்கு முன்னாடியே, Anjali workflow page-ல இருந்து முந்தைய commit-ஓட image-ஐ ரெண்டு நிமிஷத்துல redeploy பண்றாங்க.

**Insurer-ஓட team-க்கு என்ன மாறுச்சு.** Pipeline-க்கு முன்னாடி, யாருக்காவது ஞாபகம் வரும்போது, ஒரு laptop-ல இருந்து deploys நடந்துச்சு, எந்த version live-ல இருக்குன்னு யாருக்கும் உறுதியா தெரியாது. Pipeline-க்கு அப்புறம், ஒவ்வொரு production version-உம் workflow page-ல தெரியுற ஒரு commit hash, ஒவ்வொரு deploy-க்கும் பேர் வச்ச approver உண்டு, ரெண்டு மாசத்துல smoke eval மூணு prompt changes-ஐ block பண்ணுச்சு; அவை ஒவ்வொண்ணும் answer quality-ஐ குறைச்சிருக்கும். Anjali சொல்றாங்க, வேகம் இல்ல, உறுதி தான் மிக useful: ஒரு claims manager ஒரு மோசமான பதிலை report பண்ணா, எந்த code-உம் prompt-உம் அதை உண்டாக்குச்சுன்னு team-ஆல exact-ஆ சொல்ல முடியும்.

## பொதுவா பண்ற தப்புகள்

- **Tests main-ல மட்டும்.** Merge ஆனதுக்கு அப்புறம் தான் problems தெரியும். Pull requests-ல CI-ஐ run பண்ணுங்க.
- **Prompt changes-க்கு CI-ல eval இல்லாதது.** Prompt edits-உம் code changes தான்; test பண்ணுங்க.
- **Workflow files-ல secrets.** CI system-ஓட secrets அல்லது short-lived cloud credentials use பண்ணுங்க.
- **ஒவ்வொரு environment-க்கும் வேற வேற images build பண்றது.** ஒரு தடவை build பண்ணி, அதே image-ஐ staging வழியா production-க்கு promote பண்ணுங்க.
- **யாரும் try பண்ணாத rollback.** தேவை வர்றதுக்கு முன்னாடியே practice பண்ணுங்க.

- **Flaky tests-ஐ அப்படியே விட்டுவைக்கிறது.** Random-ஆ fail ஆகுற test, pass ஆகுற வரை CI-ஐ மறுபடி run பண்ண மக்களை பழக்கிடும்; அப்புறம் உண்மையான failures-உம் புறக்கணிக்கப்படும். Flaky tests-ஐ சீக்கிரம் fix பண்ணுங்க அல்லது remove பண்ணுங்க.
- **Budget இல்லாம, ஒவ்வொரு PR-லயும் live model-ஐ call பண்ற evals.** PR eval-ஐ சின்னதாவும் மலிவாவும் வச்சுக்கோங்க, முடிஞ்சதை cache பண்ணுங்க, full suite-ஐ ஒரு schedule-ல run பண்ணுங்க.
- **OIDC இருக்கும்போதும், secrets-ஆ store பண்ண நீண்ட நாள் cloud keys.**
- **ஒவ்வொரு push-லயும் paid evals-ஐ run பண்றது**, relevant changes-ல மட்டும் இல்லாம.
- **Pin பண்ணாத third-party actions.**

## Practice பண்ணுங்க

GitHub-ஓட Actions quickstart-ஐயும், deployment environments பத்தின page-ஐயும் follow பண்ணுங்க.

1. உங்க repositories-ல ஒண்ணுல, ஒவ்வொரு pull request-லயும் lint-ஐயும் tests-ஐயும் run பண்ற ஒரு workflow-ஐ சேருங்க.
2. main-க்கு merge ஆகும்போது, commit hash வச்சு tag பண்ண உங்க Docker image-ஐ build பண்ணி push பண்ற ஒரு job-ஐ சேருங்க.
3. Staging, production environments-ஐ create பண்ணி, production-க்கு உங்க சொந்த approval-ஐ require பண்ணி, முந்தைய image-க்கு rollback-ஐ practice பண்ணுங்க.
4. Prompts அல்லது retrieval code மாறும்போது மட்டும் உங்க smoke eval run ஆகுற மாதிரி paths filter-ஐ சேர்த்து, ரெண்டு pull requests open பண்ணி, ஒண்ணுல run ஆகுறதையும் ஒண்ணுல skip ஆகுறதையும் காட்டுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** CI-ஆல block ஆன ஒரு failing PR-ஐயும், production-க்கு முன்னாடி ஒரு approval gate-ஐயும், நீங்களே பண்ண ஒரு rollback-ஐயும் உங்களால காட்ட முடியும்.
