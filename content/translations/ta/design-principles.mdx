## இது என்ன

**Software design**-னா ஒரு program-ஐ parts-ஆ எப்படி பிரிக்கிறது, அந்த parts ஒண்ணுக்கொண்ணு எப்படி பேசிக்கும்னு முடிவு பண்றது. பெரும்பாலான நல்ல designs-க்கு அடியில ரெண்டு ideas இருக்கு:

- **Cohesion**: ஒரு part-க்குள்ள இருக்குறதெல்லாம் எவ்வளவு நெருக்கமா ஒண்ணா சேருதுங்குறது. High cohesion-னா ஒவ்வொரு part-உம் ஒரு வேலை செய்யுது, அதுக்குள்ள இருக்குற எல்லாமே அந்த வேலைக்காகத் தான்.
- **Coupling**: ஒரு part இன்னொண்ணோட details-ஐ எவ்வளவு சார்ந்திருக்குங்குறது. Loose coupling-னா மத்ததை தொடாமலே ஒரு part-ஐ மாத்தலாம்.

நல்ல design-னா high cohesion-உம் loose coupling-உம். ஒரு சின்ன மாற்றம் பரவும்போது bad design-ஐ நீங்க உணரலாம்: email template-ஐ மாத்தணும்னா, எப்படியோ model-ஐ call பண்ற code-ஐயும் edit பண்ண வேண்டியிருக்கு.

பெரும்பாலான software-ஐ விட AI வேலையில இது இன்னும் அதிகமா முக்கியம். ஒரே வருஷத்துல ஒரு team model providers-ஐ மாத்தலாம், privacy-sensitive-ஆன ஒரு customer-க்காக ஒரு self-hosted model சேர்க்கலாம், vector store-ஐயும் மாத்தலாம். Model call இருபது இடங்கள்ல புதைஞ்சிருந்தா, ஒவ்வொரு மாற்றமும் risk-ஆன ஒரு rewrite. ஒரு சின்ன boundary-க்கு பின்னாடி இருந்தா, ஒவ்வொரு மாற்றமும் ஒரு புது file-உம் ஒரு test-உம் தான்.

அங்க போய் சேர்றதுக்கான அஞ்சு பிரபலமான guidelines தான் **SOLID principles**. Robert C. Martin இதை object-oriented code-க்காக தொகுத்தாரு, ஆனா இந்த ideas சாதாரண Python functions-க்கும் modules-க்கும் கூட வேலை செய்யும். இதை மனப்பாடமா ஒப்பிக்க வேண்டியதில்ல. இது தடுக்குற problems-ஐ உண்மையான code-ல கண்டுபிடிக்கத் தெரிஞ்சா போதும்.

## இது எப்படி வேலை செய்யுது

### அஞ்சு principles, சாதாரண வார்த்தைகள்ல

| Principle | சாதாரண வார்த்தைகள்ல | நீங்க இதை மீறுறீங்கன்னு காட்டுற அடையாளம் |
| --- | --- | --- |
| **S**ingle responsibility | ஒரு module அல்லது class, மாறுறதுக்கு ஒரே காரணம் | PDFs படிக்குற, model-ஐ call பண்ற, email அனுப்புற ஒரே file |
| **O**pen-closed | "Open for extension, closed for modification": ஏற்கனவே வேலை செய்யுற code-ஐ edit பண்ணாம, புது code சேர்த்து behaviour சேர்க்கணும் | ஒவ்வொரு புது provider-க்கும் business logic-க்குள்ள இன்னொரு `elif` |
| **L**iskov substitution | ஒரு interface-ஓட எந்த implementation-உம், அந்த interface எதிர்பார்க்கப்படுற எல்லா இடத்துலயும் வேலை செய்யணும் | மத்த clients text return பண்ற இடத்துல ஒரு client `None` return பண்ணுது |
| **I**nterface segregation | ஒரே ஒரு பெரிய interface இல்லாம, நிறைய சின்ன, focused interfaces | ஒவ்வொரு part-உம் ரெண்டு methods தான் use பண்ணாலும், எல்லா part-உம் சார்ந்திருக்குற ஒரு பெரிய `Storage` class |
| **D**ependency inversion | High-level logic ஒரு குறிப்பிட்ட library-ஐ இல்லாம, தனக்கு சொந்தமான ஒரு interface-ஐ சார்ந்திருக்கு | Business logic-க்குள்ள ஆழமா `openai`-ஐ import பண்ணி call பண்றது |

**Open-closed-னா "ஒரு file-ஐயும் edit பண்ணவே கூடாது"-னு அர்த்தம் இல்ல.** அடிக்கடி மாறுற code (எந்த provider, எந்த output format) புது pieces-ஆ சேர்க்கப்படணும், வேலை செய்யுற core அசையாம இருக்கணும்ங்குறது தான் அர்த்தம். எங்கயாவது ஒரு இடம் எந்த piece-ஐ use பண்றதுன்னு இன்னும் தேர்ந்தெடுக்கணும். அந்த choice-ஐ logic முழுக்க பரப்பாம, program-ஓட ஓரத்துல ஒரே இடத்துல வைங்க.

**Liskov promises பத்தினது, class names பத்தினது இல்ல.** ஒரு interface-னா ஒரு promise: "எனக்கு ஒரு prompt string குடுங்க, நான் ஒரு text string return பண்றேன்". அதை உடைக்குற ஒரு client இதோ:

```python
class CheapClient:
    def complete(self, prompt: str) -> str | None:
        try:
            return self._call_api(prompt)
        except TimeoutError:
            return None   # every caller now has to check for None
```

இதுக்கு சரியான method name இருக்கு, அதனால swap பண்ணலாம்னு தோணும். ஆனா மத்த clients-க்காக எழுதின code `reply.splitlines()` பண்ணுது, இந்த client முதல் தடவை time out ஆகும்போதே அது `AttributeError`-ஓட crash ஆகும். ஒரு implementation கம்மியா ஏத்துக்கும்போதும் (மத்தவை ஏத்துக்குற நீளமான prompts-ஐ இது மறுக்குது) அல்லது அதோட பாதி methods-க்கு "not supported" raise பண்ணும்போதும் இதே trap வரும். Promise-ஐ காப்பாத்துங்க: caller ஏற்கனவே handle பண்ற ஒரு error-ஐ raise பண்ணுங்க, அல்லது client-க்குள்ளயே retry பண்ணுங்க.

### Dependency injection

SOLID-ல பெரும்பாலானதுக்கு பின்னாடி இருக்குற practical tool **dependency injection** தான். ஒரு function தனக்கு தேவையானதை தானே create பண்றதுக்கு பதிலா, வெளியில இருந்து வாங்கிக்குது:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

`Protocol` ஒரு shape-ஐ விவரிக்குது. பொருந்துற `complete` method இருக்குற எந்த class-உம், எதுல இருந்தும் inherit பண்ணாமலே fit ஆகும், mypy மாதிரி ஒரு type checker உங்களுக்காக அதை check பண்ணும். இப்போ `summarise`-க்கு அது எந்த provider-ஐ use பண்ணுதுன்னு தெரியாது, அதைப் பத்தி கவலையும் இல்ல. Production ஒரு real client-ஐ pass பண்ணுது, tests ஒரு fake-ஐ pass பண்ணுது, provider மாத்துறதுன்னா `summarise`-ஐ edit பண்றது இல்ல, ஒரு புது class எழுதுறது தான்.

Direction-ஐ கவனிங்க. Interface business logic-க்கு சொந்தமானது: `summarise` தனக்கு என்ன வேணும்னு சொல்லுது. Provider library வெளிப்பக்கம் தள்ளப்படுது. Dependency inversion-ல இருக்குற "inversion" அது தான்.

### Model interface எவ்வளவு thin-ஆ இருக்கணும்?

மேல இருக்குற code-ஐ பார்த்து ஒரு experienced engineer கேக்குற கேள்வி இது தான். உண்மையான provider APIs எல்லாம் ஒரே மாதிரி இல்ல. Messages எடுத்துக்குறது, tools call பண்றது, structured JSON return பண்றது, tokens stream பண்றது, prompts cache பண்றது, இதுலெல்லாம் அவை வித்தியாசப்படுது. ஒரே method இருக்குற `complete(prompt) -> str` interface இது எல்லாத்தையும் மறைச்சிடுது. அதனால நீங்க ஒரு உண்மையான trade-off-ஐ சந்திக்கிறீங்க:

- **ரொம்ப thin**-ஆ இருந்தா, features-ஐ இழப்பீங்க. உங்க product-க்கு tool calling வேணும்னா, ஒரு plain text interface-ஆல அதை சொல்ல முடியாது.
- **ரொம்ப wide**-ஆ இருந்தா, provider details வெளியே கசியும். `messages`, `tools`, `response_format`, `stream` இருக்குற ஒரு interface உண்மையில ஒரு provider-ஓட API-ஐ copy பண்ணது தான், அடுத்த provider அதுல fit ஆகாது.

பெரும்பாலான cases-ஐ மூணு rules handle பண்ணும்:

1. **Interface-ஐ ஒரு chat call-ஐ வெச்சு இல்ல, உங்க product-க்கு என்ன வேணுமோ அதை வெச்சு shape பண்ணுங்க.** உங்க app invoice fields-ஐ extract பண்ணுதுன்னா, interface `extract_invoice(text) -> Invoice`-ஆ இருக்கலாம், இதுல `Invoice` உங்களோட சொந்த typed class. அப்போ ஒவ்வொரு adapter-உம் உள்ளுக்குள்ள structured output-க்கு அதோட provider-ஓட best feature-ஐ use பண்ணும், உங்க core logic-க்கு ஒரு clean, typed result கிடைக்கும்.
2. **Provider-specific features adapter-க்குள்ளயே இருக்கட்டும்.** Prompt caching அல்லது ஒரு special retry header adapter-ஓட விஷயம். உங்க product-க்கு தேவையான ஏதோ ஒண்ணை ஒரு provider உண்மையிலேயே செய்ய முடியலைன்னா, அது ஒரு product decision; "not supported" error-க்கு பின்னாடி மறைக்க வேண்டிய விஷயம் இல்ல.
3. **ஒரு gateway-ஐ யோசிங்க.** LiteLLM மாதிரி libraries-உம், OpenAI-style chat format-ல பேசுற servers-உம் (உதாரணமா vLLM) நிறைய models-ஐ ஒரே மாதிரி தெரிய வைக்குது, அதனால உங்க adapter சின்னதாவே இருக்கும். அப்போ நீங்க gateway-ஐயும், அதோட எல்லா models-உம் share பண்ற features-ஐயும் சார்ந்திருப்பீங்க. *LLM gateways* lesson இதை cover பண்ணுது.

ஒரு summariser-க்கு, `complete(prompt) -> str` தான் சரியான size.

```flow
title: ஒரு AI app-ல ports and adapters
Wiring at start-up | settings-ஐ படிக்குது, adapters-ஐ create பண்ணுது -[ஒரு client-ஐ உள்ள pass பண்ணுது]-> Core logic | prompts, parsing, rules
Core logic -[call பண்ணுது]-> ModelClient port | core-க்கு சொந்தமான interface
ModelClient port -[இதுல implement ஆகுது]-> HostedClient | provider SDK-ஐ wrap பண்ணுது
ModelClient port -[இதுல implement ஆகுது]-> SelfHostedClient | HTTP மூலமா vLLM-ஐ call பண்ணுது
ModelClient port -[இதுல implement ஆகுது]-> FakeClient | tests-ல use ஆகுது
```

### Ports and adapters

இதே idea-ஐ முழு codebase-க்கும் apply பண்ணா, அதுக்கு ஒரு பெயர் இருக்கு: **ports and adapters**, இதை **hexagonal architecture**-னும் சொல்லுவாங்க. Alistair Cockburn இதை விவரிச்சாரு. Interviewers ரெண்டு பெயரையும் use பண்ணுவாங்க.

- **Core logic**-னா product என்ன செய்யுதோ அது: ஒரு ticket-ஐ classify பண்றது, ஒரு prompt-ஐ build பண்றது, ஒரு answer-ஐ score பண்றது. இது வெளியில இருந்து எதையும் import பண்ணாது.
- **Ports**-னா core-க்கு தேவையான சின்ன interfaces: ஒரு model client, ஒரு document store, ஒரு notifier.
- **Adapters** உண்மையான services வெச்சு ports-ஐ implement பண்ணுது: ஒரு provider-ஓட SDK, ஒரு vector database, email அல்லது WhatsApp.
- **Wiring** ஓரத்துல இருக்கு (web app-ஓட start-up, command-line entry point): அது settings-ஐ படிச்சு, real adapters-ஐ create பண்ணி, அவற்றை உள்ள pass பண்ணுது.

உங்க design-க்கு ஒரு quick test: network இல்லாம, API key இல்லாம, database இல்லாம core logic-ஐ ஒரு unit test-ல ஓட்ட முடியுமா? முடியும்னா, boundaries சரியான இடத்துல இருக்கு.

### Inheritance-ஐ விட composition

Retries, logging, cost tracking மாதிரி behaviour சேர்க்கணும்னா, உடனே தோணுற வழி ஒரு subclass: `RetryingOpenAIClient(OpenAIClient)`. அப்புறம் `RetryingSelfHostedClient`, `LoggingRetryingOpenAIClient` எல்லாம் வேணும், ஒவ்வொரு combination-க்கும் classes எண்ணிக்கை வளர்ந்துட்டே போகும். **Composition**-னா அதுக்கு பதிலா wrap பண்றது:

```python
import time

class RetryingClient:
    """Wraps any ModelClient and retries failed calls."""

    def __init__(self, inner: ModelClient, attempts: int = 3):
        self._inner, self._attempts = inner, attempts

    def complete(self, prompt: str) -> str:
        for i in range(self._attempts):
            try:
                return self._inner.complete(prompt)
            except Exception:
                if i == self._attempts - 1:
                    raise
                time.sleep(2 ** i)
```

`RetryingClient` தானே ஒரு `ModelClient`, அதனால எந்த provider கூடவும் வேலை செய்யும், wiring step-ல wrappers-ஐ அடுக்கலாம்: `RetryingClient(HostedClient(...))`. இது தான் செயல்ல open-closed: புது behaviour, இருக்குற clients-ல எந்த edit-உம் இல்ல. (Real code-ல, ஒவ்வொரு `Exception`-க்கும் இல்ல, timeouts-க்கும் rate limits-க்கும் மட்டும் retry பண்ணுங்க; *Errors, retries and cost* lesson-ஐ பாருங்க.)

### Functions-ஆ, classes-ஆ?

எல்லா இடத்துலயும் classes தேவையில்ல. தெளிவான inputs-உம் outputs-உம் இருக்குற சாதாரண functions தான் பல நேரம் எல்லாத்தையும் விட clean-ஆன Python design, ஒரு dependency-ஐ parameter ஆக்குறது மூலமாவே ஒரு function-க்குள்ள inject பண்ணலாம். பல calls share பண்ற state அல்லது settings ஏதாவது ஒண்ணு வெச்சிருக்கும்போது, உதாரணமா API key-உம் timeout-உம் இருக்குற ஒரு client, அல்லது ஒரே interface-க்கு ஒண்ணுக்கு பதிலா இன்னொண்ணு போடக்கூடிய பல implementations வேணும்போது, class-ஐ எடுங்க.

### எப்போ refactor பண்றது

**Refactoring**-னா code என்ன செய்யுதோ அதை மாத்தாம அதோட structure-ஐ மாத்துறது. அந்த code-ஐ நீங்க எப்படியும் மாத்தப் போறீங்க, அந்த மாற்றம் கஷ்டமா இருக்குன்னா அப்போ பண்ணுங்க. முதல்ல மாற்றம் ஈஸியா ஆகுற மாதிரி code-ஐ reshape பண்ணுங்க, அப்புறம் அந்த ஈஸியான மாற்றத்தை பண்ணுங்க. Safe-ஆன வழி:

1. **முதல்ல tests.** எதையும் தொடுறதுக்கு முன்னாடி, இன்னைக்கு இருக்குற behaviour-ஐ, அசிங்கமான behaviour-ஆ இருந்தாலும், pin பண்ற tests எழுதுங்க. நீங்க எதையாவது உடைச்சா அவை சொல்லும்.
2. **சின்ன steps.** ஒரு function-ஐ move பண்ணுங்க, tests ஓட்டுங்க, commit பண்ணுங்க. ஒரு branch-ல ஒரு வாரம் எடுக்குற refactor பொதுவா ஒரு வலியான merge-ல தான் முடியும்.
3. **Structure-ஐயும் behaviour-ஐயும் தனித்தனியா வைங்க.** ஒரு commit ஒண்ணு code-ஐ reshape பண்ணும், இல்லன்னா அது என்ன செய்யுதுன்னு மாத்தும், ஒருபோதும் ரெண்டும் இல்ல; அப்போ ஒரு reviewer ஒவ்வொண்ணையும் check பண்ணலாம்.

வேலை செய்யுற, யாருக்கும் மாத்த தேவையில்லாத code-ஐ refactor பண்ணாதீங்க. ஒரு உண்மையான ரெண்டாவது case (ரெண்டாவது provider, ரெண்டாவது output format) அல்லது fake தேவைப்படுற ஒரு test வர்ற வரைக்கும் interface சேர்க்காதீங்க.

### Low-level design interviews

நிறைய இந்திய product companies ஒரு **low-level design** (LLD) round நடத்துறாங்க. Rate limiter அல்லது parking lot மாதிரி சின்ன ஒண்ணுக்கு classes-உம் interfaces-உம் design பண்ண சொல்லுவாங்க. (ஒரு **system design** round அதுக்கு பதிலா முழு services எப்படி ஒண்ணா சேருதுன்னு கேக்கும்.)

"ஒவ்வொரு user-க்கும் ஒரு நிமிஷத்துக்கு N requests allow பண்ற ஒரு rate limiter design பண்ணுங்க"-ங்குறதுக்கு ஒரு model answer interfaces-ல ஆரம்பிக்கும், அப்புறம் ஒரு simple strategy:

```python
from typing import Protocol

class Clock(Protocol):
    def now(self) -> float: ...

class RateLimiter(Protocol):
    def allow(self, user_id: str) -> bool: ...

class FixedWindow:
    def __init__(self, limit: int, window_s: float, clock: Clock):
        self.limit, self.window_s, self.clock = limit, window_s, clock
        self.counts: dict[str, tuple[int, int]] = {}  # user -> (window number, count)

    def allow(self, user_id: str) -> bool:
        window = int(self.clock.now() // self.window_s)
        seen, n = self.counts.get(user_id, (window, 0))
        n = n if seen == window else 0
        if n >= self.limit:
            return False
        self.counts[user_id] = (window, n + 1)
        return True
```

அப்புறம் trade-offs-ஐ சத்தமா சொல்லுங்க. Clock inject பண்ணப்படுது, அதனால ஒரு test ஒரு நிமிஷம் காத்திருக்காம fake clock வெச்சு நேரத்தை set பண்ணுது. Fixed window-க்கு தெரிஞ்ச ஒரு பலவீனம் இருக்கு: ஒரு user 0:59-ல N requests-உம் 1:00-ல இன்னும் N-உம் பண்ணலாம், ரெண்டு seconds-ல limit-ஓட ரெட்டிப்பு. ஒரு user-ஓட allowance-ஐ நேரம் போக போக சீரா refill பண்ற **token bucket** இதை smooth ஆக்குது, அது அதே `RateLimiter` interface-க்கு பின்னாடி ஒரு ரெண்டாவது class, அதனால `allow()`-ஐ call பண்ற API code மாறவே மாறாது. பல servers-ல, counts Redis மாதிரி ஒரு shared store-க்கு போகும்: இன்னும் ஒரு adapter.

## ஒரு worked example

Delhi-ல ஒரு legal-tech startup-ல இருக்குற Rohit-ஓட team ஒரு வாரத்துல ஒரு contract summariser build பண்ணாங்க. எல்லாமே 300 lines இருக்குற ஒரே file-ல இருந்துச்சு: அது PDF-ஐ படிச்சுது, ஒரு hosted model provider-ஐ நேரடியா call பண்ணுச்சு, Markdown format பண்ணுச்சு, result-ஐ email பண்ணுச்சு.

ரெண்டு மாசம் கழிச்சு, மூணு requests ஒரே நேரத்துல வருது. ஒரு பெரிய client தன்னோட contracts-ஐ தன் சொந்த cloud account-ல ஓடுற ஒரு model process பண்ணணும்னு கேக்குறாங்க. Sales team-க்கு summaries Word documents-ஆ வேணும். அப்புறம் tests ஓட சுமார் நாலு நிமிஷம் ஆகுது, ஏன்னா ஒவ்வொரு test-உம் ஒரு real API call பண்ணுது, காசும் செலவாகுது.

Rohit சின்ன steps-ல refactor பண்றாரு, முதல்ல இன்னைக்கு இருக்குற behaviour-ஐ சுத்தி tests வெச்சு.

**1. மாறுறதுக்கான காரணத்தை வெச்சு பிரிங்க.** அவர் `reader.py` (PDF-ல இருந்து text), `summariser.py` (prompt-உம் parsing-உம்), `formatters.py` (Markdown, இப்போ Word-உம்), `delivery.py` (email), `llm.py` (model clients) create பண்றாரு. ஒவ்வொரு file-க்கும் மாறுறதுக்கு ஒரே காரணம்.

**2. ஒரு port-உம் ரெண்டு adapters-உம்.** `llm.py`-ல:

```python
import httpx
from openai import OpenAI

# ModelClient is the Protocol shown earlier, defined in this file.

class HostedClient:
    """A hosted provider, reached through its own SDK."""
    def __init__(self, api_key: str, model: str):
        self._sdk = OpenAI(api_key=api_key, timeout=30)
        self._model = model

    def complete(self, prompt: str) -> str:
        resp = self._sdk.chat.completions.create(
            model=self._model,
            messages=[{"role": "user", "content": prompt}],
        )
        return resp.choices[0].message.content or ""

class SelfHostedClient:
    """A model served with vLLM inside the customer's own cloud."""
    def __init__(self, base_url: str, model: str):
        self._http = httpx.Client(base_url=base_url, timeout=60)
        self._model = model

    def complete(self, prompt: str) -> str:
        r = self._http.post("/v1/chat/completions", json={
            "model": self._model,
            "messages": [{"role": "user", "content": prompt}],
        })
        r.raise_for_status()
        return r.json()["choices"][0]["message"]["content"] or ""
```

ரெண்டுமே ஒரு string-ஐ return பண்ணுது, ஒருபோதும் `None`-ஐ இல்ல, அதனால ரெண்டுமே ஒரே promise-ஐ காப்பாத்துது. ரெண்டுமே failure-ல error raise பண்ணுது, அதை caller ஏற்கனவே handle பண்ணுது.

**3. Port-ஐ மட்டும் தெரிஞ்ச core logic.** `summariser.py` `ModelClient`-ஐ import பண்ணுது, வெளியில இருந்து வேற எதையும் இல்ல:

```python
from llm import ModelClient

PROMPT = "Summarise this contract in 5 bullet points. Flag any termination clause.\n\n{text}"

def summarise(text: str, client: ModelClient) -> list[str]:
    reply = client.complete(PROMPT.format(text=text))
    return [line.lstrip("-* ").strip() for line in reply.splitlines() if line.strip()]
```

**4. ஓரத்துல wiring.** `main.py` ஒவ்வொரு customer-ஓட settings-ஐ படிச்சு client-ஐ தேர்ந்தெடுக்குது. எந்த providers இருக்குன்னு தெரிஞ்ச, codebase-ஓட ஒரே இடம் இது தான்:

```python
from dataclasses import dataclass

from llm import HostedClient, ModelClient, SelfHostedClient

@dataclass
class Settings:
    model_host: str      # "hosted" or "self_hosted"
    model: str
    api_key: str = ""
    base_url: str = ""

def make_client(s: Settings) -> ModelClient:
    if s.model_host == "self_hosted":
        return SelfHostedClient(s.base_url, s.model)
    return HostedClient(s.api_key, s.model)
```

**5. ஒரு fake வெச்சு வேகமான tests.** `test_summariser.py`-ல:

```python
from summariser import summarise

class FakeClient:
    def __init__(self, reply: str):
        self.reply = reply
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply

def test_summarise_returns_clean_bullets():
    fake = FakeClient("- Term: 2 years\n\n- Notice period: 90 days\n")
    assert summarise("CONTRACT TEXT", fake) == ["Term: 2 years", "Notice period: 90 days"]
    assert "CONTRACT TEXT" in fake.prompts[0]
```

Reply bullets-ஆ clean பண்ணப்படுதா, contract text prompt-க்கு போய் சேர்ந்துச்சான்னு test check பண்ணுது, network-உம் API key-உம் இல்லாமலே. ஒவ்வொரு unit test-உம் fakes use பண்ண ஆரம்பிச்ச அப்புறம், Rohit-ஓட suite நிமிஷங்களுக்கு பதிலா seconds-ல ஓடுது. Real providers-ஐ call பண்ற ரெண்டு மூணு slow tests-ஐ அவர் வெச்சிருக்காரு, அவை ஒவ்வொரு release-க்கும் முன்னாடி ஓடும்; ஒரு fake பிடிக்க முடியாத விஷயங்களை அவை பிடிக்கும்: மாறின response shape, அல்லது தப்பான model name.

Self-hosted client ஒரு புது class, `summarise()` கொஞ்சம் கூட மாறல. Word output ஒரு புது formatter. ஒவ்வொரு request-உம் ஒரு rewrite-க்கு பதிலா சுமார் ஒரு நாள் எடுத்துச்சு.

எங்க நிறுத்தணும்னும் அவருக்குத் தெரியும். PDF reader-க்கு அவர் interface சேர்க்கல, ஏன்னா ஒரே ஒரு reader தான் இருக்கு, இன்னொண்ணுக்கு plan-உம் இல்ல.

## பொதுவான தப்புகள்

- **Logic-க்குள்ள ஆழமா external services-ஐ call பண்றது.** Network இல்லாம code-ஐ test பண்ண முடியாது, provider மாத்தணும்னா ஒவ்வொரு file-லயும் தேடணும்.
- **Promise-ஐ காப்பாத்தாத ஒரு fake.** Real clients ஒரு string return பண்ற இடத்துல fake ஒரு list return பண்ணா, உங்க tests pass ஆகும், production fail ஆகும். Fakes real ஒண்ணோட அதே interface-ஐ follow பண்ணணும்.
- **ஒரு provider-ஓட API-ஐ copy பண்ற interface.** General-ஆ தெரியும், ஆனா அந்த provider-க்கு மட்டும் தான் fit ஆகும். Caller பக்கத்துல இருந்து design பண்ணுங்க: core logic-க்கு உண்மையில என்ன வேணும்?
- **ரொம்ப சீக்கிரமே ரொம்ப அதிகமான abstraction.** 100 lines script-க்கு interfaces, factories, layers எல்லாம் வெச்சா படிக்க கஷ்டமாகும். உண்மையான ரெண்டாவது case-க்கோ ஒரு test-க்கோ தான் abstraction சேருங்க.
- **Behaviour சேர்க்க subclass பண்றது.** Retries, logging, caching-ஐ subclasses-ஆ வெச்சா, ஒவ்வொரு combination-க்கும் ஒரு class-ஆ பெருகிடும். அதுக்கு பதிலா wrap பண்ணுங்க.
- **Tests இல்லாம, அல்லது ஒரே பெரிய step-ல refactor பண்றது.** நீங்க எதை உடைச்சீங்கன்னு சொல்ல முடியாது. Tests வெச்சு behaviour-ஐ pin பண்ணுங்க, அப்புறம் சின்ன commits-ல நகருங்க.
- **Interviews-ல SOLID-ஐ ஒப்பிக்கிறது.** உண்மையான code-ல problem-ஐ கண்டுபிடிச்சு, trade-off-ஐ சொல்லி, அதை fix பண்ண முடியுமான்னு தான் interviewers பாப்பாங்க.
