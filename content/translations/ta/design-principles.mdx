## இது என்ன

**Software design**-னா ஒரு program-ஐ parts-ஆ எப்படி பிரிக்கிறது, அந்த parts தங்களுக்குள்ள எப்படி பேசிக்குதுன்னு முடிவு பண்றது. பெரும்பாலான நல்ல designs-க்கு அடியில ரெண்டு idea இருக்கும்:

- **Cohesion**: ஒவ்வொரு part-உம் ஒரு வேலை தான் செய்யும், உள்ள இருக்குறதெல்லாம் அந்த வேலைக்கு சம்பந்தப்பட்டது.
- **Coupling**: parts ஒண்ணோட details-ஐ இன்னொண்ணு எவ்வளவு சார்ந்திருக்குன்னு. Loose coupling-னா மத்ததை தொடாமலே ஒரு part-ஐ மாத்தலாம்.

நல்ல design-னா high cohesion, loose coupling. மோசமான design-ல email template-ஐ மாத்தணும்னா, model-ஐ call பண்ற code-ஐயும் edit பண்ண வேண்டியிருக்கும்.

**SOLID principles** அங்க போறதுக்கான ஐந்து பிரபலமான guidelines. இவை object-oriented programming-ல இருந்து வந்தது, ஆனா சாதாரண Python functions, modules-க்கும் இந்த ideas பொருந்தும். இதை மனப்பாடம் பண்ணி சொல்ல தேவையில்லை; இது தடுக்குற problems-ஐ அடையாளம் காண தெரிஞ்சா போதும்.

## இது எப்படி work ஆகுது

ஐந்து principles, சாதாரண வார்த்தைகள்ல:

| Principle | சாதாரண வார்த்தைகள்ல | நீங்க இதை உடைக்கிறீங்கன்னு காட்டுற அறிகுறி |
| --- | --- | --- |
| **S**ingle responsibility | ஒரு module அல்லது class-க்கு ஒரே ஒரு மாறுற காரணம் | Data படிச்சு, model call பண்ணி, email அனுப்புற ஒரு file |
| **O**pen for extension | வேலை செய்யுற code-ஐ edit பண்ணாம, புது code சேர்த்து புது behaviour கொண்டு வாங்க | ஒவ்வொரு புது provider-க்கும் நீளமான chain-ல இன்னொரு `elif` |
| **L**iskov substitution | Interface எங்க எதிர்பார்க்கப்படுதோ அங்க அதோட எந்த implementation-உம் வேலை செய்யணும் | பாதி methods-ல "not supported"ன்னு raise பண்ற ஒரு "provider" |
| **I**nterface segregation | சின்ன, focus ஆன interfaces | எல்லா parts-உம் சார்ந்திருக்குற ஒரே பெரிய `Storage` class |
| **D**ependency inversion | ஒரு குறிப்பிட்ட library-யை இல்லாம, interface-ஐ சார்ந்திருங்க | Business logic-க்குள்ள ஆழமா `openai.chat...` call பண்றது |

**Dependency injection** இதுல பெரும்பாலானதுக்கு பின்னாடி இருக்குற practical tool. ஒரு function தனக்கு தேவையானதை தானே உருவாக்குறதுக்கு பதிலா, அதை வெளியில இருந்து வாங்கிக்கும்:

```python
from typing import Protocol

class ModelClient(Protocol):
    def complete(self, prompt: str) -> str: ...

def summarise(text: str, client: ModelClient) -> str:
    return client.complete(f"Summarise in 3 bullet points:\n{text}")
```

இப்போ `summarise`-க்கு எந்த provider use ஆகுதுன்னு கவலை இல்லை. Production-ல real client-ஐ pass பண்றோம்; tests-ல fake-ஐ pass பண்றோம்; provider மாத்தணும்னா `summarise`-ஐ edit பண்ணாம, ஒரு புது class எழுதினா போதும்.

```flow
title: Business logic ஒரு சின்ன interface-ஐ சார்ந்திருக்கு, provider-ஐ இல்ல
summarise() -> ModelClient interface | complete(prompt) -> str
ModelClient interface -> Provider A client
ModelClient interface -> Provider B client
ModelClient interface -> Tests-க்கான fake client
```

ஒரு AI application-ஐ organise பண்ற பொதுவான வழி இதே idea-வை முழு codebase-லயும் use பண்றது:

- **Core logic** (product என்ன செய்யுது: ticket-ஐ classify பண்றது, prompt build பண்றது, answer-ஐ score பண்றது) வெளியில எதையும் சார்ந்திருக்காது.
- **Adapters** (model client, vector store, database, email) சின்ன interfaces-ஐ implement பண்ணும்.
- **Wiring** edge-ல (API startup, CLI) real adapters-ஐ உருவாக்கி உள்ள pass பண்ணும்.

**Functions-ஆ classes-ஆ?** எல்லா இடத்துலயும் classes தேவையில்லை. தெளிவான inputs, outputs இருக்குற சாதாரண functions தான் Python-ல பல நேரம் சுத்தமான design. பல functions share பண்ற state அல்லது settings ஏதாவது இருந்தா (API key, timeout இருக்குற ஒரு client மாதிரி), அல்லது ஒரே interface-க்கு பல மாத்திக்கக்கூடிய implementations வேணும்னா classes-ஐ use பண்ணுங்க.

**Interview-ல.** Low-level design rounds-ல ஒரு rate limiter அல்லது parking lot மாதிரி சின்ன விஷயத்துக்கு classes, interfaces-ஐ design பண்ண சொல்வாங்க. System design rounds-ல services எப்படி ஒண்ணா சேருதுன்னு கேப்பாங்க. ரெண்டுலயும் அதே idea தான்: parts-க்கு பேர் வைங்க, ஒவ்வொண்ணுக்கும் ஒரு வேலை கொடுங்க, மத்ததை தொடாமலே ஒண்ணை எப்படி மாத்துவீங்க, test பண்ணுவீங்கன்னு காட்டுங்க.

## ஒரு worked example

Delhi-ல ஒரு legal-tech startup-ல இருக்குற Rohit-ஓட team ஒரு வாரத்துல ஒரு contract summariser build பண்ணுச்சு. எல்லாமே 300 வரி இருக்குற ஒரே file-ல இருந்துச்சு: PDF-ஐ படிக்கும், ஒரு model provider-ஐ நேரடியா call பண்ணும், Markdown-ஆ format பண்ணும், result-ஐ email பண்ணும்.

ரெண்டு மாசம் கழிச்சு, மூணு requests ஒரே நேரத்துல வருது: ஒரு client தங்க சொந்த cloud-ல host பண்ண model-ல தங்க data-வை process பண்ணணும்னு கேக்குறாங்க, sales team summaries-ஐ Word documents-ஆ கேக்குறாங்க, ஒவ்வொரு test-உம் real API calls பண்றதால tests ஓட நிமிஷக்கணக்கா ஆகுது.

Rohit படிப்படியா refactor பண்றாரு, முதல்ல இப்போ இருக்குற behaviour-க்கு tests எழுதிட்டு:

1. **Single responsibility.** File-ஐ `reader.py` (PDF-ல இருந்து text), `summariser.py` (prompt, parsing), `formatters.py` (Markdown, இப்போ Word-உம்), `delivery.py` (email)-ன்னு பிரிக்கிறாரு.
2. **Model-க்கு ஒரு interface.** `summariser.py` இப்போ ஒரு `ModelClient`-ஐ வாங்கிக்குது. `ProviderAClient`, `SelfHostedClient` ரெண்டையும் எழுதுறாரு, ஒவ்வொண்ணும் `complete()` இருக்குற சின்ன class.
3. **Edge-ல injection.** API startup customer-ஓட settings-ஐ படிச்சு, சரியான client-ஐயும் formatter-ஐயும் pass பண்ணுது.
4. **Fast tests.** Unit tests ஒரு fixed summary திருப்பி தர்ற `FakeClient`-ஐ pass பண்ணுது. Test suite நாலு நிமிஷத்துல இருந்து மூணு வினாடிக்கு வருது.

Self-hosted client தன்னோட tests-ஓட ஒரு புது class; `summarise()` கொஞ்சம் கூட மாறல. Word output ஒரு புது formatter; வேற எதுவும் மாறல. ஒவ்வொரு request-உம் rewrite இல்லாம, ஒரு நாள்ல முடிஞ்சுது.

அவரு இன்னும் அதிகமா போகாம நிறுத்திக்கிறாரு: PDF reader-க்கு interface சேர்க்கல, ஏன்னா reader ஒண்ணே ஒண்ணு தான், இன்னொண்ணு வர்ற plan-உம் இல்லை. நிஜமா ரெண்டாவது case இருக்கும்போது அல்லது testing தேவைப்படும்போது தான் abstraction சேர்க்கணும்.

## பொதுவா பண்ற தப்புகள்

- **Logic-க்குள்ள ஆழமா external services-ஐ call பண்றது.** Network இல்லாம code-ஐ test பண்ணவே முடியாது, provider மாத்தவும் கஷ்டம்.
- **ரொம்ப சீக்கிரமே ரொம்ப abstraction.** 100 வரி script-க்கு interfaces, factories, layers போட்டா படிக்க ஈஸியாகாது, கஷ்டமாகும்.
- **பெரிய "utils" அல்லது "manager" modules.** Module-ஓட பேரே அது என்ன செய்யுதுன்னு சொல்லலைன்னா, அது பல வேலை செய்யுது போல.
- **ஒரு implementation-க்காக interface-ஐ மாத்துறது.** அப்புறம் மத்த எல்லா implementations-உம் callers-உம் மாறணும்.
- **SOLID-ஐ மனப்பாடம் பண்ண rules-ஆ பார்க்கிறது.** Interviewers பார்க்குறது, real code-ல problem-ஐ கண்டுபிடிச்சு fix பண்ண முடியுமான்னு தான்.

## Practice பண்ணுங்க

1. API-ஐ நேரடியா call பண்ற ஏதாவது ஒரு script-ஐ எடுத்து, client-ஐ உள்ள தானே உருவாக்காம pass பண்ற மாதிரி மாத்துங்க. Fake வச்சு ஒரு test எழுதுங்க.
2. உங்க பெரிய file-க்கு மாறுறதுக்கான காரணங்களை list பண்ணுங்க. ரெண்டுக்கு மேல இருந்தா, எப்படி பிரிப்பீங்கன்னு sketch பண்ணுங்க.
3. நீங்க உருவாக்குன interface-க்கு பின்னாடி ரெண்டாவது implementation-ஐ, அதை use பண்ற code-ஐ edit பண்ணாம சேருங்க.
4. Model provider-ஐ swap பண்ற மாதிரி ஒரு AI app-ஐ எப்படி structure பண்ணுவீங்கன்னு ரெண்டு நிமிஷத்துல explain பண்ணி பழகுங்க.
