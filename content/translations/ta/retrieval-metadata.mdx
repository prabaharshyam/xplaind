## இது என்ன

**Metadata**-னா ஒரு chunk-ஓட text இல்லாம, அதை பத்தின தகவல். RAG-ல இது அஞ்சு வேலை பண்ணுது:

- **Filters**: product, region, document type, language அல்லது date வச்சு searches-ஐ restrict பண்ணுது.
- **Citations**: ஒரு பதில் எங்க இருந்து வந்ததுன்னு சரியா சொல்லுது (document, section, page, link).
- **Freshness**: current versions-ஐ prefer பண்ணுது அல்லது கட்டாயமாக்குது, superseded ஆனதை drop பண்ணுது.
- **Permissions**: யார் ஒரு chunk-ஐ பார்க்கலாம்னு முடிவு பண்ணுது.
- **Better matching**: document title, section path மாதிரி chunk text-ல இல்லாத context-ஐ சேர்க்குது.

```flow
Chunk text | "இந்த limit 45 நாள்." தனியா கண்டுபிடிக்க கஷ்டம் -> Metadata-ஓட store ஆனது | doc: Leave Policy 2026 (v4), section: Earned leave > Carry forward, page 4, state KA, access: all-employees
Metadata-ஓட store ஆனது -> Embed ஆன text | "Leave Policy 2026 > Earned leave > Carry forward: இந்த limit 45 நாள்."
Metadata-ஓட store ஆனது -> Query filter | user-ஓட state, superseded இல்லாதது, user-ஓட groups-ல இருக்குற access
```

இந்த lesson-ல Bengaluru-ல ஒரு IT company-ல அஞ்சு states-ல இருக்குற employees-க்கு service பண்ற HR assistant-ஐ follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Ingestion-ல collect பண்ணுங்க.** ஒவ்வொரு chunk-க்கும் குறைஞ்சது இதை store பண்ணுங்க:

- document id, title, source system, link;
- section path ("Leave Policy > Earned leave > Carry forward"), page;
- document type (policy, circular, FAQ, contract);
- dates: published, effective from, effective to, last modified;
- language;
- owner அல்லது department;
- access groups.

**Contextual text.** "இந்த limit 45 நாள்"ன்னு சொல்ற chunk-ஐ retrieve பண்றது கஷ்டம். Embed ஆகுற text-ஓட முன்னாடி title, section path-ஐ சேர்க்கலாம் ("Leave Policy v4 > Earned leave > Carry forward: இந்த limit 45 நாள்"). அல்லது ஒரு model-ஐ வச்சு ஒவ்வொரு chunk-க்கும் ஒரு வரி context எழுத வைக்கலாம். இந்த மாதிரி contextual enrichment retrieval failures-ஐ கவனிக்கத்தக்க அளவுக்கு குறைக்கும்.

**Generated metadata.** ஒரு model ஒரு சின்ன summary, keywords அல்லது அந்த chunk பதில் சொல்ற questions-ஐ சேர்க்கலாம். Users documents-ல இருக்குறதை விட ரொம்ப வேற மாதிரி சொல்லும்போது, likely questions-ஐ embed பண்றது உதவும். Ingestion-ல ஒரு chunk-க்கு ஒரு model call செலவாகும். அதனால முதல்ல உங்க golden set-ல gain-ஐ அளந்து பாருங்க.

**Query-ல இருந்து filters.** சில filters user-ஓட context-ல இருந்து வரும் (அவங்க region, access groups). மத்தவற்றை ஒரு சின்ன model வச்சு கேள்வியில இருந்து infer பண்ணலாம் ("2026-ல இருந்து Karnataka-க்கு leave rules" என்பது region = KA, effective after 2026-01-01 ஆகும்). Conservative-ஆ infer பண்ணுங்க: தப்பான filter சரியான பதிலை மறைச்சுடும்.

**Freshness rules.** Effective dates, ஒரு "superseded by" link-ஐ store பண்ணுங்க. User history பத்தி கேக்கலைன்னா, default-ஆ superseded documents-ஐ filter பண்ணிடுங்க.

**Consistency.** Filters match ஆகணும்னா fixed vocabularies use பண்ணுங்க (department names, document types, region codes). மத்த data மாதிரி metadata-வையும் ingestion-ல validate பண்ணுங்க.

**ஒரு chunk record நடைமுறையில:**

| Field | Example | எதுக்கு use ஆகுது |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations, links |
| `section_path`, `page` | Earned leave, Carry forward; page 4 | துல்லியமான citations, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | User-ஓட profile-ல இருந்து filters |
| `effective_from`, `effective_to` | 2026-01-01, open | Freshness |
| `superseded_by` | none | பழைய versions-ஐ drop பண்றது |
| `language` | `en` | Filters, analysers தேர்ந்தெடுக்கறது |
| `access_groups` | `all-employees` | Permissions |

**Metadata-வை validate பண்றது.** மத்த data மாதிரியே metadata-வையும் நடத்துங்க. Ingestion-ல required fields இருக்கான்னு, values fixed lists-ல இருந்து வருதான்னு, effective dates அர்த்தமுள்ளதான்னு (end date, start date-க்கு அப்புறம் இருக்கணும்) check பண்ணுங்க. Fail ஆகுற chunks-ஐ reject பண்ணுங்க அல்லது quarantine பண்ணுங்க, ஒவ்வொரு run-லயும் counts-ஐ report பண்ணுங்க. "KA"-க்கு பதிலா "Karnatka"ன்னு tag ஆன ஒரே ஒரு document, ஒவ்வொரு Karnataka employee-ஓட search-லயும் சத்தமே இல்லாம காணாம போயிடும்.

**Metadata-வை code-ல validate பண்ணுங்க.** எதையும் index பண்றதுக்கு முன்னாடி check ஆகுற fixed vocabularies, date rules:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, field_validator, model_validator

State = Literal["KA", "TN", "MH", "DL", "ALL"]
DocType = Literal["policy", "circular", "faq", "contract"]

class ChunkMeta(BaseModel):
    doc_id: str
    title: str
    section_path: str
    page: int
    doc_type: DocType
    state: State
    language: Literal["en", "hi", "ta", "kn", "mr"]
    effective_from: date
    effective_to: date | None = None
    superseded_by: str | None = None
    access_groups: list[str]

    @field_validator("access_groups")
    @classmethod
    def not_empty(cls, v):
        if not v:
            raise ValueError("every chunk needs at least one access group")
        return v

    @model_validator(mode="after")
    def dates_in_order(self):
        if self.effective_to and self.effective_to < self.effective_from:
            raise ValueError("effective_to is before effective_from")
        return self
```

ஒவ்வொரு chunk-ஐயும் `ChunkMeta.model_validate` வழியா ஓட்டுங்க. Pass ஆனதை index பண்ணுங்க. Fail ஆனதை error-ஓட ஒரு quarantine table-ல எழுதுங்க. இப்போ "Karnatka" காணாம போறதுக்கு பதிலா சத்தமா fail ஆகும்.

**கேள்வியில இருந்து filters-ஐ பாதுகாப்பா infer பண்ணுங்க.** ஒரு சின்ன model-கிட்ட filters-ஐ confidence-ஓட structured output-ஆ கேளுங்க. கேள்வியில clear-ஆ சொல்லியிருந்தா மட்டும் apply பண்ணுங்க:

```python
class Filters(BaseModel):
    state: State | None = None
    year_from: int | None = None
    doc_type: DocType | None = None
    explicit: bool        # true only if the user named these in the question

def apply_filters(f: Filters, user_state):
    filters = {"state": [user_state, "ALL"], "current": True}    # from the profile, always safe
    if f.explicit:
        if f.state:
            filters["state"] = [f.state, "ALL"]
        if f.year_from:
            filters["effective_from_gte"] = date(f.year_from, 1, 1)
        if f.doc_type:
            filters["doc_type"] = f.doc_type
    return filters
```

Filtered search எதுவும் திருப்பி தரலைன்னா, inferred filters இல்லாம ஒரு தடவை retry பண்ணுங்க. Logs-ல அதை note பண்ணுங்க.

**ஒரு document-ஐ supersede பண்றது.** புது version வரும்போது, அதே transaction-ல பழையதை mark பண்ணுங்க:

```sql
BEGIN;
UPDATE chunks SET superseded_by = 'HR-LP-2026', effective_to = '2025-12-31' WHERE doc_id = 'HR-LP-2025';
INSERT INTO chunks (...) VALUES (...);   -- the new version's chunks
COMMIT;
```

Default searches `superseded_by IS NULL`-ஐ filter பண்ணும். History கேள்விகள் ("2024-ல rule என்ன?") அந்த filter-ஐ எடுத்துட்டு dates-ஐ use பண்ணும்.

**Payoff-ஐ check பண்ணுங்க.** உங்க golden set-ல ஒவ்வொரு metadata பகுதி இருக்கும்போதும் இல்லாதப்போதும் (contextual text, generated questions, inferred filters) recall at 5-ஐ அளந்து, உதவுறதை மட்டும் வச்சுக்கோங்க.

## ஒரு நாள், ஒரு example

Bengaluru-ல ஒரு IT company-ஓட HR assistant அஞ்சு states-ல இருக்குற employees-க்கு service பண்ணுது. Leave, holiday rules state-க்கு state வேறுபடும், policies ஒவ்வொரு வருஷமும் திருத்தப்படுது.

முன்னாடி: chunks-ல file name மட்டும் தான் இருந்துச்சு. Assistant Karnataka, Maharashtra holiday lists-ஐ கலந்துடுச்சு, சில நேரம் போன வருஷ policy-ஐ quote பண்ணுச்சு.

Re-ingestion-க்கு அப்புறம், ஒவ்வொரு chunk-லயும் state, policy type, effective dates, version, section path, access groups இருக்கு. Employee-ஓட state அவங்க sign-on profile-ல இருந்து வருது. அவங்க வேற state பத்தி கேட்டாதான் தவிர, அதை filter-ஆ apply பண்றோம். Superseded versions default-ஆ விலக்கப்படுது. Embed ஆகுற text title, section path-ஓட ஆரம்பிக்குது.

100 கேள்விகள் golden set-ல, சரியான பதில்கள் 71%-ல இருந்து 90%-க்கு உயர்ந்துச்சு. இப்போ citations "Leave Policy 2026, Karnataka, section 3.2, page 4"ன்னு படிக்குது. HR staff அதை சில நொடிகள்ல check பண்ணிடலாம்.

| 100 கேள்விகள்ல அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| சரியான பதில்கள் | 71% | 90% |
| தப்பான state-ஐ quote பண்ண பதில்கள் | 9 | 0 |
| போன வருஷ policy-ஐ quote பண்ண பதில்கள் | 7 | 1 |
| Citation format | File name மட்டும் | Document, state, section, page |

**Filter முடிவு எப்படி work ஆகுது.** Bengaluru-ல இருக்குற ஒரு employee "அக்டோபர்ல எத்தனை holidays?"ன்னு கேட்டா, assistant sign-on profile-ல இருந்து `state = KA`-ஐ apply பண்ணும். "அக்டோபர்ல Pune office holidays"ன்னு கேட்டா, ஒரு சின்ன model வேற state-ஐ கண்டுபிடிக்கும். Filter பண்றதுக்கு முன்னாடி assistant "Maharashtra holiday list-ஐ சொல்றீங்களா?"ன்னு கேக்கும். கேக்குறதுக்கு ஒரு tap தான் செலவு. சத்தமில்லாம தப்பான filter போட்டா தப்பான பதில் தான் கிடைக்கும்.

## பொதுவா பண்ற தப்புகள்

- **File name மட்டும் வச்சிருக்கறது.** Filter பண்ணவோ, சரியா cite பண்ணவோ, versions-ஐ handle பண்ணவோ முடியாது.
- **Free-text metadata values.** "HR", "Human Resources", "hr dept" filters-ஐ உடைக்கும். Fixed lists use பண்ணுங்க.
- **Effective dates இல்லாம இருக்கறது.** பழைய versions தொடர்ந்து ஜெயிக்கும்.
- **ரொம்ப aggressive-ஆன inferred filters.** தப்பா infer ஆன filter சரியான பதிலை மறைச்சுடும். User context-ஐ prefer பண்ணுங்க, தெரியலைன்னா கேளுங்க.
- **அளக்காம metadata generate பண்றது.** Ingestion-ல பணம் செலவாகும். அது உதவுதுன்னு நிரூபிங்க.
- **Free-text metadata values.** Fixed lists use பண்ணி validate பண்ணுங்க.
- **Fallback இல்லாம inferred filters apply பண்றது.** Results காலியா இருந்தா அவை இல்லாம retry பண்ணுங்க.

## குறைவான metadata போதுமான நேரங்கள்

- ஒவ்வொரு document-க்கும் ஒரே version இருக்குற **சின்ன, ஒரே topic collection**.
- **எல்லாரும் எல்லாத்தையும் பார்க்கலாம்**, எதுவும் காலாவதியாகாது.
- Retrieval உதவுதான்னே test பண்ற **prototype**.

நிறைய document types, versions, regions அல்லது permission groups வந்ததுக்கு அப்புறம் தான் rich metadata பலன் தரும்.

## Demo-ல இருந்து production-க்கு

- Ingestion-ல **ஒவ்வொரு chunk-ஓட metadata-வையும் validate பண்ணுங்க**, ஒவ்வொரு run-லயும் quarantine counts-ஐ report பண்ணுங்க.
- **Transactions-ல supersede பண்ணுங்க**, default-ஆ superseded documents-ஐ filter பண்ணுங்க.
- ஒவ்வொரு search-க்கும் **apply ஆன filters-ஐ log பண்ணுங்க**, infer ஆனதையும் சேர்த்து.
- Content owners-ஓட சேர்ந்து **vocabularies-ஐ review பண்ணுங்க** (states, document types, departments).
- ஒவ்வொரு metadata feature-ஓட **value-வையும் golden set-ல அளந்து பாருங்க**.

## Practice பண்ணுங்க

Metadata extraction பத்தின LlamaIndex-ஓட page-ஐயும், Microsoft-ஓட security filter pattern-ஐயும் படிங்க.

1. உங்க RAG documents-ஐ ஒவ்வொரு chunk-லயும் title, section path, type, dates, language-ஓட re-ingest பண்ணுங்க.
2. Embed ஆகுற text-ஓட முன்னாடி title, section path-ஐ சேர்த்து, அதுக்கு முன்னாடியும் பின்னாடியும் recall at 5-ஐ compare பண்ணுங்க.
3. ஒரு document-ஓட பழைய version-ல "superseded" flag சேர்த்து, filtering அதை பதில்கள்ல இருந்து நீக்குதுன்னு காட்டுங்க.
4. வேணும்னே bad metadata இருக்குற அஞ்சு chunks-ஐ ChunkMeta வழியா ஓட்டி, ஒவ்வொண்ணும் தெளிவான error-ஓட quarantine-ல போய் சேருதுன்னு confirm பண்ணுங்க.
