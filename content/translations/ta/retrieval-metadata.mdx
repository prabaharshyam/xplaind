## இது என்ன

**Metadata**-னா ஒரு chunk-ஓட text இல்லாம, அந்த chunk பத்தின தகவல். RAG-ல அது அஞ்சு வேலைகள் செய்யுது:

- **Filters**: ஒரு search-ஐ state, document type, language அல்லது date வெச்சு சுருக்குது.
- **Citations**: ஒரு answer சரியா எங்க இருந்து வந்துச்சுன்னு சொல்லுது (document, section, page, link).
- **Freshness**: போன வருஷத்தோட version இல்லாம, in force-ஆ இருக்குற version-ல இருந்து answer பண்ணுது.
- **Permissions**: ஒரு chunk-ஐ யார் பாக்கலாம்னு முடிவு பண்ணுது.
- **Better matching**: document title அல்லது section path மாதிரி, chunk text-ல இல்லாத context-ஐ சேர்க்குது.

```flow
Chunk text | "This limit is 45 days." Hard to find on its own -> Stored with metadata | doc: Leave Policy 2026, section: Earned leave > Carry forward, page 4, state KA, access: all-employees
Stored with metadata -> Embedded text | "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days."
Stored with metadata -> Query filter | user's groups, user's state, in force today
Stored with metadata -> Citation | Leave Policy 2026, Karnataka, section 3.2, page 4
```

பிரச்சனை என்னன்னா, metadata சத்தமில்லாம fail ஆகும். ஒரு தப்பான date அல்லது தப்பா spell பண்ண ஒரு state, கேள்வி கேக்குற நேரத்துல எந்த error-ஐயும் காட்டாது; சரியான chunk திரும்ப வரவே வராது, model தப்பான chunk-ல இருந்து confident-ஆ answer சொல்லும்.

இந்த lesson, அஞ்சு states-க்கு serve பண்ற ஒரு Bengaluru IT company-ஓட HR assistant-ஐ follow பண்ணுது. Exercise இதே ideas-ஐ government orders-க்கு கொண்டு போகுது, அங்க versions-உம் amendments-உம் இன்னும் கஷ்டம்.

## இது எப்படி work ஆகுது

### Ingestion-லயே collect பண்ணுங்க

ஒவ்வொரு chunk-க்கும் குறைஞ்சது இதையெல்லாம் store பண்ணுங்க:

| Field | Example | எதுக்கு use ஆகுது |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations, links |
| `doc_group` | `LP` (எல்லா versions-உம் translations-உம்) | Versions-ஐயும் language copies-ஐயும் link பண்ண |
| `section_id`, `section_path`, `page` | 3.2; Earned leave, Carry forward; page 4 | Precise citations, amendments, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | User-ஓட profile-ல இருந்து filters |
| `issued_on` | 2025-12-10 | "The 2019 order" மாதிரி கேள்விகள் |
| `effective_from`, `effective_to` | 2026-01-01, காலி | Freshness, history கேள்விகள் |
| `superseded_by` | காலி | Answers-ல "replaced by" notes |
| `language` | `en` | Filters, எந்த copy-ஐ காட்டணும்னு தேர்ந்தெடுக்க |
| `access_groups` | `all-employees` | Permissions |

இப்பவே collect பண்ணுங்க; அப்புறம் சேர்க்கணும்னா ஒவ்வொரு file-ஐயும் திரும்ப parse பண்ணணும்.

**PDFs-ல இருந்து இதை எடுக்கிறது.** சில fields source system-ல இருந்து வரும் (link, owner, access groups). மத்ததை document-லயே படிக்கணும்: headers-ல இருக்குற order numbers, issue dates, section numbers. Clean-ஆன digital PDFs-க்கு rules ("No."-க்கும் dates-க்கும் regular expressions) work ஆகும்; scanned files-க்கு OCR-உம் ஒரு model-உம் வேணும், ரெண்டுமே தப்பு பண்ணும். Extract பண்ண fields-ஐ நம்புறதுக்கு முன்னாடி, சுமார் 50 documents இருக்குற ஒரு sample-ஐ கையால check பண்ணி, ஒவ்வொரு field-க்கும் errors-ஐ எண்ணுங்க. Dates-ஐ கவனமா பாருங்க: "03/12/2019" இந்தியால 3 December, ஆனா US defaults இருக்குற ஒரு parser-க்கு அது 12 March, அதனால format-ஐ வெளிப்படையா சொல்லுங்க.

### Contextual text

"This limit is 45 days"-னு சொல்ற ஒரு chunk-ஐ retrieve பண்றது கஷ்டம், ஏன்னா அது *எந்த* limit-னு அதுல எதுவுமே இல்லை. நீங்க embed பண்ற text-க்கு முன்னால title-ஐயும் section path-ஐயும் சேருங்க: "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days". இதுக்கு செலவே இல்லை.

இன்னும் strong-ஆன version: ஒவ்வொரு chunk-உம் அதோட document-ல எங்க வருதுன்னு ஒன்னு ரெண்டு வாக்கியங்கள்ல எழுத ஒரு model-கிட்ட கேளுங்க. Anthropic இந்த "contextual retrieval"-ஐ அதோட சொந்த datasets-ல test பண்ணி, அது top-20 retrieval failure rate-ஐ 35% குறைச்சதாவும், keyword (BM25) search-லயும் apply பண்ணும்போது 49%, reranking-உம் சேர்த்தா 67% குறைச்சதாவும் report பண்ணுச்சு. ஒவ்வொரு chunk-க்கும் ஒரு model call செலவாகும், அதனால உங்க சொந்த golden set-ல measure பண்ணுங்க.

### Generated metadata

ஒரு model ஒரு சின்ன summary, keywords, அல்லது ஒரு chunk பதில் சொல்ற questions-ஐயும் எழுதலாம். Users documents-ல இருந்து ரொம்ப வித்தியாசமா கேக்கும்போது generated questions உதவும் ("can I carry over my leave?" vs "Carry forward of earned leave").

ஒவ்வொரு generated question-ஐயும் **parent chunk-ஓட id கூட, அதுக்குன்னு ஒரு தனி vector-ஆ** store பண்ணுங்க. ஒரு question vector match ஆனா, parent chunk-ஐ return பண்ணுங்க, question text-ஐ ஒருபோதும் இல்லை, ஏன்னா model உண்மையான document-ல இருந்து தான் answer பண்ணணும். ரெண்டு gotchas: generated questions chunk சொல்றதை விட அதிகமா promise பண்ணலாம், அதனால ஒரு sample-ஐ spot-check பண்ணுங்க; அதோட அவை பழசாயிடும், அதனால chunk text-ஓட ஒரு hash-ஐ store பண்ணி, அது மாறும்போது திரும்ப generate பண்ணுங்க.

### Fixed vocabularies, code-ல validate பண்ணது

Filters exact values-ஐ compare பண்ணும். ஒரு filter-க்கு "HR", "Human Resources", "hr dept" மூணும் மூணு வேற வேற departments. Departments, document types, states, languages-க்கு fixed lists use பண்ணுங்க, ஒவ்வொரு chunk-ஐயும் index ஆகுறதுக்கு முன்னாடி check பண்ணுங்க:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, field_validator, model_validator

State = Literal["KA", "TN", "MH", "TS", "GJ", "ALL"]   # the client's five states, plus ALL
DocType = Literal["policy", "circular", "faq", "contract"]

class ChunkMeta(BaseModel):
    doc_id: str
    doc_group: str               # same for every version and translation
    title: str
    section_id: str              # stable id such as "3.2"
    section_path: str
    page: int
    doc_type: DocType
    state: State
    language: Literal["en", "hi", "ta", "kn", "mr", "te", "gu"]
    issued_on: date
    effective_from: date
    effective_to: date | None = None
    superseded_by: str | None = None
    access_groups: list[str]

    @field_validator("access_groups")
    @classmethod
    def not_empty(cls, v):
        if not v:
            raise ValueError("every chunk needs at least one access group")
        return v

    @model_validator(mode="after")
    def dates_in_order(self):
        if self.effective_to and self.effective_to < self.effective_from:
            raise ValueError("effective_to is before effective_from")
        return self
```

ஒவ்வொரு chunk-ஐயும் `ChunkMeta.model_validate` வழியா அனுப்புங்க, pass ஆனதை index பண்ணுங்க, fail ஆனதை error கூட ஒரு quarantine table-ல எழுதுங்க. ஒவ்வொரு run-லயும் quarantine counts-ஐ report பண்ணுங்க. "Karnatka"-னு tag பண்ண ஒரு document இப்போ சத்தமா fail ஆகும்; ஒவ்வொரு Karnataka employee-ஓட search-ல இருந்தும் காணாம போகாது. State list client-ஓட உண்மையான list-ஓட சரியா match ஆகணும்; சேர்க்க மறந்த ஒரு state-ஓட எல்லா documents-உம் quarantine-க்கு போயிடும்.

### Freshness: ஒரே ஒரு "in force" rule

ஒரு simple "current" flag use பண்ணாதீங்க. எல்லா இடத்துலயும் ஒரே date rule use பண்ணுங்க: ஒரு chunk **ஒரு period-ல in force**-னா, `effective_from` அந்த period-ஓட முடிவு நாள் அன்னைக்கோ அதுக்கு முன்னாடியோ இருக்கணும், `effective_to` காலியா இருக்கணும் அல்லது period-ஓட தொடக்க நாள் அன்னைக்கோ அதுக்கு அப்புறமோ இருக்கணும்.

- **Default கேள்விகள்** ("how many leave days can I carry forward?"): period இன்னைக்கு, Asia/Kolkata time-ல.
- **"What was the rule in 2024?"**: period 1 January-ல இருந்து 31 December 2024 வரை. 2023-ல இருந்து 2025 வரை in force-ஆ இருந்த ஒரு policy திரும்ப வரும், அது 2024-க்கு முன்னாடியே ஆரம்பிச்சு, இப்போ superseded ஆகியிருந்தாலும் கூட.
- **"What did the 2019 order say?"**: இது 2019-ல *issue* ஆன order பத்தி கேக்குது, அதனால `issued_on`-ஓட year வெச்சு filter பண்ணுங்க, அது இன்னும் in force-ஆ இருக்கா இல்லையான்னு பாக்காதீங்க.

ஒரு gotcha: December-ல 1 January-க்குன்னு announce பண்ண ஒரு policy இன்னும் in force இல்லை. "Next year's policy" பத்தின ஒரு கேள்விக்கு அடுத்த வருஷம் தான் period-ஆ இருக்கணும், இல்லைன்னா default rule அதை மறைச்சுடும்.

ஒரு புது version முழு document-ஐயும் replace பண்ணும்போது, பழசை அதே transaction-ல close பண்ணுங்க, அப்போ எந்த search-உம் ரெண்டையும் பாக்காது, ரெண்டுமே இல்லாமலும் இருக்காது:

```sql
BEGIN;
UPDATE chunks SET superseded_by = 'HR-LP-2026', effective_to = '2025-12-31'
WHERE doc_id = 'HR-LP-2025';
INSERT INTO chunks (...) VALUES (...);   -- the new version's chunks
COMMIT;
```

Filtering-ஐ date rule தான் செய்யுது. Answer "replaced by Leave Policy 2026"-னு சொல்றதுக்காக தான் `superseded_by` வெச்சிருக்கோம்.

### Partial amendments

உண்மையான documents பெரும்பாலும் ஒரு நேரத்துல ஒரு பகுதியா தான் மாறும். ஒரு government order "in paragraph 4 of order 112/2019, for 'Rs 300' substitute 'Rs 450'"-னு சொல்லி, மத்த எல்லா paragraphs-ஐயும் in force-ஆவே விடலாம். முழு document-க்கான ஒரு "superseded" flag-ஆல இதை சொல்ல முடியாது. பழைய order-ஐ superseded-னு mark பண்ணா அதோட மத்த paragraphs காணாம போயிடும்; அப்படியே விட்டா பழைய rate தான் ஜெயிச்சுக்கிட்டே இருக்கும்.

Amendments-ஐ section level-ல model பண்ணுங்க:

- ஒவ்வொரு chunk-லயும் ஒரு stable `section_id` இருக்கணும் (paragraph 4, clause 3.2).
- ஒரு amendments table `amending_doc`, `amended_doc`, `section_id`, அது effect-க்கு வர்ற date-ஐ record பண்ணும்.
- ஒரு amendment effect-க்கு வரும்போது, amend ஆன section-ஓட `effective_to`-ஐ மட்டும் முடிங்க, மத்ததை அப்படியே விடுங்க.
- Query time-ல, ஒரு base section retrieve ஆகும்போது, அதுக்கான எல்லா amendments-ஐயும் date வரிசையில எடுத்து, ரெண்டையும் model-க்கு குடுங்க.

இது முக்கியம், ஏன்னா எந்த chunk-உம் தனியா work ஆகாது. Amendment "substitute 'Rs 450'"-னு சொல்லும், எதுக்கு பதிலான்னு சொல்லாது; base paragraph பழசாயிடுச்சு. Answer ரெண்டையும் cite பண்ணணும்: "order 112/2019, paragraph 4, as amended by order 37/2022". Department consolidated versions publish பண்ணா, அதையும் index பண்ணுங்க, ஆனா citations-க்காக chain-ஐ வெச்சுக்கோங்க.

Amendment links-உம் extract பண்ற metadata தான். "in partial modification of" அல்லது "in supersession of" மாதிரி phrases, அதைத் தொடர்ந்து ஒரு order number வந்தா, அது நல்ல starting rules; ஆனா extract பண்ற எந்த field மாதிரியும் ஒரு sample-ல check பண்ணுங்க.

### Translations

ஒரு Hindi order-உம் அதோட English copy-யும் ரெண்டு documents இல்லை, ரெண்டு languages-ல இருக்குற ஒரே document. ரெண்டுக்கும் ஒரே `doc_group`, `section_id` குடுங்க. Results-ல ஒரு document group, section-க்கு ஒரு chunk மட்டும் வெச்சுக்கோங்க, user-ஓட language-ல இருக்குற copy-ஐ காட்டுங்க. இல்லைன்னா top five results-ல ரெண்டு இடம், அதே paragraph ரெண்டு தடவை வந்து வீணாகும். ரெண்டும் வேறுபடும்போது எந்த copy authoritative-னு department-கிட்ட கேளுங்க, அதை record பண்ணி, அதையே cite பண்ணுங்க.

### Permissions, sync-ல வெச்சுக்கிறது

Chunks மேல user ids இல்லாம **group ids** store பண்ணுங்க (`finance`, `all-employees`), filter-ஐ search-க்கு உள்ளயே apply பண்ணுங்க, அப்போ அனுமதி இல்லாத chunk model-ஐ ஒருபோதும் reach பண்ணாது. ரெண்டு syncs-க்கு தனித்தனி schedules வேணும்:

- **Document permissions** source system-ல மாறும் (ஒரு file-ஐ திரும்ப share பண்றாங்க). அதை அடிக்கடி re-sync பண்ணுங்க, ஒரு metadata update-ஆ; text-ஐ re-embed பண்ண வேண்டாம்.
- **User groups** ஆளுங்க teams மாறும்போது மாறும். User-ஓட groups-ஐ query time-ல identity system-ல இருந்து படிங்க, அல்லது நாட்கள் இல்லாம நிமிஷங்களுக்கு மட்டும் cache பண்ணுங்க. Cache பண்ண ஒரு group list-ஆல தான், Finance-ஐ விட்டு போன ஒருத்தர் இன்னும் Finance circulars-ஐ பாத்துக்கிட்டு இருக்காரு.

### கேள்வியில இருந்து filters

சில filters user-ஓட profile-ல இருந்து வரும் (அவங்க state, அவங்க groups). மத்ததை ஒரு small model கேள்வியில இருந்து infer பண்ணும். தப்பா infer பண்ண filter சரியான answer-ஐ மறைச்சுடும், அதனால அவற்றை கவனமா apply பண்ணுங்க:

```python
STATE_NAMES = {"KA": "Karnataka", "TN": "Tamil Nadu", "MH": "Maharashtra",
               "TS": "Telangana", "GJ": "Gujarat"}

class Filters(BaseModel):            # structured output from a small model
    state: Literal["KA", "TN", "MH", "TS", "GJ"] | None = None  # a real state, never ALL
    state_named: bool = False         # true only if the question names the state itself
    in_force_year: int | None = None  # "what was the rule in 2024?"
    issued_year: int | None = None    # "the 2019 order on transfers"
    doc_type: DocType | None = None

def in_force(start: date, end: date) -> dict:
    """In force at any time from start to end."""
    return {"effective_from": {"$lte": end},
            "$or": [{"effective_to": None}, {"effective_to": {"$gte": start}}]}

def build_filters(f: Filters, user, today: date):
    if f.state and f.state != user.state and not f.state_named:
        return None, f"Do you mean the {STATE_NAMES[f.state]} documents?"
    where = {"access_groups": {"$in": user.groups},           # never dropped
             "state": {"$in": [f.state or user.state, "ALL"]}}
    if f.in_force_year:
        y = f.in_force_year
        where |= in_force(date(y, 1, 1), date(y, 12, 31))
    elif f.issued_year:
        y = f.issued_year
        where["issued_on"] = {"$gte": date(y, 1, 1), "$lte": date(y, 12, 31)}
    else:
        where |= in_force(today, today)                       # default
    if f.doc_type:
        where["doc_type"] = f.doc_type
    return where, None
```

Filter syntax generic தான்; அதை உங்க vector store-ஓட syntax-க்கு மாத்திக்கோங்க. `today`-ஐ server-ஓட UTC date இல்லாம, Asia/Kolkata-ல இருக்குற date-ஆ pass பண்ணுங்க. ஒரு filtered search எதுவுமே return பண்ணலைன்னா, access filter, user-ஓட state மட்டும் வெச்சு ஒரு தடவை retry பண்ணுங்க, அது cite பண்றதோட dates-ஐ காட்டுங்க, empty search-ஐ log பண்ணுங்க. ஒரு retry-ல access filter-ஐ ஒருபோதும் drop பண்ணாதீங்க.

### Filters-உம் search speed-உம்

Filters approximate vector indexes கூட interact பண்ணும். உதாரணமா pgvector-ல, default-ஆ filter index scan-க்கு *அப்புறம்* தான் apply ஆகும். அதோட documentation 10% rows-ஐ match பண்ற ஒரு filter-ஐ example-ஆ குடுக்குது: ஒரு HNSW index-உம் default `hnsw.ef_search` 40-உம் இருந்தா, average-ஆ சுமார் 4 rows தான் மிஞ்சும், அதனால நீங்க கேட்டதை விட குறைவான results தான் கிடைக்கும். Version 0.8.0-ல இருந்து iterative index scans-ஐ on பண்ணலாம் (`SET hnsw.iterative_scan = relaxed_order`); அது போதுமான rows pass ஆகுற வரை அல்லது ஒரு scan limit (`hnsw.max_scan_tuples`) வர்ற வரை index-ஓட இன்னும் அதிகமான பகுதியை scan பண்ணும். கொஞ்சமே distinct values இருக்குற ஒரு field-க்கு, ஒவ்வொரு value-க்கும் ஒரு partial index-ஐ pgvector suggest பண்ணுது. மத்த stores வேற மாதிரி இருக்கும், அதனால உங்ககிட்ட இருக்குறதுலயே அதிக selective-ஆன filter-ஐ (ஒரு சின்ன state, ஒரு அரிதான document type) test பண்ணி, அது இன்னும் முழு top-k-ஐ return பண்ணுதான்னு check பண்ணுங்க.

### Payoff-ஐ check பண்ணுங்க

ஒவ்வொரு addition-க்கும் (contextual text, generated questions, inferred filters), அது இருந்தும் இல்லாமலும் உங்க golden set-ல recall at 5-ஐ measure பண்ணுங்க, உதவுறதை மட்டும் வெச்சுக்கோங்க. History கேள்விகளையும் வேற state கேள்விகளையும் சேருங்க, ஏன்னா அங்க தான் filters தப்பா போகும்.

## ஒரு worked example

Bengaluru IT company-ஓட HR assistant Karnataka, Tamil Nadu, Maharashtra, Telangana, Gujarat-ல இருக்குற employees-க்கு serve பண்ணுது. Leave, holiday rules state-க்கு state மாறும், policies ஒவ்வொரு வருஷமும் revise ஆகும்.

**முன்னாடி:** chunks-ல file name மட்டும் தான் இருந்துச்சு. Assistant Karnataka, Maharashtra holiday lists-ஐ கலந்துச்சு, சில நேரம் போன வருஷ policy-ஐ quote பண்ணுச்சு. முதல் fix ஒரு `current = true` filter-ஐ சேர்த்துச்சு, அப்புறம் "what was the carry-forward limit in 2024?" எதையுமே return பண்ணலை.

**Re-ingestion-க்கு அப்புறம்:** ஒவ்வொரு chunk-லயும் மேல இருக்குற table-ல உள்ள fields இருக்கு. State-உம் groups-உம் employee-ஓட sign-on profile-ல இருந்து வருது. Date rule default-ஆ இன்னைக்கு; ஒரு வருஷத்தை பேர் சொல்லி கேட்டா அந்த வருஷத்துக்கு மாறும். Embed பண்ற text title, section path-ல இருந்து ஆரம்பிக்குது. கீழ இருக்குற numbers எதிர்பார்க்கக்கூடிய மாதிரியான மாற்றத்துக்கு ஒரு illustration தான், measure பண்ண result இல்லை:

| 100 golden questions-ல, இப்படின்னு வெச்சுக்கோங்க | முன்னாடி | அப்புறம் |
| --- | --- | --- |
| சரியான answers | 71 | 90 |
| தப்பான state-ஐ quote பண்ண answers | 9 | 0 |
| போன வருஷ policy-ஐ quote பண்ண answers | 7 | 1 |
| மத்த தப்பான answers | 13 | 9 |

இப்போ citations "Leave Policy 2026, Karnataka, section 3.2, page 4"-னு வருது, HR staff அவற்றை சில நொடிகள்ல check பண்ணலாம்.

**Filter முடிவுகள் எப்படி work ஆகுது.** Bengaluru-ல இருக்குற Priya "how many holidays in October?"-னு கேக்குறாங்க. Assistant அவங்க profile-ல இருந்து `state = KA`-ஐயும், இன்னைக்கு in force-ஐயும் apply பண்ணுது. அப்புறம் அவங்க "holidays in Pune office in October"-னு கேக்குறாங்க. Small model Pune-ஐ Maharashtra-வுக்கு map பண்ணுது, ஆனா அவங்க state-ஐ பேர் சொல்லலை, அதனால `build_filters` ஒரு கேள்வியை return பண்ணுது: "Do you mean the Maharashtra documents?" கேக்குறதுக்கு ஒரு tap தான் செலவு; சத்தமில்லாத ஒரு தப்பான filter-க்கு ஒரு தப்பான answer தான் விலை. அவங்க "Maharashtra holidays"-னு type பண்ணியிருந்தா, filter நேரடியா apply ஆகியிருக்கும்.

அவங்க "what was the carry-forward limit in 2024?"-னு கேக்கும்போது, model `in_force_year = 2024`-ஐ return பண்ணுது. January 2026-ல இருந்து superseded ஆன 2023-ல இருந்து 2025 வரையான policy, date rule-ஓட match ஆகி, "replaced by Leave Policy 2026"-ங்குற note கூட திரும்ப வருது.

## பொதுவா பண்ற தப்புகள்

- **File name மட்டும்.** Filter பண்ண முடியாது, சரியா cite பண்ண முடியாது, versions-ஐ handle பண்ண முடியாது.
- **Free-text metadata values.** "HR", "Human Resources", "hr dept" filters-ஐ உடைக்கும். Fixed lists use பண்ணி அவற்றை validate பண்ணுங்க.
- **ஒரு உண்மையான value-ஐ விட்டுப்போன vocabulary.** மறந்துபோன ஒரு state அதோட எல்லா documents-ஐயும் quarantine பண்ணும், இல்லைன்னா அதை விட மோசமா, state இல்லாமலே index பண்ணும்.
- **ஒவ்வொரு search-லயும் ஒரு "current only" filter.** அப்போ history கேள்விகள் எதையுமே return பண்ணாது. கேள்வி கேக்குற period கூட in-force rule-ஐ use பண்ணுங்க.
- **Partial amendments-க்கு முழு document supersession.** அது இன்னும் in force-ஆ இருக்குற paragraphs-ஐ மறைக்கும், இல்லைன்னா பழைய values-ஐ வெச்சுக்கும். Amendments-ஐ section வாரியா track பண்ணுங்க.
- **Translations-ஐ தனி documents-ஆ வெக்கிறது.** Duplicate paragraphs மத்த results-ஐ வெளியே தள்ளும்.
- **Aggressive-ஆன inferred filters.** User-ஓட profile-க்கு முன்னுரிமை குடுங்க, inferred filter அதை மாத்தினா கேளுங்க.
- **Access filter-ஐ drop பண்ற ஒரு fallback.** ஒரு empty result, ஒரு user பாக்கக்கூடியதை ஒருபோதும் விரிவாக்கக் கூடாது.
- **பழைய group lists.** Query time-ல இருக்குற user-ஓட groups தான் access-ஐ முடிவு பண்ணும், அதனால அவற்றை fresh-ஆ படிங்க.
- **Measure பண்ணாம metadata generate பண்றது.** ஒவ்வொரு chunk-க்கும் ஒரு model call செலவாகும்; அது உதவுதுன்னு prove பண்ணுங்க.

## கொஞ்சம் metadata போதும்னு இருக்குற இடங்கள்

- ஒவ்வொரு document-க்கும் ஒரே version இருக்குற **ஒரு சின்ன, ஒரே topic collection**.
- **எல்லாரும் எல்லாத்தையும் பாக்கலாம்**, எதுவும் பழசாகாது.
- Retrieval உதவுதான்னே test பண்ற **ஒரு prototype**.

அப்போ கூட document id, section, page-ஐ store பண்ணுங்க: citations-க்கு அவை தேவை, அதுக்கு செலவே இல்லை. நிறைய document types, versions, regions அல்லது permission groups வந்த உடனே rich metadata-க்கு பலன் கிடைக்கும்.

## Demo-ல இருந்து production-க்கு

- Parser அல்லது document format மாறும்போதெல்லாம் **extract பண்ண fields-ஐ ஒரு sample-ல கையால check பண்ணுங்க**.
- ஒவ்வொரு search-க்கும் **apply ஆன filters-ஐ log பண்ணுங்க**, inferred filters, fallbacks உட்பட.
- Re-embedding-ல இருந்து தனியா, அதோட சொந்த schedule-ல **permissions-ஐ re-sync பண்ணுங்க**.
- Content owners கூட சேர்ந்து **vocabularies-ஐ review பண்ணுங்க** (states, document types, departments).

## Practice பண்ணுங்க

Metadata extraction பத்தின LlamaIndex-ஓட page-ஐயும் Microsoft-ஓட security filter pattern-ஐயும் படிங்க.

1. உங்க RAG documents-ஐ, ஒவ்வொரு chunk-லயும் title, section id, path, type, dates, language, access groups கூட re-ingest பண்ணுங்க.
2. Embed பண்ற text-க்கு முன்னால title, section path-ஐ சேர்த்து, முன்னாடியும் அப்புறமும் recall at 5-ஐ compare பண்ணுங்க.
3. ஒரு document-க்கு போன வருஷம் முடிஞ்ச ஒரு பழைய version குடுங்க. Default கேள்விக்கு புது version-உம், போன வருஷத்தை பேர் சொல்லி கேக்குற கேள்விக்கு பழைய version-உம் கிடைக்குதுன்னு காட்டுங்க.
4. ஒரு document-ஓட ஒரு section-ஐ இன்னொரு document amend பண்ற மாதிரி வெச்சுக்கோங்க. Answer ரெண்டையும் cite பண்ணுதுன்னு காட்டுங்க.
5. வேணும்னே தப்பான metadata இருக்குற அஞ்சு chunks-ஐ `ChunkMeta` வழியா அனுப்பி, ஒவ்வொண்ணும் தெளிவான error கூட quarantine-ல போய் சேருதுன்னு confirm பண்ணுங்க.
