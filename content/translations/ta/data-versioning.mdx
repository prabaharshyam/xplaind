## இது என்ன

**Data versioning**, Git code-ஐ track பண்ற மாதிரியே, datasets-ஓட versions-ஐயும் (அவற்றை உருவாக்குற steps-ஐயும்) track பண்ணும். ஒவ்வொரு training run-உம் எந்த data version-ஐ use பண்ணுச்சுன்னு record பண்ணும். அதனால நீங்க:

- எந்த பழைய model-ஐயும் அப்படியே reproduce பண்ணலாம்;
- ரெண்டு dataset versions-க்கு நடுவுல என்ன மாறுச்சுன்னு பார்க்கலாம்;
- புது dataset உடைஞ்சிருந்தா, முந்தைய dataset-க்கு roll back பண்ணலாம்;
- ஒரு decision-க்கு பின்னாடி இருக்குற data-வை auditors-க்கு காட்டலாம்.

பெரிய files-ஐ நேரடியா Git-ல போடக்கூடாது. DVC மாதிரி tools data-வை cloud storage-ல வச்சு, சின்ன pointer files-ஐ Git-ல வைக்கும். Data lakes, warehouses-உம் table versioning ("time travel") கொடுக்கும்.

```flow
Sources-ல இருந்து raw data -> Dataset build பண்றது
Pipeline code | Git commit a1b2c3 -> Dataset build பண்றது
Dataset build பண்றது -> Data v2026-10-01 | manifest: rows, hash, query, commit
Data v2026-10-01 -> Training run 412 | data, code versions-ஐ log பண்ணும்
Training run 412 -> Model registry: fraud-model v7 -> Production predictions
```

Lineage எதிர் திசையில போகும்: எந்த prediction-உம் → model v7 → run 412 → data v2026-10-01 → commit a1b2c3.

இந்த lesson-ல Chennai-ல ஒரு health-insurance company-யோட fraud model, retrain பண்ணப்புறம் மோசமாச்சு. அதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Inputs-ஐ snapshot பண்ணுங்க.** Training datasets-ஐ ஒரு id இருக்குற immutable snapshots-ஆ நடத்துங்க: content hash, தேதி போட்ட path, அல்லது tool-managed version. ஒரு dataset-ஐ அதே இடத்துல ஒருபோதும் overwrite பண்ணாதீங்க.

**Pipeline-ஐயும் version பண்ணுங்க.** Raw data-வை training data-வா மாத்துற code (filters, joins, labels, feature computation) Git-ல version ஆகும். ஒரு data version என்பது, ஒரு குறிப்பிட்ட raw data மேல, ஒரு குறிப்பிட்ட pipeline version run ஆனதோட output.

**Lineage-ஐ record பண்ணுங்க.** ஒவ்வொரு training run-உம் data version id-ஐ log பண்ணும்; registry-ல இருக்குற ஒவ்வொரு model-உம் அதோட run-ஓட link ஆகும். ஒரு production prediction-ல இருந்து, exact data-வுக்கு பின்னாடி நடந்து போகலாம்.

**Versions-ஐ compare பண்ணுங்க.** Versions-க்கு நடுவுல row counts, label balance, feature distributions, schema மாற்றங்கள், sample diffs. பெரிய மாற்றங்களை code மாற்றங்களை review பண்ற மாதிரியே review பண்ணுங்க.

**Labels-உம் மாறும்.** Correct பண்ண labels, புது labelling guidelines, தாமதமா வர்ற outcomes datasets-ஐ மாத்தும். அவற்றை version பண்ணி, ஏன்னு note பண்ணுங்க.

**Privacy, deletion.** Versioned data-விலயும் personal data இருக்கு. DPDP Act-ஓட கீழ retention rules, erasure requests பழைய versions-க்கும் பொருந்தும். Deletion எப்படி propagate ஆகும்னு plan பண்ணுங்க, உதாரணமா பாதிக்கப்பட்ட versions-ஐ நீக்கின records இல்லாம rebuild பண்ணி, அதை document பண்றது.

**Practical-ஆ வச்சுக்கோங்க.** சின்ன teams-க்கு, cloud storage-ல தேதி போட்ட folders, ஒரு manifest-ஓட (row counts, hash, source query, pipeline commit), ஒவ்வொரு run-லயும் path-ஐ log பண்றது போதுமா இருக்கலாம். Volume-உம் team size-உம் வளர வளர ஒரு tool-ஐ எடுத்துக்கோங்க.

**ஒவ்வொரு dataset version-க்கும் ஒரு manifest:**

| Field | Example |
| --- | --- |
| Version id | `claims-train-2026-10-01` |
| Content hash | `sha256:9f2c...` |
| Rows | 812,440 |
| Positive label share | 2.3% |
| Source query or tables | `claims_v3 joined with investigations` |
| Pipeline commit | `a1b2c3d` |
| Created by and date | `pipeline-bot, 2026-10-01` |
| Notes | "Relabelled 1,200 claims after the audit of July" |

Dataset build ஆகும்போதே manifest-ஐ automatic-ஆ எழுதுங்க, data பக்கத்துலயே store பண்ணுங்க. அந்த build-ஐ trigger பண்ண pull request-ல முந்தைய manifest-ஓட ஒரு comparison-ஐ print பண்ணுங்க. "positive label share: 2.3% to 1.1%"ன்னு பார்க்குற reviewer, training ஆரம்பிக்கிறதுக்கு முன்னாடியே சரியான கேள்வியை கேப்பாங்க.

**ஒரு tool-ஐ தேர்ந்தெடுக்கிறது.** ரெண்டு மூணு பேர் இருக்குற team-க்கு, தேதி போட்ட folders-உம் ஒரு manifest-உம் போதும். DVC, Git-ல pointer files-ஐயும், data-வை pull, push பண்ற commands-ஐயும் சேர்க்கும். பல பேர் models train பண்ண ஆரம்பிச்சப்புறம் இது உதவும். Delta Lake, Apache Iceberg மாதிரி lakehouse table formats "time travel"-ஐ சேர்க்கும். அதனால ஒரு table-ஐ ஒரு குறிப்பிட்ட தேதியில எப்படி இருந்துச்சோ அப்படி query பண்ணலாம். Training data ஏற்கனவே warehouse-ல இருக்குற teams-க்கு இது பொருந்தும். எதை தேர்ந்தெடுத்தாலும் rule ஒண்ணே: ஒரு training run எந்த data version-ஐ use பண்ணுச்சுன்னு exact-ஆ record பண்ணணும், அந்த version அதுக்கு அப்புறம் ஒருபோதும் மாறக்கூடாது.

**Manifest-ஐ automatic-ஆ எழுதுங்க.** Dataset build-ஓட கடைசியில சில lines:

```python
import hashlib, json, subprocess
from datetime import datetime
from zoneinfo import ZoneInfo
from pathlib import Path

def file_hash(path, chunk=1 << 20):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while block := f.read(chunk):
            h.update(block)
    return "sha256:" + h.hexdigest()

def write_manifest(data_path, df, label_col, notes=""):
    commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"], capture_output=True, text=True).stdout.strip()
    manifest = {
        "version": Path(data_path).stem,
        "hash": file_hash(data_path),
        "rows": int(len(df)),
        "positive_share": round(float(df[label_col].mean()), 4),
        "columns": list(df.columns),
        "pipeline_commit": commit,
        "created": datetime.now(ZoneInfo("Asia/Kolkata")).isoformat(timespec="seconds"),
        "notes": notes,
    }
    Path(data_path).with_suffix(".manifest.json").write_text(json.dumps(manifest, indent=2))
    return manifest
```

**முந்தைய version-ஓட compare பண்ணுங்க, எதிர்பாராதது நடந்தா fail பண்ணுங்க.**

```python
def compare(old, new, max_share_change=0.3, max_row_change=0.2):
    problems = []
    if set(old["columns"]) != set(new["columns"]):
        problems.append(f"columns changed: {set(old['columns']) ^ set(new['columns'])}")
    if abs(new["rows"] - old["rows"]) / old["rows"] > max_row_change:
        problems.append(f"rows {old['rows']} -> {new['rows']}")
    rel = abs(new["positive_share"] - old["positive_share"]) / max(old["positive_share"], 1e-9)
    if rel > max_share_change:
        problems.append(f"positive share {old['positive_share']:.2%} -> {new['positive_share']:.2%}")
    return problems
```

Data-வை build பண்ண pull request-ல இந்த comparison-ஐ print பண்ணுங்க. ஒரு failure எப்பவும் தப்பு இல்லை, ஆனா training-க்கு முன்னாடி யாராவது அதை notes-ல விளக்கணும்.

**நாலு commands-ல DVC.** Data cloud storage-ல இருக்கும்; Git சின்ன pointer files-ஐ track பண்ணும்:

```bash
dvc init
dvc remote add -d store s3://my-bucket/dvc       # or Azure, GCS, a shared drive
dvc add data/claims-train-2026-10-01.parquet     # writes a .dvc pointer file
git add data/*.dvc .gitignore && git commit -m "Training data 2026-10-01" && dvc push
```

அப்புறம் யாரும் ஒரு commit-ஐ `git checkout` பண்ணி, `dvc pull` பண்ணா, exact அந்த data கிடைக்கும்.

**Lakehouse-ல time travel.** Training data Delta Lake tables-ல இருந்தா, ஒவ்வொரு run-உடனும் table version-ஐ record பண்ணி, அதை அப்படியே திரும்ப படிங்க:

```sql
SELECT * FROM claims_train VERSION AS OF 42;
SELECT * FROM claims_train TIMESTAMP AS OF '2026-10-01T00:00:00+05:30';
```

Retention period முடிஞ்சதும் cleanup jobs பழைய versions-ஐ நீக்கும். அதனால models-ஐ reproduce பண்ண உங்களுக்கு தேவையானதை விட அந்த period-ஐ நீளமா வச்சிருங்க, அல்லது முக்கியமான snapshots-ஐ export பண்ணுங்க.

**Versions முழுக்க erasure.** ஒருத்தர் erasure கேட்டா, அவங்க records இருக்குற எல்லா dataset versions-ஐயும் கண்டுபிடிங்க (ஒவ்வொரு version-க்கும் record ids-ஓட ஒரு index வச்சிருங்க). அவங்க இல்லாம அந்த versions-ஐ rebuild பண்ணி, ஒவ்வொரு manifest-லயும் note பண்ணுங்க. பழைய versions-ல train ஆன models-ஐ retrain பண்ணணுமான்னு privacy lead-ஓட சேர்ந்து முடிவு பண்ணுங்க.

## ஒரு worked example

Chennai-ல ஒரு health-insurance company, அதோட claim-fraud model-ஐ retrain பண்ணுது. Recall 0.72-ல இருந்து 0.61-க்கு விழுந்திருக்கு.

DVC-ல data version ஆகியிருக்குறதால, team புது dataset-ஐ முந்தைய dataset-ஓட compare பண்ணுது:

- Positive labels 14% குறைவு, ஆனா fraud cases குறையல;
- label query மாறியிருந்துச்சு: pipeline refactor-ல இப்போ investigation-ல இருக்குற claims விலக்கப்பட்டிருக்கு. சமீபத்திய fraud-ல பெரிய பங்கு அவை தான்.

Pipeline-ஐ fix பண்ணி, dataset-ஐ ஒரு புது version-ஆ rebuild பண்ணி, retrain பண்ணி, 0.73 recall-ஐ திரும்ப பெற்றாங்க. அந்த refactor-ஓட original pull request-ல ஒரு data check சேர்க்கப்பட்டிருக்கு: versions-க்கு நடுவுல positive label share 20%-க்கு மேல ஒரு விளக்கம் இல்லாம மாறினா அது fail ஆகும்.

அப்புறம், ஒரு customer-ஓட erasure request அவங்க records-ஐ delete பண்ணணும்னு சொல்லுது. Team பாதிக்கப்பட்ட training versions-ஐ அவங்க இல்லாம rebuild பண்ணி, மாற்றத்தை record பண்ணி, rebuild ஆன model-ஓட metrics மாறலைன்னு உறுதி பண்ணுது.

**Team வச்சுக்கிட்டது என்ன.** Fix-க்கு ஒரு நாள் தான் ஆச்சு, ஏன்னா evidence ஏற்கனவே இருந்துச்சு: பக்கத்து பக்கத்துல இருந்த ரெண்டு manifests label share மாற்றத்தை காட்டுச்சு, ஒவ்வொரு manifest-லயும் இருந்த pipeline commit நேரா அந்த refactor-ஐ காட்டுச்சு. Versioning இல்லாம, இதே investigation-க்கு பெரும்பாலும் வாரக்கணக்குல guess பண்ணணும், அல்லது நடக்கவே நடக்காது, பலவீனமான model சத்தமில்லாம ship ஆகிடும்.

## பொதுவா பண்ற தப்புகள்

- **Datasets-ஐ அதே இடத்துல overwrite பண்றது.** Compare பண்ணவும் reproduce பண்ணவும் உங்களுக்கு இருந்த திறனை இழப்பீங்க. ஒரு row fix-க்கு கூட எப்பவும் புது id-ஓட புது version-ஐ எழுதுங்க.
- **Data-வை version பண்ணி, pipeline-ஐ பண்ணாம இருக்கிறது.** Data எப்படி உருவாச்சுன்னு விளக்க முடியாது.
- **Model-ல இருந்து data-வுக்கு link இல்லாம இருக்கிறது.** ஒவ்வொரு run-லயும் data version-ஐ log பண்ணுங்க.
- **Label மாற்றங்களை கண்டுக்காம விடுறது.** Feature மாற்றங்கள் மாதிரியே அவையும் models-ஐ மாத்தும்.
- **பழைய versions-ல privacy-ஐ மறக்கிறது.** Retention, erasure ஒவ்வொரு copy-க்கும் பொருந்தும்.
- **கையால எழுதுற manifests**, அவை நிஜ data-வை விட்டு விலகிப் போகும்.
- **Versions-க்கு நடுவுல label share அல்லது row counts-ஐ check பண்ணாம இருக்கிறது.**
- **Erasure requests-ல பழைய versions-ஐ மறக்கிறது.**

## Versioning simple-ஆவே இருக்கலாம்னா

- **Training data இல்லாத, prompt மட்டும் இருக்குற AI apps**: பதிலா prompts, test sets, indexes-ஐ version பண்ணுங்க.
- **ஒரு ஆள், ஒரு சின்ன dataset**: ஒரு manifest-ஓட தேதி போட்ட folder போதும்.
- **ஒருபோதும் மாறாத data**, ஒரு fixed public benchmark மாதிரி: அதோட பெயரையும் hash-ஐயும் ஒரு தடவை record பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **Dataset versions-ஐ immutable-ஆ ஆக்குங்க**, ஒவ்வொரு training run-உடனும் version-ஐ log பண்ணுங்க.
- **CI-ல manifests-ஐ automatic-ஆ எழுதி compare பண்ணுங்க.**
- **Model registry-ல models-ஐ data versions-ஓட link பண்ணுங்க.**
- **ஒவ்வொரு version-க்கும் record ids-ஐ index பண்ணுங்க**, அப்போ erasure requests-ஐ நிறைவேத்தலாம்.
- **பழைய versions-க்கு retention-ஐ**, உங்க reproducibility தேவைகளை விட நீளமா set பண்ணுங்க.

## Practice பண்ணுங்க

DVC-ஓட get-started guide-ஐயும், Made With ML-ஓட data versioning lesson-ஐயும் follow பண்ணுங்க.

1. ஒரு dataset-ஐ DVC-ஓட version control-ல வைங்க (அல்லது manifest-ஓட, தேதி போட்ட, hash பண்ண folders), அதை ஒரு training run-ஓட link பண்ணுங்க.
2. Data-வை மாத்துங்க (rows சேர்ங்க, labels-ஐ fix பண்ணுங்க), ஒரு புது version-ஐ உருவாக்குங்க, versions-க்கு நடுவுல ஒரு comparison report எழுதுங்க.
3. Label share ஒரு threshold-ஐ தாண்டி மாறினா fail ஆகுற ஒரு data check-ஐ சேருங்க.
4. உங்க dataset-ஓட ரெண்டு versions-ஐ build பண்ணுங்க, ஒண்ணுல ஒரு slice-ஐ relabel பண்ணி. Label-share மாற்றத்துல compare function fail ஆகணும்.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு பழைய model-ஐ அதோட record பண்ண code, data versions-ல இருந்து reproduce பண்ண முடியும், ரெண்டு dataset versions-க்கு நடுவுல இருக்குற வித்தியாசத்தை explain பண்ண முடியும்.
