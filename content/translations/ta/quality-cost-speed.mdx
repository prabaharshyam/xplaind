## இது என்ன

ஒவ்வொரு LLM app-உம் மூணு விஷயங்களை ஒண்ணுக்கொண்ணு trade பண்ணுது:

- **Quality**: answers எவ்ளோ தடவை சரியா, முழுசா, பாதுகாப்பா இருக்கு.
- **Cost**: ஒரு request-க்கும் ஒரு மாசத்துக்கும் ஆகுற பணம்.
- **Speed**: users எவ்ளோ நேரம் காத்திருக்காங்க.

பெரிய models, அதிக retrieved context, rerankers, reflection steps, agent loops எல்லாம் பொதுவா quality-ஐ ஏத்தும், கூடவே cost, latency-யும் ஏத்தும். நல்ல engineering இந்த trade-offs-ஐ கண்ணுக்கு தெரியுற மாதிரி வச்சு, product-ஐ சொந்தமா வச்சிருக்குறவங்களோட சேர்ந்து வேணும்னே முடிவு பண்ணும்.

```flow
dir: LR
title: தேர்ந்தெடுத்தது: exclusions, claims-க்கு router + reranker: 88%, ₹0.30, 3.1 s p95
Question -> Router
Router -[easy]-> Small model | 76%, ₹0.08, 1.6 s
Router -[hard: exclusions, claims]-> Large model + reranker | 89%, ₹0.64, 4.3 s
```

Streaming ஒரு வினாடிக்குள்ள முதல் வார்த்தைகளை கொண்டு வரும்.

இந்த lesson, Hyderabad-ல ஒரு health-insurance company-யை பத்தி; அங்க call-centre agents live calls-ஓட போது ஒரு assistant-ஐ use பண்றாங்க.

## இது எப்படி work ஆகுது

**மூணையும் ஒரே test set-ல அளங்க.** ஒவ்வொரு option-க்கும் இதை record பண்ணுங்க:

- உங்க eval-ல இருந்து quality (மொத்தமா மட்டும் இல்ல, category வாரியா);
- ஒரு request-க்கு cost (tokens மடங்கு prices);
- median-லயும் 95th percentile-லயும் latency, time to first token-உம்.

**Options-ஐ ஒரு table-ல போடுங்க.** உதாரணமா: small model, large model, large model plus reranker. அப்புறம் trade-off ஒரு business பேச்சா மாறும்: "reranker accuracy-ஐ 85%-ல இருந்து 89%-க்கு ஏத்துது, p95-ல ஒரு request-க்கு 400 ms சேக்குது; worth-ஆ?"

**எந்த quality முக்கியம்னு கேளுங்க.** சாதாரண chat-க்கு 85% போதும்; medical அல்லது financial answers-க்கு quality, safety தான் முக்கியம். தப்புகளை அவற்றோட விளைவுகளை வச்சு எடை போடுங்க.

**முதல்ல free wins-ஐ தேடுங்க.** சில மாற்றங்கள் quality-ஐ பாதிக்காம speed அல்லது cost-ஐ மேம்படுத்தும்:

- streaming (உணரப்படுற speed);
- prompt caching (திரும்ப வர்ற prefixes-க்கு cost, speed);
- சின்ன outputs, prompts;
- சார்பில்லாத steps-ஐ parallel-ஆ ஓட்டுறது;
- தேவையில்லாத steps-ஐ எடுக்குறது.

**Difficulty வச்சு route பண்ணுங்க.** எளிய requests-ஐ வேகமான, மலிவான model-க்கும், கஷ்டமானதை strong model-க்கும் அனுப்புங்க. Router எவ்ளோ தடவை தப்பு பண்ணுதுன்னு அளங்க.

**Budgets-ஐ முடிவு பண்ணுங்க.** ஒரு latency budget (உதாரணம்: p95-ல first token 1.5 s-க்கு கீழ), ஒரு request-க்கு cost ceiling-ஐ ஒத்துக்குங்க; அப்புறம் அதுக்குள்ள quality-ஐ அதிகப்படுத்துங்க.

**திரும்பப் பாருங்க.** விலைகள் குறையும், models முன்னேறும், usage வளரும்; சிறந்த trade-off மாறும். சில மாசத்துக்கு ஒரு தடவை table-ஐ திரும்ப run பண்ணுங்க.

**Levers-உம் அவற்றோட விளைவுகளும்:**

| Lever | Quality | Cost | Speed |
| --- | --- | --- | --- |
| பெரிய model | ஏறும் | ஏறும் | மெதுவா |
| Reranker | ஏறும் | கொஞ்சம் ஏறும் | கொஞ்சம் மெதுவா |
| அதிக retrieved context | அடிக்கடி ஏறும், அப்புறம் இறங்கும் | ஏறும் | First token மெதுவா |
| Router | Large model-க்கு கிட்ட | இறங்கும் | Average-ல வேகம் |
| Streaming | அதே | அதே | ரொம்ப வேகமா தெரியும் |
| Prompt caching | அதே | இறங்கும் | First token வேகம் |
| சின்ன outputs | அதே அல்லது நல்லது | இறங்கும் | வேகம் |

**விளைவை வச்சு எடை போடுறது.** Test set-ஐ categories-ஆ பிரிச்சு, ஒவ்வொண்ணுக்கும் business-ல இருந்து ஒரு weight கொடுங்க: இங்க ஒரு தப்பான பதில் எவ்ளோ செலவானது? Insurer-க்கு exclusions, claims அதிக weight, பொதுவான questions குறைவு. Weighted score சாதாரண accuracy-ஐ விட வேற மாதிரி options-ஐ rank பண்ணலாம்; அது choice-க்கான காரணத்தை எல்லாருக்கும் தெளிவா காட்டும்.

**Recommendation-ஐ எழுதுறது.** Product owner-க்கு ஒரு paragraph: பரிசீலிச்ச options, தேர்ந்தெடுத்தது, அதோட quality, cost, latency, மிக accurate option-ஓட ஒப்பிட்டா எதை விட்டுக்கொடுக்குது, எப்போ திரும்பப் பாக்கணும். உதாரணம்: "Exclusions, claims-ல reranker-ஓட router-ஐ recommend பண்றோம்: 88% accuracy, ஒரு request-க்கு கிட்டத்தட்ட ₹0.30, p95-ல 3.1 s. எல்லா இடத்துலயும் reranker-ஓட large model 1 point நல்லது, ஆனா cost ரெண்டு மடங்கு, live calls-ல மெதுவா."

**Router-ஐ அளக்குறது.** Router சரியான requests-ஐ சரியான model-க்கு அனுப்புனா தான் காசை மிச்சப்படுத்தும். Test questions-ல ஒரு sample-ஐ easy அல்லது hard-ன்னு label பண்ணி, router-ஐ ஓட்டி, ரெண்டு வகை தப்புகளை எண்ணுங்க: small model-க்கு போன hard questions (quality-ஐ பாதிக்கும்), large model-க்கு போன easy questions (பணத்தை வீணாக்கும்). முதல் வகை அதிக முக்கியம். அது அதிக risk உள்ள category-ல அடிக்கடி நடந்தா, insurer exclusions, claims-க்கு பண்ணின மாதிரி அந்த முழு category-யையும் strong model-க்கு route பண்ணுங்க.

**Code-ல ஒரு weighted comparison.** ஒவ்வொரு option-ஐயும் business weights-ஓட category வாரியா score பண்ணி, பக்கத்துல cost, latency-யை காட்டுங்க:

```python
WEIGHTS = {"exclusions": 3.0, "claims": 3.0, "premiums": 2.0, "general": 1.0}

def weighted_quality(results):
    """results: list of (category, correct_bool)."""
    num = sum(WEIGHTS[c] * ok for c, ok in results)
    den = sum(WEIGHTS[c] for c, _ in results)
    return num / den

def p95(values):
    v = sorted(values)
    return v[int(0.95 * (len(v) - 1))]

def summarise(option_runs):
    """option_runs: name -> list of dicts with category, correct, cost_inr, ms."""
    table = []
    for name, runs in option_runs.items():
        table.append({"option": name,
                      "quality": round(weighted_quality([(r["category"], r["correct"]) for r in runs]), 3),
                      "cost_inr": round(sum(r["cost_inr"] for r in runs) / len(runs), 3),
                      "p95_ms": p95([r["ms"] for r in runs])})
    return table
```

**யாரும் தேர்ந்தெடுக்கக் கூடாத options-ஐ விடுங்க.** வேற ஒரு option quality, cost, speed-ல குறைஞ்சது இதே அளவு நல்லதாவும், ஒண்ணுல அதை விட நல்லதாவும் இருந்தா, இந்த option dominated:

```python
def frontier(table):
    def dominates(a, b):
        better_or_equal = a["quality"] >= b["quality"] and a["cost_inr"] <= b["cost_inr"] and a["p95_ms"] <= b["p95_ms"]
        strictly = a["quality"] > b["quality"] or a["cost_inr"] < b["cost_inr"] or a["p95_ms"] < b["p95_ms"]
        return better_or_equal and strictly
    return [o for o in table if not any(dominates(other, o) for other in table if other is not o)]
```

மிச்சம் இருக்குறது தான் உண்மையான choice, அது ஒரு business choice: எவ்ளோ quality-க்கு எத்தனை ரூபாய், எத்தனை milliseconds worth.

**முதல்ல budgets, அப்புறம் quality-ஐ அதிகப்படுத்துங்க.** Product owner-ஓட ஒரு request-க்கு cost ceiling, p95 latency target-ஐ ஒத்துக்குங்க, frontier-ஐ ரெண்டுக்குள்ளயும் இருக்குற options-க்கு filter பண்ணி, அதுல சிறந்த quality-ஐ எடுங்க. இது ஒரு மங்கலான விவாதத்தை ஒரு சின்ன meeting-ஆ மாத்தும்.

**விலைகளும் models-உம் மாறிக்கிட்டே இருக்கும்.** Comparison-ஐ date-ஓடவும் use பண்ண prices-ஓடவும் சேர்த்து வச்சுக்கோங்க. ஒரு provider விலையை குறைச்சா அல்லது புது model கொண்டு வந்தா, அதே test set-ஐ திரும்ப ஓட்டி table-ஐ update பண்ணுங்க; சிறந்த choice அடிக்கடி சில மாசத்துக்குள்ள மாறும்.

**ஒரு ரூபாய்க்கான quality மட்டும் முழு கதை இல்ல.** Safety-critical categories-க்கு, எந்த சேமிப்பாலும் கீழ போக முடியாத ஒரு minimum quality-ஐ வச்சு, cost எதுவா இருந்தாலும் அந்த categories-ஐ strong model-க்கு route பண்ணுங்க.

## ஒரு worked example

Hyderabad-ல ஒரு health-insurance company-யோட assistant, அவங்க call-centre agents-க்கு policy questions-க்கு பதில் சொல்லுது.

Team 150 test questions-ல நாலு options-ஐ ஒப்பிடுது:

| Option | Accuracy | ஒரு request-க்கு cost | p95 latency |
|---|---|---|---|
| Small model | 76% | ₹0.08 | 1.6 s |
| Large model | 85% | ₹0.60 | 3.9 s |
| Large model + reranker | 89% | ₹0.64 | 4.3 s |
| Router (small; hard ones to large) | 86% | ₹0.24 | 2.8 s |

Product owner-ஓட பார்வை: agents live calls-ல இருக்காங்க, அதனால latency ரொம்ப முக்கியம்; தப்பான coverage answers புகார்களையும் refunds-ஐயும் உண்டாக்கும், அதனால accuracy அதை விட முக்கியம். அவங்க exclusions, claims கேள்விகளுக்கு (அதிக risk உள்ள categories) reranker-ஓட router-ஐ தேர்ந்தெடுக்குறாங்க; மொத்தமா 88%, ஒரு request-க்கு கிட்டத்தட்ட ₹0.30, p95-ல 3.1 s. Streaming முதல் வார்த்தைகளை ஒரு வினாடிக்குள்ள வர வைக்குது.

| முடிவு காரணி | Choice-ஐ எப்படி வடிவமைச்சது |
| --- | --- |
| Agents live calls-ல | Latency முக்கியம், அதனால streaming, router |
| தப்பான coverage answers புகார்களையும் refunds-ஐயும் உண்டாக்கும் | Exclusions, claims-க்கு reranker |
| Call-centre volume-ல cost | Router பெரும்பாலான traffic-ஐ small model-ல வச்சிருக்கும் |

## பொதுவா பண்ற தப்புகள்

- **ஒரு dimension-ஐ சத்தமில்லாம optimise பண்றது.** மூணையும் காட்டுங்க.
- **மொத்த accuracy மட்டும்.** தப்புகளோட விளைவுகள், categories வச்சு weight பண்ணுங்க.
- **Tail latency-ஐ புறக்கணிக்கிறது.** Users மெதுவான requests-ஐ நினைவு வச்சிருப்பாங்க.
- **Free wins-ஐ தவற விடுறது.** முதல்ல streaming, caching.
- **முடிவை திரும்பவே பாக்காம இருக்குறது.**
- **Product owner இல்லாம தேர்ந்தெடுக்குறது.** Trade-off ஒரு business முடிவு; table-ஐ காட்டி அவங்களை எடை போட விடுங்க.
- **Weight இல்லாத accuracy**, சில தப்புகள் மத்ததை விட பல மடங்கு செலவானதா இருக்கும்போது.
- **Dominated options-ஐ** விவாதத்துல வச்சிருக்குறது.
- **Date, prices record பண்ணாத comparison**, அது சத்தமில்லாம காலாவதியாகும்.

## முழு trade-off study தேவையில்லாத நேரங்கள்

- **குறைவான volume**: ஒரு நாளைக்கு சில ரூபாய்ல strongest model போதும்; அப்புறம் optimise பண்ணலாம்.
- **ஒரு option எல்லா targets-ஐயும்** நிறைய இடம் மிச்சம் வச்சு தொடுது.
- **ஆரம்ப prototypes**, அங்க task வேலை செய்யுதான்னு கத்துக்கிறது தான் முதல்.
