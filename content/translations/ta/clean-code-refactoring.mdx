## இது என்ன

**Clean code** என்பது அடுத்த ஆள் பயமில்லாம படிச்சு, புரிஞ்சுகிட்டு, மாத்தக்கூடிய code. அந்த அடுத்த ஆள் பெரும்பாலும் நீங்களே தான், மூணு மாசம் கழிச்சு, ஏன் அப்படி எழுதுனீங்கன்னு நினைவே இல்லாம.

Clean code என்பது கெட்டிக்காரத்தனமான tricks-ஓ குறைஞ்ச lines-ஓ இல்ல. அது படிக்கிறவங்களை பத்தினது. ஒரு function-ஓட பேரை பார்த்தே அது என்ன பண்ணுதுன்னு சொல்ல முடியுமா? மேல இருந்து கீழ வரை தாவாம follow பண்ண முடியுமா? ஒரு rule-ஐ ஒரே இடத்துல மாத்த முடியுமா?

**Refactoring** என்பது code என்ன பண்ணுதோ அதை மாத்தாம, அது எப்படி எழுதப்பட்டிருக்குன்னு மாத்துறது. Behaviour மாறாம இருக்குன்னு tests உறுதிப்படுத்த, ஒரு நேரத்துல ஒரு சின்ன step-ஆ rename பண்றீங்க, split பண்றீங்க, simplify பண்றீங்க, duplication-ஐ நீக்குறீங்க. Risky-ஆன rewrite இல்லாம messy code, clean code ஆகுறது இப்படித்தான்.

## இது எப்படி work ஆகுது

பெரிய வித்தியாசம் தர்ற பழக்கங்கள்:

| பழக்கம் | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| தெளிவான names | `def calc(d, f):` | `def invoice_total(items, include_gst):` |
| Named constants | `amount * 1.18` | `amount * (1 + GST_RATE)` |
| சின்ன functions | 120 lines உள்ள ஒரு `process()` | `read_orders()`, `validate()`, `total()`, `write_report()` |
| Early returns | நாலு nested `if` blocks | தப்பான cases-ஐ முதல்ல handle பண்ணி, அப்புறம் main path |
| ஒரே source of truth | அதே rule மூணு files-ல copy | எல்லாரும் call பண்ற ஒரே function |
| நேர்மையான comments | `# loop over items` | `# 30 நாளுக்கு மேல பழைய refunds-க்கு manager approval வேணும் (policy 4.2)` |

நல்ல comments **ஏன்**னு சொல்லும், என்னன்னு இல்ல. Code என்ன பண்ணுதுன்னு அதுவே சொல்லிடும்; comment, code சொல்ல முடியாததை சொல்லணும், business rule அல்லது ஒரு விசித்திரமான தேர்வுக்கான காரணம் மாதிரி.

Refactoring ஒரு பாதுகாப்பான loop-ஐ follow பண்ணும்:

```flow
dir: LR
Tests pass ஆகுது -> ஒரு சின்ன மாற்றம் | rename, function-ஐ extract பண்ணு, constant சேரு
ஒரு சின்ன மாற்றம் -> Tests-ஐ ஓட்டு
Tests-ஐ ஓட்டு -[pass]-> Commit
Commit -> ஒரு சின்ன மாற்றம்
Tests-ஐ ஓட்டு -[fail]-> Undo பண்ணி இன்னும் சின்ன step try பண்ணு
Undo பண்ணி இன்னும் சின்ன step try பண்ணு -> ஒரு சின்ன மாற்றம்
```

சின்ன steps தான் முக்கியம். ஒரு rename, tests run, ஒரு commit. ஒரு function extract, run, commit. ஒரு test fail ஆனா, எந்த step உடைச்சதுன்னு சரியா தெரியும், அந்த ஒண்ணை மட்டும் undo பண்ணலாம். பெரிய big-bang rewrite-ல இது எதுவும் கிடைக்காது.

**Extract function** தான் மிக பயனுள்ள refactor. ஒரு நீளமான function-க்குள்ள ஒரே வேலை பண்ற ஒரு block-ஐ எடுத்து, அந்த வேலையை சொல்ற பேரோட தனி function-ஆ மாத்தி, அதை call பண்ணுங்க. நீளமான function steps-ஓட ஒரு list மாதிரி படிக்க ஆரம்பிக்கும்.

**Code smells** என்பது code-ஐ மாத்துறது கஷ்டமா இருக்கும்னு காட்டுற அறிகுறிகள்: ஒரு screen-ல அடங்காத நீளமான functions, பல இடங்கள்ல copy ஆன அதே logic, அஞ்சு files-ல edits தேவைப்படுற ஒரு மாற்றம், ஆழமான nesting, `data`, `temp`, `x` மாதிரி பேர் உள்ள variables. இவை bugs இல்ல; bugs உருவாகுற இடங்கள்.

**AI projects-ல clean code.** Prompts-க்கும் pipelines-க்கும் அதே பழக்கங்கள் பொருந்தும். Functions-க்குள்ள புதைஞ்ச நீளமான strings-ஆ இல்லாம, prompts-ஐ தெளிவான பேரோட தனி files-ல வைங்க. Pipeline-ஓட ஒவ்வொரு step-க்கும் (load, chunk, embed, retrieve, generate) தனி function கொடுங்க, அப்போ மத்ததை தொடாம ஒண்ணை test பண்ணவோ மாத்தவோ முடியும். Chunk size, top-k, temperature மாதிரி settings-ஐ ஒரே config file-ல constants-ஆ பேர் வைங்க, அப்போ ஒரு experiment ஒரே ஒரு line-ஐ மாத்தும், diff என்ன try பண்ணோம்னு சரியா காட்டும்.

**எப்போ refactor பண்ணக்கூடாது.** Refactoring-க்கு cost இருக்கு: நேரம், review முயற்சி, கொஞ்சம் risk. Work ஆகுற, யாரும் மாத்த plan பண்ணாத code-க்கும், throwaway scripts-க்கும், outage நடுவுலயும் இதை skip பண்ணுங்க; outage-ல சின்ன fix தான் சரி. அவசர மாற்றம் ship ஆகி, அதை சுத்தி tests வந்த பிறகு, அதுக்குன்னு தனி pull request-ல tidy up பண்ணுங்க.

## ஒரு worked example

Kavya, Kochi-ல ஒரு edtech company-ல 140 lines உள்ள `process_file()` function-ஐ inherit பண்றாங்க. அது course purchases-ஓட ஒரு CSV-ஐ படிச்சு, refunds-ஐ filter பண்ணி, GST சேர்த்து, coupons apply பண்ணி, ஒரு summary எழுதுது. ஒரு புது rule வருது: ஒரு அரசு scheme-க்கு GST skip பண்ணணும். Function-ஐ மாத்துறது risky-ஆ தெரியுது.

**முதல்ல, tests.** இன்னைக்கு இருக்குற behaviour-ஐ சுத்தி ஆறு tests எழுதுறாங்க, சின்ன sample CSVs வச்சு: சாதாரண purchases, ஒரு refund, ஒரு coupon, ஒரு zero amount, ஒரு missing field, ஒரு duplicate row. பழைய code-ல எல்லாம் pass ஆகுது. இப்போ அவங்ககிட்ட ஒரு safety net இருக்கு.

**அப்புறம் சின்ன steps.** `d`-ஐ `purchases`-ஆவும் `t`-ஐ `total`-ஆவும் rename பண்றாங்க. Tests pass; commit. `* 1.18`-ஓட மூணு copies-ஐ ஒரு `GST_RATE` constant-ஆலயும் ஒரு `with_gst()` function-ஆலயும் மாத்துறாங்க. Tests pass; commit. `read_purchases()`, `apply_coupon()`, `write_summary()` extract பண்றாங்க. ஒவ்வொரு step-லயும் tests run ஆகி, அதுக்குன்னு ஒரு commit கிடைக்குது.

Main function இப்போ business process மாதிரி படிக்கிற பதினோரு lines:

```python
def process_file(path):
    purchases = read_purchases(path)
    paid = [p for p in purchases if not p.is_refund]
    totals = [with_gst(apply_coupon(p)) for p in paid]
    write_summary(totals)
```

**அப்புறம் புது rule.** Scheme-க்கு GST-ஐ skip பண்றது இப்போ ஒரே function-ல, `with_gst()`-ல, ஒரு மாற்றமும் ஒரு புது test-உம் தான். Pull request சின்னதா, review பண்ண சுலபமா இருக்கு, reviewer அதே நாள் approve பண்றாரு.

## பொதுவான தப்புகள்

- **Tests இல்லாம refactor பண்றது.** Behaviour மாத்திட்டீங்களான்னு சொல்ல முடியாது. முதல்ல இன்னைக்கு அது என்ன பண்ணுதோ அதுக்கு tests சேருங்க.
- **ஒரே step-ல refactor-ம் behaviour மாற்றமும் பண்றது.** Tidy-up-ஐயும் புது feature-ஐயும் தனி commits-ல பண்ணுங்க, அப்போ ஒவ்வொண்ணும் review பண்ண சுலபம்.
- **பெரிய rewrites.** அவை வாரக்கணக்கா எடுக்கும், யாருக்கும் நினைவில்லாத விஷயங்களை உடைக்கும். சின்ன, பாதுகாப்பான steps தான் ஜெயிக்கும்.
- **கெட்டிக்காரத்தனமான one-liners.** படிக்கிறவங்க decode பண்ண வேண்டியிருந்தா, குறைவா இருக்கிறது clean ஆகாது.
- **Code-ஐ repeat பண்ற comments.** அவை பழசாகிடும். ஏன்னு விளக்குங்க, இல்லன்னா comment தேவையில்லாத அளவுக்கு rename பண்ணுங்க.
- **யாரும் தொடாத code-ஐ மெருகேத்துறது.** எல்லாத்தையும் இல்ல, நீங்க மாத்தப்போறதை refactor பண்ணுங்க.

## Practice

1. Exercise-ல இருக்குற one-line function-ஐ எடுத்து, tests-ஓட clean-ஆ மாத்தி எழுதுங்க.
2. உங்க projects-ல ஒண்ணுல மிக நீளமான function-ஐ கண்டுபிடிச்சு, அதுல இருந்து ரெண்டு சின்ன functions-ஐ extract பண்ணுங்க, tests green-ஆவே இருக்கணும்.
3. ஒரு script-ல விளக்கம் இல்லாத ஒவ்வொரு number-ஐயும் named constant-ஆ மாத்துங்க.
4. ஒரு take-home அல்லது review-ல, உங்க code-ஐ ஏன் அந்த மாதிரி structure பண்ணீங்கன்னு ரெண்டு வாக்கியத்துல விளக்குங்க.
