## இது என்ன

**Human approval step** ஒரு action நடக்குறதுக்கு முன்னாடி agent-ஐ pause பண்ணும். Agent என்ன பண்ண நினைக்குது, ஏன்னு ஒரு ஆளுக்கு காட்டும். அவங்க approve, edit, reject பண்ணும்போது மட்டும் தொடரும். Production agents-ல இது தான் human-in-the-loop-ஓட மிகவும் பொதுவான வடிவம்.

Approval, செலவு அதிகமான, திரும்ப எடுக்க முடியாத, வெளிய போற அல்லது regulated ஆன actions-க்கு: refunds, payments, customers-க்கு emails, messages, records மாற்றம், எதையாவது delete பண்றது, legal அல்லது medical முடிவுகளை தொடுற எதுவும். Data-வை படிக்கிறதுக்கு பெரும்பாலும் approval தேவையில்ல.

```flow
Agent propose பண்றது: order 7781-க்கு ₹2,499 refund -> Risk rules
Risk rules -[படிக்கிறது, அல்லது சின்னதும் reversible-உம்]-> Run பண்ணு
Risk rules -[limit-ஐ தாண்டின refund]-> Pause | state-ஐ checkpoint-ஆ save பண்ணு; run "interrupted"-ஆ முடியும்
Pause -> Approval card | action, காரணம், evidence: Approve, Amount-ஐ Edit, காரணத்தோட Reject
Approval card -[4 மணி நேரம் பதில் இல்ல]-> Remind பண்ணி, அப்புறம் escalate
Approval card -[decision]-> Checkpoint-ல இருந்து resume -> Act பண்ணு -> Customer-க்கு சொல்லு
Customer-க்கு சொல்லு -> Log | decision, edit, காரணம், decide பண்ண ஆன seconds
```

இந்த lesson-ல Jaipur-ல இருக்குற ஒரு e-commerce company-ஓட returns and refunds agent-ஐ follow பண்றோம்.

## இது எப்படி work ஆகுது

**Actions-ஐ risk படி வகைப்படுத்துங்க.** ஒவ்வொரு tool-ஐயும் list பண்ணி rate பண்ணுங்க: read-only, reversible internal மாற்றம், irreversible அல்லது external. ஒரு எளிய rule set எதுக்கு approval வேணும்னு முடிவு பண்ணும்: irreversible அல்லது external actions-க்கு எப்பவும்; மத்தவைக்கு ஒரு threshold-க்கு மேல (₹1,000-க்கு மேல இருக்குற refunds மாதிரி); reads-க்கு ஒருபோதும் இல்ல.

**Durable-ஆ pause பண்ணுங்க.** Agent நிறுத்தி காத்திருக்கணும், சில நேரம் மணிக்கணக்கா, ஒரு server process-ஐ திறந்து வைக்காம. Checkpoints இருக்குற frameworks இதை பண்ணும்: state save ஆகும், run "interrupted" state-ல முடியும், அப்புறம் வர்ற ஒரு call அதே இடத்துல இருந்து அந்த ஆளோட decision-ஓட resume பண்ணும்.

**சரியான தகவலை காட்டுங்க.** Approval screen-ல proposed action எளிய வார்த்தைகள்ல ("order 7781-க்கு ...@okaxis UPI ID-க்கு ₹4,500 refund"), agent-ஓட காரணம், அது use பண்ண evidence (order, policy clause), one-click approve, edit, reject இருக்கணும். Approver முடிவு பண்ண வேற மூணு systems-ஐ திறக்க வேண்டியிருந்தா, கண்ணை மூடிட்டு approve பண்ண ஆரம்பிச்சிடுவாங்க.

**Edit-உம் feedback-உம்.** Approver parameters-ஐ மாத்தலாம் (₹4,500-ஐ ₹3,000-ஆ), ஒரு note-உம் சேர்க்கலாம். ரெண்டுமே agent-ஓட state-க்கு போகும், அதனால agent அந்த மாற்றத்தை customer-க்கு explain பண்ணலாம்; உங்க logs-க்கும் போகும், training, eval data-வா.

**Measure பண்ணுங்க.** Approval rate, edit rate, rejection காரணங்கள், decide பண்ண ஆகுற நேரம் எல்லாம் track பண்ணுங்க. மாதக்கணக்கா rejection rate கிட்டத்தட்ட பூஜ்யம்னா, low-risk cases-க்கு இந்த step-ஐ தளர்த்தலாம். Edits இல்லாம time-to-decide குறைஞ்சுக்கிட்டே போனா, அது rubber-stamping-ஆ இருக்கலாம்.

**Timeouts-உம் escalation-உம்.** யாரும் பதில் சொல்லலைன்னா என்ன நடக்கும்னு முடிவு பண்ணுங்க: remind பண்ணுங்க, வேற approver-க்கு escalate பண்ணுங்க, அல்லது பாதுகாப்பா cancel பண்ணுங்க. "Approve"-ஐ default-ஆ வைக்கவே வேண்டாம்.

**ஒரு agent-க்கான risk table:**

| Tool | வகை | Rule |
| --- | --- | --- |
| `read_order` | Read-only | Approval தேவையில்ல |
| `issue_return_label` | Reversible | Auto-approved |
| `refund` ₹1,000 வரை, order 30 நாளுக்குள்ள | பணம், சின்னது | Auto-approved |
| `refund`, வேற எந்த case-ம் | பணம் | Support lead approve பண்ணுவார் |
| Legal action பத்தி சொல்ற எந்த message-ம் | Legal risk | முழுசா ஒரு ஆள்கிட்ட handover |

**Card-ஐ design பண்றது.** முடிவை முதல்ல வையுங்க, amount-உம் recipient-உம் இருக்குற ஒரே வாக்கியத்துல. அதுக்கு கீழ agent சொன்ன காரணத்தையும் evidence-ஐயும் கொடுங்க: customer-ஓட photo, எண்ணோட policy clause மாதிரி. Buttons பெருசா, விளைவை பேரா வச்சு இருக்கணும். "Reject" ஒரு சின்ன list-ல இருந்து காரணத்தையும் free text-ஐயும் கேக்கணும், ஏன்னா அந்த காரணங்களை தான் அப்புறம் analyse பண்ணுவீங்க. Card-ஐ உண்மையான approvers-ஓட test பண்ணுங்க: அவங்க முடிவு பண்ண வேற system-ஐ திறக்கிறாங்கன்னா, card-ல ஏதோ குறையுது.

**Evidence வச்சு தளர்த்துறது.** Approval நிரந்தரம் இல்ல. ஒரு மாசம், ரெண்டு மாசம் data வந்த பிறகு, ஒவ்வொரு rule-ஓட approval, edit, rejection rates-ஐ பாருங்க. எதுவும் edit பண்ணாம கிட்டத்தட்ட எல்லாத்தையும் approve பண்ற இடத்துல, threshold-ஐ கொஞ்சம் உயர்த்தி complaints-ஐ கவனிங்க. அடிக்கடி edit பண்ற இடத்துல, முதல்ல agent-ஓட examples-ஐ சரி பண்ணுங்க.

**Policy-ஐ ஒரு pure function-ஆ.** Rules-ஐ prompt-ல வைக்காம, test பண்ணக்கூடிய code-ல வையுங்க:

```python
from dataclasses import dataclass

@dataclass
class Decision:
    route: str            # "auto", "approve" or "handover"
    approver: str | None = None
    reason: str = ""

def policy(tool, args, context):
    if tool in {"read_order", "track_shipment"}:
        return Decision("auto", reason="read-only")
    if tool == "issue_return_label":
        return Decision("auto", reason="reversible")
    if tool == "refund":
        amount, age = args["amount_inr"], context["order_age_days"]
        if amount <= 1000 and age <= 30:
            return Decision("auto", reason="small refund within 30 days")
        if amount <= 25000:
            return Decision("approve", "support_lead", "refund above auto limit")
        return Decision("approve", "finance_manager", "large refund")
    if context.get("mentions_legal_action"):
        return Decision("handover", reason="legal risk")
    return Decision("approve", "support_lead", "unknown tool: default to a person")

assert policy("refund", {"amount_inr": 800}, {"order_age_days": 12}).route == "auto"
assert policy("refund", {"amount_inr": 40000}, {"order_age_days": 3}).approver == "finance_manager"
```

தெரியாத tools default-ஆ ஒரு ஆள்கிட்ட போகும், "auto"-க்கு ஒருபோதும் போகாது. Agent loop எந்த tool-ஐ ஓட்டுறதுக்கு முன்னாடியும் `policy`-ஐ call பண்ணும்; "approve"-னா ஒரு pending action-ஐ save பண்ணி run-ஐ pause பண்ணும்.

**Durable pending action.** ஒவ்வொரு request-ஐயும் approver-க்கு தேவையான எல்லாத்தோடும், ஒரு idempotency key-ஓடும் store பண்ணுங்க. அப்போ double click அல்லது retry அதை ரெண்டு தடவை ஓட்ட முடியாது:

```python
import sqlite3, time, uuid

db = sqlite3.connect("approvals.db")
db.execute("""CREATE TABLE IF NOT EXISTS pending (
    id TEXT PRIMARY KEY, run_id TEXT, tool TEXT, args TEXT, summary TEXT,
    approver TEXT, status TEXT DEFAULT 'waiting', decided_by TEXT, note TEXT,
    created REAL, decided REAL)""")

def request(run_id, tool, args_json, summary, approver):
    pid = uuid.uuid4().hex
    db.execute("INSERT INTO pending (id, run_id, tool, args, summary, approver, created) VALUES (?,?,?,?,?,?,?)",
               (pid, run_id, tool, args_json, summary, approver, time.time()))
    db.commit()
    return pid

def decide(pid, user, approve, note="", new_args_json=None):
    cur = db.execute("""UPDATE pending SET status=?, decided_by=?, note=?, decided=?, args=COALESCE(?, args)
                        WHERE id=? AND status='waiting'""",
                     ("approved" if approve else "rejected", user, note, time.time(), new_args_json, pid))
    db.commit()
    return cur.rowcount == 1        # False if already decided: the second click does nothing
```

`decide` வெற்றி பெற்றா, உங்க code pause ஆன run-ஐ அந்த decision-ஓட resume பண்ணும். Request-ல பேர் சொன்ன approver role `user`-க்கு இருக்கான்னு `decide`-ல check பண்ணுங்க; agent-கிட்ட கேட்டவரே தன்னோட பெரிய refund-ஐ approve பண்ணக்கூடாது.

**Timeouts ஒரு scheduled job-ஆ.** ஒவ்வொரு சில நிமிஷமும் limit-ஐ தாண்டி காத்திருக்குற requests-ஐ கண்டுபிடிங்க: 30 நிமிஷத்துல remind, 2 மணி நேரத்துல அடுத்த approver-க்கு escalate, 24 மணி நேரத்துல customer-க்கு ஒரு message-ஓட பாதுகாப்பா cancel. கடைசி நிலை cancel தான், approve ஒருபோதும் இல்ல.

**Approvers-ஐயும் test பண்ணுங்க.** அப்பப்போ வேணும்னே ஒரு தப்பான request-ஐ queue-ல வையுங்க, உதாரணம்: அந்த customer-க்கு deliver ஆகவே ஆகாத ஒரு order-க்கு refund. அது approve ஆனா, cards-க்கு நல்ல evidence வேணும், இல்லன்னா கவனமா review பண்ண queue ரொம்ப நீளம்.

## ஒரு worked example

Jaipur-ல ஒரு e-commerce company return, refund requests-ஐ பார்த்துக்க ஒரு agent-ஐ deploy பண்ணுது.

Risk rules: orders-ஐ படிக்கிறதுக்கு approval இல்ல; return label கொடுக்கிறது reversible, auto-approved; 30 நாளுக்குள்ள இருக்குற orders-க்கு ₹1,000-க்கு கீழ refunds auto-approve; மத்த எல்லா refunds-க்கும் support lead-ஓட approval; legal action பத்தி சொல்ற எந்த message-ம் முழுசா ஒரு ஆள்கிட்ட போகும்.

Approval card இப்படி இருக்கும்: "Order 7781-க்கு ₹2,499 refund (blue kurta, size M). Customer சொல்றாங்க கிழிஞ்சு வந்துச்சுன்னு; photo attach பண்ணியிருக்காங்க. Policy 4.2: damage 7 நாளுக்குள்ள report பண்ணா full refund; report பண்ணது நாள் 3-ல." Approve, Edit amount, Reject with reason.

முதல் மாசத்துல leads 91% approve பண்ணாங்க, 6% edit பண்ணாங்க (பெரும்பாலும் ஒரு set-ல ஒரு item மட்டும் damage ஆன partial refunds), 3% reject பண்ணாங்க (damage தெரியாத photos). Median decision time 40 seconds. நீங்க edit cases-ஐ agent-ஓட examples-ல சேர்க்குறீங்க, அதுக்கு அப்புறம் edits 2%-க்கு குறையுது. அந்த evidence வச்சு client auto-approve threshold-ஐ ₹1,500-க்கு உயர்த்துது; complaints கூடாம மூணுல ஒரு பங்கு approvals போயிடுச்சு.

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்துக்கும் approval, இல்ல எதுக்கும் இல்ல.** ஒவ்வொரு read-க்கும் approval வச்சா ஆட்களோட நேரம் வீணாகும்; payments-க்கு approval இல்லன்னா பொறுப்பற்றது. Actions-ஐ risk படி rate பண்ணுங்க.
- **காத்திருக்கும்போது ஒரு process-ஐ திறந்து வைக்கிறது.** Approvals-க்கு மணிநேரம் ஆகலாம். State-ஐ save பண்ணி அப்புறம் resume பண்ணுங்க.
- **Evidence இல்லாத approval screens.** ஆட்களால judge பண்ண முடியாது, அதனால approve click பண்ணிடுவாங்க.
- **Timeout-ல approve-ஐ default-ஆ வைக்கிறது.** மௌனம் சம்மதம் இல்ல. Escalate பண்ணுங்க அல்லது cancel பண்ணுங்க.
- **Edits-ல இருந்து கத்துக்காம இருக்கிறது.** Agent எங்க தப்பு பண்றதுன்னு காட்டுற உங்களோட best data edits-உம் rejections-உம் தான்.
- **Approval rules prompt-ல மட்டும் எழுதுறது.** Model அவற்றை skip பண்ணலாம்; code skip பண்ணாது.
- **கேட்டவரே approve பண்ண விடுறது.** பணம், data மாற்றங்களுக்கு, யார் கேக்குறாங்க, யார் approve பண்றாங்கன்னு பிரிங்க.
- **Approvals-ல idempotency இல்லாம இருக்கிறது.** ஒரு double click action-ஐ ரெண்டு தடவை ஓட்டிடும்.

## Approval steps தேவையில்லாத நேரங்கள்

- **Read-only agents**, தேடி பதில் சொல்றது மட்டும்.
- **முழுசா reversible, செலவு கம்மியான actions**, undo இருக்குற ஒரு note அல்லது tag சேர்க்கிறது மாதிரி.
- **Code-ல ஏற்கனவே tight limits இருக்குற actions**, ஒரு customer-க்கு மாசத்துக்கு சின்ன cap இருக்குற refunds மாதிரி; அங்க தப்பின் செலவு review-ஐ விட கம்மி.

Approvals-க்கு தாமதம், staff நேரம்னு cost இருக்கு. தப்பு விலை அதிகமா, திரும்ப எடுக்க முடியாததா, company-க்கு வெளிய இருக்குற ஆட்களுக்கு தெரியுறதா இருக்குற இடத்துல மட்டும் use பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **Policy-ஐ tests-ஓட code-ல வச்சிருங்க**, business owners-ஓட ஒரு table-ஆ review பண்ணுங்க.
- **ஒவ்வொரு request-ஐயும் decision-ஐயும் store பண்ணுங்க**: யார், எப்போ, என்ன மாறுச்சு, ஏன்.
- **Queue-ஓட வயசு பத்தியும்**, ஒரு agent-க்கு requests திடீர்னு கூடுறது பத்தியும் alert வச்சிருங்க.
- **Rates-ஐ மாசம் ஒரு தடவை review பண்ணுங்க**, rule வாரியா: approval, edit, rejection, decide பண்ண நேரம்.
- **Approvers படிக்கிறாங்களான்னு பார்க்க**, அப்பப்போ test requests-ஐ வையுங்க.

## Practice பண்ணுங்க

LangGraph-ஓட interrupts guide-ஐ அல்லது agents-in-LangGraph course-ஓட approval section-ஐ படிங்க.

1. நீங்க build பண்ண ஒரு agent-ஓட tools-ஐ list பண்ணி, ஒவ்வொண்ணையும் read-only, reversible, irreversible-ன்னு rate பண்ணுங்க. Approval rules-ஐ எழுதுங்க.
2. ஒரு risky tool-க்கு முன்னாடி durable pause சேருங்க; proposed action-ஐ அதோட காரணத்தோட காட்டி, approve, edit, reject பண்ண விடுற ஒரு சின்ன script அல்லது page-ஐயும் சேருங்க.
3. ஒவ்வொரு decision-ஐயும் எடுத்த நேரத்தோட log பண்ணுங்க; approval, edit, rejection rates-ஐ காட்டுற query-ஐ எழுதுங்க.
4. உங்க policy function-க்கு unit tests எழுதுங்க: ஒவ்வொரு tool, threshold amounts-ஓட ரெண்டு பக்கமும், ஒரு தெரியாத tool.
