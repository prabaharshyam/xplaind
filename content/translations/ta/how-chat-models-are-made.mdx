## இது என்ன

தினமும் நீங்க use பண்ற chat assistants ஒரே தடவையில train ஆகல. அவை stages-ஆ build ஆகுது, ஒவ்வொரு stage-உம் வேற வேற ஒண்ணை சேர்க்குது.

1. **Pre-training.** Model ஒரு பெரிய அளவு text-ஐ படிக்குது (web pages, books, code), அடுத்த token-ஐ predict பண்ண கத்துக்குது. இதுக்கு தான் பணமும் compute-உம் அதிகம் போகும். முடிவுல கிடைக்கிறது ஒரு **base model**. அதுக்கு language பத்தியும் உலகம் பத்தியும் நிறைய தெரியும், ஆனா அது text-ஐ தொடர மட்டும் தான் செய்யும்.
2. **Supervised fine-tuning (SFT).** Base model-ஐ, ஒரு prompt-உம் ideal answer-உம் உள்ள examples-ல train பண்றாங்க, அவற்றை மக்கள் எழுதியோ check பண்ணியோ இருப்பாங்க. அது instructions-ஐ follow பண்ணவும் assistant மாதிரி பதில் சொல்லவும் கத்துக்குது. இதை instruction tuning-ன்னும் சொல்வாங்க.
3. **Preference tuning.** ஒரே prompt-க்கு ரெண்டு answers-ஐ மக்கள் compare பண்ணி, நல்லதை தேர்ந்தெடுக்கிறாங்க. அப்புறம் விரும்பப்பட்ட answers அதிகம் வர்ற மாதிரி model-ஐ tune பண்றாங்க. ரெண்டு பொதுவான methods: **RLHF** (reinforcement learning from human feedback), **DPO** (direct preference optimisation).

Stage 2, 3 ரெண்டையும் சேர்த்து பெரும்பாலும் **post-training**-ன்னு சொல்வாங்க. அவை மொத்த compute-ல சின்ன பங்கு தான் எடுக்கும், ஆனா model-ஓட behaviour-ஐ ரொம்ப மாத்தும். ஒரு provider ஒரு model-ஓட "base" version-ஐயும் "instruct" அல்லது "chat" version-ஐயும் release பண்ணும்போது, வித்தியாசம் post-training தான்.

```flow
title: Raw text-ல இருந்து chat model வரை
dir: LR
பெரிய text collection | web, books, code
பெரிய text collection -> Pre-training | அடுத்த token-ஐ predict பண்றது
Pre-training -> Base model | text-ஐ தொடரும்
Base model -> Supervised fine-tuning | prompt, ideal answer
Supervised fine-tuning -> Instruct model | instructions-ஐ follow பண்ணும்
Instruct model -> Preference tuning | RLHF அல்லது DPO
Preference tuning -> Chat model | helpful, polite, safe
```

ஒரு பயனுள்ள படம்: pre-training model-க்கு knowledge-ஐ கொடுக்குது, SFT helpful-ஆ இருக்குற format-ஐ கத்துக்கொடுக்குது, preference tuning, சாத்தியமான பல answers-ல மக்கள் உண்மையில எதை விரும்புவாங்கன்னு model-ஓட judgement-ஐ வடிவமைக்குது.

## இது எப்படி work ஆகுது

**Stage 1: pre-training.** Training text tokens-ஆ வெட்டப்படும். ஒவ்வொரு இடத்துக்கும் model அடுத்த token-ஐ guess பண்ணி, தன் guess-ஐ உண்மையானதோட compare பண்ணி, தன் weights-ஐ கொஞ்சூண்டு adjust பண்ணும். டிரில்லியன் கணக்கான tokens மேல இதை திரும்ப திரும்ப பண்றதால, grammar, facts, reasoning patterns, code எல்லாம் கத்துக்கும். Model என்ன கத்துக்குதுங்கறது அது என்ன படிக்குதுன்னு பெருசா சார்ந்தது. Odia, Assamese மாதிரி ஒரு மொழி training text-ல அரிதா இருந்தா, அந்த மொழில model பலவீனமா இருக்கும்.

Base model-கிட்ட "How do I reset my UPI PIN?"ன்னு prompt கொடுத்தா, அது பதில் சொல்லலாம், இல்லன்னா இன்னும் கேள்விகளோட ஒரு list-ஐ உருவாக்கலாம், ஏன்னா web-ல கேள்விகள் நிறைஞ்ச pages நிறைய இருக்கு. அது வேணும்னே உதவாம இருக்கல. Likely text-ஐ predict பண்ணுது.

**Stage 2: supervised fine-tuning.** Train ஆன மக்கள் ஆயிரக்கணக்கான prompts-ஐ உயர்தர answers-ஓட எழுதுறாங்க: explanations, summaries, code, polite refusals. ஆரம்ப பொது example-ஆன OpenAI-ஓட InstructGPT வேலை சுமார் 13,000 இப்படிப்பட்ட demonstration examples use பண்ணுச்சு. அவற்றை எழுதுறது slow-ஆ, costly-ஆ இருக்கும், ஏன்னா ஒரு கஷ்டமான கேள்விக்கு நல்ல answer எழுத ஒரு திறமையான ஆளுக்கு நிறைய நேரம் ஆகலாம். SFT-க்கு அப்புறம் model கேள்விகளை தொடராம, அவற்றுக்கு பதில் சொல்லும்.

ஒரு SFT example ஒரு சின்ன chat மாதிரி இருக்கும்:

```json
{"messages": [
  {"role": "user", "content": "How do I reset my UPI PIN?"},
  {"role": "assistant", "content": "Open your UPI app, go to the bank account, choose Reset UPI PIN, and verify with your debit card details and the OTP sent to your phone."}
]}
```

**Stage 3: preference tuning.** எந்த prompt-க்கும் ஏற்றுக்கொள்ளக்கூடிய பல answers இருக்கு, சில மத்தவற்றை விட நல்லது. ஒரே சிறந்த answer-ஐ எழுதுறது கஷ்டம், ஆனா ரெண்டு answers-ஐ compare பண்றது சுலபம். அதனால மக்களுக்கு ஒரு prompt-ஐயும் model-ஓட ரெண்டு answers-ஐயும் காட்டி, எது நல்லதுன்னு கேக்குறாங்க. ஒவ்வொரு judgement-உம் ஒரு **preference pair** ஆகும்:

```json
{"prompt": "My order is late. What can I do?",
 "chosen": "Sorry about the delay. You can track it under My Orders. If it is more than 3 days late, you can ask for a refund there.",
 "rejected": "Orders are sometimes late. Please wait."}
```

இந்த pairs-ல இருந்து கத்துக்க ரெண்டு முக்கிய வழிகள்.

- **RLHF.** முதல்ல pairs-ல ஒரு தனி **reward model**-ஐ train பண்ணுவாங்க. அது எந்த answer-க்கும் மக்கள் எவ்வளவு விரும்புவாங்கன்னு ஒரு score கொடுக்கும். அப்புறம் chat model-ஐ reinforcement learning வச்சு train பண்ணுவாங்க, அதிக score கிடைக்கிற answers தர. ஆனா SFT model-க்கு நெருக்கமாவே இருக்கும், அப்போ தான் score நல்லா வர்றதுக்காக விசித்திரமான text-க்கு drift ஆகாது.
- **DPO.** Reward model-ஐ skip பண்ணிடுவாங்க. Chat model-ஐ pairs-ல நேரடியா train பண்ணுவாங்க; ஆரம்பத்துல இருந்ததோட ஒப்பிட்டு chosen answer இன்னும் likely ஆகவும், rejected answer குறைவா likely ஆகவும். இது சாதாரண training code தான், மலிவு, ஓட்டுறதுக்கு இன்னும் stable. பல open model families DPO அல்லது அது மாதிரி methods-க்கு மாறிட்டாங்க.

மூணாவது வகை **RLAIF**, எந்த answer நல்லதுன்னு தீர்மானிக்க மக்களுக்கு பதிலா ஒரு strong model-ஐ use பண்ணும். இது மலிவு, ஆனா அந்த judge model-ஓட blind spots-ஐயும் சேர்த்து எடுத்துக்கும்.

| Stage | Training data | என்ன சேர்க்குது | தோராயமான செலவு |
| --- | --- | --- | --- |
| Pre-training | டிரில்லியன் கணக்கான tokens உள்ள raw text | Language, facts, code பத்தின knowledge | பெரும்பாலான compute; பெரிய labs மட்டும் பண்ணும் |
| Supervised fine-tuning | ஆயிரக்கணக்குல இருந்து பத்தாயிரக்கணக்கு வரை prompt, ideal-answer pairs | Instructions-ஐ follow பண்ணும், assistant மாதிரி பதில் சொல்லும் | சின்ன compute; expert writing costly |
| Preference tuning (RLHF அல்லது DPO) | பத்தாயிரக்கணக்கான chosen, rejected pairs | நல்ல judgement, tone, safety | சின்ன compute; human comparisons மலிவு |

இந்த numbers பொதுவான patterns தான், சரியான எண்கள் இல்லை. ஒவ்வொரு lab-ஓட recipe-உம் வேற, காலப்போக்குல மாறும்.

**Browser-லயே try பண்ணுங்க.** ஒரு reward model preferences-ஐ scores-ஆ மாத்துது. ஒரு pairwise preference எப்படி ஒரு probability ஆகுதுன்னு பாருங்க.

```python
import math

def prefer_probability(score_a, score_b):
    return 1 / (1 + math.exp(-(score_a - score_b)))      # the Bradley-Terry form used in reward modelling

pairs = [("helpful, cites the policy", 2.1, "vague answer", 0.4),
         ("polite refusal", 0.2, "unsafe instructions", -1.5),
         ("short and right", 1.0, "long and right", 0.9)]
for a, sa, b, sb in pairs:
    print(f"P({a!r} preferred over {b!r}) = {prefer_probability(sa, sb):.2f}")
```

## ஒரு example

Hyderabad-ல ஒரு team, சின்ன கடை owners-க்கு bank statements-ஐ Telugu, English-ல explain பண்ற ஒரு bot build பண்றாங்க. ஒவ்வொரு stage-உம் என்ன சேர்க்குதுன்னு பார்க்க, ஒரே open-weight model family-ஓட மூணு versions-ஐ ஒரே prompt-ல compare பண்றாங்க: "Explain this ₹2,350 debit marked NACH".

| Version | Prompt-க்கு என்ன பண்ணுச்சு | ஏன் |
| --- | --- | --- |
| Base model | Forum post மாதிரி இருந்த மூணு வரிகளை எழுதிட்டு, அப்புறம் வேற ஒரு கேள்வி | அது text-ஐ தொடர மட்டும் தான் பண்ணும்; forum posts நிறைய இருக்கு |
| SFT-க்கு அப்புறம் | NACH ஒரு automatic debit, பொதுவா ஒரு loan EMI அல்லது subscription-ன்னு ஒரு நீளமான, formal paragraph-ல சொல்லுச்சு | ஒரு helpful answer-ஓட format-ஐ கத்துக்கிச்சு |
| Preference tuning-க்கு அப்புறம் | அதே explanation-ஐ மூணு குட்டி வரிகள்ல சொல்லுச்சு, bank app-ல mandate list-ஐ check பண்ணச் சொல்லுச்சு, இன்னொரு entry-ஐ explain பண்ணவும் முன்வந்துச்சு | அடுத்த step-ஓட, சுருக்கமான, practical answers-ஐ மக்கள் விரும்பி இருந்தாங்க |

Team chat version-ஐ தங்களோட ஆரம்பப் புள்ளியா எடுக்குது. அப்புறம் அதோட Telugu replies கொஞ்சம் விறைப்பா இருக்கு, சில நேரம் English-க்கு மாறிடுதுன்னு கவனிக்குறாங்க. அந்த gap pre-training-ல இருந்து வருது, அங்க Telugu text அரிதா இருந்துச்சு. Pre-training-ல இருக்குற gap-ஐ எவ்வளவு prompt பண்ணாலும் முழுசா சரி பண்ண முடியாது. அதனால 200 real கேள்விகள்ல ரெண்டு options-ஐ test பண்றாங்க: Telugu examples உள்ள ஒரு கவனமான prompt, அவங்க Telugu பேசுற support staff எழுதின 1,500 replies-ல ஒரு சின்ன SFT run. Public leaderboard-ல இல்லாம, தங்களோட சொந்த test-ல எது நல்லா score பண்ணுதோ அதையே வச்சுக்குறாங்க.

## பொதுவா பண்ற தப்புகள்

- **Base model-ஐ chatbot-ஆ use பண்றது.** அது பதில் சொல்லாம text-ஐ தொடரும். நீங்களே SFT பண்ணப் போறதில்லைன்னா instruct அல்லது chat version-ஐ download பண்ணுங்க.
- **Post-training knowledge-ஐ சேர்க்கும்னு நினைக்கிறது.** அது பெரும்பாலும் behaviour-ஐ தான் மாத்தும். Facts pre-training-ல இருந்தோ run time-ல retrieval-ல இருந்தோ வரும்.
- **RLHF model-ஐ உண்மை பேச வைக்கும்னு நினைக்கிறது.** மக்கள் விரும்புற answers-ஐ அது reward பண்ணும், ஆனா தப்பா இருந்தாலும் confident-ஆ, smooth-ஆ இருக்குற text-ஐ மக்கள் விரும்பலாம்.
- **Refusals-ஐ உங்க prompt-ஓட bug-ஆ எடுத்துக்கிறது.** அளவுக்கு மீறின refusals பெரும்பாலும் preference tuning-ல இருந்து வரும். தெளிவான prompt உதவும், ஆனா சில behaviour model-க்குள்ளயே இருக்கு.
- **Interview-ல DPO-வையும் RLHF-ஐயும் குழப்பிக்கிறது.** ரெண்டும் preference pairs-ல இருந்து கத்துக்கும். RLHF முதல்ல ஒரு reward model-ஐ train பண்ணும்; DPO பண்ணாது.

## Chat models ஏன் இப்படி behave பண்ணுது

தினசரி quirks நிறைய இந்த stages-ல இருந்து வருது.

- **Sycophancy.** Models உங்க கூட ஒத்துப்போக முனையும், ஏன்னா preference tuning-ல ஒத்துப்போற answers அடிக்கடி விரும்பப்பட்டிருக்கு.
- **நீளமான, பஞ்சு வச்ச answers.** Reviewers முழுமையான answers-ஐ reward பண்ணி இருந்தா, நீளமா இருந்தா நல்லதுன்னு model கத்துக்கும்.
- **மொழிகளுக்கு நடுவுல சமமின்மை.** Hindi அல்லது Tamil quality, pre-training-லயும் SFT examples-லயும் அந்த மொழி எவ்வளவு இருந்ததுன்னு சார்ந்தது.
- **Knowledge cut-off.** Pre-training data சேகரிச்ச பிறகு நடந்தது model-க்கு தெரியாது, நீங்க புது தகவல் கொடுத்தா தவிர.

## Demo-ல இருந்து production-க்கு

- **Model card-ஐ படிங்க.** பொதுவா அதுல model எந்த stages-ஐ கடந்தது, என்ன data use ஆச்சு, எந்த மொழிகள் cover ஆச்சுன்னு இருக்கும்.
- **சரியான version-ஐ தேர்ந்தெடுங்க.** Applications-க்கு instruct அல்லது chat versions use பண்ணுங்க. நீங்களே SFT பண்ணப் போறீங்கன்னா, அல்லது plain text completion-க்கு மட்டும் base model use பண்ணுங்க.
- **உங்க மொழிகள்ல test பண்ணுங்க.** உங்க users எழுதுற ஒவ்வொரு மொழியிலும் real கேள்விகள்ல model-ஐ score பண்ணுங்க, கலந்த Hinglish, Tanglish உட்பட.
- **உங்க சொந்த pairs-ஐ வச்சுக்கோங்க.** Reviewers ஒரு reply-ஐ fix பண்ணாலோ ரெண்டு drafts-ல ஒண்ணை தேர்ந்தெடுத்தாலோ, அதை store பண்ணுங்க. பின்னாடி இவை SFT, preference data ஆகும்.
