## இது என்ன

Standard RAG documents-ஐ chunks-ஆ வெட்டி, embed பண்ணி, similarity வச்சு retrieve பண்ணும். நிறைய சின்ன documents-க்கு இது நல்லா work ஆகும். ஆனா 300 pages annual report, ஒரு insurance regulation, ஒரு master services agreement மாதிரி ஒரு நீண்ட, structured document-க்கு அவ்வளவு நல்லா work ஆகாது. ஏன்னா:

- பதில் ஒரு passage எங்க இருக்குங்கறதை சார்ந்து இருக்கு ("standalone statements-ல இல்ல, consolidated statements-ஓட notes-ல");
- Text "section 2.4-ல define பண்ணபடி"ன்னு சொல்லும், ஆனா அந்த definition ரொம்ப தூரத்துல இருக்கும்;
- நிறைய passages ஒரே மாதிரி தெரியும் (ஒவ்வொரு வருஷத்து revenue table), அதனால similarity-ஆல அவற்றை பிரிச்சு பார்க்க முடியாது.

**Vectorless retrieval** document-ஓட structure-ஐ அப்படியே வச்சிருக்கும். Table of contents-ல இருந்து ஒரு tree build பண்றோம் (chapters, sections, sub-sections, ஒவ்வொண்ணுக்கும் சின்ன summary), அப்புறம் model யோசிச்சு கீழ இறங்கும்: top level-ஐ படிக்கும், சரியா இருக்கும்னு தோணுற section-ஐ தேர்ந்தெடுத்து திறக்கும், மறுபடி தேர்ந்தெடுக்கும், கடைசியில தேவையான pages-ஐ படிக்கும். PageIndex மாதிரி open-source projects இந்த idea-வை package பண்ணியிருக்கு.

```flow
title: Annual report FY2026, 320 pages: model-க்கு தேவையான branches-ஐ மட்டும் திறக்கும்
Annual report -> Corporate overview | strategy, products
Annual report -> Directors' report | performance, risks
Annual report -> Standalone statements | parent company மட்டும்
Annual report -[opened: analysts consolidated-ஐ தான் சொல்றாங்க]-> Consolidated statements
Consolidated statements -> Balance sheet, P&L, cash flow
Consolidated statements -[opened]-> Notes
Notes -[opened]-> Note 38 Contingent liabilities | p.241, Note 41-ஐ refer பண்ணுது
Note 38 Contingent liabilities -[opened]-> Note 41 Disputed tax matters | p.247
Note 41 Disputed tax matters -> பதில்ல Note 38, Note 41 cite ஆகுது
```

## இது எப்படி work ஆகுது

**Tree-ஐ ஒரு தடவை build பண்ணுங்க.** Document-ஓட headings-ஐ ஒரு hierarchy-ஆ parse பண்ணுங்க. ஒவ்வொரு node-க்கும் title, page range, சில வரி summary store பண்ணுங்க; summary-ஐ indexing நேரத்துல ஒரு model எழுதலாம். Scan பண்ண அல்லது சரியா format ஆகாத documents-ஐ முதல்ல clean பண்ணணும்; method-க்கு கிடைக்குற structure எவ்வளவு நல்லதோ, அவ்வளவு தான் அதுவும்.

**ஒவ்வொரு கேள்விக்கும் navigate பண்ணுங்க.** Model-க்கு கேள்வியையும், top-level nodes-ஐயும் (titles, summaries மட்டும், இது மலிவு) கொடுங்க. எந்த nodes திறக்கணும், ஏன்னு கேளுங்க. அவற்றை expand பண்ணுங்க, leaf sections வர்ற வரைக்கும் repeat பண்ணுங்க. அப்புறம் அவற்றோட முழு text-ஐ prompt-ல வச்சு, sections, pages-ஐ cite பண்ணி பதில் சொல்ல வைங்க.

**References-ஐ follow பண்ணுங்க.** ஒரு section "see note 14"ன்னு சொன்னா, model அந்த node-ஐ கேக்கலாம். Vectors-ஆல இது முடியாது.

**Cost.** ஒவ்வொரு கேள்விக்கும் வரிசையா பல model calls ஆகும், அதனால ஒரு vector lookup-ஐ விட slow-ஆவும் costly-ஆவும் இருக்கும். Precision தேவைப்படுற, value அதிகமான சில நீண்ட documents-க்கும் கேள்விகளுக்கும் இது பொருந்தும், உதாரணமா ஒரு analyst ஒரு company-ஓட filings பத்தி கேக்குறது. 50,000 support articles-ல search பண்றதுக்கு இது பொருந்தாது; அங்க hybrid search தான் ஜெயிக்கும்.

நிறைய production systems ரெண்டையும் சேர்த்து use பண்ணுது: எந்த documents முக்கியம்னு கண்டுபிடிக்க vector அல்லது keyword search, அப்புறம் ஒவ்வொரு நீண்ட document-க்குள்ளயும் tree navigation.

**Vector RAG vs tree navigation:**

| Factor | Vector RAG | Tree navigation |
| --- | --- | --- |
| எந்த documents-க்கு best | நிறைய சின்னவை | சில நீண்ட, structured ஆனவை |
| Cross-references | Miss ஆகும் | Follow பண்ணும் |
| ஒரே மாதிரி தெரியுற passages | அடிக்கடி குழம்பும் | Tree-ல இருக்குற இடத்தை வச்சு பிரிச்சு பார்க்கும் |
| ஒரு கேள்விக்கு calls | ஒரு search, ஒரு answer | வரிசையா பல |
| Latency | பெரும்பாலும் fast: ஒரு lookup | Slow: ஒவ்வொரு call-க்கும் கூடும் |
| Setup | Chunk பண்ணி embed பண்ணணும் | Headings parse பண்ணி, node summaries எழுதணும் |

**Tree-ஐ check பண்ணுங்க.** Method-ஐ நம்புறதுக்கு முன்னாடி, ஒவ்வொரு document-க்கும் tree-ஐ print பண்ணி, உண்மையான table of contents-ஓட ஒப்பிடுங்க. Headings detect ஆகாததால flat-ஆ இருக்குற trees, page ranges overlap ஆகுற sections, வெளிப்படையா இல்லாத summaries இதெல்லாம் தேடுங்க. முக்கியமான சில documents-ஓட tree-ஐ கையால fix பண்றது பெரும்பாலும் worth தான், ஏன்னா அதே documents-ஐ நிறைய தடவை query பண்ணுவாங்க.

**Node summaries எழுதுறது.** நல்ல summaries ஒரு section-ல என்ன இருக்குன்னு சொல்லும், அது என்ன வாதாடுதுன்னு இல்லை: "Contingent liabilities by type, both years, with references to tax notes" model தேர்ந்தெடுக்க உதவும்; "Discusses the company's risks" உதவாது. Users கேக்குற key terms-ஐ சேர்த்துக்குங்க, உதாரணமா taxes, schemes, contract parties-ஓட பெயர்கள்.

**PDF-ஓட bookmarks-ல இருந்து tree build பண்ணுங்க.** நிறைய நீண்ட PDFs-ல PyMuPDF படிக்கக்கூடிய ஒரு table of contents இருக்கும்:

```python
import fitz

def build_tree(pdf_path):
    doc = fitz.open(pdf_path)
    toc = doc.get_toc()                         # [[level, title, page], ...]
    nodes = []
    for i, (level, title, page) in enumerate(toc):
        end = next((p - 1 for l, _, p in toc[i + 1:] if l <= level), doc.page_count)
        nodes.append({"id": f"n{i}", "level": level, "title": title.strip(),
                      "pages": (page, max(page, end)), "summary": None})
    return doc, nodes

def text_of(doc, node):
    a, b = node["pages"]
    return "\n".join(doc[p - 1].get_text() for p in range(a, b + 1))
```

`get_toc()` empty-ஆ வந்தா, font size வச்சு headings-ஐ detect பண்ணுங்க, அல்லது முக்கியமான documents-க்கு முதல் ரெண்டு levels-ஐ கையால எழுதுங்க. ஒவ்வொரு node-ஓட `summary`-யையும் indexing நேரத்துல ஒரு தடவை ஒரு model நிரப்பும்.

**Navigation loop.** Titles, summaries-ஐ காட்டி, model nodes-ஐ தேர்ந்தெடுக்க விட்டு, அவற்றை திறந்து, ஒரு cap-ல நிறுத்துங்க:

```python
import json

def children(nodes, parent):
    if parent is None:
        return [n for n in nodes if n["level"] == 1]
    i = nodes.index(parent)
    out = []
    for n in nodes[i + 1:]:
        if n["level"] <= parent["level"]:
            break
        if n["level"] == parent["level"] + 1:
            out.append(n)
    return out

def navigate(question, doc, nodes, choose, answer, max_open=6):
    """choose(question, options) -> {"open": [ids], "done": bool}, as structured output."""
    frontier, gathered, opened = children(nodes, None), [], 0
    while frontier and opened < max_open:
        menu = [{"id": n["id"], "title": n["title"], "pages": n["pages"], "summary": n["summary"]} for n in frontier]
        pick = choose(question, json.dumps(menu, ensure_ascii=False))
        chosen = [n for n in frontier if n["id"] in pick["open"]][: max_open - opened]
        if not chosen:
            break
        next_frontier = []
        for n in chosen:
            opened += 1
            kids = children(nodes, n)
            if kids:
                next_frontier += kids
            else:
                gathered.append((n["title"], n["pages"], text_of(doc, n)))
        if pick.get("done"):
            break
        frontier = next_frontier
    if not gathered:
        return "I could not find a section that answers this.", []
    return answer(question, gathered), [(t, p) for t, p, _ in gathered]
```

காட்டுன ஒவ்வொரு menu-வையும், எடுத்த ஒவ்வொரு choice-யையும் log பண்ணுங்க. ஒரு பதில் தப்பா வந்தா, model எங்க தப்பான பக்கம் திரும்புச்சுன்னு log-ல அப்படியே தெரியும்.

**References-ஐ follow பண்றது.** Gathered text-ல "see Note 14" இருந்தா, அந்த node child இல்லைன்னாலும் அதை அடுத்த menu-ல சேர்த்துடுங்க. Gathered text மேல "Note \d+", "Section \d+(\.\d+)*", "Schedule [IVX]+" மாதிரி ஒரு simple regex போட்டா, பெரும்பாலான annual reports, circulars-க்கு போதும்.

**Search-ஓட mix பண்ணுங்க.** நீண்ட documents நிறைய இருக்குற ஒரு library-க்கு, document titles, node summaries மேல keyword அல்லது vector search பண்ணி document-ஐயும் ஒரு starting node-ஐயும் தேர்ந்தெடுத்து, அப்புறம் அதுக்குள்ள navigate பண்ணுங்க.

## ஒரு example

Mumbai-ல ஒரு equity research team கேக்குறாங்க: "FY2026 முடிவுல disputed GST demands-க்கான contingent liability எவ்வளவு, அது வளர்ந்திருக்கா?"

Annual report 320 pages. சாதாரண vector search GST, contingent liabilities பத்தி சொல்ற அஞ்சு chunks-ஐ கொண்டு வருது: standalone statements, consolidated statements, directors' report, முந்தின வருஷ comparison column-ல இருந்து. Model standalone, consolidated figures-ஐ கலந்து தப்பான பதில் சொல்லுது.

Tree navigation-ஓட:

1. Model top level-ஐ பார்க்குது: Corporate overview, Directors' report, Standalone financial statements, Consolidated financial statements. Analysts வேற சொல்லலைன்னா consolidated-ஐ தான் சொல்றாங்க, அதனால அதை திறக்குது.
2. உள்ள: Balance sheet, Profit and loss, Cash flow, Notes. Notes-ஐ திறந்து, அப்புறம் "Note 38: Contingent liabilities and commitments"-ஐ திறக்குது.
3. அந்த note-ல ரெண்டு வருஷத்துக்கும் ஒரு table இருக்கு, disputed tax details-க்கு Note 41-ஐ refer பண்ணுது. Model Note 41-யையும் திறக்குது.

பதில் Note 38 (page 241), Note 41 (page 247) ரெண்டையும் cite பண்ணி, ரெண்டு வருஷ figures-ஐயும் ஒரே table-ல இருந்து கொடுக்குது. அஞ்சு model calls, சுமார் ஒன்பது seconds ஆச்சு; vector RAG-க்கு ரெண்டு seconds-க்கும் குறைவு. Page-ஓட ஒப்பிட்டு பார்க்கக்கூடிய சரியான பதிலுக்கு team காத்திருக்க தயார்.

| Approach | சரியா | Calls | Time |
| --- | --- | --- | --- |
| Vector RAG | இல்லை: standalone, consolidated figures கலந்துடுச்சு | 2 | 2 s-க்கும் குறைவு |
| Tree navigation | ஆமா, ரெண்டு வருஷமும், page citations-ஓட | 5 | சுமார் 9 s |

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்துக்கும் use பண்றது.** நிறைய சின்ன documents-க்கு tree search slow-ஆவும் costly-ஆவும் இருக்கும், பலன் இல்லை.
- **உடைஞ்ச table of contents-ஐ நம்புறது.** Scan பண்ண அல்லது சரியா tag ஆகாத PDFs flat அல்லது தப்பான tree கொடுக்கும். நம்புறதுக்கு முன்னாடி tree-ஐ check பண்ணுங்க.
- **Model சுத்திக்கிட்டே இருக்க விடுறது.** ஒரு கேள்விக்கு திறக்கக்கூடிய nodes-க்கு cap வைங்க, இல்லன்னா cost, latency எல்லையில்லாம கூடும்.
- **Evaluation-ஐ skip பண்றது.** அதே golden set-ல உங்க hybrid RAG-ஓட compare பண்ணுங்க; ஒரு method smart-ஆ கேக்குதுங்கறதுக்காக adopt பண்ணாதீங்க.
- **Page numbers-ஐ இழக்கிறது.** Page, section citations தான் முக்கிய பலன்; ஒவ்வொரு step-லயும் அவற்றை வச்சிருங்க.
- **Node openings-க்கு cap இல்லாம இருக்கிறது**, அப்போ கஷ்டமான கேள்விகள் சுத்தி சுத்தி cost ஏத்தும்.
- **Print பண்ணி check பண்ணாத tree-ஐ நம்புறது**, உண்மையான table of contents-ஓட ஒப்பிடாம.

## எப்போ vectors-ஐ use பண்ணணும்

- **நிறைய சின்ன documents**, FAQs அல்லது support articles மாதிரி: hybrid search fast-ஆவும் மலிவாவும் இருக்கும்.
- **உண்மையான structure இல்லாத documents**, chat logs அல்லது emails மாதிரி.
- **Latency budget இறுக்கமா இருக்கும்போது**, வரிசையா பல calls ரொம்ப slow-ஆ இருக்கும் இடத்துல.

## Demo-ல இருந்து production-க்கு

- **Ingestion-க்கு அப்புறம் ஒவ்வொரு document-ஓட tree-ஐ check பண்ணுங்க**, முக்கியமானவற்றை கையால fix பண்ணுங்க.
- **ஒரு கேள்விக்கு openings, time-க்கு cap வைங்க**, தெளிவான "not found" பதிலோட.
- **ஒவ்வொரு கேள்விக்கும் menus, choices-ஐ log பண்ணுங்க.**
- **ஒரே document version-ல திரும்ப வர்ற கேள்விகளுக்கு answers-ஐ cache பண்ணுங்க.**
- **ஒரு document-ஓட புது version வந்தா trees, summaries-ஐ re-build பண்ணுங்க.**

## Practice பண்ணுங்க

PageIndex introduction-ஐ படிங்க, tree எப்படி build ஆகுதுன்னு அவங்க docs-ஐ ஒரு தடவை ஓட்டி பாருங்க.

1. ஒரு நீண்ட public document எடுங்க, உதாரணமா ஒரு listed company-ஓட annual report அல்லது ஒரு regulator-ஓட master circular. Headings-ஓட page ranges-ஓட ஒரு tree build பண்ணுங்க; தேவைன்னா முதல் ரெண்டு levels-ஐ கையால.
2. சரியான section வேணும்ங்குற பத்து கேள்விகள் எழுதுங்க, அதுல ரெண்டு cross-reference தேவைப்படுறதா இருக்கணும்.
3. அவற்றை உங்க hybrid RAG-ஆலயும், ஒரு simple navigate-the-tree loop-ஆலயும் (அதிகபட்சம் ஆறு node openings) பதில் சொல்ல வைங்க. Correctness, latency, cost-ஐ compare பண்ணுங்க.
4. உங்க document-ஓட tree-ஐ print பண்ணி, print பண்ண table of contents-ஓட ஒப்பிட்டு, கண்டுபிடிக்குற முதல் மூணு வித்தியாசங்களை fix பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க test-ல எந்த வகை கேள்வி, document-க்கு tree navigation ஜெயிச்சுது, அதுக்கு என்ன cost ஆச்சுன்னு சொல்ல முடியும்.
