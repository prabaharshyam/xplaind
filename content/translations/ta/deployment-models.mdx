## இது என்ன

ஒரு **deployment model** ரெண்டு கேள்விகளுக்கு பதில் சொல்லுது: model-உம் application-உம் எங்க ஓடுது, அவற்றை யார் கட்டுப்படுத்துறாங்க? குறைந்த control-ல இருந்து அதிக control வரைக்கும் முக்கிய options:

1. **Vendor API (multi-tenant SaaS)**: model provider-ஓட public endpoint-ஐ call பண்றீங்க. ஆரம்பிக்க வேகம், புது models, குறைவான control.
2. **Client-ஓட cloud வழியா model**: அதே அல்லது ஒத்த models, client-ஓட சொந்த cloud account, region-க்குள்ள (Amazon Bedrock, Azure AI Foundry, Google Vertex AI), அவங்களுக்கு ஏற்கனவே இருக்குற cloud contract-ஓட.
3. **Dedicated அல்லது private capacity**: reserve பண்ண capacity அல்லது ஒரு private endpoint, சில நேரம் traffic public internet-ஐ தொடாத private networking-ஓட.
4. **Client-ஓட cloud-ல self-hosted open-weight models**: Llama, Qwen, Mistral, Gemma variants மாதிரி models-ஐ அவங்க account-ல இருக்குற GPU machines-ல நீங்க ஓட்டுறீங்க.
5. **On-premises**: அதே, client-ஓட சொந்த data centre-ல.
6. **Air-gapped**: வெளி networks-ஓட எந்த connection-உம் இல்லை. Models, code, updates கட்டுப்படுத்தப்பட்ட transfer வழியா வரும்.

Application-ஐயும் (API, retrieval, database) model-ஐ பொறுத்து இல்லாம, இதே தேர்வுகளை தனியா follow பண்ண வைக்கலாம்.

```flow
dir: LR
title: குறைவான control, வேகமான ஆரம்பத்துல இருந்து, அதிக control, அதிக வேலை வரைக்கும்
Vendor API | வாரங்கள் -> Client-ஓட cloud | approve ஆன tenancy, region
Client-ஓட cloud -> Dedicated | private network
Dedicated -> Self-hosted | அவங்க GPUs, நீங்க operate பண்றீங்க
Self-hosted -> On-prem | அவங்க data centre
On-prem -> Air-gapped | network இல்லை, transfers மட்டும்
```

App, retrieval, logs, model-ஐ விட வேற rung-ல இருக்கலாம்.

இந்த lesson, Bengaluru, Mumbai, Hyderabad-ல இருக்குற மூணு clients-ஐ follow பண்ணுது; ஒவ்வொருத்தருக்கும் வேற deployment தேவைப்பட்டுச்சு.

## இது எப்படி work ஆகுது

**தேர்வை எது முடிவு பண்ணுது.**

- *Data rules*: data எங்க போகலாம்ங்கிறதை பத்தின regulation, contracts, internal policy. இந்திய regulators-உம் நிறைய enterprises-உம் data இந்தியாவுக்குள்ளயே இருக்கணும்னு கேக்குறாங்க; சில data premises-ஐ விட்டு போகவே கூடாது.
- *தேவையான model quality*: strongest models பெரும்பாலும் APIs-ஆ அல்லது cloud partners வழியா மட்டும் கிடைக்கும். Open-weight models நிறைய tasks-க்கு பின்னாடியே நெருக்கமா வருது; extraction, classification, நல்லா வரையறுக்கப்பட்ட documents மேல RAG-க்கு சரியா இருக்கும்.
- *Cost, volume*: APIs ஒரு token-க்கு charge பண்ணும்; self-hosting-ல ஒரு பெரிய fixed GPU cost இருக்கு, அது அதிக, நிலையான volume-ல மட்டும் பலன் தரும்.
- *Skills*: self-hosting-க்கு GPUs, serving engines, monitoring, upgrades-ஐ நடத்தத் தெரிஞ்ச ஆட்கள் வேணும்.
- *Latency, availability*: on-premises network delay-ஐ குறைக்கலாம், ஆனா uptime-ஐ client-ஓட team தலைல போடும்.

**ஆரம்பத்துலயே கேக்க வேண்டிய கேள்விகள்.** Data எங்க process ஆகலாம்? ஏற்கனவே approve ஆன provider யாராவது இருக்காங்களா? ஏற்கனவே ஒரு cloud contract இருக்கா? Handover-க்கு அப்புறம் இந்த system-ஐ யார் நடத்துவாங்க? Model-ஐ upgrade பண்ண வேண்டியிருக்கும்போது என்ன நடக்கும்?

**Hybrid பொதுவானது.** Sensitive requests-ஐ ஒரு self-hosted model-க்கு route பண்ணி, மத்தவற்றை ஒரு API-க்கு; அல்லது embeddings-க்கு ஒரு self-hosted model-ஐயும், generation-க்கு ஒரு cloud model-ஐயும் use பண்ணுங்க.

**Air-gapped-ஓட specifics.** Package downloads இல்லை, model downloads இல்லை, SaaS monitoring இல்லை, internet வழியா license checks இல்லை. எல்லாமே (container images, model weights, Python packages) bundle பண்ணி, scan பண்ணி, transfer ஆகும். Updates-ஐ scheduled releases-ஆ plan பண்ணுங்க.

**Options-ஐ score பண்றது:**

| Factor | Vendor API | Client-ஓட cloud | Self-hosted | Air-gapped |
| --- | --- | --- | --- | --- |
| Data control | மிகக் குறைவு | அதிகம், அவங்க tenancy-ல | மிக அதிகம் | முழுசா |
| Model quality | Strongest | Strong | நல்ல open-weight | நல்ல open-weight |
| குறைந்த volume-ல cost | மிகக் குறைவு | குறைவு | அதிகம்: idle GPUs | மிக அதிகம் |
| Launch நேரம் | நாட்கள்-வாரங்கள் | வாரங்கள் | மாசங்கள் | மாசங்கள் |
| தேவையான skills | கொஞ்சம் | Cloud skills | GPU serving, monitoring | அவை எல்லாம், offline-ல |

**முதல் meeting-ல கேக்க வேண்டிய கேள்விகள்.** இந்த data எங்க process ஆகலாம், ஏற்கனவே approve ஆன provider யாராவது இருக்காங்களா? ஏற்கனவே ஒரு cloud contract, region இருக்கா? எந்த data, இருந்தா, premises-ஐ விட்டு ஒருபோதும் போகக்கூடாது? Handover-க்கு அப்புறம் இந்த system-ஐ யார் நடத்துவாங்க, அவங்களுக்கு GPU skills இருக்கா? Model-ஐ எவ்வளவு அடிக்கடி upgrade பண்ணணும், அதை யார் approve பண்றாங்க? பதில்கள் பெரும்பாலும் ஆறு options-ஐ ஒரு மணி நேரத்துக்குள்ள ஒண்ணு ரெண்டா சுருக்கிடும்.

**Offline sites-க்கு bill of materials.** ஒரு air-gapped build-க்கு, ஒவ்வொரு artefact-ஐயும் list பண்ணுங்க: pinned versions இருக்குற container images, checksums இருக்குற model weights, Python, system packages, vector database, offline-ல வேலை செய்யுற monitoring tools, documentation. Client-ஓட security team அவற்றை scan பண்ணி transfer பண்ணும். ஒரு package விடுபட்டா ஒரு release வாரக்கணக்குல தாமதமாகலாம், அதனால உண்மையான visit-க்கு முன்னாடி, connect ஆகாத ஒரு test machine-ல install-ஐ rehearse பண்ணுங்க.

**API vs self-hosted, numbers-ல.** உண்மையான quotes வச்சு திரும்ப பண்ணக்கூடிய முதல் ஒப்பீடு (ஒவ்வொரு price-ஓட தேதியையும் record பண்ணுங்க):

```python
def monthly_costs(tokens_in_m, tokens_out_m, api_in_usd, api_out_usd,
                  gpu_hour_inr, gpus, hours=730, ops_people=0.5, ops_cost_inr=250_000, usd_to_inr=84):
    """tokens in millions per month; API prices in USD per million tokens."""
    api = (tokens_in_m * api_in_usd + tokens_out_m * api_out_usd) * usd_to_inr
    self_host = gpu_hour_inr * gpus * hours + ops_people * ops_cost_inr
    return {"API ₹/month": round(api), "self-hosted ₹/month": round(self_host),
            "cheaper": "API" if api < self_host else "self-hosted"}

print(monthly_costs(tokens_in_m=900, tokens_out_m=120, api_in_usd=0.8, api_out_usd=4,
                    gpu_hour_inr=250, gpus=2))
```

GPUs use ஆனாலும் ஆகாட்டியும் ஒவ்வொரு மணி நேரமும் பணம் செலவழிக்கும், அதனால self-hosting அதிக, நிலையான volume-ல, அல்லது data rules வேற வழி விடாதப்போ மட்டும் ஜெயிக்கும். ஆட்களையும் கணக்கில சேருங்க: serving stack-ஐ யாராவது patch பண்ணி, monitor பண்ணி, upgrade பண்ணணும்.

**Sensitivity வச்சு route பண்ணுங்க.** ஒரு hybrid design-ல, ஒவ்வொரு request-உம் எங்க போகணும்னு ஒரு சின்ன rule முடிவு பண்ணும்:

```python
SENSITIVE_FIELDS = {"aadhaar", "pan", "medical_history", "bank_account"}

def route(request):
    if request.get("classification") == "restricted" or SENSITIVE_FIELDS & set(request.get("fields", [])):
        return "self_hosted"            # stays on the client's servers
    return "cloud_model"                # stronger model, client's cloud region
```

Rule-ஐ client-ஓட data owner-ஓட சேர்ந்து எழுதுங்க, ஒவ்வொரு data class-ல இருந்தும் examples வச்சு test பண்ணுங்க, ஒவ்வொரு request-க்கும் route-ஐ log பண்ணுங்க.

**ஒரு air-gapped bundle build பண்றது.** Connect ஆன ஒரு build machine-ல, எல்லாத்தையும் versions, checksums-ஓட சேகரிச்சு, client-ஓட approve ஆன process வழியா transfer பண்ணுங்க:

```bash
mkdir -p bundle/{images,models,wheels}
docker pull vllm/vllm-openai:v0.10.1 && docker save vllm/vllm-openai:v0.10.1 | gzip > bundle/images/vllm.tar.gz
docker save claims-api:1.4.0 | gzip > bundle/images/claims-api.tar.gz
huggingface-cli download org/model-8b-instruct --revision <commit> --local-dir bundle/models/model-8b
pip download -r requirements.txt -d bundle/wheels
(cd bundle && find . -type f -exec sha256sum {} \; > SHA256SUMS)
```

Offline பக்கம், `sha256sum -c SHA256SUMS` transit-ல எதுவும் மாறலைன்னு நிரூபிக்கும், `docker load` images-ஐ restore பண்ணும், `pip install --no-index --find-links wheels -r requirements.txt` internet இல்லாம install பண்ணும். உண்மையான visit-க்கு முன்னாடி, networking disable பண்ண ஒரு machine-ல முழு install-ஐயும் rehearse பண்ணுங்க.

**ஆரம்பத்துல இருந்தே upgrades-ஐ plan பண்ணுங்க.** ஒவ்வொரு option-க்கும் புது model versions-க்கு ஒரு வழி வேணும்: ஒரு API தானா மாறும் (pin பண்ணி test பண்ணுங்க), client-ஓட cloud தன்னோட schedule-ல models-ஐ சேர்க்கும், self-hosted அல்லது offline setups-க்கு திரும்ப திரும்ப பண்ணக்கூடிய bundle-and-test process வேணும்.

## ஒரு worked example

மூணு clients, மூணு பதில்கள்:

- *Bengaluru-ல ஒரு D2C brand*: customer-support assistant, public-facing data மட்டும், சின்ன team. ஒரு gateway வழியா **Vendor API**, கிடைக்குற இடத்துல இந்திய region. மூணு வாரத்துல live.
- *Mumbai-ல ஒரு private bank*: ரகசியமான documents-ஓட ஒரு internal policy assistant. Bank-ஓட risk team ஏற்கனவே Central India-ல அதோட Azure tenancy-ஐ approve பண்ணியிருக்கு. Private networking, bank-ஓட keys-ஓட **Client-ஓட cloud வழியா models**. புதுசா எதையும் approve பண்ண வேண்டியதில்லாததால, approval ஆறு மாசத்துக்கு பதிலா நாலு வாரம் எடுத்துச்சு.
- *Hyderabad-ல ஒரு defence electronics supplier*: ஒரு classified network-ல engineering-document search. **Air-gapped self-hosting**: ரெண்டு on-premises GPU servers-ல vLLM-ஓட serve பண்ண ஒரு open-weight model, அதே network-ல embeddings, vector database, client-ஓட security team scan பண்ணி transfer பண்ற images, weights-ஓட ஒரு காலாண்டு update package. Model frontier APIs-ஐ விட குறைவான திறன் உள்ளது, அதனால scope retrieval, summarisation-க்கு சுருக்கப்பட்டிருக்கு, அங்க evals அது நல்லா செயல்படுதுன்னு காட்டுது.

| Client | Deployment | ஏன் | Outcome |
| --- | --- | --- | --- |
| Bengaluru D2C brand | Gateway வழியா Vendor API | Public data, சின்ன team | மூணு வாரத்துல live |
| Mumbai private bank | அதோட approve ஆன Azure tenancy-ல models | ரகசிய documents, ஏற்கனவே இருக்குற approval | நாலு வாரத்துல approve ஆச்சு |
| Hyderabad defence supplier | Local GPUs-ல Air-gapped vLLM | Classified network | Scope retrieval, summaries-க்கு சுருக்கப்பட்டது |

## பொதுவா பண்ற தப்புகள்

- **Data rules பத்தி கேக்குறதுக்கு முன்னாடி ஒரு public API-ஐ propose பண்றது.** வாரங்களையும் நம்பகத்தன்மையையும் இழப்பீங்க.
- **Self-hosting மலிவுன்னு நினைக்கிறது.** குறைந்த volume-ல idle GPUs, tokens-ஐ விட ரொம்ப செலவு.
- **யார் operate பண்ணுவாங்கன்னு கண்டுக்காம இருக்கிறது.** Client-ல யாராலும் upgrade பண்ண முடியாத ஒரு self-hosted model ஒரு சுமை ஆகும்.
- **"Open-weight"-ஐ "licence terms இல்லை"ன்னு எடுத்துக்கிறது.** Commercial use limits-க்கு ஒவ்வொரு model-ஓட licence-ஐயும் படிங்க.
- **Stack-ஓட மீதியை மறக்குறது.** Traces, logs, vector stores, model-க்கு இருக்குற அதே rules-ஐ follow பண்ணணும்.
- **Idle hours-ஐயும் நடத்துற ஆட்களையும் கணக்கிடாம GPU cost-ஐயும் API cost-ஐயும் compare பண்றது.**
- **Offline-ல ஒருபோதும் rehearse பண்ணாத air-gapped installs**, முதல் missing package-லயே fail ஆகும்.
- **Self-hosted, offline setups-ல models-க்கு upgrade path இல்லாம இருக்கிறது.**

## தேர்வு எளிதா இருக்கும் நேரங்கள்

- **குறைவான அல்லது உறுதியில்லாத volume, கடுமையான data rules இல்லை**: ஒரு API அல்லது client-ஓட cloud model service-ல ஆரம்பிங்க.
- **Data premises-ஐ விட்டு ஒருபோதும் போகக்கூடாது**: cost எவ்வளவு ஆனாலும், self-hosted அல்லது air-gapped.
- **Value-ஐ நிரூபிக்க ஒரு pilot**: அனுமதிக்கப்பட்ட வேகமான option-ஐ use பண்ணி, scale பண்றதுக்கு முன்னாடி திரும்ப பாருங்க.

## Demo-ல இருந்து production-க்கு

- **Data rules-ஐயும் முடிவையும்** தேதிகள், ஒத்துக்கொண்ட ஆட்களோட பதிவு பண்ணுங்க.
- முதல் சில மாசங்களுக்கு அப்புறம், உண்மையான volumes-ஓட **cost comparison-ஐ திரும்ப பண்ணுங்க**.
- Hybrid setups-ல ஒவ்வொரு request-க்கும் **route-ஐ log பண்ணுங்க**.
- Offline, self-hosted upgrades-க்கு **test பண்ண ஒரு bundle process-ஐ வச்சிருங்க**.
- எந்த option-ஐ தேர்ந்தெடுத்தாலும் **model versions-ஐ pin பண்ணி test பண்ணுங்க**.

## Practice பண்ணுங்க

ஒரு cloud provider-ஓட model service data privacy page-ஐயும், self-hosting பக்கத்துக்கு vLLM launch post-ஐயும் படிங்க.

1. நீங்க தேர்ந்தெடுத்த ஒரு client-க்கு நாலு deployment models-ஓட ஒரு பக்க ஒப்பீடு எழுதுங்க, data control, model quality, அவங்க volume-ல cost, launch நேரம், தேவையான skills-ஐ score பண்ணி.
2. அவற்றுக்கு இடையில தேர்ந்தெடுக்க, முதல் meeting-ல நீங்க கேக்குற கேள்விகளை list பண்ணுங்க.
3. உங்க RAG app-ஓட air-gapped version-க்கு bill of materials-ஐ வரைங்க: நீங்க transfer பண்ண வேண்டிய ஒவ்வொரு image, package, weight file-உம்.
4. monthly_costs-ஐ உங்க சொந்த volumes-ஓட மூணு traffic levels-ல ஓட்டி, self-hosting ஏறத்தாழ எங்க பலன் தர ஆரம்பிக்கும்னு கண்டுபிடிங்க.
