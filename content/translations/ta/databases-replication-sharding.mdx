## இது என்ன

பெரும்பாலான systems தங்களோட முக்கியமான data-வை ஒரு **database**-ல வச்சிருக்கும். Product வளரும்போது முதல்ல திணறுறது பெரும்பாலும் database தான். ஏன்னா ஒவ்வொரு app server-உம் அதோட பேசுது, அதோட data-வும் சரியா இருக்கணும். நாலு ideas உங்களை ரொம்ப தூரம் கூட்டிட்டு போகும்.

- **Model-ஐ choose பண்றது.** PostgreSQL, MySQL மாதிரி relational (SQL) databases data-வை relationships இருக்குற tables-ல வச்சு, transactions-ஐ support பண்ணும். DynamoDB, MongoDB, Cassandra மாதிரி NoSQL databases அதுல கொஞ்சத்தை விட்டுட்டு, easy horizontal scale-ஐயோ flexible documents-ஐயோ கொடுக்கும்.
- **Indexes**, தேர்ந்தெடுத்த columns-ஓட sorted structure-ஐ வச்சு lookups-ஐ வேகமாக்கும்.
- **Replication**, reads-ஐ பிரிக்கவும் failures-ஐ தாங்கவும், data-வோட copies-ஐ பல servers-ல வைக்கும்.
- **Sharding**, ஒரு database போதாதப்போ data-வையே பல databases-ல பிரிக்கும்.

```flow
App servers -[எழுதுறது]-> Primary
Primary -[replication, lag ஆகலாம்]-> Replica 1
Primary -[replication, lag ஆகலாம்]-> Replica 2
App servers -[படிக்கிறது]-> Replica 1
```

## இது எப்படி work ஆகுது

**Access pattern படி model-ஐ தேர்ந்தெடுங்க.** பெரும்பாலான products-க்கு relational database தான் strong default: orders, users, payments-ல தெளிவான relationships இருக்கு, transactions தேவை, flexible queries-ஆல பலன் கிடைக்கும். பெரிய write scale-உம் simple key lookups-உம் வேணும்னா, flexible document வடிவம் வேணும்னா, time-series data-னா NoSQL பொருந்தும். நிறைய systems ரெண்டையும் use பண்ணும்: core data-க்கு PostgreSQL, அடிக்கடி தேவைப்படுற simple data-க்கு Redis அல்லது ஒரு key-value store.

**Indexes** ஒரு புத்தகத்தோட பின்னாடி இருக்குற index மாதிரி வேலை செய்யும். Index இல்லன்னா ஒரு customer-ஓட orders-ஐ கண்டுபிடிக்க ஒவ்வொரு row-வையும் scan பண்ணணும்: O(n). `customer_id`-ல ஒரு B-tree index இருந்தா, database நேரா சரியான rows-க்கு, கிட்டத்தட்ட O(log n)-ல போயிடும். `(customer_id, created_at)`-ல ஒரு **composite index** இருந்தா, அவற்றை time படி sort ஆனதாவே திருப்பும். Indexes storage-ஐ சாப்பிடும், writes-ஐ மெதுவாக்கும். அதனால உண்மையான query patterns-க்கு மட்டும் சேருங்க, queries அவற்றை use பண்றாங்களான்னு `EXPLAIN` வச்சு check பண்ணுங்க.

**Replication** ஒவ்வொரு மாற்றத்தையும் ஒரு **primary**-ல இருந்து ஒண்ணு அல்லது அதிக **replicas**-க்கு copy பண்ணும். Writes primary-க்கு போகும்; reads replicas-க்கு போகலாம். இது read load-ஐ பிரிக்கும், primary fail ஆனா ஒரு replica பொறுப்பை எடுத்துக்க உதவும். பெரும்பாலான replication asynchronous, அதனால replicas milliseconds அல்லது seconds பின்தங்கலாம். அதனால தான் அந்த பழைய bug வருது: ஒரு user ஏதோ save பண்ணுவாங்க, அடுத்த screen-ல அது தெரியாது. Fix: user-ஓட சொந்த புது writes-ஐ primary-ல இருந்தே படிக்கிறது.

**Sharding** ஒரு பெரிய table-ஐ ஒரு **shard key** படி பல independent databases-ல பிரிக்கும். ஒரே key value இருக்குற எல்லா rows-உம் ஒரே shard-ல இருக்கும். நல்ல key data-வையும் traffic-ஐயும் சமமா பரப்பும், ஒரு request-க்கு தேவையானதை ஒரே shard-ல வச்சிருக்கும். Sharding உண்மையான complexity-ஐ சேர்க்கும்: shards முழுக்க queries மெதுவா இருக்கும், shards முழுக்க transactions கஷ்டம், shards சேர்க்கும்போது data-வை நகர்த்துறதுக்கு கவனம் தேவை. Indexes, caching, replicas போதாதப்போ தான் இதை பண்ணுங்க.

| Technique | எதை solve பண்ணும் | Cost |
|---|---|---|
| Index | மெதுவான lookups, sorts | storage, மெதுவான writes |
| Read replicas | அதிக reads; failover | replication lag, அதிக servers |
| Vertical scaling | எல்லாத்தையும், கொஞ்ச நாளைக்கு | விலை, ஒரு உச்சம் |
| Sharding | ஒரு server-க்கு அதிகமான data அல்லது writes | சிக்கலான queries, rebalancing, cross-shard transactions |
| Caching (அடுத்த lesson) | அடிக்கடி வர்ற hot data-வோட repeated reads | பழைய data, invalidation |

**Browser-லயே try பண்ணுங்க.** Consistent hashing-ல ஒரு shard சேர்க்கும்போது கொஞ்சம் keys மட்டும் நகரும். ஓட்டி பார்த்து compare பண்ணுங்க.

```python
import hashlib, bisect

def ring(shards, points=50):
    r = sorted((int(hashlib.md5(f"{s}-{i}".encode()).hexdigest(), 16), s) for s in shards for i in range(points))
    return [h for h, _ in r], [s for _, s in r]

def lookup(key, hashes, owners):
    h = int(hashlib.md5(key.encode()).hexdigest(), 16)
    return owners[bisect.bisect(hashes, h) % len(hashes)]

keys = [f"user-{i}" for i in range(10_000)]
before = {k: lookup(k, *ring(["A", "B", "C"])) for k in keys}
after = {k: lookup(k, *ring(["A", "B", "C", "D"])) for k in keys}
moved = sum(before[k] != after[k] for k in keys)
print(f"{moved / len(keys):.0%} of keys moved when adding shard D")
```

## ஒரு worked example

Fatima-வோட team இந்தியா முழுக்க concerts, events-க்கு ஒரு ticketing platform நடத்துது. `bookings` table 30 crore rows ஆகி, pages மெதுவாகிட்டு இருந்துச்சு.

**Step 1: indexes.** "My bookings" screen `SELECT * FROM bookings WHERE user_id = ? ORDER BY created_at DESC LIMIT 20` ஓட்டுச்சு. `EXPLAIN` full table scan-ஐ காட்டுச்சு. `(user_id, created_at)`-ல ஒரு composite index போட்டதும் 4 seconds-ல இருந்து 3 milliseconds ஆச்சு.

**Step 2: read replicas.** Events browse பண்றதும் bookings பார்க்குறதும் traffic-ல 90%. ரெண்டு replicas சேர்த்து அந்த reads-ஐ அங்க route பண்ணாங்க; seat holds-உம் payments-உம் primary-லயே இருந்துச்சு. Primary CPU 85%-ல இருந்து 30%-க்கு குறைஞ்சுது. கொஞ்ச நாள்ல support tickets வந்துச்சு: "Book பண்ணேன் ஆனா என் ticket தெரியல." Busy sales-ல replica lag இரண்டு seconds வரை இருந்துச்சு. அதனால app-ஐ மாத்தினாங்க: ஒரு user book பண்ணதுக்கு அப்புறம் 30 seconds-க்கு, அவங்க bookings-ஐ primary-ல இருந்தே படிக்கணும்.

**Step 3: sharding, அப்புறம்.** ஒரு வருஷம் கழிச்சு, ஒரு superstar-ஓட tour sale-ல writes ஒரு primary தாங்குறதை தாண்டிடுச்சு. `user_id` படி bookings-ஐ shard பண்ணாங்க; writes சமமா பரவுச்சு, ஒவ்வொரு user-ஓட history-உம் ஒரே shard-ல இருந்துச்சு. `event_id` படி shard பண்ணலாமான்னு யோசிச்சாங்க, ஆனா ஒரு hit tour-ஓட எல்லா bookings-உம் ஒரே shard-ல விழுந்து அதை overload பண்ணியிருக்கும்; அதுக்கு **hot shard**-ன்னு பேரு. ஒவ்வொரு event-ஓட seat inventory தனியா, சின்ன table-ல, தன் சொந்த database-ல இருந்துச்சு. ஏன்னா seat holds-க்கு ஒரு event-க்குள்ள strong consistency தேவைப்பட்டுச்சு.

Order தான் முக்கியம்: ஒவ்வொரு step-உம் அடுத்ததை விட மலிவு, அளவீடுகள் தேவைன்னு காட்டினப்புறம் தான் அடுத்த step-ஐ எடுத்தாங்க.

## பொதுவா பண்ற தப்புகள்

**எல்லாத்துக்கும் index போடுறது.** ஒவ்வொரு index-உம் ஒவ்வொரு write-ஐயும் மெதுவாக்கும். உங்க உண்மையான queries filter, sort பண்ற columns-க்கு மட்டும் index போடுங்க.

**Replication lag-ஐ புறக்கணிக்கிறது.** Write பண்ணினதும் replicas-ல இருந்து படிச்சா பழைய data தெரியும். "Read your own writes"-ஐ primary-ல இருந்து படிக்கிற மாதிரி plan பண்ணுங்க.

**ரொம்ப சீக்கிரம் sharding பண்றது.** இது அப்புறம் வர்ற ஒவ்வொரு மாற்றத்தையும் கஷ்டமாக்கும். முதல்ல indexes, query fixes, caching, replicas எல்லாத்தையும் தீர்த்துடுங்க.

**Hot spots உருவாக்குற shard key.** Dates, அல்லது ஒரு popular customer அல்லது event load-ஐ ஒரே shard-ல குவிக்கலாம். சமமா use ஆகுற நிறைய values இருக்குற keys-ஐ தேர்ந்தெடுங்க.

**Hot paths-ல cross-shard joins தேவைப்படுறது.** பொதுவான requests எல்லா shards-ஐயும் படிக்கணும்னா, உங்க access pattern-க்கு key தப்பு.

**Scalable-ஆ தோணுதுன்னு NoSQL-ஐ choose பண்றது.** Transactions-உம் flexible queries-உம் தேவைன்னா, நல்லா index பண்ண relational database பல வருஷம் உங்களுக்கு போதுமா இருக்கும்.

## Practice பண்ணுங்க

1. Watch & learn panel-ல இருக்குற sharding, replication video lessons-ஐ பாருங்க.
2. மேல இருக்குற exercise-ஐ பண்ணுங்க.
3. Project check-ஐ பண்ணுங்க: index இருக்கும்போதும் இல்லாதப்போவும் ஒரு query-ஐ time பண்ணி, query plan-ஐ படிங்க.
4. உங்களுக்கு தெரிஞ்ச ஒரு app-க்கு, sharding தேவைப்பட அதிக வாய்ப்பு இருக்குற table-ஐயும், நீங்க தேர்ந்தெடுக்குற key-ஐயும் சொல்லுங்க.
