## இது என்ன

நிறைய automations **ஏதாவது நடக்குற நிமிஷமே** react பண்ணணும்: ஒரு payment succeed ஆகுது, ஒரு order போடப்படுது, ஒரு form submit ஆகுது, ஒரு support ticket close ஆகுது. **Webhook** அதை சாத்தியமாக்குது.

Webhook-னா ஒரு event நடந்ததும், நீங்க கொடுத்த web address (URL)-க்கு ஒரு app அனுப்புற message. இது ஒரு doorbell மாதிரி. ஒவ்வொரு சில நிமிஷமும் கதவை போய் பார்க்காம (அதுக்கு பேரு **polling**), யாராவது வந்தா உங்களுக்கு சொல்லிடும்.

```flow
dir: LR
title: Polling: மெதுவு, நிறைய வீணான requests
உங்க app -[புதுசா ஏதாவது இருக்கா?]-> Store
Store -[இல்ல ... இல்ல ... இருக்கு, ஒரு order]-> உங்க app
```

```flow
dir: LR
title: Webhook: நடக்கும்போதே சொல்லிடும், வேகம், வீணான checks இல்ல
Store -[event-ஐ POST பண்ணும்]-> உங்க URL (n8n)
உங்க URL (n8n) -[200 OK]-> Store
```

Message பெரும்பாலும் ஒரு HTTP **POST** request, அதோட **JSON** body event-ஐ விவரிக்கும்: என்ன நடந்தது, எப்போ, details என்ன.

இந்த lesson-ல Jaipur-ல ஒரு handicrafts store-ஐ follow பண்றோம். Payment succeed ஆன உடனே invoice-ஐ email பண்ணணும்னு அவங்க நினைக்கிறாங்க. Lesson முடியும்போது, webhooks-ஐ receive பண்ணி, test பண்ணி, secure பண்ணி, repeats ஆனாலும் safe-ஆ handle பண்ண முடியும்.

## இது எப்படி work ஆகுது

### Receive பண்றது

உங்க automation tool உங்களுக்கு ஒரு URL கொடுக்கும், உதாரணம்: n8n-ஓட **Webhook** node-ல இருந்து. அதை sender app-ஓட settings-ல paste பண்ணி, எந்த events அனுப்பணும்னு தேர்ந்தெடுங்க. ஒரு event நடந்தா, sender உங்க URL-க்கு JSON-ஐ post பண்ணும், அந்த data-ஓட உங்க workflow ஆரம்பிக்கும்.

### Test URL vs production URL

நிறைய tools ரெண்டு URLs கொடுக்கும்:

| URL | எப்போ work ஆகும் | எதுக்கு use பண்றது |
| --- | --- | --- |
| Test URL | நீங்க editor-ல listen பண்ணிட்டு இருக்கும்போது | Build பண்ணவும் debug பண்ணவும் |
| Production URL | Workflow publish (active) ஆனதும் | Real events-க்கு |

Beginners பண்ற பொதுவான தப்பு: sender-ஓட settings-ல test URL-ஐயே விட்டுடுறது. நீங்க பார்த்துட்டு இருக்கும்போது எல்லாம் work ஆகும், editor-ஐ close பண்ணா நின்னுடும்.

### Payload-ஐ பாருங்க

ஒரு test event-ஐ trigger பண்ணி, வந்த exact JSON-ஐ பாருங்க. Field பெயர்களும் nesting-உம் provider-க்கு provider மாறும். உங்க mappings-ஐ ஞாபகத்துல இருந்து இல்லாம, ஒரு real sample-ல இருந்து build பண்ணுங்க.

### சீக்கிரமா respond பண்ணுங்க

Senders ஒரு fast success reply எதிர்பார்ப்பாங்க, பெரும்பாலும் சில நொடிகள்ல ஒரு HTTP `200 OK`. உங்க workflow முதல்ல PDF generate பண்றது மாதிரி மெதுவான வேலையை பண்ணா, sender timeout ஆகி **retry** பண்ணலாம். அதனால: உடனே reply பண்ணுங்க, அப்புறம் வேலையை பண்ணுங்க.

### Retries, duplicates

உங்க endpoint fail ஆனா அல்லது மெதுவா இருந்தா, பெரும்பாலான senders retry பண்ணுவாங்க, சில சமயம் பல மணி நேரத்துல பல தடவை. சிலர் design-ஏ "at least once" தான் deliver பண்ணுவாங்க. எப்படி இருந்தாலும், **ஒரே event உங்களுக்கு ஒரு தடவைக்கு மேல வரலாம்.**

இதுக்கான defence **idempotency**: உங்க actions-ஐ repeat ஆனாலும் safe-ஆ இருக்க வைக்கிறது. நீங்க ஏற்கனவே process பண்ணியிருக்கீங்களான்னு பார்க்க, event அல்லது payment-ஓட id-ஐ use பண்ணுங்க:

```flow
Webhook வருது | payment id = pay_771 -> pay_771 ஏற்கனவே நம்ம sheet-ல இருக்கா?
pay_771 ஏற்கனவே நம்ம sheet-ல இருக்கா? -[இருக்கு]-> நிறுத்து | duplicate: எதுவும் பண்ணாத
pay_771 ஏற்கனவே நம்ம sheet-ல இருக்கா? -[இல்ல]-> Invoice உருவாக்கு, email பண்ணு, pay_771-ஓட ஒரு row சேர்
```

Duplicate "payment captured" ஒரு போதும் ரெண்டு invoices-ஐயோ ரெண்டு emails-ஐயோ உருவாக்கக்கூடாது.

### Security

உங்க URL-ஐ தெரிஞ்சுக்குற யாரும் fake events-ஐ post பண்ணலாம், உதாரணம்: உண்மையான shipment-ஐ trigger பண்ற fake "payment captured". இதை பாதுகாக்க:

| Protection | என்ன பண்ணும் |
| --- | --- |
| **Signature-ஐ verify பண்ணுங்க** | நிறைய providers ஒவ்வொரு webhook-ஐயும் ஒரு shared secret வச்சு sign பண்ணுவாங்க; data-வை நம்புறதுக்கு முன்னாடி உங்க workflow signature-ஐ check பண்ணும் |
| **HTTPS, நீளமான guess பண்ண முடியாத path** | URL-ஐ கண்டுபிடிக்க கஷ்டமாக்கும், போற வழியில data-வை படிக்க முடியாம பண்ணும் |
| **Provider-ஓட API-ல இருந்து re-fetch பண்ணுங்க** | முக்கியமான events-க்கு, அந்த payment உண்மையிலயே succeed ஆச்சான்னு provider-கிட்டயே நேரடியா கேளுங்க |

### தவறின events

உங்க endpoint, sender-ஓட retry window-ஐ விட நீண்ட நேரம் down-ஆ இருந்தா, events சத்தமில்லாம தொலைஞ்சு போகலாம். முக்கியமான flows-க்கு **reconciliation** ஓட்டுங்க, உதாரணம்: ராத்திரி; அது உங்க records-ஐ provider-ஓட API-வோட ஒப்பிட்டு, இடைவெளிகளை நிரப்பும்.

| --- | --- | --- |
| 1 | Production URL இருக்குற Webhook node, gateway-ஓட dashboard-ல "payment captured" events-க்கு சேர்த்தது | Events-ஐ உடனே receive பண்ண |
| 2 | Gateway-ல இருந்து copy பண்ண webhook secret வச்சு signature-ஐ verify பண்ணு | Fake requests-ஐ reject பண்ண |
| 3 | உடனே `200 OK` reply பண்ணு | Gateway timeout ஆகி retry பண்றதை தடுக்க |
| 4 | Sheet-ல payment id-ஐ check பண்ணு; இருந்தா நிறுத்து | Duplicates எதுவும் பண்ணாது |
| 5 | Invoice PDF உருவாக்கு, email பண்ணு, payment id-ஓட row சேர் | உண்மையான வேலை |
| 6 | ராத்திரி: gateway-ஓட API-ல இருந்து அன்னைக்கு captured payments-ஐ sheet-வோட ஒப்பிடு | தவறின எதையும் பிடிக்க |

**திருவிழா sale.** Diwali sale-ஓட போது n8n server restart ஆகி ரெண்டு நிமிஷம் down ஆகுது. Server திரும்ப வந்ததும், தவறின events-ஐ gateway retry பண்ணுது. அதுல ரெண்டு events உண்மையில restart-க்கு கொஞ்சம் முன்னாடியே process ஆகியிருந்துச்சு, ஆனா அவற்றோட replies gateway-க்கு போய் சேரல, அதனால அவை ரெண்டு தடவை வருது. Duplicate check ரெண்டையும் தடுக்குது.

| நிலைமை | என்ன நடந்தது | எந்த step handle பண்ணுச்சு |
| --- | --- | --- |
| தெரியாத sender-ஓட fake request | Signature ஒத்துப்போகல | Step 2: reject ஆச்சு |
| Restart-க்கு அப்புறம் event ரெண்டு தடவை deliver ஆச்சு | Payment id ஏற்கனவே sheet-ல இருக்கு | Step 4: நிறுத்தியது |
| 2 நிமிஷ outage-ல அனுப்பின events | Gateway அப்புறம் retry பண்ணுச்சு | Steps 1 முதல் 5, சில நிமிஷம் தாமதமா |
| ஒரு வார nightly reconciliation | Missing payments எதுவும் இல்ல | Step 6 |

Step 4 இல்லாம இருந்திருந்தா, ரெண்டு customers-க்கு ஒவ்வொருத்தருக்கும் ரெண்டு invoices போயிருக்கும், நடக்காத ₹8,400 sales accounts sheet-ல தெரிஞ்சிருக்கும்.

## பொதுவா பண்ற தப்புகள்

- **Production-ல test URL-ஐ use பண்றது.** Editor-ஐ close பண்ணதும் events வர்றது நின்னுடும்.
- **Sign பண்ணாத requests-ஐ நம்புறது.** Action எடுக்குறதுக்கு முன்னாடி signatures-ஐ verify பண்ணுங்க.
- **மெதுவான responses.** Senders retry பண்ணுவாங்க, duplicates உருவாகும். முதல்ல reply பண்ணுங்க, அப்புறம் வேலை பண்ணுங்க.
- **Duplicate check இல்லாதது.** Retries இரட்டை invoices, emails, orders-ஐ உருவாக்கும்.
- **Reconciliation இல்லாதது.** நீண்ட outages-ல events சத்தமில்லாம தொலையும்.
- **Secrets-ஐ log பண்றது.** Webhook secret-ஐயோ முழு payment details-ஐயோ மத்தவங்க படிக்கக்கூடிய logs-ல எழுதாதீங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற, webhooks பத்தின Zapier-ஓட விளக்கத்தையும், n8n-ஓட Webhook node docs-ஐயும் படிங்க.

1. **Receive.** n8n-ல ஒரு webhook workflow உருவாக்கி, ஒரு form tool-ல இருந்தோ curl மாதிரி ஒரு command-ல இருந்தோ test request அனுப்பி trigger பண்ணுங்க.
2. **Duplicates.** அதே event-ஐ ரெண்டு தடவை அனுப்பி, ரெண்டாவது எதுவும் பண்ணாத மாதிரி duplicate check ஒண்ணை சேருங்க.
3. **Security.** Shared-secret check ஒண்ணை சேர்த்து, தப்பான secret-ஓட வர்ற request reject ஆகுறதை காட்டுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** Webhooks ஏன் retry பண்ணுதுன்னு explain பண்ண முடியும், உங்க duplicate check work ஆகுறதை காட்ட முடியும், outage-ஓட போது தவறின events-ஐ எப்படி பிடிப்பீங்கன்னு சொல்ல முடியும்.
