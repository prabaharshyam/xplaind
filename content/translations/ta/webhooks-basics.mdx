## இது என்ன

நிறைய automations **ஏதாவது நடக்குற நிமிஷமே** react பண்ணணும்: ஒரு payment succeed ஆகுது, ஒரு order போடப்படுது, ஒரு form submit ஆகுது. **Webhook** அதை சாத்தியமாக்குது.

Webhook-னா ஒரு event நடந்த உடனே, நீங்க கொடுத்த web address (URL)-க்கு ஒரு app அனுப்புற message. இது ஒரு doorbell மாதிரி. ஒவ்வொரு சில நிமிஷமும் கதவை போய் பார்க்குறதுக்கு பதிலா (அதுக்கு பேரு **polling**), யாராவது வந்தா உங்களுக்கு சொல்லிடும்.

```flow
dir: LR
title: Polling: மெதுவு, நிறைய வீணான requests
உங்க app -[புதுசா ஏதாவது இருக்கா?]-> Store
Store -[இல்ல ... இல்ல ... இருக்கு, ஒரு order]-> உங்க app
```

```flow
dir: LR
title: Webhook: நடக்கும்போதே சொல்லிடும், வேகம், வீணான checks இல்ல
Store -[event-ஐ POST பண்ணும்]-> உங்க URL (n8n)
உங்க URL (n8n) -[200 OK]-> Store
```

Message பொதுவா ஒரு HTTP **POST** request, அதுல event-ஐ விவரிக்கிற ஒரு **JSON** body இருக்கும். ஒரு payment gateway-ஓட event மாதிரியான, simplify பண்ணின ஒரு example:

```json
{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}
```

இந்த sample-ல amount paise-ல இருக்கு, அதனால 420000-னா ₹4,200.

**Webhook-ஆ API-ஆ?** API-ல, *நீங்க* provider-ஐ call பண்ணி கேக்குறீங்க. Webhook-ல, ஏதாவது மாறினா provider *உங்களை* call பண்ணுது. நல்ல automations ரெண்டையும் use பண்ணும்: ஏதோ நடந்துச்சுன்னு webhook சொல்லும், details-ஐ check பண்ணவும் gaps-ஐ நிரப்பவும் API உதவும்.

இந்த lesson Jaipur-ல இருக்குற ஒரு handicrafts store-ஐ follow பண்ணுது; ஒரு payment succeed ஆன உடனே invoice email ஆகணும்னு அவங்க விரும்புறாங்க.

## இது எப்படி work ஆகுது

### ஒரு delivery-ஓட வாழ்க்கை

ஒவ்வொரு delivery-உம் அதே loop-ஐ தான் follow பண்ணும். Sender உங்க reply-ஐ மட்டும் தான் பார்க்கும்.

```flow
title: ஒரு webhook delivery
Event நடக்குது | உதாரணமா ஒரு payment capture ஆகுது -> Sender உங்க secret வச்சு JSON-ஐ sign பண்ணுது
Sender உங்க secret வச்சு JSON-ஐ sign பண்ணுது -> உங்க URL-க்கு POST
உங்க URL-க்கு POST -> உங்க reply
உங்க reply -[timeout-க்குள்ள 2xx]-> Delivered | sender நிறுத்திடும்
உங்க reply -[error அல்லது நேரத்துக்குள்ள reply இல்ல]-> அப்புறம் retry | அதே event, அதே id
அப்புறம் retry -> உங்க URL-க்கு POST
```

அதனால ஒரு `2xx` reply sender-க்கு "முடிஞ்சது"-னு அர்த்தம், அடுத்த second-லயே உங்க workflow fail ஆனாலும் கூட. எந்த failure-உம் அதே event-ஐ திரும்ப கொண்டு வரும்.

### Receive பண்றது: test, production URLs

உங்க automation tool உங்களுக்கு ஒரு URL கொடுக்கும், உதாரணமா n8n-ஓட **Webhook** node-ல இருந்து. அதை sending app-ஓட settings-ல paste பண்ணி, எந்த events அனுப்பணும்னு தேர்ந்தெடுங்க. நிறைய tools ரெண்டு URLs கொடுக்கும்:

| URL | எப்போ work ஆகும் | எதுக்கு use பண்றது |
| --- | --- | --- |
| Test URL | நீங்க editor-ல listen பண்ணிட்டு இருக்கும்போது | Build பண்ணவும் debug பண்ணவும் |
| Production URL | Workflow publish (active) ஆனதும் | Real events-க்கு |

Beginners பண்ற ஒரு பொதுவான தப்பு: sender-ஓட settings-ல test URL-ஐயே விட்டுடுறது. நீங்க பார்த்துட்டு இருக்கும்போது எல்லாம் work ஆகும், அப்புறம் நின்னுடும்.

இங்க ரெண்டு Webhook node settings முக்கியம். **Raw Body**, sender post பண்ணின exact bytes-ஐ அப்படியே வச்சுக்கும்; signature-ஐ check பண்ண அது தேவை. **Respond**, n8n எப்போ reply பண்ணணும்னு control பண்ணும்: உடனே, கடைசி node முடிஞ்சதும், அல்லது நீங்க சரியா வேணும்ங்குற இடத்துல வைக்கிற ஒரு **Respond to Webhook** node-ல.

### Real events வர்றதுக்கு முன்னாடி test பண்ணுங்க

Field பெயர்கள் provider-க்கு provider மாறும், அதனால mappings-ஐ ஒரு real sample-ல இருந்து build பண்ணுங்க. `curl` வச்சு நீங்களே ஒண்ணு அனுப்பலாம்: n8n-ல "Listen for test event"-ஐ click பண்ணுங்க, அப்புறம் உங்க சொந்த test URL-ஓட இதை run பண்ணுங்க:

```bash
curl -X POST "https://your-n8n.example.com/webhook-test/payments" \
  -H "Content-Type: application/json" \
  -d '{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
```

நிறைய beginners-ஐ ஒரு trap நிறுத்திடும். n8n உங்க laptop-ல run ஆனா, அதோட URL `localhost`-ல ஆரம்பிக்கும், internet-ல இருக்குற ஒரு gateway-ஆல அதை reach பண்ண முடியாது. ஒரு public n8n (n8n Cloud, அல்லது HTTPS இருக்குற ஒரு server), உங்க laptop-க்கு ஒரு public address கொடுக்குற ngrok அல்லது Cloudflare Tunnel மாதிரி ஒரு **tunnel**, அல்லது provider என்ன அனுப்புதுன்னு பார்க்க மட்டும் webhook.site-ஐ use பண்ணுங்க.

பெரும்பாலான gateways-ல real பணம் இல்லாத ஒரு **test mode**-உம் இருக்கும். Test mode-க்கும் live mode-க்கும் பொதுவா தனித்தனி webhooks, தனித்தனி secrets இருக்கும்.

### உங்க reply sender-க்கு என்ன சொல்லுது

Sender உங்க reply-ஓட status code-ஐ மட்டும் தான் படிக்கும், சில seconds மட்டும் தான் காத்திருக்கும். Razorpay, ஒரு இந்திய payment gateway, 5 seconds-க்குள்ள ஒரு `2xx` reply எதிர்பார்க்கும். வேற எந்த code-ஐயும், அல்லது நேரத்துக்குள்ள reply வராததையும் failure-ஆ எடுத்துக்கிட்டு, event உருவான நேரத்துல இருந்து 24 மணி நேரத்துக்கு, இடைவெளியை கூட்டிக்கிட்டே retry பண்ணும். அந்த 24 மணி நேரமும் deliveries fail ஆகிட்டே இருந்தா, webhook-ஐ disable பண்ணிடும் (இதெல்லாம் November 2026 நிலவரப்படி). மத்த providers-க்கு வேற windows இருக்கும், அதனால அவங்க docs-ஐ படிங்க.

| உங்க reply | Sender என்ன முடிவு பண்ணும் | எப்போ அனுப்பணும் |
| --- | --- | --- |
| `200` (அல்லது வேற ஒரு `2xx`) | Delivered; திரும்ப அனுப்பவே அனுப்பாது | Event save ஆயிடுச்சு, அல்லது ஏற்கனவே உங்ககிட்ட இருக்குற ஒரு duplicate |
| `401` | Failed; பொதுவா retry ஆகும் | Signature match ஆகல |
| `500` | Failed; அப்புறம் retry ஆகும் | Event-ஐ save பண்ண முடியல, உதாரணமா உங்க database down |
| நேரத்துக்குள்ள reply இல்ல | Failed; அப்புறம் retry ஆகும் | உங்க workflow ரொம்ப மெதுவா இருந்துச்சு அல்லது server down |

### முதல்ல save, அப்புறம் reply, அப்புறம் வேலை

இந்த lesson-ல எல்லாத்தையும் விட முக்கியமான idea இது தான். சாத்தியமான மூணு orders-ல, ரெண்டு fail ஆகும்.

| Order | என்ன தப்பா போகும் |
| --- | --- |
| எல்லா வேலையையும் பண்ணிட்டு, அப்புறம் reply | PDF உருவாக்குற மாதிரி மெதுவான வேலை timeout-ஐ தாண்டிடும். நீங்க வேலை பண்ணிட்டு இருக்கும்போதே sender retry பண்ணும், உங்களுக்கு duplicates வரும். |
| முதல்ல reply, அப்புறம் வேலை | `200`-க்கு அப்புறம் n8n crash அல்லது restart ஆனா, sender திரும்ப அனுப்பவே அனுப்பாது, event தொலைஞ்சிடும். |
| Save, reply, அப்புறம் save பண்ணின copy-ல இருந்து வேலை | Sender "முடிஞ்சது"-னு கேக்குறதுக்கு முன்னாடியே event safe-ஆ இருக்கு. Fail ஆன வேலை உங்க copy-ல இருந்து retry ஆகும். |

**Durable-ஆ save பண்றது**-னா restart-ஐ தாங்குற ஒரு இடத்துல event-ஐ எழுதுறது: ஒரு database table (உதாரணமா Postgres அல்லது Supabase) அல்லது ஒரு message queue. ஒரு insert வேகமா நடக்கும், timeout-க்குள்ளயே நல்லா முடிஞ்சிடும். Raw body, event id, receive பண்ணின நேரம், ஒரு **status** இதையெல்லாம் store பண்ணுங்க: save ஆனதும் `received`, வேலை முடிஞ்சதும் `done`.

```flow
title: Save, reply, அப்புறம் வேலை
Webhook வருது -> Signature match ஆகுதா?
Signature match ஆகுதா? -[இல்ல]-> 401 reply பண்ணி நிறுத்து
Signature match ஆகுதா? -[ஆமா]-> Event id-ஐ insert பண்ணு | status received
Event id-ஐ insert பண்ணு -[ஏற்கனவே இருக்கு]-> 200 reply பண்ணி நிறுத்து | ஒரு duplicate
Event id-ஐ insert பண்ணு -[save ஆச்சு]-> 200 reply பண்ணு
200 reply பண்ணு -> Invoice உருவாக்கி email பண்ணு
Invoice உருவாக்கி email பண்ணு -> Status-ஐ done-னு mark பண்ணு
```

Reply-க்கு அப்புறம் workflow crash ஆனா, row `received`-ஆவே இருக்கும். ஒரு **sweep**, அதாவது சுமார் ஒவ்வொரு 15 நிமிஷத்துக்கும் run ஆகுற ஒரு scheduled workflow, 10 நிமிஷத்துக்கு அப்புறமும் `received`-ஆ இருக்குற rows-ஐ எடுத்து வேலையை திரும்ப run பண்ணும். அதனால வேலை repeat பண்ண safe-ஆ இருக்கணும்: ஒவ்வொரு sub-step-ஐயும் (invoice உருவாச்சு, email போச்சு) record பண்ணுங்க, அப்போ rerun missing ஆனதை மட்டும் பண்ணும்.

### Duplicates, idempotency

பெரும்பாலான senders **at-least-once delivery** promise பண்ணுவாங்க: ஒரு event-ஐ தொலைக்குறதை விட ரெண்டு தடவை அனுப்புறதையே விரும்புவாங்க. இதுக்கான defence **idempotency**: ஒரு event-ஐ ரெண்டு தடவை process பண்ணாலும், ஒரு தடவை process பண்ணின அதே effect தான் இருக்கும்.

ரெண்டு வேற வேற வேலைகளுக்கு ரெண்டு ids use பண்ணுங்க:

- **Event id** ஒரு delivery-ஐ identify பண்ணும். அந்த event-ஓட ஒவ்வொரு retry-லயும் அதோட value அதே தான், அதனால "இந்த delivery-ஐ முன்னாடியே பார்த்திருக்கேன்"-னு அது சொல்லும். உதாரணமா Razorpay அதை `x-razorpay-event-id` header-ல அனுப்பும்.
- **Business id**, payment id மாதிரி, real-world விஷயத்தை identify பண்ணும். ரெண்டு *வேற வேற* events ஒரே payment-ஐ விவரிக்கலாம் (உதாரணமா `payment.captured`, `order.paid`), அதனால invoice-ஐ payment id-ஐ key-ஆ வச்சு பண்ணுங்க.

**Experts-ஐயே மாட்ட வைக்கிற race.** "Sheet-ல id-ஐ தேடு; இல்லைன்னா சேர்"-ங்குற design ஆசையா தோணும். ஒரு மெதுவான reply-க்கு அப்புறம், original வந்த ஒரு second கழிச்சு retry வரலாம். ரெண்டு copies-உம் `pay_771`-ஐ தேடும், ரெண்டுக்கும் எதுவும் கிடைக்காது, ரெண்டுமே invoice உருவாக்கும், ஏன்னா check-க்கும் write-க்கும் நடுவுல இன்னொரு copy நுழைஞ்சிடுச்சு.

இதுக்கான fix **duplicate வந்தா fail ஆகுற ஒரே ஒரு step**. `event_id` column-க்கு ஒரு unique key கொடுத்து, வெறுமனே insert பண்ணுங்க. சரியா ஒரே ஒரு insert தான் succeed ஆகும்; இன்னொண்ணுக்கு "duplicate key" error வரும், அதை உங்க workflow "ஏற்கனவே இருக்கு, 200 reply பண்ணி நிறுத்து"-னு எடுத்துக்கும். Invoice-ஓட `payment_id`-க்கும் ஒரு unique key போடுங்க.

Google Sheet-ல unique key கிடையாது. எப்பவாவது ஒரு double invoice வந்தா பரவாயில்லைன்னு ஏத்துக்குற, சின்ன, குறைவான volume இருக்குற shop-க்கு மட்டும் தான் sheet lookup ஓகே. ஒரு sale-க்கு முன்னாடி database table-க்கு மாறிடுங்க.

### Events order மாறி வரலாம்

Delivery order guarantee கிடையாது; Razorpay-ஓட webhook guidance இதை நேரடியாவே சொல்லுது (November 2026 நிலவரப்படி). முந்தைய attempt-ல இருந்து retry ஆன ஒரு `payment.failed`, success ஆன `payment.captured`-க்கு *அப்புறம்* வரலாம்; "கடைசி event தான் ஜெயிக்கும்"-னு வச்சா, pay பண்ணின order-ஐ failed-னு mark பண்ணிடும். இதை ரெண்டு rules handle பண்ணும்:

- **States-ஐ முன்னாடி மட்டும் நகர்த்துங்க.** ஒரு order `created`-ல இருந்து `paid`-க்கு போகலாம், ஆனா `paid`-ல இருந்து `failed`-க்கு திரும்ப போகவே கூடாது. அதை பின்னாடி நகர்த்துற events-ஐ ignore பண்ணுங்க.
- **முக்கியமான நேரத்துல, current state-ஐ கேளுங்க.** Ship அல்லது refund பண்றதுக்கு முன்னாடி, இப்போ status என்னன்னு provider-ஓட API-ஐ call பண்ணுங்க.

### Security

உங்க URL தெரிஞ்ச யார் வேணும்னாலும் ஒரு fake "payment captured"-ஐ post பண்ணி, ஒரு real shipment-ஐ trigger பண்ணலாம். அதை layers-ஆ protect பண்ணுங்க.

**Signature-ஐ verify பண்ணுங்க.** நீங்களும் provider-உம் ஒரு **webhook secret**-ஐ share பண்றீங்க. ஒவ்வொரு delivery-க்கும், provider ஒரு **HMAC**-ஐ compute பண்ணும், அதாவது secret வச்சு உருவாக்கின body-ஓட ஒரு fingerprint, அதை ஒரு header-ல அனுப்பும். உதாரணமா Razorpay ஒரு HMAC-SHA256 hex value-ஐ `X-Razorpay-Signature`-ல அனுப்பும் (November 2026 நிலவரப்படி). நீங்க receive பண்ணின body மேல அதே HMAC-ஐ compute பண்றீங்க; ரெண்டும் match ஆனா, sender-க்கு secret தெரியும், body மாறல. Webhook-ஓட சொந்த secret-ஐ use பண்ணுங்க, உங்க API key secret-ஐ இல்ல.

Check work ஆகுமா இல்லையான்னு மூணு details தான் முடிவு பண்ணும்:

1. **Raw body-ஐ use பண்ணுங்க.** Signature அனுப்பின exact bytes-ஐ cover பண்ணும். JSON-ஐ parse பண்ணி திரும்ப text-ஆ மாத்தினா, spaces அல்லது key order மாறலாம், அதனால ஒரு genuine event கூட fail ஆகும். n8n-ல **Raw Body**-ஐ on பண்ணுங்க.
2. **Constant time-ல compare பண்ணுங்க.** சாதாரண comparison முதல் தப்பான character-லயே நின்னுடும், அது timing clues-ஐ leak பண்ணலாம். n8n-ஓட **Crypto** node HMAC-ஐ compute பண்ணும், ஆனா IF node comparison constant-time இல்ல. High-value flows-க்கு, Node-ஓட `crypto.timingSafeEqual` வச்சு ஒரு **Code** node-ல compare பண்ணுங்க; self-hosted n8n-ல, முதல்ல `NODE_FUNCTION_ALLOW_BUILTIN` environment variable வச்சு `crypto` module-ஐ allow பண்ணுங்க.
3. **Provider ஒரு timestamp-ஐ sign பண்ணும் இடத்துல, பழைய messages-ஐ reject பண்ணுங்க.** ஒரு signature message-ஐ யார் அனுப்பினாங்கன்னு prove பண்ணும், எப்போன்னு இல்ல, அதனால பிடிபட்ட ஒரு request-ஐ அப்புறம் replay பண்ணலாம். Stripe மாதிரி சில providers ஒரு timestamp-ஐ sign பண்ணுவாங்க, அதனால சில நிமிஷத்தை விட பழசான எதையும் reject பண்ணலாம். அது இல்லாத இடத்துல, உங்க unique event id ஒரு replay-ஐ harmless ஆக்கிடும்.

Standard library மட்டும் use பண்ற இந்த Python script, raw-body trap-ஐ காட்டுது:

```python
import hmac, hashlib, json

SECRET = b"test_secret_123"

def is_genuine(raw_body: bytes, signature: str) -> bool:
    expected = hmac.new(SECRET, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)  # constant-time

raw = b'{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
sig = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()

print(is_genuine(raw, sig))                          # True
print(is_genuine(json.dumps(json.loads(raw)).encode(), sig))  # False: spaces were added
```

ரெண்டாவது தடவை fail ஆகுறது ஏன்னா `json.dumps` spaces-ஐ சேர்க்குது: அதே data, வேற bytes.

**மத்த layers:** HTTPS-உம் நீளமான, random URL path-உம் use பண்ணுங்க (ரெண்டுமே signature-க்கு பதிலா ஆகாது). பொருட்களை ship பண்றதுக்கு முன்னாடி, provider-ஓட API-ல இருந்து payment-ஐ திரும்ப fetch பண்ணுங்க; Razorpay-யே webhooks-க்கு ஒரு backstop-ஆ அதோட fetch APIs-ஐ use பண்ண சொல்லுது, உதாரணமா time-sensitive ஆன ஒரு flow webhook வர்ற வரைக்கும் காத்திருக்க முடியாத போது.

### தவறின events, reconciliation

Retries சின்ன outages-ஐ cover பண்ணும், நீண்ட outages-ஐ இல்ல. Retry window-ஐ தாண்டினா, எந்த error-உம் இல்லாம events தொலைஞ்சிடும், சில providers webhook-ஐ off பண்ணிடுவாங்க. முக்கியமான flows-க்கு ரெண்டு safety nets இருக்கும்:

- **Sweep**, நீங்க save பண்ணி ஆனா முடிக்காத events-க்கான வேலையை retry பண்ணும்.
- **Reconciliation**, உதாரணமா nightly, அன்னைக்கு capture ஆன எல்லா payments-ஐயும் provider-ஓட API-கிட்ட கேட்டு, உங்க invoices கூட compare பண்ணும். Missing ஆன எதுவும் அப்போ process ஆகும்.

ஒரு alert-உம் set பண்ணுங்க: business hours-ல ஒரு மணி நேரத்துக்கு எந்த webhook-உம் வரலைன்னா, அல்லது ஒரு webhook disable ஆயிடுச்சுன்னு provider சொன்னா, அன்னைக்கே யாராவது பார்க்கணும்.

## பொதுவா பண்ற தப்புகள்

- **Production-ல test URL-ஐ use பண்றது.** Editor-ஐ close பண்ணதும் events வர்றது நின்னுடும்.
- **Event save ஆகுறதுக்கு முன்னாடியே reply பண்றது.** `200`-க்கு அப்புறம் ஒரு crash வந்தா event தொலைஞ்சிடும், ஏன்னா sender அதை திரும்ப அனுப்பாது.
- **Reply பண்றதுக்கு முன்னாடி மெதுவான வேலையை பண்றது.** Sender timeout ஆகி retry பண்ணும், duplicates உருவாகும்.
- **Duplicate check-ஆ "தேடு, அப்புறம் எழுது".** ஒண்ணா வர்ற ரெண்டு copies-உம் pass ஆயிடும். ஒரு unique key use பண்ணுங்க.
- **ஒரு duplicate-க்கு error-ஓட reply பண்றது.** ஏற்கனவே உங்ககிட்ட இருக்குற ஒரு event-ஐ sender retry பண்ணிட்டே இருக்கும். `200` reply பண்ணுங்க.
- **Parse பண்ணின JSON மேல signature-ஐ check பண்றது, அல்லது URL-ஐ மட்டும் நம்புறது.** Raw body-ஐ use பண்ணுங்க; ஒரு secret URL leak ஆகலாம்.
- **Events order-ல வரும்னு நினைக்கிறது.** States-ஐ முன்னாடி மட்டும் நகர்த்துங்க, பணம் சம்பந்தப்பட்ட action-க்கு முன்னாடி திரும்ப fetch பண்ணுங்க.
- **Test, live secrets-ஐ கலக்குறது.** ஒவ்வொரு mode-க்கும் பொதுவா அதோட சொந்த webhook, secret இருக்கும்.
- **Sweep இல்ல, reconciliation இல்ல, alert இல்ல.** Crashes-உம் நீண்ட outages-உம் சத்தமில்லாம events-ஐ தொலைச்சிடும்.
- **Secrets-ஐ log பண்றது.** Webhook secret-ஐயும் முழு payment details-ஐயும் shared logs-ல இருந்து வெளியே வைங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற Zapier-ஓட webhooks explanation-ஐயும், n8n-ஓட Webhook node docs-ஐயும் படிங்க.

1. **Receive பண்ணுங்க.** n8n-ல ஒரு Webhook workflow build பண்ணுங்க, மேல இருக்குற `curl` command-ஐ உங்க test URL-க்கு அனுப்புங்க, வந்த JSON-ஐ study பண்ணுங்க. n8n ஒரு laptop-ல run ஆனா, ஒரு tunnel வழியா வெளியில இருந்து reach பண்ணுங்க.
2. **Reply பண்றதுக்கு முன்னாடி save பண்ணுங்க.** Unique event id-உம் ஒரு status column-உம் இருக்குற ஒரு `webhook_events` table உருவாக்குங்க. ஒவ்வொரு event-ஐயும் insert பண்ணுங்க, அப்புறம் ஒரு Respond to Webhook node வச்சு reply பண்ணுங்க. Reply-க்கு அப்புறம் வேணும்னே workflow-ஐ நிறுத்தி, row `received`-ஆவே இருக்குறதை காட்டுங்க.
3. **Duplicates.** அதே event-ஐ ஒரே நேரத்துல ரெண்டு தடவை அனுப்புங்க (`&` வச்சு join பண்ணின ரெண்டு `curl` commands). ஒரு row, ஒரு invoice, ரெண்டு copies-க்கும் ஒரு `200` இருக்குறதை காட்டுங்க.
4. **Security.** ஒரு test secret வச்சு body-ஐ sign பண்ணுங்க (`openssl dgst -sha256 -hmac "test_secret_123"`, அல்லது மேல இருக்குற Python script), அதை ஒரு signature header-ல அனுப்பி raw body மேல verify பண்ணுங்க. Body-ல ஒரு character-ஐ மாத்தி ஒரு `401`-ஐ காட்டுங்க.
5. **Sweep, reconcile.** 15-நிமிஷ sweep-ஐ build பண்ணுங்க, உங்க provider-க்கு ஒரு nightly reconciliation எப்படி work ஆகும்னு மூணு sentences-ல விவரிங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** "முதல்ல reply" ஏன் events-ஐ தொலைக்குதுன்னு explain பண்ண முடியும், ரெண்டு copies ஒண்ணா வரும்போது உங்க duplicate check தாங்குறதை காட்ட முடியும், tamper பண்ணின ஒரு request reject ஆகுறதை காட்ட முடியும், ரெண்டு நாள் outage-ல miss ஆன events-ஐ எப்படி பிடிப்பீங்கன்னு சொல்ல முடியும்.
