## இது என்ன

RAG-க்காக documents-ஐ search பண்றதுக்கு முன்னாடி, அவற்றை **chunks**-ஆ பிரிப்பாங்க: embed பண்ணவும், retrieve பண்ணவும், prompt-ல பொருத்தவும் ஏத்த சின்ன passages. Retrieval எதை கண்டுபிடிக்க முடியும்னு chunking தான் முடிவு பண்ணுது. Chunk ரொம்ப பெருசா இருந்தா, அதோட embedding பல topics-ஐ கலந்து blur ஆகிடும். ரொம்ப சின்னதா இருந்தா, அதை புரிஞ்சுக்க தேவையான context போயிடும்.

```flow
title: Fixed-size chunks, every 2,000 characters: the table is cut in half, topics mixed
HR policy -> Chunk 1 | leave policy ... the earned leave table, first rows
HR policy -> Chunk 2 | the rest of the table ... notice period ... probation
```

```flow
title: Structure-aware chunks: headings, then paragraphs, about 400 tokens, with overlap
HR policy, by headings -> Leave > Earned leave | the full table
HR policy, by headings -> Leave > Sick leave
HR policy, by headings -> Exit > Notice period
HR policy, by headings -> Exit > Probation
```

ஒவ்வொரு structure-aware chunk-உம் ஒரு topic தான், அதோட title path முன்னாடி இருக்கும்.

இந்த lesson-ல Pune-ல ஒரு manufacturing company-யோட HR assistant-ஐ follow பண்ணுவோம். அது 120 பக்க employee handbook-ல இருந்து கேள்விகளுக்கு பதில் சொல்லுது.

## இது எப்படி work ஆகுது

**Size.** Chunk size-ஐ tokens அல்லது characters-ல அளப்பாங்க. Prose-க்கு பொதுவா 300 முதல் 800 tokens-ல ஆரம்பிக்கலாம். சின்ன chunks (100 முதல் 300) FAQs மாதிரி precise fact lookup-க்கு ஏத்தது; பெரிய chunks, explanation தேவைப்படுற கேள்விகளுக்கு ஏத்தது.

- *ரொம்ப பெரிய chunks*: Embedding பல ideas-ஐ சராசரியா எடுக்குது, அதனால எந்த ஒரு கேள்விக்கும் நல்லா match ஆகாது. Retrieve ஆன ஒவ்வொரு chunk-உம் prompt-ஐ தேவையில்லாத text-ஆல நிரப்பும், tokens செலவாகும், model-உம் distract ஆகும்.
- *ரொம்ப சின்ன chunks*: "This limit is 45 days" மாதிரி ஒரு sentence எந்த limit-னு சொல்லாமலே retrieve ஆகும். Answers தப்பாகவோ vague-ஆகவோ வரும்.

**Overlap.** பக்கத்துல இருக்குற chunks-க்கு நடுவுல கொஞ்சம் text-ஐ (உதாரணத்துக்கு 10 முதல் 20%) repeat பண்ணா, boundary-ல பிளந்த ஒரு sentence அல்லது idea, ஏதாவது ஒரு chunk-ல முழுசா இருக்கும்.

**Structure வழியா பிரிங்க.** ஒவ்வொரு N characters-க்கும் வெட்டுறதை விட இது நல்லது:

- முதல்ல headings, sections-ல பிரிங்க, அப்புறம் paragraphs, அப்புறம் sentences (recursive splitting);
- tables, lists, code blocks-ஐ முழுசா வச்சிருங்க;
- FAQs-க்கு ஒரு chunk-க்கு ஒரு question-and-answer pair.

**Context சேருங்க.** ஒவ்வொரு chunk-உடனும் document title-ஐயும் section heading-ஐயும் store பண்ணுங்க. Embed பண்ற text-ஓட முன்னாடியும் அடிக்கடி சேர்ப்பாங்க. அப்போ "This limit is 45 days"ங்குறது "Leave Policy > Earned leave: This limit is 45 days"னு ஆகும்.

**Metadata.** Citations-க்கும் filters-க்கும் document id, page, section-ஐ வச்சுக்கோங்க.

**Test பண்ணுங்க.** Chunking ஒரு முடிவு, அதை evaluate பண்ணணும், guess பண்ணக்கூடாது. Real கேள்விகள் set-ல ரெண்டு மூணு sizes-ஐ try பண்ணி, சரியான passages retrieve ஆகுதான்னு அளங்க.

**Document type வாரியா chunking:**

| Document type | Strategy | Typical size |
| --- | --- | --- |
| Policies and manuals | Headings-ல பிரிங்க, அப்புறம் paragraphs; section path-ஐ முன்னாடி சேருங்க | 300 to 600 tokens |
| FAQs | ஒரு chunk-க்கு ஒரு question-and-answer pair | ஒவ்வொரு pair-க்கும் தேவையான அளவு |
| Tables, price lists | ஒவ்வொரு table-ஐயும் முழுசா வைங்க; heading-ஐ சேருங்க | ஒரு table |
| Contracts | Clause வாரியா பிரிங்க; clause numbers-ஐ வச்சிருங்க | ஒரு clause அல்லது sub-clause |
| Chat transcripts, tickets | ஒரு ticket அல்லது ஒரு conversation, இல்லன்னா சில turns-ஓட ஒரு window | 200 to 500 tokens |
| Code | Function அல்லது class வாரியா | ஒரு function |

**Chunk metadata.** ஒவ்வொரு chunk-லயும் இருக்கணும்: document id, title, section path, page, version அல்லது date, access group ஏதாவது இருந்தா அதுவும். இந்த metadata தான் citations-ஐ சாத்தியமாக்குது ("Handbook, section 4.2, page 37"), filters-ஐ அனுமதிக்குது ("current version மட்டும்", "இந்த user பார்க்க அனுமதி இருக்குற documents மட்டும்"), ஒரு document மாறும்போது எல்லாத்தையும் re-index பண்ணாம அந்த ஒரு document-ஓட chunks-ஐ மட்டும் rebuild பண்ணவும் உதவுது.

**Re-chunking சாதாரணம் தான்.** ஒரு test நல்ல strategy-ஐ காட்டுச்சுன்னா, re-chunk பண்ணி re-embed பண்ணுங்க. Chunking code-ஐ version பண்ணி வச்சுக்கோங்க, settings-ஐ index-ஓட சேர்த்து record பண்ணுங்க. அப்போ தான் இப்போதைய results எந்த strategy-ல வந்துச்சுன்னு எப்பவும் தெரியும்.

**PDFs, scanned documents-ஐ chunk பண்றது.** Extract பண்ண PDF text-ல ஒவ்வொரு page-லயும் page headers, footers, page numbers இருக்கும். Chunking-க்கு முன்னாடி, பெரும்பாலான pages-ல repeat ஆகுற lines-ஐ நீக்குங்க. இல்லன்னா அவை ஒவ்வொரு chunk-ஐயும் அதோட embedding-ஐயும் கெடுக்கும். Scans-க்கு முதல்ல OCR run பண்ணி, ஒரு sample-ஐ check பண்ணுங்க. ஏன்னா headings-ல OCR errors இருந்தா structure-aware splitting உடையும். ஒவ்வொரு chunk-ஓட ஆரம்ப page number-ஐயும் வச்சுக்கோங்க. அப்போ ஒரு chunk page break-ஐ தாண்டினாலும் citations சரியான page-ஐ காட்டும்.

**Code-ல ஒரு structure-aware splitter.** இது Markdown அல்லது headings இருக்குற text-ல work ஆகும், section path-ஐ வச்சுக்கும், overlap-ஐ சேர்க்கும். எளிமைக்காக sizes words-ல இருக்கு; exact limits வேணும்னா embedding model-ஓட tokenizer-க்கு மாறுங்க:

```python
import re

def split_by_headings(text, max_words=350, overlap_words=50, title=""):
    chunks, path, buf = [], [], []

    def flush():
        words = " ".join(buf).split()
        start = 0
        while start < len(words):
            piece = words[start:start + max_words]
            header = " > ".join([title] + path)
            chunks.append({"section": header, "text": f"{header}: " + " ".join(piece)})
            if start + max_words >= len(words):
                break
            start += max_words - overlap_words
        buf.clear()

    for line in text.splitlines():
        m = re.match(r"^(#{1,4})\s+(.*)", line)
        if m:
            flush()
            level = len(m.group(1))
            path[:] = path[:level - 1] + [m.group(2).strip()]
        elif line.strip():
            buf.append(line.strip())
    flush()
    return chunks
```

ஒவ்வொரு chunk-உம் "Leave Policy > Earned leave: ..." மாதிரி அதோட section path-ல ஆரம்பிக்கும். அதனால ஒரு சின்ன sentence-உம் அது எதை பத்தின்னு சொல்லும்.

**PDFs-ல repeat ஆகுற lines-ஐ நீக்குங்க.** Extract பண்ண PDF text-ஐ chunk பண்றதுக்கு முன்னாடி, பெரும்பாலான pages-ல வர்ற lines-ஐ drop பண்ணுங்க:

```python
from collections import Counter

def strip_repeats(pages, share=0.6):
    """pages: list of page texts."""
    counts = Counter(l.strip() for p in pages for l in set(p.splitlines()) if l.strip())
    repeated = {l for l, n in counts.items() if n >= share * len(pages)}
    return ["\n".join(l for l in p.splitlines() if l.strip() not in repeated) for p in pages]
```

**Small to big.** Precise retrieval-க்கு சின்ன chunks வேணும்; நல்ல answers-க்கு context வேணும். ரெண்டையும் பண்ணுங்க: சின்ன chunks-ஐ (ஒரு அல்லது ரெண்டு paragraphs) index பண்ணுங்க, ஒவ்வொண்ணும் எந்த section-ல இருந்து வந்துச்சுன்னு store பண்ணுங்க. ஒரு சின்ன chunk match ஆகும்போது, model-க்கு முழு parent section-ஐ (அல்லது அந்த chunk-ஐயும் அதோட பக்கத்து chunks-ஐயும்) கொடுங்க. இது பெரும்பாலும் எந்த ஒரு chunk size-ஐயும் விட நல்லா வேலை செய்யும்.

**Model எழுதுற context.** Headings வலுவா இல்லாத documents-க்கு, ஒரு மலிவான model ஒவ்வொரு chunk-க்கும் அது எங்க இருக்குன்னு சொல்லும் ஒரு sentence எழுதலாம் ("2026 leave policy-ல, earned leave-ஐ carry forward பண்றது பத்தின section-ல இருந்து"). Embed பண்றதுக்கு முன்னாடி அதை முன்னாடி சேருங்க. இதுக்கு ingestion நேரத்துல ஒரு chunk-க்கு ஒரு call செலவாகும், ஒரு தடவை தான். Vague-ஆன chunks-க்கு retrieval-ஐ இது மேம்படுத்தும். முழு document-ஐ prompt caching பண்ணா இது ரொம்ப மலிவாகும்.

**அளந்து பாருங்க, அப்புறம் தேர்ந்தெடுங்க.** Practice-ல இருந்து 20-கேள்வி test-ஐ வச்சுக்கோங்க. ஒவ்வொரு strategy-க்கும் size-க்கும் recall at 5-ஐ ஒரு சின்ன table-ல record பண்ணுங்க. Numbers பார்த்து தேர்ந்தெடுங்க, அந்த table-ஐ index settings-ஓட வச்சுக்கோங்க.

## ஒரு worked example

Pune-ல ஒரு manufacturing company-யோட HR assistant, 120 பக்க employee handbook-ல இருந்து கேள்விகளுக்கு பதில் சொல்லுது.

முதல் முயற்சி: overlap இல்லாம fixed 2,000-character chunks. 40 real employee கேள்விகளோட test பண்ணப்போ, சரியான passage top five results-ல இருக்குறது 55% தான். Failures: leave section-ஓட table ரெண்டு chunks-ஆ பிளந்திருந்துச்சு; "notice period" பத்தின answers-ல notice period, probation, resignation கலந்த chunks retrieve ஆச்சு.

ரெண்டாவது முயற்சி: headings-ல பிரிச்சு, அப்புறம் paragraphs, சுமார் 400 tokens வரை, 60-token overlap-ஓட; tables முழுசா; title-உம் section path-உம் முன்னாடி சேர்த்து. இப்போ சரியான passage 85% கேள்விகளுக்கு top five-ல இருக்கு.

மூணாவது முயற்சி, 200-token chunks: 82%, context இல்லாத answers கூடுச்சு. அவங்க 400-token version-ஐயே வச்சுக்கிறாங்க.

| Attempt | Strategy | Right passage in top 5 |
| --- | --- | --- |
| 1 | Fixed 2,000 characters, no overlap | 55% |
| 2 | Headings then paragraphs, ~400 tokens, 60-token overlap, tables whole, title path prepended | 85% |
| 3 | Same, but ~200 tokens | 82%, more answers missing context |

மிகப்பெரிய ஒரே gain, leave table-ஐ முழுசா வச்சதுல வந்தது: attempt 1-ஓட 18 failures-ல எட்டு, leave entitlements பத்தின கேள்விகள்.

**Employees என்ன கவனிச்சாங்க.** மாற்றத்துக்கு அப்புறம், ரொம்ப common புகாரான "பாதி answer தான் கொடுக்குது" கிட்டத்தட்ட மறைஞ்சிடுச்சு. மொத்த கேள்விகள்ல மூணுல ஒரு பங்கா இருந்த leave கேள்விகளுக்கு, இப்போ முழு table retrieve ஆச்சு. அதனால assistant, முதல் சில rows-ஐ மட்டும் quote பண்ணாம, "என் மூணாவது வருஷத்துல எத்தனை earned leaves கிடைக்கும்?"னு கேட்டா சரியா பதில் சொல்ல முடிஞ்சுது.

## பொதுவா பண்ற தப்புகள்

- **Fixed-size cuts tables, sentences வழியா வெட்டுறது.**
- **Overlap இல்லாம இருக்கிறது.** Boundaries-ல பிளந்த ideas தொலைஞ்சு போகும்.
- **"Context வச்சுக்க"ன்னு பெரிய chunks use பண்றது.** Retrieval மோசமாகும், prompts costly ஆகும்.
- **Headings, page numbers-ஐ இழக்கிறது.**
- **அளக்கவே இல்லாம இருக்கிறது.** Real கேள்விகள்ல sizes-ஐ test பண்ணுங்க.
- **ஒரு தடவை chunk பண்ணிட்டு திரும்ப test பண்ணாம இருக்கிறது.** Documents அல்லது கேள்விகள் மாறினா, உங்க test set-ஓட retrieval-ஐ மறுபடி check பண்ணுங்க.
- **Repeat ஆகுற page headers, footers ஒவ்வொரு chunk-லயும் இருக்கிறது.**
- **எல்லா document types-க்கும் ஒரே chunk size-ஐ தேர்ந்தெடுக்கிறது.** Policies, FAQs, tables, tickets-க்கு வேற வேற strategies வேணும்.
- **Retrieval test-ஐ rerun பண்ணாம chunking-ஐ மாத்துறது.**

## Chunking பெருசா பாதிக்காத இடங்கள்

- **சின்ன documents**, ஒரு பக்க notices மாதிரி, அவை ஒரு chunk-லயே முழுசா பொருந்தும்.
- **ஏற்கனவே structured ஆன items**, ஒரு record-க்கு ஒரு FAQ pair, ஒரு product அல்லது ஒரு ticket மாதிரி.
- **Context-க்குள்ளயே பொருந்துற சின்ன collections**, அங்க retrieval-ஐயே தவிர்த்துடலாம்.

## Demo-ல இருந்து production-க்கு

- **Chunking code, settings-ஐ version பண்ணுங்க**, index-ஓட சேர்த்து record பண்ணுங்க.
- **மாற்றம் வரும்போது ஒரு நேரத்துல ஒரு document-ஐ மட்டும் re-chunk பண்ணுங்க**, chunk ids-ல document ids-ஐ use பண்ணி.
- **Retrieval test-ஐ வச்சிருங்க**, ஒவ்வொரு chunking மாற்றத்துக்கும் rerun பண்ணுங்க.
- **ஒவ்வொரு ingestion-க்கு அப்புறமும் chunks-ஓட ஒரு sample-ஐ கண்ணால பாருங்க**: உடைஞ்ச tables, நடுவுல வர்ற headers சீக்கிரம் தெரிஞ்சிடும்.
- **ஒவ்வொரு document-க்கும் chunk counts, sizes-ஐ track பண்ணுங்க**, 200 பக்க manual மூணு chunks மட்டும் கொடுக்குற மாதிரி parsing failures-ஐ பிடிக்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற Pinecone-ஓட chunking strategies guide-ஐ படிங்க.

1. ஒரு நீளமான document-ஐ மூணு விதமா chunk பண்ணுங்க: fixed size, structure வழியா recursive, structure-ஓட overlap, headings சேர்த்து.
2. 20 கேள்விகளை, ஒவ்வொண்ணுக்கும் பதில் இருக்குற passage-ஓட எழுதுங்க.
3. ஒவ்வொரு method-க்கும் சரியான passage எத்தனை தடவை top five-ல வருதுன்னு அளங்க.
4. உங்க சிறந்த method-ல small-to-big retrieval-ஐ சேர்த்து, அதே 20 கேள்விகள்ல answer quality மாறுதான்னு அளங்க.
