## இது என்ன

Language-model systems-ஓட செலவை குறைக்க ரெண்டு மிக வலுவான levers:

- **Model tiering** (அல்லது routing): ஒவ்வொரு request-க்கும் மிகவும் capable model தேவையில்ல. Classify பண்றது, extract பண்றது, எளிமையான கேள்விகளுக்கு பதில் சொல்றதை சின்ன, மலிவான, fast model-ஆல பண்ணுங்க; கஷ்டமானதை மட்டும் பெரிய model-க்கு அனுப்புங்க.
- **Batching**: இரவு documents tag பண்றது, நேத்துத்து tickets-ஐ summarise பண்றது, corpus-ஐ re-embed பண்றது மாதிரி, சில நொடிகள்ல answer தேவையில்லாத வேலை **batch API** வழியா போகும். Providers batches-ஐ மணி நேரங்களுக்குள்ள, பெரிய discount-ஓட, பெரும்பாலும் சாதாரண விலையில கிட்டத்தட்ட பாதிக்கு process பண்ணுவாங்க.

ரெண்டும் உங்க traffic தெரிஞ்சிருக்கிறதை சார்ந்தவை: requests-ல எவ்ளோ ஈசி, எவ்ளோ காத்திருக்கலாம்.

```flow
Incoming work -> மணி நேரம் காத்திருக்கலாமா?
மணி நேரம் காத்திருக்கலாமா? -[ஆமா]-> Batch API, discount-ஓட | ids வச்சு results, failures-ஐ மறுபடி ஓட்டு
மணி நேரம் காத்திருக்கலாமா? -[இல்ல]-> சின்ன model -> Validator pass ஆச்சா?
Validator pass ஆச்சா? -[ஆமா]-> Answer
Validator pass ஆச்சா? -[இல்ல, கிட்டத்தட்ட 2.5%]-> பெரிய model -> Answer
Fit summaries மாதிரி கஷ்டமான task -[நேரடியா]-> பெரிய model
```

இந்த lesson, மாசத்துக்கு 400,000 resumes-ஐ process பண்ற Pune-ல உள்ள ஒரு HR-tech company-ஓட resume-screening service-ஐ பின்தொடருது.

## இது எப்படி work ஆகுது

**Tiering patterns.**

- *Task வாரியா fixed*: ஒவ்வொரு feature-ம் தன்னோட evals-ஐ pass பண்ற மலிவான model-ஐ use பண்ணும். Standard form-ல இருந்து extraction-க்கு சின்ன model போதும்; legal summary எழுத பெரிய model தேவைப்படலாம். இது மிக எளிமையான, மிக பொதுவான முறை.
- *Cascade*: முதல்ல சின்ன model-ஐ try பண்ணுங்க; அதோட output-ஐ check பண்ணுங்க (confidence, ஒரு validator, "தெரியல"ன்னு அதுவே சொல்றது); check fail ஆனா மட்டும் பெரிய model-க்கு escalate பண்ணுங்க.
- *Router*: ஒரு classifier அல்லது சின்ன model கஷ்டத்தை கணிச்சு, முன்கூட்டியே model-ஐ தேர்ந்தெடுக்கும். RouteLLM மாதிரி research systems இதை preference data-ல இருந்து கத்துக்கும்.

ஒவ்வொரு route-க்கும் தனி eval வேணும். நிஜமான கேள்வி "சின்ன model நல்லதா?" இல்ல, "நாம அனுப்புற requests-ல அது போதுமான அளவு நல்லதா?" அது.

**Batching patterns.** Requests-ஐ ஒரு file-ல சேகரிங்க (ஒரு request-க்கு ஒரு JSON line, உங்க சொந்த id-ஓட), batch-ஐ submit பண்ணுங்க, poll பண்ணுங்க அல்லது notify ஆகுங்க, அப்புறம் results-ஐ ids-ஓட match பண்ணுங்க. பகுதி failure-க்கு design பண்ணுங்க: சில items error ஆகி மறுபடி submit பண்ண வேணும். Batch வேலையை idempotent-ஆ வைங்க, அப்பதான் reruns safe.

**சேர்த்து பயன்படுத்த வேண்டிய மத்த cost levers.** நீளமான, திரும்ப வர்ற prefixes-க்கு prompt caching; குட்டி prompts, outputs (உங்களுக்கு வேண்டிய fields-ஐ மட்டும் கேளுங்க); reranking-க்கு பிறகு குறைவான retrieve ஆன chunks; ஒரே மாதிரி answers-ஐ cache பண்றது.

**ஒரு call-க்கு cost மட்டும் இல்ல, தீர்ந்த task-க்கு cost-ஐ அளங்க.** பாதி நேரம் fail ஆகி retry அல்லது ஒரு ஆள் தேவைப்படுற மலிவான model மொத்தத்துல அதிகமா செலவாகலாம்.

**Resume pipeline-க்கான routes:**

| Task | Route | ஏன் | ஆதாரம் |
| --- | --- | --- | --- |
| Field extraction | சின்ன model, validation fail ஆனா escalate | சின்ன model கிட்டத்தட்ட அதே அளவு accurate | 500 resumes-ல 98%-க்கு எதிரா 97% |
| Fit summary | பெரிய model | சின்ன model தெளிவா மோசம் | Recruiter ratings |
| Bulk uploads | இரவு Batch API | காலைக்குள்ள வேணும், சில நொடிகள்ல இல்ல | Discount விலை |
| பகல் uploads | Real time | Recruiters காத்திருக்காங்க | Latency தேவைகள் |

**Cascade-க்கு validator கட்டுறது.** எது escalate ஆகும்ங்கிறதை check தான் முடிவு பண்ணும், அதனால அது மோசமான outputs-ஐ நம்பகமா பிடிக்கணும். Extraction-க்கு, JSON schema-க்கு எதிரா validate பண்ணுங்க, தேவையான fields இருக்கான்னும் நம்பும்படி இருக்கான்னும் check பண்ணுங்க (email-ல at sign இருக்கணும், அனுபவ வருஷங்கள் 0-க்கும் 50-க்கும் நடுவுல), முடிஞ்சா totals-ஐ ஒப்பிடுங்க. Free text-க்கு, மலிவான judge அல்லது "தெரியல"ன்னு அதுவே சொல்றது வேலை செய்யலாம், ஆனா அதை test பண்ணுங்க: நம்புறதுக்கு முன்னாடி label பண்ணின set-ல எத்தனை மோசமான outputs-ஐ அது தவறவிடுதுன்னு அளங்க.

**Batch job-ஐ ஓட்டுறது.** ஒரு request-க்கு ஒரு line, உங்க சொந்த id-ஓட எழுதி, submit பண்ணி, batch id-ஐ record பண்ணுங்க. Results வந்ததும், ids வச்சு match பண்ணி, successes-ஐ எழுதி, failures-ஐ ஒரு புது batch-ல சேகரிங்க. ஒவ்வொரு write-ஐயும் idempotent-ஆ ஆக்குங்க, அப்பதான் crash-க்கு பிறகு batch-ஐ மறுபடி ஓட்டுனா duplicates உருவாகாது.

**Code-ல ஒரு cascade.** முதல்ல சின்ன model, கடுமையான validator, check fail ஆனா மட்டும் பெரிய model:

```python
import json
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()
SMALL, LARGE = "claude-haiku-5-5", "claude-sonnet-5-5"     # check the docs for current names

class Resume(BaseModel):
    name: str
    years_experience: float
    skills: list[str]
    last_employer: str | None = None

def extract(model, text):
    r = client.messages.create(model=model, max_tokens=500,
        messages=[{"role": "user", "content": "Return only JSON with name, years_experience, skills, "
                   f"last_employer (null if absent).\n\n{text}"}])
    out = "".join(b.text for b in r.content if b.type == "text")
    return out, r.usage

def valid(raw, text):
    try:
        item = Resume.model_validate_json(raw)
    except ValidationError:
        return None
    if not 0 <= item.years_experience <= 50 or not item.skills:
        return None
    if item.name.split()[0].lower() not in text.lower():      # the name must appear in the resume
        return None
    return item

def cascade(text, stats):
    raw, usage = extract(SMALL, text)
    stats["small_calls"] += 1
    if (item := valid(raw, text)):
        return item
    stats["escalated"] += 1
    raw, usage = extract(LARGE, text)
    return valid(raw, text)            # None goes to a person
```

Escalation rate-ஐ track பண்ணுங்க. அது ஏறுனா, சின்ன model ஒரு புது வகை input-ஓட திணறுது, சேமிப்பு குறையுதுன்னு அர்த்தம்.

**Anthropic-ஓட Message Batches API-ஓட batch requests.** அவசரம் இல்லாத வேலையை ஒரே தடவையா submit பண்ணி, உங்க சொந்த ids வச்சு results-ஐ எடுங்க:

```python
import time

def run_batch(items):
    batch = client.messages.batches.create(requests=[
        {"custom_id": it["id"],
         "params": {"model": SMALL, "max_tokens": 500,
                    "messages": [{"role": "user", "content": f"Return only JSON ...\n\n{it['text']}"}]}}
        for it in items])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    done, failed = {}, []
    for result in client.messages.batches.results(batch.id):
        if result.result.type == "succeeded":
            msg = result.result.message
            done[result.custom_id] = "".join(b.text for b in msg.content if b.type == "text")
        else:
            failed.append(result.custom_id)
    return done, failed            # resubmit `failed`, or send them to the real-time path
```

Batch processing சாதாரண calls-ஐ விட மலிவா இருக்கும், ஒரு நாள் வரை ஆகலாம்; இப்போதைய விலையையும் turnaround-ஐயும் தேதியோட check பண்ணுங்க. Batch outputs-ஐ real-time outputs-ஐ validate பண்றது மாதிரியே சரியா validate பண்ணுங்க.

**தீர்ந்த task-க்கு cost, அளந்து.** 200 items sample-ல, ஒவ்வொரு path-க்கும் பண்ணின model calls, tokens, cost, கடைசி result சரியான்னு record பண்ணுங்க. அப்புறம் ஒப்பிடுங்க:

| Path | Accuracy | ஒரு item-க்கு cost |
| --- | --- | --- |
| எல்லாத்துக்கும் பெரிய model | அளந்தது | அளந்தது |
| Cascade | அளந்தது | அளந்தது, escalations உட்பட |
| Cascade + uploads-க்கு batch | அளந்தது | அளந்தது |

அந்த task-க்கான accuracy bar-ஐ எட்டுற மிக மலிவான path-ஐ தேர்ந்தெடுங்க.

## ஒரு worked example

Pune-ல ஒரு HR-tech company தங்க clients-க்காக resumes-ஐ screen பண்ணுது. ஒவ்வொரு resume-க்கும் structured extraction (name, skills, experience), job description-க்கு எதிரா fit summary. Volume: மாசத்துக்கு 400,000 resumes, பெரும்பாலும் ஒரு hiring drive-க்கு முன்னாடி சாயங்காலம் bulk-ஆ upload ஆகும்.

முன்னாடி: ஒவ்வொரு resume-ம் real time-ல பெரிய model வழியா போச்சு. மாசாந்திர model செலவு: கிட்டத்தட்ட ₹14 lakh.

Redesign:

1. Extraction, கடுமையான JSON schema-ஓட சின்ன model-க்கு போகுது. 500 resumes golden set-ல, field accuracy பெரிய model-ஓட 98%-க்கு எதிரா 97%; validation failures (2.5%) பெரிய model-க்கு escalate ஆகும்.
2. Fit summary பெரிய model-லயே இருக்கு, ஏன்னா recruiter ratings-ல சின்னது தெளிவா மோசமா score பண்ணுச்சு.
3. Bulk uploads இரவு discount-ஓட batch API வழியா போகும். வேலை நாள்ல சேர்ந்த resumes மட்டும் real time-ல ஓடும்.
4. ஆயிரக்கணக்கான resumes-க்கு ஒரே மாதிரி இருக்குற job description, prompt-ஓட ஆரம்பத்துல இருந்து cache ஆகுது.

மாசாந்திர செலவு கிட்டத்தட்ட ₹5 lakh-ஆ குறையுது. Summaries-க்கான recruiter ratings மாறல, ரெண்டு numbers-ஐயும் மாசாந்திர review-ல பக்கத்துல பக்கத்துல report பண்றீங்க.

| அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| மாசாந்திர model செலவு | கிட்டத்தட்ட ₹14 lakh | கிட்டத்தட்ட ₹5 lakh |
| Extraction field accuracy | 98% | 97% + escalation |
| Summaries-க்கு recruiter rating | Baseline | மாறல |

## பொதுவா பண்ற தப்புகள்

- **Vibe வச்சு சின்ன model-ஐ தேர்ந்தெடுக்கிறது.** ஒவ்வொரு route-க்கும் evals ஓட்டுங்க; மலிவா இருந்து தப்பா இருந்தா அது costly.
- **User-ஐ எதிர்கொள்ற வேலையை batch பண்றது.** Batches மணி நேரங்கள் ஆகலாம். காத்திருக்கக்கூடியதை மட்டும் batch பண்ணுங்க.
- **Escalation path இல்லாம இருக்கிறது.** நம்பகமான failure check இல்லாத cascade மோசமான answers-ஐ முன்னாடி அனுப்பும்.
- **கணக்குல retries-ஐ புறக்கணிக்கிறது.** தீர்ந்த task-க்கு cost-ஐ எண்ணுங்க.
- **பகுதி batch failures-ஐ மறக்குறது.** சில items எப்பவும் fail ஆகும்; rerun-க்கு plan பண்ணுங்க.
- **பலவீனமான validator**, சின்ன model-ஓட மோசமான outputs-ஐ pass பண்ணி, cascade quality-ஐ இழந்து பணத்தை சேமிக்குது.
- **Fail ஆன batch items-ஐ புறக்கணிக்கிறது**, அவை அமைதியா காணாம போகும்.
- **தீர்ந்த task-க்கு cost-க்கு பதிலா ஒரு call-க்கு cost-ஐ ஒப்பிடுறது.**

## Tiering, batching எப்போ worth இல்ல

- **குறைவான volume**: சேமிப்பு engineering time-ஐ விட சின்னது.
- **ஒவ்வொரு request-ம் அவசரம்**, அதனால batching பொருந்தாது.
- **சின்ன model உங்க evals-ல fail ஆகுது**, நீங்க அனுப்ப போற traffic-ல.
- **Cascade escalate பண்ண நம்பகமான validator இல்ல.**

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு feature-க்கும் escalation rate, தீர்ந்த task-க்கு cost-ஐ track பண்ணுங்க.**
- **ஒவ்வொரு model அல்லது prompt மாற்றத்துலயும் routes-ஐ மறுபடி evaluate பண்ணுங்க.**
- **Batch failures-ஐ ids வச்சு, retries, ஒரு report-ஓட கையாளுங்க.**
- **அவசர வேலைக்கும் batch வேலைக்கும் தனி limits வைங்க**, அப்பதான் இரவு jobs பகல் users-ஐ மெதுவாக்காது.
- **Cost ஒப்பீட்டுல prices-ஐ தேதியோட record பண்ணுங்க.**

## Practice பண்ணுங்க

உங்க provider-ஓட batch processing guide-ஐயும் RouteLLM post-ஐயும் படிங்க.

1. ஒரு feature-ஐ எடுத்து 50 golden cases-ல ஒரு சின்ன, ஒரு பெரிய model-ஐ evaluate பண்ணுங்க. ஒவ்வொண்ணுக்கும் accuracy, ஒரு case-க்கு cost-ஐ record பண்ணுங்க.
2. ஒரு cascade கட்டுங்க: முதல்ல validator-ஓட சின்ன model, failures-ஐ பெரிய model-க்கு escalate பண்ணி. Blended accuracy, cost-ஐ அளங்க.
3. ஒரு batch API வழியா 100 அவசரம் இல்லாத requests-ஐ ஓட்டி, fail ஆன items-ஐ கையாளுங்க, cost-ஐ real-time calls-ஓட ஒப்பிடுங்க.
4. 50 resumes-ஐ cascade வழியா ஓட்டி, escalation rate, சரியான extraction-க்கு cost-ஐ record பண்ணி, பெரிய model மட்டும் use பண்றதோட ஒப்பிடுங்க.
