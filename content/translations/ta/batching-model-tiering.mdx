## இது என்ன

சேர்ந்து வேலை செய்யுற மூணு cost levers:

- **Model tiering** (அல்லது routing). ஒவ்வொரு request-க்கும் ரொம்ப capable-ஆன model தேவையில்ல. Classify பண்றது, extract பண்றது, simple கேள்விகளுக்கு பதில் சொல்றதை ஒரு சின்ன, cheap, fast model வச்சு பண்ணுங்க; கஷ்டமானதை மட்டும் ஒரு பெரிய model-க்கு அனுப்புங்க.
- **Reasoning effort.** இப்போதைய models பதில் சொல்றதுக்கு முன்னாடி யோசிக்குது, அந்த thinking tokens-க்கு output tokens-ஆ தான் bill பண்ணுவாங்க, அந்த text-ஐ நீங்க பாக்கவே இல்லைன்னாலும். Model எவ்வளவு யோசிக்கணும்னு ஒரு effort setting control பண்ணும். ஈஸியான, அதிக volume வேலைக்கு default அரிதா தான் தேவைப்படும்.
- **Batching.** சில நொடிகள்ல answer தேவையில்லாத வேலை ஒரு provider-ஓட **batch API** வழியா போகும்: நிறைய requests-ஐ ஒரே நேரத்துல upload பண்ணி, results-ஐ அப்புறம் பெரிய discount-ஓட வாங்குவீங்க. உதாரணங்கள்: இரவுல documents-ஐ tag பண்றது, நேத்தைய tickets-ஐ summarise பண்றது, ஒரு archive-ஐ re-score பண்றது.

வார்த்தைகள் பத்தி ஒரு note. இந்த lesson-ல "batching"-னா provider-ஓட discount உள்ள, asynchronous product. **Continuous batching** வேற விஷயம்: vLLM மாதிரி ஒரு serving engine உங்க சொந்த GPUs-ல ஒரே நேரத்துல நிறைய requests-ஐ எப்படி அடுக்குதுங்குறது அது. "Inside LLM inference: prefill, decode and the KV cache" lesson அதை cover பண்ணுது.

## இது எப்படி work ஆகுது

### மூணு tiering patterns

- **Task வாரியா fixed.** ஒவ்வொரு feature-உம் அதோட evals-ஐ pass பண்ற ரொம்ப cheap-ஆன model-ஐ use பண்ணும். ஒரு standard form-ல இருந்து extraction-க்கு ஒரு சின்ன model போதுமா இருக்கலாம்; ஒரு legal summary-க்கு பெரிய model தேவைப்படலாம். இது தான் ரொம்ப simple-ஆன, ரொம்ப common-ஆன pattern. இங்க ஆரம்பிங்க.
- **Cascade.** முதல்ல சின்ன model-ஐ try பண்ணுங்க, அதோட output-ஐ check பண்ணுங்க, check fail ஆனா மட்டும் பெரிய model-க்கு escalate பண்ணுங்க. Structured extraction மாதிரி, ஒரு cheap check நல்ல output-ஐயும் மோசமான output-ஐயும் பிரிச்சுப் பாக்க முடியுற tasks-க்கு இது பொருந்தும்.
- **Router.** ஒரு classifier, அல்லது ஒரு சின்ன model, கஷ்டத்தை கணிச்சு முன்னாடியே model-ஐ தேர்ந்தெடுக்கும். RouteLLM மாதிரி research systems இதை preference data-ல இருந்து கத்துக்குது. Router chat-க்கு பொருந்தும்: அங்க ரெண்டு calls-ஐ ஒண்ணு பின்னாடி ஒண்ணா பண்ண முடியாது, check பண்ண இன்னும் output-உம் இருக்காது.

ஒவ்வொரு route-க்கும் அதோட சொந்த eval வேணும். உண்மையான கேள்வி "சின்ன model நல்லதா?" இல்ல, "நாம அதுக்கு அனுப்புற requests-ல அது போதுமான அளவு நல்லதா?"

### Cascade cost formula

ஒவ்வொரு item-க்கும், ஒரு cascade-க்கு சின்ன call-ஓட cost ஆகும், கூட escalate ஆகுற share-க்கு பெரிய call-ஓட cost:

`cost per item = small cost + escalation rate × large cost`

Escalate ஆன items ரெண்டு calls-க்கும் pay பண்ணும். அதனால பத்துல ஒரு பங்கு விலையுள்ள ஒரு சின்ன model, 40% escalation-ஓட, பெரிய model தனியா ஆகுறதுல 0.1 + 0.4 = 0.5 தான் ஆகும்: quality நிலைச்சா பாதி விலை. Haiku 5.5-க்கும் Sonnet 5.5-க்கும் நடுவுல இருக்குற மாதிரி 20 மடங்கு அல்லது அதுக்கு மேல price gap இருந்தா, கிட்டத்தட்ட எல்லா item-உம் escalate ஆகுற வரை cascade cheap-ஆவே இருக்கும். பணம் அரிதா தான் risk. ரெண்டு விஷயங்கள் தான் risk: check உள்ள விடுற தப்பான answers, escalate ஆன requests-க்கு வர்ற extra காத்திருப்பு.

### Validators-உம் அவற்றோட miss rate-உம்

எது escalate ஆகும்னு check தான் முடிவு பண்ணுது, அதனால அதை வேற எந்த model-ஐயும் போல test பண்ணுங்க. Cheap checks-ஐ layers-ஆ use பண்ணுங்க:

1. **Format.** Output schema-படி parse ஆகுதா?
2. **Range.** Values நம்பக்கூடியதா இருக்கா? உதாரணமா, years of experience 0-ல இருந்து 50-க்குள்ள, குறைஞ்சது ஒரு skill.
3. **Grounding.** Answer source-ல இருக்கா? உதாரணமா, candidate-ஓட பேர், list பண்ண பெரும்பாலான skills, கடைசி employer resume text-ல இருக்கணும். பக்காவா format ஆன, ஆனா கற்பனையா உருவாக்குன values-ஐ இது பிடிக்கும்.
4. **Call-ல இருந்து வர்ற signals.** `max_tokens`-ஐ தொட்டதால நின்ன ஒரு response, அல்லது ஒரு refusal, ஒரு failure, answer இல்ல.

அப்புறம் label பண்ணுன ஒரு golden set-ல சின்ன model-ஐ ஓட்டி **miss rate**-ஐ எண்ணுங்க: தப்பா இருந்த outputs-ல, எத்தனை எல்லா checks-ஐயும் pass பண்ணுச்சு? Format checks சத்தமான failures-ஐ பிடிக்கும். அமைதியான errors (நம்பக்கூடிய, ஆனா தப்பான employer) அவற்றை pass பண்ணிடும். Free text-க்கு, model தானே சொல்ற "unsure" அல்லது ஒரு cheap judge model இன்னொரு signal-ஐ சேர்க்கலாம், ஆனா அதோட miss rate-ஐயும் இதே மாதிரி அளங்க.

### Reasoning effort-உம் thinking tokens-உம்

Claude models-ல, `output_config.effort` `low`, `medium`, `high`, `xhigh` அல்லது `max` எடுக்கும். Thinking உட்பட எல்லா output tokens-ஐயும் இது shape பண்ணும். November 2026 நிலவரப்படி, default Claude Haiku 5.5-லயும் Claude Opus 5.5-லயும் `medium`, Claude Sonnet 5.5-ல `high`. Simple, அதிக volume வேலைக்கு Anthropic `low`-ஐ suggest பண்ணுது.

மூணு gotchas:

- **Thinking `max_tokens`-ல சேரும்.** ரொம்ப tight-ஆன `max_tokens` ஒரு reply-ஐ பாதி answer-லயே வெட்டிடலாம். இடம் விடுங்க, `stop_reason == "max_tokens"`-ஐ ஒரு failure-ஆ நடத்துங்க.
- **Thinking switches model-க்கு model மாறும்.** Haiku 5.5-ல `high` effort அல்லது அதுக்கு கீழ `thinking: {"type": "disabled"}` அனுப்பலாம். Sonnet 5.5-உம் Opus 5.5-உம் அதை ஒரு error-ஓட reject பண்ணும், அதனால அதுக்கு பதிலா effort-ஐ குறைங்க.
- **Effort-உம் ஒரு நாலாவது tier.** ஒரு cascade build பண்றதுக்கு முன்னாடி, பெரிய model-ஐயும் குறைவான effort-ல test பண்ணுங்க. சில நேரம் அது ஒரே model, ஒரே cache வச்சே quality-ஐ நிலைக்க வைக்கும்.

ஒவ்வொரு route-க்கும் `usage.output_tokens`-ஐ படிங்க. Output tokens கண்ணுக்கு தெரியுற reply-ஐ விட ரொம்ப அதிகமா இருந்தா, உங்க பணம் thinking-ல தான் போகுது.

### Batching: இது எப்படி நடந்துக்கும்

இவை 28 November 2026 நிலவரப்படி Anthropic-ஓட Message Batches rules; மத்த providers details-ல மாறுபடுவாங்க.

- **Price:** input, output tokens-ல 50% off. OpenAI-உம் Google-உம் discount உள்ள batch modes குடுக்குறாங்க; அவங்களோட இப்போதைய terms-ஐ check பண்ணுங்க.
- **Speed:** பெரும்பாலான batches ஒரு மணி நேரத்துக்குள்ள முடியும், ஆனா 24 மணி நேரத்துக்குள்ள process ஆகாத எந்த request-உம் expire ஆகும். யாராவது காத்திருக்குற வேலையை batch பண்ணவே பண்ணாதீங்க.
- **Size:** ஒரு batch-க்கு 100,000 requests அல்லது 256 MB வரை. Results 29 நாள் கிடைக்கும்.
- **Results:** அவை எந்த order-லயும் வரலாம். உங்க சொந்த `custom_id` வச்சு match பண்ணுங்க. ஒவ்வொரு item-உம் `succeeded`, `errored`, `canceled` அல்லது `expired`; கடைசி மூணுக்கு உங்களுக்கு bill பண்ண மாட்டாங்க.
- **Limits:** batches-க்கு எல்லா models-க்கும் share ஆகுற தனி rate limits இருக்கு: ஒரு நிமிஷத்துக்கு requests, கூட queue-ல காத்திருக்குற requests-க்கு ஒரு cap (Build tier-ல 300,000). இவை real-time limits-ல இருந்து தனி, batches-க்கு ramp limits கிடையாது. அதனால ஒரு பெரிய overnight job, பகல்ல recruiters நம்பியிருக்குற per-minute token limits-ஐ காலி பண்ணாது.
- **Batch-ல allow இல்லாதவை:** streaming, fast mode, server-side fallbacks.

### இந்த picture-க்குள்ள caching

Prompt caching, tiering, batching கூட சேர்ந்தே வேலை செய்யும். Stable-ஆன பகுதியை முதல்ல வைங்க (instructions, அப்புறம் job description), அதை `cache_control` வச்சு mark பண்ணுங்க. Claude Opus 5.5, Sonnet 5.5, Haiku 5.5 குறைஞ்சது 512 tokens உள்ள prefixes-ஐ cache பண்ணும்; அதை விட குட்டியான prefix எந்த error-உம் இல்லாம சாதாரணமா process ஆகும். ஒரு 5-minute cache write-க்கு input price-ஓட 1.25 மடங்கு ஆகும், ஒரு 1-hour write-க்கு 2 மடங்கு. Reads ரொம்ப cheap. Batches-ல requests எந்த order-லயும் ஓடுறதால cache hits best effort தான். 1-hour cache-ஐ use பண்ணுங்க, Anthropic suggest பண்ற மாதிரி, மீதியை submit பண்றதுக்கு முன்னாடி prefix-ஐ write பண்ண முதல்ல ஒரு request அனுப்புங்க.

### Code-ல ஒரு cascade

Low effort-ல சின்ன model, layers-ஆ checks, ஒரு check fail ஆனா மட்டும் பெரிய model:

```python
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()
SMALL, LARGE = "claude-haiku-5-5", "claude-sonnet-5-5"   # check the models page for current names

PROMPT = ("Return only JSON with name, years_experience, skills and "
          "last_employer (null if absent). Copy names exactly as written.\n\n")

class Resume(BaseModel):
    name: str
    years_experience: float
    skills: list[str]
    last_employer: str | None = None

def extract(model, effort, text):
    r = client.messages.create(
        model=model, max_tokens=2000,              # thinking counts toward max_tokens
        output_config={"effort": effort},
        messages=[{"role": "user", "content": PROMPT + text}])
    if r.stop_reason != "end_turn":                # cut off or refused: treat as a failure
        return None, r.usage
    return "".join(b.text for b in r.content if b.type == "text"), r.usage

def valid(raw, text):
    if raw is None:
        return None
    try:
        item = Resume.model_validate_json(raw)
    except ValidationError:
        return None
    page = text.lower()
    words = item.name.lower().split()
    if not words or not all(w in page for w in words):          # name must be in the resume
        return None
    if not 0 <= item.years_experience <= 50 or not item.skills:
        return None
    found = sum(s.lower() in page for s in item.skills)
    if found < 0.8 * len(item.skills):                          # most skills must be in the text
        return None
    if item.last_employer and item.last_employer.lower() not in page:
        return None
    return item

def cascade(text, stats):
    raw, _ = extract(SMALL, "low", text)
    stats["small"] += 1
    if item := valid(raw, text):
        return item
    stats["escalated"] += 1
    raw, _ = extract(LARGE, "high", text)
    return valid(raw, text)                                      # None goes to a person
```

ஒரு empty name `if not words` check-ல fail ஆகி, crash ஆகாம escalate ஆகும். Escalation rate-ஐ தினமும் track பண்ணுங்க. அது ஏறுனா, ஒரு புது வகை input வந்திருக்கு, savings சுருங்குது.

### Fit summary, cache பண்ணி batch பண்ணது

ஒரு hiring drive-ல ஒவ்வொரு resume-க்கும் job description ஒரே மாதிரி தான், அதனால அது முதல்ல போகும், caching-க்கு mark பண்ணப்படும்:

```python
import time

def run_batch(items, job_description):
    batch = client.messages.batches.create(requests=[
        {"custom_id": it["id"],                                  # your id: 1-64 letters, digits, - or _
         "params": {"model": LARGE, "max_tokens": 4000,
                    "output_config": {"effort": "medium"},
                    "system": [{"type": "text",
                                "text": "You screen resumes for this role.\n\n" + job_description,
                                "cache_control": {"type": "ephemeral", "ttl": "1h"}}],
                    "messages": [{"role": "user",
                                  "content": "Write a five-line fit summary.\n\n" + it["text"]}]}}
        for it in items])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    done, retry = {}, []
    for r in client.messages.batches.results(batch.id):         # any order: key by custom_id
        if r.result.type == "succeeded":
            m = r.result.message
            done[r.custom_id] = "".join(b.text for b in m.content if b.type == "text")
        else:                                                    # errored, expired or canceled
            retry.append(r.custom_id)
    return done, retry
```

`retry`-ஐ ஒரு புது, சின்ன batch-க்கு அனுப்புங்க, அல்லது காலைக்குள்ள recruiters-க்கு தேவைன்னா real-time path-க்கு அனுப்புங்க. Batch outputs-ஐ real-time outputs-ஐ மாதிரியே validate பண்ணுங்க. ஒரு sample-ல `usage.cache_read_input_tokens`-ஐ check பண்ணுங்க: அது zero-லயே இருந்தா, prefix-ல ஏதோ ஒண்ணு மாறிக்கிட்டே இருக்கு.

## ஒரு worked example

Pune-ல ஒரு HR-tech company தன் clients-க்காக resumes-ஐ screen பண்ணுது. ஒவ்வொரு resume-க்கும் structured extraction (name, experience, skills, last employer) நடக்கும், job description-ஓட compare பண்ணி ஒரு fit summary-உம் வரும். Volume மாசத்துக்கு 400,000 resumes, அதுல கிட்டத்தட்ட 80% ஒரு hiring drive-க்கு முந்தைய சாயங்காலம் bulk-ஆ upload ஆகுது.

கீழே இருக்குற எல்லா figures-உம் assume பண்ண token counts வச்சு ஒரு illustration தான், உதாரணமா ஒரு dollar-க்கு ₹90, மேல இருக்குற 28 November 2026 prices வச்சு. உங்க சொந்த numbers `usage` logs-ல இருந்து வரும்.

**முன்னாடி.** எல்லாமே Claude Sonnet 5.5-ல real time-ல அதோட default `high` effort-ல ஓடுது. ஒரு resume-க்கு:

- Extraction: 3,400 input tokens ($0.0068), 900 output tokens, அதுல கிட்டத்தட்ட 650 thinking ($0.009). மொத்தம் $0.0158.
- Fit summary: 5,000 input tokens ($0.010), 1,400 output tokens, அதுல கிட்டத்தட்ட 1,050 thinking ($0.014). மொத்தம் $0.024.

அது ஒரு resume-க்கு $0.0398, மாசத்துக்கு $15,920, கிட்டத்தட்ட ₹14.3 lakh. கவனிங்க, ஒவ்வொரு call-லயும் thinking மட்டுமே 40%-க்கு மேல.

**Step 1: ஒரு golden set-ல validator-ஐ தேர்ந்தெடுக்குறது.** Team 500 resumes-ஐ கையால label பண்ணி, எல்லா field-உம் சரியா இருக்குற resumes-ஐ எண்ணுது:

| Path | Escalate ஆனது | Checks-ஐ pass பண்ண தப்பான outputs | முழுசா சரியான resumes |
| --- | --- | --- | --- |
| Sonnet 5.5 மட்டும் | பொருந்தாது | பொருந்தாது | 489 (97.8%) |
| Haiku 5.5 மட்டும் | பொருந்தாது | பொருந்தாது | 466 (93.2%) |
| Cascade, format, range checks | 15 (3%) | 34-ல 22 | 476 (95.2%) |
| Cascade, கூட grounding checks | 35 (7%) | 34-ல 7 | 489 (97.8%) |

Format-only validator 3% escalation-ல கவர்ச்சியா தெரிஞ்சுது, ஆனா 34 தப்பான outputs-ல 22-ஐ அது miss பண்ணுச்சு. Grounding checks escalation rate-ஐ ரெண்டு மடங்குக்கு மேல ஆக்குது, பெரிய model-ஓட quality-க்கு சமமா வருது. Team அவற்றை தேர்ந்தெடுக்குது.

**Step 2: levers-ஐ ஒவ்வொண்ணா apply பண்றது.**

| Lever | என்ன மாறுது | அப்புறம் மாசச் செலவு | மிச்சம் |
| --- | --- | --- | --- |
| ஆரம்பம் | எல்லாத்துக்கும் Sonnet 5.5, real time | ₹14.33 lakh | எதுவும் இல்ல |
| 1. Extraction-க்கு cascade | Low effort-ல Haiku 5.5: ஒரு resume-க்கு $0.0005, கூட escalations-க்கு 7% × $0.0158 | ₹9.22 lakh | ₹5.11 lakh |
| 2. Fit summaries-ல குறைவான effort | Medium effort: thinking கிட்டத்தட்ட 400 tokens-க்கு குறையுது, summary cost $0.0175 | ₹6.88 lakh | ₹2.34 lakh |
| 3. Bulk uploads-ஐ batch பண்றது | 80% resumes பாதி விலையில | ₹4.13 lakh | ₹2.75 lakh |
| 4. Job description-ஐ cache பண்றது | 2,000-token prefix, 90% calls அதை cache-ல இருந்து படிக்குது (batches-ல 1-hour writes, real time-ல 5-minute) | ₹3.45 lakh | ₹0.68 lakh |

ஒரு reviewer படிக்கிற மாதிரி table-ஐ படிங்க:

- **Lever 1:** escalations-க்கு ஆகுற செலவு, எல்லா சின்ன-model calls-ஐயும் சேர்த்ததை விட ரெண்டு மடங்குக்கு மேல. Escalation rate-ல ஒவ்வொரு point-உம் bill-ல தெரியும்.
- **Lever 2:** effort மாற்றத்துக்கு அதோட சொந்த eval தேவைப்பட்டுச்சு. Recruiters ரெண்டு settings-லயும் 100 summaries-ஐ blind-rate பண்ணி எந்த வித்தியாசமும் பாக்கல. அந்த check இல்லைன்னா, அது வெறும் guess தான்.
- **Lever 3:** batching அதுக்கு முன்னாடி இருக்குற எல்லாத்தையும் 0.6-ஆல பெருக்குது (80% பாதி விலையில, 20% முழு விலையில).
- **Lever 4:** இங்க caching-ஆல வர்ற மிச்சம் சின்னது, ஏன்னா 5,000 input tokens-ல prefix 2,000 தான். 400-token extraction instructions cache ஆகவே ஆகாது: அவை 512-token minimum-க்கு கீழ.

Bill மாசத்துக்கு கிட்டத்தட்ட ₹14.3 lakh-ல இருந்து கிட்டத்தட்ட ₹3.45 lakh-க்கு குறையுது, தோராயமா 76% குறைவு, golden-set accuracy-உம் recruiter ratings-உம் மாறாம. பகல் uploads real time-லயே இருக்கும். அங்க, escalate ஆகுற 7% resumes ரெண்டு calls-க்கு காத்திருக்கும், அதனால team அந்த path-க்கு p95 latency-ஐ தனியா track பண்ணுது.

## பொதுவா பண்ற தப்புகள்

- **Vibe வச்சு சின்ன model-ஐ தேர்ந்தெடுக்குறது.** ஒவ்வொரு route-க்கும் evals ஓட்டுங்க. Cheap-ஆ இருந்து தப்பா இருந்தா அது expensive தான்.
- **Low escalation rate-ஐ நம்புறது.** Format மட்டும் check பண்ற validator, நல்லா format ஆன ஆனா தப்பான answers-ஐ pass பண்ணிடும். அதோட miss rate-ஐ ஒரு golden set-ல அளங்க.
- **Cost per successful task-க்கு பதிலா cost per call-ஐ எண்ணுறது.** Escalations, retries, மனுஷங்க பண்ற fixes எல்லாத்தையும் சேருங்க.
- **Thinking tokens-ஐ கண்டுக்காம விடுறது.** ஒரு பெரிய model-ல default effort, reasoning-ஐ bill-ல ரொம்பப் பெரிய line ஆக்கிடலாம். ஒவ்வொரு route-க்கும் effort-ஐ set பண்ணி evals கூட check பண்ணுங்க.
- **`max_tokens`-ஐ ரொம்ப tight-ஆ வைக்கிறது.** Thinking அதுல சேரும், அதனால replies வெட்டப்பட்டு model failures மாதிரி தெரியும்.
- **Users-க்கு நேரடியா போற வேலையை batch பண்றது.** Batches பொதுவா ஒரு மணி நேரத்துக்குள்ள முடியும், ஆனா 24 மணி நேரம் வரை ஆகலாம்.
- **Fail ஆன batch items-ஐ தொலைச்சிடுறது.** `custom_id` வச்சு match பண்ணுங்க, errored, expired items-ஐ retry பண்ணுங்க, reruns duplicates உருவாக்காத மாதிரி writes-ஐ idempotent-ஆ வைங்க.
- **Escalation-ஓட latency-ஐ மறந்துடுறது.** Chat-ல, ஒரு cascade ரொம்பக் கஷ்டமான கேள்விகளை ரொம்ப slow ஆக்கும். ஒரு router அல்லது ஒரே ஒரு model users-க்கு நல்லா serve பண்ணலாம்.
- **Cache ஆக முடியாத prefix-ஐ cache பண்றது.** அது ரொம்ப குட்டியா இருக்கு, ஒவ்வொரு request-லயும் மாறுது, அல்லது பகல் uploads-க்கு நடுவுல 5-minute cache expire ஆகிடுது.

## Tiering, batching எப்போ worth இல்ல

- **குறைவான volume.** Savings, engineering நேரத்தை விட குறைவு.
- **ஒவ்வொரு request-உம் அவசரம்**, அதனால batching பொருந்தாது.
- **சின்ன model உங்க evals-ல fail ஆகுது**, நீங்க அனுப்பப் போற traffic-ல, பெரிய model-ல குறைவான effort setting-உம் உதவல.
- **Cascade escalate பண்ண நம்பகமான check எதுவும் இல்ல**, router-க்கு தெளிவான signal-உம் இல்ல.

## Demo-ல இருந்து production-க்கு

- **Escalation rate, validator miss rate, cost per successful task-ஐ track பண்ணுங்க**, ஒவ்வொரு feature-க்கும், ஒவ்வொரு வாரமும்.
- **Golden set-ஐ மறுபடி ஓட்டுங்க**, ஒவ்வொரு model, prompt அல்லது effort மாற்றத்துக்கும். Models-ஐ மாத்தும்போது effort-ஐ மறுபடி sweep பண்ணுங்க, ஏன்னா levels model-க்கு model வேற மாதிரி நடந்துக்கும்.
- **Batch failures-ஐ handle பண்ணுங்க**, id வச்சு, retries, ஒரு report, deadline-க்கு முன்னாடி ஒரு real-time fallback-ஓட.
- **அவசர வேலையையும் batch வேலையையும் தனியா வைங்க.** Batch-க்கு தனி limits இருக்கு; கட்டுப்பாடு இல்லாம ஓடுற ஒரு job real-time quota-வை காலி பண்ணாம இருக்க workspace limits use பண்ணுங்க.
- **Prices-ஐ தேதியோட பதிவு பண்ணுங்க**, ஒவ்வொரு cost comparison-லயும், ஒவ்வொரு review-க்கும் முன்னாடி அவற்றை மறுபடி check பண்ணுங்க.

## Practice பண்ணுங்க

உங்க provider-ஓட batch processing guide-ஐயும் RouteLLM post-ஐயும் படிங்க.

1. ஒரு feature-ஐ தேர்ந்தெடுத்து 50 golden cases-ல ஒரு சின்ன model-ஐயும் ஒரு பெரிய model-ஐயும் ஓட்டுங்க. ஒவ்வொண்ணுக்கும் accuracy, output tokens (thinking உட்பட), ஒரு case-க்கு cost-ஐ record பண்ணுங்க.
2. Format, range, grounding checks-ஓட ஒரு cascade build பண்ணுங்க. Escalation rate-ஐயும் validator-ஓட miss rate-ஐயும் report பண்ணுங்க.
3. அதே 50 cases-ல பெரிய model-ஐ ரெண்டு effort levels-ல ஓட்டி, quality-ஐயும் output tokens-ஐயும் compare பண்ணுங்க.
4. அவசரம் இல்லாத 100 requests-ஐ ஒரு batch-ஆ submit பண்ணி, fail ஆன items-ஐ `custom_id` வச்சு retry பண்ணி, cost-ஐ real-time calls கூட compare பண்ணுங்க.
5. Worked example-ல இருக்குற மாதிரி ஒரு lever-by-lever table எழுதுங்க, உங்க சொந்த `usage` numbers-ஐயும் தேதி போட்ட prices-ஐயும் வச்சு.
