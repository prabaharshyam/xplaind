## இது என்ன

நீங்க வேலை செய்யப்போற கிட்டத்தட்ட எல்லா company-யும் தன்னோட customers, orders, tickets, payments-ஐ PostgreSQL, MySQL, SQL Server மாதிரி ஒரு relational database-ல வச்சிருக்கும். அந்த databases-கிட்ட கேள்வி கேக்குற மொழி தான் **SQL**. ஒரு AI engineer-க்கு SQL optional இல்லை. இதுக்காக use பண்ணுவீங்க:

- AI system-க்கு தேவையான **data-வை எடுக்க**, உதாரணம்: resolutions-ஓட பழைய tickets;
- Build பண்றதுக்கு முன்னாடி **baseline அளக்க**: "இன்னைக்கு refunds-க்கு எவ்வளவு நேரம் ஆகுது?";
- System ship ஆனதுக்கு அப்புறம் **அது உதவுச்சான்னு check பண்ண**.

நாலு idea இந்த வேலையில பெரும்பகுதியை கவர் பண்ணும்:

| Idea | என்ன பண்ணும் | வழக்கமான use |

## இது எப்படி work ஆகுது

### Joins

Join, match ஆகுற ஒரு column-ல tables-ஐ சேர்க்கும்.

| Join | எதை வச்சுக்கும் | எதுக்கு use பண்றது |
| --- | --- | --- |
| `JOIN` (inner) | ரெண்டு பக்கமும் match ஆகுற rows மட்டும் | Customer இருக்குற orders |
| `LEFT JOIN` | இடது table-ல இருக்குற எல்லா rows; வலது பக்கம் match இல்லன்னா blank | Orders இல்லாத customers; reply இல்லாத tickets |

```sql
-- customers who have never ordered
SELECT c.id, c.city
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

### GROUP BY

`GROUP BY` rows-ஐ ஒரு group-க்கு ஒரு row-ஆ சுருக்கி aggregates calculate பண்ணும்: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. Grouping-க்கு **முன்னாடி** rows-ஐ `WHERE`-ல filter பண்ணுங்க; **அப்புறம்** groups-ஐ `HAVING`-ல filter பண்ணுங்க:

```sql
SELECT city, COUNT(*) AS refunds
FROM refunds r JOIN orders o ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY city
HAVING COUNT(*) > 100;
```

### Window functions

Window functions தொடர்புடைய rows முழுக்க calculate பண்ணும், ஆனா rows-ஐ சுருக்காது:

| Function | Example | என்ன தரும் |
| --- | --- | --- |
| `ROW_NUMBER()` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | ஒவ்வொரு customer-ஓட rows-க்கும் நேர வரிசையில 1, 2, 3 |
| `LAG(col)` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | முந்தின row-ஓட value, row-க்கு row compare பண்ண |
| `SUM(col)` | `OVER (ORDER BY day)` | ஓடிக்கிட்டிருக்குற total |
| `AVG(col)` | `OVER (ORDER BY day ROWS 6 PRECEDING)` | ஏழு நாள் moving average |

`PARTITION BY`, `GROUP BY` மாதிரியே rows-ஐ groups-ஆ பிரிக்கும், ஆனா ஒவ்வொரு row-உம் result-ல இருக்கும்.

### Indexes-உம் query plans-உம்

Index இல்லன்னா, match-ஐ கண்டுபிடிக்க database ஒவ்வொரு row-வையும் படிக்கும்: இது **sequential scan**. `refunds(created_at)`-ல ஒரு index இருந்தா, அது நேரா சரியான rows-க்கு போயிடும்.

```flow
dir: LR
title: 3 கோடி rows-ல ஜூலை refunds-ஐ கண்டுபிடிக்கிறது
Index இல்லை -> 30,000,000 rows-ஐயும் படிச்சு, 2,000,000-ஐ வச்சுக்கும் -> 40 வி
created_at-ல Index -> 1 ஜூலைக்கு நேரா போய், முன்னோக்கி படிக்கும் -> 2 வி
```

Indexes reads-ஐ வேகமாக்கும், writes-ஐ கொஞ்சம் மெதுவாக்கும். அதனால நீங்க அதிகமா filter, join பண்ற columns-க்கு மட்டும் போடுங்க. ஒரு query-க்கு முன்னாடி `EXPLAIN ANALYZE` போட்டு run பண்ணா, database index use பண்ணுச்சா, முழு table-ஐயும் scan பண்ணுச்சா, ஒவ்வொரு step-க்கும் எவ்வளவு நேரம் ஆச்சுன்னு பார்க்கலாம்.

## ஒரு worked example

Hyderabad-ல ஒரு food delivery company refund requests-க்கு ஒரு AI assistant வேணும்னு நினைக்குது. எதையும் build பண்றதுக்கு முன்னாடி baseline தேவை: இன்னைக்கு ஒரு refund-க்கு எவ்வளவு நேரம் ஆகுது, city வாரியா?

```sql
SELECT c.city,
       COUNT(*) AS refunds,
       ROUND(AVG(EXTRACT(EPOCH FROM r.resolved_at - r.created_at) / 3600), 1) AS avg_hours
FROM refunds r
JOIN orders o    ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY c.city
ORDER BY avg_hours DESC;
```

அடுத்து, assistant-ஓட training examples-க்கு, திரும்ப திரும்ப complain பண்றவங்க dominate பண்ணாம இருக்க, ஒவ்வொரு customer-ஓட **முதல்** refund request-ஐ மட்டும் எடுக்கணும்:

```sql
SELECT *
FROM (
  SELECT r.*,
         ROW_NUMBER() OVER (PARTITION BY o.customer_id ORDER BY r.created_at) AS n
  FROM refunds r JOIN orders o ON o.id = r.order_id
) t
WHERE n = 1;
```

**Slow query.** Baseline query 3 கோடி rows-ல 40 வினாடி எடுக்குது. `EXPLAIN ANALYZE` date filter-க்கு `refunds`-ல sequential scan நடக்குறதை காட்டுது. Client-ஓட data team-கிட்ட கேக்குறீங்க; அவங்க அமைதியான நேரத்துல primary database-ல `CREATE INDEX CONCURRENTLY ON refunds (created_at)` run பண்றாங்க; அந்த index நீங்க query பண்ற read replica-க்கும் வருது. இப்போ query ரெண்டு வினாடிக்கு கீழ முடியுது.

| City | ஜூலைல இருந்து refunds | Resolve ஆக சராசரி மணி நேரம் |
| --- | --- | --- |
| Hyderabad | 48,200 | 31.4 |
| Vijayawada | 9,800 | 27.9 |
| Warangal | 4,100 | 22.6 |

Numbers-ஐயும் query நேரங்களையும் உங்க notes-ல எழுதிக்குறீங்க. இந்த table தான் உங்க assistant முந்த வேண்டிய baseline; அந்த index ஒரு quick win, client-ஓட data team-கிட்ட நல்ல பேரும் வாங்கித் தரும்.

## பொதுவா பண்ற தப்புகள்

- **Join பண்ணி பெருக்கிடுறது.** Orders-ஐ order items-ஓட join பண்ணி, அப்புறம் order totals-ஐ sum பண்ணா, ஒவ்வொரு order-உம் ஒவ்வொரு item-க்கும் ஒரு தடவை எண்ணப்படும். Join பண்றதுக்கு முன்னாடி சரியான level-ல aggregate பண்ணுங்க.
- **Left join வேண்டிய இடத்துல inner join போடுறது.** Orders இல்லாத customers report-ல இருந்து சத்தமில்லாம மறைஞ்சு போவாங்க.
- **Aggregates-ஐ WHERE-ல filter பண்றது.** `WHERE COUNT(*) > 5` fail ஆகும்; `HAVING` use பண்ணுங்க.
- **Production database-ல heavy queries run பண்றது.** Read replica அல்லது export கேளுங்க. Client-ஓட live app-ஐ மெதுவாக்குறது முதல் வாரத்துக்கு நல்லதில்லை.
- **எல்லாத்துக்கும் index போடுறது.** ஒவ்வொரு index-உம் storage-ஐயும் write speed-ஐயும் சாப்பிடும். Real-ஆன slow queries-க்கு மட்டும் போடுங்க, `EXPLAIN ANALYZE`-ல உறுதி பண்ணுங்க.
- **Dates-ஐ text-ஓட compare பண்றது.** சரியான date types-ஐயும் `DATE '2026-07-01'` மாதிரி literals-ஐயும் use பண்ணுங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற SQLBolt lessons 1 முதல் 12 வரை browser-லயே பண்ணுங்க, அப்புறம் window functions பத்தின PostgreSQL page-ஐ படிங்க.

1. **Set up.** ஏதாவது ஒரு free PostgreSQL-ல, உதாரணம்: local Docker container, `customers`, `orders`, `refunds` tables உருவாக்கி, சில நூறு rows made-up data insert பண்ணுங்க.
2. **Baseline.** மேல இருக்குற baseline query-ஐ எழுதுங்க, கூடவே இதுவரை order போடாத customers-ஐ list பண்ற ஒரு query-யையும் எழுதுங்க.
3. **Window.** ஒவ்வொரு refund-க்கும், அந்த customer-ஓட முந்தின refund-ல இருந்து எத்தனை நாள் ஆச்சுன்னு காட்ட `LAG` use பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** GROUP BY-க்கும் window function-க்கும் இருக்குற வித்தியாசத்தை ஒரே வாக்கியத்துல explain பண்ண முடியும், index சேர்த்ததுக்கு அப்புறம் வேகமான ஒரு query-யை காட்ட முடியும்.
