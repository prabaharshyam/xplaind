## இது என்ன

ஒரு application-ல prompt தான் code. **System prompt**-ல எல்லா requests-உம் share பண்ற நிலையான instructions இருக்கும்: model-ஓட role, task, rules, output format, examples. **User message**-ல இந்த request-க்கான specific input இருக்கும். நல்ல prompt design, நீங்க try பண்ண ஒரு input-ல மட்டும் இல்லாம, ஆயிரக்கணக்கான வேற வேற inputs-லயும் results தெளிவா, consistent-ஆ, test பண்ணக்கூடியதா இருக்க வைக்கும்.

```flow
System prompt | எல்லா request-க்கும் ஒரே மாதிரி, ஒரு versioned file: role, audience, task, context (price list, timings, policies), rules ("தெரியலன்னா சொல்லிட்டு hand over பண்ணு"), output format, length, 2-3 வேற வேற examples -> Model
User message | ஒவ்வொரு request-லயும் மாறும்: customer-ஓட message, data-வா நடத்தப்படுது -> Model
Model -> Reply -> உங்க test set-ஆல check
```

System prompt நிலையா, versioned-ஆ இருக்கும்; ஒரு request-ல இருந்து அடுத்ததுக்கு user message மட்டும் மாறும்.

இந்த lesson-ல Chennai-ல ஒரு phone-repair chain, ஒரு வரி prompt-ஐ நூற்றுக்கணக்கான real messages-ல work ஆகுற prompt-ஆ மாத்துறதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**System prompt-ல என்ன போடணும்.**

- *Role, audience*: "Chennai-ல இருக்குற ஒரு mobile phone repair chain-ஓட customers கேக்குற கேள்விகளுக்கு நீ பதில் சொல்லுற."
- *Task*: ஒவ்வொரு input-க்கும் என்ன பண்ணணும்.
- *Context*: Model-க்கு தேவையான facts (policies, product names, tone guidelines).
- *Rules*: என்ன பண்ணணும், என்ன பண்ணக் கூடாது, தெரியலன்னா என்ன பண்ணணும் ("கேள்வி repairs பத்தி இல்லன்னா, repairs-க்கு மட்டும் தான் help பண்ண முடியும்னு சொல்லு").
- *Output format*: exact structure, length, language.
- *Examples*: ஒண்ணு முதல் மூணு worked input-output pairs.

Secrets-ஐ prompts-ல வைக்காதீங்க; சில சமயம் users model-ஐ அவற்றை சொல்ல வச்சிடலாம்.

**Specific-ஆ இருங்க, ஏன்னும் சொல்லுங்க.** "Customers phone-ல படிக்கிறதால answers 80 words-க்குள்ள இருக்கட்டும்"ங்குறது "concise-ஆ இரு"ன்னு சொல்றதை விட நல்லா work ஆகும். Models காரணங்களை நல்லா follow பண்ணும்.

**Descriptions-ஐ விட examples நல்லது.** ஒரு நல்ல example tone, length, format, edge-case handling எல்லாத்தையும் ஒரே நேரத்துல காட்டும். Model ஒரு example-ஐ ரொம்ப அப்படியே copy பண்ணிடாம இருக்க, ஒரு tricky case உட்பட வேற வேற examples use பண்ணுங்க.

**நீளமான prompts-ஐ structure பண்ணுங்க.** Instructions, context, examples-க்கு தெளிவான sections அல்லது tags use பண்ணுங்க, அப்போ model எது எதுன்னு பிரிச்சு புரிஞ்சுக்கும். நீளமான reference documents-ஐ கேள்விக்கு முன்னாடி வைங்க.

**Data-வை instructions-ல இருந்து பிரிங்க.** User கொடுத்த text-ஐ தெளிவா mark பண்ணுங்க ("Customer-ஓட message கீழ இருக்குற tags-க்கு நடுவுல இருக்கு"), அப்போ அதுக்குள்ள இருக்குற instructions data-வா எடுத்துக்கப்படும்.

**நிறைய inputs-ல test பண்ணுங்க.** ஒரு example-ல work ஆகுற prompt பெரும்பாலும் மத்ததுல fail ஆகும். கஷ்டமான, வித்தியாசமான inputs உட்பட 20-ல இருந்து 50 realistic inputs-ஓட ஒரு set-ஐ உருவாக்குங்க, எல்லாத்தையும் ஓட்டுங்க, failures-ஐ படிங்க, ஒண்ணை மாத்துங்க, மறுபடி ஓட்டுங்க. இதுதான் evals-ஓட ஆரம்பம்.

**Prompts-ஐ version பண்ணுங்க.** அவற்றை code-ல பல இடங்கள்ல paste பண்றதுக்கு பதிலா, version control-ல இருக்குற files-ல வைங்க.

**Prompt improvement loop:**

| Round | மாற்றம் | 50 test messages-ல pass count |
| --- | --- | --- |
| 0 | "Reply to the customer politely." | 18 |
| 1 | Role, facts, price list சேர்த்தாங்க | 31 |
| 2 | Rules சேர்த்தாங்க: list-ல இல்லாத prices வேண்டாம், rival shops வேண்டாம், language match | 39 |
| 3 | Format, 60-word காரணம் சேர்த்தாங்க | 42 |
| 4 | ரெண்டு examples சேர்த்தாங்க | 44 |
| 5 | Water-damage rule, example சேர்த்தாங்க | 47 |

ஒவ்வொரு round-லயும் ஒண்ணு மட்டும் மாறுச்சு, அதனால எந்த மாற்றம் உதவுச்சுன்னு team-க்கு தெரிஞ்சுது. ஒரு மாற்றம் pass count-ஐ குறைச்சப்போ, அதை revert பண்ணாங்க. இந்த discipline தான் prompt வேலையை ஊகிக்கிறதா இல்லாம engineering-ஆ ஆக்குது.

**தெளிவான sections-ஓட ஒரு prompt.** Tags இருந்தா எந்த பகுதி எதுன்னு model-க்கு தெளிவா தெரியும், நீங்களும் ஒரு நேரத்துல ஒரு பகுதியை சுலபமா மாத்தலாம்:

```python
SYSTEM = """<role>
You answer WhatsApp questions from customers of Fixit, a phone repair chain in Chennai.
</role>

<facts>
Shops: T. Nagar, Velachery, Anna Nagar. Open 10 am to 8 pm, closed Tuesdays.
{price_list}
</facts>

<rules>
- Quote only prices in the price list. If a repair is not listed, say a technician will call.
- Never mention other shops.
- Reply in the customer's language (English, Tamil or Tanglish).
- Keep replies under 60 words, because customers read on phones.
- Water damage: never promise a fix; ask them to bring the phone in, switched off.
</rules>

<examples>
Customer: screen change for redmi note 12 how much
Reply: A Redmi Note 12 screen replacement is ₹2,400 and takes about an hour. Visit any Fixit shop, 10 am to 8 pm, except Tuesdays.
</examples>"""

def build_messages(customer_text):
    return [{"role": "user", "content": f"<customer_message>\n{customer_text}\n</customer_message>"}]
```

**Prompt-ஐ code மாதிரி test பண்ணுங்க.** ஒவ்வொரு test message-ஐயும் ஓட்டி, properties-ஐ code-ல check பண்ணி, pass count-ஐ print பண்ணுங்க:

```python
import re

PRICES = {"2,400", "1,800", "3,200", "650"}                # every price in the list
TAMIL = re.compile(r"[஀-௿]")

def check(customer_text, reply):
    problems = []
    if len(reply.split()) > 60:
        problems.append("too long")
    for amount in re.findall(r"₹\s?([\d,]+)", reply):
        if amount not in PRICES:
            problems.append(f"unlisted price ₹{amount}")
    if TAMIL.search(customer_text) and not TAMIL.search(reply):
        problems.append("did not reply in Tamil")
    if re.search(r"\b(other shop|competitor)\b", reply, re.I):
        problems.append("mentioned another shop")
    return problems

def run(cases, generate):
    failures = {c: p for c in cases if (p := check(c, generate(c)))}
    print(f"{len(cases) - len(failures)}/{len(cases)} passed")
    return failures
```

Code checks, rule மீறல்கள்ல பெரும்பாலானதை இலவசமா பிடிச்சிடும். Code-ஆல பார்க்க முடியாத தரங்களுக்கு (உதாரணம்: reply கேள்விக்கு உண்மையிலேயே பதில் சொல்லுச்சா) மட்டும் model judge-ஐ வச்சுக்கோங்க.

**பெரிய tasks-ஐ steps-ஆ பிரிங்க.** Classify பண்ணி, price-ஐ தேடி, reply எழுதி, அதை translate-ம் பண்ற ஒரே prompt-ஐ debug பண்றது கஷ்டம். பல சின்ன prompts (classify, அப்புறம் reply, அப்புறம் check) ஒவ்வொண்ணையும் test பண்றது சுலபம், சுலபமான steps-க்கு மலிவான models use பண்ணலாம், எங்க fail ஆச்சுன்னு exact-ஆ தெரியும். இதுக்கு விலை: அதிக calls, கொஞ்சம் அதிக delay.

**தேவைப்படும்போது reasoning-க்கு இடம் கொடுங்க.** ஒரு task-ஐ வேலை செஞ்சு கண்டுபிடிக்கணும்னா (உதாரணம்: பல rules-ஓட eligibility check), பதில் சொல்றதுக்கு முன்னாடி reason பண்ண model-ஐ சொன்னா accuracy பெரும்பாலும் கூடும். Reasoning models இதை தானே பண்ணும். Reasoning-ஐ customer பார்க்குறதுல இருந்து வெளிய வைங்க, reasoning-ஐ இல்ல, final answer-ஐ check பண்ணுங்க.

**Prompts-ஐ versions-ஓட files-ல வைங்க.** ஒவ்வொரு prompt-ஐயும் ஒரு version name-ஓட file-ஆ வச்சு, start-up-ல load பண்ணி, ஒவ்வொரு request-ஓடயும் version-ஐ log பண்ணுங்க. அப்போ quality குறைஞ்சா, அதுக்கு காரணமான prompt மாற்றத்தை கண்டுபிடிக்கலாம்.

## ஒரு worked example

Chennai-ல ஒரு phone-repair chain, customers-ஓட WhatsApp messages-க்கு replies draft பண்ற assistant வேணும்னு நினைக்குது.

முதல் prompt: "Reply to the customer politely." 30 real messages-ல replies நீளமா இருக்கு, shop கொடுக்காத prices-ஐ promise பண்ணுது, rival brands-ஓட warranties பத்திய கேள்விகளுக்கும் பதில் சொல்லுது.

Improve பண்ண system prompt (சுருக்கமா):

- Role: Chennai-ல நாலு stores இருக்குற "FixFast Mobiles"-க்கு, staff review பண்றதுக்கான replies-ஐ draft பண்றது.
- Facts: பொதுவான repairs-க்கு price list, store timings, parts-க்கு 90 நாள் warranty.
- Rules: list-ல இல்லாத price-ஐ ஒருபோதும் promise பண்ணாதே ("inspection-க்கு அப்புறம் confirm பண்றோம்"ன்னு சொல்லு); மத்த shops பத்தி பேசாதே; customer-ஓட மொழியில reply பண்ணு (Tamil அல்லது English); staff இதை WhatsApp-ல அனுப்புறதால 60 words-க்குள்ள.
- Format: greeting, answer, next step.
- ரெண்டு examples: English-ல ஒரு screen replacement கேள்வி, Tamil-ல ஒரு battery கேள்வி.

அதே 30 messages-ஓட 20 புதுசையும் சேர்த்து மறுபடி ஓட்டுனாங்க: 50-ல 44 drafts, edits இல்லாம அல்லது சின்ன edits-ஓட use பண்ண முடியுது; முன்னாடி 30-ல 11 தான். மீதி ஆறு failures பெரும்பாலும் water damage பத்தினது; team அதுக்கு ஒரு rule-உம் example-உம் சேர்த்து மறுபடி ஓட்டுது.

**மீதி ஆறு failures கத்துக்கொடுத்தது.** Failures-ஐ படிக்க பத்து நிமிஷம் தான் ஆச்சு, எந்த பொதுவான prompting tip-ஐயும் விட பயனுள்ளதா இருந்தது. Customers water damage-ஐ பல விதமா சொன்னாங்க ("phone வாளியில விழுந்துடுச்சு", "மழையில நனைஞ்சுடுச்சு"), model, முதல்ல inspection தேவைப்படுற பிரச்சனைக்கு repair prices சொல்லுச்சு. ஒரு rule ("எந்த liquid damage-க்கும், phone-ஐ கொண்டு வரச் சொல்லு; ஒருபோதும் price சொல்லாதே") மற்றும் ஒரு example, பெரும்பாலானதை சரி பண்ணுச்சு.

## பொதுவான தவறுகள்

- **ஒரு example-ல test பண்றது.** வேற வேற inputs-ஓட ஒரு set use பண்ணி, failures-ஐ படிங்க.
- **தெளிவில்லாத instructions.** என்ன வேணும்னும், ஏன்னும் exact-ஆ சொல்லுங்க.
- **தெரியாத சூழ்நிலைக்கு rule இல்லாதது.** பதில் context-ல இல்லன்னா என்ன பண்ணணும்னு model-கிட்ட சொல்லுங்க.
- **Prompts-ல secrets.** Passwords, keys-ஐ அங்க வைக்காதீங்க.
- **ஒரே நேரத்துல நிறைய மாற்றங்கள்.** ஒண்ணை மாத்துங்க, மறுபடி ஓட்டுங்க, ஒப்பிடுங்க.

- **Prompt-ஐ rules-ஆல நிரப்புறது.** "Never", "always" வரிகள் நிறைஞ்ச ஒரு பக்கம் model-ஐ குழப்பும், தனக்குள்ளயே முரண்படும். Rules-ஐ கொஞ்சமா, specific-ஆ, காரணத்தோட வைங்க; test set-ல தேவையில்லன்னு தெரிஞ்சதை நீக்குங்க.
- **ரெண்டு மூணு inputs-ல மட்டும் prompt-ஐ test பண்றது.** வித்தியாசமானவை உட்பட 20-ல இருந்து 50 set-ஐ use பண்ணுங்க.
- **பல steps இருக்குற task-க்கு ஒரே பெரிய prompt.** ஒவ்வொரு step-ஐயும் test பண்ற மாதிரி பிரிங்க.
- **Code-ல பல இடங்கள்ல paste பண்ணின prompts**, அதனால versions வேற வேறயா போயிடும்.

## Prompt வேலை தீர்வு இல்லாத இடங்கள்

- **Model-க்கு facts தெரியாது**: நீளமான prompts-ஐ விட retrieval அல்லது tools சேருங்க.
- **பல careful rounds-க்கு அப்புறமும் ஒரே format தவறு தொடருது**: structured output அல்லது fine-tuning சரி பண்ணலாம்.
- **Task-க்கு exact logic தேவை** (உதாரணம்: tax calculations): code-ல பண்ணி, result-ஐ model explain பண்ணட்டும்.
- **முன்னேற்றம் தட்டையாயிடுச்சு**: மூணு rounds-ல ஒவ்வொண்ணுக்கும் ஒரு pass தான் சேருதுன்னா, bottleneck வேற இடத்துல இருக்கு.

## Demo-ல இருந்து production-க்கு

- **Prompts-ஐ files-ல version பண்ணுங்க**, ஒவ்வொரு request-லயும் version-ஐ log பண்ணுங்க.
- **ஒவ்வொரு prompt மாற்றத்துக்கும் CI-ல test set-ஐ ஓட்டுங்க**, pull request-ல pass count-ஓட.
- **ஒரு தடவைக்கு ஒண்ணை மாத்துங்க**, ஒவ்வொரு version-உம் எதை சரி பண்ணுச்சுன்னு சின்ன changelog வச்சுக்கோங்க.
- **Model மாறுனா மறுபடி test பண்ணுங்க**, ஏன்னா ஒரு model-க்கு tune பண்ண prompts வேற model-ல வேற மாதிரி behave ஆகலாம்.
- **User text-ஐ தெளிவா mark பண்ண tags-ல வைங்க**, rules-ஐ அது மாத்த விடாதீங்க.

## Practice

கீழ link பண்ணியிருக்குற prompting best-practices guide-ஐ படிங்க.

1. உங்களுக்கு தெரிஞ்ச ஒரு domain-ல, role, rules, format, ரெண்டு examples-ஓட ஒரு assistant-க்கு system prompt எழுதுங்க.
2. ஐந்து கஷ்டமானவை உட்பட 20 test inputs-ஓட ஒரு set உருவாக்கி, எந்த outputs fail ஆகுதுன்னு note பண்ணுங்க.
3. ஒவ்வொரு தடவையும் ஒண்ணை மட்டும் மாத்தி, ரெண்டு rounds-ல prompt-ஐ improve பண்ணி, ஒவ்வொண்ணுக்கு அப்புறமும் pass count-ஐ note பண்ணுங்க.
4. உங்க 20 test inputs-ல check function-ஐ சேர்த்து, ஒவ்வொரு prompt version-க்கும் pass count-ஐ ஒரு சின்ன table-ல note பண்ணுங்க.
