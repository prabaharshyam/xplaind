## இது என்ன

MCP-க்கு முன்னாடி, ஒவ்வொரு AI app-க்கும் ஒவ்வொரு system-க்கும் தனி code தேவைப்பட்டுச்சு. மூணு assistants, நாலு systems-னா பன்னிரண்டு integrations. **Model Context Protocol** (MCP) இதை சரி பண்ற ஒரு open standard. ஒவ்வொரு system-ஐயும் ஒரு தடவை **MCP server**-ஆ wrap பண்ணுவீங்க, ஒவ்வொரு AI app-லயும் எந்த server-ஓடயும் பேச முடியுற ஒரு **MCP client** இருக்கும்: மூணு பெருக்கல் நாலு இல்ல, மூணு கூட்டல் நாலு பாகங்கள் தான்.

Anthropic MCP-ஐ 25 November 2024 அன்னைக்கு release பண்ணுச்சு. December 2025-ல அதை Agentic AI Foundation-கிட்ட கொடுத்துச்சு; அது Linux Foundation-க்கு கீழ Anthropic, Block, OpenAI சேர்ந்து ஆரம்பிச்ச ஒரு directed fund, அங்க அதோட maintainers அதை open-ஆ develop பண்றாங்க. Versions-க்கு date தான் பேர். இப்போதைய version **2026-07-28**, இது அஞ்சாவது release; அதுக்கு முந்தையது 2025-11-25. ஒரு tutorial எந்த version-க்கு எழுதப்பட்டதுன்னு எப்பவுமே check பண்ணுங்க.

ஒரு server மூணு வகையான விஷயங்களை offer பண்ணலாம். ரொம்ப முக்கியமானது, ஒவ்வொண்ணையும் use பண்ணலாம்னு யார் முடிவு பண்றாங்கங்கிறது தான்:

| Feature | அது என்ன | யார் use பண்ண முடிவு பண்றாங்க | உதாரணம் | Messages |
| --- | --- | --- | --- | --- |
| Tools | JSON schema இருக்குற functions | Model, ஒரு task நடக்கும்போது | `search_tickets(query, status)` | `tools/list`, `tools/call` |
| Resources | ஒரு URI வச்சு முகவரி இடப்பட்ட data | App அல்லது user அதை attach பண்ணுவாங்க | `ticket://T-1042` | `resources/list`, `resources/read` |
| Prompts | Reusable prompt templates | User ஒரு menu-ல இருந்து ஒண்ணை தேர்ந்தெடுப்பாங்க | "இந்த ticket thread-ஐ summarise பண்ணு" | `prompts/list`, `prompts/get` |

## இது எப்படி work ஆகுது

### Host, client, server

**Host**-னா user வேலை செய்யுற AI app. அதுக்குள்ள, ஒரு **client** ஒரு **server**-ஓட connection-ஐ வச்சிருக்கும், அதனால மூணு servers இருக்குற ஒரு host-ல மூணு clients இருக்கும். Client தன் server-ஓட tools-ஐ model-க்கு list பண்ணும். Model ஒரு tool-ஐ கேட்டா, client அந்த call-ஐ அந்த server-க்கு அனுப்பி result-ஐ திருப்பி கொடுக்கும். Model எப்பவுமே ஒரு server-ஓட நேரா பேசாது, அதனால control host கையில தான் இருக்கும்.

```flow
dir: LR
title: ஒரு system-க்கு ஒரு server, எல்லா hosts-உம் share பண்ணும்
IDE assistant | ஒவ்வொரு server-க்கும் ஒரு client இருக்குற host -> Maintenance-log server | find_machine, get_maintenance_history, log_observation
Chat assistant | ஒவ்வொரு server-க்கும் ஒரு client இருக்குற host -> Maintenance-log server
Chat assistant -> Spare-parts server
```

### Wire-ல போற messages

MCP messages JSON-RPC 2.0: ஒரு request-ல ஒரு `id`, ஒரு `method`, `params` இருக்கும், reply-லயும் அதே `id` வரும். 2026-07-28-ல இருந்து protocol **stateless**. பழைய versions ஒரு `initialize` handshake-ஓட ஆரம்பிச்சு ஒரு session-ஐ வச்சிருந்துச்சு. இப்போ ஒவ்வொரு request-உம் protocol version-ஐயும் client capabilities-ஐயும் `_meta`-ல கொண்டு வரும், கூடவே client-ஓட name, version-ஐயும் கொண்டு வரணும். ஒரு client முதல்ல `server/discover`-ஐ call பண்ணலாம், ஆனா கட்டாயம் இல்ல. இன்னும் upgrade பண்ணாத clients-க்கு official Python SDK அதே server-ல இருந்தே பழைய handshake-ஐயும் serve பண்ணும்.

Failures ரெண்டு வகை:

- **Tool error**-னா `isError: true`-ஓட வர்ற ஒரு சாதாரண result. Model அதை படிச்சு திரும்ப try பண்ணலாம், அதனால என்ன தப்பாச்சு, பதிலா என்ன பண்ணணும்னு சொல்லுங்க.
- **Protocol error**-னா ஒரு code-ஓட வர்ற JSON-RPC `error`, உதாரணம் ஒரு malformed request-க்கு. அதை client handle பண்ணும்; model பெரும்பாலும் அதை பார்க்கவே பார்க்காது.

**Browser-லயே try பண்ணுங்க.** இது worked example-ஓட server-ல இருந்து record பண்ண ஒரு request, ரெண்டு replies, இடத்துக்காக trim பண்ணது. Code ஒரு reply-ஐ model பார்க்குற வடிவத்துக்கு மாத்துது.

```python
import json

request = {"jsonrpc": "2.0", "id": 7, "method": "tools/call",
           "params": {"name": "get_maintenance_history", "arguments": {"tag": "CNC-14", "limit": 1},
                      "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}

ok = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": False,
      "content": [{"type": "text", "text": "{\"date\": \"2026-11-18\", \"note\": \"Vibration at high RPM\"}"}]}}
refused = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": True,
      "content": [{"type": "text", "text": "Error executing tool get_maintenance_history: No machine 'CNC-14' in your plant."}]}}

def for_the_model(reply):
    assert reply["id"] == request["id"], "a reply must match its request id"
    if "error" in reply:  # protocol error: the host deals with it
        raise RuntimeError(reply["error"]["message"])
    text = "\n".join(c["text"] for c in reply["result"]["content"] if c["type"] == "text")
    return {"tool_result": text, "is_error": reply["result"]["isError"]}

print(json.dumps(for_the_model(ok)))
print(json.dumps(for_the_model(refused)))
```

### Transports: local, remote

| அம்சம் | stdio (local) | Streamable HTTP (remote) |
| --- | --- | --- |
| எப்படி ஓடும் | Host server-ஐ ஒரு child process-ஆ start பண்ணி standard input, output வழியா பேசும் | Server ஒரே URL-ல இருக்குற ஒரு web service, உதாரணம் `https://mcp.example.in/maintenance` |
| எதுக்கு நல்லது | Files, local databases, developer tools | Shared company systems, ஒரே இடத்துல update, log பண்ணலாம் |
| User யாரு | அந்த machine-ல host-ஐ ஓட்டுறவங்க | Sign-in பண்ணவங்க: ஒவ்வொரு request-லயும் ஒரு OAuth token |

**Streamable HTTP**-ல, client ஒவ்வொரு message-ஐயும் அந்த ஒரே URL-க்கு POST பண்ணும், server JSON-ஓட பதில் சொல்லும், இல்ல முதல்ல progress அனுப்பும்போது events-ஓட ஒரு stream-ஆ பதில் சொல்லும். 2026-07-28-ல, ஒவ்வொரு request-உம் body-ல இருந்து copy பண்ண ஒரு `Mcp-Method` header-ஐ கொண்டு வரும், tool, resource, prompt requests `Mcp-Name`-ஐயும் கொண்டு வரும், அதனால ஒரு gateway body-ஐ parse பண்ணாமலே requests-ஐ route பண்ணலாம்; headers-உம் body-உம் ஒத்துப்போகாத request-க்கு 400 error கிடைக்கும். இனிமே session id கிடையாது: பழைய `Mcp-Session-Id` header-ஐ server ignore பண்ணும், புதுசா ஒண்ணும் உருவாக்காது. ஒரு workflow-க்கு state வேணும்னா, ஒரு tool `draft_id` மாதிரி ஒரு handle-ஐ return பண்ணும், model அதை திரும்ப pass பண்ணும்.

ரெண்டு gotchas. பழைய tutorials **HTTP+SSE** transport-ஐ (`transport="sse"`) use பண்ணுது, அது deprecated: புதுசா எதையும் அதுல ஆரம்பிக்காதீங்க. அப்புறம், ஒரு stdio server standard output-ல MCP messages-ஐ மட்டும் தான் எழுதணும்: தேவையில்லாத ஒரு `print` கூட connection-ஐ உடைச்சிடும், அதனால standard error-க்கு log பண்ணுங்க.

### Python-ல ஒரு server build பண்றது

Official Python SDK `mcp` package, November 2026 நிலவரப்படி version 2.x (`pip install "mcp[cli]"`). அதோட main class `MCPServer`. SDK 1.x tutorials `mcp.server.fastmcp`-ல இருந்து `FastMCP`-ஐ import பண்ணுது, அது 2.x-ல fail ஆகும்: code-ஐ update பண்ணுங்க, இல்ல `mcp<2`-ன்னு pin பண்ணுங்க.

```python
# tickets_server.py
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open") -> list[dict]:
    """Search support tickets by keywords. status is 'open' or 'closed'. Returns up to 10."""
    if status not in ("open", "closed"):
        raise ToolError("status must be 'open' or 'closed'.")
    return ticket_db.search(query, status=status, limit=10)

@mcp.resource("ticket://{ticket_id}")
def ticket(ticket_id: str) -> str:
    """The full text of one ticket."""
    return ticket_db.get(ticket_id).body

@mcp.prompt()
def summarise_ticket(ticket_id: str) -> str:
    return f"Summarise ticket {ticket_id} in five bullets."

if __name__ == "__main__":
    mcp.run()  # stdio; use mcp.run(transport="streamable-http") for a remote server
```

Function-ஓட பேர், type hints, docstring தான் tool-ஓட name, input schema, description ஆகும், அதனால tool-design lesson இங்க நேரா பொருந்தும். `ToolError`-ஐ raise பண்ணா ஒரு `isError: true` result return ஆகும்: "Error executing tool <name>: " prefix-க்கு அப்புறம் உங்க message.

**Model-ஐ connect பண்றதுக்கு முன்னாடி test பண்ணுங்க.** MCP Inspector (`npx @modelcontextprotocol/inspector`, இல்ல `mcp dev tickets_server.py`) வச்சு ஒவ்வொரு tool-ஐயும் உங்க சொந்த arguments-ஓட, தப்பான arguments உட்பட, call பண்ணி raw results-ஐ பார்க்கலாம். பெரும்பாலான bugs ஒரு chat-ல பார்க்குறதை விட இங்க சீக்கிரம் தெரிஞ்சிடும்.

**உங்க சொந்த client.** Assistants-லயும் code editors-லயும் clients ஏற்கனவே இருக்கு; உங்க சொந்த agent SDK-ஐ use பண்ணலாம்:

```python
import asyncio
from mcp import Client, StdioServerParameters

async def main():
    server = StdioServerParameters(command="python", args=["tickets_server.py"])
    async with Client(server) as client:  # or Client("https://.../mcp") for a remote server
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("search_tickets", {"query": "refund"})
        print(result.is_error, result.structured_content)

asyncio.run(main())
```

ஒவ்வொரு tool-ஓட `name`, `description`, `input_schema`-ஐ model-க்கு கொடுங்க, அதோட calls-ஐ `client.call_tool`-க்கு அனுப்புங்க, ஒரு call fail ஆச்சுன்னு model-க்கு தெரியுற மாதிரி `is_error`-ஐ திரும்ப pass பண்ணுங்க.

### ஒரு server client-கிட்ட என்ன கேக்கலாம்

**Elicitation** ஒரு tool call நடுவுல user-கிட்ட ஏதாவது கேக்க விடும்: விடுபட்ட ஒரு detail, இல்ல ஒரு bulk change-க்கு முன்னாடி "40 tickets-ஐயும் close பண்ணலாமா?". 2026-07-28-ல இது rounds-ஆ work ஆகும்: server தன் கேள்விகளோட `resultType: "input_required"`-ஐ return பண்ணும், host user-கிட்ட கேக்கும், client பதில்களோட call-ஐ திரும்ப பண்ணும். AI app வழியா போகக்கூடாத ஒரு password அல்லது payment-க்கு, server user-ஐ ஒரு web page-க்கு அனுப்பும் (URL mode).

பழைய material **sampling** (server host-ஓட model-கிட்ட text எழுத சொல்றது), **roots** (எந்த folders-ஐ use பண்ணணும்னு host server-கிட்ட சொல்றது) பத்தியும் சொல்லும். ரெண்டுமே 2026-07-28-ல deprecated ஆச்சு, logging-உம் கூட. 28 July 2027 அன்னைக்கோ அதுக்கு அப்புறமோ release ஆகுற முதல் revision வரைக்குமாவது இவை spec-ல இருக்கும், ஆனா புதுசா எதையும் இதுமேல build பண்ணாதீங்க. 2026-07-28-ல, நீண்ட நேரம் ஓடுற jobs (**tasks**) core-ல இருந்து வெளிய ஒரு extension-க்கு மாறிடுச்சு. Interactive screens (**MCP Apps**) ஒரு தனி extension.

### Tools-க்கு context செலவாகும்

Connect ஆன ஒவ்வொரு tool-ஓட name, description, schema-உம் ஒவ்வொரு turn-லயும் model-ஓட context-ல இருக்கும். Anthropic-ஓட documentation (November 2026-ல check பண்ணது) சொல்லுது: ஒரு சாதாரண அஞ்சு-server setup எந்த வேலையும் ஆரம்பிக்கிறதுக்கு முன்னாடியே definitions-க்கே சுமார் 55,000 tokens use பண்ணலாம், 30 முதல் 50 tools-க்கு மேல போனா tool தேர்வு மோசமாகும். அதனால:

- கம்மியான, task வடிவ, தனித்தனி பேர் இருக்குற tools-ஐ offer பண்ணுங்க; ரெண்டு servers-லயும் `search` இருக்கலாம்னா, system பேரை prefix பண்ணுங்க (`maint_search`).
- Results-க்கு cap வையுங்க: ஒரு `limit` argument, சின்ன fields, முழு documents-க்கு பதிலா IDs.
- Host support பண்ணா tools-ஐ தேவைப்படும்போது load பண்ணுங்க. உதாரணமா, Claude-ஓட tool search tool `defer_loading`-ன்னு mark பண்ண tools-ஐ model அவற்றை search பண்ற வரைக்கும் context-க்கு வெளியவே வச்சிருக்கும்.

### சுருக்கமா security

ஒரு server உண்மையான systems-க்கு access இருக்குற code, அதோட output model-க்குள்ள போகும். முக்கிய risks: **tool poisoning** (descriptions அல்லது results-ல மறைச்சு வச்ச instructions), **approve பண்ணதுக்கு அப்புறம் மாறுறது** (versions-ஐ pin பண்ணுங்க), servers-க்கு நடுவுல **பேர் மோதல்கள்**, **ரொம்ப அதிக reach** (ஒரே company-wide token). அடுத்து வர்ற lesson, Securing agent tools and MCP servers, இன்னும் ஆழமா போகும்; worked example builder பக்கத்தை காட்டுது.

## ஒரு worked example

Pune-ல ஒரு manufacturing company-க்கு PUN-1, PUN-2-ன்னு ரெண்டு plants இருக்கு. Engineers தங்க IDE-ல ஒரு AI assistant-ஐயும், chat-ல இன்னொண்ணையும் use பண்றாங்க, ரெண்டுக்குமே maintenance log வேணும். Contractors தங்க சொந்த plant-ஐ மட்டும் தான் பார்க்கணும்.

நீங்க மூணு tools-ஓட ஒரு remote MCP server build பண்றீங்க: `find_machine`, `get_maintenance_history`, `log_observation`. Remote MCP OAuth-ஐ use பண்ணுது: company-ஓட single sign-on (SSO) தான் tokens-ஐ issue பண்ற **authorization server**, உங்க MCP server அவற்றை check பண்ற **resource server**.

```flow
title: Remote server-ஓட முதல் connection
Assistant token இல்லாம server-ஐ call பண்ணுது -> Server metadata link-ஓட 401 reply
Server metadata link-ஓட 401 reply -> எந்த sign-in service-னு assistant படிக்குது
எந்த sign-in service-னு assistant படிக்குது -> Engineer company SSO-ல sign in பண்றாங்க
Engineer company SSO-ல sign in பண்றாங்க -> SSO இந்த server-க்கு மட்டும் token கொடுக்குது | user, plant, scopes
SSO இந்த server-க்கு மட்டும் token கொடுக்குது -> Assistant token-ஓட call-ஐ திரும்ப பண்ணுது
Assistant token-ஓட call-ஐ திரும்ப பண்ணுது -> Server token-ஐ check பண்ணி, அந்த user-ஆ tool-ஐ ஓட்டுது
```

SDK metadata-ஐ serve பண்ணி 401-ஐ உங்களுக்காக அனுப்பிடும். உங்க code tokens-ஐ check பண்ணி user-ஓட limits-ஐ apply பண்ணும்:

```python
# maintenance_server.py
import json, sqlite3
from mcp.server import MCPServer
from mcp.server.auth.middleware.auth_context import get_access_token
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver.exceptions import ToolError

db = sqlite3.connect("maintenance.db", check_same_thread=False)
audit = open("audit.jsonl", "a", buffering=1)  # one JSON line per call

def verify_with_sso(token: str) -> dict | None:
    """Your SSO library checks signature, expiry and issuer; returns the claims or None."""
    ...

class SSOTokenVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        claims = verify_with_sso(token)
        if claims is None:
            return None
        return AccessToken(token=token, client_id=claims["azp"], subject=claims["sub"],
                           scopes=claims["scope"].split(), resource=claims["aud"],
                           claims={"plant": claims["plant"]})

mcp = MCPServer("maintenance", token_verifier=SSOTokenVerifier(), auth=AuthSettings(
    issuer_url="https://sso.example.in",
    resource_server_url="https://mcp.example.in/maintenance",
    required_scopes=["maintenance.read"],
    validate_token_resource=True,  # refuse tokens issued for any other service
))

def caller(tool: str, args: dict) -> tuple[str, str, list[str]]:
    """Who is calling, from the checked token, never from the model. Writes the audit line."""
    tok = get_access_token()
    audit.write(json.dumps({"user": tok.subject, "client": tok.client_id, "tool": tool, "args": args}) + "\n")
    return tok.subject, tok.claims["plant"], tok.scopes

@mcp.tool()
def get_maintenance_history(tag: str, limit: int = 5) -> list[dict]:
    """Latest maintenance events for one machine in your plant, newest first. limit is 1 to 20."""
    user, plant, _ = caller("get_maintenance_history", {"tag": tag, "limit": limit})
    rows = db.execute(
        "SELECT e.done_on, e.kind, e.note, e.by_user FROM events e JOIN machines m ON m.id = e.machine_id "
        "WHERE m.tag = ? AND m.plant_id = ? ORDER BY e.done_on DESC LIMIT ?",
        (tag, plant, max(1, min(limit, 20)))).fetchall()
    if not rows:
        raise ToolError(f"No machine '{tag}' in your plant. Call find_machine to search by name.")
    return [{"date": d, "kind": k, "note": n, "by": b} for d, k, n, b in rows]

@mcp.tool()
def log_observation(tag: str, note: str) -> str:
    """Add a short note (max 500 characters) to a machine's log. Writes only to the notes table."""
    user, plant, scopes = caller("log_observation", {"tag": tag, "note": note[:80]})
    if "maintenance.write" not in scopes:
        raise ToolError("Your sign-in does not allow writing notes. Ask your supervisor to add it.")
    row = db.execute("SELECT id FROM machines WHERE tag = ? AND plant_id = ?", (tag, plant)).fetchone()
    if row is None:
        raise ToolError(f"No machine '{tag}' in your plant.")
    db.execute("INSERT INTO notes (machine_id, note, by_user) VALUES (?, ?, ?)", (row[0], note[:500], user))
    db.commit()
    return f"Note added to {tag}."

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000,
            streamable_http_path="/maintenance")  # serve behind HTTPS in production
```

மூணு design choices தான் security-ஐ தாங்குது:

1. **Plant token-ல இருந்து வருது, model-ல இருந்து இல்ல.** எந்த tool-லயும் `plant_id` argument இல்ல, அதனால எந்த prompt-உம் வேற plant-ஐ கேக்க முடியாது. ஒவ்வொரு query-உம் SSO token-ல போட்ட plant வச்சு filter பண்ணும்.
2. **Token இந்த server-க்காகவே இருக்கணும்.** `validate_token_resource=True` இருந்தா, வேற service-க்கு issue ஆன ஒரு உண்மையான token-க்கும் 401 தான் கிடைக்கும்.
3. **Writes-க்கு ஒரு scope வேணும்.** படிக்க `maintenance.read` வேணும்; `log_observation`-க்கு `maintenance.write`-உம் வேணும்.

இந்த server-ஐ ரெண்டு users-க்கான stand-in tokens வச்சு test பண்ணோம் (`find_machine`-உம் அதே pattern தான், மேல விட்டுட்டோம்). PUN-1-ல engineer-ஆ இருக்குற Anita chat-ல கேக்குறாங்க: "CNC-14-ஓட spindle கடைசியா எப்போ service ஆச்சு, அதுக்கப்புறம் யாராவது vibration report பண்ணாங்களா?" Assistant `get_maintenance_history`-ஐ call பண்ணி ரெண்டு rows வாங்குது: 2 October 2026 அன்னைக்கு suresh.p bearings-ஐ மாத்தினது, 18 November 2026 அன்னைக்கு meera.d போட்ட "Vibration at high RPM". ரெண்டையும் வச்சு பதில் சொல்லிட்டு, அப்புறம் `log_observation` வச்சு அவங்க note-ஐ log பண்ணுது.

Ravi ஒரு contractor, அவரோட token-ல PUN-2-உம் `maintenance.read` மட்டும் தான் இருக்கு; அவர் தன் IDE-ல இருந்து அதே கேள்வியை கேக்குறார். அதே query `plant_id = 'PUN-2'`-ஓட ஓடி, எதுவும் கிடைக்காம, "No machine 'CNC-14' in your plant." return பண்ணுது. அவரோட `log_observation` call-க்கு "Your sign-in does not allow writing notes." கிடைக்குது. ரெண்டுமே `isError: true` results, அதனால assistant அவற்றை explain பண்ணுது. Audit log-ல ஒவ்வொரு call-க்கும் ஒரு line இருக்கு, உதாரணம் `{"user": "ravi.contractor", "client": "ide-assistant", "tool": "get_maintenance_history", "args": {"tag": "CNC-14", "limit": 2}}`.

இதை production-grade ஆக்க இன்னும் ரெண்டு layers வேணும். Server-ஓட database account machines, events-ஐ படிக்கவும் notes-ல insert பண்ணவும் மட்டும் தான் முடியணும், அப்போ உங்க filter-ல ஒரு bug இருந்தாலும் எதையும் delete பண்ண முடியாது. அப்புறம் server **Anita-ஓட token-ஐ எப்பவுமே** வேற API-க்கு **forward பண்ணக்கூடாது**. அது token passthrough, MCP security guidance அதை தடை பண்ணுது; ஒரு downstream API-க்கு user வேணும்னா, அந்த API-க்காகவே issue ஆன ஒரு தனி token வாங்குங்க.

பின்னாடி IT ஒரு spare-parts system-ஐ சேர்க்கும்போது, அதே sign-in-ஓட ஒரு ரெண்டாவது server-ஐ deploy பண்றாங்க, ரெண்டு assistants-க்கும் எந்த மாற்றமும் இல்லாம அதோட tools கிடைச்சிடும்.

## பொதுவான தப்புகள்

- **ஒரு பழைய tutorial-ஐ வரிக்கு வரி follow பண்றது.** `FastMCP` imports, `transport="sse"`, session ids, `initialize` handshake எல்லாம் 2024, 2025-ஓடது. முதல்ல versions-ஐ check பண்ணுங்க.
- **எல்லாருக்கும் ஒரே super-user credential.** யார் கேக்குறாங்கன்னு server கண்டுக்கலைன்னா, ஒவ்வொரு user-உம் எல்லாத்தையும் தொட முடியும். Sign-in பண்ண user-ஆ act பண்ணுங்க.
- **Identity-ஐ ஒரு tool argument-ல இருந்து எடுக்குறது.** ஒரு `user_id` அல்லது `plant_id` parameter இருந்தா, model-ஓ, அதுக்குள்ள inject ஆன text-ஓ வேற ஒருத்தரோட data-வை தேர்ந்தெடுக்கலாம். Check பண்ண token-ல இருந்து identity-ஐ படிங்க.
- **Token passthrough.** உங்க server-க்காக issue ஆகாத tokens-ஐ accept பண்றது, இல்ல user-ஓட token-ஐ வேற services-க்கு forward பண்றது audit-ஐயும் scope checks-ஐயும் உடைக்கும்.
- **முழு database-ஐயும் திறந்து விடுறது.** Users database administrators இல்லைன்னா, `run_sql` வேண்டாம், task வடிவ tools-ஐ offer பண்ணுங்க.
- **பெரிய results.** ஆயிரக்கணக்கான rows context-ஐ நிரப்பி அடுத்த ஒவ்வொரு turn-ஐயும் slow பண்ணும். Cap பண்ணுங்க, paginate பண்ணுங்க, summarise பண்ணுங்க.
- **Timeouts இல்லாதது.** ஒரு slow ERP-க்காக காத்திருக்குற tool agent-ஐ block பண்ணும். Server-ஓட சொந்த calls-க்கு timeout வையுங்க, ஒரு client read timeout-உம் set பண்ணுங்க (Python `Client`-ல `read_timeout_seconds`).
- **Servers-ஐயும் results-ஐயும் நம்புறது.** தெரியாத அல்லது pin பண்ணாத servers, instructions-ஆ நடத்தப்படுற ticket text, இதெல்லாம் tool poisoning-ஐயும் prompt injection-ஐயும் கூப்பிடும்.
- **Logging இல்லாதது.** ஒவ்வொரு call-க்கும் user, tool, arguments இல்லாம, ஒரு incident-ஐ investigate பண்ண முடியாது.

## உங்களுக்கு MCP தேவையில்லாத இடங்கள்

- **சில tools இருக்குற ஒரே app**, அந்த tools-ஐ அது மட்டும் தான் use பண்ணும்: உங்க code-ல சாதாரண tool definitions simple.
- **Fixed workflows**, அங்க உங்க code functions-ஐ நேரா call பண்ணும், எந்த model-உம் tools-ஐ தேர்ந்தெடுக்காது.
- **Strict environments**, அங்க ஒவ்வொரு புது network service-க்கும் review வேணும்: in-process tools-ஓட ஆரம்பிங்க, ரெண்டாவது app-க்கு தேவைப்படும்போது MCP-க்கு மாறுங்க.

பல hosts அல்லது agents-க்கு அதே tools வேணும்போது, இல்ல மக்கள் ஏற்கனவே use பண்ற assistants-ஐ உங்க systems-ல plug பண்ண விரும்பும்போது MCP பயன் தரும்.

## Demo-ல இருந்து production-க்கு

- **Company sign-in வழியா OAuth**, narrow scopes, இந்த server-க்காகவே check பண்ண tokens, token-ல இருந்து identity, ஒரு least-privilege database account.
- **ஒரு central audit log**: user, client, tool, arguments, result size.
- **ஒரு approved-server list**, pin பண்ண versions, tool descriptions மாறும்போதெல்லாம் ஒரு review.
- **ஒவ்வொரு tool-க்கும் limits:** timeouts, result caps, rate limits, writes-க்கு user confirmation.

## Practice பண்ணுங்க

Anthropic-ஓட இலவச Introduction to Model Context Protocol course-ஐ எடுங்க, இல்ல official introduction-ஐயும் Python SDK-ஓட get-started guide-ஐயும் படிங்க.

1. உங்களுக்கு பிடிச்ச ஒரு சின்ன SQLite database (books, fees, appointments) மேல ரெண்டு tools-ஓட ஒரு local stdio server-ஐ `MCPServer` வச்சு build பண்ணுங்க.
2. அதை MCP Inspector-ல திறந்து, ஒவ்வொரு tool-ஐயும் தப்பான arguments-ஓட call பண்ணுங்க, model recover ஆக உதவாத ஒவ்வொரு error message-ஐயும் திரும்ப எழுதுங்க.
3. அதை ஒரு MCP-capable assistant-ஓட connect பண்ணி, ரெண்டு tools-உம் தேவைப்படுற கேள்விகளை கேளுங்க. ஒரு table-ல மட்டும் insert பண்ற ஒரு write tool-ஐ சேருங்க, ஒவ்வொரு call-ஐயும் log பண்ணுங்க, ஒரு record-ல ஒரு prompt injection-ஐ மறைச்சு வச்சு என்ன ஆகுதுன்னு பாருங்க.
4. அதை `transport="streamable-http"`-ஓட ஓட்டுங்க, ரெண்டு users-க்கு ரெண்டு test tokens-ஐ accept பண்ற ஒரு `TokenVerifier`-ஐ சேருங்க, ஒவ்வொரு user-உம் தன் சொந்த rows-ஐ மட்டும் பார்க்குறாங்கன்னு காட்டுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** host, client, server-ஐ explain பண்ண முடியும், உங்க server ஒரு உண்மையான client-ல ஓடுறதை காட்ட முடியும், ஒரே tool-ல இருந்து ரெண்டு users வேற வேற results வாங்குறதை காட்ட முடியும், வேற ஒருத்தரோட server-ஐ install பண்றதுக்கு முன்னாடி கேக்க வேண்டிய மூணு கேள்விகளை சொல்ல முடியும்.
