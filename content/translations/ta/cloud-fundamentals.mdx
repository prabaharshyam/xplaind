## இது என்ன

ஒரு public cloud, computers, storage, networks, ready-made services-ஐ மணி நேரத்துக்கு அல்லது use-க்கு ஏத்த மாதிரி உங்களுக்கு வாடகைக்கு தருது. AWS, Microsoft Azure, Google Cloud ஆகிய மூணு பெரிய providers-உம் கிட்டத்தட்ட ஒரே building blocks-ஐ வேற வேற பேர்கள்ல தர்றாங்க. இந்திய enterprises பெரும்பாலும் group முழுக்க ஒரே choice-ஐ follow பண்ணுவாங்க; banks, government-சம்பந்தப்பட்ட clients இந்திய regions-ஐயோ ஒரு குறிப்பிட்ட provider-ஓட sovereign offering-ஐயோ கூட கேக்கலாம்.

எல்லா services-உம் உங்களுக்கு தேவையில்ல. ஒரு AI deployment சுமார் ஆறு வகையை use பண்ணும்:

- **Compute**: உங்க code எங்க run ஆகுது.
- **Storage**: files, documents.
- **Databases**: structured data, பெரும்பாலும் pgvector-ஓட PostgreSQL.
- **Networking**: private networks, load balancers, DNS.
- **Identity and access**: யார் என்ன பண்ணலாம்.
- **Managed AI**: cloud-ல இருந்து hosted model APIs; data agreements-க்கு இது முக்கியமா இருக்கலாம்.

```flow
title: ஒரு Indian region-ல (உதாரணம்: Mumbai), ஒரு virtual network-குள்ள ஒரு app
Users | company SSO -> Load balancer | HTTPS, public subnet-ல
Load balancer -> Serverless containers | app, private subnet-ல, least-privilege role-ஓட
Serverless containers -> Managed PostgreSQL
Serverless containers -> Object storage
Serverless containers -> Managed model API
```

இந்த lesson-ல Hyderabad-ல ஒரு pharma company-க்கு Azure-ல அவங்க document assistant-ஐ design பண்றதை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Regions and zones.** ஒவ்வொரு region-லயும் (இந்தியாவுல provider-ஐ பொறுத்து Mumbai, Hyderabad, Pune, Delhi மற்றும் சில) பல zones இருக்கும், அவை தனி data centres. Resilience-க்கு instances-ஐ zones முழுக்க பரப்பி வைங்க. Users-க்கு latency, data residency rules, அங்க என்ன models கிடைக்குதுங்கிறதை வச்சு region-ஐ தேர்ந்தெடுங்க.

**Compute choices**, அதிகம் managed-ல இருந்து குறைவா managed வரை: serverless containers (Cloud Run, Azure Container Apps, அல்லது Fargate-ல AWS ECS, ECS Express Mode உட்பட; AWS App Runner புது customers-க்கு மூடியிருக்கு) இதுல நீங்க ஒரு image கொடுத்தா ஒரு URL கிடைக்கும்; managed Kubernetes (EKS, AKS, GKE) client-ஓட platform team ஒண்ணை run பண்ணும்போது; GPUs அல்லது முழு control வேணும்னா virtual machines. பெரும்பாலான AI APIs-க்கு serverless containers தான் வேகமான safe ஆரம்பம்.

**Storage and databases.** Documents-க்கு object storage (S3, Blob Storage, Cloud Storage). Relational data-க்கும் vectors-க்கும் managed PostgreSQL. Managed services-ஐ use பண்ணுங்க: backups, patches, failover எல்லாம் கூடவே வரும்.

**Networking.** Resources ஒரு virtual network-ல private subnets-ல இருக்கும். Databases-க்கு public address இருக்கக்கூடாது; உங்க app அவற்றை private-ஆ அணுகும். வெளியில இருந்து வர்ற traffic, HTTPS-ஓட ஒரு load balancer வழியா வரும்.

**Identity.** நீண்ட நாள் access keys-ஐ store பண்றதுக்கு பதிலா, ஒவ்வொரு service-க்கும் தேவையான permissions மட்டும் இருக்குற சொந்த identity-ஐ (ஒரு role அல்லது managed identity) கொடுங்க. மக்கள் company-ஓட single sign-on வழியா sign in ஆவாங்க.

**Managed models.** ஒவ்வொரு cloud-உம் முக்கிய models-ஐ resell பண்ணுது (Amazon Bedrock, Azure OpenAI-ஓட Microsoft Foundry, Google Vertex AI). Data அவங்களோட existing cloud contract, region-குள்ளயே இருக்குறதால clients இவற்றை அடிக்கடி prefer பண்றாங்க.

**Cost.** Compute, managed databases, வெளிய போற data transfer, model tokens தான் பெரும்பாலான bills-ஐ உருவாக்கும். Build பண்றதுக்கு முன்னாடி provider-ஓட pricing calculator-ஐ use பண்ணுங்க, முதல் நாளே budget alert-ஐ set பண்ணுங்க.

**ஒரே building blocks, மூணு பேர்கள்:**

| Building block | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Serverless containers | ECS on Fargate (Express Mode) | Container Apps | Cloud Run |
| Managed Kubernetes | EKS | AKS | GKE |
| Object storage | S3 | Blob Storage | Cloud Storage |
| Managed PostgreSQL | RDS, Aurora | Azure Database for PostgreSQL | Cloud SQL, AlloyDB |
| Service identity | IAM role | Managed identity | Service account |
| Secrets | Secrets Manager | Key Vault | Secret Manager |
| Managed models | Bedrock | Microsoft Foundry (Azure OpenAI) | Vertex AI |

ஒரு cloud-ஐ ஒழுங்கா கத்துக்கோங்க, அப்புறம் இந்த மாதிரி ஒரு table வச்சு translate பண்ணிக்கோங்க.

**ஒரு Indian region-ல ஒரு container-ஐ deploy பண்றது.** Google Cloud-ல, ஒரு command, தன்னோட சொந்த identity-ஓடயும் Secret Manager-ல இருந்து secrets-ஓடயும் ஒரு private service-ஐ deploy பண்ணும்:

```bash
gcloud run deploy claims-api \
  --image asia-south1-docker.pkg.dev/my-project/apps/claims-api:3f9c2e1 \
  --region asia-south1 \
  --service-account claims-api@my-project.iam.gserviceaccount.com \
  --no-allow-unauthenticated \
  --set-secrets MODEL_API_KEY=model-api-key:latest,DATABASE_URL=db-url:latest \
  --min-instances 1 --max-instances 10 --cpu 1 --memory 1Gi
```

`--no-allow-unauthenticated`-னா permission இருக்குற callers (ஒரு load balancer, ஒரு gateway, அல்லது அதன் வழியா sign in ஆன users) மட்டும் தான் இதை அணுக முடியும். Traffic திடீர்னு எகிறினா `--max-instances` cost-ஐ cap பண்ணும். AWS (Fargate-ல ECS), Azure (Container Apps) இதே ideas-ஐ வேற syntax-ல எடுத்துக்கும்: ஒரு image, ஒரு region, ஒரு identity, reference வச்சு secrets, scaling limits.

**முதல் நாளே ஒரு budget alert.**

```bash
gcloud billing budgets create --billing-account=XXXXXX-XXXXXX-XXXXXX \
  --display-name="claims-pilot" --budget-amount=20000INR \
  --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --threshold-rule=percent=1.0
```

ஒவ்வொரு cloud-லயும் இதுக்கு இணையான ஒண்ணு இருக்கு. Alerts-ஐ ஒரு shared channel-க்கு அனுப்புங்க, ஒருத்தரோட inbox-க்கு இல்ல.

**உங்க cloud வழியா models.** Client-ஓட cloud வழியா ஒரு model-ஐ call பண்ணா, traffic அவங்க contract, identity controls-குள்ளயே இருக்கும். Anthropic-ஓட SDK-ல, Bedrock client அதே message shape-ஐ use பண்ணும்:

```python
from anthropic import AnthropicBedrock

client = AnthropicBedrock(aws_region="ap-south-1")      # uses the service's IAM role, not a key
reply = client.messages.create(
    model="<the model id shown in your Bedrock console>", max_tokens=300,
    messages=[{"role": "user", "content": "Summarise this claim note: ..."}])
```

Data residency-ஐ promise பண்றதுக்கு முன்னாடி, ஒவ்வொரு Indian region-லயும் எந்த models-உம் features-உம் கிடைக்குதுன்னு check பண்ணுங்க; சில மத்த இடங்களை விட Indian regions-க்கு தாமதமா வரும்.

**பணம் எங்க போகுது.** ஒரு typical AI app-ல model tokens-உம் managed databases-உம் தான் அதிகம், அப்புறம் compute, அப்புறம் cloud-ஐ விட்டு வெளிய போற data transfer. ஒவ்வொரு resource-க்கும் project, environment tag போடுங்க, அப்போ bill-ஐ பிரிக்கலாம்; முதல் மாசத்துல வாரா வாரம் cost breakdown-ஐ பாருங்க.

**Default-ஆ private.** Databases-ஐயும் vector stores-ஐயும் public address இல்லாத private networks-ல வச்சுக்கோங்க, கிடைக்குற இடத்துல private endpoints வழியா model services-ஐ அணுகுங்க, load balancer அல்லது gateway-ஐ மட்டும் internet-க்கு expose பண்ணுங்க.

**உங்க browser-லயே try பண்ணுங்க.** Build பண்றதுக்கு முன்னாடி ஒரு மாச cloud bill-ஐ estimate பண்ணுங்க. Inputs-ஐ உங்களோடதா மாத்துங்க.

```python
requests_per_day = 20_000
instance_rupees_per_hour = 6        # one small container instance; check current prices
instances = 2
db_rupees_per_month = 4_000
egress_gb, egress_rupees_per_gb = 50, 8

compute = instance_rupees_per_hour * 24 * 30 * instances
total = compute + db_rupees_per_month + egress_gb * egress_rupees_per_gb
print(f"compute ₹{compute:,}, total ₹{total:,} a month")
print(f"about ₹{total / (requests_per_day * 30):.3f} per request before model costs")
```

## ஒரு worked example

Azure-ல இருக்குற ஒரு Hyderabad pharma company, அவங்க regulatory team-க்கு ஒரு document assistant வேணும்னு கேக்குறாங்க. Requirements: data இந்தியாவுலயே இருக்கணும், public database கூடாது, company accounts வச்சு sign-in.

உங்க design:

- **Region**: எல்லாத்துக்கும் Central India, company-ஓட Azure AI agreement வழியா தேவையான model அங்க கிடைக்குதான்னு check பண்ணப்புறம்.
- **Compute**: உங்க FastAPI image-ஐ run பண்ற Azure Container Apps, 1-ல இருந்து 5 instances வரை scale ஆகும்.
- **Storage**: source PDFs-க்கு Blob Storage; chunks-க்கு pgvector-ஓட Azure Database for PostgreSQL, app-ஓட private network-ல இருந்து மட்டும் அணுகக்கூடிய மாதிரி.
- **Identity**: App ஒரு managed identity-ஐ use பண்ணும்; அதுக்கு ஒரு storage container-க்கும் database-க்கும் read access, stored keys எதுவும் இல்ல. Users Microsoft Entra ID வச்சு sign in ஆவாங்க.
- **Cost**: calculator, model tokens-க்கு முன்னாடி மாசத்துக்கு சுமார் ₹55,000-ன்னு estimate பண்ணுது; tokens-ஐ எதிர்பார்க்குற usage-ல இருந்து தனியா estimate பண்ணுவீங்க. 80%-ல ஒரு budget alert set பண்ணியிருக்கு.

Client-ஓட cloud team ஒரே review-ல approve பண்ணுது, முக்கிய காரணம் ஒவ்வொரு choice-உம் அவங்க ஏற்கனவே இருக்குற patterns-ஓட பொருந்துறது.

| Monthly estimate-ஓட வரி | அதை எது தீர்மானிக்குது | எப்படி குறைக்கலாம் |
| --- | --- | --- |
| Container Apps | Instances, run ஆகுற மணி நேரங்கள் | இரவுல ஒரு instance-க்கு scale பண்ணுங்க |
| PostgreSQL | Instance size, storage | சின்னதா ஆரம்பிச்சு, அளந்த load படி scale பண்ணுங்க |
| Blob Storage | Store பண்ண gigabytes | பழைய versions-ஐ archive பண்ணுங்க |
| Data transfer | Cloud-ஐ விட்டு வெளிய போற data | Traffic-ஐ region-குள்ளயே வச்சுக்கோங்க |
| Model tokens | Requests × tokens | குட்டி prompts, caching, எளிய கேள்விகளை சின்ன model-க்கு route பண்றது |

**Review ஏன் சுமூகமா போச்சு.** வெளி designs-ஓட பெரும்பாலானவற்றை client-ஓட cloud team இதே மூணு காரணங்களுக்காக reject பண்ணும்: public endpoints, stored keys, இந்தியாவுக்கு வெளிய regions. உங்க design மூணையும் தவிர்த்துச்சு, அவங்க team ஏற்கனவே run பண்ற services-ஐ use பண்ணுச்சு, ஒவ்வொரு network boundary-யையும் காட்டுற ஒரு diagram-ஓட வந்துச்சு. அவங்க பண்ண ஒரே மாற்றம், resources-க்கு ஒரு naming convention தான்.

## பொதுவா பண்ற தப்புகள்

- **மூணு clouds-ஐ மேலோட்டமா கத்துக்கிறது.** ஒண்ணை ஒழுங்கா கத்துக்கோங்க; பேர்களை இன்னொண்ணுக்கு translate பண்ண ஒரு நாள் போதும்.
- **Public databases.** Public address இருக்குற database தான் மிக common-ஆன serious cloud தப்பு.
- **Code-ல நீண்ட நாள் access keys.** Service identities-ஐயும் short-lived credentials-ஐயும் use பண்ணுங்க.
- **Data transfer, model costs-ஐ புறக்கணிக்கிறது.** அவை compute-ஐ விட அதிகமா போகலாம். Estimate பண்ணுங்க.
- **Latency-ஐ மட்டும் வச்சு region-ஐ தேர்ந்தெடுக்கிறது.** முதல்ல residency rules, model availability-ஐ check பண்ணுங்க.

- **Budget alert இல்லாதது.** மறந்து போன ஒரு GPU machine அல்லது கட்டுப்பாடு இல்லாம ஓடுற ஒரு loop, ஒரு weekend-ல lakhs செலவு வைக்கலாம். முதல் நாளே alerts set பண்ணுங்க.
- **ஒரு gateway அல்லது load balancer-க்கு பின்னாடி இருக்க வேண்டிய services public-ஆ அணுகக்கூடிய மாதிரி விடுறது.**
- **Maximum instance count இல்லாதது**, அதனால traffic spike அல்லது ஒரு bug, bill-ஐ எல்லையே இல்லாம scale பண்ணிடும்.
- **Tag பண்ணாத resources**, அதனால எந்த project-க்கு எவ்வளவு cost-ன்னு யாராலயும் சொல்ல முடியாது.

## குறைவான cloud போதும்ங்கிறது எப்போ

- **ஒரு prototype அல்லது demo**: Vercel, Render, Railway மாதிரி ஒரு platform-உம் ஒரு hosted database-உம் வேகமானது.
- **Client எல்லாத்தையும் on-premises-ல run பண்றாங்க**: அவங்க platform-ஐ கத்துக்கோங்க.
- **ஒரு server function-ல API key இருக்குற ஒரே ஒரு static site**: முழு virtual network தேவையில்லாத overkill.

## Demo-ல இருந்து production-க்கு

- **Users, data residency, model availability-க்காக regions-ஐ தேர்ந்தெடுத்து**, ஏன்னு record பண்ணுங்க.
- **Service identities-ஐயும் secret references-ஐயும்** use பண்ணுங்க, stored keys வேண்டாம்.
- **Data services-ஐ private-ஆ வச்சு**, gateway மட்டும் public-ஆ இருக்கட்டும்.
- **முதல் நாளிலிருந்தே budgets-ஐயும் maximum instances-ஐயும்** set பண்ணுங்க.
- **Project, environment வாரியா resources-ஐ tag பண்ணி**, ஆரம்பத்துல வாரா வாரம் costs-ஐ review பண்ணுங்க.

## Practice பண்ணுங்க

Microsoft Learn-ஓட cloud concepts modules-ஐ முடிங்க, அப்புறம் Azure-க்கு architecture and services path-ஐ படிங்க, இல்லன்னா Google Cloud பிடிச்சா Google-ஓட getting-started path.

1. ஒரு free account-ல, உங்க containerised API-ஐ ஒரு Indian region-ல ஒரு serverless container service-ல deploy பண்ணுங்க.
2. Object storage-ஐயும், private-ஆ மட்டும் அணுகக்கூடிய ஒரு managed PostgreSQL-ஐயும் சேர்த்து, app-க்கு keys-க்கு பதிலா ஒரு service identity கொடுங்க.
3. ஒரு மாசத்துக்கு 50,000 requests-க்கு இந்த set-up-ஐ provider-ஓட calculator-ல price பண்ணி, ஒரு budget alert-ஐ set பண்ணுங்க.
4. Maximum instance count-ஓடயும் ஒரு budget alert-ஓடயும் deploy பண்ணி, ஒரு நாள் test traffic-க்கு அப்புறம் cost breakdown-ஐ check பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க deployment-ஐ region, network boundaries, identities-ஓட வரைய முடியும், அதோட estimated monthly bill-ஓட ஒவ்வொரு வரியையும் explain பண்ண முடியும்.
