## இது என்ன

ஒரு forward deployed engineer (FDE) ஒரு client-ஓட organisation-க்குள்ளயே இருந்து வேலை செய்வாரு, தெளிவில்லாத ஒரு business problem-ஐ மக்கள் உண்மையா use பண்ற software-ஆ மாத்துவாரு. நீங்க அதை செய்யுறதை சில மணி நேரத்துல பார்க்க தான் interview loop முயற்சி பண்ணுது.

### இந்த role-உம் loop-உம் எங்க இருந்து வந்துச்சு

இந்த role-ஐ முதல்ல ஆரம்பிச்சது தாங்க தான்னு Palantir சொல்லுது. இந்த engineers-ஐ அவங்க Forward Deployed Software Engineers-னு கூப்பிடுறாங்க, செல்லப்பேர் "Deltas"; core platform-ஐ build பண்ற "Devs"-ஓட compare பண்றாங்க: ஒரு Dev நிறைய customers-க்கு ஒரு capability-ஐ build பண்றாரு, ஒரு Delta ஒரு customer-க்கு நிறைய capabilities-ஓட serve பண்றாரு. பெரும்பாலான Palantir FDE onsites-ல ஒரு "decomposition" round இருக்குன்னு candidate reports-உம் prep guides-உம் சொல்லுது: சுமார் 60 நிமிஷம், code கொஞ்சம் அல்லது இல்லவே இல்ல, interviewer தெளிவில்லாத problem இருக்குற ஒரு customer-ஆ நடிப்பாரு. சிலர் ஒரு "learning" round பத்தியும் சொல்றாங்க: பழக்கமில்லாத ஒரு concept, API அல்லது system-ஐ வேகமா புரிஞ்சுக்கிட்டு அதுமேல build பண்ணணும்.

இப்போ AI labs-உம் AI startups-உம் இந்த title-ஐ use பண்றாங்க. OpenAI, Anthropic ரெண்டுமே முக்கியமான customers கூட embed ஆகுற FDEs-ஐ hire பண்றாங்க. OpenAI loop பத்தின prep guides, production-level coding, system design, ஒரு customer-facing exercise, நீங்க build பண்ண ஒண்ணுல ஒவ்வொரு முடிவையும் defend பண்ற ஒரு project deep-dive இருக்குன்னு report பண்றாங்க. Report பண்ற round எண்ணிக்கை மாறுது, அதனால எந்த exact number-ஐயும் நம்பாதீங்க.

இந்தியால இந்த title வேகமா பரவுது. July 2026-ல TCS chief executive K Krithivasan, company-ஓட staff-ல 1% முதல் 1.5% பேரை forward deployed roles-ல வைக்கணும்னு Reuters கிட்ட சொன்னாரு; Reuters அதை சுமார் 5,900 முதல் 8,900 பேர்னு கணக்குப் போட்டுச்சு; அவங்களை hire பண்ணுவாங்களா, retrain பண்ணுவாங்களான்னு அவரு சொல்லல. Coforge தன் FDE team-ஐ சுமார் 20-ல இருந்து 100-ஆ வளர்க்க plan பண்றதா July 2026-ல report ஆச்சு. 2026-ல இந்த title-ஓட Bengaluru postings-ல Google Cloud-உம் Nanonets-உம் இருந்துச்சு. சில firms இதே வேலைக்கு வேற titles use பண்றாங்க, அதனால job description-ஐ படிங்க.

### Rounds-உம் ஒவ்வொண்ணும் எதை test பண்ணுதுன்னும்

| Round | எதை test பண்ணும் | Strong-னா எப்படி இருக்கும் |
|---|---|---|
| Practical coding | குழப்பமான data, APIs, validation, tests | முதல்ல data பத்தி கேக்குறது; மோசமான rows-ஐ report பண்றது; edge cases-ஐ test பண்றது |
| Problem decomposition | தெளிவில்லாத ஒரு goal-ஐ plan-ஆ மாத்துறது | Solutions-க்கு முன்னாடி கேள்விகள்; ஒரு KPI, ஒரு baseline, gate-ஓட ஒரு முதல் step |
| Learning (Palantir-ல report ஆனது) | பழக்கமில்லாத system-ஐ வேகமா புரிஞ்சுக்கிறது | நல்ல கேள்விகள்; system-ஐ உடைக்காம extend பண்றது |
| AI system design | Client constraints-க்குள்ள ஒரு end-to-end design | Client-ஓட data, rules, budget, team கூட இணைஞ்ச choices |
| Client role-play | Pressure-ல expectations-ஐ manage பண்றது | அடிபணியவும் இல்ல, மறுக்கவும் இல்ல; options தர்றது; ஒரு owner, ஒரு தேதியோட முடிக்கிறது |
| Behavioural, project deep-dive | Ownership, மோதல், failure, கத்துக்கிறது | அளந்த result-உம் ஒரு lesson-உம் இருக்குற STAR கதைகள் |
| Take-home அல்லது work sample | ஒரு time box-க்குள்ள judgement | வேலை செய்யுற core path, நேர்மையான README, சின்ன eval, செலவழிச்ச நேரம் சொல்லப்பட்டிருக்கு |

எல்லா company-யும் எல்லா round-ஐயும் நடத்தாது. FDE roles-க்கே உரியது decomposition தான்:

```flow
dir: LR
title: Decomposition round
தெளிவில்லாத ஒரு problem -> Goal, owner -> Process, data -> KPI + baseline -> Non-AI உட்பட options -> Proof of concept + gate -> Risks
```

இந்திய banks-க்கு விக்கிற ஒரு AI startup-ல FDE loop-க்கு தயாராகுற Arjun-ங்குற கற்பனை candidate-ஐ இந்த lesson follow பண்ணுது.

4. On-site வேலையும் travel-உம் சாதாரணமா எவ்வளவு, ஒரு FDE-ஓட success-ஐ எப்படி அளக்குறாங்க?

Policies மாறுறதால, முன்னாடியை விட 2026-ல மூணாவது கேள்வி ரொம்ப முக்கியம். Anthropic candidates-க்கு guidance publish பண்ணுது: உங்க resume-ஐ job description கூட check பண்றது மாதிரி சில விஷயங்களுக்கு Claude-ஐ use பண்ணலாம், ஆனா உங்க answers-ஐ அதை வச்சு எழுத கூடாது. 2025-ல Meta, candidates ஒரு AI assistant-ஐ use பண்ணக்கூடிய coding interviews-ஐ trial பண்றதா report ஆச்சு. Rules company-க்கு company மாறும், சில நேரம் ஒரே loop-ல round-க்கு round கூட மாறும். கேக்குறது சாதாரணம்; தப்பா guess பண்ணா loop-ஏ முடிஞ்சிடலாம்.

### Practical coding

நிறைய FDE coding rounds உண்மையான client வேலை மாதிரியே இருக்கும்; ஆனா சில loops, candidates report பண்ற Palantir loop உட்பட, algorithm மாதிரி problems-உம் தருவாங்க; எதை எதிர்பார்க்கணும்னு கேளுங்க. ஒரு யதார்த்தமான 30 நிமிஷ task: "ஒரு lender தன் branch system-ல இருந்து UPI collections-ஐ CSV-ஆ export பண்றாங்க. சில rows-ல amount இல்ல, dates ரெண்டு formats-ல இருக்கு, அல்லது transaction ID repeat ஆகுது. Clean records-ஐயும், காரணங்களோட rejected rows list-ஐயும் return பண்ணுங்க, அப்புறம் அதை ஒரு API endpoint பின்னாடி வைங்க."

முதல் ரெண்டு நிமிஷத்தை கேள்விகளுக்கு செலவழிங்க. Duplicate-ஐ reject பண்ணணுமா, இல்ல ரெண்டாவது copy ஜெயிக்கணுமா? Negative amounts refunds-ஆ errors-ஆ? எந்த date formats வருது? அப்புறம் core-ஐ எழுதுங்க:

```python
from datetime import date, datetime
from decimal import Decimal
from pydantic import BaseModel, Field, ValidationError, field_validator

class Txn(BaseModel):
    txn_id: str = Field(min_length=1)
    amount: Decimal = Field(gt=0)
    paid_on: date

    @field_validator("paid_on", mode="before")
    @classmethod
    def parse_date(cls, v: str) -> date:
        for fmt in ("%Y-%m-%d", "%d/%m/%Y"):
            try:
                return datetime.strptime(str(v).strip(), fmt).date()
            except ValueError:
                pass
        raise ValueError(f"unknown date format: {v!r}")

def clean(rows):
    good, rejected, seen = [], [], set()
    for line, row in enumerate(rows, start=2):  # line 1 is the header
        try:
            txn = Txn(**row)
        except ValidationError as e:
            rejected.append((line, e.errors()[0]["msg"]))
            continue
        if txn.txn_id in seen:
            rejected.append((line, "duplicate txn_id"))
            continue
        seen.add(txn.txn_id)
        good.append(txn)
    return good, rejected
```

ஆறு rows இருக்குற ஒரு sample-ஐ குடுத்தா (ஒரு நல்ல row, amount இல்லாத ஒண்ணு, `dd/mm/yyyy` date ஒண்ணு, repeat ஆன ID ஒண்ணு, negative amount ஒண்ணு, "Nov 5"-ங்குற date ஒண்ணு), இது ரெண்டு rows-ஐ வச்சுக்கிட்டு நாலை reject பண்ணும், ஒவ்வொண்ணுக்கும் line number-உம் காரணமும் சேர்த்து. `float`-க்கு பதிலா `Decimal` வேணும்னே use பண்ணது: பணத்துல rounding errors வரக்கூடாது. Upload பண்ண file-ஐ accept பண்ற ஒரு FastAPI endpoint-க்குள்ள `clean`-ஐ wrap பண்ண இன்னும் சில நிமிஷம் தான் ஆகும் ("FastAPI-ல REST APIs" lesson-ஐ பாருங்க).

| Interviewers எதை check பண்றாங்க | Weak | Strong |
|---|---|---|
| கேள்விகள் | உடனே type பண்ண ஆரம்பிக்கிறது | எது மோசமான row, duplicates-ஐ என்ன பண்றதுன்னு கேக்குறது |
| மோசமான data | மோசமான rows-ஐ அமைதியா skip பண்றது | Reject ஆன ஒவ்வொரு row-ஐயும் காரணத்தோட return பண்றது |
| Types | பணத்துக்கு floats, dates-க்கு strings | `Decimal`, உண்மையான dates, ஒரு validation model |
| Tests | "என் sample-ல work ஆகுது" | ஆரம்பத்துல சொன்ன edge cases-க்கு ரெண்டு மூணு tests |
| பேசுறது | பத்து நிமிஷம் அமைதி | ஒவ்வொரு trade-off-ஐயும் சத்தமா சொல்றது, உதாரணமா "இப்போதைக்கு duplicates-ஐ reject பண்றேன்; மாத்துறது ஈஸி" |

Task-ல ஒரு language model இருந்தாலும் இதே பழக்கங்கள் தான்: ஒரு schema define பண்ணுங்க, reply-ஐ validate பண்ணுங்க, validation error-ஓட ஒண்ணு ரெண்டு தடவை retry பண்ணுங்க, அப்புறம் சத்தமா fail பண்ணி log பண்ணுங்க. இந்த pattern-ஐ "Structured JSON output வாங்குறது" lesson cover பண்ணுது.

### Problem decomposition

"ஒரு hospital discharge delays-ஐ குறைக்கணும்" மாதிரி ஒரு prompt குடுத்தா, final answer-க்கு இல்ல, நீங்க எப்படி யோசிக்கிறீங்கன்னு தான் score. ஆறு steps-ஐ சத்தமா பண்ணுங்க:

1. **Goal-ஐயும் அதோட owner-ஐயும் clarify பண்ணுங்க.** யாரு கேக்குறாங்க, அவங்களுக்கு என்ன மாறும்?
2. **இப்போதைய process, volumes, data பத்தி கேளுங்க.** நேரம் உண்மையா எங்க போகுது? ஒரு நாளைக்கு எத்தனை discharges? என்ன record ஆகுது, எங்க?
3. **ஒரு KPI, ஒரு baseline-ஐ agree பண்ணுங்க**, உதாரணமா "fit for discharge"-ல இருந்து bed-ஐ விட்டு போற வரைக்குமான median மணி நேரம், இன்னைக்கு அளந்தது.
4. **Non-AI உட்பட options-ஐ list பண்ணுங்க**, ஒரு checklist அல்லது pharmacy timing-ல ஒரு மாற்றம் மாதிரி, அப்புறம் ஒண்ணை தேர்ந்தெடுத்து ஏன்னு சொல்லுங்க.
5. **ஒரு gate-ஓட proof of concept-ஐ plan பண்ணுங்க.** Proof of concept-னா உண்மையான data-ல ஒரு சின்ன, time-boxed test. Gate-னா தொடரலாமா வேண்டாமான்னு முடிவு பண்ற, முன்னாடியே agree பண்ண ஒரு number, உதாரணமா "ஒரு ward-ல நாலு வாரத்துல median delay-ஐ 20% குறைக்கணும்".
6. **Risks-ஐயும் அவற்றை எப்படி குறைப்பீங்கன்னும் சொல்லுங்க**: patient data rules, staff adoption, தப்பான outputs.

Interviewer numbers எதுவும் தரலைன்னா, assumptions-ஐ சத்தமா சொல்லுங்க ("மூணு hospitals-ல ஒரு நாளைக்கு 200 discharges-னு வச்சுக்குவோம்"). ரெண்டு failure modes சாதாரணம்: முதல் அஞ்சு நிமிஷத்துலயே ஒரு model-ஐ propose பண்றது, முடிவே இல்லாம கேள்விகள் கேக்குறது. பாதி நேரத்துக்குள்ள ஒரு KPI-உம் ஒரு முதல் option-உம் board-ல இருக்கணும். கேள்விகள் பத்தி "Discovery" lesson இன்னும் ஆழமா போகுது.

### Learning round

Palantir loop பத்தின prep guides-உம் candidate reports-உம் ஒரு interviewer பத்தி சொல்லுது: நீங்க பழக்கமில்லாத ஒரு concept, API அல்லது system-ஐ கத்துக்கிட்டு அதுமேல build பண்ணும்போது அவரு உங்க reference-ஆ இருப்பாரு. Score உங்க learning curve தான்: துல்லியமான கேள்விகள் கேக்குறீங்களா, summarise பண்ணி உங்க புரிதலை check பண்றீங்களா, சொன்னதுமேல build பண்றீங்களா. Practice பண்ண, பழக்கமில்லாத ஒரு open-source repository-ஐ 20 நிமிஷம் படிங்க, அப்புறம் ஒரு module-ஐ சத்தமா விளக்கி ஒரு சின்ன feature-ஐ சேருங்க.

### AI system design

Structure-ஐ "Design interview" lesson cover பண்ணுது. FDE-ல இருக்குற twist: client-ஓட constraints தான் problem, அது noise இல்ல: இந்தியாவுக்குள்ளயே இருக்க வேண்டிய data, ஏற்கனவே இருக்குற ஒரு vendor stack, fixed budget, நீங்க போனதுக்கு அப்புறம் maintain பண்ணப்போற ஒரு சின்ன team. ஒவ்வொரு choice-ஐயும் இதுல ஒண்ணோட இணைங்க, evals, ஒரு human fallback, ஒரு handover plan-ஐயும் சேருங்க.

### Client role-play

ஒரு interviewer சந்தேகப்படுற, பொறுமையில்லாத, அல்லது requirements-ஐ மாத்திக்கிட்டே இருக்குற ஒரு client-ஆ நடிப்பாரு. அஞ்சு moves use பண்ணுங்க:

1. கேட்டதை ஒரே வாக்கியத்துல **summarise பண்ணுங்க**.
2. **Demand-க்கு பின்னாடி இருக்குற தேவையை கண்டுபிடிங்க.** தேதிக்கோ request-க்கோ என்ன காரணம்னு கேளுங்க.
3. **Risks-ஐ facts-ஆ சொல்லுங்க**, பயமா இல்ல: எது test ஆகல, என்ன தப்பா போகலாம், யாரு பாதிக்கப்படுவாங்க.
4. **Trade-offs-ஓட ரெண்டு options தாங்க**, client தேர்ந்தெடுக்கட்டும்.
5. அடுத்த step, ஒரு owner, ஒரு தேதி, எழுத்துல confirmation-ஓட **முடிங்க**.

| சூழ்நிலை | Weak response | Strong response |
| --- | --- | --- |
| "அடுத்த வாரம் எல்லா branches-லயும் live பண்ணுங்க" | "சரி, try பண்றோம்" அல்லது "முடியாது" | தேதிக்கு என்ன காரணம்னு கேளுங்க; risks-ஐ சொல்லுங்க; ஒரு board demo அல்லது partial rollout தாங்க |
| "AI ஒரு தப்பு பண்ணிடுச்சு; cancel பண்றோம்" | Model-ஐ defend பண்றது | என்ன நடந்துச்சுன்னு கேளுங்க, case-ஐ பாருங்க, safeguards-ஐயும் ஒரு fix plan-ஐயும் விளக்குங்க |
| "இந்த feature-ஐயும் சேருங்க" | அங்கேயே ஒத்துக்கிறது | "நான் இதை size பண்ணி வியாழக்கிழமைக்குள்ள options-ஓட வர்றேன்" |
| உங்க proposal-க்கு அப்புறம் அமைதி | பேசிக்கிட்டே இருக்குறது | நேரடியா ஒரு கேள்வி: "இதுல எது உங்க board timeline-க்கு பொருந்தும்?" |

புது request-ஐ size பண்றதை "Scope creep-ஐ manage பண்றது" lesson இன்னும் ஆழமா cover பண்ணுது.

### Behavioural கேள்விகளும் project deep-dive-உம்

STAR (situation, task, action, result) use பண்ணி ஆறு முதல் எட்டு கதைகளை தயார் பண்ணுங்க, ஒவ்வொண்ணுலயும் அளந்த ஒரு result-உம் ஒரு lesson-உம். இவற்றை cover பண்ணுங்க: ஆரம்பம் முதல் முடிவு வரை நீங்க நடத்தின ஒரு project, ஒரு stakeholder கூட கருத்து வேறுபாடு, ஒரு failure, நீங்க முடியாதுன்னு சொன்ன ஒரு நேரம், தெளிவில்லாத சூழ்நிலையில வேலை செய்தது, ஏதோ ஒண்ணை வேகமா கத்துக்கிட்டது. நீங்க பண்ணதுக்கு "நான்"-னு சொல்லுங்க, team-ஓட வேலைக்கு மட்டும் "நாங்க".

இதோ ஒரு strong கதை. Situation: "எங்க team-ஓட monthly sales report-க்கு மூணு நாள் manual spreadsheet வேலை ஆச்சு." Task: "அதை வேகப்படுத்த சொன்னாங்க." Action: "Steps-ஐ map பண்ணேன், data pulls-ஐயும் checks-ஐயும் Python-ல automate பண்ணேன், analysts review பண்ற ஒரு validation step-ஐ சேர்த்தேன்." Result: "அடுத்த மூணு monthly cycles-ல ஒவ்வொரு தடவையும் சுமார் நாலு மணி நேரம் தான் ஆச்சு, release-க்கு அப்புறம் கண்டுபிடிச்ச errors மாசத்துக்கு அஞ்சுல இருந்து zero-ஆ குறைஞ்சுது." Lesson: "Analysts-ஐ இன்னும் முன்னாடியே சேர்த்திருக்கணும்; நான் miss பண்ண ரெண்டு edge cases-ஐ அவங்க checks பிடிச்சுது." இந்த result-ல ஒரு before, ஒரு after, ஒரு காலம், அளந்த முறை எல்லாம் இருக்கு.

ஒரு project deep-dive-ல ஒவ்வொரு choice-க்கும் "ஏன் X இல்ல?"-னு எதிர்பாருங்க: நீங்க reject பண்ண alternative-ஐயும் ஏன்னும் தயார் பண்ணிக்கோங்க.

### Take-home

- **Time box-ஐ மதிங்க.** நாலு மணி நேரம்னு சொன்னா, சுமார் நாலு மணி நேரம் செலவழிங்க, உண்மையான number-ஐ README-ல எழுதுங்க. இருபது மணி நேரம் polish பண்ணா, நீங்க constraints-ஐ கண்டுக்க மாட்டீங்கன்னு அவங்களுக்கு தெரியும்.
- **Breadth சேர்க்குறதுக்கு முன்னாடி ஒரு path-ஐ end to end வேலை செய்ய வைங்க.**
- **ஒரு README எழுதுங்க**: ஒரே command-ல எப்படி run பண்றது, assumptions, trade-offs, அடுத்து என்ன பண்ணுவீங்க.
- **Evidence காட்டுங்க**: சில tests, அல்லது labelled examples-ல ஒரு சின்ன eval, failures-ஐ நேர்மையா list பண்ணி.
- **Present பண்ணா**, client-ஓட problem-ஐயும் result-ஐயும் வச்சு ஆரம்பிங்க, அப்புறம் design.
- **உங்களுக்கு சொன்ன AI-tool rules-ஐ follow பண்ணுங்க**, allow பண்ண tools-ஐ எப்படி use பண்ணீங்கன்னு சொல்லுங்க.

### இன்னும் client experience இல்லையா

இந்த path-ல இருக்குற பெரும்பாலானவங்களுக்கு பணம் தர்ற client இதுவரை இருந்ததில்ல. ஆனாலும் உங்ககிட்ட கதைகள் இருக்கு. ஒரு professor, ஒரு internship manager, ஒரு hackathon judge, ஒரு family business அல்லது ஒரு NGO "client"-ஆ இருக்கலாம். ஒவ்வொண்ணுக்கும் அவங்க என்ன கேட்டாங்க, அவங்களுக்கு என்ன தேவைப்பட்டுச்சு, ஒரு கருத்து வேறுபாடு, ஒரு number-ஐ note பண்ணுங்க. இன்னும் நல்லது, ஒரு உண்மையான ஆளுக்கு ஏதாவது சின்னதா build பண்ணுங்க, உதாரணமா ஒரு kirana கடைக்கு low-stock alert sheet, notes வச்சுக்கோங்க. உங்க capstone case study ("ஒரு case study, ஆரம்பம் முதல் முடிவு வரை" lesson-ஐ பாருங்க) ஒரு project deep-dive-க்கு உதவும்.

## ஒரு worked example

Arjun-க்கு loop-க்கு முன்னாடி ஒரு வாரம் இருக்கு. அவரோட plan:

| நாள் | Focus | Output |
| --- | --- | --- |
| 1 | Recruiter கேள்விகள்; rounds list | Round list, timings, AI-tool rules எல்லாம் ஒரே note-ல |
| 2 | Coding | ரெண்டு 30 நிமிஷ tasks: மேல இருக்குற CSV cleaner, retries-ஓட ஒரு structured-output call |
| 3 | Decomposition | "ஒரு மாநில transport corporation-க்கு குறைவான complaints வேணும்"-ல ரெண்டு timed, record பண்ண attempts |
| 4 | Behavioural | ஆறு STAR கதைகள் எழுதி, ஒவ்வொண்ணையும் ரெண்டு நிமிஷத்துக்குள்ள சத்தமா படிச்சது |
| 5 | Role-play | ஒரு friend client-ஆ நடிச்ச ரெண்டு role-plays |
| 6 | System design | Bank branch staff-க்கு ஒரு policy assistant-க்கான ஒரு design |
| 7 | Full mock | ஒவ்வொரு type-லயும் ஒரு mock round; சாயங்காலம் rest |

3-வது நாள் அவரோட முதல் recording-ல மூணு நிமிஷத்துலயே ஒரு chatbot-ஐ propose பண்றாரு. ரெண்டாவது attempt-ல பன்னிரண்டு நிமிஷம் கேள்விகளுக்கு செலவழிச்சு, ஒரு லட்சம் passenger trips-க்கு complaints-ங்குற KPI-க்கு வந்து சேர்றாரு.

உண்மையான loop-ல role-play இப்படி போகுது. Interviewer, Mumbai-ல ஒரு private bank-ஓட branch operations head Meera-வா நடிக்கிறாரு. Pilot assistant, bank-ஓட 180 branches-ல 12-ல staff-ஓட policy கேள்விகளுக்கு பதில் சொல்லுது.

> **Meera:** "இந்த pilot ரொம்ப மெதுவா போகுது. அடுத்த வெள்ளிக்குள்ள 180 branches-லயும் live ஆகணும்னு எங்க MD நினைக்கிறாரு."
>
> **Arjun:** "சரியா புரிஞ்சுக்கிட்டேனான்னு check பண்றேன்: pilot மெதுவா இருக்குற மாதிரி தோணுறதால, வெள்ளிக்குள்ள எல்லா branch-உம் live ஆகணும்னு MD நினைக்கிறாரு. அடுத்த வெள்ளி என்ன நடக்குது?"
>
> **Meera:** "Board meeting இருக்கு. நாங்க AI-ல முன்னாடி இருக்கோம்னு அவரு காட்டணும்."
>
> **Arjun:** "இது உதவுது. அப்போ உண்மையான goal board-க்கு ஒரு strong கதை. ரெண்டு facts முக்கியம். உங்க security review இன்னும் முடியல, ரெண்டு pilot branches-ல பாதிக்கும் குறைவான staff தான் இதுவரை assistant-ஐ use பண்றாங்க. Review இல்லாம 180 branches-ஐ on பண்ணா, உங்க security team அதை நிறுத்தலாம், அப்புறம் board ஒரு rollback பத்தி கேள்விப்படும்."
>
> **Meera:** "அப்போ முடியாதுன்னு சொல்றீங்க."
>
> **Arjun:** "வெள்ளிக்குள்ள MD-க்கு உண்மையான ஏதாவது தர ரெண்டு வழிகள் இருக்குன்னு சொல்றேன். ஒண்ணு: live pilot numbers-ஓட ஒரு board demo, தேதி போட்ட மூணு-wave rollout plan. ரெண்டு: ready-ஆ இருக்குற அஞ்சு pilot branches-ல full use-ஐ on பண்றது, உங்க security team திங்கள்குள்ள ஒரு fast review முடிச்சா. முதலாவது safe; ரெண்டாவது அதிகமா காட்டும், ஆனா review-ஐ பொறுத்தது."
>
> **Meera:** "Board-க்கு உண்மையான branches பிடிக்கும். Option ரெண்டை try பண்ணுவோம்."
>
> **Arjun:** "அப்போ இன்னைக்கே உங்க security team-க்கு review pack-ஐ அனுப்புறேன், திங்கள் சாயங்காலம் 5 மணிக்குள்ள முடிவு பண்ணுவோம். Clear ஆகலைன்னா demo-க்கு திரும்புவோம். ஒரு மணி நேரத்துக்குள்ள owners, தேதிகளோட email-ல இதை confirm பண்றேன்."

அஞ்சு role-play moves-உம் இருக்கு, கூடவே ஒரு fallback. Meera "அப்போ முடியாதுன்னு சொல்றீங்க"-னு சொல்லும்போது அவரு வாதாடல; திரும்ப options-க்கு போறாரு.

Behavioural round-ல அவரு மேல இருக்குற sales-report கதையை (மூணு நாள்ல இருந்து சுமார் நாலு மணி நேரம்) use பண்றாரு, ஒரு college project-ல இருந்து இன்னொண்ணையும்: அவரு retries-உம் alerts-உம் சேர்த்ததுக்கு அப்புறம் ஒரு மாசத்துல nightly failed data jobs 12%-ல இருந்து 1%-ஆ குறைஞ்சுது.

## பொதுவா பண்ற தப்புகள்

- **Coding-க்கு மட்டும் தயாராகுறது.** Decomposition-க்கும் role-play-க்கும் அதே மாதிரி timed practice வேணும்.
- **நேரா solution-க்கு குதிக்கிறது.** முதல்ல goal, process, data பத்தி கேளுங்க, சத்தமா.
- **Drive பண்ணாம கேள்விகள் மட்டும் கேக்குறது.** Decomposition round-ல பாதி நேரத்துக்குள்ள ஒரு KPI-ஐயும் ஒரு முதல் option-ஐயும் board-ல வைங்க.
- **எல்லாத்துக்கும் சரின்னு சொல்றது, அல்லது நேரடியா முடியாதுன்னு சொல்றது.** ஒரு request-ஐ size பண்ணி client-க்கு உண்மையான choice தர முடியுமான்னு interviewers test பண்றாங்க.
- **Results இல்லாத கதைகள்.** ஒவ்வொரு கதைக்கும் ஒரு before, ஒரு after, அளந்த முறை, உங்க பங்கு, ஒரு lesson வேணும்.
- **பொதுவான system designs.** ஒவ்வொரு choice-ஐயும் client-ஓட constraints கூட இணைங்க.
- **Take-home-ஐ overbuild பண்றது.** Time box-ஐ ரொம்ப தாண்டிப் போனா உங்க judgement தெரியாது, மறைஞ்சுடும்.
- **AI-tool rules-ஐ கண்டுக்காம விடுறது.** ஒவ்வொரு round-லயும் எது allowed-னு கேட்டு அதை follow பண்ணுங்க.

## Practice பண்ணுங்க

Tech Interview Handbook-ஓட behavioural guide-ஐயும், FDE role பத்தின a16z essay-ஐயும் படிங்க.

1. உங்க சொந்த வேலை அல்லது projects-ல இருந்து ஆறு STAR கதைகள் எழுதுங்க, ஒவ்வொண்ணுலயும் அளந்த ஒரு result-உம் ஒரு lesson-உம். ஒவ்வொண்ணையும் ரெண்டு நிமிஷத்துக்குள்ள சத்தமா படிங்க.
2. மேல இருக்குற CSV-cleaning task-ஐ tests-ஓட 30 நிமிஷத்துல பண்ணுங்க, பண்ணும்போதே சத்தமா பேசிக்கிட்டு.
3. நீங்க தேர்ந்தெடுக்குற இந்திய business problems-ல மூணு timed decomposition exercises (ஒவ்வொண்ணும் 30 நிமிஷம்) பண்ணுங்க. உங்களை record பண்ணி, உங்க முதல் proposal-க்கு முன்னாடி எத்தனை நிமிஷம் ஆச்சுன்னு note பண்ணுங்க. அஞ்சுக்கு கீழனா நீங்க குதிச்சுட்டீங்க.
4. இந்த path-ஓட lessons-ல இருக்குற ஒரு scenario-வை வச்சு, ஒரு friend-ஐ கஷ்டமான client-ஆ நடிக்க சொல்லுங்க. அஞ்சு role-play moves-ஐயும் practice பண்ணி, ஒரு owner, ஒரு தேதியோட முடிங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** பார்த்திராத ஒரு business problem-ஐ 30 நிமிஷத்துல, சத்தமா, கேள்விகள், ஒரு KPI, gate-ஓட ஒரு proof of concept-ஆ உடைக்க முடியும், ஒரு role-play client-ஓட நடக்காத demand-ஐ அடிபணியாமலும் மறுக்காமலும் handle பண்ண முடியும்.
