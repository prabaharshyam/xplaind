## இது என்ன

**System design**-னா ஒரு software system-ஓட பகுதிகள் எப்படி ஒண்ணா பொருந்துதுன்னு முடிவு பண்றது. அப்போ தான் அது users-க்கு தேவையானதை, அது சந்திக்கப்போற scale-ல, அதோட budget-குள்ள செய்யும். இதுல components (apps, services, databases, caches, queues), அவற்றுக்கு இடையில data எப்படி ஓடுது, ஏதாவது fail ஆனா என்ன நடக்கும்னு எல்லாம் அடங்கும்.

ஒரே ஒரு சரியான பதில் அரிதா தான் இருக்கும். நல்ல design-னா அதோட choices requirements-க்கு பொருந்தணும், அதோட trade-offs வெளிப்படையா சொல்லப்படணும். Interviewers தேடுறதும் அதைத்தான்: ஒரு perfect diagram-ஐ விட, தெளிவான process, நியாயமான numbers, நேர்மையான trade-offs.

```flow
dir: LR
1. Requirements | இது என்ன பண்ணணும்? எவ்வளவு வேகம், எவ்வளவு பெருசு, எவ்வளவு நம்பகம்? -> 2. Estimates | users, ஒரு second-க்கு requests, storage, bandwidth, average-லயும் peak-லயும்

```

## இது எப்படி work ஆகுது

**1. Requirements-ஐ clarify பண்ணுங்க.** அவற்றை **functional** requirements (system என்ன பண்ணும், "users ஒரு seat-ஐ book பண்ணலாம்" அல்லது "users order status-ஐ பார்க்கலாம்" மாதிரி), **non-functional** requirements (எவ்வளவு நல்லா பண்ணும்: latency, availability, consistency, scale, cost, security) ஆ பிரிங்க. Users யாரு, எத்தனை பேர், எந்த features scope-ல இருக்குன்னு கேளுங்க. பதில்களை எழுதி வச்சுக்கோங்க.

**2. Estimate பண்ணுங்க.** ஒரு **back-of-the-envelope estimate** users-ஐ load-ஆ மாத்தும். பயனுள்ள facts: ஒரு நாள்ல கிட்டத்தட்ட 1 lakh seconds (86,400) இருக்கு. அதனால ஒரு நாளைக்கு 1 crore requests-னா கிட்டத்தட்ட 115 per second. Average-ஐ விட பல மடங்கு peaks-க்கு plan பண்ணுங்க. Storage-ஐ estimate பண்ண: ஒரு item-ஓட size × ஒரு நாளைக்கு items × வச்சிருக்குற நாட்கள். ஒரு database போதுமா, நிறைய வேணுமான்னு இந்த numbers தான் முடிவு பண்ணும்.

**3. High-level design-ஐ sketch பண்ணுங்க.** முக்கியமான boxes, arrows வரையுங்க: clients, ஒரு load balancer, stateless app servers, ஒரு cache, ஒரு database, files-க்கு object storage, மெதுவான jobs-க்கு background workers இருக்குற ஒரு queue. ஒரு request-ஐ முதல்ல இருந்து கடைசி வரை அதுக்குள்ள நடத்திக் காட்டுங்க.

**4. Deep dive.** இந்த system-க்கு ரொம்ப முக்கியமான பகுதிகளை தேர்ந்தெடுத்து ஆழமா போங்க: data model, அதோட indexes, ரொம்ப busy-ஆன path-ஐ scale பண்றது, data-வை consistent-ஆ வச்சுக்கறது, அல்லது திடீர் spike-ஐ handle பண்றது.

**5. Trade-offs, failures.** ஒவ்வொரு choice-க்கும் என்ன செலவுன்னு சொல்லுங்க. Cache reads-ஐ வேகப்படுத்தும், ஆனா பழைய data-வை serve பண்ணலாம். Queue spikes-ஐ சமப்படுத்தும், ஆனா delay-ஐ சேர்க்கும். அதிக replicas availability-ஐ உயர்த்தும், ஆனா செலவு அதிகம். ஒவ்வொரு component-க்கும் "இந்த box fail ஆனா என்ன?"ன்னு கேளுங்க.

| Non-functional தேவை | வழக்கமான numbers | Design levers |
|---|---|---|
| Latency | ஒரு page-க்கு p95 200 ms-க்கு கீழ | caches, CDNs, குறைவான hops, indexes |
| Throughput | ஒரு second-க்கு ஆயிரக்கணக்கான requests | அதிக app servers, load balancing, async work |
| Availability | 99.9% = மாசத்துக்கு கிட்டத்தட்ட 43 நிமிஷம் down | replicas, health checks, single point of failure இல்லாம |
| Consistency | payments-க்கு strong, likes-க்கு eventual | transactions, primary-only reads, idempotency |
| Cost | ஒரு lakh requests-க்கு rupees | சரியான size machines, caching, மலிவான storage tiers |

**Browser-லயே try பண்ணுங்க.** Back-of-envelope numbers தான் பெரும்பாலான designs-ஐ முடிவு பண்ணும். Inputs-ஐ மாத்தி run பண்ணுங்க.

```python
daily_users = 200_000
requests_per_user = 15
peak_factor = 3
bytes_per_record = 2_000

per_second = daily_users * requests_per_user / 86_400
print(f"average {per_second:,.0f} requests/s, peak about {per_second * peak_factor:,.0f}/s")
storage_gb_year = daily_users * requests_per_user * bytes_per_record * 365 / 1e9
print(f"about {storage_gb_year:,.0f} GB of records a year")
```

## ஒரு நாள், ஒரு example

மீரா interview-ல Bengaluru-ல ஒரு food delivery app-க்கு order-status page-ஐ design பண்ண கேக்கப்படுறாங்க: order பண்ணதுக்கு அப்புறம் customers "Preparing", "Picked up", "Arriving"-ஐயும் rider-ஓட location-ஐயும் பார்ப்பாங்க.

**Requirements.** அவங்க கேட்டு உறுதி பண்றாங்க: active orders-க்கு status, rider location-ஐ காட்டணும். Updates கிட்டத்தட்ட 5 seconds-குள்ள வரணும். ஒரு நாளைக்கு 20 lakh orders, dinner நேரத்துல peak. History scope-ல இல்லை. Perfect freshness-ஐ விட availability முக்கியம்: சில seconds பழைய location-ஐ காட்டினா பரவாயில்லை.

**Estimates.** ஒரு நாளைக்கு 20 lakh orders, ஒவ்வொண்ணும் கிட்டத்தட்ட 40 நிமிஷம் active. Riders ஒவ்வொரு 5 seconds-க்கும் location அனுப்புறாங்க. அதனால ஒவ்வொரு order-உம் கிட்டத்தட்ட 480 updates உருவாக்கும். அது ஒரு நாளைக்கு கிட்டத்தட்ட 96 crore updates: average-ஆ கிட்டத்தட்ட 11,000 per second, dinner peak-ல ஒருவேளை 40,000. Customers page-ஐ அடிக்கடி refresh பண்றதால reads இன்னும் அதிகம். ஒவ்வொரு location update-உம் சின்னது, கிட்டத்தட்ட 100 bytes. ஆனா delivery-க்கு அப்புறம் அவற்றை வச்சுக்க தேவையில்லை.

**High-level design.** Rider apps locations-ஐ ஒரு load balancer-க்கு பின்னாடி இருக்குற ingestion service-க்கு அனுப்புது. ஒவ்வொரு order-க்கும் latest location, order ID-ஐ key-ஆ வச்சு, ஒரு குறுகிய expiry-ஓட Redis மாதிரி in-memory store-ல போகும். Order status மாற்றங்கள் main database-ல எழுதப்பட்டு, ஒரு queue-க்கும் publish ஆகும். Customer apps ஒரு notification service-க்கு WebSocket connection-ஐ திறந்து வச்சிருக்கும். அது status, location மாற்றங்களை push பண்ணும். Connection விழுந்தா, app Redis-ல இருந்து படிக்குற ஒரு read API-ஐ poll பண்றதுக்கு மாறும்.

**Deep dive, trade-offs.** அதிக அளவுல வர்ற location stream ஏன் main SQL database-ல போகக்கூடாதுன்னு அவங்க explain பண்றாங்க: நாளைக்கு யாருக்கும் தேவையில்லாத data-க்காக அந்த database bottleneck ஆயிடும். Refunds, support-க்கு முக்கியமான status database-ல போகும். Trade-off-ஐ சொல்றாங்க: ஒரு node fail ஆனா Redis கடைசி சில seconds locations-ஐ இழக்கலாம். இங்க அது ஏத்துக்கலாம். Order status durable. Failure cases-ஓட முடிக்கிறாங்க: notification service down-னா polling இன்னும் work ஆகும். Redis down-னா page map இல்லாம status-ஐ காட்டும்.

Interviewer அப்புறம் சொன்னார்: தனக்கு தனிச்சு தெரிஞ்சது boxes இல்லை. ஒவ்வொரு choice-ம் ஒரு number அல்லது requirement-ஓட திரும்ப இணைக்கப்பட்டிருந்ததுதான்.

## பொதுவா பண்ற தப்புகள்

**கேக்காம வரையறது.** Requirements இல்லாம diagram-க்கு குதிச்சா, தப்பான problem-க்கு confident-ஆன design வரும். முதல் சில நிமிஷங்களை கேள்விகளுக்கு செலவழிங்க.

**Numbers-ஐ skip பண்றது.** Estimate இல்லாம, ஒரு database போதுமான்னு சொல்ல முடியாது. தோராயமான numbers-ஆ இருந்தாலும், தெளிவா சொன்னா, எதுவும் இல்லாததை விட நல்லது.

**Average-க்கு design பண்றது, peak-க்கு இல்லை.** Sales, results day, Tatkal windows சாதாரண traffic-ஐ விட பல மடங்கு கொண்டு வரும். Peak-க்கு size பண்ணி, spikes-ஐ எப்படி absorb பண்ணுவீங்கன்னு சொல்லுங்க.

**தெரிஞ்ச எல்லா components-ஐயும் சேர்க்கறது.** Microservices, Kafka, Kubernetes எல்லா இடத்துலயும் இருந்தா design-ஐ ஓட்டறது கஷ்டமாகும். ஒரு requirement-க்கு தேவைப்படும்போது மட்டும் ஒரு component-ஐ சேருங்க.

**Trade-offs-ஐ மறைக்கறது.** ஒவ்வொரு choice-க்கும் ஒரு cost இருக்கு. அதை சத்தமா சொல்றது உங்க judgement-ஐ காட்டும்.

**Failure-ஐ மறந்துடுறது.** ஒவ்வொரு box-உம் down ஆனா என்ன ஆகும்னு கேளுங்க. Reviewers முதல்ல தேடுறது single points of failure-ஐ தான்.

## Practice பண்ணுங்க

1. Core building blocks-ஓட ஒரு tour-க்கு, Watch & learn panel-ல இருக்குற video lessons-ஐ பாருங்க.
2. மேல இருக்குற estimation exercise-ஐ பண்ணுங்க, அப்புறம் நீங்க தினமும் use பண்ற ஒரு app-க்கு திரும்ப பண்ணுங்க.
3. Project check-ஐ பண்ணுங்க: தெரிஞ்ச ஒரு இந்திய app feature-க்கு ஒரு பக்க design.
4. அஞ்சு steps-ஐயும் ஒரு நிமிஷத்துக்குள்ள சத்தமா சொல்லி practice பண்ணுங்க. அப்போ interview-ல அவை இயல்பா வரும்.
