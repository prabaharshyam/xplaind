## இது என்ன

**Kubernetes**, machines-ஓட ஒரு குழுவுல (ஒரு cluster) containers-ஐ run பண்ணுது. "இந்த image-ஓட மூணு copies, ஒவ்வொண்ணுக்கும் 1 CPU, 2 GB memory, இந்த பெயர்ல reach பண்ணலாம்"னு நீங்க என்ன வேணும்னு விவரிப்பீங்க; அந்த விவரிப்புக்கு ஏத்த மாதிரியே நிஜம் இருக்கும்படி Kubernetes பார்த்துக்கும்: containers-ஐ start பண்ணும், crash ஆனவற்றை restart பண்ணும், failed machines-ல இருந்து அவற்றை நகர்த்தும், traffic-ஐ பரப்பும்.

**Helm**, ஒரு app-ஓட எல்லா Kubernetes files-ஐயும் மாத்தக்கூடிய values-ஓட ஒரு **chart**-ஆ package பண்ணும்; அதனால அதே chart staging-லயும் production-லயும் வேற வேற settings-ஓட install ஆகும்.

ஒரு FDE-ஆ நீங்க பெரும்பாலும் Kubernetes-ஓட ஓரத்துல வேலை செய்வீங்க: ஒரு image-ஐயும் ஒரு chart அல்லது சில YAML files-ஐயும் ship பண்ணுவீங்க, client-ஓட platform team cluster-ஐ run பண்ணும்.

```flow
வெளி traffic, HTTPS -> Ingress | contracts.bank.example
Ingress -> Service: contracts-api | ஒரு stable பெயர்; ready ஆன pods-க்கு மட்டும் அனுப்பும்
Service: contracts-api -> Pod 1
Service: contracts-api -> Pod 2
Service: contracts-api -> Pod 3
Deployment | contracts-api:2.3.1-ஓட 3 replicas; ஒவ்வொரு pod-உம் 500m CPU, 1Gi request பண்ணும், limits 1 CPU, 2Gi; probes /health, /ready -> Pod 1
ConfigMap, Secret | settings, platform team உருவாக்குற model key -> Pod 2
Helm chart + values-staging.yaml அல்லது values-prod.yaml -[helm upgrade, helm rollback]-> Deployment
```

இந்த lesson-ல, Mumbai-ல ஒரு bank-ஓட Kubernetes platform-ல deploy பண்ண ஒரு contract-analysis API-ஐ follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

முக்கிய objects:

- **Pod**: ஒண்ணா run ஆகுற ஒண்ணு அல்லது அதுக்கு மேற்பட்ட containers. Pods தூக்கி எறியக்கூடியவை; Kubernetes அவற்றை சுதந்திரமா மாத்தும்.
- **Deployment**: எந்த image-ஓட எத்தனை pods run பண்ணணும், ஒரு புது version-ஐ எப்படி roll out பண்ணணும் (படிப்படியா, ஒரு நேரத்துல சிலதை மாத்தி) என்று சொல்லும்.
- **Service**: இப்போ healthy-ஆ இருக்குற pods-க்கு traffic-ஐ அனுப்புற ஒரு stable பெயரும் address-உம்.
- **Ingress**: வெளி HTTP traffic-ஐ services-க்கு route பண்ணும், பெரும்பாலும் HTTPS-ஓட.
- **ConfigMap**, **Secret**: environment variables அல்லது files-ஆ pods-க்கு போற settings, sensitive values.
- **HorizontalPodAutoscaler**: CPU, memory அல்லது custom metrics-ஐ பார்த்து pods-ஐ கூட்டும் அல்லது குறைக்கும்.

ஒவ்வொரு container-உம் **requests** (அதுக்கு உத்தரவாதமா கிடைக்குறது), **limits** (அது use பண்ணக்கூடிய அதிகபட்சம்) declare பண்ணும். Memory limit-ஐ தாண்டுற container kill ஆகும்; அது `OOMKilled`-ஆ தெரியும். **Probes**, ஒரு pod உயிரோட இருக்கு (liveness), traffic-க்கு ready (readiness)ன்னு Kubernetes-க்கு சொல்லும்; இவை serving lesson-ல வந்த `/health`, `/ready` endpoints-க்கு map ஆகும்.

நீங்க `kubectl`-ஓட பேசுவீங்க: `get pods`, `describe pod`, `logs`, `rollout status`, `rollout undo`. Helm-ஓட: `helm install`, `helm upgrade --values prod.yaml`, `helm rollback`.

**பொதுவான pod states-உம் என்ன பண்ணணும்னும்:**

| State | பொதுவா என்ன அர்த்தம் | முதல் command |
| --- | --- | --- |
| Pending | Requests-க்கு எந்த machine-லயும் இடம் இல்ல | Scheduling events-க்கு `kubectl describe pod` |
| ImagePullBackOff | தப்பான image பெயர், tag அல்லது registry access | Tag-ஐயும் registry secret-ஐயும் check பண்ணுங்க |
| CrashLoopBackOff | App start ஆனதும் exit ஆகுது | `kubectl logs --previous` |
| OOMKilled | Memory limit தாண்டிடுச்சு | Peak memory-ஐ அளவுங்க; limit-ஐ ஏத்துங்க அல்லது use-ஐ குறைங்க |
| Running, ஆனா ready இல்ல | Readiness probe fail ஆகுது | `/ready` endpoint-ஐயும் அதோட dependencies-ஐயும் check பண்ணுங்க |

**Requests, limits-ஐ தேர்ந்தெடுக்கிறது.** Set பண்றதுக்கு முன்னாடி அளவுங்க. Users அனுப்புற மிகப்பெரிய documents உட்பட, உண்மையான inputs-ஓட ஒரு load test run பண்ணி, ஒவ்வொரு pod-க்கும் memory, CPU-ஐ கவனிங்க. Requests-ஐ சாதாரண use-க்கு கிட்ட வைங்க, memory limits-ஐ நீங்க பார்த்த peak-ஐ விட சௌகரியமா மேல வைங்க. ரொம்ப குறைவான requests, cluster pods-ஐ ரொம்ப நெருக்கமா அடுக்க விடும்; ரொம்ப குறைவான limits, பெரிய inputs-ல pods-ஐ kill பண்ணும். Numbers-ஐ platform team-ஓட பேசி முடிவு பண்ணுங்க, ஏன்னா machines-க்கு பணம் கொடுக்கிறது அவங்க.

**Platform team-ஓட வேலை செய்றது.** அவங்க என்ன கொடுக்குறாங்கன்னு சீக்கிரமே கேளுங்க: namespace, ingress set-up, Secrets எப்படி உருவாக்கப்படுது, எந்த registries allowed, monitoring, log collection. பல platform teams-க்கு ஒரு standard chart அல்லது required labels, resource limits மாதிரி policies இருக்கும்; அவற்றை ignore பண்ற deploy reject ஆகும்.

**ஒரு AI API-க்கு வடிவமைக்கப்பட்ட Deployment.** Probes, resources, ஒரு safe rollout, streams-க்கான grace period:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: claims-api}
spec:
  replicas: 3
  strategy:
    rollingUpdate: {maxUnavailable: 0, maxSurge: 1}        # never drop below 3 during a rollout
  selector: {matchLabels: {app: claims-api}}
  template:
    metadata: {labels: {app: claims-api}}
    spec:
      terminationGracePeriodSeconds: 120                    # longer than the longest streamed answer
      containers:
        - name: api
          image: registry.example.in/claims-api:3f9c2e1
          ports: [{containerPort: 8000}]
          envFrom: [{secretRef: {name: claims-api-secrets}}]
          resources:
            requests: {cpu: "500m", memory: "768Mi"}
            limits: {memory: "1536Mi"}
          readinessProbe:
            httpGet: {path: /ready, port: 8000}
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 20
            periodSeconds: 10
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: claims-api}
spec:
  minAvailable: 2
  selector: {matchLabels: {app: claims-api}}
```

**Autoscaling.** ஆரம்பத்துல CPU-ல scale பண்ணுங்க; பெரும்பாலும் model calls-க்காக காத்திருக்குற AI APIs-க்கு, ஒரு pod-க்கு in-flight requests மாதிரி ஒரு custom metric load-ஐ நல்லா track பண்ணும்:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: claims-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: claims-api}
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 65}}
```

**GPU workloads.** ஒரு model server pod GPUs-ஐ வெளிப்படையா கேக்கும், GPU nodes-ல அனுமதிக்கப்படும்:

```yaml
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.10.1
          resources: {limits: {nvidia.com/gpu: 1}}
      tolerations:
        - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
```

Model weights, ஒரு persistent volume அல்லது முன்னாடியே warm பண்ண cache-ல இருக்கணும், ஒவ்வொரு pod start-லயும் download ஆகக்கூடாது; இல்லைன்னா scale up பண்ண பல நிமிஷங்கள் ஆகும்.

**ஒவ்வொரு environment-க்கும் Helm values.** Templates-ஐ ஒரே தடவை வச்சு, வித்தியாசங்களை சின்னதா வச்சுக்கோங்க:

```yaml
# values-prod.yaml
replicas: 3
image: {tag: 3f9c2e1}
resources: {requests: {cpu: 500m, memory: 768Mi}, limits: {memory: 1536Mi}}
hpa: {min: 3, max: 12}
```

`helm upgrade --install claims-api ./chart -f values-prod.yaml --atomic --timeout 10m`, புது pods எப்பவும் ready ஆகலைன்னா தானா rollback பண்ணும்.

**உங்க browser-ல try பண்ணுங்க.** ஒரு Deployment-ஐ apply பண்றதுக்கு முன்னாடி, probes, limits இல்லாததை check பண்ணுங்க. YAML-ஐ edit பண்ணுங்க.

```python
import yaml

deployment = yaml.safe_load("""
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: api
          image: registry.example.in/claims-api:latest
          resources: {requests: {cpu: 500m}}
""")
spec = deployment["spec"]
if spec.get("replicas", 1) < 2:
    print("fewer than 2 replicas: one restart takes the service down")
for c in spec["template"]["spec"]["containers"]:
    if c["image"].endswith(":latest"): print(f"{c['name']}: pin the image tag")
    if "readinessProbe" not in c: print(f"{c['name']}: add a readiness probe")
    if "limits" not in c.get("resources", {}): print(f"{c['name']}: set a memory limit")
```

## ஒரு நாள், ஒரு example

Mumbai-ல ஒரு bank-ஓட Kubernetes platform-ல ஒரு contract-analysis API-ஐ deploy பண்றீங்க. Platform team உங்களுக்கு ஒரு namespace கொடுத்து, ஒரு Helm chart கேக்குறாங்க.

உங்க chart-ஓட `values-prod.yaml`-ல 3 replicas, 500m CPU, 1Gi memory requests, 1 CPU, 2Gi limits, `contracts-api:2.3.1` image tag, ingress host, model key வச்சிருக்குற ஒரு Secret-க்கான reference set பண்ணியிருக்கீங்க (Secret-ஐ platform team உருவாக்கும்; அதோட value உங்க chart-ல ஒருபோதும் இருக்காது).

`helm upgrade`-க்கு அப்புறம், மூணுல ரெண்டு pods திரும்ப திரும்ப restart ஆகுது. நீங்க check பண்றீங்க:

```bash
kubectl get pods -n contracts
kubectl describe pod contracts-api-7d9c-xk2lp -n contracts   # Last State: OOMKilled
kubectl logs contracts-api-7d9c-xk2lp -n contracts --previous
```

`OOMKilled`: புது version ஒரு பெரிய tokenizer-ஐயும் ஒரு PDF library-யையும் load பண்ணுது; பெரிய contracts-ல அவை 2.4 GB வரை peak ஆகுது. `helm rollback contracts-api`-ஆல rollback பண்றீங்க, அதனால users பாதிக்கப்படலை; platform team-ஓட பேசி உறுதி பண்ணதுக்கு அப்புறம் limit-ஐ 3Gi-க்கு ஏத்துறீங்க; அடுத்த memory jump deploy-க்கு முன்னாடியே பிடிபட, CI-ல 300-page contract-ஓட ஒரு test-ஐ சேக்குறீங்க.

| Step | Command அல்லது change |
| --- | --- |
| Restarts-ஐ கண்டுபிடிக்கிறது | `kubectl get pods -n contracts` |
| காரணத்தை கண்டுபிடிக்கிறது | `kubectl describe pod ...` OOMKilled-ஐ காட்டுச்சு |
| Users-ஐ பாதுகாக்கிறது | `helm rollback contracts-api` |
| Fix | Memory limit 3Gi-க்கு ஏத்தப்பட்டது, platform team-ஓட ஒத்துக்கிட்டு |
| தடுக்கிறது | CI-ல 300-page contract test சேர்க்கப்பட்டது |

## பொதுவா பண்ற தப்புகள்

- **Resource requests அல்லது limits இல்லாம இருக்கிறது.** Pods நசுக்கப்படும் அல்லது மத்தவற்றை நசுக்கும். ரெண்டையும் எப்பவும் அளவீடுகள்ல இருந்து set பண்ணுங்க.
- **Readiness probe இல்லாம இருக்கிறது.** Models இன்னும் load ஆகிட்டு இருக்குற pods-க்கு traffic போகும், ஒவ்வொரு deploy-க்கு அப்புறமும் users errors பார்ப்பாங்க.
- **Chart-ல Secrets.** Values files Git-ல போயிடும். Platform manage பண்ற Secrets-ஐ reference பண்ணுங்க.
- **Image tag-ஆ `latest` use பண்றது.** Rollbacks-உம் audits-உம் ஊகம் ஆகிடும்.
- **Production-ல kubectl edit-ஆல விஷயங்களை fix பண்றது.** அடுத்த Helm upgrade அதை திருப்பிடும். Chart-ஐ மாத்துங்க.
- **குறைவான replicas இருக்கும்போது maxUnavailable பூஜ்யத்துக்கு மேல இருக்கிறது**, அதனால rollout capacity-ஐ குறைக்கும்.
- **குறுகிய termination grace period**, ஒவ்வொரு deploy-லயும் streamed answers-ஐ வெட்டிடும்.
- **Pod start-ல model weights-ஐ download பண்றது**, scale-up-ஐ மெதுவாக்கும்.

## Kubernetes தேவையில்லாத சமயங்கள்

- **கொஞ்சம் services, மிதமான traffic**: serverless containers (Cloud Run, Container Apps, Fargate-ல ECS) எளிமையானவை.
- **Platform engineers இல்லாத ஒரு சின்ன team**, cluster-ஏ முக்கிய வேலை ஆகிடும்.
- **Prototypes, pilots**, client-ஓட platform team ஏற்கனவே உங்களுக்காக ஒரு cluster run பண்றாங்கன்னா தவிர.

## Demo-ல இருந்து production-க்கு

- **Load tests-ல இருந்து requests, limits-ஐ set பண்ணி**, OOMKilled pods-க்கு alert வைங்க.
- **சொல்றதை உண்மையா check பண்ற readiness, liveness probes-ஐ use பண்ணுங்க.**
- **maxUnavailable 0, ஒரு PodDisruptionBudget-ஓட capacity-ஐ பாதுகாங்க.**
- **`helm upgrade --atomic`-ஓட deploy பண்ணி**, rollback-ஐ ஒரே command-ஆ வச்சுக்கோங்க.
- **GPU workloads-க்கு model weights-ஐ volumes-ல cache பண்ணுங்க.**

## Practice பண்ணுங்க

Kubernetes basics tutorial-ஐயும் Helm-ஓட quickstart-ஐயும் பண்ணுங்க. ஒரு free local cluster (kind, minikube அல்லது Docker Desktop-ஓடது) போதும்.

1. உங்க containerised FastAPI app-ஐ, ஒரு Deployment, ஒரு Service, `/ready`, `/health`-ல readiness, liveness probes-ஓட deploy பண்ணுங்க.
2. அதை "staging" (1 replica), "prod" (3 replicas)-க்கு தனித்தனி values-ஓட ஒரு Helm chart-ஆ package பண்ணுங்க.
3. வேணும்னே ஒரு memory limit-ஐ ரொம்ப குறைவா set பண்ணி, pod `OOMKilled` ஆகுறதை பாருங்க, `kubectl describe`-ல ஏன்னு படிங்க, அப்புறம் fix பண்ணி மறுபடி roll out பண்ணுங்க.
4. maxUnavailable 0, ஒரு PodDisruptionBudget-ஓட deploy பண்ணி, ஒரு rollout நடக்கும்போது load test run பண்ணி, எந்த request-உம் fail ஆகலைன்னு உறுதி பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க app-ஐ Helm-ஆல deploy பண்ணி, upgrade பண்ணி, rollback பண்ண முடியும்; ஒரு pod ஏன் run ஆகலைன்னு `kubectl describe`-ல இருந்து explain பண்ண முடியும்.
