## இது என்ன

"எங்க WhatsApp orders-ஐ automate பண்ண முடியுமா?"ன்னு கேக்குறது ஒரே கேள்வி மாதிரி தெரியும். அதுக்குள்ள டஜன் கணக்கான கேள்விகள் ஒளிஞ்சிருக்கு. Voice notes-உம் சேர்த்தா? List-ல இல்லாத ஒரு product வந்தா? Result-ஐ யார் check பண்ணுவாங்க? Messages-ஐ யார் பாக்கலாம்? ஆறு மாசம் கழிச்சு இதை யார் சரி பண்ணுவாங்க? ஒரு **automation scope** வேலை ஆரம்பிக்கறதுக்கு முன்னாடியே இதுக்கெல்லாம் பதில் சொல்லுது, அதனால என்ன கிடைக்குது, எதுக்கு பணம் குடுக்குறோம்னு ரெண்டு பக்கத்துக்கும் தெரியும்.

Scope-னா ஒரு சின்ன written agreement, பொதுவா ஒண்ணு ரெண்டு பக்கம், technical design இல்ல: owner ஒவ்வொரு வரியையும் படிச்சு yes-ஓ no-வோ சொல்ல முடியணும். அதுல பதினொரு பகுதிகள் இருக்கு:

| பகுதி | பதில் சொல்ற கேள்வி |
| --- | --- |
| **Process-உம் boundaries-உம்** | எங்க ஆரம்பிக்குது, எங்க முடியுது? |
| **Inputs-உம் volumes-உம்** | என்ன வருது, எந்த formats-ல, ஒரு நாளைக்கு எத்தனை? |
| **Steps** | System என்ன பண்ணுது, ஆளுங்க இன்னும் என்ன பண்றாங்க? |
| **Exceptions** | System handle பண்ண முடியாத cases-க்கு என்ன ஆகும்? |
| **Systems-உம் access-உம்** | எந்த accounts தேவை, யார்கிட்ட இருந்து, எப்போ வரைக்குள்ள? |
| **Data-வும் risks-உம்** | என்ன personal data எங்க போகுது? என்ன தப்பா போகலாம்? |
| **Assumptions** | Price மாறாம இருக்க எது உண்மையா இருக்கணும்? |
| **Success measures** | எந்த baseline-க்கு எதிரா எது improve ஆகுது? |
| **Acceptance-உம் sign-off-உம்** | எந்த test, எந்த data-ல, "accepted"-னு யார் சொல்றாங்க? |
| **Support-உம் changes-உம்** | Fixes எவ்வளவு நாள் free, எது change-ஆ count ஆகும்? |
| **Price, payments, timeline** | எவ்வளவு, எப்போ pay பண்ணணும், எந்த dates-க்குள்ள? |

**In scope**-னா நீங்க promise பண்ற வேலை. **Out of scope**-னா பண்ண மாட்டேன்னு நீங்க எழுத்துல சொன்ன வேலை. ஒரு **change request**-னா scope-ஐ மாத்த ஒரு written proposal, அது time-லயும் price-லயும் என்ன effect பண்ணும்னு சேர்த்து.

```flow
Discovery | process map, samples -> Draft scope -[client reads]-> Questions, edits
Questions, edits -> Draft scope
Draft scope -> Signed scope | in, out, acceptance, support, price
Signed scope -> Build -> Acceptance test -> Handover -> Support period -> Change requests
```

இந்த lesson Indore-ல இருக்குற freelance automation specialist Ritika-வை follow பண்ணுது. ஒரு distributor அவங்ககிட்ட "WhatsApp-ல வர்ற orders-ஐ automate பண்ணுங்க"ன்னு கேட்டிருக்காங்க. Lesson முடியும்போது, ஒரு owner sign பண்ற scope-ஐ, நீங்க defend பண்ணக்கூடிய ஒரு price-ஓட, உங்களால எழுத முடியும்.

## இது எப்படி work ஆகுது

### Process map-ல இருந்து ஆரம்பிங்க

Discovery-ல வந்த map-ஐ use பண்ணுங்க. கீழ இருக்குற worked example-ல இருக்குற மாதிரி, start-ஐயும் end-ஐயும் concrete events-ஆ எழுதுங்க. அப்புறம் ஒவ்வொரு step-ஐயும் **automated**, **assisted** (system draft பண்ணுது, ஒரு ஆள் approve பண்றாங்க) அல்லது **manual**-னு mark பண்ணுங்க. Map-உம் இந்த decisions-உம் சேர்ந்தது தான் scope.

முதல் version-க்கு ஒரு useful default: ஒரு step-ஐ undo பண்றது கஷ்டம்னா, அதை automated ஆக்காம assisted ஆக்குங்க. பின்னாடி, அது safe-னு data காட்டினதும், ஒரு human check-ஐ எடுக்குறது ஈஸி; ஒரு costly தப்பு நடந்ததுக்கு அப்புறம் ஒண்ணை சேர்க்குறது ஈஸி இல்ல.

### Samples-ஐ collect பண்ணி count பண்ணுங்க

சாதாரண நாட்கள்ல இருந்து சுமார் 40 real inputs கேளுங்க (20-ல இருந்து 50 வரை போதும்), messy ones-உம் சேர்த்து, client-க்கு பிடிச்ச examples இல்ல. அப்புறம் count பண்ணுங்க:

| Input type | 40 samples-ல count | Decision |
| --- | --- | --- |
| Typed text orders | 22 | In scope |
| கையால எழுதின lists-ஓட photos | 12 | In scope, staff review-ஓட |
| Voice notes | 5 | இப்போதைக்கு out of scope; phase 2 |
| வேற apps-ல இருந்து forward பண்ண PDFs | 1 | ஒரு exception-ஆ staff-க்கு அனுப்பப்படும் |

இந்த sample size-ல counts தோராயமானது தான். 40-ல பன்னிரண்டு photos-னா, வேலையிலயும் risk-லயும் photos ஒரு பெரிய share-னு சொல்லுது; ஒரு PDF-னா PDFs இருக்குன்னு மட்டும் சொல்லுது, அது எவ்வளவு common-னு இல்ல. அதனால staff-கிட்டயும் கேளுங்க: "அரிதா இருந்தாலும் வேற என்ன வரும்?"

ஒவ்வொரு exception-க்கும் choose பண்ணுங்க: automatic-ஆ handle பண்றதா, ஒரு ஆள்கிட்ட அனுப்புறதா, இல்ல exclude பண்றதா, அந்த choice-ஐ எழுதி வைங்க. "ஒரு ஆள்கிட்ட அனுப்புறது"-க்கு பேர் சொன்ன ஒரு queue-உம் பேர் சொன்ன ஒரு ஆளும் வேணும்.

Samples-ல real customers-ஓட details இருக்கு: அதை client control பண்ற ஒரு folder-ல வைங்க, கடைசியில உங்ககிட்ட இருக்குற copies-ஐ delete பண்ணிடுங்க.

### Human checkpoints-ஐ ஒத்துக்கோங்க

Payments, customers-க்கு போற messages, deletions இதுக்கெல்லாம் பொதுவா approval தேவை. யார் approve பண்றாங்க, எந்த tool-லன்னு பேர் சொல்லுங்க. யாருக்கும் நேரம் இல்லாத ஒரு checkpoint ஒரு வாரத்துக்குள்ள skip ஆகிடும், அதனால அதை வேகமா ஆக்குங்க: original message-க்கு பக்கத்துல extract பண்ண result, confirm பண்ண ஒரே ஒரு button.

### Access-ஐ ஒரு dependency-ஆ ஆக்குங்க

ஒவ்வொரு system-ஐயும், தேவையான account-ஐயும், அதை யார் குடுப்பாங்க, எப்போ வரைக்குள்ளன்னும் list பண்ணுங்க. Technical problems-ஐ விட access delays தான் பல நேரம் projects-ஐ அதிகமா நிறுத்தி வைக்குது.

WhatsApp ஒரு common example. ஒரு automation-க்கு **WhatsApp Business Platform** தேவை, அது Meta-வோட API, பொதுவா ஒரு provider வழியா; phone-ல இருக்குற free WhatsApp Business app போதாது. Meta முதல்ல business-கிட்ட business verification-ஐ முடிக்க சொல்லலாம். Providers report பண்றபடி review-க்கு சில மணி நேரத்துல இருந்து சுமார் ரெண்டு வாரம் வரை ஆகுது, சில சமயம் அதுக்கு மேலயும், guaranteed time எதுவும் இல்ல, அதனால client அதை முதல் வாரத்துலயே ஆரம்பிக்கணும். அதே number API-ல சேர்ந்ததுக்கு அப்புறம் staff அதே number-ல phone app-ஐ தொடர்ந்து use பண்ண முடியுமான்னும் provider-கிட்ட கேளுங்க; Meta சில cases-ல, conditions-ஓட, இதை allow பண்ணுது.

Scope-ல இதை எழுதுங்க: "Access late-ஆ வந்தா, எத்தனை நாள் late ஆச்சோ அத்தனை நாள் go-live தள்ளிப் போகும்."

### Data-வையும் risks-ஐயும் எழுதி வைங்க

பெரும்பாலான automations personal data-வை நகர்த்துது: பேர்கள், phone numbers, order history. இந்தியால, Digital Personal Data Protection Act, 2023 (DPDP Act) இதை cover பண்ணுது. Data எதுக்கு use ஆகுதுன்னு முடிவு பண்ற business தான் **data fiduciary**. நீங்க, messaging provider, AI provider எல்லாரும் அதோட சார்பா data-வை process பண்றீங்க, **data processors**-ஆ; ஒரு valid contract-ஓட மட்டும் தான் ஒரு fiduciary ஒரு processor-ஐ use பண்ணலாம்னு Act சொல்லுது. DPDP Rules November 2025-ல notify ஆச்சு, அதோட பெரும்பாலான duties May 2027-ல இருந்து apply ஆகும், அதனால clients இப்போவே இதைப் பத்தி கேக்குறாங்க. இது legal advice இல்ல; அசாதாரணமான எதுக்கும், client ஒரு lawyer-கிட்ட கேக்கணும்.

Scope-ல, சாதாரண வார்த்தைகள்ல பதில் சொல்லுங்க:

- System-க்குள்ள என்ன personal data வருது, யார்கிட்ட இருந்து;
- அது எங்க store-உம் process-உம் ஆகுது, எந்த AI provider, எந்த region உட்பட;
- Raw messages-உம் photos-உம் delete ஆகுறதுக்கு முன்னாடி எவ்வளவு நாள் வச்சிருக்கப்படும்;
- அதை யார் பாக்கலாம்;
- Business API data-ல AI provider train பண்ணுதா (அதோட இப்போதைய terms-ஐ check பண்ணி date-ஐ note பண்ணுங்க).

முக்கியமான மூணுல இருந்து அஞ்சு risks-ஐ list பண்ணுங்க, ஒவ்வொண்ணுக்கும் ஒரு mitigation-உம் ஒரு owner-உம்.

### Assumptions-ஐ சொல்லுங்க

Assumption-னா நீங்க நம்பி இருக்குற ஆனா check பண்ணாத ஒரு விஷயம், உதாரணமா "client product list-ஐ update-ஆ வச்சிருப்பாங்க" அல்லது "billing import format மாறாது". அதுல ஒண்ணு fail ஆனா, extra work ஒரு change request. இது ஒரு fixed price-ஐ நியாயமா வச்சிருக்கும்.

### முதல்ல baseline-ஐ measure பண்ணுங்க, அப்புறம் targets வைங்க

Measure பண்ணாத ஒரு saving-ஐ நீங்க claim பண்ண முடியாது. சில சாதாரண நாட்களுக்கு இப்போ இருக்குற process-ஐ time பண்ணுங்க, இன்னைக்கு வர்ற errors-ஐ count பண்ணுங்க, அப்புறம் அதுக்கு எதிரா targets வைங்க (ROI-ஐ measure பண்ற lesson அதை ரூபாயா மாத்தும்).

### Acceptance-ஐ ஒரு test-ஆ define பண்ணுங்க

"System நல்லா work ஆகுது"-ங்கறது ஒரு test இல்ல. Test பண்ணக்கூடிய ஒரு acceptance-க்கு அஞ்சு பகுதிகள் இருக்கு:

1. **Data:** எந்த items, எந்த period-ல இருந்து, யார் choose பண்ணது. Client தான் choose பண்ணணும், in-scope items-ல இருந்து மட்டும்.
2. **Answer key:** ஒவ்வொரு item-க்கும் சரியான result, test-க்கு முன்னாடியே client பக்கத்துல தயார் பண்ணது.
3. **Correct-க்கு definition:** உதாரணமா, product code-உம் quantity-உம் ரெண்டுமே bill பண்ண invoice கூட match ஆகணும்.
4. **Threshold:** reach பண்ண வேண்டிய number.
5. **Sign-off:** accept பண்ற authority இருக்குற ஆள், reply பண்ண அவருக்கு எவ்வளவு நேரம்.

ரெண்டு gotchas. முதல்ல, line accuracy-உம் order accuracy-உம் ஒண்ணு இல்ல. 90% lines சரியா இருந்து, ஒரு order-ல அஞ்சு lines இருந்து, errors சமமா பரவியிருந்தா, சுமார் 59% orders தான் முழுசா சரியா இருக்கும் (0.9-ஓட power 5 சுமார் 0.59). நீங்க எதை measure பண்றீங்க, human review-க்கு அது என்ன அர்த்தம்னு சொல்லுங்க. ரெண்டாவது, office manager test-ஐ run பண்ணலாம், ஆனா owner மட்டும் தான் அதை accept பண்ண முடியும். Owner-ஓட பேரை சொல்லி ஒரு reply window சேருங்க, உதாரணமா: "அஞ்சு working days-க்குள்ள failures-ஓட written list எதுவும் வரலைன்னா, test pass ஆனதா கணக்கு."

### Support-உம் changes-உம்

Support period-ஐ சொல்லுங்க, உதாரணமா go-live-க்கு அப்புறம் 30 நாள் fixes, ஒரு fix-க்கும் ஒரு change-க்கும் நடுவுல கோடு போடுங்க:

- **ஒரு fix:** scope சொல்றதை system பண்ணல. Support நேரத்துல free.
- **ஒரு change:** புதுசா அல்லது வேற மாதிரியா இருக்குற எதுவும், உதாரணமா ஒரு புது input format, field அல்லது system, இல்லன்னா billing software upgrade மாதிரி client பக்கத்துல நடக்குற ஒரு change. ஒரு change request-ஆ price பண்ணப்படும்.

Time-ஐயோ price-ஐயோ மாத்தாம project நடுவுல சேர்க்கப்படுற requests தான் **scope creep**. அதை absorb-உம் பண்ணாதீங்க, refuse-உம் பண்ணாதீங்க: ஒவ்வொண்ணையும் ஒரு சின்ன quote-ஓட phase 2 list-ல போடுங்க.

### Effort-ஐ estimate பண்ணுங்க

வேலையை அரை நாள் கணக்குல estimate பண்ணக்கூடிய tasks-ஆ பிரிச்சு கூட்டுங்க. நீங்க பாக்காததுக்கு ஒரு contingency சேருங்க, உதாரணமா 15-ல இருந்து 25%, samples குறைவா இருந்தா இன்னும் அதிகம், அப்புறம் உங்க day rate-ஆல multiply பண்ணுங்க. ஒரு பகுதியை estimate பண்ணவே முடியலைன்னா, அது fixed price-க்கு ready இல்ல: முதல்ல ஒரு சின்ன paid prototype-ஐ sell பண்ணுங்க.

### ஒரு pricing model-ஐயும் payment milestones-ஐயும் choose பண்ணுங்க

| Model | எப்போ best | Surprises-ஐ யார் தாங்குறாங்க |
| --- | --- | --- |
| Fixed price | Scope தெளிவா இருக்கு, samples-ஐ பாத்தாச்சு | நீங்க |
| Time and materials | Scope தெளிவில்ல அல்லது exploratory | Client |
| Monthly retainer | Support-க்கு அப்புறம் maintenance-உம் சின்ன changes-உம் | ரெண்டு பேரும், ஒரு monthly hours cap-க்குள்ள |

முதல் client-க்கு ஒரு sensible default: milestones-ல pay பண்ற fixed price, உதாரணமா sign பண்ணும்போது 40%, acceptance-ல 40%, support முடியும்போது 20%. Advance commitment-ஐ காட்டுது, உங்க ஆரம்ப நாட்களுக்கு pay பண்ணுது; acceptance-ல pay பண்றது client-ஐ பாதுகாக்குது; கடைசி பகுதி support நேரத்துல நீங்க responsive-ஆ இருக்க வைக்குது. Prices-ல GST சேர்ந்திருக்கான்னு சொல்லுங்க.

Monthly running costs-ஐயும் scope-ல போடுங்க (messaging provider, AI usage, hosting), முடிஞ்சவரை client நேரடியா pay பண்ணணும்.

## ஒரு worked example

Sanjay Jain-க்கு சொந்தமான Indore distributor-ல Ritika பண்ண discovery-ல தெரிஞ்சது: 300 retailers-கிட்ட இருந்து ஒரு நாளைக்கு சுமார் 150 orders, மாசத்துக்கு 26 working days. அது WhatsApp-ல typed text-ஆ, voice notes-ஆ, Hindi-லயும் English-லயும் கையால எழுதின lists-ஓட photos-ஆ, அப்பப்போ வேற app-ல இருந்து forward பண்ண ஒரு PDF-ஆ வருது. ரெண்டு staff ஒவ்வொரு order-ஐயும் CSV files-ஐ import பண்ற ஒரு billing software-ல type பண்றாங்க. அவங்களோட ரெண்டு வார baseline: ஒரு order-க்கு சுமார் 3 நிமிஷம், 2% orders தப்பான quantity-ஓட ship ஆகுது.

### அவங்க அனுப்புற scope

**WhatsApp order entry, version 1, 2 December 2026**

- **Process:** ஒரு order message business WhatsApp number-க்கு வரும்போது ஆரம்பிக்குது; அந்த நாளோட confirm ஆன orders billing software import பண்ற ஒரு CSV file-ல வரும்போது முடியுது.
- **In:** Business number-க்கு வர்ற text, photo orders; retailer, products, quantities-ஐ AI extract பண்ணி product list கூட match பண்றது; staff ஒவ்வொரு order-ஐயும் confirm அல்லது correct பண்ற ஒரு review screen; ஒரு daily CSV export.
- **Out:** Voice notes (phase 2), payments-உம் payment reminders-உம், stock checks, retailers-க்கு automatic replies, billing software-ல எந்த change-உம்.
- **Exceptions:** தெரியாத products அல்லது retailers, படிக்க முடியாத photos, forward பண்ண PDFs original message-ஓட review queue-க்கு போகும்.
- **Access (client குடுக்கணும்):** ஒரு provider வழியா WhatsApp Business Platform account, Meta business verification 4 December-க்குள்ள ஆரம்பிச்சு 14 December-க்குள்ள ready; codes-ஓட product, retailer lists, 4 December-க்குள்ள; billing software ஏத்துக்கிட்ட ஒரு CSV file.
- **Data:** Retailer பேர்கள், phone numbers, orders எல்லாம் provider, automation server (India-ல host பண்ணது), AI provider-ஓட API வழியா போகும். Raw messages-உம் photos-உம் 90 நாளுக்கு அப்புறம் delete ஆகும். ரெண்டு order staff-உம் owner-உம் மட்டும் தான் log in பண்ண முடியும். ரெண்டு providers கூடவும் processor terms go-live-க்கு முன்னாடி confirm ஆகும்.
- **Risks:** Verification delay ஆகுது (owner: client; அதுவரைக்கும் ஒரு test number-ல build பண்றது). Photos படிக்க முடியல (owner: Ritika; அதை review-க்கு அனுப்பி, rate-ஐ வாரா வாரம் report பண்றது). Staff check பண்றதை நிறுத்திடுறாங்க (owner: Sanjay Jain; ஒவ்வொரு order-க்கும் ஒரு confirm click வேணும், கூடவே ஒரு weekly spot check).
- **Assumptions:** Client product list-ஐ update-ஆ வச்சிருப்பாங்க; CSV format மாறாது; volumes ஒரு நாளைக்கு 250 orders-க்கு கீழ இருக்கும்.
- **Success:** Entry time ஒரு order-க்கு சுமார் 3 நிமிஷத்துல இருந்து சுமார் 1 நிமிஷம்; தப்பான quantities இன்னைக்கு இருக்குற 2%-ஐ விட அதிகமாகக் கூடாது, target 1%.
- **Acceptance:** October 2026-ல இருந்து client choose பண்ண 200 in-scope text, photo orders. Client-ஓட accountant bill பண்ண invoices-ல இருந்து answer key-ஐ 7 December-க்குள்ள தயார் பண்ணுவாரு. Sign-off: Sanjay Jain, எழுத்துல, test முடிஞ்சு அஞ்சு working days-க்குள்ள.

## பொதுவா பண்ற தப்புகள்

- **Samples இல்லாத scope,** அல்லது நல்லா தெரியணும்னு தேர்ந்தெடுத்த samples-ஓட scope.
- **எது out-னு சொல்லாம இருக்குறது.** எழுதாத exclusions free work-ஆ மாறும்.
- **Access-ஐ கடைசியில யோசிக்குறது.** Meta verification மட்டுமே build-ஓட சில பகுதிகளை விட அதிக நேரம் எடுக்கலாம்.
- **Answer key-உம் named signer-உம் இல்லாத acceptance.** Test ஒரு opinion-ஆ மாறிடும்.
- **Lines-ஐ measure பண்ணி orders-ஐ promise பண்றது.** 90% lines correct-ஆ இருந்தாலும், நிறைய orders-ஐ இன்னும் fix பண்ண வேண்டியிருக்கும்.
- **Data section இல்லாம இருக்குறது.** முதல் privacy கேள்வியே go-live-ஐ நிறுத்திடும்.
- **Fix-க்கும் change-க்கும் நடுவுல கோடு இல்லாதது.** ஒவ்வொரு request-உம் "broken-ஆ இருக்கு"-னு தான் வரும்.
- **Running costs-ஐ மறைக்கிறது,** அல்லது owner படிக்க முடியாத ஒரு scope எழுதுறது.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற project scope பத்தின Atlassian-ஓட guide-ஐயும், user stories பத்தின GOV.UK-ஓட guide-ஐயும் படிங்க.

1. **Samples.** உங்க process map-ல இருக்குற ஒரு idea-க்கு, 20-ல இருந்து 40 real அல்லது realistic inputs-ஐ collect பண்ணி count பண்ணுங்க, ஒவ்வொரு type-க்கும் ஒரு decision-ஓட.
2. **Scope.** பதினொரு பகுதிகளையும் ஒண்ணு ரெண்டு பக்கத்துல சாதாரண வார்த்தைகள்ல எழுதுங்க, Ritika-வோடதை கூட compare பண்ணுங்க.
3. **Acceptance.** அஞ்சு-பகுதி test-ஐ எழுதி, அதை எப்படி run பண்ணுவாங்கன்னு வேற ஒருத்தர்கிட்ட கேளுங்க. அவங்களுக்கு ஒரு கேள்வி இருந்தா, அது இன்னும் முடியல.
4. **Price.** Contingency-ஓட ஒரு effort table-ஐயும் ஒரு running-cost table-ஐயும் build பண்ணுங்க, ஒவ்வொரு price-க்கும் date போட்டு.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க scope-ஐ business owner கிட்ட குடுத்து, எது in, எது out, success எப்படி measure ஆகும், எவ்வளவு cost ஆகும்னு அவங்களை எழுத்துல ஒத்துக்க வைக்க முடியும்.
