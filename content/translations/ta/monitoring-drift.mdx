## இது என்ன

Model monitoring நாலு layers-ஐ பாக்குது:

- **Service health**: model ஓடுதா? Latency, errors, throughput.
- **Data quality-உம் input drift-உம்**: inputs இன்னும் சரியா இருக்கா, training data மாதிரியே இருக்கா? Missing values, புது categories, மாறின distributions.
- **Prediction drift**: scores அல்லது predicted classes-ஓட distribution மாறிடுச்சா?
- **Performance**: உண்மையான outcomes வர்றப்போ, overall-உம் segment வாரியாவும் accuracy முன்ன இருந்த இடத்துலயே இருக்கா?

**Data drift**-னா inputs மாறிடுச்சு; **concept drift**-னா inputs-க்கும் outcomes-க்கும் இடையில இருக்குற தொடர்பு மாறிடுச்சு (அதே features இப்போ வேற மாதிரி predict பண்ணுது, fraud patterns மாறுற மாதிரி).

| Layer | என்ன check ஆகுது | எதை பிடிக்கும் |
|---|---|---|
| Service health | Latency, errors, ஒவ்வொரு நிமிஷமும் | Outages |
| Inputs | Schema, missing rates, baseline-ஓட ஒப்பிட்டு ஒவ்வொரு feature-க்கும் drift, தினமும் | Upstream bugs, புது data வடிவங்கள் |
| Predictions | Partner, city வாரியா approval rate, தினமும் | Behaviour-ல திடீர் மாற்றம் |
| Performance | Labels வர வர, மாசம், segment வாரியா default rate | மெதுவான தேய்மானம், concept drift |

## இது எப்படி work ஆகுது

**Baselines.** Training, validation data-ஓட summary statistics-ஐ சேமிச்சு வைங்க (ஒவ்வொரு feature-க்கும் distributions, score distributions, segment shares). Monitoring, live data-வை இதோட ஒப்பிடும்.

**Data checks.** Schema checks (types, allowed values), missing-value rates, ஒவ்வொரு feature-க்கும் drift scores; population stability index அல்லது statistical distance measures மாதிரி. Distribution ஒரு threshold-ஐ தாண்டி நகர்ந்த features-ஐ flag பண்ணுங்க.

**Prediction checks.** ஒவ்வொரு predicted class-ஓட share, average score, action threshold-ஐ தாண்டுற share. திடீர் தாவல் பெரும்பாலும், எந்த outcome-உம் வர்றதுக்கு முன்னாடியே upstream bug-ஐ காட்டிடும்.

**தாமதமா வர்ற ground truth.** Outcomes பெரும்பாலும் லேட்டா வரும்: loan default 90 நாள் கழிச்சு, churn ஒரு மாசம் கழிச்சு. Labels வரும்போது performance-ஐ track பண்ணுங்க; அதுவரைக்கும் proxies use பண்ணுங்க (complaints, overrides, ஆரம்ப repayment behaviour).

**Segments.** Region, channel, product, customer type வாரியா track பண்ணுங்க; drift பெரும்பாலும் ஒரு segment-ல தான் ஆரம்பிக்கும்.

**Alerts-உம் response-உம்.** எல்லா drift-க்கும் action தேவையில்ல. Severity-ஓட thresholds define பண்ணுங்க: investigate, retrain, roll back, அல்லது fallback-க்கு மாறுங்க. Alerts-ஐ ஒரு owner-க்கும் ஒரு runbook-க்கும் route பண்ணுங்க.

**Retraining policy.** Schedule-ல (மாசாமாசம்), trigger-ல (drift அல்லது performance drop), அல்லது ரெண்டுலயும் retrain பண்ணுங்க. Retrain பண்ண ஒவ்வொரு model-உம் முதல் model மாதிரியே அதே evaluation, promotion checks வழியா போகணும்; இப்போதைய production model-ஓட ஒப்பீடும் சேர்த்து.

**Feedback loops.** Models, தாங்க பின்னாடி கத்துக்குற data-வையே மாத்தலாம்: transactions-ஐ block பண்ற fraud model-னா, அது fraud-ஆ இல்லையான்னு நீங்க ஒருபோதும் பாக்க மாட்டீங்க. சார்பில்லாத labels கிடைக்க ஒரு சின்ன random holdout அல்லது human review sample வச்சுக்கோங்க.

**Severities-ஓட alert thresholds:**

| Signal | Threshold | Severity | Response |
| --- | --- | --- | --- |
| Error rate | 5 நிமிஷத்துக்கு 1%-க்கு மேல | High | On-call-ஐ page பண்ணுங்க; service-ஐ check பண்ணுங்க |
| Feature missing rate | Baseline-ஐ விட double | Medium | Source-ஐ விசாரிங்க |
| Partner வாரியா approval rate | ஒரே நாள்ல 10 points-க்கு மேல மாறுது | High | Inputs-ஐ check பண்ணுங்க; தேவைன்னா fallback model |
| ஒரு முக்கிய feature-ஓட drift score | 3 நாளுக்கு agree பண்ண limit-ஐ தாண்டுது | Medium | Review பண்ணுங்க; retrain பத்தி யோசிங்க |
| Segment வாரியா default rate | ரெண்டு மாசத்துக்கு plan-ஐ விட மேல | Medium | சமீபத்திய data-வோட retrain பண்ணுங்க |

**Drift score-ஐ படிக்குறது.** Population stability index, ஒரு feature-ஓட values training data-லயும் live data-லயும் buckets-ல எப்படி விழுதுன்னு ஒப்பிடும். சின்ன values-னா சின்ன மாற்றம்; பெரிய values-னா உண்மையான shift. இதை ஒரு சுட்டிக்காட்டி மாதிரி எடுத்துக்கோங்க, தீர்ப்பா இல்ல: model கிட்டத்தட்ட use பண்ணாத ஒரு feature-ல shift இருந்தா முக்கியமில்லாம போகலாம்; ஆனா அதோட மிக முக்கியமான feature-ல ஒரு சின்ன shift முக்கியமா இருக்கலாம். Action எடுக்குறதுக்கு முன்னாடி feature importance-ஐயும் drift-ஓட சேர்த்து பாருங்க.

**Runbook எழுதுறது.** ஒவ்வொரு alert-க்கும் எழுதுங்க: யாரு owner, முதல்ல check பண்ண வேண்டிய மூணு விஷயங்கள், fallback-க்கு எப்படி மாறுறது, எப்போ roll back பண்றது. Fallback-ஐ ready-யாவும் test பண்ணியும் வச்சுக்கோங்க; பிரச்சனை தர்ற feature இல்லாத ஒரு எளிய model அல்லது ஒரு rules policy மாதிரி; அப்போ containment நிமிஷங்கள்ல முடியும்.

**Code-ல Population stability index.** Training data-ல ஒரு feature-ஐ buckets-ஆ பிரிச்சு, அதே buckets-ல live data-வை ஒப்பிடுங்க:

```python
import numpy as np

def psi(expected, actual, buckets=10):
    edges = np.unique(np.quantile(expected, np.linspace(0, 1, buckets + 1)))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

def drift_report(train_df, live_df, features, warn=0.1, alert=0.25):
    rows = []
    for f in features:
        value = psi(train_df[f].dropna(), live_df[f].dropna())
        missing_change = live_df[f].isna().mean() - train_df[f].isna().mean()
        level = "alert" if value > alert else "warn" if value > warn else "ok"
        rows.append((f, round(value, 3), f"{missing_change:+.1%}", level))
    return sorted(rows, key=lambda r: -r[1])
```

பொதுவான rules of thumb, PSI 0.1-க்கு கீழ stable, 0.25-க்கு மேல பெரிய shift-ன்னு எடுத்துக்கும்; ஆனா thresholds-ஐ model owner-ஓட agree பண்ணி, கடந்த மாசங்களோட ஒப்பிட்டு check பண்ணுங்க. Evidently மாதிரி libraries charts-ஓட இதே மாதிரி reports தரும்.

**Segment வாரியா prediction rates.** Upstream bugs பெரும்பாலும் முதல்ல ஒரு partner அல்லது region-ல positive predictions-ஓட share தாவுறதா தெரியும்:

```python
def rate_alerts(today, history, min_change=0.10):
    """today/history: dict segment -> approval rate; history holds the 30-day average."""
    return {s: (history[s], r) for s, r in today.items()
            if s in history and abs(r - history[s]) > min_change}
```

**நேர்மையான outcomes-க்கு ஒரு holdout.** Model ஒரு transaction-ஐ block பண்ணா, அது fraud-ஆ இல்லையான்னு ஒருபோதும் தெரியாது. ஒரு சின்ன random share-ஐ (business, risk teams-ஓட agree பண்ணி, பெரும்பாலும் 1%-க்கு ரொம்ப கீழ) model-ஓட முடிவை தாண்டி சாதாரண handling அல்லது human review-க்கு போக விடுங்க, outcome-ஐ record பண்ணுங்க:

```python
import random

def decide(txn, model_score, threshold=0.8, holdout_rate=0.005):
    if random.random() < holdout_rate:
        return {"action": "review", "holdout": True}       # outcome measured without the model's influence
    return {"action": "block" if model_score > threshold else "allow", "holdout": False}
```

உலகம் மாறும்போது model உண்மையில் எப்படி செயல்படுதுன்னு பாக்க, holdout-ல precision, recall-ஐ measure பண்ணுங்க.

**LLM apps-க்கான Drift.** அதே யோசனைகள் inputs-க்கும் (question length, language mix, topics) outputs-க்கும் (refusal rate, answer length, citation rate, judge scores) பொருந்தும். Hindi கேள்விகளோட share கூடுறது அல்லது ஒரு புது topic cluster, retraining இல்லாம புது documents அல்லது prompt மாற்றங்கள் தேவைப்படுற drift ஆ இருக்கலாம்.

## ஒரு worked example

Bengaluru-ல ஒரு BNPL (buy now, pay later) company-ஓட credit model checkout-ல சின்ன loans-ஐ approve பண்ணுது.

Monitoring dashboard-உம் alerts-உம்:

- Service: p95 latency, error rate.
- Inputs: training baseline-ஓட ஒப்பிட்டு 40 features-க்கு தினசரி drift scores; ஒவ்வொரு partner-ஓட payloads-க்கும் schema checks.
- Predictions: partner, city வாரியா approval rate.
- Performance: outcomes வர வர, approval month, segment வாரியா 60-day default rate.

மார்ச்ல, ஒரு பெரிய e-commerce partner-ஓட approval rate ராத்திரியோட ராத்திரியா 61%-ல இருந்து 79%-க்கு தாவுது. அந்த partner-க்கு "device age" feature பூஜ்யத்துக்கு விழுந்துடுச்சுன்னு input drift காட்டுது: அவங்க app update அதை அனுப்புறதை நிறுத்திடுச்சு, model பூஜ்யத்தை "புத்தம் புது device"ன்னு படிச்சுது, அது low-risk signal. Team ரெண்டு மணி நேரத்துல அந்த partner-ஐ அந்த feature இல்லாத fallback model-க்கு மாத்துது, partner தன் payload-ஐ சரி பண்ணுது.

தனியா, நாலு மாசத்துல tier-3 cities-ல first-time borrowers-ஓட defaults மெதுவா ஏறுறது, சமீபத்திய data-வோடவும் முன்னாடி எடுத்த சின்ன loans-ல repayment behaviour-க்கான ஒரு புது feature-ஓடவும் retraining-ஐ trigger பண்ணுது. Retrain பண்ண model promotion checks-ல pass ஆகி, shadow, canary stages வழியா roll out ஆகுது.

Borderline applicants-ல 2% random sample, score எப்படி இருந்தாலும் approve ஆகுது; அதனால model இல்லன்னா reject பண்ணியிருக்கும் applicants பத்தி company தொடர்ந்து கத்துக்குது.

| Event | எப்படி கண்டுபிடிச்சாங்க | Response | நேரம் |
| --- | --- | --- | --- |
| Partner approvals 61%-ல இருந்து 79%-க்கு தாவுச்சு | Approval-rate alert, அப்புறம் input drift | அந்த partner-க்கு fallback model | ரெண்டு மணி நேரம் |
| Tier-3 first-time borrowers அதிகமா default ஆகுறாங்க | நாலு மாசத்துக்கு segment வாரியா performance | புது feature-ஓட retrain, shadow அப்புறம் canary | வாரங்கள் |

## பொதுவா பண்ற தப்புகள்

- **Uptime-ஐ மட்டும் monitor பண்றது.** ஓடிக்கிட்டிருக்குற model-உம் ரொம்ப தப்பா இருக்கலாம்.
- **Baselines இல்லாம இருக்குறது.** Drift-க்கு ஒப்பிட ஏதாவது வேணும்.
- **ஒவ்வொரு சின்ன drift-க்கும் alert பண்றது.** Thresholds, severities வைங்க, இல்லன்னா alerts-ஐ யாரும் கண்டுக்க மாட்டாங்க.
- **பிரச்சனையை கவனிக்க labels-க்காக காத்திருக்கிறது.** Inputs, predictions-ஐ தினமும் பாருங்க.
- **Feedback loops-ஐ கண்டுக்காம விடுறது.** கத்துக்கிறதுக்கு சார்பில்லாத samples வச்சுக்கோங்க.
- **ஒவ்வொரு PSI அசைவுக்கும் alert பண்றது**, இது alerts-ஐ புறக்கணிக்க மக்களை பழக்கிடும்.
- **Holdout இல்லாம இருக்குறது**, அதனால model அனுமதிச்ச cases-க்கு மட்டும் தான் outcomes இருக்கும்.
- **Inputs-ஐ மட்டும் monitor பண்றது**, segment வாரியா prediction rates-ஐ பாக்காம.

## எப்போ lighter monitoring போதும்

- **ஒரு தடவை மட்டும் செய்யுற analysis-க்கு use பண்ற model.**
- **Low-impact recommendations**, மக்களே எப்பவும் முடிவு பண்ற, errors-ஓட விலை குறைவா இருக்குற இடங்கள்.
- **Stable inputs**, கட்டுப்படுத்தப்பட்ட process-ல ஒரு fixed sensor மாதிரி, அங்க error, range checks பெரும்பாலான பிரச்சனைகளை பிடிச்சுடும்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு model version-ஓடவும் baselines-ஐ save பண்ணுங்க.**
- **Drift, segment reports-ஐ தினமும் run பண்ணுங்க**, agree பண்ண thresholds-ஓடவும் owners-ஓடவும்.
- **Random holdout வச்சுக்கோங்க**, முடிவுகள் outcomes-ஐ மறைக்குற இடத்துல, business-ஓட agree பண்ணி.
- **Labels வர வர performance-ஐ track பண்ணுங்க**, segment வாரியா.
- **Runbooks எழுதுங்க**, ஒவ்வொரு alert-க்கும் fallback, rollback steps-ஓட.

## Practice பண்ணுங்க

Evidently-ஓட introduction-ஐயும், Made With ML-ல இருக்குற monitoring lessons-ஐயும், Google-ஓட Rules of ML-ஐயும் படிங்க.

1. ஒரு training set-ல இருந்து baseline statistics-ஐ save பண்ணுங்க, அப்புறம் ஒரு புது batch-ல drift-ஐ simulate பண்ணி (ஒரு feature-ஐ shift பண்ணி, இன்னொண்ணை உடைச்சு), ரெண்டையும் ஒரு drift report-ஆல கண்டுபிடிங்க.
2. Simulated நாட்கள்ல segment வாரியா approval அல்லது positive-prediction rate-க்கு ஒரு சின்ன dashboard செய்யுங்க.
3. ஒரு பக்க monitoring, retraining policy எழுதுங்க: என்ன check ஆகுது, thresholds, யாருக்கு alert போகுது, அவங்க என்ன பண்றாங்க.
4. உங்க baseline மேலயும் simulated batch மேலயும் drift_report-ஐ run பண்ணி, shift பண்ண feature flag ஆகுதுன்னும் stable ஆனவை flag ஆகலன்னும் check பண்ணுங்க.
