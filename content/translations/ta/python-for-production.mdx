## இது என்ன

Script Python-உம் production Python-உம் பார்க்க ஒரே மாதிரி இருக்கும், ஆனா அழுத்தத்துல ரொம்ப வேற மாதிரி நடந்துக்கும். ஒரு script, உங்க laptop-ல, நீங்க பார்த்த data-வுல, ஒரு தடவை ஓடும். Production code ஒரு நாளைக்கு ஆயிரக்கணக்கான தடவை, நீங்க பார்த்தே இல்லாத data-வுல ஓடும்; நீங்க போனதுக்கு அப்புறம் வேற ஆட்கள் அதை மாத்துவாங்க.

நாலு பழக்கங்கள் பெரும்பாலான இடைவெளியை மூடிடும்:

| பழக்கம் | என்ன பண்ணும் | எங்க ரொம்ப முக்கியம் |
| --- | --- | --- |
| **Type hints** | ஒவ்வொரு function-ம் எதை எடுக்கும், எதை return பண்ணும்னு சொல்லும்; அதனால code ஓடுறதுக்கு முன்னாடியே editors, checkers தப்புகளை பிடிக்கும் | நீங்க எழுதுற ஒவ்வொரு function-லயும் |
| **Dataclasses** | Boilerplate இல்லாம, சாதாரண records-க்கு ஒரு தெளிவான வடிவம் தரும் | உங்க சொந்த internal data-வுக்கு |
| **Pydantic models** | வெளியில இருந்து வர்ற data-வை check பண்ணி, தப்பா இருந்தா தெளிவான error-ஓட மறுக்கும் | API requests, files, LLM replies |
| **async and await** | ஒரு process, பல மெதுவான network calls-க்காக ஒரே நேரத்துல காத்திருக்க விடும் | Model APIs-ஐ call பண்ற services |

```flow

API requests -[Pydantic-ஆல validate]-> Type போட்ட, check பண்ண objects

Type போட்ட, check பண்ண objects -> உங்க system | உள்ள dataclasses, ஒவ்வொரு function-லயும் type hints
```

இந்த lesson-ல Bengaluru-ல ஒரு lending startup, loan enquiry emails-ல இருந்து fields-ஐ LLM வச்சு எடுக்குது; அப்புறம் அதுல 200-ஐ வேகமா process பண்ணணும். Lesson முடியும் போது, வெளியில இருந்து வர்ற data-வை சரியா validate பண்ணவும், async எப்போ உதவும்னு தெரிஞ்சுக்கவும் முடியும்.

## இது எப்படி work ஆகுது

### Type hints

```python
def emi(principal: float, annual_rate: float, months: int) -> float:
    ...
```

Python run time-ல hints-ஐ கண்டுக்காது; ஒரு string-ஐ கொடுத்தா அதுவே error raise பண்ணாது. அதோட மதிப்பு tools-ல இருந்து வருது: ஒரு number வர வேண்டிய இடத்துல string கொடுத்தா உங்க editor எச்சரிக்கும், **mypy**, **pyright** மாதிரி type checkers CI-ல ஒரு முழு project-ஐ check பண்ணும். Hints documentation-உம் தான்: `def score(ticket: Ticket) -> float`, ஒரு comment-ஐ விட அடுத்த engineer-க்கு அதிகம் சொல்லும்.

### Dataclasses

```python
from dataclasses import dataclass

@dataclass
class LineItem:
    sku: str
    qty: int
    price: float
```

`@dataclass`, முக்கியமா data-வை வச்சிருக்குற ஒரு class-க்கு constructor, equality, printing-ஐ எழுதிடும். உள்ள என்ன போகுதுன்னு நீங்க control பண்ற, உங்க சொந்த internal records-க்கு இதை use பண்ணுங்க.

### Pydantic: boundary-ல validation

ஒரு **Pydantic** model பார்க்க dataclass மாதிரி இருக்கும், ஆனா **validate** பண்ணும். அதுக்கு ஒரு dictionary அல்லது JSON கொடுத்தா, அது:

- பாதுகாப்பா convert பண்ண முடிஞ்சதை convert பண்ணும், உதாரணம் "42"-ஐ 42-ஆ;
- முடியாததை reject பண்ணும், உதாரணம் ஒரு number-க்கு "five lakh";
- எந்த field, ஏன் fail ஆச்சுன்னு சரியா சொல்லும்.

| `amount_inr: int`-க்கான input | Result |
| --- | --- |
| `500000` | ஏத்துக்கும் |
| `"500000"` | 500000-ஆ convert ஆகும் |
| `"5,00,000"` | Reject (commas), நீங்க ஒரு cleaning step சேர்த்தா தவிர |
| `"five lakh"` | தெளிவான error-ஓட reject |
| இல்லை | Reject, அந்த field-க்கு ஒரு default இருந்தா தவிர |

Data உள்ள வர்ற ஒவ்வொரு boundary-லயும் Pydantic-ஐ use பண்ணுங்க: request bodies, config files, CSV rows, **குறிப்பா LLM output**; அது பெரும்பாலும் கிட்டத்தட்ட சரியா இருக்கும். வாசல்லயே validate பண்ணா, மோசமான data உங்க code-ஓட மீதிக்கு போகவே போகாது; போனா மூணு functions தள்ளி குழப்பமான errors-ஆ வரும்.

### async and await

ஒரு சாதாரண function **block** ஆகும்: ஒரு model reply-க்காக ரெண்டு வினாடி காத்திருக்கும்போது, அந்த process-ல வேற எதுவும் நடக்காது. ஒரு `async def` function reply-ஐ `await` பண்ணி, இடைப்பட்ட நேரத்துல **event loop** வேற வேலையை ஓட்ட விடும்.

```flow
dir: LR
title: வரிசையா, blocking: சுமார் 6 s
Call 1, 2 s -> Call 2, 2 s -> Call 3, 2 s -> 6 s-க்கு அப்புறம் முடிஞ்சுது
```

```flow
dir: LR
title: async-ஓட concurrent: சுமார் 2 s
Start -> Call 1, 2 s
Start -> Call 2, 2 s
Start -> Call 3, 2 s
Call 1, 2 s -> சுமார் 2 s-ல முடிஞ்சுது
Call 2, 2 s -> சுமார் 2 s-ல முடிஞ்சுது
Call 3, 2 s -> சுமார் 2 s-ல முடிஞ்சுது
```

இது network அல்லது disk-ஐ **காத்திருக்குறதுக்கு** மட்டும் தான் உதவும்; images-ஐ resize பண்றது மாதிரி கடுமையான computation-க்கு இல்லை. அதோட சங்கிலியில இருக்குற ஒவ்வொரு library-உம் async-ஐ புரிஞ்சதா இருக்கணும்: `requests`-க்கு பதிலா `httpx`, `time.sleep`-க்கு பதிலா `asyncio.sleep`.

## ஒரு உதாரணம்

Bengaluru-ல ஒரு lending startup, loan enquiry emails-ல இருந்து fields-ஐ LLM வச்சு எடுக்க நினைக்குது. Model JSON-ஐ return பண்ணுது. அது பெரும்பாலும் சரியா இருக்கும், ஆனா சில நேரம் ஒரு field இல்லாம இருக்கும், அல்லது amount ஒரு number-க்கு பதிலா "five lakh"ன்னு இருக்கும்.

**Reply-ஐ validate பண்றது:**

```python
import logging
from pydantic import BaseModel, Field, ValidationError

log = logging.getLogger(__name__)

class Enquiry(BaseModel):
    name: str
    city: str
    amount_inr: int = Field(gt=0, le=10_000_000)
    purpose: str | None = None

def parse(reply: str) -> Enquiry | None:
    try:
        return Enquiry.model_validate_json(reply)
    except ValidationError as e:
        log.warning("bad model reply: %s", e.errors())
        return None
```

`parse('{"name": "Divya", "city": "Pune", "amount_inr": "500000"}')` ஒரு valid `Enquiry`-ஐ return பண்ணும்; amount ஒரு integer-ஆ convert ஆகியிருக்கும். `"amount_inr": "five lakh"` இருக்குற ஒரு reply, அந்த field-ஓட பேரை சொல்ற ஒரு error-ஓட fail ஆகும்; அதனால code குப்பையை store பண்றதுக்கு பதிலா, இன்னும் உறுதியான prompt-ஓட retry பண்ணலாம்.

**200 emails-ஐ process பண்றது.** Model-ஐ ஒண்ணொண்ணா call பண்ணா latency 200 மடங்கு ஆகும்: ஒண்ணுக்கு 2 வினாடின்னா சுமார் 7 நிமிஷம். `httpx.AsyncClient`, `asyncio.gather` வச்சா emails ஒரே நேரத்துல அனுப்பப்படும்; ஒரு **semaphore** ஒரே நேரத்துல எத்தனை in flight-ல இருக்கலாம்னு limit பண்ணும், அதனால startup provider-ஓட rate limit-க்கு கீழயே இருக்கும்:

```python
import asyncio
import httpx

sem = asyncio.Semaphore(10)

async def extract(client, email):
    async with sem:
        reply = await call_model(client, email)   # your async model call
        return parse(reply)

async def main(emails):
    async with httpx.AsyncClient(timeout=30) as client:
        return await asyncio.gather(*(extract(client, e) for e in emails))

results = asyncio.run(main(emails))
```

| Approach | 200 emails-க்கு நேரம் | Rate-limit risk |
| --- | --- | --- |
| ஒண்ணொண்ணா | சுமார் 7 நிமிஷம் | இல்லை |
| 200-ஐயும் ஒரே நேரத்துல | வினாடிகள், அப்புறம் நிறைய 429 errors | அதிகம் |
| 10 limit-ஓட async | சுமார் 40 வினாடி | குறைவு |

## பொதுவா பண்ற தப்புகள்

- **Hints-ஐ checks-ஆ நினைக்கிறது.** `amount: int`, run time-ல ஒரு string-ஐ தடுக்காது. வெளியில இருந்து வர்ற data-வை Pydantic-ஆல validate பண்ணுங்க; உங்க சொந்த code-க்கு hints use பண்ணுங்க.
- **ரொம்ப தாமதமா validate பண்றது.** Boundary-ஐ தாண்டி நழுவுற மோசமான data, மூணு functions தள்ளி ஒரு குழப்பமான error-ஆ தெரியும். உள்ள வரும்போதே validate பண்ணுங்க.
- **async code-க்குள்ள block பண்றது.** `async def`-க்குள்ள `requests.get` அல்லது `time.sleep`-ஐ call பண்ணா, முழு event loop-உம் உறைஞ்சிடும்.
- **வரம்பில்லாத concurrency.** 5,000 requests-ஐ ஒரே நேரத்துல அனுப்பினா rate limits trip ஆகி, உங்களை block பண்ணலாம். Cap பண்ணுங்க.
- **எல்லா இடத்துலயும் dictionaries.** Functions-க்கு நடுவுல raw dicts அனுப்புறது `"ammount"` மாதிரி typos-ஐ மறைச்சுடும். உங்க data-வுக்கு ஒரு model கொடுங்க.
- **CPU-heavy வேலைக்கு async use பண்றது.** இது image processing அல்லது model training-ஐ வேகப்படுத்தாது.
