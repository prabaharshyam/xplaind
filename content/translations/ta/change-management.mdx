## இது என்ன

**Change management**-னா மக்கள் பழைய வேலை முறையில இருந்து புது முறைக்கு மாற உதவுற வேலை. AI systems-க்கு இதுல இவை வரும்:

- மாற்றம் ஏன் நடக்குது, ஒவ்வொருத்தருக்கும் அதோட அர்த்தம் என்னன்னு விளக்குறது;
- design-லயும் testing-லயும் users-ஐ involve பண்றது;
- அவங்களோட சொந்த உண்மையான cases-ஐ வச்சு training;
- பழக்கங்கள் உருவாகுற முதல் வாரங்கள்ல support;
- adoption-ஐ அளந்து, மக்களை எது தடுக்குதுன்னு பார்த்து நடவடிக்கை எடுக்குறது.

ADKAR-ங்குற ஒரு பிரபலமான model சொல்றது: ஒவ்வொருத்தருக்கும் ஏன்னு **awareness**, பங்கெடுக்க **desire**, எப்படின்னு **knowledge**, நடைமுறையில செய்ய **ability**, அது நிலைக்க **reinforcement** வேணும். Adoption நின்னுபோச்சுன்னா, இதுல எது விடுபட்டிருக்குன்னு கண்டுபிடிங்க.

| ADKAR | ஒவ்வொருத்தருக்கும் என்ன வேணும் | நீங்க என்ன பண்றீங்க |
|---|---|---|
| **A**wareness | ஏன் இந்த மாற்றம்? | Leaders காரணத்தையும் என்ன மாறுதுன்னும் விளக்குறாங்க |
| **D**esire | எனக்கு இது வேணுமா? | வேலை, பழி, கூடுதல் வேலை பத்தி நேர்மையான பதில்கள் |
| **K**nowledge | இது எப்படி வேலை செய்யுது? | அவங்க சொந்த cases-ல 45-நிமிஷ training |
| **A**bility | தினமும் என்னால செய்ய முடியுமா? | Champions, ஒரு support channel, ஆரம்ப எரிச்சல்களை சரி பண்றது |
| **R**einforcement | இது நிலைக்குமா? | Results-ஐ share பண்றது, processes-ஐயும் targets-ஐயும் update பண்றது |

## இது எப்படி work ஆகுது

**கவலைகளுக்கு பேர் வைங்க.** வழக்கமானவை: "இது என்னை replace பண்ணுமா?", "AI தப்பா இருக்கும்போது என் மேல பழி வருமா?", "இதோட output-ஐ check பண்றது கூடுதல் வேலையா?", "என் வேலை கண்காணிக்கப்படுதா?" Leaders முன்னாடி இருக்கும்போது இவற்றுக்கு நேர்மையா பதில் சொல்லுங்க. Roles மாறப்போகுதுன்னா, எப்படின்னு சொல்லுங்க.

**Accountability-ஐ தெளிவாக்குங்க.** AI உதவியோட எடுத்த ஒரு முடிவு தப்பா இருந்தா யார் பொறுப்பு? பெரும்பாலும் முன்னாடி மாதிரியே, அதை review பண்ணி approve பண்ணவங்க தான். இதை எழுத்துல வைங்க; அவங்க சரியா check பண்ண வேண்டியது review step-ல கிடைக்குதான்னு பார்த்துக்கோங்க.

**Champions-ஐ involve பண்ணுங்க.** ஒவ்வொரு team-ல இருந்தும் மதிக்கப்படுற users-ஐ தேர்ந்தெடுத்து, ஆரம்ப versions-ஐ test பண்ணவும் design-ஐ வடிவமைக்கவும் வைங்க. அவங்க feedback system-ஐ மேம்படுத்தும்; அவங்க ஆதரவு எந்த அறிவிப்பையும் விட நல்லா சக ஊழியர்களை சம்மதிக்க வைக்கும்.

**உண்மையான வேலையில training.** அவங்க சொந்த queue-ல இருந்து எடுத்த cases-ஓட சின்ன sessions (45 நிமிஷம்): எப்படி use பண்றது, எதுல நல்லா இருக்கு, எங்க தோத்துப்போகும், எப்படி check பண்றது, எப்படி feedback குடுக்குறது. System தப்பா இருக்குற examples-ஐயும் சேருங்க.

**முதல் வாரங்கள்ல support.** கேள்விகளுக்கு கண்ணுக்குத் தெரியுற ஒரு channel, ஒவ்வொரு team-லயும் ஒரு champion, ஆரம்ப எரிச்சல்களை உடனே சரி பண்றது. கவனிக்கலன்னா ஆரம்ப விரக்திகள் நிரந்தர அபிப்ராயங்களா மாறிடும்.

**அளந்து நடவடிக்கை எடுங்க.** ஒவ்வொரு நபருக்கும் ஒவ்வொரு team-க்கும் usage, feedback, use பண்ணாததுக்கான காரணங்களை track பண்ணுங்க. குறைவா use பண்றவங்ககிட்ட பேசுங்க; அவங்க காரணங்கள் பெரும்பாலும் சரி பண்ணக்கூடியவை (மெதுவான ஒரு step, விடுபட்ட ஒரு field, இதை பத்தி ஒருபோதும் சொல்லாத ஒரு manager).

**Reinforce பண்ணுங்க.** Results-ஐ share பண்ணுங்க (மிச்சமான நேரம், குறைஞ்ச rework), teams-க்கு credit குடுங்க, processes-ஐயும் targets-ஐயும் update பண்ணுங்க; அப்போ புது முறையே normal முறையா ஆகும்.

**கவலைகளும் நேர்மையான பதில்களும்:**

| கவலை | உதவுற பதில் |
| --- | --- |
| "இது என்னை replace பண்ணுமா?" | Roles-ல என்ன மாறுது, ஏதாவது மாறுதுன்னா, என்ன அப்படியே இருக்குதுன்னு தெளிவா சொல்லுங்க; project team மட்டும் இல்ல, leaders பதில் சொல்லணும் |
| "இது தப்பா இருக்கும்போது என் மேல பழி வருமா?" | எழுத்துல accountability: flag பண்ணப்பட்ட, முக்கியமான fields-ஓட review officers-ஓட பொறுப்பு; tool sources-ஐ பக்கத்துல பக்கத்துல காட்டும் |
| "இது கூடுதல் வேலையா?" | ஒத்த team-ல இருக்குற சக ஊழியர்கள்கிட்ட இருந்து, முன்னாடியும் பின்னாடியும் ஒரு file-க்கு ஆன நேரத்தை அளந்து காட்டுங்க |
| "என்னை monitor பண்றாங்களா?" | என்ன அளக்குறோம், ஏன், யார் பார்க்குறாங்கன்னு சொல்லுங்க; adoption-ஐ team வாரியா அளங்க, தனி நபர்களை rank பண்ண அல்ல |

**ஒரு adoption dashboard.** ஒவ்வொரு team-க்கும் ஒவ்வொரு வாரத்துக்கும் காட்டுங்க: தகுதியான வேலையில tool வச்சு செஞ்சதோட பங்கு, ஒரு item-க்கு median நேரம், rework rate, முக்கிய feedback காரணங்கள். எடுத்த நடவடிக்கைகளுக்கு ஒரு சின்ன note column-ஐ சேருங்க. ஒரு team ஒத்துக்கிட்ட அளவுக்கு (உதாரணமா 50%) கீழ போனா, அந்த வாரமே யாராவது போய் பார்க்கணும். Dashboard எங்க உதவி தேவைன்னு கண்டுபிடிக்க தான், teams-ஐ குத்தம் சொல்ல இல்ல.

**நிலைக்குற training.** Team-ஓட சொந்த queue-ல இருந்து cases எடுங்க, system தப்பா இருக்குற ஒண்ணையும் சேருங்க, demo-வை பார்க்குறதுக்கு பதிலா session-லயே மக்களை try பண்ண விடுங்க. கேள்விகளை எங்க கேக்கலாம், அவங்க champion யார்னு சொல்லி முடிங்க. தவறவிட்டவங்களுக்கு session-ஐ திரும்ப நடத்துங்க; ஏன்னா training-ஐ skip பண்றவங்க தான் பின்னாடி tool வேலை செய்யலன்னு சொல்றவங்களா இருப்பாங்க.

## ஒரு worked example

Chennai lender-ல pilot ஆரம்பிச்சு மூணு வாரம் கழிச்சு, Anna Nagar branch-ல adoption 92%, Tambaram-ல 41%.

நீங்க Tambaram போய் officers-ஓட பேசுறீங்க. மூணு காரணங்கள் வருது:

- Branch manager, எந்த figure தப்பா இருந்தாலும் அது "AI-ஆ இருந்தாலும் இல்லன்னாலும் உங்க பொறுப்பு"ன்னு சொல்லியிருக்காரு; அதனால பலர் எல்லாத்தையும் திரும்ப retype பண்றது தான் பாதுகாப்புன்னு முடிவு பண்ணிட்டாங்க.
- ரெண்டு officers training-ஐ தவறவிட்டாங்க.
- Draft summary-ல இருந்த English headings, அவங்க regional credit head விரும்புற format-ஐ விட வித்தியாசமா இருந்துச்சு.

நடவடிக்கைகள்: flag பண்ணப்பட்ட, முக்கியமான fields-ஐ review பண்றது officers-ஓட பொறுப்புன்னும், side-by-side view தான் check பண்ண அங்கீகரிக்கப்பட்ட வழின்னும் head of operations ஒரு note அனுப்புறாரு; officers fields-ஐ எப்படி verify பண்றாங்கன்னு காட்டுற ஒரு session-ல branch manager சேர்றாரு. ஒரு repeat training நடக்குது. Summary template-ல ஒரு regional variant சேருது. ரெண்டு வாரத்துல Tambaram 85%-ஐ எட்டுது, அதோட median file நேரம் 37-ல இருந்து 25 நிமிஷமா குறையுது.

| Branch அளவீடு | Visit-க்கு முன்னாடி | ரெண்டு வாரம் கழிச்சு |
| --- | --- | --- |
| Tambaram-ல adoption | 41% | 85% |
| Tambaram-ல median file நேரம் | 37 நிமிஷம் | 25 நிமிஷம் |
| சரி பண்ணப்பட்ட காரணங்கள் | பழி பத்தின message, தவறவிட்ட training, template பொருந்தாதது | தெளிவுபடுத்துன note, repeat training, regional template |

## பொதுவா பண்ற தப்புகள்

- **Email-ல launch பண்றது.** ஒரு அறிவிப்பு adoption இல்ல.
- **வேலை பத்தின கேள்வியை தவிர்க்குறது.** அமைதி வதந்திகளை வளர்க்கும். என்ன மாறுதுன்னு நேர்மையா சொல்லுங்க.
- **பொதுவான demos-ல training.** மக்களோட சொந்த cases-ஐ, failures உட்பட, use பண்ணுங்க.
- **தெளிவில்லாத accountability.** பழி வருமோன்னு பயந்தா மக்கள் tool-ஐ நம்பவும் மாட்டாங்க, use பண்ணவும் மாட்டாங்க.
- **குறைவா ஏத்துக்குறவங்களை போய் பார்க்காம இருக்குறது.** காரணங்கள் அந்த இடத்துக்கே உரியவை, பெரும்பாலும் சுலபமா சரி பண்ணலாம்.

## Practice பண்ணுங்க

Prosci-யோட ADKAR model விளக்கத்தை படிங்க.

1. உங்க use case-க்கு, மூணு குழுக்களோட (front-line staff, அவங்க managers, risk அல்லது compliance) சாத்தியமான கவலைகளை பட்டியல் போட்டு, ஒவ்வொண்ணையும் எப்படி address பண்ணுவீங்கன்னு எழுதுங்க.
2. உண்மையான cases-ஐ வச்சு, system தப்பா இருக்குற ஒண்ணு உட்பட, 45-நிமிஷ training session-ஐ plan பண்ணுங்க.
3. ஒரு adoption dashboard-ஐ design பண்ணுங்க: ஒவ்வொரு team-க்கும் என்ன அளப்பீங்க, ஒரு team 50%-க்கு கீழ போனா என்ன பண்ணுவீங்க.

**இதை நீங்க முடிச்சுட்டீங்கன்னு எப்போ சொல்லலாம்:** நின்னுபோன ஒரு team-க்கு ADKAR-ல எந்த element விடுபட்டிருக்குன்னும், அதை சரி பண்ண இந்த வாரம் என்ன பண்ணுவீங்கன்னும் உங்களால explain பண்ண முடியும்போது.
