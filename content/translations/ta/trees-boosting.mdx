## இது என்ன

**Decision tree** features பத்தி வரிசையா கேள்விகள் கேட்டு predict பண்ணும்: "EMI-to-income ratio 0.45-க்கு மேல இருக்கா? ஆமான்னா, applicant கடந்த வருஷத்துல ஒரு payment miss பண்ணியிருக்காங்களா?" ஒவ்வொரு பதிலும் ஒரு branch வழியா போய், ஒரு leaf-ல prediction கொடுக்கும். இந்த கேள்விகளை trees data-ல இருந்து கத்துக்கும்.

ஒரே tree எளிதா overfit ஆகிடும். இதை ரெண்டு ensemble methods சரி பண்ணும்:

- **Random forest**: நிறைய trees; ஒவ்வொண்ணும் rows, features-ஓட random sample-ல train ஆகும், predictions-ஓட average எடுப்பாங்க. நம்பகமானது, உடைக்குறது கஷ்டம்.
- **Gradient boosting**: trees ஒண்ணுக்கு அப்புறம் ஒண்ணா build ஆகும்; ஒவ்வொரு புது tree-உம் அதுவரைக்கும் இருக்குற ensemble-ஓட தப்புகளை சரி பண்ணும். XGBoost, LightGBM, CatBoost popular implementations. Tabular data-ல பொதுவா இதுதான் அதிக accuracy கொடுக்கும்.

```flow
EMI / income above 0.45? -[ஆமா]-> Missed a payment in the last 12 months?
EMI / income above 0.45? -[இல்ல]-> Credit history under 2 years?
Missed a payment in the last 12 months? -[ஆமா]-> Risk 0.41
Missed a payment in the last 12 months? -[இல்ல]-> Risk 0.18
Credit history under 2 years? -[ஆமா]-> Risk 0.12
Credit history under 2 years? -[இல்ல]-> Risk 0.03
```

Boosting இது மாதிரி நிறைய trees-ஐ சேர்க்கும்: tree 1, அதோட tree 2-ல இருந்து ஒரு சின்ன correction, இப்படியே tree 640 வரைக்கும்.

இந்த lesson-ல Gurugram-ல இருக்குற ஒரு digital lender, personal loans-ல 90-day defaults-ஐ predict பண்றதை follow பண்றோம்.

## இது எப்படி work ஆகுது

**Business data-க்கு trees ஏன் பொருந்துது.** கலந்த feature types-ஐ handle பண்ணும், feature scaling தேவையில்ல, non-linear effects, interactions-ஐ தானா பிடிக்கும் ("self-employed applicants-க்கு அதிக EMI ratio இன்னும் அதிகமா முக்கியம்"), missing values-ஐயும் சமாளிக்கும் (பெரும்பாலான boosting libraries அதை natively handle பண்ணும்).

**Boosting-க்கான முக்கிய settings.**

- *Trees எண்ணிக்கை* மற்றும் *learning rate*: நிறைய சின்ன steps (குறைஞ்ச learning rate, அதிக trees) பொதுவா நல்லா generalise ஆகும்; validation set-ல early stopping use பண்ணா, validation error குறையுறது நின்னதும் trees சேர்க்குறது நிக்கும்.
- *Tree depth*: ஆழம் குறைவான trees (depth 3-ல இருந்து 8) complexity-ஐ கட்டுப்படுத்தும்.
- ஒவ்வொரு tree-க்கும் rows, columns-ஐ *subsampling* பண்றது: randomness சேர்த்து overfitting-ஐ குறைக்கும்.
- *ஒரு leaf-க்கு minimum samples*, regularisation terms: model சின்ன சின்ன groups-ஐ fit பண்றதை தடுக்கும்.

**Categorical features.** குறைவான categories-க்கு one-hot encoding work ஆகும்; நிறைய இருந்தா (city, product), leakage வராம கவனமா target encoding use பண்ணுங்க, இல்லன்னா categories-ஐ நேரா handle பண்ற library use பண்ணுங்க.

**Predictions-ஐ explain பண்றது.** Feature importance, model மொத்தமா எந்த features-ஐ நம்புச்சுன்னு காட்டும்; ஆனா correlated features இருந்தா தப்பா வழிநடத்தலாம். SHAP values individual predictions-ஐ explain பண்ணும்: இந்த applicant-ஓட risk-ஐ ஒவ்வொரு feature-உம் எவ்வளவு மேலே அல்லது கீழே தள்ளுச்சு. Regulated decisions-க்கு இப்படிப்பட்ட explanations பெரும்பாலும் வேணும்.

**Limits.** Trees தான் பார்த்த target values-க்கு வெளியே extrapolate பண்ண முடியாது; raw images, audio, text-க்கும் இது சரியான tool இல்ல, அங்க neural networks தான் ஜெயிக்கும்.

**Boosting-ஐ tune பண்றது, வரிசையா:**

| Setting | எதுல ஆரம்பிக்கணும் | Effect |
| --- | --- | --- |
| Learning rate | 0.03-ல இருந்து 0.1 | குறைஞ்சா மெதுவா இருக்கும், ஆனா பொதுவா நல்லா generalise ஆகும் |
| Trees எண்ணிக்கை | நிறைய, early stopping-ஓட | Early stopping சரியான எண்ணிக்கையை தானே தேர்ந்தெடுக்கும் |
| Max depth | 4-ல இருந்து 8 | ஆழமான trees அதிக interactions-ஐ பிடிக்கும், அதிகமா overfit ஆகும் |
| Row, column subsampling | 0.7-ல இருந்து 0.9 | Randomness overfitting-ஐ குறைக்கும் |
| ஒரு leaf-க்கு minimum samples | 20-ல இருந்து 100 | Model சின்ன groups-ஐ fit பண்றதை தடுக்கும் |

நேரத்தை வச்சு split பண்ண validation set-ல tune பண்ணுங்க, அப்புறம் ஒரு பிந்தைய test period-ல ஒரே ஒரு தடவை confirm பண்ணுங்க. Training, validation scores-க்கு நடுவுல இருக்குற gap வளர்ந்துக்கிட்டே போனா, அதுதான் overfitting-ஓட தெளிவான அறிகுறி.

**ஒரே split-ல மூணு models, code-ல.**

```python
import numpy as np
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.tree import DecisionTreeClassifier
from sklearn.ensemble import RandomForestClassifier, HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

X, y = make_classification(n_samples=12_000, n_features=20, n_informative=10, flip_y=0.03, random_state=4)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=4)

models = {
    "single tree": DecisionTreeClassifier(max_depth=6, random_state=4),
    "random forest": RandomForestClassifier(n_estimators=300, min_samples_leaf=5, n_jobs=-1, random_state=4),
    "boosting": HistGradientBoostingClassifier(learning_rate=0.05, max_iter=2000, max_depth=6,
                                               early_stopping=True, validation_fraction=0.15,
                                               n_iter_no_change=30, random_state=4),
}
for name, m in models.items():
    m.fit(X_tr, y_tr)
    tr = roc_auc_score(y_tr, m.predict_proba(X_tr)[:, 1])
    te = roc_auc_score(y_te, m.predict_proba(X_te)[:, 1])
    print(f"{name:<14} train {tr:.3f}  test {te:.3f}")
print("trees used by boosting:", models["boosting"].n_iter_)
```

Early stopping, 2,000 வரைக்கும் இருக்குற எண்ணிக்கையில இருந்து trees எண்ணிக்கையை தேர்ந்தெடுத்துச்சு. Train, test scores-க்கு நடுவுல இருக்குற gap, overfitting-ஐ ஒரே பார்வையில காட்டும்.

**Real use-ஐ பிரதிபலிக்கிற importance.**

```python
from sklearn.inspection import permutation_importance

r = permutation_importance(models["boosting"], X_te, y_te, scoring="roc_auc", n_repeats=5, random_state=4)
top = np.argsort(-r.importances_mean)[:5]
for i in top:
    print(f"feature {i}: drop in AUC {r.importances_mean[i]:.3f} ± {r.importances_std[i]:.3f}")
```

Correlated features importance-ஐ பகிர்ந்துக்கும்; அதனால ஒரு feature, அதோட twin signal-ஐ தாங்குறதால மட்டுமே முக்கியமில்லாத மாதிரி தெரியலாம். ரெண்டையும் சேர்த்து drop பண்ணி check பண்ணுங்க.

**Common sense-க்கு பொருந்துற constraints.** EMI-to-income ratio ஏறும்போது risk ஒருபோதும் குறையக்கூடாதுன்னா, அதை model-கிட்ட சொல்லுங்க. `HistGradientBoostingClassifier(monotonic_cst=[...])` ஒவ்வொரு feature-க்கும் 1, -1 அல்லது 0 எடுக்கும்; இது credit committees-கிட்ட model-ஐ defend பண்ண ஈஸியா இருக்கும், புது data-ல பெரும்பாலும் இன்னும் robust-ஆவும் இருக்கும்.

**Native categorical support.** pandas categorical columns-ஓட `categorical_features="from_dtype"` கொடுத்தா, boosting model one-hot encoding இல்லாம categories-ல நேரா split பண்ணும். LightGBM, XGBoost, CatBoost-உம் இதையே இன்னும் அதிக tuning options-ஓட தரும்; நிறைய categories இருக்குற data-ல CatBoost-ஓட defaults வலுவானதா பெயர் வாங்கியிருக்கு.

**கொஞ்சம், கவனமா tune பண்ணுங்க.** Learning rate, depth, ஒரு leaf-க்கு minimum samples இவற்றுல ஒரு சின்ன search, time-based validation set-ல score பண்ணி, பெரும்பாலான gain-ஐ பிடிச்சுடும். பெரிய searches validation set-ஏ overfit பண்ணிடும்.

## ஒரு worked example

Gurugram-ல ஒரு digital lender, 120 features-ல இருந்து personal loans-ஓட 90-day default-ஐ predict பண்றாங்க: bureau data, bank-statement summaries, application details, app usage.

- Logistic regression baseline: ROC AUC 0.71.
- Random forest: 0.75.
- Early stopping, depth 6, learning rate 0.03, row, column subsampling-ஓட LightGBM: 0.79; இது training-ஐ விட பிந்தைய quarter-ஓட loans-ல test பண்ணது.

Explanation: SHAP காட்டுறது: முக்கிய drivers bank statements-ல bounce ஆன EMIs, EMI-to-income ratio, credit history நீளம். Reject ஆன ஒவ்வொரு applicant-க்கும், top மூணு காரணங்கள் rejection letter-க்கான எளிய மொழி messages-ஆ map ஆகும்.

Development-ல ஒரு warning sign: "number of collection calls"ங்குற feature-க்கு ரொம்ப அதிக importance இருந்துச்சு. Loans bad ஆனதுக்கு அப்புறம் தான் அது record ஆச்சு, அதனால outcome-ஐ leak பண்ணுச்சு. அதை remove பண்ணதும் validation AUC 0.86-ல இருந்து உண்மையான 0.79-க்கு வந்துச்சு.

| Model | Validation ROC AUC (பிந்தைய quarter) |
| --- | --- |
| Logistic regression baseline | 0.71 |
| Random forest | 0.75 |
| LightGBM, tuned, early stopping | 0.79 |
| Leaky collection-calls feature-ஓட LightGBM | 0.86 (உண்மையில்ல) |

**Model-ல இருந்து rejection letter வரைக்கும்.** Lending-ல reject ஆன applicant-கிட்ட முக்கிய காரணங்களை சொல்லணும்; RBI-ஓட fair practices rules, lenders அதை எழுத்துல கொடுக்கணும்னு சொல்லுது. ஒவ்வொரு rejection-க்கும், risk-ஐ மேலே தள்ளுற SHAP values அதிகமா இருக்குற மூணு features-ஐ team எடுத்து, compliance team-ஓட ஒத்துக்கிட்ட எளிய வாக்கியத்துல map பண்ணும்: "கடந்த ஆறு மாசத்துல பல EMI payments bounce ஆயிருக்கு", "உங்க existing EMIs உங்க வருமானத்துல பெரிய பங்கு", "உங்க credit history ரெண்டு வருஷத்துக்கு குறைவு". Engineers இந்த வாக்கியங்களை அப்பப்ப எழுத மாட்டாங்க; review பண்ண list-ல இருந்து தான் வரும், அதனால wording consistent-ஆ, accurate-ஆ, fair-ஆ இருக்கும். அதே SHAP values, model தான் சாராம இருக்க வேண்டிய feature-ஐ (உதாரணமா location-க்கான proxy) சார்ந்திருக்கும்போது analysts-ஐ கண்டுபிடிக்கவும் உதவும்.

## பொதுவா பண்ற தப்புகள்

- **Early stopping இல்லாம ஆழமான trees.** Boosting சீக்கிரமே overfit ஆகும்.
- **Feature importance-ஐ கண்மூடித்தனமா நம்புறது.** ஒரு feature ரொம்ப நல்லா தெரிஞ்சா leakage இருக்கான்னு check பண்ணுங்க.
- **நேரம் வரிசையா இருக்குற data-ல random splits.** பிந்தைய period-ல validate பண்ணுங்க.
- **நூற்றுக்கணக்கான categories-ஐ one-hot encode பண்றது.** Category-aware methods use பண்ணுங்க.
- **Regulated uses-ல explanations-ஐ தவிர்க்குறது.** Lending, insurance decisions-க்கு காரணங்கள் வேணும்.

- **வேற வேற test sets-ல models-ஐ compare பண்றது.** ஒவ்வொரு candidate-ஐயும் ஒரே பிந்தைய-period data-ல evaluate பண்ணுங்க, இல்லன்னா comparison-க்கு அர்த்தமே இல்ல.
- **Early stopping இல்லாதது**, அதனால trees எண்ணிக்கை ஒரு guess தான்.
- **Features correlated-ஆ இருக்கும்போது built-in importance-ஐ உண்மைன்னு படிக்கிறது.**
- **Validation set-ஏ overfit பண்ற பெரிய hyperparameter searches.**

## Trees சரியான tool இல்லாத நேரங்கள்

- **Images, audio, free text**, அங்க neural networks, pretrained models தான் ஜெயிக்கும்.
- **Training range-க்கு ரொம்ப வெளியே இருக்குற predictions**, trees அதுக்கு extrapolate பண்ண முடியாது.
- **முழுசா transparent formula தேவைப்படும்போது**: logistic regression அல்லது scorecard approve ஆகுறது ஈஸியா இருக்கலாம்.
- **ரொம்ப சின்ன datasets**, அங்க ஒரு simple linear model பெரும்பாலும் நல்லா generalise ஆகும்.

## Demo-ல இருந்து production-க்கு

- **Early stopping use பண்ணுங்க**, தேர்ந்தெடுத்த trees எண்ணிக்கையை record பண்ணுங்க.
- **பிந்தைய time period-ல validate பண்ணுங்க**, train-test gap-ஐ கவனிங்க.
- **Business rule தெளிவா இருக்குற இடத்துல monotonic constraints சேருங்க.**
- **ஒவ்வொரு model version-ஓடவும் permutation importance-ஐ store பண்ணுங்க**, versions-க்கு நடுவுல compare பண்ணுங்க.
- **Customers அல்லது regulators கேக்கக்கூடிய individual decisions-க்கு explanations-ஐ வச்சுக்கோங்க.**
