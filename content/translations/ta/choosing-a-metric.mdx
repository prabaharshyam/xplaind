## இது என்ன

**Evaluation metric** ஒரு model-ஓட predictions-ஐ, compare பண்ணக்கூடிய ஒரு number-ஆ மாத்துது. வேற வேற metrics வேற வேற behaviour-ஐ reward பண்ணும், அதனால use-ல எது முக்கியமோ அதை வச்சு தான் தேர்ந்தெடுக்கணும்.

| | Predicted positive | Predicted negative |
|---|---|---|
| **உண்மையிலேயே positive** | True positive (பிடிச்சது) | False negative (miss ஆனது) |
| **உண்மையிலேயே negative** | False positive (false alarm) | True negative (சரியா fine) |

```flow
dir: LR
title: Precision-ம் recall-உம் எங்க இருந்து வருது
எல்லா real positives -> பிடிச்சது: true positives
எல்லா real positives -> Miss ஆனது: false negatives
கிளப்பின ஒவ்வொரு alarm-உம் -> சரி: true positives
கிளப்பின ஒவ்வொரு alarm-உம் -> தப்பு: false positives
```

**Recall** = TP / (TP + FN): உண்மையான positives-ல எத்தனையை பிடிச்சீங்க. **Precision** = TP / (TP + FP): flag பண்ணதுல எத்தனை சரி.

இந்த lesson-ல Mumbai-ல ஒரு bank-ல இருக்குற மூணு teams-ஐ follow பண்ணப் போறோம்; ஒவ்வொண்ணும் வேற problem-க்கு வேற metric-ஐ தேர்ந்தெடுக்குது.

## இது எப்படி work ஆகுது

**Classification.**

- *Accuracy*: சரியானவற்றோட share. Classes balanced-ஆ இருந்தா fine; rare events-ல ஏமாத்தும்.
- *Precision*: predicted positives-ல எத்தனை சரி. False alarms costly-ஆ இருந்தா (genuine payments-ஐ block பண்றது) முக்கியம்.
- *Recall*: actual positives-ல எத்தனையை பிடிச்சது. Misses costly-ஆ இருந்தா (missed fraud, missed disease) முக்கியம்.
- *F1*: ஒரு threshold-ல precision-க்கும் recall-க்கும் ஒரு balance.
- *ROC AUC*: எல்லா thresholds-லயும், model positives-ஐ negatives-க்கு மேல எவ்வளவு நல்லா rank பண்ணுதுங்கிறது; class balance-ஐ பொறுத்து மாறாது, அதனால rare classes-ல மோசமான performance-ஐ மறைச்சிடலாம்.
- *PR AUC* (average precision): positive class-ல focus பண்ணும்; rare events-க்கு better.
- *Log loss*, calibration: probabilities நம்பக்கூடியதான்னு.

**Regression.**

- *MAE*: original units-ல average absolute error; outliers-ஆல குறைவா பாதிக்கப்படும், explain பண்றதும் எளிது.
- *RMSE*: பெரிய errors-ஐ அதிகமா punish பண்ணும்; பெரிய misses ரொம்ப மோசம்னா use பண்ணுங்க.
- *MAPE*: percentage error; புரிஞ்சுக்க எளிது, ஆனா zero பக்கத்துல இருக்கும் values-ல break ஆகும், சின்ன actuals-ஐ அளவுக்கு மீறி punish பண்ணும்.
- *Quantile அல்லது pinball loss*: ranges-ஐ predict பண்ணும்போது (உதாரணம்: promises-க்கு delivery time-ஓட 90th percentile).

**Ranking and recommendation.** Precision at k, recall at k, NDCG: சரியான items மேல பக்கம் வந்துச்சா?

**Cost-weighted metrics.** Outcomes-க்கு பணத்தை போடுங்க: ஒரு false positive-ஓட cost, ஒரு false negative-ஓட cost, ஒரு true positive-ஓட value. Expected value-வை maximise பண்ற model-ஐயும் threshold-ஐயும் தேர்ந்தெடுங்க. Business owners-க்கு இது பெரும்பாலும் ரொம்ப தெளிவான metric.

**Offline metric versus business KPI.** Offline metric ஒரு proxy தான். அதை improve பண்ணா, உண்மையான KPI (losses, revenue, மிச்சப்படுத்துன நேரம்) நகருதான்னு A/B tests அல்லது pilots வச்சு check பண்ணுங்க.

**Segment வாரியா.** முக்கியமான groups (region, language, customer type) வாரியா metrics-ஐ report பண்ணுங்க; அப்போ average-ல நல்லா இருந்து சில users-க்கு மோசமா இருக்குற models சிக்கும்.

**Problem-க்கு metric-ஐ பொருத்துறது:**

| Problem | மோசமான error | Primary metric | கூடவே report பண்ணுங்க |
| --- | --- | --- | --- |
| Card fraud (rare) | Missed fraud | PR AUC, fixed alert budget-ல recall | Cost-weighted value |
| Spam filter | Real email spam-ல போறது | Precision | Recall |
| Disease screening | Missed disease | Recall | Precision, doctors-க்கு வேலை குவியாம இருக்க |
| Delivery time promise | Late delivery | 90th percentile quantile loss | MAE |
| Sales forecast | பெரிய misses | RMSE | Reporting-க்கு MAE |
| Recommendations | மேல இருக்குற items irrelevant-ஆ இருக்குறது | Precision at k, NDCG | Clicks அல்லது sign-ups-ல A/B test |

**Thresholds scores-ஐ decisions-ஆ மாத்தும்.** பெரும்பாலான classifiers 0-க்கும் 1-க்கும் இடையில ஒரு score கொடுக்கும். எந்த threshold-க்கு மேல ஒரு case flag ஆகணும்னு நீங்க தேர்ந்தெடுக்கிறீங்க. குறைவான threshold அதிக positives-ஐ பிடிக்கும் (அதிக recall), ஆனா அதிக false alarms வரும் (குறைவான precision); அதிகமான threshold எதிர்மாறா பண்ணும். பொதுவா "சரியான" threshold-ன்னு ஒண்ணு இல்ல: ஒவ்வொரு error-க்கும் எவ்வளவு cost, உங்க team எத்தனை cases-ஐ review பண்ண முடியும்ங்கிறதை பொறுத்தது. ஒரு practical முறை: capacity-ஐ fix பண்ணுறது, உதாரணம்: "fraud team ஒரு நாளைக்கு 300 alerts review பண்ணலாம்", அந்த 300 alerts வர்ற threshold-ஐ தேர்ந்தெடுத்து, அந்த point-ல recall-ஐ report பண்றது.

**Calibration.** Model 0.8-ன்னு சொன்னா, 80% chance-ன்னு அர்த்தமா? பெரும்பாலும் இல்ல. Calibrated model-ஓட scores உண்மையான frequencies-ஓட பொருந்தும்: சுமார் 0.8 score வாங்கின cases-ல சுமார் 80% positive-ஆ இருக்கும். Insurance price பண்றது, doctor-க்கு risk level காட்டுறது மாதிரி, மக்கள் probability-யையே வச்சு action எடுக்கும்போது calibration முக்கியம். Reliability plot வச்சு check பண்ணுங்க, Platt scaling அல்லது isotonic regression மாதிரி methods வச்சு சரி பண்ணுங்க.

**Rare-event problem-ல metrics, code-ல.** 2% positives இருக்குற ஒரு synthetic fraud மாதிரி dataset, numbers எவ்வளவு வித்தியாசமா நடந்துக்குதுன்னு காட்டும்:

```python
import numpy as np
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import (accuracy_score, roc_auc_score, average_precision_score,
                             precision_score, recall_score, brier_score_loss)

X, y = make_classification(n_samples=20_000, n_features=12, weights=[0.98], class_sep=0.9, random_state=7)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, stratify=y, random_state=7)
p = LogisticRegression(max_iter=1000).fit(X_tr, y_tr).predict_proba(X_te)[:, 1]

print("accuracy, always 'no':", round(accuracy_score(y_te, np.zeros_like(y_te)), 3))
print("ROC AUC:", round(roc_auc_score(y_te, p), 3), " PR AUC:", round(average_precision_score(y_te, p), 3))
print("precision, recall at 0.5:", round(precision_score(y_te, p > 0.5), 3), round(recall_score(y_te, p > 0.5), 3))
print("Brier:", round(brier_score_loss(y_te, p), 4))
```

"Never fraud"ன்னு predict பண்ணாலே சுமார் 98% accuracy கிடைக்கும், ROC AUC நம்பிக்கை தர்ற மாதிரி தெரியும், rare class பத்தின உண்மையான கதையை PR AUC தான் சொல்லும்.

**Costs-ல இருந்து threshold-ஐ தேர்ந்தெடுங்க.** Thresholds-ஐ sweep பண்ணி, மொத்த cost குறைவா இருக்கிறதை வச்சுக்கோங்க:

```python
def best_threshold(y_true, scores, cost_fp=200, cost_fn=15_000):
    best = None
    for t in np.linspace(0.01, 0.99, 99):
        pred = scores >= t
        fp = int(((pred == 1) & (y_true == 0)).sum())
        fn = int(((pred == 0) & (y_true == 1)).sum())
        cost = fp * cost_fp + fn * cost_fn
        if best is None or cost < best[1]:
            best = (round(float(t), 2), cost, fp, fn)
    return {"threshold": best[0], "cost_inr": best[1], "false_alarms": best[2], "missed": best[3]}

print(best_threshold(y_te, p))
```

Miss ஆன fraud-க்கு false alarm-ஐ விட 75 மடங்கு cost-ன்னா, best threshold 0.5-ஐ விட ரொம்ப கீழ இருக்கும்.

**வித்தியாசம் உண்மையானதா?** Interval கிடைக்க test set-ஐ bootstrap பண்ணுங்க:

```python
def bootstrap_ci(y_true, scores, metric=average_precision_score, n=1000, seed=0):
    rng = np.random.default_rng(seed)
    vals = []
    for _ in range(n):
        idx = rng.integers(0, len(y_true), len(y_true))
        if y_true[idx].sum() == 0:
            continue
        vals.append(metric(y_true[idx], scores[idx]))
    return np.percentile(vals, [2.5, 97.5]).round(3)

print("PR AUC 95% interval:", bootstrap_ci(y_te, p))
```

ரெண்டு models-ஓட intervals நிறைய overlap ஆனா, இந்த test set-ஐ மட்டும் வச்சு ஒண்ணு better-ன்னு claim பண்ணாதீங்க.

**ஒரு range-ஐ predict பண்றது.** Delivery promises-க்கு, 90th percentile-க்கு train பண்ணி, pinball loss வச்சு score பண்ணுங்க:

```python
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.metrics import mean_pinball_loss

rng = np.random.default_rng(1)
km = rng.uniform(1, 12, 3000).reshape(-1, 1)
minutes = 10 + 3 * km[:, 0] + rng.gamma(2, 4, 3000)          # skewed delays
q90 = GradientBoostingRegressor(loss="quantile", alpha=0.9).fit(km[:2000], minutes[:2000])
pred = q90.predict(km[2000:])
print("share delivered within the promise:", round(float((minutes[2000:] <= pred).mean()), 2))
print("pinball loss:", round(mean_pinball_loss(minutes[2000:], pred, alpha=0.9), 2))
```

சுமார் 90% deliveries சொன்ன நேரத்துக்குள்ள வந்து சேரணும்; அந்த share-ஐ உண்மையான data-ல area வாரியா check பண்ணுங்க.

- **ATM cash demand forecasting**: cash தீர்ந்து போறது, extra வச்சிருக்கிறதை விட ரொம்ப மோசம். அதனால demand-ஓட 90th percentile-ஐ predict பண்ணி, quantile loss வச்சு evaluate பண்றாங்க, reporting-க்கு MAE-யும் கூடவே.

**Business-க்கு இந்த choice-ஐ explain பண்றது.** Fraud team head-க்கு PR AUC வேண்டாம்; அந்த model bank-க்கு என்ன பண்ணும்னு தெரியணும். அதனால team இப்படி translate பண்ணுச்சு: "உங்க analysts handle பண்ணக்கூடிய ஒரு நாளைக்கு 300 alerts-ல, புது model ஒவ்வொரு 100 fraud cases-லயும் சுமார் 78-ஐ பிடிக்குது, முன்னாடி 64. அதாவது ஒரு மாசத்துக்கு சுமார் ₹1.1 crore நஷ்டம் தவிர்க்கப்படுது, கூடுதல் analyst நேரம் இல்லாம." Model metric model-ஐ தேர்ந்தெடுத்துச்சு; ரூபாய் figure தான் decision எடுக்க வச்சுது.

## பொதுவா பண்ற தப்புகள்

- **Imbalanced data-ல accuracy.**
- **Rare events-க்கு ROC AUC மட்டும்.** PR AUC-யையும், உங்க operating point-ல precision-ஐயும் பாருங்க.
- **சின்ன அல்லது zero actuals-ல MAPE.** MAE அல்லது weighted variants use பண்ணுங்க.
- **KPI-ஐ நகர்த்தாத metric-ஐ optimise பண்றது.** Pilots அல்லது A/B tests வச்சு validate பண்ணுங்க.
- **Overall numbers மட்டும்.** Segments-ஐயும் check பண்ணுங்க.

- **பழக்கத்துல threshold-ஐ தேர்ந்தெடுக்கிறது.** 0.5 அரிதா தான் best threshold-ஆ இருக்கும். Costs-ஐயும் review capacity-யையும் வச்சு தேர்ந்தெடுங்க.
- **Calibration check பண்ணாம scores-ஐ probabilities-ஆ எடுத்துக்கிறது.**
- **Results பார்த்த பிறகு metric-ஐ தேர்ந்தெடுக்கிறது.** Experiment-க்கு முன்னாடியே agree பண்ணுங்க.
- **சின்ன test sets-ல interval இல்லாதது**, அதனால noise-ஐ progress-ன்னு report பண்றாங்க.
- **Error costs ஒரு பக்கம் சாஞ்சிருக்கும்போது default threshold 0.5.**

## ஒரு simple metric போதும்ங்கிறது எப்போ

- **ஆரம்ப exploration-ல**, ஒரு நல்ல metric ideas-ஐ வேகமா compare பண்ண உதவும்.
- **முழுமையான evaluation-க்கு முன்னாடி ஒரு quick sanity check**, baseline-ஓட.

## Practice பண்ணுங்க

scikit-learn-ஓட metrics guide-ஐயும், precision, recall, ROC பத்தின Google-ஓட classification module-ஐயும் படிங்க.

1. உங்களுக்கு தெரிஞ்ச மூணு problems-க்கு (ஒரு rare-event classification, ஒரு forecast, ஒரு ranking), ஒரு primary metric-ஐ தேர்ந்தெடுத்து, ஒவ்வொண்ணையும் ஒரு வாக்கியத்துல justify பண்ணுங்க.
2. ஒரு imbalanced dataset-ல, ரெண்டு models-க்கு ROC AUC-யையும் PR AUC-யையும் compare பண்ணி, அவை எங்க முரண்படுதுன்னு note பண்ணுங்க.
3. உங்க சொந்த cost assumptions வச்சு ஒரு cost-weighted evaluation build பண்ணி, அதுல இருந்து ஒரு threshold-ஐ தேர்ந்தெடுங்க.
4. ஒரு imbalanced dataset-ல உங்க சொந்த costs வச்சு best_threshold-ஐ run பண்ணுங்க, அப்புறம் ஒரு missed case-ஓட cost-ஐ பாதியா குறைச்சு, threshold எவ்வளவு தூரம் நகருதுன்னு பாருங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க metric choice-ஐ business owner-கிட்ட ரூபாய்ல, engineer-கிட்ட model behaviour பத்தி, ரெண்டு விதமாவும் defend பண்ண முடியும்.
