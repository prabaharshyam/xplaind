## இது என்ன

Prompt engineering-னா ஒரு நல்ல instruction எழுதுறது. **Context engineering**-னா ஒரு call-ல model பார்க்குற எல்லாமே: system prompt, tool definitions, examples, retrieved documents, memory, இதுவரை நடந்த conversation, முந்தைய tool calls-ஓட results. ஒரு one-shot கேள்விக்கு இவை சின்னதா இருக்கும். ஐம்பது steps வேலை செய்யுற ஒரு agent-க்கு இவை குவியும், கேள்வி இப்படி மாறும்: இப்போ window-ல என்ன இருக்கணும், என்ன இருக்கக்கூடாது?

Context ஒரு budget. ரொம்ப நீளமான windows இருக்குற models-உம் கூட, window சம்பந்தமில்லாத material-ஆல நிறையும்போது மோசமா வேலை செய்யும்: details-ஐ miss பண்ணும், goal-ஐ மறக்கும், ஒரு step-க்கு செலவும் அதிகமாகும்.

| Step 37-ல context | முன்னாடி | பின்னாடி |
|---|---|---|
| System prompt | Rules, 6k tokens | Principles, 1.5k tokens |
| Tools | 12 definitions | 4 definitions |
| Data | முழு purchase register-உம் supplier filings-உம் | Notes: pages 1-2 resolved, INV-7781, INV-7790 open; 20 mismatches இருக்குற தற்போதைய page |
| Tool results | 36 பழையவை, window நிறையுற வரை | 2 புதியவை |
| Result | Suppliers-ஐ குழப்பி, limit-ஐ தொட்டுச்சு | ஒரே run-ல 3,000 mismatches |

## இது எப்படி work ஆகுது

**சரியான altitude-ல system prompt.** ரொம்ப தெளிவில்லாதது ("helpful-ஆ இரு") எந்த வழிகாட்டுதலும் தராது; ரொம்ப கடுமையானது (பக்கம் பக்கமா if-then rules) நீங்க எதிர்பார்க்காத cases-ல உடையும். தெளிவான principles, முக்கிய steps, headings-ஓட ஒழுங்குபடுத்தின சில examples-ஐ குறிவைங்க.

**இலகுவான tools.** ஒவ்வொரு tool definition-உம் ஒவ்வொரு call-லயும் tokens செலவழிக்குது, ஒன்றோடொன்னு overlap ஆகுற ஒவ்வொரு tool-உம் accuracy-ஐ குறைக்குது. தற்போதைய task-க்கு தேவையான tools-ஐ மட்டும் கொடுங்க.

**Just-in-time retrieval.** எல்லா documents-ஐயும் முன்னாடியே load பண்றதுக்கு பதிலா, agent-க்கு தேடி பார்க்க வழிகள் கொடுங்க (search, open file, read record), தேவைப்படும்போது தேவையானதை எடுக்க விடுங்க. File paths, record ids மாதிரி இலகுவான references-ஐ context-ல வச்சு, content-ஐ தேவைப்படும்போது fetch பண்ணுங்க.

**பழைய tool results-ஐ clear பண்ணுங்க.** மூணு steps முன்னாடி use பண்ண 5,000-token search result வெறும் சுமை. Results use ஆனதும் அவற்றை நீக்குங்க அல்லது சுருக்குங்க, என்ன கண்டுபிடிச்சதுன்னு ஒரு வரி note வச்சுக்கிட்டு.

**Compaction.** Context அதோட limit-ஐ நெருங்கும்போது, history-ஐ ஒரு சின்ன state-ஆ summarise பண்ணுங்க: goal, எடுத்த decisions, open questions, key facts. அந்த summary-ஓட புதுசா ஆரம்பிங்க.

**Structured notes.** நீளமான tasks-க்கு, agent context-க்கு வெளியே ஒரு notes file அல்லது to-do list வச்சு, அதை திரும்ப படிக்க வைங்க, அப்போ compaction-க்கு அப்புறமும் progress தப்பிக்கும்.

**Sub-agents.** ஒரு sub-task-ஐ தன்னோட சுத்தமான context இருக்குற ஒரு sub-agent-கிட்ட கொடுத்து, அதோட summary-ஐ மட்டும் திரும்ப எடுத்துக்குங்க.

**Tokens எங்க போகுது:**

| பகுதி | பொதுவான பிரச்சனை | Fix |
| --- | --- | --- |
| System prompt | அரிதான cases-க்கு பக்கம் பக்கமா rules | Principles, steps, ஒண்ணு ரெண்டு examples |
| Tool definitions | ஒன்றோடொன்னு overlap ஆகுற பல tools | இந்த task-க்கு தேவையான tools மட்டும் |
| Retrieved documents | முன்னாடியே எல்லாத்தையும் load பண்றது | Id வச்சு தேவைப்படும்போது fetch பண்ணு |
| Tool results | எப்பவும் வச்சிருக்குறது | Use ஆனதும் clear பண்ணு, ஒரு வரி note வச்சிரு |
| History | ஒவ்வொரு turn-லயும் வளருது | State summary-ஆ compact பண்ணு |

**ஒரு நல்ல compaction summary எழுதுறது.** ஒரு summary அதுக்கு முன்னாடி இருந்த எல்லாத்தையும் மாத்தும், அதனால agent தொடர தேவையானதை அது சுமக்கணும்: அசல் task, constraints முழுசா, எடுத்த decisions, ஏன்னு, இதுவரை results totals-ஆ, ids-ஓட open items, அடுத்த step. ஒவ்வொரு step எப்படி செய்யப்பட்டுச்சுங்கிற விவரிப்பை விட்டுடுங்க. Compaction-உடனும் இல்லாமலும் ஒரு task-ஐ ஓட்டி, இறுதி results பொருந்துதான்னு பார்த்து compaction-ஐ test பண்ணுங்க; compact பண்ண run ஒரு constraint-ஐ மறந்தா, summary prompt-ல ஒரு section விடுபட்டிருக்கு.

**Effect-ஐ அளக்குறது.** ஒரு சில tasks-க்கு, ஒவ்வொரு மாற்றத்துக்கு முன்னாடியும் பின்னாடியும், ஒவ்வொரு step-லயும் பகுதி வாரியா token counts-ஐ log பண்ணுங்க. மூணு numbers-ஐ கவனிங்க: ஒரு task-க்கு tokens, ஒரு task-க்கு cost, task success. Tokens-ஐ குறைச்சு success-ஐ குறைக்குற மாற்றம், model-க்கு தேவையான எதையோ நீக்கிடுச்சு.

**பழைய tool results-ஐ code-ல clear பண்றது.** சமீபத்திய சில results-ஐ முழுசா வச்சு, பழையவற்றை ஒரு வரி note-ஆ மாத்துங்க:

```python
def clear_old_results(messages, keep_last=3, max_chars=400):
    """Anthropic-style messages: tool results are blocks of type 'tool_result' in user turns."""
    seen = 0
    for msg in reversed(messages):
        if msg["role"] != "user" or not isinstance(msg["content"], list):
            continue
        for block in msg["content"]:
            if block.get("type") != "tool_result":
                continue
            seen += 1
            text = str(block.get("content", ""))
            if seen > keep_last and len(text) > max_chars:
                block["content"] = f"[cleared: {len(text)} chars; first line: {text.splitlines()[0][:120]}]"
    return messages
```

Call நடந்துச்சுன்னும், அது ஏறத்தாழ என்ன return பண்ணுச்சுன்னும் model-க்கு இன்னும் தெரியும், ஆனா அதோட 5,000 tokens தெரியாது. அதுக்கு details திரும்ப தேவைன்னா, tool-ஐ திரும்ப call பண்ணலாம்.

**Fixed sections இருக்குற ஒரு compaction prompt.** "இதை summarise பண்ணு"ங்கிற free-form ஒண்ணு constraints-ஐ இழக்கும். Agent தொடர தேவையான பகுதிகளை கேளுங்க:

```python
COMPACT_PROMPT = """Summarise this work so another assistant can continue it with no other context.
Use exactly these headings:
TASK: the original request and every constraint, word for word where possible
DECISIONS: what was decided and why, one line each
RESULTS SO FAR: totals and key facts, with ids
OPEN ITEMS: what remains, with ids
NEXT STEP: the single next action
Leave out how each step was done."""
```

Context ஒரு threshold-ஐ தாண்டும்போது இதை ஓட்டி, system prompt-ஓட summary-யையும் வச்சு ஒரு புது conversation ஆரம்பிச்சு, ரெண்டு token counts-ஐயும் log பண்ணுங்க.

**Context-க்கு வெளியே notes.** நீளமான tasks-க்கு, agent-க்கு ரெண்டு சின்ன tools கொடுத்து, ஒவ்வொரு milestone-க்கு அப்புறமும் தன்னோட notes-ஐ update பண்ண சொல்லுங்க:

```python
from pathlib import Path

NOTES = Path("runs/notes-{run_id}.md")

def read_notes(run_id):
    p = Path(str(NOTES).format(run_id=run_id))
    return p.read_text() if p.exists() else "(no notes yet)"

def write_notes(run_id, text):
    p = Path(str(NOTES).format(run_id=run_id))
    p.parent.mkdir(exist_ok=True)
    p.write_text(text[:4000])                    # keep notes short
    return "saved"
```

Compaction அல்லது restart-க்கு அப்புறம், agent முதல்ல தன்னோட notes-ஐ படிச்சுட்டு தொடரும்.

**அதிக context-னா மோசமான answers-ஆ இருக்கலாம்.** நீளமான inputs பத்தின studies, எளிய lookups-க்கு கூட context வளர வளர accuracy குறையுதுன்னும், நீளமான inputs-ஓட நடுவுல இருக்குற facts குறைவான நம்பகத்தன்மையோட use ஆகுதுன்னும் கண்டுபிடிச்சிருக்கு. Context engineering-னா, window-ஐ நிரப்புறது இல்லை, model task-ஐ நல்லா பண்ண உதவுற மிகச் சின்ன tokens set-ஐ கொடுக்குறது.

**Order முக்கியம்.** Cache பண்ண முடியுறதுக்காக stable content-ஐ (system prompt, tool definitions) முதல்ல வைங்க, வேலை பண்ற material-ஐ நடுவுல, தற்போதைய கேள்வியையும் சமீபத்திய results-ஐயும் கடைசியில வைங்க; அங்க தான் models அதிகம் கவனம் செலுத்தும்.

## ஒரு worked example

Chennai GST consultancy-க்கான ஒரு agent, ஒரு client-ஓட purchase register-ஐ supplier filings-ஓட reconcile பண்ணுது: ஆயிரக்கணக்கான invoices, விளக்க வேண்டிய mismatches, ஒரு இறுதி report.

முதல் version முழு register-ஐயும், முழு filing data-வையும், பன்னிரண்டு tools-ஐயும் context-ல load பண்ணுச்சு. நாற்பது invoices-க்கு அப்புறம் window limit-ஐ தொட்டுச்சு, அதுக்கு முன்னாடியே ஒரே மாதிரி பேர் இருக்குற suppliers-ஐ குழப்பிச்சு.

Redesign:

- System prompt, reconciliation rules-ஐயும் report format-ஐயும் ஒரு worked mismatch-ஓட விளக்குது.
- நாலு tools மட்டும்: `list_mismatches(page)`, `get_invoice(id)`, `get_supplier_filing(gstin, period)`, `write_note(text)`.
- Agent ஒரு நேரத்துல 20 mismatches இருக்குற ஒரு page-ஐ பாக்குது. ஒவ்வொண்ணுக்கு அப்புறமும் ஒரு note எழுதுது ("Page 3: 14 timing differences-ஆ resolve ஆச்சு, 4 supplier file பண்ணல, 2-க்கு client input வேணும்: INV-7781, INV-7790") பழைய tool results clear ஆகுது.
- ஒவ்வொரு 100 mismatches-க்கும், history totals, open items-ஓட summary-ஆ compact ஆகுது.

Agent இப்போ ஒரே run-ல 3,000 mismatches-ஐ handle பண்ணுது. ஒரு invoice-க்கு cost 70% குறையுது, supplier matching-ல error rate குறையுது, ஏன்னா model கைல இருக்குற case-ஓட records-ஐ மட்டும் தான் பார்க்குது.

| அளவு | முதல் version | Redesign |
| --- | --- | --- |
| ஒரு run-ல handle பண்ண mismatches | சுமார் 40, அப்புறம் window நிறைஞ்சுது | 3,000 |
| ஒரு invoice-க்கு cost | Baseline | 70% குறைவு |
| Supplier matching errors | ஒரே மாதிரி பேர்களை அடிக்கடி குழப்பம் | அரிது |

## பொதுவா பண்ற தப்புகள்

- **பின்னாடி தேவைப்படும்னு எல்லாத்தையும் load பண்றது.** அதிக context நல்ல context இல்லை. தேவைப்படும்போது retrieve பண்ணுங்க.
- **ஒவ்வொரு tool result-ஐயும் எப்பவும் வச்சிருக்கிறது.** Use ஆனதும் results-ஐ clear பண்ணுங்க அல்லது summarise பண்ணுங்க.
- **Goal-ஐயே compact பண்ணி தொலைக்கிறது.** ஒரு summary சமீபத்திய நிகழ்வுகளை மட்டும் இல்லை, task, constraints, open items-ஐயும் வச்சிருக்கணும்.
- **ஐந்து-tool task-க்கு இருபது tools.** ஒவ்வொண்ணும் tokens செலவழிக்குது, தப்பான தேர்வுக்கு அழைப்பும் விடுக்குது.
- **உண்மையான context-ஐ எப்பவும் பார்க்காம இருக்கிறது.** Fail ஆகுற steps-ல model வாங்குனதை log பண்ணி படிங்க; காரணம் பெரும்பாலும் தெரியும்.
- **Constraints-ஐ விட்டுடுற free-form compaction summaries.** Fixed headings use பண்ணுங்க.
- **Note இல்லாம results-ஐ clear பண்றது**, அதனால model அதே call-ஐ திரும்ப பண்ணும்.
- **Calls-க்கு இடையில tool order-ஐ மாத்துறது**, இது prompt caching-ஐ உடைக்கும்.

## Context engineering காத்திருக்கக்கூடிய நேரங்கள்

- **சின்ன tasks**, window-க்குள்ள நல்லா சில steps-ல முடியுறவை.
- **Single calls**, ஒரு fixed prompt, ஒரு input-ஓட.
- **குறைந்த volume**, அதிகப்படியான tokens-க்கு செலவு குறைவு, quality ஏற்கனவே நல்லா இருக்கு.

நீளமான agent runs, நீளமான chats, பெரிய documents, context வளர வளர cost அல்லது accuracy குறையுற எதுக்கும் இது ரொம்ப முக்கியம்.

## Demo-ல இருந்து production-க்கு

- ஒவ்வொரு step-லயும் **பகுதி வாரியா tokens-ஐ log பண்ணுங்க**: system, tools, history, results.
- Clearing, compaction-க்கு **thresholds வைங்க**, ஒவ்வொண்ணும் எப்போ தூண்டப்படுதுன்னு log பண்ணுங்க.
- அதே tasks-ல compaction-உடனும் இல்லாமலும் results-ஐ compare பண்ணி **compaction-ஐ test பண்ணுங்க**.
- Trace-ஓட link பண்ணி, ஒவ்வொரு run-க்கும் **notes-ஐ storage-ல வச்சிருங்க**.
- **Caching-க்கு ஏத்த மாதிரி context-ஐ order பண்ணுங்க**, மாற்றங்களுக்கு அப்புறம் cache hit rates-ஐ check பண்ணுங்க.

## Practice பண்ணுங்க

Agents-க்கான context engineering பத்தின Anthropic-ஓட article-ஐயும் context windows page-ஐயும் படிங்க.

1. நீங்க build பண்ண ஏதாவது ஒரு agent-ஐ எடுத்து, அதோட கடைசி step-ல அனுப்புன முழு context-ஐ log பண்ணுங்க. பகுதி வாரியா tokens-ஐ எண்ணுங்க: system prompt, tools, history, tool results.
2. பழைய tool results-ஐ clear பண்றதையும், context நீங்க தேர்ந்தெடுக்குற ஒரு threshold-ஐ தாண்டும்போது ஒரு compaction step-ஐயும் சேருங்க.
3. அதே ஐந்து tasks-ஐ முன்னாடியும் பின்னாடியும் ஓட்டி, ஒரு task-க்கு tokens, task success-ஐ compare பண்ணுங்க.
