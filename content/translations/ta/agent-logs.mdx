## இது என்ன

ஒரு agent தப்பா ஏதாவது செஞ்சா, ஏன்னு தெரியணும்: எந்த step வழி தப்புச்சு, model என்ன பார்த்துச்சு, எந்த tool என்ன திருப்பி தந்துச்சு. **Agent logs** (அடிக்கடி traces-ன்னு சொல்லுவாங்க) ஒவ்வொரு run-ஓட ஒவ்வொரு step-ஐயும் record பண்ணும்:

- ஒவ்வொரு model call: input messages, reply, tokens, நேரம்;
- ஒவ்வொரு tool call: tool, arguments, result அல்லது error, நேரம்;
- இறுதி outcome, user, prompt-ஓட model-ஓட versions.

| Step | Type | Input | Output | நேரம் |
|---|---|---|---|---|
| 1 | model | கேள்வி + tools | get_tracking-ஐ கூப்பிடுது | 1.1 s |
| 2 | tool | get_tracking(SHP-77812) | "Nagpur hub, 3 Nov" | 0.4 s |
| 3 | model | ... + tracking result | get_eta-ஐ கூப்பிடுது | 0.9 s |
| 4 | tool | get_eta(SHP-77812) | **ERROR: timeout** | 5.0 s |
| 5 | model | ... + அந்த error | **"Arrives 5 November"**: கற்பனை | 0.8 s |

Run 9c1f, user cust-2231, prompt v6, model chat-default.

இந்த lesson-ல Hyderabad-ல ஒரு logistics company-ஐ follow பண்ணப் போறோம்; அவங்களோட shipment agent சில நேரம் customers-க்கு தப்பான delivery dates சொல்லிட்டிருந்தது.

## இது எப்படி work ஆகுது

**ஒவ்வொரு step-ஐயும் structured data-வா record பண்ணுங்க**, சிதறிக்கிடக்குற print statements-ஆ இல்லை. ஒரு எளிய வடிவம்: run id, step number, type (model அல்லது tool), inputs, outputs, start-உம் end-உம் நேரம், tokens, cost. Runs-ஐ JSON lines-ஆ அல்லது ஒரு tracing tool-ல store பண்ணுங்க.

**முடிஞ்சா ஒரு tracing tool use பண்ணுங்க.** LLM apps-க்காக build ஆன tools (Langfuse, Arize Phoenix, LangSmith, இன்னும் சில; நிறைய OpenTelemetry-ல) ஒவ்வொரு run-ஐயும், நீங்க விரிவாக்கி பார்க்கக்கூடிய steps-ஓட tree-ஆ, timings, costs-ஓட காட்டும்.

**எல்லாத்தையும் link பண்ணுங்க.** ஒவ்வொரு run-க்கும் ஒரு id குடுத்து, tool logs, application logs-க்கு அனுப்புங்க; அதனால ஒரு request-ஐ எல்லா systems வழியாவும் follow பண்ணலாம்.

**Fail ஆன runs-ஐ படிங்க.** முடிவுல இருந்து (என்ன தப்பாச்சு) ஆரம்பிச்சு பின்னாடி நடங்க: tool result தப்பா இருந்துச்சா? Model அதை தப்பா படிச்சுதா? முன்னாடியே தப்பான tool-ஐ தேர்ந்தெடுத்துச்சா? Information எப்பவுமே கிடைக்கவே இல்லையா?

**Failures-ஐ tests-ஆ மாத்துங்க.** ஒவ்வொரு interesting failure-ஓட input-ஐயும் ஒரு test case-ஆ save பண்ணி, மாற்றங்களுக்கு அப்புறம் மறுபடி run பண்ணுங்க.

**Privacy-ஐ கவனிங்க.** Logs-ல user messages, tool data இருக்கும். Personal data-வை mask பண்ணுங்க, access-ஐ restrict பண்ணுங்க, retention periods வைங்க.

**Measure பண்ணுங்க.** Logs-ல இருந்து success rates, ஒரு task-க்கு steps, ஒரு task-க்கு cost, ரொம்ப slow ஆன steps, ரொம்ப common ஆன errors கிடைக்கும்.

**JSON lines-ஆ ஒரு step record:**

```text
{"run":"9c1f","step":4,"type":"tool","name":"get_eta","args":{"id":"SHP-77812"},
 "error":"timeout after 5 s","start":"2026-11-03T21:52:10+05:30","ms":5004}
```

**Logs சீக்கிரமா பதில் சொல்ல வேண்டிய கேள்விகள்:**

| கேள்வி | தேவையான fields |
| --- | --- |
| இந்த பதில் ஏன் தப்பாச்சு? | ஒவ்வொரு step-ஓட inputs, outputs, வரிசையா |
| எந்த tool அதிகம் fail ஆகுது? | ஒரு step-க்கு tool பேர், error |
| ஒரு task-க்கு என்ன cost ஆகுது? | ஒரு model call-க்கு tokens, cost; ஒரு run-க்கு கூட்டினது |
| புது prompt உதவுச்சா? | ஒவ்வொரு run-லயும் prompt version, கூட outcome |
| எந்த user-க்கு problem வந்துச்சு? | Pseudonymous user id, run id |

**ஒரு வழக்கமான review பழக்கம்.** வாரத்துக்கு ஒரு தடவை, பத்து runs-ஐ படிங்க: fail ஆன அல்லது மோசமான feedback வந்த அஞ்சு, random-ஆ எடுத்த அஞ்சு. Random runs முக்கியம், ஏன்னா யாரும் இன்னும் புகார் பண்ணாத problems-ஐ அவை காட்டும்; உதாரணம், மூணு steps போதும்ங்குற இடத்துல agent எட்டு steps எடுக்குறது. ஒவ்வொரு run-க்கும் என்ன சரியா போச்சு, என்ன தப்பா போச்சுன்னு ஒரு வரி எழுதுங்க. ஒரு மாசத்துல, எந்த dashboard-ஐ விடவும், அடுத்து என்ன fix பண்ணணும்னு இந்த notes நல்லா காட்டும்.

**Volume கூடும்போது logs-ஐ பயனுள்ளதா வச்சுக்கிறது.** Error, refusal அல்லது negative feedback இருக்குற ஒவ்வொரு run-ஐயும் store பண்ணுங்க, மத்ததுல ஒரு sample. உங்க release cycle-ஐ cover பண்ற அளவுக்கு நீண்ட நாள் வச்சுக்கோங்க; அப்போ ஒரு மாற்றத்துக்கு முன்னாடி, அப்புறம் compare பண்ணலாம்.

**நீங்களே எழுதக்கூடிய ஒரு சின்ன tracer.** ஒரு tool-ஐ adopt பண்றதுக்கு முன்னாடி, சில வரிகள் ஒவ்வொரு step-க்கும் ஒரு run id, ஒரு timing, ஒரு structured record தரும்:

```python
import json, time, uuid
from contextlib import contextmanager
from contextvars import ContextVar

RUN_ID = ContextVar("run_id", default=None)
STEP = ContextVar("step", default=0)

def start_run(user, prompt_version, model):
    rid = uuid.uuid4().hex[:8]
    RUN_ID.set(rid); STEP.set(0)
    write({"run": rid, "type": "run_start", "user": user, "prompt": prompt_version, "model": model})
    return rid

def write(record):
    record["at"] = time.strftime("%Y-%m-%dT%H:%M:%S%z")
    with open("traces.jsonl", "a") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")

@contextmanager
def step(kind, name, **inputs):
    STEP.set(STEP.get() + 1)
    rec = {"run": RUN_ID.get(), "step": STEP.get(), "type": kind, "name": name, "inputs": inputs}
    t0 = time.monotonic()
    try:
        yield rec                           # the caller sets rec["output"], tokens, cost
    except Exception as err:
        rec["error"] = f"{type(err).__name__}: {err}"
        raise
    finally:
        rec["ms"] = round((time.monotonic() - t0) * 1000)
        write(rec)

# Use it around every model and tool call:
start_run("cust-2231", "v6", "chat-default")
with step("tool", "get_tracking", id="SHP-77812") as rec:
    rec["output"] = "Nagpur hub, 3 Nov 21:40"
```

**ஒரு run-ஐ திருப்பி படிக்கிறது.** அதே file "run 9c1f-ல என்ன நடந்துச்சு?"ங்குற கேள்விக்கு பதில் சொல்லும்:

```python
def show(run_id, path="traces.jsonl"):
    rows = [json.loads(l) for l in open(path) if json.loads(l)["run"] == run_id]
    for r in sorted(rows, key=lambda r: r.get("step", 0)):
        what = r.get("error") or str(r.get("output", ""))[:60]
        print(f'{r.get("step", "-"):>2} {r["type"]:<9} {r.get("name", ""):<14} {r.get("ms", ""):>6} ms  {what}')
```

ஒரு tracing tool-க்கு மாறும்போது, அதே fields-ஐ வச்சுக்கோங்க. பெரும்பாலான tools OpenTelemetry spans-ஐ ஏத்துக்கும்; அதனால மாறுறது பெரும்பாலும் records எங்க அனுப்பப்படுதுங்குறதை மாத்துறது தான்.

**Behaviour-ஐ மாத்துற எல்லாத்தையும் log பண்ணுங்க.** Model பேரு, version, sampling settings, prompt template version, உண்மையில அனுப்பின final prompt, tool versions, retrieval settings. வாரங்கள் கழிச்சு ஒரு bug வரும்போது, கேள்வி எப்பவும் "இந்த run-ல என்ன வித்தியாசம்?"ன்னு தான் இருக்கும், log பண்ண settings மட்டுமே அதுக்கு பதில் சொல்லும்.

**Data-வை பார்க்குறது உங்க எண்ணத்தை மாத்தும்.** நிஜ runs-ஐ தொடர்ந்து படிக்கிற teams, நல்ல பதில்னா என்னங்குற தங்க எண்ணம் மாறுறதை கண்டுபிடிப்பாங்க: அவங்க கற்பனை பண்ணாத failure types-ஐயும், யாரும் எழுதாத requirements-ஐயும் கவனிப்பாங்க. அவற்றை prompt-லயும் eval set-லயும் சேருங்க.

**Traces-ல இருந்து agent metrics.** Run வாரியா group பண்ணி கணக்கிடுங்க: success rate, ஒரு run-க்கு steps, ஒரு run-க்கு cost, tool error இருக்குற runs-ஓட பங்கு, அடிக்கடி failure-க்கு முன்னாடி வர்ற tools. ஒரு run-க்கு steps அதிகமாகுறது, ஒரு prompt அல்லது tool மாற்றம் agent-ஐ குழப்பிடுச்சுன்னு காட்டுற முதல் அறிகுறியா இருக்கும்.

## ஒரு example

Hyderabad-ல ஒரு logistics company-ஓட agent, tracking, delay-reason, ETA tools-ஐ கூப்பிட்டு "என் shipment எங்க இருக்கு?"ன்னு பதில் சொல்லுது. Customers அப்பப்போ தப்பான delivery dates வருதுன்னு report பண்றாங்க.

Report பண்ண ஒரு run-ஓட trace-ஐ team திறக்குது:

```text
run 9c1f  user=cust-2231  prompt=v6  model=chat-default  5 steps  6.2 s  Rs 0.38
 1 model      -> calls get_tracking("SHP-77812")
 2 tool       get_tracking: last scan "Nagpur hub, 3 Nov 21:40"
 3 model      -> calls get_eta("SHP-77812")
 4 tool       get_eta: ERROR timeout after 5 s
 5 model      -> "Your shipment will arrive on 5 November."
```

ETA tool timeout ஆச்சு, model தெரியலன்னு சொல்றதுக்கு பதிலா ஒரு date-ஐ கற்பனை பண்ணிடுச்சு. Fixes: tool இப்போ ஒரு தெளிவான error message தருது ("ETA unavailable right now"); `get_eta` ஒண்ணை தந்தா தவிர ஒரு date-ஐ சொல்லவே கூடாதுன்னு prompt சொல்லுது; run-ல ETA result இல்லன்னா இறுதி பதில்ல dates-ஐ ஒரு check block பண்ணுது. Trace ஒரு test case ஆகுது.

| Fix | Effect |
| --- | --- |
| ETA tool "ETA unavailable right now"ன்னு தருது | Model அமைதியை இல்லாம, தெளிவான error-ஐ பார்க்குது |
| Prompt: get_eta தந்தா தவிர date சொல்லக்கூடாது | கற்பனை dates குறையுது |
| ETA result இல்லன்னா பதில்ல dates-ஐ check block பண்ணுது | Customers பார்க்குறதுக்கு முன்னாடியே கற்பனை dates பிடிபடுது |
| Run ஒரு test case-ஆ save ஆச்சு | ஒவ்வொரு மாற்றத்துக்கு அப்புறமும் case மறுபடி test ஆகுது |

**Trace இதை ஏன் வேகமா ஆக்குச்சு.** Step logs இல்லன்னா, team இறுதி message-ஐ மட்டுமே பார்த்திருக்கும், "Your shipment will arrive on 5 November"; அப்போ ETA service-ஐயோ model-ஐயோ random-ஆ குற்றம் சொல்லியிருக்கலாம். Trace ரெண்டையும் ஒரே நேரத்துல காட்டுச்சு: tool timeout ஆச்சு, அந்த அமைதியை model நிரப்பிடுச்சு. ஒவ்வொரு fix-உம் அந்த ரெண்டு காரணங்கள்ல ஒண்ணை குறிவச்சுது, save பண்ண test ரெண்டுமே fix ஆகியிருக்குன்னு நிரூபிக்குது.

## பொதுவா பண்ற தப்புகள்

- **இறுதி பதில்களை மட்டும் log பண்றது.**
- **Structure இல்லாத print statements.** Search பண்ணவும் analyse பண்ணவும் கஷ்டம்.
- **Run ids இல்லாதது.** Systems முழுக்க steps-ஐ connect பண்ண முடியாது.
- **Personal data-வை mask பண்ணாம log பண்றது.**
- **புகார் வந்த பிறகு மட்டும் logs-ஐ படிக்கிறது.** ஒரு sample-ஐ தொடர்ந்து review பண்ணுங்க.

- **Runs-ல versions இல்லாதது.** Prompt, model versions இல்லன்னா, ஒரு மாற்றம் நிலைமையை நல்லாக்குச்சா மோசமாக்குச்சான்னு சொல்ல முடியாது.
- **தாமதமா வர்ற logs.** Event நடந்து 15 நிமிஷம் கழிச்சு traces வந்தா, live debugging அவற்றுக்காக காத்திருக்கணும்.
- **Prompt template-ஐ log பண்ணி, final prompt-ஐ log பண்ணாம இருக்கிறது.** Bugs அடிக்கடி fill பண்ண இடத்துல ஒளிஞ்சிருக்கும்.

## எளிய logging போதும்ங்குற நேரங்கள்

- **Tools இல்லாத ஒரே model call**: ஒவ்வொரு request-க்கும் tokens, நேரம், outcome இருக்குற ஒரு log line போதும்.
- **நீங்களே run பண்ற ஒரு prototype**: மத்தவங்க use பண்ற வரை, ஒவ்வொரு step-ஐயும் console-ல print பண்ணா வேலை செய்யும்.
- **ரெண்டு அல்லது மூணு steps இருக்குற fixed workflows**: ஒரு shared request id இருக்குற சாதாரண application logs போதும்.

Runs-ல பல steps இருக்கும்போது, tools முக்கியமான வழிகள்ல fail ஆகும்போது, அல்லது பல பேர் ஒரே system-ஐ debug பண்ணும்போது, முழு traces-க்கு மாறுங்க.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு run-ஐயும் trace பண்ணுங்க**, எல்லா failures-ஐயும் negative-feedback runs-ஐயும் store பண்ணுங்க, மத்ததை sample பண்ணுங்க.
- **எழுதுறதுக்கு முன்னாடி personal data-வை mask பண்ணுங்க**, access-ஐ restrict பண்ணுங்க, உங்க release cycle-ஐ cover பண்ற அளவுக்கு retention வைங்க.
- **ஒரு support ticket-ல இருந்து ஒரு run-ஐ திறக்கிறதை ஈஸியாக்குங்க**: user-க்கு தெரியுற error message-ல run id-ஐ வைங்க.
- **Trace metrics-க்கு alert வைங்க**: tool error rate, ஒரு run-க்கு steps, ஒரு run-க்கு cost.
- **Interesting runs-ஐ ஒரு click அல்லது ஒரு command-ல test cases-ஆ மாத்துங்க.**
