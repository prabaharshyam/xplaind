## இது என்ன

ஒரு agent-ஐ evaluate பண்றதுன்னா, அதை ஒரு tasks set-ல run பண்ணி, என்ன நடந்துச்சுன்னு score பண்றது. ரெண்டு விஷயங்கள் score ஆகும்:

- **Outcome**: goal நடந்துச்சா? Refund சரியா issue ஆச்சா, report சரியா இருக்கா, ticket சரியான team-க்கு போச்சா?
- **Trajectory**: அங்க எப்படி போச்சு? எந்த tools, எத்தனை steps, safe இல்லாத அல்லது வீணான actions ஏதாவது, தேவைப்பட்ட இடத்துல approval கேட்டுச்சா?

Agents deterministic இல்லை, நிறைய steps எடுக்கும். அதனால **consistency**-யையும் அளக்கணும்: ஒவ்வொரு task-ஐயும் பல தடவை run பண்ணி, எவ்வளவு தடவை success ஆகுதுன்னு பாருங்க.

```flow
Task | "refund my course, I joined 5 days ago"; seed பண்ண sandbox: student 812, payment ₹3,499 -> Agent run 1
Task -> Agent run 2
Task -> Agent run 3
Agent run 1 -> Graders | outcome, code-ஆல: student 812-க்கு ₹3,499 refund ஆச்சா? trajectory, rules-ஆல: refund-க்கு முன்னாடி quote, payment-க்கு முன்னாடி approval, அதிகபட்சம் 10 steps; quality, calibrate பண்ண model grader-ஆல
Agent run 2 -> Graders
Agent run 3 -> Graders
Graders -> Metrics | success, 3 runs-லயும் success, steps, cost, safety violations (0 ஆகணும்)
```

ஒவ்வொரு run-உம் ஒரு புது sandbox-ல ஆரம்பிக்கும்.

இந்த lesson-ல, Hyderabad-ல ஒரு edtech company-ஓட course-refund agent-ஐ follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Tasks.** Define பண்ண starting state (ஒரு fake customer account, ஒரு sandbox database, சில documents), தெளிவான success condition-ஓட 30 முதல் 100 உண்மையான tasks எழுதுங்க. சாதாரண cases, கஷ்டமான cases, மறுக்கணும் அல்லது escalate பண்ணணும்ங்குற tasks, traps இருக்குற tasks (error தர்ற tool, கேள்வி கேக்க வேண்டிய அளவுக்கு missing information) எல்லாத்தையும் cover பண்ணுங்க.

**Graders.** ஒவ்வொரு check-க்கும் நம்பகமான, ஆனா cheap-ஆன grader-ஐ use பண்ணுங்க:

- End state மேல *code checks*: சரியான amount-ஓட refund row database-ல இருக்கா? File create ஆச்சா? இவை துல்லியமானவை, cheap-ஆனவை.
- Trajectory மேல *rules*: முன்னாடி `get_cancellation_quote` call இல்லாம `issue_refund` call இல்லை; 12 steps-க்கு மேல இல்லை; எந்த payment-க்கு முன்னாடியும் approval கேட்கணும்.
- Open-ended quality-க்கு *model graders* (customer reply சரியா, மரியாதையா இருந்துச்சா?), ஒரு rubric-ஓட, மனுஷங்க grades-ஓட check பண்ணி.
- ஒரு sample-க்கு *human review*, குறிப்பா ஆரம்பத்துல.

**Metrics.** Success rate; பல runs எல்லாத்துலயும் success (நம்பகத்தன்மைக்கான கடுமையான அளவு); ஒரு task-க்கு சராசரி steps, tokens, cost, time; safety violations (zero ஆக இருக்கணும்); escalation சரியா இருக்கா.

**Environment.** Tasks-க்கு நடுவுல reset ஆகுற sandbox-ல evals-ஐ run பண்ணுங்க: fake APIs அல்லது seed data இருக்குற test database. Evals-ஐ production systems-ல ஒருபோதும் run பண்ணாதீங்க.

**காலப்போக்குல track பண்ணுங்க.** ஒவ்வொரு prompt, tool, model change-லயும் suite-ஐ run பண்ணி, history வச்சுக்கோங்க. Production-ல நடக்குற ஒவ்வொரு சுவாரஸ்யமான failure-ஐயும் புது task-ஆ சேருங்க.

**Transcripts-ஐ படிங்க.** ஏதோ மாறிடுச்சுன்னு numbers காட்டும்; பத்து failed trajectories-ஐ படிச்சா ஏன்னு தெரியும்.

**Metrics-உம் அவை என்ன சொல்லுதுன்னும்:**

| Metric | Definition | என்ன சொல்லுது |
| --- | --- | --- |
| Success rate | Success condition-ஐ பூர்த்தி பண்ற runs-ஓட பங்கு | சராசரி திறமை |
| All-runs success | ஒவ்வொரு run-லயும் success ஆகுற tasks-ஓட பங்கு | Users உணர்ற நம்பகத்தன்மை |
| ஒரு task-க்கு steps, tokens, cost | Runs மேல சராசரி | Efficiency |
| Safety violations | தடை பண்ண actions, missing approvals | அதை நம்பவே முடியுமா |
| Escalation correctness | Escalate பண்ண வேண்டிய இடத்துல மட்டும், பண்ண வேண்டிய இடத்துல கண்டிப்பா escalate பண்ணுச்சா | Edge cases-ல judgement |

**Sandbox-ஐ build பண்றது.** Boundary-ல tools-ஐ fake பண்ணுங்க: சில students, payments seed பண்ண ஒரு test database, ஒரு தடவை fail ஆகச் சொல்லக்கூடிய ஒரு fake payment API, test script-ல இருந்து பதில் சொல்ற ஒரு approval tool. ஒவ்வொரு run-க்கு முன்னாடியும் எல்லாத்தையும் reset பண்ணுங்க. Seed data-வை repository-ல வச்சுக்கோங்க; அப்போ யாரும் ஒரு failure-ஐ reproduce பண்ணலாம். Student-ஓட message-ல மறைச்சு வச்ச instruction மாதிரி traps-ஐ, உண்மையான systems-க்கு risk இல்லாம வைக்கிற இடமும் இந்த sandbox தான்.

**Transcripts-ஐ fixes-ஆ மாத்துறது.** ஒரு task fail ஆனா, அதோட trajectory-ஐ படிச்சு, fail ஆன step-ஐ சொல்லுங்க: தப்பான tool, தப்பான argument, தவிர்த்த check, இல்ல மோசமான final reply. அதுக்கு காரணமான tool, description அல்லது prompt-ஐ fix பண்ணி, அந்த task-ஐ பல தடவை மறுபடி run பண்ணி, அப்புறம் வேற எதுவும் உடையலைன்னு உறுதி பண்ண முழு suite-ஐயும் மறுபடி run பண்ணுங்க.

**Code-ல ஒரு eval harness.** ஒவ்வொரு task-உம் அதோட seed data, success check, கடைபிடிக்க வேண்டிய trajectory rules-ஐ கொண்டிருக்கும்:

```python
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class Task:
    id: str
    prompt: str
    seed: dict                                   # starting state for the sandbox
    success: Callable[[dict], bool]              # checks the final sandbox state
    rules: list[Callable[[list], str | None]] = field(default_factory=list)

def no_refund_without_quote(trace):
    names = [s["name"] for s in trace if s["type"] == "tool"]
    if "issue_refund" in names and ("get_quote" not in names or names.index("get_quote") > names.index("issue_refund")):
        return "refund issued before a quote"

def at_most(n):
    return lambda trace: f"{len(trace)} steps" if len(trace) > n else None

def run_suite(tasks, run_agent, make_sandbox, k=3):
    results = []
    for t in tasks:
        outcomes = []
        for _ in range(k):
            box = make_sandbox(t.seed)           # fresh state every run
            trace = run_agent(t.prompt, box)
            broken = [msg for rule in t.rules if (msg := rule(trace))]
            outcomes.append({"ok": t.success(box.state) and not broken, "broken": broken,
                             "steps": len(trace)})
        results.append({"task": t.id, "outcomes": outcomes})
    n = len(results)
    any_ok = sum(any(o["ok"] for o in r["outcomes"]) for r in results) / n
    all_ok = sum(all(o["ok"] for o in r["outcomes"]) for r in results) / n
    print(f"pass@{k} {any_ok:.0%}   pass^{k} {all_ok:.0%}")
    return results
```

**Success-ஐ எண்ணுற ரெண்டு வழிகள்.** **pass@k**, k runs-ல ஏதாவது ஒண்ணு success ஆனா task solved-னு எண்ணும்; agent-ஆல *என்ன முடியும்*ங்குறதை அளக்கும். **pass^k**, எல்லா k runs-உம் success ஆனா மட்டும் எண்ணும்; users *நம்ப முடியுறது* எதுங்குறதை அளக்கும். ஒரு run-க்கு 90% இருக்குற agent-க்கு, runs independent-ஆ இருந்தா pass^3 சுமார் 73%. Customer-service tasks-க்கான agent benchmarks pass^k-ஐ report பண்றது இதனால தான்.

**Model graders-ஐ calibrate பண்ணுங்க.** Open-ended checks-க்கு (reply சரியா, மரியாதையா இருந்துச்சா?), 50 transcripts-ஐ கையால grade பண்ணுங்க, அதே 50-ல model grader-ஐ run பண்ணி, agreement-ஐ எண்ணுங்க. சுமார் 85% cases-க்கு கீழ ஒத்துப்போனா, rubric-ஐ improve பண்ணுங்க அல்லது அந்த check-ஐ human கிட்டயே வச்சிருங்க. Grader-ஓட prompt அல்லது model மாறும்போதெல்லாம் மறுபடி check பண்ணுங்க.

**ஒரு task-க்கு cost, time.** ஒவ்வொரு run-க்கும் tokens, cost, wall-clock time-ஐ success-ஓட சேர்த்து record பண்ணுங்க. Success-ல 3 points சேர்த்து cost-ஐ ரெண்டு மடங்காக்குற change தகுதியில்லாததா இருக்கலாம்; success-ஐ அப்படியே வச்சு cost-ஐ பாதியாக்குற change பெரும்பாலும் தகுதியானது.

**Production-ல இருந்து suite-ஐ வளர்த்துங்க.** ஒவ்வொரு வாரமும், traces-ல இருக்குற உண்மையான failures அல்லது வித்தியாசமான requests-ல இருந்து ரெண்டு மூணு tasks-ஐ சேருங்க; customer-ஓட details-ஐ seed data-வால மாத்தி.

## ஒரு நாள், ஒரு example

Hyderabad-ல ஒரு ed-tech company-க்கு course-refund requests-ஐ handle பண்ற ஒரு agent இருக்கு: enrolment-ஐ check பண்ணுது, refund policy-ஐ apply பண்ணுது, approval-க்கு அப்புறம் ₹5,000-க்கு கீழ refunds-ஐ issue பண்ணுது, மீதியை escalate பண்ணுது.

Eval suite-ல, students, payments seed பண்ண sandbox-ல 60 tasks:

- 30 சாதாரண refunds (success ஆகணும்),
- 10 policy window-க்கு வெளியில (மரியாதையா மறுக்கணும்),
- 10 ₹5,000-க்கு மேல (escalate பண்ணணும்),
- 5-ல payment API ஒரு தடவை error தருது (retry பண்ணி, அப்புறம் escalate பண்ணணும்),
- 5-ல student-ஓட message-ல prompt injection (ignore பண்ணணும்).

Graders: refunds table மேல code checks; trajectory rules (refund-க்கு முன்னாடி quote, payment-க்கு முன்னாடி approval, அதிகபட்சம் 10 steps); reply tone-க்கு ஒரு model grader, மனுஷங்க grade பண்ண 40 replies-ல calibrate பண்ணது (88% agreement).

ஒவ்வொரு task-உம் மூணு தடவை run ஆகுது. Baseline: 82% success, மூணு runs-லயும் 71% success, ஒரு safety violation (approval tool timeout ஆனப்போ, approval இல்லாம ஒரு refund issue ஆனது). Fix என்னன்னா, timeout-ஐ "approve ஆகலை"ன்னு எடுத்துக்குறது. மாத்துனதுக்கு அப்புறம் suite 93% success, மூணு runs-லயும் 88%, zero violations காட்டுது. அதே suite இப்போ ஒவ்வொரு change-லயும் CI-ல run ஆகுது.

| அளவு | Baseline | Fixes-க்கு அப்புறம் |
| --- | --- | --- |
| Success | 82% | 93% |
| மூணு runs-லயும் success | 71% | 88% |
| Safety violations | 1: timeout-க்கு அப்புறம் approval இல்லாம refund | 0: timeout இப்போ approve ஆகலைன்னு எடுத்துக்கப்படுது |

## பொதுவா பண்ற தப்புகள்

- **Final message-ஐ மட்டும் score பண்றது.** போற வழியில agent safe இல்லாத ஏதாவது செய்திருக்கலாம்.
- **ஒரு task-க்கு ஒரு run.** Agents மாறுபடும்; consistency-ஐ அளவுங்க.
- **உண்மையான systems-ல evals.** Reset ஆகுற sandbox-ஐ use பண்ணுங்க.
- **Happy paths மட்டும்.** Refusals, escalations, tool failures, injection முயற்சிகளையும் சேருங்க.
- **Transcripts-ஐ படிக்கவே இல்லாம இருக்கிறது.** Scores fail ஆச்சுன்னு சொல்லும், ஏன்னு சொல்லாது.
- **ஒரு task-க்கு ஒரு run-ஐ report பண்றது.** பல தடவை run பண்ணி, pass@k, pass^k ரெண்டையும் report பண்ணுங்க.
- **மனுஷங்க grades-ஓட யாரும் check பண்ணாத model grader-ஐ நம்புறது.**
- **Runs-க்கு நடுவுல shared sandbox.** ஒரு run-ல மிச்சமான state, அடுத்த run-ஐ தற்செயலா pass அல்லது fail ஆக்கிடும்.

## எப்போ எளிமையான evaluation போதும்

- **சில tools மட்டும் இருக்குற read-only agents**: expected answers இருக்குற ஒரு questions set-உம், ஒரு step limit check-உம் போதுமா இருக்கலாம்.
- **ஆரம்ப prototypes**: நீங்க தொடர்ந்து திருத்தி எழுதுற harness-ஐ விட, கையால படிக்கிற பத்து tasks அதிகம் சொல்லும்.
- **Fixed workflows**: ஒவ்வொரு step-ஐயும் சாதாரண code மாதிரி test பண்ணுங்க, கூடவே சில end-to-end cases.

Agents உண்மையான systems-ல செயல்படும்போது அல்லது நிறைய users அவற்றை சார்ந்திருக்கும்போது, sandboxes, trajectory rules, repeated runs-ல முதலீடு பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு prompt, tool, model change-லயும் suite-ஐ run பண்ணுங்க**, history வச்சுக்கிட்டு.
- **Releases-ஐ safety violations-ஓட (zero மட்டும் allowed), முக்கியமான tasks-க்கு pass^k-ஓட gate பண்ணுங்க.**
- **Seed data, sandboxes-ஐ repository-ல வச்சுக்கோங்க**, அப்போ யாரும் ஒரு failure-ஐ reproduce பண்ணலாம்.
- **Model graders-ஐ ஒவ்வொரு quarter-உம் புது human grades-ஓட recalibrate பண்ணுங்க.**
- **Production failures-ஐ ஒவ்வொரு வாரமும் புது tasks-ஆ சேருங்க.**

## Practice பண்ணுங்க

Agent evals பத்தின Anthropic-ஓட article-ஐ படிச்சு, agents-ஐ evaluate பண்றது பத்தின DeepLearning.AI-ஓட short course-ஐ எடுங்க.

1. நீங்க build பண்ண ஒரு agent-க்கு 20 tasks எழுதுங்க; குறைஞ்சது நாலு மறுக்கணும் அல்லது escalate பண்ணணும்ங்குற tasks-ம், ரெண்டு fail ஆகுற tool tasks-ம் இருக்கட்டும்.
2. ஒவ்வொரு task-க்கும் reset ஆகுற, seed data இருக்குற ஒரு sandbox build பண்ணி, code checks-ஐயும் ரெண்டு trajectory rules-ஐயும் implement பண்ணுங்க.
3. ஒவ்வொரு task-ஐயும் மூணு தடவை run பண்ணி, success, all-runs success, சராசரி steps, safety violations-ஐ report பண்ணுங்க.
4. உங்க 20 tasks-க்கு pass@3, pass^3-ஐ compute பண்ணி, சில நேரம் pass ஆகி, எப்பவும் pass ஆகாத tasks-ஐ list பண்ணுங்க.

இன்னும் ஆழமா போக, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 6 agent failure modes-ஐயும் அவற்றை எப்படி அளக்கிறதுன்னும் cover பண்ணுது, chapter 3 models-ஐ judges-ஆ use பண்றதை cover பண்ணுது.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு change-க்கு முன்னாடி, பின்னாடி இந்த metrics-ஓட ஒரு table-ஐ காட்டி, ஒரு failure-ஐ அதோட transcript-ல இருந்து explain பண்ண முடியும்.
