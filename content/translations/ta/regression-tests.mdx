## இது என்ன

**Regression**-னா, ஒரு மாற்றத்துக்கு அப்புறம் முன்னாடி வேலை செஞ்சது வேலை செய்யாம போறது. LLM apps-ல regressions சாதாரணமா, சத்தமில்லாம நடக்கும். ஒரு case-ஐ சரி பண்ற prompt tweak மூணு மத்ததை உடைக்கும். ஒரு model upgrade output format-ஐ மாத்தும். ஒரு புது chunking setting பெரும்பாலான questions-ஐ மேம்படுத்தும், ஆனா ஒரு முக்கியமான document-ஐ தொலைக்கும்.

**Regression tests**, ஒவ்வொரு மாற்றத்துக்கும் உங்க eval set-ஐ automatic-ஆ திரும்ப ஓட்டும்; அப்போ users பாக்குறதுக்கு முன்னாடியே இந்த உடைவுகள் பிடிபடும்.

```flow
Pull request | ஒரு prompt, model, retrieval அல்லது code மாற்றம் -> Fast tier, ஒவ்வொரு push-லயும், கிட்டத்தட்ட 90 s | app start ஆகுது, JSON valid, 4 options, 1 answer, duplicates இல்ல, must-refuse cases, 15 critical cases
Fast tier, ஒவ்வொரு push-லயும், கிட்டத்தட்ட 90 s -[fail ஆச்சு]-> Merge block ஆச்சு
Fast tier, ஒவ்வொரு push-லயும், கிட்டத்தட்ட 90 s -[pass ஆச்சு]-> Full tier, deploy-க்கு முன்னாடி அல்லது nightly | 120 cases, production baseline-க்கு எதிரா category வாரியா judge scores
Full tier, deploy-க்கு முன்னாடி அல்லது nightly -> Tolerance-குள்ள, எந்த critical category-யும் இறங்கல?
Tolerance-குள்ள, எந்த critical category-யும் இறங்கல? -[ஆமா]-> Deploy
Production bugs -> புது test cases -> Fast tier, ஒவ்வொரு push-லயும், கிட்டத்தட்ட 90 s
```

இந்த lesson, Noida-ல ஒரு edtech company-யோட quiz-generation feature-ஐ பத்தி; அது chapter text-ஐ multiple-choice questions-ஆ மாத்துது.

## இது எப்படி work ஆகுது

**ரெண்டு tiers tests.**

- *ஒவ்வொரு push-லயும் fast checks* (வினாடிகள்-ல இருந்து சில நிமிஷம்): மலிவான, deterministic code-level checks. App start ஆகுதா? Output valid JSON-ஆ parse ஆகுதா? தேவையான fields இருக்கா? தெரிஞ்ச must-refuse inputs மறுக்கப்படுதா? ஒரு சின்ன set critical cases இன்னும் pass ஆகுதா?
- *முக்கியமான மாற்றங்கள்ல அல்லது nightly முழுசான evals*: model judges-ஓட முழு test set, category வாரியா scores-ஐ இப்போ இருக்குற production version-ஓட ஒப்பிடுறது.

**Baseline-ஓட ஒப்பிடுங்க.** இப்போ இருக்குற production version-ஓட scores-ஐ சேர்த்து வைங்க. மொத்த quality ஒரு set tolerance-ஐ தாண்டி இறங்கலன்னா, எந்த critical category-யும் (safety, refusals, முக்கிய customers-ஓட cases) கொஞ்சம் கூட இறங்கலன்னா ஒரு மாற்றம் pass ஆகும்.

**Non-determinism-ஐ கையாளுங்க.** Model outputs runs-க்கு இடையில மாறும். முடிஞ்ச இடங்கள்ல tests-க்கு low temperature use பண்ணுங்க, exact text-க்கு பதிலா criteria வச்சு judge பண்ணுங்க, borderline cases-ஐ ஒரு தடவைக்கு மேல ஓட்டுங்க.

**Model upgrades-உம் மாற்றங்கள் தான்.** ஒரு provider புது model-ஐ release பண்ணும்போது, அல்லது நீங்க மாறலாம்னு நினைக்கும்போது, முழு eval-ஐ ஓட்டுங்க. Release notes-ஐ வச்சு இல்ல, results-ஐ வச்சு முடிவு பண்ணுங்க: ஒரு புது model மொத்தமா நல்லா இருந்தும் உங்க குறிப்பிட்ட cases-ல மோசமா இருக்கலாம்.

**CI-ல இணைங்க.** ஒவ்வொரு pull request-லயும் fast checks-ஐ ஓட்டுங்க; fail ஆனா merging-ஐ block பண்ணுங்க. ஒரு prompt அல்லது model மாற்றத்தை deploy பண்றதுக்கு முன்னாடி முழு eval-ஐ ஓட்டுங்க. Trends பாக்க results-ஐ சேர்த்து வைங்க.

**ஒவ்வொரு bug-ஐயும் சேருங்க.** ஒவ்வொரு production failure-உம் ஒரு regression test case ஆகும்.

**ஒவ்வொரு tier-லயும் என்ன போகும்:**

| Tier | எப்போ ஓடும் | உள்ளடக்கம் | நேரம் |
| --- | --- | --- | --- |
| Fast | ஒவ்வொரு push-லயும் | ஒரு சின்ன set மேல code checks, critical cases, must-refuse inputs | வினாடிகள்-ல இருந்து நிமிஷங்கள் |
| Full | Deploy-க்கு முன்னாடி, nightly | முழு test set, judges, category வாரியா ஒப்பீடு | நிமிஷங்கள்-ல இருந்து ஒரு மணி நேரம் |
| Model candidate | புது model வரும்போது | Full tier கூட downstream-ல use ஆகுற format checks | தேவையான அளவு |

**CI workflow-ஐ வார்த்தைகள்ல.** ஒவ்வொரு pull request-லயும், dependencies-ஐ install பண்ணி, test settings-ஓட app-ஐ start பண்ணி, fast tier-ஐ ஓட்டி, ஏதாவது check fail ஆனா job-ஐ fail பண்ணுங்க. Main branch-க்கு merge ஆகும்போது, அல்லது "run full eval" மாதிரி ஒரு label வரும்போது, full tier-ஐ ஓட்டுங்க. Scores-ஐ சேர்த்து வச்ச production baseline-ஓட category வாரியா ஒப்பிட்டு, pull request-ல ஒரு table-ஐ post பண்ணி, ஒரு critical category இறங்கியிருந்தா fail பண்ணுங்க. ஒவ்வொரு run-ஓட results-ஐயும் commit-ஓட சேர்த்து வைங்க; அப்போ காலப்போக்குல quality-ஐ chart பண்ணி, மெதுவான சரிவை பிடிக்கலாம்.

**Tolerances-ஐ set பண்றது.** ஒரே version-ல full tier-ஐ பல தடவை ஓட்டி, randomness-னால மட்டும் scores எவ்ளோ நகருதுன்னு பாருங்க. Overall tolerance-ஐ அந்த noise-க்கு கொஞ்சம் மேல வைங்க. Safety, refusals மாதிரி critical categories-க்கு கொஞ்சம் கூட இறங்க விடாதீங்க, அங்க இன்னும் cases சேருங்க; அப்போ ஒரு single failure தெளிவா தெரியும்.

**Code-ல fast tier.** Property checks சாதாரண tests தான். இது pytest use பண்ணி, சில சேர்த்து வச்ச chapters-ல quiz generator-ஐ ஓட்டுது:

```python
import json, pytest
from quiz import generate_quiz             # your app's function

CHAPTERS = json.load(open("tests/fast_chapters.json"))   # 15 saved chapters

@pytest.mark.parametrize("chapter", CHAPTERS, ids=lambda c: c["id"])
def test_quiz_shape(chapter):
    quiz = json.loads(generate_quiz(chapter["text"]))
    assert 3 <= len(quiz["questions"]) <= 10
    for q in quiz["questions"]:
        assert len(q["options"]) == 4
        assert len(set(q["options"])) == 4, "duplicate options"
        assert q["answer"] in q["options"]

def test_refuses_out_of_scope():
    out = generate_quiz("Write me a poem about cricket.")
    assert json.loads(out).get("error") == "not_a_chapter"
```

**Code-ல baseline ஒப்பீடு.** Full tier ஒவ்வொரு case-க்கும் அதோட category-ஓட ஒரு score-ஐ எழுதுது; இந்த script ஒரு candidate run-ஐ சேர்த்து வச்ச production run-ஓட ஒப்பிடுது:

```python
import json
from collections import defaultdict

CRITICAL = {"safety", "refusals"}

def by_category(path):
    scores = defaultdict(list)
    for line in open(path):
        r = json.loads(line)
        scores[r["category"]].append(r["score"])
    return {c: sum(v) / len(v) for c, v in scores.items()}

def compare(baseline_path, candidate_path, tolerance=0.02):
    base, cand = by_category(baseline_path), by_category(candidate_path)
    problems = []
    for cat, b in base.items():
        drop = b - cand.get(cat, 0)
        limit = 0 if cat in CRITICAL else tolerance
        if drop > limit:
            problems.append(f"{cat}: {b:.2f} -> {cand.get(cat, 0):.2f}")
    return problems

problems = compare("evals/production.jsonl", "evals/candidate.jsonl")
print("PASS" if not problems else "FAIL\n" + "\n".join(problems))
raise SystemExit(1 if problems else 0)       # a non-zero exit fails the CI job
```

**ஒரு இறக்கத்தை நம்பறதுக்கு முன்னாடி noise-ஐ அளங்க.** மாறாத production version-ல full tier-ஐ மூணுல இருந்து அஞ்சு தடவை ஓட்டுங்க. History accuracy தானாவே 0.84-க்கும் 0.87-க்கும் இடையில நகர்ந்தா, 0.85-ல இருக்குற ஒரு candidate regress ஆகல. சின்ன categories-க்கு cases சேருங்க: 20 cases-ல ஒரு failure 5-point ஊசலாட்டம்.

**Flaky cases.** சில cases ஒரு run-ல pass ஆகி அடுத்ததுல fail ஆகும். அவற்றை மூணு தடவை ஓட்டி ரெண்டு passes-ஐ கேளுங்க, அல்லது case-ஐ சரி பண்ணுங்க: அடிக்கடி எதிர்பார்க்குற answer தெளிவில்லாம இருக்கும். புரிஞ்சுக்காம ஒரு flaky case-ஐ சும்மா delete பண்ணாதீங்க.

**Bill-ஐ சின்னதா வைங்க.** Judge-ஓட full evals ஒவ்வொரு run-லயும் பணம் செலவாகும். மாறாத inputs, prompts-க்கு outputs-ஐ cache பண்ணுங்க, routine runs-க்கு ஒரு மலிவான judge-ஐயும் releases-க்கு முன்னாடி ஒரு strong judge-ஐயும் use பண்ணுங்க, full tier-ஐ ஒவ்வொரு push-லயும் இல்லாம labels அல்லது nightly ஓட்டுங்க.

**நீங்க test பண்றதை pin பண்ணுங்க.** ஒவ்வொரு run-ஓடவும் சரியான model version, prompt version, retrieval settings, judge prompt-ஐ record பண்ணுங்க. ஒரு score, அதே மாதிரி பண்ணின இன்னொரு score-ஓட மட்டும் தான் ஒப்பிடத்தக்கது.

## ஒரு worked example

Noida-ல ஒரு ed-tech company-யோட quiz-generation feature, chapter text-ல இருந்து multiple-choice questions-ஐ JSON-ஆ உருவாக்குது.

அவங்க set up:

- *ஒவ்வொரு push-லயும்*: app வழியா 15 chapters; ஒவ்வொரு output-உம் நாலு options, ஒரு சரியான answer-ஓட valid JSON-ஆ இருக்கா, duplicate options இல்லையா, sensitive historical content உள்ள ரெண்டு chapters அனுமதிக்கப்படாத வார்த்தைகளை உருவாக்கலயான்னு checks. 90 வினாடி ஆகும்.
- *Deploy பண்றதுக்கு முன்னாடி*: factual accuracy, difficulty-க்கு ஒரு judge score பண்ணின 120 chapters, subject வாரியா production-ஓட ஒப்பிடுறது.

ஒரு developer cost-ஐ குறைக்க prompt-ஐ சுருக்குறாரு. Fast checks pass ஆகுது. Full eval, science-க்கு accuracy மாறாம, history-க்கு 9 points இறங்கியிருக்குன்னு காட்டுது; ஏன்னா சுருக்கின prompt, chapter-ல இருக்குற facts-ஐ மட்டும் use பண்ணணும்ங்கிற ஒரு instruction-ஐ விட்டுடுச்சு. Release-க்கு முன்னாடி மாற்றம் திரும்ப வேலை செய்யப்படுது.

மாசங்களுக்கு அப்புறம், provider-ஓட புது model மொத்தமா 3 points அதிகமா score பண்ணுது, ஆனா JSON fields-ஐ வேற வரிசையில தருது; அதை ஒரு பழைய client parser-ஆல கையாள முடியல. Fast checks அதை பிடிக்குது, மாறுறதுக்கு முன்னாடி parser சரி பண்ணப்படுது.

| மாற்றம் | Fast tier | Full tier | முடிவு |
| --- | --- | --- | --- |
| Cost சேமிக்க prompt சுருக்கினது | Pass ஆச்சு | History accuracy 9 points இறங்குச்சு | Release-க்கு முன்னாடி திரும்ப வேலை செய்யப்பட்டது |
| புது provider model | ஒரு பழைய parser-ஐ உடைக்குற JSON field-order மாற்றத்தை பிடிச்சுது | மொத்தமா 3 points அதிகம் | Parser சரி பண்ணப்பட்டது, அப்புறம் மாறினாங்க |

## பொதுவா பண்ற தப்புகள்

- **Prompts-க்கு automated tests இல்லாம இருக்குறது.** Prompt மாற்றங்கள் code மாற்றங்கள்.
- **Exact-text ஒப்பீடுகள்.** Outputs மாறும்; properties, criteria-ஐ check பண்ணுங்க.
- **Averages மட்டும்.** Critical categories-ஐ தனியா பாதுகாங்க.
- **Evals ஓட்டாம models-ஐ upgrade பண்றது.**
- **Production bugs-ஐ test set-ல சேக்காம இருக்குறது.**
- **Fast tier மெதுவா வளர விடுறது.** அது சில நிமிஷங்களுக்கு மேல ஆனா, மக்கள் அதை skip பண்ணுவாங்க. மெதுவான cases-ஐ full tier-க்கு நகர்த்துங்க.
- **Judge-ஐயும் app-ஐயும் ஒரே நேரத்துல மாத்துறது.** எந்த மாற்றம் score-ஐ நகர்த்துச்சுன்னு சொல்ல முடியாது.
- **Green ஆக்க failing cases-ஐ delete பண்றது.** App-ஐ சரி பண்ணுங்க அல்லது case-ஐ சரி பண்ணுங்க, ஏன்னு எழுதி வைங்க.

## இலகுவான testing போதுமான நேரங்கள்

- **தினமும் மாறுற ஒரு prototype**: நீங்க திரும்ப திரும்ப எழுதுற ஒரு முழு suite-ஐ விட ஒரு கைப்பிடி smoke checks நல்லது.
- **சில expert users உள்ள internal tools**, அவங்க பிரச்சனைகளை சீக்கிரம் சொல்வாங்க: fast tier-ஐ வச்சுக்கோங்க, பெரிய மாற்றங்களுக்கு முன்னாடி மட்டும் full tier-ஐ ஓட்டுங்க.
- **ஒரு தெரிஞ்ச file format-ஐ parse பண்றது** மாதிரி fixed, deterministic steps: சாதாரண unit tests போதும்.

உண்மையான users output-ஐ சார்ந்திருக்க ஆரம்பிச்சதும் full tier, baselines, critical categories-ஐ சேருங்க.

## Demo-ல இருந்து production-க்கு

- **Fast tier-ல merges-ஐ block பண்ணுங்க**, அதை சில நிமிஷங்களுக்குள்ள வச்சுக்கோங்க.
- **ஒவ்வொரு prompt, model, retrieval release-க்கு முன்னாடியும் full tier-ஐ ஓட்டி**, pull request-ல category table-ஐ post பண்ணுங்க.
- **ஒவ்வொரு run-ஐயும்** அதோட commit, versions-ஓட சேர்த்து வச்சு, மெதுவான சரிவை பிடிக்க scores-ஐ காலப்போக்குல chart பண்ணுங்க.
- **Test set-ஐ காலாண்டுக்கு ஒரு தடவை review பண்ணுங்க**: பழைய cases-ஐ நீக்குங்க, புது user patterns-ஐயும் ஒவ்வொரு production bug-ஐயும் சேருங்க.
- **ஒரு model upgrade checklist வச்சுக்கோங்க**: full tier, ஒவ்வொரு downstream consumer-க்கும் format checks, cost, latency ஒப்பீடு.
