## இது என்ன

**Vibe coding**-னா code-ஐ நீங்களே type பண்றதுக்கு பதிலா, உங்களுக்கு என்ன வேணும்னு ஒரு AI agent-கிட்ட விவரிச்சு software build பண்றது. நல்லா தெரிஞ்ச AI researcher Andrej Karpathy, February 2025-ல ஒரு post-ல இந்த வார்த்தையை உருவாக்கினாரு. Vibes-க்கு விட்டுக்கொடுத்து, AI எழுதுறதை accept பண்ணி, code-ஐ கிட்டத்தட்ட பார்க்காமலே இருக்குற ஒரு style-ஐ அவரு விவரிச்சாரு. இந்த phrase எவ்வளவு வேகமா பரவுச்சுன்னா, Collins Dictionary "vibe coding"-ஐ 2025-ஓட Word of the Year-ஆ ஆக்கிடுச்சு.

அந்த original, review பண்ணாத style-க்கும் ஒரு இடம் இருக்கு. ஒரு weekend prototype-க்கு, உங்க சொந்த laptop-ல ஒரு one-off script-க்கு, அல்லது தூக்கிப்போடப் போற ஒரு demo-க்கு அது பரவாயில்ல. ஆனா மத்தவங்களோட data, பணம், passwords அல்லது private notes வச்சிருக்குற எதுக்கும் அது risky, ஏன்னா code என்ன பண்ணுதுன்னு யாருமே check பண்ணல. **இந்த lesson review பண்ற version-ஐ கத்துக்குடுக்குது**: பெரும்பாலான code-ஐ Claude எழுதும்; goal-ஐ set பண்றது, ஒவ்வொரு step-ஐயும் check பண்றது, எது ship ஆகணும்னு முடிவு பண்றது நீங்க. ஒரு interviewer "vibe coding"-னு சொன்னா, அவங்க எந்த அர்த்தத்துல சொல்றாங்கன்னு கேட்டு தெரிஞ்சுக்கோங்க.

**Claude Code** Anthropic-ஓட coding agent. ஒரு **agent**-னா text replies மட்டும் இல்லாம, ஒரு loop-ல actions எடுக்குற AI. ஒரு chatbot நீங்க copy பண்றதுக்கு code-ஐ suggest பண்ணும். Claude Code உங்க project-க்குள்ளயே act பண்ணும்: files-ஐ படிக்கும், எழுதும், edit பண்ணும், tests, builds மாதிரி commands run பண்ணும், errors-ஐ படிச்சு மறுபடி try பண்ணும். இதை terminal-ல, VS Code அல்லது ஒரு JetBrains IDE-ல, Claude desktop app-ல, அல்லது claude.ai/code-ல browser-லயே use பண்ணலாம்.

இங்க skill-னா புத்திசாலித்தனமான வார்த்தைகள் இல்ல. ஒரு நல்ல team lead, வேகமா வேலை செய்யுற ஒரு புது colleague கூட use பண்ற அதே skill தான்: goal-ஐ explain பண்றது, வேலையை சின்ன steps-ஆ பிரிக்கிறது, திரும்ப வர்றதை review பண்றது, என்ன மாத்தணும்னு சரியா சொல்றது.

```flow
title: ஒவ்வொரு feature-க்கும் ஒரு loop; வேலை செய்யுற ஒவ்வொரு step-க்கு அப்புறமும் commit
நீங்க: ஒரு spec, ஒரு feature -> Claude plan mode-ல plan பண்ணும்
Claude plan mode-ல plan பண்ணும் -[நீங்க approve அல்லது trim பண்றீங்க]-> Claude files-ஐ edit பண்ணும்
Claude files-ஐ edit பண்ணும் -> Claude tests-ஐயும் app-ஐயும் run பண்ணும்
Claude tests-ஐயும் app-ஐயும் run பண்ணும் -> நீங்க diff-ஐ படிச்சு app-ஐ try பண்றீங்க
நீங்க diff-ஐ படிச்சு app-ஐ try பண்றீங்க -[work ஆகுது]-> Commit, அடுத்த feature
நீங்க diff-ஐ படிச்சு app-ஐ try பண்றீங்க -[தப்பா இருக்கு]-> Precise feedback அல்லது rewind
Precise feedback அல்லது rewind -> Claude plan mode-ல plan பண்ணும்
```

## இது எப்படி work ஆகுது

### 1. Set up பண்ணுங்க, cost-ஐ தெரிஞ்சுக்கோங்க

Official overview page-ல இருக்குற command-ஐ வச்சு Claude Code-ஐ install பண்ணுங்க, அப்புறம் ஒரு புது folder-ல terminal-ஐ திறந்து `claude` run பண்ணுங்க. முதல் தடவை login பண்ண சொல்லும். அதே folder-ல `git init`-உம் run பண்ணுங்க, அப்போ ஒவ்வொரு change-ஐயும் பார்க்கவும் undo பண்ணவும் முடியும். நீங்க terminal-ஐ use பண்ணதே இல்லன்னா, docs-ல ஒரு சின்ன terminal guide இருக்கு.

உங்களுக்கு ஒரு paid Claude plan அல்லது Claude Console-ல ஒரு API account வேணும். Claude Code Free plan-ல கிடையாது. Anthropic-ஓட pricing page-ல 28 November 2026 அன்னைக்கு check பண்ணப்போ இருந்த prices:

Anthropic-ஓட pricing page Pro-வை "for everyday work"-னும் Max-ஐ "for all-day work"-னும் சொல்லுது. ஒரு build நடுவுல 5-hour limit-ஐ தொட்டா, reset-க்கு wait பண்ணணும் அல்லது paid usage credits-ஐ on பண்ணணும். நீங்க எவ்வளவு use பண்ணியிருக்கீங்கன்னு பார்க்க ஒரு session-ல `/usage` type பண்ணுங்க. அதிகமா pay பண்றதுக்கு முன்னாடி, Pro உங்களுக்கு போதுமான்னு பார்க்க கீழ இருக்குற மாதிரி ஒரு சின்ன app நல்ல test.

### 2. ஒரு சின்ன spec எழுதுங்க

எந்த code-க்கும் முன்னாடி `SPEC.md`-ல அரை page எழுதுங்க: app என்ன பண்ணும், யாரு use பண்ணுவாங்க, முக்கியமான மூணு முதல் அஞ்சு features, phone-ல எப்படி தெரியணும், எது scope-க்கு வெளியில. எல்லாத்தையும் விட out-of-scope list தான் முக்கியம், ஏன்னா நீங்க கேக்காத விஷயங்களை Claude சேர்க்காம அது தடுக்கும். உங்களுக்கு என்ன வேணும்னு உறுதியா தெரியலன்னா, உங்களை interview பண்ண Claude-கிட்ட சொல்லுங்க: "Ask me questions one at a time until you could write SPEC.md, then write it."

### 3. CLAUDE.md-ஆல அதுக்கு ஒரு memory கொடுங்க

ஒவ்வொரு session-உம் ஒரு fresh context-ஓட ஆரம்பிக்கும். ஒவ்வொரு session ஆரம்பத்துலயும் Claude `CLAUDE.md`-ஐ படிக்கும், அதனால code-ல இருந்து அதுவா கண்டுபிடிக்க முடியாததை அதுல போடுங்க: app-ஐ எப்படி run, test பண்றது, உங்க rules, உதாரணமா "mobile first, 360 px wide", "no paid APIs" அல்லது "never put keys in client code". First draft-க்கு `/init` run பண்ணுங்க, அப்புறம் lines-ஐ delete பண்ணுங்க. ஒவ்வொரு file-ஐயும் 200 lines-க்கு கீழ வைக்க Anthropic-ஓட docs suggest பண்ணுது, ஏன்னா ஒவ்வொரு line-உம் ஒவ்வொரு task-லயும் Claude-ஓட attention-ல கொஞ்சத்தை எடுத்துக்கும். ஒரே விஷயத்துக்காக Claude-ஐ ரெண்டு தடவை correct பண்ணா, ஒரு line சேருங்க.

### 4. நீங்க use பண்ணப்போற controls

| நீங்க பண்ண நினைக்கிறது | இதை பண்ணுங்க |
|---|---|
| Edits இல்லாம ஒரு plan வாங்க | `/plan`-உம் task-உம் type பண்ணுங்க, அல்லது mode-ல plan-னு காட்டுற வரைக்கும் Shift+Tab அழுத்துங்க |
| ஒவ்வொரு command-ஐயும் நீங்களே approve பண்ண | Auto mode-ல இருந்து manual (default) mode-க்கு போக Shift+Tab அழுத்துங்க |
| என்ன மாறுச்சுன்னு பார்க்க | `/diff` type பண்ணுங்க, அல்லது `git diff` run பண்ணுங்க |
| Claude-ஓட கடைசி edits-ஐ undo பண்ண | காலியான prompt-ல Esc-ஐ ரெண்டு தடவை அழுத்துங்க, அல்லது `/rewind` type பண்ணுங்க |
| சம்பந்தமில்லாத ஒரு புது task-ஐ ஆரம்பிக்க | `/clear` type பண்ணுங்க (`/resume`-ஆல திரும்ப வரலாம்) |
| நீளமான session-ஐ சுருக்க | எதை வச்சுக்கணும்னு சொல்லி `/compact` type பண்ணுங்க, உதாரணமா `/compact keep the test commands` |
| ஒரு step நடுவுல Claude-ஐ நிறுத்த | Esc அழுத்துங்க |

**Permission modes** உங்ககிட்ட கேக்காம Claude என்ன பண்ணலாம்னு முடிவு பண்ணும். புது terminal, VS Code sessions **auto mode**-ல ஆரம்பிக்கும்: routine steps-க்கு நிக்காம Claude வேலை செய்யும், ஒரு தனி safety model ஒவ்வொரு action-ஐயும் check பண்ணி risky ஆனதை block பண்ணும், உதாரணமா ஒரு production deploy, ஒரு force push, அல்லது தெரியாத ஒரு server-க்கு data அனுப்புறது. Auto mode prompts-ஐ குறைக்கும், ஆனா safety-க்கு guarantee கிடையாதுன்னு Anthropic வெளிப்படையா சொல்லுது. உங்க முதல் project-ல manual mode-ஐ யோசிச்சு பாருங்க; அதுல ஒவ்வொரு command-க்கும் முன்னாடி Claude கேக்கும், அதனால அது என்ன run பண்ணுதுன்னு நீங்க கத்துக்குவீங்க. உங்க சொந்த laptop-ல bypass mode-ஐ use பண்ணவே பண்ணாதீங்க; docs அதை isolated containers-க்கு மட்டும் தான் வைக்குது.

**Checkpoints backup இல்ல.** Claude அதோட file tools-ஆல பண்ண edits-ஐ `/rewind` undo பண்ணும், ஆனா ஒரு shell command பண்ண எல்லா change-ஐயும் இல்ல. உங்க உண்மையான history Git தான்: வேலை செய்யுற ஒவ்வொரு step-க்கு அப்புறமும் commit பண்ணுங்க.

### 5. Plan பண்ணுங்க, அப்புறம் சின்ன steps-ல build பண்ணுங்க

முதல்ல ஒரு plan கேளுங்க, அதை படிங்க, தேவையில்லாததை வெட்டுங்க. அப்புறம் ஒரு நேரத்துல ஒரு feature build பண்ணுங்க: layout, அப்புறம் data, அப்புறம் calculations, அப்புறம் saving, அப்புறம் deployment. சின்ன step-னா சின்ன diff, சின்ன diff-ஐ தான் நீங்க உண்மையிலயே படிக்க முடியும். Claude அதோட வேலையை அதுவே check பண்ண ஒரு வழி கொடுங்க: tests, அல்லது "run the app and check it at 360 px wide". Built-in `/verify` command, app-ஐ build பண்ணி run பண்ணி result-ஐ பார்க்க Claude-கிட்ட சொல்லும்.

### 6. Diff-ல red flags இருக்கான்னு படிங்க

நல்லா review பண்ண ஒவ்வொரு line-உம் புரியணும்னு அவசியம் இல்ல. இதையெல்லாம் skim பண்ணி பாருங்க, ஏதாவது ஒண்ணு கண்ணுல பட்டா "ஏன்?"னு கேளுங்க:

- **நீங்க சொல்லாத files.** ஒரு layout fix settlement maths-ஐ தொடவே கூடாது.
- **Delete பண்ணின அல்லது weak ஆக்கின tests.** Pressure-ல இருக்குற ஒரு agent சில நேரம், fail ஆகுற ஒரு test எதை expect பண்ணுதுங்கறதையே மாத்தி அதை "fix" பண்ணிடும்.
- **நீங்க ஒத்துக்காத புது packages.** ஒவ்வொண்ணும் இனிமே நீங்க depend பண்ற code.
- **Browser-ல run ஆகுற எந்த file-லயும் ஒரு secret key.**
- **அளவுக்கு மீறின size.** ஒரு one-line bug-க்கு 300-line diff வந்தா அதுக்கு explanation வேணும்.

### 7. Link-ஐ share பண்றதுக்கு முன்னாடி security-ஐ check பண்ணுங்க

AI-built apps பாதிக்கப்படுற ஒரு பொதுவான வழி புத்திசாலித்தனமான hacking இல்ல. திறந்தே விட்ட ஒரு key அல்லது database தான். வேற யாருக்காவது link கிடைக்கறதுக்கு முன்னாடி:

- **Client code-ல secret keys இல்ல.** Next.js-ல, `NEXT_PUBLIC_`-ல ஆரம்பிக்குற பேர் இருக்குற எந்த variable-உம், ஒவ்வொரு visitor-க்கும் அனுப்புற JavaScript-க்குள்ள copy ஆகிடும். Publish பண்ண safe-ஆன values-க்கு மட்டும் அந்த prefix-ஐ use பண்ணுங்க.
- **`.env` `.gitignore`-ல இருக்கு**, உங்க git history-ல எந்த key-உம் இல்ல.
- **ஒவ்வொரு Supabase table-லயும் row-level security.** Supabase-ஓட browser key public-ஆ இருக்கத்தான் உருவாக்கப்பட்டது; ஒவ்வொரு user-உம் எந்த rows-ஐ படிக்கலாம் அல்லது மாத்தலாம்னு row-level security தான் முடிவு பண்ணும். Secret (service role) key அந்த rules-ஐ skip பண்ணிடும், அதனால அது server-லயே இருக்கணும்.
- **Input-ஐ server-ல check பண்ணுங்க**, form-ல மட்டும் இல்ல.
- அப்புறம் Claude-கிட்ட நேரடியா கேளுங்க: "Review this project for exposed secrets, tables without row-level security and unchecked input. List each problem with the file."

## ஒரு worked example

இது ஒரு உதாரணத்துக்கான கதை; நேரங்களும் உதாரணத்துக்கு தான், measure பண்ணது இல்ல. Nisha Pune-ல மூணு friends கூட ஒரு flat-ஐ share பண்றாங்க, WhatsApp chat-ல bills-ஐ பிரிக்கிறது அவங்களுக்கு அலுத்துப்போச்சு. அவங்க ஒரு product designer, developer இல்ல.

**Spec.** அவங்க `SPEC.md` எழுதுறாங்க: "ஒரு one-page web app. ஒரு bill சேர்க்கலாம்: amount, யார் pay பண்ணாங்க, யார் share பண்றாங்க (pay பண்ணவங்க எப்பவுமே share பண்றாங்க). யார் யாருக்கு தரணும்னு, முடிஞ்ச அளவு குறைவான payments-ல காட்டணும். Phone-ல வேலை செய்யணும். Browser-ல save ஆகும்; login இல்ல. Rupees, whole numbers. Scope-க்கு வெளியில: accounts, சமமில்லாத splits, payment links." அவங்க `claude` run பண்ணி, `/init` type பண்ணி, spec-ஐ படிச்சு கேள்விகள் கேக்க Claude-கிட்ட சொல்றாங்க. ஒரு bill-ஐ சில flatmates மட்டும் share பண்ண முடியுமான்னு Claude கேக்குது. முடியும்னு சொல்றாங்க: ஒருத்தர் ஊர்ல இல்லாதப்போ groceries மூணு பேருக்குள்ள பிரியும்.

**Plan-உம், அவங்களோட push-back-உம்.** Plan mode-ல Claude ஒரு Next.js app-ஐ propose பண்ணுது: ஒரு server, ஒரு form, ஒரு bill list, ஒரு settlement function, local storage, tests. Nisha கேக்குறாங்க: "There is no login and no database. Is there a simpler stack?" Claude ரெண்டு options கொடுக்குது: plain HTML-உம் JavaScript-உம், அல்லது tests-க்கு Vitest-ஓட ஒரு சின்ன Vite app. அவங்க Vite-ஐ தேர்ந்தெடுக்குறாங்க, ஏன்னா அது Vercel host பண்ணக்கூடிய plain static files-ஆ build ஆகும், Vitest maths-ஐ test பண்றதை ஈஸி ஆக்கும். Step one-ஐ மட்டும் approve பண்றாங்க: page-உம் form-உம். அது அவங்க phone-ல run ஆகுது. Commit பண்றாங்க.

**Tests பிடிச்ச bug.** Step three-க்கு, அதாவது settlement maths-க்கு, முதல்ல tests கேக்குறாங்க. ஒரு test, அவங்களே கையால check பண்ணக்கூடிய ஒரு case-ஐ use பண்ணுது: Nisha, Aarti, Meera share பண்ற groceries-க்கு Nisha ₹1,000 pay பண்றாங்க. ₹1,000-ஐ மூணால வகுத்தா ₹333.33, அதனால ஒருத்தர் ஒரு rupee அதிகமா கொடுக்கணும். Claude ஒரு rule-based test-உம் எழுதுது: shares-ஐ கூட்டினா எப்பவுமே bill amount வரணும். அந்த test fail ஆகுது. முதல் version எல்லாருக்கும் ₹333 கொடுத்துச்சு, கூட்டினா ₹999, அதனால ஒரு rupee காணாம போகுது. Claude காரணத்தை explain பண்ணி, மிச்சம் இருக்குற rupee-ஐ pay பண்ணவங்களுக்கு கொடுத்து fix பண்ணுது:

```js
export function splitBill(amount, payer, people) {
  const share = Math.floor(amount / people.length); // 1000 / 3 -> 333
  const shares = Object.fromEntries(people.map((p) => [p, share]));
  shares[payer] += amount - share * people.length; // payer is a sharer: 333 + 1 = 334
  return shares;
}
// splitBill(1000, "Nisha", ["Nisha", "Aarti", "Meera"])
// -> { Nisha: 334, Aarti: 333, Meera: 333 }; Aarti and Meera each owe Nisha 333
```

ஒரு rupee காணாம போனதை அவங்க கண்ணால பார்த்து கண்டுபிடிச்சிருக்கவே மாட்டாங்க. Rule-based test அதை பிடிச்சுது, பின்னாடி ஏதாவது ஒரு change அதே தப்பை திரும்ப கொண்டு வந்தா அதையும் பிடிக்கும்.

**ஒரு red flag.** 360 px screen-ல table-ஐ fix பண்ணும்போது, Claude-ஓட diff settlement file-ஐயும் edit பண்ணுது. Nisha ஏன்னு கேக்குறாங்க. அது சம்பந்தமே இல்லாத ஒரு rename. அவங்க Esc-ஐ ரெண்டு தடவை அழுத்தி, rewind பண்ணி, "change only the CSS"-னு சேர்த்து மறுபடி கேக்குறாங்க.

**Shipping.** Deploy பண்றதுக்கு முன்னாடி, step 7-ல இருக்குற security review-ஐ கேக்குறாங்க. Keys-உம் இல்ல, server-உம் இல்ல, அதனால `.gitignore`-ல `.env` இல்லங்கறது மட்டும் தான் finding; Claude அதை சேர்க்குது. சாயங்காலம் Vercel-ல deploy பண்றாங்க. மறுநாள் காலையில flatmates app-ஐ use பண்றாங்க. சுமார் அஞ்சு மணி நேரம் ஆச்சு, அதுல பெரும்பகுதி அவங்களுக்கு என்ன வேணும்னு முடிவு பண்றதுலயே போச்சு.

## பொதுவா பண்ற தப்புகள்

**ஒரே message-ல முழு app-ஐயும் கேக்குறது.** Review பண்ண முடியாத, test பண்ணாத ஒரு பெரிய குழப்பம் தான் கிடைக்கும். ஒரு நேரத்துல ஒரு feature கேளுங்க.

**Spec-ஐ skip பண்றது.** Spec இல்லன்னா Claude guess பண்ணும், அந்த தப்பான guess மேல அது build பண்ணின பிறகு தான் நீங்க அதை கவனிப்பீங்க. எது scope-க்கு வெளியிலன்னும் எழுதுங்க.

**தேவைக்கு மேல build பண்ற plan-ஐ accept பண்றது.** Agents அடிக்கடி உங்களுக்கு தேவையானதை விட பெரிய stack-ஐ propose பண்ணும். Approve பண்றதுக்கு முன்னாடி "is there a simpler way?"-னு கேளுங்க.

**புரியாத changes-ஐ accept பண்றது.** Explanation கேளுங்க. Code, அதோட bugs, அதோட security எல்லாத்துக்கும் owner நீங்க தான்.

**Auto mode-ஐயோ checkpoints-ஐயோ safety net-ஆ நம்புறது.** Auto mode ஒரு model-ஓட judgement, guarantee இல்ல; checkpoints சில changes-ஐ miss பண்ணும். வேலை செய்யுற ஒவ்வொரு step-க்கு அப்புறமும் commit பண்ணுங்க.

**Browser பார்க்கக்கூடிய இடத்துல keys-ஐ போடுறது.** Client code-லயோ ஒரு `NEXT_PUBLIC_` variable-லயோ இருக்குற secret public தான். Secrets-ஐ server-side environment variables-லயும், git ignore பண்ற ஒரு `.env` file-லயும் வைங்க.

**Database-ஐ திறந்தே விடுறது.** Row-level security இல்லாத ஒரு Supabase table-ஐ, உங்க app-ஓட public key இருக்குற யார் வேணாலும் படிக்கலாம், பெரும்பாலும் மாத்தவும் முடியும்; அந்த key ஒவ்வொரு visitor-கிட்டயும் இருக்கு.

**முடிவில்லாத "fix it" loops.** ரெண்டு correction-க்கு அப்புறமும் அதே bug இருந்தா, நிறுத்துங்க. `/clear` run பண்ணுங்க, அப்புறம் exact steps, எதிர்பார்த்த result, உண்மையான result, நீங்க கத்துக்கிட்டது எல்லாம் வச்சு ஒரே ஒரு புது prompt எழுதுங்க, எந்த change-க்கும் முன்னாடி காரணத்தை கேளுங்க.

## Practice பண்ணுங்க

இந்த guided task-ஐ சுமார் 45 நிமிஷத்துல பண்ணுங்க. உங்களுக்கு ஒரு paid plan அல்லது ஒரு API account வேணும்.

1. ஒரு புது folder உருவாக்கி, `git init` run பண்ணுங்க, அப்புறம் `claude`.
2. Worked example-ல வர்ற Nisha-வோட bill splitter-க்கு, உங்க சொந்த வார்த்தைகள்ல, ஒரு out-of-scope list-ஓட `SPEC.md` எழுதுங்க.
3. `/init` run பண்ணுங்க, `CLAUDE.md`-ஐ திறந்து run, test commands-ஐயும் உங்க சொந்த rule ஒண்ணையும் சேருங்க. சின்னதா வைங்க.
4. `/plan` type பண்ணி முழு app-க்கும் ஒரு plan கேளுங்க. குறைஞ்சது ஒரு part-ஐ reject அல்லது simplify பண்ணுங்க, ஏன்னு ஒரு sentence எழுதுங்க.
5. Step one-ஐ மட்டும் build பண்ணுங்க. `/diff`-ஆல diff-ஐ படிங்க, page-ஐ 360 px wide-ல try பண்ணுங்க, commit பண்ணுங்க.
6. மூணு பேர் share பண்ற ₹1,000-ஐயும் சேர்த்து `splitBill`-க்கு tests கேளுங்க. அதுல "shares add up to the bill" மாதிரி ஒரு rule இருக்கான்னு check பண்ணுங்க.
7. மேல இருக்குற "Prompt-ஐ சரி பண்ணுங்க" exercise-ஐ பண்ணுங்க, அப்புறம் உங்க answers-ஐ model answers கூட compare பண்ணுங்க.
