## இது என்ன

எல்லா automation-உம் என்னைக்காவது fail ஆகும். ஒரு API down ஆகும், ஒரு token expire ஆகும், ஒரு customer தன் phone number-ஐ தப்பா type பண்ணுவாங்க, எவ்வளவு வேகமா அனுப்பலாம்னு ஒரு provider limit வைப்பாங்க. Fail **ஆகுமா**ங்குறது கேள்வி இல்ல, **எப்படி** fail ஆகுதுங்குறது தான். நல்லா build பண்ண automation பாதுகாப்பா fail ஆகும்: எதுவும் தொலையாது, எதுவும் ரெண்டு தடவை நடக்காது, என்ன பண்ணணும்னு சரியான ஆளுக்கு தெரியும்.

**Error handling**-னா ஒரு step fail ஆகும்போது, அல்லது ஒரு step "success" ஆனாலும் தப்பான ஏதோ ஒண்ணை return பண்ணும்போது, automation பண்ற எல்லாமே:

| வேலை | அதோட அர்த்தம் |
| --- | --- |
| **Retry** | Temporary-ஆ இருக்க வாய்ப்புள்ள errors-ஐ மறுபடியும் try பண்றது, மெதுவா, குறிப்பிட்ட தடவைகள் மட்டும் |
| **Stop** | தானா சரியாகாத errors-ஐ திரும்பத் திரும்ப try பண்ணாம இருக்கிறது; அவற்றை record பண்றது |
| **Alert** | ஒரு ஆளுக்கு, ஒரு தடவை, act பண்ண போதுமான details-ஓட சொல்றது |
| **Recover** | காரணம் சரியானதும், எதையும் ரெண்டு தடவை பண்ணாம, பாதுகாப்பா மறுபடியும் process பண்றது |
| **Record** | Review-க்கும் reruns-க்கும், ஒவ்வொரு item-க்கும் என்ன நடந்ததுன்னு ஒரு history வச்சிருக்கிறது |

இந்த அஞ்சு வேலைகளுக்கும் கீழ ரெண்டு ideas இருக்கு. முதல்ல, சரியான response **retry பண்ணா என்ன மாறும்**ங்குறதைப் பொறுத்தது: busy-ஆ இருக்குற server அடுத்த தடவை பதில் சொல்லலாம், தப்பான phone number எப்பவுமே சரியாகாது. ரெண்டாவது, "send" அல்லது "pay"-க்கான ஒரு call fail ஆனா, எதுவுமே அனுப்பப்படலை அல்லது pay ஆகலைன்னு எப்பவும் அர்த்தம் இல்ல. பெரும்பாலான நிஜ duplicates அதை மறக்கிறதால தான் வருது.

இந்த lesson, Bengaluru-ல ஒரு logistics startup-ஐ follow பண்ணுது; அவங்க delivery updates ரெண்டு தடவை போச்சு, rate limits-ல மாட்டிச்சு, ஒரு தடவை ஒரு நாள் முழுக்க நின்னுபோச்சு. Example tool n8n.

## இது எப்படி work ஆகுது

### Retry பண்ணா என்ன மாறும்னு வச்சு error-ஐ வகைப்படுத்துங்க

```flow
ஒரு error வருது -> Step data-வை படிக்க மட்டும் செஞ்சுதா?
Step data-வை படிக்க மட்டும் செஞ்சுதா? -[ஆமா]-> Temporary error-ஆ? | timeout, 429, 500 முதல் 504
Step data-வை படிக்க மட்டும் செஞ்சுதா? -[இல்லை]-> Outcome தெரியலையா? | send, pay அல்லது create-ல timeout அல்லது 500 முதல் 504
Outcome தெரியலையா? -[ஆமா]-> உங்க key வச்சு status-ஐ check பண்ணு | அப்புறம் அதே key-ஓட retry பண்ணு
Outcome தெரியலையா? -[இல்லை]-> Temporary error-ஆ?
Temporary error-ஆ? -[ஆமா]-> Backoff-ஓட retry பண்ணு | இன்னும் fail ஆனா needs attention
Temporary error-ஆ? -[இல்லை]-> ஒரு record பத்தினதா? | 400, 404, invalid data
ஒரு record பத்தினதா? -[ஆமா]-> Needs attention list | மீதியை தொடரு
ஒரு record பத்தினதா? -[இல்லை]-> Run-ஐ நிறுத்து | 401, 403, expire ஆன token; owner-க்கு alert பண்ணு
```

| வகை | Examples | என்ன பண்ணணும் |
| --- | --- | --- |
| **Temporary** | Network blips, rate limits (HTTP 429), ஒரு read-ல server errors (500 முதல் 504) | Throttle பண்ணுங்க, அப்புறம் backoff-ஓட, ஒரு cap வச்சு retry பண்ணுங்க |
| **Outcome தெரியாது** | எதையாவது send, pay அல்லது create பண்ற ஒரு step-ல timeout அல்லது 500 முதல் 504 | முதல்ல check பண்ணுங்க, அப்புறம் அதே key-ஓட மட்டும் retry பண்ணுங்க |
| **Permanent, ஒரு record** | Bad input (400), இல்லாத ஒரு record (404), "12345" மாதிரி ஒரு phone number | Reason-ஓட record பண்ணுங்க, மத்தவற்றை தொடருங்க |
| **Permanent, முழு workflow** | தப்பான அல்லது expire ஆன credentials (401, 403), delete ஆன ஒரு sheet | உடனே நிறுத்தி owner-க்கு alert பண்ணுங்க |
| **Logic** | Run success ஆகுது, ஆனா தப்பா ஏதோ பண்ணுது, உதாரணமா தப்பா map ஆன ஒரு field | Validation-உம் monitoring-உம் மட்டும் தான் இவற்றை பிடிக்கும் |

Status codes ஒரு ஆரம்பம் தான். ரெண்டு patterns இன்னும் அதிகமா சொல்லும்:

- **மத்த records போகும்போது, அதே record ஒவ்வொரு attempt-லயும் fail ஆகுது.** அப்போ பிரச்சனை அந்த record-ல தான், code 500-னு சொன்னாலும் கூட. சில APIs bad input-ல crash ஆகி server error-னு report பண்ணும். வழக்கமான retries-க்கு அப்புறம், அதை "needs attention"-க்கு அனுப்புங்க.
- **ஒண்ணுக்கு அப்புறம் ஒண்ணா, எல்லா record-உம் fail ஆகுது.** அப்போ பிரச்சனை service-ல அல்லது உங்க credentials-ல, records-ல இல்ல. 2,000 items-ஐ ஒவ்வொண்ணா fail ஆக விடாம, சீக்கிரமே நிறுத்துங்க.

### Timeouts-க்கு தெளிவான அர்த்தம் இல்ல

Timeout-னா நீங்க wait பண்றதை நிறுத்திட்டீங்கன்னு அர்த்தம், provider எதுவுமே பண்ணலைன்னு இல்ல. SMS போயிருக்கலாம், reply மட்டும் தொலைஞ்சிருக்கலாம். கண்மூடித்தனமா retry பண்ணா customer-க்கு அது ரெண்டு தடவை போகும். உதாரணமா, ஒரு 500-ஐயும் இதே மாதிரி எடுத்துக்கணும்னு Stripe-ஓட docs சொல்லுது: பணம் போயிருக்கலாம், போகாமலும் இருக்கலாம்.

பாதுகாப்பான pattern-ல மூணு பகுதிகள் இருக்கு:

1. **Call பண்றதுக்கு முன்னாடி attempt-ஐ record பண்ணுங்க.** ஒரு unique key-ஓட, "sending" status-ஓட ஒரு send-log row எழுதுங்க; அப்புறம் அதை "sent" அல்லது "failed"-ஆ update பண்ணுங்க.
2. **Provider support பண்ணா ஒரு idempotency key அனுப்புங்க.** Idempotency key-னா request கூட நீங்க அனுப்புற ஒரு unique value, அதை வச்சு provider ஒரு repeat-ஐ அடையாளம் கண்டுக்கும். உதாரணமா, Stripe ஒரு `Idempotency-Key` header-ஐ ஏத்துக்கும்: அதே key-ஓடயும் அதே details-ஓடயும் retry பண்ணா, மறுபடியும் charge பண்ணாம முதல் result-ஐயே return பண்ணும். அதோட v1 API docs அதே key-ஓட 24 hours-க்குள்ள retry பண்ண சொல்லுது (November 2026 நிலவரப்படி). உங்க provider-ஓட docs-ஐ check பண்ணுங்க; சிலர் இதைத் தருவாங்க, சிலர் தர மாட்டாங்க.
3. **Timeout ஆனா, retry பண்றதுக்கு முன்னாடி பாருங்க.** Provider-கிட்ட status API இருந்தா, message அல்லது payment இருக்கான்னு கேளுங்க. இல்லைன்னா மட்டும் retry பண்ணுங்க. Retry-க்கு ஒருநாளும் புது key generate பண்ணாதீங்க: புது key provider-கிட்ட "இது ஒரு புது request"-னு சொல்லும்.

Provider-கிட்ட idempotency key-உம் இல்ல, status lookup-உம் இல்லைன்னா, ஒவ்வொரு action-க்கும் எந்த தப்பு மலிவுன்னு முடிவு பண்ணுங்க. ரெண்டு தடவை போன delivery update எரிச்சல் தான்; ரெண்டு தடவை குடுத்த refund நிஜ பணம். பணம் சம்பந்தப்பட்ட எதுக்கும், outcome தெரியாத ஒண்ணை auto-retry பண்ணாதீங்க: ஒரு ஆள் check பண்ண "needs attention"-ல போடுங்க.

### Retry பண்றதுக்கு முன்னாடி throttle பண்ணுங்க

தெரிஞ்ச ஒரு daily peak-ல வர்ற rate limits (HTTP 429) கெட்ட நேரம் இல்ல: உங்க plan அனுமதிக்கிறதை விட வேகமா அனுப்புறீங்க. **Provider-ஓட documented limit-ஐ விட வேகமா அனுப்பாதீங்க**, அப்போ 429s அரிதா தான் வரும்; retries-ஐ ஒரு safety net-ஆ வச்சுக்கோங்க.

உதாரணமா, plan ஒரு second-க்கு 10 messages அனுமதிக்குதுன்னு வச்சுக்கோங்க. ஒரு second gap-ஓட 8 messages-ஆ batches அனுப்புங்க: அதே account-ஐ use பண்ற மத்த workflows-க்கு அது 20 percent headroom விடும். அப்போ 3,000 evening messages-க்கு சுமார் 375 seconds ஆகும், ஆறு நிமிஷத்துக்கு கொஞ்சம் மேல. n8n-ல இதை HTTP Request node-ஓட **Batching** option (Items per Batch, Batch Interval) வச்சு பண்ணலாம், அல்லது ஒரு **Loop Over Items** node-உம் loop-க்குள்ள ஒரு **Wait** node-உம் வச்சு பண்ணலாம்.

### Backoff, jitter-ஓட retry

Temporary errors-ஐ சில தடவை retry பண்ணுங்க, ஒவ்வொரு தடவையும் இன்னும் அதிக நேரம் wait பண்ணுங்க. அப்புறம் **jitter** சேருங்க, அதாவது ஒவ்வொரு wait-லயும் ஒரு random extra நேரம். அது இல்லைன்னா, 7 pm-ல 500 items fail ஆகும்போது, 500-உம் சரியா அதே second-ல retry பண்ணி, மறுபடியும் ஒண்ணா fail ஆகும்.

```flow
dir: LR
Attempt 1 -[fail ஆகுது]-> 5 முதல் 10 s wait -> Attempt 2 -[fail ஆகுது]-> 10 முதல் 20 s wait -> Attempt 3 -[fail ஆகுது]-> 20 முதல் 40 s wait -> Attempt 4 -[fail ஆகுது]-> Needs attention, alert
```

ஒரு நியாயமான default: ஒவ்வொரு தடவையும் wait-ஐ double பண்ணுங்க, ஒரு random 0 முதல் 100 percent சேருங்க, 3 முதல் 5 attempts-க்கு அப்புறம் நிறுத்துங்க. ஒரு 429 கூட ஒரு **Retry-After** header வரலாம், seconds-ஆ அல்லது ஒரு date-ஆ. உங்க சொந்த number-க்கு பதிலா அதை use பண்ணுங்க.

**n8n உங்களுக்கு என்ன தருது.** ஒவ்வொரு node-லயும் **Max Tries**, **Wait Between Tries (ms)**-ஓட ஒரு **Retry On Fail** setting இருக்கு. November 2026 நிலவரப்படி, Max Tries அதிகபட்சம் 5, wait அதிகபட்சம் 5,000 ms-னு n8n-ஓட docs சொல்லுது, HTTP Request node உங்களுக்காக Retry-After-ஐ படிக்காது. ஒரே ஒரு wait setting தான் இருக்கு, அதனால wait வளராது. ஒரு network blip-க்கு அது பரவாயில்ல. நீளமான, வளர்ற waits-க்கு, retry-ஐ நீங்களே build பண்ணுங்க: node-ஓட error output-ஐ ஒரு Wait node-க்கு route பண்ணி திரும்ப loop பண்ணுங்க, அது நிக்கிறதுக்கு ஒரு counter வச்சு.

### Idempotency: ரெண்டு தடவை run பண்ணாலும் safe

ஒரு step-ஐ ரெண்டு தடவை run பண்ணா, ஒரு தடவை run பண்ண அதே effect தான் வரும்னா, அது **idempotent**. Retries-உம் reruns-உம் steps-ஐ repeat பண்ணும், அதனால எதையாவது create பண்ற ஒவ்வொரு step-க்கும் இது தேவை.

ஒவ்வொரு action-க்கும் ஒரு **unique key**-ஓட ஒரு send log வச்சுக்கோங்க. Act பண்றதுக்கு முன்னாடி, அந்த key ஏற்கனவே "sent"-னு mark ஆகியிருக்கான்னு check பண்ணுங்க; ஆகியிருந்தா skip பண்ணுங்க. Key-ஐ **action எதைப் பத்தினதோ அதுல இருந்து** தேர்ந்தெடுங்க, அப்போ அதே real-world action-க்கு எப்பவும் அதே key வரும்:

| Action | நல்ல key | Bad key, ஏன் |
| --- | --- | --- |
| Delivery update SMS | Order id plus status, உதாரணமா ORD-4471 plus "out for delivery" | Run id: ஒவ்வொரு rerun-க்கும் புதுசா ஒண்ணு வரும், அதனால எதுவுமே skip ஆகாது |
| Monthly fee reminder | Member id plus billing month | Member id மட்டும்: அது அடுத்த மாச reminder-ஐ block பண்ணிடும் |
| Ledger-ல invoice | Supplier-ஓட invoice number | Process பண்ண நேரம்: ஒவ்வொரு தடவையும் unique, அதனால எதையும் பிடிக்காது |

ரெண்டு runs overlap ஆக முடியும்னா, ஒரு check-க்கு அப்புறம் ஒரு action வந்தாலும் race ஆகலாம்: ரெண்டு runs-உம் check பண்ணும், ரெண்டுக்கும் எதுவும் தெரியாது, ரெண்டும் அனுப்பும். அதே key-ஓட ரெண்டாவது row-ஐ மறுக்கிற ஒரு store-ல (உதாரணமா unique constraint இருக்குற ஒரு database table), "sending" row-ஐ முதல்ல எழுதினா, அந்த gap மூடிடும்.

### திரும்ப வர்றதை validate பண்ணுங்க

Green tick-னா call return ஆச்சுன்னு மட்டும் தான் அர்த்தம். Response அர்த்தமுள்ளதான்னு check பண்ணுங்க: எதிர்பார்த்த list காலியா இல்ல, தேவையான fields இருக்கு, ஒரு "200 OK" body-ல error message இல்ல. வழக்கமா 8,000 rows இருக்குற ஒரு export-ல ஒண்ணுமே இல்லைன்னா, "successfully" எதுவும் பண்ணாம இருக்கிறதுக்கு பதிலா, அதை error-ஆ எடுத்து நிறுத்துங்க. n8n-ல, ஒரு IF node bad responses-ஐ ஒரு **Stop and Error** node-க்கு route பண்ணலாம், அது வேணும்னே run-ஐ fail பண்ணும்.

### Bad records-ஐ தனியா பிரிங்க, ஆனா எல்லாமே fail ஆனா நிறுத்துங்க

300-ல ஒரு bad item மீதி 299-ஐ நிறுத்தக் கூடாது. Items-ஐ தனித்தனியா process பண்ணி, ஒவ்வொரு failure-ஐயும் அதோட reason-ஓட ஒரு "needs attention" list-ல எழுதுங்க; இதை சில சமயம் **dead-letter queue**-னு சொல்வாங்க. n8n-ல, node-ஓட **On Error**-ஐ **Continue (using error output)**-ஆ set பண்ணி, அந்த output-ஐ list கூட connect பண்ணுங்க. யாராவது அந்த records-ஐ சரி பண்ணி, அப்புறம் reprocess பண்ணுவாங்க. எதுவும் சத்தம் இல்லாம தொலையாது.

எதிர் case-க்கு ஒரு **circuit breaker** தேவை: failures குவியும்போது run-ஐ pause பண்ற ஒரு rule, உதாரணமா தொடர்ந்து 20 failures, அல்லது கடைசி 50 items-ல பாதிக்கு மேல. அது இல்லைன்னா, ஒரு outage 2,000 dead-letter rows-ஆவும் 2,000 alerts-ஆவும் மாறிடும்.

### உதவுற alerts

| Weak alert | Useful alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. SMS provider token expire ஆயிடுச்சு. Settings, Credentials, SMS provider-ல அதை renew பண்ணிட்டு rerun பண்ணுங்க; அனுப்பின messages skip ஆகும். Run link: ..." |

Owner உண்மையிலேயே பார்க்குற இடத்துக்கு அனுப்புங்க, உதாரணமா email, Slack, Teams அல்லது WhatsApp. Repeats-ஐ group பண்ணுங்க, அப்போ ஒரு outage-க்கு 500 இல்ல, ஒரே ஒரு message தான் போகும்.

n8n-ல, ஒரு **Error Trigger** node-ல start ஆகுற ஒரு தனி **error workflow** create பண்ணி, ஒவ்வொரு workflow-ஓட Settings-லயும் அதை தேர்ந்தெடுங்க. ஒரு automatic execution fail ஆகும்போது அது run ஆகும். நீங்க கையால test பண்ணும்போது அது run ஆகாது, அதனால ஒரு நிஜ scheduled அல்லது webhook run வச்சு test பண்ணுங்க.

### Errors மட்டும் இல்ல, volume-ஐயும் monitor பண்ணுங்க

எல்லாத்தையும் விட அதிக ஆபத்தான failure-ல error-ஏ இருக்காது. ஒரு நாளைக்கு process ஆன items-ஐயும் failures-ஐயும் track பண்ணுங்க. "1,000-க்கு குறைவு" மாதிரி ஒரு fixed threshold ஒவ்வொரு அமைதியான Sunday-லயும் fire ஆகும், பாதி உடைஞ்ச ஒரு நாளை miss பண்ணும். அதுக்கு பதிலா **அதே weekday-ஓட சமீபத்திய average** கூட compare பண்ணுங்க, உதாரணமா "8 pm-க்குள்ள கடைசி நாலு Tuesdays-ஓட average-ல பாதிக்கு குறைவா அனுப்பியிருந்தா alert பண்ணு", அந்த rule-ஐ மாசா மாசம் review பண்ணுங்க.

### n8n-ல என்ன use பண்றது

| வேலை | n8n feature |
| --- | --- |
| ஒரு blip-க்கு சின்ன retry | Node Settings, Retry On Fail |
| நீளமான அல்லது வளர்ற waits | Error output-ல இருந்து ஒரு Wait node-க்கு, ஒரு counter-ஓட திரும்ப loop |
| Rate limit-க்குள்ள இருக்க | HTTP Request Batching, அல்லது ஒரு Wait node-ஓட Loop Over Items |
| ஒரு bad record-ஐ தாண்டி தொடர | On Error-ஐ Continue (using error output)-ஆ set பண்றது |
| முழு run-ஐ நிறுத்த | On Error-ஐ Stop Workflow-ஆ set பண்றது, அல்லது ஒரு Stop and Error node |
| Fail ஆன எந்த run-க்கும் alert | Error Trigger node-ல start ஆகுற ஒரு error workflow |
| Duplicates, dead letters | உங்க send log-ல ஒரு lookup, failed records-க்கு ஒரு sheet அல்லது table |

### Ownership-உம் ஒரு runbook-உம்

ஒவ்வொரு automation-க்கும் பேர் சொல்லப்பட்ட ஒரு owner-உம், ஒரு சின்ன runbook-உம் இருக்கணும்: அது என்ன பண்ணுது, பொதுவான failures, ஒவ்வொண்ணையும் எப்படி சரி பண்றது, பாதுகாப்பா எப்படி rerun பண்றது.

## ஒரு worked example

Bengaluru-ல ஒரு logistics startup, customers-க்கு SMS-ல delivery updates அனுப்பி, order system-ஐ update பண்ற ஒரு automation-ஐ run பண்ணுது: ஒரு நாளைக்கு சுமார் 8,000 messages, அதுல பெரும்பாலானது 6 pm-ல இருந்து 9 pm வரை. கீழ இருக்குற numbers ஒரு typical முதல் மாசத்தோட illustration தான், அளந்த results இல்ல.

**முதல் மாசம் மோசமா போச்சு:**

| பிரச்சனை | காரணம் |
| --- | --- |
| Evening peaks-ல messages fail ஆச்சு | Workflow முடிஞ்ச வரை வேகமா அனுப்புச்சு, SMS provider அதை rate-limit பண்ணுச்சு (HTTP 429) |
| சில customers-க்கு ரெண்டு messages போச்சு | Fail ஆன ஒரு run-ஐ கையால rerun பண்ணாங்க, அது முன்னாடி அனுப்பின messages-ஐ மறுபடியும் அனுப்புச்சு; timeout ஆன sends கண்மூடித்தனமா retry ஆச்சு |
| ஒரு நாள் எதுவுமே போகல, error-உம் இல்ல | Order system-க்கான ஒரு login token expire ஆயிருந்துச்சு; export step சத்தமா fail ஆகாம ஒரு காலி list-ஐ return பண்ணுச்சு |

**Fixes:**

1. **Plan-ஓட limit-க்கு throttle:** provider-ஓட documented rate-க்கு கீழ batches, நடுவுல ஒரு wait.
2. 429s-ல **backoff, jitter-ஓட retries**, Retry-After இருந்தா அதை use பண்ணி, அதிகபட்சம் நாலு attempts, அப்புறம் "needs attention" sheet. ஒரு send-ல timeout அல்லது 500 முதல் 504 வந்தா, அது முதல்ல fix 3-ல இருக்குற status check வழியா போகும்.
3. **Order id plus status வச்சு key பண்ண ஒரு send log.** ஒவ்வொரு message-உம் call-க்கு முன்னாடி "sending"-ஆ எழுதப்படும். ஒரு rerun "sent"-னு mark ஆன எதையும் skip பண்ணும். Timeout-க்கு அப்புறம், மறுபடியும் அனுப்புறதுக்கு முன்னாடி workflow அந்த key வச்சு provider-ஓட delivery status-ஐ check பண்ணும்.
4. **Export-ஐ validate பண்றது.** காலியான அல்லது ரொம்ப சின்ன export இப்போ green-ஆ முடியாம, "order export 0 rows return பண்ணுச்சு; order system login-ஐ check பண்ணுங்க"-னு சொல்லி run-ஐ நிறுத்தும். சத்தம் இல்லாத அந்த நாளை பிடிச்சிருக்கக் கூடிய fix இது தான்.
5. **Credentials errors run-ஐ உடனே நிறுத்தும்**, token-ஐ எங்க renew பண்ணணும்னு சொல்லி owner-க்கு alert பண்ணும்.
6. **ஒரு circuit breaker:** தொடர்ந்து 20 failed sends வந்தா run pause ஆகி, ஒரு alert அனுப்பும்.
7. **8 pm-ல ஒரு volume check**, அதே weekday-ஓட கடைசி நாலு நாட்களோட average கூட compare பண்ணி, 50 percent-க்கு கீழ போனா alert பண்ணும்.

**அடுத்த மாசம் (illustrative):**

| அளவு | மாசம் 1 | மாசம் 2 |
| --- | --- | --- |
| Duplicate messages | சுமார் 900 | 3, எல்லாமே status lookup-ஏ down-ஆ இருந்தப்போ வந்த timeouts-க்கு அப்புறம் |
| Rate limits-ஆல தொலைஞ்ச messages | சுமார் 1,200 | 0; கொஞ்சம் 429s, எல்லாமே retry-ல அனுப்பப்பட்டுச்சு |
| அடுத்த login expiry-ஐ சரி பண்ண ஆன நேரம் | சுமார் 9 hours (ஒரு customer தான் முதல்ல complain பண்ணாங்க) | 20 minutes (என்ன பண்ணணும்னு alert சொல்லுச்சு) |
| Attention தேவைப்பட்ட records | தெரியாது | 35, ஒவ்வொண்ணும் ஒரு reason-ஓட, எல்லாமே ஒரு நாளுக்குள்ள சரி பண்ணப்பட்டுச்சு |

என்ன நடந்ததுன்னு provider-ஆல சொல்ல முடியலைன்னா, ஒரு அரிய duplicate-க்கும் ஒரு அரிய missed update-க்கும் நடுவுல நீங்க தேர்ந்தெடுக்கணும். Delivery updates-க்கு team duplicate-ஐ தேர்ந்தெடுத்துச்சு.

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்தையும் retry பண்றது.** Permanent errors-ஐ சரி பண்ணணும்; ஒவ்வொரு தடவையும் fail ஆகுற record "needs attention"-ல தான் இருக்கணும்.
- **Timeout ஆன send-ஐ கண்மூடித்தனமா retry பண்றது.** முதல் attempt work ஆயிருக்கலாம். முதல்ல உங்க key வச்சு check பண்ணுங்க.
- **ஒவ்வொரு attempt-க்கும் ஒரு புது key.** ஒரு run id அல்லது timestamp ஒவ்வொரு retry-ஐயும் புதுசா காட்டும், அதனால எதுவுமே skip ஆகாது.
- **Throttling-க்கு பதிலா retries.** தினமும் அதே மணி நேரத்துல 429s வந்தா, வேகத்தை குறைங்க; இன்னும் கடுமையா retry மட்டும் பண்ணாதீங்க.
- **Jitter-உம் cap-உம் இல்லாத fixed waits.** எல்லாமே ஒரே நேரத்துல retry ஆகும், outage இன்னும் மோசமாகும், நீங்க block ஆகலாம்.
- **Green run-ஐ நம்புறது.** காலியான அல்லது விசித்திரமான "successful" responses-ஐ validate பண்ணுங்க.
- **ஒரு bad item batch-ஐ நிறுத்துது, அல்லது ஒரு dead service ஒவ்வொரு item-ஐயும் fail பண்ணுது.** Records-ஐ தனியா பிரிங்க, ஆனா failures குவியும்போது run-ஐ நிறுத்துங்க.
- **Details இல்லாத alerts, அல்லது 500 alerts.** என்ன உடைஞ்சுது, என்ன பண்ணணும்னு ஒரு தடவை சொல்லுங்க.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற n8n-ஓட error handling guide-ஐ படிங்க, N8N102 course-ல error-handling பகுதியை மறுபடியும் பாருங்க.

1. **Retries.** வேணும்னே fail ஆகுற ஒரு endpoint-க்கு ஒரு HTTP Request node-ஐ point பண்ணுங்க (உதாரணமா 503 return பண்ற உங்க சொந்த சின்ன webhook workflow). Retry On Fail-ஐ on பண்ணி, retries உண்மையிலேயே run ஆச்சான்னு execution log-ல confirm பண்ணுங்க. அப்புறம் error output, ஒரு Wait node, ஒரு counter வச்சு ஒரு நீளமான retry-ஐ build பண்ணுங்க.
2. **Throttle.** 50 test items-ஐ timed batches-ஆ அனுப்பி, timing உங்க plan கூட match ஆகுதான்னு check பண்ணுங்க.
3. **Duplicates, dead letters.** ஒரு unique key-ஓட ஒரு send log, "sending" அப்புறம் "sent" status, ஒரு "needs attention" sheet சேருங்க. Workflow-ஐ ரெண்டு தடவை run பண்ணி, எதுவும் ரெண்டு தடவை போகலைன்னு காட்டுங்க.
4. **Alerts, checks.** Error Trigger node-ஓட ஒரு error workflow-ஐயும் ஒரு useful alert-ஐயும், ஒரு empty-result check-ஐயும், ஒரு same-weekday volume check-ஐயும் create பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு temporary error, ஒரு permanent error, ஒரு bad item, ஒரு காலி input வச்சு உங்க workflow-ஐ நாலு வழியில உடைக்க முடியும், ஒவ்வொண்ணுக்கும் சரியான behaviour-ஐ காட்ட முடியும், duplicates இல்லாம அதை rerun பண்ண முடியும்.
