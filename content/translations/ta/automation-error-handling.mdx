## இது என்ன

எல்லா automation-உம் என்னைக்காவது fail ஆகும். API down ஆகும், token expire ஆகும், customer phone number-ஐ தப்பா type பண்ணுவாங்க, provider எவ்வளவு வேகமா அனுப்பலாம்னு limit போடும். கேள்வி fail ஆகுமா இல்லையான்னு இல்ல, **எப்படி** fail ஆகுதுங்கறது தான். நல்லா கட்டின automation பாதுகாப்பா fail ஆகும்: எதுவும் தொலையாது, எதுவும் ரெண்டு தடவை நடக்காது, சரியான ஆளுக்கு என்ன பண்ணணும்னு தெரியும்.

**Error handling** என்பது ஒரு step fail ஆகும்போது automation பண்ற எல்லாமே:

| வேலை | அர்த்தம் |
| --- | --- |
| **Retry** | Temporary-ஆ இருக்க வாய்ப்பு உள்ள errors-ஐ மறுபடி try பண்றது |
| **Stop** | தானா சரியாகாத errors-ஐ record பண்ணி, தொடர்ந்து try பண்ணாம இருக்கிறது |
| **Alert** | செயல்பட போதுமான details-ஓட ஒரு ஆளுக்கு சொல்றது |
| **Recover** | காரணத்தை சரி பண்ணின பிறகு, actions duplicate ஆகாம பாதுகாப்பா மறுபடி process பண்றது |
| **Record** | பின்னாடி பார்க்க, என்ன நடந்ததுங்கற history-ஐ வச்சிருக்கிறது |

இந்த lesson Bengaluru-ல ஒரு logistics startup-ஐ follow பண்ணுது. அவங்க delivery-update automation duplicate messages அனுப்புச்சு, rate limits-ல மாட்டுச்சு, ஒரு நாள் முழுக்க எதுவுமே பண்ணல. கடைசியில உங்க சொந்த automations-ஐ பாதுகாப்பா fail ஆக வைக்க முடியும்.

## இது எப்படி work ஆகுது

### Errors-ல என்னென்ன வகை இருக்குன்னு தெரிஞ்சுக்கோங்க

```flow
ஒரு error வருது -> தற்காலிகமா இருக்க வாய்ப்பு இருக்கா? | timeout, 429, 500-504
தற்காலிகமா இருக்க வாய்ப்பு இருக்கா? -[ஆமா]-> Backoff-ஓட retry | அப்பவும் fail ஆனா alert
தற்காலிகமா இருக்க வாய்ப்பு இருக்கா? -[இல்லை]-> ஒரு தப்பான record பத்தியா? | 400, 404, invalid data
ஒரு தப்பான record பத்தியா? -[ஆமா]-> Record-ஐ "needs attention"-ல போடு | மீதியை தொடரு
ஒரு தப்பான record பத்தியா? -[இல்லை]-> முழு workflow பத்தியா? | 401, 403, expire ஆன token
முழு workflow பத்தியா? -[ஆமா]-> உடனே நிறுத்து | fix-ஓட owner-க்கு alert
```

| வகை | Examples | என்ன பண்ணணும் |
| --- | --- | --- |
| **Temporary** | Network blips, timeouts, rate limits (HTTP 429), server errors (500 முதல் 504) | Backoff-ஓட retry |
| **Permanent** | தப்பான credentials (401, 403), தப்பான input (400), இல்லாத record (404), invalid data | நிறுத்து, record பண்ணு, காரணத்தை சரி பண்ணு |
| **Logic** | Automation ஓடுச்சு ஆனா தப்பான வேலை பண்ணுச்சு, உதாரணம்: ஒரு field தப்பா map ஆகியிருக்கு | Checks-ம் monitoring-ம் மட்டும் தான் இதை பிடிக்கும் |

### Backoff-ஓட retry

Temporary errors-ஐ சில தடவை retry பண்ணுங்க, ஒவ்வொரு தடவையும் அதிக நேரம் காத்திருந்து. அப்போ தான் திணறிட்டு இருக்குற service-ஐ நாம தொடர்ந்து தாக்க மாட்டோம்:

```flow
dir: LR
Attempt 1 -[fail ஆச்சு]-> 5 s wait பண்ணு -> Attempt 2 -[fail ஆச்சு]-> 30 s wait பண்ணு -> Attempt 3 -[fail ஆச்சு]-> 2 min wait பண்ணு -> Attempt 4 -[fail ஆச்சு]-> ஒரு ஆளுக்கு alert
```

Service **Retry-After** header அனுப்புனா அதை மதிங்க: எவ்வளவு நேரம் காத்திருக்கணும்னு அது சரியா சொல்லும். Retries-ஓட எண்ணிக்கைக்கு எப்பவும் ஒரு cap வைங்க.

### Idempotency: ரெண்டு தடவை ஓடினாலும் safe

Retries-உம் manual reruns-உம் actions-ஐ repeat பண்ணலாம். Invoice, payment, message மாதிரி ஏதாவது உருவாக்குறதுக்கு முன்னாடி, order id plus status மாதிரி ஒரு unique key வச்சு, அது ஏற்கனவே இருக்கான்னு check பண்ணுங்க. இருந்தா skip பண்ணுங்க. அப்போ retries-ஓ reruns-ஓ duplicates உருவாக்காது.

### உதவுற alerts

| வலுவில்லாத alert | Useful alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. SMS provider token expire ஆகிடுச்சு. Settings, Credentials, SMS provider-ல renew பண்ணுங்க. Run link: ..." |

Owner உண்மையா பார்க்குற channel-க்கு alerts அனுப்புங்க: email, Slack, Teams, WhatsApp மாதிரி. Repeated alerts-ஐ group பண்ணுங்க, அதனால ஒரு outage ஒரு message அனுப்பும், 500 இல்ல.

### Dead-letter queue

Permanent-ஆ fail ஆன records **"needs attention"** list-க்கு போகும், இதை dead-letter queue-னும் சொல்வாங்க, காரணத்தோட. யாராவது அவற்றை சரி பண்ணி பின்னாடி மறுபடி process பண்ணுவாங்க. எதுவும் சத்தமில்லாம தொலையாது.

### Partial failures

300 items process பண்ணும்போது, ஒரு தப்பான item மத்த 299-ஐ நிறுத்தக்கூடாது. Items-ஐ தனித்தனியா process பண்ணுங்க, failures-ஐ சேகரிச்சு, கடைசியில report பண்ணுங்க.

### Monitoring

தினமும் runs, failures, process ஆன items-ஐ track பண்ணுங்க. திடீர்னு **zero** items process பண்ற workflow பெரும்பாலும் உடைஞ்சிருக்கும், எந்த error-உம் இல்லாம கூட, உதாரணமா export காலியா வந்ததால.

### Ownership, runbook

ஒவ்வொரு automation-க்கும் ஒரு பேர் சொல்லப்பட்ட owner-உம், ஒரு சின்ன runbook-உம் இருக்கணும்: அது என்ன பண்ணுது, பொதுவான failures என்னென்ன, ஒவ்வொண்ணையும் எப்படி சரி பண்றது.

## ஒரு worked example

Bengaluru-ல ஒரு logistics startup ஒரு automation ஓட்டுது. அது customers-க்கு SMS-ல delivery updates அனுப்பி, order system-ஐயும் update பண்ணுது: ஒரு நாளைக்கு சுமார் 8,000 messages.

**முதல் மாசம் மோசமா போச்சு:**

| Problem | காரணம் |
| --- | --- |
| மாலை peak நேரத்துல messages fail ஆச்சு | SMS provider workflow-ஐ rate-limit பண்ணுச்சு (HTTP 429) |
| சில customers-க்கு ரெண்டு messages போச்சு | Fail ஆன run-ஐ கையால rerun பண்ணினாங்க, முன்னாடி அனுப்பின messages மறுபடி போச்சு |
| ஒரு நாள் எதுவுமே அனுப்பல, error-உம் இல்ல | Login token expire ஆகிடுச்சு; step சத்தமா fail ஆகாம, empty result return பண்ணுச்சு |

**Fixes:**

1. SMS provider-ஓட 429, 5xx responses-ல **backoff-ஓட retries**, அதோட Retry-After header-ஐ மதிச்சு, அதிகபட்சம் நாலு attempts.
2. ஒவ்வொரு message-க்கும் **ஒரு unique key**, order id plus status, அனுப்புறதுக்கு முன்னாடி check பண்ணி, அதனால reruns duplicates அனுப்பாது.
3. **Expire ஆன அல்லது invalid credentials run-ஐ உடனே நிறுத்தும்**, retry பண்றதுக்கு பதிலா "SMS provider-க்கு token expire ஆகிடுச்சு, Settings, Credentials-ல renew பண்ணுங்க"ன்னு owner-க்கு alert.
4. **Fail ஆன records "needs attention" sheet-க்கு போகும்**, காரணத்தோட; சரி பண்ணினதுக்கு அப்புறம் ஒரு button அவற்றை மறுபடி process பண்ணும்.
5. **தினசரி check**: இரவு 8 மணிக்குள்ள 1,000-க்கு குறைவான messages தான் போயிருந்தா alert அனுப்பும்.

| Rate limits-ல தொலைஞ்ச messages | சுமார் 1,200 | 0 (எல்லாமே retry ஆச்சு) |

## பொதுவான தப்புகள்

- **எல்லாத்தையும் retry பண்றது.** Permanent errors-ஐ சரி பண்ணணும், retry இல்ல.
- **Duplicate protection இல்லாதது.** Retries-உம் reruns-உம் double actions உருவாக்கும்.
- **Details இல்லாத alerts.** "Workflow failed"ங்கறதை வச்சு எதுவும் பண்ண முடியாது.
- **ஒரு தப்பான item முழு batch-ஐயும் நிறுத்துறது.** Items-ஐ தனித்தனியா handle பண்ணுங்க.
- **Errors-ஐ மட்டும் பார்க்கிறது.** எதுவும் பண்ணாத workflow healthy-ஆ தெரியலாம்.
- **Cap-உம் waits-உம் இல்லாம retry பண்றது.** Outage-ஐ இன்னும் மோசமாக்கும், நீங்க block ஆகவும் வாய்ப்பிருக்கு.

## Practice

கீழ link பண்ணியிருக்குற n8n-ஓட error handling guide-ஐ படிங்க, N8N102 course-ல error-handling பகுதியையும் மறுபடி பாருங்க.

1. **Retries.** ஒரு workflow-ல ஒரு API step-க்கு backoff-ஓட retries சேருங்க, வேணும்னே fail ஆகுற ஒரு endpoint-ஓட test பண்ணுங்க.
2. **Duplicates, dead letters.** ஒரு idempotency check-ம், permanent failures-க்கு ஒரு "needs attention" list-உம் சேருங்க.
3. **Alerts.** Workflow, step, record, error-ஐ சொல்ற ஒரு alert-ஐயும், தினசரி "items ரொம்ப குறைவு" check-ஐயும் உருவாக்குங்க.

**இது முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க workflow-ஐ மூணு விதமா உடைக்க முடியும்போது, temporary error, permanent error, தப்பான item, ஒவ்வொண்ணுக்கும் சரியான behaviour-ஐ காட்ட முடியும்போது.
