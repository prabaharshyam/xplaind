## இது என்ன

Model தேர்ந்தெடுக்குறதுன்னா, உங்க application-ஓட ஒவ்வொரு பகுதியையும் எந்த language model, எந்த provider-ஓடது, எந்த size-ல இயக்கும்னு முடிவு பண்றது. நூற்றுக்கணக்கான options இருக்கு: API-க்கு பின்னாடி hosted models, நீங்களே run பண்ற open-weight models. ஒவ்வொரு மாசமும் புதுசு வருது, ஒவ்வொண்ணும் record scores பத்தி ஒரு press release-ஓட.

அந்த scores **benchmarks**-ல இருந்து வருது: school maths, general knowledge, code எழுதுறது மாதிரி ஒரு skill-ஐ அளக்குற fixed public test sets. ஒரு **leaderboard**, தேர்ந்தெடுத்த benchmarks-ஓட scores-ஐ சேர்த்தோ, ரெண்டு anonymous answers-ல மக்கள் வாக்களிச்சோ models-ஐ rank பண்ணுது.

Benchmarks உபயோகமானவை தான், ஆனா அவை உங்க கேள்வியை விட வேற கேள்விக்கு பதில் சொல்லுது. அவை கேக்குறது "இந்த tests-ல எந்த model நல்லது?". உங்களுக்கு தெரியணும்: "என் task-ல, நான் தாங்கக்கூடிய price-லயும் speed-லயும், என் rules-க்குள்ள, எந்த model போதுமான அளவு நல்லது?" நம்பகமா தேர்ந்தெடுக்க நாலு steps இருக்கு.

```flow

எல்லா candidate models -> Hard requirements-ல filter பண்ணு | licence, data location, மொழிகள், price
Hard requirements-ல filter பண்ணு -> Public benchmarks வச்சு shortlist பண்ணு | 3 முதல் 5 models
Public benchmarks வச்சு shortlist பண்ணு -> உங்க சொந்த data-ல test பண்ணு | உங்க inputs, உங்க rubric
உங்க சொந்த data-ல test பண்ணு -> Quality, cost, speed பொருந்துதா?
Quality, cost, speed பொருந்துதா? -[இல்லை]-> Design-ஐ மாத்து | சின்ன task, நல்ல prompt, retrieval
Design-ஐ மாத்து -> உங்க சொந்த data-ல test பண்ணு
Quality, cost, speed பொருந்துதா? -[ஆமா]-> Launch பண்ணி monitor பண்ணு | models மாறும்போது திரும்ப check பண்ணு
```

## இது எப்படி work ஆகுது

**Step 1: Hard requirements-ல filter பண்ணுங்க.** சிலதை prompting-ஆல சரி பண்ண முடியாது. முதல்ல அவற்றை எழுதி வைங்க, ஒண்ணுல fail ஆகுற ஒவ்வொரு model-ஐயும் நீக்குங்க.

- **Licence, terms.** Commercial-ஆ use பண்ண முடியுமா? அதோட outputs-ஐ வச்சுக்க முடியுமா? சில open-weight licences, பெரிய companies-க்கு limits வச்சிருக்கு.
- **Data location, privacy.** இந்திய cloud region-லயோ உங்க சொந்த servers-லயோ run ஆகுமா? இந்தியாவோட data protection law-ஆலயும், banks-க்கு RBI rules-ஆலயும், இது நிறைய options-ஐ நீக்கிடலாம்.
- **மொழிகள்.** உங்க users எழுதுற மொழிகளை, கலந்த Hinglish உட்பட, handle பண்ணுமா?
- **Context length, speed, price.** உங்க நீளமான document-ஐ படிக்குமா? போதுமான வேகத்துல பதில் சொல்லுமா? ஒரு request-க்கான cost உங்க budget-ல பொருந்துமா?

**Step 2: Public benchmarks வச்சு shortlist பண்ணுங்க.** Test பண்ணத் தகுந்த 3 முதல் 5 candidates-ஐ தேர்ந்தெடுக்க benchmarks, leaderboards-ஐ use பண்ணுங்க; winner-ஐ தேர்ந்தெடுக்க இல்லை. இந்த limits-ஐ மனசுல வச்சு படிங்க:

- **Leaderboards தங்க tests-ஐ தேர்ந்தெடுக்குது.** ஆயிரக்கணக்கான benchmarks-ல ஒரு leaderboard கொஞ்சத்தை மட்டும் cover பண்ணுது, அந்த தேர்வு தான் யார் ஜெயிக்கிறாங்கன்னு முடிவு பண்ணும். பெரும்பாலானவை English, general knowledge பக்கம் சாய்ஞ்சிருக்கு.
- **சின்ன details scores-ஐ மாத்தும்.** ஒரே model, ஒரே benchmark-ல, prompt எப்படி எழுதப்பட்டுச்சு, எப்படி score பண்ணாங்கங்கிறதை பொறுத்து ரொம்ப வேற scores வாங்கினதை Hugging Face ஒருமுறை கண்டுபிடிச்சது. ஒரே மாதிரி அளந்த scores-ஐ மட்டும் compare பண்ணுங்க.
- **Saturation.** Top models எல்லாம் 100%-க்கு பக்கத்துல score பண்ணும்போது, ஒரு benchmark அவற்றை பிரிக்காது. Leaderboards saturated benchmarks-ஐ ஒரு வருஷம் ரெண்டு வருஷத்துக்கு ஒருமுறை மாத்துறாங்க.
- **Contamination.** Benchmark questions public, அதனால அவை web text-க்குள்ளயும் அப்புறம் training data-க்குள்ளயும் leak ஆகும். கேள்விகளை பார்த்த model ஞாபகத்துல இருந்து நல்லா score பண்ணும். Labs இதை ரெண்டு பொதுவான வழிகள்ல check பண்றாங்க: test-க்கும் training data-வுக்கும் இடையில பகிரப்பட்ட நீளமான வார்த்தை வரிசைகளை தேடுறது (n-gram overlap), test questions-ஐ model சந்தேகப்படுற அளவு எளிதா predict பண்ணுதான்னு பாக்குறது (low perplexity). பழைய, popular benchmarks-ல வர்ற scores-ஐ கவனமா எடுத்துக்குங்க.
- **Vote-based rankings**, சின்ன chats-ல பலர் எதை விரும்புறாங்கன்னு காட்டும்: பெரும்பாலும் smooth-ஆ, confident-ஆ, நல்ல formatting-ஓட இருக்குற answers. அது உங்க task-ஓட பொருந்தாம போகலாம்.

**Step 3: உங்க சொந்த data-ல test பண்ணுங்க.** முடிவு பண்றது இந்த step தான். 100 முதல் 300 real inputs-ஓட ஒரு test set உருவாக்குங்க; personal data anonymise பண்ணி, ஒவ்வொரு மொழியையும் ஒவ்வொரு வகை request-ஐயும் cover பண்ணி. எந்த outputs-ஐயும் பார்க்குறதுக்கு முன்னாடி ஒரு scoring rubric எழுதுங்க. Shortlist பண்ண ஒவ்வொரு model-ஐயும் ஒரே prompt-ஓட run பண்ணி, quality, cost, speed மூணையும் சேர்த்து record பண்ணுங்க. எப்படி score பண்றதுன்னு test sets, LLM judges lessons சொல்லுது.

ஒரு சின்ன harness, compare பண்றதை நியாயமா வச்சிருக்கும்:

```python
import json, time

def run(model_name, call_model, cases, score):
    """call_model(prompt) returns (text, cost_in_rupees). score(case, text) returns 0 to 1."""
    total, cost, slow = 0.0, 0.0, []
    for case in cases:
        start = time.time()
        text, rupees = call_model(case["input"])
        slow.append(time.time() - start)
        total += score(case, text)
        cost += rupees
    slow.sort()
    return {
        "model": model_name,
        "quality": round(total / len(cases), 3),
        "cost_per_1000": round(cost / len(cases) * 1000, 1),
        "p95_seconds": round(slow[int(len(slow) * 0.95) - 1], 2),
    }

cases = [json.loads(line) for line in open("helpdesk_test.jsonl")]
# results = [run(name, fn, cases, score) for name, fn in candidates.items()]
```

**Step 4: Launch பண்ணி monitor பண்ணுங்க.** ஒவ்வொரு வாரமும் real conversations-ஐ sample பண்ணி score பண்ணுங்க. Provider model-ஐ update பண்ணும்போது, prices மாறும்போது, மலிவான model வரும்போது உங்க test set-ஐ திரும்ப run பண்ணுங்க. மாறுறதை பாதுகாப்பா ஆக்குறது உங்க test set தான்.

**Build or buy.** Hosted APIs ஆரம்பிக்க வேகம், உங்களுக்காக scale ஆகும், பெரும்பாலும் strongest models-உம் அவை தான். Open-weight models, அதிக volume-ல data மேலயும் cost மேலயும் உங்களுக்கு control கொடுக்கும், ஆனா servers-ஐ நீங்களே நடத்தணும். பல teams ஒரு API-ல ஆரம்பிச்சு, அப்புறம் தங்க test set போதுமான அளவு நல்லதுன்னு நிரூபிச்சதும், அதிக volume உள்ள, எளிய steps-ஐ ஒரு சின்ன open model-க்கு மாத்துறாங்க.

## ஒரு worked example

Chennai-ல ஒரு lending company-க்கு, Tamil-லயும் English-லயும் loan கேள்விகளுக்கு ஒரு helpdesk assistant வேணும். Data இந்தியாவுக்குள்ளயே இருக்கணும், budget ஒரு conversation-க்கு சுமார் ₹0.37.

எட்டு candidates-ல ஆரம்பிக்கிறாங்க. Filter மூணை நீக்குது: ஒண்ணு இந்திய region-ல run ஆக முடியாது, ஒண்ணோட licence அவங்க use-ஐ தடை பண்ணுது, ஒண்ணு budget-ஐ விட ரொம்ப அதிகம். Instructions-ஐ follow பண்றதுல பலவீனமான இன்னொரு model-ஐ நீக்க public leaderboards உதவுது. நாலு மிச்சம்.

உண்மையான 240 கேள்விகள் (120 Tamil, 120 English), பெயர்களும் loan numbers-உம் நீக்கப்பட்டு, ஒரு rubric-ஓட test set உருவாக்குறாங்க: policy-ல இருந்து சரியான facts, தெளிவான அடுத்த step, மரியாதையான tone, சரியான மொழி.

| Model | Leaderboard rank | சொந்த test: Tamil | சொந்த test: English | ஒரு conversation-க்கு cost | p95 reply time |
| --- | --- | --- | --- | --- | --- |
| A, பெரிய hosted | 1 | 81% | 93% | ₹0.62 | 3.1 s |
| B, நடுத்தர hosted | 6 | 84% | 90% | ₹0.21 | 1.4 s |
| C, open-weight, self-hosted | 11 | 74% | 88% | ₹0.09 | 1.9 s |
| D, சின்ன hosted | 15 | 62% | 85% | ₹0.05 | 0.8 s |

எப்படி compare பண்றதுன்னு காட்ட இந்த numbers ஒரு உதாரணத்துக்கு தான். Leaderboard-ல முதல்ல இருக்குற A, English-ல சிறந்தது, ஆனா budget-ஐ தாண்டுது, Tamil-ல B-ஐ விட கொஞ்சம் மோசம். A-ஓட விலையில மூணுல ஒரு பங்குல B ரெண்டு மொழிகள்லயும் bar-ஐ தொடுது, அதனால B-ஐ தேர்ந்தெடுக்குறாங்க. C-ஐ ஒரு fallback-ஆ வச்சிருக்காங்க; அதை அப்புறம் Tamil replies-ல fine-tune பண்ணலாம். ஒரு புது model அறிவிக்கப்படும்போதெல்லாம் அந்த 240 கேள்விகளையும் திரும்ப run பண்றாங்க.

## பொதுவா பண்ற தப்புகள்

- **Headline score பார்த்து தேர்ந்தெடுக்குறது.** Leaderboard வெற்றின்னா அந்த tests-ல நல்லது, உங்க task-ல இல்லை.
- **English-ல மட்டும் test பண்றது.** இந்திய மொழிகள்லயும் கலந்த மொழி text-லயும் quality பெரும்பாலும் குறையும். உங்க users எழுதுற ஒவ்வொரு மொழியிலயும் test பண்ணுங்க.
- **வேற வேற மாதிரி அளந்த scores-ஐ compare பண்றது.** வேற prompts, scoring rules scores-ஐ ரொம்ப மாத்தும்.
- **Launch வரைக்கும் cost, speed-ஐ கண்டுக்காம இருக்கிறது.** 2 points நல்லா இருந்து, 3 மடங்கு விலை இருக்குற model தப்பான தேர்வா இருக்கலாம்.
- **திரும்ப check பண்ணாம இருக்கிறது.** Prices குறையும், models மேம்படும். ஆறு மாசம் முன்னாடி எடுத்த தேர்வு இப்போ அதிக விலையா இருக்கலாம்.
- **பழைய benchmarks-ஐ நம்புறது.** Popular, பழைய test sets training data-ல இருக்க வாய்ப்பு அதிகம், அதனால அதிக scores ஞாபகமா இருக்கலாம்.

## Benchmarks உண்மையிலேயே உதவுற நேரங்கள்

- **Shortlist-ஐ வேகமா உருவாக்க.** Coding, நீளமான documents மாதிரி உங்களுக்கு தேவையான skill-ல தெளிவா பலவீனமா இருக்குற models-ஐ அவை நீக்கும்.
- **இந்த field-ஐ follow பண்ண.** ஒரு புது, கஷ்டமான benchmark, models எவ்வளவு வேகமா மேம்படுதுன்னு காட்டும்.
- **ஒரு claim-ஐ check பண்ண.** ஒரு vendor தங்க model maths-ல சிறந்ததுன்னு சொன்னா, test பண்ண நேரம் செலவழிக்கிறதுக்கு முன்னாடி ஒரு public benchmark முதல் check கொடுக்கும்.

## Practice பண்ணுங்க

1. உங்களுக்கு தெரிஞ்ச ஒரு AI feature-க்கு hard requirements-ஐ list பண்ணுங்க: licence, data location, மொழிகள், context length, speed, price.
2. ரெண்டு public leaderboards-ஐ திறந்து, ஒவ்வொண்ணும் எந்த benchmarks-ஐ use பண்ணுதுன்னு note பண்ணுங்க. ரெண்டுலயும் ரொம்ப வேற மாதிரி rank ஆன ஒரு model-ஐ கண்டுபிடிங்க.
3. உங்க feature-க்கு பத்து real test inputs எழுதுங்க, ஒரு நல்ல answer-ல என்ன இருக்கணும்னும் எழுதுங்க. ரெண்டு models-ஐ அவற்றுல run பண்ணி ரெண்டையும் score பண்ணுங்க.
