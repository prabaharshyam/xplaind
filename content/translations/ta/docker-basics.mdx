## இது என்ன

**Container**-னா தனக்கு தேவையான எல்லாத்தோடயும் package பண்ணி run ஆகுற ஒரு program: Python version, libraries, உங்க code, அதோட start command. உங்க laptop-ல, colleague-ஓட machine-ல, client-ஓட server-ல, cloud service-ல, எங்க run பண்ணாலும் ஒரே மாதிரி வேலை செய்யும்.

Container-ஐ ஒரு **image**-ல இருந்து build பண்றீங்க, image-ஐ ஒரு **Dockerfile**-ல இருந்து build பண்றீங்க; Dockerfile-னா steps-ஓட ஒரு சின்ன recipe. **Docker Compose** பல containers-ஐ ஒரே file-ல இருந்து ஒண்ணா start பண்ணும்: உங்க API, pgvector இருக்குற PostgreSQL database, ஒரு Redis cache, production-ல இருக்கப்போற மாதிரியே connect ஆகி.

Containers virtual machines கிடையாது. அவை host-ஓட Linux kernel-ஐ share பண்ணும், அதனால சில வினாடிகள்ல start ஆகும், memory-உம் கம்மியா தான் எடுக்கும்.

```flow
dir: LR
Dockerfile -[docker build]-> Image | tag: claims-api:1.4.0
Image -[docker push]-> Registry | Docker Hub, GHCR, ஒரு cloud registry
Image -[docker run, compose up]-> Containers | laptop-ல, server-ல அல்லது cloud-ல run ஆகுது
```

| | Virtual machine | Container |
|---|---|---|
| ஒவ்வொரு app-உம் என்ன சுமக்குது | App, அதோட libraries, ஒரு முழு guest OS, hypervisor மேல | App, அதோட libraries, host kernel-ஐ share பண்ற container runtime மேல |
| Start ஆக ஆகுற நேரம் | நிமிஷங்கள் | வினாடிகள் |
| Memory | Gigabytes | Megabytes |

இந்த lesson, Jaipur-ல ஒரு bank-ஓட IT team-க்கு ஒரு document-search API-ஐ handover பண்றதை follow பண்ணுது; அவங்க எல்லாத்தையும் தங்க சொந்த servers-ல தான் run பண்றாங்க.

## இது எப்படி work ஆகுது

**Dockerfile.** ஒவ்வொரு வரியும் ஒரு layer சேர்க்கும்:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN pip install uv && uv sync --frozen --no-dev --no-install-project
COPY src ./src
USER 1000
CMD [".venv/bin/uvicorn", "app.main:app", "--app-dir", "src", "--host", "0.0.0.0", "--port", "8000"]
```

Docker layers-ஐ cache பண்ணும். Code-க்கு முன்னாடி dependency files-ஐ copy பண்ணா, code மாறினா எல்லா packages-ஐயும் திரும்ப install பண்ணாது, அதனால rebuilds சில வினாடிகள்ல முடியும்.

**Build, run.** `docker build -t claims-api:1.4.0 .` ஒரு image-ஐ build பண்ணி tag பண்ணும். `docker run -p 8000:8000 --env-file .env claims-api:1.4.0` அதை run பண்ணும்; container-ஓட port-ஐ உங்க port-க்கு map பண்ணி, settings-ஐ environment variables-ஆ pass பண்ணும். `docker ps`, `docker logs`, `docker exec -it name bash` இதெல்லாம் உள்ள என்ன நடக்குதுன்னு பார்க்க உதவும்.

**Data.** Container remove ஆனா அதோட சொந்த filesystem-உம் போயிடும். Database files, model cache மாதிரி அழியக்கூடாத data-வை **volume**-ல வைங்க.

**Compose.** `compose.yaml` services-ஐயும், அவற்றோட images அல்லது build folders, ports, environment, volumes, எது எதை சார்ந்திருக்குன்னும் list பண்ணும். `docker compose up` எல்லாத்தையும் start பண்ணும்; services ஒண்ணை ஒண்ணு பேரை வச்சு reach பண்ணும், அதனால உங்க API `postgres:5432`-க்கு connect ஆகும்.

**Registries.** Images ஒரு registry-க்கு (Docker Hub, GitHub Container Registry, அல்லது client-ஓட cloud registry) push ஆகும், servers அங்க இருந்து pull பண்ணும். ஒவ்வொரு image-க்கும் `latest` மட்டும் இல்லாம, ஒரு version-ஐயும் tag பண்ணுங்க; அப்போ என்ன run ஆகுதுன்னு தெரியும், rollback-உம் பண்ணலாம்.

**தினசரி commands:**

| Command | என்ன செய்யுது |
| --- | --- |
| `docker build -t name:tag .` | இங்க இருக்குற Dockerfile-ல இருந்து ஒரு image build பண்ணும் |
| `docker run -p 8000:8000 name:tag` | ஒரு port-ஐ map பண்ணி அதை run பண்ணும் |
| `docker ps` | Run ஆகுற containers-ஐ list பண்ணும் |
| `docker logs -f name` | ஒரு container-ஓட logs-ஐ follow பண்ணும் |
| `docker exec -it name bash` | Run ஆகுற container-க்குள்ள ஒரு shell திறக்கும் |
| `docker images` | Images-ஐயும் அவற்றோட sizes-ஐயும் list பண்ணும் |
| `docker compose up -d` | compose.yaml-ல இருக்குற எல்லா services-ஐயும் background-ல start பண்ணும் |
| `docker compose down` | அவற்றை stop பண்ணி remove பண்ணும் (volumes இருக்கும்) |

**Start ஆகாத container-ஐ debug பண்றது.** முதல்ல அதுக்கு `docker logs` பாருங்க: பெரும்பாலான failures ஒரு environment variable இல்லாதது, தப்பான start command, அல்லது ஏற்கனவே use ஆகுற port இதுல ஒண்ணா தான் இருக்கும். உடனே exit ஆகுதுன்னா, normal command-க்கு பதிலா ஒரு shell-ஓட run பண்ணி சுத்தி பாருங்க. Start ஆகுது, ஆனா database-ஐ reach பண்ண முடியலைன்னா, Compose-க்குள்ள database `localhost`-ல இல்லை, `db` மாதிரி அதோட service name-ல இருக்கும்னு ஞாபகம் வச்சுக்கோங்க; ஏன்னா ஒவ்வொரு container-க்கும் தனி network address இருக்கு.

**AI apps-க்கான images.** AI images சீக்கிரமே பெருசாயிடும்: machine learning libraries, model files, system packages எல்லாம் சேரும். முடிஞ்சா model weights-ஐ image-க்கு வெளியில வச்சு, start-up-ல ஒரு volume-க்கு download பண்ணுங்க, இல்லன்னா ஒரு hosted model-ஐ call பண்ணுங்க. Packages install பண்ண மட்டும் compilers தேவைப்பட்டா multi-stage builds use பண்ணுங்க: ஒரு stage-ல build பண்ணி, results-ஐ ஒரு slim final stage-க்கு copy பண்ணுங்க. சின்ன images வேகமா pull ஆகும், வேகமா start ஆகும், security scanners-க்கும் குறை சொல்ல குறைவா தான் இருக்கும்.

**Production மாதிரி ஒரு Dockerfile.** ரெண்டு stages, ஒரு health check, image-ல secrets இல்லை:

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim AS build
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev --no-install-project
COPY src ./src

FROM python:3.12-slim
WORKDIR /app
COPY --from=build /app/.venv ./.venv
COPY --from=build /app/src ./src
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
RUN useradd --uid 1000 --create-home app
USER app
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health')" || exit 1
CMD ["uvicorn", "app.main:app", "--app-dir", "src", "--host", "0.0.0.0", "--port", "8000"]
```

அதுக்கு பக்கத்துல ஒரு `.dockerignore`:

```text
.env
.git
__pycache__/
data/
models/
*.ipynb
```

**Database ready ஆகுற வரை காத்திருக்குற Compose.** `depends_on` மட்டும் இருந்தா container start ஆகுற வரை தான் காத்திருக்கும், Postgres connections-ஐ ஏத்துக்குற வரை இல்லை:

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    env_file: .env
    depends_on:
      db: {condition: service_healthy}
  db:
    image: pgvector/pgvector:pg16
    environment: {POSTGRES_PASSWORD: devonly, POSTGRES_DB: app}
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
volumes:
  pgdata:
```

`devonly` password local machine-க்கு மட்டும்; real environments-ல credentials-ஐ ஒரு secret store-ல இருந்து எடுக்கணும்.

**Containers-ல GPUs.** Host-ல NVIDIA-வோட container toolkit install ஆகியிருந்தா, `docker run --gpus all ...` ஒரு container-க்கு GPUs-ஐ கொடுக்கும். Compose-ல அவற்றை `deploy.resources.reservations.devices`-ல கேளுங்க. Host driver-க்கு பொருந்துற ஒரு CUDA base image-ஐ use பண்ணுங்க, image சின்னதா இருக்க model weights-ஐ ஒரு mounted volume-ல வைங்க.

**Scan, pin.** CI-ல Trivy அல்லது Docker Scout மாதிரி ஒரு tool வச்சு images-ஐ தெரிஞ்ச vulnerabilities-க்காக scan பண்ணி, தீவிரமான findings இருந்தா fail பண்ணுங்க. Base images-ஐ ஒரு version-க்கு (அல்லது digest-க்கு) pin பண்ணுங்க; அப்போ அடுத்த மாசம் rebuild பண்ணும்போது Python-ஓ system libraries-ஓ சத்தமில்லாம மாறாது.

**AI apps-க்கு size முக்கியம்.** ஒவ்வொரு மாற்றத்துக்கு அப்புறமும் `docker images`-ஐ பாருங்க. Hosted model use பண்ற ஒரு Python app சில நூறு megabytes இருக்கணும்; PyTorch, CUDA இருக்குறது பல gigabytes இருக்கலாம், அது ஒவ்வொரு deploy-ஐயும் autoscale-ஐயும் slow பண்ணும். Heavy model serving-ஐ தனி image-ஆ பிரிங்க, அப்போ API image சின்னதா இருக்கும்.

**Browser-லயே try பண்ணுங்க.** ஒரு சின்ன Dockerfile linter: மூணு பொதுவான தப்புகளை flag பண்ணும். Dockerfile text-ஐ edit பண்ணி run பண்ணுங்க.

```python
dockerfile = """FROM python:latest
COPY . /app
RUN pip install -r /app/requirements.txt
CMD ["python", "/app/main.py"]"""

lines = [l.strip() for l in dockerfile.splitlines() if l.strip()]
if any(l.startswith("FROM") and (":latest" in l or ":" not in l) for l in lines):
    print("Pin the base image version instead of latest.")
if not any(l.startswith("USER") for l in lines):
    print("Add a USER line so the app does not run as root.")
if lines.index(next(l for l in lines if l.startswith("COPY"))) < lines.index(next(l for l in lines if l.startswith("RUN pip"))):
    print("Copy requirements first and install before copying the code, so builds reuse the cache.")
```

## ஒரு worked example

நீங்க Jaipur bank-ஓட IT team-க்கு ஒரு document-search API-ஐ handover பண்றீங்க; அவங்க எல்லாத்தையும் தங்க சொந்த servers-ல run பண்றாங்க. அவங்களுக்கு try பண்ண ஒரே ஒரு command வேணும்.

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    env_file: .env
    depends_on: [db]
  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:
```

அவங்க `.env.example`-ஐ `.env`-க்கு copy பண்ணி, model key-ஐயும் ஒரு database password-ஐயும் நிரப்பி, `docker compose up -d` run பண்ணி, `localhost:8000/docs`-ஐ திறக்குறாங்க. API database-ஐ `db:5432`-ல reach பண்ணுது. Machine-ஐ restart பண்ணும்போது, database `pgdata` volume-ல இருக்குறதால documents இன்னும் indexed-ஆவே இருக்கு.

அவங்க security team image-ஐ scan பண்ணி, அது root-ஆ run ஆகுதுன்னு flag பண்றாங்க. `USER 1000` வரி அதை fix பண்ணுது. Image size-ஐயும் கேக்குறாங்க: `python:3.12-slim` அதை முழு Python image-ல இருக்குற 1 GB-க்கு மேல இல்லாம, கிட்டத்தட்ட 250 MB-ல வச்சிருக்கு.

| Bank-ஓட review point | முன்னாடி | அப்புறம் |
| --- | --- | --- |
| Root-ஆ run ஆகுதா | ஆமா | இல்லை: `USER 1000` |
| Image size | முழு Python image-ல 1 GB-க்கு மேல | `python:3.12-slim`-ல கிட்டத்தட்ட 250 MB |
| Image-ல secrets | இல்லை, run time-ல `.env` வழியா pass ஆகுது | அவங்க scanner confirm பண்ணுச்சு |
| Restart-க்கு அப்புறம் data | இருக்கு, `pgdata` volume-ல | இருக்கு |
| எந்த version run ஆகுது | `1.4.0` tag | `1.3.2`-க்கு rollback test பண்ணியாச்சு |

## பொதுவா பண்ற தப்புகள்

- **Secrets-ஐ image-க்குள்ள bake பண்றது.** Image இருக்குற யார் வேணும்னாலும் படிக்கலாம். Secrets-ஐ run time-ல pass பண்ணுங்க.
- **Production-ல `latest` use பண்றது.** என்ன run ஆகுதுன்னு தெரியாது, rollback-உம் பண்ண முடியாது. Versions-ஐ tag பண்ணுங்க.
- **Data-வை container-க்குள்ளயே வைக்கிறது.** அடுத்த deploy-ல அது மறைஞ்சிடும். Volumes அல்லது managed database use பண்ணுங்க.
- **Root-ஆ run பண்றது.** பல client security reviews இதை reject பண்ணும். ஒரு non-root user சேருங்க.
- **முழு folder-ஐயும் முதல்லயே copy பண்றது.** அப்போ ஒவ்வொரு code மாற்றத்துக்கும் எல்லா packages-உம் மறுபடி install ஆகும். Dependency files-ஐ copy பண்ணி, install பண்ணி, அப்புறம் code-ஐ copy பண்ணுங்க. `.git`, `.env`, data folders-க்கு ஒரு `.dockerignore` சேருங்க.

- **எல்லாத்துக்கும் ஒரே பெரிய container.** API, database, cache-ஐ தனித்தனி services-ஆ வைங்க; அப்போ ஒவ்வொண்ணையும் தனியா restart பண்ணலாம், scale பண்ணலாம், upgrade பண்ணலாம்.
- **.dockerignore இல்லாதது**, அதனால .env files-உம் data folders-உம் images-க்குள்ள போயிடுது.
- **Model weights image-க்குள்ள bake ஆகுறது**, அதனால அது gigabytes ஆகி deploy slow ஆகுது.
- **Health condition இல்லாத depends_on**, அதனால database ready ஆகுறதுக்கு முன்னாடியே app start ஆகுது.

பல பேர் அல்லது பல servers ஒரே விஷயத்தை ஒரே மாதிரி run பண்ண வேண்டிய நிலை வரும்போது containers-க்கு மதிப்பு கூடுது.

## Demo-ல இருந்து production-க்கு

- **Images-ஐ commit hash-ஓட tag பண்ணுங்க**, `latest` மட்டும் வேண்டாம்.
- **CI-ல images-ஐ scan பண்ணுங்க**, தீவிரமான vulnerabilities இருந்தா fail பண்ணுங்க.
- **Non-root user-ஆ run பண்ணுங்க**, ஒரு health check-ஓட.
- **Secrets-ஐ images-ல வைக்காதீங்க**; run time-ல inject பண்ணுங்க.
