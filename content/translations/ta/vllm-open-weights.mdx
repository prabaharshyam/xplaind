## இது என்ன

**Open-weight models** தங்க weights-ஐ வெளியிடும், அதனால அவற்றோட licence-படி உங்க சொந்த hardware-ல run பண்ணலாம். **vLLM** அப்படிப்பட்ட models-ஐ GPUs-ல திறமையா serve பண்ற ஒரு open-source engine. ரெண்டு ideas தான் அதை வேகமா ஆக்குது.

- **PagedAttention.** ஒரு model பதில் எழுதும்போது, முன்னாடி வந்த ஒவ்வொரு token-ஓட memory-ஐயும் வச்சிருக்கும்; அதுக்கு பேர் **KV cache**. பழைய servers ஒவ்வொரு request-க்கும், வரக்கூடிய மிக நீளமான பதிலுக்காக ஒரு நீளமான block-ஐ reserve பண்ணும், அதுல பெரும்பகுதி காலியாவே இருக்கும். vLLM cache-ஐ சின்ன pages-ல வச்சிருக்கும், ஒரு request வளரும்போது மட்டும் pages சேரும், ஒரு operating system memory-ஐ manage பண்ற மாதிரி. வீணாகுறது கொஞ்சம் தான், அதனால ஒரு GPU-ல ரொம்ப அதிகமான requests பொருந்தும்.
- **Continuous batching.** ஒரே நேரத்துல நிறைய requests-ல வேலை செய்யும்போது தான் ஒரு GPU மிக efficient-ஆ இருக்கும். ஒரு முழு batch முடியுற வரைக்கும் காத்திருக்காம, மத்தவை முடிய முடிய, ஒவ்வொரு step-லயும் புது requests batch-ல சேர vLLM விடும்.

vLLM ஒரு **OpenAI-compatible API**-ஐ expose பண்ணும், அதனால பெரும்பாலான client code-உம் gateways-உம் மாறாம அதோட வேலை செய்யும்.

```flow
title: ஒரு request vLLM server வழியா போறது
dir: LR
Client or gateway -[OpenAI-style API, ஒரு key-ஓட]-> vLLM server
vLLM server -> Scheduler | continuous batching: ஒவ்வொரு step-லயும் requests சேரும், வெளியேறும்
Scheduler -> KV cache in pages | PagedAttention; prompts-ஓட பொதுவான தொடக்கம் reuse ஆகும்
KV cache in pages -> GPU memory | weights-உம் cache-உம் இதை share பண்ணும்
vLLM server -> Metrics | queue length, cache usage, time to first token
```

இந்த lesson, claim documents-ஐ தங்க சொந்த servers-லயே வச்சிருக்க வேண்டிய Chennai-ல இருக்குற ஒரு insurance company-ஐ follow பண்ணுது.

## இது எப்படி work ஆகுது

### Model-ஐ தேர்ந்தெடுக்குறது

Leaderboard-ல இருந்து இல்ல, task-லயும் உங்க சொந்த evals-லயும் இருந்து ஆரம்பிங்க. அப்புறம் நாலு விஷயங்களை check பண்ணுங்க.

- **Licence.** Qwen3.5 family, Gemma 4 உட்பட இப்போ இருக்குற நிறைய models Apache 2.0-ல release ஆகியிருக்கு. மத்த சிலது conditions சேர்க்கும்; Meta-வோட Llama community licence ஒரு உதாரணம். நீங்க download பண்ற அதே weights கூட வர்ற licence file-ஐ படிங்க.
- **Size, type.** 4 முதல் 14 billion parameters இருக்குற models ஒரு GPU-ல ஓடும், extraction, classification, grounded RAG answers-க்கு பல நேரம் அதுவே போதும். Qwen3.5-35B-A3B (35 billion parameters, ஒரு token-க்கு சுமார் 3 billion active) மாதிரி ஒரு **mixture-of-experts (MoE)** model-க்கு அதோட எல்லா parameters-க்கும் memory வேணும், ஆனா ஒரு சின்ன model-ஓட கிட்டத்தட்ட அதே வேகத்துல generate பண்ணும்.
- **Context length.** Long-context models useful தான், ஆனா நீளமான contexts-க்கு cache memory-ல விலை கொடுக்கணும்.
- **மொழிகள்.** Models-க்கு இடையில மத்த எல்லாத்தையும் விட இது தான் அதிகமா மாறுபடும். அடுத்த section-ஐ பாருங்க.

November 2026 நிலவரப்படி, பொதுவான starting points-ல இவையும் அடங்கும்: Qwen3.5 (0.8B முதல் 397B வரை sizes, February, March 2026-ல release ஆனது), Qwen3.6 (April 2026), Qwen3.8-27B (August 2026), Gemma 4 (E2B முதல் 31B வரை), OpenAI-ஓட gpt-oss-20b, gpt-oss-120b. ஒவ்வொரு மாசமும் புது models வருது, அதனால இதை test பண்ண வேண்டிய ஒரு shortlist-ஆ பாருங்க, ஒரு ranking-ஆ இல்ல.

### இந்திய மொழிகளுக்கு ஒரு model-ஐ தேர்ந்தெடுக்குறது

எந்த benchmark-ஐ விடவும் இந்த மூணு checks அதிகமா சொல்லும்.

1. **ஒரு word-க்கு tokens (fertility).** பெரும்பாலும் English text-ல build ஆன ஒரு tokenizer, Malayalam அல்லது Odia words-ஐ நிறைய சின்ன துண்டுகளா பிரிக்கும். ஒரு model-க்கு ஒரு word-க்கு மூணு மடங்கு tokens தேவைப்பட்டா, ஒவ்வொரு request-க்கும் மூணு மடங்கு compute செலவாகும், அதிக நேரம் எடுக்கும், அதே context-ல குறைவான text தான் பொருந்தும். உங்க users-ஓட 200 உண்மையான sentences-ல இதை அளங்க:

```python
from transformers import AutoTokenizer

sentences = open("malayalam_sample.txt", encoding="utf-8").read().splitlines()
words = sum(len(s.split()) for s in sentences)
for name in ["Qwen/Qwen3.5-9B", "google/gemma-4-E4B-it"]:   # add every candidate
    tok = AutoTokenizer.from_pretrained(name)
    tokens = sum(len(tok.encode(s, add_special_tokens=False)) for s in sentences)
    print(f"{name}: {tokens / words:.2f} tokens per word")
```

2. **Native speakers review பண்ண ஒரு golden set.** Native script, romanised text (Manglish, Hinglish), code-mixed messages எல்லாத்தையும் சேருங்க, ஏன்னா உண்மையான users இதையெல்லாம் கலந்து தான் எழுதுவாங்க. Machine-translate பண்ண test sets, weak models-ஐ அவை உண்மையா இருக்குறதை விட நல்லதா காட்டும்.
3. **ஒவ்வொரு மொழிக்கும் quantized quality.** Quantization பல நேரம் English-ஐ விட lower-resource மொழிகள்ல அதிக quality-ஐ குறைக்கும். நீங்க உண்மையா serve பண்ணப்போற quantized checkpoint-லயே இந்திய மொழி evals-ஐ run பண்ணுங்க.

Test-ல சேர்க்க வேண்டிய candidates:

### ஒரு GPU-ஐ தேர்ந்தெடுக்குறது

எது பொருந்தும்னு memory முடிவு பண்ணும். Tokens எவ்வளவு வேகமா வரும்னு **memory bandwidth**, அதாவது GPU தன்னோட memory-ஐ எவ்வளவு வேகமா படிக்குதுங்கறது, முடிவு பண்ணும், ஏன்னா ஒவ்வொரு புது token-உம் எல்லா active weights-ஐயும் ஒரு தடவை படிக்கும்.

| GPU memory | உதாரண GPUs | 16-bit-ல பொருந்துறது | 4-bit-ல பொருந்துறது |
| --- | --- | --- | --- |
| 24 GB | NVIDIA L4, RTX 4090 | சுமார் 8B வரை, சின்ன contexts | சுமார் 14B வரை |
| 48 GB | NVIDIA L40S, RTX 6000 Ada | சுமார் 14B வரை | 27B முதல் 32B, cache-க்கு இடத்தோட |
| 80 GB | NVIDIA A100 80 GB, H100 | 27B முதல் 32B, கொஞ்சம் cache | சுமார் 70B, மிதமான cache |
| 141 GB | NVIDIA H200 | சுமார் 60B | மொத்தம் சுமார் 100B இருக்குற MoE models |

இந்தியால இதை E2E Networks (Delhi NCR-லயும் Chennai-லயும் H100 capacity list பண்ணியிருக்கு), Yotta மாதிரி local GPU clouds-ல இருந்து rent பண்ணலாம். தகுதியான startups, researchers, institutions அரசாங்கத்தோட IndiaAI Compute Portal-ல subsidised hours-க்கு apply பண்ணலாம். விலைகள் அடிக்கடி மாறும், அதனால நீங்க plan பண்ற அன்னைக்கே providers-ஓட pages-ஐ check பண்ணுங்க.

### Memory-ஐ கணக்கு பண்றது

**Weights.** 16-bit-ல ஒரு parameter-க்கு சுமார் 2 bytes, 8-bit-ல 1 byte, 4-bit-ல அரை byte-ஐ விட கொஞ்சம் அதிகம். ஒரு 27B model-க்கு 16-bit-ல சுமார் 54 GB, 4-bit-ல சுமார் 15 GB வேணும்.

**KV cache.** ஒரு standard transformer-ல, ஒவ்வொரு token-க்கும் `2 × layers × KV heads × head size × bytes` வேணும். அந்த 2, keys-க்கும் values-க்கும். இந்த நாலு numbers-ஐயும் model-ஓட `config.json`-ல படிங்க. அப்புறம் in flight-ல இருக்குற tokens-ஆல பெருக்குங்க: concurrent requests × அவற்றோட average length.

**உங்க browser-லயே try பண்ணுங்க.** இது ஒரு பொதுவான 8B model-ஓட shape-ஐ (32 layers, 8 KV heads, head size 128) 16-bit-ல use பண்ணுது:

```python
layers, kv_heads, head_dim, bytes_per = 32, 8, 128, 2
per_token = 2 * layers * kv_heads * head_dim * bytes_per      # 131,072 bytes
for users, context in [(10, 4000), (40, 4000), (40, 16000)]:
    gb = per_token * users * context / 1e9
    print(f"{users} users x {context} tokens: {gb:.1f} GB of KV cache")
```

இது சுமார் 5, 21, 84 GB-னு print பண்ணும். ஒரு GPU எத்தனை users-க்கு serve பண்ணும்னு பொதுவா model இல்ல, context length தான் முடிவு பண்ணும்.

ரெண்டு gotchas. Qwen3.5 மாதிரி புது **hybrid** models, சுமார் நாலு layers-ல ஒண்ணுல மட்டும் தான் full attention use பண்ணும், அதனால அவற்றோட cache இந்த formula சொல்றதை விட ரொம்ப சின்னது. Cache-ஐ 8-bit-ல (`--kv-cache-dtype fp8`) store பண்ணா அது பாதியாகும், ஆனா நீங்க அளக்க வேண்டிய ஒரு quality cost இருக்கு.

### Quantization

Weights-ஐ 8 அல்லது 4 bits-ல store பண்ணா weight memory சுமார் பாதி அல்லது முக்கால்வாசி குறையும், பல நேரம் generation-உம் வேகமாகும், கொஞ்சம் quality loss-ஓட. பொதுவான formats **AWQ**, **GPTQ** (4-bit), **FP8** (8-bit). ஏற்கனவே quantize ஆன ஒரு checkpoint-ஐ download பண்ணுங்க, உதாரணமா model maker வெளியிட்டது; vLLM அதோட config-ல இருந்து method-ஐ படிச்சுக்கும். `--quantization` flag ஒரு 16-bit model-ஐ AWQ-ஆ மாத்தாது. விதிவிலக்கு `--quantization fp8_per_tensor` (வெறும் `fp8` இப்போ இதை பண்றதில்ல): L40S, H100 மாதிரி FP8 support இருக்குற GPUs-ல இது load time-லயே quantize பண்ணும்.

| `--tensor-parallel-size` | 2 | ஒரு machine-ல ஒரு model-ஐ பல GPUs-க்கு பிரிக்கும் |

| `--speculative-config` | JSON | Speculative decoding: ஒரு வேகமான guesser tokens-ஐ draft பண்ணும், model அவற்றை check பண்ணும்; குறைவான load-ல latency-ஐ குறைக்கும் |

**v0.34.0-ல memory மாற்றம்.** வேற ஏதும் சொல்லலைன்னா, பழைய releases GPU memory-ல 90%, அப்புறம் 92% use பண்ணுச்சு. v0.34.0, NVIDIA, AMD GPUs-ல ஒரு **extensible KV cache**-ஐ on பண்ணுது: warm-up-க்கு அப்புறம் உண்மையா free-ஆ இருக்குற memory-ல இருந்து cache-ஐ size பண்ணும், set பண்ணாத `--gpu-memory-utilization` இப்போ 1.0-னு அர்த்தம். பெரும்பாலான configs-ல இருந்து இந்த flag-ஐ எடுத்துடுங்கன்னு release notes சொல்லுது. இதனால ரெண்டு gotchas. அதே GPU-ல இருக்குற இரண்டாவது process, உதாரணமா ஒரு embedding model, ஒவ்வொண்ணுக்கும் ஒரு share set பண்ணலைன்னா இப்போ memory-யே கிடைக்காது. அப்புறம், சில models-ல per-token latency கூடலாம்னு notes சொல்லுது; opt out பண்ண `--gpu-memory-utilization 0.9` அல்லது `--no-enable-extensible-kv-cache` pass பண்ணுங்க. Default `--block-size`-உம் 16-ல இருந்து 64-ஆ மாறிடுச்சு.

**Reasoning models.** இப்போ இருக்குற நிறைய models பதில் சொல்றதுக்கு முன்னாடி "think" பண்ணும். அந்த model-க்கு தேவையான reasoning-parser, tool-call-parser flags-க்கு, GitHub-ல vLLM-ஓட recipes repository-ல அதோட page-ஐ பாருங்க. அவை இல்லைன்னா, thinking text பதிலுக்குள்ள வந்து JSON parsing-ஐ உடைச்சுடும்.

### Endpoint-ஐ secure பண்றது

`--api-key` (அல்லது `VLLM_API_KEY` variable) `/v1`-க்கு கீழ இருக்குற routes-ஐயும் இன்னும் சில prefixes-ஐயும் மட்டும் தான் பாதுகாக்கும். `/invocations` மாதிரி மத்த routes open-ஆவே இருக்கும்னு vLLM docs எச்சரிக்குது. அதனால vLLM-ஐ நேரடியா expose பண்ணவே பண்ணாதீங்க. அதை உங்க gateway-க்கு பின்னாடி வைங்க, gateway மட்டும் அதை reach பண்ற மாதிரி ஒரு Kubernetes network policy use பண்ணுங்க.

### Go-live-க்கு முன்னாடி load testing

உண்மையான மாதிரி prompts-ஐ ஏறிக்கிட்டே போற concurrency-ல அனுப்பி, time to first token-ஐயும் total time-ஐயும் record பண்ணுங்க:

```python
import asyncio, time
from openai import AsyncOpenAI

aclient = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="your-key")

async def one(prompt):
    t0 = time.perf_counter(); first = None
    stream = await aclient.chat.completions.create(model="chat-local", stream=True, max_tokens=300,
                                                   messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if first is None and chunk.choices and chunk.choices[0].delta.content:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0

async def run(prompts, concurrency):
    sem = asyncio.Semaphore(concurrency)
    async def limited(p):
        async with sem:
            return await one(p)
    results = await asyncio.gather(*(limited(p) for p in prompts))
    ttft = sorted(r[0] for r in results if r[0]); total = sorted(r[1] for r in results)
    print(f"c={concurrency}: p95 first token {ttft[int(0.95 * (len(ttft) - 1))]:.2f}s, "
          f"p95 total {total[int(0.95 * (len(total) - 1))]:.2f}s")

# for c in (1, 8, 32, 64): asyncio.run(run(sample_prompts, c))
```

p95 first-token time உங்க budget-க்குள்ள இருக்குற மிக அதிகமான concurrency தான் ஒரு replica-வோட capacity.

### இதை operate பண்றது

vLLM `/metrics`-ல Prometheus metrics-ஐ expose பண்ணும். CPU மேல இல்ல, `vllm:num_requests_waiting` (queue), `vllm:kv_cache_usage_perc` (cache எவ்வளவு full) மேல alert பண்ணுங்க, scale பண்ணுங்க. Prefix caching default-ஆ on: ஒரே system prompt அல்லது document-ஓட தொடங்குற requests அதோட cache-ஐ reuse பண்ணும். Shared content-ஐ prompts-ஓட ஆரம்பத்துல வைங்க, `vllm:prefix_cache_hits`-ஐ `vllm:prefix_cache_queries`-ஆல வகுத்து hit rate-ஐ track பண்ணுங்க. ஒரு failure அல்லது upgrade service-ஐ நிறுத்தாம இருக்க ஒரு spare replica வைங்க, weights-ஐ ஒரு internal volume-ல வைங்க, ஏன்னா start-up-ல downloads மெதுவா இருக்கும், locked-down networks-ல பல நேரம் block ஆகும்.

## ஒரு worked example

Chennai-ல ஒரு insurance company claim documents-ஐ தங்க சொந்த servers-லயே வச்சிருக்கணும். Claim forms-ல இருந்து 20 fields extract பண்ணணும், claims staff-க்கு சின்ன grounded answers வேணும்; ஒரு நாளைக்கு சுமார் 30,000 requests. கீழ இருக்குற எல்லா numbers-உம் method-ஐ காட்டுறதுக்கான உதாரணங்கள் மட்டும் தான்.

**Model.** Tamil forms உட்பட 300 உண்மையான forms-ல evals, மூணு open-weight models-ஐ ஒரு frontier API கூட compare பண்ணுது. இதுல சிறந்தது ஒரு 27B dense model: API-ஓட 97%-க்கு எதிரா 95% field accuracy. Data-வை தங்க premises-லயே வச்சிருக்க company அந்த gap-ஐ ஏத்துக்குது.

**Memory.** 16-bit-ல weights-க்கு 54 GB வேணும், ஒரு 48 GB L40S-க்கு இது அதிகம். Maker-ஓட 4-bit AWQ checkpoint-க்கு சுமார் 15 GB போதும், evals 94.5%-க்கு மட்டும் தான் இறங்குது. Runtime overhead சுமார் 7 GB எடுக்குதுன்னு வச்சுக்குவோம், அப்போ cache-க்கு சுமார் 26 GB மிஞ்சும். Model-ஓட config 64 layers, 8 KV heads, head size 128-னு சொல்லுது, அதனால ஒவ்வொரு token-க்கும் 2 × 64 × 8 × 128 × 2 bytes, சுமார் 0.26 MB வேணும். அது சுமார் 99,000 tokens-க்கு இடம், அதாவது average 3,000 tokens இருக்குற சுமார் 33 requests.

**Traffic.** 10 மணி நேர working day-ல 30,000 requests-னா ஒரு second-க்கு சுமார் 0.8; peak இதோட ரெட்டிப்புன்னு வச்சுக்குவோம், ஒரு second-க்கு சுமார் 1.7. ஒவ்வொரு request-உம் சுமார் 6 seconds எடுத்தா, in flight-ல இருக்குற requests = arrival rate × ஒவ்வொண்ணும் எடுக்குற நேரம் (Little's law) = 1.7 × 6, சுமார் 10. ஒரு GPU 33-ஐ தாங்கும், அதனால அது peak-ஐ சமாளிக்கும். இரண்டாவது GPU headroom குடுக்கும், failures, upgrades நேரத்துலயும் service-ஐ ஓட வைக்கும். 30 concurrent requests-ல p95 first-token time 2 seconds-க்கு கீழ இருக்குன்னு ஒரு load test உறுதிப்படுத்துது.

**Cost.** ஒவ்வொரு GPU-க்கும் ஒரு மணி நேரத்துக்கு ₹100-னு வச்சுக்குவோம்; இது ஒரு quote இல்ல, உதாரணத்துக்கான figure. 730 மணி நேர மாசத்துக்கு ரெண்டு GPUs-க்கு ₹1,46,000, அதாவது ஒரு மாசத்துக்கு 9,00,000 requests-ல 1,000 requests-க்கு சுமார் ₹162. API ஒரு million input tokens-க்கு ₹100, ஒரு million output tokens-க்கு ₹400 charge பண்ணுதுன்னு வச்சுக்குவோம், இதுவும் உதாரணம் தான். 3,000 input, 300 output tokens இருக்குற ஒவ்வொரு request-க்கும் ₹0.42, அதாவது 1,000-க்கு ₹420. Break-even ₹1,46,000 ÷ ₹0.42, ஒரு மாசத்துக்கு சுமார் 3,48,000 requests அல்லது ஒரு நாளைக்கு 11,600. ஒரு நாளைக்கு 3,000 requests-னா, self-hosting-க்கு 1,000-க்கு சுமார் ₹1,620 ஆகும். ரெண்டு figure-லயும் GST-ஓ, அதை run பண்ற engineer-ஓட நேரமோ சேர்க்கல.

## பொதுவா பண்ற தப்புகள்

- **Leaderboard-ல இருந்து model-ஐ எடுக்குறது.** உங்க சொந்த data-ல, உங்க users-ஓட மொழிகள், scripts-ல test பண்ணுங்க.
- **Sizing-ல KV cache-ஐ மறந்துடுறது.** Weights பொருந்திடும், அப்புறம் load-ல server மெதுவாகும் அல்லது நின்னுடும். In flight-ல இருக்குற tokens-க்கு size பண்ணுங்க.
- **`--max-model-len`-ஐ model-ஓட maximum-க்கு set பண்றது.** ஒரு 262,144-token limit ஒரு GPU-ல start-up-லயே fail ஆகலாம். உங்க traffic-க்கு தேவையான அளவுக்கு set பண்ணுங்க.
- **பழக்கத்துல `--gpu-memory-utilization 0.9`-ஐ தொடர்ந்து வச்சிருக்குறது.** v0.34.0-ல அது cache-க்கு போக வேண்டிய memory-ஐ தடுத்து வைக்கும். ஒரு GPU-வை share பண்ணும்போது மட்டும் set பண்ணுங்க.
- **அளக்காம quantize பண்றது,** முக்கியமா இந்திய மொழிகள்ல, அவை English-ஐ விட அதிக quality-ஐ இழக்கலாம்.
- **Licences-ஐ கண்டுக்காம விடுறது.** அந்த exact weights-க்கான licence file-ஐ படிங்க.
- **Pin பண்ணாத image, engine அல்லது model revision,** அதனால ஒரு restart சத்தமில்லாம outputs-ஐ மாத்திடும்.
- **vLLM-ஐ நேரடியா expose பண்றது,** `--api-key` மட்டும் வச்சு; சில routes open-ஆவே இருக்கும்.

## vLLM-ஓட self-host பண்ணக்கூடாத இடங்கள்

- **குறைவான அல்லது திடீர்னு ஏறி இறங்குற volume,** அப்போ idle GPUs-க்கு API calls-ஐ விட அதிகமா செலவாகும்; break-even-ஐ கணக்கு பண்ணுங்க.
- **உங்களுக்கு மிக strong-ஆன models வேணும்,** அவை APIs-ஆ மட்டும் தான் கிடைக்கலாம்.
- **Operate பண்ண யாரும் இல்ல.** GPUs, drivers, upgrades, on-call எல்லாம் உண்மையான வேலை.

## Demo-ல இருந்து production வரை

- **Image, vLLM version, model revision-ஐ pin பண்ணுங்க,** weights-ஐ volumes-ல cache பண்ணி.
- ஒவ்வொரு model அல்லது setting மாற்றத்துக்கு அப்புறமும் **load test பண்ணுங்க**, ஒரு replica-வோட capacity-ஐ record பண்ணுங்க.
- **Queue length, KV cache usage மேல alert பண்ணுங்க, scale பண்ணுங்க.**

- Failures-க்கும் rolling upgrades-க்கும் **ஒரு spare replica வைங்க**.
