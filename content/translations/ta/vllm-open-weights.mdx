## இது என்ன

**Open-weight models** தங்க weights-ஐ வெளியிடும், அதனால அவற்றை உங்க சொந்த hardware-ல run பண்ணலாம். **vLLM** அப்படிப்பட்ட models-ஐ GPUs-ல திறமையா serve பண்ற ஒரு open-source engine. அதோட ரெண்டு முக்கிய ideas:

- **PagedAttention**: ஒவ்வொரு request-ஓட attention cache-ஐ வச்சிருக்குற memory-ஐ, ஒரு operating system memory-ஐ manage பண்றது மாதிரி, சின்ன pages-ல manage பண்ணும்; அதனால ஒரு GPU-ல ரொம்ப அதிக requests பொருந்தும்.
- **Continuous batching**: மத்த requests முடிஞ்ச உடனே புது requests batch-ல சேரும், முழு batch-க்காக காத்திருக்காது; இது GPU-ஐ busy-ஆ வச்சிருக்கும்.

vLLM ஒரு **OpenAI-compatible API**-ஐ expose பண்ணும், அதனால பெரும்பாலான client code-உம் gateways-உம் மாறாம அதோட வேலை செய்யும்.

```flow
Client code அல்லது gateway -[OpenAI-compatible API]-> vLLM server
vLLM server -> Continuous batching | requests ஒவ்வொரு step-லயும் batch-ல சேரும், வெளியேறும்
Continuous batching -> GPU memory, 48 GB | 4-bit weights கிட்டத்தட்ட 9 GB; KV cache pages-ல: PagedAttention, வீணாகுற இடைவெளி இல்ல
vLLM server -> Metrics | tokens per second, queue length, cache usage
```

Model revision-ஐயும் vLLM version-ஐயும் pin பண்ணுங்க.

இந்த lesson, claim documents-ஐ தங்க சொந்த servers-ல வச்சிருக்க வேண்டிய Chennai-ல ஒரு insurance company-ஐ follow பண்ணுது.

## இது எப்படி work ஆகுது

**Model-ஐ தேர்ந்தெடுக்குறது.** Leaderboards-ல இல்ல, task-லயும் உங்க evals-லயும் இருந்து ஆரம்பிங்க. Commercial use-க்கான licence-ஐ, அது கையாளுற மொழிகளை (இந்திய மொழிகள்ல models-க்கு இடையில ரொம்ப வித்தியாசம் இருக்கும்), context length-ஐ, size-ஐ check பண்ணுங்க. சின்ன models (7 முதல் 14 billion parameters) ஒரு GPU-ல ஓடும், extraction, classification, grounded RAG answers-க்கு பெரும்பாலும் போதும்.

**Memory-ஐ அளக்குறது.** ஒரு தோராயமான விதி: 16-bit precision-ல weights-க்கு ஒரு parameter-க்கு கிட்டத்தட்ட 2 bytes வேணும். 8-billion-parameter model-க்கு weights-க்கு கிட்டத்தட்ட 16 GB வேணும். அதுக்கு மேல, attention (KV) cache concurrent requests எண்ணிக்கையோடும் அவற்றோட context length-ஓடும் வளரும். ஒரு 24 GB GPU, மிதமான concurrency-ஓட ஒரு 8B model-ஐ serve பண்ணலாம்; ஒரு 70B model-க்கு 16-bit-ல கிட்டத்தட்ட 140 GB வேணும், அதனால பல GPUs அல்லது quantization.

**Quantization.** Weights-ஐ 8 அல்லது 4 bits-ல சேமிச்சா memory பாதி அல்லது முக்கால் பங்கு குறையும், பெரும்பாலும் வேகமும் கூடும், சின்ன quality இழப்போட; அதை உங்க சொந்த evals-ல அளக்கணும். பொதுவான formats: AWQ, GPTQ, FP8.

**Run பண்றது.**

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.90
# now: POST http://localhost:8000/v1/chat/completions
```

முக்கிய settings: maximum context length (குறைவா இருந்தா அதிக concurrent requests பொருந்தும்), GPU memory பங்கு, பல GPUs-ல tensor parallelism (`--tensor-parallel-size 2`), quantization.

**Production-ல.** அதை ஒரு container-ல, weights ஒரு volume-ல அல்லது ஒரு internal image-க்குள்ள, உங்க gateway-க்கு பின்னாடி, health checks, metrics (tokens per second, queue length, cache usage), GPUs அனுமதிக்குற இடத்துல autoscaling-ஓட run பண்ணுங்க. Model revision-ஐயும் vLLM version-ஐயும் pin பண்ணுங்க, ஒவ்வொரு upgrade-க்கு முன்னாடியும் evaluate பண்ணுங்க.

**முக்கிய vLLM settings:**

| Setting | Example | விளைவு |
| --- | --- | --- |
| `--max-model-len` | 8192 | குறைவான limits, concurrent requests-க்கு அதிக இடம் விடும் |
| `--gpu-memory-utilization` | 0.90 | vLLM use பண்ணக்கூடிய GPU memory பங்கு |
| `--tensor-parallel-size` | 2 | ஒரு machine-ல பல GPUs-ல ஒரு model-ஐ பிரிக்கும் |
| `--quantization` | awq | Memory மிச்சப்படுத்த ஒரு quantized checkpoint-ஐ use பண்ணும் |

**ஒரு API-ஓட நியாயமா ஒப்பிடுறது.** அதே golden set-ஐ self-hosted model-லயும் ஒரு API model-லயும் run பண்ணுங்க. Task, language வாரியா accuracy, realistic load test-ல p95 latency, 1,000 requests-க்கான cost, GPUs-ஓட முழு மாசாந்திர செலவை உண்மையான volume-ஆல வகுத்து சேர்த்து, பதிவு பண்ணுங்க. Self-hosting முழு load-ல per-token மலிவா தெரியும், குறைவான use-ல செலவானதா தெரியும்; அதனால உண்மையான எதிர்பார்க்குற volume-ஐ use பண்ணுங்க. Client-ஓட team கையெழுத்து போடக்கூடிய ஒரு சின்ன table-ஆ result-ஐ எழுதுங்க.

**Operate பண்றது.** Queue length-ஐயும் cache usage-ஐயும் கவனிங்க: வளருற queue-னா அதிக capacity அல்லது குறைவான contexts வேணும்னு அர்த்தம். ஒரு failure அல்லது upgrade service-ஐ நிறுத்தாம இருக்க, ஒரு spare GPU அல்லது replica வச்சிருங்க. Weights-ஐ ஒரு internal registry அல்லது volume-ல வைங்க, ஏன்னா start-up-ல internet-ல இருந்து download பண்றது மெதுவானது, locked-down networks-ல block ஆகவும் செய்யலாம்.

**vLLM-ஐ ஒரு container-ல run பண்றது.** Weights ஒரு volume-ல, ஒரு pin பண்ணின image, OpenAI-compatible server port 8000-ல:

```bash
docker run --gpus all --rm -p 8000:8000 \
  -v /data/hf-cache:/root/.cache/huggingface \
  -e HF_TOKEN \
  vllm/vllm-openai:v0.10.1 \
  --model Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 \
  --gpu-memory-utilization 0.90 --served-model-name chat-local
```

`--served-model-name` clients use பண்ற பேரை அமைக்கும்; அதனால apps-ஐ மாத்தாமலேயே அடியில இருக்குற model-ஐ மாத்தலாம்.

**எந்த OpenAI-style API மாதிரியும் call பண்றது, structured output-ஓட.**

```python
from openai import OpenAI
from pydantic import BaseModel

class Claim(BaseModel):
    policy_number: str
    amount_inr: int
    reason: str

client = OpenAI(base_url="http://localhost:8000/v1", api_key="not-needed-locally")
r = client.chat.completions.create(
    model="chat-local",
    messages=[{"role": "user", "content": "Extract: Policy HX-22981, claim of Rs 18,400 for a cracked windscreen."}],
    response_format={"type": "json_schema", "json_schema": {"name": "claim", "schema": Claim.model_json_schema()}},
)
print(Claim.model_validate_json(r.choices[0].message.content))
```

Server, generation-ஐ schema-க்குள்ள கட்டுப்படுத்துது, அதனால reply parse ஆகும்; இருந்தாலும் structured-output lesson சொல்றபடி values-ஐ validate பண்ணுங்க.

**Go-live-க்கு முன்னாடி load testing.** Realistic prompts-ஐ அதிகரிக்குற concurrency-ல அனுப்பி, time to first token, tokens per second, errors-ஐ பதிவு பண்ணுங்க:

```python
import asyncio, time
from openai import AsyncOpenAI

aclient = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="x")

async def one(prompt):
    t0 = time.perf_counter(); first = None
    stream = await aclient.chat.completions.create(model="chat-local", stream=True, max_tokens=300,
                                                   messages=[{"role": "user", "content": prompt}])
    async for chunk in stream:
        if first is None and chunk.choices and chunk.choices[0].delta.content:
            first = time.perf_counter() - t0
    return first, time.perf_counter() - t0

async def run(prompts, concurrency):
    sem = asyncio.Semaphore(concurrency)
    async def limited(p):
        async with sem:
            return await one(p)
    results = await asyncio.gather(*(limited(p) for p in prompts))
    ttft = sorted(r[0] for r in results if r[0]); total = sorted(r[1] for r in results)
    print(f"c={concurrency}: p95 first token {ttft[int(0.95 * (len(ttft) - 1))]:.2f}s, "
          f"p95 total {total[int(0.95 * (len(total) - 1))]:.2f}s")

# for c in (1, 8, 32, 64): asyncio.run(run(sample_prompts, c))
```

p95 first-token time உங்க budget-ஐ தாண்டுற concurrency தான் ஒரு replica-வோட capacity.

**Metrics-ஐ கவனிங்க.** vLLM, `/metrics`-ல Prometheus metrics-ஐ expose பண்ணும்; ஓடுற, காத்திருக்குற requests, KV cache usage உட்பட. Requests ரொம்ப நேரம் காத்திருந்தா அல்லது cache usage கிட்டத்தட்ட நிரம்பியே இருந்தா alert பண்ணுங்க, CPU-ஐ வச்சு இல்ல, இந்த signals-ஐ வச்சு replicas-ஐ scale பண்ணுங்க.

**Shared prefixes-ஐ மறுபடி use பண்ணுங்க.** Prefix caching, ஒரே system prompt அல்லது document-ஓட ஆரம்பிக்குற requests அதை திரும்ப compute பண்றதை தவிர்க்க விடும்; chat, RAG workloads-க்கு உதவும். உங்க version-ல அது on-ல இருக்கான்னு check பண்ணுங்க, shared content-ஐ prompts-ஓட ஆரம்பத்துல வைங்க.

**உங்க browser-ல try பண்ணுங்க.** உங்க traffic-க்கான KV cache-ஐ மதிப்பிடுங்க; ஒரு GPU எத்தனை users-ஐ serve பண்ணலாம்னு இதுதான் பெரும்பாலும் தீர்மானிக்கும்.

```python
layers, kv_heads, head_dim, bytes_per = 32, 8, 128, 2      # a typical 8B model at 16-bit
per_token = 2 * layers * kv_heads * head_dim * bytes_per
for users, context in [(10, 4000), (40, 4000), (40, 16000)]:
    gb = per_token * users * context / 1e9
    print(f"{users} users x {context} tokens: {gb:.1f} GB of KV cache")
```

## ஒரு worked example

Chennai-ல ஒரு insurance company, claim documents-ஐ தங்க சொந்த servers-ல வச்சிருக்கணும். Claim forms-ல இருந்து 20 fields extraction-உம், claims staff-க்கு குறுகிய grounded answers-உம் வேணும், ஒரு நாளைக்கு கிட்டத்தட்ட 30,000 requests.

300 உண்மையான forms-ல evals, 7 முதல் 14 billion parameters உள்ள மூணு open-weight models-ஐ ஒரு frontier API-ஓட ஒப்பிடுது. சிறந்த 14B model 95% field accuracy-ஐ அடையுது, API-க்கு 97%; data on-premises-ல இருக்கிறதுக்காக client இந்த இடைவெளியை ஏத்துக்குறாங்க.

Sizing: 16-bit-ல 14B model-க்கு weights-க்கு கிட்டத்தட்ட 28 GB வேணும். 4-bit AWQ quantization-ஓட கிட்டத்தட்ட 9 GB வேணும், evals 94.5%-க்கு மட்டும் குறையுது. ஒரு 48 GB GPU-ல, KV cache-க்கு கிட்டத்தட்ட 30 GB மிஞ்சும். Claim requests சராசரியா 8,000-token limit-க்குள்ள கிட்டத்தட்ட 3,000 tokens, ஒரு load test p95-ல ஒவ்வொண்ணும் 3 seconds-க்கு குறைவா 40 concurrent requests-ஐ காட்டுது. ரெண்டு GPUs headroom-ஐயும் redundancy-யையும் தருது.

vLLM, client-ஓட Kubernetes cluster-ல containers-ல ஓடுது, முன்னாடி இருந்த அதே gateway-க்கு பின்னாடி; அதனால application code ஒரே ஒரு model alias-ஐ மட்டும் மாத்துது. Eval suite pass ஆன பிறகு காலாண்டுக்கு ஒரு தடவை upgrades நடக்குது.

| Option | Field accuracy | Weights-க்கான memory | குறிப்புகள் |
| --- | --- | --- | --- |
| Frontier API | 97% | பொருந்தாது | Data வளாகத்தை விட்டு போகும் |
| 14B model, 16-bit | 95% | கிட்டத்தட்ட 28 GB | பொருந்தும், cache-க்கு இடம் குறைவு |
| 14B model, 4-bit AWQ | 94.5% | கிட்டத்தட்ட 9 GB | p95-ல 3 s-க்கு குறைவா 40 concurrent requests; இதை தேர்ந்தெடுத்தாங்க |

## பொதுவா பண்ற தப்புகள்

- **Leaderboard-ல இருந்து ஒரு model-ஐ தேர்ந்தெடுக்குறது.** உங்க சொந்த data, மொழிகள்ல test பண்ணுங்க.
- **Sizing-ல KV cache-ஐ மறக்குறது.** Weights பொருந்தும், அப்புறம் load-ல server fail ஆகும். Concurrency-க்கு size பண்ணுங்க.
- **அளக்காம quantize பண்றது.** சில tasks மத்தவற்றை விட அதிக quality இழக்கும். உங்க evals-ஐ run பண்ணுங்க.
- **Licences-ஐ புறக்கணிக்குறது.** சில open-weight licences commercial use அல்லது பெரிய deployments-ஐ restrict பண்ணும்.
- **Pin பண்ணாத versions.** ஒரு புது model revision அல்லது engine release outputs-ஐ மாத்தலாம். Pin பண்ணி evaluate பண்ணுங்க.
- **ஒரு GPU server-க்கு CPU-ல scale பண்றது**; queue, cache metrics-ல scale பண்ணுங்க.
- **Pin பண்ணாத images, model revisions**, அதனால ஒரு restart நடத்தையை மாத்தும்.
- **Load test இல்லாம**, அதனால capacity-ஐ users கண்டுபிடிக்குறாங்க.

## vLLM-ஓட self-host பண்ணக்கூடாத இடங்கள்

- **குறைவான அல்லது திடீர்னு ஏறி இறங்குற volume**, அங்க சும்மா இருக்குற GPUs, API calls-ஐ விட அதிகம் செலவாகும்.
- **உங்களுக்கு வலுவான models வேணும்**, அவை APIs-ஆ மட்டும் கிடைக்கலாம்.
- **Operate பண்ண யாருமில்ல**: GPUs, drivers, upgrades, on-call எல்லாம் உண்மையான வேலை.
