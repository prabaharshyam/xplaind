## இது என்ன

**Test**-னா நீங்க தேர்ந்தெடுத்த input-ஓட உங்க code-ஐ run பண்ணி, result நீங்க எதிர்பார்க்குற மாதிரி இருக்கான்னு check பண்ற ஒரு சின்ன code துண்டு. **Unit test** ஒரு சின்ன பகுதியை, பெரும்பாலும் ஒரு function-ஐ, தனியா check பண்ணும். Result தப்பா இருந்தா test fail ஆகி எங்கன்னு சொல்லும்.

இன்னைக்கு நீங்க எழுதுற code-ஐ விட, அதுக்கு அப்புறம் வர்ற ஒவ்வொரு change-க்கும் தான் tests அதிகம் முக்கியம். ஆறு மாசம் கழிச்சு நீங்களோ உங்க teammate-ஓ ஒரு function-ஐ மாத்துவீங்க. Tests இல்லன்னா, எதுவும் உடையலன்னு தெரிஞ்சுக்க app-ஐ click பண்ணி பார்த்து நம்பிக்கை வைக்கிறது தான் வழி. Tests இருந்தா, ஒரு command run பண்ணா சில வினாடிகள்ல தெரிஞ்சுடும்.

**pytest** Python-க்கான standard testing tool. `test_`-ல ஆரம்பிக்குற பேர் உள்ள சாதாரண functions-ஐ எழுதுறீங்க, சாதாரண `assert` statements use பண்றீங்க; pytest அவற்றை கண்டுபிடிச்சு run பண்ணி, ஒண்ணு fail ஆனா எந்த values வித்தியாசப்பட்டதுன்னு சரியா காட்டும்.

## இது எப்படி work ஆகுது

ஒரு test மூணு steps-ஐ follow பண்ணும், இதை **arrange, act, assert**-ன்னு சொல்வாங்க: inputs-ஐ தயார் பண்ணுங்க, code-ஐ ஒரு தடவை call பண்ணுங்க, result-ஐ check பண்ணுங்க.

```python
# gst.py
def gst(amount: float, rate: float = 0.18) -> float:
    if amount < 0:
        raise ValueError("amount must not be negative")
    return round(amount * rate, 2)
```

```python
# test_gst.py
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(100) == 18.0

def test_rounds_to_two_decimals():
    assert gst(10.555) == 1.9

def test_negative_amount_is_refused():
    with pytest.raises(ValueError):
        gst(-1)
```

Project folder-ல `pytest` run பண்ணா `3 passed in 0.02s` மாதிரி ஒரு report வரும்.

நீங்க வேலை செய்யுற loop:

```flow
dir: LR
Code எழுது அல்லது மாத்து -> pytest run பண்ணு
pytest run பண்ணு -[ஒரு test fail ஆச்சு]-> Failure-ஐ படி | எந்த values வித்தியாசம்
Failure-ஐ படி -> Code எழுது அல்லது மாத்து
pytest run பண்ணு -[எல்லாம் pass]-> Commit
```

மூணு tools பெரும்பாலான real tests-ஐ கவர் பண்ணும்:

| Tool | என்ன பண்ணும் | Example use |
| --- | --- | --- |
| `@pytest.mark.parametrize` | ஒரே test-ஐ பல inputs-ல run பண்ணும் | ஒவ்வொரு GST rate: 5%, 12%, 18%, 28% |
| `@pytest.fixture` | ஒரு test பேர் சொல்லி கேக்குற பகிரப்பட்ட setup | ஒரு sample invoice, ஒரு temporary folder |
| Fakes, mocks | மெதுவான அல்லது வெளி பகுதிகளை மாத்தும் | ஒரு fixed reply தர்ற model client |
| `pytest.raises` | ஒரு error raise ஆகுதான்னு check பண்ணும் | Negative amounts மறுக்கப்படுது |
| `tmp_path` | ஒவ்வொரு test-க்கும் புது temporary folder | Files எழுதுற code |

Tests-ஐ copy பண்றதுக்கு பதிலா **parametrise** பண்ணுங்க:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (100, 0.05, 5.0),
    (100, 0.12, 12.0),
    (100, 0.28, 28.0),
])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

**Fixtures** பகிரப்பட்ட setup-ஐ வச்சிருக்கும்:

```python
@pytest.fixture
def invoice():
    return {"items": [("Charger", 999.0), ("Cable", 299.0)], "rate": 0.18}

def test_invoice_total(invoice):
    assert invoice_total(invoice) == 1531.64
```

**Fakes** tests-ஐ வேகமாவும் ஒவ்வொரு தடவையும் ஒரே மாதிரியும் வச்சிருக்கும். ஒரு function model client-ஐ parameter-ஆ வாங்கினா (இதுக்கு **dependency injection**-னு பேர்), ஒரு test ஒரு fake-ஐ pass பண்ணலாம்:

```python
class FakeClient:
    def complete(self, prompt):
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

**எதை முதல்ல test பண்றது.** Tests இல்லாத ஒரு project-ல, ஒரு bug அதிக செலவு வைக்கும் இடத்துல ஆரம்பிங்க: பணம் calculations, மத்த systems படிக்குற data, நீங்க மாத்தப்போற code. அப்புறம் நீங்க fix பண்ற ஒவ்வொரு bug-க்கும் ஒரு test சேருங்க. AI projects-ல ரெண்டு வகையை தனியா வைங்க: உங்களோட parsing, validation, scoring logic-க்கு வேகமான unit tests (ஒவ்வொரு commit-லயும் run ஆகும்), golden set-ல உண்மையான model-ஓட மெதுவான evaluation runs (schedule-ல run ஆகும்). ரெண்டையும் கலந்தா அன்றாட tests மெதுவாவும் நம்பகமில்லாமலும் போகும்.

## ஒரு worked example

Chennai-ல ஒரு logistics company-ல invoice-extraction service-ஐ Sneha maintain பண்றாங்க. ₹0.50 rounding வித்தியாசம் இருந்த ஒரு invoice reject ஆச்சுன்னு ஒரு customer report பண்றாரு. வேற எதையும் உடைக்காம அதை fix பண்ண விரும்புறாங்க.

**முதல்ல, fail ஆகுற ஒரு test.** Code-ஐ தொடுறதுக்கு முன்னாடி, bug-ஐ reproduce பண்ற ஒரு test எழுதுறாங்க: lines கூட்டுனா ₹1,180.00, ஆனா அச்சடிச்ச total ₹1,180.50 இருக்குற ஒரு invoice. Business ₹1 வரை rounding-ஐ அனுமதிக்குறதால, அது accept ஆகணும்னு test எதிர்பார்க்குது. pytest run பண்றாங்க: புது test fail ஆகுது; அது bug-ஐ சரியா பிடிக்குதுன்னு இது நிரூபிக்குது.

**அப்புறம் fix.** `validate_total`-ல check `lines_total == printed_total`-ஆ இருந்துச்சு. அதை `abs(lines_total - printed_total) <= 1.0`-ஆ மாத்துறாங்க. புது test pass ஆகுது.

**அப்புறம் edges.** ₹1 tolerance புது கேள்விகளை கிளப்புது, அதனால parametrise பண்றாங்க: சரியா ₹1 வித்தியாசம் accept ஆகும், ₹1.01 reject ஆகும், negative வித்தியாசம் positive மாதிரியே நடத்தப்படும். ஒரு case fail ஆகுது: floating-point error-னால அவங்க check ₹1.01 வித்தியாசத்தை accept பண்ணிடுச்சு. Amounts-ஐ `Decimal`-க்கு மாத்துறாங்க, எல்லா cases-உம் pass ஆகுது.

**கடைசியா, முழு suite.** எல்லா 214 tests-ஐயும் run பண்றாங்க. சம்பந்தமில்லாத ஒரு test fail ஆகுது: forged invoice-ஐ reject பண்ண பழைய exact-match behaviour-ஐ அது சார்ந்திருந்துச்சு. Team-ஓட பேசுறாங்க, forgery check ஒரு தனி rule use பண்ணணும்னு எல்லாரும் ஒத்துக்குறாங்க, ரெண்டையும் update பண்றாங்க. Tests இல்லன்னா, அந்த forgery check production-ல சத்தமில்லாம வேலை செய்றதை நிறுத்தியிருக்கும்.

## பொதுவா பண்ற தப்புகள்

- **Happy path-ஐ மட்டும் test பண்றது.** Bugs edges-ல இருக்கும்: zero, empty lists, negatives, ரொம்ப பெரிய values, missing fields.
- **பத்து விஷயங்களை check பண்ற ஒரே test.** Fail ஆனா எது-ன்னு தெரியாது. ஒரு test-க்கு ஒரு behaviour, என்னன்னு சொல்ற பேரோட.
- **ஒண்ணை ஒண்ணு அல்லது வரிசையை சார்ந்த tests.** ஒவ்வொரு test-உம் தனக்கு வேண்டியதை set up பண்ணி, தனியா pass ஆகணும்.
- **Unit tests-ல உண்மையான network அல்லது model calls.** மெதுவா இருக்கும், காசு செலவாகும், tests-ஐ நம்பகமில்லாம ஆக்கும். Fake பண்ணுங்க; உண்மையான service-ஐ தனியா, அடிக்கடி இல்லாம test பண்ணுங்க.
- **Bug fix பண்ணதுக்கு அப்புறம் tests எழுதுறது.** முதல்ல fail ஆகுற test-ஐ எழுதுங்க; அப்போ அது உண்மையிலேயே bug-ஐ பிடிக்குதுன்னு தெரியும்.
- **100% coverage-ஐ துரத்துறது.** Coverage எது run ஆச்சுன்னு காட்டும், check ஆச்சான்னு இல்லை. முக்கியமான behaviour-ஐ test பண்ணுங்க.

## Practice பண்ணுங்க

1. `gst` function-ஐ copy பண்ணி, மேல இருக்குற மூணு tests-ஐ எழுதி pytest run பண்ணுங்க. அப்புறம் வேணும்னே function-ஐ உடைச்சு failures-ஐ பாருங்க.
2. ஒவ்வொரு GST slab-க்கும் ஒரு parametrised test-உம், rounding-க்கு ஒண்ணும் சேருங்க.
3. ஒரு fake model client-ஐ call பண்ற function எழுதி, ஒரு fixture வச்சு test பண்ணுங்க.
4. ஒரு interview-ல, tests இல்லாத ஒரு project-ல tests-ஐ எப்படி சேர்ப்பீங்கன்னு ஒரு நிமிஷத்துல explain பண்ணுங்க.
