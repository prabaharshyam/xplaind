## இது என்ன

**Test**-னா நீங்க தேர்ந்தெடுக்குற ஒரு input-ஓட உங்க code-ஐ run பண்ணி, result நீங்க எதிர்பார்க்குற மாதிரி இருக்கான்னு check பண்ற ஒரு சின்ன code துண்டு. **Unit test** ஒரு சின்ன பகுதியை, பெரும்பாலும் ஒரு function-ஐ, தனியா check பண்ணும். Result தப்பா இருந்தா test fail ஆகி எங்கன்னு சொல்லும்.

இன்னைக்கு நீங்க எழுதுற code-க்கு விட, அதுக்கு அப்புறம் வர்ற ஒவ்வொரு change-க்கும் தான் tests அதிகம் முக்கியம். ஆறு மாசம் கழிச்சு நீங்களோ உங்க teammate-ஓ ஒரு function-ஐ மாத்துவீங்க. Tests இல்லன்னா, எதுவும் உடையலன்னு தெரிஞ்சுக்க ஒரே வழி app-ல click பண்ணி பார்த்துட்டு நல்லா இருக்கும்னு நம்புறது தான். Tests இருந்தா, ஒரு command run பண்ணா சில வினாடிகள்லயே தெரிஞ்சுடும்.

**pytest** தான் Python-க்கான standard testing tool. `test_`-ல ஆரம்பிக்குற பேர் உள்ள சாதாரண functions எழுதி, சாதாரண `assert` statements use பண்ணுவீங்க. pytest அவற்றை கண்டுபிடிச்சு run பண்ணும்; ஒண்ணு fail ஆனா எந்த values வித்தியாசப்பட்டுச்சுன்னு சரியா காட்டும்.

ஆரம்பத்துல இருந்தே ஒரு limit-ஐ மனசுல வச்சுக்கோங்க: நீங்க check பண்ணணும்னு நினைச்சதை மட்டும் தான் ஒரு test பிடிக்கும். எந்த cases-ன்னு தேர்ந்தெடுக்குறது தான் உண்மையான skill; இந்த lesson-ல பெரும்பாலானது அந்த தேர்வை பத்தி தான்.

## இது எப்படி work ஆகுது

### உங்க முதல் tests

ஒரு test-ல மூணு steps இருக்கும், இதை பெரும்பாலும் **arrange, act, assert**-ன்னு சொல்வாங்க: inputs-ஐ தயார் பண்ணுங்க, code-ஐ ஒரு தடவை call பண்ணுங்க, result-ஐ check பண்ணுங்க.

இதோ ஒரு GST helper. இது Python-ஓட exact decimal type-ஆன `Decimal`-ஐ use பண்ணுது, ஏன்னா money drift ஆகக் கூடாது (ஏன்னு அடுத்த பகுதி காட்டும்). இந்த example-க்கு, finance team-ஓட rule இதுன்னு வச்சுக்கோங்க: paisa-க்கு round பண்ணணும், அரை paisa மேல போகும். அந்த rule ஒரு business முடிவு, அதனால உங்க சொந்த finance team-கிட்ட confirm பண்ணிக்கோங்க.

```python
# gst.py
from decimal import Decimal, ROUND_HALF_UP

PAISA = Decimal("0.01")

def gst(amount: Decimal, rate: Decimal = Decimal("0.18")) -> Decimal:
    """GST on an amount, rounded to the paisa, half a paisa rounded up."""
    if amount < 0:
        raise ValueError("amount must not be negative")
    return (amount * rate).quantize(PAISA, rounding=ROUND_HALF_UP)
```

```python
# test_gst.py
from decimal import Decimal as D
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(D("100")) == D("18.00")

def test_half_paisa_rounds_up():
    # 100.25 x 0.18 = 18.045 exactly, so it must round up to 18.05
    assert gst(D("100.25")) == D("18.05")

def test_negative_amount_is_refused():
    with pytest.raises(ValueError, match="negative"):
        gst(D("-1"))
```

Folder-ல `pytest` run பண்ணா அது `3 passed`-ன்னு print பண்ணும். ஒவ்வொரு பேரும் அது எதிர்பார்க்குற behaviour-ஐ சொல்லுது, அதனால failure report ஒரு வாக்கியம் மாதிரி படிக்கும். `match=` error message-ஐயும் check பண்ணும், அதனால வேற ஏதோ ஒரு `ValueError`-னால test தற்செயலா pass ஆகாது.

நீங்க work பண்ற loop:

```flow
dir: LR
Code எழுது அல்லது மாத்து -> pytest run பண்ணு
pytest run பண்ணு -[ஒரு test fail ஆகுது]-> Failure-ஐ படி | எந்த values வித்தியாசப்பட்டுச்சு
Failure-ஐ படி -> Code எழுது அல்லது மாத்து
pytest run பண்ணு -[எல்லாம் pass]-> Commit
```

### Money-யும் floats-உம்

ஏன் சாதாரண floats வேண்டாம்? அதே function-ஐ `round(amount * rate, 2)`-ஓட எழுதுங்க, rounding test fail ஆகும்:

```
>       assert gst(100.25) == 18.05
E       assert 18.04 == 18.05
E        +  where 18.04 = gst(100.25)
```

ஒரு float numbers-ஐ binary-ல store பண்ணும், பெரும்பாலான decimal fractions-க்கு exact binary வடிவம் கிடையாது. `100.25 * 0.18` 18.044999999999998...-ஆ store ஆகுது, நடுப்புள்ளிக்கு கொஞ்சம் கீழ, அதனால அது கீழ round ஆகுது. இந்த error 15-வது digit-ல ஒளிஞ்சிருக்கல: customer ஒரு paisa தப்பா இருக்குற bill-ஐ பார்ப்பாங்க. இதுல இருந்து மூணு rules வருது:

- **Money:** strings-ல இருந்து build பண்ண `Decimal` use பண்ணுங்க (`Decimal("100.25")`), அல்லது முழு paise-ஐ integers-ஆ store பண்ணுங்க. `Decimal(0.1)`-ன்னு எப்பவும் எழுதாதீங்க: அது float-ஓட error-ஐ copy பண்ணி 0.1000000000000000055511151231257827.... தரும்.
- **Money இல்லாத floats** (ஒரு model-ஓட confidence score, ஒரு average, ஒரு similarity): `pytest.approx`-ஓட compare பண்ணுங்க; default-ஆ அது பத்து லட்சத்துல ஒண்ணு அளவுக்கு relative difference-ஐ அனுமதிக்கும்.
- **Compute பண்ண floats மேல `==` எப்பவும் வேண்டாம்.** Inputs மாறுற வரைக்கும் தான் அது உங்க laptop-ல வேலை செய்யும்.

```python
def test_mean_score_needs_approx():
    # (0.1 + 0.2) / 2 is 0.15000000000000002, so == 0.15 alone fails
    assert (0.1 + 0.2) / 2 == pytest.approx(0.15)
```

### Copy பண்றதுக்கு பதிலா parametrise பண்ணுங்க

22 September 2025-ல இருந்து, GST-க்கு ரெண்டு main slabs இருக்கு, 5%, 18%; அதோட sugary fizzy drinks, பெரிய cars மாதிரி ஒரு சின்ன set of goods-க்கு ஒரு special 40% rate. (பழைய 12%, 28% slabs எடுக்கப்பட்டுச்சு, ஆனா சில special rates இன்னும் இருக்கு.) ஒரே parametrised test slabs-ஐயும் zero edges-ஐயும் cover பண்ணும்:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (D("1000"), D("0.05"), D("50.00")),
    (D("1000"), D("0.18"), D("180.00")),
    (D("1000"), D("0.40"), D("400.00")),
    (D("1000"), D("0"), D("0.00")),
    (D("0"), D("0.18"), D("0.00")),
], ids=["5-percent", "18-percent", "40-percent", "zero-rate", "zero-amount"])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

ஒவ்வொரு row-உம் தனி test-ஆ report ஆகும், உதாரணமா `test_rates[40-percent]`, அதனால failure case-ஓட பேரை சொல்லும். `ids` இல்லன்னா pytest இந்த rows-க்கு `amount0-rate0-expected0` மாதிரி பேர் வைக்கும், அது படிக்க கஷ்டம்.

### Fixtures-உம் conftest.py-உம்

**Fixture**-னா ஒரு test அதோட பேரை parameter-ஆ குடுத்து கேக்குற shared setup. பல test files use பண்ற fixtures-ஐ `conftest.py`-ல வைங்க; pytest அந்த file-ஐ தானாவே load பண்ணும், import தேவையில்ல.

```python
# invoice.py
from decimal import Decimal
from gst import gst

def invoice_total(invoice: dict) -> Decimal:
    subtotal = sum((price for _, price in invoice["items"]), Decimal("0"))
    return subtotal + gst(subtotal, invoice["rate"])
```

```python
# conftest.py
from decimal import Decimal as D
import pytest

@pytest.fixture
def invoice():
    return {"items": [("Charger", D("999.00")), ("Cable", D("299.00"))],
            "rate": D("0.18")}
```

```python
# test_invoice.py
from decimal import Decimal as D
from invoice import invoice_total

def test_total_adds_gst_to_subtotal(invoice):
    assert invoice_total(invoice) == D("1531.64")   # 1298.00 + 233.64

def test_empty_invoice_totals_zero(invoice):
    invoice["items"] = []          # changes only this test's copy
    assert invoice_total(invoice) == D("0")
```

Default-ஆ ஒரு fixture ஒவ்வொரு test-க்கும் மறுபடியும் run ஆகும், அதனால ஒரு test அதை மாத்தினா இன்னொரு test உடையாது. மெதுவா இருக்குற, எப்பவும் மாறாத setup-க்கு மட்டும் (ஒரு பெரிய sample file-ஐ load பண்றது மாதிரி) wider scope (`scope="session"`) use பண்ணுங்க. ஒரு fixture அதோட value-ஐ `yield` பண்ணி, `yield`-க்கு அப்புறம் clean up பண்ணலாம். Built-in `tmp_path` fixture, files எழுதுற code-க்காக, ஒவ்வொரு test-க்கும் ஒரு புது temporary folder தரும்.

### Model, API calls-க்கு fakes

உண்மையான model calls மெதுவா இருக்கும், காசு செலவாகும், ஒவ்வொரு தடவையும் வேற reply தரலாம். Unit tests-ல, அவற்றை ஒரு fixed reply return பண்ற **fake**-ஆல மாத்துங்க. இப்படி ஒரு பகுதியை மாத்துறதுக்கு **mocking**-ன்னு பேர்.

Code-ஐ நீங்களே எழுதுறீங்கன்னா, client-ஐ ஒரு parameter-ஆ pass பண்றது தான் cleanest design. இதுக்கு **dependency injection**-ன்னு பேர்:

```python
# triage.py
import json

def classify(ticket: str, client) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    return json.loads(reply)["category"]
```

```python
# test_triage.py
from triage import classify

class FakeClient:
    def complete(self, prompt: str) -> str:
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

நீங்க inherit பண்ற பெரும்பாலான code, அதுக்கு பதிலா, client-ஐ module level-ல ஒரு தடவை create பண்ணும். அப்போ pytest-ஓட `monkeypatch`-ஓட அதை swap பண்ணுங்க; test முடிஞ்சதும் அது original-ஐ திரும்ப வச்சிடும். `unittest.mock.Mock` fake-ஐ build பண்ணி, அது எப்படி call ஆச்சுன்னு record பண்ணும். இந்த version bad replies-ஐயும் handle பண்ணுது; AI projects-ல எல்லாத்தையும் விட test பண்ண தகுதியான code இது தான்:

```python
# llm.py
class ModelClient:
    """Stands in for a real model SDK client."""
    def complete(self, prompt: str) -> str:
        raise RuntimeError("this would make a real, paid network call")
```

```python
# tickets.py
import json
from llm import ModelClient

client = ModelClient()          # created once, when the module is imported
CATEGORIES = {"refund", "delivery", "other"}

def classify(ticket: str) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    try:
        category = json.loads(reply)["category"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return "needs_review"
    return category if category in CATEGORIES else "needs_review"
```

```python
# test_tickets.py
from unittest.mock import Mock
import pytest
import tickets
from llm import ModelClient

def fake_client(reply: str) -> Mock:
    fake = Mock(spec=ModelClient)    # only methods the real client has
    fake.complete.return_value = reply
    return fake

def test_reads_category_and_sends_ticket(monkeypatch):
    fake = fake_client('{"category": "refund"}')
    monkeypatch.setattr(tickets, "client", fake)
    assert tickets.classify("Money not returned") == "refund"
    fake.complete.assert_called_once()
    assert "Money not returned" in fake.complete.call_args.args[0]

@pytest.mark.parametrize("reply", [
    "Sure! This looks like a refund.",   # prose, not JSON
    '{"label": "refund"}',               # wrong key
    '{"category": "lottery"}',           # unknown category
    "null",                              # valid JSON, wrong shape
    "",                                  # empty reply
])
def test_bad_reply_goes_to_review(monkeypatch, reply):
    monkeypatch.setattr(tickets, "client", fake_client(reply))
    assert tickets.classify("Where is my parcel?") == "needs_review"
```

அனுபவமுள்ள engineers-ஐயும் மாட்டிவிடுற ரெண்டு gotchas:

- **பேர் எங்க use ஆகுதோ அங்க patch பண்ணுங்க, எங்க define ஆகுதோ அங்க இல்ல.** `tickets.py` `from llm import client`-ன்னு எழுதியிருந்தா, அதுக்கு அந்த பேரோட சொந்த copy இருக்கும்; அதனால `llm.client`-ஐ patch பண்ணா எதுவும் மாறாது, உண்மையான call இன்னும் run ஆகும். `tickets.client`-ஐ patch பண்ணுங்க.
- **சாதாரண `Mock()` எந்த attribute-ஐயும் ஏத்துக்கும்.** ஒரு typo, அல்லது உண்மையான client-ல rename ஆன ஒரு method, test-ல இன்னும் "வேலை செய்யும்", bug production-க்கு போயிடும். `Mock(spec=ModelClient)` உண்மையான class-ல இல்லாத எதுக்கும் `AttributeError` raise பண்ணும்.

எதை use பண்றது:

| நிலைமை | Use பண்ணுங்க | ஏன் |
| --- | --- | --- |
| நீங்க எழுதுற புது code | Client-ஐ pass பண்ணுங்க (dependency injection) | Patching இல்ல; code-க்கு என்ன தேவைன்னு test சரியா காட்டும் |
| Module-level client உள்ள inherited code | அதை use பண்ற module மேல `monkeypatch.setattr` | ஒரு test-க்கு ஒரு பேரை swap பண்ணி, அப்புறம் restore பண்ணும் |
| என்ன அனுப்புச்சுன்னு (prompt மாதிரி) check பண்ணியே ஆகணும் | `Mock(spec=...)`, `call_args` | ஒவ்வொரு call-ஐயும் record பண்ணும்; spec typos-ஐ பிடிக்கும் |
| Files எழுதுற code | Built-in `tmp_path` fixture | ஒவ்வொரு test-க்கும் ஒரு புது folder, எதுவும் மிச்சம் இருக்காது |
| உண்மையான model-ஓட behaviour | Golden set மேல ஒரு evaluation run, unit test இல்ல | Unit tests பதிலோட quality-ஐ judge பண்ண முடியாது |

### Unit tests vs evaluations

AI projects-ல ரெண்டு வகை test-ஐ தனித்தனியா வைங்க. வேகமான unit tests உங்க சொந்த logic-ஐ check பண்ணும்: prompts build பண்றது, replies-ஐ parse பண்றது, validation, scoring. அவை ஒவ்வொரு commit-லயும் run ஆகும். மெதுவான **evaluations** ஒரு fixed golden set of inputs-ஐ உண்மையான model-க்கு அனுப்பி பதில்களை score பண்ணும்; ஒரு prompt change அல்லது model update results-ஐ மோசமாக்கிடுச்சான்னு பிடிக்க. அவற்றை எப்படி build பண்றதுன்னு "Test sets and evals" lesson (P1) சொல்லும். ரெண்டையும் கலந்தா தினசரி tests மெதுவா, செலவா, flaky-ஆ ஆயிடும்.

ஒரு **marker** அவற்றை தனியா வைக்கும். அதை `pyproject.toml`-ல register பண்ணுங்க; `--strict-markers` தப்பா type பண்ண marker-ஐ warning-ஆ இல்லாம error-ஆ மாத்தும்:

```toml
[tool.pytest.ini_options]
addopts = "--strict-markers"
markers = ["eval: calls the real model on the golden set; run on a schedule"]
```

ஒவ்வொரு evaluation test-க்கும் `@pytest.mark.eval` tag போடுங்க, ஒவ்வொரு commit-லயும் `pytest -m "not eval"` run பண்ணுங்க.

### தினமும் tests run பண்றது

| Command | என்ன பண்ணும் |
| --- | --- |
| `pytest -x` | முதல் failure-லயே நிறுத்தும் |
| `pytest -k rounding` | பேர்ல "rounding" இருக்குற tests-ஐ மட்டும் run பண்ணும் |
| `pytest test_gst.py::test_half_paisa_rounds_up` | ஒரு test-ஐ run பண்ணும் |
| `pytest --lf` | போன தடவை fail ஆன tests-ஐ மட்டும் மறுபடி run பண்ணும் |
| `pytest -m "not eval"` | `eval`-ன்னு mark பண்ண tests-ஐ skip பண்ணும் |
| `pytest --cov=. --cov-report=term-missing` | Coverage-ஐ காட்டும், எந்த test-உம் run பண்ணாத line numbers-ஓட (`pytest-cov` package தேவை) |

**Coverage**-னா tests நடக்கும்போது உங்க code-ல எவ்வளவு பங்கு run ஆச்சுங்கிறது. "Missing" column-ஐ படிங்க: எந்த test-உம் run பண்ணாத lines-ஐ அது list பண்ணும், அவை தான் உங்க blind spots. ஒரு `if`-ஓட true அல்லது false side எப்பவுமே run ஆகலைன்னா அதையும் பார்க்க `--cov-branch` சேருங்க. ஆனா coverage, code run ஆச்சுன்னு மட்டும் தான் நிரூபிக்கும், ஏதாவது result-ஐ check பண்ணுச்சுன்னு இல்ல: `assert` இல்லாம `gst(D("100"))`-ஐ call பண்ற ஒரு test-உம் கணக்குல வரும். Gaps-ஐ கண்டுபிடிக்க அதை use பண்ணுங்க, 100% அடைய வேண்டிய score-ஆ இல்ல.

**Continuous integration (CI)** ஒவ்வொரு push அல்லது pull request-க்கும் அதே command-ஐ ஒரு clean machine-ல run பண்ணும்; அது fail ஆனா team merging-ஐ block பண்ணும். உங்க laptop-ல pass ஆகுற ரெண்டு விஷயங்கள் அங்க உடையும். முதல்ல, CI machine-ல உங்க project list பண்ற packages மட்டும் தான் இருக்கும், அதனால ஒரு missing dependency வெளிய தெரிஞ்சுடும். ரெண்டாவது, CI machines பெரும்பாலும் UTC use பண்ணும், இது India-வை விட ஐந்தரை மணி நேரம் பின்னாடி. அப்போ "இன்னைக்கு" பத்தின ஒரு test, IST நள்ளிரவு 12-ல இருந்து காலை 5:30 வரைக்கும் run ஆனா fail ஆகலாம். Date அல்லது clock-ஐ உங்க code-க்குள்ள pass பண்ணுங்க, machine-ஓட setting-ஐ நம்பாம time zone-ஐ பேர் சொல்லி குடுங்க (`ZoneInfo("Asia/Kolkata")`).

### எதை முதல்ல test பண்றது

Tests இல்லாத ஒரு project-ல, bug வந்தா எங்க எல்லாத்தையும் விட அதிக நஷ்டம் ஆகுமோ அங்க ஆரம்பிங்க:

1. **Money-யும் legal சம்பந்தப்பட்ட எதுவும்:** totals, tax, refunds, limits.
2. **மத்த systems படிக்குற data:** உங்க API return பண்ற JSON, நீங்க export பண்ற CSV.
3. **நீங்க மாத்தப்போற code:** முதல்ல அதோட இப்போதைய behaviour-ஐ pin பண்ற tests எழுதுங்க, அப்புறம் மாத்துங்க.
4. **நீங்க fix பண்ற ஒவ்வொரு bug-உம்:** முதல்ல அதை reproduce பண்ற ஒரு test, அப்புறம் fix. இது ஒரு **regression test**; அதே bug திரும்ப வர்றதை இது தடுக்கும்.

Project-ல tests எங்க இருக்கும்னு (ஒரு `tests/` folder, ஒரு `src` layout, README commands) "Project tooling: environments, tests and logs" lesson-ல பாருங்க.

## ஒரு worked example

Sneha, Chennai-ல ஒரு logistics company-ல ஒரு invoice-extraction service-ஐ maintain பண்றாங்க. இந்த service ஒரு scan பண்ண invoice-ஐ படிச்சு, line amounts-ஐயும் print ஆன total-ஐயும் எடுத்து, ரெண்டும் ஒத்துப்போகலன்னா invoice-ஐ reject பண்ணும். ஒரு உண்மையான invoice reject ஆச்சுன்னு ஒரு customer report பண்றாங்க. அதோட lines: freight ₹1,040.37, loading ₹128.98, toll ₹10.65; இவற்றை கூட்டினா ₹1,180.00, ஆனா print ஆன total ₹1,180.50. Business ₹1 வரைக்கும் rounding difference-ஐ அனுமதிக்குது (இந்த example-க்காக வச்ச ஒரு illustrative rule).

**முதல்ல, fail ஆகுற ஒரு test.** Code-ஐ தொடுறதுக்கு முன்னாடி, bug-ஐ reproduce பண்ணி, invoice accept ஆகணும்னு எதிர்பார்க்குற ஒரு test-ஐ எழுதுறாங்க. pytest run பண்றாங்க, புது test fail ஆகுது. Test உண்மையிலேயே bug-ஐ பிடிக்குதுன்னு அது நிரூபிக்குது; fix-க்கு முன்னாடியே pass ஆகுற test எதையும் நிரூபிக்காது.

**அப்புறம் fix.** பழைய check `sum(lines) == printed_total`. அதை ₹1.00 வரைக்கும் difference-ஐ அனுமதிக்குற மாதிரி மாத்துறாங்க, புது test pass ஆகுது.

**அப்புறம் edges.** ஒரு limit-க்கு ரெண்டு edges இருக்கு, அதனால parametrise பண்றாங்க: சரியா ₹1 மேலயும் சரியா ₹1 கீழயும் accept ஆகணும், எந்த பக்கமா இருந்தாலும் ₹1.01 reject ஆகணும். ஒரு case fail ஆகுது: சரியா ₹1 மேல இருக்குறது reject ஆகுது. Floats தான் காரணம். Python 3.12 அல்லது அதுக்கு அப்புறம் வந்த versions-ல, மூணு lines-ஓட `sum()` 1180 இல்ல, `1179.9999999999998` தருது (பழைய versions-ல, அல்லது `+`-ஓட கூட்டினா, தற்செயலா 1180.0 வருது); அதனால 1181.00-ல இருந்து difference `1.0000000000002274`, limit-க்கு கொஞ்சம் மேல. Extractor amounts-ஐ text-ஆ குடுக்கவும், check `Decimal` use பண்ணவும் மாத்துறாங்க:

```python
# validate.py
from decimal import Decimal

TOLERANCE = Decimal("1.00")          # business rule: up to Rs 1 of rounding

def total_is_valid(line_amounts: list[str], printed_total: str) -> bool:
    lines_total = sum((Decimal(a) for a in line_amounts), Decimal("0"))
    return abs(lines_total - Decimal(printed_total)) <= TOLERANCE
```

```python
# test_validate.py
import pytest
from validate import total_is_valid

LINES = ["1040.37", "128.98", "10.65"]      # add up to exactly 1180.00

@pytest.mark.parametrize("printed, expected", [
    ("1180.50", True),    # the customer's bug: 50 paise of rounding
    ("1181.00", True),    # exactly Rs 1 over: allowed
    ("1179.00", True),    # exactly Rs 1 under: allowed
    ("1181.01", False),   # just over the limit
    ("1178.99", False),   # just under the limit
], ids=["50-paise", "plus-1", "minus-1", "plus-1.01", "minus-1.01"])
def test_rounding_tolerance(printed, expected):
    assert total_is_valid(LINES, printed) is expected
```

அஞ்சு cases-உம் pass ஆகுது. Float bug-ஐ கண்டுபிடிச்சது எதுன்னு கவனிங்க: customer-ஓட case இல்ல, சரியா limit மேல இருக்குற edge தான். Bugs இருக்குற இடம் edges தான்.

**கடைசியா, முழு suite.** Project-ல இருக்குற எல்லா tests-ஐயும், சில நூறு tests, ஒரு நிமிஷத்துக்குள்ள run பண்றாங்க. சம்பந்தமில்லாத ஒரு test fail ஆகுது: சில paise மாத்தப்பட்ட total உள்ள ஒரு போலி invoice-ஐ reject பண்ண அது பழைய exact match-ஐ நம்பியிருந்துச்சு. அவங்க team-கிட்ட பேசுறாங்க. Forgery check-க்கு தனி rule தேவைன்னு எல்லாரும் ஒத்துக்குறாங்க, அவங்க ரெண்டையும் update பண்றாங்க. Tests இல்லன்னா, அந்த forgery check production-ல வேலை செய்யாம போயிருக்கும், யாரும் கவனிச்சிருக்க மாட்டாங்க.

## பொதுவா பண்ற தப்புகள்

- **Happy path-ஐ மட்டும் test பண்றது.** Bugs edges-ல தான் இருக்கும்: zero, empty lists, negatives, சரியான limit, ரொம்ப பெரிய values, missing fields.
- **பத்து விஷயங்களை check பண்ற ஒரே test.** அது fail ஆனா எதுன்னு சொல்ல முடியாது. ஒரு test-க்கு ஒரு behaviour, என்னன்னு சொல்ற பேரோட.
- **ஒண்ணுக்கொண்ணு அல்லது order-ஐ சார்ந்திருக்குற tests.** ஒவ்வொரு test-உம் தனக்கு தேவையானதை set up பண்ணி, தனியா run பண்ணாலும் pass ஆகணும். Module level-ல இருக்குற shared lists அல்லது dictionaries தான் வழக்கமான காரணம்.
- **Unit tests-ல உண்மையான network அல்லது model calls.** அவை மெதுவா இருக்கும், காசு செலவாகும், tests-ஐ flaky ஆக்கும். அவற்றை fake பண்ணுங்க, உண்மையான model-ஐ ஒரு scheduled evaluation run-ஓட judge பண்ணுங்க.
- **Floats-ஐ `==`-ஓட compare பண்றது, அல்லது float-ல இருந்து `Decimal` build பண்றது.** Money-க்கு `Decimal("1.10")`, மத்த floats-க்கு `pytest.approx` use பண்ணுங்க.
- **தப்பான இடத்துல patch பண்றது, அல்லது `spec` இல்லாம `Mock` use பண்றது.** உண்மையான call இன்னும் run ஆகும், அல்லது ஒரு typo சத்தமில்லாம pass ஆகும்.
- **Code என்ன பண்ணுதுன்னு இல்லாம, அது எப்படி work ஆகுதுன்னு test பண்றது.** எந்த private helper call ஆச்சுன்னு check பண்ற test, ஒவ்வொரு harmless refactor-லயும் உடையும். Outputs-ஐயும் வெளிய தெரியுற effects-ஐயும் check பண்ணுங்க.
- **Fail ஆகுறதை நீங்க ஒரு தடவை கூட பார்க்காத test.** அதை fix-க்கு முன்னாடி எழுதுங்க, அல்லது ஒரு தடவை வேணும்னே code-ஐ உடைச்சு பாருங்க. Fail ஆகவே முடியாத test எதையும் பாதுகாக்காது.
- **Clock அல்லது machine-ஓட time zone-ஐ சார்ந்திருக்குறது.** Dates-ஐ pass பண்ணுங்க, நாள் முக்கியம்னா `Asia/Kolkata`-ன்னு பேர் சொல்லுங்க.
- **100% coverage-க்கு பின்னாடி ஓடுறது.** Coverage என்ன run ஆச்சுன்னு காட்டும், அது check ஆச்சான்னு இல்ல. முக்கியமான behaviour-ஐ test பண்ணுங்க.
