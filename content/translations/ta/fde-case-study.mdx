## இது எப்படி work ஆகுது

### Discovery: கேட்டது தப்பு

கேட்டது "customers-க்கு ஒரு chatbot". ஒன்பது interviews-உம், loan team-ஐ அரை நாள் கவனிச்சதும், customer queries-ஐ call centre ஏற்கனவே நல்லா handle பண்ணுதுன்னு காட்டுச்சு. வலி உள்ளே தான் இருந்துச்சு: officers ஒரு file-க்கு சுமார் 40 நிமிஷம் bank statements, salary slips, bureau reports படிக்கிறதுலயும், figures-ஐ திரும்ப type பண்றதுலயும், ஒரு credit note எழுதுறதுலயும் செலவு பண்ணாங்க. மாசம் 6,000 files-னா, அது சுமார் 4,000 officer-hours. Retype பண்றப்போ வர்ற தப்புகளால 7% files credit committee-ல இருந்து திரும்ப வந்துச்சு.

Head of operations-க்கு ஒத்துப்போற numbers-ஓட வந்ததால தான் இந்த reframe work ஆச்சு. Discovery numbers estimates தான், அதனால contract-க்கு முன்னாடியே team loan-system timestamps-ல இருந்து உண்மையான baseline-ஐ அளந்துச்சு: நாலு வாரம், 6,200 files-ல median 41 நிமிஷம்.

### KPI, scope

- **KPI**: ஒரு file-க்கு median officer time, pilot ஆரம்பிச்சு பத்து வாரத்துக்குள்ள 41-ல இருந்து 22 நிமிஷம்.
- **Guardrail**: rework 7%-ஐ தாண்டக்கூடாது. **Adoption**: officers அவங்க files-ல குறைஞ்சது 80%-ல draft-ஐ use பண்ணணும்.
- **Scope-க்குள்ள**: English PDFs, phone photos-ல இருந்து 24 fields, அதுல 10 critical; ஒரு draft credit note; ஒரு review screen.
- **Scope-க்கு வெளியே**: credit decisions, customer features, மத்த மொழிகள்.

### Proof of concept: average மறைச்சது

Golden set-னா ஆறு branches-ல இருந்து 300 masked பழைய files, இரண்டு senior officers தனித்தனியா label பண்ணது. அவங்க ஒத்துப்போகாத இடத்துல credit head முடிவு பண்ணாங்க. 300 files-ல பத்து critical fields-னா score பண்ண 3,000 values.

ஒவ்வொரு document-ஐயும் ஒரு structured-output model call படிச்சுது, ஒவ்வொரு value-உம் ஒரு schema-வை pass பண்ணணும். இது ஒரு பகுதி:

```python
from decimal import Decimal
from typing import Literal
from pydantic import BaseModel, Field, model_validator

class Source(BaseModel):
    page: int = Field(ge=1)
    text: str = Field(min_length=1)  # the exact words the value was read from

class Amount(BaseModel):
    rupees: Decimal | None  # None if the document does not show it
    source: Source | None
    confidence: Literal["high", "low"]

class SalarySlip(BaseModel):
    employer: str
    month: str = Field(pattern=r"^\d{4}-\d{2}$")  # for example 2026-06
    gross_pay: Amount
    net_pay: Amount  # critical field

    @model_validator(mode="after")
    def net_not_above_gross(self):
        g, n = self.gross_pay.rupees, self.net_pay.rupees
        if g is not None and n is not None and n > g:
            raise ValueError("net pay above gross pay: re-read or flag")
        return self
```

மூணு choices copy பண்ண தகுந்தவை. ஒவ்வொரு value-உம் அதோட page-ஐயும் அது வந்த வார்த்தைகளையும் கூடவே கொண்டு வருது, அதனால ஒரு officer சில seconds-ல அதை check பண்ணலாம். ஒரு value இல்லைன்னா அது `None`, எப்பவுமே guess இல்ல. "Net pay gross pay-ஐ தாண்ட முடியாது" மாதிரி cross-checks, ஒரு format check miss பண்ற தப்பான reads-ஐ பிடிக்குது. "Low" confidence-ங்குறது model தன்னைப் பத்தி சொல்ற அபிப்பிராயம் இல்ல, அது நம்பகமானது இல்ல. அதை rules set பண்ணுச்சு: மோசமான image-quality score, fail ஆன ஒரு cross-check, அல்லது ஒத்துப்போகாத இரண்டு reads.

முதல் result 93%, 95% gate-க்கு கீழ. Golden set-ஐ document source வாரியா பிரிச்சப்போ ஏன்னு தெரிஞ்சுது:

| Slice | Score பண்ண values | முதல் run | Image clean-up-க்கு அப்புறம் |
| --- | --- | --- | --- |
| Net banking, HR systems-ல இருந்து வந்த PDFs (180 files) | 1,800 | 98.0% | 98.0% |
| Phone photos (120 files) | 1,200 | 85.5% | 94.0% |
| எல்லா files | 3,000 | 93.0% | 96.4% |

பெரும்பாலான misses, page முழுக்க இருண்ட நிழல் விழுந்த phone photos. ஒரு image clean-up step (நேரா ஆக்குறது, வெளிச்சத்தை சமமாக்குறது), low-confidence flag ரெண்டும் அதுல பெரும்பாலானதை சரி பண்ணுச்சு. Expert சொல்ற point-ஐ கவனிங்க: மொத்த figure pass ஆச்சு, ஆனா photos மட்டும் தனியா இன்னும் pass ஆகல. அதனால gate note அதை வெளிப்படையா சொல்லுச்சு:

> **Gate 1, week 4.** Criteria: 300 files முழுக்க 10 critical fields-ல குறைஞ்சது 95%; ஒவ்வொரு summary-உம் அதோட source pages-ஐ cite பண்ணணும். Result: மொத்தம் 96.4% (PDFs 98.0%, photos 94.0%); ஒவ்வொரு summary-லயும் citations. Head of operations-ஓட முடிவு: இரண்டு conditions-ஓட pilot-க்கு போகலாம். Low-confidence flag எப்பவும் on-ல இருக்கும், photo slice ஒவ்வொரு வாரமும் தனியா report பண்ணப்படும்.

### Pilot-க்கான engineering

Pilot system weeks 3, 4-ல build ஆச்சு, proof of concept-ஓட கடைசி கூடவே. Lender-ஓட risk team ஏற்கனவே ஒரு இந்திய region-ல அவங்க சொந்த Azure tenancy-ஐ approve பண்ணியிருந்தாங்க, அதனால புது vendor approval ஆரம்பிக்காம, models அந்த tenancy வழியா, ஒரு fallback-ஓட ஒரு gateway-க்கு பின்னாடி use ஆச்சு. Service containers-ல ஓடுச்சு, CI-ல evals, Entra ID வழியா sign-on, ஒவ்வொரு officer-ஓட branch படி documents filter, ஒவ்வொரு view, edit-க்கும் ஒரு audit log, traces-ல personal data mask.

Risk team-ஓட கேள்விகள் உங்க சொந்த வேலைக்கு ஒரு useful list. Data எங்க store, process ஆகுது? Provider அதை models-ஐ train பண்ண use பண்ணலாமா? எந்த files-ஐ யார் பார்க்கலாம்? எது log ஆகுது, எவ்வளவு நாள்? Logs, eval set உட்பட எல்லா இடத்துலயும் ஒரு customer-ஓட data எப்படி அழிக்கப்படுது? FDE ஒவ்வொண்ணுக்கும் எழுத்துல பதில் சொன்னாங்க, provider-ஓட published data-privacy terms-ஐ ஒரு link-ஓட quote பண்ணி, ஞாபகத்துல இருந்து இல்ல.

### Pilot: ஆளுங்க, scope, லேட்டான ஒரு review

Anna Nagar, Tambaram-ங்குற இரண்டு branches-ல இருபது officers பத்து வாரம் இதை use பண்ணாங்க, ஒரு weekly demo, ஒரு risk log-ஓட.

- **Week 6.** Production security review schedule ஆகவே இல்ல. அதே நாள் CIO office-க்கு escalate பண்ணதும், week 9-க்கு book ஆச்சு; production gate-ஐ அது block பண்ணியிருக்கும் நேரத்துக்கு மூணு வாரம் முன்னாடி.
- **Week 7.** Adoption Anna Nagar-ல 92%, Tambaram-ல 41%. எந்த figure தப்பா இருந்தாலும் "AI-ஓ இல்லையோ" அது officer-ஓட தப்புன்னு branch manager சொல்லியிருந்தாரு, அதனால safe-ஆ இருக்க officers எல்லாத்தையும் திரும்ப type பண்ணாங்க. Officers எதுக்கு பொறுப்புன்னு head of operations எழுதி குடுத்தாங்க: week 8-ல சேர்த்த side-by-side review screen-ஐ use பண்ணி, flag ஆன fields-ஐயும் critical fields-ஐயும் review பண்றது. திரும்ப training, ஒரு regional summary template-ஓட, Tambaram இரண்டு வாரத்துல 85%-க்கு வந்துச்சு.
- **Week 7.** ஒரே வாரத்துல மூணு change requests வந்துச்சு. Collections summaries phase 2-க்கு போச்சு. PDF export-க்கு பதிலா Tamil salary slips swap பண்ணப்பட்டு week 9-ல ship ஆச்சு. Approve-or-reject recommendations decline ஆச்சு, ஏன்னா credit decisions scope-க்கு வெளியே.

Result: median 24 நிமிஷம், 5.1% rework, 88% adoption. 22 நிமிஷ target கொஞ்சத்துல miss ஆச்சு. Measures முன்னாடியே agree பண்ணதால, client success-னா என்னன்னு இல்லாம rollout பத்தி பேசுனாங்க.

### இரண்டு வாரத்தை வீணாக்குன தப்பான திருப்பம்

Proof of concept-ல கிடைச்சதுலயே பெரிய model எல்லா page-ஐயும் படிச்சுது, ஏன்னா அது தான் best-ஆ score பண்ணுச்சு. POC report 300 files-ல ஒரு file-க்கான cost-ஐ காட்டுச்சு, அது சின்னதா தெரிஞ்சுது. Retries-உம், ஒவ்வொரு page கூடவும் அனுப்புற நீளமான fixed instructions-உம் சேர்த்து, மாசம் 6,000 files-க்கு யாரும் அதை பெருக்கிப் பார்க்கல.

Week 10-ல business case-க்காக FDE full-volume projection-ஐ build பண்ணப்போ அதை கண்டுபிடிச்சாங்க: மாசம் சுமார் ₹14 lakh, அதாவது ஒரு file-க்கு ₹233, ஆனா ஒரு file-க்கு value சுமார் ₹173 தான். அந்த விலையில rollout நஷ்டத்துல தான் போகும்.

எந்த memo-வும் எழுதுறதுக்கு முன்னாடி, அந்த வார update-லயே head of operations-கிட்ட, ஒரு fix plan-உம் ஒரு தேதியும் கூட ஒரு risk-ஆ சொன்னாங்க. Weeks 11, 12-ல team typed PDFs-ஐ ஒரு சின்ன model-க்கு அனுப்புச்சு, photos-க்கும் low-confidence pages-க்கும் மட்டும் பெரிய model-ஐ வச்சுது. Fixed instructions-ஐ cache பண்ணாங்க, ஏற்கனவே extract ஆன pages-ஐ திரும்ப படிக்கிறதை நிறுத்துனாங்க. Golden set-ஐ திரும்ப run பண்ணப்போ accuracy-ல எந்த இழப்பும் இல்ல. Cost மாசம் சுமார் ₹9 lakh-க்கு, ஒரு file-க்கு ₹150-க்கு குறைஞ்சுது. அதுக்கு ஆன விலை இரண்டு engineer-weeks, அதை FDE-ஓட side ஏத்துக்கிச்சு, ஒரு audit-report export முதல் rollout wave-க்கு தள்ளிப்போச்சு.

### Business case

CEO, CFO-க்கான memo, value-ஐயும் cost-ஐயும் ஒரே unit-ல compare பண்ணுச்சு, ஒரு file-க்கு 26 நிமிஷம்ங்குற ஒரு cautious planning figure-ல. Officer time-க்கு lender-ஓட சொந்த HR figure-ஆன மணிக்கு சுமார் ₹600, loaded, value போட்டாங்க.

| Line | மாசத்துக்கு |
| --- | --- |
| மிச்சமான நேரம்: 6,000 files × 15 min = 1,500 hours × ₹600 | ₹9.0 lakh |
| குறைவா திரும்ப வர்ற files: 114 × 2 hours × ₹600 | ₹1.4 lakh |
| Running cost, எல்லாம் சேர்த்து | ₹9.0 lakh |
| Net value | மாசம் ₹1.4 lakh, வருஷத்துக்கு சுமார் ₹16 lakh (pilot-ஓட 24 நிமிஷத்துல சுமார் ₹31 lakh) |
| Break-even | ஒரு file-க்கு சுமார் 13 நிமிஷம் மிச்சம் |

இது ஒரு modest case, memo-வும் அதை சொல்லுச்சு: இந்திய salaries-ல மிச்சமான நேரம் running cost-ஐ கஷ்டப்பட்டு தான் cover பண்ணுது, margin quality-ல இருந்து தான் வருது. முதல் draft வருஷத்துக்கு ₹50 lakh value-ஐ மாசத்துக்கு ₹9 lakh cost கூட compare பண்ணியிருந்துச்சு, அந்த cost வருஷத்துக்கு ₹1.08 crore. Meeting-க்கு முந்தின நாள் CFO-ஓட analyst அதை பிடிச்சாரு. Break-even line monthly report-ல வரணும்ங்குற condition-ஓட CFO மூணு மாதாந்திர waves-ஐ approve பண்ணாரு.

### Production, handover

Waves weeks 15 முதல் 18, 19 முதல் 22, 23 முதல் 26-ல ஓடுச்சு, கடைசி இரண்டுக்கும் FDE support பண்ணாங்க. Weeks 23 முதல் 26-ல lender-ஓட engineers Karthik-உம் Divya-உம் முதல்ல பார்த்தாங்க, அப்புறம் அவங்க பார்த்துட்டு இருக்கும்போது ஒவ்வொரு core task-ஐயும் இவங்களே செஞ்சாங்க: ஒரு release, ஒரு rollback, CI வழியா evals-ஓட ஒரு prompt change, இரண்டு simulated incidents. அப்புறம் sign-off, அவங்க access remove, gateway keys rotate, மூணு மாசம் escalation-only support.

கடைசி wave முடிஞ்சு மூணு மாசம் கழிச்சு, 180 officers முழுக்க numbers: median 25 நிமிஷம், 5.3% rework, 84% adoption, மாசம் ₹8.7 lakh running cost. அது வருஷத்துக்கு net சுமார் ₹25 lakh. Photos அதிகமா இருக்குற இரண்டு rural branches 29 நிமிஷத்துல இருந்துச்சு, அது தான் அடுத்த வேலை.

## ஒரு worked example

ஒரு portfolio-க்கோ ஒரு interview-க்கோ, இரண்டு நிமிஷத்துக்குள்ள சொன்ன engagement இது:

"சென்னையில ஒரு lender ஒரு customer chatbot கேட்டாங்க. உண்மையான செலவு document வேலைன்னு discovery காட்டுச்சு: ஒரு loan file-க்கு சுமார் 40 நிமிஷம், மாசம் 6,000 files, அதுல 7% தப்புகளுக்காக திரும்ப வந்துச்சு. நாங்க ஒரு KPI-ஐ agree பண்ணோம், ஒரு file-க்கு median நிமிஷங்கள், அளந்த 41-ல இருந்து target 22 வரை, rework-ஐ ஒரு guardrail-ஆ வச்சு. என் proof of concept 95% accuracy gate-ஐ 93%-ல miss பண்ணுச்சு; golden set-ஐ பிரிச்சப்போ phone photos தான் problem-னு தெரிஞ்சுது, image clean-up அதை 96.4%-க்கு கொண்டு போச்சு. 20 officers-ஓட பத்து வார pilot-ல, ஒரு branch-ல இருந்த blame பயத்தை சரி பண்ணதுக்கு அப்புறம், நேரம் 24 நிமிஷத்துக்கு குறைஞ்சுது, target-க்கு கொஞ்சம் குறைவு, 5.1% rework, 88% adoption-ஓட. என் தப்பு: full volume-ல model-க்கு week 10-ல தான் விலை போட்டேன், அது ஒரு file-க்கு மிச்சப்படுத்துனதை விட அதிகமா செலவாச்சு. ஈஸியான pages-ஐ ஒரு சின்ன model-க்கு route பண்ணது இரண்டு வாரத்துல cost-ஐ மூணுல ஒரு பங்குக்கு மேல குறைச்சுது. 180 officers-க்கு rollout ஆகி மூணு மாசம் கழிச்சு: 25 நிமிஷம், வருஷத்துக்கு net சுமார் ₹25 lakh. அடுத்த தடவை security review-ஐயும் cost model-ஐயும் முதல் வாரத்துலயே ஆரம்பிப்பேன்."

ஒவ்வொரு பகுதியும் ஏன் இருக்கு:

| கதையோட பகுதி | கேக்குறவங்களுக்கு அது என்ன காட்டுது |
| --- | --- |
| கேட்டதும் reframe-உம் | Build பண்றதுக்கு முன்னாடி உண்மையான problem-ஐ கண்டுபிடிக்குறீங்க |
| அளந்த baseline-ஓட ஒரு KPI | Model scores இல்ல, business results-ஐ அளக்குறீங்க |
| Miss ஆன gate-உம் slice-உம் | Average-ஐ நம்பாம evals-ஐ சரியா படிக்குறீங்க |
| "Target-க்கு கொஞ்சம் குறைவு" | நேர்மையா report பண்றீங்க, அதனால மத்த numbers-ஐ நம்ப முடியுது |
| தப்பும் அதோட cost-உம் | உங்க சொந்த தப்புகளை கவனிச்சு சீக்கிரமே சொல்றீங்க |
| Rollout-க்கு அப்புறம் net value | Client யோசிக்கிற மாதிரியே பணத்தைப் பத்தி யோசிக்கிறீங்க |

## பொதுவா பண்ற தப்புகள்

இவை portfolio case studies-ஐ மூழ்கடிக்கும், interviewers இவற்றை சீக்கிரமே கண்டுபிடிச்சுடுவாங்க:

- **கற்பனை numbers-ஐ results-ஆ காட்டுறது.** கற்பனை client-னா, உங்க discovery figures assumptions தான். அவற்றை label பண்ணி ஒரு source குடுங்க. உங்க சொந்த golden set-ல இருந்து வர்ற numbers மட்டும் தான் results.
- **"Efficiency-ஐ 40% improve பண்ணோம்".** எதோட, எந்த baseline-ல இருந்து, எப்படி அளந்து, எத்தனை cases-ல? Number-ஐ அதோட unit, baseline, sample-ஓட எழுதுங்க.
- **Average மட்டும்.** ஒரு accuracy figure fail ஆகுற slice-ஐ மறைச்சுடும். Document type அல்லது source வாரியான breakdown-ஐ காட்டுங்க.
- **Failure-ஏ இல்லாதது, அல்லது ஒரே வரியில solve ஆன failure.** அதை எப்படி கண்டுபிடிச்சீங்க, நேரத்துலயோ பணத்துலயோ எவ்வளவு செலவாச்சு, client-கிட்ட என்ன சொன்னீங்கன்னு சொல்லுங்க.
- **Cost இல்லாத value.** உங்க system ஒரு case-க்கு ₹150 run பண்ண செலவாகுதுன்னா, அது மிச்சப்படுத்துறதுக்கு பக்கத்துலயே, அதே unit-ல அதை சொல்லுங்க.
- **Code link இல்ல, அல்லது யாராலயும் run பண்ண முடியாத code.** ஒரு reviewer README-ல இருந்து உங்க evals-ஐ திரும்ப run பண்ண முடியணும்.
- **ஒவ்வொரு stage-ஐயும் ஒரே நீளத்துல திரும்ப சொல்றது.** Process-ஐ விவரிக்கிறதுல இல்ல, decisions-லயும் evidence-லயும் உங்க வார்த்தைகளை செலவு பண்ணுங்க.

## Practice பண்ணுங்க

Business context-க்கு FDE role பத்தின a16z essay-ஐ படிங்க.

இந்த lesson-ஓட check தான் capstone write-up. ஒரு public dataset-ஐயும், உங்களுக்கு தெரிஞ்ச ஒரு இந்திய industry-ல ஒரு கற்பனை client-ஐயும் தேர்ந்தெடுங்க, உதாரணமா ஒரு hospital chain, ஒரு logistics company, ஒரு state department அல்லது ஒரு retailer. இந்த lesson-ஓட shape-ல இரண்டு அல்லது மூணு pages எழுதுங்க:

1. Numbers-ஓட discovery findings, ஒவ்வொண்ணும் அதோட source-ஓட assumption-னு label பண்ணி, உதாரணமா ஒரு published guide, ஒரு annual report, அல்லது அந்த வேலையை செய்யுற ஒருத்தர் கூட ஒரு interview.
2. KPI, baseline, target, guardrail, exclusions-ஓட scope.
3. உங்க golden set, அதை எப்படி label பண்ணீங்க, குறைஞ்சது ஒரு slice வாரியா பிரிச்ச results, அது pass பண்ண வேண்டிய gate.
4. அதோட governance choices-ஓட architecture: access, logging, masking, data எங்க போகுது.
5. Assume பண்ண monthly volume-ல ஒரு case-க்கான cost, ஒரு case-க்கான value-க்கு எதிரா.
6. உங்க build-ல தப்பா போன ஒரு விஷயம், அதை எப்படி கண்டுபிடிச்சீங்க, உங்களுக்கு அது எவ்வளவு செலவாச்சு.
7. வேற ஒருத்தர் அதை எப்படி run பண்ணுவாங்க: ஒரு README, ஒரு runbook, evals-ஐ திரும்ப run பண்ற ஒரு command.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க case study-ஐ இரண்டு நிமிஷத்துல சொல்ல முடியும், எந்த numbers-ஐ அளந்தீங்க, எதை assume பண்ணீங்கன்னு காட்ட முடியும், "வேற மாதிரி என்ன பண்ணுவீங்க?"-ங்குற கேள்விக்கு நேர்மையா பதில் சொல்ல முடியும்.
