## இது என்ன

ஒரு **KPI** (key performance indicator)-னா project வேலை செஞ்சுதான்னு சொல்ற அந்த ஒரு number. ஒரு AI deployment-க்கு, முழுமையான KPI plan-ல ஆறு பகுதிகள் இருக்கு:

- Business result கூட இணைஞ்ச **ஒரு primary KPI**: ஒரு loan file-க்கு minutes, first-response time, ஒரு officer ஒரு நாளைக்கு process பண்ற claims, solve ஆன ஒரு ticket-க்கு cost.
- **ஒரு baseline**: உங்க system வர்றதுக்கு முன்னாடி, அதே முறையில, அதே மாதிரியான ஆளுங்க, cases-க்கு அளந்த KPI.
- **தேதியோட ஒரு target**, எது met, close, missed-னு முன்னாடியே ஒத்துக்கிட்ட bands.
- **Guardrail measures**: மோசமாகக்கூடாத விஷயங்கள், உதாரணமா error rate, customer complaints அல்லது compliance exceptions.
- **Adoption**: ஆளுங்க உண்மையிலேயே system-ஐ use பண்றாங்களா, ஏன்னா யாரும் use பண்ணாத tool-ஆல KPI-ஐ நகர்த்த முடியாது.
- **ஒரு method**: ஒவ்வொரு number-உம் எங்க இருந்து வருது, எந்த cases count ஆகும், எந்த வாரங்கள் count ஆகும், யார் report பண்றாங்க.

Accuracy அல்லது faithfulness மாதிரி model metrics inputs தான், KPI இல்ல. Officers நம்பாத ஒரு 95%-accurate extractor-னா, அவங்க எப்படியும் திரும்ப type பண்ணுவாங்க; யாருக்கும் ஒரு minute கூட மிச்சமாகாது.

### Number-ஐ exact-ஆ define பண்ணுங்க

Discovery கண்டுபிடிச்ச problem-ல இருந்து ஆரம்பிங்க. Officers ஒரு file-க்கு சுமார் 40 minutes செலவு பண்றாங்கன்னா, KPI ஒரு file-க்கான time, "AI accuracy" இல்ல. அப்புறம் அதை தெளிவா நிர்ணயிங்க, ஏன்னா தெளிவில்லாத KPI-னா ஒவ்வொரு பக்கமும் result-ஐ அவங்களுக்கு ஏத்த மாதிரி படிச்சுக்குவாங்க:

- **Start, end events.** "File-ஐ open பண்றதுல இருந்து credit note-ஐ submit பண்றது வரைக்கும்", ரெண்டையுமே loan system stamp பண்ணுது.
- **எந்த cases count ஆகும்.** ஒரு pilot officer handle பண்ண எல்லா file-உம், அவங்க draft-ஐ use பண்ணாலும் பண்ணாட்டியும். ஆளுங்க ஒரு புது tool-ஐ முதல்ல ஈஸியான cases-ல தான் try பண்ணுவாங்க. Tool use ஆன files-ஐ மட்டும் count பண்ணா, அது உண்மையை விட வேகமா தெரியும்.
- **எந்த statistic.** Median, mean இல்ல. Lunch நேரத்துலயோ ராத்திரி முழுக்கவோ open-ஆவே விட்ட ஒரு file, hours-ஆ காட்டும். அப்படி ஒரு file mean-ஐ நிறைய நகர்த்தும், median-ஐ கிட்டத்தட்ட நகர்த்தாது. Data-க்கு ஒரு check-ஆ, ரெண்டு மணி நேரத்துக்கு மேல ஆன files-ஓட share-ஐ தனியா report பண்ணுங்க.
- **Elapsed time-உம் working time-உம் ஒண்ணு இல்ல.** Timestamps கடிகாரத்தை அளக்குது, உழைப்பை இல்ல. Baseline-ஐயும் pilot-ஐயும் ஒரே மாதிரி அளக்குற வரைக்கும் அது பரவாயில்ல.

Surveys-ஐ விட, systems ஏற்கனவே record பண்ற numbers-ஐ (timestamps, ticket close times) தேர்ந்தெடுங்க. எந்த system-உம் அந்த number-ஐ record பண்ணலைன்னா, முதல்ல measurement-ஐ set up பண்ணுங்க: சில cases-க்கு start, end times-ஓட ஒரு simple log, pilot-க்கு முன்னாடியே ஆரம்பிச்சு.

### சரியான ஆளுங்க மேல baseline-ஐ அளங்க

அதே team, அதே மாதிரியான cases, போதுமான volume (சில நூறு cases, குறைஞ்சது ரெண்டுல இருந்து நாலு வாரம் வரைக்கும்), ஒரு சாதாரண காலம் use பண்ணுங்க. Month-end rush, festival season அல்லது ஒரு புது credit policy, இதெல்லாம் அதை கெடுத்துடும்.

ரெண்டு baselines அளங்க: முழு organisation-க்கு ஒண்ணு, pilot group-க்கு மட்டும் ஒண்ணு. Pilot groups பெரும்பாலும் அவங்க ஆர்வமா இருக்குறதாலயோ, நல்லா run ஆகுறதாலயோ, head office-க்கு பக்கத்துல இருக்குறதாலயோ தான் தேர்ந்தெடுக்கப்படுறாங்க. Pilot officers ஏற்கனவே 35 minutes எடுத்திருந்தா, அவங்களை lender முழுக்கவான 41 கூட compare பண்ணா, tool மிச்சப்படுத்தவே இல்லாத ஆறு minutes-க்கு அதுக்கு credit போயிடும். Chennai lender-ல ரெண்டு baselines-உம் 41 minutes-ஆ வந்துச்சு, அதனால pilot comparison நியாயமானது. இருந்தாலும் pilot branches average-ஐ விட ஆர்வமா இருந்தாங்க, அதனால தான் full rollout-க்கு business case அப்புறமா இன்னும் கவனமான ஒரு figure-ஐ plan பண்ணுச்சு (executives கூட பேசுறது பத்தின lesson-ஐ பாருங்க).

### ஆசையில இருந்து இல்ல, evidence-ல இருந்து target-ஐ set பண்ணுங்க

"பாதியா குறைங்க"ங்குறது ஒரு ஆசை. Defend பண்ணக்கூடிய ஒரு target வேலையில இருந்தே வருது. Discovery-ல, team officers கூடவே உட்கார்ந்து பார்த்துக்கிட்டே சில files-ஐ time பண்ணுச்சு (case-ஓட figures): சுமார் 16 minutes documents-ஐ படிக்குறதுலயும் applicant-ஐ judge பண்றதுலயும் போச்சு, சுமார் 25 figures-ஐ திரும்ப type பண்றதுலயும் credit note எழுதுறதுலயும் போச்சு. Assistant figures-ஐயும் note-ஐயும் draft பண்ணுது, ஆனா officers இன்னும் flag ஆன, critical fields-ஐ check பண்றாங்க; அதுக்கு சுமார் 6 minutes ஆகும்னு team estimate பண்ணுச்சு. அதனால target 16 + 6 = 22 minutes.

இப்படி build பண்ண target ரெண்டு வேலை செய்யுது. அது எங்க இருந்து வந்துச்சுன்னு client-ஆல பார்க்க முடியும். Pilot miss ஆனா, எந்த step-ஐ பார்க்கணும்னு உங்களுக்கு தெரியும்: இங்க, checking estimate பண்ணதை விட அதிக நேரம் எடுத்துச்சு.

### Met, close, missed-னா என்னன்னு முன்னாடியே ஒத்துக்கோங்க

Weekly medians தற்செயலா நகரும். June baseline வாரங்கள்ல, எதுவுமே மாறாம இருந்தப்பவும், வாரத்துக்கு சுமார் 170 files-ல, pilot group-ஓட weekly median ஒண்ணுல இருந்து ரெண்டு minutes வரைக்கும் நகர்ந்துச்சு. அதனால 22 target-க்கு எதிரா 24 result வந்தா, யாரும் அதை பார்க்குறதுக்கு முன்னாடியே ஒத்துக்கிட்ட ஒரு rule வேணும்.

| Band | Range | என்ன நடக்கும் |
| --- | --- | --- |
| Met | 22 minutes அல்லது அதுக்கு கீழ | Rollout-ஐ recommend பண்ணுங்க |
| Close | 22-க்கு மேல, 26 minutes வரைக்கும் | கவனமான ஒரு planning figure-ஓடவும், gap-க்கு ஒரு fix plan-ஓடவும் rollout-ஐ recommend பண்ணுங்க |
| Missed | 26 minutes-க்கு மேல | ஒரு சின்ன extension, குறுகின scope கூட fix plan, இல்லைன்னா stop |

பின்னாடி வாரங்களை வச்சு judge பண்ணுங்க. முதல் வாரங்கள்ல results ரெண்டு பக்கமும் distort ஆகும்: officers இன்னும் tool-ஐ கத்துக்கிட்டு இருப்பாங்க, சிலர் புதுசான ஒண்ணு வந்ததால excite ஆகி அப்புறம் use பண்றதை விட அதிகமா use பண்ணுவாங்க (novelty effect). Lender, முதல் problems சரியானதுக்கு அப்புறம், pilot weeks 7 to 10 வச்சு judge பண்ணுச்சு.

ஒரு gap-ல எவ்வளவு தற்செயல்னு பார்க்க, median-க்கு ஒரு likely range-ஐ compute பண்ணுங்க. தனித்தனி files-ஐ இல்ல, officers-ஐ resample பண்ணுங்க, ஏன்னா ஒரு officer-ஓட files ஒரே மாதிரி இருக்கும்:

```python
import numpy as np
import pandas as pd

df = pd.read_csv("pilot_files.csv", parse_dates=["opened_at", "submitted_at"])
df["minutes"] = (df["submitted_at"] - df["opened_at"]).dt.total_seconds() / 60

# Weekly median per branch: the numbers behind the weekly line
print(df.pivot_table(index="pilot_week", columns="branch",
                     values="minutes", aggfunc="median").round(1))

# Judge on pilot weeks 7 to 10, using every file, draft used or not
end = df[df["pilot_week"].between(7, 10)]
officers = [g.to_numpy() for _, g in end.groupby("officer_id")["minutes"]]

# Resample officers, not files: one officer's files are alike
rng = np.random.default_rng(7)
n = len(officers)
medians = [np.median(np.concatenate([officers[i] for i in rng.integers(0, n, n)]))
           for _ in range(2000)]
low, high = np.percentile(medians, [2.5, 97.5])
print(f"median {end['minutes'].median():.1f} min, likely range {low:.1f} to {high:.1f}")
```

Target likely range-க்கு வெளியே இருந்தா, அந்த gap உண்மையானது, noise இல்ல. அதை நேரடியா சொல்லுங்க.

### Gaming-க்கு எதிரா ஒண்ணையும் சேர்த்து guardrails-ஐ தேர்ந்தெடுங்க

அதிக errors-ஓட வேகமான processing வெற்றி இல்ல. Client-ஓட risk owners ஏற்கனவே கவலைப்படுற ஒண்ணு அல்லது ரெண்டு quality measures-ஐ தேர்ந்தெடுங்க, உதாரணமா credit committee rework, audit exceptions. Rework ஒரு lagging measure: committee, submit ஆனதுல இருந்து ஒண்ணு ரெண்டு வாரம் கழிச்சு தான் files-ஐ திரும்ப அனுப்பும், அதனால அந்த lag-ஓட report பண்ணுங்க, கடைசி வாரத்தை வச்சு அதை judge பண்ணாதீங்க.

Gaming-க்கு எதிரா ஒரு guardrail சேருங்க. Economist Charles Goodhart பேர்ல இருக்குற Goodhart's law-ஐ பெரும்பாலும் இப்படி சொல்லுவாங்க: "ஒரு measure target ஆனதும், அது நல்ல measure-ஆ இருக்குறதை நிறுத்திடும்". 22 minutes-ஐ தொடணும்ங்குற pressure-ல, ஒரு officer draft-ஐ படிக்காமலேயே accept பண்ணலாம். Number நல்லாகும்; உண்மையான result நல்லாகாது. அதனால எந்த edit-உம் இல்லாம accept ஆன drafts-ஓட share-ஐ track பண்ணுங்க, ஒரு senior officer வாரத்துக்கு random-ஆ 20 files-ஐ spot-check பண்ணட்டும். Zero-edit share 100%-ஐ நோக்கி ஏறிட்டே போக, spot checks-ல miss ஆன errors தெரிஞ்சா, அது rubber-stamping.

### நியாயமா compare பண்ணுங்க

Pilot நடக்கும்போது வேற ஏதாவது எப்பவுமே மாறும்: ஒரு புது policy, leave-ல இருக்குற staff, ஒரு seasonal rush. ஒரு comparison group அதை பிடிக்கும். அதே வாரங்கள்ல system இல்லாத அதே மாதிரியான ஆளுங்களுக்கு KPI-ஐ track பண்ணுங்க; lender-ல, மத்த branches முழுக்க சுமார் 41 minutes-லயே இருந்தாங்க, அதனால அந்த குறைவு lender முழுக்கவான ஒரு மாற்றம் இல்ல. எல்லாருக்கும் ஒரே நேரத்துல tool கிடைச்சா, அதே ஆளுங்களை முன்னாடியும் அப்புறமும் compare பண்ணுங்க, வேற என்னென்ன மாறுச்சோ எல்லாத்தையும் எழுதி வைங்க. Pilot ஆரம்பிக்குறதுக்கு முன்னாடியே method-ஐ measurement plan-ல போடுங்க, அப்போ யாரும் அப்புறமா தனக்கு சாதகமான comparison-ஐ தேர்ந்தெடுக்க முடியாது.

### KPI-ஐ rupees-ஆ மாத்துங்க

Executives fund பண்றது rupees-ஐ, minutes-ஐ இல்ல. Lender-ஓட சொந்த HR figure-படி ஒரு loaded officer hour-க்கு சுமார் ₹600-னு வச்சா, ஒவ்வொரு file-லயும் ஒரு minute மிச்சமானா 6,000 files ÷ 60 = மாசத்துக்கு 100 officer hours, அதோட மதிப்பு மாசத்துக்கு சுமார் ₹60,000. பதினஞ்சு minutes மிச்சமானா மாசத்துக்கு சுமார் ₹9 lakh. அந்த ஒரு conversion இருந்தா, யார் வேணும்னாலும் ஒவ்வொரு weekly result-ஐயும் பணமா மாத்திக்கலாம்.

| Input (model அல்லது system) | Outcome (business) | அது எப்படி rupees-ஆ மாறுது |
| --- | --- | --- |
| Extraction accuracy | ஒரு loan file-க்கான minutes | மிச்சமான minutes × files × ஒரு minute-க்கான cost |
| Faithfulness score | Rework rate | திரும்ப அனுப்பப்படாத files × திரும்ப செய்ய ஆகுற hours × hourly cost |
| Retrieval recall | ஒரு policy கேள்விக்கு பதில் சொல்ற time | மிச்சமான minutes × கேள்விகள் × ஒரு minute-க்கான cost |
| Latency | ஒரு agent ஒரு மணி நேரத்துக்கு handle பண்ற calls | கூடுதல் staff இல்லாம handle ஆகுற கூடுதல் calls |

Running cost தெரிஞ்சதும், break-even-ஐ கணக்கு பண்ணுங்க: value-உம் cost-உம் சமமாகுற, ஒரு file-க்கான மிகச் சின்ன saving. Lender-ல, full-volume cost model லேட்டா, contract week 10-ல தான் வந்துச்சு (case study lesson-ஐ பாருங்க). அது சுமார் 13 minutes break-even குடுத்துச்சு: saving 13 minutes அல்லது அதுக்கு மேல இருக்கணும், அதாவது ஒரு file-க்கு 28 minutes அல்லது அதுக்கு கீழ. முதல் வாரங்கள்லயே cost model-ஐ build பண்ணுங்க, அப்போ pilot judge ஆகுறதுக்கு முன்னாடியே அந்த floor தெரியும்.

### ஒவ்வொரு வாரமும் report பண்ணுங்க, group வாரியா பிரிச்சு

ஒவ்வொரு வாரமும் KPI, guardrail, adoption-ஓட ஒரு line அனுப்புங்க. Pilot week 2-ல அது இப்படி இருந்துச்சு: "ஒரு file-க்கு median 27 minutes (baseline 41, target 22); rework 5.4%, limit 7%; 78% files-ல draft use ஆச்சு."

அதை branch வாரியாவும் பிரிங்க. ஒரு வாரம் கழிச்சு, blended line காட்டாததை அந்த split காட்டுச்சு: Anna Nagar-ல 92% files-ல draft use ஆச்சு, ஆனா Tambaram-ல 41% தான், அங்க median 37 minutes. அங்க இருந்த officers AI errors-க்கு தங்க மேல பழி வரும்னு பயந்து எல்லாத்தையும் திரும்ப type பண்ணாங்க. அந்த split தான் அதை சரி பண்ண branch visit-க்கு வழி வகுத்துச்சு (change management பத்தின lesson-ஐ பாருங்க). Blended number ஒரு problem இருக்கான்னு சொல்லும். Split அது எங்க இருக்குன்னு சொல்லும்.

## ஒரு worked example

Chennai lender-ல discovery முடிஞ்சதும், மேல இருக்குற table-ல இருக்குற plan-ஐ நீங்க propose பண்றீங்க. Head of operations முதல்ல "90% AI accuracy"-ஐ target-ஆ கேக்குறாங்க. Golden set-ல accuracy-ஐ ஒரு quality input-ஆ track பண்ண நீங்க ஒத்துக்குறீங்க. அப்புறம், officers நம்பாத ஒரு accurate draft எதையும் மிச்சப்படுத்தாதுன்னு explain பண்றீங்க. Lender பணம் குடுக்குறது officer time-க்கும் rework-க்கும் தான், அதனால அவை தான் KPI-உம் guardrail-உம். அவங்க ஒத்துக்குறாங்க, plan scope of work-க்குள்ள போகுது.

Pilot-க்கு முன்னாடி, June timestamps-ஐ ரெண்டு தடவை எடுக்குறீங்க: lender முழுக்க (41 minutes, 6,200 files), 20 pilot officers-க்கு மட்டும் (41 minutes, சுமார் 690 files). Time பண்ண steps-ல இருந்து target-ஐ (22 minutes) set பண்ணி, bands-ஐ ஒத்துக்குறீங்க.

Pilot நடக்கும்போது, weekly line pilot week 3-ல Tambaram-ஐ flag பண்ணுது, ரெண்டு வாரம் கழிச்சு அங்க adoption 85%-க்கு திரும்ப வருது. அப்புறம் pilot weeks 7 to 10 verdict-ஐ குடுக்குது:

| Measure | Baseline | Target | Pilot weeks 7 to 10 | Verdict |
| --- | --- | --- | --- | --- |
| ஒரு file-க்கான median minutes | 41 | 22 | 24 (likely range 23 to 25) | Close |
| Rework rate | 7% | 7%-க்கு மேல இல்ல | 5.1% | நிலைச்சுது, இன்னும் நல்லாச்சு |
| Adoption | பொருந்தாது | 80% files | 88% | Met |

## பொதுவா பண்ற தப்புகள்

- **Model metrics-ஐ KPI-ஆ வைக்குறது.** Accuracy ஒரு வழி; business-ல time, cost அல்லது errors தான் இலக்கு.
- **Baseline இல்லாதது, அல்லது தப்பான group-ஓட baseline.** "Officers-க்கு வேகமா இருக்குற மாதிரி தோணுது"ங்குறது ஒரு budget review-ல நிக்காது, lender முழுக்கவான baseline ஒரு ஆர்வமான pilot group-ஐ இருக்குறதை விட நல்லா காட்டலாம்.
- **Tool use ஆன files-ஐ மட்டும் count பண்றது.** ஆளுங்க அதை முதல்ல ஈஸியான cases-ல தான் use பண்ணுவாங்க. எல்லா pilot file-ஐயும் count பண்ணுங்க.
- **முதல் வாரங்களை வச்சு judge பண்றது.** கத்துக்குறதும் novelty effect-உம் அவற்றை distort பண்ணும். ஒத்துக்கிட்ட மாதிரி, பின்னாடி வாரங்களை வச்சு judge பண்ணுங்க.
- **கொஞ்சத்துல miss ஆனதை அப்புறமா வாதம் பண்றது.** Pilot ஆரம்பிக்குறதுக்கு முன்னாடியே met, close, missed bands-ஐ ஒத்துக்கோங்க.
- **நல்லா கேக்குதுன்னு தேர்ந்தெடுத்த target.** Time பண்ண steps-ல இருந்து build பண்ணுங்க, அப்போ ஒரு miss எங்க பார்க்கணும்னு சொல்லும்.
- **Gaming-ஐ பிடிக்க முடியாத guardrails.** Rework மட்டும் lag ஆகும்; edit இல்லாம accept ஆன drafts-ஓட spot checks-ஐயும் சேருங்க.
- **Blended number மட்டும்.** ஒவ்வொரு வாரமும் branch அல்லது team வாரியா பிரிங்க, இல்லைன்னா நின்னுபோன ஒரு group average-க்குள்ள ஒளிஞ்சுக்கும்.
- **ரொம்ப அதிகமான KPIs.** பத்து numbers இருந்தா எது முக்கியம்னு யாருக்கும் தெரியாது. ஒரு primary, சில guardrails, ஒரு adoption measure.

## Practice பண்ணுங்க

Measuring success பத்தின GOV.UK guide-ஐ படிங்க.

1. உங்க discovery exercise-ல இருந்த use case-க்கு, ஒரு முழு KPI plan எழுதுங்க: start, end events-ஓட primary KPI, முழு organisation-க்கும் pilot group-க்கும் ஒரு baseline method, time பண்ண steps-ல இருந்து build பண்ண target, met, close, missed bands, ரெண்டு guardrails, ஒரு adoption measure.
2. ஒவ்வொரு number-உம் எங்க இருந்து வருது, எந்த cases count ஆகும், யார் report பண்றாங்கன்னு exact-ஆ விவரிங்க.
3. ஒரு case-க்கு மிச்சமாகுற ஒரு minute-ஐ, client தன்னோடதுன்னு ஏத்துக்குற ஒரு cost figure-ஐ வச்சு, மாசத்துக்கு rupees-ஆ மாத்துங்க.
4. ஒவ்வொரு guardrail-க்கும், உண்மையான result இல்லாமலேயே ஆளுங்க KPI-ஐ நகர்த்தக்கூடிய ஒரு வழியையும், அதை நீங்க எப்படி கண்டுபிடிப்பீங்கன்னும் எழுதுங்க.
5. Team வாரியா பிரிச்சு, pilot week 4-க்கான weekly line-ஐ draft பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** accuracy ஏன் KPI இல்லைன்னு ஒரு client-கிட்ட explain பண்ண முடியும், அவங்க sign பண்ணக்கூடிய ஒரு measurement plan-ஐ காட்ட முடியும், எந்த result-ஐ close-னு சொல்வீங்கன்னு முன்னாடியே சொல்ல முடியும்.
