## இது என்ன

**Multi-agent system** ஒரு task-ஐ பல agents இடையில பிரிக்கும்; ஒவ்வொண்ணுக்கும் தன்னோட instructions, tools, context இருக்கும். மூணு patterns தான் பெரும்பாலான real designs-ஐ கவர் பண்ணும்:

- **Supervisor-உம் workers-உம்**: ஒரு lead agent plan பண்ணி, sub-tasks-ஐ worker agents-க்கு (பெரும்பாலும் அது call பண்ணக்கூடிய tools-ஆ) delegate பண்ணி, அவற்றோட results-ஐ சேர்க்கும்.
- **Hand-offs**: ஒரு agent, தன் role-க்கு வெளியே ஏதாவது வர்ற வரைக்கும் ஒரு conversation-ஐ handle பண்ணும்; அப்புறம் control-ஐ context-ஓட ஒரு specialist agent-க்கு pass பண்ணும். Customer service-ல இது சாதாரணம்: front-desk agent billing கேள்விகளை billing agent-க்கு hand off பண்ணும்.
- **Generator-உம் reviewer-உம்**: ஒரு agent வேலையை produce பண்ணும்; இன்னொண்ணு criteria-வுக்கு எதிரா check பண்ணி feedback-ஓட திருப்பி அனுப்பும்.

முந்தின lesson-ல sub-agents பத்தி, பிரிக்குறது ஏன் உதவுதுன்னு பார்த்தோம்: சுத்தமான contexts, specialised tools, parallel வேலை. இந்த lesson patterns-ஐ தேர்ந்தெடுத்து ஓட்டுறதை பத்தியது.

```flow
Lead -> Worker 2
Lead -> Worker 3
```



இந்த lesson Bengaluru-ல ஒரு bank-ஓட customer assistant-ஐ follow பண்ணுது; அது ஒரு பெரிய agent-ல இருந்து specialists-ஓட ஒரு தொகுப்பா மறுபடி build பண்ணப்பட்டது.

## இது எப்படி work ஆகுது

**Supervisor-உம் workers-உம்.** Supervisor, user-ஓட goal-ஐயும், tools மாதிரி describe பண்ணப்பட்ட workers-ஓட list-ஐயும் பாக்கும் ("research_competitor: researches one named company, returns a 200-word summary with sources"). எதை call பண்ணணும்னு (parallel-ஆ கூட) அது முடிவு பண்ணி, final answer-ஐ எழுதும். பலம்: parallelism, context isolation. Risks: தெளிவில்லாத delegation, duplicate வேலை, summaries-ல details தொலைஞ்சு போறது, அதிக token use.

**Hand-offs.** ஒவ்வொரு agent-உம் தன்னோட tools-ஓடவும் permissions-ஓடவும் ஒரு domain-ஐ வச்சிருக்கும். Hand-off ஒரு tool call தான் ("transfer_to_billing"), அது conversation-ஐ நகர்த்தும். பலம்: ஒவ்வொரு agent-உம் சின்னதாவும் focus-ஓடவும் இருக்கும்; permissions narrow-ஆ இருக்கும் (billing agent மட்டும் தான் refunds issue பண்ண முடியும்). Risks: agents இடையில ping-pong, transfer-ல context தொலையுறது, users திரும்ப திரும்ப சொல்றது.

**Generator-உம் reviewer-உம்.** Reviewer-கிட்ட ஒரு checklist அல்லது rubric இருக்கும், அது குறிப்பிட்ட பிரச்சனைகளை திருப்பி தரும். பலம்: ஒரே pass-ல தவறவிடுற errors-ஐ பிடிக்கும். Risks: முடிவில்லாத loops (rounds-ஐ cap பண்ணுங்க), எல்லாத்தையும் approve பண்ற reviewers (தெரிஞ்ச மோசமான drafts-ல reviewer-ஐ test பண்ணுங்க).

**Shared state vs messages.** Agents ஒரு பொது state object-ஐ (graph frameworks-ல மாதிரி) பகிர்ந்துக்கலாம், அல்லது messages pass பண்ணலாம். Shared state debugging-ஐ எளிதாக்கும்; messages agents-ஐ இன்னும் independent-ஆ வச்சிருக்கும். எப்படியிருந்தாலும், ஒவ்வொரு agent-ஓட steps-ஐயும் ஒரே request id-க்கு கீழ trace பண்ணுங்க.

**எப்போ வேண்டாம்.** Task வரிசையா, இறுக்கமா பிணைஞ்சிருந்தா, நல்ல tools இருக்குற ஒரு agent பெரும்பாலும் cost-லயும் reliability-லயும் ஜெயிக்கும். முதல்ல ஒரு single-agent baseline-ஐ measure பண்ணுங்க.

**Patterns ஒப்பீடு:**

| Pattern | பலம் | Risks | எதுக்கு நல்லது |
| --- | --- | --- | --- |
| Supervisor-உம் workers-உம் | Parallel வேலை, சுத்தமான contexts | தெளிவில்லாத delegation, அதிக token use | Research, பரந்த analysis |
| Hand-offs | சின்ன focused agents, narrow permissions | Ping-pong, context தொலையுறது | தனித்தனி domains இருக்குற customer service |
| Generator-உம் reviewer-உம் | ஒரு pass தவறவிடுற errors-ஐ பிடிக்கும் | Loops, தாராளமான reviewers | Regulated அல்லது high-stakes எழுத்து |

**Hand-off-ஐ design பண்றது.** Hand-off tool, அனுப்புற agent எழுதின ஒரு சின்ன summary-ஐ கொண்டு போகணும்: customer யாரு (verification-க்கு அப்புறம்), என்ன கேட்டாங்க, என்ன முடிஞ்சிருக்கு, என்ன மீதம் இருக்கு. கடைசி சில turns-ஐயும் சேர்த்து pass பண்ணுங்க. Domains-ஐ தாண்டுற scripted conversations-ஓட test பண்ணுங்க, balance கேள்வியை தொடர்ந்து card block மாதிரி; customer தன் identity-யையோ request-ஐயோ திரும்ப சொல்லவே வேண்டியதில்லன்னு check பண்ணுங்க. ஒவ்வொரு hand-off-ஐயும் அதோட காரணத்தோட log பண்ணுங்க; அப்போ தாங்களே handle பண்ண வேண்டிய வேலையை pass பண்ற agents-ஐ கண்டுபிடிக்கலாம்.

**Role descriptions எழுதுறது.** ஒவ்வொரு agent-ஓட description-உம் அது எதை handle பண்ணும், எதை hand off பண்ணணும், எதை ஒருபோதும் செய்யக்கூடாதுன்னு சொல்லணும். Overlaps தான் மிக மோசமான failures-ஐ உண்டாக்கும்: ரெண்டு agents-உம் refunds தங்களுக்குன்னு நினைச்சா, ஒண்ணு வாதாடும் அல்லது ரெண்டும் action எடுக்கும். Descriptions-ஐ பக்கத்துல பக்கத்துல வச்சு படிச்சு, test பண்றதுக்கு முன்னாடி ஒவ்வொரு overlap-ஐயும் நீக்குங்க.

**Code-ல ஒரு hand-off.** Hand-off என்பது, அடுத்த agent-க்கு தேவையான summary-ஐ arguments-ல கொண்டு போற ஒரு tool. Conversation-ஐ நகர்த்துறதும் transfers-ஐ எண்ணுறதும் உங்க code தான், model இல்ல:

```python
AGENTS = {
    "front_desk": {"tools": ["get_profile", "transfer"], "prompt": "Greet, verify, route."},
    "cards":      {"tools": ["block_card", "card_status", "transfer"], "prompt": "Card issues only."},
    "loans":      {"tools": ["loan_balance", "transfer"], "prompt": "Loan questions only."},
}
TRANSFER_TOOL = {
    "name": "transfer",
    "description": "Hand the customer to another team. Use only for requests outside your role.",
    "input_schema": {"type": "object", "properties": {
        "to": {"type": "string", "enum": list(AGENTS)},
        "summary": {"type": "string", "description": "Who the verified customer is, what they asked, what is done, what remains"},
    }, "required": ["to", "summary"]},
}
MAX_TRANSFERS = 3

def handle_transfer(state, args):
    state["transfers"] += 1
    if state["transfers"] > MAX_TRANSFERS or args["to"] == state["agent"]:
        state["agent"] = "human_queue"
        return "Passing you to a person who can help with all of this."
    state["handoff_notes"].append({"from": state["agent"], "to": args["to"], "summary": args["summary"]})
    state["agent"] = args["to"]
    return f"Transferred to {args['to']}."
```

பெறுற agent தன்னோட prompt, tools, hand-off summary, கடைசி சில turns-ஓட ஆரம்பிக்கும்; முழு history-யோட இல்ல. `cards` agent-கிட்ட மட்டும் தான் `block_card` இருக்கு, அதனால குழம்பிப்போன front-desk agent ஒரு card-ஐ block பண்ண முடியாது.

**Planted mistakes-ஓட reviewer-ஐ test பண்ணுங்க.** ஒரு generator-reviewer ஜோடி, reviewer எவ்வளவு நல்லா இருக்காங்களோ அவ்வளவு தான் நல்லது:

```python
PLANTED = [
    ("Interest is 12% a year; the EMI on ₹5 lakh over 5 years is ₹4,000.", "wrong EMI"),   # real EMI is about ₹11,100
    ("You can withdraw your fixed deposit any time without penalty.", "missing penalty"),
    ("This loan is guaranteed approved.", "promise of approval"),
]

def reviewer_recall(review_fn):
    caught = sum(1 for draft, _ in PLANTED if not review_fn(draft)["pass"])
    return caught / len(PLANTED)
```

நிஜ reviews-ல இருந்து எடுத்த 20-ல இருந்து 50 planted mistakes-ஓட ஒரு set-ஐ வச்சுக்கோங்க; reviewer-ஓட prompt அல்லது model-ஐ மாத்துற ஒவ்வொரு தடவையும் recall-ஐ track பண்ணுங்க. நல்ல drafts-ஐ அடிக்கடி fail பண்ணலன்னும் check பண்ணுங்க, இல்லன்னா writers அதை புறக்கணிக்க கத்துக்குவாங்க.

**Agents systems ஏன் fail ஆகுது.** Multi-agent failures பத்தின ஆய்வுகள், பெரும்பாலான பிரச்சனைகள் பலவீனமான models பத்தியது இல்லன்னு சொல்லுது: roles overlap ஆகும் அல்லது தெளிவில்லாம இருக்கும், agents தாங்க கண்டுபிடிச்சதை pass பண்ணாது, யாராவது ரொம்ப சீக்கிரம் நிறுத்திடுவாங்க, அல்லது final result-ஐ யாருமே check பண்ணாது. ஒவ்வொரு role-ஓட எல்லைகளையும் எழுதுங்க, hand-off summaries-ஐ கட்டாயமாக்குங்க, முடிஞ்ச answer-ஐ check பண்ற பொறுப்பை ஒரு agent-கிட்ட (அல்லது உங்க code-கிட்ட) தெளிவா கொடுங்க.

**கூடுதல் cost-ஐ எண்ணுங்க.** ஒவ்வொரு agent-உம் instructions-ஐயும் tool definitions-ஐயும் repeat பண்ணும், summaries கூடுதல் calls. ஒரு single-agent baseline-ஓட ஒப்பிட்டு task-க்கு tokens-ஐ measure பண்ணி, quality அல்லது speed-ல கிடைக்குற லாபம் அதுக்கு தகுதியான்னு முடிவு பண்ணுங்க.

## ஒரு worked example

Bengaluru-ல ஒரு bank-ஓட customer assistant balances, card blocks, loan queries, complaints-ஐ handle பண்ணுது.

Version one, 22 tools இருந்த ஒரு single agent, 9% நேரம் தப்பான tools-ஐ தேர்ந்தெடுத்துச்சு; அதுக்கு card-block permissions-ஐ பாதுகாப்பா கொடுக்கவே முடியல.

Version two hand-offs use பண்ணுது:

- Balances, FAQs-க்கு read-only tools-ஓடவும், ஒவ்வொரு specialist-க்கும் ஒரு hand-off tool-ஓடவும் ஒரு **front-desk agent**.
- Cards-ஐ block பண்ணலாம் (identity-ஐ confirm பண்ணின பிறகு), ஆனா பணத்தை நகர்த்த முடியாத ஒரு **cards agent**.
- Loan accounts-க்கு read access-உம் prepayment calculator-உம் இருக்குற ஒரு **loans agent**.
- Grievance system-ல complaints-ஐ record பண்ணி, customer-க்கு ஒரு complaint reference number தர்ற ஒரு **complaints agent**.

ஒவ்வொரு hand-off-உம் ஒரு சின்ன summary-ஐயும் கடைசி சில turns-ஐயும் pass பண்ணுது; அதனால customers திரும்ப சொல்ல வேண்டியதில்ல. தொடர்ச்சியா ரெண்டுக்கு மேல hand-offs நடக்காம தடுத்து, அதுக்கு பதிலா ஒரு human-கிட்ட route பண்ற ஒரு rule இருக்கு. தப்பான tool தேர்வுகள் 2%-க்கு குறையுது, ஒவ்வொரு agent-ஓட permissions-உம் narrow-ஆ இருக்குறதால security team approve பண்ணுது. Token use 30% கூடுது, முக்கியமா summaries-னால; இதை bank ஏத்துக்குது.

Complaint responses-க்கு மட்டும் ஒரு generator-reviewer ஜோடி சேர்க்கப்படுது; அங்க ஒரு reviewer agent tone-ஐயும், reference number, timelines சரியா இருக்கான்னும் check பண்ணுது; அது 6% drafts-ல பிரச்சனைகளை பிடிக்குது.

| Measure | ஒரு agent, 22 tools | நாலு specialists-க்கு hand-offs |
| --- | --- | --- |
| தப்பான tool தேர்வுகள் | 9% | 2% |
| Card-block permissions | பாதுகாப்பா கொடுக்க முடியல | Cards agent மட்டும், identity checks-க்கு அப்புறம் |
| Token use | Baseline | Summaries-னால சுமார் 30% அதிகம் |
| Security review | Approve ஆகல | Approve ஆச்சு |

## பொதுவா பண்ற தப்புகள்

- **எளிய task-க்கு பல agents.** ஒண்ணுல ஆரம்பிங்க; ஒரு பிரச்சனையை measure பண்ணும்போது பிரிங்க.
- **தெளிவில்லாத roles.** Overlap ஆகுற agents வாதாடும் அல்லது வேலையை duplicate பண்ணும். கூர்மையான role descriptions எழுதுங்க.
- **தகவல் தொலையுற hand-offs.** ஒரு summary-ஐயும் சமீபத்திய turns-ஐயும் pass பண்ணுங்க; முக்கிய விவரங்களை users திரும்ப சொல்ல வேண்டியதில்லன்னு test பண்ணுங்க.
- **Loop limits இல்லாம இருக்குறது.** Agents வேலையை முன்னும் பின்னும் முடிவில்லாம hand back பண்ணலாம்.
- **ஒவ்வொரு agent-க்கும் தனி traces மட்டும்.** ஒரு request, எல்லா agents-ஓட steps-ஐயும் ஒண்ணா காட்டணும்.
- **Test பண்ணாத reviewers.** Planted mistakes-ல எத்தனையை அவங்க பிடிக்கிறாங்கன்னு measure பண்ணுங்க.
- **தனக்கே transfer பண்ணிக்கிற agents.** Code-ல அதை block பண்ணி, transfers-ஐ cap பண்ணுங்க.

## எப்போ ஒரு agent போதும்

- **ஒரே domain, சில tools மட்டும்**: ஒரு single agent மலிவானது, debug பண்ணவும் எளிது.
- **வரிசையான, இறுக்கமா பிணைஞ்ச steps**, பிரிக்குறது hand-off இழப்புகளை மட்டும் சேர்க்கும் இடங்கள்.
- **குறைந்த volume**, பல agents-ஓட engineering செலவு திரும்ப கிடைக்காத இடங்கள்.

Domains-க்கு வெவ்வேற permissions தேவைப்படும்போது, வேலையை parallel-ஆ ஓட்ட முடியும்போது, அல்லது ஒரே context எல்லாத்தையும் வச்சுக்க முடியாதபோது பல agents-ஆ பிரிங்க.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு agent-ஐயும் ஒரே request id-க்கு கீழ trace பண்ணுங்க**, hand-off summaries தெரியுற மாதிரி.
- **Transfer rates-ஐயும் loops-ஐயும் track பண்ணுங்க**, ஒவ்வொரு agent ஜோடிக்கும்; மிக மோசமான conversations-ஐ வாரம் ஒரு தடவை review பண்ணுங்க.
- **ஒவ்வொரு agent-க்கும் தனி permissions வச்சுக்கோங்க**, tool code-ல enforce பண்ணி.
