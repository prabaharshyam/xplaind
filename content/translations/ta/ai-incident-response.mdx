## இது என்ன

**Incident**-னா, users-ஐயோ business-ஐயோ பாதிச்சு, அவசர response தேவைப்படுற எந்த event-உம். வழக்கமான outages-ஓட AI systems புது வகைகளை சேர்க்குது:

- **Availability**: provider outage, rate limits, உடைஞ்ச pipeline.
- **Cost**: கட்டுப்பாடு இல்லாம ஓடுற agents அல்லது traffic spikes budget-ஐ எரிக்கிறது.
- **Quality**: ஒரு model, prompt அல்லது document மாற்றத்துக்கு அப்புறம் பதில்கள் திடீர்னு தப்பா வர்றது.
- **Safety, security**: harmful content, prompt injection, data leakage, அனுமதியில்லாத actions.
- **Fairness, compliance**: நியாயமில்லாத outputs-ஓட ஒரு pattern, அல்லது personal data தப்பா use ஆகுறது.

**Incident response**-ங்கறது இவற்றை கையாளுற திட்டமிட்ட வழி: detect, assess, contain, fix, communicate, learn.

```flow
dir: LR
Detect | alerts, complaints -> Assess | severity 1, 2 அல்லது 3; roles பெயர் போட்டு
Assess -> Contain | kill switch, rollback, document நீக்கு, மனுஷங்க எடுத்துக்குறாங்க
Contain -> Investigate | traces, logs, release ids
Investigate -> Communicate | client, users, தேவைப்பட்டா regulators
Communicate -> Learn | blameless review, owners-ஓட actions, புது eval cases
Learn -[monitoring மேம்படுது]-> Detect
```

இந்த lesson-ல, Chennai-ல ஒரு e-commerce company-ல ஒரு சனிக்கிழமை நடந்த incident-ஐ follow பண்றோம்; அங்க support assistant தப்பான returns window-ஐ சொல்லிடுச்சு.

## இது எப்படி work ஆகுது

**Detect.** Errors, latency, cost, guardrail triggers, refusal rates, negative feedback, online eval scores மேல alerts. ஒரு தெளிவான channel வழியா users, staff reports. நிறைய AI incidents முதல்ல சில complaints-ஆ தான் தெரியும்; அவற்றை சீரியசா எடுத்துக்குங்க.

**Severity-ஐ assess பண்றது.** Levels-ஐ முன்னாடியே define பண்ணுங்க. உதாரணமா: data leakage, customers-க்கு harmful output அல்லது அனுமதியில்லாத actions-க்கு severity 1; பரவலா தப்பான பதில்கள் அல்லது முழு outage-க்கு severity 2; ஒரு area-ல degraded quality-க்கு severity 3. யாரை எழுப்புறது, எவ்வளவு வேகமா என்பதை severity தான் அமைக்கும்.

**Roles.** Coordinate பண்ணி decisions எடுக்குற ஒரு incident commander, hands-on fix பண்ற ஒருத்தர், stakeholders-ஓட communicate பண்ற ஒருத்தர். சின்ன team-ல ஒரே ஆள் பல roles-ஐ வச்சிருக்கலாம், ஆனா commander role தெளிவா இருக்கணும்.

**முதல்ல contain பண்ணுங்க.** காரணத்தை கண்டுபிடிக்கிறதுக்கு முன்னாடி harm-ஐ நிறுத்துங்க: ஒரு tool அல்லது feature-க்கு kill switch flip பண்ணுங்க, முந்தின release-க்கு rollback பண்ணுங்க, index-ல ஒரு document-ஐ disable பண்ணுங்க, மனுஷங்களுக்கு route பண்ணுங்க. உங்களுக்கு தேவைப்படுறதுக்கு முன்னாடியே containment options இருந்து test ஆகியிருக்கணும்.

**Records வச்சு investigate பண்ணுங்க.** Traces, audit logs, release identifiers என்ன நடந்துச்சுன்னு காட்டும். அவற்றை preserve பண்ணுங்க.

**Communicate.** Clients-க்கும் users-க்கும் சரியான நேரத்துல, நேர்மையான updates தேவை. Regulated clients-க்கு DPDP Act-ல personal data breach reporting மாதிரி notification duties இருக்கலாம்; அவங்க privacy, legal teams-ஐ உடனே சேர்த்துக்குங்க.

**Learn.** ஒரு blameless post-incident review: timeline, impact, root causes (பெரும்பாலும் பல), என்ன நல்லா நடந்துச்சு, என்ன மாத்தணும், owners, dates-ஓட. Trigger பண்ண cases-ஐ eval suite-லயும் monitoring-லயும் சேருங்க.

**Severity levels, responses:**

| Level | Examples | Response |
| --- | --- | --- |
| 1 | Data leakage, customers-க்கு harmful output, அனுமதியில்லாத actions | On-call, leads-ஐ உடனே page பண்ணுங்க; நிமிஷங்கள்ல contain |
| 2 | பரவலா தப்பான பதில்கள், முழு outage | 15 நிமிஷத்துல on-call; சில மணி நேரத்துல client-க்கு தகவல் |
| 3 | ஒரு area-ல degraded quality | அடுத்த working day; முடியும் வரை track பண்ணப்படும் |

**ஒவ்வொரு incident வகைக்கும் ஒரு runbook page.** ஒவ்வொரு வகை incident-க்கும் ஒரு page எழுதுங்க: எப்படி detect ஆகுது, switches-க்கு links-ஓட முதல் மூணு containment actions, யாருக்கு சொல்லணும், சம்பந்தப்பட்ட traces, logs எங்க இருக்கு. அழுத்தத்துல படிக்கிற அளவுக்கு சின்னதா வச்சிருங்க. ஒரு tabletop exercise-ல அந்த page-ஐ அப்படியே follow பண்ணி, தெளிவில்லாத அல்லது பழசான ஒவ்வொரு இடத்தையும் note பண்ணி, அதே வாரத்துல fix பண்ணுங்க.

**ஒரு incident-ஓட போது client-க்கு எழுதுறது.** ஒத்துக்கிட்ட இடைவெளிகள்ல சின்ன, உண்மையான updates அனுப்புங்க: என்ன நடக்குது, users என்ன பார்த்திருக்கலாம், என்ன செஞ்சிருக்கோம், அடுத்த update எப்போ வரும். ஆரம்ப updates-ல causes-ஐ ஊகிக்காதீங்க. "தப்பான பதில்களை நிறுத்திட்டோம், எத்தனை customers பாதிக்கப்பட்டாங்கன்னு உறுதி பண்ணிக்கிட்டு இருக்கோம்"ன்னு சொல்றது, தப்பா போற ஒரு confident விளக்கத்தை விட அதிக நம்பிக்கையை உருவாக்கும்.

**Hard limits மட்டும் இல்லாம, normal-ல இருந்து drift-ஐ detect பண்ணுங்க.** நிறைய AI incidents ஒரு rate சத்தமில்லாம மாறுவது தான். கடந்த ஒரு மணி நேரத்தை சமீபத்திய நாட்களோட அதே மணி நேரத்தோட ஒப்பிடுங்க:

```python
from statistics import mean, pstdev

def anomalous(current, history, min_sigma=3.0, min_abs=0.02):
    """current: rate this hour; history: same-hour rates from the last 14 days."""
    mu, sd = mean(history), pstdev(history) or 0.005
    return (current - mu) / sd > min_sigma and current - mu > min_abs

# e.g. refusal rate, guardrail triggers, thumbs-down rate, judge failure rate
if anomalous(0.11, [0.03, 0.04, 0.03, 0.05, 0.04, 0.03, 0.04]):
    page_on_call("Refusal rate 11% vs about 4% normal for this hour")
```

**ஒரு மோசமான document-ஐ ஒரே step-ல contain பண்ணுங்க.** "Assistant தப்பான price-ஐ quote பண்ணுது"ங்கறதுக்கு வேகமான fix, பெரும்பாலும் ஒரு source-ஐ நீக்குறது தான்:

```python
def quarantine_document(doc_id, index, cache, audit, reason, who):
    index.set_flag(doc_id, quarantined=True)        # every search filters quarantined docs
    purged = cache.delete_where(source_doc=doc_id)  # cached answers built from it
    audit.write(actor=who, action="quarantine", target=doc_id, detail={"reason": reason, "cache_purged": purged})
```

அதை ஒரு admin button-ஆ ஆக்கி, launch-க்கு முன்னாடி test பண்ணி, runbook-ல சேருங்க.

**Traces-ல இருந்து impact-ஐ அளவிடுங்க.** Customers-உம் regulators-உம் "எத்தனை பேர் இதை பார்த்தாங்க?"ன்னு கேப்பாங்க. Traces retrieve ஆன document ids-ஐ record பண்ணியிருந்தா, பதில் ஒரே ஒரு query:

```sql
SELECT count(DISTINCT user_id) AS users, count(*) AS answers,
       min(created_at) AS first_seen, max(created_at) AS last_seen
FROM traces
WHERE 'pricing-2026-11' = ANY(retrieved_doc_ids)
  AND created_at BETWEEN '2026-11-06 09:00+05:30' AND '2026-11-07 14:30+05:30';
```

Trace data இல்லன்னா இது நாள் கணக்கான ஊகமா மாறும்; அதனால தான் retrieved ids-ஐ முதல் நாள்ல இருந்தே log பண்ணணும்.

**இந்தியால reporting duties.** ஒரு personal data breach, DPDP Act, அதோட Rules-ல Data Protection Board-க்கும் பாதிக்கப்பட்டவங்களுக்கும் notice கடமைகளை trigger பண்ணலாம். தனியா, CERT-In-ஓட 2022 directions, நிறைய வகை cyber security incidents-ஐ 6 மணி நேரத்துக்குள்ள report பண்ணணும்னு கேக்குது. ஒரு incident reportable-ஆ இல்லையான்னு யார் முடிவு பண்ணுவாங்கன்னு (பெரும்பாலும் client-ஓட legal அல்லது privacy lead) முன்னாடியே ஒத்துக்கிட்டு, அவங்க contact-ஐ runbook-ல வச்சிருங்க.

**Practice பண்ணுங்க.** ஒவ்வொரு quarter-லயும் ஒரு வேற scenario-ஓட ஒரு tabletop exercise ஓட்டுங்க: leak ஆன ஒரு document, social media-ல ஒரு jailbreak screenshot, ஒரு provider outage, formatting-ஐ உடைக்கிற ஒரு model update. Detection-ஐயும் containment-ஐயும் time பண்ணி, உங்களை மெதுவாக்கினதை fix பண்ணுங்க.

## ஒரு example

சனிக்கிழமை, காலை 11:40. Chennai-ல ஒரு e-commerce company-ஓட support assistant, ₹5,000-க்கு மேல இருக்குற orders-க்கு 60 நாளுக்குள்ள free returns கிடைக்கும்னு customers-க்கு சொல்ல தொடங்குது. Policy 15 நாள்னு சொல்லுது.

11:55: returns கேள்விகள்ல negative feedback மூணு மடங்கு ஆகுது; ஒரு alert fire ஆகுது. On-call engineer incident commander ஆகி severity 2-ஐ declare பண்றாங்க.

12:05: அன்னைக்கு காலைல marketing publish பண்ண ஒரு "Diwali returns campaign" page-ஐ பதில்கள் cite பண்றதை traces காட்டுது; அதுல ஒரு product category-க்கு மட்டும் 60 நாள்னு இருந்துச்சு. Containment: அந்த page index-ல இருந்து நீக்கப்படுது, assistant-ஓட returns பதில்கள் ஒரு fixed, approved policy message-க்கு மாத்தப்படுது.

12:20: customer support leads-க்கு சொல்லப்படுது; பாதிக்கப்பட்ட customers-க்கு 60 நாள் வாக்குறுதியை நிறைவேத்த தயாராகுறாங்க. Audit logs 312 conversations-ஐ identify பண்ணுது; அந்த orders-க்கு அந்த statement-ஐ honour பண்ண company முடிவு பண்ணுது.

திங்கள் blameless review மூணு causes-ஐ கண்டுபிடிக்குது: indexing-க்கு முன்னாடி marketing pages-ஓட review இல்லை, campaign pages-ல effective-date, scope metadata இல்லை, returns மேல golden-set questions இல்லை. Actions: marketing pages ஒரு review step-ஓட ஒரு தனி index-க்கு போகும், scope metadata சேர்க்கப்படும், 20 returns questions golden set-ல சேர்க்கப்படும், policy சம்பந்தப்பட்ட பதில்கள்ல திடீர் மாற்றங்களுக்கு ஒரு alert.

| Time | Event |
| --- | --- |
| 11:40 | Assistant 60-நாள் returns-ஐ வாக்குறுதி கொடுக்க தொடங்குது |
| 11:55 | Feedback alert; severity 2 declare ஆகுது |
| 12:05 | Campaign page index-ல இருந்து நீக்கம்; fixed policy message on |
| 12:20 | Support leads-க்கு தகவல்; 312 conversations identify ஆகி, honour பண்ணப்பட்டது |
| திங்கள் | Blameless review: மூணு causes, owners-ஓட நாலு actions |

## பொதுவா பண்ற தப்புகள்

- **Contain பண்றதுக்கு முன்னாடி investigate பண்றது.** முதல்ல harm-ஐ நிறுத்துங்க.
- **Test பண்ணாத kill switches, rollbacks.** அவற்றை practice பண்ணுங்க.
- **Severity levels இல்லாம இருக்கிறது.** ஒவ்வொரு incident-உம் ஒண்ணு பதட்டமா மாறும், இல்லன்னா புறக்கணிக்கப்படும்.
- **Client-கிட்ட மௌனம்.** கெட்ட செய்தி எப்படியும் பரவும்; சீக்கிரமே, நேர்மையா சொல்லுங்க.
- **யார் தப்புன்னு பார்க்குற reviews.** மக்கள் தப்புகளை மறைப்பாங்க, system முன்னேறாது.
- **Traces-ல retrieved ids இல்லாம இருக்கிறது**, அதனால impact-ஐ அளக்க முடியாது.
- **காகிதத்துல மட்டும் இருக்குற containment tools.** Launch-க்கு முன்னாடி ஒவ்வொரு switch-யையும் quarantine-யையும் test பண்ணுங்க.
- **Client-க்கு சொல்றதுக்கு root cause-க்காக காத்திருக்கிறது.** உங்ககிட்ட இருக்குற facts-ஐ அனுப்புங்க.

## எப்போ lighter process போதும்

- **ஒரு சில users இருக்குற internal prototypes**: பெயர் போட்ட ஒரு owner, ஒரு kill switch, ஒரு chat channel போதும்.
- **Public data மேல read-only tools**, மோசமான நிலைமையே மக்கள் check பண்ணக்கூடிய ஒரு தப்பான பதில்தான்ங்குற இடத்துல.

Customers, personal data, பணம் அல்லது regulated decisions சம்பந்தப்படும்போது, முழு severity levels, on-call rotas, runbooks, drills தேவை.

## Demo-ல இருந்து production-க்கு

- **Errors-க்கு மட்டும் இல்லாம**, refusals, guardrail triggers, feedback, judge failures-ஓட rate மாற்றங்களுக்கு alert பண்ணுங்க.
- **Containment-ஐ ஒரு click தூரத்துல வச்சிருங்க**: kill switches, rollback, document quarantine, எல்லாமே test ஆகி.
- **Retrieved ids, versions, users-ஐ log பண்ணுங்க**, அப்போ impact-ஐ வேகமா அளக்கலாம்.
- **DPDP, CERT-In கடமைகளுக்கு reporting decision-maker-ஐ** runbook-ல பெயர் போடுங்க.
- **Quarter-க்கு ஒரு தடவை drill பண்ணி**, ஒவ்வொரு தடவையும் மெதுவான step-ஐ fix பண்ணுங்க.

## Practice பண்ணுங்க

Incidents-ஐ manage பண்றது பத்தின Google SRE chapter-ஐயும், postmortem culture பத்தின அதோட workbook chapter-ஐயும் படிங்க. AI Incident Database-ல incidents-ஐ பாருங்க.

1. நீங்க build பண்ண ஒரு AI system-க்கு severity levels, roles-ஐ define பண்ணி, ஒவ்வொரு incident வகைக்கும் இருக்கும் containment actions-ஐ list பண்ணுங்க.
2. ஒரு tabletop exercise ஓட்டுங்க: "Assistant தப்பான price-ஐ quote பண்ணுது", detection, containment, communication, investigation-ஐ walk through பண்ணுங்க.
3. அந்த exercise-க்கு ஒரு blameless review எழுதுங்க, குறைஞ்சது மூணு actions-ஓட.
4. உங்க சொந்த traces-க்கான impact query-ஐ எழுதி, கடந்த வாரத்துல ஒரு document-க்கு ஓட்டுங்க.

இன்னும் ஆழமா படிக்க, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 10 வேகமான detection, response-க்கான monitoring-ஐயும், chapter 5 நிறைய incidents-ஓட பின்னாடி இருக்குற attacks-ஐயும் பேசுது.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க containment options வேலை செய்றதை (ஒரு rollback, ஒரு kill switch), உங்க team உண்மையிலயே use பண்ற ஒரு review template-ஐயும் காட்ட முடியும்.
