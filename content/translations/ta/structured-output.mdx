## இது என்ன

Applications-க்கு data தேவை, prose இல்ல. Model-ஓட reply-ல இருந்து உங்க code ஒரு price, ஒரு category அல்லது items list-ஐ படிக்கணும்னா, **structured output** கேளுங்க: வரையறுக்கப்பட்ட shape-க்கு (ஒரு **schema**) பொருந்துற JSON. அப்புறம் உங்க code use பண்றதுக்கு முன்னாடி validate பண்ணுங்க.

இப்போ பெரும்பாலான providers, model-ஐ schema-க்கு பொருந்துற valid JSON-ஐ தர வைக்கிற features-ஐயோ, அதையே பண்ற tool definitions-ஐயோ கொடுக்கறாங்க.

```flow
குழப்பமான text | "Selling my Samsung Galaxy S21, 2 yrs old, minor scratches, 18k negotiable, pickup Malviya Nagar" -> Model
Schema | product: str, price_inr: int 0-க்கு மேல, condition: enum, city: str அல்லது null -> Model
Model -> JSON -> Validate
Validate -[சரி]-> Save | product "Samsung Galaxy S21", price_inr 18000, condition "used", city "Jaipur"
Validate -[fail]-> Error-ஓட ஒரு தடவை retry
Error-ஓட ஒரு தடவை retry -[மறுபடி fail]-> Moderator
```

இந்த lesson-ல Jaipur-ல ஒரு online marketplace, sellers-ஓட free-text listings-ஐ search பண்ணக்கூடிய records-ஆ மாத்துறதை follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**Shape-ஐ வரையறுங்க.** Fields, அவற்றோட types, எது required-ன்னு முடிவு பண்ணுங்க. Python-ல Pydantic model ஒரு வசதியான வழி:

```python
from typing import Literal
from pydantic import BaseModel, Field

class Listing(BaseModel):
    product: str
    price_inr: int = Field(gt=0)
    condition: Literal["new", "used", "refurbished"]
    city: str | None = None
```

**அதை கேளுங்க.** Schema-ஓட provider-ஓட structured-output feature, இல்லன்னா schema-வை tool-ஓட input-ஆ வச்ச tool calling, இல்லன்னா fallback-ஆ தெளிவான instructions-ஓட exact JSON-ஓட ஒரு example.

**Validate பண்ணுங்க.** Reply-ஐ parse பண்ணி schema-ஓட validate பண்ணுங்க:

```python
from pydantic import ValidationError

try:
    item = Listing.model_validate_json(reply_text)
except ValidationError as err:
    # log err, retry once with the error message, or send to a person
    ...
```

Validation, தப்பான types (price "about 500"ங்குற text-ஆ இருக்கிறது), missing fields, range-க்கு வெளியே இருக்குற values-ஐ பிடிக்கும்.

**Failures-ஐ கையாளுங்க.** Validation error வந்தா: என்ன தப்புன்னு model-கிட்ட சொல்லி ஒரு தடவை retry பண்ணுங்க; மறுபடி fail ஆனா அந்த item-ஐ human review-க்கு mark பண்ணுங்க. Invalid data-வை உங்க database-குள்ள விடாதீங்க.

**"தெரியாது"-ஐ அனுமதிங்க.** Input-ல தகவல் இல்லாம இருக்கலாம்ன்ற இடத்துல fields-ஐ optional ஆக்குங்க அல்லது null-ஐ allow பண்ணுங்க, instructions-லயும் அதை சொல்லுங்க. இல்லன்னா shape-ஐ நிரப்ப model ஒரு value-வை கற்பனை பண்ணலாம்.

**Categories-க்கு enums use பண்ணுங்க.** அனுமதிக்கப்பட்ட values-ஓட fixed list ("new", "used", "refurbished") பின்னால செய்யுற analysis-க்கு categories-ஐ consistent-ஆ வச்சிருக்கும்.

**Schema design தேர்வுகள்:**

| Field வகை | நல்ல design | தவிர்க்க வேண்டியது |
| --- | --- | --- |
| Money | Range check-ஓட integer rupees, உதாரணம் `price_inr: int > 0` | "18k" மாதிரி text |
| Category | அனுமதிக்கப்பட்ட values-ஓட enum | மாறிக்கிட்டே இருக்கும் free text |
| இல்லாம இருக்கக்கூடிய தகவல் | Optional, null allowed, instructions-லயும் சொல்லுங்க | கற்பனையை கட்டாயப்படுத்துற required fields |
| திரும்ப வர்ற items | Objects-ஓட ஒரு list | item1, item2 மாதிரி numbered fields |
| Dates | Validate பண்ண ISO dates | வேற வேற formats-ல free-form dates |

**கண்மூடித்தனமா இல்ல, error-ஓட retry பண்ணுங்க.** Validation fail ஆனா, model-ஓட முந்தின reply-ஐயும், exact validation message-ஐயும் அனுப்புங்க, உதாரணம் "price_inr: input should be a valid integer, got '18k'". பெரும்பாலான errors ஒரு retry-ல சரியாயிடும். Error இல்லாம retry பண்ணா பெரும்பாலும் அதே தப்பையே திரும்ப பண்ணும்.

**ஐந்து layers, லேசுல இருந்து கனமானது வரை.** Model-ஐ சரியான shape-க்கு பல இடங்கள்ல தள்ளலாம்:

| Layer | எப்படி work ஆகுது | Reliability | Cost |
| --- | --- | --- | --- |
| Prompting | Instructions + exact example | Strong models-ல நல்லா இருக்கும், உறுதி இல்ல | இலவசம் |
| Post-processing | Closing bracket missing, JSON-ஐ சுத்தி code fence மாதிரி common slips-ஐ code சரி பண்ணும் | தப்புகள் சின்னதா, திரும்ப திரும்ப வந்தா work ஆகும் | மலிவு |
| Retry | Validation error-ஓட, fit ஆகுற வரை மறுபடி கேக்குறது | அதிகம், ஆனா ஒவ்வொரு retry-க்கும் ஒரு call செலவு | கூடுதல் calls, delay |
| Constrained decoding | Output-ஐ valid-ஆ வச்சிருக்குற tokens-ஐ மட்டும் provider அல்லது library model-ஐ தேர்ந்தெடுக்க விடும் | Shape உறுதி | கொஞ்சம் மெதுவு; support ஆகுற formats மட்டும் |
| Fine-tuning | உங்க format-ல நிறைய examples-ல train பண்றது | ஒரு fixed format-க்கு அதிகம் | Data, training முயற்சி |

முதல் மூணு, கிட்டத்தட்ட சரியா இருக்குற model-க்கான கட்டுகள். Providers-ஓட structured-output features-உம், Outlines, guidance, llama.cpp grammars மாதிரி open-source libraries-உம் constrained decoding-ஐ தான் use பண்றாங்க: model அடுத்த token-ஐ தேர்ந்தெடுக்க போகும்போது, grammar-ஐ உடைக்குற ஒவ்வொரு token-உம் choices-ல இருந்து நீக்கப்படும். Models ஒரே சில தப்புகளை திரும்ப திரும்ப பண்ணும், அதனால post-processing நிறைய தூரம் போகும்: ஒரு forgiving parser, சரியா format ஆன YAML-ஐ 90%-ல இருந்து 99.99%-க்கு உயர்த்துச்சுன்னு LinkedIn report பண்ணுச்சு.

**Valid JSON-னா correct JSON இல்ல.** பழைய "JSON mode" features, reply parse ஆகும்னு மட்டும் தான் உறுதி கொடுக்கும், உங்க fields இருக்குன்னு இல்ல. Schema-constrained output-ல கூட தப்பான value இருக்கலாம். எந்த JSON-உம் reply `max_tokens`-ஐ தொட்டா வெட்டப்படலாம், அதனால முதல்ல stop reason-ஐ check பண்ணுங்க.

**Types-ஐ மட்டும் இல்ல, values-ஐயும் check பண்ணுங்க.** `price_inr` ஒரு positive integer-ன்னு schema உறுதி பண்ணும், ஆனா ரெண்டு வருஷம் பழைய phone-க்கு ₹18,000 நியாயமான்னு அதுக்கு தெரியாது. Validation-க்கு அப்புறம் business checks சேருங்க: category-க்கு நியாயமான range-ல prices, தெரிஞ்ச list-ல இருந்து cities, எதிர்காலத்துல இல்லாத dates. Schema-வை தாண்டி business check-ல fail ஆகுற values-உம் invalid ones மாதிரியே review-க்கு போகும். இந்த ரெண்டு layer approach, முதல்ல schema, அப்புறம் business rules, invoice extraction-க்கும் கிட்டத்தட்ட எல்லா structured-output pipelines-க்கும் use பண்ற அதே pattern.

**முழு pipeline code-ல.** உத்தரவாதமான shape-ஐ வாங்க ஒரு பொதுவான வழி: உங்க schema-வை input-ஆ கொண்ட ஒரே ஒரு tool-ஐ model-க்கு கொடுத்து, அந்த tool-ஐ use பண்ணணும்னு கட்டாயப்படுத்துறது. இது Anthropic-ஓட Python SDK-ல ஓடுது; மத்த providers-க்கும் இணையானவை இருக்கு:

```python
import anthropic
from pydantic import ValidationError

client = anthropic.Anthropic()
TOOL = {"name": "save_listing", "description": "Save one product listing.",
        "input_schema": Listing.model_json_schema()}
CITIES = {"Jaipur", "Ajmer", "Udaipur", "Jodhpur"}

def business_errors(item):
    errors = []
    if not 100 <= item.price_inr <= 500_000:
        errors.append(f"price_inr {item.price_inr} is outside 100 to 500000")
    if item.city and item.city not in CITIES:
        errors.append(f"city {item.city!r} is not a city we serve")
    return errors

def extract(text, max_attempts=2):
    messages = [{"role": "user", "content": "Extract the listing. Use null for anything not stated.\n\n" + text}]
    for _ in range(max_attempts):
        reply = client.messages.create(
            model="claude-sonnet-5-5", max_tokens=500, messages=messages,   # check the docs for current names
            tools=[TOOL], tool_choice={"type": "tool", "name": "save_listing"},
        )
        if reply.stop_reason == "max_tokens":
            return None, "cut off: raise max_tokens"
        call = next(b for b in reply.content if b.type == "tool_use")
        try:
            item = Listing.model_validate(call.input)
            problems = business_errors(item)
        except ValidationError as err:
            item, problems = None, [str(err)]
        if not problems:
            return item, "ok"
        # Send the exact error back so the model can fix it.
        messages += [{"role": "assistant", "content": reply.content},
                     {"role": "user", "content": [{"type": "tool_result", "tool_use_id": call.id,
                                                   "is_error": True, "content": "; ".join(problems)}]}]
    return None, "to moderator: " + "; ".join(problems)
```

ஒவ்வொரு outcome-உம் ஒரு valid `Listing` அல்லது தெளிவான காரணம், அதனால தான் moderator queue எது தப்பாச்சுன்னு exact-ஆ காட்ட முடியுது. ஒவ்வொரு outcome-ஐயும் தினமும் எண்ணுங்க; ஒரு வகை error அதிகமானா, inputs மாறிடுச்சுன்னு அது பெரும்பாலும் முதல் அடையாளம்.

## ஒரு worked example

Jaipur-ல ஒரு online marketplace, sellers-ஓட listings-ஐ free text-ஆ பெறுது: "Selling my Samsung Galaxy S21, 2 yrs old, minor scratches, 18k negotiable, pickup Malviya Nagar".

Pipeline, provider-ஓட structured output feature-ஐ use பண்ணி, product, price, condition, city உள்ள ஒரு `Listing`-ஐ model-கிட்ட கேக்குது. ஒவ்வொரு reply-லயும் validation ஓடுது.

500 listings-ல results:

- 471 முதல் தடவையே valid.
- 18-ல prices "18k" அல்லது "around 20,000"ன்னு எழுதப்பட்டிருந்தது; schema text-ஐ reject பண்ணுது, code validation error-ஓட ஒரு தடவை retry பண்ணுது, 15 integers-ஆ (18000, 20000) திரும்ப வந்துச்சு.
- மத்த 11 முழுசா fail ஆச்சு (listing-ல price-ஏ இல்ல, அல்லது ஒரு post-ல ரெண்டு products). Retry-க்கு அப்புறமும் fail ஆன 3-ஓட சேர்த்து, 14 moderator queue-க்கு போகுது.

Invalid-ஆ எதுவும் database-க்கு போகாததால, site-ல price filters-உம் city search-உம் தொடர்ந்து work ஆகுது.

| Step | Listings | Share |
| --- | --- | --- |
| முதல் தடவையே valid | 471 | 94% |
| Error-ஓட ஒரு retry-ல சரியானது | 15 | 3% |
| Moderators-க்கு அனுப்பியது | 14 | 3% |
| Database-ல invalid records | 0 | 0% |

**Moderators-க்கு ஏன் பிடிச்சுது.** Moderators-க்கு வந்த 14 listings, original text, model-ஓட முயற்சி, exact validation error-ஓட வந்துச்சு, அதனால ஒவ்வொண்ணும் சில வினாடிகள்ல சரியாச்சு. Pipeline-க்கு முன்னாடி, moderators தினமும் நூற்றுக்கணக்கான listings-ஐ கையால சரி பண்ணாங்க.

## பொதுவான தவறுகள்

- **String tricks வச்சு free text-ஐ parse பண்றது.** JSON கேட்டு validate பண்ணுங்க.
- **"பெரும்பாலும் சரியா தான் இருக்கும்"ன்னு validation-ஐ skip பண்றது.**
- **ஒவ்வொரு field-ஐயும் கட்டாயப்படுத்துறது.** இல்லாம இருக்கக்கூடிய தகவலுக்கு null-ஐ allow பண்ணுங்க.
- **Free-text categories.** Fixed list use பண்ணுங்க.
- **முடிவில்லாம retry பண்றது.** Error-ஓட ஒரு தடவை retry பண்ணி, அப்புறம் ஒரு ஆள்கிட்ட அனுப்புங்க.

- **Tests-ஐ update பண்ணாம schema-வை மாத்துறது.** Expected outputs-ஓட sample inputs set-ஐ வச்சிருந்து, schema மாறும்போதெல்லாம் மறுபடி ஓட்டுங்க.
- **Stop reason-ஐ கவனிக்காம விடுறது.** `max_tokens`-ல வெட்டப்பட்ட reply, model எவ்வளவு நல்லதா இருந்தாலும், உடைஞ்ச JSON.
- **பெரிய, ஆழமா nested ஆன schemas.** ஒவ்வொரு கூடுதல் field-உம் தப்பாகுற இன்னொரு வாய்ப்பு. உங்க code use பண்றதை மட்டும் கேளுங்க, ரொம்ப பெரிய extractions-ஐ steps-ஆ பிரிங்க.

## Schema தேவையில்லாத இடங்கள்

- **Reply நேரா ஒரு ஆளுக்கு போகுது**, உதாரணம் chat answer அல்லது email draft. Plain text போதும்.
- **ஒரு சின்ன list-ல இருந்து ஒரு label**: strict prompt + reply அனுமதிக்கப்பட்ட வார்த்தைகள்ல ஒண்ணான்னு ஒரு check போதும்.
- **Notebook-ல விரைவான exploration**, எந்த fields முக்கியம்னு தெரியறதுக்கு முன்னாடி.

## Demo-ல இருந்து production-க்கு

- **Schema-வை API மாதிரி version பண்ணுங்க**, அவற்றோட எழுதப்பட்ட records இருக்கும் வரை பழைய versions-ஐ படிக்கக்கூடியதா வச்சிருங்க.
- **Real குழப்பமான inputs-ஓட, expected outputs-ஓட ஒரு test set வச்சிருங்க**, ஒவ்வொரு schema, prompt, model மாற்றத்துக்கும் ஓட்டுங்க.
- **ஒவ்வொரு outcome-ஐயும் log பண்ணுங்க**: முதல் தடவையே valid, retry-ல சரியானது, வெட்டப்பட்டது, review-க்கு போனது. Rates-ஐ தினமும் கவனிங்க.
- **Reviewers-க்கு context கொடுங்க**: original text, model-ஓட முயற்சி, exact error.
- **Cost-ஐ கவனிங்க**: retries-உம் நீளமான schemas-உம் tokens-ஐ கூட்டும், அதனால ஒரு call-க்கு இல்ல, ஒரு valid record-க்கு tokens-ஐ track பண்ணுங்க.
