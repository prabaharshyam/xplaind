## இது என்ன

உங்க laptop-ல work ஆகுற code ஒரு ஆரம்பம் தான், முடிவு இல்லை. **Project tooling**-னா உங்க code-ஐ சுத்தி இருக்குற எல்லாமே; வேற ஒருத்தர் அதை run பண்ணவும், பாதுகாப்பா மாத்தவும், விடியற்காலை 2 மணிக்கு debug பண்ணவும் அது உதவும். நாலு பகுதிகள் ரொம்ப முக்கியம்:

| பகுதி | என்ன தருது | இது இல்லன்னா |
| --- | --- | --- |
| **தனிப்படுத்தின environment** | Project-ஓட packages வேற எதோடயும் மோதாது | "என் machine-ல work ஆகுது" |
| **pyproject.toml-உம் ஒரு நல்ல layout-உம்** | Project எங்கயும் ஒரே மாதிரி install ஆகும் | அதை set up பண்றது எப்படின்னு யாருக்கும் தெரியாது |
| **pytest-ஓட tests** | ஏதாவது உடைக்கிற மாற்றம், ship ஆகுறதுக்கு முன்னாடியே சத்தமா fail ஆகும் | Users bugs-ஐ கண்டுபிடிப்பாங்க |
| **Logging** | Production-ல ஏதாவது தப்பா போனா, என்ன நடந்ததுன்னு பார்க்கலாம் | ஊகம் தான் |

இதுல எதுவுமே கவர்ச்சியானது இல்ல. ஆனா இல்லன்னா எல்லாமே கவனிக்கப்படும்; பெரும்பாலும் நீங்க ஒப்படைச்ச அடுத்த வாரம் client-ஓட engineer-ஆல.

இந்த lesson-ல, Coimbatore-ல ஒரு textile exporter-க்கு நீங்க build பண்ண invoice extractor-ஐ, அவங்க engineer-ஆன Karthik எடுத்துக்கிறதை follow பண்றோம். Lesson முடியும் போது, README-ஐ மட்டும் வச்சு ஒரு புதுசா வர்றவர் set up பண்ணி, test பண்ணி, debug பண்ணக்கூடிய projects-ஐ நீங்க உருவாக்குவீங்க.

## இது எப்படி work ஆகுது

### Environments-உம் lock files-உம்

ஒவ்வொரு project-க்கும் தன் சொந்த virtual environment கிடைக்கும். `pip`-ஓட `venv`, அல்லது வேகமான `uv` மாதிரி tools ஒண்ணை உருவாக்கி, நீங்க pin பண்ண versions-ஐ அப்படியே install பண்ணும். `uv.lock` அல்லது முழுசா pinned `requirements.txt` மாதிரி **lock file**, உங்க packages சார்ந்திருக்குற packages உட்பட ஒவ்வொரு package-ஓட சரியான version-ஐயும் record பண்ணும்; அதனால வேற machine-உம் சரியா அதே set-ஐ பெறும்.

### Layout

ஒரு Python project-க்கு பொதுவான, பாதுகாப்பான வடிவம்:

```text
invoice-extractor/
  pyproject.toml           # name, version, dependencies, tool settings
  uv.lock                  # exact versions of everything
  README.md                # how to set up, test and run
  src/invoice_extractor/   # your package
      __init__.py
      extract.py
      models.py
  tests/                   # pytest tests
      conftest.py          # shared fixtures
      test_extract.py
      fixtures/sample_invoice.txt
```

`src` folder, உங்க சொந்த folder-ல இருந்து மட்டும் work ஆகுற code-ஐ tests தப்பா import பண்றதை தடுக்கும். `pyproject.toml`, `setup.py` மாதிரி பழைய files-ஓட குவியலை மாத்தி, pytest, linters மாதிரி tools-ஓட settings-ஐ ஒரே இடத்துல வச்சிருக்கும்.

### pytest

ஒரு test-னா பேர் `test_`-ல ஆரம்பிக்கிற, சாதாரண `assert` use பண்ற ஒரு function. pytest எல்லாத்தையும் கண்டுபிடிச்சு run பண்ணும்:

```python
def test_total_matches_line_items(sample_invoice):
    inv = parse_invoice(sample_invoice)
    assert inv.total == sum(i.amount for i in inv.items)
```

**Fixtures**, tests பேர் சொல்லி கேக்குற shared setup-ஐ கொடுக்கும்: ஒரு sample PDF, ஒரு temporary folder, ஒரு fake model client. அவை `tests/conftest.py`-ல இருக்கும்.

### Model-ஐ call பண்ற code-ஐ test பண்றது

Unit tests-ல real model calls மெதுவானவை, பணம் செலவாகும், ஒவ்வொரு தடவையும் கொஞ்சம் வேற பதில் தரும்; அதனால tests தற்செயலா fail ஆகும். அதுக்கு பதிலா:

| | Unit tests | Evaluation suite |
|---|---|---|
| எப்போ | வேகமா, ஒவ்வொரு commit-லயும் | மெதுவா, ஒரு schedule-ல |
| எதை check பண்ணும் | உங்க parsing, validation, scoring logic | 50-200 examples இருக்குற golden set-ல real model |
| Model | ஒரு fake client fixed reply தரும் | Real model; quality-ஐ score பண்ணி, காலப்போக்குல track பண்ணும் |

உங்க சொந்த logic-ஐ fake client வச்சு test பண்ணுங்க; model-ஓட quality-ஐ தனியா அளங்க.

### Logging

Production-ல `print` output மறைஞ்சிடும். `logging` module ஒவ்வொரு message-க்கும் ஒரு **level**, ஒரு நேரம், அது வந்த module-ஐ கொடுத்து, platform logs-ஐ சேகரிக்கிற இடத்துக்கு அனுப்பும்.

| Level | எதுக்கு |
| --- | --- |
| DEBUG | Developers-க்கான விவரம், production-ல off |
| INFO | சாதாரண நிகழ்வுகள்: ஒரு request handle ஆச்சு, ஒரு file process ஆச்சு |
| WARNING | வித்தியாசமா இருந்தாலும் handle ஆனது: ஒரு retry, ஒரு மோசமான input skip ஆச்சு |
| ERROR | ஏதோ fail ஆச்சு, கவனிக்கணும் |

ஒவ்வொரு module-க்கும் ஒரு logger use பண்ணுங்க, `log = logging.getLogger(__name__)`, output-ஐ start-up-ல ஒரு தடவை configure பண்ணுங்க, ஒரு புதுசா வர்றவருக்கு உதவுற facts-ஐ log பண்ணுங்க: எந்த request, எந்த document, எவ்வளவு நேரம் ஆச்சு, என்ன fail ஆச்சு.

### README

ஒரு நல்ல README, ஒரு புதுசா வர்றவர் உங்ககிட்ட எதுவும் கேக்காம, clone-ல இருந்து tests pass ஆகுற வரை போக வைக்கும். அதுல சரியான commands வரிசையா இருக்கும்: environment-ஐ set up பண்ணு, environment variables-ஐ set பண்ணு (உண்மையான secret values இல்லாம), tests-ஐ run பண்ணு, tool-ஐ run பண்ணு. அதை எழுதி, அப்புறம் ஒரு புது folder-ல நீங்களே test பண்ணுங்க; பெரும்பாலான READMEs ரெண்டாவது வரியிலயே உடையும்.

## ஒரு உதாரணம்

Coimbatore-ல ஒரு textile exporter-க்கு ஒரு invoice extractor-ஐ build பண்ணீங்க. அடுத்த மாசம் அவங்க engineer-ஆன Karthik, நீங்க இல்லாம அதை run பண்ணி maintain பண்ணணும்.

**முதல் நாள்.** அவர் repository-ஐ clone பண்ணி, README-ஐ follow பண்றாரு:

```text
uv sync            # installs the exact locked versions
uv run pytest      # 12 passed
```

நீங்க test பண்ண versions-ஐயே lock file install பண்ணுது. பன்னிரண்டுல ரெண்டு tests:

```python
import pytest

from invoice_extractor.extract import parse_invoice
from invoice_extractor.models import Invoice

def test_total_matches_line_items(sample_invoice):
    inv = parse_invoice(sample_invoice)
    assert inv.total == sum(i.amount for i in inv.items)

def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValueError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

`sample_invoice` என்பது `tests/conftest.py`-ல இருக்குற ஒரு fixture; அது ஒரு சின்ன text file-ஐ load பண்ணும், அதனால real model call தேவையில்ல.

**ஒரு மாசம் கழிச்சு.** Production-ல ஒரு invoice fail ஆகுது. Log வரி இப்படி இருக்கு:

```text
2026-11-20 10:14:03 WARNING invoice_extractor.extract invoice=INV-8812 pages=3 field=total model_value="12,40,000.00" error="not a number"
```

இந்திய முறை digit grouping, number parser-ஐ உடைச்சதுன்னு Karthik உடனே பார்த்துடுறாரு. "12,40,000.00"-க்கு ஒரு test-ஐ சேர்த்து, parser-ஐ சரி பண்ணி, எல்லா 13 tests-உம் pass ஆகுறதை பார்த்து, ship பண்றாரு.

| Tooling இல்லாம | Tooling-ஓட |
| --- | --- |
| ஒரு user-ஓட "சில நேரம் fail ஆகுது" | Invoice, field, value-ஐ பேர் சொல்ற ஒரு log வரி |
| ஒரு fix-ஐ check பண்ண வழி இல்லை | Fix-க்கு முன்னாடி fail ஆகி, அப்புறம் pass ஆகுற ஒரு புது test |
| Server-ல வேற package versions | எங்கயும் ஒரே locked versions |
| Karthik உங்களுக்கு WhatsApp-ல message பண்றாரு | Karthik தனியா 20 நிமிஷத்துல fix பண்றாரு |

## பொதுவா பண்ற தப்புகள்

- **System Python-ல install பண்றது.** உங்க laptop-ல work ஆகும், வேற எங்கயும் ஆகாது. எப்பவும் ஒரு project environment use பண்ணுங்க.
- **Pin பண்ணாத versions.** ஒரு library breaking change-ஓட release பண்ணா, புது install fail ஆகும். Lock file-ஐ commit பண்ணுங்க.
- **Real model-ஐ call பண்ற tests.** அவை மெதுவானவை, பணம் செலவாகும், தற்செயலா fail ஆகும். Unit tests-ல client-ஐ fake பண்ணுங்க.
- **Secrets அல்லது personal data-வை log பண்றது.** API keys, முழு documents, customer phone numbers-ஐ ஒருபோதும் log பண்ணாதீங்க. அதுக்கு பதிலா ids, sizes-ஐ log பண்ணுங்க.
- **"run main.py"ன்னு சொல்ற README.** Set up, test, run பண்ண சரியான commands-ஐ எழுதி, அவற்றை நீங்களே test பண்ணுங்க.
- **Production-ல DEBUG logging-ஐ on-ல விடுறது.** அது disks-ஐ நிரப்பிடும், data-வை leak பண்ணவும் கூடும்.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற pytest-ஓட Get Started page-ஐ செய்து, அப்புறம் Python-ஓட logging tutorial-ஓட basic section-ஐ படிங்க.

1. **Restructure.** நீங்க எழுதுன ஏதாவது ஒரு script-ஐ, `pyproject.toml`, ஒரு `src` layout, ஒரு `tests` folder இருக்குற ஒரு project-ஆ மாத்துங்க.
2. **Test.** ஐந்து tests எழுதுங்க; அதுல ஒண்ணு ஒரு fixture use பண்ணணும், ஒண்ணு ஒரு error raise ஆகுதான்னு check பண்ணணும்.
3. **Log.** ஒவ்வொரு `print`-ஐயும் ஒரு பொருத்தமான level-ல ஒரு logger call-ஆ மாத்துங்க, ஒரு failure-ஐ debug பண்ண உதவுற ஒரு log வரியையும் சேருங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** Repository-ஐ ஒரு friend-கிட்ட கொடுத்து, README-ல இருக்குற ரெண்டு commands-ல tests-ஐ run பண்ண வச்சு, அவை எல்லாம் pass ஆக வைக்க முடியும்.
