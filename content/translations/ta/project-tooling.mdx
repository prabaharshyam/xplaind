## இது என்ன

உங்க laptop-ல வேலை செய்யுற code ஆரம்பம் தான், முடிவு இல்ல. **Project tooling**-னா உங்க code-ஐ சுத்தி இருக்குற எல்லாமே: அது இன்னொருத்தர் அதை run பண்ண, safe-ஆ மாத்த, ராத்திரி 2 மணிக்கு debug பண்ண உதவுது. ஒவ்வொரு பகுதியும் ஒரு புது ஆள் கேக்கப்போற ஒரு கேள்விக்கு பதில் சொல்லுது:

| புது ஆள் கேக்குறது | பதில் சொல்ற file அல்லது tool | அது இல்லைன்னா |
| --- | --- | --- |
| எந்த Python, எந்த packages? | `pyproject.toml`, `uv.lock`, `.python-version` | "என் machine-ல வேலை செய்யுது" |
| Code எங்க இருக்கு, அதை எப்படி import பண்றது? | `.venv`-ல install ஆன ஒரு `src` layout | ஒரே ஒரு folder-ல இருந்து மட்டும் வேலை செய்யுற imports |
| என் change எதையாவது உடைச்சுதா? | pytest tests | Users கண்டுபிடிக்குற bugs |
| இந்த code tidy-ஆ, obvious தப்புகள் இல்லாம இருக்கா? | ruff | ஒவ்வொரு review-லயும் style சண்டைகள் |
| API key எங்க போகும்? | `.env` (ignored), `.env.example` (committed) | git-ல leak ஆன keys |
| Production-ல என்ன நடந்துச்சு? | ஒரே தடவை configure பண்ண `logging` | ஊகம் |
| Clean machine-லயும் இன்னும் வேலை செய்யுதா? | ஒவ்வொரு push-லயும் CI | "என் laptop-ல pass ஆச்சு" |
| முதல்ல என்ன type பண்ணணும்? | Exact commands இருக்குற README | உங்களுக்கு ஒரு WhatsApp message |

இதுல எதுவுமே glamorous இல்ல. ஆனா இல்லாதப்போ எல்லாமே கவனிக்கப்படும், பொதுவா நீங்க handover பண்ண அடுத்த வாரம், client-ஓட engineer-ஆல.

இந்த lesson-ல Coimbatore-ல ஒரு textile exporter-க்கு நீங்க build பண்ண invoice extractor-ஐ, அவங்க engineer Karthik அதை எடுத்துக்கும்போது follow பண்றோம். இது **uv**-ஐ use பண்ணுது: Astral-ஓட ஒரு fast tool, அது environment-ஐ create பண்ணும், packages-ஐ install பண்ணும், lock file-ஐ எழுதும், Python-ஐயே install பண்ணவும் முடியும். சாதாரண `venv`, `pip`-உம் வேலை செய்யும்; ஒவ்வொரு section-உம் வித்தியாசத்தை காட்டும்.

```flow
title: Clone-ல இருந்து நம்பகமான change வரை
dir: LR
Repository-ஐ clone பண்ணு -> Locked versions-ஐ install பண்ணு | uv sync
Locked versions-ஐ install பண்ணு -> Secrets-ஐ சேர் | .env.example-ஐ .env-ஆ copy பண்ணு
Secrets-ஐ சேர் -> Lint-உம் test-உம் | ruff-உம் pytest-உம்
Lint-உம் test-உம் -> Code-ஐ மாத்து
Code-ஐ மாத்து -> Push
Push -> CI ஒரு clean machine-ல checks-ஐ மறுபடி ஓட்டும்
```

## இது எப்படி work ஆகுது

### Layout

```text
invoice-extractor/
  pyproject.toml          # what the project is and needs
  uv.lock                 # exact versions of everything (commit it)
  .python-version         # the Python version the team uses
  .gitignore              # .venv, .env, __pycache__
  .env.example            # variable names, no real values
  README.md
  .github/workflows/ci.yml
  src/invoice_extractor/
      __init__.py
      cli.py              # entry point: configures logging, builds the client
      extract.py
      models.py
      llm.py              # the real model client
  tests/
      conftest.py         # shared fixtures, including a fake model client
      test_extract.py
      fixtures/sample_invoice.txt
```

`uv init --package invoice-extractor` இதுல பெரும்பாலானதை உங்களுக்காக create பண்ணிடும், ஒரு `src` folder, ஒரு `.python-version`, ஒரு git repository உட்பட.

### pyproject.toml

இதோ ஒரு முழுசான file, நாங்க uv 0.13.10, pytest 9.2.0, ruff 0.17.6 (28 November 2026 நிலவரப்படி மிகப் புதிய releases) வச்சு ஓட்டின மாதிரியே:

```toml
[project]
name = "invoice-extractor"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pydantic>=2.10",
]

[project.scripts]
invoice-extractor = "invoice_extractor.cli:main"

[dependency-groups]
dev = ["pytest>=9.0", "ruff>=0.17"]

[build-system]
requires = ["uv_build>=0.13.10,<0.14.0"]
build-backend = "uv_build"

[tool.pytest]
testpaths = ["tests"]
addopts = ["-ra", "--strict-markers"]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```

ஒவ்வொரு பகுதியும் என்ன பண்ணுது:

- **`[project]`** package-க்கு பேர் வைக்குது, அது run ஆக என்ன தேவைன்னு list பண்ணுது. இங்க exact pins வேண்டாம், ranges (`>=2.10`) use பண்ணுங்க; exact versions-ஐ lock file வச்சுக்கும்.
- **`[project.scripts]`** ஒரு command-ஐ create பண்ணுது, அதனால `uv run invoice-extractor` `cli.py`-ல இருக்குற `main()`-ஐ call பண்ணும்.
- **`[dependency-groups]`** developers-க்கு மட்டும் தேவைப்படுற tools-ஐ வச்சுக்குது. `uv sync` default-ஆ `dev` group-ஐ install பண்ணும்; `uv sync --no-dev` அதை production image-ல சேர்க்காம விட்டுடும்.
- **`[build-system]`** `src/`-ஐ install பண்ணக்கூடிய package-ஆ எப்படி மாத்துறதுன்னு சொல்லுது. அது இல்லைன்னா, uv அந்த folder-ஐ scripts-ஓட ஒரு loose collection-ஆ தான் பார்க்கும், உங்க package-ஐ install பண்ணாது.
- **`[tool.pytest]`** pytest 9-ல சேர்த்த native TOML table. பழைய pytest-ல, அதே keys-ஓட `[tool.pytest.ini_options]` use பண்ணுங்க.

**Python-ஐ pin பண்றது.** `requires-python` நீங்க support பண்றதா promise பண்ற range. `.python-version` எல்லாரும், CI உட்பட, உண்மையா use பண்ற ஒரே version; அது இல்லைன்னா uv அதை download பண்ணிடும். Python 3.15 9 October 2026-ல வந்துச்சு, ஆனா முதல் நாளே மாறணும்னு அவசியம் இல்ல: `.python-version`-ஐ ஏத்துறதுக்கு முன்னாடி, உங்க கனமான libraries புது version-க்கு wheels publish பண்றாங்களான்னு check பண்ணுங்க, அப்புறம் CI அதை prove பண்ணட்டும்.

### src layout, எல்லாரும் மறக்குற install step

Code `src/`-ல இருக்கும்போது, நீங்க project folder-ல நிக்குறீங்கங்குறதுக்காக மட்டும் Python `invoice_extractor`-ஐ import பண்ண முடியாது. அது தான் point: ஒரு user மாதிரியே, ஒரு install வழியா தான் tests உங்க package-ஐ reach பண்ண முடியும். Package-ல ஒரு file missing-ஆ இருந்தாலோ, `pyproject.toml`-ல ஒரு தப்பான setting இருந்தாலோ, அது client-ஓட server-ல இல்லாம உங்க laptop-லயே தெரிஞ்சுடும்.

இதோட விளைவு கிட்டத்தட்ட ஒவ்வொரு beginner-ஐயும் தடுக்கி விழ வைக்குது. Package install ஆகலைன்னா, tests ஆரம்பிக்குறதுக்கு முன்னாடியே fail ஆகும்:

```text
E   ModuleNotFoundError: No module named 'invoice_extractor'
```

`uv sync` project-ஐ `.venv`-ல **editable** mode-ல install பண்ணுது, அதனால reinstall பண்ணாமலே உங்க edits effect-க்கு வரும். சாதாரண pip-ல, இதையே கையால பண்ணுங்க: ஒரு venv create பண்ணி activate பண்ணுங்க, அப்புறம் `pip install -e . --group dev` ஓட்டுங்க (`--group`-க்கு pip 25.1 அல்லது அதுக்கு அப்புறம் வந்த version வேணும்). `PYTHONPATH`-ல `src`-ஐ சேர்த்தோ, `conftest.py`-ல `sys.path` hacks போட்டோ இந்த error-ஐ "fix" பண்ணாதீங்க; அது layout தர்ற பாதுகாப்பையே எடுத்துடும்.

### Lock files, --locked

`uv add httpx` ஒரே step-ல range-ஐ `pyproject.toml`-ல சேர்த்து `uv.lock`-ஐ update பண்ணுது. Lock ஒவ்வொரு package-ஓட exact version-ஐயும் file hash-ஐயும் record பண்ணுது, உங்க packages depend பண்ற packages உட்பட. நீங்க deploy பண்ற எந்த application அல்லது service-க்கும் அதை commit பண்ணுங்க. மத்தவங்களுக்காக publish பண்ற ஒரு library இன்னும் `pyproject.toml`-ல loose ranges-ஐ தான் வச்சுக்கும், அப்போ தான் அது அதோட users மேல versions-ஐ திணிக்காது; ஆனாலும் உங்க சொந்த CI-க்காக அதோட lock-ஐ commit பண்றது useful தான்.

CI, Dockerfiles, README-ல `uv sync --locked` வச்சு install பண்ணுங்க. யாராவது `pyproject.toml`-ஐ கையால edit பண்ணிட்டு `uv lock` ஓட்ட மறந்துட்டா, அது உடனே நின்னுடும்:

```text
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
  cause: Requirements for `invoice-extractor==0.1.0` differ; added: httpx>=0.28
```

சாதாரண `uv sync` அதுக்கு பதிலா சத்தமில்லாம lock-ஐ மறுபடி எழுதிடும், அப்போ நீங்க test பண்ற versions நீங்க ship பண்ற versions-ல இருந்து விலகிப் போயிடும். வேணும்னே, ஒரு தடவைக்கு ஒரு package-ஆ upgrade பண்ணுங்க: `uv lock --upgrade-package pydantic`, tests ஓட்டுங்க, ரெண்டு files-ஐயும் commit பண்ணுங்க. pip-ல lock-க்கு சமமானது pip-tools மாதிரி ஒரு tool உருவாக்குற fully pinned requirements file; `pip freeze`-உம் வேலை செய்யும், ஆனா அப்போ install ஆகியிருக்குற மத்த எதையும் அது கூட கலந்துடும்.

### ruff வச்சு lint, format

**Ruff** ரெண்டு வேலை செய்யுற ஒரே fast tool. `ruff check` ஒரு **linter**: bugs ஆக வாய்ப்புள்ளதையும் bad patterns-ஐயும் கண்டுபிடிக்கும். `ruff format` ஒரு **formatter**: spacing-ஐயும் line breaks-ஐயும் ஒரே house style-ல மறுபடி எழுதும், அதனால reviews commas பத்தி இல்லாம logic பத்தி இருக்கும்.

```text
uv run ruff check --fix    # find problems, fix the safe ones
uv run ruff format         # rewrite layout
```

ruff 0.16-ல இருந்து, default set பெருசு: பல groups-ல இருந்து 400-க்கும் மேல rules. ஒரு `select` line அந்த default-ஐ நீக்கிட்டு, நீங்க பேரு சொல்ற groups-ஐ மட்டும் exact-ஆ வைக்கும். மேல இருக்குறது அதை விட சின்ன, predictable set தருது: `E`, `F` (pycodestyle, Pyflakes), `I` (sorted imports), `B` (bugbear: mutable default argument மாதிரி பொதுவான bug patterns), `UP` (உங்க Python version-க்கான புதிய, simple-ஆன syntax). Rule groups-ஐ ஒரு தடவைக்கு ஒண்ணா சேருங்க; ஒரு பழைய codebase-ல எல்லாத்தையும் ஒரே தடவை on பண்ணா நூத்துக்கணக்கான warnings வரும், team linter-ஐயே off பண்ணிடும்.

### Secrets, settings

Code secrets-ஐ environment variables-ல இருந்து மட்டும் தான் படிக்கும், வேற எங்கேயும் இல்ல:

```python
client = ModelClient(api_key=os.environ["MODEL_API_KEY"])
```

Variable இல்லைன்னா, இது start-up-லயே `KeyError: 'MODEL_API_KEY'` raise பண்ணும், முதல் invoice-ல வர்ற குழப்பமான failure-ஐ விட இது எவ்வளவோ நல்லது. Local-ஆ, values-ஐ ஒரு `.env` file-ல வச்சு `uv run --env-file .env` வச்சு load பண்ணுங்க. உண்மையான values இல்லாம பேருங்களை மட்டும் list பண்ற ஒரு `.env.example`-ஐ commit பண்ணுங்க:

```text
MODEL_API_KEY=
LOG_LEVEL=INFO
```

உங்க `.gitignore`-ஐ check பண்ணுங்க: `uv init` எழுதுறது `.venv`-ஐ cover பண்ணும், ஆனா `.env`-ஐ இல்ல, அதனால நீங்களே அதை சேர்த்து `git check-ignore .env` வச்சு confirm பண்ணுங்க. எப்பவாவது ஒரு உண்மையான key ஒரு commit-க்குள்ள போயிடுச்சுன்னா, அடுத்த commit-ல file-ஐ delete பண்றது உதவாது, ஏன்னா அது git history-ல இருந்துடும். முதல்ல key-ஐ revoke பண்ணி rotate பண்ணுங்க, அப்புறம் clean up பண்ணுங்க.

### Logging

Logging-ஐ **ஒரே தடவை**, entry point-ல configure பண்ணுங்க, வேற எங்கேயும் இல்ல:

```python
# cli.py
import logging
import os


def main() -> None:
    logging.basicConfig(
        level=os.environ.get("LOG_LEVEL", "INFO").upper(),
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
    )
```

மத்த ஒவ்வொரு module-உம் தன் பேருல ஒரு logger-ஐ கேட்டு வாங்குறது மட்டும் தான், ஒரு புது ஆள் act பண்ணக்கூடிய facts-ஐ log பண்ணும்:

```python
# extract.py
log = logging.getLogger(__name__)

log.warning(
    "invoice=%s field=total model_value=%r error=%s",
    data.get("id"),
    data["total"],
    err,
)
```

மேல இருக்குற மாதிரி, ஒரு f-string build பண்றதுக்கு பதிலா values-ஐ arguments-ஆ pass பண்ணுங்க; அப்போ logging module உண்மையா emit பண்ற messages-ஐ மட்டும் தான் format பண்ணும். உங்க log platform JSON fields-ல search பண்ண முடிஞ்சா, format-ஐ ஒரு line-க்கு ஒரு JSON object-ஆ மாத்துங்க; ids, fields, timings-ஐ log பண்ற பழக்கம் அதே தான். ஒரு command-ஓட உண்மையான output-க்கு, அதாவது extract பண்ண JSON மாதிரி, `print` இன்னும் OK தான்; program என்ன பண்ணுதுங்குற messages-க்கு அது தப்பு.

| Level | எதுக்கு use பண்றது | Production-ல |
| --- | --- | --- |
| DEBUG | Developers-க்கான detail: prompts, raw replies | Off |
| INFO | சாதாரண events: process ஆன ஒரு file, அது எடுத்த நேரத்தோட | On |
| WARNING | வித்தியாசமா இருந்தாலும் handle ஆனது: success ஆன ஒரு retry, skip பண்ண ஒரு bad input | On |
| ERROR | ஏதோ fail ஆயிடுச்சு, ஒரு ஆள் பார்க்கணும் | On, alerts-உம் |

API keys, passwords, முழு documents, customer phone numbers அல்லது PAN numbers மாதிரி personal data-வை எப்பவுமே log பண்ணாதீங்க. அதுக்கு பதிலா ids, sizes, timings-ஐ log பண்ணுங்க.

### Tests, ஒரு fake model client

pytest, fixtures, parametrised tests, mocking எல்லாம் "Writing tests with pytest" lesson-ல (B3) இருக்கு. Project structure-க்கு முக்கியம் எது எங்க இருக்குங்குறது தான். Shared fixtures `tests/conftest.py`-ல போகும், அதை pytest தானாவே load பண்ணும். Model-ஐ call பண்ற code-க்கு, எல்லாத்தையும் விட clean-ஆன design client-ஐ உள்ள pass பண்றது தான், அப்போ ஒரு test அதுக்கு ஒரு fake-ஐ குடுக்கலாம்:

```python
# tests/conftest.py
import json
from pathlib import Path

import pytest

FIXTURES = Path(__file__).parent / "fixtures"


class FakeModelClient:
    """Returns a fixed reply and records each prompt. No network, no cost."""

    def __init__(self, reply: dict):
        self.reply = json.dumps(reply)
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply


@pytest.fixture
def sample_invoice() -> str:
    return (FIXTURES / "sample_invoice.txt").read_text(encoding="utf-8")


@pytest.fixture
def fake_client() -> FakeModelClient:
    return FakeModelClient(
        {
            "id": "INV-0001",
            "gstin": "33ABCDE1234F1Z5",
            "total": "1500.00",
            "items": [
                {"description": "Cotton yarn", "amount": "1000.00"},
                {"description": "Dyeing", "amount": "500.00"},
            ],
        }
    )
```

இந்த unit tests உங்க சொந்த logic-ஐ check பண்ணும், ஒவ்வொரு push-லயும் ஒரு second-க்கும் ரொம்ப குறைவான நேரத்துல ஓடிடும். உண்மையான model-ஓட answers-ஐ judge பண்றது வேற வேலை, அதை fixed-ஆன, label பண்ண உண்மையான examples set மேல ஓடுற ஒரு evaluation run செய்யும்; "Test sets and evals" lesson (P1) 30-ல இருந்து 100 cases வச்சு ஆரம்பிக்கலாம்னு suggest பண்ணுது.

### ஒவ்வொரு push-லயும் CI

CI (continuous integration) ஒவ்வொரு push-க்கும் pull request-க்கும் அதே checks-ஐ ஒரு clean machine-ல ஓட்டும், அதனால "என் laptop-ல pass ஆச்சு"-ங்குறது இனிமே ஒரு argument இல்ல. ஒரு முழுசான GitHub Actions workflow:

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.4.0
      - run: uv sync --locked
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run pytest
```

uv `.python-version`-ஐ படிச்சு runner-ல அந்த Python-ஐ install பண்ணும். ஒரு gotcha: `setup-uv`-க்கு அதோட புது releases-க்கு `@v10` மாதிரி short tag இல்ல, அதனால முழு version-ஐ எழுதுங்க (அல்லது, இன்னும் strict-ஆ, commit hash-ஐ). Branch protection-ஐ on பண்ணுங்க, அப்போ CI red-ஆ இருக்கும்போது ஒரு pull request merge ஆக முடியாது.

நல்ல README ஒரு புது ஆளை உங்ககிட்ட எதுவுமே கேக்காம clone-ல இருந்து passing tests வரை போக விடும்:

## ஒரு worked example

Coimbatore exporter-க்காக நீங்க invoice extractor-ஐ build பண்ணீங்க. அடுத்த மாசம் Karthik நீங்க இல்லாமலே அதை run பண்ணி maintain பண்ணணும்.

**முதல் நாள்.** அவர் repository-ஐ clone பண்ணி README-ஐ follow பண்றாரு. `uv sync --locked` நீங்க test பண்ண அதே exact versions-ஐ install பண்ணுது, `uv run pytest` 12 passed-னு report பண்ணுது. அந்த பன்னிரண்டுல ரெண்டு tests:

```python
import pytest
from pydantic import ValidationError

from invoice_extractor.extract import parse_amount, parse_invoice
from invoice_extractor.models import Invoice


def test_total_matches_line_items(sample_invoice, fake_client):
    inv = parse_invoice(sample_invoice, client=fake_client)
    assert inv.total == sum(i.amount for i in inv.items)
    assert "Cotton yarn" in fake_client.prompts[0]


def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValidationError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

முதல் test `parse_invoice`-க்கு `conftest.py`-ல இருக்குற fake client-ஐ குடுக்குது, அதனால network call இல்லாமலே parsing logic-ஐயும், invoice text prompt-க்கு போய் சேர்ந்துச்சான்னும் check பண்ணுது. ஒரு GSTIN எப்பவுமே 15 characters, அதனால `Invoice` model அந்த 11-character GSTIN-ஐ reject பண்ணுது.

**ஒரு மாசம் கழிச்சு.** Production-ல ஒரு invoice fail ஆகுது. Log line இப்படி இருக்கு:

```text
2026-12-18 10:14:03,512 WARNING invoice_extractor.extract invoice=INV-8812 field=total model_value='12,40,000.00' error=not a number
```

என்ன நடந்ததுன்னு Karthik-க்கு உடனே புரியுது. Model total-ஐ Indian digit grouping-ஓட (12 lakh 40 thousand) copy பண்ணியிருக்கு, `parse_amount` நேரடியா `Decimal(value)`-ஐ call பண்ணுச்சு, அது commas-ஐ reject பண்ணும். Fake reply `"1500.00"`-ஐ use பண்ணதால எல்லா tests-உம் pass ஆச்சு, அந்த format உண்மையான invoices-ல எப்பவுமே இருந்ததில்ல. அவர் மூணு steps-ல வேலை செய்யுறாரு:

1. **Reproduce பண்றாரு.** எந்த fix-க்கும் முன்னாடி fail ஆகுற ஒரு test-ஐ சேர்க்குறாரு:

```python
def test_reads_indian_digit_grouping():
    assert str(parse_amount("12,40,000.00")) == "1240000.00"
```

2. **Fix பண்றாரு.** ஒரே ஒரு line-ஐ மாத்துறாரு: `return Decimal(value.replace(",", ""))`. `float`-க்கு பதிலா `Decimal` use பண்றதால paise exact-ஆ இருக்கும்.
3. **Prove பண்றாரு.** 13 tests-உம் pass ஆகுது, ruff clean, அவர் push பண்றாரு. Change merge ஆகுறதுக்கு முன்னாடி CI ஒரு clean runner-ல checks-ஐ மறுபடி ஓட்டுது.

அவர் fake reply-ஐயும் `"1,500.00"`-ஆ மாத்துறாரு, ஏன்னா ஒரு fake நீங்க அதுக்கு குடுக்குற replies அளவுக்கு தான் நல்லா இருக்கும்; அவற்றோட shape-ஐ உண்மையான logs-ல இருந்து copy பண்ணுங்க. முழு fix-க்கும் அவருக்கு சுமார் 20 நிமிஷம் ஆகுது, தனியாவே.

## பொதுவா பண்ற தப்புகள்

- **System Python-ல install பண்றது.** உங்க laptop-ல வேலை செய்யும், வேற எங்கேயும் செய்யாது. ஒவ்வொரு project-க்கும் அதுக்குன்னு ஒரு `.venv` வேணும்.
- **Install-ஏ ஆகாத ஒரு src layout.** Tests `ModuleNotFoundError`-ஓட fail ஆகும். ஒரு `[build-system]` சேர்த்து `uv sync` ஓட்டுங்க, அல்லது `pip install -e .`; `sys.path`-ஐ patch பண்ணாதீங்க.
- **Lock file-ஐ commit பண்ணாம விடுறது, அல்லது CI-ல சாதாரண `uv sync` ஓட்டுறது.** மாசக்கணக்கு கழிச்சு ஒரு dependency release ஒரு fresh install-ஐ உடைச்சுடும். `uv.lock`-ஐ commit பண்ணி `--locked` use பண்ணுங்க.
- **`.venv` அல்லது `.env`-ஐ commit பண்றது.** முதலாவது repository-ஐ பெருசாக்கும்; ரெண்டாவது keys-ஐ leak பண்ணும். ரெண்டையும் ignore பண்ணுங்க, `.env.example`-ஐ commit பண்ணுங்க, எப்பவாவது commit ஆன எந்த key-ஐயும் rotate பண்ணுங்க.
- **ஒவ்வொரு module-லயும், அல்லது library code-க்குள்ள `basicConfig`-ஐ call பண்றது.** Logging-ஐ ஒரே தடவை, entry point-ல configure பண்ணுங்க.
- **Secrets அல்லது personal data-வை log பண்றது.** Ids, sizes, timings-ஐ log பண்ணுங்க, keys, முழு documents, phone numbers-ஐ எப்பவுமே இல்ல.
- **Production-ல DEBUG-ஐ on-லயே விடுறது.** அது disks-ஐ நிரப்பும், paid log platforms-ல காசு செலவாகும், அடிக்கடி customer data இருக்குற raw prompts-ஐ print பண்ணும்.
- **உண்மையான model-ஐ call பண்ற unit tests.** அவை slow, காசு செலவாகும், random-ஆ fail ஆகும். ஒரு fake client-ஐ pass பண்ணுங்க; quality-ஐ ஒரு தனி evaluation-ல measure பண்ணுங்க.
- **எல்லா lint rules-ஐயும் ஒரே தடவை on பண்றது.** நூத்துக்கணக்கான warnings வரும், team அவற்றை படிக்குறதையே நிறுத்திடும். Rule groups-ஐ கொஞ்சம் கொஞ்சமா சேருங்க.
- **யாருமே follow பண்ணிப் பார்க்காத README.** Handover-க்கு முன்னாடி ஒரு fresh clone-ல இருந்து அதை test பண்ணுங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற pytest-ஓட Get Started page-ஐ முடிங்க, அப்புறம் Python-ஓட logging tutorial-ல basic section-ஐ.

1. **Restructure பண்ணுங்க.** `uv init --package` ஓட்டி, நீங்க எழுதின ஒரு script-ஐ `src/`-க்கு மாத்துங்க. `pyproject.toml`-ல `[dependency-groups]`, `[tool.pytest]`, `[tool.ruff.lint]`-ஐ சேருங்க, அப்புறம் `uv sync` ஓட்டி `uv.lock`-ஐயும் `.python-version`-ஐயும் commit பண்ணுங்க.
2. **Install ஏன் முக்கியம்னு பாருங்க.** Package install ஆகாத ஒரு scratch venv-ல pytest ஓட்டி `ModuleNotFoundError`-ஐ படிங்க. அப்புறம் அதை install பண்ணி மறுபடி ஓட்டுங்க.
3. **Model-ஐ fake பண்ணுங்க.** உங்க code ஒரு model-ஐ call பண்ணுதுன்னா, function client-ஐ ஒரு parameter-ஆ வாங்குற மாதிரி மாத்துங்க, `conftest.py`-ல ஒரு `FakeModelClient` fixture எழுதுங்க, அதை use பண்ற ஒரு test-ஐயும், ஒரு bad reply clear-ஆன error raise பண்ணுதான்னு check பண்ற ஒரு test-ஐயும் சேருங்க.
4. **Lint பண்ணுங்க, log பண்ணுங்க.** `ruff check --fix`, `ruff format` ஓட்டுங்க. Debugging-க்கான ஒவ்வொரு `print`-ஐயும் சரியான level-ல ஒரு logger call-ஆ மாத்துங்க, environment-ல இருந்து `LOG_LEVEL` எடுத்து, உங்க entry point-ல logging-ஐ ஒரே தடவை configure பண்ணுங்க.
5. **Secrets, CI.** எந்த key இருந்தாலும் அதை `.env`-க்கு மாத்துங்க, `.env`-ஐ `.gitignore`-ல சேருங்க, ஒரு `.env.example`-ஐ commit பண்ணுங்க, மேல இருக்குற workflow-ஐ சேருங்க. Push பண்ணி அது green ஆகுறதை பாருங்க.
6. **புது ஆள் test.** உங்க repository-ஐ `/tmp`-க்குள்ள clone பண்ணி, உங்க README-ஐ மட்டும் follow பண்ணி, உடையுற ஒவ்வொரு step-ஐயும் fix பண்ணுங்க.
