## இது என்ன

Git-ல ஒரு **branch**-னா ஒரு commit-ஐ சுட்டிக்காட்டுற label. ஒரு branch-ல புது commit பண்ணா, label அதுக்கு முன்னாடி நகரும். Branch-னா அவ்வளவு தான்; அதனால அதை உருவாக்குறது உடனடி, teams ஒவ்வொரு change-க்கும் ஒண்ணு உருவாக்கும்: bug fix, feature, experiment.

எல்லாரும் பகிர்ந்துக்கிற branch, பெரும்பாலும் **main**-னு பேரு, எப்பவும் work ஆகணும்; ஏன்னா எல்லாரும் அதன் மேல build பண்றாங்க, அதுதான் deploy ஆகுது. அதனால main-ல நேரடியா வேலை செய்யக்கூடாது. ஒரு branch உருவாக்கி, அங்க change-ஐ build பண்ணி test பண்ணி, தயாரானதும் திரும்ப கொண்டு வருவீங்க.

வேலையை திரும்ப கொண்டு வர ரெண்டு வழிகள் இருக்கு:

- **Merge** ரெண்டு history lines-ஐ இணைக்கும். நீங்க branch பண்ணதுக்கு அப்புறம் main நகர்ந்திருந்தா, Git ரெண்டு parents இருக்குற ஒரு **merge commit**-ஐ உருவாக்கும். History, side branch உட்பட, என்ன நடந்ததுன்னு அப்படியே காட்டும்.
- **Rebase** உங்க commits-ஐ இன்னொரு branch-ஓட மேல, நீங்க அதோட latest commit-ல இருந்தே ஆரம்பிச்ச மாதிரி replay பண்ணும். History ஒரு நேரான line ஆகும், படிக்க ஈஸி; ஆனா உங்க commits புது ids வாங்கும்.

ரெண்டும் கடைசியில ஒரே code-ஐ தான் தரும். வித்தியாசம் history எப்படி தெரியுதுங்குறதுலயும், அது யாருக்கு safe-ங்குறதுலயும்.

## இது எப்படி work ஆகுது

ஒரு team-ல அன்றாட வேலை இப்படி இருக்கும்:

```flow
title: ஒரு feature branch, ஆரம்பத்துல இருந்து merge வரை
Main-ஐ update பண்ணுங்க | git switch main, git pull -> புது branch | git switch -c feature/otp
புது branch -> சின்ன சின்ன steps-ஆ commit பண்ணுங்க | git add, git commit
சின்ன சின்ன steps-ஆ commit பண்ணுங்க -> Branch-ஐ push பண்ணுங்க | git push -u origin feature/otp
Branch-ஐ push பண்ணுங்க -> Pull request | review, checks
Pull request -[main நகர்ந்துடுச்சு]-> Main-ஐ உள்ள கொண்டு வாங்க | main-ஐ merge பண்ணுங்க, இல்ல main மேல rebase பண்ணுங்க
Main-ஐ உள்ள கொண்டு வாங்க -> Pull request
Pull request -[approve ஆச்சு, green]-> Main-ல merge பண்ணுங்க
Main-ல merge பண்ணுங்க -> Branch-ஐ delete பண்ணுங்க
```

**Create பண்ணி switch பண்றது.** `git switch -c feature/otp` நீங்க இருக்குற இடத்துல ஒரு branch-ஐ உருவாக்கி அதுக்கு உங்களை கொண்டு போகும். `git switch main` திரும்ப கொண்டு வரும். `git branch` branches-ஐ list பண்ணும்; இப்போ இருக்குறதுக்கு பக்கத்துல star இருக்கும்.

**Merge பண்றது.** Main-ல இருந்து `git merge feature/otp` branch-ஐ உள்ள கொண்டு வரும். நீங்க branch பண்ணதுல இருந்து main நகரலைன்னா, Git **fast-forward** பண்ணும்: main-ஓட label-ஐ உங்க கடைசி commit-க்கு நகர்த்தும், அவ்வளவு தான். Main நகர்ந்திருந்தா Git ஒரு merge commit-ஐ உருவாக்கும்.

**Conflicts.** ரெண்டு பக்கமும் ஒரே file-ல ஒரே lines-ஐ மாத்தியிருந்தா, Git நின்னு file-ஐ mark பண்ணும்:

```text
<<<<<<< HEAD
OTP_EXPIRY_SECONDS = 300
=======
OTP_EXPIRY_SECONDS = 120
>>>>>>> feature/otp
```

`=======`-க்கு மேல இருக்குறது உங்க current branch-ல இருக்குறது; கீழ இருக்குறது உள்ள வர்ற change. நீங்க file-ஐ வேணும்ங்குற version-க்கு edit பண்ணி, markers-ஐ delete பண்ணி, அதை `git add` பண்ணி, commit பண்ணுவீங்க. Conflict ஒரு error இல்லை. Git தனியா பதில் சொல்ல முடியாத ஒரு கேள்வியை உங்ககிட்ட கேக்குது, அவ்வளவு தான்.

**Rebase பண்றது.** உங்க branch-ல `git rebase main` உங்க commits-ஐ ஒரு பக்கம் எடுத்து வச்சு, branch-ஐ main-ஓட நுனிக்கு நகர்த்தி, அவற்றை ஒண்ணொண்ணா replay பண்ணும். ஏதாவது ஒண்ணுல conflict வந்தா Git நிக்கும்; நீங்க file-ஐ fix பண்ணி, `git add` பண்ணி, `git rebase --continue` ஓட்டுவீங்க. `git rebase --abort` எல்லாத்தையும் முன்னாடி இருந்த மாதிரியே திருப்பிடும்.

| | Merge | Rebase |
| --- | --- | --- |
| History | ரெண்டு lines-ஐயும் வச்சுக்கும், merge commit சேர்க்கும் | ஒரே நேரான line |
| Commit ids | மாறாது | உங்க commits புது ids வாங்கும் |
| Shared branches-ல safe-ஆ | ஆமா | இல்லை: வேற யார்கிட்டயும் இல்லாத commits-ல மட்டும் |
| Conflicts | Merge-ல ஒரே தடவை resolve பண்றது | ஒவ்வொரு commit-க்கும் resolve பண்ண வேண்டி வரலாம் |
| எதுக்கு நல்லது | முடிஞ்ச branch-ஐ main-க்குள்ள கொண்டு வர | Review-க்கு முன்னாடி உங்க சொந்த branch-ஐ update பண்ண |

நிறைய teams ரெண்டையும் சேர்த்து use பண்ணும்: வேலை செய்யும்போது உங்க சொந்த branch-ஐ current-ஆ வச்சுக்க rebase பண்ணுங்க; pull request main-க்கு போகும்போது merge பண்ணுங்க (பெரும்பாலும் **squash merge**, branch-ஐ ஒரே commit-ஆ மாத்தும்).

## ஒரு example

Priya, Bengaluru-ல ஒரு fintech startup-ல login service-ல வேலை செய்றாங்க. அவங்க ticket: OTP expiry-ஐ அஞ்சு நிமிஷத்துல இருந்து ரெண்டு நிமிஷமா குறைக்கணும்.

Fresh main-ல இருந்து ஆரம்பிச்சு ஒரு branch உருவாக்குறாங்க:

```bash
git switch main
git pull
git switch -c feature/otp-expiry
```

`config.py`-ல `OTP_EXPIRY_SECONDS`-ஐ மாத்தி, test-ஐ update பண்ணி, ரெண்டு தடவை commit பண்றாங்க: ஒண்ணு change-க்கு, ஒண்ணு test-க்கு. Branch-ஐ push பண்ணி pull request திறக்குறாங்க.

அவங்க pull request review-க்கு காத்திருக்கும்போது, teammate Arjun அதே line-ல ஒரு change-ஐ merge பண்றாங்க: ஒரு regulator guideline பத்தின comment-ஓட, மதிப்பை 300 seconds-க்கு மாத்தியிருக்காங்க. Priya-வோட pull request இப்போ "This branch has conflicts"-ன்னு காட்டுது.

அவங்க branch அவங்களோடது, வேற யாரும் pull பண்ணல, அதனால rebase பண்றாங்க:

```bash
git fetch origin
git rebase origin/main
```

Git அவங்க முதல் commit-ஐ replay பண்ணி நின்னுடுது: `config.py`-ல conflict. Arjun-ஓட comment-ஐ படிச்சு, lead-கிட்ட check பண்ணி, இந்த flow-க்கு regulator 120 seconds அனுமதிக்குதுன்னு தெரிஞ்சுக்கிறாங்க. தங்க மதிப்பையும் Arjun-ஓட comment-ஐயும் வச்சுக்கிட்டு, markers-ஐ நீக்கி, continue பண்றாங்க:

```bash
git add config.py
git rebase --continue
git push --force-with-lease
```

`--force-with-lease` GitHub-ல இருக்குற அவங்க branch-ஐ replace பண்ணும், ஆனா இடைல வேற யாரும் அதுல push பண்ணியிருக்கலேன்னா மட்டும். Rebase-க்கு அப்புறம் push பண்ண safe-ஆன வழி இதுதான். Pull request green-ஆ, conflict இல்லாம இருக்கு; approve ஆகி ஒரே clean commit-ஆ main-ல squash-merge ஆகுது, அவங்க branch-ஐ delete பண்றாங்க.

## பொதுவா பண்ற தப்புகள்

- **Main-ல நேரடியா வேலை செய்றது.** ஒரு மோசமான commit எல்லாருடைய base-ஐயும் உடைச்சுடும். ஒரு வரி fix-க்கு கூட branch பண்ணுங்க.
- **ரொம்ப நாள் இருக்குற branches.** மூணு வாரம் இருக்குற branch வலிக்குற conflicts-ஐ சேர்த்துக்கும். சின்ன changes-ஐ அடிக்கடி merge பண்ணுங்க.
- **Shared branch-ஐ rebase பண்றது.** Teammates pull பண்ண commits-ஐ மாத்துனா, அவங்ககிட்ட இருக்குற copies இனி ஒத்து வராது. உங்க சொந்த, share பண்ணாத வேலையை மட்டும் rebase பண்ணுங்க.
- **சாதாரண `git push --force`.** அது teammate-ஓட commits-ஐ அழிச்சுடலாம். `--force-with-lease` use பண்ணுங்க, அதுவும் உங்க சொந்த branch-ல மட்டும்.
- **Conflicts-ஐ கண்ணை மூடிக்கிட்டு resolve பண்றது.** ரெண்டையும் படிக்காம "mine" அல்லது "theirs"-ஐ எடுத்தா, யாரோட fix-ஐயாவது சத்தமில்லாம undo பண்ணிடலாம். ரெண்டு பக்கத்தையும் படிங்க, அப்புறம் tests ஓட்டுங்க.
- **Conflict markers-ஐ commit பண்றது.** Commit பண்றதுக்கு முன்னாடி `<<<<<<<`-ஐ search பண்ணுங்க. நிறைய teams இதுக்கு CI-ல ஒரு check சேர்க்கும்.

## Practice பண்ணுங்க

1. ஒரு file இருக்குற practice repository உருவாக்குங்க. ரெண்டு branches-ல line 3-ஐ மாத்துங்க, ஒண்ணை main-ல merge பண்ணுங்க, அப்புறம் மத்ததை merge பண்ணி conflict-ஐ resolve பண்ணுங்க.
2. மூணு சின்ன commits இருக்குற ஒரு branch உருவாக்குங்க. அது இருக்கும்போதே main-ல ஒரு commit சேர்ங்க. உங்க branch-ஐ main மேல rebase பண்ணி, முன்னாடியும் பின்னாடியும் `git log --oneline --graph --all`-ஐ பாருங்க.
3. ஒரு rebase நடுவுல `git rebase --abort` முயற்சி பண்ணி, எல்லாம் முன்னாடி இருந்த மாதிரியே திரும்பிடுச்சான்னு confirm பண்ணுங்க.
4. Interview-ல சொல்ற மாதிரி, எப்போ merge பண்ணுவீங்க, எப்போ rebase பண்ணுவீங்கன்னு ஒரு நிமிஷத்துக்குள்ள சத்தமா explain பண்ணுங்க.
