## இது என்ன

ஒரு language model எவ்வளவு பெருசு, அதுல எவ்வளவு போட்டிருக்குன்னு மூணு எண்கள் சொல்லும்.

1. **Parameters**: model-குள்ள training மாத்துற எண்கள். "Llama 3 8B"-ல கிட்டத்தட்ட 8 billion இருக்கு. அதிக parameters ஒரு model-க்கு கத்துக்க அதிக capacity தரும், run பண்ண அதிக memory, compute வேணும்.
2. **Training tokens**: அது எவ்வளவு text-ல இருந்து கத்துக்கிச்சு. Meta-வோட Llama models 1.4 trillion tokens (Llama 1)-ல இருந்து 2 trillion (Llama 2), கிட்டத்தட்ட 15 trillion (Llama 3) வரை போனுச்சு.
3. **Training compute**: training எத்தனை arithmetic operations எடுத்துச்சு, FLOPs (floating-point operations)-ல அளக்கப்படும். ஒரு பொதுவான estimate **6 × parameters × training tokens**.

ஒரு **scaling law**, இவை வளர வளர quality எப்படி மேம்படுதுன்னு experiments-ல இருந்து விவரிக்கும். அதிர்ச்சியான கண்டுபிடிப்பு என்னன்னா, முன்னேற்றம் சீரா, கணிக்கக்கூடிய விதத்துல இருக்கும்; அதனால labs சின்ன models-ஐ train பண்ணி, ஒரு curve-ஐ fit பண்ணி, பணம் செலவழிக்கறதுக்கு முன்னாடியே ஒரு ரொம்ப பெரிய model எப்படி செய்யும்னு forecast பண்ணலாம்.

## இது எப்படி work ஆகுது

**Size, memory.** ஒரு model-ஐ run பண்ண, அதோட weights GPU memory-ல பொருந்தணும்: parameters × ஒரு parameter-க்கு bytes. 16-bit precision-ல (2 bytes), ஒரு 7B model-க்கு கிட்டத்தட்ட 14 GB, ஒரு 70B model-க்கு கிட்டத்தட்ட 140 GB, KV cache, மத்த overhead-க்கு முன்னாடி. 8 அல்லது 4 bits-க்கு Quantisation இதை சுருக்கும், GPU lesson விளக்குற மாதிரி.

**Dense, sparse.** Dense model-ல ஒவ்வொரு token-க்கும் ஒவ்வொரு parameter-உம் use ஆகும். **Mixture-of-experts** (MoE) model layers-ஐ "experts"-ஆ பிரிக்கும், ஒரு சின்ன router ஒவ்வொரு token-க்கும் சிலதை தேர்ந்தெடுக்கும். Mixtral 8x7B-ல மொத்தம் 46.7 billion parameters இருக்கு, ஆனா ஒவ்வொரு token-க்கும் கிட்டத்தட்ட 12.9 billion மட்டும் active; அதனால இது கிட்டத்தட்ட ஒரு 13B model-ஓட cost, வேகத்துல run ஆகுது, ஆனா அதிக knowledge-ஐ வச்சிருக்கு. எல்லா experts-ஐயும் வைக்க memory இன்னும் வேணும்.

**Chinchilla rule.** 2022-ல, DeepMind வெவ்வேற அளவு data-ல வெவ்வேற sizes-ஓட 400-க்கும் மேற்பட்ட models-ஐ train பண்ணி கேட்டுச்சு: ஒரு fixed compute budget-க்கு, size-உம் data-வும் எந்த கலவையில சிறந்த model-ஐ தரும்? பதில்: கிட்டத்தட்ட **ஒரு parameter-க்கு 20 training tokens**, ரெண்டையும் சேர்த்து வளர்க்கறது. முந்தைய நிறைய பெரிய models undertrained: GPT-3-ல 175 billion parameters இருந்துச்சு, ஆனா 300 billion training tokens தான், ஒரு parameter-க்கு 2-க்கும் கம்மி. DeepMind-ஓட 70-billion-parameter Chinchilla, 1.4 trillion tokens-ல train ஆகி, ரொம்ப பெரிய models-ஐ தோற்கடிச்சுது.

**Chinchilla-வுக்கு அப்பால.** இந்த rule *training*-ஓட cost-ஐ optimise பண்ணும். ஆனா ஒரு பிரபலமான model million தடவை *use* ஆகும், ஒரு சின்ன model run பண்ண மலிவு. அதனால labs இப்போ சின்ன models-ஐ ஒரு parameter-க்கு 20 tokens-ஐ ரொம்ப தாண்டி train பண்றாங்க: Llama 3 8B கிட்டத்தட்ட 15 trillion tokens பார்த்துச்சு, ஒரு parameter-க்கு கிட்டத்தட்ட 1,900. Training அதிக cost ஆகும், ஆனா ஒவ்வொரு user-ஓட request-உம் குறைவா cost ஆகும், அதிக data-வோட quality தொடர்ந்து மேம்படும்.

**Diminishing returns.** Quality ஒரு power law-வை follow பண்ணும், அதனால ஒவ்வொரு படிக்கும் முந்தையதை விட அதிகம் செலவாகும். Language modelling-ல, training loss-ஐ கிட்டத்தட்ட 3.4-ல இருந்து 2.8-க்கு குறைக்க கிட்டத்தட்ட பத்து மடங்கு அதிக data வேணும். ஒரு task-ல 90%-ல இருந்து 95%-க்கு போக, 60%-ல இருந்து 90%-க்கு போறதை விட ரொம்ப அதிகம் செலவாகலாம்.

**Bottlenecks.** ரெண்டு வரம்புகள் மிரட்டுது: நல்ல public text தீர்ந்துக்கிட்டு வருது, ஏன்னா training sets புது எழுத்தை விட வேகமா வளருது; training runs-க்கு மிகப்பெரிய அளவு மின்சாரமும் வேணும். Synthetic data, சிறந்த data தேர்வு, திறமையான models மேல ஆர்வம் இருக்கறதுக்கு இதுவும் ஒரு காரணம்.

Planning-க்கு ஒரு quick calculator:

```python
def weights_gb(params_billion, bytes_per_param=2):
    return params_billion * bytes_per_param           # 1B params x 2 bytes = 2 GB

def training_gpu_hours(params, tokens, gpu_flops=312e12, utilisation=0.4):
    flops = 6 * params * tokens                       # common estimate
    return flops / (gpu_flops * utilisation) / 3600

print(weights_gb(8))                                  # 16 GB at 16-bit
print(round(training_gpu_hours(1e9, 20e9)))           # 1B model, 20B tokens: about 267 GPU-hours
print(round(training_gpu_hours(8e9, 15e12)))          # 8B model, 15T tokens: about 1.6 million GPU-hours
```

இங்க GPU வேகம் 16-bit precision-ல ஒரு high-end data-centre GPU-ஓட peak; உண்மையான utilisation பொதுவா 30%-ல இருந்து 50%.

## ஒரு worked example

Bengaluru-ல ஒரு startup Kannada-ல நல்லா எழுதுற ஒரு model-ஐ விரும்புது. ஒரு founder தங்களோட சொந்த Kannada text-ல scratch-ல இருந்து ஒரு 1-billion-parameter model-ஐ pre-train பண்ணலாம்னு சொல்றாரு.

அவங்க கணக்கு போடுறாங்க:

1. **தேவையான data.** 1B parameters-க்கு Chinchilla கிட்டத்தட்ட 20 billion tokens-ஐ பரிந்துரைக்கும். அவங்ககிட்ட கிட்டத்தட்ட 3 billion tokens நல்ல Kannada text இருக்கு, ஒரு வழக்கமான web crawl-ல Kannada வெறும் 0.01% தான்.
2. **Compute.** 6 × 1 billion × 20 billion = 1.2 × 10²⁰ operations, ஒரு high-end GPU-ல கிட்டத்தட்ட 270 மணி நேரம், இல்ல எட்டுல ஒண்ணரை நாள். தாங்கக்கூடியது.
3. **உண்மையான வரம்பு data.** 3 billion tokens-ஐ பல தடவை repeat பண்ணி train பண்றது புது data-வை விட குறைவா கத்துக்கொடுக்கும், ஒரு 1B model பொது knowledge எதுவுமே இல்லாம ஆரம்பிக்குது.

| Scratch-ல இருந்து pre-train பண்ண 1B model | 4.1 | அதிகம்: data வேலை + compute | ரொம்ப குறைவு |
| 8B open model, அப்படியே use பண்ணா | 6.2 | எதுவுமில்ல | குறைவு |
| 8B open model, அவங்க Kannada text-ல தொடர்ந்து training | 7.6 | மிதமானது | குறைவு |

எண்கள் புரிய வைக்குறதுக்கான உதாரணம். Compute ஒருபோதும் bottleneck இல்ல; data-வும் ஏற்கனவே இருக்குற model-ஓட முன்னிலையும் தான். அவங்க open model-ஓட தொடர்ந்த training-ஐ தேர்ந்தெடுக்குறாங்க.

## பொதுவா பண்ற தப்புகள்

- **தலைமுறைகளுக்கு இடையில parameter counts-ஐ ஒப்பிடுறது.** ஒரு புது 8B model ஒரு பழைய 70B-ஐ தோற்கடிக்கலாம்.
- **MoE models-க்கு மொத்த parameters-ஐ மட்டும் எண்ணுறது.** வேகமும் cost-உம் active parameters-ஐ follow பண்ணும்; memory மொத்தத்தை follow பண்ணும்.
- **Parameter counts-ல இருந்து GPUs-ஐ size பண்ணும்போது KV cache-ஐயும் overhead-ஐயும் மறக்குறது.**
- **ஒரு product model-க்கு Chinchilla-வையே இலக்கா எடுக்குறது.** அது training cost-ஐ optimise பண்ணும்; அதிகம் use ஆகுற models ரொம்ப அதிக நேரம் train ஆகும்.
- **Data quality-ஐ புறக்கணிக்கிறது.** அதே எண்ணிக்கை tokens-ல சிறந்த text ஒரு சிறந்த model-ஐ தரும்.
- **போதுமான data இல்லாம scratch-ல இருந்து pre-train பண்றது.** ஒரு open model-ல இருந்து ஆரம்பிக்கிறது பொதுவா ரொம்ப நல்லது.

## பெருசு எப்போ நல்லது இல்ல

- **Classification, extraction மாதிரி குறுகிய tasks** பெரும்பாலும் சின்ன models-லயே தரத்தை எட்டும்.
- **அதிக volume** ஒரு பெரிய model-ஓட running cost-ஐ ஆதிக்கம் செலுத்த வைக்கும்.
- **Latency budgets** ஒவ்வொரு token-ஐயும் வேகமா எழுதுற சின்ன models-ஐ விரும்பும்.
- **On-device அல்லது private deployments**-ல சின்ன models தான் பொருந்தலாம்.

## Demo-ல இருந்து production-க்கு

- **வேலை செய்யக்கூடிய மிகச் சின்ன model-ல இருந்து ஆரம்பிங்க**, உங்க test set சொன்னா மட்டும் மேல போங்க.
- **மொத்த parameters, precision, KV cache-ல இருந்து hardware-ஐ size பண்ணுங்க**, headroom-ஓட.
- **Model தேர்வுகளை அடிக்கடி மறுபரிசீலனை பண்ணுங்க.** புது சின்ன models இடைவெளியை தொடர்ந்து மூடுது.
- **எந்த training project-க்கும் compute-க்கு முன்னாடி data-வை plan பண்ணுங்க**, உங்ககிட்ட உண்மையில எவ்வளவு பயனுள்ள data இருக்குன்னு அளங்க.

## Practice பண்ணுங்க

2. Calculator-ஐ use பண்ணி, Chinchilla புள்ளியில ஒரு 3B model-க்கு training compute-ஐ estimate பண்ணுங்க. எத்தனை GPU-hours?
3. நீங்க அக்கறை காட்டுற ஒரு benchmark-ல, ஒரு பழைய பெரிய model-ஐ தோற்கடிக்கற, சமீபத்திய ஒரு சின்ன model-ஐ கண்டுபிடிங்க.
