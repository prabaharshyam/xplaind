## இது என்ன

ஒரு LLM app-ஐ deploy பண்றதுன்னா, அதை online-ல, உண்மையான users நம்பிக்கையா அணுகுற இடத்துல வைக்கிறது. Monitoring-னா, அங்க போனதுக்கு அப்புறம் அது எப்படி நடந்துக்குதுன்னு கவனிக்கிறது. LLM apps-க்கு, monitoring நாலு வகை signals-ஐ கவர் பண்ணும்:

- **Errors**: fail ஆன requests, provider errors, timeouts.
- **Latency**: users எவ்வளவு நேரம் காத்திருக்காங்க, குறிப்பா time to first token.
- **Cost**: ஒரு request, ஒரு user, ஒரு நாளுக்கு tokens-உம் பணமும்.
- **Quality**: user feedback, automatic checks, sampled review மூலமா பதில்கள் இன்னும் நல்லா இருக்கான்னு.

```flow
Users -[HTTPS]-> ஒரு managed service-ல Container, இந்திய region | secret settings-ல இருந்து key, ஒரு /health endpoint
ஒரு managed service-ல Container, இந்திய region -> Model API
ஒரு managed service-ல Container, இந்திய region -> ஒவ்வொரு request-உம் log ஆகுது | id, user, latency, tokens, cost, model, prompt version, rating
ஒவ்வொரு request-உம் log ஆகுது -> தினசரி dashboard | requests, error rate, p95 latency, ஒரு நாளைக்கு cost, thumbs-up rate
தினசரி dashboard -> Alerts | errors 2%-க்கு மேல, ஒரு நாளைக்கு cost ₹150-க்கு மேல, app down
தினசரி dashboard -[வாராவாரம்]-> 20 உண்மையான conversations-ஐ படிங்க -> Fix -> Test env + evals -> சின்ன release -> எல்லா users
```

இந்த lesson, Coimbatore-ல final-year student-ஆ இருக்குற Arjun-ஐ பின்தொடருது; அவரு தன் college-ஓட regulations மேல ஒரு RAG app-ஐ classmates-க்காக deploy பண்றாரு.

## இது எப்படி work ஆகுது

**எளிமையா deploy பண்ணுங்க.** முதல் app-க்கு, ஒரு managed platform போதும்: ஒரு serverless service-ல ஒரு container (Cloud Run, Azure Container Apps, Amazon ECS Express Mode மாதிரி), அல்லது Vercel, Render, Railway மாதிரி ஒரு platform-ல ஒரு web app. API key-ஐ platform-ஓட secret settings-ல வைங்க, environment variables set பண்ணுங்க, ஒரு health-check endpoint சேருங்க, HTTPS-ஐ enable பண்ணுங்க (பொதுவா automatic).

**ஒவ்வொரு request-ஐயும் log பண்ணுங்க**: request id, user (அல்லது ஒரு pseudonymous id), latency, tokens, cost, model, prompt version, errors ஆகியவற்றோட. ஒரு tracing tool அல்லது structured logs use பண்ணுங்க.

**Dashboards.** ஒரு நாளைக்கு requests, error rate, p95 latency, ஒரு நாளைக்கு cost, feedback rate இருக்குற ஒரு சின்ன dashboard. ஆரம்பத்துல தினமும் பாருங்க.

**Alerts.** ஒரு threshold-ஐ தாண்டுற error rate; ஒரு daily budget-ஐ தாண்டுற cost; latency spikes; app down ஆகுறது. யாராவது பார்க்குற இடத்துக்கு அனுப்புங்க.

**Quality signals.**

- *User feedback*: thumbs up அல்லது down, ஒரு optional காரணத்தோட.
- *Automatic checks*: format validity, refusals, citations இருக்கா, guardrail triggers.
- *Sampled review*: வாரத்துக்கு 20 உண்மையான conversations-ஐ படிங்க.
- *Online evals*: live பதில்களோட ஒரு sample-ஐ ஒரு judge score பண்றது.

எந்த error-உம் இல்லாமலே quality குறையலாம்: ஒரு provider ஒரு model-ஐ update பண்றாங்க, documents மாறுது, users புது வகை கேள்விகள் கேக்க ஆரம்பிக்கிறாங்க.

**Latency-க்கு ரெண்டு பகுதிகள் இருக்கு.** Stream ஆகுற ஒரு reply-க்கு, users **time to first token** (TTFT)-ஐயும் அப்புறம் **time per output token** (TPOT)-ஐயும் உணர்றாங்க. மொத்த நேரம் தோராயமா TTFT + TPOT × output tokens: 1.2 வினாடி TTFT-உம் ஒரு token-க்கு 30 ms-உம் 300 tokens-க்கு மொத்தம் சுமார் 10 வினாடி, ஆனா user 1.2-க்கு அப்புறமே படிக்க ஆரம்பிச்சுடுறாங்க. மக்கள் ஒரு token-க்கு ரொம்ப தோராயமா 100-ல இருந்து 150 ms-ல படிக்கிறாங்க, அதனால அதை விட வேகமான streaming கிட்டத்தட்ட தெரியாது, ஆனா மெதுவான முதல் token எப்பவும் தெரியும். **Percentiles** (p50, p95)-ஐ report பண்ணுங்க, வெறும் average-ஐ ஒருபோதும் இல்ல: 100 ms-ல ஒன்பது replies-உம் 3,000 ms-ல ஒண்ணும் சராசரி 390 ms; அது யாரையும் விவரிக்கல.

**Metrics, logs, traces.** Metrics, 3:05-க்கு ஏதோ தப்பா போச்சுன்னு சொல்ற மொத்தங்கள். Logs, 3:05-க்கு என்ன நடந்துச்சுன்னு சொல்ற தனித்தனி events. ஒரு **trace**, ஒரு request-ஓட ஒவ்வொரு step-ஐயும் (retrieval, prompt, model call, tool calls, இறுதி பதில்) ஒவ்வொண்ணோட நேரம், cost-ஓட இணைக்கும்; அதனால எந்த step fail ஆச்சுன்னு பார்க்கலாம். Langfuse, LangSmith, Arize Phoenix அல்லது வெறும் OpenTelemetry மாதிரி tools இவற்றை சேகரிக்கும்.

**மக்களோட நடத்தையில இருந்து வர்ற signals.** Users அரிதா தான் thumbs down அழுத்துவாங்க, ஆனா அவங்க நடத்தை பேசும்: ஒரு reply-ஐ பாதியிலயே நிறுத்துறது, regenerate அழுத்துறது, அதே கேள்வியை மாத்தி கேக்குறது, ரெண்டு turns-ல முடிய வேண்டிய ஒரு task-க்கு நீளமான conversations. இவற்றை explicit ratings-ஓட சேர்த்து track பண்ணுங்க.

**மூணு வகை drift.** உங்க code-ல எந்த மாற்றமும் இல்லாமலே quality மாறலாம்:

- **உங்க சொந்த மாற்றங்கள்**: ஒரு prompt edit, ஒரு புது document set, வேற chunk size.
- **உங்க users மாறுறாங்க**: புது வகை கேள்விகள், ஒரு புது language, exam results அறிவிச்சதுக்கு அப்புறம் நீளமான inputs.
- **Model மாறுது**: ஒரு provider அதே பேருக்கு பின்னாடி ஒரு model-ஐ update அல்லது retire பண்றாங்க. கிடைக்குற இடத்துல தேதியோட model versions-ஐ pin பண்ணுங்க, மாறுறதுக்கு முன்னாடி evals-ஐ திரும்ப run பண்ணுங்க.

**உங்க monitoring எவ்வளவு நல்லது?** Software operations-ல இருந்து மூணு numbers: ஒரு பிரச்சனையை **கண்டுபிடிக்க ஆகுற நேரம்**, அதை **தீர்க்க ஆகுற நேரம்**, **change failure rate**, அதாவது ஒரு fix அல்லது rollback தேவைப்படுற releases-ஓட பங்கு. அதிக change failure rate-ன்னா, release-க்கு முன்னாடி உங்க evals இன்னும் அதிகமா பிடிக்கணும்னு அர்த்தம்.

**ஒரு சின்ன logging wrapper.** ஒரு tool வாங்குறதுக்கு முன்னாடி, சில வரிகளே பெரும்பாலான பலனை தரும். இது ஒரு reply-ஐ stream பண்ணி, TTFT-ஐயும் மொத்த நேரத்தையும் அளந்து, ஒரு request-க்கு ஒரு JSON line எழுதுது:

```python
import json, time, uuid
import anthropic

client = anthropic.Anthropic()
PRICES = {"input": 3 / 1e6, "output": 15 / 1e6}       # USD per token; check current prices
USD_TO_INR = 84
VERSION = "rag-v14"                                    # prompt and code version

def answer(user_id, question, system, messages):
    start, first, rid = time.monotonic(), None, str(uuid.uuid4())
    record = {"id": rid, "user": user_id, "version": VERSION, "model": "claude-sonnet-5-5"}
    try:
        with client.messages.stream(model=record["model"], max_tokens=600,
                                    system=system, messages=messages) as stream:
            parts = []
            for text in stream.text_stream:
                first = first or time.monotonic()
                parts.append(text)
            final = stream.get_final_message()
        u = final.usage
        record |= {"ok": True, "stop": final.stop_reason,
                   "in": u.input_tokens, "out": u.output_tokens,
                   "cost_inr": round((u.input_tokens * PRICES["input"] + u.output_tokens * PRICES["output"]) * USD_TO_INR, 3)}
        return "".join(parts), rid
    except anthropic.APIError as err:
        record |= {"ok": False, "error": type(err).__name__}
        raise
    finally:
        now = time.monotonic()
        record |= {"ttft_ms": round(((first or now) - start) * 1000), "total_ms": round((now - start) * 1000)}
        with open("requests.jsonl", "a") as f:
            f.write(json.dumps(record) + "\n")
```

கேள்வி, பதில் text வேணும்னே விடப்பட்டிருக்கு; கீழ இருக்குற privacy note-ஐ பாருங்க. ஒரு தினசரி job அந்த file-ஐ படிச்சு thresholds-ஐ check பண்ணும்:

```python
import json, statistics

def daily_report(path="requests.jsonl", cost_limit_inr=150, error_limit=0.02):
    rows = [json.loads(line) for line in open(path)]
    ok = [r for r in rows if r["ok"]]
    p95 = statistics.quantiles([r["total_ms"] for r in ok], n=20)[-1]
    errors = 1 - len(ok) / len(rows)
    cost = sum(r["cost_inr"] for r in ok)
    alerts = [msg for bad, msg in [
        (errors > error_limit, f"error rate {errors:.1%}"),
        (cost > cost_limit_inr, f"cost ₹{cost:.0f}"),
        (any(r["stop"] == "max_tokens" for r in ok), "some replies were cut off"),
    ] if bad]
    return {"requests": len(rows), "p95_ms": round(p95), "errors": f"{errors:.1%}",
            "cost_inr": round(cost), "alerts": alerts}
```

**Logs-ல privacy.** முழு prompts-உம் replies-உம் debugging-ஐ ரொம்ப எளிதாக்கும், ஆனா அவை தனிப்பட்ட data. இந்தியாவோட Digital Personal Data Protection Act-ல, நீங்க என்ன வச்சிருக்கீங்க, ஏன்னு உங்க privacy notice-ல சொல்லுங்க, தேவையான வரை மட்டும் வச்சிருங்க, phone numbers, email addresses, ID numbers-ஐ mask பண்ணுங்க, logs-ஐ யார் படிக்கலாம்னு limit பண்ணுங்க. பல teams ஒவ்வொரு request-க்கும் metadata-வையும், சின்ன, சம்மதம் வாங்கின, mask பண்ணப்பட்ட ஒரு sample-க்கு மட்டும் முழு text-ஐயும் log பண்றாங்க.

**பாதுகாப்பா release பண்ணுங்க.** Changes-ஐ முதல்ல ஒரு test environment-க்கு deploy பண்ணுங்க, உங்க evals-ஐ run பண்ணுங்க, அப்புறம் release பண்ணுங்க; எல்லாருக்கும் போறதுக்கு முன்னாடி users-ல ஒரு சின்ன பங்குக்கு போனா நல்லது. முந்தைய version-ஐ roll back-க்கு ready-யா வச்சிருங்க.

**Signals-உம் அவை சொல்றதும்:**

| Signal | Threshold உதாரணம் | Breach என்ன சொல்லுது |
| --- | --- | --- |
| Error rate | 10 நிமிஷத்துக்கு 2%-க்கு மேல | Provider outage, bug, மோசமான deploy |
| p95 latency | 8 வினாடிக்கு மேல | மெதுவான retrieval, நீளமான outputs, provider மெதுவா இருக்குறது |
| ஒரு நாளைக்கு cost | ₹150-க்கு மேல | ஒரு heavy user, ஒரு script, ஒரு loop |
| Thumbs-down rate | ஒரு வாரத்துல ரெண்டு மடங்கு | விடுபட்ட documents, ஒரு prompt மாற்றம், புது கேள்விகள் |
| Refusal rate | ஒரு topic-க்கு திடீர்னு ஏறுது | Documents index ஆகல |

**இருபது நிமிஷத்துல ஒரு வாராந்திர review.** Dashboard-ஐ திறந்து போன வாரத்தோட ஒப்பிடுங்க. மிகச் சமீபத்திய பத்து thumbs-down conversations-ஐயும் பத்து random-ஆனவற்றையும் படிங்க. ஏதாவது தப்பு இருந்தா, ஒவ்வொரு conversation-க்கும் என்ன தப்புன்னு ஒரு வரி எழுதுங்க. மிகப் பொதுவான காரணத்தை தேர்ந்தெடுத்து fix பண்ணுங்க. இந்த சின்ன பழக்கம், யாராவது சத்தமா குறை சொல்றதுக்கு வாரங்கள் முன்னாடியே பெரும்பாலான quality பிரச்சனைகளை பிடிச்சுடும்.

**Roll back பண்றது.** முந்தைய container image-ஐ tag பண்ணி ready-யா வச்சிருங்க. ஒரு rollback, platform-ல ஒரு command அல்லது ஒரு click-ஆ இருக்கணும், launch-க்கு முன்னாடி ஒரு தடவை test பண்ணப்பட்டிருக்கணும். ஒவ்வொரு log line-லயும் version-ஐ பதிவு பண்ணுங்க; அப்போ rollback-க்கு அப்புறம் பழைய version தான் traffic-ஐ serve பண்ணுதுன்னு உறுதி பண்ணலாம்.

**Region தேர்ந்தெடுக்குறது.** உங்க users-க்கு மிக நெருக்கமான, எந்த data rules-ம் அனுமதிக்கிற hosting region-ஐ தேர்ந்தெடுங்க, உதாரணமா இந்திய users-ஓட தனிப்பட்ட data-க்கு ஒரு இந்திய region. Model provider அல்லது அதோட cloud partner-உம் பக்கத்துல ஒரு endpoint தர்றாங்களான்னு check பண்ணுங்க, ஏன்னா ஒவ்வொரு model call-உம் கண்டங்களை கடக்குறதா இருந்தா, ஒரு வேகமான app server-ஆல பெரிசா பலன் இல்ல. Region தேர்வை உங்க README-ல எழுதுங்க; அது திட்டமிட்டு எடுத்ததுன்னு reviewers பார்க்கலாம்.

## பொதுவா பண்ற தப்புகள்

- **Cost-ஐயும் tokens-ஐயும் log பண்ணாம இருக்குறது.**
- **Errors-ஐ மட்டும் watch பண்றது.** Errors இல்லாமலே quality குறையும்.
- **Alerts இல்லாம இருக்குறது.** பிரச்சனைகளை users கண்டுபிடிக்கிறாங்க.
- **Code-லயோ image-லயோ secrets.** Platform-ஓட secrets-ஐ use பண்ணுங்க.
- **Rollback இல்லாத big-bang releases.**
- **Percentiles-க்கு பதிலா averages.** ஒரு மெதுவான request ஒரு average-ல ஒளிஞ்சுக்கும்; p95 அதை காட்டும்.
- **Version இல்லாத logs.** ஒவ்வொரு line-லயும் model, prompt version இல்லன்னா, எந்த release ஒரு மாற்றத்தை உண்டாக்கிச்சுன்னு சொல்ல முடியாது.
- **எல்லாத்தையும் எப்பவும் log பண்றது.** Logs-ல இருக்குற தனிப்பட்ட data-க்கு masking, retention limit, கட்டுப்படுத்தப்பட்ட access தேவை.

## எளிமையே போதுமான இடங்கள்

- **ஒரு தனிப்பட்ட tool அல்லது ஒரு நாள் demo**: token usage-ஐயும் errors-ஐயும் console-ல print பண்ணுங்க.
- **ஒரு சில users இருக்குற ஒரு சின்ன internal pilot**: ஒரு log file, மேல இருக்குற daily report, conversations-ஐ வாராந்திரமா படிக்குறது.
- **ஒரு hosted no-code assistant**, அங்க platform-ஓட சொந்த usage page cost-ஐயும் errors-ஐயும் கவர் பண்ணும்.

உண்மையான users app-ஐ நம்பியிருக்கும்போது அல்லது pipeline-ல பல steps இருக்கும்போது tracing tools, online evals, staged releases-ஐ சேருங்க.

## Demo-ல இருந்து production-க்கு

- **எந்த failures-ஐ முதல்ல பிடிக்கணும்னு முடிவு பண்ணுங்க**, அப்புறம் அவற்றுக்கான metrics-ஐ தேர்ந்தெடுங்க: தப்பான format, விடுபட்ட பதில்கள், மெதுவான replies, கட்டுப்பாடில்லாத cost.
- **ஒவ்வொரு metric-ஐயும் பிரிச்சு பாருங்க**: version, model, feature, நாள் வாரியா; அப்போ ஒரு மாற்றத்தை அதோட காரணத்துக்கு கண்டுபிடிக்கலாம்.
- **Model versions-ஐ pin பண்ணுங்க**, மாறுறதுக்கு முன்னாடி evals-ஐ திரும்ப run பண்ணுங்க.
- **ஒரு பக்க runbook எழுதுங்க**: alerts யாருக்கு போகுது, எப்படி roll back பண்றது, ஒரு backup model-க்கு எப்படி மாறுறது.
- **நீங்க கண்டுபிடிக்கிறதை evals-க்கே திருப்பி குடுங்க**: ஒவ்வொரு உண்மையான failure-உம் ஒரு test case ஆகும்.
