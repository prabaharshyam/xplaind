## இது என்ன

**Trace**-னா ஒரு request-ஓட ஆரம்பத்துல இருந்து முடிவு வரைக்கும் உள்ள record. அது **spans**-ஆல ஆனது, ஒவ்வொரு step-க்கும் ஒண்ணு: query rewrite, retrieval, reranker, ஒவ்வொரு model call, ஒவ்வொரு tool call. ஒவ்வொரு span-உம் அதோட inputs, outputs, start-உம் end-உம் நேரம் இதை store பண்ணும்; model calls-ன்னா model பேரு, token counts, cost-உம். Spans nest ஆகும், அதனால agent-ஓட மூணாவது tool call ரெண்டாவது model turn-க்குள்ள நடந்துச்சுன்னு பார்க்கலாம்.

சாதாரண application logs ஏதோ நடந்துச்சுன்னு மட்டும் சொல்லும். AI system-ஓட traces அது ஏன் அப்படி பதில் சொல்லுச்சுன்னு சொல்லும். Langfuse, Arize Phoenix மாதிரி open-source tools, commercial tools, cloud providers-ஓட சொந்த tools எல்லாமே traces-ஐ store பண்ணி காட்டும். நிறைய tools OpenTelemetry மேல build ஆகியிருக்கு; இது traces-க்கான பொதுவான standard.

```flow
title: Trace 8f3a, ஒரு citizen கேள்வி: 3.8 s, ₹0.42
Trace 8f3a | tags: user anon-5521, session s-901, app 2.4.0, prompt v17 -> rewrite_query, 0.4 s | in: கேள்வி, out: search text
rewrite_query, 0.4 s -> hybrid_search, 0.3 s | out: doc ids, scores
hybrid_search, 0.3 s -> rerank, 0.2 s | out: மறுபடி ஒழுங்கு பண்ண ids
rerank, 0.2 s -> generate, 2.9 s | model, tokens in-உம் out-உம், cost, output text
```

இந்த lesson-ல Bhubaneswar-ல ஒரு state-government helpdesk assistant ஒரு விவசாயிக்கு scheme தொகையை தப்பா சொன்ன கதையை follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

**Instrument பண்றது.** பெரும்பாலான tools model client-க்கு ஒரு decorator அல்லது wrapper தரும். Decorate பண்ண ஒவ்வொரு function-உம் ஒரு span ஆகும், model calls tokens, cost-ஐ தானா record பண்ணும். அப்புறம் உதவுற attributes-ஐ சேருங்க: user id (அல்லது pseudonymous id), session id, app version, prompt version, retrieve ஆன document ids அவங்க scores-ஓட.

**Group பண்றது.** ஒரு **session** ஒரு conversation-ஓட traces-ஐ group பண்ணும்; user ids வச்சு ஒரு user அனுபவிச்ச எல்லாத்தையும் பார்க்கலாம்.

**Data-வை கவனிங்க.** Traces-ல prompts, outputs இருக்கும்; அதுல personal data இருக்கலாம். Sensitive fields-ஐ அனுப்புறதுக்கு முன்னாடி mask பண்ணுங்க அல்லது விட்டுடுங்க, retention period வைங்க, யார் traces பார்க்கலாம்னு restrict பண்ணுங்க, client கேட்டா self-hosted அல்லது in-region tool-ஐ prefer பண்ணுங்க.

**Use பண்றது.**

- *Debug*: ஒரு மோசமான பதிலோட trace-ஐ திறங்க. சரியான passage retrieve ஆச்சா? அது prompt-ல இருந்துச்சா? Model அதை ignore பண்ணுச்சா?
- *Measure*: step வாரியா latency, ஒரு request-க்கு tokens-உம் cost-உம், model வாரியா error rates.
- *Improve*: interesting traces-ஐ ஒரு dataset-ல save பண்ணுங்க; அவை eval cases ஆகும்.

**Sampling.** High volume-ல errors அல்லது குறைவான feedback இருக்குற எல்லா traces-ஐயும் வச்சுக்கோங்க, மத்ததுல ஒரு sample.

**ஒவ்வொரு tool வகையும் என்ன தரும்:**

| Option | Strengths | எப்போ யோசிக்கணும் |
| --- | --- | --- |
| Open-source, self-hosted (Langfuse, Phoenix) | Data உங்ககிட்டயே இருக்கும்; run பண்ண free | Client-க்கு in-region அல்லது on-premises data வேணும்னா |
| Commercial hosted tools | Operate பண்ண குறைவு; extra analysis features | Speed முக்கியம், data rules அனுமதிச்சா |
| Cloud provider-ஓட tracing | இருக்குற cloud stack-ஓட சரியா பொருந்தும் | App ஏற்கனவே அந்த cloud-ல run ஆகுதுன்னா |
| Plain OpenTelemetry, உங்க சொந்த store-ஓட | முழு control, standard format | ஏற்கனவே observability tooling run பண்றீங்கன்னா |

**வாரா வாரம் ஒரு trace review.** வாரத்துக்கு முப்பது நிமிஷம் ஒதுக்குங்க. மோசமான user feedback, errors, வழக்கத்துக்கு மேல அதிக cost இருக்குற traces-ஐயும், சாதாரண ones-ல ஒரு random sample-ஐயும் எடுங்க. ஒவ்வொரு மோசமான பதிலுக்கும் எந்த step fail ஆச்சுன்னு note பண்ணுங்க: query rewrite, retrieval, reranking, prompt அல்லது model. Notes-ஐ எண்ணுங்க. சில வாரம் ஆனதும், engineering effort எங்க பலன் தரும்னு அந்த எண்ணிக்கை காட்டும்; save பண்ண traces உண்மையான use-ல இருந்து வந்த eval cases-ஆ வளரும்.

**Step வாரியா cost, latency.** ஒவ்வொரு span-உம் நேரத்தையும் tokens-ஐயும் record பண்றதால, step வாரியா totals-ஐ chart பண்றது ஈஸி. Teams-க்கு அடிக்கடி ஆச்சரியம் வரும்: ஒரு பெரிய model-ல run ஆகுற query-rewrite call, பதிலை விட அதிக cost ஆகலாம்; அல்லது ஒரு reranker, model-ஐ விட அதிக delay சேர்க்கலாம்.

**Plain OpenTelemetry-ஓட tracing.** பெரும்பாலான LLM tracing tools (Langfuse, Arize Phoenix, இன்னும் சில) OpenTelemetry data-வை ஏத்துக்கும்; அதனால standard-ஐ வச்சு instrument பண்ணா, அப்புறம் எப்போ வேணும்னாலும் மாறிக்கலாம்:

```python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))   # endpoint and auth from env vars
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("policy-rag")

def answer(question, user_id, session_id):
    with tracer.start_as_current_span("answer") as root:
        root.set_attributes({"app.release": "assistant-2026.11.3", "user.id": user_id, "session.id": session_id})
        with tracer.start_as_current_span("retrieve") as span:
            hits = search(question)
            span.set_attributes({"retrieval.ids": [h["id"] for h in hits],
                                 "retrieval.top_score": hits[0]["score"] if hits else 0})
        with tracer.start_as_current_span("generate") as span:
            reply = call_model(question, hits)
            span.set_attributes({"gen_ai.request.model": reply.model,
                                 "gen_ai.usage.input_tokens": reply.usage.input_tokens,
                                 "gen_ai.usage.output_tokens": reply.usage.output_tokens})
        return reply
```

`gen_ai.*` பேர்கள் generative AI-க்கான OpenTelemetry conventions-ஐ follow பண்ணும்; tracing tools அதை புரிஞ்சுக்கும். `OTEL_EXPORTER_OTLP_ENDPOINT`-ஐ உங்க tool-ஓட point பண்ணுங்க; client கேட்டா, இந்திய region-ல self-host பண்ணுங்க.

**Export-க்கு முன்னாடி mask பண்ணுங்க.** Span attributes அல்லது events-ல போறதுக்கு முன்னாடி, உங்க code-லயே personal data-வை நீக்கிடுங்க. நீங்க attach பண்ற ஒவ்வொரு prompt-க்கும் answer-க்கும், security lessons-ல வந்த masking patterns-ஐ வச்சு ஒரு சின்ன helper போட்டா, ஆரம்பிக்க அது போதும்; அது சரியா work ஆகுதான்னு store ஆன traces-ல ஒரு sample-ஐ review பண்ணுங்க.

**முக்கியமான traces-ஐ வச்சுக்கோங்க.** எல்லாத்தையும் 10% sample பண்ணா, உங்களுக்கு தேவையான அரிதான failures-ல பெரும்பாலானது போயிடும். ரெண்டு பொதுவான வழிகள்:

- **Head sampling, exceptions-ஓட**: error ஆகுற, thumbs down வாங்குற, latency threshold-ஐ தாண்டுற requests-ஓட traces-ஐ எப்பவும் வச்சுக்கோங்க (உங்க exporter அல்லது collector check பண்ற ஒரு attribute-ஆல mark பண்ணுங்க), மத்ததை sample பண்ணுங்க.
- **OpenTelemetry Collector-ல tail sampling**: collector ஒவ்வொரு trace-உம் முடியுற வரை காத்திருந்து, errors அல்லது slow spans இருக்குற எல்லாத்தையும், மத்ததுல ஒரு percentage-ஐயும் வச்சுக்கும்.

**Traces-ல இருந்து step வாரியா cost, latency.** Spans-ஐ பேர் வாரியா group பண்ணி, ஒரு நாளுக்கு நேரம், tokens-ஐ கூட்டுங்க. "step வாரியா மொத்த cost-ல பங்கு" chart பெரும்பாலும் ஒரு ஈஸியான win-ஐ காட்டும்: உதாரணம், பெரிய model-ல run ஆகுற rewrite step, அல்லது ஒரு oversized filter-னால slow ஆகுற retrieval.

**Trace-ல இருந்து test case-க்கு.** ஒரு trace id-ஐ எடுத்து, அதோட கேள்வி, retrieve ஆன ids, expected answer-ஐ eval set-ல எழுதுற ஒரு button அல்லது command சேருங்க. இது எவ்வளவு ஈஸியோ, அவ்வளவு வேகமா eval set நிஜ failures-ஓட வளரும்.

**Browser-லயே try பண்ணுங்க.** ஒரு சின்ன tracer: ஒவ்வொரு step-உம் தன் நேரத்தை record பண்ணும், அதனால slow ஆனது தனியா தெரியும்.

```python
import time, random
from contextlib import contextmanager

spans = []
@contextmanager
def span(name):
    t0 = time.perf_counter()
    yield
    spans.append((name, (time.perf_counter() - t0) * 1000))

random.seed(2)
with span("answer"):
    with span("rewrite"): time.sleep(0.02)
    with span("retrieve"): time.sleep(random.uniform(0.05, 0.2))
    with span("generate"): time.sleep(0.1)
for name, ms in sorted(spans, key=lambda s: -s[1]):
    print(f"{name:<9} {ms:6.0f} ms")
```

## ஒரு example

Bhubaneswar-ல ஒரு state-government helpdesk assistant, scheme-கள் பத்தின citizens-ஓட கேள்விகளுக்கு பதில் சொல்லுது. ஒரு official report பண்றாங்க: "மாநிலத்தோட crop-support scheme-ல instalment ₹4,000ன்னு ஒரு விவசாயிகிட்ட சொல்லிடுச்சு. உண்மையில ₹2,000." (இங்க வர்ற scheme-உம் தொகைகளும் example-க்காக கற்பனையா எடுத்தது.)

அந்த session-க்கு traces-ஐ search பண்ணி, சம்பந்தப்பட்ட trace-ஐ திறக்குறீங்க:

```text
trace 8f3a  user=anon-5521  app=2.4.0  prompt=v17   3.8 s  ₹0.42
  rewrite_query        0.4 s   "crop-support scheme instalment amount"
  hybrid_search        0.3 s   top: doc 112 (0.71), doc 87 (0.69), doc 113 (0.66)
  rerank               0.2 s   top: doc 87, doc 112, doc 113
  generate             2.9 s   in 3,210 tok / out 182 tok
```

Doc 87 2019-ஓட ஒரு note, scheme-ஓட பழைய version பத்தினது, வேற தொகையோட. Reranking-க்கு அப்புறம் அது தான் முதல்ல வந்துச்சு, இப்போதைய scheme guideline-க்கு மேல. Model அதை அப்படியே quote பண்ணுச்சு. Bug model-ல இல்லை; effective date இல்லாத ஒரு stale document தான் காரணம்.

நீங்க `effective_from` metadata-வையும் ஒரு filter-ஐயும் சேர்த்து, அந்த trace-ஓட query-ஐ ஒரு test-ல மறுபடி run பண்ணி, இந்த trace-ஐ golden set-ல save பண்றீங்க; இனிமே இந்த case test ஆகும். ஒவ்வொரு step-உம் record ஆகியிருந்ததால, முழு investigation-உம் பதினஞ்சு நிமிஷத்துல முடிஞ்சுது.

| Investigation-ல step | எடுத்த நேரம் |
| --- | --- |
| User, நேரம் வச்சு session-ஓட trace-ஐ கண்டுபிடிக்கிறது | 2 நிமிஷம் |
| 2019 note முதல்ல வந்ததை பார்க்கிறது | 3 நிமிஷம் |
| Effective dates-ஐயும் filter-ஐயும் சேர்த்து, query-ஐ மறுபடி run பண்றது | 8 நிமிஷம் |
| Trace-ஐ golden-set case-ஆ save பண்றது | 2 நிமிஷம் |

## பொதுவா பண்ற தப்புகள்

- **இறுதி பதிலை மட்டும் log பண்றது.** Retrieval failures-ஐயும் generation failures-ஐயும் உங்களால பிரிச்சு பார்க்க முடியாது.
- **Version tags இல்லாதது.** Traces-ல app, prompt versions இல்லன்னா, ஒரு மாற்றத்தையும் quality குறைஞ்சதையும் connect பண்ண முடியாது.
- **Personal data-வை mask பண்ணாம trace பண்றது.** Traces ஒரு sensitive data store ஆயிடும். Mask பண்ணுங்க, restrict பண்ணுங்க, expire பண்ணுங்க.
- **பார்க்கவே பார்க்காம இருக்கிறது.** யாராவது படிச்சா தான் traces பயன்படும்; வாரா வாரம் ஒரு sample-ஐ review பண்ணுங்க.
- **Failures-ஐ tests-ஆ மாத்தாம விடுறது.** Trace பண்ண ஒவ்வொரு மோசமான பதிலும் ஏற்கனவே தயாரா இருக்குற ஒரு eval case.
- **Model call-ஐ மட்டும் trace பண்றது**, அதனால retrieval, tool problems கண்ணுக்கே தெரியாது.
- **ஒரே மாதிரி sampling**, அது அரிதான failures-ல பெரும்பாலானதை தூக்கி எறிஞ்சுடும்.
- **எல்லா இடத்துலயும் proprietary tracing calls**, அதனால அப்புறம் மாறுறது கஷ்டம்; OpenTelemetry-ஐ prefer பண்ணுங்க.

## Simple logs போதும்ங்குற நேரங்கள்

- **ஒரு request-க்கு ஒரே ஒரு model call**, retrieval இல்லை, tools இல்லை: tokens, நேரம், outcome இருக்குற ஒரு structured log line போதும்.
- **நீங்க மட்டும் use பண்ற ஒரு prototype.**
- **Batch jobs**, அங்க ஒவ்வொரு item-க்கும் logs, ஒரு summary report இருந்தா debugging-க்கு போதும்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு step-ஐயும் trace பண்ணுங்க**, release, user, session attributes-ஓட.
- **Export-க்கு முன்னாடி personal data-வை mask பண்ணுங்க**, retention, access controls வைங்க.
- **எல்லா failures-ஐயும் slow requests-ஐயும் வச்சுக்கோங்க**, மத்ததை sample பண்ணுங்க.
- **வாரா வாரம் step வாரியா cost, latency-ஐ chart பண்ணுங்க.**
- **மோசமான traces-ஐ ஒரே command-ல eval cases-ஆ மாத்துங்க.**

## Practice பண்ணுங்க

Langfuse-ஓட tracing overview-வையும் OpenTelemetry-ஓட traces page-ஐயும் படிங்க.

1. உங்க RAG app-ல ஒரு free, self-host பண்ணக்கூடிய tool-ஓட tracing சேருங்க; rewrite, retrieval (document ids, scores-ஓட), reranking, generation-ஐ தனித்தனி spans-ஆ record பண்ணுங்க.
2. Traces-ஐ app version-ஓடயும் prompt version-ஓடயும் tag பண்ணுங்க, அனுப்புறதுக்கு முன்னாடி email addresses, phone numbers-ஐ mask பண்ணுங்க.
3. பத்து கேள்வி கேளுங்க, slow ஆன step-ஐயும் அதிக cost ஆன request-ஐயும் கண்டுபிடிங்க, ஒரு மோசமான பதிலோட trace-ஐ eval case-ஆ save பண்ணுங்க.
4. உங்க traces-ஐ OpenTelemetry வழியா ஒரு self-hosted tool-க்கு export பண்ணுங்க; அப்புறம் endpoint-ஐ ரெண்டாவது tool-க்கு மாத்தி, அதே spans வருதான்னு confirm பண்ணுங்க.
