## இது என்ன

Git ஒரு codebase-ல நடக்குற ஒவ்வொரு change-ஐயும் record பண்ணுது. தனியா இருக்கும்போது நீங்க பெரும்பாலும் commit, push மட்டும் பண்ணுவீங்க. ஒரு team-ல **main** branch shared, எப்பவும் work ஆகணும்; ஏன்னா மத்தவங்க, பல நேரம் ஒரு live product-உம், அதை நம்பியிருக்காங்க. அதனால teams ஒரு routine follow பண்றாங்க:

```flow
dir: LR
main | எப்பவும் work ஆகும் -> உங்க branch | சின்ன commits
உங்க branch -[push]-> Pull request | review, automated checks
Pull request -> Teammates comment பண்றாங்க, நீங்க fix பண்றீங்க -> Pull request
Pull request -[merge]-> main, update ஆச்சு
```

1. ஒரு வேலைக்கு ஒரு **branch** உருவாக்குங்க.
2. தெளிவான messages-ஓட சின்ன **commits** பண்ணுங்க.
3. Push பண்ணி ஒரு **pull request** (PR) திறங்க.
4. Teammates **review** பண்ணுவாங்க; automated checks ஓடும்.
5. அவங்க flag பண்ணதை fix பண்ணுங்க, அப்புறம் **merge** பண்ணுங்க.

ரெண்டு பேர் ஒரே lines-ஐ மாத்தும்போது, Git ஒரு **merge conflict**-ஐ raise பண்ணும், முடிவை ஒரு ஆள் எடுப்பாங்க.

இந்த lesson Mumbai-ல ஒரு brokerage-க்கான project-ல மூணு வாரம் ஆன உங்களை follow பண்ணும்: ஒரு market-data client-ல retries சேர்க்குறீங்க, review வாங்குறீங்க, ஒரு teammate-ஓட change-ஓட conflict-ஐ resolve பண்றீங்க. Lesson முடியும்போது ஒவ்வொரு step-லயும் உங்களுக்கு comfortable-ஆ இருக்கும்.

## இது எப்படி work ஆகுது

### Branches

Branches ஒரு commit-ஐ சுட்டிக்காட்டுற செலவில்லாத labels. `git switch -c fix/gst-rounding` ஒண்ணை உருவாக்கி உங்களை அதுக்கு கொண்டு போகும். Branches-க்கு அவை என்ன பண்றாங்களோ அதை வச்சு பேர் வைங்க:

| Prefix | எதுக்கு | Example |
| --- | --- | --- |
| `feat/` | புது feature | `feat/retry-market-data` |
| `fix/` | Bug fix | `fix/gst-rounding` |
| `docs/` | Documentation | `docs/setup-guide` |
| `chore/` | Tooling, dependencies | `chore/update-pandas` |

உங்க முதல் branch-க்கு முன்னாடி client-ஓட naming convention-ஐ check பண்ணுங்க.

### Commits

ஒவ்வொரு commit-உம் ஒரு விஷயத்தை பண்ணி, ஏன்னு சொல்லணும்:

| பலவீனமானது | பலமானது |
| --- | --- |
| "fix" | "Fix GST rounding to two decimals for invoices over ₹1 lakh" |
| "wip" | "Add retry wrapper for market data client (no callers yet)" |
| "changes" | "MD-214: retry market data calls with backoff on 429 and 503" |

நிறைய teams messages-க்கு முன்னாடி ticket id போடும். ஆறு மாசம் கழிச்சு, code ஏன் இப்படி இருக்குன்னு உங்க உட்பட யாரும் புரிஞ்சுக்க தெளிவான history தான் வழி.

### Pull requests

ஒரு PR reviewer-க்கு தேவையான context-ஐ கொண்டு போகணும்:

- என்ன மாறுச்சு, **ஏன்**.
- **எப்படி test பண்ணீங்க**.
- **Risky-ஆன எதுவும்**: performance, security, behaviour மாற்றங்கள்.
- Ticket-க்கு link, கண்ணுக்கு தெரியுற எதுக்கும் screenshots.

PRs-ஐ சின்னதா வைங்க. 200 வரி PR-க்கு கவனமான review கிடைக்கும்; 3,000 வரி PR-க்கு ஒரு rubber stamp கிடைக்கும், bugs மறைஞ்சுக்கும்.

### Review ரெண்டு பக்கமும் நடக்கும்

**Review பண்ணும்போது**, style-க்கு முன்னாடி behaviour, risk-ஐ பாருங்க: சரியானதை பண்ணுதா, எது உடையலாம், test பண்ணியிருக்கா? **Review வாங்கும்போது**, ஒவ்வொரு comment-க்கும் பதில் சொல்லுங்க, code-ஐ மாத்தியோ ஏன் மாத்தலைன்னு explain பண்ணியோ; தனிப்பட்டதா எடுத்துக்காதீங்க. Review code பத்தினது, உங்களை பத்தி இல்லை.

### Current-ஆ இருக்கிறதும், conflicts-ஐ resolve பண்றதும்

உங்க PR காத்திருக்கும்போது main நகர்ந்துக்கிட்டே இருக்கும். புது main-ஐ `git merge main` வச்சு, இல்ல team rebase விரும்பினா `git rebase main` வச்சு உங்க branch-க்குள்ள கொண்டு வாங்க. ரெண்டு பக்கமும் ஒரே lines மாறியிருந்தா, Git file-ல conflict-ஐ mark பண்ணும்:

```text
<<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = Decimal("0.18")
>>>>>>> main
```

மேல இருக்குற பகுதி உங்க branch; கீழ இருக்குறது main. (Rebase நடுவுல பக்கங்கள் மாறும்: HEAD main, கீழ இருக்குறது உங்க commit.) File-ஐ சரியான **final** version-க்கு edit பண்ணுங்க; அது பெரும்பாலும் ரெண்டையும் சேர்த்ததா இருக்கும். Markers-ஐ நீக்குங்க, tests ஓட்டுங்க, அப்புறம் `git add` பண்ணி commit பண்ணுங்க.

### Protected branches, history

Clients பெரும்பாலும் main-ஐ **protect** பண்ணுவாங்க: நேரடி push இல்லை, review-உம் passing checks-உம் தேவை. இதை சுத்தி போக ஒருபோதும் முயற்சி பண்ணாதீங்க. வேற யாரோ use பண்ற ஒரு branch-ஐ ஒருபோதும் **force-push** பண்ணாதீங்க: அது அவங்க கால் கீழ இருந்து history-ஐ உருவி எடுக்கும், அவங்க வேலை தொலையலாம்.

### Secrets

Git-ல commit பண்ண API key, file-ஐ delete பண்ணாலும் history-ல இருக்கும். Secrets-ஐ environment variables-ல வைங்க, secret files-ஐ `.gitignore`-ல list பண்ணுங்க; ஒரு key leak ஆயிடுச்சுன்னா **உடனே rotate பண்ணுங்க**, அப்புறம் clean பண்ணுங்க.

## ஒரு example

Mumbai-ல ஒரு brokerage-ஓட project-ல மூணு வாரம் ஆயிடுச்சு. உங்க ticket, MD-214: market-data client-ல retries சேர்க்கணும்; market திறக்கும்போது அது சில நேரம் rate-limit ஆகுது.

```text
git switch main && git pull
git switch -c feat/retry-market-data
# edit, test
git add src/marketdata/client.py tests/test_client.py
git commit -m "MD-214: retry market data calls with backoff on 429 and 503"
git push -u origin feat/retry-market-data
```

**PR.** உங்க description என்ன மாறுச்சுன்னு சொல்லுது; 429-ஐ ரெண்டு தடவை தர்ற ஒரு fake server-ஓட test பண்ணீங்கன்னும், ஒரு risk-ஐயும் flag பண்ணுது: மோசமான case-ல retries சேர்ந்து 7 seconds ஆகும், dashboard 10 seconds-ல time out ஆகும்.

**Review.** Reviewer Farhan, மொத்த retry நேரத்தை 3 seconds-ல cap பண்ண சொல்றாங்க. நீங்க மாத்தி, cap-க்கு ஒரு test சேர்த்து, "Done, capped at 3s total, test added"ன்னு reply பண்ணி, push பண்றீங்க.

**Conflict.** இதுக்குள்ள Priya அதே client-ல configurable timeout சேர்க்குற ஒரு change-ஐ merge பண்ணிட்டாங்க. உங்க branch இப்போ conflict ஆகுது. Main-ஐ merge பண்றீங்க, ரெண்டு பக்கத்தையும் படிக்கிறீங்க, அவங்க புது timeout setting-ஐயும் உங்க retry wrapper-ஐயும் **ரெண்டையுமே** வச்சுக்கிறீங்க, tests ஓட்டி, push பண்றீங்க.

| Step | Command அல்லது action | Result |
| --- | --- | --- |
| ஆரம்பம் | `git switch -c feat/retry-market-data` | உங்க சொந்த branch |
| வேலையை save பண்ணுங்க | `git commit -m "MD-214: ..."` | ஒரு தெளிவான commit |
| Share பண்ணுங்க | `git push -u origin ...`, PR திறங்க | Review, checks ஆரம்பிக்கும் |
| Review fix | Retries-ஐ 3 s-ல cap பண்ற புது commit | Farhan-ஓட comment resolve ஆச்சு |
| Conflict | `git merge main`, edit, test, commit | ரெண்டு changes-உம் இருக்கு |
| முடிவு | Checks green, approval, merge, branch delete | Main-ல உங்க feature இருக்கு |

Checks green ஆகுது, Farhan approve பண்றாங்க, நீங்க merge பண்ணி branch-ஐ delete பண்றீங்க.

## பொதுவா பண்ற தப்புகள்

- **பெரிய pull requests.** வேலையை பிரிங்க; நீளமான diffs-ல reviewers bugs-ஐ தவறவிடுவாங்க.
- **"wip", "changes" மாதிரி commit messages.** பின்னாடி ஏன்னு யாருக்கும் தெரியாது.
- **Secrets-ஐ commit பண்றது.** Environment variables, `.gitignore` use பண்ணுங்க; leak ஆன key-ஐ உடனே rotate பண்ணுங்க.
- **Conflicts-ஐ கண்ணை மூடிக்கிட்டு resolve பண்றது.** ஒவ்வொரு conflict-க்கும் "mine"-ஐ ஏத்துக்கிட்டா teammate-ஓட fix போயிடும். ரெண்டு பக்கத்தையும் படிங்க.
- **Shared branches-ஐ force-push பண்றது.** வேற யாரும் use பண்ணாத branches-ல மட்டும் history-ஐ rewrite பண்ணுங்க.
- **ஒரு branch வாரக்கணக்கா பழசாகி போக விடுறது.** Conflicts சின்னதா இருக்க main-ஐ அடிக்கடி merge பண்ணுங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற GitHub flow-வையும், basic branching and merging பத்தின Pro Git chapter-ஐயும் படிங்க.

1. **ஒரு உண்மையான PR.** உங்க சொந்த repository-ல ஒரு branch, ரெண்டு சின்ன commits, ஒழுங்கான description-ஓட ஒரு pull request பண்ணுங்க.
2. **ஒரு conflict.** வேணும்னே ஒண்ணை உருவாக்குங்க: main-லயும் உங்க branch-லயும் ஒரே line-ஐ மாத்தி, merge பண்ணி resolve பண்ணுங்க.
3. **Review.** ஒரு friend-ஓட PR-ஐ, இல்ல ஒரு open-source PR-ஐ review பண்ணி, ரெண்டு பயனுள்ள comments போடுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** பயமில்லாம ஒரு merge conflict-ஐ resolve பண்ண முடியும், ஒரு அந்நியர் review பண்ணக்கூடிய PR description-ஐ எழுத முடியும்.
