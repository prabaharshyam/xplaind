## இது என்ன

Agents எத்தனை steps எடுக்கணும்னு தானே முடிவு பண்ணுது. சில நேரம் அது தப்பா போகும்: ஒரு tool fail ஆகிட்டே இருக்கும், agent retry பண்ணிட்டே இருக்கும்; ரெண்டு agents வேலையை மாத்தி மாத்தி தள்ளிக்கிட்டே இருக்கும்; அல்லது agent ஒரு draft-ஐ "improve" பண்ணிட்டே இருக்கும். Limits இல்லைன்னா, ஒரு loop tokens-ஐ எரிக்கும், downstream systems-ஐ அடிக்கும், real actions-ஐ திரும்ப திரும்ப செய்யும்.

இதை மூணு controls தடுக்கும்:

- **Loop limits**: ஒரு task-க்கு, sub-agents இருந்தா ஒரு run-க்கு, அதிகபட்ச steps அல்லது tool calls எண்ணிக்கை.
- **Budgets**: ஒரு task-க்கு, ஒரு user-க்கு, முழு feature-க்கு ஒரு நாளுக்குன்னு tokens, time, பணத்துக்கு caps.
- **Kill switches**: deploy இல்லாமலே ஒரு operator ஒரு tool-ஐயோ, ஒரு agent-ஐயோ, முழு feature-ஐயோ நிறுத்த ஒரு வேகமான, நம்பகமான வழி.

Repetition checks, circuit breakers, rate, concurrency limits, idempotency keys இதுக்கு support பண்ணும்.

```flow
title: ஒவ்வொரு limit-உம் எங்க check ஆகுது
ஒவ்வொரு task | 15 steps, 60,000 tokens, 90 s வரை -> Shared store | Postgres அல்லது Redis
ஒவ்வொரு model call | estimate-ஐ reserve பண்ணி, அப்புறம் settle -> Shared store
ஒவ்வொரு tool call | kill switch, circuit breaker, idempotency key -> Shared store
ஒவ்வொரு நாளும் | ஒரு student-க்கு ₹15, feature-க்கு ₹8,000 -> Shared store
Shared store -> Provider spend limit | கடைசி backstop
```

இந்த lesson ஒரு illustrative case-ஐ follow பண்ணுது: Bengaluru-ல ஒரு edtech company-ஓட homework-help agent, ஒரே ராத்திரியில அதோட weekly budget-ஐ விட பத்து மடங்கு செலவு பண்ணுச்சு.

## இது எப்படி work ஆகுது

### Per-task limits

Loop-க்குள்ளயே steps, tool calls, tokens, ஆன நேரம் எல்லாத்தையும் count பண்ணுங்க. ஒவ்வொரு cap-ஐயும் ஒரு வாரத்து real runs-ல இருந்து choose பண்ணுங்க: 95th percentile-ஓட சுமார் ரெண்டு மடங்கு. 95% tasks 12 steps-லயும் ₹2-லயும் முடிஞ்சா, 25 steps, ₹5 cap சாதாரண வேலையை வெட்டாம runaways-ஐ நிறுத்தும். Model-ஐயோ prompt-ஐயோ மாத்தும்போது numbers-ஐ திரும்ப பாருங்க.

ஒரு limit-ஐ hit பண்ணும்போது, சுத்தமா stop பண்ணுங்க: state-ஐ save பண்ணுங்க, என்ன முடிஞ்சுது, அதுக்கு பதிலா அவங்க என்ன பண்ணலாம்னு user-க்கு எளிய வார்த்தைகள்ல சொல்லுங்க, investigate பண்ண வேண்டிய failure-ஆ log பண்ணுங்க. Stop ஆன ஒரு task எப்பவுமே crash மாதிரி தெரியக்கூடாது.

### Repetition checks, circuit breakers

ஒரு **repetition check** ஒரு task-க்குள்ள work ஆகும். ஒரே tool ஒரே arguments-ஓட மூணு தடவை call ஆனா, அல்லது ஒரே error வரிசையா மூணு தடவை திரும்ப வந்தா, task-ஐ சீக்கிரமே முடிச்சுடுங்க.

ஒரு **circuit breaker** எல்லா tasks முழுக்க work ஆகும். ஒவ்வொரு tool-ஓட failures-ஐயும் shared store-ல count பண்ணுங்க. உதாரணமா, எல்லா users-லயும் சேர்த்து ஒரு நிமிஷத்துல ஒரு tool 20 தடவை fail ஆனா, circuit-ஐ "open" பண்ணுங்க: அடுத்த அஞ்சு நிமிஷத்துக்கு அந்த tool-க்கு வர்ற ஒவ்வொரு call-உம் tool-ஐ அடையாமலே, ஒரு தெளிவான message-ஓட உடனே fail ஆகும். அப்புறம் ஒரு trial call-ஐ மட்டும் விடுங்க; அது work ஆனா, circuit-ஐ close பண்ணுங்க. Repetition check ஒரு task loop ஆகுறதை நிறுத்தும். Circuit breaker ஆயிரம் tasks ஒவ்வொண்ணும் கொஞ்சம் கொஞ்சம் loop ஆகுறதை நிறுத்தும்; ஒரே ராத்திரியில வர்ற பெரிய bill பொதுவா இப்படித்தான் உருவாகும்.

### Sub-agents முழுக்க run-level caps

ஒரு planner sub-agents-கிட்ட வேலையை கொடுக்கும்போது, ஒவ்வொண்ணும் தன்னோட 15-step cap-ஐ மதிக்கலாம், ஆனா மொத்த run நூற்றுக்கணக்கான steps எடுக்கலாம். ஒவ்வொரு run-க்கும் ஒரு root `run_id` கொடுங்க, அதை ஒவ்வொரு sub-agent-க்கும் pass பண்ணுங்க, அந்த id-க்கு எதிரா shared store-ல steps-ஐ count பண்ணுங்க. மொத்தத்தையும் (உதாரணமா ஒரு run-க்கு 40 steps), hand-offs எண்ணிக்கையையும் (உதாரணமா 4) cap பண்ணுங்க.

### ஒரு user-க்கு, ஒரு நாளுக்கு budgets

ஒரு user ஒரு நாள்ல பண்ற செலவை count பண்ணுங்க, cap-ஐ தாண்டினா மரியாதையா மறுத்துடுங்க. முழு feature-ஐயும் ஒரு நாளுக்கு count பண்ணுங்க, 50%, 80%-ல top users, task types-ஐ list பண்ற alerts-ஓட, அப்போ cap எல்லாரையும் வெட்டுறதுக்கு முன்னாடியே யாராவது நடவடிக்கை எடுப்பாங்க. Asia/Kolkata நாட்களை use பண்ணுங்க, அப்போ உங்க users-ஓட நடு ராத்திரியில limits reset ஆகும்.

Counts ஒரு database அல்லது Redis மாதிரி ஒரு shared store-ல இருக்கணும்: memory-ல count பண்ற ஆறு servers cap-ஐ விட ஆறு மடங்கு அனுமதிக்கும். ஆனா shared store மட்டும் போதாது. இயல்பா எழுதுற code "check, call, record":

1. இன்னைக்கோட total-ஐ படிங்க. அது ₹14, cap ₹15, அதனால ஒரு ₹1 call-க்கு அனுமதி உண்டு.
2. Model-ஐ call பண்ணுங்க.
3. Real cost-ஐ total-ல சேருங்க.

ஒரே user-கிட்ட இருந்து வர்ற இருபது requests, எதுவும் step 3-ஐ அடையுறதுக்கு முன்னாடியே எல்லாமே step 1-ஐ செய்யலாம், அதனால இருபதுமே pass ஆகி செலவு பண்ணும். Step 3-ஐ atomic ஆக்குறது உதவாது: race இருக்குறது check-க்கும் spend-க்கும் நடுவுல இருக்குற gap-ல. இந்த bug-க்கு பேரு **check-then-act**.

Fix **reserve, then settle**. Call-க்கு முன்னாடி, புது total cap-க்குள்ள இருந்தா மட்டும் succeed ஆகுற ஒரே conditional statement-ல, ஒரு upper-bound estimate-ஐ total-ல சேருங்க. Call-க்கு அப்புறம், estimate-ஐ எடுத்துட்டு real cost-ஐ வைங்க. ஓடிட்டு இருக்குற ஒவ்வொரு call-உம் ஏற்கனவே count ஆகியிருக்கு, அதனால எந்த check-உம் பழைய total-ஐ பார்க்காது.

### Code-ல ஒரு race-safe budget

இந்த version SQLite use பண்ணுது, அதனால ஒரு laptop-லயே ஓடும். ஒரு SQLite file ஒரே machine-ல இருக்குற processes-க்கு மட்டும் தான் shared; பல servers இருந்தா, இதே pattern-ஐ Postgres அல்லது Redis-ல use பண்ணுங்க.

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from datetime import datetime
from zoneinfo import ZoneInfo

# Adds the estimate only if the new total stays within the cap; else returns no row.
RESERVE = """INSERT INTO spend (scope, day, paise) VALUES (?, ?, ?)
  ON CONFLICT (scope, day) DO UPDATE SET paise = spend.paise + excluded.paise
  WHERE spend.paise + excluded.paise <= ?
  RETURNING paise"""

@dataclass(frozen=True)
class Reservation:
    scopes: tuple
    day: str
    paise: int

def connect(path):
    db = sqlite3.connect(path, timeout=10, isolation_level=None)  # we run our own transactions
    db.execute("CREATE TABLE IF NOT EXISTS spend (scope TEXT, day TEXT,"
               " paise INTEGER NOT NULL, PRIMARY KEY (scope, day))")
    return db

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

@contextmanager
def write_tx(db):
    db.execute("BEGIN IMMEDIATE")           # take the write lock before reading anything
    try:
        yield
        db.execute("COMMIT")
    except BaseException:
        db.execute("ROLLBACK")
        raise

class OverBudget(Exception):
    pass

def reserve(db, caps, paise):
    """caps is {scope: cap in paise}. Reserve on every scope, or on none."""
    if paise > min(caps.values()):
        return None
    day = today()
    try:
        with write_tx(db):
            for scope, cap in sorted(caps.items()):       # same order everywhere
                if not db.execute(RESERVE, (scope, day, paise, cap)).fetchall():
                    raise OverBudget(scope)               # rolls back earlier scopes
    except OverBudget:
        return None
    return Reservation(tuple(sorted(caps)), day, paise)

def settle(db, r, actual_paise):
    """Swap the estimate for the real cost, on the day it was reserved."""
    with write_tx(db):
        for scope in r.scopes:
            db.execute("UPDATE spend SET paise = paise + ? WHERE scope = ? AND day = ?",
                       (actual_paise - r.paise, scope, r.day))
```

User, feature caps ரெண்டையும் சேர்த்து `reserve`-ஐ call பண்ணுங்க. அது `None` return பண்ணா, மரியாதையா மறுத்துடுங்க; இல்லைன்னா model-ஐ call பண்ணி, அப்புறம் usage report-ல இருக்குற cost-ஓட `settle` பண்ணுங்க.

Details முக்கியம்:

- **எல்லாமே அல்லது எதுவுமே இல்ல.** User, feature counters ஒரே transaction-ல மாறும், அதனால feature cap மறுத்தா user-க்கு charge ஆகி நிக்காது.
- **பணம் முழு paise-ல.** Integers சரியா கூடும்; floating-point rupees drift ஆகும்.
- **Reservation தன்னோட நாளை வச்சுக்கும்.** இரவு 11:59-க்கு ஆரம்பிக்கிற ஒரு call, அடுத்த நாளுக்கு இல்ல, reserve ஆன நாளுக்கு எதிரா தான் settle ஆகும்.
- **Failures safe பக்கம் விழும்.** `settle`-க்கு முன்னாடி server crash ஆனா, estimate count ஆனபடியே இருக்கும்; யாரும் அதிகமா செலவு பண்ண மாட்டாங்க. ஒரு call provider-ஐ அடையவே இல்லைன்னா, 0-ஓட settle பண்ணுங்க. என்ன bill ஆச்சுன்னு சொல்ல முடியலைன்னா, reservation-ஐ அப்படியே வச்சுக்குங்க.
- **இதே shape மத்த இடங்கள்லயும் work ஆகும்.** Postgres `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING`-ஐ support பண்ணுது; conflict ஆகுற row lock ஆகும், அதனால ரெண்டாவது request காத்திருந்து அப்புறம் புது total-ஐ பார்க்கும். Deadlocks-ஐ தவிர்க்க scopes-ஐ ஒரு fixed order-ல lock பண்ணுங்க (`sorted` call). Redis-ல, read, compare, `INCRBY` மூணையும் ஒரே Lua script-ல வைங்க; Redis அதை atomic-ஆ ஓட்டும்.
- **Feature row ஒரு hot spot.** ஒவ்வொரு request-உம் அதை கொஞ்ச நேரம் lock பண்ணும். ரொம்ப அதிக traffic-ல, அதை பல rows-ஆ பிரிங்க அல்லது Redis use பண்ணுங்க.

### Call-க்கு முன்னாடி cost-ஐ estimate பண்றது

Reservation ஒரு upper bound-ஆ இருந்தா மட்டும் தான் cap நிக்கும். Input tokens-ஐ count பண்ணுங்க (உங்க provider-ஓட token counter-ஆல, இல்லைன்னா அதிகமா estimate பண்ணுங்க), model முழு `max_tokens`-ஐயும் எழுதும்னு எடுத்துக்குங்க:

```python
def estimate_paise(input_tokens, max_tokens, in_paise_per_m, out_paise_per_m):
    """Upper bound: every input token, plus the most output max_tokens allows."""
    cost = input_tokens * in_paise_per_m + max_tokens * out_paise_per_m
    return -(-cost // 1_000_000)                     # round up to whole paise
```

உதாரணமா, ஒரு model-க்கு ஒரு million input tokens-க்கு ₹25, ஒரு million output tokens-க்கு ₹125 ஆகுதுன்னு வச்சுக்குங்க (இது கற்பனை numbers; உங்க provider-ஓட price page-ஐ use பண்ணுங்க, அதை check பண்ண date-ஐ record பண்ணுங்க). 3,000-token prompt, `max_tokens` 1,000-ஓட `estimate_paise(3000, 1000, 2500, 12500)`-ஐ reserve பண்ணும், அது 20 paise. பெரும்பாலான calls சீக்கிரமே முடிஞ்சுடும், மீதியை `settle` திருப்பி கொடுக்கும்.

ரெண்டு gotchas. உங்க provider output-ஆ bill பண்ற எல்லாத்தையும், reasoning tokens இருந்தா அதையும் சேர்த்து, `max_tokens` bound பண்ணுதான்னு check பண்ணுங்க. நீங்க stream பண்ணா, output வர வர count பண்ணலாம், ஒரு run budget-ஓ kill switch-ஓ stop-னு சொன்னா stream-ஐ close பண்ணலாம்; cancel ஆன stream-ஐ உங்க provider எப்படி bill பண்ணுதுன்னு தெரியுற வரைக்கும், முழு reservation-ஐயும் வச்சுக்குங்க.

### Concurrent test-ஆல நிரூபிக்கிறது

ஒரு race real concurrency-ல மட்டும் தான் வெளிய வரும். இங்க இருபது workers, ஒவ்வொண்ணும் தனித்தனி servers மாதிரி தன்னோட சொந்த connection-ஓட, ஒரே user-க்கு ஒரே நேரத்துல 100 calls பண்ணுது:

```python
import time
from concurrent.futures import ThreadPoolExecutor

CAPS = {"user:u42": 1500, "feature:homework": 800_000}   # ₹15 and ₹8,000

def one_call(db):
    r = reserve(db, CAPS, 200)          # estimate: ₹2
    if r is None:
        return 0
    time.sleep(0.01)                    # stands in for the model call
    settle(db, r, 150)                  # real cost: ₹1.50
    return 150

def test_cap_holds_under_concurrency(tmp_path):
    path = tmp_path / "budgets.db"
    connect(path).close()
    def server(_):
        db = connect(path)
        return sum(one_call(db) for _ in range(5))
    with ThreadPoolExecutor(max_workers=20) as pool:
        spent = sum(pool.map(server, range(20)))
    total = connect(path).execute(
        "SELECT paise FROM spend WHERE scope = 'user:u42' AND day = ?", (today(),)).fetchone()[0]
    assert 0 < spent == total <= 1500
```

எங்க runs-ல இது ஒவ்வொரு தடவையும் pass ஆச்சு, ₹13.50 செலவு. Check-then-spend version, அதே test-ல, ₹15 cap-க்கு எதிரா ₹42 வரைக்கும் விட்டுடுச்சு. இந்த test-ஐ CI-ல வச்சுக்குங்க, அப்போ யாரும் reservation-ஐ "simplify" பண்ணி எடுத்துட மாட்டாங்க.

### Rate, concurrency limits

இன்னும் ரெண்டு limits உங்க பணத்தை இல்லாம உங்க systems-ஐ பாதுகாக்கும்:

- **Rate limits** ஒரு நிமிஷத்துக்கு வர்ற requests-ஐ cap பண்ணும். ஒரு பொதுவான algorithm **token bucket**: ஒவ்வொரு user-ஓட bucket-லயும் அதிகபட்சம், உதாரணமா, 10 tokens இருக்கும், ஒவ்வொரு ஆறு seconds-க்கும் ஒண்ணு refill ஆகும். ஒவ்வொரு request-உம் ஒரு token எடுக்கும்; bucket காலியா இருந்தா "slow down"-னு அர்த்தம். சின்ன bursts pass ஆகும், ஆனா average ஒரு நிமிஷத்துக்கு பத்துலயே இருக்கும்.
- **Concurrency limits** ஒரே நேரத்துல ஓடுற tasks-ஐ cap பண்ணும், உதாரணமா ஒரு user-க்கு 2. அப்போ "try again"-ஐ பத்து தடவை அழுத்தினா, பத்து இல்ல, ரெண்டு tasks தான் ஓடும். ஒரு "running" counter மேல reserve pattern-ஐ use பண்ணுங்க, அதை ஒரு `finally` block-ல release பண்ணுங்க, ஒவ்வொரு slot-க்கும் ஒரு expiry கொடுங்க, ஏன்னா crash ஆன server தன்னோட `finally`-ஐ ஓட்டவே ஓட்டாது.

### Kill switches

Kill switch-னா உங்க code ஒவ்வொரு step-க்கும் ஒவ்வொரு tool call-க்கும் முன்னாடி check பண்ற ஒரு flag, levels-ஓட: ஒரு tool-ஐ disable பண்றது (எல்லா refunds-ஐயும் நிறுத்துறது), agent-ஐ disable பண்றது (ஒரு human queue-க்கோ ஒரு simple form-க்கோ fall back ஆகுறது), அல்லது feature-ஐ disable பண்றது. Redeploy பண்ணாம ஒரு admin screen-ல இருந்தோ ஒரு config service-ல இருந்தோ flip பண்ணுங்க. Flags-ஐ ஒரு short cache-ஓட shared store-ல இருந்து படிங்க, அப்போ ஒரு மாற்றம் எல்லா இடத்துலயும் சில seconds-க்குள்ள effect-க்கு வரும்:

```python
import json, logging, time

log = logging.getLogger("agent")
WRITE_TOOLS = {"send_email", "issue_refund", "message_driver"}
MAX_STALE = 60                                           # seconds
_cache = {"read_at": float("-inf"), "ok_at": float("-inf"), "flags": {}}

def flags():
    now = time.monotonic()
    if now - _cache["read_at"] > 5:                      # refresh every 5 seconds
        _cache["read_at"] = now
        try:
            _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
            _cache["ok_at"] = now
        except Exception:
            log.warning("flag store unreachable; using last flags")
    if now - _cache["ok_at"] > MAX_STALE:                # no good read for a minute
        return {**_cache["flags"], "write_tools_off": True}
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    if tool and f.get(f"tool_{tool}_off"):
        return False
    return not (tool in WRITE_TOOLS and f.get("write_tools_off"))
```

`config_store`-னா உங்ககிட்ட இருக்குற எந்த shared store-ஆவும் இருக்கலாம்: ஒரு database row, Redis, அல்லது ஒரு feature-flag service. இந்த code ஒரு bounded வழியில safe-ஆ fail ஆகும். ஒரு சின்ன outage எதையும் மாத்தாது. ஒரு நல்ல read இல்லாம ஒரு நிமிஷம் ஆனா, அல்லது start-up-ல முதல் read fail ஆனா, emails, refunds மாதிரி write tools off ஆகும், read-only tools தொடர்ந்து work ஆகும். பழைய flags-ஐ என்னைக்குமே வச்சுக்கிட்டா, outage நேரத்துல flip பண்ண ஒரு switch வந்து சேரவே சேராது.

### Actions-க்கு idempotency

ஒவ்வொரு real-world action-க்கும், அதை unique ஆக்குறதுல இருந்து build பண்ண ஒரு key கொடுங்க (உதாரணமா order id, refund reason). Receiving system அதே key-ஓட வர்ற ரெண்டாவது action-ஐ மறுக்கும், அதனால loops-உம் retries-உம் payments-ஐயோ messages-ஐயோ திரும்ப செய்ய முடியாது.

### Kill switch-ஐ drill பண்ணுங்க

மாசத்துக்கு ஒரு தடவை, முதல்ல staging-ல, அப்புறம் production-ல ஒரு அமைதியான நேரத்துல, ஒவ்வொரு switch-ஐயும் flip பண்ணி, tasks சில seconds-க்குள்ள stop ஆகுதா, users-க்கு ஒரு தெளிவான message தெரியுதா, app-ஓட மத்த பகுதிகள் தொடர்ந்து work ஆகுதான்னு check பண்ணுங்க. நேரத்தை அளந்து, யார் பண்ணாங்கன்னு record பண்ணுங்க. ஒருபோதும் practice பண்ணாத teams, switch start-up-ல மட்டும் தான் படிக்கப்பட்டுச்சு, அல்லது on-call-ல இருந்த யாருக்கும் அது எங்க இருக்குன்னு தெரியலைன்னு ஒரு real incident-ல தான் கத்துக்குவாங்க.

## ஒரு worked example

Homework-help agent ஒரு மாசம் நல்லா ஓடுச்சு, வாரத்துக்கு சுமார் ₹18,000 model செலவுல. அப்புறம், ஒரு ஞாயிற்றுக்கிழமை ராத்திரி, ஒரு maths tool-ல வந்த ஒரு மாற்றம் ஒரு வகை கேள்விக்கு அதை error return பண்ண வச்சுது. Agent சின்ன சின்ன மாற்றங்களோட retry பண்ணுச்சு, students "try again"-ஐ அழுத்திக்கிட்டே இருந்தாங்க. திங்கள் காலைக்குள்ள feature ₹1.8 லட்சம் செலவு பண்ணியிருந்துச்சு, ஒரு சாதாரண வாரத்தை விட பத்து மடங்கு.

Team ஒரு மாசத்து runs-ஐ எடுத்து, அதுல இருந்து limits-ஐ set பண்ணாங்க:

- **Per task.** 95% tasks 7 steps, 25,000 tokens, 40 seconds-ல முடிஞ்சுது, அதனால caps 15 steps, 60,000 tokens, 90 seconds. மூணு ஒரே மாதிரி tool errors வந்தா task "இந்த கேள்வியை என்னால solve பண்ண முடியல; உங்க teacher உதவுவாங்க"-ன்னு முடியும்.
- **Per student.** 95% students ஒரு நாளுக்கு ₹6-க்கு கீழ தான் செலவு பண்ணாங்க, அதனால cap ₹15, ஒரு friendly "நாளைக்கு வாங்க"-வா காட்டப்படும். ஒவ்வொரு student-உம் ஒரே நேரத்துல 2 tasks ஓட்டலாம்.
- **ஒரு நாளுக்கு feature.** வாரத்துக்கு ₹18,000-னா ஒரு நாளுக்கு சுமார் ₹2,600, சாதாரண நாட்கள்லயே ரொம்ப busy-ஆன நாள் சுமார் ₹4,000. Cap ₹8,000, ஒரு average நாளோட சுமார் மூணு மடங்கு, ரொம்ப busy-ஆன நாளோட ரெண்டு மடங்கு. 50% (₹4,000), 80% (₹6,400)-ல on-call engineer-ஓட phone-க்கு alerts போகும்.
- **Circuit breaker** maths tool மேல: ஒரு நிமிஷத்துல 20 failures வந்தா அதை அஞ்சு நிமிஷத்துக்கு pause பண்ணும்.
- **Kill switch.** ஒவ்வொரு tool-க்கும் agent-க்கும் ஒரு admin toggle. Agent-ஐ off பண்ணா "homework help ஓய்வுல இருக்கு"-ங்குற ஒரு banner காட்டும்; app-ஓட மத்த பகுதிகள் தொடர்ந்து ஓடும்.
- **Provider.** Backstop-ஆ ஒரு hard monthly spend limit.

அந்த ஞாயிற்றுக்கிழமை ராத்திரி ஒவ்வொரு control-உம் என்ன பண்ணியிருக்கும்:

| Control | Incident மேல effect |
| --- | --- |
| Circuit breaker | Fault வந்த ஒரு நிமிஷத்துக்குள்ள, எல்லா students-க்கும் maths tool-ஐ pause பண்ணும் |
| Repetition check | Loop ஆகுற ஒவ்வொரு task-ஐயும் மூணு errors-க்கு அப்புறம் முடிக்கும் |
| Per-student cap, 2 running tasks | "Try again" damage-ஐ பல மடங்கு ஆக்குறதை நிறுத்தும் |
| ₹8,000 feature cap | எந்த நாளும் ₹8,000-க்கு மேல ஆகாது, அந்த ராத்திரி ஆன ₹1.8 லட்சத்துக்கு எதிரா |
| ₹4,000-ல alert | இன்னும் மலிவா இருக்கும்போதே யாரையாவது எழுப்பும் |

ரெண்டு வாரம் கழிச்சு, இதே மாதிரி ஒரு tool fault ஒரு நிமிஷத்துக்குள்ள circuit breaker-ஐ trip பண்ணுச்சு. Bill சில நூறு ரூபாய் தான், எந்த student-உம் complaint பண்றதுக்கு முன்னாடியே alert team-ஐ அடைஞ்சுடுச்சு.

## பொதுவா பண்ற தப்புகள்

- **Step cap இல்லாம இருக்கிறது.** இது தான் எல்லாத்தையும் விட மலிவான பாதுகாப்பு; முதல்ல இதை சேருங்க.
- **Memory-ல வச்ச budgets.** ஒவ்வொரு server-உம் தனியா count பண்ணும், உண்மையான total cap-ஐ ரொம்ப தாண்டி போகும். ஒரு shared store use பண்ணுங்க.
- **Check-then-act budgets.** Total-ஐ படிச்சு, model-ஐ call பண்ணி, அப்புறம் cost-ஐ சேர்த்தா, ஒரே நேரத்துல வர்ற requests எல்லாமே அதே check-ஐ pass பண்ணிடும். முதல்ல reserve பண்ணுங்க, ஒரே statement-ல.
- **Upper bounds இல்லாத estimates.** Average cost-ஐ reserve பண்ணா, cap leak ஆகும். முழு `max_tokens`-க்கு reserve பண்ணுங்க.
- **Concurrent tasks-க்கு cap இல்லாம இருக்கிறது.** பத்து parallel tasks ஒவ்வொண்ணும் per-task cap-ஐ pass பண்ணும்.
- **Per-agent caps மட்டும்.** வேலையை மாத்தி மாத்தி தள்ளுற sub-agents-க்கு ஒரு root run-க்கு ஒரே count வேணும்.
- **Deploy தேவைப்படுற kill switch.** ஒரு incident-ல உங்களுக்கு seconds வேணும், build pipeline இல்ல.
- **Start-up-ல மட்டும் படிக்குற kill switch.** அடுத்த restart வரைக்கும் அது எதுவும் செய்யாது.
- **Fail open ஆகுறது.** Flag store ரொம்ப நேரம் down-ஆ இருந்தா, write tools-ஐ off-ஆ எடுத்துக்குங்க.
- **சத்தமில்லாத stops.** என்ன நடந்துச்சுன்னு user-க்கு சொல்லுங்க, log பண்ணுங்க; stop ஆன task fix பண்ண வேண்டிய ஒரு bug.
- **Idempotent இல்லாத actions-ஐ retry பண்றது.** Idempotency keys use பண்ணுங்க, அப்போ loops payments-ஐயோ messages-ஐயோ திரும்ப செய்ய முடியாது.
- **Floating-point பணம்.** Paise-ஐ integers-ஆ count பண்ணுங்க.

## எப்போ simple limits போதும்

- **உங்க சொந்த team use பண்ற ஒரு prototype**: ஒரு step cap-உம் provider-ஓட spend alert-உம் மட்டுமே போதுமா இருக்கலாம்.
- **ஒண்ணு ரெண்டு model calls மட்டும் இருக்குற fixed workflows**, ஒரு request-க்கு cost predictable-ஆ இருக்குற இடத்துல.
- **சில users மட்டும் இருக்குற read-only internal tools.**

வெளியாட்கள் runs-ஐ start பண்ண முடியும்போதோ, agents actions எடுக்க முடியும்போதோ தான் per-user budgets, feature caps, layered kill switches முக்கியமாகும்.

## Demo-ல இருந்து production-க்கு

- **Budgets-ஐ shared storage-ல atomic-ஆ reserve பண்ணுங்க**, ஒவ்வொரு model call-க்கும் முன்னாடி, அப்புறம் settle பண்ணுங்க.
- **Flags-ஐயும் circuit breakers-ஐயும் check பண்ணுங்க**, ஒவ்வொரு step, tool call-க்கும் முன்னாடி.
- **Feature budgets-ல 50%, 80%-ல alert பண்ணுங்க**, அதிகமா செலவு பண்ற top users-ஐ list பண்ணி.
- **Concurrent budget test-ஐ CI-ல வச்சுக்குங்க.**
- **Kill switches-ஐ மாசாமாசம் drill பண்ணுங்க**, ஒவ்வொண்ணும் எவ்வளவு நேரம் எடுத்துச்சுன்னு record பண்ணுங்க.
- **ஒவ்வொரு stop-ஐயும் காரணத்தோட log பண்ணுங்க**, limits சரியா set ஆகியிருக்கான்னு review பண்ணுங்க.

## Practice பண்ணுங்க

Unbounded consumption பத்தின OWASP-ஓட entry-ஐ படிங்க.

1. நீங்க build பண்ண ஒரு agent-ல step, token, time caps-ஐ, ஒரு சுத்தமான stop message-ஓட சேருங்க.
2. மூணு ஒரே மாதிரி tool errors-க்கு அப்புறம் task-ஐ முடிக்கிற ஒரு repetition check-ஐ சேர்த்து, வேணும்னே உடைச்ச ஒரு tool-ஆல அதை trigger பண்ணுங்க.
3. இந்த lesson-ல இருக்குற reserve-and-settle budget-ஐயும் kill switch-ஐயும் சேர்த்து, ரெண்டும் work ஆகுறதை காட்டுங்க.
4. உங்க budget code-க்கு எதிரா concurrent test-ஐ ஓட்டுங்க. அப்புறம் `reserve`-ஐ ஒரு சாதாரண "total-ஐ படிச்சு, அப்புறம் சேர்க்குற" version-ஆல மாத்தி, test fail ஆகுறதை பாருங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு tool-ஐ வேணும்னே உடைச்சு, agent உங்க limits-க்குள்ள stop ஆகுறதை ஒரு log entry-ஓடயும் ஒரு alert-ஓடயும் காட்ட முடியும்போது.
