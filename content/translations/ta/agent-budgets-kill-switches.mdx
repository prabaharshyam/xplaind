## இது என்ன

Agents எத்தனை steps எடுக்கணும்னு தாங்களே முடிவு பண்ணுது. பெரும்பாலும் அது ஒரு பலம். சில நேரம் agent loop ஆகும்: ஒரு tool fail ஆகிக்கிட்டே இருக்கும், அது retry பண்ணிக்கிட்டே இருக்கும், ரெண்டு agents வேலையை ஒருத்தருக்கொருத்தர் திருப்பி கொடுத்துக்கிட்டே இருக்கும், அல்லது ஒரு draft-ஐ "improve" பண்ணிக்கிட்டே இருக்கும். Limits இல்லன்னா, ஒரு loop tokens-ஐ எரிக்கும், downstream systems-ஐ அடிக்கும், actions-ஐ திரும்ப திரும்ப செய்யும்.

மூணு controls இதை தடுக்குது:

- **Loop limits**: ஒரு task-க்கு அதிகபட்ச steps அல்லது tool calls.
- **Budgets**: ஒரு task, ஒரு user, ஒரு நாள், முழு feature-க்கு tokens, time, பணத்தோட caps.
- **Kill switches**: deploy இல்லாம ஒரு operator ஒரு agent-ஐயோ tool-ஐயோ முழு feature-ஐயோ நிறுத்த ஒரு வேகமான, நம்பகமான வழி.

```flow
Every task | steps 15 வரை, tokens 60,000 வரை, time 90 s வரை -> Shared store | ஒரு database அல்லது cache
Every tool call | kill switch on-ஆ? அதே call 3 தடவையா? நிறுத்து; idempotency key set -> Shared store
Every day | user செலவு ₹15 வரை, feature ₹40,000 வரை, ₹30,000-ல alert -> Shared store
Shared store -> Provider spend limit | backstop
```

இந்த lesson-ல, Bengaluru-ல ஒரு edtech company-ஓட homework-help agent ஒரே ராத்திரியில தன் வாராந்திர budget-ஐ விட பத்து மடங்கு செலவு பண்ணதை follow பண்றோம்.

## இது எப்படி work ஆகுது

**Per-task limits.** Loop-ல steps, tool calls-ஐ count பண்ணி, உண்மையான runs-ல இருந்து தேர்ந்தெடுத்த ஒரு cap-ல நிறுத்துங்க (95% tasks 12 steps-ல முடியுதுன்னா, 25-ல cap). Tokens-ம் கடந்த நேரமும் track பண்ணுங்க. ஒரு limit-ஐ தொடும்போது சுத்தமா நிறுத்துங்க: state-ஐ save பண்ணி, என்ன முடிஞ்சுது, என்ன மீதி இருக்குன்னு user-க்கு சொல்லி, ஆராய வேண்டிய failure-ஆ log பண்ணுங்க.

**Repetition checks.** ஒரே tool ஒரே arguments-ஓட வரிசையா பல தடவை call ஆனா, அல்லது ஒரே error திரும்ப திரும்ப வந்தா கண்டுபிடிச்சு, சீக்கிரமே நிறுத்துங்க.

**Per-user, daily budgets.** ஒரு user-க்கு ஒரு நாளுக்கான செலவை count பண்ணி, cap-ஐ தாண்டினா பணிவா மறுங்க. ஒரு feature-wide daily cap வச்சு, உதாரணமா 80%-ல ஒரு alert போடுங்க. இவற்றை agent-ஓட memory-ல இல்லாம, ஒரு shared store-ல (database அல்லது cache) வைங்க, அப்போ servers முழுக்க இது நிக்கும்.

**Provider-side limits.** பெரும்பாலான model providers, ஒரு key அல்லது project-க்கு spend limits அல்லது alerts set பண்ண விடுவாங்க. அவற்றை கடைசி பாதுகாப்பா use பண்ணுங்க, ஒரே பாதுகாப்பா இல்லை.

**Kill switches.** ஒவ்வொரு task-க்கு முன்னாடியும், முடிஞ்சா ஒவ்வொரு tool call-க்கு முன்னாடியும் உங்க code check பண்ற ஒரு configuration flag, levels-ஓட: ஒரு tool-ஐ disable பண்ணு (எல்லா refunds-ம் நிறுத்து), agent-ஐ disable பண்ணு (ஒரு human queue அல்லது ஒரு simple form-க்கு fall back), feature-ஐ disable பண்ணு. Redeploy இல்லாம ஒரு admin screen அல்லது config service-ல இருந்து flip பண்ணுங்க. Fire drill மாதிரி அடிக்கடி test பண்ணுங்க.

**Actions-க்கு idempotency.** ஒவ்வொரு action-க்கும் ஒரு unique key கொடுங்க; அப்போ அதே key-ஓட retry அல்லது loop ஆகுற "send refund" ஒரே ஒரு தடவை தான் நடக்கும்.

**Control layers:**

| Layer | Example | எதை நிறுத்தும் |
| --- | --- | --- |
| Per task | 15 steps, 60,000 tokens, 90 seconds | கட்டுப்பாடு இல்லாம ஓடுற ஒரு task |
| Repetition | 3 ஒரே மாதிரி errors வந்தா task முடியும் | Retry loops |
| Per user per day | ₹15 model செலவு | ஒரு user அல்லது ஒரு script budget-ஐ உறிஞ்சுறது |
| Feature per day | ₹40,000, ₹30,000-ல alert | நிறைய users-ஐ பாதிக்குற ஒரு fault |
| Kill switch | ஒவ்வொரு tool-க்கும் agent-க்கும் toggle | எதையும், seconds-ல |
| Provider limit | API project-ல மாதாந்திர hard cap | மத்தது எல்லாமே fail ஆகும்போது |

**Kill-switch drill ஓட்டுறது.** மாசத்துக்கு ஒரு தடவை, staging-ல, அப்புறம் production-ல ஒரு அமைதியான நேரத்துல, ஒவ்வொரு switch-ஐயும் flip பண்ணி மூணு விஷயங்களை check பண்ணுங்க: tasks seconds-ல நிக்குதா, users error-க்கு பதிலா தெளிவான message பார்க்குறாங்களா, app-ஓட மத்தது தொடர்ந்து work ஆகுதா. Time பண்ணுங்க, யார் செஞ்சாங்கன்னு எழுதுங்க, திரும்ப on பண்ணுங்க. ஒரு தடவையும் practice பண்ணாத teams, ஒரு உண்மையான incident-ல switch start-up-ல மட்டும் தான் check ஆகுதுன்னு, அல்லது on-call-ல யாருக்கும் அது எங்க இருக்குன்னே தெரியலைன்னு கண்டுபிடிப்பாங்க.

**User message-ஐ தேர்ந்தெடுக்கிறது.** நிறுத்தப்பட்ட task ஒரு crash மாதிரி தெரியவே கூடாது. என்ன நடந்துச்சுன்னு, user அதுக்கு பதிலா என்ன பண்ணலாம்னு சாதாரண வார்த்தையில சொல்லுங்க: "இந்த கேள்வியை என்னால solve பண்ண முடியல; உங்க teacher உதவலாம்", அல்லது "Homework help இப்போ ஓய்வுல இருக்கு; நாளைக்கு திரும்ப try பண்ணுங்க." ஒவ்வொரு stop-யையும் காரணத்தோட log பண்ணுங்க, அப்போ limits ரொம்ப இறுக்கமா இருக்கான்னு team பார்க்கலாம்.

**Code-ல ஒரு budget.** ஒரு user-க்கு ஒரு நாளுக்கான செலவை ஒரு atomic update-ஓட count பண்ணுங்க, அப்போ ரெண்டு servers ஒரே user-ஐ cap-ஐ தாண்ட விட முடியாது:

```python
db = sqlite3.connect("budgets.db", isolation_level=None)
db.execute("CREATE TABLE IF NOT EXISTS spend (user_id TEXT, day TEXT, paise INTEGER, PRIMARY KEY (user_id, day))")
DAILY_CAP_PAISE = 1500                                   # ₹15 per user per day

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

def can_spend(user_id, estimate_paise):
    row = db.execute("SELECT paise FROM spend WHERE user_id=? AND day=?", (user_id, today())).fetchone()
    return (row[0] if row else 0) + estimate_paise <= DAILY_CAP_PAISE

def record_spend(user_id, paise):
    db.execute("""INSERT INTO spend (user_id, day, paise) VALUES (?, ?, ?)
                  ON CONFLICT(user_id, day) DO UPDATE SET paise = paise + excluded.paise""",
               (user_id, today(), paise))
```

ஒவ்வொரு model call-க்கு முன்னாடியும் ஒரு estimate-ஓட `can_spend`-ஐ check பண்ணி, அப்புறம் usage report-ல இருந்து உண்மையான cost-ஐ record பண்ணுங்க. பணத்தை floating-point rupees-ல இல்லாம, முழு paise-ல count பண்ணுங்க. Postgres அல்லது Redis-ல இதே pattern, ஒரு `INSERT ... ON CONFLICT` அல்லது expiry-ஓட ஒரு `INCRBY`.

**Code-ல ஒரு kill switch.** Flags-ஐ ஒரு சின்ன cache-ஓட ஒரு shared store-ல இருந்து படிங்க, அப்போ ஒரு மாற்றம் எல்லா இடத்திலயும் seconds-ல effect ஆகும்:

```python
import json, time

_cache = {"at": 0.0, "flags": {}}

def flags():
    if time.time() - _cache["at"] > 5:                   # refresh every 5 seconds
        _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
        _cache["at"] = time.time()
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    return not (tool and f.get(f"tool_{tool}_off"))

# In the loop, before every model call and every tool call:
if not allowed("homework_helper", tool="send_email"):
    stop_cleanly("Homework help is resting; try again tomorrow.")
```

`config_store`-ங்கறது உங்ககிட்ட ஏற்கனவே இருக்குற எந்த shared store-ஆவும் இருக்கலாம்: ஒரு database row, Redis, அல்லது ஒரு feature-flag service. Store-ஐ அடைய முடியலன்னா, safe-ஆ fail பண்ணுங்க: write tools-ஐ off-ஆ எடுத்துக்குங்க.

**Numbers-ஐ தேர்ந்தெடுக்கிறது.** Limits-ஐ ஊகத்துல இல்லாம, உண்மையான runs-ல இருந்து set பண்ணுங்க. ஒரு வாரத்துக்கு ஒரு task-க்கு steps, tokens, cost-ஓட distribution-ஐ பாருங்க: 95% tasks 12 steps-லயும் ₹2-லயும் முடியுதுன்னா, 25 steps, ₹6 cap சாதாரண use-ஐ பாதிக்காம கட்டுப்பாடு இல்லாம ஓடுறதை நிறுத்தும். Models அல்லது prompts-ஐ மாத்தும்போது numbers-ஐ திரும்ப பாருங்க, ஏன்னா ரெண்டுமே சாதாரண costs-ஐ மாத்தும்.

**சுவர் வர்றதுக்கு முன்னாடியே alert.** ஒரு feature-wide budget, அந்த நாளோட cap-ல 50%, 80%-ல team-ஐ எச்சரிக்கணும்; alert-ல செலவு அதிகமான top users, top task types இருக்கணும், அப்போ cap எல்லாரையும் வெட்டுறதுக்கு முன்னாடி யாராவது நடவடிக்கை எடுக்கலாம்.

## ஒரு example

Bengaluru-ல ஒரு edtech-ஓட homework-help agent ஒரு மாசம் நல்லா ஓடுச்சு. அப்புறம் ஒரு ஞாயிற்றுக்கிழமை ராத்திரி, ஒரு maths tool-ல ஒரு மாற்றம் ஒரு வகை கேள்விக்கு error கொடுக்க வச்சுது. Agent சின்ன மாற்றங்களோட retry பண்ணுச்சு, சில students "try again"-ஐ அழுத்திக்கிட்டே இருந்தாங்க. திங்கள் காலைக்குள்ள ஒரு feature ₹1.8 லட்சம் செலவு பண்ணியிருந்துச்சு, சாதாரண வாரத்தை விட பத்து மடங்கு.

Fixes:

- Per task: அதிகபட்சம் 15 steps, 60,000 tokens, 90 seconds. வரிசையா மூணு ஒரே மாதிரி tool errors வந்தா task "இந்த கேள்வியை என்னால solve பண்ண முடியல; உங்க teacher உதவலாம்"ன்னு முடியும்.
- Per student: ஒரு நாளுக்கு ₹15 model செலவு; "நாளைக்கு வாங்க"ன்னு ஒரு friendly message-ஆ காட்டப்படும்.
- Feature: ₹40,000 daily cap, ₹30,000-ல on-call engineer-ஓட phone-க்கு alert.
- Kill switch: ஒவ்வொரு tool-க்கும் முழு agent-க்கும் ஒரு admin toggle, ஒவ்வொரு task-க்கு முன்னாடியும் check ஆகும். Agent-ஐ off பண்ணா "homework help ஓய்வுல இருக்கு"ங்குற ஒரு banner காட்டும், app-ஓட மத்தது தொடர்ந்து ஓடும்.
- Provider: backstop-ஆ API project-ல ஒரு hard monthly spend limit.

ரெண்டு வாரம் கழிச்சு இதே மாதிரி ஒரு tool fault, repetition check-ஆல நிமிஷங்கள்ல நிறுத்தப்பட்டுச்சு, ₹600 தான் செலவு; எந்த student-உம் complaint பண்றதுக்கு முன்னாடியே alert team-க்கு சொல்லிடுச்சு.

| Incident | Cost | எப்படி முடிஞ்சுது |
| --- | --- | --- |
| முதல் tool fault, limits இல்லாம | ஒரே ராத்திரியில ₹1.8 லட்சம் | திங்கள் காலை தான் கவனிச்சாங்க |
| ரெண்டு வாரம் கழிச்சு இதே மாதிரி fault | ₹600 | Repetition check நிமிஷங்கள்ல நிறுத்துச்சு; alert on-call-க்கு போச்சு |

## பொதுவா பண்ற தப்புகள்

- **Step cap இல்லாம இருக்கிறது.** ஒரே மலிவான பாதுகாப்பு; முதல்ல இதை சேருங்க.
- **Memory-ல வச்ச budgets.** ஒவ்வொரு server-உம் தனியா count பண்ணும், உண்மையான மொத்தம் cap-ஐ ரொம்ப தாண்டும். Shared store use பண்ணுங்க.
- **Deploy தேவைப்படுற kill switch.** ஒரு incident-ல உங்களுக்கு seconds வேணும், build pipeline இல்லை.
- **சத்தமில்லாத stops.** என்ன நடந்துச்சுன்னு user-க்கு சொல்லுங்க, log பண்ணுங்க; நிறுத்தப்பட்ட task ஒரு fix பண்ண வேண்டிய bug.
- **Idempotent இல்லாத actions-ஐ retry பண்றது.** Idempotency keys use பண்ணுங்க, அப்போ loops payments அல்லது messages-ஐ திரும்ப செய்ய முடியாது.
- **ஒரு server-ஓட memory-ல budgets.** பல servers-ல பரவுற users cap-ஐ பல மடங்கு பெறுவாங்க.
- **Floating-point பணம்.** Paise-ஐ integers-ஆ count பண்ணுங்க.
- **Start-up-ல மட்டும் படிக்குற kill switch.** அடுத்த restart வரைக்கும் அது எதுவும் செய்யாது.
- **திறந்து fail ஆகுறது.** Flag store down-ஆ இருந்தா, risky tools-ஐ off-ஆ எடுத்துக்குங்க.

## எப்போ simple limits போதும்

- **உங்க சொந்த team use பண்ற prototype**: ஒரு step cap-உம் provider-ஓட spend alert-உம் தான் உங்களுக்கு வேணும்.
- **ஒண்ணு அல்லது ரெண்டு model calls மட்டும் இருக்குற fixed workflows**, ஒரு request-க்கு cost predictable-ஆ இருக்கும் இடத்துல.
- **Read-only internal tools**, சில users மட்டும் இருக்குற.

வெளியாட்கள் agent runs-ஐ trigger பண்ண முடியும்போது அல்லது agents செயல்படும்போது, per-user budgets, feature caps, layered kill switches முக்கியம்.

## Demo-ல இருந்து production-க்கு

- **Budgets, flags-ஐ shared storage-ல store பண்ணுங்க**, ஒவ்வொரு model, tool call-க்கு முன்னாடியும் check பண்ணுங்க.
- **Daily limits-க்கு Asia/Kolkata நாட்களை use பண்ணுங்க**, அப்போ உங்க users எதிர்பார்க்குற நேரத்துல reset ஆகும்.
- **Feature budgets-ல 50%, 80%-ல alert** போடுங்க, அதிகம் செலவு பண்றவங்க list-ஓட.
- **Kill switches-ஐ மாசாமாசம் drill பண்ணுங்க**, ஒவ்வொண்ணும் எவ்வளவு நேரம் எடுத்துச்சுன்னு record பண்ணுங்க.
- **ஒவ்வொரு stop-யையும் காரணத்தோட log பண்ணுங்க**, limits சரியா set ஆகியிருக்கான்னு review பண்ணுங்க.

## Practice பண்ணுங்க

Unbounded consumption பத்தின OWASP-ஓட entry-ஐ படிங்க.

1. நீங்க build பண்ண ஒரு agent-ல step, token, time caps-ஐ, ஒரு சுத்தமான stop message-ஓட சேருங்க.
2. மூணு ஒரே மாதிரி tool errors-க்கு அப்புறம் ஒரு task-ஐ முடிக்கிற repetition check-ஐ சேர்த்து, வேணும்னே உடைச்ச ஒரு tool-ஆல trigger பண்ணுங்க.
3. ஒரு சின்ன database table-ல ஒரு per-user daily budget-ஐயும், ஒரு config file-ல இருந்து படிக்குற ஒரு kill switch-ஐயும் சேர்த்து, ரெண்டும் work ஆகுறதை காட்டுங்க.
4. உங்க server-ஓட ரெண்டு copies-ஐ ஓட்டி, ஒரு user-க்கு ரெண்டுக்கும் requests அனுப்பி, shared budget இன்னும் cap-ல நிக்குதுன்னு நிரூபியுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு tool-ஐ வேணும்னே உடைச்சு, agent உங்க limits-க்குள்ள நிக்குறதை, ஒரு log entry-ஓடயும் ஒரு alert-ஓடயும் காட்ட முடியும்.
