## இது என்ன

**ஒரு AI feature-ஐ price பண்றது**-னா customers அதுக்கு எப்படி pay பண்ணணும்னு முடிவு பண்றது, revenue அதோட cost-ஐ cover பண்ணி நல்ல margin விடுதான்னு check பண்றது. ரெண்டு விஷயங்கள் இதை சாதாரண software-ல இருந்து வித்தியாசமாக்குது:

- **ஒவ்வொரு use-க்கும் variable cost.** ஒரு சாதாரண software feature-ஐ இன்னொரு customer click பண்ணா கூடுதலா கிட்டத்தட்ட எந்த செலவும் இல்ல. ஒரு AI feature ஒவ்வொரு request-க்கும் model tokens-க்கு காசு கட்டுது. Heavy users light users-ஐ விட ரொம்ப அதிகமா செலவு வைக்குறாங்க.
- **உறுதியில்லாத value.** AI தங்களுக்கு எவ்வளவு மதிப்புன்னு customers இன்னும் கத்துக்கிட்டு இருக்காங்க, அதனால copy பண்றதுக்கு settled-ஆன "normal" price எதுவும் இல்ல.

இந்த lesson Varun-ஐ follow பண்ணுது. அவர் Bengaluru-ல ஒரு accounting SaaS company-ல product manager. அவரோட company small businesses-க்கு மாசம் ₹999 plan (plus GST) விக்குது, invoices-ஐ படிச்சு ledger entries-ஐ suggest பண்ற ஒரு feature-ஐ சேர்க்குது. இந்த lesson-ல வர்ற company numbers எல்லாமே illustrative. ஒவ்வொரு invoice-ஐயும் process பண்ண ₹1.00 ஆகுதுன்னு வச்சுக்குவோம்; அந்த number எங்க இருந்து வருதுன்னு கீழ பார்ப்பீங்க.

| User | மாசம் invoices | ஒவ்வொண்ணும் ₹1.00-ல cost | ₹999 plan கூட ஒப்பிட்டா |
|---|---|---|---|
| Light | 30 | ₹30 | சின்னது |
| Typical | 150 | ₹150 | பரவாயில்ல |
| Heavy (ஒரு accountant) | 2,000 | **₹2,000** | அவங்க pay பண்றதுல ரெட்டிப்பு |

```flow

title: Flat price-ல ஏன் நஷ்டம் வரலாம்
```

இந்த lesson-ஓட மீதி பகுதி நாலு கேள்விகளுக்கு வரிசையா பதில் சொல்லுது: ஒரு use-க்கு உண்மையில என்ன cost, எந்த pricing model பொருந்தும், heavy users margin-ஐ சாப்பிடாம எப்படி தடுக்குறது, customers எவ்வளவு pay பண்ணுவாங்க.

## இது எப்படி work ஆகுது

### Step 1: ஒரு request-ஓட cost-ஐ build பண்ணுங்க

Cost-ஐ estimate பண்ண beta தேவையில்ல. நாலு numbers போதும்: உள்ள போற tokens, வெளிய வர்ற tokens, ஒரு token-க்கான price, exchange rate. அப்புறம் model bill காட்டாததை சேர்க்கணும்.

```flow
title: Cost per request-ஐ build பண்றது
Input tokens × input price -> Dollars-ல model cost
தெரியுற output-உம் thinking tokens-உம் × output price -> Dollars-ல model cost
Dollars-ல model cost -[× exchange rate]-> Rupees-ல model cost
Rupees-ல model cost -[× retry factor]-> Retries சேர்த்த cost
Retries சேர்த்த cost -[+ storage, logs, hosting]-> Cost per request
```

28 November 2026 நிலவரப்படி, Anthropic இந்த API prices-ஐ ஒரு million tokens-க்கு US dollars-ல list பண்ணுது (Haiku prices 100,000 tokens வரை இருக்குற prompts-க்கு பொருந்தும்):

| Model | Input | Output | எதுக்கு நல்லது |
| --- | --- | --- | --- |
| Claude Haiku 5.5 | $0.10 | $0.50 | தெளிவான, simple, high-volume tasks |
| Claude Sonnet 5.5 | $2 | $10 | Photos, handwriting மாதிரி கஷ்டமான inputs |

மத்த providers-உம் இதே structure-ஐ (தனித்தனி input, output prices) வேற numbers-ஓட use பண்றாங்க. அவங்களோட இப்போதைய price page-ஐ படிச்சு, நீங்க use பண்ற ஒவ்வொரு number பக்கத்துலயும் check date-ஐ எழுதுங்க.

Sonnet 5.5-ல ஒரு invoice-க்கு Varun-ஓட estimate (token counts illustrative; 50 real invoices-ல உங்களோடதை நீங்களே அளந்து பாருங்க):

- Input: 1,500 tokens (instructions-உம் invoice image-உம்) × ஒரு million-க்கு $2 = $0.003.
- Output: 200 தெரியுற tokens (ledger entries) plus 400 thinking tokens = 600 × ஒரு million-க்கு $10 = $0.006.
- Model cost: $0.009. ஒரு dollar-க்கு ₹94-னு assume பண்ணா, அது ₹0.85.
- Retries: 10-ல 1 invoice format check-ல fail ஆகி திரும்ப run ஆகுதுன்னு வச்சுக்குவோம், அதனால 1.1-ஆல பெருக்குங்க: ₹0.93.
- Storage, logs, ஒவ்வொரு invoice-க்கும் பிரிச்ச hosting மாதிரி மத்த per-use costs: ₹0.07-னு வச்சுக்குவோம்.
- **ஒரு invoice-க்கு cost: சுமார் ₹1.00.**

### Step 2: மறைஞ்சிருக்குற thinking tokens-ஐ கவனிங்க

இப்போ இருக்குற பெரும்பாலான models பதில் சொல்றதுக்கு முன்னாடி "think" பண்ணுது. அந்த thinking tokens-ஐ user-உம் உங்க app-உம் பார்க்கவே இல்லைன்னாலும், அவை output-ஆ, முழு output price-ல bill ஆகுது. Response ஒரு summary-ஐ மட்டும் காட்டினாலும் முழு thinking-க்கும் நீங்க pay பண்றீங்கன்னு Anthropic-ஓட documentation சொல்லுது.

ஒரு PM-ஐ beta bill ஆச்சரியப்படுத்துறதுக்கு இது தான் மிகப் பொதுவான காரணம். Varun-ஓட முதல் beta வாரத்துல, model அதோட default effort level-ல run ஆச்சு; Anthropic-ஓட API-ல Sonnet 5.5-க்கு அது `high`. 200 தெரியுற tokens-ஐ தர்றதுக்கு ஒரு invoice-க்கு சுமார் 1,600 tokens think பண்ணுச்சு. Output line 1,800 × ஒரு million-க்கு $10 = $0.018 ஆச்சு, ஒரு invoice-க்கு முழு cost சுமார் **₹2.24**-க்கு ஏறுச்சு, estimate-ஐ விட ரெட்டிப்புக்கும் அதிகம். Extraction-க்கு குறைவான effort level-ஐ set பண்ணி, அப்புறம் ஒரு test set invoices-ல accuracy-ஐ check பண்ணதும், thinking சுமார் 400 tokens-க்கும் cost ₹1.00-க்கும் திரும்ப வந்துச்சு.

இதுல இருந்து ரெண்டு rules வருது. Thinking tokens-ஐ தனியா log பண்ணுங்க (Anthropic ஒவ்வொரு response-ஓட usage data-லயும் அவற்றை report பண்ணுது, OpenAI reasoning tokens-ஐ இதே மாதிரி ஒரு field-ல report பண்ணுது). அப்புறம் maximum output length-ஐ தெரியுற reply size-க்கு cap பண்ணவே பண்ணாதீங்க: thinking-உம் அந்த limit-க்குள்ள count ஆகும், அதனால tight cap பதிலை பாதியில வெட்டிடும், retry இன்னும் அதிகமா cost ஆகும்.

### Step 3: GST, gateway fees, rupee-ஐ கணக்குல எடுங்க

மூணு India-specific விஷயங்கள் சத்தமில்லாம margin-ஐ நகர்த்துது.

- **GST.** இந்தியால software subscriptions-க்கு 18% GST இருக்கு. "₹999 + GST"-னு advertise பண்ணா, customer ₹1,178.82 pay பண்றாங்க, நீங்க ₹999 வச்சுக்குறீங்க. "₹999 GST உட்பட"-னு advertise பண்ணா, நீங்க 999 ÷ 1.18 = ₹846.61 மட்டும் தான் வச்சுக்குவீங்க, நீங்க நினைச்சிருக்கக்கூடியதை விட சுமார் 15% குறைவு. எப்பவுமே GST இல்லாத price-ல margin-ஐ கணக்கு பண்ணுங்க, pricing page-ல எதை சொல்றீங்கன்னு தெளிவா சொல்லுங்க. GST-க்கு register ஆன business buyers பொதுவா GST-ஐ திரும்ப claim பண்ணலாம்; consumers பண்ண முடியாது, அதனால consumer apps-க்கு buyer-க்கு முக்கியமானது inclusive price தான்.
- **Payment gateway fees.** Razorpay-ஓட standard domestic rate ஒவ்வொரு payment-லயும் 2%, plus அந்த fee மேல GST (28 November 2026 அன்னைக்கு check பண்ணது). ₹1,178.82 payment-ல 2% சுமார் ₹24, plus அது மேல சுமார் ₹4 GST. Register ஆன ஒரு business பொதுவா fee மேல இருக்குற GST-ஐ திரும்ப claim பண்ணலாம்.
- **Exchange rate.** பெரும்பாலான model APIs US dollars-ல bill பண்ணுது. November 2025 நடுவுல rupee ஒரு dollar-க்கு சுமார் ₹88.7; November 2026 நடுவுல, May 2026-ல சுமார் ₹96-ஐ தொட்ட பிறகு, சுமார் ₹93.5-ல இருந்து ₹94. அந்த நகர்வு மட்டுமே ஒரு வருஷத்துல அதே dollar bill-ஐ rupees-ல சுமார் 6% அதிக விலையாக்கிடுச்சு: மாசம் $10,000 bill சுமார் ₹8.9 lakh-ல இருந்து ₹9.4 lakh ஆச்சு. ஒரு buffer வச்சு price பண்ணுங்க, rupee நகரும்போது திரும்ப கணக்கு பண்ணுங்க. GST-க்கு register ஆன ஒரு Indian company ஒரு foreign API-ஐ வாங்கும்போது, பொதுவா reverse charge-ல GST-ஐ அதுவே கட்டி திரும்ப claim பண்ணும்; details-ஐ உங்க accountant கிட்ட check பண்ணுங்க.

### Step 4: ஒரு pricing model-ஐ தேர்ந்தெடுங்க

| Model | உதாரணம் (date இல்லைன்னா illustrative) | எதுக்கு நல்லது | கவனிக்க வேண்டியது |
| --- | --- | --- | --- |
| Bundled | ஒவ்வொரு plan-லயும் AI included | Adoption | மறைஞ்ச cost; fair-use limits வேணும் |
| Tiered | Pro-ல மாசம் 200, Business-ல 2,500 | தெளிவு, upgrades | Included அளவுகளை முடிவு பண்றது |
| Add-on | AI-க்கு ஒரு user-க்கு மாசம் ₹299 | தெளிவான value signal | குறைவான adoption |
| Usage-based | ஒரு invoice-க்கு ₹1.50 | Price cost-ஐ follow பண்ணும் | Customers-க்கு budget பண்றது கஷ்டம் |
| Outcome-based | Intercom Fin: ஒரு resolution-க்கு $0.99 (28 November 2026 அன்னைக்கு check பண்ணது) | Price value-ஐ follow பண்ணும் | Success-க்கு ரெண்டு பேரும் ஒத்துக்கிட்ட definition வேணும் |

பெரும்பாலான products இவற்றை கலக்குது: included usage இருக்குற ஒரு tier, அதுக்கு மேல paid packs. இந்த hybrid பெரும்பாலான customers-க்கு bill-ஐ predictable-ஆ வச்சுக்குது, அதே நேரம் எல்லாரையும் விட heavy-ஆன users-கிட்ட charge-உம் பண்ணுது.

Outcome-based pricing கவர்ச்சியா இருக்கு, ஆனா நிறைய எதிர்பார்க்குது. Fin-ஓட கடைசி பதிலுக்கு அப்புறம் customer மேற்கொண்டு எந்த help-உம் கேக்காத ஒரு conversation-ஐ தான் Intercom billable Fin resolution-னு define பண்ணுது. அது என்ன பண்ணுதுன்னு கவனிங்க: fail ஆகுற ஒவ்வொரு attempt-ஓட cost-ஐயும் vendor தான் சுமக்குது, அதனால உங்க success rate அதிகமாவும் நிலையாவும் இருந்தா மட்டும் தான் இது work ஆகும். இதை தேர்ந்தெடுக்குறதுக்கு முன்னாடி, நீங்களும் customer-உம் logs-ல இருந்து count பண்ணக்கூடிய ஒரு "outcome"-ஓட சரியான definition-ஐ எழுதுங்க.

### Step 5: customers நம்புற credits-ஐ design பண்ணுங்க

Packs அல்லது credits வித்தா, முன்னாடியே மூணு விஷயங்களை முடிவு பண்ணுங்க.

- **Expiry.** எந்த warning-உம் இல்லாம மாச கடைசியில expire ஆகுற credits ஏமாத்து வேலை மாதிரி தோணும், கோபமான support tickets-ஐ உண்டாக்கும். 12 மாசம் valid ஆகுற packs-ஐ prefer பண்ணுங்க, அல்லது use பண்ணாத included usage-ஐ ஒரு மாசத்துக்கு roll over பண்ணுங்க.
- **Visibility.** App-ல ஒரு usage meter-ஐ காட்டுங்க, included use-ஓட 80%-லயும் 100%-லயும் email-லயும் product-லயும் warn பண்ணுங்க.
- **Breakage.** Breakage-னா காசு கட்டியும் use பண்ணவே பண்ணாத credits-ல இருந்து வர்ற revenue. உங்க margin-ஐ அது மேல build பண்ணாதீங்க. Use பண்ணாத credits-க்கு pay பண்றோம்னு கவனிக்குற customers விட்டுப் போயிடுவாங்க.

### Step 6: margin-ஐ காப்பாத்துங்க

- **Per-account rate limits.** ஒரு account-க்கு daily cap (உதாரணமா, ஒரு சாதாரண heavy நாளோட 3 மடங்கு) இருந்தா, ஒரு script அல்லது abuse பண்ணப்பட்ட free trial ஒரே ராத்திரியில ஒரு மாச budget-ஐ எரிச்சிடாம தடுக்கும்.
- **Model tiering.** தெளிவான, simple requests-ஐ சின்ன model-க்கும், கஷ்டமானதை மட்டும் பெரிய model-க்கும் அனுப்புங்க.
- **Caching.** ஒவ்வொரு request-லயும் ஒரு cached prompt prefix-க்கு (fixed instructions) முழு price கட்டுறதுக்கு பதிலா, அதை reuse பண்ணுங்க.
- அவசரம் இல்லாத வேலைக்கு **சின்ன outputs-உம் batch processing-உம்**.
- **Top 5% users-ஐ கவனிங்க.** கீழ இருக்குற Varun-ஓட mix-ல, 5% customers 55% cost-ஐ உண்டாக்குறாங்க.

### Step 7: cost-ஐ வச்சு இல்ல, value-ஐ வச்சு price பண்ணுங்க

Cost floor-ஐ முடிவு பண்ணுது. Value ceiling-ஐ முடிவு பண்ணுது: மிச்சமான மணி நேரங்கள், தவிர்த்த தப்புகள், கூடுதலா வர்ற revenue. ஒரு price-ஐ fix பண்றதுக்கு முன்னாடி, Varun-ஓட team பத்து customers-கிட்ட invoice entry-க்கு எவ்வளவு நேரம் ஆகுது, யார் செய்யுறாங்கன்னு கேட்டுச்சு. சின்ன கடைகள் வாரத்துக்கு ஒண்ணு ரெண்டு மணி நேரம், owner-ஏ செய்யுறாருன்னு சொன்னாங்க. Accountants ஒவ்வொரு மாசமும் staff-ஓட முழு நாட்கள் போகுதுன்னு சொன்னாங்க. Cost-ல இருக்குற வித்தியாசம் இல்ல, value-ல இருக்குற அந்த வித்தியாசம் தான் accountants-க்கு தனி Business plan-ஐ நியாயப்படுத்துச்சு. Surveys-ஓட மட்டும் இல்லாம, real offers-ஓட (ஒரு pricing page, ஒரு sales quote) prices-ஐ test பண்ணுங்க: மக்கள் survey-ல ஒண்ணு சொல்லுவாங்க, pay பண்றது வேற ஒண்ணுக்கு.

Costs-உம் usage-உம் ரெண்டுமே மாறும். Token prices பொதுவா குறைஞ்சுகிட்டு வந்திருக்கு, ஆனா நல்ல features இன்னும் அதிகமான, நீளமான requests-ஐ கொண்டு வரும், rupee-உம் நகரும். Beta-ல இருந்து இல்லாம, real usage-ல இருந்து ஒவ்வொரு quarter-உம் unit economics-ஐ திரும்ப கணக்கு பண்ணுங்க.

**உங்க browser-லயே try பண்ணுங்க.** இது tokens-ல இருந்து ஒரு invoice-க்கு cost-ஐயும், ஒவ்வொரு customer type-க்கும் மிச்சம் இருக்குற margin-ஐயும் கணக்கு பண்ணுது. Numbers-ஐ உங்களோடதா மாத்திப் பாருங்க.

```python
# Illustrative token counts; prices are Anthropic list prices, USD per million tokens, checked 28 November 2026
INR_PER_USD = 94          # assumption; check today's rate
RETRY = 1.1               # 1 in 10 requests runs twice
OTHER_INR = 0.07          # storage, logs, hosting per request

def cost_per_invoice(tokens_in, visible_out, thinking, price_in, price_out):
    usd = tokens_in * price_in / 1e6 + (visible_out + thinking) * price_out / 1e6
    return usd * INR_PER_USD * RETRY + OTHER_INR

print(f"Sonnet 5.5, high effort: ₹{cost_per_invoice(1500, 200, 1600, 2, 10):.2f}")
print(f"Sonnet 5.5, low effort:  ₹{cost_per_invoice(1500, 200, 400, 2, 10):.2f}")
print(f"Haiku 5.5:               ₹{cost_per_invoice(1500, 200, 400, 0.10, 0.50):.2f}")

cost = 0.45               # blended cost after tiering, from the worked example
for name, invoices, pays in [("Light", 30, 999), ("Typical", 150, 999), ("Heavy", 2000, 2499)]:
    ai_cost = invoices * cost
    print(f"{name}: pays ₹{pays} before GST, AI cost ₹{ai_cost:.2f}, left ₹{pays - ai_cost:.2f}")
```

- **Blended cost: ஒரு invoice-க்கு சுமார் ₹0.45**

Quarterly review-க்கு Varun மூணு alerts set பண்றாரு: ஒரு invoice-க்கு cost ₹0.60-ஐ தாண்டுறது, rupee ஒரு dollar-க்கு ₹100-ஐ தாண்டுறது, எந்த account-ஆவது அதோட plan-ல included invoices-ஓட 3 மடங்குக்கு மேல use பண்றது.

## பொதுவா பண்ற தப்புகள்

- **Flat price-ல unlimited AI.** எல்லாரையும் விட heavy-ஆன 5% users பாதிக்கும் மேல cost-ஐ உண்டாக்கி, அவங்களுக்கு ஆகுற cost-ஐ விட குறைவா pay பண்ணலாம்.
- **தெரியுற reply length-ஐ வச்சு price பண்றது.** Thinking tokens output-ஆ bill ஆகுது. Prices set பண்றதுக்கு முன்னாடி அவற்றை அளங்க, ஒவ்வொரு task-க்கும் effort level-ஐ set பண்ணுங்க.
- **GST-inclusive price-ல margin-ஐ கணக்கு பண்றது.** அதுல 18% எப்பவுமே உங்களோடது இல்ல, gateway இன்னும் சுமார் 2% எடுத்துக்கும்.
- **Exchange rate-ஐ கண்டுக்காம விடுறது.** Usage-ல எந்த மாற்றமும் இல்லாமலே, rupee பலவீனமாகும்போது dollar-ல bill ஆகுற model விலை ஏறும்.
- **Beta usage-ஐ வச்சு price பண்றது.** Beta users ஆர்வமானவங்க, எண்ணிக்கையில குறைவு. Launch-க்கு அப்புறம் usage, request length, user mix எல்லாம் மாறும்.
- **Per-account rate limit இல்லாதது.** ஒரு script அல்லது abuse பண்ணப்பட்ட free trial ஒரே ராத்திரியில ஒரு மாச budget-ஐ எரிச்சிடலாம்.
- **யாருக்கும் தெரியாம expire ஆகுற credits.** Customers ஏமாந்த மாதிரி உணர்ந்து விட்டுப் போவாங்க. ஒரு meter காட்டுங்க, முன்னாடியே warn பண்ணுங்க, rollover-ஐ allow பண்ணுங்க.
- **Cost-ஐ மட்டும் வச்சு price பண்றது.** Customers value-க்கு தான் pay பண்றாங்க; அதுல கொஞ்சத்தை capture பண்ணுங்க.
- **Competitor-ஓட price-ஐ copy பண்றது.** அவங்க costs, customers, value எல்லாம் உங்களோடதுல இருந்து வேற.

## Practice பண்ணுங்க

a16z-ஓட generative AI economics பத்தின essay-ஐ படிங்க, ஒரு independent comparison site-ல இப்போதைய model prices-ஐ check பண்ணுங்க. நீங்க use பண்ற ஒவ்வொரு price பக்கத்துலயும் check date-ஐ எழுதுங்க.

1. உங்களுக்கு தெரிஞ்ச ஒரு AI feature-க்கு, tokens-ல இருந்து cost per request-ஐ build பண்ணுங்க: input, தெரியுற output, thinking, price, exchange rate, retries, மத்த costs. அப்புறம் light, typical, heavy users-க்கு மாசம் எத்தனை requests-னு estimate பண்ணுங்க.
2. ரெண்டு pricing options-ஐ design பண்ணுங்க (உதாரணமா, included usage-ஓட tiered ஒண்ணு, usage-based ஒண்ணு). GST இல்லாத prices-ல, ஒவ்வொரு user type-க்கும் AI cost போக என்ன மிச்சம்னு கணக்கு பண்ணுங்க.
3. Rupee 7% பலவீனமா இருக்குற மாதிரியும், thinking tokens ரெட்டிப்பான மாதிரியும் numbers-ஐ திரும்ப run பண்ணுங்க. ஏதாவது segment negative-ஆ மாறுதா?
4. Willingness to pay-ஐ test பண்ண அஞ்சு customers-கிட்ட நீங்க கேக்குற கேள்விகளை எழுதுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** நீங்க தேர்ந்தெடுத்த pricing-ல light, typical, heavy users-க்கு margins-ஐ காட்ட முடியும், cost per request-ல ஒவ்வொரு rupee-உம் எங்க இருந்து வருதுன்னு விளக்க முடியும், எல்லாரையும் விட heavy-ஆன users-கிட்ட இருந்து எப்படி பாதுகாக்குறீங்கன்னு சொல்ல முடியும்.
