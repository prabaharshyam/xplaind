## இது என்ன

Code-ல இருந்து ஒரு language model-ஐ call பண்றது எந்த web API-ஐ call பண்றதும் மாதிரி தான்: உங்க program உங்க prompt-ஓட ஒரு request அனுப்பும், provider model-ஐ run பண்ணும், நீங்க reply-ஐயும், எத்தனை tokens use ஆச்சுன்னு மாதிரி details-ஐயும் திரும்ப பெறுவீங்க. இதை வச்சு, உங்க சொந்த programs summarise பண்ணலாம், classify பண்ணலாம், extract பண்ணலாம், எழுதலாம்.

ஒவ்வொரு பெரிய provider-உம் ஒரு API-யும், HTTP details-ஐ wrap பண்ற ஒரு official Python SDK-யும் (software development kit) தருவாங்க.

```flow
dir: LR
உங்க script | client = Anthropic(), key environment-ல இருந்து, messages.create(...) -[HTTPS POST: model, max_tokens, system, messages]-> Model provider | system prompt + message history மேல model-ஐ run பண்ணுது
Model provider -[reply text, usage, stop reason]-> உங்க script அதை படிக்குது | .content-ஓட text blocks, tokens-ல reply.usage
```

இந்த lesson Gurugram-ல இருக்குற backend developer Vikram-ஐ follow பண்ணுது; அவர் குழப்பமான meeting notes-ஐ நேர்த்தியான summaries-ஆ மாத்துற ஒரு tool-ஐ build பண்றாரு.

## இது எப்படி work ஆகுது

**ஒரு key வாங்குங்க.** Provider-ஓட developer console-ல ஒரு account create பண்ணுங்க, தேவைப்பட்டா கொஞ்சம் credit சேருங்க, ஒரு API key create பண்ணுங்க. அதை ஒரு password மாதிரி நடத்துங்க.

**Key-ஐ code-ல இருந்து வெளியில வைங்க.** அதை ஒரு environment variable-ல store பண்ணுங்க; பெரும்பாலும் `.gitignore`-ல list பண்ணியிருக்குற ஒரு `.env` file-ல. SDK பொதுவா ஒரு standard variable name-ல இருந்து அதை தானா படிக்கும்.

**SDK-ஐ install பண்ணுங்க** உங்க project-ஓட virtual environment-ல pip வச்சு.

**ஒரு message அனுப்புங்க.** ஒரு வழக்கமான call model-ஓட பேரை சொல்லி, output length-க்கு ஒரு limit வச்சு, messages-ஓட ஒரு list-ஐ pass பண்ணும். Anthropic-ஓட Python SDK-ல காட்டியிருக்கு; மத்த providers-ஓட SDKs-உம் இதே pattern-ஐ follow பண்ணும்:

```python
import anthropic

client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment

reply = client.messages.create(
    model="claude-sonnet-5-5",          # check the docs for current model names
    max_tokens=300,
    system="You are a concise assistant for a small bakery in Pune.",
    messages=[{"role": "user", "content": "Write a two-line WhatsApp message announcing fresh plum cakes for Christmas."}],
)

text = "".join(b.text for b in reply.content if b.type == "text")
print(text)
print("tokens in:", reply.usage.input_tokens, "out:", reply.usage.output_tokens)
```

Reply-ஓட `content` blocks-ஓட ஒரு list. புது models text-க்கு முன்னாடி ஒரு thinking block-ஐ வைக்கலாம்; அதனால முதல் block தான் answer-ன்னு எடுத்துக்காம, type `text` ஆன blocks-ஐ எடுங்க.

**Message list.** ஒரு conversation-னா roles (user, assistant) இருக்குற messages-ஓட ஒரு list. ஒரு chat-ஐ தொடர, புது message-ஓட சேர்த்து முந்தின turns-ஐ திரும்ப அனுப்புங்க; API தானா முந்தின calls-ஐ நினைவுல வச்சுக்காது. **System** prompt standing instructions-ஐ வைக்கும்.

**Usage, cost.** ஒவ்வொரு reply-உம் input, output tokens-ஐ report பண்ணும். ஒவ்வொரு call-க்கும் எவ்வளவு செலவுன்னு தெரிஞ்சுக்க, model-ஓட per-token price-ஆல பெருக்குங்க. Build பண்ணும்போதே usage-ஐ print பண்ணுங்க, அப்போ costs உங்களை அதிர்ச்சிப்படுத்தாது.

**Model தேர்ந்தெடுக்கிறது.** Providers பெரிய, அதிக திறன் இருக்குற models-ஐயும், சின்ன, வேகமான, மலிவான models-ஐயும் தருவாங்க. ஒரு mid-sized model-ஓட ஆரம்பிச்சு, மாத்துறதுக்கு முன்னாடி test பண்ணுங்க.

**ஒரு request-ஓட parts, அவை எதை கட்டுப்படுத்துது:**

| Part | எதை கட்டுப்படுத்துது | Tip |
| --- | --- | --- |
| `model` | Capability, speed, price | Current names-க்கு docs-ஐ பாருங்க |
| `max_tokens` | Reply-ஓட அதிகபட்ச நீளம் | எப்பவும் set பண்ணுங்க |
| `system` | முழு chat-க்கான role, tone, rules | Calls முழுக்க stable-ஆ வைங்க |
| `messages` | இதுவரைக்குமான conversation | User, assistant turns மாறி மாறி வரணும் |
| Reply `usage` | Use ஆன tokens | முதல் நாள்ல இருந்தே log பண்ணுங்க |
| Reply stop reason | ஏன் நின்னுச்சு: முடிஞ்சுது, அல்லது token limit-ஐ அடைஞ்சுது | Limit-ஐ அடைஞ்சா, answer வெட்டப்பட்டிருக்கு |

**Streaming.** ஒரு நீளமான reply முடிய பத்து வினாடி அல்லது அதுக்கு மேல ஆகலாம். Streaming-ல API text எழுதப்படும்போதே அனுப்பும், அதனால user கிட்டத்தட்ட ஒரு வினாடியில படிக்க ஆரம்பிப்பாங்க. Chat interfaces கிட்டத்தட்ட எப்பவும் stream பண்ணும்; ஆயிரம் files-ஐ இரவு summarise பண்றது மாதிரி background jobs-க்கு பொதுவா தேவையில்லை.

**Errors, retries.** API calls அப்பப்போ fail ஆகும், உங்க code அதை எதிர்பார்க்கணும்:

| Error | என்ன அர்த்தம் | என்ன பண்றது |
| --- | --- | --- |
| 401 அல்லது 403 | Key இல்லை, தப்பு, அல்லது அனுமதி இல்லை | Key-ஐ fix பண்ணுங்க; retry பண்ணாதீங்க |
| 400 | உங்க request-ல ஏதோ invalid | Message-ஐ படிச்சு request-ஐ fix பண்ணுங்க |
| 429 | Rate limit: நிமிஷத்துக்கு ரொம்ப அதிக requests அல்லது tokens | காத்திருந்து retry பண்ணுங்க, வேகத்தை குறைச்சு |
| 500, 529 அல்லது ஒரு timeout | Provider error அல்லது overload | அதிகமாகுற காத்திருப்போட retry பண்ணுங்க; தொடர்ந்தா ஒரு backup model-க்கு மாறுங்க |

Anthropic-ஓட SDK ஏற்கனவே rate limits, overloads, connection errors-ஐ அதிகமாகுற காத்திருப்போட ரெண்டு தடவை retry பண்ணும்; எத்தனை தடவைன்னு `max_retries`-ஆயும், எவ்வளவு நேரம் காத்திருக்கணும்னு `timeout`-ஆயும் set பண்ணலாம். எல்லா retries-உம் fail ஆனா user என்ன பார்க்கணும்னு உங்க code தான் முடிவு பண்ணணும்.

**ஒரு சின்ன chat program.** இது எல்லா parts-ஐயும் ஒண்ணா சேர்க்குது: history, streaming, அனுப்புறதுக்கு முன்னாடி ஒரு token check, cut-off detection, errors.

```python
import anthropic

client = anthropic.Anthropic(max_retries=3, timeout=60)
MODEL = "claude-sonnet-5-5"            # check the docs for current model names
SYSTEM = "You help students in Kerala plan their study week. Be brief."
history = []

def ask(text):
    history.append({"role": "user", "content": text})
    size = client.messages.count_tokens(model=MODEL, system=SYSTEM, messages=history).input_tokens
    if size > 20_000:
        history.pop()
        return "This conversation is too long. Please start a new one."
    try:
        with client.messages.stream(model=MODEL, max_tokens=500, system=SYSTEM, messages=history) as stream:
            for chunk in stream.text_stream:
                print(chunk, end="", flush=True)        # words appear as they arrive
            reply = stream.get_final_message()
    except anthropic.RateLimitError:
        history.pop()
        return "Busy right now. Please try again in a minute."
    except anthropic.APIStatusError as err:
        history.pop()
        return f"The AI service returned an error ({err.status_code})."
    except anthropic.APIConnectionError:
        history.pop()
        return "Could not reach the AI service. Check the connection."
    history.append({"role": "assistant", "content": reply.content})
    if reply.stop_reason == "max_tokens":
        print("\n[reply cut off at the length limit]")
    print(f"\n(tokens in {reply.usage.input_tokens}, out {reply.usage.output_tokens})")

ask("I have maths and chemistry exams in two weeks. Make a plan for Monday.")
ask("Move chemistry to the evening.")             # the model sees the first turn too
```

ஒரு error வந்தா, user-ஓட message history-ல இருந்து எடுக்கப்படும்; அதனால அடுத்த முயற்சி தொடர்ந்து ரெண்டு user messages-ஐ அனுப்பாது.

**Sampling settings.** சில models `temperature` மாதிரி settings-ஐ ஏத்துக்கும்; அது wording எவ்வளவு வேறுபடணும்னு கட்டுப்படுத்தும். Model எப்படி வார்த்தைகளை தேர்ந்தெடுக்குதுங்குற lesson அதை explain பண்ணும். புது models சில settings-ஐ fix பண்ணியிருக்கலாம், அதனால நம்புறதுக்கு முன்னாடி model-ஓட documentation-ஐ check பண்ணுங்க.

**Conversation history-க்கும் பணம் செலவாகும்.** ஒவ்வொரு turn-லயும் முழு history-ஐயும் திரும்ப அனுப்புறதால, நீளமான chats ஒவ்வொரு message-க்கும் அதிக costly ஆகும்: turn 20 turns 1 முதல் 19-க்கும் மறுபடி input-ஆ pay பண்ணும். Real apps பழைய turns-ஐ trim அல்லது summarise பண்ணும், system prompt-ஐ stable-ஆ வைக்கும்; அப்போ providers அதை cache பண்ணி, திரும்ப வர்ற பகுதிக்கு கம்மியா charge பண்ணலாம்.

**Browser-லயே try பண்ணுங்க.** History-ஐ திரும்ப அனுப்புறது ஒவ்வொரு turn-ஐயும் எப்படி costly ஆக்குதுன்னு பாருங்க. Numbers-ஐ மாத்தி மறுபடி run பண்ணுங்க.

```python
system_tokens, question, answer = 1200, 100, 250
history = 0
for turn in range(1, 11):
    sent = system_tokens + history + question
    print(f"turn {turn:>2}: {sent:>5} input tokens")
    history += question + answer       # this turn is resent next time
```

## ஒரு worked example

Gurugram-ல இருக்குற backend developer Vikram, குழப்பமான meeting notes-ஐ action items-ஓட ஒரு நேர்த்தியான summary-ஆ மாத்துற ஒரு command-line tool-ஐ build பண்றாரு.

- அவர் தன் key-ஓட `.env`-ஐ create பண்ணி, `.env`-ஐ `.gitignore`-ல சேர்த்து, `python-dotenv` வச்சு load பண்றாரு.
- அவர் script ஒரு notes file-ஐ படிச்சு, ஒரு system prompt-ஓட ("Summarise in five bullet points, then list action items as owner: task: due date") அனுப்பி, reply-ஐயும் token usage-ஐயும் print பண்ணுது.
- ரெண்டு page note-ல அது கிட்டத்தட்ட 1,800 input, 250 output tokens use பண்ணுது; அவர் model-ஓட prices-ல அது ஒரு run-க்கு ஒரு ரூபாய்க்கும் ரொம்ப கம்மி.
- ஒரு check சேர்க்கிறாரு: notes file 20,000 characters-க்கு மேல இருந்தா, தற்செயலான பெரிய bills-ஐ தவிர்க்க user-ஐ எச்சரிக்கிறாரு.

## பொதுவா பண்ற தப்புகள்

- **API key-ஐ code-லயே எழுதுறது.** Environment variables use பண்ணுங்க; எப்பவாவது commit ஆன key-ஐ rotate பண்ணுங்க.
- **`max_tokens`-ஐ மறக்கிறது.** எப்பவும் output-ஐ cap பண்ணுங்க.
- **API முந்தின calls-ஐ நினைவுல வச்சுக்கும்னு எதிர்பார்க்கிறது.** Conversation history-ஐ நீங்களே அனுப்புங்க.
- **பழைய model names-ஐ use பண்றது.** Docs-ல current list-ஐ பாருங்க.
- **Usage numbers-ஐ கண்டுக்காம விடுறது.** முதல் call-ல இருந்தே tokens-ஐ track பண்ணுங்க.

- **முழு response object-ஐ logs-ல print பண்றது.** அதுல user text இருக்கலாம். அதுக்கு பதிலா ids, token counts, timings-ஐ log பண்ணுங்க.
- **ஒவ்வொரு call-உம் success ஆகும்னு நினைக்கிறது.** Rate limits, overloads, timeouts-ஐ handle பண்ணி, user-க்கு தெளிவான message காட்டுங்க.
- **எல்லாத்தையும் retry பண்றது.** தப்பான key அல்லது invalid request ஒவ்வொரு தடவையும் அதே மாதிரி fail ஆகும்.
- **Stop reason-ஐ கண்டுக்காம விடுறது.** `max_tokens`-ஐ அடைஞ்ச reply முழுமையாகல.

## Demo-ல இருந்து production-க்கு

- **Key-ஐ server-ல வைங்க.** அதை ஒரு mobile app-லயோ browser code-லயோ ship பண்ணாதீங்க; browser உங்க server-ஐ call பண்ணும், உங்க server model-ஐ call பண்ணும்.
- **ஒரு user-க்கு limits வைங்க**: நிமிஷத்துக்கு requests, ஒரு நாளைக்கு tokens; அப்போ ஒரு user அல்லது script bill-ஐ ஏத்த முடியாது.
- **Metadata-வை log பண்ணுங்க**: request id, model, tokens, எடுத்த நேரம், stop reason, error type.
- **Provider dated names தந்தா, ஒரு model version-ஐ pin பண்ணுங்க**, புதுசுக்கு மாறுறதுக்கு முன்னாடி test பண்ணுங்க.
- **Outages-க்கு plan பண்ணுங்க**: user-க்கு ஒரு தெளிவான message, முக்கியமான features-க்கு ஒரு backup model.
