## இது என்ன

**Audit log**-னா முக்கியமான events-ஓட record: யார் என்ன செஞ்சாங்க, எப்போ, எந்த data-வுக்கு, என்ன result-ஓட. இது application logs, traces-ல இருந்து வேறுபடுது:

- **Application logs** engineers debug பண்ண உதவும். அவை noisy-ஆ இருக்கும், குறுகிய காலம் தான் இருக்கும், format-ஐ சுதந்திரமா மாத்தலாம்.
- **Traces** ஒரு request-ஓட உள் steps-ஐ விவரமா காட்டும், engineering, quality வேலைக்காக.
- **Audit logs** accountability கேள்விகளுக்கு பதில் சொல்லும்: "March 3-ல account 4471 பத்தி assistant-கிட்ட யார் கேட்டாங்க, அது அவங்களுக்கு என்ன காட்டுச்சு, refund-ஐ யாராவது approve பண்ணாங்களா?" அவை முழுமையா, consistent-ஆ, tampering-ல இருந்து பாதுகாக்கப்பட்டு, வரையறுக்கப்பட்ட காலத்துக்கு வச்சிருக்கணும்.

AI systems-க்கு, audit events-ல பொதுவா sign-ins-உம், ஒவ்வொரு கேள்வி, பதிலும் (அல்லது அவற்றோட reference) இருக்கும். retrieve ஆன documents, எடுத்த tool actions, approvals, rejections, configuration changes (prompt, model, permissions), admin actions-உம் வரும்.

| | Application logs | Traces | Audit logs |
|---|---|---|---|
| யாருக்கு | Engineers | Quality, debugging | Compliance, சர்ச்சைகள் |
| என்ன இருக்கும் | Noisy, சின்ன வரிகள், format மாறும் | ஒரு request-ஓட ஒவ்வொரு உள் step-உம் | யார் என்ன செஞ்சாங்க, எப்போ, எதுக்கு, result என்ன |
| வடிவம் | Free text | Spans | நிலையான வடிவம், append-only |
| எவ்வளவு காலம் | நாட்கள் | வாரங்கள் | Policy படி, வருஷங்கள் |

## இது எப்படி work ஆகுது

**ஒரு நிலையான event வடிவம்.** ஒவ்வொரு event-உம் குறிப்பிட்ட time zone-ல ஒரு timestamp-ஐயும், actor-ஐயும் record பண்ணும்: ஒரு user id, ஒரு service, அல்லது "agent on behalf of user X". அது action, target (document அல்லது record ids), outcome, விவரங்களுக்கு link பண்ற ஒரு request அல்லது trace id, அந்த நேரத்துல இருந்த app, prompt, model versions-ஐயும் record பண்ணும்.

**என்ன record பண்ணக்கூடாது.** Passwords, tokens, முழு card numbers-ஐ ஒருபோதும் log பண்ணாதீங்க. Personal data பத்தி வேணுமின்னே முடிவு பண்ணுங்க: பெரும்பாலும் audit log-ல ids, hashes-ஐ store பண்ணி, முழு text-ஐ தனியா, இன்னும் கட்டுப்படுத்தப்பட்ட, குறைவான retention இருக்குற ஒரு store-ல வச்சு, id-ஆ link பண்ணுவீங்க. Client-ஓட retention policy-ஐயும் சட்டத்தையும் follow பண்ணுங்க; இந்தியாவோட DPDP Act, personal data தேவைக்கு மேல வச்சிருக்கக்கூடாதுன்னு சொல்லுது.

**Tamper resistance.** Application code edit அல்லது delete பண்ண முடியாத ஒரு append-only store-ல audit events-ஐ எழுதுங்க: retention locks இருக்குற write-once storage bucket, ஒரு managed audit service, அல்லது தனி log account. யார் log-ஐ படிக்கலாம்னு கட்டுப்படுத்தி, log-க்கான access-ஐயும் log பண்ணுங்க.

**Query பண்ண முடியுற மாதிரி வைங்க.** விசாரணைகளுக்கு நிமிஷங்கள்ல பதில் வேணும்: "March-ல இந்த customer record-ஓட எல்லா actions", "agent propose பண்ணி ஒரு நபர் approve பண்ண ஒவ்வொரு refund-உம்". Events-ஐ உங்க client-ஓட tools search பண்ணக்கூடிய format-ல store பண்ணுங்க.

**Clock, identity.** Synchronised clocks-ஐயும், sign-on-ல இருந்து verify ஆன identity-ஐயும் use பண்ணுங்க, user type பண்ண பேரை ஒருபோதும் இல்ல.

**ஒரு audit event, field by field:**

| Field | உதாரணம் | ஏன் |
| --- | --- | --- |
| Timestamp | `2026-05-03 11:02:14 IST` | எப்போ, குறிப்பிட்ட time zone-ல |
| Actor | `user=emp-2213` அல்லது `agent (on behalf of emp-2213)` | யார், sign-on மூலம் verify ஆனது |
| Action | `ask`, `retrieve`, `propose`, `approve` | என்ன நடந்துச்சு |
| Target | `customer=CUST-4471`, document ids | எதுக்கு |
| Outcome | `success`, `rejected`, `error` | என்ன result-ஓட |
| Links | `request=req-88a1 trace=tr-71f0` | விவரங்களை எங்க பார்க்கிறது |
| Versions | `prompt=v12 model=...` | எந்த configuration இதை உருவாக்குச்சு |

**Retention, access நடைமுறையில.** Launch-க்கு முன்னாடி client-ஓட compliance team-ஓட retention-ஐ ஒத்துக்கோங்க. உதாரணமா, financial record rules-க்கு பொருந்த audit events-ஐ எட்டு வருஷம், முழு கேள்வி, பதில் text-ஐ கட்டுப்படுத்தப்பட்ட store-ல 180 நாள், application logs-ஐ 30 நாள் வச்சுக்கோங்க. Audit log-க்கான read access-ஐ compliance, security மாதிரி ஒரு சின்ன, பேர் சொல்லப்பட்ட குழுவுக்கு கொடுங்க, மொத்த engineering team-க்கு இல்ல, ஒவ்வொரு quarter-உம் அந்த list-ஐ review பண்ணுங்க.

**Postgres-ல ஒரு insert-only table.** Permissions-ம் ஒரு trigger-உம், அதனால app-ஆலயும், கவனக்குறைவான admin script-ஆலயும் history-ஐ மாத்த முடியாது:

```sql
CREATE TABLE audit_events (
  id bigserial PRIMARY KEY,
  at timestamptz NOT NULL DEFAULT now(),
  actor text NOT NULL, action text NOT NULL, target text,
  outcome text NOT NULL, request_id text, versions jsonb,
  detail jsonb, prev_hash text, hash text NOT NULL
);

CREATE FUNCTION audit_no_change() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'audit_events is append-only';
END $$ LANGUAGE plpgsql;

CREATE TRIGGER audit_lock BEFORE UPDATE OR DELETE ON audit_events
  FOR EACH ROW EXECUTE FUNCTION audit_no_change();

GRANT INSERT, SELECT ON audit_events TO app;
GRANT USAGE ON SEQUENCE audit_events_id_seq TO app;
```

**Code-ல ஒரு hash chain.** ஒவ்வொரு event-உம் முந்தையதோட hash-ஐ உள்ளடக்கும்; அதனால மாத்தப்பட்ட அல்லது காணாமப்போன row, நீங்க verify பண்ணும்போது தெரிஞ்சுடும்:

```python
import hashlib, json

def event_hash(event, prev_hash):
    body = json.dumps({k: event[k] for k in sorted(event) if k not in ("hash", "prev_hash")},
                      sort_keys=True, default=str, ensure_ascii=False)
    return hashlib.sha256((prev_hash or "").encode() + body.encode()).hexdigest()

def append(db, event):
    with db.transaction():
        last = db.fetchone("SELECT hash FROM audit_events ORDER BY id DESC LIMIT 1 FOR UPDATE")
        prev = last[0] if last else None
        event["prev_hash"], event["hash"] = prev, event_hash(event, prev)
        db.insert("audit_events", event)

def verify(rows):
    prev = None
    for r in rows:                                 # ordered by id
        if r["prev_hash"] != prev or event_hash(r, prev) != r["hash"]:
            return f"chain broken at event {r['id']}"
        prev = r["hash"]
    return "ok"
```

`verify`-ஐ தினமும் இரவு run பண்ணி, சமீபத்திய hash-ஐ application எழுத முடியாத ஒரு இடத்துல நகலெடுங்க; தனி account, அல்லது compliance-க்கு தினமும் ஒரு email மாதிரி. அப்போ database access இருக்குறவங்க கூட chain-ஐ அமைதியா மாத்த முடியாது.

**Exports-க்கு write-once storage.** Cloud object stores, ஒரு retention காலத்துக்கு objects-ஐ delete ஆகாத மாதிரி lock பண்ணலாம் (உதாரணம், compliance mode-ல S3 Object Lock). Audit events-ஐ தினமும் compressed files-ஆ அங்க export பண்ணுங்க. இது main database-ஐயும் சின்னதா வச்சுக்கும்.

**Investigators-க்கு தேவைப்படுற queries, முன்னாடியே தயாரா.**

```sql
-- Everything that touched one customer in a date range, in IST:
SELECT at AT TIME ZONE 'Asia/Kolkata', actor, action, outcome, request_id
FROM audit_events WHERE target = 'customer=CUST-4471'
  AND at >= '2026-03-01 00:00+05:30' AND at < '2026-04-01 00:00+05:30' ORDER BY at;

-- Agent proposals approved by one manager:
SELECT a.at, a.target, a.detail->>'amount_inr' AS amount
FROM audit_events a WHERE a.action = 'approve' AND a.actor = 'emp-1180' ORDER BY a.at;
```

இவற்றை compliance team-க்கு named queries அல்லது dashboard views-ஆ save பண்ணுங்க.

**Log-க்கான access-ஐயும் log பண்ணுங்க.** Audit events-ஐ படிக்கிறதும் record பண்ண வேண்டிய ஒரு event: யார் எந்த customer-ஐ எப்போ தேடுனாங்க.

## ஒரு worked example

Kochi-ல ஒரு cooperative bank, loan-restructuring requests-க்கு பதில்களை draft பண்ண staff-க்கு உதவ ஒரு AI agent-ஐ use பண்றாங்க. ஆறு மாசம் கழிச்சு, ஒரு borrower தன்னோட request நியாயமில்லாம reject ஆனதா புகார் பண்றாங்க; bank-ஓட ombudsman office முழு history-யும் கேக்குது.

ஒவ்வொரு event-உம் audit பண்ணப்பட்டதால, bank-ஓட compliance officer ஒரு மணி நேரத்துல இதை கொடுக்க முடியுது:

```text
2026-05-03 11:02:14 IST  user=emp-2213 (branch: Aluva)  action=ask
    request=req-88a1 trace=tr-71f0 customer=CUST-4471 prompt=v12 model=alias:chat-default(2026-04)
2026-05-03 11:02:19 IST  agent(on behalf of emp-2213)  action=retrieve
    docs=[policy-restructuring-v6#s4, cust-4471-statement-2026-04]
2026-05-03 11:02:31 IST  agent(on behalf of emp-2213)  action=propose  type=reject_restructuring  reason_ref=tr-71f0
2026-05-03 11:09:47 IST  user=emp-0457 (manager)  action=approve  proposal=req-88a1
```

Use ஆன policy version அதுக்கு அப்புறம் திருத்தப்பட்டிருக்குன்னும், AI-ஓட recommendation-ஐ ஒரு manager ஏழு நிமிஷத்துக்குள்ள approve பண்ணாருன்னும் history காட்டுது. Bank அந்த case-ஐ மறுபடி திறக்குது, restructuring rejections-க்கு approver-ஓட எழுத்துப்பூர்வ note வேணும்னு ஒரு rule-ஐ சேர்க்குது. Audit log தப்பை தடுக்கல, ஆனா அதை தெரியுற மாதிரி, சரி பண்ணக்கூடிய மாதிரி, ombudsman-க்கு விளக்கக்கூடிய மாதிரி ஆக்குச்சு.

**Bank அதுக்கு அப்புறம் என்ன மாத்துச்சு.** எழுத்துப்பூர்வ note rule-ஐ தாண்டி, bank ரெண்டு checks-ஐ சேர்த்துச்சு. அதிக தாக்கம் உள்ள ஒரு AI recommendation-ஐ ஒரு manager ரெண்டு நிமிஷத்துக்குள்ள approve பண்ணா, ஒரு alert வரும்; இது கண்மூடி முத்திரை குத்துறதோட அறிகுறி. ஒரு மாசாந்திர report, managers agent-ஓட proposals-ஐ எத்தனை தடவை override பண்றாங்கன்னு காட்டும்.

## பொதுவா பண்ற தப்புகள்

- **Debug logs-ஐ audit trail-ஆ use பண்றது.** அவை முழுமையில்ல, edit பண்ணலாம், சுழற்சில மறைஞ்சுடும்.
- **எல்லாத்தையும் முழுசா record பண்றது.** நீண்ட retention இருக்குற log-ல personal data-ஓட முழு prompts, புது privacy risk-ஐ உருவாக்கும். References-ஐ store பண்ணி, முழு text-ஐ குறைவான retention-ஓட தனியா வச்சுக்கோங்க.
- **Edit பண்ணக்கூடிய storage.** ஒரு administrator entries-ஐ அமைதியா delete பண்ண முடிஞ்சா, log எதையும் நிரூபிக்காது.
- **Version தகவல் இல்லாம இருக்குறது.** Prompt, model versions இல்லாம, system அப்போ ஏன் அப்படி நடந்துக்கிச்சுன்னு உங்களால விளக்க முடியாது.
- **Agent-ஐ actor-ஆ log பண்றது.** யாருக்காக செயல்பட்டுச்சு, யார் approve பண்ணாங்கன்னு எப்பவும் record பண்ணுங்க.
- **Failures-ஐ மட்டும் audit பண்றது.** சர்ச்சைகள் பெரும்பாலும் "work ஆன" decisions பத்தி தான். வெற்றிகரமான actions, approvals-ஐயும் record பண்ணுங்க.
- **Application update அல்லது delete பண்ணக்கூடிய audit rows.** Permissions, ஒரு trigger வச்சு lock பண்ணுங்க.
- **Tampering-ஐ detect பண்ற வழி இல்லாம இருக்குறது.** ஒரு hash chain use பண்ணி, சமீபத்திய hash-ஐ வேற இடத்துல வச்சுக்கோங்க.
- **சம்பவம் நடக்கும்போதே investigation queries-ஐ build பண்றது.** முன்னாடியே எழுதி test பண்ணுங்க.

## சாதாரண logs போதுமான நேரங்கள்

- **வேற users இல்லாத prototypes, தனிப்பட்ட tools.**
- **Public தகவல்கள் மேல இருக்குற read-only assistants**, யாரோட records-உம் மாறாத இடங்கள்ல.
- **Customer data-வை தொடாத, குறுகிய கால internal experiments.**

System records மேல செயல்படும்போது, personal அல்லது financial data-வை handle பண்ணும்போது, அல்லது client-ஓட compliance team "யார் என்ன செஞ்சாங்க, எப்போ?"ன்னு கேக்கும்போது, முறையான audit logs தேவை.

## Demo-ல இருந்து production-க்கு

- **நிலையான event schema-வை use பண்ணுங்க**, verify ஆன identities, IST timestamps, versions-ஓட.
- **Audit storage-ஐ append-only ஆக்குங்க**, தினமும் இரவு hash-chain check-ஓட.
- **தினமும் write-once storage-க்கு export பண்ணுங்க**, ஒத்துக்கிட்ட retention-ஓட.
- **Read access-ஐ கட்டுப்படுத்தி, log பண்ணுங்க**, பேர் சொல்லப்பட்ட ஒரு குழுவுக்கு, ஒவ்வொரு quarter-உம் review பண்ணி.
- **Investigation queries-ஐ save பண்ணி, test பண்ணி வச்சுக்கோங்க.**

## Practice பண்ணுங்க

OWASP Logging Cheat Sheet-ஐ படிங்க, குறிப்பா என்ன log பண்ணணும், எதை விலக்கணும்ங்கிற பகுதிகளை.

1. மேல இருக்குற fields-ஓட உங்க AI app-க்கு ஒரு audit event schema-வை define பண்ணி, ask, retrieve, tool action, approval, configuration change-க்கு events-ஐ emit பண்ணுங்க.
2. அவற்றை ஒரு append-only store-ல எழுதுங்க (உதாரணம், object lock இருக்குற ஒரு cloud bucket, அல்லது insert-only permissions இருக்குற தனி database table).
3. ஒரு investigator-க்கு தேவைப்படுற ரெண்டு queries-ஐ எழுதுங்க: ஒரு customer id-க்கு ஒரு date range-ல இருக்குற எல்லா events, குறிப்பிட்ட ஒரு manager approve பண்ண ஒவ்வொரு agent action-உம்.
4. Hash chain-ஓட பத்து events-ஐ insert பண்ணி, ஒரு admin-ஆ trigger-ஐ disable பண்ணி ஒரு row-ஐ மாத்தி, verify அந்த break-ஐ report பண்றதை காட்டுங்க.

**எப்போ முடிஞ்சதுன்னு சொல்லலாம்:** Application logs-ஐ படிக்காம, உங்க audit log-ஐ மட்டும் வச்சு ஒரு request-ஓட முழு கதையையும் புனரமைக்க முடியும்.
