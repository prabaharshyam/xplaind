## இது என்ன

Embedding-னா ஒரு text துண்டோட அர்த்தத்தை குறிக்கிற numbers list. ஒரு sentence embedding model-க்குள்ள போய், 384 அல்லது 1,536 மாதிரி numbers-ஆ வெளியே வரும். அந்த numbers தனியா பார்த்தா ஒரு மனுஷனுக்கு எதுவும் புரியாது. முக்கியம் என்னன்னா ரெண்டு lists எப்படி compare ஆகுதுங்கறது: ஒரே மாதிரி அர்த்தம் உள்ள texts-க்கு கிட்டத்தட்ட ஒரே திசையில காட்டுற lists கிடைக்கும், சம்பந்தமில்லாத texts-க்கு வேற வேற திசையில.

Semantic search-க்கு பின்னாடி இருக்குற trick இதுதான். "How do I get my money back?"-உம் "refund policy"-யும் ஒரே வார்த்தையை பகிர்ந்துக்கல, ஆனாலும் அவற்றோட embeddings பக்கத்துல இருக்கும். அதனால embeddings-ல build பண்ண search ஒண்ணுல இருந்து இன்னொண்ணை கண்டுபிடிக்கும். ஒரு keyword search அதை miss பண்ணிடும்.

Search, RAG, duplicate tickets கண்டுபிடிக்க, customer feedback-ஐ theme வாரியா group பண்ண, ஒத்த items-ஐ recommend பண்ண embeddings-ஐ use பண்ணுவீங்க.


## இது எப்படி work ஆகுது

1. **Embedding model text-ஐ படிக்குது.** இது ஒரு neural network. பொருந்தணும்ங்குற text pairs (ஒரு கேள்வியும் அதோட answer-உம், ஒரு title-உம் அதோட article-உம்), பொருந்தக்கூடாத pairs, இவை ரொம்ப அதிகமா இருக்குறதுல train ஆனது. Training, பொருந்துற pairs-ஐ பக்கத்துல கொண்டு வரும்.
2. **அது ஒரு vector-ஐ output பண்ணும்.** ஒரு model-க்கு, சின்னதோ நீளமானதோ, ஒவ்வொரு text-உம் ஒரே நீளமுள்ள vector-ஆ மாறும். வேற வேற models வேற வேற நீளங்களை தரும், வேற models-ஓட vectors-ஐ ஒண்ணோட ஒண்ணு compare பண்ண முடியாது.
3. **Vectors-ஐ ஒரு similarity score வச்சு compare பண்றீங்க.** வழக்கமானது cosine similarity: 1-னா ஒரே திசை, 0-னா சம்பந்தமில்லை. நிறைய libraries vectors-ஐ normalise பண்ணும், அதனால ஒரு simple dot product அதே ranking-ஐ தரும்.
4. **பின்னால search பண்ண vectors-ஐ store பண்றீங்க.** சில ஆயிரம் texts-க்கு ஒரு NumPy array போதும். லட்சக்கணக்கானவைக்கு, pgvector, Qdrant, Pinecone மாதிரி ஒரு vector database, approximate index வச்சு நெருக்கமான vectors-ஐ வேகமா கண்டுபிடிக்கும்.

ரெண்டு practical points. முதல்ல, query-யையும் documents-ஐயும் ஒரே model-ல embed பண்ணுங்க. ரெண்டாவது, ஒரு embedding model-க்கு அதுக்குன்னு ஒரு input limit இருக்கும், பெரும்பாலும் சில நூறு tokens. அதுக்கு மேல இருக்குறதை சத்தமில்லாம வெட்டிடும். நீளமான documents-ஐ embed பண்றதுக்கு முன்னாடி chunks-ஆ பிரிக்கிறதுக்கு இது ஒரு காரணம்.

**Model-ஐ தேர்ந்தெடுக்கிறது:**

| Option | Size, cost | எதுக்கு நல்லது |
| --- | --- | --- |
| சின்ன open model (MiniLM மாதிரி) | Laptop-ல ஓடும், free | Prototypes, English text, ஆயிரக்கணக்கான items |
| பெரிய open multilingual model | வேகத்துக்கு GPU வேணும், ஓட்ட free | இந்திய மொழிகள், Hinglish, நல்ல quality |
| Hosted embedding API | Token-க்கு பணம், servers வேண்டாம் | வேகமா ஆரம்பிக்க, பெரிய scale, managed updates |

**தேர்ந்தெடுக்கிறதுக்கு முன்னாடி test பண்ணுங்க.** இருபது real queries-ஐ சேகரிங்க, ஒவ்வொண்ணுக்கும் முதல்ல வரணும்னு நீங்க நினைக்கிற ticket அல்லது passage-ஓட. எல்லாத்தையும் ரெண்டு மூணு candidate models-ல embed பண்ணி, சரியான item எத்தனை தடவை top three-ல வருதுன்னு எண்ணுங்க. இதுக்கு ஒரு மதியம் போதும், எந்த public leaderboard-ஐயும் விட இது நல்லது. ஏன்னா இது உங்க users-ஓட வார்த்தைகள், spellings, மொழிகளை use பண்ணுது. Model-ஐ மாத்தலாமான்னு யோசிக்கும்போதெல்லாம் இந்த test-ஐ திரும்ப பண்ணுங்க, ஏன்னா மாத்தினா முழு collection-ஐயும் re-embed பண்ணணும்.

**Code-ல embeddings.** `sentence-transformers` library-ஓட:

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
docs = ["Dhoni hit the winning six in 2011", "Add the soaked rice to the biryani masala",
        "Kohli scored a century in Perth", "Fry onions until golden brown"]
vecs = model.encode(docs, normalize_embeddings=True)            # shape (4, 384)

query = model.encode(["how to cook biryani"], normalize_embeddings=True)[0]
scores = vecs @ query                                            # cosine, because vectors are normalised
for score, text in sorted(zip(scores, docs), reverse=True)[:2]:
    print(f"{score:.2f}  {text}")
```

**Multilingual models, அவற்றோட prefixes.** Hindi, Tamil, Hinglish, மத்த இந்திய மொழி text-க்கு, ஒரு multilingual model-ஐ use பண்ணுங்க. E5 family மாதிரி சிலது, inputs queries-ஆ அல்லது passages-ஆன்னு mark பண்ணியிருக்கணும்னு எதிர்பார்க்கும்:

```python
m = SentenceTransformer("intfloat/multilingual-e5-base")
passages = m.encode(["passage: बिरयानी बनाने के लिए चावल भिगो दें", "passage: Kohli scored a century"],
                    normalize_embeddings=True)
q = m.encode(["query: biryani kaise banate hain"], normalize_embeddings=True)[0]
print(passages @ q)
```

ஒவ்வொரு model-ஓட card-ஐயும் படிச்சு, அதோட prefixes, input limit, languages-ஐ தெரிஞ்சுக்கோங்க. Prefixes இல்லன்னா errors வராது, results மோசமாகும், அதனால தான் அதை miss பண்றது ஈஸி.

**Size, storage.** ஒவ்வொரு vector-க்கும் ஒரு fixed dimensions எண்ணிக்கை இருக்கும் (384, 768, 1,024 அல்லது அதுக்கு மேல). Storage = vectors × dimensions × bytes: பத்து லட்சம் 768-dimension vectors, 32-bit floats-ஆ கிட்டத்தட்ட 3 GB எடுக்கும். 16-bit-ல store பண்ணா அதுல பாதி, கிட்டத்தட்ட எந்த இழப்பும் இல்லாம. 8-bit அல்லது binary quantisation இன்னும் சுருக்கும், ஆனா quality-ல கொஞ்சம் இழப்பு. சில புது models, ஒவ்வொரு vector-லயும் முதல் பகுதியை மட்டும் (உதாரணத்துக்கு 1,024 dimensions-ல 256) வச்சுக்கிட்டாலும் நல்லா search பண்ற மாதிரி train ஆகியிருக்கு. எந்த சுருக்கலையும் உங்க சொந்த golden queries-ல test பண்ணுங்க.

**Benchmarks ஒரு ஆரம்பப் புள்ளி தான்.** MTEB மாதிரி public leaderboards பல tasks, மொழிகள்ல embedding models-ஐ compare பண்ணும், shortlist பண்ண உதவும். உங்க users-ஓட queries, spellings வச்சு நீங்க பண்ற சொந்த test தான் முடிவு பண்ணும்.

```python
def top3_hit_rate(model, queries, corpus, correct_ids):
    """queries[i] should find corpus item correct_ids[i] in its top 3."""
    c = model.encode(corpus, normalize_embeddings=True)
    q = model.encode(queries, normalize_embeddings=True)
    top3 = (-(q @ c.T)).argsort(axis=1)[:, :3]
    return sum(correct_ids[i] in top3[i] for i in range(len(queries))) / len(queries)
```

**Model-ஐ மாத்தினா re-embed பண்ணணும்.** வேற வேற models-ஓட vectors வேற வேற spaces-ல இருக்கும், கலக்க முடியாது. ஒவ்வொரு vector-ஓடவும் model பெயரையும் version-ஐயும் store பண்ணுங்க, எந்த மாற்றத்துக்கும் முழு re-embed-ஐயும் (ஒரு test-ஐயும்) plan பண்ணுங்க.

## ஒரு worked example

Chennai-ல ஒரு edtech support team-கிட்ட 2,000 பழைய tickets இருக்குன்னு வச்சுக்கோங்க, agents-க்கு ஒத்த, solve ஆன tickets-ஐ காட்ட அவங்க நினைக்கிறாங்க.

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("all-MiniLM-L6-v2")   # small, free, runs on a laptop
tickets = [
    "Payment deducted but course not unlocked",
    "Money taken twice for one order",
    "Video keeps buffering on mobile data",
    "Certificate shows the wrong name",
]
vectors = model.encode(tickets, normalize_embeddings=True)

query = model.encode(["UPI debited, no access to the course"], normalize_embeddings=True)
scores = vectors @ query.T            # dot product = cosine similarity here
for i in np.argsort(-scores[:, 0])[:2]:
    print(round(float(scores[i, 0]), 2), tickets[i])
```

Query "UPI debited"-னும் "no access"-னும் சொல்லுது, ticket "payment deducted"-னும் "not unlocked"-னும் சொல்லுது. ஆனாலும் முதல் result முதல் ticket தான். ரெண்டாவதா double-charge ticket வரணும்: அதுவும் பணம் பத்தினது, அதனால நெருக்கம், ஆனா கொஞ்சம் குறைவு. Buffering, certificate tickets-ஓட scores குறைவா இருக்கணும். Run பண்ணி check பண்ணுங்க: exact scores model version-ஐ பொறுத்தது.

இப்போ "certificate name spelling mistake"-ஐ try பண்ணுங்க. அது certificate ticket-ஓட ஆழமா match ஆகணும், மத்த எல்லாத்தோடயும் பலவீனமா. அப்படி இல்லன்னா, நீங்க encode பண்ற அல்லது compare பண்ற விதத்துல ஏதோ தப்பு.

**Team என்ன அளந்தாங்க.** 30 real agent queries-ல, சின்ன English model சரியான ticket-ஐ top three-ல 22 தடவை வச்சுது. ஒரு multilingual model 27 தடவை வச்சுது. "payment cut aachu, course open aagala" மாதிரி Tamil-English கலந்து எழுதுன queries-ஐ பிடிச்சதால தான் பெரும்பாலும். Team multilingual model-ஐ தேர்ந்தெடுத்தாங்க, order ids-க்கு keyword search-ஐயும் வச்சுக்கிட்டாங்க, ஏன்னா ரெண்டு models-உம் அதை நல்லா handle பண்ணல.

## பொதுவா பண்ற தப்புகள்

- **Models-ஐ கலக்குறது.** ரெண்டு வேற embedding models-ஓட vectors வேற வேற spaces-ல இருக்கும். Model-ஐ மாத்தினா எல்லாத்தையும் re-embed பண்ணுங்க.
- **முழு documents-ஐ embed பண்றது.** 30 பக்க PDF-ஐ ஒரே vector-க்குள்ள நசுக்கினா detail போயிடும், model-ஓட limit-ஐ தாண்டின text drop ஆகும். முதல்ல chunk பண்ணுங்க.
- **Score-ஐ probability-ஆ நம்புறது.** 0.62 score "62% relevant"னு அர்த்தம் இல்லை. Scores ranking-க்கு மட்டும் உதவும், நல்ல thresholds model-க்கு model மாறும், அதனால எந்த cut-off-ஐயும் உங்க சொந்த data-ல இருந்து set பண்ணுங்க.
- **Exact terms-ஐ கண்டுக்காம விடுறது.** Order numbers, product codes, அரிதான பெயர்கள்ல embeddings பலவீனம். இவை முக்கியம்னா keyword search-ஓட சேர்த்து use பண்ணுங்க.
- **உங்க சொந்த text-ல test பண்ணாம இருக்கிறது.** ஒரு public leaderboard-ல top-ல இருக்குற model, இந்திய பெயர்கள், Hinglish, உங்க domain-ஓட jargon-ல மோசமா இருக்கலாம். தேர்ந்தெடுக்கிறதுக்கு முன்னாடி இருபது real queries-ல check பண்ணுங்க.
- **ஒரு model-ஓட query, passage prefixes-ஐ மறக்கிறது.** எதுவும் error ஆகாது; results மட்டும் மோசமாகும்.
- **ஒரே index-ல ரெண்டு models-ஓட vectors-ஐ கலக்குறது.**
- **Leaderboard-ஐ மட்டும் வச்சு தேர்ந்தெடுக்கிறது.** உங்க சொந்த queries-ல test பண்ணுங்க.

## Embeddings சிறந்த tool இல்லாத இடங்கள்

- **Exact identifiers**: order numbers, PAN, part codes, பெயர்களை keyword search அல்லது database lookup வச்சு கண்டுபிடிக்கிறது நல்லது.
- **ரொம்ப சின்ன collections**, 30 FAQs மாதிரி: keyword matching அல்லது எல்லாத்தையும் prompt-ல போடுறது simple.
- **Structured filters**, "கடந்த வாரம் ₹5,000-க்கு மேல இருக்குற orders" மாதிரி: ஒரு SQL query similarity-ஐ விட நல்லது.

## Demo-ல இருந்து production-க்கு

- **ஒரு golden query set-ஐ வச்சிருங்க**, ஒவ்வொரு model அல்லது setting மாற்றத்துக்கும் hit rate-ஐ rerun பண்ணுங்க.
