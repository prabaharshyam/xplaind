## இது என்ன

LangGraph ஒரு open-source Python, JavaScript framework. Agents-ஐயும் multi-step AI workflows-ஐயும் **graphs**-ஆ build பண்ண இது உதவுது. ஒரு graph-க்கு நாலு பகுதிகள்:

- **State**: run-க்கு தெரிஞ்ச எல்லாத்தையும் வச்சிருக்குற ஒரு typed dictionary, உதாரணமா messages, ticket id, propose பண்ண ஒரு credit.
- **Nodes**: state-ஐ படிச்சு, அவை மாத்துற fields-ஐ மட்டும் திருப்பி குடுக்குற functions. ஒரு node ஒரு model-ஐ call பண்ணலாம், ஒரு tool-ஐ call பண்ணலாம், இல்லைன்னா plain code ஓட்டலாம்.
- **Edges**: அடுத்து எந்த node ஓடணும். ஒரு **conditional edge**-னா state-ஐ படிச்சு அடுத்த node-ஓட பேரை திருப்பி குடுக்குற ஒரு function.
- **Checkpointer**: ஒவ்வொரு step-க்கு அப்புறமும் state-ஐ ஒரு `thread_id` கீழ save பண்ணும். அதனால ஒரு run pause ஆகலாம், resume ஆகலாம், restart ஆனாலும் தப்பிக்கலாம், replay பண்ணலாம்.

ஒரு agent loop-னா ஒரு சின்ன graph: ஒரு model node, ஒரு tool node, model tools கேக்குறதை நிறுத்துற வரை ரெண்டுக்கும் நடுவுல loop பண்ற ஒரு conditional edge. ஒரு workflow-னா fixed edges இருக்குற ஒரு graph. LangGraph ரெண்டையும் ஒரே system-ல கலக்க விடுது.

இந்த lesson ஒரே graph-ஐ ஆரம்பத்துல இருந்து முடிவு வரை build பண்ணுது. Chennai-ல ஒரு broadband provider-க்கு support tickets வருது. Billing tickets-ல service இல்லாத நாட்களுக்கு ஒரு credit கிடைக்கலாம், ஒவ்வொரு credit-உம் billing system-க்கு போறதுக்கு முன்னாடி ஒரு supervisor அதை approve பண்ணணும்.

```flow
title: Support-ticket graph (ஒவ்வொரு step-க்கு அப்புறமும் state save ஆகும், ஒவ்வொரு thread_id-க்கும் தனியா)
START -> classify
classify -[billing]-> billing_agent | outage நாட்களை பார்த்து, ஒரு credit-ஐ propose பண்ணும்
classify -[outage]-> outage_agent
billing_agent -[credit zero மேல]-> approve_credit | interrupt: ஒரு supervisor முடிவு பண்றாங்க
billing_agent -[credit இல்லை]-> reply
approve_credit -[approve ஆச்சு]-> apply_credit | billing system-ஐ ஒரே ஒரு தடவை call பண்ணும்
approve_credit -[reject ஆச்சு]-> reply
apply_credit -> reply
outage_agent -> END
reply -> END
```

### முழு graph

மேல இருந்து கீழ வரை ஒரு தடவை படிங்க. Model-க்கும் billing system-க்கும் பதிலா சின்ன stand-ins இருக்கு, அதனால API key இல்லாமலே இது ஓடும். இதை `ticket_graph.py`-ஆ save பண்ணுங்க; அடுத்து வர்ற blocks இதோட பேர்களை use பண்ணுது.

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Ticket(TypedDict, total=False):
    messages: Annotated[list, add_messages]  # reducer: new messages are appended
    ticket_id: str
    category: str              # "billing" or "outage"
    outage_days: int
    proposed_credit_inr: int
    approved_credit_inr: int   # 0 means the supervisor said no
    credit_ref: str

# Stand-ins for real systems, so the graph runs with no API key.
OUTAGE_DAYS = {"TKT-4471": 3}     # the network status tool
CREDITS = {}                      # the billing system, keyed by idempotency key

def add_credit(key: str, amount_inr: int) -> str:
    return CREDITS.setdefault(key, f"CR-{len(CREDITS) + 1:04d}")  # same key, one credit

def classify(state: Ticket) -> dict:
    text = state["messages"][-1].content.lower()   # a model call in real life
    return {"category": "billing" if "bill" in text else "outage"}

def route_ticket(state: Ticket) -> str:
    return "billing_agent" if state["category"] == "billing" else "outage_agent"

def billing_agent(state: Ticket) -> dict:
    days = OUTAGE_DAYS.get(state["ticket_id"], 0)
    return {"outage_days": days, "proposed_credit_inr": min(days * 100, 500)}

def outage_agent(state: Ticket) -> dict:
    return {"messages": [("ai", "There is a fibre cut in your area. We will update you by 6 pm.")]}

def approve_credit(state: Ticket) -> dict:
    decision = interrupt({                          # the run pauses here
        "ticket_id": state["ticket_id"],
        "proposed_credit_inr": state["proposed_credit_inr"],
        "reason": f"{state['outage_days']} days without service",
    })
    # On resume this node runs again from the top, and interrupt() returns the decision.
    return {"approved_credit_inr": decision["credit_inr"] if decision["approved"] else 0}

def apply_credit(state: Ticket) -> dict:
    ref = add_credit(key=state["ticket_id"], amount_inr=state["approved_credit_inr"])
    return {"credit_ref": ref}

def reply(state: Ticket) -> dict:
    amount = state.get("approved_credit_inr", 0)
    text = (f"We have added a ₹{amount} credit to your next bill (ref {state['credit_ref']})."
            if amount else "We checked your account. No credit applies this time.")
    return {"messages": [("ai", text)]}

g = StateGraph(Ticket)
for node in (classify, billing_agent, outage_agent, approve_credit, apply_credit, reply):
    g.add_node(node)                                # the node is named after the function
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route_ticket, ["billing_agent", "outage_agent"])
g.add_conditional_edges("billing_agent",
    lambda s: "approve_credit" if s["proposed_credit_inr"] > 0 else "reply",
    ["approve_credit", "reply"])
g.add_conditional_edges("approve_credit",
    lambda s: "apply_credit" if s["approved_credit_inr"] > 0 else "reply",
    ["apply_credit", "reply"])
g.add_edge("apply_credit", "reply")
g.add_edge("outage_agent", END)
g.add_edge("reply", END)
app = g.compile(checkpointer=InMemorySaver())
```

Credit policy (service இல்லாத ஒவ்வொரு நாளுக்கும் ₹100, அதிகபட்சம் ₹500) இந்த lesson-க்கான ஒரு உதாரணம் தான், எந்த உண்மையான provider-ஓட rule-உம் இல்ல. ஒரு real system-ல, `classify` ஒரு label-ஐ திருப்பி குடுக்குற ஒரு model call-ஆ இருக்கும், `billing_agent` ஒரு சின்ன model-and-tool loop-ஆ இருக்கும் (கீழ இருக்குற prebuilt agent-ஐ பாருங்க). ஒவ்வொரு `add_conditional_edges` call-ஓட கடைசியில இருக்குற list, route திருப்பி குடுக்கக்கூடிய nodes-ஓட பேர்களை சொல்லுது. `app.get_graph().draw_mermaid()` graph-ஐ ஒரு Mermaid diagram-ஆ print பண்ணும்; edges நீங்க நினைச்ச மாதிரி இருக்கான்னு வேகமா check பண்ண இது ஒரு வழி.

### State updates எப்படி merge ஆகுது

ஒரு node அது மாத்துற fields-ஐ மட்டும் திருப்பி குடுக்கும், LangGraph அதை state-ல merge பண்ணும். பெரும்பாலான fields-க்கு, புது value பழைய value-ஐ replace பண்ணும். ஒரு **reducer** இருக்குற field, உதாரணமா `add_messages` இருக்குற `messages`, replace ஆகாம combine ஆகும்: புது messages கடைசியில சேரும். அதனால தான் `reply` ஒரே ஒரு message-ஐ திருப்பி குடுத்தாலும் customer-ஓட message அப்படியே இருக்கு. Reducer-ஐ மறந்தா, `messages`-ல எழுதுற ஒவ்வொரு node-உம் conversation-ஐ அழிச்சுடும். ஆரம்பத்துல வர்ற bugs-லயே இது தான் ரொம்ப common.

### Pause, approve, resume

ஒவ்வொரு run-உம் ஒரு thread-ஐ குறிப்பிடுது. இங்க thread-னா ticket தான், அதனால TKT-4471 பத்தின எல்லாமே ஒரே இடத்துல இருக்கும்:

```python
config = {"configurable": {"thread_id": "TKT-4471"}, "recursion_limit": 20}
first = {"ticket_id": "TKT-4471",
         "messages": [("user", "Net was down 3 days. Why is my bill the full ₹799?")]}
out = app.invoke(first, config)
print(out["__interrupt__"][0].value)
# {'ticket_id': 'TKT-4471', 'proposed_credit_inr': 300, 'reason': '3 days without service'}

# Hours later, the supervisor's dashboard resumes the same thread:
out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
print(out["messages"][-1].content)
# We have added a ₹300 credit to your next bill (ref CR-0001).
```

Approval-ஐ safe ஆக்குற மூணு rules:

- **Resume ஆகும்போது node திரும்ப ஓடும்.** LangGraph `interrupt()`-க்கு அடுத்த line-ல இருந்து தொடராது; அது `approve_credit`-ஐ அதோட முதல் line-ல இருந்து திரும்ப ஓட்டும், இந்த தடவை `interrupt()` முடிவை திருப்பி குடுக்கும். ஒரு test-ல, `interrupt()`-க்கு முன்னாடி வச்ச ஒரு counter ரெண்டு தடவை ஏறுச்சு. அதனால `interrupt()`-க்கு முன்னாடி இருக்குற எதுக்கும் side effects இருக்கக்கூடாது.
- **Action-ஐ அடுத்த node-ல வைங்க.** Credit `approve_credit`-ல இல்ல, `apply_credit`-ல தான் apply ஆகுது. அந்த node ticket id-ஐ ஒரு idempotency key-ஆ use பண்ணுது, அதனால அது ரெண்டு தடவை ஓடினாலும் customer-க்கு ஒரே ஒரு credit தான் கிடைக்கும்.
- **Supervisor edit பண்ணலாம்.** Resume value-னா உங்க dashboard அனுப்புற எதுவோ அது தான். `{"approved": True, "credit_inr": 250}` அனுப்பினா ₹250 apply ஆகும்.

Checkpointer இல்லைன்னாலும் `interrupt()` run-ஐ நிறுத்தும், ஆனா `Command(resume=...)` "Cannot use Command(resume=...) without checkpointer"-னு fail ஆகும். `compile(interrupt_before=["apply_credit"])`-உம் pause பண்ணும், ஆனா ஒரு node-க்குள்ள `interrupt()` வச்சா supervisor-க்கு தேவையான data-வை மட்டும் சரியா அனுப்ப முடியும்.

### Checkpoints: inspect, replay, fork

ஒவ்வொரு step-உம் save ஆகுறதால, ஒரு thread-ஓட history-ஐ படிக்கலாம், ரொம்ப புதுசானது முதல்ல:

```python
for snap in app.get_state_history(config):
    print(snap.metadata["step"], snap.next, snap.values.get("credit_ref"))
```

"Agent ₹200 propose பண்ணியிருந்து, supervisor வேண்டாம்னு சொல்லியிருந்தா என்ன ஆகும்?"-னு கேக்க, approval-க்கு சரியா முன்னாடி இருக்குற checkpoint-ல இருந்து fork பண்ணுங்க:

```python
past = next(s for s in app.get_state_history(config) if s.next == ("approve_credit",))
fork = app.update_state(past.config, {"proposed_credit_inr": 200})
out = app.invoke(None, fork)                       # runs on and pauses again, now at ₹200
out = app.invoke(Command(resume={"approved": False}), config)
print(out["messages"][-1].content)
# We checked your account. No credit applies this time.
```

`invoke(None, ...)`-னா "புது input இல்லாம இந்த checkpoint-ல இருந்து தொடரு". Fork தான் latest state ஆகும்; original steps history-ல அப்படியே இருக்கும்.

### ஒரு database checkpointer

`InMemorySaver` ஒரே Python process-க்குள்ள தான் இருக்கும். ஒரு restart அல்லது deploy ஆனா pause ஆன எல்லா tickets-உம் போயிடும். Production-ல checkpoints-ஐ Postgres-ல store பண்ணுங்க, saver-ஐ ஒவ்வொரு request-க்குள்ளயும் இல்லாம, server start ஆகும்போது ஒரு தடவை create பண்ணுங்க:

```python
# pip install "langgraph-checkpoint-postgres==3.2.1" "psycopg[binary,pool]"
import os
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver

pool = ConnectionPool(os.environ["CHECKPOINT_DB_URL"],
                      kwargs={"autocommit": True, "prepare_threshold": 0}, open=True)
saver = PostgresSaver(pool)
saver.setup()                       # creates the checkpoint tables if missing
app = g.compile(checkpointer=saver)
```

அந்த ரெண்டு connection settings, `PostgresSaver.from_conn_string` use பண்ற settings-ல ரெண்டு (row factory-ஐ saver தானே set பண்ணிக்கும்). அந்த helper ஒரு `with` block, அதோட முடிவுல connection-ஐ close பண்ணிடும்; ஒரு script-க்கு அது சரி, ஒரு web server-க்கு சரி இல்ல. Connection string-ஐ ஒரு environment variable-ல வைங்க, shutdown-ல `pool.close()`-ஐ call பண்ணுங்க.

இந்த saver வச்சு, நாங்க TKT-4471-ஐ ஒரு process-ல pause பண்ணி, அந்த process-ஐ முடிச்சு, ஒரு புது process-ல இருந்து approve பண்ணோம்: thread அப்பவும் `approve_credit`-ல காத்துட்டு இருந்துச்சு, சாதாரணமா முடிஞ்சுது.

**Crash-உம் pause-உம் வேற வேற.** நாங்க `apply_credit`-க்குள்ள இருக்கும்போது process-ஐ kill-உம் பண்ணோம். Thread-ஐ எதுவும் தானா restart பண்ணல. ஒரு புது process அதை `approve_credit`-ல கண்டுபிடிச்சுது, ஏன்னா default mode ஒவ்வொரு step-ஐயும் background-ல save பண்ணும், கடைசி step இன்னும் எழுதப்படல. `app.invoke(None, config)` save ஆன முடிவோட `approve_credit`-ஐ திரும்ப ஓட்டுச்சு, அப்புறம் `apply_credit`, `reply`. `invoke`-க்கு `durability="sync"` குடுத்தா, அடுத்த step ஆரம்பிக்கிறதுக்கு முன்னாடி ஒவ்வொரு step-உம் save ஆகும், அதனால அப்போ thread `apply_credit`-லயே காத்திருந்துச்சு. இதுல இருந்து ரெண்டு பாடங்கள்: கடைசியா save ஆன step-க்கு அப்புறம் இருக்குற ஒரு node ரெண்டு தடவை ஓடலாம், அதனால side effects-ஐ idempotent ஆக்குங்க; முடியாம நிக்குற threads-ஐ தொடர ஒரு சின்ன job உங்களுக்கு வேணும்.

### Progress-ஐ stream பண்றது

ஒவ்வொரு step நடக்கும்போதே பார்க்க `invoke`-க்கு பதிலா `stream`-ஐ use பண்ணுங்க:

```python
demo = {"configurable": {"thread_id": "TKT-4471-demo"}, "recursion_limit": 20}
for update in app.stream(first, demo, stream_mode="updates"):
    print(update)
# {'classify': {'category': 'billing'}}
# {'billing_agent': {'outage_days': 3, 'proposed_credit_inr': 300}}
# {'__interrupt__': (Interrupt(value={...}, ...),)}
```

ஒவ்வொரு item-உம் ஒரு node-ஓட update, அதனால ஒரு chat screen நீண்ட அமைதிக்கு பதிலா "Checking your connection…"-னு காட்டலாம்.

### Model இல்லாம test பண்றது

Routes-உம் nodes-உம் plain functions, அதனால பெரும்பாலான tests-க்கு model-ஏ தேவையில்ல:

```python
def test_billing_ticket_goes_to_billing_agent():
    assert route_ticket({"category": "billing"}) == "billing_agent"

def test_credit_waits_for_approval_then_applies():
    config = {"configurable": {"thread_id": "test-1"}, "recursion_limit": 20}
    out = app.invoke({"ticket_id": "TKT-4471",
                      "messages": [("user", "Why is my bill the full amount?")]}, config)
    assert out["__interrupt__"][0].value["proposed_credit_inr"] == 300
    out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
    assert out["credit_ref"].startswith("CR-")
```

Model-ஐ call பண்ற nodes-க்கு, fixed replies இருக்குற ஒரு fake model-ஐ குடுங்க, அப்புறம் save பண்ணி வச்ச சில real tickets-ஐ CI-ல முழு graph வழியா ஓட்டுங்க.

### Prebuilt agent

பழைய tutorials `langgraph.prebuilt.create_react_agent`-ஐ use பண்ணுது. LangGraph 1.0-ல இருந்து அது deprecated: அதை call பண்ணா அது "has been moved to `langchain.agents`"-னு warn பண்ணும். இப்போதைய prebuilt model-and-tools loop LangChain-ஓட `create_agent`, அது LangGraph மேல ஓடுது:

```python
# pip install "langchain==1.5.2" plus your model provider's package
from langchain.agents import create_agent

def outage_days(ticket_id: str) -> int:
    """Days without service on this ticket's connection."""
    return OUTAGE_DAYS.get(ticket_id, 0)

billing_helper = create_agent(chat_model, tools=[outage_days],
                              system_prompt="You answer broadband billing questions.")
out = billing_helper.invoke({"messages": [("user", "Ticket TKT-4471: why is my bill high?")]})
```

`chat_model`-னா tool calling-ஐ support பண்ற எந்த LangChain chat model-உம். Result ஒரு compiled graph, அதனால அது இன்னும் பெரிய ஒரு graph-ஓட ஒரு node-ஆ இருக்கலாம். அது தான் **sub-graph**. ஒரு plain tool loop-க்கு `create_agent`-ல ஆரம்பிங்க. Routing, approvals அல்லது பல specialists தேவைப்படும்போது உங்க சொந்த `StateGraph`-ஐ எழுதுங்க.

### ஒவ்வொரு run-க்கும் limit வைங்க

`recursion_limit` ஒரு run-ல இருக்குற steps-ஓட எண்ணிக்கையை cap பண்ணுது. ஒரு run அதை தொட்டா, LangGraph `GraphRecursionError`-ஐ raise பண்ணும்; அதை catch பண்ணி ஒரு ஆள்கிட்ட handover-ஆ மாத்தலாம். ஒவ்வொரு call-லயும் அதை நீங்களே set பண்ணுங்க: default LangGraph 1.0.5 வரை 25, 1.0.6-ல இருந்து 1.1.3 வரை 10,000, 1.1.4-ல இருந்து (1.2.24 உட்பட) 10,007. அதனால தன்னையே திருப்தி படுத்திக்கவே முடியாத ஒரு draft-and-check loop, default அதை நிறுத்துறதுக்கு முன்னாடி ஆயிரக்கணக்கான model calls பண்ணலாம்.

### Basics-க்கு அப்பால

- **Parallel branches.** ஒரு conditional edge பல `Send("node", data)` objects-ஐ திருப்பி குடுத்து ஒரே node-ஐ பல தடவை parallel-ஆ ஓட்டலாம், உதாரணமா பத்து connections-ஐ ஒரே நேரத்துல check பண்றது; ஒரு reducer results-ஐ merge பண்ணும்.
- **Long-term memory.** Checkpoints ஒரு thread-க்கு மட்டும் சொந்தம். "Tamil-ல பேச விரும்புறாங்க" மாதிரி, ஒரு customer கூடவே எல்லா tickets-லயும் போக வேண்டிய facts, `compile(store=...)`-ஓட குடுக்குற ஒரு **store**-ல போகணும், உதாரணமா `InMemoryStore` அல்லது ஒரு Postgres store.
- **Functional API.** `langgraph.func`-ல இருக்குற `@entrypoint`-உம் `@task`-உம், graph வரையாமலே சாதாரண Python functions-க்கு checkpoints-ஐயும் interrupts-ஐயும் குடுக்கும்.
- **Tracing.** `LANGSMITH_TRACING=true`-உம் ஒரு LangSmith API key-உம் இருந்தா, ஒவ்வொரு node-ஓட input-உம் output-உம் record ஆகும், அதனால "bot ஏதோ வித்தியாசமா சொல்லுச்சு"-ங்குறது நீங்க திறக்கக்கூடிய ஒரு link ஆகிடும்.

**எல்லா பகுதிகளும் ஒரே பார்வையில:**

| பகுதி | Ticket graph-ல | Gotcha |
| --- | --- | --- |
| Reducer இருக்குற state | `messages` `add_messages`-ஐ use பண்ணுது | Reducer இல்லைன்னா, ஒவ்வொரு reply-உம் history-ஐ அழிச்சுடும் |
| Conditional edge | `route_ticket`-உம் ரெண்டு lambdas-உம் | அதோட possible nodes list-ல இருக்குற ஒரு பேரை தான் திருப்பி குடுக்கணும் |
| Checkpointer | `InMemorySaver`, அப்புறம் `PostgresSaver` | In memory-னா restart-ல pause ஆன tickets போயிடும் |
| `interrupt()` | `approve_credit`-க்குள்ள | Resume-ல node அதோட முதல் line-ல இருந்து திரும்ப ஓடும் |
| Idempotency key | `add_credit`-ல ticket id | இது இல்லைன்னா, ஒரு rerun ரெண்டாவது credit-ஐ apply பண்ணும் |
| `recursion_limit` | ஒவ்வொரு config-லயும் 20 | Default இப்போ உங்களை காப்பாத்த முடியாத அளவுக்கு ரொம்ப அதிகம் |

## ஒரு worked example

Chennai-ல TKT-4471 ticket வருது: "Net was down 3 days. Why is my bill the full ₹799?" Checkpointer என்ன save பண்ணுச்சுன்னு table காட்டுது; மேல இருக்குற code-ஓட ஒரு real run-ல இருந்து `get_state_history` வச்சு படிச்சது.

| Step | அடுத்த node | State-ல என்ன மாறுச்சு |
| --- | --- | --- |
| 0 | classify | Customer-ஓட message-உம் `ticket_id`-உம் உள்ள வந்தாச்சு |
| 1 | billing_agent | `category` = billing |
| 2 | approve_credit | `outage_days` = 3, `proposed_credit_inr` = 300. Run இங்க pause ஆகும், dashboard proposal-ஐ காட்டும் |
| 3 | apply_credit | Supervisor approve பண்ணதுக்கு அப்புறம்: `approved_credit_inr` = 300 |
| 4 | reply | `credit_ref` = CR-0001 |
| 5 | (முடிஞ்சது) | Reply message சேர்ந்தது; இப்போ ரெண்டு messages இருக்கு |

மூணு விஷயங்களை கவனிங்க. Pause-க்குன்னு தனியா checkpoint எதுவும் சேரல: step 2 அடுத்த node `approve_credit`-னு மட்டும் சொல்லுது. Approval-உம் side effect-உம் தனித்தனி steps, அதனால `approve_credit` திரும்ப ஓடினாலும் அதால ஒரு credit-ஐ apply பண்ண முடியாது. ஒரு auditor கேக்கக்கூடிய ஒவ்வொரு value-உம் (ஏன் ₹300, எந்த credit reference) ஒரு prompt-க்குள்ள மறைஞ்சு இல்லாம, save ஆன ஒரு state-ல இருக்கு.

அதே ticket-ல ரெண்டு variations:

- **Supervisor reject பண்றாங்க.** `approve_credit`-க்கு அப்புறம் route நேரா `reply`-க்கு போகும், `apply_credit` ஓடவே ஓடாது, credit எதுவும் இல்லைன்னு customer-க்கு சொல்லப்படும்.
- **ஒரு வாரம் கழிச்சு customer complain பண்றாங்க.** நீங்க TKT-4471 thread-ஐ திறந்து, ஒவ்வொரு step-ஐயும் படிச்சு, original history-ஐ தொடாமலே, வேற credit குடுத்திருந்தா என்ன ஆயிருக்கும்னு test பண்ண step 2-ல இருந்து fork பண்ணலாம்.

## பொதுவா பண்ற தப்புகள்

- **ஒரே பெரிய node.** Classify பண்றது, look up பண்றது, approve பண்றது, reply பண்றது எல்லாத்தையும் ஒரே function-ல வச்சா, ஒரு graph-ஓட முக்கிய பயனான visibility, testability, safe pause points எல்லாம் போயிடும்.
- **`interrupt()`-க்கு முன்னாடி side effects.** Resume-ல node மேல இருந்து திரும்ப ஓடும், அதனால அங்க வச்ச ஒரு SMS, email அல்லது credit ரெண்டு தடவை நடக்கும்.
- **Idempotent இல்லாத actions.** Resumes-உம் crash recovery-உம் ஒரு node-ஐ திரும்ப ஓட்டலாம். ஒவ்வொரு payment, credit அல்லது message API-க்கும் ticket id மாதிரி ஒரு idempotency key-ஐ குடுங்க.
- **Production-ல in-memory checkpoints.** ஒவ்வொரு restart அல்லது deploy-லயும் pause ஆன runs-உம் conversations-உம் போயிடும். ஒரு database checkpointer use பண்ணி, அதை backup பண்ணுங்க.
- **ஒவ்வொரு message-க்கும் புது `thread_id`.** அப்போ assistant ஒவ்வொரு தடவையும் conversation-ஐ மறந்துடும். ஒரு conversation-க்கு அல்லது ஒரு ticket-க்கு ஒரு thread use பண்ணுங்க, ரெண்டு customers-க்கு நடுவுல ஒரு thread-ஐ எப்பவுமே share பண்ணாதீங்க.
- **Limit இல்லாம வளர்ற state.** ஒவ்வொரு tool result-ஐயும் எப்பவும் சேர்த்துட்டே இருந்தா prompts நீளமாவும் செலவாவும் ஆகும். ஒரு node-ல trim பண்ணுங்க அல்லது summarise பண்ணுங்க.
- **Default `recursion_limit`-ஐ நம்புறது.** 1.2.24-ல அது 10,007 steps. ஒரு சின்ன limit-ஐ set பண்ணி, `GraphRecursionError`-ஐ catch பண்ணுங்க.
- **பழைய tutorials-ஐ copy பண்றது.** நிறைய tutorials இன்னும் deprecated ஆன `create_react_agent`-ஐயோ, இப்போ `InMemorySaver`-க்கு ஒரு alias-ஆ இருக்குற `MemorySaver`-ஐயோ use பண்ணுது. Versions-ஐ pin பண்ணுங்க, upgrade பண்றதுக்கு முன்னாடி changelog-ஐ படிங்க.

## LangGraph தேவையில்லாத நேரங்கள்

- **ஒரு simple tool loop**: agent-loop lesson-ல இருக்குற சின்ன loop, `create_agent`, அல்லது ஒரு model provider-ஓட சொந்த agent SDK போதுமா இருக்கலாம்.
- **Pauses-உம் branching-உம் இல்லாத ஒரு fixed pipeline**: வரிசையா call பண்ற சாதாரண functions படிக்கவும் debug பண்ணவும் இன்னும் ஈஸி.
- **ஏற்கனவே வேற ஒரு framework-ல இருக்குற ஒரு team**, அந்த framework saved state, pauses, tracing-ஐ cover பண்ணா.

ஒவ்வொரு conversation-க்கும் saved state, ஆளுங்களுக்காக pauses, branching, ஒரு run-ஐ inspect பண்ணி replay பண்ற வசதி இதெல்லாம் தேவைப்படும்போது தான் LangGraph-க்கு அர்த்தம் இருக்கு.

## Demo-ல இருந்து production-க்கு

- **ஒரு database checkpointer use பண்ணுங்க**, start-up-ல ஒரு தடவை create பண்ணி, மத்த production data மாதிரியே அதையும் backup பண்ணுங்க.
- **Durability-ஐ யோசிச்சு தேர்ந்தெடுங்க.** Default background-ல save பண்ணும்; `durability="sync"` ஒவ்வொரு அடுத்த step-க்கும் முன்னாடி save பண்ணும், payments, credits பக்கத்துல அந்த extra நேரம் worth தான்.
- **மாட்டிக்கிட்ட threads-ஐ recover பண்ணுங்க.** Crash-க்கு அப்புறம் பாதியில நின்ன threads-ஐ கண்டுபிடிச்சு, `invoke(None, config)` வச்சு அவற்றை தொடர்ற ஒரு சின்ன job-ஐ ஓட்டுங்க.
- **ஒவ்வொரு run-லயும் `recursion_limit`-உம் ஒரு timeout-உம் set பண்ணுங்க**, `GraphRecursionError`-ஐ ஒரு ஆள்கிட்ட handover-ஆ மாத்துங்க.
- **Graph-ஐ version பண்ணுங்க.** Pause ஆன ஒரு thread, அப்போ எந்த graph deploy ஆகியிருக்கோ அதுல தான் resume ஆகும். புது state fields-ஐ optional-ஆ சேருங்க, pause ஆன threads காத்திருக்கக்கூடிய ஒரு node-ஐ rename-ஓ remove-ஓ பண்ணாதீங்க. ஒரு breaking change-க்கு, பழைய graph-ஓட pause ஆன threads முடியுற வரை அதை ஓட விடுங்க, இல்லைன்னா அவற்றை முதல்ல approve அல்லது cancel பண்ணுங்க.
- **ஒவ்வொரு node-ஐயும் thread id-ஓட trace பண்ணுங்க**, அப்போ ஒரு support ticket நேரா அதோட run-க்கு கூட்டிட்டு போகும்.
- **Routes, nodes, சில முழு tickets-ஐ** fake models வச்சு CI-ல test பண்ணுங்க.

## Practice பண்ணுங்க

LangChain Academy-ஓட free Introduction to LangGraph-ஐ எடுங்க, குறைஞ்சது முதல் மூணு modules.

1. மேல இருக்குற ticket graph-ஐ நீங்க தேர்ந்தெடுக்குற ரெண்டு categories-க்கு திரும்ப build பண்ணுங்க, model தேவையில்லாத routing tests-ஓட.
2. அதே `thread_id`-ல ரெண்டாவது message அனுப்பி, state-ல முதல் message இன்னும் இருக்குன்னு காட்டுங்க.
3. `interrupt()`-க்கு முன்னாடி ஒரு counter வச்சு அது ரெண்டு தடவை ஓடுறதை பாருங்க; அப்புறம் side effect-ஐ அடுத்த node-க்கு மாத்தி ஒரு idempotency key சேருங்க.
4. `PostgresSaver` வச்சு ஒரு run-ஐ pause பண்ணி, உங்க Python process-ஐ நிறுத்தி, ஒரு புது process-ல இருந்து அதை approve பண்ணுங்க.
5. முடிஞ்ச ஒரு thread-ஐ approval-க்கு முந்தைய step-ல இருந்து `update_state` வச்சு fork பண்ணி, வேற ஒரு முடிவோட resume பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க graph-ஐ வரைய முடியும், state எங்க save ஆகுதுன்னு காட்ட முடியும், approval node ஏன் திரும்ப ஓடுதுன்னு explain பண்ண முடியும், உங்க program-ஐ restart பண்ணதுக்கு அப்புறம் pause ஆன ஒரு run-ஐ resume பண்ண முடியும்.
