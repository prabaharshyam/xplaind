## இது என்ன

**Tool calling** (function calling-ன்னும் சொல்லுவாங்க) ஒரு model உங்க code-ஐ use பண்ண விடும். Tools-ஓட பேர்கள், அவை என்ன பண்ணும், என்ன inputs எடுக்கும்னு model-க்கு விவரிப்பீங்க. ஒரு கேள்விக்கு ஒரு tool தேவைப்படும்போது, model அதை குறிப்பிட்ட arguments-ஓட call பண்ணச் சொல்லி ஒரு request-ஓட பதில் சொல்லும். உங்க code tool-ஐ ஓட்டி, result-ஐ திருப்பி அனுப்பும், model அதை வச்சு பதில் சொல்லும்.

Model தானா எதையும் ஓட்டாது. Control எப்பவும் உங்க code-கிட்டயே.

```flow
title: Model தானா எதையும் ஓட்டாது: control உங்க code-கிட்டயே இருக்கும்
1. உங்க app user message-ஐயும் tool list-ஐயும் அனுப்புது -> 2. Model கேக்குது: tool_use get_order_status | order_id
2. Model கேக்குது: tool_use get_order_status -> 3. உங்க app arguments-ஐ validate பண்ணி, உண்மையான function-ஐ ஓட்டுது
3. உங்க app arguments-ஐ validate பண்ணி, உண்மையான function-ஐ ஓட்டுது -> 4. tool_result | "Shipped 3 Nov, out for delivery"
4. tool_result -> 5. Model final answer தருது, அல்லது இன்னொரு tool_use
```

இந்த lesson-ல Gurugram-ல இருக்குற ஒரு fashion e-commerce site தன் support chat-ல order tools-ஐ சேர்க்குறதை follow பண்றோம்.

## இது எப்படி work ஆகுது

**Tool-ஐ விவரிங்க.** ஒவ்வொரு tool-க்கும் ஒரு பேர், ஒரு description, ஒரு input schema இருக்கும்:

```python
tools = [{
    "name": "get_order_status",
    "description": "Look up an order's status and expected delivery date by order id. "
                   "Use when the customer asks where their order is.",
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "Like ORD-12345678"}},
        "required": ["order_id"],
    },
}]
```

எப்போ ஒரு tool-ஐ call பண்ணணும்னு model முக்கியமா அதோட **பேர், description**-ஐ வச்சு முடிவு பண்ணும், arguments-ஐ schema-ல இருந்து நிரப்பும். தெளிவான, குறிப்பிட்ட descriptions தான் எல்லாத்தையும் விட முக்கியம்.

**Round trip.**

1. User-ஓட message-ஐயும் tool list-ஐயும் அனுப்புங்க.
2. Model ஒரு tool-use request-ஓட பதில் சொல்லும், உதாரணம் `get_order_status`, `{"order_id": "ORD-48213907"}`-ஓட.
3. உங்க code arguments-ஐ validate பண்ணி, உண்மையான function-ஐ ஓட்டி, ஒரு result-ஐ பெறும்.
4. அந்த request-ஓட link ஆன ஒரு tool-result message-ல result-ஐ திருப்பி அனுப்புங்க.
5. Model final answer-ஐ எழுதும், அல்லது இன்னொரு tool கேக்கும்.

**Errors-உம் results தான்.** Order இல்லன்னா அல்லது ஒரு service down-னா, tool result-ஆ ஒரு தெளிவான error message-ஐ திருப்பி அனுப்புங்க ("ORD-48213907 id-ல order எதுவும் கிடைக்கல; customer-ஐ id-ஐ check பண்ண சொல்லுங்க"). அப்போ model யூகிக்காம, recover ஆகலாம், user-கிட்ட கேக்கலாம், அல்லது மன்னிப்பு கேக்கலாம்.

**Safety.** எதையும் ஓட்டுறதுக்கு முன்னாடி arguments-ஐ validate பண்ணுங்க. Read-only tools-ஐயும் எதையாவது மாத்துற tools-ஐயும் பிரிங்க, risky actions-க்கு confirmation கேளுங்க. Tool results-ஐ data-வா நடத்துங்க, instructions-ஆ இல்ல.

**Server-side tools.** சில providers தாங்களே ஓட்டுற tools-ஐயும் (web search மாதிரி) offer பண்ணுவாங்க. உங்க சொந்த systems-க்கு, tools-ஐ உங்க பக்கம் தான் ஓட்டுவீங்க.

**நல்ல, பலவீனமான tool definitions:**

| பகுதி | பலவீனம் | பலம் |
| --- | --- | --- |
| பேர் | `order` | `get_order_status` |
| Description | "Order API" | "Look up an order's status and delivery date by order id. Use when the customer asks where their order is." |
| Parameter | `id: string` | `order_id`, "Like ORD-12345678"-ன்னு விவரிக்கப்பட்டது |
| Error result | Empty | "No order found with id ...; ask the customer to check the id" |

**Arguments-ஐ validate பண்றது.** Model-ஓட arguments-ஐ ஒரு web form-ல வர்ற input மாதிரி நடத்துங்க. Schema படி types, formats-ஐ check பண்ணுங்க, அந்த record-ல செயல்பட user-க்கு அனுமதி இருக்கான்னு check பண்ணுங்க, மத்த எதையும் உதவுற error result-ஓட reject பண்ணுங்க. ஒரு model, வேற customer-க்கு சொந்தமான, வடிவம் சரியான id-ஐ உருவாக்கலாம்; அதனால ownership checks prompt-ல இல்ல, உங்க code-ல இருக்கணும்.

**ஒரே reply-ல பல tool calls.** Calls ஒண்ணை ஒண்ணு சார்ந்திருக்காதப்போ, உதாரணம் ஒரு order status-உம் return policy-உம், model ஒரே நேரத்துல ஒண்ணுக்கு மேல tools-ஐ கேக்கலாம். அவற்றை ஓட்டுங்க, விரும்பினா parallel-ஆ, ஒவ்வொரு request-க்கும் ஒரு result-ஐ, அந்த request id-ஓட link பண்ணி திருப்பி அனுப்புங்க. ஒரு call இன்னொண்ணோட result-ஐ சார்ந்திருந்தா, model அவற்றை தனித்தனி turns-ல கேக்கும்.

**Tools-க்கு இடையில choose பண்றது.** ரெண்டாவது அல்லது மூணாவது tool-ஐ சேர்க்கும்போது, ஒரு set realistic கேள்விகளுக்கு model எதை தேர்ந்தெடுக்குதுன்னு test பண்ணுங்க. தப்பா தேர்ந்தெடுத்தா, fix கிட்டத்தட்ட எப்பவும் descriptions-ல தான்: ஒவ்வொரு tool எப்போ பொருந்தும், எப்போ பொருந்தாதுன்னு தெளிவா சொல்லுங்க.

**மூணு வகை tools, மூணு அளவு risk.**

| வகை | உதாரணங்கள் | Risk | Rule |
| --- | --- | --- | --- |
| Read: அறிவை எடுக்க | Order status, product search, policy lookup | கம்மி-ல இருந்து நடுத்தரம்: data வெளிய வரலாம் | User பார்க்க அனுமதி இருக்கான்னு check பண்ணுங்க; தேவையான fields-ஐ மட்டும் திருப்புங்க |
| Compute: திறனை நீட்ட | Calculator, date maths, sandbox-ல code ஓட்டுறது | Sandbox-ல இருந்தா கம்மி | பணம், dates-க்கு model-ஓட arithmetic-ஐ விட tools-ஐ விரும்புங்க |
| Write: உலகத்தை மாத்த | ஒரு return ஆரம்பிக்கிறது, email அனுப்புறது, record update பண்றது, payment பண்றது | அதிகம் | Confirmation, limits, audit log; நம்பகமில்லாத text-ஐ மட்டும் வச்சு ஒருபோதும் இல்ல |

**Tool use-ஐ வழிநடத்துறது.** Default-ஆ, tool-ஐ call பண்ணலாமான்னு model முடிவு பண்ணும் (`auto`). நீங்க ஏதாவது ஒரு tool-ஐ கட்டாயமாக்கலாம் (`any`), பேர் சொன்ன ஒரு tool-ஐ கட்டாயமாக்கலாம் (structured output-க்கு உதவும்), அல்லது ஒரு turn-க்கு tools-ஐ நிறுத்தலாம் (`none`). Fixed workflows-ல tools-ஐ கட்டாயமாக்குறது வசதி; open chat-ல தெளிவான descriptions-ஓட `auto` பெரும்பாலும் நல்லா வேலை செய்யும்.

**Code-ல முழு round trip.** இது Anthropic-ஓட Python SDK-ஐ use பண்ணுது; மத்த providers-உம் இதே pattern-ஐ follow பண்ணும். Arguments Pydantic-ஆல validate ஆகுது, ownership code-ல check ஆகுது, write tool-க்கு customer-ஓட confirmation தேவை:

```python
import anthropic
from pydantic import BaseModel, Field, ValidationError

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"            # check the docs for current model names

class OrderArgs(BaseModel):
    order_id: str = Field(pattern=r"^ORD-\d{8}$")

ORDERS = {"ORD-48213907": {"customer": "c_101", "status": "Out for delivery today"}}

def get_order_status(customer_id, order_id):
    order = ORDERS.get(order_id)
    if not order or order["customer"] != customer_id:          # ownership check in code
        return f"No order {order_id} on this account; ask the customer to check the id."
    return order["status"]

def start_return(customer_id, order_id, confirmed=False):
    if not confirmed:
        return "Not started: ask the customer to confirm the return first."
    return f"Return started for {order_id}; pickup in 2 days."

TOOLS = [
    {"name": "get_order_status", "description": "Look up an order's status by order id. Use when the customer asks where an order is.",
     "input_schema": OrderArgs.model_json_schema()},
    {"name": "start_return", "description": "Start a return. Only after the customer has clearly confirmed in this chat.",
     "input_schema": OrderArgs.model_json_schema()},
]
HANDLERS = {"get_order_status": get_order_status, "start_return": start_return}

def chat_turn(customer_id, messages, confirmed=False):
    while True:
        reply = client.messages.create(model=MODEL, max_tokens=600, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": reply.content})
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return "".join(b.text for b in reply.content if b.type == "text")
        results = []
        for call in calls:                                   # one result per request, matched by id
            try:
                args = OrderArgs.model_validate(call.input)
                fn = HANDLERS[call.name]
                extra = {"confirmed": confirmed} if call.name == "start_return" else {}
                out, err = fn(customer_id, args.order_id, **extra), False
            except ValidationError:
                out, err = "Order ids look like ORD-12345678. Ask the customer for theirs.", True
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})

msgs = [{"role": "user", "content": "Where is ORD-48213907?"}]
print(chat_turn("c_101", msgs))
```

மூணு விஷயங்களை கவனிங்க. Customer id உங்க session-ல இருந்து வரும், model-ல இருந்து ஒருபோதும் இல்ல. Confirmation flag உங்க சொந்த interface-ஆல ("Yes, start the return" button) set ஆகுது, customer ஒத்துக்கிட்டாருன்னு model சொல்றதால இல்ல. தப்பான அல்லது வேற ஒருத்தரோட order id ரெண்டுக்கும் அதே மரியாதையான message தான் வரும், அதனால bot வேற யாரோட order இருக்குன்னு ஒருபோதும் உறுதி பண்ணாது. உண்மையான app-ல, agent-loop lesson காட்டுற மாதிரி `while` loop-ஐ ஒரு step limit-ஓட cap பண்ணுங்க.

**Tool set-ஐ தேர்ந்தெடுக்கிறது.** Tools அதிகம்னா abilities அதிகம், ஆனா choose பண்றது கஷ்டமாகும், descriptions context-ஐ நிரப்பும். சில பழக்கங்கள்:

- **கம்மியான tools-ஓட ஆரம்பிங்க**, ஒரு test கேள்விக்கு தேவைப்படும்போது மட்டும் ஒண்ணை சேருங்க.
- **உதவாத tools-ஐ remove பண்ணுங்க**: ஒரு tool இல்லாம success குறையலைன்னா, அதை தூக்கிடுங்க.
- **Usage-ஐ கவனிங்க**: ஒவ்வொரு tool-ஓட calls-ஐ எண்ணுங்க. ஒருபோதும் call ஆகாத tool-ஓட description மோசமா இருக்கலாம்; அடிக்கடி தப்பா call ஆகுற tool-க்கு எளிமையான design தேவைப்படலாம்.
- **எப்பவும் சேர்ந்து ஓடுற tools-ஐ merge பண்ணுங்க**, "customer-ஐ கண்டுபிடி" அப்புறம் "orders-ஐ எடு" மாதிரி, ஒண்ணா.

**MCP வழியா tools-ஐ share பண்றது.** Model Context Protocol, AI apps-க்கு tools, data-வை expose பண்ற ஒரு open standard. ஒரு tool-ஐ ஒரு தடவை MCP server-ஆ எழுதுங்க, MCP-ஐ support பண்ற எந்த app அல்லது agent-உம் அதை use பண்ணலாம். அதே rules தான்: inputs-ஐ validate பண்ணுங்க, permissions-ஐ check பண்ணுங்க, write actions-ல கவனமா இருங்க.

**Tool use-ஐ test பண்றது.** நீங்க எதிர்பார்க்குற tool, arguments-ஓட realistic கேள்விகளோட ஒரு list வச்சிருங்க, எந்த tool-உம் தேவையில்லாத கேள்விகளையும் சேர்த்து. Tools, descriptions, model-ல எது மாறினாலும் அதை ஓட்டி, தப்பான tool, தப்பான arguments, விடுபட்ட calls-ஐ எண்ணுங்க. Berkeley Function Calling Leaderboard மாதிரி public benchmarks models-ஐ இதுல ஒப்பிடும், ஆனா உங்க சொந்த கேள்விகள் தான் அதிக முக்கியம்.

## ஒரு worked example

Gurugram-ல ஒரு fashion e-commerce site தன் support chat-ல order tools-ஐ சேர்க்குது: `get_order_status`, `get_return_policy`, `start_return` (customer confirm பண்ணணும்).

ஒரு customer எழுதுறார்: "என் kurta order ORD-48213907 எங்க இருக்கு? தாமதமா இருந்தா return பண்ணணும்."

1. Model id-ஓட `get_order_status`-ஐ call பண்ணும்.
2. Code திருப்புது: "Shipped 3 Nov, out for delivery today, Gurugram hub."
3. Model order இன்னைக்கு வருதுன்னு பதில் சொல்லி, `get_return_policy`-ஐ call பண்ணி 15-நாள் return window-ஐ விளக்கும்.
4. அது `start_return`-ஐ call பண்ணாது, ஏன்னா order தாமதமா இல்ல; customer வற்புறுத்தினா, முதல்ல confirmation கேக்கும்.

ஒரு customer தப்பான id-ஐ type பண்ணா, tool ஒரு "not found" message-ஐ திருப்பும், model அவங்க confirmation SMS-ஐ check பண்ண சொல்லும்.

| Customer message | Call ஆன tools | Result |
| --- | --- | --- |
| "ORD-48213907 எங்க? தாமதமா இருந்தா return" | get_order_status, get_return_policy | இன்னைக்கு வருது; 15-நாள் return window விளக்கப்பட்டது |
| Return பண்ணணும்னு வற்புறுத்துறார் | Confirm ஆகுற வரை எதுவும் இல்ல | start_return-க்கு முன்னாடி confirmation கேக்குது |
| தப்பான order id | get_order_status "not found" திருப்புது | Confirmation SMS-ஐ check பண்ண சொல்லுது |

## பொதுவா பண்ற தப்புகள்

- **மங்கலான tool descriptions.** அப்போ model தப்பான tool-ஐயோ எதுவுமே இல்லாததையோ call பண்ணும்.
- **Arguments-ஐ validate பண்ணாம tools-ஐ ஓட்டுறது.**
- **Errors-ஐ விழுங்குறது.** அவற்றை தெளிவான tool results-ஆ திருப்புங்க.
- **Confirmation இல்லாம risky actions.**
- **Tool result-ஐ திருப்பி அனுப்ப மறக்கிறது.** அது இல்லாம model பதில் சொல்ல முடியாது.
- **Identity அல்லது ஒப்புதலை model-ஐ நம்பி எடுத்துக்கிறது.** User id-உம் "customer ஒத்துக்கிட்டாரு"ங்கிறதும் உங்க app-ல இருந்து வரணும், tool arguments-ல இருந்து இல்ல.
- **பெரிய results-ஐ திருப்புறது.** Model-க்கு தேவையான சில fields-ஐ மட்டும் திருப்புங்க; பெரிய results tokens-ஐ செலவழிக்கும், model-ஐ குழப்பும்.
- **Model-ல கூட்டல் கழித்தல் பண்றது.** Totals, discounts, dates-ஐ ஒரு tool கணக்கிடட்டும்.

## Tools தேவையில்லாத நேரங்கள்

- **பதில் prompt-லயே இருக்கு**, அல்லது ஏற்கனவே retrieve ஆன documents-ல இருக்கு.
- **ஒரு fixed step எப்பவும் ஓடும்**: உங்க code-ல function-ஐ நேரா call பண்ணி, அதோட result-ஐ prompt-ல போடுங்க.
- **உங்களுக்கு ஒரு JSON வடிவம் மட்டும் வேணும்**: structured output simple-ஆ இருக்கலாம்; ஆனா கட்டாயமாக்கப்பட்ட ஒரே tool-உம் அதை பெற ஒரு வழி.

## Demo-ல இருந்து production-க்கு

- **Tool definitions-ஐ prompt-ஓட சேர்த்து version பண்ணுங்க**, ஒவ்வொரு மாற்றத்துக்கும் tool choice-ஐ test பண்ணுங்க.
- **ஒவ்வொரு call-ஐயும் log பண்ணுங்க**: tool, arguments, result size, நேரம், errors, யாருக்காக ஓடுச்சு.
- **ஒவ்வொரு tool-க்கும் timeouts set பண்ணுங்க**, ஒண்ணு மெதுவா இருக்கும்போது தெளிவான message-ஐ திருப்புங்க.
- **Read, write tools-ஐ code-லயும் permissions-லயும் பிரிங்க**, writes-க்கு audit log வச்சிருங்க.
- **Write actions-ஐ ஒரு user-க்கும் ஒரு நாளுக்கும் rate-limit பண்ணுங்க.**

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற tool-use overview-ஐ படிங்க.

1. ஒரு model-க்கு ஒரு read-only tool-ஐ கொடுத்து (உதாரணம் ஒரு weather lookup அல்லது ஒரு சின்ன product table), code-ல முழு round trip-ஐ முடிங்க.
2. தெரியாத inputs-க்கு tool ஒரு error-ஐ திருப்ப வச்சு, model அதை handle பண்றதை காட்டுங்க.
3. ரெண்டாவது tool-ஐ சேர்த்து, அஞ்சு வேற வேற கேள்விகளுக்கு model எதை தேர்ந்தெடுக்குதுன்னு test பண்ணுங்க.
