## இது என்ன

நீங்க ஒரு language model-க்கு prompt அனுப்புறப்போ, ரெண்டு வேற வேற மாதிரி வேலை நடக்குது.

1. **Prefill.** Model உங்க prompt-ஓட ஒவ்வொரு token-ஐயும் ஒரே நேரத்துல, parallel-ஆ படிக்குது. இதை பண்ணும்போது ஒவ்வொரு token-க்கும் சில results-ஐ **KV cache**-ல சேமிச்சு வைக்குது. GPU ஒரு second-ல எவ்வளவு arithmetic பண்ண முடியும்ங்கிறது தான் Prefill-ஓட limit, அதனால நீளமான prompts-க்கு அதிக நேரம் ஆகும்.
2. **Decode.** Model reply-ஐ ஒரு தடவைக்கு ஒரு token-ஆ எழுதுது. ஒவ்வொரு token-ஐ உருவாக்கவும் அதோட எல்லா weights-ஐயும் GPU memory-ல இருந்து திருப்பி படிக்கணும், ஆனா அவற்றை வச்சு பண்ற maths ரொம்ப கொஞ்சம் தான். Memory-ல இருந்து data எவ்வளவு வேகமா வருதுங்கிறது தான் Decode-ஓட limit, computing power இல்ல.

Users உணர்றது இந்த பிரிவுனால தான். எதுவும் தெரியுறதுக்கு முன்னாடி இருக்குற காலி காத்திருப்பு பெரும்பாலும் prefill, அதை **time to first token (TTFT)**-னு அளப்பாங்க. அதுக்கப்புறம் text வர்ற வேகம் decode, அதை **time per output token (TPOT)**-னு அளப்பாங்க. கிட்டத்தட்ட:

**மொத்த நேரம் ≈ TTFT + TPOT × output tokens எண்ணிக்கை**

```flow
title: ஒரு LLM server வழியா ஒரு request
dir: LR
Prompt வருது -> Queue | GPU busy-னா காத்திருக்கும்
Queue -> Prefill | எல்லா prompt tokens-ஐயும் ஒரே நேரத்துல படிக்கும்
Prefill -> KV cache நிரம்பியாச்சு | ஒவ்வொரு token-க்கும் சேமிப்பு
KV cache நிரம்பியாச்சு -> Decode step | ஒரு புது token
Decode step -> Done? | stop token அல்லது length limit
Done? -[இல்ல]-> Decode step
Done? -[ஆமா]-> Reply முடிஞ்சது
```

## இது எப்படி work ஆகுது

**KV cache.** ஒரு transformer-ல, ஒவ்வொரு புது token-ம் attention வழியா முந்தின ஒவ்வொரு token-ஐயும் திரும்பி பார்க்குது, அதுக்கு ஒவ்வொண்ணுக்கும் ஒரு "key", ஒரு "value" vector வேணும். ஒவ்வொரு step-லயும் முழு sequence-க்கும் இவற்றை திருப்பி compute பண்றது வீணா இருக்கும், அதனால model இவற்றை store பண்ணி, ஒவ்வொரு புது token-க்கும் இன்னொரு ஜோடியை சேர்க்குது. அந்த store தான் KV cache. இது நிறைய computation-ஐ மிச்சப்படுத்தும், ஆனா GPU memory-ஐ எடுத்துக்கும், அந்த அளவு context நீளத்தோடயும் ஒரே நேரத்துல serve பண்ற requests எண்ணிக்கையோடயும் வளரும்.

எந்த special trick-உம் இல்லாம, இதோட size கிட்டத்தட்ட:

**2 × layers × model width × context tokens × batch size × bytes per number**

2 keys-க்கும் values-க்கும். *AI Engineering* book, 2,048 tokens உள்ள 32 requests-ஐ, ஒரு number-க்கு 2 bytes-ல serve பண்ற 13-billion-parameter Llama 2 model-ஐ (40 layers, width 5,120) வச்சு கணக்கு போடுது: கிட்டத்தட்ட 54 GB, model weights-ஐ விடவே அதிகம். நிறைய புது models attention heads நடுவுல keys, values-ஐ share பண்ணுது, அது இதை நிறைய குறைக்கும், ஆனா பிரச்சனையோட வடிவம் அதே தான்: நீளமான contexts-உம் நிறைய users-உம் memory-ஐ தின்னுடுது.

```python
def kv_cache_gb(layers, width, context, batch, bytes_per_value=2, kv_share=1.0):
    """kv_share < 1 for models that share keys and values across heads (for example 0.125)."""
    return 2 * layers * width * context * batch * bytes_per_value * kv_share / 1e9

def reply_seconds(ttft_s, tpot_ms, output_tokens):
    return ttft_s + tpot_ms / 1000 * output_tokens

print(round(kv_cache_gb(40, 5120, 2048, 32), 1))   # 53.7, the book's example
print(reply_seconds(1.2, 40, 300))                 # 13.2 seconds for 300 tokens
```

**Batching.** ஒரு request-ஐ decode பண்றப்போ GPU பெரும்பாலும் memory-க்காக காத்திருக்கும், அதனால அதுகிட்ட arithmetic திறன் மிச்சம் இருக்கும். நிறைய requests-ஐ சேர்த்து serve பண்ணா அந்த மிச்ச திறன் use ஆகும், **throughput** (எல்லா users-ஐயும் சேர்த்து ஒரு second-க்கு tokens) கூடும், ஒரு request-க்கான cost குறையும்.

- **Static batching** முழு batch-க்காக காத்திருக்கும். முன்னாடி வந்த requests, பின்னாடி வர்றதுக்காக காத்திருக்கும்.
- **Dynamic batching** batch நிரம்புனாலோ ஒரு சின்ன timer முடிஞ்சாலோ தொடங்கும்.
- **Continuous batching** ஒவ்வொரு step-லயும் முடிஞ்ச request-க்கு பதிலா புதுசை மாத்திடும், அதனால 20-token reply, 1,000-token reply-க்காக காத்திருக்காது. vLLM, TensorRT-LLM, Text Generation Inference மாதிரி serving engines இதை பண்ணும்.

Batching கொஞ்சம் latency-ஐ கொடுத்து நிறைய throughput-ஐ வாங்கும். முதல் token கொஞ்சம் மெதுவா வர்றதை ஏத்துக்கிட்டா throughput ரெண்டு மடங்கு, மூணு மடங்கு ஆகுதுன்னு teams சொல்றாங்க.

**Speculative decoding.** ஒரு சின்ன, வேகமான **draft** model அடுத்த சில tokens-ஐ ஊகிக்கும். Main model அவை எல்லாத்தையும் ஒரே pass-ல check பண்ணும், checking-உம் prefill மாதிரி parallel-ஆ நடக்குறதால இது மலிவு. அது ஒத்துக்குற tokens-ஐ வச்சுக்கிட்டு, தன்னோட ஒண்ணை சேர்க்கும். Output, main model எழுதியிருக்கும் அதே தான், வேகம் மட்டும் கூடுதல். Code மாதிரி ஊகிக்கக்கூடிய text-ல இது நல்லா work ஆகும். இப்படி 70-billion-parameter model-ஓட reply நேரத்தை பாதிக்கும் மேல குறைச்சதா DeepMind சொன்னாங்க.

**Prompt caching.** நிறைய requests ஒரே நீளமான instructions-ஓட தொடங்குச்சுன்னா, server அந்த பொதுவான தொடக்கத்துக்கான KV cache-ஐ வச்சுக்கிட்டு அதோட prefill-ஐ தவிர்க்கலாம். Providers cached input tokens-ஐ ரொம்ப குறைஞ்ச விலையில வைக்கிறாங்க. Prompt-ஓட fixed பகுதியை முதல்ல வைங்க.

**Batch APIs.** யாரும் காத்திருக்காத வேலைக்கு, உதாரணமா இரவு summaries-க்கு, providers கிட்டத்தட்ட பாதி விலையில batch endpoints தர்றாங்க, அவை சில மணி நேரத்துல results-ஐ திருப்பி தரும்.

| நீங்க பார்க்குற பிரச்சனை | எந்த பகுதி | உதவுற levers |
| --- | --- | --- |
| Reply-க்கு முன்னாடி நீளமான காலி காத்திருப்பு | Prefill (TTFT) | சின்ன prompts, prompt caching, குறைவான queueing, streaming |
| Reply மெதுவா stream ஆகுது | Decode (TPOT) | சின்ன அல்லது quantised model, speculative decoding, வேகமான GPU memory |
| Busy நேரத்துல மட்டும் மெதுவு | Queueing, memory | Continuous batching, அதிக replicas, concurrency limits |
| நீளமான chats-ல out-of-memory | KV cache | சின்ன context, paged அல்லது quantised KV cache, குறைவான concurrent requests |
| Offline jobs-க்கு cost அதிகம் | Throughput | Batch APIs, பெரிய batches, சின்ன models |

## ஒரு worked example

Chennai-ல ஒரு telecom company தங்க சொந்த GPU-ல 8-billion-parameter open model வச்சு support chatbot ஓட்டுறாங்க. ஒவ்வொரு request-லயும் கிட்டத்தட்ட 6,000 tokens (instructions, policies, chat history) போகுது, கிட்டத்தட்ட 250 tokens திரும்ப வருது. Users முதல் வார்த்தைக்கு கிட்டத்தட்ட 4 seconds காத்திருக்காங்க; அப்புறம் text ஒரு token-க்கு கிட்டத்தட்ட 25 ms வேகத்துல stream ஆகுது.

மொத்த நேரம் ≈ 4 + 0.025 × 250 ≈ 10 seconds. Stream நல்லா தான் இருக்கு; காலி காத்திருப்பு தான் பிரச்சனை, அது prefill.

அவங்க மூணு மாற்றங்கள் பண்றாங்க:

1. **Prompt-ஐ trim பண்றாங்க.** Bot-க்கு அரிதா தேவைப்படுற policies retrieval-க்கு போகுது, பத்து turns-க்கு அப்புறம் chat history-ஐ summarise பண்றாங்க. சராசரி prompt 2,500 tokens-ஆ குறையுது.
2. **Fixed தொடக்கத்தை cache பண்றாங்க.** 1,200-token instructions ஒவ்வொரு request-க்கும் ஒரே மாதிரி இருக்கு, அதனால அதை முதல்ல வச்சு cache பண்றாங்க.
3. **Server-ஐ continuous batching-க்கும் paged KV cache memory-க்கும் மாத்துறாங்க**, ஒரு GPU-க்கு concurrent requests-ல ஒரு cap போடுறாங்க.

| Measure | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| p50 time to first token | 4.0 s | 0.9 s |
| p95 time to first token | 7.5 s | 1.8 s |
| Busy hour-ல ஒரு GPU-க்கு requests | 6 | 20 |
| ஒரு நாளைக்கு out-of-memory errors | 40 | 0 |

இந்த numbers உதாரணத்துக்கு மட்டும், எப்படி யோசிக்கணும்ன்னு காட்ட. அவங்க இப்போ average-க்கு பதிலா **p95**-ஐயும் track பண்ண ஆரம்பிக்கிறாங்க, ஏன்னா ஒரு மாட்டிக்கிட்ட request, பெரும்பாலான users உணர்றதை விட average-ஐ ரொம்ப மோசமா காட்டிடும்.

## பொதுவா பண்ற தப்புகள்

- **நீளமான prompt-க்கு model-ஐ குத்தம் சொல்றது.** முதல் வார்த்தை காத்திருப்பு பெரும்பாலும் prefill. Hardware வாங்குறதுக்கு முன்னாடி prompt-ஐ வெட்டி, cache பண்ணுங்க.
- **Averages மட்டும் அளக்குறது.** p50, p95 use பண்ணுங்க, first-token நேரத்தை prompt நீளத்துக்கு எதிரா plot பண்ணுங்க.
- **GPU "utilisation"-ஐ மட்டும் பார்க்குறது.** GPU 100% busy-ன்னு காட்டலாம், ஆனா பெருசா பயனுள்ள வேலை பண்ணாம இருக்கலாம். Tokens per second, cost per request-ஐ track பண்ணுங்க.
- **KV cache memory-ஐ கண்டுக்காம விடுறது.** Weights சுலபமா பொருந்தினாலும், நீளமான contexts × நிறைய users GPU memory-ஐ தாண்டிடலாம்.
- **Hidden tokens உடனே வந்துடும்ன்னு நினைக்கிறது.** Reasoning, agent steps users பார்க்காத tokens-ஐ உருவாக்கும்; அவை முதல் தெரியுற வார்த்தையை தாமதப்படுத்தும்.
- **Offline jobs-க்கு online API use பண்றது.** யாரும் காத்திருக்காதப்போ Batch APIs மலிவு.

## முதல்ல எந்த lever-ஐ இழுக்கணும்

மெதுவான பகுதியை குறி வச்ச, மலிவான மாற்றத்துல இருந்து தொடங்குங்க.

- **முதல் வார்த்தை காத்திருப்பு ரொம்ப நீளம்:** prompt-ஐ சுருக்கி cache பண்ணுங்க, reply-ஐ stream பண்ணுங்க, அப்புறம் queueing-ஐ பாருங்க.
- **Stream ரொம்ப மெதுவு:** புது GPU-க்கு முன்னாடி சின்ன அல்லது quantised model, அல்லது speculative decoding.
- **Scale-ல ரொம்ப costly:** batching, batch APIs, அப்புறம் model tiering.

## Demo-ல இருந்து production-க்கு

- **ஒரு latency budget வைங்க.** உதாரணம், p95 first token 2 seconds-க்கு கீழ, அதுக்கப்புறம் குறைஞ்சது ஒரு second-க்கு 15 tokens.
- **TTFT-ஐயும் TPOT-ஐயும் தனித்தனியா அளங்க**, user உண்மையில பார்க்குற முதல் token-க்கான நேரத்தையும்.
- **உண்மையான prompt நீளங்களோட load-test பண்ணுங்க.** சின்ன test prompts prefill, KV cache பிரச்சனைகளை மறைச்சுடும்.
- **Prompts-ஓட fixed பகுதியை stable-ஆவும் முதல்லயும் வைங்க**, அப்போ தான் caching work ஆகும்.
- **Model மாத்துன பிறகு திருப்பி check பண்ணுங்க.** வேற tokenizer அல்லது size உள்ள புது model, இந்த எல்லா numbers-ஐயும் மாத்திடும்.

## Practice பண்ணுங்க

1. ஏதாவது ஒரு LLM API-ஐ streaming on பண்ணி call பண்ணுங்க. ஒரு சின்ன prompt-க்கும் 5,000-token prompt-க்கும் முதல் token வரைக்குமான நேரம், மொத்த நேரத்தை note பண்ணுங்க. எது அதிகமா மாறுச்சு?
2. மேல இருக்குற code-ஐ வச்சு, உங்களுக்கு பிடிச்ச open model-க்கு 8,000 tokens, 16 users-க்கான KV cache-ஐ estimate பண்ணுங்க.
3. உங்களுக்கு தெரிஞ்ச ஒரு மெதுவான AI feature-ஐ எடுத்து, அது table-ல எந்த row-ல வருது, நீங்க முதல்ல try பண்ற lever எதுன்னு எழுதுங்க.
