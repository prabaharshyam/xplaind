## இது என்ன

LLM apps-ல cost-ஐயும் காத்திருக்குற நேரத்தையும் மூணு techniques குறைக்குது. இவை வேற வேற layers-ல வேலை செய்யுது, இவற்றை குழப்பிக்கிறது தான் பெரும்பாலான caching bugs-க்கு காரணம்.

- **Prompt caching** model provider பக்கம் நடக்குது. உங்க prompt-ஓட ஆரம்பப் பகுதியோட (instructions, tool definitions, ஒரு நீளமான document) processed form-ஐ provider வெச்சுக்குது. சரியா அதே content-ஓட ஆரம்பிக்கிற அடுத்த request அந்த வேலையை skip பண்ணுது, அதனால cost குறைவு, முதல் token-உம் சீக்கிரமா வரும். ஆனாலும் model ஒவ்வொரு தடவையும் புது answer தான் எழுதுது.
- **Response caching** உங்க சொந்த app-ல நடக்குது. முடிஞ்ச answers-ஐ நீங்க store பண்ணி, அதே request மறுபடி வந்தா அதுல ஒண்ணை return பண்றீங்க, model call-ஏ இல்லாம. இதை நீங்களே build பண்றதால, store பண்ண ஒவ்வொரு answer-ஐயும் யார் பார்க்கலாம்னு நீங்க தான் முடிவு பண்றீங்க.
- **Streaming** delivery-ஐ மாத்துது, வேலையை இல்ல. Reply generate ஆக ஆக கொஞ்சம் கொஞ்சமா screen-க்கு வருது, அதனால user ஒண்ணு ரெண்டு seconds-ல படிக்க ஆரம்பிக்கிறாங்க.

மூணையும் use பண்ற ஒரு request இப்படி இருக்கும்:


இந்த lesson Chennai-ல ஒரு legal-tech company-ஓட contract assistant-ஐ follow பண்ணுது. Lawyers ஒரு agreement-ஐ upload பண்ணி, அது மேல சுமார் பத்து கேள்விகள் கேக்குறாங்க.

## இது எப்படி வேலை செய்யுது

### நேரம் எங்க போகுது

ஒரு reply-க்கு ரெண்டு phases. முதல்ல model முழு input-ஐயும் படிக்குது (**prefill**). அப்புறம் reply-ஐ ஒரு தடவைக்கு ஒரு token-ஆ எழுதுது (**decode**). நீளமான input முதல் token-ஐ slow பண்ணும். நீளமான output அதுக்கு அப்புறம் வர்ற எல்லாத்தையும் slow பண்ணும். அதனால ஒரு 30,000-token contract பெரும்பாலும் **time to first token** (TTFT)-ஐ பாதிக்கும், ஒரு 1,000-token answer பெரும்பாலும் மொத்த நேரத்தை பாதிக்கும். Prompt caching முதலாவதை தாக்குது; streaming ரெண்டாவதை மறைக்குது; சின்ன answers-உம் சின்ன models-உம் அதை குறைக்குது.

### Prompt caching

Cache ஒரு **exact prefix**-ஐ match பண்ணுது: சமீபத்துல பார்த்த ஒரு request-ஓட அதே bytes-ல, அதே order-ல request ஆரம்பிக்கணும். ஒரு character மாறினா, அதுக்கு அப்புறம் இருக்குற எல்லாமே invalid ஆகிடும். அதனால prompt-ஐ எல்லாத்தையும் விட stable-ஆனதுல இருந்து எல்லாத்தையும் விட குறைவா stable-ஆனது வரை order பண்ணுங்க:

1. tool definitions, ஒரு fixed order-ல;
2. system instructions;
3. நீளமான reference documents (contract, policy, codebase);
4. per-user அல்லது per-session data;
5. latest கேள்வியும் conversation turns-உம்.

Timestamp, request id அல்லது user-ஓட name-ஐ மேல எப்பவுமே வைக்காதீங்க. Model-க்கு இன்னைக்கு date தேவைன்னா, அதை கடைசி பக்கத்துல வைங்க.

| ஒரு request-க்கு breakpoints | 4 வரை |
| ஒரு entry-ஐ யார் share பண்றாங்க | உங்க workspace மட்டும்; வேற organisation எப்பவுமே இல்ல |

இதுல இருந்து ரெண்டு rules வருது. 5-minute cache ஒரு read-லயே தன் cost-ஐ திரும்ப எடுத்துடும்; 1-hour cache-க்கு ரெண்டு read வேணும். அப்புறம் price-ஐ விட lifetime தான் முக்கியம்: ஒரு prefix-ஐ share பண்ற requests lifetime-ஐ விட அதிக இடைவெளில வந்தா, ஒவ்வொரு request-உம் write premium கொடுக்கும், எதுக்கும் read discount கிடைக்காது, அது caching இல்லாததை விட அதிக cost ஆகும்.

Prefix-ஐ share பண்ற requests-க்கு நடுவுல இருக்குற gap-ஐ வெச்சு lifetime-ஐ choose பண்ணுங்க. 5 நிமிஷத்துக்குள்ள-னா default-ஐ use பண்ணுங்க; steady traffic-ஏ அதை warm-ஆ வெச்சுக்கும். 5-ல இருந்து 60 நிமிஷம்-னா 1-hour cache. ஒரு மணி நேரத்துக்கு மேல-னா, ஒண்ணு முதல் request cold-ஆ இருக்குறதை ஏத்துக்கோங்க, இல்லைன்னா **pre-warm** பண்ணுங்க: traffic வரும்னு எதிர்பார்க்குறதுக்கு கொஞ்சம் முன்னாடி (worker start, முதல் lawyer-ஓட login), shared prefix-ஐ `max_tokens`-ஐ 0-ஆ set பண்ணி ஒரு தடவை அனுப்புங்க. அப்போ Claude-ஓட API cache-ஐ write பண்ணிட்டு, எதையும் generate பண்ணாம return ஆகும்.

**இன்னும் write ஆகிட்டிருக்குற cache-ஐ parallel requests share பண்ணாது.** முதல் response ஆரம்பிச்ச பிறகு தான் ஒரு entry readable ஆகும். ஒரே நேரத்துல பத்து requests அனுப்பினா, பத்துமே முழு விலை கொடுக்கும். முதல்ல ஒண்ணை அனுப்பி, அதோட முதல் token-க்கு wait பண்ணிட்டு, அப்புறம் மீதியை அனுப்புங்க.

**மத்த providers.** OpenAI மாதிரி சில providers, prompt ஒரு minimum length-ஐ தொட்டவுடனே (அவங்க documentation-படி, model-ஐ பொறுத்து குறைஞ்சது 1,024 tokens) தானாவே cache பண்ணுது. Claude automatic caching அல்லது explicit breakpoints குடுக்குது. Stable content முதல்ல-ங்குறது எல்லா இடத்துலயும் வேலை செய்யும்; minimums, lifetimes, prices வேற வேற, அதனால savings-ஐ estimate பண்றதுக்கு முன்னாடி உங்க provider-ஓட page-ஐ படிங்க.

**Code-ல prompt caching.** Anthropic-ஓட Python SDK-ல stable பகுதியோட முடிவை mark பண்றீங்க, cache-ல இருந்து என்ன read ஆச்சுன்னு usage report காட்டும்:

```python
import anthropic

client = anthropic.Anthropic()
POLICY = open("returns_policy.md").read()          # long, rarely changes

def ask(question):
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000,  # check the docs for current model names
        system=[
            {"type": "text", "text": "You answer questions about our returns policy. Be brief."},
            {"type": "text", "text": POLICY,
             "cache_control": {"type": "ephemeral"}},  # cache up to here; add "ttl": "1h" for slow traffic
        ],
        messages=[{"role": "user", "content": question}],   # changing part goes last
    )
    u = reply.usage
    print(f"cache write {u.cache_creation_input_tokens}, cache read {u.cache_read_input_tokens}, "
          f"uncached {u.input_tokens}")
    return reply

ask("Can I return a kurta after 10 days?")       # first call writes the cache
ask("Do you refund shipping charges?")           # later calls read it
```

**வேலை செய்யுதான்னு check பண்றது.** ஒவ்வொரு call-லயும் மூணு usage numbers-ஐயும் log பண்ணுங்க. வரிசையா அஞ்சு requests அனுப்புங்க: முதலாவதுல ஒரு cache write தெரியணும், மீதில கிட்டத்தட்ட அதே size-ல cache reads. Reads zero-லயே இருந்தா, prefix-ல ஏதோ ஒண்ணு இன்னும் மாறுது: ஒரு timestamp, ஒரு request id, வேற order-ல build ஆன tools, keys sort பண்ணாத JSON, minimum-க்கு கீழ இருக்குற prefix, அல்லது மாறின model அல்லது thinking setting. Reads prefix-ஐ விட ரொம்ப சின்னதா இருந்தா, breakpoint தப்பான இடத்துல இருக்கு.

### Response caching, user-க்கு scope பண்ணி

ஒரு response cache-னா ஒரு key-value store, dictionary அல்லது Redis மாதிரி. Key-ல **answer-ஐ மாத்துற எல்லாமே** இருக்கணும்: normalise பண்ண கேள்வி, document அல்லது data version, prompt version, model, அப்புறம் **scope**, அதாவது answer-ஐ யார் பார்க்க allowed-ங்குறது.

Teams மறந்துடுற பகுதி scope தான், அதை மறந்தா data leak ஆகும். Key-ல கேள்வி மட்டும் இருக்குன்னு வெச்சுக்கோங்க. Asha "என் order எங்க இருக்கு?"-னு கேக்குறாங்க, அவங்க address-ஓட answer store ஆகுது. Ravi அதே வார்த்தைகளை கேக்குறாரு, cache-ல இருந்து Asha-வோட answer அவருக்கு கிடைக்குது, milliseconds-ல, எந்த log-லயும் error இல்லாம. Provider-ஓட prompt cache இதை பண்ண முடியாது, ஏன்னா model ஒவ்வொரு தடவையும் புது answer எழுதுது. உங்க response cache பண்ண முடியும், ஏன்னா அது store பண்ண text-ஐ return பண்ணுது.

மூணு scopes use பண்ணுங்க. **Public**: எல்லாருக்கும் ஒண்ணு தான், product FAQs, fixed help text மாதிரி. **Tenant**: ஒரு company-க்குள்ள ஒண்ணு தான், ஒரு law firm-ஓட சொந்த standard NDA மாதிரி, ஆனா வேற firm-க்கு எப்பவுமே காட்டக்கூடாது. **User**: personal அல்லது permission-ஐ பொறுத்தது; user id-ஆல key பண்ணுங்க, இல்லைன்னா cache-ஏ பண்ணாதீங்க. யாரும் மறக்க முடியாத மாதிரி scope-ஐ ஒரு required argument ஆக்குங்க:

```python
import hashlib, json, time

CACHE, TTL_SECONDS = {}, 24 * 3600
PROMPT_VERSION, MODEL = "faq-v3", "claude-sonnet-5-5"

def cache_key(scope, question, doc_version):
    norm = " ".join(question.lower().split())
    raw = json.dumps([scope, norm, doc_version, PROMPT_VERSION, MODEL])
    return hashlib.sha256(raw.encode()).hexdigest()

def cached_answer(scope, question, doc_version, compute):
    # scope: "public", "firm:<id>" or "user:<id>"; there is no default on purpose
    key = cache_key(scope, question, doc_version)
    hit = CACHE.get(key)
    if hit and time.time() - hit["at"] < TTL_SECONDS:
        return hit["answer"]
    answer, complete = compute(question)          # complete: the reply finished normally
    if complete:                                  # never cache errors or cut-off replies
        CACHE[key] = {"answer": answer, "at": time.time()}
    return answer
```

Ship பண்றதுக்கு முன்னாடி ஒரு two-account test ஓட்டுங்க: user A ஒரு personal கேள்வி கேக்குறாங்க, user B அதே வார்த்தைகளை கேக்குறாங்க, B-க்கு A-வோட answer கிடைக்கக்கூடாது. Stable answers-க்கு கூட ஒரு expiry வைங்க, source மாறும்போது entries-ஐ clear பண்ணுங்க; cache ஆன ஒரு தப்பான answer யாராவது கவனிக்கிற வரைக்கும் repeat ஆகிட்டே இருக்கும்.

### Semantic caching, கவனமா

**Semantic caching** embeddings use பண்ணி கேள்விகளை அர்த்தத்தை வெச்சு match பண்ணுது, அதனால "நம்ம NDA-ல notice period?" கேள்வி "NDA notice period என்ன?"-க்கான answer-ஐ reuse பண்ணலாம். இது hit rates-ஐ ஏத்தும், ஆனா ஒவ்வொரு தப்பான match-உம் confident-ஆன ஒரு தப்பான answer-ஐ குடுக்கும். மூணு guards:

- **Similarity search-க்கு முன்னாடியே scope-ஆல filter பண்ணுங்க**, அப்போ கேக்குறவர் பார்க்க allowed-ஆன answers-ல இருந்து மட்டும் தான் match வர முடியும்.
- **Numbers, names-ல exact-ஆ ஒத்துப்போகணும்னு require பண்ணுங்க.** "Order 41-க்கு refund", "order 14-க்கு refund" text-ஆ கிட்டத்தட்ட ஒண்ணு தான், கேள்விகளா முழுக்க வேற:

```python
import re

def numbers_match(new_q, cached_q):
    return re.findall(r"\d+", new_q) == re.findall(r"\d+", cached_q)
```

- **Similarity threshold-ஐ உங்க சொந்த data-வை வெச்சு set பண்ணுங்க.** எல்லா இடத்துக்கும் safe-ஆன ஒரு universal number இல்ல. Candidate matches-ஐ log பண்ணுங்க, அதுல 200-ஐ ஒருத்தர் சரியா தப்பான்னு label பண்ணட்டும், அந்த feature-க்கு நீங்க set பண்ண target-க்கு கீழ wrong-match rate வர்ற வரைக்கும் threshold-ஐ ஏத்துங்க.

### Streaming

Streaming மொத்த generation time-ஐயோ cost-ஐயோ மாத்தாது. அது experience-ஐ மாத்துது: text ஒண்ணு ரெண்டு seconds-க்குள்ள ஆரம்பிக்குது, மீதி வந்துட்டிருக்கும்போதே user படிக்கிறாங்க, சீக்கிரமாவே Stop அமுக்கலாம். Chat-ல எப்பவுமே stream பண்ணுங்க. TTFT-ஐ measure பண்ணுங்க:

```python
import time
import anthropic

client = anthropic.Anthropic()

def stream_answer(question):
    start, first = time.perf_counter(), None
    with client.messages.stream(model="claude-sonnet-5-5", max_tokens=2000,
                                messages=[{"role": "user", "content": question}]) as stream:
        for text in stream.text_stream:
            if first is None:
                first = time.perf_counter() - start
            print(text, end="", flush=True)     # in a web app, send each piece to the browser
        final = stream.get_final_message()
    print("\nfirst text after", round(first, 2) if first else None,
          "s; total", round(time.perf_counter() - start, 2), "s; stop:", final.stop_reason)
```

Server timing மட்டும் முழு கதை இல்ல: browser-ல, user Send அமுக்கும்போதும் முதல் வார்த்தைகள் paint ஆகும்போதும் `performance.now()`-ஐ record பண்ணுங்க, real users-ல இருந்து p50, p95-ஐ report பண்ணுங்க. மூணு gotchas. சில proxies, compression layers, hosting platforms response-ஐ buffer பண்ணுது, அதனால local-ல வேலை செய்யுற stream production-ல மொத்தமா ஒரே தடவையா வரும்; real path வழியா test பண்ணுங்க. ஒரு stream பாதில fail ஆகலாம், அதனால partial text-ஐ தெளிவான "answer interrupted, try again" message-ஓட காட்டுங்க, அதை எப்பவுமே cache பண்ணாதீங்க. அப்புறம் answer முடியறதுக்கு முன்னாடியே text screen-ல இருக்கும், அதனால safety filter அல்லது JSON validation மாதிரி முழு answer தேவைப்படுற எந்த check-உம் ஒவ்வொரு piece-லயும் ஓடணும், இல்லைன்னா text காட்ட ஆரம்பிக்கிறதுக்கு முன்னாடியே ஓடணும்.

### மத்த speed levers

சின்ன outputs, ஏன்னா generation time length-ஓட சேர்ந்து வளரும். Simple steps-க்கு சின்ன models. வரிசையா குறைவான calls. ஒண்ணை ஒண்ணு சாராத calls-ஐ parallel-ஆ (உதாரணமா `asyncio.gather` வெச்சு), அப்போ காத்திருப்பு எல்லாத்தோட கூட்டுத்தொகை இல்ல, எல்லாத்தையும் விட slow-ஆன call அளவு தான்; rate limits-ஐ கவனிங்க, ஒரு burst 429 errors-ஐ return பண்ணலாம். குறைவான, நல்ல retrieved chunks.

## ஒரு worked example

Chennai contract assistant ஒரு 40-page agreement பத்தின கேள்விகளுக்கு பதில் சொல்லுது. கீழ இருக்குற numbers November 2026 நிலவரப்படி Claude Sonnet 5.5 list prices-ஐ வெச்சு build பண்ண ஒரு **illustration** தான் (ஒரு million input tokens-க்கு $2, ஒரு million output-க்கு $10, cache writes 5 நிமிஷத்துக்கு $2.50 அல்லது 1 மணி நேரத்துக்கு $4, cache reads $0.10), இந்த assumptions-ஓட: instructions-உம் contract-உம் 30,000 tokens, ஒவ்வொரு கேள்வியும் 100 tokens, அது தனியா அனுப்பப்படுது, ஒவ்வொரு answer-உம் 300 output tokens use பண்ணுது, ஒரு contract-க்கு 10 கேள்விகள். இந்த figures-ஐ reuse பண்றதுக்கு முன்னாடி இப்போதைய prices-ஐ check பண்ணுங்க.

**முன்னாடி.** ஒவ்வொரு கேள்வியும் முழு 30,100 tokens-ஐயும் முழு விலைல அனுப்புது: $0.0602 input, $0.003 output, அதனால ஒரு கேள்விக்கு $0.0632, **ஒரு contract-க்கு $0.63**. எதுவும் stream ஆகல, அதனால lawyer-க்கு சுமார் 9 seconds எதுவும் தெரியாது.

**அப்புறம், முதல் முயற்சி.** Team contract-ஐயும் instructions-ஐயும் முன்னாடி நகர்த்தி, ஒரு breakpoint சேர்த்து, default 5-minute cache-ஐயே வெச்சுக்குது. கேள்விகள் 5 நிமிஷத்துக்கும் குறைவான இடைவெளில வந்திருந்தா, கேள்வி 1-க்கு $0.078 ஆகியிருக்கும் (write premium அதை முன்னாடியை விட அதிக விலையாக்குது), அதுக்கு அப்புறம் ஒவ்வொரு கேள்விக்கும் $0.0062, அதனால **ஒரு contract-க்கு $0.13, 79% குறைவு**. ஆனா logs கிட்டத்தட்ட ஒவ்வொரு call-லயும் cache writes-ஐ காட்டுது. Lawyers அடுத்த கேள்வி கேக்குறதுக்கு முன்னாடி ஒவ்வொரு answer-ஐயும் clause கூட வெச்சு படிக்கிறாங்க, அடிக்கடி 5-ல இருந்து 15 நிமிஷம் கழிச்சு. ஒவ்வொரு entry-உம் expire ஆகுது, ஒவ்வொரு கேள்வியும் write price கொடுக்குது, bill ஏறி **ஒரு contract-க்கு $0.78 ஆகுது, caching இல்லாததை விட 24% அதிகம்**.

**அப்புறம், சரி பண்ணது.** அவங்க 1-hour cache-க்கு மாறுறாங்க. இப்போ கேள்வி 1-க்கு write-க்காக $0.12, அடுத்த ஒன்பதுக்கு ஒவ்வொண்ணுக்கும் $0.0062: **ஒரு contract-க்கு $0.18, முன்னாடியை விட சுமார் 72% குறைவு**. ஒரு dollar-க்கு சுமார் ₹94-ல (mid-November 2026), அது ஒரு contract-க்கு கிட்டத்தட்ட ₹59-ல இருந்து ₹17-க்கு இறங்குது. கவனிங்க, output tokens (ஒரு answer-க்கு $0.003) இப்போ cache ஆன ஒரு கேள்வியோட cost-ல பாதி, அதனால அடுத்த saving சின்ன answers தான்.

Firm-கிட்ட அதோட சொந்த standard templates பத்தின கேள்விகளுக்கு ஒரு response cache-உம் இருக்கு ("நம்ம standard NDA-ல notice period என்ன?"). அது firm-ஓட id, template version, prompt version-ஆல key பண்ணப்பட்டிருக்கு, அதனால firm A-வோட template answers firm B-க்கு எப்பவுமே போகாது. Upload பண்ண contract பத்தின answers response-cache பண்ணப்படவே இல்ல: ஒவ்வொரு contract-உம் அதுக்குன்னு access list இருக்குற ஒரு matter-க்கு சொந்தம்.

முதல் கேள்வியையும் வேகமாக்க, ஒரு contract upload ஆகி முடிஞ்சவுடனே, lawyer இன்னும் type பண்ணிட்டிருக்கும்போதே, team `max_tokens`-ஐ 0-ஆ set பண்ணி cache-ஐ pre-warm பண்ணுது.

## பொதுவான தப்புகள்

- **Prompt-ஓட மேல ஏதோ மாறுற ஒண்ணு.** ஒரு date, request id அல்லது user name ஒவ்வொரு cache read-ஐயும் உடைக்கும். கண்டுபிடிக்க: repeat calls-ல `cache_read_input_tokens` 0-லயே இருக்கும்.
- **Traffic-க்கு தப்பான lifetime.** Cache lifetime-ஐ விட நீளமான gaps caching-ஐ ஒரு surcharge ஆக்கிடும். கண்டுபிடிக்க: பெரும்பாலான calls-ல cache writes, கொஞ்சம் reads.
- **Scope இல்லாத response cache keys.** ஒரு user-ஓட order, salary அல்லது contract இன்னொரு user-க்கு போகும். கண்டுபிடிக்க: launch-க்கு முன்னாடியும் ஒவ்வொரு cache change-க்கு அப்புறமும் ஓட்டுற ஒரு two-account test.
- **மாறுற data-ல இருந்து வர்ற answers-ஐ, key-ல expiry அல்லது version இல்லாம cache பண்றது.** பழைய prices-உம் பழைய rules-உம் தொடர்ந்து serve ஆகும். கண்டுபிடிக்க: ஒரு update-க்கு அப்புறம் source கூட ஒத்துப்போகாத answers.
- **Failures-ஐ cache பண்றது.** ஒரு timeout, ஒரு refusal அல்லது `max_tokens`-ஆல பாதில வெட்டப்பட்ட reply store ஆகி எல்லாருக்கும் replay ஆகும். Normal-ஆ முடிஞ்ச replies-ஐ மட்டும் store பண்ணுங்க.
- **Cold cache-க்கு parallel requests அனுப்புறது.** எல்லாமே முழு விலை கொடுக்கும். கண்டுபிடிக்க: ஒரே second-ல ஒரு burst cache writes.
- **Streaming generation-ஐ வேகமாக்கும்னு நம்புறது.** அது காத்திருப்பை குறைவா feel பண்ண வைக்குது; cost-உம் மொத்த நேரமும் மாறாது.
- **Averages-ஐ மட்டும் measure பண்றது.** Time to first token-க்கும் மொத்த நேரத்துக்கும் p50, p95-ஐ report பண்ணுங்க, server-ல மட்டும் இல்லாம browser-லயும் measure பண்ணி.

## Caching எப்போ உதவாது

- **ஒவ்வொரு request-உம் வேற மாதிரி**, நீளமான shared prefix இல்ல, repeat ஆகுற கேள்விகளும் கொஞ்சம் தான்.
- **Traffic குறைவா, பரவலா இருக்கு**, அதனால 1 hour-லயும் கூட, அடுத்த request வர்றதுக்கு முன்னாடியே cache ஆன prefixes expire ஆகிடும்.
- **Shared பகுதி சின்னது**, minimum cacheable length-க்கு கீழ.
- **ஒவ்வொரு தடவையும் answers fresh-ஆ இருக்கணும்**, live prices அல்லது stock levels மாதிரி.
- **Slow பகுதி வேற இடத்துல இருக்கு**: retrieval, ஒரு slow tool அல்லது உங்க சொந்த server. Model call-ஐ optimise பண்றதுக்கு முன்னாடி measure பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- ஒவ்வொரு call-லயும் **cache read, write tokens-ஐ log பண்ணுங்க**, ஒவ்வொரு feature-க்கும் hit rate-ஐ track பண்ணுங்க.
- Browser-ல இருந்து, feature, model வாரியா, p50, p95-ல **time to first token-ஐயும் மொத்த நேரத்தையும் track பண்ணுங்க**.
- Prompt, model, data-வை வெச்சு **cache keys-ஐ version பண்ணுங்க**, எல்லா இடத்துலயும் expiries வைங்க, release-ப்போ அல்லது source data மாறும்போது response caches-ஐ clear பண்ணுங்க.
- **ஒவ்வொரு response cache key-லயும் scope-ஐ ஒரு required பகுதி ஆக்குங்க**, two-account test-ஐ உங்க test suite-ல வெச்சுக்கோங்க.

## Practice

கீழ link பண்ண prompt caching guide-ஐயும் streaming guide-ஐயும் படிங்க.

1. உங்க prompts-ல ஒண்ணை stable content முதல்ல வர்ற மாதிரி restructure பண்ணி, ஒரு breakpoint சேருங்க. அஞ்சு requests அனுப்பி, ஒவ்வொண்ணுக்கும் cache write, cache read, uncached tokens-ஐ record பண்ணுங்க.
2. உங்க real traffic-ல requests-க்கு நடுவுல இருக்குற gap-ஐ கண்டுபிடிங்க, 5 minutes-ஆ 1 hour-ஆன்னு choose பண்ணுங்க, உங்க provider-ஓட இப்போதைய prices-ல இருந்து ஒரு session-க்கான cost-ஐ ரெண்டு வழியிலயும் calculate பண்ணுங்க.
3. ஒரு chat interface-க்கு streaming சேர்த்து, முன்னாடியும் அப்புறமும் browser-ல time to first token-ஐ measure பண்ணுங்க.
4. Repeat ஆகுற ஒரு கேள்வி type-க்கு ஒரு scoped response cache சேருங்க, அப்புறம் two-account test-ஐ எழுதி, scope-ஐ எடுத்தா அது fail ஆகுறதை பாருங்க.
