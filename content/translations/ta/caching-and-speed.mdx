## இது என்ன

LLM apps-ல cost-ஐயும் காத்திருக்கும் நேரத்தையும் குறைக்க மூணு techniques:

- **Prompt caching**: Provider, prompt-ஓட நீளமான, மாறாத ஆரம்பத்தை (system prompt, ஒரு document, tool definitions) process பண்ணின வடிவத்துல store பண்ணி வைக்கும், அதனால அதே மாதிரி ஆரம்பிக்குற அடுத்த requests மலிவாவும் வேகமாவும் இருக்கும்.
- **Response caching**: உங்க app answers-ஐ store பண்ணி, அதே (அல்லது சமமான) request திரும்ப வரும்போது, model call-ஐ முழுசா தவிர்த்து நேரடியா திருப்பும்.
- **Streaming**: reply-ஐ generate ஆகும்போதே token token-ஆ user-க்கு அனுப்பறது, அதனால அவங்க கிட்டத்தட்ட உடனே படிக்க ஆரம்பிக்கலாம்.

```flow
dir: LR
title: Prompt caching: மாறாத பகுதியை முதல்ல வைங்க
மாறாத prefix | instructions, tools, 40 page contract: முதல் call-க்கு பிறகு cache ஆகும் -> கேள்வி | ஒவ்வொரு request-லயும் மாறும்
```

கேள்வி 1 முழு விலை கொடுத்து 9 நொடி எடுக்கும்; கேள்வி 2-ல இருந்து, cache ஆன prefix முதல் token-ஐ கிட்டத்தட்ட 2 நொடிக்கு கொண்டு வரும்.

```flow
title: Response cache: key = normalise பண்ணின கேள்வி + template version + model version
கேள்வி -> Response cache-ல இருக்கா?
Response cache-ல இருக்கா? -[hit]-> உடனே answer, model call இல்ல
Response cache-ல இருக்கா? -[miss]-> Model -> Tokens-ஐ screen-க்கு stream பண்ணு
```

இந்த lesson, ஒவ்வொரு upload ஆன agreement-க்கும் வக்கீல்கள் கிட்டத்தட்ட பத்து கேள்விகள் கேக்குற Chennai-ல உள்ள ஒரு legal-tech company-ஓட contract assistant-ஐ பின்தொடருது.

## இது எப்படி work ஆகுது

**Prompt caching.** Cache-ல இருந்து படிக்கிற input tokens-க்கு providers குறைவா, பெரும்பாலும் ரொம்ப குறைவா charge பண்ணுவாங்க, அவற்றை process பண்றதும் வேகம். Cache ஒரு exact prefix-ல வேலை செய்யும்: request அதே content-ஓட, அதே வரிசையில ஆரம்பிக்கணும். அதனால:

- மாறாததை முதல்ல வைங்க: system prompt, tool definitions, நீளமான reference documents;
- மாறுறதை கடைசியில வைங்க: user-ஓட கேள்வி, சமீபத்திய conversation turns;
- மேல எந்த மாறுற விஷயத்தையும் (timestamp, user name) சேர்க்காதீங்க.

Caches ஒரு காலம் பயன்படுத்தாம இருந்தா expire ஆகும்; minimum length, lifetime, pricing பத்தின உங்க provider-ஓட விதிகளை check பண்ணுங்க.

**Response caching.** Answer-ஐ normalise பண்ணின request (கூடவே prompt, model version) key-ஆ வச்சு store பண்ணுங்க. திரும்ப வர்ற, ஒரே மாதிரி கேள்விகளுக்கு நல்லது: FAQ answers, product descriptions, fixed text-ஓட translations. Expiry times வைங்க, அடிப்படை data மாறும்போது invalidate பண்ணுங்க, answers-ல personal அல்லது permission-ஐ சார்ந்த data இருந்தா cached answers-ஐ users நடுவுல share பண்ணவே பண்ணாதீங்க. "Semantic caching" ஒரே மாதிரி இல்லாம, ஒத்த கேள்விகளை match பண்ணும்; கவனமா use பண்ணுங்க, ஏன்னா கிட்டத்தட்ட ஒரே மாதிரி இருக்கற கேள்விகளுக்கு வேற answers தேவைப்படலாம்.

**Streaming.** மொத்த generation time மாறாது, ஆனா users முழு reply-க்கு காத்திருக்காம, பொதுவா முதல் வார்த்தைகளை ஒரு சில நொடிகள்ல பார்ப்பாங்க. உணரப்படுற வேகம் பெருசா மேம்படும், users சீக்கிரமே படிக்கிறதை நிறுத்தலாம் அல்லது cancel பண்ணலாம். Stream நடுவுல errors, disconnections-ஐ கையாளுங்க.

**மத்த speed levers.** குட்டி outputs (generation time நீளத்தோட வளரும்); எளிமையான steps-க்கு சின்ன models; குறைவான sequential model calls; independent calls-ஐ parallel-ஆ ஓட்டுறது; குறைவான, நல்ல chunks-ஐ retrieve பண்றது.

**மூணு techniques ஒப்பீடு:**

| Technique | எதை சேமிக்கும் | எப்போ வேலை செய்யும் | எதை கவனிக்கணும் |
| --- | --- | --- | --- |
| Prompt caching | Input cost, முதல் token வர்ற நேரம் | நீளமான, ஒரே மாதிரி prefixes சீக்கிரம் reuse ஆகும்போது | Prefix மாறுறது; cache expiry |
| Response caching | முழு model call | ஒரே மாதிரி, திரும்ப வர்ற கேள்விகள் | Personal data; பழைய answers |
| Streaming | உணரப்படுற காத்திருப்பு நேரம் | Chat, நீளமான answers | Stream நடுவுல errors, disconnects |

**Cache வேலை செய்யுதான்னு check பண்றது.** ஒவ்வொரு response-ஓட usage data-லயும் cache ஆன input tokens-ஐ providers report பண்ணுவாங்க. அவற்றை log பண்ணுங்க. Prompt-ஐ மறுவரிசைப்படுத்துன பிறகு, ஐந்து requests-ஐ தொடர்ந்து அனுப்பி, cached count ரெண்டாவது request-ல இருந்து ஏறுதான்னு உறுதிபடுத்துங்க. அது பூஜ்யத்துலயே இருந்தா, prefix-ல இன்னும் எதோ மாறுற விஷயம் இருக்கு, பெரும்பாலும் ஒரு timestamp, ஒரு request id, அல்லது மாறுற வரிசையில list ஆன tool definitions.

**Response caches-ஐ invalidate பண்றது.** Answer-ஐ மாத்துற ஒவ்வொரு input-ஐயும் key-ல சேருங்க: கேள்வி, template அல்லது document version, prompt version, model. மாறாத answers-க்கும் expiry வைங்க, source மாறும்போது entries-ஐ clear பண்ணுங்க. Cache ஆன தப்பான answer, மெதுவான சரியான answer-ஐ விட மோசம், ஏன்னா யாராவது கவனிக்கிற வரை அது திரும்ப திரும்ப வரும்.

**நேரம் எங்க போகுது.** ஒரு reply-க்கு ரெண்டு phases. முதல்ல model முழு input-ஐயும் படிக்கும் (**prefill**); அப்புறம் reply-ஐ ஒரு நேரத்துல ஒரு token-ஆ எழுதும் (**decode**). நீளமான inputs முதல் token-ஐ மெதுவாக்கும்; நீளமான outputs அதுக்கு பிறகு எல்லாத்தையும் மெதுவாக்கும். அதனால 20,000-token document பெரும்பாலும் முதல் token-க்கான நேரத்தை பாதிக்கும், 1,000-token answer பெரும்பாலும் மொத்த நேரத்தை பாதிக்கும். Caching முதலாவதுக்கு உதவும்; குட்டி answers, சின்ன models ரெண்டாவதுக்கு உதவும்.

**Code-ல prompt caching.** Anthropic-ஓட API-ல நீங்க மாறாத prefix-ஓட முடிவை mark பண்ணுவீங்க, usage report cache-ல இருந்து எது படிக்கப்பட்டுச்சுன்னு சொல்லும்:

```python
import anthropic

client = anthropic.Anthropic()
POLICY = open("returns_policy.md").read()          # long, rarely changes

def ask(question):
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=400,  # check the docs for current names
        system=[
            {"type": "text", "text": "You answer questions about our returns policy. Be brief."},
            {"type": "text", "text": POLICY, "cache_control": {"type": "ephemeral"}},   # cache up to here
        ],
        messages=[{"role": "user", "content": question}],   # changing part goes last
    )
    u = reply.usage
    print(f"cache write {u.cache_creation_input_tokens}, cache read {u.cache_read_input_tokens}, "
          f"uncached {u.input_tokens}")
    return reply

ask("Can I return a kurta after 10 days?")       # first call writes the cache
ask("Do you refund shipping charges?")           # later calls read it, cheaper and faster
```

Cache-ல எழுதுறது சாதாரண input-ஐ விட கொஞ்சம் அதிகம் செலவாகும்; படிக்கிறது ரொம்ப குறைவு. Cache lifetime-க்குள்ள ஒரே prefix பலமுறை use ஆனா இது பலன் தரும். மத்த providers தானாவே அல்லது வேற settings-ஓட cache பண்ணுவாங்க; கொள்கை, மாறாத content முதல்ல, அதேதான்.

**Code-ல ஒரு response cache.** திரும்ப வர்ற, ஒரே மாதிரி requests-க்கு, answer-ஐ பாதிக்கிற எல்லாத்தையும் key-ஆ வச்ச ஒரு dictionary அல்லது Redis store:

```python
import hashlib, json, time

CACHE, TTL_SECONDS = {}, 24 * 3600
PROMPT_VERSION, MODEL = "faq-v3", "claude-sonnet-5-5"

def cache_key(question, doc_version):
    norm = " ".join(question.lower().split())
    raw = json.dumps([norm, doc_version, PROMPT_VERSION, MODEL])
    return hashlib.sha256(raw.encode()).hexdigest()

def cached_answer(question, doc_version, compute):
    key = cache_key(question, doc_version)
    hit = CACHE.get(key)
    if hit and time.time() - hit["at"] < TTL_SECONDS:
        return hit["answer"]
    answer = compute(question)
    CACHE[key] = {"answer": answer, "at": time.time()}
    return answer
```

எல்லா users-க்கும் ஒரே மாதிரி இருக்கற answers-ஐ மட்டும் cache பண்ணுங்க. User-ஓட account, orders அல்லது permissions-ஐ சார்ந்த எதுவும் cache-ஐ தவிர்க்கணும் இல்லன்னா key-ல user-ஓட id-ஐ சேர்க்கணும்.

**Independent calls-ஐ parallel-ஆ ஓட்டுறது.** ஒரு page-க்கு ஒரே review-ல இருந்து ஒரு summary, ஒரு sentiment label, மூணு tags வேணும்னா, calls-ஐ ஒரே நேரத்துல ஓட்டுங்க. மொத்த காத்திருப்பு கூட்டுத்தொகை இல்ல, மெதுவான call-ஓட நேரம் ஆகும்:

```python
import asyncio
import anthropic

aclient = anthropic.AsyncAnthropic()

async def one(instruction, text):
    r = await aclient.messages.create(model="claude-haiku-5-5", max_tokens=150,
                                      messages=[{"role": "user", "content": f"{instruction}\n\n{text}"}])
    return "".join(b.text for b in r.content if b.type == "text")

async def analyse(review):
    return await asyncio.gather(
        one("Summarise in one line:", review),
        one("Answer positive, negative or mixed:", review),
        one("Give three topic tags, comma-separated:", review),
    )
```

Fan out பண்ணும்போது உங்க rate limits-ஐ மதிங்க; parallel calls-ஓட ஒரு திடீர் வெள்ளம் 429 errors-ஐ உண்டாக்கலாம்.

**Semantic caching, கவனமா.** Embedding வச்சு ஒத்த கேள்விகளை match பண்றது hit rates-ஐ ஏத்தலாம், ஆனா ஒவ்வொரு தப்பான match-ம் தப்பான answer-ஐ கொடுக்கும். உயர்ந்த similarity threshold வைங்க, personal அல்லது numeric details இல்லாத பொதுவான கேள்விகளுக்கு மட்டும் வரம்பிடுங்க, நம்புறதுக்கு முன்னாடி matches எவ்ளோ தடவை தப்புன்னு அளங்க.

## ஒரு worked example

Chennai-ல ஒரு legal-tech company-ஓட contract assistant, வக்கீல் upload பண்ற 40-page agreement பத்தின கேள்விகளுக்கு பதில் சொல்லுது, ஒரு contract-க்கு பொதுவா 10 கேள்விகள்.

முன்னாடி: ஒவ்வொரு கேள்வியும் முழு contract-ஐயும் (கிட்டத்தட்ட 30,000 tokens) கேள்வியோட அனுப்புச்சு. ஒவ்வொரு answer-க்கும் 9 நொடி ஆச்சு, input tokens ஒவ்வொரு தடவையும் முழுசா bill ஆச்சு.

பின்னாடி:

- Contract-உம் instructions-உம் முதல்ல வருது, cache ஆகுது; கேள்விகள் கடைசியில. ரெண்டாவது கேள்வியில இருந்து, பெரும்பாலான input tokens ஒரு சிறிய விலையில cache-ல இருந்து படிக்கப்படுது, முதல் token கிட்டத்தட்ட 2 நொடியில வருது.
- Answers screen-க்கு stream ஆகுது.
- Firm-ஓட சொந்த standard template பத்தின பொதுவான கேள்விகள் ("நம்ம standard NDA-ல notice period என்ன?") template version-ஐ key-ஆ வச்ச ஒரு response cache-ல இருந்து answer ஆகுது.

ஒரு contract session-க்கு cost கிட்டத்தட்ட 70% குறையுது, tool மெதுவா இருக்குன்னு வக்கீல்கள் புகார் சொல்றதை நிறுத்துறாங்க.

| ஒரு contract session-க்கு அளவீடு | முன்னாடி | பின்னாடி |
| --- | --- | --- |
| முதல் token-க்கு நேரம், அடுத்த கேள்விகள் | முழு answer-க்கு கிட்டத்தட்ட 9 நொடி | கிட்டத்தட்ட 2 நொடி, அப்புறம் stream |
| முழுசா bill ஆகுற input tokens | ஒவ்வொரு கேள்வியும் | முதல் கேள்விக்கு பிறகு பெரும்பாலும் cached |
| Cost | Baseline | கிட்டத்தட்ட 70% குறைவு |

**வக்கீல்களுக்கு என்ன மாறுச்சு.** ஒரு புது contract-ஓட முதல் கேள்விக்கு இன்னும் முழு நேரம் ஆகும், ஏன்னா cache காலியா இருக்கு. அடுத்த ஒவ்வொரு கேள்வியும் வேகமாவும் மலிவாவும் இருக்கு, stream ஆகுற text-னால வக்கீல்கள் உடனே படிக்க ஆரம்பிக்கிறாங்க. Team முதல் answer-க்கு கீழ "இந்த contract பத்தின அடுத்த கேள்விகள் வேகமா இருக்கும்" ன்னு ஒரு குட்டி note சேர்த்தாங்க, அது tool-ஐ அதோட மிக மெதுவான நொடியை வச்சு judge பண்றதை நிறுத்துச்சு.

## பொதுவா பண்ற தப்புகள்

- **Prompt-ஓட ஆரம்பத்துல மாறுற content.** அது cache-ஐ உடைக்கும்.
- **User-ஐ அல்லது மாறுற data-வை சார்ந்த answers-ஐ cache பண்றது.**
- **Response caches-க்கு expiry அல்லது invalidation இல்லாம இருக்கிறது.**
- **Chat interfaces-ல stream பண்ணாம இருக்கிறது.**
- **Streaming generation-ஐ வேகமாக்குதுன்னு நினைக்கிறது.** அது காத்திருப்பை குறைவா உணர வைக்குது.
- **Per-user answers-ஐ globally cache பண்றது.** ஒரு user-ஓட order details இன்னொரு user-க்கு போயிடும்.
- **Averages மட்டும் அளக்கிறது.** முதல் token நேரம், மொத்த நேரத்துக்கு p50, p95-ஐ report பண்ணுங்க.

## Caching எப்போ உதவாது

- **ஒவ்வொரு request-ம் வேற**, நீளமான பகிரப்பட்ட prefix இல்ல, திரும்ப வர்ற கேள்விகள் குறைவு.
- **Traffic குறைவா, சிதறி இருக்கு**, அதனால அடுத்த request-க்கு முன்னாடியே cache ஆன prefixes expire ஆகிடும்.
- **Answers ஒவ்வொரு தடவையும் fresh-ஆ இருக்கணும்**, உதாரணத்துக்கு live prices அல்லது stock levels.
- **மெதுவான பகுதி வேற இடத்துல இருக்கு**: retrieval, ஒரு மெதுவான tool அல்லது உங்க சொந்த server. Model call-ஐ optimise பண்றதுக்கு முன்னாடி அளங்க.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு call-லயும் cache read, write tokens-ஐ log பண்ணுங்க**, ஒவ்வொரு feature-க்கும் hit rate-ஐ track பண்ணுங்க.
- **முதல் token நேரம், மொத்த நேரத்தை** p50, p95-ல, feature, model வாரியா track பண்ணுங்க.
- **Cache keys-ஐ** prompt, model, data-வோட version பண்ணுங்க, release-ல caches-ஐ clear பண்ணுங்க.
- **எல்லா இடத்துலயும் expiries வைங்க**, source data மாறும்போது ஒரு தெளிவான invalidation path-உம்.
- **ரெண்டு accounts வச்சு cache-ஐ test பண்ணுங்க**, எந்த personal answer-உம் users நடுவுல போகலன்னு நிரூபிக்க.

## Practice பண்ணுங்க

கீழ இணைச்சிருக்குற prompt caching guide-ஐயும், streaming guide-ஐயும் படிங்க.

1. உங்க prompts-ல ஒண்ணை மறுகட்டமைங்க, மாறாத content முதல்ல வரும்படி, caching-ஐ enable பண்ணி, ஐந்து requests-ல token costs-ஐ ஒப்பிடுங்க.
2. ஒரு chat interface-ல streaming-ஐ சேர்த்து, முன்னாடி, பின்னாடி முதல் token நேரத்தை அளங்க.
3. திரும்ப வர்ற ஒரு கேள்வி வகைக்கு expiry-ஓட ஒரு response cache சேருங்க.
4. உங்க apps-ல ஒண்ணுல prompt-caching example-ஐ சேர்த்து, ஐந்து கேள்விகளை தொடர்ந்து அனுப்பி, ஒவ்வொண்ணுக்கும் cache read tokens, முதல் token நேரத்தை record பண்ணுங்க.

இன்னும் ஆழமா படிக்க, Chip Huyen-ஓட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட chapter 9 prefill, decode, prompt caching, parallelism-ஐயும், chapter 10 exact, semantic caches-ஐயும் பேசுது.

**இது முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** Prompt caching எதை சேமிக்குது, மாறாத பகுதி எங்க இருக்கணும், மொத்த நேரம் அதேதான்னாலும் streaming ஏன் உதவுதுன்னு விளக்க முடியும்போது.
