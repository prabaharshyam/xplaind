## இது என்ன

நிறைய இந்திய businesses இன்னும் வேற எதோடவும் பேச முடியாத software-ல தான் ஓடுது: 15 வருஷ பழைய ஒரு desktop ERP, ஒரு bank-ஓட back-office screens, API இல்லாத ஒரு government portal. ஆளுங்க நாள் முழுக்க ஒரு screen-ல இருந்து இன்னொரு screen-க்கு values-ஐ copy பண்ணிட்டு இருக்காங்க. **Robotic process automation (RPA)** அந்த copy வேலையை எடுத்துக்குது.

RPA software "robots"-ஐ use பண்ணுது; அவை ஒரு ஆள் பண்ற மாதிரியே applications-ஐ அதோட **user interface** வழியா இயக்கும்: programs-ஐ open பண்றது, buttons-ஐ click பண்றது, fields-ல type பண்றது, screens-ல இருந்து values-ஐ படிக்கிறது, reports-ஐ download பண்றது. API இல்லாத systems-க்கு, இல்லன்னா ஒரு integration build பண்ண ரொம்ப நாள் ஆகும்னா, இது தான் tool.

முக்கியமான idea: API-னா software-க்காக கட்டின ஒரு கதவு; RPA-னா ஆளுங்களுக்காக கட்டின கதவு வழியா software நடந்து போறது. அந்த கதவு robots-க்காக design பண்ணதே இல்ல. ஒரு button-ஓட பெயர் மாறுனாலோ, ஒரு screen slow-ஆ இருந்தாலோ, திடீர்னு ஒரு pop-up வந்தாலோ robot நின்னுடும். அதனால RPA powerful தான், ஆனா எளிதா உடையும்; skill-ல பெரும்பகுதி அந்த உடையுற தன்மையை manage பண்றது தான்.

முன்னணி RPA tools-ல **UiPath**, **Automation Anywhere**, **Microsoft Power Automate Desktop** இருக்கு. Steps-ஐ ஒரு studio app-ல design பண்ணுவீங்க, அப்புறம் அவற்றை ஒரு schedule-ல அல்லது தேவைப்படும்போது, ஒரு desktop-லயோ server-லயோ ஓட்டுவீங்க. Power Automate for desktop, Windows 11-ஓட extra cost இல்லாம வருது, அதனால practice பண்ண இது ஒரு ஈஸியான இடம்; ஆனா flows-ஐ unattended-ஆ ஓட்டவோ cloud-ல இருந்து trigger பண்ணவோ paid licence வேணும்.

இந்த lesson, Kolkata-ல ஒரு general insurer-ஓட claims team-ஐ follow பண்ணுது; ஒரு பழைய claims system-ல data entry வேலையை ஒரு AI step-உம் ஒரு RPA robot-உம் எடுத்துக்குது. கடைசியில RPA எப்போ சரியான tool-னு, duplicates create பண்ணாத, சத்தமில்லாம fail ஆகாத robot-ஐ எப்படி build பண்றதுன்னு, அது போட்ட காசை திரும்ப எடுக்குதான்னு எப்படி check பண்றதுன்னு உங்களுக்கு தெரியும்.

## இது எப்படி work ஆகுது

### Attended, unattended robots

| Type | எங்க, எப்போ ஓடும் | உதாரணம் |
| --- | --- | --- |
| **Attended** | ஒரு ஆளோட computer-ல, அவங்க start பண்ணும்போது | Agent "Go"-வை click பண்ணதும் 40 fields இருக்குற ஒரு form-ஐ fill பண்ற robot |
| **Unattended** | தனி machines-ல தானா, ஒரு queue-ல இருந்து items-ஐ எடுத்து | ராத்திரி முழுக்க 300 claims-ஐ enter பண்ற robot |

Attended robots ஒரு ஆள் வேகமா வேலை செய்ய help பண்ணும்; ஒவ்வொரு run-ஐயும் ஒரு ஆள் பார்த்துட்டு இருப்பாங்க. Unattended robots ஒரு shift வேலையையே replace பண்ணும், யாரும் அவற்றை பார்க்க மாட்டாங்க. கீழ இருக்குற ஒவ்வொரு design rule-உம் unattended robots-க்கு தான் ரொம்ப முக்கியம்.

### Production model: queue, orchestrator, robot

ஒரு demo robot ஒரு spreadsheet-ல rows-ஐ loop பண்ணும். ஒரு production robot ஒரு **queue**-ல இருந்து வேலை செய்யும். ஒவ்வொரு வேலையும், உதாரணமா ஒரு claim email, அதோட data-வும் ஒரு status-உம் உள்ள ஒரு **queue item** ஆகும்; status new, in progress, successful அல்லது failed மாதிரி இருக்கும். ஒரு **orchestrator**, அதாவது RPA platform-ஓட control centre (UiPath அதை Orchestrator-னு சொல்லுது), queues-ஐ வச்சிருக்கும், schedules-ல robots-ஐ start பண்ணும், credentials-ஐ store பண்ணும், logs-ஐ வச்சுக்கும்.

ஒரு spreadsheet loop தராத மூணு விஷயங்களை queues தரும். பல robots வேலையை பகிர்ந்துக்கலாம். ஒரு crash ஆனா, முழு batch இல்ல, அப்போ நடந்துட்டு இருந்த item மட்டும் தான் போகும். எத்தனை items wait பண்ணுது, முடிஞ்சுது, மாட்டிக்கிட்டு இருக்குன்னு business ஒரே பார்வையில பார்க்கலாம்.

### Business, system exceptions

விஷயங்கள் ரெண்டு ரொம்ப வேற வேற வழிகள்ல தப்பா போகும், robot அவற்றை பிரிச்சு பார்க்கணும்.

| | Business exception | System exception |
| --- | --- | --- |
| **என்ன நடந்துச்சு** | Data ஒரு rule-ஐ மீறுது: policy expire ஆயிடுச்சு, GSTIN match ஆகல, ஒரு required field missing | Technical-ஆ எதோ fail ஆச்சு: app crash ஆச்சு, ஒரு screen time out ஆச்சு, network போயிடுச்சு |
| **Retry பண்ணா help ஆகுமா?** | இல்ல. அடுத்த தடவையும் data அதே மாதிரி தப்பா தான் இருக்கும் | பெரும்பாலும் ஆகும். அதே item ரெண்டாவது try-ல அடிக்கடி work ஆகும் |
| **என்ன பண்ணணும்** | Item-ஐ failed-னு mark பண்ணி, காரணத்தோட ஒரு ஆள்கிட்ட அனுப்புங்க | App-ஐ close பண்ணி restart பண்ணுங்க, அப்புறம் retry, மூணு தடவை மாதிரி ஒரு limit வரை |

எல்லாத்தையும் retry பண்றது தான் classic தப்பு. ஒரு business exception-ஐ மூணு தடவை retry பண்ணா மூணு runs வீணாகும், கடைசியில அது ஒரு ஆள்கிட்ட தான் போகும். ஒரு system exception-ஐ நேரா ஒரு ஆள்கிட்ட அனுப்புனா, ஒரு restart சரி பண்ணியிருக்கக்கூடிய manual வேலையை create பண்ணுது. UiPath-ஓட REFramework மாதிரி templates இந்த பிரிவை ஏற்கனவே உள்ள வச்சிருக்கு. Tools-ஓட exact retry settings வேற வேற, அதனால உங்க version-ஓட documentation-ஐ check பண்ணுங்க.

### Retries-உம் duplicates-உம்: idempotency

RPA-ல ரொம்ப ஆபத்தான failure-ஐ create பண்றது retries தான். யோசிச்சு பாருங்க: robot ஒரு claim-ஐ type பண்ணி, Save-ஐ click பண்ணுது, பழைய app ரெண்டு நிமிஷம் freeze ஆகுது. Robot time out ஆகி ஒரு system exception-ஐ report பண்ணுது. Queue அந்த item-ஐ retry பண்ணுது. ஆனா முதல் Save உண்மையாவே போயிடுச்சு. Retry அந்த claim-ஐ ரெண்டாவது தடவை enter பண்ணுது, இப்போ ஒரு accident-க்கு insurer-கிட்ட ரெண்டு claims இருக்கு.

இதுக்கு fix **idempotency**: ஒரு item-ஐ ரெண்டு தடவை ஓட்டுனாலும் ஒரு தடவை ஓட்டுன அதே result தான் வரணும். நடைமுறையில:

1. **பழைய system search பண்ணக்கூடிய ஒரு unique key-ஐ தேர்ந்தெடுங்க**, உதாரணமா policy number plus date of loss.
2. **Create பண்றதுக்கு முன்னாடி search பண்ணுங்க.** ஒவ்வொரு item-ஓட ஆரம்பத்துலயும், target system-ல அந்த key-ஐ தேடுங்க. Record ஏற்கனவே இருந்தா, அதோட reference-ஐ எடுத்துக்கிட்டு அடுத்த step-க்கு போங்க.
3. **கடைசியில மட்டும் தான் item-ஐ successful-னு mark பண்ணணும்**, புது reference tracking sheet-ல திரும்ப எழுதுனதுக்கு அப்புறம்; Save-ஐ click பண்ணதும் உடனே இல்ல.

```flow
title: ஒரு idempotent queue item
அடுத்த queue item-ஐ எடு -> ஏற்கனவே claims system-ல இருக்கா?
ஏற்கனவே claims system-ல இருக்கா? -[ஆமா]-> இருக்குற claim number-ஐ படி
ஏற்கனவே claims system-ல இருக்கா? -[இல்ல]-> Form-ஐ fill பண்ணி save பண்ணு | அப்புறம் புது claim number-ஐ படி
இருக்குற claim number-ஐ படி -> Claim number-ஐ tracking sheet-ல எழுது
Form-ஐ fill பண்ணி save பண்ணு -> Claim number-ஐ tracking sheet-ல எழுது
Claim number-ஐ tracking sheet-ல எழுது -> Item-ஐ successful-னு mark பண்ணு
```

சில orchestrators அதே reference உள்ள ரெண்டாவது queue item-ஐ ஏத்துக்க மறுக்கவும் முடியும். அது duplicate வேலை queue-க்குள்ள வர்றதை தடுக்கும், ஆனா ஒரு retry target app-ல ரெண்டு தடவை save பண்றதை தடுக்காது. அதை search-before-create step மட்டும் தான் தடுக்கும்.

### Robots screen-ல விஷயங்களை எப்படி கண்டுபிடிக்குது: selectors

நல்ல RPA fixed screen positions-ல click பண்ணாது. ஒவ்வொரு element-ஐயும் அதோட properties வச்சு கண்டுபிடிக்கும்: window-ஓட title, ஒரு field-ஓட label, அதோட type. இந்த description-ஐ **selector**-னு சொல்றாங்க. அதே Policy number box-க்கு, UiPath use பண்ற style-ல, simplify பண்ண ரெண்டு selectors இதோ:

```text
Brittle:  <wnd app='claims.exe' title='Claims v4.2 - User RKUMAR' />
          <ctrl automationid='txt_4471' idx='7' />

Robust:   <wnd app='claims.exe' title='Claims*' />
          <ctrl name='Policy No*' role='editable text' />
```

Brittle selector மூணு காரணங்களால உடையும். Window title-ல ஒரு version number-உம் ஒரு user name-உம் இருக்கு, ரெண்டும் மாறும். `txt_4471`-ங்கிற id-ஐ app தானா generate பண்ணுது, அடுத்த build-ல அது மாறலாம். `idx='7'` ஒரு box-ஐ அதே மாதிரி இருக்குற boxes-ல அதோட order வச்சு எடுக்குது: அதுக்கு மேல ஒரு field சேர்த்தா robot தப்பான box-ல type பண்ணும். மத்த attributes வேலையை செய்ய முடியும்போது `idx`-ஐ தவிர்க்கணும்னு UiPath-ஓட சொந்த guidance சொல்லுது. Robust selector ஒரு ஆள் அடையாளம் கண்டுபிடிக்கக்கூடிய விஷயங்களை use பண்ணுது: app, window title-ஓட ஆரம்பம், field-ஓட label. `*` ஒரு **wildcard**, எந்த characters-ஐயும் match பண்ணும், அதனால "Claims v4.3" கூட match ஆகும். `?` சரியா ஒரே ஒரு character-ஐ match பண்ணும்.

ரெண்டு பழக்கங்கள் selectors-ஐ நீடிக்க வைக்கும். Position-ஐ விட label-ஐ prefer பண்ணுங்க. Type பண்ணதுக்கு அப்புறம், அடுத்த step-க்கு போறதுக்கு முன்னாடி value-ஐ திரும்ப படிங்க, இல்லன்னா எதிர்பார்த்த அடுத்த screen வந்துச்சான்னு check பண்ணுங்க.

### Remote desktops-உம் Citrix-உம்

சில organisations பழைய apps-ஐ **Citrix** அல்லது ஒரு remote desktop வழியா publish பண்றாங்க. அப்போ robot-க்கு screen-ஓட ஒரு படம் மட்டும் தான் தெரியும், element properties எதுவும் இல்ல. அது **image matching**-க்கு, அதாவது ஒரு button எப்படி இருக்குன்னு பார்த்து கண்டுபிடிக்கிறதுக்கு, அல்லது **OCR**-க்கு, அதாவது படத்துல இருந்து text-ஐ படிக்கிறதுக்கு, திரும்பும். Theme, font, screen resolution அல்லது display scaling மாறுனா ரெண்டுமே உடையலாம்.

முதல்ல RPA vendor-ஓட remote component-ஐ install பண்ணலாமான்னு IT team-கிட்ட கேளுங்க. உதாரணமா, UiPath-க்கு ஒரு Remote Runtime இருக்கு; அது Citrix server-ல ஓடி, robot-ஓட machine-ல இருக்குற ஒரு extension-ஓட வேலை செய்யும், அப்போ robot-க்கு திரும்ப உண்மையான selectors கிடைக்கும். அது allow இல்லன்னா, robot machine-ஓட resolution-ஐயும் scaling-ஐயும் fix பண்ணுங்க, ஒவ்வொரு image-ஐயும் பக்கத்துல இருக்குற ஒரு text label-ஓட anchor பண்ணுங்க, ஒவ்வொரு step-ஐயும் text-ஐ திரும்ப படிச்சு verify பண்ணுங்க.

### RPA, computer-use agent, இல்ல API?

**Computer-use agents**-னா screenshots-ல இருந்து screens-ஐ இயக்குற AI models; ஒவ்வொரு click-ஐயும் போற போக்குல முடிவு பண்ணும். இதுவரை பார்க்காத screens-ஐயும் அவை சமாளிக்கும், ஆனா ஒவ்வொரு step-க்கும் ஒரு model call செலவாகும், அவை slow-ஆ இருக்கும், அதே screen-ல வேற action-ஐ தேர்ந்தெடுக்கவும் செய்யலாம். Robot ஒரு claims அல்லது banking system-ல எழுதும்போது அந்த கணிக்க முடியாத தன்மையை ஏத்துக்கிறது கஷ்டம்.

| நிலைமை | Best choice | ஏன் |
| --- | --- | --- |
| System-க்கு use பண்ணக்கூடிய API இருக்கு | API integration | ரொம்ப வேகம், ரொம்ப உறுதி, clear errors |
| நிலையான screens, அதிக volume, API இல்ல | RPA | ஒரு item-க்கு செலவு கம்மி, கணிக்கலாம், audit பண்ணலாம் |
| மாறுற அல்லது பழக்கமில்லாத screens, கம்மி volume | Computer-use agent, ஒவ்வொரு மாற்றத்தையும் ஒரு ஆள் approve பண்ணணும் | RPA-வை அடிக்கடி fix பண்ண வேண்டிய இடத்துல flexible |

ஒரு நல்ல pattern இவற்றை சேர்க்கும்: நிலையான steps-க்கு RPA, எதிர்பாராத ஒரு screen-ல இருந்து மீள மட்டும் ஒரு agent, எதையும் save பண்றதுக்கு முன்னாடி ஒரு ஆள் approve பண்ணணும்.

### RPA plus AI

RPA screens வழியா data-வை நகர்த்தும்; AI documents-ஐ படிக்கும், emails-ஐ classify பண்ணும், fields-ஐ extract பண்ணும். ரெண்டும் சேர்ந்தா, தனியா எதுவும் handle பண்ண முடியாத processes-ஐ cover பண்ணும். AI step குழப்பமான input-ஐ clean fields-ஆ மாத்தும்; validation அவற்றை உங்க சொந்த data-வோட check பண்ணும்; robot validate ஆன fields-ஐ மட்டும் தான் type பண்ணும். ஒரு AI guess-ஐ robot நேரா ஒரு system of record-ல key பண்ண விடவே கூடாது.

### காசு திரும்ப வருமா? ஒரு break-even check

Robots free இல்ல. ஒன்னை build பண்றதுக்கு முன்னாடி compare பண்ணுங்க:

- **மாசத்துக்கு saving** = மாசத்துக்கு save ஆகுற hours × staff-ஓட loaded hourly cost (salary plus overheads).
- **மாசத்துக்கு cost** = licences + robot machines + AI calls, இருந்தா + maintenance hours × developer rate.

அப்புறம் ஒரு தடவை build பண்ற cost-ஐ மாசத்துக்கு net saving-ஆல divide பண்ணா payback period கிடைக்கும். ஒரு நேர்மையான rule: Free ஆன hours உண்மையாவே வேற வேலைக்கு use ஆனா மட்டும் தான் saving-ஆ கணக்கு போடணும். இல்லன்னா robot cost-ஐ மட்டும் தான் கூட்டும்.

### Robots-ஐ safe-ஆவும் ஓடிட்டும் வைக்கிறது

Screens மாறும்போது, passwords expire ஆகும்போது, pop-ups வரும்போது robots உடையும். முதல் நாள்ல இருந்தே அதுக்கு plan பண்ணுங்க:

- **Monitoring.** ஒரு run fail ஆனாலோ queue நகராம நின்னாலோ, பெயர் சொல்லி நியமிச்ச ஒரு owner-க்கு alert பண்ணுங்க. நின்னுபோன robot சத்தம் போடாது; முதல் அறிகுறி பெரும்பாலும் கோபமான ஒரு customer தான்.
- **ஒரு robot register.** ஒவ்வொரு robot-ஓட owner, அது தொடுற systems, அது use பண்ற accounts-ஐ record பண்ணுங்க.
- **Least-privilege accounts-உம் ஒரு vault-உம்.** ஒவ்வொரு robot-க்கும் அதுக்கு தேவையான access மட்டும் உள்ள தனி account குடுங்க. அதோட password-ஐ orchestrator-ஓட சொந்த store அல்லது CyberArk மாதிரி ஒரு credential vault-ல வைங்க, script-ல எப்பவுமே வைக்காதீங்க.
- **Audit logs.** ஒவ்வொரு item-ஓட key, ஒவ்வொரு step, result-ஐ log பண்ணுங்க, அப்போ robot என்ன பண்ணுச்சுன்னு prove பண்ணலாம். Phone numbers மாதிரி personal data-வை logs-ல mask பண்ணுங்க.
- **Target app மாறுறதுக்கு முன்னாடி test பண்ணுங்க.** App team-கிட்ட release dates-ஐ கேளுங்க. ஒவ்வொரு புது version live ஆகுறதுக்கு முன்னாடி அதோட test copy-ல robot-ஐ ஓட்டுங்க, அப்போ இடம் மாறுன fields production-ல இல்ல, testing-லயே தெரியும்.

## ஒரு worked example

இது typical numbers வச்சு build பண்ண ஒரு illustrative case, அளந்து பார்த்த deployment இல்ல.

Kolkata-ல ஒரு general insurer-க்கு motor claim intimations email-ல வருது: ஒரு நாளைக்கு சுமார் 300. Claims team ஒவ்வொரு email-ல இருந்தும் அதோட attachments-ல இருந்தும் details-ஐ, API இல்லாத ஒரு பழைய desktop claims system-க்கு copy பண்றாங்க. ஒவ்வொரு claim-க்கும் சுமார் 6 நிமிஷம் ஆகுது, அதனால 300 × 6 = 1,800 நிமிஷம், அதாவது ஒரு நாளைக்கு 30 மணி நேர வேலை.

**Design:**

```flow
Claim உள்ள email -> AI extraction step | policy no., vehicle no., loss நடந்த தேதி, இடம்
AI extraction step -> Policy database-ஓட validate பண்ணு
Policy database-ஓட validate பண்ணு -[ok]-> Queue item | key: policy no. plus date of loss
Policy database-ஓட validate பண்ணு -[ok இல்ல]-> ஒரு ஆளோட queue | காரணமும் ஒரு screenshot-உம்
Queue item -> Unattended robot | முதல்ல search, கிடைக்கலன்னா create
Unattended robot -[app crash]-> App-ஐ restart பண்ணி retry | system exception, 3 tries வரை
App-ஐ restart பண்ணி retry -> Unattended robot
Unattended robot -[screen அடையாளம் தெரியல]-> ஒரு ஆளோட queue
Unattended robot -> Claim number திரும்ப tracking sheet-க்கு
```

1. ஒரு **AI extraction step** ஒவ்வொரு email-ஐயும் attachment-ஐயும் படிச்சு fields-ஐ தரும்: policy number, vehicle number, loss நடந்த தேதி, இடம், description.
2. Fields policy database-ஓட **validate** ஆகும்: policy இருக்கா, active-ஆ இருக்கா, vehicle match ஆகுதா? Fail ஆனவை business exceptions, காரணத்தோட ஒரு ஆள்கிட்ட போகும்.
3. Valid claims, policy number plus date of loss-ஐ key-ஆ வச்சு **queue items** ஆகும்.
4. ஒரு **unattended robot** claims system-ல அந்த key-ஐ search பண்ணும். Claim இல்லன்னா, "New intimation"-ஐ open பண்ணி, fields-ஐ fill பண்ணி, save பண்ணி, புது claim number-ஐ படிச்சு, அதை tracking sheet-ல எழுதும். அதுக்கு அப்புறம் தான் item successful-னு mark ஆகும்.
5. App crashes system exceptions: restart பண்ணி retry, மூணு தடவை வரை. Robot-க்கு அடையாளம் தெரியாத எந்த screen-உம் ஒரு screenshot-ஓட ஒரு ஆள்கிட்ட போகும்.

**முதல் quarter எப்படி இருக்கலாம்:**

| அளவு | முன்னாடி | அப்புறம் |
| --- | --- | --- |
| Data entry-ல staff நேரம் | ஒரு நாளைக்கு சுமார் 30 மணி நேரம் | ஒரு நாளைக்கு சுமார் 6 மணி நேரம், பெரும்பாலும் exceptions |
| அதே நாள்ல enter ஆன claims | சுமார் 70% | சுமார் 98% |
| Robot outages | பொருந்தாது | 2, ரெண்டுமே system updates fields-ஐ இடம் மாத்துனதுக்கு அப்புறம் |
| Retries-ஆல வந்த duplicate claims | பொருந்தாது | 0, search-before-create-னால |

**காசு திரும்ப வருமா?** இந்த assume பண்ண figures-ஐ use பண்ணுங்க; முடிவு பண்றதுக்கு முன்னாடி உண்மையான quotes-ஐ வாங்குங்க.

- Save ஆன hours: 30 − 6 = ஒரு நாளைக்கு 24. 25 working days-ல, அது மாசத்துக்கு 600 hours.
- Loaded staff cost ஒரு மணி நேரத்துக்கு ₹400-னு வச்சுக்குங்க. Saving: 600 × ₹400 = மாசத்துக்கு ₹2,40,000.
- Running costs மாசத்துக்கு licences, robot machines-க்கு ₹1,00,000, AI extraction-க்கு ₹15,000, ஒரு மணி நேரத்துக்கு ₹1,000-ல 20 maintenance hours (₹20,000)-னு வச்சுக்குங்க. மொத்தம்: ₹1,35,000.
- Net saving: ₹2,40,000 − ₹1,35,000 = மாசத்துக்கு ₹1,05,000. Build பண்ண ₹6,00,000 ஆனா, payback-க்கு சுமார் 6 மாசம் ஆகும்.

இப்போ இதை திருப்பி பாருங்க. ஒவ்வொரு claim-உம் 6 நிமிஷம் × 24/30 = 4.8 நிமிஷம், அதாவது 0.08 hours save பண்ணுது, அதனால ஒரு claim-ஓட மதிப்பு 0.08 × ₹400 = ₹32. 25 நாள்ல மாசத்துக்கு ₹1,35,000-ஐ cover பண்ண, robot-க்கு ₹1,35,000 ÷ (25 × ₹32), அதாவது ஒரு நாளைக்கு சுமார் 170 claims வேணும். இந்த assumptions-படி, ஒரு நாளைக்கு சுமார் 170 claims-க்கு கீழ போனா robot நஷ்டம் தான். Case-ஐ முடிவு பண்றது volume தான், robot எவ்வளவு புத்திசாலின்னு இல்ல.

Claims system upgrade ஆகும்போது robot-ஐ ஒரு direct API integration-ஆல replace பண்ண insurer plan பண்றாங்க. அதுவரை robot தான் பாலம்; எல்லா logic-உம் document பண்ண ஒரே queue process-ல இருக்குறதால, அதை retire பண்றதும் செலவு கம்மி.

## பொதுவா பண்ற தப்புகள்

- **API இருக்குற இடத்துல RPA-வை use பண்றது.** API வேகம், உறுதி, clear errors-உம் தரும். Build பண்றதுக்கு முன்னாடி vendor அல்லது IT team-கிட்ட கேளுங்க.
- **Positions, generated ids அல்லது index numbers-ஓட கட்டின selectors.** Labels-உம் wildcards-உம் use பண்ணுங்க, type பண்ணதுக்கு அப்புறம் values-ஐ திரும்ப படிங்க.
- **எல்லாத்தையும் retry பண்றது, இல்லன்னா எதையுமே retry பண்ணாம இருக்குறது.** Business exceptions-ஐ ஒரு ஆள்கிட்ட அனுப்புங்க; system exceptions-ஐ ஒரு fixed எண்ணிக்கை வரை retry பண்ணுங்க.
- **Create பண்றதுக்கு முன்னாடி search இல்ல.** Save-க்கு அப்புறம் ஒரே ஒரு timeout போதும், retry ஒரு duplicate record-ஐ create பண்ணிடும்.
- **ஒரு item-ஐ ரொம்ப சீக்கிரமா done-னு mark பண்றது.** Reference திரும்ப எழுதுனதுக்கு அப்புறம் மட்டும் தான் successful-னு mark பண்ணுங்க.
- **மாறிக்கிட்டே இருக்குற ஒரு process-ஐ automate பண்றது.** முதல்ல process-ஐ fix பண்ணுங்க அல்லது நிலைப்படுத்துங்க; ஒரு robot இன்னைக்கு இருக்குற குழப்பத்தை அப்படியே உறைய வச்சிடும்.
- **Owner இல்ல, alerts இல்ல.** உடைஞ்ச unattended robots சத்தமில்லாம fail ஆகும், வேலை குவிஞ்சுக்கிட்டே போகும்.
- **Admin accounts உள்ள robots, அல்லது scripts-ல passwords.** Least-privilege accounts-உம் ஒரு vault-உம் use பண்ணுங்க.
- **கணக்கு போடாமலே build பண்றது.** கம்மி volume-ல, save ஆகுற நேரத்தை விட licences-உம் maintenance-உம் அதிகமா செலவாகலாம்.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற UiPath Academy-ல ஒரு free beginner course எடுங்க. நீங்க Windows 11-ல இருந்தா, ஏற்கனவே install ஆகியிருக்குற Power Automate for desktop-லயும் practice பண்ணலாம். கீழ link பண்ணியிருக்குற Microsoft Learn path, Power Automate cloud flows-ஐ cover பண்ணுது; API பக்கத்துக்கு அது ஒரு useful companion.

1. **Build பண்ணுங்க.** ஒரு spreadsheet-ல இருந்து rows-ஐ படிச்சு, ஒவ்வொரு row-க்கும் ஒரு web அல்லது desktop form-ஐ fill பண்ணி, save பண்ணி, ஒரு confirmation number-ஐ sheet-ல திரும்ப எழுதுற ஒரு robot-ஐ உருவாக்குங்க.
2. **அதை உடைங்க.** Window-ஐ resize பண்ணுங்க, display scaling-ஐ மாத்துங்க, target box-க்கு மேல ஒரு field சேருங்க. ஒவ்வொரு failure-ஐயும் better selectors வச்சு fix பண்ணுங்க, type பண்ணதுக்கு அப்புறம் ஒரு read-back check சேருங்க.
3. **Idempotent ஆக்குங்க.** அதே sheet-ஐ ரெண்டு தடவை ஓட்டுங்க. ரெண்டாவது run எதையும் புதுசா create பண்ணக்கூடாது; ஒவ்வொரு record-ஐயும் கண்டுபிடிச்சு அதோட ஏற்கனவே இருக்குற number-ஐ எடுத்துக்கணும்.
4. **தேர்ந்தெடுத்து, செலவை கணக்கு போடுங்க.** உங்க workplace அல்லது college-ல ஒரு process-க்கு, RPA, ஒரு API, ஒரு computer-use agent-ல எதுன்னு முடிவு பண்ணுங்க, உங்க சொந்த assume பண்ண figures வச்சு அதோட break-even volume-ஐ கணக்கு போடுங்க.

**நீங்க முடிச்சிட்டீங்கன்னு அர்த்தம், எப்போன்னா** ஒரு API அல்லது AI agent-ஐ விட RPA-வை எப்போ தேர்ந்தெடுப்பீங்கன்னு explain பண்ண முடியும்போது, ஒரு சின்ன layout மாற்றத்தையும் duplicates இல்லாத ஒரு ரெண்டாவது run-ஐயும் தாங்குற robot-ஐ காட்ட முடியும்போது, ஒரு உண்மையான process-க்கு ஒரு break-even volume-ஐ சொல்ல முடியும்போது.
