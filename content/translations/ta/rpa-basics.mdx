## இது என்ன

நிறைய இந்திய businesses இன்னும் வேற எதோடயும் பேச முடியாத software-ல ஓடுது: 15 வருஷ பழைய desktop ERP, ஒரு bank-ஓட back-office screens, API இல்லாத ஒரு government portal. மக்கள் தங்க நாளை ஒரு screen-ல இருந்து இன்னொண்ணுக்கு values-ஐ copy பண்றதுலயே கழிக்கிறாங்க. **Robotic process automation (RPA)** அந்த copy பண்ற வேலையை எடுத்துக்கும்.

RPA, ஒரு ஆள் செய்யுற மாதிரி, applications-ஐ அவற்றோட **user interface** வழியா இயக்குற software "robots"-ஐ use பண்ணும்: programs-ஐ திறக்கும், buttons-ஐ click பண்ணும், fields-ல type பண்ணும், screens-ல இருந்து values-ஐ copy பண்ணும், reports-ஐ download பண்ணும். Systems-க்கு API இல்லாத இடத்துல, அல்லது integration build பண்ண ரொம்ப நேரம் ஆகுற இடத்துல இதை use பண்றோம்.

```flow
dir: LR
title: API automation: வேகம், உறுதி, இதுவே விருப்பம்
System A, API இருக்கு -[data, நேரடியா]-> System B, API இருக்கு
```

```flow
dir: LR
title: RPA: ஒரு ஆள் வேலை செய்யுற எங்கயும் work ஆகும், ஆனா அதிக உடையக்கூடியது
Robot | UiPath, Power Automate Desktop -[screen-ல clicks, typing]-> பழைய desktop app, API இல்லை
```

முன்னணி RPA tools-ல **UiPath**, **Automation Anywhere**, **Microsoft Power Automate Desktop** இருக்கு. Steps-ஐ record பண்ணலாம் அல்லது design பண்ணலாம், அப்புறம் ஒரு schedule-ல அல்லது தேவைப்படும்போது, ஒரு desktop-லயோ server-லயோ run பண்ணலாம்.

இந்த lesson-ல Kolkata-ல ஒரு general insurer-ஓட claims team-ஐ follow பண்றோம்; ஒரு AI step-உம் ஒரு RPA robot-உம் சேர்ந்து, ஒரு பழைய claims system-ல data entry-ஐ எடுத்துக்குது. Lesson முடியும் போது, RPA எப்போ சரியான tool-ஆ இருக்கும்னும், அதை ஓட வைக்க என்ன செலவாகும்னும் தெரிஞ்சுக்குவீங்க.

## இது எப்படி work ஆகுது

### Attended, unattended robots

| Type | எப்போ ஓடும் | உதாரணம் |
| --- | --- | --- |
| **Attended** | ஒரு ஆள் start பண்ணும்போது, அவங்க computer-ல | Agent "Go" click பண்ணதுக்கு அப்புறம், 40-field form-ஐ நிரப்புற ஒரு robot |
| **Unattended** | தானா, தனி machines-ல, ஒரு queue-ஐ வேலை செய்யும் | ராத்திரி முழுக்க 300 claims-ஐ உள்ளிடுற ஒரு robot |

### Robots screen-ல எப்படி விஷயங்களை கண்டுபிடிக்குது

நல்ல RPA, நிலையான screen positions-ல click பண்ணாது. அது elements-ஐ அவற்றோட properties வச்சு அடையாளம் காணும்: ஒரு button-ஓட பேர், ஒரு field-ஓட label, ஒரு web page-ஓட structure. இந்த identifiers-க்கு **selectors**ன்னு பேரு. அப்போ சின்ன layout மாற்றங்கள் robot-ஐ உடைக்காது.

Properties கிடைக்காத பழைய applications-க்கோ remote desktops-க்கோ, robots **image matching** அல்லது **OCR**-ஐ நம்பலாம்; இவை அதிக உடையக்கூடியவை: ஒரு colour அல்லது font மாறினாலே உடையலாம்.

### RPA எங்க பொருந்தும்

- Legacy desktop applications, பழைய ERPs, banking back-office screens மாதிரி; APIs இல்லாத portals.
- அதிக volume, நிலையான, rule-based tasks: systems-க்கு நடுவுல data-வை copy பண்றது, தினசரி reports-ஐ உருவாக்கி download பண்றது, orders-ஐ உள்ளிடுறது.
- ஒரு சரியான integration build ஆகுற வரை ஒரு பாலம்.

### RPA எங்க பொருந்தாது

| நிலைமை | சிறந்த தேர்வு |
| --- | --- |
| System-க்கு ஒரு நல்ல API இருக்கு | API-ஐ use பண்ணுங்க: வேகம், உறுதி |
| Process அல்லது screens அடிக்கடி மாறுது | முதல்ல process-ஐ சரி பண்ணுங்க, அல்லது காத்திருங்க |
| பலவிதமான inputs-ல judgement தேவை | ஒரு AI step-உம் ஒரு ஆளும்; data entry-க்கு மட்டும் RPA |

### RPA-வும் AI-உம் சேர்ந்து

RPA screens வழியா data-வை நகர்த்தும்; AI documents-ஐ படிக்கும், emails-ஐ classify பண்ணும், அடுத்த step-ஐ முடிவு பண்ணும். சேர்ந்து, ரெண்டுல ஒண்ணால மட்டும் handle பண்ண முடியாத processes-ஐ cover பண்ணும்:

```flow
Claim இருக்குற Email -> AI step | email-ஐயும் attachment-ஐயும் படிச்சு; policy no., vehicle no., date, place-ஐ எடு
AI step -> Policy database-ஓட validate பண்ணு
Policy database-ஓட validate பண்ணு -[சரி]-> RPA robot | பழைய claims system-ல type பண்ணும்
Policy database-ஓட validate பண்ணு -[சரியில்ல]-> ஒரு ஆளோட queue | screenshots-ஓட
RPA robot -> Claim number tracking sheet-க்கு திரும்ப
```

**Computer-use agents**, அதாவது screenshots-ல இருந்து screens-ஐ இயக்குற AI, புதுசு, அதிக flexible, ஆனா design பண்ண RPA steps-ஐ விட மெதுவு, செலவு அதிகம், எதிர்பார்க்க கஷ்டம். பொதுவான pattern: நிலையான steps-க்கு RPA, மாறுபாட்டுக்கு judgement தேவைப்படுற இடத்துல மட்டும் AI.

### Running costs-உம் governance-உம்

Screens மாறும்போது, passwords expire ஆகும்போது, எதிர்பாராத pop-ups வரும்போது robots உடையும். இவற்றுக்கு budget போடுங்க:

- RPA platform-க்கும் robot machines-க்கும் **licences**;
- **monitoring**, அதனால நின்னு போன robot ஒரு alert-ஐ raise பண்ணும்;
- **maintenance**, selectors-ஐ வேகமா சரி பண்ணக்கூடிய ஒருத்தர்.

ஒவ்வொரு robot-க்கும் ஒரு register வச்சிருங்க: அதோட owner, அது தொடுற systems, அது use பண்ற credentials. Robots-க்கு **least-privilege** accounts கொடுங்க, அவற்றுக்கு தேவையான access மட்டும்; அவற்றோட passwords-ஐ robot-ஓட script-ல இல்லாம, ஒரு vault-ல store பண்ணுங்க.

## ஒரு உதாரணம்

Kolkata-ல ஒரு general insurer, motor claim intimations-ஐ email-ல பெறுது: ஒரு நாளைக்கு சுமார் 300. Claims team ஒவ்வொரு email-ல இருந்தும் அதோட attachments-ல இருந்தும் விவரங்களை, API இல்லாத ஒரு பழைய desktop claims system-க்கு copy பண்றாங்க. ஒவ்வொரு claim-க்கும் சுமார் 6 நிமிஷம், team முழுக்க ஒரு நாளைக்கு கிட்டத்தட்ட 30 மணி நேர வேலை.

**தீர்வு:**

1. ஒரு **AI extraction step** ஒவ்வொரு intimation email-ஐயும் attachment-ஐயும் படிச்சு, structured fields-ஐ உருவாக்குது: policy number, vehicle number, இழப்பு நடந்த date, இடம், விளக்கம்.
2. அந்த fields policy database-ஓட **validate** ஆகுது: policy இருக்கா, active-ஆ இருக்கா, vehicle பொருந்துதா?
3. ஒரு **unattended RPA robot** claims system-ஐ திறந்து, "New intimation"-க்கு போய், validate ஆன fields-ஐ நிரப்பி, save பண்ணி, புது claim number-ஐ tracking sheet-ல திரும்ப எழுதுது.
4. Validation fail ஆனவை, robot அடையாளம் காணாத எந்த screen-உம், screenshots-ஓட **ஒரு ஆளோட queue**-க்கு போகுது.

**முதல் quarter-ல results:**

| Measure | Before | After |
| --- | --- | --- |
| Data entry-க்கு staff நேரம் | ஒரு நாளைக்கு சுமார் 30 மணி நேரம் | ஒரு நாளைக்கு சுமார் 6 மணி நேரம், பெரும்பாலும் exceptions |
| அதே நாள்ல உள்ளிடப்பட்ட claims | சுமார் 70% | சுமார் 98% |
| Robot outages | பொருந்தாது | 2, ரெண்டுமே system updates fields-ஐ நகர்த்தினதுக்கு அப்புறம் |
| ஒவ்வொரு outage-ஐயும் சரி பண்ண நேரம் | பொருந்தாது | ஒரு நாளுக்குள்ள; monitoring RPA developer-க்கு alert பண்ணுச்சு |

அடுத்த வருஷம் claims system upgrade ஆகும்போது, robot-ஐ ஒரு நேரடி API integration-ஆல மாத்த insurer திட்டமிட்டிருக்கு. அது வரைக்கும், robot தான் பாலம்.

## பொதுவா பண்ற தப்புகள்

- **API இருக்குற இடத்துல RPA.** APIs வேகம், உறுதி.
- **நிலையான screen positions.** சின்ன மாற்றங்கள் robots-ஐ உடைக்காம இருக்க element properties use பண்ணுங்க.
- **நிலையில்லாத processes-ஐ automate பண்றது.** Process அல்லது screens மாறும்போதெல்லாம் robots உடையும்.
- **Monitoring அல்லது owner இல்லாம இருக்குறது.** உடைஞ்ச robots சத்தமில்லாம fail ஆகும், வேலை யாருக்கும் தெரியாம குவியும்.
- **Admin credentials இருக்குற robots.** ஒரு vault-ல store பண்ண least-privilege accounts use பண்ணுங்க.
- **வெளியேறும் வழிகளை மறக்குறது.** எந்த cases ஒரு ஆள்கிட்ட போகும்னு plan பண்ணி, அந்த queue-ஐ வேலை செய்ய எளிதா ஆக்குங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற UiPath Academy-ல ஒரு free beginner course-ஐ எடுங்க, அல்லது Microsoft Learn-ல இருக்குற Power Automate Desktop modules-ஐ பாருங்க.

1. **Build.** ஒரு website அல்லது desktop app-ஐ திறந்து, ஒரு spreadsheet row-ல இருந்து ஒரு form-ஐ நிரப்பி, ஒரு confirmation-ஐ save பண்ற ஒரு simple robot-ஐ செய்யுங்க.
2. **உடைங்க.** Window-வை resize பண்ணி, அல்லது screen resolution-ஐ மாத்தி, layout-ஐ கொஞ்சம் மாத்தி, அது இன்னும் work ஆகுதான்னு பாருங்க. நல்ல selectors வச்சு சரி பண்ணுங்க.
3. **தேர்ந்தெடுங்க.** உங்க organisation-ல ஒரு process-க்கு, RPA, API integration, AI agent இதுல எது சிறந்தது, ஏன்னு எழுதுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு API அல்லது ஒரு AI agent-ஐ விட RPA-ஐ எப்போ தேர்ந்தெடுப்பீங்கன்னு explain பண்ணி, ஒரு சின்ன layout மாற்றத்தையும் தாங்குற ஒரு robot-ஐ காட்ட முடியும்.
