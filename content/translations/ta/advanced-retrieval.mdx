## இது என்ன

நல்ல hybrid search-உம் query-யும் document-உம் ஒரே மாதிரி இல்லாதப்போ fail ஆகும். மூணு techniques, நீங்க எதை வச்சு search பண்றீங்க அல்லது எதை return பண்றீங்கன்னதை மாத்தும்:

- **Query rewriting**: ஒரு model, user-ஓட message-ஐ இன்னும் நல்ல search queries-ஆ மாத்தும்.
- **HyDE** (hypothetical document embeddings): ஒரு model நம்பும்படியான ஒரு பதிலை எழுதும், அதை வச்சு நீங்க search பண்ணுவீங்க.
- **Parent-child chunks**: துல்லியத்துக்கு சின்ன chunks-ல search பண்ணி, அப்புறம் ஒவ்வொண்ணும் வந்த பெரிய section-ஐ model-க்கு கொடுப்பீங்க.

ஒவ்வொண்ணுக்கும் ஒரு விலை இருக்கு, பெரும்பாலும் ஒரு கூடுதல் model call அல்லது அதிக tokens; அதனால அது சரி பண்ற problem-ஐ உங்க golden set காட்டும்போது மட்டும் ஒண்ணை சேருங்க.

```flow
User: "And for senior citizens?" -> chat history வச்சு Query rewrite | "FD interest rate for senior citizens"
chat history வச்சு Query rewrite -> சின்ன queries-க்கு optional HyDE | ஒரு போலி பதிலை எழுதி, அதை embed பண்ணு
சின்ன queries-க்கு optional HyDE -> சின்ன child chunks-ல search | c17, c18, c42
சின்ன child chunks-ல search -> Parent sections-ஐ எடுத்து, duplicates-ஐ நீக்கு | section 3.2, section 7.1
Parent sections-ஐ எடுத்து, duplicates-ஐ நீக்கு -> Model-க்கு prompt | கேள்வி + parent sections
```

இந்த lesson-ல Delhi-ல ஒரு bank-ஓட internal assistant, 900 pages circulars-ல இருந்து staff கேள்விகளுக்கு பதில் சொல்றதை follow பண்றோம்.

## இது எப்படி work ஆகுது

**Query rewriting** பல வகையான மோசமான queries-ஐ handle பண்ணும்:

- *Follow-ups.* "And for senior citizens?" தனியா இருந்தா அர்த்தமே இல்ல. Chat history வச்சு "Fixed deposit interest rate for senior citizens"-ஆ rewrite பண்ணுங்க.
- *கலந்த கேள்விகள்.* "Compare the cancellation rules for Gold and Platinum cards" ரெண்டு queries-ஆ ஆகும், ஒவ்வொரு card-க்கும் ஒண்ணு, results merge ஆகும்.
- *Jargon gaps.* Users "PF withdrawal"ன்னு எழுதுவாங்க; documents-ல "provident fund advance"ன்னு இருக்கும். Rewrite synonyms சேர்க்கலாம், அல்லது மூணு விதமா எழுதி ("multi-query") results-ஐ merge பண்ணலாம்.

ஒரு சின்ன, வேகமான model இதை நல்லா பண்ணும். Rewrites-ஐ log பண்ணுங்க: retrieval fail ஆகும்போது, பெரும்பாலும் rewrite தான் காரணம்.

**HyDE.** ஒரு கேள்வி சின்னது, கேள்வியா எழுதப்பட்டது; அதுக்கு பதில் சொல்ற passage நீளமானது, ஒரு statement-ஆ எழுதப்பட்டது. அவற்றோட embeddings ரொம்ப தூரத்துல இருக்கலாம். HyDE, ஒரு model-கிட்ட சின்ன, தப்பாவும் இருக்கலாம்ங்குற ஒரு பதிலை எழுத சொல்லி, அதை embed பண்ணி, அதை வச்சு search பண்ணும். போலி பதில் உண்மையான passage மாதிரியே இருக்குறதால, அதுக்கு பக்கத்துல போய் விழும். Queries சின்னதா, documents formal-ஆ இருக்கும்போது இது ரொம்ப உதவும். Model-ஓட யூகம் confident-ஆ தலைப்புக்கு சம்பந்தமில்லாம இருந்தா கெடுதல் பண்ணும், ஒவ்வொரு search-க்கு முன்னாடியும் ஒரு model call-ஐயும் சேர்க்கும்.

**Parent-child chunks.** சின்ன chunks (100-ல இருந்து 200 tokens) துல்லியமா match ஆகும், ஆனா பதில் சொல்ல தேவையான சுத்தி இருக்குற context பெரும்பாலும் இருக்காது: ரெண்டு paragraphs அப்புறம் வர்ற exception, table header மாதிரி. பெரிய chunks context கொடுக்கும், ஆனா மோசமா match ஆகும். அதனால சின்ன "child" chunks-ஐ index பண்ணி, ஒவ்வொண்ணும் அதோட "parent"-ஓட (section அல்லது page) id-ஐ வச்சிருக்கும். Children-ஐ search பண்ணி, அப்புறம் prompt-க்காக அவற்றோட parents-ஐ எடுத்து, duplicates-ஐ நீக்குங்க. சில நேரம் sentence-window retrieval-ன்னு சொல்லப்படுற ஒரு variant, match-க்கு ரெண்டு பக்கமும் சில வாக்கியங்களை return பண்ணும்.

**ஒவ்வொரு technique-ஓட cost, benefit:**

| Technique | எதை சரி பண்ணும் | கூடுதல் cost | எதுக்கு route பண்றது |
| --- | --- | --- | --- |
| Query rewriting | Follow-ups, கலந்த கேள்விகள், jargon gaps | ஒரு சின்ன model call | முதல் turn-க்கு அப்புறம் வர்ற chat turns; நீளமான அல்லது கலந்த queries |
| Multi-query | Jargon, phrasing gaps | ஒரு call, பல searches | Top scores குறைவா இருக்குற queries |
| HyDE | சின்ன, தெளிவில்லாத queries | ஒரு model call | சுமார் எட்டு வார்த்தைகளுக்கு குறைவான queries |
| Parent-child | துல்லியமான match-ஐ சுத்தி context இல்லாதது | அதிக prompt tokens | Chunks build ஆனதும், எல்லா queries |

Routing முக்கியம்: ஏற்கனவே work ஆகுற queries-ல எல்லா techniques-ஐயும் run பண்ணா, latency-யும் cost-உம் கூடும், ஆனா பெரிய பலன் இருக்காது.

**Rewriting, multi-query, HyDE-ஐ code-ல.** ஒரே சின்ன, வேகமான model மூணையும் handle பண்ணும்:

```python
import anthropic

client = anthropic.Anthropic()
FAST = "claude-haiku-5-5"                         # check the docs for current names

def ask(prompt, max_tokens=200):
    r = client.messages.create(model=FAST, max_tokens=max_tokens,
                               messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in r.content if b.type == "text").strip()

def standalone(question, last_turns):
    history = "\n".join(f"{t['role']}: {t['text']}" for t in last_turns[-4:])
    return ask(f"Rewrite the last question so it makes sense on its own. Reply with the question only.\n\n"
               f"{history}\nuser: {question}")

def variants(question, n=3):
    text = ask(f"Write {n} different ways a bank's policy documents might phrase this question. "
               f"One per line, no numbering.\n\n{question}")
    return [question] + [l for l in text.splitlines() if l.strip()][:n]

def hyde(question):
    return ask(f"Write a short, formal policy paragraph that would answer: {question}", max_tokens=150)

def route(question, history, search):
    q = standalone(question, history) if history else question
    if len(q.split()) < 8:
        return search(hyde(q))                     # short and vague: search with a fake answer
    if " and " in q or " vs " in q or "compare" in q.lower():
        results = [search(v) for v in variants(q)]
        return fuse(results)                       # reciprocal rank fusion, as in the RAG lesson
    return search(q)
```

அசல் கேள்வி, ஒவ்வொரு rewrite, எந்த route run ஆச்சுன்னு log பண்ணுங்க. ஒரு பதில் தப்பா போகும்போது, பெரும்பாலும் rewrite தான் காரணம்.

**Code-ல parent-child.** Children-ஐ `parent_id`-ஓட store பண்ணி, children-ஐ search பண்ணி, parents-ஐ ஒரு தடவை மட்டும் return பண்ணுங்க:

```python
def parent_child(question, search_children, get_parent, k_children=12, k_parents=4):
    seen, parents = set(), []
    for child in search_children(question, k=k_children):
        if child["parent_id"] not in seen:
            seen.add(child["parent_id"])
            parents.append(get_parent(child["parent_id"]))
        if len(parents) == k_parents:
            break
    return parents
```

**Contextual retrieval.** Ingestion-ல, ஒவ்வொரு chunk-ஐயும் அதோட document-ல நிறுத்துற ஒண்ணு-ரெண்டு வாக்கியங்களை ("This is from the 2026 FD rates circular, section on senior citizens") எழுத ஒரு model-கிட்ட சொல்லி, embedding, keyword indexing ரெண்டுக்கும் முன்னாடி அதை சேருங்க. Anthropic தன்னோட tests-ல இது failed retrievals-ஐ சுமார் பாதியா குறைச்சுதுன்னும், reranking-ஓட சேர்ந்தா சுமார் மூணுல ரெண்டு பங்கா குறைச்சுதுன்னும் report பண்ணுச்சு. இதுக்கு ஒரு chunk-க்கு ஒரு call, ஒரே ஒரு தடவை செலவாகும்; முழு document-ஐ cached prompt-ல வச்சா, அந்த cost நிறைய குறையும்.

**ஒவ்வொரு technique-ஐயும் அதோட target-ல தனியா அளந்து பாருங்க.** Follow-ups, சின்ன queries, கலந்த queries-க்கு recall-ஐ technique on, off-ஓட தனித்தனியா report பண்ணுங்க. ஒரு technique தெளிவா உதவுற query types-க்கு மட்டும் அதை வச்சுக்கோங்க.

## ஒரு worked example

Delhi-ல ஒரு bank-ஓட internal assistant, 900 pages circulars-ல இருந்து staff கேள்விகளுக்கு பதில் சொல்லுது. Golden set மூணு failure clusters-ஐ காட்டுது.

*Follow-ups fail ஆகுது.* Home loan prepayment பத்தின கேள்விக்கு அப்புறம் "What about NRIs?" கேட்டா, NRI account rules retrieve ஆகுது. கடைசி ரெண்டு turns-ஐ use பண்ற ஒரு rewrite step-ஐ சேர்க்குறீங்க: query "home loan prepayment charges for NRI borrowers" ஆகுது. Follow-up கேள்விகள்ல recall at 5, 41%-ல இருந்து 83%-க்கு ஏறுது.

*சின்ன கேள்விகள் fail ஆகுது.* "KYC refresh period?" KYC-ஐ சும்மா குறிப்பிடுற pages-ஓட match ஆகுது. HyDE இதை generate பண்ணுது: "Customers classified as high risk must update KYC every two years, medium risk every eight years and low risk every ten years." அதோட embedding உண்மையான periodic-update clause-க்கு பக்கத்துல விழுது. சின்ன queries-ல recall at 5, 58%-ல இருந்து 74%-க்கு போகுது. நீளமான, குறிப்பிட்ட கேள்விகள்ல HyDE எந்த வித்தியாசமும் பண்ணல; அதனால எட்டு வார்த்தைகளுக்கு குறைவான queries-ஐ மட்டும் அதுல route பண்றீங்க.

*பதில்கள் exceptions-ஐ miss பண்ணுது.* சரியான 150-token chunk கிடைக்குது, ஆனா priority-sector loans-க்கான exception அடுத்த paragraph-ல இருக்குறதால, பதில்கள் தப்பா வருது. Parent-child-க்கு மாறுனா (150 tokens children, ஒரு sub-section அளவு parents), அப்படிப்பட்ட 11 cases-ல 9-ஐ சரி பண்ணுது; விலையா சுமார் 40% அதிக prompt tokens.

| Failure cluster | Fix | முன்னாடி Recall at 5 | பின்னாடி |
| --- | --- | --- | --- |
| Follow-up கேள்விகள் | கடைசி ரெண்டு turns-ஓட rewrite | 41% | 83% |
| சின்ன கேள்விகள் | எட்டு வார்த்தைகளுக்கு குறைவான queries-க்கு HyDE | 58% | 74% |
| Miss ஆன exceptions | Parent-child chunks | 11-ல 11 fail | 11-ல 2 fail |

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்தையும் ஒரே நேரத்துல சேர்க்கிறது.** எந்த மாற்றம் உதவுச்சுன்னு உங்களால சொல்ல முடியாது. ஒண்ணை சேருங்க, அளந்து பாருங்க, வச்சுக்கோங்க அல்லது எடுத்துடுங்க.
- **உரையாடல் இல்லாம rewrite பண்றது.** தனியா rewrite பண்ண follow-up இன்னும் அர்த்தமில்லாம தான் இருக்கும்.
- **HyDE-ஓட text-ஐ நம்புறது.** Hypothetical answer ஒரு search key மட்டும் தான். அதை user-க்கு காட்டவே கூடாது, final prompt-க்குள்ளயும் விடக்கூடாது.
- **பெரிய parents.** 20-page முழு documents-ஐ return பண்ணா context budget வெடிச்சு, பதில் புதைஞ்சுடும். Parents sections-ஆ இருக்கணும், files-ஆ இல்ல.
- **Latency-ஐ கண்டுக்காம இருக்குறது.** Retrieval-க்கு முன்னாடி ரெண்டு கூடுதல் model calls, response time-ஐ ரெண்டு மடங்காக்கலாம். சின்ன model use பண்ணி, அளந்து பாருங்க.
- **Rewrites-ஐ log பண்ணாம இருக்குறது.** மோசமான rewrite, retrieval failure மாதிரியே தெரியும்.
- **ஒவ்வொரு query-க்கும் எல்லா techniques-ஐயும் ஆன் பண்றது.** Query type வச்சு route பண்ணி, அளந்து பாருங்க.

## அடிப்படை retrieval போதுமான நேரங்கள்

- **Chat history இல்லாத தனி கேள்விகள்**, documents-ஓட சொந்த மொழியிலயே எழுதப்பட்டவை.
- **சின்ன, நல்லா structure ஆன collections**, அங்க சாதாரண hybrid search ஏற்கனவே சரியான passage-ஐ கண்டுபிடிக்கும்.
- **இறுக்கமான latency budgets**, அங்க search-க்கு முன்னாடி ஒரு கூடுதல் model call ரொம்ப மெதுவு.
