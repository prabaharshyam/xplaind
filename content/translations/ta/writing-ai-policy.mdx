## இது என்ன

**AI policy** ஒரு organisation AI-ஐ எப்படி use பண்ணி, build பண்ணுதுங்குறதுக்கான rules-ஐ வகுக்கும். அது இல்லன்னா மக்கள் ஊகிக்கிறாங்க: சிலர் AI-ஐ முழுசா தவிர்த்து பின்தங்கிடுறாங்க, சிலர் client data-வை free tools-ல paste பண்றாங்க. நல்ல policy பாதுகாப்பான வழியை எளிதான வழியா மாத்தும்.

நல்ல முதல் policy **ரெண்டு முதல் நாலு பக்கம்**, வக்கீல்களுக்கு இல்லாம employees-க்கு எழுதினது, ஆறு மாசத்துக்கு ஒரு தடவை review பண்ணது. இதுல பெரும்பாலும் ரெண்டு பகுதிகள் இருக்கும்:

| பகுதி | யாருக்கு பொருந்தும் | என்ன கவர் பண்ணும் |
| --- | --- | --- |
| **AI tools-ஐ use பண்றது** | எல்லாருக்கும் | எந்த tools, எந்த data, என்ன review, disclosure |
| **AI features build பண்றது** | Product, engineering teams | Risk assessment, testing, oversight, monitoring, launch-க்கு முன்னாடி approval |

| Policy-ஓட பகுதி | என்ன சொல்லுது |
|---|---|
| Principles | 3-5 சின்ன commitments |
| Approved tools | பேர் சொல்லி, settings-ஓட |
| Data classes | Public, internal, confidential, personal: எந்த tools எதை பார்க்கலாம் |
| Use cases | ஊக்குவிக்கப்படுறது, restrict பண்ணது, தடை பண்ணது |
| Review | யாரு accountable, எதை review பண்றது |
| Disclosure | AI use பண்ணதை customers-க்கு எப்போ சொல்றது |
| AI build பண்றது | Risk assessment, அப்புறம் evals, அப்புறம் approval |
| Incidents | எப்படி report பண்றது, blame இல்லாம |
| Training | எல்லாருக்கும் 30 நிமிஷம், regular updates-ஓட |

Pune-ல ஒரு software services company-ல delivery head Neha-வை இந்த lesson follow பண்ணும். ஒரு client-ஓட security review, அந்த company-யை முதல் AI policy எழுத வைக்குது. Lesson முடியும்போது, ஒரு புது employee real tasks-க்கு apply பண்ணக்கூடிய practical policy-ஐ draft பண்ண முடியும்.

## இது எப்படி work ஆகுது

### Principles

மத்த எல்லாமே பின்பற்றுற மூணு முதல் ஐந்து சின்ன commitments, உதாரணம்:

1. AI உதவியோட பண்ண வேலைக்கு மனுஷங்கதான் accountable.
2. Clients-ஓடது உட்பட personal, confidential data-வை பாதுகாக்கணும்.
3. AI involved-ஆ இருக்கும்போது customers-கிட்ட வெளிப்படையா இருக்கணும்.
4. Launch-க்கு முன்னாடி quality, fairness-ஐ test பண்ணணும்.
5. பிரச்சனைகளை சீக்கிரம், blame இல்லாம report பண்ணணும்.

Principles-க்கு India's AI Governance Guidelines-உம், NIST AI Risk Management Framework மாதிரி frameworks-உம் நல்ல sources.

### Approved tools

Approved tools-ஓட பேரையும் அவை எப்படி configure ஆகியிருக்குன்னும் சொல்லுங்க, உதாரணம்: "company data-ல train ஆகாத மாதிரி configure பண்ண company-யோட enterprise AI assistant". வேலை data-வுக்கு personal accounts-ஐ use பண்ணக்கூடாதுன்னு தெளிவா சொல்லுங்க.

### Data classes

| Class | Examples | எந்த tools process பண்ணலாம் |
| --- | --- | --- |
| Public | Publish ஆன material, public circulars | எந்த tool-உம் |
| Internal | Process notes, internal templates | Approved tools மட்டும் |
| Confidential | Client code, contracts, வெளியிடாத results | Approved tools மட்டும், client contracts அனுமதிக்குற இடத்துல மட்டும் |
| Personal | Customer அல்லது employee personal data | குறிப்பா approve ஆன systems மட்டும்; DPDP Act-ஐ follow பண்ணும் |

Personal data **DPDP Act**-ஐ follow பண்ணும்: மக்களுக்கு சொன்ன நோக்கங்களுக்கு மட்டும், consent மாதிரி ஒரு சட்டபூர்வ அடிப்படையில, தேவையானதை விட அதிகமா இல்லாம use பண்ணணும்.

### Use cases

| ஊக்குவிக்கப்படுறது | Restrict பண்ணது (approval வேணும்) | தடை பண்ணது |
| --- | --- | --- |
| Drafting, summarising, research | Customer-facing AI features | Approve ஆகாத tools-ல customer data |
| Coding assistance, review-ஓட | Hiring, credit மாதிரி மனுஷங்களை பத்தின முடிவுகள் | உண்மையான நபர்களோட deepfakes |
| Internal documents-ஐ translate பண்றது | Medical, legal, financial advice | Review இல்லாம, மனுஷங்க மேல சட்ட விளைவுகள் இருக்குற முழுக்க automated முடிவுகள் |

தடை பண்ண ஒவ்வொரு use-க்கும், ஒரு allowed மாற்று இருந்தா அதை காட்டுங்க. "செய்யாதீங்க"ன்னு மட்டும் சொல்ற policy, use-ஐ மறைமுகமா போக வைக்கும்.

### Review-உம் accountability-உம்

AI output-ஐ use பண்றவங்க தான் அதுக்கு பொறுப்பு. Customer-facing, high-risk uses-க்கு ஒரு **named owner**-உம் documented review-உம் வேணும்.

### Disclosure

AI use பண்ணதை customers அல்லது readers-கிட்ட எப்போ சொல்றதுன்னு சொல்லுங்க: chatbots தங்களை AI-ன்னு அறிமுகப்படுத்தணும், clients அல்லது rules கேக்குற இடத்துல AI உதவியோட பண்ண reports label பண்ணப்படணும்.

### AI features build பண்றது

Launch-க்கு முன்னாடி, risk-க்கு ஏத்த அளவுல ஒரு சின்ன package:

```flow
dir: LR
Idea -> Risk assessment -> Evaluation results -> Oversight plan -> Monitoring, incident plan -> ஒரு named group-ஓட Approval -> Launch
```

Low-risk internal summariser-க்கு ஒரு பக்கம் போதும்; customer-facing credit assistant-க்கு இன்னும் நிறைய வேணும்.

### Incidents

ஒரு AI தப்பு, data leak, harmful output-ஐ எப்படி report பண்றது, யாருக்கு, எவ்வளவு சீக்கிரம்னு, உதாரணம்: "24 மணி நேரத்துக்குள்ள security team-க்கு", **நேர்மையான reports-க்கு blame இல்லாம**. மறைக்கப்பட்ட தப்புகள் தான் விலை அதிகம்.

### Training-உம் updates-உம்

எல்லா staff-க்கும் ஒரு குறுகிய training, ஒரு named policy owner, ஒரு review date. Tools-உம் சட்டங்களும் வேகமா மாறும்; ரெண்டு வருஷம் பழசான policy தப்பாதான் இருக்கும்.

## ஒரு worked example

Pune-ல 300 பேர் இருக்குற ஒரு software services company-க்கு AI policy இல்ல. Staff பல tools-ஐ கலந்து use பண்றாங்க, சிலர் client code-ஓட. ஒரு security review-ல ஒரு பெரிய client கேக்குறாங்க: "உங்க company-ல AI use எப்படி govern ஆகுது?" யார்கிட்டயும் நல்ல பதில் இல்லை.

Delivery head Neha, CTO-வோடயும் legal counsel-ஓடயும் சேர்ந்து ரெண்டு வாரத்துல மூணு பக்க policy-ஐ draft பண்றாங்க:

| Section | என்ன எழுதினாங்க |
| --- | --- |
| Principles | Accountability, client confidentiality முதல், transparency, quality, fairness, பிரச்சனைகளை report பண்றது |
| Approved tools | Enterprise AI assistant-உம், approved IDE-ல code assistant-உம், ரெண்டுமே company data-ல train ஆகாத மாதிரி configure பண்ணது |
| Client code, data | Approved tools-ல மட்டும், client contract அனுமதிக்குற இடத்துல மட்டும்; opt out பண்ண clients-ஓட ஒரு list |
| Restricted | Client-facing AI features-க்கு risk assessment-உம் client-ஓட approval-உம் வேணும் |
| Prohibited | Client வேலைக்கு personal AI accounts; approve ஆகாத tools-ல எந்த customer personal data-வும் |
| Incidents | 24 மணி நேரத்துக்குள்ள security team-க்கு report; நேர்மையான தப்புகளுக்கு blame இல்லை |
| Training | எல்லா staff-க்கும் 30 நிமிஷம்; policy owner ஆறு மாசத்துக்கு ஒரு தடவை review பண்ணுவாரு |

**அடுத்து என்ன நடந்துச்சு:**

| Measure | Policy-க்கு முன்னாடி | ஒரு மாசம் கழிச்சு |
| --- | --- | --- |
| Approved AI tools use | குறைவு; நிறைய பேர் personal accounts-ல | சுமார் மூணு மடங்கு அதிகம் |
| Client security review | பதில் இல்லாத கேள்வி | Pass ஆச்சு |
| Report ஆன incidents | எதுவும் report ஆகல, சிலது சந்தேகம் | ரெண்டு report ஆகி சீக்கிரம் fix ஆச்சு |

மக்களுக்கு கடைசியா என்ன அனுமதின்னு தெரிஞ்சதால approved tools usage மூணு மடங்கு ஆச்சு. Report ஆன ரெண்டு incidents, உண்மையான பேர்கள் இருந்த ஒரு test file-உம் ஒரு client-ஓட API key இருந்த ஒரு prompt-உம், ஒரு நாளுக்குள்ள பிடிபட்டுச்சு; ஏன்னா report பண்றதுக்கு blame இல்ல.

## பொதுவா பண்ற தப்புகள்

- **AI-ஐ முழுசா தடை பண்றது.** மக்கள் எப்படியும் use பண்ணுவாங்க, பாதுகாப்பில்லாம, கண்ணுக்கு தெரியாம.
- **யாரும் படிக்காத நீளமான legal documents.** எளிமையா, examples-ஓட, ஒரு பக்க summary-ஓட எழுதுங்க.
- **Client contracts-ஐ புறக்கணிக்கிறது.** நிறைய contracts client data-வை எப்படி process பண்ணலாம்னு restrict பண்ணும்.
- **Owner-உம் review date-உம் இல்லாம இருக்கிறது.** Tools-உம் சட்டங்களும் வேகமா மாறும்.
- **Incident route இல்லாம இருக்கிறது.** அப்போ தப்புகள் மறைஞ்சே இருக்கும்.
- **"செய்யாதீங்க" மட்டும்.** வேலையை செய்ய approved வழியை எப்பவும் காட்டுங்க.

## Practice பண்ணுங்க

கீழே link பண்ணியிருக்குற NIST AI RMF-ஓட govern function-ஐயும், PRS-ஓட DPDP Act summary-ஐயும், EU AI Act summary-ல தடை பண்ண, high-risk uses list-ஐயும் மேலோட்டமா படிங்க.

1. **Draft.** உங்களுக்கு தெரிஞ்ச ஒரு organisation-க்கு, மேல இருக்குற ஒவ்வொரு section-ஓடயும் ரெண்டு பக்க AI policy எழுதுங்க.
2. **Summarise.** Employees-க்கு ஐந்து dos, ஐந்து don'ts இருக்குற ஒரு பக்க summary எழுதுங்க.
3. **Test பண்ணுங்க.** வேற வேற teams-ல இருந்து ரெண்டு பேரை படிச்சு, எது தெளிவில்லன்னு ஒண்ணு சொல்லச் சொல்லுங்க; அதை fix பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** உங்க policy-ஐ ஒரு புது employee-கிட்ட கொடுத்து, மூணு example tasks-க்கு எந்த tool-ஐயும் எந்த data-வையும் use பண்ணலாம்னு அவங்க சரியா சொல்ல வைக்க முடியும்.
