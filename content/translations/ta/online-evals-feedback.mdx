## இது என்ன

**Offline evals** ship பண்றதுக்கு முன்னாடி ஒரு fixed golden set-ஐ test பண்ணும். **Online evals** ship பண்ணின பிறகு, real traffic-ல நடக்குறதை score பண்ணும். ரெண்டும் வேணும்: offline evals தெரிஞ்ச regressions-ஐ நிறுத்தும்; online evals தெரியாதவற்றை கண்டுபிடிக்கும்.

Online signals நாலு வகையா வரும்:

- **Automatic checks**, ஒவ்வொரு response-லயும்: சரியான format, citations இருக்கா, refusal-ஆ இல்லையா, length, latency, guardrail triggers.
- **Model-graded scores**, ஒரு sample-ல: sources-க்கு faithfulness, relevance, tone; human grades-ஓட நீங்க check பண்ண ஒரு judge model score பண்ணும்.
- **User feedback**: thumbs up அல்லது down, ஒரு reason, answer-ஐ copy பண்ணாங்களா, திரும்ப கேட்டாங்களா, ஒரு ஆள்கிட்ட escalate பண்ணாங்களா.
- **Human review**: ஒரு expert வாராந்திர sample-ஐ படிச்சு, என்ன தப்பா போச்சுன்னு label பண்ணுவாங்க.

```flow
Live request -[காத்திருக்காம]-> User-க்கு answer
Live request -> Trace சேமிக்கப்பட்டது
Trace சேமிக்கப்பட்டது -> ஒவ்வொரு trace-லயும் Rules | format, citations, refusal, length, latency
Trace சேமிக்கப்பட்டது -> 10% sample + எல்லா negative feedback-லயும் Judge | faithfulness, relevance
Trace சேமிக்கப்பட்டது -> User feedback | thumbs-உம் reason-உம், rephrase பண்ண கேள்வி, escalation
Trace சேமிக்கப்பட்டது -> வாராந்திர human review | காரணம் வாரியா label பண்ண 50 traces
ஒவ்வொரு trace-லயும் Rules -> நாள், version, topic, language வாரியா Dashboard
10% sample + எல்லா negative feedback-லயும் Judge -> நாள், version, topic, language வாரியா Dashboard
User feedback -> நாள், version, topic, language வாரியா Dashboard
வாராந்திர human review -> நாள், version, topic, language வாரியா Dashboard
நாள், version, topic, language வாரியா Dashboard -[திடீர் மாற்றங்களுக்கு alerts]-> மிகப்பெரிய காரணத்தை fix பண்ணு -> Offline golden set-ல cases-ஐ சேரு
```

## இது எப்படி work ஆகுது

**Asynchronously score பண்ணுங்க.** Response user-கிட்ட போன பிறகு, traces-ல இருந்து checks-ஐயும் judges-ஐயும் run பண்ணுங்க; அதனால latency எதுவும் சேராது.

**புத்திசாலித்தனமா sample பண்ணுங்க.** எல்லா traces-ஐயும் rules-ஆ மலிவா score பண்ணுங்க; random 5-ல இருந்து 10%-க்கும், negative feedback அல்லது guardrail trigger இருக்குற ஒவ்வொரு trace-க்கும் judge-ஐ run பண்ணுங்க.

**Feedback-ஐ எளிதாவும் குறிப்பிட்டதாவும் ஆக்குங்க.** ஒரு thumbs down-க்கு அப்புறம் மூணு quick reasons ("wrong", "incomplete", "not what I asked") வெறும் thumbs down-ஐ விட நிறைய தகவல் தரும். Implicit signals-உம் உதவும்: ஒரு நிமிஷத்துக்குள்ள rephrase பண்ண கேள்வி, பெரும்பாலும் முதல் answer தவறவிட்டுச்சுன்னு அர்த்தம்.

**ஒரு எண்ணை இல்ல, trends-ஐ பாருங்க.** நாள் வாரியாவும் version வாரியாவும் dashboards: faithfulness, refusal rate, negative feedback rate, escalations. திடீர் மாற்றங்களுக்கு alert பண்ணுங்க, உதாரணம் ஒரு document upload-க்கு அப்புறம் refusal rate double ஆகுறது, அல்லது ஒரு provider-ஓட model update-க்கு அப்புறம் faithfulness குறையுறது.

**Loop-ஐ மூடுங்க.** ஒவ்வொரு வாரமும்: மிக மோசமா score ஆன, negative rating வாங்கின traces-ஐ படிங்க, காரணம் வாரியா group பண்ணுங்க (retrieval miss, stale document, prompt gap, out-of-scope கேள்வி), பெரிய group-ஐ fix பண்ணுங்க, fix நிலைச்சிருக்க representative cases-ஐ offline golden set-ல சேருங்க.

**Judge-ஐ check பண்ணுங்க.** ஒரு judge model-க்கும் சொந்த errors இருக்கு. ஒவ்வொரு சில வாரங்களுக்கும், ஒரு ஆள் judge பண்ண 50 samples-ஐ grade பண்ணி, agreement-ஐ check பண்ணட்டும். Agreement குறைஞ்சா, அதோட numbers-ஐ நம்பறதுக்கு முன்னாடி judge prompt-ஐ சரி பண்ணுங்க.

**Signals-உம் அவை எதை பிடிக்கும்:**

| Signal | Cost | எதை பிடிக்கும் |
| --- | --- | --- |
| ஒவ்வொரு trace-லயும் rule checks | கிட்டத்தட்ட இலவசம் | உடைஞ்ச formats, missing citations, மெதுவான responses |
| Topic வாரியா refusal rate | இலவசம் | Missing documents, ரொம்ப கண்டிப்பான prompts |
| ஒரு sample-ல judge | Model calls | Faithful இல்லாத அல்லது relevant இல்லாத answers |
| Thumbs-உம் reasons-உம் | இலவசம் | Users உண்மையில் எதை விரும்பல |
| ஒரு நிமிஷத்துக்குள்ள rephrase | இலவசம் | கேள்வியை தவறவிட்ட answers |
| வாராந்திர human review | Staff நேரம் | எந்த automatic signal-உம் சொல்லாத காரணங்கள் |

**வாராந்திர review-ஐ நடத்துறது.** 50 traces-ஐ எடுங்க: judge score-ல மிக மோசமான 20, negative feedback இருக்குற 20, random-ஆ 10. ஒவ்வொண்ணுக்கும், ஒரு சின்ன list-ல இருந்து ஒரு காரண label-ஐ எழுதுங்க: retrieval miss, stale அல்லது missing document, prompt gap, out of scope, model error, அல்லது fine. Labels-ஐ எண்ணுங்க. பெரிய group தான் அடுத்த வாரத்தோட fix. Counts-ஐ வாரம் வாரமா வச்சுக்கோங்க; அப்போ fixes வர வர காரணங்கள் சுருங்குறதை நீங்களும் client-உம் பாக்கலாம்.

**Client-கிட்ட சொல்றது.** Offline score-ஐ மட்டும் இல்ல, online dashboard-ஐயும் வாராந்திர காரண counts-ஐயும் பகிருங்க. ஒரு பிரச்சனையை கண்டுபிடிச்சு, விளக்கி, அது சரியானதை காட்டுற team-ஐ, launch-ல வந்த ஒரு உயர்ந்த எண்ணை மட்டும் சொல்ற team-ஐ விட clients ரொம்ப அதிகமா நம்புவாங்க.

**Deterministic sampling.** Judge-க்கு traces-ஐ trace id-ஐ hash பண்ணி தேர்ந்தெடுங்க; அப்போ ஒரே trace எப்பவும் sample-ல இருக்கும் அல்லது இருக்காது, reruns-உம் dashboards-உம் ஒத்துப்போகும்:

```python
import hashlib

def in_sample(trace_id, rate=0.08):
    h = int(hashlib.sha256(trace_id.encode()).hexdigest()[:8], 16)
    return h / 0xFFFFFFFF < rate

def should_judge(trace):
    return (in_sample(trace["id"])
            or trace.get("feedback") == "down"
            or trace.get("guardrail_triggered")
            or trace.get("stop_reason") == "max_tokens")
```

**Conversation-ல இருந்து implicit signals.** மக்கள் thumbs down-ஐ அபூர்வமா தான் அழுத்துவாங்க, ஆனா அவங்க behaviour நிறைய சொல்லும். முடிஞ்ச conversations மேல ஓடுற ஒரு சின்ன detector:

```python
from difflib import SequenceMatcher

def implicit_signals(turns):
    """turns: list of {"role", "text", "at" (seconds), "stopped_early", "regenerated"}."""
    flags = []
    users = [t for t in turns if t["role"] == "user"]
    for a, b in zip(users, users[1:]):
        similar = SequenceMatcher(None, a["text"].lower(), b["text"].lower()).ratio() > 0.6
        if similar and b["at"] - a["at"] < 90:
            flags.append("rephrased within 90 s")
    if any(t.get("stopped_early") for t in turns):
        flags.append("stopped a reply")
    if any(t.get("regenerated") for t in turns):
        flags.append("regenerated")
    if any(w in t["text"].lower() for t in users for w in ("wrong", "not what i asked", "galat")):
        flags.append("said it was wrong")
    return flags
```

Explicit ratings-ஓட பக்கத்துல, நாள் வாரியாவும் version வாரியாவும் flags-ஐ எண்ணுங்க. குறைவான thumbs down-ஓட ஆனா அதிக rephrasing இருக்குற ஒரு version, பெரும்பாலும் நல்லது இல்ல.

**Feedback-ஐ கவனமா design பண்ணுங்க.** இயல்பான நேரங்கள்ல கேளுங்க (ஒரு answer-க்கு அப்புறம், task நடுவுல இல்ல), ஒரு tap-ஆ வச்சுக்கோங்க, thumbs down-க்கு அப்புறம் ரெண்டு அல்லது மூணு reasons-ஐ குடுங்க. யாரு feedback தர்றாங்கன்னு நினைவுல வச்சுக்கோங்க: அதிருப்தியான users-உம் ரொம்ப சந்தோஷமான users-உம், அதனால explicit ratings சாய்ஞ்சிருக்கும். காட்டின ரெண்டு options-ல முதல்ல வர்றதுக்கு feedback அதிகமா வர்றதும், அது முதல்ல வந்ததாலேயே. Versions-ஐ ஒரே feedback design வச்சு ஒப்பிடுங்க, redesigns-க்கு இடையில இல்ல.

**Dashboard-க்கு ஒரு query.** Traces Postgres-ல விழுந்தா, version வாரியா ஒரு தினசரி view சில வரிகள் தான்:

```sql
SELECT date(created_at AT TIME ZONE 'Asia/Kolkata') AS day, app_version,
       count(*) AS requests,
       avg(CASE WHEN feedback = 'down' THEN 1.0 ELSE 0 END) AS thumbs_down_rate,
       avg(CASE WHEN judge_verdict = 'fail' THEN 1.0 END) AS judge_fail_rate,
       avg(CASE WHEN refused THEN 1.0 ELSE 0 END) AS refusal_rate
FROM traces
WHERE created_at > now() - interval '30 days'
GROUP BY 1, 2 ORDER BY 1, 2;
```

**சுருங்குற loops-ஐ கவனிங்க.** Feedback-ல இருந்து நீங்க rank அல்லது recommend பண்ணா, ஏற்கனவே காட்டினதை பத்தி தான் பெரும்பாலும் கத்துக்குவீங்க. Traffic-ல ஒரு சின்ன share-ஐ மற்ற options-ஐ explore பண்ண வச்சுக்கோங்க; மாற்றங்களை clicks-ஐ மட்டும் இல்ல, offline evals-ஆலயும் judge பண்ணுங்க.

## ஒரு worked example

Chennai-ல ஒரு telecom-ஓட customer assistant offline golden set-ல 91% pass ஆச்சு. Launch-க்கு ஆறு வாரம் கழிச்சு, negative feedback 6%-ல இருந்து 11%-க்கு மெதுவா ஏறுச்சு.

Online data காட்டினது:

- Faithfulness (10% sample-ல judge பண்ணது) 0.93-ல நிலையா இருக்கு: answers அவற்றோட sources-ஓட பொருந்துது.
- Refusal rate 8%-ல இருந்து 17%-க்கு ஏறியிருக்கு.
- பெரும்பாலான negative feedback "not what I asked" என்ற reason-ஓட வந்துச்சு.

அந்த traces-ல 60-ஐ படிச்சதுல காரணம் தெரிஞ்சுது: ஒரு புது prepaid plan launch ஆச்சு, customers Tamil-லயும் English-லயும் அதை பத்தி கேட்டாங்க, ஆனா plan documents index-ல சேர்க்கப்படல. Assistant சரியா refuse பண்ணுச்சு, customers அதிருப்தியானாங்க.

Fixes: marketing team-ஓட plan launches இப்போ ஒரு indexing job-ஐ trigger பண்ணுது; ஒரு topic-க்கான refusal rate தாவுனா alert வருது; புது plans பத்தின 25 கேள்விகள் golden set-ல சேர்ந்துச்சு. ஒரு வாரத்துக்குள்ள negative feedback மறுபடி 6%-க்கு வந்துச்சு. மாசாந்திர review-ல client-க்கு timeline-ஐ காட்டுனீங்க; அது ஆரம்ப 91%-ஐ விட நம்பிக்கைக்கு நிறைய உதவுச்சு.

| வாரம் | Negative feedback | Refusal rate | Action |
| --- | --- | --- | --- |
| Launch | 6% | 8% | எதுவுமில்ல |
| வாரம் 6 | 11% | 17% | 60 traces படிச்சாங்க: புது plan documents missing |
| வாரம் 7 | 6% | 8% | Plan launches indexing-ஐ trigger பண்ணுது; topic refusal alert; 25 golden cases சேர்ந்துச்சு |

## பொதுவா பண்ற தப்புகள்

- **Online signals இல்லாம ship பண்றது.** கோபமான users-கிட்ட இருந்தோ client-ஓட boss-கிட்ட இருந்தோ தான் பிரச்சனைகள் உங்களுக்கு தெரிய வரும்.
- **Check பண்ணாத judge-ஐ நம்புறது.** Judge scores drift ஆகும், blind spots இருக்கும்; human grades-ஓட அடிக்கடி ஒப்பிடுங்க.
- **Feedback-ஐ collect பண்ணி படிக்காம விடுறது.** வாராந்திர review-ஐ schedule பண்ணுங்க.
- **Averages மட்டும்.** நிலையான ஒரு average, ஒரு topic அல்லது language ரொம்ப மோசமாகுறதை மறைச்சுடும். Topic, language, version வாரியா slice பண்ணுங்க.
- **Tests சேர்க்காம fix பண்றது.** அடுத்த மாற்றத்துக்கு அப்புறம் அதே failure திரும்ப வரும்.
- **ஒவ்வொரு run-லயும் மாறுற random sampling.** Samples நிலையா இருக்க trace id-ஐ hash பண்ணுங்க.
- **Explicit ratings-ஐ மட்டும் நம்புறது.** குறைவான பேர் தான் தருவாங்க, அவை negative-ஆவும் positive-ஆவும் சாயும்.
- **Clicks அல்லது thumbs-க்கு மட்டும் optimise பண்றது**, இது product-ஐ அது ஏற்கனவே செய்யுறதை நோக்கி சுருக்கிடும்.

## எப்போ online evals காத்திருக்கலாம்

- **Launch-க்கு முன்னாடி**: ஒரு நல்ல test set-ல offline evals தான் முதல்ல.
- **ரொம்ப குறைவான traffic**: sample பண்றதுக்கு பதிலா ஒவ்வொரு conversation-ஐயும் படிங்க.
- **சில experts மட்டுமே use பண்ற internal tools**, ஏதாவது தப்புன்னா அவங்களே நேரடியா சொல்லுவாங்க.

## Demo-ல இருந்து production-க்கு

- **Traces-ல இருந்து asynchronously score பண்ணுங்க**, response path-ல ஒருபோதும் வேண்டாம்.
- **Feedback-ஐயும் implicit flags-ஐயும் trace id-ஓடவும் version-ஓடவும் சேமிங்க.**
- **Version, topic வாரியா திடீர் மாற்றங்களுக்கு alert பண்ணுங்க**, ஒரு மோசமான conversation-க்கு இல்ல.
- **வாராந்திர காரண review-ஐ நடத்தி**, counts-ஐ client-ஓட பகிருங்க.
- **ஒவ்வொரு சில வாரங்களுக்கும் judge-ஐ human grades-ஓட மறுபடி check பண்ணுங்க.**

## Practice பண்ணுங்க

Langfuse-ஓட evaluation overview-ஐயும், evaluation process பத்தின Eugene Yan-ஓட கட்டுரையையும் படிங்க.

1. உங்க app-ல மூணு reasons-ஓட ஒரு thumbs up அல்லது down-ஐ சேருங்க, trace id-ஓட சேமிங்க.
2. ரெண்டு automatic checks (citation இருக்கு, response length limit-க்குள்ள இருக்கு) எழுதி, faithfulness-க்கு ஒரு judge-ஐ எழுதி, responses அனுப்பின பிறகு 10% sample-ல run பண்ணுங்க.
3. 30 judge பண்ண samples-ஐ நீங்களே grade பண்ணி, judge-ஓட எவ்வளவு அடிக்கடி ஒத்துப்போறீங்கன்னு compute பண்ணுங்க.
4. உங்க சொந்த conversations-ல ஒரு வாரத்துக்கு implicit_signals-ஐ run பண்ணி, flag ஆனவற்றை thumbs down வாங்கினவற்றோட ஒப்பிடுங்க.
