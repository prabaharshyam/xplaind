## இது என்ன

Machine learning-னா data-ல இருந்து கத்துக்கிறது; data-வோ noisy-ஆ, skewed-ஆ, முழுமையில்லாம இருக்கும். **Statistics**-னா uncertainty-க்குள்ள உங்களை நீங்களே ஏமாத்திக்காம data-ல இருந்து கத்துக்க உதவுற toolkit. ML engineering-ல ஒவ்வொரு வாரமும் வர்ற ஐந்து பகுதிகள்:

| பகுதி | எந்த கேள்விக்கு பதில் சொல்லுது | எந்த வழக்கமான தப்பை தடுக்குது |
| --- | --- | --- |
| **Data-வை describe பண்றது** | Typical என்ன, எவ்வளவு பரவியிருக்கு? | Misleading average-ஐ report பண்றது |
| **Sampling** | நாம கவலைப்படுற மக்களை நம்ம data represent பண்ணுதா? | Tier-3 towns-ல fail ஆகுற model |
| **உறவுகள்** | இதெல்லாம் சேர்ந்து நகருதா, ஒண்ணு இன்னொண்ணுக்கு காரணமா? | ஒரு feature தான் outcome-க்கு காரணம்னு claim பண்றது |
| **Uncertainty** | இந்த number-ல எவ்வளவு உறுதி? | Noise-ஆ இருக்குற 1-point gain-ஐ கொண்டாடுறது |
| **Experiments** | நம்ம change உண்மையிலேயே உதவுச்சா? | Festival sale-ஓட credit-ஐ புது model-க்கு கொடுக்குறது |

## இது எப்படி work ஆகுது

### Averages-உம் spread-உம்

**Mean** எல்லாத்தையும் கூட்டி, எண்ணிக்கையால வகுக்கும். Extreme values அதை இழுக்கும். **Median**-னா sort பண்ணா நடுவுல வர்ற value. அது இழுக்கப்படாது.

**Standard deviation** (SD) spread-ஐ அளக்கும்: கிட்டத்தட்ட, ஒரு typical value mean-ல இருந்து எவ்வளவு தூரத்துல இருக்குன்னு. Bell-shaped data-ல, சுமார் 68% values mean-ல இருந்து ஒரு SD-க்குள்ளயும், சுமார் 95% ரெண்டு SD-க்குள்ளயும் வரும்.

பெரும்பாலான values சின்னதா, சில ரொம்ப பெருசா இருக்குற **skewed** data-ல இந்த rule உடைஞ்சிடும். இந்திய incomes, order values, insurance claims, app latencies எல்லாமே skewed தான். அங்க "mean plus two SDs" tail-ஐ தப்பா கணிக்கும்; percentiles தான் அதை நேர்மையா describe பண்ணும். 90th percentile-னா 90% cases அதுக்கு கீழ வர்ற value.

| Data shape | எந்த average use பண்ணணும் | எந்த spread use பண்ணணும் |
| --- | --- | --- |
| கிட்டத்தட்ட symmetric, bell-shaped | Mean | Standard deviation |
| Skewed, நீளமான tail | Median | 90th, 99th மாதிரி percentiles |

Summarise பண்றதுக்கு முன்னாடி எப்பவும் ஒரு histogram plot பண்ணுங்க.

### நீங்க சந்திக்கப்போற distributions

ஒரு **probability distribution** ஒவ்வொரு value-உம் வர்றதுக்கு எவ்வளவு வாய்ப்புன்னு describe பண்ணும். Shape தெரிஞ்சா எந்த summaries, tests, models அர்த்தமுள்ளதுன்னு தெரியும். பெரும்பாலான ML வேலைக்கு நாலு shapes போதும்:

| Distribution | இது எதை எண்ணுது | ML-ல எங்க வரும் |
| --- | --- | --- |
| **Binomial** | n yes-or-no trials-ல successes | n test questions-ல சரியான answers; n visitors-ல buyers |
| **Poisson** | Events independent-ஆ இருக்கும்போது, ஒரு fixed window-க்கு events | ஒரு நிமிஷத்துக்கு orders, ஒரு மணி நேரத்துக்கு support tickets; அசாதாரண spikes-க்கு alerting |
| **Normal** | பல சின்ன effects-ஓட sum அல்லது average-ஆ இருக்குற values | பெரிய samples-ஓட averages; அதனால தான் accuracy, means-க்கான intervals work ஆகுது |
| **Long-tailed** (log-normal மாதிரி) | பணம், நேரம், size | Order values, latency, session length: medians, percentiles use பண்ணுங்க, modelling-க்கு முன்னாடி பெரும்பாலும் log எடுங்க |

**Base rates.** நீங்க தேடுறது rare-ஆ இருந்தா, நல்ல classifier கூட பெரும்பாலும் false alarms தான் பண்ணும். உதாரணமா, 1 லட்சம் UPI transactions-ல 0.5% fraud-ன்னு வச்சுக்கோங்க (500 cases). ஒரு model 90% fraud-ஐ பிடிக்குது, 5% genuine payments-ஐ தப்பா flag பண்ணுது. அது 450 frauds-ஐயும் 4,975 genuine payments-ஐயும் flag பண்ணும், அதனால அதோட alerts-ல 8% மட்டும் தான் fraud. Precision-ஐ judge பண்றதுக்கு முன்னாடி எப்பவும் base rate-ஐ கேளுங்க.

### Sampling-உம் selection bias-உம்

ஒரு model அது கத்துக்கிட்ட sample அளவுக்கு தான் நல்லா இருக்கும். கேளுங்க: **இந்த data-ல யார் missing?** சில cases-க்கு சாதகமான முறையில collect பண்ண data **selection bias**-ஐ உருவாக்கும். உதாரணங்கள்: complain பண்ண customers மட்டும், அல்லது approve ஆன loans மட்டும்; அப்போ reject ஆன applicants எப்படி repay பண்ணியிருப்பாங்கன்னு உங்களுக்கு தெரியவே தெரியாது.

Selection bias launch-க்கு அப்புறம் சத்தமில்லாம models-ஐ உடைக்கும். உங்க training data-ல இருக்குற segment shares-ஐ சமீபத்திய live traffic-ஓட compare பண்ணி, launch-க்கு முன்னாடியே அதை கண்டுபிடிங்க. City tier, device, language, new vs returning users use பண்ணுங்க. உதாரணமா, training rows-ல 72% metros-ல இருந்து வருது, ஆனா போன மாச users-ல 48% தான் metros-ன்னா, model ரொம்ப கம்மியான small-town users-ஐ தான் பார்த்திருக்கு. இன்னும் data collect பண்ணுங்க, reweight பண்ணுங்க, அல்லது குறைஞ்சது segment வாரியா accuracy-ஐ report பண்ணுங்க.

### Correlation, causation, Simpson's paradox

ரெண்டு விஷயங்கள் சேர்ந்து நகர்ந்தா, ஒண்ணு இன்னொண்ணுக்கு காரணம்னு அர்த்தம் இல்லை. Ice-cream sales-உம் நீரில் மூழ்குற சம்பவங்களும் கோடையில ரெண்டுமே அதிகமாகும்: வெயில் தான் ரெண்டையும் இயக்குது. ஒரு model correlations-ஐ வச்சு **predict** பண்ணலாம். ஒரு **cause**-ஐ claim பண்ண, உதாரணமா ஒரு discount retention-ஐ அதிகமாக்குச்சுன்னு சொல்ல, ஒரு randomised experiment அல்லது கவனமான causal methods வேணும்.

Groups-ஐ கலந்தா ஒரு முடிவே தலைகீழா மாறலாம். இது தான் **Simpson's paradox**. ஒரு support bot பெரும்பாலும் Hindi users-க்கு roll out ஆகுதுன்னு வச்சுக்கோங்க; அவங்க questions கஷ்டமானவை:

| Queries | பழைய bot resolve பண்ணது | புது bot resolve பண்ணது |
| --- | --- | --- |
| English | 900-ல 720 (80%) | 300-ல 255 (85%) |
| Hindi | 100-ல 50 (50%) | 700-ல 385 (55%) |
| **எல்லாம்** | **1,000-ல 770 (77%)** | **1,000-ல 640 (64%)** |

புது bot ஒவ்வொரு language-லயும் better, ஆனா மொத்தமா பார்த்தா மோசமா தெரியுது, ஏன்னா கஷ்டமான queries அதுக்கு தான் அதிகமா வந்துச்சு. ஒரே மாதிரியானதை ஒரே மாதிரியானதோட, segment வாரியா compare பண்ணுங்க, அல்லது யாருக்கு எந்த version-னு randomise பண்ணுங்க.

### Standard error-உம் confidence intervals-உம்

SD தனித்தனி values-ஐ describe பண்ணும். **Standard error** (SE), ஒரு mean அல்லது accuracy மாதிரி ஒரு estimate, ஒரு sample-ல இருந்து இன்னொரு sample-க்கு எவ்வளவு ஆடும்னு describe பண்ணும். Sample size-ஓட square root-ஓட அது குறையும்: நாலு மடங்கு data SE-ஐ பாதியாக்கும். n examples-ல அளந்த ஒரு accuracy p-க்கு, SE-னா p × (1 − p) ÷ n-ஓட square root.

ஒரு **95% confidence interval** கிட்டத்தட்ட estimate plus or minus 2 SE. உண்மையான number-க்கு நம்பக்கூடிய values-ஓட ஒரு range-ஐ அது தரும்; 95% தடவை உண்மையான value-ஐ பிடிக்குற ஒரு method வச்சு அது உருவாக்கப்படுது. 200 test examples-ல, அளந்த 87%-க்கு பின்னாடி இருக்குற உண்மையான accuracy சுமார் 82% முதல் 92% வரை எங்க வேணும்னாலும் இருக்கலாம்.

| Test examples | அளந்த 87%-ஐ சுத்தி 95% interval |
| --- | --- |
| 200 | சுமார் ± 4.7 points |
| 1,000 | சுமார் ± 2.1 points |
| 5,000 | சுமார் ± 0.9 points |

F1 அல்லது median உட்பட எந்த metric-க்கும் interval எடுக்க ஒரு சீக்கிரமான வழி **bootstrapping**. உங்க test set-ஐ replacement-ஓட பல தடவை resample பண்ணுங்க, ஒவ்வொரு தடவையும் metric-ஐ மறுபடி calculate பண்ணுங்க, results-ஓட நடு 95%-ஐ எடுங்க.

### ஒரே test set-ல ரெண்டு models-ஐ compare பண்றது

அதே 200 questions-ல model A 87% score பண்ணுது, model B 88%. ரெண்டு intervals overlap ஆகுதான்னு check பண்றது ஒரு பொதுவான பழக்கம். அந்த rule misleading: வித்தியாசம் உண்மையா இருந்தாலும் ரெண்டு 95% intervals overlap ஆகலாம். ரெண்டு models-உம் *அதே* questions-க்கு பதில் சொன்னதையும் அது கண்டுக்காது; ரெண்டுமே சரியா சொன்ன, அல்லது ரெண்டுமே தப்பா சொன்ன questions cancel ஆகிடும், disagreements மட்டும் தான் முக்கியம்.

அதுக்கு பதிலா, **வித்தியாசத்தை நேரடியா, question வாரியா pair பண்ணி** அளங்க:

```text
  Same 200 questions (illustrative):
  A right, B wrong:   7      B right, A wrong:   9      net: B +2 questions
  Paired bootstrap of B minus A:  +1 point, 95% interval -3 to +5 points
                                  includes 0: no clear winner
```

```python
import numpy as np

# 1 = answered correctly, 0 = wrong; the same 200 questions in the same order
a = np.array([1]*167 + [1]*7 + [0]*9 + [0]*17)   # model A: 174 right, 87%
b = np.array([1]*167 + [0]*7 + [1]*9 + [0]*17)   # model B: 176 right, 88%

rng = np.random.default_rng(0)
idx = rng.integers(0, len(a), size=(10_000, len(a)))   # resample questions
diffs = b[idx].mean(axis=1) - a[idx].mean(axis=1)      # B minus A on the same draw
low, high = np.percentile(diffs, [2.5, 97.5])
print(f"B minus A: {b.mean() - a.mean():+.1%}, 95% interval {low:+.1%} to {high:+.1%}")
# B minus A: +1.0%, 95% interval -3.0% to +5.0%
```

இதுக்கு classic alternative **McNemar's test**; models disagree பண்ற questions-ஐ மட்டும் தான் அது பார்க்கும். இங்க அது p = 0.80 தருது. ஒரு useful gotcha: net gain 3 questions அல்லது அதுக்கு கம்மியா இருந்தா, எத்தனை questions இருந்தாலும் McNemar's test-ல p எப்பவுமே 0.05-க்கு கீழ வர முடியாது.

### p-values-உம் significance-உம், simple-ஆ

ஒரு **p-value** ஒரே ஒரு கேள்விக்கு பதில் சொல்லும்: change உண்மையிலேயே எதுவுமே பண்ணலைன்னா, வெறும் random noise மட்டுமே குறைஞ்சது இவ்வளவு பெரிய வித்தியாசத்தை எவ்வளவு அடிக்கடி உருவாக்கும்? 0.03 p-value-னா சுமார் 3% தடவை. வழக்கப்படி, p 0.05-க்கு கீழ இருக்குற result-ஐ **statistically significant**-ன்னு சொல்வாங்க.

p-value-னா change work ஆகுறதுக்கான chance *இல்லை*; சின்ன p-value-னா பெரிய effect-ன்னும் அர்த்தம் இல்லை. Sample போதுமான அளவு பெருசா இருந்தா, ship பண்ற அளவுக்கு worth இல்லாத ரொம்ப சின்ன gain கூட significant ஆகிடும். p-value மட்டும் இல்லாம, effect-ஓட size-ஐ அதோட confidence interval-ஓட சேர்த்து எப்பவும் report பண்ணுங்க.

### A/B tests

ஒரு change உதவுதான்னு தெரிஞ்சுக்க, users-ஐ **randomly** பிரிங்க: சிலர் பழைய version-ஐ (control) பார்ப்பாங்க, சிலர் புதுசை (treatment). ரெண்டையும் அதே நாட்கள்ல run பண்ணி, முன்னாடியே தேர்ந்தெடுத்த ஒரு metric-ஐ compare பண்ணுங்க.

Primary metric-ஐ கவனமா தேர்ந்தெடுங்க. **Average order value** வாங்குன users-ஐ மட்டும் தான் எண்ணும். புது model *யார்* வாங்குறாங்கங்கறதையே மாத்திச்சுன்னா, ரெண்டு groups-லயும் இருக்குற buyers வேற வேற ஆட்கள், அதனால comparison biased ஆகும். **Revenue per user** மொத்த revenue-ஐ group-ல இருக்குற எல்லா users-ஆலயும் வகுக்கும், அவங்க வாங்குனாலும் வாங்கலைன்னாலும்; அதனால அது நியாயமா இருக்கும். அதை primary metric-ஆ வைங்க, order value-ஐயும் conversion-ஐயும் secondary metrics-ஆ வச்சுக்கோங்க.

| Rule | ஏன் |
| --- | --- |
| ஒரு primary metric, sample size, duration எல்லாம் முன்னாடியே fix பண்ணுங்க | Change எதுவுமே பண்ணலைன்னா, 20 independent metrics-ஐ check பண்ணா குறைஞ்சது ஒண்ணு luck-ஆல "win" பண்ண 64% chance இருக்கு |
| யார் எந்த version பார்க்கணும்னு randomise பண்ணுங்க | அப்போ தான் groups change-ஆல மட்டும் வேறுபடும் |
| Sample ratio-வை check பண்ணுங்க | 10 லட்சம் users-ஓட plan பண்ண 50/50 split 5,03,000 vs 4,97,000-ஆ வந்தா, assignment அல்லது logging-ல bug இருக்குன்னு அர்த்தம்; result-ஐ நம்பாதீங்க |
| முழு வாரங்களுக்கு run பண்ணுங்க | Weekday, weekend behaviour வேற வேற |
| நல்லா தெரியுதுன்னு சீக்கிரமே நிறுத்தாதீங்க | எதுவுமே பண்ணாத ஒரு change-ஐ நாங்க simulate பண்ணப்போ, 14 நாள் தினமும் check பண்ணி முதல் தடவை p 0.05-க்கு கீழ வந்தவுடனே நிறுத்துனா, 5% இல்லை, 22% தடவை ஒரு "winner"-ஐ அறிவிச்சது |
| Novelty effects-ஐ கவனிங்க | புது design புதுசா இருக்குறதால users click பண்ணுவாங்க; ரெண்டாவது வாரத்துல gain மங்குதான்னு check பண்ணுங்க |
| Guardrail metrics-ஐ கவனிங்க | Revenue-ல gain வந்தா, கூடவே returns, complaints அதிகமாகக் கூடாது |

### எத்தனை users வேணும்?

Test-க்கு முன்னாடி, நாலு inputs வச்சு sample size-ஐ முடிவு பண்ணுங்க:

1. **Baseline**: இப்போ இருக்குற value, உதாரணமா 3.4% conversion rate.
2. **Minimum detectable effect (MDE)**: கண்டுபிடிக்க worth-ஆன மிகச் சின்ன gain, உதாரணமா 10% relative lift, 3.4%-ல இருந்து 3.74%-க்கு.
3. **Significance level**: பொதுவா 5%; change எதுவுமே பண்ணாதப்போ நீங்க ஏத்துக்குற false-alarm rate.
4. **Power**: பொதுவா 80%; MDE அளவுள்ள ஒரு உண்மையான effect-ஐ கண்டுபிடிக்கிற chance.

இந்த inputs-ஓட உங்களுக்கு **ஒரு group-க்கு சுமார் 46,700 users** வேணும். MDE-ஐ பாதியாக்கி 5% lift-ஆ வச்சா, ஒரு group-க்கு சுமார் 1.83 லட்சம் வேணும்: effect-ஐ பாதியாக்குனா users கிட்டத்தட்ட நாலு மடங்காகும். Python-ல, `statsmodels.stats.power.NormalIndPower().solve_power` இந்த calculation-ஐ பண்ணும்.

Revenue per user-க்கு conversion-ஐ விட ரொம்ப அதிகமான users வேணும், ஏன்னா சில ரொம்ப பெரிய orders அதை ரொம்ப noisy ஆக்கிடும். ரெண்டு standard fixes உதவும். Average பண்றதுக்கு முன்னாடி ஒவ்வொரு user-ஓட revenue-ஐயும் 99th மாதிரி ஒரு உயர்ந்த percentile-ல cap பண்ணுங்க. அல்லது CUPED மாதிரி ஒரு variance-reduction method use பண்ணுங்க; test-க்கு முன்னாடி ஒவ்வொரு user-உம் எவ்வளவு spend பண்ணாங்கன்னு வச்சு அது adjust பண்ணும்.

```flow

ரெண்டு versions-உம் அதே காலத்துலயா? -[ஆமா]-> Split plan பண்ண மாதிரி வந்துச்சா?
```

## ஒரு worked example

Mumbai-ல ஒரு e-commerce company-யோட data team, புது recommendation model average order value-வை ₹1,240-ல இருந்து ₹1,310-க்கு உயர்த்துச்சுன்னு report பண்றாங்க: ₹70 gain. Leadership கொண்டாட ready-ஆ இருக்காங்க. நீங்க அதை check பண்றீங்க. கீழ இருக்குற test numbers illustrative தான், ஒரு simulated test-ல இருந்து generate பண்ணது, ஆனா உண்மையான tests மாதிரியே behave பண்ணும்.

**Step 1: averages.** Order values skewed. சில பெரிய electronics orders mean-ஐ நகர்த்துச்சு. Median order ₹780-ல இருந்து ₹790-க்கு மட்டும் தான் உயர்ந்துச்சு.

**Step 2: timing.** Comparison போன மாசம் (பழைய model) vs இந்த மாசம் (புது model). இந்த மாசம் ஒரு festival sale இருந்துச்சு. ரெண்டு மாசங்களையும் compare பண்ண முடியாது, அதனால அந்த ₹70 model பத்தி எதுவுமே சொல்லல.

**Step 3: சரியான test-ஐ design பண்ணுங்க.** ஆரம்பிக்கிறதுக்கு முன்னாடி, team இதையெல்லாம் fix பண்ணுது:

- **Primary metric:** revenue per user; ஒவ்வொரு user-ஓட revenue-உம் order values-ஓட 99th percentile-ல (சுமார் ₹7,300) cap பண்ணது.
- **Secondary metrics:** conversion, mean, median order value. **Guardrail:** return rate.
- **Size:** capped revenue per user-ல 5% lift-ஐ கண்டுபிடிக்க ஒரு group-க்கு சுமார் 3.9 லட்சம் users வேணும். ரெண்டு முழு வார traffic ஒரு group-க்கு சுமார் 5 லட்சம் தரும், அதனால test சரியா ரெண்டு வாரம் run ஆகுது.

**Step 4: split-ஐ check பண்ணுங்க.** Groups-ல 5,00,212, 4,99,788 users இருக்காங்க. இந்த counts-ல chi-square test p = 0.67 தருது, அதனால split ஒரு நியாயமான 50/50-ஓட ஒத்துப்போகுது.

**Step 5: results-ஐ படிங்க.**

| Measure | பழைய model | புது model | வித்தியாசம் (95% interval) |
| --- | --- | --- | --- |
| Revenue per user, capped (primary) | ₹40.61 | ₹42.16 | +₹1.55 (+₹0.29 முதல் +₹2.81) |
| Conversion rate | 3.38% | 3.45% | +0.07 points (சுமார் 0 முதல் +0.14) |
| Mean order value | ₹1,237 | ₹1,258 | +₹21 (−₹12 முதல் +₹54) |
| Median order value | ₹781 | ₹796 | +₹15 (−₹6 முதல் +₹34) |
| Return rate (guardrail) | 6.28% | 6.15% | −0.13 points (−0.64 முதல் +0.38) |

**Step 6: முடிவு பண்ணுங்க.** Primary metric-ஓட interval zero-வை exclude பண்ணுது, அதனால model உண்மையிலேயே உதவுது: revenue per user-ல சுமார் +3.8%. Gain கொஞ்சம் அதிகமா வாங்குறதுலயும் கொஞ்சம் பெரிய orders-லயும் இருந்து வருது; ரெண்டுமே தனியா பார்த்தா தெளிவா இல்லை. Returns-ல எந்த harm-உம் இல்லை. முதல் report-ல இருந்த ₹70 festival மாசத்துல இருந்தும் சில பெரிய orders-ல இருந்தும் வந்தது. Mean order value-ஐ மட்டும் பார்த்திருந்தா inconclusive-ஆ தெரிஞ்சிருக்கும்னு கவனிங்க.

10 லட்சம் users-க்கு, இந்த gain-ஓட மதிப்பு சுமார் ₹15.5 லட்சம்; நம்பக்கூடிய range ₹2.9 லட்சம் முதல் ₹28 லட்சம். Leadership இந்த நேர்மையான numbers-ஓட model-ஐ roll out பண்றாங்க. Team தங்க launch checklist-ல "Impact-ஐ claim பண்றதுக்கு முன்னாடி A/B test" சேர்க்குது.

## பொதுவா பண்ற தப்புகள்

- **Skewed data-ஓட mean-ஐ report பண்றது.** Median, percentiles, ஒரு histogram பாருங்க.
- **Base rate-ஐ கண்டுக்காம விடுறது.** 95% accurate-ஆன fraud model கூட அதோட பெரும்பாலான alerts-ல தப்பா இருக்கலாம்.
- **வேற வேற காலங்களை compare பண்றது.** Seasons, festivals எல்லாத்தையும் மாத்திடும்; அதுக்கு பதிலா randomise பண்ணுங்க.
- **Data-ல யார் missing-ன்னு கண்டுக்காம விடுறது.** Launch-க்கு முன்னாடி training segments-ஐ live traffic-ஓட compare பண்ணுங்க.
- **Correlation-ஐ causation-ஆ நினைக்கிறது.** Prediction cause-க்கு proof இல்லை, pooled numbers தலைகீழா மாறலாம் (Simpson's paradox).
- **Overlapping intervals வச்சு ரெண்டு models-ஐ judge பண்றது.** அதே test set-ல paired bootstrap அல்லது McNemar's test use பண்ணுங்க.
- **Buyers-only metric-ஐ primary metric-ஆ use பண்றது.** Order value இல்லை, revenue per user use பண்ணுங்க.
- **Peek பண்றது, சீக்கிரமே நிறுத்துறது, அல்லது நிறைய metrics-ஐ check பண்றது.** ஒரு primary metric, sample size, duration-ஐ முன்னாடியே fix பண்ணுங்க.
- **Sample ratio check-ஐ skip பண்றது.** சமமில்லாத split-னா உடைஞ்ச test, result இல்லை.

## Practice பண்ணுங்க

கீழ link பண்ணியிருக்குற p-values, confidence intervals, bootstrapping பத்தின StatQuest videos-ஐயும், Google-ஓட Machine Learning Crash Course-ல இருக்குற data module-ஐயும் பாருங்க.

1. **Mean vs median.** பணம் அல்லது நேரம் column இருக்குற ஏதாவது ஒரு public dataset-ஐ load பண்ணுங்க. ஒரு histogram plot பண்ணி, mean, median, 90th, 99th percentiles-ஐ compare பண்ணுங்க.
2. **Paired bootstrap.** ரெண்டு models-ஐ, அல்லது ரெண்டு prompts-ஐ, அதே 200 test examples-ல score பண்ணுங்க. மேல இருக்குற code use பண்ணி வித்தியாசத்துக்கு 95% interval எடுங்க, அப்புறம் McNemar's test run பண்ணி ரெண்டு முடிவுகளையும் compare பண்ணுங்க.
3. **ஒரு test design பண்ணுங்க.** உங்களுக்கு முக்கியமான ஒரு change-க்கு A/B test design பண்ணுங்க: primary metric, guardrails, MDE, `statsmodels` வச்சு sample size, முழு வாரங்கள்ல duration.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** 200 examples-ல 1-point accuracy gain ஏன் convincing இல்லைன்னு explain பண்ண முடியும், paired test வச்சு ரெண்டு models-ஐ compare பண்ண முடியும், ஒரு நியாயமான A/B test-ஐ size பண்ணி design பண்ண முடியும்.
