## இது என்ன

ஒரு language model, ஒரு **base model**-ஆ தான் ஆரம்பிக்குது; அடுத்த token-ஐ predict பண்ண, ரொம்ப பெரிய அளவு text-ல train ஆகுது. அப்புறம் companies அதை, instructions-ஐ follow பண்ணி ஒரு helpful assistant மாதிரி நடந்துக்கிற மாதிரி இன்னும் train பண்ணுறாங்க. **Fine-tuning**-னா அதோட ஒரு சின்ன version-ஐ நீங்களே பண்றது: ஏற்கனவே இருக்குற ஒரு model-ஐ எடுத்து, உங்க சொந்த examples-ல தொடர்ந்து train பண்ணுறீங்க; அதனால அதோட **weights** (model-க்குள்ள இருக்குற numbers) உங்க task பக்கம் நகருது.

மேற்கொண்டு training-ல மூணு வகைகள் பொதுவானவை:

- **Continued pre-training**, legal அல்லது medical documents மாதிரி ஒரு துறையோட இன்னும் raw text-ஐ model-க்கு கொடுக்கும். இது costly, application teams-க்கு அபூர்வம்.
- **Supervised fine-tuning (SFT)**, ஒரு prompt-ஐயும் நீங்க விரும்புற exact answer-ஐயும் ஆயிரக்கணக்கான தடவை model-க்கு காட்டும். இது தான் வழக்கமான தேர்வு.
- **Preference tuning** (RLHF, அல்லது DPO-ன்னு ஒரு எளிய method), ஒரு prompt-க்கு ரெண்டு answers-ஐயும், மக்கள் எதை விரும்புனாங்கன்னும் model-க்கு காட்டும். இது tone, judgement-ஐ வடிவமைக்கும்.

அதனால தான் ஒரு chat model, base model-ஐ விட வேற மாதிரி நடந்துக்குது: அது மூணையும் கடந்து வந்தது. பெரும்பாலான application teams SFT மட்டும் பண்ணுவாங்க, சில நேரம் preference tuning.

Fine-tuning, ஒரு model-க்கு **எப்படி பதில் சொல்லணும்**ன்னு கத்துக்கொடுக்க நல்லது: ஒரு format, ஒரு tone, ஒரு கண்டிப்பான routine, ஒரு குறுகிய classification. **Facts**-ஐ கத்துக்கொடுக்க இது மோசமான வழி, ஏன்னா facts மாறும், model அவற்றை இன்னும் தப்பா ஞாபகம் வச்சுக்கலாம். Facts-க்கு, retrieval use பண்ணுங்க. Prompting, RAG, fine-tuning பத்தின lesson அவற்றுக்கு இடையில தேர்ந்தெடுக்க உதவும். இந்த lesson, நீங்க fine-tune பண்றதுன்னு முடிவு பண்ணதுக்கு அப்புறம் என்ன நடக்குதுங்குறது பத்தியது.

```flow
title: Fine-tuning loop
Task-ஐயும் ஒரு test-ஐயும் define பண்ணுங்க | எது நல்லதுன்னு எப்படி எண்ணுறது?
Task-ஐயும் ஒரு test-ஐயும் define பண்ணுங்க -> Examples சேகரிச்சு clean பண்ணுங்க | முதல்ல quality
Examples சேகரிச்சு clean பண்ணுங்க -> Train, validation, test-ஆ பிரிங்க | test locked-ஆ இருக்கணும்
Train, validation, test-ஆ பிரிங்க -> சில passes train பண்ணுங்க | validation loss-ஐ கவனிங்க
சில passes train பண்ணுங்க -> Prompt baseline-ஐ விட நல்லதா?
Prompt baseline-ஐ விட நல்லதா? -[இல்ல]-> Data-வை fix பண்ணுங்க, அல்லது நிறுத்துங்க | பெரும்பாலும் data தான் பிரச்சனை
Data-வை fix பண்ணுங்க, அல்லது நிறுத்துங்க -> Examples சேகரிச்சு clean பண்ணுங்க
Prompt baseline-ஐ விட நல்லதா? -[ஆமா]-> பழைய திறமைகளை check பண்ணுங்க | forgetting
பழைய திறமைகளை check பண்ணுங்க -> Deploy பண்ணி monitor பண்ணுங்க | மாறினா retrain பண்ணுங்க
```

இந்த lesson-ல, Pune-ல claim emails-ஐ 12 categories-ல பிரிக்க விரும்புற ஒரு insurer-ஐ follow பண்ணப் போறோம்.

## இது எப்படி work ஆகுது

1. **Training set-க்கு முன்னாடி test-ஐ எழுதுங்க.** இந்த task-க்கு "நல்லது"ன்னா என்னன்னு முடிவு பண்ணி, சரியான answers-ஓட உண்மையான examples-ஓட ஒரு சின்ன test set-ஐ build பண்ணுங்க. அது இல்லாம, fine-tuning உதவுச்சான்னு சொல்ல முடியாது.
2. **Examples சேகரிங்க.** ஒவ்வொண்ணும் ஒரு input-உம் ideal output-உம். முடிஞ்ச இடத்துல ஒரு ஆள் check பண்ண உண்மையான பழைய வேலையை use பண்ணுங்க. எத்தனை வேணும்ங்குறது task-ஐ பொறுத்தது: சில நூறு சிறப்பான examples ஒரு format-ஐ கத்துக்கொடுக்கும்; கஷ்டமான task-க்கு ஆயிரக்கணக்கானவை வேணும்.
3. **Clean பண்ணுங்க.** Duplicates-ஐ நீக்கி, தப்பான labels-ஐ சரி பண்ணி, examples முழுக்க format ஒரே மாதிரி இருக்கணும், personal data-வை எடுத்துடுங்க. Model தான் பார்க்கிறதை, தப்புகளோட சேர்த்து copy பண்ணும்.
4. **Data-வை பிரிங்க.** பெரும்பகுதி **training**-க்கு. சின்ன பகுதி **validation**, training நடக்கும்போது முன்னேற்றத்தை check பண்ண. மூணாவது பகுதி **test set**, கடைசி வரை தொடவே கூடாது.
5. **Train பண்ணுங்க.** Model examples-ஐ சில தடவை படிக்கும் (ஒவ்வொரு முழு pass-உம் ஒரு epoch), ideal answers வர்ற வாய்ப்பை அதிகமாக்க அதோட weights நகரும். **Loss**-ஐ கவனிப்பீங்க; model எவ்வளவு தப்புன்னு அளக்கும் ஒரு number அது. Training loss குறையணும். Training loss தொடர்ந்து குறைஞ்சு, validation loss ஏற ஆரம்பிச்சா, model examples-ஐ மனப்பாடம் பண்ணுது; இதுக்கு **overfitting**-னு பேரு. அங்கயே நிறுத்துங்க.
6. **வலுவான baseline-ஓட test பண்ணுங்க.** நியாயமான ஒப்பீடு, சோம்பேறித்தனமா எழுதின prompt-ஓட base model இல்ல. நல்லா எழுதின prompt-உம் சில நல்ல examples-உம் உள்ள base model தான். வச்சுக்கிற தகுதி வரணும்னா, fine-tuning அதை தெளிவா ஜெயிக்கணும்.
7. **எதை மறந்துச்சுன்னு check பண்ணுங்க.** உங்க task-க்கு சம்பந்தமில்லாத prompts-ஐ try பண்ணுங்க. ஒரு குறுகிய fine-tune, ஒரு model-ஐ பொதுவான instructions-ல மோசமாக்கலாம்; இதுக்கு **catastrophic forgetting**-னு பேரு.
8. **Deploy பண்ணி, பகுதிகளை வச்சுக்கோங்க.** Data, labelling guide, settings, test set-ஐ version பண்ணுங்க; ஏன்னா base model அல்லது உங்க rules மாறும்போது retrain பண்ணுவீங்க.

ஒரு SFT example பொதுவா JSON-ஓட ஒரு வரியா store ஆகும், ஒரு சின்ன chat மாதிரி எழுதப்பட்டு:

```json
{"messages": [
  {"role": "user", "content": "Classify this claim email.\n\nSubject: Hospital bill for my father\nBody: He was admitted on 3 March for 4 days at a Pune hospital. Please process the cashless request."},
  {"role": "assistant", "content": "health_cashless"}
]}
```

ஒரு சின்ன script data-வை பிரிச்சு, test set-ஐ பத்திரமா வச்சுக்கும்:

```python
import json, random

random.seed(7)                       # same split every time
rows = [json.loads(line) for line in open("claims_clean.jsonl")]
random.shuffle(rows)

n = len(rows)
test = rows[: int(n * 0.05)]         # locked away until the end
valid = rows[int(n * 0.05): int(n * 0.15)]
train = rows[int(n * 0.15):]

for name, part in [("train", train), ("valid", valid), ("test", test)]:
    with open(f"{name}.jsonl", "w") as f:
        for r in part:
            f.write(json.dumps(r) + "\n")
print(len(train), len(valid), len(test))
```

இங்க duplicates முக்கியம். ஒரே email training-லயும் test-லயும் இருந்தா, test score பொய்யா உயர்ந்து தெரியும். பிரிக்கிறதுக்கு முன்னாடி exact, near duplicates-ஐ நீக்குங்க.

**Hosted-ஆ, open weights-ஆ?** சில providers தங்க models-ஐ API வழியா fine-tune பண்ண விட்டு, result-ஐ host பண்ணி கொடுப்பாங்க; இது எளிது, ஆனா அவங்களோட கட்டிப்போடும். Open-weight models-ல, model-ஐ நீங்களே train பண்ணி serve பண்ணுவீங்க; இது control கொடுக்கும், ஆனா GPUs-உம் skills-உம் வேணும். Availability, prices மாறும், அதனால provider-ஓட இப்போதைய documentation-ஐ check பண்ணுங்க. பெரிய GPU இல்லாம open models-ஐ எப்படி train பண்றதுன்னு அடுத்த lesson cover பண்ணும்.

## ஒரு நாள், ஒரு example

Pune insurer மாசம் 200,000 claim emails-ஐ 12 categories-ல பிரிக்குது. ஒரு பெரிய model-ல ஆறு examples உள்ள prompt, label பண்ண 300 emails-ல 78% score பண்ணுது; இந்த volume-க்கு call-க்கான cost ரொம்ப அதிகம்.

Agents ஏற்கனவே label பண்ண 40,000 emails அவங்ககிட்ட இருக்கு. Training-க்கு முன்னாடி, 400-ஓட ஒரு sample-ஐ check பண்ணி, சுமார் 10-ல 1 label தப்புன்னு கண்டுபிடிக்கிறாங்க; முக்கியமா ரெண்டு agents "health reimbursement", "health cashless"-ஐ வேற வேற மாதிரி use பண்ணதால. ஒரு பக்க labelling guide எழுதி, குழப்பமான categories-ஐ ரெண்டு senior agents-ஐ வச்சு relabel பண்ணி, 3,000 duplicate emails-ஐ நீக்குறாங்க. இந்தியாவோட data protection law-ல personal data ஆன பெயர்கள், phone numbers, policy numbers-ஐ mask பண்ணுறாங்க.

30,000 cleaned examples-ல ஒரு சின்ன open-weight model-ஐ fine-tune பண்ணுறாங்க; 2,000-ஐ validation-க்கும், அசல் 300 test emails-ஐ தொடாமலும் வச்சிருக்காங்க. ரெண்டாவது pass-க்கு அப்புறம் validation loss improve ஆகுறது நின்னுடுது, அதனால அங்க நிறுத்துறாங்க.

| Option | 300 test emails-ல accuracy | ஒரு email-க்கு relative cost | குறிப்புகள் |
| --- | --- | --- | --- |
| ஆறு-example prompt-ஓட பெரிய model | 78% | 1x (baseline) | மாத்த எளிது, இந்த volume-ல costly |
| அதே prompt, error review-க்கு அப்புறம் improve பண்ணது | 84% | 1x | ஒரு மதியம் வேலை |
| Fine-tune பண்ண சின்ன model | 91% | சுமார் 0.1x | Data maintenance, retraining வேணும் |

இந்த table-ல இருக்குற numbers புரிய வைக்க மட்டும், எப்படி ஒப்பிடுறதுன்னு காட்ட. முக்கியம் method தான்: fine-tune, *improve பண்ண* prompt-ஓட (84%) judge ஆகுது, முதல் prompt-ஓட (78%) இல்ல.

இந்த குறுகிய task-க்கு cost, accuracy ரெண்டுலயும் fine-tune பண்ண model தெளிவா ஜெயிக்குது. ஆனா யாராவது அதுல ஒரு பொதுவான கேள்வியை type பண்ணப்போ, பதில் வித்தியாசமா இருந்துச்சு; இது forgetting. அது classify பண்ண மட்டும் use ஆகுறதால, அது பிரச்சனை இல்ல. அது customers-கிட்ட ஒருபோதும் பேசக்கூடாதுன்னு ஒரு rule சேக்குறாங்க.

## பொதுவா பண்ற தப்புகள்

- **Test-க்கு பதில் training set-ஓட ஆரம்பிக்கிறது.** Test இல்லாம, எதையாவது improve பண்ணீங்களான்னு சொல்ல முடியாது.
- **குழப்பமான labels-ல train பண்றது.** Model தப்புகளையும் கருத்து வேறுபாடுகளையும் கத்துக்கும்.
- **பலவீனமான prompt-ஓட ஒப்பிடுறது.** முதல்ல prompt-ஐ improve பண்ணுங்க, அப்புறம் fine-tuning இன்னும் ஜெயிக்குதான்னு பாருங்க.
- **Test examples-ஐ training-க்குள்ள leak ஆக விடுறது.** Splits முழுக்க duplicates, நல்லா தெரியுற ஆனா அர்த்தமில்லாத score-ஐ கொடுக்கும்.
- **Facts சேக்க fine-tuning use பண்றது.** Policies, prices மாறும், fine-tune update ஆக மெதுவானது. Retrieval use பண்ணுங்க.
- **Forgetting-ஐ ignore பண்றது.** நீங்க train பண்ணாத tasks-ல model-ஐ test பண்ணுங்க, அல்லது அது எங்க use ஆகுதுங்குறதை restrict பண்ணுங்க.
- **Training examples-ல personal data வைக்கிறது.** Model அதை திரும்ப சொல்லலாம், ஒரே fix retraining தான்.

## Fine-tuning தப்பான tool-ஆ இருக்குற சமயங்கள்

- பிரச்சனை, இல்லாத அல்லது மாறிட்டே இருக்குற knowledge. Retrieval அல்லது tools use பண்ணுங்க.
- ஒரு better prompt இன்னும் try பண்ணலை. அது வாரக்கணக்குல இல்ல, நிமிஷங்கள்ல முடியும்.
- உங்ககிட்ட test set இல்ல, அல்லது சில நூறுக்கும் குறைவான நல்ல examples தான் இருக்கு.
- Task மாசம் மாசம் மாறுது. தொடர்ந்து retrain பண்ணுவீங்க.
- ஒரு answer எங்க இருந்து வந்ததுன்னு காட்டணும். Fine-tune பண்ண model sources-ஐ cite பண்ண முடியாது, retrieval முடியும்.
- Volume குறைவு. Maintenance செலவு, மிச்சத்தை விட அதிகமா இருக்கும்.

## Demo-ல இருந்து production-க்கு

- **எல்லாத்தையும் version பண்ணுங்க.** Data, cleaning script, labelling guide, settings, test set-ஐ version control-ல வச்சு, ஒவ்வொரு result-உம் எந்த model-ல இருந்து வந்ததுன்னு note பண்ணுங்க.
- **Retraining-க்கு plan பண்ணுங்க.** Base models retire ஆகி மாறும், உங்க rules-உம் மாறும். Retraining கஷ்டமா இருந்தா, project அழுகிடும்.
- **Launch-க்கு அப்புறம் கவனிங்க.** ஒவ்வொரு வாரமும் உண்மையான inputs, outputs-ஐ sample எடுத்து, உங்க test set-ஓட ஒப்பிடுங்க. Email-ஓட வகை மாறுனா, accuracy அமைதியா விழும்.
- **ஒரு fallback வச்சுக்கோங்க.** Fine-tune பண்ண model down ஆனா அல்லது குழம்புனா, prompt-based version-க்கு route பண்ணுங்க.
- **Data-வை document பண்ணுங்க.** எங்க இருந்து வந்தது, யார் label பண்ணாங்க, என்ன நீக்கப்பட்டது. Clients-உம் auditors-உம் கேப்பாங்க.

## Practice பண்ணுங்க

முதல்ல ஒரு paper exercise, அப்புறம் ஒரு சின்ன உண்மையான exercise.

1. உங்க சொந்த வேலையில இருந்து ஒரு task-ஐ எடுங்க. "நல்லது"ன்னா என்னன்னு எழுதி, சரியான answers-ஓட பத்து test examples எழுதுங்க.
2. உங்களால முடிஞ்ச சிறந்த prompt-ஐ மூணு examples-ஓட எழுதி, அந்த பத்துல score பண்ணுங்க.
3. உண்மையா எத்தனை cleaned examples சேகரிக்க முடியும், யார் அவற்றை check பண்ணுவாங்கன்னு எழுதுங்க.
4. முடிவு பண்ணுங்க: fine-tune, prompt-ஐ improve பண்றது, இல்ல retrieval. அதை நியாயப்படுத்த மூணு வரிகள் எழுதுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** Test data ஏன் பார்க்கப்படாம இருக்கணும், ஏன் சிறந்த prompt-ஓட ஒப்பிடணும்னு explain பண்ணி, fine-tuning ஒரு model-ஐ மோசமாக்குற ஒரு வழியை சொல்ல முடியும்.
