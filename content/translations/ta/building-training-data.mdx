## இது என்ன

**Data curation**-னா ஒரு model கத்துக்குற examples-ஐ தேர்ந்தெடுக்குறது, எழுதுறது, சுத்தம் பண்றது, balance பண்றது. Fine-tuning-ல இதுதான் பெரும்பாலான வேலை: training run ஒரு மணி நேரத்துல முடியலாம், ஆனா data-க்கு வாரக்கணக்கு ஆகும்.

எதை கத்துக் கொடுக்கிறீங்கங்கிறதை பொறுத்து format மாறும்:

- **Supervised fine-tuning (SFT):** ஒரு instruction அல்லது chat, அதுக்கு ideal response.
- **Preference tuning (DPO அல்லது RLHF):** ஒரு prompt, ஒரு நல்ல response, ஒரு மோசமான response.
- **Continued pre-training:** உங்க field-ல இருந்து சாதாரண text, உதாரணத்துக்கு legal judgements.
- **Reward model அல்லது judge:** score அல்லது label இருக்குற responses.

ஒவ்வொரு dataset-உம் மூணு விஷயத்துல மதிப்பிடப்படும். சமையலை வச்சு யோசிச்சா எளிது:

- **Quality** புதுசான பொருட்கள்: ஒவ்வொரு example-உம் சரியா, consistent-ஆ இருக்கு.
- **Coverage** சரியான கலவை: users உண்மையிலேயே கொண்டு வர்ற cases-ஐ examples cover பண்ணுது.
- **Quantity** மேசைக்கு போதுமான சாப்பாடு: task-க்கு போதுமான examples இருக்கு.

Curation-னா data-வை நீக்குறதும் தான். உங்க model-க்கு ஒரு கெட்ட பழக்கம் இருந்தா, உதாரணத்துக்கு கேக்காத advice-ஐ எல்லா answer-லயும் சேர்க்குறது, அந்த பழக்கத்தை காட்டுற training examples-ஐ தேடி எடுத்து நீக்குங்க, நீங்க எதிர்பார்க்குற behaviour-ஐ காட்டுற examples-ஐ சேருங்க.

## இது எப்படி work ஆகுது

**Quality.** ஒரு example இப்படி இருந்தா high quality:

1. நீங்க train பண்ற task-க்கு **relevant**.
2. **Task-க்கு தேவையானதோட aligned.** Task-க்கு சின்ன answers வேணும்னா examples சின்னதா இருக்கணும்; ஒவ்வொரு score-க்கும் ஒரு காரணம் வேணும்னா, அதுவும் இருக்கணும்.
3. மத்த examples-ஓட **consistent**. ஒரே case-ஐ label பண்ற ரெண்டு பேர் பெரும்பாலும் ஒத்துப்போகணும்.
4. **சரியான format-ல**, model எப்படி produce பண்ணணுமோ அப்படியே, தேவையில்லாத HTML-ஓ உடைஞ்ச JSON-ஓ இல்லாம.
5. **Unique.** Duplicates சில cases-க்கு அதிக weight கொடுக்கும், test set-க்குள்ளயும் leak ஆகலாம்.
6. **Use பண்ண அனுமதி இருக்கணும்**: use பண்ணக்கூடாத personal data இல்லை, train பண்ண உரிமை இல்லாத content இல்லை.

Volume-ஐ விட quality ஜெயிக்கும்னு evidence ரொம்ப strong. LIMA study, ஒரு பெரிய model-ஐ கவனமா தேர்ந்தெடுத்த வெறும் 1,000 examples-ல fine-tune பண்ணுச்சு; மக்கள் அந்த answers-ஐ ஒரு முன்னணி commercial model-ஓட பெரும்பாலும் சமமா rate பண்ணாங்க. Yi models-ஐ உருவாக்குன team, கவனமா எழுதுன 10,000 examples, noisy-ஆன லட்சக்கணக்கான examples-ஐ விட நல்லா வேலை செய்றதை கண்டுபிடிச்சாங்க.

**Labelling guide.** யாராவது பெரிய அளவுல label பண்றதுக்கு முன்னாடி, ஒரு perfect output எப்படி இருக்கும்னு எழுதி வைங்க; கஷ்டமான cases-ஓட examples-உம், அவற்றை எப்படி handle பண்றதுங்கிறதும் இருக்கணும். அப்புறம் ஒரு pilot பண்ணுங்க: ரெண்டு பேர் ஒரே 30 items-ஐ label பண்றாங்க, நீங்க compare பண்றீங்க, அவங்க ஒத்துப்போகாத இடத்துல guide-ஐ fix பண்றீங்க. Agreement அதிகமாகுற வரைக்கும் இதை repeat பண்ணுங்க. இதுதான் quality-க்கு இருக்குற மலிவான step.

**Coverage.** Real users வகை வகையா இருப்பாங்க, அதனால உங்க data-வும் அப்படியே இருக்கணும். Inputs எப்படி வேறுபடுதுன்னு list பண்ணுங்க: மொழி, நீளம், topic, difficulty, format (typed அல்லது scanned), single-turn அல்லது multi-turn. ஒவ்வொண்ணும் mix-ல இருக்கணும். Llama 3-ஓட முந்தைய versions-ஐ விட வந்த gains-ஓட பெரும்பகுதிக்கு, புது architecture இல்லை, நல்ல data quality-யும் variety-யும் தான் காரணம்னு Meta சொல்லுச்சு. ஆனா அதிக variety எப்பவும் நல்லது கிடையாது: சம்பந்தமில்லாத data சேர்த்தா, உங்க task-ல model மோசமாகலாம்.

**Quantity.** ஒரு fixed number கிடையாது. இது இதை பொறுத்தது:

- **Task.** Reviews-ஐ positive, negative-ன்னு பிரிக்க, financial filings பத்தி கேள்விகளுக்கு பதில் சொல்றதை விட ரொம்ப குறைவான examples போதும்.
- **Base model.** அது ஏற்கனவே எவ்வளவு நெருக்கமா இருக்கோ, அவ்வளவு குறைவான examples போதும். Data கம்மியா இருந்தா, ஒரு strong model-ல இருந்து ஆரம்பிங்க.
- **Method.** LoRA மாதிரி light methods நூற்றுக்கணக்குல இருந்து சில ஆயிரம் examples-ல வேலை செய்யும்; full fine-tuning-க்கு பொதுவா பத்தாயிரக்கணக்குல அல்லது அதுக்கு மேல வேணும்.

Practical approach: **50 முதல் 100 சிறந்த examples**-ல ஆரம்பிங்க. பெரும்பாலான cases-ல அவை ஒரு தெரியுற improvement கொடுக்கும். அவை தெளிவா உதவுச்சுன்னா, இன்னும் data இன்னும் உதவும். எதுவும் நடக்கலைன்னா, உங்க prompt format-ஐயும் settings-ஐயும் check பண்ணுங்க; fail ஆன சின்ன set-ஐ பெரிய set பெரும்பாலும் காப்பாத்தாது.

அப்புறம் **learning curve**-ஐ அளக்குங்க: உங்ககிட்ட இருக்குறதுல 25%, 50%, 100%-ல train பண்ணி, ஒவ்வொண்ணையும் ஒரே test set-ல score பண்ணுங்க. Data சேர்க்க சேர்க்க gains பொதுவா குறையும். இன்னும் செங்குத்தா ஏறிக்கிட்டு இருக்குற curve, இன்னும் collect பண்ணுன்னு சொல்லுது; flat curve, quality-ல கவனம் செலுத்துன்னு சொல்லுது.

ஒரு சின்ன script learning curve-க்கு data-வை split பண்ணி, labeller agreement-ஐ check பண்ணுது:

```python
import json, random

def subsets(rows, fractions=(0.25, 0.5, 1.0), seed=7):
    rows = rows[:]
    random.Random(seed).shuffle(rows)       # same order every time, so subsets nest
    return {f: rows[: int(len(rows) * f)] for f in fractions}

def agreement(labels_a, labels_b):
    """Share of items two labellers marked the same way."""
    same = sum(a == b for a, b in zip(labels_a, labels_b))
    return same / len(labels_a)

train = [json.loads(line) for line in open("train.jsonl")]
for f, part in subsets(train).items():
    with open(f"train_{int(f * 100)}.jsonl", "w") as out:
        out.writelines(json.dumps(r) + "\n" for r in part)

print(agreement(["late_fee", "deposit", "lock_in"], ["late_fee", "deposit", "notice"]))  # 0.67
```

**வேகப்படுத்துற வழிகள்.** புதுசா எழுதுறதை விட, ஒரு draft-ஐ check பண்ணி திருத்துறது மக்களுக்கு வேகமா இருக்கும்; அதனால பல teams, ஒரு strong model ஒவ்வொரு answer-ஐயும் draft பண்ணட்டும், experts திருத்தட்டும்னு வைக்கிறாங்க. Bias-ஐ கவனிங்க: மக்கள் smooth-ஆன draft-ஐ ரொம்ப சுலபமா ஏத்துக்குவாங்க, அதனால திருத்தின items-ல ஒரு random sample-ஐ நீங்களே check பண்ணுங்க.

| Step | நல்லது எப்படி இருக்கும் | பொதுவான failure |
| --- | --- | --- |
| Labelling guide | எழுதின rules, கஷ்டமான cases-ஓட worked examples | "சரியா பார்த்து label பண்ணுங்க" |
| Pilot | ரெண்டு பேர், ஒரே 30 items, அதிக agreement | நேரம் மிச்சம் பண்ண skip பண்ணது |
| Coverage plan | Input types list, ஒவ்வொண்ணுக்கும் target count | முதல்ல கிடைச்ச files எதுவோ அது |
| முதல் set | 50 முதல் 100 சிறந்த, variety இருக்குற examples | Check பண்ணாத 5,000 examples |
| Cleaning | Dedupe பண்ணது, ஒரே format, personal data mask பண்ணது | Test items training-க்குள்ள copy ஆனது |
| Learning curve | 25%, 50%, 100%-ல scores | ஒரே training run, compare இல்லை |

## ஒரு worked example

Hyderabad-ல ஒரு legal-tech startup, English-லயும் Telugu-லயும் இருக்குற residential rental agreements-ஐ படிச்சு, ஒரு fixed summary கொடுக்குற model வேணும்னு நினைக்குது: rent, deposit, lock-in period, notice period, வருஷ increase, வழக்கத்துக்கு மாறான clauses. அவங்ககிட்ட 3,000 agreements இருக்கு, ரெண்டு வாரத்துக்கு ரெண்டு lawyers, AI உதவிக்கு பணம்.

1. **Guide, pilot.** Lawyers ரெண்டு பக்க guide எழுதுறாங்க. 30 agreements-ஓட pilot-ல fields-ல 70% ஒத்துப்போறாங்க; "வழக்கத்துக்கு மாறானது"ன்னா என்னங்கிறதுல தான் பெரும்பாலும் வேறுபடுறாங்க. அவங்க guide-ல வழக்கத்துக்கு மாறான clauses-ஓட பன்னிரண்டு examples சேர்க்குறாங்க; அடுத்த pilot 92% வருது.
2. **Coverage.** Users upload பண்றதுக்கு பொருந்துற மாதிரி agreements-ஐ தேர்ந்தெடுக்குறாங்க: 60% English, 40% Telugu, ஐந்துல ஒண்ணு scanned, standard-உம் custom formats-உம்.
3. **Drafts, review.** ஒரு strong model ஒவ்வொரு summary-யையும் fixed format-ல draft பண்ணுது, lawyers திருத்துறாங்க. ஒவ்வொருத்தரும் 25-க்கு பதிலா ஒரு நாளைக்கு சுமார் 80 முடிக்கிறாங்க.
4. **Cleaning.** Duplicate templates நீக்கப்படுது, tenant, owner பெயர்களும் Aadhaar numbers-உம் mask பண்ணப்படுது, 120 agreements test set-ஆ பூட்டி வைக்கப்படுது.
5. **Learning curve.**

| Training examples | 120 test agreements-ல சரியான fields |
| --- | --- |
| 150 | 68% |
| 300 | 76% |
| 600 | 81% |

இந்த numbers ஒரு உதாரணத்துக்கு தான். Curve இன்னும் ஏறிக்கிட்டு இருக்கு, அதனால இன்னும் 600 collect பண்றது worth-ஆ இருக்க வாய்ப்பு அதிகம். Telugu scores English-ஐ விட 9 points பின்னாடி இருக்கு, அதனால அடுத்த batch Telugu agreements பக்கம் அதிகம் சாயும்.

## பொதுவா பண்ற தப்புகள்

- **Guide எழுதுறதுக்கு முன்னாடி label பண்றது.** மக்கள் ஒத்துப்போக மாட்டாங்க, model அந்த வேறுபாட்டையே கத்துக்கும்.
- **எளிதா கிடைக்குற data-வை எடுத்துக்கிறது.** Coverage gaps production-ல blind spots ஆகும்.
- **அதிகம்னா எப்பவும் நல்லதுன்னு நம்புறது.** ஆயிரம் noisy examples, நூறு சுத்தமான examples-கிட்ட தோத்துப்போகலாம்.
- **Test items training-க்குள்ள leak ஆக விடுறது.** Split பண்றதுக்கு முன்னாடி duplicates-ஐ நீக்குங்க, test set-ஐ தொடாம வைங்க.
- **Expert workflows-ஐ கண்மூடித்தனமா copy பண்றது.** Experts obvious-ஆ தெரியுற steps-ஐ skip பண்ணுவாங்க. அவங்க எப்படி வேலை செய்யுறாங்கன்னு பார்த்து, ஒவ்வொரு step-ஐயும் எழுதுங்க.
- **Multi-turn cases-ஐ மறக்குறது.** Users conversations பண்ணா, follow-ups, corrections உட்பட conversations-ல train பண்ணுங்க.

## Training dataset தேவையில்லாத நேரங்கள்

- **ஒரு நல்ல prompt ஏற்கனவே தேவையான level-ஐ தொட்டிருக்கு.** முதல்ல அதை அளந்து பாருங்க.
- **பிரச்சனை missing facts.** Dataset-ஐ விட retrieval-ஐ update பண்றது வேகம்.
- **Test பண்ண வழி இல்லை.** முதல்ல test set-ஐ உருவாக்குங்க; training உதவுச்சான்னே அதுதான் சொல்லும்.

## Demo-ல இருந்து production-க்கு

- **Data-வுக்கு version போடுங்க**, guide-ஓடும் cleaning script-ஓடும், எந்த model-ஐயும் திரும்ப உருவாக்க முடியணும்.
- **ஒவ்வொரு example-உம் எங்க இருந்து வந்ததுன்னு record பண்ணுங்க**: ஒரு ஆள் எழுதினதா, model draft பண்ணதா, real use-ல இருந்து எடுத்ததா.
- **Production-ல இருந்து set-ஐ வளர்த்துங்க.** Reviewer corrections-உம் user feedback-உம் தான் உங்க சிறந்த புது examples.
- **Product மாறும்போது guide-ஐ மறுபடி check பண்ணுங்க**, பழைய labels காலாவதியான rules-ஐ கத்துக் கொடுக்காம இருக்க.
- **Deletion path வச்சிருங்க.** யாராவது தங்க data-வை நீக்கச் சொன்னா, அதை கண்டுபிடிச்சு நீக்கி, retrain பண்ண முடியணும்.

## Practice பண்ணுங்க

1. உங்களுக்கு தெரிஞ்ச ஒரு task-ஐ எடுங்க. ஐந்து கஷ்டமான cases-ஓட ஒரு பக்க labelling guide எழுதுங்க.
2. ஒரு friend-ஐ உங்க guide வச்சு 20 items-ஐ label பண்ண சொல்லுங்க, நீங்களும் அதையே பண்ணுங்க. Agreement-ஐ அளந்து, guide-ஐ fix பண்ணுங்க.
3. ஒரு coverage plan எழுதுங்க: உங்க inputs வேறுபடுற ஐந்து வழிகள், ஒவ்வொண்ணுலயும் முதல்ல எத்தனை examples collect பண்ணுவீங்கன்னு.
