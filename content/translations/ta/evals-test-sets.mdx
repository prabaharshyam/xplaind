## இது என்ன

**Evals**-னா ஒரு AI application-க்கான repeatable tests. உண்மையான inputs நிறைஞ்ச ஒரு fixed **test set**-ல app-ஐ run பண்ணி, ஒவ்வொரு output-ஐயும் score பண்ணுவீங்க. அதனால ஒவ்வொரு change-க்கும் (புது prompt, model, retrieval setting) முந்தின number-ஓட ஒப்பிட்டு பார்க்க ஒரு number கிடைக்கும். Evals இல்லைன்னா, teams feel-ல prompts-ஐ மாத்துவாங்க; நல்லதாச்சா மோசமாச்சான்னு அவங்களுக்கே தெரியாது.

```flow
Real inputs | logs, tickets -> Test set: 60 cases | routine 35, claims 10, complaints 8, must escalate 7
Hard cases -> Test set: 60 cases
Past failures -> Test set: 60 cases
Test set: 60 cases -> App version N -> Outputs -> Scorers | code checks, அப்புறம் model judge, அப்புறம் human sample
Scorers -> Version, category வாரியா results -> எந்த category-உம் மோசமாகலைன்னா மட்டும் ship பண்ணுங்க
```

இந்த lesson-ல, Pune-ல ஒரு insurance broker-ஓட policyholder email assistant-ஐ follow பண்ணப் போறோம். எந்த prompt நல்லதுன்னு அங்க team விவாதிச்சுட்டு இருந்தாங்க.

## இது எப்படி work ஆகுது

**Test set-ஐ உண்மையில இருந்து build பண்ணுங்க.** முடிஞ்சா உண்மையான user inputs-ஐ சேகரிங்க (logs, support tickets, sample documents), கூடவே கஷ்டம்னு தெரிஞ்ச cases-ஐயும். ஆரம்பத்துல 30 முதல் 100 வரை போதும். இவை cover ஆகணும்:

- சாதாரண, தினசரி cases;
- edge cases (நீளமான inputs, வித்தியாசமான formats, கலந்த மொழிகள்);
- மறுக்கணும் அல்லது escalate பண்ணணும்ங்குற cases;
- முன்னாடி நடந்த failures (ஒவ்வொரு bug-உம் ஒரு test case ஆகணும்).

**ஒவ்வொரு case-க்கும் "நல்லது"ன்னா என்னன்னு define பண்ணுங்க.** Task-ஐ பொறுத்து:

- exact expected value (category, extract பண்ண field, number);
- answer-ல கண்டிப்பா இருக்கணும்ங்குற facts அல்லது citations;
- answer பண்ணவே கூடாத விஷயங்கள் (refund promise பண்றது, medical advice கொடுக்கிறது);
- ஒரு ஆள் அல்லது model judge apply பண்ற rubric (சரியா இருக்கா, முழுசா இருக்கா, மரியாதையா இருக்கா).

**நம்பகமான, ஆனா cheap-ஆன முறையில score பண்ணுங்க.** முதல்ல code checks: exact match, JSON validity, required keywords, length limits, சரியான citations. Open-ended quality-க்கு model judges, அவங்க grades மனுஷங்க grades-ஓட எவ்வளவு ஒத்துப்போகுதுன்னு check பண்ணி. ஒரு sample-க்கு human review, குறிப்பா ஆரம்பத்துல.

**Data-வை பாருங்க.** Scorers எழுதுறதுக்கு முன்னாடி, 50 முதல் 100 உண்மையான outputs-ஐ படிச்சு, அவை எப்படி fail ஆகுதுன்னு note பண்ணுங்க. ரொம்ப பயனுள்ள evals, பொதுவான metrics-ல இருந்து இல்ல, நாம கவனிச்ச failure patterns-ல இருந்து தான் வருது.

**ஒவ்வொரு change-லயும் run பண்ணி ஒப்பிடுங்க.** Versions-ஓட scores-ஐ, case category வாரியா ஒரு table-ல வச்சுக்கோங்க. Average ஏறுச்சு, ஆனா refusals உடைஞ்சுதுன்னா அது improvement கிடையாது.

**Set-ஐ உயிரோட வச்சிருங்க.** Users புது பிரச்சனைகளை கண்டுபிடிக்கும்போது புது cases சேருங்க; இப்போ உண்மையை பிரதிபலிக்காத cases-ஐ நீக்குங்க; users-ஐ represent பண்ணாம போற அளவுக்கு அந்த set-க்கே tune பண்ணாதீங்க.

**வாக்குவாதத்தை முடிக்கிற ஒரு results table:**

| Version | Judge score | பிடிச்ச escalations | Policy number இருந்தது | Approval promise பண்ணது |
| --- | --- | --- | --- | --- |
| பழைய prompt | 71% | 7-ல 4 | 60-ல 58 | 0 |
| புது prompt | 78% | 7-ல 3 | 60-ல 59 | 0 |
| Escalation rules-ஓட | 80% | 7-ல 7 | 60-ல 60 | 0 |

**முதல்ல outputs-ஐ படிங்க.** ஒரு scorer-ஐ எழுதுறதுக்கு முன்னாடி, 50 முதல் 100 உண்மையான inputs-ல app-ஐ run பண்ணி ஒவ்வொரு output-ஐயும் படிங்க. மோசமான ஒவ்வொண்ணுக்கும் ஒரு சின்ன note எழுதுங்க: "ரெண்டாவது கேள்வியை ignore பண்ணிடுச்சு", "இல்லாத ஒரு policy clause-ஐ கற்பனை பண்ணிடுச்சு", "complaint-க்கு ரொம்ப formal-ஆ இருக்கு". Notes-ஐ group பண்ணுங்க. பெரிய groups தான் உங்க முதல் evals, முடிஞ்சா code checks-ஆ எழுதுங்க. இதுக்கு பெரும்பாலும் ஒரு மதியம் ஆகும்; தப்பான விஷயங்களை அளக்குறதுல போற வாரக்கணக்கான நேரத்தை இது மிச்சப்படுத்தும்.

**ஒரே command-ஆ மாத்துங்க.** யாரும் run பண்ணாத eval, eval-ஏ கிடையாது. Test set-ஐ repository-ல வைங்க, ஒவ்வொரு case-ஐயும் run பண்ணி table-ஐ print பண்ற script எழுதுங்க, ஒவ்வொரு prompt, model, retrieval change-க்கும் CI-ல run பண்ணுங்க. ஒவ்வொரு run-ஓட results-ஐயும் version-ஓட save பண்ணுங்க; அப்போ எந்த ரெண்டு runs-ஐயும் ஒப்பிடலாம்.

**எத்தனை cases.** நல்லா தேர்ந்தெடுத்த முப்பது cases பெரும்பாலான பெரிய regressions-ஐ பிடிக்கும்; நூறு cases category வாரியா stable numbers கொடுக்கும். Size-ஐ விட முக்கியம் coverage: users கவலைப்படுற ஒவ்வொரு category-உம், escalations மாதிரி முக்கியமான categories-ல ஒரு miss கூட தெரியுற அளவுக்கு போதுமான cases-உம். ஏழு escalation cases இருந்தா, ஒரு miss 14 points drop; அதை யாராலும் ignore பண்ண முடியாது. Product வளர வளர set-ஐயும் வளர்த்துங்க, வேலை பண்ணும்போது quick checks-க்கு, சில seconds-ல run ஆகுற சுமார் பத்து cases கொண்ட சின்ன "smoke" set-ஐ தனியா பிரிச்சு வச்சுக்கோங்க.

**கடைசி output-ஐ மட்டும் இல்ல, ஒவ்வொரு step-ஐயும் evaluate பண்ணுங்க.** ஒரு app email-ல இருந்து details-ஐ extract பண்ணி, அப்புறம் reply draft பண்ணுதுன்னா, extraction-ஐயும் தனியா test பண்ணுங்க. கடைசி score இறங்கும்போது, step வாரியா scores எந்த step உடைஞ்சுதுன்னு சொல்லும்.

**ஒரு பெரிய set இல்ல, பல சின்ன sets வச்சுக்கோங்க.** உண்மையான traffic மாதிரி இருக்கும் ஒரு set, app overall எப்படி இருக்குன்னு சொல்லும். கூடவே, தெரிஞ்ச கஷ்டமான cases-ஓட ஒரு set, app மறுக்க வேண்டிய scope-க்கு வெளியில இருக்குற inputs-ஓட ஒரு set, உண்மையான users அனுப்புற typos, கலந்த மொழிகள், Romanised text இருக்குற ஒரு set-உம் சேருங்க. எதை பத்தி கவலைப்படுறீங்களோ, அதுக்கு ஒரு test set கொடுங்க.

**வித்தியாசம் உண்மையானதா?** 60 cases-ல 4 points gain வெறும் noise-ஆ இருக்கலாம். OpenAI சொல்ற ஒரு rough rule: ஒரு version நல்லதுன்னு சுமார் 95% உறுதியா சொல்ல, 30-point வித்தியாசத்துக்கு சுமார் 10 cases, 10 points-க்கு 100, 3 points-க்கு 1,000, 1 point-க்கு 10,000 வேணும். வித்தியாசம் ஒவ்வொரு தடவை 3 மடங்கு சின்னதானா, சுமார் 10 மடங்கு அதிகமான cases வேணும். அதனால பெரிய regressions-ஐ பிடிக்க சின்ன sets, சின்ன gains-ஐ நம்புறதுக்கு முன்னாடி பெரிய sets use பண்ணுங்க.

**Stability-ஐ check பண்ண bootstrap பண்ணுங்க.** உங்க cases-ஐ replacement-ஓட re-sample பண்ணி, ஒவ்வொரு re-sample-ஐயும் score பண்ணி, score எவ்வளவு ஆடுதுன்னு பாருங்க. ஒரு re-sample 90% கொடுத்து, இன்னொண்ணு 70% கொடுத்தா, versions-ஐ ஒப்பிட அந்த set ரொம்ப சின்னது.

```python
import json, random, statistics
from collections import defaultdict

def run_eval(cases, app, checks):
    """cases: dicts with 'input', 'category' and expectations. checks: functions(case, output) -> bool."""
    rows = []
    for case in cases:
        out = app(case["input"])
        rows.append({"category": case["category"], "passed": all(check(case, out) for check in checks)})
    return rows

def report(rows, bootstraps=1000, seed=7):
    by_cat = defaultdict(list)
    for r in rows:
        by_cat[r["category"]].append(r["passed"])
    for cat, results in sorted(by_cat.items()):
        print(f"{cat:<12} {sum(results)}/{len(results)}")
    rng = random.Random(seed)
    scores = [statistics.mean(rng.choice(rows)["passed"] for _ in rows) for _ in range(bootstraps)]
    scores.sort()
    print(f"overall {statistics.mean(r['passed'] for r in rows):.0%}, "
          f"95% of re-samples between {scores[25]:.0%} and {scores[-26]:.0%}")

# cases = [json.loads(line) for line in open("evals/cases.jsonl")]
# report(run_eval(cases, my_app, [no_dosage_advice, keeps_policy_number, escalates_when_needed]))
```

கடைசியில print ஆகுற range ரொம்ப அகலமா இருந்தா, சின்ன வித்தியாசங்களை பத்தி விவாதிக்கிறதுக்கு முன்னாடி இன்னும் cases சேகரிங்க.

**Averages தப்பா வழிநடத்தலாம், கவனமா இருங்க.** Categories-ஓட sizes ரொம்ப வேறுபட்டா, version A ஒவ்வொரு category-லயும் version B-ஐ விட நல்லா இருந்தும், overall-ல தோத்துப் போகலாம். இதுக்கு Simpson's paradox-னு பேரு. Total-ஐ மட்டும் இல்லாம, scores-ஐ category வாரியா படிக்கணும்ங்குறதுக்கு இது இன்னொரு காரணம்.

**Model judge-ஐ calibrate பண்றது.** ஒரே rubric-ஐ வச்சு ரெண்டு பேரை 30 outputs-ஐ grade பண்ண சொல்லுங்க, அப்புறம் judge-ஐ grade பண்ண வைங்க, ஒப்பிடுங்க. Agreement குறைவா இருந்தா, பெரும்பாலும் rubric தெளிவா இல்லைன்னு அர்த்தம்: pass, fail examples-ஓட அதை திரும்ப எழுதி, மறுபடி test பண்ணுங்க. Judge-ஓட model அல்லது prompt-ஐ மாத்தும்போதெல்லாம் agreement-ஐ மறுபடி check பண்ணுங்க, அதே answer-க்கு அதே grade வரணும்னா judge-ஐ temperature 0-ல run பண்ணுங்க. LLM judges, open-ended answers-ஐ score பண்றது பத்தின lessons இன்னும் ஆழமா போகும்.

## ஒரு நாள், ஒரு example

Pune-ல ஒரு insurance broker-ஓட assistant, policyholder emails-க்கு replies draft பண்ணுது. புது prompt நல்லதான்னு team விவாதிக்குது.

அவங்க ஒரு eval build பண்றாங்க:

- 60 உண்மையான emails (anonymise பண்ணது): 35 சாதாரண கேள்விகள், 10 claims-status queries, 8 complaints, 7 மனுஷன் பார்க்க வேண்டியவை (legal threats, medical details).
- Code checks: email-ல policy number இருந்தா reply-லயும் இருக்கணும்; எந்த reply-உம் claim approval promise பண்ணக்கூடாது; ஏழு escalation cases-உம் "needs human"னு mark ஆகணும்.
- ஒரு rubric-ஓட model judge (policy wording-க்கு சரியா இருக்கா, எல்லா கேள்விக்கும் பதில் இருக்கா, மரியாதையா இருக்கா). 30 replies-ல ரெண்டு staff members-ஓட grades-ஓட calibrate பண்ணது (85% agreement).

Results: பழைய prompt judge-ல 71% எடுத்து, 7 escalations-ல 3-ஐ miss பண்ணுது; புது prompt 78% எடுத்தாலும் 4 escalations-ஐ miss பண்ணுது. ரெண்டுமே ஏத்துக்க முடியாது. மூணாவது version-ல explicit escalation rules சேர்த்தாங்க: 80%, 7 escalations-ல 7-ம் பிடிபட்டுச்சு. ஒரு மதியத்துல அந்த table வாக்குவாதத்தை முடிச்சுடுச்சு.

**Broker இதுக்கப்புறம் என்ன வச்சுக்கிட்டாங்க.** மோசமான reply பத்தின ஒவ்வொரு complaint-ஐயும், அதோட category-ஓட ஒரு புது case-ஆ team இப்போ சேக்குறாங்க. மூணு மாசத்துக்கு அப்புறம் set 60-ல இருந்து 140 cases-ஆ வளர்ந்திருக்கு, prompts பத்தின வாக்குவாதங்களை table தான் தீர்க்குது, பெரும்பாலும் சில நிமிஷத்துல.

## பொதுவா பண்ற தப்புகள்

- **Test set-ஏ இல்லாம இருக்கிறது.** ரெண்டு examples-ஐ பார்த்து changes-ஐ judge பண்றது.
- **கற்பனையா எழுதின test cases மட்டும்.** உண்மையான inputs-ஐ use பண்ணுங்க.
- **Averages மட்டும் பார்க்கிறது.** Categories-ஐ பாருங்க, குறிப்பா safety cases-ஐ.
- **Check பண்ணாத model judges.** மனுஷங்க grades-ஓட ஒப்பிடுங்க.
- **மாறாத frozen set.** ஒவ்வொரு புது failure-ஐயும் சேருங்க.

## எப்போ சின்ன eval போதும்

- **ஆரம்ப prototypes**: நீங்களே கையால படிக்கிற 20 முதல் 30 cases, ஒரு பெரிய pipeline-ஐ விட நல்லது.
- **பெரிய, தெளிவான changes**, உதாரணமா தெளிவா நல்லதோ மோசமோ ஆன ஒரு புது model, சின்ன set-லயே தெரிஞ்சுடும்.
- **Classification மாதிரி closed tasks**, code-ஆலயே score பண்ணிடலாம்; judge தேவையில்லை.

## Demo-ல இருந்து production-க்கு

- **ஒரே command, CI-ல**: ஒவ்வொரு prompt, model, retrieval அல்லது code change-லயும் eval-ஐ run பண்ணுங்க; முக்கியமான category மோசமானா release-ஐ block பண்ணுங்க.
- **Results-ஓட எல்லாத்தையும் version பண்ணுங்க**: test set, rubric, judge prompt, model, app prompt, settings. அப்போ எந்த ரெண்டு runs-ஐயும் ஒப்பிடலாம்.
- **Eval-ஐயே check பண்ணுங்க**: அதிக scores, users-ம் reviewers-ம் "நல்லது"ன்னு சொல்றதோட ஒத்துப்போகுதா? ரெண்டு metrics எப்பவும் சேர்ந்தே நகருதுன்னா, ஒண்ணை drop பண்ணுங்க; ஒருபோதும் ஒத்துப்போகலைன்னா, ஆராயுங்க.
- **Cost-ஐ கவனிங்க**: வேலை பண்ணும்போது quick smoke set-ஐயும், release-க்கு முன்னாடி முழு set-ஐயும் run பண்ணுங்க.
- **Production-ஐ திரும்ப உள்ள கொண்டு வாங்க**: logs, complaints, online evals-ல இருந்து வர்ற failures ஒவ்வொரு வாரமும் புது cases ஆகணும்.
