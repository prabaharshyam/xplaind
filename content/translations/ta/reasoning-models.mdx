## இது என்ன

AI-ல பெரும்பாலான பணம் நீங்க ஒரு model-ஐ பாக்குறதுக்கு முன்னாடியே செலவாகுது: அதை train பண்றதுல. **Test-time compute** அதோட மறுபக்கம். Answer பண்ற நேரத்துல அதிகம் computing செலவழிக்கிறது, அப்போ answer சரியா இருக்க வாய்ப்பு அதிகம். "Test time"-ங்கிறது inference-க்கான research வார்த்தை, model use ஆகுற நேரம்.

இதை செய்ய மூணு பொதுவான வழிகள் இருக்கு.

1. **படிப்படியா யோசிக்க சொல்லுங்க.** இது **chain-of-thought** (CoT) prompting: model answer-க்கு முன்னாடி தன்னோட reasoning-ஐ எழுதும். இதோட நெருங்கிய சொந்தம் **self-critique**, அங்க model முடிக்கிறதுக்கு முன்னாடி தன்னோட draft-ஐ தானே check பண்ணும்.
2. **பல answers-ஐ உருவாக்கி சிறந்ததை வச்சுக்கோங்க.** இது **best-of-N**. வெற்றியாளரை ஒரு **verifier** (ஒரு test, ஒரு rule check அல்லது ஒரு scoring model) மூலமா, அல்லது answers exact-ஆ இருந்தா majority vote மூலமா எடுக்கலாம்.
3. **ஒரு reasoning model-ஐ use பண்ணுங்க.** இந்த models answer பண்றதுக்கு முன்னாடி நீண்ட நேரம் யோசிக்க train பண்ணப்பட்டவை. பெரும்பாலானவை எவ்ளோ effort செலவழிக்கணும்னு set பண்ண விடும், சிலது thinking-ஐ மறைச்சு result-ஐ மட்டும் காட்டும்.

மூணுமே accuracy-க்காக பணத்தையும் காத்திருக்குற நேரத்தையும் மாத்திக்குது. எப்போ இந்த trade worth-னு தெரிஞ்சுக்கிறது தான் திறமை.

```flow
title: ஒரு question-க்கு எவ்ளோ thinking வேணும்னு தேர்ந்தெடுக்குறது
New question -> Plain model-க்கு கஷ்டமா? | உங்க test set-ஐ பாருங்க
Plain model-க்கு கஷ்டமா? -[இல்ல]-> Plain answer | வேகம், மலிவு
Plain model-க்கு கஷ்டமா? -[ஆமா]-> Step-by-step prompt | இதை முதல்ல try பண்ணுங்க
Step-by-step prompt -> போதுமானதா?
போதுமானதா? -[ஆமா]-> Ship பண்ணுங்க
போதுமானதா? -[இல்ல]-> Answers-ஐ check பண்ண முடியுமா? | tests, rules, exact values
Answers-ஐ check பண்ண முடியுமா? -[ஆமா]-> N sample பண்ணி verify பண்ணுங்க | best-of-N அல்லது vote
Answers-ஐ check பண்ண முடியுமா? -[இல்ல]-> Reasoning model | effort budget set பண்ணுங்க
```

## இது எப்படி work ஆகுது

**Chain of thought.** எளிய வடிவம் ஒரு வரி சேக்கும்: "Answer-க்கு முன்னாடி படிப்படியா யோசிங்க," அல்லது "உங்க reasoning-ஐ விளக்குங்க, அப்புறம் final answer-ஐ கடைசி வரியில தாங்க." நீங்க விரும்புற steps-ஐ list பண்ணலாம், அல்லது ஒரு worked example காட்டலாம். இந்த முறைக்கு பேர் வச்ச 2022 paper, maths word problems-ல பெரிய gains-ஐ காட்டுச்சு; அப்புறம் வந்த வேலை, இது கற்பனை facts-ஐ குறைக்கலாம்னு கண்டுபிடிச்சுது. சிக்கல் நீளம்: reasoning-ஓட answer-ல tokens நிறைய இருக்கும், அவை எல்லாத்துக்கும் பணமும் நேரமும் செலவாகும்.

**Best-of-N.** பல answers கேளுங்க, முடிஞ்சா கொஞ்சம் வித்தியாசத்தோட (அதிக temperature அல்லது கொஞ்சம் மாறின prompts), அப்புறம் ஒண்ணை தேர்ந்தெடுங்க.

- **ஒரு verifier-ஓட.** உருவாக்கின code-ஐ tests-ஓட ஓட்டுறது, உருவாக்கின SQL-ஐ ஓட்டி rows வருதான்னு பாக்குறது, extract பண்ண date ஒரு உண்மையான date-ஆன்னு check பண்றது. Maths-க்கு ஒரு நல்ல verifier-ஓட ஒரு சின்ன model, verifier இல்லாத கிட்டத்தட்ட 30 மடங்கு பெரிய model-ஓட பொருந்துறதை OpenAI கண்டுபிடிச்சுது.
- **Majority vote மூலமா**, இதை self-consistency-ன்னும் சொல்வாங்க. அதே maths question-ஐ அஞ்சு தடவை கேட்டு, அடிக்கடி வர்ற final number-ஐ எடுங்க. Answers exact-ஆ இருக்கும்போது இது work ஆகும்: ஒரு number, ஒரு label, ஒரு choice.
- **ஒரு scoring model மூலமா.** ஒரு reward model அல்லது LLM judge ஒவ்வொரு answer-ஐயும் rate பண்ணும். Open-ended text-க்கு இது work ஆகும், ஆனா judge எவ்ளோ நல்லதோ அவ்ளோ தான்.

N answers-ஐ sample பண்றது கிட்டத்தட்ட N மடங்கு செலவாகும், அதனால N பொதுவா சின்னது: உண்மையான products-ல 3-ல இருந்து 8. நூற்றுக்கணக்கான அல்லது ஆயிரக்கணக்கான samples-ஓட research runs gains தொடர்ந்து வர்றதை காட்டுது, ஆனா எந்த product-உம் ஒவ்வொரு request-க்கும் அதை தாங்க முடியாது.

**Reasoning models.** இவை, பெரும்பாலும் checkable answers உள்ள problems-ல reinforcement learning-ஓட, reply பண்றதுக்கு முன்னாடி ஒரு நீண்ட உள் chain of thought-ஐ உருவாக்க train பண்ணப்படுது. இதை பொதுவா ஒரு effort அல்லது budget setting மூலமா கட்டுப்படுத்துவீங்க. Maths, code, planning, multi-step analysis-ல இவை பிரகாசிக்கும். எளிய questions-ல பெரும்பாலும் cost, delay-ஐ மட்டும் கூட்டும்.

Majority voting-க்கு ஒரு சின்ன helper:

```python
from collections import Counter

def majority_answer(ask, question, n=5):
    """ask(question) returns the model's final answer as a short string."""
    answers = [ask(question).strip().lower() for _ in range(n)]
    best, votes = Counter(answers).most_common(1)[0]
    agreement = votes / n
    # Low agreement is a signal: send it to a stronger model or a person.
    return best, agreement

# answer, agreement = majority_answer(ask, "If 3x + 7 = 25, what is x?")
# if agreement < 0.6: escalate(question)
```

| Method | கூடுதல் cost | கூடுதல் காத்திருப்பு | எப்போ சிறந்தது | கவனிக்க வேண்டியது |
| --- | --- | --- | --- | --- |
| Step-by-step prompt | Output tokens-ஓட 2-ல இருந்து 5 மடங்கு | சில வினாடிகள் | Multi-step problems | Users scroll பண்ணி தாண்ட வேண்டிய நீண்ட answers |
| 5-ஓட majority vote | கிட்டத்தட்ட 5 மடங்கு | Parallel-ஆ ஓடுனா கொஞ்சம் | Exact answers: numbers, labels | Free-form text-க்கு பயனில்ல |
| Verifier-ஓட best-of-N | கிட்டத்தட்ட N மடங்கு, கூட checks | Parallel-ஆ இருந்தா கொஞ்சம் | Code, SQL, test பண்ணக்கூடிய formats | பலவீனமான verifier மோசமான answers-ஐ தேர்ந்தெடுக்கும் |
| Reasoning model | அடிக்கடி 3-ல இருந்து 10 மடங்கு | வினாடிகள்-ல இருந்து நிமிடங்கள் | கஷ்டமான maths, code, planning | எளிய questions-க்கும் thinking-க்கு பணம் கொடுக்குறது |

இந்த multipliers, options-ஐ ஒப்பிட உதவுற தோராயமான patterns, விலைகள் இல்ல. உங்க சொந்த questions-ல அளங்க.

## ஒரு worked example

Kota-ல ஒரு coaching company, JEE-style maths problems-க்கு students-ஓட answers-ஐ AI check பண்ணி தப்புகளை விளக்கணும்னு விரும்புது, ஒரு நாளைக்கு கிட்டத்தட்ட 300 problems. Answers தெரிஞ்ச 200 problems-ஓட ஒரு test set-ஐ உருவாக்கி options-ஐ ஒப்பிடுறாங்க.

| Option | சரியான checks | 100 problems-க்கு cost | வழக்கமான காத்திருப்பு |
| --- | --- | --- | --- |
| Mid-size model, plain prompt | 71% | ₹20 | 3 s |
| அதே model, step-by-step prompt | 81% | ₹55 | 8 s |
| Step-by-step, 5-ல majority | 88% | ₹275 | 9 s (parallel) |
| Reasoning model, medium effort | 90% | ₹120 | 20 s |
| Route: 5-ல majority, votes ஒத்துப்போகலன்னா மட்டும் reasoning model | 91% | ₹140 | பெரும்பாலானவைக்கு 9 s, சிலதுக்கு 25 s |

இந்த numbers உதாரணத்துக்கு தான், எப்படி ஒப்பிடுறதுன்னு காட்ட. ரெண்டு விஷயங்கள் தனியா தெரியுது. Step-by-step prompt ஒரு பெரிய, மலிவான வெற்றி. அப்புறம் routing எல்லா single options-ஐயும் மிஞ்சுச்சு: அஞ்சுல நாலு அல்லது அஞ்சு samples ஒத்துப்போனா, answer கிட்டத்தட்ட எப்பவும் சரியா இருக்கும்; அதனால சர்ச்சையான problems (ஆறுல ஒண்ணு) மட்டும் reasoning model-க்கு போகுது.

"Checking your working…"-ன்னு ஒரு progress bar-ஓட காட்டுறாங்க; ஏன்னா ஏதோ நடக்குதுன்னு பாக்க முடிஞ்சா students ஒரு சின்ன காத்திருப்பை ஏத்துக்குவாங்க.

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்துக்கும் reasoning model use பண்றது.** எளிய lookups, greetings, formatting-க்கு அது தேவையில்ல. ஒண்ணும் சேக்காத thinking-க்கு பணம் கொடுக்குறீங்க.
- **மலிவான படியை தவிர்க்கிறது.** ஒரு step-by-step prompt பெரும்பாலும் ஒரு சின்ன செலவுல பெரிய இடைவெளியை அடைக்கும்.
- **Free-form text-ல vote பண்றது.** ரெண்டு நல்ல paragraphs எப்பவும் ஒரே மாதிரி இருக்காது, அதனால vote எதுவும் கண்டுபிடிக்காது. அதுக்கு பதிலா ஒரு verifier அல்லது ஒரு judge use பண்ணுங்க.
- **பலவீனமான verifier-ஐ நம்புறது.** Checker-ஐ ஏமாத்த எளிதுன்னா, best-of-N அதை சிறப்பா ஏமாத்துற answer-ஐ தேர்ந்தெடுக்கும்.
- **Users-க்கு raw reasoning-ஐ காட்டுறது.** அது நீளமா இருக்கும், குழப்பலாம், தப்பான திருப்பங்களும் இருக்கலாம். Answer-ஐயும் ஒரு சின்ன விளக்கத்தையும் காட்டுங்க.
- **காத்திருப்பை மறக்குறது.** Thinking முடியுற வரை user எதையும் பாக்க மாட்டாரு. Model-ஓட first token-ஐ இல்ல, "user பாக்குற முதல் வார்த்தைக்கான நேரத்தை" அளங்க.

## அதிக thinking தப்பான tool-ஆ இருக்கும் நேரங்கள்

- **Model-க்கு facts இல்ல.** நீண்ட நேரம் யோசிச்சா knowledge சேராது. Retrieval use பண்ணுங்க.
- **Task எளிது அல்லது creative.** சின்ன replies, summaries, tone மாற்றங்கள் அரிதா மேம்படும்.
- **ஒரு சின்ன gain-ஐ விட latency முக்கியம்.** ஒரு voice agent அல்லது autocomplete பத்து வினாடி காத்திருக்க முடியாது.
- **Gain-ஐ அளக்க முடியல.** Test set இல்லன்னா, அதிகம் செலவழிப்பீங்க, ஆனா அது உதவுச்சான்னு தெரியாது.

## Demo-ல இருந்து production-க்கு

- **Difficulty வச்சு route பண்ணுங்க.** எளிய questions-ஐ வேகமான model-க்கு அனுப்பி, ஒரு check fail ஆனா அல்லது samples ஒத்துப்போகலன்னா மட்டும் escalate பண்ணுங்க.
- **Budget-ஐ cap பண்ணுங்க.** Effort அல்லது thinking limits-ஐயும் ஒரு maximum output length-ஐயும் set பண்ணி, ஒரு request-க்கு cost-ஐ track பண்ணுங்க.
- **Samples-ஐ parallel-ஆ ஓட்டுங்க.** அஞ்சு answers ஒரே நேரத்துல ஒண்ணு மாதிரியே நேரம் எடுக்கும்.
- **Progress காட்டுங்க.** ஒரு visible step அல்லது progress message காத்திருப்பை குறைவா உணர வைக்கும்.
- **Disagreements-ஐ log பண்ணுங்க.** Samples ஒத்துப்போகாத questions தான் உங்க சிறந்த test cases, training examples.

## Practice பண்ணுங்க

1. Answers தெரிஞ்ச பத்து maths அல்லது logic questions-ஐ எடுங்க. ஏதாவது ஒரு chat model-ல ஒரு plain prompt-ஐ, அப்புறம் ஒரு step-by-step prompt-ஐ score பண்ணுங்க.
2. அது தப்பா பண்ண questions-க்கு, ஒவ்வொண்ணுக்கும் அஞ்சு answers-ஐ sample பண்ணி majority எடுங்க. Vote எத்தனையை சரிபண்ணுச்சு?
3. ஒவ்வொரு method-க்கும் cost, காத்திருப்பை எழுதி, ஒரு student app-க்கு எதை ship பண்ணுவீங்கன்னு முடிவு பண்ணுங்க.
