## இது என்ன

AI-ல பெரும்பாலான பணம் நீங்க ஒரு model-ஐ பாக்குறதுக்கு முன்னாடியே செலவாகுது: அதை train பண்றதுல. **Test-time compute** அதோட மறுபக்கம். Answer பண்ற நேரத்துல அதிகம் computing செலவழிக்கிறது, அப்போ answer சரியா இருக்க வாய்ப்பு அதிகம். "Test time"-ங்கிறது inference-க்கான research வார்த்தை, அதாவது train ஆன ஒரு model use ஆகுற நேரம்.

இதை செய்ய மூணு பொதுவான வழிகள் இருக்கு.

1. **Step by step யோசிக்க சொல்லுங்க.** இது **chain-of-thought** (CoT) prompting: model answer-க்கு முன்னாடி தன்னோட reasoning-ஐ எழுதும். இதோட நெருங்கிய சொந்தம் **self-critique**: model முடிக்கிறதுக்கு முன்னாடி தன்னோட draft-ஐ தானே check பண்ணும்.
2. **பல answers-ஐ generate பண்ணி best-ஐ வச்சுக்கோங்க.** இது **best-of-N**. ஒரு **verifier** (ஒரு test, ஒரு rule check அல்லது ஒரு scoring model) winner-ஐ தேர்ந்தெடுக்கும்; answers exact-ஆ இருந்தா ஒரு majority vote அதை செய்யும்.
3. **ஒரு reasoning model-ஐ use பண்ணுங்க.** இந்த models answer பண்றதுக்கு முன்னாடி நீளமா யோசிக்க train பண்ணப்பட்டவை. அவை எவ்வளவு effort செலவழிக்கணும்னு நீங்க set பண்ணுவீங்க. Thinking அடிக்கடி மறைஞ்சிருக்கும்: நீங்க answer-ஐ மட்டும் தான் பாப்பீங்க, ஆனா thinking-க்கும் பணம் கட்டுவீங்க.

மூணுமே accuracy-க்காக பணத்தையும் காத்திருக்குற நேரத்தையும் விட்டுக்குடுக்குது. Model சரியான answer-ஐ *அடைய முடியும்*, ஆனா வழியில அடிக்கடி தடுமாறும்போது தான் கூடுதல் thinking பலன் தரும்: multi-step maths, code, planning மாதிரி. Model-கிட்ட facts இல்லைன்னா அது உதவாது.

## இது எப்படி work ஆகுது

### Chain of thought

இதோட எல்லாத்தையும் விட simple-ஆன version prompt-ல ஒரே ஒரு line சேர்க்குறது தான்: "Think step by step, then give only the final answer on the last line." நீங்க வேணும்ங்கிற steps-ஐ list பண்ணலாம், அல்லது ஒரு worked example காட்டலாம். இந்த method-க்கு பேர் வச்ச 2022 paper (Wei and others, கீழ link இருக்கு) பெரிய models-ல maths word problems-ல பெரிய gains காட்டுச்சு. கடைசி line-ல வர்ற answer முக்கியம்: உங்க code அதை கண்டுபிடிக்கணும்.

முதல் சிக்கல் நீளம்: reason பண்ணின ஒரு answer-ல நிறைய அதிக tokens இருக்கும், ஒவ்வொண்ணுக்கும் பணமும் நேரமும் ஆகும். ரெண்டாவது சிக்கல் சத்தமில்லாதது: **எழுதின reasoning தான் answer-க்கான உண்மையான காரணம்னு எந்த guarantee-உம் இல்ல.** 2025 Anthropic study-ல, models-க்கு answer-க்கான ஒரு hint ரகசியமா குடுக்கப்பட்டது. அவை hint-ஐ use பண்ணப்போ, Claude 3.7 Sonnet தன்னோட reasoning-ல அதை 25% நேரம் மட்டும் தான் சொல்லுச்சு, DeepSeek R1 39% நேரம். முன்னாடி வந்த work (Turpin and others, 2023) chain-of-thought prompts-லயும் இதே pattern-ஐ கண்டுபிடிச்சுது. அதனால காட்டுற reasoning-ஐ ஒரு உதவியான draft-ஆ பாருங்க, proof-ஆ இல்ல. Steps எவ்வளவு நம்பும்படி இருக்குன்னு இல்ல, final answer-ஐ check பண்ணுங்க.

### Best-of-N-உம் verifiers-உம்

கொஞ்சம் variety-ஓட (zero-க்கு மேல ஒரு temperature, அல்லது கொஞ்சம் வேற வேற prompts) பல answers கேளுங்க, அப்புறம் ஒண்ணை தேர்ந்தெடுங்க.

- **Majority vote மூலமா**, இதை **self-consistency**-ன்னும் சொல்லுவாங்க. ஒரே maths question-ஐ அஞ்சு தடவை கேட்டு, எல்லாத்தையும் விட அதிகமா வர்ற final number-ஐ எடுங்க. Answers exact-ஆ இருந்தா மட்டும் தான் இது work ஆகும்: ஒரு number, ஒரு label, ஒரு choice. ஒத்துப்போறதும் ஒரு signal: samples ஒத்துப்போகலைன்னா, அந்த question கஷ்டமானதா இருக்க வாய்ப்பு அதிகம்.
- **ஒரு outcome verifier-ஓட**, இது final answer-ஐ check பண்ணும். Generate ஆன code-ஐ tests மேல ஓட்டுங்க, generate ஆன SQL-ஐ ஓட்டி அதோட result-ஐ ஏற்கனவே தெரிஞ்ச ஒரு result-ஓட compare பண்ணுங்க, அல்லது extract பண்ணின date உண்மையான date-ஆன்னு check பண்ணுங்க. 2021-ல OpenAI report பண்ணுச்சு: grade-school maths problems-ல, ஒரு trained verifier-ஓட இருந்த 6-billion-parameter model, fine-tune பண்ணின ஒரு 175-billion-parameter model-ஐ கொஞ்சமா வென்றது; இந்த gain-ஐ model size-ல 30 மடங்கு அதிகரிப்புக்கு சமம்னு அவங்க ஒப்பிட்டாங்க.
- **ஒரு process verifier-ஓட**, பொதுவா ஒரு **process reward model** (PRM); இது கடைசியை மட்டும் இல்லாம ஒவ்வொரு step-ஐயும் score பண்ணும். OpenAI-ஓட 2023 paper "Let's Verify Step by Step", competition maths-ல answer-level feedback-ஐ விட step-level feedback நல்லா இருந்துச்சுன்னு கண்டுபிடிச்சுது; அது ஒரு test subset-ல 78% solve பண்ணுச்சு. இந்த lesson-ஓட main resource-ஆன Hugging Face write-up, search-ஐ guide பண்ண ஒரு PRM-ஐ use பண்ணுச்சு; போதுமான samples குடுத்தப்போ, MATH-500 benchmark-ல 1B, 3B models அவற்றோட 8B, 70B siblings-ஐ வென்றதை காட்டுச்சு.
- **ஒரு scoring model-ஓட**, ஒரு LLM judge மாதிரி. இது open-ended text-க்கு work ஆகும், ஆனா judge எவ்வளவு நல்லதோ அவ்வளவு தான்.

N answers-ஐ sample பண்ண கிட்டத்தட்ட N மடங்கு cost ஆகும், அதனால N பொதுவா சின்னது: products-ல சுமார் 3 முதல் 8, research runs-ல use பண்ற நூற்றுக்கணக்கானதை விட ரொம்ப கம்மி.

Majority voting-க்கு ஒரு சின்ன helper. Normalising step-ஐ கவனிங்க: "12.50", "25/2", "12.5" எல்லாம் ஒரே answer தான், ஒரு plain text comparison vote-ஐ மூணா பிரிச்சுடும்.

```python
from collections import Counter
from fractions import Fraction

def normalise(text):
    """Turn '12.50', ' 25/2 ' and '12.5' into the same vote. Non-numbers stay as text."""
    t = text.strip().lower().rstrip(".")
    try:
        return Fraction(t)  # exact, so rounding never splits a vote
    except (ValueError, ZeroDivisionError):
        return t

def majority_answer(ask, question, n=3):
    """ask(question) returns the model's final answer as a short string."""
    votes = Counter(normalise(ask(question)) for _ in range(n))
    best, count = votes.most_common(1)[0]
    unanimous = count == n
    # Accept only a unanimous answer. Anything else goes to the stronger model.
    return best, unanimous

# answer, ok = majority_answer(ask, "If 3x + 7 = 25, what is x?")
# if not ok: answer = ask_reasoning_model(question)
```

கடைசி line-ல ஒரு வெறும் number-ஐ மட்டும் தர model-கிட்ட கேளுங்க. "x = 6" மாதிரி ஒரு answer text-ஆவே இருக்கும், "6"-ஓட match ஆகாது.

### Reasoning models

இந்த models, அடிக்கடி check பண்ணக்கூடிய answers இருக்குற problems மேல reinforcement learning மூலமா, reply பண்றதுக்கு முன்னாடி நீளமா யோசிக்க train பண்ணப்படுது. Maths, code, planning-ல இவை ஜொலிக்கும்; simple questions-ல பெரும்பாலும் cost-உம் delay-உம் தான் கூட்டும்.

நீங்க இவற்றை prompt-ஆல இல்ல, ஒரு **effort setting**-ஆல steer பண்ணுவீங்க. உதாரணமா, November 2026 நிலவரப்படி, OpenAI-ஓட Responses API-ல `reasoning.effort` இருக்கு, Anthropic-ஓட API-ல `output_config.effort` இருக்கு; recent Claude models-ல அதோட levels `low`-ல இருந்து `max` வரை. Effort-ங்கிறது ஒரு soft guidance, token count இல்ல: low effort-ல ஈஸியான inputs-க்கு model thinking-ஐ skip பண்ணலாம். Defaults model-க்கு model மாறும் (Anthropic-ஓட default பெரும்பாலான Claude models-ல `high`, சில புது models-ல `medium`), அதனால effort-ஐ explicit-ஆ set பண்ணுங்க, ரெண்டு மூணு levels-ஐ தனித்தனி options-ஆ test பண்ணுங்க. பழைய tutorials ஒரு fixed thinking budget (`budget_tokens`) காட்டும்; Anthropic அதை deprecate பண்ணிடுச்சு, Claude 4.7-உம் அதுக்கு அப்புறம் வந்த models-உம் அதை reject பண்ணும்.

**Reasoning model மேல chain-of-thought prompts-ஐ அடுக்காதீங்க.** அது ஏற்கனவே answer பண்றதுக்கு முன்னாடி யோசிக்குது. OpenAI தன்னோட o1 reasoning models-ஐ launch பண்ணப்போ, அதோட prompting guide simple, direct prompts-ஐ use பண்ணவும், chain-of-thought instructions குடுக்காம இருக்கவும் சொல்லுச்சு. Anthropic முதல்ல effort level-ஐ மாத்த சொல்லுது, அதுக்கு அப்புறம் தான், ஒரு task-க்கு இன்னும் தேவைப்பட்டா, "Think carefully before responding" மாதிரி ஒரு சின்ன nudge. Steps-ஐ script பண்ணாதீங்க, எல்லா reasoning-ஐயும் reply-ல கேக்காதீங்க: மறைஞ்ச thinking-க்கு ஒரு தடவை, அதோட visible copy-க்கு இன்னொரு தடவை பணம் கட்டுவீங்க.

### நீங்க எதுக்கு பணம் கட்டுறீங்க, user எதுக்கு காத்திருக்காரு

- **Thinking output tokens-ஆ bill ஆகும்**, நீங்க அதை பாக்கவே இல்லைன்னாலும். Output tokens பொதுவா input tokens-ஐ விட அதிகம் cost ஆகும்.
- **ஒரு summary-க்கும் முழு thinking-ஓட cost தான்.** Anthropic thinking-ஓட ஒரு சின்ன summary-ஐ return பண்ண முடியும், ஆனா summary-ஓட நீளத்துக்கு இல்ல, அதுக்கு பின்னாடி இருக்குற முழு thinking-க்கும் bill ஆகும்.
- **Thinking output limit-ல கணக்காகும்.** சின்ன replies-க்கு அளவு வச்ச ஒரு output limit (Anthropic-ல `max_tokens`) thinking நடக்கும்போதே தீர்ந்துடலாம், reply கொஞ்சம் answer-ஓட அல்லது answer-ஏ இல்லாம நின்னுடும். ரெண்டுக்கும் இடம் விடுங்க, அல்லது effort-ஐ குறைங்க.
- **உண்மையான count-ஐ படிங்க.** Anthropic அதை `usage.output_tokens_details.thinking_tokens`-ல report பண்ணும்; OpenAI தன்னோட usage data-ல `output_tokens_details`-க்கு கீழ reasoning tokens-ஐ report பண்ணும். ஒவ்வொரு request-க்கும் அதை log பண்ணுங்க: உங்க bill-ஐ விளக்குற number அது தான்.
- **Thinking நடக்கும்போது visible-ஆ எதுவும் stream ஆகாது.** Thinking மறைஞ்சிருந்தா (Anthropic-ஓட Claude 5 models-ல அது தான் default), thinking முடிஞ்ச அப்புறம் தான் முதல் visible வார்த்தை வரும். User பாக்குற முதல் வார்த்தை வரைக்குமான நேரத்தை அளங்க, progress-ஆ ஒரு status line அல்லது ஒரு thinking summary காட்டுங்க.
- **Multi-turn chats-க்கு அதிக cost.** Conversation-ல இருக்குற thinking அடுத்த turns-ல input-ஆ bill ஆகும்: சில models-ல முந்தைய ஒவ்வொரு turn-ல இருந்தும், வேற சிலதுல கடைசி turn-ல இருந்து மட்டும். Conversation நடுவுல effort level-ஐ மாத்துறதும் prompt cache-ஐ உடைக்கலாம்.

### Methods-ஐ பக்கத்து பக்கத்துல வச்சு பாத்தா

| Method | கூடுதல் cost | கூடுதல் காத்திருப்பு | எப்போ best-ஆ work ஆகும் | எதுல கவனம் வேணும் |
| --- | --- | --- | --- | --- |
| Step-by-step prompt | Output tokens-ஓட 2 முதல் 5 மடங்கு | வினாடிகள் | Non-reasoning model-ல multi-step problems | நீளமான replies; சரியா தோணும் ஆனா சரியில்லாத reasoning |
| 5-ஓட majority vote | சுமார் 5 மடங்கு | Parallel-ஆ ஓட்டினா கொஞ்சம் தான் | Exact answers: numbers, labels | Free-form text-க்கு பயனில்ல; எல்லா samples-க்கும் ஒரே blind spots |
| Verifier-ஓட best-of-N | சுமார் N மடங்கு, கூட checks | Parallel-ஆ இருந்தா கொஞ்சம் தான் | Code, SQL, test பண்ணக்கூடிய formats | ஒரு weak verifier மோசமான answers-ஐ எடுக்கும் |
| Reasoning model | அடிக்கடி 3 முதல் 10 மடங்கு | வினாடிகள்ல இருந்து நிமிஷங்கள் வரை | கஷ்டமான maths, code, planning | மறைஞ்ச thinking-க்கு bill; output limit ரொம்ப சின்னது |

இந்த multipliers options-ஐ compare பண்றதுக்கான தோராயமான patterns, prices இல்ல. உங்க சொந்த questions-ல அளந்து பாருங்க.

## ஒரு worked example

Kota-ல ஒரு coaching company, JEE-style maths problems-க்கு students-ஓட answers-ஐ AI check பண்ணி தப்புகளை விளக்கணும்னு விரும்புது, ஒரு நாளைக்கு சுமார் 300 problems. Teachers தினமும் புது practice problems எழுதுறாங்க, students வேற books-ல இருந்தும் doubts upload பண்றாங்க, அதனால பெரும்பாலான problems **answer key இல்லாம** தான் வருது. AI முதல்ல சரியான answer-ஐ கண்டுபிடிக்கணும், அப்புறம் அதை student-ஓட answer-ஓட compare பண்ணணும். (Key இருக்குற இடத்துல, ஒரு plain comparison அந்த பகுதியை செஞ்சுடும், எந்த model-உம் தேவையில்ல.)

Options-ஐ compare பண்ண, teachers check பண்ணின answers இருக்குற 200 பழைய problems-ஓட ஒரு test set-ஐ team build பண்ணுது. கீழ "சரி"-ன்னா அந்த option சரியான answer-ஐ கண்டுபிடிச்சுதுன்னு அர்த்தம். அதுக்கு அப்புறம் வர்ற explanation step எல்லா option-க்கும் ஒரே cost தான், அதனால அதை விட்டுட்டோம். எல்லா numbers-உம் method-ஐ காட்டுறதுக்காக தேர்ந்தெடுத்த உதாரணங்கள் தான்; அளந்த prices இல்ல.

Testing-க்கு முன்னாடியே ஒத்துக்கிட்ட targets: குறைஞ்சது 88% சரி, 100 problems-க்கு ₹150-க்கு கீழ, பெரும்பாலான students-க்கு 10 வினாடிக்குள்ள result.

| Option | சரி | 100 problems-க்கு cost | வழக்கமான காத்திருப்பு |
| --- | --- | --- | --- |
| Mid-size model, plain prompt | 71% | ₹20 | 3 s |
| அதே model, step-by-step prompt | 81% | ₹55 | 8 s |
| Step-by-step, 5-ஓட majority | 88% | ₹275 | 9 s (parallel) |
| Reasoning model, low effort | 82% | ₹45 | 8 s |
| Reasoning model, medium effort | 90% | ₹120 | 20 s |
| Reasoning model, high effort | 91% | ₹260 | 45 s |
| Router: 3 plain answers, அவை ஒத்துப்போகலைன்னா மட்டும் reasoning model (medium) | 90.5% | ₹96 | 70%-க்கு 3 s, 30%-க்கு 23 s |

**Noise-ஐ மனசுல வச்சு படிங்க.** 200 problems-ல, 90% பக்கத்துல margin of error ரெண்டு பக்கமும் சுமார் 4 points (Quality, cost, speed trade-offs lesson-ஐ பாருங்க). அதனால quality-ல 88%, 90%, 90.5%, 91% எல்லாம் tie தான், cost-உம் காத்திருப்பும் தான் முடிவு பண்ணும்.

- Step-by-step prompt ஒரு பெரிய, மலிவான வெற்றி: 100-க்கு ₹35 அதிகமா 10 points. தானா reason பண்ணாத எந்த model-லயும் இதை முதல்ல try பண்ணுங்க.
- Low effort target-ஐ miss பண்ணுது. High effort, medium-ஐ விட ரெண்டு மடங்குக்கும் அதிகமா cost ஆகுது, students-ஐ 45 வினாடி காத்திருக்க வைக்குது, அதுவும் noise-க்குள்ள இருக்குற ஒரு gain-க்காக. ஒரு effort sweep-ஓட வழக்கமான shape இது தான்: ஆரம்பத்துல பெரிய gains, அப்புறம் அதிக விலைக்கு சின்ன gains.
- 5-ஓட majority-யும் high effort-உம் budget-ஐ உடைக்குது. Medium effort quality-யையும் cost-ஐயும் தாண்டுது, ஆனா ஒவ்வொரு student-உம் 20 வினாடி காத்திருக்கணும், அதனால wait target-ல fail ஆகுது. Router மட்டும் தான் மூணையும் meet பண்ணுது.

**Router எப்படி work ஆகுது, அதோட numbers எங்க இருந்து வருது.** ஒவ்வொரு problem-க்கும் முதல்ல மூணு வேகமான plain-prompt answers கிடைக்கும், parallel-ஆ, ஒவ்வொண்ணும் 100-க்கு ₹20: மொத்தம் 100-க்கு ₹60. மூணும் ஒத்துப்போனா, அந்த answer use ஆகும். இல்லைன்னா, problem medium effort-ல reasoning model-க்கு போகும்.

- Test set-ல, 200-ல 140 problems-ல (70%) மூணும் ஒத்துப்போச்சு. அதுல 136-ல ஒத்துப்போன answer சரி, அதாவது 97%. 100% இல்ல: ஒரு model-க்கு ஒரு blind spot இருந்தா, ஒவ்வொரு தடவையும் அதே sign error மாதிரி, மூணு samples-உம் அதே தப்பான answer-ல ஒத்துப்போகும். ஒத்துப்போறது evidence, proof இல்ல.
- மீதி 60 problems (30%) reasoning model-க்கு போச்சு, அது 45-ஐ சரியா பண்ணுச்சு, அதாவது 75%. அதோட overall 90%-ஐ விட இது ரொம்ப கம்மி, ஏன்னா இவை தான் கஷ்டமான problems.
- Accuracy: 136 + 45 = 200-ல 181, அதாவது 90.5%.
- Cost: samples-க்கு ₹60, கூட 30% problems × ₹120 = escalations-க்கு ₹36, அதனால 100-க்கு ₹96.
- காத்திருப்பு: ஒத்துப்போற 70%-க்கு 3 வினாடி, escalate ஆகுற 30%-க்கு 3 + 20 = 23 வினாடி. Reasoning model மட்டும் use பண்றதை விட, எல்லாரையும் விட அதிக நேரம் காத்திருக்குற students 3 வினாடி அதிகமா காத்திருக்காங்க, 95th-percentile காத்திருப்பை slow path தான் set பண்ணுது.

முதல் stage-ல ஏன் plain answers? மூணு step-by-step answers-க்கு 100-க்கு ₹165 ஆகும், reasoning model மட்டும் use பண்றதை விட அதிகம். முதல் stage difficulty-க்கான ஒரு மலிவான test-ஆ இருந்தா போதும்.

**முடிவு.** அவங்க router-ஐ தேர்ந்தெடுத்தாங்க: noise-க்குள்ள reasoning model-ஓட அதே quality, 20% மலிவு, 10-ல 7 students-க்கு 20 வினாடிக்கு பதிலா 3 வினாடியில result. Escalate ஆன problems-க்கு app ஒரு progress bar-ஓட "Checking your working carefully…" காட்டுது, ஏன்னா ஏதோ நடக்குதுன்னு பாக்க முடிஞ்சா students ஒரு சின்ன காத்திருப்பை ஏத்துக்குவாங்க. ராத்திரி முழுக்க check ஆகுற homework ஒரு batch API வழியா போகுது; November 2026 நிலவரப்படி, OpenAI-உம் Anthropic-உம் அதுக்கு normal rate-ல பாதி விலை வைக்குறாங்க.

Escalate ஆன ஒவ்வொரு problem-ஐயும் ஒரு புது test case-ஆ log பண்றாங்க, புது problems-ல 97% figure-ஐ மாசா மாசம் re-check பண்றாங்க: அந்த number எவ்வளவு நல்லதோ, router-உம் அவ்வளவு தான் நல்லது.

## பொதுவா பண்ற தப்புகள்

- **எல்லாத்துக்கும் reasoning model use பண்றது.** Greetings, lookups, formatting-க்கு அது தேவையில்ல. எதையும் சேர்க்காத thinking-க்கு பணம் கட்டுறீங்க.
- **மலிவான step-ஐ skip பண்றது.** தானா reason பண்ணாத ஒரு model-ல, ஒரு step-by-step prompt அடிக்கடி gap-ல பெரும்பகுதியை cost-ஓட ஒரு சின்ன பங்குலயே மூடிடும்.
- **Reasoning model-க்கு step-by-step prompts சேர்க்குறது.** அது ஏற்கனவே யோசிக்குது. அதுக்கு பதிலா effort level-ஐ set பண்ணுங்க.
- **Thinking-க்கு இடமே இல்லாத output limit.** Thinking அதுல கணக்காகும், அதனால answers பாதியில வெட்டுப்படும்.
- **Free-form text மேல vote பண்றது.** ரெண்டு நல்ல paragraphs எப்பவுமே ஒரே மாதிரி இருக்காது, அதனால vote-க்கு எதுவும் கிடைக்காது. அதுக்கு பதிலா ஒரு verifier அல்லது judge use பண்ணுங்க.
- **ஒத்துப்போறதை உண்மையா எடுத்துக்கிறது.** ஒரே model-ஓட samples-க்கு அதோட blind spots எல்லாம் இருக்கும். Unanimous answers எவ்வளவு அடிக்கடி சரியா இருக்குன்னு அளங்க.
- **ஒரு weak verifier-ஐ நம்புறது.** Checker-ஐ ஏமாத்துறது ஈஸின்னா, best-of-N அதை எல்லாத்தையும் விட நல்லா ஏமாத்துற answer-ஐ எடுக்கும்.
- **Raw reasoning-ஐ நம்புறது அல்லது காட்டுறது.** Answer-ஐ உண்மையா drive பண்ணினதை அது விட்டுடலாம், அதுல தப்பான திருப்பங்களும் இருக்கும். Results-ஐ check பண்ணுங்க, users-க்கு answer-ஐ ஒரு சின்ன, check பண்ணின explanation-ஓட காட்டுங்க.

## அதிக thinking தப்பான tool-ஆ இருக்கும் நேரங்கள்

- **Model-கிட்ட facts இல்ல.** நீண்ட நேரம் யோசிச்சா knowledge சேராது. Retrieval use பண்ணுங்க.
- **Task simple அல்லது creative.** சின்ன replies, summaries, tone மாத்துறது அரிதா தான் improve ஆகும்.
- **ஒரு சின்ன gain-ஐ விட latency முக்கியம்.** ஒரு voice agent அல்லது autocomplete பத்து வினாடி காத்திருக்க முடியாது.
- **Gain-ஐ அளக்க முடியாது.** Test set இல்லாம, அதிகம் செலவு பண்ணுவீங்க, அது உதவுச்சான்னு தெரியாது.

## Demo-ல இருந்து production-க்கு

- **Difficulty-ஐ பொறுத்து route பண்ணுங்க.** ஈஸியான questions-ஐ fast path-ல அனுப்புங்க, ஒரு check fail ஆனா அல்லது samples ஒத்துப்போகலைன்னா மட்டும் escalate பண்ணுங்க.
- **செலவுக்கு cap வைங்க.** Effort-ஐ explicit-ஆ set பண்ணுங்க, thinking-க்கு இடம் இருக்குற மாதிரி ஒரு output limit set பண்ணுங்க, ஒவ்வொரு request-க்கும் thinking tokens-ஐயும் cost-ஐயும் track பண்ணுங்க.
- **Progress காட்டுங்க**, முக்கியமா thinking மறைஞ்சிருக்கும்போது.
- **Effort sweep-ஐ மறுபடி ஓட்டுங்க**, model-ஐயோ அதோட version-ஐயோ மாத்தும்போது, ஏன்னா அதே level வேற மாதிரி behave பண்ணலாம்.

## Practice பண்ணுங்க

1. Answers தெரிஞ்ச பத்து maths அல்லது logic questions எடுங்க. எந்த chat model-லயும், ஒரு plain prompt-ஐ, அப்புறம் ஒரு step-by-step prompt-ஐ score பண்ணுங்க.
2. அது தப்பா பண்ணின questions-க்கு, ஒவ்வொண்ணுக்கும் அஞ்சு answers sample பண்ணி majority-ஐ எடுங்க. Vote எத்தனையை சரி பண்ணுச்சு? ஏதாவது unanimous-ஆ இருந்தும் தப்பா இருந்துச்சா?
3. ஒரு reasoning model-க்கு API access இருந்தா, அதே பத்து questions-ஐ ரெண்டு effort levels-ல ஓட்டுங்க. Usage data-ல இருந்து thinking tokens-ஐ log பண்ணி, ஒரு question-க்கு cost-ஐ கணக்கு பண்ணுங்க.
4. ஒவ்வொரு method-க்கும் accuracy, cost, காத்திருப்பை எழுதுங்க, ஒரு student app-க்கு எதை ship பண்ணுவீங்கன்னு முடிவு பண்ணுங்க.
