## இது என்ன

ஒரு RAG system பல sources-ல இருந்து text-ஐ ஒரே index-க்கு copy பண்ணும். அந்த sources-க்கு access rules இருந்துச்சு: HR-க்கு மட்டும் திறந்திருக்குற ஒரு SharePoint site, ஒரு project team-ஓட பகிரப்பட்ட ஒரு drive, ஒரு customer-ஓட account manager-க்கு மட்டும் தெரியுற ஒரு ticket. நீங்க செய்யலன்னா, index அந்த rules-ஐ வச்சுக்காது.

**Permission-aware RAG** (security trimming அல்லது document-level access control-ன்னும் சொல்வாங்க), கேக்குற user-க்கு original system-ல பார்க்க அனுமதி இருக்குற passages-ஐ மட்டுமே retrieval எப்பவும் திருப்பி தருதுன்னு உறுதி பண்ணும். User SharePoint-ல document-ஐ திறக்க முடியலன்னா, assistant அதை quote பண்ண முடியாது.

```flow
title: Ingestion
SharePoint file + அதோட permissions -> Chunk text + allowed_groups, allowed_users | இல்லையா? யாருக்கும் தெரியாது
SharePoint file + அதோட permissions -[ஒவ்வொரு 10 நிமிஷத்துக்கும் மறுபடி sync]-> Chunk text + allowed_groups, allowed_users
```

```flow
title: Query
User sign in பண்றாங்க -> Verified token | user, groups
Verified token -> ஒரு filter-ஓட Search | allowed_groups user-ஓட ஒரு group-ஐ பகிருது, search-க்குள்ளயே, ranking-க்கு முன்னாடி
ஒரு filter-ஓட Search -> அனுமதிக்கப்பட்ட chunks மட்டுமே model-க்கு போகும்
```

இந்த lesson Mumbai-ல ஒரு asset management company-ஓட assistant-ஐ follow பண்ணுது; research notes, HR policies, board papers, client agreements மேல அது வேலை செய்யுது.

## இது எப்படி work ஆகுது

**Ingestion-ல rights-ஐ capture பண்ணுங்க.** ஒரு document-ஐ index பண்ணும்போது, அதை யார் படிக்கலாம்னும் எடுங்க: source system-ஓட permissions-ல இருந்து users, groups. அவற்றை ஒவ்வொரு chunk-லயும் metadata-ஆ சேமிங்க, உதாரணம் `allowed_groups: ["hr-core", "leadership"]`, `allowed_users: [...]`.

**Search-க்குள்ளயே filter பண்ணுங்க.** Query நேரத்துல, user-ஓட verified sign-on token-ல இருந்து அவங்க identity-யையும் groups-ஐயும் எடுத்து, ஒரு filter சேருங்க: `allowed_groups` user-ஓட groups-ஓட overlap ஆகுற chunks மட்டும், அல்லது `allowed_users`-ல அவங்க இருக்குறவை. இந்த filter vector அல்லது keyword search-க்குள்ளயே, ranking-க்கு முன்னாடி run ஆகணும்; அப்போ restricted chunks candidate list-க்கு வரவே வராது. Retrieval-க்கு பிறகு filter பண்றது scores, counts, timing வழியா leak ஆகும், user-க்கு results எதுவுமே இல்லாம கூட போகலாம்.

**Deny by default.** Permission data இல்லாத ஒரு chunk, சரி பண்ற வரைக்கும் யாருக்குமே தெரியாது. "Rule இல்ல"ன்றதை ஒருபோதும் "public"ன்னு எடுத்துக்காதீங்க.

**Rights-ஐ sync-ல வச்சிருங்க.** Permissions தினமும் மாறும்: மக்கள் teams-ல சேருவாங்க, files share ஆகும், sites lock ஆகும். Content-ல இருந்து தனியா, ஒரு schedule-ல அல்லது change events-ல இருந்து rights-ஐ மறுபடி sync பண்ணுங்க. Lag-ஐ measure பண்ணி, client-ஓட agree பண்ணுங்க ("permission மாற்றங்கள் 15 நிமிஷத்துக்குள்ள அமலுக்கு வரும்").

**Groups பெருசா ஆகும்.** Users நூற்றுக்கணக்கான groups-ல இருக்கலாம், ஒண்ணுக்குள்ள ஒண்ணா nested ஆகவும். Nested groups-ஐ sign-in அல்லது index நேரத்துல resolve பண்ணி, புத்திசாலித்தனமா cache பண்ணுங்க.

**மாற்று: source-ல check பண்றது.** சின்ன result sets-க்கு, candidates-ஐ retrieve பண்ணி, ஒவ்வொரு document-ஐயும் user-ஆல திறக்க முடியுமான்னு source system-கிட்ட user-ஆ கேக்கலாம். இது எப்பவும் புதுசா இருக்கும் ஆனா மெதுவு, இதுவும் எதுவும் model-க்கு போறதுக்கு முன்னாடி நடக்கணும்.

**Test பண்ணுங்க.** வெவ்வேற roles இருக்குற test users-ஐயும் "பாக்கக்கூடாத" கேள்விகளோட ஒரு set-ஐயும் build பண்ணி, CI-ல run பண்ணுங்க.

**Access-ஐ எங்க enforce பண்றது:**

| Approach | எப்படி வேலை செய்யும் | பலம் | பலவீனம் |
| --- | --- | --- | --- |
| Index-ல filter | Permissions chunks-ல சேமிக்கப்படும்; search-ல filter | வேகம், scale ஆகும் | Permission sync வேணும்; சின்ன lag |
| Source-ல check | ஒவ்வொரு candidate-க்கும் source system-கிட்ட கேக்கும் | எப்பவும் சமீபத்தியது | மெதுவு; அதிக calls |
| Group வாரியா தனி indexes | ஒவ்வொரு audience-க்கும் ஒரு index | சில groups-க்கு எளிது | நிறைய groups-ல உடைஞ்சுடும் |
| Retrieval-க்கு பிறகு filter | கடைசியில restricted results-ஐ நீக்குறது | பயனுள்ளது எதுவுமில்ல | Leaks, காலியான results |

**CI-ல persona tests.** ஒவ்வொரு role-க்கும் test users-ஐ உருவாக்குங்க, உதாரணம் analyst, HR staff, director, contractor, தெரிஞ்ச group memberships-ஓட. ஒவ்வொருத்தருக்கும், அவங்க பாக்க வேண்டிய documents, ஒருபோதும் பாக்கக்கூடாத documents-ஓட கேள்விகளை எழுதுங்க. Model-ஓட answer மேல இல்ல, retrieve ஆன chunk ids மேல assert பண்ணுங்க; ஏன்னா ஆபத்து, ஒரு restricted chunk prompt-க்குள்ள வர்றதே. Ingestion, search, permission sync-ல ஒவ்வொரு மாற்றத்துக்கும் இந்த tests-ஐ run பண்ணுங்க.

**Sync window-ஐ agree பண்றது.** Permission மாற்றங்கள் ஒரு index-ல உடனே அமலுக்கு வர முடியாது. உண்மையான lag-ஐ measure பண்ணி, client-ஓட security team-ஓட எழுத்துல agree பண்ணி, ஒரு sync fail ஆனாலோ தாமதமானாலோ alert பண்ணுங்க. மிக sensitive sources-க்கு, board papers மாதிரி, ரெண்டாவது layer-ஆ source-ல check பண்றதை யோசிங்க.

**Schema-ல deny by default.** Access data இல்லாம ஒரு chunk-ஐ index பண்றதையே முடியாததா ஆக்குங்க:

```sql
CREATE TABLE chunks (
  id text PRIMARY KEY,
  doc_id text NOT NULL,
  body text NOT NULL,
  embedding vector(384) NOT NULL,
  allowed_groups text[] NOT NULL CHECK (cardinality(allowed_groups) > 0)
);
CREATE INDEX ON chunks USING gin (allowed_groups);

-- The search, with the user's groups from the verified token as $2:
SELECT id, body FROM chunks
WHERE allowed_groups && $2
ORDER BY embedding <=> $1
LIMIT 20;
```

`&&`-னா "ரெண்டு arrays-உம் குறைஞ்சது ஒரு value-ஐ பகிருது". Groups இல்லாத ஒரு chunk-ஐ insert பண்ணவே முடியாது.

**Row-level security-ஓட ரெண்டாவது பூட்டு.** Application, database session-ல user-ஓட groups-ஐ set பண்ணா, யாராவது `WHERE`-ஐ மறந்தாலும் Postgres அதே rule-ஐ enforce பண்ணும்:

```sql
ALTER TABLE chunks ENABLE ROW LEVEL SECURITY;
CREATE POLICY read_by_group ON chunks FOR SELECT
  USING (allowed_groups && string_to_array(current_setting('app.user_groups', true), ','));
-- per request, inside a transaction:
-- SELECT set_config('app.user_groups', 'hr-core,all-staff', true);
```

Table-ஐ சொந்தமா வச்சிருக்காத ஒரு role-ஆ connect பண்ணுங்க; ஏன்னா நீங்க `ALTER TABLE chunks FORCE ROW LEVEL SECURITY`-ஐயும் run பண்ணாதவரை table owners policies-ஐ தாண்டிடுவாங்க.

**Nested groups-ஐ flatten பண்ணுங்க.** Directories groups-க்குள்ள groups-ஐ வைக்கும். ஒரு தடவை resolve பண்ணுங்க, cycles-க்கு எதிரா ஒரு guard-ஓட:

```python
def expand_groups(user_groups, parents_of):
    """parents_of: dict mapping a group to the groups that contain it."""
    seen, stack = set(), list(user_groups)
    while stack:
        g = stack.pop()
        if g in seen:
            continue
        seen.add(g)
        stack.extend(parents_of.get(g, []))
    return sorted(seen)
```

Session முழுக்க result-ஐ cache பண்ணி, user மறுபடி sign in பண்றப்போ அல்லது directory மாறும்போது refresh பண்ணுங்க.

**Answers-ஐ இல்ல, ids-ஐ check பண்ற persona tests.**

```python
import pytest

PERSONAS = {
    "analyst":    {"groups": ["all-staff"],             "never": {"board-2026-q3-c1", "salaries-c4"}},
    "hr_staff":   {"groups": ["all-staff", "hr-core"],  "never": {"board-2026-q3-c1"}},
    "contractor": {"groups": ["contractors"],           "never": {"handbook-c2", "salaries-c4"}},
}
QUESTIONS = ["What did the board decide about the Pune office?", "What is the salary band for level 5?",
             "What is the leave policy?"]

@pytest.mark.parametrize("persona", PERSONAS)
def test_never_retrieves_restricted(persona, search):
    p = PERSONAS[persona]
    for q in QUESTIONS:
        ids = {c["id"] for c in search(q, groups=p["groups"])}
        assert not ids & p["never"], f"{persona} retrieved {ids & p['never']} for: {q}"
```

தடை செய்யப்பட்ட ஒரு chunk retrieve ஆனாலே test fail ஆகும்; ஒரு model அதை திருப்பி சொல்றதுக்கு ரொம்ப முன்னாடியே.

**Caches, summaries, memories-உம் leak ஆகும்.** Restricted documents-ல இருந்து உருவான ஒரு cached answer, சேமிச்ச conversation summary, அல்லது agent memory, அதே access rules-ஐ கொண்டிருக்கணும், அல்லது user வாரியா key பண்ணப்படணும். Retrieval-க்கு பிறகு retrieve ஆன text சேமிக்கப்படுற ஒவ்வொரு இடத்தையும் check பண்ணுங்க.

## ஒரு worked example

Mumbai-ல ஒரு asset management company, research notes, HR policies, board papers, client agreements மேல ஒரே assistant வேணும்னு விரும்புது.

Ingestion-ல, ஒரு connector ஒவ்வொரு SharePoint file-ஐயும் அதோட permissions-ஐயும் படிச்சு, groups-ஐ expand பண்ணி, ஒவ்வொரு chunk-லயும் `allowed_groups`-ஐ சேமிக்குது. Query நேரத்துல, API user-ஓட groups-ஐ அவங்க OIDC token-ல இருந்து படிச்சு, filter-ஐ hybrid search-ல சேர்க்குது.

அஞ்சு personas-ஓட testing:

- ஒரு analyst "கடைசி board meeting-ல merger பத்தி என்ன பேசினாங்க?"ன்னு கேக்குறாங்க. Board-paper chunks ஒண்ணுமே retrieve ஆகல; அந்த topic-ல access இருக்குற documents எதுவும் கிடைக்கலன்னு assistant சொல்லுது.
- ஒரு director அதே கேள்வியை கேக்குறாங்க, board minutes-ஐ cite பண்ற ஒரு answer கிடைக்குது.
- ஒரு analyst "senior managers-க்கு notice period என்ன?"ன்னு கேக்குறாங்க. எல்லா employees-க்கும் திறந்திருக்குற HR policy retrieve ஆகுது; confidential salary bands file ஆகல.

Pilot-ஓட போது, HR team ஒரு draft policy-ஐ restrict பண்ணுது. Permission sync ஒவ்வொரு பத்து நிமிஷத்துக்கும் run ஆகுது; அதனால பத்து நிமிஷம் வரைக்கும் பழைய rights அமல்ல இருக்கும். Client-ஓட security team இந்த window-ஐ எழுத்துல ஏத்துக்கிட்டு, ஒரு sync fail ஆனா alert வேணும்னு கேக்குது.

## பொதுவா பண்ற தப்புகள்

- **Retrieval-க்கு பிறகு filter பண்றது.** Restricted chunks results-ஐ பாதிக்கும், leak ஆகலாம். Search-க்குள்ளயே filter பண்ணுங்க.
- **Missing permissions-ஐ public-ன்னு எடுத்துக்கிறது.** Deny by default.
- **Content-ஐ sync பண்ணி rights-ஐ பண்ணாம விடுறது.** இன்னைக்கு lock பண்ண ஒரு document, index-ல இன்னும் தெரியும்.
- **Request body-ல இருந்து identity-ஐ நம்புறது.** User-ஐயும் groups-ஐயும் verified token-ல இருந்து மட்டும் எடுங்க.
- **Negative tests இல்லாம இருக்குறது.** ஒவ்வொரு persona-வும் பாக்க வேண்டியதை மட்டும் இல்ல, பாக்கக்கூடாததையும் test பண்ணுங்க.
- **Restricted documents-ல இருந்து உருவான answers-ஐ users இடையில cache பண்றது.**
- **Permission tests-ல model-ஓட answer-ஐ assert பண்றது, retrieve ஆன ids-ஐ இல்ல.**
- **Nested groups expand ஆகாம இருக்குறது**, அதனால users பாக்க வேண்டிய documents-ஐ தவறவிடுறாங்க, அல்லது tests தப்பான காரணத்துக்காக pass ஆகுது.

## எப்போ permission-aware retrieval தேவையில்ல

- **எல்லாரும் எல்லாத்தையும் படிக்கலாம்**, public policies அல்லது வெளியிடப்பட்ட handbook மாதிரி.
- **ஒரே user-ஓட சொந்த documents**, அங்க index எப்படியும் user வாரியா தான்.
- **சில தெளிவான audiences**, அங்க ஒவ்வொரு audience-க்கும் தனி indexes எளிது.

## Demo-ல இருந்து production-க்கு

- **Access-ஐ query-லயும் database-லயும் enforce பண்ணுங்க**, deny by default.
- **Ingestion, search, sync-ல ஒவ்வொரு மாற்றத்துக்கும் CI-ல persona tests-ஐ run பண்ணுங்க.**
- **Agree பண்ண window-ஓட ஒப்பிட்டு permission sync lag-ஐ measure பண்ணி, alert பண்ணுங்க.**
- **Caches, summaries, memories-ஐ user அல்லது access group வாரியா scope பண்ணுங்க.**
- **ஒவ்வொரு search-க்கும் use பண்ண groups-ஐ log பண்ணுங்க**, audits-க்காக.

## Practice பண்ணுங்க

Microsoft-ஓட security filter pattern-ஐயும், access control-ஓட RAG பத்தின Pinecone-ஓட கட்டுரையையும் படிங்க.

1. உங்க RAG index-ல ஒவ்வொரு chunk-லயும் ஒரு `allowed_groups` field-ஐ சேருங்க; உங்க documents முழுக்க குறைஞ்சது மூணு groups இருக்கட்டும்.
2. User-ஓட groups-ஐ ஒரு (real அல்லது simulated) verified token-ல இருந்து படிச்சு, search-க்குள்ளயே filter பண்ணுங்க.
3. மூணு personas-க்கு ஐந்து "பாக்கக்கூடாது" tests எழுதி, உங்க test suite-ல run பண்ணுங்க.
4. Row-level security policy-ஐ சேர்த்து, வேணும்னே உங்க search-ல இருந்து WHERE clause-ஐ நீக்கி, restricted chunks இன்னும் வரலன்னு உறுதிபண்ணுங்க.
