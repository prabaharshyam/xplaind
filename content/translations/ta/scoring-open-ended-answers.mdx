## இது என்ன

Calculator-ஐ test பண்றது எளிது: 2 + 2 எப்பவும் 4. Emails, summaries, explanations எழுதுற ஒரு AI-ஐ test பண்றது கஷ்டம், ஏன்னா நிறைய நல்ல answers இருக்கும். இந்த lesson, அப்படிப்பட்ட answers-க்கு number போடுற முக்கிய வழிகளையும், ஒவ்வொண்ணும் எப்போ பொருந்தும்னும் சொல்லுது.

நாலு குடும்பங்கள் இருக்கு, அதிக exact-ல இருந்து குறைவான exact வரை:

1. **Functional correctness.** Output வேலை செய்யுதா? Generate பண்ணின code அதோட tests-ல pass ஆகுது, generate பண்ணின SQL query சரியான rows தருது, extract பண்ணின invoice total ledger-ஓட ஒத்துப்போகுது.
2. **Exact match.** Answer reference-ஓட அப்படியே ஒண்ணா இருக்கா? Numbers, dates, labels, multiple-choice letters-க்கு நல்லது.
3. **Reference-ஓட similarity.** Answer ஒரு நல்ல answer-க்கு எவ்வளவு கிட்ட இருக்கு, **வார்த்தைகள்ல** (lexical similarity, BLEU, ROUGE மாதிரி) அல்லது **அர்த்தத்துல** (semantic similarity, embeddings use பண்ணி)?
4. **Judgement.** ஒரு நபர் அல்லது ஒரு judge model answer-க்கு rating தருவாங்க, தனியா (5-ல ஒரு score) அல்லது இன்னொரு answer-ஓட (**pairwise comparison**). LLM judges lesson-ல judge prompts ஆழமா இருக்கு.

## இது எப்படி work ஆகுது

**Functional correctness.** Execute பண்ணவோ test பண்ணவோ முடிஞ்சா, அதைத்தான் முதல்ல பண்ணுங்க. ஒரு code assistant-க்கு unit tests run பண்ணி score போடுவாங்க. Text-to-SQL feature, generate பண்ணின query-ஐயும் reference query-ஐயும் ஒரு test database-ல run பண்ணி results-ஐ ஒப்பிடும். Extraction feature, fields-ஐ system of record-ஓட check பண்ணும். வேற எதுவும் இவ்வளவு நம்பகமில்ல. ஒரு coding benchmark-ல, சரியான, தப்பான solutions-க்கு word-overlap scores கிட்டத்தட்ட ஒரே மாதிரி இருந்துச்சுன்னு OpenAI கண்டுபிடிச்சது; code-ஐ run பண்ணா மட்டும் தான் வித்தியாசம் தெரிஞ்சுது.

**Exact match**, கவனமா. முதல்ல normalise பண்ணுங்க: lowercase, spaces trim, number formats ஒரே மாதிரி. சரியான value தப்பான answer-க்குள்ள இருக்குற பிரச்சனையை கவனிங்க: "Born on 12 September 1929" அதுல "1929" இருக்கு, ஆனா உண்மையான date 12 June-னா அது தப்பு. Labels-க்கு, முழு வாக்கியத்தை இல்ல, label field-ஐ மட்டும் ஒப்பிடுங்க.

**Lexical similarity.** ரெண்டு texts-ஐயும் வார்த்தைகள் அல்லது வார்த்தை ஜோடிகளா பிரிச்சு, எத்தனை ஒத்துப்போகுதுன்னு எண்ணுவாங்க. BLEU (machine translation-ல இருந்து), ROUGE (summarisation-ல இருந்து) தான் மிகவும் பிரபலமானவை. தொடர்புடைய ஒரு idea, **edit distance**, ஒரு string-ஐ இன்னொண்ணா மாத்த எத்தனை எழுத்து மாற்றங்கள் வேணும்னு எண்ணும்; பேர்கள், codes-க்கு பயனுள்ளது.

இவங்களோட பலவீனங்கள் இன்றைய models-க்கு தீவிரமானவை:

- வேற வார்த்தைகள்ல சொன்ன சரியான answer-க்கு குறைவான score. "How is it going?"-க்கும் "How are you?"-க்கும் கிட்டத்தட்ட வார்த்தைகள் பொதுவா இல்ல.
- Reference-ஓட வார்த்தைகளை copy பண்ணின தப்பான answer-க்கு அதிக score. "Let's eat, grandma"-உம் "Let's eat grandma"-உம் வார்த்தைகள் அடிப்படையில் கிட்டத்தட்ட ஒண்ணு.
- References-ல நல்ல answers விடுபட்டிருக்கலாம், இல்ல அவையே தப்பா இருக்கலாம்.

மலிவான smoke alarms-ஆ இவை இன்னும் உதவும், உதாரணம்: ஒரு template மாற்றம் எல்லா replies-ஐயும் உடைச்சுதுன்னு கவனிக்க.

**Semantic similarity.** Answer-ஐயும் reference-ஐயும் embeddings-ஆ மாத்தி, -1 முதல் 1 வரை cosine similarity-ஓட ஒப்பிடுங்க. Paraphrases அதிக score வாங்கும். பெரிய அளவுல மலிவு, ஆனா score embedding model-ஐ சார்ந்தது, "refund approved"-ஐயும் "refund rejected"-ஐயும் கிட்டன்னு rate பண்ணலாம், சரியான threshold-ஐ மக்களோட judgements-ஓட check பண்ணி தான் வைக்கணும்.

```python
import numpy as np

def cosine(a, b):
    a, b = np.asarray(a), np.asarray(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

def score(answer, reference, embed, must_include=()):
    """embed(text) returns a vector. must_include holds facts that need an exact check."""
    facts_ok = all(f.lower() in answer.lower() for f in must_include)
    return {"facts_ok": facts_ok, "meaning": round(cosine(embed(answer), embed(reference)), 3)}

# score(draft, agent_reply, embed, must_include=["ORD-48213", "₹2,499"])
```

Pattern-ஐ கவனிங்க: சரியா இருக்கணும்னு வேண்டிய facts-க்கு exact checks, wording-க்கு similarity.

**Pairwise comparison.** ரெண்டு பாடல்கள்ல எது பிடிக்கும்னு சொல்றது, ஒவ்வொண்ணுக்கும் 10-ல score தர்றதை விட எளிது. Answers-க்கும் இதே தான். ஒரே கேள்விக்கு ரெண்டு answers-ஐ random order-ல, labels இல்லாம காட்டி, எது நல்லதுன்னு கேளுங்க, tie-ஐயும் அனுமதிங்க. Wins-ஐ எண்ணுங்க. நிறைய models இருந்தா, Elo அல்லது Bradley–Terry மாதிரி ranking methods wins-ஐ ஒரு league table-ஆ மாத்தும்; public arenas மில்லியன் கணக்கான votes-ல இருந்து chatbots-ஐ இப்படித்தான் rank பண்றாங்க.

ரெண்டு limits முக்கியம்:

- **Preference என்பது correctness இல்ல.** Voter-க்கு சரியான answer தெரியலன்னா, maths result அல்லது medical fact மாதிரி, நம்பிக்கையா சொல்ற தப்பான answer-ஐ அவங்க விரும்பலாம். Style, helpfulness-க்கு vote பண்ணுங்க; facts-ஐ தனியா check பண்ணுங்க.
- **நிறைய comparisons வேணும்**, models சேர்க்க சேர்க்க pairs எண்ணிக்கை வேகமா வளரும். ரெண்டு prompts அல்லது ரெண்டு models-ல ஒரு product முடிவுக்கு, உங்க சொந்த கேள்விகள்ல 100 முதல் 300 side-by-side comparisons பொதுவா போதும்.

| --- | --- | --- | --- |
| Functional check | Code, SQL, extraction, formats | Build பண்ணின பிறகு குறைவு | Cases-ஐ தவறவிடுற tests |
| Exact match | Numbers, labels, குறுகிய facts | ரொம்ப குறைவு | தப்பான answer-க்குள்ள சரியான value |
| Lexical (BLEU, ROUGE) | Smoke tests, translation drift | ரொம்ப குறைவு | அர்த்தத்தை இல்ல, வார்த்தை copy பண்றதை பாராட்டும் |
| Semantic similarity | Reference இருக்குற paraphrased answers | குறைவு | எதிர்மாறான facts-க்கும் கிட்டத்துல score வரும் |
| Rubric-ஓட judge | Reference இல்லாத open text | நடுத்தரம் | Judge bias; மக்களோட check பண்ணுங்க |
| Pairwise comparison | ரெண்டு systems-ல தேர்ந்தெடுக்க | நடுத்தரம் முதல் அதிகம் | Preference-ஐ correctness-ஆ நினைக்குறது |

## ஒரு worked example

Delhi-ல ஒரு electronics retailer-க்கு, customer emails-க்கு Hindi, English-ல replies draft பண்ற assistant இருக்கு. ஒவ்வொரு reply-உம் சரியான order number, refund amount-ஐ சொல்லி, நாகரிகமா முடிக்கணும். Team, 300 பழைய emails-உம் அவங்க best agents-ஓட replies-உம் வச்சு prompt A (இப்போ இருக்கிறது)-ஐ prompt B (புதுசு)-ஓட ஒப்பிட விரும்புறாங்க.

முதல்ல agents-ஓட replies-க்கு எதிரா ROUGE try பண்றாங்க. Prompt A 0.41, prompt B 0.33 வாங்குது, B மோசம்னு தோணுது. Drafts-ஐ படிச்சு பார்த்தா வேற கதை: B குறுகிய, தெளிவான Hindi எழுதுது, அது agents-ஓட நீளமான replies-ஓட குறைவான வார்த்தைகளை பகிர்ந்துக்குது.

அதனால மூணு layers-ல score போடுறாங்க:

| Layer | Prompt A | Prompt B |
| --- | --- | --- |
| Order number, refund amount சரி (order system-ஓட exact check) | 94% | 97% |
| Agent-ஓட reply-க்கு கிட்டத்துல அர்த்தம் (cosine 0.80-க்கு மேல) | 88% | 90% |
| ரெண்டு senior agents judge பண்ணின side-by-side wins, 150 emails, ties அனுமதி | 38% | 51% (11% ties) |
| Agent-ஓட reply-க்கு எதிரா ROUGE-L | 0.41 | 0.33 |

Numbers உதாரணத்துக்கு மட்டும். B facts-லயும் preference-லயும் ஜெயிக்குது, word overlap-ல மட்டும் தோக்குது; அதை dashboard-ல இருந்து எடுத்துடுறாங்க. ஒவ்வொரு release-லயும் exact checks-ஐ ஓட விடுறாங்க.

## பொதுவா பண்ற தப்புகள்

- **Chat, summaries, explanations-க்கு BLEU அல்லது ROUGE-ஐ முக்கிய quality score-ஆ use பண்றது.**
- **Similarity score-ஐ facts check பண்ண விடுறது.** "Approved"-உம் "rejected"-உம் கிட்டத்துல தெரியலாம். முக்கிய facts-ஐ exact-ஆ check பண்ணுங்க.
- **சரியான answers இருக்குற கேள்விகளுக்கு vote பண்றது.** Preference மக்கள் எதை விரும்புறாங்கன்னு கண்டுபிடிக்கும், எது உண்மைன்னு இல்ல.
- **Answers-ஐ ஒரே order-ல காட்டுறது.** மக்களும் judges-உம் முதல் answer-ஐயோ நீளமான answer-ஐயோ விரும்புவாங்க. Order-ஐ randomise பண்ணுங்க, ஒரே மாதிரி நீளம் உள்ளவற்றை ஒப்பிடுங்க.
- **யாருமே check பண்ணாத threshold-ஐ நம்புறது.** Similarity thresholds-ஐ ஒரு sample-ல மனித judgements-ஓட ஒப்பிட்டு தேர்ந்தெடுங்க.
- **எல்லாத்துக்கும் ஒரே number.** பெரும்பாலான products-க்கு சில scores வேணும்: facts, format, meaning, preference.

## எளிமையா வைக்க வேண்டிய இடங்கள்

- **Closed tasks:** classification, extraction, routing-க்கு exact checks-உம் precision, recall-உம் போதும். Similarity அல்லது judges தேவையில்ல.
- **ஆரம்ப prototypes:** எந்த metric-ஐயும் build பண்றதுக்கு முன்னாடி 30 answers-ஐ நீங்களே படிங்க.
- **அரிதான high-stakes answers:** legal அல்லது medical outputs-க்கு, scores எப்படி இருந்தாலும், நிபுணர் review வேணும்.

## Demo-ல இருந்து production வரை

- **Scores-ஐ layer பண்ணுங்க:** ஒவ்வொரு response-லயும் exact checks, ஒரு sample-ல judge அல்லது similarity, releases-க்கு side-by-side comparison.
- **References-ஐ test set-ஓட சேர்த்து version பண்ணுங்க**, தப்பானவை கண்டா சரிபண்ணுங்க.
- **Metrics-ஐ மக்களோட ஒப்பிட்டு மறுபடியும் check பண்ணுங்க**, சில மாசத்துக்கு ஒரு தடவை; ஏன்னா மனித judgement-ல இருந்து விலகிப்போற ஒரு metric, metric இல்லாததை விட மோசம்.
- **Segment வாரியா scores report பண்ணுங்க:** language, topic, length. ஒட்டுமொத்த முன்னேற்றம், Hindi replies-ல வந்த சரிவை மறைச்சுடலாம்.

## Practice பண்ணுங்க

1. Reference answers இருக்குற எந்த AI feature-ல இருந்தும் பத்து answers எடுங்க. Exact match, word overlap, உங்க சொந்த judgement மூணுலயும் score போடுங்க. மூணும் எங்க வேறுபடுது?
2. ஒவ்வொரு answer-லயும் இருக்க வேண்டிய exact facts-ஐ எழுதி, அவற்றுக்கு ஒரு check build பண்ணுங்க.
3. பத்து கேள்விகள்ல ரெண்டு prompts-ஐ random order-ல side by side ஒப்பிடுங்க. உங்க preferences word-overlap scores-ஓட ஒத்துப்போச்சா?
