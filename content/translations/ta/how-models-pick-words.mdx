## இது என்ன

Language model ஒரு முழு answer-ஐ ஒரே மூச்சுல எழுதாது. ஒரு நேரத்துல ஒரு **token** எழுதும் (token-னா ஒரு வார்த்தை அல்லது ஒரு வார்த்தையோட துண்டு). ஒவ்வொண்ணையும் தேர்ந்தெடுக்க, அது தெரிஞ்ச ஒவ்வொரு token-க்கும் ஒரு score தரும், application அந்த scores-ஐ chances-ஆ மாத்தும், ஒரு token pick ஆகும். அந்த pick text-ல சேரும், answer முடியுற வரை அடுத்த token-க்கு மொத்தமும் திரும்ப நடக்கும்.

இந்த picking step-க்கு பேரு **sampling**. அதை மாத்த model-ஐ மாத்த தேவையில்லை. API call-ல இருக்குற சில settings pick எவ்வளவு துணிச்சலா இருக்கணும்னு முடிவு பண்ணும்: **temperature**, **top-p**, **top-k**. நீங்க பண்ற கிட்டத்தட்ட ஒவ்வொரு LLM call-லயும் இந்த settings-ஐ தொடுவீங்க.

அதனால தான் ஒரே prompt ரெண்டு வேற answers தரலாம். Model ஒரே ஒரு store பண்ண reply-ஐ தேடுறதில்லை. ஒவ்வொரு step-லயும் அதுக்கு பல நியாயமான அடுத்த tokens இருக்கு, sampling அவற்றுக்குள்ள ஒண்ணை pick பண்ணும்.

```flow
dir: LR
title: ஒரு reply எழுதுற ஒரு step
Prompt, இதுவரை text -> Model ஒவ்வொரு token-க்கும் score தருது | logits
Model ஒவ்வொரு token-க்கும் score தருது -> Temperature scores-ஐ reshape பண்ணுது
Temperature scores-ஐ reshape பண்ணுது -> Chances கூடி 100 percent ஆகுது | softmax
Chances கூடி 100 percent ஆகுது -> Top-k, top-p unlikely tokens-ஐ தூக்குது
Top-k, top-p unlikely tokens-ஐ தூக்குது -> Chance-ஐ வச்சு random-ஆ ஒண்ணை pick பண்ணு
Chance-ஐ வச்சு random-ஆ ஒண்ணை pick பண்ணு -> Text-ல சேரு
Text-ல சேரு -> Prompt, இதுவரை text
```

இந்த lesson Bengaluru-ல ஒரு fintech team-ஐ follow பண்ணுது; அவங்க மூணு LLM features-ஐ சேக்குறாங்க, ஒவ்வொண்ணுக்கும் settings-ஐ தேர்ந்தெடுக்கணும்.

## இது எப்படி work ஆகுது

1. **Model சாத்தியமான ஒவ்வொரு அடுத்த token-க்கும் score தருது.** இந்த raw scores-க்கு **logits**ன்னு பேரு. பெரிய number-னா இந்த இடத்துல அந்த token பொருந்தும்னு model நினைக்குது. ஒரு vocabulary-ல பத்தாயிரக்கணக்கான tokens இருக்கு, அதனால ஒவ்வொரு step-லயும் பத்தாயிரக்கணக்கான scores இருக்கும்.
2. **Softmax scores-ஐ chances-ஆ மாத்துது.** ஒவ்வொரு score-உம் 0-க்கும் 1-க்கும் இடையில ஒரு number ஆகும், எல்லா numbers-உம் கூடினா 1 வரும். அதிகமான score இருக்குற token-க்கு அதிக chance கிடைக்கும், ஆனா எல்லாமும் இல்லை.
3. **Temperature முதல்ல scores-ஐ reshape பண்ணும்.** Softmax-க்கு முன்னாடி ஒவ்வொரு logit-ம் temperature-ஆல divide ஆகும். **Low** temperature (0.2 சொல்லலாம்) இடைவெளிகளை விரிவாக்கும், அதனால top token கிட்டத்தட்ட எல்லா chance-ஐயும் எடுக்கும். **High** temperature (1.5 சொல்லலாம்) இடைவெளிகளை சுருக்கும், அதனால rare tokens-க்கு நிஜமான chance கிடைக்கும். சரியா 1-ல எதுவும் மாறாது. 0-ல model எப்பவும் top token-ஐ எடுக்கும்; இதுக்கு **greedy** decoding-ன்னு பேரு.
4. **Top-k, top-p list-ஐ வெட்டும்.** **Top-k** சிறந்த k tokens-ஐ மட்டும் வச்சுக்கும், உதாரணமா 40. **Top-p** (nucleus sampling-ன்னும் சொல்வாங்க) chances கூடினா p ஆகுற (உதாரணமா 0.9) மிக சிறிய tokens group-ஐ வச்சுக்கும். மிஞ்சுனவற்றோட chances மறுபடி 1 ஆகுற மாதிரி scale ஆகும்.
5. **ஒரு token random-ஆ pick ஆகும், அதோட chance-க்கு ஏத்த மாதிரி.** 60% chance இருக்குற token பத்துல கிட்டத்தட்ட ஆறு தடவை pick ஆகும். அப்புறம் loop திரும்ப ஆரம்பிக்கும்.
6. **அது நிக்கும்,** model ஒரு end token எழுதும்போது, maximum length-ஐ அடையும்போது, அல்லது நீங்க தேர்ந்தெடுத்த ஒரு **stop sequence**-ஐ உருவாக்கும்போது.

**ஒவ்வொரு setting-உம் என்ன செய்யுது:**

| Setting | எதை கட்டுப்படுத்துது | குறைவான value | அதிகமான value |
| --- | --- | --- | --- |
| Temperature | Chances எவ்வளவு தட்டையா இருக்கு | அதிக steady, safest wording-ஐ repeat பண்ணும் | அதிக variety, அதிக surprise, உளறல் வர அதிக risk |
| Top-p | Likely mass-ல எவ்வளவை வச்சுக்கணும் | குறைவான options, safer | அதிக options, அதிக variety |
| Top-k | எத்தனை tokens-ஐ வச்சுக்கணும் | குறைவான options, safer | அதிக options, அதிக variety |
| Max tokens | அனுமதிக்கப்படுற நீளமான reply | மலிவு, வெட்டப்படலாம் | நீளமானது, அதிக செலவு |
| Stop sequences | Reply-ஐ முடிக்குற text | எதுவும் தேவையில்லை | கட்டுப்பாடில்லாத output-ஐ நிறுத்தி, செலவை மிச்சப்படுத்தும் |

Model ரொம்ப உறுதியா இருக்கும்போது top-k, top-p வேற வேற மாதிரி நடந்துக்கும். ஒரு token-க்கு 95% chance இருந்தா, top-p 0.9 அந்த ஒரு token-ஐ மட்டும் வச்சுக்கலாம்; ஆனா top-k 40 இன்னும் 40-ஐ வச்சுக்கும். அதனால தான் top-p model எவ்வளவு உறுதியா இருக்குன்னு ஏத்துக்கும், top-k ஏத்துக்காது.

Defaults provider, model-ஐ பொறுத்து மாறும், சில புது models இந்த settings-ல சிலதை fix பண்ணலாம் அல்லது புறக்கணிக்கலாம். நீங்க use பண்ற model-க்கு provider-ஓட documentation-ஐ check பண்ணுங்க.

## ஒரு worked example

"My favourite Indian city to visit is" prompt-ஐ எடுத்துக்கோங்க; model அஞ்சு அடுத்த tokens-க்கு இந்த scores-ஐ தருதுன்னு வச்சுக்கோங்க. கணக்கு எளிதா புரிய numbers கற்பனையானவை.

| Token | Score (logit) |
| --- | --- |
| Mumbai | 3.0 |
| Delhi | 2.5 |
| Chennai | 1.5 |
| Jaipur | 0.5 |
| Pune | -0.5 |

நாலு temperatures-ல chances இதோ:

| Temperature | Mumbai | Delhi | Chennai | Jaipur | Pune |
| --- | --- | --- | --- | --- | --- |
| 0.2 | 92.4% | 7.6% | 0.1% | 0.0% | 0.0% |
| 0.5 | 70.2% | 25.8% | 3.5% | 0.5% | 0.1% |
| 1.0 | 51.5% | 31.2% | 11.5% | 4.2% | 1.6% |
| 2.0 | 36.9% | 28.7% | 17.4% | 10.6% | 6.4% |

0.2-ல model கிட்டத்தட்ட ஒவ்வொரு தடவையும் "Mumbai"ன்னு சொல்லும். 2.0-ல பதினாறு முயற்சிக்கு ஒரு தடவை Pune-ஐ சொல்லும்.

இப்போ temperature 1.0-ல list-ஐ வெட்டுவோம். மேல இருந்து chances-ஐ கூட்டுனா: Mumbai 51.5%, அப்புறம் Delhi 82.7%, அப்புறம் Chennai 94.2%. **Top-p 0.9**-ல 90%-ஐ எட்டுற மிக சிறிய group அந்த மூணு. **Top-k 3**-ல group-உம் அதே மூணு. அவற்றோட chances மறுபடி 100% ஆகுற மாதிரி scale ஆகும்: Mumbai 54.7%, Delhi 33.1%, Chennai 12.2%. Jaipur, Pune இனி pick ஆகவே முடியாது.

இந்த கணக்கை சில வரி Python-ல check பண்ணலாம்:

```python
import numpy as np

tokens = ["Mumbai", "Delhi", "Chennai", "Jaipur", "Pune"]
logits = np.array([3.0, 2.5, 1.5, 0.5, -0.5])

def chances(logits, temperature=1.0):
    scaled = logits / temperature
    e = np.exp(scaled - scaled.max())      # subtract the max for numeric safety
    return e / e.sum()

for t in (0.2, 0.5, 1.0, 2.0):
    print(t, np.round(chances(logits, t) * 100, 1))

def top_p(probs, p=0.9):
    order = np.argsort(-probs)
    keep, total = [], 0.0
    for i in order:
        keep.append(i)
        total += probs[i]
        if total >= p:
            break
    out = np.zeros_like(probs)
    out[keep] = probs[keep]
    return out / out.sum()

print(np.round(top_p(chances(logits)) * 100, 1))   # [54.7 33.1 12.2  0.   0. ]
rng = np.random.default_rng(0)
print(tokens[rng.choice(5, p=top_p(chances(logits)))])
```

Help-centre answers-க்கு 0.2-னு low temperature-ஓட, retrieval, citations use பண்ணாங்க. Account names-க்கு 0.9 use பண்ணி, இருபது names-ஐ generate பண்ணி, product manager-ஐ தேர்ந்தெடுக்க விட்டாங்க.

## பொதுவான jobs-க்கான ஆரம்ப புள்ளிகள்

இவை ஆரம்ப புள்ளிகள், rules இல்லை. உங்க சொந்த examples-ல test பண்ணுங்க.

| Job | Try பண்ண temperature | ஏன் |
| --- | --- | --- |
| Extraction, classification, routing | 0 முதல் 0.2 | ஒரே சரியான answer, அதனால steady தான் நல்லது |
| Documents-ல இருந்து answers (RAG) | 0 முதல் 0.3 | Sources-க்கு நெருக்கமா இருக்கணும் |
| Code எழுதுறது அல்லது fix பண்றது | 0 முதல் 0.3 | சின்ன மாற்றங்கள் code-ஐ உடைக்கலாம் |
| Summaries, emails | 0.3 முதல் 0.7 | கொஞ்சம் இயல்பான wording, கொஞ்சம் drift |
| Brainstorming, names, slogans | 0.7 முதல் 1.0 | உங்களுக்கு variety வேணும் |

## இந்த settings தப்பான lever-ஆ இருக்குற நேரம்

- **Hallucinations-ஐ நிறுத்த.** Low temperature model ஒவ்வொரு தடவையும் அதோட top choice-ஐ எடுக்க வைக்கும், ஆனா top choice தப்பா இருக்கலாம். Model-க்கு facts-ஐ கொடுங்க (retrieval), sources கேளுங்க, answer-ஐ check பண்ணுங்க. Grounding, citations lesson-ஐ பாருங்க.
- **Valid JSON-ஐ பெற.** Low temperature சுத்தமான JSON தரும்னு நம்பாதீங்க. Model-ஐ உங்க format-க்குள்ள கட்டுப்படுத்துற structured output-ஐ use பண்ணுங்க. Structured output lesson-ஐ பாருங்க.
- **Results-ஐ exact-ஆ repeat ஆக வைக்க.** Temperature 0-ல கூட, servers requests-ஐ batch பண்ற விதம், arithmetic பண்ற விதம் காரணமா runs-க்கு இடையில outputs கொஞ்சம் வேறுபடலாம். ஒரு audit trail வேணும்னா input, settings, output-ஐ log பண்ணுங்க.
- **தெளிவில்லாத prompt-ஐ சரி பண்ண.** Instruction தெளிவில்லாததால answers மாறுதுன்னா, எந்த setting-ஐயும் விட prompt-ஐ இறுக்குறது அதிகம் உதவும்.

## Playground-ல இருந்து production-க்கு

- **Settings-ஐ ஒரே இடத்துல வைங்க.** Temperature, மத்த settings-ஐ code முழுக்க சிதறவிடாம, ஒவ்வொரு task-க்கும் config-ல store பண்ணுங்க; ஒவ்வொரு call-லயும் அவற்றை log பண்ணுங்க, அப்போ ஒரு மோசமான answer-ஐ reproduce பண்ணலாம்.
- **ஒரு தடவைக்கு மேல test பண்ணுங்க.** ஒவ்வொரு test கேள்வியையும் மூணு முதல் அஞ்சு தடவை run பண்ணுங்க. Runs-க்கு இடையில scores நிறைய ஆடுனா, ஒரு run என்ன காட்டினாலும் feature போதுமான அளவு steady இல்லை.
- **பல answers-ஐ sample பண்றது ஒரு tool, default இல்லை.** பல answers-ஐ generate பண்ணி, அவற்றில் பெரும்பாலானவை ஒத்துக்கிற ஒண்ணை, அல்லது ஒரு judge விரும்புற ஒண்ணை எடுக்கலாம். இது கஷ்டமான reasoning கேள்விகளை அடிக்கடி improve பண்ணும், ஆனா பல மடங்கு செலவாகும், தாமதத்தையும் சேர்க்கும். Stakes இதை நியாயப்படுத்துற இடத்துல use பண்ணுங்க.
- **Cost-ஐ cap பண்ணுங்க.** Max tokens வைங்க, reply-க்கு தெளிவான முடிவு இருந்தா ஒரு stop sequence-ஐயும் சேருங்க, அப்போ ஒரு வித்தியாசமான reply முடிவில்லாம போய் உங்களுக்கு பணம் செலவழிக்காது.
- **Randomness இருந்தா தான் retrying உதவும்.** Temperature 0-ல, அதே call-ஐ திரும்ப run பண்ணா பொதுவா அதே தப்பான answer தான் கிடைக்கும்.

## பொதுவா பண்ற தப்புகள்

- **எல்லா இடத்துலயும் default temperature-ஐ use பண்றது.** Extraction-க்கும் brainstorming-க்கும் ரொம்ப வேற settings தேவை.
- **Temperature-ஐயும் top-p-ஐயும் ஒண்ணா மாத்துறது.** ரெண்டும் ஒரே choice-ஐ reshape பண்ணுது. ஒண்ணை மாத்தி, test பண்ணி, அப்புறம் மத்ததை தொடலாமான்னு முடிவு பண்ணுங்க.
- **Temperature 0-னா சரின்னு நம்புறது.** அதுக்கு அர்த்தம் steady; steady-ஆன தப்பான answer இன்னும் தப்பு தான்.
- **Factual tasks-க்கு "அதிக creative" answers-க்காக high temperature வைக்கிறது.** அதிக variety கிடைக்கும், கூடவே அதிக mistakes-உம்.
- **ஒரு run-ஐ வச்சு ஒரு setting-ஐ judge பண்றது.** அதிர்ஷ்டமான அல்லது அதிர்ஷ்டமில்லாத ஒரு sample உங்களுக்கு கொஞ்சமா தான் சொல்லும். பல தடவை run பண்ணுங்க.
- **Stop sequence அல்லது max tokens-ஐ மறக்கிறது.** முடிவே இல்லாத reply பணத்தை செலவழிக்கும்.
