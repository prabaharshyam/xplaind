## இது என்ன

Hosted model-க்கு போற ஒவ்வொரு call-உம் **token** வச்சு bill ஆகுது; token-னா ஒரு வார்த்தை அல்லது வார்த்தையோட ஒரு துண்டு. **Cost control**-னா எந்த features, users, steps அந்த tokens-ஐ செலவு பண்ணுதுன்னு தெரிஞ்சுக்கிட்டு, users-ஐ பாதிக்காம அந்த செலவை குறைக்கிறது. ஒரு request-ஓட bill-க்கு நாலு பகுதிகள் இருக்கு:

- **Fresh input**: system prompt, tool definitions, history, retrieve பண்ண text, user-ஓட message, இதெல்லாம் முழு input price-ல.
- **Cache reads and writes**: input-ல provider-ஓட prompt cache-ல இருந்து வர்ற, அல்லது அதுல save ஆகுற பகுதி, ரொம்ப கம்மியான அல்லது கொஞ்சம் அதிகமான price-ல.
- **Output**: தெரியுற reply, input price-ஐ விட பல மடங்கு அதிகமான price-ல.
- **Thinking**: ஒரு reasoning model-ஓட மறைஞ்சிருக்குற reasoning tokens. Response-ல அதுல ஒண்ணு கூட தெரியலைன்னாலும் அவை output-ஆ தான் bill ஆகும்.

```flow
title: ஒரு request-ல பணம் எங்க போகுது
dir: LR
System prompt, tools | ஒவ்வொரு call-லயும் அதே தான், அதனால cache பண்ணலாம் -> Input bill
History, retrieve பண்ண text | ஒவ்வொரு turn-லயும் வளரும் -> Input bill
User message | பொதுவா சின்னது -> Input bill
Input bill -> Model
Model -[மறைஞ்சிருக்குற reasoning]-> Output bill | thinking output-ஆ bill ஆகும்
Model -[தெரியுற reply]-> Output bill
```

இந்த lesson-ல பெரும்பகுதியை ரெண்டு facts தான் நடத்துது. Token எண்ணிக்கையில பொதுவா input தான் பெருசு, ஏன்னா நீளமான fixed prefix ஒவ்வொரு call-லயும் திரும்ப போகுது. ஒரு token-க்கான price-ல பொதுவா output (thinking சேர்த்து) தான் பெருசு. அதனால பெரிய savings இங்க இருந்து தான் வருது: prefix-ஐ முழு price-ல திரும்ப அனுப்பாம இருக்குறது, task-க்கு தேவையானதை விட அதிகமா think பண்ணாம இருக்குறது, சின்ன model pass ஆகுற இடத்துல பெரிய model-ஐ use பண்ணாம இருக்குறது.

## இது எப்படி work ஆகுது

### முதல்ல அளங்க

ஒவ்வொரு call-ஐயும் அதோட usage numbers-ஓட log பண்ணுங்க: fresh input tokens, cache-read tokens, cache-write tokens, output tokens, API report பண்ணா output-ல thinking-ஓட பங்கு (Anthropic-ஓட field `usage.output_tokens_details.thinking_tokens`; OpenAI-உம் reasoning tokens-ஐ `output_tokens_details`-க்குள்ள தான் report பண்ணுது). ஒவ்வொரு call-ஐயும் feature, user, model, effort setting, prompt version வச்சு tag பண்ணுங்க. அப்போ இந்த கேள்விகளுக்கு பதில் சொல்லலாம்: எந்த feature அதிகமா cost ஆகுது, எந்த users, எந்த agent step, எவ்வளவு thinking. மாசத்தோட மொத்த total மட்டும் இருந்தா இதெல்லாம் மறைஞ்சுடும்.

Cost per request மட்டும் இல்லாம **cost per completed task**-ஐ track பண்ணுங்க. Fail ஆகுற, retry ஆகுற, அல்லது ஒரு ஆள்கிட்ட போற ஒரு மலிவான call உண்மையில மலிவு இல்லை.

| Claude Haiku 5.5, 100,000 tokens வரைக்குமான prompts | $0.10 | $0.50 | $0.01 | $0.125 | $0.05 / $0.25 |

இதுல இருந்து மூணு விஷயங்களை படிக்கலாம். Output-க்கு input-ஐ விட அஞ்சு மடங்கு cost. ரெண்டுலயுமே சின்ன model பெரிய model-ஐ விட 40 மடங்கு மலிவு. Batch சரியா பாதி விலை. மத்த providers-உம் இதே structure-ஐ வேற numbers-ஓட use பண்றாங்க, அதனால அவங்களோட இப்போதைய pages-ஐ படிச்சு, நீங்க check பண்ண தேதியை எழுதி வைங்க.

### Model தேர்வு: மிகப்பெரிய lever

Classification, clean text-ல இருந்து extraction, routing, சின்ன replies இதுக்கெல்லாம் ஒரு சின்ன model பெரும்பாலும் பெரிய model-க்கு சமமா இருக்கும். ஒவ்வொரு task-ஐயும் உங்க eval set-ல ரெண்டு மூணு model sizes-ஓட test பண்ணி, pass ஆகுறதுல மலிவானதை use பண்ணுங்க, கஷ்டமான requests-ஐ மட்டும் பெரிய model-க்கு அனுப்புங்க. Batching, model tiering பத்தின lesson routers-ஐ ஆழமா cover பண்ணுது. Switch பண்ணும்போது tokens-ஐ திரும்ப எண்ணுங்க: வேற வேற models வேற வேற tokenizers use பண்ணலாம், அதனால அதே text வேற எண்ணிக்கையில tokens-ஆ இருக்கலாம்.

### Reasoning tokens-உம் effort-உம்

இப்போதைய பெரும்பாலான models பதில் சொல்றதுக்கு முன்னாடி think பண்ணுது, அந்த thinking முழு output price-ல output-ஆ bill ஆகுது. Response-ல ஒரு summary மட்டும் காட்டினாலும், எதுவுமே காட்டலைன்னாலும், முழு thinking-க்கும் நீங்க பணம் கட்டுறீங்கன்னு Anthropic-ஓட documentation தெளிவா சொல்லுது. அதனால தெரியுற reply-ஓட நீளம் bill-ஓட match ஆகாது.

Opus 5.5 prices-ல ஒரு சின்ன example: 10 visible tokens-உம் 90 thinking tokens-உம் இருக்குற ஒரு ticket label-க்கு 100 × $20 per million = $0.002 output ஆகும், label-க்கு மட்டும் ஆகுற $0.0002-ஐ விட பத்து மடங்கு.

இதை கட்டுப்படுத்துறது **effort** setting (மத்த providers-ல "reasoning effort"). Effort கம்மியானா thinking கம்மி, low effort-ல simple inputs-க்கு model thinking-ஐயே skip பண்ணலாம். Anthropic API-ல default, Opus 5.5, Haiku 5.5-க்கு `medium`, மத்த பெரும்பாலான models-க்கு `high`, அதனால அதை explicit-ஆ set பண்ணுங்க. மூணு rules:

- **ஒவ்வொரு route-க்கும் tune பண்ணுங்க.** Chat, tagging, extraction பெரும்பாலும் low effort-லயும் quality-ஐ தக்க வச்சுக்கும்; multi-step maths, code, planning-க்கு பெரும்பாலும் high வேணும். ஒவ்வொரு route-க்கும் eval-ல அளங்க.
- **`max_tokens`-ல இடம் விடுங்க.** Thinking-உம் அதுக்குள்ள தான் count ஆகும். 200-token reply-க்கு size பண்ண ஒரு cap, model think பண்ணும்போது answer-ஐ truncate பண்ணிடும், அப்புறம் retry-க்கு ஆகுற cost, cap மிச்சப்படுத்தினதை விட அதிகம்.
- **ஒரு conversation-க்குள்ள effort-ஐ மாத்தாம வைங்க.** Requests-க்கு நடுவுல அதை மாத்தினா prompt cache invalidate ஆகலாம்.

### Prompt caching

Prompt caching, prompt-ஓட நீளமான, மாறாத ஆரம்பப் பகுதியை (system prompt, tool definitions, அல்லது ஒரு பெரிய document மாதிரி) store பண்ணி வைக்குது, அதனால அடுத்த calls அதை மலிவா read பண்ணலாம். இது ஒரு prefix match: முதல்ல tools, அப்புறம் system prompt, அப்புறம் messages; எந்த இடத்துல மாற்றம் வந்தாலும் அதுக்கு அப்புறம் இருக்குற எல்லாமே invalidate ஆகும். Anthropic API-ல, November 2026 நிலவரப்படி:

- 5-minute cache write-க்கு input price-ஓட 1.25 மடங்கு ஆகும், ஒரு read-லயே லாபம் வந்துடும். 1-hour write-க்கு 2 மடங்கு ஆகும், ரெண்டு reads-ல லாபம் வரும்.
- ஒரு read-க்கு பெரும்பாலான models-ல input-ஓட 0.1 மடங்கு, Opus 5.5, Sonnet 5.5-ல 0.05 மடங்கு.
- ஒரு minimum length-ஐ விட சின்ன prompts (இப்போதைய models-ல 512 tokens) cache ஆகாது, அதை சொல்ல எந்த error-உம் வராது.

Caching சத்தமில்லாம fail ஆகும். பொதுவான காரணங்கள்: system prompt-ஓட மேல் பகுதியில ஒரு date அல்லது request ID, ஒவ்வொரு தடவையும் வேற order-ல build ஆகுற tool definitions, மாத்தின effort setting, வேற model-க்கு switch பண்றது (ஒவ்வொரு model-க்கும் தனி cache), அல்லது traffic ரொம்ப கம்மியா இருந்து calls-க்கு நடுவுல 5-minute lifetime முடிஞ்சுடுறது. Usage-ல cache-read count-ஐ check பண்ணுங்க. அது zero-லயே இருந்தா, அந்த மாற்றத்தை கண்டுபிடிங்க.

**Response caching** வேற: முழு answers-ஐ store பண்ணி, திரும்ப வர்ற கேள்விகளுக்கு model-ஐயே skip பண்றீங்க. ஒவ்வொரு hit-லயும் இன்னும் அதிகமா மிச்சமாகும், ஆனா பழைய அல்லது leak ஆன answers போற risk இருக்கு. Caching, speed பத்தின lesson ரெண்டையும் cover பண்ணுது.

### Batch APIs

காத்திருக்கக்கூடிய வேலை (ராத்திரி summaries, bulk tagging, eval runs, backfills மாதிரி) ஒரு batch API வழியா போகலாம். Anthropic-ஓட Message Batches API input-க்கும் output-க்கும் normal price-ல 50% தான் வாங்குது. பெரும்பாலான batches ஒரு மணி நேரத்துக்குள்ள முடியும்; 24 மணி நேரத்துக்குள்ள முடியாத requests expire ஆகும், அவற்றுக்கு bill வராது. Batch discount-உம் caching discount-உம் சேர்ந்தே கிடைக்கும், batches 5 நிமிஷத்துக்கு மேல எடுக்கலாம்ங்குறதால 1-hour cache அவற்றுக்கு ஏத்தது.

### Agents: ஒவ்வொரு step-லயும் history வளரும்

ஒரு agent ஒவ்வொரு step-லயும் முழு conversation-ஐயும் அனுப்புது, அதனால ஒவ்வொரு step-லயும் input வளருது. 4,000-token prefix, ஒவ்வொரு step-லயும் 1,500 புது tokens-ன்னு வச்சுக்கோங்க. எட்டு steps-ல 4,000 × 8 + 1,500 × (0 + 1 + … + 7) = 32,000 + 42,000 = 74,000 input tokens போகுது, ஒரே task மாதிரி தோணுற ஒண்ணுக்கு. Fixed prefix-ஐயும் முந்தைய history-ஐயும் cache பண்ணுங்க, task-க்கு தேவையான tools-ஐ மட்டும் load பண்ணுங்க, ஒரு step limit வைங்க, நீளமான runs-ல பழைய tool results-ஐ summarise அல்லது clear பண்ணுங்க. Agent budgets, kill switches பத்தின lesson limits-ஐ cover பண்ணுது.

### இந்திய மொழிகளும் self-hosting-உம்

Tokenizer-ஐ பொறுத்து, அதே reply-க்கு English-ஐ விட Hindi, Tamil, Bengali-ல பல மடங்கு அதிக tokens தேவைப்படலாம், அதனால நீங்க serve பண்ற ஒவ்வொரு மொழிக்கும் tokens per request-ஐ அளங்க. இந்திய மொழிகள்ல AI பத்தின lesson இதை cover பண்ணுது.

ஒரு open model-ஐ self-host பண்ணா, per-token bill-க்கு பதிலா ஒரு fixed மாச bill வரும். உதாரணமா, ஒரு GPU server-ஐ run பண்ண, ஆளுங்களோட நேரம் சேர்த்து, மாசம் ₹2.5 லட்சம் ஆகுதுன்னு வச்சுக்கோங்க. ஒரு batched summary-க்கு ₹0.47-ன்னா, மாசம் சுமார் 5.3 லட்சம் summaries அனுப்பும்போது API-க்கும் அதே cost ஆகும் (2,50,000 ÷ 0.47). அதுக்கு கீழ API தான் ஜெயிக்கும்; அதுக்கு மேல, open model அதே evals-ஐ pass பண்ணி, server busy-ஆவே இருந்தா மட்டும் தான் self-hosting ஜெயிக்கும். vLLM, total cost of ownership பத்தின lessons உண்மையான numbers-ஐ எப்படி போடுறதுன்னு காட்டுது.

### ஒரு calculator

இந்த calculator table-ல இருக்குற prices-ஐயும், ஒரு dollar-க்கு ₹94-ங்குற ஒரு illustrative rate-ஐயும் use பண்ணுது (November 2026 நடுவுல rupee சுமார் ₹93-ல இருந்து ₹94 வரை trade ஆச்சு). கீழ இருக்குற worked example-ஓட rows-ஐ இது print பண்ணுது.

```python
RATE = 94  # rupees per US dollar: illustrative (about 93 to 94 in mid November 2026)

# US dollars per million tokens, Anthropic API pricing page, checked 28 November 2026
PRICES = {
    "opus-5.5":  {"in": 4.00, "out": 20.00, "cache_read": 0.20, "cache_write": 5.00},
    "haiku-5.5": {"in": 0.10, "out": 0.50, "cache_read": 0.01, "cache_write": 0.125},
}

def cost_inr(model, fresh_in, out, cache_read=0, cache_write=0, batch=False):
    """Rupees for one request. `out` includes thinking tokens, which bill as output."""
    p = PRICES[model]
    usd = (fresh_in * p["in"] + out * p["out"]
           + cache_read * p["cache_read"] + cache_write * p["cache_write"]) / 1e6
    return usd * RATE * (0.5 if batch else 1)

rows = {  # (rupees per request, requests per month)
    "summary, before":  (cost_inr("opus-5.5", 1500, 200), 300_000),
    "summary, batch":   (cost_inr("opus-5.5", 1500, 200, batch=True), 300_000),
    "classify, before": (cost_inr("opus-5.5", 600, 100), 300_000),
    "classify, small":  (cost_inr("haiku-5.5", 600, 10), 300_000),
    "chat, before":     (cost_inr("opus-5.5", 6000, 750), 60_000),
    "chat, after":      (cost_inr("opus-5.5", 1000, 500, cache_read=2700, cache_write=300), 60_000),
}
for name, (per, n) in rows.items():
    print(f"{name:17} ₹{per:.4f} each, ₹{per * n / 1e5:.2f} lakh a month")
```

### Safe-ஆ குறைக்கிறது

ஒரு தடவைக்கு ஒரு lever-ஐ மட்டும் மாத்துங்க, முன்னாடியும் பின்னாடியும் அந்த feature-ஓட evals-ஐ run பண்ணுங்க. Cost-ஐயும் quality-ஐயும் பக்கத்து பக்கத்துல report பண்ணுங்க. ஒரு மாற்றம் பணத்தை மிச்சப்படுத்தி quality-ஐ கொஞ்சம் குறைச்சா, team அந்த trade-ஐ ஏத்துக்கிச்சுன்னும் ஏன்னும் எழுதி வைங்க.

### Launch-க்கு முன்னாடி ஒரு feature-க்கு விலை போடுறது

Pilot-ல இருந்து ஒரு user-க்கு மாசம் ஆகுற cost-ஐ estimate பண்ணுங்க: ஒரு user-ஓட requests × ஒரு request-ஓட cost. அதை GST, payment fees போக user கட்டுறதோட compare பண்ணுங்க. உதாரணமா, கீழ இருக்குற trim பண்ண chat-ல ஒரு reply-க்கு ₹1.51-ன்னா, மாசம் 600 messages அனுப்புற ஒரு student-க்கு ₹906 ஆகும், ஆனா ஒரு ₹149 plan சுமார் ₹120 தான் கொண்டு வரும். ஒண்ணு, chat அதோட eval-ஐ pass பண்ற ஒரு மலிவான route-ல run ஆகணும், இல்லைன்னா plan-க்கு ஒரு daily limit இருக்கணும். Launch-க்கு முன்னாடியே caps வைங்க, முதல் ரெண்டு வாரத்துல திரும்ப check பண்ணுங்க, ஏன்னா உண்மையான users pilot group மாதிரி நடந்துக்குறது அரிது.

## ஒரு worked example

Kolkata-ல இருக்குற ஒரு customer-service platform model calls-க்கு மாசம் சுமார் ₹6.3 லட்சம் செலவு பண்ணுது, எல்லாமே Opus 5.5-ல; அதை பாதியா குறைக்கணும்னு நினைக்குது. கீழ இருக்குற எல்லா volumes-உம் token counts-உம் illustrative தான், மேல இருக்குற table வச்சு, ஒரு dollar-க்கு ₹94-ல price பண்ணது.

**Step 1: அளங்க.** Tag பண்ண logs மூணு features-ஐ காட்டுது:

- **ராத்திரி ticket summaries**: ஒரு ராத்திரிக்கு 10,000, மாசம் 3 லட்சம். ஒவ்வொண்ணுக்கும் 1,500 input, 200 output tokens. காலை 10 மணிக்கு முன்னாடி யாரும் அவற்றை படிக்கிறதில்லை.
- **Ticket classification**: மாசம் 3 லட்சம். ஒவ்வொண்ணுக்கும் 600 input tokens, ஆனா output 100 tokens: ஒரு 10-token label, அதோட 90 tokens thinking.
- **Live chat**: மாசம் 60,000 replies. ஒவ்வொண்ணுக்கும் 5,000-token system prompt-உம் tools-உம், uncached, அதோட 1,000 tokens history-உம் கேள்வியும். Output 750 tokens: 450 visible, 300 thinking.

**Step 2: ஒவ்வொரு feature-க்கும் விலை போடுங்க.**

- Summaries: (1,500 × $4 + 200 × $20) ÷ 10 லட்சம் = $0.0100, அதாவது ஒவ்வொண்ணுக்கும் ₹0.94, அதனால 3 லட்சம் × ₹0.94 = ₹2.82 லட்சம் (45%).
- Classification: (600 × $4 + 100 × $20) ÷ 10 லட்சம் = $0.0044, அதாவது ஒவ்வொண்ணுக்கும் ₹0.41, அதனால ₹1.24 லட்சம் (20%). 100 output tokens-ல 90 thinking.
- Chat: (6,000 × $4 + 750 × $20) ÷ 10 லட்சம் = $0.0390, அதாவது ஒவ்வொண்ணுக்கும் ₹3.67, அதனால 60,000 × ₹3.67 = ₹2.20 லட்சம் (35%).

மொத்தம்: ₹6.26 லட்சம்.

**Step 3: ஒவ்வொரு feature-க்கும் ஒரு lever-ஐ மாத்துங்க.**

- **Summaries batch API-க்கு போகுது.** அதே tokens, பாதி விலையில: ஒவ்வொண்ணுக்கும் ₹0.47, மாசம் ₹1.41 லட்சம். காலை 10 மணிக்கு ரொம்ப முன்னாடியே ready ஆயிடும்.
- **Classification low effort-ல Haiku 5.5-க்கு போகுது.** Opus 5.5-லயே effort-ஐ மட்டும் குறைச்சா thinking போயிடும் (600 × $4 + 10 × $20 = $0.0026, ஒவ்வொண்ணுக்கும் ₹0.24, 41% கம்மி). Low effort-ல சின்ன model-க்கு (600 × $0.10 + 10 × $0.50) ÷ 10 லட்சம் = $0.000065, ஒவ்வொண்ணுக்கும் ₹0.0061, மாசம் சுமார் ₹1,800 ஆகும். Label பண்ண 400 tickets-ல accuracy 94%-ல இருந்து 93%-க்கு போகுது, team அதை ஏத்துக்குது.
- **Chat Opus 5.5-லயே இருக்கு.** System prompt-ஐ 5,000-ல இருந்து 3,000 tokens-ஆ trim பண்ணி cache பண்றாங்க. பகல் நேர busy traffic 90% hit rate குடுக்குது, அதனால சராசரியா 2,700 tokens ஒரு million-க்கு $0.20-ல cache reads, 300 tokens ஒரு million-க்கு $5-ல writes. சுமார் 150 வார்த்தைக்குள்ள replies வேணும்னு prompt கேக்குது, அது visible output-ஐ 450-ல இருந்து 200 tokens-க்கு கொண்டு வருது. Thinking 300-லயே இருக்கு. `max_tokens` 200 இல்ல, 1,200-ஆ set பண்ணிருக்காங்க, அதனால thinking எந்த reply-ஐயும் truncate பண்ணாது. ஒரு reply-க்கு: 1,000 × $4 + 2,700 × $0.20 + 300 × $5 + 500 × $20 = $0.01604, அதாவது ₹1.51, அதனால மாசம் ₹0.90 லட்சம்.
- **Limits.** ஒவ்வொரு support agent-க்கும் ஒரு daily cap, chat-ஓட tool use-க்கு ஒரு step limit, budget-ல 80%-ல ஒரு spending alert, provider console-ல ஒரு hard monthly limit.

## பொதுவா பண்ற தப்புகள்

- **தெரியுற reply-ஐ மட்டும் பார்க்குறது.** ஒரு model upgrade-க்கு அப்புறம் replies அதே நீளத்துல தெரிஞ்சாலும் bill டபுள் ஆகுது. காரணம் thinking tokens: price-ஐ குறை சொல்றதுக்கு முன்னாடி usage-ல thinking count-ஐ check பண்ணுங்க.
- **எல்லாத்தையும் திரும்ப அனுப்புற retries.** Timeout-ல மூணு உடனடி retries ஒரு 6,000-token prompt-ஐ நாலு தடவை வரை bill பண்ணும், overload-ஐ இன்னும் மோசமாக்கும். Exponential backoff, jitter-ஓட அதிகபட்சம் ரெண்டு retries மட்டும் use பண்ணுங்க.
- **ஒருபோதும் hit ஆகாத cache.** System prompt-ஓட மேல ஒரு timestamp இருந்தா ஒவ்வொரு prefix-உம் வேற மாதிரி ஆயிடும். அறிகுறி: cache-read tokens zero-லயே இருக்கும், ஆனா plain input-ஐ விட அதிகமா cost ஆகுற cache writes வந்துக்கிட்டே இருக்கும்.
- **ஒவ்வொரு call-லயும் எல்லா tools-உம்.** தலா 200 tokens இருக்குற முப்பது tool definitions, step-க்கு ரெண்டு tools தான் தேவைன்னாலும், ஒவ்வொரு step-லயும் 6,000 input tokens சேர்க்கும்.
- **Thinking-க்கு இடம் இல்லாத `max_tokens` cap.** Replies ஒரு `max_tokens` stop reason-ஓட வாக்கியத்தோட நடுவுல நின்னுடும், users retry பண்ணுவாங்க, நீங்க ரெண்டு தடவை பணம் கட்டுவீங்க.
- **Completed task-க்கு இல்லாம request-க்கு cost-ஐ judge பண்றது.** ஒரு call-க்கு 20 மடங்கு மலிவான, ஆனா அஞ்சுல ஒரு தடவை fail ஆகுற model, retries-உம் human review-உம் சேர்த்து கணக்கு பண்ணா அதிகமா cost ஆகலாம்.
- **Quality-ஐ check பண்ணாம cost-ஐ குறைக்கிறது.** ஒவ்வொரு மாற்றத்துக்கும் evals-ஐ run பண்ணுங்க, numbers-ஐ வச்சுக்கோங்க.

## செலவை குறைக்குறது தப்பான இலக்கா இருக்கும்போது

- **Feature இன்னும் work ஆகல.** முதல்ல உங்க evals-ல quality-ஐ சரி பண்ணுங்க; optimise அப்புறம் பண்ணலாம்.
- **Savings ரொம்ப சின்னது.** மாசம் ₹2,000 மிச்சப்படுத்துறது வாரக்கணக்கான engineering-க்கோ, அளக்கக்கூடிய ஒரு quality drop-க்கோ worth இல்லை.
- **Latency அல்லது trust அதைவிட முக்கியம்.** High-stakes task-ல மெதுவா இருக்குற அல்லது அதிக தப்பு பண்ற ஒரு மலிவான model, support-லயும் இழக்குற users-லயும் அதிகமா cost ஆகலாம்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு call-ஐயும் tag பண்ணுங்க**, feature, user, model, effort, prompt version வச்சு, எல்லா token counts-ஐயும் cost-ஐயும் store பண்ணுங்க.
- **ஒரு cost dashboard build பண்ணுங்க**: feature வாரியா தினசரி spend, cost per completed task, அதிகமா use பண்ற users, output-ல thinking-ஓட பங்கு, cache hit rate, budget-க்கும் alert threshold-க்கும் lines-ஓட. Quality metrics கூட சேர்த்து வாரா வாரம் review பண்ணுங்க.
- **ஒவ்வொரு feature-க்கும் budgets வைங்க**, alerts-ஓட, provider-ல hard limits-ஓட.
- **அடிக்கடி திரும்ப price பண்ணுங்க.** Providers விலையை குறைக்குறாங்க, மலிவான models-ஐ release பண்றாங்க; ஆறு மாசத்துக்கு முன்னாடி எடுத்த ஒரு முடிவு இப்போ தேவைக்கு அதிகமா பணம் கட்ட வைக்கலாம்.
- **மலிவான path-ஐ test பண்ணி வைங்க**, ஒரு சின்ன fallback model மாதிரி, cost திடீர்னு ஏறினா சீக்கிரம் switch பண்ணலாம்.

## Practice பண்ணுங்க

கீழ link பண்ணிருக்குற, production-ல LLM applications பத்தின Chip Huyen-ஓட article-ஐ படிங்க, குறிப்பா cost sections-ஐ. அவங்களோட *AI Engineering* (O'Reilly, 2025) புத்தகத்தோட Chapters 9, 10 இன்னும் ஆழமா போகுது.

1. உங்க apps-ல ஒண்ணுல cost logging சேருங்க, thinking, cache tokens-ஐ தனியா பிரிச்சு, அதிகமா cost ஆகுற feature-ஐ கண்டுபிடிங்க.
2. அந்த feature-க்கு, உங்க eval set-ஐ ரெண்டு effort levels-லயும் ஒரு சின்ன model-லயும் run பண்ணி, ஒவ்வொரு option-க்கும் calculator வச்சு விலை போடுங்க.
3. நீளமான fixed prefix-ஐ cache பண்ணி usage data-ல cache reads-ஐ confirm பண்ணுங்க, அல்லது அவசரமில்லாத ஒரு job-ஐ batch API-க்கு மாத்துங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** feature வாரியாவும் user வாரியாவும் cost-ஐ காட்ட முடியும், output-ல thinking எவ்வளவு பங்குன்னு காட்ட முடியும், உங்க eval scores-ஐ பாதிக்காம cost-ஐ குறைச்ச ஒரு மாற்றத்தை கணக்கோட எழுதி காட்ட முடியும்.
