## இது என்ன

LLM apps-ல ஒவ்வொரு request-க்கும் காசு செலவாகும்; users அதிகமாக, prompts நீளமாக, agent loops வரும்போது செலவும் வளரும். **Cost control**-னா பணம் எங்க போகுதுன்னு தெரிஞ்சுக்கிட்டு, user experience-ஐ பாதிக்காம அதை குறைக்கிறது. முக்கிய levers: model தேர்வு, prompt size, output size, caching, batching, limits.

| Feature (tag பண்ண logs-ல இருந்து) | மாசம் ₹6 லட்சத்துல பங்கு | Fix |
|---|---|---|
| ராத்திரி ticket summaries | 45% | Batch API-க்கு மாத்துங்க |
| Live chat replies | 35% | Prompt-ஐ trim பண்ணி cache பண்ணுங்க, replies-ஐ cap பண்ணுங்க |
| Ticket classification | 20% | ஒரு சின்ன model (accuracy 94%-ல இருந்து 93%) |

```flow
dir: LR
ஒவ்வொரு call-ஐயும் feature வாரியா tag பண்ணுங்க -> பெரிய பங்கை கண்டுபிடிங்க -> ஒரு fix போடுங்க -> Caps சேருங்க | ஒரு agent-க்கு daily cap, budget-ல 80%-ல alert, provider hard limit
Caps சேருங்க -> அடுத்த மாசம்: ₹2.7 லட்சம் | customer satisfaction மாறல
```

இந்த lesson, Kolkata-ல இருக்குற ஒரு customer-service platform-ஐ பின்தொடருது; அவங்க தங்க model bill-ஐ பாதியா குறைக்க நினைச்சாங்க.

## இது எப்படி work ஆகுது

**முதல்ல அளங்க.** ஒவ்வொரு call-க்கும் tokens-ஐயும் cost-ஐயும் feature, user, model tag-ஓட log பண்ணுங்க. அப்போ இந்த கேள்விகளுக்கு பதில் சொல்லலாம்: எந்த feature அதிகம் செலவு வைக்குது? எந்த users? ஒரு agent-ஓட எந்த step? மாச மொத்தம் மட்டும் இதை மறைச்சுடும்; ஒரு user-க்கும் ஒரு feature-க்கும் ஆகுற செலவு எங்க நடவடிக்கை எடுக்கணும், ஒரு feature தன் செலவை தானே ஈடுகட்ட முடியுமான்னு காட்டும்.

**Model தேர்வு: மிகப்பெரிய lever.** சின்ன models, பெரிய models-ஐ விட பல மடங்கு மலிவா இருக்கலாம். Classification, சுத்தமான text-ல இருந்து extraction, routing, சின்ன replies மாதிரி எளிய tasks-க்கு, ஒரு சின்ன model பெரும்பாலும் பெரியதுக்கு சமமா இருக்கும். ஒவ்வொரு task-யையும் உங்க eval set-ல ரெண்டு மூணு model அளவுகளோட test பண்ணி, pass பண்றதுல மலிவானதை use பண்ணுங்க. கஷ்டமான requests-ஐ மட்டும் பெரிய model-க்கு அனுப்புங்க.

**Prompt size.** ஒவ்வொரு request-உம் தன் input-க்கு காசு குடுக்கும். System prompts-ஐ trim பண்ணுங்க, retrieve பண்ற chunks குறைவாவும் சின்னதாவும் அனுப்புங்க, நீளமான conversation history-ஐ summarise பண்ணுங்க, use பண்ணாத tool definitions-ஐ நீக்குங்க.

**Output size.** Output tokens பொதுவா input-ஐ விட அதிகம் செலவாகும். சுருக்கமான formats கேளுங்க, `max_tokens` set பண்ணுங்க.

**Caching.** நீளமான பகிரப்பட்ட prefixes-க்கு prompt caching; திரும்பத் திரும்ப வர்ற கேள்விகளுக்கு response caching.

**Batching.** காத்திருக்கக்கூடிய வேலை (ராத்திரி summaries, bulk classification, ஒரு corpus-ஐ embed பண்றது) batch APIs வழியா போகலாம்; மணிக்கணக்குல முடிவு வர்றதுக்கு ஈடா providers பொதுவா பெரிய discount தருவாங்க.

**Limits.** ஒரு user-க்கு daily caps, agents-க்கு step limits, spending alerts, provider console-ல hard limits.

**கணக்கை தெரிஞ்சுக்கோங்க.** ஒரு request-ஓட cost என்பது input tokens × input price கூட்டல் output tokens × output price; cached input பொதுவா ரொம்ப குறைவா bill ஆகும். ஒரு சின்ன calculator மதிப்பீடுகளை நேர்மையா வைக்கும்:

```python
def cost_per_request_inr(input_tokens, output_tokens, in_price_usd_per_m, out_price_usd_per_m,
                         cached_share=0.0, cache_discount=0.9, usd_to_inr=85):
    """Prices are US dollars per million tokens. cached_share: fraction of input served from the prompt cache."""
    fresh = input_tokens * (1 - cached_share)
    cached = input_tokens * cached_share * (1 - cache_discount)
    usd = ((fresh + cached) * in_price_usd_per_m + output_tokens * out_price_usd_per_m) / 1e6
    return usd * usd_to_inr

def monthly_cost_inr(requests_per_month, **kw):
    return requests_per_month * cost_per_request_inr(**kw)

# A chat reply: 3,000 input tokens (60% cached), 250 output, $3 / $15 per million tokens
per = cost_per_request_inr(3000, 250, 3, 15, cached_share=0.6)
print(round(per, 2), round(monthly_cost_inr(300_000, input_tokens=3000, output_tokens=250,
      in_price_usd_per_m=3, out_price_usd_per_m=15, cached_share=0.6)))
```

Prices-உம் exchange rate-உம் மாறிக்கிட்டே இருக்கும், அதனால provider-ஓட தற்போதைய page-ல இருந்து படிச்சு, எந்த தேதியில check பண்ணீங்கன்னு பதிவு பண்ணுங்க. இந்த கணக்கு சீக்கிரமா காட்டுற ரெண்டு விஷயம்: output tokens பொதுவா input-ஐ விட பல மடங்கு அதிகம் செலவாகும், ஒவ்வொரு call-லயும் திரும்பத் திரும்ப வர்ற நீளமான prompts வேகமா சேர்ந்துடும்.

**Language-உம் முக்கியம்.** Tokenizer-ஐ பொறுத்து, அதே reply-க்கு Hindi, Tamil, Bengali-ல English-ஐ விட பல மடங்கு tokens தேவைப்படலாம்; அதனால நீங்க serve பண்ற ஒவ்வொரு language-க்கும் ஒரு request-க்கு tokens-ஐ அளங்க. இந்திய மொழிகள்ல AI பத்தின lesson இதை பேசுது.

**Difficulty வச்சு route பண்ணுங்க.** ஒரு சின்ன, வேகமான classifier அல்லது rules, எளிய requests-ஐ மலிவான model-க்கும், scope-க்கு வெளியே இருக்குற கேள்விகளை model call இல்லாத ஒரு stock reply-க்கும், கஷ்டமானவற்றை மட்டும் வலுவான model-க்கும் அனுப்பலாம். AI app-ஐ layers-ஆ வளர்க்குறது பத்தின lesson routers-ஐயும் gateways-ஐயும் பேசுது.

**அதிர்ச்சிகளை கவனிங்க.** Retry storms, loop-ல சுத்துற agents, ஒரு பெரிய document, அல்லது ஒரு heavy user ராத்திரிக்குள்ள செலவை பல மடங்கு ஆக்கிடலாம்.

**Levers-உம் வழக்கமான சேமிப்பும்:**

| Lever | வழக்கமான விளைவு | Risk |
| --- | --- | --- |
| எளிய tasks-க்கு சின்ன model | அந்த task-ல பெரிய சேமிப்பு | Test பண்ணலன்னா quality குறையும் |
| காத்திருக்கக்கூடிய வேலைக்கு Batch API | பெரிய discount | மணிக்கணக்குல தாமதம் |
| Prompt caching | திரும்ப வர்ற prefixes-ல input செலவு குறையும் | Prefix மாறினா வேலை செய்யாது |
| சின்ன prompts-உம் outputs-உம் | அதே விகிதத்துல சேமிப்பு | Context அல்லது detail விடுபடலாம் |
| Response caching | திரும்பத் திரும்ப வர்ற calls-ஐ நீக்கும் | பழைய அல்லது பகிரப்பட்ட பதில்கள் |
| Caps-உம் alerts-உம் | அதிர்ச்சிகளை தடுக்கும் | Users limits-ஐ தொடுவாங்க |

**நடவடிக்கைக்கு வழிவகுக்கிற cost dashboard.** Feature வாரியா தினசரி செலவு, அதிகம் use பண்ற users-ஓட ஒரு user-க்கு cost, வெற்றிகரமான ஒரு task-க்கு cost, top feature-க்கு prompt-ஓட ஒவ்வொரு பகுதியில இருந்து வர்ற tokens-ஓட பங்கு ஆகியவற்றை காட்டுங்க. Budget-க்கும் alert threshold-க்கும் ஒரு கோடு சேருங்க. வாரா வாரம் review பண்ணுங்க. அடுத்து எந்த feature-ஐ optimise பண்ணணும், போன வாரம் பண்ண மாற்றம் வேலை செஞ்சுதான்னு ஒரே பார்வையில dashboard சொல்லணும்.

**பாதுகாப்பா குறைக்கிறது.** ஒரு நேரத்துல ஒரு lever-ஐ மட்டும் மாத்துங்க, அதுக்கு முன்னாடியும் பின்னாடியும் அந்த feature-ஓட evals-ஐ run பண்ணுங்க. Cost-ஐயும் quality-யையும் பக்கத்துல பக்கத்துல report பண்ணுங்க. ஒரு மாற்றம் காசு மிச்சப்படுத்தி quality-ஐ கொஞ்சம் குறைச்சா, இங்க classifier-ல மாதிரி, team அந்த trade-ஐ ஏத்துக்கிச்சுன்னும் ஏன்னும் எழுதி வைங்க.

**Launch-க்கு முன்னாடி ஒரு feature-க்கு விலை போடுறது.** Pilot-ல இருந்து ஒரு user-க்கு மாசத்துக்கு ஆகுற cost-ஐ மதிப்பிடுங்க: ஒரு user-க்கு requests, ஒரு request-க்கு tokens, model-ஓட price. அதை அந்த feature ஒரு user-க்கு சம்பாதிக்கிறதோட அல்லது மிச்சப்படுத்துறதோட ஒப்பிடுங்க. ஒரு user-ஓட மாச cost அவங்க value-வை தாண்டலாம்னா, முதல் பெரிய bill வர்றதுக்கு அப்புறம் இல்ல, launch-க்கு முன்னாடியே caps வைங்க. உண்மையான traffic-ஓட முதல் ரெண்டு வாரத்துல மதிப்பீட்டை திரும்ப பாருங்க, ஏன்னா உண்மையான users அரிதா தான் pilot குழு மாதிரி நடந்துக்குவாங்க.

## ஒரு worked example

Kolkata-ல ஒரு customer-service platform model calls-க்கு மாசம் ₹6 லட்சம் செலவு பண்ணி, அதை பாதியா குறைக்க விரும்புது.

Feature வாரியா logging காட்டுறது:

- 45% ஒரு ராத்திரி job-க்கு, அது team leads-க்காக 10,000 support tickets-ஐ summarise பண்ணுது; காலை 10 மணிக்கு முன்னாடி யாரும் அதை படிக்கிறதில்ல;
- 35% live chat replies-க்கு;
- 20% ticket classification-க்கு.

மாற்றங்கள்:

- ராத்திரி summaries, provider-ஓட batch API-க்கு பெரிய discount-ஓட போகுது, காலைக்கு முன்னாடியே முடிஞ்சுடுது.
- Ticket classification பெரிய model-ல இருந்து சின்னதுக்கு மாறுது; label பண்ண 400 tickets-ல accuracy 94%-ல இருந்து 93%-ஆ குறையுது, team அதை ஏத்துக்குது.
- Live chat பெரிய model-ஐயே வச்சுக்குது, ஆனா system prompt 40% trim பண்ணப்பட்டு cache ஆகுது, replies 200 tokens-க்கு cap ஆகுது.
- ஒரு agent-க்கு daily cap-உம், budget-ல 80%-ல ஒரு spending alert-உம் சேர்க்கப்படுது.

அடுத்த மாச bill ₹2.7 லட்சம், customer satisfaction scores-ல எந்த மாற்றமும் இல்ல.

| மாற்றம் | Cost விளைவு | Quality check |
| --- | --- | --- |
| ராத்திரி summaries batch-க்கு | 45% செலவுல பெரிய discount | முன்னாடி மாதிரியே 10 மணிக்கு முன்னாடி ready |
| Classification சின்ன model-க்கு | ரொம்ப மலிவு | 400 tickets-ல 94%-ல இருந்து 93%, ஏத்துக்கப்பட்டுச்சு |
| Chat prompt 40% trim பண்ணி cache பண்ணப்பட்டுச்சு; replies cap பண்ணப்பட்டுச்சு | Chat செலவு குறைவு | Satisfaction மாறல |

## பொதுவா பண்ற தப்புகள்

- **Feature வாரியாவும் user வாரியாவும் அளக்காம optimise பண்றது.**
- **எல்லாத்துக்கும் மிகப்பெரிய model-ஐ use பண்றது.**
- **காத்திருக்கக்கூடிய வேலைக்கு real-time விலை குடுக்குறது.**
- **நீளமான prompts-உம் limit இல்லாத outputs-உம்.**
- **Alerts-உம் caps-உம் இல்லாம இருக்குறது.**
- **Quality-ஐ check பண்ணாம cost-ஐ குறைக்குறது.** ஒவ்வொரு மாற்றத்துக்கும் evals-ஐ run பண்ணுங்க.

## செலவை குறைக்குறது தப்பான இலக்கா இருக்கும்போது

- **Feature இன்னும் வேலை செய்யல.** முதல்ல உங்க evals-ல quality-ஐ சரி பண்ணுங்க; அப்புறம் optimise பண்ணுங்க.
- **சேமிப்பு ரொம்ப சின்னது.** மாசம் ₹2,000 சேமிக்க வாரக்கணக்குல engineering வேலையோ, அளக்கக்கூடிய quality குறைவோ தேவையில்ல.
- **Latency அல்லது நம்பிக்கை அதிக முக்கியம்.** அதிக risk இருக்குற ஒரு task-ல, மெதுவான அல்லது அதிக தப்பு பண்ற மலிவான model, support-லயும் இழந்த users-லயும் அதிகமா செலவு வைக்கலாம்.

## Demo-ல இருந்து production-க்கு

- **ஒவ்வொரு call-ஐயும் tag பண்ணுங்க**: feature, user, model, prompt version; tokens-ஐயும் cost-ஐயும் store பண்ணுங்க.
- **ஒவ்வொரு feature-க்கும் budgets** alerts-ஓட set பண்ணுங்க, provider-ல hard limits-ஓட.
- **Cost dashboard-ஐ வாரா வாரம் review பண்ணுங்க**, quality metrics-ஓட சேர்த்து, ஒவ்வொரு model அல்லது prompt மாற்றத்துக்கு அப்புறமும் திரும்ப check பண்ணுங்க.
- **அடிக்கடி திரும்ப விலை பாருங்க.** Providers விலையை குறைக்கிறாங்க, மலிவான models-ஐ release பண்றாங்க; ஆறு மாசத்துக்கு முன்னாடி எடுத்த தேர்வு இப்போ அதிகமா காசு வாங்கலாம்.
- **மலிவான வழியை test பண்ணி வச்சிருங்க**, உதாரணமா ஒரு சின்ன fallback model; செலவு திடீர்னு ஏறினா சீக்கிரமா மாறலாம்.

## Practice பண்ணுங்க

கீழ இருக்குற, production-க்கான LLM applications பத்தின Chip Huyen-ஓட கட்டுரையை, குறிப்பா cost பகுதிகளை படிங்க. இன்னும் ஆழமா போக, அவங்க புத்தகம் *AI Engineering*-ஓட (O'Reilly, 2025) 9, 10-வது chapters inference cost, batch APIs, routing, caching பத்தி பேசுது.

1. உங்க apps-ல ஒண்ணுல feature, user tags-ஓட ஒவ்வொரு call-க்கும் cost logging சேர்த்து, அதிக செலவு வைக்குற feature-ஐ கண்டுபிடிங்க.
2. அந்த feature-ஐ உங்க eval set-ல ஒரு சின்ன model-ஓட test பண்ணி, மாறலாமான்னு முடிவு பண்ணுங்க.
3. அவசரமில்லாத ஒரு job-ஐ batch processing-க்கு மாத்துங்க, அல்லது ஒரு cap-ஐயும் ஒரு alert-ஐயும் சேருங்க.

**இதை நீங்க முடிச்சுட்டீங்கன்னு எப்போ சொல்லலாம்:** ஒவ்வொரு feature-க்கும் ஒவ்வொரு user-க்கும் cost-ஐ காட்டி, உங்க eval scores-ஐ பாதிக்காம செலவை குறைச்ச ஒரு மாற்றத்தை காட்ட முடியும்போது.
