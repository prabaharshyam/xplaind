## இது என்ன

ஒரு **scope of work (SOW)**-ங்கிறது discovery-ஐ ரெண்டு பக்கமும் sign பண்ற ஒரு plan-ஆ மாத்துற document. நீங்க என்ன deliver பண்ணுவீங்க, என்ன பண்ண மாட்டீங்க, எப்போ வரைக்கும், ஒவ்வொரு deliverable-உம் எப்படி accept ஆகும், client என்ன தரணும், changes-உம் பணமும் எப்படி handle ஆகும்னு அது சொல்லும். சில firms இதை statement of work-னு சொல்லுவாங்க. ரெண்டு பேரும் அடிக்கடி ஒரே document-க்கு use ஆகுது, ஆனா சில firms scope of work-ஐ statement of work-ஓட ஒரு section-ஆ பார்க்குறாங்க.

ஒரு SOW பொதுவா ஒரு **master services agreement (MSA)**-க்கு கீழ இருக்கும். MSA ஒரு தடவை sign ஆகும், அதுல பொதுவான legal terms இருக்கும்: confidentiality, liability, data protection, ரெண்டு பக்கத்துல யார் வேணும்னாலும் contract-ஐ எப்படி முடிக்கலாம். அப்புறம் ஒவ்வொரு project-க்கும் அதோட specifics-ஓட தனி SOW வரும். SOW-உம் MSA-வும் முரண்பட்டா, எது ஜெயிக்கும்னு contract பொதுவா சொல்லும், அதனால check பண்ணுங்க. MSA இல்லைன்னா, அந்த legal terms SOW-க்குள்ளயோ ஒரு தனி contract-லயோ போகணும், client-ஓட legal team அவற்றை review பண்ண விரும்புவாங்க.

ஒரு நல்ல AI SOW-ல இந்த பகுதிகள் இருக்கும்:

- **Objective**: பிரச்சனை, அப்புறம் baseline, target-ஓட primary KPI.
- **In scope**, **out of scope**: நீங்க என்ன build பண்ணுவீங்க, செய்வீங்க, என்ன செய்ய மாட்டீங்க, ரெண்டையும் சம அளவு தெளிவா.
- **Deliverables**: ஒவ்வொரு உறுதியான output-உம், உதாரணமா deploy பண்ண ஒரு service, ஒரு eval report, ஒரு runbook, training sessions.
- **Milestones**: தேதிகள், proof of concept (POC), pilot, production-க்கு இடையில இருக்குற stage gates-ஓட.
- **Acceptance criteria**: ஒவ்வொரு deliverable-உம் pass பண்ண வேண்டிய test.
- **Assumptions, dependencies**: நீங்க client-ஐ எதுக்கெல்லாம் நம்பியிருக்கீங்க, தேதிகளோட.
- **Roles**: யார் முடிவு பண்றாங்க, யார் accept பண்றாங்க, யார் review பண்றாங்க, யார் support பண்றாங்க.
- **Change process**: புது requests எப்படி size பண்ணப்பட்டு approve ஆகுது.
- **Risks**: தெரிஞ்ச risks, ஒவ்வொண்ணுக்கும் ஒரு owner-ஓட.
- **Commercial terms**: price, payments, model, cloud costs-ஐ யார் கட்டுறாங்க, எது யாருக்கு சொந்தம்.

இதோ copy பண்ணி fill பண்ணக்கூடிய ஒரு பக்க skeleton. ஒரு section சின்னதா இருந்தாலும் headings-ஐ வெச்சுக்கோங்க; காலியா இருக்குற ஒரு heading-னா நீங்க இன்னும் பதில் சொல்லாத ஒரு கேள்வி.

## இது எப்படி work ஆகுது

### வேற யாரோ run பண்ணக்கூடிய ஒரு test-ஆ acceptance-ஐ எழுதுங்க

"Assistant சரியா பதில் சொல்லுது"-ங்கிறதை accept-உம் பண்ண முடியாது, reject-உம் பண்ண முடியாது. Test பண்ணக்கூடிய ஒரு criterion-க்கு நாலு பகுதிகள் இருக்கு:

1. **பேர் சொன்ன ஒரு test set.** எந்த files அல்லது questions, எத்தனை, யார் தேர்ந்தெடுத்தாங்க.
2. **ஒரு bar.** உதாரணமா, 10 critical fields-ல குறைஞ்சது 95% field accuracy.
3. **ஒரு judge.** சரியான answer எதுன்னு யார் முடிவு பண்றாங்க, கருத்து வேறுபாடுகள் எப்படி தீர்க்கப்படும்.
4. **ஒரு version.** Result எந்த model, configuration-க்கு பொருந்துது.

முதல், மூணாவது பகுதிகளுக்குள்ள ரெண்டு traps இருக்கு. முதல்ல, **test set held out-ஆ இருக்கணும்**. ஒரு proof of concept நடக்கும்போது team failures-ஐ study பண்ணி fix பண்ணும். அது study பண்ண அதே files-ல judge பண்ணப்பட்டா, அந்த files-க்கு ஏத்த மாதிரி fit பண்ணியே gate-ஐ pass பண்ணிடலாம், அப்புறம் புது files-ல மோசமா பண்ணும். அதனால data-வை பிரிங்க: ஒரு பகுதி build பண்ணவும் debug பண்ணவும், இன்னொரு held-out பகுதி, build team-கிட்ட இருந்து பூட்டி வெச்சது, அது தான் gate-ஐ முடிவு பண்ணும். ஒரு useful rule: held-out set-ஐ தேர்ந்தெடுக்குறவர் client பக்கத்து ஆளா இருக்கணும்.

ரெண்டாவது, **பழைய process தானாவே சரியான answer ஆகிடாது**. Ground truth-னா நீங்க score பண்றதுக்கு use பண்ற சரியான answers-ஓட set. நீங்க குறைக்க முயற்சி பண்ற rework-க்கு staff figures-ஐ திரும்ப type பண்றது தான் காரணம்னா, அவங்களோட original entries-லயும் அதே errors இருக்கும். அவற்றை வெச்சு AI-ஐ score பண்ணா, AI சரியா இருந்து அவங்க தப்பா இருந்தப்போ AI-க்கு தண்டனை கிடைக்கும். ஒவ்வொரு test item-ஐயும் client பக்கத்து அனுபவம் உள்ள ரெண்டு staff check பண்ணட்டும், கருத்து வேறுபாடு வந்தா மூணாவது ஒருத்தர் அதை எப்படி தீர்ப்பாருன்னு முன்னாடியே ஒத்துக்கோங்க.

### AI-ஓட நிச்சயமின்மை பத்தி நேர்மையா இருங்க

Model outputs மாறும், client-ஓட உண்மையான documents-ஐ பார்க்குறதுக்கு முன்னாடி யாராலயும் 95%-னு promise பண்ண முடியாது. இதை மறைக்காதீங்க; எழுதி வைங்க. Define பண்ண test set-ல bar என்ன, acceptance-க்கு அப்புறமும் தொடர்ந்து இருக்குற human review என்ன, ஒரு gate miss ஆனா என்ன நடக்கும்னு சொல்லுங்க. மூணு options இருக்கு: ஒரு fix plan-ஓட ஒரு சின்ன extension, work ஆகுறதுக்கு மட்டும் scope-ஐ சுருக்குறது, இல்லைன்னா ஒரு எழுத்துப்பூர்வ report-ஓட நிறுத்துறது. எல்லாரும் நம்பிக்கையா இருக்கும்போதே இதை ஒத்துக்கிட்டா, அப்புறம் வர்ற ஒரு கஷ்டமான பேச்சு அமைதியாவும் சீக்கிரமாவும் முடிஞ்சுடும்.

### Model version-ஐ fix பண்ணுங்க

ஒரு engagement நடக்கும்போதே model providers models-ஐ update பண்ணுவாங்க, retire பண்ணுவாங்க. உதாரணமா, November 2026 நிலவரப்படி, Anthropic-ஓட model deprecations page, publicly release ஆன ஒரு model-ஐ retire பண்றதுக்கு முன்னாடி குறைஞ்சது 60 நாள் notice தர்றதா promise பண்ணுது, retire ஆன model-க்கு அனுப்புற requests fail ஆகும்னு சொல்லுது. மத்த providers-உம் cloud platforms-உம் அவங்களோட சொந்த schedules-ஐ வெச்சிருக்காங்க. ஒரு model-ல accept ஆன system, அதுக்கு பதிலா வர்ற model-ல வேற மாதிரி behave பண்ணலாம்.

அதனால SOW இப்படி சொல்லணும்: acceptance ஒரு பேர் சொன்ன model version-க்கு பொருந்தும். Provider அதை மாத்தினாலோ retire பண்ணாலோ, புது version-ல acceptance test-ஐ திரும்ப run பண்ணுவீங்க. System bar-க்கு கீழ விழுந்தா, fixes-க்கு யார் பணம் கட்டணும்னு SOW சொல்லும். ஒரு common split: உங்க support period-க்குள்ள வர்ற fixes உங்களோடது, அதுக்கு அப்புறம் அவை change requests.

### எது out-னு பேர் சொல்லுங்க, நீங்க நம்பியிருக்குறதுக்கு தேதி போடுங்க

"Out of scope: core banking system கூட integration; Tamil-language documents; mobile app; customer-facing use." பெரும்பாலான disputes யாருமே எழுதி வைக்காத விஷயங்கள்ல இருந்து தான் வருது.

Dependencies-க்கு ஒரு owner, ஒரு தேதி, ஒரு விளைவு வேணும்: "10 July-க்குள்ள client document store-க்கு read access தருவாங்க; ஒவ்வொரு வார தாமதமும் milestone 2-ஐ ஒரு வாரம் தள்ளும்." விளைவு எழுதலைன்னா, client பண்ற தாமதம் சத்தமில்லாம நீங்க miss பண்ண deadline ஆயிடும்.

### சரியான ஆள் accept பண்ணட்டும்

நிறைய இந்திய enterprises-ல SOW-ல procurement அல்லது IT sign பண்ணுவாங்க, ஏன்னா vendor budget அவங்ககிட்ட இருக்கு. ஆனா "ஆமா, இது முடிஞ்சது"-னு சொல்லக்கூடியவர் பொதுவா business owner தான், உதாரணமா head of operations. அவங்க வேற வேற ஆளுங்களா இருந்தா, SOW-ல business owner-ஐ **acceptance authority**-ஆ பேர் போடுங்க. அப்புறம் sign பண்றதுக்கு முன்னாடி acceptance criteria-க்கு அவங்களோட எழுத்துப்பூர்வ ஒப்புதலை வாங்குங்க; ஒரு email reply போதும். இல்லைன்னா document-ல இருக்குற ஒவ்வொரு test-ஐயும் pass பண்ணிட்டும் "எங்களுக்கு தேவைப்பட்டது இது இல்ல"-னு கேக்க வேண்டி வரும்.

### Commercial terms-ஐ முடிவு பண்ணுங்க

Clients முதல்ல எதிர்க்குறது commercial terms-ஐ தான், அதனால technical பகுதிகளுக்கு குடுக்குற அதே கவனத்தோட இதையும் draft பண்ணுங்க. இங்க நீங்க legal advice தரல. உங்க வேலை ஒவ்வொரு கேள்வியையும் எழுப்புறது, ஒரு sensible default-ஐ propose பண்றது, அப்புறம் client-ஓட legal, procurement teams-உம் உங்க சொந்த teams-உம் wording-ஐ review பண்ண விடுறது.

- **Pricing model.** Size பண்ணக்கூடிய வேலைக்கு **fixed price** சரியா இருக்கும், உதாரணமா define பண்ண ஒரு test-ஓட நாலு வார POC. உண்மையான நிச்சயமின்மை இருக்குற வேலைக்கு **time and materials** (effort-க்கு ஏத்த மாதிரி பணம், அடிக்கடி ஒரு cap-ஓட) சரியா இருக்கும், உதாரணமா users changes கேக்கப்போற ஒரு pilot. நிறைய AI projects ரெண்டையும் கலக்கும்: POC-க்கு fixed, pilot-க்கு cap போட்ட time and materials.
- **Gates-ஓட இணைச்ச payments.** உதாரணமா, sign பண்ணும்போது ஒரு share, pass ஆகுற ஒவ்வொரு gate-லயும் ஒரு share. இது பணத்தை evidence-ஓட இணைக்கும், gate 1-ல நிறுத்துற client செஞ்ச வேலைக்கு மட்டும் தான் கட்டுவாங்க.
- **Model, cloud costs.** Model API calls-க்கும் hosting-க்கும் யார் கட்டுறாங்கன்னு சொல்லுங்க. அடிக்கடி இவை client-ஓட சொந்த cloud account-ல ஓடும், client நேரடியா கட்டுவாங்க. நீங்க கட்டி அவங்ககிட்ட pass on பண்ணா, ஒரு monthly cap போடுங்க; அதை தாண்ட எழுத்துப்பூர்வ approval வேணும். ஒரு pilot success ஆனதும் usage சீக்கிரமா வளரலாம்.
- **Intellectual property (IP).** Code, prompts, golden sets, eval harness (tests-ஐ run பண்ற scripts) யாருக்கு சொந்தம்னு சொல்லுங்க. Golden sets client-ஓட data-வையும் experts-ஓட நேரத்தையும் வெச்சு build ஆகுறதால, clients அடிக்கடி அவை தங்களுக்கு சொந்தம்னு எதிர்பார்ப்பாங்க. Project-க்கு முன்னாடியே நீங்க build பண்ண reusable tools-ஐ நீங்க வெச்சுக்க விரும்பலாம். ரெண்டையும் எழுதி வைங்க.
- **Data protection.** இந்தியாவோட Digital Personal Data Protection Act, 2023-படி, personal data ஏன், எப்படி use ஆகணும்னு முடிவு பண்ற client தான் **Data Fiduciary**. அவங்க சார்பா அதை process பண்ற நீங்க ஒரு **Data Processor**; ஒரு valid contract-க்கு கீழ மட்டும் தான் ஒரு processor-ஐ engage பண்ணலாம்னு Act சொல்லுது. அந்த contract பொதுவா ஒரு data processing agreement (DPA). DPDP Rules November 2025-ல notify ஆச்சு, பெரும்பாலான duties May 2027-ல இருந்து apply ஆகும், அதனால இப்போ sign ஆகுற contracts அவற்றுக்கு கீழ தான் ஓடும்.
- **Confidentiality, liability.** இவை பொதுவா MSA-ல இருக்கும். AI-க்கு ஒரு point-ஐ check பண்ணுங்க: system-ஓட output-ஐ use பண்ணி எடுக்குற ஒரு decision-க்கு யார் பொறுப்பு? சுத்தமான பதில்: ஒரு மனுஷ decision-maker-ஐ loop-ல வெச்சுக்கிட்டு, AI எடுக்குற decisions-ஐ out of scope-ல போடுறது, worked example-ல பண்ற மாதிரி.

### சுருக்கமா வைங்க, அப்புறம் ஒரு புது ஆள்கிட்ட test பண்ணுங்க

Business owner main SOW-ஐ பதினைஞ்சு நிமிஷத்துல படிக்க முடியணும். Field lists, test-set design மாதிரி technical details-ஐ ஒரு appendix-ல போடுங்க.

Sign பண்றதுக்கு முன்னாடி, discovery meetings-ல இல்லாத ஒருத்தர்கிட்ட draft-ஐ குடுங்க. மூணு கேள்விகள் கேளுங்க: சரியா என்ன deliver ஆகும், என்ன ஆகாது, ஒவ்வொரு deliverable-உம் எப்படி accept ஆகும்? ஒவ்வொரு தயக்கமும் ஒரு ambiguity-ஐ காட்டும், ஒவ்வொரு ambiguity-உம் acceptance நேரத்துல வரப்போற ஒரு வாக்குவாதம்.

## ஒரு worked example

Chennai lender-ஓட credit-file assistant-க்கான SOW-ல இருந்து ஒரு பகுதி. Vendor budget வெச்சிருக்குற lender-ஓட IT head இதுல sign பண்றாரு; இது head of operations-ஐ acceptance authority-ஆ பேர் போடுது.

> **Objective.** 20 pilot officers-க்கு ஒரு loan file-க்கான median officer நேரத்தை 41 நிமிஷத்துல (baseline, June) இருந்து 22 நிமிஷமா குறைக்கணும், credit committee rework-ஐ 7%-க்கு மேல ஏத்தாம.
>
> **In scope.** Bank statements, salary slips, bureau reports-ல இருந்து (English, PDF, phone photos) ஒத்துக்கிட்ட 24 fields-ஐ extract பண்றது; lender-ஓட template-ல ஒரு draft credit summary; officers-க்கு ஒரு review screen; lender-ஓட Azure tenancy-ல deployment; eval, pilot reports; runbook; ரெண்டு training sessions.
>
> **Out of scope.** Credit decisions, அவை officers-கிட்டயும் credit committee-கிட்டயும் தான் இருக்கும்; customer-facing features; English தவிர வேற மொழிகள்ல இருக்குற documents; ஒரு file export-ஐ தாண்டி loan origination system கூட integration.
>
> **Acceptance (proof of concept, week 4).** Lender-ஓட credit team தேர்ந்தெடுத்த 300 masked பழைய files. 100 development-க்காக build team-கிட்ட share பண்ணப்படும். 200 held out: build team-கிட்ட ஒருபோதும் காட்டப்படாது, gate-ஐ score பண்ண use ஆகும். Held-out files-க்கான ground truth-ஐ ரெண்டு senior credit officers check பண்ணுவாங்க, கருத்து வேறுபாடுகளை credit manager தீர்ப்பாரு. Bar: 10 critical fields-ல குறைஞ்சது 95% field accuracy, ஒவ்வொரு summary-உம் அதோட source pages-ஐ cite பண்ணணும். Appendix-ல பேர் சொன்ன model version-க்கு acceptance பொருந்தும்.
>
> **Dependencies.** 10 July-க்குள்ள ரெண்டு வருஷ masked files-க்கு read access; வாரத்துக்கு 4 மணி நேரம் ஒரு senior credit officer. ஒவ்வொரு வார தாமதமும் milestone 2-ஐ ஒரு வாரம் தள்ளும்.
>
> **Change process.** புது requests log பண்ணப்பட்டு, மூணு working days-க்குள்ள size பண்ணப்பட்டு, வேலை ஆரம்பிக்குறதுக்கு முன்னாடி head of operations எழுத்துப்பூர்வமா approve பண்ணணும்.
>
> **Commercial.** POC ஒரு fixed fee-ல; pilot ஒரு cap-ஓட time and materials-ல; payments signing-லயும் ரெண்டு gates-லயும் பிரிக்கப்படும். Model, hosting costs lender-ஓட Azure account-ல ஓடும், lender கட்டுவாங்க. Golden sets, prompts, project code lender-க்கு சொந்தம்; எங்களோட pre-existing tools-ஐ நாங்க வெச்சுக்குவோம். DPDP Act-க்கு கீழ ஒரு data processing agreement attach பண்ணப்பட்டிருக்கு.

ஒவ்வொரு clause-உம் எதை தடுக்குதுன்னு கவனிங்க. Held-out split, team debug பண்ண files-க்கு fit பண்ணி gate-ஐ pass பண்றதை தடுக்குது. ரெண்டு senior officers, பழைய retyping errors-க்கு test reward குடுக்குறதை தடுக்குறாங்க. Production-ல usage வளரும்போது திடீர்னு ஒரு bill வர்றதை cost clause தடுக்குது.

**இது எப்படி பலன் தந்துச்சு.** Week 7-ல, pilot நடக்கும்போது, collections head borrower correspondence-க்கு summaries கேட்டாரு. SOW scope-ஐயும் change process-ஐயும் பேர் சொல்லியிருந்ததால, அந்த request log பண்ணப்பட்டு கிட்டத்தட்ட நாலு வாரம்னு size பண்ணப்பட்டுச்சு. அதுக்கு புது document types, புது users, ஒரு புது golden set தேவைப்பட்டுச்சு. Head of operations அதை production gate-க்கு அப்புறம் phase 2-ஆ approve பண்ணாரு; credit-file வேலையை அது சத்தமில்லாம தாமதப்படுத்த விடல. Phase 2 அப்புறம் ரெண்டாவது contract ஆச்சு. Scope creep-ஐ manage பண்றது பத்தின lesson அந்த வாரத்தை விரிவா follow பண்ணுது.

## பொதுவா பண்ற தப்புகள்

- **மங்கலான acceptance.** "நல்லா work ஆகுது"-ங்கிறது முடிவில்லாத வாக்குவாதத்துக்கு வழி வைக்கும். Test set, bar, judge, model version-ஐ பேர் சொல்லுங்க.
- **Tuning set-லயே test பண்றது.** Team debug பண்ண files-ல measure பண்ண acceptance, quality-ஐ இருக்குறதை விட அதிகமா காட்டும். Build team ஒருபோதும் பார்க்காத ஒரு பகுதியை held out-ஆ வைங்க.
- **பழைய process-ஐ answer key-ஆ நம்புறது.** நீங்க சரி பண்ற errors original entries-லயே இருக்கும். Experts ground truth-ஐ check பண்ணட்டும்.
- **எது out-னு சொல்லாம இருக்குறது.** எழுதாத assumptions disputes ஆகும்.
- **தேதி இல்லாத dependencies.** அப்போ client தாமதங்கள் நீங்க miss பண்ண deadlines ஆயிடும்.
- **Gate miss ஆனா என்ன பண்றதுன்னு plan இல்லாம இருக்குறது.** வேலை ஆரம்பிக்குறதுக்கு முன்னாடியே extend, narrow, இல்லைன்னா stop-னு ஒத்துக்கோங்க.
- **Model changes-ஐ கண்டுக்காம இருக்குறது.** Acceptance-க்கு அப்புறம் வர்ற ஒரு provider update quality-ஐ மாத்தலாம். Version-ஐ fix பண்ணுங்க, re-acceptance எப்படி நடக்கும்னு ஒத்துக்கோங்க.
- **முடிவில்லாத வேலைக்கு fixed price.** தெரியாத விஷயங்கள் நிறைஞ்ச ஒரு pilot-க்கு fixed fee போட்டா, corners cut பண்ணவோ ஒவ்வொரு request-க்கும் வாக்குவாதம் பண்ணவோ தள்ளப்படுவீங்க.
- **யாருக்கும் சொந்தமில்லாத model costs.** API bill-க்கு யாரும் owner இல்லைன்னா, முதல் பெரிய invoice ஒரு dispute ஆயிடும்.
- **IP பத்தி பேசாம இருக்குறது.** நீங்க reuse பண்ண plan பண்ண golden sets உட்பட எல்லாமே தங்களுக்கு சொந்தம்னு clients நினைச்சுக்குவாங்க. Ownership-ஐ எழுதி வைங்க.
- **Sign பண்றவர் accept பண்றவர் இல்ல.** Procurement sign பண்ணும், operations reject பண்ணும். Acceptance authority-ஐ பேர் சொல்லி, criteria-க்கு அவங்க ஒப்புதலை வாங்குங்க.

## Practice பண்ணுங்க

Atlassian-ஓட project scope guide-ஐயும் GOV.UK-ஓட user stories guide-ஐயும் படிங்க. அப்புறம்:

1. மேல இருக்குற skeleton-ஐ copy பண்ணி, உங்க discovery, KPI exercises-ல வந்த use case-க்கு fill பண்ணுங்க. Main document-ஐ ரெண்டு பக்கத்துக்குள்ள வைங்க.
2. மூணு deliverables-க்கு acceptance criteria எழுதுங்க. ஒவ்வொண்ணும் test set-ஐயும் அது எப்படி held out-ஆ இருக்குன்னும், bar, judge, model version-ஐயும் பேர் சொல்லணும்.
3. Commercial section-ஐ எழுதுங்க: ஒவ்வொரு stage-க்கும் fixed price-ஆ time and materials-ஆன்னு தேர்ந்தெடுத்து, ஏன்னு ஒரு வாக்கியத்துல சொல்லுங்க. Model costs-ஐ யார் கட்டுறாங்க, golden set யாருக்கு சொந்தம்னு சொல்லுங்க.
4. உங்க discovery notes-ஐ பார்க்காத ஒரு friend கூட swap பண்ணுங்க. மூணு stranger questions-ஐ அவங்ககிட்ட கேட்டு, அவங்க கண்டுபிடிக்குற ஒவ்வொரு ambiguity-ஐயும் fix பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** room-ல இல்லாத ஒருத்தர்கிட்ட உங்க SOW-ஐ குடுத்து, என்ன deliver ஆகும், என்ன ஆகாது, ஒவ்வொரு பகுதியும் எப்படி accept ஆகும், எதுக்கு யார் கட்டுறாங்கன்னு அவங்களை சரியா சொல்ல வைக்க முடியும்.
