## இது என்ன

ஒரு **security questionnaire**, அதை vendor risk assessment-ன்னும் சொல்லுவாங்க, ஒரு supplier-க்கு data அல்லது systems access குடுக்குறதுக்கு முன்னாடி ஒரு enterprise அதை check பண்ற வழி. அது client-ஓட சொந்த spreadsheet-ஆ இருக்கலாம்; Cloud Security Alliance-ஓட **CAIQ** (Consensus Assessments Initiative Questionnaire), AI systems-க்கான அதோட புது **AI-CAIQ**, அல்லது Shared Assessments-ஓட **SIG** மாதிரி ஒரு standard set-ஆ இருக்கலாம்; இல்லைன்னா நீங்க பதில்களை type பண்ணி evidence upload பண்ற ஒரு vendor-risk portal-ஆ இருக்கலாம்.

கேள்விகள் கிட்டத்தட்ட ஒவ்வொரு தடவையும் அதே விஷயங்களை தான் cover பண்ணும்: policies, reports, access control, encryption, penetration tests, logging, incident response, backups, data location, retention, sub-processors. இப்போ ஒரு AI section-உம் இருக்கு: client data-வை வச்சு training, model providers, prompt injection, human oversight, change testing.

### ஒரு reviewer பேர் சொல்லிக் கேக்குற reports, standards

- **SOC 2**-னா உங்க controls பத்தி ஒரு independent auditor குடுக்குற report. **Type I**, ஒரு குறிப்பிட்ட நேரத்துல அவை சரியா design பண்ணப்பட்டிருந்துச்சுன்னு சொல்லும்; **Type II**, பல மாசம் நீடிக்கிற ஒரு review period முழுக்க அவை work-உம் ஆச்சுன்னு சொல்லும், அதனால reviewers அதை தான் விரும்புவாங்க. அந்த period ரொம்ப நாளைக்கு முன்னாடியே முடிஞ்சிருந்தா, அதுக்கப்புறம் இருக்குற நேரத்தை cover பண்ற ஒரு "bridge letter" கேப்பாங்கன்னு எதிர்பாருங்க. SOC 2 ஒரு attestation report, certificate இல்ல: "நாங்க SOC 2 certified"-ன்னு எழுதாம, "எங்ககிட்ட SOC 2 Type II report இருக்கு"-ன்னு எழுதுங்க.
- **ISO/IEC 27001** ஒரு information security management system-ஐ certify பண்ணும்; **ISO/IEC 42001** ஒரு AI management system-ஐ certify பண்ணும், அதாவது ஒரு company தான் build பண்ற அல்லது use பண்ற AI-ஐ எப்படி govern பண்ணுதுன்னு.
- **NIST AI Risk Management Framework** ஒரு voluntary US framework. அதுக்கு எதிரா யாரும் certify ஆகுறது இல்ல; உங்க process அதுக்கு எப்படி map ஆகுதுன்னு நீங்க காட்டலாம்.

## இது எப்படி work ஆகுது

### ஒரு answer library build பண்ணுங்க

பெரும்பாலான கேள்விகள் clients-க்கு இடையில repeat ஆகும். Approved answers-ஓட review பண்ணின ஒரு library வச்சுக்குங்க; ஒவ்வொண்ணுக்கும் ஒரு **owner** (பொதுவா அந்த control-ஐ நடத்துறவங்க), ஒரு **last-reviewed date**, **evidence links** (policies, SOC 2 report, penetration test summary, architecture diagrams, test results) இருக்கணும். ஒவ்வொரு புது questionnaire-க்கும் library-ல இருந்து பதில் சொல்லுங்க, அப்புறம் புது பதில்களை திரும்ப அதுல சேருங்க. Architecture மாறும்போது, உதாரணமா ஒரு புது model provider அல்லது tracing tool வந்தா, பாதிக்கப்படுற ஒவ்வொரு பதிலையும் அதே வாரத்துல சரி பண்ணுங்க. போன வருஷ system பத்தின பதில் ஒரு தப்பான பதில் தான்.

Repeat வேலையை இன்னும் குறைக்க, CAIQ மாதிரி ஒரு standard questionnaire-ஐ ஒரு தடவை fill பண்ணி, client தன்னோடதை அனுப்புறதுக்கு முன்னாடியே அதை offer பண்ணுங்க. அப்புறம் ஒரு **trust centre** நடத்துங்க: ஒரு public security summary, கூடவே approved clients ஒரு non-disclosure agreement-ன் கீழ SOC 2 report-ஐயும் மத்த evidence-ஐயும் download பண்ற ஒரு gated area.

### ஒரு follow-up-ஐ தாங்குற பதில்களை எழுதுங்க

வெறும் "Yes" follow-ups-ஐ கூப்பிடும், ஒரு overclaim contract breach ஆகிடலாம். ஒரு நல்ல பதில் என்ன, எப்படி, எங்கன்னு சொல்லும். ஒரு control பாதி தான் இருந்தா "Partially"-ன்னு சொல்லுங்க: என்ன இருக்கு, என்ன இல்ல, மீதிக்கு date என்ன. எல்லாம் இருக்குன்னு claim பண்ற vendor-ஐ விட, "இன்னும் இல்ல, இதோ plan"-ங்குறதை reviewers ரொம்ப ரொம்ப அதிகமா நம்புவாங்க.

| கேள்வி | Weak பதில் | Strong பதில் |
| --- | --- | --- |
| Encryption at rest இருக்கா? | "Yes" | "AES-256, keys Azure Key Vault-ல, Central India region; keys வருஷா வருஷம் rotate ஆகும்" |
| Data-வை training-க்கு use பண்றீங்களா? | "No" | "Provider X-ஓட enterprise terms எங்க API data-வை வச்சு training பண்றதை exclude பண்ணுது; abuse checks-க்காக அது requests-ஐ 30 நாள் வச்சிருக்கும்; clause attach பண்ணியிருக்கோம்" |
| Prompt injection? | "நாங்க industry-standard AI security use பண்றோம்" | "நாங்க risk-ஐ குறைக்குறோம்: least-privilege tools, outbound actions-க்கு approval, CI-ல run ஆகுற injection test set; latest results attach பண்ணியிருக்கோம்" |
| Pen testing? | "Yes" | "Web app-க்கு வருஷத்துக்கு ஒரு external test; 15 January 2027-க்கு book ஆன test-ல AI endpoints இருக்கு" |

இங்க இருக்குற provider, retention period, dates எல்லாம் உதாரணங்கள் தான்; உங்களோடதை உங்க சொந்த contracts-ல இருந்து எழுதுங்க.

### AI section

கிட்டத்தட்ட ஒவ்வொரு AI questionnaire-லயும் இந்த கேள்விகளை எதிர்பாருங்க, பதில்களை current-ஆ வச்சுக்குங்க:

- **Providers, terms:** எந்த providers, regions, training பத்தியும் requests-ஐ எவ்வளவு நாள் வச்சிருப்பாங்கன்னும் contract என்ன சொல்லுது. ஒவ்வொரு provider-ஓட terms-ஐயும் கடைசியா எப்போ படிச்சீங்கன்னு date-ஐ record பண்ணுங்க, ஏன்னா terms மாறும்.
- **அனுப்புற data:** எந்த fields model-க்கு போகுது, personal data முதல்ல mask ஆகுதா.
- **எல்லா இடத்துலயும் retention:** prompts app-ல மட்டும் இல்ல, provider-கிட்டயும், உங்க tracing tool, logs, backups-லயும் இருக்கும். எல்லாத்துக்கும் பதில் சொல்லுங்க.
- **Prompt injection, actions:** model எந்த tools-ஐ call பண்ண முடியும், என்ன permissions-ஓட, எந்த actions-க்கு ஒரு ஆளோட approval வேணும்.
- **Guardrails, audit logs, kill switches,** test results-ஓட.
- **Change control:** ஒரு புது model அல்லது prompt-ஐ release-க்கு முன்னாடி எப்படி test பண்றீங்க.

### Sub-processors, data flows

Client data-வை தொடுற ஒவ்வொரு third party-யையும் list பண்ணுங்க: cloud, model provider, vector database, tracing tool, email service, பதில்களை draft பண்ண நீங்க use பண்ற எந்த AI tool-உம். ஒவ்வொண்ணுக்கும் purpose-உம் data location-உம் குடுங்க. ஒரு புது sub-processor-ஐ client எதிர்க்கலாம்னு contracts பல நேரம் அனுமதிக்கும், அதனால ஒண்ணு சேர்க்கணும்னா முதல்ல client-கிட்ட சொல்லணும். ஒரு பக்க **data flow map** (data எங்க உள்ள வருது, அது போற ஒவ்வொரு store, service, ஒவ்வொண்ணோட region, அதை யாரு பாக்க முடியும்) தனியாவே நிறைய கேள்விகளுக்கு பதில் சொல்லிடும்.

### இந்திய regulatory கேள்விகள்

அனுபவமுள்ள reviewers-க்கு தெரிஞ்ச அஞ்சு gotchas:

- **எல்லா bank data-வும் இந்தியாவுக்குள்ள தான் இருக்கணும்னு எந்த RBI rule-உம் சொல்லல.** தெளிவான legal rule payment system data-வை தான் cover பண்ணுது. DPDP Act, அனுமதிச்ச countries-ஐ list பண்றதுக்கு பதிலா, அரசாங்கம் பேர் சொல்ற countries-க்கு transfers-ஐ restrict பண்ண அனுமதிக்குது. இருந்தாலும் பெரும்பாலான banks policy-படி இந்திய hosting-ஐ கேக்கும், அதனால அதை எதிர்பாருங்க, ஆனா "வெளிநாட்டுல எந்த data-வும் இருக்கக் கூடாதுன்னு RBI தடை பண்ணுது"-ன்னு எழுதவே எழுதாதீங்க.
- **Act-ஓட சொந்த வார்த்தைகளை use பண்ணுங்க.** DPDP Act **Data Fiduciary** (bank), **Data Processor** (நீங்க), **Data Principal** (customer), **personal data breach** பத்தி பேசுது. "Sub-processor", "controller" ரெண்டும் நிறைய questionnaires copy பண்ற GDPR-style contracts-ல இருந்து வருது. கேட்ட மாதிரியே கேள்விக்கு பதில் சொல்லுங்க, ஆனா legal positions-ஐ Act-ஓட terms-ல சொல்லுங்க.
- **Dates தெரிஞ்சுக்குங்க.** DPDP Rules November 2025-ல notify ஆச்சு; security safeguards, breach intimation உட்பட பெரும்பாலான duties May 2027-ல இருந்து apply ஆகும். இப்போ sign பண்ற contracts அந்த date-ஐ தாண்டியும் ஓடும், அதனால banks இப்பவே கேக்குறாங்க.
- **Clocks வேற வேற ஆளுங்களோடது.** Bank-ஓட 6-மணி நேர RBI report, bank incident-ஐ detect பண்ணின நேரத்துல இருந்து ஓடும், அதனால நீங்க லேட்டா சொன்னா bank அதோட deadline-ஐ miss பண்ணிடும். உங்க on-call team ஒரு ஞாயிற்றுக்கிழமை ராத்திரி 2 மணிக்கும் meet பண்ண முடியுற notice window-க்கு மட்டும் ஒத்துக்குங்க. DPDP Act-ன் கீழ Data Fiduciary தான் Data Protection Board-க்கும் பாதிக்கப்பட்டவங்களுக்கும் சொல்லும்; உங்க வேலை bank-க்கு வேகமா சொல்றது.
- **Versions மாறுபடும்.** Small finance banks, NBFCs, மத்த regulated entities-க்கு அவங்களுக்குன்னு தனி versions இருக்கு, பழைய questionnaires IT services outsourcing பத்தின 2023 Master Direction-ஐ cite பண்ணலாம். Substance-க்கு பதில் சொல்லுங்க, bank confirm பண்ற version-ஐ cite பண்ணுங்க, எந்த compliance claim-ஐயும் உங்க legal adviser approve பண்ணட்டும். CERT-In-empanelled auditor பண்ற penetration tests-ஐ banks பல நேரம் கேப்பாங்க, அதனால book பண்றதுக்கு முன்னாடி கேட்டுக்குங்க.

### Evidence, drafting, follow-up calls

முழு SOC 2 report மாதிரி sensitive evidence-ஐ non-disclosure agreement-ன் கீழ, expire ஆகுற ஒரு link மூலமா மட்டும் share பண்ணுங்க. பழசாகிப் போற text-ஐ paste பண்றதுக்கு பதிலா living documents-க்கு link குடுங்க. Injection, permission tests-ஓட CI results-ஐ ஒரு சின்ன PDF-ஆ export பண்ற மாதிரி வச்சுக்குங்க: reviewers எல்லாத்தையும் விட கம்மியா பாத்திருக்கிறது AI evidence தான்.

ஒரு model உங்க library, design notes-ல இருந்து பதில்களை draft பண்ணலாம். மூணு rules. அது library-யையும் attach பண்ணின documents-ஐயும் மட்டும் தான் use பண்ணணும், use பண்ணின library ids-ஐ cite பண்ணணும். பேர் குறிப்பிட்ட ஒருத்தர் ஒவ்வொரு பதிலையும் approve பண்ணணும், அப்போ தான் இட்டுக்கட்டின எந்த control-உம் வெளிய போகாது. அப்புறம் client-ஓட questionnaire confidential: உங்க sub-processor list-ல ஏற்கனவே இருக்குற approved provider, region-ஓட மட்டும் draft பண்ணுங்க. ஒரு bank-ஓட questionnaire-ஐ personal chatbot account-ல paste பண்றதே ஒரு data-handling failure தான்.

Follow-up calls-க்கு, system தெரிஞ்ச engineer-ஐயும் data flow map-ஐயும் கூட்டிட்டு போங்க, உங்களுக்கு தெரிஞ்சதுக்கு மட்டும் பதில் சொல்லுங்க, check பண்ண வேண்டியிருந்த எதையும் அதே நாள்ல அனுப்புங்க.

```python
import yaml
from datetime import date, timedelta

def load(path="security-answers.yaml"):
    with open(path) as f:
        return yaml.safe_load(f)

def stale(answers, today=None, max_age_days=180):
    today = today or date.today()
    cutoff = today - timedelta(days=max_age_days)
    return [(a["id"], a["owner"]) for a in answers
            if a["reviewed"] < cutoff or not a.get("evidence")]

def suggest(question, answers, top=3):
    words = set(question.lower().split())
    def overlap(a):
        text = a["question"] + " " + " ".join(a["tags"])
        return len(words & set(text.lower().split()))
    return [a["id"] for a in sorted(answers, key=overlap, reverse=True)[:top]]

answers = load()
print(stale(answers, today=date(2026, 11, 28)))
print(suggest("Are prompts retained in logs?", answers, top=1))
```

Candidates-ஐ கண்டுபிடிக்க `suggest`-ஐ, அல்லது பெரிய library-க்கு embeddings-ஐ use பண்ணுங்க, ஆனா ஒவ்வொரு match-ஐயும் ஒரு ஆள் check பண்ணணும்: கிட்டத்தட்ட சரியா இருக்குற ஒரு பதில் கூட தப்பா இருக்கலாம்.

## ஒரு worked example

இந்த example ஒரு விளக்கத்துக்கு தான்: counts, dates method-ஐ காட்டுது, உண்மையான deal-ஐ இல்ல.

ஒரு successful pilot-க்கு அப்புறம், Bengaluru-ல ஒரு AI startup-க்கு ஒரு பெரிய private bank-ல இருந்து 240 கேள்வி spreadsheet வருது, ரெண்டு வாரத்துல குடுக்கணும். FDE Meera coordinate பண்றாங்க.

**Day 1: triage.** Library 170 கேள்விகளுக்கு match ஆகுது. மீதி 70-ல 40 AI-specific, 30 bank-specific. ஒவ்வொரு group-க்கும் ஒரு owner-உம் due date-உம் கிடைக்குது.

**Days 2 முதல் 6: AI கேள்விகள்.** அவங்க உண்மையான design documents-ல (data flow map, gateway configuration, masking rules, guardrail tests, approval step, audit log schema) இருந்து பதில் சொல்றாங்க, ஒவ்வொரு பதிலும் ஒரு document section-ஐ cite பண்ணுது.

"Prompts-ஐ retain பண்றீங்களா?"-ங்குற கேள்வியை check பண்ணும்போது, tracing tool முழு prompts-ஐயும் இந்தியாவுக்கு வெளிய வச்சிருக்குன்னு கண்டுபிடிக்குறாங்க; library-ல இருந்த பதில் பழசாகியிருந்துச்சு. Team tracing-ஐ ஒரு இந்திய region-க்கு மாத்தி, account numbers-ஐ முதல்ல mask பண்ணுது. Meera பதில், sub-processor list, data flow map மூணையும் அதே நாள் update பண்றாங்க.

**Days 3 முதல் 9: bank-specific கேள்விகள்.** Startup-ஓட legal adviser கூட சேர்ந்து, அவங்க அந்த கேள்விகளை மேல இருக்குற table-ல இருக்குற rules-க்கு map பண்றாங்க:

- **Outsourcing:** startup audit, inspection clauses-ஐ ஏத்துக்குது, அதோட cloud, model provider, tracing tool-ஐ subcontractors-ஆ list பண்ணுது.
- **Incident notice:** bank 2 மணி நேரத்துக்குள்ள notice கேக்குது. Meera on-call lead கூட confirm பண்ணிட்டு, runbook-ல CERT-In step பக்கத்துலயே ஒரு "bank-கிட்ட சொல்லு" step சேர்க்குறாங்க.
- **Logs:** retention இந்திய region-ல 180 நாளா set ஆகுது.
- **DPDP:** பதில்கள் startup-ஐ bank-ஓட Data Processor-ஆ விவரிக்குது, draft data processing agreement-ஐயும் erasure procedure-ஐயும் attach பண்ணுது.

**Days 10 முதல் 12: gaps, review.** ரெண்டு உண்மையான gaps தெரியுது: AI endpoints-க்கு penetration test இல்ல, model misbehaviour-க்கு incident plan இல்ல. ரெண்டுக்கும் அவங்க "Partially"-ன்னு பதில் சொல்றாங்க, ஒரு CERT-In-empanelled firm கூட book பண்ணின test-ஐயும் ஒரு draft runbook-ஐயும் attach பண்றாங்க. பேர் குறிப்பிட்ட ஒருத்தர் ஒவ்வொரு பதிலையும் review பண்றாங்க.

**Outcome.** Bank ரெண்டு conditions-ஓட ஏத்துக்குது: 60 நாளுக்குள்ள test report, go-live-க்கு முன்னாடி final runbook. 70 புது பதில்களும் owners, dates-ஓட library-க்கு போகுது, அதனால அடுத்த bank இன்னும் அதிக matches-ஓட ஆரம்பிக்கும்.

## பொதுவான தப்புகள்

- **Overclaiming.** பொய்யான ஒரு "Yes" legal problem ஆகிடலாம். "Partially"-ன்னு சொல்லி plan-ஐ குடுங்க.
- **தெளிவில்லாத AI பதில்கள்.** "நாங்க industry-standard AI security use பண்றோம்"-க்கு எந்த அர்த்தமும் இல்ல. Providers, regions, terms, controls-ஐ பேர் சொல்லுங்க.
- **ஒரு sub-processor-ஐயோ data-வோட ஒரு copy-யையோ விட்டுடுறது,** போன மாசம் சேர்த்த, prompts-ஐ வச்சிருக்குற ஒரு tracing tool மாதிரி, அல்லது பதில்களை draft பண்ண use பண்ண AI tool மாதிரி.
- **Owner அல்லது review date இல்லாத பதில்கள்,** அதனால ஒரு பதில் உண்மை இல்லாம போகும்போது யாரும் கவனிக்க மாட்டாங்க.
- **AI draft பண்ணின பதில்களை check பண்ணாம அனுப்புறது.**
- **"SOC 2 certified" அல்லது "NIST AI RMF certified"-ன்னு சொல்றது.** SOC 2 ஒரு audit report, NIST framework-க்கு certification-ஏ கிடையாது.
- **இந்திய law-ஐ லூசா சொல்றது.** "நாங்க RBI compliant" ரொம்ப vague, "RBI எல்லா data-வும் இந்தியாவுல இருக்கணும்னு சொல்லுது" தப்பு. எந்த rule, நீங்க என்ன பண்றீங்க, எந்த evidence அதை காட்டுதுன்னு சொல்லுங்க.
- **On-call team meet பண்ண முடியாத ஒரு notice window-ஐ promise பண்றது.**

## முழு library தேவையில்லாத நேரங்கள்

- **உங்க முதல் ஒண்ணு ரெண்டு questionnaires**: அவற்றுக்கு கவனமா பதில் சொல்லுங்க, அப்புறம் அந்த பதில்களை library-ஆ மாத்துங்க.
- சில கேள்விகளை email-ல கேக்குற **சின்ன clients**: நேரடியா பதில் சொல்லுங்க, அதே அளவு துல்லியமா.
- Company-ஓட சொந்த security review process cover பண்ற **internal projects**.

## Demo-ல இருந்து production-க்கு

- **Library-ஐ version control-ல வச்சுக்குங்க**, பழசான பதில்களை மாசா மாசமும் ஒவ்வொரு architecture மாற்றத்தப்பவும் flag பண்ணுங்க.
- **Sub-processor list-ஐயும் data flow map-ஐயும் சேர்த்தே maintain பண்ணுங்க**, ஒவ்வொரு service-க்கும் purpose, location-ஓட.
- **ஒரு இந்திய rules sheet வச்சுக்குங்க** (rule, date, யாரை கட்டுப்படுத்துது, உங்க evidence), regulators புது directions வெளியிடும்போது legal-ஐ அதை review பண்ண வைங்க.
- **ஒவ்வொரு questionnaire-ஐயும் track பண்ணுங்க**: date, அனுப்பின answer version, promise பண்ணின follow-ups.
