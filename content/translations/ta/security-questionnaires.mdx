## இது என்ன

**Security questionnaire** (vendor risk assessment) என்பது, ஒரு enterprise, ஒரு supplier-க்கு data அல்லது systems-ஐ access தர்றதுக்கு முன்னாடி அவங்களை check பண்ற வழி. அது client-ஓட சொந்த spreadsheet-ஆ இருக்கலாம், Cloud Security Alliance-ஓட CAIQ அல்லது SIG questionnaire மாதிரி ஒரு standard-ஆ இருக்கலாம், இல்ல ஒரு vendor-risk platform-ஓட portal-ஆ இருக்கலாம். கேள்விகள் இதை cover பண்ணும்:

- company-ஓட security programme, policies, certifications (SOC 2, ISO 27001);
- access control, authentication, staff vetting;
- transit-ல, rest-ல encryption, key management;
- network security, vulnerability management, penetration tests;
- logging, monitoring, incident response;
- business continuity, backups, disaster recovery;
- data handling: location, retention, deletion, sub-processors;
- இப்போ அதிகமா, AI-specific கேள்விகளும்: client data-ல training, model providers, prompt injection, output review, human oversight.

```flow
Questionnaire, 240 கேள்விகள் -> Answer library
Answer library -[170 match ஆச்சு]-> Evidence links-ஓட review பண்ணின answers
Answer library -[40 AI-specific]-> Design docs-ல இருந்து பதில் | data flow map, gateway config, masking rules, guardrail tests, approval step, audit log schema
Answer library -[30 client-specific]-> Legal-ஓட draft | RBI outsourcing, localisation
Design docs-ல இருந்து பதில் -> Gaps: "Partially" + தேதியிட்ட plan
Legal-ஓட draft -> Gaps: "Partially" + தேதியிட்ட plan
Gaps: "Partially" + தேதியிட்ட plan -[புது answers திரும்ப சேர்க்கப்படுது]-> Answer library
```

இந்த lesson, Bengaluru-ல ஒரு AI startup-ல FDE-ஆ இருக்குற Meera, ஒரு வெற்றிகரமான pilot-க்கு அப்புறம் ஒரு பெரிய private bank-ஓட questionnaire-க்கு பதில் சொல்றதை follow பண்ணுது.

## இது எப்படி work ஆகுது

**ஒரு answer library build பண்ணுங்க.** பெரும்பாலான கேள்விகள் clients-க்கு இடையில repeat ஆகும். Approved answers-ஓட review பண்ணின ஒரு library வச்சுக்கோங்க; ஒவ்வொண்ணுக்கும் ஒரு owner, last-checked date, evidence links (policy documents, SOC 2 report, penetration test summary, architecture diagrams) இருக்கணும். புது questionnaires-க்கு அதுல இருந்து பதில் சொல்லுங்க, review-க்கு அப்புறம் புது answers-ஐ திரும்ப சேருங்க.

**துல்லியமா, உண்மையா பதில் சொல்லுங்க.** விவரம் இல்லாத "Yes" follow-up கேள்விகளை கூப்பிடும்; ஒரு overclaim contract breach-ஆ மாறலாம். நல்ல answers என்ன, எப்படி, எங்கன்னு சொல்லும்: "எல்லா data-வும் rest-ல AES-256-ல encrypt ஆகுது, keys Central India-ல Azure Key Vault-ல இருக்கு; keys வருஷத்துக்கு ஒரு தடவை rotate ஆகும்."

**Partial மற்றும் planned.** விளக்கத்தோடும் மீதிக்கு ஒரு தேதியோடும் "Partially" ஏத்துக்கலாம்; தப்பான "Yes" ஏத்துக்க முடியாது.

**AI section.** திரும்ப திரும்ப கேக்கப்படுற பதில்களை தயாரா வச்சுக்கோங்க:

- எந்த model providers, regions use ஆகுது, எந்த terms-ல (data-ல training, retention)?
- Model-க்கு என்ன data அனுப்பப்படுது, personal data mask ஆகுதா?
- Prompt injection எப்படி கையாளப்படுது, risky actions-க்கு outputs-ஐ மனிதர்கள் review பண்றாங்களா?
- என்ன guardrails, audit logs, kill switches இருக்கு?
- Release-க்கு முன்னாடி model அல்லது prompt மாற்றங்கள் எப்படி test ஆகுது?

**Sub-processors.** Client data-ஐ தொடுற ஒவ்வொரு third party-யையும் (cloud, model provider, tracing tool, email service) purpose-ஓடும் location-ஓடும் list பண்ணுங்க. புதுசா வர்றவங்களை எதிர்க்குற உரிமை clients-க்கு பெரும்பாலும் இருக்கும்.

**Evidence, NDAs.** முழு SOC 2 report மாதிரி sensitive evidence-ஐ, non-disclosure agreement-ஓட, expire ஆகுற secure link வழியா share பண்ணுங்க.

**பலவீனமான, வலுவான answers:**

| கேள்வி | பலவீனம் | வலுவானது |
| --- | --- | --- |
| Rest-ல encryption? | "Yes" | "AES-256, keys Central India-ல Azure Key Vault-ல; வருஷத்துக்கு ஒரு தடவை rotate" |
| Data training-க்கு use ஆகுதா? | "No" | "Provider X-ஓட contract client data-ல training-ஐ விலக்குது; retention 30 நாள்; clause 7.2 attach பண்ணியிருக்கோம்" |
| Prompt injection? | "நாங்க industry-standard AI security use பண்றோம்" | "Least-privilege tools, outbound actions-க்கு approval, CI-ல injection test set; சமீபத்திய results attach" |
| Pen testing? | "Yes" | "Web app-க்கு வருஷாந்திர external test; அடுத்த மாசம் book பண்ணின test-ல AI endpoints சேர்க்கப்பட்டிருக்கு" |

**Library-ஐ உயிரோட வச்சுக்கிறது.** ஒவ்வொரு answer-க்கும் ஒரு owner (பொதுவா அந்த control-ஐ run பண்றவங்க), ஒரு review date குடுங்க. Architecture மாறினா, உதாரணம் புது model provider அல்லது புது tracing tool, library-ல பாதிக்கப்படுற answers-ஐ தேடி அதே வாரத்துல update பண்ணுங்க. ஒவ்வொரு questionnaire-க்கு அப்புறமும் புது கேள்விகளையும் அவற்றோட review பண்ணின answers-ஐயும் சேருங்க. இப்படி maintain பண்ணின library, ரெண்டு வாரம் அவசரப்பட்டு ஓடுறதை, சில நாள் கவனமான வேலையா மாத்தும்.

**Client-ஓட reviewers-ஓட வேலை செய்றது.** Follow-up calls-ஐ எதிர்பாருங்க. System தெரிஞ்ச engineer-ஐயும், data flow map-ஐயும், evidence-ஐயும் கொண்டு வாங்க. உங்களுக்கு தெரிஞ்சதுக்கு மட்டும் பதில் சொல்லுங்க, check பண்ண வேண்டியதை எழுதி வச்சுக்கோங்க, அதே நாள் அனுப்புங்க. எல்லாத்தையும் செய்யுறோம்னு சொல்ற vendors-ஐ விட, "இதை இன்னும் பண்றதில்ல, plan இதோ"ன்னு சொல்ற vendors-ஐ reviewers அதிகம் நம்புவாங்க.

**Answer library-ஐ data-ஆ வைக்கிறது.** Answers-ஐ team code மாதிரி review பண்ணுற ஒரு file-ல வைங்க, bookkeeping-ஐ ஒரு script பாத்துக்கும்:

```yaml
# security-answers.yaml
- id: enc-at-rest
  question: Is customer data encrypted at rest?
  answer: >
    Yes. Postgres and object storage use AES-256 with keys in Azure Key Vault (Central India), rotated yearly.
  owner: platform-lead
  evidence: [docs/architecture.pdf#storage, key-vault-policy.pdf]
  reviewed: 2026-09-14
  tags: [encryption, storage]
- id: ai-training
  question: Is our data used to train AI models?
  answer: >
    No. Our model provider's enterprise terms exclude training on API data; retention is 30 days for abuse
    monitoring (terms version and clause attached).
  owner: cto
  evidence: [provider-terms-2026-07.pdf]
  reviewed: 2026-07-30
  tags: [ai, vendor]
```

```python
import yaml
from datetime import date, timedelta

def load(path="security-answers.yaml"):
    return yaml.safe_load(open(path))

def stale(answers, max_age_days=180):
    cutoff = date.today() - timedelta(days=max_age_days)
    return [(a["id"], a["owner"]) for a in answers if a["reviewed"] < cutoff or not a.get("evidence")]

def suggest(question, answers, top=3):
    words = set(question.lower().split())
    scored = sorted(answers, key=lambda a: -len(words & set((a["question"] + " " + " ".join(a["tags"])).lower().split())))
    return [a["id"] for a in scored[:top]]
```

`stale`-ஐ மாசத்துக்கு ஒரு தடவை run பண்ணி, ஒவ்வொரு owner-க்கும் அவங்க list-ஐ அனுப்புங்க. ஒரு புது questionnaire-க்கு candidate answers-ஐ கண்டுபிடிக்க `suggest`-ஐ (பெரிய libraries-க்கு embeddings-ஐ) use பண்ணுங்க, ஆனா ஒவ்வொரு answer-உம் போறதுக்கு முன்னாடி ஒரு நபர் check பண்ணணும்: ஒரு model அல்லது keyword match கிட்டத்துல இருக்குற ஆனா தப்பான answer-ஐ தேர்ந்தெடுக்கலாம்.

**AI-ஓட draft பண்றது, கவனமா.** உங்க library-ல இருந்தும் architecture notes-ல இருந்தும் ஒரு model answers-ஐ draft பண்ணலாம்; நீளமான questionnaires-ல இது நேரத்தை மிச்சப்படுத்தும். விதிகள்: அது library-யையும் attach பண்ணின documents-ஐயும் மட்டும் use பண்ணலாம், ஒவ்வொரு draft-உம் அது use பண்ண library ids-ஐ cite பண்ணணும், பேர் சொல்லப்பட்ட ஒரு நபர் ஒவ்வொரு answer-ஐயும் approve பண்ணணும். உங்ககிட்ட இல்லாத ஒரு control-ஐ ஒரு model கண்டுபிடிக்க ஒருபோதும் விடாதீங்க.

**AI section, current-ஆ.** உங்க model providers-ஐ அவங்க terms-ஐ check பண்ண தேதியோட, use பண்ற regions, என்ன data அனுப்பப்படுது அது mask ஆகுதா, guardrails-உம் அவற்றோட test results-உம், kill switches, prompt, model மாற்றங்கள் எப்படி test ஆகுது, sub-processor list-ஐ list பண்ணுங்க. இதுல எது மாறினாலும் அதே வாரத்துல இந்த section-ஐ update பண்ணுங்க.

**நல்லா வயசாகுற evidence.** பழசாயிடுற text-ஐ paste பண்றதுக்கு பதிலா, living documents-க்கு (தற்போதைய architecture diagram, சமீபத்திய eval, penetration test summaries) link குடுங்க. Injection tests, permission tests-ஓட CI results-ஐ ஒரு குறுகிய PDF-ஆ export பண்ற மாதிரி வச்சுக்கோங்க, ஏன்னா AI-specific evidence-ஐ தான் reviewers முன்னாடி பார்த்திருக்க வாய்ப்பு குறைவு.

## ஒரு worked example

Bengaluru-ல ஒரு AI startup, ஒரு பெரிய private bank-ஓட ஒரு வெற்றிகரமான pilot-க்கு அப்புறம், ரெண்டு வாரம் deadline-ஓட 240 கேள்விகள் உள்ள ஒரு spreadsheet-ஐ வாங்குறாங்க. FDE Meera ஒருங்கிணைக்குறாங்க.

170 கேள்விகளை cover பண்ற answer library-ல இருந்து ஆரம்பிக்குறாங்க. மீதியில, 40 AI-specific, 30 bank-specific (உதாரணம், RBI outsourcing guidelines, data localisation).

AI கேள்விகளுக்கு, system-ஓட உண்மையான design documents-ஐ use பண்றாங்க: data flow map, gateway configuration (இந்திய region மட்டும், model provider data-ல train பண்ணக்கூடாதுன்னு contract), masking rules, test results-ஓட guardrail list, customer-facing messages-க்கு human approval step, audit log schema. ஒவ்வொரு answer-உம் சம்பந்தப்பட்ட document section-ஐ cite பண்ணுது.

ரெண்டு கேள்விகள் உண்மையான gaps-ஐ காட்டுது: AI endpoints-க்கு முறையான வருஷாந்திர penetration test இல்ல, model misbehaviour-க்குன்னு ஆவணப்படுத்தின incident plan இல்ல. ரெண்டுக்கும் "Partially"ன்னு பதில் சொல்றாங்க, அடுத்த மாசம் book பண்ணின ஒரு external penetration test-உம் attach பண்ணின ஒரு draft incident runbook-உம் சேர்த்து. Bank-ஓட security team நிபந்தனைகளோட plan-ஐ ஏத்துக்குது, வழக்கமான மூணு மாசத்துக்கு பதிலா நாலு வாரத்துல contract முன்னேறுது.

| Questionnaire-ஓட பகுதி | எண்ணிக்கை | எப்படி கையாளப்பட்டது |
| --- | --- | --- |
| Library-ல இருந்து பதில் | 170 | Checks-ஓட மறுபடியும் use |
| AI-specific | 40 | Design documents-ல இருந்து citations-ஓட பதில் |
| Bank-specific | 30 | Legal-ஓட draft |
| Gaps | 2 | Book பண்ணின pen test-உம் draft runbook-உம் சேர்த்து "Partially" |
| Outcome | | மூணு மாசத்துக்கு பதிலா நாலு வாரத்துல contract |

## பொதுவா பண்ற தப்புகள்

- **Overclaim பண்றது.** தப்பான "Yes" அப்புறம் ஒரு legal பிரச்சனையா மாறலாம். "Partially"ன்னு சொல்லி விளக்குங்க.
- **ஒவ்வொரு தடவையும் முதல்ல இருந்து ஆரம்பிக்குறது.** Owners, dates-ஓட ஒரு answer library maintain பண்ணுங்க.
- **தெளிவில்லாத AI answers.** "நாங்க industry-standard AI security use பண்றோம்"ங்கிறதுக்கு அர்த்தமில்ல. Providers, regions, terms, controls-ஐ பேரோட சொல்லுங்க.
- **Sub-processors-ஐ மறக்குறது.** Client data-ஐ பார்க்குற ஒரு tracing அல்லது email tool-உம் கணக்குல வரும்.
- **Library பழசாக விடுறது.** போன வருஷ architecture பத்தின answers தப்பான answers.
- **Owner அல்லது review date இல்லாத answers.** அவை காலாவதி ஆகுறதை யாரும் கவனிக்க மாட்டாங்க.
- **ஒவ்வொண்ணையும் ஒரு நபர் check பண்ணாம AI draft பண்ணின answers-ஐ அனுப்புறது.**
- **புது sub-processors-ஐ மறக்குறது**, போன மாசம் சேர்த்த ஒரு tracing tool மாதிரி.

## முழு library தேவையில்லாத இடங்கள்

- **உங்க முதல் ஒண்ணு ரெண்டு questionnaires**: கவனமா பதில் சொல்லுங்க, அப்புறம் அந்த answers-ஐ library-ஆ மாத்துங்க.
- **சின்ன clients** email-ல சில கேள்விகள் கேட்டா: அதே துல்லியத்தோட நேரடியா பதில் சொல்லுங்க.
- **Company-ஓட சொந்த security review process cover பண்ற internal projects.**

## Demo-ல இருந்து production வரை

- **Library-ஐ version control-ல வைங்க**, owners, dates, evidence links-ஓட.
- **பழசான answers-ஐ மாசாமாசமும் ஒவ்வொரு architecture மாற்றத்துலயும் flag பண்ணுங்க.**
- **Sub-processor list-ஐ maintain பண்ணுங்க**, ஒவ்வொண்ணுக்கும் purpose, location-ஓட.
- **AI test results-ஐ** (injection, permissions, guardrails) evidence-ஆ export பண்ணுங்க.
- **ஒவ்வொரு questionnaire-ஐயும் track பண்ணுங்க**: அதோட தேதி, அனுப்பின answers-ஓட version, குடுத்த follow-up வாக்குறுதிகள்.

## Practice பண்ணுங்க

CSA CAIQ-ஐ (free) download பண்ணி அதோட control domains-ஐ பார்வையிடுங்க; LLM applications-க்கான OWASP Top 10-ஐ திரும்ப படிங்க.

1. 20 CAIQ கேள்விகளை எடுத்து, நீங்க build பண்ணின ஒரு system-க்கு, evidence links அல்லது "இன்னும் இல்ல" + ஒரு plan-ஓட பதில் சொல்லுங்க.
2. ஒரு bank சேர்க்கக்கூடிய பத்து AI-specific கேள்விகளை எழுதி, துல்லியமா பதில் சொல்லுங்க.
3. உங்க system-ல இருக்குற ஒவ்வொரு sub-processor-ஐயும் அதோட purpose, data location-ஓட list பண்ணுங்க.
4. உங்க 20 CAIQ answers-ஐ owners, dates-ஓட ஒரு YAML library-ஆ மாத்தி, அதுல stale check-ஐ run பண்ணுங்க.

**இவை முடிஞ்சா நீங்க ready:** ஒரு reviewer-கிட்ட உங்க answers-ஐயும் evidence-ஐயும் குடுத்து, ஒவ்வொரு answer-உம் ஒரு follow-up கேள்வியை தாங்கும்படி பண்ணலாம்.
