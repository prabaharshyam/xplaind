## இது என்ன

**Latency budget**-னா நீங்க ஏத்துக்கிற மிக மெதுவான response, ஒரு குறிப்பிட்ட percentile-ல, ஒரு request-ஓட ஒவ்வொரு step-க்கும் ஒரு target-ஆ பிரிச்சது. ஒரு chat assistant-க்கு, உதாரணமா: p95 time to first token 2 seconds-க்குள்ள, p95 full answer 10 seconds-க்குள்ள, errors 1%-க்கு கீழ. அப்புறம் first-token budget இப்படி பிரியும்: auth 50 ms, query rewrite 300 ms, retrieval-உம் reranking-உம் 400 ms, model first token 700 ms, network-க்கும் queueing-க்கும் 550 ms slack.

**Load testing** realistic traffic-ஐ system மேல step by step கூட்டிக்கிட்டே அனுப்பி, response times, errors, resource use-ஐ record பண்ணும். எந்த load-ல system உடையுது, எது முதல்ல உடையுதுன்னு உங்க users கண்டுபிடிக்கிறதுக்கு முன்னாடியே அது சொல்லிடும்.

உங்களுக்கு தேவைப்படுற மூணு வார்த்தைகள். **p95**-னா 95% requests எந்த நேரத்தை விட வேகமா முடியுதோ அந்த நேரம். **Time to first token**-னா answer-ஓட முதல் வார்த்தை தெரியுற வரைக்குமான காத்திருப்பு. **Concurrent users**-னா ஒரே நேரத்துல chat session-ல இருக்குறவங்க; அவங்கள்ல பெரும்பாலானவங்க படிச்சுக்கிட்டோ type பண்ணிக்கிட்டோ இருப்பாங்க, அதனால ஒரே நேரத்துல in flight-ல இருக்குற requests ரொம்ப குறைவு.

இந்த lesson, Jaipur-ல ஒரு intercity bus operator festival-season traffic-க்கு தன்னோட booking assistant-ஐ தயார் பண்றதை follow பண்ணுது.

## இது எப்படி work ஆகுது

### Averages இல்ல, percentiles

1.5 seconds average, 5% users 4-ல இருந்து 9 seconds வரை காத்திருக்குறதை மறைக்கலாம். Median (p50), p95, p99-ஐ track பண்ணுங்க. Tail பார்க்குறதை விட முக்கியம்: ஒரு session-ல 20 messages அனுப்புற ஒரு user-க்கு, p99-ஐ விட slow-ஆன குறைஞ்சது ஒரு reply-ஐ சந்திக்க சுமார் 18% chance இருக்கு (1 minus 0.99 power 20).

Experts follow பண்ற ரெண்டு rules:

- **Percentiles கூட்டினா வராது.** Total-ஓட p95, ஒவ்வொரு step-ஓட p95-ஐயும் கூட்டினது இல்ல. Slow steps ஒரே request-ல அரிதா தான் சேர்ந்து நடக்கும், அதனால கூட்டுத்தொகை பொதுவா total-ஐ அதிகமா காட்டும்; ஆனா busy database மாதிரி ஒரே காரணம் எல்லா steps-ஐயும் ஒரே நேரத்துல slow பண்ணா, அவை சேர்ந்தே நகரும். Step numbers-ஐ அந்த step-ஓட சொந்த p95-க்கான targets-ஆ வச்சுக்குங்க, end-to-end p95-ஐ traces-ல இருந்து நேரடியா படிங்க.
- **Percentiles-ஐ average பண்ண முடியாது.** மூணு servers 1.2 seconds p95 காட்டுது, ஒண்ணு, 3.5 seconds median-ஓட, 6 seconds காட்டுதுன்னு வச்சுக்குங்க; ஒவ்வொண்ணும் traffic-ல கால் பங்கு எடுக்குது. நாலு p95-ஓட average 2.4 seconds. ஆனா slow server-ஓட requests-ல பாதி 3.5 seconds-க்கு மேல எடுக்குது, அது எல்லா requests-லயும் 12.5%, அதனால உண்மையான p95 3.5 seconds-க்கு மேல. Percentiles-ஐ எல்லா raw timings-ல இருந்தோ, merge பண்ண histograms-ல இருந்தோ கணக்கு போடுங்க.

```python
import random

random.seed(7)
def p95(xs):
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]

# Four steps, each with its own spread of times in seconds
auth     = [random.lognormvariate(-3.5, 0.3) for _ in range(10_000)]
retrieve = [random.lognormvariate(-1.3, 0.4) for _ in range(10_000)]
rerank   = [random.lognormvariate(-1.8, 0.5) for _ in range(10_000)]
model    = [random.lognormvariate(-0.5, 0.35) for _ in range(10_000)]
total = [a + b + c + d for a, b, c, d in zip(auth, retrieve, rerank, model)]

print(f"sum of the step p95s: {p95(auth) + p95(retrieve) + p95(rerank) + p95(model):.2f} s")
print(f"p95 of the total:     {p95(total):.2f} s")
```

இது கூட்டுத்தொகைக்கு 2.03 seconds-உம், உண்மையான total-க்கு 1.67 seconds-உம் print பண்ணும், ஏன்னா இங்க steps independent.

### AI requests-ஐ slow ஆக்குறது எது

**Generation time** கிட்டத்தட்ட output tokens பெருக்கல் ஒரு token-க்கான நேரம். ஒரு second-க்கு 60 tokens-ல, 450-token answer stream ஆக 7.5 seconds, 200-token answer சுமார் 3.3 seconds எடுக்கும். Answer நீளத்தை cap பண்றது தான் பெரும்பாலும் உங்ககிட்ட இருக்குற மிக மலிவான speed-up.

**Time to first token** prompt நீளத்தோடவும், உங்க system-லயும் provider-லயும் இருக்குற queueing-ஓடவும், அந்த மணி நேரத்துல provider-ஓட load-ஓடவும் கூடும். Context-ஐ trim பண்ணுங்க, உங்க provider support பண்ணா ஒரு cached prompt prefix-ஐ reuse பண்ணுங்க. Reasoning models எதையும் காட்டுறதுக்கு முன்னாடி யோசிக்கலாம், அதனால user உண்மையா பார்க்குற முதல் token-ஐ அளங்க.

**Rate limits** நிமிஷத்துக்கு tokens அல்லது requests மேல இருக்கும்; நீங்க எத்தனை servers ஓட்டினாலும் அவை calls-ஐ 429 (Too Many Requests)-ஓட reject பண்ணும். உங்க provider input, output tokens-ஐ எப்படி count பண்ணுதுன்னு check பண்ணுங்க, peak-ல என்ன வேணும்னு கணக்கு போடுங்க, வாரக்கணக்கா முன்னாடியே அதிக limit கேளுங்க.

### Little's law வச்சு sizing

**Little's law**: requests in flight = arrival rate x ஒவ்வொரு request-உம் system-ல இருக்குற நேரம். Pilot-ஓட logs-ல ஒவ்வொரு active user-உம் நிமிஷத்துக்கு சுமார் 2 messages அனுப்புறாங்கன்னு தெரியுதுன்னு வச்சுக்குங்க. 500 users-ல அது ஒரு second-க்கு சுமார் 17 requests. ஒவ்வொண்ணும் 4.5 seconds எடுத்தா, எந்த நேரத்துலயும் சுமார் 75 answers stream ஆகிட்டு இருக்கும். 500 இல்ல, அந்த எண் தான் உங்க connection pools, worker counts, எந்த concurrency cap-ஐயும் size பண்ணும்.

### Test-ஐ design பண்றது

உண்மையான behaviour-ஐ model பண்ணுங்க: உண்மையான கேள்விகள் (masked), வழக்கமான prompt, answer நீளங்கள், messages நடுவுல think time, expected peak. குறைவுல இருந்து peak-ஐ தாண்டி ramp பண்ணுங்க, percentiles settle ஆக **ஒவ்வொரு step-ஐயும்** ரெண்டு மூணு நிமிஷம் **hold பண்ணுங்க**. p95, p99, status code வாரியா errors, CPU, memory, database connections, queue நீளம், provider 429s-ஐ கவனிங்க.

**Closed, open tests.** ஒரு **closed** test-ல, think time உள்ள Locust users மாதிரி, ஒவ்வொரு simulated user-உம் reply வர்ற வரை காத்திருந்து தான் திரும்ப அனுப்புவாங்க. System slow ஆனா test குறைவா அனுப்பும், அந்த slow period-ல வர வேண்டியதை விட குறைவான measurements தான் வரும். இதுக்கு பேர் **coordinated omission**: real users பின்வாங்காத சரியான அந்த நேரத்துல test அமைதியா பின்வாங்குது. ஒரு **open** test-ல, என்ன ஆனாலும் requests ஒரு fixed rate-ல வரும், sale திறக்கும்போது travellers முண்டியடிச்சு வர்ற மாதிரி. k6 இதை அதோட constant-arrival-rate, ramping-arrival-rate executors மூலமா குடுக்குது. Bottlenecks-ஐ step by step கண்டுபிடிக்க ஒரு closed ramp use பண்ணுங்க, அப்புறம் queue-ஐ பார்க்க expected arrival rate-ல ஒரு burst-ஓட open test ஓட்டுங்க.

**Soak test.** Expected peak-ஐ 30-ல இருந்து 60 நிமிஷம் வரை hold பண்ணுங்க. Memory, connections, file handles leaks நேரம் போகப்போக தான் தெரியும்.

### ஒரு fake model server

Real-model load tests-க்கு காசு செலவாகும், rate limits-உம் தீரும். பெரும்பாலான rounds-ஐ ஒரு சின்ன fake service-க்கு எதிரா ஓட்டுங்க; அதுக்கு provider-ஓட API-ஓட அதே streaming shape இருக்கும், அதோட first-token delays உங்க traces-ல இருந்து sample பண்ணது:

```python
import asyncio, json, os, random
from fastapi import FastAPI
from fastapi.responses import JSONResponse, StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.30, 0.35, 0.35, 0.35, 0.40, 0.40, 0.40, 0.45, 0.45, 0.45, 0.45, 0.50, 0.50,
                 0.50, 0.50, 0.55, 0.55, 0.55, 0.60, 0.60, 0.60, 0.65, 0.70, 0.70, 1.40]
TOKENS_PER_S = 60
REPLY_TOKENS = 450                                    # today's typical answer length
SHARE_429 = float(os.getenv("FAKE_429_SHARE", "0"))   # for example 0.05

@app.post("/v1/messages")
async def messages():
    if random.random() < SHARE_429:
        return JSONResponse({"error": "rate_limited"}, status_code=429,
                            headers={"retry-after": "2"})
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for i in range(REPLY_TOKENS):
            yield f"data: {json.dumps({'text': f'tok{i} '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

இந்த delays model-க்கு 0.7 seconds p95 குடுக்கும், அது தான் budget-ல model-ஓட share, 25-ல ஒரு slow reply-ஓட. அதை `uvicorn fake_model:app`-ஓட ஓட்டுங்க, test environment-ல மட்டும் configuration மூலமா உங்க app-ஓட model base URL-ஐ அது பக்கம் point பண்ணுங்க. உங்க retries, fallback-ஐ test பண்ண `FAKE_429_SHARE`-ஐ set பண்ணுங்க.

### Stream-ஐ time பண்ற ஒரு Locust ramp

`stream=True`-ஓட, request-க்கான Locust-ஓட சொந்த row, response headers வந்ததுமே clock-ஐ நிறுத்திடும், பெரும்பாலும் சில milliseconds-ல, first token-க்கு ரொம்ப முன்னாடியே. அதனால இந்த test தன்னோட சொந்த ரெண்டு timings-ஐ record பண்ணுது:

```python
import random, time
from locust import HttpUser, LoadTestShape, between, task

QUESTIONS = [q.strip() for q in open("load/questions.txt", encoding="utf-8") if q.strip()]

class Traveller(HttpUser):
    wait_time = between(20, 30)          # think time between messages

    @task
    def ask(self):
        start, first = time.perf_counter(), None
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
                return
            for line in r.iter_lines():               # read the whole stream
                if line and first is None:
                    first = time.perf_counter()
        end = time.perf_counter()
        if first is not None:
            self.record("first token", first - start)
        self.record("full answer", end - start)

    def record(self, name, seconds):
        self.environment.events.request.fire(
            request_type="STREAM", name=name, response_time=seconds * 1000,
            response_length=0, exception=None, context={})

class Ramp(LoadTestShape):
    # (end second, users): hold each step for two minutes
    steps = [(120, 50), (240, 100), (360, 200), (480, 300), (600, 400), (720, 500), (840, 550)]

    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10                      # add up to 10 users a second
        return None
```

அதை `locust -f load/locustfile.py --headless --host https://staging.example.in --csv results --csv-full-history`-ஓட ஓட்டுங்க. அப்புறம் `results_stats_history.csv` file-ல ஒவ்வொரு name-க்கும் ஒவ்வொரு second-உம் ஒரு row வரும், அதுல user count-உம் கடைசி சுமார் 10 seconds-ஓட percentiles-உம் இருக்கும். `first token`, `full answer` rows-ஐ படிங்க, ஒவ்வொரு hold-ஓட கடைசி நிமிஷத்துல 95% column-ஓட median-ஐ எடுங்க, ஏன்னா low load-ல ஒரு 10-second window-ல கொஞ்சம் requests தான் இருக்கும். Traces-ல இருந்து per-step p95-உம் work ஆகும். Built-in POST row-ஐ (headers மட்டும்) ignore பண்ணுங்க, Aggregated row-ஐயும் ignore பண்ணுங்க, அது மூணு timings-ஐயும் கலக்குது.

### Overload, retries, streaming

- **Retry storms.** ஒவ்வொரு 429-ஐயும் timeout-ஐயும் உடனே, மூணு தடவை வரை retry பண்ணா, கஷ்டப்படுற ஒரு system-க்கு நாலு மடங்கு வரை traffic வரலாம். Exponential backoff-உம் random jitter-உம் வச்சு retry பண்ணுங்க, provider `retry-after` header அனுப்பினா அதை மதிங்க, retries-ஐ traffic-ல ஒரு சின்ன share-ல cap பண்ணுங்க.
- **Admission control.** ஒவ்வொரு instance-உம் ஒரே நேரத்துல serve பண்ற streams-ஐ cap பண்ணுங்க. கூடுதல் requests ஒரு சின்ன queue-ல, அதிகபட்சம் சில seconds, காத்திருக்கட்டும்; அப்புறம் "இப்போ busy-ஆ இருக்கோம், ஒரு நிமிஷம் கழிச்சு try பண்ணுங்க"-னு மரியாதையா காட்டுங்க. எல்லாருக்கும் timeout ஆகுறதை விட, சிலரை திருப்பி அனுப்புறது மேல்.
- **Autoscaling, cold starts.** புது instances start ஆகி warm up ஆக நிமிஷக்கணக்கா ஆகலாம். தெரிஞ்ச peak-க்கு, அது ஆரம்பிக்கிறதுக்கு முன்னாடியே scale up பண்ணுங்க.
- **Proxies வழியா streaming.** ஒரு proxy அல்லது load balancer response-ஐ buffer பண்ணலாம், அதனால tokens ஒரே கட்டியா வரும்; அல்லது idle-னு நினைக்கிற connection-ஐ close பண்ணலாம். Streaming route-ல buffering, idle-timeout settings-ஐ check பண்ணுங்க.

| Load-ல தெரியுற அறிகுறி | வாய்ப்புள்ள காரணம் | Fix |
| --- | --- | --- |
| Latency ஏறுது, CPU low | Database connections அல்லது locks-க்காக காத்திருக்கு | பெரிய pool, indexes, caching, குறைவான queries |
| CPU 100%-ல | ரொம்ப கம்மியான workers அல்லது heavy parsing | அதிக workers, வேலையை background jobs-க்கு மாத்துங்க |
| 429 errors | Provider rate limit | அதிக limit, fallback model, சின்ன outputs |
| Errors ஆரம்பிக்கும்போது traffic எகிறுது | உடனடி retries | Jitter-ஓட backoff, retry cap |
| Bursts-ல மட்டும் queue வளருது | Arrival rate-க்கு ரொம்ப கம்மியான streams | Concurrency cap, busy message, சீக்கிரமே scale up |
| First token மட்டும் slow | நீளமான prompts அல்லது provider queueing | Context-ஐ trim பண்ணுங்க, prefix-ஐ cache பண்ணுங்க |
| Tokens ஒரே கட்டியா வருது | ஒரு proxy stream-ஐ buffer பண்ணுது | அந்த route-ல buffering-ஐ off பண்ணுங்க |
| சரியா ஒரு நிமிஷம் கழிச்சு errors | ஏதோ ஒரு layer-ல timeout அல்லது idle limit | எல்லா layers-லயும் timeouts-ஐ align பண்ணுங்க |

### Traces-ஐ open பண்ணிக்கிட்டே results-ஐ படிங்க

ஒரு step-ல p95 எகிறினா, அந்த நிமிஷத்தோட ரொம்ப slow traces-ஐ open பண்ணுங்க. வளர்ந்த step (database waits, reranker, model slot-க்கான queueing) தான் bottleneck, மேல இருக்குற table பொதுவா fix-ஐ சொல்லிடும். அப்புறம் அதே test-ஐ திரும்ப ஓட்டுங்க, அப்போ தான் சமமானதை சமமானதோட compare பண்ண முடியும்.

## ஒரு worked example

Jaipur bus operator, festival travel நேரத்துல ஒரே நேரத்துல chat பண்ற சுமார் 500 travellers-ஐ எதிர்பார்க்குது, காலை 10 மணிக்கு ஒரு seat sale திறக்குது. Budget: p95 first token 2 seconds-க்கு கீழ, p95 full answer 10 seconds-க்கு கீழ, errors 1%-க்கு கீழ. கீழ இருக்குற எல்லா numbers-உம் illustrative தான்.

**Round 1: closed ramp, fake model.** p95 first token 50 users-ல 1.1 seconds-ல இருந்து 200-ல 6 seconds-க்கு ஏறுது. CPU 25%-ல இருக்கு. ரொம்ப slow traces எல்லாம் database connection-க்காக காத்திருக்கு: pool-ல 10 தான் இருக்கு. 40 pool-உம் route table-ல ஒரு index-உம் அதை fix பண்ணுது.

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| p95 first token, pool 10 | 1.1 s | 2.4 s | 6.0 s | நிறுத்தியாச்சு: timeouts | ஓட்டல | ஓட்டல |
| p95 first token, pool 40 + index | 1.1 s | 1.1 s | 1.2 s | 1.2 s | 1.3 s | 1.4 s |

**Round 2: real model-ல ஒரு சின்ன run.** பத்து நிமிஷம், 300 users வரை ramp, API account-ஐ வச்சிருக்கவங்க கூட முன்னாடியே பேசி ஒத்துக்கிட்டது. சுமார் 220 users-ல 429 errors ஆரம்பிக்குது. தோராயமான கணக்கும் ஒத்துப்போகுது: pilot-ஓட logs-படி ஒவ்வொரு user-உம் நிமிஷத்துக்கு சுமார் 2,000 tokens (1,550 in, 450 out) உள்ள சுமார் 2 messages அனுப்புறாங்க, அதனால ஒரு user-க்கு நிமிஷத்துக்கு 4,000 tokens; account-ஓட நிமிஷத்துக்கு 900,000 tokens 225 users-ல தீர்ந்துடும். Team answers-ஐ 200 tokens-ல cap பண்ணுது; அது streaming நேரத்தை 7.5-ல இருந்து சுமார் 3.3 seconds-க்கும், ஒரு message-க்கான tokens-ஐ 1,750-க்கும் குறைக்குது. அவங்க அதிக limit கேக்குறாங்க; பத்து நாள் கழிச்சு provider நிமிஷத்துக்கு 2.5 million tokens குடுக்குது. அவங்க gateway மூலமா ஒரு fallback model-உம், retries-ல jitter-ஓட backoff-உம் சேர்க்குறாங்க.

**Round 3: open burst test, fake model** (இப்போ 200-token replies-க்கு set பண்ணது). Little's law: 500 users-ல, ஒரு second-க்கு சுமார் 17 requests, ஒவ்வொண்ணும் சுமார் 4.5 seconds-னா, சுமார் 75 streams in flight. Sale திறக்கும்போது arrivals ஒரு second-க்கு சுமார் 25-க்கு எகிறுது, அதாவது சுமார் 113 in flight. ஒவ்வொண்ணும் 48 streams-ல cap பண்ண ரெண்டு instances 96-ஐ தான் தாங்கும். Burst-ல p95 first token 9 seconds-ஐ தொடுது, 6% requests timeout ஆகுது. Closed ramp இதை காட்டவே இல்ல, ஏன்னா அதோட users சும்மா காத்திருந்தாங்க. Fix: காலை 9:45-க்கு start பண்ண ஒரு மூணாவது instance, 3-second queue-உம் busy message-உம் உள்ள admission control. Re-run-ல p95 first token 1.5 seconds-லயே இருக்கு, யாரையும் திருப்பி அனுப்பல.

**Round 4: confirm.** Real model-ல 550 users-ல பத்து நிமிஷம்: p95 first token 1.6 seconds, p95 full answer 5.2 seconds, errors 0.3%. அந்த load நிமிஷத்துக்கு 1.9 million tokens use பண்ணுது, limit-ல 77%. Fake model-ல 500 users-ல ஒரு 45 நிமிஷ soak, memory flat-ஆ இருக்குறதையும் connections leak ஆகலைன்னும் காட்டுது.

**Launch நாள்.** Peak 480 travellers-ஐ தொடுது. காலை 10 மணி burst-ல demand கொஞ்ச நேரத்துக்கு நிமிஷத்துக்கு சுமார் 2.6 million tokens கேக்குது, limit-ஐ விட 5% அதிகம்; gateway ரெண்டு நிமிஷத்துக்கு சில percent requests-ஐ fallback model-க்கு அனுப்புது. p95 first token 2 seconds-க்கு கீழயே இருக்கு.

**Report**-ல budget line-ஓட users-க்கு எதிரா p95 காட்டுற ஒரு chart, கண்டுபிடிச்ச ஒவ்வொரு bottleneck-உம் அதோட fix-உம், அடுத்த ceiling-உம் இருக்கு: சுமார் 700 steady users (2.5 million வகுத்தல் ஒரு user-க்கு நிமிஷத்துக்கு 3,500 tokens), bursts-ல அதுக்கு முன்னாடியே.

## பொதுவா பண்ற தப்புகள்

- **Averages-ஐ report பண்றது.** First token-க்கும் full answer-க்கும் p50, p95, p99-ஐ report பண்ணுங்க.
- **Percentiles-ஐ கூட்டுறது அல்லது average பண்றது.** ரெண்டுமே work ஆகாது; raw timings-ல இருந்து கணக்கு போடுங்க.
- **ஒரு நேரத்துல ஒரு request-ஐ மட்டும் test பண்றது.** Pools, locks, rate limits concurrency-ல மட்டும் தான் fail ஆகும்.
- **Unrealistic traffic.** ஒரே மாதிரியான சின்ன prompts-உம் think time இல்லாததும் அர்த்தமில்லாத numbers-ஐ தான் குடுக்கும்.
- **Closed tests மட்டும்.** System slow ஆனா அவை பின்வாங்கிடும், அதனால ஒரு real rush உருவாக்குற queue-ஐ மறைச்சுடும்.
- **Streams-க்கு Locust-ஓட request row-ஐ நம்புறது.** Streaming on-ஆ இருந்தா, அது headers-ஐ மட்டும் தான் time பண்ணும்.
- **Real-model load tests-ல காசை கொட்டுறது.** பெரும்பாலான rounds-க்கு fake model use பண்ணுங்க, ஒரு சின்ன real run மட்டும் போதும்.
- **Provider limits-ஐ மறக்குறது.** பெரும்பாலும் அவை தான் உண்மையான ceiling. Token கணக்கை போட்டு, சீக்கிரமே கேளுங்க.
- **உடனடி retries.** System கஷ்டப்படுற சரியான அந்த நேரத்துல அவை load-ஐ பெருக்கும்.

## முழு load test காத்திருக்கலாம்ங்கிற நேரங்கள்

- **கொஞ்சம் users மட்டும் உள்ள internal tools**: பத்து concurrent requests-ஓட ஒரு quick check போதும்.
- **Batch systems**, அங்க per-user latency-ஐ விட ஒரு மணி நேரத்துக்கான throughput தான் முக்கியம்; அதை test பண்ணுங்க.
- **உங்களுக்காக scale பண்ற platforms-ல ஆரம்ப pilots**, rate limits-ஐயும் timeouts-ஐயும் check பண்ணியிருந்தா போதும்.

## Demo-ல இருந்து production-க்கு

- **Step வாரியா ஒரு latency budget வச்சுக்குங்க**, ஒவ்வொரு release-லயும் traces-ஐ அதோட compare பண்ணுங்க.
- **Launch-க்கு முன்னாடியும் பெரிய மாற்றங்களுக்கு முன்னாடியும் load-test பண்ணுங்க**, பெரும்பாலும் ஒரு fake model server-ஓட.
- **ஒவ்வொரு ramp step-க்கும் p50, p95, p99, errors-ஐ report பண்ணுங்க**, கண்டுபிடிச்ச bottleneck-ஓட சேர்த்து.
- **Traffic patterns மாறும்போது திரும்ப test பண்ணுங்க**, exam season, ஒரு festival sale, அல்லது நீளமான answers உள்ள ஒரு புது feature மாதிரி.
- **Production-ல p95 first-token time-க்கும் 429 rate-க்கும் alert வைங்க**, tokens-per-minute headroom-ஐ கண்ணுல வச்சுக்குங்க.

## Practice பண்ணுங்க

Monitoring பத்தின Google SRE chapter-ஐயும் Locust-ஓட first-test guide-ஐயும் படிங்க.

1. பத்து real requests-ஓட traces-ஐ வச்சு, உங்க app-க்கு step வாரியா ஒரு latency budget எழுதுங்க. End-to-end p95-ஐ தனியா check பண்ணுங்க.
2. மேல இருக்குற fake model server-ஐ ஓட்டி, உங்க app-ஐ அது பக்கம் point பண்ணுங்க.
3. Locust ramp-ஐ 50-ல இருந்து 550 users வரை ஓட்டுங்க. ஒவ்வொரு hold-லயும் first token, full answer-க்கு p50, p95, p99-ஐ record பண்ணுங்க, p95 முதல் தடவையா உங்க budget-ஐ எங்க தாண்டுதுன்னு note பண்ணுங்க.
4. முதல் bottleneck-ஐ கண்டுபிடிச்சு fix பண்ணி, re-run பண்ணுங்க; அப்புறம் Little's law வச்சு உங்க peak-லயும், அந்த rate-ஓட 1.5 மடங்கு burst-லயும் requests in flight-ஐ estimate பண்ணுங்க.
