## இது என்ன

**Latency budget** ஏத்துக்கக்கூடிய அதிகபட்ச response நேரம், steps வாரியா பிரிச்சது. ஒரு chat assistant-க்கு: 95th percentile-ல முதல் token 1.5 seconds-க்குள்ள, முழு answer 8 seconds-க்குள்ள. அப்புறம் budget steps-ஆ பிரியும்: auth 50 ms, query rewrite 300 ms, retrieval, reranking 400 ms, model-ஓட time to first token 700 ms.

**Load testing** system மேல உண்மையான மாதிரி traffic-ஐ, படிப்படியா ஏத்திக்கிட்டே அனுப்பி, response times, errors, resource use-ஐ record பண்ணும்; அதனால எந்த load-ல அது உடையுது, முதல்ல என்ன உடையுதுன்னு உங்களுக்கு தெரியும்.

```flow

title: Latency budget: 2 s-ல p95 first token
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> மிச்சமிருக்குற slack, 550 ms
```

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| முன்னாடி: 10 connections உள்ள pool | 1 s | 2 s | 6 s | | | |
| பின்னாடி: 40 pool + ஒரு index | 1 s | 1 s | 1 s | 1 s | 1 s | 1 s |

Users எண்ணிக்கைக்கு ஏத்த p95 first token, fake model வச்சு அளந்தது.

இந்த lesson, Jaipur-ல ஒரு intercity bus operator தங்க booking assistant-ஐ festival-season traffic-க்கு தயார் பண்றதை follow பண்ணுது.

## இது எப்படி work ஆகுது

**Averages இல்ல, percentiles.** 2 seconds average, 5% users 15 seconds காத்திருக்கிறதை மறைச்சுடலாம். Median (p50), 95th (p95), 99th percentile (p99)-ஐ track பண்ணுங்க. Users-க்கு மெதுவானது தான் ஞாபகம் இருக்கும்.

**Step வாரியா budget.** Traces ஒவ்வொரு step-ஓட timing-ஐயும் தரும். மொத்தம் target-ஐ தவறவிடும்போது, எந்த step-ஐ சரி பண்ணணும்ன்னு budget காட்டும்: மெதுவான reranker, அதிக chunks, சின்னது போதும்ங்கிற இடத்துல பெரிய model, அல்லது cold start.

**AI-க்கே உரிய காரணிகள்.** Generation நேரத்துல output நீளம் ஆதிக்கம் செலுத்தும், அதனால சின்ன answers வேகமா வரும். Time to first token prompt நீளத்தை பொறுத்தது, அதனால context-ஐ சுருக்குங்க. Provider latency மணி நேரத்தை, region-ஐ பொறுத்து மாறும். Tokens per minute rate limits, நீங்க எத்தனை servers ஓட்டுனாலும் throughput-ஐ cap பண்ணும்; பெரிய launch-க்கு முன்னாடி அவற்றை check பண்ணி, provider-கிட்ட சீக்கிரமே அதிக limits கேளுங்க.

**Test-ஐ design பண்றது.** உண்மையான நடத்தையை மாதிரியா எடுங்க: கேள்வி வகைகளோட mix, messages நடுவுல think time, வழக்கமான prompt, answer நீளங்கள், எதிர்பார்க்குற peak (சொல்லுங்க, இரவு 7 மணிக்கு 300 concurrent users). Locust (Python) அல்லது k6 மாதிரி tools use பண்ணுங்க. குறைவுல இருந்து எதிர்பார்க்குற peak-ஐ தாண்டி ramp பண்ணுங்க, கொஞ்ச நேரம் வச்சிருங்க, p95, error rate, CPU, memory, database connections, provider-ஓட 429 responses-ஐ கவனிங்க.

**Tests-ல model costs.** உண்மையான models-க்கு எதிரா load tests-க்கு உண்மையான காசு செலவாகும், rate limits தீர்ந்துடும். பெரும்பாலான rounds-ஐ, உண்மையான மாதிரி delay-க்கு அப்புறம் பதில் சொல்ற ஒரு fake model server-க்கு எதிரா ஓட்டுங்க, அப்புறம் உண்மையான provider-க்கு எதிரா ஒரு சின்ன, கட்டுப்படுத்தப்பட்ட test.

**பொதுவான bottlenecks-உம் fixes-உம்:**

| Load-ல தெரியுற symptom | சாத்தியமான காரணம் | Fix |
| --- | --- | --- |
| Latency ஏறுது, CPU குறைவு | Database connections அல்லது locks-க்காக காத்திருக்கு | பெரிய pool, indexes, குறைவான queries |
| CPU 100% | ரொம்ப குறைவான workers அல்லது கனமான parsing | அதிக workers, background jobs |
| 429 errors | Provider rate limit | அதிக limit, fallback model, சின்ன outputs |
| முதல் token மட்டும் மெதுவு | நீளமான prompts | Context-ஐ trim பண்ணுங்க, prefix-ஐ cache பண்ணுங்க |
| முழு answers மெதுவு | நீளமான outputs | Answer நீளத்துல cap |
| ஒரு நிமிஷத்துக்கு அப்புறம் errors | Timeouts ரொம்ப குறைவா வச்சிருக்கு | Layers முழுக்க timeouts-ஐ ஒத்து வைங்க |

**ஒரு fake model server கட்டுறது.** Provider-ஓட அதே API உள்ள ஒரு சின்ன service எழுதுங்க. அது முதல் token-க்கு முன்னாடி, உங்க traces-ல இருந்து sample எடுத்த உண்மையான மாதிரி நேரம் காத்திருந்து, அப்புறம் வழக்கமான token rate-ல ஒரு fixed reply-ஐ stream பண்ணும். App-ஐ ஒரு setting வழியா அதை நோக்கி திருப்புங்க. இப்போ நாள் முழுக்க இலவசமா load tests ஓட்டலாம், provider-ஓட சொந்த limits-ஐ தவிர எல்லா bottleneck-ஐயும் கண்டுபிடிக்கலாம்; அந்த limits-ஐ ஒரு சின்ன உண்மையான test check பண்ணும்.

**Result-ஐ report பண்றது.** Users-க்கு எதிரா p95-ஓட ஒரு chart, budget line, ஒவ்வொரு round-லயும் கண்டுபிடிச்ச bottleneck-உம் அதுக்கான fix-உம், அடுத்து எதிர்பார்க்குற ceiling-ஐயும் காட்டுங்க. System அடுத்து எங்க உடையும்ன்னு தெரிஞ்சுக்கிறது clients-க்கு பிடிக்கும், ஏன்னா எதுக்கு plan பண்ணணும்ன்னு அது சொல்லும்.

**ஒரு fake model server.** உண்மையான API-ஓட அதே streaming வடிவம், delays உங்க traces-ல இருந்து sample எடுத்தது:

```python
import asyncio, json, random
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.6, 0.8, 0.9, 1.1, 1.4, 2.2]       # sampled from real traces
TOKENS_PER_S = 60
REPLY = "This is a fixed answer of realistic length used only for load testing. " * 6

@app.post("/v1/messages")
async def messages():
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for word in REPLY.split():
            yield f"data: {json.dumps({'text': word + ' '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Test environment-ல மட்டும், configuration வழியா உங்க app-ஓட model base URL-ஐ இதை நோக்கி திருப்புங்க. ஒரு பங்கு requests-க்கு 429 errors-ஐ திருப்பி தர ஒரு switch சேருங்க, அப்போ உங்க retries, fallbacks test ஆகும்.

**Ramp up ஆகுற ஒரு Locust test.**

```python
from locust import HttpUser, task, between, LoadTestShape
import random

QUESTIONS = [l.strip() for l in open("load/questions.txt")]     # real questions, masked

class Learner(HttpUser):
    wait_time = between(5, 20)                                   # think time between messages

    @task
    def ask(self):
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            for _ in r.iter_lines():
                pass                                             # read the whole stream
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")

class Ramp(LoadTestShape):
    steps = [(60, 10), (120, 50), (180, 100), (240, 200), (300, 300)]   # (end second, users)
    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10
        return None
```

`locust -f load/locustfile.py --host https://staging.example.in --csv results`-ஓட run பண்ணுங்க. CSV files ஒவ்வொரு step-க்கும் p50, p95, p99-ஐ தரும்; users-க்கு எதிரா p95-ஐ plot பண்ணி, உங்க budget line-ஐ mark பண்ணுங்க.

**Time to first token-க்கு தனி measurement வேணும்.** Locust-ஓட built-in timing முழு request-ஐயும் கவர் பண்ணும். Streaming-க்கு, app-ஓட சொந்த traces-ல first-byte time-ஐயும் record பண்ணுங்க, ஒவ்வொரு ramp step-க்கும் p95 first-token time-ஐ அங்க இருந்து படிங்க.

**உண்மையான model-ல ஒரு கட்டுப்படுத்தப்பட்ட run.** Fake server வச்சு bottlenecks-ஐ சரி பண்ணதுக்கு அப்புறம், உங்க rate limits, budget-க்குள்ள, எதிர்பார்க்குற peak-ல உண்மையான model-க்கு எதிரா ஒரு சின்ன test ஓட்டுங்க, provider latency, limits-ஐ உறுதிப்படுத்த. API account-ஐ வச்சிருக்குறவங்களோட அந்த run-ஐ முன்னாடியே ஒத்துக்கோங்க.

**Traces-ஐ திறந்து வச்சு results-ஐ படிங்க.** 100 users-ல p95 திடீர்னு குதிச்சா, அந்த நிமிஷத்தோட மெதுவான traces-ஐ திறங்க. வளர்ந்த step (database waits, reranker, model slots-க்கான queueing) தான் bottleneck, மேல உள்ள fix table பெரும்பாலும் தீர்வை சொல்லிடும்.

**உங்க browser-ல try பண்ணுங்க.** Timings list-ல இருந்து percentiles. Average மெதுவான tail-ஐ மறைச்சுடும்.

```python
import random, statistics

random.seed(6)
timings = [random.gauss(1.2, 0.2) for _ in range(950)] + [random.uniform(4, 9) for _ in range(50)]
timings.sort()
p = lambda q: timings[int(q * (len(timings) - 1))]
print(f"average {statistics.mean(timings):.2f} s")
print(f"p50 {p(0.5):.2f} s, p95 {p(0.95):.2f} s, p99 {p(0.99):.2f} s")
```

## ஒரு worked example

Jaipur-ல ஒரு intercity bus operator, bus bookings, complaints-க்கு ஒரு AI assistant-ஐ launch பண்றாங்க; festival travel-ல 500 concurrent users-ல peak ஆகும்ன்னு எதிர்பார்க்குறாங்க.

Budget: p95-ல first token 2 s-க்கு கீழ, p95-ல முழு answer 10 s-க்கு கீழ, errors 1%-க்கு கீழ.

Round 1, உண்மையான மாதிரி delays உள்ள fake model-க்கு எதிரா: p95 first token 50 users-ல 1.1 s-ல இருந்து 200 users-ல 6 s வரைக்கும் ஏறுது. Requests database connections-க்காக queue-ல நிக்குதுன்னு traces காட்டுது: pool size 10. அதை 40-ஆ ஏத்தி, route table-ல ஒரு index சேர்த்ததும் 500 users-ல p95 1.3 s ஆகுது.

Round 2, 300 users-ல உண்மையான model-க்கு எதிரா 10 நிமிஷ test: provider 429 errors கிட்டத்தட்ட 220 users-ல ஆரம்பிக்குது. Token-per-minute limit தான் ceiling. ரெண்டு வாரம் முன்னாடியே அதிக limit கேக்குறீங்க, gateway வழியா ஒரு fallback model சேக்குறீங்க, answer நீளத்தை 200 tokens-ல cap பண்றீங்க, அது சராசரி generation நேரத்தையும் மூணுல ஒரு பங்கு குறைக்குது.

கடைசி test 550 users-ல budget-ஐ எட்டுது. Launch நாள் peak எந்த சம்பவமும் இல்லாம 480 users வரை போகுது, உங்க report அடுத்த bottleneck-ஐ (கிட்டத்தட்ட 700 users-ல provider limits) பட்டியலிடுது, அதனால client plan பண்ணிக்கலாம்.

| Round | Finding | Fix | Result |
| --- | --- | --- | --- |
| 1, fake model | 200 users-ல p95 6 s; 10 connection pool | 40 pool, route-table index | 500 users-ல p95 1.3 s |
| 2, real model | கிட்டத்தட்ட 220 users-ல இருந்து 429s | அதிக limit, fallback, 200-token cap | 550 users-ல budget எட்டுச்சு |
| Launch நாள் | Peak 480 users | எதுவும் தேவையில்ல | சம்பவங்கள் இல்ல |

## பொதுவா பண்ற தப்புகள்

- **Averages-ஐ report பண்றது.** p95, p99 use பண்ணுங்க.
- **ஒரு நேரத்துல ஒரு request-ஐ மட்டும் test பண்றது.** Concurrency பிரச்சனைகள் (pools, locks, rate limits) load-ல மட்டும் தான் தெரியும்.
- **உண்மையில்லாத traffic.** Think time இல்லாத ஒரே மாதிரி சின்ன prompts தவறான numbers-ஐ தரும்.
- **Real-model load tests-ல காசை எரிக்கிறது.** பெரும்பாலான rounds-க்கு fake model use பண்ணுங்க.
- **Provider limits-ஐ மறந்துடுறது.** அவை தான் பெரும்பாலும் உண்மையான ceiling. சீக்கிரமே check பண்ணி உயர்த்துங்க.
- **ஒவ்வொரு round-க்கும் உண்மையான model-க்கு எதிரா load-test பண்றது**, budget-ஐயும் rate limits-ஐயும் எரிக்கும்.
- **Think time இல்லாம இருக்குறது**, அதனால சில test users ஆயிரக்கணக்கானவங்க மாதிரி நடந்துக்குவாங்க.
- **Streamed answers-க்கு மொத்த நேரத்தை மட்டும் அளக்குறது**; first-token time-ஐயும் track பண்ணுங்க.

## முழு load test காத்திருக்கலாம்ங்கிற நேரங்கள்

- **சில users மட்டும் உள்ள internal tools**: பத்து concurrent requests-ஓட ஒரு quick check போதும்.
- **Batch systems**, அங்க ஒரு user-க்கான latency-ஐ விட ஒரு மணி நேரத்துக்கான throughput முக்கியம்; அதை test பண்ணுங்க.
- **உங்களுக்காக scale ஆகுற platforms**, தாராளமான limits-ஓட, ஆரம்ப pilots-க்கு, rate limits check பண்ணியிருக்கிற வரை.

## Demo-ல இருந்து production-க்கு

- **Step வாரியா ஒரு latency budget வச்சுக்கோங்க**, traces-ஐ அதோட ஒப்பிடுங்க.
- **Launch-க்கு முன்னாடியும் பெரிய மாற்றங்களுக்கு முன்னாடியும் load-test பண்ணுங்க**, பெரும்பாலும் ஒரு fake model server வச்சு.
- **ஒவ்வொரு ramp step-க்கும் p50, p95, p99, errors-ஐ report பண்ணுங்க**, கண்டுபிடிச்ச bottleneck-ஓட.
- **Traffic patterns மாறும்போது திருப்பி test பண்ணுங்க**, exam season அல்லது festival sale மாதிரி.
- **Production-ல p95 first-token time-க்கு alert வைங்க.**
