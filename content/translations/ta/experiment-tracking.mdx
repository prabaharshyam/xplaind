## இது என்ன

**Experiment tracking** ஒவ்வொரு training run-ஐயும் தானா log பண்ணும்: code version (ஒரு Git commit), data version, parameters, metrics, environment (library versions), plots மாதிரி artefacts, train ஆன model. ஒவ்வொரு run-உம் sort பண்ண, compare பண்ண, reproduce பண்ணக்கூடிய ஒரு row ஆகுது.

**Model registry**-னா தேர்ந்தெடுத்த model versions-ஓட ஒரு shelf. ஒவ்வொரு version-க்கும் notes, tags (உதாரணமா, யாரு approve பண்ணாங்க) இருக்கும், அது ஒரு **alias**-ஐயும் வச்சிருக்கலாம்: சரியா ஒரே ஒரு version-ஐ point பண்ற `champion` மாதிரி நகர்த்தக்கூடிய ஒரு பேரு. Production alias-ஐ தான் load பண்ணும், file path-ஐ ஒருபோதும் இல்ல, அதனால deploy ஆன model எதுன்னு எப்பவுமே தெரியும்.

பொதுவான tools: MLflow (open source), Weights & Biases, cloud ML platforms-லயே built-in-ஆ இருக்குற tracking. இந்த lesson MLflow 3-ஐ use பண்ணுது. MLflow-ல, பழைய fixed stages (Staging, Production)-க்கு பதிலா aliases வந்துடுச்சு: version 2.9-ல இருந்தே stages deprecated, MLflow 3.18-ல அவற்றை call பண்ணா அவை remove ஆகப்போகுதுன்னு ஒரு warning print ஆகும்.

```flow
title: From training run to production
Training run 412 | commit a1b2c3d, data claims-2026-09, val PR AUC 0.46
Training run 412 -[team picks it and registers it]-> claims-fraud v14
claims-fraud v14 -[gate on October claims, then owner signs off]-> Alias champion
Alias champion -[loaded at start-up]-> Claim scoring service
Alias champion -[rollback: point it back]-> claims-fraud v13
```

இந்த lesson, Hyderabad-ல மாசா மாசம் claim-fraud model-ஐ retrain பண்ற ஒரு insurer-ஓட ML team-ஐ follow பண்ணுது.

## இது எப்படி work ஆகுது

### ஒரு run-ஐ define பண்ற எல்லாத்தையும் log பண்ணுங்க

| Item | Example | ஏன் முக்கியம் | யாரு record பண்றது |
| --- | --- | --- | --- |
| Parameters | `max_depth=6`, `learning_rate=0.05` | Runs-க்கு நடுவுல இருக்குற வித்தியாசங்களை explain பண்ணும் | நீங்க, அல்லது autologging |
| Metrics | Overall-ஆவும் region வாரியாவும் PR AUC | Winner-ஐ தேர்ந்தெடுக்கும், அது யாருக்கு fail ஆகுதுன்னு காட்டும் | நீங்க (segments எப்பவுமே) |
| Code version | Git commit, clean tree | Training logic-ஐ reproduce பண்ணும் | MLflow, ஒரு Git repo-ல script-ஆ run பண்ணும்போது |
| Data version | `claims-2026-09` கூட ஒரு hash | Inputs-ஐ reproduce பண்ணும் | நீங்க |
| Environment | `requirements.txt`, Python version | "என் machine-ல work ஆகுது" பிரச்சனையை தவிர்க்கும் | MLflow, log ஆகுற ஒவ்வொரு model கூடவும் |
| Model-உம் schema-வும் | Model file, input columns, types | தப்பான inputs-ஐ serving reject பண்ண உதவும் | நீங்க, `log_model` மூலமா |
| Seed | `random_state=42` | Rerun பண்ணா அதே model வரும்படி பண்ணும் | நீங்க |

இந்த ரெண்டு rules தான் இதை நம்பக்கூடியதா ஆக்குது.

- **Commit, run ஆன code-ஐ தான் describe பண்ணணும்.** ஒரு Git repository-க்குள்ள script-ஐ run பண்ணும்போது MLflow commit-ஐ `mlflow.source.git.commit` tag-ஆ record பண்ணும், ஆனா uncommitted edits-ஐ அது கவனிக்காது. பாதி edit ஆன ஒரு file-ல இருந்தோ notebook-ல இருந்தோ வர்ற run, அதை ஒருபோதும் உருவாக்காத ஒரு commit-ஐ point பண்ணும். அதனால கீழே இருக்குற script, uncommitted changes இருந்தா run ஆக மறுக்கும். Notebook-ல, முதல்ல commit பண்ணுங்க, இல்லைன்னா training code-ஐ ஒரு script-க்கு மாத்துங்க.
- **Data-வோட பேரு data version இல்ல.** `claims-2026-09` வெறும் ஒரு label தான்; அதுக்கு பின்னாடி இருக்குற file-ஐ யாராவது overwrite பண்ணலாம். அதே இடத்துல ஒருபோதும் edit ஆகாத snapshots-ஐ store பண்ணுங்க, file-ஓட hash-ஐ log பண்ணுங்க, அப்போ சத்தமில்லாம நடக்குற மாற்றம் வெளிய தெரியும். DVC மாதிரி tools, அல்லது Delta Lake மாதிரி table formats-ல இருக்குற time travel, பழைய versions-ஐ உங்களுக்காக வச்சிருக்கும் (data versioning lesson-ஐ பாருங்க).

**Autologging** (`mlflow.autolog()`) scikit-learn, XGBoost மாதிரி libraries-க்கு பெரும்பாலான parameters-ஐயும் metrics-ஐயும் ஒரே line-ல capture பண்ணும். உங்க data version-ஓ segments-ஓ அதுக்கு தெரியாது, அதனால அவற்றை நீங்களே சேருங்க.

### ஒரு training run-ஐ track பண்றது

இந்த script fraud model-ஐ train பண்ணி ஒரு run-ஐ log பண்ணுது. Claims table-ல ஒரு `region` column, ஒரு `region_code` feature, ஒரு `is_fraud` label இருக்குன்னு இது assume பண்ணுது.

```python
import hashlib, subprocess, sys
import mlflow
import pandas as pd
from mlflow.models import infer_signature
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import average_precision_score
from sklearn.model_selection import train_test_split

DATA = "data/claims-2026-09.parquet"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]

def git(*args):
    return subprocess.run(["git", *args], capture_output=True, text=True, check=True).stdout.strip()

if git("status", "--porcelain", "--untracked-files=no"):   # ignores mlflow.db and mlruns/
    sys.exit("Uncommitted changes: commit first, or this run cannot be reproduced.")

with open(DATA, "rb") as f:
    data_sha = hashlib.file_digest(f, "sha256").hexdigest()[:12]   # Python 3.11 or newer

df = pd.read_parquet(DATA)
df[FEATURES] = df[FEATURES].astype("float64")      # floats can hold missing values at serving time
train, val = train_test_split(df, test_size=0.2, stratify=df["is_fraud"], random_state=42)
params = {"max_depth": 6, "learning_rate": 0.05, "max_iter": 300, "random_state": 42}

mlflow.set_experiment("claims-fraud")
with mlflow.start_run() as run:
    mlflow.set_tags({"data_version": "claims-2026-09", "data_sha256": data_sha})
    mlflow.log_input(mlflow.data.from_pandas(train, source=DATA, targets="is_fraud"), context="training")
    mlflow.log_params(params)

    model = HistGradientBoostingClassifier(**params).fit(train[FEATURES], train["is_fraud"])
    proba = model.predict_proba(val[FEATURES])
    mlflow.log_metric("val_pr_auc", average_precision_score(val["is_fraud"], proba[:, 1]))
    for region, part in val.groupby("region"):
        s = model.predict_proba(part[FEATURES])[:, 1]
        mlflow.log_metric(f"val_pr_auc_{region}", average_precision_score(part["is_fraud"], s))

    mlflow.sklearn.log_model(
        model, name="model",
        signature=infer_signature(val[FEATURES], proba),
        input_example=val[FEATURES].head(3),
        pyfunc_predict_fn="predict_proba",
        skops_trusted_types=["sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor"],
    )
    print("run", run.info.run_id)
```

ஒவ்வொரு MLflow 3 detail-உம் என்ன பண்ணுது (MLflow 3.18-ல check பண்ணது, November 2026):

- **`name="model"`** பழைய `artifact_path` argument-க்கு பதிலா வருது; அது இன்னும் work ஆகும், ஆனா இப்போ ஒரு deprecation warning log பண்ணும்.
- **`registered_model_name` இல்ல.** Training script-க்குள்ளயே register பண்ணா ஒவ்வொரு experiment-க்கும் ஒரு registry version உருவாகும். ஒவ்வொரு run-ஐயும் log பண்ணுங்க; winner-ஐ மட்டும் register பண்ணுங்க.
- **`signature`-உம் `input_example`-உம்** input columns-ஐயும் types-ஐயும் model கூடவே store பண்ணும், அதனால ஒரு column missing-ஆவோ spelling தப்பாவோ இருக்குற request-ஐ serving reject பண்ண முடியும். Features முதல்ல floats-ஆ cast பண்ணப்படுது: integer-ஆ infer ஆன ஒரு column-ல serving time-ல ஒரு value missing-ஆ இருந்தா check fail ஆகும். அப்புறம் ஒவ்வொரு caller-உம் floats-ஐயே அனுப்பணும்; integer columns-ஐ check reject பண்ணும். (MLflow இன்னும் integer columns பத்தி ஒரு hint print பண்ணலாம்: அது logged dataset-ல இருக்குற `is_fraud` label-ஐ பத்தினது, model-ஐ இல்ல.) MLflow model பக்கத்துலயே `requirements.txt`, `conda.yaml`-ஐயும் எழுதும்.
- **`log_input`** run-ஐ dataset கூட link பண்ணி, அதோட ஒரு சின்ன digest-ஐ store பண்ணும்; உங்க சொந்த hash-ஐ தவிர இது இன்னொரு check.
- **`pyfunc_predict_fn="predict_proba"`** generic loader-ஐ hard-ஆன 0 அல்லது 1 labels-ஐ இல்லாம, fraud probabilities-ஐ return பண்ண வைக்கும்.
- **`skops_trusted_types`.** MLflow இப்போ scikit-learn models-ஐ skops-ல save பண்ணுது; இது pickle-ஐ விட safe-ஆன format, ஏன்னா ஒரு pickle-ஐ load பண்ணா file-ல ஒளிஞ்சிருக்குற எந்த code-ஐயும் run பண்ண முடியும். Trust பண்ண சொல்லாத object types-ஐ skops ஏத்துக்காது, `HistGradientBoostingClassifier`-க்கு இந்த ஒண்ணு தேவை. நீங்க check பண்ண types-ஐ மட்டும், நீங்களே train பண்ண models-க்கு மட்டும் trust பண்ணுங்க.

Default-ஆ MLflow 3.18 runs-ஐ நீங்க run பண்ற folder-ல `mlflow.db`-ங்குற ஒரு local SQLite file-ல எழுதும். அவற்றை browse பண்ண அங்கேயே `mlflow ui` run பண்ணுங்க.

### Promotion check: அதே data, உண்மையான gains, ஒவ்வொரு segment-உம்

இங்க தான் trap இருக்கு. Champion-ஓட logged PR AUC போன மாச validation split-ல இருந்து வந்தது; candidate-ஓடது இந்த மாசத்துல இருந்து. Fraud patterns-உம் fraud-ஓட share-உம் மாசத்துக்கு மாசம் மாறும், அதனால அந்த ரெண்டு numbers-ஐ compare பண்றது, models-ஐ compare பண்ற அளவுக்கு data-வையும் compare பண்ணுது. Fair test-னா **ரெண்டு models-ஐயும் அதே fresh holdout-ல** score பண்றது, அதுல எதுவுமே train ஆகியிருக்கக் கூடாது: இங்க, October-ஓட claims.

Insurer-ஓட rule-க்கு மூணு parts இருக்கு:

1. **Overall gain noise-ஐ தாண்டி தெளிவா இருக்கணும்.** Holdout claims-ஐ பல தடவை resample பண்ணி (ஒரு bootstrap) ஒவ்வொரு தடவையும் PR AUC gain-ஐ recompute பண்ணுங்க. Gain-ஓட 90% interval zero-க்கு மேலயே இருந்தா மட்டும் promote பண்ணுங்க.
2. **எந்த region-உம் fraud-catching recall-ஐ இழக்கக் கூடாது.** Investigators மாசத்துக்கு top 5% claims-ஐ மட்டும் தான் check பண்ண முடியும். ஒவ்வொரு region-க்கும், அதோட fraud cases-ல எவ்வளவு share அந்த top 5%-க்குள்ள வருதுன்னு measure பண்ணுங்க. எந்த region-உம் 2 points-க்கு மேல குறையக் கூடாது.
3. **Check-ஓட report-ஐ படிச்சப்புறம் ஒரு owner sign off பண்ணணும்.**

```python
import numpy as np
import pandas as pd
import mlflow
from mlflow import MlflowClient
from sklearn.metrics import average_precision_score

NAME = "claims-fraud"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]
REVIEW_RATE = 0.05        # investigators can check the top 5% of claims each month
MAX_RECALL_DROP = 0.02    # no region may lose more than 2 points of recall
client = MlflowClient()

def scores_of(version, X):
    model = mlflow.pyfunc.load_model(f"models:/{NAME}/{version}")
    return model.predict(X)[:, 1]          # column 1 = probability of fraud

def recall_by_region(y, s, region):
    flagged = np.zeros(len(s), dtype=bool)
    flagged[np.argsort(-s)[: int(len(s) * REVIEW_RATE)]] = True   # the claims investigators open
    return {r: flagged[(region == r) & (y == 1)].mean() for r in np.unique(region)}

def pr_auc_gain_interval(y, s_new, s_old, n=500, seed=0):
    rng = np.random.default_rng(seed)
    gains = []
    for _ in range(n):
        i = rng.integers(0, len(y), len(y))   # resample claims with replacement
        gains.append(average_precision_score(y[i], s_new[i]) - average_precision_score(y[i], s_old[i]))
    return np.percentile(gains, [5, 95])

def check(candidate, holdout):
    champion = client.get_model_version_by_alias(NAME, "champion").version
    X = holdout[FEATURES].astype("float64")      # match the logged signature, or loading code rejects it
    y, region = holdout["is_fraud"].to_numpy(), holdout["region"].to_numpy()
    s_new, s_old = scores_of(candidate, X), scores_of(champion, X)

    low, high = pr_auc_gain_interval(y, s_new, s_old)
    problems = []
    if low <= 0:
        problems.append(f"PR AUC gain not clear: 90% interval {low:+.3f} to {high:+.3f}")
    r_new, r_old = recall_by_region(y, s_new, region), recall_by_region(y, s_old, region)
    for r in r_old:
        if r_new[r] < r_old[r] - MAX_RECALL_DROP:
            problems.append(f"{r}: recall {r_old[r]:.2f} -> {r_new[r]:.2f}")
    return champion, problems

holdout = pd.read_parquet("data/claims-2026-10.parquet")    # last month: neither model trained on it
champion, problems = check(candidate="14", holdout=holdout)
print("blocked:" if problems else "passed: ready for owner sign-off", problems)
```

மூணு எச்சரிக்கைகள். Holdout ஒரு judge-ஆ இருக்கணும், coach-ஆ இல்ல: October claims-ல pass ஆகுற வரை ஆளுங்க models-ஐ tune பண்ணிட்டே இருந்தா, October fresh-ஆ இருக்காது. 2-point limit ஒரு business decision; results-ஐ யாராவது பார்க்குறதுக்கு முன்னாடியே fraud team கூட அதை ஒத்துக்கோங்க. அப்புறம் சுமார் 150 fraud cases இருக்குற ஒரு region-ல வெறும் மூணு cases பக்கம் மாறினாலே 2 points நகரும், அதனால இந்த guardrail வேணும்னே noisy-ஆ இருக்கு: அப்பப்போ ஒரு நல்ல model-ஐயும் block பண்ணும், ரெண்டு தப்புல அது தான் செலவு கம்மியானது. Block ஆன model ஒரு ஆள்கிட்ட போகும், குப்பைக்கு இல்ல.

### Aliases-ஐ நகர்த்தி promote, roll back பண்ணுங்க

```python
from mlflow import MlflowClient
NAME = "claims-fraud"
client = MlflowClient()

def promote(candidate, champion, approver):
    client.set_model_version_tag(NAME, candidate, "approved_by", approver)
    client.set_registered_model_alias(NAME, "previous", champion)
    client.set_registered_model_alias(NAME, "champion", candidate)

def rollback():
    previous = client.get_model_version_by_alias(NAME, "previous").version
    client.set_registered_model_alias(NAME, "champion", previous)
```

Serving code `mlflow.pyfunc.load_model("models:/claims-fraud@champion")`-ஐ load பண்ணும். ஓடிக்கிட்டு இருக்குற server model-ஐ ஒரே ஒரு தடவை, start-up-ல, load பண்ணுச்சு, அதனால service reload அல்லது restart ஆகுற வரை alias-ஐ நகர்த்துறதால எதுவுமே மாறாது. Reload-ஐ promotion, rollback steps-ஓட ஒரு பகுதியா ஆக்குங்க, ஒவ்வொரு prediction கூடவும் served version-ஐ log பண்ணுங்க, அப்போ lineage ஒரு தனி decision வரைக்கும் போய் சேரும்.

### Gain உண்மையா? உங்க browser-லயே try பண்ணுங்க

ரெண்டு models அதே 6,000 claims-ஐ score பண்ணுது, அதுல சுமார் 3% fraud. Candidate நல்லா தெரியுது, ஆனா இதே மாதிரி claims இருக்குற வேற ஒரு மாசத்துலயும் gain நிலைக்குமான்னு bootstrap கேக்குது.

```python
import numpy as np
from sklearn.metrics import average_precision_score

rng = np.random.default_rng(7)
n = 6000                                    # one month of claims, about 3% of them fraud
y = (rng.random(n) < 0.03).astype(int)
signal = 2.5 * y + rng.normal(0, 1, n)      # the pattern both models learned
champion = signal + rng.normal(0, 0.60, n)  # each model adds its own errors
candidate = signal + rng.normal(0, 0.55, n) # slightly fewer errors

print("champion PR AUC ", round(average_precision_score(y, champion), 3))
print("candidate PR AUC", round(average_precision_score(y, candidate), 3))

gains = []
for _ in range(200):                        # resample the same claims for both models
    i = rng.integers(0, n, n)
    gains.append(average_precision_score(y[i], candidate[i]) - average_precision_score(y[i], champion[i]))
low, high = np.percentile(gains, [5, 95])
print(f"90% interval for the gain: {low:+.3f} to {high:+.3f}")
print("promote" if low > 0 else "too close to call: keep the champion")
```

இது PR AUC 0.439-ஐயும் 0.472-ஐயும் print பண்ணும், ஆனாலும் interval சுமார் -0.02-ல இருந்து +0.07 வரை போகுது: 200-க்கும் குறைவான fraud cases-ல ஒரு 0.03 gain இன்னும் proof இல்ல. Candidate-ஓட `0.55`-ஐ `0.30`-ஆ மாத்தி திரும்ப run பண்ணுங்க: இப்போ promote பண்ற அளவுக்கு gain பெருசா இருக்கும்.

### LLM apps-க்கும் இதே idea

ஒரு prompt அல்லது retrieval change-ஐ ஒரு experiment-ஆ பாருங்க. Prompt version, model name, top-k, chunk size, category வாரியான eval scores-ஐ ஒரு run-ஆ log பண்ணுங்க. அப்போ "prompt-ஓட version 13 Hindi questions-க்கு உதவுச்சா?"ங்குறது ஒரு sorted table ஆகும், ஞாபகம் இல்ல. அதே noise rule இங்கயும் பொருந்தும்: 50 eval questions-ல ஒரு 2-point gain பெரும்பாலும் chance தான்.

## ஒரு worked example

Hyderabad insurer-ஓட ML team மாசா மாசம் அதோட claim-fraud model-ஐ retrain பண்ணுது. Tracking வர்றதுக்கு முன்னாடி, models `final_v3_really_final.pkl` மாதிரி பேருள்ள files-ஆ இருந்துச்சு; production model-ஐ எந்த data train பண்ணுச்சுன்னு ஒரு auditor கேட்டப்போ, யாராலயும் சொல்ல முடியல.

இப்போ ஒவ்வொரு run-உம் அதோட parameters, commit, data snapshot-உம் hash-உம், overall-ஆவும் region வாரியாவும் validation PR AUC-ஐ log பண்ணுது. கீழே இருக்குற numbers ஒரு illustration-க்கு மட்டும் தான்.

| Run | மாற்றம் | Val PR AUC (சொந்த split) | Weakest region | முடிவு |
| --- | --- | --- | --- | --- |
| 398 | போன மாச champion, v13, August data-ல train ஆனது | 0.41 | 0.33 | Baseline |
| 405 | இன்னும் deep-ஆன trees | 0.42 | 0.31 | Drop பண்ணியாச்சு: weakest region குறைஞ்சுது |

**Banking, lending-ல இதே கேள்விகள் எழுத்துப்பூர்வமா வரும்னு எதிர்பார்க்கலாம்.** August 2025-ல RBI, finance-ல responsible AI பத்தி, அது அமைச்ச ஒரு committee எழுதுன FREE-AI report-ஐ publish பண்ணுச்சு. அதோட recommendations-ல இதுவும் இருக்கு: regulated entities அவங்க AI models-ஓட ஒரு inventory-ஐ வச்சுக்கணும், risk அடிப்படையில அவற்றை audit பண்ணணும். இவை recommendations தான், rules இல்ல, ஆனா lineage, approvals, model cards இருக்குற ஒரு registry தான் ரெண்டுக்குமே தேவையான raw material.

## பொதுவா பண்ற தப்புகள்

- **Spreadsheets-ல கையால track பண்றது.** அது முழுசா இருக்காது, பழசாயிடும், data version-ஐ ஒருபோதும் record பண்ணாது.
- **Data-வோட பேரை data version-ஆ நினைக்கிறது.** அதே பேருல overwrite ஆன ஒரு file சத்தமில்லாம reproducibility-ஐ உடைக்கும்; ஒரு hash-ஐ log பண்ணுங்க, snapshots-ஐ read-only-ஆ வச்சுக்கோங்க.
- **Commit ஆகாத code-க்கு ஒரு commit-ஐ log பண்றது.** Notebook edits-உம் uncommitted changes-உம் commit tag-ஐ பொய்யா ஆக்கிடும்.
- **வேற வேற மாசங்களோட logged metrics-ஐ compare பண்றது.** Champion-ஐயும் candidate-ஐயும் அதே fresh holdout-ல score பண்ணுங்க.
- **ரொம்ப சின்ன gain-ஐ வச்சு promote பண்றது.** சில நூறு positive cases இருந்தா, 0.01-ல இருந்து 0.03 வரையான மாற்றம் chance-ஆ இருக்கலாம்.
- **Overall score-ஐ மட்டும் வச்சு promote பண்றது.** Overall gain, ஒரு region அல்லது customer group-க்கு நடக்குற loss-ஐ மறைக்கலாம்.
- **Models-ஐ தேர்ந்தெடுக்க test set-ஐ திரும்ப திரும்ப use பண்றது.** அதுக்கு எதிரா tune பண்ண ஆரம்பிச்சதுமே, அது future-ஐ measure பண்ணாது.
- **ஒவ்வொரு run-ஐயும் register பண்றது.** Registry experiments-ஆல நிரம்பிடும்; ship பண்ண வாய்ப்பு இருக்குறதை மட்டும் register பண்ணுங்க.
- **Production-ல ஒரு file path-ஐ load பண்றது.** ஒரு registry alias-ல இருந்து serve பண்ணுங்க, ஒரு `previous` alias-ஐ வச்சுக்கோங்க, alias நகரும்போது service-ஐ reload பண்ணுங்க.
- **Empty-ஆ இருக்கக்கூடிய integer input columns.** Infer ஆன signature அவற்றை integers-ஆ mark பண்ணும், அதனால serving time-ல ஒரு missing value schema check-ஐ fail ஆக்கும்; அந்த மாதிரி columns-க்கு floats use பண்ணுங்க.
- **Fail ஆன runs-ஐ delete பண்றது, அல்லது ஒரே laptop-ல track பண்றது.** Fail ஆன runs எது work ஆகாதுன்னு காட்டும்; ஒரே laptop-ல இருக்குற history அந்த laptop கூடவே போயிடும்.

## Tracking-ஐ எப்போ இலகுவா வச்சுக்கலாம்

- **ஒரே ஒரு quick experiment**: results-ஐ எழுதி வச்ச ஒரு notebook போதுமா இருக்கலாம்.
- **Prompt மட்டும் இருக்குற prototypes**: prompt versions, scores-ஓட ஒரு spreadsheet நல்ல ஆரம்பம் தான், ஒருத்தருக்கு மேல prompts-ஐ மாத்த ஆரம்பிக்குற வரை.
- **ஒரு தடவை train பண்ணி, அரிதா மாறுற model**: அதோட lineage-ஐ ஒரு தடவை, கவனமா record பண்ணுங்க, அப்பவும் அதை ஒரு registry-ல இருந்து தான் serve பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **ஒரு shared tracking server-ஐ run பண்ணுங்க**: database backend, artefacts-க்கு cloud storage, company-ஓட sign-in-க்கு பின்னாடி; உதாரணமா `mlflow server --backend-store-uri postgresql://... --artifacts-destination s3://...`. அதை back up பண்ணுங்க: அது தான் ஒவ்வொரு model decision-ஓட history.
- **Pipeline-ல tracking-ஐ automatic ஆக்குங்க**, அப்போ log ஆகாம ஒரு run நடக்கவே முடியாது.
- **Promotion-ஐ code-ல gate பண்ணுங்க**: அதே fresh holdout-ல, noise checks, segment checks-ஓட; அப்புறம் ஒரு owner-ஓட sign-off-ஐ கட்டாயமாக்குங்க.
- **ஒரு alias-ல இருந்து serve பண்ணுங்க**, ஒவ்வொரு prediction கூடவும் served version-ஐ log பண்ணுங்க, தேவைப்படுறதுக்கு முன்னாடியே ஒரு rollback-ஐ rehearse பண்ணுங்க.
- **Prompt, retrieval experiments-ஐ** training runs மாதிரியே track பண்ணுங்க.

## Practice பண்ணுங்க

MLflow-ஓட tracking guide-ஐயும், Made With ML-ஓட experiment tracking, versioning lessons-ஐயும் படிங்க.

1. ஒரு training script-ல tracking சேருங்க: parameters, per-segment metrics, ஒரு clean commit, ஒரு data hash, signature-ஓட model. Uncommitted edit இருந்தா script run ஆக மறுக்குதான்னு check பண்ணுங்க.
2. ரெண்டு settings-ஐ மாத்தி மாத்தி பத்து experiments run பண்ணி, `mlflow ui`-ல compare பண்ணுங்க. Overall-ஆ ஜெயிச்சு ஒரு segment-ல தோக்குற ஒரு run-ஐ கண்டுபிடிங்க.
3. Best-ஆன ரெண்டை register பண்ணி, ஒண்ணை `champion`-ஆ set பண்ணி, ரெண்டுமே train ஆகாத ஒரு holdout-ல இன்னொண்ணுக்கு எதிரா promotion check-ஐ run பண்ணுங்க.
4. Promote பண்ணுங்க, அப்புறம் roll back பண்ணுங்க, புதுசா start பண்ண ஒரு prediction script பழைய version-ஐ load பண்ணுதான்னு confirm பண்ணுங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** ஒரு தனி prediction-ஐ, அதை உருவாக்குன model version, run, code commit, data snapshot வரை trace பண்ண முடியும்போது தான்.
