## இது என்ன

**Transformer**-னா 2017-ல அறிமுகமான ஒரு neural network architecture; **attention**-னு ஒரு mechanism-ஐ சுத்தி build ஆனது. இது ஒரு sequence-ஐ (வார்த்தைகள், image patches, audio frames) process பண்ணும். ஒவ்வொரு layer-லயும், ஒவ்வொரு position-உம் மத்த positions-ல இருந்து எவ்வளவு எடுக்கணும்னு முடிவு பண்ணும்.

மூணு families இதை use பண்ணுது:

- **Decoder-only** models ஒரு நேரத்துல ஒரு token-ஆ text generate பண்ணும். Llama family மாதிரி இன்னைக்கு இருக்குற open chat, coding models இப்படி தான் build ஆகியிருக்கு.
- **Encoder-only** models முழு text-ஐயும் ஒரே நேரத்துல படிச்சு representations உருவாக்கும்: classifiers, search-க்கான நிறைய embedding models. Qwen3-Embedding (June 2025) மாதிரி சில புது embedding models இதுக்கு பதிலா decoder models-ல இருந்து build ஆனது.
- **Encoder-decoder** models ஒரு sequence-ஐ படிச்சு இன்னொண்ணை எழுதும்: translation, summarisation.

Vision transformers ஒரு image-ஐ patches-ஆ வெட்டி, ஒவ்வொரு patch-ஐயும் ஒரு token மாதிரி நடத்தும்.

கீழ இருக்குற table, ஒரு head-ல "it" வார்த்தையில இருந்து வர்ற attention-ஐ காட்டுது. இந்த numbers விளக்கத்துக்காக மட்டும் தான், ஒரு நிஜ model-ல இருந்து எடுத்தது இல்லை.

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| Encoder (ரெண்டு பக்கமும் பார்க்கும்) | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |
| Decoder (முன்னாடி வந்ததை மட்டும் பார்க்கும்) | 0.03 | **0.45** | 0.06 | 0.02 | 0.36 | 0.03 | 0.05 | 0 | 0 | 0 |

Encoder-ஆல "trusted"-ஐ பார்க்க முடியும்; "it"-னா bank தான்னு அது தான் சொல்லுது (ஒரு loan யாரையும் trust பண்ணாது). Decoder-ஆல பின்னாடி வர்ற வார்த்தைகளை பார்க்க முடியாது, அதனால "it"-ல நிக்கும்போது "bank"-ஆ "loan"-ஆன்னு இன்னும் முடிவாகல. "trusted" மாதிரி பின்னாடி வர்ற tokens திரும்பி பார்த்து அதை முடிவு பண்ணும். ஒவ்வொரு row-ஓட கூட்டுத்தொகையும் 1.

## இது எப்படி work ஆகுது

### Tokens, embeddings

ஒரு **tokenizer** text-ஐ tokens-ஆ split பண்ணும்: முழு வார்த்தைகள், வார்த்தைகளோட துண்டுகள், அல்லது தனி bytes. நிறைய chat-model tokenizers byte-pair encoding use பண்ணும்: bytes-ல ஆரம்பிச்சு, அடிக்கடி பக்கத்து பக்கத்துல வர்ற pairs-ஐ திரும்ப திரும்ப merge பண்ணி புது tokens ஆக்கும். அப்புறம் ஒவ்வொரு token id-உம் கத்துக்கிட்ட ஒரு table-ல இருந்து ஒரு row-ஐ select பண்ணும்; அது ஒரு vector (ஒரு **embedding**) தரும். உதாரணமா, Llama 3 8B-க்கு 128,256 tokens vocabulary இருக்கு, vectors 4,096 numbers அகலம்.

Tokenizers தங்களோட merges-ஐ training text-ல இருந்து கத்துக்கும்; அதனால அந்த text-ல அரிதா இருந்த languages அதிக துண்டுகளா உடையும். OpenAI-ஓட பழைய `cl100k_base`, புது `o200k_base` tokenizers வச்சு ஒரு sentence-ஐ நாங்க count பண்ணோம் (November 2026):

| Sentence | cl100k_base | o200k_base |
| --- | --- | --- |
| The bank approved the loan. | 6 | 6 |
| Bank ne loan approve kar diya. | 8 | 7 |
| बैंक ने लोन मंज़ूर कर दिया। | 31 | 11 |

புது tokenizer-லயும் Hindi sentence-க்கு English sentence-ஐ விட கிட்டத்தட்ட ரெண்டு மடங்கு tokens தேவைப்படுது. அதிக tokens-னா அதிக bill, slow-ஆன replies, context-ல குறைவான இடம். Indian languages-ல AI பத்தின lesson இதை இன்னும் ஆழமா பார்க்குது.

### Position

Attention தானா order-ஐ கண்டுக்காது: வார்த்தைகளை shuffle பண்ணாலும் ஒவ்வொரு token-க்கும் அதே mix தான் கிடைக்கும். அதனால model-க்கு position information வேணும். 2017 transformer-உம் BERT-உம் ஒவ்வொரு embedding-ஓடயும் ஒரு position vector-ஐ **சேர்த்துச்சு**. BERT இப்படி 512 vectors கத்துக்கிச்சு; அதனால தான் அதால 512 tokens-ஐ தாண்டி படிக்க முடியாது.

Llama-family models-உம் ModernBERT-உம் இதுக்கு பதிலா **rotary position embeddings (RoPE)** use பண்ணுது. ஒவ்வொரு attention layer-க்குள்ளயும், ஒவ்வொரு query-ஐயும் key-ஐயும் அதோட position-ஐ பொறுத்த ஒரு angle-ல rotate பண்ணும். அப்போ ரெண்டு tokens-க்கு இடையிலான score அவை எவ்வளவு தூரத்துல இருக்குங்குறதை பொறுத்து இருக்கும். கொஞ்சம் extra training கொடுத்தா, model முதல்ல பார்த்ததை விட நீளமான contexts-க்கு rotary embeddings-ஐ stretch பண்ணலாம்; context windows வளர்ந்ததுக்கு இதுவும் ஒரு வழி.

### Attention

ஒவ்வொரு token-உம் கத்துக்கிட்ட மூணு matrices-ஐ use பண்ணி, தன்னோட embedding-ல இருந்து மூணு vectors கணக்கிடும்:

- ஒரு **query**: நான் எதை தேடுறேன்?
- ஒரு **key**: என்னை எதை வச்சு match பண்ணலாம்?
- ஒரு **value**: என்னை select பண்ணா நான் என்ன கடத்துவேன்?

Model ஒரு token-ஓட query-க்கும் ஒவ்வொரு key-க்கும் dot product எடுக்கும். பெரிய dot product-னா "relevant". அப்புறம் scores-ஐ key size-ஓட square root-ஆல வகுக்கும்; ஏன்னா vector size கூட கூட dot products-உம் கூடும், ரொம்ப பெரிய scores வந்தா softmax ஒரே ஒரு token-ஐ மட்டும் pick பண்ணிட்டு கத்துக்குறதை நிறுத்திடும். ஒரு **softmax** scores-ஐ கூட்டுத்தொகை 1 வர்ற weights-ஆ மாத்தும். Output-னா values-ஓட weighted sum: அந்த token attend பண்ணதை கலந்து உருவான ஒரு புது vector.

ஒரு decoder-ல, softmax-க்கு முன்னாடி ஒரு **causal mask** எதிர்கால tokens-ஓட scores-ஐ minus infinity-ஆ set பண்ணும், அதனால அவற்றோட weights சரியா 0 ஆகும். அது இல்லைன்னா, training-ல ஒவ்வொரு position-உம் அது predict பண்ண வேண்டிய token-ஐயே பார்த்துடும்.

Mask-ஓட ஒரு head, NumPy-ல:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                  # relevance of every token to every other
    if causal:                                     # hide future tokens
        future = np.triu(np.ones_like(scores), k=1) == 1
        scores = np.where(future, -np.inf, scores)
    weights = softmax(scores)                      # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "because", "she"]
x = rng.normal(size=(len(tokens), 16))             # one 16-number vector per token
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(out.shape)                                   # (6, 8): one new vector per token
print(np.round(w, 2))                              # zeros above the diagonal
```

முதல் row `[1, 0, 0, 0, 0, 0]`: "Priya" தன்னை மட்டும் தான் attend பண்ண முடியும். இங்க weights random. Train ஆன ஒரு model-ல, "she"-க்கான row "Priya" மேல அதிக weight போடும்.

### Multi-head attention, layer

பல heads பக்கத்துல பக்கத்துல ஓடும், ஒவ்வொண்ணுக்கும் தனியா query, key, value matrices இருக்கும்; அதனால ஒவ்வொண்ணும் வேற ஒரு relationship-ஐ கத்துக்கலாம். Width 768, 12 heads-னா, ஒவ்வொரு head-உம் 64 numbers-ல வேலை செய்யும்; outputs திரும்ப 768-ஆ சேர்க்கப்பட்டு, இன்னொரு matrix-ஆல கலக்கப்படும். PyTorch-ல இது built-in-ஆவே இருக்கு:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                      # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)   # True = hidden
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                    # (2, 10, 768) and (2, 10, 10)
```

ஒரு layer-னா attention, அதுக்கு அப்புறம் ஒவ்வொரு token-லயும் தனித்தனியா வேலை செய்யுற ஒரு **feed-forward** network. Shortcut connections ஒவ்வொரு block-ஓட input-ஐயும் அதோட output-ஓட திரும்ப சேர்க்கும், அதனால deep stacks-ஐயும் train பண்ண முடியும். 2017 model ஒவ்வொரு block-க்கும் அப்புறம் normalise பண்ணுச்சு; Llama-style models ஒவ்வொரு block-க்கும் முன்னாடி normalise பண்ணும் (RMSNorm வச்சு), இது இன்னும் stable-ஆ train ஆகும். பெரிய models இந்த மாதிரி டஜன் கணக்கான layers-ஐ stack பண்ணும்.

```flow
dir: TB
title: Llama style-ல ஒரு decoder layer, ஒவ்வொரு layer-லயும் திரும்ப வருது
Token vectors -> Normalise
Normalise -> Masked multi-head attention | queries, keys-க்கு rotary positions apply ஆகும்
Masked multi-head attention -> Input-ஐ திரும்ப சேர்க்கும்
Input-ஐ திரும்ப சேர்க்கும் -> மறுபடி Normalise
மறுபடி Normalise -> Feed-forward | gated, கிட்டத்தட்ட 3.5 மடங்கு அகலம்
Feed-forward -> மறுபடி சேர்க்கும்
மறுபடி சேர்க்கும் -> அடுத்த layer
```

### Generation, KV cache, sampling

ஒரு decoder கடைசி position-ஓட vector-ஐ அதோட vocabulary-ல இருக்குற ஒவ்வொரு token-க்கும் ஒரு score-ஆ மாத்தி, அப்புறம் ஒண்ணை pick பண்ணும். **Temperature** softmax-க்கு முன்னாடி scores-ஐ வகுக்கும்: 1-க்கு கீழ இருந்தா choice safe-ஆ இருக்கும், 1-க்கு மேல இருந்தா variety அதிகமா இருக்கும். **Top-p** probabilities-ஓட கூட்டுத்தொகை p (உதாரணமா 0.9) வர்ற வரை ரொம்ப likely ஆன tokens-ஐ மட்டும் வச்சு, அதுல இருந்து sample பண்ணும். Choose ஆன token சேர்க்கப்படும், loop மறுபடி ஓடும்.

ஒவ்வொரு step-லயும் முழு text-க்கும் keys, values-ஐ மறுபடி கணக்கிடுறது வேஸ்ட், அதனால model அவற்றை store பண்ணி வைக்கும்: அது தான் **KV cache**. ஒவ்வொரு புது token-உம் தன்னோட query, key, value-ஐ மட்டும் கணக்கிட்டு cache-ஐ attend பண்ணும். இதனால generation fast-ஆ இருக்கும், ஆனா ஒவ்வொரு token-ஓடயும் ஒவ்வொரு user-ஓடயும் cache வளரும்.

### நீளமான context-ஓட மூணு costs

| Cost | எதோட வளரும் | உங்களுக்கு இதுக்கு என்ன அர்த்தம் |
| --- | --- | --- |
| API bill | Tokens, linear-ஆ | Prompt-ல இருக்குற ஒவ்வொரு extra token-க்கும், ஒவ்வொரு call-லயும் காசு கட்டணும் |
| KV cache memory | Tokens × users | நீளமான chats-உம் நிறைய users-உம் GPU memory-ஐ நிரப்பிடும் |
| Attention compute | Length-ஓட square | Context நீளமான பிறகு தான் இது முக்கியம் |

Llama 3 8B shape-க்கு, ஒவ்வொரு புது token-உம் ஒவ்வொரு layer-லயும் weight matrices-ல சுமார் 218 million multiply-adds பண்ணும், அது attend பண்ற முன்னாடி இருக்குற ஒவ்வொரு token-க்கும் இன்னும் சுமார் 8,000 (config-ல இருந்து போட்ட rough கணக்கு). 2,000 tokens-ல attention வேலையில பத்துல ஒரு பங்குக்கும் குறைவு; கிட்டத்தட்ட 27,000 tokens-ல தான் அது சமமா வரும். முழு sequence-க்கும் பார்த்தா, attention வேலை square-ஆ வளரும்: 8,000 tokens-க்கு 1,000 tokens-ஐ விட சுமார் 64 மடங்கு attention வேலை. **FlashAttention** அதே exact result-ஐ slow GPU memory-க்கு ரொம்ப குறைவான trips-ல கணக்கிடும், அதனால fast-ஆ இருக்கும், ஆனா comparisons எண்ணிக்கை அப்படியே தான் இருக்கும்.

### புது variations: ஒரு 2026 model card-ஐ படிக்கிறது

| Idea | அது என்ன மாத்துது | Config-ல எங்க தெரியும் |
| --- | --- | --- |
| Rotary positions | Position attention-க்குள்ளயே வரும்; contexts-ஐ stretch பண்ணலாம் | `rope_theta`, `rope_scaling` |
| Grouped-query attention | Query heads-ஓட groups ஒரு key-value head-ஐ share பண்ணும்: KV cache சின்னது, quality loss கொஞ்சம் தான் | `num_attention_heads`-ஐ விட குறைவான `num_key_value_heads` |
| Gated feed-forward | ரெண்டுக்கு பதிலா மூணு matrices | `intermediate_size`, `hidden_act` |
| Mixture of experts | நிறைய feed-forward "experts"; ஒரு router ஒவ்வொரு token-ஐயும் சில experts-க்கு மட்டும் அனுப்பும் | `num_local_experts`, `num_experts_per_tok` |
| Local attention | சில layers பக்கத்துல இருக்குற tokens-ஐ மட்டும் attend பண்ணும், நீளமான input cost-ஐ குறைக்கும் | sliding-window settings |

Mixture of experts ரெண்டு numbers-ஐ பிரிக்குது. **Total** parameters எல்லாமே memory-ல இருக்கணும்; **active** parameters ஒரு token-க்கான compute-ஐ முடிவு பண்ணும். Mixtral 8x7B-க்கு மொத்தம் 46.7 billion, ஒரு token-க்கு 12.9 billion use பண்ணும்; DeepSeek-V3-க்கு மொத்தம் 671 billion, active 37 billion. Hardware size பண்றதுக்கு முன்னாடி ரெண்டு numbers-ஐயும் படிங்க.

### Parameters எங்க இருக்கு

```python
def params(width, layers, vocab, ffn, heads, kv_heads, gated=True, tied=False):
    head = width // heads
    attn = 2 * width * width + 2 * width * kv_heads * head   # Q and output, then K and V
    ff = (3 if gated else 2) * width * ffn                     # gated layers use 3 matrices
    emb = vocab * width * (1 if tied else 2)                   # input table, output layer
    return layers * (attn + ff) + emb

# Llama 3 8B, from its published config
print(params(width=4096, layers=32, vocab=128_256, ffn=14_336, heads=32, kv_heads=8) / 1e9)
# about 8.03, matching the published 8B size
```

ஒவ்வொரு layer-ஓட weights-ல சுமார் அஞ்சுல நாலு பங்கு attention-ல இல்ல, feed-forward block-ல தான் இருக்கு. ஒரு number-க்கு 2 bytes-ல (16-bit), 8 billion parameters-க்கு எந்த KV cache-உம் இல்லாமலேயே சுமார் 16 GB GPU memory தேவை.

### Pre-training, adaptation

Models-ஐ பெரிய அளவு text-ல அடுத்த token-ஐ (decoders) அல்லது மறைச்ச tokens-ஐ (encoders) predict பண்ண pre-train பண்ணுவாங்க. Grammar, facts, reasoning patterns எல்லாமே prediction-க்கு உதவும், அதனால model அவற்றை கத்துக்கும். அப்புறம் chat models-ஐ instruction tuning, preference training வச்சு வடிவமைப்பாங்க. உங்க சொந்த tasks-க்கு fine-tune பண்ணலாம், அல்லது prompts, retrieval-ஓட model-ஐ அப்படியே use பண்ணலாம்.

Transformers ஜெயிச்சதுக்கு காரணம்: attention தூரத்துல இருக்குற tokens-ஐ நேரடியா இணைக்கும், எல்லா positions-உம் GPUs-ல parallel-ஆ train ஆகும்; அதனால ரொம்ப பெரிய models-க்கும் datasets-க்கும் scale பண்ண முடிஞ்சுது.

## ஒரு worked example

Chennai-ல ஒரு legal-tech startup-க்கு Indian court judgments மேல மூணு வேலைகள் இருக்கு.

**1. Area of law வாரியா classify பண்றது** (property, family, criminal, tax, labour). அவங்ககிட்ட 12,000 labelled judgment summaries இருக்கு. ஒரு சின்ன fine-tuned encoder தான் தெளிவான choice: cheap, fast, labels-ஐயும் use பண்ண முடியும். அவங்க test set-ல இது 91% accuracy, keyword counts-ல gradient-boosted model 82%-னு வச்சுக்கோங்க (விளக்கத்துக்கான numbers). இந்த gain context-ல இருந்து வருது: "the appellant's claim to ancestral property"-ங்குறது, "property"-ங்குற வார்த்தை இல்லாதப்போ கூட property law தான்.

முழு judgments அவங்களோட BERT-style encoder-ஓட 512-token limit-ஐ தாண்டி போகும். அந்த limit, அது train ஆன 512 learned position vectors-ல இருந்து வருது, attention cost-ல இருந்து இல்ல. அவங்களுக்கு ரெண்டு options இருக்கு:

- ஒவ்வொரு judgment-ஐயும் chunks-ஆ பிரிச்சு, ஒவ்வொண்ணையும் classify பண்ணி, votes-ஐ combine பண்றது.
- 8,192 tokens படிக்கக்கூடிய ModernBERT மாதிரி ஒரு long-context encoder-ஐ use பண்றது. முழு window, short inputs-ஐ விட slow-ஆ இருக்கும்னு அதோட model card warn பண்ணுது, அதனால speed-ஐயும் test பண்றாங்க.

**2. Semantic search.** ஒரு embedding model ஒவ்வொரு paragraph-ஐயும் ஒரு தடவை vector-ஆ மாத்தும்; queries vector search மூலமா match ஆகும்.

**3. Summaries.** Privacy-க்காக, ஒரு GPU-ல ஒரு 8B open model-ஐ self-host பண்ணலாமான்னு யோசிக்கிறாங்க. எதையும் வாங்குறதுக்கு முன்னாடி config-ல இருந்து size பண்றாங்க:

```python
def kv_cache_gb(tokens, layers=32, kv_heads=8, head_dim=128, bytes_per_number=2, users=1):
    per_token = 2 * layers * kv_heads * head_dim * bytes_per_number   # one key and one value
    return per_token * tokens * users / 1e9

print(kv_cache_gb(1))                     # 0.000131 GB, about 0.13 MB per token
print(kv_cache_gb(6_500, users=10))       # 8.5 GB for 10 judgments at once
print(kv_cache_gb(6_500, users=10, kv_heads=32))   # 34 GB without grouped-query attention
```

| Item | Memory |
| --- | --- |
| Weights, 2 bytes-ல 8 billion | சுமார் 16 GB |
| KV cache, 6,000 tokens-ஓட 10 judgments, summary-க்கு இன்னும் 500 | சுமார் 8.5 GB |
| Runtime overhead-க்கு முன்னாடி total | சுமார் 25 GB |

Runtime overhead சேர்த்தா, ஒரே நேரத்துல 10-க்கு ஒரு 24 GB GPU-ல headroom இல்ல; 40 அல்லது 48 GB GPU-ல இடம் இருக்கும், இல்லைன்னா ஒரே நேரத்துல 5 process பண்ணலாம். இது fit ஆகுறதுக்கு காரணமே grouped-query attention தான்: ஒவ்வொரு query head-க்கும் ஒரு key-value head இருந்தா cache நாலு மடங்கு பெருசா இருக்கும்.

## பொதுவா பண்ற தப்புகள்

- **எல்லா transformer-ஐயும் chatbot-ன்னு நினைக்கிறது.** Encoders, decoders, encoder-decoders வேற வேற வேலைக்கு பொருந்தும்; classification-ல ஒரு சின்ன encoder அடிக்கடி பெரிய chat model-ஐ ஜெயிக்கும்.
- **Weights-ஐ மட்டும் வச்சு hardware size பண்றது.** KV cache context length-ஓடயும் users-ஓடயும் வளரும்; நீளமான contexts-க்கும் நிறைய users-க்கும் weights-ஐ விட அதிக memory தேவைப்படலாம்.
- **Encoder-ஓட 512-token limit-ஐ attention cost-னு குழப்பிக்கிறது.** அது model train ஆன position table-ல இருந்து வருது.
- **Attention maps-ஐ explanations-ஆ படிக்கிறது.** ஒரு head-ல information எங்க flow ஆச்சுன்னு தான் attention weights காட்டும், model ஏன் அந்த முடிவு எடுத்துச்சுன்னு இல்ல.
- **தப்பான chat template அல்லது tokenizer-ஐ use பண்றது.** ஒரு template-ஓட fine-tune ஆன model இன்னொரு template-ல மோசமா behave பண்ணும்; document பண்ண அதே template-ஐ use பண்ணுங்க.
- **Mixture-of-experts model-ஓட total parameters-ஐ அதோட speed-ஆ சொல்றது.** Memory total parameters-ஐ follow பண்ணும்; ஒரு token-க்கான compute active parameters-ஐ follow பண்ணும்.
- **Tokenisation-ஐ மறந்துடுறது.** Hindi அல்லது Tamil text-க்கு English-ஐ விட பல மடங்கு tokens தேவைப்படலாம்; அது cost, speed, context-ல இருக்குற இடம் எல்லாத்தையும் மாத்தும்.

## Transformer internals தேவையில்லாத நேரங்கள்

- **API வழியா models-ஐ use பண்றது**: தினசரி வேலையில prompts, retrieval, evals தான் அதிகம் முக்கியம்.
- **Tabular prediction**, அங்க boosted trees பெரும்பாலும் சிறந்த tool.
- **சின்ன text tasks**, ஒரு keyword rule அல்லது சின்ன classifier-ஏ ஏற்கனவே நல்லா கையாளும்.

Models-ஐ தேர்ந்தெடுக்கும்போது, GPUs-ஐ size பண்ணும்போது, long-context behaviour-ஐ debug பண்ணும்போது, fine-tune பண்ணும்போது internals தெரிஞ்சிருந்தா பலன் தரும்.

## Demo-ல இருந்து production-க்கு

- **Hardware வாங்குறதுக்கு முன்னாடி memory-ஐ estimate பண்ணுங்க**: weights, அதோட உங்க நிஜ context length-லயும் users எண்ணிக்கையிலயும் KV cache.

- **Long-context accuracy-ஐ உங்க சொந்த documents-ல benchmark பண்ணுங்க**, விளம்பரப்படுத்துன window-ஐ மட்டும் நம்பாம.
- **Language வாரியா tokens-ஐ count பண்ணுங்க**, உங்க users எழுதுற languages-க்கு.
- **ஒவ்வொரு deployment-ஓடயும் model, version, config-ஐ record பண்ணுங்க**.
