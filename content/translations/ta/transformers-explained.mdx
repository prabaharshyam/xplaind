## இது என்ன

**Transformer**-னா 2017-ல அறிமுகமான ஒரு neural network architecture; **attention**-னு ஒரு mechanism-ஐ சுத்தி build ஆனது. இது ஒரு sequence-ஐ (வார்த்தைகள், image patches, audio frames) process பண்ணும்; எது முக்கியம்னு முடிவு பண்ண, ஒவ்வொரு position-உம் மத்த எல்லா positions-ஐயும் பார்க்கலாம்.

மூணு families இதை use பண்ணுது:

- **Decoder-only** models ஒரு நேரத்துல ஒரு token-ஆ text generate பண்ணும்: இன்னைக்கு இருக்குற chat, coding models.
- **Encoder-only** models text-ஐ படிச்சு representations உருவாக்கும்: search-க்கான நிறைய embedding models, classifiers. (சமீபத்திய சில embedding models decoder-only models-ல இருந்து மாத்தி அமைச்சது.)
- **Encoder-decoder** models ஒரு sequence-ஐ இன்னொண்ணா மாத்தும்: translation, summarisation.

Vision transformers images-ஐ patches-ஆ உடைச்சு, அவற்றை tokens மாதிரி நடத்தும்.

## இது எப்படி work ஆகுது

**Tokens, embeddings.** Text tokens-ஆ உடையுது; ஒவ்வொரு token-உம் ஒரு vector (embedding) ஆகுது. Order தெரியணும்னு positional information சேர்க்கப்படுது.

**Attention.** ஒவ்வொரு token-க்கும் model மூணு vectors கணக்கிடும்: query (நான் எதை தேடுறேன்?), key (என்கிட்ட என்ன இருக்கு?), value (நான் என்ன கடத்துறேன்?). Query-ஐ எல்லா keys-ஓடயும் compare பண்ணி attention weights எடுக்கும், அப்புறம் values-ஓட weighted mix-ஐ எடுக்கும். "The bank approved the loan because it trusted the applicant"-ல, attention "it" "the bank" மேல focus பண்ண உதவுது.

**Multi-head attention.** பல attention heads parallel-ஆ run ஆகும்; ஒவ்வொண்ணும் வேற வேற relationships-ஐ (grammar, references, topics) கத்துக்க சுதந்திரம் உண்டு.

**Layers.** ஒவ்வொரு transformer layer-லயும் attention, அதுக்கு அப்புறம் ஒரு சின்ன feed-forward network இருக்கும்; deep stacks-ஐ train பண்ண முடியுற மாதிரி shortcuts, normalisation இருக்கும். பெரிய models பல டஜன் layers அடுக்கி வச்சிருக்கும்.

**Generation.** Decoder-only model, சாத்தியமான ஒவ்வொரு அடுத்த token-க்கும் ஒரு probability-ஐ predict பண்ணி, ஒண்ணை எடுத்து (sampling), சேர்த்து, திரும்ப பண்ணும். Training-ல ஒவ்வொரு position-உம் எதிர்கால tokens-ஐ பார்க்காம இருக்க ஒரு mask தடுக்கும்.

**Cost.** Attention ஒவ்வொரு token-ஐயும் மத்த எல்லாத்தோடயும் compare பண்றதால, sequence நீளம் கூடுனா cost வேகமா கூடும். அதனாலதான் context windows-க்கு limits இருக்கு, நீளமான prompts slow-ஆவும் costly-ஆவும் இருக்கு. Engineering tricks (efficient attention kernels, keys, values-ஐ cache பண்றது) cost-ஐ குறைக்கும்.

**Pre-training, adaptation.** Models-ஐ பெரிய data-ல, விடுபட்ட அல்லது அடுத்த tokens-ஐ predict பண்ண pre-train பண்ணுவாங்க; அப்புறம் adapt பண்ணுவாங்க: chat models-க்கு instruction tuning, preference training; குறிப்பிட்ட tasks-க்கு fine-tuning; அல்லது prompts, retrieval-ஓட அப்படியே use பண்ணலாம்.

**ஏன் இது ஜெயிச்சுது.** Attention நீண்ட தூர relationships-ஐ நல்லா கையாளும், GPUs-ல parallel-ஆ திறமையா train ஆகும்; அதனால ரொம்ப பெரிய models-ஐயும் datasets-ஐயும் scale பண்ண முடிஞ்சுது.

**மூணு families பக்கத்துல பக்கத்துல:**

| Family | எப்படி படிக்கும் | என்ன உருவாக்கும் | வழக்கமான use |
| --- | --- | --- | --- |
| Encoder-only | முழு input-ஐயும் ஒரே நேரத்துல | ஒரு token-க்கு அல்லது ஒரு text-க்கு ஒரு vector | Classification, embeddings, search |
| Decoder-only | இடமிருந்து வலம், முன்னாடி எட்டிப் பார்க்காம | அடுத்த token, திரும்ப திரும்ப | Chat, coding, drafting, reasoning |
| Encoder-decoder | Input-ஐ முழுசா படிச்சு, அப்புறம் generate பண்ணும் | ஒரு புது sequence | Translation, summarisation |

**Attention-ஐ சாதாரண arithmetic-ல பார்க்கலாம்.** ஒரு token-க்கு, அதோட query-ஐ ஒவ்வொரு token-ஓட key-ஓடயும் dot product எடுங்க. பெரிய dot products-னா "relevant". Scores-ஐ vector size-ஓட square root-ஆல வகுத்து stable range-ல வச்சுக்கோங்க, அப்புறம் softmax மூலமா கூட்டுத்தொகை 1 வர்ற weights-ஆ மாத்துங்க. ஒவ்வொரு token-ஓட value-ஐயும் அதோட weight-ஆல பெருக்கி கூட்டுங்க. கிடைக்குறது அந்த token-க்கு ஒரு புது vector; அது எந்த tokens-ஐ கவனிச்சுதோ அவற்றோட information-ஐ கலந்து இருக்கும். ஒவ்வொரு head-உம் தனக்குனு கத்துக்கிட்ட queries, keys, values-ஓட இதை பண்ணும், results எல்லாம் சேர்க்கப்படும்.

**Pre-training என்ன கத்துக்கொடுக்கும்.** பெரிய அளவு text முழுக்க அடுத்த அல்லது விடுபட்ட token-ஐ predict பண்றதால, model grammar, facts, styles, reasoning patterns எல்லாத்தையும் கத்துக்கும்; ஏன்னா இவை எல்லாமே prediction-க்கு உதவும். அப்புறம் instruction tuning, preference training அந்த raw திறமையை, requests-ஐ follow பண்ற ஒரு helpful assistant-ஆ வடிவமைக்கும்.

**Attention-ஐ NumPy-ல சில வரியில.** ஒரு head, ஒரு causal mask, யார் யாரை attend பண்றாங்கன்னு பார்க்க weights print ஆகும்:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                       # how relevant each token is to each other
    if causal:
        scores = np.where(np.triu(np.ones_like(scores), k=1) == 1, -np.inf, scores)
    weights = softmax(scores)                           # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "she"]
x = rng.normal(size=(len(tokens), 16))                  # token embeddings plus position
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(np.round(w, 2))                                   # upper triangle is 0: no peeking ahead
```

Train ஆன model-ல, "she"-க்கான row "Priya" மேல அதிக weight போடும். இங்க weights random; ஆனா shapes-உம் mask-உம் நிஜ models ஒவ்வொரு layer-லயும் ஒவ்வொரு head-க்கும் கணக்கிடுறதே தான்.

**Multi-head shapes.** Model width 768, 12 heads-ன்னா, ஒவ்வொரு head-உம் 64 dimensions-ல வேலை செய்யும்; அவற்றோட outputs திரும்ப 768-ஆ சேர்த்து, இன்னொரு matrix-ஆல கலக்கப்படும். இதே idea PyTorch-ல:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                           # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                         # (2, 10, 768) and (2, 10, 10)
```

**Parameters எங்க இருக்கு.** ஒவ்வொரு layer-லயும் attention-ல width × width அளவுல நாலு matrices இருக்கும் (queries, keys, values, output); feed-forward block பொதுவா width-ஓட நாலு மடங்கு வரை விரிஞ்சு திரும்ப வரும், அது கிட்டத்தட்ட இன்னொரு ரெண்டு மடங்கு weights:

```python
def layer_params(width, ff_mult=4):
    attn = 4 * width * width
    ff = 2 * width * (ff_mult * width)
    return attn + ff

w, layers, vocab = 4096, 32, 128_000
total = layers * layer_params(w) + vocab * w
print(f"about {total / 1e9:.1f} billion parameters")    # about 7 billion: the 7B to 8B range
```

நிஜ models சில details-ல வேறுபடும் (grouped key-value heads, gated feed-forward layers), ஆனா இந்த estimate சரியான range-ல வந்து நிக்கும்.

**நீளமான inputs ஏன் அதிக cost.** Attention ஒவ்வொரு token-ஐயும் முன்னாடி இருக்குற எல்லாத்தோடயும் compare பண்றதால, வேலை நீளத்தோட square-ஆ கூடும்: 8,000 tokens-க்கு 1,000 tokens-ஐ விட கிட்டத்தட்ட 64 மடங்கு attention வேலை. Generation-லயும் முன்னாடி இருக்குற ஒவ்வொரு token-க்கும் keys, values-ஓட ஒரு cache வச்சிருக்கும்; அதனாலதான் நீளமான contexts-க்கு நிறைய GPU memory தேவை.

## ஒரு example

Chennai-ல ஒரு legal-tech startup, Indian court judgments-ஐ area of law வாரியா (property, family, criminal, tax, labour) classify பண்றாங்க, அதோட அவற்றுக்கு semantic search-உம் வேணும்.

- **Classification**: 12,000 labelled judgment summaries-ல ஒரு சின்ன encoder-only transformer-ஐ fine-tune பண்றாங்க. அது 91% accuracy எடுக்குது; keyword features-ல gradient-boosted model 82% தான். காரணம், "the appellant's claim to ancestral property" மாதிரி context-ஐ attention பிடிக்கும்.
- **Search**: paragraphs-ஐ embed பண்ண ஒரு embedding model (encoder) use பண்ணி, ஒத்த passages-ஐ retrieve பண்றாங்க.
- **Summaries**: ஒரு API வழியா decoder-only language model-ஐ, retrieve ஆன passages prompt-ல வச்சு use பண்றாங்க.

Judgments encoder-ஓட 512-token limit-ஐ தாண்டும்போது, முழு text-ஐ classify பண்ணாம, முதல் பகுதிகளையும் ரொம்ப relevant ஆன பகுதிகளையும் classify பண்றாங்க; இது நீளத்தோட attention cost கூடுறதோட நேரடி விளைவு.

| Task | Model type | Result |
| --- | --- | --- |
| Area-of-law classification | Fine-tuned சின்ன encoder | 91%, keyword features-க்கு 82% |
| ஒத்த passages-ஐ search பண்றது | Encoder embedding model | Judgments முழுக்க semantic matches |
| Summaries | API வழியா decoder-only model | Retrieve ஆன passages-ல இருந்து cited summaries |
| நீளமான judgments | 512-token limit இருக்குற encoder | ரொம்ப relevant ஆன பகுதிகளை classify பண்றது |

## பொதுவா பண்ற தப்புகள்

- **எல்லா transformers-ஐயும் chatbots-ன்னு நினைக்கிறது.** Encoders, decoders, encoder-decoders வேற வேற வேலைக்கு பொருந்தும்.
- **Sequence limits-ஐ கவனிக்காம விடுறது.** நீளமான inputs truncate ஆகும் அல்லது costly ஆகும்.
- **ஒரு சின்ன encoder போதும்ங்குற இடத்துல பெரிய model-ஐ fine-tune பண்றது.** Model size-ஐ task-க்கு ஏத்த மாதிரி வைங்க.
- **Attention weights-ஐ explanations-ன்னு நினைக்கிறது.** முடிவுகளுக்கு அவை நம்பகமான explanations இல்லை.
- **Tokenisation-ஐ மறந்துடுறது.** Indian languages-ல ஒரு வார்த்தைக்கு அடிக்கடி அதிக tokens ஆகும்; அது limits, cost-ஐ பாதிக்கும்.
- **Attention தானா "புரிஞ்சுக்குது"ன்னு நினைக்கிறது**: அது weighted averaging தான்; அர்த்தம் training-ல இருந்து வருது.
- **Prompts, context design பண்ணும்போது நீளமான inputs-ஓட quadratic cost-ஐ கவனிக்காம விடுறது.**

## Transformer internals தேவையில்லாத நேரங்கள்

- **API வழியா models-ஐ use பண்றது**: தினசரி வேலையில prompts, retrieval, evals தான் அதிகம் முக்கியம்.
- **Tabular prediction**, அங்க boosted trees பெரும்பாலும் சிறந்த tool.
- **சின்ன text tasks**, ஒரு keyword rule அல்லது சின்ன classifier-ஏ ஏற்கனவே நல்லா கையாளும்.

Models-ஐ தேர்ந்தெடுக்கும்போது, hardware size பண்ணும்போது, long-context behaviour-ஐ debug பண்ணும்போது, fine-tune பண்ணும்போது internals தெரிஞ்சிருந்தா பலன் தரும்.

## Demo-ல இருந்து production-க்கு

- **Hardware தேர்ந்தெடுக்குறதுக்கு முன்னாடி, architecture-ல இருந்து (layers, width, heads, context) memory-யையும் cost-ஐயும் estimate பண்ணுங்க.**
- **Quadratic attention cost இருக்குறதால, prompts, contexts-ஐ தேவையான அளவை விட நீளமா வைக்காதீங்க.**
- **Model-ஓட சொந்த tokenizer-ஐயும் chat template-ஐயும் documentation-ல சொன்ன மாதிரியே use பண்ணுங்க.**
- **விளம்பரப்படுத்துன window-ஐ மட்டும் இல்லாம, உங்க சொந்த documents-ல long-context accuracy-ஐ benchmark பண்ணுங்க.**
- **ஒவ்வொரு deployment-ஓடயும் model architecture, version-ஐ record பண்ணுங்க.**
