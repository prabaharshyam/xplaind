## இது என்ன

**Total cost of ownership (TCO)** என்பது ஒரு system ஒரு காலத்துல, பொதுவா ஒண்ணு முதல் மூணு வருஷத்துல, ஆக்குற எல்லா செலவும், model bill மட்டும் இல்ல. ஒரு AI system-க்கு:

- **Model costs**: API-ல tokens, அல்லது self-hosting-க்கு GPUs (வாங்கினது அல்லது வாடகைக்கு எடுத்தது).
- **Infrastructure**: app-க்கு compute, databases, vector stores, storage, networking, monitoring, gateways.
- **People**: கட்டுறது, நடத்துறது, on-call, evaluate பண்றது, upgrade பண்றது. பெரும்பாலும் மிகப் பெரிய item.
- **Data work**: connectors, pipelines, golden sets-ஐ label பண்றது, documents-ஐ சுத்தம் பண்றது.
- **Compliance, security**: audits, penetration tests, reviews.
- **Change**: model upgrades, re-embedding, providers models-ஐ deprecate பண்ணும்போது prompt-ஐ மறுபடி எழுதுறது.

நோக்கம் options-க்கு நடுவுல நியாயமான ஒப்பீடு, client-க்கு நேர்மையான budget.

| வருஷத்துக்கு total cost of ownership | இதுல என்ன இருக்கு |
|---|---|
| Model | API-ல tokens, அல்லது self-host பண்ணா மாசம் முழுக்க ஓடுற GPUs |
| Infrastructure | App compute, databases, vector store, monitoring |
| People | Build, operate, on-call, evals, upgrades: **பெரும்பாலும் மிகப் பெரியது** |
| Data | Connectors, pipelines, golden sets, clean-up |
| Compliance | Audits, pen tests, reviews |
| Change | Model upgrades, re-embedding, prompt rework |

```flow

Model + infra + people + data + compliance + change -> ஒரு claim-க்கு cost
ஒரு claim-க்கு cost -> ஒரு claim-ஓட value-ஓட ஒப்பிடு
```

## இது எப்படி work ஆகுது

**Usage-ல இருந்து ஆரம்பிங்க.** Users, ஒரு user-க்கு ஒரு நாளைக்கு requests, ஒரு request-க்கு input, output tokens (traces-ல இருந்து அளந்து, ஊகிக்காம), வருஷத்துல வளர்ச்சி, peak vs average.

**API option.** ஒரு request-க்கு cost = input tokens × input price + output tokens × output price, caching discounts, batch discounts, model tiering-க்கு ஏத்து adjust பண்ணி. அதை மாசாந்திர requests-ஆல பெருக்குங்க. இப்போதைய price lists, independent comparisons use பண்ணுங்க; prices அடிக்கடி மாறும், பொதுவா குறையும்.

**Self-hosted option.** Peak load-ஐ headroom-ஓட தாங்க தேவையான GPUs (load tests-ல இருந்து) × மணி நேர விலை அல்லது amortise பண்ணின purchase, busy-ஆ இருந்தாலும் இல்லன்னாலும் மாசம் முழுக்க ஓடும். அதோட operate, monitor, upgrade பண்ண engineering time, open model weak-ஆ இருந்தா quality gap-ஐயும் சேருங்க.

**Sensitivity.** Usage உங்க estimate-ல பாதியா அல்லது ரெண்டு மடங்கா இருந்தா, output நீளம் அதிகமானா, prices 30% குறைஞ்சா cost எப்படி நகருதுன்னு காட்டுங்க. ஒரே ஒரு exact usage level-ல மட்டும் அர்த்தமுள்ள முடிவுகள் நொறுங்கக்கூடியவை.

**Unit economics.** Client-க்கு முக்கியமான unit-க்கு result-ஐ சொல்லுங்க: தீர்த்த ticket-க்கு cost, process பண்ணின claim-க்கு, ஒரு employee-க்கு மாசத்துக்கு. அதை value-ஓட ஒப்பிடுங்க: சேமிச்ச மணி நேரம், வேகமான processing, குறைஞ்ச errors.

**ஒரே page-ல ஒப்பீடு (உதாரண figures):**

| மாசத்துக்கு item | Option A: அவங்க cloud வழியா API | Option B: self-hosted open model |
| --- | --- | --- |
| Model | caching, tiering-க்கு பிறகு கிட்டத்தட்ட ₹6.5 lakh | நாலு GPUs-க்கு கிட்டத்தட்ட ₹10 lakh |
| Infrastructure | கிட்டத்தட்ட ₹1.2 lakh | கிட்டத்தட்ட ₹1.5 lakh |
| People | ஒரு engineer-ல ஒரு சின்ன பகுதி | கிட்டத்தட்ட 1.5 engineers, கிட்டத்தட்ட ₹3 lakh |
| Evals-ல quality | Baseline | 2 points குறைவு |
| வருஷ மொத்தம் | கிட்டத்தட்ட ₹1 crore | கிட்டத்தட்ட ₹1.75 crore |

**நடைமுறையில் sensitivity.** ரெண்டு options-ஐயும், அளந்த usage-ல பாதி, ரெண்டு மடங்கு, outputs ரெண்டு மடங்கு நீளம், API prices 30% குறைவுன்னு மறுபடி கணக்கிடுங்க. Crossover point-ஐ எழுதிக்கோங்க: self-hosting மலிவாகுற usage. இங்க அது இப்போதைய volume-ஓட கிட்டத்தட்ட மூணு மடங்கு. அந்த ஒரு number ஒரு விவாதத்தை review trigger-ஆ மாத்தும்: "மாசாந்திர requests 3 million-ஐ தாண்டினா மறுபடி பாருங்க".

**Value பக்கம்.** Cost மட்டும் ஒரு system-ஐ நியாயப்படுத்த முடியாது. Pilot-ல இருந்து value-வை சேருங்க: ஒரு task-க்கு சேமிச்ச நிமிஷங்கள் × மாசத்துக்கு tasks, தவிர்த்த errors, customers-க்கு வேகமான turnaround. Cost, value-வை ஒரு unit-க்கு பக்கத்துல பக்கத்துல வைங்க, அப்பதான் leaders bill-ஐ மட்டும் இல்லாம margin-ஐயும் பார்ப்பாங்க.

**நீங்க மறுபடி ஓட்டக்கூடிய cost model.** Assumptions எல்லாத்தையும் ஒரே இடத்துல வைங்க, ஒவ்வொரு price check பண்ண தேதியோட:

```python
PRICES = {"checked": "2026-11-08", "usd_to_inr": 84,
          "in_per_m": 3.0, "out_per_m": 15.0, "cache_read_ratio": 0.1,      # USD per million tokens
          "gpu_hour_inr": 250, "engineer_month_inr": 250_000}

def api_month(requests, in_tok, out_tok, cached_share=0.5, small_share=0.0, small_ratio=0.25):
    p = PRICES
    per_req_usd = (in_tok * (1 - cached_share) * p["in_per_m"] + in_tok * cached_share * p["in_per_m"] * p["cache_read_ratio"]
                   + out_tok * p["out_per_m"]) / 1e6
    blended = per_req_usd * (1 - small_share + small_share * small_ratio)       # share sent to a cheaper model
    return requests * blended * p["usd_to_inr"]

def self_host_month(gpus, engineers=1.5, infra_inr=150_000):
    p = PRICES
    return gpus * p["gpu_hour_inr"] * 730 + engineers * p["engineer_month_inr"] + infra_inr

def table(base_requests, in_tok=3000, out_tok=400, gpus=4):
    print(f"prices checked {PRICES['checked']}")
    for label, mult in [("half usage", 0.5), ("measured", 1), ("double usage", 2)]:
        a = api_month(base_requests * mult, in_tok, out_tok, small_share=0.4) + 0.3 * PRICES["engineer_month_inr"]
        s = self_host_month(gpus if mult <= 1 else gpus * 2)
        print(f"{label:<13} API ₹{a/1e5:6.1f} lakh   self-hosted ₹{s/1e5:6.1f} lakh")

table(base_requests=600_000)
```

Traces-ல இருந்து client-ஓட நிஜ usage-ஐயும் இப்போதைய quotes-ஐயும் போடுங்க. Print ஆகுற தேதி, prices எப்போ உண்மையா இருந்ததுன்னு எல்லாரையும் நேர்மையா வச்சிருக்கும்.

**Crossover-ஐ கண்டுபிடிங்க.** Self-hosted line API line-க்கு கீழ போற வரை usage-ஐ படிப்படியா ஏத்துங்க:

```python
def crossover(in_tok=3000, out_tok=400, gpus_per_million=2):
    for r in range(100_000, 20_000_001, 100_000):
        gpus = max(1, round(r / 1e6 * gpus_per_million))
        if self_host_month(gpus) < api_month(r, in_tok, out_tok, small_share=0.4):
            return r
    return None
```

`gpus_per_million` ஒரு load test-ல இருந்து வரணும், ஊகத்துல இல்ல. Crossover எதிர்பார்க்குற usage-ஐ விட ரொம்ப மேல இருந்தா முடிவு ஈசி; பக்கத்துல இருந்தா usage வளர வளர மறுபடி பார்க்க plan பண்ணுங்க.

**ஒவ்வொரு line-ஐயும் எண்ணுங்க.** Tokens, GPUs தாண்டி: embeddings, re-embedding, vector database, tracing, log storage, evaluation runs (judge calls சேர்ந்து போகும்), staging environments, security reviews, system-ஐ நடத்தி, monitor பண்ணி, மேம்படுத்துற ஆட்கள். People-ஐ விட்டுடுறது இந்த ஒப்பீடுகள்ல மிகப் பொதுவான தப்பு.

**Cost-ஓட value-வை சேருங்க.** ஒவ்வொரு வேலை unit-க்கும், அளந்த value-வை cost-க்கு பக்கத்துல வைங்க: சேமிச்ச நிமிஷங்கள் × ஒரு நிமிஷத்துக்கான loaded staff cost, தவிர்த்த errors, வேகமான turnaround. ஒரு வரி ratio ("ஒரு ticket-க்கு AI cost ₹4, சேமிச்ச staff time ₹60") தான் முடிவெடுக்கறவங்களுக்கு ஞாபகம் இருக்கும்.

## ஒரு worked example

ஒரு Kolkata insurance company, 2,000 staff-க்கு claims-document assistant-ஐ rollout பண்ண திட்டமிடுது. Pilot-ல அளந்தது: ஒரு user-க்கு ஒரு வேலை நாளுக்கு 25 requests, ஒரு request-க்கு 3,000 input tokens (பெரும்பாலும் retrieve ஆன passages), 300 output tokens. அது மாசத்துக்கு கிட்டத்தட்ட 1.1 million requests.

**Option A, அவங்க cloud வழியா API.** உதாரணமா 1,000 input tokens-க்கு ₹0.25, 1,000 output tokens-க்கு ₹1.00 வச்சா: (3 × 0.25) + (0.3 × 1.00) = ஒரு request-க்கு ₹1.05, மாசத்துக்கு கிட்டத்தட்ட ₹11.5 lakh. மாறாத system prompt-ல prompt caching, எளிமையான lookups-ஐ சின்ன model-க்கு tiering பண்ணா அது கிட்டத்தட்ட ₹6.5 lakh ஆகுது. Infrastructure ₹1.2 lakh. Operations-க்கு ஒரு engineer-ஓட நேரத்துல ஒரு சின்ன பகுதி.

**Option B, self-hosted open model.** Load tests peak load-க்கு மூணு GPUs, கூடவே ஒரு spare-ன்னு காட்டுது, ஒரு GPU-க்கு மாசத்துக்கு உதாரணமா ₹2.5 lakh: ₹10 lakh. Infrastructure ₹1.5 lakh. கூடவே serving stack-ஐ நடத்த கிட்டத்தட்ட ஒன்றரை engineers, மாசத்துக்கு கிட்டத்தட்ட ₹3 lakh. Evals accuracy 2 points குறைவுன்னு காட்டுது.

ஒரு வருஷத்துல, A-க்கு கிட்டத்தட்ட ₹1 crore, B-க்கு கிட்டத்தட்ட ₹1.75 crore ஆகுது. Usage மூணு மடங்கானா அல்லது data rules கேட்டா மட்டும்தான் B ஜெயிக்கும். Client A-ஐ தேர்ந்தெடுக்குறாங்க, மாசத்துக்கு volume 3 million requests-ஐ தாண்டினா review பண்றதுன்னு. Value பக்கம்: pilot மாசத்துக்கு 40,000 claims-ல ஒரு claim-க்கு 9 நிமிஷம் சேமிச்சுதுன்னு காட்டுச்சு, கிட்டத்தட்ட 6,000 staff hours, cost-ஐ விட நல்லாவே அதிகம்.

(இங்க prices உதாரணத்துக்கு மட்டும். Model-ஐ கட்டுற நாள்ல providers, comparisons-ல இருந்து இப்போதைய prices-ஐ use பண்ணுங்க.)

| Pilot-ல அளந்தது | Value |
| --- | --- |
| ஒரு claim-க்கு சேமிச்ச நேரம் | 9 நிமிஷம் |
| மாசத்துக்கு claims | 40,000 |
| மாசத்துக்கு சேமிச்ச staff hours | கிட்டத்தட்ட 6,000 |
| முடிவு | Option A, volume மாசத்துக்கு 3 million requests-ஐ தாண்டினா review |

## பொதுவா பண்ற தப்புகள்

- **Tokens மட்டும் அல்லது GPUs மட்டும் எண்ணுறது.** People, change costs பெரும்பாலும் ஆதிக்கம் செலுத்தும்.
- **Token counts-ஐ ஊகிக்கிறது.** நிஜ traces-ல இருந்து அளங்க; retrieve ஆன context input tokens-ஐ ஊதிப் பெருக்கும்.
- **Average-க்கு size பண்றது.** Self-hosted capacity peaks-ஐ தாங்கணும்; APIs அவற்றை தாங்கிக்கும்.
- **Price trends-ஐ புறக்கணிக்கிறது.** API prices தொடர்ந்து குறைஞ்சிருக்கு; மூணு வருஷ GPU commitments நல்லா வயசாகாம போகலாம்.
- **Value பக்கம் இல்லாம இருக்கிறது.** சேமிச்ச மணி நேரம் அல்லது errors இல்லாத cost model எதையும் நியாயப்படுத்தாது.
- **Self-hosted (மற்றும் API) cost-ல people-ஐ விட்டுடுறது.**
- **தேதி இல்லாத prices**, சில மாசம் கழிச்சு அமைதியா பழசாகிடும்.
- **GPU counts-ஐ ஊகிக்கிறது**, load test-ல capacity-ஐ அளக்காம.

## எப்போ விரிவான cost model தேவையில்ல

- **சின்ன, fixed budget-ல ஒரு pilot**: spend cap-உம், வாராவாரம் bill-ஐ ஒரு பார்வையும் போதும்.
- **நிஜமான மாற்று இல்ல**, உதாரணத்துக்கு data rules on-premises hosting-ஐ கட்டாயப்படுத்துறது: தேர்ந்தெடுக்க இல்ல, budgeting-க்கு cost-ஐ model பண்ணுங்க.
- **ரொம்ப சின்ன usage**, value-வுக்கு பக்கத்துல cost ஒரு rounding error.

## Demo-ல இருந்து production-க்கு

- **Cost model-ஐ repository-ல வைங்க**, தேதியிட்ட prices, அளந்த usage-ஓட.
- **மாசாமாசம் update பண்ணுங்க**, traces, நிஜ bill-ல இருந்து, வித்தியாசங்களை விளக்கி.
- **ஒரு வேலை unit-க்கு cost-ஐ track பண்ணுங்க**, ஒரு unit-க்கு value பக்கத்துல.
- **Usage, prices அல்லது models மாறும்போது crossover-ஐ மறுபடி கணக்கிடுங்க.**
- **ஒவ்வொரு line-ஐயும் சேருங்க**: evals, tracing, storage, staging, people.
