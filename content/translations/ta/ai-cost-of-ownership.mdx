## இது என்ன

**Total cost of ownership (TCO)**-னா ஒரு system-க்கு ஒரு காலத்துல, பொதுவா ஒண்ணுல இருந்து மூணு வருஷத்துல, ஆகுற எல்லா செலவும், model bill மட்டும் இல்ல. இதோட வேலை options-ஐ நியாயமா compare பண்ண உதவுறதும், client-க்கு ஒரு நேர்மையான budget குடுக்குறதும் தான்.

| Cost line | அதுல என்ன வரும் | மக்கள் என்ன மறந்துடுறாங்க |
|---|---|---|
| Model | API மூலமா tokens, அல்லது self-host பண்ணா GPUs (வாடகைக்கு அல்லது வாங்கினது) | மறைஞ்சிருக்குற reasoning tokens; idle-ஆ இருக்கும்போதும் bill ஆகுற GPUs |
| Infrastructure | App compute, databases, vector store, storage, gateways, monitoring | Log, trace storage, staging environments |
| People | Build, operate, on-call, evaluations, upgrades | On-call cover-க்கு தேவைப்படுற ரெண்டாவது engineer |
| Data | Connectors, pipelines, golden sets, documents-ஐ clean-up பண்றது | Embedding model மாறும்போது re-embedding |
| Compliance | Audits, penetration tests, security, legal reviews | ஒவ்வொரு பெரிய மாற்றத்துக்கு அப்புறமும் மறுபடி reviews |
| Change | Model upgrades, ஒரு provider model-ஐ retire பண்ணும்போது prompt-ஐ மறுபடி வேலை பார்க்குறது | ஒவ்வொரு புது model-லயும் evals-ஐ மறுபடி run பண்றது |
| India-specific | Cloud, API bills மேல GST, dollar prices மேல exchange rate | GST ஒரு நிஜ cost-ஆ, இல்ல திரும்ப claim பண்ண முடியுமா |

## இது எப்படி வேலை செய்யுது

### அளந்த usage-ல இருந்து ஆரம்பிங்க

Users, ஒரு user-க்கு ஒரு நாளைக்கு requests, peak vs average, வருஷத்துல growth இதையெல்லாம் collect பண்ணுங்க. அப்புறம் மக்கள் பொதுவா ஊகிக்குற மூணு விஷயங்களை traces-ல இருந்து அளங்க:

- **ஒரு user action-க்கு calls.** ஒரு agent அல்லது ஒரு retrieval pipeline ஒரு கேள்விக்கு மூணுல இருந்து ஆறு model calls பண்ணலாம்: query-ஐ rewrite பண்றது, retrieve பண்றது, answer பண்றது, check பண்றது. Cost ஒரு call-க்கு தான், ஒரு கேள்விக்கு இல்ல.
- **ஒரு call-க்கு input tokens.** Retrieve ஆன passages பெரும்பாலும் input-ஐ user-ஓட கேள்வியை விட பல மடங்கு பெரிசாக்கிடும்.
- **Reasoning உட்பட, ஒரு call-க்கு output tokens.** Reasoning models answer பண்றதுக்கு முன்னாடி யோசிக்கும். அந்த thinking மறைஞ்சிருக்கும், ஆனா output tokens-ஆ bill ஆகும் (OpenAI-ஓட documentation இதை வெளிப்படையா சொல்லுது). ஒரு சின்ன visible answer-க்கு பின்னாடி ஒரு நீளமான invisible bill இருக்கலாம்.

### API option

ஒரு call-க்கு cost = input tokens × input price + output tokens × output price. அப்புறம் மூணு adjustments பண்ணுங்க:

- **Prompt caching.** ஒவ்வொரு call-லயும் மறுபடி படிக்கப்படுற ஒரு fixed system prompt அல்லது shared document prefix, caching குடுக்குற providers-கிட்ட சாதாரண input price-ஓட ஒரு சின்ன பங்குக்கு bill ஆகும்.
- **Batch discounts**: overnight summaries மாதிரி, மணிக்கணக்கா காத்திருக்கக்கூடிய வேலைக்கு.
- **Tiering.** Simple requests-ஐ (lookups, classification) ஒரு மலிவான, சின்ன model-க்கு அனுப்புங்க, கஷ்டமானதுக்கு பெரிய model-ஐ வச்சுக்கோங்க.

பெரும்பாலான API prices US dollars-ல இருக்கு, அதனால rupee rate-உம் ஒரு input தான். Prices-ஐ provider-ஓட page-லயும் Artificial Analysis மாதிரி ஒரு independent comparison-லயும் படிங்க, ஒவ்வொண்ணு பக்கத்துலயும் check பண்ண date-ஐ எழுதுங்க.

### Self-hosted option

GPUs-ஐ ஒரு spare-ஓட **peak**-க்கு size பண்ணணும், உங்க latency target-ல உங்க சொந்த prompts-ஐ வச்சு பண்ண ஒரு load test-ல இருந்து. அப்புறம் busy-ஆ இருந்தாலும் இல்லன்னாலும் மாசத்தோட ஒவ்வொரு மணி நேரத்துக்கும் காசு குடுக்குறீங்க. Case-ஐ decide பண்ற number **utilisation**:

utilisation = serve பண்ண requests ÷ மாசத்துல fleet serve பண்ணியிருக்கக்கூடிய requests

Working days-ல ஒரு நாளைக்கு ஒன்பது மணி நேரம் use ஆகுற, month-end peak-க்கு size பண்ண ஒரு office tool பெரும்பாலும் 10% அல்லது அதுக்கும் குறைவான utilisation-ல தான் ஓடும். 10% utilisation-ல ஒவ்வொரு request-உம் full use-ல ஆகுறதை விட பத்து மடங்கு GPU cost-ஐ சுமக்கும்.

ரெண்டு pricing choices முக்கியம்:

- **On-demand** GPUs-க்கு ஒரு மணி நேரத்துக்கு ஆகுற cost தான் மிக அதிகம், ஆனா அவற்றை release பண்ணிடலாம்.
- **Reserved** GPUs (ஒரு வருஷம் அல்லது மூணு வருஷ commitment) ஒரு மணி நேரத்துக்கு குறைவான cost, ஆனா usage குறைஞ்சாலும் API prices இறங்கினாலும் நீங்க காசு குடுத்தே ஆகணும்.

Serving stack-ஐ run பண்ண, patch பண்ண, models-ஐ upgrade பண்ண, pager-ஐ சுமக்க தேவையான ஆளுங்களையும், உங்க evals-ல open model குறைவா score பண்ணா அந்த quality gap-ஐயும் சேருங்க.

### India-specific lines

- **GST.** Cloud, API services-க்கு பொதுவா 18% GST வரும் (November 2026 நிலவரப்படி IT, cloud services-க்கான வழக்கமான rate). ஒரு foreign provider-கிட்ட வாங்குற ஒரு GST-registered business பொதுவா அதை reverse charge-ல கட்டும், அதை input tax credit-ஆ திரும்ப claim பண்ணலாம். Credit claim பண்ண முடியாத ஒரு organisation-க்கு அது நிஜ cost. எந்த case பொருந்தும்னு client-ஓட finance team-கிட்ட கேளுங்க; இந்த lesson-ல இருக்குற figures எல்லாம் GST-க்கு முன்னாடி.
- **Exchange rate.** Rupee இறங்கும்போது dollar-ல price ஆன ஒரு API bill ஏறும். November 2026 நடுவுல rupee ஒரு வாரத்துக்குள்ள ஒரு dollar-க்கு சுமார் ₹94.2-ல இருந்து சுமார் ₹93.5-க்கு நகர்ந்துச்சு; ₹100-க்கு போனா model line-ல சுமார் 7% கூடும். Rate-ஐ sensitivity table-ல போடுங்க.
- **Region.** Data rules ஒரு Indian cloud region-ஐ கட்டாயமாக்கலாம். நீங்க price பண்ண model அல்லது GPU type அங்க கிடைக்குதா, அந்த region-ஓட price-ல, check பண்ணுங்க.

### Sensitivity-உம் crossover-உம்

ஒரு நேரத்துல ஒரு assumption-ஐ மட்டும் மாத்தி ரெண்டு options-ஐயும் மறுபடி கணக்கு போடுங்க: usage பாதியா, ரெண்டு மடங்கா; outputs ரெண்டு மடங்கு நீளமா; API prices 30% குறைவா; weak-ஆன rupee; load test-ல இருந்து குறைவான GPU throughput. ஒரே ஒரு exact number-ல மட்டும் நிக்குற முடிவு fragile.

**Crossover**-னா எந்த usage-க்கு மேல இன்னொரு option தொடர்ந்து மலிவா இருக்குமோ அந்த usage. ரெண்டு traps:

- **Steps.** GPUs முழு units-ஆ தான் வரும், அதனால ஒவ்வொரு தடவை ஒண்ணு சேர்க்கும்போதும் self-hosted line jump ஆகும். ஒரு spreadsheet ஒரு volume-ல self-hosting ஜெயிக்குற மாதிரியும் அதுக்கு கொஞ்சம் மேல தோக்குற மாதிரியும் காட்டலாம். எந்த volume-க்கு மேல அது தொடர்ந்து ஜெயிக்குதோ அதை report பண்ணுங்க.
- **Thin margins.** ஒரு extra request-க்கு API-க்கும் GPU-க்கும் கிட்டத்தட்ட ஒரே cost-னா, சின்ன மாற்றங்களுக்கே crossover பயங்கரமா ஆடும். அதை வெளிப்படையா சொல்லுங்க.

### Price trends

ஒரு குறிப்பிட்ட quality level-க்கான API prices வேகமா குறைஞ்சிருக்கு. ஒரு fixed benchmark score-ஐ எட்டுற models-ஓட per-token price வருஷத்துக்கு 9-ல இருந்து 900 மடங்கு வரை குறைஞ்சதுன்னு Epoch AI March 2025-ல estimate பண்ணுச்சு; எந்த performance level அளக்கப்பட்டுச்சுங்கறதை பொறுத்து அது மாறும். அவை ஒரு token-க்கான prices, reasoning models ஒரு task-க்கு இன்னும் நிறைய tokens use பண்ணலாம். மூணு வருஷ GPU commitment இந்த trend-க்கு எதிரா பந்தயம் கட்டுது, அதனால அதை ஒரு "prices 30% குறைவு" row-ஓட test பண்ணுங்க.

### மறுபடி run பண்ணக்கூடிய ஒரு cost model

எல்லா assumptions-ஐயும் ஒரே இடத்துல, check பண்ண date-ஓட வச்சுக்கோங்க. கீழ இருக்குற ஒவ்வொரு number-உம் illustrative, worked example-க்கு match ஆகுற மாதிரி தேர்ந்தெடுத்தது:

```python
import math

# Every number is illustrative. Replace each with your own dated quote or measurement.
P = {"rate_date": "2026-11-19", "usd_to_inr": 93.5,        # rupees per US dollar, about mid-November 2026
     "in_per_m": 3.0, "out_per_m": 15.0,                    # USD per million tokens, a mid-tier API model
     "cache_ratio": 0.1,                                    # cached input billed at 10% of the input price
     "gpu_month": 250_000,                                  # one rented GPU, on demand, all 730 hours
     "gpu_rps": 1.2,                                        # requests per second per GPU, from YOUR load test
     "engineer_month": 200_000,                             # loaded monthly cost of one engineer
     "busy_seconds": 22 * 9 * 3600,                         # 22 working days of 9 busy hours
     "peak_factor": 2.0}                                    # month-end peak against the busy-hour average

def api_month(req, p=P, in_tok=3000, out_tok=300, cached=0.4, small_share=0.4, small_ratio=0.25):
    in_usd = in_tok * (1 - cached + cached * p["cache_ratio"]) * p["in_per_m"] / 1e6
    per_req = (in_usd + out_tok * p["out_per_m"] / 1e6) * (1 - small_share + small_share * small_ratio)
    return req * per_req * p["usd_to_inr"] + 120_000 + 0.3 * p["engineer_month"]   # + infra + 0.3 engineer

def gpus(req, p=P):
    peak_rps = req / p["busy_seconds"] * p["peak_factor"]
    return math.ceil(peak_rps / p["gpu_rps"]) + 1                                   # + one spare

def self_month(req, p=P):
    return gpus(req, p) * p["gpu_month"] + 150_000 + 1.5 * p["engineer_month"]       # + infra + 1.5 engineers

def utilisation(req, p=P):
    return req / (gpus(req, p) * p["gpu_rps"] * 730 * 3600)

def crossover(p=P, limit=30_000_000, step=100_000):
    """Volume above which self-hosting stays cheaper, or None if it never does up to the limit."""
    last_api_win = 0
    for r in range(step, limit + 1, step):
        if self_month(r, p) >= api_month(r, p):
            last_api_win = r
    return None if last_api_win == limit else last_api_win + step

base = 1_100_000
print(f"Illustrative prices, rupee rate of {P['rate_date']}")
print(f"measured: API ₹{api_month(base)/1e5:.1f} lakh, self-hosted ₹{self_month(base)/1e5:.1f} lakh, "
      f"{gpus(base)} GPUs at {utilisation(base):.0%} utilisation")
scenarios = {"as measured": {}, "reserved GPUs at ₹1.6 lakh": {"gpu_month": 160_000},
             "load test gives 1.0 req/s": {"gpu_rps": 1.0}, "API prices 30% lower": {"in_per_m": 2.1, "out_per_m": 10.5},
             "rupee at ₹100": {"usd_to_inr": 100},
             "reserved, API 30% lower": {"gpu_month": 160_000, "in_per_m": 2.1, "out_per_m": 10.5}}
for name, change in scenarios.items():
    p = {**P, **change}
    c = crossover(p)
    print(f"{name:<27} API ₹{api_month(base, p)/1e5:4.1f} lakh  self ₹{self_month(base, p)/1e5:4.1f} lakh  "
          f"crossover {'none below 30M' if c is None else f'{c/1e6:.1f}M'}")
```

இந்த model volume கூடும்போதும் people, infrastructure-ஐ fixed-ஆ வச்சிருக்கு, அதனால அதிக volume-ல self-hosting நிஜத்தை விட நல்லா தெரியும்: பதினைஞ்சு GPUs இருக்குற ஒரு fleet-க்கு ஒன்றரை engineers-ஐ விட அதிகம் வேணும். யாருக்காவது ஒரு number-ஐ காட்டுறதுக்கு முன்னாடி client-ஓட traces, load test, quotes-ஐ போட்டு மாத்துங்க.

## ஒரு worked example

ஒரு Kolkata insurance company 2,000 staff-க்கு ஒரு claims-document assistant-ஐ roll out பண்ண plan பண்ணுது. Pilot-ல அளந்தது: 22 working days-ல ஒரு user-க்கு ஒரு working day-க்கு 25 requests, ஒரு request-க்கு 3,000 input tokens (பெரும்பாலும் retrieve ஆன passages), 300 output tokens, ஒரு request-க்கு ஒரு model call. அது 2,000 × 25 × 22 = மாசத்துக்கு 1.1 million requests. Month-end traffic சாதாரண busy-hour rate-ஐ விட ரெண்டு மடங்கு. எல்லா prices-உம் code-ல இருக்குற illustrative prices தான்.

**Option A, அவங்க cloud மூலமா API.** ஒரு request-க்கு: 3,000 × $3 ÷ 1,000,000 + 300 × $15 ÷ 1,000,000 = $0.0135, ₹93.5-ல சுமார் ₹1.26. 1.1 million requests-க்கு அது மாசத்துக்கு சுமார் ₹13.9 lakh. Fixed system prompt-ஐயும் instructions-ஐயும் (input tokens-ல 40%) cache பண்ணா அது சுமார் ₹10.6 lakh-க்கு வரும். 40% requests-ஐ, அதாவது simple lookups-ஐ, கால்வாசி price-ல இருக்குற ஒரு model-க்கு அனுப்புனா அது சுமார் ₹7.4 lakh-க்கு, அதாவது ஒரு request-க்கு ₹0.67-க்கு வரும். ₹1.2 lakh infrastructure-உம் ஒரு engineer-ஓட 30%-உம் சேர்த்தா: சுமார் **மாசத்துக்கு ₹9.2 lakh**.

**Option B, self-hosted open model.** ஒரு GPU latency target-ல ஒரு second-க்கு 1.2 requests serve பண்ணுதுன்னு load test காட்டுது. Month-end peak ஒரு second-க்கு சுமார் 3.1 requests, அதனால மூணு GPUs கூட ஒரு spare: நாலு GPUs, ஒவ்வொண்ணும் ₹2.5 lakh, மொத்தம் ₹10 lakh. ₹1.5 lakh infrastructure-உம், serving, upgrades, on-call-க்கு ஒன்றரை engineers-உம் (₹3 lakh) சேர்த்தா: சுமார் **மாசத்துக்கு ₹14.5 lakh**. Evals-ல accuracy 2 points குறைவு. Fleet 9% utilisation-ல ஓடுது, ஏன்னா அது month-end-க்கு size பண்ணப்பட்டு, ஒவ்வொரு ராத்திரிக்கும் weekend-க்கும் காசு குடுக்கப்படுது.

| --- | --- | --- |
| Model | Caching, tiering-க்கு அப்புறம் சுமார் ₹7.4 lakh | 9% utilisation-ல நாலு GPUs-க்கு ₹10 lakh |

**Crossover எங்க?** API-ல ஒவ்வொரு extra request-க்கும் சுமார் ₹0.67 ஆகும். Average-ஐ விட ரெண்டு மடங்குக்கு size பண்ண ஒரு GPU-ல அது சுமார் ₹0.58. வித்தியாசம் வெறும் ஒன்பது paise தான், அதனால spare GPU-வையும் extra engineers-ஐயும் ஈடு கட்ட self-hosting-க்கு ரொம்ப பெரிய volume வேணும். On demand-ல, மாசத்துக்கு சுமார் 8.3 million requests-க்கு மேல தான் அது தொடர்ந்து ஜெயிக்கும், அதாவது இன்னைக்கு volume-ஐ விட ஏழுல இருந்து எட்டு மடங்கு. ₹1.6 lakh-ல reserved GPUs-னா, அது சுமார் 1.9 million-க்கு இறங்குது: நெருக்கமா இருக்கு. ஆனா load test 1.2-க்கு பதிலா ஒரு second-க்கு 1.0 request-னு காட்டியிருந்தாலோ, API prices 30% குறைஞ்சிருந்தாலோ, on-demand crossover-ஏ இருந்திருக்காது. அந்த fragility தான் finding.

**Decision.** A-வை தேர்ந்தெடுங்க. Plan-ல ரெண்டு review triggers எழுதுங்க: monthly volume 1.5 million-ஐ தாண்டும்போது, ஒரு reserved GPU quote வாங்கி load test-ஐ மறுபடி run பண்ணுங்க; API price, rupee rate அல்லது ஒரு data rule எப்போ மாறினாலும், model-ஐ மறுபடி run பண்ணுங்க. API prices பொதுவா குறையுற போக்குல இருக்கும்போது ஒரு வருஷ reservation cost-ஐ lock பண்ணிடும்னு recommendation-ல note பண்ணுங்க; API prices 30% குறைஞ்சா, reserved crossover சுமார் 6.1 million வரை தள்ளிப் போகும்.

**Value side.** மாசத்துக்கு 40,000 claims-ல ஒரு claim-க்கு 9 நிமிஷம் மிச்சம்னு pilot காட்டுச்சு, அதாவது சுமார் 6,000 staff hours. ஒரு மணி நேரத்துக்கு ₹400 illustrative loaded staff cost-ல, அது ஒரு claim-க்கு ₹60 மதிப்புள்ள நேரம், ஒரு claim-க்கு சுமார் ₹23 AI cost-க்கு எதிரா (₹9.2 lakh ÷ 40,000). Leadership team ஞாபகம் வச்சுக்கப்போறது அந்த ratio தான், token bill இல்ல.

## பொதுவான தப்புகள்

- **Token price-ஐ GPU rent கூட compare பண்றது.** ரெண்டு பக்கத்துலயும் எல்லா lines-ஐயும் எண்ணுங்க: people, infrastructure, evals, change. ரெண்டு options-லயும் ரொம்ப அடிக்கடி விடுபடுற line people தான்.
- **Usage-ஐ ஊகிக்குறது.** Retrieve ஆன context-உம் மறைஞ்சிருக்குற reasoning tokens-உம் சேர்த்து, ஒரு user action-க்கு calls, ஒரு call-க்கு tokens-ஐ traces-ல இருந்து அளங்க.
- **Average-க்கு size பண்றது, அல்லது full utilisation-னு நினைக்குறது.** GPUs peak-ஐ cover பண்ணணும், மாசம் முழுக்க bill ஆகும். Utilisation-ஐ model-ல போடுங்க.
- **முதல் crossover-ஐ நம்புறது.** முழு-GPU steps lines-ஐ cross பண்ணவும் uncross பண்ணவும் வைக்கும். Stable point-ஐயும் அது எவ்வளவு நகருதுன்னும் report பண்ணுங்க.
- **Price-fall row இல்லாம GPUs-ஐ reserve பண்றது.** API prices இறங்கும்போது ஒரு நீண்ட commitment பழசாகி நஷ்டம் தரலாம்.
- **Rupee-யையும் GST-யையும் கண்டுக்காம விடுறது.** ஒரு dollar bill exchange rate கூட நகரும், திரும்ப claim பண்ண முடியலைன்னா GST நிஜ cost.
- **Date இல்லாத prices.** சில மாசங்களுக்குள்ள அவை சத்தமில்லாம தப்பாகிடும்.
- **Value side இல்லாதது.** மிச்சமான hours அல்லது errors இல்லாத ஒரு cost model எதையும் justify பண்ண முடியாது.

## ஒரு detailed cost model எப்போ தேவையில்ல

- **ஒரு சின்ன, fixed budget-க்குள்ள இருக்குற pilot**: ஒரு spend cap-உம் வாரத்துக்கு ஒரு தடவை bill-ஐ பார்க்குறதும் போதும்.
- **நிஜமான alternative இல்லாதப்போ**, உதாரணமா data rules on-premises hosting-ஐ கட்டாயமாக்கும்போது: cost-ஐ budgeting-க்காக model பண்ணுங்க, choose பண்றதுக்காக இல்ல.
- **ரொம்ப சின்ன usage**, value பக்கத்துல cost ஒரு rounding error மாதிரி இருக்கும்போது.

## Demo-ல இருந்து production வரை

- **Cost model-ஐ repository-ல வச்சுக்கோங்க**, date போட்ட prices, rupee rate, அளந்த usage-ஓட.
- **மாசா மாசம் அதை reconcile பண்ணுங்க**, traces, நிஜ bill கூட; ஒவ்வொரு வித்தியாசத்தையும் explain பண்ணுங்க.
- **ஒரு unit வேலைக்கு cost-ஐ track பண்ணுங்க**, ஒரு unit-க்கு value பக்கத்துல, அதே dashboard-ல.
- **Crossover-ஐ மறுபடி run பண்ணுங்க**, usage, prices, rupee, models அல்லது load-test results மாறும்போது.
- **API account-ல budget alerts set பண்ணுங்க**, அப்போ கட்டுப்பாடு இல்லாம ஓடுற ஒரு agent loop month end-ல இல்லாம சில மணி நேரத்துலயே தெரிஞ்சிடும்.

## Practice

மூணு models-க்கு இப்போதைய prices-ஐ collect பண்ண Artificial Analysis-ஐ use பண்ணுங்க, ஒவ்வொண்ணு பக்கத்துலயும் check பண்ண date-ஐ எழுதுங்க, tiering எப்படி cost-ஐ குறைக்குதுன்னு பார்க்க routing பத்தின RouteLLM post-ஐ மறுபடி படிங்க.

1. உங்க சொந்த app-ஓட traces-ல இருந்து, ஒரு user action-க்கு calls-ஐயும், ஒரு call-க்கு average input, output, reasoning tokens-ஐயும் அளங்க.
2. 100, 1,000, 10,000 daily users-க்கு cost model-ஐ adapt பண்ணுங்க: ஒரு API option, அப்புறம் utilisation, people, infrastructure சேர்ந்த ஒரு self-hosted option.
3. ஒரு sensitivity table (usage பாதியா, ரெண்டு மடங்கா; output ரெண்டு மடங்கா; API prices 30% குறைவா; rupee ₹100-ல), stable crossover, மாசத்துக்கு value பத்தி ஒரு line, இதையெல்லாம் சேருங்க.
