## இது என்ன

**Single sign-on (SSO)** employees-ஐ தங்களோட company account-ஓட ஒரு தடவை sign in பண்ணி, அனுமதிக்கப்பட்ட எல்லா apps-ஐயும் புது passwords இல்லாம access பண்ண விடும். இது company-ஓட identity provider வழியா work ஆகும்: Microsoft Entra ID, Okta, Google Workspace, Ping மாதிரி. யாராவது வேலையை விட்டு போனா, IT ஒரு account-ஐ disable பண்ணா போதும், எல்லாத்துக்குமான access-உம் நின்னுடும்.

மூணு standards முக்கியம்:

- **OAuth 2.0**: access tokens வச்சு, ஒரு app user-ஓட சார்பா வரையறுக்கப்பட்ட, திரும்ப பெறக்கூடிய permission-ஓட செயல்பட விடும். தனியா பார்த்தா இது permission பத்தினது, identity பத்தினது இல்லை.
- **OpenID Connect (OIDC)**: OAuth 2.0-ஓட மேல இருக்குற sign-in layer. App ஒரு **ID token** பெறும். அது user யாருன்னு சொல்லும், email, name, group memberships மாதிரி claims-ஓட. பெரும்பாலான புது apps OIDC-ஐ use பண்றாங்க.
- **SAML 2.0**: XML அடிப்படையிலான பழைய SSO standard. நிறைய பெரிய இந்திய enterprises-உம் government bodies-உம் internal apps-க்கு இன்னும் இதை use பண்றாங்க.

```flow
User app-ஐ திறக்கறாங்க -> உங்க app sign in-க்கு redirect பண்ணுது -> Identity provider | Entra ID, Okta
Identity provider -[password + MFA, provider-க்கு மட்டும் தெரியும்]-> சின்ன ஆயுள் உள்ள code-ஓட திரும்ப redirect
சின்ன ஆயுள் உள்ள code-ஓட திரும்ப redirect -> உங்க app code-ஐ tokens-க்கு exchange பண்ணுது
உங்க app code-ஐ tokens-க்கு exchange பண்ணுது -> ID token (யாரு) + access token (என்ன பண்ணலாம்)
ID token (யாரு) + access token (என்ன பண்ணலாம்) -> Signature, issuer, audience, expiry-ஐ verify பண்றது -> Session உருவாக்கறது | user id, email, groups
```

இந்த lesson-ல Chennai-ல ஒரு automobile-parts manufacturer-ல plant staff-க்கு roll out பண்ண ஒரு quality-documents assistant-ஐ follow பண்ணுவோம்.

## இது எப்படி work ஆகுது

**OIDC sign-in flow** (PKCE-ஓட authorisation code flow, recommend பண்றது):

1. User உங்க app-ஐ திறக்கறாங்க. அது அவங்களை identity provider-க்கு redirect பண்ணும்.
2. அங்க sign in பண்றாங்க, பெரும்பாலும் multi-factor authentication-ஓட. உங்க app அவங்க password-ஐ பார்க்கவே பார்க்காது.
3. Provider ஒரு சின்ன ஆயுள் உள்ள code-ஓட திரும்ப redirect பண்ணும்.
4. உங்க server அந்த code-ஐ ஒரு ID token-க்கும் access token-க்கும் exchange பண்ணும்.
5. உங்க server token-ஓட signature, issuer, audience, expiry-ஐ verify பண்ணி, தன்னோட சொந்த session-ஐ உருவாக்கும்.

**Claims, groups.** ID token user-ஓட groups அல்லது roles-ஐ கொண்டு வரலாம் ("claims-officers-south", "hr-admins"). உங்க app-க்கு தேவையான groups-ஐ சேர்க்கச் சொல்லி client-ஓட identity team-கிட்ட கேளுங்க. இவை தான் உங்க app-ல user என்ன பண்ணலாம்னு, பின்னாடி எந்த documents-ஐ retrieve பண்ணலாம்னு தீர்மானிக்கும்.

**User-ஆ downstream systems-ஐ call பண்றது.** SharePoint அல்லது ஒரு internal API மாதிரி இன்னொரு system-ல இருந்து உங்க AI app-க்கு data தேவைப்படலாம். சிறந்த pattern: user-ஓட token-ஐ அந்த system-க்கு scope பண்ண ஒரு token-ஆ exchange பண்றது ("on-behalf-of" flow). அப்போ அந்த system user-ஓட சொந்த permissions-ஐ apply பண்ணும். ஒரு shared service account அந்த permissions-ஐ bypass பண்ணிடும்.

**App-ஐ register பண்றது.** Client-ஓட identity team உங்க app-ஐ provider-ல register பண்ணும்: redirect URLs, எந்த users அல்லது groups use பண்ணலாம், எந்த claims அனுப்பணும். பெரிய companies-ல இதுக்கு நிமிஷங்கள் இல்லை, நாட்கள் ஆகும். Request-ஐ முதல் வாரத்துலயே ஆரம்பிங்க.

**Library use பண்ணுங்க.** Token validation-ஐ நீங்களே எழுதாதீங்க. Provider-ஓட SDK அல்லது உங்க framework-க்கு நல்லா தெரிஞ்ச library-ஐ use பண்ணுங்க.

**எந்த standard-ஐ எதிர்பார்க்கலாம்:**

| Situation | வர வாய்ப்புள்ள standard | Notes |
| --- | --- | --- |
| புது web app, modern provider | OIDC | எளிமையானது, JSON tokens, நல்ல libraries |
| பெரிய enterprise, பழைய internal apps | SAML 2.0 | XML assertions; library அல்லது gateway use பண்ணுங்க |
| User-க்காக ஒரு API-ஐ call பண்ற app | OAuth 2.0 access tokens | அவற்றை இடுங்கலா scope பண்ணுங்க |
| SharePoint அல்லது Box-ஐ படிக்குற AI app | OIDC sign-in + on-behalf-of | Downstream system user permissions-ஐ apply பண்ணும் |

**Registration request.** ஒரு பக்க request நாட்கணக்குல போற முன்னும் பின்னுமான பேச்சை மிச்சப்படுத்தும். இதுல app-ஓட பெயர், நோக்கம், ஒவ்வொரு environment-க்கும் redirect URLs, use பண்ணக்கூடிய groups, தேவையான claims (email, name, groups), app user-ஓட சார்பா மத்த systems-ஐ call பண்ணுதா, எந்த scopes-ஓட, ஒரு technical contact இருக்கணும். புது groups-ஐ உருவாக்கறதுக்கு பதிலா, ஏற்கனவே இருக்குற groups எதுன்னு identity team-கிட்ட கேளுங்க. ஏன்னா groups-ஐ உருவாக்கி நிரப்பறது தான் பெரும்பாலும் ரொம்ப மெதுவான step.

**Sign-in-க்கு அப்புறம் sessions.** Tokens verify ஆனதும், ஒரு நியாயமான ஆயுளோட server-side session வச்சுக்கோங்க. Plant shifts-க்கு எட்டு மணி நேரம் மாதிரி. Session renew ஆகும்போது group membership-ஐ திரும்ப check பண்ணுங்க. IT ஒரு account-ஐ disable பண்ணா, அடுத்த renewal fail ஆகி access முடிஞ்சுடும்.

**FastAPI, Authlib-ஓட OIDC sign-in.** Library redirects, PKCE, code exchange, token checks எல்லாத்தையும் பார்த்துக்கும்:

```python
import os
from authlib.integrations.starlette_client import OAuth
from fastapi import FastAPI, Request, HTTPException, Depends
from starlette.middleware.sessions import SessionMiddleware

app = FastAPI()
app.add_middleware(SessionMiddleware, secret_key=os.environ["SESSION_SECRET"], https_only=True,
                   max_age=8 * 3600)

oauth = OAuth()
oauth.register(
    name="corp",
    server_metadata_url=os.environ["OIDC_DISCOVERY_URL"],   # e.g. .../v2.0/.well-known/openid-configuration
    client_id=os.environ["OIDC_CLIENT_ID"],
    client_secret=os.environ["OIDC_CLIENT_SECRET"],
    client_kwargs={"scope": "openid email profile", "code_challenge_method": "S256"},
)

@app.get("/login")
async def login(request: Request):
    return await oauth.corp.authorize_redirect(request, request.url_for("callback"))

@app.get("/auth/callback")
async def callback(request: Request):
    token = await oauth.corp.authorize_access_token(request)    # verifies the ID token
    claims = token["userinfo"]
    request.session["user"] = {"id": claims["sub"], "email": claims.get("email"),
                               "groups": claims.get("groups", [])}
    return {"signed_in": claims.get("email")}

def require_group(group):
    def check(request: Request):
        user = request.session.get("user")
        if not user or group not in user["groups"]:
            raise HTTPException(status_code=403)
        return user
    return check

@app.get("/admin/reports")
def reports(user=Depends(require_group("claims-officers-south"))):
    return {"ok": True, "for": user["email"]}
```

Session verify ஆன subject id, groups-ஐ store பண்ணும். Browser அனுப்பின எதையும் store பண்ணாது. User-ஓட key-ஆ `sub` claim-ஐ (அல்லது provider-ஓட object id-ஐ) use பண்ணுங்க. Email மாறலாம், அதனால email வேண்டாம்.

**ஒரு API-க்கு அனுப்பப்படுற tokens-ஐ verify பண்றது.** ஒரு front end உங்க API-க்கு bearer tokens அனுப்பினா, ஒவ்வொரு request-லயும் அவற்றை check பண்ணுங்க:

```python
import jwt

jwks = jwt.PyJWKClient(os.environ["OIDC_JWKS_URL"])

def verify(bearer):
    key = jwks.get_signing_key_from_jwt(bearer)
    return jwt.decode(bearer, key.key, algorithms=["RS256"],
                      audience=os.environ["API_AUDIENCE"], issuer=os.environ["OIDC_ISSUER"])
```

Signature, audience, issuer, expiry எல்லாத்தையும் `jwt.decode` check பண்ணும். இதுல எதையும் skip பண்ணாதீங்க.

**பெரிய group lists.** சில providers, ஒரு user-க்கு ரொம்ப அதிக groups இருந்தா token-ல groups-ஐ list பண்றதை நிறுத்திடும் (Microsoft Entra ID ஒரு "overage" pointer-க்கு மாறும்). ஒண்ணு, app-ஓட groups-ஐ மட்டும் அனுப்பச் சொல்லி identity team-கிட்ட கேளுங்க (app roles ஒரு clean வழி). இல்லைன்னா sign-in நேரத்துல provider-ஓட API-ல இருந்து groups-ஐ எடுங்க.

**வேலையை விட்டு போறவங்க, SCIM.** Identity provider-ல ஒரு user-ஐ disable பண்ணா புது sign-ins நிக்கும், ஆனா ஏற்கனவே திறந்திருக்குற session சில மணி நேரம் இருக்கலாம். Sessions-ஐ குறுகியதா வச்சு, renewal-ல திரும்ப check பண்ணுங்க. Client support பண்ணா SCIM provisioning-ஐ ஏத்துக்கோங்க. அப்போ அவங்க directory-ல ஒரு user-ஐ நீக்கினா, உங்க app-ல உடனே deactivate ஆகிடுவாங்க.

**SAML எழுதாமலே SAML.** Client SAML மட்டும் தர்றாங்கன்னா, முன்னாடி ஒரு gateway அல்லது identity broker-ஐ வைங்க (நிறைய managed auth services SAML-ஐ OIDC-ஆ translate பண்ணும்). அப்போ உங்க app ஒரே standard-ஐ தான் பேசும்.

**Browser-லயே try பண்ணுங்க.** ஒரு ID token மூணு base64 பகுதிகள். நடுவுல இருக்குறதை decode பண்ணா claims தெரியும். உங்க library verify பண்றது அதைத்தான்.

```python
import base64, json

token = ("eyJhbGciOiJSUzI1NiJ9."
         "eyJzdWIiOiJ1LTQ0MSIsImVtYWlsIjoicHJpeWFAZXhhbXBsZS5pbiIsImdyb3VwcyI6WyJjbGFpbXMtc291dGgiXSwiZXhwIjoxOTAwMDAwMDAwfQ."
         "signature")
header, payload, signature = token.split(".")
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(claims)
print("never trust these until the signature, issuer, audience and expiry are checked")
```

## ஒரு நாள், ஒரு example

Microsoft Entra ID use பண்ற ஒரு Chennai automobile-parts manufacturer, உங்க quality-documents assistant-ஐ 1,200 plant staff-க்கு கிடைக்க வைக்க விரும்புது.

முதல் வாரம்: identity team-க்கு ஒரு பக்க request அனுப்புறீங்க: app பெயர், staging, production-க்கான redirect URLs, சேர்க்க வேண்டிய groups (`quality-engineers`, `plant-chennai`, `plant-pune`, `contractors`), user-ஓட சார்பா app SharePoint-ஐ call பண்ண வேணுமா (ஆமா, read-only).

உங்க FastAPI backend ஒரு maintained OIDC library-ஐ use பண்ணுது. Sign-in-க்கு அப்புறம், அது ID token-ஐ verify பண்ணி, user-ஓட id, email, groups-ஐ ஒரு session-ல store பண்ணுது. SharePoint-க்கு போற requests ஒரு on-behalf-of token-ஐ use பண்ணுது. அதனால Pune engineer தன்னோட சொந்த SharePoint permissions அனுமதிக்குற documents-ஐ மட்டும் தான் retrieve பண்ண முடியும்.

Go-live-ல contractors sign in பண்ண முடியலைன்னு புகார் பண்றாங்க. Provider-ஓட sign-in error அவங்க app-க்கு assign ஆகலைன்னு சொல்லுது: identity team employee groups-ஐ மட்டும் assign பண்ணியிருந்தாங்க, `contractors`-ஐ இல்லை. Provider-ஓட assignment-ல ஒரு மாற்றம் அதை fix பண்ணுச்சு. அடுத்த மாசம் ஒரு quality engineer company-ஐ விட்டு போனப்போ, IT அவங்க account-ஐ disable பண்ணாங்க. நீங்க எதுவும் பண்ணாமலே assistant-க்கான அவங்க access முடிஞ்சுச்சு.

| Event | என்ன நடந்தது | யார் fix பண்ணாங்க |
| --- | --- | --- |
| முதல் வாரம் | Registration request அனுப்பப்பட்டது | நீங்க, identity team-க்கு |
| Go-live | Contractors sign in பண்ண முடியலை | Identity team group assignment-ஐ சேர்த்தாங்க |
| ஒரு மாசம் கழிச்சு | ஒரு engineer company-ஐ விட்டு போனார் | IT ஒரு account-ஐ disable பண்ணாங்க; access தானா முடிஞ்சுது |

## பொதுவா பண்ற தப்புகள்

- **சொந்தமா login எழுதறது.** Clients அதை மறுப்பாங்க. அவங்க security controls-ஐ மோசமா duplicate பண்ணும்.
- **Token validation steps-ஐ skip பண்றது.** Signature, issuer, audience, expiry-ஐ ஒவ்வொரு தடவையும், ஒரு library வச்சு check பண்ணுங்க.
- **OAuth access tokens-ஐ identity-க்கு proof-ஆ use பண்றது.** User யாருன்னு தெரிஞ்சுக்க OIDC ID token-ஐ use பண்ணுங்க.
- **எல்லா downstream calls-க்கும் ஒரே service account.** அப்போ users தங்க சொந்த permissions தடுக்குறதையும் பார்க்க முடியும்.
- **App registration-ஐ லேட்டா கேக்கறது.** Identity teams-க்கு queues-உம் approvals-உம் இருக்கும். முதல் நாளே கேளுங்க.
- **Email-ஐ key-ஆ வச்சு users-ஐ அடையாளம் காண்றது.** Emails மாறும். நிலையான subject அல்லது object id-ஐ use பண்ணுங்க.
- **Renewal check இல்லாத நீண்ட sessions.** அப்போ வேலையை விட்டு போனவங்களுக்கும் access இருக்கும்.
- **Bearer tokens-ல audience அல்லது issuer checks-ஐ skip பண்றது.**

## Single sign-on தேவையில்லாத நேரங்கள்

- **Consumer apps.** அங்க Google, GitHub அல்லது email sign-in தான் users எதிர்பார்க்குறது.
- **ஒரு team-க்கான prototype.** Pilot approve ஆகுற வரை, ஒரு managed auth service-ஓட email login போதும்.
- **User இல்லாத machine-to-machine calls.** அவை client credentials அல்லது API keys-ஐ use பண்ணும்.

Enterprise clients கிட்டத்தட்ட எப்பவும் production-க்கு முன்னாடி SSO வேணும்னு கேப்பாங்க. முதல் வாரத்துல இருந்தே அதுக்கு plan பண்ணுங்க.

## Demo-ல இருந்து production-க்கு

- **முதல் வாரத்துலயே registration request-ஐ அனுப்புங்க**, ஒவ்வொரு environment-க்கும் redirect URLs-ஓட.

## Practice பண்ணுங்க

Okta-ஓட OAuth, OIDC பத்தின illustrated guide-ஐ படிச்சுட்டு, அப்புறம் OIDC, SAML பத்தின Auth0-ஓட pages-ஐ படிங்க.

1. ஒரு identity provider-ல free developer account உருவாக்கி, ஒரு redirect URL-ஓட ஒரு app-ஐ register பண்ணுங்க.
2. உங்க FastAPI app-ல ஒரு maintained library வச்சு OIDC sign-in-ஐ சேருங்க. Sign-in-க்கு அப்புறம் verify ஆன claims-ஐ print பண்ணுங்க.
3. ஒரு group claim-ஐ சேர்த்து, நீங்க தேர்ந்தெடுத்த group-ஓட members மட்டும் call பண்ணக்கூடிய ஒரு endpoint-ஐ காட்டுங்க.
4. ஒரு test user-ஆ sign in பண்ணி, provider-ல அவரை group-ல இருந்து நீக்கி, protected endpoint 403 திருப்பி தர எவ்வளவு நேரம் ஆகுதுன்னு அளந்து பாருங்க.

**முடிஞ்சதுன்னு எப்போ சொல்லலாம்:** OIDC code flow-ஓட ஒவ்வொரு step-ஐயும் explain பண்ண முடியும், அனுமதிக்கப்பட்ட group-க்கு வெளியே இருக்குற user-ஐ உங்க app reject பண்றதையும் காட்ட முடியும்.
