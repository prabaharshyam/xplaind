## What it is

**Vibe coding** means building software by describing what you want to an AI agent instead of typing the code yourself. Andrej Karpathy, a well-known AI researcher, coined the term in a post in February 2025. He described a style where you give in to the vibes, accept what the AI writes and barely look at the code. The phrase spread so fast that Collins Dictionary made "vibe coding" its Word of the Year for 2025.

That original, unreviewed style has a place. It is fine for a weekend prototype, a one-off script on your own laptop, or a demo you will throw away. It is risky for anything that holds other people's data, money, passwords or private notes, because nobody has checked what the code does. **This lesson teaches the reviewed version**: Claude writes most of the code, and you set the goal, check every step and decide what ships. When an interviewer says "vibe coding", find out which meaning they intend.

**Claude Code** is Anthropic's coding agent. An **agent** is an AI that takes actions in a loop, not only text replies. A chatbot suggests code for you to copy. Claude Code acts in your project: it reads files, writes and edits them, runs commands such as tests and builds, reads the errors and tries again. You can use it in a terminal, in VS Code or a JetBrains IDE, in the Claude desktop app, or in the browser at claude.ai/code.

The skill is not clever wording. It is the skill a good team lead uses with a fast new colleague: explain the goal, break the work into small steps, review what comes back, and say exactly what to change.

```flow
title: One loop per feature; commit after each working step
You: a spec and one feature -> Claude plans in plan mode
Claude plans in plan mode -[you approve or trim]-> Claude edits files
Claude edits files -> Claude runs tests and the app
Claude runs tests and the app -> You read the diff and try the app
You read the diff and try the app -[works]-> Commit, next feature
You read the diff and try the app -[wrong]-> Precise feedback or rewind
Precise feedback or rewind -> Claude plans in plan mode
```

## How it works

### 1. Set up and know the cost

Install Claude Code with the command on the official overview page, then open a terminal in a new folder and run `claude`. It asks you to log in the first time. Run `git init` in the folder too, so every change can be seen and undone. If you have never used a terminal, the docs have a short terminal guide.

You need a paid Claude plan or an API account on the Claude Console. Claude Code is not part of the Free plan. Prices on Anthropic's pricing page, as of 28 November 2026:

| Plan | Price in US dollars (checked 28 Nov 2026) | Usage |
|---|---|---|
| Free | $0 | Chat only; Claude Code not included |
| Pro | $20 a month, or $17 a month billed yearly ($200 up front) | More than Free, with a 5-hour and a weekly limit |
| Max | $100 a month | 5x Pro usage |
| Ultra | $200 a month | 10x Pro usage a week, no 5-hour limit for verified accounts |

In India the plans are billed in rupees, and the rupee amount can change, so check claude.ai/upgrade on the day you buy. Claude Code shares your plan's limits with chat. Anthropic's pricing page pitches Pro "for everyday work" and Max "for all-day work". If you hit the 5-hour limit in the middle of a build, you wait for the reset or turn on paid usage credits. Type `/usage` in a session to see how much you have used. A small app like the one below is a good test of whether Pro is enough for you before you pay for more.

### 2. Write a short spec

Before any code, write half a page in `SPEC.md`: what the app does, who uses it, the three to five features that matter, how it should look on a phone, and what is out of scope. The out-of-scope list matters most, because it stops Claude adding things you never asked for. If you are unsure what you want, ask Claude to interview you: "Ask me questions one at a time until you could write SPEC.md, then write it."

### 3. Give it a memory with CLAUDE.md

Each session starts with a fresh context. Claude reads `CLAUDE.md` at the start of every session, so put there what it cannot work out from the code: how to run and test the app, and your rules, such as "mobile first, 360 px wide", "no paid APIs" or "never put keys in client code". Run `/init` to get a first draft, then delete lines. Anthropic's docs suggest keeping each file under 200 lines, because every line takes some of Claude's attention on every task. If you correct Claude about the same thing twice, add a line.

### 4. The controls you will use

| You want to | Do this |
|---|---|
| Get a plan with no edits | Type `/plan` and the task, or press Shift+Tab until the mode shows plan |
| Approve each command yourself | Press Shift+Tab to leave auto mode for the manual (default) mode |
| See what changed | Type `/diff`, or run `git diff` |
| Undo Claude's last edits | Press Esc twice on an empty prompt, or type `/rewind` |
| Start a new, unrelated task | Type `/clear` (you can return with `/resume`) |
| Shorten a long session | Type `/compact` with what to keep, for example `/compact keep the test commands` |
| Stop Claude mid-step | Press Esc |

**Permission modes** decide what Claude may do without asking you. New terminal and VS Code sessions start in **auto mode**: Claude works without stopping for routine steps, and a separate safety model checks each action and blocks risky ones, such as a production deploy, a force push or sending data to an unknown server. Anthropic says plainly that auto mode reduces prompts but does not guarantee safety. On your first project, consider the manual mode, where Claude asks before each command, so you learn what it runs. Never use the bypass mode on your own laptop; the docs limit it to isolated containers.

**Checkpoints are not a backup.** `/rewind` undoes edits Claude made with its file tools, but not every change a shell command made. Git is your real history: commit after every working step.

### 5. Plan, then build in small steps

Ask for a plan first, read it, and cut anything you do not need. Then build one feature at a time: the layout, then the data, then the calculations, then saving, then deployment. A small step gives a small diff, and a small diff is one you can actually read. Give Claude a way to check its own work: tests, or "run the app and check it at 360 px wide". The built-in `/verify` command asks Claude to build and run the app and look at the result.

### 6. Read the diff for red flags

You do not need to understand every line to review well. Skim for these and ask "why?" when you see one:

- **Files you did not mention.** A layout fix should not touch the settlement maths.
- **Deleted or weakened tests.** An agent under pressure sometimes "fixes" a failing test by changing what it expects.
- **New packages** you did not agree to. Each one is code you now depend on.
- **A secret key** in any file that runs in the browser.
- **Size out of proportion.** A one-line bug with a 300-line diff needs an explanation.

### 7. Check security before you share the link

A common way AI-built apps get hurt is not clever hacking. It is a key or a database left open. Before anyone else gets the link:

- **No secret keys in client code.** In Next.js, any variable whose name starts with `NEXT_PUBLIC_` is copied into the JavaScript sent to every visitor. Use that prefix only for values that are safe to publish.
- **`.env` is in `.gitignore`**, and no key appears in your git history.
- **Row-level security on every Supabase table.** Supabase's browser key is meant to be public; row-level security decides which rows each user may read or change. The secret (service role) key skips those rules, so it must stay on the server.
- **Check input on the server**, not only in the form.
- Then ask Claude directly: "Review this project for exposed secrets, tables without row-level security and unchecked input. List each problem with the file."

## A worked example

This is an illustrative story; the times are illustrative, not measured. Nisha shares a flat in Pune with three friends and is tired of splitting bills in a WhatsApp chat. She is a product designer, not a developer.

**The spec.** She writes `SPEC.md`: "A one-page web app. Add a bill: amount, who paid, who shares it (the payer always shares). Show who owes whom, with the fewest payments. Works on a phone. Saves in the browser; no login. Rupees, whole numbers. Out of scope: accounts, unequal splits, payment links." She runs `claude`, types `/init`, and asks Claude to read the spec and ask questions. Claude asks whether a bill can be shared by only some flatmates. Yes, she says: when one person is away, groceries are split among three.

**The plan, and her push-back.** In plan mode Claude proposes a Next.js app with a server, a form, a bill list, a settlement function, local storage and tests. Nisha asks: "There is no login and no database. Is there a simpler stack?" Claude offers two options: plain HTML and JavaScript, or a small Vite app with Vitest for tests. She picks Vite, because it builds to plain static files that Vercel can host, and Vitest makes the maths easy to test. She approves step one only: the page and the form. It runs on her phone. She commits.

**The bug the tests caught.** For step three, the settlement maths, she asks for tests first. One test uses a case she can check by hand: Nisha pays ₹1,000 for groceries shared by Nisha, Aarti and Meera. ₹1,000 divided by three is ₹333.33, so one person must pay a rupee more. Claude writes a rule-based test too: the shares must always add up to the bill. That test fails. The first version gave everyone ₹333, which adds up to ₹999, so one rupee vanishes. Claude explains the cause and fixes it by giving the leftover rupee to the payer:

```js
export function splitBill(amount, payer, people) {
  const share = Math.floor(amount / people.length); // 1000 / 3 -> 333
  const shares = Object.fromEntries(people.map((p) => [p, share]));
  shares[payer] += amount - share * people.length; // payer is a sharer: 333 + 1 = 334
  return shares;
}
// splitBill(1000, "Nisha", ["Nisha", "Aarti", "Meera"])
// -> { Nisha: 334, Aarti: 333, Meera: 333 }; Aarti and Meera each owe Nisha 333
```

She would never have spotted a lost rupee by eye. The rule-based test caught it, and it will catch the same mistake if a later change brings it back.

**A red flag.** While fixing the table on a 360 px screen, Claude's diff also edits the settlement file. Nisha asks why. It was an unrelated rename. She presses Esc twice, rewinds, and asks again with "change only the CSS".

**Shipping.** Before deploying, she asks for the security review in step 7. There are no keys and no server, so the only finding is that `.env` is missing from `.gitignore`; Claude adds it. In the evening she deploys to Vercel. Her flatmates use the app the next morning. It took about five hours, most of it spent deciding what she wanted.

## Common mistakes

**Asking for the whole app in one message.** You get a big, untested tangle you cannot review. Ask for one feature at a time.

**Skipping the spec.** Without one, Claude guesses, and you only notice the wrong guess after it has built on top of it. Write what is out of scope, too.

**Accepting an over-built plan.** Agents often propose a bigger stack than you need. Ask "is there a simpler way?" before approving.

**Accepting changes you do not understand.** Ask for an explanation. You own the code, its bugs and its security.

**Trusting auto mode or checkpoints as your safety net.** Auto mode is a model's judgement, not a guarantee, and checkpoints miss some changes. Commit after every working step.

**Putting keys where the browser can see them.** A secret in client code or in a `NEXT_PUBLIC_` variable is public. Keep secrets in server-side environment variables and a `.env` file that git ignores.

**Leaving a database open.** A Supabase table without row-level security can be read, and often changed, by anyone with your app's public key, which every visitor has.

**Endless "fix it" loops.** If the same bug survives two corrections, stop. Run `/clear`, then write one new prompt with the exact steps, the expected and actual result, and what you learned, and ask for the cause before any change.

## Practice

Do this guided task in about 45 minutes. You will need a paid plan or an API account.

1. Make a new folder, run `git init`, then `claude`.
2. Write `SPEC.md` for Nisha's bill splitter from the worked example, in your own words, with an out-of-scope list.
3. Run `/init`, open `CLAUDE.md` and add the run and test commands plus one rule of your own. Keep it short.
4. Type `/plan` and ask for a plan for the whole app. Reject or simplify at least one part, and write one sentence on why.
5. Build only step one. Read the diff with `/diff`, try the page at 360 px wide, and commit.
6. Ask for tests for `splitBill` that include ₹1,000 shared by three. Check that a rule like "shares add up to the bill" is among them.
7. Do the "Fix the prompt" exercise above, then compare your answers with the model answers.
