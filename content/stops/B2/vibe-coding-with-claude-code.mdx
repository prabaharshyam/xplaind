## What it is

**Vibe coding** is building software by describing what you want to an AI coding agent, then steering and checking its work, instead of typing most of the code yourself. The term took off in 2025 and is now how many founders, product managers, analysts and students build their first tools.

**Claude Code** is Anthropic's coding agent. Unlike a chatbot that only suggests code, it acts in your project: it reads files, writes and edits them, runs commands such as tests and builds, looks at the errors and tries again. You can use it in a terminal, inside VS Code or JetBrains, in the Claude desktop app, or in the browser on claude.ai.

The skill is not typing prompts. It is the same skill a good engineering lead uses with a new team member: explain the goal clearly, break the work into steps, review what comes back, and say what to change.

```flow
title: Repeat in small steps; commit after each working step
You: an idea and a spec -> Claude Code plans
Claude Code plans -[you approve]-> Claude Code edits files
Claude Code edits files -> Claude Code runs tests and the app
Claude Code runs tests and the app -> Summary of changes, errors, output
Summary of changes, errors, output -> You review the diff, try it, give feedback
You review the diff, try it, give feedback -> You: an idea and a spec
```

## How it works

**1. Set up.** Install Claude Code from the official docs, open a terminal in an empty folder and run `claude`. It needs a Claude subscription or API account. Make the folder a git repository so every change can be seen and undone.

**2. Write a short spec.** Before any code, write half a page: what the app does, who uses it, the three to five features that matter, what it should look like on a phone, and what is out of scope. Ask Claude to read it and ask you questions. This one habit removes most bad results.

**3. Give it a memory with CLAUDE.md.** Claude reads `CLAUDE.md` at the start of every session. Put the stack, how to run and test the app, and your rules in it, such as "mobile first", "no paid APIs" or "never commit secrets". You can ask Claude to write the first version with `/init`.

**4. Plan, then build, in small steps.** Ask for a plan first (Claude Code has a plan mode that only reads and proposes). Approve or correct it. Then build one feature at a time: the layout, then the data, then the calculations, then saving, then deployment.

**5. Review every change.** Read the summary and skim the diff. Run the app yourself. Ask "why did you do it this way?" when something looks odd. Commit when a step works.

**6. Let it test and fix.** Ask Claude to write tests for important logic and run them. When something breaks, paste the error or describe exact steps; it is very good at tracing a bug when it has evidence.

| Stage | What you say | What to check |
|---|---|---|
| Spec | "Read SPEC.md and ask me anything unclear" | its questions show it understood |
| Plan | "Plan the first feature; don't write code yet" | files touched, approach, nothing extra |
| Build | "Implement step 1 of the plan" | it runs; the diff is small and readable |
| Test | "Add tests for the split calculation and run them" | tests cover edge cases, not just the happy path |
| Fix | "On 360 px wide the table overflows. Fix it" | the fix, and that nothing else moved |
| Ship | "Set up deployment to Vercel and explain the steps" | no secrets in code; environment variables used |

## A worked example

Nisha shares a flat in Pune with three friends and is tired of splitting bills in a WhatsApp chat. She is a product designer, not a developer.

She writes `SPEC.md`: "A one-page web app. Add a bill with who paid and who shares it. Show who owes whom, settling with the fewest payments. Works on a phone. Saves in the browser; no login. Rupees." She runs `claude` in a new folder and asks it to read the spec and ask questions. Claude asks whether bills can be split unequally and whether she wants a UPI link for payments. She says unequal splits later, UPI links yes.

She asks for a plan and gets: a Next.js app, a form, a list of bills, a settlement function, local storage, and tests for the settlement maths. She approves step one only: the page and the form. It runs. She commits.

Step three is the settlement maths. She asks Claude to write tests first, with a case she knows the answer to: three friends, one paid ₹3,000 for groceries. One test fails because rounding leaves ₹1 unaccounted for. Claude explains the cause and fixes it by giving the remainder to the payer. She would never have spotted that by eye.

In the evening she asks Claude to set up deployment to Vercel. Her flatmates use the app the next morning. Total time: about five hours, most of it deciding what she wanted.

## Common mistakes

**Asking for the whole app in one message.** You get a big, untested tangle. Ask for one feature at a time.

**Skipping the spec.** Without one, Claude guesses, and you only notice the wrong guess after it has built on top of it.

**Accepting changes you do not understand.** Ask for an explanation. You own the code, its bugs and its security.

**No git.** Without commits you cannot see what changed or go back. Commit after every working step.

**Putting API keys in the code.** Keep secrets in environment variables and a `.env` file that git ignores. Ask Claude to check for secrets before you push.

**Endless "fix it" loops.** If the same bug survives three attempts, stop. Describe the exact steps, the expected and actual result, and ask Claude to explain the cause before changing anything.
