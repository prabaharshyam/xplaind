## What it is

Many automations must react **the moment something happens**: a payment succeeds, an order is placed, a form is submitted. A **webhook** makes that possible.

A webhook is a message one app sends to a web address (URL) you provide, as soon as an event happens. It is like a doorbell. Instead of checking the door every few minutes, which is called **polling**, you are told when someone arrives.

```flow
dir: LR
title: Polling: slow, many wasted requests
Your app -[anything new?]-> Store
Store -[no ... no ... yes, an order]-> Your app
```

```flow
dir: LR
title: Webhook: told when it happens, fast, no wasted checks
Store -[POST the event]-> Your URL (n8n)
Your URL (n8n) -[200 OK]-> Store
```

The message is usually an HTTP **POST** request with a **JSON** body describing the event. A simplified example, shaped like a payment gateway's event:

```json
{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}
```

In this sample the amount is in paise, so 420000 means ₹4,200.

**Webhook or API?** With an API, *you* call the provider and ask. With a webhook, the provider calls *you* when something changes. Good automations use both: the webhook says something happened, and the API lets you check details and fill gaps.

This lesson follows a handicrafts store in Jaipur that wants an invoice emailed the instant a payment succeeds.

## How it works

### The life of one delivery

Every delivery follows the same loop. The sender only watches your reply.

```flow
title: One webhook delivery
Event happens | for example a payment is captured -> Sender signs the JSON with your secret
Sender signs the JSON with your secret -> POST to your URL
POST to your URL -> Your reply
Your reply -[2xx within the timeout]-> Delivered | the sender stops
Your reply -[error or no reply in time]-> Retry later | same event, same id
Retry later -> POST to your URL
```

So a `2xx` reply means "done" to the sender, even if your workflow fails a second later, and any failure brings the same event back.

### Receiving: test and production URLs

Your automation tool gives you a URL, for example from n8n's **Webhook** node. You paste it into the sending app's settings and choose which events to send. Many tools give two URLs:

| URL | Works when | Use it for |
| --- | --- | --- |
| Test URL | You are listening in the editor | Building and debugging |
| Production URL | The workflow is published (active) | Real events |

A common beginner mistake is leaving the test URL in the sender's settings: everything works while you watch, then stops.

Two Webhook node settings matter here. **Raw Body** keeps the exact bytes the sender posted, which you need to check a signature. **Respond** controls when n8n replies: immediately, when the last node finishes, or at a **Respond to Webhook** node you place exactly where you want.

### Test before real events arrive

Field names vary by provider, so build mappings from a real sample. You can send one yourself with `curl`: click "Listen for test event" in n8n, then run this with your own test URL:

```bash
curl -X POST "https://your-n8n.example.com/webhook-test/payments" \
  -H "Content-Type: application/json" \
  -d '{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
```

One trap stops many beginners. If n8n runs on your laptop, its URL starts with `localhost`, which a gateway on the internet cannot reach. Use a public n8n (n8n Cloud, or a server with HTTPS), a **tunnel** such as ngrok or Cloudflare Tunnel that gives your laptop a public address, or webhook.site to just inspect what the provider sends.

Most gateways also have a **test mode** with no real money. Test and live mode usually have separate webhooks and separate secrets.

### What your reply tells the sender

The sender reads only your reply's status code, and waits only seconds. Razorpay, an Indian payment gateway, expects a `2xx` reply within 5 seconds. It treats any other code, or no reply in time, as a failure and retries with increasing gaps for 24 hours after the event was created. If deliveries keep failing for those 24 hours, it disables the webhook (all as of November 2026). Other providers have different windows, so read their docs.

| Your reply | What the sender concludes | When to send it |
| --- | --- | --- |
| `200` (or another `2xx`) | Delivered; never send it again | The event is saved, or it is a duplicate you already have |
| `401` | Failed; usually retried | The signature does not match |
| `500` | Failed; retried later | You could not save the event, for example your database is down |
| No reply in time | Failed; retried later | Your workflow was too slow or the server was down |

### Save first, then reply, then do the work

This is the most important idea in the lesson. Of three possible orders, two fail.

| Order | What goes wrong |
| --- | --- |
| Do all the work, then reply | Slow work, such as making a PDF, passes the timeout. The sender retries while you work, and you get duplicates. |
| Reply first, then do the work | If n8n crashes or restarts after the `200`, the sender never resends and the event is lost. |
| Save, reply, then work from the saved copy | The event is safe before the sender hears "done". Failed work is retried from your copy. |

**Saving durably** means writing the event somewhere that survives a restart: a database table (for example Postgres or Supabase) or a message queue. One insert is fast, well inside the timeout. Store the raw body, the event id, the time received and a **status**: `received` when saved, `done` when the work has finished.

```flow
title: Save, reply, then work
Webhook arrives -> Signature matches?
Signature matches? -[no]-> Reply 401 and stop
Signature matches? -[yes]-> Insert event id | status received
Insert event id -[already exists]-> Reply 200 and stop | a duplicate
Insert event id -[saved]-> Reply 200
Reply 200 -> Create invoice and email it
Create invoice and email it -> Mark status done
```

If the workflow crashes after the reply, the row stays `received`. A **sweep**, a scheduled workflow that runs every 15 minutes or so, picks up rows still `received` after 10 minutes and runs the work again. So the work must be safe to repeat: record each sub-step (invoice created, email sent) so a rerun does only what is missing.

### Duplicates and idempotency

Most senders promise **at-least-once delivery**: they would rather send an event twice than lose it. The defence is **idempotency**: processing an event twice has the same effect as processing it once.

Use two ids for two different jobs:

- The **event id** identifies one delivery. Its value is the same on every retry of that event, so it tells you "I have seen this delivery before". Razorpay, for example, sends it in the `x-razorpay-event-id` header.
- The **business id**, such as the payment id, identifies the real-world thing. Two *different* events can describe one payment (for example `payment.captured` and `order.paid`), so key the invoice on the payment id.

**The race that catches experts.** A tempting design is "look up the id in the sheet; if it is not there, add it". After a slow reply, the retry can arrive one second after the original. Both copies look up `pay_771`, both find nothing, both create an invoice, because another copy slipped in between the check and the write.

The fix is **one step that fails on a duplicate**. Give the `event_id` column a unique key and simply insert. Exactly one insert succeeds; the other gets a "duplicate key" error, which your workflow treats as "already have it, reply 200 and stop". Put a unique key on the invoice's `payment_id` too.

A Google Sheet has no unique key. A sheet lookup is acceptable only for a small, low-volume shop that accepts the occasional double invoice. Move to a database table before a sale.

### Events can arrive out of order

Delivery order is not guaranteed; Razorpay's webhook guidance says so directly (as of November 2026). A retried `payment.failed` from an earlier attempt can arrive *after* the successful `payment.captured`, and "the latest event wins" would mark a paid order as failed. Two rules handle this:

- **Only move states forward.** An order can go from `created` to `paid`, but never from `paid` back to `failed`. Ignore events that would move it backwards.
- **When it matters, ask for the current state.** Before shipping or refunding, call the provider's API for the status now.

### Security

Anyone who learns your URL could post a fake "payment captured" that triggers a real shipment. Protect it in layers.

**Verify the signature.** You and the provider share a **webhook secret**. For each delivery, the provider computes an **HMAC**, a fingerprint of the body made with the secret, and sends it in a header. Razorpay, for example, sends an HMAC-SHA256 hex value in `X-Razorpay-Signature` (as of November 2026). You compute the same HMAC over the body you received; if they match, the sender knows the secret and the body was not changed. Use the webhook's own secret, not your API key secret.

Three details decide whether the check works:

1. **Use the raw body.** The signature covers the exact bytes sent. Parse the JSON and turn it back into text, and spaces or key order can change, so a genuine event fails. In n8n, turn on **Raw Body**.
2. **Compare in constant time.** A normal comparison stops at the first wrong character, which can leak timing clues. n8n's **Crypto** node can compute the HMAC, but an IF node comparison is not constant-time. For high-value flows, compare in a **Code** node with Node's `crypto.timingSafeEqual`; on self-hosted n8n, allow the `crypto` module first with the `NODE_FUNCTION_ALLOW_BUILTIN` environment variable.
3. **Reject old messages, where the provider signs a timestamp.** A signature proves who sent a message, not when, so a captured request could be replayed later. Some providers, such as Stripe, sign a timestamp so you can reject anything older than a few minutes. Where there is none, your unique event id makes a replay harmless.

This Python script, standard library only, shows the raw-body trap:

```python
import hmac, hashlib, json

SECRET = b"test_secret_123"

def is_genuine(raw_body: bytes, signature: str) -> bool:
    expected = hmac.new(SECRET, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, signature)  # constant-time

raw = b'{"event":"payment.captured","payload":{"payment":{"entity":{"id":"pay_771","amount":420000,"currency":"INR","status":"captured"}}}}'
sig = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()

print(is_genuine(raw, sig))                          # True
print(is_genuine(json.dumps(json.loads(raw)).encode(), sig))  # False: spaces were added
```

It fails the second time because `json.dumps` adds spaces: same data, different bytes.

**Other layers:** use HTTPS and a long, random URL path (neither replaces the signature). Before shipping goods, re-fetch the payment from the provider's API; Razorpay itself advises using its fetch APIs as a backstop to webhooks, for example when a time-sensitive flow cannot wait for the webhook to arrive.

### Missed events and reconciliation

Retries cover short outages, not long ones. Beyond the retry window, events are lost without any error, and some providers switch the webhook off. Important flows have two safety nets:

- The **sweep** retries work for events you saved but did not finish.
- The **reconciliation**, for example nightly, asks the provider's API for all of the day's captured payments and compares them with your invoices. Anything missing is processed then.

Also set an alert: if no webhook arrives for an hour during business hours, or the provider says a webhook was disabled, someone looks the same day.

## A worked example

A handicrafts store in Jaipur uses Razorpay and wants an invoice emailed the moment a payment succeeds. A typical order is ₹4,200. Gateway details are as of November 2026. They build this in n8n:

| # | Step | Why |
| --- | --- | --- |
| 1 | Webhook node: production URL, Raw Body on, replies through a Respond to Webhook node. Added in the Razorpay dashboard for `payment.captured`. | Receive events instantly, with the exact bytes |
| 2 | Compute the HMAC-SHA256 of the raw body with the webhook secret and compare it with `X-Razorpay-Signature` in a Code node. On a mismatch, reply `401`. | Reject fake requests |
| 3 | Insert the `x-razorpay-event-id`, payment id and raw body into `webhook_events` (unique event id, status `received`). Duplicate key: reply `200` and stop. Any other failure: reply `500`. | The event is safe before the gateway hears "done"; copies stop here |
| 4 | Respond to Webhook: `200`. | Well inside the 5-second limit |
| 5 | Create the invoice PDF in an `invoices` table with a unique payment id, email it, then set the event's status to `done`. | The slow work, safe to repeat |
| 6 | Every 15 minutes: rerun step 5 for rows still `received` after 10 minutes. | Finish work that crashed |
| 7 | Nightly: fetch the day's captured payments from the Razorpay API and compare them with the invoices. | Catch anything that never arrived |

**The festival sale (an illustration).** During the Diwali sale, orders arrive every few seconds.

- The PDF service hangs and n8n restarts mid-invoice for one payment. That event was already saved and answered, so Razorpay does not resend it. Ten minutes later the sweep finds the row still `received` and sends the invoice.
- Another restart takes the server down for two minutes. Razorpay gets no reply for those payments and retries them once the server is back.
- pay_771 had been saved just before that restart, but the `200` never left the server. Razorpay retries it; the insert in step 3 hits the duplicate key, and the workflow replies `200` and stops.

| Situation | What happened | Which step handled it |
| --- | --- | --- |
| Fake request from an unknown sender | Signature did not match | Step 2: rejected with `401` |
| Crash after the reply, before the invoice | Row stayed `received` | Step 6: finished by the sweep |
| Events sent during the 2-minute outage | Retried by Razorpay later | Steps 1 to 5, a few minutes late |
| pay_771 delivered twice | Event id already in the table | Step 3: stopped with `200` |
| A week of nightly reconciliation | No missing payments found | Step 7 |

The store's first version replied immediately and used a sheet lookup. The crashed invoice would have been lost for good, because the gateway had its `200`, and the duplicate pay_771 would have created a second invoice: ₹4,200 of sales that never happened.

## Common mistakes

- **Using the test URL in production.** Events stop arriving once you close the editor.
- **Replying before the event is saved.** A crash after the `200` loses the event, because the sender will not resend it.
- **Doing slow work before replying.** The sender times out and retries, creating duplicates.
- **"Look up, then write" as the duplicate check.** Two copies arriving together both pass. Use a unique key.
- **Answering a duplicate with an error.** The sender keeps retrying an event you already have. Reply `200`.
- **Checking the signature on parsed JSON, or trusting the URL alone.** Use the raw body; a secret URL can leak.
- **Assuming events arrive in order.** Only move states forward, and re-fetch before acting on money.
- **Mixing test and live secrets.** Each mode usually has its own webhook and secret.
- **No sweep, no reconciliation, no alert.** Crashes and long outages lose events silently.
- **Logging secrets.** Keep the webhook secret and full payment details out of shared logs.
