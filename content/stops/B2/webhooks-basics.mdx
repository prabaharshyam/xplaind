## What it is

Many automations need to react **the moment something happens**: a payment succeeds, an order is placed, a form is submitted, a support ticket is closed. A **webhook** makes that possible.

A webhook is a message one app sends to a web address (URL) you provide, as soon as an event happens. It is like a doorbell. Instead of checking the door every few minutes, which is called **polling**, you are told when someone arrives.

```text
   Polling (checking again and again)            Webhook (told when it happens)
 +-----------+    "anything new?"   +-------+   +-------+   POST {event}   +-----------+
 | Your app  | ------------------> | Store |   | Store | ---------------> | Your URL  |
 |           | <------ "no" ------ |       |   |       |                  | (n8n)     |
 |           | ------------------> |       |   |       | <-- 200 OK ----- |           |
 |           | <------ "no" ------ |       |   +-------+                  +-----------+
 |           | ------------------> |       |
 |           | <-- "yes, order" -- |       |   fast, no wasted checks
 +-----------+                     +-------+
   slow, many wasted requests
```

The message is usually an HTTP **POST** request with a **JSON** body describing the event: what happened, when, and the details.

This lesson follows a handicrafts store in Jaipur that wants an invoice emailed the instant a payment succeeds. By the end you will receive, test, secure and safely repeat webhooks.

## How it works

### Receiving

Your automation tool gives you a URL, for example from n8n's **Webhook** node. You paste it into the sending app's settings and choose which events to send. When an event happens, the sender posts JSON to your URL, and your workflow starts with that data.

### Test versus production URLs

Many tools give two URLs:

| URL | Works when | Use it for |
| --- | --- | --- |
| Test URL | You are listening in the editor | Building and debugging |
| Production URL | The workflow is published (active) | Real events |

A common beginner mistake is leaving the test URL in the sender's settings. Everything works while you watch, and stops when you close the editor.

### Inspect the payload

Trigger a test event and look at the exact JSON received. Field names and nesting vary by provider. Build your mappings from a real sample, not from memory.

### Respond quickly

Senders expect a fast success reply, usually an HTTP `200 OK` within a few seconds. If your workflow does slow work first, such as generating a PDF, the sender may time out and **retry**. So: reply immediately, then do the work.

### Retries and duplicates

If your endpoint fails or is slow, most senders retry, sometimes several times over many hours. Some deliver "at least once" by design. Either way, **you may receive the same event more than once.**

The defence is **idempotency**: making your actions safe to repeat. Use the event's or payment's id to check whether you already processed it:

```text
  Webhook arrives (payment id = pay_771)
        |
        v
  Is pay_771 already in our sheet?
        |-- yes --> stop (duplicate, do nothing)
        |-- no  --> create invoice, email it, add row with pay_771
```

A duplicate "payment captured" must never create two invoices or two emails.

### Security

Anyone who learns your URL could post fake events, such as a fake "payment captured" that triggers a real shipment. Protect it:

| Protection | What it does |
| --- | --- |
| **Verify the signature** | Many providers sign each webhook with a shared secret; your workflow checks the signature before trusting the data |
| **HTTPS and a long, unguessable path** | Makes the URL hard to find and the data unreadable in transit |
| **Re-fetch from the provider's API** | For important events, ask the provider directly whether the payment really succeeded |

### Missed events

If your endpoint is down longer than the sender's retry window, events can be lost silently. For important flows, run a **reconciliation**, for example nightly, that compares your records with the provider's API and fills any gaps.

## A worked example

A handicrafts store in Jaipur uses a payment gateway. It wants an invoice emailed and a row added to its accounts sheet as soon as a payment succeeds.

They build this in n8n:

| # | Step | Why |
| --- | --- | --- |
| 1 | Webhook node with a production URL, added in the gateway's dashboard for "payment captured" events | Receive events instantly |
| 2 | Verify the signature using the webhook secret copied from the gateway | Reject fake requests |
| 3 | Reply `200 OK` immediately | Stop the gateway timing out and retrying |
| 4 | Check the payment id against the sheet; if found, stop | Duplicates do nothing |
| 5 | Create the invoice PDF, email it, add the row with the payment id | The real work |
| 6 | Nightly: compare the day's captured payments from the gateway's API with the sheet | Catch anything missed |

**The festival sale.** During the Diwali sale, the n8n server restarts and is down for two minutes. The gateway retries the missed events once the server is back. Two of those events had actually been processed just before the restart, but their replies never reached the gateway, so they arrive twice. The duplicate check stops both.

| Situation | What happened | Which step handled it |
| --- | --- | --- |
| Fake request from an unknown sender | Signature did not match | Step 2: rejected |
| Event delivered twice after the restart | Payment id already in the sheet | Step 4: stopped |
| Events sent during the 2-minute outage | Retried by the gateway later | Steps 1 to 5, a few minutes late |
| A week of nightly reconciliation | No missing payments found | Step 6 |

Without step 4, two customers would have received two invoices each, and the accounts sheet would have shown ₹8,400 of sales that never happened.

## Common mistakes

- **Using the test URL in production.** Events stop arriving once you close the editor.
- **Trusting unsigned requests.** Verify signatures before acting.
- **Slow responses.** Senders retry, creating duplicates. Reply first, work after.
- **No duplicate check.** Retries create double invoices, emails or orders.
- **No reconciliation.** Long outages lose events silently.
- **Logging secrets.** Do not write the webhook secret or full payment details into logs others can read.

## Practise

Read Zapier's explanation of webhooks, linked below, and n8n's Webhook node docs.

1. **Receive.** Create a webhook workflow in n8n and trigger it with a test request, from a form tool or a command such as curl.
2. **Duplicates.** Send the same event twice and add a duplicate check so the second does nothing.
3. **Security.** Add a shared-secret check and show a request with the wrong secret being rejected.

**You are done when you can** explain why webhooks retry, show your duplicate check working and say how you would catch events missed during an outage.
