## What it is

**Clean code** is code that the next person can read, understand and change without fear. That next person is usually you, three months later, with no memory of why you wrote it that way.

Clean code is not about clever tricks or the fewest lines. It is about a reader. Can they tell what a function does from its name? Can they follow it top to bottom without jumping around? Can they change one rule in one place?

**Refactoring** is changing how code is written without changing what it does. You rename, split, simplify and remove duplication, one small step at a time, with tests confirming the behaviour stays the same. It is how messy code becomes clean code without a risky rewrite.

## How it works

The habits that make the biggest difference:

| Habit | Before | After |
| --- | --- | --- |
| Clear names | `def calc(d, f):` | `def invoice_total(items, include_gst):` |
| Named constants | `amount * 1.18` | `amount * (1 + GST_RATE)` |
| Small functions | One 120-line `process()` | `read_orders()`, `validate()`, `total()`, `write_report()` |
| Early returns | Four nested `if` blocks | Handle bad cases first, then the main path |
| One source of truth | The same rule copied in three files | One function everyone calls |
| Honest comments | `# loop over items` | `# Refunds older than 30 days need manager approval (policy 4.2)` |

Good comments explain **why**, not what. The code already says what it does; a comment should say what the code cannot, such as a business rule or the reason for an odd choice.

Refactoring follows a safe loop:

```flow
dir: LR
Tests pass -> One small change | rename, extract a function, add a constant
One small change -> Run the tests
Run the tests -[pass]-> Commit
Commit -> One small change
Run the tests -[fail]-> Undo and try a smaller step
Undo and try a smaller step -> One small change
```

Small steps matter. A rename, a run of the tests, a commit. An extracted function, a run, a commit. If a test fails, you know exactly which step broke it and can undo just that one. A big-bang rewrite gives you none of that.

**Extract function** is the most useful refactor. Take a block inside a long function that does one job, move it into its own function with a name that says that job, and call it. The long function starts reading like a list of steps.

**Code smells** are signs that code will be hard to change: functions too long to fit on a screen, the same logic copied in several places, a change that needs edits in five files, deep nesting, and variables named `data`, `temp` or `x`. They are not bugs; they are where bugs breed.

**Clean code in AI projects.** The same habits apply to prompts and pipelines. Keep prompts in their own files with clear names rather than long strings buried in functions. Give each step of a pipeline (load, chunk, embed, retrieve, generate) its own function, so you can test and swap one without touching the rest. Name settings such as chunk size, top-k and temperature as constants in one config file, so an experiment changes one line and the diff shows exactly what was tried.

**When not to refactor.** Refactoring has a cost: time, review effort and some risk. Skip it for code that works and that nobody plans to change, for throwaway scripts, and in the middle of an outage, where the smallest fix is the right one. Tidy up later, in its own pull request, once the urgent change has shipped and has tests around it.

## A worked example

Kavya inherits a 140-line function, `process_file()`, at an edtech company in Kochi. It reads a CSV of course purchases, filters refunds, adds GST, applies coupons and writes a summary. A new rule is coming: GST must be skipped for one government scheme. Changing the function feels risky.

**First, tests.** She writes six tests around today's behaviour, using small sample CSVs: normal purchases, a refund, a coupon, a zero amount, a missing field and a duplicate row. All pass on the old code. Now she has a safety net.

**Then small steps.** She renames `d` to `purchases` and `t` to `total`. Tests pass; commit. She replaces three copies of `* 1.18` with a `GST_RATE` constant and a `with_gst()` function. Tests pass; commit. She extracts `read_purchases()`, `apply_coupon()` and `write_summary()`. Each step runs the tests and gets its own commit.

The main function is now eleven lines that read like the business process:

```python
def process_file(path):
    purchases = read_purchases(path)
    paid = [p for p in purchases if not p.is_refund]
    totals = [with_gst(apply_coupon(p)) for p in paid]
    write_summary(totals)
```

**Then the new rule.** Skipping GST for the scheme is now one change, in one function, `with_gst()`, plus one new test. The pull request is short and easy to review, and her reviewer approves it the same day.

## Common mistakes

- **Refactoring without tests.** You cannot tell whether you changed behaviour. Add tests for what it does today first.
- **Refactoring and changing behaviour in one step.** Do the tidy-up and the new feature in separate commits, so each is easy to review.
- **Big rewrites.** They take weeks and break things nobody remembered. Small, safe steps win.
- **Clever one-liners.** Shorter is not cleaner if the reader has to decode it.
- **Comments that repeat the code.** They go stale. Explain the why, or rename until the comment is not needed.
- **Polishing code nobody will touch.** Refactor what you are about to change, not everything.
