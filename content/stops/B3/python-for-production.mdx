## What it is

Script Python and production Python look alike, but behave very differently under pressure. A script runs once, on your laptop, on data you have seen. Production code runs thousands of times a day, on data you have never seen, and other people change it after you leave.

Four habits close most of the gap:

| Habit | What it does | Where it matters most |
| --- | --- | --- |
| **Type hints** | Say what each function takes and returns, so editors and checkers catch mistakes before the code runs | Every function you write |
| **Dataclasses** | Give plain records a clear shape without boilerplate | Your own internal data |
| **Pydantic models** | Check data from outside and refuse it with a clear error if it is wrong | API requests, files, LLM replies |
| **async and await** | Let one process wait on many slow network calls at once | Services that call model APIs |

```text
   outside world                 your system
 +----------------+   validate   +-------------------------------------+
 | API requests   | --(Pydantic)--> typed, checked objects             |
 | CSV rows       | --(Pydantic)--> dataclasses inside                 |
 | LLM JSON reply | --(Pydantic)--> type hints on every function       |
 +----------------+              +-------------------------------------+
     messy, untrusted                  clean, predictable
```

This lesson follows a lending startup in Bengaluru that extracts fields from loan enquiry emails with an LLM, and then needs to process 200 of them quickly. By the end you will validate outside data properly and know when async helps.

## How it works

### Type hints

```python
def emi(principal: float, annual_rate: float, months: int) -> float:
    ...
```

Python ignores hints at run time; passing a string will not raise an error by itself. Their value comes from tools: your editor warns when you pass a string where a number belongs, and type checkers such as **mypy** or **pyright** check a whole project in CI. Hints are also documentation: `def score(ticket: Ticket) -> float` tells the next engineer more than a comment would.

### Dataclasses

```python
from dataclasses import dataclass

@dataclass
class LineItem:
    sku: str
    qty: int
    price: float
```

`@dataclass` writes the constructor, equality and printing for a class that mainly holds data. Use them for your own internal records, where you control what goes in.

### Pydantic: validation at the boundary

A **Pydantic** model looks like a dataclass but **validates**. Give it a dictionary or JSON and it:

- converts what it safely can, such as "42" to 42;
- rejects what it cannot, such as "five lakh" for a number;
- tells you exactly which field failed and why.

| Input for `amount_inr: int` | Result |
| --- | --- |
| `500000` | Accepted |
| `"500000"` | Converted to 500000 |
| `"5,00,000"` | Rejected (commas), unless you add a cleaning step |
| `"five lakh"` | Rejected with a clear error |
| missing | Rejected, unless the field has a default |

Use Pydantic at every boundary where data enters: request bodies, config files, CSV rows, and **especially LLM output**, which is often almost right. Validating at the edge means bad data never reaches the rest of your code, where it would cause confusing errors three functions later.

### async and await

A normal function **blocks**: while it waits two seconds for a model reply, nothing else happens in that process. An `async def` function can `await` the reply and let the **event loop** run other work in the meantime.

```text
  Sequential (blocking):  [call 1 ....2s....][call 2 ....2s....][call 3 ....2s....]  = 6 s

  Concurrent (async):     [call 1 ....2s....]
                          [call 2 ....2s....]
                          [call 3 ....2s....]                                        = about 2 s
```

This only helps with **waiting**, on the network or the disk, not with heavy computation such as resizing images. And every library in the chain must be async-aware: `httpx` instead of `requests`, `asyncio.sleep` instead of `time.sleep`.

## A worked example

A lending startup in Bengaluru wants fields extracted from loan enquiry emails with an LLM. The model returns JSON. It is usually correct, but sometimes a field is missing, or the amount says "five lakh" instead of a number.

**Validating the reply:**

```python
import logging
from pydantic import BaseModel, Field, ValidationError

log = logging.getLogger(__name__)

class Enquiry(BaseModel):
    name: str
    city: str
    amount_inr: int = Field(gt=0, le=10_000_000)
    purpose: str | None = None

def parse(reply: str) -> Enquiry | None:
    try:
        return Enquiry.model_validate_json(reply)
    except ValidationError as e:
        log.warning("bad model reply: %s", e.errors())
        return None
```

`parse('{"name": "Divya", "city": "Pune", "amount_inr": "500000"}')` returns a valid `Enquiry`, with the amount converted to an integer. A reply with `"amount_inr": "five lakh"` fails with an error naming the field, so the code can retry with a firmer prompt instead of storing junk.

**Processing 200 emails.** Calling the model one at a time takes 200 times the latency: about 7 minutes at 2 seconds each. With `httpx.AsyncClient` and `asyncio.gather`, the emails are sent concurrently, and a **semaphore** limits how many are in flight at once, so the startup stays under the provider's rate limit:

```python
import asyncio
import httpx

sem = asyncio.Semaphore(10)

async def extract(client, email):
    async with sem:
        reply = await call_model(client, email)   # your async model call
        return parse(reply)

async def main(emails):
    async with httpx.AsyncClient(timeout=30) as client:
        return await asyncio.gather(*(extract(client, e) for e in emails))

results = asyncio.run(main(emails))
```

| Approach | Time for 200 emails | Rate-limit risk |
| --- | --- | --- |
| One at a time | about 7 minutes | None |
| All 200 at once | seconds, then many 429 errors | High |
| Async with a limit of 10 | about 40 seconds | Low |

## Common mistakes

- **Treating hints as checks.** `amount: int` does not stop a string at run time. Validate outside data with Pydantic; use hints for your own code.
- **Validating too late.** Bad data that slips past the boundary shows up three functions later as a confusing error. Validate on entry.
- **Blocking inside async code.** Calling `requests.get` or `time.sleep` inside an `async def` freezes the whole event loop.
- **Unlimited concurrency.** Firing 5,000 requests at once trips rate limits and can get you blocked. Cap it.
- **Dictionaries everywhere.** Passing raw dicts between functions hides typos like `"ammount"`. Give your data a model.
- **Using async for CPU-heavy work.** It will not make image processing or model training faster.
