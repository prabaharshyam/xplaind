## What it is

Every developer uses two tools every day:

- The **terminal**: a text window for running commands. You move between folders, run programs, install packages and use tools such as Git from it.
- **Git**: a version control system that records snapshots of your project, called **commits**, so you can see what changed, undo mistakes and share code. **GitHub** hosts Git repositories online so others can see them and work with you.

```text
   Your folder                Git (on your computer)           GitHub (online)
 +---------------+  git add  +-------------------------+  git push  +---------------+
 | hello.py      | --------> | commit 1 "Add hello"    | ---------> | your public   |
 | expenses.py   |  git      | commit 2 "Add expenses" |            | repository,   |
 | README.md     |  commit   | commit 3 "Add README"   |            | with README   |
 +---------------+           +-------------------------+            +---------------+
      edit files                 history you can undo                 shareable link
```

Employers look at GitHub profiles. A repository with clear commits and a good README is the simplest proof that you can write and organise code, and interviewers often open it during the interview.

## How it works

### Terminal basics

| Command | What it does |
| --- | --- |
| `pwd` | Shows the folder you are in (Mac, Linux; on Windows, `cd` alone) |
| `ls` | Lists files (`dir` on Windows Command Prompt) |
| `cd projects` | Goes into a folder |
| `cd ..` | Goes up one folder |
| `mkdir python-practice` | Makes a new folder |
| `python hello.py` | Runs a program |

The **up arrow** repeats earlier commands, and **Tab** completes file and folder names, which saves a lot of typing and typos.

### Set up Git once

Install Git, then tell it who you are:

```bash
git config --global user.name "Priya Raman"
git config --global user.email "priya@example.com"
```

### Start a repository and make commits

```bash
cd python-practice
git init                         # start tracking this folder
git status                       # what has changed?
git add hello.py                 # choose changes for the next commit
git commit -m "Add hello script that prints name and date"
git log --oneline                # see the history
```

`git add` puts changes in the **staging area**: a list of what will go into the next snapshot. `git commit` saves that snapshot with a message. This two-step design lets you commit related changes together and leave others for later.

### Good commit messages

| Weak | Strong |
| --- | --- |
| "update" | "Add expense totals by category" |
| "fixed stuff" | "Handle missing amounts in expense CSV" |
| "final" | "Add README with usage examples" |

Write in the present tense, say what changed, and keep the first line short. Your future self will read these when something breaks.

### Undo with Git

| Situation | Command |
| --- | --- |
| See what changed since the last commit | `git diff` |
| Throw away changes to one file | `git restore expenses.py` |
| Unstage a file you added by mistake | `git restore --staged expenses.py` |
| See an old version | `git log --oneline`, then `git show <commit>` |

### Push to GitHub

Create an empty repository on GitHub, then connect and push:

```bash
git remote add origin https://github.com/priya-raman/python-practice.git
git branch -M main
git push -u origin main
```

GitHub will ask you to sign in; follow its prompts or set up an SSH key. After the first push, `git push` alone sends new commits.

### README and .gitignore

A `README.md` explains what the project is and how to run it. GitHub shows it on the repository's front page.

A `.gitignore` file lists things Git should not track:

```text
.venv/
__pycache__/
.env
```

The `.env` line matters most: `.env` files often hold API keys. Create `.gitignore` **before** your first `git add`, because once a secret is committed, it stays in the history even if you delete the file later. If a key is ever pushed, revoke it at once and create a new one.

## A worked example

Ravi, learning Python in Nagpur, has a folder of exercise scripts: an expense tracker, a marks calculator and a weather fetcher that uses an API key. He turns it into a GitHub portfolio.

| Step | What he does | Why |
| --- | --- | --- |
| 1 | `git init` in the folder | Start tracking history |
| 2 | Creates `.gitignore` with `.venv/` and `.env` | Keep the environment and his API key out of Git |
| 3 | Commit: "Add expense tracker with category totals" | One clear, meaningful step |
| 4 | Commit: "Handle missing amounts in expense CSV" | A second, separate improvement |
| 5 | Commit: "Add README with usage examples" | Explain the project to visitors |
| 6 | `git push` to a new public repository | A link to share |

His README has a one-line summary, how to run each script, and a sample of the output.

**A mistake, undone.** A week later he breaks the expense tracker while adding a feature. `git diff` shows exactly which lines he changed. `git restore expenses.py` brings back the last committed version in a second, and he tries the feature again more carefully.

**The payoff.** In an interview the next month, the panel opens his repository and asks him about the commit "Handle missing amounts in expense CSV". He explains the bug, how he found it and how he fixed it. It is the best part of the interview.

## Common mistakes

- **One giant commit at the end.** Commit small, meaningful steps as you go.
- **Messages like "update".** Say what changed.
- **Committing secrets.** Keep keys in `.env`, list it in `.gitignore` before your first commit, and revoke any key that is ever pushed.
- **Committing virtual environments and caches.** Ignore them.
- **No README.** Visitors cannot tell what the project does or how to run it.
- **Working without `git status`.** Check it often; it tells you exactly where you are.
