## What it is

Two tools sit under almost all software work:

- The **terminal** (also called the shell or the command line) is a window where you type commands instead of clicking. You move between folders, run programs, install packages and use tools such as Git from it.
- **Git** is a version control system. It records snapshots of your project, called **commits**, so you can see what changed, undo mistakes and share code. **GitHub** is a website that stores copies of Git repositories online so others can see them and work with you. Git works without GitHub; GitHub is just one place to send your history.

Git is close to universal: in Stack Overflow's 2022 developer survey, 93% of developers said they use it. Course material, take-home tasks and your first team's code will almost always arrive as a Git repository.

The one idea that makes Git easy: your changes live in one of four places, and each command moves them from one place to the next.

```flow
title: Where your changes live
dir: LR
Working folder | the files you edit -[git add]-> Staging area | what the next commit will hold
Staging area -[git commit]-> Local repository | your history of commits
Local repository -[git push]-> GitHub | the shared copy online
GitHub -[git clone, git pull]-> Working folder
```

Most confusion with Git comes from not knowing which place a change is in. `git status` tells you, so run it before and after every other Git command.

This lesson follows Ravi, who is learning Python in Nagpur, as he turns a folder of exercise scripts into a public repository. Its check is a small project of your own, marked with the rubric at the end.

## How it works

### Terminal basics

**Pick your terminal first.** On a Mac, open the Terminal app. On Linux, any terminal works. On Windows, install Git for Windows, which comes with **Git Bash**, and use Git Bash (or WSL, Linux inside Windows) for this course, so every command works as written. PowerShell also accepts `pwd`, `ls` and `cd`; the old Command Prompt uses different commands, such as `dir` instead of `ls`.

| Command | What it does |
| --- | --- |
| `pwd` | Prints the folder you are in |
| `ls` | Lists the files in this folder |
| `ls -a` | Also lists hidden files, whose names start with a dot, such as `.gitignore` and `.env` |
| `cd python-practice` | Goes into a folder |
| `cd ..` | Goes up one folder |
| `cd ~` | Goes to your home folder |
| `mkdir python-practice` | Makes a new folder |
| `python expenses.py` | Runs a program (`python3` on some Mac and Linux machines) |

**Paths.** An absolute path starts from the top of the disk, such as `/home/ravi/python-practice` (in Git Bash, the C drive is `/c`, so a Windows home folder looks like `/c/Users/Ravi`). A relative path starts from where you are now: `python-practice` only works if that folder is inside the current one. When you see "No such file or directory", you are almost always in the wrong folder: run `pwd` and `ls` before anything else. Avoid spaces in folder names; if one has them, wrap it in quotes, as in `cd "My Projects"`.

**Environment variables** are named values the terminal passes to every program it starts. `echo $HOME` prints one. `export CITY=Nagpur` sets one, but only for that terminal window; close it and the value is gone. Projects therefore keep API keys in a `.env` file that the program reads, which is exactly the file that must never reach Git.

Three keys save hours: the **up arrow** brings back earlier commands, **Tab** completes file and folder names (and avoids typos), and **Ctrl+C** stops a program that is running or stuck.

### Set up Git once

Check that Git is installed, then tell it who you are:

```bash
git --version
git config --global user.name "Ravi Deshmukh"
git config --global user.email "12345678+ravi-d@users.noreply.github.com"
git config --global init.defaultBranch main
```

Your name and email are stamped into every commit, and anyone can read them once you push. If you do not want your personal email public, GitHub gives you a private "noreply" address: in GitHub's email settings, tick "Keep my email address private" and copy the address it shows. The one above is only an example of its shape.

The last line names the first branch `main`, the name GitHub uses. Without it, some Git versions call the first branch `master` and print a long hint about it.

### The everyday loop: status, add, commit

```bash
cd python-practice
git init                  # once per project: start tracking this folder
git status                # which files are new, changed or staged?
git add expenses.py       # stage this file for the next commit
git commit -m "Add expense tracker with category totals"
git log --oneline         # one line per commit, newest first
```

`git add` puts changes in the **staging area**, and `git commit` saves everything staged as one snapshot. The two steps exist so that a commit holds one idea. If you fixed a bug and also started a new feature, stage only the bug fix, commit it, and keep the half-done feature for later.

`git add .` stages everything in the folder that Git is not told to ignore. It is fast, and it is also how secrets and junk get committed, so run `git status` first and read the list. `git diff` shows changes you have not staged yet; `git diff --staged` shows what is about to be committed.

### Commit messages that help

| Weak | Strong |
| --- | --- |
| "update" | "Add expense totals by category" |
| "fixed stuff" | "Handle missing amounts in expense CSV" |
| "final" | "Add README with usage examples" |

The rules that matter:

- **Start with a verb, as an instruction:** "Add", "Fix", "Handle", "Remove". A useful test: the message should complete the sentence "If applied, this commit will...".
- **One change per commit.** If you need "and" to describe it, it is probably two commits.
- **Keep the first line short.** A common convention is about 50 characters. If you need to explain why, leave a blank line and write more below it.
- **Commit when the code runs.** Then every commit in your history is a safe point to go back to.

### Keep secrets and clutter out: .gitignore

A file named `.gitignore`, in the top folder of the project, lists what Git should never track:

```text
.venv/
__pycache__/
.env
```

`.venv/` is your virtual environment (large, and rebuilt from `requirements.txt`), `__pycache__/` is Python's cache, and `.env` holds keys. The `.env` line matters most.

The rule beginners miss: **`.gitignore` only affects files Git is not tracking yet.** If `.env` is already in a commit, adding it to `.gitignore` later changes nothing, and `git status` keeps showing it. Stop tracking it like this:

```bash
git rm --cached .env      # stop tracking; the file stays on your disk
git commit -m "Stop tracking .env"
```

That removes it from future commits only. The old commit still holds the key, and anyone who can see the repository can read it. So treat the key as leaked: revoke it on the provider's website and make a new one. Deleting the file is not enough.

GitHub adds one safety net. On public repositories it turns on **push protection** for personal accounts by default, which blocks a push containing a secret in a format it recognises, such as many cloud and AI provider keys. It cannot recognise every secret, for example a password you made up, so the real defence is creating `.gitignore` before your first `git add`.

### Undo before it becomes a commit

| Situation | Command |
| --- | --- |
| See what changed and is not staged | `git diff` |
| See what is staged for the next commit | `git diff --staged` |
| Throw away your edits to one file | `git restore expenses.py` |
| Unstage a file but keep your edits | `git restore --staged expenses.py` |
| Look at an old commit | `git log --oneline`, then `git show a7d7b78` |

Be careful with `git restore expenses.py`: it brings back the last committed version, and the edits you throw away are gone for good, because Git never saved them. Undoing a commit, including one you have already pushed, is the subject of the lesson on undoing things in Git.

### Push to GitHub, with sign-in that works

On GitHub, click **New repository**, name it `python-practice`, and leave the README, .gitignore and licence options off, so the repository starts empty. Then connect your folder to it and push:

```bash
git remote add origin https://github.com/ravi-d/python-practice.git
git push -u origin main
```

`origin` is the usual nickname for your GitHub copy. `-u` links your `main` to it, so from then on plain `git push` and `git pull` work.

**Signing in is where most beginners get stuck.** Since 13 August 2021, GitHub has not accepted your account password for Git commands. If the terminal asks for a username and password and you type your GitHub password, the push fails. Pick one of these instead:

| Your setup | What to do |
| --- | --- |
| Windows with Git for Windows | Git Credential Manager comes with it. On the first push a sign-in window opens; choose the browser, sign in to GitHub, and it remembers you. |
| Mac or Linux | Install the GitHub CLI and run `gh auth login`. Choose GitHub.com and HTTPS, say yes to authenticating Git with your GitHub credentials, and finish in the browser. |
| Anything else | Create a fine-grained personal access token (GitHub Settings, then Developer settings) with read and write access to Contents for this repository, and paste it where the terminal asks for a password. Treat it like a password. |

SSH keys are another option; the lesson on Linux, the shell and SSH covers them.

**One more trap.** If you did tick "Add a README" on GitHub, your first push is refused, because GitHub has a commit your computer does not:

```text
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/ravi-d/python-practice.git'
```

For a new repository the simplest fix is to delete it on GitHub (its Settings page, at the bottom), create it again empty and push. Running `git pull` first does not help: Git stops with "refusing to merge unrelated histories".

### Working with others: a first look

Team work and take-home tasks start the other way round: the repository already exists on GitHub.

```bash
git clone https://github.com/example-team/expense-app.git
cd expense-app
git pull                          # bring in teammates' new commits
git switch -c add-monthly-report  # a new branch for your change
# edit files, then git add and git commit
git push -u origin add-monthly-report
```

A **branch** is a separate line of commits, so your change does not touch `main` until it is ready. After pushing the branch, you open a **pull request** on GitHub: a page that shows your changes so a teammate can review them before they are merged into `main`.

If you and a teammate change the same lines, Git cannot choose between you. It stops with a **merge conflict** and marks the file:

```text
<<<<<<< HEAD
print(sorted(totals.items()))
=======
print("Totals:", totals)
>>>>>>> 3c1dea94b5893015fb3b508cd578f48b684bd511
```

The part above `=======` is your version; the part below is the incoming one. Edit the file to the version you want, delete the three marker lines, then `git add` the file and run `git commit --no-edit` to keep Git's message. If `git pull` stops with "Need to specify how to reconcile divergent branches", you both made commits; `git pull --no-rebase --no-edit` merges them. The lessons on branches and on Git with a team go deeper.

## A worked example

Ravi has a folder with an expense tracker, a marks calculator and a weather fetcher that reads an API key from `.env`. Here is his real session, with output shortened. Your commit hashes (the short codes such as `81d3fe3`) will be different.

**1. Start tracking, and look before adding anything.**

```text
$ cd ~/python-practice
$ git init
Initialized empty Git repository in /home/ravi/python-practice/.git/
$ git status
On branch main

No commits yet

Untracked files:
	.env
	.venv/
	__pycache__/
	expenses.py
	marks.py
	weather.py
```

The `.env` line is the danger: one `git add .` now would commit his key.

**2. Create `.gitignore` and check again.**

```text
$ printf '.venv/\n__pycache__/\n.env\n' > .gitignore
$ git status --short
?? .gitignore
?? expenses.py
?? marks.py
?? weather.py
```

`??` means untracked. `.env`, `.venv/` and `__pycache__/` have disappeared from the list, which is the proof that the ignore file works.

**3. First commit: one script, plus the ignore file.**

```text
$ git add .gitignore expenses.py
$ git commit -m "Add expense tracker with category totals"
[main (root-commit) 81d3fe3] Add expense tracker with category totals
 2 files changed, 9 insertions(+)
```

**4. A bug fix as its own commit.** A blank amount in his CSV crashed the tracker. He fixes the line, then checks exactly what he changed:

```text
$ git diff
-        totals[row["category"]] = totals.get(row["category"], 0) + float(row["amount"])
+        totals[row["category"]] = totals.get(row["category"], 0) + float(row["amount"] or 0)
$ git add expenses.py
$ git commit -m "Handle missing amounts in expense CSV"
```

**5. The other scripts and a README, one commit each.** His README:

```markdown
# Python practice
Small scripts from my first month of learning Python.

- expenses.py: reads expenses.csv and prints total spending per category
- marks.py: turns a list of marks into grades
- weather.py: prints today's weather for a city; needs WEATHER_API_KEY in a .env file

Run any script with: python expenses.py
```

```text
$ git log --oneline
e2c538a Add README with usage examples
cf4559b Add weather fetcher that reads its key from .env
812980e Add marks calculator with grade bands
a7d7b78 Handle missing amounts in expense CSV
81d3fe3 Add expense tracker with category totals
```

**6. Push.** He creates an empty repository on GitHub, runs `gh auth login` once on his Ubuntu laptop, then:

```text
$ git remote add origin https://github.com/ravi-d/python-practice.git
$ git push -u origin main
To https://github.com/ravi-d/python-practice.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

**7. A mistake, undone.** A week later he adds a line that crashes the tracker. Before he commits anything:

```text
$ git status --short
 M expenses.py
$ git diff
+print(totals["food"])
$ git restore expenses.py
$ git status --short
```

`M` means modified. After `git restore`, `git status` prints nothing: the file matches his last commit again.

**8. The last check.** `git log --all --oneline -- .env` lists every commit that ever touched `.env`. For Ravi it prints nothing, so his key has never been in his history.

Anyone who opens his repository, a reviewer or an interviewer, now sees three things in a minute: a README that says how to run each script, a history of small, clearly named steps, and no `.env`, `.venv/` or cache files.

## Common mistakes

- **Running Git in the wrong folder.** "fatal: not a git repository" means you are outside the project; `git init` run in your home folder makes `git status` list every file you own. Run `pwd` first.
- **Typing your GitHub password at the push prompt.** It is rejected. Use Git Credential Manager, `gh auth login` or a personal access token.
- **Adding `.gitignore` after `.env` was committed.** It has no effect on tracked files. Use `git rm --cached .env`, commit, and replace the key.
- **`git add .` without reading `git status`.** This is how keys, `.venv/` and large data files get committed.
- **Ticking "Add a README" on a new GitHub repository** and then pushing an existing folder. The push is refused. Create new repositories empty.
- **One giant commit, or messages like "update".** Commit each finished step, and say what it changes.
- **`git restore` on edits you wanted to keep.** Those edits cannot be recovered. Check `git diff` first.
