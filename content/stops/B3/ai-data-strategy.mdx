## What it is

An AI product is only as good as its data: the documents it reads when answering, the examples it is judged against, and the feedback that makes it better. A **data strategy** is the plan for all of that, written before the build starts, not discovered after launch.

It answers six questions:

| Question | Example answer |
| --- | --- |
| **What data** does the product need at run time and for improvement? | Policy documents at run time; real customer questions and expert answers for evaluation |
| **Where** does it come from, and **who owns** it? | The policy team owns the documents; support owns the question log |
| **Are we allowed** to use it for this purpose? | Customers were told chats help improve answers, and can opt out |
| **How good** is it, and how is it kept current? | Documents reviewed each quarter; duplicates removed |
| **How do we evaluate** the product with it? | A golden set of 150 questions run before every release |
| **How does use create better data?** | Thumbs down plus reason, reviewed weekly; fixes added to the golden set |

```text
          Three kinds of data in an AI product
 +-------------------+  +-------------------+  +-------------------+
 |  RUN-TIME         |  |  EVALUATION       |  |  FEEDBACK         |
 |  what it reads    |  |  what it's judged |  |  what users tell  |
 |  when answering   |  |  against          |  |  you after        |
 |  documents,       |  |  golden set of    |  |  thumbs, edits,   |
 |  records, history |  |  real questions   |  |  overrides        |
 +-------------------+  +-------------------+  +-------------------+
            \                    |                     /
             +---------> a better product <-----------+
```

This lesson follows Lakshmi, a product manager at an agri-tech startup in Chennai, as she writes the data plan for a voice assistant that answers farmers' crop questions. By the end you will be able to write a one-page data plan that a privacy officer and an engineer would both accept.

## How it works

### Run-time data

For a product that answers from documents, decide which document collections it searches, how they are kept fresh, and who can see what. For personalisation, decide which user data is used, with consent. Missing or stale run-time data often causes more wrong answers than the model itself.

### Evaluation data

A **golden set** is a collection of realistic inputs with expected outputs or quality judgements, built with domain experts. Start with 50 to 100 cases from real users, not invented ones. Grow it with every important failure you find. The golden set is the product's quality contract: without it, "is it better now?" is just opinion.

### Feedback data

Design the product to capture feedback from day one:

- thumbs up and down, with a short reason;
- edits users make to drafts, which show exactly what was wrong;
- overrides by human reviewers;
- escalations to a person.

Feedback is only useful if someone reviews it on a schedule and turns it into fixes and new golden-set cases.

### Labelling

Some improvements need labelled data: correct categories, correct extractions, correct answers. Decide who labels (domain experts, trained staff or a vendor), with what written guidelines, and how you check label quality, for example by having two people label a sample and comparing.

### Permission and privacy

Under India's **DPDP Act** and similar laws, personal data may be used only for purposes people were told about and agreed to, or on another lawful ground. Using customer chats to improve a model may need explicit notice and consent. Contracts with business clients may forbid using their data for anything but their own service. Decide all of this **before** collecting.

### Quality and coverage

| Check | Question | Risk if ignored |
| --- | --- | --- |
| Coverage | Do we have all user types, languages and regions? | Failures and bias for missing groups |
| Freshness | Is the data current? | Outdated answers |
| Duplicates | Is the same thing counted many times? | Skewed results |
| Errors | Are labels and records correct? | The product learns mistakes |

Bias in data becomes bias in the product.

### Ownership and governance

Name an owner for each dataset, define how long it is kept and when it is deleted, and record where it came from. Unowned data quietly goes stale.

### The flywheel

```text
   more usage  --->  more feedback  --->  better data
       ^                                       |
       |                                       v
   better product  <---  fixes, new golden cases
```

Good products turn usage into data that improves the product. The flywheel only turns if feedback is captured, permitted and actually used.

## A worked example

A Chennai agri-tech startup is building a voice assistant that answers farmers' crop questions in Tamil and English. Lakshmi, the product manager, writes the data plan.

| Data | Source | Owner | Permission | Kept for |
| --- | --- | --- | --- | --- |
| Run-time: crop advisories | Agricultural university advisories and state agriculture department guidance, updated each season | Content lead | Public sources | Until replaced |
| Run-time: weather and prices | Weather and market price feeds | Engineering | Licensed feeds | Rolling 30 days |
| Evaluation: golden set | 200 real farmer questions collected with field staff, across five crops and three districts, answers checked by two agronomists | Lakshmi | Farmers agreed during collection | Ongoing |
| Feedback | Voice prompt "Did this help?" after each answer, a callback option, and weekly corrections from field staff | Support lead | Notice in Tamil on first use, with opt-out | Recordings 90 days, unless the farmer agrees otherwise |

**A coverage gap.** When she reviews the first 200 questions, almost none come from women farmers, who do much of the field work in the target districts. Field staff run two sessions with women's self-help groups and add 60 questions, many about crops and pests the first sample missed.

**Six months later:**

| Measure | At launch | Six months |
| --- | --- | --- |
| Golden set size | 200 questions | 650 questions |
| Accuracy reporting | Overall only | By crop and by district, monthly |
| Most common failure | Pest names in local dialect | Fixed with a glossary built from feedback |

The glossary came straight from the flywheel: farmers pressed "did not help", field staff listened to the recordings, and the team added the local names.

## Common mistakes

- **Assuming you can use whatever data you have.** Check consent, law and contracts first.
- **No evaluation set.** Without one, quality becomes opinion and every change is a gamble.
- **Feedback buttons nobody reads.** Build the weekly review routine, not just the button.
- **Ignoring coverage.** Missing groups and languages become failures and bias.
- **No owner.** Unowned data goes stale and nobody notices.
- **Inventing test questions.** Real user questions are messier and more useful than ones the team imagines.

## Practise

Read the PAIR guidebook chapter on data collection and evaluation, linked below, and Hamel Husain's field guide to improving AI products.

1. **List the data.** For an AI product idea, list run-time, evaluation and feedback data, with the source and owner of each.
2. **Permission.** For each, write the permission basis and how long you will keep it.
3. **Golden set.** Draft 30 evaluation cases with someone who knows the domain, and note one coverage gap.

**You are done when you can** present a one-page data plan that a privacy officer and an engineer would both accept.
