## What it is

A **data strategy** for an AI product answers:

- **What data** does the product need at run time (documents, records, user history) and for improvement (examples, labels, feedback)?
- **Where** does it come from, and **who owns** it?
- **Are we allowed** to use it for this purpose (consent, contracts, law)?
- **How good** is it, and how do we keep it current?
- **How do we evaluate** the product with it?
- **How does use create better data** over time?

## How it works

**Run-time data.** For retrieval: which document collections, how they are kept fresh, who can see what. For personalisation: which user data, with consent. Missing or stale run-time data is the top cause of wrong answers.

**Evaluation data.** A golden set of realistic inputs with expected outputs or quality judgements, built with domain experts. Start with 50 to 100 cases; grow it with every important failure. This is the product's quality contract.

**Feedback data.** Thumbs up and down with reasons, edits users make to drafts, overrides by reviewers, escalations. Design the product to capture these from day one; they are your improvement engine.

**Labelling.** Some improvements need labelled data (correct categories, correct extractions). Decide who labels (domain experts, trained staff, vendors), with what guidelines, and how you check label quality.

**Permission and privacy.** Under India's DPDP Act and similar laws, personal data may be used only for purposes people were told about and agreed to (or other lawful grounds). Using customer chats to improve a model may need explicit notice and consent. Contracts with business clients may forbid using their data for anything but their service. Decide this before collecting.

**Quality.** Check coverage (all user types, languages, regions), freshness, duplicates and errors. Bias in data becomes bias in the product.

**Ownership and governance.** Name an owner for each dataset, define retention and deletion, and record where data came from.

**The flywheel.** Good products turn usage into data that improves the product, which brings more usage. It only works if feedback is captured, permitted and actually used.

## A worked example

A Chennai agri-tech startup builds an assistant that answers farmers' crop questions in Tamil and English by voice.

Data plan by the PM, Lakshmi:

- **Run-time**: agricultural university advisories and state agriculture department guidance, updated each season; local weather and market price feeds.
- **Evaluation**: 200 real farmer questions collected with field staff, in Tamil and English, across five crops and three districts, with answers checked by two agronomists.
- **Feedback**: after each answer, a voice prompt "Did this help?" plus a callback option; field staff log corrections weekly.
- **Permission**: farmers hear a short notice in Tamil on first use explaining that recordings help improve answers, with the choice to opt out; recordings are deleted after 90 days unless the farmer agrees otherwise.
- **Coverage gap found**: almost no questions from women farmers in the first sample; field staff run two sessions with women's self-help groups to add them.

Six months later, the evaluation set has 650 questions, monthly accuracy is reported by crop and district, and the most common failure (pest names in local dialect) has been fixed with a glossary built from feedback.

## Common mistakes

- **Assuming you can use whatever data you have.** Check consent and contracts.
- **No evaluation set.** Quality becomes opinion.
- **Feedback buttons nobody reads.** Build the review routine.
- **Ignoring coverage.** Missing groups and languages become failures and bias.
- **No owner.** Unowned data goes stale and nobody notices.

## Practise

Read the PAIR chapter on data collection and evaluation, and Hamel Husain's field guide.

1. For an AI product idea, list run-time, evaluation and feedback data, with source and owner for each.
2. For each, write the permission basis and retention period.
3. Draft 30 evaluation cases with a domain expert, and note one coverage gap.

**You are done when you can** present a one-page data plan that a privacy officer and an engineer would both accept.
