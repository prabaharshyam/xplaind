## What it is

**Big-O notation** describes how the work an algorithm does grows as its input grows. It does not tell you the exact number of seconds; it tells you the shape of the curve. If you double the input, does the work stay the same, double, or quadruple?

That matters because real data grows. A script that checks 100 test orders in a blink may take all night on the 10 lakh orders a Flipkart seller sees during a Big Billion Days sale. Big-O lets you predict that before you run the code, and choose an approach that scales.

```text
 work
  ^                                         O(n²)
  |                                       /
  |                                     /
  |                                  /        O(n log n)
  |                              /       ___/
  |                         /      ___/         O(n)
  |                    /     ___/        _____/
  |              /     ___/      _____/
  |        /   ___/  _____/                    O(log n)
  |   / ___/____/____________________________  O(1)
  +-------------------------------------------------> input size n
```

The common classes, from best to worst, are O(1), O(log n), O(n), O(n log n) and O(n²). There are worse ones, such as O(2ⁿ), that only work on tiny inputs.

## How it works

To find the Big-O of some code, count how many times the most repeated step runs as n grows, then keep only the biggest term and drop constants.

- A single loop over n items runs its body n times: **O(n)**.
- A loop inside a loop over the same items runs n × n times: **O(n²)**.
- Halving the problem each step, as binary search does, takes about log₂ n steps: **O(log n)**.
- A good sort, such as Python's built-in `sorted`, does about n × log n comparisons: **O(n log n)**.
- Reading a list item by position, or a dict value by key, takes the same time however big the collection is: **O(1)**.

We drop constants because they do not change the shape. Looping over the list twice is O(2n), which we still write as O(n): doubling n doubles the work either way. We drop smaller terms for the same reason: O(n² + n) is O(n²), because when n is 10 lakh the n² part swamps the rest.

**Space complexity** uses the same notation for memory. Building a set of every order ID needs O(n) extra space; adding up the amounts needs only O(1).

Here is what the classes mean in practice if one step takes one microsecond:

| Complexity | n = 1,000 | n = 10 lakh (1,000,000) | Typical example |
|---|---|---|---|
| O(1) | 1 µs | 1 µs | dict lookup |
| O(log n) | 10 µs | 20 µs | binary search |
| O(n) | 1 ms | 1 second | one pass over a list |
| O(n log n) | 10 ms | 20 seconds | sorting |
| O(n²) | 1 second | about 11.5 days | nested loops over all pairs |

The last row is the one that bites. An O(n²) method that feels instant in testing can be unusable in production.

## A worked example

Priya works on the payments team at a fintech in Bengaluru. Every night she must flag duplicate UPI transaction IDs in the day's file before it is settled. On a busy day the file has about 20 lakh rows.

Her first version compares every transaction with every other one:

```python
def has_duplicate(ids):
    for i in range(len(ids)):
        for j in range(i + 1, len(ids)):
            if ids[i] == ids[j]:
                return True
    return False
```

That is O(n²). With 20 lakh IDs it makes about 2 lakh crore comparisons. It never finished before the settlement deadline.

Her second version sorts the list first, so duplicates sit next to each other, then makes one pass:

```python
def has_duplicate(ids):
    ids = sorted(ids)
    for i in range(1, len(ids)):
        if ids[i] == ids[i - 1]:
            return True
    return False
```

Sorting is O(n log n) and the pass is O(n), so the whole thing is O(n log n). It ran in a few seconds.

Her third version uses a set, which is a **hash map** of keys:

```python
def has_duplicate(ids):
    seen = set()
    for t in ids:
        if t in seen:
            return True
        seen.add(t)
    return False
```

Each `in` check and `add` is O(1) on average, so the whole function is O(n) time. It uses O(n) extra memory for the set, which was fine on the server. This version ran in under a second, and it stops early as soon as it finds a duplicate.

The lesson Priya wrote in her team's notes: before optimising code line by line, check its Big-O. Moving from O(n²) to O(n) beat any amount of tuning.

## Common mistakes

**Hiding a loop inside a "simple" call.** `if x in my_list` looks like one step, but on a list it scans every item: O(n). Put it inside a loop and you have O(n²). Use a set or dict when you check membership many times.

**Counting lines instead of repetitions.** Five lines that each run once are O(1). One line inside two nested loops is O(n²). Look at how often the busiest line runs.

**Forgetting the cost of building things.** Converting a list to a set is O(n). That is worth it when you then do many lookups, not when you do one.

**Treating average as worst case.** Dict lookups are O(1) on average, but a bad hash function can make them slow. Quicksort is O(n log n) on average and O(n²) in its worst case. Interviewers often ask about both.

**Ignoring memory.** An O(n) time solution that needs O(n) extra memory may not fit when n is crores of rows. Say the space cost as well as the time cost.

**Optimising too early.** If n will never be more than 50, clear O(n²) code can be better than clever O(n log n) code. Big-O matters when n is large.
