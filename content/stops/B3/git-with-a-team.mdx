## What it is

Git records every change to a codebase. On your own, you mostly commit and push. On a team, the **main** branch is shared and must always work, because other people, and often a live product, depend on it. So teams follow a routine:

```text
   main  o------------o------------------------o------> (always works)
          \                                   /
   branch  o---o---o  push  -->  pull request  merge
           your small    |       review +
           commits       |       automated checks
                         v
                   teammates comment, you fix
```

1. Create a **branch** for one piece of work.
2. Make small **commits** with clear messages.
3. Push and open a **pull request** (PR).
4. Teammates **review**; automated checks run.
5. Fix what they flag, then **merge**.

When two people change the same lines, Git raises a **merge conflict**, and a person decides the result.

This lesson follows you, three weeks into a project for a brokerage in Mumbai, as you add retries to a market-data client, get reviewed and resolve a conflict with a teammate's change. By the end you will be comfortable with every step.

## How it works

### Branches

Branches are cheap labels pointing at a commit. `git switch -c fix/gst-rounding` creates one and moves you onto it. Name branches for what they do:

| Prefix | Use for | Example |
| --- | --- | --- |
| `feat/` | A new feature | `feat/retry-market-data` |
| `fix/` | A bug fix | `fix/gst-rounding` |
| `docs/` | Documentation | `docs/setup-guide` |
| `chore/` | Tooling, dependencies | `chore/update-pandas` |

Check the client's naming convention before your first branch.

### Commits

Each commit should do one thing and say why:

| Weak | Strong |
| --- | --- |
| "fix" | "Fix GST rounding to two decimals for invoices over ₹1 lakh" |
| "wip" | "Add retry wrapper for market data client (no callers yet)" |
| "changes" | "MD-214: retry market data calls with backoff on 429 and 503" |

Many teams prefix messages with a ticket id. In six months, a clear history is how anyone, including you, understands why code looks the way it does.

### Pull requests

A PR carries the context a reviewer needs:

- **What** changed and **why**.
- **How you tested** it.
- **Anything risky**: performance, security, behaviour changes.
- A link to the ticket, and screenshots for anything visible.

Keep PRs small. A 200-line PR gets a careful review; a 3,000-line one gets a rubber stamp and hides bugs.

### Review goes both ways

When **reviewing**, check behaviour and risk before style: does it do the right thing, what could break, is it tested? When **being reviewed**, answer every comment, either by changing the code or explaining why not, and never take it personally. Review is about the code, not you.

### Staying current and resolving conflicts

While your PR waits, main moves on. Bring the new main into your branch with `git merge main`, or `git rebase main` if the team prefers rebasing. If the same lines changed on both sides, Git marks the conflict in the file:

```text
<<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = Decimal("0.18")
>>>>>>> main
```

The top part is your branch; the bottom is main. You edit the file to the correct **final** version, which often combines both, remove the markers, run the tests, then `git add` and commit.

### Protected branches and history

Clients often **protect** main: no direct pushes, a review and passing checks required. Never work around this. And never **force-push** a branch someone else is using: it rewrites history under their feet and can lose their work.

### Secrets

An API key committed to Git stays in the history even after you delete the file. Keep secrets in environment variables, list secret files in `.gitignore`, and if a key ever leaks, **rotate it at once**, then clean up.

## A worked example

You are three weeks into a project with a brokerage in Mumbai. Your ticket, MD-214: add retries to the market-data client, which sometimes gets rate-limited at market open.

```text
git switch main && git pull
git switch -c feat/retry-market-data
# edit, test
git add src/marketdata/client.py tests/test_client.py
git commit -m "MD-214: retry market data calls with backoff on 429 and 503"
git push -u origin feat/retry-market-data
```

**The PR.** Your description says what changed, that you tested with a fake server returning 429 twice, and flags a risk: in the worst case, retries add up to 7 seconds, and the dashboard times out at 10 seconds.

**The review.** Farhan, the reviewer, asks you to cap the total retry time at 3 seconds. You change it, add a test for the cap, reply "Done, capped at 3s total, test added", and push.

**The conflict.** Meanwhile Priya merged a change to the same client that added a configurable timeout. Your branch now conflicts. You merge main, read both sides, keep her new timeout setting **and** your retry wrapper, run the tests, and push.

| Step | Command or action | Result |
| --- | --- | --- |
| Start | `git switch -c feat/retry-market-data` | Your own branch |
| Save work | `git commit -m "MD-214: ..."` | One clear commit |
| Share | `git push -u origin ...` and open a PR | Review and checks start |
| Review fix | New commit capping retries at 3 s | Farhan's comment resolved |
| Conflict | `git merge main`, edit, test, commit | Both changes kept |
| Finish | Checks green, approval, merge, delete branch | Main has your feature |

Checks go green, Farhan approves, you merge and delete the branch.

## Common mistakes

- **Huge pull requests.** Split the work; reviewers miss bugs in long diffs.
- **Commit messages like "wip" and "changes".** Nobody will know why later.
- **Committing secrets.** Use environment variables and `.gitignore`; rotate any leaked key at once.
- **Resolving conflicts blindly.** Accepting "mine" for every conflict drops a teammate's fix. Read both sides.
- **Force-pushing shared branches.** Only rewrite history on branches nobody else uses.
- **Letting a branch go stale for weeks.** Merge main in regularly so conflicts stay small.

## Practise

Read GitHub flow, linked below, and the Pro Git chapter on basic branching and merging.

1. **A real PR.** In a repository of your own, make a branch, two small commits and a pull request with a proper description.
2. **A conflict.** Create one on purpose: change the same line on main and on your branch, then merge and resolve it.
3. **Review.** Review a friend's PR, or an open-source one, and leave two useful comments.

**You are done when you can** resolve a merge conflict without fear and write a PR description a stranger could review.
