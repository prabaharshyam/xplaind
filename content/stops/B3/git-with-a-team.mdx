## What it is

Git records every change to a codebase. On your own, you mostly commit and push. On a team, the main branch is shared and must always work, so everyone follows a routine:

1. Create a **branch** for one piece of work.
2. Make small **commits** with clear messages.
3. Push and open a **pull request** (PR).
4. Teammates **review**; automated checks run.
5. Fix what they flag, then **merge**.

When two people change the same lines, Git raises a **merge conflict**, and a person decides the result.

## How it works

**Branches** are cheap labels pointing at a commit. `git switch -c fix/gst-rounding` creates one and moves you onto it. Name branches for what they do.

**Commits** should each do one thing and say why. "Fix GST rounding to two decimals for invoices over ₹1 lakh" beats "fix". Many teams follow a format such as a ticket id prefix, so check the client's convention before your first commit.

**Pull requests** carry the context a reviewer needs: what changed, why, how you tested it and anything risky. Keep them small; a 200-line PR gets a careful review, a 3,000-line one gets a rubber stamp. Link the ticket. Screenshots help for anything visible.

**Review** goes both ways. When reviewing, check behaviour and risk before style. When reviewed, answer every comment, change the code or explain why not, and never take it personally.

**Staying current.** While your PR waits, main moves on. Bring it in with `git merge main` (or `git rebase main` if the team rebases). If the same lines changed, Git marks the conflict in the file:

```text
<<<<<<< HEAD
TAX_RATE = 0.18
=======
TAX_RATE = Decimal("0.18")
>>>>>>> main
```

You edit the file to the correct final version, remove the markers, run the tests, then `git add` and commit.

**Protected branches.** Clients often block direct pushes to main and require a review and passing checks. Never work around this, and never force-push a branch someone else is using: it rewrites history under their feet.

## A worked example

You are three weeks into a project with a Mumbai brokerage. Your task: add retries to the market-data client.

```text
git switch main && git pull
git switch -c feat/retry-market-data
# edit, test
git add src/marketdata/client.py tests/test_client.py
git commit -m "MD-214: retry market data calls with backoff on 429 and 503"
git push -u origin feat/retry-market-data
```

Your PR description says what changed, that you tested with a fake server returning 429 twice, and that retries add up to 7 seconds in the worst case, a risk for the 10-second dashboard timeout. The reviewer, Farhan, asks you to cap retries at 3 seconds. You change it, reply "Done, capped at 3s total, test added", and push.

Meanwhile Priya merged a change to the same client. Your branch now conflicts. You merge main, resolve the conflict by keeping her new timeout setting and your retry wrapper, run the tests, push. Checks go green, Farhan approves, you merge and delete the branch.

## Common mistakes

- **Huge pull requests.** Split the work. Reviewers miss bugs in long diffs.
- **Commit messages like "wip" and "changes".** In six months nobody, including you, will know why.
- **Committing secrets.** An API key in history stays there even after you delete the file. Use environment variables and a `.gitignore`; if a key leaks, rotate it at once.
- **Resolving conflicts blindly.** Accepting "mine" for every conflict drops a teammate's fix. Read both sides.
- **Force-pushing shared branches.** Only rewrite history on branches nobody else uses.

## Practise

Read GitHub flow and the Pro Git chapter on basic branching and merging.

1. In a repository of your own, make a branch, two small commits and a pull request with a proper description.
2. Create a conflict on purpose: change the same line on main and on your branch, then merge and resolve it.
3. Review a friend's PR (or an open-source one) and leave two useful comments.

**You are done when you can** resolve a merge conflict without fear and write a PR description a stranger could review.
