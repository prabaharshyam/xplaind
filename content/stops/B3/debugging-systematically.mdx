## What it is

**Debugging** is finding out why a program does something other than what you expect, and fixing the cause. The bug might crash the program, give a wrong number, or work on your laptop and fail on the server.

Beginners often debug by guessing: change a line, run again, change another. That works for small bugs and wastes hours on real ones. Experienced engineers use a method. It is not faster on easy bugs, but it always finishes, and it is what interviewers want to hear when they ask how you would track something down.

## How it works

```flow
title: The debugging loop
Reproduce it | smallest input that fails, every time -> Read the error | traceback from the bottom up
Read the error -> Form a guess | what must be true for this to happen?
Form a guess -> Narrow it down | print, breakpoint, halve the search
Narrow it down -[guess wrong]-> Form a guess
Narrow it down -[cause found]-> Fix the cause, not the symptom
Fix the cause, not the symptom -> Add a test that fails without the fix
```

**Reproduce.** Find the smallest input that triggers the bug every time. "It sometimes fails" becomes "it fails when the CSV has an empty amount". A reliable reproduction is half the work.

**Read the error.** A Python traceback reads from the bottom up:

```text
Traceback (most recent call last):
  File "report.py", line 31, in <module>
    print(monthly_total(rows))
  File "report.py", line 12, in monthly_total
    total = total + row["amount"]
TypeError: unsupported operand type(s) for +: 'int' and 'str'
```

The last line is the error: you tried to add a number and a string. The line above it is where it happened. The lines above that show how the program got there.

**Narrow it down.** Ask what must be true for this error to happen, then check it. Three tools, from quick to thorough:

| Tool | How | Good for |
| --- | --- | --- |
| `print(repr(x))` | Print values at key points | Quick checks; `repr` shows quotes and types |
| `breakpoint()` | Pause and inspect in the debugger | Seeing all variables at the moment it goes wrong |
| Editor debugger | Click to set breakpoints, step, watch values | Longer investigations |
| Logging | `logging.debug(...)` with context | Bugs that only show on a server |
| `git bisect` | Binary search through commits | "It worked last week" |

**The debugger.** Put `breakpoint()` on a line and run the program. It pauses there, and you can type `p row` to print a variable, `n` to run the next line, `s` to step into a function, and `c` to continue. You see the real state at the moment it matters, instead of guessing.

**Halve the search.** If a 200-line pipeline produces a wrong total, check the value halfway through. Right there? The bug is in the second half. Wrong? The first half. A handful of checks finds the line. `git bisect` does the same across commits: mark a good commit and a bad one, and Git walks you to the change that broke it.

**Fix the cause.** Wrapping the failing line in `try/except` hides a symptom; the bad data is still there. Fix where the wrong value comes from.

**Prove it.** Write a test that fails without your fix and passes with it.

**Bugs in AI apps.** When an LLM feature gives a wrong answer, the same method applies, with a trace in place of a traceback. Open the trace for that request and check each step in order: was the question rewritten correctly, did retrieval find the right passage, did the prompt include it, and did the model use it? The first step that looks wrong is where to dig.

## A worked example

Imran's monthly sales report for a chain of pharmacies in Pune shows ₹0 for one store, while the dashboard shows ₹4.2 lakh.

**Reproduce.** He runs the report for October on his laptop with the same export file. Same result: ₹0 for the Kothrud store. Reproducible.

**Read.** There is no error at all, which is itself a clue: the code runs but skips or zeroes the data.

**Guess and narrow.** What must be true for the total to be zero? Either no rows match the store, or every amount is zero. He puts `breakpoint()` inside the loop and prints `row["store"]` for the first few rows: `'Kothrud '`, with a trailing space. His filter compares against `'Kothrud'`. No rows match.

**Fix the cause.** He could add the space to his filter, but the real problem is untidy data from the export. He strips whitespace from store names where the file is read, so every later step gets clean values.

**Prove it.** He adds a test with a store name that has a trailing space and checks it is counted. He also adds a check that warns when a store in the master list has no rows, so a similar mismatch would be loud next time instead of silently showing ₹0.

## Common mistakes

- **Changing code before you can reproduce the bug.** You cannot know your fix worked.
- **Reading the traceback from the top.** The error and the line that failed are at the bottom.
- **Fixing the symptom.** A `try/except` that swallows the error makes the next bug harder to find.
- **Changing several things at once.** If it starts working, you will not know which change mattered.
- **Leaving debug prints and breakpoints in.** Search for `breakpoint(` and stray prints before you commit.
- **Not adding a test.** Without one, the bug can return the next time someone touches that code.

## Practice

1. Plant a bug in a small script (a string amount, an off-by-one in a range) and find it with `breakpoint()`.
2. Read three tracebacks from your own past errors and say, from the last line, what went wrong.
3. In a practice repository, break something in one of ten commits and find it with `git bisect`.
4. Explain your debugging method out loud in one minute, as you would in an interview.
