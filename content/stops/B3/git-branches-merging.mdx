## What it is

A **branch** in Git is a label that points at a commit. When you make a new commit on a branch, the label moves forward to it. That is all a branch is, so creating one is instant, and teams create one for every change: a bug fix, a feature, an experiment.

The shared branch, usually called **main**, should always work, because everyone builds on it and it is what gets deployed. So you never work directly on main. You make a branch, build and test your change there, and bring it back when it is ready.

There are two ways to bring work back:

- **Merge** joins two lines of history. If main has moved on since you branched, Git creates a **merge commit** with two parents. History shows exactly what happened, including the side branch.
- **Rebase** replays your commits on top of another branch, as if you had started from its latest commit. History becomes a straight line, which is easier to read, but your commits get new ids.

Both end with the same code. They differ in what the history looks like and in who it is safe for.

## How it works

The everyday loop on a team looks like this:

```flow
title: A feature branch from start to merge
Update main | git switch main, git pull -> New branch | git switch -c feature/otp
New branch -> Commit small steps | git add, git commit
Commit small steps -> Push the branch | git push -u origin feature/otp
Push the branch -> Pull request | review and checks
Pull request -[main moved on]-> Bring main in | merge main, or rebase onto main
Bring main in -> Pull request
Pull request -[approved, green]-> Merge into main
Merge into main -> Delete the branch
```

**Creating and switching.** `git switch -c feature/otp` makes a branch where you are and moves you onto it. `git switch main` moves back. `git branch` lists branches; the current one is starred.

**Merging.** From main, `git merge feature/otp` brings the branch in. If main has not moved since you branched, Git does a **fast-forward**: it simply moves main's label to your last commit. If main has moved, Git makes a merge commit.

**Conflicts.** If both sides changed the same lines of the same file, Git stops and marks the file:

```text
<<<<<<< HEAD
OTP_EXPIRY_SECONDS = 300
=======
OTP_EXPIRY_SECONDS = 120
>>>>>>> feature/otp
```

The part above the `=======` is what is on your current branch; below is the incoming change. You edit the file to the version you want, delete the markers, run `git add` on it, and commit. A conflict is not an error. It is Git asking you a question it cannot answer alone.

**Rebasing.** On your branch, `git rebase main` takes your commits, sets them aside, moves your branch to the tip of main, and replays them one by one. If one conflicts, Git stops; you fix the file, `git add` it and run `git rebase --continue`. `git rebase --abort` puts everything back as it was.

| | Merge | Rebase |
| --- | --- | --- |
| History | Keeps both lines, adds a merge commit | One straight line |
| Commit ids | Unchanged | Your commits get new ids |
| Safe on shared branches | Yes | No: only on commits nobody else has |
| Conflicts | Resolved once, in the merge | May need resolving per commit |
| Good for | Bringing a finished branch into main | Updating your own branch before review |

Many teams combine them: rebase your own branch to keep it current while you work, and merge (often a **squash merge**, which turns the branch into one commit) when the pull request goes into main.

## A worked example

Priya works at a fintech startup in Bengaluru on the login service. Her ticket: shorten the OTP expiry from five minutes to two.

She starts from a fresh main and makes a branch:

```bash
git switch main
git pull
git switch -c feature/otp-expiry
```

She changes `OTP_EXPIRY_SECONDS` in `config.py`, updates the test, and commits twice: one commit for the change, one for the test. She pushes the branch and opens a pull request.

While her pull request waits for review, her teammate Arjun merges a change to the same line: he moved the value to 300 seconds with a comment about a regulator's guideline. Priya's pull request now shows "This branch has conflicts".

Her branch is her own, and nobody else has pulled it, so she rebases:

```bash
git fetch origin
git rebase origin/main
```

Git replays her first commit and stops: `config.py` has a conflict. She reads Arjun's comment, checks with her lead, and learns the regulator allows 120 seconds for this flow. She keeps her value, keeps Arjun's comment, removes the markers and continues:

```bash
git add config.py
git rebase --continue
git push --force-with-lease
```

`--force-with-lease` replaces her branch on GitHub, but only if nobody else pushed to it in the meantime. That is the safe way to push after a rebase. The pull request is green and conflict-free; it is approved and squash-merged into main as one clean commit, and she deletes the branch.

## Common mistakes

- **Working directly on main.** One bad commit breaks everyone's base. Always branch, even for a one-line fix.
- **Long-lived branches.** A branch that lives for three weeks collects painful conflicts. Merge small changes often.
- **Rebasing a shared branch.** Rewriting commits that teammates have pulled leaves them with copies that no longer match. Rebase only your own unshared work.
- **Plain `git push --force`.** It can wipe a teammate's commits. Use `--force-with-lease`, and only on your own branch.
- **Resolving conflicts blindly.** Picking "mine" or "theirs" without reading both can silently undo someone's fix. Read both sides, and run the tests after.
- **Committing conflict markers.** Search for `<<<<<<<` before you commit. Many teams add a check in CI for it.

## Practice

1. Make a practice repository with one file. Create two branches that both change line 3, merge one into main, then merge the other and resolve the conflict.
2. Make a branch with three small commits. While it exists, add a commit to main. Rebase your branch onto main and look at `git log --oneline --graph --all` before and after.
3. Try `git rebase --abort` in the middle of a rebase and confirm everything is back as it was.
4. Explain out loud, as you would in an interview, when you would merge and when you would rebase, in under a minute.
