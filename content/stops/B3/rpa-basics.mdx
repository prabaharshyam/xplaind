## What it is

Many Indian businesses still run on software that cannot talk to anything else: a 15-year-old desktop ERP, a bank's back-office screens, a government portal with no API. People spend their days copying values from one screen to another. **Robotic process automation (RPA)** takes over that copying.

RPA uses software "robots" that operate applications through their **user interface**, as a person would: opening programs, clicking buttons, typing into fields, reading values from screens and downloading reports. It is the tool for systems that have no API, or where building an integration would take too long.

The key idea: an API is a door built for software, while RPA is software walking through the door built for people. That door was never designed for robots. A renamed button, a slow screen or a surprise pop-up can stop the robot. So RPA is powerful but fragile, and most of the skill lies in managing that fragility.

```flow
dir: LR
title: API automation: fast, sturdy, preferred
System A, has an API -[data, directly]-> System B, has an API
```

```flow
dir: LR
title: RPA: works anywhere a person can, more fragile
Robot | UiPath, Power Automate Desktop -[clicks and typing on screen]-> Old desktop app, no API
```

Leading RPA tools include **UiPath**, **Automation Anywhere** and **Microsoft Power Automate Desktop**. You design the steps in a studio app, then run them on a schedule or on demand, on a desktop or a server. Power Automate for desktop comes with Windows 11 at no extra cost, which makes it an easy place to practise, though running flows unattended or triggering them from the cloud needs a paid licence.

This lesson follows the claims team of a general insurer in Kolkata as an AI step and an RPA robot take over data entry into an old claims system. By the end you will know when RPA is the right tool, how to build a robot that does not create duplicates or fail silently, and how to check whether it pays for itself.

## How it works

### Attended and unattended robots

| Type | Runs | Example |
| --- | --- | --- |
| **Attended** | On a person's computer, when that person starts it | A robot that fills a 40-field form after the agent clicks "Go" |
| **Unattended** | On its own, on dedicated machines, taking items from a queue | A robot that enters 300 claims overnight |

Attended robots help one person go faster; a person watches every run. Unattended robots replace a shift of work, and nobody watches them. Every design rule below matters most for unattended robots.

### The production model: queue, orchestrator, robot

A demo robot loops over rows in a spreadsheet. A production robot works from a **queue**. Each piece of work, such as one claim email, becomes a **queue item** with its data and a status, such as new, in progress, successful or failed. An **orchestrator**, the control centre of the RPA platform (UiPath calls it Orchestrator), holds the queues, starts robots on schedules, stores credentials and keeps logs.

Queues give you three things a spreadsheet loop does not. Several robots can share the work. A crash loses only the item in progress, not the whole batch. And the business can see at a glance how many items are waiting, done or stuck.

### Business and system exceptions

Things go wrong in two very different ways, and a robot must tell them apart.

| | Business exception | System exception |
| --- | --- | --- |
| **What happened** | The data breaks a rule: policy expired, GSTIN does not match, a required field is missing | Something technical failed: the app crashed, a screen timed out, the network dropped |
| **Will a retry help?** | No. The data will be just as wrong next time | Usually. The same item often works on a second try |
| **What to do** | Mark the item failed and send it to a person, with the reason | Close and restart the app, then retry, up to a limit such as three times |

The classic mistake is to retry everything. A business exception retried three times wastes three runs and still ends with a person. A system exception sent straight to a person creates manual work a restart would have cleared. Templates such as UiPath's REFramework build this split in. Tools differ in their exact retry settings, so check the documentation for your version.

### Retries and duplicates: idempotency

Retries create the most dangerous failure in RPA. Picture it: the robot types a claim, clicks Save, and the old app freezes for two minutes. The robot times out and reports a system exception. The queue retries the item. But the first Save did go through. The retry enters the claim a second time, and now the insurer has two claims for one accident.

The fix is **idempotency**: running an item twice must give the same result as running it once. In practice:

1. **Pick a unique key the old system can search**, such as policy number plus date of loss.
2. **Search before you create.** At the start of each item, look the key up in the target system. If the record exists, pick up its reference and skip to the next step.
3. **Mark the item successful only at the very end**, after the new reference is written back to the tracking sheet, never just after clicking Save.

```flow
title: An idempotent queue item
Take the next queue item -> Already in the claims system?
Already in the claims system? -[yes]-> Read the existing claim number
Already in the claims system? -[no]-> Fill the form and save | then read the new claim number
Read the existing claim number -> Write the claim number to the tracking sheet
Fill the form and save -> Write the claim number to the tracking sheet
Write the claim number to the tracking sheet -> Mark the item successful
```

Some orchestrators can also refuse a second queue item with the same reference. That stops duplicate work entering the queue, but it does not stop a retry from saving twice in the target app. Only the search-before-create step does that.

### How robots find things on screen: selectors

Good RPA does not click at fixed screen positions. It finds each element by its properties: the window's title, a field's label, its type. This description is called a **selector**. Here are two simplified selectors, in the style UiPath uses, for the same Policy number box:

```text
Brittle:  <wnd app='claims.exe' title='Claims v4.2 - User RKUMAR' />
          <ctrl automationid='txt_4471' idx='7' />

Robust:   <wnd app='claims.exe' title='Claims*' />
          <ctrl name='Policy No*' role='editable text' />
```

The brittle one breaks for three reasons. The window title includes a version number and a user name, which change. The id `txt_4471` is generated by the app and can change on the next build. And `idx='7'` picks a box by its order among similar boxes: add one field above it and the robot types into the wrong one. UiPath's own guidance is to avoid `idx` where other attributes can do the job. The robust one uses things a person would recognise: the app, the start of the window title and the field's label. The `*` is a **wildcard** that matches any characters, so "Claims v4.3" still matches. A `?` matches exactly one character.

Two habits make selectors last. Prefer the label over the position. And after typing, read the value back, or check that the expected next screen appeared, before moving on.

### Remote desktops and Citrix

Some organisations publish old apps through **Citrix** or a remote desktop. The robot then sees only a picture of the screen, with no element properties. It falls back on **image matching**, finding a button by how it looks, or **OCR**, reading text from the picture. A changed theme, font, screen resolution or display scaling can break both.

First ask the IT team whether the RPA vendor's remote component can be installed. UiPath, for example, has a Remote Runtime that runs on the Citrix server and works with an extension on the robot's machine, so the robot gets real selectors again. If that is not allowed, fix the robot machine's resolution and scaling, anchor each image to a nearby text label, and verify every step by reading text back.

### RPA, computer-use agent or API?

**Computer-use agents** are AI models that operate screens from screenshots, deciding each click as they go. They cope with screens they have never seen, but each step costs a model call, they are slower, and they can choose a different action on the same screen. That unpredictability is hard to accept when the robot is writing into a claims or banking system.

| Situation | Best choice | Why |
| --- | --- | --- |
| The system has a usable API | API integration | Fastest, sturdiest, clear errors |
| Stable screens, high volume, no API | RPA | Cheap per item, predictable, auditable |
| Varied or unfamiliar screens, low volume | Computer-use agent, with a person approving each change | Flexible where RPA would need constant fixing |

A good pattern combines them: RPA for the stable steps, and an agent only to recover from an unexpected screen, with a person approving before anything is saved.

### RPA plus AI

RPA moves data through screens; AI reads documents, classifies emails or extracts fields. Together they cover processes neither handles alone. The AI step turns messy input into clean fields; validation checks them against your own data; the robot types only validated fields. Never let a robot key an AI guess straight into a system of record.

### Does it pay? A break-even check

Robots are not free. Before you build one, compare:

- **Saving per month** = hours saved per month × loaded hourly cost of staff (salary plus overheads).
- **Cost per month** = licences + robot machines + AI calls, if any + maintenance hours × developer rate.

Then divide the one-time build cost by the monthly net saving to get the payback period. One honest rule: count the saving only if the freed hours are really used for other work. Otherwise the robot only adds cost.

### Keeping robots safe and running

Robots break when screens change, passwords expire or pop-ups appear. Plan for that from day one:

- **Monitoring.** Alert a named owner when a run fails or the queue stops moving. A stopped robot is silent; the first sign is often an angry customer.
- **A robot register.** Record each robot's owner, the systems it touches and the accounts it uses.
- **Least-privilege accounts and a vault.** Give each robot its own account with only the access it needs. Keep its password in a credential vault, such as the orchestrator's own store or CyberArk, never in the script.
- **Audit logs.** Log each item's key, each step and the result, so you can prove what the robot did. Mask personal data, such as phone numbers, in logs.
- **Test before the target app changes.** Ask the app team for release dates. Run the robot against the test copy of each new version before it goes live, so moved fields are found in testing, not in production.

## A worked example

This is an illustrative case built from typical numbers, not a measured deployment.

A general insurer in Kolkata receives motor claim intimations by email: about 300 a day. The claims team copies details from each email and its attachments into an old desktop claims system that has no API. Each claim takes about 6 minutes, so 300 × 6 = 1,800 minutes, or 30 hours of work a day.

**The design:**

```flow
Email with a claim -> AI extraction step | policy no., vehicle no., date and place of loss
AI extraction step -> Validate against the policy database
Validate against the policy database -[ok]-> Queue item | key: policy no. plus date of loss
Validate against the policy database -[not ok]-> A person's queue | with the reason and a screenshot
Queue item -> Unattended robot | search first, then create if not found
Unattended robot -[app crash]-> Restart the app and retry | system exception, up to 3 tries
Restart the app and retry -> Unattended robot
Unattended robot -[screen not recognised]-> A person's queue
Unattended robot -> Claim number back to the tracking sheet
```

1. An **AI extraction step** reads each email and attachment and produces fields: policy number, vehicle number, date and place of loss, description.
2. The fields are **validated** against the policy database: does the policy exist, is it active, does the vehicle match? Failures are business exceptions and go to a person with the reason.
3. Valid claims become **queue items** keyed on policy number plus date of loss.
4. An **unattended robot** searches the claims system for that key. If there is no claim, it opens "New intimation", fills the fields, saves, reads the new claim number, and writes it to the tracking sheet. Only then is the item marked successful.
5. App crashes are system exceptions: restart and retry, up to three times. Any screen the robot does not recognise goes to a person with a screenshot.

**What the first quarter might look like:**

| Measure | Before | After |
| --- | --- | --- |
| Staff time on data entry | about 30 hours a day | about 6 hours a day, mostly exceptions |
| Claims entered the same day | about 70% | about 98% |
| Robot outages | not applicable | 2, both after system updates moved fields |
| Duplicate claims from retries | not applicable | 0, because of search-before-create |

**Does it pay?** Use these assumed figures; get real quotes before you decide.

- Hours saved: 30 − 6 = 24 a day. Over 25 working days, that is 600 hours a month.
- Suppose the loaded staff cost is ₹400 an hour. Saving: 600 × ₹400 = ₹2,40,000 a month.
- Suppose running costs are ₹1,00,000 a month for licences and robot machines, ₹15,000 for AI extraction, and 20 maintenance hours at ₹1,000 an hour (₹20,000). Total: ₹1,35,000.
- Net saving: ₹2,40,000 − ₹1,35,000 = ₹1,05,000 a month. If the build costs ₹6,00,000, payback takes about 6 months.

Now turn it around. Each claim saves 6 minutes × 24/30 = 4.8 minutes, or 0.08 hours, so a claim is worth 0.08 × ₹400 = ₹32. To cover ₹1,35,000 a month over 25 days, the robot needs ₹1,35,000 ÷ (25 × ₹32), or about 170 claims a day. With these assumptions, under about 170 claims a day the robot loses money. Volume decides the case, not how clever the robot is.

The insurer plans to replace the robot with a direct API integration when the claims system is upgraded. Until then, the robot is the bridge, and it is cheap to retire because all the logic sits in one documented queue process.

## Common mistakes

- **Using RPA where an API exists.** The API is faster, sturdier and gives clear errors. Ask the vendor or IT team before you build.
- **Selectors tied to positions, generated ids or index numbers.** Use labels and wildcards, and read values back after typing.
- **Retrying everything, or nothing.** Send business exceptions to a person; retry system exceptions a fixed number of times.
- **No search before create.** One timeout after Save, and the retry makes a duplicate record.
- **Marking an item done too early.** Mark it successful only after the reference is written back.
- **Automating a process that keeps changing.** Fix or settle the process first; a robot freezes today's mess in place.
- **No owner, no alerts.** Broken unattended robots fail silently while work piles up.
- **Robots with admin accounts or passwords in scripts.** Use least-privilege accounts and a vault.
- **Building before doing the sums.** At low volume, licences and maintenance can cost more than the time saved.

## Practice

Take a free beginner course at UiPath Academy, linked below. If you are on Windows 11, you can also practise in Power Automate for desktop, which is already installed. The Microsoft Learn path linked below covers Power Automate cloud flows, a useful companion for the API side.

1. **Build.** Make a robot that reads rows from a spreadsheet, fills a web or desktop form for each row, saves, and writes a confirmation number back to the sheet.
2. **Break it.** Resize the window, change the display scaling and add a field above the target box. Fix every failure with better selectors, and add a read-back check after typing.
3. **Make it idempotent.** Run the same sheet twice. The second run must create nothing new; it should find each record and pick up its existing number.
4. **Choose and cost.** For one process at your workplace or college, decide between RPA, an API and a computer-use agent, and work out its break-even volume with your own assumed figures.

**You are done when you can** explain when you would choose RPA over an API or an AI agent, show a robot that survives a small layout change and a second run without duplicates, and give a break-even volume for one real process.
