## What it is

Code that works on your laptop is the start, not the finish. **Project tooling** is everything around your code that lets someone else run it, change it safely and debug it at 2 am. Each piece answers one question a stranger will ask:

| The stranger asks | The file or tool that answers | Without it |
| --- | --- | --- |
| Which Python and which packages? | `pyproject.toml`, `uv.lock`, `.python-version` | "Works on my machine" |
| Where is the code and how do I import it? | A `src` layout, installed into `.venv` | Imports that work only from one folder |
| Did my change break anything? | pytest tests | Bugs found by users |
| Is this code tidy and free of obvious slips? | ruff | Style arguments in every review |
| Where does the API key go? | `.env` (ignored) and `.env.example` (committed) | Keys leaked into git |
| What happened in production? | `logging`, configured once | Guessing |
| Does it still work on a clean machine? | CI on every push | "It passed on my laptop" |
| What do I type first? | A README with exact commands | A WhatsApp message to you |

None of this is glamorous. All of it is noticed when missing, usually by the client's engineer the week after you hand over.

This lesson follows an invoice extractor you built for a textile exporter in Coimbatore, as their engineer, Karthik, takes it over. It uses **uv**, a fast tool from Astral that creates the environment, installs packages, writes the lock file and can install Python itself. Plain `venv` and `pip` work too; each section shows the difference.

```flow
title: From clone to a trusted change
dir: LR
Clone the repository -> Install locked versions | uv sync
Install locked versions -> Add secrets | copy .env.example to .env
Add secrets -> Lint and test | ruff and pytest
Lint and test -> Change the code
Change the code -> Push
Push -> CI repeats the checks on a clean machine
```

## How it works

### The layout

```text
invoice-extractor/
  pyproject.toml          # what the project is and needs
  uv.lock                 # exact versions of everything (commit it)
  .python-version         # the Python version the team uses
  .gitignore              # .venv, .env, __pycache__
  .env.example            # variable names, no real values
  README.md
  .github/workflows/ci.yml
  src/invoice_extractor/
      __init__.py
      cli.py              # entry point: configures logging, builds the client
      extract.py
      models.py
      llm.py              # the real model client
  tests/
      conftest.py         # shared fixtures, including a fake model client
      test_extract.py
      fixtures/sample_invoice.txt
```

`uv init --package invoice-extractor` creates most of this for you, including a `src` folder, a `.python-version` and a git repository.

### pyproject.toml

Here is a complete one, as we ran it with uv 0.13.10, pytest 9.2.0 and ruff 0.17.6 (the newest releases as of 28 November 2026):

```toml
[project]
name = "invoice-extractor"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "pydantic>=2.10",
]

[project.scripts]
invoice-extractor = "invoice_extractor.cli:main"

[dependency-groups]
dev = ["pytest>=9.0", "ruff>=0.17"]

[build-system]
requires = ["uv_build>=0.13.10,<0.14.0"]
build-backend = "uv_build"

[tool.pytest]
testpaths = ["tests"]
addopts = ["-ra", "--strict-markers"]

[tool.ruff.lint]
select = ["E", "F", "I", "B", "UP"]
```

What each part does:

- **`[project]`** names the package and lists what it needs to run. Use ranges here (`>=2.10`), not exact pins; the lock file holds the exact versions.
- **`[project.scripts]`** creates a command, so `uv run invoice-extractor` calls `main()` in `cli.py`.
- **`[dependency-groups]`** holds tools only developers need. `uv sync` installs the `dev` group by default; `uv sync --no-dev` leaves it out of a production image.
- **`[build-system]`** says how to turn `src/` into an installable package. Without it, uv treats the folder as a loose collection of scripts and does not install your package.
- **`[tool.pytest]`** is the native TOML table added in pytest 9. On older pytest, use `[tool.pytest.ini_options]` with the same keys.

**Pinning Python.** `requires-python` is the range you promise to support. `.python-version` is the one version everybody, including CI, actually uses; uv downloads it if it is missing. Python 3.15 came out on 9 October 2026, but you do not have to move on day one: before you raise `.python-version`, check that your heavier libraries publish wheels for the new version, then let CI prove it.

### The src layout, and the install step everyone forgets

With the code in `src/`, Python cannot import `invoice_extractor` just because you are standing in the project folder. That is the point: tests can only reach your package the way a user would, through an install. A missing file in the package, or a wrong setting in `pyproject.toml`, shows up on your laptop instead of on the client's server.

The corollary trips up nearly every beginner. If the package is not installed, the tests fail before they start:

```text
E   ModuleNotFoundError: No module named 'invoice_extractor'
```

`uv sync` installs the project into `.venv` in **editable** mode, so your edits take effect without reinstalling. With plain pip, do the same by hand: create and activate a venv, then run `pip install -e . --group dev` (`--group` needs pip 25.1 or later). Do not "fix" the error by adding `src` to `PYTHONPATH` or putting `sys.path` hacks in `conftest.py`; that removes the protection the layout gives you.

### Lock files and --locked

`uv add httpx` adds the range to `pyproject.toml` and updates `uv.lock` in one step. The lock records the exact version and file hash of every package, including the packages your packages depend on. Commit it for any application or service you deploy. A library published for others still keeps loose ranges in `pyproject.toml`, so it does not force versions on its users, but committing its lock for your own CI is still useful.

In CI, Dockerfiles and the README, install with `uv sync --locked`. If someone edited `pyproject.toml` by hand and forgot to run `uv lock`, it stops at once:

```text
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
  cause: Requirements for `invoice-extractor==0.1.0` differ; added: httpx>=0.28
```

Plain `uv sync` would quietly rewrite the lock instead, and the versions you test would drift from the versions you ship. Upgrade on purpose, one package at a time: `uv lock --upgrade-package pydantic`, run the tests, commit both files. The pip equivalent of a lock is a fully pinned requirements file produced by a tool such as pip-tools; `pip freeze` also works but mixes in whatever else happens to be installed.

### Lint and format with ruff

**Ruff** is one fast tool that does two jobs. `ruff check` is a **linter**: it finds likely bugs and bad patterns. `ruff format` is a **formatter**: it rewrites spacing and line breaks into one house style, so reviews are about logic, not commas.

```text
uv run ruff check --fix    # find problems, fix the safe ones
uv run ruff format         # rewrite layout
```

Since ruff 0.16, the default set is large: over 400 rules from many groups. A `select` line replaces that default with exactly the groups you name. The one above gives a smaller, predictable set: `E` and `F` (pycodestyle and Pyflakes), `I` (sorted imports), `B` (bugbear: common bug patterns such as a mutable default argument) and `UP` (newer, simpler syntax for your Python version). Add more rule groups one at a time; switching on everything at once on an old codebase produces hundreds of warnings and the team turns the linter off.

### Secrets and settings

The code reads secrets from environment variables and nothing else:

```python
client = ModelClient(api_key=os.environ["MODEL_API_KEY"])
```

If the variable is missing, this raises `KeyError: 'MODEL_API_KEY'` at start-up, which is far better than a confusing failure on the first invoice. Locally, keep values in a `.env` file and load it with `uv run --env-file .env`. Commit a `.env.example` that lists the names with no real values:

```text
MODEL_API_KEY=
LOG_LEVEL=INFO
```

Check your `.gitignore`: the one `uv init` writes covers `.venv` but not `.env`, so add it yourself and confirm with `git check-ignore .env`. If a real key ever reaches a commit, deleting the file in a later commit does not help, because it stays in the git history. Revoke and rotate the key first, then clean up.

### Logging

Configure logging **once**, at the entry point, and nowhere else:

```python
# cli.py
import logging
import os


def main() -> None:
    logging.basicConfig(
        level=os.environ.get("LOG_LEVEL", "INFO").upper(),
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
    )
```

Every other module only asks for a logger named after itself and logs facts a stranger can act on:

```python
# extract.py
log = logging.getLogger(__name__)

log.warning(
    "invoice=%s field=total model_value=%r error=%s",
    data.get("id"),
    data["total"],
    err,
)
```

Pass values as arguments, as above, rather than building an f-string; the logging module then formats only the messages it actually emits. If your log platform can search JSON fields, switch the format to one JSON object per line; the habit of logging ids, fields and timings stays the same. `print` is still fine for a command's real output, such as the extracted JSON; it is wrong for messages about what the program is doing.

| Level | Use for | In production |
| --- | --- | --- |
| DEBUG | Detail for developers: prompts, raw replies | Off |
| INFO | Normal events: a file processed, with its duration | On |
| WARNING | Odd but handled: a retry that succeeded, a bad input skipped | On |
| ERROR | Something failed and needs a person | On, and alerts |

Never log API keys, passwords, full documents or personal data such as customer phone numbers or PAN numbers. Log ids, sizes and timings instead.

### Tests, and a fake model client

pytest itself, fixtures, parametrised tests and mocking are covered in the "Writing tests with pytest" lesson (B3). What matters for project structure is where things live. Shared fixtures go in `tests/conftest.py`, which pytest loads on its own. For code that calls a model, the cleanest design passes the client in, so a test can hand it a fake:

```python
# tests/conftest.py
import json
from pathlib import Path

import pytest

FIXTURES = Path(__file__).parent / "fixtures"


class FakeModelClient:
    """Returns a fixed reply and records each prompt. No network, no cost."""

    def __init__(self, reply: dict):
        self.reply = json.dumps(reply)
        self.prompts: list[str] = []

    def complete(self, prompt: str) -> str:
        self.prompts.append(prompt)
        return self.reply


@pytest.fixture
def sample_invoice() -> str:
    return (FIXTURES / "sample_invoice.txt").read_text(encoding="utf-8")


@pytest.fixture
def fake_client() -> FakeModelClient:
    return FakeModelClient(
        {
            "id": "INV-0001",
            "gstin": "33ABCDE1234F1Z5",
            "total": "1500.00",
            "items": [
                {"description": "Cotton yarn", "amount": "1000.00"},
                {"description": "Dyeing", "amount": "500.00"},
            ],
        }
    )
```

These unit tests check your own logic and run in well under a second on every push. Judging the real model's answers is a different job, done by an evaluation run on a fixed set of real, labelled examples; the "Test sets and evals" lesson (P1) suggests starting with 30 to 100 cases.

### CI on every push

CI (continuous integration) runs the same checks on a clean machine for every push and pull request, so "it passed on my laptop" stops being an argument. A complete GitHub Actions workflow:

```yaml
# .github/workflows/ci.yml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.4.0
      - run: uv sync --locked
      - run: uv run ruff check
      - run: uv run ruff format --check
      - run: uv run pytest
```

uv reads `.python-version` and installs that Python on the runner. One gotcha: `setup-uv` has no short tag such as `@v10` for its newer releases, so write the full version (or, stricter, the commit hash). Turn on branch protection so a pull request cannot merge while CI is red.

### The README

A good README lets a stranger go from clone to passing tests without asking you anything:

```text
git clone <repository-url> && cd invoice-extractor
uv sync --locked
cp .env.example .env          # then put your own key in .env
uv run pytest
uv run --env-file .env invoice-extractor tests/fixtures/sample_invoice.txt
```

Write it, then follow it yourself in a fresh clone under `/tmp`. Most READMEs break on the second line.

## A worked example

You built the invoice extractor for the Coimbatore exporter. Next month Karthik must run and maintain it without you.

**Day one.** He clones the repository and follows the README. `uv sync --locked` installs exactly the versions you tested, and `uv run pytest` reports 12 passed. Two of the twelve tests:

```python
import pytest
from pydantic import ValidationError

from invoice_extractor.extract import parse_amount, parse_invoice
from invoice_extractor.models import Invoice


def test_total_matches_line_items(sample_invoice, fake_client):
    inv = parse_invoice(sample_invoice, client=fake_client)
    assert inv.total == sum(i.amount for i in inv.items)
    assert "Cotton yarn" in fake_client.prompts[0]


def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValidationError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

The first test hands `parse_invoice` the fake client from `conftest.py`, so it checks the parsing logic and that the invoice text reached the prompt, with no network call. A GSTIN is always 15 characters, and the `Invoice` model rejects the 11-character one.

**A month later.** One invoice fails in production. The log line reads:

```text
2026-12-18 10:14:03,512 WARNING invoice_extractor.extract invoice=INV-8812 field=total model_value='12,40,000.00' error=not a number
```

Karthik sees at once what happened. The model copied the total with Indian digit grouping (12 lakh 40 thousand), and `parse_amount` called `Decimal(value)` directly, which rejects commas. Every test passed because the fake reply used `"1500.00"`, a format real invoices never had. He works in three steps:

1. **Reproduce.** He adds a test that fails before any fix:

```python
def test_reads_indian_digit_grouping():
    assert str(parse_amount("12,40,000.00")) == "1240000.00"
```

2. **Fix.** He changes one line: `return Decimal(value.replace(",", ""))`. Using `Decimal` rather than `float` keeps paise exact.
3. **Prove.** All 13 tests pass, ruff is clean, and he pushes. CI repeats the checks on a clean runner before the change merges.

He also changes the fake reply to `"1,500.00"`, because a fake is only as good as the replies you give it; copy their shape from real logs. The whole fix takes him about 20 minutes, alone.

| Without tooling | With tooling |
| --- | --- |
| "It fails sometimes," from a user | A log line naming the invoice, field and value |
| No way to prove a fix | A test that fails before the fix and passes after |
| Different package versions on the server | `uv sync --locked` everywhere |
| Karthik messages you on WhatsApp | Karthik fixes it alone, and CI checks his work |

## Common mistakes

- **Installing into the system Python.** It works on your laptop and nowhere else. Every project gets its own `.venv`.
- **A src layout that is never installed.** Tests fail with `ModuleNotFoundError`. Add a `[build-system]` and run `uv sync`, or `pip install -e .`; do not patch `sys.path`.
- **Not committing the lock file, or running plain `uv sync` in CI.** A dependency release breaks a fresh install months later. Commit `uv.lock` and use `--locked`.
- **Committing `.venv` or `.env`.** The first bloats the repository; the second leaks keys. Ignore both, commit `.env.example`, and rotate any key that was ever committed.
- **Calling `basicConfig` in every module, or inside library code.** Configure logging once, in the entry point.
- **Logging secrets or personal data.** Log ids, sizes and timings, never keys, full documents or phone numbers.
- **Leaving DEBUG on in production.** It fills disks, costs money on paid log platforms and often prints raw prompts with customer data.
- **Unit tests that call the real model.** They are slow, cost money and fail at random. Pass in a fake client; measure quality in a separate evaluation.
- **Turning on every lint rule at once.** Hundreds of warnings and the team stops reading them. Add rule groups gradually.
- **A README nobody has followed.** Test it from a fresh clone before handover.

## Practice

Work through pytest's Get Started page, linked below, then the basic section of Python's logging tutorial.

1. **Restructure.** Run `uv init --package` and move one script you have written into `src/`. Add `[dependency-groups]`, `[tool.pytest]` and `[tool.ruff.lint]` to `pyproject.toml`, then `uv sync` and commit `uv.lock` and `.python-version`.
2. **See the install matter.** In a scratch venv where the package is not installed, run pytest and read the `ModuleNotFoundError`. Then install it and run again.
3. **Fake the model.** If your code calls a model, change the function to take the client as a parameter, write a `FakeModelClient` fixture in `conftest.py`, and add one test that uses it and one that checks a bad reply raises a clear error.
4. **Lint and log.** Run `ruff check --fix` and `ruff format`. Replace every debugging `print` with a logger call at the right level, and configure logging once in your entry point with `LOG_LEVEL` from the environment.
5. **Secrets and CI.** Move any key into `.env`, add `.env` to `.gitignore`, commit a `.env.example`, and add the workflow above. Push and watch it go green.
6. **The stranger test.** Clone your repository into `/tmp`, follow only your README, and fix every step that breaks.

**You are done when you can** hand the repository to a friend who runs `uv sync --locked` and `uv run pytest` from the README and sees every test pass, while CI shows the same result on the latest commit.
