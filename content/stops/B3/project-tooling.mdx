## What it is

Code that works on your laptop is the start, not the finish. **Project tooling** is everything around your code that lets someone else run it, change it safely and debug it at 2 am. Four parts matter most:

| Part | What it gives you | Without it |
| --- | --- | --- |
| **An isolated environment** | The project's packages do not clash with anything else | "Works on my machine" |
| **pyproject.toml and a sensible layout** | The project installs the same way everywhere | Nobody knows how to set it up |
| **Tests with pytest** | A change that breaks something fails loudly before it ships | Bugs found by users |
| **Logging** | When something goes wrong in production, you can see what happened | Guessing |

None of this is glamorous. All of it is noticed when missing, usually by the client's engineer the week after you hand over.

This lesson follows an invoice extractor you built for a textile exporter in Coimbatore, as their engineer, Karthik, takes it over. By the end your projects will be ones a stranger can set up, test and debug from the README alone.

## How it works

### Environments and lock files

Each project gets its own virtual environment. Tools such as `venv` with `pip`, or the faster `uv`, create one and install exactly the versions you pin. A **lock file**, such as `uv.lock` or a fully pinned `requirements.txt`, records the exact version of every package, including the packages your packages depend on, so another machine gets exactly the same set.

### Layout

A common, safe shape for a Python project:

```text
invoice-extractor/
  pyproject.toml           # name, version, dependencies, tool settings
  uv.lock                  # exact versions of everything
  README.md                # how to set up, test and run
  src/invoice_extractor/   # your package
      __init__.py
      extract.py
      models.py
  tests/                   # pytest tests
      conftest.py          # shared fixtures
      test_extract.py
      fixtures/sample_invoice.txt
```

The `src` folder stops tests from accidentally importing code that only works from your own folder. `pyproject.toml` replaces a pile of older files such as `setup.py` and holds settings for tools like pytest and linters in one place.

### pytest

A test is a function whose name starts with `test_`, using plain `assert`. pytest finds and runs them all:

```python
def test_total_matches_line_items(sample_invoice):
    inv = parse_invoice(sample_invoice)
    assert inv.total == sum(i.amount for i in inv.items)
```

**Fixtures** provide shared setup that tests ask for by name: a sample PDF, a temporary folder, a fake model client. They live in `tests/conftest.py`.

### Testing code that calls a model

Real model calls in unit tests are slow, cost money and give slightly different answers each time, so tests fail randomly. Instead:

```text
   Unit tests (fast, every commit)          Evaluation suite (slower, scheduled)
 +---------------------------------+      +----------------------------------+
 | your parsing, validation,       |      | real model on a golden set of    |
 | scoring logic                   |      | 50-200 examples                  |
 | fake client returns fixed reply |      | scores quality, tracks over time |
 +---------------------------------+      +----------------------------------+
```

Test your own logic with a fake client; measure the model's quality separately.

### Logging

`print` output vanishes in production. The `logging` module gives each message a **level**, a time and the module it came from, and sends it wherever the platform collects logs.

| Level | Use for |
| --- | --- |
| DEBUG | Detail for developers, off in production |
| INFO | Normal events: a request handled, a file processed |
| WARNING | Something odd but handled: a retry, a bad input skipped |
| ERROR | Something failed and needs attention |

Use one logger per module, `log = logging.getLogger(__name__)`, configure output once at start-up, and log facts that help a stranger: which request, which document, how long it took, what failed.

### The README

A good README lets a stranger go from clone to passing tests without asking you anything. It has the exact commands, in order: set up the environment, set any environment variables (without real secret values), run the tests, run the tool. Write it, then test it yourself in a fresh folder; most READMEs break on the second line.

## A worked example

You built an invoice extractor for a textile exporter in Coimbatore. Next month their engineer, Karthik, must run and maintain it without you.

**Day one.** He clones the repository and follows the README:

```text
uv sync            # installs the exact locked versions
uv run pytest      # 12 passed
```

The lock file installs the same versions you tested. Two of the twelve tests:

```python
import pytest

from invoice_extractor.extract import parse_invoice
from invoice_extractor.models import Invoice

def test_total_matches_line_items(sample_invoice):
    inv = parse_invoice(sample_invoice)
    assert inv.total == sum(i.amount for i in inv.items)

def test_rejects_gstin_with_wrong_length():
    with pytest.raises(ValueError):
        Invoice(gstin="33ABCDE1234", total=100, items=[])
```

`sample_invoice` is a fixture in `tests/conftest.py` that loads a small text file, so no real model call is needed.

**A month later.** An invoice fails in production. The log line reads:

```text
2026-11-20 10:14:03 WARNING invoice_extractor.extract invoice=INV-8812 pages=3 field=total model_value="12,40,000.00" error="not a number"
```

Karthik sees at once that Indian digit grouping broke the number parser. He adds a test for "12,40,000.00", fixes the parser, sees all 13 tests pass and ships.

| Without tooling | With tooling |
| --- | --- |
| "It fails sometimes," from a user | A log line naming the invoice, field and value |
| No way to check a fix | A new test that fails before the fix and passes after |
| Different package versions on the server | The same locked versions everywhere |
| Karthik messages you on WhatsApp | Karthik fixes it in 20 minutes alone |

## Common mistakes

- **Installing into the system Python.** It works on your laptop and nowhere else. Always use a project environment.
- **Unpinned versions.** A library releases a breaking change and a fresh install fails. Commit the lock file.
- **Tests that call the real model.** They are slow, cost money and fail randomly. Fake the client in unit tests.
- **Logging secrets or personal data.** Never log API keys, full documents or customer phone numbers. Log ids and sizes instead.
- **A README that says "run main.py".** Write the exact commands to set up, test and run, and test them yourself.
- **Leaving DEBUG logging on in production.** It fills disks and can leak data.

## Practise

Work through pytest's Get Started page, linked below, then the basic section of Python's logging tutorial.

1. **Restructure.** Turn any script you have written into a project with `pyproject.toml`, a `src` layout and a `tests` folder.
2. **Test.** Write five tests, including one that uses a fixture and one that checks an error is raised.
3. **Log.** Replace every `print` with a logger call at a sensible level, and add one log line that would help debug a failure.

**You are done when you can** hand the repository to a friend, have them run the tests with two commands from the README, and have them all pass.
