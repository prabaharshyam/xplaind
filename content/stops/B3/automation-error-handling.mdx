## What it is

Every automation fails eventually. An API is down, a token expires, a customer types their phone number wrongly, a provider limits how fast you can send. The question is not **whether** it fails but **how**. A well-built automation fails safely: nothing is lost, nothing is done twice, and the right person knows what to do.

**Error handling** is everything an automation does when a step fails, or when a step "succeeds" but returns something wrong:

| Job | What it means |
| --- | --- |
| **Retry** | Try again errors that are likely temporary, slowly and a limited number of times |
| **Stop** | Do not keep trying errors that will not fix themselves; record them |
| **Alert** | Tell a person, once, with enough detail to act |
| **Recover** | Reprocess safely once the cause is fixed, without doing anything twice |
| **Record** | Keep a history of what happened to each item, for review and for reruns |

Two ideas sit under all five jobs. First, the right response depends on **what a retry would change**: a busy server may answer next time, a wrong phone number never will. Second, a failed call to "send" or "pay" does not always mean nothing was sent or paid. Most real duplicates come from forgetting that.

This lesson follows a Bengaluru logistics startup whose delivery updates were sent twice, hit rate limits and once stopped for a whole day. The example tool is n8n.

## How it works

### Classify the error by what a retry would change

```flow
An error happens -> Was the step only reading data?
Was the step only reading data? -[yes]-> Temporary error? | timeout, 429, 500 to 504
Was the step only reading data? -[no]-> Outcome unknown? | timeout or 500 to 504 on a send, pay or create
Outcome unknown? -[yes]-> Check status by your key | then retry with the same key
Outcome unknown? -[no]-> Temporary error?
Temporary error? -[yes]-> Retry with backoff | then needs attention if it still fails
Temporary error? -[no]-> About one record? | 400, 404, invalid data
About one record? -[yes]-> Needs attention list | carry on with the rest
About one record? -[no]-> Stop the run | 401, 403, expired token; alert the owner
```

| Kind | Examples | What to do |
| --- | --- | --- |
| **Temporary** | Network blips, rate limits (HTTP 429), server errors (500 to 504) on a read | Throttle, then retry with backoff and a cap |
| **Outcome unknown** | A timeout or a 500 to 504 on a step that sends, pays or creates something | Check first, then retry only with the same key |
| **Permanent, one record** | Bad input (400), a missing record (404), a phone number like "12345" | Record it with the reason, carry on with the others |
| **Permanent, whole workflow** | Wrong or expired credentials (401, 403), a deleted sheet | Stop at once and alert the owner |
| **Logic** | The run succeeds but does the wrong thing, such as a field mapped wrongly | Only validation and monitoring catch these |

Status codes are a starting point. Two patterns tell you more:

- **The same record fails on every attempt while other records go through.** Then the problem is that record, even if the code says 500. Some APIs crash on bad input and report a server error. After the normal retries, send it to "needs attention".
- **Every record fails, one after another.** Then the problem is the service or your credentials, not the records. Stop early instead of failing 2,000 items one by one.

### Timeouts are ambiguous

A timeout means you stopped waiting, not that the provider did nothing. The SMS may have gone out and only the reply was lost. Retry blindly and the customer gets it twice. Stripe's docs, for example, say to treat a 500 the same way: the money may or may not have moved.

The safe pattern has three parts:

1. **Record the attempt before you call.** Write a send-log row with a unique key and the status "sending"; afterwards, update it to "sent" or "failed".
2. **Pass an idempotency key if the provider supports one.** An idempotency key is a unique value you send with the request so the provider can recognise a repeat. Stripe, for example, accepts an `Idempotency-Key` header: if you retry with the same key and the same details, it returns the first result instead of charging again. Its v1 API docs say to retry with the same key within 24 hours (as of November 2026). Check your own provider's docs; some offer this, some do not.
3. **On a timeout, look before you retry.** If the provider has a status API, ask whether the message or payment exists. Retry only if it does not. Never generate a new key for the retry: a new key tells the provider "this is a new request".

If the provider has neither an idempotency key nor a status lookup, decide per action which mistake is cheaper. A delivery update sent twice is annoying; a refund paid twice is real money. For anything involving money, do not auto-retry an unknown outcome: put it in "needs attention" for a person to check.

### Throttle before you retry

Rate limits (HTTP 429) at a known daily peak are not bad luck: you send faster than your plan allows. **Send no faster than the provider's documented limit**, so 429s rarely happen, and keep retries as a safety net.

Suppose, for example, the plan allows 10 messages per second. Send batches of 8 with a one-second gap: that leaves 20 percent headroom for other workflows using the same account. Then 3,000 evening messages take about 375 seconds, a little over six minutes. In n8n you can do this with the HTTP Request node's **Batching** option (Items per Batch and Batch Interval), or with a **Loop Over Items** node and a **Wait** node inside the loop.

### Retry with backoff and jitter

Retry temporary errors a few times, waiting longer each time. Then add **jitter**, a random extra amount on each wait. Without it, when 500 items fail at 7 pm, all 500 retry at exactly the same second and fail again together.

```flow
dir: LR
Attempt 1 -[fails]-> Wait 5 to 10 s -> Attempt 2 -[fails]-> Wait 10 to 20 s -> Attempt 3 -[fails]-> Wait 20 to 40 s -> Attempt 4 -[fails]-> Needs attention and alert
```

A sensible default: double the wait each time, add a random 0 to 100 percent, stop after 3 to 5 attempts. A 429 may come with a **Retry-After** header, given in seconds or as a date. Use it instead of your own number.

**What n8n gives you.** Each node has a **Retry On Fail** setting with **Max Tries** and **Wait Between Tries (ms)**. As of November 2026, n8n's docs say Max Tries is limited to 5 and the wait to 5,000 ms, and the HTTP Request node does not read Retry-After for you. There is one wait setting, so the wait does not grow. That is fine for a network blip. For longer, growing waits, build the retry yourself: route the node's error output to a Wait node and loop back, with a counter so it stops.

### Idempotency: safe to run twice

A step is **idempotent** when running it twice has the same effect as running it once. Retries and reruns repeat steps, so every step that creates something needs this.

Keep a send log with a **unique key** per action. Before you act, check whether the key is already marked "sent"; if so, skip. Choose the key from **what the action is about**, so the same real-world action always gives the same key:

| Action | Good key | Bad key, and why |
| --- | --- | --- |
| Delivery update SMS | Order id plus status, for example ORD-4471 plus "out for delivery" | The run id: every rerun gets a new one, so nothing is ever skipped |
| Monthly fee reminder | Member id plus billing month | Member id alone: it blocks next month's reminder |
| Invoice in the ledger | Invoice number from the supplier | Time of processing: unique every time, so it catches nothing |

If two runs can overlap, a check followed by an action can still race: both runs check, both see nothing, both send. Writing the "sending" row first, in a store that refuses a second row with the same key (for example a database table with a unique constraint), closes that gap.

### Validate what comes back

A green tick only means the call returned. Check the response makes sense: an expected list is not empty, needed fields are present, a "200 OK" body holds no error message. If an export that normally has 8,000 rows has none, treat it as an error and stop, rather than "successfully" doing nothing. In n8n, an IF node can route bad responses to a **Stop and Error** node, which fails the run on purpose.

### Isolate bad records, but stop when everything fails

One bad item out of 300 should not stop the other 299. Process items independently and write each failure, with its reason, to a "needs attention" list, sometimes called a **dead-letter queue**. In n8n, set the node's **On Error** to **Continue (using error output)** and connect that output to the list. Someone fixes those records and reprocesses them later. Nothing is silently lost.

The opposite case needs a **circuit breaker**: a rule that pauses the run when failures pile up, for example 20 failures in a row, or more than half of the last 50 items. Without it, an outage turns into 2,000 dead-letter rows and 2,000 alerts.

### Alerts that help

| Weak alert | Useful alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. The SMS provider token has expired. Renew it in Settings, Credentials, SMS provider, then rerun; sent messages will be skipped. Run link: ..." |

Send it where the owner actually looks, such as email, Slack, Teams or WhatsApp. Group repeats, so one outage sends one message, not 500.

In n8n, create a separate **error workflow** that starts with an **Error Trigger** node, and choose it in each workflow's Settings. It runs when an automatic execution fails. It does not run when you test by hand, so test it with a real scheduled or webhook run.

### Monitor volume, not just errors

The most dangerous failure has no error at all. Track items processed and failures per day. A fixed threshold such as "fewer than 1,000" fires every quiet Sunday and misses a day that is half broken. Compare with the **same weekday's recent average** instead, for example "alert if by 8 pm we have sent less than half of the average of the last four Tuesdays", and review the rule monthly.

### What to use in n8n

| Job | n8n feature |
| --- | --- |
| Short retry of a blip | Node Settings, Retry On Fail |
| Longer or growing waits | Error output to a Wait node, looping back with a counter |
| Stay under a rate limit | HTTP Request Batching, or Loop Over Items with a Wait node |
| Carry on past one bad record | On Error set to Continue (using error output) |
| Stop the whole run | On Error set to Stop Workflow, or a Stop and Error node |
| Alert on any failed run | An error workflow starting with an Error Trigger node |
| Duplicates and dead letters | A lookup against your send log, and a sheet or table for failed records |

### Ownership and a runbook

Every automation has a named owner and a short runbook: what it does, the common failures, how to fix each, and how to rerun safely.

## A worked example

A logistics startup in Bengaluru runs an automation that sends delivery updates to customers by SMS and updates the order system: about 8,000 messages a day, most of them between 6 pm and 9 pm. The numbers below are an illustration of a typical first month, not measured results.

**The first month went badly:**

| Problem | Cause |
| --- | --- |
| Messages failed during evening peaks | The workflow sent as fast as it could, and the SMS provider rate-limited it (HTTP 429) |
| Some customers got two messages | A failed run was rerun by hand and sent earlier messages again; timed-out sends were retried blindly |
| One day nothing was sent, with no error | A login token for the order system had expired; the export step returned an empty list instead of failing loudly |

**The fixes:**

1. **Throttle to the plan's limit:** batches below the provider's documented rate, with a wait between them.
2. **Retries with backoff and jitter** on 429s, using Retry-After when present, at most four attempts, then the "needs attention" sheet. A timeout or a 500 to 504 on a send goes through the status check in fix 3 first.
3. **A send log keyed by order id plus status.** Each message is written as "sending" before the call. A rerun skips anything marked "sent". After a timeout, the workflow checks the provider's delivery status by that key before sending again.
4. **Validate the export.** An empty or very short export now stops the run with "order export returned 0 rows; check the order system login" instead of finishing green. This is the fix that would have caught the silent day.
5. **Credentials errors stop the run** at once and alert the owner with where to renew the token.
6. **A circuit breaker:** 20 failed sends in a row pause the run and send one alert.
7. **A volume check at 8 pm** against the average of the last four of the same weekday, alerting below 50 percent.

**The next month (illustrative):**

| Measure | Month 1 | Month 2 |
| --- | --- | --- |
| Duplicate messages | About 900 | 3, all after timeouts when the status lookup was itself down |
| Messages lost to rate limits | About 1,200 | 0; a handful of 429s, all sent on retry |
| Time to fix the next login expiry | About 9 hours (a customer complained first) | 20 minutes (the alert said what to do) |
| Records needing attention | Unknown | 35, each with a reason, all fixed within a day |

When the provider cannot say what happened, you choose between a rare duplicate and a rare missed update. For delivery updates the team chose the duplicate.

## Common mistakes

- **Retrying everything.** Permanent errors need fixing; a record that fails every time belongs in "needs attention".
- **Retrying a timed-out send blindly.** The first attempt may have worked. Check by your key first.
- **A new key on every attempt.** A run id or a timestamp makes every retry look new, so nothing is skipped.
- **Retries instead of throttling.** If 429s come at the same hour every day, slow down; do not just retry harder.
- **Fixed waits with no jitter and no cap.** Everything retries at once, the outage gets worse and you may be blocked.
- **Trusting a green run.** Validate empty or odd "successful" responses.
- **One bad item stops the batch, or a dead service fails every item.** Isolate records, but stop the run when failures pile up.
- **Alerts without details, or 500 of them.** Say what broke and what to do, once.

## Practice

Read n8n's guide to error handling, linked below, and revisit the error-handling part of the N8N102 course.

1. **Retries.** Point an HTTP Request node at an endpoint that fails on purpose (for example a small webhook workflow of your own that returns 503). Turn on Retry On Fail and confirm in the execution log that the retries actually ran. Then build a longer retry with the error output, a Wait node and a counter.
2. **Throttle.** Send 50 test items in timed batches and check the timing matches your plan.
3. **Duplicates and dead letters.** Add a send log with a unique key, the "sending" then "sent" status, and a "needs attention" sheet. Run the workflow twice and show nothing is sent twice.
4. **Alerts and checks.** Create an error workflow with an Error Trigger node and a useful alert, an empty-result check and a same-weekday volume check.

**You are done when you can** break your workflow four ways, with a temporary error, a permanent error, a bad item and an empty input, show the right behaviour for each, and rerun it with no duplicates.
