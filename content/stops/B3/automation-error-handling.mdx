## What it is

Every automation fails eventually. An API is down, a token expires, a customer types their phone number wrongly, a provider limits how fast you can send. The question is not **whether** it fails but **how**. A well-built automation fails safely: nothing is lost, nothing is done twice, and the right person knows what to do.

**Error handling** is everything an automation does when a step fails:

| Job | What it means |
| --- | --- |
| **Retry** | Try again errors that are likely temporary |
| **Stop** | Record errors that will not fix themselves, and do not keep trying |
| **Alert** | Tell a person, with enough detail to act |
| **Recover** | Reprocess safely once the cause is fixed, without duplicating actions |
| **Record** | Keep a history of what happened for later review |

This lesson follows a logistics startup in Bengaluru whose delivery-update automation sent duplicate messages, hit rate limits and once did nothing for a whole day. By the end you will make your own automations fail safely.

## How it works

### Know the kinds of error

```text
   An error happens
        |
        v
   Is it likely temporary? (timeout, 429, 500-504)
        |-- yes --> retry with backoff, then alert if still failing
        |
        no
        v
   Is it about one bad record? (400, 404, invalid data)
        |-- yes --> put the record in "needs attention", continue the rest
        |
        no
        v
   Is it about the whole workflow? (401, 403, expired token)
        |-- yes --> stop now, alert the owner with the fix
```

| Kind | Examples | What to do |
| --- | --- | --- |
| **Temporary** | Network blips, timeouts, rate limits (HTTP 429), server errors (500 to 504) | Retry with backoff |
| **Permanent** | Wrong credentials (401, 403), bad input (400), missing record (404), invalid data | Stop, record, fix the cause |
| **Logic** | The automation ran but did the wrong thing, such as a field mapped wrongly | Only checks and monitoring catch these |

### Retry with backoff

Retry temporary errors a few times, waiting longer each time, so you do not hammer a struggling service:

```text
  attempt 1 --fails--> wait 5 s --> attempt 2 --fails--> wait 30 s
     --> attempt 3 --fails--> wait 2 min --> attempt 4 --fails--> alert
```

Respect a **Retry-After** header if the service sends one: it tells you exactly how long to wait. Always cap the number of retries.

### Idempotency: safe to run twice

Retries and manual reruns can repeat actions. Before creating something, such as an invoice, a payment or a message, check whether it already exists, using a unique key like the order id plus the status. If it exists, skip it. Then retries and reruns never create duplicates.

### Alerts that help

| Weak alert | Useful alert |
| --- | --- |
| "Workflow failed." | "Delivery SMS workflow, step 'Send SMS', order ORD-4471: 401 Unauthorized. The SMS provider token has expired. Renew it in Settings, Credentials, SMS provider. Run link: ..." |

Send alerts to a channel the owner actually watches, such as email, Slack, Teams or WhatsApp. Group repeated alerts, so one outage sends one message, not 500.

### Dead-letter queue

Records that failed permanently go into a **"needs attention"** list, sometimes called a dead-letter queue, with the reason. Someone fixes them and reprocesses them later. Nothing is silently lost.

### Partial failures

When processing 300 items, one bad item should not stop the other 299. Process items independently, collect the failures, and report them at the end.

### Monitoring

Track runs, failures and items processed per day. A workflow that suddenly processes **zero** items is often broken, even with no error at all, for example because an export came back empty.

### Ownership and a runbook

Every automation has a named owner and a short runbook: what it does, the common failures and how to fix each.

## A worked example

A logistics startup in Bengaluru runs an automation that sends delivery updates to customers by SMS and updates the order system: about 8,000 messages a day.

**The first month went badly:**

| Problem | Cause |
| --- | --- |
| Messages failed during evening peaks | The SMS provider rate-limited the workflow (HTTP 429) |
| Some customers got two messages | A failed run was rerun by hand, and earlier messages were sent again |
| One day, nothing was sent at all, with no error | A login token had expired; the step returned an empty result instead of failing loudly |

**The fixes:**

1. **Retries with backoff** on 429 and 5xx responses from the SMS provider, honouring its Retry-After header, with at most four attempts.
2. **A unique key** per message, order id plus status, checked before sending, so reruns never send duplicates.
3. **Expired or invalid credentials stop the run** at once and alert the owner with "token expired for SMS provider, renew at Settings, Credentials" instead of retrying.
4. **Failed records go to a "needs attention" sheet** with the reason; a button reprocesses them after fixing.
5. **A daily check** alerts if fewer than 1,000 messages were sent by 8 pm.

**The next month:**

| Measure | Month 1 | Month 2 |
| --- | --- | --- |
| Duplicate messages | About 900 | 0 |
| Messages lost to rate limits | About 1,200 | 0 (all retried) |
| Time to fix the next token expiry | About 9 hours (noticed by a customer complaint) | 20 minutes (the alert said what to do) |
| Records needing attention | Unknown | 35, all with a reason, all fixed within a day |

## Common mistakes

- **Retrying everything.** Permanent errors need fixing, not retries.
- **No duplicate protection.** Retries and reruns create double actions.
- **Alerts without details.** "Workflow failed" is not actionable.
- **One bad item stops the whole batch.** Handle items independently.
- **Watching only for errors.** A workflow doing nothing can look healthy.
- **Retrying without a cap or waits.** You make an outage worse and may get blocked.

## Practise

Read n8n's guide to error handling, linked below, and revisit the error-handling part of the N8N102 course.

1. **Retries.** Add retries with backoff to one API step in a workflow, and test with a deliberately failing endpoint.
2. **Duplicates and dead letters.** Add an idempotency check and a "needs attention" list for permanent failures.
3. **Alerts.** Create an alert that names the workflow, step, record and error, and a daily "too few items" check.

**You are done when you can** break your workflow three ways, with a temporary error, a permanent error and a bad item, and show the right behaviour for each.
