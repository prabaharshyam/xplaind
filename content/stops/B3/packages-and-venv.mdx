## What it is

Most useful Python does not come from Python itself. It comes from **packages** other people wrote: `requests` for web APIs, `pandas` for tables, `numpy` for arrays, and the official SDKs for AI model providers. You install them with **pip**, Python's package installer.

That creates a problem. Project A needs pandas version 2.1; project B needs 2.3. If both install into the same place, one breaks. The solution is a **virtual environment**: a private folder of installed packages for one project.

```text
   Without environments                 With environments
 +--------------------------+       +-----------------+  +-----------------+
 |  System Python           |       | project-a/.venv |  | project-b/.venv |
 |  pandas 2.3 (upgraded    |       | pandas 2.1      |  | pandas 2.3      |
 |  for project B)          |       | requests 2.32   |  | anthropic SDK   |
 |  -> project A breaks     |       +-----------------+  +-----------------+
 +--------------------------+         each project has its own, nothing clashes
```

A **requirements.txt** file lists the packages and versions a project needs, so anyone, on any machine, can recreate the same environment.

This lesson follows Nikhil, a student in Pune, as he gets a classmate's project running and stops his own projects from breaking each other. By the end you will set up a fresh environment for any project from its requirements file in under two minutes.

## How it works

### Create and activate an environment

Inside your project folder:

```bash
python -m venv .venv
```

Then activate it:

| System | Command |
| --- | --- |
| Windows (Command Prompt or PowerShell) | `.venv\Scripts\activate` |
| Mac or Linux | `source .venv/bin/activate` |

Your terminal prompt now starts with `(.venv)`. Anything you install goes into this project only. Type `deactivate` to leave it.

### Install packages

```bash
pip install requests pandas
pip list                       # what is installed in this environment
pip show pandas                # details and version of one package
```

### Record what you installed

```bash
pip freeze > requirements.txt
```

`pip freeze` prints every package with its **exact** version, such as `pandas==2.3.1`, so others install the same. A requirements file looks like:

```text
# shortened: pip freeze also lists every sub-dependency
certifi==2025.8.3
numpy==2.3.2
pandas==2.3.1
requests==2.32.5
```

### Recreate on another machine

After cloning a project, create and activate a fresh environment, then:

```bash
pip install -r requirements.txt
```

### Version specifiers

A requirements file can pin exactly or allow a range:

| Line | Means |
| --- | --- |
| `pandas==2.3.1` | Exactly this version: most reproducible |
| `pandas>=2.2` | This version or newer: may break when a new major version arrives |
| `pandas>=2.2,<3` | Any 2.x from 2.2 up: a common compromise for libraries |
| `pandas` | Whatever is newest today: avoid in projects others will run |

For an application you will deploy, pin exact versions so the server gets what you tested. For a library other people install, allow sensible ranges so it does not clash with their other packages. When you upgrade, upgrade on purpose: change the version, run your tests, then commit the new file.

### Packages for AI work

AI projects add a few habits. Model provider SDKs, such as the official Anthropic or OpenAI Python packages, change quickly, so pin them and read the release notes before upgrading. These SDKs read your API key from an environment variable, such as `ANTHROPIC_API_KEY`; set it in your shell or a `.env` file that is listed in `.gitignore`, never in the code. Large packages such as PyTorch can be hundreds of megabytes and depend on your computer's graphics card, so follow the project's own install instructions for them rather than a plain `pip install`.

### Keep it out of Git

Add `.venv/` to `.gitignore` and commit `requirements.txt` instead. Environments are large, hundreds of megabytes, and tied to one machine's operating system.

### Choose your editor's interpreter

In VS Code, select the `.venv` Python interpreter (Command Palette, "Python: Select Interpreter"). Otherwise the editor may use a different Python from your terminal and report packages as missing.

### Newer tools

| Tool | What it adds |
| --- | --- |
| `pip` and `venv` | Built in; enough to start |
| `uv` | Much faster installs and environment creation, with a lock file |
| Poetry | Dependency management and packaging with a lock file |

**Lock files** pin every sub-dependency too, not just the packages you named. The ideas stay the same: one environment per project, versions recorded in a file.

## A worked example

Nikhil, a student in Pune, clones a classmate's project that calls a weather API and plots temperatures for Indian cities. He runs it:

```text
$ python main.py
ModuleNotFoundError: No module named 'requests'
```

The project needs packages he does not have. He creates an environment and installs from the project's file:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

It works, and the chart of Chennai, Delhi and Shimla temperatures appears.

Later he adds a feature that needs `matplotlib`. He installs it, runs `pip freeze > requirements.txt`, and commits the updated file. His classmate pulls, runs `pip install -r requirements.txt`, and gets exactly the same version.

| Before | After |
| --- | --- |
| Everything installed into system Python | One `.venv` per project |
| Upgrading pandas for one assignment broke another | Projects cannot affect each other |
| "Works on my machine" | `requirements.txt` recreates the same setup anywhere |
| 400 MB repositories when `.venv` was committed | `.venv/` in `.gitignore`; only the small text file is shared |

A month earlier, Nikhil had installed everything into his system Python, and upgrading pandas for one assignment broke another. Separate environments ended that problem for good.

## Common mistakes

- **Installing into the system Python.** Projects then interfere with each other.
- **Forgetting to activate the environment.** Packages go to the wrong place, or appear "missing". Check for `(.venv)` in your prompt.
- **Committing `.venv` to Git.** Commit `requirements.txt` instead.
- **No version pins.** A future release can break your code; `pip freeze` records exact versions.
- **Editor using a different interpreter.** Select the project's `.venv` in your editor.
- **Running `pip` and `python` from different places.** Use `python -m pip install ...` to be sure they match.

## Practise

Read the Python Packaging User Guide's page on pip and virtual environments, linked below.

1. **Create.** Make a project folder with its own virtual environment and install `requests`.
2. **Rebuild.** Save `requirements.txt`, delete the environment, recreate it, and reinstall from the file.
3. **Share.** Add `.venv/` to `.gitignore` and push the project to GitHub without it.

**You are done when you can** set up a fresh environment for any project from its requirements file in under two minutes.
