## What it is

Most useful Python comes from **packages** other people wrote: `requests` for web APIs, `pandas` for tables, the official SDKs for AI model providers. You install them with **pip**, Python's package installer.

A **virtual environment** is a private folder of installed packages for one project. Each project gets its own, so installing a new version for one project cannot break another. A **requirements.txt** file lists the packages and versions a project needs, so anyone can recreate the same environment.

## How it works

**Create and activate an environment** inside your project folder:

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Mac or Linux:
source .venv/bin/activate
```

Your terminal prompt now shows `(.venv)`. Anything you install goes into this project only.

**Install packages.**

```bash
pip install requests pandas
pip list                       # what is installed
```

**Record what you installed.**

```bash
pip freeze > requirements.txt
```

`pip freeze` writes exact versions, such as `pandas==2.3.1`, so others install the same.

**Recreate on another machine.** After cloning a project, create and activate a fresh environment, then:

```bash
pip install -r requirements.txt
```

**Keep it out of Git.** Add `.venv/` to `.gitignore`; commit `requirements.txt` instead. Environments are large and machine-specific.

**Choose your editor's interpreter.** In VS Code, select the `.venv` Python interpreter so the editor and the terminal agree.

**Newer tools.** Tools such as `uv` and Poetry do the same jobs faster and with lock files that pin every sub-dependency. The ideas are identical: one environment per project, versions recorded in a file.

## A worked example

Nikhil clones a classmate's project that calls a weather API and plots temperatures for Indian cities. Running `python main.py` fails: `ModuleNotFoundError: No module named 'requests'`.

He creates an environment and installs from the project's file:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python main.py
```

It works. Later he adds a feature that needs `matplotlib`, installs it, runs `pip freeze > requirements.txt`, and commits the updated file. His classmate pulls, runs `pip install -r requirements.txt`, and gets the same version.

A month earlier, Nikhil had installed everything into his system Python; upgrading `pandas` for one assignment broke another. Separate environments ended that problem.

## Common mistakes

- **Installing into the system Python.** Projects then interfere with each other.
- **Forgetting to activate the environment.** Packages go to the wrong place, or are "missing".
- **Committing `.venv` to Git.** Commit `requirements.txt` instead.
- **No version pins.** A future release can break your code; `pip freeze` records exact versions.
- **Editor using a different interpreter.** Select the project's `.venv` in your editor.

## Practise

Read the Python Packaging User Guide's page on pip and virtual environments linked below.

1. Create a project folder with its own virtual environment and install `requests`.
2. Save `requirements.txt`, delete the environment, recreate it, and reinstall from the file.
3. Add `.venv/` to `.gitignore` and push the project to GitHub without it.

**You are done when you can** set up a fresh environment for any project from its requirements file in under two minutes.
