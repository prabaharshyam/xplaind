## What it is

A **test** is a small piece of code that runs your code with an input you choose and checks that the result is what you expect. A **unit test** checks one small part, usually one function, on its own. When the result is wrong, the test fails and tells you where.

Tests matter less for the code you write today than for every change after it. Six months from now, you or a teammate will change a function. Without tests, the only way to know nothing broke is to click through the app and hope. With tests, you run one command and know in seconds.

**pytest** is the standard testing tool for Python. You write plain functions whose names start with `test_` and use plain `assert` statements. pytest finds them, runs them, and when one fails it shows exactly which values differed.

Keep one limit in mind from the start: a test only catches what you thought to check. Choosing the cases is the real skill, and most of this lesson is about that choice.

## How it works

### Your first tests

A test has three steps, often called **arrange, act, assert**: prepare the inputs, call the code once, check the result.

Here is a GST helper. It uses `Decimal`, Python's exact decimal type, because money must not drift (the next part shows why). For this example, suppose the finance team's rule is: round to the paisa, and half a paisa goes up. That rule is a business decision, so confirm it with your own finance team.

```python
# gst.py
from decimal import Decimal, ROUND_HALF_UP

PAISA = Decimal("0.01")

def gst(amount: Decimal, rate: Decimal = Decimal("0.18")) -> Decimal:
    """GST on an amount, rounded to the paisa, half a paisa rounded up."""
    if amount < 0:
        raise ValueError("amount must not be negative")
    return (amount * rate).quantize(PAISA, rounding=ROUND_HALF_UP)
```

```python
# test_gst.py
from decimal import Decimal as D
import pytest
from gst import gst

def test_default_rate_is_18_percent():
    assert gst(D("100")) == D("18.00")

def test_half_paisa_rounds_up():
    # 100.25 x 0.18 = 18.045 exactly, so it must round up to 18.05
    assert gst(D("100.25")) == D("18.05")

def test_negative_amount_is_refused():
    with pytest.raises(ValueError, match="negative"):
        gst(D("-1"))
```

Run `pytest` in the folder and it prints `3 passed`. Each name says the behaviour it expects, so a failure report reads like a sentence. `match=` checks the error message too, so the test does not pass by accident on some other `ValueError`.

The loop you work in:

```flow
dir: LR
Write or change code -> Run pytest
Run pytest -[a test fails]-> Read the failure | which values differed
Read the failure -> Write or change code
Run pytest -[all pass]-> Commit
```

### Money and floats

Why not plain floats? Write the same function with `round(amount * rate, 2)` and the rounding test fails:

```
>       assert gst(100.25) == 18.05
E       assert 18.04 == 18.05
E        +  where 18.04 = gst(100.25)
```

A float stores numbers in binary, and most decimal fractions have no exact binary form. `100.25 * 0.18` is stored as 18.044999999999998..., just below the halfway point, so it rounds down. The error is not hidden in the 15th digit: the customer sees a bill that is one paisa wrong. Three rules follow:

- **Money:** use `Decimal` built from strings (`Decimal("100.25")`), or store whole paise as integers. Never write `Decimal(0.1)`: it copies the float's error and gives 0.1000000000000000055511151231257827....
- **Floats that are not money** (a model's confidence score, an average, a similarity): compare with `pytest.approx`, which by default allows a relative difference of one in a million.
- **Never `==` on computed floats.** It works on your laptop until the inputs change.

```python
def test_mean_score_needs_approx():
    # (0.1 + 0.2) / 2 is 0.15000000000000002, so == 0.15 alone fails
    assert (0.1 + 0.2) / 2 == pytest.approx(0.15)
```

### Parametrise instead of copying

Since 22 September 2025, GST has two main slabs, 5% and 18%, plus a special 40% rate for a small set of goods such as sugary fizzy drinks and large cars. (The old 12% and 28% slabs were removed, though a few special rates remain.) One parametrised test covers the slabs and the zero edges:

```python
@pytest.mark.parametrize("amount, rate, expected", [
    (D("1000"), D("0.05"), D("50.00")),
    (D("1000"), D("0.18"), D("180.00")),
    (D("1000"), D("0.40"), D("400.00")),
    (D("1000"), D("0"), D("0.00")),
    (D("0"), D("0.18"), D("0.00")),
], ids=["5-percent", "18-percent", "40-percent", "zero-rate", "zero-amount"])
def test_rates(amount, rate, expected):
    assert gst(amount, rate) == expected
```

Each row is reported as its own test, for example `test_rates[40-percent]`, so a failure names the case. Without `ids`, pytest names these rows `amount0-rate0-expected0` and so on, which are harder to read.

### Fixtures and conftest.py

A **fixture** is shared setup that a test asks for by naming it as a parameter. Put fixtures that many test files use in `conftest.py`; pytest loads that file on its own, with no import needed.

```python
# invoice.py
from decimal import Decimal
from gst import gst

def invoice_total(invoice: dict) -> Decimal:
    subtotal = sum((price for _, price in invoice["items"]), Decimal("0"))
    return subtotal + gst(subtotal, invoice["rate"])
```

```python
# conftest.py
from decimal import Decimal as D
import pytest

@pytest.fixture
def invoice():
    return {"items": [("Charger", D("999.00")), ("Cable", D("299.00"))],
            "rate": D("0.18")}
```

```python
# test_invoice.py
from decimal import Decimal as D
from invoice import invoice_total

def test_total_adds_gst_to_subtotal(invoice):
    assert invoice_total(invoice) == D("1531.64")   # 1298.00 + 233.64

def test_empty_invoice_totals_zero(invoice):
    invoice["items"] = []          # changes only this test's copy
    assert invoice_total(invoice) == D("0")
```

By default a fixture runs again for every test, so one test changing it cannot break another. Use a wider scope (`scope="session"`) only for setup that is slow and never changed, such as loading a large sample file. A fixture can `yield` its value and clean up after the `yield`. The built-in `tmp_path` fixture gives each test a fresh temporary folder for code that writes files.

### Fakes for model and API calls

Real model calls are slow, cost money and can give a different reply each time. In unit tests, replace them with a **fake** that returns a fixed reply. Replacing a part this way is called **mocking**.

If you write the code, the cleanest design is to pass the client in as a parameter. This is called **dependency injection**:

```python
# triage.py
import json

def classify(ticket: str, client) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    return json.loads(reply)["category"]
```

```python
# test_triage.py
from triage import classify

class FakeClient:
    def complete(self, prompt: str) -> str:
        return '{"category": "refund"}'

def test_classify_reads_category():
    assert classify("Money not returned", client=FakeClient()) == "refund"
```

Most code you inherit instead creates the client once, at module level. Then you swap it with pytest's `monkeypatch`, which puts the original back after the test. `unittest.mock.Mock` builds the fake and records how it was called. This version also handles bad replies, which is the code most worth testing in AI projects:

```python
# llm.py
class ModelClient:
    """Stands in for a real model SDK client."""
    def complete(self, prompt: str) -> str:
        raise RuntimeError("this would make a real, paid network call")
```

```python
# tickets.py
import json
from llm import ModelClient

client = ModelClient()          # created once, when the module is imported
CATEGORIES = {"refund", "delivery", "other"}

def classify(ticket: str) -> str:
    reply = client.complete(f"Classify this support ticket as JSON: {ticket}")
    try:
        category = json.loads(reply)["category"]
    except (json.JSONDecodeError, KeyError, TypeError):
        return "needs_review"
    return category if category in CATEGORIES else "needs_review"
```

```python
# test_tickets.py
from unittest.mock import Mock
import pytest
import tickets
from llm import ModelClient

def fake_client(reply: str) -> Mock:
    fake = Mock(spec=ModelClient)    # only methods the real client has
    fake.complete.return_value = reply
    return fake

def test_reads_category_and_sends_ticket(monkeypatch):
    fake = fake_client('{"category": "refund"}')
    monkeypatch.setattr(tickets, "client", fake)
    assert tickets.classify("Money not returned") == "refund"
    fake.complete.assert_called_once()
    assert "Money not returned" in fake.complete.call_args.args[0]

@pytest.mark.parametrize("reply", [
    "Sure! This looks like a refund.",   # prose, not JSON
    '{"label": "refund"}',               # wrong key
    '{"category": "lottery"}',           # unknown category
    "null",                              # valid JSON, wrong shape
    "",                                  # empty reply
])
def test_bad_reply_goes_to_review(monkeypatch, reply):
    monkeypatch.setattr(tickets, "client", fake_client(reply))
    assert tickets.classify("Where is my parcel?") == "needs_review"
```

Two gotchas catch even experienced engineers:

- **Patch where the name is used, not where it is defined.** If `tickets.py` had said `from llm import client`, it would hold its own copy of the name, so patching `llm.client` changes nothing and the real call still runs. Patch `tickets.client`.
- **A plain `Mock()` accepts any attribute.** A typo, or a method renamed in the real client, still "works" in the test and the bug reaches production. `Mock(spec=ModelClient)` raises `AttributeError` for anything the real class does not have.

Which to use:

| Situation | Use | Why |
| --- | --- | --- |
| New code you are writing | Pass the client in (dependency injection) | No patching; the test shows exactly what the code needs |
| Inherited code with a module-level client | `monkeypatch.setattr` on the module that uses it | Swaps one name for one test and restores it after |
| You must check what was sent, such as the prompt | `Mock(spec=...)` and `call_args` | Records every call; spec catches typos |
| Code that writes files | The built-in `tmp_path` fixture | A fresh folder per test, nothing left behind |
| Behaviour of the real model | An evaluation run on a golden set, not a unit test | Unit tests cannot judge answer quality |

### Unit tests versus evaluations

In AI projects, keep two kinds of test apart. Fast unit tests check your own logic: building prompts, parsing replies, validation, scoring. They run on every commit. Slower **evaluations** send a fixed golden set of inputs to the real model and score the answers, to catch a prompt change or model update that made results worse. The "Test sets and evals" lesson (P1) covers how to build them. Mixing the two makes everyday tests slow, costly and flaky.

A **marker** keeps them apart. Register it in `pyproject.toml`; `--strict-markers` turns a mistyped marker into an error instead of a warning:

```toml
[tool.pytest.ini_options]
addopts = "--strict-markers"
markers = ["eval: calls the real model on the golden set; run on a schedule"]
```

Tag each evaluation test with `@pytest.mark.eval`, and run `pytest -m "not eval"` on every commit.

### Running tests day to day

| Command | What it does |
| --- | --- |
| `pytest -x` | Stop at the first failure |
| `pytest -k rounding` | Run only tests whose names contain "rounding" |
| `pytest test_gst.py::test_half_paisa_rounds_up` | Run one test |
| `pytest --lf` | Rerun only the tests that failed last time |
| `pytest -m "not eval"` | Skip tests marked `eval` |
| `pytest --cov=. --cov-report=term-missing` | Show coverage, with the line numbers no test ran (needs the `pytest-cov` package) |

**Coverage** is the share of your code that ran during the tests. Read the "Missing" column: it lists lines no test ran, and those are your blind spots. Add `--cov-branch` to also see an `if` whose true or false side never ran. But coverage only proves code ran, not that anything checked the result: a test that calls `gst(D("100"))` with no `assert` still counts. Use it to find gaps, not as a score to reach 100%.

**Continuous integration (CI)** runs the same command on a clean machine for every push or pull request, and the team blocks merging when it fails. Two things break there that pass on your laptop. First, the CI machine has only the packages your project lists, so a missing dependency shows up. Second, CI machines often use UTC, five and a half hours behind India. A test about "today" can then fail when run between midnight and 5:30 am IST. Pass the date or clock into your code, and name the time zone (`ZoneInfo("Asia/Kolkata")`) instead of relying on the machine's setting.

### What to test first

In a project with no tests, start where a bug would cost the most:

1. **Money and anything legal:** totals, tax, refunds, limits.
2. **Data other systems read:** the JSON your API returns, the CSV you export.
3. **Code you are about to change:** write tests that pin down its current behaviour first, then change it.
4. **Every bug you fix:** first a test that reproduces it, then the fix. This is a **regression test**; it stops the same bug coming back.

For where tests sit in a project (a `tests/` folder, a `src` layout, the README commands), see the "Project tooling: environments, tests and logs" lesson.

## A worked example

Sneha maintains an invoice-extraction service at a logistics company in Chennai. The service reads a scanned invoice, pulls out the line amounts and the printed total, and rejects the invoice if they disagree. A customer reports that a genuine invoice was rejected. Its lines are freight ₹1,040.37, loading ₹128.98 and toll ₹10.65, which add up to ₹1,180.00, but the printed total is ₹1,180.50. The business allows up to ₹1 of rounding difference (an illustrative rule for this example).

**First, a failing test.** Before touching the code, she writes a test that reproduces the bug and expects the invoice to be accepted. She runs pytest and the new test fails. That proves the test really captures the bug; a test that passes before the fix proves nothing.

**Then the fix.** The old check was `sum(lines) == printed_total`. She changes it to allow a difference of up to ₹1.00, and the new test passes.

**Then the edges.** A limit has two edges, so she parametrises: exactly ₹1 over and exactly ₹1 under are accepted, and ₹1.01 either way is rejected. One case fails: exactly ₹1 over is rejected. The floats explain why. With Python 3.12 or later, `sum()` of the three lines gives `1179.9999999999998`, not 1180 (older versions, or adding with `+`, happen to give 1180.0), so the difference from 1181.00 is `1.0000000000002274`, just over the limit. She changes the extractor to hand over the amounts as text and the check to use `Decimal`:

```python
# validate.py
from decimal import Decimal

TOLERANCE = Decimal("1.00")          # business rule: up to Rs 1 of rounding

def total_is_valid(line_amounts: list[str], printed_total: str) -> bool:
    lines_total = sum((Decimal(a) for a in line_amounts), Decimal("0"))
    return abs(lines_total - Decimal(printed_total)) <= TOLERANCE
```

```python
# test_validate.py
import pytest
from validate import total_is_valid

LINES = ["1040.37", "128.98", "10.65"]      # add up to exactly 1180.00

@pytest.mark.parametrize("printed, expected", [
    ("1180.50", True),    # the customer's bug: 50 paise of rounding
    ("1181.00", True),    # exactly Rs 1 over: allowed
    ("1179.00", True),    # exactly Rs 1 under: allowed
    ("1181.01", False),   # just over the limit
    ("1178.99", False),   # just under the limit
], ids=["50-paise", "plus-1", "minus-1", "plus-1.01", "minus-1.01"])
def test_rounding_tolerance(printed, expected):
    assert total_is_valid(LINES, printed) is expected
```

All five cases pass. Note what found the float bug: not the customer's case, but the edge exactly on the limit. Edges are where bugs live.

**Finally, the whole suite.** She runs every test in the project, a few hundred, in under a minute. One unrelated test fails: it relied on the old exact match to reject a forged invoice whose total had been changed by a few paise. She talks to the team. They agree the forgery check needs its own rule, and she updates both. Without tests, that forgery check would have stopped working in production and nobody would have noticed.

## Common mistakes

- **Testing only the happy path.** Bugs live at the edges: zero, empty lists, negatives, the exact limit, very large values, missing fields.
- **One test that checks ten things.** When it fails, you cannot tell which. One behaviour per test, with a name that says what.
- **Tests that depend on each other or on order.** Each test should set up what it needs and pass when run alone. Shared lists or dictionaries at module level are the usual cause.
- **Real network or model calls in unit tests.** They are slow, cost money and make tests flaky. Fake them, and judge the real model with a scheduled evaluation run.
- **Comparing floats with `==`, or building `Decimal` from a float.** Use `Decimal("1.10")` for money and `pytest.approx` for other floats.
- **Patching the wrong place, or using a `Mock` without `spec`.** The real call still runs, or a typo passes silently.
- **Testing how the code works instead of what it does.** A test that checks which private helper was called breaks on every harmless refactor. Check outputs and visible effects.
- **A test you never saw fail.** Write it before the fix, or break the code on purpose once. A test that cannot fail protects nothing.
- **Depending on the clock or the machine's time zone.** Pass dates in and name `Asia/Kolkata` when the day matters.
- **Chasing 100% coverage.** Coverage shows what ran, not whether it was checked. Test the behaviour that matters.
