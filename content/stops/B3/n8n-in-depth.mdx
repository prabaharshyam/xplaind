## What it is

Your first n8n workflow had a trigger and a few nodes. Workflows that a business depends on go further. They process thousands of records, call APIs with strict limits, combine data from two systems that disagree, and must keep working when something fails at 3 am with nobody watching.

n8n has a building block for each of these:

| Building block | What it is for |
| --- | --- |
| **Sub-workflows** | Shared steps that many workflows call, like functions |
| **Paging, batches and waits** | Fetching and sending data without breaking an API's limits |
| **Merge** | Combining two sources by a shared id, including the items that do not match |
| **Code nodes** | Small JavaScript or Python snippets for logic the visual nodes do not cover |
| **AI nodes** | Reading messy text, such as emails, into fields that rules can check |
| **Error workflows** | Alerting a person when an automatic run fails |

This lesson follows a skincare brand in Bengaluru as it automates its daily payment reconciliation, the job of checking that every prepaid order was really paid out by the payment gateway.

```flow
title: Daily payment reconciliation
Schedule: 6 am IST -> Shopify: prepaid orders, last 10 days
Schedule: 6 am IST -> Gateway: settled payments, last 3 days | paged and paced
Shopify: prepaid orders, last 10 days -> Merge on payment id | keeps unmatched items from both sides
Gateway: settled payments, last 3 days -> Merge on payment id
Merge on payment id -> Code: flag each row -> Sub-workflow: upsert to sheet -> Slack: summary
Any failure -> Error workflow | alert finance-ops with the execution link
```

## How it works

### Items: the idea under everything

Every node receives a list of **items** and passes a list on. Each item is one JSON record, like one row of a sheet. Most nodes run once per item: ten items into Gmail means ten emails. An **expression** such as `{{ $json.email }}` reads a field of the current item. To read a field from an earlier node, name that node: `{{ $('Get orders').item.json.order_name }}`.

### Structure: one job per workflow

Keep each workflow to one job. Put shared steps in a **sub-workflow**: a separate workflow that starts with the **When Executed by Another Workflow** trigger and is called with the **Execute Sub-workflow** node. In the trigger, define the input fields you expect, such as `payment_id` and `flag`, rather than accepting any data. The calling node then lists exactly which fields to fill in, and a missing one is easy to spot.

Name nodes for what they do, such as "Get prepaid orders", not "HTTP Request 3", so anyone can read the canvas.

### Volume and rate limits

Most APIs return results a **page** at a time and limit how many requests you may send per second or minute. Three tools work together:

- **Pagination** fetches page after page until there are no more. The HTTP Request node has a pagination option, and many app nodes have a "Return All" switch that pages for you.
- **Batching** controls how fast you send. The HTTP Request node has a Batching option (items per batch, and a pause between batches). For more control, use **Loop Over Items** with a batch size and a **Wait** node inside the loop.
- **Retry On Fail**, in each node's settings, repeats a failed call. It allows at most five tries and at most five seconds between them, so it handles a brief blip, not pacing and not a long outage.

The pacing rule is simple arithmetic. If the limit is L requests a minute and each batch sends B requests, wait at least B × 60 ÷ L seconds between batches. For 20 requests a batch and a limit of 60 a minute, that is 20 seconds. Add some margin, because requests inside one batch can leave at the same moment.

```flow
dir: LR
Request a page | 100 rows -> Process the rows -> More pages?
More pages? -[yes, after a pause]-> Request a page
More pages? -[no]-> Next step
```

### Merging data, and keeping what does not match

The **Merge** node can combine two inputs by position, or by **matching fields**, such as a payment id that appears in both. For matching fields, the output setting decides what survives:

| Output choice | What comes out | Like |
| --- | --- | --- |
| Keep Matches | Only items found in both inputs | An inner join |
| Keep Non-Matches | Only items with no partner | The leftovers |
| Keep Everything | Matches and non-matches from both inputs | A full outer join |
| Enrich Input 1 or 2 | All of one input, plus matching data from the other | A left or right join |

The labels above are those in recent versions; check the dropdown in yours. For a reconciliation, the unmatched items are the findings, so Keep Matches would hide every problem. Choose Keep Everything; Keep Non-Matches alone would also drop the matched rows whose amounts you still need to check. Two more traps: if both inputs have a field called `amount`, one overwrites the other, so rename fields with an **Edit Fields** node first. And match on a key that is unique on both sides, such as a payment id, not one that can repeat, such as a customer's phone number.

### Code nodes

A **Code** node runs JavaScript or Python. In "Run Once for All Items" mode, the default, it reads every item with `$input.all()`, can read another node's items with `$('Node name').all()`, and must return a list of objects, each with a `json` key. This one adds an amount written the Indian way:

```js
// Mode: Run Once for All Items
return $input.all().map((item) => ({
  json: {
    ...item.json,
    amount_text: (item.json.amount / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' }),
  },
}));
```

For an amount of 12500000 paise, `amount_text` is "₹1,25,000.00". Prefer JavaScript unless you need Python: since n8n 2.0 the Code node runs native Python, which reads items as `_items` and has none of n8n's other built-in helpers. Keep Code nodes short and commented. If one grows past a screen, it is a small service hiding inside a node, and it is hard to test there.

### Schedules and time zones

A Schedule trigger fires in the workflow's time zone. A self-hosted instance defaults to America/New_York unless you set the `GENERIC_TIMEZONE` variable, so a "6 am" job can run in the Indian afternoon. Set the time zone to Asia/Kolkata in the workflow's settings, then check the run times in the executions list. Expressions like `$now` follow the same setting, so "yesterday" means yesterday in India.

### When to use AI, and when not to

Use an AI node only where rules cannot do the job: reading free text. A good example is a wholesale buyer's email that says "paid ₹48,300 against invoices 112 and 118, less TDS". An **Information Extractor** with structured output can turn that into invoice numbers and an amount, which an IF node then checks against your invoice list before a person confirms. The rule: if an IF, Switch or Code node can decide it, do not ask a model. A model writing "reasons" for money mismatches adds cost and can invent a cause that sounds right. Keep the AI Agent for tasks where the next tool call depends on what the last one returned, with the safeguards from the lesson "Automation with n8n".

### Reliability

| Practice | Why |
| --- | --- |
| Retry On Fail on API nodes | Brief network errors fix themselves on a second try |
| Idempotent writes | Upsert on a unique id, so a rerun updates rows instead of duplicating them |
| Overlapping time windows | Fetch a few days, not just yesterday, so one missed run heals itself the next day |
| An error workflow | Starts with an Error Trigger and posts the workflow, failing node and execution link to the team |
| Item-count checks | Alert when a step that should return rows returns none; zero items stop a branch, so turn on Always Output Data first |

Set the error workflow in the main workflow's settings, and publish the error workflow too. It fires only for automatic runs, not for runs you start by hand in the editor, so test it with a short schedule.

### Testing with pinned data

**Pin** the output of a node, such as the gateway call, and the editor reuses it instead of calling the API again. Production runs ignore pinned data. Keep a set of awkward pinned cases, such as a refund, an amount in odd paise and an order with no payment id, and rerun them after every change.

### Maintainability

As of November 2026, n8n's built-in Git source control is on its Business and Enterprise plans. On other plans, export workflows as JSON and commit them to Git yourself. Keep a separate test instance or project with its own credentials, and change production only after a test run passes.

### Self-hosting basics

n8n is not open source. Its Sustainable Use License allows self-hosting for your own business; the lesson "Automation with n8n" covers client work. Self-hosting, for example with Docker, makes you the operator:

- **Encryption key.** n8n encrypts saved credentials with a key it generates. If the data volume is not kept, a rebuilt container makes a new key and every credential is unreadable. Set `N8N_ENCRYPTION_KEY` yourself and back it up with the database.
- **Disk.** Execution data is pruned by default, after 14 days or 10,000 executions. Keep pruning on, and do not save full data for every successful run of a busy workflow.
- **Database and scale.** Use Postgres for anything serious. For high volume, **queue mode** uses Redis to hand runs to separate worker processes.
- **Updates.** n8n has had critical security flaws, including one in January 2026. Apply security releases within days.

## A worked example

A D2C skincare brand in Bengaluru sells about 1,500 orders a day on Shopify. For example, suppose about 60% are prepaid through Razorpay and the rest are cash on delivery. Each morning, Kavya in finance spends two hours checking that every prepaid order was paid out. Three facts about the gateway shape the design:

- **Settlements come later.** Razorpay's standard domestic cycle is T+2 working days from capture, and it varies by merchant. Yesterday's orders are not settled yet, so matching yesterday to yesterday flags everything.
- **Rows are keyed by payment id.** Each settlement row has an `entity_id` (a payment id starting `pay_`), `amount`, `fee`, `tax` and `credit`. Its `order_id` is Razorpay's own order id, not the Shopify order number. So the store must save the Razorpay payment id on each order at checkout; where it lives depends on your checkout app.
- **Amounts are in paise, and fees come off.** `amount` is the gross payment in paise. `fee` already includes the GST that `tax` shows, and `credit` is `amount` minus `fee`. Comparing `credit` with the order total flags every order. Compare `amount` instead, and check the fee on its own.

Kavya's workflow, with its time zone set to Asia/Kolkata:

| # | Node | What it does |
| --- | --- | --- |
| 1 | Schedule trigger and Sheets | Runs at 6 am IST; a Sheets node on the top branch, so it runs first, reads the results sheet as "Read results" |
| 2 | Shopify, then Filter | Gets orders from the last 10 days with Return All, keeps prepaid ones |
| 3 | HTTP Request | Gets settlement rows for the last 3 days, page by page, about one request a second |
| 4 | Filter and Edit Fields | Keeps payment rows (refunds have their own type), renames fields so nothing clashes |
| 5 | Merge | Matches on `payment_id`, Keep Everything |
| 6 | Code | Skips payments already marked ok, flags the rest (below) |
| 7 | Sub-workflow "Upsert result" | Sheets Append or Update Row, matched on `payment_id` |
| 8 | IF and Slack | Alerts if step 3 found no rows on a working day; otherwise posts counts and the sheet link |
| + | Error workflow | Alerts finance-ops with the execution link |

The Code node in step 6:

```js
// Mode: Run Once for All Items. Each item is one merged row.
const done = new Set($('Read results').all()
  .filter((i) => i.json.flag === 'ok').map((i) => i.json.payment_id));
const out = [];
for (const item of $input.all()) {
  const r = item.json;
  if (done.has(r.payment_id)) continue; // never downgrade an ok row
  const orderPaise = Math.round(Number(r.order_total) * 100);
  let flag = 'ok';
  if (!r.order_name) {
    flag = 'settled, no order found';
  } else if (!r.settlement_id) {
    const days = $now.diff(DateTime.fromISO(r.paid_at), 'days').days;
    flag = days > 5 ? 'settlement overdue' : 'waiting';
  } else if (r.gateway_amount !== orderPaise) {
    flag = 'amount differs';
  } else if (r.gateway_fee > Math.ceil(r.gateway_amount * 0.0236)) {
    flag = 'fee above contract'; // 2% plus 18% GST; use your rate
  }
  const paise = r.gateway_amount ?? orderPaise;
  const amount_text = (paise / 100).toLocaleString('en-IN', { style: 'currency', currency: 'INR' });
  out.push({ json: { ...r, flag, amount_text } });
}
return out;
```

`Math.round` turns the order total, which Shopify sends as text such as "1499.50", into whole paise, so tiny decimal errors, such as 114.99999 for ₹1.15, cannot cause a false alarm. `Math.ceil` allows for fee rounding. The 2% rate is only an illustration; use the rate in your contract. For example, a ₹1,000 UPI payment at 2% has a fee of ₹20 plus ₹3.60 GST, so `fee` is 2360 paise and `credit` is 97640.

Each flag leads to one clear action, written by a template, not a model:

| Flag | What it usually means | Who acts |
| --- | --- | --- |
| waiting | Paid, inside the normal settlement window | Nobody yet |
| settlement overdue | More than 5 days and still not settled | Finance raises it with the gateway |
| amount differs | Order edited after payment, or a part refund | Finance checks the order history |
| settled, no order found | Payment from another channel, or a missing payment id | Store team fixes the order record |
| fee above contract | Wrong pricing plan applied | Finance raises it with the gateway |

Because writes are upserts on `payment_id`, a row moves from "waiting" to "ok" on a later morning instead of piling up as duplicates. The skip matters: once a settlement drops out of the 3-day window, its order would otherwise look unsettled and be re-flagged "overdue". The 10-day order window covers payments that settle late. The 5-day limit is a trade-off: a long bank-holiday weekend can raise a few false alarms, which the team accepts rather than miss a real one.

**A bad morning.** One day the gateway's API returned errors at 6 am. Retries failed, and the error workflow posted the alert with the execution link. Kavya reran it at 9 am. The upserts meant no duplicates, and because each run fetches three days, even a missed day would have been covered the next morning.

## Common mistakes

- **One giant workflow.** Split shared steps into named sub-workflows with defined inputs.
- **Ignoring rate limits.** Page, batch and wait; retries are not pacing.
- **Merging with Keep Matches for a reconciliation.** It silently drops the problems you are looking for.
- **Comparing net with gross, or rupees with paise.** Compare like with like, in whole paise.
- **Matching yesterday to yesterday.** Settlements lag; use overlapping windows.
- **Non-idempotent writes.** Plain appends create duplicates on every rerun.
- **Leaving the time zone on the default.** Set Asia/Kolkata in the workflow settings.
- **Using AI where a rule would do.** Never let a model explain money.
- **Testing the error workflow by hand.** It only fires for automatic runs.
- **Losing the encryption key.** Back it up with the database before you need it.

1. **Volume.** Build a workflow that pages through at least 300 rows from an API or sheet and processes them in batches with a Wait. Work out the wait from the limit, and write the sum in a sticky note.
2. **Merge and write.** Merge two sources on a shared id with Keep Everything, flag each row in a short Code node, and write through a sub-workflow that upserts on the id. Pin one awkward case for each flag.
3. **Failure.** Set the time zone to Asia/Kolkata, add an error workflow, break a node on purpose, and let the workflow run on a short schedule. Confirm the alert, then rerun.

**You are done when you can** rerun your workflow twice in a row without creating duplicates, and show an error alert with a link to the failed execution.
