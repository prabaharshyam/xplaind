## What it is

Your first n8n workflow had a trigger and a few nodes. Real business automations go further: they process thousands of records, call APIs with strict limits, combine data from several systems, include AI steps, and must keep working when something fails at 3 am.

n8n has building blocks for each of these:

| Building block | What it is for |
| --- | --- |
| **Sub-workflows** | Reusable workflows called from others, like functions |
| **Loops and batches** | Processing items in groups to respect API limits |
| **Merge and split** | Combining data from two sources, or splitting lists into items |
| **Code nodes** | Small JavaScript or Python snippets for logic the visual nodes do not cover |
| **AI nodes** | Model calls, structured output parsers, and agent nodes with tools |
| **Error workflows** | Running when a workflow that names them in its settings fails, to alert someone |

```text
  [Schedule 6 am]
        |
        +--> [Shopify: orders, page by page] -----------+
        |                                                |
        +--> [Gateway: settlements, batch + wait] -------+
                                                         v
                                               [Merge on order id]
                                                         |
                                                 [Code: flag mismatches]
                                                         |
                                         [Sub-workflow: write row if new]
                                                         |
                                          [AI: explain each mismatch]
                                                         |
                                                 [Slack: summary]

  Any failure --> [Error workflow: alert finance-ops with execution link]
```

This lesson follows a skincare brand in Bengaluru as it automates daily order reconciliation. By the end you will build workflows that handle volume, limits, AI and failure.

## How it works

### Structure

Keep each workflow focused on one job. Put shared logic, such as "look up a customer" or "send an alert", in **sub-workflows** that other workflows call. Name nodes clearly: "Get open orders from Shopify", not "HTTP Request 3". A colleague, or you in three months, should understand the workflow from the canvas.

### Volume and rate limits

Many APIs limit how many requests you can make per second or minute, and return at most a page of results at a time. Use:

- **pagination**, to fetch results page by page instead of all at once;
- **Loop Over Items** with a batch size, to process items in groups;
- a **Wait** node between batches, to stay under the limit.

```text
  3,000 items --> [batch of 100] --> [API calls] --> [wait 1 s] --> next batch
```

### Merging data

The **Merge** node combines items from two branches, either by position or by a matching field, such as matching sheet rows to CRM contacts by email, or orders to payments by order id.

### Code nodes

Useful for parsing unusual formats, date maths, or formatting amounts the Indian way (₹1,25,000). Keep them short and commented. Complex logic is hard to test and maintain inside a code node; move it to a proper service if it grows.

### AI steps

Use a model node with a clear prompt and a **structured output parser**, so later nodes get reliable, named fields rather than free text. **Agent nodes** can call tools, such as other nodes or sub-workflows, for multi-step tasks. Treat them like any agent: give them only the tools they need, limit the number of steps, and require approval for risky actions such as payments.

### Reliability

| Practice | Why |
| --- | --- |
| Retries on flaky nodes | Temporary API errors fix themselves on a second try |
| Idempotent writes | Check whether a record already exists before creating it, so reruns never duplicate |
| An error workflow | Posts to your team chat with the workflow name, failing node and execution link |
| Item-count checks | Catch runs that quietly process nothing |

### Maintainability

Export workflows as JSON into Git, or use n8n's source control features where available. Keep separate development and production instances or projects, and store credentials per environment. Test changes in development before touching production.

### Self-hosting basics

Running n8n yourself, for example with Docker, gives you control over data. You then own backups of its database, updates, security and scaling. For high volume, **queue mode** runs executions on separate worker processes.

## A worked example

A D2C skincare brand in Bengaluru sells about 1,500 orders a day through its Shopify store. Every morning, the finance team spends two hours matching orders against payment gateway settlements and the accounting sheet. They automate it:

| # | Node | What it does |
| --- | --- | --- |
| 1 | Schedule trigger | Runs at 6 am |
| 2 | Shopify | Fetches yesterday's orders in pages of 250 |
| 3 | HTTP Request in a loop | Fetches settlements from the payment gateway's API in batches, with a 1-second wait to respect its limit |
| 4 | Merge | Joins orders and settlements on order id |
| 5 | Code | Flags mismatches: amount differs, settlement missing, refund not recorded; formats amounts in Indian style |
| 6 | Sub-workflow "write to accounting sheet" | Checks if a row for the order exists before adding, so reruns are safe |
| 7 | AI node with structured output | Writes a one-line explanation of each mismatch for the finance team |
| 8 | Slack | Posts totals and a link to the mismatch sheet |
| + | Error workflow | Alerts the finance-ops channel with the execution link on any failure |

**Results:**

| Measure | Before | After |
| --- | --- | --- |
| Finance team's morning reconciliation | About 2 hours | About 15 minutes reviewing flagged cases |
| Mismatches found per day | Varied, some missed | 20 to 40, all listed with a reason |

**A bad morning.** One day the payment gateway's API was down at 6 am. The node retried three times, then the error workflow posted the alert with a link to the failed execution. The team reran the workflow at 9 am. Because every write checked for an existing row first, the rerun completed with no duplicates.

## Common mistakes

- **One giant workflow.** Split it into sub-workflows with clear names.
- **Ignoring rate limits.** Paginate, batch and wait.
- **Non-idempotent writes.** Reruns create duplicates.
- **Logic buried in big code nodes.** Keep code small; move complex logic to a service.
- **No version control or test instance.** Changes to production break things silently.
- **AI output as free text.** Use a structured output parser so later steps get reliable fields.

## Practise

Complete n8n's N8N102 Integrations course, linked below, and read the hosting overview.

1. **Volume.** Build a workflow that processes at least 100 items from an API or sheet in batches, with a wait between batches.
2. **Merge, write, AI.** Add a merge of two data sources, a sub-workflow for writing records that checks for existing rows, and an AI step with structured output.
3. **Failure.** Add an error workflow that alerts you, break a node on purpose, and confirm the alert and a clean rerun. Error workflows do not run for manual test runs, so let the workflow run on its trigger.

**You are done when you can** rerun your workflow twice in a row without creating duplicates, and show an error alert with a link to the failed execution.
