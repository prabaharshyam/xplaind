## What it is

Your program does not have to know everything itself. A **web API** lets it ask another service for data or actions over the internet: today's weather, a map route, a payment's status, government open data, or an answer from an AI model. Every AI model provider works this way, so calling an API from Python is the core skill behind calling language models later.

You send an **HTTP request** to a URL. The service replies with:

- a **status code**: did it work?
- usually a body in **JSON**: the data.

```text
  Your Python program                                   Weather service
 +---------------------+   GET /weather?city=Chennai   +-----------------+
 | requests.get(...)   | ----------------------------> |                 |
 |                     |   headers: X-API-Key: ...     |                 |
 |                     |                               |                 |
 |                     | <---------------------------- |                 |
 | r.status_code = 200 |   200 OK                      |                 |
 | r.json()            |   {"city": "Chennai",         |                 |
 +---------------------+    "temp_c": 31.5}            +-----------------+
```

This lesson follows Anita, who builds a small air-quality dashboard for her city. By the end you will call a public API, check the status and read nested JSON safely.

## How it works

### The requests library

```python
import requests

r = requests.get("https://api.example.com/weather",
                 params={"city": "Chennai"}, timeout=10)
print(r.status_code)
data = r.json()          # JSON text becomes Python dictionaries and lists
print(data["temp_c"])
```

`params` adds query parameters to the URL, so this request goes to `.../weather?city=Chennai`.

### Status codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `200` | OK: it worked | Use the data |
| `400` | Bad request: something about your request is wrong | Check parameters and body |
| `401` / `403` | Not signed in, or not allowed | Check the API key and permissions |
| `404` | Not found | Check the URL or the item id |
| `429` | Too many requests | Slow down; wait and retry |
| `500` to `504` | The server failed | Often temporary; retry later |

Check before using the data. `r.raise_for_status()` raises an error for 4xx and 5xx codes, so your code does not carry on with an error reply as if it were data.

### JSON in Python

`r.json()` turns the reply into dictionaries (for JSON objects) and lists (for JSON arrays). Read nested values step by step:

```python
data["current"]["temp_c"]          # an object inside an object
data["results"][0]["location"]     # the first item of a list
```

Always print the whole reply once, to see its real shape, before writing code that reads it.

### Parameters, headers and bodies

| Part | Used for | Example |
| --- | --- | --- |
| `params` | Query parameters on the URL | `params={"city": "Pune"}` |
| `headers` | Keys, content type and other metadata | `headers={"Authorization": "Bearer ..."}` |
| `json` | A JSON body you send, usually with POST | `requests.post(url, json={"text": "..."})` |

### Timeouts

Without `timeout=`, a request to a slow or broken server can hang **forever**, freezing your program or your whole automation. Always set one, and handle `requests.Timeout`.

### Keys and secrets

Never write API keys in code you share or commit. Read them from an environment variable:

```python
import os
key = os.environ["AQ_KEY"]
```

### Retrying safely

Some failures fix themselves. A `429` or a `503` often succeeds a few seconds later. A simple, polite retry looks like this:

```python
import time

for attempt in range(3):
    r = requests.get(url, params=params, timeout=10)
    if r.status_code not in (429, 500, 502, 503, 504):
        break
    retry_after = r.headers.get("Retry-After", "")
    wait = int(retry_after) if retry_after.isdigit() else 2 ** attempt
    time.sleep(wait)
```

It retries only errors that are likely temporary, waits longer each time, and respects the server's `Retry-After` header if it sends one. Never retry a `401` or `404`: the request itself is wrong, and repeating it changes nothing.

### Reading API documentation

Every API's documentation answers the same questions, usually in this order: the **base URL**, how to **authenticate** (which header carries the key), the **endpoints** (paths such as `/latest` or `/holidays`), each endpoint's **parameters**, an **example response**, the **error codes** it uses, and its **rate limits**. Read these sections before writing code, and copy the example response into a file so you can test your parsing without calling the API every time. Calling an AI model's API later is exactly the same process: find the endpoint, send the key in a header, post a JSON body and read the JSON reply.

### Limits and cost

Most APIs limit requests per minute and some charge per call. Read the documentation's limits section, and when you get a `429`, wait and retry with growing delays instead of hammering the server.

## A worked example

Anita is building a small dashboard of air quality for her city. She uses a public API that returns current readings for a location.

```python
import os, requests

url = "https://api.airquality.example/v1/latest"
r = requests.get(url, params={"city": "Delhi"},
                 headers={"X-API-Key": os.environ["AQ_KEY"]}, timeout=10)

if r.status_code == 200:
    for reading in r.json()["results"][:5]:
        print(reading["location"], reading["parameter"], reading.get("value", "no reading"))
elif r.status_code == 429:
    print("Rate limited; try again in a minute")
else:
    print("Request failed:", r.status_code, r.text[:200])
```

(The URL here is illustrative; the lesson's resource shows real, working examples.)

| Run | What happened | Cause | Fix |
| --- | --- | --- | --- |
| 1 | `401 Unauthorized` | Her key was not set in the new terminal | `export AQ_KEY=...` before running |
| 2 | `200`, then `KeyError: 'value'` on one location | Some locations have no `value` field | Printed the full JSON; used `.get("value", "no reading")` |
| 3 | Hung for minutes | She had removed `timeout=` while testing | Put `timeout=10` back |
| 4 | Five readings printed | Working | Ready for the dashboard |

Printing the full JSON once, on the second run, saved her an hour of guessing.

## Common mistakes

- **Not checking the status code.** Code then fails confusingly on error replies.
- **No timeout.** A slow server can hang your program.
- **Guessing the JSON shape.** Print it and read it first.
- **API keys in code.** Use environment variables.
- **Ignoring rate limits.** Respect them, or you get blocked.
- **Assuming every field is always present.** Use `.get()` with a default for optional fields.
