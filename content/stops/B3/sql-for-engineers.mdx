## What it is

Almost every company you will work with keeps its customers, orders, tickets and payments in a relational database such as PostgreSQL, MySQL or SQL Server. **SQL** is the language for asking those databases questions. For an AI engineer, SQL is not optional. You use it to:

- **pull the data** an AI system needs, such as past tickets with their resolutions;
- **measure the baseline** before you build: "how long do refunds take today?";
- **check whether the system helped** after it ships.

Four ideas cover most of this work:

| Idea | What it does | Typical use |
| --- | --- | --- |
| **Joins** | Combine tables on a matching column | Orders with their customers' cities |
| **GROUP BY** | One row per group, with totals or averages | Refunds per city |
| **Window functions** | Calculate across related rows, keeping every row | Each customer's first ticket; moving averages |
| **Indexes** | Make lookups fast | Turning a 40-second query into 2 seconds |

```text
   customers               orders                  refunds
 +----+--------+      +----+-------------+      +----+----------+------------+
 | id | city   |<-----| id | customer_id |<-----| id | order_id | created_at |
 +----+--------+      +----+-------------+      +----+----------+------------+
          joined on matching ids to answer: "refunds per city"
```

This lesson follows a food delivery company in Hyderabad as you measure its refund baseline before building an AI assistant. By the end you will answer business questions with joins, grouping and window functions, and speed up a slow query.

## How it works

### Joins

A join combines tables on a matching column.

| Join | Keeps | Use for |
| --- | --- | --- |
| `JOIN` (inner) | Only rows that match on both sides | Orders that have a customer |
| `LEFT JOIN` | Every row from the left table; blanks where the right has no match | Customers with no orders; tickets with no reply |

```sql
-- customers who have never ordered
SELECT c.id, c.city
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

### GROUP BY

`GROUP BY` collapses rows into one row per group and computes aggregates: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`. Filter rows **before** grouping with `WHERE`; filter groups **after** with `HAVING`:

```sql
SELECT city, COUNT(*) AS refunds
FROM refunds r JOIN orders o ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY city
HAVING COUNT(*) > 100;
```

### Window functions

Window functions calculate across related rows **without** collapsing them:

| Function | Example | Gives |
| --- | --- | --- |
| `ROW_NUMBER()` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | 1, 2, 3 for each customer's rows in time order |
| `LAG(col)` | `OVER (PARTITION BY customer_id ORDER BY created_at)` | The previous row's value, for row-to-row comparison |
| `SUM(col)` | `OVER (ORDER BY day)` | A running total |
| `AVG(col)` | `OVER (ORDER BY day ROWS 6 PRECEDING)` | A seven-day moving average |

`PARTITION BY` splits rows into groups, like `GROUP BY`, but every row stays in the result.

### Indexes and query plans

Without an index, the database reads every row to find matches: a **sequential scan**. An index on `refunds(created_at)` lets it jump straight to the right rows.

```text
  No index: read 30,000,000 rows, keep 2,000,000       -> 40 s
  Index on created_at: jump to July 1, read forward    ->  2 s
```

Indexes speed up reads and slow down writes a little, so add them for the columns you filter and join on most. Run `EXPLAIN ANALYZE` before a query to see whether the database used an index or scanned the whole table, and how long each step took.

## A worked example

A food delivery company in Hyderabad wants an AI assistant for refund requests. Before building anything, you need the baseline: how long does a refund take today, by city?

```sql
SELECT c.city,
       COUNT(*) AS refunds,
       ROUND(AVG(EXTRACT(EPOCH FROM r.resolved_at - r.created_at) / 3600), 1) AS avg_hours
FROM refunds r
JOIN orders o    ON o.id = r.order_id
JOIN customers c ON c.id = o.customer_id
WHERE r.created_at >= DATE '2026-07-01'
GROUP BY c.city
ORDER BY avg_hours DESC;
```

Next, for the assistant's training examples, you want each customer's **first** refund request only, so repeat complainers do not dominate:

```sql
SELECT *
FROM (
  SELECT r.*,
         ROW_NUMBER() OVER (PARTITION BY o.customer_id ORDER BY r.created_at) AS n
  FROM refunds r JOIN orders o ON o.id = r.order_id
) t
WHERE n = 1;
```

**The slow query.** The baseline query takes 40 seconds on 30 million rows. `EXPLAIN ANALYZE` shows a sequential scan on `refunds` for the date filter. You ask the client's data team, who agree to `CREATE INDEX ON refunds (created_at)` on the read replica. The query now takes under two seconds.

| City | Refunds since July | Average hours to resolve |
| --- | --- | --- |
| Hyderabad | 48,200 | 31.4 |
| Vijayawada | 9,800 | 27.9 |
| Warangal | 4,100 | 22.6 |

You write the numbers and the query times in your notes. The table is the baseline your assistant must beat, and the index is a quick win that earns goodwill with the client's data team.

## Common mistakes

- **Joining and multiplying.** Joining orders to order items, then summing order totals, counts each order once per item. Aggregate at the right level before joining.
- **Inner join when you needed a left join.** Customers with no orders silently disappear from the report.
- **Filtering aggregates in WHERE.** `WHERE COUNT(*) > 5` fails; use `HAVING`.
- **Running heavy queries on the production database.** Ask for a read replica or an export. Slowing the client's live app is a bad first week.
- **Indexing everything.** Each index costs storage and write speed. Add them for real, slow queries, and confirm with `EXPLAIN ANALYZE`.
- **Comparing dates with text.** Use proper date types and literals such as `DATE '2026-07-01'`.
