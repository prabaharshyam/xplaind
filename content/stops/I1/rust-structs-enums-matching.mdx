## What it is

Rust gives you two ways to build your own types.

A **struct** groups related values under one name, like a row in a table: a student has a name, a roll number and marks.

An **enum** says a value is exactly one of several possibilities, and each possibility can carry different data: a payment is pending, successful with a reference number, or failed with a reason.

**Pattern matching** with `match` looks at a value, finds which shape it has, pulls out its data and runs the right code. The compiler checks that you handled every shape.

```flow
title: A struct has all of its fields (and)
Order -> id: u64
Order -> items: Vec<String>
Order -> total: u32
```

```flow
title: An enum is exactly one of its variants (or); match must handle every one
OrderStatus -> Placed
OrderStatus -> Preparing
OrderStatus -> OutForDelivery | carries rider
OrderStatus -> Delivered
```

A struct groups fields that all exist together; an enum says a value is exactly one of a fixed set of shapes.

## How it works

**Structs and methods.**

```rust
#[derive(Debug)]
struct Student {
    name: String,
    marks: Vec<u32>,
}

impl Student {
    fn new(name: &str) -> Self {
        Student { name: name.to_string(), marks: Vec::new() }
    }
    fn average(&self) -> f64 {
        if self.marks.is_empty() { return 0.0; }
        self.marks.iter().sum::<u32>() as f64 / self.marks.len() as f64
    }
    fn add_mark(&mut self, m: u32) {
        self.marks.push(m);
    }
}
```

`Self` means the type itself. `&self` borrows the struct to read it, `&mut self` borrows it to change it, and plain `self` takes ownership. `new` is just a convention for a constructor.

**Enums with data.**

```rust
enum Payment {
    Pending,
    Success { utr: String },
    Failed { reason: String },
}
```

**Option instead of null.** Rust has no null. A value that might be missing has the type `Option<T>`, which is just an enum: `Some(value)` or `None`. Because it is a different type from `T`, you cannot accidentally use a missing value; the compiler makes you deal with `None`. This removes the most common crash in other languages.

**match.**

```rust
fn message(p: &Payment) -> String {
    match p {
        Payment::Pending => "Waiting for the bank".to_string(),
        Payment::Success { utr } => format!("Paid. Reference {utr}"),
        Payment::Failed { reason } => format!("Payment failed: {reason}"),
    }
}
```

Patterns can do a lot more:

| Pattern | Matches | Example |
|---|---|---|
| A literal | one exact value | `1 => "one"` |
| A range | any value in the range | `90..=100 => "A grade"` |
| Several values | any of them | `"SL" \| "3A" => "budget"` |
| A variant with data | that variant, binding its fields | `Some(x) => x * 2` |
| A guard | the pattern, if a condition holds | `Some(m) if m > 35 => "pass"` |
| The wildcard | anything else | `_ => "other"` |

**if let** is a shortcut when you only care about one case: `if let Some(phone) = user.phone { send_sms(&phone); }`.

**Destructuring.** Patterns also pull structs and tuples apart: `let Student { name, .. } = s;` takes out the name, and `let (lat, lon) = point;` splits a pair. The `..` means "ignore the other fields". You will use this constantly in `match` arms and function parameters.

**Result is an enum too.** Errors use the same idea as Option: `Result<T, E>` is either `Ok(value)` or `Err(error)`. Once you are comfortable matching on Option, error handling in the next lesson will feel natural, because it is the same pattern applied to failures.

## A worked example

Vikram builds the order-tracking screen for a food delivery start-up in Kochi. The old JavaScript version stored the status as a string and the rider name in a separate field that was sometimes empty. Bugs crept in: "Out for delivery" screens with no rider, and typos like "Delivred" that matched no branch.

In Rust he models the states so that bad combinations cannot exist:

```rust
enum OrderStatus {
    Placed,
    Preparing { minutes_left: u32 },
    OutForDelivery { rider: String, phone: String },
    Delivered,
    Cancelled { refund: Option<u32> },
}

fn customer_text(s: &OrderStatus) -> String {
    match s {
        OrderStatus::Placed => "Order placed".into(),
        OrderStatus::Preparing { minutes_left } if *minutes_left <= 5 => "Almost ready".into(),
        OrderStatus::Preparing { minutes_left } => format!("Ready in about {minutes_left} min"),
        OrderStatus::OutForDelivery { rider, .. } => format!("{rider} is on the way"),
        OrderStatus::Delivered => "Delivered. Enjoy your meal".into(),
        OrderStatus::Cancelled { refund: Some(r) } => format!("Cancelled. Rs {r} refunded"),
        OrderStatus::Cancelled { refund: None } => "Cancelled".into(),
    }
}
```

A rider now exists only when the order is out for delivery. A refund is clearly either present or absent. A typo in a variant name will not compile.

Three months later the product team adds `PickedUpByCustomer`. Vikram adds the variant, and the compiler lists every `match` in the code base that does not handle it yet. Nothing is missed, and no customer sees a blank screen.

## Common mistakes

**Using strings or integers for states.** `status: String` invites typos and impossible values. Use an enum.

**Reaching for `unwrap()` on every Option.** It crashes on `None`. Use `match`, `if let`, `unwrap_or(default)` or `?` instead.

**Putting `_ =>` everywhere.** A wildcard silences the "not all cases handled" check, so a new variant slips through unnoticed. List the variants when you can.

**Huge structs with many Option fields.** If fields only make sense in certain states, the data is really an enum. Move each group of fields into the variant it belongs to.

**Forgetting `&` when matching on a borrowed value.** Match on `&self` or `s` by reference so you do not move the data out of it.
