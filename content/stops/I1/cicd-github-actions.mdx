## What it is

**Continuous integration (CI)** runs checks on every change: lint, type checks, unit tests, and for AI systems a small eval suite. A change that fails does not merge.

**Continuous delivery (CD)** takes a merged change through environments automatically: build an image, deploy to staging, run smoke tests, then deploy to production, often after a person approves.

GitHub Actions is one common way to do both. Workflows are YAML files in `.github/workflows/` that run on events such as a pull request or a push to main. GitLab CI, Azure DevOps and Jenkins work similarly; clients will have their own choice.

```text
  Pull request                 Merge to main
      |                              |
      v                              v
 [CI: lint, types,          [Build image, tag = commit hash]
  tests, smoke eval]                 |
      |                              v
  pass? -- no --> blocked     [Deploy to staging] --> [smoke tests]
      |                              |
     yes --> can merge               v
                              [Approval by a named reviewer]
                                     |
                                     v
                              [Deploy same image to production]
                                     |
                         problem? --> redeploy previous tag
```

This lesson follows the handover of a claims assistant to an insurer's engineering team in Kochi.

## How it works

**Triggers and jobs.** A workflow runs on events (`pull_request`, `push` to main, a tag, a manual dispatch). It contains jobs; each job runs steps on a fresh machine, called a runner.

**The CI job** checks out code, installs dependencies (with caching), runs lint, types and tests. For an AI app, add a small, fast eval: 20 golden questions against a fixed retrieval index, failing the build if accuracy drops below a threshold. Keep slow, costly evals for a nightly job.

**The build job** builds the Docker image, tags it with the commit hash and pushes it to the client's registry.

**Deploy jobs** use **environments**. A `staging` environment deploys automatically; a `production` environment requires a named reviewer's approval and has its own secrets. Secrets are stored in the CI system or fetched from the cloud at run time; never in the repository. Better still, let the runner sign in to the cloud with short-lived credentials through OpenID Connect instead of stored keys.

**Rollback.** Because each deploy uses an image tagged with a commit, rolling back means redeploying the previous tag. Make it a single button or command and practise it.

**What runs where, and how often:**

| Check | When | Typical time | Fails the build? |
| --- | --- | --- | --- |
| Lint and format | Every PR | Seconds | Yes |
| Type checks | Every PR | Under a minute | Yes |
| Unit tests with a fake model | Every PR | 1 to 3 minutes | Yes |
| Smoke eval, 20 golden questions | Every PR touching prompts or retrieval | 1 to 2 minutes | Yes, below a threshold |
| Full eval, hundreds of cases | Nightly | 10 to 60 minutes | Alerts the team |
| Load test | Before major releases | Varies | Blocks release if too slow |

**Caching.** Installing dependencies on every run is slow. Cache them, keyed on the lock file, so CI takes minutes, not ten. Fast CI gets used; slow CI gets bypassed.

**Branch protection.** In the repository settings, require the CI job to pass and at least one review before merging to main. Without this, CI is only advice.

**Secrets in practice.** The workflow needs some secrets: a model API key for the smoke eval, credentials to push images, credentials to deploy. Store them in the repository's or environment's secret settings, where they are encrypted and hidden in logs. Give each environment its own secrets, so a staging key can never touch production. For cloud access, prefer OpenID Connect: the cloud trusts the specific repository and branch, and issues a credential that expires within the hour. There is then no long-lived key to leak at all.

## A worked example

You hand over a claims-assistant to a Kochi insurer's engineering team. Their lead, Anjali, wants every change tested and nothing in production without her team's sign-off.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q
      - run: uv run python evals/smoke.py --min-accuracy 0.85
  deploy-staging:
    if: github.event_name == 'push'
    needs: test
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/build_push_deploy.sh staging ${{ github.sha }}
  deploy-production:
    needs: deploy-staging
    environment: production        # requires approval from the insurer's leads
    runs-on: ubuntu-latest
    steps:
      - run: ./scripts/build_push_deploy.sh production ${{ github.sha }}
```

A week later a teammate changes the prompt and the smoke eval drops from 0.89 to 0.78; CI fails and the PR cannot merge. Later a production deploy causes slow responses; Anjali redeploys the previous commit's image from the workflow page in two minutes, before most users notice.

**What changed for the insurer's team.** Before the pipeline, deploys happened when someone remembered, from a laptop, and nobody was sure which version was live. After it, every production version is a commit hash shown on the workflow page, every deploy has a named approver, and the smoke eval has blocked three prompt changes in two months that would each have reduced answer quality. Anjali says the most useful part is not speed but certainty: when a claims manager reports a bad answer, the team can say exactly which code and prompt produced it.

## Common mistakes

- **Tests only on main.** Problems are found after merging. Run CI on pull requests.
- **No eval in CI for prompt changes.** Prompt edits are code changes; test them.
- **Secrets in workflow files.** Use the CI system's secrets or short-lived cloud credentials.
- **Building different images per environment.** Build once, promote the same image through staging to production.
- **A rollback nobody has tried.** Practise it before you need it.

- **Flaky tests left in place.** A test that fails randomly teaches people to rerun CI until it passes, and then real failures get ignored too. Fix or remove flaky tests quickly.
- **Evals that call a live model on every PR without a budget.** Keep the PR eval small and cheap, cache what you can, and run the full suite on a schedule.

## Practise

Follow GitHub's Actions quickstart and the page on deployment environments.

1. Add a workflow that runs lint and tests on every pull request in one of your repositories.
2. Add a job that builds and pushes your Docker image tagged with the commit hash on merges to main.
3. Create staging and production environments, require your own approval for production, and practise a rollback to the previous image.

**You are done when you can** show a failing PR blocked by CI, an approval gate before production, and a rollback you performed.
