## What it is

**Continuous integration (CI)** runs checks on every pull request: lint, type checks, unit tests and, for AI systems, a small eval. Branch protection makes a failing change unable to merge.

**Continuous delivery (CD)** takes each merged change through environments automatically: build an image, deploy it to staging, smoke test it, then promote it to production after a person approves. Without that approval step it is called **continuous deployment**. Most client teams in banking, insurance and health want the approval.

GitHub Actions is one common way to do both. GitLab CI, Azure DevOps and Jenkins use the same ideas with different syntax; a client will have their own choice.

```flow
title: From pull request to production
Pull request -> CI: lint, types, tests, smoke eval -> Pass?
Pass? -[no]-> Merge blocked
Pass? -[yes]-> Review and merge to main
Review and merge to main -> Build one image | tag = commit hash
Build one image -> Deploy to staging -> Smoke test staging -> Approval by a named reviewer
Approval by a named reviewer -> Promote the same image to production -> Healthy?
Healthy? -[no]-> Redeploy the last good tag
```

This lesson follows the handover of a claims assistant to an insurer's engineering team in Kochi.

## How it works

### The parts of a workflow

| Part | What it is | In this lesson |
| --- | --- | --- |
| Workflow | A YAML file in `.github/workflows/` | `ci-cd.yml` and `rollback.yml` |
| Event | What starts it | A pull request, a push to main, a manual run |
| Job | A group of steps on one fresh machine (a runner) | test, smoke-eval, build, deploy-staging, deploy-production |
| Step | One command, or one ready-made **action** | `uv run pytest`, `docker/build-push-action` |
| Environment | A named deploy target with its own secrets and rules | staging, production |

Jobs run in parallel unless one `needs` another. Each job starts on a clean machine, so anything it needs (code, tools, credentials) it must fetch itself.

### What runs where, and how often

| Check | When | Typical time | Fails the build? |
| --- | --- | --- | --- |
| Lint, format, type checks | Every pull request | Under a minute | Yes |
| Unit tests with a fake model | Every pull request | 1 to 3 minutes | Yes |
| Smoke eval, 50 golden questions | Pull requests touching prompts, retrieval or evals | 2 to 4 minutes | Yes, if it falls clearly below main |
| Staging smoke test | After each staging deploy | Under a minute | Yes, blocks production |
| Full eval, hundreds of cases | Nightly | 10 to 60 minutes | Alerts the team |

The times are typical ranges, not measurements. The rule behind the table: the faster and cheaper a check, the earlier it runs.

### A smoke eval that does not flake

A model is not perfectly repeatable, so a small eval can pass and fail on the same code. With 20 questions, each question is worth 5 points: one answer flipping moves a score from 0.85 to 0.80. A gate that flips on rerun teaches people to press "Re-run" until it is green, and then real failures are ignored too. Four habits fix this:

- **Use about 50 cases.** Each case is then worth 2 points, not 5.
- **Use temperature 0** where your model supports it, and a fixed retrieval index.
- **Retry a failed case once.** A real regression fails twice; noise usually does not.
- **Compare with main, not a fixed number.** Store main's score in `evals/baseline.json` (a nightly job can refresh it) and fail only if the pull request is more than 2 cases worse. Keep a hard floor as well, so slow drift cannot pass.

The check `expected in answer` below is a crude smoke test: it rewards long answers that happen to contain the phrase. The nightly full eval should use stricter grading. The script decides with its exit code; any non-zero exit fails the job.

```python
import argparse, json, sys
from app.answer import answer   # your pipeline, called with temperature 0

p = argparse.ArgumentParser()
p.add_argument("--baseline", default="evals/baseline.json")
p.add_argument("--tolerance", type=int, default=2)   # cases, not percent
p.add_argument("--floor", type=float, default=0.80)
args = p.parse_args()

def ok(case):
    return case["expected"].lower() in answer(case["question"]).lower()

cases = [json.loads(line) for line in open("evals/smoke.jsonl")]
correct = sum(ok(c) or ok(c) for c in cases)          # one retry per failed case
base = json.load(open(args.baseline))["correct"]
print(f"smoke: {correct}/{len(cases)} correct, main has {base}")
failed = correct < base - args.tolerance or correct / len(cases) < args.floor
sys.exit(1 if failed else 0)
```

### Secrets, environments and OIDC

**Secrets** live in the repository's or environment's settings, encrypted and masked in logs, never in the repository. Give each environment its own secrets, so a staging key can never reach production. An environment's secrets stay locked until a required reviewer approves the job.

**Required reviewers.** You can name up to six people or teams; one approval is enough. You can also stop the person who started a deploy from approving it. On GitHub Free, Pro and Team, required reviewers work only in public repositories; private repositories need GitHub Enterprise. Check the client's plan before you promise an approval gate.

**Pull requests from forks get no secrets** (except a limited `GITHUB_TOKEN`). That is why the smoke eval below skips fork pull requests, which a maintainer then evaluates by hand. Avoid the `pull_request_target` trigger as a workaround: it runs with your secrets, so running a fork's code under it lets a stranger read them.

**OIDC instead of keys.** With `id-token: write`, a job can ask GitHub for a signed token that names the repository and environment, for example `repo:kochi-insure/claims-assistant:environment:production`. The cloud trusts tokens that match exactly that name and returns credentials that expire, by default after one hour on AWS. There is no long-lived key to leak. Azure and Google Cloud have the same pattern.

**Registry.** Pushing to GitHub's registry (GHCR) needs only `GITHUB_TOKEN`. But a service on AWS that pulls a private GHCR image needs a stored pull credential. If the client runs on AWS, pushing to their ECR registry is often simpler, because the IAM role already grants pull access.

### Supply chain: pin every action

A third-party action runs with access to your code and secrets. A version tag such as `@v4` is only a pointer, and its owner (or an attacker) can move it. In March 2025, attackers moved the tags of the popular `tj-actions/changed-files` action to malicious code that printed secrets into build logs (CVE-2025-30066). Workflows pinned to an earlier commit SHA kept running the safe code.

So pin every third-party action to its full 40-character commit SHA, with the version in a comment, and let Dependabot propose updates (add `package-ecosystem: "github-actions"` to `.github/dependabot.yml`). Read the diff before you merge an update. Two notes from checking on 28 November 2026:

- `astral-sh/setup-uv` no longer publishes moving major tags after v7, so `@v10` would not resolve. Its own README pins a SHA.
- GitHub now documents workflow lockfiles (`.github/workflows/actions.lock`, made with `gh actions-lock`) that pin actions used by your actions too. Its setup guide is listed for GitHub Enterprise Cloud; on other plans, use SHA pins.

### Speed, cost and safety switches

- **Caching.** `setup-uv` caches packages on GitHub-hosted runners by default. For other tools, cache on the lock file. Fast CI gets used; slow CI gets bypassed.
- **Concurrency.** Cancel an older run when someone pushes again to the same pull request. Never cancel a run on main: it may be halfway through a deploy. Give each deploy target its own concurrency group so two deploys never overlap.
- **Timeouts.** A job's default timeout is 360 minutes. Set `timeout-minutes` on every job so a stuck model call cannot burn six hours of runner time.
- **Path filters inside the job.** If you skip a whole workflow with `on.pull_request.paths`, a required check from it stays "Pending" and blocks the merge. So the smoke eval job always runs and its steps check what changed.
- **Least privilege.** Set `permissions: {contents: read}` at the top and add only what a job needs, such as `packages: write` or `id-token: write`.

### Branch protection

In the repository's rules for main, require the test and smoke-eval checks to pass and at least one review before merging. Without this, CI is only advice.

### The complete workflow

Action versions checked on 28 November 2026. All six declare the Node 24 runtime.

```yaml
name: ci-cd
on:
  pull_request:
  push:
    branches: [main]

permissions: {contents: read}
concurrency:                       # cancels old pull request runs only
  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: true
env:
  IMAGE: ${{ vars.IMAGE_REPO }}:${{ github.sha }}   # registry names must be lowercase

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - run: uv sync --frozen
      - run: uv run ruff check . && uv run mypy src && uv run pytest -q

  smoke-eval:
    if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions: {contents: read, pull-requests: read}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: dorny/paths-filter@ceb8a2b8f2d89434be7ff52d3de7ec3738c5cc9d # v4.0.3
        id: changed
        with:
          filters: |
            ai: ['prompts/**', 'src/retrieval/**', 'evals/**']
      - if: steps.changed.outputs.ai == 'true'
        uses: astral-sh/setup-uv@1db35dd8eee11c5894872e0b383ae6c406cf738d # v10.4.0
      - if: steps.changed.outputs.ai == 'true'
        run: uv sync --frozen && uv run python evals/smoke.py --tolerance 2
        env:
          ANTHROPIC_API_KEY: ${{ secrets.EVAL_API_KEY }}

  build:
    needs: test
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    timeout-minutes: 20
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: docker/login-action@8aa5831fb8d48d8f76594c7ddde61ae58019f550 # v4.8.0
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - uses: docker/build-push-action@c3c9e263c25d99ce0380d002d59b67737d91b0dc # v7.4.0
        with: {context: ., push: true, tags: "${{ env.IMAGE }}"}

  deploy-staging:
    needs: build
    environment: staging
    concurrency: {group: deploy-staging}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"   # health check plus five real questions

  deploy-production:
    needs: deploy-staging
    environment: production          # required reviewers; its own role and secrets
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 15
    permissions: {contents: read, id-token: write}
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/migrate.sh && ./scripts/deploy.sh "$IMAGE"   # same image, no rebuild
      - run: ./scripts/smoke_test.sh "${{ vars.BASE_URL }}"
```

`vars.DEPLOY_ROLE_ARN` and `vars.BASE_URL` are environment variables, so the same lines point at staging in one job and production in the other.

### Rollback, and why migrations decide whether it works

Because every image is tagged with its commit, rollback is a redeploy of the last good tag. Make it a manual workflow that uses the same production environment and approval:

```yaml
name: rollback
on:
  workflow_dispatch:
    inputs:
      sha: {description: "Commit of the last good image", required: true}
permissions: {contents: read, id-token: write}
jobs:
  rollback:
    environment: production
    concurrency: {group: deploy-production}
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: aws-actions/configure-aws-credentials@45666896f5d8e0f10ae255413f3a4cdd03bdc8f5 # v6.3.1
        with: {role-to-assume: "${{ vars.DEPLOY_ROLE_ARN }}", aws-region: ap-south-1}
      - run: ./scripts/deploy.sh "${{ vars.IMAGE_REPO }}:$SHA"
        env: {SHA: "${{ inputs.sha }}"}   # passed as a variable, not pasted into the script
```

Rolling back the app does not roll back the database. If release 42 renames a column, release 41's image will crash against the new schema. So run migrations as their own step before the deploy, and change the schema in **expand and contract** steps: release one adds the new column and writes to both; release two reads the new one; release three, weeks later, drops the old column. At every point, the previous image still works.

**Try it in your browser.** This checker finds jobs without timeouts and actions not pinned to a commit SHA. Paste in your own workflow and run it.

```python
import re, yaml

workflow = yaml.safe_load("""
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - uses: some-org/setup-thing@v2
      - run: pytest -q
""")
for name, job in workflow["jobs"].items():
    if "timeout-minutes" not in job:
        print(f"{name}: add timeout-minutes (the default is 360)")
    for step in job.get("steps", []):
        ref = step.get("uses", "")
        if ref and not ref.startswith("./") and not re.fullmatch(r"[0-9a-f]{40}", ref.split("@")[-1]):
            print(f"{name}: pin {ref} to a full commit SHA")
```

## A worked example

You hand over the claims assistant to the Kochi insurer's engineering team. Their lead, Anjali, wants every change tested and nothing in production without her team's sign-off. The insurer uses GitHub Enterprise Cloud with private repositories, so required reviewers are available. You set up the two workflows above. The numbers below are an illustration of how the gates behave.

**Day 1: setting up.** You create staging and production environments. Production lists Anjali and her deputy as reviewers, with self-review blocked. In AWS you create two IAM roles. The production role trusts only `repo:kochi-insure/claims-assistant:environment:production`. You delete the old access key that a contractor had left in a `.env` file. You record main's smoke score in `evals/baseline.json`: 46 of 50.

**Week 2: a prompt change.** A teammate shortens the system prompt to save tokens. The smoke eval runs because `prompts/` changed. First pass: 39 of 50. Two of the 11 failures pass on retry, so the score is 41 of 50 (0.82). That is 5 cases below main's 46, more than the tolerance of 2, so the check fails and the pull request cannot merge. A fixed threshold of 0.80 would have let it through. The teammate restores two sentences about policy numbers, scores 45, and merges.

**Week 5: a slow release.** A new retrieval setting passes every check but makes answers slow in production. Anjali opens the rollback workflow, pastes the previous commit hash and approves. The last good image is back in about two minutes, with no rebuild. The release had only added a column, so the old image runs fine against the database.

**What changed for the insurer.** Before, deploys happened from a laptop, and nobody was sure which version was live. Now every production version is a commit hash with a named approver. When a claims manager reports a bad answer, the team can say exactly which code and prompt produced it.

## Common mistakes

- **CI only on main.** Problems are found after merging. Run CI on pull requests and make it a required check.
- **A tiny eval with a fixed threshold.** It flakes, and people learn to rerun until green. Use about 50 cases, temperature 0, one retry, and compare with main.
- **Paid evals on every push.** Run the smoke eval only when prompts, retrieval or evals change; run the full suite nightly.
- **Skipping a whole workflow with a path filter.** Its required checks stay Pending. Filter inside the job.
- **Secrets in files, or long-lived cloud keys as secrets.** Use environment secrets, and OIDC for cloud access.
- **Rebuilding per environment.** Build once, promote the same image.
- **Tag-pinned third-party actions.** Tags move. Pin full SHAs and let Dependabot propose updates.
- **Workflow-wide cancel-in-progress.** A new merge kills a deploy halfway. Cancel pull request runs only.
- **No timeouts.** A stuck job runs for up to six hours.
- **A rollback nobody has tried, or a migration that breaks it.** Practise rollback, and use expand and contract.
- **Flaky tests left in place.** Fix or remove them quickly, or real failures get ignored too.

## When a lighter pipeline is enough

- **A personal project**: lint and tests on pull requests are plenty.
- **Platforms with built-in deploys**, such as Vercel previews, where CI only needs checks.
- **Notebooks and research code** that never deploy.

## From demo to production

What a client's engineering lead will check before taking over your pipeline:

- **Main is protected**: required checks and at least one review.
- **Production needs approval**, has its own secrets and a role that trusts only that environment.
- **No long-lived cloud keys** anywhere in GitHub.
- **Every action is pinned** to a commit SHA, with Dependabot on.
- **The AI gate is stable**, with a baseline and a nightly full eval.
- **Rollback is written down and has been run**, and migrations follow expand and contract.
