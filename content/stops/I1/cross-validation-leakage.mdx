## What it is

To know how a model will perform on new data, you must test it on data it never learned from, under conditions like real use.

- **Train, validation, test**: train on one part, tune choices on a validation part, and report final performance once on a test part kept untouched until the end.
- **Cross-validation**: repeat training and validation on several different splits (folds) and average, for a more stable estimate when data is limited.
- **Data leakage**: any way information from the validation or test data, or from the future, reaches training, making results look better than they will be.

```text
  Random k-fold (fine for independent rows)
  fold 1: [VAL][trn][trn][trn][trn]
  fold 2: [trn][VAL][trn][trn][trn]   ... average the 5 scores

  Time-based (rows ordered by time)
  split 1: [train: Jan-Jun ][val: Jul]
  split 2: [train: Jan-Jul    ][val: Aug]
  split 3: [train: Jan-Aug       ][val: Sep]   ... never train on the future

  Grouped (same patient = same fold)
  patient A's 4 admissions -> all in fold 2
  patient B's 2 admissions -> all in fold 5
```

This lesson follows a hospital network in Chennai whose readmission model looked brilliant until the leaks were found.

## How it works

**k-fold cross-validation.** Split the data into k folds (often 5). Train on k minus 1, validate on the remaining one; repeat k times. For classification, stratified folds keep class proportions equal.

**Time-based splits.** When data has time order (transactions, demand, churn), random splits leak the future into training. Train on earlier periods and validate on later ones; time-series cross-validation rolls this window forward.

**Grouped splits.** If the same customer, patient or store appears in many rows, keep all of its rows in the same fold. Otherwise the model memorises individuals and looks better than it is on new ones.

**Common sources of leakage.**

- *Preprocessing on all data*: scaling, imputing or target encoding computed before splitting uses information from validation rows. Fit preprocessing on the training fold only; scikit-learn **pipelines** do this automatically inside cross-validation.
- *Future features*: features computed with information after the prediction time.
- *Target proxies*: columns that are consequences of the outcome (a "closed reason" field when predicting churn).
- *Duplicates*: the same record appearing in train and test.
- *Tuning on the test set*: choosing models by test score turns it into a validation set; final results become optimistic.

**Signs of leakage.** Validation scores that are surprisingly high; a single feature with overwhelming importance; a large drop when scoring on a truly new period.

**Final check.** Before launch, score the model on the most recent period it never saw, ideally exactly as it will run in production.

**Which split matches which problem:**

| Data | Split to use | Why |
| --- | --- | --- |
| Independent rows, no time order | Stratified k-fold | Stable estimate, class balance kept |
| Transactions, demand, churn | Time-based, rolling forward | The model always predicts the future |
| Many rows per customer or patient | Grouped k-fold | New customers are what the model will see |
| Both time order and groups | Time-based, with groups not crossing the boundary | Combines both risks |

**The rule behind every split:** the validation data should look like the data the model will meet in real use, and training must use only information available at prediction time. If you can explain how your split mirrors production, you have probably chosen well.

**A leakage checklist before you trust a score.** For every feature, ask "would I know this value at the moment the prediction is made?" Fit every preprocessing step inside a pipeline. Remove exact duplicates across splits. Look at feature importance and question anything that seems too good. And score the most recent untouched period last.

**Leakage from feature engineering.** Many leaks enter through features built from event logs: "number of support calls", "last status", "days since last payment". Each must be computed only from events before the prediction moment. A safe habit is to fix a "prediction time" column for every row and filter every source table to events before it when building features.

## A worked example

A Chennai hospital network predicts 30-day readmission from discharge records.

The first notebook reported AUC 0.91 with random 5-fold cross-validation. Concerns:

1. Many patients have several admissions. With random folds, the same patient appeared in training and validation. **Grouped folds by patient**: AUC 0.83.
2. Missing lab values were filled with the mean computed on the whole dataset before splitting. Moving imputation into a pipeline: AUC 0.82.
3. A feature "follow-up appointment cancelled" was sometimes recorded after readmission. Removing it: AUC 0.78.
4. Training on 2023 to 2025 admissions and testing on the first half of 2026: AUC 0.77.

The honest number, 0.77, is what the clinical team planned around. In the six-month pilot, live AUC was 0.76.

| Fix | AUC after the fix |
| --- | --- |
| Random 5-fold (start) | 0.91 |
| Grouped folds by patient | 0.83 |
| Imputation inside a pipeline | 0.82 |
| Removed the post-readmission feature | 0.78 |
| Trained on 2023-2025, tested on early 2026 | 0.77 |
| Live in the six-month pilot | 0.76 |

The drop from 0.91 to 0.77 was not the model getting worse. It was the measurement getting honest, and it is why the pilot held no surprises.

## Common mistakes

- **Random splits on time-ordered data.**
- **The same entity in train and test.** Group by customer, patient or store.
- **Preprocessing before splitting.** Use pipelines.
- **Repeatedly checking the test set.** Keep it for the final report.
- **Ignoring suspiciously good scores.** Investigate before celebrating.

- **Tuning with cross-validation, then reporting the cross-validation score as final.** After many tuning rounds, even the cross-validation score is optimistic. Keep a separate final test set.
- **Assuming leakage is rare.** It is one of the most common reasons models fail after launch. Check for it every time, especially with features built from logs or event tables.
