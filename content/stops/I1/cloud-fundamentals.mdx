## What it is

A public cloud rents you computers, storage, networks and ready-made services, billed by use. AWS, Microsoft Azure and Google Cloud offer nearly the same building blocks under different names. Enterprises usually follow a group-wide choice, and banks, insurers and pharma companies often add rules about where data may sit.

This lesson goes deep on Azure, because the course resources are Microsoft Learn paths. Every step has a close match on the other clouds, shown in the table further down.

An AI deployment uses about seven kinds of service:

- **Compute**: where your code runs.
- **Storage**: files and documents.
- **Databases**: structured data, often PostgreSQL with the pgvector extension for embeddings.
- **Networking**: virtual networks, private endpoints, the one public entry point.
- **Identity and access**: who and what can do which actions.
- **Managed models**: hosted model APIs, where the deployment type decides where prompts are processed.
- **Monitoring**: logs, metrics and alerts, so you can see what happened.

**Shared responsibility.** The provider secures the buildings, hardware and managed services. You own what you configure: your data, who can access it, which endpoints are public, and what you spend. The lesson "Cloud security basics" goes deeper.

```flow
title: The document assistant in Central India, inside one virtual network
Staff | Entra ID sign-in -> Application Gateway | the only public entry, HTTPS
Application Gateway -> Container Apps | internal-only environment, managed identity
Container Apps -[private endpoint]-> Blob Storage
Container Apps -[private access]-> PostgreSQL with pgvector
Container Apps -[secret reference]-> Key Vault
Container Apps -[private endpoint]-> Foundry model | regional Standard deployment
Container Apps -> Log Analytics
```

This lesson follows a pharma company in Hyderabad as you design its document assistant on Azure.

## How it works

### Regions and zones

A region is a group of data centres in one area. Azure has four in India: Central India (Pune), South India (Chennai), West India (Mumbai) and India South Central (Hyderabad), which launched in August 2026. AWS has Mumbai and Hyderabad; Google Cloud has Mumbai and Delhi.

Some regions have availability zones: separate data centres with their own power and cooling, so replicas spread across zones survive one failing. Not every region has zones or every service, so check Azure's products-by-region page for each service you plan to use.

Choose a region in this order:

1. **Residency**: what the client's policy, contracts and regulators require.
2. **Availability**: are all your services, and the model with the right deployment type, offered there?
3. **Latency**: distance to users. Every Indian region is close enough for a chat app.
4. **Price**: prices differ a little between regions; this matters least.

Write the reasons down; the client's cloud team will ask.

### Compute choices

| You need | Choose | Why |
| --- | --- | --- |
| An HTTP API in a container (most AI apps) | Container Apps | Replicas, scaling, HTTPS and revisions are built in |
| Short jobs triggered by events or a timer | Container Apps jobs or Azure Functions | Pay only while the job runs |
| To fit the client's existing platform | AKS (managed Kubernetes) | Only if their platform team already runs it |
| GPUs or full control of the machine | Virtual machines | You patch and scale them yourself |

Container Apps bills for the CPU and memory of running replicas. `--min-replicas 0` scales to zero when idle, but the first request after a quiet spell waits for a cold start. For a staff tool, one warm replica is a fair trade.

### Storage and databases

Use Blob Storage for documents and Azure Database for PostgreSQL (flexible server) for records and vectors; backups, patching and failover come built in. Two details catch people out:

- pgvector must be allow-listed before it can be created: set the server parameter `azure.extensions` to `vector`, then run `CREATE EXTENSION vector;`. The extension's name is `vector`, not `pgvector`.
- Choose **private access** (`--vnet` and `--subnet`) when you create the server. Decide it up front: switching later takes a migration with downtime.

### Networking and private endpoints

Everything sits in a virtual network. The Container Apps environment gets its own subnet and is internal-only, so the app has no public address. The only public entry is an Application Gateway, or the client's existing gateway.

Blob Storage, Key Vault and Foundry are reached through **private endpoints**: a private IP address for the service inside your network. Then turn off each service's public network access. The classic failure: the endpoint exists, but no private DNS zone (for example, `privatelink.blob.core.windows.net`) is linked to the network. The name still resolves to the public address, which you just closed, and every call fails.

### Identity

Give the app a **managed identity**: Azure issues it short-lived tokens, so there is no key to store or leak. Grant it roles at the narrowest scope that works:

- **Storage Blob Data Reader** on one blob container, not the whole subscription.
- **Key Vault Secrets User** on one vault.
- **Cognitive Services OpenAI User** on the Foundry resource.
- **AcrPull** on the container registry.

Two gotchas. Management roles such as Owner and Contributor let you change a resource but not read its data with your own token; that needs a data role. And role assignments can take a few minutes to apply, so a 403 right after granting may fix itself.

People sign in through the company's Microsoft Entra ID, never with shared accounts.

### Managed models and the residency trap

Microsoft Foundry (renamed from Azure AI Foundry in November 2025) hosts models under the client's Azure contract. The **deployment type**, not the resource's region, decides where prompts are processed:

| Deployment type | Where prompts can be processed | Use when |
| --- | --- | --- |
| Global (Standard or provisioned) | Any Azure region where the model runs | No residency rule; you want the most quota |
| Data Zone | Inside a Microsoft-defined zone: US, EU or Asia Pacific | The rule allows a multi-country zone |
| Standard or provisioned, regional | The deployment's own region | Data must be processed in India |

Stored data stays in the resource's geography for every type; what changes is where each request is processed. A Global deployment on a Central India resource can still send a prompt abroad. New models are often offered as Global only at first, so check the region-availability table, and the deployment dialog in the portal, before you promise residency. AWS has the same switch: an India inference profile (model IDs starting `in.`) routes only between Mumbai and Hyderabad, while a `global.` profile can route anywhere.

The app calls its deployment with its managed identity, so there is no API key at all:

```python
from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token = get_bearer_token_provider(DefaultAzureCredential(), "https://ai.azure.com/.default")
client = OpenAI(base_url="https://docassist-ai.openai.azure.com/openai/v1/", api_key=token)
reply = client.chat.completions.create(
    model="docassist-chat",  # your deployment's name, not a model ID
    messages=[{"role": "user", "content": "Summarise this stability report: ..."}])
```

### Quotas

Model throughput is limited by a quota in tokens per minute, per model, per region, per subscription. GPU virtual machine quota often starts at zero on a new subscription. Increases are not instant and can be refused, so request quota in week one, not launch week.

### Deploy it from the command line

These commands build what the diagram shows; the `$` variables hold IDs from earlier steps.

```bash
# 1. Create the identity first, so it can be granted access before the app exists.
az identity create -g rg-docassist -n id-docassist -l centralindia
ID=$(az identity show -g rg-docassist -n id-docassist --query id -o tsv)
PRINCIPAL=$(az identity show -g rg-docassist -n id-docassist --query principalId -o tsv)
CLIENT_ID=$(az identity show -g rg-docassist -n id-docassist --query clientId -o tsv)

# 2. Least privilege. Repeat for Key Vault Secrets User, AcrPull and Cognitive Services OpenAI User.
az role assignment create --assignee-object-id "$PRINCIPAL" --assignee-principal-type ServicePrincipal \
  --role "Storage Blob Data Reader" --scope "$STORAGE_ID/blobServices/default/containers/source-pdfs"

# 3. An internal-only environment on your own subnet, sending logs to Log Analytics.
az containerapp env create -g rg-docassist -n env-docassist -l centralindia \
  --infrastructure-subnet-resource-id "$APPS_SUBNET_ID" --internal-only true \
  --logs-destination log-analytics --logs-workspace-id "$WORKSPACE_GUID" --logs-workspace-key "$WORKSPACE_KEY"

# 4. The app: ingress reachable only inside the network, secrets by reference, a hard ceiling on replicas.
az containerapp create -g rg-docassist -n docassist-api --environment env-docassist \
  --image acrdocassist.azurecr.io/docassist-api:3f9c2e1 \
  --registry-server acrdocassist.azurecr.io --registry-identity "$ID" --user-assigned "$ID" \
  --secrets "db-url=keyvaultref:https://kv-docassist.vault.azure.net/secrets/db-url,identityref:$ID" \
  --env-vars DATABASE_URL=secretref:db-url AZURE_CLIENT_ID="$CLIENT_ID" \
  --ingress external --target-port 8000 --cpu 1 --memory 2Gi --min-replicas 1 --max-replicas 5
```

`AZURE_CLIENT_ID` tells `DefaultAzureCredential` which user-assigned identity to use; without it, token requests can fail. `--max-replicas` is your real cap on compute spend.

### Logs, metrics and cost

Container Apps sends console logs to a Log Analytics workspace. Add Application Insights for request times and errors, and alert on error rate and slow responses. Logs are billed per gigabyte ingested, so do not log full prompts or documents: it costs money and copies sensitive data.

The bill for an AI app is usually led by model tokens, then the database, compute, logs and data leaving the cloud. Tag every resource with project and environment so the bill can be split. Set a budget with alerts on day one:

```bash
az consumption budget create-with-rg -g rg-docassist -n docassist-pilot \
  --amount 125000 --category Cost --time-grain Monthly --time-period start-date=2026-12-01 \
  --notifications "{at80:{enabled:true,operator:GreaterThan,threshold:80,contact-emails:[cloud-alerts@example.com]}}"
```

The start date must be the first of a month, no more than three months ahead. The amount is in the subscription's billing currency. A budget only alerts: it does not stop anything, and cost data can arrive hours late. Send alerts to a shared mailbox or channel, not one person.

### Infrastructure as code

Once the design works, describe it in Bicep (Azure's own language) or Terraform (any cloud), changed only through reviewed pull requests. See the lesson "Environments, secrets and Terraform".

| Building block | Azure | AWS | Google Cloud |
| --- | --- | --- | --- |
| Serverless containers | Container Apps | ECS on Fargate | Cloud Run |
| Managed Kubernetes | AKS | EKS | GKE |

## A worked example

A Hyderabad pharma company on Azure wants a document assistant for its regulatory team. Requirements: data stored and processed in India, no public database, sign-in with company accounts, and a pilot of about 1,500 questions a day.

**1. Region.** India South Central in Hyderabad is nearest, but it opened in August 2026 and Microsoft is adding services over time. Suppose the products-by-region page shows everything the design needs in Central India: you choose it and note Hyderabad for later.

**2. Model.** Suppose the team's first-choice model is offered in India only as Global Standard. That fails the processing rule. Suppose another model is offered as regional Standard in Central India and passes the team's 40 test questions: you deploy that one. You request its tokens-per-minute quota the same day.

**3. Network and identity.** The design follows the diagram: an internal Container Apps environment behind the company's Application Gateway; Blob Storage, Key Vault and Foundry through private endpoints with their DNS zones; PostgreSQL with private access. One user-assigned identity holds the four roles listed earlier, each at the narrowest scope.

**4. Cost.** Estimate before you build. Every price below is a supposed figure for illustration, not a quote; replace each with the Azure pricing calculator's number for your region on the day you check. You can run it on this page.

```python
# Illustrative prices only. Replace each with the Azure pricing calculator's figure.
replica_rupees_per_hour = 8           # suppose: one replica, 1 vCPU and 2 GiB
replica_hours = (2 * 12 + 1 * 12) * 30  # 2 replicas by day, 1 at night
fixed = {"PostgreSQL": 12_000, "Blob, Key Vault, private endpoints": 3_000,
         "Log Analytics": 4_000, "Data transfer out": 500}

questions = 1_500 * 30                 # per month
input_tokens, output_tokens = 4_000, 500  # per question, with retrieved chunks
rupees_per_m_in, rupees_per_m_out = 250, 1_000  # suppose

compute = replica_rupees_per_hour * replica_hours
infra = compute + sum(fixed.values())
tokens = questions * (input_tokens * rupees_per_m_in + output_tokens * rupees_per_m_out) / 1e6
print(f"compute ₹{compute:,}  infrastructure ₹{infra:,}  tokens ₹{tokens:,.0f}")
print(f"total ₹{infra + tokens:,.0f} a month, ₹{(infra + tokens) / questions:.2f} per question")
```

It prints infrastructure ₹28,140 and tokens ₹67,500: ₹95,640 a month, or ₹2.13 a question. Tokens cost more than all the infrastructure together, so optimise them first.

| Line (illustrative) | Monthly | What drives it | How to reduce it |
| --- | --- | --- | --- |
| Model tokens | ₹67,500 | Questions × tokens per question | Fewer, shorter retrieved chunks; cache repeated answers |
| PostgreSQL | ₹12,000 | Server size and storage | Start small; resize on measured load |
| Container Apps | ₹8,640 | Replica-hours | One replica at night; scale to zero for dev |
| Log Analytics | ₹4,000 | Gigabytes of logs ingested | Log metadata, not prompts |
| Blob, Key Vault, endpoints | ₹3,000 | Stored data, endpoints per hour | Archive old versions |
| Data transfer out | ₹500 | Data leaving Azure | Keep traffic inside the region |

The client is billed in rupees, so the budget is 1,25,000 a month with an alert at 80% (₹1,00,000), just above the ₹95,640 estimate, so the alert means real overspend rather than firing every month. `--max-replicas 5` and a per-user limit of 60 questions an hour cap a runaway loop long before the budget email arrives.

**5. Review.** Cloud teams usually reject outside designs for public endpoints, stored keys, foreign regions or unclear model processing. This design avoids all four, uses services they already run, and comes with the diagram and a one-page note on region and deployment type. Their only change is their naming convention.

## Common mistakes

- **Learning three clouds shallowly.** Learn one properly, then translate.
- **Trusting the resource's region for model residency.** Global and Data Zone deployments can process prompts outside India. Check the deployment type.
- **Public databases and storage.** Use private access and private endpoints, and turn public network access off.
- **A private endpoint without its private DNS zone.** The name resolves to the closed public address and every call fails.
- **Keys in code or settings.** This includes storage account keys copied from the portal. Use managed identities and Key Vault references, and turn off shared-key access.
- **Owner or Contributor instead of a data role**, or roles granted at subscription scope "to make it work".
- **Treating a budget as a cap.** It only alerts. Set `--max-replicas` and rate limits.
- **Counting compute but not tokens and logs**, often the larger lines in AI apps.
- **Requesting quota in launch week.** Increases are not instant.
- **Untagged resources**, so nobody can tell which project costs what.

## When you need less cloud

- **A prototype or demo**: a platform such as Vercel, Render or Railway with a hosted database is faster. Move when real data arrives.
- **The client runs everything on-premises**: learn their platform instead.
- **A small internal tool with no sensitive data**: one Container App with built-in sign-in may be enough; a full private network is overkill.

## From demo to production

- **Everything as code.** Bicep or Terraform in the repository, reviewed in pull requests; no manual portal changes in production.
- **Separate environments.** Different resource groups or subscriptions for dev and prod, each with its own budget.
- **Guardrails by policy.** An Azure Policy that allows only Indian regions enforces residency even when someone makes a mistake, and another can deny public network access.
- **Resilience.** Use zone redundancy where the region offers it, test a database restore, and choose a second Indian region for disaster recovery if the client needs one.
- **Alerts people act on.** Error rate, slow responses, token use per day and quota use, sent to a shared channel with a named owner.
- **A design record.** Region, deployment type, network boundaries and identities, with the reason for each, ready for the client's review.
