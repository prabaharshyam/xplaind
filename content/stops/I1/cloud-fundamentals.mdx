## What it is

A public cloud rents you computers, storage, networks and ready-made services by the hour or by use. The three big providers, AWS, Microsoft Azure and Google Cloud, offer nearly the same building blocks under different names. Indian enterprises often follow a group-wide choice; banks and government-linked clients may also require Indian regions or a specific provider's sovereign offering.

You do not need every service. An AI deployment uses about six kinds:

- **Compute**: where your code runs.
- **Storage**: files and documents.
- **Databases**: structured data, often PostgreSQL with pgvector.
- **Networking**: private networks, load balancers, DNS.
- **Identity and access**: who can do what.
- **Managed AI**: hosted model APIs from the cloud, which may matter for data agreements.

```flow
title: An app in an Indian region, for example Mumbai, inside a virtual network
Users | company SSO -> Load balancer | HTTPS, in the public subnet
Load balancer -> Serverless containers | the app, in a private subnet, with a least-privilege role
Serverless containers -> Managed PostgreSQL
Serverless containers -> Object storage
Serverless containers -> Managed model API
```

This lesson follows a pharma company in Hyderabad as you design its document assistant on Azure.

## How it works

**Regions and zones.** Each region (Mumbai, Hyderabad, Pune, Delhi and others in India, depending on the provider) has several zones, separate data centres. Spread instances across zones for resilience. Pick the region by latency to users, by data residency rules and by which models are offered there.

**Compute choices**, from most to least managed: serverless containers (Cloud Run, Azure Container Apps, or AWS ECS on Fargate, including ECS Express Mode; AWS App Runner is closed to new customers) where you give an image and get a URL; managed Kubernetes (EKS, AKS, GKE) when the client's platform team runs one; virtual machines when you need GPUs or full control. For most AI APIs, serverless containers are the fastest safe start.

**Storage and databases.** Object storage (S3, Blob Storage, Cloud Storage) for documents. Managed PostgreSQL for relational data and vectors. Use managed services: backups, patches and failover come built in.

**Networking.** Resources sit in a virtual network with private subnets. Databases should have no public address; your app reaches them privately. Outside traffic arrives through a load balancer with HTTPS.

**Identity.** Give each service its own identity (a role or managed identity) with only the permissions it needs, rather than storing long-lived access keys. People sign in through the company's single sign-on.

**Managed models.** Each cloud resells major models (Amazon Bedrock, Microsoft Foundry with Azure OpenAI, Google Vertex AI). Clients often prefer these because the data stays under their existing cloud contract and region.

**Cost.** Compute, managed databases, data transfer out and model tokens make up most bills. Use the provider's pricing calculator before you build, and set a budget alert on day one.

**The same building blocks, three names:**

| Building block | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| Serverless containers | ECS on Fargate (Express Mode) | Container Apps | Cloud Run |
| Managed Kubernetes | EKS | AKS | GKE |
| Object storage | S3 | Blob Storage | Cloud Storage |
| Managed PostgreSQL | RDS, Aurora | Azure Database for PostgreSQL | Cloud SQL, AlloyDB |
| Service identity | IAM role | Managed identity | Service account |
| Secrets | Secrets Manager | Key Vault | Secret Manager |
| Managed models | Bedrock | Microsoft Foundry (Azure OpenAI) | Vertex AI |

Learn one cloud properly, then use a table like this to translate.

**Deploy a container in an Indian region.** On Google Cloud, one command deploys a private service with its own identity and secrets from Secret Manager:

```bash
gcloud run deploy claims-api \
  --image asia-south1-docker.pkg.dev/my-project/apps/claims-api:3f9c2e1 \
  --region asia-south1 \
  --service-account claims-api@my-project.iam.gserviceaccount.com \
  --no-allow-unauthenticated \
  --set-secrets MODEL_API_KEY=model-api-key:latest,DATABASE_URL=db-url:latest \
  --min-instances 1 --max-instances 10 --cpu 1 --memory 1Gi
```

`--no-allow-unauthenticated` means only callers with permission (a load balancer, a gateway or signed-in users through it) can reach it. `--max-instances` caps cost if traffic spikes. AWS (ECS on Fargate) and Azure (Container Apps) take the same ideas in different syntax: an image, a region, an identity, secrets by reference, and scaling limits.

**A budget alert on day one.**

```bash
gcloud billing budgets create --billing-account=XXXXXX-XXXXXX-XXXXXX \
  --display-name="claims-pilot" --budget-amount=20000INR \
  --threshold-rule=percent=0.5 --threshold-rule=percent=0.9 --threshold-rule=percent=1.0
```

Every cloud has an equivalent. Send alerts to a shared channel, not one person's inbox.

**Models through your cloud.** Calling a model through the client's cloud keeps traffic under their contract and identity controls. With Anthropic's SDK, the Bedrock client uses the same message shape:

```python
from anthropic import AnthropicBedrock

client = AnthropicBedrock(aws_region="ap-south-1")      # uses the service's IAM role, not a key
reply = client.messages.create(
    model="<the model id shown in your Bedrock console>", max_tokens=300,
    messages=[{"role": "user", "content": "Summarise this claim note: ..."}])
```

Check which models and features each Indian region offers before promising data residency; some arrive in Indian regions later than in others.

**Where the money goes.** For a typical AI app, model tokens and managed databases dominate, then compute, then data transfer out of the cloud. Tag every resource with the project and environment so the bill can be split, and look at the cost breakdown weekly in the first month.

**Private by default.** Put databases and vector stores on private networks with no public address, reach model services through private endpoints where offered, and expose only the load balancer or gateway to the internet.

## A worked example

A Hyderabad pharma company on Azure wants a document assistant for its regulatory team. Requirements: data stays in India, no public database, sign-in with company accounts.

Your design:

- **Region**: Central India for everything, after checking the required model is offered there through the company's Azure AI agreement.
- **Compute**: Azure Container Apps running your FastAPI image, scaling from 1 to 5 instances.
- **Storage**: Blob Storage for source PDFs; Azure Database for PostgreSQL with pgvector for chunks, reachable only from the app's private network.
- **Identity**: the app uses a managed identity with read access to one storage container and the database, and no stored keys. Users sign in with Microsoft Entra ID.
- **Cost**: the calculator estimates about ₹55,000 a month before model tokens, with tokens estimated separately from expected usage. A budget alert is set at 80%.

The client's cloud team approves in one review, mainly because every choice matches their existing patterns.

| Line of the monthly estimate | What drives it | How to reduce it |
| --- | --- | --- |
| Container Apps | Instances and hours running | Scale to one instance at night |
| PostgreSQL | Instance size, storage | Start small; scale with measured load |
| Blob Storage | Gigabytes stored | Archive old versions |
| Data transfer | Data leaving the cloud | Keep traffic inside the region |
| Model tokens | Requests × tokens | Shorter prompts, caching, routing easy questions to a smaller model |

**Why the review went smoothly.** The client's cloud team rejects most outside designs on the same three points: public endpoints, stored keys and regions outside India. Your design avoided all three, used services their team already ran, and came with a diagram showing every network boundary. Their only change was a naming convention for resources.

## Common mistakes

- **Learning three clouds shallowly.** Learn one properly; translating names to another takes a day.
- **Public databases.** A database with a public address is the most common serious cloud mistake.
- **Long-lived access keys in code.** Use service identities and short-lived credentials.
- **Ignoring data transfer and model costs.** They can exceed compute. Estimate them.
- **Picking a region for latency alone.** Check residency rules and model availability first.

- **No budget alert.** A forgotten GPU machine or a runaway loop can cost lakhs in a weekend. Set alerts on the first day.
- **Services left publicly reachable** when they should sit behind a gateway or load balancer.
- **No maximum instance count**, so a traffic spike or a bug scales the bill without limit.
- **Untagged resources**, so nobody can tell which project costs what.

## When you need less cloud

- **A prototype or demo**: a platform such as Vercel, Render or Railway and a hosted database is faster.
- **The client runs everything on-premises**: learn their platform instead.
- **A single static site with an API key on a server function**: a full virtual network is overkill.

## From demo to production

- **Choose regions** for users, data residency and model availability, and record why.
- **Use service identities and secret references**, never stored keys.
- **Keep data services private**, with only the gateway public.
- **Set budgets and maximum instances** from day one.
- **Tag resources** by project and environment, and review costs weekly at first.
