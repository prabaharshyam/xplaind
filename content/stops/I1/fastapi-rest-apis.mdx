## What it is

A REST API lets other programs use your system over HTTP. Each **endpoint** is a URL plus a method: `POST /tickets` creates a ticket, `GET /tickets/42` reads one. The caller sends JSON and gets JSON back, with a **status code** that says what happened.

FastAPI is a Python framework for building these APIs. You write ordinary functions with type hints and Pydantic models; FastAPI turns them into endpoints that validate input, convert output to JSON and publish interactive documentation at `/docs`. It also runs async code natively, which suits services that wait on model APIs.

```text
  Caller (another team's app)
      |  POST /claims/triage   {"policy_no": "MOT1234567", "description": "..."}
      v
  [FastAPI]
      |-- validate body with Pydantic --- fails? --> 422, list of bad fields
      |-- inject model client (Depends)
      v
  [your function] --> model API --- down? --> 503 "try again shortly"
      |
      v
  [response_model filters output]
      |
      v
  200 {"category": "motor", "summary": "Rear bumper damage"}
```

This lesson follows an insurance broker in Kochi that wants other teams to call a claims-triage service.

## How it works

**Methods.** GET reads and must not change anything. POST creates or triggers work. PUT replaces, PATCH updates part, DELETE removes. Keeping to these meanings lets caches, retries and other engineers guess correctly.

**Status codes.** 200 OK and 201 Created for success. 400 for a malformed request, 401 when the caller is not signed in, 403 when they are but may not do this, 404 when the thing does not exist, 422 when the body fails validation (FastAPI's default), 429 when they are sending too much. 500 means your code broke, and 503 means a dependency, such as the model provider, is down.

**Models.** A Pydantic model on the request body means FastAPI rejects bad input with a 422 and a list of exactly which fields failed, before your function runs. A `response_model` controls what goes back, so an internal field such as a cost figure never leaks by accident.

**Dependencies.** FastAPI's `Depends` injects shared things, such as the database session, the current user or a model client, into each endpoint. In tests you swap them for fakes.

**Testing.** `TestClient` calls your app in memory, with no server, so endpoint tests run in milliseconds.

**Status codes callers rely on:**

| Code | Meaning | Caller's usual reaction |
| --- | --- | --- |
| 200, 201 | Success, or created | Use the result |
| 400 | Malformed request | Fix the request; do not retry |
| 401 | Not signed in | Sign in, then retry |
| 403 | Not allowed | Stop; ask for access |
| 404 | Not found | Check the id |
| 422 | Body failed validation | Fix the named fields |
| 429 | Too many requests | Wait, then retry |
| 500 | Your code broke | Report it |
| 503 | A dependency is down | Retry later with backoff |

**Designing endpoints that age well.** Use nouns for resources (`/claims`, `/claims/{id}`) and methods for actions. Put a version in the path or a header (`/v1/claims`) so you can change the API later without breaking callers. Return the same error shape everywhere, for example `{"detail": "..."}`, so callers can handle errors in one place. And document every endpoint in the code with a summary and examples; FastAPI shows them at `/docs` automatically, which is often the only documentation other teams will read.

## A worked example

A Kochi insurance broker wants other teams to send claim descriptions and get back a category and a summary.

```python
from fastapi import FastAPI, HTTPException, Depends
from pydantic import BaseModel, Field

app = FastAPI(title="Claims triage")

class ClaimIn(BaseModel):
    policy_no: str = Field(pattern=r"^[A-Z]{3}\d{7}$")
    description: str = Field(min_length=20, max_length=5000)

class ClaimOut(BaseModel):
    category: str
    summary: str

@app.post("/claims/triage", response_model=ClaimOut, status_code=200)
async def triage(claim: ClaimIn, llm=Depends(get_llm)):
    try:
        result = await llm.classify(claim.description)
    except ProviderDown:
        raise HTTPException(503, "Triage is unavailable; try again shortly")
    return ClaimOut(category=result.category, summary=result.summary)
```

A request with policy number "abc123" never reaches the model: FastAPI returns 422 naming the field. If the model provider is down, callers get a 503 they can retry, not a confusing 500.

The test fakes the model:

```python
from fastapi.testclient import TestClient

def test_triage_returns_category():
    app.dependency_overrides[get_llm] = lambda: FakeLLM("motor", "Rear bumper damage")
    r = TestClient(app).post("/claims/triage",
        json={"policy_no": "MOT1234567", "description": "Car was hit from behind at a signal"})
    assert r.status_code == 200 and r.json()["category"] == "motor"
```

Open `/docs` and the broker's other teams can try the endpoint in the browser, with the request schema already written for them.

**What other teams noticed first.** The broker's mobile team integrated in a day, mostly because `/docs` showed every field, its rules and an example, and because bad requests came back with a 422 naming the exact field. When the model provider had a short outage, their app showed "Triage is busy, try again in a minute" for the 503 instead of crashing, because the status code told it what kind of failure it was.

## Common mistakes

- **Returning 200 for errors.** A body saying `"error": true` with status 200 breaks every retry and monitoring tool. Use the right code.
- **Returning your database rows directly.** Internal fields leak. Always set a response model.
- **Blocking calls in async endpoints.** A synchronous model client inside `async def` freezes the server. Use an async client, or declare the endpoint with plain `def` so FastAPI runs it in a thread pool.
- **No timeout on the model call.** One hung request ties up a worker forever. Set timeouts and return 503 or 504.
- **Skipping input limits.** Without a maximum length, someone pastes a 300-page document and your token bill jumps.
