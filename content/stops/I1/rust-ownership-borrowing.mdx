## What it is

Every program has to answer one question: when is a piece of memory no longer needed? C and C++ leave it to you, which leads to crashes and security holes when you free too early, too late or twice. Java, Go and Python use a garbage collector that finds unused memory while the program runs, which costs time and causes pauses.

Rust answers the question at compile time with **ownership**. Each value has exactly one owner, a variable. When the owner goes out of scope, Rust frees the value right there. No collector, no manual freeing, no double frees.

To use a value without taking it, you **borrow** it with a reference. The **borrow checker** is the part of the compiler that makes sure every borrow is safe.

```text
 OWNERSHIP                         BORROWING
 let a = String::from("Goa");      let a = String::from("Goa");
 let b = a;   // move              let r1 = &a;   // reader
   a  ──X     (no longer valid)    let r2 = &a;   // another reader  OK
   b  ──► "Goa"                    let w  = &mut a; // writer while
                                                    // readers live? NO
 end of scope: b dropped, freed    rule: many readers OR one writer
```

## How it works

**Moves.** Assigning a heap value, or passing it to a function, moves ownership:

```rust
let city = String::from("Mysuru");
take(city);            // ownership moves into the function
// println!("{city}"); // error: value borrowed here after move
```

Small fixed-size values such as integers, floats, `bool` and `char` implement **Copy**, so they are copied instead of moved. That is why `let y = x;` with numbers leaves both usable.

**Borrows.** Add `&` to lend a value without moving it. The function signature says what it needs:

| Signature | Meaning | Caller keeps the value? |
|---|---|---|
| `fn show(s: &String)` | read-only borrow | yes |
| `fn add(s: &mut String)` | borrow that can change it | yes, and sees the change |
| `fn consume(s: String)` | takes ownership | no |
| `fn copy_it(n: i32)` | Copy type, copied in | yes |

**The rule.** At any moment a value can have either any number of `&T` readers or exactly one `&mut T` writer. This is how Rust prevents data races at compile time: two threads cannot write the same data at once, because two writers cannot exist.

**Borrows end when they are last used,** not at the end of the block. Modern Rust is smart about this, so many "errors" disappear if you simply finish using a reference before changing the original.

**Clone when you really need two copies.** `.clone()` makes an independent copy. It is the right tool sometimes, but cloning everything to silence the compiler wastes memory.

**Lifetimes.** When a function returns a reference, the compiler must know which input it came from, so it can check the returned reference does not outlive that data. Usually it works this out. When it cannot, you name the lifetime:

```rust
fn longer<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() >= y.len() { x } else { y }
}
```

`'a` says: the result lives no longer than both inputs. It changes nothing at run time; it only lets the compiler check.

**Slices are borrows too.** `&s[0..3]` borrows part of a string and `&v[1..]` borrows part of a vector. A slice is just a pointer and a length, so it costs nothing to create, and the borrow checker treats it like any other reference. This is why idiomatic functions take `&str` and `&[T]`: they accept a whole string or vector, or just a piece of one.

**Ownership and threads.** The same rules make concurrency safe. To send data to another thread you move it there, and to share it you wrap it in types such as `Arc` and `Mutex` that enforce the readers-or-writer rule at run time. You will meet these in the concurrency lesson.

## A worked example

Meera builds a small tool for her college placement cell in Chennai. It keeps student names and shortlists them.

Her first try:

```rust
fn main() {
    let mut students = vec![String::from("Arjun"), String::from("Fatima")];
    let first = &students[0];
    students.push(String::from("Rohit"));
    println!("First: {first}");
}
```

The compiler refuses: "cannot borrow `students` as mutable because it is also borrowed as immutable". The reason is real, not pedantic. Pushing can make the vector move its contents to a bigger block of memory, which would leave `first` pointing at freed memory. In C++ this compiles and sometimes crashes in production.

She fixes it by finishing with the reader before changing the list:

```rust
let first = students[0].clone();  // or print it here, before the push
students.push(String::from("Rohit"));
println!("First: {first}");
```

Then she splits the work into functions, choosing the borrow each one needs:

```rust
fn print_all(list: &Vec<String>) {
    for name in list { println!("{name}"); }
}

fn add(list: &mut Vec<String>, name: &str) {
    list.push(name.to_string());
}

fn longest(list: Vec<String>) -> String {
    list.into_iter().max_by_key(|n| n.len()).unwrap_or_default()
}
```

`print_all` only reads, so it borrows. `add` changes the list, so it borrows mutably. `longest` takes ownership because it hands back one of the strings and does not need the rest. Reading the signatures alone tells a teammate exactly what each function does to the data.

## Common mistakes

**Cloning to make errors go away.** It works, but it hides the design problem and copies data. First ask who should own the value and who only needs to look at it.

**Holding a reference across a change.** As in Meera's example, a reader that is still in use blocks any writer. Finish using it, or copy the small value you need.

**Returning a reference to a local variable.** The local is dropped when the function ends, so the reference would dangle. Return the owned value instead.

**Storing references in structs too early.** Structs that hold `&T` need lifetime annotations and get complicated fast. Beginners should store owned types like `String` and `Vec<T>` first.

**Taking `&String` or `&Vec<T>` as parameters.** Prefer `&str` and `&[T]`; they accept more kinds of input and are the idiomatic choice.
