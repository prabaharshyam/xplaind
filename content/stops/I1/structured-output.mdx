## What it is

Applications need data, not prose. If your code must read a price, a category or a list of items from the model's reply, ask for **structured output**: JSON that matches a defined shape (a **schema**). Then validate it before your code uses it.

Most providers now offer features that constrain the model to produce valid JSON matching a schema, or use tool definitions to do the same.

```flow
Messy text | "Selling my Samsung Galaxy S21, 2 yrs old, minor scratches, 18k negotiable, pickup Malviya Nagar" -> The model
Schema | product: str, price_inr: int above 0, condition: enum, city: str or null -> The model
The model -> JSON -> Validate
Validate -[ok]-> Save | product "Samsung Galaxy S21", price_inr 18000, condition "used", city "Jaipur"
Validate -[fails]-> Retry once with the error
Retry once with the error -[fails again]-> A moderator
```

This lesson follows an online marketplace in Jaipur turning free-text seller listings into searchable records.

## How it works

**Define the shape.** Decide the fields, their types and which are required. In Python, a Pydantic model is a convenient way:

```python
from typing import Literal
from pydantic import BaseModel, Field

class Listing(BaseModel):
    product: str
    price_inr: int = Field(gt=0)
    condition: Literal["new", "used", "refurbished"]
    city: str | None = None
```

**Ask for it.** Either use the provider's structured-output feature with the schema, or tool calling with the schema as the tool's input, or, as a fallback, clear instructions plus an example of the exact JSON.

**Validate.** Parse the reply and validate it against the schema:

```python
from pydantic import ValidationError

try:
    item = Listing.model_validate_json(reply_text)
except ValidationError as err:
    # log err, retry once with the error message, or send to a person
    ...
```

Validation catches wrong types (the price as the text "about 500"), missing fields and values out of range.

**Handle failures.** On a validation error: retry once, telling the model what was wrong; if it fails again, mark the item for human review. Never let invalid data into your database.

**Allow "unknown".** Make fields optional or allow null where the input may not contain the information, and say so in the instructions. Otherwise the model may invent a value to fill the shape.

**Use enums for categories.** A fixed list of allowed values ("new", "used", "refurbished") keeps categories consistent for later analysis.

**Schema design choices:**

| Field kind | Good design | Avoid |
| --- | --- | --- |
| Money | Integer rupees with a range check, such as `price_inr: int > 0` | Text like "18k" |
| Category | Enum of allowed values | Free text that varies |
| Information that may be missing | Optional, null allowed, and say so in the instructions | Required fields that force invention |
| Repeating items | A list of objects | Numbered fields like item1, item2 |
| Dates | ISO dates, validated | Free-form dates in mixed formats |

**Retry with the error, not blindly.** When validation fails, send the model its previous reply and the exact validation message, such as "price_inr: input should be a valid integer, got '18k'". Most errors are fixed in one retry. Retrying without the error usually repeats the same mistake.

**Five layers, from light to heavy.** You can push a model towards the right shape at several points:

| Layer | How it works | Reliability | Cost |
| --- | --- | --- | --- |
| Prompting | Instructions plus an exact example | Good on strong models, never guaranteed | Free |
| Post-processing | Code fixes common slips, such as a missing closing bracket or a code fence around the JSON | Works when mistakes are small and repeat | Cheap |
| Retry | Ask again, with the validation error, until it fits | High, but each retry costs a call | Extra calls and delay |
| Constrained decoding | The provider or library only lets the model pick tokens that keep the output valid | Shape guaranteed | Slightly slower; only supported formats |
| Fine-tuning | Train on many examples in your format | High for one fixed format | Data and training effort |

The first three are bandages for a model that is nearly right. Constrained decoding is what providers' structured-output features and open-source libraries such as Outlines, guidance and llama.cpp grammars use: when the model is about to choose its next token, every token that would break the grammar is removed from the choices. Models make the same few mistakes again and again, so post-processing can go a long way: LinkedIn reported that a forgiving parser lifted correctly formatted YAML from 90% to 99.99%.

**Valid JSON is not correct JSON.** Older "JSON mode" features promise only that the reply parses, not that it has your fields. Even schema-constrained output can carry a wrong value. And any JSON can be cut off if the reply hits `max_tokens`, so check the stop reason first.

**Check values, not just types.** A schema can confirm that `price_inr` is a positive integer, but not that ₹18,000 is plausible for a two-year-old phone. Add business checks after validation: prices within a sensible range for the category, cities from a known list, dates not in the future. Values that pass the schema but fail a business check go to review just like invalid ones. This two-layer approach, schema first and business rules second, is the same pattern used for invoice extraction and almost every other structured-output pipeline.

**The whole pipeline in code.** One common way to get a guaranteed shape is to give the model a single tool whose input is your schema and require it to use that tool. This runs with Anthropic's Python SDK; other providers have equivalents:

```python
import anthropic
from pydantic import ValidationError

client = anthropic.Anthropic()
TOOL = {"name": "save_listing", "description": "Save one product listing.",
        "input_schema": Listing.model_json_schema()}
CITIES = {"Jaipur", "Ajmer", "Udaipur", "Jodhpur"}

def business_errors(item):
    errors = []
    if not 100 <= item.price_inr <= 500_000:
        errors.append(f"price_inr {item.price_inr} is outside 100 to 500000")
    if item.city and item.city not in CITIES:
        errors.append(f"city {item.city!r} is not a city we serve")
    return errors

def extract(text, max_attempts=2):
    messages = [{"role": "user", "content": "Extract the listing. Use null for anything not stated.\n\n" + text}]
    for _ in range(max_attempts):
        reply = client.messages.create(
            model="claude-sonnet-5-5", max_tokens=500, messages=messages,   # check the docs for current names
            tools=[TOOL], tool_choice={"type": "tool", "name": "save_listing"},
        )
        if reply.stop_reason == "max_tokens":
            return None, "cut off: raise max_tokens"
        call = next(b for b in reply.content if b.type == "tool_use")
        try:
            item = Listing.model_validate(call.input)
            problems = business_errors(item)
        except ValidationError as err:
            item, problems = None, [str(err)]
        if not problems:
            return item, "ok"
        # Send the exact error back so the model can fix it.
        messages += [{"role": "assistant", "content": reply.content},
                     {"role": "user", "content": [{"type": "tool_result", "tool_use_id": call.id,
                                                   "is_error": True, "content": "; ".join(problems)}]}]
    return None, "to moderator: " + "; ".join(problems)
```

Every outcome is either a valid `Listing` or a clear reason, which is what lets the moderator queue show exactly what went wrong. Count each outcome per day; a rise in one kind of error is often the first sign that inputs have changed.

## A worked example

An online marketplace in Jaipur receives seller listings as free text: "Selling my Samsung Galaxy S21, 2 yrs old, minor scratches, 18k negotiable, pickup Malviya Nagar".

The pipeline asks the model for a `Listing` with product, price, condition and city, using the provider's structured output feature. Validation runs on every reply.

Results on 500 listings:

- 471 valid on the first try.
- 18 had prices written as "18k" or "around 20,000"; the schema rejects text, the code retries once with the validation error, and 15 come back as integers (18000, 20000).
- 11 others fail outright (no price in the listing at all, or two products in one post). With the 3 that still fail after the retry, 14 go to a moderator queue.

Because nothing invalid reaches the database, the price filters and city search on the site keep working.

| Step | Listings | Share |
| --- | --- | --- |
| Valid on first try | 471 | 94% |
| Fixed by one retry with the error | 15 | 3% |
| Sent to moderators | 14 | 3% |
| Invalid records in the database | 0 | 0% |

**Why moderators liked it.** The 14 listings that reached moderators arrived with the original text, the model's attempt and the exact validation error, so each took seconds to fix. Before the pipeline, moderators fixed hundreds of listings a day by hand.

## Common mistakes

- **Parsing free text with string tricks.** Ask for JSON and validate.
- **Skipping validation because "it is usually right".**
- **Forcing every field.** Allow null for information that may be absent.
- **Free-text categories.** Use a fixed list.
- **Retrying forever.** Retry once with the error, then send to a person.

- **Changing the schema without updating tests.** Keep a set of sample inputs with expected outputs and rerun it whenever the schema changes.
- **Ignoring the stop reason.** A reply cut off at `max_tokens` is broken JSON, however good the model.
- **Huge, deeply nested schemas.** Every extra field is another chance to be wrong. Ask only for what your code uses, and split very large extractions into steps.

## When you do not need a schema

- **The reply goes straight to a person**, such as a chat answer or an email draft. Plain text is fine.
- **One label from a short list**, where a strict prompt plus a check that the reply is one of the allowed words is enough.
- **Quick exploration** in a notebook, before you know which fields matter.

## From demo to production

- **Version the schema** like an API, and keep old versions readable while records written with them exist.
- **Keep a test set** of real messy inputs with expected outputs, and run it on every schema, prompt or model change.
- **Log every outcome**: valid first time, fixed by retry, cut off, sent to review. Watch the rates by day.
- **Give reviewers context**: the original text, the model's attempt and the exact error.
- **Mind cost**: retries and long schemas add tokens, so track tokens per valid record, not per call.
