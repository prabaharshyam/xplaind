## What it is

Applications need data, not prose. If your code must read a price, a category or a list of items from the model's reply, ask for **structured output**: JSON that matches a defined shape (a **schema**). Then validate it before your code uses it.

Most providers now offer features that constrain the model to produce valid JSON matching a schema, or use tool definitions to do the same.

```text
  messy text                     schema                      validated record
 "Selling my Samsung      +-----------------------+      {"product": "Samsung Galaxy S21",
  Galaxy S21, 2 yrs old,  | product: str          |       "price_inr": 18000,
  minor scratches, 18k    | price_inr: int > 0    | -->   "condition": "used",
  negotiable, pickup      | condition: enum       |       "city": "Jaipur"}
  Malviya Nagar"          | city: str or null     |
                          +-----------------------+
           |                       |
           +----> model ----> JSON ---> validate ---> ok: save
                                          |
                                       fails: retry once with error -> fails again: moderator
```

This lesson follows an online marketplace in Jaipur turning free-text seller listings into searchable records.

## How it works

**Define the shape.** Decide the fields, their types and which are required. In Python, a Pydantic model is a convenient way:

```python
from typing import Literal
from pydantic import BaseModel, Field

class Listing(BaseModel):
    product: str
    price_inr: int = Field(gt=0)
    condition: Literal["new", "used", "refurbished"]
    city: str | None = None
```

**Ask for it.** Either use the provider's structured-output feature with the schema, or tool calling with the schema as the tool's input, or, as a fallback, clear instructions plus an example of the exact JSON.

**Validate.** Parse the reply and validate it against the schema:

```python
from pydantic import ValidationError

try:
    item = Listing.model_validate_json(reply_text)
except ValidationError as err:
    # log err, retry once with the error message, or send to a person
    ...
```

Validation catches wrong types (the price as the text "about 500"), missing fields and values out of range.

**Handle failures.** On a validation error: retry once, telling the model what was wrong; if it fails again, mark the item for human review. Never let invalid data into your database.

**Allow "unknown".** Make fields optional or allow null where the input may not contain the information, and say so in the instructions. Otherwise the model may invent a value to fill the shape.

**Use enums for categories.** A fixed list of allowed values ("new", "used", "refurbished") keeps categories consistent for later analysis.

**Schema design choices:**

| Field kind | Good design | Avoid |
| --- | --- | --- |
| Money | Integer rupees with a range check, such as `price_inr: int > 0` | Text like "18k" |
| Category | Enum of allowed values | Free text that varies |
| Information that may be missing | Optional, null allowed, and say so in the instructions | Required fields that force invention |
| Repeating items | A list of objects | Numbered fields like item1, item2 |
| Dates | ISO dates, validated | Free-form dates in mixed formats |

**Retry with the error, not blindly.** When validation fails, send the model its previous reply and the exact validation message, such as "price_inr: input should be a valid integer, got '18k'". Most errors are fixed in one retry. Retrying without the error usually repeats the same mistake.

**Check values, not just types.** A schema can confirm that `price_inr` is a positive integer, but not that ₹18,000 is plausible for a two-year-old phone. Add business checks after validation: prices within a sensible range for the category, cities from a known list, dates not in the future. Values that pass the schema but fail a business check go to review just like invalid ones. This two-layer approach, schema first and business rules second, is the same pattern used for invoice extraction and almost every other structured-output pipeline.

## A worked example

An online marketplace in Jaipur receives seller listings as free text: "Selling my Samsung Galaxy S21, 2 yrs old, minor scratches, 18k negotiable, pickup Malviya Nagar".

The pipeline asks the model for a `Listing` with product, price, condition and city, using the provider's structured output feature. Validation runs on every reply.

Results on 500 listings:

- 471 valid on the first try.
- 18 had prices written as "18k" or "around 20,000"; the schema rejects text, the code retries once with the validation error, and 15 come back as integers (18000, 20000).
- 11 others fail outright (no price in the listing at all, or two products in one post). With the 3 that still fail after the retry, 14 go to a moderator queue.

Because nothing invalid reaches the database, the price filters and city search on the site keep working.

| Step | Listings | Share |
| --- | --- | --- |
| Valid on first try | 471 | 94% |
| Fixed by one retry with the error | 15 | 3% |
| Sent to moderators | 14 | 3% |
| Invalid records in the database | 0 | 0% |

**Why moderators liked it.** The 14 listings that reached moderators arrived with the original text, the model's attempt and the exact validation error, so each took seconds to fix. Before the pipeline, moderators fixed hundreds of listings a day by hand.

## Common mistakes

- **Parsing free text with string tricks.** Ask for JSON and validate.
- **Skipping validation because "it is usually right".**
- **Forcing every field.** Allow null for information that may be absent.
- **Free-text categories.** Use a fixed list.
- **Retrying forever.** Retry once with the error, then send to a person.

- **Changing the schema without updating tests.** Keep a set of sample inputs with expected outputs and rerun it whenever the schema changes.
