## What it is

**Sorting** puts items in order. Once data is sorted, duplicates sit together, the extremes are at the ends, and you can find anything quickly.

**Binary search** finds an item in sorted data by checking the middle and throwing away the half that cannot contain it. Each check halves what is left, so it needs about log₂ n checks: 20 for 10 lakh items, 24 for 1 crore. More generally, it finds where a yes/no test flips from "no" to "yes", such as "is `a[i]` at least x?". Searching a range of possible answers this way is **binary search on the answer**.

**Two pointers** walk two positions through an array to solve pair and range problems in one pass instead of nested loops. A **sliding window** is the two-pointer pattern for the best contiguous stretch.

Binary search for 42 with the `first_at_least` code shown later (start with `lo = 0`, `hi = 10`):

```flow
dir: LR
title: Binary search for 42 in [3 8 15 21 27 33 42 50 61 77]
Check 1: index 5 holds 33 -[less than 42: go right]-> Check 2: index 8 holds 61
Check 2: index 8 holds 61 -[not less: keep, go left]-> Check 3: index 7 holds 50
Check 3: index 7 holds 50 -[not less: keep, go left]-> Check 4: index 6 holds 42
Check 4: index 6 holds 42 -[not less: lo meets hi]-> Answer: index 6
```

Four checks, where a scan from the left needs seven.

Two pointers looking for a pair that sums to 56:

```flow
dir: LR
title: Two pointers: a pair summing to 56 in sorted [5 12 18 25 30 38 45]
L at 5, R at 45: sum 50 -[too small: move L right]-> L at 12, R at 45: sum 57
L at 12, R at 45: sum 57 -[too big: move R left]-> L at 12, R at 38: sum 50
L at 12, R at 38: sum 50 -[too small: move L right]-> L at 18, R at 38: sum 56, found
```

Four steps instead of all 21 pairs.

## How it works

### Sorting algorithms and what they cost

| Algorithm | Average time | Worst time | Extra space | Stable? | When it is the right choice |
|---|---|---|---|---|---|
| Insertion sort (and bubble sort) | O(n²) | O(n²) | O(1) | yes | tiny or nearly sorted lists, where insertion sort is close to O(n) |
| Merge sort | O(n log n) | O(n log n) | O(n) | yes | predictable time; linked lists; files too big for memory |
| Quicksort | O(n log n) | O(n²) | O(log n) | no | fast in memory, with a random or median-of-three pivot |
| Heap sort | O(n log n) | O(n log n) | O(1) | no | a guaranteed bound with no extra memory |
| Python's `sorted` and `list.sort` | O(n log n) | O(n log n) | up to O(n) | yes | real data, which often has runs already in order |
| Counting sort (radix sort builds on it) | O(n + k) | O(n + k) | O(n + k) | yes | integer keys with a small range k, such as marks out of 100 |

**Merge sort** halves the list until each piece has one item, then merges sorted pieces by repeatedly taking the smaller front item: about log₂ n levels of O(n) merging, so O(n log n).

**Quicksort** picks a pivot, moves smaller items left and larger ones right, and sorts each side. Even splits give O(n log n). "Always pick the first item" on already sorted data splits n items into 0 and n − 1 every time, costing O(n²), so real implementations pick a random pivot or the median of three.

**Python's sort**, usually called Timsort, is a hybrid of merge sort and insertion sort. It finds runs already in order, extends short runs with insertion sort and merges them, so an already sorted list takes one O(n) pass. Since Python 3.11 it chooses the order of merges with the Powersort strategy.

**Why comparison sorts cannot beat O(n log n).** n items can be in n! orders, and the sort must tell them apart. Each comparison at best halves the possibilities, so the worst case needs at least log₂(n!) comparisons, roughly n log₂ n. For 10 items, 10! is 36,28,800, so at least 22 comparisons. Counting sort escapes the limit by never comparing: it sorts 10 lakh marks from 0 to 100 with 101 counters in one pass.

### Stability and sort keys

A sort is **stable** when items with equal keys keep their original order. It matters for multi-key sorts. To list orders by city with dates in order inside each city, you can sort by date and then by city: the second sort keeps the date order among equal cities only because it is stable. In Python, the one-step `sorted(orders, key=lambda o: (o.city, o.date))` gives the same result. Python guarantees stability, even with `reverse=True`; C++ `std::sort`, heap sort and a typical quicksort do not.

### Do you need a full sort?

- **Only the smallest or largest:** `min()` or `max()`, one O(n) pass.
- **The top 10 of 1 crore scores:** `heapq.nlargest(10, scores)` keeps a heap of 10 items, about O(n log k) with k = 10.
- **Only exact lookups,** such as "is this PAN in the list?": build a `set` once, then each lookup is O(1) on average. Sort when you need order: ranges, "first at or after", the nearest value, ranks.

### Binary search without off-by-one bugs

Most bugs come from mixing conventions. A reliable convention is the **half-open range**: the answer is always somewhere from `lo` to `hi`, and you stop when they meet.

```python
def first_at_least(a, x):
    """Index of the first item that is at least x; len(a) if there is none."""
    lo, hi = 0, len(a)            # the answer is always in lo..hi
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] < x:
            lo = mid + 1          # mid and everything left of it is too small
        else:
            hi = mid              # mid might be the answer, so keep it
    return lo

marks = [10, 20, 20, 20, 30]
print(first_at_least(marks, 20))   # 1
print(first_at_least(marks, 99))   # 5, which is len(marks): not found
```

Each pass shrinks the range, so the loop ends. For 20 it checks indices 2, 1 and 0 and returns 1, the first of the three 20s. This is what Python's `bisect.bisect_left` does, so in real code you call the library:

| Call | What it returns | On `[10, 20, 20, 20, 30]` |
|---|---|---|
| `bisect_left(a, x)` | first index whose item is at least x | `bisect_left(a, 20)` is 1 |
| `bisect_right(a, x)` | first index whose item is greater than x | `bisect_right(a, 20)` is 4 |
| `bisect_right(a, x) - bisect_left(a, x)` | how many items equal x | 4 − 1 = 3 |
| result equals `len(a)` | nothing qualifies | `bisect_left(a, 99)` is 5 |

So x first appears at `bisect_left` and last at `bisect_right(a, x) - 1`, if it is present at all.

In Java or C++ with 32-bit integers, `(lo + hi) / 2` can overflow once `lo + hi` passes about 2.1 billion; Joshua Bloch described this bug in Java's own library in 2006. Write `lo + (hi - lo) / 2` there. Python integers do not overflow.

### Binary search on the answer

Many problems ask for "the smallest value that works": a capacity, a daily limit, the earliest day. If the test "does v work?" is **monotonic** (once yes, yes for every larger v), binary search the range of possible answers. Use the `first_at_least` template with `a[mid] < x` replaced by "mid does not work". It takes about log₂(size of the range) checks, each one run of the test.

The precondition matters most. "Have cumulative sign-ups reached 50,000 by day d?" is monotonic, because totals never go down. "Were the day's sales above ₹1 lakh?" can go yes, no, yes, and binary search would return a wrong day with no error.

For a real-valued answer, such as a rate, floats may never meet: run a fixed number of halvings, for example 60, or stop when `hi - lo` is below the precision you need.

### Two pointers and sliding windows

**Why the pair method is correct.** Say the smallest and largest remaining items sum to too little. The smallest item plus anything else left is even smaller, so it cannot be in any answer, and dropping it is safe. The same logic drops the largest item when the sum is too big. Each step removes one item, so there are at most n − 1 steps.

```python
def has_pair(prices, target):
    left, right = 0, len(prices) - 1
    while left < right:
        total = prices[left] + prices[right]
        if total == target:
            return prices[left], prices[right]
        if total < target:
            left += 1             # need a bigger sum
        else:
            right -= 1            # need a smaller sum
    return None

print(has_pair([5, 12, 18, 25, 30, 38, 45], 56))   # (18, 38)
```

For unsorted data, sort first (O(n log n)), or make one pass with a set, checking whether `target - p` was already seen (O(n) time and memory).

**A sliding window** grows its right edge one step at a time and, while the rule is broken, shrinks its left edge. It is correct only when shrinking always makes the rule easier to meet. "Total within budget" has that property only if every value is zero or more.

### Recognising the pattern

```flow
title: Which pattern fits?
Contiguous stretch? -[yes]-> Sliding window | O(n); shrinking must help
Contiguous stretch? -[no]-> Pair with a target?
Pair with a target? -[yes, sorted]-> Two pointers | O(n) time, O(1) memory
Pair with a target? -[yes, unsorted]-> Hash set | O(n) time and memory
Pair with a target? -[no]-> First, last or smallest that works?
First, last or smallest that works? -[test is monotonic]-> Binary search | O(log n) checks
First, last or smallest that works? -[test flips back and forth]-> Scan or rethink
```

In an interview, name the pattern and its precondition (sorted, monotonic or non-negative) before you code.

## A worked example

Sneha runs analytics for an online coaching platform in Hyderabad. The numbers are illustrative.

### 1. The longest run of days within a budget

What is the longest run of consecutive days whose total ad spend stayed within ₹1 lakh? A year has 66,795 possible runs (365 × 366 ÷ 2), so checking them all is O(n²). A sliding window takes one pass:

```python
def longest_within(spend, budget):
    best = total = left = 0
    for right, amount in enumerate(spend):
        total += amount                   # grow: day `right` joins
        while total > budget:             # shrink until within budget
            total -= spend[left]
            left += 1
        best = max(best, right - left + 1)
    return best

week = [30, 20, 40, 10, 25, 60, 15]       # spend in thousands of rupees
print(longest_within(week, 100))          # 4
```

The trace for one week, with a budget of 100 (₹1 lakh):

| Day | Spend | Window after shrinking | Total | Best so far |
|---|---|---|---|---|
| 1 | 30 | days 1 to 1 | 30 | 1 |
| 2 | 20 | days 1 to 2 | 50 | 2 |
| 3 | 40 | days 1 to 3 | 90 | 3 |
| 4 | 10 | days 1 to 4 | 100 | 4 |
| 5 | 25 | days 2 to 5 (day 1 dropped) | 95 | 4 |
| 6 | 60 | days 4 to 6 (days 2 and 3 dropped) | 95 | 4 |
| 7 | 15 | days 5 to 7 (day 4 dropped) | 100 | 4 |

The answer is 4 days (days 1 to 4). Each day joins once and leaves at most once, so at most 2n steps: O(n). On day 6 one shrink step was not enough, which is why the code uses `while`, not `if`.

This is safe only because spend is never negative. Net refunds into the figures and it breaks: with `[80, 30, -50]` and a budget of 100, the window drops day 1 when the total hits 110 and reports 2, but all three days total 60, so the true answer is 3. With negative values, use another method, such as prefix sums.

### 2. The first day sign-ups reach a target

Finance asks: on which day did cumulative sign-ups first reach a target? Sign-ups are never negative, so "reached by day d?" is no, no, then yes for every later day. That is monotonic:

```python
from bisect import bisect_left
from itertools import accumulate

def first_day_reaching(daily, target):
    totals = list(accumulate(daily))      # running totals, O(n)
    i = bisect_left(totals, target)       # first day whose total is at least target
    return i if i < len(totals) else -1   # len(totals) means never reached

print(first_day_reaching([120, 90, 200, 150, 80], 400))   # 2
print(first_day_reaching([120, 90, 200, 150, 80], 9999))  # -1
```

This is the `first_at_least` template, done by the library. The totals reach 410 on the third day, index 2.

Building `totals` is already an O(n) pass, so for one target a plain scan is just as good. The search pays off when she answers many targets: about 9 checks each for a year of daily data, and about 17 for ten years of hourly data (87,600 hours).

### 3. Searching for an answer that is not in any list

Mentors grade assignment batches in submission order. This week's seven batches have 40, 25, 35, 50, 20, 30 and 45 pages, and all must be graded within 3 days, with each day's batches within a daily page limit. What is the smallest limit that works?

The answer lies between 50 (the biggest batch must fit) and 245 (everything in one day), and a bigger limit never needs more days, so the test is monotonic:

```python
def days_needed(pages, limit):
    days, today = 1, 0
    for p in pages:
        if today + p > limit:             # today is full; start a new day
            days, today = days + 1, 0
        today += p
    return days

def smallest_limit(pages, max_days):
    lo, hi = max(pages), sum(pages)       # smallest and largest sensible answers
    while lo < hi:
        mid = (lo + hi) // 2
        if days_needed(pages, mid) <= max_days:
            hi = mid                      # mid works; try smaller
        else:
            lo = mid + 1                  # too small; go bigger
    return lo

print(smallest_limit([40, 25, 35, 50, 20, 30, 45], 3))    # 95
```

The answer is 95 pages a day: 40 + 25, then 35 + 50, then 20 + 30 + 45. A limit of 94 needs 4 days. The search covers 196 possible limits in 7 checks of one O(n) pass each.

## Common mistakes

**Binary searching unsorted data or a test that is not monotonic.** You get a wrong answer and no error. Prove the test goes "no, then yes" and never back.

**Off-by-one bounds.** Mixing an inclusive and an exclusive `hi`, or writing `lo = mid` when `mid` rounds down, loops forever once two items are left. Use one convention, such as the half-open template, and test lengths 0, 1 and 2. In Java or C++, also write `lo + (hi - lo) / 2`.

**Using bisect's result without checking it.** `bisect_left` returns `len(a)` when nothing qualifies, so indexing with it raises an `IndexError`.

**Sorting inside a loop.** Sort once, outside it. And use `min()`, `heapq.nlargest` or a set when you need less than full order.

**Assuming every sort is stable.** C++ `std::sort`, heap sort and most quicksorts are not, so a two-step multi-key sort can come out wrong.

**Using two pointers on unsorted data.** Sort first or use a hash set.

**Using a sum-based sliding window with negative values.** Refunds or losses break it silently. Check that every value is zero or more.

**Shrinking the window with `if` instead of `while`.** One step may not be enough, as day 6 in the trace shows.
