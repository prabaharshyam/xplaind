## What it is

A **decision tree** predicts by asking a sequence of questions about features: "Is the EMI-to-income ratio above 0.45? If yes, has the applicant missed a payment in the last year?" Each answer leads down a branch to a prediction at a leaf. Trees learn these questions from data.

Single trees overfit easily. Two ensemble methods fix this:

- **Random forest**: many trees, each trained on a random sample of rows and features, with predictions averaged. Robust and hard to break.
- **Gradient boosting**: trees built one after another, each new tree correcting the errors of the ensemble so far. XGBoost, LightGBM and CatBoost are popular implementations. Usually the most accurate on tabular data.

```text
             EMI / income > 0.45 ?
               /            \
             yes             no
             /                 \
   missed payment in      credit history < 2 yrs ?
   last 12 months ?          /           \
     /        \            yes            no
   yes        no            |              |
    |          |        risk 0.12      risk 0.03
 risk 0.41  risk 0.18

  Boosting: tree 1 + small correction from tree 2 + ... + tree 640
```

## How it works

**Why trees suit business data.** They handle mixed feature types, need no feature scaling, capture non-linear effects and interactions automatically ("high EMI ratio matters more for self-employed applicants"), and cope with missing values (most boosting libraries handle them natively).

**Key settings for boosting.**

- *Number of trees* and *learning rate*: many small steps (a low learning rate with more trees) usually generalise better; use early stopping on a validation set to stop adding trees when validation error stops improving.
- *Tree depth*: shallow trees (depth 3 to 8) limit complexity.
- *Subsampling* of rows and columns per tree: adds randomness that reduces overfitting.
- *Minimum samples per leaf* and regularisation terms: stop the model from fitting tiny groups.

**Categorical features.** One-hot encoding works for few categories; for many (city, product), use target encoding with care to avoid leakage, or a library that handles categories directly.

**Explaining predictions.** Feature importance shows which features the model relied on overall, but can mislead with correlated features. SHAP values explain individual predictions: how much each feature pushed this applicant's risk up or down. Regulated decisions often need such explanations.

**Limits.** Trees cannot extrapolate beyond the target values they saw, and they are not the right tool for raw images, audio or text, where neural networks win.

**Tuning boosting, in order:**

| Setting | Start with | Effect |
| --- | --- | --- |
| Learning rate | 0.03 to 0.1 | Lower is slower but usually generalises better |
| Number of trees | Many, with early stopping | Early stopping picks the right number for you |
| Max depth | 4 to 8 | Deeper trees capture more interactions and overfit more |
| Row and column subsampling | 0.7 to 0.9 | Randomness reduces overfitting |
| Minimum samples per leaf | 20 to 100 | Stops the model fitting tiny groups |

Tune on a validation set split by time, then confirm once on a later test period. A gap between training and validation scores that keeps growing is the clearest sign of overfitting.

## A worked example

A Gurugram digital lender predicts 90-day default on personal loans from 120 features: bureau data, bank-statement summaries, application details and app usage.

- Logistic regression baseline: ROC AUC 0.71.
- Random forest: 0.75.
- LightGBM with early stopping, depth 6, learning rate 0.03, row and column subsampling: 0.79, tested on loans from a later quarter than training.

Explanation: SHAP shows the top drivers are bounced EMIs in bank statements, the EMI-to-income ratio and credit history length. For each rejected applicant, the top three reasons are mapped to plain-language messages for the adverse-action notice.

A warning sign during development: a feature "number of collection calls" had very high importance. It was recorded after loans went bad, so it leaked the outcome. Removing it dropped validation AUC from 0.86 to the honest 0.79.

| Model | Validation ROC AUC (later quarter) |
| --- | --- |
| Logistic regression baseline | 0.71 |
| Random forest | 0.75 |
| LightGBM, tuned, early stopping | 0.79 |
| LightGBM with the leaky collection-calls feature | 0.86 (not real) |

**From model to adverse-action notice.** In lending, a rejected applicant must be told the main reasons. For each rejection, the team takes the three features with the largest SHAP values pushing risk up, and maps each to a plain sentence agreed with the compliance team: "Several EMI payments bounced in the last six months", "Your existing EMIs are a high share of your income", "Your credit history is shorter than two years". Engineers never write these sentences on the fly; they come from a reviewed list, so the wording is consistent, accurate and fair. The same SHAP values also help analysts spot when the model leans on a feature it should not, such as a proxy for location.

## Common mistakes

- **Deep trees without early stopping.** Boosting overfits quickly.
- **Trusting feature importance blindly.** Check for leakage when a feature looks too good.
- **Random splits on time-ordered data.** Validate on a later period.
- **One-hot encoding hundreds of categories.** Use category-aware methods.
- **Skipping explanations in regulated uses.** Lending and insurance decisions need reasons.

- **Comparing models on different test sets.** Evaluate every candidate on the same later-period data, or the comparison means nothing.
