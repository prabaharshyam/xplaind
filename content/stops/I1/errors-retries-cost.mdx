## What it is

Language model APIs fail sometimes, and they cost money on every call. A production-ready app handles both:

- **Errors**: rate limits, overloaded servers, timeouts, bad requests, authentication problems.
- **Retries**: trying again, the right way, for errors that are temporary.
- **Cost caps**: limits that stop a bug or a heavy user from running up a large bill.

```text
  Call the model API
        |
        v
   success? --yes--> use the result, log tokens and cost
        |
        no
        v
   retryable? (429, 500, 503, overloaded, timeout)
        |                     |
        no                    yes
        v                     v
   fail fast:           attempts left?
   log, alert,            |        |
   fix the cause         yes       no --> fallback: cache, smaller model,
                          |              "try again", or a person
                          v
                wait: retry-after, or 2^n seconds + jitter
                          |
                          +--> call again
```

This lesson follows Fatima, whose nightly review-summarising job failed and tripled her bill.

## How it works

**Sort errors into two kinds.**

- *Worth retrying*: `429` rate limit, `500` and `503` server errors, provider "overloaded" errors, network timeouts. These often succeed a moment later.
- *Not worth retrying unchanged*: `400` bad request (your input is wrong, for example too long or malformed), `401` invalid key, `403` not permitted, `404` unknown model. Retrying sends the same broken request again; fix the cause instead.

**Retry with exponential backoff.** Wait, then retry; double the wait each time (1 s, 2 s, 4 s, 8 s), add a little randomness (jitter) so many clients do not retry at the same moment, and stop after a few attempts. If the response includes a `retry-after` header, wait that long. Many official SDKs retry automatically; check the default settings rather than adding a second retry layer on top.

**Rate limits.** Providers limit requests and tokens per minute. Stay under them by limiting concurrency (how many calls run at once), spreading batch jobs out and using batch APIs for non-urgent work. Higher limits usually come with higher usage tiers.

**Timeouts.** Set a timeout on every call so a stuck request does not hang your app.

**Fallbacks.** For important features, decide what happens when calls keep failing: a cached answer, a simpler model, a friendly "please try again", or routing to a person.

**Cost guards.**

- Set a monthly spending limit or alerts in the provider's console: the simplest protection against a runaway bug.
- Cap `max_tokens` on every call so one request cannot produce an enormous reply.
- Limit requests per user per day.
- Log tokens and cost per request so you can see where money goes.
- Cap loops and retries; a bug that retries forever is a bug that spends forever.

**Backoff in numbers.** With a base of 1 second, doubling and up to 1 second of jitter, five attempts wait roughly:

| Attempt | Wait before it | Total time so far |
| --- | --- | --- |
| 1 | 0 s | 0 s |
| 2 | about 1 to 2 s | about 1.5 s |
| 3 | about 2 to 3 s | about 4 s |
| 4 | about 4 to 5 s | about 8.5 s |
| 5 | about 8 to 9 s | about 17 s |

After that, stop and use the fallback. For interactive features, users will not wait 17 seconds, so use fewer attempts and a faster fallback. For overnight batch jobs, longer waits are fine.

**Cost per request.** Every response tells you how many input and output tokens were used. Multiply by the provider's current prices and log the result with the request id, user and feature. A weekly look at cost per feature and per user shows quickly whether one feature, one user or one bug is driving the bill.

## A worked example

Fatima's app summarises customer reviews for 300 small sellers each night. One morning she finds the job failed halfway and the bill was three times normal.

The logs show: the provider returned `429` errors at peak; her code retried immediately and indefinitely, flooding the API; a review in Hindi with 40,000 characters of repeated emoji made one request enormous, and that request failed with `400` and was retried 200 times.

Her fixes:

```python
import random, time

RETRYABLE = {429, 500, 503, 529}

def call_with_retry(send, max_attempts=5):
    for attempt in range(max_attempts):
        try:
            return send()
        except APIError as e:
            if e.status not in RETRYABLE or attempt == max_attempts - 1:
                raise
            time.sleep(min(30, 2 ** attempt) + random.random())
```

She also truncates each review to 4,000 characters, sets `max_tokens=300` for summaries, runs at most five calls at a time, and sets a monthly spend limit with an alert at half. The next month's bill returns to normal and the nightly job completes.

| Problem | Fix | Effect |
| --- | --- | --- |
| Immediate, endless retries on 429 | Backoff with jitter, five attempts | No more flooding at peak |
| Retrying a 400 error 200 times | Fail fast on 400, 401, 403, 404 | One failure logged, not 200 |
| A 40,000-character review | Truncate input to 4,000 characters | Request size capped |
| Long summaries | `max_tokens=300` | Output size capped |
| 50 calls at once | At most five at a time | Under the rate limit |
| No spending guard | Monthly limit with an alert at 50% | A runaway bill is stopped early |

## Common mistakes

- **Retrying everything.** 400 and 401 errors will not fix themselves.
- **Retrying immediately and forever.** Back off, add jitter and stop.
- **No spending limit or alerts.**
- **No `max_tokens` cap.**
- **Double retries.** Check what the SDK already does before adding your own.
