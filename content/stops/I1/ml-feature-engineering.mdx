## What it is

**Feature engineering** creates model inputs from raw data. A transactions table does not directly tell a churn model much; features such as "orders in the last 30 days", "change in monthly spend versus the previous quarter" and "days since last order" do.

Good features capture what a domain expert would look at.

```flow
dir: LR
title: Prediction date: 1 Nov
The past, allowed | orders, sessions, tickets -> Features "as of" 1 Nov | counts, trends, recency
Features "as of" 1 Nov -[predict]-> The future, never in features | next orders: this is the label
```

This lesson follows a food-delivery company in Bengaluru predicting which customers will order again within 14 days.

## How it works

**Aggregates over time windows.** Counts, sums, averages, maximums over the last 7, 30 or 90 days. Trends: this month versus last month. Recency: days since the last event.

**Ratios and differences.** EMI to income, spend per visit, returns per order, price relative to category average.

**Date and time parts.** Day of week, hour, month, festival periods (Diwali, Onam, Eid, Pongal), salary days at month start. Indian demand and payment patterns are strongly seasonal.

**Categories.** One-hot encoding for few values; frequency or target encoding for many (with target encoding computed only on training folds to avoid leakage); grouping rare categories into "other".

**Text.** Simple: length, keyword flags. Stronger: embeddings from a language model, used as features.

**Location.** Distance to a store or hub, PIN code characteristics, city tier.

**Leakage.** The cardinal rule: a feature must use only information available at the moment of prediction. Compute every aggregate "as of" the prediction time. Features that quietly include future data (a refund recorded after the order you are scoring) make models look brilliant in testing and fail in production.

**Training-serving consistency.** Features must be computed the same way when training and when serving. Write feature code once and reuse it, or use a feature store. Mismatches (a timezone difference, a different definition of "active") silently degrade production models.

**Selection.** More features are not always better. Remove useless or redundant ones; check importance and stability across time.

**Feature ideas by data type:**

| Raw data | Example features |
| --- | --- |
| Transactions | Orders in last 7, 30, 90 days; average value; change versus previous 30 days; days since last order |
| Ratings and support | Last rating; tickets in last 30 days; share of late deliveries |
| Dates | Day of week, hour, month, festival window, salary week |
| Categories | One-hot for few values; frequency or fold-safe target encoding for many; rare values grouped as "other" |
| Text | Length, keyword flags, embeddings |
| Location | Distance to store or hub, city tier |

**Start from experts.** The best features usually come from asking the people who know the business: "what would make you think a customer is about to leave?" Delivery managers suggested late-delivery share; finance suggested payday timing. Each became a feature that beat anything automatic.

**Point-in-time features in pandas.** Compute everything "as of" a cutoff date, from events strictly before it:

```python
import numpy as np, pandas as pd

rng = np.random.default_rng(2)
events = pd.DataFrame({
    "customer": rng.integers(1, 301, 6000),
    "ts": pd.Timestamp("2026-01-01") + pd.to_timedelta(rng.integers(0, 300, 6000), unit="D"),
    "amount": rng.gamma(2, 400, 6000).round(),
    "late": rng.random(6000) < 0.1,
})

def features_as_of(events, cutoff):
    past = events[events.ts < cutoff]
    out = {}
    for days in (7, 30, 90):
        w = past[past.ts >= cutoff - pd.Timedelta(days=days)]
        g = w.groupby("customer")
        out[f"orders_{days}d"] = g.size()
        out[f"spend_{days}d"] = g.amount.sum()
    g = past.groupby("customer")
    out["days_since_last"] = (cutoff - g.ts.max()).dt.days
    out["late_share"] = g.late.mean()
    f = pd.DataFrame(out).fillna(0)
    f["spend_trend"] = f.spend_30d / (f.spend_90d / 3 + 1)          # last month vs monthly average
    return f

cut = pd.Timestamp("2026-09-01")
X = features_as_of(events, cut)
print(X.describe().T[["mean", "max"]].round(1).head(8))
```

For training, build features at several cutoffs (one per month), each paired with labels from after its cutoff. That gives more examples and tests stability over time.

**Festival and salary-cycle features.**

```python
FESTIVALS = pd.to_datetime(["2026-03-04", "2026-08-28", "2026-10-20", "2026-11-08"])   # check the year's dates

def calendar_features(dates):
    d = pd.Series(pd.to_datetime(dates))
    days_to_fest = d.apply(lambda x: min(((f - x).days for f in FESTIVALS if f >= x), default=365))
    return pd.DataFrame({"dow": d.dt.dayofweek, "month": d.dt.month,
                         "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": days_to_fest.clip(upper=60)})
```

Festival dates move every year and differ by region, so keep them in a dated table, not in code.

**Encoding inside a pipeline.** Keep categorical handling with the model, so serving matches training:

```python
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, TargetEncoder
from sklearn.pipeline import make_pipeline
from sklearn.ensemble import HistGradientBoostingClassifier

prep = ColumnTransformer([
    ("few", OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=20), ["city_tier", "channel"]),
    ("many", TargetEncoder(), ["pin_code"]),           # fitted with internal cross-fitting to limit leakage
], remainder="passthrough")
model = make_pipeline(prep, HistGradientBoostingClassifier())
```

`TargetEncoder` in scikit-learn uses cross-fitting during `fit_transform`, which reduces the leakage that naive target encoding causes.

**Measure each feature group's value.** Train with and without each group (recency, spend, delivery, calendar) on the same time split and keep the groups that clearly help. Features that only help on one cutoff month are probably noise.

## A worked example

A Bengaluru food-delivery company predicts whether a customer will order again within 14 days.

Raw data: orders, ratings, app sessions, support tickets and promotions.

Features built "as of" each prediction date:

- orders in the last 7, 30 and 90 days; days since last order;
- average order value and its change versus the previous 30 days;
- share of orders with a delay over 15 minutes in the last 30 days;
- last rating given; support tickets in the last 30 days;
- weekend share of orders; whether the customer usually orders on payday week;
- city tier and distance to the nearest cloud kitchen cluster.

Results: the baseline with only order counts reached AUC 0.72; with engineered features, 0.81. The most valuable new features were the delay share and the change in order value.

A leakage scare: "customer contacted support in the next 7 days" had appeared in an early draft through a misaligned join; it was found because the validation score jumped to 0.95, which was too good to be true.

| Model | AUC |
| --- | --- |
| Baseline: order counts only | 0.72 |
| With engineered features | 0.81 |
| With the accidental leaky feature | 0.95 (too good to be true) |
| After removing the leak | 0.81 |

**Which features mattered, and why.** The delay share captured something the business already suspected: customers forgive one late delivery, but two in a month make them try a competitor. The change in order value caught customers drifting away gradually, ordering smaller baskets before stopping. Neither appears in raw order counts. Both came from conversations with the operations team, and both were cheap to compute from data the company already had. The team also learned what did not help: app session counts added almost nothing once order recency was included, so they dropped them and saved a costly daily data pipeline.

## Common mistakes

- **Future information in features.** Compute everything as of prediction time.
- **Different code for training and serving.** Share feature code or use a feature store.
- **Target encoding on all data.** Compute it within training folds only.
- **Ignoring Indian calendar effects.** Festivals and salary cycles matter.
- **Too-good-to-be-true scores.** Investigate them for leakage.

- **Building hundreds of features at once.** Add features in small groups and measure each group's gain, so you know which ones earn their place and their maintenance cost.
- **Aggregates that include the prediction day or later.**
- **Festival dates hard-coded once** and wrong the next year.
- **Feature code copied between training and serving** instead of shared.

## When heavy feature engineering is not needed

- **Unstructured data** such as images, audio or long text, where neural networks learn their own features.
- **A strong pretrained model or embeddings** already capture what you need.
- **Very small data**, where a few expert features and a simple model beat a hundred engineered ones.

## From demo to production

- **Compute features as of the prediction time**, with tests that fail on future data.
- **Share feature code** between training and serving, or use a feature store.
- **Keep calendars in data tables** with dates per year and region.
- **Track feature distributions** for drift, and missing rates per source.
- **Measure value by feature group** at each retrain, and drop what stops helping.
