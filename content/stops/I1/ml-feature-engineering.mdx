## What it is

**Feature engineering** is creating model inputs from raw data. A model cannot read a transactions table the way a person does. It needs one row per thing you predict about (here, one customer at one date) and columns that summarise the past: "orders in the last 30 days", "days since the last order", "share of recent orders delivered late".

Good features capture what a domain expert would look at, in a form the model can use. On tabular data this is often where most of the accuracy comes from.

Every feature has a **prediction time**: the moment the model would be asked. Everything before it may be used. Everything after it is the future, and the label lives there.

```flow
dir: LR
title: Prediction time: 00:00 IST, 1 November
Events before 1 Nov | orders, ratings, tickets -> Features as of 1 Nov | counts, trends, recency
Features as of 1 Nov -[model]-> Label: ordered 1 to 14 Nov | never used in a feature
```

This lesson follows a food-delivery company in Bengaluru predicting which customers will order again within 14 days.

## How it works

### The one rule: compute everything as of the prediction time

**Leakage** is when a feature contains information the model would not have at prediction time. It makes validation scores look brilliant and production results disappoint. Three habits prevent most of it.

1. **Filter strictly before the cutoff.** Use `ts < cutoff`, not `<=`. An event stamped at the cutoff may have happened after the prediction.
2. **Join slowly changing tables as of the cutoff.** For ratings, loyalty tier or credit limit, take the latest value before the cutoff, not the latest value today. In pandas, `merge_asof` does this:

```python
import pandas as pd

labels = pd.DataFrame({"customer": [1, 1, 2], "cutoff": pd.to_datetime(["2026-09-01", "2026-10-01", "2026-10-01"])})
ratings = pd.DataFrame({"customer": [1, 1, 2, 2],
                        "rated_at": pd.to_datetime(["2026-08-20", "2026-10-01", "2026-09-15", "2026-10-03"]),
                        "rating": [5, 2, 4, 1]})
joined = pd.merge_asof(labels.sort_values("cutoff"), ratings.sort_values("rated_at"),
                       left_on="cutoff", right_on="rated_at", by="customer",
                       allow_exact_matches=False)     # strictly before the cutoff
print(joined)
```

Customer 1's cutoff on 1 October gets the rating of 5 from 20 August. The rating of 2 given on 1 October itself is excluded, and so is customer 2's rating from 3 October.

3. **Validate on a later time period.** Build training rows at several cutoffs (one per month), train on the earlier ones and test on the later ones. A random split mixes future rows into training, so leaks and short-lived patterns look like skill.

### Feature families

| Raw data | Example features | Why it helps |
| --- | --- | --- |
| Orders | Orders and spend in the last 7, 30 and 90 days; days since the last order | Habit and recency are the strongest signals for "will they come back" |
| Changes | 30-day average basket versus 90-day average; this month versus last | Catches customers drifting away gradually |
| Ratios | EMI to income, returns per order, price versus category average | Puts amounts on a comparable scale across people |
| Service | Share of late deliveries in the last 30 days; last rating; recent tickets | Captures bad experiences that push people to competitors |
| Calendar | Day of week, salary week, days to the next festival | Indian demand and payments follow festivals and pay cycles |
| Categories | City tier, channel, PIN code | Groups behave differently; needs encoding (below) |
| Text and location | Keyword flags, text embeddings; distance to the nearest kitchen | Turns unstructured data into numbers |

**Start from experts.** Ask the people who run the business: "what makes you think a customer is about to leave?" Delivery managers will suggest late deliveries; finance will suggest payday timing. Then measure each idea, because a sensible idea can still add nothing (the worked example shows one).

### Numeric transforms

- **Missing values.** Decide what a gap means. "No orders in 30 days" is a real zero; "no orders ever" makes an average undefined. Fill real zeros with 0, and add a missing flag (`never_ordered = 1`) where the absence itself is informative. `HistGradientBoostingClassifier` in scikit-learn accepts missing values directly.
- **Skewed amounts.** Spend in rupees is long-tailed: most customers spend a few thousand, a few spend lakhs. Use `log1p(amount)` for linear models and neural networks.
- **Scaling.** Standardise for linear models, k-nearest neighbours and neural networks. Tree models split on order, so scaling changes nothing for them.
- **Interactions.** Trees find interactions on their own. Linear models need them written out, for example `late_share × orders_30d`.

### Categories

- **Few values** (city tier, channel): one-hot encoding, with rare values grouped as "other".
- **Many values** (PIN code, restaurant ID): frequency encoding, target encoding, or the **hashing trick** (`FeatureHasher` maps each value to one of a fixed number of columns; collisions cost a little accuracy but memory stays fixed). For millions of IDs, deep models learn an **embedding** per ID.

**Target encoding** replaces each category with its average label. It is powerful and easy to leak. If you compute the averages on all rows, each row's own label is inside its feature. The demo below gives PIN codes no real signal at all:

```python
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import TargetEncoder
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.metrics import roc_auc_score

rng = np.random.default_rng(0)
df = pd.DataFrame({"pin_code": rng.integers(0, 2000, 6000).astype(str),
                   "y": rng.random(6000) < 0.3})          # pin code carries NO real signal

# Wrong: encode with means from ALL rows, then split
df["pin_mean"] = df.groupby("pin_code").y.transform("mean")
tr, te = train_test_split(df, test_size=0.3, random_state=0)
m = LogisticRegression().fit(tr[["pin_mean"]], tr.y)
print("encoded before split:", round(roc_auc_score(te.y, m.predict_proba(te[["pin_mean"]])[:, 1]), 2))

# Right: the encoder lives inside the pipeline and is fitted on training rows only
pipe = make_pipeline(TargetEncoder(), LogisticRegression()).fit(tr[["pin_code"]], tr.y)
print("encoded after split :", round(roc_auc_score(te.y, pipe.predict_proba(te[["pin_code"]])[:, 1]), 2))
```

It prints 0.85 for the wrong way and about 0.5 for the right way (the exact value varies a little between runs): pure noise scored as a strong feature. scikit-learn's `TargetEncoder` also cross-fits inside `fit_transform`, so even the training rows never see their own label. The same rule applies to scalers, imputers and feature selection: fit them after the split, inside the pipeline. This demo uses a random split only because the data has no time order.

### Calendar features

```python
import pandas as pd

# In production this is a reviewed data file, one row per festival, year and region
festivals = pd.DataFrame([
    ("onam", "2026-08-26", "kerala"),          # Thiruvonam day
    ("dussehra", "2026-10-20", "all"),
    ("diwali", "2026-11-08", "all"),
], columns=["festival", "date", "region"]).assign(date=lambda d: pd.to_datetime(d.date))

def calendar_features(dates, region):
    d = pd.Series(pd.to_datetime(dates))
    fest = festivals[festivals.region.isin([region, "all"])].date
    gap = d.apply(lambda x: min(((f - x).days for f in fest if f >= x), default=60))
    return pd.DataFrame({"date": d, "dow": d.dt.day_of_week, "salary_week": (d.dt.day <= 7).astype(int),
                         "days_to_festival": gap.clip(upper=60)})

print(calendar_features(["2026-08-20", "2026-10-15", "2026-11-03"], "kerala"))
```

Festival dates move every year, and some (such as Eid) depend on the moon sighting, so dates can differ by a day between official lists. Keep a region column and update the table each year from official holiday lists.

### Training-serving consistency

**Training-serving skew** is when production computes a feature differently from training. Common causes: UTC days in serving and IST days in training, a different definition of "active customer", or a serving query that misses the last hour of data. The model does not crash; it just gets quietly worse.

```flow
dir: LR
title: One feature function, two callers
Raw events -> features_as_of | one tested function
features_as_of -[many past cutoffs]-> Training rows
features_as_of -[cutoff = now]-> Live features
```

Write the feature code once and call it from both places, and keep encoders inside the model pipeline so the fitted objects travel with the model. At scale, a **feature store** such as Feast (open source) does this for you. It builds training sets with a point-in-time join (the latest feature value at or before each label's timestamp), copies fresh values into a fast online store (called materialisation), and serves those values at prediction time.

### Choosing features

More features are not always better. Each one costs a pipeline to maintain and a chance to leak. Measure in groups (counts, recency, service, calendar), two ways: add each group to a simple baseline, and drop each group from the full set. Features often overlap, so dropping one group may cost little even when adding it alone helps. Keep groups whose gain repeats across several test months.

## A worked example

The Bengaluru team's question: will a customer order in the 14 days after each monthly cutoff? The code below uses synthetic data, so you can run it, see the numbers and break it. Two effects are planted: half the customers start drifting away at some point (smaller baskets first, then fewer orders two months later), and two late deliveries in a month can make a customer switch apps.

```python
import numpy as np, pandas as pd
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

# 1. Synthetic orders for 3,000 customers, January to October 2026, with two planted effects
rng = np.random.default_rng(7)
N, days = 3000, pd.date_range("2026-01-01", "2026-10-31")
base = rng.gamma(2, 0.06, N)                             # usual daily chance of ordering
late_p = np.where(rng.random(N) < 0.3, 0.3, 0.05)        # 30% live where deliveries run late
drift = np.where(rng.random(N) < 0.5, rng.integers(30, 270, N), 9999)  # day a customer starts drifting
late_log, left, rows = np.zeros((len(days), N), bool), np.zeros(N, bool), []
for t, day in enumerate(days):
    shrink = np.clip(1 - (t - drift) / 60, 0.4, 1)       # drifters first buy smaller baskets,
    fade = np.clip(1 - (t - drift - 60) / 20, 0.05, 1)   # then two months later stop ordering
    left |= (late_log[max(0, t - 30):t].sum(0) >= 2) & (rng.random(N) < 0.03)  # 2 late orders: may switch apps
    ordered = rng.random(N) < base * fade * np.where(left, 0.1, 1)
    late_log[t] = ordered & (rng.random(N) < late_p)
    for c in np.flatnonzero(ordered):
        rows.append((c, day, round(rng.gamma(4, 100) * shrink[c]), late_log[t, c]))
orders = pd.DataFrame(rows, columns=["customer", "ts", "amount", "late"])

# 2. Features as of a cutoff, from orders strictly before it
def features_as_of(orders, cutoff):
    past, out = orders[orders.ts < cutoff], {}
    for d in (7, 30, 90):
        g = past[past.ts >= cutoff - pd.Timedelta(days=d)].groupby("customer")
        out[f"orders_{d}d"], out[f"spend_{d}d"] = g.size(), g.amount.sum()
        if d == 30: out["late_share_30d"] = g.late.mean()
    out["days_since_last"] = (cutoff - past.groupby("customer").ts.max()).dt.days
    f = pd.DataFrame(out).reindex(range(N))
    f = f.fillna({c: 0 for c in f if c.startswith(("orders_", "spend_"))})
    f["basket_change"] = (f.spend_30d / f.orders_30d) / (f.spend_90d / f.orders_90d)  # NaN if no orders
    return f                                              # trees accept NaN; it means "no recent orders"

# 3. One row per customer per monthly cutoff; label = ordered in the 14 days after it
def labelled(cutoff):
    X = features_as_of(orders, cutoff)
    nxt = orders[(orders.ts >= cutoff) & (orders.ts < cutoff + pd.Timedelta(days=14))]
    X["leaky_orders_7d"] = features_as_of(orders, cutoff + pd.Timedelta(days=7)).orders_7d  # bad join
    return X, X.index.isin(nxt.customer).astype(int)

def stack(months):
    parts = [labelled(pd.Timestamp(f"2026-{m:02d}-01")) for m in months]
    return pd.concat([x for x, _ in parts]), np.concatenate([y for _, y in parts])

Xtr, ytr = stack(range(4, 9))     # train on April to August cutoffs
Xte, yte = stack([9, 10])         # test on later months, never a random split

def auc(cols):
    m = HistGradientBoostingClassifier(random_state=0).fit(Xtr[cols], ytr)
    return round(roc_auc_score(yte, m.predict_proba(Xte[cols])[:, 1]), 3)

full = [c for c in Xtr if c != "leaky_orders_7d"]
print("orders_30d only     ", auc(["orders_30d"]))
for name, extra in [("+ 7 and 90 day counts", ["orders_7d", "orders_90d"]), ("+ recency", ["days_since_last"]),
                    ("+ basket change", ["basket_change"]), ("+ late share", ["late_share_30d"])]:
    print(name.ljust(20), auc(["orders_30d"] + extra))
print("all features        ", auc(full))
print("all + leaky feature ", auc(full + ["leaky_orders_7d"]))
```

The leaky column copies a real bug: a weekly table keyed by the week's last day, joined to the cutoff as if keyed by its first day, so "last 7 days" quietly became "next 7 days".

What it prints (test AUC on the September and October cutoffs; synthetic data, so treat these as illustrations):

| Features | Test AUC |
| --- | --- |
| Orders in the last 30 days only | 0.803 |
| Plus 7-day and 90-day counts | 0.832 |
| Plus days since last order | 0.818 |
| Plus basket change | 0.807 |
| Plus late-delivery share | 0.805 |
| All honest features | 0.848 |
| All, plus the leaky join | 0.935 |

Rerunning with five other seeds gives the same pattern, with each number moving by about 0.01.

**What the numbers teach.**

- **Windows and recency do the heavy lifting.** One 30-day count cannot tell "ordered twice last week" from "ordered twice a month ago". Adding 7-day and 90-day windows gives the model a trend, and days since the last order gives it timing.
- **A real cause can still add little.** Late deliveries really do drive customers away in this data, because the simulation says so. Yet the late-share feature adds almost nothing alone: it affects few customers in any 14-day window, and those who already left show up as fewer orders. Basket change behaves the same way. Ideas that are sensible in a meeting still have to earn their place in a test.
- **The leak is loud.** A jump from 0.85 to 0.93 from one column is the warning. Find it by removing the newest columns one at a time, then read the join that produced the winner.

## Common mistakes

- **Using events at or after the cutoff.** Filter with `ts < cutoff`, and join slowly changing tables with an as-of join, not "latest value today".
- **Random splits on time-ordered data.** The same customer appears at many cutoffs, and the future leaks into training. Train on earlier months, test on later ones.
- **Fitting encoders, scalers or imputers before the split.** Put them inside the pipeline so they are fitted on training rows only.
- **Separate feature code for training and serving.** Two versions drift apart (UTC versus IST, "active" defined twice). Share one function or use a feature store.
- **Hard-coding festival dates.** They move every year and differ by region. Keep a dated table.
- **Celebrating a jump instead of investigating it.** A big gain from one feature or one join is a leak until proven otherwise.
- **Adding hundreds of features at once.** Add them in groups and measure each group, so you know which ones pay for their maintenance.

## When heavy feature engineering is not needed

- **Unstructured data** such as images, audio or long text, where neural networks learn their own features.
- **A strong pretrained model or embeddings** already capture what you need.
- **Very small data**, where a few expert features and a simple model beat a hundred engineered ones.

## From demo to production

- **Test the as-of rule**: a unit test that adds a future event and checks no feature changes.
- **Compare training and serving outputs** for a sample of customers before launch, and on a schedule after it.
- **Track feature distributions and missing rates** per source, so a broken upstream table shows up as an alert, not a slow accuracy drop.
- **Re-measure feature groups at each retrain**, and drop those that stop helping.
