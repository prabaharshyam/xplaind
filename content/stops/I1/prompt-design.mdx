## What it is

In an application, the prompt is code. The **system prompt** holds the standing instructions every request shares: the model's role, the task, rules, the output format and examples. The **user message** holds the specific input for this request. Good prompt design makes results clear, consistent and testable across thousands of different inputs, not just the one you tried.

```text
  +---------------------------------------------------------+
  | SYSTEM PROMPT (same for every request, versioned file)  |
  |   role and audience                                     |
  |   task                                                  |
  |   context: price list, timings, policies                |
  |   rules, including "if unsure, say so and hand over"    |
  |   output format and length, with the reason             |
  |   2-3 varied examples, one of them tricky               |
  +---------------------------------------------------------+
  | USER MESSAGE (changes every request)                    |
  |   <customer_message> ... treated as data ... </...>     |
  +---------------------------------------------------------+
                          |
                          v
                 model reply --> checked by your test set
```

This lesson follows a phone-repair chain in Chennai as it turns a one-line prompt into one that works on hundreds of real messages.

## How it works

**What goes in the system prompt.**

- *Role and audience*: "You answer questions from customers of a mobile phone repair chain in Chennai."
- *Task*: what to do with each input.
- *Context*: facts the model needs (policies, product names, tone guidelines).
- *Rules*: what to do and not do, and what to do when unsure ("If the question is not about repairs, say you can only help with repairs").
- *Output format*: exact structure, length, language.
- *Examples*: one to three worked input-output pairs.

Keep secrets out of prompts; users can sometimes get a model to reveal them.

**Be specific and explain why.** "Keep answers under 80 words because customers read on their phones" works better than "be concise". Models follow reasons well.

**Examples beat descriptions.** A good example shows tone, length, format and edge-case handling at once. Use varied examples, including one tricky case, so the model does not copy one example too literally.

**Structure long prompts.** Use clear sections or tags for instructions, context and examples so the model can tell them apart. Put long reference documents before the question.

**Separate data from instructions.** Mark user-provided text clearly ("The customer's message is between the tags below") so instructions inside it are treated as data.

**Test on many inputs.** A prompt that works on one example often fails on others. Build a set of 20 to 50 realistic inputs, including hard and odd ones, run them all, read the failures, change one thing, and run again. This is the start of evals.

**Version prompts.** Keep them in files under version control, not pasted into code in several places.

**The prompt improvement loop:**

| Round | Change | Pass count on 50 test messages |
| --- | --- | --- |
| 0 | "Reply to the customer politely." | 18 |
| 1 | Added role, facts and the price list | 31 |
| 2 | Added rules: no unlisted prices, no rival shops, language matching | 39 |
| 3 | Added format and the 60-word reason | 42 |
| 4 | Added two examples | 44 |
| 5 | Added a water-damage rule and example | 47 |

Each round changed one thing, so the team knew which change helped. When a change lowered the pass count, they reverted it. That discipline is what makes prompt work engineering rather than guessing.

## A worked example

A Chennai phone-repair chain wants an assistant that drafts replies to customer WhatsApp messages.

First prompt: "Reply to the customer politely." On 30 real messages, replies are long, promise prices the shop does not offer and answer questions about rival brands' warranties.

Improved system prompt (abridged):

- Role: drafts replies for staff to review for "FixFast Mobiles", four stores in Chennai.
- Facts: price list for common repairs, store timings, warranty of 90 days on parts.
- Rules: never promise a price not in the list (say "we'll confirm after inspection"); never discuss other shops; reply in the customer's language (Tamil or English); under 60 words because staff send these on WhatsApp.
- Format: greeting, answer, next step.
- Two examples: a screen replacement question in English and a battery question in Tamil.

Rerun on the same 30 messages plus 20 new ones: 44 of 50 drafts are usable with no or minor edits, against 11 of 30 before. The six failures are mostly about water damage; the team adds a rule and an example for those and reruns.

**What the six remaining failures taught.** Reading the failures took ten minutes and was more useful than any general prompting tip. Customers described water damage in many ways ("phone fell in the bucket", "got wet in the rain"), and the model offered repair prices for a fault that needs inspection first. One rule ("for any liquid damage, ask them to bring the phone in; never quote a price") and one example fixed most of them.

## Common mistakes

- **Testing on one example.** Use a varied set and read failures.
- **Vague instructions.** Say exactly what you want and why.
- **No rule for the unsure case.** Tell the model what to do when the answer is not in its context.
- **Secrets in prompts.** Never put passwords or keys there.
- **Many changes at once.** Change one thing, rerun, compare.

- **Overloading the prompt with rules.** A page of "never" and "always" lines confuses the model and contradicts itself. Keep rules few, specific and explained, and remove ones the test set shows are not needed.

## Practise

Read the prompting best-practices guide linked below.

1. Write a system prompt for an assistant in a domain you know, with role, rules, format and two examples.
2. Build a set of 20 test inputs including five hard ones, and record which outputs fail.
3. Improve the prompt in two rounds, changing one thing each time, and record the pass count after each.

**You are done when you can** show a prompt, a test set and a before-and-after pass count.
