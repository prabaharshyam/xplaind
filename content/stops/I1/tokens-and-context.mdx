## What it is

Language models read and write **tokens**, small pieces of text: often a whole common word, sometimes part of a word, a number or a punctuation mark. Everything about using models is measured in tokens:

- **Price**: providers charge per million input tokens and per million output tokens; output tokens usually cost several times more.
- **Limits**: the **context window** is the maximum number of tokens in one call, counting everything sent and the reply.
- **Speed**: more output tokens take longer to generate.

| Part of one API call's context window | Tokens | Note |
|---|---|---|
| System prompt | 1,200 | The same every call |
| Conversation history | 3,000 | Grows every turn |
| Retrieved passages | 800 | |
| New user message | 150 | Tamil text uses more tokens |
| Reply, up to max_tokens | 300 | |

All of it is counted, and all of the input is paid for, on every call.

```flow
dir: LR
title: One call, end to end
System prompt + history + passages + new message -[input tokens, paid every call]-> The model
The model -[output tokens, up to max_tokens]-> Reply
```

This lesson follows an e-learning company in Chennai building a doubt-solving chatbot in Tamil and English.

## How it works

**What a token is.** A tokenizer splits text into pieces from a fixed vocabulary. In English, 100 tokens are roughly 75 words. Hindi, Tamil and other Indian scripts often need more tokens for the same meaning, so the same message can cost more and use more of the window. Numbers and code also split into many tokens.

**Counting.** Provider dashboards and replies report token usage per call, and providers offer token-counting endpoints or libraries to count before sending.

**What fills the context window.** In a chat app, everything sent on each call counts:

- the system prompt;
- the whole conversation so far (the API has no memory; you resend it);
- any documents or retrieved passages;
- tool definitions and tool results;
- and the reply, up to `max_tokens`.

As a conversation grows, every turn resends more history, so cost per turn rises.

**Estimating cost.** Cost = input tokens × input price + output tokens × output price. Example: 2,000 input tokens and 500 output tokens, with output five times the price of input per token. Input counts as 2,000 units; output as 500 × 5 = 2,500 units. The output costs more even though it is a quarter of the length.

**Staying inside the window.** Trim or summarise old conversation turns; retrieve only relevant passages instead of whole documents; set a sensible `max_tokens`; truncate oversized inputs with a warning. Very long contexts also tend to reduce answer quality for details buried in the middle.

**Caching.** If many calls share a long, identical beginning (a big system prompt or a document), prompt caching can make repeated input much cheaper and faster. A later lesson covers it.

**How cost grows with conversation length** (1,200-token system prompt, 100-token questions, 250-token answers, history resent):

| Turn | Input tokens sent | Of which history |
| --- | --- | --- |
| 1 | 1,300 | 0 |
| 3 | 2,000 | 700 |
| 6 | 3,050 | 1,750 |
| 10 | 4,450 | 3,150 |

By turn 10, most of what you pay for is history. Summarising older turns into a short paragraph keeps the input roughly flat, and caching the system prompt makes its 1,200 tokens much cheaper on every call after the first.

**Count before you send.** For anything a user can paste, such as a document or a long message, count tokens before calling the model. If it is too long, either retrieve only the relevant parts, summarise it first, or tell the user plainly that it is too long. Failing with a clear message is far better than a silent cut-off or a surprise bill.

**Count tokens in code.** Count before sending anything a user can make large. With Anthropic's SDK, the count uses the same tokenizer the model will use:

```python
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"                  # check the docs for current names

def count(system, messages):
    return client.messages.count_tokens(model=MODEL, system=system, messages=messages).input_tokens

english = [{"role": "user", "content": "Please send the electricity bill for October."}]
hindi = [{"role": "user", "content": "कृपया अक्टूबर का बिजली का बिल भेजें।"}]
print(count("Be brief.", english), count("Be brief.", hindi))   # the Hindi line usually costs more
```

For open models, the model's own tokenizer from Hugging Face (`AutoTokenizer.from_pretrained(...)`) gives exact counts offline. Rough rules such as "4 characters per token" hold only for English.

**A context budget.** Decide in advance how the window is shared, so one part cannot crowd out the others:

| Part | Budget (example, 16,000-token target) | When over budget |
| --- | --- | --- |
| System prompt and tools | 2,000 | Shorten; move rarely used rules into retrieval |
| Conversation history | 4,000 | Summarise older turns |
| Retrieved passages | 6,000 | Fewer, better chunks |
| Tool results | 2,000 | Return only needed fields |
| Reply (`max_tokens`) | 2,000 | Ask for shorter answers |

The target is usually far below the model's maximum, because cost and delay grow with every token, and quality often drops before the limit.

**Keeping history within budget.** Keep the latest turns word for word and fold older ones into a running summary:

```python
def fit_history(history, summary, budget_tokens, count_fn, keep_last=6):
    """history: list of {"role", "content"} turns, oldest first."""
    recent = history[-keep_last:]
    older = history[:-keep_last]
    if older:
        summary = summarise(summary, older)       # one cheap model call, done rarely
    prefix = [{"role": "user", "content": f"Summary of the earlier conversation: {summary}"},
              {"role": "assistant", "content": "Understood."}] if summary else []
    msgs = prefix + recent
    while count_fn(msgs) > budget_tokens and len(recent) > 2:
        recent = recent[2:]                       # drop the oldest user-assistant pair
        msgs = prefix + recent
    return msgs, summary
```

`summarise` is your own function: a short model call that merges the old summary with the turns being folded in. Summarise only when the history crosses the budget, not on every turn.

**Long context is not free attention.** Models are not equally good at using every part of a long input. Tests that hide one fact in a long document (often called "needle in a haystack") show facts in the middle are found less reliably than those near the start or end. Put the most important instructions at the start, the question at the end, and give retrieved passages in order of relevance.

**Maximum and effective context.** A model may accept 200,000 tokens or more, but how well it uses them varies by task. Test your own case: hide a known fact at different positions in a realistic document and check whether answers stay correct.

## A worked example

A Chennai e-learning company builds a doubt-solving chatbot for Class 10 students in Tamil and English.

Measurements from a week of testing:

- System prompt with syllabus guidance: 1,200 tokens.
- A typical question: 60 tokens in English, about 150 in Tamil.
- A typical answer: 250 tokens.
- After ten turns, the history adds about 3,000 tokens to every call.

At their model's prices, a ten-turn chat cost about four times as much as a two-turn chat, mostly from resent history. They change three things: summarise history after six turns, cache the system prompt, and cap answers at 300 tokens. Average cost per conversation falls by 55%, and Tamil users no longer hit the app's per-call input cap in long sessions.

**Why Tamil users hit the limit first.** The same question took about two and a half times as many tokens in Tamil as in English, and answers in Tamil were longer in tokens too. The team capped each call at 16,000 input tokens to control cost. In long revision sessions, Tamil conversations reached that cap after about 30 turns, while English ones rarely did. Summarising history after six turns fixed this for both, and it also made the bot answer faster, because shorter inputs are processed more quickly. The team now tests every prompt change with both Tamil and English conversations, and reports cost per conversation separately for each language, so a change that is cheap in English but expensive in Tamil is caught before it ships.

## Common mistakes

- **Counting words instead of tokens.** Prices and limits are in tokens, and Indian languages use more.
- **Forgetting history is resent.** Long chats grow expensive.
- **Ignoring output price.** Output tokens usually cost more.
- **No `max_tokens`.** Replies can be long and costly.
- **Stuffing whole documents in.** Retrieve what is relevant.

- **Assuming a bigger context window solves everything.** Very long inputs cost more, are slower, and details in the middle are often missed. Send what is relevant, not everything you have.
- **Estimating Indian-language tokens with English rules.** Count with the real tokenizer.
- **Filling the window because it is there.** Every extra token adds cost and delay and can reduce accuracy.

## When you need not manage context closely

- **Short, single-turn calls**, such as classifying a message: count once while designing and move on.
- **Low volume internal tools**, where a bigger bill is cheaper than the engineering time.
- **Batch jobs over short records**, where every input is similar in size.

Manage context closely for long chats, pasted documents, agents with many tool results and anything in Indian languages at scale.

## From demo to production

- **Log input and output tokens per call**, split by part where you can: system, history, retrieved, tools.
- **Enforce budgets in code**, not just in the prompt.
- **Cap user input length** with a clear message, and count before sending.
- **Alert on token growth**: a rising average input size often means history or retrieval is not being trimmed.
- **Re-check budgets when you change models**, because tokenizers and prices differ.
