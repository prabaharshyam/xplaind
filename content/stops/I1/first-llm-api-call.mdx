## What it is

Calling a language model from code is like calling any web API: your program sends a request with your prompt, the provider runs the model, and you get back the reply plus details such as how many tokens were used. With that, your own programs can summarise, classify, extract and write.

Every major provider offers an API and an official Python SDK (software development kit) that wraps the HTTP details.

```text
  your script                                    model provider
 +----------------------------+   HTTPS POST    +------------------------+
 | client = Anthropic()       | --------------> | runs the model on:     |
 |   key from environment     |  model,         |   system prompt        |
 | messages.create(...)       |  max_tokens,    |   + message history    |
 |                            |  system,        |                        |
 |                            |  messages[]     |                        |
 |                            | <-------------- |                        |
 | reply.content[0].text      |  reply text,    |                        |
 | reply.usage (tokens)       |  usage, stop    |                        |
 +----------------------------+  reason         +------------------------+
```

## How it works

**Get a key.** Create an account in the provider's developer console, add a small amount of credit if required, and create an API key. Treat it like a password.

**Keep the key out of code.** Store it in an environment variable, often in a `.env` file that is listed in `.gitignore`. The SDK usually reads it automatically from a standard variable name.

**Install the SDK** in your project's virtual environment with pip.

**Send a message.** A typical call names the model, sets a limit on output length, and passes a list of messages. Shown here with Anthropic's Python SDK; other providers' SDKs follow the same pattern:

```python
import anthropic

client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY from the environment

reply = client.messages.create(
    model="claude-sonnet-5-5",          # check the docs for current model names
    max_tokens=300,
    system="You are a concise assistant for a small bakery in Pune.",
    messages=[{"role": "user", "content": "Write a two-line WhatsApp message announcing fresh plum cakes for Christmas."}],
)

print(reply.content[0].text)
print("tokens in:", reply.usage.input_tokens, "out:", reply.usage.output_tokens)
```

**The message list.** A conversation is a list of messages with roles (user and assistant). To continue a chat, send the earlier turns again with the new message; the API does not remember previous calls by itself. The **system** prompt sets standing instructions.

**Usage and cost.** Each reply reports input and output tokens. Multiply by the model's price per token to know what each call costs. Print usage while you build so costs never surprise you.

**Choosing a model.** Providers offer larger, more capable models and smaller, faster, cheaper ones. Start with a mid-sized model and test before changing.

**The parts of a request, and what they control:**

| Part | Controls | Tip |
| --- | --- | --- |
| `model` | Capability, speed and price | Check the docs for current names |
| `max_tokens` | Maximum reply length | Always set it |
| `system` | Role, tone, rules for the whole chat | Keep it stable across calls |
| `messages` | The conversation so far | Alternate user and assistant turns |
| Reply `usage` | Tokens used | Log it from day one |
| Reply stop reason | Why it stopped: finished, or hit the token limit | If it hit the limit, the answer is cut off |

**Conversation history costs money.** Because you resend the whole history every turn, long chats get more expensive with each message: turn 20 pays for turns 1 to 19 again as input. Real apps trim or summarise old turns, and keep the system prompt stable so providers can cache it and charge less for the repeated part.

## A worked example

Vikram, a backend developer in Gurugram, builds a command-line tool that turns messy meeting notes into a tidy summary with action items.

- He creates `.env` with his key, adds `.env` to `.gitignore`, and loads it with `python-dotenv`.
- His script reads a notes file, sends it with a system prompt ("Summarise in five bullet points, then list action items as owner: task: due date"), and prints the reply and token usage.
- On a two-page note it uses about 1,800 input and 250 output tokens; at his model's prices that is well under a rupee per run.
- He adds a check: if the notes file is over 20,000 characters, he warns the user, to avoid accidental large bills.

He pushes the repository to GitHub without the key and with a README showing example output.

| Run | Input | Input tokens | Output tokens | Cost |
| --- | --- | --- | --- | --- |
| Two-page notes | 1 file | about 1,800 | about 250 | Well under ₹1 |
| A 60-page notes dump | blocked by the 20,000-character check | 0 | 0 | ₹0 |

The length check took Vikram two lines and protects every future user from a surprise bill.

**From script to habit.** Vikram's teammates started using the tool within a week. The most-used feature was not the summary but the action-item list in a fixed "owner: task: due date" format, because they could paste it straight into their tracker. That came entirely from the system prompt, which shows how much of an LLM app's value comes from clear instructions rather than clever code.

## Common mistakes

- **Hard-coding the API key.** Use environment variables; rotate any key that was ever committed.
- **Forgetting `max_tokens`.** Always cap output.
- **Expecting the API to remember earlier calls.** Send the conversation history yourself.
- **Using outdated model names.** Check the current list in the docs.
- **Ignoring usage numbers.** Track tokens from your first call.

- **Printing the whole response object into logs.** It can contain user text. Log ids, token counts and timings instead.
