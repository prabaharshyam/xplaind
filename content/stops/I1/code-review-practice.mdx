## What it is

A **code review** is when a teammate reads your change before it is merged. On GitHub and GitLab this happens on a **pull request** (or merge request): the change, its description, automated checks, and a thread of comments on specific lines.

Reviews do three jobs. They catch bugs before users do. They keep the codebase consistent, so it does not become a patchwork of styles. And they spread knowledge: after a review, two people understand the change instead of one.

A review is a conversation about the code, not a judgement of the person. Teams that review well ship faster, because problems are caught when they are cheap to fix.

## How it works

```flow
title: A pull request from open to merge
Author opens a small pull request | what, why, how it was tested -> Automated checks | tests, linter, build
Automated checks -[fail]-> Author fixes -> Automated checks
Automated checks -[pass]-> Reviewer reads | correctness first, then design, then style
Reviewer reads -[changes needed]-> Comments: specific, kind, labelled
Comments: specific, kind, labelled -> Author replies or pushes fixes -> Reviewer reads
Reviewer reads -[looks good]-> Approve and merge
```

**As the author**, make your change easy to review:

- Keep it small and about one thing. A 200-line pull request gets a careful review; a 2,000-line one gets a skim.
- Write a description: what changed, why, and how you tested it. Link the ticket. Add screenshots for anything visible.
- Review your own diff first. You will catch leftover prints and typos before anyone else does.
- Make the checks pass before asking for review.

**As the reviewer**, look at what matters most, in order:

| Order | Look at | Examples |
| --- | --- | --- |
| 1 | Correctness | Wrong logic, unhandled errors, edge cases, security, data leaks |
| 2 | Tests | Is the new behaviour tested? Would the test fail without the change? |
| 3 | Design | Does it fit the system? Is anything duplicated? Will it be easy to change? |
| 4 | Readability | Names, long functions, confusing logic, missing "why" comments |
| 5 | Style | Formatting and import order, ideally fixed by a linter, not by a person |

Write comments that are specific (what and where), say why it matters, and suggest a fix. Label what is optional with "nit:" or "optional:". Ask questions when you are unsure instead of asserting. Say what is good, too; it tells the author what to keep doing.

**As the author receiving comments**, assume good intent. Thank, fix, and reply on each thread. If you disagree, explain with evidence. If a thread goes back and forth more than twice, talk it through on a call.

**Reviewing in an unfamiliar area.** You do not need to know the whole codebase to review well. Read the description and the ticket first, so you know what the change is meant to do. Run the code or the tests locally if you can. Focus on what you can judge, such as error handling, edge cases, tests and readability, and say clearly which parts you could not assess, so the author can ask someone else about them.

**Reviewing AI changes.** A change to a prompt, a model or retrieval settings is a code change too, but its effect shows in outputs, not in the diff. Ask for the eval results by category before and after, and a few example outputs that changed. A one-word prompt edit can fix one kind of question and quietly break another.

**Speed matters.** A pull request that waits three days for review goes stale: main moves on, conflicts pile up and the author loses context. Many teams aim to give a first review within one working day. If you cannot review properly in time, say so, so the author can find someone else.

## A worked example

Aditya, a junior engineer at a food-delivery startup in Gurugram, opens a pull request that adds a "reorder last meal" button. It changes 640 lines across the app, the API and the database.

His reviewer, Meera, asks him to split it: one pull request for the API endpoint with tests, one for the button. The first is 180 lines. She reviews it in fifteen minutes and leaves four comments:

- "The endpoint takes the user id from the request body, so anyone could reorder for another user. Could we use the id from the logged-in session instead?" (correctness and security, blocking)
- "There is no test for a user with no past orders. What should it return?" (tests, blocking)
- "Could `get_last()` reuse `OrderRepository.latest_for_user()`? It looks like the same query." (design)
- "nit: `res` could be `last_order`. Not blocking."

She ends with: "The error handling for a closed restaurant is really clear, nice."

Aditya fixes the security issue, adds the test, reuses the existing query and renames the variable. He replies on each thread with what he changed. Meera approves; the change merges the same day. The second pull request, for the button, goes through even faster, because the API was already reviewed.

## Common mistakes

- **Huge pull requests.** Reviewers skim them and bugs slip through. Split by step.
- **Commenting only on style.** Let tools handle formatting; spend human attention on logic, tests and security.
- **Vague comments.** "This is wrong" leaves the author guessing. Say what, why, and a suggestion.
- **Taking comments personally.** A comment is about the code. Ask a question if one feels harsh.
- **Approving without reading.** A rubber stamp is worse than no review, because people trust it.
- **Blocking on preferences.** If it is a taste, mark it optional and let the author decide.
