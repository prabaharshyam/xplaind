## What it is

AI engineering interviews increasingly include a **design round**: "Design a customer-support assistant for a bank", "Design a system to answer questions over 10 million documents", "How would you build an agent that books travel?" You have 30 to 45 minutes, a whiteboard or shared document, and an interviewer who interrupts with "what if...?".

They are testing structured thinking, sound trade-offs and production awareness, more than knowledge of any one tool.

```text
   35-MINUTE DESIGN ANSWER
   0-5    CLARIFY        users | scale | latency | cost | languages | data rules | success
   5-10   HIGH LEVEL     boxes and arrows: channel -> API -> routing -> tools / RAG -> model -> reply
   10-28  DEEP DIVES     the 2-3 parts that matter most for THIS problem
   28-31  FAILURES       hallucination | injection | outage | cost | privacy
   31-34  EVAL + OPS     test set | metrics | launch bar | monitoring | rollout
   34-35  TRADE-OFFS     with more time, at 10x scale

   interviewer: "what if...?"  -->  treat as a new requirement, adapt the design
```

This lesson follows a strong answer to "design a WhatsApp assistant for a state electricity board, in Tamil and English".

## How it works

**A reliable structure.**

1. **Clarify (3 to 5 minutes).** Users, task, scale (users, documents, requests per second), latency and cost constraints, languages, data sensitivity, what success means. Ask, then state assumptions out loud.
2. **High-level design (5 minutes).** Sketch the main components and the request flow before going deep.
3. **Deep dives (15 to 20 minutes).** The parts that matter most for this problem: usually retrieval (ingestion, chunking, hybrid search, reranking, permissions), generation (prompting, grounding, model choice), tools or agents, and evaluation.
4. **Failure modes and safety (5 minutes).** Hallucination, injection, outages, cost spikes, privacy.
5. **Evaluation and operations (5 minutes).** Test sets, metrics, launch bar, monitoring, rollout.
6. **Trade-offs and next steps (2 minutes).** What you would do with more time or at ten times the scale.

**Habits that score well.**

- Think aloud; name trade-offs ("hybrid search costs a bit more but catches policy numbers").
- Use numbers: rough token counts, costs, latency budgets.
- Start simple, then add complexity where the requirements demand it.
- Respond to interruptions as new requirements, not as attacks.
- Keep an eye on time; do not spend 25 minutes on chunking.

**Common questions to practise.** RAG over company documents; a customer-support assistant with actions; summarising long documents; a coding assistant; a multilingual chatbot for India; an agent with tools; evaluating a model upgrade; cutting cost by half.

**Practise out loud.** Record yourself or practise with a friend. Speaking a design is a different skill from knowing it.

**Signals interviewers look for:**

| Strong signal | Weak signal |
| --- | --- |
| Asks about users, scale and data rules first | Starts naming tools |
| States assumptions with numbers | Avoids numbers |
| Explains why each choice fits this problem | Lists technologies |
| Covers failure modes and evaluation | Stops at the happy path |
| Adapts calmly to "what if" | Defends the first design rigidly |
| Manages time across all parts | Spends most of the time on one box |

**Practising with a partner.** Swap roles each session. The interviewer picks a prompt the candidate has not seen, times each phase, and interrupts twice with "what if" questions, such as an outage, a new language or ten times the traffic. Afterwards, the interviewer gives three notes: one thing done well, one gap, one habit to change. Playing the interviewer teaches you what a clear answer sounds like.

**Making estimates quickly.** Practise a few back-of-the-envelope numbers until they are automatic: tokens per page of text, requests per second from daily users, cost per request from token counts and prices, and GPU memory for a model size. Interviewers do not need exact figures; they want to see that you reason with orders of magnitude.

## A worked example

Prompt: "Design a WhatsApp assistant for a state electricity board that answers billing and outage questions in Tamil and English."

A strong candidate, in summary:

- *Clarify*: 2 million consumers; peaks after bills are issued and during outages; answers must be accurate on tariffs; outage data in an internal system; consumer number used for account questions; data must stay in India.
- *Design*: WhatsApp Business Platform via a provider → API service → intent routing (billing, outage, tariff FAQ, complaint) → tools for bill lookup and outage status (consumer number verified by OTP) → RAG over tariff orders and FAQs in both languages → model in an Indian region → reply.
- *Deep dive*: bilingual retrieval with Tamil and English chunks; tariff tables extracted carefully; outage answers only from the live tool, never generated; complaints logged with a reference number and handed to people.
- *Failures*: outage spikes (cache outage status per area, scale out), wrong tariffs (citations, refusal, weekly review), injection (no write tools besides complaint logging), provider outage (fallback message with helpline).
- *Evaluation*: 300 real questions in both languages, accuracy by intent; launch to one district first.
- *Cost*: rough estimate per conversation and monthly total at expected volume.

The interviewer asks, "what if the outage system is down?" The candidate answers: show last known status with a timestamp and the helpline, and alert on-call.

| Phase | What the electricity-board answer covered |
| --- | --- |
| Clarify | 2 million consumers, bill-day and outage peaks, Indian data residency |
| Design | WhatsApp provider, intent routing, OTP-verified tools, bilingual RAG |
| Deep dive | Outage answers only from the live tool; tariff tables extracted carefully |
| "What if the outage system is down?" | Last known status with a timestamp, the helpline, and an on-call alert |

## Common mistakes

- **Jumping into details without clarifying.**
- **Naming tools instead of explaining choices.**
- **Ignoring evaluation and operations.**
- **No numbers.**
- **Running out of time on one component.**
