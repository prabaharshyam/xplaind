## What it is

Every LLM app trades three things against each other:

- **Quality**: how often answers are correct, complete and safe.
- **Cost**: money per request and per month.
- **Speed**: how long users wait, both for the first words and for the full reply.

Bigger models, more retrieved context, rerankers, reflection steps and agent loops usually raise quality. They also raise cost and latency. Good engineering makes these trade-offs visible, measures them honestly, and lets the people who own the product decide on purpose.

The hard part is knowing which differences in the table are real. A test set is a sample, so every accuracy figure carries a margin of error. On 150 questions, 86% and 88% are the same result. And if you improve a system by studying its failures on a test set, its score on that set is no longer a fair estimate.

```flow
title: The decision method
Measure options on a tuning set | quality by category, cost, p95
Measure options on a tuning set -> Drop dominated options
Drop dominated options -> Apply budgets | latency and cost ceilings
Apply budgets -> Treat gaps inside the margin as ties
Treat gaps inside the margin as ties -> Tune the chosen option
Tune the chosen option -> Pass a gate on fresh questions | run once
Pass a gate on fresh questions -> Recommend and date it
```

The example follows a health-insurance company in Hyderabad whose call-centre agents use an assistant during live calls.

## How it works

### Measure all three on the same questions

For each option, record:

- quality from your eval, split by category (for example exclusions, claims, premiums, general questions);
- cost per request: input and output tokens times the price, plus any reranker or router call;
- latency at the median and the 95th percentile (p95), and time to first token.

Use the same questions, in the same order, for every option, so you can do the paired check below.

### Is the difference real?

An accuracy measured on n questions is an estimate. A rough 95% margin of error is:

**margin ≈ 2 × √(p × (1 − p) / n)**

| Accuracy | Questions | Rough margin |
| --- | --- | --- |
| 88% | 150 | ±5.3 points |
| 86% | 200 | ±4.9 points |
| 88% | 470 | ±3.0 points |
| 88% | 1,060 | ±2.0 points |

The margin shrinks with the square root of n: to halve it you need four times as many questions. So a two-point gap on 150 questions tells you nothing on its own.

**Compare paired, not separately.** Two margins that overlap do not settle the question, because both options faced the same questions. Count two numbers: questions only A got right, and questions only B got right. The questions both got right or both got wrong carry no information about the difference. If the gap between the two counts is smaller than 2 × √(their sum), the difference is not shown. For example, 8 against 4 flips is a gap of 4, but 2 × √12 is about 7, so it is a tie. With 18 against 3 the gap is 15 against a threshold of about 9: that difference is real. (This is a rough version of the McNemar test.)

**Measure the noise floor.** Run the same option twice on the same questions. LLM outputs vary from run to run, and LLM judges vary too. If a rerun flips 6 answers, a new option that flips 6 answers has shown nothing.

**Small categories cannot prove high floors.** If an option gets all 30 questions in a category right, the true error rate could still be about 3 in 30, or 10%. This is the "rule of three": zero errors in n questions still allows an error rate up to about 3/n. To show a floor such as "at least 85% on claims", work out in advance how many claims questions you need, and build that many.

### Tune on one set, pass the gate on another

When you read failures on a test set and change prompts, routing rules or thresholds to fix them, the fixes fit that set's quirks. The score on that set goes up by more than real quality does. Picking the best of several options on one set has the same effect: the winner's score is partly luck.

So keep two sets:

- a **tuning set** you look at freely, to compare options and find failures;
- a **gate set** of fresh questions (for example, sampled from recent calls) that nobody reads while building. Run it once, at sign-off. If the option fails, fix it on the tuning set, and refresh the gate with new questions before the next attempt. A gate you have read is no longer a gate.

### Weight by consequence

Plain accuracy treats every wrong answer the same. A wrong answer about a policy exclusion can cause a complaint and a refund; a wrong answer about office hours costs little. Give each category a weight from the business cost of an error, taken from the client's own data and agreed with the product owner. For example, suppose the insurer's records show a wrong exclusion or claims answer leads to an escalation costing about ₹1,500, a premiums error about ₹1,000 and a general error about ₹500: the weights become 3, 3, 2 and 1. Write the weights and their source next to the comparison, because the weights can change the ranking.

### Drop options nobody should pick

An option is **dominated** if another option is at least as good on quality, cost and speed, and better on at least one. Dropping dominated options leaves the **Pareto frontier**: the real choices. Read quality with the margin in mind. If two options are within noise on quality, treat them as tied, and cost and speed decide. If the decision turns on a quality gap smaller than the margin, the answer is more questions, not a confident guess.

### The levers and what they move

| Lever | Quality | Cost | Speed |
| --- | --- | --- | --- |
| Larger model | Up | Up | Slower |
| Higher reasoning or effort setting | Up on hard tasks | Up (more tokens) | Slower |
| Reranker | Up | Slightly up | Slightly slower |
| More retrieved context | Up, then down | Up | Slower first token |
| Router | Near the strong model if it routes well | Down | Faster median; p95 near the slow path |
| Batch API (offline work only) | Same | About half at major providers | Up to 24 hours |
| Priority or fast tier | Same | Up | Faster, steadier |
| Streaming, prompt caching, shorter outputs | Same | Same or down | Faster, or feels faster |

Many reasoning models have an effort setting (for example, OpenAI's `reasoning.effort`). It trades quality against cost and latency inside one model, so test two or three settings as separate options. Batch APIs from OpenAI and Anthropic charge half the normal price for requests that can wait, as of November 2026: good for nightly summaries or re-scoring old tickets, useless on a live call. The last row is covered in the lessons Caching and speed, Cost control and Latency budgets and load testing; apply those free wins before you pay for anything.

### Measure the router, including its own cost

A router sends easy requests to a cheap model and hard ones to a strong model. It saves money only if it routes well, and it has costs of its own:

- **Misroutes.** Label a sample as easy or hard, run the router, and count hard questions sent to the small model (these hurt quality) and easy ones sent to the large model (these waste money). The first kind matters more. If it is common in a high-risk category, send that whole category to the strong model.
- **Overhead.** The routing decision runs on every request. A language-model call as a router adds its own price and delay; simple rules or a small embedding classifier are far cheaper and faster. Measure the overhead either way.
- **The tail.** If 30% of traffic goes to a model with a 3.9 s p95, the router's p95 is not the small model's. Nearly all of the slowest 5% of requests come from the slow path, so the blended p95 lands inside that path's distribution.

### A comparison in code

```python
import math

WEIGHTS = {"exclusions": 3.0, "claims": 3.0, "premiums": 2.0, "general": 1.0}

def weighted_quality(results):
    """results: list of (category, correct) pairs; correct is True or False."""
    num = sum(WEIGHTS[c] * ok for c, ok in results)
    den = sum(WEIGHTS[c] for c, _ in results)
    return num / den

def margin(p, n):
    """Rough 95% margin of error for an accuracy p measured on n questions."""
    return 2 * math.sqrt(p * (1 - p) / n)

def paired(a, b):
    """a, b: True/False per question for two options, same questions, same order."""
    a_only = sum(x and not y for x, y in zip(a, b))
    b_only = sum(y and not x for x, y in zip(a, b))
    real = abs(a_only - b_only) > 2 * math.sqrt(a_only + b_only)
    return a_only, b_only, real

def frontier(options):
    """options: dicts with quality, cost_inr and p95_s. Drops dominated options."""
    def dominates(a, b):
        no_worse = (a["quality"] >= b["quality"] and a["cost_inr"] <= b["cost_inr"]
                    and a["p95_s"] <= b["p95_s"])
        better = (a["quality"] > b["quality"] or a["cost_inr"] < b["cost_inr"]
                  or a["p95_s"] < b["p95_s"])
        return no_worse and better
    return [o for o in options if not any(dominates(x, o) for x in options if x is not o)]
```

`margin(0.88, 150)` returns about 0.053, or 5 points.

### Budgets first, then maximise quality

Agree two ceilings with the product owner before looking at results: a latency budget (for example, first words within 1 s and full reply within 4 s at p95) and a cost per request. Filter the frontier to options inside both, then pick the best quality among them, reading ties as ties. For safety-critical categories, also agree a minimum quality that no saving can buy below.

## A worked example

The Hyderabad insurer's assistant answers policy questions for agents on live calls. All numbers below are illustrative, chosen to show the method.

The agreed budgets: first words within 1 s and the full reply within 4 s at p95, and at most ₹0.40 per request.

**Round 1, on a tuning set of 150 questions:**

| Option | Accuracy | Cost per request | p95 latency |
| --- | --- | --- | --- |
| Small model | 76% | ₹0.08 | 1.6 s |
| Large model | 85% | ₹0.60 | 3.9 s |
| Large model + reranker | 89% | ₹0.64 | 4.3 s |
| Router (70% small, 30% large) | 86% | ₹0.24 | 3.0 s |

The router's cost follows from its traffic split: 0.7 × ₹0.08 + 0.3 × ₹0.60 plus about ₹0.002 for its classifier, about ₹0.24. Its p95 is 3.0 s, nearly double the small model's, because the slowest 5% of requests come mostly from the large model.

What the team can and cannot conclude:

- The large model alone is dominated: the router matches its accuracy and is cheaper and faster. Drop it.
- The small model is clearly worse. On the paired check it got 3 questions right that the router missed, and the router got 18 right that it missed. That gap is real.
- Large model plus reranker breaks both budgets (4.3 s, ₹0.64). Its lead over the router is also inside the ±5-point margin: the paired check shows 4 against 8 flips, a tie.

Reading the router's mistakes, the team saw they clustered in exclusions and claims. They changed the design: all exclusions and claims questions go to the large model with the reranker, and the router handles the rest. Now 38% of traffic takes the strong path. On the same 150 questions it scored 88%, but they had tuned on those questions, so that figure is optimistic.

```flow
dir: LR
title: Chosen design: about ₹0.30 per request, 3.5 s p95
Question -> Router | rules plus a small classifier
Router -[general, premiums]-> Small model | 62% of traffic
Router -[exclusions, claims]-> Large model + reranker | 38% of traffic
```

**Round 2, the gate.** Before building, they had agreed a floor: at least 85% on exclusions and claims, judged by the low end of the margin. A quick calculation showed that 120 high-risk questions at 90% accuracy would give a low end of only about 84.5%, so they built a gate of 400 fresh questions from the last month's calls, with 240 on exclusions and claims. Nobody read them during tuning.

| Option | Exclusions and claims (240) | Other (160) | Cost | p95 |
| --- | --- | --- | --- | --- |
| Chosen design | 90.0% | 83.8% | ₹0.30 | 3.5 s |
| Large + reranker everywhere | 90.8% | 86.3% | ₹0.64 | 4.3 s |

On the high-risk questions the chosen design scored 216 out of 240; the margin runs from about 86% to 94%, so it clears the floor. Both options use the same path for these questions, so the 216 against 218 gap can only come from run-to-run noise or the router misplacing a few of them. Across all 400, it got 14 questions right that the more expensive option missed, and missed 20 that it got right. A gap of 6 against a threshold of about 12 is a tie. The cost per request is 0.62 × ₹0.08 + 0.38 × ₹0.64 + ₹0.002, about ₹0.30.

**The recommendation the product owner signed:** "We recommend the router, with all exclusions and claims questions on the large model and reranker. On 400 fresh questions it reached 90% on exclusions and claims, above the agreed 85% floor, at about ₹0.30 per request and 3.5 s at p95. Using the large model with reranker everywhere showed no quality difference we can measure on 400 questions, costs twice as much and breaks the 4 s budget. Streaming keeps first words under 1 s. Prices and results are as measured in November 2026, test set version 2; we will re-run the comparison when a provider changes prices or ships a new model."

## Common mistakes

- **Optimising one dimension silently.** Show quality, cost and speed together.
- **Calling noise a win.** 86% against 88% on 150 questions is a tie. Give the margin and the paired flips, or add questions.
- **Passing the gate on the tuning set.** Fixes fitted to a set inflate its score. Keep a fresh gate set and run it once.
- **Overall accuracy only.** Split by category and weight by the cost of errors.
- **Weights the engineer invented.** Derive them from the client's data and record their source.
- **Average latency only.** Report p95 and time to first token.
- **Forgetting the router's own costs.** Its call, its misroutes and its tail all count.
- **Keeping dominated options** in the meeting, where they waste time.
- **No date, prices or test-set version** on the comparison, so it goes stale without anyone noticing.
- **Deciding without the product owner.** The trade-off is a business decision; show the table and let them weigh it.

## When a full trade-off study is not needed

- **Low volume.** If the strongest model costs a few hundred rupees a month at your traffic, use it and optimise later.
- **One option clears every target** with room to spare, including the low end of its margin.
- **Early prototypes**, where learning whether the task works at all comes first. Still keep the questions you collect: they become your tuning set.

## From demo to production

- **Keep the comparison table** with dates, prices, weights and the test-set versions for both the tuning and the gate set.
- **Track quality, cost per request and p95 latency** in production by feature and category.
- **Refresh the gate set** from recent traffic before each sign-off, so it matches what users ask now.
- **Hold minimum quality** for high-risk categories that no routing change can go below.
- **Measure the router's mistakes** by category every month.
- **Re-run the comparison** on price changes, new models and big traffic changes.
