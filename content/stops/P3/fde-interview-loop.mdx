## What it is

A forward deployed engineer (FDE) works inside a client's organisation and turns a vague business problem into software people use. The interview loop tries to watch you do that in a few hours.

### Where the role and the loop come from

Palantir says it pioneered the role. It calls these engineers Forward Deployed Software Engineers, nicknamed "Deltas", and contrasts them with "Devs", who build the core platform: a Dev builds one capability for many customers, a Delta serves one customer with many capabilities. Candidate reports and prep guides describe a "decomposition" round in most Palantir FDE onsites: about 60 minutes, little or no code, with the interviewer playing a customer who has a vague problem. Some also describe a "learning" round, where you must pick up an unfamiliar concept, API or system quickly and build on it.

AI labs and AI startups now use the title too. OpenAI and Anthropic both hire FDEs who embed with key customers. Prep guides on OpenAI's loop report production-level coding and system design, a customer-facing exercise and a project deep-dive where you defend every decision in something you built. Reported round counts differ, so do not rely on any exact number.

In India the title is spreading fast. In July 2026, TCS chief executive K Krithivasan told Reuters the company wants 1% to 1.5% of its staff in forward deployed roles, which Reuters put at roughly 5,900 to 8,900 people; he did not say whether they would be hired or retrained. Coforge was reported in July 2026 to plan growing its FDE team from about 20 to 100. Bengaluru postings with the title in 2026 included Google Cloud and Nanonets. Some firms use other titles for the same work, so read the job description.

### The rounds and what each one tests

| Round | What it tests | What strong looks like |
|---|---|---|
| Practical coding | Messy data, APIs, validation, tests | Asks about the data first; reports bad rows; tests edge cases |
| Problem decomposition | Turning a vague goal into a plan | Questions before solutions; a KPI, a baseline and a gated first step |
| Learning (reported at Palantir) | Picking up an unfamiliar system fast | Good questions; extends the system without breaking it |
| AI system design | An end-to-end design under client constraints | Choices tied to the client's data, rules, budget and team |
| Client role-play | Managing expectations under pressure | Neither caves nor refuses; offers options; closes with an owner and a date |
| Behavioural and project deep-dive | Ownership, conflict, failure, learning | STAR stories with a measured result and a lesson |
| Take-home or work sample | Judgement inside a time box | Working core path, honest README, small eval, time spent stated |

Not every company runs every round. Decomposition is the one most specific to FDE roles:

```flow
dir: LR
title: The decomposition round
A vague problem -> Goal and owner -> Process and data -> KPI + baseline -> Options including non-AI -> Proof of concept + gate -> Risks
```

This lesson follows Arjun, a fictional candidate preparing for an FDE loop at an AI startup that sells to Indian banks.

## How it works

### Before the loop: ask the recruiter four questions

1. Which rounds are there, how long is each, and which ones are a case or a role-play?
2. Is there a take-home? What is the suggested time, and will I present it?
3. What are the rules on AI tools, in the application and in the coding round?
4. How much on-site work and travel is normal, and how is an FDE's success measured?

The third question matters more in 2026 than it used to, because policies differ. Anthropic publishes candidate guidance that allows some uses of Claude, such as checking your resume against the job description, but not having it write your answers. In 2025, Meta was reported to be trialling coding interviews in which candidates can use an AI assistant. Rules differ between companies, and sometimes between rounds of the same loop. Asking is normal; guessing wrong can end a loop.

### Practical coding

Many FDE coding rounds look like real client work, though some loops, including Palantir's as candidates report it, also set algorithm-style problems; ask which to expect. A realistic 30-minute task: "A lender exports UPI collections from its branch system as CSV. Some rows have missing amounts, dates in two formats, or a repeated transaction ID. Return the clean records and a list of rejected rows with reasons, then put it behind an API endpoint."

Spend the first two minutes on questions. Should a duplicate be rejected, or should the second copy win? Are negative amounts refunds or errors? Which date formats appear? Then write the core:

```python
from datetime import date, datetime
from decimal import Decimal
from pydantic import BaseModel, Field, ValidationError, field_validator

class Txn(BaseModel):
    txn_id: str = Field(min_length=1)
    amount: Decimal = Field(gt=0)
    paid_on: date

    @field_validator("paid_on", mode="before")
    @classmethod
    def parse_date(cls, v: str) -> date:
        for fmt in ("%Y-%m-%d", "%d/%m/%Y"):
            try:
                return datetime.strptime(str(v).strip(), fmt).date()
            except ValueError:
                pass
        raise ValueError(f"unknown date format: {v!r}")

def clean(rows):
    good, rejected, seen = [], [], set()
    for line, row in enumerate(rows, start=2):  # line 1 is the header
        try:
            txn = Txn(**row)
        except ValidationError as e:
            rejected.append((line, e.errors()[0]["msg"]))
            continue
        if txn.txn_id in seen:
            rejected.append((line, "duplicate txn_id"))
            continue
        seen.add(txn.txn_id)
        good.append(txn)
    return good, rejected
```

Fed a six-row sample with one good row, a missing amount, a `dd/mm/yyyy` date, a repeated ID, a negative amount and the date "Nov 5", it keeps two rows and rejects four, each with its line number and reason. `Decimal` rather than `float` is deliberate: money should not pick up rounding errors. Wrapping `clean` in a FastAPI endpoint that accepts an uploaded file takes another few minutes (see the lesson "REST APIs with FastAPI").

| What interviewers check | Weak | Strong |
|---|---|---|
| Questions | Starts typing at once | Asks what counts as a bad row and what to do with duplicates |
| Bad data | Skips bad rows silently | Returns each rejected row with a reason |
| Types | Floats for money, strings for dates | `Decimal`, real dates, one validation model |
| Tests | "It works on my sample" | Two or three tests for the edge cases named at the start |
| Talking | Silent for ten minutes | Says each trade-off aloud, for example "rejecting duplicates for now; easy to change" |

If the task involves a language model, the same habits apply: define a schema, validate the reply, retry once or twice with the validation error, then fail loudly and log. The lesson "Get structured JSON output" covers the pattern.

### Problem decomposition

Given a prompt such as "a hospital wants to reduce discharge delays", you are scored on how you think, not on a final answer. Work through six steps aloud:

1. **Clarify the goal and its owner.** Who is asking, and what would change for them?
2. **Ask about the current process, volumes and data.** Where does the time actually go? How many discharges a day? What is recorded, and where?
3. **Agree a KPI and a baseline**, for example the median hours from "fit for discharge" to leaving the bed, measured today.
4. **List options, including non-AI ones**, such as a checklist or a change in pharmacy timing, then pick one and say why.
5. **Plan a proof of concept with a gate.** A proof of concept is a small, time-boxed test on real data. A gate is a number agreed in advance that decides whether you continue, for example "cut median delay by 20% in one ward over four weeks".
6. **Name risks and how you would reduce them**: patient data rules, staff adoption, wrong outputs.

If the interviewer gives no numbers, state assumptions aloud ("suppose 200 discharges a day across three hospitals"). Two failure modes are common: proposing a model in the first five minutes, and asking questions forever. By halfway, have a KPI and a first option on the board. The lesson "Discovery" goes deeper on the questions.

### The learning round

Prep guides and candidate reports on Palantir's loop describe an interviewer who acts as your reference while you learn an unfamiliar concept, API or system and then build on it. The score is your learning curve: whether you ask precise questions, check your understanding by summarising, and build on what you were told. Practise by reading an unfamiliar open-source repository for 20 minutes, then explaining one module aloud and adding a small feature.

### AI system design

The lesson "The design interview" covers the structure. The FDE twist is that the client's constraints are the problem, not noise: data that must stay in India, an existing vendor stack, a fixed budget, a small team who will maintain it after you leave. Tie each choice to one of those, and include evals, a human fallback and a handover plan.

### Client role-play

An interviewer plays a client who is sceptical, impatient or changing requirements. Use five moves:

1. **Summarise** what you heard in one sentence.
2. **Find the need behind the demand.** Ask what is driving the date or the request.
3. **State the risks as facts**, not as fears: what is untested, what could go wrong, who would be affected.
4. **Offer two options with trade-offs** and let the client choose.
5. **Close** with the next step, an owner, a date and written confirmation.

| Situation | Weak response | Strong response |
| --- | --- | --- |
| "Make it live for all branches next week" | "Sure, we'll try" or "Impossible" | Ask what drives the date; name the risks; offer a board demo or a partial rollout |
| "The AI made a mistake; we're cancelling" | Defend the model | Ask what happened, look at the case, explain the safeguards and a fix plan |
| "Add this feature too" | Agree on the spot | "Let me size it and come back with options by Thursday" |
| Silence after your proposal | Keep talking | Ask a direct question: "Which of these fits your board timeline?" |

The lesson "Managing scope creep" covers sizing a new request in more depth.

### Behavioural questions and the project deep-dive

Prepare six to eight stories using STAR (situation, task, action, result), each with a measured result and a lesson. Cover a project you drove end to end, a disagreement with a stakeholder, a failure, a time you said no, working with ambiguity, and learning something fast. Say "I" for what you did and "we" only for the team's work.

Here is a strong story. Situation: "Our team's monthly sales report took three days of manual spreadsheet work." Task: "I was asked to speed it up." Action: "I mapped the steps, automated the data pulls and checks in Python, and added a validation step the analysts reviewed." Result: "Over the next three monthly cycles it took about four hours each time, and errors found after release fell from five a month to none." Lesson: "I should have involved the analysts earlier; their checks caught two edge cases I missed." The result has a before, an after, a period and a way it was measured.

In a project deep-dive, expect "why not X?" on every choice: prepare the alternative you rejected and why.

### The take-home

- **Respect the time box.** If it says four hours, spend about four and write the real number in the README. Twenty polished hours tells them you ignore constraints.
- **Make one path work end to end** before adding breadth.
- **Write a README**: how to run it in one command, assumptions, trade-offs, what you would do next.
- **Show evidence**: a few tests, or a small eval on labelled examples, with the failures listed honestly.
- **If you present it**, start with the client's problem and result, then the design.
- **Follow the AI-tool rules** you were given, and say how you used any tools you were allowed.

### No client experience yet

Most learners on this path have never had a paying client. You still have stories. A professor, an internship manager, a hackathon judge, a family business or an NGO can be the "client". For each, note what they asked for, what they needed, one disagreement and one number. Better still, build something small for a real person, such as a low-stock alert sheet for a kirana shop, and keep notes. Your capstone case study (see the lesson "A case study, end to end") can supply a project deep-dive.

## A worked example

Arjun has one week before his loop. His plan:

| Day | Focus | Output |
| --- | --- | --- |
| 1 | Recruiter questions; list of rounds | Round list, timings and AI-tool rules in one note |
| 2 | Coding | Two 30-minute tasks: the CSV cleaner above and a structured-output call with retries |
| 3 | Decomposition | Two timed, recorded attempts on "a state transport corporation wants fewer complaints" |
| 4 | Behavioural | Six STAR stories written, each read aloud in under two minutes |
| 5 | Role-play | Two role-plays with a friend playing the client |
| 6 | System design | One design for a policy assistant for bank branch staff |
| 7 | Full mock | One mock round of each type; rest in the evening |

On day 3 his first recording shows him proposing a chatbot after three minutes. His second attempt spends twelve minutes on questions and lands on a KPI of complaints per lakh passenger trips.

In the real loop, the role-play goes like this. The interviewer plays Meera, head of branch operations at a private bank in Mumbai. The pilot assistant answers policy questions for staff in 12 of the bank's 180 branches.

> **Meera:** "This pilot is moving too slowly. Our MD wants it live in all 180 branches by next Friday."
>
> **Arjun:** "Let me check I have this right: the MD wants every branch live by Friday because the pilot feels slow. What is happening next Friday?"
>
> **Meera:** "The board meets. He wants to show we are ahead on AI."
>
> **Arjun:** "That helps. So the real goal is a strong story for the board. Two facts matter. Your security review is not finished, and in two pilot branches fewer than half the staff use the assistant yet. If we switch on 180 branches without the review, your security team can stop it, and the board hears about a rollback."
>
> **Meera:** "So you are saying no."
>
> **Arjun:** "I am saying there are two ways to give the MD something real by Friday. One: a board demo with live pilot numbers and a dated three-wave rollout plan. Two: switch on full use in the five pilot branches that are ready, if your security team can finish a fast review by Monday. The first is safer; the second shows more but depends on the review."
>
> **Meera:** "The board will like real branches. Let's try option two."
>
> **Arjun:** "Then I will send your security team the review pack today, and we decide by Monday, 5 pm. If it is not cleared, we fall back to the demo. I will confirm this by email within the hour, with owners and dates."

All five role-play moves are there, plus a fallback. When Meera says "so you are saying no", he does not argue; he goes back to the options.

In the behavioural round he uses the sales-report story above (three days to about four hours) and a second one from a college project, where nightly failed data jobs fell from 12% to 1% over a month after he added retries and alerts.

## Common mistakes

- **Preparing only for coding.** Decomposition and role-play need the same timed practice.
- **Jumping to a solution.** Ask about the goal, the process and the data first, aloud.
- **Asking questions without driving.** By halfway through a decomposition round, put a KPI and a first option on the board.
- **Saying yes to everything, or flatly no.** Interviewers test whether you can size a request and give the client a real choice.
- **Stories without results.** Every story needs a before and an after, how it was measured, your own part and a lesson.
- **Generic system designs.** Tie each choice to the client's constraints.
- **Overbuilding the take-home.** Going far past the time box hides your judgement instead of showing it.
- **Ignoring the AI-tool rules.** Ask what is allowed in each round and follow it.

## Practice

Read the Tech Interview Handbook's behavioural guide and the a16z essay on the FDE role.

1. Write six STAR stories from your own work or projects, each with a measured result and a lesson. Read each aloud in under two minutes.
2. Do the CSV-cleaning task above in 30 minutes, with tests, speaking aloud as you go.
3. Do three timed decomposition exercises (30 minutes each) on Indian business problems you choose. Record yourself and note how many minutes passed before your first proposal. Under five means you jumped.
4. Ask a friend to play a difficult client using one of the scenarios in this path's lessons. Practise all five role-play moves and end with an owner and a date.

**You are done when you can** decompose an unseen business problem into questions, a KPI and a gated proof of concept in 30 minutes, out loud, and handle a role-play client's unrealistic demand without caving or refusing.
