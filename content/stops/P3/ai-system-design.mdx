## What it is

**AI system design** is planning an AI product on paper before or while you build it. It covers who it serves and how success is measured, its components and how a request flows through them, where it can fail, and how it is evaluated and run in production. A short design document lets a team agree on decisions, spot risks early and explain the system to clients and reviewers.

```flow
User, an underwriter -> Web app -> API service -> Input guardrails
Input guardrails -> Hybrid search | department filter + effective date
Hybrid search -> Reranker -[top 5]-> Model in the insurer's cloud region
Model in the insurer's cloud region -[outage]-> Fallback model
Model in the insurer's cloud region -> Output guardrails -> Answer with citation links
Fallback model -> Output guardrails
```

Around it: masked tracing, evals in CI, and dashboards for latency, cost, feedback and refusals.

This lesson follows a design for an internal underwriting assistant at a general insurer in Mumbai.

## How it works

A practical design document, two to four pages, covers:

**1. Users and goals.** Who uses it, for what task, and the success metric with a baseline (for example, "reduce median time to answer policy questions from 6 minutes to under 2").

**2. Requirements and constraints.** Volume and peak load, latency budget, cost per request, languages, data residency, privacy and compliance rules, who may see which data.

**3. Components.** Interface; API service; retrieval (document ingestion, parsing, chunking, embeddings, index, hybrid search, reranking); prompt and model choices (and a fallback model); tools; guardrails; human review points; logging, tracing and evaluation.

**4. Request flow.** Step by step, what happens to one request, with the data passed at each step. A simple diagram helps.

**5. Failure modes and guards.** For each component, what can go wrong and what catches it:

- retrieval misses → hybrid search, metadata filters, evaluation of recall;
- hallucination → grounding, citations, refusal when sources are silent;
- injection → least privilege, data marking, approvals;
- provider outage → retries, fallback model, graceful error;
- runaway cost → caps, budgets, alerts;
- stale data → re-indexing pipeline, freshness alerts.

**6. Evaluation.** The test set (size, sources, categories), metrics for retrieval and answers, the launch bar, and how regressions are caught in CI.

**7. Operations.** Deployment, monitoring signals, alerts, on-call, release process, and data retention.

**8. Open questions and trade-offs.** What you have not decided yet and the options.

If you are building rather than interviewing, grow the system one layer at a time instead of drawing every box on day one. The lesson on growing an AI app in layers (context, guardrails, router and gateway, caches, agents) covers that order.

**A failure-mode table:**

| Component | What can go wrong | Guard |
| --- | --- | --- |
| Parsing | Scanned tables garbled | Table extraction; flagged pages reviewed |
| Retrieval | Superseded circulars ranked first | Effective-date filter |
| Retrieval | Right passage missed | Hybrid search, reranker, recall tracked |
| Generation | Unsupported claims | Citations required; refusal when sources are silent |
| Documents | Injection in uploaded files | No write tools; content treated as data |
| Provider | Outage or rate limits | Retries, fallback model, clear message |
| Cost | Runaway usage | Per-user caps, daily budget alert |

**Reviewing a design.** Walk through one request from the user's tap to the answer. At each box, ask three questions: what data is here, who may see it, and what happens if this part fails or is slow. Invite a security or compliance reviewer to the walk-through early. Questions such as "where is this data stored?" are cheap in week one and expensive in week ten.

**Keeping it current.** Treat the document as living. When a decision changes, update the page and note the date and reason in a short decision log at the end. New team members and client reviewers then read one accurate page instead of reconstructing history from chat threads.

**Back-of-envelope numbers in code.** Capacity, rate limits and cost decide many design choices; work them out before drawing boxes:

```python
def estimate(daily_requests, busy_hours=8, peak_factor=2.5,
             in_tokens=3_500, out_tokens=350, price_in=3, price_out=15, usd_to_inr=84,
             tpm_limit=400_000):
    """Prices in USD per million tokens; check current prices and note the date."""
    peak_per_min = daily_requests / (busy_hours * 60) * peak_factor
    tokens_per_min = peak_per_min * (in_tokens + out_tokens)
    cost_day = daily_requests * (in_tokens * price_in + out_tokens * price_out) / 1e6 * usd_to_inr
    return {
        "peak requests per minute": round(peak_per_min, 1),
        "peak tokens per minute": round(tokens_per_min),
        "within rate limit": tokens_per_min < tpm_limit,
        "cost per day ₹": round(cost_day),
        "cost per month ₹": round(cost_day * 30),
    }

print(estimate(daily_requests=20_000))
```

If peak tokens per minute exceed the provider limit, the design needs a higher tier, caching, a smaller model for some steps or a queue. If the monthly cost surprises the client, find out now, not after launch.

**A latency budget, step by step.** Write down a target and an allowance for each step, then measure against it:

| Step | Allowance (p95) |
| --- | --- |
| Auth, parsing the request | 50 ms |
| Query rewrite (small model) | 400 ms |
| Hybrid search | 150 ms |
| Reranking 30 candidates | 250 ms |
| Model, time to first token | 1,200 ms |
| Total to first token | about 2 s |

Each component owner now has a number. When the total slips, the trace shows which step broke its allowance.

**The architecture in layers.** A useful order for adding parts, from essential to optional: the model call with good context (retrieval, tools); guardrails on inputs and outputs; a router and gateway (several models, fallbacks, keys, budgets); caching; and finally agent patterns with write actions. Each layer adds capability and new failure modes, so add one when a measured need appears.

**Design decisions as records.** Keep a short decision log in the document: date, decision, options considered, reason, who agreed. For example: "2026-11-02: hybrid search with reranker; vector-only missed policy codes (recall 71% vs 89%); agreed with client IT." Later reviewers and new team members see why, not just what.

**A template to start from.** Store the design document as Markdown in the repository with the eight headings in this lesson, the estimate output, the latency budget, the failure-mode table and the decision log. Review it in pull requests like code.

## A worked example

Design summary for an internal assistant at a Mumbai general insurer, answering underwriters' questions from 2,000 policy wordings, circulars and underwriting guidelines:

- *Goal*: underwriters' lookup time from 6 minutes to 2; launch bar 85% correct with citations on a 120-question test set, 100% of "not covered by documents" questions refused.
- *Constraints*: 300 users, peak 40 requests a minute, first token under 2 s, data in India, access by department.
- *Components*: layout-aware parsing with OCR for old circulars; 400-token chunks with section paths; hybrid search with department filters and a reranker; a mid-sized model through the insurer's cloud region with a fallback; citations rendered as links; tracing with masked logs.
- *Failure modes*: superseded circulars (effective-date filter), scanned tables (table extraction, flagged pages), injection via uploaded documents (no write tools), outage (fallback, then a clear message).
- *Evaluation*: recall at 5, answer correctness by a calibrated judge plus underwriter review of 30 answers a month; fast checks in CI.
- *Operations*: container service, dashboards for latency, cost, feedback and refusal rate, re-indexing nightly.

The document took two days and prevented a month of rework when the compliance team asked about data residency in week one.

| Design element | Decision |
| --- | --- |
| Goal | Lookup time from 6 minutes to 2 |
| Launch bar | 85% correct with citations on 120 questions; 100% refusal on out-of-scope ones |
| Constraints | 300 users, 40 requests a minute at peak, first token under 2 s, data in India |
| Payoff | Compliance's week-one residency question answered from the document, avoiding a month of rework |

## Common mistakes

- **Starting from the model instead of the user and metric.**
- **No failure analysis.** Every component fails somehow.
- **No evaluation plan.** "We'll see how it does" is not a plan.
- **Ignoring constraints.** Latency, cost and data rules shape the design.
- **Long documents nobody reads.** Two to four clear pages.
- **Skipping the capacity and cost estimate**, then discovering rate limits or the bill after launch.
- **One latency target for the whole system** with no allowance per step.
- **Design decisions with no recorded reason**, so they get relitigated every month.

## When a full design document is overkill

- **A one-week prototype** to test an idea: a half-page note with the goal, the data and the success measure is enough.
- **A small internal tool** with few users and no sensitive data.
- **A change inside an existing system**, which needs an update to its design document, not a new one.

## From demo to production

- **Keep the design document in the repository**, updated with every major change.
- **Re-run the capacity and cost estimate** when traffic, models or prices change.
- **Measure each step against its latency allowance** from traces.
- **Maintain the decision log** with dates and reasons.
- **Review failure modes** after every incident and add new rows.
