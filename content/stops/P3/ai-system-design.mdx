## What it is

**AI system design** is deciding, on paper, what an AI product is made of and proving with numbers that it will work. A good design answers six questions: what are the parts, what data crosses each arrow, what does one request cost, how long does the user wait, what breaks and how would we know, and how will we measure quality?

"The design interview" covers presenting one under a clock; this lesson covers what goes in it.

A product that answers from documents has two pipelines: **ingestion** runs offline and turns documents into an index; the **request path** runs on every question. Most quality problems start in ingestion, so draw both.

```flow
title: Underwriting assistant, the request path
Underwriter's question -> API service | login, department, per-user cap
API service -> Input checks | mask personal data, flag injection
Input checks -> Query rewrite | small model
Query rewrite -> Hybrid search | department and effective-date filters
Hybrid search -[top 40]-> Reranker
Reranker -[top 6]-> Main model | answers only from the passages, with citations
Main model -[outage]-> Fallback model
Main model -> Citation check
Fallback model -> Citation check
Citation check -[passes]-> Answer with links to clauses
Citation check -[fails]-> Refusal and route to a senior underwriter
```

```flow
dir: LR
title: The ingestion pipeline, nightly
New wordings and circulars -> Parser and OCR | tables kept as tables -> Chunker | 400 tokens with section path -> Embeddings and keyword index -> Index | version, effective date, department
```

The lesson follows one design: an assistant for 300 underwriters at a general insurer in Mumbai, answering from 2,000 policy wordings, circulars and guidelines. All volumes, token counts and timings are this design's assumptions, not measurements from a real insurer.

## How it works

### Start from the user and the constraints

Write the goal as a metric with a baseline: "median time to answer a policy question, from 6 minutes to under 2." Then list constraints that change a box or a number.

- **Who reads the answer, and what does a wrong one cost?** A trained underwriter, but a wrong exclusion can misprice a policy. So every answer cites a clause.
- **Volume and peaks.** 300 users, about 25 questions each a working day, mostly within 8 busy hours.
- **Data rules.** Documents, the index and logs stay in India. Whether model calls may be processed outside India is for the compliance team to decide, and it decides between calling a provider directly and a cloud provider's regional endpoint, if one in India offers the chosen model. Ask in week one.
- **Access.** Motor underwriters must not see health reinsurance treaties, a rule that shapes the search.

### The decisions every design must state

A list of boxes is not a design. Name the big choices and the reason for each.

| Decision | This design's choice | Change it when |
| --- | --- | --- |
| Prompt only, retrieval or fine-tuning | Retrieval: documents change monthly and answers need citations | The need is format or style at volume, not knowledge (see "Prompting, RAG or fine-tuning") |
| Long context or retrieval | Retrieval: about 25 million tokens of documents against a 1-million-token window | The corpus is small and stable, and caching keeps it cheap |
| Model tier | Mid-sized model for answers; small model for query rewriting | The small model meets the launch bar for a whole category |
| Hosted API or self-hosted open weights | Hosted, region set by compliance | Data may not leave your servers, or steady volume keeps GPUs busy |
| Vector store | Postgres with a vector extension | The index outgrows one machine |
| Streamed or batch | Streamed: a person is waiting | Nobody waits: a batch API costs half |

Size the index before choosing a database. Suppose 2,000 documents average 25 pages of about 500 tokens: 25 million tokens, or 62,500 chunks of 400 tokens. At 1,024 numbers per embedding and 4 bytes each, that is about 256 MB of vectors, which fits in memory on one ordinary server. A distributed vector database would add cost for no gain.

### Trace one request, with the data at each step

Note what each step receives and passes on; privacy and cost problems show up here.

1. **API service.** Receives the question, user id and department; rejects users over their daily cap.
2. **Input checks.** Mask policy and phone numbers before logging; flag text that tries to instruct the model.
3. **Query rewrite.** A small model turns "does the fire one cover riots" into a query with the policy name: about 300 tokens in, 40 out.
4. **Hybrid search.** Keyword and vector search run in parallel, filtered by department and effective date. Keyword search catches policy codes and clause numbers, exact strings that embeddings often miss.
5. **Reranker.** Scores the top 40 candidates and keeps 6.
6. **Main model.** Receives about 1,500 tokens of fixed instructions (identical on every call, so cached) and 2,700 fresh tokens: six 400-token passages plus the question. It writes about 350.
7. **Citation check.** Plain code: every cited clause id must exist in the passages sent, or the answer is refused and routed to a person.

Access control lives in step 4. Filter after the answer and the model has already read text the user may not see.

### Numbers before boxes: load, limits and cost

```python
# Anthropic list prices, US dollars per million tokens, checked 28 November 2026
SONNET = {"in": 2.00, "cache_read": 0.10, "out": 10.00}   # Claude Sonnet 5.5
HAIKU = {"in": 0.10, "out": 0.50}                          # Claude Haiku 5.5, prompts up to 100,000 tokens

def estimate(users=300, questions_per_user=25, work_days=22, busy_hours=8, peak_factor=2.5,
             cached_in=1_500, fresh_in=2_700, out=350,   # main model, tokens per question
             rewrite_in=300, rewrite_out=40,             # small model rewrites the query
             usd_to_inr=94, fixed_inr_month=60_000):     # suppose: search, hosting, tracing
    daily = users * questions_per_user
    peak_per_min = daily / (busy_hours * 60) * peak_factor
    usd = ((fresh_in * SONNET["in"] + cached_in * SONNET["cache_read"] + out * SONNET["out"])
           + (rewrite_in * HAIKU["in"] + rewrite_out * HAIKU["out"])) / 1e6
    month_inr = daily * work_days * usd * usd_to_inr + fixed_inr_month
    return {
        "peak questions a minute": round(peak_per_min),
        "peak uncached input tokens a minute": round(peak_per_min * fresh_in),
        "peak output tokens a minute": round(peak_per_min * out),
        "model cost per question (rupees)": round(usd * usd_to_inr, 2),
        "model spend a month (US dollars)": round(daily * work_days * usd),
        "total a month (rupees)": round(month_inr),
        "per user a month (rupees)": round(month_inr / users),
    }

print(estimate())
# {'peak questions a minute': 39, 'peak uncached input tokens a minute': 105469,
#  'peak output tokens a minute': 13672, 'model cost per question (rupees)': 0.86,
#  'model spend a month (US dollars)': 1502, 'total a month (rupees)': 201141,
#  'per user a month (rupees)': 670}
```

The ₹94 to the dollar and ₹60,000 of fixed costs are illustrative. Compare it with published limits. On the Claude API, as of November 2026, the lowest standard tier (Start) allows Sonnet 5.5 2,000,000 input tokens and 400,000 output tokens a minute. Cache reads do not count towards the input limit. So peak load uses about 5% of it: the rate limit is not the problem.

The monthly bill is. Each tier also has a monthly spend cap: $500 for Start, $1,000 for Build and $200,000 for Scale. At about $1,500 a month, this design would stop partway through the month on either lower tier, with errors retries cannot fix. The design must name the tier or cloud contract and set a lower budget alert. Cloud platforms set their own quotas, and their regional and multi-region endpoints cost 10% more than global ones, per Anthropic's pricing page, so redo the sum for the route compliance picks.

Fresh input is the biggest cost: $0.0054 (2,700 tokens at $2 per million) of the $0.0091 per question. Sending 4 passages instead of 6 saves about 18%, if recall holds on the eval set. Cache writes are left out: at this traffic the cached prefix rarely expires. Fixed costs are 30% of the total, so cost per user falls as usage grows.

### A latency budget, step by step

Underwriters read the answer as it streams, so the target is first visible text in under 2 seconds for 95 in 100 questions (p95).

| Step | Allowance (p95) |
| --- | --- |
| Login, cap and input checks | 50 ms |
| Query rewrite, small model | 300 ms |
| Hybrid search, keyword and vector in parallel | 150 ms |
| Reranking 40 candidates | 200 ms |
| Main model, time to first token | 1,000 ms |
| Total, with about 300 ms spare | 1.7 s |

Summed p95s overstate the real p95, since steps are rarely all slow at once, so the budget is safe, not exact. If the model streams, for example, 60 tokens a second, the 350-token answer needs about 6 seconds more. When the total slips, the trace shows which step broke its allowance. The query rewrite is the first step to cut.

### Failure modes, how you detect them, and the guard

A failure row is useful only if someone would notice the failure, so give every row a detection signal.

| Component | What goes wrong | How you would know | Guard |
| --- | --- | --- | --- |
| Parsing | Scanned tables become jumbled text | Per-document parse score | Table extraction; flagged pages checked before indexing |
| Index | A superseded circular ranks first | Dated trap questions in the eval set fail | Effective-date filter; old versions kept but marked |
| Search | The right clause is missed | Recall at 5 on the eval set, tracked weekly | Hybrid search, reranker, query rewrite |
| Access | A user sees another department's treaty | CI test with a user from each department | Permission filter inside the search |
| Model | A claim the passages do not support | Citation check failures; judge score on sampled traffic | Answer only from passages, or refuse |
| Documents | Instructions hidden in an uploaded file | Injection flags in traces | No write tools; passages marked as data, not instructions |
| Provider | Outage, rate limit or ramp limit errors (429) | Error rate and fallback share | Retries with backoff, fallback model, clear message |
| Cost | Usage runs away | Daily spend against budget | Per-user caps, an alert at 80% of budget |

### Human review: where, and how much

Put people where the model is weakest and mistakes cost most. Here, refused and low-scoring answers go to a senior underwriter, new circulars are checked before indexing, and 30 answers a month are sampled.

Then size it. At 7,500 questions a day, if 4% are routed, that is 300 reviews. At 3 minutes each, that is 15 hours a day, about two full-time reviewers. If the client cannot staff that, fix retrieval or route fewer kinds of question. An unstaffed queue is not a guard.

### Evaluation and the launch bar

Build the test set from real questions, by category, for example 60 single-document questions, 25 needing two documents, 15 superseded-circular traps, and 20 the documents do not cover, which must be refused. Measure retrieval (recall at 5: is the right clause in the top five?) and answers (correct and cited, scored by a model judge checked against underwriter labels).

Know what a small set can show: 85% correct on 120 questions has a 95% margin of about 6 points either way. So a 2-point difference between two models is noise. And 20 refusals out of 20 still allows a true failure rate of about 15%. Grow the traps as real traffic arrives. Run fast checks on every prompt or model change in CI: 120 questions at about ₹0.86 each is about ₹100 a run, plus the judge.

### Keep the document alive

Keep it as Markdown in the repository, reviewed in pull requests, ending with open questions and a decision log: date, decision, options, reason, who agreed. For example: "2026-11-02: hybrid search with a reranker. Vector-only search missed policy codes (recall at 5: 71% against 89% on the eval set). Agreed with client IT." Walk a compliance reviewer through it in week one, when "where is this stored?" is still cheap to answer.

## A worked example

Page one of the insurer's design document:

| Section | Content |
| --- | --- |
| Goal | Median lookup time from 6 minutes to under 2 for 300 underwriters |
| Launch bar | At least 85% correct with citations on 120 questions; all 20 out-of-scope questions refused; recall at 5 of 85% or more |
| Load and cost | 7,500 questions a day, 39 a minute at peak; ₹0.86 of model cost a question; about ₹2 lakh a month, ₹670 per user, prices checked 28 November 2026 |
| Latency | First text under 2 s at p95; full answer in about 8 s |
| Components | Nightly ingestion with OCR and table extraction; hybrid search with department and date filters; reranker; mid-sized model with a tested fallback; citation check |
| Human review | About 4% of questions to senior underwriters, about two reviewers' time; 30 answers a month sampled |
| Open questions | May model calls leave India? Which API tier or cloud contract covers about $1,500 a month? |

What the numbers changed before any code:

1. **The spend cap.** The bill is above two tiers' monthly caps, so a contract decision went into the plan, instead of a stopped service in week three.
2. **The review queue.** The client had assumed "occasional" review; two people's hours made them fund retrieval work and a rota.
3. **The vector store.** 256 MB of vectors fits the insurer's existing Postgres: one less vendor to review.
4. **The compliance question.** Raised in week one, so the model route was settled before the gateway was built.

Now test it with a change. Suppose 2,700 claims staff join next year. Ten times the users gives about 390 questions a minute and about 1.05 million uncached input tokens a minute at peak: still under the Start tier's input limit, but about $15,000 a month. Cost per user falls to about ₹490, because fixed costs are shared. The first thing to break is the review queue: 4% of 75,000 is 3,000 reviews a day, so the routed share must fall first.

## Common mistakes

- **Boxes with no numbers.** Symptom: no box has an owner, a latency allowance or a failure row, so reviewers cannot challenge it.
- **Drawing only the request path.** Symptom: no parsing, versions or effective dates, until a stale circular reaches a user.
- **Checking the rate limit but not the spend cap.** Symptom: "well under our tokens-per-minute limit", with no monthly bill and no price check date.
- **Filtering access after generation.** Symptom: "the UI hides restricted answers". The model has already read the restricted text.
- **A failure table with no detection column.** Symptom: guards for failures nobody would notice.
- **Unsized human review.** Symptom: "uncertain answers go to a human", with no share, minutes or team.
- **Trusting a small eval set.** Symptom: choosing a model on a 2-point gain over 120 questions, or calling 20 out of 20 refusals proof.
- **A long document nobody reads.** Two to four pages, summary table first.

## When a full design document is overkill

- **A one-week prototype:** a half page with the goal, the data, the success measure and a rough cost per request.
- **A small internal tool** with few users and no sensitive data.
- **A change inside an existing system:** update its document and decision log instead.

## From demo to production

- **Re-run the estimate** whenever traffic, models, token counts or prices change, and date the prices.
- **Compare traces with the latency budget** weekly.
- **Put every detection signal on the dashboard**, with alerts for fallback use, spend and refusal rate.
- **Add a failure row after every incident.**
- **Re-size human review monthly.**
