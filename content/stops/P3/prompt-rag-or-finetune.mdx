## What it is

When a language model does not do what you need, the fix depends on what is actually wrong. There are two kinds of problem, and five main tools.

**The model lacks knowledge** (your policies, a customer's account, this week's prices). Bring the knowledge in at query time, in the prompt:

- **Long context**: put whole documents in the prompt. With **prompt caching**, the provider stores an unchanged start of the prompt, so repeat calls read it cheaply.
- **RAG (retrieval-augmented generation)**: search your documents and put only the few best passages in the prompt.
- **Tools and agentic search**: let the model call a database, an API or a search tool, read the result and search again if needed.

**The model knows enough but behaves wrongly** (format, tone, steps, edge cases):

- **Prompting**: clearer instructions, examples, and the API's **structured output**, where you give a JSON schema and the reply must match it.
- **Fine-tuning**: train the model further on your examples so the behaviour is built in. This changes the model's weights, so it is the slowest and least reversible fix.

The short rule: knowledge goes into the context; behaviour goes into the prompt first and into the weights last.

```flow
title: Diagnose before you choose
What is wrong? -[it does not know something]-> Bring knowledge in at query time
What is wrong? -[it knows, but does it wrong]-> Prompting and structured output
Bring knowledge in at query time -[small, stable, asked about often]-> Long context with caching
Bring knowledge in at query time -[large, changing or per-user]-> RAG
Bring knowledge in at query time -[live records or several lookups]-> Tools or agentic search
Prompting and structured output -[still costly or inconsistent at high volume]-> Fine-tune, often a small model
```

Mature systems combine these, and every option is measured on the same test set. This lesson follows three problems at a software company in Pune that each needed a different fix.

## How it works

### Step 1: diagnose knowledge versus behaviour

Read 20 to 30 failed outputs before choosing anything. For each one ask: was the needed fact in the prompt? If not, it is a knowledge problem, and no amount of instruction or training on style will fix it. If the fact was there and the answer still came out wrong, in the wrong format or in the wrong tone, it is a behaviour problem. Many teams skip this and fine-tune a model to fix what was really missing context.

### Step 2: fix behaviour with the prompt first

Prompting is fast, cheap and reversible: you can test a change in minutes. Spend an afternoon before anything bigger. State the task and output format plainly, add two or three good examples including an edge case, and run your test set. This also sets the fair baseline that every later option must beat.

For **format** problems, use the API's structured output: you supply a JSON schema and the provider only lets the model produce replies that fit it. The shape is then guaranteed, though values can still be wrong, so validate them in code. The lesson on structured output covers this. Fine-tuning purely to get valid JSON is usually a mistake in 2026.

### Step 3: bring knowledge in the cheapest reliable way

All three options put facts in front of the model at query time. Updating means changing a document or a database row, not retraining.

**Long context with caching.** As of November 2026, Anthropic's latest Claude models accept 1 million tokens of input. Caching changes the cost a lot. Anthropic list prices for Claude Sonnet 5.5, checked on 28 November 2026: input $2 per million tokens, cache read $0.10 (5% of input), 5-minute cache write $2.50, output $10. So on Sonnet 5.5 a cached corpus costs less per question than a RAG prompt whenever the corpus is under about 20 times the RAG context. A 60,000-token handbook read from cache costs the same as 3,000 fresh tokens. Other models and providers price caching differently (on Claude Haiku 5.5 a cache read is 10% of input), so redo the sum for yours.

The catches: the cache expires after 5 minutes without use by default, so it only pays with steady traffic; any change at the start of the prompt breaks it; accuracy falls in very long inputs (the "lost in the middle" effect); and long inputs slow the first token. The lesson "Long context or RAG" covers these in depth.

**RAG.** Use it when the corpus is large (far beyond what you want to pay for per call), changes often, must respect each user's permissions, or answers must cite a passage. It needs chunking, indexing and tuning, and it misses whatever the search misses.

**Tools and agentic search.** For live, structured data (a fixed-deposit rate, an order status, a balance), query the system of record through a tool. RAG over documents can return an old figure; a database query cannot. Agentic search, where the model runs its own searches step by step, fits questions where the next lookup depends on the last. It costs more: each step re-sends the growing conversation. For example, six steps that each add 3,000 tokens of results to 2,000 tokens of instructions send 57,000 input tokens in total, against about 4,000 for one RAG call.

### Step 4: fine-tune only for form, at volume

Fine-tuning fits a narrow task with many good examples where prompting works but is too long, too costly, too slow or still inconsistent at high volume: a classification with 30 labels, a house style across millions of replies, a small model that must match a large one.

**Facts belong in retrieval.** Two EMNLP 2024 papers are worth knowing by name. Ovadia and colleagues ("Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs") found RAG beat unsupervised fine-tuning for both familiar and entirely new knowledge. Gekhman and colleagues ("Does Fine-Tuning LLMs on New Knowledge Encourage Hallucinations?") found, in supervised closed-book question answering, that examples with new facts are learned slowly and, once learned, increase hallucination. Models mostly get facts from pre-training; fine-tuning teaches them how to use what they know.

"Fine-tuning" covers several methods with different data needs:

| Method | Training data | Typical use |
| --- | --- | --- |
| Supervised fine-tuning (SFT) | Inputs paired with ideal outputs | Format, style, classification, extraction |
| Preference tuning, for example DPO | Pairs of a better and a worse answer | Tone, helpfulness, what to refuse |
| Reinforcement fine-tuning | Prompts plus a grader that scores answers | Tasks with checkable answers, few labels |
| Distillation | A large model's outputs as SFT data | A small, cheap model copying a large one on one task |

Most teams use LoRA, which trains a small add-on to the model instead of all its weights; the lessons on how fine-tuning works and fine-tuning in practice cover the methods. Two practical checks come before any plan. First, availability: not every model offers fine-tuning, and the offer changes. OpenAI posted an update dated 8 May 2026 saying it is winding down its fine-tuning platform, which is no longer accessible to new users. Check your provider's documentation and write down the date. Open-weight models you train and host yourself avoid this risk but need GPUs and skills. Second, for distillation, read the terms of use: many providers forbid using their outputs to train competing models.

### The options compared

| Factor | Prompting and structured output | Long context, cached | RAG | Tools | Fine-tuning |
| --- | --- | --- | --- | --- | --- |
| Fixes | Behaviour, format | Missing knowledge, small corpus | Missing knowledge, large corpus | Live, structured data | Consistent form at volume |
| Time to try | Minutes | Hours | Days | Days | Weeks |
| Updating | Edit the prompt | Change the document | Re-index | None, data is live | Retrain |
| Cost per request | Grows with prompt length | Low if the cache stays warm | Retrieval plus a short prompt | One call per lookup | Low with a small model |
| Main risk | Long prompts at volume | Cache misses, lost in the middle | Search misses | Tool errors, slow multi-step | Stale, costly upkeep |

### Measure every option on one test set

Use the same questions, graders and cost and latency measurements for every candidate. Split the test set by problem type: questions that need private or recent facts, and questions about format or behaviour. The knowledge options should win the first group; if they do not, your diagnosis was wrong.

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.3f}{p95:>8.0f}")
    return rows
```

### Price fine-tuning against the best cheap baseline

Compare the monthly saving with the build cost over a short useful life. Build cost means people's time to collect and check data and run evals, not only GPU hours. A short life is realistic, because a better base model often arrives within months and the work repeats.

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.414, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
print(finetune_break_even(2_000_000, 0.056, 0.01, build_cost_inr=400_000, upkeep_per_month_inr=40_000))
```

The worked example below explains the inputs. The first line prices fine-tuning against an uncached large model: a saving of ₹7.68 lakh a month and break-even in 0.5 months. The second prices it against the same model with the prompt cached: a saving of ₹52,000 a month, 7.7 months to break even and a net loss of ₹88,000 over six months. Same fine-tune, opposite answer. Always price against the cheapest option that already works.

## A worked example

Three problems at a Pune software company. All costs are illustrative: they use the Claude Sonnet 5.5 and Haiku 5.5 list prices checked on 28 November 2026, an illustrative rate of ₹94 to the dollar, and assumed token counts at low effort, so almost no thinking tokens. Check `usage` in real responses, since thinking bills as output. Accuracy figures are the kind a team would record, not measured results.

**1. The support bot and six weekly-changing handbooks.** The company sells six products, each customer may see only their own product's handbook, and each handbook is about 400,000 tokens. Cached long context, even for one product's handbook, would cost about ₹4.10 per question (400,000 tokens at the cache-read price, plus a 300-token question and a 300-token answer). RAG with about 4,000 tokens of passages costs about ₹1.09. RAG also enforces each customer's permissions with a metadata filter and cites the section it used. So they choose **RAG**, re-indexed on every update.

The crossover matters. Had there been one 60,000-token handbook asked about all day, cached long context would cost about ₹0.90 per question against ₹1.09, need no index, and see every section at once. Test it on cross-section questions and it may be the better choice.

**2. Ticket summaries vary and miss the customer's priority.** The model has the ticket; the instruction is unclear. **Prompting and structured output**: a schema with a required `priority` field limited to four values, one rule on how to judge priority, and two examples. Suppose that on 50 test tickets, correct priority goes from 31 to 46 and the format never breaks again. It took an afternoon.

**3. Classifying 20 lakh log lines a month into 30 categories.** Today they call Sonnet 5.5 with a 2,000-token prompt (category definitions and examples) sent fresh each time, plus about 100 tokens of log line and 20 tokens of output. That is about ₹0.41 a line, or ₹8.3 lakh a month. They have 50,000 labelled lines, and a vendor offers to fine-tune a small open-weight model: suppose ₹4 lakh to build, ₹40,000 a month to maintain, and ₹0.01 a line to serve.

Against today's bill, fine-tuning pays back in two weeks. But first they cache the prompt. At about 46 lines a minute the cache never goes cold, and the 2,000-token prompt is above the 512-token minimum. Cost falls to about ₹0.056 a line (₹1.13 lakh a month) with no change in accuracy. Against that baseline, the same fine-tune takes 7.7 months to pay back. They also try Haiku 5.5 with the same cached prompt: about ₹0.004 a line, ₹7,500 a month, but suppose accuracy falls from 96% to 91%. The lines are not urgent, so the batch API, half price on Anthropic as of November 2026, would cut either bill further.

The volume decides it. Over a six-month life, the inputs above give a break-even volume of about 23 lakh lines a month against the cached baseline. Two new clients will take volume to 1 crore lines a month next quarter. Suppose a pilot fine-tune on 10,000 of the labels scores 96% on the test set, the same as Sonnet. At 1 crore lines the fine-tune saves about ₹4.2 lakh a month and pays back in about a month. Haiku would be cheaper still, but its 5-point gap means about 5 lakh more wrong tags a month. So they **cache the prompt today and fine-tune for the larger volume**, keeping the cached prompt as the fallback and baseline.

| Problem | Diagnosis | Approach | Illustrative result |
| --- | --- | --- | --- |
| Six handbooks of 400,000 tokens each, per-customer access | Knowledge, large and permissioned | RAG with filters, re-indexed weekly | ₹1.09 a question against ₹4.10 for cached long context |
| Summaries miss priority | Behaviour | Schema, a priority rule, two examples | Priority right on 46 of 50, up from 31 |
| 20 lakh log lines a month, rising to 1 crore | Form at volume | Cache now, fine-tune a small model for the larger volume | ₹8.3 lakh to ₹1.13 lakh a month now; fine-tune pays back in a month at 1 crore |

## Common mistakes

- **Fine-tuning to add facts.** Facts belong in the context, through long context, RAG or a tool.
- **Skipping the prompt.** It is the cheapest fix, often enough, and the baseline everything else must beat.
- **Fine-tuning for JSON format** before trying structured output.
- **Building RAG for a small, stable document** that cached long context would handle more simply.
- **Using RAG over documents for live numbers** such as rates or balances, instead of a tool.
- **Pricing fine-tuning against an uncached bill.** Cache the prompt and try a smaller model first, then compare.
- **Leaving people's time out** of the build cost, or assuming a long useful life.
- **Comparing options on different test sets** or with different graders.
- **Planning around a fine-tuning service** without checking that it exists for your model today.

## When the choice is already clear

- **The answer must cite private documents**: retrieval, whatever else you add.
- **The data lives in a database**: a tool, not an index of documents.
- **Low volume**: fine-tuning rarely pays back; improve the prompt.
- **The task changes every few weeks**: prompts and retrieval adapt faster than retraining.
- **You have no labelled examples**: fine-tuning is not possible yet; start collecting them from reviewed outputs.

## From demo to production

- **Keep one test set** split by problem type, and use it for every approach.
- **Record quality, cost and p95 latency** for each option, with dates.
- **Watch the cache hit rate** if you rely on caching; a silent drop can multiply the bill.
- **Recalculate break-even** when prices, volumes or models change.
- **Collect reviewed outputs** as future training data, even if you do not fine-tune yet.
- **Re-test fine-tuned models** against each new base model with a good, cached prompt.
