## What it is

When a language model does not do what you need, there are three main ways to improve it:

- **Better prompting**: clearer instructions, examples, structure and format.
- **RAG (retrieval-augmented generation)**: fetching relevant information from your documents or data and putting it in the prompt.
- **Fine-tuning**: training the model further on your own examples so it learns a behaviour.

They solve different problems and are often combined. Choosing well saves months.

```flow
What is wrong? -[the model does not know something: facts, policies, accounts, recent events]-> RAG or tools | update by re-indexing; cite sources
What is wrong? -[it knows, but does it wrong: format, tone, steps, edge cases]-> Prompting first | instructions, examples, a template
What is wrong? -[prompting works, but is too long, costly or inconsistent at high volume]-> Fine-tune, often a smaller model | needs many good examples and evals
```

Mature systems combine all three, each checked on the same test set.

This lesson follows three problems at a software company in Pune that each needed a different fix.

## How it works

**Diagnose the problem first.**

- *The model does not know something* (your products, policies, recent events, a customer's account): that is a knowledge problem. Use **RAG** or tools. Fine-tuning is a poor way to add facts: it is costly to update and the model may still misremember them.
- *The model knows enough but does the task the wrong way* (format, tone, steps, edge cases): try **prompting** first: instructions, examples, a clearer format.
- *Prompting works but is long, expensive, slow or still inconsistent for a narrow, high-volume task*: consider **fine-tuning** a model, often a smaller one, on many good examples.

**Why prompting first.** It is fast, cheap and reversible: you can test a change in minutes. Many problems blamed on "the model" disappear with clearer instructions and two good examples.

**When RAG fits.** Information that changes often (a handbook updated weekly), is large (thousands of documents), is private, or must be cited. Updating means re-indexing, not retraining.

**When fine-tuning fits.**

- a consistent style or format across very many requests;
- a narrow classification or extraction task with lots of labelled examples;
- making a small, cheap model match a large one on one task;
- shortening prompts that carry many examples.

It needs hundreds to thousands of quality examples, evaluation, and repeating when the base model changes.

**Combine.** A common mature setup: a well-designed prompt, RAG for knowledge, and possibly a fine-tuned small model for one high-volume step. Evaluate each change on the same test set.

**The approaches compared:**

| Factor | Prompting | RAG | Fine-tuning |
| --- | --- | --- | --- |
| Fixes | Behaviour, format | Missing or changing knowledge | Consistent behaviour at scale |
| Time to try | Minutes | Days | Weeks |
| Data needed | A few examples | Your documents | Hundreds to thousands of labelled examples |
| Updating | Edit the prompt | Re-index | Retrain |
| Cost per request | Grows with prompt length | Adds retrieval and context | Can be lowest with a small model |
| Citations | No | Yes | No |

**Estimating when fine-tuning pays off.** Compare the monthly cost of the current approach with the fine-tuned option: training cost spread over its useful life, plus serving cost at your volume, plus the time to build and maintain the training data. Fine-tuning usually pays off for high-volume, narrow tasks where a small model can replace a large one, and rarely for low-volume or fast-changing tasks. Write the calculation down, with the volume at which it breaks even.

**Testing prompt fixes first.** Before any larger change, spend an afternoon on the prompt: state the task and format plainly, add two or three good examples including an edge case, and run the test set. Teams are often surprised how many problems this solves, and it sets a fair baseline for judging RAG or fine-tuning.

**Run all candidates on one test set.** The fairest comparison uses the same questions, the same graders and the same cost and latency measurements:

```python
def compare(approaches, test_set, grade):
    """approaches: dict name -> function(question) returning (answer, cost_inr, latency_ms)."""
    rows = []
    for name, fn in approaches.items():
        scores, costs, lat = [], [], []
        for case in test_set:
            answer, cost, ms = fn(case["question"])
            scores.append(grade(case, answer)); costs.append(cost); lat.append(ms)
        lat.sort()
        rows.append((name, sum(scores) / len(scores), sum(costs) / len(costs), lat[int(0.95 * (len(lat) - 1))]))
    print(f"{'approach':<22}{'quality':>8}{'₹/req':>8}{'p95 ms':>8}")
    for name, q, c, p95 in rows:
        print(f"{name:<22}{q:>8.0%}{c:>8.2f}{p95:>8.0f}")
    return rows

# compare({"prompt v3": prompt_only, "prompt + RAG": with_rag, "fine-tuned small": tuned}, tests, grade)
```

Split the test set by problem type: questions that need private or recent facts, and questions about format or behaviour. RAG should win the first group and fine-tuning may win the second; if not, your diagnosis was wrong.

**When fine-tuning pays off, in numbers.**

```python
def finetune_break_even(requests_per_month, cost_now_inr, cost_tuned_inr,
                        build_cost_inr, upkeep_per_month_inr, life_months=6):
    saving = (cost_now_inr - cost_tuned_inr) * requests_per_month - upkeep_per_month_inr
    total = saving * life_months - build_cost_inr
    months = build_cost_inr / saving if saving > 0 else float("inf")
    return {"monthly saving ₹": round(saving), f"net over {life_months} months ₹": round(total),
            "months to break even": round(months, 1)}

print(finetune_break_even(2_000_000, 0.40, 0.06, build_cost_inr=600_000, upkeep_per_month_inr=50_000))
```

`build_cost_inr` should include people's time to collect and check data and run evals, not just GPU hours. A short `life_months` is realistic: a new base model often arrives within months and the work repeats.

**Facts belong in retrieval.** Studies comparing the two for new knowledge found retrieval usually wins, and fine-tuning on facts the base model never saw can even encourage confident errors. Use fine-tuning to teach form (format, tone, a narrow classification) and retrieval to supply facts.

**Order of attempts.** Prompt, then prompt plus retrieval or tools, then fine-tuning only if a measured gap remains and the numbers above make sense. Each step keeps the previous one as the baseline.

## A worked example

Three problems at a Pune software company:

1. *The support bot must answer from a product handbook that changes every week.* Knowledge that changes: **RAG** over the handbook, re-indexed on every update. Fine-tuning would be out of date within a week.
2. *Ticket summaries vary in format and miss the customer's priority.* The model has the information; the instruction is unclear. **Prompting**: a fixed template, a rule about priority and two examples fix 90% of cases in an afternoon.
3. *Classifying 2 million log lines a month into 30 categories with a large model costs too much.* They have 50,000 labelled lines from past work. **Fine-tune** a small model: on their test set it matches the large model's accuracy at a fraction of the cost and latency.

| Problem | Diagnosis | Approach | Result |
| --- | --- | --- | --- |
| Support bot and a weekly-changing handbook | Knowledge | RAG, re-indexed on each update | Always current |
| Ticket summaries vary and miss priority | Behaviour | Template, a priority rule, two examples | 90% fixed in an afternoon |
| 2 million log lines a month, too costly | Volume on a narrow task | Fine-tuned small model on 50,000 labels | Same accuracy, far lower cost and latency |

## Common mistakes

- **Fine-tuning to add facts.** Use retrieval.
- **Skipping prompting.** It is the cheapest fix and often enough.
- **Choosing by fashion.** Diagnose knowledge versus behaviour.
- **No evaluation set.** You cannot compare approaches without one.
- **Forgetting maintenance.** Fine-tuned models need retraining; RAG needs fresh indexes.
- **Comparing approaches on different test sets** or with different graders.
- **Leaving people's time out** of the fine-tuning cost.
- **Fine-tuning to add facts** that change, which retrieval handles better.

## When the choice is already clear

- **The answer must cite private documents**: retrieval, whatever else you add.
- **Low volume**: fine-tuning rarely pays back; improve the prompt.
- **The task changes every few weeks**: prompts and retrieval adapt faster than retraining.
- **You have no labelled examples**: fine-tuning is not possible yet; start collecting them from reviewed outputs.

## From demo to production

- **Keep one test set** split by problem type, and use it for every approach.
- **Record quality, cost and p95 latency** for each option with dates.
- **Recalculate break-even** when prices, volumes or models change.
- **Collect reviewed outputs** as future training data, even if you do not fine-tune yet.
- **Re-test fine-tuned models** against new base models with good prompts when they appear.
