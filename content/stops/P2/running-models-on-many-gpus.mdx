## What it is

A single GPU has a fixed amount of memory and speed. Two different problems push you to use many:

1. **The model is too big for one GPU.** A 70B model at 16-bit precision needs about 140 GB for its weights alone, more than a single 80 GB GPU.
2. **One copy cannot serve all your users.** Even if the model fits, traffic may need several copies.

There are two basic answers: **copy** the model, or **split** it.

- **Replica parallelism** (called **data parallelism** in training): run full copies on several GPUs. Each copy serves different requests, or trains on different batches.
- **Model parallelism**: split one model across GPUs. The two main ways are **tensor parallelism** (split the work inside each layer) and **pipeline parallelism** (split the layers into groups).

Real systems often combine them: a model split across 4 GPUs, with several such groups as replicas.

```flow
title: Choosing how to spread a model
Model and expected traffic -> Fits on one GPU with KV cache room?
Fits on one GPU with KV cache room? -[yes]-> Replicas | one copy per GPU
Fits on one GPU with KV cache room? -[no]-> Fits inside one server?
Fits inside one server? -[yes]-> Tensor parallelism across its GPUs
Fits inside one server? -[no]-> Tensor inside servers, pipeline across them
Replicas -> Add copies for more traffic | behind a load balancer
Tensor parallelism across its GPUs -> Add copies for more traffic | behind a load balancer
Tensor inside servers, pipeline across them -> Add copies for more traffic | behind a load balancer
```

## How it works

**Replicas.** The simplest and most robust option: every GPU (or group of GPUs) holds a whole model and handles its own requests. More replicas means more throughput, and if one fails the others keep serving. With models of different sizes and GPUs of different memory, deciding what to place where becomes a packing puzzle: three 13B models on one 40 GB GPU, or one 34B model?

**Tensor parallelism.** A layer is mostly matrix multiplication. Split the matrices across, say, 4 GPUs: each computes its slice at the same time, then they exchange results. This makes a too-big model fit, and can reduce latency because the work is shared. The catch is communication: GPUs talk inside every layer, so they need very fast links, such as the high-speed connections between GPUs inside one server. Across slower networks, tensor parallelism usually stops paying off.

**Pipeline parallelism.** Put layers 1 to 20 on GPU 1, 21 to 40 on GPU 2, and so on. A request passes through each stage in turn. Splitting batches into small "micro-batches" keeps all stages busy, which helps training throughput. For serving, each request waits on every stage plus the network hops between them, so pipeline parallelism is avoided when latency matters. It is mostly used to span servers when a model is too big for one.

**Long inputs.** **Context parallelism** splits a very long input across GPUs, and **sequence parallelism** splits the operations on it. They matter mainly for very long context windows.

**Training needs more.** Besides weights, training holds gradients and optimiser states, often several times the size of the weights. Data parallelism with **sharding** (spreading those states across GPUs, as in ZeRO or FSDP) plus tensor and pipeline parallelism lets large teams train very large models. For fine-tuning, LoRA and quantisation usually remove the need for most of this.

Serving engines handle the details. With vLLM, splitting a model across 4 GPUs is one setting:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 GPUs in this server (tensor parallelism).
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)

# More users? Run more copies (replicas) on other GPU groups or servers
# behind a load balancer. Spanning servers adds pipeline_parallel_size.
```

| Approach | What it splits | Best for | Main cost |
| --- | --- | --- | --- |
| Replicas (data parallelism) | Nothing; full copies | More users, reliability | Needs the model to fit per copy |
| Tensor parallelism | Work inside each layer | Too-big models, lower latency | Needs very fast links between GPUs |
| Pipeline parallelism | Groups of layers | Very big models across servers; training | Adds delay per request |
| Context or sequence parallelism | The input sequence | Very long contexts | Complexity |
| Sharded data parallelism (training) | Gradients and optimiser states | Training big models | Communication overhead |

**Try it in your browser.** How many GPUs does a model need? Change the size, precision and GPU memory.

```python
import math

def gpus_needed(params_billion, bytes_per_param, gpu_gb, kv_cache_gb, headroom=0.9):
    need = params_billion * bytes_per_param + kv_cache_gb
    return need, math.ceil(need / (gpu_gb * headroom))

for params, bpp in [(8, 2), (70, 2), (70, 1)]:
    need, n = gpus_needed(params, bpp, gpu_gb=80, kv_cache_gb=20)
    print(f"{params}B at {bpp} bytes: {need:.0f} GB -> {n} GPU(s) of 80 GB")
```

## A worked example

An insurer in Hyderabad wants to self-host a 70B open model for 2,000 staff, with a p95 first-token time under 2 seconds. Each server has 8 GPUs of 80 GB, with fast links inside the server.

1. **Does it fit on one GPU?** 70 billion × 2 bytes ≈ 140 GB at 16-bit. No.
2. **Inside one server?** Yes. Tensor parallelism across 4 GPUs gives 320 GB, leaving plenty for the KV cache of many concurrent chats. At 8-bit precision, 2 GPUs could hold it if quality is confirmed on their test set.
3. **More users.** Each server holds two copies (two groups of 4 GPUs). Load tests show one copy comfortably handles their busy-hour traffic within the latency budget, so two copies in one server give headroom and survive a GPU failure.

| Set-up | GPUs used | Busy-hour p95 first token | Notes |
| --- | --- | --- | --- |
| Tensor 4, one copy | 4 | 1.4 s | No spare if a GPU fails |
| Tensor 4, two copies | 8 | 0.9 s | Chosen: headroom and failover |
| Tensor 2 at 8-bit, four copies | 8 | 0.8 s | Needs a quality check after quantising |
| Pipeline across two servers | 16 | 2.6 s | Slower and costlier; not needed |

The numbers are for illustration. They also plan to test the 8-bit option, which could double capacity on the same hardware if quality holds.

## Common mistakes

- **Splitting a model that fits on one GPU.** Replicas are simpler and usually faster.
- **Tensor parallelism across slow networks.** Keep it inside a server with fast links.
- **Forgetting the KV cache** when checking whether a model fits.
- **Pipeline parallelism for chat serving.** It adds delay to every request.
- **No headroom.** A single copy has no failover; one GPU fault takes the service down.
- **Sizing from average traffic.** Size for the busy hour, with load tests at real prompt lengths.

## When you do not need any of this

- **Hosted APIs**: the provider handles it.
- **Small models** that fit on one GPU with room to spare: just add replicas when needed.
- **Fine-tuning with LoRA and quantisation**, which often fits on a single GPU.

## From demo to production

- **Measure memory per copy** (weights plus KV cache at your context length and concurrency) before buying GPUs.
- **Load-test each layout** with real prompt and reply lengths.
- **Keep at least two copies** for any service people depend on.
- **Monitor per replica**: utilisation, queue length, latency and errors.
- **Re-plan after model changes**, as size and context length change the layout.
