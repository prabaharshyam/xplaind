## What it is

A single GPU has a fixed amount of memory and speed. Two different problems push you to use many:

1. **The model is too big for one GPU.** A 70B model at 16-bit precision needs about 140 GB for its weights alone, more than one 80 GB GPU.
2. **One copy cannot serve all your users.** Even if the model fits, the busy hour may need several copies.

There are two basic answers: **copy** the model, or **split** it.

- **Replica parallelism** (called **data parallelism** in training): run full copies on several GPUs. Each copy serves different requests, or trains on different batches.
- **Model parallelism**: split one model across GPUs. The main ways are **tensor parallelism** (split the work inside each layer), **pipeline parallelism** (split the layers into groups called stages) and, for mixture-of-experts models, **expert parallelism** (put different experts on different GPUs).

Real systems combine them: for example, a model split across 4 GPUs, with several such groups as replicas.

The rule that drives every choice: **splitting costs communication, and communication needs bandwidth.** The more often GPUs must talk, the faster the link between them must be.

```flow
title: Choosing how to spread a model
Model and busy-hour traffic -> Weights plus KV cache fit on one GPU?
Weights plus KV cache fit on one GPU? -[yes]-> Replicas | one copy per GPU
Weights plus KV cache fit on one GPU? -[no]-> Fit inside one NVLink server?
Fit inside one NVLink server? -[yes]-> Tensor parallelism | size 2, 4 or 8
Fit inside one NVLink server? -[no]-> Tensor inside servers, pipeline across them
Replicas -> Add copies for more traffic | behind a load balancer
Tensor parallelism -> Add copies for more traffic | behind a load balancer
Tensor inside servers, pipeline across them -> Add copies for more traffic | behind a load balancer
```

## How it works

### Replicas: the default whenever the model fits

Every GPU, or group of GPUs, holds a whole model and serves its own requests. Copies never talk to each other, so any network works, and if one fails the others keep serving.

Deciding what goes where is a packing puzzle, and the arithmetic is simple: about 2 bytes per parameter at 16-bit, 1 byte at 8-bit and 0.5 bytes at 4-bit. For example, on one 80 GB GPU you could place two 8B models at 16-bit (16 GB each, 32 GB in total) or one 32B model at 8-bit (32 GB). Both leave about 40 GB of the usable 72 GB for KV caches. This lesson keeps about 10% spare for the engine's own use. (vLLM used 90% of each GPU's memory by default for many versions; recent versions changed the default, so check yours.)

### Tensor parallelism: share each layer's work

A transformer layer is mostly matrix multiplication. Tensor parallelism splits each matrix across, say, 4 GPUs. Each GPU stores a quarter of the weights and computes its slice at the same time. In the usual scheme (from Megatron-LM), the GPUs combine their partial results twice per layer, once after attention and once after the feed-forward block. For a 70B model with 80 layers, that is 160 exchanges for every token generated.

Why it can cut latency: each new token needs every weight read from memory once. With 4 GPUs, each reads a quarter, so time per token drops, though by less than 4 times.

The catch is those exchanges. They are small but very frequent, so they need the fastest link you have:

| Link | Where you find it | Bandwidth (order of magnitude) | Good for |
| --- | --- | --- | --- |
| NVLink (H100 SXM) | Between GPUs inside one server | 900 GB/s per GPU, both directions together | Tensor parallelism |
| PCIe Gen5 x16 | GPU to CPU; GPUs in servers without NVLink | 128 GB/s, both directions together | Replicas; pipeline |
| InfiniBand NDR | Between servers | 400 Gb/s per port, about 50 GB/s each way | Pipeline; training |

When you read a cloud instance listing, look for "SXM" and "NVLink" (or "NVSwitch"). A "PCIe" GPU card usually has no NVLink, or a bridge that joins only two cards. The vLLM documentation advises that on GPUs without NVLink, such as the L40S, pipeline parallelism often gives better throughput than tensor parallelism.

**Valid sizes.** The attention heads are divided among the GPUs, so the tensor-parallel size must divide the head count exactly. A model with 64 heads can use 1, 2, 4, 8, 16, 32 or 64 GPUs, but not 3, 5 or 6. In practice, inside one server, that means 1, 2, 4 or 8.

**Gotcha: shared key-value heads.** Most modern models share keys and values across groups of attention heads. A 70B model with 8 key-value heads split across 8 GPUs puts one key-value head on each GPU, so the KV cache splits evenly. Split it across 16 GPUs and each key-value head is copied onto two GPUs, so the cache per GPU stops shrinking.

### Pipeline parallelism: split the layers into stages

Put layers 1 to 40 on server A and layers 41 to 80 on server B. A request runs through stage A, crosses the network, then runs through stage B.

Be precise about latency. A request passes through all 80 layers in order whether they sit on one GPU or many. So pipeline parallelism adds only a small hop per stage boundary, but it **does not make one request faster**, because no stage shares another's work. Tensor parallelism can make a request faster; pipeline cannot.

Its strength is bandwidth: each stage sends only its output, once per stage, not twice per layer. That is why pipeline is the split used across servers, where links are slower.

Its weakness is idle time, called the **bubble**. With one request in flight, only one stage works at a time. To keep all stages busy, the batch is cut into **micro-batches** that follow each other down the pipe. In training, with `p` stages and `m` micro-batches, a share of about (p − 1) ÷ (m + p − 1) of the time is idle. For example, 4 stages and 16 micro-batches waste about 3 ÷ 19, or 16%. In serving, many concurrent requests fill the pipe the same way.

### Mixture-of-experts models and expert parallelism

In a **mixture-of-experts (MoE)** model, each layer has many feed-forward "experts", and a small router sends each token to only a few of them. Sizing follows two different numbers:

- **Memory follows total parameters.** Every expert must be loaded, because the next token may need any of them.
- **Compute per token follows active parameters.** Only the chosen experts run.

For example, Qwen3-235B-A22B has 235B total parameters, of which about 22B are active per token (8 of 128 experts). At 8-bit, its weights need about 235 GB, so it needs at least 4 GPUs of 80 GB (4 × 72 = 288 GB usable), leaving only about 53 GB for the cache. An 8-GPU server gives far more room. Yet each token costs roughly the compute of a 22B dense model.

**Expert parallelism** places different experts on different GPUs and sends each token to the GPU that holds its expert. The attention part is usually copied (data parallel) or split with tensor parallelism. In vLLM it is one flag, `--enable-expert-parallel`. Two gotchas: popular experts get overloaded while others sit idle, so engines offer expert load balancing; and at large batch sizes, nearly every expert is used by some token, so the memory-reading savings of MoE shrink.

### Long inputs: context and sequence parallelism

**Context parallelism** cuts one very long input, such as a 500,000-token document, into chunks on different GPUs. Each GPU computes attention for its chunk while keys and values are passed around the group. **Sequence parallelism** is a training add-on to tensor parallelism: it splits the parts of a layer that tensor parallelism leaves whole, such as normalisation, along the sequence, to save activation memory. You need either only at very long contexts.

### Training needs far more memory than serving

Full training with mixed precision and the Adam optimiser holds about 16 bytes per parameter: 2 for 16-bit weights, 2 for gradients and 12 for 32-bit optimiser states (a master copy of the weights plus two running averages). For a 70B model that is about 1,120 GB, before activations. **Sharded data parallelism** (ZeRO in DeepSpeed, FSDP in PyTorch) spreads these states across the data-parallel GPUs instead of copying them. Large training runs combine it with tensor and pipeline parallelism. For fine-tuning, LoRA and quantisation usually remove the need for most of this.

### What the engine does for you

With vLLM, splitting a model across 4 GPUs is one setting:

```python
from vllm import LLM, SamplingParams

# Split each layer across 4 NVLink-connected GPUs in this server.
llm = LLM(model="your-org/your-70b-model", tensor_parallel_size=4)
out = llm.generate(["Summarise this claim note: ..."], SamplingParams(max_tokens=200))
print(out[0].outputs[0].text)
```

For a model too big for one server, the vLLM guide's rule of thumb is: tensor-parallel size equals the GPUs per server, and pipeline-parallel size equals the number of servers. Two servers of 8 GPUs means `--tensor-parallel-size 8 --pipeline-parallel-size 2`. Across servers, vLLM uses Ray by default (start a Ray cluster, then run one `vllm serve` on one server); a multiprocessing launcher is the alternative.

| Approach | What it splits | Link it needs | Best for | Main cost |
| --- | --- | --- | --- | --- |
| Replicas (data parallelism) | Nothing; full copies | Any | More users, failover | Each copy must fit |
| Tensor parallelism | Matrices inside each layer | NVLink, inside a server | Too-big models, lower time per token | Two exchanges per layer per token |
| Pipeline parallelism | Groups of layers | A good network is enough | Spanning servers; training | No latency gain; bubbles |
| Expert parallelism | Experts of an MoE model | Fast; tokens move to experts | Large MoE models | Uneven load across experts |
| Context or sequence parallelism | The input sequence | Fast | Very long inputs | Complexity |
| Sharded data parallelism | Gradients and optimiser states | Fast for large models | Training big models | Extra communication |

**Try it in your browser.** Find the smallest valid tensor-parallel size for a model and traffic. Change the numbers.

```python
def kv_cache_gb(layers, kv_heads, head_dim, tokens, bytes_per=2):
    # 2 = one key and one value per token, per layer, per key-value head
    return 2 * layers * kv_heads * head_dim * bytes_per * tokens / 1e9

def smallest_tp(params_billion, bytes_per_param, cache_gb, gpu_gb, heads, usable=0.9):
    need = params_billion * bytes_per_param + cache_gb
    for tp in (1, 2, 4, 8):                      # sizes that fit in one 8-GPU server
        if heads % tp == 0 and tp * gpu_gb * usable >= need:
            return need, tp
    return need, None                            # needs pipeline across servers

# A 70B model: 80 layers, 64 heads, 8 key-value heads of size 128
cache = kv_cache_gb(80, 8, 128, tokens=60 * 4000)    # 60 requests x 4,000 tokens
for bpp, label in [(2, "16-bit"), (1, "8-bit")]:
    need, tp = smallest_tp(70, bpp, cache, gpu_gb=80, heads=64)
    print(f"{label}: {need:.0f} GB needed -> tensor-parallel size {tp}")
```

It prints about 219 GB and size 4 at 16-bit, and about 149 GB and size 4 at 8-bit. The 8-bit model fits on 2 GPUs only if each copy serves fewer requests: about 56 at 4,000 tokens. The script ignores the few GB per GPU that the engine itself uses, so keep a margin.

## A worked example

An insurer in Hyderabad wants to self-host a 70B open model (80 layers, 64 attention heads, 8 key-value heads of size 128) for 2,000 staff, with a p95 first-token time under 2 seconds. Each server has 8 GPUs of 80 GB joined by NVLink. The traffic figures below are their planning estimates, not measurements.

1. **Busy-hour load.** Suppose 600 staff are active in the busy hour, each sending a request every 2 minutes: 5 requests a second. Each takes about 12 seconds to finish streaming. Requests in flight = arrivals × time each = 5 × 12 = **60**. Each holds about 4,000 tokens (instructions, policy text, chat history and reply).
2. **KV cache.** 2 × 80 layers × 8 heads × 128 × 2 bytes = 327,680 bytes, about 0.33 MB per token. 60 × 4,000 tokens × 0.33 MB ≈ **79 GB**.
3. **Does it fit on one GPU?** The weights alone are about 140 GB at 16-bit; one GPU gives 72 GB usable. No.
4. **Smallest valid split.** Two GPUs give 144 GB usable: barely the weights, no cache. Three give 216 GB, just short of the 219 GB needed, and do not divide 64 heads anyway. Four give 288 GB: 140 GB of weights leaves about **148 GB** of cache, room for about 112 requests of 4,000 tokens. Tensor-parallel size 4.
5. **Capacity and failover.** One copy holds the busy hour, but a single fault would stop the service. Two copies of 4 GPUs fill one server; a second server protects against the whole server failing.
6. **Cost.** At an example rate of ₹362 per GPU-hour (the on-demand price on E2E Networks' H100 page, checked 28 November 2026, before 18% GST), one 8-GPU server for a 730-hour month costs 8 × 362 × 730 ≈ **₹21.1 lakh**, about ₹24.9 lakh with GST. Prices vary by provider and plan, so get quotes. At 40 requests per person per working day for 22 days, that is about 7 billion tokens a month, or about ₹300 per million tokens. A hosted API priced below that is cheaper, unless data must stay on their own servers. Running one copy at night also saves money.

| Layout | GPUs | Cache room per copy | Requests per copy at 4,000 tokens | p95 first token (illustrative) |
| --- | --- | --- | --- | --- |
| Tensor 4, one copy | 4 | About 148 GB | About 112 | 1.4 s; no failover |
| Tensor 4, two copies (chosen) | 8 | About 148 GB | About 112 | 0.9 s; survives a GPU fault |
| Tensor 2 at 8-bit, four copies | 8 | About 74 GB | About 56 | 0.8 s if quality holds |
| Tensor 8, pipeline 2, one copy | 16 | About 1,010 GB | Far more than needed | No faster; twice the GPUs |

The memory columns are calculated; the latency column only illustrates what a load test might show. The 8-bit option must first pass quality tests on real claim notes.

## Common mistakes

- **Splitting a model that fits on one GPU.** Replicas are simpler, need no fast links and survive failures.
- **Sizing from weights alone.** The KV cache for the busy hour can be as large as the weights.
- **Tensor parallelism over PCIe or a network.** It talks twice per layer; keep it on NVLink inside a server.
- **A tensor-parallel size that does not divide the head count.** The engine refuses to start; use 2, 4 or 8.
- **Expecting pipeline parallelism to cut latency.** It spans servers; it never makes one request faster.
- **Sizing a mixture-of-experts model by active parameters.** All experts must be in memory.
- **Splitting past the number of key-value heads.** The cache per GPU stops shrinking.
- **One copy only.** One GPU fault takes the service down.
- **Sizing from average traffic.** Size for the busy hour, with load tests at real prompt lengths.

## When you do not need any of this

- **Hosted APIs**: the provider handles it. Compare their price per million tokens with your GPU cost first.
- **Small models** that fit on one GPU with room for the cache: just add replicas when needed.
- **Fine-tuning with LoRA and quantisation**, which often fits on a single GPU.

## From demo to production

- **Measure memory per copy** (weights plus KV cache at your context length and concurrency) before buying or renting GPUs.
- **Check the links**: confirm "SXM" and "NVLink" in the instance listing before planning tensor parallelism.
- **Load-test each layout** with real prompt and reply lengths, and watch p95, not the average.
- **Keep at least two copies** for any service people depend on, on more than one server.
- **Monitor per replica**: queue length, KV cache use, latency and errors. Add copies when the queue grows.
- **Scale with the working day**: fewer copies at night if traffic drops.
- **Re-plan after model changes**, because size, head counts and context length change the layout.
