## What it is

Fine-tuning changes one model. **Model merging** combines two or more models into one by mixing their weights. It usually works best when the models were fine-tuned from the **same base model**, so their weights line up.

Why bother?

- **Several skills in one model.** If you fine-tuned one model for complaints and another for replies, a merge can do both.
- **No forgetting from training tasks in sequence.** Training on task A, then task B, often makes a model forget A. Training each separately and merging avoids that.
- **No GPUs needed.** Simple merges are arithmetic on weights and run on an ordinary computer.
- **Smaller deployments.** One model instead of several, useful on phones, laptops and other devices with limited memory, or where data must not leave the device.

Merging is different from an **ensemble**. An ensemble runs several models and combines their answers, which costs several calls per request. A merge combines the weights once; afterwards you serve a single model at normal cost.

Merging is still young and partly experimental. Many top entries on open model leaderboards have been merges, but results vary, so treat every merge as a new model to test.

```flow
title: Merging fine-tuned models
Base model -> Fine-tune for task A | adapter or full
Base model -> Fine-tune for task B
Fine-tune for task A -> Task vector A | A minus base
Fine-tune for task B -> Task vector B | B minus base
Task vector A -> Combine | average, SLERP, TIES, DARE
Task vector B -> Combine
Combine -> Merged model
Merged model -> Test every task, general skills, safety
```

## How it works

**Task vectors.** Subtract the base model's weights from a fine-tuned model's weights and you get a **task vector**: the change that fine-tuning made. With LoRA, the adapter itself is essentially the task vector. Adding task vectors to the base combines skills, and subtracting one can reduce a behaviour, which researchers have used to weaken unwanted abilities or biases.

**Linear combination.** The simplest merge is a weighted average of the weights or of the task vectors. It works surprisingly well, especially for models from the same base. "Model soups" averaged several fine-tuned versions of one model and improved accuracy at no extra running cost. Weights let one model count more than another.

**SLERP.** Spherical linear interpolation blends two models along a curved path rather than a straight line, which can preserve each model's character better than a plain average. An interpolation factor from 0 to 1 sets which model counts more. It merges two models at a time; merge a third by repeating.

**TIES and DARE.** Fine-tuning changes nearly every weight, but most changes are tiny and add little. Those small changes from different tasks can clash when merged. Both methods first **prune** each task vector, keeping only the important changes:

- **TIES** keeps the largest changes, then settles conflicts where tasks push a weight in opposite directions, before merging.
- **DARE** randomly drops most changes and rescales the rest to keep their overall effect.

Both often give clearly better merges than plain averaging, and the advantage grows as you merge more models.

**Layer stacking.** Instead of mixing weights, build a model from layers of different models, sometimes called a "frankenmerge". It can make a bigger model from smaller ones (one team built a 10.7B model from two copies of a 7B one), and is one way to start a mixture-of-experts model from an existing one. These usually need further training to work well.

**Concatenation** joins adapters side by side. It keeps all parameters, so it saves no memory and is rarely worth it.

Merging two LoRA adapters with PEFT looks like this:

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("base-model-id")
model = PeftModel.from_pretrained(base, "adapters/complaints", adapter_name="complaints")
model.load_adapter("adapters/replies", adapter_name="replies")

# Combine into a new adapter; TIES keeps the strongest changes (density) and resolves conflicts.
model.add_weighted_adapter(
    adapters=["complaints", "replies"], weights=[1.0, 1.0],
    adapter_name="merged", combination_type="ties", density=0.3,
)
model.set_adapter("merged")
```

For whole models, the open-source tool mergekit runs merges from a short configuration file.

| Method | How it combines | Strengths | Watch out for |
| --- | --- | --- | --- |
| Weighted average | Averages weights or task vectors | Simple, often good | Tasks can interfere |
| SLERP | Blends two models along a curve | Smooth blend of two | Two models at a time |
| TIES | Keeps big changes, resolves sign conflicts | Better with several tasks | Density setting needs tuning |
| DARE | Drops most changes randomly, rescales | Robust, simple to apply | Randomness; test more than once |
| Layer stacking | Combines layers, can grow size | Can upscale or build MoE | Usually needs further training |

**Try it in your browser.** Average two task vectors, then try a TIES-style merge that keeps only the big changes.

```python
import numpy as np

rng = np.random.default_rng(7)
base = rng.normal(size=10)
task_a = np.where(rng.random(10) < 0.3, rng.normal(0, 1, 10), rng.normal(0, 0.05, 10))
task_b = np.where(rng.random(10) < 0.3, rng.normal(0, 1, 10), rng.normal(0, 0.05, 10))

average = base + (task_a + task_b) / 2
def trim(v, keep=0.3):
    cut = np.quantile(np.abs(v), 1 - keep)
    return np.where(np.abs(v) >= cut, v, 0)
ties = base + trim(task_a) + trim(task_b)
print("average change:", (average - base).round(2))
print("TIES change:   ", (ties - base).round(2))
```

## A worked example

A bank in Mumbai has three LoRA adapters on the same open 8B base model: complaint classification, reply drafting in English and Hindi, and KYC field extraction. They want one model on branch laptops with no internet.

They try three merges and test each on every task's own test set:

| Model | Complaint accuracy | Reply quality (reviewer score out of 5) | KYC extraction accuracy |
| --- | --- | --- | --- |
| Separate adapters (target) | 93% | 4.3 | 96% |
| Weighted average of all three | 89% | 4.0 | 84% |
| TIES, density 0.3 | 92% | 4.2 | 88% |
| TIES of complaints and replies; KYC kept separate | 92% | 4.2 | 96% |

The numbers are for illustration. Extraction, the most precise task, suffered most in every full merge. The team ships a merged model for complaints and replies and keeps the KYC adapter separate, loaded only when a document is scanned. Both fit on the laptops. They also re-run their safety and refusal checks, because merging can weaken behaviour none of the adapters was trained on.

## Common mistakes

- **Merging models from different bases** without understanding the risks. Results are usually poor.
- **Testing only one task.** A merge can quietly hurt another task or general abilities.
- **Skipping safety checks.** Refusal and safety behaviour can weaken after merging.
- **Trusting leaderboard merges blindly.** Some are tuned to benchmarks; test on your own data.
- **Using concatenation to save memory.** It does not.
- **Forgetting the licence.** A merge inherits the licence terms of every model in it.

## When not to merge

- **Tasks that need high precision** may be better kept as separate adapters.
- **You can afford one good multi-task fine-tune** with enough data for every task.
- **Serving several adapters is already cheap**, as many servers support it efficiently.
- **The models come from different base models.**

## From demo to production

- **Version merges like models**: the inputs, method, weights and settings in a config file.
- **Keep the separate adapters** as a fallback and for comparison.
- **Test every task, plus general and safety checks**, before each release.
- **Re-merge when any input model changes**, and re-test.
