## What it is

Fine-tuning changes one model. **Model merging** combines two or more models into one by mixing their weights. No training run is needed: a merge is arithmetic on the weight files.

Merging works best when the models were fine-tuned from the **same base model**. Why? Fine-tuning moves the weights only a short distance from where they started. Two models fine-tuned from one base still sit close to it and to each other, and weight number 1,000 means roughly the same thing in both. Two models trained from scratch learn their features in different orders, so averaging them mixes unrelated numbers and usually breaks both.

Why merge?

- **One model for mixed requests.** If one request needs two skills (classify a complaint and draft the reply), a merged model handles it in one call, with no router choosing between models.
- **One file to ship.** A merged model is a plain model. Any runtime can load it, including ones with no adapter support.
- **Less forgetting than training in sequence.** Training on task A and then task B often makes a model forget A. Training each task separately and merging reduces that risk, but brings its own problem: the tasks' changes interfere, so every task must be retested.
- **No GPUs needed.** Simple merges run on a CPU. You need disk space and memory for the models, not a GPU.

What merging does **not** buy you is memory, when the inputs are LoRA adapters. A LoRA adapter is small. For example, rank 16 on every linear layer of a Llama-3-8B-shaped model is about 42 million parameters, roughly 84 MB at 16-bit, against about 16 GB for the base at 16-bit. Three adapters add about 1.6% to the base. Merging them saves almost nothing.

Merging is also different from an **ensemble**. An ensemble runs several models on every request and combines their answers, so each request costs several calls. A merge combines the weights once; afterwards you serve one model at normal cost.

A note on reputation. In 2024 merges filled the top of Hugging Face's Open LLM Leaderboard. The leaderboard team hid merges by default, saying their scores often did not carry over to real use. The leaderboard itself was retired in March 2025. The lesson stands: a merge's public scores tell you little about your tasks.

```flow
title: Merging fine-tuned models
Base model -> Fine-tune for task A | adapter or full
Base model -> Fine-tune for task B
Fine-tune for task A -> Task vector A | A minus base
Fine-tune for task B -> Task vector B | B minus base
Task vector A -> Combine | average, SLERP, TIES, DARE
Task vector B -> Combine
Combine -> Merged model
Merged model -> Test every task and safety
Test every task and safety -[pass the bar]-> Ship one model
Test every task and safety -[miss the bar]-> Keep separate models
```

## How it works

### Task vectors

Subtract the base model's weights from a fine-tuned model's weights and you get a **task vector**: the change fine-tuning made. Add task vectors to the base and you combine skills. Subtract one and you weaken a behaviour. The paper that named task vectors (Ilharco and others, ICLR 2023) made GPT-2 produce far fewer toxic outputs by subtracting a task vector learned from toxic text.

With LoRA, the adapter stores the task vector in factored form: two thin matrices, A and B, whose product B times A is the change to each layer. This detail matters later. Combining the A matrices and B matrices separately is not the same as combining the real changes.

### Weighted average and task arithmetic

The simplest merge is a weighted sum of task vectors added to the base. With weights of 0.5 and 0.5 it is an average; with weights of 1.0 and 1.0 it is plain **task arithmetic**. Averaging works surprisingly well for models from one base. The "model soups" paper (Wortsman and others, ICML 2022) averaged many fine-tuned versions of one model and often beat the best single one, at no extra running cost.

The weakness is interference. An average halves a change that only one task made, and when two tasks push a weight in opposite directions, they cancel.

### SLERP

**Spherical linear interpolation** blends two models along an arc instead of a straight line. Why the arc? If two weight vectors point in different directions, the midpoint of the straight line between them is shorter than either. The model's weights shrink, which can dull both models. The arc keeps the size. A factor `t` from 0 to 1 sets the blend: 0 is the first model, 1 the second. SLERP takes exactly two models; for a third, merge again.

### TIES and DARE

Fine-tuning changes nearly every weight, but most changes are tiny. These small changes add little, yet they clash when merged. **TIES** (Yadav and others, NeurIPS 2023) cleans each task vector in three steps:

1. **Trim.** Keep only the largest changes in each task vector. The `density` setting is the share kept: 0.3 keeps the top 30%.
2. **Elect a sign.** For each weight, add up the kept changes. The direction with more total change wins.
3. **Disjoint mean.** Average only the kept changes that agree with the winning sign. A change only one task made keeps its full size.

**DARE** (Yu and others, 2023) replaces the trim step. It drops a random share of each task vector's changes and scales the survivors up so the total effect stays about the same. It can be combined with TIES as `dare_ties`: DARE's random drop, then TIES's sign election.

The papers that introduced both methods report gains over plain averaging. Check this on your own tasks. Newer variants exist, such as Model Breadcrumbs and DELLA, and mergekit supports them. Sakana AI showed in 2024 that an evolutionary search can find good merge recipes automatically. Learn TIES well first.

**Try it in your browser.** Two task vectors with a conflict on weight 0, agreement on weight 3, and changes only one task made on weights 4 and 5.

```python
import numpy as np

# Changes two fine-tunes made to the same 8 weights (their task vectors).
# Weight 0: the tasks disagree. Weight 3: they agree. Weights 4 and 5: only one task cares.
# The rest are tiny changes, mostly noise.
task_a = np.array([ 0.90, 0.02, -0.03, 0.80, 0.01, -0.70,  0.02, 0.00])
task_b = np.array([-0.85, 0.03,  0.02, 0.75, 0.60,  0.01, -0.02, 0.01])

def ties(vectors, density=0.4):
    stacked = np.stack(vectors)
    # 1. Trim: in each vector, keep only the largest changes (the top `density` share).
    trimmed = []
    for v in stacked:
        cut = np.quantile(np.abs(v), 1 - density)
        trimmed.append(np.where(np.abs(v) >= cut, v, 0.0))
    trimmed = np.stack(trimmed)
    # 2. Elect a sign per weight: the direction with more total change wins.
    sign = np.where(trimmed.sum(axis=0) >= 0, 1.0, -1.0)
    # 3. Disjoint mean: average only the kept changes that agree with that sign.
    agree = (np.sign(trimmed) == sign) & (trimmed != 0)
    count = np.maximum(agree.sum(axis=0), 1)
    return (trimmed * agree).sum(axis=0) / count

average = (task_a + task_b) / 2
merged = ties([task_a, task_b])
for name, v in [("task A ", task_a), ("task B ", task_b), ("average", average), ("TIES   ", merged)]:
    print(name, v.round(2) + 0.0)
```

The output:

```text
task A  [ 0.9   0.02 -0.03  0.8   0.01 -0.7   0.02  0.  ]
task B  [-0.85  0.03  0.02  0.75  0.6   0.01 -0.02  0.01]
average [ 0.03  0.02  0.    0.78  0.3  -0.34  0.    0.  ]
TIES    [ 0.9   0.    0.    0.78  0.6  -0.7   0.    0.  ]
```

Read it weight by weight. The average cancels weight 0 to almost nothing, so both tasks lose it, and it halves weights 4 and 5. TIES keeps 4 and 5 at full size and clears the noise. But look at weight 0: TIES keeps task A's 0.9 and throws away task B's change completely. TIES does not make conflicts go away. It picks a winner, and the losing task pays. This is why a precise task often drops after a merge.

### Layer stacking

Instead of mixing weights, you can build a model from layers of different models, sometimes called a "frankenmerge". It can grow a model. SOLAR 10.7B (Kim and others, 2023) took two copies of a 32-layer 7B model, removed 8 layers from each, and joined them into 48 layers. It needed further pretraining to work well, and most stacked models do.

### Merging LoRA adapters with PEFT

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("base-model-id")
model = PeftModel.from_pretrained(base, "adapters/complaints", adapter_name="complaints")
model.load_adapter("adapters/replies", adapter_name="replies")

# ties_svd applies TIES to the real change (B times A) of each layer, then compresses it back to a LoRA.
model.add_weighted_adapter(
    adapters=["complaints", "replies"], weights=[1.0, 1.0],
    adapter_name="merged", combination_type="ties_svd", density=0.5,
)
model.set_adapter("merged")
merged = model.merge_and_unload()   # one plain model, no adapter needed at run time
merged.save_pretrained("merged-model")
```

Gotchas in PEFT (checked against version 0.22):

- The plain `linear`, `ties` and `dare_*` types combine the A and B matrices separately. PEFT's own documentation calls `linear` a rough approximation. Prefer the `_svd` types, which work on the real change.
- The plain types need every adapter to have the same rank `r`. The `_svd` types do not.
- `cat` joins the adapters side by side. It gives the exact sum of the changes, but the new adapter's rank is the sum of all ranks.
- DoRA adapters are not supported.

### Merging full models with mergekit

For full fine-tunes, the open-source tool mergekit runs a merge from a short YAML file:

```yaml
merge_method: ties
base_model: ./base-8b
models:
  - model: ./complaints-8b
    parameters: {density: 0.5, weight: 1.0}
  - model: ./replies-8b
    parameters: {density: 0.5, weight: 1.0}
dtype: bfloat16
```

Run it with `mergekit-yaml merge.yml ./merged`. For TIES, mergekit divides by the total weight by default (`normalize`), so weights of 1.0 and 1.0 act as an even blend.

### Choosing the settings

Merge settings are guesses until you measure them. A small search is cheap, because a merge needs no training run.

1. Hold out a small **dev set** per task, for example 100 to 200 examples, separate from the final test set.
2. Start with equal weights and try density 0.2, 0.5 and 0.8. For SLERP, try `t` of 0.3, 0.5 and 0.7.
3. If one task drops, raise its weight, for example from 1.0 to 1.5, and try again.
4. Keep the best setting by your acceptance bar, not by the average score. Then run the test set once.
5. Save each config with its scores, so you can rebuild any merge.

| Method | How it combines | Strengths | Watch out for |
| --- | --- | --- | --- |
| Weighted average | Weighted sum of task vectors | Simple baseline, often good | Halves single-task changes; conflicts cancel |
| SLERP | Blends two models along an arc | Keeps weight size; smooth blend | Two models at a time |
| TIES | Trim, elect sign, disjoint mean | Better with several tasks | On a conflict one task loses; tune density |
| DARE | Random drop, then rescale | Pairs well with TIES | Random: compare a few seeds |
| Layer stacking | Joins layers, can grow size | Can make a bigger model | Usually needs further training |

## A worked example

A bank in Mumbai has three LoRA adapters, all rank 16 on the same open 8B base model: complaint classification, reply drafting in English and Hindi, and KYC field extraction. Branch staff paste a whole customer letter, and many letters are complaints that also need a reply. The offline app the bank's IT team approved loads one model file at a time and cannot pick an adapter per request. KYC scanning is a separate screen in the app, used a few times a day.

Memory is not the reason to merge here. The three adapters add only about 250 MB to a base of about 16 GB at 16-bit. The reasons are one model file and one call for a mixed letter.

Before merging, the team writes down the test sets and the bar:

- **Complaints:** 400 labelled letters; accuracy.
- **Replies:** 150 letters; two reviewers score each draft from 1 to 5 against a rubric, and the scores are averaged.
- **KYC:** 300 scanned documents; share of fields extracted exactly right.
- **Safety:** 200 prompts the assistant must refuse, such as requests for another customer's account details.
- **Bar:** no task more than 2 points below its separate adapter (0.2 for replies), and no fewer refusals.

They tune on separate dev sets, then run the test sets. The numbers below are for illustration, not measured results.

| Model | PEFT setting | Complaints | Replies (out of 5) | KYC | Meets the bar? |
| --- | --- | --- | --- | --- | --- |
| Separate adapters (target) | none | 93% | 4.3 | 96% | target |
| Average of all three | `svd`, weights 1/3 each | 89% | 4.0 | 84% | no |
| TIES of all three | `ties_svd`, density 0.5, weights 1.0 | 92% | 4.2 | 88% | no: KYC |
| TIES, KYC weighted up | as above, KYC weight 1.5 | 91% | 4.1 | 91% | no: KYC |
| TIES of complaints and replies | `ties_svd`, density 0.5 | 92% | 4.2 | n/a | yes |

The plain average dilutes every skill to a third, so it fails everywhere. TIES does better, but KYC extraction, the most precise task, loses conflicts it cannot afford. Weighting it up helps KYC and starts to hurt the others.

So the team ships two files. The letter screen uses the merged complaints-and-replies model, which handles a mixed letter in one call. The scan screen loads a second model, the base with the KYC adapter folded in, only when a document is scanned. The safety set passes with the same refusal count. They re-ran it because merging can weaken behaviour that none of the adapters was trained on.

## Common mistakes

- **Merging models from different bases.** Also check that the inputs share a tokenizer and a chat template. A merge of models that expect different prompt formats can produce broken replies.
- **Merging LoRA adapters to save memory.** Adapters are small; the saving is tiny.
- **Judging by the average score.** A merge can look fine on average while one task drops badly. Compare every task against its own target.
- **Tuning on the test set.** Picking density and weights on the test set makes the test score look better than real use will be. Use a dev set.
- **Using plain `linear` or `ties` on LoRA adapters and expecting an exact sum.** These types combine the A and B matrices separately. Use `cat` for an exact sum; the `_svd` types are exact only when `svd_rank` is at least the sum of the ranks.
- **Skipping safety checks.** A 2024 study (Hammoud and others, Findings of EMNLP) found that merging can carry one model's weak safety behaviour into the merged model.
- **Trusting public merges.** Test a downloaded merge on your own data.
- **Forgetting the licence.** A merge must follow the terms of every model in it. A non-commercial input can limit how you may use the merge, so read each licence. Some licences add naming rules: Llama 3.1's licence asks that a shared model built from it has a name starting with "Llama".

## When not to merge

Ask these questions in order:

1. **Can you serve the adapters separately?** For LoRA adapters this is usually the best choice. Servers such as vLLM keep one base model in GPU memory and apply a different adapter per request, even in the same batch. For example: `vllm serve base-model-id --enable-lora --lora-modules complaints=./adapters/complaints replies=./adapters/replies --max-loras 4`. Each request names its adapter. Merge LoRA adapters mainly when the runtime cannot do this, or one request needs several skills at once.
2. **Is one task very precise?** Extraction, maths or strict formats often lose in a merge. Keep it separate.
3. **Can you afford one multi-task fine-tune?** With data for every task, training on the mix often beats a merge, because the model learns to balance the tasks.
4. **Do the models come from different bases?** Do not merge.

## From demo to production

- **Version merges like models.** Keep the config file, input model versions, scores and test set versions together.
- **Keep the separate models** as a fallback and as the comparison point.
- **Test every task, plus general and safety checks**, before each release, against the bar you set in advance.
- **Re-merge and re-test when any input changes.** A new adapter version means a new merge.
- **Record the licence of every input** in the merged model's card.
