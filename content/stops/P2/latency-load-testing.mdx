## What it is

A **latency budget** is the longest acceptable response time, broken down by step. For a chat assistant: first token within 1.5 seconds at the 95th percentile, full answer within 8 seconds. The budget then splits across steps: auth 50 ms, query rewrite 300 ms, retrieval and reranking 400 ms, model time to first token 700 ms.

**Load testing** sends realistic traffic at the system, rising step by step, and records response times, errors and resource use, so you know the load at which it breaks and what breaks first.

```flow
dir: LR
title: Latency budget: p95 first token in 2 s
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| Before: a pool of 10 connections | 1 s | 2 s | 6 s | | | |
| After: a pool of 40 + an index | 1 s | 1 s | 1 s | 1 s | 1 s | 1 s |

p95 first token by number of users, measured with a fake model.

## How it works

**Percentiles, not averages.** An average of 2 seconds can hide 5% of users waiting 15 seconds. Track the median (p50), the 95th (p95) and the 99th percentile (p99). Users remember the slow ones.

**Budget by step.** Traces give you each step's timing. When the total misses the target, the budget shows which step to attack: a slow reranker, too many chunks, a large model where a small one would do, or a cold start.

**AI-specific factors.** Output length dominates generation time, so shorter answers are faster. Time to first token depends on prompt length, so trim context. Provider latency varies by hour and region. Rate limits on tokens per minute cap throughput no matter how many servers you run; check them before a big launch and ask the provider for higher limits early.

**Designing the test.** Model real behaviour: the mix of question types, think time between messages, typical prompt and answer lengths, and the expected peak (say, 300 concurrent users at 7 pm). Use tools such as Locust (Python) or k6. Ramp from low to beyond the expected peak, hold, and watch p95, error rate, CPU, memory, database connections and provider 429 responses.

**Model costs in tests.** Load tests against real models cost real money and use up rate limits. Run most rounds against a fake model server that replies after a realistic delay, then one short, controlled test against the real provider.

**Common bottlenecks and fixes:**

| Symptom under load | Likely cause | Fix |
| --- | --- | --- |
| Latency rises, CPU low | Waiting on database connections or locks | Larger pool, indexes, fewer queries |
| CPU at 100% | Too few workers or heavy parsing | More workers, background jobs |
| 429 errors | Provider rate limit | Higher limit, fallback model, shorter outputs |
| Slow first token only | Long prompts | Trim context, cache the prefix |
| Slow full answers | Long outputs | Cap answer length |
| Errors after a minute | Timeouts set too low | Align timeouts across layers |

**Building a fake model server.** Write a tiny service with the same API as the provider. It waits a realistic time before the first token, sampled from your traces, then streams a fixed reply at a typical token rate. Point the app at it with a setting. Now you can run load tests all day for free and find every bottleneck except the provider's own limits, which one short real test then checks.

**Reporting the result.** Show a chart of p95 against users, the budget line, the bottleneck found at each round and the fix, and the next ceiling you expect. Clients value knowing where the system will break next, because it tells them what to plan for.

**A fake model server.** Same streaming shape as the real API, delays sampled from your traces:

```python
import asyncio, json, random
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.6, 0.8, 0.9, 1.1, 1.4, 2.2]       # sampled from real traces
TOKENS_PER_S = 60
REPLY = "This is a fixed answer of realistic length used only for load testing. " * 6

@app.post("/v1/messages")
async def messages():
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for word in REPLY.split():
            yield f"data: {json.dumps({'text': word + ' '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

Point your app's model base URL at it through configuration in the test environment only. Add a switch to return 429 errors for a share of requests, to test your retries and fallbacks.

**A Locust test that ramps up.**

```python
from locust import HttpUser, task, between, LoadTestShape
import random

QUESTIONS = [l.strip() for l in open("load/questions.txt")]     # real questions, masked

class Learner(HttpUser):
    wait_time = between(5, 20)                                   # think time between messages

    @task
    def ask(self):
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            for _ in r.iter_lines():
                pass                                             # read the whole stream
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")

class Ramp(LoadTestShape):
    steps = [(60, 10), (120, 50), (180, 100), (240, 200), (300, 300)]   # (end second, users)
    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10
        return None
```

Run with `locust -f load/locustfile.py --host https://staging.example.in --csv results`. The CSV files give p50, p95 and p99 per step; plot p95 against users and mark your budget line.

**Time to first token needs its own measurement.** Locust's built-in timing covers the whole request. For streaming, also record first-byte time in the app's own traces, and read p95 first-token time from there for each ramp step.

**One controlled run on the real model.** After fixing bottlenecks with the fake server, run a short test against the real model at the expected peak, within your rate limits and budget, to confirm provider latency and limits. Agree the run in advance with whoever owns the API account.

**Read results with traces open.** When p95 jumps at 100 users, open the slowest traces from that minute. The step that grew (database waits, reranker, queueing for model slots) is the bottleneck, and the fix table above usually names the remedy.

**Try it in your browser.** Percentiles from a list of timings. The average hides the slow tail.

```python
import random, statistics

random.seed(6)
timings = [random.gauss(1.2, 0.2) for _ in range(950)] + [random.uniform(4, 9) for _ in range(50)]
timings.sort()
p = lambda q: timings[int(q * (len(timings) - 1))]
print(f"average {statistics.mean(timings):.2f} s")
print(f"p50 {p(0.5):.2f} s, p95 {p(0.95):.2f} s, p99 {p(0.99):.2f} s")
```

## A worked example

A Jaipur intercity bus operator is launching an AI assistant for bus bookings and complaints, expected to peak at 500 concurrent users during festival travel.

The budget: first token under 2 s at p95, full answer under 10 s at p95, errors under 1%.

Round 1, against a fake model with realistic delays: p95 first token rises from 1.1 s at 50 users to 6 s at 200 users. Traces show requests queuing for database connections: the pool size is 10. Raising it to 40 and adding an index on the route table brings p95 to 1.3 s at 500 users.

Round 2, a 10-minute test against the real model at 300 users: provider 429 errors start at about 220 users. The token-per-minute limit is the ceiling. You request a higher limit two weeks ahead, add a fallback model through the gateway, and cap answer length at 200 tokens, which also cuts average generation time by a third.

The final test meets the budget at 550 users. The launch day peak reaches 480 users without incident, and your report lists the next bottleneck (provider limits at about 700 users) so the client can plan.

| Round | Finding | Fix | Result |
| --- | --- | --- | --- |
| 1, fake model | p95 6 s at 200 users; connection pool of 10 | Pool of 40, route-table index | p95 1.3 s at 500 users |
| 2, real model | 429s from about 220 users | Higher limit, fallback, 200-token cap | Budget met at 550 users |
| Launch day | Peak 480 users | None needed | No incidents |

## Common mistakes

- **Reporting averages.** Use p95 and p99.
- **Testing one request at a time.** Concurrency problems (pools, locks, rate limits) only show under load.
- **Unrealistic traffic.** Identical tiny prompts with no think time give misleading numbers.
- **Burning money on real-model load tests.** Use a fake model for most rounds.
- **Forgetting provider limits.** They are often the real ceiling. Check and raise them early.
- **Load-testing against the real model for every round**, burning budget and rate limits.
- **No think time**, so a few test users behave like thousands.
- **Measuring only total time** for streamed answers; track first-token time too.

## When a full load test can wait

- **Internal tools with a handful of users**: a quick check with ten concurrent requests is enough.
- **Batch systems**, where throughput per hour matters more than per-user latency; test that instead.
- **Platforms that scale for you** with generous limits, for early pilots, as long as rate limits are checked.

## From demo to production

- **Keep a latency budget by step** and compare traces against it.
- **Load-test before launch and before big changes**, mostly with a fake model server.
- **Report p50, p95, p99 and errors** per ramp step, with the bottleneck found.
- **Re-test when traffic patterns change**, such as exam season or a festival sale.
- **Alert on p95 first-token time** in production.
