## What it is

A **latency budget** is the slowest response you accept, at a stated percentile, split into a target for each step of a request. For a chat assistant, for example: p95 time to first token within 2 seconds, p95 full answer within 10 seconds, errors under 1%. The first-token budget then splits into auth 50 ms, query rewrite 300 ms, retrieval and reranking 400 ms, model first token 700 ms, and 550 ms of slack for network and queueing.

**Load testing** sends realistic traffic at the system, rising step by step, and records response times, errors and resource use. It tells you the load at which the system breaks, and what breaks first, before your users find out.

```flow
dir: LR
title: Latency budget: p95 first token in 2 s
Auth, 50 ms -> Rewrite, 300 ms -> Retrieve + rerank, 400 ms -> Model first token, 700 ms -> Slack, 550 ms
```

Three words you will need. **p95** is the time that 95% of requests beat. **Time to first token** is the wait until the first word of the answer appears. **Concurrent users** means people in a chat session at the same moment; most of them are reading or typing, so far fewer requests are in flight at once.

This lesson follows an intercity bus operator in Jaipur preparing its booking assistant for festival-season traffic.

## How it works

### Percentiles, not averages

An average of 1.5 seconds can hide 5% of users waiting 4 to 9 seconds. Track the median (p50), p95 and p99. The tail matters more than it looks: a user who sends 20 messages in a session has about an 18% chance (1 minus 0.99 to the power 20) of hitting at least one reply slower than p99.

Two rules experts follow:

- **Percentiles do not add up.** The p95 of the total is not the sum of each step's p95. Slow steps rarely happen on the same request, so the sum usually overstates the total; but when one cause slows every step at once, such as a busy database, they move together. Treat step numbers as targets for that step's own p95, and read the end-to-end p95 directly from traces.
- **Percentiles do not average.** Suppose three servers show a p95 of 1.2 seconds and one, with a median of 3.5 seconds, shows 6 seconds, each taking a quarter of the traffic. The average of the four p95s is 2.4 seconds. But half the slow server's requests take over 3.5 seconds, which is 12.5% of all requests, so the true p95 is above 3.5 seconds. Compute percentiles from all raw timings, or from merged histograms.

```python
import random

random.seed(7)
def p95(xs):
    xs = sorted(xs)
    return xs[int(0.95 * (len(xs) - 1))]

# Four steps, each with its own spread of times in seconds
auth     = [random.lognormvariate(-3.5, 0.3) for _ in range(10_000)]
retrieve = [random.lognormvariate(-1.3, 0.4) for _ in range(10_000)]
rerank   = [random.lognormvariate(-1.8, 0.5) for _ in range(10_000)]
model    = [random.lognormvariate(-0.5, 0.35) for _ in range(10_000)]
total = [a + b + c + d for a, b, c, d in zip(auth, retrieve, rerank, model)]

print(f"sum of the step p95s: {p95(auth) + p95(retrieve) + p95(rerank) + p95(model):.2f} s")
print(f"p95 of the total:     {p95(total):.2f} s")
```

This prints 2.03 seconds for the sum and 1.67 seconds for the true total, because the steps here are independent.

### What makes AI requests slow

**Generation time** is roughly output tokens multiplied by the time per token. At 60 tokens a second, a 450-token answer takes 7.5 seconds to stream and a 200-token answer about 3.3 seconds. Capping answer length is often the cheapest speed-up you have.

**Time to first token** grows with prompt length, with queueing in your own system and at the provider, and with the provider's load at that hour. Trim context and reuse a cached prompt prefix where your provider supports it. Reasoning models may think before they show anything, so measure the first token the user actually sees.

**Rate limits** on tokens or requests per minute reject calls with 429 (Too Many Requests) however many servers you run. Check how your provider counts input and output tokens, work out what you need at peak, and ask for a higher limit weeks ahead.

### Sizing with Little's law

**Little's law**: requests in flight = arrival rate x time each request spends in the system. Suppose the pilot's logs show each active user sends about 2 messages a minute. At 500 users that is about 17 requests a second. If each takes 4.5 seconds, about 75 answers are streaming at any moment. That number, not 500, sizes your connection pools, worker counts and any concurrency cap.

### Designing the test

Model real behaviour: real questions (masked), typical prompt and answer lengths, think time between messages, and the expected peak. Ramp from low to beyond the peak and **hold each step** for a couple of minutes, so percentiles settle. Watch p95 and p99, errors by status code, CPU, memory, database connections, queue length and provider 429s.

**Closed and open tests.** In a **closed** test, such as Locust users with think time, each simulated user waits for a reply before sending again. When the system slows, the test sends less, and the slow period produces fewer measurements than it should. This is called **coordinated omission**: the test quietly backs off exactly when real users would not. In an **open** test, requests arrive at a set rate whatever happens, the way travellers rush in when a sale opens. k6 offers this through its constant-arrival-rate and ramping-arrival-rate executors. Use a closed ramp to find bottlenecks step by step, then an open test at the expected arrival rate, with a burst, to see the queue.

**Soak test.** Hold the expected peak for 30 to 60 minutes. Leaks of memory, connections or file handles only show over time.

### A fake model server

Real-model load tests cost money and use up rate limits. Run most rounds against a small fake service with the same streaming shape as the provider's API, its first-token delays sampled from your traces:

```python
import asyncio, json, os, random
from fastapi import FastAPI
from fastapi.responses import JSONResponse, StreamingResponse

app = FastAPI()
FIRST_TOKEN_S = [0.30, 0.35, 0.35, 0.35, 0.40, 0.40, 0.40, 0.45, 0.45, 0.45, 0.45, 0.50, 0.50,
                 0.50, 0.50, 0.55, 0.55, 0.55, 0.60, 0.60, 0.60, 0.65, 0.70, 0.70, 1.40]
TOKENS_PER_S = 60
REPLY_TOKENS = 450                                    # today's typical answer length
SHARE_429 = float(os.getenv("FAKE_429_SHARE", "0"))   # for example 0.05

@app.post("/v1/messages")
async def messages():
    if random.random() < SHARE_429:
        return JSONResponse({"error": "rate_limited"}, status_code=429,
                            headers={"retry-after": "2"})
    async def stream():
        await asyncio.sleep(random.choice(FIRST_TOKEN_S))
        for i in range(REPLY_TOKENS):
            yield f"data: {json.dumps({'text': f'tok{i} '})}\n\n"
            await asyncio.sleep(1 / TOKENS_PER_S)
        yield "data: [DONE]\n\n"
    return StreamingResponse(stream(), media_type="text/event-stream")
```

The delays give a model p95 of 0.7 seconds, the model's share of the budget, with one slow reply in 25. Run it with `uvicorn fake_model:app`, and point your app's model base URL at it through configuration in the test environment only. Set `FAKE_429_SHARE` to test your retries and fallback.

### A Locust ramp that times the stream

With `stream=True`, Locust's own row for the request stops its clock when the response headers arrive, often a few milliseconds, long before the first token. So this test records two timings of its own:

```python
import random, time
from locust import HttpUser, LoadTestShape, between, task

QUESTIONS = [q.strip() for q in open("load/questions.txt", encoding="utf-8") if q.strip()]

class Traveller(HttpUser):
    wait_time = between(20, 30)          # think time between messages

    @task
    def ask(self):
        start, first = time.perf_counter(), None
        with self.client.post("/answer", json={"text": random.choice(QUESTIONS)},
                              stream=True, catch_response=True, timeout=60) as r:
            if r.status_code != 200:
                r.failure(f"status {r.status_code}")
                return
            for line in r.iter_lines():               # read the whole stream
                if line and first is None:
                    first = time.perf_counter()
        end = time.perf_counter()
        if first is not None:
            self.record("first token", first - start)
        self.record("full answer", end - start)

    def record(self, name, seconds):
        self.environment.events.request.fire(
            request_type="STREAM", name=name, response_time=seconds * 1000,
            response_length=0, exception=None, context={})

class Ramp(LoadTestShape):
    # (end second, users): hold each step for two minutes
    steps = [(120, 50), (240, 100), (360, 200), (480, 300), (600, 400), (720, 500), (840, 550)]

    def tick(self):
        t = self.get_run_time()
        for end, users in self.steps:
            if t < end:
                return users, 10                      # add up to 10 users a second
        return None
```

Run it with `locust -f load/locustfile.py --headless --host https://staging.example.in --csv results --csv-full-history`. The file `results_stats_history.csv` then gets a row every second for each name, with the user count and percentiles over roughly the last 10 seconds. Read the `first token` and `full answer` rows, and take the median of the 95% column over the last minute of each hold, since a 10-second window at low load holds few requests. Per-step p95 from traces works too. Ignore the built-in POST row (headers only) and the Aggregated row, which mixes all three timings.

### Overload, retries and streaming

- **Retry storms.** If every 429 or timeout is retried at once, up to three times, a struggling system can receive up to four times the traffic. Retry with exponential backoff and random jitter, honour a `retry-after` header when the provider sends one, and cap retries at a small share of traffic.
- **Admission control.** Cap the streams each instance serves at once. Let extra requests wait in a short queue, a few seconds at most, then show a polite "We are busy, please try again in a minute". Turning a few people away beats timing out everyone.
- **Autoscaling and cold starts.** New instances can take minutes to start and warm up. For a known peak, scale up before it begins.
- **Streaming through proxies.** A proxy or load balancer may buffer the response, so tokens arrive in one lump, or close a connection it thinks is idle. Check the buffering and idle-timeout settings on the streaming route.

| Symptom under load | Likely cause | Fix |
| --- | --- | --- |
| Latency rises, CPU low | Waiting on database connections or locks | Larger pool, indexes, caching, fewer queries |
| CPU at 100% | Too few workers or heavy parsing | More workers, move work to background jobs |
| 429 errors | Provider rate limit | Higher limit, fallback model, shorter outputs |
| Traffic jumps as errors start | Instant retries | Backoff with jitter, retry cap |
| Queue grows only in bursts | Too few streams for the arrival rate | Concurrency cap, busy message, scale up early |
| Slow first token only | Long prompts or provider queueing | Trim context, cache the prefix |
| Tokens arrive in one lump | A proxy buffering the stream | Turn buffering off on that route |
| Errors after exactly a minute | A timeout or idle limit in one layer | Align timeouts across every layer |

### Read results with traces open

When p95 jumps at a step, open the slowest traces from that minute. The step that grew (database waits, the reranker, queueing for a model slot) is the bottleneck, and the table above usually names the fix. Then re-run the same test, so you compare like with like.

## A worked example

The Jaipur bus operator expects about 500 travellers chatting at once during festival travel, with a seat sale opening at 10 am. The budget: p95 first token under 2 seconds, p95 full answer under 10 seconds, errors under 1%. All numbers below are illustrative.

**Round 1: closed ramp, fake model.** p95 first token climbs from 1.1 seconds at 50 users to 6 seconds at 200. CPU sits at 25%. The slowest traces all wait for a database connection: the pool holds 10. A pool of 40 and an index on the route table fix it.

| Concurrent users | 50 | 100 | 200 | 300 | 500 | 550 |
|---|---|---|---|---|---|---|
| p95 first token, pool of 10 | 1.1 s | 2.4 s | 6.0 s | stopped: timeouts | not run | not run |
| p95 first token, pool of 40 + index | 1.1 s | 1.1 s | 1.2 s | 1.2 s | 1.3 s | 1.4 s |

**Round 2: one short run on the real model.** Ten minutes, ramping to 300 users, agreed in advance with whoever owns the API account. 429 errors start at about 220 users. Rough arithmetic agrees: the pilot's logs show each user sends about 2 messages a minute of about 2,000 tokens (1,550 in, 450 out), so 4,000 tokens per user per minute, and the account's 900,000 tokens per minute runs out at 225 users. The team caps answers at 200 tokens, which cuts streaming time from 7.5 to about 3.3 seconds and tokens per message to 1,750. They request a higher limit; ten days later the provider grants 2.5 million tokens per minute. They also add a fallback model through their gateway, and backoff with jitter on retries.

**Round 3: open burst test, fake model** (now set to 200-token replies). Little's law: at 500 users, about 17 requests a second of about 4.5 seconds each means about 75 streams in flight. When the sale opens, arrivals jump to about 25 a second, or about 113 in flight. The two instances, capped at 48 streams each, hold 96. Under the burst, p95 first token reaches 9 seconds and 6% of requests time out. The closed ramp never showed this, because its users simply waited. The fix: a third instance started at 9:45 am, and admission control with a 3-second queue and the busy message. On the re-run, p95 first token stays at 1.5 seconds and nobody is turned away.

**Round 4: confirm.** Ten minutes on the real model at 550 users: p95 first token 1.6 seconds, p95 full answer 5.2 seconds, errors 0.3%. That load uses 1.9 million tokens per minute, 77% of the limit. A 45-minute soak on the fake model at 500 users shows flat memory and no leaked connections.

**Launch day.** The peak reaches 480 travellers. During the 10 am burst, demand briefly needs about 2.6 million tokens per minute, 5% above the limit, and the gateway sends a few percent of requests to the fallback model for two minutes. p95 first token stays under 2 seconds.

**The report** shows a chart of p95 against users with the budget line, each bottleneck found and its fix, and the next ceiling: about 700 steady users (2.5 million divided by 3,500 tokens per user per minute), and sooner during bursts.

## Common mistakes

- **Reporting averages.** Report p50, p95 and p99, for first token and full answer.
- **Adding or averaging percentiles.** Neither works; compute them from raw timings.
- **Testing one request at a time.** Pools, locks and rate limits only fail under concurrency.
- **Unrealistic traffic.** Identical tiny prompts and no think time give numbers that mean nothing.
- **Only closed tests.** They back off when the system slows, so they hide the queue a real rush builds.
- **Trusting Locust's request row for streams.** With streaming on, it times only the headers.
- **Burning money on real-model load tests.** Use a fake model for most rounds and one short real run.
- **Forgetting provider limits.** They are often the real ceiling. Do the token arithmetic and ask early.
- **Instant retries.** They multiply load exactly when the system is struggling.

## When a full load test can wait

- **Internal tools with a handful of users**: a quick check with ten concurrent requests is enough.
- **Batch systems**, where throughput per hour matters more than per-user latency; test that instead.
- **Early pilots on platforms that scale for you**, as long as you have checked rate limits and timeouts.

## From demo to production

- **Keep a latency budget by step** and compare traces against it every release.
- **Load-test before launch and before big changes**, mostly with a fake model server.
- **Report p50, p95, p99 and errors** per ramp step, with the bottleneck found.
- **Re-test when traffic patterns change**, such as exam season, a festival sale or a new feature with longer answers.
- **Alert on p95 first-token time and 429 rate** in production, and keep the tokens-per-minute headroom in view.
