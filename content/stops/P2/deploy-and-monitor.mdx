## What it is

Deploying an LLM app means putting it online where real users can reach it reliably. Monitoring means watching how it behaves once there. For LLM apps, monitoring covers four kinds of signal:

- **Errors**: failed requests, provider errors, timeouts.
- **Latency**: how long users wait, especially time to first token.
- **Cost**: tokens and money per request, per user and per day.
- **Quality**: whether answers are still good, from user feedback, automatic checks and sampled review.

```flow
Users -[HTTPS]-> Container on a managed service, Indian region | key from secret settings, a /health endpoint
Container on a managed service, Indian region -> Model API
Container on a managed service, Indian region -> Every request logged | id, user, latency, tokens, cost, model, prompt version, rating
Every request logged -> Daily dashboard | requests, error rate, p95 latency, cost per day, thumbs-up rate
Daily dashboard -> Alerts | errors over 2%, cost over ₹150 a day, app down
Daily dashboard -[weekly]-> Read 20 real conversations -> Fix -> Test env + evals -> Small release -> All users
```

## How it works

**Deploy simply.** For a first app, a managed platform is enough: a container on a serverless service (such as Cloud Run, Azure Container Apps or Amazon ECS Express Mode), or a web app on a platform such as Vercel, Render or Railway. Keep the API key in the platform's secret settings, set environment variables, add a health-check endpoint and enable HTTPS (usually automatic).

**Log every request** with a request id, user (or a pseudonymous id), latency, tokens, cost, model, prompt version and errors. Use a tracing tool or structured logs.

**Dashboards.** A small dashboard with requests per day, error rate, p95 latency, cost per day and feedback rate. Look at it daily at first.

**Alerts.** Error rate above a threshold; cost above a daily budget; latency spikes; the app being down. Send them somewhere someone will see them.

**Quality signals.**

- *User feedback*: thumbs up or down, with an optional reason.
- *Automatic checks*: format validity, refusals, citations present, guardrail triggers.
- *Sampled review*: read 20 real conversations a week.
- *Online evals*: a judge scoring a sample of live answers.

Quality can drop without any error: a provider updates a model, documents change, users start asking new kinds of questions.

**Latency has two parts.** For a streamed reply, users feel **time to first token** (TTFT) and then **time per output token** (TPOT). Total time is roughly TTFT + TPOT × output tokens: a 1.2-second TTFT and 30 ms per token for 300 tokens is about 10 seconds in total, though the user starts reading after 1.2. People read at very roughly 100 to 150 ms per token, so faster streaming than that is barely noticed, while a slow first token always is. Report **percentiles** (p50, p95), never just the average: nine replies at 100 ms and one at 3,000 ms average 390 ms, which describes nobody.

**Metrics, logs and traces.** Metrics are totals that tell you something went wrong at 3:05. Logs are the individual events that tell you what happened at 3:05. A **trace** joins every step of one request (retrieval, prompt, model call, tool calls, final answer) with the time and cost of each, so you can see which step failed. Tools such as Langfuse, LangSmith, Arize Phoenix or plain OpenTelemetry collect them.

**Signals from how people behave.** Users rarely press thumbs down, but their behaviour speaks: stopping a reply half-way, pressing regenerate, rephrasing the same question, or long conversations on a task that should take two turns. Track these alongside explicit ratings.

**Three kinds of drift.** Quality can change with no code change of yours:

- **Your own changes**: a prompt edit, a new document set, a different chunk size.
- **Your users change**: new kinds of questions, a new language, longer inputs after exam results are announced.
- **The model changes**: a provider updates or retires a model behind the same name. Pin dated model versions where offered, and re-run evals before moving.

**How good is your monitoring?** Three numbers from software operations: **time to detect** a problem, **time to resolve** it, and **change failure rate**, the share of releases that need a fix or rollback. A high change failure rate means your evals should catch more before release.

**A small logging wrapper.** Before buying a tool, a few lines give you most of the value. This one streams a reply, measures TTFT and total time, and writes one JSON line per request:

```python
import json, time, uuid
import anthropic

client = anthropic.Anthropic()
PRICES = {"input": 3 / 1e6, "output": 15 / 1e6}       # USD per token; check current prices
USD_TO_INR = 84
VERSION = "rag-v14"                                    # prompt and code version

def answer(user_id, question, system, messages):
    start, first, rid = time.monotonic(), None, str(uuid.uuid4())
    record = {"id": rid, "user": user_id, "version": VERSION, "model": "claude-sonnet-5-5"}
    try:
        with client.messages.stream(model=record["model"], max_tokens=600,
                                    system=system, messages=messages) as stream:
            parts = []
            for text in stream.text_stream:
                first = first or time.monotonic()
                parts.append(text)
            final = stream.get_final_message()
        u = final.usage
        record |= {"ok": True, "stop": final.stop_reason,
                   "in": u.input_tokens, "out": u.output_tokens,
                   "cost_inr": round((u.input_tokens * PRICES["input"] + u.output_tokens * PRICES["output"]) * USD_TO_INR, 3)}
        return "".join(parts), rid
    except anthropic.APIError as err:
        record |= {"ok": False, "error": type(err).__name__}
        raise
    finally:
        now = time.monotonic()
        record |= {"ttft_ms": round(((first or now) - start) * 1000), "total_ms": round((now - start) * 1000)}
        with open("requests.jsonl", "a") as f:
            f.write(json.dumps(record) + "\n")
```

The question and answer text are left out on purpose; see the privacy note below. A daily job reads the file and checks the thresholds:

```python
import json, statistics

def daily_report(path="requests.jsonl", cost_limit_inr=150, error_limit=0.02):
    rows = [json.loads(line) for line in open(path)]
    ok = [r for r in rows if r["ok"]]
    p95 = statistics.quantiles([r["total_ms"] for r in ok], n=20)[-1]
    errors = 1 - len(ok) / len(rows)
    cost = sum(r["cost_inr"] for r in ok)
    alerts = [msg for bad, msg in [
        (errors > error_limit, f"error rate {errors:.1%}"),
        (cost > cost_limit_inr, f"cost ₹{cost:.0f}"),
        (any(r["stop"] == "max_tokens" for r in ok), "some replies were cut off"),
    ] if bad]
    return {"requests": len(rows), "p95_ms": round(p95), "errors": f"{errors:.1%}",
            "cost_inr": round(cost), "alerts": alerts}
```

**Privacy in logs.** Full prompts and replies make debugging much easier, but they are personal data. Under India's Digital Personal Data Protection Act, say in your privacy notice what you keep and why, keep it only as long as needed, mask phone numbers, email addresses and ID numbers, and limit who can read the logs. Many teams log metadata for every request and full text for a small, consented, masked sample.

**Release safely.** Deploy changes to a test environment first, run your evals, then release, ideally to a small share of users before everyone. Keep the previous version ready to roll back.

**Signals and what they tell you:**

| Signal | Example threshold | What a breach suggests |
| --- | --- | --- |
| Error rate | Above 2% for 10 minutes | Provider outage, bug, bad deploy |
| p95 latency | Above 8 seconds | Slow retrieval, long outputs, provider slowness |
| Cost per day | Above ₹150 | A heavy user, a script, a loop |
| Thumbs-down rate | Doubles in a week | Missing documents, a prompt change, new questions |
| Refusal rate | Jumps for one topic | Documents not indexed |

**A weekly review in twenty minutes.** Open the dashboard and compare with last week. Read the ten most recent thumbs-down conversations and ten random ones. Write one line per conversation on what went wrong, if anything. Pick the most common cause and fix it. This small habit catches most quality problems weeks before anyone complains loudly.

**Rolling back.** Keep the previous container image tagged and ready. A rollback should be one command or one click on the platform, tested once before launch. Record the version in every log line, so after a rollback you can confirm the old version is serving traffic.

**Choosing a region.** Pick the hosting region closest to your users and allowed by any data rules, such as an Indian region for Indian users' personal data. Check that the model provider or its cloud partner also offers an endpoint nearby, because a fast app server is little help if every model call crosses continents. Write the region choice in your README, so reviewers can see it was deliberate.

## A worked example

Arjun, a final-year student in Coimbatore, deploys his RAG app over his college's regulations so classmates can use it.

## Common mistakes

- **No logging of cost and tokens.**
- **Only watching errors.** Quality drops without errors.
- **No alerts.** Problems are found by users.
- **Secrets in the code or image.** Use the platform's secrets.
- **Big-bang releases without a rollback.**
- **Averages instead of percentiles.** One slow request hides in an average; the p95 shows it.
- **Logs without the version.** Without the model and prompt version on each line, you cannot tell which release caused a change.
- **Logging everything forever.** Personal data in logs needs masking, a retention limit and restricted access.

## When simple is enough

- **A personal tool or a one-day demo**: print token usage and errors to the console.
- **A small internal pilot** with a handful of users: one log file, the daily report above and a weekly read of conversations.
- **A hosted no-code assistant**, where the platform's own usage page covers cost and errors.

Add tracing tools, online evals and staged releases when real users depend on the app or the pipeline has several steps.

## From demo to production

- **Decide what failures to catch first**, then pick metrics for them: wrong format, missing answers, slow replies, runaway cost.
- **Break every metric down** by version, model, feature and day, so a change can be traced to its cause.
- **Pin model versions** and re-run evals before switching.
- **Write a one-page runbook**: who gets alerts, how to roll back, how to switch to a backup model.
- **Feed what you find back into evals**: every real failure becomes a test case.
