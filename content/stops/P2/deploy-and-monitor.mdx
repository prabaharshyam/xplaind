## What it is

Deploying an LLM app means putting it online where real users can reach it reliably. Monitoring means watching how it behaves once there. For LLM apps, monitoring covers four kinds of signal:

- **Errors**: failed requests, provider errors, timeouts.
- **Latency**: how long users wait, especially time to first token.
- **Cost**: tokens and money per request, per user and per day.
- **Quality**: whether answers are still good, from user feedback, automatic checks and sampled review.

## How it works

**Deploy simply.** For a first app, a managed platform is enough: a container on a serverless service (such as Cloud Run, Azure Container Apps or AWS App Runner), or a web app on a platform such as Vercel, Render or Railway. Keep the API key in the platform's secret settings, set environment variables, add a health-check endpoint and enable HTTPS (usually automatic).

**Log every request** with a request id, user (or a pseudonymous id), latency, tokens, cost, model, prompt version and errors. Use a tracing tool or structured logs.

**Dashboards.** A small dashboard with requests per day, error rate, p95 latency, cost per day and feedback rate. Look at it daily at first.

**Alerts.** Error rate above a threshold; cost above a daily budget; latency spikes; the app being down. Send them somewhere someone will see them.

**Quality signals.**

- *User feedback*: thumbs up or down, with an optional reason.
- *Automatic checks*: format validity, refusals, citations present, guardrail triggers.
- *Sampled review*: read 20 real conversations a week.
- *Online evals*: a judge scoring a sample of live answers.

Quality can drop without any error: a provider updates a model, documents change, users start asking new kinds of questions.

**Release safely.** Deploy changes to a test environment first, run your evals, then release, ideally to a small share of users before everyone. Keep the previous version ready to roll back.

## A worked example

Arjun, a final-year student in Coimbatore, deploys his RAG app over his college's regulations so classmates can use it.

- He containerises the FastAPI app and deploys it to a serverless container service in an Indian region, with the API key in secret settings.
- Every request logs latency, tokens, cost, whether an answer was found and a thumbs rating.
- A simple dashboard (a notebook reading the logs daily) shows the first week: 1,240 questions, median latency 2.3 s, p95 6.8 s, 1.2% errors, ₹410 total cost, 81% thumbs up of rated answers.
- Reading the thumbs-down cases shows most are about the new exam timetable, which was not yet indexed. He adds it.
- An alert he set at ₹150 a day fires on day nine, when a classmate's script sends 3,000 requests; he adds a per-user daily limit.

He submits the link and a one-page report of the week's numbers as his project.

## Common mistakes

- **No logging of cost and tokens.**
- **Only watching errors.** Quality drops without errors.
- **No alerts.** Problems are found by users.
- **Secrets in the code or image.** Use the platform's secrets.
- **Big-bang releases without a rollback.**
