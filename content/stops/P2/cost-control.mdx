## What it is

Every call to a hosted model is billed by the **token**, a word or piece of a word. **Cost control** means knowing which features, users and steps spend those tokens, and cutting the spend without hurting users. The bill for one request has four parts:

- **Fresh input**: the system prompt, tool definitions, history, retrieved text and the user's message, at the full input price.
- **Cache reads and writes**: the part of the input served from, or saved into, the provider's prompt cache, at a much lower or slightly higher price.
- **Output**: the visible reply, at a price several times the input price.
- **Thinking**: the hidden reasoning tokens of a reasoning model. They are billed as output even when the response shows none of them.

```flow
title: Where the money goes in one request
dir: LR
System prompt and tools | same on every call, so cacheable -> Input bill
History and retrieved text | grows with every turn -> Input bill
User message | usually small -> Input bill
Input bill -> Model
Model -[hidden reasoning]-> Output bill | thinking bills as output
Model -[visible reply]-> Output bill
```

Two facts drive most of this lesson. Input is usually the larger token count, because the long fixed prefix is resent on every call. Output, including thinking, is usually the larger price per token. So the big savings come from not resending the prefix at full price, not thinking harder than a task needs, and not using a large model where a small one passes.

## How it works

### Measure first

Log every call with its usage numbers: fresh input tokens, cache-read tokens, cache-write tokens, output tokens and, where the API reports it, the thinking share of output (Anthropic's field is `usage.output_tokens_details.thinking_tokens`; OpenAI reports reasoning tokens under `output_tokens_details` too). Tag each call with feature, user, model, effort setting and prompt version. Then you can answer: which feature costs most, which users, which agent step, and how much is thinking. A monthly total alone hides all of this.

Track **cost per completed task**, not just cost per request. A cheap call that fails, gets retried or goes to a human is not cheap.

### Read the price page, and date it

As of 28 November 2026, Anthropic's API prices three current model sizes like this (US dollars per million tokens):

| Model | Input | Output | Cache read | 5-minute cache write | Batch input / output |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5.5 | $4 | $20 | $0.20 | $5 | $2 / $10 |
| Claude Sonnet 5.5 | $2 | $10 | $0.10 | $2.50 | $1 / $5 |
| Claude Haiku 5.5, prompts up to 100,000 tokens | $0.10 | $0.50 | $0.01 | $0.125 | $0.05 / $0.25 |

Three things to read off it. Output costs five times input. The smallest model is 40 times cheaper than the largest on both. Batch is exactly half price. Other providers use the same structure with different numbers, so read their current pages and write down the date you checked.

### Model choice: the biggest lever

For classification, extraction from clean text, routing and short replies, a small model often matches a large one. Test each task on your eval set with two or three model sizes, use the cheapest that passes, and send only hard requests to the big model. The lesson on batching and model tiering covers routers in depth. Re-count tokens when you switch: different models can use different tokenizers, so the same text can be a different number of tokens.

### Reasoning tokens and effort

Most current models think before answering, and that thinking bills as output at the full output price. Anthropic's documentation is explicit that you pay for the full thinking even when the response shows only a summary or nothing, so the visible reply length does not match the bill.

A quick example on Opus 5.5 prices: a ticket label that is 10 visible tokens plus 90 thinking tokens costs 100 × $20 per million = $0.002 of output, ten times the $0.0002 for the label alone.

The control is the **effort** setting (or "reasoning effort" on other providers). Lower effort means less thinking, and at low effort the model may skip thinking on simple inputs. On Anthropic's API the default is `medium` for Opus 5.5 and Haiku 5.5 and `high` for most other models, so set it explicitly. Three rules:

- **Tune per route.** Chat, tagging and extraction often hold quality at low effort; multi-step maths, code and planning often need high. Measure on the eval for each route.
- **Leave room in `max_tokens`.** Thinking counts toward it. A cap sized for a 200-token reply truncates the answer when the model thinks, and the retry costs more than the cap saved.
- **Keep effort stable within a conversation.** Changing it between requests can invalidate the prompt cache.

### Prompt caching

Prompt caching stores a long, unchanging start of the prompt, such as the system prompt, tool definitions or a big document, so later calls read it cheaply. It is a prefix match: tools first, then the system prompt, then messages, and any change at one point invalidates everything after it. On Anthropic's API, as of November 2026:

- A 5-minute cache write costs 1.25 times the input price and pays off after one read. A 1-hour write costs 2 times and pays off after two reads.
- A read costs 0.1 times input on most models, and 0.05 times on Opus 5.5 and Sonnet 5.5.
- Prompts shorter than a minimum length, 512 tokens on the current models, are not cached, and no error tells you.

Caching fails quietly. Common causes: a date or request ID near the top of the system prompt, tool definitions built in a different order each time, a changed effort setting, a switch to another model (each model has its own cache), or traffic so thin that the 5-minute lifetime runs out between calls. Check the cache-read count in usage. If it stays at zero, find the change.

**Response caching** is different: you store whole answers and skip the model for repeated questions. It saves more per hit but risks stale or leaked answers. The lesson on caching and speed covers both.

### Batch APIs

Work that can wait, such as nightly summaries, bulk tagging, eval runs and backfills, can go through a batch API. Anthropic's Message Batches API charges 50% of the normal price for input and output. Most batches finish within an hour; requests not finished within 24 hours expire and are not billed. Batch and caching discounts stack, and the 1-hour cache suits batches because they can take longer than 5 minutes.

### Agents: the history grows every step

An agent sends the whole conversation on every step, so input grows with each step. Suppose a 4,000-token prefix and 1,500 new tokens per step. Eight steps send 4,000 × 8 + 1,500 × (0 + 1 + … + 7) = 32,000 + 42,000 = 74,000 input tokens, for what feels like one task. Cache the fixed prefix and the earlier history, load only the tools the task needs, set a step limit, and summarise or clear old tool results in long runs. The lesson on agent budgets and kill switches covers limits.

### Indian languages and self-hosting

The same reply can need several times more tokens in Hindi, Tamil or Bengali than in English, depending on the tokenizer, so measure tokens per request for each language you serve. The lesson on AI in Indian languages covers this.

Self-hosting an open model swaps a per-token bill for a fixed monthly one. For example, suppose a GPU server costs ₹2.5 lakh a month to run, including people's time. At ₹0.47 per batched summary, the API costs the same once you send about 5.3 lakh summaries a month (2,50,000 ÷ 0.47). Below that the API wins, and above it self-hosting wins only if the open model passes the same evals and the server stays busy. The lessons on vLLM and on total cost of ownership show how to fill in real numbers.

### A calculator

This calculator uses the prices in the table and an illustrative rate of ₹94 to the dollar (the rupee traded at about ₹93 to ₹94 in mid November 2026). It prints the rows of the worked example below.

```python
RATE = 94  # rupees per US dollar: illustrative (about 93 to 94 in mid November 2026)

# US dollars per million tokens, Anthropic API pricing page, checked 28 November 2026
PRICES = {
    "opus-5.5":  {"in": 4.00, "out": 20.00, "cache_read": 0.20, "cache_write": 5.00},
    "haiku-5.5": {"in": 0.10, "out": 0.50, "cache_read": 0.01, "cache_write": 0.125},
}

def cost_inr(model, fresh_in, out, cache_read=0, cache_write=0, batch=False):
    """Rupees for one request. `out` includes thinking tokens, which bill as output."""
    p = PRICES[model]
    usd = (fresh_in * p["in"] + out * p["out"]
           + cache_read * p["cache_read"] + cache_write * p["cache_write"]) / 1e6
    return usd * RATE * (0.5 if batch else 1)

rows = {  # (rupees per request, requests per month)
    "summary, before":  (cost_inr("opus-5.5", 1500, 200), 300_000),
    "summary, batch":   (cost_inr("opus-5.5", 1500, 200, batch=True), 300_000),
    "classify, before": (cost_inr("opus-5.5", 600, 100), 300_000),
    "classify, small":  (cost_inr("haiku-5.5", 600, 10), 300_000),
    "chat, before":     (cost_inr("opus-5.5", 6000, 750), 60_000),
    "chat, after":      (cost_inr("opus-5.5", 1000, 500, cache_read=2700, cache_write=300), 60_000),
}
for name, (per, n) in rows.items():
    print(f"{name:17} ₹{per:.4f} each, ₹{per * n / 1e5:.2f} lakh a month")
```

### Cutting safely

Change one lever at a time and run the feature's evals before and after. Report cost and quality side by side. When a change saves money but lowers quality slightly, write down that the team accepted the trade and why.

### Pricing a feature before launch

Estimate cost per user per month from the pilot: requests per user times cost per request. Compare it with what the user pays after GST and payment fees. For example, with the trimmed chat below at ₹1.51 a reply, a student who sends 600 messages a month costs ₹906, while a ₹149 plan might bring in about ₹120. Either the chat runs on a cheaper route that passes its eval, or the plan has a daily limit. Set caps before launch, and recheck in the first two weeks, because real users rarely behave like the pilot group.

## A worked example

A customer-service platform in Kolkata spends about ₹6.3 lakh a month on model calls, all on Opus 5.5, and wants to halve it. All volumes and token counts below are illustrative, priced with the table above at ₹94 to the dollar.

**Step 1: measure.** Tagged logs show three features:

- **Nightly ticket summaries**: 10,000 a night, 3 lakh a month. Each has 1,500 input and 200 output tokens. Nobody reads them before 10 am.
- **Ticket classification**: 3 lakh a month. Each has 600 input tokens, but output is 100 tokens: a 10-token label plus 90 tokens of thinking.
- **Live chat**: 60,000 replies a month. Each has a 5,000-token system prompt and tools, uncached, plus 1,000 tokens of history and question. Output is 750 tokens: 450 visible and 300 thinking.

**Step 2: price each feature.**

- Summaries: (1,500 × $4 + 200 × $20) ÷ 10 lakh = $0.0100, which is ₹0.94 each, so 3 lakh × ₹0.94 = ₹2.82 lakh (45%).
- Classification: (600 × $4 + 100 × $20) ÷ 10 lakh = $0.0044, which is ₹0.41 each, so ₹1.24 lakh (20%). Thinking is 90 of the 100 output tokens.
- Chat: (6,000 × $4 + 750 × $20) ÷ 10 lakh = $0.0390, which is ₹3.67 each, so 60,000 × ₹3.67 = ₹2.20 lakh (35%).

Total: ₹6.26 lakh.

**Step 3: change one lever per feature.**

- **Summaries move to the batch API.** Same tokens at half price: ₹0.47 each, ₹1.41 lakh a month. They are ready long before 10 am.
- **Classification moves to Haiku 5.5 at low effort.** Lowering effort alone on Opus 5.5 removes the thinking (600 × $4 + 10 × $20 = $0.0026, ₹0.24 each, 41% less). The small model at low effort costs (600 × $0.10 + 10 × $0.50) ÷ 10 lakh = $0.000065, ₹0.0061 each, about ₹1,800 a month. On 400 labelled tickets, accuracy goes from 94% to 93%, and the team accepts it.
- **Chat keeps Opus 5.5.** The system prompt is trimmed from 5,000 to 3,000 tokens and cached. Busy daytime traffic gives a 90% hit rate, so on average 2,700 tokens are cache reads at $0.20 per million and 300 are writes at $5 per million. The prompt asks for replies under about 150 words, which brings visible output from 450 to 200 tokens. Thinking stays at 300. `max_tokens` is set to 1,200, not 200, so the thinking never truncates a reply. Per reply: 1,000 × $4 + 2,700 × $0.20 + 300 × $5 + 500 × $20 = $0.01604, which is ₹1.51, so ₹0.90 lakh a month.
- **Limits.** A daily cap per support agent, a step limit on the chat's tool use, a spending alert at 80% of budget and a hard monthly limit in the provider console.

| Feature | Before | After | Lever | Quality check |
| --- | --- | --- | --- | --- |
| Nightly summaries | ₹2.82 lakh | ₹1.41 lakh | Batch API, half price | Ready before 10 am as before |
| Classification | ₹1.24 lakh | ₹0.02 lakh | Small model, low effort | 94% to 93% on 400 tickets, accepted |
| Live chat | ₹2.20 lakh | ₹0.90 lakh | Shorter cached prompt, shorter replies | Satisfaction scores unchanged |
| Total | ₹6.26 lakh | ₹2.33 lakh | | 63% lower |

The ₹2.33 lakh is an estimate. The team checks it against the next month's real bill, because the 90% cache hit rate is an assumption: at night, when chats are more than 5 minutes apart, the cache expires and every reply pays a write instead of a read.

## Common mistakes

- **Reading only the visible reply.** The bill doubles after a model upgrade while replies look the same length. The cause is thinking tokens: check the thinking count in usage before blaming the price.
- **Retries that resend everything.** Three instant retries on a timeout bill a 6,000-token prompt up to four times and make an overload worse. Use at most two retries, with exponential backoff and jitter.
- **A cache that never hits.** A timestamp at the top of the system prompt makes every prefix different. Symptom: cache-read tokens stay at zero while cache writes, which cost more than plain input, keep appearing.
- **Every tool on every call.** Thirty tool definitions of 200 tokens each add 6,000 input tokens to every step, even when the step needs two tools.
- **A `max_tokens` cap with no room for thinking.** Replies stop mid-sentence with a `max_tokens` stop reason, users retry, and you pay twice.
- **Judging cost per request, not per completed task.** A model 20 times cheaper per call that fails a fifth of the time can cost more once retries and human review are counted.
- **Cutting cost without checking quality.** Run the evals on every change, and keep the numbers.

## When cutting cost is the wrong goal

- **The feature is not working yet.** Get quality right on your evals first; optimise later.
- **The savings are tiny.** Saving ₹2,000 a month is not worth weeks of engineering or a measurable quality drop.
- **Latency or trust matters more.** A cheaper model that is slower or makes more mistakes on a high-stakes task can cost more in support and lost users.

## From demo to production

- **Tag every call** with feature, user, model, effort and prompt version, and store all the token counts and the cost.
- **Build one cost dashboard**: spend per day by feature, cost per completed task, the heaviest users, the thinking share of output and the cache hit rate, with lines for the budget and the alert threshold. Review it weekly with the quality metrics.
- **Set budgets per feature** with alerts, and hard limits at the provider.
- **Re-price regularly.** Providers cut prices and release cheaper models; a choice from six months ago may now be overpaying.
- **Keep the cheaper path tested**, such as a smaller fallback model, so you can switch quickly if costs spike.
