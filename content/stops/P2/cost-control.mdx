## What it is

LLM apps cost money on every request, and costs grow with users, longer prompts and agent loops. **Cost control** means knowing where the money goes and reducing it without hurting the user experience. The main levers are model choice, prompt size, output size, caching, batching and limits.

```text
   monthly spend ₹6 lakh, by feature (from tagged logs)
   nightly ticket summaries  ██████████████████████  45%  -> batch API
   live chat replies         █████████████████       35%  -> trim + cache prompt, cap replies
   ticket classification     ██████████              20%  -> small model (94% -> 93%)

   + per-agent daily cap   + alert at 80% of budget   + provider hard limit
   next month: ₹2.7 lakh, customer satisfaction unchanged
```

This lesson follows a customer-service platform in Kolkata that wanted to halve its model bill.

## How it works

**Measure first.** Log tokens and cost for every call, tagged with feature, user and model. Then you can answer: which feature costs most? Which users? Which step of an agent? Monthly totals alone hide this; cost per user and per feature show where to act and whether a feature can pay for itself.

**Model choice: the biggest lever.** Smaller models can cost many times less than the largest ones. For simple tasks such as classification, extraction from clean text, routing and short replies, a small model often matches a large one. Test each task on your eval set with two or three model sizes and use the cheapest that passes. Route only hard requests to the big model.

**Prompt size.** Every request pays for its input. Trim system prompts, send fewer and shorter retrieved chunks, summarise long conversation history, and remove unused tool definitions.

**Output size.** Output tokens usually cost more than input. Ask for concise formats and set `max_tokens`.

**Caching.** Prompt caching for long shared prefixes; response caching for repeated questions.

**Batching.** Work that can wait (nightly summaries, bulk classification, embedding a corpus) can go through batch APIs, which providers typically offer at a large discount in exchange for results within hours.

**Limits.** Daily caps per user, step limits on agents, spending alerts and hard limits in the provider console.

**Watch for surprises.** Retry storms, agents looping, a single huge document, or one heavy user can multiply costs overnight.

**Levers and typical savings:**

| Lever | Typical effect | Risk |
| --- | --- | --- |
| Smaller model for simple tasks | Large saving on that task | Quality drop if not tested |
| Batch API for waiting work | Large discount | Hours of delay |
| Prompt caching | Lower input cost on repeated prefixes | Breaks if the prefix varies |
| Shorter prompts and outputs | Proportional saving | Missing context or detail |
| Response caching | Removes repeated calls | Stale or shared answers |
| Caps and alerts | Prevents surprises | Users hitting limits |

**A cost dashboard that drives action.** Show spend per day by feature, cost per user for the heaviest users, cost per successful task, and the share of tokens from each part of the prompt for the top feature. Add a line for the budget and the alert threshold. Review it weekly. The dashboard should answer, in one glance, which feature to optimise next and whether last week's change worked.

**Cutting safely.** Change one lever at a time and run the feature's evals before and after. Report cost and quality side by side. When a change saves money but lowers quality slightly, as with the classifier here, write down that the team accepted the trade and why.

**Pricing a feature before launch.** Estimate cost per user per month from the pilot: requests per user, tokens per request and the model's price. Compare it with what the feature earns or saves per user. If one user's monthly cost could exceed their value, set caps before launch, not after the first large bill. Revisit the estimate in the first two weeks of real traffic, because real users rarely behave like the pilot group.

## A worked example

A Kolkata customer-service platform spends ₹6 lakh a month on model calls and wants to halve it.

Logging by feature shows:

- 45% on a nightly job that summarises 10,000 support tickets for team leads, which nobody reads before 10 am;
- 35% on live chat replies;
- 20% on ticket classification.

Changes:

- The nightly summaries move to the provider's batch API at a large discount, finishing well before morning.
- Ticket classification switches from the large model to a small one; on 400 labelled tickets, accuracy drops from 94% to 93%, which the team accepts.
- Live chat keeps the large model, but the system prompt is trimmed by 40% and cached, and replies are capped at 200 tokens.
- A per-agent daily cap and a spending alert at 80% of budget are added.

The next month's bill is ₹2.7 lakh, with no change in customer satisfaction scores.

| Change | Cost effect | Quality check |
| --- | --- | --- |
| Nightly summaries to batch | Large discount on 45% of spend | Ready before 10 am as before |
| Classification to small model | Much cheaper | 94% to 93% on 400 tickets, accepted |
| Chat prompt trimmed 40% and cached; replies capped | Lower chat cost | Satisfaction unchanged |

## Common mistakes

- **Optimising without measuring by feature and user.**
- **Using the largest model for everything.**
- **Paying real-time prices for work that can wait.**
- **Long prompts and unlimited outputs.**
- **No alerts or caps.**

- **Cutting cost without checking quality.** Run the evals on every change.

## Practise

Read Chip Huyen's article on building LLM applications for production linked below, especially the cost sections.

1. Add cost logging per call with feature and user tags to one of your apps, and find the most expensive feature.
2. Test that feature with a smaller model on your eval set and decide whether to switch.
3. Move one non-urgent job to batch processing, or add a cap and an alert.

**You are done when you can** show cost per feature and per user, and one change that cut cost without hurting your eval scores.
