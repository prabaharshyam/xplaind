## What it is

Every AI product starts the same way: your app sends a question to a model and shows the answer. That is a complete, working architecture. Most real products grow from there by adding parts, and the order matters.

A common order, as many teams grow:

1. **Enhance context.** Give the model the right information: retrieval from documents, data lookups, tools.
2. **Put in guardrails.** Check what goes into the model and what comes out.
3. **Add a router and a gateway.** Send each request to the right place, and manage all model calls in one spot.
4. **Add caches.** Avoid paying twice for the same work.
5. **Add agent patterns.** Loops, several steps and actions that change things in the world.

Alongside all of this, from the first day: **monitoring**, so you can see what each part does.

This is not a strict recipe. The point is to add a layer only when a real problem asks for it, so the system stays as simple as the product allows.

```flow
title: One request through a grown AI app
User question -> Input guardrails | mask personal data, block injection
Input guardrails -> Router | intent: FAQ, account, out of scope
Router -[FAQ]-> Cache | exact or semantic
Cache -[miss]-> Retrieve context | documents, data, tools
Router -[account]-> Retrieve context
Router -[out of scope]-> Stock reply
Retrieve context -> Gateway | keys, limits, retries, fallback
Gateway -> Model
Model -> Output guardrails | format, facts, safety
Output guardrails -[fail]-> Retry or hand to a person
Output guardrails -[pass]-> Answer and log the trace
```

## How it works

**Step 1: enhance context.** A model only knows its training data and what you put in the prompt. Most early quality problems are missing or stale facts, so the first addition is usually retrieval (documents, a database, a search index) or tools (an order lookup, a calculator). The RAG and tool-calling lessons cover these in depth.

**Step 2: guardrails.** There are two kinds.

- **Input guardrails** stop private data leaking to outside services, for example by masking Aadhaar numbers, phone numbers and names before the model call, and catch harmful or injected instructions.
- **Output guardrails** check the answer before the user sees it: valid format, no unsupported claims, no personal data, nothing against your policy. When a check fails you can retry, fall back to another model, return a safe message or hand to a person.

Guardrails add latency, especially on streamed answers, where you must decide whether to check text before or while it is shown. Keep fast checks inline and slower ones on a sample.

**Step 3: router and gateway.**

- A **router** decides where a request goes, usually with a small, fast intent classifier. It can send easy questions to a cheap model and hard ones to a strong model, send billing disputes to a person, answer out-of-scope questions with a polite stock reply without calling a model at all, or ask for clarification when a message is ambiguous ("Freeze my account, or the weather?").
- A **gateway** is one place through which every model call passes. It holds the API keys so they are not scattered across services, controls who may use which model, enforces spend limits, logs every call, and retries or falls back to another provider when one is down.

**Step 4: caches.**

- **Exact cache:** the same normalised question, template version and model gives the same stored answer. Safe and simple.
- **Semantic cache:** reuse an answer when a new question *means* the same as an old one, matched with embeddings and a similarity threshold. It can save a lot when questions repeat, but a loose match returns the wrong answer ("refund for order 1" is close to "refund for order 2"). Only add it when the hit rate is high and you have measured its mistakes.
An exact cache key that is safe to reuse includes everything that changes the answer:

```python
import hashlib, re

def cache_key(question, template_version, model, day):
    """Same key only when the answer would be the same: same words, prompt, model and day."""
    normalised = re.sub(r"\s+", " ", question.strip().lower())
    raw = f"{normalised}|{template_version}|{model}|{day}"
    return hashlib.sha256(raw.encode()).hexdigest()

# cache_key("What are Dr Mehta's timings?", "v7", "fast-model", "2026-11-08")
```

- **Prompt caching** and the **KV cache** happen at the model provider or server; keep the fixed part of your prompt first so they work.

**Step 5: agent patterns.** So far each request flows one way. Agent patterns add loops (retrieve again if the first answer is incomplete), several steps, and **write actions** such as sending an email or booking an appointment. They make the system far more capable and far riskier. Add them last, with approvals for anything that changes data, limits on what tools can do, and budgets on steps and spend.

**Monitoring from day one.** Log every request as a trace: the input, retrieved context, model, prompt version, output, guardrail results, latency and cost, with personal data masked. Track a few signals on a dashboard: error and refusal rates, guardrail triggers, cost per request, latency, and user feedback. As the system grows, traces are how you find which layer failed.

| Layer | Add it when | Typical tools | New risk it brings |
| --- | --- | --- | --- |
| Context | Answers miss or invent facts | Vector search, SQL, APIs | Wrong or stale documents |
| Guardrails | Real users and real data arrive | PII masking, validators, judge checks | Latency, false blocks |
| Router | Requests differ in difficulty or type | Small classifier, rules | Misrouted requests |
| Gateway | More than one model, service or team | LiteLLM, cloud gateways | A single point of failure |
| Cache | Many repeated questions | Redis, vector index | Stale or wrong reuse |
| Agents and actions | Tasks need several steps or changes | Agent SDKs, LangGraph | Runaway loops, harmful actions |

## A worked example

A chain of 40 clinics in Pune runs a WhatsApp assistant. It began as one model call with a long prompt listing timings and fees. Six months in, there are four problems: fees quoted are sometimes out of date, patients share Aadhaar and phone numbers in messages, the same ten questions make up 40% of traffic, and patients keep asking it to book appointments.

They grow it in order:

1. **Context.** Timings, fees and doctor schedules now come from the clinic system at question time. Out-of-date fees disappear.
2. **Guardrails.** Aadhaar and phone numbers are masked before any model call. An output check blocks anything that reads like a diagnosis and confirms fees match the clinic system.
3. **Router.** A small classifier sends the top FAQs to fixed answers, lab-report questions to a secure link, and anything urgent to a phone number, with no model call.
4. **Exact cache** for the remaining repeated questions, keyed on the normalised question and the date, because schedules change daily.
5. **Booking as a tool**, last: the assistant proposes a slot, the patient confirms with a button, and every booking is logged.

| Measure | Before | After |
| --- | --- | --- |
| Model calls per 1,000 messages | 1,000 | 520 |
| Wrong fee or timing answers (weekly sample) | 6% | under 1% |
| Messages sent to the model with Aadhaar numbers | Some each day | None |
| Bookings completed in chat | 0 | 22% of booking requests |

The numbers are for illustration. They did not add a semantic cache: a test showed it matched "Dr Mehta's timings" with "Dr Mehra's timings".

## Common mistakes

- **Building the whole platform first.** Five layers before ten users means five places to debug and nothing learned.
- **Adding agents before context works.** An agent that acts on wrong facts does more damage, faster.
- **Guardrails that only log.** A check that does not block, retry or escalate protects nothing.
- **A semantic cache on questions with details.** Order numbers, names and dates make similar questions mean different things.
- **No traces.** Without a trace per request, you cannot tell whether retrieval, the router or the model failed.
- **Keys and limits spread across services.** A gateway, even a simple one, keeps spend and access in one place.

## When to stay simple

- **Internal tools for a handful of people** may never need a router, gateway or cache.
- **Low volume** makes caching and routing savings too small to matter.
- **Read-only answers** do not need agent loops or write actions.

## From demo to production

- **Write down why each layer exists**, with the problem it solved and its measured effect.
- **Test layers separately**: retrieval recall, router accuracy, guardrail false-block rate, cache error rate.
- **Version everything together**: prompts, router model, guardrail rules and cache keys, so a release can be rolled back as one.
- **Fail safely**: if a layer is down, the request should fall back to a simpler path, not an error page.
