## What it is

**Open-weight models** publish their weights, so you can run them on your own hardware. **vLLM** is an open-source engine that serves such models efficiently on GPUs. Its two key ideas:

- **PagedAttention**: it manages the memory that holds each request's attention cache in small pages, like an operating system manages memory, so far more requests fit on one GPU.
- **Continuous batching**: new requests join the batch as soon as others finish, instead of waiting for a whole batch, which keeps the GPU busy.

vLLM exposes an **OpenAI-compatible API**, so most client code and gateways work with it unchanged.

```text
   client code / gateway  --(OpenAI-compatible API)-->  [vLLM server]
                                                         |
                       continuous batching: requests join and leave the batch every step
                                                         |
             GPU memory (48 GB):  [weights 4-bit, ~9 GB][ KV cache in pages ................ ]
                                                          PagedAttention: no wasted gaps
                                                         |
   metrics: tokens per second | queue length | cache usage     pinned: model revision + vLLM version
```

This lesson follows an insurance company in Chennai that must keep claim documents on its own servers.

## How it works

**Choosing a model.** Start from the task and your evals, not leaderboards. Check the licence for commercial use, the languages it handles (Indian languages vary widely between models), context length and size. Smaller models (7 to 14 billion parameters) run on one GPU and are often enough for extraction, classification and grounded RAG answers.

**Sizing memory.** A rough rule: weights need about 2 bytes per parameter at 16-bit precision. An 8-billion-parameter model needs about 16 GB for weights. On top of that, the attention (KV) cache grows with the number of concurrent requests and their context length. A 24 GB GPU can serve an 8B model with modest concurrency; a 70B model needs about 140 GB at 16-bit, so several GPUs or quantization.

**Quantization.** Storing weights in 8 or 4 bits cuts memory by half or three quarters and often increases speed, with a small quality loss that you must measure on your own evals. Common formats include AWQ, GPTQ and FP8.

**Running it.**

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 8192 --gpu-memory-utilization 0.90
# now: POST http://localhost:8000/v1/chat/completions
```

Key settings: maximum context length (shorter means more concurrent requests fit), GPU memory share, tensor parallelism across several GPUs (`--tensor-parallel-size 2`) and quantization.

**In production.** Run it in a container with the weights in a volume or baked into an internal image, behind your gateway, with health checks, metrics (tokens per second, queue length, cache usage) and autoscaling where GPUs allow. Pin the model revision and the vLLM version, and evaluate before every upgrade.

**Key vLLM settings:**

| Setting | Example | Effect |
| --- | --- | --- |
| `--max-model-len` | 8192 | Shorter limits leave more room for concurrent requests |
| `--gpu-memory-utilization` | 0.90 | Share of GPU memory vLLM may use |
| `--tensor-parallel-size` | 2 | Splits a model across GPUs in one machine |
| `--quantization` | awq | Uses a quantized checkpoint to save memory |

**Comparing with an API fairly.** Run the same golden set through the self-hosted model and an API model. Record accuracy by task and language, p95 latency under a realistic load test, and cost per 1,000 requests, including the GPUs' full monthly cost divided by actual volume. Self-hosting often looks cheap per token at full load and expensive at low use, so use the real expected volume. Write the result as a short table the client's team can sign off.

**Operating it.** Watch the queue length and cache usage: a growing queue means you need more capacity or shorter contexts. Keep one spare GPU or replica so a failure or an upgrade does not stop service. Store the weights in an internal registry or volume, because downloading them at start-up from the internet is slow and may be blocked on locked-down networks.

## A worked example

A Chennai insurance company must keep claim documents on its own servers. It wants extraction of 20 fields from claim forms and short grounded answers for its claims staff, about 30,000 requests a day.

Evals on 300 real forms compare three open-weight models of 7 to 14 billion parameters against a frontier API. The best 14B model reaches 95% field accuracy against the API's 97%; the client accepts the gap for keeping data on-premises.

Sizing: the 14B model at 16-bit needs about 28 GB for weights. With 4-bit AWQ quantization it needs about 9 GB, and the evals drop only to 94.5%. On a single 48 GB GPU, that leaves ample room for the KV cache at 8,000-token contexts, and a load test shows 40 concurrent requests at under 3 seconds each at p95. Two GPUs give headroom and redundancy.

vLLM runs in containers on the client's Kubernetes cluster, behind the same gateway as before, so the application code changes only one model alias. Upgrades happen quarterly after the eval suite passes.

| Option | Field accuracy | Memory for weights | Notes |
| --- | --- | --- | --- |
| Frontier API | 97% | Not applicable | Data would leave the premises |
| 14B model, 16-bit | 95% | About 28 GB | Fits, less room for the cache |
| 14B model, 4-bit AWQ | 94.5% | About 9 GB | 40 concurrent requests under 3 s at p95; chosen |

## Common mistakes

- **Picking a model from a leaderboard.** Test on your own data and languages.
- **Forgetting the KV cache in sizing.** Weights fit, then the server fails under load. Size for concurrency.
- **Quantizing without measuring.** Some tasks lose more quality than others. Run your evals.
- **Ignoring licences.** Some open-weight licences restrict commercial use or large deployments.
- **Unpinned versions.** A new model revision or engine release can change outputs. Pin and evaluate.

## Practise

Follow the vLLM quickstart on any GPU you can access (a free notebook GPU is enough for a small model), and read the PagedAttention post.

1. Serve a small instruct model with vLLM and call it with an OpenAI-compatible client.
2. Calculate the weight memory for a 7B, 14B and 70B model at 16-bit and 4-bit, and estimate how many GPUs each needs.
3. Run your extraction or RAG golden set against the self-hosted model and an API model, and compare accuracy, latency and cost per 1,000 requests.

**You are done when you can** serve a model behind an OpenAI-compatible endpoint and justify its size, quantization and GPU choice with numbers.
