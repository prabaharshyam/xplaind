## What it is

Three techniques cut cost and waiting time in LLM apps. They work at different layers, and mixing them up causes most caching bugs.

- **Prompt caching** happens at the model provider. The provider keeps the processed form of the start of your prompt (instructions, tool definitions, a long document). A later request that begins with exactly the same content skips that work, so it costs less and the first token arrives sooner. The model still writes a fresh answer every time.
- **Response caching** happens in your own app. You store finished answers and return one when the same request comes again, with no model call at all. Because you build it, you decide who may see each stored answer.
- **Streaming** changes delivery, not work. The reply reaches the screen piece by piece as it is generated, so the user starts reading in a second or two.

A request that uses all three looks like this:

```flow
title: One request, three layers
Question arrives -> In my response cache?
In my response cache? -[hit, same scope]-> Return stored answer | no model call
In my response cache? -[miss]-> Call the model -> Provider reads cached prefix | instructions and documents
Provider reads cached prefix -> Stream tokens to the screen -> Store the finished answer | only if safe to reuse
```

This lesson follows a contract assistant at a legal-tech company in Chennai. Lawyers upload an agreement and ask about ten questions on it.

## How it works

### Where the time goes

A reply has two phases. First the model reads the whole input (**prefill**). Then it writes the reply one token at a time (**decode**). A long input slows the first token. A long output slows everything after it. So a 30,000-token contract mostly hurts **time to first token** (TTFT), while a 1,000-token answer mostly hurts total time. Prompt caching attacks the first; streaming hides the second; shorter answers and smaller models shrink it.

### Prompt caching

The cache matches an **exact prefix**: the request must start with the same bytes, in the same order, as a request seen recently. One changed character invalidates everything after it. So order the prompt from most stable to least stable:

1. tool definitions, in a fixed order;
2. system instructions;
3. long reference documents (the contract, the policy, the codebase);
4. per-user or per-session data;
5. the latest question and conversation turns.

Never put a timestamp, a request id or the user's name at the top. If the model needs today's date, put it near the end.

**The numbers that decide whether it pays.** With Claude's API, as of November 2026 (checked on 28 November 2026; see the pricing page linked below):

| Item | Value |
| --- | --- |
| Cache write, 5-minute lifetime (the default) | 1.25x the normal input price |
| Cache write, 1-hour lifetime (`"ttl": "1h"`) | 2x the normal input price |
| Cache read | 0.1x on most models; 0.05x on Sonnet 5.5 and Opus 5.5; 0.025x on Fable 5.1 and 5.2 |
| Lifetime | Counted from the start of the last request that wrote or read the entry; each read restarts the clock at no extra cost |
| Minimum cacheable prefix | 512 tokens on current models (1,024 to 4,096 on some older ones); shorter prefixes are not cached and no error is raised |
| Breakpoints per request | Up to 4 |
| Who shares an entry | Your workspace only; never another organisation |

Two rules follow. A 5-minute cache pays for itself after one read; a 1-hour cache needs two. And the lifetime matters more than the price: if requests sharing a prefix arrive further apart than the lifetime, every request pays the write premium and none gets the read discount, which costs more than no caching.

Choose the lifetime by the gap between requests that share the prefix. Under 5 minutes, use the default; steady traffic keeps it warm on its own. Between 5 and 60 minutes, use the 1-hour cache. Over an hour, either accept a cold first request or **pre-warm**: just before traffic is expected (worker start, the first lawyer's login), send the shared prefix once with `max_tokens` set to 0. Claude's API then writes the cache and returns without generating anything.

**Parallel requests do not share a cache that is still being written.** An entry becomes readable only once the first response starts. If you fire ten requests at the same moment, all ten pay full price. Send one first, wait for its first token, then send the rest.

**Other providers.** Some, such as OpenAI, cache automatically once a prompt reaches a minimum length (at least 1,024 tokens, depending on the model, per its documentation). Claude offers automatic caching or explicit breakpoints. Stable content first works everywhere; minimums, lifetimes and prices differ, so read your provider's page before estimating savings.

**Prompt caching in code.** With Anthropic's Python SDK you mark the end of the stable part, and the usage report shows what was read from cache:

```python
import anthropic

client = anthropic.Anthropic()
POLICY = open("returns_policy.md").read()          # long, rarely changes

def ask(question):
    reply = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=2000,  # check the docs for current model names
        system=[
            {"type": "text", "text": "You answer questions about our returns policy. Be brief."},
            {"type": "text", "text": POLICY,
             "cache_control": {"type": "ephemeral"}},  # cache up to here; add "ttl": "1h" for slow traffic
        ],
        messages=[{"role": "user", "content": question}],   # changing part goes last
    )
    u = reply.usage
    print(f"cache write {u.cache_creation_input_tokens}, cache read {u.cache_read_input_tokens}, "
          f"uncached {u.input_tokens}")
    return reply

ask("Can I return a kurta after 10 days?")       # first call writes the cache
ask("Do you refund shipping charges?")           # later calls read it
```

**Checking that it works.** Log the three usage numbers on every call. Send five requests in a row: the first should show a cache write and the rest cache reads of about the same size. If reads stay at zero, something in the prefix still changes: a timestamp, a request id, tools built in a different order, JSON without sorted keys, a prefix below the minimum, or a changed model or thinking setting. If reads are much smaller than the prefix, the breakpoint is in the wrong place.

### Response caching, scoped to the user

A response cache is a key-value store, such as a dictionary or Redis. The key must contain **everything that changes the answer**: the normalised question, the document or data version, the prompt version, the model, and the **scope**, meaning who is allowed to see the answer.

Scope is the part teams forget, and forgetting it leaks data. Suppose the key is only the question. Asha asks "Where is my order?" and the answer, with her address, is stored. Ravi asks the same words and gets Asha's answer from the cache, in milliseconds, with no error in any log. The provider's prompt cache cannot cause this, because the model writes a new answer each time. Your response cache can, because it returns stored text.

Use three scopes. **Public**: the same for everyone, such as product FAQs and fixed help text. **Tenant**: the same within one company, such as a law firm's own standard NDA, but never shown to another firm. **User**: personal or permission-dependent; key it by user id, or do not cache it at all. Make the scope a required argument so nobody can forget it:

```python
import hashlib, json, time

CACHE, TTL_SECONDS = {}, 24 * 3600
PROMPT_VERSION, MODEL = "faq-v3", "claude-sonnet-5-5"

def cache_key(scope, question, doc_version):
    norm = " ".join(question.lower().split())
    raw = json.dumps([scope, norm, doc_version, PROMPT_VERSION, MODEL])
    return hashlib.sha256(raw.encode()).hexdigest()

def cached_answer(scope, question, doc_version, compute):
    # scope: "public", "firm:<id>" or "user:<id>"; there is no default on purpose
    key = cache_key(scope, question, doc_version)
    hit = CACHE.get(key)
    if hit and time.time() - hit["at"] < TTL_SECONDS:
        return hit["answer"]
    answer, complete = compute(question)          # complete: the reply finished normally
    if complete:                                  # never cache errors or cut-off replies
        CACHE[key] = {"answer": answer, "at": time.time()}
    return answer
```

Before shipping, run a two-account test: user A asks a personal question, user B asks the same words, and B must not receive A's answer. Set an expiry even for stable answers, and clear entries when the source changes; a cached wrong answer repeats until someone notices.

### Semantic caching, carefully

**Semantic caching** matches questions by meaning, using embeddings, so "notice period in our NDA?" can reuse the answer to "What is the NDA notice period?". It raises hit rates, but every wrong match serves a confident wrong answer. Three guards:

- **Filter by scope before the similarity search**, so a match can only come from answers the asker is allowed to see.
- **Require exact agreement on numbers and names.** "Refund for order 41" and "refund for order 14" are nearly identical as text and completely different as questions:

```python
import re

def numbers_match(new_q, cached_q):
    return re.findall(r"\d+", new_q) == re.findall(r"\d+", cached_q)
```

- **Set the similarity threshold from your own data.** There is no safe universal number. Log candidate matches, have a person label 200 of them right or wrong, and raise the threshold until the wrong-match rate is below a target you set for that feature.

### Streaming

Streaming does not change total generation time or cost. It changes the experience: text starts within a second or two, the user reads while the rest arrives, and can press Stop early. In chat, always stream. Measure TTFT:

```python
import time
import anthropic

client = anthropic.Anthropic()

def stream_answer(question):
    start, first = time.perf_counter(), None
    with client.messages.stream(model="claude-sonnet-5-5", max_tokens=2000,
                                messages=[{"role": "user", "content": question}]) as stream:
        for text in stream.text_stream:
            if first is None:
                first = time.perf_counter() - start
            print(text, end="", flush=True)     # in a web app, send each piece to the browser
        final = stream.get_final_message()
    print("\nfirst text after", round(first, 2) if first else None,
          "s; total", round(time.perf_counter() - start, 2), "s; stop:", final.stop_reason)
```

Server timing is not the whole story: in the browser, record `performance.now()` when the user presses Send and when the first words are painted, and report p50 and p95 from real users. Three gotchas. Some proxies, compression layers and hosting platforms buffer the response, so a stream that works locally arrives all at once in production; test through the real path. A stream can fail halfway, so show the partial text with a clear "answer interrupted, try again" and never cache it. And text is on screen before the answer is finished, so any check that needs the full answer, such as a safety filter or JSON validation, must run on each piece or run before you start showing text.

### Other speed levers

Shorter outputs, since generation time grows with length. Smaller models for simple steps. Fewer calls in sequence. Independent calls in parallel (for example with `asyncio.gather`), so the wait is the slowest call, not the sum; mind rate limits, as a burst can return 429 errors. Fewer, better retrieved chunks.

## A worked example

The Chennai contract assistant answers questions about a 40-page agreement. The numbers below are an **illustration** built on Claude Sonnet 5.5 list prices as of November 2026 ($2 per million input tokens, $10 per million output, cache writes $2.50 for 5 minutes or $4 for 1 hour, cache reads $0.10), with these assumptions: the instructions and contract are 30,000 tokens, each question is 100 tokens and is sent on its own, each answer uses 300 output tokens, and there are 10 questions per contract. Check current prices before you reuse the figures.

**Before.** Every question sends the full 30,100 tokens at full price: $0.0602 of input plus $0.003 of output, so $0.0632 per question and **$0.63 per contract**. Nothing streams, so the lawyer sees nothing for about 9 seconds.

**After, first attempt.** The team moves the contract and instructions to the front, adds a breakpoint, and keeps the default 5-minute cache. If questions came less than 5 minutes apart, question 1 would cost $0.078 (the write premium makes it dearer than before) and each later question $0.0062, so **$0.13 per contract, 79% less**. But the logs show cache writes on almost every call. Lawyers read each answer against the clause before asking the next question, often 5 to 15 minutes later. Each entry expires, each question pays the write price, and the bill rises to **$0.78 per contract, 24% more than no caching**.

**After, fixed.** They switch to the 1-hour cache. Question 1 now costs $0.12 for the write, and the next nine $0.0062 each: **$0.18 per contract, about 72% less** than before. At about ₹94 to the dollar (mid-November 2026), that is roughly ₹59 down to ₹17 per contract. Note that the output tokens ($0.003 per answer) are now half the cost of a cached question, so shorter answers are the next saving.

| Per contract session (illustrative) | No caching | 5-minute cache, gaps over 5 min | 1-hour cache, streaming on |
| --- | --- | --- | --- |
| Input cost, 10 questions | Full price every time | Write premium every time | One write, nine cheap reads |
| Total cost | $0.63 | $0.78 | $0.18 |
| Wait before any text, question 1 | About 9 s | About 9 s | About 2 to 3 s (streamed, cache still empty) |
| Wait before any text, questions 2 to 10 | About 9 s | About 9 s | About 1 to 2 s (cached prefix, streamed) |

The firm also has a response cache for questions about its own standard templates ("What is the notice period in our standard NDA?"). It is keyed by the firm's id, the template version and the prompt version, so firm A's template answers never reach firm B. Answers about an uploaded contract are not response-cached at all: each contract belongs to one matter with its own access list.

To speed up the first question too, the team pre-warms the cache with `max_tokens` set to 0 when a contract finishes uploading, while the lawyer is still typing.

## Common mistakes

- **Something variable at the top of the prompt.** A date, a request id or a user name breaks every cache read. Detect it: `cache_read_input_tokens` stays at 0 on repeated calls.
- **The wrong lifetime for the traffic.** Gaps longer than the cache lifetime turn caching into a surcharge. Detect it: cache writes on most calls and few reads.
- **Response cache keys with no scope.** One user's order, salary or contract reaches another user. Detect it: a two-account test, run before launch and after every cache change.
- **Caching answers from changing data, with no expiry or version in the key.** Old prices and old rules keep being served. Detect it: answers that disagree with the source after an update.
- **Caching failures.** A timeout, a refusal or a reply cut off by `max_tokens` is stored and replayed to everyone. Store only replies that finished normally.
- **Firing parallel requests at a cold cache.** All of them pay full price. Detect it: a burst of cache writes in the same second.
- **Believing streaming makes generation faster.** It makes waiting feel shorter; cost and total time are unchanged.
- **Measuring averages only.** Report p50 and p95 for time to first token and total time, measured in the browser as well as on the server.

## When caching does not help

- **Every request is different**, with no long shared prefix and few repeated questions.
- **Traffic is low and spread out**, so cached prefixes expire before the next request, even at 1 hour.
- **The shared part is short**, below the minimum cacheable length.
- **Answers must be fresh every time**, such as live prices or stock levels.
- **The slow part is elsewhere**: retrieval, a slow tool or your own server. Measure before optimising the model call.

## From demo to production

- **Log cache read and write tokens** on every call, and track the hit rate per feature.
- **Track time to first token and total time** at p50 and p95, by feature and model, from the browser.
- **Version cache keys** with the prompt, model and data, set expiries everywhere, and clear response caches on release or when source data changes.
- **Make scope a required part of every response cache key**, and keep the two-account test in your test suite.
