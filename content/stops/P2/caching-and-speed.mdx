## What it is

Three techniques cut cost and waiting time in LLM apps:

- **Prompt caching**: the provider stores the processed form of a long, unchanging beginning of a prompt (system prompt, a document, tool definitions), so later requests that start the same way are cheaper and faster.
- **Response caching**: your app stores answers and returns them directly when the same (or an equivalent) request comes again, skipping the model call entirely.
- **Streaming**: sending the reply to the user token by token as it is generated, so they start reading almost at once.

## How it works

**Prompt caching.** Providers charge less, often far less, for input tokens read from cache, and processing them is quicker. The cache works on an exact prefix: the request must start with the same content, in the same order. So:

- put stable content first: system prompt, tool definitions, long reference documents;
- put changing content last: the user's question, the latest conversation turns;
- avoid adding anything variable (a timestamp, a user name) at the top.

Caches expire after a period of no use; check your provider's rules on minimum length, lifetime and pricing.

**Response caching.** Store the answer keyed by the normalised request (and the prompt and model version). Good for repeated, identical questions: FAQ answers, product descriptions, translations of fixed text. Set expiry times, invalidate when underlying data changes, and never share cached answers across users when they contain personal or permission-dependent data. "Semantic caching" matches similar rather than identical questions; use it carefully, because near-identical questions can need different answers.

**Streaming.** Total generation time does not change, but users see the first words in well under a second instead of waiting for the full reply. Perceived speed improves enormously, and users can stop reading or cancel early. Handle errors and disconnections mid-stream.

**Other speed levers.** Shorter outputs (generation time grows with length); smaller models for simple steps; fewer sequential model calls; running independent calls in parallel; retrieving fewer, better chunks.

## A worked example

A Chennai legal-tech company's contract assistant answers questions about a 40-page agreement the lawyer uploads, typically 10 questions per contract.

Before: each question sent the full contract (about 30,000 tokens) plus the question. Each answer took 9 seconds and the input tokens were billed in full every time.

After:

- The contract and instructions come first and are cached; questions come last. From the second question on, most input tokens are read from cache at a fraction of the price and the first token arrives in about 2 seconds.
- Answers stream to the screen.
- Common questions about the firm's own standard template ("What is the notice period in our standard NDA?") are answered from a response cache keyed by template version.

Cost per contract session falls by about 70%, and lawyers stop complaining that the tool is slow.

## Common mistakes

- **Variable content at the start of the prompt.** It breaks the cache.
- **Caching answers that depend on the user or on changing data.**
- **No expiry or invalidation for response caches.**
- **Not streaming in chat interfaces.**
- **Assuming streaming makes generation faster.** It makes waiting feel shorter.

Read the prompt caching guide linked below, and the streaming guide.

1. Restructure one of your prompts so stable content comes first, enable caching, and compare token costs over five requests.
2. Add streaming to a chat interface and measure time to first token before and after.
3. Add a response cache with an expiry for one repeated question type.

**You are done when you can** explain what prompt caching saves, where the unchanging part must go, and why streaming helps even though total time is the same.
