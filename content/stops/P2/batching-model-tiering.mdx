## What it is

Two of the strongest cost levers for language-model systems:

- **Model tiering** (or routing): not every request needs the most capable model. Classify, extract or answer simple questions with a small, cheap, fast model; send only the hard ones to a large one.
- **Batching**: work that does not need an answer in seconds, such as nightly document tagging, summarising yesterday's tickets or re-embedding a corpus, goes through a **batch API**. Providers process batches within hours at a large discount, often around half the normal price.

Both depend on knowing your traffic: what share of requests is easy, and what share can wait.

```flow
Incoming work -> Can it wait hours?
Can it wait hours? -[yes]-> Batch API, discounted | results by id, rerun failures
Can it wait hours? -[no]-> Small model -> Validator passes?
Validator passes? -[yes]-> Answer
Validator passes? -[no, about 2.5%]-> Large model -> Answer
A hard task such as fit summaries -[directly]-> Large model
```

This lesson follows a resume-screening service at an HR-tech company in Pune processing 400,000 resumes a month.

## How it works

**Tiering patterns.**

- *Fixed by task*: each feature uses the cheapest model that passes its evals. Extraction from a standard form may need only a small model; drafting a legal summary may need a large one. This is the simplest and most common.
- *Cascade*: try the small model first; check its output (confidence, a validator, a self-reported "unsure"); escalate to the large model only when the check fails.
- *Router*: a classifier, or a small model, predicts difficulty and picks the model up front. Research systems such as RouteLLM learn this from preference data.

Every route needs its own eval. The real question is not "is the small model good?" but "is it good enough on the requests we send it?"

**Batching patterns.** Collect requests in a file (one JSON line per request with your own id), submit the batch, poll or get notified, then match results to ids. Design for partial failure: some items error and need resubmitting. Keep batch work idempotent so reruns are safe.

**Other cost levers worth combining.** Prompt caching for long, repeated prefixes; shorter prompts and outputs (ask for exactly the fields you need); fewer retrieved chunks after reranking; caching identical answers.

**Measure cost per successful task**, not just cost per call. A cheap model that fails half the time and needs a retry or a human may cost more overall.

**Routes for the resume pipeline:**

| Task | Route | Why | Evidence |
| --- | --- | --- | --- |
| Field extraction | Small model, escalate on validation failure | Small model nearly as accurate | 97% against 98% on 500 resumes |
| Fit summary | Large model | Small model clearly worse | Recruiter ratings |
| Bulk uploads | Batch API overnight | Needed by morning, not in seconds | Discounted price |
| Daytime uploads | Real time | Recruiters wait for them | Latency needs |

**Building a validator for a cascade.** The check decides what escalates, so it must catch bad outputs reliably. For extraction, validate against the JSON schema, check required fields are present and plausible (an email has an at sign, years of experience are between 0 and 50), and compare totals where possible. For free text, a cheap judge or a self-reported "unsure" can work, but test it: measure how many bad outputs it misses on a labelled set before trusting it.

**Running a batch job.** Write one line per request with your own id, submit, and record the batch id. When results arrive, match them by id, write successes, and collect failures into a new batch. Make every write idempotent, so rerunning a batch after a crash does not create duplicates.

**A cascade in code.** Small model first, a strict validator, the large model only when the check fails:

```python
import json
import anthropic
from pydantic import BaseModel, ValidationError

client = anthropic.Anthropic()
SMALL, LARGE = "claude-haiku-5-5", "claude-sonnet-5-5"     # check the docs for current names

class Resume(BaseModel):
    name: str
    years_experience: float
    skills: list[str]
    last_employer: str | None = None

def extract(model, text):
    r = client.messages.create(model=model, max_tokens=500,
        messages=[{"role": "user", "content": "Return only JSON with name, years_experience, skills, "
                   f"last_employer (null if absent).\n\n{text}"}])
    out = "".join(b.text for b in r.content if b.type == "text")
    return out, r.usage

def valid(raw, text):
    try:
        item = Resume.model_validate_json(raw)
    except ValidationError:
        return None
    if not 0 <= item.years_experience <= 50 or not item.skills:
        return None
    if item.name.split()[0].lower() not in text.lower():      # the name must appear in the resume
        return None
    return item

def cascade(text, stats):
    raw, usage = extract(SMALL, text)
    stats["small_calls"] += 1
    if (item := valid(raw, text)):
        return item
    stats["escalated"] += 1
    raw, usage = extract(LARGE, text)
    return valid(raw, text)            # None goes to a person
```

Track the escalation rate. If it climbs, the small model is struggling with a new kind of input, and the savings are shrinking.

**Batch requests with Anthropic's Message Batches API.** Submit non-urgent work in one go and collect results by your own ids:

```python
import time

def run_batch(items):
    batch = client.messages.batches.create(requests=[
        {"custom_id": it["id"],
         "params": {"model": SMALL, "max_tokens": 500,
                    "messages": [{"role": "user", "content": f"Return only JSON ...\n\n{it['text']}"}]}}
        for it in items])
    while client.messages.batches.retrieve(batch.id).processing_status != "ended":
        time.sleep(60)
    done, failed = {}, []
    for result in client.messages.batches.results(batch.id):
        if result.result.type == "succeeded":
            msg = result.result.message
            done[result.custom_id] = "".join(b.text for b in msg.content if b.type == "text")
        else:
            failed.append(result.custom_id)
    return done, failed            # resubmit `failed`, or send them to the real-time path
```

Batch processing is priced lower than normal calls and can take up to a day; check the current price and turnaround, with the date. Validate batch outputs exactly as you would real-time ones.

**Cost per successful task, measured.** Over a sample of 200 items, record for each path the model calls made, tokens, cost and whether the final result was correct. Then compare:

Pick the cheapest path that meets the accuracy bar for that task.

## A worked example

A Pune HR-tech company screens resumes for its clients. Each resume gets structured extraction (name, skills, experience) and a fit summary against the job description. Volume: 400,000 resumes a month, mostly uploaded in bulk the evening before a hiring drive.

Before: every resume went through a large model in real time. Monthly model spend: about ₹14 lakh.

The redesign:

1. Extraction moves to a small model with a strict JSON schema. On a golden set of 500 resumes, field accuracy is 97% against 98% for the large model; validation failures (2.5%) escalate to the large model.
2. The fit summary stays on the large model, where the small one scored clearly worse in recruiter ratings.
3. Bulk uploads go through the batch API overnight, at a discount. Only resumes added during the working day run in real time.
4. The job description, identical for thousands of resumes, sits at the start of the prompt and is cached.

Monthly spend falls to about ₹5 lakh. Recruiter ratings of the summaries are unchanged, and you report both numbers side by side in the monthly review.

| Measure | Before | After |
| --- | --- | --- |
| Monthly model spend | About ₹14 lakh | About ₹5 lakh |
| Extraction field accuracy | 98% | 97% plus escalation |
| Recruiter rating of summaries | Baseline | Unchanged |

## Common mistakes

- **Choosing the small model by vibe.** Run the evals for each route; cheap and wrong is expensive.
- **Batching user-facing work.** Batches can take hours. Only batch what can wait.
- **No escalation path.** A cascade without a reliable failure check sends bad answers onwards.
- **Ignoring retries in the maths.** Count cost per successful task.
- **Forgetting partial batch failures.** Some items always fail; plan the rerun.
- **A weak validator** that passes bad small-model outputs, so the cascade saves money by losing quality.
- **Ignoring failed batch items**, which silently go missing.
- **Comparing cost per call** instead of cost per successful task.

## When tiering and batching are not worth it

- **Low volume**: the savings are smaller than the engineering time.
- **Every request is urgent**, so batching does not fit.
- **The small model fails your evals** on the traffic you would send it.
- **There is no reliable validator** for the cascade to escalate on.

## From demo to production

- **Track escalation rate and cost per successful task** per feature.
- **Re-evaluate routes** on every model or prompt change.
- **Handle batch failures** by id, with retries and a report.
- **Keep urgent and batch work on separate limits** so overnight jobs never slow daytime users.
- **Record prices with dates** in the cost comparison.
