## What it is

**Total cost of ownership (TCO)** is everything a system costs over a period, usually one to three years, not just the model bill. Its job is to let you compare options fairly and give the client an honest budget.

| Cost line | What goes in it | What people forget |
|---|---|---|
| Model | Tokens through an API, or GPUs (rented or bought) if self-hosted | Hidden reasoning tokens; GPUs billed while idle |
| Infrastructure | App compute, databases, vector store, storage, gateways, monitoring | Log and trace storage, staging environments |
| People | Build, operate, on-call, evaluations, upgrades | The second engineer you need for on-call cover |
| Data | Connectors, pipelines, golden sets, document clean-up | Re-embedding when the embedding model changes |
| Compliance | Audits, penetration tests, security and legal reviews | Repeat reviews after each major change |
| Change | Model upgrades, prompt rework when a provider retires a model | Re-running evals on every new model |
| India-specific | GST on cloud and API bills, exchange rate on dollar prices | Whether GST is a real cost or can be claimed back |

```flow
dir: LR
title: From measured usage to a decision
Measured usage | traces and load tests -> API option | tokens, infra, people
Measured usage -> Self-hosted option | GPUs at real utilisation, infra, people
API option -> Sensitivity and crossover
Self-hosted option -> Sensitivity and crossover
Sensitivity and crossover -> Cost per claim against value per claim
```

This lesson follows an insurance company in Kolkata planning a claims-document assistant for 2,000 staff.

## How it works

### Start from measured usage

Collect users, requests per user per day, peak against average, and growth over the year. Then measure, from traces, three things people usually guess:

- **Calls per user action.** An agent or a retrieval pipeline may make three to six model calls for one question: rewrite the query, retrieve, answer, check. Cost is per call, not per question.
- **Input tokens per call.** Retrieved passages often make input several times larger than the user's question.
- **Output tokens per call, including reasoning.** Reasoning models think before they answer. That thinking is hidden but billed as output tokens (OpenAI's documentation says so explicitly). A short visible answer can carry a long invisible bill.

### The API option

Cost per call = input tokens × input price + output tokens × output price. Then apply three adjustments:

- **Prompt caching.** A fixed system prompt or shared document prefix, re-read on every call, is billed at a fraction of the normal input price by providers that offer caching.
- **Batch discounts** for work that can wait hours, such as overnight summaries.
- **Tiering.** Send simple requests (lookups, classification) to a cheaper, smaller model and keep the larger model for hard ones.

Most API prices are in US dollars, so the rupee rate is an input too. Read prices from the provider's page and an independent comparison such as Artificial Analysis, and write the check date next to every one.

### The self-hosted option

GPUs must be sized for the **peak** with a spare, from a load test on your own prompts at your latency target. You then pay for them every hour of the month, busy or not. The number that decides the case is **utilisation**:

utilisation = requests served ÷ requests the fleet could serve in the month

An office tool used nine hours a day on working days, sized for a month-end peak, often runs at 10% or less. At 10% utilisation each request carries ten times the GPU cost it would at full use.

Two pricing choices matter:

- **On-demand** GPUs cost the most per hour but can be released.
- **Reserved** GPUs (a one- or three-year commitment) cost less per hour, but you pay even if usage falls or API prices drop.

Add the people to run the serving stack, patch it, upgrade models and carry the pager, and the quality gap if the open model scores lower on your evals.

### India-specific lines

- **GST.** Cloud and API services generally attract 18% GST (the usual rate for IT and cloud services as of November 2026). A GST-registered business buying from a foreign provider usually pays it under reverse charge and may claim it back as input tax credit. An organisation that cannot claim credit pays it as real cost. Ask the client's finance team which case applies; the figures in this lesson are before GST.
- **Exchange rate.** A dollar-priced API bill rises when the rupee falls. In mid-November 2026 the rupee moved from about ₹94.2 to about ₹93.5 to the dollar within a week, and a move to ₹100 adds about 7% to the model line. Put the rate in the sensitivity table.
- **Region.** Data rules may require an Indian cloud region. Check that the model or GPU type you priced is offered there, at that region's price.

### Sensitivity and the crossover

Recompute both options while changing one assumption at a time: usage halved and doubled, outputs twice as long, API prices 30% lower, a weaker rupee, a lower GPU throughput from the load test. A decision that only holds at one exact number is fragile.

The **crossover** is the usage above which the other option stays cheaper. Two traps:

- **Steps.** GPUs come in whole units, so the self-hosted line jumps each time you add one. A spreadsheet can show self-hosting winning at one volume and losing just above it. Report the volume above which it keeps winning.
- **Thin margins.** If the API and the GPU cost almost the same per extra request, the crossover swings wildly with small changes. Say so.

### Price trends

API prices for a given level of quality have fallen fast. Epoch AI estimated in March 2025 that the per-token price of models reaching a fixed benchmark score fell between 9 and 900 times a year, depending on which performance level was measured. Those are prices per token, and reasoning models can use many more tokens per task. A three-year GPU commitment bets against this trend, so test it with a "prices 30% lower" row.

### A cost model you can rerun

Keep every assumption in one place, with the date it was checked. Every number below is illustrative, chosen to match the worked example:

```python
import math

# Every number is illustrative. Replace each with your own dated quote or measurement.
P = {"rate_date": "2026-11-19", "usd_to_inr": 93.5,        # rupees per US dollar, about mid-November 2026
     "in_per_m": 3.0, "out_per_m": 15.0,                    # USD per million tokens, a mid-tier API model
     "cache_ratio": 0.1,                                    # cached input billed at 10% of the input price
     "gpu_month": 250_000,                                  # one rented GPU, on demand, all 730 hours
     "gpu_rps": 1.2,                                        # requests per second per GPU, from YOUR load test
     "engineer_month": 200_000,                             # loaded monthly cost of one engineer
     "busy_seconds": 22 * 9 * 3600,                         # 22 working days of 9 busy hours
     "peak_factor": 2.0}                                    # month-end peak against the busy-hour average

def api_month(req, p=P, in_tok=3000, out_tok=300, cached=0.4, small_share=0.4, small_ratio=0.25):
    in_usd = in_tok * (1 - cached + cached * p["cache_ratio"]) * p["in_per_m"] / 1e6
    per_req = (in_usd + out_tok * p["out_per_m"] / 1e6) * (1 - small_share + small_share * small_ratio)
    return req * per_req * p["usd_to_inr"] + 120_000 + 0.3 * p["engineer_month"]   # + infra + 0.3 engineer

def gpus(req, p=P):
    peak_rps = req / p["busy_seconds"] * p["peak_factor"]
    return math.ceil(peak_rps / p["gpu_rps"]) + 1                                   # + one spare

def self_month(req, p=P):
    return gpus(req, p) * p["gpu_month"] + 150_000 + 1.5 * p["engineer_month"]       # + infra + 1.5 engineers

def utilisation(req, p=P):
    return req / (gpus(req, p) * p["gpu_rps"] * 730 * 3600)

def crossover(p=P, limit=30_000_000, step=100_000):
    """Volume above which self-hosting stays cheaper, or None if it never does up to the limit."""
    last_api_win = 0
    for r in range(step, limit + 1, step):
        if self_month(r, p) >= api_month(r, p):
            last_api_win = r
    return None if last_api_win == limit else last_api_win + step

base = 1_100_000
print(f"Illustrative prices, rupee rate of {P['rate_date']}")
print(f"measured: API ₹{api_month(base)/1e5:.1f} lakh, self-hosted ₹{self_month(base)/1e5:.1f} lakh, "
      f"{gpus(base)} GPUs at {utilisation(base):.0%} utilisation")
scenarios = {"as measured": {}, "reserved GPUs at ₹1.6 lakh": {"gpu_month": 160_000},
             "load test gives 1.0 req/s": {"gpu_rps": 1.0}, "API prices 30% lower": {"in_per_m": 2.1, "out_per_m": 10.5},
             "rupee at ₹100": {"usd_to_inr": 100},
             "reserved, API 30% lower": {"gpu_month": 160_000, "in_per_m": 2.1, "out_per_m": 10.5}}
for name, change in scenarios.items():
    p = {**P, **change}
    c = crossover(p)
    print(f"{name:<27} API ₹{api_month(base, p)/1e5:4.1f} lakh  self ₹{self_month(base, p)/1e5:4.1f} lakh  "
          f"crossover {'none below 30M' if c is None else f'{c/1e6:.1f}M'}")
```

It prints:

```text

measured: API ₹9.2 lakh, self-hosted ₹14.5 lakh, 4 GPUs at 9% utilisation
as measured                 API ₹ 9.2 lakh  self ₹14.5 lakh  crossover 8.3M
reserved GPUs at ₹1.6 lakh  API ₹ 9.2 lakh  self ₹10.9 lakh  crossover 1.9M
load test gives 1.0 req/s   API ₹ 9.2 lakh  self ₹17.0 lakh  crossover none below 30M
API prices 30% lower        API ₹ 7.0 lakh  self ₹14.5 lakh  crossover none below 30M
rupee at ₹100               API ₹ 9.7 lakh  self ₹14.5 lakh  crossover 5.3M
reserved, API 30% lower     API ₹ 7.0 lakh  self ₹10.9 lakh  crossover 6.1M
```

The model keeps people and infrastructure fixed as volume grows, which flatters self-hosting at high volume: a fleet of fifteen GPUs needs more than one and a half engineers. Swap in the client's traces, load test and quotes before you show anyone a number.

## A worked example

A Kolkata insurance company plans to roll out a claims-document assistant to 2,000 staff. Measured in the pilot: 25 requests per user per working day over 22 working days, 3,000 input tokens (mostly retrieved passages) and 300 output tokens per request, one model call per request. That is 2,000 × 25 × 22 = 1.1 million requests a month. Month-end traffic is twice the normal busy-hour rate. All prices are the illustrative ones in the code.

**Option A, API through their cloud.** Per request: 3,000 × $3 ÷ 1,000,000 + 300 × $15 ÷ 1,000,000 = $0.0135, about ₹1.26 at ₹93.5. At 1.1 million requests that is about ₹13.9 lakh a month. Caching the fixed system prompt and instructions (40% of input tokens) brings it to about ₹10.6 lakh. Sending 40% of requests, the simple lookups, to a model at a quarter of the price brings it to about ₹7.4 lakh, or ₹0.67 per request. Add ₹1.2 lakh of infrastructure and 30% of one engineer: about **₹9.2 lakh a month**.

**Option B, self-hosted open model.** The load test shows one GPU serves 1.2 requests per second at the latency target. The month-end peak is about 3.1 requests per second, so three GPUs plus one spare: four at ₹2.5 lakh, ₹10 lakh. Add ₹1.5 lakh of infrastructure and one and a half engineers for serving, upgrades and on-call, ₹3 lakh: about **₹14.5 lakh a month**. Evals show 2 points lower accuracy. The fleet runs at 9% utilisation, because it is sized for month-end and paid for every night and weekend.

| Per month (illustrative) | Option A: API | Option B: self-hosted |
| --- | --- | --- |
| Model | About ₹7.4 lakh after caching and tiering | ₹10 lakh for four GPUs at 9% utilisation |
| Infrastructure | ₹1.2 lakh | ₹1.5 lakh |
| People | 0.3 engineer, ₹0.6 lakh | 1.5 engineers, ₹3 lakh |
| Quality on evals | Baseline | 2 points lower |
| Total per month | About ₹9.2 lakh | About ₹14.5 lakh |
| Total per year | About ₹1.1 crore | About ₹1.74 crore |

**Where is the crossover?** Each extra request costs about ₹0.67 on the API. On a GPU sized for twice the average, it costs about ₹0.58. The gap is only nine paise, so self-hosting needs a very large volume to pay back its spare GPU and extra engineers. On demand, it keeps winning only above about 8.3 million requests a month, seven to eight times today's volume. With reserved GPUs at ₹1.6 lakh, it drops to about 1.9 million: close. But if the load test had shown 1.0 request per second instead of 1.2, or API prices fell 30%, there would be no on-demand crossover at all. That fragility is the finding.

**Decision.** Choose A. Write two review triggers into the plan: when monthly volume passes 1.5 million, get a reserved GPU quote and rerun the load test; and whenever the API price, the rupee rate or a data rule changes, rerun the model. Note in the recommendation that a one-year reservation locks in cost while API prices tend to fall; with API prices 30% lower, the reserved crossover moves out to about 6.1 million.

**Value side.** The pilot showed 9 minutes saved per claim on 40,000 claims a month, about 6,000 staff hours. At an illustrative loaded staff cost of ₹400 an hour, that is ₹60 of time per claim against about ₹23 of AI cost per claim (₹9.2 lakh ÷ 40,000). That ratio, not the token bill, is what the leadership team will remember.

## Common mistakes

- **Comparing token price with GPU rent.** Count every line on both sides: people, infrastructure, evals, change. People are the line most often missing, on both options.
- **Guessing usage.** Measure calls per user action and tokens per call from traces, including retrieved context and hidden reasoning tokens.
- **Sizing for the average, or assuming full utilisation.** GPUs cover the peak and bill all month. Put utilisation in the model.
- **Trusting the first crossover.** Whole-GPU steps make the lines cross and uncross. Report the stable point and how far it moves.
- **Reserving GPUs without a price-fall row.** A long commitment can age badly as API prices drop.
- **Ignoring rupee and GST.** A dollar bill moves with the exchange rate, and GST is real cost if it cannot be claimed back.
- **Prices with no date.** They go quietly wrong within months.
- **No value side.** A cost model without the hours or errors saved cannot justify anything.

## When a detailed cost model is not needed

- **A pilot under a small, fixed budget**: a spend cap and a weekly look at the bill are enough.
- **No real alternative**, such as data rules forcing on-premises hosting: model the cost for budgeting, not choosing.
- **Tiny usage**, where the cost is a rounding error next to the value.

## From demo to production

- **Keep the cost model in the repository**, with dated prices, the rupee rate and measured usage.
- **Reconcile it monthly** with traces and the real bill, and explain each difference.
- **Track cost per unit of work** next to value per unit, on the same dashboard.
- **Rerun the crossover** when usage, prices, the rupee, models or load-test results change.
- **Set budget alerts** on the API account, so a runaway agent loop shows up in hours, not at month end.
