## What it is

**Total cost of ownership (TCO)** is everything a system costs over a period, usually one to three years, not just the model bill. For an AI system:

- **Model costs**: tokens on an API, or GPUs (bought or rented) for self-hosting.
- **Infrastructure**: compute for the app, databases, vector stores, storage, networking, monitoring, gateways.
- **People**: building, operating, on-call, evaluating, upgrading. Often the largest item.
- **Data work**: connectors, pipelines, labelling golden sets, document clean-up.
- **Compliance and security**: audits, penetration tests, reviews.
- **Change**: model upgrades, re-embedding, prompt rework when providers deprecate models.

The point is a fair comparison between options and an honest budget for the client.

```text
   TOTAL COST OF OWNERSHIP (per year)
   +--------------------------------------------------------------+
   | model        tokens (API)  or  GPUs running all month (self)  |
   | infra        app compute, databases, vector store, monitoring |
   | people       build, operate, on-call, evals, upgrades   <-- often biggest
   | data         connectors, pipelines, golden sets, clean-up     |
   | compliance   audits, pen tests, reviews                       |
   | change       model upgrades, re-embedding, prompt rework      |
   +--------------------------------------------------------------+
   compare options on the same usage  -->  cost per claim vs value per claim
```

This lesson follows an insurance company in Kolkata planning a claims-document assistant for 2,000 staff.

## How it works

**Start from usage.** Users, requests per user per day, input and output tokens per request (measured from traces, not guessed), growth over the year, and peak versus average.

**API option.** Cost per request = input tokens times input price + output tokens times output price, adjusted for caching discounts, batch discounts and model tiering. Multiply by monthly requests. Use current price lists and independent comparisons; prices change often, usually downwards.

**Self-hosted option.** GPUs needed for peak load with headroom (from load tests), times hourly price or amortised purchase, running all month whether busy or not. Add engineering time to operate, monitor and upgrade, and the quality gap if the open model is weaker.

**Sensitivity.** Show how cost moves if usage is half or double the estimate, if output length grows, or if prices fall 30%. Decisions that only make sense at one exact usage level are fragile.

**Unit economics.** Express the result per unit the client cares about: cost per resolved ticket, per claim processed, per employee per month. Compare with the value: hours saved, faster processing, fewer errors.

**The comparison on one page (illustrative figures):**

| Item per month | Option A: API through their cloud | Option B: self-hosted open model |
| --- | --- | --- |
| Model | About ₹6.5 lakh after caching and tiering | About ₹10 lakh for four GPUs |
| Infrastructure | About ₹1.2 lakh | About ₹1.5 lakh |
| People | A fraction of one engineer | About 1.5 engineers, about ₹3 lakh |
| Quality on evals | Baseline | 2 points lower |
| Year total | About ₹1 crore | About ₹1.75 crore |

**Sensitivity in practice.** Recompute both options at half and double the measured usage, with outputs twice as long, and with API prices 30% lower. Write down the crossover point, the usage at which self-hosting would become cheaper. Here it is roughly three times current volume. That single number turns a debate into a review trigger: "revisit if monthly requests pass 3 million".

**The value side.** Cost alone cannot justify a system. Pair it with value from the pilot: minutes saved per task times tasks per month, errors avoided, faster turnaround for customers. Put cost and value per unit side by side, so leaders can see the margin, not just the bill.

## A worked example

A Kolkata insurance company plans to roll out a claims-document assistant to 2,000 staff. Measured in the pilot: 25 requests per user per working day, 3,000 input tokens (mostly retrieved passages) and 300 output tokens per request. That is about 1.1 million requests a month.

**Option A, API through their cloud.** At an illustrative ₹0.25 per 1,000 input tokens and ₹1.00 per 1,000 output tokens: (3 × 0.25) + (0.3 × 1.00) = ₹1.05 per request, about ₹11.5 lakh a month. Prompt caching on the fixed system prompt and tiering simple lookups to a smaller model bring it to about ₹6.5 lakh. Infrastructure ₹1.2 lakh. One engineer at a fraction of their time for operations.

**Option B, self-hosted open model.** Load tests show three GPUs for peak load plus one spare, at an illustrative ₹2.5 lakh per GPU per month: ₹10 lakh. Infrastructure ₹1.5 lakh. Plus about one and a half engineers to run the serving stack, about ₹3 lakh a month. Evals show 2 points lower accuracy.

Over a year, A costs about ₹1 crore and B about ₹1.75 crore. B only wins if usage triples or if data rules require it. The client chooses A, with a review if volume passes 3 million requests a month. Value side: the pilot showed 9 minutes saved per claim on 40,000 claims a month, about 6,000 staff hours, comfortably above the cost.

## Common mistakes

- **Counting only tokens or only GPUs.** People and change costs often dominate.
- **Guessing token counts.** Measure from real traces; retrieved context inflates input tokens.
- **Sizing for the average.** Self-hosted capacity must cover peaks; APIs absorb them.
- **Ignoring price trends.** API prices have fallen steadily; three-year GPU commitments may not age well.
- **No value side.** A cost model without the hours or errors saved cannot justify anything.
