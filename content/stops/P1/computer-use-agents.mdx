## What it is

A **computer-use agent** works with software through its screen: it receives screenshots, decides where to click and what to type, and repeats. A **browser agent** does the same inside a web browser, sometimes reading the page's structure as well as its picture.

They fill a real gap. When a system has an API, call the API. When it does not, as with many government portals, insurer and bank portals, and older desktop applications, screen control may be the only way to automate it without a human.

```text
   THE LADDER (use the highest rung that works)
   [1] API                         fastest, cheapest, most reliable
   [2] scripted browser tool       Playwright: fixed steps, exposed as one tool
   [3] agent-driven browsing       reads page structure, decides actions
   [4] full computer use           screenshot -> decide -> click/type -> screenshot ...
                                   slowest, costliest, least reliable

   SAFETY BOX for rungs 3 and 4
   isolated VM | dedicated account | site allow-list | approval before submit/pay/delete
   | screenshots recorded | captchas and OTPs go to a person
```

This lesson follows a chartered accountancy firm in Pune that spent hours every month downloading clients' tax documents by hand.

## How it works

**A ladder of options, from most to least reliable:**

1. **An API**, if one exists or can be requested.
2. **Scripted browser automation** with a library such as Playwright: fixed steps written by you, exposed to the agent as a tool ("download_gst_return(gstin, period)"). Fast, cheap and predictable.
3. **Agent-driven browsing**: the agent reads the page structure and decides actions, for sites that vary.
4. **Full computer use** from screenshots, for desktop apps and the hardest cases. Slowest, most expensive and least reliable.

Use the highest rung that works, and combine them: scripted tools for the known steps, agent control only where pages are unpredictable.

**The loop.** Screenshot, decide an action (click at a point, type, scroll, press a key), act, screenshot again. Each step is a model call with an image, so long tasks take minutes and cost real money.

**Safety.**

- Run in an isolated virtual machine or container with only the apps and accounts needed.
- Restrict which websites can be reached.
- Never give it general credentials; use a dedicated account with the least permission.
- Treat everything on screen as untrusted: web pages can contain instructions aimed at agents.
- Require human approval before submitting forms, paying, sending or deleting.
- Record screenshots or video of every session for audit.

**Reliability.** Pages change, pop-ups appear, sessions expire, captchas block bots. Expect failures, detect them (the expected confirmation did not appear) and hand back to a person.

**Rungs compared:**

| Rung | Speed per action | Cost | Breaks when | Best for |
| --- | --- | --- | --- | --- |
| API | Milliseconds | Lowest | The API changes, rarely | Anything with an API |
| Scripted tool | Under a second | Low | Page layout changes; fails loudly | Stable portals |
| Agent browsing | Seconds | Medium | Unusual pages, pop-ups | Varying sites |
| Computer use | Tens of seconds | Highest | Many things | Desktop apps, last resort |

**Detecting failure.** Every automated step should know what success looks like: a confirmation message, a downloaded file of the expected size, a new row in a list. Check for it after each important action. When it is missing, stop rather than guess, save the last screenshot and the steps so far, and hand the task to a person with a clear note. A silent wrong action in a tax or banking portal costs far more than a stopped task.

**Measuring the value.** Track hours saved, success rate per step, average time per action and the number of hand-backs. Hand-backs are not failures of the project; they are the system working as designed. If they cluster on one page, that page is a candidate for a scripted tool instead.

## A worked example

A Pune chartered accountancy firm spends hours each month downloading clients' tax documents from a government portal and an older accounting desktop app with no API.

The design:

- For the portal, a scripted Playwright tool logs in with the client-authorised credentials from a vault, navigates to known pages and downloads the files. The agent calls the tool; it does not browse freely. When the portal's layout changes, the script fails loudly and an engineer fixes it.
- For the desktop accounting app, a computer-use agent runs in a Windows virtual machine with no internet access except the file share. It exports ledgers by following the app's menus. Before saving over any file it asks a staff member to approve.
- Captchas and one-time passwords go to a person by design.

Results: the monthly download work for 120 clients falls from about 60 staff hours to 12, mostly approvals and exceptions. Computer-use steps average 40 seconds per action and succeed 91% of the time; failures are handed back with the last screenshot.

| Measure | Before | After |
| --- | --- | --- |
| Staff hours per month, 120 clients | About 60 | About 12, mostly approvals and exceptions |
| Computer-use time per action | Not applicable | About 40 seconds |
| Computer-use success rate | Not applicable | 91%, failures handed back with a screenshot |

## Common mistakes

- **Screen control where an API or a script would do.** It is slower, costlier and flakier.
- **Running on a real desktop with real logins.** Use an isolated machine and a dedicated account.
- **Trusting on-screen text.** Pages can carry injected instructions.
- **No human before irreversible actions.** Submissions and payments need approval.
- **Trying to beat captchas.** Respect them; hand the step to a person.

## Practise

Read the computer-use tool docs and Playwright's getting-started page.

1. Script a browser task on a public site with Playwright (for example, fetch the latest notices from a government website) and expose it to an agent as one tool.
2. Run a browser or computer-use agent in a container on a harmless task, with screenshots saved for every step.
3. Add an approval step before any form submission, and test with a page containing a hidden instruction.

**You are done when you can** explain which rung of the ladder you used for each step and why.
