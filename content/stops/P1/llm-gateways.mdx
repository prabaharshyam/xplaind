## What it is

An **LLM gateway** is a service that sits between your applications and the model providers. Applications call the gateway with one API format; the gateway forwards each request to the right provider and model, and handles the cross-cutting concerns once:

- **Routing**: which model and provider serve this request.
- **Fallbacks**: what to try when a provider errors, times out or rate-limits.
- **Keys and access**: teams get gateway keys; the real provider keys live only in the gateway.
- **Limits and budgets**: per team, per key, per user.
- **Logging and cost**: every request, its tokens and its cost, in one place.
- **Caching**: optional reuse of identical requests.

Open-source options such as LiteLLM, commercial gateways, and the cloud providers' API management services all fill this role.

```flow
Chatbot -[key A]-> Gateway, 2 instances
Extraction -[key B]-> Gateway, 2 instances
Summariser -[key C]-> Gateway, 2 instances
Search -[key D]-> Gateway, 2 instances
Gateway, 2 instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails]-> Fallback 1: model X, second region
Fallback 1: model X, second region -[fails]-> Fallback 2: approved model Y, provider 2
```

The gateway adds budgets per key with alerts at 75%, retries and timeouts, and masked logs (team, feature, model, tokens, cost, latency). The provider keys live only here, in a secret store, and are rotated.

This lesson follows a fintech in Bengaluru where five AI features from four teams each called providers directly.

## How it works

**One interface.** Most gateways accept an OpenAI-compatible or similar request format and translate it for each provider, so switching a feature from one model to another is a configuration change, not a code change.

**Routing rules.** Route by model alias (`summariser-default` points to a specific model you can change centrally), by team, by region (send Indian user data only to Indian-region endpoints) or by request features. Smarter routers send easy requests to cheap models; the next lesson covers this.

**Fallbacks.** A chain such as: primary model in the Mumbai region; on timeout or 5xx, the same model in another region; on failure again, a different provider's comparable model. Fallbacks need care: the fallback model must be good enough for the task and allowed under the data rules.

**Retries and timeouts.** The gateway retries with backoff on 429s and transient errors, and enforces timeouts, so every application does not reimplement it.

**Budgets.** Each key carries a monthly or daily budget; requests past it are refused or downgraded. Alerts fire at thresholds.

**The cost of a gateway.** It is one more service to run, secure and keep available; if it goes down, every AI feature does. Run it with at least two instances, health checks and its own monitoring.

**Gateway features and the problems they solve:**

| Feature | Problem it solves |
| --- | --- |
| One request format | Each team writing code for each provider |
| Model aliases | Model names hard-coded in many apps |
| Fallbacks | One provider outage taking a feature down |
| Central keys | Provider keys scattered across teams and laptops |
| Budgets per key | One feature quietly using most of the spend |
| Unified logs | No view of cost, latency or errors across features |
| Caching | Paying again for identical requests |

**Testing fallbacks.** A fallback that has never fired may not work. In staging, break the primary on purpose, with a wrong key or a blocked endpoint, and check that requests succeed through the next option, that latency stays acceptable, and that logs record which model actually served each request. Repeat after every change to the chain. Also run the feature's evals against each fallback model, so you know what quality users get during an outage.

**Rolling out a gateway.** Move one low-risk feature first, compare its errors, latency and cost with before, then migrate the others one at a time. Keep each team's old direct keys working for a short overlap, then revoke them, so the gateway becomes the only path to providers.

**A gateway configuration.** LiteLLM's proxy is a common open-source choice; other gateways follow the same ideas. One file defines aliases, real models, fallbacks and the admin key:

```yaml
# litellm-config.yaml
model_list:
  - model_name: chat-default                 # the alias apps use
    litellm_params:
      model: anthropic/claude-sonnet-5-5     # check the docs for current names
      api_key: os.environ/ANTHROPIC_API_KEY
      timeout: 30
  - model_name: chat-backup
    litellm_params:
      model: bedrock/<model id from your Bedrock console>
      aws_region_name: ap-south-1
  - model_name: fast
    litellm_params:
      model: anthropic/claude-haiku-5-5

litellm_settings:
  num_retries: 2
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/GATEWAY_DB_URL     # stores keys, budgets and spend
```

Run it with two or more instances behind a load balancer: `litellm --config litellm-config.yaml --port 4000`.

**Apps call the alias, not the provider.** Any OpenAI-compatible client works:

```python
import os
from openai import OpenAI

client = OpenAI(base_url="https://gateway.internal.example.in", api_key=os.environ["TEAM_CLAIMS_KEY"])
reply = client.chat.completions.create(model="chat-default",
                                       messages=[{"role": "user", "content": "Summarise this claim: ..."}])
```

Switching every app to a new model is now one line in the gateway config, reviewed like code and tested on the golden set first.

**Keys with budgets per team.** The admin creates a virtual key for each feature:

```bash
curl -s https://gateway.internal.example.in/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"models": ["chat-default", "fast"], "max_budget": 50, "budget_duration": "30d",
       "metadata": {"team": "claims", "owner": "platform-lead"}}'
```

The team never sees the provider keys; revoking their virtual key cuts them off without rotating anything else. Budgets are in the gateway's currency setting (often US dollars), so convert and note the rate.

**Region-aware routing.** For Indian personal data, point the aliases used by those features only at Indian-region endpoints, and keep a separate alias for features allowed to use other regions. Log the region of every call so an audit can confirm the rule held.

**The gateway is critical infrastructure.** Monitor its own latency (it should add only milliseconds), error rate and database health, keep it close to your apps, and have a documented emergency path, such as a feature flag that sends one critical feature directly to its provider.

**Try it in your browser.** A gateway's fallback chain, simulated: when the primary fails, the next model answers.

```python
import random

random.seed(5)
def call(model):
    if model == "primary" and random.random() < 0.3:
        raise TimeoutError("primary timed out")
    return f"answer from {model}"

def gateway(chain=("primary", "backup")):
    for model in chain:
        try:
            return call(model)
        except TimeoutError as err:
            print("  fell back:", err)
    return "all models failed"

for i in range(5):
    print(i, gateway())
```

## A worked example

A Bengaluru fintech has five AI features built by four teams. Each team has its own provider keys; finance sees one big monthly bill. A provider outage last month took down the customer chatbot for 50 minutes.

You deploy a gateway with two instances on their Kubernetes cluster:

- Every team gets a gateway key tagged with team and feature; provider keys are moved into the gateway's secret store and rotated.
- Model aliases: `chat-default`, `extract-default`, `embed-default`, each pointing to a specific model, so upgrades happen centrally after evals pass.
- Fallbacks for `chat-default`: same model in a second region, then a comparable model from a second provider approved by the compliance team.
- Budgets: each feature has a monthly cap and an alert at 75%.
- Logs: every request with team, feature, model, tokens, cost and latency go to their analytics store.

The next provider incident causes 90 seconds of slower responses while the fallback takes over, instead of 50 minutes of errors. Finance gets a monthly cost report by feature for the first time, and it shows that one internal summarisation job uses 40% of spend. That team moves it to a batch job and a cheaper model.

| Measure | Before the gateway | After |
| --- | --- | --- |
| Effect of a provider incident | 50 minutes of chatbot errors | 90 seconds of slower responses |
| Provider keys | Held by four teams | Only in the gateway, rotated |
| Cost visibility | One monthly bill | Report by team and feature |
| Biggest finding | Unknown | A summary job using 40% of spend, moved to batch and a cheaper model |

## Common mistakes

- **A single gateway instance.** You have created a new single point of failure. Run several.
- **Fallbacks to unapproved models or regions.** An outage should not silently send data somewhere it is not allowed to go.
- **Model names hard-coded in apps.** Use aliases so upgrades and swaps are central.
- **No per-feature attribution.** Cost reports by provider alone do not tell you what to fix.
- **Gateway logs with full prompts and no masking.** The gateway becomes the biggest sensitive data store you have.
- **A single gateway instance** that takes every AI feature down when it fails.
- **Untested fallbacks**, which break output formats or quality when they first fire.
- **Model names in application code** instead of gateway aliases.

## When a gateway is overkill

- **One app with one provider**: the provider SDK with retries and a budget alert is enough.
- **A small team** that would spend more time running the gateway than it saves.
- **A managed platform** that already provides keys, budgets and routing.

A gateway pays off once several teams or apps share providers, keys and budgets.

## From demo to production

- **Run at least two instances** with health checks and their own monitoring.
- **Keep the config in Git**, reviewed, and tested on the golden set for model changes.
- **Issue virtual keys** per team with budgets and owners.
- **Route personal data to approved regions only**, and log regions.
- **Drill fallbacks** by breaking the primary in staging.
