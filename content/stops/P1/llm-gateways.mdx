## What it is

An **LLM gateway** is one service between your applications and the model providers. Applications send every request to the gateway in one API format. The gateway forwards it to the right provider and model, and handles the shared work once, instead of in every app:

- **Routing**: which model and provider serve this request.
- **Failover**: what to try when a provider errors, times out or rate-limits you.
- **Keys and access**: teams get gateway keys; the real provider keys live only in the gateway.
- **Rate limits and budgets**: per team, per feature or per user.
- **Logging and cost**: every request with its tokens, cost and latency, in one place.

This lesson follows a Bengaluru fintech where five AI features from four teams each called providers directly, with their own keys.

```flow
title: One gateway in front of every provider
Chatbot -[key chatbot]-> Gateway, 2 or more instances
Claims extraction -[key claims]-> Gateway, 2 or more instances
Nightly summaries -[key batch]-> Gateway, 2 or more instances
Gateway, 2 or more instances -[alias chat-default]-> Model X, Mumbai
Model X, Mumbai -[fails, cool-down]-> Model X, Hyderabad
Model X, Hyderabad -[fails]-> Fallback alias: approved model Y, India
```

Each key carries its own rate limit and budget. The gateway checks them before forwarding, logs the result, and keeps provider keys in a secret store.

### Three ways to get a gateway

| Kind | Examples | Pick it when |
| --- | --- | --- |
| Self-hosted, open source | LiteLLM proxy (MIT licence) | Data must stay in your own cloud account and region, and you have a platform team that can run a service with a database |
| Your cloud's API management | Azure API Management (its `llm-token-limit` policy), Google Apigee (its LLM token quota policy) | You already use that cloud's API management for other APIs and mostly call that cloud's models |
| A vendor's managed gateway | Several vendors host one for you | You are small, have no one to run infrastructure, and the vendor's data processing locations are allowed for your data |

The decision usually comes down to two questions. Where may your data be processed? And who will be woken up when the gateway breaks at night? A managed gateway sees every prompt, so check where it processes data before anything else.

## How it works

### One interface and model aliases

Most gateways accept the OpenAI-style chat format and translate it for each provider. Apps never name a real model. They call an **alias** such as `chat-default`, and the gateway maps it to a real model. Upgrading every app to a new model becomes one reviewed line in the gateway config, tested on your golden set first.

### Two layers of failover

Good failover has two layers, and it helps to keep them separate in your head.

1. **Deployments behind one alias.** The same model in two places, for example Mumbai and Hyderabad. The gateway retries on another deployment when one fails.
2. **A fallback alias.** A different, approved model, used only when every deployment of the first alias has failed.

A failing deployment should not slow every request. A **cool-down** (also called a circuit breaker) handles this. After too many failures in a short window, the gateway skips that deployment for a set time. Requests stop paying the timeout first. When the cool-down ends, the gateway tries the deployment again.

### A gateway configuration

LiteLLM's proxy is a common open-source choice; other gateways use the same ideas with different syntax. One file defines aliases, deployments, retries, cool-downs and the fallback. Checked against LiteLLM 1.111.0.

```yaml
# gateway.yaml: the whole gateway in one reviewed file
model_list:
  # Alias chat-default: the same model deployed in two Indian regions.
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>             # in-Region ID or India profile, never APAC or global
      aws_region_name: ap-south-1           # Mumbai
      order: 1                              # used first while healthy
      timeout: 30                           # seconds, normal calls
      stream_timeout: 10                    # seconds, streaming calls
  - model_name: chat-default
    litellm_params:
      model: bedrock/<model id>
      aws_region_name: ap-south-2           # Hyderabad
      order: 2                              # used when Mumbai fails or cools down
      timeout: 30
      stream_timeout: 10
  # Fallback alias: another provider, also in India, approved and tested on the evals.
  - model_name: chat-backup
    litellm_params:
      model: vertex_ai/<model id>
      vertex_project: os.environ/GCP_PROJECT
      vertex_location: asia-south1          # Mumbai
      timeout: 30

router_settings:
  num_retries: 2                            # retries on 429s and server errors
  allowed_fails: 3                          # more than 3 failures in a minute starts a cool-down
  cooldown_time: 60                         # seconds a cooling deployment is skipped
  fallbacks: [{"chat-default": ["chat-backup"]}]

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL     # keys, limits, budgets and spend live here
```

Start it with `litellm --config gateway.yaml --port 4000`. Run two or more instances behind a load balancer, all pointing at the same database.

**A region trap on Bedrock.** Bedrock's cross-Region inference profiles can process prompts outside the Region you call. An APAC profile stays within Asia Pacific, not India, and a global profile can use any supported commercial Region. For some Claude models Bedrock now has an India geographic profile that routes only between Mumbai and Hyderabad. If data must be processed in India, use that profile or an in-Region model ID, and check the Bedrock Regional availability table first: not every model is offered in-Region in Hyderabad.

### Apps call the alias, not the provider

Any OpenAI-compatible client works. Read the response headers to see what actually served the request:

```python
import os
from openai import OpenAI

client = OpenAI(base_url=os.environ["GATEWAY_URL"], api_key=os.environ["CHATBOT_KEY"])

raw = client.chat.completions.with_raw_response.create(
    model="chat-default",                       # the alias, never a provider model name
    messages=[{"role": "user", "content": "Explain my last card statement in two lines: ..."}],
)
reply = raw.parse()
print(reply.choices[0].message.content)
print("model group:", raw.headers.get("x-litellm-model-group"))      # chat-backup means it fell back
print("fallbacks:", raw.headers.get("x-litellm-attempted-fallbacks"))
print("cost in USD:", raw.headers.get("x-litellm-response-cost"))
```

### Keys with rate limits and budgets

The admin creates one virtual key per feature. A virtual key is a key the gateway issues; it maps to the real provider keys, which the team never sees.

```bash
curl -s "$GATEWAY_URL/key/generate" \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"key_alias": "chatbot", "models": ["chat-default", "chat-backup"],
       "rpm_limit": 600, "tpm_limit": 200000,
       "max_budget": 400, "budget_duration": "30d",
       "metadata": {"team": "support", "feature": "chatbot", "owner": "platform-lead"}}'
```

`rpm_limit` caps requests per minute and `tpm_limit` caps tokens per minute for this key. List the fallback alias in `models` too: in testing, a key allowed only `chat-default` got a plain error instead of the backup. Revoking the key cuts one feature off without rotating anything else. Three behaviours from testing this setup are worth knowing:

- **Rate limit and budget fail differently.** Going over `rpm_limit` returned HTTP 429, which a client can retry after a pause. A spent budget returned HTTP 422 with type `budget_exceeded`. Retrying that only wastes time, so clients must treat it as final and alert a person.
- **Budgets are approximate.** The gateway checks the budget before each request, so the request that crosses the line still completes. In a test with a 0.05 dollar budget, spend reached 0.065 before requests were refused. Set the cap a little below what you can really afford.
- **Check the reset date.** Read `budget_reset_at` from `/key/info` after creating a key, rather than assuming the period starts today. Budgets are in US dollars, so convert to rupees at a stated rate in your reports.

### Sharing a provider's quota fairly

Your provider gives you a quota per model, for example a number of tokens per minute in Mumbai. Every key shares it. The rule: **the limits of the features that must never be starved should add up to less than the provider quota, with headroom.** Batch jobs get a smaller limit, run at night, and wait on 429s. Without per-key limits, the first busy job takes the whole quota, and the customer chatbot fails even though "the provider is up".

### Fallback edge cases

Fallbacks are where gateways fail in production. Plan for these:

- **Streams.** If a stream fails before the first token, the gateway can try the next deployment and the user never knows; LiteLLM does this. Once the user has seen half an answer, a switch means restarting the answer or stitching text from two models. Decide in the app what to show, for example "the answer was interrupted, retry?".
- **Tool calls.** Never retry a request whose tool call already ran something with side effects, such as a payment or an email. Make those tools safe to repeat, with an idempotency key, or do not retry them.
- **Prompt caching.** Provider prompt caches do not move with you. During a fallback, every request pays full price and full latency for the long system prompt, so expect cost and time to first token to jump during an outage.
- **Format and tool-call shape.** The backup model may format JSON or tool calls slightly differently. Run the feature's evals on the fallback alias, and test the parser on its output.
- **Errors that should not fall back.** A malformed request fails on every model. Falling back only adds latency and cost. Fall back on timeouts, 429s and server errors.
- **Fallbacks that hide a broken key.** In a test, a wrong key on the primary returned 401, the gateway did not retry it, and it fell back at once. Users saw nothing wrong. Alert when the fallback rate for an alias rises, not only on errors.

### Try it: cool-downs in a fallback chain

This simulation has a Mumbai outage from request 3 to request 12. Watch how the cool-down stops requests waiting on Mumbai, and how a cool-down that is too long keeps skipping Mumbai after it has recovered.

```python
import random

random.seed(7)
ALLOWED_FAILS = 2      # cool down after more than this many failures
COOLDOWN = 5           # requests to skip a cooling deployment
fails = {"mumbai": 0, "hyderabad": 0, "backup": 0}
cooling_until = {"mumbai": 0, "hyderabad": 0, "backup": 0}

def call(deployment, t):
    # Mumbai has an outage from request 3 to request 12.
    if deployment == "mumbai" and 3 <= t <= 12:
        raise TimeoutError("timed out")
    if random.random() < 0.05:
        raise TimeoutError("timed out")
    return deployment

def gateway(t, chain=("mumbai", "hyderabad", "backup")):
    tried = []
    for d in chain:
        if t < cooling_until[d]:
            continue                       # skip without waiting for a timeout
        try:
            served = call(d, t)
            fails[d] = 0
            return served, tried
        except TimeoutError:
            tried.append(d)
            fails[d] += 1
            if fails[d] > ALLOWED_FAILS:
                cooling_until[d] = t + COOLDOWN
                fails[d] = 0
    return "error", tried

for t in range(16):
    served, tried = gateway(t)
    note = f"(waited on {', '.join(tried)})" if tried else ""
    print(f"request {t:2}: served by {served:9} {note}")
```

Requests 3 to 5 each wait for a Mumbai timeout. Then Mumbai cools down and requests 6 to 9 go straight to Hyderabad. Request 8 shows the second layer: Hyderabad has a random timeout, so the backup answers. At request 10 the cool-down ends while Mumbai is still down, so requests 10 to 12 wait on it again and a second cool-down starts. Mumbai is back from request 13, but it is still cooling down, so it is not used. Try `COOLDOWN = 2` and `ALLOWED_FAILS = 0` to see the trade-off between waiting on timeouts and missing a recovery.

### Region-aware routing and logs

For Indian personal data, the aliases those features use should point only at Indian-region deployments. Keep a separate alias for features allowed to use other regions. Log the alias, deployment and region of every call, so an audit can confirm the rule held. Mask personal data in the gateway's logs: it sees every prompt, so unmasked logs make it your biggest sensitive data store.

### The cost of a gateway

It is one more service to run, secure and keep available, and every AI feature depends on it. Measure its own overhead: send the same set of requests directly and through the gateway, and compare median and slow (p95) latency, especially time to first token for streams. Keep it close to your apps, monitor its error rate and database, and keep a documented emergency path, such as a feature flag that sends one critical feature directly to its provider.

## A worked example

The Bengaluru fintech has five AI features from four teams. Each team holds its own provider keys, and finance sees one big monthly bill. The figures below are an illustration of a typical rollout, not measured results.

**The trigger.** A provider outage took the customer chatbot down for about 50 minutes. In the same month, a nightly statement-summary job overran into the morning and used most of the shared token quota, so the chatbot also returned rate-limit errors.

**The setup.** The platform team deploys the gateway as two instances on the company's Kubernetes cluster.

- **Keys.** Every feature gets its own gateway key, tagged with team and feature. Provider keys move into the gateway's secret store and are rotated. The old direct keys keep working for two weeks, then are revoked, so the gateway becomes the only path.
- **Aliases.** `chat-default`, `extract-default` and `embed-default`, each mapped to a specific model.
- **Failover for `chat-default`.** The same model in Mumbai and Hyderabad, with a 60-second cool-down, then a fallback alias with a model from a second provider, also hosted in India and approved by compliance.
- **Evals on the fallback.** Before go-live, the team runs the chatbot's 300-question golden set on both. Suppose the primary scores 92% and the backup 88%, with two JSON format failures that a parser fix resolves. The team accepts 88% for outages and records it in the runbook.
- **Quota sharing.** Suppose the Mumbai quota is 400,000 tokens per minute. The chatbot gets 200,000 and claims extraction 100,000. The batch job gets 60,000 and runs after midnight. That totals 360,000, which leaves headroom for spikes.
- **Budgets and logs.** Each key has a monthly budget with an alert at 75%. Every request is logged with team, feature, alias, deployment, tokens, cost and latency, with personal data masked.

**The result.** In the next provider incident, users see a short period of slower answers while Mumbai cools down and Hyderabad serves, instead of errors. The fallback-rate alert tells the on-call engineer what happened. The first cost report by feature shows the statement-summary job using about 40% of spend. That team moves it to a cheaper model and the provider's batch API.

## Common mistakes

- **One gateway instance.** You have created a new single point of failure for every AI feature. Run several.
- **Fallbacks to unapproved models or regions.** An outage must not quietly send data somewhere it is not allowed to go. This includes Bedrock APAC or global profiles when data must stay in India.
- **Model names in application code.** Use aliases so upgrades and swaps happen in one place.
- **Key limits that add up to more than the provider quota.** Then one busy key can still starve the others.
- **Retrying a budget error.** A spent budget will not refill in a few seconds. Treat it as final and alert someone.
- **Untested fallbacks.** A fallback that has never fired may break output formats or quality when it first does.
- **Alerting only on errors.** Fallbacks hide failures from users, so a broken primary key can go unnoticed for weeks.
- **Gateway logs with full prompts and no masking.** The gateway becomes the biggest sensitive data store you have.

## When a gateway is overkill

- **One app with one provider.** The provider's SDK with retries, a timeout and a billing alert is enough.
- **A small team** that would spend more time running the gateway than it saves.
- **A managed platform** that already gives you keys, budgets and routing.

A gateway pays off once several teams or apps share providers, keys, quota and budgets.

## From demo to production

- **Run two or more instances** with health checks, their own monitoring and a shared database.
- **Keep the config in Git**, reviewed like code, and test model changes on the golden set.
- **Issue one key per feature**, with a rate limit, a budget and a named owner.
- **Route personal data only to approved regions**, and log the region of every call.
- **Drill failover in staging.** Break the primary on purpose with a wrong key or a blocked endpoint. Check that requests still succeed, that latency stays acceptable, and that logs and headers show which model served them. Repeat after every change to the chain.
- **Roll out one low-risk feature first**, compare its errors, latency and cost with before, then move the others one at a time.
