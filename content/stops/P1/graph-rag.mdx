## What it is

Standard RAG retrieves passages similar to the question. Two kinds of questions defeat it:

- **Multi-hop questions** that follow links: "Which projects share a contractor with the delayed Chennai metro package?" The facts sit in different documents and no single passage is similar to the question.
- **Global questions** about a whole collection: "What are the recurring problems in last year's customer complaints?" No passage contains the answer; it emerges from many.

**Graph RAG** adds a **knowledge graph**: entities (people, companies, products, places, events) as nodes and relationships between them as edges, extracted from the documents. Retrieval can then follow relationships and use pre-written summaries of groups of related entities. Microsoft's open-source GraphRAG is one well-known implementation; graph databases such as Neo4j are another route.

```flow
Documents -> Chunks -> Model extracts entities and relationships -> Knowledge graph
Knowledge graph -> Communities detected and summarised
Question -[local search]-> Entities + neighbours + source chunks
Question -[global search]-> Map over community summaries, then reduce
```

```flow
dir: LR
title: A piece of the graph
Project: Metro Pkg 4 | overrun 27% -[contractor]-> ABC Infra
ABC Infra -[also on]-> Project: Pune Ring Road
ABC Infra -[sub-contracts to]-> XYZ Steel
```

This lesson follows an infrastructure finance company in Mumbai whose analysts ask questions that span hundreds of project documents.

## How it works

**Indexing (GraphRAG style).**

1. Chunk the documents as usual.
2. Use a model to extract entities and relationships from each chunk, with short descriptions ("ABC Infra, contractor; supplies steel for Package 4").
3. Merge duplicates ("ABC Infra Ltd" and "ABC Infrastructure").
4. Detect **communities**: clusters of closely connected entities.
5. Have a model write a summary of each community, at several levels of detail.

**Querying.**

- *Local search* for questions about specific entities: find the entities in the question, gather their neighbours, relationships and source chunks, and answer from that.
- *Global search* for collection-wide questions: map the question over community summaries, then reduce the partial answers into one.

**Costs.** Indexing calls a model on every chunk and every community, so it can cost many times more than embedding alone, and must be re-run or updated as documents change. Entity extraction makes mistakes; merges can join things that should stay separate. Queries, especially global ones, use many tokens.

**When it is worth it.** Collections rich in entities and relationships (contracts, investigations, research literature, supplier networks, case files), where multi-hop or global questions are frequent and valuable. For most FAQ-style or policy-lookup assistants, hybrid search with good metadata is cheaper and enough.

**Lighter alternatives.** Store extracted entities as metadata and filter on them; keep a small structured table of key relationships; generate summaries of document groups. Often these give most of the benefit.

**Standard RAG versus Graph RAG:**

| Aspect | Hybrid RAG | Graph RAG |
| --- | --- | --- |
| Single-document questions | Strong | No better |
| Multi-hop questions | Weak | Strong |
| Collection-wide questions | Weak | Strong with community summaries |
| Indexing cost | Embeddings only | Model calls per chunk and community |
| Updates | Re-embed changed chunks | Re-extract and re-merge |
| Failure risk | Missed passages | Wrong extractions and merges |

**Routing between the two.** Few teams replace hybrid RAG; they add a graph for the questions it cannot answer. A small classifier, or a model call, decides whether a question mentions relationships across entities ("which contractors also work on...", "who else is linked to...") or is about the whole collection ("what are the recurring..."). Those go to graph search; everything else goes to hybrid RAG. Log the route for each question so you can check the router's mistakes on the test set.

**Keeping citations.** Every entity, relationship and community summary should keep links to the chunks it came from. Answers can then cite real documents, and analysts can check whether an extracted relationship is actually stated or was invented during extraction.

**A small graph in code.** Extract triples with a model (as structured output), load them into NetworkX, and answer local questions from neighbourhoods:

```python
import networkx as nx
from pydantic import BaseModel

class Triple(BaseModel):
    subject: str
    relation: str
    object: str

class Extraction(BaseModel):
    triples: list[Triple]

def normalise(name):
    n = name.lower().replace("limited", "ltd").replace("infrastructure", "infra")
    return " ".join(w for w in n.replace(".", "").split() if w not in {"ltd", "pvt", "private"})

def build_graph(chunks, extract):
    """extract(text) -> Extraction, via structured output from a model."""
    g = nx.MultiDiGraph()
    for c in chunks:
        for t in extract(c["text"]).triples:
            s, o = normalise(t.subject), normalise(t.object)
            g.add_node(s, label=t.subject); g.add_node(o, label=t.object)
            g.add_edge(s, o, relation=t.relation, source=c["id"])
    return g

def local_context(g, entities, hops=2, limit=40):
    nodes = set()
    for e in map(normalise, entities):
        if e in g:
            nodes |= set(nx.ego_graph(g.to_undirected(as_view=True), e, radius=hops))
    facts = [f'{g.nodes[u]["label"]} —{d["relation"]}→ {g.nodes[v]["label"]} [{d["source"]}]'
             for u, v, d in g.subgraph(nodes).edges(data=True)]
    return facts[:limit]
```

The facts carry their source chunk ids, so the answer can cite real documents. The `normalise` rules are a crude start at entity resolution; check merges by hand for the important entities, and keep a list of names that must never be merged.

**Communities for global questions.** Group closely linked entities and summarise each group once:

```python
from networkx.algorithms.community import louvain_communities

def communities(g, seed=7):
    groups = louvain_communities(g.to_undirected(), seed=seed)
    return sorted(groups, key=len, reverse=True)
```

A model writes a summary per community (with the chunk ids it drew on). For "What are the recurring delay causes across all packages?", ask the question of each community summary, then combine the partial answers.

**Check the extraction before trusting the graph.** Sample 50 extracted triples and mark each as stated in the source, implied, or wrong. If more than a few percent are wrong, improve the extraction prompt (give the allowed entity types and relations) before building anything on top.

**Estimate the indexing bill first.** Count chunks × (extraction prompt + chunk + output tokens), plus one summary call per community. Run it on 5% of the collection, measure, and multiply before committing to the whole thing.

## A worked example

A Mumbai infrastructure finance company reviews thousands of project reports, contractor agreements and site inspection notes. Analysts ask questions like "Which contractors appear in projects with cost overruns above 20%, and where else do they work?"

Hybrid RAG answers single-project questions well but fails these: the facts are spread across hundreds of documents.

A pilot builds a graph of projects, contractors, sub-contractors, locations and inspection findings from 3,000 documents. Indexing costs about 25 times the embedding-only pipeline, a one-time cost plus weekly updates. Entity merging needs a hand-built list of company name variants, because the same contractor appears under several spellings.

On a 40-question test set of multi-hop and global questions, the graph approach answers 70% well, against 30% for hybrid RAG. On single-document questions it is no better. The company keeps both: questions are routed to graph search when they mention relationships across projects, and to hybrid RAG otherwise.

| Measure | Hybrid RAG | Graph approach |
| --- | --- | --- |
| Multi-hop and global questions answered well, of 40 | 30% | 70% |
| Single-document questions | Good | No better |
| Indexing cost | Baseline | About 25 times, plus weekly updates |
| Extra work | None | A hand-built list of contractor name variants |

## Common mistakes

- **Graph RAG for simple lookups.** It adds cost without benefit.
- **Ignoring entity resolution.** Duplicate or wrongly merged entities corrupt every answer that uses them.
- **Forgetting updates.** A graph built once goes stale.
- **No comparison.** Measure against hybrid RAG on the questions that matter.
- **Losing citations.** Keep links from entities and summaries back to source chunks.
- **Trusting extracted relationships without sampling them** against the source text.
- **Free-form relation names.** Give the extractor a fixed list, or the graph fills with near-duplicates.
- **Skipping a cost estimate** before indexing the whole collection.

## When Graph RAG is not worth it

- **Questions are mostly about one document or one fact**: hybrid RAG answers them more cheaply.
- **Documents change constantly**, making re-extraction expensive.
- **Few entities and relationships matter**: a small table of key facts, maintained by people, may be enough.

## From demo to production

- **Keep source chunk ids** on every entity, relationship and summary.
- **Measure extraction accuracy** on a sample after every prompt or model change.
- **Update incrementally**: re-extract changed documents and re-run community summaries on a schedule.
- **Route questions** between graph and hybrid search, and log the route.
- **Track indexing and query cost** separately from ordinary RAG.
