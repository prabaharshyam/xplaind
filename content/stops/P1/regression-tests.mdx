## What it is

A **regression** is when something that used to work stops working after a change. In LLM apps, regressions are common and quiet: a prompt tweak that fixes one case breaks three others; a model upgrade changes the output format; a new chunking setting improves most questions but loses one important document.

**Regression tests** rerun your eval set automatically on every change so these breaks are caught before users see them.

```text
   pull request (prompt, model, retrieval or code change)
        |
        v
   FAST TIER (every push, ~90 s)                    blocks merge on failure
   app starts | JSON valid | 4 options, 1 answer | no duplicates | must-refuse cases | 15 critical cases
        |
        v
   FULL TIER (before deploy or nightly)
   120 cases, judge scores by category  vs  production baseline
   overall within tolerance?  AND  no critical category down?  --> deploy
        |
   production bugs --> new test cases (both tiers as fits)
```

This lesson follows a quiz-generation feature at an edtech company in Noida that turns chapter text into multiple-choice questions.

## How it works

**Two tiers of tests.**

- *Fast checks on every push* (seconds to a few minutes): code-level checks that are cheap and deterministic. Does the app start? Does the output parse as valid JSON? Are required fields present? Do known must-refuse inputs get refused? Do a small set of critical cases still pass?
- *Fuller evals on important changes or nightly*: the whole test set with model judges, comparing scores by category against the current production version.

**Compare against a baseline.** Store the scores of the current production version. A change passes if overall quality does not drop beyond a set tolerance and no critical category (safety, refusals, key customers' cases) drops at all.

**Handle non-determinism.** Model outputs vary between runs. Use low temperature for tests where possible, judge on criteria rather than exact text, and for borderline cases run more than once.

**Model upgrades are changes too.** When a provider releases a new model, or you consider switching, run the full eval. Decide from the results, not the release notes: a newer model may be better overall and worse on your specific cases.

**Wire it into CI.** Run fast checks on every pull request; block merging on failure. Run the fuller eval before deploying a prompt or model change. Store results so you can see trends.

**Add every bug.** Each production failure becomes a regression test case.

**What goes in each tier:**

| Tier | Runs | Contents | Time |
| --- | --- | --- | --- |
| Fast | Every push | Code checks on a small set, critical cases, must-refuse inputs | Seconds to minutes |
| Full | Before deploy, nightly | Whole test set, judges, comparison by category | Minutes to an hour |
| Model candidate | When a new model appears | Full tier plus format checks used downstream | As long as needed |

**A CI workflow in words.** On each pull request, install dependencies, start the app with test settings, run the fast tier, and fail the job if any check fails. On merge to the main branch, or on a label such as "run full eval", run the full tier, compare scores with the stored production baseline by category, post a table to the pull request, and fail if a critical category dropped. Store every run's results with the commit, so you can chart quality over time and spot slow decline.

**Setting tolerances.** Run the full tier several times on the same version to see how much scores move from randomness alone. Set the overall tolerance just above that noise. For critical categories, such as safety and refusals, allow no drop at all, and add more cases there so a single failure is clearly visible.

## A worked example

A Noida ed-tech company's quiz-generation feature creates multiple-choice questions from chapter text, as JSON.

Their setup:

- *On every push*: 15 chapters through the app; checks that every output is valid JSON with four options and one correct answer, no duplicate options, and that two chapters containing sensitive historical content produce no disallowed phrasing. Takes 90 seconds.
- *Before deploying*: 120 chapters scored by a judge for factual accuracy and difficulty, compared with production by subject.

A developer shortens the prompt to cut costs. Fast checks pass. The full eval shows accuracy unchanged for science but down 9 points for history, because the shortened prompt dropped an instruction to use only facts in the chapter. The change is reworked before release.

Months later, the provider's newer model scores 3 points higher overall but produces a different JSON field order that one old client parser cannot handle; the fast checks catch it, and the parser is fixed before switching.

| Change | Fast tier | Full tier | Decision |
| --- | --- | --- | --- |
| Shortened prompt to save cost | Passed | History accuracy down 9 points | Reworked before release |
| Newer provider model | Caught a JSON field-order change breaking an old parser | 3 points higher overall | Parser fixed, then switched |

## Common mistakes

- **No automated tests for prompts.** Prompt changes are code changes.
- **Exact-text comparisons.** Outputs vary; check properties and criteria.
- **Only averages.** Protect critical categories separately.
- **Upgrading models without running evals.**
- **Not adding production bugs to the test set.**

- **Letting the fast tier grow slow.** If it takes more than a few minutes, people skip it. Move slow cases to the full tier.
