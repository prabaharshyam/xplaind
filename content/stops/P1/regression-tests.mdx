## What it is

A **regression** is when something that used to work stops working after a change. In LLM apps, regressions are common and quiet. A prompt tweak that fixes one case breaks three others. A model upgrade changes the output format. A new chunking setting improves most questions but loses one important document.

**Regression tests** rerun your eval set automatically on every change so these breaks are caught before users see them.

```flow
Pull request | a prompt, model, retrieval or code change -> Fast tier, every push, about 90 s | app starts, JSON valid, 4 options and 1 answer, no duplicates, must-refuse cases, 15 critical cases
Fast tier, every push, about 90 s -[fails]-> Merge blocked
Fast tier, every push, about 90 s -[passes]-> Full tier, before deploy or nightly | 120 cases, judge scores by category against the production baseline
Full tier, before deploy or nightly -> Within tolerance, and no critical category down?
Within tolerance, and no critical category down? -[yes]-> Deploy
Production bugs -> New test cases -> Fast tier, every push, about 90 s
```

This lesson follows a quiz-generation feature at an edtech company in Noida that turns chapter text into multiple-choice questions.

## How it works

**Two tiers of tests.**

- *Fast checks on every push* (seconds to a few minutes): code-level checks that are cheap and deterministic. Does the app start? Does the output parse as valid JSON? Are required fields present? Do known must-refuse inputs get refused? Do a small set of critical cases still pass?
- *Fuller evals on important changes or nightly*: the whole test set with model judges, comparing scores by category against the current production version.

**Compare against a baseline.** Store the scores of the current production version. A change passes if overall quality does not drop beyond a set tolerance and no critical category (safety, refusals, key customers' cases) drops at all.

**Handle non-determinism.** Model outputs vary between runs. Use low temperature for tests where possible, judge on criteria rather than exact text, and for borderline cases run more than once.

**Model upgrades are changes too.** When a provider releases a new model, or you consider switching, run the full eval. Decide from the results, not the release notes: a newer model may be better overall and worse on your specific cases.

**Wire it into CI.** Run fast checks on every pull request; block merging on failure. Run the fuller eval before deploying a prompt or model change. Store results so you can see trends.

**Add every bug.** Each production failure becomes a regression test case.

**What goes in each tier:**

| Tier | Runs | Contents | Time |
| --- | --- | --- | --- |
| Fast | Every push | Code checks on a small set, critical cases, must-refuse inputs | Seconds to minutes |
| Full | Before deploy, nightly | Whole test set, judges, comparison by category | Minutes to an hour |
| Model candidate | When a new model appears | Full tier plus format checks used downstream | As long as needed |

**A CI workflow in words.** On each pull request, install dependencies, start the app with test settings, run the fast tier, and fail the job if any check fails. On merge to the main branch, or on a label such as "run full eval", run the full tier. Compare scores with the stored production baseline by category, post a table to the pull request, and fail if a critical category dropped. Store every run's results with the commit, so you can chart quality over time and spot slow decline.

**Setting tolerances.** Run the full tier several times on the same version to see how much scores move from randomness alone. Set the overall tolerance just above that noise. For critical categories, such as safety and refusals, allow no drop at all, and add more cases there so a single failure is clearly visible.

**The fast tier in code.** Property checks are plain tests. This one uses pytest and runs the quiz generator on a few saved chapters:

```python
import json, pytest
from quiz import generate_quiz             # your app's function

CHAPTERS = json.load(open("tests/fast_chapters.json"))   # 15 saved chapters

@pytest.mark.parametrize("chapter", CHAPTERS, ids=lambda c: c["id"])
def test_quiz_shape(chapter):
    quiz = json.loads(generate_quiz(chapter["text"]))
    assert 3 <= len(quiz["questions"]) <= 10
    for q in quiz["questions"]:
        assert len(q["options"]) == 4
        assert len(set(q["options"])) == 4, "duplicate options"
        assert q["answer"] in q["options"]

def test_refuses_out_of_scope():
    out = generate_quiz("Write me a poem about cricket.")
    assert json.loads(out).get("error") == "not_a_chapter"
```

**The baseline comparison in code.** The full tier writes one score per case with its category; this script compares a candidate run with the stored production run:

```python
import json
from collections import defaultdict

CRITICAL = {"safety", "refusals"}

def by_category(path):
    scores = defaultdict(list)
    for line in open(path):
        r = json.loads(line)
        scores[r["category"]].append(r["score"])
    return {c: sum(v) / len(v) for c, v in scores.items()}

def compare(baseline_path, candidate_path, tolerance=0.02):
    base, cand = by_category(baseline_path), by_category(candidate_path)
    problems = []
    for cat, b in base.items():
        drop = b - cand.get(cat, 0)
        limit = 0 if cat in CRITICAL else tolerance
        if drop > limit:
            problems.append(f"{cat}: {b:.2f} -> {cand.get(cat, 0):.2f}")
    return problems

problems = compare("evals/production.jsonl", "evals/candidate.jsonl")
print("PASS" if not problems else "FAIL\n" + "\n".join(problems))
raise SystemExit(1 if problems else 0)       # a non-zero exit fails the CI job
```

**Measure the noise before trusting a drop.** Run the full tier three to five times on the unchanged production version. If history accuracy moves between 0.84 and 0.87 on its own, a candidate at 0.85 has not regressed. For small categories, add cases: with 20 cases, one failure is a 5-point swing.

**Flaky cases.** Some cases pass on one run and fail on the next. Run them three times and require two passes, or fix the case: often the expected answer is ambiguous. Never just delete a flaky case without understanding it.

**Keep the bill small.** Full evals with a judge cost money on every run. Cache outputs for unchanged inputs and prompts, use a cheaper judge for routine runs and a stronger one before releases, and run the full tier on labels or nightly rather than on every push.

**Pin what you test.** Record the exact model version, prompt version, retrieval settings and judge prompt with every run. A score is only comparable with another score made the same way.

## A worked example

A Noida ed-tech company's quiz-generation feature creates multiple-choice questions from chapter text, as JSON.

Their setup:

- *On every push*: 15 chapters through the app; checks that every output is valid JSON with four options and one correct answer, no duplicate options, and that two chapters containing sensitive historical content produce no disallowed phrasing. Takes 90 seconds.
- *Before deploying*: 120 chapters scored by a judge for factual accuracy and difficulty, compared with production by subject.

A developer shortens the prompt to cut costs. Fast checks pass. The full eval shows accuracy unchanged for science but down 9 points for history, because the shortened prompt dropped an instruction to use only facts in the chapter. The change is reworked before release.

Months later, the provider's newer model scores 3 points higher overall but returns JSON fields in a different order, which one old client parser cannot handle. The fast checks catch it, and the parser is fixed before the switch.

| Change | Fast tier | Full tier | Decision |
| --- | --- | --- | --- |
| Shortened prompt to save cost | Passed | History accuracy down 9 points | Reworked before release |
| Newer provider model | Caught a JSON field-order change breaking an old parser | 3 points higher overall | Parser fixed, then switched |

## Common mistakes

- **No automated tests for prompts.** Prompt changes are code changes.
- **Exact-text comparisons.** Outputs vary; check properties and criteria.
- **Only averages.** Protect critical categories separately.
- **Upgrading models without running evals.**
- **Not adding production bugs to the test set.**
- **Letting the fast tier grow slow.** If it takes more than a few minutes, people skip it. Move slow cases to the full tier.
- **Changing the judge and the app at the same time.** You cannot tell which change moved the score.
- **Deleting failing cases to get green.** Fix the app or fix the case, and write down why.

## When lighter testing is enough

- **A prototype that changes daily**: a handful of smoke checks beats a full suite you keep rewriting.
- **Internal tools with a few expert users**, who report problems fast: keep the fast tier, run the full tier before big changes only.
- **Fixed, deterministic steps**, such as parsing a known file format: ordinary unit tests are enough.

Add the full tier, baselines and critical categories once real users depend on the output.

## From demo to production

- **Block merges on the fast tier**, and keep it under a few minutes.
- **Run the full tier before every prompt, model or retrieval release**, and post the category table on the pull request.
- **Store every run** with its commit and versions, and chart scores over time to catch slow decline.
- **Review the test set quarterly**: retire stale cases, add new user patterns and every production bug.
- **Have a model upgrade checklist**: full tier, format checks for every downstream consumer, cost and latency comparison.
