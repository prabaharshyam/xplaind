## What it is

The fine-tuning lessons explain what fine-tuning changes and how LoRA saves memory. This lesson is about running one well: the choices you make at the start, the few settings that matter most, and how to tell from the loss curves whether it is working.

Every fine-tune starts with three choices:

1. **A base model.** For a first test of whether the task is possible, use the strongest model you can afford: if it cannot learn the task, weaker ones will not. Then try smaller models to cut cost.
2. **A method.** Start with **LoRA** or another light method. It needs less memory and less data, and many adapters can share one base model when serving. Try full fine-tuning later, if you have thousands of examples or more and LoRA falls short.
3. **A tool.** The easiest is a provider's fine-tuning service: upload data, get a model back, but with few settings and only their models. Open-source frameworks such as Hugging Face TRL and PEFT, Unsloth, Axolotl, LLaMA-Factory and LitGPT run on your own GPUs and give you every setting.

Two common development paths:

- **Progression path.** Test the code on the cheapest model, test the data on a middling model, push quality with the best one, then compare several sizes to find the best price and performance.
- **Distillation path.** Fine-tune a strong model on a small, excellent dataset, use it to generate more training data, then train a cheaper model on that.

```flow
title: A fine-tuning run you can trust
Clean data and a locked test set -> Smoke test on the smallest model | does the code run end to end?

```

## How it works

**Learning rate** is the size of each step when weights are updated. It is the setting most likely to make or break a run.

- Too high: the loss jumps around or shoots up, and outputs can turn to nonsense.
- Too low: the loss barely falls and the model hardly changes.
- Useful values range widely, from about 1e-7 to 1e-3. LoRA runs commonly start around 1e-4 to 2e-4; full fine-tuning uses much smaller values, often a tenth or less of the rate used at the end of pre-training.
- A **schedule** often warms up briefly, then lowers the rate towards the end.

**Batch size** is how many examples each update learns from. Very small batches (fewer than about 8) can make training unstable; larger batches give steadier updates but need more memory. When memory is tight, **gradient accumulation** adds up several small batches before each update, giving the stability of a bigger batch without the memory.

**Epochs** are full passes over the training data. Very large datasets may need only one or two; a few thousand examples may keep improving for several. Let the validation loss decide: keep training while it falls, stop when it starts rising.

**Prompt loss weight** controls how much the prompt part of each example counts. At inference the user writes the prompt and the model writes the response, so most setups count the response fully and the prompt little or not at all (many tools default to masking the prompt; some use around 10%).

**Reading the curves.** Plot training loss and validation loss after every few dozen steps.

| What you see | Likely cause | What to do |
| --- | --- | --- |
| Loss spikes or becomes NaN | Learning rate too high, or bad data | Lower the rate; check for empty or huge examples |
| Loss flat from the start | Rate too low, wrong labels, or loss on wrong tokens | Raise the rate; check the data format and masking |
| Training falls, validation rises | Overfitting | Fewer epochs, more data, keep the earlier checkpoint |
| Both still falling at the end | Undertrained | More epochs or more data |
| Loss fine, outputs poor | Data teaches the wrong thing, or prompt format differs at inference | Read examples; use the exact chat template in training and use |

**Habits that save days.**

- **Smoke test** the whole pipeline on a tiny model and a few examples: load, train, save, reload, generate.
- **Overfit on purpose**: train on 20 examples until the model repeats them. If it cannot, something is broken.
- **Save checkpoints** to a folder that exists, often enough that a crash costs minutes, not hours.
- **Use the same chat template** in training and in use. A mismatch quietly ruins results.
- **Log every setting** and the data version with each run.

A tiny helper to read your loss logs:

```python
def diagnose(train_loss, val_loss):
    """Lists of loss values measured at the same steps."""
    if any(x != x or x > 10 * train_loss[0] for x in train_loss):   # NaN or blow-up
        return "Unstable: lower the learning rate and check for bad examples."
    if train_loss[-1] > 0.95 * train_loss[0]:
        return "Not learning: raise the learning rate or check data and masking."
    best = val_loss.index(min(val_loss))
    if best < len(val_loss) - 1:
        return f"Overfitting after step {best}: keep that checkpoint or use fewer epochs."
    return "Both still falling: more epochs or more data may help."

print(diagnose([2.1, 1.6, 1.2, 0.9, 0.7], [2.0, 1.6, 1.4, 1.5, 1.7]))
```

## A worked example

An ed-tech company in Chennai is fine-tuning an open 8B model with LoRA to grade short answers in English and Tamil as correct, partly correct or wrong, with a one-line reason. They have 2,400 graded answers, keep 300 as a locked test set and 200 for validation.

First, a smoke test on a 0.5B model with 20 examples: the run, saving and reloading all work, and the model memorises the 20 examples. Then the real runs:

| Run | Learning rate | Epochs | What the curves showed | Test accuracy |
| --- | --- | --- | --- | --- |
| 1 | 2e-3 | 3 | Loss jumped, then exploded; outputs gibberish | Not usable |
| 2 | 1e-6 | 3 | Loss barely moved; outputs like the base model | 61% |
| 3 | 2e-4 | 3 | Validation best at end of epoch 2, then rose | 84% (epoch-2 checkpoint) |
| Prompt-only baseline | n/a | n/a | n/a | 72% |

The numbers are for illustration. Run 3's epoch-2 checkpoint beats the prompt baseline by 12 points. Tamil accuracy is 6 points below English, so the next step is more Tamil examples, not more tuning.

## Common mistakes

- **Starting with a full fine-tune on a huge model.** Prove the task with LoRA first.
- **Skipping the smoke test.** A typo in a save path can waste a night's training.
- **Judging by training loss alone.** Only validation and test results show real learning.
- **Using all epochs blindly.** Keep the checkpoint where validation was best.
- **Changing many settings at once.** Change one, compare, then the next.
- **A different prompt format in production.** The model learned one template; give it the same one.

## When to stop tuning settings

- **Validation results are stable across sensible settings.** Further gains will come from data, not knobs.
- **One segment lags**, such as a language or a question type: add examples for it.
- **The prompt baseline is close.** If fine-tuning only wins by a point or two, the upkeep may not be worth it.

## From demo to production

- **Record each run**: data version, base model, method, every setting, curves and test scores.
- **Keep the best checkpoint and its exact template**, and test the deployed model on the same test set.
- **Re-run the recipe** when the base model or data changes; a recorded recipe makes it routine.
- **Monitor after launch**, since real inputs drift away from training data.
