## What it is

Agents decide for themselves how many steps to take. Sometimes that goes wrong: a tool keeps failing and the agent keeps retrying, two agents hand work back and forth, or it keeps "improving" a draft. Without limits, a loop burns tokens, hammers downstream systems and repeats real actions.

Three controls prevent this:

- **Loop limits**: a maximum number of steps or tool calls per task, and per run when sub-agents are involved.
- **Budgets**: caps on tokens, time and money per task, per user and per day for the whole feature.
- **Kill switches**: a fast, reliable way for an operator to stop a tool, an agent or a whole feature without a deploy.

Repetition checks, circuit breakers, rate and concurrency limits and idempotency keys support them.

```flow
title: Where each limit is checked
Every task | up to 15 steps, 60,000 tokens, 90 s -> Shared store | Postgres or Redis
Every model call | reserve the estimate, then settle -> Shared store
Every tool call | kill switch, circuit breaker, idempotency key -> Shared store
Every day | ₹15 per student, ₹8,000 for the feature -> Shared store
Shared store -> Provider spend limit | the backstop
```

This lesson follows an illustrative case: a homework-help agent at a Bengaluru edtech company that spent ten times its weekly budget in one night.

## How it works

### Per-task limits

Count steps, tool calls, tokens and elapsed time in the loop. Choose each cap from a week of real runs: about twice the 95th percentile. If 95% of tasks finish in 12 steps and ₹2, a cap of 25 steps and ₹5 stops runaways without cutting off normal work. Revisit the numbers when you change the model or the prompt.

On hitting a limit, stop cleanly: save state, tell the user in plain words what was done and what they can do instead, and log it as a failure to investigate. A stopped task should never look like a crash.

### Repetition checks and circuit breakers

A **repetition check** works inside one task. If the same tool is called with the same arguments three times, or the same error comes back three times in a row, end the task early.

A **circuit breaker** works across all tasks. Count each tool's failures in the shared store. If, for example, a tool fails 20 times in a minute across all users, "open" the circuit: for the next five minutes every call to that tool fails at once with a clear message, without reaching the tool. Then let one trial call through; if it works, close the circuit. A repetition check stops one task looping. A circuit breaker stops a thousand tasks each looping a little, the usual shape of an overnight bill.

### Run-level caps across sub-agents

When a planner hands work to sub-agents, each one may respect its own 15-step cap while the run as a whole takes hundreds of steps. Give every run a root `run_id`, pass it to every sub-agent, and count steps against that id in the shared store. Cap the total (for example 40 steps per run) and the number of hand-offs (for example 4).

### Budgets per user and per day

Count spend per user per day and refuse politely past the cap. Count the whole feature per day too, with alerts at 50% and 80% that list the top users and task types, so someone acts before the cap cuts everyone off. Use Asia/Kolkata days, so limits reset at your users' midnight.

The counts must live in a shared store, such as a database or Redis: six servers counting in memory allow six times the cap. But a shared store is not enough. The natural code is "check, call, record":

1. Read today's total. It is ₹14 and the cap is ₹15, so a ₹1 call is allowed.
2. Call the model.
3. Add the real cost to the total.

Twenty requests from one user can all do step 1 before any reaches step 3, so all twenty pass and spend. Making step 3 atomic does not help: the race is in the gap between check and spend. This bug is called **check-then-act**.

The fix is **reserve, then settle**. Before the call, add an upper-bound estimate to the total in one conditional statement that succeeds only if the new total stays within the cap. After the call, swap the estimate for the real cost. Every in-flight call is already counted, so no check sees a stale total.

### A race-safe budget in code

This version uses SQLite so it runs on a laptop. A SQLite file is shared only by processes on one machine; with several servers, use the same pattern on Postgres or Redis.

```python
import sqlite3
from contextlib import contextmanager
from dataclasses import dataclass
from datetime import datetime
from zoneinfo import ZoneInfo

# Adds the estimate only if the new total stays within the cap; else returns no row.
RESERVE = """INSERT INTO spend (scope, day, paise) VALUES (?, ?, ?)
  ON CONFLICT (scope, day) DO UPDATE SET paise = spend.paise + excluded.paise
  WHERE spend.paise + excluded.paise <= ?
  RETURNING paise"""

@dataclass(frozen=True)
class Reservation:
    scopes: tuple
    day: str
    paise: int

def connect(path):
    db = sqlite3.connect(path, timeout=10, isolation_level=None)  # we run our own transactions
    db.execute("CREATE TABLE IF NOT EXISTS spend (scope TEXT, day TEXT,"
               " paise INTEGER NOT NULL, PRIMARY KEY (scope, day))")
    return db

def today():
    return datetime.now(ZoneInfo("Asia/Kolkata")).date().isoformat()

@contextmanager
def write_tx(db):
    db.execute("BEGIN IMMEDIATE")           # take the write lock before reading anything
    try:
        yield
        db.execute("COMMIT")
    except BaseException:
        db.execute("ROLLBACK")
        raise

class OverBudget(Exception):
    pass

def reserve(db, caps, paise):
    """caps is {scope: cap in paise}. Reserve on every scope, or on none."""
    if paise > min(caps.values()):
        return None
    day = today()
    try:
        with write_tx(db):
            for scope, cap in sorted(caps.items()):       # same order everywhere
                if not db.execute(RESERVE, (scope, day, paise, cap)).fetchall():
                    raise OverBudget(scope)               # rolls back earlier scopes
    except OverBudget:
        return None
    return Reservation(tuple(sorted(caps)), day, paise)

def settle(db, r, actual_paise):
    """Swap the estimate for the real cost, on the day it was reserved."""
    with write_tx(db):
        for scope in r.scopes:
            db.execute("UPDATE spend SET paise = paise + ? WHERE scope = ? AND day = ?",
                       (actual_paise - r.paise, scope, r.day))
```

Call `reserve` with the user and feature caps together. If it returns `None`, refuse politely; otherwise call the model, then `settle` with the cost from the usage report.

The details matter:

- **All or none.** The user and feature counters change in one transaction, so a refusal from the feature cap does not leave the user charged.
- **Money in whole paise.** Integers add exactly; floating-point rupees drift.
- **The reservation keeps its day.** A call that starts at 11:59 pm settles against the day it was reserved on, not the next one.
- **Failures land on the safe side.** If the server crashes before `settle`, the estimate stays counted; no one overspends. If a call never reached the provider, settle with 0. If you cannot tell what was billed, keep the reservation.
- **The same shape works elsewhere.** Postgres supports `INSERT ... ON CONFLICT DO UPDATE ... WHERE ... RETURNING`; the conflicting row is locked, so a second request waits and then sees the new total. Lock scopes in a fixed order (the `sorted` call) to avoid deadlocks. In Redis, put the read, compare and `INCRBY` in one Lua script, which Redis runs atomically.
- **The feature row is a hot spot.** Every request locks it briefly. At very high traffic, split it into several rows or use Redis.

### Estimating cost before the call

The cap holds only if the reservation is an upper bound. Count the input tokens (with your provider's token counter, or over-estimate) and assume the model writes the full `max_tokens`:

```python
def estimate_paise(input_tokens, max_tokens, in_paise_per_m, out_paise_per_m):
    """Upper bound: every input token, plus the most output max_tokens allows."""
    cost = input_tokens * in_paise_per_m + max_tokens * out_paise_per_m
    return -(-cost // 1_000_000)                     # round up to whole paise
```

For example, suppose a model costs ₹25 per million input tokens and ₹125 per million output tokens (made-up numbers; use your provider's price page and record the date you checked it). A 3,000-token prompt with `max_tokens` of 1,000 reserves `estimate_paise(3000, 1000, 2500, 12500)`, which is 20 paise. Most calls finish early and `settle` returns the rest.

Two gotchas. Check that `max_tokens` bounds everything your provider bills as output, including any reasoning tokens. And if you stream, you can count output as it arrives and close the stream when a run budget or kill switch says stop; until you know how your provider bills a cancelled stream, keep the whole reservation.

### Proving it with a concurrent test

A race shows up only under real concurrency. Here twenty workers, each with its own connection like separate servers, make 100 calls for one user at once:

```python
import time
from concurrent.futures import ThreadPoolExecutor

CAPS = {"user:u42": 1500, "feature:homework": 800_000}   # ₹15 and ₹8,000

def one_call(db):
    r = reserve(db, CAPS, 200)          # estimate: ₹2
    if r is None:
        return 0
    time.sleep(0.01)                    # stands in for the model call
    settle(db, r, 150)                  # real cost: ₹1.50
    return 150

def test_cap_holds_under_concurrency(tmp_path):
    path = tmp_path / "budgets.db"
    connect(path).close()
    def server(_):
        db = connect(path)
        return sum(one_call(db) for _ in range(5))
    with ThreadPoolExecutor(max_workers=20) as pool:
        spent = sum(pool.map(server, range(20)))
    total = connect(path).execute(
        "SELECT paise FROM spend WHERE scope = 'user:u42' AND day = ?", (today(),)).fetchone()[0]
    assert 0 < spent == total <= 1500
```

In our runs this passed every time, with ₹13.50 spent. The check-then-spend version, in the same test, let up to ₹42 through against the ₹15 cap. Keep the test in CI so nobody "simplifies" the reservation away.

### Rate and concurrency limits

Two more limits protect your systems rather than your money:

- **Rate limits** cap requests per minute. A common algorithm is the **token bucket**: each user's bucket holds up to, say, 10 tokens and refills one every six seconds. Each request takes a token; an empty bucket means "slow down". Short bursts pass, but the average stays at ten a minute.
- **Concurrency limits** cap tasks running at once, for example 2 per user. Pressing "try again" ten times then gives two running tasks, not ten. Use the reserve pattern on a "running" counter, release it in a `finally` block, and give each slot an expiry, because a crashed server never runs its `finally`.

### Kill switches

A kill switch is a flag your code checks before every step and every tool call, with levels: disable one tool (stop all refunds), disable the agent (fall back to a human queue or a simple form), or disable the feature. Flip it from an admin screen or a config service without redeploying. Read flags from the shared store with a short cache, so a change takes effect within seconds everywhere:

```python
import json, logging, time

log = logging.getLogger("agent")
WRITE_TOOLS = {"send_email", "issue_refund", "message_driver"}
MAX_STALE = 60                                           # seconds
_cache = {"read_at": float("-inf"), "ok_at": float("-inf"), "flags": {}}

def flags():
    now = time.monotonic()
    if now - _cache["read_at"] > 5:                      # refresh every 5 seconds
        _cache["read_at"] = now
        try:
            _cache["flags"] = json.loads(config_store.get("agent_flags") or "{}")
            _cache["ok_at"] = now
        except Exception:
            log.warning("flag store unreachable; using last flags")
    if now - _cache["ok_at"] > MAX_STALE:                # no good read for a minute
        return {**_cache["flags"], "write_tools_off": True}
    return _cache["flags"]

def allowed(agent, tool=None):
    f = flags()
    if f.get("all_agents_off") or f.get(f"{agent}_off"):
        return False
    if tool and f.get(f"tool_{tool}_off"):
        return False
    return not (tool in WRITE_TOOLS and f.get("write_tools_off"))
```

`config_store` is whatever shared store you have: a database row, Redis or a feature-flag service. The code fails safe in a bounded way. A short outage changes nothing. After a minute with no good read, or at start-up if the first read fails, write tools such as emails and refunds switch off while read-only tools keep working. Keeping old flags forever would mean a switch flipped during the outage never arrives.

### Idempotency for actions

Give each real-world action a key built from what makes it unique (for example the order id and refund reason). The receiving system refuses a second action with the same key, so loops and retries cannot repeat payments or messages.

### Drill the kill switch

Once a month, in staging and then in production at a quiet hour, flip each switch and check that tasks stop within seconds, users see a clear message, and the rest of the app keeps working. Time it and record who did it. Teams that never practise learn in a real incident that the switch was read only at start-up, or that nobody on call knew where it was.

## A worked example

The homework-help agent ran fine for a month, at about ₹18,000 of model spend a week. Then, on a Sunday night, a change in a maths tool made it return an error for one type of question. The agent retried with small variations, and students kept pressing "try again". By Monday morning the feature had spent ₹1.8 lakh, ten times a normal week.

The team pulled a month of runs and set limits from them:

- **Per task.** 95% of tasks finished in 7 steps, 25,000 tokens and 40 seconds, so the caps are 15 steps, 60,000 tokens and 90 seconds. Three identical tool errors end the task with "I couldn't solve this one; your teacher can help."
- **Per student.** 95% of students spent under ₹6 a day, so the cap is ₹15, shown as a friendly "come back tomorrow". Each student may run 2 tasks at once.
- **Feature per day.** ₹18,000 a week is about ₹2,600 a day, and the busiest normal day was about ₹4,000. The cap is ₹8,000, about three times an average day and twice the busiest. Alerts go to the on-call engineer's phone at 50% (₹4,000) and 80% (₹6,400).
- **Circuit breaker** on the maths tool: 20 failures in a minute pauses it for five minutes.
- **Kill switch.** An admin toggle per tool and for the agent. Turning off the agent shows a "homework help is resting" banner; the rest of the app keeps running.
- **Provider.** A hard monthly spend limit as the backstop.

What each control would have done on that Sunday night:

| Control | Effect on the incident |
| --- | --- |
| Circuit breaker | Pauses the maths tool within a minute of the fault, for every student |
| Repetition check | Ends each looping task after three errors |
| Per-student cap and 2 running tasks | Stops "try again" from multiplying the damage |
| Feature cap of ₹8,000 | No day can cost more than ₹8,000, against ₹1.8 lakh that night |
| Alert at ₹4,000 | Wakes someone while it is still cheap |

Two weeks later a similar tool fault tripped the circuit breaker within a minute. The bill was a few hundred rupees, and the alert reached the team before any student complained.

## Common mistakes

- **No step cap.** The single cheapest protection; add it first.
- **Budgets held in memory.** Each server counts separately and the true total runs far past the cap. Use a shared store.
- **Check-then-act budgets.** Reading the total, calling the model and then adding the cost lets concurrent requests all pass the same check. Reserve first, in one statement.
- **Estimates that are not upper bounds.** If you reserve the average cost, the cap leaks. Reserve for the full `max_tokens`.
- **No cap on concurrent tasks.** Ten parallel tasks each pass a per-task cap.
- **Per-agent caps only.** Sub-agents that hand work back and forth need one count per root run.
- **A kill switch that needs a deploy.** In an incident you need seconds, not a build pipeline.
- **A kill switch read only at start-up.** It does nothing until the next restart.
- **Failing open.** If the flag store is down for long, treat write tools as off.
- **Silent stops.** Tell the user what happened and log it; a stopped task is a bug to fix.
- **Retrying non-idempotent actions.** Use idempotency keys so loops cannot repeat payments or messages.
- **Floating-point money.** Count paise as integers.

## When simpler limits are enough

- **A prototype used by your own team**: a step cap and the provider's spend alert may be all you need.
- **Fixed workflows with one or two model calls**, where cost per request is predictable.
- **Read-only internal tools** with a handful of users.

Per-user budgets, feature caps and layered kill switches matter once outsiders can start runs or agents can act.

## From demo to production

- **Reserve budgets atomically in shared storage** before every model call, and settle after.
- **Check flags and circuit breakers** before every step and tool call.
- **Alert at 50% and 80%** of feature budgets, listing the top spenders.
- **Keep the concurrent budget test in CI.**
- **Drill the kill switches monthly** and record how long each took.
- **Log every stop** with its reason, and review whether limits are set right.
