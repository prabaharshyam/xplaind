## What it is

**Evals** are repeatable tests for an AI application. You run the app on a fixed **test set** of realistic inputs and score each output, so every change (a new prompt, model or retrieval setting) gets a number you can compare with the last one. Without evals, teams change prompts by feel and cannot tell whether they made things better or worse.

## How it works

**Build the test set from reality.** Collect real user inputs where possible (logs, support tickets, sample documents), plus cases you know are hard. Aim for 30 to 100 to start, covering:

- common, everyday cases;
- edge cases (long inputs, unusual formats, mixed languages);
- cases that should be refused or escalated;
- past failures (every bug becomes a test case).

**Define what good means per case.** Depending on the task:

- an exact expected value (category, extracted field, number);
- required facts or citations the answer must contain;
- things the answer must not do (promise refunds, give medical advice);
- a rubric a person or a model judge applies (correct, complete, polite).

**Score with the cheapest reliable method.** Code checks first: exact match, JSON validity, required keywords, length limits, correct citations. Model judges for open-ended quality, with their agreement checked against human grades. Human review for a sample, especially early.

**Look at the data.** Before writing scorers, read 50 to 100 real outputs and note how they fail. The most useful evals come from observed failure patterns, not from generic metrics.

**Run on every change and compare.** Keep a table of versions and scores, by category of case. A change that raises the average while breaking refusals is not an improvement.

**Keep it alive.** Add new cases as users find new problems; retire cases that no longer reflect reality; never tune so hard on the set that it stops representing users.

## A worked example

A Pune insurance broker's assistant drafts replies to policyholder emails. The team argues about whether a new prompt is better.

They build an eval:

- 60 real emails (anonymised): 35 routine questions, 10 claims-status queries, 8 complaints, 7 that need a human (legal threats, medical details).
- Code checks: the reply contains the policy number when the email had one; no reply promises claim approval; the seven escalation cases are marked "needs human".
- A model judge with a rubric (accurate to the policy wording, answers every question, polite), calibrated against two staff members' grades on 30 replies (85% agreement).

Results: the old prompt scores 71% on the judge and misses 3 of 7 escalations; the new prompt scores 78% but misses 4 escalations. Neither is acceptable. A third version adds explicit escalation rules: 80% and 7 of 7 escalations caught. The table settles the argument in an afternoon.

## Common mistakes

- **No test set.** Changes are judged by a couple of examples.
- **Made-up test cases only.** Use real inputs.
- **Only averages.** Look at categories, especially safety cases.
- **Unchecked model judges.** Compare with human grades.
- **A frozen set.** Add every new failure.
