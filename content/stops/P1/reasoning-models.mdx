## What it is

Most of the money in AI is spent before you ever see a model: training it. **Test-time compute** is the other side. It means spending more computing at the moment of answering, so the answer is more likely to be right. "Test time" is the research word for inference, the time when a trained model is used.

There are three common ways to do it.

1. **Ask it to think step by step.** This is **chain-of-thought** (CoT) prompting: the model writes out its reasoning before the answer. A close cousin is **self-critique**, where the model checks its own draft before finishing.
2. **Generate several answers and keep the best.** This is **best-of-N**. A **verifier** (a test, a rule check or a scoring model) picks the winner, or a majority vote does when answers are exact.
3. **Use a reasoning model.** These models are trained to think at length before they answer. You set how much effort they spend. The thinking is often hidden: you see only the answer, but you still pay for the thinking.

All three trade money and waiting time for accuracy. Extra thinking pays when the model *can* reach the right answer but often slips on the way, as in multi-step maths, code and planning. It does not help when the model lacks the facts.

## How it works

### Chain of thought

The simplest version adds one line to the prompt: "Think step by step, then give only the final answer on the last line." You can also list the steps you want, or show one worked example. The 2022 paper that named the method (Wei and others, linked below) showed large gains on maths word problems with large models. The last-line answer matters: your code has to find it.

The first catch is length: a reasoned answer has many more tokens, and each costs money and time. The second is quieter: **the written reasoning is not guaranteed to be the real reason for the answer.** In a 2025 Anthropic study, models were slipped a hint to the answer. When they used the hint, Claude 3.7 Sonnet mentioned it in its reasoning only 25% of the time, and DeepSeek R1 39% of the time. Earlier work (Turpin and others, 2023) found the same pattern with chain-of-thought prompts. So treat shown reasoning as a helpful draft, not as proof. Check the final answer, not how convincing the steps sound.

### Best-of-N and verifiers

Ask for several answers with a little variety (a temperature above zero, or slightly different prompts), then choose one.

- **By majority vote**, also called **self-consistency.** Ask the same maths question five times and take the most common final number. It works only when answers are exact: a number, a label, a choice. Agreement is also a signal: when samples disagree, the question is probably hard.
- **With an outcome verifier**, which checks the final answer. Run generated code against tests, run generated SQL and compare the result with a known one, or check that an extracted date is real. In 2021 OpenAI reported that on grade-school maths problems, a 6-billion-parameter model with a trained verifier slightly beat a fine-tuned 175-billion-parameter model, a gain they compared to a 30-fold increase in model size.
- **With a process verifier**, usually a **process reward model** (PRM), which scores each step instead of only the end. OpenAI's 2023 paper "Let's Verify Step by Step" found that step-level feedback beat answer-level feedback on competition maths, solving 78% of a test subset. Hugging Face's write-up, this lesson's main resource, used a PRM to guide search and showed 1B and 3B models beating their 8B and 70B siblings on the MATH-500 benchmark when given enough samples.
- **With a scoring model**, such as an LLM judge. This works for open-ended text but is only as good as the judge.

Sampling N answers costs roughly N times as much, so N is usually small: about 3 to 8 in products, far below the hundreds used in research runs.

A small helper for majority voting. Note the normalising step: "12.50", "25/2" and "12.5" are the same answer, and a plain text comparison would split the vote three ways.

```python
from collections import Counter
from fractions import Fraction

def normalise(text):
    """Turn '12.50', ' 25/2 ' and '12.5' into the same vote. Non-numbers stay as text."""
    t = text.strip().lower().rstrip(".")
    try:
        return Fraction(t)  # exact, so rounding never splits a vote
    except (ValueError, ZeroDivisionError):
        return t

def majority_answer(ask, question, n=3):
    """ask(question) returns the model's final answer as a short string."""
    votes = Counter(normalise(ask(question)) for _ in range(n))
    best, count = votes.most_common(1)[0]
    unanimous = count == n
    # Accept only a unanimous answer. Anything else goes to the stronger model.
    return best, unanimous

# answer, ok = majority_answer(ask, "If 3x + 7 = 25, what is x?")
# if not ok: answer = ask_reasoning_model(question)
```

Ask the model for a bare number on the last line. An answer like "x = 6" stays as text and will not match "6".

### Reasoning models

These models are trained, often with reinforcement learning on problems with checkable answers, to think at length before replying. They shine on maths, code and planning; on simple questions they mostly add cost and delay.

You steer them with an **effort setting**, not with the prompt. For example, as of November 2026, OpenAI's Responses API has `reasoning.effort`, and Anthropic's API has `output_config.effort`, with levels from `low` up to `max` on recent Claude models. Effort is soft guidance, not a token count: at low effort the model may skip thinking on easy inputs. Defaults differ by model (Anthropic's is `high` on most Claude models and `medium` on a few newer ones), so set effort explicitly and test two or three levels as separate options. Older tutorials show a fixed thinking budget (`budget_tokens`); Anthropic has deprecated it, and Claude 4.7 and later models reject it.

**Do not stack chain-of-thought prompts on a reasoning model.** It already thinks before answering. When OpenAI launched its o1 reasoning models, its prompting guide advised simple, direct prompts and no chain-of-thought instructions. Anthropic recommends changing the effort level first, and only then a short nudge such as "Think carefully before responding" if a task still needs it. Do not script the steps or ask for all the reasoning in the reply: you would pay for the hidden thinking and again for a visible copy.

### What you pay for, and what the user waits for

- **Thinking is billed as output tokens**, even when you never see it. Output tokens usually cost more than input tokens.
- **A summary costs the full thinking.** Anthropic can return a short summary of the thinking, but you are billed for all the thinking behind it, not for the summary's length.
- **Thinking counts toward the output limit.** An output limit (`max_tokens` at Anthropic) sized for short replies can run out during thinking, and the reply stops with little or no answer. Leave room for both, or lower the effort.
- **Read the real count.** Anthropic reports it in `usage.output_tokens_details.thinking_tokens`; OpenAI reports reasoning tokens under `output_tokens_details` in its usage data. Log it per request: it is the number that explains your bill.
- **Nothing visible streams while it thinks.** With the thinking hidden (the default on Anthropic's Claude 5 models), the first visible word arrives only after thinking ends. Measure the time to the first word the user sees, and show a status line or a thinking summary as progress.
- **Multi-turn chats cost more.** Thinking that stays in the conversation is billed as input on later turns: on some models from every earlier turn, on others only from the last one. Changing the effort level mid-conversation can also break the prompt cache.

### The methods side by side

| Method | Extra cost | Extra wait | Works best when | Watch out for |
| --- | --- | --- | --- | --- |
| Step-by-step prompt | 2 to 5 times the output tokens | Seconds | Multi-step problems on a non-reasoning model | Long replies; reasoning that sounds right but is not |
| Majority vote of 5 | About 5 times | Little, if run in parallel | Exact answers: numbers, labels | Useless for free-form text; shared blind spots |
| Best-of-N with a verifier | About N times plus checks | Little, if parallel | Code, SQL, formats you can test | A weak verifier picks bad answers |
| Reasoning model | Often 3 to 10 times | Seconds to minutes | Hard maths, code, planning | Hidden thinking billed; output limit too small |

These multipliers are rough patterns to compare options, not prices. Measure on your own questions.

## A worked example

A coaching company in Kota wants AI to check students' answers to JEE-style maths problems and explain mistakes, about 300 problems a day. Teachers write new practice problems every day, and students also upload doubts from other books, so most problems arrive **without an answer key**. The AI must first find the right answer, then compare it with the student's. (Where a key exists, a plain comparison does that part and no model is needed.)

To compare options, the team builds a test set of 200 past problems whose answers teachers have checked. "Correct" below means the option found the right answer. The explanation step that follows costs the same for every option, so it is left out. All numbers are illustrative, chosen to show the method; they are not measured prices.

The targets, agreed before testing: at least 88% correct, under ₹150 per 100 problems, and most students get a result within 10 seconds.

| Option | Correct | Cost per 100 problems | Typical wait |
| --- | --- | --- | --- |
| Mid-size model, plain prompt | 71% | ₹20 | 3 s |
| Same model, step-by-step prompt | 81% | ₹55 | 8 s |
| Step-by-step, majority of 5 | 88% | ₹275 | 9 s (parallel) |
| Reasoning model, low effort | 82% | ₹45 | 8 s |
| Reasoning model, medium effort | 90% | ₹120 | 20 s |
| Reasoning model, high effort | 91% | ₹260 | 45 s |
| Router: 3 plain answers, reasoning model (medium) only when they disagree | 90.5% | ₹96 | 3 s for 70%, 23 s for 30% |

**Read it with the noise in mind.** On 200 problems, the margin of error near 90% is about 4 points either way (see the lesson Quality, cost and speed trade-offs). So 88%, 90%, 90.5% and 91% are a tie on quality, and cost and wait decide.

- The step-by-step prompt was a big, cheap win: 10 points for ₹35 more per 100. Try it first on any model that does not reason by itself.
- Low effort misses the target. High effort costs more than twice as much as medium and makes students wait 45 seconds, for a gain inside the noise. This is the usual shape of an effort sweep: large gains at first, then small ones at a high price.
- The majority of 5 and high effort break the budget. Medium effort clears quality and cost, but every student waits 20 seconds, so it fails the wait target. Only the router meets all three.

**How the router works, and where its numbers come from.** Each problem first gets three quick plain-prompt answers, run in parallel at ₹20 per 100 each: ₹60 per 100 in all. If all three agree, that answer is used. If not, the problem goes to the reasoning model at medium effort.

- On the test set, all three agreed on 140 of 200 problems (70%). The agreed answer was right on 136 of them, or 97%. Not 100%: when a model has a blind spot, such as the same sign error every time, three samples agree on the same wrong answer. Agreement is evidence, not proof.
- The other 60 problems (30%) went to the reasoning model, which got 45 right, or 75%. That is well below its 90% overall, because these are the hard problems.
- Accuracy: 136 + 45 = 181 of 200, or 90.5%.
- Cost: ₹60 for the samples, plus 30% of problems × ₹120 = ₹36 for escalations, so ₹96 per 100.
- Wait: 3 seconds for the 70% that agree, and 3 + 20 = 23 seconds for the 30% that escalate. The slowest students wait 3 seconds longer than with the reasoning model alone, and the slow path sets the 95th-percentile wait.

Why plain answers in the first stage? Three step-by-step answers would cost ₹165 per 100, more than the reasoning model alone. The first stage only needs to be a cheap test of difficulty.

**The decision.** They chose the router: the same quality as the reasoning model within the noise, 20% cheaper, and 7 in 10 students get a result in 3 seconds instead of 20. For escalated problems the app shows "Checking your working carefully…" with a progress bar, because students accept a short wait when they can see something is happening. Homework that is checked overnight goes through a batch API instead, which OpenAI and Anthropic price at half the normal rate, as of November 2026.

They log every escalated problem as a new test case, and re-check the 97% figure monthly on fresh problems: the router is only as good as that number.

## Common mistakes

- **Using a reasoning model for everything.** Greetings, lookups and formatting do not need it. You pay for thinking that adds nothing.
- **Skipping the cheap step.** On a model that does not reason by itself, a step-by-step prompt often closes much of the gap at a fraction of the cost.
- **Adding step-by-step prompts to a reasoning model.** It already thinks. Set the effort level instead.
- **An output limit sized for no thinking.** Thinking counts toward it, so answers get cut off.
- **Voting on free-form text.** Two good paragraphs are never identical, so a vote finds nothing. Use a verifier or a judge instead.
- **Treating agreement as truth.** Samples from one model share its blind spots. Measure how often unanimous answers are right.
- **Trusting a weak verifier.** If the checker is easy to fool, best-of-N picks the answer that fools it best.
- **Trusting or showing raw reasoning.** It can leave out what really drove the answer, and it contains wrong turns. Check results, and show users the answer with a short, checked explanation.

## When more thinking is the wrong tool

- **The model lacks facts.** Thinking longer does not add knowledge. Use retrieval.
- **The task is simple or creative.** Short replies, summaries and tone changes rarely improve.
- **Latency matters more than a small gain.** A voice agent or autocomplete cannot wait ten seconds.
- **You cannot measure the gain.** Without a test set you will pay more and not know whether it helped.

## From demo to production

- **Route by difficulty.** Send easy questions down a fast path and escalate only when a check fails or samples disagree.
- **Cap the spend.** Set effort explicitly, set an output limit with room for thinking, and track thinking tokens and cost per request.
- **Show progress**, especially when thinking is hidden.
- **Re-run the effort sweep** when you change the model or its version, because the same level can behave differently.
