## What it is

A language model's basic job is to predict the next token. These metrics measure how well it does that on some text.

**Cross-entropy** is the average "surprise" of the model at each token that actually came next. If the model gave the true next token a probability of 0.9, it was barely surprised; if it gave 0.01, it was very surprised. Surprise is measured as the negative logarithm of the probability, so certain predictions cost almost nothing and confident mistakes cost a lot. Training a language model means lowering its cross-entropy on its training text; the "loss" you see falling in a training run is this number.

**Perplexity** is the exponential of cross-entropy. It turns an abstract number into an intuitive one: roughly, **how many equally likely options the model is choosing between at each step**. A perplexity of 4 means the model is, on average, as unsure as if it were picking between four equally likely next tokens. Lower is better.

Two related units appear in papers. **Bits** use log base 2 and **nats** use the natural logarithm; PyTorch and TensorFlow report nats. **Bits per character** and **bits per byte** divide the total by the length of the text instead of the number of tokens, which matters a great deal when comparing models, as you will see.

These ideas come from Claude Shannon's 1951 work on predicting English text. A model that predicts text well can also compress it well: a model at 3.4 bits per byte could, in principle, store text in less than half its original size.

```flow
title: From token probabilities to perplexity
Text -> Tokenize
Tokenize -> Model gives probability of each actual next token
Model gives probability of each actual next token -> Take minus log of each | surprise per token
Take minus log of each -> Average them | cross-entropy
Average them -> Exponentiate | perplexity
Average them -> Divide total by bytes of text | bits per byte, comparable across tokenizers
```

## How it works

**Computing it.** You need the probability the model gave to each actual next token. Many APIs return these as **logprobs**; with open models you get them directly.

```python
import math

def perplexity_from_logprobs(logprobs):
    """logprobs: natural-log probabilities of each actual next token."""
    cross_entropy = -sum(logprobs) / len(logprobs)    # nats per token
    return math.exp(cross_entropy), cross_entropy

def bits_per_byte(logprobs, text):
    total_bits = -sum(logprobs) / math.log(2)         # convert nats to bits
    return total_bits / len(text.encode("utf-8"))

# Example: three tokens predicted with probabilities 0.5, 0.25 and 0.8
lp = [math.log(0.5), math.log(0.25), math.log(0.8)]
print(perplexity_from_logprobs(lp))                   # perplexity about 2.15
```

With Hugging Face Transformers, passing the input as labels returns the cross-entropy loss directly, and `exp(loss)` is the perplexity. The primary resource shows a sliding-window version for long texts.

**What a value means depends on the text.**

- **Structured text** (HTML, code, forms) is more predictable, so perplexity is lower.
- **A bigger vocabulary** gives more options per step, so perplexity tends to be higher.
- **More context** helps prediction, so perplexity drops as the model sees more earlier text.
- **Text the model memorised** gets unusually low perplexity; **gibberish or unusual ideas** get very high perplexity.

**The comparison trap.** Perplexity is per token, and different models use different tokenizers. A tokenizer that splits Telugu into many tiny pieces makes each piece easier to predict, giving a lower per-token perplexity without the model being any better. To compare models on the same text, use **bits per byte** (or per character): the total surprise divided by the length of the text itself, which is the same for every model.

**Post-trained models.** Instruction tuning and preference tuning teach a model to be helpful, not to predict raw text. Chat models often have *higher* perplexity than their base models while being far more useful. Quantisation can also shift perplexity in unexpected ways. So perplexity is best for comparing **base models** on raw text, and for training curves, not for ranking chat assistants.

**Practical uses.**

- **Picking a base model for your domain.** Lower bits per byte on your held-out text means a better starting point for continued training or fine-tuning.
- **Watching training.** Validation loss (cross-entropy) shows learning, and a gap from training loss signals overfitting.
- **Detecting contamination.** Unusually low perplexity on benchmark questions suggests the model saw them in training.
- **Cleaning data.** Very high perplexity flags broken extractions, wrong languages or spam; very low perplexity flags near-duplicates of what the model already knows.

| Use | What to compare | Watch out for |
| --- | --- | --- |
| Choose a base model for your text | Bits per byte on held-out text | Different tokenizers make per-token numbers unfair |
| Monitor training | Training and validation loss | Units: nats in most frameworks |
| Spot contamination | Perplexity on test items versus similar unseen text | Some text is just easy to predict |
| Filter training data | Very high or very low perplexity outliers | Unusual but valid text also scores high |
| Rank chat assistants | Do not use perplexity | Post-training raises perplexity |

## A worked example

A legal-tech team in Hyderabad wants to continue training an open model on Telugu court judgements. They have three candidate base models and 2,000 held-out judgement paragraphs.

| Model | Reported perplexity (per token) | Tokens for the whole set | Bits per byte |
| --- | --- | --- | --- |
| A | 9 | 2.4 million | 1.77 |
| B | 14 | 1.1 million | 0.97 |
| C | 21 | 1.3 million | 1.33 |

The set is about 4.3 million bytes of text. The numbers are for illustration. On per-token perplexity, A looks best. But A's tokenizer splits Telugu into more than twice as many tokens as B's, making each token easier to guess. Once the total surprise is divided by the same number of bytes, B models Telugu legal text best, and its efficient tokenizer will also make training and use cheaper.

They also sort the paragraphs by perplexity. The 30 highest turn out to be garbled scans and a few pages in English; they fix the extraction before training. Finally, they test B on real tasks (summarising judgements, answering questions about them) before committing, because modelling text well is a signal, not a guarantee of task quality.

## Common mistakes

- **Comparing per-token perplexity across different tokenizers.** Use bits per byte or per character.
- **Mixing up bits and nats.** A loss of 2.0 nats is about 2.9 bits; perplexity is the same either way.
- **Ranking chat models by perplexity.** Post-training changes it in ways unrelated to usefulness.
- **Reading low perplexity as quality.** It can mean memorisation, or just very predictable text.
- **Using a different test set for each model.** Compare on exactly the same text.
- **Ignoring context length.** Models scored with longer context get lower perplexity.

## When you do not need these metrics

- **Using a hosted chat model through an API** for an application: judge it on task tests, not perplexity.
- **Comparing instruction-tuned assistants**: use evals on your tasks and side-by-side comparisons.
- **Small fine-tunes for classification**: accuracy, precision and recall say more.

## From demo to production

- **Track validation loss** in every training run, in one stated unit.
- **Keep a held-out domain set** and record bits per byte for each base model you consider.
- **Use perplexity filters in data pipelines** to catch broken or off-language text, and review a sample of what they flag.
- **Check new benchmark results for contamination** when a model's scores look too good.
