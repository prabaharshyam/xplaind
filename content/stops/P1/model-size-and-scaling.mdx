## What it is

Three numbers describe how big a language model is and how much went into it.

1. **Parameters**: the numbers inside the model that training adjusts. "Llama 3 8B" has about 8 billion. More parameters give a model more capacity to learn, and need more memory and compute to run.
2. **Training tokens**: how much text it learned from. Meta's Llama models went from 1.4 trillion tokens (Llama 1) to 2 trillion (Llama 2) to about 15 trillion (Llama 3).
3. **Training compute**: how many arithmetic operations training took, measured in FLOPs (floating-point operations). A common estimate is **6 × parameters × training tokens**.

A **scaling law** describes, from experiments, how quality improves as these grow. The striking finding is that the improvement is smooth and predictable, so labs can train small models, fit a curve, and forecast how a much larger one will do before spending the money.

```flow
title: What decides how good a model is
Compute budget -> Model size | parameters
Compute budget -> Training data | tokens, quality, variety
Model size -> Quality
Training data -> Quality
Model size -> Running cost | memory, speed per token
Quality -> Choose the smallest model that meets your bar
Running cost -> Choose the smallest model that meets your bar
```

## How it works

**Size and memory.** To run a model, its weights must fit in GPU memory: parameters times bytes per parameter. At 16-bit precision (2 bytes), a 7B model needs about 14 GB and a 70B model about 140 GB, before the KV cache and other overhead. Quantisation to 8 or 4 bits shrinks this, as the GPU lesson explains.

**Dense and sparse.** In a dense model every parameter is used for every token. A **mixture-of-experts** (MoE) model splits layers into "experts" and a small router picks a few for each token. Mixtral 8x7B has 46.7 billion parameters in total, but only about 12.9 billion are active for each token, so it runs at roughly the cost and speed of a 13B model while holding more knowledge. The memory to hold all the experts is still needed.

**The Chinchilla rule.** In 2022, DeepMind trained over 400 models of different sizes on different amounts of data and asked: for a fixed compute budget, what mix of size and data gives the best model? The answer: about **20 training tokens per parameter**, growing both together. Many earlier large models were undertrained: GPT-3 had 175 billion parameters but only 300 billion training tokens, under 2 per parameter. DeepMind's 70-billion-parameter Chinchilla, trained on 1.4 trillion tokens, beat much larger models.

**Beyond Chinchilla.** The rule optimises the cost of *training*. But a popular model is *used* millions of times, and a smaller model is cheaper to run. So labs now train small models far past 20 tokens per parameter: Llama 3 8B saw about 15 trillion tokens, nearly 1,900 per parameter. Training costs more, but every user's request costs less, and quality keeps improving with more data.

**Diminishing returns.** Quality follows a power law, so each step costs more than the last. In language modelling, cutting the training loss from about 3.4 to 2.8 needs around ten times more data. Moving from 90% to 95% on a task can cost far more than moving from 60% to 90%.

**Bottlenecks.** Two limits loom: good public text is running out, since training sets grow faster than new writing, and training runs need enormous amounts of electricity. This is one reason for interest in synthetic data, better data selection and more efficient models.

A quick calculator for planning:

```python
def weights_gb(params_billion, bytes_per_param=2):
    return params_billion * bytes_per_param           # 1B params x 2 bytes = 2 GB

def training_gpu_hours(params, tokens, gpu_flops=312e12, utilisation=0.4):
    flops = 6 * params * tokens                       # common estimate
    return flops / (gpu_flops * utilisation) / 3600

print(weights_gb(8))                                  # 16 GB at 16-bit
print(round(training_gpu_hours(1e9, 20e9)))           # 1B model, 20B tokens: about 267 GPU-hours
print(round(training_gpu_hours(8e9, 15e12)))          # 8B model, 15T tokens: about 1.6 million GPU-hours
```

The GPU speed here is one high-end data-centre GPU's peak at 16-bit precision; real utilisation is usually 30% to 50%.

| GPT-3 (2020) | 175 billion | 300 billion | 1.7 |
| Chinchilla (2022) | 70 billion | 1.4 trillion | 20 |
| Llama 2 70B (2023) | 70 billion | 2 trillion | 29 |
| Llama 3 8B (2024) | 8 billion | about 15 trillion | about 1,900 |

## A worked example

A startup in Bengaluru wants a model that writes well in Kannada. A founder proposes pre-training a 1-billion-parameter model from scratch on their own Kannada text.

They do the arithmetic:

1. **Data needed.** Chinchilla suggests about 20 billion tokens for 1B parameters. They have about 3 billion tokens of good Kannada text, and Kannada is only around 0.01% of a typical web crawl.
2. **Compute.** 6 × 1 billion × 20 billion = 1.2 × 10²⁰ operations, about 270 hours on one high-end GPU, or a day and a half on eight. Affordable.
3. **The real limit is data.** Training on 3 billion tokens repeated many times teaches less than fresh data, and a 1B model starts with no general knowledge at all.

They compare three plans on 200 real Kannada writing tasks:

| Plan | Quality score (out of 10, native reviewers) | Cost to build | Cost to run per 1,000 replies |
| --- | --- | --- | --- |
| 1B model pre-trained from scratch | 4.1 | High: data work plus compute | Very low |
| 8B open model, used as is | 6.2 | None | Low |
| 8B open model, continued training on their Kannada text | 7.6 | Moderate | Low |

The numbers are for illustration. Compute was never the bottleneck; data and the head start of an existing model were. They choose continued training of the open model.

## Common mistakes

- **Comparing parameter counts across generations.** A newer 8B model can beat an older 70B one.
- **Counting only total parameters for MoE models.** Speed and cost follow the active parameters; memory follows the total.
- **Forgetting the KV cache and overhead** when sizing GPUs from parameter counts.
- **Treating Chinchilla as the goal for a product model.** It optimises training cost; heavily used models train much longer.
- **Ignoring data quality.** The same number of tokens of better text gives a better model.
- **Pre-training from scratch without enough data.** Starting from an open model is usually far better.

## When bigger is not better

- **Narrow tasks** such as classification or extraction often reach the bar with small models.
- **High volume** makes the running cost of a large model dominate.
- **Latency budgets** favour smaller models, which write each token faster.
- **On-device or private deployments** may only fit small models.

## From demo to production

- **Start from the smallest model that might work**, and move up only when your test set says so.
- **Size hardware from total parameters, precision and the KV cache**, with headroom.
- **Revisit model choices regularly.** Newer small models keep closing the gap.
- **Plan data before compute** for any training project, and measure how much useful data you really have.
