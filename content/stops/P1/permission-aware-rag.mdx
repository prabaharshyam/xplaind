## What it is

A RAG system copies text from many sources into one index. Those sources had access rules: a SharePoint site open only to HR, a drive shared with one project team, a ticket visible to one customer's account manager. The index does not keep those rules unless you make it.

**Permission-aware RAG** (also called security trimming or document-level access control) ensures that retrieval only ever returns passages the asking user is allowed to see in the original system. If the user cannot open the document in SharePoint, the assistant cannot quote it.

```text
   INGESTION                                   QUERY
   SharePoint file + permissions               user signs in --> verified token: user, groups
        |                                                          |
        v                                                          v
   chunk text + allowed_groups: [hr-core, leadership]      search WITH filter:
              + allowed_users: [...]                       allowed_groups ∩ user groups ≠ ∅
              (missing? -> visible to nobody)              (inside the search, before ranking)
        |                                                          |
   rights re-synced every 10 minutes                       only permitted chunks --> model
```

This lesson follows an assistant at an asset management company in Mumbai over research notes, HR policies, board papers and client agreements.

## How it works

**Capture rights at ingestion.** When you index a document, also fetch who may read it: users and groups from the source system's permissions. Store them on every chunk as metadata, for example `allowed_groups: ["hr-core", "leadership"]`, `allowed_users: [...]`.

**Filter inside the search.** At query time, take the user's identity and groups from their verified sign-on token and add a filter: only chunks where `allowed_groups` overlaps the user's groups, or `allowed_users` contains them. The filter must run inside the vector or keyword search, before ranking, so restricted chunks never reach the candidate list. Filtering after retrieval leaks through scores, counts and timing, and can leave the user with no results.

**Deny by default.** A chunk with missing permission data is visible to nobody until fixed. Never treat "no rule" as "public".

**Keep rights in sync.** Permissions change daily: people join teams, files get shared, sites get locked. Re-sync rights on a schedule, or from change events, separately from content. Measure the lag and agree it with the client ("permission changes take effect within 15 minutes").

**Groups get large.** Users can be in hundreds of groups, nested inside each other. Resolve nested groups at sign-in or index time, and cache them sensibly.

**Alternative: check at the source.** For small result sets, you can retrieve candidates then ask the source system, as the user, whether they can open each document. This is always current but slower, and it still must happen before anything reaches the model.

**Test it.** Build test users with different roles and a set of "must not see" questions, and run them in CI.

**Where to enforce access:**

| Approach | How it works | Strengths | Weaknesses |
| --- | --- | --- | --- |
| Filter in the index | Permissions stored on chunks; filter in the search | Fast, scales | Needs permission sync; small lag |
| Check at source | Ask the source system per candidate | Always current | Slower; more calls |
| Separate indexes per group | One index for each audience | Simple for a few groups | Breaks down with many groups |
| Filter after retrieval | Drop restricted results at the end | None worth having | Leaks and empty results |

**Persona tests in CI.** Create test users for each role, such as analyst, HR staff, director and contractor, with known group memberships. For each, write questions with documents they must see and documents they must never see. Assert on the retrieved chunk ids, not on the model's answer, because the danger is a restricted chunk entering the prompt at all. Run these tests on every change to ingestion, search or the permission sync.

**Agreeing the sync window.** Permission changes cannot take effect instantly in an index. Measure the real lag, agree it with the client's security team in writing, and alert when a sync fails or runs late. For the most sensitive sources, such as board papers, consider checking at source as a second layer.

## A worked example

A Mumbai asset management company wants one assistant over research notes, HR policies, board papers and client agreements.

At ingestion, a connector reads each SharePoint file and its permissions, expands groups and stores `allowed_groups` on every chunk. At query time, the API reads the user's groups from their OIDC token and adds the filter to the hybrid search.

Testing with five personas:

- An analyst asks "What was discussed about the merger in the last board meeting?" Zero board-paper chunks are retrieved; the assistant says it found no accessible documents on that topic.
- A director asks the same question and gets an answer citing the board minutes.
- An analyst asks "What is the notice period for senior managers?" The HR policy, open to all employees, is retrieved; the confidential salary bands file is not.

During the pilot, the HR team restricts a draft policy. The permission sync runs every ten minutes, so for up to ten minutes the old rights apply. The client's security team accepts this window, in writing, and asks for an alert if a sync fails.

| Persona | Question | Result |
| --- | --- | --- |
| Analyst | "What was discussed about the merger at the last board meeting?" | No board-paper chunks; told no accessible documents found |
| Director | Same question | Answer citing the board minutes |
| Analyst | "Notice period for senior managers?" | HR policy retrieved; salary bands file not |

## Common mistakes

- **Filtering after retrieval.** Restricted chunks influence results and can leak. Filter inside the search.
- **Treating missing permissions as public.** Deny by default.
- **Syncing content but not rights.** A document locked down today stays visible in the index.
- **Trusting identity from the request body.** Take user and groups only from a verified token.
- **No negative tests.** Test what each persona must not see, not just what they should.

## Practise

Read Microsoft's security filter pattern and Pinecone's article on RAG with access control.

1. Add an `allowed_groups` field to every chunk in your RAG index, with at least three groups across your documents.
2. Read the user's groups from a (real or simulated) verified token and filter inside the search.
3. Write five "must not see" tests across three personas and run them in your test suite.

**You are done when you can** show two users asking the same question and getting different, correct answers, and a test proving a restricted document never reaches the model.
