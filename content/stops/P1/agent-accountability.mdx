## What it is

**Accountability** means that for any action an agent takes, someone can answer four questions. Who was responsible? What was the agent allowed to do? Why did it do what it did? How will a mistake be put right? Agents do not carry responsibility; people and organisations do.

Governance frameworks put this at the centre. The NIST AI Risk Management Framework's "govern" function asks for clear roles and responsibilities. The EU AI Act requires human oversight, record-keeping and named duties for providers and deployers of high-risk systems.

```flow
title: The accountability chain
Business owner | decides the scope, answers for results -> Agent card | purpose, tools, may do alone, needs approval, never, limits, evals
Technical owner | runs it, keeps records -> Agent card
Compliance reviewer | checks against the rules -> Agent card
Agent card -> Action -> Approval | who, when, what they saw
Approval -> Audit record | steps and versions
Complaint -> A person reviews the records -> Refund, fix or a new eval case -> Report
Audit record -> A person reviews the records
```

This lesson follows a motor-insurance renewal agent at an insurance broker in Delhi.

## How it works

**Name the owners.** For each agent: a business owner who decides what it may do and answers for its results, a technical owner who runs it, and a risk or compliance reviewer. Write their names in the agent's documentation.

**Document the scope.** A short "agent card": purpose, users, tools and permissions, actions it may take alone, actions needing approval, actions it must never take, known limits and the evals it passed. Review it when the agent changes.

**Approvals with identity.** When a person approves an action, record who, when and what they saw. Their approval is part of the accountability chain, so the approval screen must show enough to make a real decision.

**Records.** Audit logs that reconstruct every action: the request, the agent's steps, tool calls with arguments, approvals, and the versions of prompt, model and tools. Keep them for the agreed period.

**Disclosure.** Tell people when they are dealing with an agent, and when content or decisions were AI-assisted, as required by law or good practice.

**Redress.** A clear way for affected people to report a problem and reach a human, a process to investigate using the records, and a commitment to fix and to learn (add the case to the eval suite).

**Review.** Regularly look at what the agent did: samples of actions, overrides, complaints, incidents. Change its scope when evidence says so, in either direction.

**An agent card in practice:**

| Section | Example entry |
| --- | --- |
| Purpose | Renew motor policies: fetch quotes, recommend, purchase after confirmation |
| Users | Retail customers renewing in the app |
| Tools | get_vehicle, get_quotes, purchase_policy |
| May do alone | Fetch quotes, recommend with reasons |
| Needs approval | Purchase, only after explicit customer confirmation |
| Never | Change cover type or add-ons without confirmation |
| Known limits | Commercial vehicles not supported |
| Owners | Head of retail operations; platform lead; compliance officer |
| Last reviewed | 2026-10-01 |

**Testing the chain.** Pick one real action from last week. Using only documents and records, try to answer five questions: who asked, what the agent was allowed to do, what it did step by step, who approved and what they saw, and which versions were running. Time how long it takes. If any answer needs someone's memory, or takes more than an hour, fix the gap before a regulator or an unhappy customer finds it.

**Accountability for vendors.** When an agent uses a third-party model or tool, the contract should say who handles what: incident notification, data use, record retention and changes to the model. Your organisation still answers to customers, so the agent card names the vendor and what the contract covers.

**Keep the agent card next to the code.** Store it as a file in the repository and test it, so it cannot drift from what the agent really does:

```yaml
# agents/renewals.card.yaml
purpose: Renew motor policies after the customer confirms
owners: {business: Head of retail operations, technical: Platform lead, risk: Compliance officer}
tools:
  get_vehicle: {kind: read}
  get_quotes: {kind: read}
  purchase_policy: {kind: write, approval: customer_confirmation}
never: [change cover type without confirmation, add add-ons without confirmation]
last_reviewed: 2026-10-01
```

```python
import yaml
from datetime import date, timedelta
from agents.renewals import TOOLS          # the tool definitions the agent really uses

def test_card_matches_code():
    card = yaml.safe_load(open("agents/renewals.card.yaml"))
    assert set(card["tools"]) == {t["name"] for t in TOOLS}, "card and code list different tools"
    for name, spec in card["tools"].items():
        if spec["kind"] == "write":
            assert "approval" in spec, f"{name} writes but has no approval rule"

def test_card_reviewed_recently():
    card = yaml.safe_load(open("agents/renewals.card.yaml"))
    assert date.today() - card["last_reviewed"] < timedelta(days=180), "card review overdue"
```

Adding a tool without updating the card now fails the build, which forces the conversation with the owners.

**An audit record that answers the five questions.** One append-only table, written by the platform, never editable by the agent's service account:

```sql
CREATE TABLE agent_audit (
  id bigserial PRIMARY KEY,
  run_id text NOT NULL,
  at timestamptz NOT NULL DEFAULT now(),
  actor text NOT NULL,           -- the customer, the agent, or the approver's staff id
  kind text NOT NULL,            -- request, tool_call, approval, result
  detail jsonb NOT NULL,         -- tool name and arguments, what the approver saw, the outcome
  prompt_version text, model text, tool_versions jsonb
);
-- Reconstruct one run in order:
SELECT at AT TIME ZONE 'Asia/Kolkata', actor, kind, detail FROM agent_audit WHERE run_id = $1 ORDER BY at;
```

Grant the application role `INSERT` and `SELECT` only. Keep records for the period your sector requires, and export them to cheaper storage rather than deleting early.

**Sector expectations in India.** Regulators are setting out what they expect from AI in their sectors. The RBI, for example, has published a framework for responsible AI in financial services that stresses governance, named accountability and audit trails. Read the current guidance for your client's sector before design, not after launch.

**Responsibility does not move to the vendor.** If a model provider's update changes behaviour, your organisation still answers to the customer. That is why the card names the pinned model version and the evals it passed, and why model changes go through the same review as code changes.

**Try it in your browser.** Check an agent card against the tools the agent really has. Add a tool and run it.

```python
card = {"tools": {"get_vehicle": "read", "get_quotes": "read", "purchase_policy": "write"},
        "approvals": {"purchase_policy": "customer confirmation"}}
tools_in_code = ["get_vehicle", "get_quotes", "purchase_policy", "cancel_policy"]

missing = set(tools_in_code) - set(card["tools"])
if missing:
    print("tools missing from the card:", sorted(missing))
for name, kind in card["tools"].items():
    if kind == "write" and name not in card["approvals"]:
        print(f"{name} writes but has no approval rule")
print("check done")
```

## A worked example

A Delhi insurance broker deploys an agent that renews motor policies. It checks the vehicle's details, fetches quotes from three insurers and recommends one. After the customer confirms, it completes the purchase through the insurer's API.

The accountability set-up:

- **Owners**: the head of retail operations (business), the platform lead (technical), the compliance officer (review).
- **Agent card**: may fetch quotes and recommend; may purchase only after the customer explicitly confirms in the app; may never change cover type or add-ons without confirmation; must disclose that it is an automated assistant.
- **Records**: every quote, recommendation reason, confirmation message and purchase call, with versions.
- **Redress**: a "talk to a person" option on every screen; complaints reviewed weekly.

Three months in, a customer complains that zero-depreciation cover was dropped at renewal. The records show the agent recommended a cheaper quote without that add-on and the confirmation screen did not highlight the change. Accountability is clear: the design was at fault, not the customer. The broker refunds the difference, changes the confirmation screen to highlight any cover change, adds a rule that cover changes need explicit consent, and adds ten such cases to the evals. The compliance officer's report to the board includes the incident and the fix.

| Step after the complaint | What the broker did |
| --- | --- |
| Investigation | Records showed a cheaper quote recommended without the add-on |
| Finding | The confirmation screen did not highlight the cover change |
| Redress | Refunded the difference to the customer |
| Fix | Cover changes highlighted; explicit consent required |
| Learning | Ten such cases added to the evals; incident reported to the board |

## Common mistakes

- **No named owner.** "The AI team" cannot answer for outcomes.
- **Scope only in people's heads.** Write the agent card and keep it current.
- **Approvals without context.** People approving blind are not providing oversight.
- **Records you cannot query.** Investigations need answers in hours.
- **No route for affected people.** Harm with no way to report it becomes a public complaint.
- **An agent card that lives in a slide deck.** Keep it in the repository and test it.
- **Audit tables the agent's service can edit or delete.**
- **No versions on audit records.** You cannot say which prompt or model made a decision.

## When a lighter process is enough

- **Internal read-only assistants**, such as a policy search for staff: a named owner, a short card and ordinary logs suffice.
- **Prototypes** that never touch real customers or systems.
- **Personal productivity tools** used by one person on their own data.

Full cards, approval identity, append-only audits and redress paths become necessary once an agent acts for customers, handles money or personal data, or works in a regulated sector.

## From demo to production

- **Test the card in CI** against the agent's real tools, and fail on overdue reviews.
- **Write audits to append-only storage** with run ids and versions.
- **Run the five-question drill** on one real action each month and time it.
- **Track redress cases** to closure, and add each to the eval suite.
- **Review scope quarterly** with the business owner, with numbers on actions, overrides and complaints.
