## What it is

An ML engineer interview loop is a set of rounds, each testing one skill. You pass by being solid in every round, not brilliant in one. Strong ML people can fail on the round they did not prepare for, such as DSA coding.

| Round | What is tested | What a strong candidate shows |
| --- | --- | --- |
| Online assessment or DSA coding | Data structures and algorithms in a timed problem | A correct, tested solution and its time and space complexity |
| ML coding | Pandas, NumPy, a metric or a small algorithm from scratch | Clean code that handles edge cases such as ties and empty inputs |
| ML fundamentals | How models, losses, metrics and validation work | The mechanism, the trade-off and a default choice |
| ML system design | Turning a vague business problem into a deployed system | A clear structure, numbers said aloud, production thinking |
| LLM or GenAI design | RAG, evals, prompting versus fine-tuning, cost and latency | Measurement first, then the simplest design that meets it |
| Project deep-dive | One project of yours, in depth | Numbers, decisions, mistakes and what you would change |
| Behavioural or hiring manager | Ownership, conflict, failure | Short STAR stories with real numbers |

The mix varies. Some candidate reports for ML roles at large product companies, such as Google and Meta, describe standard algorithm coding rounds next to ML design and behavioural rounds. Some companies use a take-home or a practical ML coding task instead. So ask the recruiter for the list of rounds; they expect the question.

```flow
title: ML system design in 40 minutes
1 Goal and metric -> 2 Framing and label -> 3 Data -> 4 Features | about 15 min
4 Features -> 5 Baseline, then a model -> 6 Evaluation | offline and A/B, about 12 min
6 Evaluation -> 7 Serving | batch or real time, with a fallback -> 8 Monitoring | about 8 min
8 Monitoring -> 9 Risks | fairness, abuse, failure; about 5 min
```

Below, each round in turn, then a full answer to "design fraud detection for UPI merchant payments".

## How it works

### The DSA round

This round is often the same as for software engineers. Do not expect easier problems because the role is ML, and know that this round alone can sink a loop. Some candidate reports for big-tech ML roles mention medium and sometimes hard problems.

**What is tested.** Learn these patterns, not memorised answers.

- Arrays and strings with hash maps, two pointers and sliding windows.
- Sorting, binary search and intervals (merge, overlap).
- Stacks, queues and heaps (top k, running median).
- Trees and graphs: BFS, DFS, shortest paths, topological sort.
- Dynamic programming at a basic level (one and two dimensions).

**Work through it out loud.** Interviewers score the process, not only the code.

1. Restate the problem and ask about inputs, sizes and edge cases.
2. Work a small example by hand.
3. State a brute-force solution and its cost.
4. Improve it, and say why the new idea works.
5. Code it with clear names.
6. Test it on your example and one edge case, then state time and space complexity.

ML interviewers may dress a DSA problem in data terms. For example: "Given UPI payments as `(merchant_id, timestamp)` pairs in time order, flag merchants with more than `k` payments inside any 60-second window." This is a sliding window with a hash map:

```python
from collections import defaultdict, deque

def flag_bursts(events, k, window_s):
    """events: (merchant_id, unix_seconds) sorted by time.
    Return merchants with more than k payments inside any window_s seconds."""
    recent = defaultdict(deque)          # merchant -> timestamps still in the window
    flagged = set()
    for merchant, t in events:
        q = recent[merchant]
        q.append(t)
        while q[0] <= t - window_s:      # drop payments older than the window
            q.popleft()
        if len(q) > k:
            flagged.add(merchant)
    return flagged

events = [("m1", 0), ("m2", 5), ("m1", 10), ("m1", 20), ("m1", 70), ("m2", 80)]
print(flag_bursts(events, k=2, window_s=60))   # {'m1'}
```

Each timestamp enters and leaves its queue at most once, so time is O(n) for n events. Then name the follow-up risk: memory grows with every merchant ever seen, because idle merchants' queues are never removed.

**Preparation.** Practise in Python with `collections`, `heapq` and `bisect`. Solve a few problems per pattern and redo failures a week later, in timed mocks where you talk throughout. Thinking aloud is a separate skill from solving silently, and it is the one tested.

### The ML coding round

Here you write data code, not puzzles: a pandas groupby, join or rolling window; a split by time; a metric from scratch; k-means or logistic regression in NumPy. This example combines two favourites, a time split that respects label delay and precision and recall at k.

```python
import numpy as np
import pandas as pd

def split_with_gap(df, test_start, test_end, delay_days, labels_pulled_on):
    delay = pd.Timedelta(days=delay_days)
    test_start, test_end = pd.Timestamp(test_start), pd.Timestamp(test_end)
    # Test labels must have matured too, or late fraud looks like "not fraud".
    assert test_end + delay <= pd.Timestamp(labels_pulled_on), "test labels not mature"
    train = df[df["txn_time"] < test_start - delay]   # what you could know on test_start
    test = df[(df["txn_time"] >= test_start) & (df["txn_time"] < test_end)]
    return train, test

def precision_recall_at_k(y_true, scores, k):
    y_true = np.asarray(y_true)
    top_k = np.argsort(-np.asarray(scores))[:k]     # the k highest scores
    caught = y_true[top_k].sum()
    return caught / k, caught / y_true.sum()

df = pd.DataFrame({"txn_time": pd.date_range("2026-01-01", "2026-06-30", freq="D")})
train, test = split_with_gap(df, "2026-05-01", "2026-06-01", 60, "2026-08-01")
print(train["txn_time"].max().date(), len(train), len(test))   # 2026-03-01 60 31

y = [1, 0, 0, 1, 0, 0, 0, 1, 0, 0]
s = [0.9, 0.8, 0.1, 0.7, 0.3, 0.2, 0.6, 0.4, 0.05, 0.15]
p, r = precision_recall_at_k(y, s, 3)
print(round(p, 2), round(r, 2))   # 0.67 0.67
```

Why the gap? Suppose fraud labels take up to 60 days to arrive. A model deployed on 1 May could only have been trained on transactions with final labels, which means those before about 2 March. Training on March and April rows with labels pulled later uses knowledge you would not have had, so the test score is too optimistic. In a real retraining job, rows newer than the delay are unlabelled, not negatives. Saying this unprompted is a strong signal.

### ML fundamentals: answer with mechanism, trade-off and default

A strong answer gives the mechanism, the trade-off and your default choice. Two model answers:

**"How do random forests and gradient boosting differ?"** "Both combine many decision trees. A random forest trains deep trees independently, each on a bootstrap sample, choosing from a random subset of features at every split, and averages them. That mainly reduces variance, so it needs little tuning and rarely overfits badly. Gradient boosting trains shallow trees one after another, each fitting the errors of the trees so far. That reduces bias and usually wins on tabular data, but it can overfit, so I tune the learning rate and depth and use early stopping. My default for tabular data is boosting, for example LightGBM or XGBoost, with a random forest as a quick baseline."

**"How would you detect data leakage?"** "Leakage means the model sees information it will not have at prediction time. My first signal is a score that is too good for the problem. Then I check three places. Features: is a top feature recorded after the outcome, such as `refund_issued` in a churn model? The split: are the same customer or near-duplicate rows in both train and test, or does training data come after test data? Preprocessing: was scaling or target encoding fitted on all the data? The fix is to compute every feature as of prediction time, split by time or by customer, and fit preprocessing on training data only."

Each names a mechanism, a concrete example and a decision; none recites a definition. Prepare the same shape for these topics.

| Topic | The core of a good answer |
| --- | --- |
| Bias and variance | Training and validation error both high means underfitting; a large gap between them means overfitting. Read it from learning curves |
| Regularisation | L2 shrinks all weights; L1 pushes some to exactly zero, which selects features. Both trade a little bias for less variance |
| Imbalanced data | Accuracy misleads. Use PR AUC, and precision and recall at the threshold or capacity the business can act on |
| Cross-validation | K-fold for independent rows; time-based or grouped folds when rows are ordered in time or share a customer |
| Logistic regression | A linear score passed through a sigmoid, trained with log loss. Fast, explainable, a strong baseline |
| Attention | Each token's query is compared with every token's key; the softmax of the scores weights their values |

The I1 lessons "Cross-validation and leakage" and "Choosing a metric" go deeper on the most asked topics.

### ML system design

Use the nine steps in the diagram, in order, and say numbers out loud. Three steps need the most care. In *framing*, say where the label comes from and how late it arrives. In *evaluation*, choose a split that matches reality and a metric at the operating point, by segment. In *serving*, give the latency budget and a fallback.

**Offline versus online.** A better offline score does not guarantee a better business result, because live users react to the model. Plan an A/B test with one primary metric and guardrails, such as complaint rate or latency. Know the pitfalls. Stopping as soon as the result looks significant ("peeking") inflates false wins. A test shorter than a full week misses weekday and weekend patterns. And a model that blocks or hides things stops you seeing what would have happened, so keep a small random holdout.

**Handling "why not X?".** Answer with the trade-off. For example: "A deep model could help, but with tabular features and late labels, gradient boosting usually gives similar accuracy, trains in minutes and is easier to explain to the risk team. I would try a deep model if error analysis showed patterns the trees miss."

### LLM and GenAI design questions

Some ML loops now include a question about a product built on a large language model, for example:

- "Design an assistant that answers customer questions from a bank's policy documents, in English and Hindi."
- "Should we use prompting, RAG or fine-tuning to sort support tickets into 40 categories?"

Clarify the goal and the cost of a wrong answer, then choose the simplest approach that could work: RAG when answers must come from documents that change and need citations; prompting with a few examples when the task is simple; fine-tuning a small model when volume is high and cost or latency matter. For ticket sorting with lots of labelled history, also offer a classic classifier as the baseline. Then put measurement first: an eval set of real questions, retrieval scored separately from answers, and a plan for when nothing relevant is found. Finish with cost and latency per query, privacy and a human fallback. The lessons "Build a RAG app", "Test sets and evals", "Prompting, RAG or fine-tuning" and "The design interview" cover each part.

### Project deep-dive and behavioural

**Project deep-dive.** Prepare one or two projects in depth: problem, data, baseline, what you tried, results with numbers, what went wrong, what next. Be clear about what you did yourself in a team project.

**Behavioural.** Use STAR (situation, task, action, result), with numbers and a lesson. An illustrative failure story (use your own real one):

- *Situation*: "My lead-scoring model for an insurance sales team in Pune went live. In two weeks, conversion on top-scored leads fell from about 9% in testing to about 4%."
- *Task*: "I owned the model and had to find the cause fast."
- *Action*: "I compared training and live feature values. A 'last call outcome' field was filled in after the call in the training data but blank at scoring time. That was leakage. I rebuilt features as of scoring time and added a pre-launch check comparing training and live features."
- *Result*: "Offline AUC fell from 0.91 to 0.78, but live conversion on top leads recovered to about 7%. Now I check that every feature exists at prediction time before training."

### How interviewers score you

Score your recorded practice answers against this list. The weak column holds common no-hire signals.

| They listen for | Weak | Strong |
| --- | --- | --- |
| Clarifying questions | Starts designing at once | Asks about goal, scale and constraints first |
| Label | Assumes labels exist | Says where labels come from and how late |
| Metric | "Accuracy" | A metric at the operating point, tied to the business metric |
| Baseline | Starts with a large model | Rules or a linear model first, complexity justified |
| Split | Random split | Time or group split, with a gap for label delay |
| Serving | Not mentioned | Batch or real time, latency budget, fallback |
| Monitoring | "Retrain sometimes" | Drift checks, feedback loops, a holdout, a retrain trigger |
| Communication | Long silences, no structure | Signposts each step and states numbers |

## A worked example

Question: "Design a system to detect fraudulent UPI merchant payments for a payments company." The numbers below are assumptions you would state in the interview, not real figures.

1. **Goal**: cut fraud losses with limited analyst time. Ask about latency; suppose the payment flow allows about 100 ms to block, plus a review queue.
2. **Framing**: binary classification per payment. Labels come from chargebacks and confirmed investigations. Assume they arrive within 60 days.
3. **Data**: payments, merchant profiles, device and network signals, past fraud. Fraud is rare; assume 0.05% of payments.
4. **Features**: payments per merchant in the last hour, amount compared with the merchant's usual amounts, new device, time of day, merchant category. All computed as of payment time from a feature store, so training and serving match.
5. **Model**: a rules baseline, then gradient-boosted trees with class weights. Later, graph features linking merchants, devices and accounts.
6. **Evaluation**: a time split with a 60-day gap, as in the code above. Measure PR AUC and precision and recall at the alert volume analysts can handle, by merchant category and region. Then run an A/B test on a share of traffic.
7. **Serving**: real-time scoring with a fallback to rules if the model times out. Two thresholds: auto-block above a very high score, review queue below it.
8. **Monitoring**: drift on key features, changes in alert rate, and monthly retraining. Blocked payments never reveal whether they were fraud, so send a small random sample of would-be blocks to analysts instead.
9. **Risks**: blocking genuine small merchants (give an appeal route), fraudsters adapting (retrain often), uneven error rates across regions.

Now say the numbers out loud. They show why accuracy is the wrong metric.

| Quantity (assumed) | Value |
| --- | --- |
| Payments per day | 20 lakh |
| Fraud rate | 0.05%, so 1,000 frauds a day |
| Accuracy of "never fraud" | 99.95%, with zero fraud caught |
| Alerts analysts can review | 2,000 a day |
| Frauds in the top 2,000 alerts (example) | 600 |
| Precision at 2,000 | 600 / 2,000 = 30% |
| Recall at 2,000 | 600 / 1,000 = 60% |

Then ask: "Is catching 60% of fraud at 30% precision worth the analyst cost, and would 500 more reviews a day pay for themselves?" That turns a model into a business decision.

## Common mistakes

- **Skipping DSA preparation.** Some candidate reports describe ML loops at large product companies with a standard coding round, and it can sink a strong ML candidate.
- **Jumping to deep learning.** Start with a baseline and justify each step up in complexity.
- **Ignoring the label.** Where labels come from and how late they arrive shapes the data, the split, the metric and retraining.
- **Random or gap-free splits for time-based problems.** Both leak future information and inflate scores.
- **Quoting accuracy on imbalanced data.** State precision and recall at the capacity the business can act on.
- **Treating an offline win as a launch.** Plan the A/B test, the guardrails and the holdout.
- **No serving or monitoring plan.** Say the latency budget, the fallback and what triggers retraining.
- **Shallow project stories.** Know your numbers, your own contribution and your mistakes.

## Practice

Read Chip Huyen's ML systems design notes and her ML interviews book; use the Tech Interview Handbook for behavioural rounds.

1. **DSA**: solve a few medium problems per pattern in Python, out loud and timed.
2. **ML coding**: without notes, write a time split with a label-delay gap, precision and recall at k, and k-means in NumPy. Test each on a tiny example.
3. **Fundamentals**: write 60 to 90 word answers to ten questions in the mechanism, trade-off and default shape, each with an Indian example.
4. **System design**: answer two unseen questions in 40 minutes each with the nine steps, recorded. For example, demand forecasting for a Hyderabad grocery chain, or ranking for a jobs app. Score yourself with the table.
5. **GenAI**: answer the bank assistant question and say exactly how you would build its eval set.
6. **Deep-dive and behavioural**: prepare one project deep-dive and three STAR stories, including one about a failure.

**You are done when you can** solve a medium DSA problem in 30 minutes while talking, and design an unseen ML system in 40 minutes with a clear label, an honest split, a metric at the operating point, serving and monitoring.
