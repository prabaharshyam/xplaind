## What it is

Typical ML engineer loops include:

- **ML fundamentals**: bias and variance, overfitting, regularisation, metrics, cross-validation, how specific models work (trees, logistic regression, neural networks, transformers).
- **Coding**: data manipulation in Python and pandas, implementing a simple algorithm, sometimes standard data-structure problems.
- **ML system design**: "Design a fraud detection system for UPI payments", "Design recommendations for a grocery app".
- **Case or project deep-dive**: walking through a project you built, with follow-up questions on choices and results.
- **Behavioural**: ownership, collaboration, dealing with failure.

```text
   ML SYSTEM DESIGN IN 40 MINUTES
   [1 goal + metric] -> [2 framing + label] -> [3 data] -> [4 features]      ~15 min
          -> [5 baseline, then model] -> [6 evaluation: offline + A/B]        ~12 min
          -> [7 serving: batch or real-time, fallback] -> [8 monitoring]      ~8 min
          -> [9 risks: fairness, abuse, failure]                              ~5 min

   say numbers out loud: latency budget, label delay, class balance, alert capacity
```

This lesson follows a model answer to "design fraud detection for UPI merchant transactions", a common question at Indian payments companies.

## How it works

**Fundamentals.** Be able to explain, in plain words and with an example:

- the bias-variance trade-off and how to diagnose underfitting versus overfitting from learning curves;
- why accuracy fails on imbalanced data and what to use instead;
- how gradient boosting and random forests differ;
- what leakage is and how you would find it;
- how attention works, at a high level.

**A structure for ML system design.**

1. *Clarify the goal* and the business metric; constraints (latency, scale, regulation).
2. *Frame the ML problem*: what is predicted, for whom, when; the label and how it is obtained.
3. *Data*: sources, labels, volume, freshness, biases, privacy.
4. *Features*: key groups, computed as of prediction time.
5. *Model*: a simple baseline first, then a stronger model with reasons.
6. *Evaluation*: offline metrics, splits that match reality, segments; online A/B test and guardrails.
7. *Serving*: batch or real-time, latency budget, fallback.
8. *Monitoring and iteration*: drift, feedback loops, retraining.
9. *Risks*: fairness, abuse, failure modes.

**Project deep-dives.** Prepare one or two projects in depth: problem, data, baseline, what you tried, results with numbers, what went wrong, what you would do next. Expect "why not X?" questions.

**Coding.** Practise pandas groupbys, joins and window-style calculations, writing a train-validation split by time, and implementing simple metrics or k-means from scratch.

**Behavioural.** STAR stories with numbers, as for any engineering role.

**Fundamentals that come up most:**

| Topic | What to be able to say |
| --- | --- |
| Bias and variance | How learning curves show underfitting versus overfitting, and what fixes each |
| Imbalanced data | Why accuracy misleads; PR AUC, precision and recall at a threshold |
| Trees | How random forests and gradient boosting differ |
| Leakage | What it is, how to spot a too-good score, how to fix splits and features |
| Attention | Queries, keys and values at a high level |

**Practising out loud.** System design is a speaking skill. Set a 40-minute timer, pick an unseen question, and talk through all nine steps while drawing a simple diagram. Record yourself, then listen for gaps: did you define the label, state a latency budget, name a baseline, choose a split that matches time, and say how you would monitor? Do this with a friend once a week and swap roles, because playing the interviewer shows you what a clear answer sounds like.

**Handling "why not X?".** Interviewers push on choices. Answer with the trade-off: "A deep model could help, but with tabular features and label delays, gradient boosting gives similar accuracy, trains in minutes and is easier to explain to the risk team. I would try it after the baseline if the error analysis showed patterns the trees miss."

## A worked example

Question: "Design a system to detect fraudulent UPI merchant transactions for a payments company."

A strong outline:

1. *Goal*: reduce fraud losses with limited analyst capacity; real-time decision under 100 ms for blocking, plus a review queue.
2. *Framing*: binary classification per transaction; labels from chargebacks and confirmed investigations, arriving 30 to 60 days later.
3. *Data*: transactions, merchant profiles, device and network signals, past fraud; heavy imbalance (about 0.1% to 0.3%).
4. *Features*: velocity (transactions per merchant per hour), amount relative to merchant history, new device, time of day, merchant category; all computed as of transaction time from a feature store.
5. *Model*: rules baseline; gradient-boosted trees with class weights; later, graph features linking merchants and devices.
6. *Evaluation*: time-based split; PR AUC; recall at the alert volume analysts can handle; by merchant category and region; A/B test on a share of traffic.
7. *Serving*: real-time scoring with a fallback to rules; two thresholds (auto-block at very high precision, review queue below).
8. *Monitoring*: drift on key features, alert-rate changes, feedback loop from blocked transactions (random holdout), monthly retraining.
9. *Risks*: blocking genuine small merchants (appeal route), adversaries adapting (frequent retraining), fairness across regions.

| Step | Key point in the fraud answer |
| --- | --- |
| Goal | Under 100 ms to block, plus a review queue sized to analysts |
| Label | Chargebacks and investigations, 30 to 60 days late |
| Model | Rules baseline, then boosted trees with class weights |
| Evaluation | Time split; recall at the alert volume analysts can handle |
| Monitoring | Drift, alert rates, random holdout for blocked transactions |

## Common mistakes

- **Jumping to deep learning.** Start with a baseline and justify complexity.
- **Ignoring the label.** Where labels come from and how late they arrive shapes everything.
- **Random splits for time-based problems.**
- **No serving or monitoring plan.** Interviewers want production thinking.
- **Shallow project stories.** Know your numbers and your mistakes.

## Practise

Read Chip Huyen's machine learning systems design notes and her ML interviews book; use the Tech Interview Handbook for behavioural rounds.

1. Write one-paragraph plain-language answers to ten fundamentals questions, with an Indian example each.
2. Answer two ML system design questions out loud in 40 minutes each with the nine-step structure (for example, demand forecasting for a grocery chain, ranking for a jobs app).
3. Prepare a deep-dive on one of your projects: numbers, decisions, mistakes and next steps.

**You are done when you can** design an unseen ML system in 40 minutes with clear framing, evaluation, serving and monitoring.
