## What it is

A **deployment model** answers two questions: where do the model and the application run, and who controls them? The main options, from least to most control:

1. **Vendor API (multi-tenant SaaS)**: you call the model provider's public endpoint. Fastest to start, newest models, least control.
2. **Model through the client's cloud**: the same or similar models offered inside the client's own cloud account and region (Amazon Bedrock, Azure AI Foundry, Google Vertex AI), under the cloud contract they already have.
3. **Dedicated or private capacity**: reserved capacity or a private endpoint, sometimes with private networking so traffic never crosses the public internet.
4. **Self-hosted open-weight models in the client's cloud**: you run models such as Llama, Qwen, Mistral or Gemma variants on GPU machines in their account.
5. **On-premises**: the same, in the client's own data centre.
6. **Air-gapped**: no connection to outside networks at all. Models, code and updates arrive by controlled transfer.

The application (API, retrieval, database) can follow the same choices independently of the model.

```flow
dir: LR
title: From less control and a faster start, to more control and more work
Vendor API | weeks -> Client's cloud | approved tenancy and region
Client's cloud -> Dedicated | private network
Dedicated -> Self-hosted | their GPUs, you operate
Self-hosted -> On-prem | their data centre
On-prem -> Air-gapped | no network, transfers only
```

The app, retrieval and logs can sit on a different rung from the model.

This lesson follows three clients, in Bengaluru, Mumbai and Hyderabad, who each needed a different deployment.

## How it works

**What drives the choice.**

- *Data rules*: regulation, contracts and internal policy on where data may go. Indian regulators and many enterprises require data to stay in India; some data may not leave the premises at all.
- *Model quality needed*: the strongest models are usually available only as APIs or through cloud partners. Open-weight models are close behind for many tasks and fine for extraction, classification and RAG over well-scoped documents.
- *Cost and volume*: APIs charge per token; self-hosting has a large fixed GPU cost that pays off only at high, steady volume.
- *Skills*: self-hosting needs people who can run GPUs, serving engines, monitoring and upgrades.
- *Latency and availability*: on-premises may cut network delay but puts uptime on the client's team.

**Questions to ask early.** Where may data be processed? Is any provider already approved? Is there an existing cloud contract? Who will operate the system after handover? What happens when the model needs upgrading?

**Hybrid is common.** Route sensitive requests to a self-hosted model and others to an API; or use a self-hosted model for embeddings and a cloud model for generation.

**Air-gapped specifics.** No package downloads, no model downloads, no SaaS monitoring, no license checks over the internet. Everything (container images, model weights, Python packages) is bundled, scanned and transferred. Plan updates as scheduled releases.

**Scoring the options:**

| Factor | Vendor API | Client's cloud | Self-hosted | Air-gapped |
| --- | --- | --- | --- | --- |
| Data control | Lowest | High, in their tenancy | Very high | Total |
| Model quality | Strongest | Strong | Good open-weight | Good open-weight |
| Cost at low volume | Lowest | Low | High: idle GPUs | Highest |
| Time to launch | Days to weeks | Weeks | Months | Months |
| Skills needed | Few | Cloud skills | GPU serving, monitoring | All of that, offline |

**The first-meeting questions.** Where may this data be processed, and is any provider already approved? Is there an existing cloud contract and region? Which data, if any, may never leave the premises? Who will run the system after handover, and do they have GPU skills? How often will the model need upgrading, and who approves that? The answers usually narrow six options to one or two within the hour.

**Bill of materials for offline sites.** For an air-gapped build, list every artefact: container images with pinned versions, model weights with checksums, Python and system packages, the vector database, monitoring tools that work offline, and documentation. The client's security team scans and transfers them. Missing one package can delay a release by weeks, so rehearse the install on a disconnected test machine first.

**API or self-hosted, in numbers.** A first comparison you can redo with real quotes (record the date of each price):

```python
def monthly_costs(tokens_in_m, tokens_out_m, api_in_usd, api_out_usd,
                  gpu_hour_inr, gpus, hours=730, ops_people=0.5, ops_cost_inr=250_000, usd_to_inr=84):
    """tokens in millions per month; API prices in USD per million tokens."""
    api = (tokens_in_m * api_in_usd + tokens_out_m * api_out_usd) * usd_to_inr
    self_host = gpu_hour_inr * gpus * hours + ops_people * ops_cost_inr
    return {"API ₹/month": round(api), "self-hosted ₹/month": round(self_host),
            "cheaper": "API" if api < self_host else "self-hosted"}

print(monthly_costs(tokens_in_m=900, tokens_out_m=120, api_in_usd=0.8, api_out_usd=4,
                    gpu_hour_inr=250, gpus=2))
```

GPUs cost money every hour whether used or not, so self-hosting wins only at high, steady volume, or when data rules leave no choice. Include the people: someone has to patch, monitor and upgrade the serving stack.

**Route by sensitivity.** In a hybrid design, a small rule decides where each request goes:

```python
SENSITIVE_FIELDS = {"aadhaar", "pan", "medical_history", "bank_account"}

def route(request):
    if request.get("classification") == "restricted" or SENSITIVE_FIELDS & set(request.get("fields", [])):
        return "self_hosted"            # stays on the client's servers
    return "cloud_model"                # stronger model, client's cloud region
```

Write the rule with the client's data owner, test it with examples from each data class, and log the route for every request.

**Building an air-gapped bundle.** On a connected build machine, gather everything with versions and checksums, then transfer through the client's approved process:

```bash
mkdir -p bundle/{images,models,wheels}
docker pull vllm/vllm-openai:v0.10.1 && docker save vllm/vllm-openai:v0.10.1 | gzip > bundle/images/vllm.tar.gz
docker save claims-api:1.4.0 | gzip > bundle/images/claims-api.tar.gz
huggingface-cli download org/model-8b-instruct --revision <commit> --local-dir bundle/models/model-8b
pip download -r requirements.txt -d bundle/wheels
(cd bundle && find . -type f -exec sha256sum {} \; > SHA256SUMS)
```

On the offline side, `sha256sum -c SHA256SUMS` proves nothing changed in transit, `docker load` restores images, and `pip install --no-index --find-links wheels -r requirements.txt` installs without the internet. Rehearse the whole install on a machine with networking disabled before the real visit.

**Plan upgrades from the start.** Every option needs a path for new model versions: an API changes by itself (pin and test), the client's cloud adds models on its own schedule, and self-hosted or offline setups need a repeatable bundle-and-test process.

## A worked example

Three clients, three answers:

- *A Bengaluru D2C brand*: customer-support assistant, public-facing data only, small team. **Vendor API** through a gateway, Indian region where available. Live in three weeks.
- *A Mumbai private bank*: internal policy assistant with confidential documents. The bank's risk team has already approved its Azure tenancy in Central India. **Models through the client's cloud**, with private networking and the bank's keys. The approval took four weeks instead of six months because nothing new had to be approved.
- *A Hyderabad defence electronics supplier*: engineering-document search on a classified network. **Air-gapped self-hosting**: an open-weight model served with vLLM on two on-premises GPU servers, embeddings and the vector database on the same network, and a quarterly update package of images and weights scanned and transferred by the client's security team. The model is less capable than frontier APIs, so the scope is narrowed to retrieval and summarisation, where evals show it performs well.

| Client | Deployment | Why | Outcome |
| --- | --- | --- | --- |
| Bengaluru D2C brand | Vendor API through a gateway | Public data, small team | Live in three weeks |
| Mumbai private bank | Models in its approved Azure tenancy | Confidential documents, existing approval | Approved in four weeks |
| Hyderabad defence supplier | Air-gapped vLLM on local GPUs | Classified network | Scope narrowed to retrieval and summaries |

## Common mistakes

- **Proposing a public API before asking about data rules.** You lose weeks and credibility.
- **Assuming self-hosting is cheaper.** At low volume, idle GPUs cost far more than tokens.
- **Ignoring who operates it.** A self-hosted model nobody at the client can upgrade becomes a liability.
- **Treating "open-weight" as "no licence terms".** Read each model's licence for commercial use limits.
- **Forgetting the rest of the stack.** Traces, logs and vector stores must follow the same rules as the model.
- **Comparing GPU cost with API cost** without counting idle hours and the people to run it.
- **Air-gapped installs never rehearsed offline**, which fail on the first missing package.
- **No upgrade path** for models in self-hosted or offline setups.

## When the choice is simple

- **Low or uncertain volume and no strict data rules**: start with an API or the client's cloud model service.
- **Data may never leave the premises**: self-hosted or air-gapped, whatever the cost.
- **A pilot to prove value**: use the fastest option allowed, and revisit before scaling.

## From demo to production

- **Record the data rules and the decision** with dates and the people who agreed.
- **Redo the cost comparison** with real volumes after the first months.
- **Log the route** for every request in hybrid setups.
- **Keep a tested bundle process** for offline and self-hosted upgrades.
- **Pin and test model versions** whichever option you choose.
