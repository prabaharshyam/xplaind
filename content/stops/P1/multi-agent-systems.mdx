## What it is

A **multi-agent system** splits a task across several agents, each with its own instructions, tools and context. Three patterns cover most real designs:

- **Supervisor and workers**: a lead agent plans, delegates sub-tasks to worker agents (often as tools it can call) and combines their results.
- **Hand-offs**: one agent handles a conversation until it reaches something outside its role, then passes control, with the context, to a specialist agent. Common in customer service: a front-desk agent hands billing questions to a billing agent.
- **Generator and reviewer**: one agent produces work; another checks it against criteria and sends it back with feedback.

The earlier lesson on sub-agents explained why splitting helps: clean contexts, specialised tools, parallel work. This lesson is about choosing and running the patterns.

```flow
title: Supervisor + workers: parallel, summaries back to the lead

```

```flow
dir: LR
title: Hand-offs: pass a summary and the last turns; at most 2 hand-offs, then a person

```

```flow

Writer -[draft]-> Reviewer
Reviewer -[problems]-> Writer
```

This lesson follows a customer assistant at a bank in Bengaluru, rebuilt from one large agent into a set of specialists.

## How it works

**Supervisor and workers.** The supervisor sees the user's goal and a list of workers described like tools ("research_competitor: researches one named company, returns a 200-word summary with sources"). It decides which to call, possibly in parallel, and writes the final answer. Strengths: parallelism, context isolation. Risks: vague delegation, duplicated work, lost details in summaries, high token use.

**Hand-offs.** Each agent owns a domain with its own tools and permissions. A hand-off is itself a tool call ("transfer_to_billing") that moves the conversation. Strengths: each agent stays small and focused; permissions stay narrow (only the billing agent can issue refunds). Risks: ping-pong between agents, context lost on transfer, users repeating themselves.

**Generator and reviewer.** The reviewer has a checklist or rubric and returns specific problems. Strengths: catches errors a single pass misses. Risks: endless loops (cap the rounds), reviewers that approve everything (test the reviewer on known bad drafts).

**Shared state versus messages.** Agents can share a common state object (as in graph frameworks) or pass messages. Shared state makes debugging easier; messages keep agents more independent. Either way, trace every agent's steps under one request id.

**When not to.** If the task is sequential and tightly coupled, one agent with good tools usually wins on cost and reliability. Measure a single-agent baseline first.

**The patterns compared:**

| Pattern | Strengths | Risks | Good for |
| --- | --- | --- | --- |
| Supervisor and workers | Parallel work, clean contexts | Vague delegation, high token use | Research, broad analysis |
| Hand-offs | Small focused agents, narrow permissions | Ping-pong, lost context | Customer service with distinct domains |
| Generator and reviewer | Catches errors one pass misses | Loops, lenient reviewers | Regulated or high-stakes writing |

**Designing a hand-off.** A hand-off tool should carry a short summary written by the sending agent: who the customer is (after verification), what they asked, what has been done and what remains. Pass the last few turns too. Test with scripted conversations that cross domains, such as a balance question followed by a card block, and check that the customer never has to repeat their identity or request. Log every hand-off with its reason so you can spot agents passing work they should handle.

**Writing role descriptions.** Each agent's description should say what it handles, what it must hand off, and what it must never do. Overlaps cause the worst failures: two agents that both think they handle refunds will either argue or both act. Read the descriptions side by side and remove every overlap before testing.

**A hand-off in code.** A hand-off is a tool whose arguments carry the summary the next agent needs. Your code, not the model, moves the conversation and counts transfers:

```python
AGENTS = {
    "front_desk": {"tools": ["get_profile", "transfer"], "prompt": "Greet, verify, route."},
    "cards":      {"tools": ["block_card", "card_status", "transfer"], "prompt": "Card issues only."},
    "loans":      {"tools": ["loan_balance", "transfer"], "prompt": "Loan questions only."},
}
TRANSFER_TOOL = {
    "name": "transfer",
    "description": "Hand the customer to another team. Use only for requests outside your role.",
    "input_schema": {"type": "object", "properties": {
        "to": {"type": "string", "enum": list(AGENTS)},
        "summary": {"type": "string", "description": "Who the verified customer is, what they asked, what is done, what remains"},
    }, "required": ["to", "summary"]},
}
MAX_TRANSFERS = 3

def handle_transfer(state, args):
    state["transfers"] += 1
    if state["transfers"] > MAX_TRANSFERS or args["to"] == state["agent"]:
        state["agent"] = "human_queue"
        return "Passing you to a person who can help with all of this."
    state["handoff_notes"].append({"from": state["agent"], "to": args["to"], "summary": args["summary"]})
    state["agent"] = args["to"]
    return f"Transferred to {args['to']}."
```

The receiving agent starts with its own prompt and tools, the hand-off summary and the last few turns, not the whole history. Only the `cards` agent holds `block_card`, so a confused front-desk agent cannot block a card.

**Test the reviewer with planted mistakes.** A generator-and-reviewer pair is only as good as the reviewer:

```python
PLANTED = [
    ("Interest is 12% a year; the EMI on ₹5 lakh over 5 years is ₹4,000.", "wrong EMI"),   # real EMI is about ₹11,100
    ("You can withdraw your fixed deposit any time without penalty.", "missing penalty"),
    ("This loan is guaranteed approved.", "promise of approval"),
]

def reviewer_recall(review_fn):
    caught = sum(1 for draft, _ in PLANTED if not review_fn(draft)["pass"])
    return caught / len(PLANTED)
```

Keep a set of 20 to 50 planted mistakes from real reviews, and track recall every time you change the reviewer's prompt or model. Also check it does not fail good drafts too often, or writers will learn to ignore it.

**Why systems of agents fail.** Studies of multi-agent failures find most problems are not about weak models: roles overlap or are vague, agents do not pass on what they found, someone stops too early, or nobody checks the final result. Write each role's boundaries, require hand-off summaries, and give one agent (or your code) clear responsibility for checking the finished answer.

**Count the extra cost.** Each agent repeats instructions and tool definitions, and summaries are extra calls. Measure tokens per task against a single-agent baseline and decide whether the gain in quality or speed pays for it.

## A worked example

A Bengaluru bank's customer assistant handles balances, card blocks, loan queries and complaints.

Version one, a single agent with 22 tools, chose wrong tools 9% of the time and could not safely be given card-block permissions.

Version two uses hand-offs:

- A **front-desk agent** with read-only tools for balances and FAQs and a hand-off tool to each specialist.
- A **cards agent** that can block cards (after confirming identity) but not move money.
- A **loans agent** with read access to loan accounts and the prepayment calculator.
- A **complaints agent** that records complaints in the grievance system and gives the customer a complaint reference number.

Each hand-off passes a short summary plus the last few turns, so customers do not repeat themselves. A rule stops more than two hand-offs in a row and routes to a human instead. Wrong tool choices drop to 2%, and the security team approves because each agent's permissions are narrow. Token use rises 30%, mainly from the summaries, which the bank accepts.

A generator-reviewer pair is added only for complaint responses, where a reviewer agent checks tone and that the reference number and timelines are correct; it catches issues in 6% of drafts.

| Measure | One agent, 22 tools | Hand-offs to four specialists |
| --- | --- | --- |
| Wrong tool choices | 9% | 2% |
| Card-block permissions | Could not be granted safely | Only the cards agent, after identity checks |
| Token use | Baseline | About 30% higher, from summaries |
| Security review | Not approved | Approved |

## Common mistakes

- **Many agents for a simple task.** Start with one; split when you measure a problem.
- **Vague roles.** Overlapping agents argue or duplicate work. Write sharp role descriptions.
- **Lossy hand-offs.** Pass a summary and recent turns, and test that users never need to repeat key details.
- **No loop limits.** Agents can hand work back and forth forever.
- **Traces per agent only.** One request must show every agent's steps together.
- **Untested reviewers.** Measure how many planted mistakes they catch.
- **Agents that can transfer to themselves.** Block it in code, and cap transfers.

## When one agent is enough

- **One domain with a handful of tools**: a single agent is cheaper and easier to debug.
- **Sequential, tightly coupled steps**, where splitting only adds hand-off losses.
- **Low volume**, where the engineering cost of several agents is not repaid.

Split into several agents when domains need different permissions, work can run in parallel, or one context cannot hold everything.

## From demo to production

- **Trace every agent under one request id**, with hand-off summaries visible.
- **Track transfer rates and loops** per agent pair, and review the worst conversations weekly.
- **Keep permissions per agent**, enforced in tool code.
- **Measure reviewer recall** on planted mistakes every release.
- **Hold a single-agent baseline** and compare cost and quality on every major change.
