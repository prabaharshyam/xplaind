## What it is

**Multimodal RAG** retrieves and answers from content that is not plain text: slides, charts, tables, scanned pages, diagrams and photos. There are two main approaches:

- **Convert to text, then use normal RAG.** OCR scans, describe images and charts with a vision-language model, extract tables to text, and index everything as text. Simple and compatible with existing pipelines.
- **Retrieve images directly.** Index each page as an image using a multimodal embedding model (approaches such as ColPali embed page images without OCR), retrieve the most relevant page images, and send them to a **vision-language model** to answer.

Many systems combine them.

```flow
title: Convert to text: cheap, normal RAG
Scan -[OCR]-> Text index
Chart -[a VLM describes it]-> Text index
Table -[extract]-> Text index
Text index -> A normal RAG answer
```

```flow
title: Retrieve images
Page -[render]-> Image -[multimodal embedding]-> Image index
Question -[embed]-> Top 3 page images
Image index -> Top 3 page images
Top 3 page images -> A vision-language model answers from the images
```

A hybrid uses OCR text for forms and image retrieval for photos, diagrams and slides, and shows the page thumbnail with each answer so it can be checked.

This lesson follows a chemicals manufacturer in Vadodara whose engineers query 15 years of maintenance reports full of scans, photos and diagrams.

## How it works

**Convert-to-text route.**

- Charts and diagrams: ask a vision-language model for a detailed description, including axis labels, values and trends, and store it with the page reference.
- Tables in images: extract them into structured text.
- Photos: caption them with what matters for the use case ("rust on the flange joint, upper left").

Pros: cheap queries, works with any text model, easy to filter and cite. Cons: descriptions lose detail, and you must decide in advance what matters.

**Image-retrieval route.**

- Render each page or slide as an image.
- Embed it with a multimodal retrieval model.
- At query time, embed the question, retrieve the top pages and pass the images to a vision-language model with the question.

Pros: keeps layout, charts and visual details; no OCR errors. Cons: larger indexes, image inputs cost more tokens and take longer, and fewer tools support it.

**Evaluation.** Build a golden set with questions that need the visual content ("What was the Q3 value in the revenue chart?", "Which valve is shown open in the photo?") and compare routes.

**Practical cautions.** Vision models can misread small text and numbers in charts; ask for citations to the page and, where numbers matter, check them against the underlying data if it exists. Keep images at sufficient resolution.

**Choosing by content type:**

| Content | Better route | Why |
| --- | --- | --- |
| Text-heavy scans and forms | OCR to text | Exact wording, cheap, searchable |
| Tables | Extract to structured text | Rows and headers kept for precise answers |
| Charts | Image route, or a careful description | Values and trends live in the picture |
| Diagrams and drawings | Image route | Labels, positions and connections matter |
| Photos | Image route | Detail is hard to predict in a caption |
| Slides | Image route | Layout carries meaning |

**Writing descriptions that help.** If you use the text route for visuals, ask the vision model for what users will ask about, not a general caption. For a chart: title, axes, units, every labelled value and the main trend. For a piping diagram: equipment tags, valve states and connections. Store the page number with every description. A focused description prompt, tested on a few pages against the golden set, can close much of the gap with the image route at a fraction of the query cost.

**Showing the evidence.** With visual content, a citation is more useful as a thumbnail of the page or slide. Engineers and analysts can glance at the image and confirm the answer, which also catches the model's occasional misreadings of small numbers.

**Render pages and describe visuals in code.** PyMuPDF turns PDF pages into images; a vision model describes them with a focused prompt:

```python
import base64
import fitz                                      # PyMuPDF
import anthropic

client = anthropic.Anthropic()
CHART_PROMPT = ("Describe this page for search. For each chart: title, axes and units, every labelled value, "
                "and the main trend. For tables: headers and every row. Quote numbers exactly as shown.")

def page_images(pdf_path, dpi=150):
    doc = fitz.open(pdf_path)
    for i, page in enumerate(doc, start=1):
        yield i, page.get_pixmap(dpi=dpi).tobytes("png")

def describe(png_bytes):
    r = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=800,           # check the docs for current names
        messages=[{"role": "user", "content": [
            {"type": "image", "source": {"type": "base64", "media_type": "image/png",
                                         "data": base64.b64encode(png_bytes).decode()}},
            {"type": "text", "text": CHART_PROMPT}]}])
    return "".join(b.text for b in r.content if b.type == "text")

# Text route: store describe(png) with the page number, and index it like any other chunk.
```

At answer time, the same image block format lets you send the top retrieved page images with the question for the image route.

**Retrieve images with text queries.** A multimodal embedding model places images and text in one space:

```python
from PIL import Image
from sentence_transformers import SentenceTransformer

clip = SentenceTransformer("clip-ViT-B-32")
img_vecs = clip.encode([Image.open(p) for p in photo_paths], normalize_embeddings=True)
q = clip.encode(["rust on a flange joint"], normalize_embeddings=True)[0]
best = (img_vecs @ q).argsort()[::-1][:5]
```

General models like this work for photos. For document pages full of text and charts, models trained for page retrieval (the ColPali family is a well-known example) do much better; test both on your golden set.

**Image tokens cost money.** A page image sent to a vision model is billed as many tokens, roughly in proportion to its size. Send the top two or three pages, not ten, crop to the relevant region when you can, and choose a resolution where small numbers are still readable. Measure cost per question for each route.

**Check numbers read from images.** Vision models sometimes misread small digits in charts and scans. Where the underlying data exists (the spreadsheet behind a chart), link to it and compare; otherwise show the page thumbnail with the answer so users can check.

**Try it in your browser.** Image inputs cost tokens by size. Estimate the cost of sending page images at different sizes.

```python
def image_tokens(width, height):
    return (width * height) / 750                 # a common rule of thumb; check your provider's docs

for w, h in [(1600, 2000), (1000, 1250), (800, 1000)]:
    t = image_tokens(w, h)
    print(f"{w}x{h}: about {t:,.0f} tokens per page, {3 * t:,.0f} for three pages")
```

## A worked example

A Vadodara chemicals manufacturer wants its plant engineers to query 15 years of maintenance reports: scanned forms, photos of equipment, piping diagrams and slide decks from root-cause reviews.

You test both routes on 60 questions:

- *Convert to text*: OCR for forms, model-written descriptions for photos and diagrams. 58% correct. Failures: descriptions missed the detail engineers asked about, such as which valve tag was circled.
- *Image retrieval*: page images embedded with a multimodal retriever; top three pages sent to a vision-language model. 79% correct. Failures: tiny handwritten notes on scans.

You ship a hybrid: scanned forms go through OCR (their text fields are what engineers search), while photos, diagrams and slides are retrieved as images. Answers show the page thumbnail so engineers can check. Query cost is about four times the text-only route, which the client accepts for the jump in accuracy on the questions that matter most to them.

| Route on 60 questions | Correct | Main failures | Query cost |
| --- | --- | --- | --- |
| Convert to text | 58% | Missed details such as circled valve tags | 1 |
| Image retrieval | 79% | Tiny handwritten notes | About 4 |
| Hybrid by content type | Shipped | OCR for forms, images for photos and diagrams | Between the two |

## Common mistakes

- **Ignoring visual content.** Text-only pipelines silently skip charts and photos.
- **Over-trusting chart readings.** Vision models misread small numbers; cite pages and check key values.
- **Low-resolution images.** Details vanish; keep enough resolution for the questions asked.
- **No visual questions in the golden set.** Then you cannot tell whether multimodal work helped.
- **Image route for everything.** Text-heavy documents are cheaper and often better as text.
- **Generic captions** for charts and diagrams. Ask for the values and labels users will need.
- **Sending many full-resolution pages** per question, which is slow and expensive.
- **Using a photo model for document pages.** Test a page-retrieval model too.

## When text-only RAG is enough

- **The visuals repeat what the text says**, as in many reports where charts illustrate stated numbers.
- **Tables can be extracted cleanly** to text by the PDF parser.
- **Few questions need the visuals**, so describing a handful of key pages by hand is cheaper.

## From demo to production

- **Keep page numbers and thumbnails** with every description and retrieved image.
- **Track cost per query** by route, including image tokens.
- **Re-describe pages** when the description prompt improves, and version the descriptions.
- **Keep a visual golden set** and rerun it when models change.
- **Let users flag misread numbers**, and add them to the test set.
