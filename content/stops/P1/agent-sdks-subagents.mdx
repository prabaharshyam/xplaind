## What it is

An **agent SDK** is a library, usually from a model provider, that gives you a ready agent loop: send messages, run the tools the model asks for, feed results back, repeat. Most add tracing, guardrails, session storage and ways for one agent to hand work to another. Examples include OpenAI's Agents SDK and Anthropic's Claude Agent SDK; Google and others offer similar kits.

A **sub-agent** is an agent started by another agent to do one part of a task in its own fresh context, returning only a summary. A **multi-agent system** is any design where several agents cooperate: a lead agent delegating to workers, agents handing a conversation between them, or specialists reviewing each other's work.

```flow
Lead agent | plans 5 research areas -> Financials | filings tool
Lead agent -> Legal | court search
Lead agent -> Management | news search
Lead agent -> Market | reports tool
Lead agent -> ESG | news search
Financials -[a summary, at most 400 words, with sources]-> Lead merges, spots conflicts, asks one follow-up
Legal -> Lead merges, spots conflicts, asks one follow-up
Management -> Lead merges, spots conflicts, asks one follow-up
Market -> Lead merges, spots conflicts, asks one follow-up
ESG -> Lead merges, spots conflicts, asks one follow-up
Lead merges, spots conflicts, asks one follow-up -> Brief
```

Each sub-agent runs in parallel with its own fresh context.

This lesson follows a consulting firm in Hyderabad producing due-diligence briefs on mid-sized manufacturers.

## How it works

**What SDKs save you.** The loop itself is twenty lines; the value is everything around it: retries, streaming, parallel tool calls, tracing every step, guardrails on input and output, hand-offs, sessions. Some SDKs also ship built-in tools such as file editing, shell commands or web search, with a permission system.

**Choosing.** Three common routes:

- *Your own loop* when the task is narrow, you want full control and few dependencies.
- *A vendor SDK* when the client is committed to that vendor and wants a pilot fast, especially if its built-in tools fit.
- *A graph framework* (such as LangGraph) when you need explicit control flow, durable pauses for approval and model-vendor independence.

Check how locked-in the SDK is to one vendor's models, how it stores sessions, and whether its traces export to the client's observability tools.

**Sub-agents.** Their real benefit is context isolation. A lead agent researching a market can start five sub-agents, each searching one competitor with its own full context window, and receive five one-page summaries. The lead never sees the hundreds of pages read, so its own context stays clean. Sub-agents can also run in parallel, cutting wall-clock time.

**The cost.** Each sub-agent has its own prompt, tools and history, so token use multiplies, often several times a single agent's. Coordination can fail too: two workers duplicate effort or a summary drops a key detail. Multi-agent designs pay off for broad, parallel, read-heavy tasks such as research; they rarely help tightly coupled tasks such as editing one codebase or filling in one form, where every step depends on the last.

**Three routes compared:**

| Route | Best when | Watch out for |
| --- | --- | --- |
| Your own loop | Narrow task, full control, few dependencies | You build tracing, retries and sessions yourself |
| Vendor SDK | Committed to one vendor, fast pilot, built-in tools fit | Lock-in; check trace export |
| Graph framework | Explicit control flow, durable approval pauses, vendor independence | More concepts to learn |

**Writing a delegation brief.** Each sub-agent's instructions should state the area and its boundaries ("legal cases in Indian courts since 2020; not regulatory filings, which another agent covers"), the tools it has, the output format with headings, a word limit, and a rule to include a source link for every claim. Ask for a short "open questions" list at the end, so the lead knows what is uncertain. Clear briefs prevent the two commonest failures: overlapping work and summaries that drop the one detail that mattered.

**Measuring whether the split paid off.** Run the same ten requests both ways. Record wall-clock time, total tokens, cost, and a quality score from a reviewer using a fixed rubric. A split that is faster and better but four times the cost may still be right, as here, when each brief replaces days of analyst time. The decision belongs in writing with the numbers.

**A lead and sub-agents in plain code.** You do not need a framework to see the pattern. The lead writes briefs, sub-agents run in parallel with their own fresh context, and the lead only sees their short reports:

```python
import asyncio
import anthropic

client = anthropic.AsyncAnthropic()
LEAD, WORKER = "claude-opus-5-5", "claude-sonnet-5-5"     # check the docs for current names

async def sub_agent(brief, max_tokens=1200):
    try:
        r = await asyncio.wait_for(client.messages.create(
            model=WORKER, max_tokens=max_tokens,
            system="You research one narrow area. Report in at most 200 words with a source link per claim, "
                   "then list open questions.",
            messages=[{"role": "user", "content": brief}]), timeout=120)
        return "".join(b.text for b in r.content if b.type == "text")
    except Exception as err:
        return f"FAILED: {type(err).__name__}"

async def research(question, areas):
    briefs = [f"Question: {question}\nYour area: {a}. Stay inside it; other agents cover the rest."
              for a in areas]
    reports = await asyncio.gather(*(sub_agent(b) for b in briefs))
    joined = "\n\n".join(f"## {a}\n{r}" for a, r in zip(areas, reports))
    final = await client.messages.create(
        model=LEAD, max_tokens=1500,
        messages=[{"role": "user", "content": f"Write a brief answering: {question}\n"
                   "Use only these reports. Say plainly if any area FAILED.\n\n" + joined}])
    return "".join(b.text for b in final.content if b.type == "text")

# asyncio.run(research("EV subsidy policies", ["Maharashtra", "Karnataka", "Tamil Nadu"]))
```

In a real system each sub-agent would run its own tool loop (search, fetch, read) rather than a single call, but the shape is the same: briefs out, short reports back, the lead's context stays small.

**The token bill.** Every sub-agent carries its own instructions, tool definitions and reading. Anthropic reported that its multi-agent research system used roughly 15 times the tokens of a normal chat. That can be worth it for a research brief that saves an analyst two days; it is rarely worth it for a support reply.

**Picking an SDK, concretely.** Vendor SDKs (OpenAI's Agents SDK, Anthropic's Claude Agent SDK, Google's Agent Development Kit and others) differ mainly in four places. Check each with a one-day spike before committing:

| Question | Why it matters |
| --- | --- |
| Can it use other vendors' models? | Switching later without a rewrite |
| Where do sessions and state live? | Data residency and restarts |
| Do traces export to OpenTelemetry or your tracing tool? | One view across systems |
| How are permissions and approvals for built-in tools set? | Safety in production |

**Context isolation cuts both ways.** A sub-agent sees only its brief, so it cannot use something another sub-agent found unless the lead passes it on. When work in one area depends on another, run those steps in order, or give the lead a second round to send follow-up briefs.

**Try it in your browser.** Sub-agents run in parallel, so total time is the slowest one, not the sum. Change the delays.

```python
import asyncio, time

async def sub_agent(area, seconds):
    await asyncio.sleep(seconds)              # pretend research
    return f"{area}: 3 findings"

async def lead():
    t0 = time.perf_counter()
    reports = await asyncio.gather(sub_agent("Maharashtra", 0.3), sub_agent("Karnataka", 0.5), sub_agent("Tamil Nadu", 0.2))
    print(reports)
    print(f"took {time.perf_counter() - t0:.1f} s, not {0.3 + 0.5 + 0.2:.1f} s")

await lead()
```

## A worked example

A Hyderabad consulting firm wants due-diligence briefs on mid-sized Indian manufacturers: financials, legal cases, management, market and ESG news.

A single agent took 40 minutes and often ran out of context halfway through the legal research, losing the earlier financial notes. You redesign:

- A **lead agent** reads the request, writes a plan with five research areas and starts one **sub-agent** per area in parallel.
- Each sub-agent has only the tools it needs: the legal one has a court-records search, the financial one a filings tool. Each returns a summary of at most 400 words with source links.
- The lead merges the summaries, spots conflicts (two sources disagree on revenue) and asks the financial sub-agent one follow-up question.

Wall-clock time drops to 9 minutes and coverage improves. Token use rises 3.5 times, which the firm accepts because each brief replaces two days of analyst work. You use the vendor's SDK because the firm already has an enterprise contract with that provider and its tracing shows every sub-agent's steps, which their quality team requires.

| Measure | Single agent | Lead plus five sub-agents |
| --- | --- | --- |
| Time per brief | About 40 minutes | About 9 minutes |
| Context overflow | Often, during legal research | None |
| Token use | Baseline | About 3.5 times |
| Coverage of the five areas | Uneven | Complete |

## Common mistakes

- **Multi-agent by default.** Start with one agent. Split only when context overflow or parallelism is the measured problem.
- **Vague delegation.** "Research the legal side" produces overlap. Give each sub-agent a precise scope, output format and length limit.
- **Ignoring token cost.** Measure cost per task before and after; multi-agent can multiply it.
- **Locking in without noticing.** If the client may switch model vendors, check how much of your code depends on one SDK.
- **No traces across agents.** When an answer is wrong you must see which sub-agent produced which claim.
- **No per-sub-agent limits.** One stuck worker consumes the whole budget.
- **Failing the whole task when one part fails.** Report the gap and deliver the rest.

## When one agent is better

- **Tightly coupled work**, such as editing one codebase or filling one form, where each step depends on the last.
- **Short tasks** that one agent finishes in a few steps.
- **Tight budgets**: several agents multiply token cost.
- **Strict latency needs** with little to parallelise.

## From demo to production

- **Trace the lead and every sub-agent** under one run id.
- **Set per-agent and whole-task budgets** for tokens, time and money.
- **Keep briefs as versioned templates**, and test them like prompts.
- **Compare against a single-agent baseline** on cost and quality before and after changes.
- **Plan for partial failure**: clear user messages when one area could not be covered.
