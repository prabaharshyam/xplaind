## What it is

Running a language model on your own GPU is mostly a question of **memory**. Three things compete for it, and one more thing decides speed:

- **Weights.** At 16-bit precision each parameter takes 2 bytes, so a 14B model needs about 28 to 30 GB before it does anything.
- **KV cache.** For every token in every layer, the model stores two vectors, a key and a value. This **KV cache** grows with the length of each request and with the number of requests running at once.
- **Working space.** Intermediate results (activations), the CUDA runtime and engine buffers. This lesson keeps about 10% of the GPU spare for them.
- **Speed.** Each new token means reading all the weights from memory once. So **memory bandwidth**, how many gigabytes per second the GPU can read, usually limits generation speed more than raw compute.

**Quantization** stores weights, and sometimes the cache, with fewer bits, such as 8 or 4 instead of 16. More memory is left for the cache, and fewer bytes are read per token, so generation often gets faster. The cost is some quality loss, which you measure on your own task.

Here is the effect on one 48 GB GPU, such as an NVIDIA L40S, serving a 14B model with 40 layers, 8 key-value heads and head size 128 (the shape of Qwen3-14B). After 10% spare, about 43 GB is usable; each request holds 4,000 tokens.

| Precision | Weights | Left for KV cache | Requests of 4,000 tokens |
|---|---|---|---|
| 16-bit weights, 16-bit cache | About 30 GB | About 13 GB | About 20 |
| 4-bit weights, 16-bit cache | About 10 GB | About 33 GB | About 50 |
| 4-bit weights, 8-bit cache | About 10 GB | About 33 GB | About 100 |

The rule: **weights fix the cost of entry; the cache decides how many users fit.**

```flow

dir: LR

Fits at 16-bit with cache? -[yes]-> Serve 16-bit
Fits at 16-bit with cache? -[no]-> Try FP8 weights and cache | needs FP8 support
Try FP8 weights and cache -> Eval holds? | per language and task

Eval holds? -[no]-> Try 4-bit AWQ or GPTQ, or a bigger GPU
```

This lesson follows an analytics firm in Hyderabad sizing GPUs for a self-hosted extraction model.

## How it works

### Weights

Memory for weights ≈ parameters × bytes per parameter.

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B to 8B | About 14 to 16 GB | About 7 to 9 GB | About 4 to 6 GB |
| 14B | About 28 to 30 GB | About 14 to 16 GB | About 8 to 10 GB |
| 32B | About 64 GB | About 32 to 34 GB | About 18 to 20 GB |
| 70B | About 140 GB | About 70 GB | About 37 to 40 GB |

Why is 4-bit more than half a byte per parameter? Each small group of weights (often 128) also stores a scale (and often a zero point), adding about 0.15 bits per weight. And the input embeddings and output layer often stay at 16-bit: for an 8B model with a large vocabulary, about 1 billion parameters, or 2 GB. Check the checkpoint's real file size before you plan.

### The KV cache

For each token, every layer stores one key and one value per **key-value head**:

cache per token = 2 × layers × key-value heads × head size × bytes per value

Read the numbers from the model's `config.json`: `num_hidden_layers`, `num_key_value_heads` and `head_dim` (or `hidden_size` divided by `num_attention_heads`). Most modern models use **grouped-query attention**: many attention heads share a few key-value heads. A common 8B shape has 32 attention heads but only 8 key-value heads, so using attention heads makes your estimate four times too big.

Then multiply by **tokens in flight**: peak active requests × tokens per request. Take the peak from a load test or traffic logs, never an average.

Two gotchas. **Hybrid** models, such as Qwen3.5, use full attention in only about one layer in four, so count only those layers. And **mixture-of-experts** models need memory for all their experts, though each token uses only a few.

### What the engine does with that memory

Serving engines such as vLLM use two ideas. **PagedAttention** stores each request's cache in small blocks, added only as the request grows, so a short request does not reserve room for the longest possible one. **Continuous batching** adds new requests to the running batch at every step, as others finish, so the GPU stays busy. Neither creates memory, so the arithmetic above stays the limit.

At start-up, vLLM logs the cache size in tokens and the "maximum concurrency" for your maximum request length. Compare that line with your estimate; it is the truth for your setup. From vLLM v0.34.0, an unset `--gpu-memory-utilization` uses all free memory, so set a share only when another process shares the GPU.

### Prefill and decode

Every request has two phases with different limits.

- **Prefill** reads the whole prompt at once and fills the cache. It does about 2 × parameters operations per prompt token: for a 14.8B model and a 6,000-token prompt, about 180 trillion. Prefill is limited by **compute** and sets **time to first token**, so long prompts mean slow first tokens.
- **Decode** writes one token per step. Each step reads all the weights and each request's cache, but does little maths per byte. It is limited by **memory bandwidth**, and it sets **tokens per second**.

A quick ceiling for one request: bandwidth ÷ bytes of weights. An L40S reads 864 GB/s, so a 10 GB 4-bit model can reach at most about 86 tokens per second for one request; a 30 GB 16-bit model at most about 29. Real numbers are lower. Batching is why serving is affordable: one read of the weights serves every request in the batch, so total throughput rises with batch size until compute or cache memory runs out. The price is that each user waits a little longer per token, so tune concurrency against your latency budget.

### Choosing a GPU

| GPU | Memory | Bandwidth | Native FP8 | Typical use |
| --- | --- | --- | --- | --- |
| NVIDIA L4 | 24 GB | 300 GB/s | Yes | Models up to 8B, light traffic |
| NVIDIA L40S | 48 GB | 864 GB/s | Yes | 8B to 32B models with quantization |
| NVIDIA A100 80 GB | 80 GB | About 2,000 GB/s | No | 14B to 32B at 16-bit, fine-tuning |
| NVIDIA H100 SXM | 80 GB | 3,350 GB/s | Yes | Busy services, large models with NVLink |
| NVIDIA H200 | 141 GB | 4,800 GB/s | Yes | About 70B in 8-bit on one GPU |

Three gotchas. The A100 has no FP8 units: vLLM can load FP8 checkpoints on it as weight-only, which saves memory but not compute. Blackwell GPUs, such as the B200, add hardware 4-bit floating point (NVFP4 and MXFP4); OpenAI's gpt-oss models ship in MXFP4, which is why gpt-oss-120b fits on one 80 GB GPU. And H100 PCIe cards have less bandwidth (about 2,000 GB/s) than the SXM version.

In India you can rent these from local GPU clouds such as E2E Networks (which lists H100 capacity in Delhi NCR and Chennai) and Yotta, or from global clouds' Indian regions. Eligible startups, researchers and institutions can apply for subsidised hours on the IndiaAI Compute Portal. As example rates, E2E's pages listed the L40S at ₹102 per GPU-hour and the H100 at ₹362 per GPU-hour on demand, before 18% GST (checked 28 November 2026). Prices and stock change often, so check the providers' pages, and your quota, on the day you plan.

### Quantization formats

- **FP8** (8-bit floating point). Near-16-bit quality for most models, half the memory, and faster maths on GPUs with FP8 units. Often the first thing to try.
- **AWQ and GPTQ** (4-bit integers, weights only). About a quarter of the weight memory, plus the overheads above, with modest quality loss. Download a checkpoint already quantized, ideally by the model maker.
- **NVFP4 and MXFP4** (4-bit floating point). Fast on Blackwell GPUs; newer and less widely tested.
- **bitsandbytes NF4.** Quantizes at load time in Transformers. Easy for experiments and QLoRA, but slower to serve.
- **GGUF.** The file format of llama.cpp, which Ollama and LM Studio build on, for laptops, CPUs and Apple Silicon. A Q4_K_M file uses about 4.8 to 4.9 bits per weight, so an 8B model is about 5 GB. Speed follows bandwidth: if a laptop reads memory at 80 GB/s, about 16 tokens per second is the ceiling.
- **8-bit KV cache.** Storing the cache in FP8 halves it. Measure its quality like any other change.

Work down from the highest precision that fits: 16-bit, then FP8, then 4-bit. For each, run your eval and a short load test, recording quality, memory and speed at peak. Pick the cheapest option whose quality loss your client accepts in writing.

### A memory planner in code

```python
def memory_plan(cfg, params_billion, weight_bits=16, kv_bits=16,
                context_tokens=4000, concurrent=20, gpu_gb=48, spare=0.10):
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights_gb = params_billion * weight_bits / 8          # rough: real 4-bit files are larger
    kv_token_mb = 2 * cfg["num_hidden_layers"] * kv_heads * head_dim * kv_bits / 8 / 1e6
    kv_gb = kv_token_mb * context_tokens * concurrent / 1e3
    usable = gpu_gb * (1 - spare)
    fits = weights_gb + kv_gb <= usable
    max_requests = int((usable - weights_gb) * 1e3 / (kv_token_mb * context_tokens))
    return round(weights_gb, 1), round(kv_token_mb, 3), round(kv_gb, 1), fits, max_requests

# The shape of a common 8B model; in real use, load the dict from config.json
cfg = {"num_hidden_layers": 32, "num_attention_heads": 32, "num_key_value_heads": 8, "head_dim": 128}
print(memory_plan(cfg, 8, gpu_gb=24))                  # (16.0, 0.131, 10.5, False, 10)
print(memory_plan(cfg, 8, weight_bits=8, kv_bits=8, gpu_gb=24))  # (8.0, 0.066, 5.2, True, 51)
```

At 16-bit, 20 requests of 4,000 tokens need about 10.5 GB of cache on top of 16 GB of weights: too much for a 24 GB card, which holds only 10. In 8-bit they fit, though the real FP8 file is about 9 GB, because the embeddings stay at 16-bit.

### Loading and serving a quantized model

For quick experiments in Transformers:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("your-org/your-8b-instruct",
                                             quantization_config=bnb, device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

For serving, use an engine with fast quantized kernels. vLLM reads the method from a quantized checkpoint's config:

```bash
vllm serve your-org/your-14b-instruct-awq --max-model-len 8192 --kv-cache-dtype fp8
```

To quantize a 16-bit model to FP8 at load time, vLLM v0.34.0 uses `--quantization fp8_per_tensor`; plain `fp8` no longer does this. `--max-model-len` caps one request's length; set it to what your users really send.

### Measuring quality loss

Run the golden set at each precision and compare per slice, not just overall. Quantization tends to hurt long reasoning, maths, code and less common languages first, so score Hindi, Telugu or Tamil cases separately from English. Keep a precision only if every slice that matters stays inside the agreed limit.

## A worked example

A Hyderabad analytics firm wants to self-host a model that extracts fields from invoices for 200 staff. Prompts plus replies run up to 6,000 tokens. The p95 time to first token must stay under 3 seconds. Quality scores and latencies below are illustrative, to show the method; memory figures are calculated.

**1. Measure the peak.** Replaying a busy day's logs peaks at **80 active requests** (average about 35). Size for 80.

**2. The model.** A 14B instruct model with 14.8 billion parameters, 40 layers, 8 key-value heads and head size 128. Cache per token: 2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes, about 0.16 MB. A 6,000-token request holds about 0.98 GB; the peak needs about 79 GB of cache.

**3. The original proposal.** Two H100 80 GB GPUs with tensor parallelism at 16-bit. Usable memory is 2 × 72 = 144 GB; weights take about 30 GB, leaving about 114 GB, or about 116 requests. It fits, but costs 2 × ₹362 = ₹724 an hour, and one GPU failure stops the service.

**4. Quantize.** The maker's 4-bit AWQ checkpoint is about 10 GB. Field accuracy on 500 real invoices: 95.1% at 16-bit, 94.6% at 4-bit, 94.5% with an FP8 cache too. The client's limit is 94.0%, so both pass.

**5. Fit it on L40S cards.** One L40S gives about 43 GB usable. With 4-bit weights, 33 GB is left. With a 16-bit cache, that holds 33 requests of 6,000 tokens, so the peak needs 3 GPUs and a fourth as a spare. With an FP8 cache, it holds about 67, so two GPUs carry the peak (134) and a third keeps it running if one fails.

**6. Check speed.** A load test at 80 concurrent requests on three L40S cards gives a p95 time to first token of 1.8 seconds, inside the budget. Each user's tokens come slower than on H100s, which have about four times the bandwidth, but the target is met.

| Option | GPUs | Requests at 6,000 tokens | Survives one GPU failure | Cost per hour (before GST) |
| --- | --- | --- | --- | --- |
| 16-bit, tensor parallelism | Two H100 | About 116 | No | ₹724 |
| 16-bit, two copies | Two H100 | About 86 (43 each) | No, 43 is below 80 | ₹724 |
| 4-bit weights, 16-bit cache, copies | Four L40S | About 132 (33 each) | Yes | ₹408 |
| 4-bit weights, FP8 cache, copies (chosen) | Three L40S | About 201 (67 each) | Yes | ₹306 |

Each L40S runs its own copy behind a load balancer. At the example rates checked on 28 November 2026, the chosen plan costs about ₹2.23 lakh for a 730-hour month against ₹5.29 lakh for the proposal, both before 18% GST. Reserved prices differ, so the firm still gets quotes.

## Common mistakes

- **Sizing for weights only.** The cache at peak decides how many users fit.
- **Sizing from average traffic.** Use the measured peak, or the service fails on the busiest morning.
- **Using attention heads instead of key-value heads,** or dropping the factor of 2, in the cache formula.
- **Taking 4-bit as exactly half a byte per parameter.** Scales and 16-bit embeddings add about 10 to 50%.
- **Quantizing without evals per slice.** An English-only average hides losses in Indian languages, maths and code.
- **Splitting a model that fits on one GPU.** Copies are simpler, scale better and survive failures.
- **Assuming FP8 is fast everywhere.** The A100 has no FP8 units; check the GPU generation.
- **Setting maximum context far above need.** One huge request can crowd out many small ones.

## When you do not need to think about GPUs

- **Using a hosted API** or the client's cloud model service.
- **Small models on CPUs,** such as embedding models, classifiers or a 4-bit GGUF demo on a laptop.
- **Low or spiky volume,** where a GPU rented all month costs more than paying per token.

## From demo to production

- **Plan memory** for weights, peak cache and working space; confirm it in the engine's start-up log.
- **Run the golden set** at every precision change, per language and task.
- **Load test on the real GPUs** before renting at scale, watching first-token time and errors at peak.
- **Keep at least one spare GPU** so a failure or an upgrade does not stop service.
- **Monitor cache usage and queue length** in production, and alert before the cache fills.
