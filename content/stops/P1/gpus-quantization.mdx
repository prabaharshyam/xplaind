## What it is

Running a language model on your own hardware is mostly a question of **GPU memory** and **memory bandwidth**:

- **Weights** must fit in GPU memory. At 16-bit precision, each parameter takes 2 bytes.
- The **KV cache** stores attention data for every token of every active request; it grows with context length and concurrency.
- **Generation speed** is usually limited by how fast weights can be read from memory for each new token, not by raw compute.

**Quantization** stores weights (and sometimes the cache) with fewer bits, such as 8 or 4 instead of 16, reducing memory and often increasing speed, at some cost in quality.

| One 48 GB GPU, a 14B model | Weights | KV cache | Users served |
|---|---|---|---|
| 16-bit weights | 28 GB | 20 GB | about 25 |
| 4-bit weights | 9 GB | 35 GB | about 45 |

Memory for weights ≈ parameters × bytes per parameter. KV cache ≈ tokens per request × active requests × cache size per token.

```flow
dir: LR
Quantize the weights to 4-bit -> Weights shrink from 28 GB to 9 GB -> More room for the KV cache -> About 45 users instead of 25
```

This lesson follows an analytics firm in Hyderabad sizing GPUs for a self-hosted extraction model.

## How it works

**Weights.** Memory ≈ parameters × bytes per parameter. A 7B model: about 14 GB at 16-bit, 7 GB at 8-bit, 3.5 to 4 GB at 4-bit. A 70B model: about 140 GB at 16-bit, so several GPUs, or about 35 to 40 GB at 4-bit.

**KV cache.** For each token in context, each layer stores keys and values. For a mid-sized model this can be tens to a few hundred kilobytes per token. Multiply by context length and concurrent requests: 32 requests at 8,000 tokens can need more memory than the weights. Engines like vLLM manage this memory efficiently, but they cannot create memory that is not there. Shorter maximum contexts and quantized caches let more requests fit.

**GPU choices.** Data-centre GPUs differ mainly in memory size (24 GB to 80 GB and more), memory bandwidth and support for low-precision formats such as FP8. Smaller models often run well on cheaper 24 to 48 GB cards; large models need high-memory cards and fast links between them. Check what your cloud offers in Indian regions, and the quotas, before designing around a GPU.

**Spreading a model.** Tensor parallelism splits each layer across GPUs in one machine; it needs fast GPU-to-GPU links. Running several copies of a smaller model, each on its own GPU, is simpler and scales throughput better when the model fits on one card.

**Quantization methods.** Weight-only methods (such as GPTQ and AWQ at 4-bit) shrink memory with modest quality loss; FP8 on newer GPUs gives near-16-bit quality with half the memory. Always rerun your evals: some tasks (maths, code, Indian-language text) can lose more than averages suggest.

**Throughput versus latency.** Larger batches give more tokens per second overall but slower responses per user. Tune batch size and concurrency against your latency budget.

**Weight memory at a glance:**

| Model size | 16-bit | 8-bit | 4-bit |
| --- | --- | --- | --- |
| 7B | about 14 GB | about 7 GB | about 4 GB |
| 14B | about 28 GB | about 14 GB | about 8 to 9 GB |
| 32B | about 64 GB | about 32 GB | about 18 to 20 GB |
| 70B | about 140 GB | about 70 GB | about 35 to 40 GB |

**Estimating the KV cache.** A model's configuration lists its layers, key-value heads and head size. Cache per token is roughly 2 (keys and values) × layers × key-value heads × head size × bytes per value. Multiply by the context length you allow and by peak active requests, measured in a load test rather than guessed from user numbers. Leave some memory free for the engine's working space. This arithmetic, done before buying or reserving GPUs, prevents the most expensive sizing mistakes.

**Choosing a quantization.** Start from the highest precision that fits your budget. Try FP8 if the GPUs support it, then 8-bit, then 4-bit weight-only methods. For each, run your own eval and a short load test, and record quality, memory, tokens per second and latency at peak. Pick the cheapest option whose quality loss your client accepts in writing.

**A memory planner in code.** Read the model's configuration and estimate weights plus KV cache for your traffic:

```python
import json

def memory_gb(config_path, params_billion, weight_bits=16, kv_bits=16, context_tokens=4000, concurrent=20):
    cfg = json.load(open(config_path))
    layers = cfg["num_hidden_layers"]
    kv_heads = cfg.get("num_key_value_heads", cfg["num_attention_heads"])
    head_dim = cfg.get("head_dim") or cfg["hidden_size"] // cfg["num_attention_heads"]
    weights = params_billion * 1e9 * weight_bits / 8
    kv_per_token = 2 * layers * kv_heads * head_dim * kv_bits / 8
    kv_total = kv_per_token * context_tokens * concurrent
    return {"weights GB": round(weights / 1e9, 1),
            "KV per token KB": round(kv_per_token / 1e3, 1),
            "KV total GB": round(kv_total / 1e9, 1),
            "total with 10% overhead GB": round((weights + kv_total) * 1.1 / 1e9, 1)}

# memory_gb("config.json", params_billion=8, weight_bits=8)
```

For a typical 8B model with grouped-query attention (32 layers, 8 key-value heads, head size 128) the cache is about 131 KB per token at 16-bit, so 20 requests of 4,000 tokens need roughly 10 GB on top of the weights.

**Loading a quantized model.** For quick experiments in Transformers, 4-bit loading takes a few lines:

```python
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained("org/model-8b-instruct", quantization_config=bnb,
                                             device_map="auto")
print(round(model.get_memory_footprint() / 1e9, 1), "GB")
```

For serving, prefer an engine with fast quantized kernels: vLLM can load checkpoints already quantized with AWQ or GPTQ, or quantize to FP8 on GPUs that support it (`vllm serve org/model-8b-instruct --quantization fp8`).

**Quantize the cache too.** On long-context workloads the KV cache can outgrow the weights. Engines such as vLLM can store it at 8-bit, roughly halving its memory, often with little quality loss. Test it like weight quantization.

**Measure quality loss on your task.** Run the golden set at each precision and compare per category, not just overall. Quantization tends to hurt long reasoning, maths and less common languages first, so check Indian-language cases separately. Keep the precision only where the drop is acceptable.

**Speed is not only memory.** Generation is often limited by memory bandwidth: each token reads the weights once, so smaller weights can mean faster tokens. But some quantized formats run slower on older GPUs without matching kernels. Benchmark tokens per second and time to first token on your actual hardware.

## A worked example

A Hyderabad analytics firm wants to self-host an extraction model for 200 concurrent users with prompts of up to 6,000 tokens.

Candidate: a 14B instruct model. At 16-bit, weights need about 28 GB. KV cache estimate for 200 requests × 6,000 tokens is far beyond one card, but actual concurrency in load tests averages 40 active requests. With 4-bit AWQ weights (about 9 GB) on a 48 GB GPU, roughly 35 GB is left for cache: enough for about 40 to 50 active requests at that context length in this model's configuration.

Evals: 16-bit scores 95.1% field accuracy; 4-bit scores 94.6%. Accepted.

Plan: three 48 GB GPUs, each running its own copy of the 4-bit model behind a load balancer, sized for the measured peak with one GPU of headroom. This costs about a third of the original proposal of two 80 GB GPUs running a 16-bit model with tensor parallelism, with better throughput for this workload.

| Option | GPUs | Field accuracy | Relative cost |
| --- | --- | --- | --- |
| 16-bit with tensor parallelism | Two 80 GB | 95.1% | 3 |
| 4-bit AWQ, three copies | Three 48 GB | 94.6% | 1 |

## Common mistakes

- **Sizing for weights only.** The KV cache decides concurrency.
- **Quantizing without evals.** Measure the loss on your tasks and languages.
- **Splitting a model that fits on one GPU.** Copies usually scale better than tensor parallelism.
- **Assuming a GPU type is available.** Check regional availability and quotas early.
- **Maximum context set far above need.** It wastes cache memory; set it to what users actually send.
- **Forgetting grouped-query attention** in KV estimates; use key-value heads, not attention heads.
- **Judging quantization on English-only tests** when users write in Indian languages.
- **Assuming 4-bit is always faster.** Benchmark on your GPU.

## When you do not need to think about GPUs

- **Using a hosted API** or the client's cloud model service.
- **Small models on CPUs**, such as embeddings or classifiers that run fast enough without a GPU.
- **Low volume**, where renting a GPU by the hour costs more than API calls.

## From demo to production

- **Plan memory** for weights, KV cache at peak concurrency and overhead, with headroom.
- **Record precision and quantization method** in the release file.
- **Run the golden set** at every precision change, per category and language.
- **Benchmark speed** on the real GPUs before buying or renting at scale.
- **Monitor GPU memory and utilisation** in production.
