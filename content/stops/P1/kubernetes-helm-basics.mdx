## What it is

**Kubernetes** runs containers across a group of machines (a cluster). You describe what you want, such as "three copies of this image, each with 1 CPU and 2 GB of memory, reachable at this name", and Kubernetes keeps reality matching that description: it starts containers, restarts crashed ones, moves them off failed machines and spreads traffic.

**Helm** packages all the Kubernetes files for an app into a **chart** with adjustable values, so the same chart installs into staging and production with different settings.

As an FDE you mostly work at the edge of Kubernetes: you ship an image and a chart or a few YAML files, and the client's platform team runs the cluster.

## How it works

The core objects:

- **Pod**: one or more containers running together. Pods are disposable; Kubernetes replaces them freely.
- **Deployment**: says how many pods of which image to run and how to roll out a new version (gradually, replacing a few at a time).
- **Service**: a stable name and address that sends traffic to whichever pods are healthy right now.
- **Ingress**: routes outside HTTP traffic to services, usually with HTTPS.
- **ConfigMap** and **Secret**: settings and sensitive values passed to pods as environment variables or files.
- **HorizontalPodAutoscaler**: adds or removes pods based on CPU, memory or custom metrics.

Each container declares **requests** (what it is guaranteed) and **limits** (the most it may use). A container that exceeds its memory limit is killed, which shows up as `OOMKilled`. **Probes** tell Kubernetes when a pod is alive (liveness) and ready for traffic (readiness); these map to the `/health` and `/ready` endpoints from the serving lesson.

You interact with `kubectl`: `get pods`, `describe pod`, `logs`, `rollout status`, `rollout undo`. With Helm: `helm install`, `helm upgrade --values prod.yaml`, `helm rollback`.

## A worked example

You deploy a contract-analysis API for a Mumbai bank on its Kubernetes platform. The platform team gives you a namespace and asks for a Helm chart.

Your chart's `values-prod.yaml` sets 3 replicas, requests of 500m CPU and 1Gi memory, limits of 1 CPU and 2Gi, the image tag `contracts-api:2.3.1`, the ingress host and a reference to a Secret holding the model key (the platform team creates the Secret; your chart never contains its value).

After `helm upgrade`, two of three pods keep restarting. You check:

```bash
kubectl get pods -n contracts
kubectl describe pod contracts-api-7d9c-xk2lp -n contracts   # Last State: OOMKilled
kubectl logs contracts-api-7d9c-xk2lp -n contracts --previous
```

`OOMKilled`: the new version loads a larger tokenizer and a PDF library that peak at 2.4 GB on big contracts. You roll back with `helm rollback contracts-api` so users are unaffected, raise the limit to 3Gi after agreeing it with the platform team, and add a test with a 300-page contract to CI so the next memory jump is caught before deploy.

## Common mistakes

- **No resource requests or limits.** Pods get squeezed or squeeze others. Always set both, from measurements.
- **Readiness probe missing.** Traffic reaches pods still loading models and users see errors after every deploy.
- **Secrets in the chart.** Values files end up in Git. Reference Secrets managed by the platform.
- **Using `latest` as the image tag.** Rollbacks and audits become guesswork.
- **Fixing things with kubectl edit in production.** The next Helm upgrade reverts it. Change the chart.

## Practise

Do the Kubernetes basics tutorial and Helm's quickstart. A free local cluster (kind, minikube or Docker Desktop's) is enough.

1. Deploy your containerised FastAPI app with a Deployment, a Service and readiness and liveness probes on `/ready` and `/health`.
2. Package it as a Helm chart with separate values for "staging" (1 replica) and "prod" (3 replicas).
3. Set a memory limit too low on purpose, watch the pod get `OOMKilled`, read why with `kubectl describe`, then fix it and roll out again.

**You are done when you can** deploy, upgrade and roll back your app with Helm and explain from `kubectl describe` why a pod is not running.
