## What it is

**Kubernetes** runs containers across a group of machines (a cluster). You describe what you want, such as "three copies of this image, each with 1 CPU and 2 GB of memory, reachable at this name", and Kubernetes keeps reality matching that description: it starts containers, restarts crashed ones, moves them off failed machines and spreads traffic.

**Helm** packages all the Kubernetes files for an app into a **chart** with adjustable values, so the same chart installs into staging and production with different settings.

As an FDE you mostly work at the edge of Kubernetes: you ship an image and a chart or a few YAML files, and the client's platform team runs the cluster.

```flow
Outside traffic, HTTPS -> Ingress | contracts.bank.example
Ingress -> Service: contracts-api | a stable name; sends to ready pods only
Service: contracts-api -> Pod 1
Service: contracts-api -> Pod 2
Service: contracts-api -> Pod 3
Deployment | 3 replicas of contracts-api:2.3.1; each pod requests 500m CPU and 1Gi, limits 1 CPU and 2Gi; probes /health and /ready -> Pod 1
ConfigMap and Secret | settings, and the model key made by the platform team -> Pod 2
Helm chart + values-staging.yaml or values-prod.yaml -[helm upgrade, helm rollback]-> Deployment
```

This lesson follows a contract-analysis API deployed to a bank's Kubernetes platform in Mumbai.

## How it works

The core objects:

- **Pod**: one or more containers running together. Pods are disposable; Kubernetes replaces them freely.
- **Deployment**: says how many pods of which image to run and how to roll out a new version (gradually, replacing a few at a time).
- **Service**: a stable name and address that sends traffic to whichever pods are healthy right now.
- **Ingress**: routes outside HTTP traffic to services, usually with HTTPS.
- **ConfigMap** and **Secret**: settings and sensitive values passed to pods as environment variables or files.
- **HorizontalPodAutoscaler**: adds or removes pods based on CPU, memory or custom metrics.

Each container declares **requests** (what it is guaranteed) and **limits** (the most it may use). A container that exceeds its memory limit is killed, which shows up as `OOMKilled`. **Probes** tell Kubernetes when a pod is alive (liveness) and ready for traffic (readiness); these map to the `/health` and `/ready` endpoints from the serving lesson.

You interact with `kubectl`: `get pods`, `describe pod`, `logs`, `rollout status`, `rollout undo`. With Helm: `helm install`, `helm upgrade --values prod.yaml`, `helm rollback`.

**Common pod states and what to do:**

| State | Usually means | First command |
| --- | --- | --- |
| Pending | No machine has room for the requests | `kubectl describe pod` for scheduling events |
| ImagePullBackOff | Wrong image name, tag or registry access | Check the tag and the registry secret |
| CrashLoopBackOff | The app exits on start | `kubectl logs --previous` |
| OOMKilled | Memory limit exceeded | Measure peak memory; raise the limit or reduce use |
| Running but not ready | Readiness probe failing | Check the `/ready` endpoint and its dependencies |

**Choosing requests and limits.** Measure before you set them. Run a load test with realistic inputs, including the largest documents users send, and watch memory and CPU per pod. Set requests near normal use and memory limits comfortably above the peak you saw. Too-low requests let the cluster pack pods too tightly; too-low limits kill pods on big inputs. Agree the numbers with the platform team, because they pay for the machines.

**Working with the platform team.** Ask early what they provide: the namespace, ingress setup, how Secrets are created, which registries are allowed, monitoring and log collection. Many platform teams have a standard chart or policies, such as required labels and resource limits, and a deploy that ignores them will be rejected.

**A Deployment shaped for an AI API.** Probes, resources, a safe rollout and a grace period for streams:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata: {name: claims-api}
spec:
  replicas: 3
  strategy:
    rollingUpdate: {maxUnavailable: 0, maxSurge: 1}        # never drop below 3 during a rollout
  selector: {matchLabels: {app: claims-api}}
  template:
    metadata: {labels: {app: claims-api}}
    spec:
      terminationGracePeriodSeconds: 120                    # longer than the longest streamed answer
      containers:
        - name: api
          image: registry.example.in/claims-api:3f9c2e1
          ports: [{containerPort: 8000}]
          envFrom: [{secretRef: {name: claims-api-secrets}}]
          resources:
            requests: {cpu: "500m", memory: "768Mi"}
            limits: {memory: "1536Mi"}
          readinessProbe:
            httpGet: {path: /ready, port: 8000}
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 20
            periodSeconds: 10
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: claims-api}
spec:
  minAvailable: 2
  selector: {matchLabels: {app: claims-api}}
```

**Autoscaling.** Scale on CPU to start; for AI APIs that mostly wait on model calls, a custom metric such as in-flight requests per pod tracks load better:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: claims-api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: claims-api}
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource: {name: cpu, target: {type: Utilization, averageUtilization: 65}}
```

**GPU workloads.** A model server pod asks for GPUs explicitly and is allowed onto the GPU nodes:

```yaml
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.10.1
          resources: {limits: {nvidia.com/gpu: 1}}
      tolerations:
        - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
```

Model weights belong on a persistent volume or a pre-warmed cache, not downloaded on every pod start, or scaling up takes many minutes.

**Helm values per environment.** Keep the templates once and the differences small:

```yaml
# values-prod.yaml
replicas: 3
image: {tag: 3f9c2e1}
resources: {requests: {cpu: 500m, memory: 768Mi}, limits: {memory: 1536Mi}}
hpa: {min: 3, max: 12}
```

`helm upgrade --install claims-api ./chart -f values-prod.yaml --atomic --timeout 10m` rolls back automatically if the new pods never become ready.

## A worked example

You deploy a contract-analysis API for a Mumbai bank on its Kubernetes platform. The platform team gives you a namespace and asks for a Helm chart.

Your chart's `values-prod.yaml` sets 3 replicas, requests of 500m CPU and 1Gi memory, limits of 1 CPU and 2Gi, the image tag `contracts-api:2.3.1`, the ingress host and a reference to a Secret holding the model key (the platform team creates the Secret; your chart never contains its value).

After `helm upgrade`, two of three pods keep restarting. You check:

```bash
kubectl get pods -n contracts
kubectl describe pod contracts-api-7d9c-xk2lp -n contracts   # Last State: OOMKilled
kubectl logs contracts-api-7d9c-xk2lp -n contracts --previous
```

`OOMKilled`: the new version loads a larger tokenizer and a PDF library that peak at 2.4 GB on big contracts. You roll back with `helm rollback contracts-api` so users are unaffected, raise the limit to 3Gi after agreeing it with the platform team, and add a test with a 300-page contract to CI so the next memory jump is caught before deploy.

| Step | Command or change |
| --- | --- |
| Spot the restarts | `kubectl get pods -n contracts` |
| Find the reason | `kubectl describe pod ...` showed OOMKilled |
| Protect users | `helm rollback contracts-api` |
| Fix | Memory limit raised to 3Gi, agreed with the platform team |
| Prevent | A 300-page contract test added to CI |

## Common mistakes

- **No resource requests or limits.** Pods get squeezed or squeeze others. Always set both, from measurements.
- **Readiness probe missing.** Traffic reaches pods still loading models and users see errors after every deploy.
- **Secrets in the chart.** Values files end up in Git. Reference Secrets managed by the platform.
- **Using `latest` as the image tag.** Rollbacks and audits become guesswork.
- **Fixing things with kubectl edit in production.** The next Helm upgrade reverts it. Change the chart.
- **maxUnavailable above zero with few replicas**, so a rollout drops capacity.
- **A short termination grace period**, which cuts off streamed answers on every deploy.
- **Downloading model weights at pod start**, making scale-up slow.

## When you do not need Kubernetes

- **A few services with modest traffic**: serverless containers (Cloud Run, Container Apps, ECS on Fargate) are simpler.
- **A small team without platform engineers**, where the cluster becomes the main job.
- **Prototypes and pilots**, unless the client's platform team already runs a cluster for you.

## From demo to production

- **Set requests and limits from load tests**, and alert on OOMKilled pods.
- **Use readiness and liveness probes** that check what they claim.
- **Protect capacity** with maxUnavailable 0 and a PodDisruptionBudget.
- **Deploy with `helm upgrade --atomic`** and keep rollback one command.
- **Cache model weights** on volumes for GPU workloads.

## Practice

Do the Kubernetes basics tutorial and Helm's quickstart. A free local cluster (kind, minikube or Docker Desktop's) is enough.

1. Deploy your containerised FastAPI app with a Deployment, a Service and readiness and liveness probes on `/ready` and `/health`.
2. Package it as a Helm chart with separate values for "staging" (1 replica) and "prod" (3 replicas).
3. Set a memory limit too low on purpose, watch the pod get `OOMKilled`, read why with `kubectl describe`, then fix it and roll out again.
4. Deploy with maxUnavailable 0 and a PodDisruptionBudget, run a load test during a rollout, and confirm no request failed.

**You are done when you can** deploy, upgrade and roll back your app with Helm and explain from `kubectl describe` why a pod is not running.
