## What it is

**Data curation** means choosing, writing, cleaning and balancing the examples a model learns from. For fine-tuning, it is most of the work: the training run itself may take an hour, but the data takes weeks.

The format depends on what you are teaching:

- **Supervised fine-tuning (SFT):** an instruction or chat, and the ideal response.
- **Preference tuning (DPO or RLHF):** a prompt, a better response and a worse one.
- **Continued pre-training:** plain text from your field, such as legal judgements.
- **A reward model or judge:** responses with a score or a label.

Every dataset is judged on three things. A useful picture is cooking:

- **Quality** is fresh ingredients: each example is right and consistent.
- **Coverage** is the right mix: the examples span the cases users really bring.
- **Quantity** is enough food for the table: there are enough examples for the task.

Curation is also about removing data. If your model has a bad habit, such as adding unrequested advice to every answer, look for training examples that show that habit, take them out, and add examples that show the behaviour you want.

```flow
title: Building a training dataset
Define the task and the output format -> Write a labelling guide | with tricky cases
Write a labelling guide -> Pilot: two people label the same 30 | compare
Pilot: two people label the same 30 -> Agree well enough?
Agree well enough? -[no]-> Fix the guide
Fix the guide -> Pilot: two people label the same 30
Agree well enough? -[yes]-> Label a varied first set | 50 to 100
Label a varied first set -> Clean: dedupe, format, mask personal data
Clean: dedupe, format, mask personal data -> Fine-tune and test | untouched test set
Fine-tune and test -> Still improving with more data?
Still improving with more data? -[yes]-> Label more, same guide
Label more, same guide -> Clean: dedupe, format, mask personal data
Still improving with more data? -[no]-> Improve quality, not quantity
```

## How it works

**Quality.** An example is high quality when it is:

1. **Relevant** to the task you are training for.
2. **Aligned with what the task needs.** If the task needs short answers, the examples are short; if it needs a reason with every score, they include one.
3. **Consistent** with the other examples. Two people labelling the same case should mostly agree.
4. **Correctly formatted**, exactly as the model should produce it, with no stray HTML or broken JSON.
5. **Unique.** Duplicates over-weight some cases and can leak into your test set.
6. **Allowed to be used**: no personal data you cannot use, and no content you have no right to train on.

The evidence that quality beats volume is strong. The LIMA study fine-tuned a large model on just 1,000 carefully chosen examples and got answers people often rated as good as a leading commercial model. The team behind the Yi models found 10,000 carefully written examples beat hundreds of thousands of noisy ones.

**The labelling guide.** Before anyone labels at scale, write down what a perfect output looks like, with examples of hard cases and how to handle them. Then run a pilot: two people label the same 30 items, you compare, and you fix the guide where they disagreed. Repeat until agreement is high. This is the cheapest quality step there is.

**Coverage.** Real users are varied, so your data must be too. List the ways inputs differ, such as language, length, topic, difficulty, format (typed or scanned), and single-turn or multi-turn, and make sure each matters in the mix. Meta credited most of Llama 3's gains over earlier versions to better data quality and variety, not a new architecture. More variety is not automatically better, though: adding unrelated data can make a model worse at your task.

**Quantity.** There is no fixed number. It depends on:

- **The task.** Sorting reviews into positive and negative needs far fewer examples than answering questions about financial filings.
- **The base model.** The closer it already is, the fewer examples it needs. With little data, start from a stronger model.
- **The method.** LoRA and other light methods work with hundreds to a few thousand examples; full fine-tuning usually wants tens of thousands or more.

The practical approach: start with **50 to 100 excellent examples**. In most cases they produce a visible improvement. If they clearly help, more data will help more. If they do nothing, check your prompt format and settings; a bigger set rarely rescues a failed small one.

Then measure the **learning curve**: train on 25%, 50% and 100% of what you have, and score each on the same test set. Gains usually shrink as you add data. A curve still rising steeply says collect more; a flat curve says spend effort on quality instead.

A short script splits the data for a learning curve and checks labeller agreement:

```python
import json, random

def subsets(rows, fractions=(0.25, 0.5, 1.0), seed=7):
    rows = rows[:]
    random.Random(seed).shuffle(rows)       # same order every time, so subsets nest
    return {f: rows[: int(len(rows) * f)] for f in fractions}

def agreement(labels_a, labels_b):
    """Share of items two labellers marked the same way."""
    same = sum(a == b for a, b in zip(labels_a, labels_b))
    return same / len(labels_a)

train = [json.loads(line) for line in open("train.jsonl")]
for f, part in subsets(train).items():
    with open(f"train_{int(f * 100)}.jsonl", "w") as out:
        out.writelines(json.dumps(r) + "\n" for r in part)

print(agreement(["late_fee", "deposit", "lock_in"], ["late_fee", "deposit", "notice"]))  # 0.67
```

**Speed-ups.** People find it faster to check and correct a draft than to write from scratch, so many teams have a strong model draft each answer and experts fix it. Watch for bias: people tend to accept a fluent draft too easily, so check a random sample of corrected items yourself.

| Step | What good looks like | Common failure |
| --- | --- | --- |
| Labelling guide | Written rules plus worked hard cases | "Label it sensibly" |
| Pilot | Two people, same 30 items, high agreement | Skipped to save time |
| Coverage plan | A list of input types with target counts | Whatever files came first |
| First set | 50 to 100 excellent, varied examples | 5,000 unchecked examples |
| Cleaning | Deduplicated, one format, personal data masked | Test items copied into training |
| Learning curve | Scores at 25%, 50% and 100% | One training run, no comparison |

## A worked example

A legal-tech startup in Hyderabad wants a model that reads residential rental agreements, in English and Telugu, and returns a fixed summary: rent, deposit, lock-in period, notice period, yearly increase and unusual clauses. They have 3,000 agreements, two lawyers for two weeks, and money for AI help.

1. **Guide and pilot.** The lawyers write a two-page guide. On a pilot of 30 agreements they agree on 70% of fields, mostly disagreeing on what counts as "unusual". They add twelve examples of unusual clauses to the guide; the next pilot reaches 92%.
2. **Coverage.** They pick agreements to match what users upload: 60% English and 40% Telugu, a fifth scanned, and both standard and custom formats.
3. **Drafts plus review.** A strong model drafts each summary in the fixed format, and the lawyers correct them. They manage about 80 a day each instead of 25.
4. **Cleaning.** Duplicate templates are removed, tenant and owner names and Aadhaar numbers are masked, and 120 agreements are locked away as the test set.
5. **Learning curve.**

| Training examples | Fields correct on 120 test agreements |
| --- | --- |
| 150 | 68% |
| 300 | 76% |
| 600 | 81% |

The numbers are for illustration. The curve is still rising, so collecting another 600 is likely worth it. Telugu scores lag English by 9 points, so the next batch leans towards Telugu agreements.

## Common mistakes

- **Labelling before writing a guide.** People disagree, and the model learns the disagreement.
- **Taking whatever data is easy to get.** Coverage gaps become blind spots in production.
- **Believing more is always better.** A thousand noisy examples can lose to a hundred clean ones.
- **Letting test items leak into training.** Remove duplicates before you split, and keep the test set untouched.
- **Copying expert workflows blindly.** Experts skip steps they think are obvious. Watch how they work and write every step down.
- **Forgetting multi-turn cases.** If users have conversations, train on conversations, including follow-ups and corrections.

## When you do not need a training dataset

- **A good prompt already meets the bar.** Measure that first.
- **The problem is missing facts.** Retrieval is faster to update than a dataset.
- **You have no way to test.** Build the test set first; it tells you whether training helped at all.

## From demo to production

- **Version the data** with the guide and the cleaning script, so you can rebuild any model.
- **Record where every example came from**: written by a person, drafted by a model, or taken from real use.
- **Grow the set from production.** Reviewer corrections and user feedback are your best new examples.
- **Re-check the guide** when the product changes, so old labels do not teach outdated rules.
- **Keep a deletion path.** If someone asks for their data to be removed, you must be able to find and drop it and retrain.

## Practice

1. Pick a task you know. Write a one-page labelling guide with five hard cases.
2. Ask a friend to label 20 items with your guide while you do the same. Measure agreement and fix the guide.
3. Write a coverage plan: the five ways your inputs vary, and how many examples of each you would collect first.
