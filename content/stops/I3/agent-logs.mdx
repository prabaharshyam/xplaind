## What it is

When an agent does something wrong, you need to know why: which step went off course, what the model saw, which tool returned what. **Agent logs** (often called traces) record every step of every run:

- each model call: the input messages, the reply, tokens, time;
- each tool call: the tool, arguments, result or error, time;
- the final outcome, the user and versions of the prompt and model.

## How it works

**Record each step as structured data**, not loose print statements. A simple shape: run id, step number, type (model or tool), inputs, outputs, start and end time, tokens and cost. Store runs as JSON lines or in a tracing tool.

**Use a tracing tool when you can.** Tools built for LLM apps (Langfuse, Arize Phoenix, LangSmith and others, many on OpenTelemetry) show each run as a tree of steps you can expand, with timings and costs.

**Link everything.** Give each run an id, and pass it to tool logs and application logs, so you can follow one request through every system.

**Read failed runs.** Start at the end (what went wrong) and walk back: was the tool result wrong? Did the model misread it? Did it pick the wrong tool earlier? Was the information never available?

**Turn failures into tests.** Save the input of every interesting failure as a test case and rerun it after changes.

**Mind privacy.** Logs contain user messages and tool data. Mask personal data, restrict access and set retention periods.

**Measure.** From logs you get success rates, steps per task, cost per task, slowest steps and the most common errors.

## A worked example

A Hyderabad logistics company's agent answers "Where is my shipment?" by calling tracking, delay-reason and ETA tools. Customers report occasional wrong delivery dates.

The team opens the trace of a reported run:

```text
run 9c1f  user=cust-2231  prompt=v6  model=chat-default  5 steps  6.2 s  Rs 0.38
 1 model      -> calls get_tracking("SHP-77812")
 2 tool       get_tracking: last scan "Nagpur hub, 3 Nov 21:40"
 3 model      -> calls get_eta("SHP-77812")
 4 tool       get_eta: ERROR timeout after 5 s
 5 model      -> "Your shipment will arrive on 5 November."
```

The ETA tool timed out, and the model invented a date instead of saying it did not know. Fixes: the tool now returns a clear error message ("ETA unavailable right now"); the prompt says never to state a date unless `get_eta` returned one; and a check blocks dates in the final answer when no ETA result exists in the run. The trace becomes a test case.

## Common mistakes

- **Logging only final answers.**
- **Unstructured print statements.** Hard to search and analyse.
- **No run ids.** You cannot connect steps across systems.
- **Logging personal data unmasked.**
- **Reading logs only after complaints.** Review a sample regularly.
