## What it is

When you give a model tools, it sees only their names, descriptions and parameter schemas. From that alone it must decide which tool fits, what arguments to pass and how to read the result. A tool designed for a human developer, such as a thin wrapper over every endpoint of an internal API, often confuses a model.

Good agent tools share five traits: there are **few** of them, each does one **clear job**, names and descriptions say **when** to use them, parameters are **tightly typed**, and results and errors are **short and actionable**.

| | API-shaped: 14 tools | Task-shaped: 3 tools |
|---|---|---|
| Tools | get_booking, get_booking_v2, list_segments, get_pnr_status, get_fare_rules, get_passengers, create_refund_request, ... | get_trip(booking_ref) to read; get_cancellation_quote(ref) to read; cancel_trip(quote_id) to act, with approval |
| Wrong tool picked | 22% | 3% |
| Calls per task | 4.1 | 2.3 |

```flow
dir: LR
title: Task-shaped tools
get_trip(booking_ref) | read -> get_cancellation_quote(ref) | read
get_cancellation_quote(ref) -> cancel_trip(quote_id) | acts: needs approval
```

This lesson follows a support agent at a travel company in Gurugram whose tools mirrored every endpoint of the booking API.

## How it works

**Choose tools by task, not by API.** If agents always look up a customer and then their open orders, one `get_customer_with_open_orders` tool beats two calls the model must chain. Fewer, higher-level tools mean fewer chances to go wrong.

**Name and describe for the model.** `search_policies` with the description "Search current HR policies by keywords. Use for questions about leave, travel, reimbursements or conduct. Returns up to 5 passages with policy name and section." tells the model when to call it and what comes back. Say what the tool does not do, too.

**Constrain parameters.** Use enums for fixed choices (`status: "open" | "closed"`), formats for ids (`pattern: ^ORD-\d{8}$`), sensible defaults and limits. Each loose string is a chance for the model to invent a value.

**Return what the model needs.** Do not dump 200 fields of raw JSON. Return the few fields that matter, in readable form, with ids the model can pass to the next tool. Paginate or truncate large results and say so ("showing 10 of 312; refine the search").

**Write errors as instructions.** "Error 400" teaches nothing. "No order found with id ORD-2026117. Order ids have 8 digits after ORD-; ask the user to check the id." lets the model recover.

**Separate reading from acting.** Tools that change things (refund, send, delete) should be distinct from tools that read, so you can require approval for them and log them separately.

**Test tool use.** Write 20 realistic tasks and check which tools the model calls and with what arguments. Wrong tool choices usually mean overlapping tools or unclear descriptions.

**A tool description checklist:**

| Part | Weak | Strong |
| --- | --- | --- |
| Name | `get_data` | `get_trip` |
| When to use | Missing | "Use first for any question about one trip" |
| What it returns | Missing | "Flights, passengers, status, whether it can be cancelled online" |
| What it does not do | Missing | "Does not cancel; use cancel_trip after a quote" |
| Parameter | `id: string` | `booking_ref` with a 6-character pattern |
| Error | "Error 400" | "No trip for ABC12; references are 6 letters or digits" |

**Making one tool depend on another.** Requiring the quote id in `cancel_trip` is a small design trick with a big effect. The model cannot cancel without first fetching a quote, so the customer always hears the refund amount and fees before anything happens, and the approval screen can show the quote. Use the same idea wherever an action should follow a check: a payment that needs a verified invoice id, or an email that needs a draft id the user has seen.

**Testing a tool set.** Run the same 20 tasks after every change to names, descriptions or schemas, and count three numbers: wrong tool chosen, invalid arguments, and calls per task. Small wording changes move these numbers more than people expect.

**A well-shaped tool in code.** Define arguments with Pydantic, generate the schema from it, and shape the result for the model:

```python
from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class SearchTrips(BaseModel):
    """Find a customer's trips. Use when they ask about a booking but give no reference.
    Returns at most 5 trips, newest first. Does not change or cancel anything."""
    status: Literal["upcoming", "past", "cancelled"] = "upcoming"
    city: str | None = Field(default=None, description="Destination city, e.g. Kochi")

TOOL = {"name": "search_trips", "description": SearchTrips.__doc__.strip(),
        "input_schema": SearchTrips.model_json_schema()}

def search_trips(customer_id, raw_args, db):
    try:
        args = SearchTrips.model_validate(raw_args)
    except ValidationError as err:
        field = err.errors()[0]["loc"][0]
        return f"Invalid {field}. Status must be upcoming, past or cancelled."
    trips = db.find_trips(customer_id, args.status, args.city)       # customer_id from the session
    if not trips:
        where = f" to {args.city}" if args.city else ""
        return f"No {args.status} trips{where}. Ask the customer for the booking reference."
    lines = [f"{t.ref}: {t.city}, {t.date:%d %b %Y}, {t.status}" for t in trips[:5]]
    more = f" (showing 5 of {len(trips)}; ask for a city or date to narrow)" if len(trips) > 5 else ""
    return "\n".join(lines) + more
```

The description says when to use the tool, what it returns and what it does not do. The result is a few readable lines with the ids the next tool needs, not raw database rows. Every failure path says what to do next.

**Find tools that earn their place.** More tools give more abilities but more chances to choose wrongly, and every description is sent on every call. Two simple experiments:

- **Remove one at a time.** Run your task set without each tool. If success does not drop, the tool can go.
- **Plot the calls.** Count calls per tool over a week of traces, and note which tool usually follows which. A tool never called may be badly described; two tools almost always called back to back are candidates to merge.

```python
from collections import Counter

def tool_usage(runs):
    """runs: list of lists of tool names, in order, one list per run."""
    calls, pairs = Counter(), Counter()
    for names in runs:
        calls.update(names)
        pairs.update(zip(names, names[1:]))
    return calls.most_common(), pairs.most_common(5)
```

**Version tools like APIs.** Renaming a parameter or changing what a tool returns can quietly break agent behaviour. Keep tool definitions in code next to the prompt, review changes together, and rerun the tool-choice tests on every change.

**One server, many agents.** If several apps need the same tools, expose them once through the Model Context Protocol (MCP) so each app does not reimplement them. Design rules stay the same: narrow tools, clear descriptions, helpful errors, permission checks inside the tool.

## A worked example

A Gurugram travel company's support agent first had 14 tools mirroring the booking API: `get_booking`, `get_booking_v2`, `list_segments`, `get_pnr_status`, `get_fare_rules`, `create_refund_request`, and more. In tests, the model picked the wrong one in 22% of tasks and often called `get_booking` and `get_booking_v2` both, doubling cost.

You redesign around the support team's real tasks:

```python
{
  "name": "get_trip",
  "description": "Get a customer's trip by booking reference: flights, passengers, status, "
                 "and whether it can be cancelled online. Use first for any question about one trip.",
  "input_schema": {
    "type": "object",
    "properties": {"booking_ref": {"type": "string", "pattern": "^[A-Z0-9]{6}$"}},
    "required": ["booking_ref"]
  }
}
```

The other tools become `get_cancellation_quote` (read-only: refund amount and fees) and `cancel_trip` (acting: requires the quote id, so the model must quote before cancelling). Results are short summaries, not raw API objects. An unknown reference returns "No trip found for ABC12. References are 6 letters or digits; ask the customer to read it from their e-ticket."

Wrong tool choices drop to 3%, average tool calls per task fall from 4.1 to 2.3, and `cancel_trip` can now sit behind a human approval step.

## Common mistakes

- **One tool per API endpoint.** Models struggle to chain many fine-grained tools. Build for tasks.
- **Overlapping tools.** Two tools that could both answer a question make the choice a coin toss.
- **Raw, huge results.** They waste tokens and hide the relevant field. Return what the task needs.
- **Silent failures.** Returning an empty list for an error leaves the model guessing. Say what went wrong and what to do.
- **Mixing read and write.** You cannot put approval on just the risky actions if one tool does both.
- **Raw API responses as tool results.** Hundreds of fields waste tokens and confuse the model.
- **Changing a tool without rerunning tool tests.** Small wording changes shift which tool the model picks.

## When tool design matters less

- **One or two tools** with clearly different jobs: a plain description and schema are usually enough.
- **Fixed workflows** where your code, not the model, decides which function runs.
- **Prototypes** testing whether an idea works at all: polish tools once the task is proven.

## From demo to production

- **Keep a tool-choice test set** (task, expected tool, expected arguments) and run it on every change.
- **Track per-tool error rates and calls per task** from traces.
- **Set timeouts and result-size limits** inside every tool.
- **Check permissions inside the tool**, using the session's user id.
- **Review the tool list quarterly**: remove unused tools, merge chained ones.

Read Anthropic's article on writing tools for agents and the tool-use overview in the docs.

1. Pick a small domain (a library, a clinic's appointments, a college's fee records) and design three to five tools for an assistant, with full schemas.
2. Write 15 realistic user tasks and run them against a model with your tools, logging every call and argument.
3. Change one description or merge two tools to fix the most common mistake, and rerun.
4. Remove each of your tools in turn, rerun the 15 tasks, and drop any tool whose removal does not hurt.
