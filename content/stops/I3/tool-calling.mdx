## What it is

**Tool calling** (also called function calling) lets a model use your code. You describe tools to the model: their names, what they do and the inputs they take. When a question needs a tool, the model replies with a request to call it with specific arguments. Your code runs the tool, sends back the result, and the model uses it to answer.

The model never runs anything itself. Your code stays in control.

```flow
title: The model never runs anything itself: your code stays in control
1. Your app sends the user message + tool list -> 2. The model asks: tool_use get_order_status | order_id
2. The model asks: tool_use get_order_status -> 3. Your app validates the arguments and runs the real function
3. Your app validates the arguments and runs the real function -> 4. tool_result | "Shipped 3 Nov, out for delivery"
4. tool_result -> 5. The model gives a final answer, or another tool_use
```

This lesson follows a fashion e-commerce site in Gurugram adding order tools to its support chat.

## How it works

**Describe the tool.** Each tool has a name, a description and an input schema:

```python
tools = [{
    "name": "get_order_status",
    "description": "Look up an order's status and expected delivery date by order id. "
                   "Use when the customer asks where their order is.",
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "Like ORD-12345678"}},
        "required": ["order_id"],
    },
}]
```

The model decides when to call a tool mainly from its **name and description**, and fills arguments from the schema. Clear, specific descriptions matter more than anything else.

**The round trip.**

1. Send the user's message and the tool list.
2. The model replies with a tool-use request, for example `get_order_status` with `{"order_id": "ORD-48213907"}`.
3. Your code validates the arguments, runs the real function and gets a result.
4. Send the result back in a tool-result message linked to that request.
5. The model writes the final answer, or asks for another tool.

**Errors are results too.** If the order does not exist or a service is down, send back a clear error message as the tool result ("No order found with id ORD-48213907; ask the customer to check the id"). The model can then recover, ask the user or apologise, instead of guessing.

**Safety.** Validate arguments before running anything. Separate read-only tools from tools that change things, and require confirmation for risky actions. Treat tool results as data, not instructions.

**Server-side tools.** Some providers also offer tools they run themselves (such as web search). For your own systems, you run the tools on your side.

**Good and weak tool definitions:**

| Part | Weak | Strong |
| --- | --- | --- |
| Name | `order` | `get_order_status` |
| Description | "Order API" | "Look up an order's status and delivery date by order id. Use when the customer asks where their order is." |
| Parameter | `id: string` | `order_id`, described as "Like ORD-12345678" |
| Error result | Empty | "No order found with id ...; ask the customer to check the id" |

**Validating arguments.** Treat the model's arguments like input from a web form. Check types and formats against the schema, check that the user is allowed to act on that record, and reject anything else with a helpful error result. A model can produce a well-formed id that belongs to another customer, so ownership checks belong in your code, not in the prompt.

**Several tool calls in one reply.** Models can request more than one tool at once when the calls do not depend on each other, such as an order status and the return policy. Run them, in parallel if you like, and send back one result for each request, each linked to its request id. When one call depends on another's result, the model asks for them in separate turns.

**Choosing between tools.** When you add a second or third tool, test which one the model picks for a set of realistic questions. If it chooses wrongly, the fix is almost always in the descriptions: say plainly when each tool applies and when it does not.

**Three kinds of tools, three levels of risk.**

| Kind | Examples | Risk | Rule |
| --- | --- | --- | --- |
| Read: fetch knowledge | Order status, product search, policy lookup | Low to medium: can expose data | Check the user may see it; return only needed fields |
| Compute: extend ability | Calculator, date maths, running code in a sandbox | Low, if sandboxed | Prefer tools to model arithmetic for money and dates |
| Write: change the world | Start a return, send an email, update a record, make a payment | High | Confirmation, limits, an audit log; never from untrusted text alone |

**Steering tool use.** By default the model decides whether to call a tool (`auto`). You can also require some tool (`any`), require one named tool (useful for structured output), or turn tools off for a turn (`none`). Forcing tools is handy in fixed workflows; in open chat, `auto` with clear descriptions usually works best.

**The full round trip in code.** This uses Anthropic's Python SDK; other providers follow the same pattern. Arguments are validated with Pydantic, ownership is checked in code, and the write tool needs the customer's confirmation:

```python
import anthropic
from pydantic import BaseModel, Field, ValidationError

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"            # check the docs for current model names

class OrderArgs(BaseModel):
    order_id: str = Field(pattern=r"^ORD-\d{8}$")

ORDERS = {"ORD-48213907": {"customer": "c_101", "status": "Out for delivery today"}}

def get_order_status(customer_id, order_id):
    order = ORDERS.get(order_id)
    if not order or order["customer"] != customer_id:          # ownership check in code
        return f"No order {order_id} on this account; ask the customer to check the id."
    return order["status"]

def start_return(customer_id, order_id, confirmed=False):
    if not confirmed:
        return "Not started: ask the customer to confirm the return first."
    return f"Return started for {order_id}; pickup in 2 days."

TOOLS = [
    {"name": "get_order_status", "description": "Look up an order's status by order id. Use when the customer asks where an order is.",
     "input_schema": OrderArgs.model_json_schema()},
    {"name": "start_return", "description": "Start a return. Only after the customer has clearly confirmed in this chat.",
     "input_schema": OrderArgs.model_json_schema()},
]
HANDLERS = {"get_order_status": get_order_status, "start_return": start_return}

def chat_turn(customer_id, messages, confirmed=False):
    while True:
        reply = client.messages.create(model=MODEL, max_tokens=600, tools=TOOLS, messages=messages)
        messages.append({"role": "assistant", "content": reply.content})
        calls = [b for b in reply.content if b.type == "tool_use"]
        if not calls:
            return "".join(b.text for b in reply.content if b.type == "text")
        results = []
        for call in calls:                                   # one result per request, matched by id
            try:
                args = OrderArgs.model_validate(call.input)
                fn = HANDLERS[call.name]
                extra = {"confirmed": confirmed} if call.name == "start_return" else {}
                out, err = fn(customer_id, args.order_id, **extra), False
            except ValidationError:
                out, err = "Order ids look like ORD-12345678. Ask the customer for theirs.", True
            results.append({"type": "tool_result", "tool_use_id": call.id, "content": out, "is_error": err})
        messages.append({"role": "user", "content": results})

msgs = [{"role": "user", "content": "Where is ORD-48213907?"}]
print(chat_turn("c_101", msgs))
```

Three things to notice. The customer id comes from your session, never from the model. The confirmation flag is set by your own interface (a "Yes, start the return" button), not by the model saying the customer agreed. And a wrong or foreign order id produces the same polite message, so the bot never confirms that someone else's order exists. In a real app, cap the `while` loop with a step limit, as the agent-loop lesson shows.

**Choosing the tool set.** More tools give more abilities but make choosing harder and fill the context with descriptions. A few habits:

- **Start with few tools** and add one only when a test question needs it.
- **Remove tools that do not help**: if success does not drop without a tool, drop it.
- **Watch the usage**: count calls per tool. A tool never called may be badly described; a tool often called wrongly may need a simpler design.
- **Merge tools that always run together**, such as "find customer" then "get orders", into one.

**Sharing tools with MCP.** The Model Context Protocol is an open standard for exposing tools and data to AI apps. Write a tool once as an MCP server, and any app or agent that supports MCP can use it. The same rules apply: validate inputs, check permissions, and be careful with write actions.

**Testing tool use.** Keep a list of realistic questions with the tool and arguments you expect, including questions that need no tool. Run it after every change to tools, descriptions or the model, and count wrong tool, wrong arguments and missed calls. Public benchmarks such as the Berkeley Function Calling Leaderboard compare models on this, but your own questions matter more.

## A worked example

A Gurugram fashion e-commerce site adds order tools to its support chat: `get_order_status`, `get_return_policy` and `start_return` (which needs the customer to confirm).

A customer writes: "Where is my kurta order ORD-48213907? If it's late I want to return it."

1. The model calls `get_order_status` with the id.
2. The code returns: "Shipped 3 Nov, out for delivery today, Gurugram hub."
3. The model replies that the order arrives today, and explains the 15-day return window by calling `get_return_policy`.
4. It does not call `start_return`, because the order is not late; if the customer insists, it asks for confirmation first.

When a customer types a wrong id, the tool returns a "not found" message and the model asks them to check their confirmation SMS.

| Customer message | Tools called | Result |
| --- | --- | --- |
| "Where is ORD-48213907? Return if late" | get_order_status, get_return_policy | Arrives today; 15-day return window explained |
| Insists on returning | None until confirmed | Asks for confirmation before start_return |
| Wrong order id | get_order_status returns "not found" | Asks them to check their confirmation SMS |

## Common mistakes

- **Vague tool descriptions.** The model then calls the wrong tool or none.
- **Running tools without validating arguments.**
- **Swallowing errors.** Return them as clear tool results.
- **Risky actions without confirmation.**
- **Forgetting to send the tool result back.** The model cannot answer without it.
- **Trusting identity or consent from the model.** The user id and "the customer agreed" must come from your app, not from tool arguments.
- **Returning huge results.** Return the few fields the model needs; big results cost tokens and confuse it.
- **Doing sums in the model.** Let a tool calculate totals, discounts and dates.

## When you do not need tools

- **The answer is in the prompt** or in retrieved documents already.
- **A fixed step always runs**: just call the function in your code and put its result in the prompt.
- **You only need a JSON shape**: structured output may be simpler, though a forced single tool is one way to get it.

## From demo to production

- **Version tool definitions** with the prompt, and test tool choice on every change.
- **Log every call**: tool, arguments, result size, time, errors and the user it ran for.
- **Set timeouts** on every tool and return a clear message when one is slow.
- **Separate read and write tools** in code and permissions, with an audit log for writes.
- **Rate-limit write actions** per user and per day.
