## What it is

Most systems keep their important data in a **database**. As a product grows, the database is usually the first part to strain, because every app server talks to it and its data must stay correct. Four ideas carry you a long way.

- **Choosing the model.** Relational (SQL) databases such as PostgreSQL and MySQL store data in tables with relationships and support transactions. NoSQL databases such as DynamoDB, MongoDB and Cassandra trade some of that for easy horizontal scale or flexible documents.
- **Indexes** make lookups fast by keeping a sorted structure of chosen columns.
- **Replication** keeps copies of the data on several servers, to spread reads and survive failures.
- **Sharding** splits the data itself across several databases when one is not enough.

```text
                        writes                     reads
 app servers ──────────────► [ PRIMARY ] ───────────────► [ REPLICA 1 ]
      │                           │  replication           [ REPLICA 2 ]
      │                           ▼  (may lag)
      │
      └── when one primary is not enough: SHARD by key
           user_id % 4 = 0 → [ shard A ]   = 1 → [ shard B ]
                         = 2 → [ shard C ]   = 3 → [ shard D ]
```

## How it works

**Pick the model by access pattern.** A relational database is a strong default for most products: orders, users and payments have clear relationships, need transactions, and benefit from flexible queries. NoSQL fits when you need massive write scale with simple key lookups, flexible document shapes, or time-series data. Many systems use both: PostgreSQL for core data and Redis or a key-value store for hot, simple data.

**Indexes** work like the index at the back of a book. Without one, finding a customer's orders means scanning every row: O(n). With a B-tree index on `customer_id`, the database jumps straight to the right rows in about O(log n). A **composite index** on `(customer_id, created_at)` also returns them already sorted by time. Indexes cost storage and slow down writes, so add them for real query patterns, and check with `EXPLAIN` that queries use them.

**Replication** copies every change from a **primary** to one or more **replicas**. Writes go to the primary; reads can go to replicas. This spreads read load and lets a replica take over if the primary fails. Most replication is asynchronous, so replicas can lag behind by milliseconds or seconds. That causes the classic bug where a user saves something and does not see it on the next screen; the fix is to read a user's own fresh writes from the primary.

**Sharding** splits a big table across several independent databases by a **shard key**. Every row with the same key value lives on the same shard. A good key spreads both data and traffic evenly and keeps what one request needs on one shard. Sharding adds real complexity: queries across shards are slow, transactions across shards are hard, and moving data when you add shards takes care. Postpone it until indexes, caching and replicas are not enough.

| Technique | Solves | Costs |
|---|---|---|
| Index | slow lookups and sorts | storage, slower writes |
| Read replicas | too many reads; failover | replication lag, more servers |
| Vertical scaling | everything, briefly | price, ceiling |
| Sharding | too much data or too many writes for one server | complex queries, rebalancing, cross-shard transactions |
| Caching (next lesson) | repeated reads of hot data | stale data, invalidation |

## A worked example

Fatima's team runs a ticketing platform for concerts and events across India. The `bookings` table had grown to 30 crore rows and pages were slowing down.

**Step 1: indexes.** The "My bookings" screen ran `SELECT * FROM bookings WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`. `EXPLAIN` showed a full table scan. A composite index on `(user_id, created_at)` cut it from 4 seconds to 3 milliseconds.

**Step 2: read replicas.** Browsing events and viewing bookings were 90% of traffic. They added two replicas and routed those reads there, keeping seat holds and payments on the primary. Primary CPU dropped from 85% to 30%. Soon after, support tickets arrived: "I booked but my ticket is not showing." Replica lag during busy sales was up to two seconds. They changed the app so that for 30 seconds after a user books, their own bookings are read from the primary.

**Step 3: sharding, later.** A year on, a single superstar's tour sale pushed writes past what one primary could take. They sharded bookings by `user_id`, which spread writes evenly and kept each user's history on one shard. They considered sharding by `event_id`, but a hit tour would have put all its bookings on one overloaded shard, a **hot shard**. Seat inventory for each event stayed in a separate, smaller table on its own database, because seat holds needed strong consistency within one event.

The order mattered: each step was cheaper than the next, and they only took the next one when measurements showed they needed it.

## Common mistakes

**Indexing everything.** Each index slows every write. Index the columns your real queries filter and sort on.

**Ignoring replication lag.** Reading from replicas right after a write shows stale data. Plan "read your own writes" from the primary.

**Sharding too early.** It makes every later change harder. Exhaust indexes, query fixes, caching and replicas first.

**A shard key that creates hot spots.** Dates, or one popular customer or event, can pile load onto one shard. Choose keys with many evenly used values.

**Needing cross-shard joins on hot paths.** If common requests must read every shard, the key is wrong for your access pattern.

**Choosing NoSQL because it sounds scalable.** If you need transactions and flexible queries, a well-indexed relational database will often serve you for years.
