## What it is

An **agent** is a model running in a loop with tools: it decides what to do next, calls a tool, reads the result and decides again, until the task is done or it must stop. The loop is short to write; the hard part is making it reliable.

It helps to distinguish two designs, as Anthropic's "Building effective agents" article does:

- A **workflow**: your code decides the steps (first classify, then retrieve, then draft). The model fills in each step. Predictable and easy to test.
- An **agent**: the model decides the steps and how many, choosing tools as it goes. Flexible for open-ended tasks, harder to predict.

Use a workflow when the steps are known; use an agent when they are not.

```text
          +--------------------------------------------+
          |                                            |
          v                                            |
   [model: task + history + tool list]                 |
          |                                            |
     wants a tool?  -- no -->  final answer, stop      |
          | yes                                        |
          v                                            |
   [your code runs the tool]  --> result appended -----+
          |
   step count > limit?  -- yes -->  stop cleanly, hand over to a person
```

This lesson follows a travel startup in Bengaluru building an assistant that plans weekend trips.

## How it works

**The core loop.**

```python
messages = [{"role": "user", "content": task}]
for step in range(MAX_STEPS):
    reply = call_model(messages, tools=TOOLS)
    messages.append({"role": "assistant", "content": reply.content})
    if not reply.tool_calls:                 # the model is done
        return reply.text
    results = [run_tool(c.name, c.args) for c in reply.tool_calls]
    messages.append({"role": "user", "content": results})
raise RuntimeError("Step limit reached; hand over to a person")
```

Each round: the model sees the task, everything so far and the tool list; it either answers or asks for tools; your code runs them and appends the results.

**Stopping.** The loop ends when the model answers without requesting tools. Always add a **maximum number of steps** so a confused agent cannot loop forever, burning money and repeating actions; when hit, stop cleanly and hand over.

**Good tools make good agents.** A few clear, well-described tools with helpful errors matter more than clever prompting.

**The system prompt** tells the agent its goal, its tools' purpose, how to decide it is finished, and what it must never do without confirmation.

**Start simple.** Many tasks work with a single model call plus retrieval, or a short workflow. Add agent loops when the number and order of steps truly vary.

**Workflow versus agent:**

| Aspect | Workflow | Agent |
| --- | --- | --- |
| Who decides the steps | Your code | The model |
| Predictability | High | Lower |
| Testing | Test each step | Test outcomes across many runs |
| Cost per task | Fixed, easy to estimate | Varies with the number of steps |
| Best for | Known, repeatable processes | Open-ended tasks with varying steps |

**Common workflow shapes.** Before reaching for an agent, check whether one of these fits. A **chain** runs fixed steps in order, such as extract, then check, then draft. A **router** classifies the request and sends it to one of several specialised prompts. **Parallel** calls split a task into independent parts and merge the results. An **evaluator loop** has one call draft and another check against criteria, repeating a fixed number of times. Many products that are described as agents are really one of these shapes, and they are easier to test.

**What to watch in early runs.** Print each step's tool and arguments for twenty real tasks. Look for repeated calls with tiny changes, tools the model never uses, and steps where it misreads a result. Each pattern points to a fix in a tool's description, its error messages or the stop condition in the system prompt.

## A worked example

A Bengaluru travel startup wants an assistant that answers "Plan a 3-day weekend in Coorg for two, under ₹25,000, from Bengaluru".

Tools: `search_stays(location, dates, budget)`, `get_travel_options(from, to, date)`, `get_weather(location, dates)`.

A run:

1. The model calls `get_weather` for Coorg on the dates: light rain expected.
2. It calls `get_travel_options`: a 6-hour drive or a bus.
3. It calls `search_stays` with a budget of ₹14,000 for two nights: three homestays returned.
4. It answers with a plan: drive, a homestay with a covered sit-out given the rain, two indoor-friendly activities, and a cost breakdown of about ₹22,000.

Four model calls, three tool calls. With a cap of 10 steps, a run once looped on `search_stays` with slightly different budgets when nothing matched; it stopped at the cap and the app showed "We couldn't find stays in that budget; try other dates". The team then improved the tool to return "no stays under ₹X; cheapest is ₹Y", and the loop stopped looping.

| Run | Steps | Outcome | Change made |
| --- | --- | --- | --- |
| Typical | 4 model calls, 3 tool calls | Plan at about ₹22,000 | None |
| No stays in budget | Hit the 10-step cap | Clean message to the user | Tool now says "cheapest is ₹Y" |
| Same case, after the change | 5 steps | Suggested other dates | Loop gone |

## Common mistakes

- **Using an agent when a workflow would do.**
- **No step limit.**
- **Vague tools and errors.** The agent then guesses or loops.
- **No stop condition in the instructions.**
- **No logging of each step.** You cannot debug what you cannot see.

- **Retrying a failed tool forever.** Return the error to the model with a clear message, and stop after two or three identical failures.
