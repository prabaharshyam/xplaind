## What it is

Python is the language of AI research and prototyping, but much of what makes the Python AI stack fast is written in other languages. For years that meant C and C++. More and more it means **Rust**.

You already use Rust if you use Hugging Face **tokenizers**, the **Polars** data-frame library, the **uv** package manager, the **Ruff** linter or **pydantic** (its core). Rust gives these tools C-like speed with fewer crashes and safe multi-threading.

For an AI engineer this opens a practical path: keep your project in Python, find the one slow, CPU-heavy step, rewrite just that step in Rust, and call it from Python. The tool that makes this easy is **PyO3**, with **maturin** to build and package it.

```flow
Python | notebooks, glue, training scripts -[import fastchunk: feels like any Python package]-> Rust extension, PyO3 + maturin | chunk_text(), score(), parse(): the hot loop, multi-threaded, no GIL
Rust extension, PyO3 + maturin -> Rust crates | rayon, regex, serde, ndarray, candle, tokenizers
```

## How it works

**The AI stack, and where Rust fits.**

| Layer | Python tools | Rust underneath or alongside |
|---|---|---|
| Data loading and cleaning | pandas, Polars | Polars is Rust; arrow-rs |
| Tokenising text | transformers | Hugging Face tokenizers is Rust |
| Training models | PyTorch, JAX | mostly C++ and CUDA; Rust rarely here |
| Serving and inference | vLLM, FastAPI | Candle, mistral.rs, Hugging Face text-embeddings-inference |
| Agents and tooling | LangChain, LlamaIndex | Rust CLIs and servers for speed and safe concurrency |
| Developer tools | pip, flake8 | uv and Ruff are Rust |

Training stays in Python with GPU code underneath. Rust's sweet spots are data processing, tokenising, inference servers that need low, steady latency, and command-line tools.

**Writing an extension with PyO3.**

```rust
use pyo3::prelude::*;

#[pyfunction]
fn word_counts(text: &str) -> std::collections::HashMap<String, usize> {
    let mut counts = std::collections::HashMap::new();
    for w in text.split_whitespace() {
        *counts.entry(w.to_lowercase()).or_insert(0) += 1;
    }
    counts
}

#[pymodule]
fn fasttext_tools(m: &Bound<'_, PyModule>) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(word_counts, m)?)?;
    Ok(())
}
```

Run `maturin new`, put this in `src/lib.rs`, then `maturin develop` inside your virtual environment. Now `import fasttext_tools` works in Python, and Rust types convert to Python ones automatically: `HashMap` becomes a `dict`, `Vec` becomes a `list`.

**Going parallel.** Python's Global Interpreter Lock (GIL) lets only one thread run Python at a time. Rust code can release it, then use the **rayon** crate to spread work across all cores with `par_iter()`. This is where speed-ups of ten to a hundred times come from on text-heavy work.

**Inference in Rust.** **Candle**, from Hugging Face, runs models such as Llama, Whisper and BERT in Rust, on CPU or GPU, with small binaries and fast start-up. That suits serverless functions and edge devices. Many teams also run ONNX models from Rust with the `ort` crate.

**Choosing between options.** There are three common ways to make a slow Python step faster, and Rust is only one of them:

- **Vectorise first.** If the work is maths on arrays, NumPy or Polars expressions are often enough and need no new language.
- **Cython or Numba.** Good for numeric loops when your team only knows Python; Numba compiles functions with a decorator.
- **Rust with PyO3.** Best for text processing, parsing, custom data structures and anything that needs safe multi-threading, or when you want a library that can also run without Python.

**Serving models from Rust.** For inference, a Rust server built with Axum and Candle or `ort` starts in milliseconds and uses little memory, which matters for autoscaling and for running on cheap CPUs at the edge. Hugging Face's text-embeddings-inference server is a well-known example of this pattern. Python is still the easier choice when you need the newest research models on day one, because they appear in PyTorch first.

## A worked example

Priya is an AI engineer at a legal-tech start-up in Bengaluru. Their RAG system indexes court judgments: 40 lakh documents. Re-indexing takes 9 hours, and a profiler shows 6 of them in one function: a Python loop that cleans text, splits it into sentences and builds overlapping chunks.

She keeps the whole pipeline in Python and rewrites only that function in Rust:

1. `maturin new chunker`, then she ports the loop to Rust, using the `regex` crate for sentence splits.
2. She releases the GIL and processes documents in parallel with rayon's `par_iter()`.
3. `maturin develop`, then one line changes in Python: `from chunker import chunk_documents`.
4. Unit tests compare the Rust output with the old Python output on 1,000 sample documents to make sure the chunks are identical.

The chunking step drops from 6 hours to 11 minutes on the same 16-core machine, and the full re-index from 9 hours to about 3. The remaining time is the embedding API, which is network-bound; she makes those calls concurrent in Python rather than touching Rust.

The team now ships `chunker` as an internal wheel built in CI with maturin, so nobody else needs Rust installed to use it.

## Common mistakes

**Rewriting without profiling.** The slow part is often not where you think. Measure with a profiler such as py-spy first.

**Moving network-bound code to Rust.** If the program is waiting on APIs or databases, Rust will not help much. Use async or batching instead.

**Copying big arrays between Python and Rust.** Converting a large list element by element can cost more than the work itself. Use the numpy crate with PyO3 to read NumPy arrays without copying.

**Holding the GIL during long work.** Your Rust code then blocks every other Python thread. Release it with `py.allow_threads` for long computations.

**Forgetting packaging.** Teammates without Rust need prebuilt wheels. Build them with maturin in CI for each platform you support.
