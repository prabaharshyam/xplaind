## What it is

Before MCP, every AI app needed its own code for every system. Three assistants and four systems meant twelve integrations. The **Model Context Protocol** (MCP) is an open standard that fixes this. You wrap each system once as an **MCP server**, and each AI app contains an **MCP client** that can talk to any server: three plus four pieces instead of three times four.

Anthropic released MCP on 25 November 2024. In December 2025 it gave MCP to the Agentic AI Foundation, a directed fund under the Linux Foundation co-founded by Anthropic, Block and OpenAI, where its maintainers develop it in the open. Versions are named by date. The current one is **2026-07-28**, the fifth release; the one before was 2025-11-25. Always check which version a tutorial targets.

A server can offer three kinds of thing. What matters most is who decides to use each:

| Feature | What it is | Who decides to use it | Example | Messages |
| --- | --- | --- | --- | --- |
| Tools | Functions with a JSON schema | The model, during a task | `search_tickets(query, status)` | `tools/list`, `tools/call` |
| Resources | Data addressed by a URI | The app or the user attaches it | `ticket://T-1042` | `resources/list`, `resources/read` |
| Prompts | Reusable prompt templates | The user picks one from a menu | "Summarise this ticket thread" | `prompts/list`, `prompts/get` |

## How it works

### Host, client and server

The **host** is the AI app the user works in. Inside it, one **client** holds the connection to one **server**, so a host with three servers has three clients. The client lists its server's tools for the model. When the model asks for a tool, the client sends the call to that server and returns the result. The model never talks to a server directly, so the host stays in control.

```flow
dir: LR
title: One server per system, shared by every host
IDE assistant | host with one client per server -> Maintenance-log server | find_machine, get_maintenance_history, log_observation
Chat assistant | host with one client per server -> Maintenance-log server
Chat assistant -> Spare-parts server
```

### The messages on the wire

MCP messages are JSON-RPC 2.0: a request has an `id`, a `method` and `params`, and the reply carries the same `id`. Since 2026-07-28 the protocol is **stateless**. Older versions began with an `initialize` handshake and kept a session. Now each request carries the protocol version and client capabilities in `_meta`, and should also carry the client's name and version. A client may call `server/discover` first, but need not. The official Python SDK still serves the older handshake to clients that have not upgraded, from the same server.

Failures come in two kinds:

- **A tool error** is a normal result with `isError: true`. The model reads it and can try again, so say what went wrong and what to do instead.
- **A protocol error** is a JSON-RPC `error` with a code, for example for a malformed request. The client handles it; the model usually never sees it.

**Try it in your browser.** These are one request and two replies recorded from the worked example's server, trimmed for space. The code turns a reply into what the model sees.

```python
import json

request = {"jsonrpc": "2.0", "id": 7, "method": "tools/call",
           "params": {"name": "get_maintenance_history", "arguments": {"tag": "CNC-14", "limit": 1},
                      "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}

ok = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": False,
      "content": [{"type": "text", "text": "{\"date\": \"2026-11-18\", \"note\": \"Vibration at high RPM\"}"}]}}
refused = {"jsonrpc": "2.0", "id": 7, "result": {"resultType": "complete", "isError": True,
      "content": [{"type": "text", "text": "Error executing tool get_maintenance_history: No machine 'CNC-14' in your plant."}]}}

def for_the_model(reply):
    assert reply["id"] == request["id"], "a reply must match its request id"
    if "error" in reply:  # protocol error: the host deals with it
        raise RuntimeError(reply["error"]["message"])
    text = "\n".join(c["text"] for c in reply["result"]["content"] if c["type"] == "text")
    return {"tool_result": text, "is_error": reply["result"]["isError"]}

print(json.dumps(for_the_model(ok)))
print(json.dumps(for_the_model(refused)))
```

### Transports: local and remote

| Aspect | stdio (local) | Streamable HTTP (remote) |
| --- | --- | --- |
| How it runs | The host starts the server as a child process and talks over standard input and output | The server is a web service at one URL, for example `https://mcp.example.in/maintenance` |
| Good for | Files, local databases, developer tools | Shared company systems, updated and logged in one place |
| Who is the user | Whoever runs the host on that machine | Whoever signed in: an OAuth token on every request |

With **Streamable HTTP**, the client POSTs each message to the one URL, and the server answers with JSON, or with a stream of events when it sends progress first. In 2026-07-28, every request carries an `Mcp-Method` header copied from the body, and tool, resource and prompt requests also carry `Mcp-Name`, so a gateway can route requests without parsing the body; a request whose headers and body disagree gets a 400 error. There is no session id any more: a server ignores an old `Mcp-Session-Id` header and does not mint one. If a workflow needs state, a tool returns a handle such as `draft_id` and the model passes it back.

Two gotchas. Older tutorials use the **HTTP+SSE** transport (`transport="sse"`), which is deprecated: do not start anything new on it. And a stdio server must write only MCP messages to standard output: one stray `print` breaks the connection, so log to standard error.

### Building a server in Python

The official Python SDK is the `mcp` package, version 2.x as of November 2026 (`pip install "mcp[cli]"`). Its main class is `MCPServer`. SDK 1.x tutorials import `FastMCP` from `mcp.server.fastmcp`, which fails on 2.x: update the code or pin `mcp<2`.

```python
# tickets_server.py
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open") -> list[dict]:
    """Search support tickets by keywords. status is 'open' or 'closed'. Returns up to 10."""
    if status not in ("open", "closed"):
        raise ToolError("status must be 'open' or 'closed'.")
    return ticket_db.search(query, status=status, limit=10)

@mcp.resource("ticket://{ticket_id}")
def ticket(ticket_id: str) -> str:
    """The full text of one ticket."""
    return ticket_db.get(ticket_id).body

@mcp.prompt()
def summarise_ticket(ticket_id: str) -> str:
    return f"Summarise ticket {ticket_id} in five bullets."

if __name__ == "__main__":
    mcp.run()  # stdio; use mcp.run(transport="streamable-http") for a remote server
```

The function's name, type hints and docstring become the tool's name, input schema and description, so the tool-design lesson applies directly. Raising `ToolError` returns an `isError: true` result: your message, after an "Error executing tool <name>: " prefix.

**Test before you connect a model.** The MCP Inspector (`npx @modelcontextprotocol/inspector`, or `mcp dev tickets_server.py`) lets you call each tool with your own arguments, including bad ones, and see raw results. Most bugs show up faster here than in a chat.

**Your own client.** Assistants and code editors include clients; your own agent can use the SDK:

```python
import asyncio
from mcp import Client, StdioServerParameters

async def main():
    server = StdioServerParameters(command="python", args=["tickets_server.py"])
    async with Client(server) as client:  # or Client("https://.../mcp") for a remote server
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("search_tickets", {"query": "refund"})
        print(result.is_error, result.structured_content)

asyncio.run(main())
```

Give each tool's `name`, `description` and `input_schema` to the model, send its calls to `client.call_tool`, and pass `is_error` back so the model knows a call failed.

### What a server can ask of the client

**Elicitation** lets a tool ask the user something mid-call: a missing detail, or "Close all 40 tickets?" before a bulk change. In 2026-07-28 it works in rounds: the server returns `resultType: "input_required"` with its questions, the host asks the user, and the client repeats the call with the answers. For a password or payment, which must not pass through the AI app, the server sends the user to a web page instead (URL mode).

Older material also describes **sampling** (the server asks the host's model to write text) and **roots** (the host tells the server which folders to use). Both were deprecated in 2026-07-28, along with logging. They stay in the spec until at least the first revision released on or after 28 July 2027, but build nothing new on them. In 2026-07-28, long-running jobs (**tasks**) moved out of the core into an extension. Interactive screens (**MCP Apps**) are a separate extension.

### Tools cost context

Every connected tool's name, description and schema sit in the model's context every turn. Anthropic's documentation (checked November 2026) says a typical five-server setup can use about 55,000 tokens of definitions before any work starts, and that tool choice gets worse beyond 30 to 50 tools. So:

- Offer few, task-shaped tools with distinct names; if two servers might both have `search`, prefix by system (`maint_search`).
- Cap results: a `limit` argument, short fields, IDs instead of full documents.
- Load tools on demand where the host supports it. For example, Claude's tool search tool keeps tools marked `defer_loading` out of context until the model searches for them.

### Security in brief

A server is code with access to real systems, and its output flows into the model. The main risks: **tool poisoning** (hidden instructions in descriptions or results), **changes after approval** (pin versions), **name clashes** between servers, and **too much reach** (one company-wide token). The later lesson, Securing agent tools and MCP servers, goes deeper; the worked example shows the builder's side.

## A worked example

A Pune manufacturing company has two plants, PUN-1 and PUN-2. Engineers use one AI assistant in their IDE and another in chat, and both need the maintenance log. Contractors must see only their own plant.

You build one remote MCP server with three tools: `find_machine`, `get_maintenance_history` and `log_observation`. Remote MCP uses OAuth: the company's single sign-on (SSO) is the **authorization server** that issues tokens, and your MCP server is the **resource server** that checks them.

```flow
title: First connection to the remote server
Assistant calls the server with no token -> 401 reply with a link to the server's metadata
401 reply with a link to the server's metadata -> Assistant reads which sign-in service to use
Assistant reads which sign-in service to use -> Engineer signs in with company SSO
Engineer signs in with company SSO -> SSO issues a token for this server only | user, plant, scopes
SSO issues a token for this server only -> Assistant repeats the call with the token
Assistant repeats the call with the token -> Server checks the token, then runs the tool as that user
```

The SDK serves the metadata and sends the 401 for you. Your code checks tokens and applies the user's limits:

```python
# maintenance_server.py
import json, sqlite3
from mcp.server import MCPServer
from mcp.server.auth.middleware.auth_context import get_access_token
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.mcpserver.exceptions import ToolError

db = sqlite3.connect("maintenance.db", check_same_thread=False)
audit = open("audit.jsonl", "a", buffering=1)  # one JSON line per call

def verify_with_sso(token: str) -> dict | None:
    """Your SSO library checks signature, expiry and issuer; returns the claims or None."""
    ...

class SSOTokenVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        claims = verify_with_sso(token)
        if claims is None:
            return None
        return AccessToken(token=token, client_id=claims["azp"], subject=claims["sub"],
                           scopes=claims["scope"].split(), resource=claims["aud"],
                           claims={"plant": claims["plant"]})

mcp = MCPServer("maintenance", token_verifier=SSOTokenVerifier(), auth=AuthSettings(
    issuer_url="https://sso.example.in",
    resource_server_url="https://mcp.example.in/maintenance",
    required_scopes=["maintenance.read"],
    validate_token_resource=True,  # refuse tokens issued for any other service
))

def caller(tool: str, args: dict) -> tuple[str, str, list[str]]:
    """Who is calling, from the checked token, never from the model. Writes the audit line."""
    tok = get_access_token()
    audit.write(json.dumps({"user": tok.subject, "client": tok.client_id, "tool": tool, "args": args}) + "\n")
    return tok.subject, tok.claims["plant"], tok.scopes

@mcp.tool()
def get_maintenance_history(tag: str, limit: int = 5) -> list[dict]:
    """Latest maintenance events for one machine in your plant, newest first. limit is 1 to 20."""
    user, plant, _ = caller("get_maintenance_history", {"tag": tag, "limit": limit})
    rows = db.execute(
        "SELECT e.done_on, e.kind, e.note, e.by_user FROM events e JOIN machines m ON m.id = e.machine_id "
        "WHERE m.tag = ? AND m.plant_id = ? ORDER BY e.done_on DESC LIMIT ?",
        (tag, plant, max(1, min(limit, 20)))).fetchall()
    if not rows:
        raise ToolError(f"No machine '{tag}' in your plant. Call find_machine to search by name.")
    return [{"date": d, "kind": k, "note": n, "by": b} for d, k, n, b in rows]

@mcp.tool()
def log_observation(tag: str, note: str) -> str:
    """Add a short note (max 500 characters) to a machine's log. Writes only to the notes table."""
    user, plant, scopes = caller("log_observation", {"tag": tag, "note": note[:80]})
    if "maintenance.write" not in scopes:
        raise ToolError("Your sign-in does not allow writing notes. Ask your supervisor to add it.")
    row = db.execute("SELECT id FROM machines WHERE tag = ? AND plant_id = ?", (tag, plant)).fetchone()
    if row is None:
        raise ToolError(f"No machine '{tag}' in your plant.")
    db.execute("INSERT INTO notes (machine_id, note, by_user) VALUES (?, ?, ?)", (row[0], note[:500], user))
    db.commit()
    return f"Note added to {tag}."

if __name__ == "__main__":
    mcp.run(transport="streamable-http", host="0.0.0.0", port=8000,
            streamable_http_path="/maintenance")  # serve behind HTTPS in production
```

Three design choices carry the security:

1. **The plant comes from the token, not the model.** No tool has a `plant_id` argument, so no prompt can ask for another plant. Every query filters by the plant the SSO put in the token.
2. **The token must be for this server.** With `validate_token_resource=True`, a genuine token issued for another service gets a 401.
3. **Writes need a scope.** Reading needs `maintenance.read`; `log_observation` also needs `maintenance.write`.

We tested this server with stand-in tokens for two users (`find_machine` is the same pattern, left out above). Anita, an engineer at PUN-1, asks in chat: "When was CNC-14's spindle last serviced, and has anyone reported vibration since?" The assistant calls `get_maintenance_history` and gets two rows: bearings replaced on 2 October 2026 by suresh.p, and "Vibration at high RPM" on 18 November 2026 by meera.d. It answers with both, then logs her note with `log_observation`.

Ravi, a contractor whose token says PUN-2 and `maintenance.read` only, asks the same from his IDE. The same query runs with `plant_id = 'PUN-2'`, finds nothing, and returns "No machine 'CNC-14' in your plant." His `log_observation` call gets "Your sign-in does not allow writing notes." Both are results with `isError: true`, so the assistant explains them. The audit log has one line per call, for example `{"user": "ravi.contractor", "client": "ide-assistant", "tool": "get_maintenance_history", "args": {"tag": "CNC-14", "limit": 2}}`.

Two more layers make this production-grade. The server's database account should only read machines and events and insert into notes, so a bug in your filter cannot delete anything. And the server must **never forward Anita's token** to another API. That is token passthrough, which the MCP security guidance forbids; if a downstream API needs the user, get a separate token issued for that API.

When IT later adds a spare-parts system, they deploy a second server with the same sign-in, and both assistants gain its tools unchanged.

## Common mistakes

- **Following an old tutorial line by line.** `FastMCP` imports, `transport="sse"`, session ids and the `initialize` handshake are from 2024 and 2025. Check versions first.
- **One super-user credential for everyone.** If the server ignores who is asking, every user reaches everything. Act as the signed-in user.
- **Taking identity from a tool argument.** A `user_id` or `plant_id` parameter lets the model, or text injected into it, pick someone else's data. Read identity from the checked token.
- **Token passthrough.** Accepting tokens not issued for your server, or forwarding the user's token to other services, breaks audit and scope checks.
- **Exposing the whole database.** Offer task-shaped tools, not `run_sql`, unless the users are database administrators.
- **Huge results.** Thousands of rows flood the context and slow every later turn. Cap, paginate and summarise.
- **No timeouts.** A tool waiting on a slow ERP blocks the agent. Time out the server's own calls, and set a client read timeout (`read_timeout_seconds` in the Python `Client`).
- **Trusting servers and results.** Unknown or unpinned servers, and ticket text treated as instructions, invite tool poisoning and prompt injection.
- **No logging.** Without user, tool and arguments for each call, you cannot investigate an incident.

## When you do not need MCP

- **One app with a few tools** that only it uses: plain tool definitions in your code are simpler.
- **Fixed workflows** where your code calls functions directly and no model chooses tools.
- **Strict environments** where every new network service needs review: start with in-process tools, and move to MCP once a second app needs them.

MCP pays off when several hosts or agents need the same tools, or people want to plug the assistants they already use into your systems.

## From demo to production

- **OAuth through company sign-in**, narrow scopes, tokens checked for this server, identity from the token, a least-privilege database account.
- **A central audit log** of user, client, tool, arguments and result size.
- **An approved-server list**, pinned versions, and a review whenever tool descriptions change.
- **Limits on every tool:** timeouts, result caps, rate limits, and user confirmation for writes.
