## What it is

Every AI app used to need its own custom code for every tool: one integration for the ticketing system in the chat app, another in the coding assistant, another in the agent. The **Model Context Protocol** (MCP) is an open standard that fixes this. You wrap a system once as an **MCP server**; any **MCP client**, such as a desktop assistant, an IDE or your own agent, can then discover and use it.

An MCP server can offer three kinds of thing:

- **Tools**: actions the model can call, such as `search_tickets` or `create_invoice`.
- **Resources**: data the app can read into context, such as a file, a record or a schema.
- **Prompts**: reusable prompt templates a user can pick.

```text
   HOSTS (AI apps)                 CLIENTS                     SERVERS (one per system)
   +-----------------+                                         +---------------------------+
   | IDE assistant   |--[client]---------------+-------------> | maintenance-log server    |
   +-----------------+                          |               |  tools: find_machine,     |
   +-----------------+                          |               |   get_maintenance_history,|
   | chat assistant  |--[client]---------------+               |   log_observation         |
   +-----------------+--[client]-----------------------------> | spare-parts server        |
                                                                +---------------------------+
   one server, many hosts: no new integration per app
```

This lesson follows a manufacturing company in Pune whose engineers use two different AI assistants on the same maintenance data.

## How it works

**Roles.** The *host* is the AI application the user works in. Inside it, an MCP *client* holds a connection to each *server*. The client asks a server what it offers, passes the tool list to the model, and when the model calls a tool, the client sends the call to the right server and returns the result.

**Transports.** A local server runs as a process on the same machine and talks over standard input and output, which suits desktop tools and developer machines. A remote server runs as a web service and talks over HTTP, which suits shared company systems and needs proper authentication, typically OAuth.

**Building a server.** Official SDKs exist for Python, TypeScript and other languages. In Python a minimal server is a few lines:

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("tickets")

@mcp.tool()
def search_tickets(query: str, status: str = "open") -> list[dict]:
    """Search support tickets by keywords. status is 'open' or 'closed'. Returns up to 10."""
    return ticket_db.search(query, status=status, limit=10)

if __name__ == "__main__":
    mcp.run()
```

The function's name, type hints and docstring become the tool's schema, so the tool design advice from the earlier lesson applies directly.

**Security.** An MCP server is code with access to real systems. Ask: who wrote it, what can it reach, which credentials does it use, and does it act as the user (respecting their permissions) or as an all-powerful service account? Tool descriptions and results flow into the model, so a malicious server or a poisoned record can carry prompt injection. Use least privilege, review third-party servers before installing them, and log every call.

**Local versus remote servers:**

| Aspect | Local (standard input and output) | Remote (HTTP) |
| --- | --- | --- |
| Runs on | The user's machine | A company server or cloud |
| Good for | Developer tools, local files | Shared company systems |
| Authentication | The user's own machine access | OAuth, ideally through single sign-on |
| Updates | Each user updates their copy | Update once for everyone |
| Logging | Per machine | Central audit log |

**Security questions for any server:**

| Question | Why it matters |
| --- | --- |
| Who wrote it, and can we read the code? | A server runs with the access you give it |
| What systems and data can it reach? | Limits the damage from a mistake or attack |
| Does it act as the user or as a service account? | Decides whether user permissions apply |
| Which tools write or send? | Those need tight limits or approval |
| Are calls logged with user, tool and arguments? | Needed to investigate incidents |

**Designing the tools.** The same advice as any agent tool applies: few, task-shaped tools with clear descriptions and helpful errors. Because many different hosts will use one server, good descriptions matter even more; you cannot tune a prompt in each host to make up for a vague tool. Keep write tools narrow, such as `log_observation` writing only to a notes table, so even a confused or manipulated model can do little harm.

## A worked example

A Pune manufacturing company's engineers use an AI assistant in their IDE and another in their chat tool. Both need access to the maintenance log database.

Instead of two integrations, you build one remote MCP server with three tools: `find_machine` (by tag or name), `get_maintenance_history` (last N events for a machine) and `log_observation` (adds a note; writes only to a notes table). It authenticates each user through the company's single sign-on and queries the database with that user's own permissions, so a contractor sees only their plant.

Both assistants connect to the same server. An engineer asks in chat: "When was CNC-14's spindle last serviced, and has anyone reported vibration since?" The assistant calls `find_machine`, then `get_maintenance_history`, and answers with dates and the names in the log. Every call appears in the server's audit log with user, tool and arguments.

When IT later adds a new spare-parts system, they add a second MCP server, and both assistants gain the tools without any change to the assistants themselves.

| Event | What happened |
| --- | --- |
| Engineer asks about CNC-14 | Chat assistant called find_machine, then get_maintenance_history |
| Contractor asks about another plant | The server's per-user permissions returned nothing |
| Audit review | Every call listed with user, tool and arguments |
| New spare-parts system | A second server added; both assistants gained its tools |

## Common mistakes

- **Installing unknown servers.** A third-party server runs with whatever access you give it. Read the code or use trusted sources.
- **One super-user credential.** If the server ignores the user's own permissions, every user can reach everything.
- **Exposing the whole database.** Offer task-shaped tools, not a `run_sql` tool, unless the users are database administrators.
- **Treating tool results as trusted.** Text from a ticket or document can contain injected instructions; the host must treat it as data.
- **No logging.** You cannot investigate what an assistant did without a record of tool calls.
