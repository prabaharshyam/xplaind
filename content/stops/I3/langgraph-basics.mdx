## What it is

LangGraph is an open-source Python and JavaScript framework for building agents and multi-step AI workflows as **graphs**:

- **State**: a typed object, such as a dictionary of messages, the current ticket and a draft reply, passed through the graph.
- **Nodes**: functions that take the state and return updates. A node might call a model, call a tool, or run plain code.
- **Edges**: which node runs next. Conditional edges choose based on the state, such as "if the model asked for a tool, go to the tool node; otherwise finish".
- **Checkpointer**: saves the state after every step, so a run can pause, resume, be inspected or replayed.

An agent loop is just a small graph: model node, tool node, and a conditional edge looping between them. A workflow is a graph with fixed edges. LangGraph lets you mix both in one system.

```text
   START
     |
     v
  [classify] --category--+--> [billing_agent] --proposes credit?--> [approve_credit]  INTERRUPT
                         |        (tool loop)          | no               |  supervisor decides
                         |                             v                  v
                         +--> [outage_agent] ------> [reply] <------ [apply_credit]
                                  (tool loop)          |
                                                       v
                                                      END
   checkpointer: state saved after every node, per thread_id
```

This lesson follows a broadband provider in Chennai building a support-ticket assistant with approval for credits.

## How it works

You define the state type, add nodes, connect edges and compile:

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]   # new messages are appended, not replaced
    category: str | None

def classify(state: State) -> dict:
    label = llm_classify(state["messages"][-1].content)
    return {"category": label}

def route(state: State) -> str:
    return "billing" if state["category"] == "billing" else "general"

g = StateGraph(State)
g.add_node("classify", classify)
g.add_node("billing", billing_agent)
g.add_node("general", general_agent)
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route, ["billing", "general"])
g.add_edge("billing", END)
g.add_edge("general", END)
app = g.compile(checkpointer=MemorySaver())
```

Each invocation passes a `thread_id`; the checkpointer stores state per thread, so the next message in the same thread continues where it left off. In production you swap `MemorySaver` for a database-backed checkpointer such as PostgreSQL.

**Interrupts** pause a run before or inside a node and wait for outside input, the basis of human approval. **Streaming** sends node-by-node updates to a UI. **Sub-graphs** let a node be a whole graph, useful for a specialist agent inside a larger flow.

**LangGraph pieces and what they give you:**

| Piece | What it is | What it gives you |
| --- | --- | --- |
| State | A typed dictionary | One place to see everything the run knows |
| Node | A function returning updates | Small, testable steps |
| Edge | Fixed next step | Predictable workflows |
| Conditional edge | Function choosing the next node | Routing and tool loops |
| Checkpointer | Saved state per thread | Memory, pause and resume, replay |
| Interrupt | A pause for outside input | Human approval |
| Sub-graph | A graph used as a node | Specialist agents inside a bigger flow |

**How state updates work.** A node returns only the fields it changes, and LangGraph merges them into the state. For most fields the new value replaces the old one. For fields marked with a reducer, such as the message list with `add_messages`, new values are appended instead. This is why a tool node can return just the new tool message and the history stays intact. Forgetting the reducer is a classic bug: each node then overwrites the conversation with a single message.

**Debugging with checkpoints.** Because every step is saved, you can list a thread's checkpoints, read the state at each one, and even resume from an earlier checkpoint with a changed state to see what would have happened. When a reply goes wrong, this shows which node produced which change, without adding print statements and rerunning.

**Graphs and plain code together.** Not every step needs a model. Validation, database writes and formatting are ordinary nodes with no model call, which keeps them fast, cheap and easy to test.

## A worked example

A Chennai broadband provider wants an assistant for support tickets. Requirements: classify each ticket, handle billing questions with account tools, handle outage questions with a status tool, and get a supervisor's approval before any credit is applied.

The graph: `classify` routes to `billing_agent` or `outage_agent`, each a small tool loop. If the billing agent proposes a credit, the graph routes to `approve_credit`, which interrupts. The supervisor sees the ticket, the proposed ₹300 credit and the agent's reason in their dashboard, approves or edits it, and the run resumes from the checkpoint to `apply_credit` and `reply`.

Because state is checkpointed after every node, when the server restarts mid-ticket nothing is lost. When a customer complains about a reply, you load the thread's checkpoints and see exactly which node did what with which state. Tests call individual nodes with a hand-built state, so the routing logic is unit-tested without any model calls.

| Situation | What the graph did |
| --- | --- |
| Billing question | classify, billing_agent, reply |
| Proposed ₹300 credit | Interrupted at approve_credit; resumed after the supervisor approved |
| Server restart mid-ticket | Resumed from the last checkpoint, nothing lost |
| Customer complaint | Thread checkpoints showed which node wrote the reply and from what state |

## Common mistakes

- **Putting everything in one giant node.** You lose the visibility and testability that are the point of a graph.
- **State that grows without limit.** Appending every tool result forever bloats prompts. Trim or summarise in a node.
- **In-memory checkpoints in production.** A restart loses every paused run. Use a persistent checkpointer.
- **Using a graph where a function would do.** A fixed three-step pipeline does not need a framework.
- **Ignoring versions.** The library moves fast; pin it and read the changelog before upgrading.
