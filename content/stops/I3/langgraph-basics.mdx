## What it is

LangGraph is an open-source Python and JavaScript framework for building agents and multi-step AI workflows as **graphs**. A graph has four parts:

- **State**: a typed dictionary that holds everything the run knows, such as the messages, the ticket id and a proposed credit.
- **Nodes**: functions that read the state and return only the fields they change. A node may call a model, call a tool or run plain code.
- **Edges**: which node runs next. A **conditional edge** is a function that reads the state and returns the next node's name.
- **Checkpointer**: saves the state after every step under a `thread_id`, so a run can pause, resume, survive a restart and be replayed.

An agent loop is a small graph: a model node, a tool node, and a conditional edge that loops between them until the model stops asking for tools. A workflow is a graph with fixed edges. LangGraph lets you mix both in one system.

This lesson builds one graph from start to finish. A broadband provider in Chennai gets support tickets. Billing tickets may lead to a credit for days without service, and a supervisor must approve every credit before it reaches the billing system.

```flow
title: The support-ticket graph (state saved after every step, per thread_id)
START -> classify
classify -[billing]-> billing_agent | looks up outage days, proposes a credit
classify -[outage]-> outage_agent
billing_agent -[credit above zero]-> approve_credit | interrupt: a supervisor decides
billing_agent -[no credit]-> reply
approve_credit -[approved]-> apply_credit | calls the billing system once
approve_credit -[rejected]-> reply
apply_credit -> reply
outage_agent -> END
reply -> END
```

### The whole graph

Read it once from top to bottom. Small stand-ins replace the model and the billing system, so it runs without an API key. Save it as `ticket_graph.py`; the later blocks use its names.

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Ticket(TypedDict, total=False):
    messages: Annotated[list, add_messages]  # reducer: new messages are appended
    ticket_id: str
    category: str              # "billing" or "outage"
    outage_days: int
    proposed_credit_inr: int
    approved_credit_inr: int   # 0 means the supervisor said no
    credit_ref: str

# Stand-ins for real systems, so the graph runs with no API key.
OUTAGE_DAYS = {"TKT-4471": 3}     # the network status tool
CREDITS = {}                      # the billing system, keyed by idempotency key

def add_credit(key: str, amount_inr: int) -> str:
    return CREDITS.setdefault(key, f"CR-{len(CREDITS) + 1:04d}")  # same key, one credit

def classify(state: Ticket) -> dict:
    text = state["messages"][-1].content.lower()   # a model call in real life
    return {"category": "billing" if "bill" in text else "outage"}

def route_ticket(state: Ticket) -> str:
    return "billing_agent" if state["category"] == "billing" else "outage_agent"

def billing_agent(state: Ticket) -> dict:
    days = OUTAGE_DAYS.get(state["ticket_id"], 0)
    return {"outage_days": days, "proposed_credit_inr": min(days * 100, 500)}

def outage_agent(state: Ticket) -> dict:
    return {"messages": [("ai", "There is a fibre cut in your area. We will update you by 6 pm.")]}

def approve_credit(state: Ticket) -> dict:
    decision = interrupt({                          # the run pauses here
        "ticket_id": state["ticket_id"],
        "proposed_credit_inr": state["proposed_credit_inr"],
        "reason": f"{state['outage_days']} days without service",
    })
    # On resume this node runs again from the top, and interrupt() returns the decision.
    return {"approved_credit_inr": decision["credit_inr"] if decision["approved"] else 0}

def apply_credit(state: Ticket) -> dict:
    ref = add_credit(key=state["ticket_id"], amount_inr=state["approved_credit_inr"])
    return {"credit_ref": ref}

def reply(state: Ticket) -> dict:
    amount = state.get("approved_credit_inr", 0)
    text = (f"We have added a ₹{amount} credit to your next bill (ref {state['credit_ref']})."
            if amount else "We checked your account. No credit applies this time.")
    return {"messages": [("ai", text)]}

g = StateGraph(Ticket)
for node in (classify, billing_agent, outage_agent, approve_credit, apply_credit, reply):
    g.add_node(node)                                # the node is named after the function
g.add_edge(START, "classify")
g.add_conditional_edges("classify", route_ticket, ["billing_agent", "outage_agent"])
g.add_conditional_edges("billing_agent",
    lambda s: "approve_credit" if s["proposed_credit_inr"] > 0 else "reply",
    ["approve_credit", "reply"])
g.add_conditional_edges("approve_credit",
    lambda s: "apply_credit" if s["approved_credit_inr"] > 0 else "reply",
    ["apply_credit", "reply"])
g.add_edge("apply_credit", "reply")
g.add_edge("outage_agent", END)
g.add_edge("reply", END)
app = g.compile(checkpointer=InMemorySaver())
```

The credit policy (₹100 per day without service, at most ₹500) is an example for this lesson, not any real provider's rule. In a real system, `classify` would be a model call that returns one label, and `billing_agent` would be a small model-and-tool loop (see the prebuilt agent below). The list at the end of each `add_conditional_edges` call names the nodes the route may return. `app.get_graph().draw_mermaid()` prints the graph as a Mermaid diagram, a quick check that the edges are what you meant.

### How state updates merge

A node returns only the fields it changes, and LangGraph merges them into the state. For most fields the new value replaces the old one. A field with a **reducer**, such as `messages` with `add_messages`, is combined instead: new messages are appended. That is why `reply` can return one message and the customer's message stays. Forget the reducer and every node that writes `messages` wipes out the conversation. This is the most common first bug.

### Pause, approve, resume

Each run names a thread. Here the thread is the ticket, so everything about TKT-4471 lives in one place:

```python
config = {"configurable": {"thread_id": "TKT-4471"}, "recursion_limit": 20}
first = {"ticket_id": "TKT-4471",
         "messages": [("user", "Net was down 3 days. Why is my bill the full ₹799?")]}
out = app.invoke(first, config)
print(out["__interrupt__"][0].value)
# {'ticket_id': 'TKT-4471', 'proposed_credit_inr': 300, 'reason': '3 days without service'}

# Hours later, the supervisor's dashboard resumes the same thread:
out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
print(out["messages"][-1].content)
# We have added a ₹300 credit to your next bill (ref CR-0001).
```

Three rules make approval safe:

- **The node reruns on resume.** LangGraph does not continue from the line after `interrupt()`; it runs `approve_credit` again from its first line, and this time `interrupt()` returns the decision. In a test, a counter placed before `interrupt()` went up twice. So nothing before `interrupt()` may have side effects.
- **Put the action in the next node.** The credit is applied in `apply_credit`, not in `approve_credit`. That node uses the ticket id as an idempotency key, so even if it runs twice the customer gets one credit.
- **The supervisor can edit.** The resume value is whatever your dashboard sends. Sending `{"approved": True, "credit_inr": 250}` applies ₹250.

Without a checkpointer, `interrupt()` still stops the run, but `Command(resume=...)` fails with "Cannot use Command(resume=...) without checkpointer". `compile(interrupt_before=["apply_credit"])` also pauses, but `interrupt()` inside a node lets you send the supervisor exactly the data they need.

### Checkpoints: inspect, replay and fork

Every step is saved, so you can read a thread's history, newest first:

```python
for snap in app.get_state_history(config):
    print(snap.metadata["step"], snap.next, snap.values.get("credit_ref"))
```

To ask "what if the agent had proposed ₹200 and the supervisor had said no?", fork from the checkpoint just before approval:

```python
past = next(s for s in app.get_state_history(config) if s.next == ("approve_credit",))
fork = app.update_state(past.config, {"proposed_credit_inr": 200})
out = app.invoke(None, fork)                       # runs on and pauses again, now at ₹200
out = app.invoke(Command(resume={"approved": False}), config)
print(out["messages"][-1].content)
# We checked your account. No credit applies this time.
```

`invoke(None, ...)` means "continue from this checkpoint with no new input". The fork becomes the latest state; the original steps stay in the history.

### A database checkpointer

`InMemorySaver` lives inside one Python process. A restart or deploy loses every paused ticket. In production, store checkpoints in Postgres, and create the saver once when the server starts, not inside each request:

```python
# pip install "langgraph-checkpoint-postgres==3.2.1" "psycopg[binary,pool]"
import os
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver

pool = ConnectionPool(os.environ["CHECKPOINT_DB_URL"],
                      kwargs={"autocommit": True, "prepare_threshold": 0}, open=True)
saver = PostgresSaver(pool)
saver.setup()                       # creates the checkpoint tables if missing
app = g.compile(checkpointer=saver)
```

The two connection settings are two of the ones `PostgresSaver.from_conn_string` uses (the saver sets its own row factory). That helper is a `with` block that closes the connection at its end, which suits a script but not a web server. Keep the connection string in an environment variable, and call `pool.close()` at shutdown.

With this saver, we paused TKT-4471 in one process, ended it, and approved it from a new process: the thread was still waiting at `approve_credit` and finished normally.

**A crash is different from a pause.** We also killed the process inside `apply_credit`. Nothing restarted the thread by itself. A new process found it at `approve_credit`, because the default mode saves each step in the background and the last one had not been written. `app.invoke(None, config)` reran `approve_credit` with the saved decision, then `apply_credit` and `reply`. With `durability="sync"` passed to `invoke`, each step is saved before the next starts, so the thread waited at `apply_credit` instead. Two lessons follow: a node after the last saved step can run twice, so make side effects idempotent; and you need a small job that continues unfinished threads.

### Streaming progress

Use `stream` instead of `invoke` to see each step as it happens:

```python
demo = {"configurable": {"thread_id": "TKT-4471-demo"}, "recursion_limit": 20}
for update in app.stream(first, demo, stream_mode="updates"):
    print(update)
# {'classify': {'category': 'billing'}}
# {'billing_agent': {'outage_days': 3, 'proposed_credit_inr': 300}}
# {'__interrupt__': (Interrupt(value={...}, ...),)}
```

Each item is one node's update, so a chat screen can show "Checking your connection…" instead of a long silence.

### Testing without a model

Routes and nodes are plain functions, so most tests need no model at all:

```python
def test_billing_ticket_goes_to_billing_agent():
    assert route_ticket({"category": "billing"}) == "billing_agent"

def test_credit_waits_for_approval_then_applies():
    config = {"configurable": {"thread_id": "test-1"}, "recursion_limit": 20}
    out = app.invoke({"ticket_id": "TKT-4471",
                      "messages": [("user", "Why is my bill the full amount?")]}, config)
    assert out["__interrupt__"][0].value["proposed_credit_inr"] == 300
    out = app.invoke(Command(resume={"approved": True, "credit_inr": 300}), config)
    assert out["credit_ref"].startswith("CR-")
```

For nodes that call a model, pass in a fake model with fixed replies, and run a few saved real tickets through the whole graph in CI.

### The prebuilt agent

Older tutorials use `langgraph.prebuilt.create_react_agent`. Since LangGraph 1.0 it is deprecated: calling it warns that it "has been moved to `langchain.agents`". The current prebuilt model-and-tools loop is LangChain's `create_agent`, which runs on LangGraph:

```python
# pip install "langchain==1.5.2" plus your model provider's package
from langchain.agents import create_agent

def outage_days(ticket_id: str) -> int:
    """Days without service on this ticket's connection."""
    return OUTAGE_DAYS.get(ticket_id, 0)

billing_helper = create_agent(chat_model, tools=[outage_days],
                              system_prompt="You answer broadband billing questions.")
out = billing_helper.invoke({"messages": [("user", "Ticket TKT-4471: why is my bill high?")]})
```

`chat_model` is any LangChain chat model that supports tool calling. The result is a compiled graph, so it can be one node of a bigger graph. That is a **sub-graph**. Start with `create_agent` for a plain tool loop. Write your own `StateGraph` when you need routing, approvals or several specialists.

### Limit every run

`recursion_limit` caps the number of steps in one run. When a run reaches it, LangGraph raises `GraphRecursionError`, which you can catch and turn into a handover to a person. Set it yourself on every call: the default was 25 up to LangGraph 1.0.5, 10,000 from 1.0.6 to 1.1.3 and 10,007 from 1.1.4 (including 1.2.24), so a draft-and-check loop that never satisfies itself can make thousands of model calls before the default stops it.

### Beyond the basics

- **Parallel branches.** A conditional edge can return several `Send("node", data)` objects to run one node many times in parallel, for example checking ten connections at once, and a reducer merges the results.
- **Long-term memory.** Checkpoints belong to one thread. Facts that should follow a customer across tickets, such as "prefers Tamil", go in a **store** passed with `compile(store=...)`, for example `InMemoryStore` or a Postgres store.
- **Functional API.** `@entrypoint` and `@task` from `langgraph.func` give checkpoints and interrupts to ordinary Python functions, without drawing a graph.
- **Tracing.** With `LANGSMITH_TRACING=true` and a LangSmith API key, every node's input and output is recorded, so "the bot said something odd" becomes a link you can open.

**The pieces at a glance:**

| Piece | In the ticket graph | The gotcha |
| --- | --- | --- |
| State with a reducer | `messages` uses `add_messages` | Without the reducer, each reply erases the history |
| Conditional edge | `route_ticket` and the two lambdas | Must return one of the names in its list of possible nodes |
| Checkpointer | `InMemorySaver`, then `PostgresSaver` | In memory loses paused tickets on restart |
| `interrupt()` | Inside `approve_credit` | The node reruns from its first line on resume |
| Idempotency key | Ticket id in `add_credit` | Without it, a rerun applies a second credit |
| `recursion_limit` | 20 in every config | The default is now far too high to protect you |

## A worked example

Ticket TKT-4471 arrives in Chennai: "Net was down 3 days. Why is my bill the full ₹799?" The table shows what the checkpointer saved, read with `get_state_history` from a real run of the code above.

| Step | Next node | What changed in the state |
| --- | --- | --- |
| 0 | classify | The customer's message and `ticket_id` are in |
| 1 | billing_agent | `category` = billing |
| 2 | approve_credit | `outage_days` = 3, `proposed_credit_inr` = 300. The run pauses here and the dashboard shows the proposal |
| 3 | apply_credit | After the supervisor approves: `approved_credit_inr` = 300 |
| 4 | reply | `credit_ref` = CR-0001 |
| 5 | (done) | The reply message is appended; there are now two messages |

Notice three things. The pause added no checkpoint of its own: step 2 just says the next node is `approve_credit`. The approval and the side effect are separate steps, so a rerun of `approve_credit` cannot apply a credit. And every value an auditor might ask about (why ₹300, which credit reference) is in a saved state, not hidden inside a prompt.

Two variations on the same ticket:

- **The supervisor rejects it.** The route after `approve_credit` goes straight to `reply`, `apply_credit` never runs, and the customer is told no credit applies.
- **The customer complains a week later.** You open thread TKT-4471, read each step, and can fork from step 2 to test what a different credit would have done, without touching the original history.

## Common mistakes

- **One giant node.** Classifying, looking up, approving and replying in one function throws away the visibility, the testability and the safe pause points that are the point of a graph.
- **Side effects before `interrupt()`.** The node reruns from the top on resume, so an SMS, an email or a credit placed there happens twice.
- **Actions that are not idempotent.** Resumes and crash recovery can run a node again. Pass an idempotency key, such as the ticket id, to every payment, credit or message API.
- **In-memory checkpoints in production.** Every restart or deploy loses paused runs and conversations. Use a database checkpointer and back it up.
- **A new `thread_id` for every message.** The assistant then forgets the conversation each time. Use one thread per conversation or per ticket, and never share one thread between two customers.
- **State that grows without limit.** Appending every tool result forever makes prompts long and costly. Trim or summarise in a node.
- **Trusting the default `recursion_limit`.** In 1.2.24 it is 10,007 steps. Set a small limit and catch `GraphRecursionError`.
- **Copying old tutorials.** Many still use the deprecated `create_react_agent`, or `MemorySaver`, now an alias for `InMemorySaver`. Pin versions and read the changelog before upgrading.

## When you do not need LangGraph

- **A simple tool loop**: the short loop from the agent-loop lesson, `create_agent`, or a model provider's own agent SDK may be enough.
- **A fixed pipeline** with no pauses or branching: ordinary functions called in order are easier to read and debug.
- **A team already on another framework** that covers saved state, pauses and tracing.

LangGraph earns its place when you need saved state per conversation, pauses for people, branching, and the ability to inspect and replay a run.

## From demo to production

- **Use a database checkpointer**, created once at start-up, and back it up like any other production data.
- **Choose durability on purpose.** The default saves in the background; `durability="sync"` saves before each next step, which is worth the extra time around payments and credits.
- **Recover stuck threads.** Run a small job that finds threads left mid-run after a crash and continues them with `invoke(None, config)`.
- **Set `recursion_limit` and a timeout** on every run, and turn `GraphRecursionError` into a handover to a person.
- **Version the graph.** A paused thread resumes into whatever graph is deployed. Add new state fields as optional, and do not rename or remove a node that paused threads may be waiting at. For a breaking change, keep the old graph running until its paused threads finish, or approve or cancel them first.
- **Trace every node** with the thread id, so a support ticket leads straight to its run.
- **Test routes, nodes and a few full tickets** in CI with fake models.
