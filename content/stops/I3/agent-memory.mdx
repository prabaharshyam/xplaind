## What it is

A model call has no memory. Each call sees only what you put in its context. "Memory" in an agent is everything your code stores and feeds back in:

- **Short-term memory**: the current conversation and task state, such as messages so far, tool results and the plan. It lasts for one thread or session.
- **Long-term memory**: information kept across sessions, such as a user's preferences, facts learned ("this customer's GSTIN is..."), summaries of past conversations and lessons from past tasks.

Researchers sometimes split long-term memory further: **semantic** (facts), **episodic** (what happened in past episodes) and **procedural** (how to do things, often stored as instructions).

```text
   SHORT-TERM (one thread)                      LONG-TERM (across sessions)
   thread 5521                                  store, always filtered by user id
   +-----------------------------+              +---------------------------------------+
   | summary of turns 1-24       |              | prefers 7-9 am delivery   (2026-10-02)|
   | last 6 turns in full        |  <-- read -- | allergic to sulfa drugs   (2026-09-14)|
   | cart, prescription, slot    |              | usual order: metformin... (monthly)   |
   +-----------------------------+  -- write -> +---------------------------------------+
            |                                              ^
            v                                              | background job extracts facts
      model call (fits the context window)          after each finished order
```

This lesson follows an online pharmacy in Kolkata building an assistant that helps customers reorder medicines.

## How it works

**Short-term.** Store the thread's messages and state, usually keyed by a thread id, and reload them each turn. Frameworks call this a checkpointer. Long threads outgrow the context window, so you trim (keep the last N turns), summarise older turns into a short note, or drop large tool results once used. Keep the original task and key decisions even when trimming.

**Long-term.** Decide what is worth remembering, then write it to a store: a database table for structured facts, or a vector store for free-text memories retrieved by similarity. Writing can happen in the moment (the agent calls a `save_memory` tool) or afterwards (a background job extracts facts from finished conversations). Reading happens at the start of a task: fetch the user's profile facts and the few memories most relevant to the request.

**Scope and isolation.** Every memory belongs to a scope: one user, one team, one client. Queries must filter by scope, always. A memory store without scoping is a data leak waiting to happen.

**Forgetting.** Memories go stale ("prefers morning delivery" from two years ago) and some must be deletable on request under privacy law. Store when each memory was created and its source, let users see and delete theirs, and expire what no longer matters.

**Where each kind of memory lives:**

| Kind | Example | Store | Lifetime |
| --- | --- | --- | --- |
| Short-term | Messages and cart in this chat | Thread store keyed by thread id | The session |
| Semantic | Delivery preference, allergy | Database table per user | Until changed, expired or deleted |
| Episodic | Summary of last month's order chat | Vector store, filtered by user | Months |
| Procedural | "Always check the prescription first" | System prompt or instructions file | Until the next release |

**When to write memories.** Writing during the chat through a `save_memory` tool is immediate but lets the model decide what matters, and it sometimes saves noise. A background job after the conversation can be more careful: it reads the whole chat, extracts only facts that meet clear rules, and attaches the source. Many teams use both, with the tool limited to things the user explicitly asks to be remembered.

## A worked example

A Kolkata online pharmacy builds an assistant that helps customers reorder medicines.

Short-term: within a chat, the agent keeps the cart, the prescription it is checking and the delivery slot. After 30 turns the thread is summarised into: "Customer reordering monthly diabetes medicines; prescription Rx-5521 verified; cart has 3 items; waiting for slot choice." The full transcript stays in storage for audit, but only the summary and the last six turns go to the model.

Long-term: after each order, a job extracts and saves facts with a source and date:

```text
user 88213 | prefers 7-9 am delivery           | from chat 2026-10-02
user 88213 | allergic to sulfa drugs (stated)   | from chat 2026-09-14
user 88213 | usual order: metformin 500, ...    | from orders, updated monthly
```

Next month the customer types "same as last time". The agent fetches this user's memories, filtered by user id, proposes the usual order and the 7 to 9 am slot, and flags a new item for pharmacist review because of the stated allergy.

The legal team asks how a customer deletes memories. You add a "What the assistant remembers about you" page with a delete button, and a rule that health facts are kept for at most a year unless reconfirmed.

| Request | Without memory | With scoped memory |
| --- | --- | --- |
| "Same as last time" | "Which medicines do you need?" | Proposes the usual order and 7 to 9 am slot |
| A new item in the cart | Added silently | Flagged for pharmacist review because of the stated allergy |
| "Forget my address" | No way to do it | Deleted from the memory page |

## Common mistakes

- **Stuffing the whole history into every prompt.** Cost and latency grow every turn and quality drops. Trim and summarise.
- **No scoping.** One missing filter on user id and a customer sees another's prescriptions.
- **Remembering everything.** Most chat content is noise. Save facts that will change future behaviour.
- **Memories without a source or date.** You cannot judge whether a memory is still true or explain where it came from.
- **No way to forget.** Users and regulators will ask. Build deletion in from the start.
