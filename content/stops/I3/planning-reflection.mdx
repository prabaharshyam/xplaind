## What it is

An agent loop decides one step at a time. Three patterns shape how those decisions are made:

- **ReAct** (reason, act): think briefly, call a tool, read the result, think again. Flexible and simple; the default in most frameworks.
- **Plan-then-execute**: first write a full plan of steps, then carry them out, revising the plan only when something unexpected happens.
- **Reflection**: after producing a result (or periodically), the agent critiques it against the goal or a checklist and fixes what falls short.

They combine: a plan, executed with ReAct-style steps, with a reflection pass before the final answer.

```text
  ReAct                         Plan-then-execute                  + Reflection
  think -> act -> observe       [planner, strong model]            draft
    ^                |            1. website  2. funding              |
    +----------------+            3. founders 4. competitors          v
  (adapts fast, drifts)           5. red flags 6. write            [checks]
                                      |                             code: totals add up
                                  each step: short ReAct loop       model: every claim sourced
                                  (cap 5 tool calls, small model)       |
                                                                    fail -> 1 revision -> final
```

This lesson follows a venture fund in Bengaluru building an agent that writes one-page startup briefs.

## How it works

**ReAct.** Each turn the model writes a short thought ("I need the order status before I can answer"), then a tool call, then sees the observation. It adapts quickly to what it finds. Its weakness is drift on long tasks: after fifteen steps it can forget the original goal or repeat itself.

**Plan-then-execute.** The model, often a stronger one, writes a numbered plan once. A cheaper model or plain code executes each step. Plans make long tasks more predictable, are easy to show a user or approver ("here is what I will do"), and cut cost because the expensive model runs once. The weakness is rigidity: when step 3 reveals something new, the agent must notice and re-plan rather than plough on.

**Reflection.** A second pass asks: does this result meet the requirements? Are the numbers consistent? Did I answer every part? It can be the same model with a critique prompt, a different model, or deterministic checks (tests pass, totals add up, JSON validates). Deterministic checks are cheapest and most reliable; use a model critique only where rules cannot judge.

**Cost and limits.** Each pattern adds calls. Reflection loops need a cap (say, two revision rounds) or they can loop forever on a requirement the model cannot meet.

**Comparing the patterns:**

| Pattern | Strengths | Weaknesses | Best for |
| --- | --- | --- | --- |
| ReAct | Simple, adapts to each result | Drifts on long tasks | Short tasks, a few tool calls |
| Plan-then-execute | Covers every part, cheaper steps, plan visible | Rigid if not re-planned | Long tasks with known parts |
| Reflection | Catches errors before users do | Extra calls; can loop | Outputs with checkable requirements |

**When to re-plan.** Write the rule into the executor: if a step's result contradicts an assumption in the plan, stop and ask the planner for a revised plan from that point. For example, if step 2 finds the startup was acquired last year, the brief needs a different shape, and continuing the original plan would waste steps and produce a misleading document. Log every re-plan, because frequent re-plans suggest the planner's first plans are poor.

**Making reflection useful.** A vague critique prompt such as "improve this" produces vague changes. Give the critic a specific checklist and ask for a pass or fail with a reason for each item. Send only the failed items back for revision. This keeps revisions focused and makes it easy to measure which checks fail most, which tells you what to improve in the main prompt.

## A worked example

A Bengaluru venture fund wants an agent that prepares a one-page brief on a startup from public sources: funding history, founders, product, competitors and red flags.

*Version 1, pure ReAct.* It searches, reads, searches again. On half the companies it spends 25 steps on funding news and never reaches competitors. Briefs are uneven.

*Version 2, plan-then-execute.* A planning call produces:

```text
1. Find the company's website and product description.
2. Find funding rounds (amount, date, lead investor) from news and filings.
3. Identify founders and their backgrounds.
4. List three to five competitors.
5. Look for red flags: lawsuits, layoffs, regulatory action.
6. Write the brief in the template.
```

Each step runs a short ReAct loop with a cap of five tool calls. Every section is now covered and the average cost drops by a third, because steps use a smaller model.

*Version 3, adding reflection.* Analysts find funding totals that do not match the rounds listed. A reflection step checks the draft against a checklist: totals equal the sum of rounds, every claim has a source link, every section is filled. Code checks the arithmetic; a model checks for unsourced claims. Failures go back for one revision. Unsourced claims fall from 11% to 2% of sentences.

| Version | Sections covered | Unsourced claims | Relative cost |
| --- | --- | --- | --- |
| 1: ReAct only | Uneven; competitors often missing | 11% of sentences | 1.0 |
| 2: Plan-then-execute | All six | About 11% | About 0.67 |
| 3: Plus reflection, one revision | All six | 2% | About 0.75 |

## Common mistakes

- **Planning for trivial tasks.** A two-step lookup does not need a plan; it just adds a call.
- **Plans that never change.** When a step's result contradicts the plan, the agent must re-plan, not continue blindly.
- **Endless self-critique.** Cap reflection rounds, and stop when the critique repeats itself.
- **Model critique where code would do.** If a rule can check it (sums, schemas, tests), use the rule.
- **Hiding the plan.** Showing users the plan builds trust and lets them correct the course early.
