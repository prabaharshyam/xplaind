## What it is

Some work is too slow, too unreliable or too bursty to do while a user waits: sending emails and SMS, generating PDFs, resizing images, calling an LLM, syncing with a partner's API. A **message queue** lets one part of the system, the **producer**, drop a message saying "this needs doing", and another part, a **worker** or **consumer**, pick it up and do it later.

The user gets a fast response, the slow work still happens, and if a downstream service is briefly down, the messages wait instead of being lost.

```text
 user ──► [ API ]  1. save order in DB
             │      2. publish "order placed" ──► [ QUEUE ]  ──► worker: send SMS
             │                                        │       ──► worker: update stock
             ▼                                        │       ──► worker: email invoice
       "Order placed!"  (fast)                        │  failures retry with backoff
                                                      ▼
                                              [ DEAD-LETTER QUEUE ] after N failures
```

Common tools are RabbitMQ, Amazon SQS, Google Pub/Sub, Redis-based job queues such as Celery and RQ, and Apache Kafka for high-volume event streams.

## How it works

**Producers and consumers are decoupled.** The API does not need to know how many workers exist or whether they are busy. You can add workers when the queue grows and remove them when it is empty. A spike of orders fills the queue; workers drain it at a steady pace, protecting the database and third-party APIs.

**Delivery and retries.** Most queues offer **at-least-once delivery**: a message stays in the queue until a worker confirms it is done. If the worker crashes before confirming, the message is delivered again. That means the same message can be processed twice, so consumers must be **idempotent**: doing the work twice has the same effect as once. Typical ways are a unique job ID checked before acting, or an "upsert" instead of an insert.

Failed jobs should be retried with **exponential backoff** (wait 1 second, then 2, 4, 8...), because many failures are temporary. After a few attempts, move the message to a **dead-letter queue** so one bad message does not block the rest, and alert someone.

**Task queues versus event streams.** A task queue, such as SQS or RabbitMQ, hands each job to one worker and deletes it when done. An **event stream** such as Kafka keeps an ordered, durable log of events. Several independent **consumer groups**, for example analytics, notifications and fraud checks, each read the whole stream at their own pace, and can replay old events. Kafka handles very high throughput, at the cost of more operational complexity.

| Need | Good fit | Why |
|---|---|---|
| Run background jobs (emails, PDFs, LLM calls) | Celery/RQ on Redis, SQS, RabbitMQ | simple, one worker per job, retries built in |
| Many services react to the same event | Kafka, Pub/Sub | each consumer group reads independently |
| Replay history to rebuild data | Kafka | events are kept for a set period |
| Strict order per key | Kafka partitions by key, SQS FIFO | order kept within a key |
| Very low volume, one server | Python queue + worker thread | no extra infrastructure |

**In interviews**, reach for a queue when you hear "send a notification", "process an upload", "call a slow third-party API" or "handle a spike". Then say the three follow-ups interviewers wait for: what happens on failure (retries, backoff, dead-letter queue), what happens on duplicates (idempotent consumers), and how you would notice a backlog (queue length and job age alerts).

## A worked example

Isha builds an AI study-notes feature for a learning app in Pune. Students upload a chapter PDF and get AI-generated summary notes. Her first version called the LLM inside the upload request. It took 40 to 90 seconds, phones timed out, and when the LLM provider rate-limited them during exam season, uploads simply failed.

She redesigned it around a queue:

1. The upload endpoint stores the PDF in object storage, creates a `notes_job` row with status `queued`, publishes a message with the job ID, and returns within a second. The app shows "Your notes are being prepared".
2. Workers take jobs from the queue, extract the text, call the LLM, save the notes and set the status to `done`. The app polls a status endpoint or receives a push notification.
3. LLM calls that hit a rate limit are retried with exponential backoff and jitter. Worker concurrency is capped so the team never exceeds its provider quota.
4. Workers are idempotent: before calling the LLM, a worker checks whether the job already has notes. A crash after saving but before confirming the message no longer causes a second, paid LLM call.
5. Jobs that fail five times, such as scanned PDFs with no text, go to a dead-letter queue, and the student sees a clear message suggesting they upload a text-based PDF.

During the next exam rush, uploads spiked to ten times normal. The queue grew to a few thousand jobs and drained over twenty minutes; no request timed out, and the monthly LLM bill stayed within budget because concurrency was capped.

## Common mistakes

**Doing slow work in the request.** Users wait, requests time out, and retries from impatient users double the load. Queue it and respond fast.

**Assuming exactly-once processing.** Most queues deliver at least once. Without idempotent consumers you send duplicate SMS, emails or charges.

**Retrying forever without backoff.** Immediate endless retries hammer a struggling service. Use exponential backoff, a retry limit and a dead-letter queue.

**No visibility.** A queue that silently grows means users wait silently. Monitor queue length and job age, and alert on them.

**Using Kafka for a handful of jobs.** It is powerful but heavy to run. A managed task queue is enough for most background work.

**Losing work by acknowledging too early.** Confirm a message only after the work is safely done, or a crash loses it.
