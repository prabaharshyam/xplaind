## What it is

Three habits that make a deployment safe to operate:

- **Separate environments.** Development for building, staging for testing with production-like settings, production for real users. Each has its own database, keys and settings.
- **Secrets management.** Passwords, API keys and tokens live in a secret store, reach the app at run time and never appear in code, images, logs, chat or Terraform state.
- **Infrastructure as code (IaC).** Servers, databases, networks and permissions are described in files, reviewed like code and applied by a tool such as Terraform, instead of being clicked together in a console.

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | own database, own model key, 1 instance
Apply -> Staging | masked data, own model key, 1 instance
Apply -> Production | real data, own model key with a spend limit, 3 instances
The same container image -> Development
The same container image -> Staging
The same container image -> Production
```

Each environment gets its settings from environment variables and its secrets from the vault. Only the values differ; the code and the image are the same. That is the point: if staging passes, production should too.

This lesson follows a lending company in Chandigarh preparing a rushed pilot for production on Azure. The ideas carry over to AWS and Google Cloud with different resource names.

## How it works

### Config in the environment

The same image runs everywhere; only settings differ. Read them from environment variables (`DATABASE_HOST`, `MODEL_NAME`, `LOG_LEVEL`) and validate them at start-up with a settings model. Then a missing value fails loudly on boot, during the deploy, not at 2 am on the first real request.

### What differs between environments

| Value | Example | Where it lives |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, set per environment |
| Secret | Model API key, webhook signing key | Secret store, read through the app's identity |
| Database access | Production database | Managed identity sign-in, so no password exists |
| Infrastructure | Database size, network rules | Terraform files in Git |
| Infrastructure state | Which resources Terraform manages | Remote, locked storage, one state per environment |
| Test data | Masked customer records | Staging database only |

Production also gets more instances, its own model key with a monthly spend limit set at the provider, and far fewer people who can touch it.

### Secret stores and rotation

Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) or tools such as HashiCorp Vault hold secrets, control who can read each one and can log every read. On Azure, reads are only logged once you turn on the vault's diagnostic settings, so do that on day one; an auditor will ask.

The app reads secrets through its **managed identity**: an identity that Azure gives the running app, so the app needs no password to reach the vault. Rotate secrets on a schedule, and at once when someone leaves or a leak is suspected.

Rotation has a catch. An app that reads a secret only at start-up keeps the old value until it restarts. Pick one of three patterns: restart the app after each rotation, reload secrets on a timer, or reload once when a call fails with an authentication error. Some platforms, Azure Container Apps among them, can follow the latest version of a vault secret for you; read your platform's docs to see when it restarts the app. Run a secret scanner in CI so keys never reach the repository at all.

### Terraform: code, plan, apply, state

You write files in HCL, Terraform's configuration language, describing the resources you want. Region and environment are variables, so the same files build any environment anywhere:

```hcl
variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "location" {
  type    = string
  default = "centralindia"
}

resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = var.location
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false

  authentication {
    active_directory_auth_enabled = true
    password_auth_enabled         = false
    tenant_id                     = data.azurerm_client_config.current.tenant_id
  }
}
```

The `authentication` block turns off passwords: the app signs in to Postgres with its managed identity, so there is no database password to leak or rotate.

`terraform plan` compares three things: your code, the **state** file (Terraform's record of the resources it manages), and the real cloud. It then lists what it would create, change or destroy. `terraform apply` makes those changes and updates the state.

### Remote state, one per environment

Every project starts with a backend, so state is shared, locked during an apply and kept off laptops:

```hcl
terraform {
  required_version = ">= 1.11"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 5.15" }
  }
}
```

The code in this lesson was checked with `terraform validate` on Terraform 1.17.2 and the azurerm provider 5.15.0 (November 2026). Pin the versions you have tested. Provider upgrades rename arguments. In azurerm 5.x the Key Vault argument `enable_rbac_authorization` is gone and `rbac_authorization_enabled` is required, so older copied code fails to validate.

How should you split environments? Use this rule:

- **One state per environment, with its own key and, for production, its own access.** A mistake in staging then cannot touch production.
- **Shared code in a module.** A module is a folder of Terraform that each environment calls with its own values, so staging and production stay the same shape.
- **CLI workspaces** keep several states in one backend with the same credentials. HashiCorp's docs say they are not suitable when environments need different credentials or access controls. Use them for short-lived copies, such as one per feature branch, not to separate production.

### Keeping secrets out of code and state

State stores every attribute of every resource, in plain text, including any password you generate with Terraform. Marking a value `sensitive` only hides it from the screen; it is still in state. Three defences, best first:

1. **No secret at all.** Managed identity sign-in, as on the database above.
2. **Write-only arguments** (Terraform 1.11 and later). The provider receives the value but Terraform never stores it. For example, azurerm has `administrator_password_wo` on the Postgres server and `value_wo` on Key Vault secrets, each with a `_wo_version` number you raise to rotate. Terraform 1.10 added **ephemeral resources**, which read a secret from a vault for one run without saving it.
3. **Put the value in outside Terraform.** Terraform creates the vault and the permissions; a person or a pipeline adds the secret value.

```hcl
resource "azurerm_key_vault" "kv" {
  name                       = "claims-${var.env}-kv"
  location                   = var.location
  resource_group_name        = azurerm_resource_group.main.name
  tenant_id                  = data.azurerm_client_config.current.tenant_id
  sku_name                   = "standard"
  rbac_authorization_enabled = true
  purge_protection_enabled   = var.env == "prod"
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

The role assignment lets the app read secret values and nothing else: it cannot change or delete them.

### Validated settings in code

`pydantic-settings` reads environment variables and fails fast:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_host: str
    model_api_key: SecretStr
    model_name: str                  # required: no default, so a missing value stops start-up
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()    # raises one clear error listing every missing or invalid value
```

`model_name` has no default on purpose. A default model name hides the very bug you want to catch, and model names change often. `SecretStr` keeps secrets out of logs and error messages: printing it shows `**********`. The `.env` file is for development only and must be in `.gitignore`.

### Who may apply: the review loop

A change to infrastructure starts as a pull request that edits Terraform files:

1. CI runs `terraform fmt -check`, `terraform validate` and scanners such as `tflint` and Checkov, which flag public storage, open firewall rules and missing encryption.
2. CI runs `terraform plan -out=plan.bin` and posts a summary, such as "1 to add, 0 to change, 0 to destroy".
3. A reviewer reads the plan, not only the code, because a one-line edit can force Terraform to destroy and recreate a database.
4. After approval, a pipeline applies that exact saved plan. For production, add a required approval step (for example a protected GitHub environment) and, if you need hard rules, a policy check such as Open Policy Agent.

The pipeline signs in to Azure through **OpenID Connect (OIDC)**: GitHub Actions proves who it is with a short-lived token, so no long-lived cloud password sits in CI settings. Give the staging pipeline rights on staging only, and the production pipeline rights on production only. Then nobody needs routine console access to production, and nobody runs apply from a laptop.

### Drift: what plan can and cannot see

People still change things in the console during an incident. A nightly job compares production with the code:

```bash
terraform plan -var-file=env/prod.tfvars -input=false -lock=false -detailed-exitcode > plan.txt
case $? in
  0) echo "no changes" ;;
  2) echo "DIFFERENCE: production does not match the code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

Read exit code 2 carefully. It means "plan found a difference". That is either drift (someone changed a managed resource by hand) or code that was merged but never applied. The plan text tells you which. To see only drift, add `-refresh-only`.

The big blind spot: plan only checks resources already in state. A firewall rule created by hand as a separate resource is invisible; the job stays green. Catch those with cloud activity-log alerts or policies, then delete the resource or bring it under Terraform with an import block:

```hcl
import {
  to = azurerm_postgresql_flexible_server_firewall_rule.partner
  id = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/claims-prod-rg/providers/Microsoft.DBforPostgreSQL/flexibleServers/claims-prod-db/firewallRules/partner"
}

resource "azurerm_postgresql_flexible_server_firewall_rule" "partner" {
  name             = "partner"
  server_id        = azurerm_postgresql_flexible_server.db.id
  start_ip_address = "203.0.113.10"
  end_ip_address   = "203.0.113.10"
}
```

The next plan shows "1 to import". `terraform plan -generate-config-out=generated.tf` can draft the resource block for you; that flag is still marked experimental, so review what it writes.

### Try it in your browser

Settings checked at start-up fail fast and clearly. Delete `model_name` from the dictionary and run it again.

```python
from pydantic import BaseModel, SecretStr, ValidationError

class Settings(BaseModel):
    env: str
    model_name: str
    model_api_key: SecretStr
    daily_budget_inr: int

environment = {"env": "staging", "model_name": "example-model", "model_api_key": "sk-test-123", "daily_budget_inr": "500"}
try:
    s = Settings.model_validate(environment)
    print(s.env, s.model_name, s.daily_budget_inr, s.model_api_key)   # the key prints as stars
except ValidationError as err:
    print("start-up stopped, missing or invalid:", [e["loc"][0] for e in err.errors()])
```

## A worked example

The Chandigarh lending company's pilot was built in a hurry. It used one database for testing and real data, kept the model key in a `.env` file committed months ago, and had resources created by hand in the portal.

Before production, you:

1. Revoke and rotate the leaked key and add a secret scanner to CI. It finds two more old keys in history; both are rotated.
2. Write Terraform for the network, the database, storage, the container app and the Key Vault, with `env` and `location` as variables. Import the hand-made resources that should stay, delete the rest, and confirm the plan shows no surprises.
3. Move every secret into Key Vault, and switch the database to managed identity sign-in so no password exists. Staging and production have separate model keys with separate monthly limits.
4. Load staging with masked copies of last month's applications: names, PAN and phone numbers replaced.
5. Apply only from CI: a staging pipeline and a production pipeline, each with its own OIDC identity, and a required approval before production.

When the client's auditor asks "who can read the production model key?", you show the role assignments on the vault and its access log. In a region drill, the team builds a second staging in South India by passing `location = "southindia"` and a new state key. One gotcha surfaced: Key Vault and Postgres server names must be unique across all of Azure, so the copy needs a region suffix in its names. In this example the rebuild took under an hour; yours depends on data size.

| Question from the auditor | Answer before | Answer after |
| --- | --- | --- |
| Where are secrets stored? | "In a .env file" | Key Vault, with an access log |
| Is there a database password? | Yes, in the same file | No, the app signs in with its identity |
| Who can change production? | Several people, through the portal | The production pipeline, after an approved plan |
| How would you know about a manual change? | We would not | Nightly drift check plus activity-log alerts |
| Is test data real? | Yes | No, masked copies |

## Common mistakes

- **Testing against production data.** One bad script and real customers are affected. Separate, and mask test data.
- **Secrets in Git, even briefly.** History keeps them. Rotate any key that was ever committed.
- **Believing `sensitive = true` keeps a secret out of state.** It only hides it from the screen. Use managed identity or write-only arguments.
- **Terraform state on a laptop.** It gets lost or out of date, and it may hold secrets. Use remote, locked state.
- **One state, or CLI workspaces, for staging and production.** A staging change can then reach production, with the same credentials. Use separate states and access.
- **Console changes nobody records.** Changed attributes show up as drift; new resources made by hand do not show up at all. Alert on the activity log and import or delete.
- **Running apply from laptops.** Nobody knows which code was applied. Apply the reviewed plan from CI only.
- **Different shapes per environment.** If staging lacks the private network production has, staging tests prove little.
- **Copying old provider code without pinning versions.** Arguments get renamed between major versions; pin and upgrade on purpose.

## When Terraform is more than you need

- **A single small service** on a platform that manages infrastructure for you.
- **A short-lived prototype** you will delete next month.
- **A client with its own infrastructure team and tool** (such as Bicep, CloudFormation or Pulumi): use theirs.

Check the licence fit too. Terraform from version 1.6 onwards is under the Business Source License, now with IBM as the licensor. Using it to run your own or a client's infrastructure is allowed, but building a competing hosted product on it is not. OpenTofu is an open-source fork under the Mozilla Public License 2.0, run by the Linux Foundation and a CNCF project since 2025, that reads the same HCL. Some clients prefer it for that reason.

Environment variables, validated settings and a secret store are worth having even in the smallest project.

## From demo to production

- **Keep remote, locked state** per environment, with access restricted.
- **Plan in pull requests** and apply only the reviewed plan from CI, signed in through OIDC.
- **Require an approval** before any production apply.
- **Run nightly drift checks** on production, plus alerts for resources created outside Terraform.
- **Scan Terraform** for risky settings in CI.
- **Keep secrets out of state** with managed identity and write-only arguments.
- **Validate settings at start-up**, with secrets as `SecretStr` and read through the app's identity.

## Practice

Follow Terraform's getting-started tutorials for your chosen cloud and read the Twelve-Factor page on config.

1. Write Terraform that creates a storage bucket and a small managed database for `env = "staging"`, with the database not publicly reachable. Apply it, read the plan, then destroy it.
2. Move your app's settings into a validated settings model read from environment variables, with no default for the model name, and make start-up fail clearly when one is missing.
3. Store one secret in your cloud's secret manager and have the app read it through its identity. Then rotate it and confirm the app picks up the new value.
4. In the console, change one setting of a resource Terraform manages and run the drift check: it should exit with 2. Undo that change, then create a new firewall rule by hand and run it again: it exits with 0. Import the rule with an import block.

**You are done when you can** rebuild your staging environment from code, show that no secret exists in your repository or state, and explain what your drift check cannot see.
