## What it is

Three habits that make a deployment safe to operate:

- **Separate environments.** Development for building, staging for testing with production-like settings, production for real users. Each has its own database, keys and settings.
- **Secrets management.** Passwords, API keys and tokens live in a secret store, reach the app at run time and never appear in code, images, logs or chat.
- **Infrastructure as code (IaC).** Servers, databases, networks and permissions are described in files, reviewed like code and applied by a tool such as Terraform, instead of being clicked together in a console.

```flow
Terraform files, reviewed -> Plan -> Apply
Apply -> Development | own database, own model key, 1 instance
Apply -> Staging | masked data, own model key, 1 instance
Apply -> Production | real data, own model key with a spend limit, 3 instances
The same container image -> Development
The same container image -> Staging
The same container image -> Production
```

Each environment gets its settings from the environment and its secrets from the vault.

This lesson follows a lending company in Chandigarh preparing a rushed pilot for production.

## How it works

**Config in the environment.** The same image runs everywhere; only settings differ. Read them from environment variables (`DATABASE_URL`, `MODEL_NAME`, `LOG_LEVEL`) and validate them at start-up with a settings model. Then a missing value fails loudly on boot, not at 2 am on the first real request.

**What differs between environments.** Separate databases (never point staging at production data unless it is masked), separate model API keys with their own spend limits, smaller instance counts outside production, and stricter access to production.

**Secret stores.** Cloud secret managers (AWS Secrets Manager, Azure Key Vault, Google Secret Manager) or tools like HashiCorp Vault hold secrets, control who can read each one and log every access. The app reads them at start-up through its service identity. Rotate secrets on a schedule and immediately when someone leaves or a leak is suspected. Run a secret scanner in CI to catch keys before they reach the repository.

**Terraform.** You write files in HCL describing resources:

```hcl
resource "azurerm_postgresql_flexible_server" "db" {
  name                          = "claims-${var.env}-db"
  resource_group_name           = azurerm_resource_group.main.name
  location                      = "centralindia"
  version                       = "16"
  sku_name                      = var.env == "prod" ? "GP_Standard_D2s_v3" : "B_Standard_B1ms"
  public_network_access_enabled = false
}
```

`terraform plan` shows exactly what will change; a reviewer reads the plan in the pull request; `terraform apply` makes it so. Terraform records what it manages in a **state** file, which must be stored remotely (a storage bucket with locking), never on a laptop, and protected because it can contain sensitive values. One set of files with a variable per environment keeps staging and production alike in shape.

**Where each kind of value belongs:**

| Value | Example | Where it lives |
| --- | --- | --- |
| Non-secret setting | `LOG_LEVEL`, `MODEL_NAME` | Environment variables, set per environment |
| Secret | Database password, model API key | Secret store, read through the app's identity |
| Infrastructure | Database size, network rules | Terraform files in Git |
| Infrastructure state | Which resources Terraform manages | Remote, locked, access-controlled storage |
| Test data | Masked customer records | Staging database only |

**The review loop.** A change to infrastructure starts as a pull request that edits Terraform files. CI runs `terraform plan` and posts the output, such as "1 to add, 0 to change, 0 to destroy". A reviewer reads the plan, not only the code, because the plan shows what will really happen. After approval, a pipeline with its own identity runs `terraform apply`. Nobody needs console access to production for routine changes, which shrinks the number of people who could make a mistake there.

**Validated settings in code.** `pydantic-settings` reads environment variables and fails fast:

```python
from typing import Literal
from pydantic import Field, SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: Literal["dev", "staging", "prod"]
    database_url: SecretStr
    model_api_key: SecretStr
    model_name: str = "claude-sonnet-5-5"            # check the docs for current names
    daily_budget_inr: int = Field(gt=0)
    log_level: Literal["DEBUG", "INFO", "WARNING"] = "INFO"

settings = Settings()        # raises a clear error listing every missing or invalid value
```

`SecretStr` keeps secrets out of logs and error messages: printing it shows `**********`.

**Remote state with locking.** Every Terraform project starts with a backend, so state is shared and two people cannot apply at once:

```hcl
terraform {
  required_version = ">= 1.6"
  backend "azurerm" {
    resource_group_name  = "tfstate-rg"
    storage_account_name = "claimstfstate"
    container_name       = "state"
    key                  = "claims/staging.tfstate"
    use_azuread_auth     = true
  }
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
}
```

Keep one state file per environment (a different `key`), and separate variable files such as `env/staging.tfvars` and `env/prod.tfvars`.

**Secrets without storing them in Terraform.** Let Terraform create the vault and grant the app's identity access; put the secret values in through the vault itself, so they never appear in code or state:

```hcl
resource "azurerm_key_vault" "kv" {
  name                      = "claims-${var.env}-kv"
  location                  = "centralindia"
  resource_group_name       = azurerm_resource_group.main.name
  tenant_id                 = data.azurerm_client_config.current.tenant_id
  sku_name                  = "standard"
  enable_rbac_authorization = true
}

resource "azurerm_role_assignment" "app_reads_secrets" {
  scope                = azurerm_key_vault.kv.id
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_container_app.api.identity[0].principal_id
}
```

**Detect drift on a schedule.** People sometimes change things in the console. A nightly job finds it:

```bash
terraform plan -var-file=env/prod.tfvars -detailed-exitcode -lock=false > plan.txt
case $? in
  0) echo "no drift" ;;
  2) echo "DRIFT: production differs from code"; exit 1 ;;   # alert the team
  *) echo "plan failed"; exit 1 ;;
esac
```

**Scan the code.** Tools such as `tflint` and Checkov flag public storage, open firewall rules and missing encryption in pull requests, before anything is applied.

## A worked example

A Chandigarh lending company's pilot was built in a hurry. It used one database for testing and real data, kept the model key in a `.env` file committed months ago, and had resources created by hand in the console.

Before production, you:

1. Rotate the leaked key and add a secret scanner to CI. It finds two more old keys in history; both are rotated.
2. Write Terraform for the network, the database, storage, the container app and the Key Vault, with `env` as a variable. `terraform apply` builds a clean staging; a reviewed plan builds production.
3. Move every secret into Key Vault; the app reads them through its managed identity. Staging and production have separate model keys with separate monthly limits.
4. Load staging with masked copies of last month's applications: names, PAN and phone numbers replaced.

When the client's auditor asks "who can read the production database password?", you answer with the Key Vault access policy and its access log. When a region outage drill is held, the team rebuilds staging in another region from the same Terraform in 40 minutes.

| Question from the auditor | Answer before | Answer after |
| --- | --- | --- |
| Where are secrets stored? | "In a .env file" | Key Vault, with an access log |
| Who can change production? | Several people, through the console | The deployment pipeline, after review |
| Can you rebuild the system? | Unclear | Yes, from Terraform, in 40 minutes |
| Is test data real? | Yes | No, masked copies |

## Common mistakes

- **Testing against production data.** One bad script and real customers are affected. Separate, and mask test data.
- **Secrets in Git, even briefly.** History keeps them. Rotate any key that was ever committed.
- **Terraform state on a laptop.** It gets lost or out of date, and it may hold secrets. Use remote, locked state.
- **Console changes alongside Terraform.** The next apply reverts or conflicts with them. Change the code.
- **Different shapes per environment.** If staging lacks the private network production has, staging tests prove little.
- **Secret values written in Terraform files**, where they also land in state.
- **One state file for all environments**, so a staging change can touch production.
- **Console changes nobody records**, found months later as drift.

## When Terraform is more than you need

- **A single small service** on a platform that manages infrastructure for you.
- **A short-lived prototype** you will delete next month.
- **A client with its own infrastructure team and tool** (such as Bicep, CloudFormation or Pulumi): use theirs.

Environment variables, validated settings and a secret store are worth having even in the smallest project.

## From demo to production

- **Keep remote, locked state** per environment, with access restricted.
- **Plan in pull requests** and apply only from CI after review.
- **Run nightly drift checks** on production.
- **Scan Terraform** for risky settings in CI.
- **Validate settings at start-up**, with secrets as `SecretStr` and read through the app's identity.

## Practice

Follow Terraform's getting-started tutorials for your chosen cloud and read the Twelve-Factor page on config.

1. Write Terraform that creates a storage bucket and a small managed database for `env = "staging"`, with the database not publicly reachable. Apply it, read the plan, then destroy it.
2. Move your app's settings into a validated settings model read from environment variables, and make start-up fail clearly when one is missing.
3. Store one secret in your cloud's secret manager and have the app read it through its identity.
4. Change one setting in the cloud console by hand, then run the drift check and confirm it reports the difference.

**You are done when you can** rebuild your staging environment from code and show that no secret exists anywhere in your repository.
