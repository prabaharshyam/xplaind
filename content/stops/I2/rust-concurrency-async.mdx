## What it is

**Concurrency** means doing several things in overlapping time: serving many users, downloading many files, running model requests side by side. It is hard because work that runs at the same time can step on shared data. These **data races** cause bugs that appear only under load and are notoriously hard to reproduce.

Rust's ownership rules apply across threads, so data races become compile errors. The Rust community calls this "fearless concurrency".

Rust gives you two styles:

- **Threads** for CPU-heavy work: real operating-system threads running on all your cores.
- **Async** for work that mostly waits, such as network calls. Thousands of lightweight tasks share a few threads, managed by a runtime such as **Tokio**.

```text

 core 2: [resize img 2........]              task B -> wait ... -> resume

 each thread busy computing       tasks take turns while others wait on
                                  the network; thousands per thread
```

## How it works

**Spawning threads.**

```rust
use std::thread;

let handle = thread::spawn(|| {
    (1..=1_000_000u64).sum::<u64>()
});
let sum = handle.join().unwrap();
```

A closure passed to a thread must own its data (`move`), because the thread may outlive the function that started it.

**Sharing data.** To let several threads update the same value, wrap it:

```rust
use std::sync::{Arc, Mutex};

let count = Arc::new(Mutex::new(0));
for _ in 0..4 {
    let c = Arc::clone(&count);
    thread::spawn(move || { *c.lock().unwrap() += 1; });
}
```

`Arc` gives shared ownership across threads; `Mutex` allows one writer at a time. Try to share a plain `Vec` between threads and the compiler refuses, because it is not marked **Sync**.

**Message passing.** Channels let threads talk without sharing memory: one side sends, the other receives. Many designs are simpler this way.

**Async and Tokio.** An `async fn` returns a future, a value that will finish later. `.await` pauses the task until it does, letting the runtime run other tasks meanwhile.

```rust
#[tokio::main]
async fn main() {
    let a = tokio::spawn(fetch("https://example.com"));
    let b = tokio::spawn(fetch("https://example.org"));
    let (ra, rb) = (a.await, b.await);
}
```

| Tool | Best for | Watch out |
|---|---|---|
| `std::thread` | a few CPU-heavy jobs | each thread uses real memory |
| rayon | data-parallel loops (`par_iter`) | CPU work only |
| `Arc<Mutex<T>>` | shared state that changes | hold locks briefly |
| channels (`mpsc`, Tokio channels) | passing work between parts | unbounded queues can grow |
| Tokio tasks | thousands of network waits | never block inside async |

**Futures are lazy.** Calling an `async fn` does nothing until you `.await` it or hand it to `tokio::spawn`. This surprises people coming from JavaScript, where promises start running at once. It also means you choose how tasks combine: `join!` runs several and waits for all, `select!` waits for whichever finishes first, which is how timeouts and cancellation are built.

**How Tokio schedules work.** Tokio starts a small pool of worker threads, usually one per core. Each `spawn` creates a task, a few hundred bytes of state rather than the megabytes a thread needs. When a task awaits a network read, Tokio parks it and runs another task on that thread. When the operating system says the data has arrived, the task is woken and continues. This is why one modest server can hold tens of thousands of open connections.

**Why Rust's async feels strict.** Values held across an `.await` must be safe to move between threads if the task can run on any worker. When the compiler complains that a future is "not Send", it usually means you are holding something like an `Rc` or a lock guard across an await. Drop it before awaiting, or use the async-aware version from Tokio.

## A worked example

Rahul runs the platform team at an ed-tech company in Noida. A Python service sends each student's essay to an LLM for feedback, one at a time. At exam season, 30,000 essays a day arrive and the queue backs up for hours.

He writes a small Rust service with Tokio. Each essay becomes a task. A semaphore limits the service to 50 requests in flight, to respect the API's rate limit:

```rust
use std::sync::Arc;
use tokio::sync::Semaphore;

async fn grade_all(essays: Vec<String>) {
    let limit = Arc::new(Semaphore::new(50));
    let mut jobs = Vec::new();
    for essay in essays {
        let permit = limit.clone().acquire_owned().await.unwrap();
        jobs.push(tokio::spawn(async move {
            let feedback = call_llm(&essay).await;
            drop(permit);          // free a slot for the next essay
            feedback
        }));
    }
    for j in jobs { let _ = j.await; }
}
```

Throughput rises about thirty times on the same small server, because almost all the time was waiting on the network, and waiting costs almost nothing in async Rust. When a teammate later tries to update a shared results list from several tasks without a lock, the compiler stops the build and points to the line.

## Common mistakes

**Blocking inside async code.** `std::thread::sleep` or a heavy loop in an async task stalls every other task on that thread. Use `tokio::time::sleep`, and move CPU work to `tokio::task::spawn_blocking` or rayon.

**Holding a lock too long.** Keep the code between `lock()` and the end of the guard short, and never `.await` while holding a standard Mutex.

**Using `Rc` across threads.** `Rc` is not thread-safe. The compiler will tell you to use `Arc`.

**Unbounded concurrency.** Spawning 100,000 requests at once overwhelms the other service. Limit with a semaphore or a stream with `buffer_unordered`.

**Mixing runtimes.** Libraries built for Tokio may not work on other runtimes. Pick Tokio unless you have a reason not to; most of the ecosystem uses it.
