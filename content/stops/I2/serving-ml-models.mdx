## What it is

**Serving** means making a model's predictions available where they are used. Two main patterns:

- **Batch inference**: score many records on a schedule (nightly churn scores for all customers, weekly demand forecasts for every store) and write results to a table that other systems read.
- **Real-time (online) inference**: an API that scores one request within milliseconds (fraud check at payment time, price suggestion as a seller types).

Choose batch whenever the business can wait; it is simpler, cheaper and easier to monitor.

```flow
title: Batch, nightly
Scheduler -> Load model v7 from the registry -> Compute features as of today -> Score all active loans -> Write loan_id, score, v7, timestamp -> The collections team's ranked list
```

```flow
title: Real time, per request
Application form -> FastAPI service | model v7 loaded at start-up
FastAPI service -> Validate 42 fields
Validate 42 fields -[bad input]-> Reject
Validate 42 fields -> Compute features | the same code as training
Compute features -> Return score and version | in under 80 ms
Return score and version -> Decision | or manual review if the service is down
```

This lesson follows a non-banking finance company in Kolkata serving one default-risk model both ways.

## How it works

**Package the whole prediction path.** The model alone is not enough; preprocessing and feature computation must be identical to training. Package them together (a scikit-learn pipeline, a saved preprocessing object, shared feature code) and version them with the model.

**Batch.** A scheduled job loads the registered model, computes features as of the scoring time, predicts, writes results with the model version and timestamp, and logs counts and score distributions. Use an orchestrator or a simple scheduler.

**Real-time.** A web service (for example FastAPI, or a model-serving framework such as BentoML) loads the model at start-up, validates each request's input with a schema, computes features (often from a feature store for things like "transactions in the last hour"), predicts and returns the score with the model version. Set latency budgets, timeouts and a fallback (a rule-based decision) if the model service fails.

**Input validation.** Reject or flag requests with missing fields, wrong types or values outside training ranges. Silent garbage in gives silent garbage out.

**Versioning and rollout.** Deploy new versions gradually: shadow mode (new model scores alongside the old without affecting decisions), then a canary (a small share of traffic), then full rollout. Compare outcomes and roll back if needed.

**Performance.** Measure p95 latency and throughput. Smaller models, batching requests and precomputing features help. Tree models typically serve in milliseconds on a CPU.

**Logging.** Log inputs (or their summaries), outputs and model version for monitoring and debugging, with personal data masked.

**Batch or real-time:**

| Question | Batch | Real-time |
| --- | --- | --- |
| When is the score needed? | Hours or days later is fine | Within the request |
| Cost | Low: runs on a schedule | Higher: always-on service |
| Monitoring | Counts and distributions per run | Latency, errors and drift per request |
| Failure impact | A late report | A blocked customer journey, so a fallback is needed |
| Typical examples | Churn lists, forecasts, risk reviews | Fraud checks, pricing, credit decisions |

**The rollout path in words.** Shadow mode first: the new version scores every request but its output is only logged. After enough time to see real outcomes, compare how well each version's scores ranked what actually happened, segment by segment. Then a canary at a small share, watching error rates and business measures. Then full rollout, with the previous version still loaded or one deploy away. Each stage has a named owner and a written condition for moving on or rolling back, decided before the stage starts.

**Keeping batch and real-time consistent.** When a model is served both ways, both paths must load the same registered version and call the same feature code. A useful test scores a sample of records through the batch job and through the API and checks that every score matches.

**A real-time service in code.** Load once at start-up, validate inputs against training ranges, record the version with every prediction:

```python
from contextlib import asynccontextmanager
import mlflow.pyfunc, pandas as pd
from fastapi import FastAPI
from pydantic import BaseModel, Field

MODELS = {}

@asynccontextmanager
async def lifespan(app):
    MODELS["champion"] = mlflow.pyfunc.load_model("models:/claims-fraud@champion")
    MODELS["challenger"] = mlflow.pyfunc.load_model("models:/claims-fraud@challenger")
    yield

app = FastAPI(lifespan=lifespan)

class Claim(BaseModel):
    claim_amount_inr: float = Field(gt=0, le=5_000_000)        # the range seen in training
    policy_age_days: int = Field(ge=0, le=20_000)
    hospital_tier: int = Field(ge=1, le=3)
    prior_claims: int = Field(ge=0, le=50)

@app.post("/score")
def score(claim: Claim, user_id: str):
    X = pd.DataFrame([claim.model_dump()])
    main = float(MODELS["champion"].predict(X)[0])
    shadow = float(MODELS["challenger"].predict(X)[0])          # logged, never used for the decision
    log_prediction(user_id, claim, main=main, shadow=shadow)
    return {"score": main, "model": "champion"}
```

Pydantic rejects out-of-range inputs with a clear 422 before the model sees them.

**A canary by user hash.** When the challenger is ready for real decisions, route a stable slice of users to it:

```python
import hashlib

def bucket(user_id: str) -> int:
    return int(hashlib.sha256(user_id.encode()).hexdigest()[:8], 16) % 100

def pick_model(user_id: str, canary_percent: int = 5) -> str:
    return "challenger" if bucket(user_id) < canary_percent else "champion"
```

The same user always gets the same model, which keeps their experience consistent and the comparison clean. Raise the percentage in steps (5, 25, 50, 100) while watching outcomes and errors for each group.

**Batch scoring with a version stamp.**

```python
from datetime import datetime
from zoneinfo import ZoneInfo

def score_batch(in_path, out_path, alias="champion"):
    model_uri = f"models:/claims-fraud@{alias}"
    model = mlflow.pyfunc.load_model(model_uri)
    df = pd.read_parquet(in_path)
    df["score"] = model.predict(df[FEATURES])
    df["model_version"] = mlflow.MlflowClient().get_model_version_by_alias("claims-fraud", alias).version
    df["scored_at"] = datetime.now(ZoneInfo("Asia/Kolkata")).isoformat(timespec="seconds")
    df.to_parquet(out_path)
    print(f"{len(df)} rows; score mean {df['score'].mean():.3f}; share above 0.8: {(df['score'] > 0.8).mean():.1%}")
```

The printed summary is a cheap monitor: a big jump in the mean or the high-score share is worth a look before anyone acts on the list.

**A consistency test.** Score 500 records through both the batch job and the API, and assert the scores match to a small tolerance. A difference means the two paths compute features differently, the most common silent bug in served models.

## A worked example

A Kolkata NBFC (non-banking finance company) has a trained default-risk model.

- **Batch**: every night, all active loans are scored for early-warning risk; the collections team sees a ranked list each morning. The job logs the number of loans scored and the share in each risk band; an alert fires if the counts change sharply.
- **Real-time**: at loan application, a FastAPI service scores the applicant in under 80 milliseconds at p95. It validates 42 input fields with a Pydantic model and computes bank-statement features with the same code used in training. If the service is down, the application is routed to manual review rather than auto-decided.
- **Rollout**: version 7 runs in shadow mode for two weeks beside version 6. Defaults take months to show, so two weeks of shadow scores cannot prove it ranks them better. Instead the team checks that its live scores are stable and sensible, and relies on a back-test on older loans with known outcomes, where it ranked defaults better. It then moves to 20% of traffic, then 100%. The registry keeps version 6 ready for rollback.

One early bug: the service received income in lakhs from one partner channel and in rupees from another. Input range validation caught it on day one.

| Stage for version 7 | Traffic | Outcome |
| --- | --- | --- |
| Shadow | 0% of decisions, 100% scored | Stable live scores; better than version 6 in the back-test |
| Canary | 20% | No rise in errors or complaints |
| Full rollout | 100% | Version 6 kept ready in the registry |

## Common mistakes

- **Real-time when batch would do.** It adds cost and complexity.
- **Re-implementing preprocessing in the service.** Share code with training.
- **No input validation.** Unit mismatches and missing fields silently ruin predictions.
- **All-at-once deployment.** Use shadow and canary releases.
- **No fallback.** Decide what happens when the model is unavailable.
- **No input range checks**, so out-of-range values give confident nonsense.
- **Random canary assignment per request**, so one user sees both models.
- **Batch and real-time paths computing features differently.**

## When you may not need a serving service

- **Scores needed daily or weekly**: a batch job writing to a table is cheaper and simpler.
- **Models small enough to run in the client app or database**, such as rules or a small tree exported as SQL.
- **A hosted ML platform** the client already runs, which provides endpoints, canaries and monitoring.

## From demo to production

- **Load from a registry alias** and log the version with every prediction.
- **Validate inputs** against training ranges.
- **Roll out with shadow, then a hash-based canary**, watching outcomes per group.
- **Test batch and real-time consistency** in CI.
- **Track p95 latency, errors and score distributions.**
