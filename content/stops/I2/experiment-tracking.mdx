## What it is

**Experiment tracking** logs each training run automatically: the code version (a Git commit), the data version, the parameters, the metrics, the environment (library versions), artefacts such as plots, and the trained model. Each run becomes a row you can sort, compare and reproduce.

A **model registry** is a shelf of chosen model versions. Each version has notes, tags (for example, who approved it) and can carry an **alias**: a movable name such as `champion` that points at exactly one version. Production loads the alias, never a file path, so the deployed model is always known.

Common tools are MLflow (open source), Weights & Biases, and the tracking built into cloud ML platforms. This lesson uses MLflow 3. In MLflow, aliases replace the older fixed stages (Staging, Production): stages have been deprecated since version 2.9, and calling them in MLflow 3.18 prints a warning that they will be removed.

```flow
title: From training run to production
Training run 412 | commit a1b2c3d, data claims-2026-09, val PR AUC 0.46
Training run 412 -[team picks it and registers it]-> claims-fraud v14
claims-fraud v14 -[gate on October claims, then owner signs off]-> Alias champion
Alias champion -[loaded at start-up]-> Claim scoring service
Alias champion -[rollback: point it back]-> claims-fraud v13
```

This lesson follows the ML team at an insurer in Hyderabad that retrains its claim-fraud model every month.

## How it works

### Log everything that defines a run

| Item | Example | Why it matters | Who records it |
| --- | --- | --- | --- |
| Parameters | `max_depth=6`, `learning_rate=0.05` | Explains differences between runs | You, or autologging |
| Metrics | PR AUC overall and per region | Picks the winner and shows who it fails | You (segments always) |
| Code version | Git commit, clean tree | Reproduces the training logic | MLflow, when run as a script in a Git repo |
| Data version | `claims-2026-09` plus a hash | Reproduces the inputs | You |
| Environment | `requirements.txt`, Python version | Avoids "works on my machine" | MLflow, with every logged model |
| Model and schema | Model file, input columns and types | Lets serving reject wrong inputs | You, through `log_model` |
| Seed | `random_state=42` | Makes reruns give the same model | You |

Two rules make this trustworthy.

- **The commit must describe the code that ran.** MLflow records the commit as the tag `mlflow.source.git.commit` when you run a script inside a Git repository, but it does not notice uncommitted edits. A run from a half-edited file or a notebook points at a commit that never produced it. So the script below refuses to run with uncommitted changes. In a notebook, commit first or move the training code into a script.
- **A data name is not a data version.** `claims-2026-09` is only a label; someone can overwrite the file behind it. Store snapshots that are never edited in place, and log a hash of the file so a silent change shows up. Tools such as DVC, or the time travel in table formats such as Delta Lake, keep old versions for you (see the data versioning lesson).

**Autologging** (`mlflow.autolog()`) captures most parameters and metrics for libraries such as scikit-learn and XGBoost with one line. It cannot know your data version or your segments, so add those yourself.

### Tracking a training run

This script trains the fraud model and logs one run. It assumes the claims table has a `region` column, a `region_code` feature and an `is_fraud` label.

```python
import hashlib, subprocess, sys
import mlflow
import pandas as pd
from mlflow.models import infer_signature
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import average_precision_score
from sklearn.model_selection import train_test_split

DATA = "data/claims-2026-09.parquet"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]

def git(*args):
    return subprocess.run(["git", *args], capture_output=True, text=True, check=True).stdout.strip()

if git("status", "--porcelain", "--untracked-files=no"):   # ignores mlflow.db and mlruns/
    sys.exit("Uncommitted changes: commit first, or this run cannot be reproduced.")

with open(DATA, "rb") as f:
    data_sha = hashlib.file_digest(f, "sha256").hexdigest()[:12]   # Python 3.11 or newer

df = pd.read_parquet(DATA)
df[FEATURES] = df[FEATURES].astype("float64")      # floats can hold missing values at serving time
train, val = train_test_split(df, test_size=0.2, stratify=df["is_fraud"], random_state=42)
params = {"max_depth": 6, "learning_rate": 0.05, "max_iter": 300, "random_state": 42}

mlflow.set_experiment("claims-fraud")
with mlflow.start_run() as run:
    mlflow.set_tags({"data_version": "claims-2026-09", "data_sha256": data_sha})
    mlflow.log_input(mlflow.data.from_pandas(train, source=DATA, targets="is_fraud"), context="training")
    mlflow.log_params(params)

    model = HistGradientBoostingClassifier(**params).fit(train[FEATURES], train["is_fraud"])
    proba = model.predict_proba(val[FEATURES])
    mlflow.log_metric("val_pr_auc", average_precision_score(val["is_fraud"], proba[:, 1]))
    for region, part in val.groupby("region"):
        s = model.predict_proba(part[FEATURES])[:, 1]
        mlflow.log_metric(f"val_pr_auc_{region}", average_precision_score(part["is_fraud"], s))

    mlflow.sklearn.log_model(
        model, name="model",
        signature=infer_signature(val[FEATURES], proba),
        input_example=val[FEATURES].head(3),
        pyfunc_predict_fn="predict_proba",
        skops_trusted_types=["sklearn.ensemble._hist_gradient_boosting.predictor.TreePredictor"],
    )
    print("run", run.info.run_id)
```

What each MLflow 3 detail does (checked on MLflow 3.18, November 2026):

- **`name="model"`** replaces the old `artifact_path` argument, which still works but now logs a deprecation warning.
- **No `registered_model_name`.** Registering inside the training script would create a registry version for every experiment. Log every run; register only the winner.
- **`signature` and `input_example`** store the input columns and types with the model, so serving can reject a request with a missing or misspelled column. The features are cast to floats first: a column inferred as integer fails the check when a value is missing at serving time. Every caller must then send floats too; the check rejects integer columns. (MLflow may still print a hint about integer columns: it refers to the `is_fraud` label in the logged dataset, not the model.) MLflow also writes `requirements.txt` and `conda.yaml` next to the model.
- **`log_input`** links the run to the dataset and stores a short digest of it, a second check besides your own hash.
- **`pyfunc_predict_fn="predict_proba"`** makes the generic loader return fraud probabilities, not hard 0 or 1 labels.
- **`skops_trusted_types`.** MLflow now saves scikit-learn models with skops, a safer format than pickle, because loading a pickle can run any code hidden in the file. Skops refuses object types it has not been told to trust, and `HistGradientBoostingClassifier` needs this one. Trust only types you have checked, and only for models you trained yourself.

By default MLflow 3.18 writes runs to a local SQLite file, `mlflow.db`, in the folder you run from. Run `mlflow ui` there to browse them.

### Compare runs, then register the winner

```python
import mlflow
from mlflow import MlflowClient

runs = mlflow.search_runs(experiment_names=["claims-fraud"],
                          order_by=["metrics.val_pr_auc DESC"], max_results=10)
print(runs[["run_id", "params.max_depth", "params.learning_rate",
            "metrics.val_pr_auc", "metrics.val_pr_auc_east"]].to_string(index=False))

client = MlflowClient()
run_id = runs.loc[0, "run_id"]        # in real life: the run the team chose after reading the table
model_id = client.get_run(run_id).outputs.model_outputs[0].model_id
mv = mlflow.register_model(f"models:/{model_id}", "claims-fraud")
client.update_model_version("claims-fraud", mv.version,
    description="Adds the claim-within-30-days feature; trained on claims-2026-09.")
print("registered version", mv.version)
```

In MLflow 3 a logged model is its own object with an id such as `m-5f3a...`, linked to the run that made it, so you register it by `models:/` and that id. The older `runs:/` form still works but now warns that the run holds no model files. The version's description and tags act as a small **model card**: what changed, what data it saw, known limits, who approved it.

### The promotion check: same data, real gains, every segment

Here is the trap. The champion's logged PR AUC came from last month's validation split; the candidate's came from this month's. Fraud patterns and the share of fraud change month to month, so comparing those two numbers compares the data as much as the models. The fair test scores **both models on the same fresh holdout** that neither trained on: here, October's claims.

The insurer's rule has three parts:

1. **Overall gain must be clear of noise.** Resample the holdout claims many times (a bootstrap) and recompute the PR AUC gain each time. Promote only if the 90% interval of the gain stays above zero.
2. **No region may lose fraud-catching recall.** Investigators can check only the top 5% of claims each month. For each region, measure the share of its fraud cases that land in that top 5%. No region may drop by more than 2 points.
3. **An owner signs off** after reading the check's report.

```python
import numpy as np
import pandas as pd
import mlflow
from mlflow import MlflowClient
from sklearn.metrics import average_precision_score

NAME = "claims-fraud"
FEATURES = ["claim_amount", "days_since_policy_start", "prior_claims", "garage_claims_90d", "region_code"]
REVIEW_RATE = 0.05        # investigators can check the top 5% of claims each month
MAX_RECALL_DROP = 0.02    # no region may lose more than 2 points of recall
client = MlflowClient()

def scores_of(version, X):
    model = mlflow.pyfunc.load_model(f"models:/{NAME}/{version}")
    return model.predict(X)[:, 1]          # column 1 = probability of fraud

def recall_by_region(y, s, region):
    flagged = np.zeros(len(s), dtype=bool)
    flagged[np.argsort(-s)[: int(len(s) * REVIEW_RATE)]] = True   # the claims investigators open
    return {r: flagged[(region == r) & (y == 1)].mean() for r in np.unique(region)}

def pr_auc_gain_interval(y, s_new, s_old, n=500, seed=0):
    rng = np.random.default_rng(seed)
    gains = []
    for _ in range(n):
        i = rng.integers(0, len(y), len(y))   # resample claims with replacement
        gains.append(average_precision_score(y[i], s_new[i]) - average_precision_score(y[i], s_old[i]))
    return np.percentile(gains, [5, 95])

def check(candidate, holdout):
    champion = client.get_model_version_by_alias(NAME, "champion").version
    X = holdout[FEATURES].astype("float64")      # match the logged signature, or loading code rejects it
    y, region = holdout["is_fraud"].to_numpy(), holdout["region"].to_numpy()
    s_new, s_old = scores_of(candidate, X), scores_of(champion, X)

    low, high = pr_auc_gain_interval(y, s_new, s_old)
    problems = []
    if low <= 0:
        problems.append(f"PR AUC gain not clear: 90% interval {low:+.3f} to {high:+.3f}")
    r_new, r_old = recall_by_region(y, s_new, region), recall_by_region(y, s_old, region)
    for r in r_old:
        if r_new[r] < r_old[r] - MAX_RECALL_DROP:
            problems.append(f"{r}: recall {r_old[r]:.2f} -> {r_new[r]:.2f}")
    return champion, problems

holdout = pd.read_parquet("data/claims-2026-10.parquet")    # last month: neither model trained on it
champion, problems = check(candidate="14", holdout=holdout)
print("blocked:" if problems else "passed: ready for owner sign-off", problems)
```

Three cautions. The holdout must stay a judge, not a coach: if people tune models until they pass on October's claims, October stops being fresh. The 2-point limit is a business decision; agree it with the fraud team before anyone sees results. And a region with about 150 fraud cases moves 2 points when just three cases change sides, so this guardrail is noisy on purpose: it blocks a fine model now and then, which is the cheaper error. A blocked model goes to a person, not the bin.

### Promote and roll back by moving aliases

```python
from mlflow import MlflowClient
NAME = "claims-fraud"
client = MlflowClient()

def promote(candidate, champion, approver):
    client.set_model_version_tag(NAME, candidate, "approved_by", approver)
    client.set_registered_model_alias(NAME, "previous", champion)
    client.set_registered_model_alias(NAME, "champion", candidate)

def rollback():
    previous = client.get_model_version_by_alias(NAME, "previous").version
    client.set_registered_model_alias(NAME, "champion", previous)
```

The serving code loads `mlflow.pyfunc.load_model("models:/claims-fraud@champion")`. A running server loaded the model once, at start-up, so moving the alias changes nothing until the service reloads or restarts. Make the reload part of the promotion and rollback steps, and log the served version with each prediction so lineage reaches all the way to a single decision.

### Is the gain real? Try it in your browser

Two models score the same 6,000 claims, about 3% of them fraud. The candidate looks better, but the bootstrap asks whether the gain would survive a different month of similar claims.

```python
import numpy as np
from sklearn.metrics import average_precision_score

rng = np.random.default_rng(7)
n = 6000                                    # one month of claims, about 3% of them fraud
y = (rng.random(n) < 0.03).astype(int)
signal = 2.5 * y + rng.normal(0, 1, n)      # the pattern both models learned
champion = signal + rng.normal(0, 0.60, n)  # each model adds its own errors
candidate = signal + rng.normal(0, 0.55, n) # slightly fewer errors

print("champion PR AUC ", round(average_precision_score(y, champion), 3))
print("candidate PR AUC", round(average_precision_score(y, candidate), 3))

gains = []
for _ in range(200):                        # resample the same claims for both models
    i = rng.integers(0, n, n)
    gains.append(average_precision_score(y[i], candidate[i]) - average_precision_score(y[i], champion[i]))
low, high = np.percentile(gains, [5, 95])
print(f"90% interval for the gain: {low:+.3f} to {high:+.3f}")
print("promote" if low > 0 else "too close to call: keep the champion")
```

It prints PR AUC 0.439 against 0.472, yet the interval runs from about -0.02 to +0.07: a 0.03 gain on fewer than 200 fraud cases is not yet proof. Change the candidate's `0.55` to `0.30` and run again: now the gain is large enough to promote.

### The same idea for LLM apps

Treat a prompt or retrieval change as an experiment. Log the prompt version, model name, top-k, chunk size and eval scores per category as a run. Then "did version 13 of the prompt help Hindi questions?" is a sorted table, not a memory. The same noise rule applies: a 2-point gain on 50 eval questions is usually chance.

## A worked example

The Hyderabad insurer's ML team retrains its claim-fraud model monthly. Before tracking, models were files named like `final_v3_really_final.pkl`, and when an auditor asked which data trained the production model, nobody could say.

Now every run logs its parameters, commit, data snapshot and hash, and validation PR AUC overall and per region. The numbers below are illustrative.

| Run | Change | Val PR AUC (own split) | Weakest region | Decision |
| --- | --- | --- | --- | --- |
| 398 | Last month's champion, v13, trained on August data | 0.41 | 0.33 | Baseline |
| 405 | Deeper trees | 0.42 | 0.31 | Dropped: weakest region fell |
| 409 | New feature: claim within 30 days of policy start | 0.45 | 0.38 | Promising |
| 412 | New feature, tuned learning rate | 0.46 | 0.39 | Registered as v14 |

The tempting conclusion is "0.46 beats 0.41, promote". But run 398 was scored on August's validation split and run 412 on September's. So the gate scores v13 and v14 on October's 20,000 claims, about 600 of them fraud:

- PR AUC: v13 0.40, v14 0.44. The 90% bootstrap interval of the gain is +0.02 to +0.06, so the gain is real.
- Recall in the top 5% by region: north 0.52 to 0.55, south 0.48 to 0.53, east 0.44 to 0.47, west 0.50 to 0.49. West dips 1 point, inside the 2-point limit.

The check passes. The fraud analytics lead reads the report, `promote` records her name as a tag and moves `champion` to v14 and `previous` to v13, and the scoring service reloads.

Six months later the auditor asks about one disputed claim. The prediction log shows v14 scored it; v14 points to run 412, commit `a1b2c3d`, snapshot `claims-2026-09` with its hash, and the gate report. The answer takes minutes. In the spreadsheet era, run 405 might well have shipped on its overall score.

**In banking and lending, expect the same questions in writing.** In August 2025 the RBI published the FREE-AI report, written by a committee it set up, on responsible AI in finance. Among its recommendations, regulated entities should keep an inventory of their AI models and audit them on a risk basis. These are recommendations, not rules, but a registry with lineage, approvals and model cards is the raw material for both.

## Common mistakes

- **Tracking by hand in spreadsheets.** It is incomplete, goes stale and never records the data version.
- **Treating a data name as a data version.** A file overwritten under the same name breaks reproducibility silently; log a hash and keep snapshots read-only.
- **Logging a commit for code that was not committed.** Notebook edits and uncommitted changes make the commit tag a lie.
- **Comparing logged metrics from different months.** Score champion and candidate on the same fresh holdout.
- **Promoting on a tiny gain.** With a few hundred positive cases, a 0.01 to 0.03 change can be chance.
- **Promoting on the overall score only.** A gain overall can hide a loss for one region or customer group.
- **Reusing the test set to pick models.** Once you tune against it, it no longer measures the future.
- **Registering every run.** The registry fills with experiments; register only what you might ship.
- **Loading a file path in production.** Serve from a registry alias, keep a `previous` alias, and reload the service when the alias moves.
- **Integer input columns that can be empty.** An inferred signature marks them as integers, so a missing value at serving time fails the schema check; use floats for such columns.
- **Deleting failed runs, or tracking on one laptop.** Failed runs show what does not work, and history on one laptop leaves with it.

## When tracking can be lighter

- **A single quick experiment**: a notebook with results written down may do.
- **Prompt-only prototypes**: a spreadsheet of prompt versions and scores is a fine start, until more than one person changes prompts.
- **A model trained once and rarely changed**: record its lineage once, carefully, and still serve it from a registry.

## From demo to production

- **Run a shared tracking server** with a database backend and cloud storage for artefacts, behind the company's sign-in, for example `mlflow server --backend-store-uri postgresql://... --artifacts-destination s3://...`. Back it up: it is the history of every model decision.
- **Make tracking automatic in the pipeline**, so a run cannot happen without being logged.
- **Gate promotion in code** on the same fresh holdout, with noise and segment checks, then require an owner's sign-off.
- **Serve from an alias**, log the served version with every prediction, and rehearse a rollback before you need one.
- **Track prompt and retrieval experiments** the same way as training runs.
