## What it is

**Experiment tracking** logs each training run automatically: the code version (Git commit), data version, parameters, metrics over time, artefacts such as plots, and the trained model. A **model registry** stores chosen model versions with their metadata and a label such as an alias (for example, "production"), so deployment always uses a known, approved model.

Tools include MLflow (open source), Weights & Biases, and cloud ML platforms' built-in tracking. Recent MLflow versions use movable aliases for this; its older fixed stages (Staging, Production) are deprecated.

```text
   training run 412
   +----------------------------------------------+
   | params:  depth=6, lr=0.05, features=v3        |
   | code:    git a1b2c3d     data: claims-2026-09 |
   | metrics: PR AUC 0.46, per-region scores       |
   | artefacts: model.pkl, confusion.png           |
   +----------------------------------------------+
                  | best run, approved
                  v
   model registry:  fraud-model  v13 (previous)   v14 --> alias "production"
                  |
                  v
   production service loads "fraud-model@production"   (rollback = move the alias to v13)
```

This lesson follows the ML team at an insurer in Hyderabad that retrains its claim-fraud model every month.

## How it works

**Log everything that defines a run.** Parameters (learning rate, depth, features used), metrics (validation and test scores, by segment), the Git commit, the dataset version or hash, the environment (library versions), and outputs (model file, confusion matrix, feature importance plot).

**Compare runs.** A tracking UI lists runs with their parameters and metrics, sorts by score and plots metrics across runs. You can see that depth 6 beat depth 8, or that a new feature helped only on one segment.

**Reproduce.** With code, data and parameters recorded, anyone can rerun and get the same model (within randomness, controlled by seeds).

**Register the winner.** Promote the chosen run's model to the registry as a new version, with notes: what changed, evaluation results, who approved. Production loads "the production version" from the registry rather than a file path.

**Promotion rules.** Before promoting: the model beats the current production model on the agreed metrics, including key segments; passes checks on recent data; and has an owner's approval. Keep the previous version ready for rollback.

**Lineage.** For audits and debugging, the chain should be clear: production model version → training run → code commit → data version → evaluation results.

**What to log, and why:**

| Item | Example | Why it matters |
| --- | --- | --- |
| Parameters | `depth=6`, `learning_rate=0.05` | Explains differences between runs |
| Metrics | PR AUC 0.46 overall, by region | Picks the winner fairly |
| Code version | Git commit `a1b2c3d` | Reproduces the training logic |
| Data version | `claims-2026-09`, with a hash | Reproduces the inputs |
| Environment | Library versions, Python version | Avoids "works on my machine" |
| Artefacts | Model file, plots, feature importance | Lets reviewers inspect results |
| Seed | `random_state=42` | Controls randomness |

**Adding it to a script.** With MLflow, tracking is a few lines: start a run, log parameters and metrics as you compute them, log the model at the end, and set tags for the commit and data version. The library records the run in a local folder or a tracking server the team shares. Turn on autologging for libraries such as scikit-learn and XGBoost to capture most parameters and metrics without extra code, then add the data version and segment metrics yourself, since no tool can guess those.

## A worked example

A Hyderabad insurer's ML team retrains its claim-fraud model monthly. Before tracking, models were files named like `final_v3_really_final.pkl`, and nobody could say which data version production used when an auditor asked.

With MLflow:

- Every training run logs parameters, the Git commit, the data snapshot id, overall and per-region PR AUC, and the model.
- A comparison view shows that adding "claim filed within 30 days of policy start" improved PR AUC from 0.41 to 0.46 overall, and most in two regions.
- The best run is registered as version 14 with notes and the reviewer's name; production loads the registry's production alias.
- A promotion check script compares the candidate with the current production version on last month's claims and blocks promotion if any region's recall drops more than two points.

When the auditor returns six months later, the team shows the full lineage for the model that flagged a disputed claim in minutes.

| Run | Change | PR AUC overall | Weakest region | Decision |
| --- | --- | --- | --- | --- |
| 398 | Last month's production model | 0.41 | 0.33 | Baseline |
| 405 | Deeper trees | 0.42 | 0.31 | Rejected: weakest region fell |
| 409 | New feature: claim within 30 days of start | 0.45 | 0.38 | Promising |
| 412 | New feature, tuned learning rate | 0.46 | 0.39 | Registered as v14 after review |

The comparison view made run 405's regional drop visible at a glance. In the spreadsheet era, it would have been promoted on its overall score.

## Common mistakes

- **Tracking by hand in spreadsheets.** It is incomplete and goes stale.
- **Not logging data versions.** Code and parameters alone cannot reproduce a model.
- **Loading models from file paths in production.** Use the registry so the deployed version is explicit.
- **Promoting on overall score only.** Check segments and recent data.
- **No rollback plan.** Keep the previous version ready.
- **Logging only the final run.** Failed experiments teach the team what does not work; keep them.
- **Forgetting the seed.** Without it, two runs of the same code and data can give different models.

## Practise

Read MLflow's tracking guide and the experiment tracking and versioning lessons of Made With ML.

1. Add tracking to a training script: parameters, metrics, Git commit, data hash and the model.
2. Run ten experiments varying two settings and compare them in the tracking UI.
3. Register the best model, write a promotion check against a "current production" model, and load the registered model in a separate prediction script.

**You are done when you can** trace a prediction back to the run, code commit and data version that produced the model.
