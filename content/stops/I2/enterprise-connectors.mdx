## What it is

A **connector** is the code that moves data between a business system and your AI system. A good connector does four jobs: it copies everything once, keeps the copy current, removes what was deleted, and carries who may read each item. Most enterprise AI projects need several:

- **Documents**: SharePoint and OneDrive (through Microsoft Graph), Google Drive, Confluence, network file shares, cloud storage buckets.
- **Records**: CRM systems such as Salesforce, ERPs such as SAP, ticketing such as Jira or ServiceNow, plus the client's own databases.
- **Messages**: email and chat, used carefully because of privacy.

You can build connectors yourself, use an integration platform (Airbyte, Fivetran and others offer many ready-made ones), or use the connectors bundled with a search or AI platform. Either way you must understand what they do.

```flow
title: A connector feeding an assistant
SharePoint -[Graph, OAuth, delta]-> Connector | pages, backs off, resumes
Salesforce -[REST, SystemModstamp, get deleted]-> Connector
Jira, SAP, file shares -> Connector
Connector -> Items, metadata, permissions, deletions -> Parse, chunk, embed -> Index for the assistant
Parse, chunk, embed -> Run log | read 312, added 12, changed 41, unchanged 253, deleted 6, failed 0
```

This lesson follows a Gurugram sales assistant built on SharePoint and Salesforce.

## How it works

### Authentication

Usually OAuth with an app registered by the client's IT team, scoped to read-only and to the sites, objects or projects agreed. Some systems use API keys or service users; keep those in a secret manager, never in code.

Two things break long runs. First, access tokens expire: Microsoft gives them a default life of 60 to 90 minutes, so a two-night first load cannot use one token. Ask your auth library's cache (for example MSAL) for a token before each request; it fetches a new one near expiry. Second, client secrets and certificates expire too. Put the date in the runbook and alert a month before.

### Reading in pages

APIs return results in pages. Each page ends with a cursor or a "next" link. Loop until there is no next page. The rule that matters: **save your position after each page is fully processed**, not before and not only at the end. Saving before processing skips items if you crash; saving only at the end means a crash at page 9,000 restarts at page 1.

### Rate limits

Every API limits calls. Microsoft Graph returns 429 Too Many Requests with a `Retry-After` header and asks you to wait that long before retrying; if there is no header, back off exponentially. Under the HTTP standard, `Retry-After` can be a number of seconds or a date, so parse both. Add a second or so of random jitter so that parallel workers do not all retry at the same moment and get throttled again.

### Incremental sync and change detection

The first run copies everything; later runs fetch only what changed. Nightly full re-reads of 200,000 documents are slow, costly and get you throttled.

| Method | Example | Reports deletions? | Watch out for |
| --- | --- | --- | --- |
| Delta token | Microsoft Graph delta | Yes | Links can stop working (410 Gone); keep a full re-scan path |
| Modified-since filter | Salesforce `SystemModstamp`, Jira `updated` | No | Pair with a deletion feed; overlap windows by a few minutes |
| Deletion feed | Salesforce get-deleted resource | Only deletions | Salesforce keeps at most 15 days |
| Webhooks | Jira `jira:issue_deleted` | If the event exists | Deliveries can be lost; never the only source |
| Full id comparison | Your weekly reconciliation | Yes, by difference | Slow on large sets; run it weekly as a safety net |

Two Graph delta gotchas: the same item can appear more than once in one feed (the last occurrence wins, so upsert by source id), and a deleted item comes back with a `deleted` marker and no content, so check for it before downloading.

### Deletions

A modified-since query cannot see a record that no longer exists, so deleted documents keep being quoted. Every connector needs a feed that reports deletions or a periodic id comparison, preferably both.

### Permissions

The hardest part: an assistant that ignores permissions shows a junior employee the salary review deck.

- **Read access rights with each item.** Graph's permissions endpoint returns a file's effective sharing, including access inherited from folders. Store allowed user and group ids on every chunk.
- **Keep groups as groups.** Do not expand "Sales North" into 400 user ids at index time. At query time, look up the user's current groups (from their sign-in token or a directory call) and filter by them. A person who leaves a group then loses access as soon as your group lookup sees the change, with no re-index.
- **Permission-only changes are hard to see.** Sharing a file does not change its content. Graph delta can mark items that changed sharing if you send the `Prefer: deltashowsharingchanges` header, together with `deltashowremovedasdeleted` and `deltatraversepermissiongaps`, which Microsoft says it requires. But Microsoft documents that delta returns only items whose content or metadata changed, plus their parent folders, so files that only inherit access may not appear. Microsoft also says processing permissions correctly needs the `Sites.FullControl.All` app permission, which security teams often refuse. Treat the marker as a hint. Back it with a scheduled re-read of permissions on the sites and folders the client marks as sensitive.
- **Fail closed.** If you cannot read an item's permissions, do not index it.

### An incremental connector in code

This sync for one SharePoint library follows the rules above. It saves its position per page, keeps a retry list for failed items, refreshes tokens, and handles throttling and a broken delta link:

```python
import email.utils, hashlib, json, random, time
from pathlib import Path        # client below is an httpx.Client

GRAPH = "https://graph.microsoft.com/v1.0"
STATE = Path("state/sharepoint-delta.json")

class StopRun(Exception): pass    # fatal: stop now, leave saved state as it is
class Resync(Exception): pass     # 410 Gone: the saved link no longer works

def wait_for(r, attempt):
    value = r.headers.get("Retry-After", "")
    if value.isdigit():
        delay = int(value)                                  # seconds
    elif value:
        when = email.utils.parsedate_to_datetime(value)     # an HTTP date
        delay = max(0, when.timestamp() - time.time())
    else:
        delay = min(60, 2 ** attempt)                       # no header: back off
    return delay + random.uniform(0, 1)                     # jitter

def get(client, url, token, prefer=None):
    headers = {"Authorization": f"Bearer {token()}"}  # token() reads a cache
    if prefer:
        headers["Prefer"] = prefer
    for attempt in range(6):
        r = client.get(url, headers=headers)
        if r.status_code in (429, 503):
            time.sleep(wait_for(r, attempt)); continue
        if r.status_code == 410:
            raise Resync(r.headers.get("Location"))
        if r.status_code in (401, 403):
            raise StopRun(f"access refused: {r.status_code}")
        r.raise_for_status()
        return r.json()
    raise StopRun("still throttled after 6 tries")

def process(client, token, drive_id, item, index, counts, retry):
    if "deleted" in item:
        index.delete_doc(item["id"])        # must not fail if already gone
        if item["id"] in retry:
            retry.remove(item["id"])
        counts["deleted"] += 1
        return
    if "file" not in item:
        return                              # folders carry no text
    perms = get(client, f"{GRAPH}/drives/{drive_id}/items/{item['id']}/permissions", token)
    acl = acl_from(perms)                   # user and group ids allowed to read
    text = download_and_parse(item)         # your parser
    digest = hashlib.sha256(text.encode()).hexdigest()
    if index.hash_of(item["id"]) == digest:
        index.update_meta(item["id"], meta_from(item), acl)  # renamed or reshared: no re-embed
        counts["unchanged"] += 1
    else:
        new = index.upsert_doc(item["id"], text, digest, meta_from(item), acl)
        counts["added" if new else "changed"] += 1

def save(state):
    STATE.parent.mkdir(exist_ok=True)
    tmp = STATE.with_suffix(".tmp")
    tmp.write_text(json.dumps(state))
    tmp.replace(STATE)                      # atomic: never half-written

def sync(client, token, drive_id, index):
    state = json.loads(STATE.read_text()) if STATE.exists() else {}
    retry = state.get("retry", [])
    counts = dict.fromkeys(["read", "added", "changed", "unchanged", "deleted", "failed"], 0)
    for item_id in list(retry):             # last run's failures first
        try:
            item = get(client, f"{GRAPH}/drives/{drive_id}/items/{item_id}", token)
            process(client, token, drive_id, item, index, counts, retry)
            if item_id in retry:
                retry.remove(item_id)
        except StopRun:
            raise
        except Exception:
            counts["failed"] += 1           # stays listed; alert if it stays for days
    url = (state.get("next_link") or state.get("delta_link")
           or f"{GRAPH}/drives/{drive_id}/root/delta")
    while True:
        try:
            page = get(client, url, token, prefer="deltashowremovedasdeleted, "
                       "deltatraversepermissiongaps, deltashowsharingchanges")
        except Resync as e:
            state = {"retry": retry, "reconcile": True}   # full listing, then compare ids
            url = e.args[0] or f"{GRAPH}/drives/{drive_id}/root/delta"
            continue
        for item in page.get("value", []):
            counts["read"] += 1
            try:
                process(client, token, drive_id, item, index, counts, retry)
            except StopRun:
                raise
            except Exception:
                counts["failed"] += 1
                if item["id"] not in retry:
                    retry.append(item["id"])
        state["retry"] = retry
        if "@odata.nextLink" in page:       # page done: save where to resume
            url = state["next_link"] = page["@odata.nextLink"]
            save(state)
        else:                               # last page: save the link for next time
            state.pop("next_link", None)
            state["delta_link"] = page["@odata.deltaLink"]
            save(state)
            break
    print(counts)
    return counts
```

Why it is built this way:

- **Position and failures are saved together**, in one atomic write after each page. A crash mid-page replays that page, which is safe because upserts and deletes are keyed by source id. A failed item is never skipped: it sits on the retry list until it succeeds.
- **One bad file does not freeze the feed.** Refusing to advance while any item fails sounds safe, but one corrupt PDF would then block every future change.
- **Metadata travels with the text.** `meta_from` keeps source id, URL, title, path, author, modified time and owner for citations and filters. A rename changes these but not the text, so they are updated without re-embedding.
- **Fatal errors stop the run without saving.** An access error or endless throttling is not an item failure; counting it as one would put the whole library on the retry list.
- **A broken link triggers a full listing.** On 410 Gone, Graph's `Location` header starts a fresh enumeration. That lists what exists, not what was deleted meanwhile, so the `reconcile` flag tells the scheduler to run the id comparison next.

### A weekly reconciliation

Even good change feeds miss things. Compare the ids the source has with the ids the index has:

```python
def reconcile(source_ids: set, index_ids: set, index):
    stale = index_ids - source_ids
    for doc_id in stale:
        index.delete_doc(doc_id)
    missing = source_ids - index_ids
    return {"removed_stale": len(stale), "missing_to_fetch": len(missing)}
```

If `removed_stale` is more than a handful, your change feed has a bug; fix it.

### Records: Salesforce, Jira and SAP

- **Salesforce.** Query changed records with a filter on `SystemModstamp`, not `LastModifiedDate`, because `SystemModstamp` also moves when automated processes change a record. Subtract a few minutes from the last run time so records committed late are not missed. For deletions, call the get-deleted REST resource for each object with a start and end time in UTC. It covers at most the last 15 days and works to the minute, so if the connector is down longer than that, only a full id comparison can catch up. It also shows only deletions the integration user could see.
- **Jira Cloud.** Search with JQL through the `search/jql` endpoint, which pages with a `nextPageToken` instead of the old `startAt` offset. Filter with `updated >= "last run time"`. Deleted issues simply vanish from search, so subscribe to the `jira:issue_deleted` webhook and still reconcile ids, because webhooks can be missed.
- **SAP.** You rarely get direct table access. The client's SAP team exposes data, usually as OData services (often built on CDS views), sometimes through older BAPI or RFC calls, or through their integration middleware. Some OData services support delta tokens; otherwise use a changed-on date field and a reconciliation. The main gotcha is time: getting a service built and approved takes longer than your code, so ask in week one.
- **Schema drift.** Admins add fields, rename picklist values and retire objects. Pin the API version in your URLs, map only the fields you agreed, and alert when a describe call shows new or missing fields, rather than silently indexing everything.
- **Record permissions.** Salesforce access comes from owners, roles and sharing rules, which are hard to copy exactly. A safe first release indexes only objects every sales user may read, or checks access live with the user's own login before showing a record.

### Build, buy or borrow

Integration platforms such as Airbyte or Fivetran save weeks for common systems. Before you trust one, check that it reports deletions, carries access rights and exposes run counts you can alert on. Write your own for unusual systems, such as an in-house database, or when the client's security team will not approve a third-party tool.

## A worked example

A Gurugram consumer-goods company wants a sales assistant over SharePoint (product sheets, trade-scheme circulars) and Salesforce (accounts, opportunities). The figures below are illustrative, to show the shape of the work.

**SharePoint.** An app registration with read access to six sites. Suppose the first full sync of 38,000 files is spread over two nights to stay well under throttling limits; if the saved next link still works the second night carries on from it, and if Graph answers 410 the listing starts again. Afterwards a delta run every 15 minutes returns a few hundred changed or deleted items and finishes in about a minute. Each run also re-reads permissions for changed items, and a nightly job re-reads permissions on the two sites that hold pricing and HR files.

**Salesforce.** A read-only integration user limited to Account, Opportunity and Product. Every 30 minutes the connector queries records whose `SystemModstamp` is after the last run minus five minutes, turns each into a short text summary with the record id and owner as metadata, and calls the get-deleted resource for the same window. If a sales manager deletes a duplicate account at 11:10, it leaves the index by about 11:30.

**The incident.** Suppose in week three a delta request returns 410 Gone. The connector follows the `Location` header, re-lists the library overnight, then runs the id comparison and removes 14 files deleted while the link was broken. The alert reached the on-call engineer before the client noticed, and the runbook already covered this case.

| Measure | Before | After |
| --- | --- | --- |
| SharePoint sync | Full re-read nightly, about 6 hours, often throttled | Delta every 15 minutes, about 1 minute |
| Salesforce sync | Daily export, deletions never removed | Every 30 minutes, deletions within one run |
| Deleted documents still searchable | Dozens | None in the weekly check |
| Time to notice a failed sync | Days | Minutes, through alerts |

## Common mistakes

- **Full re-syncs every time.** Use delta tokens or modified-since queries after the first load.
- **Ignoring deletions.** A modified-since query never returns deleted records; add a deletion feed and a weekly id comparison.
- **Saving the cursor at the wrong time.** Before processing skips items after a crash; only at the end restarts from page 1. Save after each page.
- **Swallowing failed items.** Counting a failure and moving on loses that item forever. Keep a retry list.
- **One token for a long run.** It expires after 60 to 90 minutes and the job dies at 3 a.m.
- **Expanding groups into users at index time.** Membership changes then need a full re-index to take effect.
- **Over-broad access.** Ask for read-only access to named sites and objects, not the whole tenant.
- **Silent connectors.** If nobody is alerted when a sync stops, the assistant quietly goes stale.
- **Re-embedding every modified file** even when only its metadata changed.

## When you do not need a custom connector

- **A one-off load** of a fixed set of files: export them once and ingest.
- **A platform connector already covers the system**, reports deletions and reads permissions.
- **Users can upload the few documents they need** directly.

## From demo to production

Starting defaults, agreed with the client's IT team in writing:

- **Schedules:** document delta every 15 minutes, record queries every 30 minutes, permission re-read nightly, full id comparison weekly. Big first loads only at night in the client's time zone, with low concurrency.
- **Alerts:** a run fails or does not start within two intervals; items read drop below half the usual; any item stays on the retry list for more than a day; a secret expires within 30 days.
- **Runbook:** what to do on 410 Gone, on an access error, and when a site, object or field is renamed.

## Practice

Read the Microsoft Graph overview, then pick any API with paging that you can use for free (GitHub issues, a public dataset API, or Graph with a developer tenant).

1. Write a connector that pulls all items with paging, honours `Retry-After`, and saves its position after each page so it can resume.
2. Kill it halfway through the first load and restart it. Confirm it continues from the saved page and does not start again.
3. Add an incremental mode that fetches only items changed since the last run, and a check that detects deleted items.
4. Record per-run counts (read, added, changed, unchanged, deleted, failed) and print a one-line summary.
5. Delete an item at the source, rerun, and confirm its chunks are gone from the index.

**You are done when you can** run your connector twice in a row and show the second run fetching only what changed, including a deletion, and show a crashed run resuming from the right page.
