## What it is

Before documents can be searched for RAG, they are split into **chunks**: passages small enough to embed, retrieve and fit into a prompt. Chunking decides what retrieval can find. If a chunk is too large, its embedding blurs many topics together; if too small, it loses the context needed to understand it.

```flow
title: Fixed-size chunks, every 2,000 characters: the table is cut in half, topics mixed
HR policy -> Chunk 1 | leave policy ... the earned leave table, first rows
HR policy -> Chunk 2 | the rest of the table ... notice period ... probation
```

```flow
title: Structure-aware chunks: headings, then paragraphs, about 400 tokens, with overlap
HR policy, by headings -> Leave > Earned leave | the full table
HR policy, by headings -> Leave > Sick leave
HR policy, by headings -> Exit > Notice period
HR policy, by headings -> Exit > Probation
```

Each structure-aware chunk is one topic, with its title path in front.

This lesson follows an HR assistant at a manufacturing company in Pune, answering questions from a 120-page employee handbook.

## How it works

**Size.** Chunk size is measured in tokens or characters. Common starting points are 300 to 800 tokens for prose. Smaller chunks (100 to 300) suit precise fact lookup such as FAQs; larger ones suit questions that need explanation.

- *Very large chunks*: the embedding averages many ideas, so it matches no single question well; and each retrieved chunk fills the prompt with irrelevant text, costing tokens and distracting the model.
- *Very small chunks*: a sentence like "This limit is 45 days" is retrieved without saying which limit; answers become wrong or vague.

**Overlap.** Repeating a little text (for example 10 to 20%) between neighbouring chunks means a sentence or idea split at a boundary still appears whole in one of them.

**Split along structure.** Better than cutting every N characters:

- split on headings and sections first, then paragraphs, then sentences (recursive splitting);
- keep tables, lists and code blocks whole;
- for FAQs, one question-and-answer pair per chunk.

**Add context.** Store the document title and section heading with each chunk, and often prepend them to the text you embed, so "This limit is 45 days" becomes "Leave Policy > Earned leave: This limit is 45 days".

**Metadata.** Keep document id, page and section for citations and filters.

**Test it.** Chunking is a choice to evaluate, not to guess. Try two or three sizes on a set of real questions and measure whether the right passages are retrieved.

**Chunking by document type:**

| Document type | Strategy | Typical size |
| --- | --- | --- |
| Policies and manuals | Split by headings, then paragraphs; prepend the section path | 300 to 600 tokens |
| FAQs | One question-and-answer pair per chunk | Whatever each pair needs |
| Tables, price lists | Keep each table whole; add the heading | One table |
| Contracts | Split by clause; keep clause numbers | One clause or sub-clause |
| Chat transcripts, tickets | One ticket or conversation, or a window of turns | 200 to 500 tokens |
| Code | By function or class | One function |

**Chunk metadata.** Every chunk should carry: document id, title, section path, page, version or date, and any access group. This metadata makes citations possible ("Handbook, section 4.2, page 37"), allows filters ("only the current version", "only documents this user may see"), and lets you rebuild a single document's chunks when it changes instead of re-indexing everything.

**Re-chunking is normal.** When a test shows a better strategy, re-chunk and re-embed. Keep the chunking code versioned and the settings recorded with the index, so you always know which strategy produced the current results.

**Chunking PDFs and scanned documents.** Extracted PDF text often includes page headers, footers and page numbers on every page. Remove lines that repeat on most pages before chunking, or they pollute every chunk and its embedding. For scans, run OCR first and check a sample, because OCR errors in headings break structure-aware splitting. And keep the page number of the start of each chunk, so citations point to the right page even when a chunk crosses a page break.

**A structure-aware splitter in code.** This one works on Markdown or text with headings, keeps the section path, and adds overlap. Sizes are in words for simplicity; switch to the embedding model's tokenizer for exact limits:

```python
import re

def split_by_headings(text, max_words=350, overlap_words=50, title=""):
    chunks, path, buf = [], [], []

    def flush():
        words = " ".join(buf).split()
        start = 0
        while start < len(words):
            piece = words[start:start + max_words]
            header = " > ".join([title] + path)
            chunks.append({"section": header, "text": f"{header}: " + " ".join(piece)})
            if start + max_words >= len(words):
                break
            start += max_words - overlap_words
        buf.clear()

    for line in text.splitlines():
        m = re.match(r"^(#{1,4})\s+(.*)", line)
        if m:
            flush()
            level = len(m.group(1))
            path[:] = path[:level - 1] + [m.group(2).strip()]
        elif line.strip():
            buf.append(line.strip())
    flush()
    return chunks
```

Each chunk starts with its section path, such as "Leave Policy > Earned leave: ...", so a short sentence still says what it is about.

**Strip repeated lines from PDFs.** Before chunking extracted PDF text, drop lines that appear on most pages:

```python
from collections import Counter

def strip_repeats(pages, share=0.6):
    """pages: list of page texts."""
    counts = Counter(l.strip() for p in pages for l in set(p.splitlines()) if l.strip())
    repeated = {l for l, n in counts.items() if n >= share * len(pages)}
    return ["\n".join(l for l in p.splitlines() if l.strip() not in repeated) for p in pages]
```

**Small to big.** Precise retrieval wants small chunks; good answers want context. Do both: index small chunks (one or two paragraphs), store which section each came from, and when a small chunk matches, give the model the whole parent section (or the chunk plus its neighbours). This often beats any single chunk size.

**Context written by a model.** For documents where headings are weak, a cheap model can write one sentence per chunk describing where it sits ("From the 2026 leave policy, section on carrying forward earned leave"). Prepend it before embedding. It costs one call per chunk at ingestion time, once, and helps retrieval on vague chunks. Prompt caching the full document makes this much cheaper.

**Measure, then choose.** Keep the 20-question test from the practice, and record recall at 5 for each strategy and size in a small table. Pick by the numbers, and keep the table with the index settings.

## A worked example

A Pune manufacturing company's HR assistant answers questions from a 120-page employee handbook.

First attempt: fixed 2,000-character chunks with no overlap. Testing with 40 real employee questions, the right passage is in the top five results for only 55%. Failures: the leave section's table was split across two chunks; answers about "notice period" retrieved chunks mixing notice period, probation and resignation.

Second attempt: split by headings, then paragraphs, up to about 400 tokens, with 60-token overlap; tables kept whole; title and section path prepended. The right passage is now in the top five for 85% of questions.

Third attempt, 200-token chunks: 82%, with more answers missing context. They keep the 400-token version.

| Attempt | Strategy | Right passage in top 5 |
| --- | --- | --- |
| 1 | Fixed 2,000 characters, no overlap | 55% |
| 2 | Headings then paragraphs, ~400 tokens, 60-token overlap, tables whole, title path prepended | 85% |
| 3 | Same, but ~200 tokens | 82%, more answers missing context |

The biggest single gain came from keeping the leave table whole: eight of the 18 failures in attempt 1 were questions about leave entitlements.

**What the employees noticed.** After the change, the most common complaint, "it gives me half the answer", almost disappeared. Questions about leave, which made up a third of all questions, now retrieved the complete table, so the assistant could answer "how many earned leaves do I get in my third year?" correctly instead of quoting only the first rows.

## Common mistakes

- **Fixed-size cuts through tables and sentences.**
- **No overlap.** Ideas split at boundaries get lost.
- **Huge chunks to "keep context".** Retrieval gets worse and prompts get costly.
- **Losing headings and page numbers.**
- **Never measuring.** Test sizes on real questions.
- **Chunking once and never testing again.** When documents or questions change, recheck retrieval with your test set.
- **Repeated page headers and footers left in every chunk.**
- **Choosing one chunk size for every document type.** Policies, FAQs, tables and tickets need different strategies.
- **Changing chunking without re-running the retrieval test.**

## When chunking hardly matters

- **Short documents**, such as one-page notices, that fit whole in a chunk.
- **Already structured items**, such as one FAQ pair, one product or one ticket per record.
- **Small collections that fit in the context**, where you can skip retrieval altogether.

## From demo to production

- **Version the chunking code and settings**, and record them with the index.
- **Re-chunk one document at a time** on change, using document ids in chunk ids.
- **Keep the retrieval test** and rerun it on every chunking change.
- **Check a sample of chunks by eye** after each ingestion: broken tables and stray headers show up quickly.
- **Track chunk counts and sizes** per document to catch parsing failures, such as a 200-page manual producing three chunks.
