## What it is

This lesson covers three tools that appear in almost every real Rust program.

**Error handling.** Rust has no exceptions. A function that can fail returns a `Result<T, E>`: either `Ok(value)` or `Err(error)`. Because the error is part of the return type, you cannot forget that a call can fail. The `?` operator makes passing errors up short and readable.

**Traits.** A trait describes behaviour that many types can share, such as "can be printed", "can be compared" or "has a GST amount". It is Rust's version of an interface.

**Generics.** Generic code works with many types. With trait bounds you say exactly what a type must be able to do, and the compiler checks it.

```text
 read_file()?  ->  parse_rows()?  ->  total()  ->  Ok(total)
      |                 |
     Err ───────────────┴──► returned to the caller at once by ?

 trait Taxable { fn gst(&self) -> f64; }
      ▲            ▲             ▲
   Book (5%)   Laptop (18%)   Medicine (12%)
 fn bill<T: Taxable>(items: &[T])  works for any of them
```

## How it works

**Result and ?.**

```rust
use std::fs;

fn read_total(path: &str) -> Result<f64, std::io::Error> {
    let text = fs::read_to_string(path)?;   // on error, return it
    let total = text.lines()
        .filter_map(|line| line.split(',').nth(1))
        .filter_map(|p| p.trim().parse::<f64>().ok())
        .sum();
    Ok(total)
}
```

`?` means: if this is `Err`, return it from the function now; otherwise give me the value. The caller then decides what to do: show a message, retry, or pass it up again.

**unwrap and expect** take the value and crash on an error. They are fine in quick experiments and tests. In real code prefer `?`, `match`, or `unwrap_or`.

**Your own error type.** An enum lists the ways your code can fail:

```rust
#[derive(Debug)]
enum BillError {
    Io(std::io::Error),
    BadPrice { line: usize },
}
```

The **thiserror** crate generates the boilerplate for messages and conversions; **anyhow** is popular in applications where you mostly want to add context and report errors.

**Traits.**

```rust
trait Taxable {
    fn price(&self) -> f64;
    fn rate(&self) -> f64;
    fn gst(&self) -> f64 { self.price() * self.rate() }  // default method
}

struct Book { price: f64 }
impl Taxable for Book {
    fn price(&self) -> f64 { self.price }
    fn rate(&self) -> f64 { 0.05 }
}
```

A trait can have default methods, like `gst` above, that every type gets for free. Rust's standard library is built from traits you will use daily: `Display` and `Debug` for printing, `Clone`, `PartialEq` for `==`, `Iterator`, `From` and `Into` for conversions.

**Generics and trait bounds.**

```rust
fn total_gst<T: Taxable>(items: &[T]) -> f64 {
    items.iter().map(|i| i.gst()).sum()
}
```

`T: Taxable` is a trait bound: any type works, as long as it implements `Taxable`. The compiler generates a specialised version for each type you actually use, so there is no speed cost.

| Tool | Use it when | Example |
|---|---|---|
| `Option<T>` | a value may simply be absent | looking up a key |
| `Result<T, E>` | an operation can fail for a reason | reading a file, parsing input |
| `panic!` | a bug that should never happen | broken internal invariant |
| Generic `T: Trait` | one type at a time, maximum speed | `fn total<T: Taxable>(..)` |
| `dyn Trait` | a mixed list of different types | `Vec<Box<dyn Taxable>>` |

**Adding context to errors.** A bare "file not found" is not much help at 2 a.m. With anyhow you can write `read_to_string(path).with_context(|| format!("reading sales file {path}"))?`, so the final message says which file failed and why. Good errors name what the program was trying to do, the input involved, and the underlying cause.

**Deriving traits.** Many common traits can be generated for you: `#[derive(Debug, Clone, PartialEq)]` above a struct gives it printing, copying and comparison without writing any code. Libraries such as serde use the same idea to turn structs into JSON with one line.

## A worked example

Sana, a back-end developer at a retail chain in Indore, writes a Rust tool that reads the day's sales file from every store and totals the GST. Her first version used `unwrap()` everywhere. One store sent a file with "N/A" in a price column, and the whole nightly job crashed at 2 a.m.

She rewrites it to treat bad data as data:

```rust
fn parse_line(n: usize, line: &str) -> Result<f64, BillError> {
    let price = line.split(',').nth(1).ok_or(BillError::BadPrice { line: n })?;
    price.trim().parse::<f64>().map_err(|_| BillError::BadPrice { line: n })
}

fn run(path: &str) -> Result<(), BillError> {
    let text = std::fs::read_to_string(path).map_err(BillError::Io)?;
    let mut total = 0.0;
    for (n, line) in text.lines().enumerate().skip(1) {
        match parse_line(n + 1, line) {
            Ok(p) => total += p,
            Err(e) => eprintln!("Skipping: {e:?}"),
        }
    }
    println!("Total sales: Rs {total:.2}");
    Ok(())
}
```

A missing file now stops the run with a clear message, while a bad row is skipped and reported. Next, different product types (books at 5%, electronics at 18%) each implement `Taxable`, and one generic `total_gst` function handles them all. When the GST council changes a rate, she edits one `impl`.

## Common mistakes

**`unwrap()` in production code.** One unexpected input becomes a crash. Use `?` and handle errors at the level that can do something sensible about them.

**Turning every error into a String.** You lose the ability to react differently to different failures. Use an error enum or a crate like thiserror.

**Huge traits.** A trait with fifteen methods is hard to implement. Keep traits small and focused, like the standard library's.

**Over-generic code.** Generics everywhere make code hard to read. Start with concrete types and make a function generic when a second type actually needs it.

**Confusing `impl Trait` and `dyn Trait`.** `impl Trait` and generics are resolved at compile time and are fastest; `dyn Trait` allows mixed types at run time with a small cost. Use `dyn` when you genuinely need a list of different types.
