## What it is

There are three ways to give a model the information it needs to answer a question:

- **Long context**: put whole documents in the prompt, then ask.
- **Retrieval (RAG)**: run one search over an index and put only the few best passages in the prompt.
- **Agentic search**: give the model search tools (keyword search, a metadata filter, "open document", a database query) and let it decide what to look up, read the results and search again until it can answer.

As of 28 November 2026, each of Anthropic's latest Claude models has a 1-million-token context window, roughly 555,000 words by Anthropic's estimate. So long context is often possible. Whether it is wise depends on accuracy, cost, latency and scale.

| | Long context | RAG | Agentic search |
| --- | --- | --- | --- |
| What the model reads | Whole documents | 3 to 10 passages from one search | Whatever its searches return, over several steps |
| Strength | Sees everything; can cross-reference | Cheap, fast, scales to millions of documents | Follows multi-step questions and exact identifiers |
| Weakness | Cost and delay grow with length; accuracy falls in long inputs | Misses what one search misses | More calls, slower, less predictable |
| Engineering | Low | Chunking, indexing, tuning | Good tools, step limits, logging |

```flow
title: A first decision, before you measure
Your documents -[fit the window, reused often]-> Long context with caching
Your documents -[too many, short factual questions]-> RAG
Your documents -[too many, answers need several lookups]-> Agentic search
RAG -[questions need whole documents]-> Document-level retrieval, then long context
```

This lesson follows a law firm in Chennai building a contract assistant with three very different uses.

## How it works

### Accuracy falls as inputs grow

Models do not use every position in a long input equally well.

- **Lost in the middle.** Liu and colleagues (2023) gave models many documents and found accuracy was highest when the answer sat near the start or the end, and lowest in the middle: a U-shaped curve.
- **Context rot.** Chroma's report (July 2025) tested 18 models and found performance grew less reliable as input grew, even on simple tasks. It fell faster when the question and the answer were less similar in wording and meaning, so the model had to infer rather than match. Even one plausible distractor, a sentence that looks like the answer but is not, lowered accuracy, and more distractors lowered it further.

One way to picture it: the more look-alike sentences surround the answer, the more chances the model has to pick the wrong one.

So separate the **advertised window** (what the API accepts) from the **effective context**: the length at which *your* task stays accurate. A "needle in a haystack" test, finding one planted sentence, is the easiest case, and current models usually pass it. Passing tells you little about questions that compare clauses, add up figures or must ignore an old version of a rule.

### Cost: you pay for every token on every call

Unless the document is cached, every question re-sends and re-pays for all of it. Claude Sonnet 5.5 list prices, checked on 28 November 2026 on Anthropic's pricing page:

| Item | USD per million tokens | Multiple of input price |
| --- | --- | --- |
| Input | $2.00 | 1x |
| Cache write, 5-minute lifetime | $2.50 | 1.25x |
| Cache write, 1-hour lifetime | $4.00 | 2x |
| Cache read | $0.10 | 0.05x |
| Output | $10.00 | 5x |

The cache-read multiple differs by model: 0.025x on Claude Fable 5.2, 0.05x on Claude Opus 5.5 and Sonnet 5.5, and 0.1x on most others, including Claude Haiku 5.5. Some models also charge more per token for long prompts: Claude Haiku 5.5 input costs $0.10 per million tokens when the prompt is up to 100,000 tokens and $0.50 for the whole request when it is longer (same check date). Other providers price caching differently, so read your own provider's page and write down the date.

### Prompt caching: what it changes, and when it fails

**How it works.** The provider stores the processed start of your prompt (the prefix). A later request with a byte-for-byte identical prefix reads it from the cache: cheaper, and faster to the first token. So put the long, stable part first and the question last, which also keeps the question next to where the model starts writing.

**Lifetime.** By default a cache entry lives 5 minutes, and each hit resets the clock. A 1-hour lifetime costs 2x to write. Anthropic's docs say the 5-minute cache pays for itself after one read and the 1-hour cache after two.

**Gotchas that experts check:**

- **Gaps longer than the lifetime.** If questions come every 15 minutes with a 5-minute cache, every call pays the 1.25x write again, so you pay *more* than with no cache.
- **A changing prefix.** A timestamp, a user name or a re-ordered tool list before the document breaks the match for everything after it.
- **Parallel calls.** A cache entry becomes available only once the first response starts, so ten questions fired at once all miss.
- **One document per user.** If 500 users each upload their own contract, that is 500 separate cache writes. Caching helps each session, not the system as a whole.
- **Isolation.** Caches are never shared between organisations, and on Anthropic's API not between workspaces either.

Check it worked: the response's `usage` reports `cache_creation_input_tokens` and `cache_read_input_tokens`. If reads stay at zero, something is breaking the prefix.

### Latency and scale

Time to first token rises with input length, so very long uncached prompts make chat feel slow. Agentic search adds a model round trip per step. And a window has a limit; a company's documents do not. For example, 18,000 manuals of about 30,000 tokens each come to 540 million tokens, 540 times a 1-million-token window. Once the corpus is bigger than the window, something must choose what to send.

### Agentic search, the third option

Instead of one search chosen by your code, the model runs the search. Anthropic describes this "just in time" approach in its context engineering guide (September 2025): Claude Code uses tools such as glob and grep to find files as it needs them, while a few files are loaded up front. The guide notes the trade-off plainly: exploring at run time is slower than reading pre-computed retrieval results.

```flow
dir: LR
title: Agentic search on one question
Question -> Search contracts by client | keyword search with filters
Search contracts by client -> Open master agreement | reads clause 9
Open master agreement -> Search for clause 9 references
Search for clause 9 references -> Answer with citations
```

**Where it wins:** questions where the next lookup depends on the last result, exact identifiers (clause numbers, error codes, part numbers) that embeddings blur, and fast-changing data you can query live instead of re-indexing. Tools can also enforce each user's permissions.

**What it costs:** every step is another model call that re-sends the growing conversation. For example, with 2,000 tokens of instructions and tools and 3,000 tokens of results added per step, six steps send 2,000 + 5,000 + ... + 17,000 = 57,000 input tokens, against about 3,000 for one RAG call. Caching the earlier turns softens this.

**How it fails:** it stops too early, loops on the same search, or floods its context with tool output. Sensible defaults: cap the steps (for example, 8), make tools return short snippets with document IDs rather than whole files, and log every tool call so you can read the failures.

### Two more patterns

- **Document-level retrieval.** Search over titles, summaries or metadata to pick the right few whole documents, then let long context read them. It suits contracts, policies and reports.
- **Map-reduce.** For "summarise all 40 board meetings", summarise each document separately (map), then combine the summaries (reduce). It fits any corpus size but loses detail, so ask each summary to keep citations.

```python
def doc_level_prompt(question, search_docs, load_doc, max_docs=3):
    docs = search_docs(question, k=max_docs)    # over titles, summaries and metadata
    context = "\n\n".join(f"<document title='{d['title']}'>\n{load_doc(d['id'])}\n</document>" for d in docs)
    return context + f"\n\nAnswer from the documents above. Cite titles and clause numbers.\nQuestion: {question}"
```

### Privacy

Long context sends whole documents to the model provider; RAG sends only passages. If documents hold personal data, check the client's data agreement and India's data-protection obligations, and redact what the task does not need.

### Decision rules

- One or a few documents, many questions in a session, answers that need the whole text: **long context, cached**.
- Large or growing collection, short factual questions, many users: **RAG**.
- Answers that need several dependent lookups or exact identifiers: **agentic search**, with step limits.
- Whole documents needed but hundreds to choose from: **document-level retrieval, then long context**.

### Test position and distractors on your own documents

Published studies give warnings, not answers. This harness plants made-up audit notes (they cannot clash with anything real) at several depths, adds look-alike distractors and tests a two-hop question:

```python
import random

FACT = "Audit note: the Hosur warehouse inspection code is HW-7319."
DISTRACTORS = ["Audit note: the Hosur office inspection code is HO-7391.",
               "Audit note: the 2019 Hosur warehouse code, now withdrawn, was HW-1973."]
HOPS = ["Audit note: the Hosur warehouse audit is led by Farida Sheikh.",
        "Audit note: Farida Sheikh's desk extension is 4826."]
CODE_Q = "What is the current inspection code for the Hosur warehouse?"
TESTS = {   # name: (where to insert notes, question, expected answer)
    "single fact": (lambda d: [(d, FACT)], CODE_Q, "HW-7319"),
    "distractors": (lambda d: [(d, FACT)] + [(random.random(), s) for s in DISTRACTORS], CODE_Q, "HW-7319"),
    "two hops": (lambda d: [(d, HOPS[0]), ((d + 0.5) % 1, HOPS[1])],
                 "Which extension reaches the person who leads the Hosur warehouse audit?", "4826"),
}

def build(doc, inserts):
    paras = doc.split("\n\n")                        # insert between paragraphs, never mid-sentence
    for depth, note in sorted(inserts, reverse=True):
        paras.insert(int(len(paras) * depth), note)
    return "\n\n".join(paras)

def run(doc, ask, depths=(0.05, 0.25, 0.5, 0.75, 0.95), runs=3):
    for name, (inserts, question, expected) in TESTS.items():
        for d in depths:
            ok = sum(expected in ask(build(doc, inserts(d)) + "\n\nAnswer from the document only. " + question)
                     for _ in range(runs))
            print(f"{name:12} depth {d:4.0%}: {ok}/{runs} correct")
```

`ask` is any function that sends a prompt and returns text. With the Anthropic SDK:

```python
import anthropic

client = anthropic.Anthropic()

def ask(prompt):
    r = client.messages.create(model="claude-opus-5-5", max_tokens=2000,   # the model you will deploy
                               output_config={"effort": "low"},
                               messages=[{"role": "user", "content": prompt}])
    return "".join(b.text for b in r.content if b.type == "text")
```

Expect the single-fact row to be near perfect; the distractor and two-hop rows are the informative ones. Then add your real question types, such as comparisons across sections.

### A cost model you can adjust

```python
# Claude Sonnet 5.5 list prices in USD per million tokens, checked 28 November 2026
# (platform.claude.com/docs/en/about-claude/pricing). Re-check before you use them.
PRICE_IN, PRICE_OUT = 2.00, 10.00
WRITE_X, READ_X = 1.25, 0.05   # 5-minute cache write and cache read, as multiples of PRICE_IN

def call_usd(fresh_in, out, cache_write=0, cache_read=0):
    """Cost of one call. fresh_in: normal input tokens; cache_write/cache_read: cached prefix tokens."""
    inp = fresh_in + cache_write * WRITE_X + cache_read * READ_X
    return (inp * PRICE_IN + out * PRICE_OUT) / 1e6

Q, DOC, ASK, OUT, RAG_IN = 12, 40_000, 100, 300, 3_000

no_cache = Q * call_usd(DOC + ASK, OUT)
cached = call_usd(ASK, OUT, cache_write=DOC) + (Q - 1) * call_usd(ASK, OUT, cache_read=DOC)
expired = Q * call_usd(ASK, OUT, cache_write=DOC)   # every gap longer than the cache lifetime
rag = Q * call_usd(RAG_IN + ASK, OUT)

for name, usd in [("long context, no cache", no_cache), ("long context, cached", cached),
                  ("long context, cache always expired", expired), ("RAG, 3,000 tokens", rag)]:
    print(f"{name:36} ${usd:.3f}")
```

It prints $0.998 with no cache, $0.182 cached, $1.238 when the cache always expires, and $0.110 for RAG. Caching cuts the long-context bill by more than 80%, which brings it close to RAG; an expired cache makes it the most expensive option. Convert dollars at the day's rate, and count your own documents' tokens with your provider's counter, since tokenizers differ.

## A worked example

A Chennai law firm wants a contract assistant. The numbers below are illustrative, of the kind the team would record; costs use the Claude Sonnet 5.5 prices checked on 28 November 2026.

**1. Reviewing one contract.** A lawyer uploads a 60-page agreement (about 40,000 tokens) and asks around 12 questions: termination rights, indemnity caps, clauses that conflict. Many answers need the whole document, so the team uses long context, contract cached and question last. Lawyers often pause more than 5 minutes between questions, so they pick the 1-hour cache. Twelve questions then cost about $0.24, against about $1.00 uncached. Suppose that on a 30-question test, long context gets 27 right and chunk-based RAG gets 22, with most RAG misses on cross-references between clauses. The team also runs the distractor test, because their contracts contain superseded versions of the same clause.

**2. Searching the precedent library.** 25,000 past contracts, far beyond any window. Lawyers ask "find indemnity clauses capped at fees paid in the last 12 months in IT services contracts". The team uses hybrid retrieval with metadata filters (contract type, year) to find the best 20 clauses, then a model summarises them with citations. They measure recall: suppose the right clause is in the top 20 for 46 of 50 test questions.

**3. Following cross-references.** A partner asks: "Which of our contracts with this client depend on a master agreement clause that changed in the 2025 amendment?" One search cannot answer it: the system must find the amendment, read which clause changed, then find contracts citing that clause. The team uses agentic search with three tools (search by client, open document, search by clause number) and a cap of 8 steps. Suppose a typical answer takes 5 tool calls and about 30 seconds: too slow for chat, fine for a research task.

| Use case | Approach | Why | Illustrative result |
| --- | --- | --- | --- |
| One 60-page contract | Long context, 1-hour cache | Answers need the whole text | 27/30 against 22/30 for chunk RAG; about $0.24 a session |
| 25,000 precedents | Hybrid retrieval with filters | Far beyond any window | Right clause in top 20 for 46/50 |
| Cross-reference questions | Agentic search, 8-step cap | Next lookup depends on the last | About 5 calls and 30 seconds per answer |

## Common mistakes

- **Trusting the advertised window.** A model that accepts 1 million tokens may not use them well. Measure effective context on your own question types.
- **Testing only with one planted fact.** It is the easiest case. Add distractors, two-hop questions and questions with no answer.
- **Comparing costs without caching**, or counting on a cache that will never hit (see the gotchas above).
- **Putting the question, a timestamp or a user name before the document.** It breaks the cache and hurts accuracy.
- **"RAG is dead" thinking.** Large and changing collections still need retrieval, at least to choose documents.
- **Using an agent for one-hop lookups.** If one search finds the answer, an agent only adds calls and delay.
- **Running an agent with no step limit or logs.** You cannot fix failures you cannot see.
- **Sending whole documents full of personal data** when passages would answer the question.

## When the choice is obvious

- **One short document**: just put it in the prompt.
- **Millions of documents**: you need retrieval of some kind, at least to choose documents.
- **Answers from structured data**, such as records or tables: query the database through a tool, not with any of these.

## From demo to production

- **Record accuracy, cost and latency** for the chosen approach on your golden set, and re-check on every model change.
- **Track the cache hit rate** from `cache_read_input_tokens`, and alert when it drops.
- **Log input tokens per request** and alert on unexpected growth.
- **Re-run the position and distractor tests** when you change models or documents grow.
- **For agents, log every tool call** and watch the steps per answer; a rising count is an early warning.
- **Re-check prices** with their date at least every quarter.
