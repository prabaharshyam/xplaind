## What it is

There are two ways to give a model the information it needs:

- **Long context**: put the whole document, or several, into the prompt and ask the question.
- **Retrieval (RAG)**: search for the few most relevant passages and put only those in the prompt.

Modern models accept very long inputs, so long context is often possible. Whether it is wise depends on accuracy, cost, latency and scale.

```text
  Long context                                 RAG
  +---------------------------------+          +-----------------+
  | whole contract (40,000 tokens)  |          | [chunk 12]      |   3,000 tokens
  | ............................... |          | [chunk 37]      |
  | ............................... |          | [chunk 41]      |
  | instructions + question (end)   |          | question        |
  +---------------------------------+          +-----------------+
   sees everything, cross-references            cheap, fast, scales to millions
   costly unless cached, slower                 misses what retrieval misses

  Middle ground:  find the right 2 documents  -->  send them whole
```

This lesson follows a law firm in Chennai building a contract-review assistant with two very different uses.

## How it works

**Accuracy in long inputs.** Models do not use all positions equally. Studies found that information in the middle of a long context is used less well than information near the start or end ("lost in the middle"), and that performance can degrade as inputs grow even on simple tasks. Newer models have improved, but you should test on your own documents and question types.

**Cost.** You pay for every input token on every call. Sending a 200,000-token document per question costs far more than sending 3,000 tokens of retrieved passages. **Prompt caching** changes this: if the same long document is reused across many questions, cached input can be much cheaper and faster on later calls.

**Latency.** Time to first token rises with input length. Long prompts make interactive use slower unless cached.

**Scale.** A context window has a limit; a company's documents do not. Once the corpus is larger than the window, you must retrieve something, at least to pick which documents to send.

**Rules of thumb.**

- One or a few documents, many questions about them in a session, and questions that need the whole document (summaries, comparisons across sections): long context, ideally cached.
- Large or growing collections, short factual questions, many users: RAG.
- Middle ground: retrieve at the document level (find the right two contracts), then put those whole documents in context.

**Hybrid habits.** Even with long context, put the instructions and the question at the end, ask for citations to sections or pages, and keep the documents in a consistent, labelled format.

**Comparing the options:**

| Factor | Long context | RAG |
| --- | --- | --- |
| Corpus size | Up to the context window | Unlimited |
| Questions needing the whole document | Strong | Weak, depends on chunking |
| Short factual lookups | Fine but costly | Strong |
| Cost per question | High uncached, lower with caching | Low |
| Latency | Higher, lower with caching | Low |
| Changing documents | Resend each time | Re-index changed items |
| Engineering effort | Low | Higher: chunking, indexing, retrieval tuning |

**A worked cost comparison.** Suppose input costs a fixed price per million tokens. Sending a 40,000-token contract with each of 12 questions means about 480,000 input tokens. With caching, later calls read the cached contract at a fraction of the normal price, so the total can drop to around a quarter. RAG sends about 3,000 tokens per question, 36,000 in total, which is cheaper still but scored worse on cross-reference questions. The right choice weighs accuracy against these costs for the task at hand, not cost alone.

**Testing on your own documents.** Published studies give warnings, not answers. Write questions where the answer sits early, in the middle and late in the document, and questions that need two distant sections. Run them both ways and read the failures.

## A worked example

A Chennai law firm wants an assistant for contract review. Two use cases:

*Reviewing one contract.* A lawyer uploads a 60-page agreement (about 40,000 tokens) and asks a dozen questions: termination rights, indemnity caps, conflicts between clauses. Many answers need the whole document. You use long context with the contract cached. The first question takes 9 seconds; later ones take 2 to 3 seconds and cost much less because of the cache. On a test of 30 questions, long context scores 90% against 73% for chunk-based RAG, which missed cross-references between clauses.

*Searching the firm's precedent library.* 25,000 past contracts, far beyond any context window. Lawyers ask "Find indemnity clauses capped at fees paid in the last 12 months in IT services contracts." You use hybrid retrieval with metadata filters to find the best 20 clauses, then a model summarises them with citations.

The firm gets both, each where it fits.

| Use case | Approach | Accuracy | Notes |
| --- | --- | --- | --- |
| Reviewing one 60-page contract | Long context, cached | 90% | Chunk-based RAG scored 73% |
| Searching 25,000 precedents | Hybrid retrieval with filters | Measured by recall | Far beyond any window |

## Common mistakes

- **Assuming long context is always more accurate.** Test it; accuracy can drop with length and position.
- **Ignoring cost per question.** Long uncached prompts on every question become expensive at scale.
- **Forgetting caching.** For repeated use of the same document it changes the economics.
- **Putting the question first.** Place instructions and the question after the long material.
- **"RAG is dead" thinking.** Large collections still need retrieval.

## Practise

Read the Lost in the Middle abstract, Chroma's context rot report and your provider's prompt caching guide.

1. Pick one long document (an annual report or policy) and write 15 questions, some needing the whole document.
2. Answer them with long context and with your RAG pipeline. Record accuracy, latency and cost for each.
3. Repeat the long-context run with prompt caching and compare.

**You are done when you can** recommend long context or RAG for a stated use case with your own numbers.
