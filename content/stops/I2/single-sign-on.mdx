## What it is

**Single sign-on (SSO)** lets employees sign in once with their company account and reach every approved app without new passwords. It works through the company's identity provider, such as Microsoft Entra ID, Okta, Google Workspace or Ping. When someone leaves, IT disables one account and access to everything stops.

Three standards matter:

- **OAuth 2.0**: lets an app act on a user's behalf with limited, revocable permission, using access tokens. On its own it is about permission, not identity.
- **OpenID Connect (OIDC)**: a sign-in layer on top of OAuth 2.0. The app receives an **ID token** saying who the user is, with claims such as email, name and group memberships. Most new apps use OIDC.
- **SAML 2.0**: an older, XML-based SSO standard. Many large Indian enterprises and government bodies still use it for internal apps.

```flow
User opens the app -> Your app redirects to sign in -> Identity provider | Entra ID, Okta
Identity provider -[password + MFA, seen only by the provider]-> Redirect back with a short-lived code
Redirect back with a short-lived code -> Your app exchanges the code for tokens
Your app exchanges the code for tokens -> ID token (who) + access token (what)
ID token (who) + access token (what) -> Verify signature, issuer, audience, expiry -> Create a session | user id, email, groups
```

This lesson follows a quality-documents assistant rolled out to plant staff at an automobile-parts manufacturer in Chennai.

## How it works

**The OIDC sign-in flow** (authorisation code flow with PKCE, the recommended one):

1. The user opens your app; it redirects them to the identity provider.
2. They sign in there, often with multi-factor authentication. Your app never sees their password.
3. The provider redirects back with a short-lived code.
4. Your server exchanges the code for an ID token and an access token.
5. Your server verifies the token's signature, issuer, audience and expiry, then creates its own session.

**Claims and groups.** The ID token can carry the user's groups or roles ("claims-officers-south", "hr-admins"). Ask the client's identity team to include the groups your app needs. These drive what the user may do in your app and, later, which documents they may retrieve.

**Calling downstream systems as the user.** Your AI app may need data from another system, such as SharePoint or an internal API. The best pattern is to exchange the user's token for one scoped to that system (the "on-behalf-of" flow), so that system applies the user's own permissions. A shared service account bypasses those permissions.

**Registering the app.** The client's identity team registers your app with the provider: its redirect URLs, which users or groups may use it and which claims to send. Expect this to take days, not minutes, at large companies. Start the request in week one.

**Use a library.** Never write token validation yourself. Use the provider's SDK or a well-known library for your framework.

**Which standard to expect:**

| Situation | Likely standard | Notes |
| --- | --- | --- |
| New web app, modern provider | OIDC | Simplest, JSON tokens, good libraries |
| Large enterprise, older internal apps | SAML 2.0 | XML assertions; use a library or a gateway |
| App calling an API for the user | OAuth 2.0 access tokens | Scope them narrowly |
| AI app reading SharePoint or Box | OIDC sign-in plus on-behalf-of | The downstream system applies user permissions |

**The registration request.** A one-page request saves days of back-and-forth. Include the app's name and purpose, redirect URLs for each environment, the groups that may use it, the claims needed (email, name, groups), whether the app calls other systems on the user's behalf and with what scopes, and a technical contact. Ask the identity team which groups already exist rather than inventing new ones, because creating and filling groups is often the slowest step.

**Sessions after sign-in.** Once tokens are verified, keep a server-side session with a sensible lifetime, such as eight hours for plant shifts, and re-check group membership when the session renews. When IT disables an account, the next renewal fails and access ends.

**OIDC sign-in with FastAPI and Authlib.** The library handles redirects, PKCE, code exchange and token checks:

```python
import os
from authlib.integrations.starlette_client import OAuth
from fastapi import FastAPI, Request, HTTPException, Depends
from starlette.middleware.sessions import SessionMiddleware

app = FastAPI()
app.add_middleware(SessionMiddleware, secret_key=os.environ["SESSION_SECRET"], https_only=True,
                   max_age=8 * 3600)

oauth = OAuth()
oauth.register(
    name="corp",
    server_metadata_url=os.environ["OIDC_DISCOVERY_URL"],   # e.g. .../v2.0/.well-known/openid-configuration
    client_id=os.environ["OIDC_CLIENT_ID"],
    client_secret=os.environ["OIDC_CLIENT_SECRET"],
    client_kwargs={"scope": "openid email profile", "code_challenge_method": "S256"},
)

@app.get("/login")
async def login(request: Request):
    return await oauth.corp.authorize_redirect(request, request.url_for("callback"))

@app.get("/auth/callback")
async def callback(request: Request):
    token = await oauth.corp.authorize_access_token(request)    # verifies the ID token
    claims = token["userinfo"]
    request.session["user"] = {"id": claims["sub"], "email": claims.get("email"),
                               "groups": claims.get("groups", [])}
    return {"signed_in": claims.get("email")}

def require_group(group):
    def check(request: Request):
        user = request.session.get("user")
        if not user or group not in user["groups"]:
            raise HTTPException(status_code=403)
        return user
    return check

@app.get("/admin/reports")
def reports(user=Depends(require_group("claims-officers-south"))):
    return {"ok": True, "for": user["email"]}
```

The session stores the verified subject id and groups, never anything the browser sent. Use the `sub` claim (or the provider's object id) as the user's key, not the email, which can change.

**Verifying tokens sent to an API.** If a front end sends bearer tokens to your API, check them on every request:

```python
import jwt

jwks = jwt.PyJWKClient(os.environ["OIDC_JWKS_URL"])

def verify(bearer):
    key = jwks.get_signing_key_from_jwt(bearer)
    return jwt.decode(bearer, key.key, algorithms=["RS256"],
                      audience=os.environ["API_AUDIENCE"], issuer=os.environ["OIDC_ISSUER"])
```

Signature, audience, issuer and expiry are all checked by `jwt.decode`; never skip any of them.

**Large group lists.** Some providers stop listing groups in the token once a user has too many (Microsoft Entra ID switches to an "overage" pointer). Either ask the identity team to send only the app's groups (app roles are a clean way), or fetch groups from the provider's API at sign-in.

**Leavers and SCIM.** Disabling a user at the identity provider stops new sign-ins, but an open session may last hours. Keep sessions short, re-check at renewal, and where the client supports it, accept SCIM provisioning so that removing a user in their directory deactivates them in your app immediately.

**SAML without writing SAML.** If the client only offers SAML, put a gateway or identity broker in front (many managed auth services translate SAML to OIDC), so your app still speaks one standard.

**Try it in your browser.** An ID token is three base64 parts. Decode the middle one to see the claims, which is what your library verifies.

```python
import base64, json

token = ("eyJhbGciOiJSUzI1NiJ9."
         "eyJzdWIiOiJ1LTQ0MSIsImVtYWlsIjoicHJpeWFAZXhhbXBsZS5pbiIsImdyb3VwcyI6WyJjbGFpbXMtc291dGgiXSwiZXhwIjoxOTAwMDAwMDAwfQ."
         "signature")
header, payload, signature = token.split(".")
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print(claims)
print("never trust these until the signature, issuer, audience and expiry are checked")
```

## A worked example

A Chennai automobile-parts manufacturer on Microsoft Entra ID wants your quality-documents assistant available to 1,200 plant staff.

Week one: you send the identity team a one-page request: app name, redirect URLs for staging and production, the groups to include (`quality-engineers`, `plant-chennai`, `plant-pune`, `contractors`) and whether the app needs to call SharePoint on the user's behalf (yes, read-only).

Your FastAPI backend uses a maintained OIDC library. After sign-in, it verifies the ID token and stores the user's id, email and groups in a session. Requests to SharePoint use an on-behalf-of token, so a Pune engineer can only retrieve documents their own SharePoint permissions allow.

At go-live, contractors complain they cannot sign in. The provider's sign-in error says they are not assigned to the app: the identity team had assigned only employee groups, not `contractors`. One change in the provider's assignment fixes it. When a quality engineer leaves the company the following month, IT disables their account and their access to the assistant ends with no action from you.

| Event | What happened | Who fixed it |
| --- | --- | --- |
| Week one | Registration request sent | You, to the identity team |
| Go-live | Contractors could not sign in | Identity team added the group assignment |
| A month later | An engineer left the company | IT disabled one account; access ended automatically |

## Common mistakes

- **Building your own login.** Clients will refuse it, and it duplicates their security controls badly.
- **Skipping token validation steps.** Check signature, issuer, audience and expiry every time, with a library.
- **Using OAuth access tokens as proof of identity.** Use the OIDC ID token for who the user is.
- **One service account for all downstream calls.** Users can then see what their own permissions forbid.
- **Asking for app registration late.** Identity teams have queues and approvals. Ask on day one.
- **Keying users by email.** Emails change; use the stable subject or object id.
- **Long sessions with no renewal check**, so leavers keep access.
- **Skipping audience or issuer checks** on bearer tokens.

## When you do not need single sign-on

- **Consumer apps**, where Google, GitHub or email sign-in is what users expect.
- **A prototype for one team**, where a managed auth service's email login is enough until the pilot is approved.
- **Machine-to-machine calls** with no user, which use client credentials or API keys instead.

Enterprise clients almost always require SSO before production; plan for it from the first week.

## From demo to production

- **Send the registration request in week one**, with redirect URLs for every environment.
- **Use maintained libraries** for OIDC and token checks.
- **Keep sessions short** and re-check groups on renewal.
- **Support SCIM or a deprovisioning hook** where the client offers it.
- **Log sign-ins, failures and group changes** to the audit log.
