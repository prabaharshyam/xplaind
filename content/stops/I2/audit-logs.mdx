## What it is

An **audit log** is a record of significant events: who did what, when, to which data, and with what result. It differs from application logs and traces:

- **Application logs** help engineers debug. They are noisy, short-lived and may change format freely.
- **Traces** show the internal steps of a request in detail, for engineering and quality work.
- **Audit logs** answer accountability questions: "Who asked the assistant about account 4471 on 3 March, what did it show them and did anyone approve the refund?" They must be complete, consistent, protected from tampering and kept for a defined period.

For AI systems, audit events usually include sign-ins and every question and answer, or a reference to them. They also cover documents retrieved, tool actions taken, approvals and rejections, configuration changes (prompt, model, permissions) and admin actions.

| | Application logs | Traces | Audit logs |
|---|---|---|---|
| For | Engineers | Quality and debugging | Compliance and disputes |
| What they hold | Noisy, short lines whose format changes | Every internal step of a request | Who did what, when, to what, and the result |
| Shape | Free text | Spans | Fixed shape, append-only |
| Kept for | Days | Weeks | Years, per policy |

## How it works

**A fixed event shape.** Each event records a timestamp in a stated time zone and the actor: a user id, a service, or "agent on behalf of user X". It also records the action, the target (document or record ids), the outcome, a request or trace id that links to details, and the app, prompt and model versions in force.

**What not to record.** Never log passwords, tokens or full card numbers. Decide deliberately about personal data: often you store ids and hashes in the audit log, and keep full text in a separate, more restricted store with a shorter retention, linked by id. Follow the client's retention policy and the law; India's DPDP Act requires that personal data is not kept longer than needed.

**Tamper resistance.** Write audit events to an append-only store that application code cannot edit or delete: a write-once storage bucket with retention locks, a managed audit service, or a separate log account. Restrict who can read the log, and log access to the log itself.

**Make it queryable.** Investigations need answers in minutes: "all actions on this customer record in March", "every refund the agent proposed that a person approved". Store events in a format your client's tools can search.

**Clock and identity.** Use synchronised clocks and the verified identity from sign-on, never a name the user typed.

**An audit event, field by field:**

| Field | Example | Why |
| --- | --- | --- |
| Timestamp | `2026-05-03 11:02:14 IST` | When, in a stated time zone |
| Actor | `user=emp-2213` or `agent (on behalf of emp-2213)` | Who, verified through sign-on |
| Action | `ask`, `retrieve`, `propose`, `approve` | What happened |
| Target | `customer=CUST-4471`, document ids | To what |
| Outcome | `success`, `rejected`, `error` | With what result |
| Links | `request=req-88a1 trace=tr-71f0` | Where to find details |
| Versions | `prompt=v12 model=...` | What configuration produced it |

**Retention and access in practice.** Agree retention with the client's compliance team before launch. For example, keep audit events for eight years to match financial record rules, full question and answer text for 180 days in a restricted store, and application logs for 30 days. Give read access to the audit log to a small named group, such as compliance and security, not to the whole engineering team, and review that list every quarter.

**An insert-only table in Postgres.** Permissions plus a trigger, so neither the app nor a careless admin script can rewrite history:

```sql
CREATE TABLE audit_events (
  id bigserial PRIMARY KEY,
  at timestamptz NOT NULL DEFAULT now(),
  actor text NOT NULL, action text NOT NULL, target text,
  outcome text NOT NULL, request_id text, versions jsonb,
  detail jsonb, prev_hash text, hash text NOT NULL
);

CREATE FUNCTION audit_no_change() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'audit_events is append-only';
END $$ LANGUAGE plpgsql;

CREATE TRIGGER audit_lock BEFORE UPDATE OR DELETE ON audit_events
  FOR EACH ROW EXECUTE FUNCTION audit_no_change();

GRANT INSERT, SELECT ON audit_events TO app;
GRANT USAGE ON SEQUENCE audit_events_id_seq TO app;
```

**A hash chain in code.** Each event includes the hash of the one before, so a changed or missing row shows up when you verify:

```python
import hashlib, json

def event_hash(event, prev_hash):
    body = json.dumps({k: event[k] for k in sorted(event) if k not in ("hash", "prev_hash")},
                      sort_keys=True, default=str, ensure_ascii=False)
    return hashlib.sha256((prev_hash or "").encode() + body.encode()).hexdigest()

def append(db, event):
    with db.transaction():
        last = db.fetchone("SELECT hash FROM audit_events ORDER BY id DESC LIMIT 1 FOR UPDATE")
        prev = last[0] if last else None
        event["prev_hash"], event["hash"] = prev, event_hash(event, prev)
        db.insert("audit_events", event)

def verify(rows):
    prev = None
    for r in rows:                                 # ordered by id
        if r["prev_hash"] != prev or event_hash(r, prev) != r["hash"]:
            return f"chain broken at event {r['id']}"
        prev = r["hash"]
    return "ok"
```

Run `verify` nightly and copy the latest hash somewhere the application cannot write, such as a separate account or a daily email to compliance. Then even someone with database access cannot quietly rewrite the chain.

**Write-once storage for exports.** Cloud object stores can lock objects against deletion for a retention period (for example S3 Object Lock in compliance mode). Export audit events there daily as compressed files. This also keeps the main database small.

**Queries investigators need, ready in advance.**

```sql
-- Everything that touched one customer in a date range, in IST:
SELECT at AT TIME ZONE 'Asia/Kolkata', actor, action, outcome, request_id
FROM audit_events WHERE target = 'customer=CUST-4471'
  AND at >= '2026-03-01 00:00+05:30' AND at < '2026-04-01 00:00+05:30' ORDER BY at;

-- Agent proposals approved by one manager:
SELECT a.at, a.target, a.detail->>'amount_inr' AS amount
FROM audit_events a WHERE a.action = 'approve' AND a.actor = 'emp-1180' ORDER BY a.at;
```

Save these as named queries or dashboard views for the compliance team.

**Log access to the log.** Reading audit events is itself an event worth recording: who searched for which customer, and when.

## A worked example

A Kochi cooperative bank uses an AI agent to help staff draft responses to loan-restructuring requests. Six months later a borrower complains that their request was rejected unfairly, and the bank's ombudsman office asks for the full history.

Because every event was audited, the bank's compliance officer can produce, in an hour:

```text
2026-05-03 11:02:14 IST  user=emp-2213 (branch: Aluva)  action=ask
    request=req-88a1 trace=tr-71f0 customer=CUST-4471 prompt=v12 model=alias:chat-default(2026-04)
2026-05-03 11:02:19 IST  agent(on behalf of emp-2213)  action=retrieve
    docs=[policy-restructuring-v6#s4, cust-4471-statement-2026-04]
2026-05-03 11:02:31 IST  agent(on behalf of emp-2213)  action=propose  type=reject_restructuring  reason_ref=tr-71f0
2026-05-03 11:09:47 IST  user=emp-0457 (manager)  action=approve  proposal=req-88a1
```

The history shows that the policy version used had since been revised, and that a manager approved the AI's recommendation within seven minutes. The bank reopens the case, and adds a rule that restructuring rejections need a written note from the approver. The audit log did not prevent the mistake, but it made it visible, fixable and explainable to the ombudsman.

**What the bank changed afterwards.** Beyond the written-note rule, the bank added two checks. An alert fires when a manager approves a high-impact AI recommendation within two minutes, a sign of rubber-stamping. A monthly report shows how often managers override the agent's proposals.

## Common mistakes

- **Using debug logs as the audit trail.** They are incomplete, editable and rotated away.
- **Recording everything in full.** Full prompts with personal data in a long-retention log create a new privacy risk. Store references and keep full text separately with shorter retention.
- **Editable storage.** If an administrator can delete entries quietly, the log proves little.
- **No version information.** Without prompt and model versions you cannot explain why the system behaved as it did then.
- **Logging the agent as the actor.** Always record on whose behalf it acted, and who approved.
- **Auditing only failures.** Disputes are usually about decisions that "worked". Record successful actions and approvals too.
- **Audit rows the application can update or delete.** Lock them with permissions and a trigger.
- **No way to detect tampering.** Use a hash chain and keep the latest hash elsewhere.
- **Building investigation queries during the incident.** Write and test them in advance.

## When ordinary logs are enough

- **Prototypes and personal tools** with no other users.
- **Read-only assistants on public information**, where nobody's records change.
- **Short-lived internal experiments** that never touch customer data.

Formal audit logs are needed once the system acts on records, handles personal or financial data, or a client's compliance team will ask "who did what, when?".

## From demo to production

- **Use a fixed event schema** with verified identities, IST timestamps and versions.
- **Make audit storage append-only**, with a nightly hash-chain check.
- **Export daily to write-once storage** with the agreed retention.
- **Restrict and log read access** to a named group, reviewed quarterly.
- **Keep investigation queries saved and tested.**
