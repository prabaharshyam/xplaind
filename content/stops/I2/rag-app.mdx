## What it is

A **RAG app** (retrieval-augmented generation) answers questions from your own documents. For each question it:

1. **retrieves** the most relevant passages from an index of your documents;
2. **augments** the prompt with those passages;
3. **generates** an answer that uses only those passages and cites them.

It is one of the most common ways companies use language models on their own data, because it needs no model training and stays current when documents change.

```text
  INGESTION (once, then on updates)
  PDFs --> [extract text, OCR] --> [chunk by heading, ~400 tokens, title + section]
       --> [embed] --> index (pgvector) with metadata: doc, page, section, dates

  QUERY TIME
  question --> [hybrid search: vectors + keywords] --> top 20 --> [rerank] --> top 5
           --> prompt: instructions + [1]..[5] with sources + question
           --> model --> answer with citations [2][4]  or  "I could not find this..."
```

This lesson follows a college in Coimbatore building an assistant for students' questions about regulations, fees, exams and scholarships.

## How it works

**Ingestion (once, then on updates).** Load documents, extract clean text, split into chunks with titles and page numbers, embed each chunk and store it in an index with its metadata.

**Query time.**

- Embed the question; retrieve the top candidates (vector search, ideally hybrid with keyword search); optionally rerank and keep the best five.
- Build the prompt: instructions, the passages each labelled with an id and source, then the question.
- Instruct the model: answer only from the passages; cite passage ids; if the passages do not contain the answer, say so.
- Return the answer with its citations, linked to the source documents.

**Contextual retrieval.** Chunks often lack context ("the limit is 45 days"). Prepending a short description of where the chunk sits in its document, and combining embeddings with keyword search, measurably reduces retrieval failures.

**Saying "I don't know".** A trustworthy RAG app refuses when the documents are silent. Include unanswerable questions in your tests.

**Evaluation.** Keep a fixed set of questions with expected sources and answers. Measure retrieval (recall at k) and answers (correctness, faithfulness) separately, and rerun after every change.

**Freshness and access.** Re-index changed documents; filter out superseded ones; if users have different permissions, filter retrieval by what each user may see.

**A minimal query function:**

```python
def answer(question, user):
    hits = hybrid_search(question, k=20, filters={"access": user.groups})
    top = rerank(question, hits)[:5]
    passages = "\n\n".join(
        f"[{i+1}] {h.title}, section {h.section}, page {h.page}\n{h.text}"
        for i, h in enumerate(top)
    )
    prompt = (
        "Answer using only the passages. Cite like [2] after each sentence. "
        "If the passages do not answer the question, say so and name the office to contact.\n\n"
        f"Passages:\n{passages}\n\nQuestion: {question}"
    )
    return call_model(prompt), top
```

Returning `top` along with the answer lets the interface link each citation to its document and page, and lets your logs show what was retrieved when an answer goes wrong.

**What to measure first:**

| Measure | Question it answers | Target to aim for |
| --- | --- | --- |
| Recall at 5 | Is the right passage retrieved? | Above 85% on the golden set |
| Correctness | Is the answer right? | Agreed with the client |
| Faithfulness | Is every claim supported by a passage? | Above 0.9 |
| Refusal rate on unanswerable questions | Does it admit when documents are silent? | Above 75% |
| Latency | Is it fast enough? | First words within 2 seconds |

**Debugging a wrong answer.** Look at the retrieved passages first. If the right passage is missing, the problem is ingestion or retrieval: parsing, chunking, filters or search. If it is present and the answer is still wrong, the problem is the prompt or the model. This one check saves a lot of guessing.

## A worked example

A college in Coimbatore builds an assistant for students' questions about academic regulations, fees, exams and scholarships, from 25 PDFs.

- Ingestion: text extracted with page numbers, split by headings into about 400-token chunks with the document title and section prepended, embedded and stored in pgvector.
- Retrieval: hybrid search (vectors plus keywords), top 20 reranked to 5.
- Prompt: "Answer using only the passages. Cite like [2]. If the answer is not in the passages, say 'I could not find this in the college regulations' and suggest the office to contact."
- Interface: the answer shows citations that open the PDF at the right page.

Testing with 50 questions (including eight unanswerable): 40 of the 42 answerable questions correct with correct citations, 6 of the 8 unanswerable correctly refused. Two failures came from a fee circular that was a scanned image; after OCR, both were fixed. Students now ask the assistant before queuing at the office, and staff answer fewer repeat questions.

| Test set of 50 questions | Result |
| --- | --- |
| Answerable questions answered correctly with right citations | 42 of 42 after the OCR fix |
| Unanswerable questions correctly refused | 6 of 8 |
| Failures traced to a scanned fee circular | 2, fixed by OCR |

**What the college learned.** The biggest single gain came from parsing, not from the model: once the scanned fee circular was readable, two wrong answers became right. Citations that opened the PDF at the right page made the office staff trust the assistant enough to point students to it, which is how usage grew.

## Common mistakes

- **No citations.** Users cannot check, and errors go unnoticed.
- **No refusal path.** The model guesses when documents are silent.
- **Skipping retrieval evaluation.** Most failures are retrieval failures.
- **Ignoring scanned documents and tables.** They need OCR and table-aware parsing.
- **Indexing once and forgetting.** Documents change; re-index.
