## What it is

Serving means running your application so real users can rely on it. It starts automatically, restarts when it crashes, handles many requests at once, refuses extra load cleanly, and shows something quickly even when the model is slow.

For a Python AI service, the usual stack is FastAPI for the app and **Uvicorn** as the server that runs it, with several worker processes. Something sits in front, such as a load balancer, an ingress or a platform like Cloud Run, to handle HTTPS and spread traffic.

AI services differ from a normal web API in three ways. Requests are slow, often 2 to 30 seconds, because they wait on model calls. Users tolerate that only if they see progress, which is why **streaming** matters. And the scarce resource is someone else's: the provider limits your requests and tokens per minute, so its quota and your bill, not your CPU, are usually the bottleneck.

```flow
Users -[HTTPS]-> Load balancer | idle timeout 30 s, routes to ready instances
Load balancer -> Container 1 | 4 Uvicorn workers, at most 40 model calls each
Load balancer -> Container 2 | same
Container 1 -[deadline 25 s, retries inside]-> Model API | tokens streamed back to the user
Container 1 -> Background queue | OCR and indexing; returns a job id
```

This lesson follows a doubt-solving assistant at an edtech company in Lucknow that slowed to a crawl every evening.

## How it works

### Workers and the event loop

One Uvicorn process runs its async endpoints on a single **event loop**. While one request awaits the model, the loop serves others, so one process can hold hundreds of waiting requests. But anything that blocks the loop freezes every request in that process: a synchronous Redis, database or `requests` call, PDF parsing, a local embedding model.

The fixes: use an **async client** for network calls; or write the endpoint as a plain `def`, which FastAPI runs in a thread pool; or move heavy work to a **background queue**. Then run several workers, usually one or two per CPU core, so one crash does not take everything down. For a service that mostly waits on a model API, removing blocking calls helps more than adding workers.

### Timeouts in layers

Every wait needs a limit, inner shorter than outer, or the outer one fires first and the user gets a blank load balancer error instead of your message. A **total** timeout caps the whole request. An **idle** timeout caps silence, so a stream that keeps sending is never cut; the AWS Application Load Balancer, for example, uses a 60-second idle timeout by default.

The official Anthropic Python SDK has a trap. Its `timeout` applies to connecting and to each wait for the next chunk, per attempt; it is not a total deadline. It also retries 429s and server errors twice by default, waiting as long as the provider's `retry-after` header asks. So `timeout=30, max_retries=2` can hold a request well past 90 seconds. Put one deadline of your own around the whole call, with the retries inside it.

| Layer | Kind | Example value | What it catches |
| --- | --- | --- | --- |
| SDK `timeout` | Per attempt, per chunk | 10 s | A dead connection or a stalled stream |
| SDK `max_retries` | Count | 1 | A brief provider error; spends the same budget |
| Your deadline | Total, retries included | 25 s | Everything above, with a message you wrote |
| Load balancer | Usually idle | 30 s | A hung instance; never fires first if the layers are right |
| Shutdown grace | Total | 30 s server, 40 s platform | Streams cut off during a deploy |

### Streaming, and what breaks it

With **server-sent events** (SSE), the server keeps the response open and sends each piece as a `data:` line. Since version 0.135.0, FastAPI supports this directly: set `response_class=EventSourceResponse` and `yield` from the endpoint. FastAPI encodes each item as JSON, so a newline in the answer cannot break the format. It sets `Cache-Control: no-cache` and `X-Accel-Buffering: no` (a hint for nginx), and sends a keep-alive comment after 15 quiet seconds.

Streaming does not make generation faster; it makes waiting feel shorter, because the first words arrive in a second or two. The gotchas appear only in production:

- **Buffering proxies.** An ingress, proxy or compression layer may hold the whole response, so users see nothing and then everything. nginx buffers proxied responses by default, and the header alone is not always enough. Turn buffering off for the route (`proxy_buffering off;` in nginx) and test through the real path.
- **Idle timeouts.** A long silence, for example while the model reads a long prompt, can trip the balancer. Keep-alive comments must come more often than its idle timeout.
- **POST in the browser.** `EventSource` cannot send a request body; read a POST stream with `fetch` and a stream reader.
- **Failures halfway.** After a 200 and half an answer, the status code cannot change. Send an error event, show the partial text with "answer interrupted, try again", and never cache it. Count these in your logs, because status-code dashboards miss them.
- **Disconnects.** When the tab closes, FastAPI cancels the generator and the SDK's `async with` closes the model stream, so you stop paying for unread tokens.

### The endpoint

A concurrency cap that sheds load, one deadline around the model call, JSON events and readable errors. Tested with FastAPI 0.165, the Anthropic SDK 2.14 and Python 3.13 against a local fake of the API; it needs FastAPI 0.135.0 or later and Python 3.11 or later.

```python
import asyncio
import anthropic
from fastapi import Depends, FastAPI, HTTPException
from fastapi.sse import EventSourceResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=10, max_retries=1)   # per attempt, per chunk
SLOTS = asyncio.Semaphore(40)      # at most 40 model calls at once in this process
MODEL_DEADLINE = 25                # seconds for the whole model call, retries included

class Question(BaseModel):
    text: str

async def model_slot():
    try:                                         # wait at most 1 s for a free slot
        await asyncio.wait_for(SLOTS.acquire(), timeout=1)
    except TimeoutError:
        raise HTTPException(429, "Busy, please try again in a few seconds",
                            headers={"Retry-After": "5"})
    try:
        yield                                    # the request streams here
    finally:
        SLOTS.release()                          # after the stream ends, even on disconnect

async def with_deadline(chunks, seconds):
    loop = asyncio.get_running_loop()
    end = loop.time() + seconds
    it = aiter(chunks)
    while True:
        try:
            yield await asyncio.wait_for(anext(it), end - loop.time())
        except StopAsyncIteration:
            return

async def model_text(question: str):
    async with client.messages.stream(
            model="claude-sonnet-5-5", max_tokens=600,      # check the docs for current names
            messages=[{"role": "user", "content": question}]) as stream:
        async for text in stream.text_stream:
            yield text

@app.post("/answer", response_class=EventSourceResponse)
async def answer(body: Question, _: None = Depends(model_slot)):
    try:
        async for text in with_deadline(model_text(body.text), MODEL_DEADLINE):
            yield {"text": text}
        yield {"done": True}
    except TimeoutError:
        yield {"error": "This is taking longer than usual. Please try again."}
    except anthropic.APIError:
        yield {"error": "The AI service is busy. Please try again."}

@app.get("/health")
async def health():
    return {"ok": True}
```

Why it is shaped this way:

- **The slot is taken before the response starts**, in a dependency, because a 429 is impossible once the 200 has gone. A one-second wait absorbs tiny bursts; beyond that, a fast "busy" beats a silent queue. The `finally` returns the slot when the stream ends, even on disconnect.
- **The deadline wraps each wait, not the yield.** `with_deadline` times every step, including opening the stream with its retries, against one end time. A timeout block around a `yield` misbehaves in async generators.
- **The cap is per process**: 40 slots, 4 workers and 2 containers allow 320 calls at once.

### Rate limits: yours and the provider's

At the evening peak, the provider's 429 is the most common failure. Retry briefly with backoff and **jitter** (a random part of the wait, so thousands of clients do not retry at the same instant); the SDK does this and honours `retry-after`, so keep the count low enough to fit the deadline. Then fail clearly, or fall back to another region or an approved smaller model through a gateway (see the LLM gateways lesson). **Limit each user** too, for example 20 questions per 10 minutes and a daily token cap, or one script can use the quota for everyone and your bill has no ceiling. Your own 429 carries `Retry-After`, and your front end should obey it.

### Health, readiness and shutdown

- **`/health`** (liveness) says the process is alive and touches nothing else, so the platform restarts only processes that are truly stuck.
- **`/ready`** (readiness) says this instance can take traffic: 503 until start-up work, such as loading an index, is done. Do not fail it on a shared dependency. If every instance checks the same database, one blip fails them all at once and the balancer removes them all, turning a partial outage into a total one. Return a clear error per request and alert separately.
- **Neither calls the model.** It costs money, and a slow provider would mark every instance unhealthy together.

**Graceful shutdown.** On a deploy, the platform sends SIGTERM. The server stops accepting connections and lets in-flight requests finish, up to `--timeout-graceful-shutdown`. That must exceed your longest stream, and the platform's grace period must exceed the server's, or the platform kills the process first. Kubernetes allows 30 seconds by default (raise `terminationGracePeriodSeconds`). Cloud Run gives only 10 seconds after SIGTERM, so long streams there can be cut during a scale-down; let the client offer a retry.

### Running it

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4 \
  --timeout-graceful-shutdown 30
```

In a test with two workers, a stream running when SIGTERM arrived finished all its tokens while new requests were not served. If you use Gunicorn, note that recent Uvicorn versions deprecate `uvicorn.workers`; use the `uvicorn-worker` package (`-k uvicorn_worker.UvicornWorker`).

### Background jobs with a queue

Work that takes minutes, such as OCR or indexing a 500-page PDF, goes to a worker process, and the request returns a job id at once. With Redis Queue (RQ):

```python
from fastapi import HTTPException
from redis import Redis
from rq import Queue
from rq.exceptions import DuplicateJobError

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents/{doc_id}/index")
def start_indexing(doc_id: str):        # plain def: runs in a thread, so Redis cannot block the loop
    job_id = f"index-{doc_id}"          # same document, same job id
    try:
        queue.enqueue("workers.index_pdf", doc_id, job_id=job_id, unique=True,
                      job_timeout=1800, result_ttl=86400)
    except DuplicateJobError:
        pass                            # a double click or a client retry: the job already exists
    return {"job_id": job_id, "status_url": f"/jobs/{job_id}"}

@app.get("/jobs/{job_id}")
def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    if job is None:
        raise HTTPException(404, "Unknown or expired job")
    return {"status": job.get_status()}
```

`unique=True`, added in RQ 2.8, makes submission **idempotent**: the same request twice gives one job. `result_ttl` keeps the finished job for a day; the default is 500 seconds, after which the status URL returns 404. Make the worker itself safe to run twice, because a worker can crash halfway. Celery, Arq and cloud task queues follow the same pattern.

### Measuring and observing

Log one line per request: request id, user, model, tokens, cost, time to first token, total time and outcome (done, deadline, provider error, shed). Watch p95 time to first token, the shed rate and the provider 429 rate; the tracing lesson covers following a request across services. Load-test the evening peak with a tool such as Locust before launch and after each change.

### Try it in your browser

Sixty requests arrive together; ten can run at once. Compare a queue that never refuses with a short wait before a 429.

```python
import asyncio, random, time

async def model_call(slots, max_wait, waits):
    t0 = time.perf_counter()
    try:
        await asyncio.wait_for(slots.acquire(), max_wait)   # None queues forever
    except asyncio.TimeoutError:
        return "rejected"                                   # send a fast 429: busy, retry soon
    waits.append(time.perf_counter() - t0)                  # time spent waiting for a slot
    try:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model call
    finally:
        slots.release()
    return "served"

async def burst(cap, max_wait, n=60):
    slots, waits = asyncio.Semaphore(cap), []
    results = await asyncio.gather(*(model_call(slots, max_wait, waits) for _ in range(n)))
    print(f"max_wait {str(max_wait):>4}: served {results.count('served'):>2}, "
          f"rejected {results.count('rejected'):>2}, worst wait {max(waits, default=0):.2f} s")

random.seed(1)
for max_wait in (None, 0.1, 0.01):
    await burst(cap=10, max_wait=max_wait)
```

With no limit, the last request waits about five model-call times before it starts; with real calls taking seconds, that is the silent spinner users leave. With a short wait, extra requests hear "busy" at once.

## A worked example

An illustrative case: the numbers show the kind of change to expect, not a measured study. A Lucknow edtech's doubt-solving assistant ran as one Uvicorn process. In the evening, students waited about 12 seconds for any text. About a third of requests hit the load balancer's 30-second limit, because a non-streamed answer sends nothing until it is complete. OCR on uploaded handwritten notes ran inside an `async def` endpoint and froze the server for everyone.

The changes:

- **Streaming** with FastAPI's SSE support. In staging the answer still arrived all at once, because the nginx ingress buffered it; turning buffering off for `/answer` fixed it.
- **Four workers per container, two containers**, 40 model slots per worker, after checking that 320 calls at once fit the provider quota.
- **Timeouts in layers**: SDK 10 s with one retry, a 25 s deadline per model call, the balancer's 30 s idle timeout above both. When the deadline fires, the student sees "This is taking longer than usual; please try again".
- **Limits**: 20 questions per 10 minutes per student, and a fast 429 with `Retry-After` when all slots are busy, shown as "Many students are asking right now, retrying in 5 seconds".
- **OCR on a background queue**, with a job id derived from the file, so a double tap creates one job. The page shows "Reading your notes..." until the result is ready.
- **Health and deploys**: `/ready` checks only start-up; graceful shutdown is 30 s inside a 40 s platform grace period.

| Measure at evening peak (illustrative) | Before | After |
| --- | --- | --- |
| Time to first text, p95 | About 12 s | About 1 to 2 s |
| Requests hitting a timeout | About 33% | Under 1% |
| Server freezes from OCR uploads | Daily | None |
| Students leaving before an answer | Baseline | Down by about two thirds |
| Provider 429s reaching students | Frequent, as blank errors | Rare, as a clear "busy, retrying" |

## Common mistakes

- **A sync client inside `async def`.** One blocking Redis, database or HTTP call freezes every request in that worker.
- **Trusting the SDK timeout as a deadline.** Retries and `retry-after` waits stack on top of it.
- **Checking the cap inside the stream.** By then the 200 has gone and a 429 is impossible.
- **Forgetting that caps multiply.** 50 per process across 4 workers and 3 containers is 600 calls at once, perhaps far above the provider quota.
- **Testing streaming only on localhost**, where no proxy buffers it.
- **A readiness check on a shared dependency.** One database blip removes every instance together.
- **A server grace period longer than the platform's.** The platform kills the process first and cuts streams anyway.
- **Clients that retry a 429 at once**, turning a short overload into a long one.
- **Random job ids**, so a double click starts the same expensive job twice.

## When simpler serving is fine

- **Internal tools with a few users**: one process, a deadline on model calls and a health check are enough.
- **Batch jobs** that never face users: a scheduled script beats a web service.
- **Serverless routes**, where the platform manages workers and shutdown. Check its time limit against your longest stream.

## From demo to production

- **Remove blocking calls**, then run several workers.
- **Cap model calls** and each user, and check the total against the provider quota.
- **Layer timeouts** and stream through the real path.
- **Queue long work** with idempotent job ids, and set grace periods.
- **Log per request** tokens, cost, time to first token and outcome; watch p95.
