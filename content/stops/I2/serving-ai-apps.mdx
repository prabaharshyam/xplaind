## What it is

Serving means running your application so real users can rely on it. It starts automatically, restarts when it crashes, handles many requests at once, and shows something quickly even when the model is slow.

For a Python AI service, the usual stack is FastAPI for the app and **Uvicorn** as the server that runs it, with several worker processes for parallelism. Something sits in front, such as a load balancer, an ingress or a platform like Cloud Run, to handle HTTPS and spread traffic.

AI services have two special traits. Requests are slow, often 2 to 30 seconds, because they wait on model calls. And users tolerate that only if they see progress, which is why **streaming** matters.

```flow
Users -[HTTPS]-> Load balancer | timeout 30 s, checks /ready
Load balancer -> Container 1 | 4 workers, Uvicorn + FastAPI
Load balancer -> Container 2 | 4 workers
Container 1 -> Model API | timeout 25 s, tokens streamed to the user
Container 1 -> Background queue | OCR, indexing; a job id and status
```

This lesson follows a doubt-solving assistant at an edtech company in Lucknow that slowed to a crawl every evening.

## How it works

**Workers and concurrency.** One Uvicorn process with async endpoints can hold many requests that are waiting on the network. CPU-heavy work, such as parsing a PDF or running a local embedding model, blocks that process. So you run several workers, usually one or two per CPU core, or move heavy work to a background queue.

**Timeouts everywhere.** Set a timeout on every model and tool call, on the request as a whole and at the load balancer, with the inner ones shorter than the outer ones. Return a clear 503 or 504 instead of hanging.

**Streaming.** With `StreamingResponse` and server-sent events, you forward tokens to the client as the model produces them. Time to first token drops from the full generation time to well under a second. Handle client disconnects, so you stop paying for tokens nobody will read.

**Health checks.** A cheap `/health` endpoint (process is up) and a `/ready` endpoint (dependencies such as the database are reachable) let the platform restart broken instances and send traffic only to ready ones. Do not call the model in a health check.

**Graceful shutdown.** When the platform stops an instance for a deploy, it should stop accepting new requests and let in-flight ones finish within a grace period. Long streaming responses need a grace period longer than your typical generation.

**Background work.** Jobs that take minutes, such as indexing a 500-page PDF, do not belong in a request. Accept the job, return an id at once, process it on a worker queue and let the client poll or receive a webhook.

**A streaming endpoint:**

```python
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

# Question is your Pydantic request model; model_stream is your async model client.
@app.post("/answer")
async def answer(req: Request, body: Question):
    async def tokens():
        async for text in model_stream(body.text, timeout=25):
            if await req.is_disconnected():
                break                     # stop paying for unread tokens
            yield f"data: {text}\n\n"
    return StreamingResponse(tokens(), media_type="text/event-stream")
```

**Measuring before and after.** Record three numbers per request: time to first token, total time and whether it timed out. Look at the 95th percentile, not the average, because the slowest requests are the ones users complain about. Load-test with a tool such as Locust at the expected evening peak before launch, and again after each change.

**A real streaming endpoint.** Forward tokens from the model as server-sent events, with a timeout, a concurrency cap and disconnect handling:

```python
import asyncio, json
import anthropic
from fastapi import FastAPI, Request, HTTPException
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI()
client = anthropic.AsyncAnthropic(timeout=30, max_retries=2)
SLOTS = asyncio.Semaphore(50)                     # at most 50 model calls at once per process

class Question(BaseModel):
    text: str

@app.post("/answer")
async def answer(req: Request, body: Question):
    if SLOTS.locked():
        raise HTTPException(status_code=429, detail="Busy, please retry in a few seconds")
    async def events():
        async with SLOTS:
            try:
                async with client.messages.stream(
                        model="claude-sonnet-5-5", max_tokens=600,         # check the docs for current names
                        messages=[{"role": "user", "content": body.text}]) as stream:
                    async for text in stream.text_stream:
                        if await req.is_disconnected():
                            return                                         # stop paying for unread tokens
                        yield f"data: {json.dumps({'text': text})}\n\n"
                yield "data: [DONE]\n\n"
            except anthropic.APIError:
                yield f"data: {json.dumps({'error': 'The AI service is unavailable. Please try again.'})}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")

@app.get("/health")
async def health():
    return {"ok": True}
```

Encoding each chunk as JSON keeps newlines inside the text from breaking the event format. Leaving the `async with` closes the stream, which stops generation when the user disconnects.

**Running it.** Several worker processes, a graceful timeout longer than the longest stream:

```bash
gunicorn app.main:app -k uvicorn.workers.UvicornWorker --workers 4 \
  --bind 0.0.0.0:8000 --timeout 120 --graceful-timeout 90
```

**Background jobs with a queue.** Long work goes to a worker; the request returns a job id at once. With Redis Queue:

```python
from redis import Redis
from rq import Queue

queue = Queue("ingest", connection=Redis.from_url("redis://redis:6379"))

@app.post("/documents")
async def upload(doc_id: str):
    job = queue.enqueue("workers.index_pdf", doc_id, job_timeout=1800, retry=None)
    return {"job_id": job.id, "status_url": f"/jobs/{job.id}"}

@app.get("/jobs/{job_id}")
async def job_status(job_id: str):
    job = queue.fetch_job(job_id)
    return {"status": job.get_status() if job else "unknown"}
```

Celery, Arq and cloud task queues follow the same pattern.

**Readiness that tells the truth.** `/ready` should check the database and the vector store with a fast query and a short timeout, and return 503 during start-up until models or indexes are loaded. The platform then sends traffic only to instances that can actually answer.

**Try it in your browser.** See why a concurrency cap matters: requests beyond it wait. Change the numbers and run it.

```python
import asyncio, random, time

async def model_call(i, slots):
    async with slots:
        await asyncio.sleep(random.uniform(0.05, 0.15))     # pretend model latency
        return i

async def main(cap, n=40):
    slots = asyncio.Semaphore(cap)
    t0 = time.perf_counter()
    await asyncio.gather(*(model_call(i, slots) for i in range(n)))
    print(f"cap {cap:>2}: {n} requests in {time.perf_counter() - t0:.2f} s")

random.seed(0)
for cap in (2, 10, 40):
    await main(cap)
```

## A worked example

A Lucknow edtech's doubt-solving assistant ran as one Uvicorn process. During evening study hours, students waited 12 seconds for any text. A third of requests timed out at the load balancer's 30-second limit, and uploads of handwritten notes for OCR froze the server for everyone.

The changes:

- Answers stream: the first words appear in about 700 milliseconds.
- Four Uvicorn workers per container and two containers, behind the load balancer.
- Timeouts: model call 25 s, request 28 s, load balancer 30 s. On timeout, the app sends "This is taking longer than usual; please try again" rather than a blank error.
- OCR moved to a background queue. The upload returns a job id; the page shows "Reading your notes..." and fetches the result when ready.
- `/ready` checks the database and queue; a broken container stops receiving traffic within 20 seconds.

Timeouts fell from 33% to under 1% in the evening peak, and the number of students who gave up before seeing an answer fell by two thirds.

| Measure at evening peak | Before | After |
| --- | --- | --- |
| Time to first text | About 12 s | About 0.7 s |
| Requests timing out | 33% | Under 1% |
| Server freezes from OCR uploads | Daily | None |
| Students leaving before an answer | Baseline | Down by two thirds |

## Common mistakes

- **One worker in production.** A single blocked request stalls everyone. Run several and measure.
- **No timeouts.** One hung model call holds a worker forever.
- **Waiting for the full answer.** Without streaming, users stare at a spinner and leave.
- **Health checks that call the model.** They cost money and fail when the provider is slow, taking healthy instances out.
- **Long jobs inside requests.** Use a queue for anything that can take more than a few seconds of CPU.
- **No load test before launch.** The first evening peak should not be the first time the service sees real traffic.
- **No cap on concurrent model calls**, so a burst hits provider rate limits and every request slows.
- **Raw text in SSE events**, where a newline inside the answer breaks the stream.
- **Ready checks that only say the process is alive.**

## When simpler serving is fine

- **Internal tools with a few users**: one process, timeouts and a health check are enough.
- **Batch jobs** that never face users: a scheduled script beats a web service.
- **Platform-hosted functions**, such as serverless routes, where the platform manages workers and shutdown.

## From demo to production

- **Cap concurrency** per process and shed load with a clear 429.
- **Set timeouts** inner to outer: model call, request, load balancer.
- **Stream with disconnect handling**, and set graceful shutdown longer than the longest stream.
- **Move long work to a queue** with job ids and status.
- **Track time to first token, total time and timeouts** at p95.
