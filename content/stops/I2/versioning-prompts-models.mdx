## What it is

An AI system's behaviour depends on more than code:

- the **prompts** (system prompts, templates, few-shot examples);
- the **model** (provider, model name and snapshot or version);
- **settings** such as temperature and maximum tokens;
- **tool definitions** the model sees;
- the **retrieval configuration** (index version, chunking, top-k, reranker).

Versioning means each of these has an identifier, changes go through review and tests, the live combination is recorded with every request, and any previous combination can be restored.

```flow
Release assistant-2026.11.3 | prompts support-system v12 and refund-rules v4; a pinned, dated model snapshot; temperature 0.2; tools lookup_order v3, create_ticket v2; index 2026-11-01 -[recorded in every trace and audit event]-> A change
A change -> Golden set in CI -> Staging -> Production alias
Production alias -[rollback: move the alias back]-> The previous release
```

Every part of a release has its own version, so any answer can be traced back to exactly what produced it.

This lesson follows the support assistant at a fintech in Gurugram, where three teams edited prompts directly in production.

## How it works

**Prompts in version control.** Store prompts as files in the repository (or in a prompt registry), not as strings scattered through code or edited in a dashboard. Changes go through pull requests with evals in CI.

**Prompt registries.** Tools such as MLflow's prompt registry, Langfuse and others store named, numbered prompt versions with aliases ("production", "staging"). The application asks for the prompt by alias; moving the alias deploys or rolls back without a code release. Useful when non-engineers edit prompts, provided changes still pass evals.

**Pin models.** Use dated model snapshots where providers offer them, rather than aliases that silently change. If you use your gateway's aliases ("chat-default"), the gateway configuration is itself versioned and reviewed.

**One release identifier.** Bundle prompt version, model, settings and index version into a release (for example "assistant-2026.11.3") recorded in every trace and audit event.

**Test before promoting.** Every change runs the golden set. Compare with the current release on quality, cost and latency. Promote through staging to production.

**Provider deprecations.** Providers retire models on announced dates. Keep a calendar, test the replacement early, and plan the switch as a release.

**Rollback.** Keep the previous release ready. Rolling back should be one action: move the alias or redeploy the previous tag.

**What to version and how:**

| Part | How to version it | Typical change |
| --- | --- | --- |
| Prompts | Files in Git or a registry with numbered versions | Wording, examples, rules |
| Model | Pinned dated snapshot, or a reviewed gateway alias | Upgrade to a newer model |
| Settings | Config file in Git | Temperature, max tokens |
| Tool definitions | Code in Git | New parameter or tool |
| Retrieval | Index version and config in Git | Chunk size, top-k, reranker |

**Change one thing at a time.** When a release changes the prompt, the model and the index together and quality drops, nobody can say which change did it. Ship them as separate releases where possible, each through the golden set. When several must ship together, such as a model switch that needs prompt adjustments, run the golden set on each step in staging so the effect of each part is known before production.

**Model switches.** Treat a new model as a release candidate: run the full golden set, compare cost and latency, check refusals and tone on sample conversations in each language you serve, and roll out gradually. Prompts tuned for one model often need small changes for the next.

**Prompts as files, releases as one manifest.**

```text
prompts/
  answer.v13.md
  answer.v14.md
  rewrite.v4.md
release.yaml
```

```yaml
# release.yaml
release: assistant-2026.11.3
model: claude-sonnet-5-5-YYYYMMDD     # a dated snapshot where the provider offers one
settings: {max_tokens: 600}
prompts: {answer: v14, rewrite: v4}
index: policies-2026-11-01
tools: tools-v7
```

```python
import hashlib, json, yaml
from pathlib import Path

def load_release(path="release.yaml"):
    rel = yaml.safe_load(open(path))
    rel["prompt_text"] = {name: Path(f"prompts/{name}.{ver}.md").read_text()
                          for name, ver in rel["prompts"].items()}
    blob = json.dumps({k: rel[k] for k in ("model", "settings", "prompts", "index", "tools")}, sort_keys=True)
    rel["fingerprint"] = hashlib.sha256(blob.encode()).hexdigest()[:10]
    return rel

RELEASE = load_release()     # log RELEASE["release"] and RELEASE["fingerprint"] on every trace
```

The fingerprint changes if anyone edits the release without renaming it, which catches "small" untracked changes.

**Checks in CI.** Fail the build when the release points to something missing or risky:

```python
import re
from datetime import date

RETIREMENTS = yaml.safe_load(open("model-retirements.yaml"))     # {model_id: "YYYY-MM-DD"}

def check_release(rel):
    problems = []
    for name, ver in rel["prompts"].items():
        if not Path(f"prompts/{name}.{ver}.md").exists():
            problems.append(f"missing prompt file {name}.{ver}")
    if not re.search(r"\d{8}$", rel["model"]):
        problems.append("model is not pinned to a dated snapshot")
    retire = RETIREMENTS.get(rel["model"])
    if retire and (date.fromisoformat(retire) - date.today()).days < 60:
        problems.append(f"{rel['model']} retires on {retire}; plan the switch")
    return problems
```

Where a provider does not offer dated names, pin what you can (your gateway's alias, reviewed) and run the golden set on a schedule to catch silent changes.

**Promotion and rollback.** Production reads `release.yaml` from the deployed commit, so promoting is merging a pull request and rolling back is redeploying the previous commit. If you use a prompt registry instead, the same rule applies: the app reads an alias, and promotion moves the alias after the golden set passes.

**A changelog humans read.** Next to `release.yaml`, keep a short `CHANGELOG.md`: release id, date, what changed, the eval results compared with the previous release, and who approved. Clients' reviewers often ask for exactly this.

## A worked example

A Gurugram fintech's support assistant had prompts edited directly in an admin panel by three teams. One Friday, complaint volume doubled. Nobody could say what had changed; traces showed only the model name.

The fix:

- Prompts move into the repository as files, with owners per prompt.
- A prompt registry holds published versions; production uses the alias `support-prod`.
- Every trace records the release: prompt versions, model snapshot, temperature, index version.
- CI runs the 120-question golden set on every prompt change and blocks a drop of more than one point.
- Gateway model aliases are changed only by pull request.

Two months later a new prompt version passes evals but customer feedback dips in Hindi conversations. Traces show the dip started with release 2026.12.2. The team moves the alias back to 2026.12.1 in a minute, then adds 25 Hindi cases to the golden set, which reveal the problem. The fixed version ships the next day.

| Event | Before versioning | After versioning |
| --- | --- | --- |
| Complaint spike | Nobody knew what changed | Traces pointed to release 2026.12.2 |
| Rollback | Hours of guesswork | Alias moved back in a minute |
| Root cause | Unknown | 25 new Hindi golden cases revealed it |
| Fix shipped | Unclear | The next day, through CI |

## Common mistakes

- **Prompts edited in production dashboards without review.** Changes become invisible.
- **Floating model aliases.** The provider updates the model and your behaviour changes without notice.
- **Versions not in traces.** You cannot link a quality change to a release.
- **No golden-set gate.** Prompt changes are code changes; test them.
- **Ignoring deprecation dates.** A forced last-minute switch is a risky release.
- **Changing several parts in one release.** When quality drops, you cannot tell which part caused it.
- **No owner per prompt.** Someone must approve each change and answer for its effect.
- **Editing a prompt file in place** instead of adding a new version.
- **Model aliases that change silently** under a fixed name.
- **No retirement calendar**, so a deprecation becomes an emergency.

## When lighter versioning is fine

- **A prototype** with one prompt: keep it in Git and note the model you used.
- **Personal tools** where nobody else depends on consistent behaviour.
- **Fixed batch jobs run once**, where recording the prompt and model in the output is enough.

## From demo to production

- **Pin every part in one release file**, and log the release id and fingerprint on every trace.
- **Run the golden set** on every release change in CI.
- **Track model retirement dates** and test replacements early.
- **Keep a changelog** with eval results and approvals.
- **Roll back by redeploying** the previous release.
