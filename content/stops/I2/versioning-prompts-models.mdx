## What it is

An AI system's behaviour depends on more than its code:

- the **prompts**: system prompts, templates, few-shot examples;
- the **model**: the exact model id;
- **settings** such as maximum tokens;
- the **tool definitions**: names, descriptions and input schemas;
- the **retrieval setup**: index version, chunk size, top-k, reranker;
- the **SDK and API version** used to call the provider.

Change any one and the answers change, even if no application code moved. **Versioning** means each part has an identifier, every change is reviewed and tested, the live combination (a **release**) is recorded with every request, and any earlier release can be restored with one action.

```flow
title: How one release reaches production
Pull request | edits a prompt, model id, setting, tool or index -> CI checks | files exist, model approved, prompts render
CI checks -> Golden set | three runs, compared with the current release
Golden set -[within the measured noise]-> Canary | 5% of users, chosen by user id
Canary -[feedback per release holds up]-> Production
Production -[rollback: redeploy the previous tag]-> Previous release
```

Versioning answers one question: "What exactly produced this answer?" Without it, a team can only guess, usually during an incident or audit.

This lesson follows a Gurugram fintech's support assistant, whose prompts three teams used to edit directly in production.

## How it works

### Prompts as files or in a registry

**Files in the repository.** Each prompt is a file such as `prompts/answer.v14.md`. A change is a new file plus a pull request, so review and history come free. This suits teams where engineers make most changes.

**A prompt registry.** Tools such as MLflow's prompt registry and Langfuse store named prompts. Every save creates a new numbered version; old versions stay unchanged. A movable name points at one version: MLflow calls it an **alias** and Langfuse calls it a **label**, for example `production`. The app asks for the prompt by that name, so promotion and rollback are one call, with no code release. This suits teams where operations staff edit prompts, provided their changes pass the same tests.

Two registry gotchas, checked on MLflow 3.18:

- **Log the version you actually loaded, not the alias.** A trace that says only "production" means nothing once the alias moves. The loaded prompt carries its version number; log that.
- **Aliases are cached.** Each running app keeps an alias lookup for 60 seconds by default. In our test, a second process still served the old version until the minute was up, so a rollback takes up to a minute to reach every server.

### Templates and render tests

Most prompts are **templates**: text with named slots filled at run time, such as `{{ policy }}`. A typo in a slot name is a silent bug: the model receives the literal text `{{ polcy }}` and does its best. So render every template in CI with sample values, and fail on any slot that is missing or any value that is unused. One more trap: Python's `str.format` treats every brace as a slot, so a JSON example inside a prompt breaks it.

### Pin an exact model id

An **exact model id** always points at the same model. An **alias** is a convenience name the provider can move to a newer model, so your behaviour can change with no change on your side, and you cannot reproduce old answers.

Naming differs by provider, so check which kind you are calling. For example, as of November 2026, Anthropic's ids from the 4.6 generation onward, such as `claude-sonnet-5-5`, have no date but each one is a fixed snapshot. For older models, the dated id `claude-sonnet-4-5-20250929` is the snapshot, and the shorter `claude-sonnet-4-5` is an alias for it. So do not test for a date pattern. Keep a short list of the exact ids your team has tested and approved, and allow only those.

Pinning has limits. Anthropic's documentation says the serving system around a model (routing, safety classifiers, sampling) can change under a fixed id and shift behaviour slightly. So also run the golden set on a schedule, for example nightly.

Pin the **SDK** too. Anthropic's SDKs send the API version that was current when the SDK's major version came out, so an SDK upgrade can change API behaviour. For example, API version `2026-10-21` removed `temperature`, `top_p` and `top_k`; requests that set them get an error. Keep the SDK in your lock file and treat a major upgrade as a release.

If your gateway offers its own names (for example `chat-default`), its configuration is part of the release: change it only by reviewed pull request.

### One release file, one fingerprint

Bundle every part into one file in the repository:

```text
prompts/
  answer.v14.md
  rewrite.v4.md
tools/
  tools.v7.json
models.yaml
release.yaml
```

```yaml
# release.yaml
release: assistant-2026.11.3
model: claude-sonnet-5-5          # an exact model id from models.yaml, never an alias
settings: {max_tokens: 600}
prompts: {answer: v14, rewrite: v4}
tools: v7                          # tools/tools.v7.json
index: policies-2026-11-01
```

At start-up the app computes a **fingerprint**: a short hash of everything the release pins, including the text of each prompt file and the tool schemas. Names alone are not enough: the most common untracked change is someone editing `answer.v14.md` in place.

```python
import hashlib, json, re
from pathlib import Path
import yaml

VAR = re.compile(r"\{\{\s*(\w+)\s*\}\}")

def render(template, **values):
    names = set(VAR.findall(template))
    missing, unused = names - values.keys(), values.keys() - names
    if missing or unused:
        raise ValueError(f"missing {sorted(missing)}, unused {sorted(unused)}")
    return VAR.sub(lambda m: str(values[m.group(1)]), template)

def sha(text):
    return hashlib.sha256(text.encode()).hexdigest()

def load_release(path="release.yaml"):
    rel = yaml.safe_load(Path(path).read_text())
    rel["prompt_text"] = {name: Path(f"prompts/{name}.{ver}.md").read_text()
                          for name, ver in rel["prompts"].items()}
    tools_text = Path(f"tools/tools.{rel['tools']}.json").read_text()
    pinned = {k: rel[k] for k in ("model", "settings", "prompts", "tools", "index")}
    pinned["prompt_sha"] = {n: sha(t) for n, t in rel["prompt_text"].items()}
    pinned["tools_sha"] = sha(tools_text)
    rel["fingerprint"] = sha(json.dumps(pinned, sort_keys=True))[:12]
    return rel

# At app start-up: RELEASE = load_release(), then log RELEASE["release"]
# and RELEASE["fingerprint"] on every trace and audit event.
```

Save this as `release.py`. One release id with two fingerprints means someone changed a file without making a new release.

What each part of a release looks like:

| What to version | How | Typical change | What can go wrong |
| --- | --- | --- | --- |
| Prompts | Files in Git or registry versions | Wording, rules, examples | Edited in place, never tested |
| Model | Exact id from an allow-list | Upgrade or forced retirement | Alias moves silently |
| Settings | `release.yaml` | Max tokens | New model rejects a setting |
| Tool schemas | Versioned JSON files | New or renamed parameter | Prompts describe the old schema |
| Retrieval | Index name and config in Git | Chunk size, top-k, reranker | Rebuilt in place, old index lost |
| SDK and API version | Lock file | Major SDK upgrade | API behaviour changes |

### Checks in CI

A second script, `check_release.py`, fails the build when the release points to something missing, unapproved or about to retire. `models.yaml` is the allow-list of exact ids with announced retirement dates:

```yaml
# models.yaml: exact ids we have tested, with the provider's retirement date (null if none announced)
claude-sonnet-5-5: null
claude-sonnet-4-5-20250929: 2026-11-30
```

```python
from datetime import date
from pathlib import Path
import yaml
from release import VAR, render

SAMPLE = {"company": "Test Co", "policy": "Refunds within 7 days.", "question": "Can I get a refund?"}

def check_release(path="release.yaml"):
    rel = yaml.safe_load(Path(path).read_text())
    approved = yaml.safe_load(Path("models.yaml").read_text())
    problems = []
    if rel["model"] not in approved:
        problems.append(f"{rel['model']} is not an approved, exact model id")
    elif approved[rel["model"]] and (approved[rel["model"]] - date.today()).days < 60:
        problems.append(f"{rel['model']} retires on {approved[rel['model']]}; plan the switch")
    if not Path(f"tools/tools.{rel['tools']}.json").exists():
        problems.append(f"missing tools file tools.{rel['tools']}.json")
    for name, ver in rel["prompts"].items():
        file = Path(f"prompts/{name}.{ver}.md")
        if not file.exists():
            problems.append(f"missing prompt file {file.name}")
            continue
        template = file.read_text()
        needed = {k: v for k, v in SAMPLE.items() if k in VAR.findall(template)}
        try:
            render(template, **needed)
        except ValueError as e:
            problems.append(f"{file.name} does not render: {e}")
    return problems

if __name__ == "__main__":
    problems = check_release()
    print("\n".join(problems) or "release OK")
    raise SystemExit(1 if problems else 0)
```

We ran both scripts: the files above print `release OK`. The alias `claude-sonnet-4-5` is reported as unapproved, the dated Sonnet 4.5 id is flagged as retiring on 30 November 2026, and a slot misspelled as `{{ polcy }}` fails the render check.

Why 60 days? As of November 2026, Anthropic's model deprecations page promises at least 60 days' notice before it retires a publicly released model, and requests to a retired model fail. Other providers and cloud platforms set their own schedules, so copy each provider's dates into `models.yaml`. A retirement then becomes a planned release, not an emergency.

### Tool schemas are an interface

The model reads tool definitions as instructions, so treat them like a public API. Adding an optional parameter is usually safe. Renaming or removing one, or changing what a value means, is a **breaking change**: prompts and examples that mention the old name now teach the wrong call. Ship it as a new tools version, update those prompts in the same release, and keep the old handler until you can no longer roll back to the old release.

### Gates that are not noise

Every change runs the golden set (your fixed test set of real questions with checked answers) and is compared with the current release on quality, cost and latency. But model outputs vary from run to run. For some current models, such as Anthropic's from Claude 4.7 on, you cannot change temperature from its default, and older versions of Anthropic's SDK noted that even temperature 0 is not fully deterministic.

So measure the noise before trusting a drop (see the regression tests lesson). Run the unchanged release three to five times and set the overall tolerance just above the spread. Allow no drop on critical categories, such as refund rules or refusals, and give them enough cases that one failure shows.

The arithmetic matters. On a 120-case set, one case is 0.83 points. Even if the model never varied, 120 cases measure quality only roughly: at about 85% correct, the standard error is about 3.3 points, and run-to-run randomness adds to that. A gate that blocks "a drop of more than one point" blocks good releases at random and teaches the team to ignore it. Small sets catch big breaks; small gains need many more cases (see the evals lesson).

### Change one thing at a time

If one release changes the prompt, the model and the index and quality drops, nobody can say which change did it. Ship them separately where you can. When parts must move together, such as a model switch that needs prompt changes, run the golden set on each step in staging. For a **model switch**, also compare cost and latency and read sample conversations in every language you serve: prompts tuned for one model often need small changes for the next.

### Roll out gradually, roll back in one step

A golden set is only a sample of real use. So send a small share of users to a new release first: a **canary**. Hash each user's id to a number from 0 to 99 and give users below, for example, 5 the new release, so each user stays on one version (as in the serving lesson). With the release id on every trace, compare thumbs-down rates and escalations per release, and raise the share only if they hold up.

Production reads `release.yaml` from the deployed commit, and each release is a Git tag. Promoting is merging and deploying; rolling back is redeploying the previous tag (or, with a registry, moving the alias back). Either way it is one action, rehearsed before you need it.

### Keep what the audit trail points to

A release id in an audit event is useful only while you can still look up what it means. Regulated clients, such as lenders and insurers, keep audit events for years under their compliance rules (see the audit logs lesson). So never delete the Git tags, prompt texts or registry versions that an audit event still references.

Keep a short `CHANGELOG.md` too: release id, date, what changed, eval results against the previous release, and who approved it.

## A worked example

The Gurugram fintech's support assistant had prompts edited directly in an admin panel by three teams. One Friday, complaints doubled. Nobody could say what had changed, because traces showed only the model name.

The fix:

- Prompts moved into the repository as files. A `CODEOWNERS` file names an owner for each prompt, and branch rules require that owner's review.
- `release.yaml` pins the exact model id, settings, prompt versions, tools version and index name. Each release is a Git tag.
- Every trace and audit event records the release id and its fingerprint.
- CI runs `check_release.py`, then the 120-case golden set three times.
- New releases go to a 5% canary for two days before full rollout.

To set the gate, the team ran the unchanged release five times. For example, suppose the scores ranged from 83.3% to 86.7%, a spread of about 3 points. So CI blocks a candidate whose average over three runs is more than 4 points below the current release's. On the 20 refund-dispute cases, the critical category, they allowed no new failures: a case counts as failed if it fails in two of three runs.

Two months later, release 2026.12.2 shortens answers with a new prompt, `answer.v15`. It passes the golden set (for example, 85.6% against 85.3%) and goes to the canary. Within a day the per-release dashboard shows a jump in thumbs-down ratings in Hindi conversations, for example from 4% to 9%, while English is flat. The team sets the canary share to zero, so 95% of users never saw the problem.

The golden set had no Hindi cases. The team took 25 failing Hindi conversations from the canary traces, masked personal details, and had a support lead write the correct answers. With those cases added, `answer.v15` fails clearly: the shorter answers drop the policy line Hindi users relied on. `answer.v16` fixes it and ships two days later, through CI and a new canary.

| Event | Before versioning | After versioning |
| --- | --- | --- |
| Finding the cause | Nobody knew what changed | Feedback per release pointed to 2026.12.2 |
| Reach of the bad release | Every user | 5% canary, for one day |
| Undo | Hours of guesswork in the panel | Canary share set to zero |
| Root cause | Unknown | 25 new Hindi golden cases showed it |
| Fix | Unclear | `answer.v16`, through CI and canary |

## Common mistakes

- **Prompts edited in a dashboard without review**, invisible to traces and tests.
- **Calling a model alias and assuming it is pinned**, or checking ids with a date pattern. Allow only exact ids from a list.
- **Editing a prompt file in place**, with a fingerprint that hashes only names.
- **Logging the alias instead of the resolved version.** After the alias moves, the old traces mean nothing.
- **A gate tighter than the noise.** It blocks good releases at random until people bypass it.
- **A golden set that misses a language or customer group** you serve. Your gate cannot see failures it has no cases for.
- **Changing several parts in one release**, so nobody can tell which one broke quality.
- **Renaming a tool parameter** without updating the prompts and examples that describe it.
- **Upgrading the SDK** as routine maintenance, or **ignoring retirement dates** until requests fail.
- **Deleting old releases** that audit events still point to.

## When lighter versioning is fine

- **A prototype** with one prompt: keep it in Git and write down the exact model id you used.
- **Personal tools** where nobody else depends on consistent behaviour.
- **One-off batch jobs**: save the prompt and model id with the output.

## From demo to production

- **One release file and fingerprint**, logged on every trace and audit event.
- **CI checks and noise-based gates** on every change, with zero tolerance on critical categories.
- **A canary for every release**, and old releases kept as long as the audit log.

## Practice

Read MLflow's prompt registry docs, then do this on your own app or a small sample.

1. Move your app's prompts into versioned files or a registry (logging the resolved version, not the alias).
2. Write `release.yaml` and `models.yaml`, and log the release id and fingerprint on every trace.
3. Edit a prompt file in place and confirm the fingerprint changes.
4. Run your golden set five times on the unchanged release, note the spread, and set your gate just above it.
5. Add `check_release.py` to CI. Then point `release.yaml` at a prompt version that does not exist, then at a model alias, and confirm the build fails both times.
6. Promote a prompt change to a canary, then roll it back with one action and time it.

**You are done when you can** answer "what exactly produced this answer?" for any past request, and roll back in under five minutes.
