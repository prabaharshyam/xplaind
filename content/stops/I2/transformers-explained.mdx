## What it is

A **transformer** is a neural network architecture, introduced in 2017, built around a mechanism called **attention**. It processes a sequence (words, image patches, audio frames). In every layer, each position decides how much to draw from the other positions.

Three families use it:

- **Decoder-only** models generate text one token at a time. Today's open chat and coding models, such as the Llama family, are built this way.
- **Encoder-only** models read the whole text at once and produce representations: classifiers, and many embedding models for search. Some newer embedding models, such as Qwen3-Embedding (June 2025), are built from decoder models instead.
- **Encoder-decoder** models read one sequence and write another: translation and summarisation.

Vision transformers cut an image into patches and treat each patch like a token.

The table shows attention from the word "it" in one head. The numbers are illustrative, not from a real model.

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| Encoder (sees both sides) | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |
| Decoder (sees only the past) | 0.03 | **0.45** | 0.06 | 0.02 | 0.36 | 0.03 | 0.05 | 0 | 0 | 0 |

The encoder can see "trusted", which tells it that "it" is the bank (a loan cannot trust anyone). The decoder cannot see later words, so at "it" the choice between "bank" and "loan" is still open. Later tokens such as "trusted" look back and settle it. Each row adds up to 1.

## How it works

### Tokens and embeddings

A **tokenizer** splits text into tokens: whole words, pieces of words or single bytes. Many chat-model tokenizers use byte-pair encoding: start from bytes and repeatedly merge the most common neighbouring pairs into new tokens. Each token id then selects a row from a learned table, giving a vector (an **embedding**). Llama 3 8B, for example, has a vocabulary of 128,256 tokens and vectors 4,096 numbers wide.

Tokenizers learn their merges from their training text, so languages that were rare in that text split into more pieces. We counted one sentence with OpenAI's older `cl100k_base` and newer `o200k_base` tokenizers (November 2026):

| Sentence | cl100k_base | o200k_base |
| --- | --- | --- |
| The bank approved the loan. | 6 | 6 |
| Bank ne loan approve kar diya. | 8 | 7 |
| बैंक ने लोन मंज़ूर कर दिया। | 31 | 11 |

The Hindi sentence still needs almost twice as many tokens as the English one, even with the newer tokenizer. More tokens means a higher bill, slower replies and less room in the context. The lesson on AI in Indian languages goes deeper.

### Position

Attention by itself ignores order: shuffle the words and each token gets the same mix. So the model needs position information. The 2017 transformer and BERT **added** a position vector to each embedding. BERT learned 512 of them, which is why it cannot read past 512 tokens.

Llama-family models and ModernBERT use **rotary position embeddings (RoPE)** instead. Inside each attention layer, every query and key is rotated by an angle that depends on its position. The score between two tokens then depends on how far apart they are. With some extra training, rotary embeddings can be stretched to contexts longer than the model first saw, which is one way context windows have grown.

### Attention

Each token computes three vectors from its embedding, using three learned matrices:

- a **query**: what am I looking for?
- a **key**: what can I be matched on?
- a **value**: what do I pass on if chosen?

The model takes the dot product of a token's query with every key. A large dot product means "relevant". It divides the scores by the square root of the key size, because dot products grow with vector size and very large scores make softmax pick one token and stop learning. A **softmax** turns the scores into weights that add up to 1. The output is the weighted sum of the values: a new vector for the token that blends in what it attended to.

In a decoder, a **causal mask** sets the scores for future tokens to minus infinity before softmax, so their weights become exactly 0. Without it, during training each position could see the very token it is asked to predict.

One head, with the mask, in NumPy:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                  # relevance of every token to every other
    if causal:                                     # hide future tokens
        future = np.triu(np.ones_like(scores), k=1) == 1
        scores = np.where(future, -np.inf, scores)
    weights = softmax(scores)                      # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "because", "she"]
x = rng.normal(size=(len(tokens), 16))             # one 16-number vector per token
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(out.shape)                                   # (6, 8): one new vector per token
print(np.round(w, 2))                              # zeros above the diagonal
```

The first row is `[1, 0, 0, 0, 0, 0]`: "Priya" can only attend to itself. The weights here are random. In a trained model, the row for "she" would put high weight on "Priya".

### Multi-head attention and the layer

Several heads run side by side, each with its own query, key and value matrices, so each can learn a different relationship. With a width of 768 and 12 heads, each head works on 64 numbers; the outputs are joined back to 768 and mixed by one more matrix. PyTorch has this built in:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                      # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)   # True = hidden
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                    # (2, 10, 768) and (2, 10, 10)
```

A layer is attention followed by a **feed-forward** network that works on each token separately. Shortcut connections add each block's input back to its output, so deep stacks stay trainable. The 2017 model normalised after each block; Llama-style models normalise before each block (with RMSNorm), which trains more stably. Large models stack dozens of these layers.

```flow
dir: TB
title: One decoder layer in the Llama style, repeated in every layer
Token vectors -> Normalise
Normalise -> Masked multi-head attention | rotary positions applied to queries and keys
Masked multi-head attention -> Add the input back
Add the input back -> Normalise again
Normalise again -> Feed-forward | gated, about 3.5 times wider
Feed-forward -> Add back again
Add back again -> Next layer
```

### Generation, the KV cache and sampling

A decoder turns the last position's vector into a score for every token in its vocabulary, then picks one. **Temperature** divides the scores before softmax: below 1 makes the choice safer, above 1 more varied. **Top-p** keeps only the most likely tokens whose probabilities add up to p (for example 0.9) and samples from those. The chosen token is appended and the loop repeats.

Recomputing keys and values for the whole text at every step would waste work, so the model stores them: the **KV cache**. Each new token computes only its own query, key and value and attends to the cache. This makes generation fast, but the cache grows with every token and every user.

### Three costs of a long context

| Cost | Grows with | What it means for you |
| --- | --- | --- |
| API bill | Tokens, linearly | Every extra token in the prompt is paid for, on every call |
| KV cache memory | Tokens times users | Long chats and many users fill GPU memory |
| Attention compute | Square of the length | Matters only once the context is long |

For a Llama 3 8B shape, each new token does about 218 million multiply-adds per layer in the weight matrices, and about 8,000 more for each earlier token it attends to (rough arithmetic from the config). At 2,000 tokens attention is under a tenth of the work; it catches up only near 27,000 tokens. Over a whole sequence, attention work grows with the square: 8,000 tokens take about 64 times the attention work of 1,000. **FlashAttention** computes the same exact result with far fewer trips to slow GPU memory, so it is faster, but the number of comparisons stays the same.

### Modern variations: reading a 2026 model card

| Idea | What it changes | Where it shows in a config |
| --- | --- | --- |
| Rotary positions | Position enters inside attention; contexts can be stretched | `rope_theta`, `rope_scaling` |
| Grouped-query attention | Groups of query heads share one key-value head: smaller KV cache, little quality loss | `num_key_value_heads` below `num_attention_heads` |
| Gated feed-forward | Three matrices instead of two | `intermediate_size`, `hidden_act` |
| Mixture of experts | Many feed-forward "experts"; a router sends each token to a few | `num_local_experts`, `num_experts_per_tok` |
| Local attention | Some layers attend only to nearby tokens, cutting long-input cost | sliding-window settings |

Mixture of experts separates two numbers. **Total** parameters must all sit in memory; **active** parameters set the compute per token. Mixtral 8x7B has 46.7 billion total and uses 12.9 billion per token; DeepSeek-V3 has 671 billion total and 37 billion active. Read both numbers before you size hardware.

### Where the parameters are

```python
def params(width, layers, vocab, ffn, heads, kv_heads, gated=True, tied=False):
    head = width // heads
    attn = 2 * width * width + 2 * width * kv_heads * head   # Q and output, then K and V
    ff = (3 if gated else 2) * width * ffn                     # gated layers use 3 matrices
    emb = vocab * width * (1 if tied else 2)                   # input table, output layer
    return layers * (attn + ff) + emb

# Llama 3 8B, from its published config
print(params(width=4096, layers=32, vocab=128_256, ffn=14_336, heads=32, kv_heads=8) / 1e9)
# about 8.03, matching the published 8B size
```

About four fifths of each layer's weights are in the feed-forward block, not in attention. At 2 bytes per number (16-bit), 8 billion parameters need about 16 GB of GPU memory before any KV cache.

### Pre-training and adaptation

Models are pre-trained on huge amounts of text to predict the next token (decoders) or hidden tokens (encoders). Grammar, facts and patterns of reasoning all help prediction, so the model learns them. Chat models are then shaped by instruction tuning and preference training. For your own tasks you can fine-tune, or use the model as it is with prompts and retrieval.

Transformers won because attention links distant tokens directly and all positions train in parallel on GPUs, which allowed scaling to very large models and datasets.

## A worked example

A Chennai legal-tech startup has three jobs on Indian court judgments.

**1. Classify by area of law** (property, family, criminal, tax, labour). They have 12,000 labelled judgment summaries. A small fine-tuned encoder is the obvious choice: cheap, fast and able to use the labels. Suppose their test set shows 91% accuracy against 82% for a gradient-boosted model on keyword counts (illustrative numbers). The gain comes from context: "the appellant's claim to ancestral property" means property law even when the word "property" is missing.

Full judgments run past the 512-token limit of their BERT-style encoder. That limit comes from the 512 learned position vectors it was trained with, not from attention cost. They have two options:

- Split each judgment into chunks, classify each and combine the votes.
- Use a long-context encoder such as ModernBERT, which reads 8,192 tokens. Its model card warns that the full window is slower than short inputs, so they test speed too.

**2. Semantic search.** An embedding model turns every paragraph into a vector once; queries are matched by vector search.

**3. Summaries.** For privacy they consider self-hosting an 8B open model on one GPU. They size it from the config before buying anything:

```python
def kv_cache_gb(tokens, layers=32, kv_heads=8, head_dim=128, bytes_per_number=2, users=1):
    per_token = 2 * layers * kv_heads * head_dim * bytes_per_number   # one key and one value
    return per_token * tokens * users / 1e9

print(kv_cache_gb(1))                     # 0.000131 GB, about 0.13 MB per token
print(kv_cache_gb(6_500, users=10))       # 8.5 GB for 10 judgments at once
print(kv_cache_gb(6_500, users=10, kv_heads=32))   # 34 GB without grouped-query attention
```

| Item | Memory |
| --- | --- |
| Weights, 8 billion at 2 bytes | About 16 GB |
| KV cache, 10 judgments of 6,000 tokens plus 500 for the summary | About 8.5 GB |
| Total before runtime overhead | About 25 GB |

A 24 GB GPU has no headroom at 10 at a time once runtime overhead is added; a 40 or 48 GB GPU leaves room, or they process 5 at a time. Grouped-query attention is what makes this fit: with one key-value head per query head the cache would be four times larger.

## Common mistakes

- **Treating every transformer as a chatbot.** Encoders, decoders and encoder-decoders suit different jobs; a small encoder often beats a large chat model on classification.
- **Sizing hardware from the weights alone.** The KV cache grows with context length and users; long contexts and many users can need more memory than the weights.
- **Confusing the 512-token encoder limit with attention cost.** It comes from the position table the model was trained with.
- **Reading attention maps as explanations.** Attention weights show where information flowed in one head, not why the model decided.
- **Using the wrong chat template or tokenizer.** A model fine-tuned with one template behaves worse with another; use the exact one documented.
- **Quoting the total parameters of a mixture-of-experts model as its speed.** Memory follows total parameters; compute per token follows active ones.
- **Forgetting tokenisation.** Hindi or Tamil text can need several times the tokens of English, changing cost, speed and context room.

## When you do not need transformer internals

- **Using models through an API**: prompts, retrieval and evals matter more day to day.
- **Tabular prediction**, where boosted trees are usually the better tool.
- **Simple text tasks** that a keyword rule or a small classifier already handles well.

Knowing the internals pays off when choosing models, sizing GPUs, debugging long-context behaviour or fine-tuning.

## From demo to production

- **Estimate memory before you buy hardware**: weights plus the KV cache at your real context length and number of users.
- **Keep prompts no longer than needed**: every token is billed, cached and attended to.
- **Use the model's own tokenizer and chat template** exactly as documented.
- **Benchmark long-context accuracy** on your own documents, not only the advertised window.
- **Count tokens per language** for the languages your users write in.
- **Record the model, version and config** with every deployment.
