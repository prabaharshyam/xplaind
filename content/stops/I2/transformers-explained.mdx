## What it is

A **transformer** is a neural network architecture, introduced in 2017, built around a mechanism called **attention**. It processes a sequence (words, image patches, audio frames) and lets every position look at every other position to decide what matters.

Three families use it:

- **Decoder-only** models generate text one token at a time: today's chat and coding models.
- **Encoder-only** models read text and produce representations: many embedding models for search, and classifiers. (Some recent embedding models are adapted from decoder-only models.)
- **Encoder-decoder** models map one sequence to another: translation and summarisation.

Vision transformers split images into patches and treat them like tokens.

| Token | The | bank | approved | the | loan | because | it | trusted | the | applicant |
|---|---|---|---|---|---|---|---|---|---|---|
| Attention from "it" | 0.02 | **0.61** | 0.05 | 0.01 | 0.18 | 0.02 | 0.04 | 0.03 | 0.01 | 0.03 |

In "The bank approved the loan because it trusted the applicant", the token "it" sends a query, compares it with every key, and mostly takes its meaning from "bank".


## How it works

**Tokens and embeddings.** Text is split into tokens; each token becomes a vector (an embedding). Positional information is added so the model knows the order.

**Attention.** For each token, the model computes three vectors: a query (what am I looking for?), a key (what do I contain?) and a value (what do I pass on?). It compares the query with every key to get attention weights, then takes a weighted mix of the values. In "The bank approved the loan because it trusted the applicant", attention helps "it" focus on "the bank".

**Multi-head attention.** Several attention heads run in parallel, each free to learn different relationships (grammar, references, topics).

**Layers.** Each transformer layer has attention followed by a small feed-forward network, with shortcuts and normalisation that make deep stacks trainable. Large models stack dozens of layers.

**Generation.** A decoder-only model predicts a probability for every possible next token, picks one (sampling), appends it, and repeats. A mask stops each position from seeing future tokens during training.

**Cost.** Attention compares every token with every other, so cost grows quickly with sequence length. This is why context windows have limits and long prompts are slower and pricier. Engineering tricks (efficient attention kernels, caching keys and values) reduce the cost.

**Pre-training and adaptation.** Models are pre-trained on huge data to predict missing or next tokens, then adapted: instruction tuning and preference training for chat models, fine-tuning for specific tasks, or used as they are with prompts and retrieval.

**Why it won.** Attention handles long-range relationships well and trains efficiently in parallel on GPUs, which allowed scaling to very large models and datasets.

**The three families side by side:**

| Family | Reads | Produces | Typical uses |
| --- | --- | --- | --- |
| Encoder-only | The whole input at once | A vector per token or per text | Classification, embeddings, search |
| Decoder-only | Left to right, no peeking ahead | The next token, repeatedly | Chat, coding, drafting, reasoning |
| Encoder-decoder | Input fully, then generates | A new sequence | Translation, summarisation |

**Attention in plain arithmetic.** For one token, take the dot product of its query with each token's key. Large dot products mean "relevant". Divide the scores by the square root of the vector size to keep them in a stable range, then turn them into weights that add up to 1 with a softmax. Multiply each token's value by its weight and add them up. The result is a new vector for the token that blends in information from the tokens it attended to. Every head does this with its own learned queries, keys and values, and the results are joined.

**What pre-training teaches.** By predicting the next or missing token across enormous amounts of text, a model learns grammar, facts, styles and patterns of reasoning, because all of them help prediction. Instruction tuning and preference training then shape that raw ability into a helpful assistant that follows requests.

**Attention in a few lines of NumPy.** One head, a causal mask, and the weights printed so you can see who attends to whom:

```python
import numpy as np

def softmax(z, axis=-1):
    z = z - z.max(axis=axis, keepdims=True)
    e = np.exp(z)
    return e / e.sum(axis=axis, keepdims=True)

def attention(Q, K, V, causal=True):
    d = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d)                       # how relevant each token is to each other
    if causal:
        scores = np.where(np.triu(np.ones_like(scores), k=1) == 1, -np.inf, scores)
    weights = softmax(scores)                           # each row sums to 1
    return weights @ V, weights

rng = np.random.default_rng(0)
tokens = ["Priya", "paid", "the", "bill", "she"]
x = rng.normal(size=(len(tokens), 16))                  # token embeddings plus position
Wq, Wk, Wv = (rng.normal(0, 0.3, (16, 8)) for _ in range(3))
out, w = attention(x @ Wq, x @ Wk, x @ Wv)
print(np.round(w, 2))                                   # upper triangle is 0: no peeking ahead
```

In a trained model, the row for "she" would put high weight on "Priya". Here the weights are random, but the shapes and the mask are exactly what real models compute, for every head in every layer.

**Multi-head shapes.** With a model width of 768 and 12 heads, each head works on 64 dimensions; their outputs are joined back to 768 and mixed by one more matrix. The same idea in PyTorch:

```python
import torch
mha = torch.nn.MultiheadAttention(embed_dim=768, num_heads=12, batch_first=True)
seq = torch.randn(2, 10, 768)                           # batch of 2, 10 tokens each
mask = torch.triu(torch.ones(10, 10, dtype=torch.bool), diagonal=1)
out, weights = mha(seq, seq, seq, attn_mask=mask)
print(out.shape, weights.shape)                         # (2, 10, 768) and (2, 10, 10)
```

**Where the parameters are.** In each layer, attention has four matrices of width × width (queries, keys, values, output); the feed-forward block usually expands to about four times the width and back, which is about twice as many weights again:

```python
def layer_params(width, ff_mult=4):
    attn = 4 * width * width
    ff = 2 * width * (ff_mult * width)
    return attn + ff

w, layers, vocab = 4096, 32, 128_000
total = layers * layer_params(w) + vocab * w
print(f"about {total / 1e9:.1f} billion parameters")    # about 7 billion: the 7B to 8B range
```

Real models differ in details (grouped key-value heads, gated feed-forward layers), but the estimate lands in the right range.

**Why long inputs cost more.** Attention compares every token with every earlier one, so the work grows with the square of the length: 8,000 tokens take about 64 times the attention work of 1,000. Generation also keeps a cache of keys and values for every earlier token, which is why long contexts need lots of GPU memory.

## A worked example

A Chennai legal-tech startup classifies Indian court judgments by area of law (property, family, criminal, tax, labour) and also wants semantic search over them.

- **Classification**: they fine-tune a small encoder-only transformer on 12,000 labelled judgment summaries. It reaches 91% accuracy against 82% for a gradient-boosted model on keyword features, because attention captures context such as "the appellant's claim to ancestral property".
- **Search**: they use an embedding model (encoder) to embed paragraphs and retrieve similar passages.
- **Summaries**: they use a decoder-only language model through an API, with retrieved passages in the prompt.

When judgments exceed the encoder's 512-token limit, they classify the first and most relevant sections rather than the whole text, a direct consequence of attention's cost with length.

| Task | Model type | Result |
| --- | --- | --- |
| Area-of-law classification | Fine-tuned small encoder | 91% against 82% for keyword features |
| Similar-passage search | Encoder embedding model | Semantic matches across judgments |
| Summaries | Decoder-only model through an API | Cited summaries from retrieved passages |
| Long judgments | Encoder with a 512-token limit | Classify the most relevant sections |

## Common mistakes

- **Treating all transformers as chatbots.** Encoders, decoders and encoder-decoders suit different jobs.
- **Ignoring sequence limits.** Long inputs are truncated or expensive.
- **Fine-tuning a huge model when a small encoder would do.** Match model size to task.
- **Assuming attention weights are explanations.** They are not reliable explanations of decisions.
- **Forgetting tokenisation.** Indian languages often use more tokens per word, affecting limits and cost.
- **Thinking attention "understands" by itself**: it is weighted averaging; meaning comes from training.
- **Ignoring the quadratic cost** of long inputs when designing prompts and context.

## When you do not need transformer internals

- **Using models through an API**: prompts, retrieval and evals matter more day to day.
- **Tabular prediction**, where boosted trees are usually the better tool.
- **Simple text tasks** that a keyword rule or a small classifier already handles well.

Knowing the internals pays off when choosing models, sizing hardware, debugging long-context behaviour or fine-tuning.

## From demo to production

- **Estimate memory and cost from the architecture** (layers, width, heads, context) before choosing hardware.
- **Keep prompts and contexts no longer than needed**, given the quadratic attention cost.
- **Use the model's own tokenizer and chat template** exactly as documented.
- **Benchmark long-context accuracy** on your own documents, not only the advertised window.
- **Record model architecture and version** with every deployment.
