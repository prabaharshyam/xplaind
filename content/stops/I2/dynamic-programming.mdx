## What it is

**Recursion** is when a function solves a problem by calling itself on a smaller version of it, until it reaches a **base case** small enough to answer directly. Counting files in a folder is naturally recursive: count the files here, then ask the same question of each sub-folder.

**Dynamic programming** (DP) is what you do when a recursion keeps solving the same smaller problems again and again. Instead of recomputing them, you solve each one once and reuse the answer, either by caching results (**memoization**) or by filling a table from the smallest case upwards (**tabulation**).

```text
 fib(5) by plain recursion: the same calls repeat
                    fib(5)
                 /          \
            fib(4)          fib(3)   ← computed again
           /     \          /    \
       fib(3)   fib(2)   fib(2) fib(1)
       /   \
   fib(2) fib(1)       15 calls for fib(5); about 2.7 crore for fib(35)

 with memoization: each value once
 fib(0) fib(1) fib(2) fib(3) fib(4) fib(5)  → 6 values, then lookups
```

## How it works

A problem suits DP when it has two properties. **Optimal substructure**: the best answer is built from best answers to smaller problems. **Overlapping subproblems**: the same smaller problems come up many times.

A reliable method has five steps:

1. **Define the state**: what single value, or small set of values, identifies a subproblem? For coin change, it is the amount still to make.
2. **Write the recurrence**: how the answer for a state comes from smaller states.
3. **Set the base cases**: the states you can answer directly, such as amount 0 needs 0 coins.
4. **Choose the order**: top-down with memoization, or bottom-up with a table.
5. **Read off the answer** and check the cost: number of states times work per state.

**Top-down memoization** keeps the natural recursive code and adds a cache. In Python, `@functools.lru_cache(maxsize=None)` does it in one line. **Bottom-up tabulation** replaces recursion with a loop that fills an array from the base case upward. It avoids recursion-depth limits and is often a little faster.

| Approach | How it looks | Good for | Watch out for |
|---|---|---|---|
| Plain recursion | function calls itself | small inputs, clarity | exponential time when subproblems repeat |
| Memoization (top-down) | recursion + cache | quick to write from a recurrence | recursion depth; cache memory |
| Tabulation (bottom-up) | loop filling a table | large inputs, predictable speed | must work out the fill order |
| Greedy | pick the best option now | problems with a proven greedy choice | wrong answers when local best is not global best |

**Spotting DP in interviews.** Phrases such as "number of ways", "minimum cost", "maximum value", "longest" or "can you reach" over a sequence or grid often signal DP. Start by writing the plain recursive version and saying its cost out loud; then point out the repeated subproblems and add a cache. Interviewers reward that path from slow to fast more than a memorised table.

## A worked example

Arjun is building a cash-dispensing feature for a payments kiosk in Lucknow. Given an amount, the kiosk should pay it with the fewest coins and notes from 1, 2, 5, 10, 20, 50, 100, 200 and 500.

For Indian denominations, always taking the largest note that fits happens to work. But the product will also run in a canteen that uses tokens of 1, 3 and 4. For 6, greedy takes 4 + 1 + 1 (three tokens), while 3 + 3 is two. So Arjun uses DP.

**State:** the amount `a` still to pay. **Recurrence:** best(a) = 1 + the smallest best(a − c) over every coin c that fits. **Base case:** best(0) = 0.

His first version is plain recursion:

```python
def fewest(a, coins):
    if a == 0:
        return 0
    return 1 + min(fewest(a - c, coins) for c in coins if c <= a)
```

For ₹30 with Indian coins it is fine; for ₹300 it effectively never finishes, because it re-solves the same amounts countless times.

Adding a cache fixes it:

```python
from functools import lru_cache

def fewest_coins(amount, coins):
    @lru_cache(maxsize=None)
    def best(a):
        if a == 0:
            return 0
        return 1 + min(best(a - c) for c in coins if c <= a)
    return best(amount)
```

Now each amount from 0 to the target is solved once: about amount × number of coins steps.

For the kiosk he uses the bottom-up version, which avoids recursion limits on large amounts:

```python
def fewest_coins_table(amount, coins):
    INF = float("inf")
    best = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a and best[a - c] + 1 < best[a]:
                best[a] = best[a - c] + 1
    return best[amount]
```

For ₹3,000 with nine denominations that is 27,000 simple steps, instant on any phone. With tokens of 1, 3 and 4 it correctly returns 2 for an amount of 6.

## Common mistakes

**No base case, or the wrong one.** The recursion never stops or returns nonsense. Write the base case first.

**Choosing a state that is too big.** Including values that do not affect the answer multiplies the number of states. Keep only what the future depends on.

**Caching on mutable arguments.** `lru_cache` needs hashable arguments. Pass tuples, not lists, or keep the list outside the cached function, as above.

**Hitting the recursion limit.** Python stops at about 1,000 nested calls. Switch to bottom-up, or raise the limit carefully, for large inputs.

**Trusting greedy without proof.** Greedy is fast and often right, but you must show it works for the problem. The 1, 3, 4 token example shows how it fails.

**Jumping to code.** Most DP bugs come from an unclear state or recurrence. Write both in a sentence before coding.
