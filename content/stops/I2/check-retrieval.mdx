## What it is

Most wrong answers from a RAG system start with retrieval: the right passage was never found, so the model could not use it. **Checking retrieval** means measuring, with a fixed set of test questions, whether the right passages come back, separately from whether the final answer is good.

```flow
A wrong answer -> Was the right passage in the top k?
Was the right passage in the top k? -[no]-> A retrieval problem | chunking, embeddings, hybrid search, query rewriting, filters
Was the right passage in the top k? -[yes]-> A generation problem | prompt, grounding rules, citations, model choice
```

This lesson follows a bank in Kochi whose staff assistant gave too many wrong answers about its circulars.

## How it works

**Build a test set.** Collect 30 to 100 realistic questions with, for each, the passage or passages that contain the answer. Use real user questions where possible, and include easy, hard, vague and unanswerable ones. Keep the set fixed so you can compare changes fairly.

**Retrieval metrics.**

- **Recall at k**: for what share of questions does at least one correct passage appear in the top k results? Recall at 5 is a common headline number. Strictly, this "at least one" version is also called hit rate; when a question has several correct passages, some tools define recall at k as the share of them found.
- **Precision at k** or **context precision**: of the k passages retrieved, how many are actually relevant? RAGAS's context precision also rewards ranking the relevant ones higher. Low precision fills prompts with noise.
- **MRR** (mean reciprocal rank): rewards putting the right passage near the top.

**Answer metrics**, measured separately:

- **Faithfulness**: are the answer's claims supported by the retrieved passages?
- **Answer correctness**: does it match the expected answer?

Tools such as RAGAS compute these, often using a model as a judge; check a sample by hand.

**Diagnose with the split.** If an answer is wrong:

- right passage *not* retrieved → fix retrieval (chunking, embeddings, hybrid search, query rewriting, filters);
- right passage retrieved but answer wrong → fix generation (prompt, grounding, model).

**Run on every change.** Changing chunk size, the embedding model or top-k can help some questions and hurt others. The fixed set shows the net effect.

**A tiny worked example of the metrics.** Four test questions, top 5 results each; the position of the first correct passage is shown:

| Question | First correct passage at | In top 5? | Reciprocal rank |
| --- | --- | --- | --- |
| Q1 | 1 | yes | 1.0 |
| Q2 | 3 | yes | 0.33 |
| Q3 | not found | no | 0 |
| Q4 | 2 | yes | 0.5 |

Recall at 5 = 3 of 4 = 75%. MRR = (1.0 + 0.33 + 0 + 0.5) ÷ 4, about 0.46.

**Building the test set fast.** Start from real questions in support tickets, search logs or chats. For each, a person who knows the documents finds the answering passage and records its document and section. Thirty questions can be done in an afternoon. Include questions the documents cannot answer, with "none" as the expected passage, so you can check the system says it does not know. Add a new question every time a user reports a wrong answer.

**Using a model as a judge.** Tools such as RAGAS use a model to score faithfulness and relevance at scale. They are useful but not perfect. Score a sample of 20 by hand and compare; if the judge disagrees with people often, fix its instructions before trusting its numbers.

**The metrics in code.** Each test case lists the ids of passages that answer it; the retriever returns ranked ids:

```python
import math

def metrics(cases, retrieve, k=5):
    """cases: list of (question, set_of_relevant_ids). Empty set = unanswerable."""
    recall = precision = mrr = ndcg = 0.0
    answerable = [c for c in cases if c[1]]
    for q, relevant in answerable:
        ranked = retrieve(q)[:k]
        hits = [1 if r in relevant else 0 for r in ranked]
        recall += any(hits)
        precision += sum(hits) / k
        mrr += next((1 / (i + 1) for i, h in enumerate(hits) if h), 0)
        dcg = sum(h / math.log2(i + 2) for i, h in enumerate(hits))
        ideal = sum(1 / math.log2(i + 2) for i in range(min(len(relevant), k)))
        ndcg += dcg / ideal
    n = len(answerable)
    return {"recall@k": recall / n, "precision@k": precision / n, "mrr": mrr / n, "ndcg@k": ndcg / n}
```

Unanswerable cases are left out of these numbers on purpose; check them separately by whether the final answer says it does not know.

**Break results down.** One overall recall hides problems. Tag each question (exact code, vague, Hindi, multi-part, recent policy) and report recall per tag. A drop on "recent policy" questions after an ingestion change usually means new documents were not indexed.

```python
from collections import defaultdict

def by_tag(cases_with_tags, retrieve, k=5):
    groups = defaultdict(list)
    for q, rel, tag in cases_with_tags:
        groups[tag].append((q, rel))
    return {tag: metrics(cs, retrieve, k)["recall@k"] for tag, cs in groups.items()}
```

**Small sets are noisy.** With 30 questions, one question is more than 3 points. Do not celebrate or panic over a 3-point change; look at which questions flipped and why. Grow the set over time, especially in the tags that matter most.

**Drafting questions with a model.** To get started fast, give a model a passage and ask for two questions it answers, in the words a user would use. A person then edits or rejects each, and records the passage as the expected answer. Mark these as synthetic and keep adding real questions from logs: models tend to reuse the passage's own words, which makes retrieval look easier than it is.

**Retrieval and answers together.** For each case, store the retrieved ids, the answer and the verdicts. Then any wrong answer falls into one of two buckets at a glance: the right passage was missing (retrieval problem) or present (generation problem).

## A worked example

A Kochi bank's internal assistant answers staff questions from 900 circulars. Staff complain that answers are often wrong.

The team writes 60 questions with the circular and paragraph that answer each. Results:

- recall at 5: 63%;
- faithfulness of answers: 0.92;
- correctness: 58%.

Faithfulness is high, so the model mostly says what retrieved passages say. Recall is low: the right passages often never arrive. Looking at the misses, most involve circular numbers ("as per RBI/2026-27/41") and recently revised circulars where older versions outrank new ones.

Changes: hybrid search with keyword matching for circular numbers, and a filter excluding superseded circulars. Recall at 5 rises to 87% and correctness to 81%, measured on the same 60 questions.

| Measure | Before | After hybrid search and the superseded filter |
| --- | --- | --- |
| Recall at 5 | 63% | 87% |
| Faithfulness | 0.92 | 0.93 |
| Correctness | 58% | 81% |

The model was never the problem; it had been faithfully answering from the wrong circulars.

**Reading the misses.** The team did not stop at the numbers. They read all 22 questions where the right passage was missing from the top five, and sorted them into causes: 9 involved circular numbers that the embedding search could not match exactly, 7 retrieved a superseded circular above the current one, 4 were vague questions, and 2 had the wrong expected passage in the test set itself. Each cause pointed to a different fix, and fixing the test set's own mistakes is a normal part of the work.

## Common mistakes

- **Judging only final answers.** You cannot tell whether retrieval or generation failed.
- **Changing the test set between runs.** Keep it fixed to compare.
- **No unanswerable questions.** You need them to test refusals.
- **Trusting automatic judges blindly.** Check a sample.
- **Optimising recall while precision collapses.** Track both.
- **Test sets made of easy questions.** Include vague, multi-part and unanswerable ones, as real users ask them.
- **Changing several things before re-testing.** Change one setting, rerun the set, record the numbers, then change the next.
- **Only synthetic questions**, which use the documents' own wording and flatter retrieval.
- **One overall number.** Break recall down by question type.
- **Mixing unanswerable questions into recall**, which hides both numbers.

## When a lighter check is enough

- **A small prototype**: ten questions checked by hand tell you whether retrieval is broadly working.
- **A collection that rarely changes**, where one careful test at launch plus spot checks may do.
- **Answers that people always verify** against the source before use.

## From demo to production

- **Keep the test set in the repository**, tagged by question type, and run it on every retrieval change.
- **Record recall, precision, MRR and nDCG** with the settings and index version.
- **Add every reported wrong answer** as a new question.
- **Spot-check model-judged scores by hand** each month.
- **Alert when recall drops** on any important tag.
