## What it is

A **trace** records one request from start to finish. It is made of **spans**, one per step: the query rewrite, the retrieval, the reranker, each model call, each tool call. Every span stores its inputs, outputs, start and end times, and for model calls the model name, token counts and cost. Spans nest, so you see that the agent's third tool call happened inside the second model turn.

Ordinary application logs tell you that something happened. Traces of an AI system tell you why it answered what it did. Open-source tools such as Langfuse and Arize Phoenix, commercial ones, and the cloud providers' own tools all store and display traces. Many are built on OpenTelemetry, the common standard for traces.

```text
  trace 8f3a  (one citizen question)                          3.8 s   ₹0.42
  ├─ rewrite_query      0.4 s   in: question    out: search text
  ├─ hybrid_search      0.3 s   out: doc ids + scores
  ├─ rerank             0.2 s   out: reordered ids
  └─ generate           2.9 s   model, tokens in/out, cost, output text
       tags: user=anon-5521  session=s-901  app=2.4.0  prompt=v17
```

This lesson follows a state-government helpdesk assistant in Bhubaneswar that gave a farmer the wrong scheme amount.

## How it works

**Instrument.** Most tools offer a decorator or a wrapper for the model client. Each decorated function becomes a span, and model calls record tokens and cost automatically. Add attributes that help later: user id (or a pseudonymous id), session id, app version, prompt version, the retrieved document ids and their scores.

**Group.** A **session** groups the traces of one conversation; user ids let you look at everything one user experienced.

**Mind the data.** Traces hold prompts and outputs, which can contain personal data. Mask or omit sensitive fields before they are sent, set a retention period, restrict who can view traces and prefer a self-hosted or in-region tool when the client requires it.

**Use them.**

- *Debug*: open the trace for a bad answer. Was the right passage retrieved? Was it in the prompt? Did the model ignore it?
- *Measure*: latency by step, tokens and cost per request, error rates by model.
- *Improve*: save interesting traces to a dataset; they become eval cases.

**Sampling.** At high volume, keep all traces with errors or low feedback, and a sample of the rest.

**What each tool type offers:**

| Option | Strengths | Consider when |
| --- | --- | --- |
| Open-source, self-hosted (Langfuse, Phoenix) | Data stays with you; free to run | The client needs in-region or on-premises data |
| Commercial hosted tools | Less to operate; extra analysis features | Speed matters and data rules allow it |
| Cloud provider's tracing | Fits the existing cloud stack | The app already runs on that cloud |
| Plain OpenTelemetry with your own store | Full control, standard format | You already run observability tooling |

**A weekly trace review.** Set aside thirty minutes each week. Pull traces with poor user feedback, errors or unusually high cost, and a random sample of ordinary ones. For each bad answer, note the failing step: query rewrite, retrieval, reranking, prompt or model. Count the notes. After a few weeks the counts show where engineering effort pays off, and the saved traces become a growing set of eval cases grounded in real use.

**Cost and latency by step.** Because every span records time and tokens, totals by step are easy to chart. Teams are often surprised: a query-rewrite call on a large model can cost more than the answer itself, or a reranker can add more delay than the model does.

## A worked example

A Bhubaneswar state-government helpdesk assistant answers citizens' questions about schemes. An official reports: "It told a farmer the instalment under the state's crop-support scheme is ₹4,000. It is ₹2,000." (The scheme and amounts here are made up for the example.)

You search traces for that session and open the one in question:

```text
trace 8f3a  user=anon-5521  app=2.4.0  prompt=v17   3.8 s  ₹0.42
  rewrite_query        0.4 s   "crop-support scheme instalment amount"
  hybrid_search        0.3 s   top: doc 112 (0.71), doc 87 (0.69), doc 113 (0.66)
  rerank               0.2 s   top: doc 87, doc 112, doc 113
  generate             2.9 s   in 3,210 tok / out 182 tok
```

Doc 87 is a 2019 note about an earlier version of the scheme, with a different amount. It ranked first after reranking, above the current scheme guideline. The model faithfully quoted it. The bug is not the model; it is a stale document without an effective date.

You add `effective_from` metadata and a filter, re-run the trace's query in a test, and save this trace to the golden set so the case is tested from now on. The whole investigation took fifteen minutes because every step was recorded.

| Step in the investigation | Time taken |
| --- | --- |
| Find the session's trace by user and time | 2 minutes |
| See that a 2019 note ranked first | 3 minutes |
| Add effective dates and a filter, re-run the query | 8 minutes |
| Save the trace as a golden-set case | 2 minutes |

## Common mistakes

- **Logging only the final answer.** You cannot tell retrieval failures from generation failures.
- **No version tags.** Without app and prompt versions on traces, you cannot connect a change to a quality drop.
- **Tracing personal data unmasked.** Traces become a sensitive data store. Mask, restrict and expire.
- **Never looking.** Traces are only useful if someone reads them; review a sample every week.
- **Not turning failures into tests.** Every traced bad answer is a ready-made eval case.

## Practise

Read Langfuse's tracing overview and OpenTelemetry's page on traces.

1. Add tracing to your RAG app with a free, self-hostable tool, recording rewrite, retrieval (with document ids and scores), reranking and generation as separate spans.
2. Tag traces with an app version and a prompt version, and mask email addresses and phone numbers before sending.
3. Ask ten questions, find the slowest step and the most expensive request, and save one bad answer's trace as an eval case.

**You are done when you can** open any answer's trace and say which step caused a wrong answer.
