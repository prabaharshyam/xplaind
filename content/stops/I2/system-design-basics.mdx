## What it is

**System design** is deciding how the parts of a software system fit together so it does what users need, at the scale it will face, within its budget. It covers the components (apps, services, databases, caches, queues), how data flows between them, and what happens when something fails.

There is rarely one right answer. A good design is one whose choices fit the requirements and whose trade-offs are stated openly. That is also what interviewers look for: a clear process, sensible numbers and honest trade-offs, more than a perfect diagram.

```text
  1. REQUIREMENTS        2. ESTIMATES            3. HIGH-LEVEL DESIGN
  what must it do?       users, requests/sec,    clients → load balancer
  how fast, how big,     storage, bandwidth      → app servers → cache
  how reliable?          at average and peak      → database, queue, workers
          │                     │                         │
          └─────────────────────┴───────────┬─────────────┘
                                            ▼
           4. DEEP DIVE into the hard parts  →  5. TRADE-OFFS AND FAILURES
           data model, hot paths, scaling       what breaks, what you chose and why
```

## How it works

**1. Clarify requirements.** Split them into **functional** requirements (what the system does, such as "users can book a seat" or "users see order status") and **non-functional** requirements (how well it does it: latency, availability, consistency, scale, cost, security). Ask who the users are, how many there are, and which features are in scope. Write the answers down.

**2. Estimate.** A **back-of-the-envelope estimate** turns users into load. Useful facts: a day has about 1 lakh seconds (86,400), so 1 crore requests a day is about 115 per second; plan for peaks of several times the average. Estimate storage per item times items per day times days kept. These numbers decide whether one database is enough or you need many.

**3. Sketch the high-level design.** Draw the main boxes and arrows: clients, a load balancer, stateless app servers, a cache, a database, object storage for files, and a queue with background workers for slow jobs. Walk one request through it end to end.

**4. Deep dive.** Pick the parts that matter most for this system and go deeper: the data model and its indexes, how to scale the busiest path, how to keep data consistent, or how to handle a sudden spike.

**5. Trade-offs and failures.** Say what each choice costs. A cache speeds reads but can serve stale data; a queue smooths spikes but adds delay; more replicas raise availability but cost more. Ask "what if this box fails?" for each component.

| Non-functional need | Typical numbers | Design levers |
|---|---|---|
| Latency | p95 under 200 ms for a page | caches, CDNs, fewer hops, indexes |
| Throughput | thousands of requests per second | more app servers, load balancing, async work |
| Availability | 99.9% = about 43 min down a month | replicas, health checks, no single point of failure |
| Consistency | strong for payments, eventual for likes | transactions, primary-only reads, idempotency |
| Cost | rupees per lakh requests | right-sized machines, caching, cheaper storage tiers |

## A worked example

Meera is asked in an interview to design the order-status page for a food delivery app in Bengaluru: after ordering, customers see "Preparing", "Picked up" and "Arriving" with the rider's location.

**Requirements.** She asks and confirms: show status and rider location for active orders; updates within about 5 seconds; 20 lakh orders a day, with a dinner peak; history is out of scope. Availability matters more than perfect freshness: showing a location a few seconds old is fine.

**Estimates.** 20 lakh orders a day, each active for about 40 minutes. Riders send a location every 5 seconds, so each order produces about 480 updates: roughly 96 crore updates a day, about 11,000 a second on average and perhaps 40,000 at the dinner peak. Customers refresh the page often, so reads are even higher. Each location update is tiny, about 100 bytes, but she does not need to keep them after delivery.

**High-level design.** Rider apps send locations to an ingestion service behind a load balancer. The latest location per order goes into an in-memory store such as Redis, keyed by order ID, with a short expiry. Order status changes are written to the main database and also published to a queue. Customer apps keep a WebSocket connection open to a notification service, which pushes status and location changes; if the connection drops, the app falls back to polling a read API that reads from Redis.

**Deep dive and trade-offs.** She explains why the high-volume location stream does not go into the main SQL database: it would turn that database into the bottleneck for data nobody needs tomorrow. Status, which matters for refunds and support, does go into the database. She names the trade-off: Redis can lose the last few seconds of locations if a node fails, which is acceptable here, while order status is durable. She closes with failure cases: if the notification service is down, polling still works; if Redis is down, the page shows status without the map.

The interviewer later said what stood out was not the boxes, but that every choice was tied back to a number or a requirement.

## Common mistakes

**Drawing before asking.** Jumping to a diagram without requirements leads to a confident design for the wrong problem. Spend the first few minutes on questions.

**Skipping the numbers.** Without an estimate you cannot say whether one database is enough. Even rough numbers, stated clearly, are better than none.

**Designing for average, not peak.** Sales, results day and Tatkal windows bring many times normal traffic. Size for the peak and say how you would absorb spikes.

**Adding every component you know.** Microservices, Kafka and Kubernetes everywhere make a design harder to run. Add a component only when a requirement needs it.

**Hiding trade-offs.** Every choice has a cost. Saying it out loud shows judgement.

**Forgetting failure.** Ask what happens when each box goes down. Single points of failure are the first thing reviewers look for.
