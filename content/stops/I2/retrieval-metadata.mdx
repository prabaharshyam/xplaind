## What it is

**Metadata** is information about a chunk rather than its text. In RAG it does five jobs:

- **Filters**: restrict a search by state, document type, language or date.
- **Citations**: say exactly where an answer came from (document, section, page, link).
- **Freshness**: answer from the version in force, not last year's.
- **Permissions**: decide who may see a chunk.
- **Better matching**: add context the chunk text lacks, such as the document title or section path.

```flow
Chunk text | "This limit is 45 days." Hard to find on its own -> Stored with metadata | doc: Leave Policy 2026, section: Earned leave > Carry forward, page 4, state KA, access: all-employees
Stored with metadata -> Embedded text | "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days."
Stored with metadata -> Query filter | user's groups, user's state, in force today
Stored with metadata -> Citation | Leave Policy 2026, Karnataka, section 3.2, page 4
```

The catch is that metadata fails silently. A wrong date or a misspelt state does not raise an error at question time; the right chunk just never comes back, and the model answers confidently from the wrong one.

This lesson follows the HR assistant of a Bengaluru IT company serving five states. The exercise moves the same ideas to government orders, where versions and amendments are harder.

## How it works

### Collect it at ingestion

For every chunk, store at least:

| Field | Example | Used for |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations and links |
| `doc_group` | `LP` (all versions and translations) | Linking versions and language copies |
| `section_id`, `section_path`, `page` | 3.2; Earned leave, Carry forward; page 4 | Precise citations, amendments, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | Filters from the user's profile |
| `issued_on` | 2025-12-10 | "The 2019 order" questions |
| `effective_from`, `effective_to` | 2026-01-01, empty | Freshness and history questions |
| `superseded_by` | empty | "Replaced by" notes in answers |
| `language` | `en` | Filters, choosing the copy to show |
| `access_groups` | `all-employees` | Permissions |

Collect it now; adding it later means re-parsing every file.

**Getting it out of PDFs.** Some fields come from the source system (link, owner, access groups). Others must be read from the document itself: order numbers, issue dates and section numbers in headers. Rules (regular expressions for "No." and dates) work for clean digital PDFs; scanned files need OCR and a model, and both make mistakes. Before trusting extracted fields, hand-check a sample of about 50 documents and count the errors per field. Watch dates closely: "03/12/2019" is 3 December in India but 12 March to a parser with US defaults, so state the format explicitly.

### Contextual text

A chunk that says "This limit is 45 days" is hard to retrieve, because nothing in it says *which* limit. Prepend the title and section path to the text you embed: "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days". It costs nothing.

The stronger version is to ask a model to write one or two sentences placing each chunk in its document. Anthropic tested this "contextual retrieval" on its own datasets and reported that it cut the top-20 retrieval failure rate by 35%, by 49% when also applied to keyword (BM25) search, and by 67% with reranking added. It costs one model call per chunk, so measure it on your own golden set.

### Generated metadata

A model can also write a short summary, keywords or the questions a chunk answers. Generated questions help when users phrase things very differently from the documents ("can I carry over my leave?" against "Carry forward of earned leave").

Store each generated question as **its own vector, with the parent chunk's id**. When a question vector matches, return the parent chunk, never the question text, because the model should answer from the real document. Two gotchas: generated questions can promise more than the chunk says, so spot-check a sample; and they go stale, so store a hash of the chunk text and regenerate when it changes.

### Fixed vocabularies, validated in code

Filters compare exact values. "HR", "Human Resources" and "hr dept" are three different departments to a filter. Use fixed lists for departments, document types, states and languages, and check every chunk before it is indexed:

```python
from datetime import date
from typing import Literal
from pydantic import BaseModel, field_validator, model_validator

State = Literal["KA", "TN", "MH", "TS", "GJ", "ALL"]   # the client's five states, plus ALL
DocType = Literal["policy", "circular", "faq", "contract"]

class ChunkMeta(BaseModel):
    doc_id: str
    doc_group: str               # same for every version and translation
    title: str
    section_id: str              # stable id such as "3.2"
    section_path: str
    page: int
    doc_type: DocType
    state: State
    language: Literal["en", "hi", "ta", "kn", "mr", "te", "gu"]
    issued_on: date
    effective_from: date
    effective_to: date | None = None
    superseded_by: str | None = None
    access_groups: list[str]

    @field_validator("access_groups")
    @classmethod
    def not_empty(cls, v):
        if not v:
            raise ValueError("every chunk needs at least one access group")
        return v

    @model_validator(mode="after")
    def dates_in_order(self):
        if self.effective_to and self.effective_to < self.effective_from:
            raise ValueError("effective_to is before effective_from")
        return self
```

Run every chunk through `ChunkMeta.model_validate`, index the ones that pass, and write the failures to a quarantine table with the error. Report quarantine counts on every run. A document tagged "Karnatka" now fails loudly, instead of vanishing from every Karnataka employee's search. The state list must match the client's real list exactly; a state you forgot to add sends all its documents to quarantine.

### Freshness: one "in force" rule

Do not use a simple "current" flag. Use one date rule everywhere: a chunk is **in force during a period** if `effective_from` is on or before the period's end, and `effective_to` is empty or on or after the period's start.

- **Default questions** ("how many leave days can I carry forward?"): the period is today, in Asia/Kolkata time.
- **"What was the rule in 2024?"**: the period is 1 January to 31 December 2024. A policy in force from 2023 to 2025 comes back, even though it started before 2024 and is superseded now.
- **"What did the 2019 order say?"**: this asks about the order *issued* in 2019, so filter on the year of `issued_on` and ignore whether it is still in force.

One gotcha: a policy announced in December for 1 January is not yet in force. A question about "next year's policy" needs the next year as the period, or the default rule hides it.

When a new version replaces a whole document, close the old one in the same transaction, so no search ever sees both or neither:

```sql
BEGIN;
UPDATE chunks SET superseded_by = 'HR-LP-2026', effective_to = '2025-12-31'
WHERE doc_id = 'HR-LP-2025';
INSERT INTO chunks (...) VALUES (...);   -- the new version's chunks
COMMIT;
```

The date rule does the filtering. `superseded_by` is kept so the answer can say "replaced by Leave Policy 2026".

### Partial amendments

Real documents are often changed one part at a time. A government order may say "in paragraph 4 of order 112/2019, for 'Rs 300' substitute 'Rs 450'", and leave every other paragraph in force. A whole-document "superseded" flag cannot express this. Mark the old order superseded and its other paragraphs vanish; leave it and the old rate keeps winning.

Model amendments at section level:

- Every chunk carries a stable `section_id` (paragraph 4, clause 3.2).
- An amendments table records `amending_doc`, `amended_doc`, `section_id` and the date it takes effect.
- When an amendment takes effect, end the `effective_to` of only the amended section, and leave the rest.
- At query time, when a base section is retrieved, also fetch every amendment to it, sorted by date, and give the model both.

This matters because neither chunk works alone. The amendment says "substitute 'Rs 450'" without saying what for; the base paragraph is out of date. The answer should cite both: "order 112/2019, paragraph 4, as amended by order 37/2022". If the department publishes consolidated versions, index those too, but keep the chain for citations.

Amendment links are themselves extracted metadata. Phrases like "in partial modification of" or "in supersession of" followed by an order number are good starting rules, but check them on a sample, as with any extracted field.

### Translations

A Hindi order and its English copy are one document in two languages, not two documents. Give both the same `doc_group` and `section_id`. In results, keep one chunk per document group and section, and show the copy in the user's language. Otherwise the top five results waste two places on the same paragraph twice. Ask the department which copy is authoritative when they differ, record it, and cite that one.

### Permissions, kept in sync

Store **group ids** on chunks (`finance`, `all-employees`), not user ids, and apply the filter inside the search so a forbidden chunk never reaches the model. Two syncs need separate schedules:

- **Document permissions** change in the source system (a file is reshared). Re-sync them often, as a metadata update; you do not need to re-embed the text.
- **User groups** change when people move teams. Read the user's groups from the identity system at query time, or cache them for minutes, not days. A cached group list is how someone who left Finance keeps seeing Finance circulars.

### Filters from the question

Some filters come from the user's profile (their state, their groups). Others are inferred from the question by a small model. A wrong inferred filter hides the right answer, so apply them conservatively:

```python
STATE_NAMES = {"KA": "Karnataka", "TN": "Tamil Nadu", "MH": "Maharashtra",
               "TS": "Telangana", "GJ": "Gujarat"}

class Filters(BaseModel):            # structured output from a small model
    state: Literal["KA", "TN", "MH", "TS", "GJ"] | None = None  # a real state, never ALL
    state_named: bool = False         # true only if the question names the state itself
    in_force_year: int | None = None  # "what was the rule in 2024?"
    issued_year: int | None = None    # "the 2019 order on transfers"
    doc_type: DocType | None = None

def in_force(start: date, end: date) -> dict:
    """In force at any time from start to end."""
    return {"effective_from": {"$lte": end},
            "$or": [{"effective_to": None}, {"effective_to": {"$gte": start}}]}

def build_filters(f: Filters, user, today: date):
    if f.state and f.state != user.state and not f.state_named:
        return None, f"Do you mean the {STATE_NAMES[f.state]} documents?"
    where = {"access_groups": {"$in": user.groups},           # never dropped
             "state": {"$in": [f.state or user.state, "ALL"]}}
    if f.in_force_year:
        y = f.in_force_year
        where |= in_force(date(y, 1, 1), date(y, 12, 31))
    elif f.issued_year:
        y = f.issued_year
        where["issued_on"] = {"$gte": date(y, 1, 1), "$lte": date(y, 12, 31)}
    else:
        where |= in_force(today, today)                       # default
    if f.doc_type:
        where["doc_type"] = f.doc_type
    return where, None
```

The filter syntax is generic; translate it to your vector store's. Pass `today` as the date in Asia/Kolkata, not the server's UTC date. If a filtered search returns nothing, retry once with only the access filter and the user's state, show the dates of whatever it cites, and log the empty search. Never drop the access filter in a retry.

### Filters and search speed

Filters interact with approximate vector indexes. In pgvector, for example, the filter is applied *after* the index scan by default. Its documentation gives the example of a filter matching 10% of rows: with an HNSW index and the default `hnsw.ef_search` of 40, only about 4 rows survive on average, so you get fewer results than you asked for. From version 0.8.0 you can turn on iterative index scans (`SET hnsw.iterative_scan = relaxed_order`), which scan more of the index until enough rows pass or a scan limit (`hnsw.max_scan_tuples`) is reached, and for a field with only a few distinct values pgvector suggests a partial index per value. Other stores differ, so test your most selective filter (a small state, a rare document type) and check it still returns a full top-k.

### Check the payoff

Measure recall at 5 on your golden set with and without each addition (contextual text, generated questions, inferred filters), and keep only what helps. Include history and other-state questions, since that is where filters go wrong.

## A worked example

The Bengaluru IT company's HR assistant serves employees in Karnataka, Tamil Nadu, Maharashtra, Telangana and Gujarat. Leave and holiday rules differ by state, and policies are revised each year.

**Before:** chunks carried only the file name. The assistant mixed Karnataka and Maharashtra holiday lists and sometimes quoted last year's policy. A first fix added a `current = true` filter, and then "what was the carry-forward limit in 2024?" returned nothing at all.

**After re-ingestion:** each chunk carries the fields in the table above. The state and groups come from the employee's sign-on profile. The date rule defaults to today; a named year switches it to that year. Embedded text starts with the title and section path. The numbers below are an illustration of the kind of change to expect, not a measured result:

| Suppose, on 100 golden questions | Before | After |
| --- | --- | --- |
| Correct answers | 71 | 90 |
| Answers quoting the wrong state | 9 | 0 |
| Answers quoting last year's policy | 7 | 1 |
| Other wrong answers | 13 | 9 |
| Citation format | File name only | Document, state, section, page |

Citations now read "Leave Policy 2026, Karnataka, section 3.2, page 4", and HR staff can check them in seconds.

**How the filter decisions work.** Priya in Bengaluru asks "how many holidays in October?". The assistant applies `state = KA` from her profile and in force today. She then asks "holidays in Pune office in October". The small model maps Pune to Maharashtra, but she did not name the state, so `build_filters` returns a question: "Do you mean the Maharashtra documents?" Asking costs one tap; a wrong silent filter costs a wrong answer. If she had typed "Maharashtra holidays", the filter would apply directly.

When she asks "what was the carry-forward limit in 2024?", the model returns `in_force_year = 2024`. The 2023 to 2025 policy, superseded since January 2026, matches the date rule and comes back, with the note "replaced by Leave Policy 2026".

## Common mistakes

- **Only a file name.** You cannot filter, cite properly or handle versions.
- **Free-text metadata values.** "HR", "Human Resources" and "hr dept" break filters. Use fixed lists and validate them.
- **A vocabulary that misses a real value.** One forgotten state quarantines all its documents, or worse, indexes them without a state.
- **A "current only" filter on every search.** History questions then return nothing. Use the in-force rule with the period the question asks about.
- **Whole-document supersession for partial amendments.** It either hides paragraphs still in force or keeps old values. Track amendments per section.
- **Translations as separate documents.** Duplicate paragraphs crowd out other results.
- **Aggressive inferred filters.** Prefer the user's profile, and ask when an inferred filter changes it.
- **A fallback that drops the access filter.** An empty result must never widen what a user may see.
- **Stale group lists.** Access is decided by the user's groups at query time, so read them fresh.
- **Generating metadata without measuring.** It costs a model call per chunk; prove it helps.

## When little metadata is needed

- **A small, single-topic collection** with one version of each document.
- **Everyone may see everything**, and nothing goes out of date.
- **A prototype** testing whether retrieval helps at all.

Even then, store the document id, section and page: citations need them, and they cost nothing. Rich metadata pays off once there are many document types, versions, regions or permission groups.

## From demo to production

- **Hand-check extracted fields** on a sample whenever the parser or document format changes.
- **Log the filters applied** to each search, including inferred ones and fallbacks.
- **Re-sync permissions** on their own schedule, separate from re-embedding.
- **Review vocabularies** (states, document types, departments) with the content owners.
