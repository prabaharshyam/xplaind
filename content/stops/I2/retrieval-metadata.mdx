## What it is

**Metadata** is information about a chunk rather than its text. In RAG it does five jobs:

- **Filters**: restrict searches by product, region, document type, language or date.
- **Citations**: say exactly where an answer came from (document, section, page, link).
- **Freshness**: prefer or require current versions, drop superseded ones.
- **Permissions**: decide who may see a chunk.
- **Better matching**: add context the chunk text lacks, such as the document title or section path.

```text
  chunk text:  "This limit is 45 days."         <- hard to find on its own

  stored with it:
  +-------------------------------------------------------------+
  | doc: Leave Policy 2026 (v4)     type: policy   lang: en     |
  | section: Leave Policy > Earned leave > Carry forward        |
  | page: 4    state: KA    effective: 2026-01-01 to (open)     |
  | superseded_by: none     access: all-employees               |
  +-------------------------------------------------------------+

  embedded text: "Leave Policy 2026 > Earned leave > Carry forward: This limit is 45 days."
  query filter:  state = user's state AND not superseded AND access in user's groups
```

This lesson follows an HR assistant at an IT company in Bengaluru serving employees in five states.

## How it works

**Collect at ingestion.** For every chunk store at least:

- document id, title, source system and link;
- section path ("Leave Policy > Earned leave > Carry forward") and page;
- document type (policy, circular, FAQ, contract);
- dates: published, effective from, effective to, last modified;
- language;
- owner or department;
- access groups.

**Contextual text.** A chunk that says "This limit is 45 days" is hard to retrieve. Prepend the title and section path to the text that gets embedded ("Leave Policy v4 > Earned leave > Carry forward: This limit is 45 days"), or have a model write a one-sentence context for each chunk. This kind of contextual enrichment can cut retrieval failures noticeably.

**Generated metadata.** A model can add a short summary, keywords or questions each chunk answers. Embedding likely questions helps when users phrase things very differently from the documents. It costs a model call per chunk at ingestion, so measure the gain on your golden set first.

**Filters from the query.** Some filters come from the user's context (their region, their access groups). Others can be inferred from the question with a small model ("leave rules for Karnataka from 2026" becomes region = KA, effective after 2026-01-01). Infer conservatively: a wrong filter hides the right answer.

**Freshness rules.** Store effective dates and a "superseded by" link. Filter out superseded documents by default, unless the user asks about history.

**Consistency.** Use fixed vocabularies (department names, document types, region codes) so filters match. Validate metadata at ingestion like any other data.

**A chunk record in practice:**

| Field | Example | Used for |
| --- | --- | --- |
| `doc_id`, `title`, `url` | `HR-LP-2026`, Leave Policy 2026 | Citations and links |
| `section_path`, `page` | Earned leave, Carry forward; page 4 | Precise citations, contextual text |
| `doc_type` | `policy` | Filters |
| `state` | `KA` | Filters from the user's profile |
| `effective_from`, `effective_to` | 2026-01-01, open | Freshness |
| `superseded_by` | none | Dropping old versions |
| `language` | `en` | Filters, choosing analysers |
| `access_groups` | `all-employees` | Permissions |

**Validating metadata.** Treat metadata like any other data. At ingestion, check that required fields exist, that values come from the fixed lists, and that effective dates make sense, such as an end date after a start date. Reject or quarantine chunks that fail, and report counts per run. A single document tagged "Karnatka" instead of "KA" silently disappears from every Karnataka employee's search.

## A worked example

A Bengaluru IT company's HR assistant serves employees in five states. Leave and holiday rules differ by state, and policies are revised each year.

Before: chunks carried only the file name. The assistant mixed Karnataka and Maharashtra holiday lists and sometimes quoted last year's policy.

After re-ingestion, each chunk carries state, policy type, effective dates, version, section path and access groups. The employee's state comes from their sign-on profile and is applied as a filter unless they ask about another state. Superseded versions are excluded by default. Embedded text starts with the title and section path.

On the 100-question golden set, correct answers rise from 71% to 90%. Citations now read "Leave Policy 2026, Karnataka, section 3.2, page 4", and HR staff can check them in seconds.

| Measure on 100 questions | Before | After |
| --- | --- | --- |
| Correct answers | 71% | 90% |
| Answers quoting the wrong state | 9 | 0 |
| Answers quoting last year's policy | 7 | 1 |
| Citation format | File name only | Document, state, section, page |

**How the filter decision works.** When an employee in Bengaluru asks "how many holidays in October?", the assistant applies `state = KA` from their sign-on profile. When they ask "holidays in Pune office in October", a small model spots the different state, and the assistant asks "Do you mean the Maharashtra holiday list?" before filtering. Asking costs one tap; a wrong silent filter would have cost a wrong answer.

## Common mistakes

- **Only a file name.** You cannot filter, cite properly or handle versions.
- **Free-text metadata values.** "HR", "Human Resources" and "hr dept" break filters. Use fixed lists.
- **No effective dates.** Old versions keep winning.
- **Aggressive inferred filters.** A wrongly inferred filter hides the right answer; prefer user context and ask when unsure.
- **Generating metadata without measuring.** It costs money at ingestion; prove it helps.
