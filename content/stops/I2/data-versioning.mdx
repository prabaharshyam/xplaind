## What it is

**Data versioning** keeps track of versions of datasets (and the steps that produce them) the way Git tracks code. Each training run records which data version it used, so you can:

- reproduce any past model exactly;
- see what changed between two dataset versions;
- roll back to a previous dataset if a new one is broken;
- show auditors the data behind a decision.

Large files do not belong directly in Git. Tools such as DVC store the data in cloud storage and keep small pointer files in Git. Data lakes and warehouses offer table versioning ("time travel") too.

```flow
Raw data from sources -> Build the dataset
Pipeline code | Git commit a1b2c3 -> Build the dataset
Build the dataset -> Data v2026-10-01 | manifest: rows, hash, query, commit
Data v2026-10-01 -> Training run 412 | logs the data and code versions
Training run 412 -> Model registry: fraud-model v7 -> Production predictions
```

Lineage runs the other way: any prediction → model v7 → run 412 → data v2026-10-01 → commit a1b2c3.

This lesson follows a health-insurance company in Chennai whose fraud model got worse after retraining.

## How it works

**Snapshot the inputs.** Treat training datasets as immutable snapshots with an id: a content hash, a date-stamped path, or a tool-managed version. Never overwrite a dataset in place.

**Version the pipeline too.** The code that turns raw data into training data (filters, joins, labels, feature computation) is versioned in Git. A data version is the output of a specific pipeline version run on specific raw data.

**Record lineage.** Each training run logs the data version id; each model in the registry links to its run. From a production prediction you can walk back to the exact data.

**Compare versions.** Row counts, label balance, feature distributions, schema changes and sample diffs between versions. Review big changes like code changes.

**Labels change too.** Corrected labels, new labelling guidelines and late-arriving outcomes change datasets. Version them and note why.

**Privacy and deletion.** Versioned data still contains personal data. Retention rules and erasure requests under the DPDP Act apply to old versions as well; plan how deletion propagates, for example by rebuilding affected versions without the deleted records and documenting it.

**Keep it practical.** For small teams, dated folders in cloud storage with a manifest (row counts, hash, source query, pipeline commit) plus logging the path in each run may be enough. Adopt a tool as volume and team size grow.

**A manifest for each dataset version:**

| Field | Example |
| --- | --- |
| Version id | `claims-train-2026-10-01` |
| Content hash | `sha256:9f2c...` |
| Rows | 812,440 |
| Positive label share | 2.3% |
| Source query or tables | `claims_v3 joined with investigations` |
| Pipeline commit | `a1b2c3d` |
| Created by and date | `pipeline-bot, 2026-10-01` |
| Notes | "Relabelled 1,200 claims after the audit of July" |

Write the manifest automatically when the dataset is built, store it next to the data, and print a comparison with the previous manifest in the pull request that triggered the build. A reviewer who sees "positive label share: 2.3% to 1.1%" asks the right question before training starts.

**Choosing a tool.** For a team of two or three, dated folders and a manifest are enough. DVC adds pointer files in Git and commands to pull and push data, which helps once several people train models. Lakehouse table formats such as Delta Lake and Apache Iceberg add "time travel", so you can query a table as it was on a given date, which suits teams whose training data already lives in a warehouse. Whatever you choose, the rule is the same: a training run must record exactly which data version it used, and that version must never change afterwards.

**Write the manifest automatically.** A few lines at the end of the dataset build:

```python
import hashlib, json, subprocess
from datetime import datetime
from zoneinfo import ZoneInfo
from pathlib import Path

def file_hash(path, chunk=1 << 20):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while block := f.read(chunk):
            h.update(block)
    return "sha256:" + h.hexdigest()

def write_manifest(data_path, df, label_col, notes=""):
    commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"], capture_output=True, text=True).stdout.strip()
    manifest = {
        "version": Path(data_path).stem,
        "hash": file_hash(data_path),
        "rows": int(len(df)),
        "positive_share": round(float(df[label_col].mean()), 4),
        "columns": list(df.columns),
        "pipeline_commit": commit,
        "created": datetime.now(ZoneInfo("Asia/Kolkata")).isoformat(timespec="seconds"),
        "notes": notes,
    }
    Path(data_path).with_suffix(".manifest.json").write_text(json.dumps(manifest, indent=2))
    return manifest
```

**Compare with the previous version, and fail on surprises.**

```python
def compare(old, new, max_share_change=0.3, max_row_change=0.2):
    problems = []
    if set(old["columns"]) != set(new["columns"]):
        problems.append(f"columns changed: {set(old['columns']) ^ set(new['columns'])}")
    if abs(new["rows"] - old["rows"]) / old["rows"] > max_row_change:
        problems.append(f"rows {old['rows']} -> {new['rows']}")
    rel = abs(new["positive_share"] - old["positive_share"]) / max(old["positive_share"], 1e-9)
    if rel > max_share_change:
        problems.append(f"positive share {old['positive_share']:.2%} -> {new['positive_share']:.2%}")
    return problems
```

Print the comparison in the pull request that built the data. A failure is not always wrong, but someone must explain it in the notes before training.

**DVC in four commands.** Data stays in cloud storage; Git tracks small pointer files:

```bash
dvc init
dvc remote add -d store s3://my-bucket/dvc       # or Azure, GCS, a shared drive
dvc add data/claims-train-2026-10-01.parquet     # writes a .dvc pointer file
git add data/*.dvc .gitignore && git commit -m "Training data 2026-10-01" && dvc push
```

Anyone can then `git checkout` a commit and `dvc pull` to get exactly that data.

**Time travel in a lakehouse.** If training data lives in Delta Lake tables, record the table version with each run and read it back exactly:

```sql
SELECT * FROM claims_train VERSION AS OF 42;
SELECT * FROM claims_train TIMESTAMP AS OF '2026-10-01T00:00:00+05:30';
```

Old versions are removed by cleanup jobs after a retention period, so keep that period longer than you need to reproduce models, or export important snapshots.

**Erasure across versions.** When a person asks for erasure, find every dataset version containing their records (keep an index of record ids per version), rebuild those versions without them, and note it in each manifest. Decide with the privacy lead whether models trained on the old versions must be retrained.

## A worked example

A Chennai health-insurance company retrains its claim-fraud model and finds recall dropped from 0.72 to 0.61.

Because data is versioned with DVC, the team compares the new dataset with the previous one:

- 14% fewer positive labels, although fraud cases had not fallen;
- the label query had changed: a refactor of the pipeline now excluded claims under investigation, which made up much of recent fraud.

They fix the pipeline, rebuild the dataset as a new version, retrain and recover recall of 0.73. The pull request for the original refactor is updated with a data check that fails if the positive label share changes by more than 20% between versions without an explanation.

Later, a customer's erasure request requires deleting their records. The team rebuilds the affected training versions without them, records the change, and confirms the rebuilt model's metrics are unchanged.

**What the team kept.** The fix took a day because the evidence was already there: two manifests side by side showed the label share change, and the pipeline commit in each manifest pointed straight at the refactor. Without versioning, the same investigation usually takes weeks of guessing, or never happens, and the weaker model quietly ships.

## Common mistakes

- **Overwriting datasets in place.** You lose the ability to compare or reproduce. Always write a new version with a new id, even for a one-row fix.
- **Versioning data but not the pipeline.** You cannot explain how data was produced.
- **No link from model to data.** Log the data version in every run.
- **Ignoring label changes.** They change models as much as feature changes.
- **Forgetting privacy in old versions.** Retention and erasure apply to every copy.
- **Manifests written by hand**, which drift from the real data.
- **No check on label share or row counts** between versions.
- **Forgetting old versions in erasure requests.**

## When versioning can stay simple

- **Prompt-only AI apps with no training data**: version prompts, test sets and indexes instead.
- **One person, one small dataset**: a dated folder with a manifest is enough.
- **Data that never changes**, such as a fixed public benchmark: record its name and hash once.

## From demo to production

- **Make dataset versions immutable** and log the version with every training run.
- **Write and compare manifests automatically** in CI.
- **Link models to data versions** in the model registry.
- **Index record ids per version** so erasure requests can be honoured.
- **Set retention** for old versions longer than your reproducibility needs.
