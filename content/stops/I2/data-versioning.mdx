## What it is

**Data versioning** keeps track of versions of datasets (and the steps that produce them) the way Git tracks code. Each training run records which data version it used, so you can:

- reproduce any past model exactly;
- see what changed between two dataset versions;
- roll back to a previous dataset if a new one is broken;
- show auditors the data behind a decision.

Large files do not belong directly in Git. Tools such as DVC store the data in cloud storage and keep small pointer files in Git. Data lakes and warehouses offer table versioning ("time travel") too.

## How it works

**Snapshot the inputs.** Treat training datasets as immutable snapshots with an id: a content hash, a date-stamped path, or a tool-managed version. Never overwrite a dataset in place.

**Version the pipeline too.** The code that turns raw data into training data (filters, joins, labels, feature computation) is versioned in Git. A data version is the output of a specific pipeline version run on specific raw data.

**Record lineage.** Each training run logs the data version id; each model in the registry links to its run. From a production prediction you can walk back to the exact data.

**Compare versions.** Row counts, label balance, feature distributions, schema changes and sample diffs between versions. Review big changes like code changes.

**Labels change too.** Corrected labels, new labelling guidelines and late-arriving outcomes change datasets. Version them and note why.

**Privacy and deletion.** Versioned data still contains personal data. Retention rules and erasure requests under the DPDP Act apply to old versions as well; plan how deletion propagates, for example by rebuilding affected versions without the deleted records and documenting it.

**Keep it practical.** For small teams, dated folders in cloud storage with a manifest (row counts, hash, source query, pipeline commit) plus logging the path in each run may be enough. Adopt a tool as volume and team size grow.

## A worked example

A Chennai health-insurance company retrains its claim-fraud model and finds recall dropped from 0.72 to 0.61.

Because data is versioned with DVC, the team compares the new dataset with the previous one:

- 14% fewer positive labels, although fraud cases had not fallen;
- the label query had changed: a refactor of the pipeline now excluded claims under investigation, which made up much of recent fraud.

They fix the pipeline, rebuild the dataset as a new version, retrain and recover recall of 0.73. The pull request for the original refactor is updated with a data check that fails if the positive label share changes by more than 20% between versions without an explanation.

Later, a customer's erasure request requires deleting their records. The team rebuilds the affected training versions without them, records the change, and confirms the rebuilt model's metrics are unchanged.

## Common mistakes

- **Overwriting datasets in place.** You lose the ability to compare or reproduce.
- **Versioning data but not the pipeline.** You cannot explain how data was produced.
- **No link from model to data.** Log the data version in every run.
- **Ignoring label changes.** They change models as much as feature changes.
- **Forgetting privacy in old versions.** Retention and erasure apply to every copy.

## Practise

Follow DVC's get-started guide and the data versioning lesson of Made With ML.

1. Put a dataset under version control with DVC (or dated, hashed folders with a manifest) and link it to a training run.
2. Change the data (add rows, fix labels), create a new version, and write a comparison report between versions.
3. Add a data check that fails when the label share changes beyond a threshold.

**You are done when you can** reproduce a past model from its recorded code and data versions, and explain the difference between two dataset versions.
